# Composition API

Как устроен компонент на Composition API: функция `setup` и `<script setup>`, хуки жизненного цикла и их порядок, макросы компилятора, закрытость компонента — и чем это отличается от Options API. Спрашивают, что делает `<script setup>`, когда выполняется `setup` и чем Composition API лучше Options API. Глубже — в каком порядке срабатывают хуки родителя и ребёнка, почему хук после `await` не работает и почему родитель не видит методы ребёнка.

::tldr
- **`setup` выполняется один раз при создании компонента,** а не на каждый рендер, как функция-компонент в React. Поэтому хуки во Vue можно вызывать по условию, а замыкания не устаревают.
- **`<script setup>` — сахар над `setup()`:** всё, что объявлено на верхнем уровне, доступно шаблону, а макросы `defineProps`, `defineEmits`, `defineModel` компилятор превращает в опции компонента.
- **Хуки жизненного цикла регистрируются синхронно, пока выполняется `setup`.** После `await` в обычном `setup()` экземпляра уже нет, и хук молча не сработает. `<script setup>` восстанавливает экземпляр сам.
- **Родитель монтируется последним, а размонтирование начинается с него:** `mounted` ребёнка срабатывает раньше `mounted` родителя.
- **Компонент на `<script setup>` закрыт:** через ссылку на шаблон родитель видит только то, что отдано через `defineExpose`.
::

## Что такое Composition API

Composition API — набор функций (`ref`, `computed`, `watch`, `onMounted`), из которых собирается логика компонента. Главная идея — **код группируется по задаче**, а не по типу.

Сквозной пример — карточка товара с загрузкой и счётчиком:

```vue
<script setup>
import { ref, computed, onMounted } from 'vue';

const props = defineProps({ id: Number });

const product = ref(null);
onMounted(async () => {
  product.value = await fetch(`/api/products/${props.id}`).then((r) => r.json());
});

const qty = ref(1);
const total = computed(() => (product.value?.price ?? 0) * qty.value);
</script>

<template>
  <article v-if="product">
    <h3>{{ product.title }}</h3>
    <input v-model.number="qty" type="number" min="1">
    <p>{{ total }} ₽</p>
  </article>
</template>
```

Всё, что относится к загрузке, стоит рядом; всё, что относится к количеству, — тоже. Любой из этих кусков можно вынести в функцию-композабл и переиспользовать (подробно — в [Композаблах](/content/vuejs/composables)).

Откуда шаблон знает про `qty` и `total`, если мы ничего не возвращали?

## setup и script setup

`<script setup>` — сахар над опцией `setup()`. Компилятор превращает блок в функцию `setup`, а переменные верхнего уровня делает доступными шаблону. Без сахара то же выглядит так:

```js
export default {
  props: { id: Number },
  setup(props) {
    const qty = ref(1);
    const total = computed(() => /* … */);
    return { qty, total };   // явно отдаём шаблону
  },
};
```

### setup выполняется один раз

Это главное отличие от функции-компонента React. В React функция компонента вызывается на **каждый** рендер, и состояние живёт в ячейках хуков (подробно — в [Механике хуков](/content/reactjs/hooks-mechanics)). Во Vue `setup` вызывается **один раз** при создании экземпляра, а перерисовывает компонент render-функция — отдельно. В проверке после трёх кликов `setup` выполнился один раз, а рендер — четыре.

Следствия:

- **Хуки можно вызывать по условию и в цикле.** Правил хуков React во Vue нет: `if (props.track) onMounted(…)` работает, потому что порядок вызовов не важен.
- **Замыкания не устаревают.** Обработчик, созданный в `setup`, читает `qty.value` в момент вызова и видит актуальное значение.
- **В `setup` нет `this`.** Экземпляр ещё создаётся, а состояние держат ref, а не свойства объекта. Пропсы приходят первым аргументом, а `emit`, `attrs`, `slots`, `expose` — вторым (`setup(props, { emit })`).

### Что ещё делает script setup

- импортированные компоненты используются в шаблоне без регистрации;
- переменная `vFocus` становится директивой `v-focus`;
- компонент **закрыт** — о чём ниже;
- `await` на верхнем уровне делает компонент асинхронным, его показывают внутри `Suspense` (подробно — во [Встроенных компонентах](/content/vuejs/built-in-components)).

`setup` создал состояние. Но некоторая работа должна произойти позже — когда компонент появится в DOM.

## Жизненный цикл

На этапы жизни компонента подписываются функциями `onX`:

| Composition API | Options API | Когда |
| --- | --- | --- |
| сам `setup` | `beforeCreate`, `created` | создание экземпляра |
| `onBeforeMount` | `beforeMount` | перед первой вставкой в DOM |
| `onMounted` | `mounted` | элементы в DOM: измерения, подписки на DOM, сторонние библиотеки |
| `onBeforeUpdate` | `beforeUpdate` | перед перерисовкой |
| `onUpdated` | `updated` | после перерисовки |
| `onBeforeUnmount` | `beforeUnmount` | перед удалением |
| `onUnmounted` | `unmounted` | удалён — отписки, таймеры |
| `onErrorCaptured` | `errorCaptured` | ошибка в потомке |
| `onActivated`, `onDeactivated` | `activated`, `deactivated` | показ и скрытие внутри `KeepAlive` |
| `onServerPrefetch` | `serverPrefetch` | загрузка данных при SSR |

### Порядок родителя и ребёнка

Родитель начинает первым, а заканчивает последним:

```text
монтирование:      parent:setup → parent:beforeMount → child:setup → child:beforeMount
                   → child:mounted → parent:mounted
размонтирование:   parent:beforeUnmount → child:beforeUnmount → child:unmounted → parent:unmounted
```

Родитель смонтирован, только когда смонтированы все дети: в его `onMounted` DOM детей уже существует. Это проверено на логе хуков. Отсюда частый вопрос «почему `mounted` ребёнка сработал раньше родителя» — так и должно быть.

### Хуки и await

Хук регистрируется в **текущем экземпляре** — том, чей `setup` выполняется прямо сейчас. Vue знает его, пока `setup` выполняется синхронно. После `await` выполнение продолжится в микрозадаче, когда текущего экземпляра уже нет:

```js
export default {
  async setup() {
    const data = await load();
    onUnmounted(() => clearInterval(timer));   // не зарегистрируется
  },
};
```

Vue предупредит «onMounted is called when there is no active component instance», и хук не сработает — в проверке так и было. Правило: **хуки регистрируют до первого `await`**.

В `<script setup>` эта проблема решена: компилятор оборачивает верхнеуровневый `await` в `withAsyncContext`, который восстанавливает экземпляр после ожидания. В проверке `onMounted` после `await` в `<script setup>` сработал.

### Хуки или watch

Хуки жизненного цикла во Vue — явные этапы жизни, а не синхронизация, как `useEffect` в React. Реакция на изменение данных — это `watch` (подробно — в [Computed и наблюдателях](/content/vuejs/computed-and-watchers)), а `onUpdated` нужен редко: он срабатывает после любой перерисовки, а не после изменения конкретных данных.

## Макросы компилятора

В `<script setup>` есть функции, которые не импортируют: их обрабатывает компилятор, а в рантайме их нет.

| Макрос | Во что превращается |
| --- | --- |
| `defineProps` | опция `props` |
| `defineEmits` | опция `emits` и функция `emit` |
| `defineModel` | проп `modelValue`, событие `update:modelValue` и ref |
| `defineExpose` | вызов `expose` — что видно родителю |
| `defineOptions` | опции компонента: `name`, `inheritAttrs` |
| `defineSlots` | только типы слотов |
| `withDefaults` | значения по умолчанию для пропсов из типа |

В проверке вывод компилятора не содержал вызовов макросов: `defineProps({ title: String })` стал `props: { title: String }`, `defineOptions` — опциями `name` и `inheritAttrs`. Если вызвать макрос вне `<script setup>`, Vue предупредит: `defineProps() is a compiler-hint helper that is only usable inside <script setup>`.

Раз макросы раскрывает компилятор, их аргументы должны быть **статически понятны**: нельзя передать в `defineProps` переменную, объявленную в том же блоке. Типы пропсов и событий — в [TypeScript с Vue](/content/typescript/ts-with-vue), использование — в [Связи компонентов](/content/vuejs/components-communication).

### Закрытый компонент

Компонент на `<script setup>` по умолчанию **закрыт**: через ссылку на шаблон родитель получает экземпляр, в котором нет внутренних переменных. Что открыть, решает компонент:

```vue
<!-- ProductForm.vue -->
<script setup>
import { ref } from 'vue';

const input = ref(null);
const draft = ref('');
function focus() { input.value.focus(); }

defineExpose({ focus });
</script>
```

```vue
<!-- Родитель -->
<script setup>
import { useTemplateRef } from 'vue';

const form = useTemplateRef('form');
form.value?.focus();   // доступно
form.value?.draft;     // undefined
</script>

<template>
  <ProductForm ref="form" />
</template>
```

В проверке родитель вызвал `focus()`, а `secret` оказался `undefined`. Компонент с обычным `setup()` без `expose` открыт целиком. Закрытость — это граница API: родитель зависит только от того, что компонент обещал.

## Options API

До Vue 3 и в легаси-проектах компоненты пишут опциями:

```js
export default {
  props: { id: Number },
  data() {
    return { product: null, qty: 1 };
  },
  computed: {
    total() { return (this.product?.price ?? 0) * this.qty; },
  },
  async mounted() {
    this.product = await fetch(`/api/products/${this.id}`).then((r) => r.json());
  },
};
```

- **`data` — функция,** чтобы у каждого экземпляра был свой объект;
- **всё — через `this`:** пропсы, данные, `computed`, методы смешаны в одном экземпляре;
- **логика задачи разложена по опциям:** загрузка в `mounted`, состояние в `data`, производное в `computed`.

Options API поддерживается, и стили можно смешивать: то, что вернул `setup()`, доступно через `this` в опциях. В проверке `this.fromSetup` читался в render-функции рядом с `data` и `computed`.

### Миксины

Логику в Options API переиспользовали **миксинами** — объектами опций, которые подмешиваются в компонент:

```js
export default {
  mixins: [counterMixin, fetchMixin],
  // откуда взялись this.count и this.load? из какого миксина?
};
```

Проблемы:

- **неявный источник:** по компоненту не видно, какое свойство пришло из какого миксина;
- **конфликты имён молчаливые:** если миксин и компонент объявили одно поле в `data`, побеждает компонент, без предупреждения — в проверке `label` компонента перекрыл миксин;
- **связи между миксинами неявные:** один миксин читает свойство другого через `this`.

Те же проблемы были у HOC в React, и решение похожее — функции, которые явно возвращают своё состояние. Во Vue это композаблы.

### Сравнение

| | Options API | Composition API |
| --- | --- | --- |
| Организация | по типу опции | по задаче |
| Переиспользование | миксины: неявный источник, конфликты | композаблы: явный импорт и возврат |
| TypeScript | слабый вывод через `this` | обычные функции и переменные |
| Доступ к состоянию | `this` | переменные в замыкании |
| Порог входа | ниже для маленьких компонентов | ниже для сложных |

Для нового кода — Composition API с `<script setup>`. Options API остаётся рабочим, его не удаляют.

## Красные флаги в ответе

- **«`setup` вызывается на каждый рендер».** Один раз при создании экземпляра, перерисовывает render-функция.
- **«Хуки Vue нельзя вызывать по условию, как в React».** Можно: `setup` выполняется один раз, порядок вызовов не важен.
- **«`onMounted` после `await` работает».** В обычном `setup()` нет: экземпляр потерян. Работает только в `<script setup>`.
- **«`mounted` родителя срабатывает раньше детей».** Наоборот: родитель смонтирован, когда смонтированы все дети.
- **«Через `ref` на компонент родитель видит всё».** У `<script setup>` — только то, что отдано через `defineExpose`.

## Как спрашивают на собеседовании

::question
Что такое Composition API и зачем он нужен?

#answer
Набор функций (`ref`, `computed`, `watch`, `onMounted`), из которых собирается логика компонента. Код группируется по задаче, а не по опциям, и любой кусок можно вынести в композабл и переиспользовать.

#more
Composition API решает три проблемы Options API: разбросанность логики одной задачи, неявное переиспользование через миксины и слабую типизацию через `this`. Он не заменяет реактивность, а даёт к ней прямой доступ: те же `ref` и `computed` работают и вне компонентов.
::

::question
Что делает script setup?

#answer
Это сахар над `setup()`: компилятор превращает блок в функцию `setup`, и все переменные, функции и импорты верхнего уровня доступны шаблону без `return`. Импортированные компоненты не нужно регистрировать.

#more
В `<script setup>` работают макросы `defineProps`, `defineEmits`, `defineModel`, `defineExpose`, `defineOptions`, которые компилятор превращает в опции. Компонент закрыт: родитель видит только `defineExpose`. Верхнеуровневый `await` делает компонент асинхронным, а компилятор сохраняет экземпляр после ожидания.
::

::question
Когда выполняется setup и есть ли в нём this?

#answer
Один раз при создании экземпляра, до монтирования. `this` в нём нет: состояние держат `ref` и `reactive`, пропсы приходят первым аргументом, а `emit`, `attrs`, `slots` — во втором.

#more
В отличие от функции-компонента React, `setup` не вызывается на каждый рендер, поэтому хуки можно вызывать по условию, а обработчики видят актуальные значения. Хуки жизненного цикла нужно зарегистрировать синхронно — до первого `await` в обычном `setup()`.
::

::question
В каком порядке срабатывают хуки родителя и ребёнка?

#answer
При монтировании: `setup` и `beforeMount` родителя, затем `setup`, `beforeMount` и `mounted` ребёнка, и последним `mounted` родителя. При размонтировании `beforeUnmount` идёт от родителя к детям, а `unmounted` — от детей к родителю.

#more
Поэтому в `onMounted` родителя DOM детей уже существует. Асинхронные дети внутри `Suspense` монтируются позже, когда разрешатся. `onUpdated` родителя срабатывает после обновления детей, которые перерисовались в том же проходе.
::

::question
Почему хук после await не срабатывает?

#answer
Хук регистрируется в текущем экземпляре, а Vue знает его только пока `setup` выполняется синхронно. После `await` код продолжается в микрозадаче, экземпляра уже нет, и Vue выводит «onMounted is called when there is no active component instance».

#more
Решение — регистрировать хуки до первого `await`. В `<script setup>` компилятор оборачивает верхнеуровневый `await` в `withAsyncContext` и восстанавливает экземпляр, поэтому там хуки после ожидания работают. То же правило касается `inject` и `watch`: после `await` `inject` возвращает `undefined` с предупреждением, а `watch` не привязан к компоненту и продолжает работать после его удаления — оба случая проверены.
::

::question
Чем Composition API лучше Options API и что не так с миксинами?

#answer
Composition API группирует код по задаче, переиспользует логику через композаблы, хорошо типизируется и не зависит от `this`. Миксины подмешивают опции в компонент: не видно, откуда пришло свойство, а конфликты имён разрешаются молча.

#more
При конфликте в `data` побеждает компонент, без предупреждения. Миксины читают свойства друг друга через `this`, и связь неявная. Это аналог проблем HOC в React, а композаблы — аналог кастомных хуков. Options API поддерживается, стили можно смешивать: результат `setup()` доступен через `this`.
::

## Практика

::practice{title="Таймер не останавливается"}
После ухода со страницы в консоли продолжают появляться запросы:

```js
export default {
  async setup() {
    const product = ref(await loadProduct());
    const timer = setInterval(refreshPrice, 5000);
    onUnmounted(() => clearInterval(timer));
    return { product };
  },
};
```

#solution
`onUnmounted` вызван после `await`: к этому моменту `setup` вышел из синхронной части, и Vue не знает, к какому экземпляру привязать хук. Он не зарегистрирован, таймер живёт вечно. В консоли было предупреждение «no active component instance».

```js
export default {
  async setup() {
    let timer;
    onUnmounted(() => clearInterval(timer));   // до первого await
    const product = ref(await loadProduct());
    timer = setInterval(refreshPrice, 5000);
    return { product };
  },
};
```

Или переписать на `<script setup>`: компилятор восстанавливает экземпляр после верхнеуровневого `await`. Но надёжнее привычка регистрировать хуки до ожидания. В проверке `onMounted` после `await` в обычном `setup()` не сработал, а в `<script setup>` — сработал.
::

::practice{title="Родитель не может вызвать метод"}
Родитель хочет поставить фокус в поле формы, но `form.value.focus` — `undefined`:

```vue
<!-- ProductForm.vue -->
<script setup>
import { ref } from 'vue';
const input = ref(null);
function focus() { input.value.focus(); }
</script>

<template><input ref="input"></template>
```

#solution
Компонент на `<script setup>` закрыт: его переменные не видны через ссылку на шаблон. Метод нужно отдать явно:

```vue
<script setup>
import { ref } from 'vue';
const input = ref(null);
function focus() { input.value.focus(); }

defineExpose({ focus });
</script>
```

Отдавать стоит методы-команды (`focus`, `reset`, `scrollToError`), а не внутреннее состояние: данные идут вниз через пропсы, события — вверх через `emit`. В проверке `focus()` из `defineExpose` вызвался, а неотданная переменная была `undefined`.
::

::practice{title="Откуда взялось значение?"}
В компоненте на Options API подключены два миксина и своё `data`. Значение `label` в шаблоне не то, что в миксине:

```js
const counterMixin = { data: () => ({ count: 100, label: 'миксин' }) };

export default {
  mixins: [counterMixin],
  data: () => ({ label: 'компонент' }),
};
```

#solution
При слиянии `data` миксина и компонента побеждает компонент, и Vue не предупреждает. В проверке `label` оказался `'компонент'`, а `count` пришёл из миксина. Такой код сложно читать: по компоненту не видно, какие поля откуда.

```js
// композабл: источник явный, конфликтов нет
export function useCounter(initial = 100) {
  const count = ref(initial);
  const inc = () => count.value++;
  return { count, inc };
}
```

```vue
<script setup>
const { count, inc } = useCounter();
const label = ref('компонент');
</script>
```

Имена в компоненте выбирает тот, кто вызывает композабл, и при совпадении можно переименовать при деструктуризации: `const { count: cartCount } = useCounter()`. Миксины во Vue 3 работают, но в новом коде их заменяют композаблами.
::
