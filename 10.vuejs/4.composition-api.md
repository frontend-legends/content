# Composition API

**Composition API** - основной способ писать компоненты в Vue 3. Он позволяет организовать логику по смыслу и переиспользовать её, в отличие от **Options API**, где код раскладывается по фиксированным секциям. Это прямой аналог перехода React от классов к хукам.

---

## script setup

Идиоматичная форма Composition API - блок `<script setup>`. Всё, что объявлено на верхнем уровне, **автоматически доступно в шаблоне**.

```vue
<script setup>
import { ref, computed, onMounted } from 'vue';

const count = ref(0);
const double = computed(() => count.value * 2);
function inc() { count.value++; }

onMounted(() => console.log('смонтирован'));
</script>

<template>
  <button @click="inc">{{ count }} / {{ double }}</button>
</template>
```

Не нужно ничего возвращать или регистрировать - `count`, `double`, `inc` сразу видны шаблону. Это сахар над функцией `setup()`.

---

## Функция setup() под капотом

`<script setup>` компилируется в опцию `setup()` - точку входа Composition API. Она выполняется **до создания компонента**, один раз, и возвращает то, что доступно шаблону.

```js
export default {
  setup() {
    const count = ref(0);
    return { count }; // явно отдаём в шаблон
  },
};
```

<b class="text-on-semi-light">Важно про setup</b> - <span class="text-gray">`setup()` запускается один раз при инициализации, до монтирования. Здесь нет `this` (компонента ещё нет). Реактивность обеспечивают `ref`/`reactive`, а не `this.data`. Поэтому stale-closure-проблем, как в React-хуках, у Vue нет - состояние живёт в реактивных ссылках, а не в замыканиях рендера.</span>

## Хуки жизненного цикла

В Composition API на этапы жизни компонента подписываются функциями `onX`, вызываемыми внутри `setup`.

```js
import { onMounted, onUpdated, onUnmounted } from 'vue';

onMounted(() => { /* DOM готов - подписки, измерения, запросы */ });
onUpdated(() => { /* после обновления DOM */ });
onUnmounted(() => { /* cleanup - отписки, таймеры */ });
```

### Карта жизненного цикла

| Composition API | Options API | Когда |
|-----------------|-------------|-------|
| `setup` | `beforeCreate` / `created` | до создания, инициализация |
| `onBeforeMount` | `beforeMount` | перед вставкой в DOM |
| `onMounted` | `mounted` | DOM готов |
| `onBeforeUpdate` | `beforeUpdate` | перед перерисовкой |
| `onUpdated` | `updated` | после перерисовки |
| `onBeforeUnmount` | `beforeUnmount` | перед удалением |
| `onUnmounted` | `unmounted` | удалён - cleanup |
| `onErrorCaptured` | `errorCaptured` | поймана ошибка потомка |

> `onMounted` ≈ `componentDidMount`/`useEffect(fn, [])` в React, `onUnmounted` ≈ cleanup. Но в отличие от `useEffect`, это явные хуки жизненного цикла, а не «синхронизация».

## Компиляторные макросы

В `<script setup>` доступны **макросы** - их не импортируют, их обрабатывает **компилятор** (в рантайме не существуют):

| Макрос | Зачем |
|--------|-------|
| `defineProps` | объявить входные props |
| `defineEmits` | объявить исходящие события |
| `defineModel` | двусторонняя привязка `v-model` (3.4+) |
| `defineExpose` | что доступно родителю через template ref |
| `defineOptions` | опции компонента (`name`, `inheritAttrs`) |

```vue
<script setup lang="ts">
const props = defineProps<{ title: string }>();
const emit = defineEmits<{ submit: [id: number] }>();
const model = defineModel();        // v-model
defineExpose({ focus });            // отдать наружу метод focus
</script>
```

<b class="text-on-semi-light">defineExpose - важная деталь</b> - <span class="text-gray">По умолчанию компонент на `<script setup>` **закрыт**: родитель через template ref не видит его внутренности (в отличие от Options API). `defineExpose` явно открывает выбранные методы/свойства - осознанный публичный API компонента.</span>

## Options API (legacy-теория)

До Vue 3 (и сейчас в Vue 2 / старых проектах) компоненты пишут через **опции**: `data`, `methods`, `computed`, `watch`, хуки жизненного цикла. Доступ к состоянию - через `this`.

```js
export default {
  data() {
    return { count: 0 };          // реактивное состояние
  },
  computed: {
    double() { return this.count * 2; },
  },
  methods: {
    inc() { this.count++; },      // доступ через this
  },
  mounted() {
    console.log('смонтирован');
  },
};
```

<b class="text-on-semi-light">Проблема Options API</b> - <span class="text-gray">Логика одной фичи **размазана** по секциям: состояние в `data`, обработчик в `methods`, производное в `computed`, побочный эффект в `mounted`. В большом компоненте связанный код разбросан, а переиспользовать его между компонентами трудно.</span>

## Почему Composition победил

| | Options API | Composition API |
|--|-------------|------------------|
| Организация кода | по типу опции | по смыслу/фиче |
| Переиспользование логики | mixins (конфликты имён, неясный источник) | composables (явно, без конфликтов) |
| TypeScript | слабая выводимость через `this` | отличная типизация |
| `this` | нужен, источник путаницы | отсутствует |
| Связанный код | разбросан по секциям | рядом |

### Mixins как legacy

До composables логику переиспользовали через **mixins** - объекты с опциями, подмешиваемые в компонент.

```js
// ❌ legacy: непонятно, откуда взялось свойство, и возможны коллизии имён
export default { mixins: [counterMixin, fetchMixin] };
```

Проблемы mixins (неявный источник свойств, конфликты имён, «магия») - ровно те же, что у HOC в React. Их заменили [composables](/content/vuejs/composables) - функции, явно возвращающие состояние и методы.

> На собесе: «Composition API относится к Options API так же, как хуки к классам в React: группировка логики по смыслу и переиспользование без mixins/HOC».

---

## Когда что использовать

- **Новый код на Vue 3** → Composition API (`<script setup>`).
- **Поддержка Vue 2 / старого проекта** → Options API (его не выпиливают, он валиден).
- Options API проще для совсем небольших компонентов, но не масштабируется по сложности.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое Composition API и зачем он нужен?</b>
<span class="text-gray">Способ организовать логику компонента по смыслу через функции (`ref`, `computed`, `onMounted`) вместо фиксированных секций. Решает разбросанность логики и переиспользование.</span>

<b class="text-on-semi-light">Что делает `<script setup>`?</b>
<span class="text-gray">Сахар над `setup()`: все объявления верхнего уровня автоматически доступны шаблону, без явного return. Плюс макросы `defineProps`/`defineEmits`.</span>

<b class="text-on-semi-light">Когда выполняется setup и есть ли в нём this?</b>
<span class="text-gray">Один раз, до создания компонента и монтирования. `this` нет - состояние держат реактивные ref/reactive, а не экземпляр.</span>

<b class="text-on-semi-light">Чем Composition API лучше Options API?</b>
<span class="text-gray">Группирует связанный код, переиспользует логику через composables без коллизий, лучше типизируется, не требует `this`.</span>

<b class="text-on-semi-light">Что такое mixins и почему от них ушли?</b>
<span class="text-gray">Объекты с опциями, подмешиваемые в компонент. Проблемы: неявный источник свойств и конфликты имён - как у HOC в React. Заменены composables.</span>

<b class="text-on-semi-light">Как соотносятся хуки жизненного цикла Vue и React?</b>
<span class="text-gray">`onMounted` ≈ `componentDidMount`/`useEffect(fn, [])`, `onUnmounted` ≈ cleanup. Но Vue-хуки - явные этапы жизни, а не модель синхронизации.</span>
