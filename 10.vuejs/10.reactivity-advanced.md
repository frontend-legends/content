# Продвинутая реактивность

Инструменты для случаев, когда глубокая реактивность лишняя или мешает: `shallowRef` и `triggerRef`, `readonly`, `toRaw` и `markRaw`, `customRef`, `effectScope` — и как устроена очередь обновлений, ради которой существует `nextTick`. Спрашивают, зачем нужны `shallowRef`, `markRaw` и `nextTick`. Глубже — почему экземпляр класса с приватными полями падает внутри `reactive`, в каком порядке выполняются наблюдатели и рендеры и что значит «Maximum recursive updates exceeded».

::tldr
- **`shallowRef` отслеживает только замену `.value`.** Для больших и неизменяемых данных это дешевле глубокой реактивности: данные заменяют целиком, а после мутации на месте вызывают `triggerRef`.
- **`markRaw` запрещает Vue оборачивать объект в Proxy.** Нужен для экземпляров сторонних библиотек: класс с `#private`-полями внутри `reactive` падает с `TypeError`, потому что `this` становится прокси.
- **`readonly` — вид на источник, а не копия:** запись через него отклоняется, а изменения источника видны.
- **`effectScope` собирает наблюдатели и `computed` и останавливает их разом.** Так композаблы и сторы освобождают ресурсы вне компонентов.
- **Обновления идут через очередь:** наблюдатели с `flush: 'pre'`, потом рендеры от родителя к детям, потом колбэки после обновления DOM. `nextTick` — промис, который разрешается после прохода очереди.
::

---

## Когда глубокая реактивность лишняя

`ref` и `reactive` по умолчанию **глубокие**: каждый вложенный объект при обращении оборачивается в Proxy, а каждое чтение записывает зависимость (подробно — в [Основах реактивности](/content/vuejs/reactivity-fundamentals)). Обычно это незаметно. Заметно — в трёх случаях:

- **большие данные:** таблица на 10 000 строк по 20 полей — это обёртки и зависимости на каждую ячейку, которую прочитал рендер;
- **неизменяемые данные:** ответ API, который никто не мутирует, а только заменяет;
- **чужие объекты:** экземпляры карт, графиков, редакторов, у которых своя логика состояния.

Сквозной пример — каталог: список товаров с сервера и карта пунктов выдачи.

## shallowRef и shallowReactive

```js
const rows = shallowRef([]);

rows.value = await fetchProducts();     // замена — отслеживается
rows.value.push(product);               // мутация — нет
```

`shallowRef` отслеживает только **присваивание `.value`**. Вложенные объекты остаются обычными: в проверке `isReactive(rows.value[0])` — `false`, а `push` не запустил эффект. Для таких данных обновление — это замена: `rows.value = [...rows.value, product]`.

Если мутация на месте всё-таки нужна, после неё вызывают `triggerRef(rows)` — он вручную запускает зависимых. Проверено.

`shallowReactive` — то же для объекта: реактивны только свойства верхнего уровня. `s.page = 2` отслеживается, `s.filters.q = 'чай'` — нет.

Компоненты в `:is` и `component`-ссылки хранят в `shallowRef` по той же причине: объекту компонента глубокая реактивность не нужна.

## readonly

```js
const cart = reactive({ items: [] });
const publicCart = readonly(cart);
```

`readonly` возвращает Proxy, который отклоняет запись — с предупреждением «target is readonly». Он **глубокий**: вложенные объекты тоже только для чтения. И это **вид на источник**, а не копия: изменения `cart` сразу видны через `publicCart`. Оба факта проверены.

Так отдают состояние наружу из стора, композабла или провайдера, оставляя изменения владельцу (подробно — в [Provide и inject](/content/vuejs/provide-inject)). `shallowReadonly` защищает только верхний уровень.

## toRaw и markRaw

**`toRaw(proxy)`** возвращает исходный объект. Нужен, чтобы передать данные туда, где Proxy мешает: в `structuredClone`, в `postMessage`, в стороннюю библиотеку, которая сравнивает объекты по ссылке. Изменения через исходный объект не отслеживаются — это и есть цель.

Сравнение по ссылке внутри реактивного массива Vue учитывает сам: `reactive([raw]).includes(raw)` возвращает `true`, хотя элемент массива — прокси. Проверено.

**`markRaw(obj)`** помечает объект, чтобы Vue никогда не оборачивал его в Proxy, даже если он окажется внутри `reactive`.

### Почему класс падает в reactive

```js
class MapWidget {
  #zoom = 1;
  zoomIn() { return ++this.#zoom; }
}

const state = reactive({ map: new MapWidget() });
state.map.zoomIn();   // TypeError: Cannot read private member #zoom from an object whose class did not declare it
```

`state.map` возвращает Proxy, и при вызове метода `this` — это прокси, а не экземпляр. Приватные поля `#` привязаны к самому объекту, у прокси их нет, и обращение `this.#zoom` падает (подробно о приватных полях — в [Прототипах и классах](/content/javascript/prototypes-and-classes)). То же случается с объектами, которые хранят внутреннее состояние в `WeakMap` по ссылке на `this` или сравнивают `this` с собой.

```js
const state = reactive({ map: markRaw(new MapWidget()) });
state.map.zoomIn();   // 2
```

В проверке без `markRaw` вызов бросил `TypeError`, с ним — сработал. Правило: **экземпляры сторонних библиотек — карт, графиков, редакторов, WebSocket-клиентов — кладут в состояние через `markRaw` или `shallowRef`**. Им не нужна реактивность Vue: у них свои события об изменениях.

## customRef

`customRef` даёт полный контроль над тем, когда отслеживать и когда оповещать:

```js
function useDebouncedRef(value, delay = 300) {
  let timer;
  return customRef((track, trigger) => ({
    get() {
      track();
      return value;
    },
    set(v) {
      clearTimeout(timer);
      timer = setTimeout(() => { value = v; trigger(); }, delay);
    },
  }));
}

const query = useDebouncedRef('');
```

`track()` в геттере записывает зависимость, `trigger()` в сеттере запускает зависимых — когда решит сеттер. В проверке три быстрых записи дали одно изменение с последним значением. Это редкий инструмент: для отложенного значения обычно хватает `refDebounced` из VueUse, а `customRef` нужен для своих правил — значение с проверкой, синхронизация с внешним хранилищем.

## effectScope

Каждый `watch`, `watchEffect` и `computed` — эффект, который нужно когда-то остановить. В компоненте это происходит само при размонтировании. Вне компонента — в сторе, в композабле, который вызвали из обычного кода, — эффекты собирают в область:

```js
const scope = effectScope();

scope.run(() => {
  const doubled = computed(() => count.value * 2);
  watch(doubled, log);
  onScopeDispose(() => socket.close());
});

scope.stop();   // остановить всё, вызвать onScopeDispose
```

Области вкладываются: вложенная остановится вместе с родительской. `effectScope(true)` создаёт **отсоединённую** область, которая живёт сама по себе. В проверке после `scope.stop()` вложенный наблюдатель остановился, а отсоединённый продолжил работать.

Компонент — тоже область эффектов, поэтому `onScopeDispose` в композабле срабатывает и при размонтировании (подробно — в [Композаблах](/content/vuejs/composables)). На `effectScope` построены сторы Pinia и `createSharedComposable` из VueUse.

## Очередь обновлений и nextTick

Изменение реактивных данных не перерисовывает компонент сразу. Эффект рендера и наблюдатели **ставятся в очередь**, и очередь выполняется в микрозадаче после текущего синхронного кода (подробно о микрозадачах — в [Event Loop](/content/javascript/event-loop)).

Порядок одного прохода проверен на логе:

```text
n.value++; n.value++          ← синхронный код, ничего не выполняется
watch pre                      ← наблюдатели с flush: 'pre', один раз на пачку
parent render → child render   ← рендеры по порядку создания: родитель раньше детей
watch post                     ← колбэки с flush: 'post', DOM уже обновлён
child updated → parent updated ← хуки onUpdated
после nextTick
```

Из этого следует:

- **несколько изменений — одна перерисовка.** Две записи `n` дали один рендер;
- **родитель обновляется раньше детей,** поэтому ребёнок не перерисовывается дважды — сначала со старыми, потом с новыми пропсами;
- **компонент в очереди один раз,** сколько бы его зависимостей ни изменилось.

### nextTick

`nextTick()` возвращает промис, который разрешится после ближайшего прохода очереди. Нужен, когда после изменения данных надо прочитать или использовать **обновлённый DOM**:

```js
items.value.push(product);
list.value.children.length;   // ещё старое число
await nextTick();
list.value.lastElementChild.scrollIntoView();   // новый элемент уже в DOM
```

В проверке сразу после `push` в списке был один элемент, после `nextTick` — два. В наблюдателях вместо `nextTick` удобнее `flush: 'post'` (подробно — в [Computed и наблюдателях](/content/vuejs/computed-and-watchers)).

### Бесконечный цикл

Если эффект меняет то, от чего сам зависит, он снова попадает в очередь. Vue считает повторы и обрывает цикл ошибкой «Maximum recursive updates exceeded. This means you have a reactive effect that is mutating its own dependencies». В проверке её вызвал наблюдатель, который увеличивал свой же источник. Типичные причины — запись состояния в `onUpdated`, в render-функции или в getter `computed`, и пара наблюдателей, которые меняют источники друг друга.

---

## Красные флаги в ответе

- **«`shallowRef` — это просто быстрый `ref`».** Он отслеживает только замену `.value`, мутации на месте не видны без `triggerRef`.
- **«`readonly` возвращает замороженную копию».** Это вид на источник: изменения источника видны.
- **«Любой объект можно положить в `reactive`».** Экземпляры классов с приватными полями падают, для них `markRaw` или `shallowRef`.
- **«`nextTick` откладывает код на следующий кадр».** Он ждёт прохода очереди Vue в микрозадаче, а не кадра браузера.
- **«Каждое изменение данных — отдельная перерисовка».** Изменения складываются, компонент обновляется один раз за проход.

## Как спрашивают на собеседовании

::question
Зачем нужен shallowRef?

#answer
Чтобы не делать глубоко реактивными большие или неизменяемые данные. `shallowRef` отслеживает только присваивание `.value`, вложенные объекты остаются обычными. Данные обновляют заменой целиком.

#more
После мутации на месте можно вызвать `triggerRef` — он вручную оповестит зависимых. `shallowReactive` делает реактивным только верхний уровень объекта. Типичные случаи: списки с сервера, большие таблицы, объекты компонентов в `:is`, экземпляры сторонних библиотек.
::

::question
Что делает markRaw и когда он нужен?

#answer
Помечает объект, чтобы Vue никогда не оборачивал его в Proxy. Нужен для экземпляров сторонних библиотек — карт, графиков, редакторов — и для больших неизменяемых данных.

#more
Без `markRaw` метод экземпляра, вызванный через прокси, получает `this`-прокси. Класс с `#private`-полями падает с `TypeError`, а код, который сравнивает `this` или хранит данные в `WeakMap` по ссылке, ведёт себя неправильно. `toRaw` делает обратное — возвращает исходный объект из прокси.
::

::question
Для чего customRef?

#answer
Для ref со своими правилами отслеживания и оповещения. Фабрика получает `track` и `trigger`: геттер вызывает `track`, сеттер решает, когда вызвать `trigger`. Классический пример — значение с задержкой: запись откладывается, а зависимые узнают только о последнем значении.

#more
Подходит для значений с проверкой, синхронизации с внешним хранилищем, ленивых значений. Для отложенного значения обычно хватает `refDebounced` из VueUse. Если `track` не вызвать, зависимости не запишутся, если `trigger` — изменения не дойдут.
::

::question
Что решает effectScope?

#answer
Собирает эффекты — `watch`, `watchEffect`, `computed` — в одну область и останавливает их разом через `scope.stop()`. В компоненте это происходит при размонтировании само, а вне компонента нужна явная область.

#more
`onScopeDispose` регистрирует очистку при остановке области и работает и в компонентах. Вложенные области останавливаются вместе с родителем, `effectScope(true)` создаёт отсоединённую. На этом построены сторы Pinia и общие композаблы.
::

::question
Зачем нужен nextTick?

#answer
Vue обновляет DOM асинхронно: изменения данных ставят компоненты в очередь, и она выполняется в микрозадаче одним проходом. `nextTick()` — промис, который разрешается после этого прохода. Нужен, чтобы прочитать или использовать обновлённый DOM.

#more
В очереди сначала наблюдатели с `flush: 'pre'`, потом рендеры от родителя к детям, потом колбэки после обновления DOM и хуки `onUpdated`. Несколько изменений дают одну перерисовку. В наблюдателях вместо `nextTick` используют `flush: 'post'`.
::

::question
Что значит «Maximum recursive updates exceeded»?

#answer
Эффект меняет данные, от которых сам зависит, и снова попадает в очередь. Vue считает повторы и обрывает цикл этой ошибкой.

#more
Типичные причины: запись состояния в `onUpdated`, в render-функции или getter `computed`, наблюдатель, который меняет собственный источник, и пара наблюдателей, меняющих источники друг друга. Исправление — производное значение через `computed` вместо записи, или условие, которое прекращает изменения.
::

## Практика

::practice{title="Карта перестала работать"}
После переноса виджета карты в состояние компонента кнопки масштаба бросают ошибку:

```js
const state = reactive({ map: null });

onMounted(() => {
  state.map = new MapWidget(container.value);
});

function zoomIn() {
  state.map.zoomIn();   // TypeError: Cannot read private member #zoom
}
```

#solution
`state.map` возвращает Proxy над экземпляром. При вызове `zoomIn` `this` — это прокси, а приватные поля класса есть только у самого экземпляра. Экземпляру сторонней библиотеки реактивность Vue не нужна:

```js
const map = shallowRef(null);

onMounted(() => {
  map.value = markRaw(new MapWidget(container.value));
});

function zoomIn() {
  map.value.zoomIn();
}
```

`shallowRef` отслеживает только появление карты, а `markRaw` гарантирует, что экземпляр не обернут, даже если его положат в другой `reactive`. Изменения состояния карты получают из её собственных событий. В проверке вызов через `reactive` бросил `TypeError`, с `markRaw` — вернул новый масштаб.
::

::practice{title="Прокрутка к новому сообщению"}
В чате после отправки нужно прокрутить к последнему сообщению, но прокручивается к предпоследнему:

```js
function send(text) {
  messages.value.push({ id: Date.now(), text });
  list.value.lastElementChild.scrollIntoView();
}
```

#solution
`push` изменил данные, но DOM обновится только после прохода очереди. В момент `scrollIntoView` последний элемент списка — ещё старое сообщение.

```js
async function send(text) {
  messages.value.push({ id: Date.now(), text });
  await nextTick();
  list.value.lastElementChild.scrollIntoView();
}
```

Если прокрутка должна происходить при любом добавлении сообщений, а не только при отправке, удобнее наблюдатель с `flush: 'post'`: `watch(() => messages.value.length, scrollToEnd, { flush: 'post' })`. В проверке сразу после `push` в списке был один элемент, после `nextTick` — два.
::

::practice{title="Таблица тормозит"}
Отчёт загружает 20 000 строк и после загрузки секунду не реагирует. Данные только показываются и заменяются целиком при смене фильтра:

```js
const rows = ref([]);
rows.value = await fetchReport(filters);
```

#solution
`ref` с массивом объектов делает реактивной каждую строку и каждое поле, к которому обратился рендер. Данные не мутируются — реактивность им не нужна.

```js
const rows = shallowRef([]);
rows.value = await fetchReport(filters);   // замена отслеживается

// если всё-таки нужна правка одной строки:
rows.value[i].status = 'paid';
triggerRef(rows);
```

`shallowRef` отслеживает только замену массива, строки остаются обычными объектами. Если строк столько, что тормозит и сам DOM, к этому добавляют виртуализацию (подробно — в [Производительности](/content/vuejs/performance)). В проверке после `push` в `shallowRef` эффект не запустился, после замены и после `triggerRef` — запустился, а строки остались нереактивными.
::
