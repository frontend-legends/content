# Загрузка данных

Как загружать данные во Vue: ручная загрузка через `watch` и её проблемы, TanStack Query для Vue с реактивными ключами и кешем, `Suspense` с асинхронным `setup` и `useFetch` в Nuxt. Спрашивают, чем плоха загрузка в `onMounted`, что такое stale-while-revalidate и зачем `useFetch` в Nuxt. Глубже — почему запрос не обновляется при смене пропса, если ключ не реактивный, почему при SSR данные загружаются дважды и откуда берутся водопады в асинхронных компонентах.

::tldr
- **Данные с сервера — кеш чужих данных, а не состояние приложения.** Им нужны загрузка, ошибки, отмена, кеш, обновление и дедупликация — это задача библиотеки, а не стора.
- **Ручная загрузка в `onMounted` не следит за параметрами:** при смене пропса компонент переиспользуется, и запроса не будет. Через `watch` следит, но гонки, кеш и ошибки остаются на тебе.
- **В Vue Query ключ запроса должен быть реактивным:** `['product', () => props.id]`. С `props.id` в ключе — снимок, и при смене товара запрос не повторится.
- **Запросы с одним ключом делят кеш:** два компонента — один запрос. В пределах `staleTime` данные считаются свежими, после — показываются из кеша и обновляются в фоне.
- **В Nuxt начальные данные загружают через `useFetch` или `useAsyncData`:** результат с сервера передаётся клиенту в payload, и при гидратации запрос не повторяется. Для действий пользователя — `$fetch`.
::

---

## Почему серверные данные особенные

Сквозной пример — страница товара: карточка, цена, отзывы. Данные товара принадлежат серверу. У клиента — **копия**, которая может устареть, пока пользователь читает страницу. Отсюда задачи, которых нет у обычного состояния: показать загрузку и ошибку, не дать устаревшему ответу перезаписать новый, не загружать одно и то же дважды, обновить данные, когда пользователь вернулся на вкладку, и сбросить кеш после изменения на сервере.

Общая модель — свежесть и устаревание, stale-while-revalidate, мутации и инвалидация, оптимистичные обновления — разобрана в [Загрузке данных React](/content/reactjs/data-fetching): она одинакова для всех фреймворков. Здесь — как это выглядит во Vue.

## Ручная загрузка

Первый вариант, который пишут все:

```vue
<script setup>
const props = defineProps({ id: Number });
const product = ref(null);

onMounted(async () => {
  product.value = await fetch(`/api/products/${props.id}`).then((r) => r.json());
});
</script>
```

Проблемы по порядку:

1. **Не следит за параметрами.** Роутер переиспользует компонент при переходе с `/products/1` на `/products/2`, `onMounted` не срабатывает второй раз, и на странице старый товар (подробно — в [Композаблах](/content/vuejs/composables)).
2. **Нет загрузки и ошибки.** Нужны ещё два ref и `try/finally`.
3. **Гонка.** Если переход быстрый, медленный ответ на первый товар перезапишет второй.
4. **Нет кеша.** Вернулся на товар — снова запрос и снова индикатор загрузки.
5. **Нет дедупликации.** Цена и карточка загружают один и тот же товар двумя запросами.

Первые три решаются через `watch` с `onWatcherCleanup` (подробно — в [Computed и наблюдателях](/content/vuejs/computed-and-watchers)). Остальные — это уже кеш, и писать его вручную — значит писать библиотеку.

## TanStack Query для Vue

```vue
<script setup>
import { useQuery } from '@tanstack/vue-query';

const props = defineProps({ id: Number });

const { data: product, isPending, isError, error } = useQuery({
  queryKey: ['product', () => props.id],
  queryFn: () => fetch(`/api/products/${props.id}`).then((r) => r.json()),
  staleTime: 30_000,
});
</script>

<template>
  <p v-if="isPending">Загрузка…</p>
  <p v-else-if="isError">{{ error.message }}</p>
  <ProductCard v-else :product="product" />
</template>
```

Модель та же, что у React-версии: ключ, функция загрузки, кеш. Отличие — **реактивность**. Результат `useQuery` — набор ref: `data`, `isPending`, `isFetching`, `error`. В проверке `isRef(data)` — `true`, поэтому в скрипте нужен `.value`, а в шаблоне ref разворачиваются.

### Ключ должен быть реактивным

Главная ловушка Vue-версии. Ключ — это то, по чему библиотека решает, что данные изменились:

```js
queryKey: ['product', props.id]           // число — снимок на момент вызова
queryKey: ['product', () => props.id]     // геттер — библиотека следит за изменением
queryKey: ['product', productId]          // ref — тоже следит
```

С числом в ключе смена `id` ничего не меняет: ключ тот же, запроса нет. В проверке компонент с геттером в ключе показал «Товар 2», а с числом — остался на «Товар 1». Vue Query принимает в ключе ref и геттеры и сам разворачивает их — это та же идея, что `toValue` в композаблах.

Остальные параметры тоже могут быть реактивными. `enabled: () => userId.value !== null` откладывает зависимый запрос, пока нет нужных данных. В проверке заказы не загружались, пока не появился пользователь, и загрузились сразу после.

### Кеш и дедупликация

Запросы с одинаковым ключом **делят кеш**. Карточка и блок цены, оба с ключом `['product', 3]`, сделают один запрос — проверено. Компоненты не знают друг о друге: кеш живёт в `QueryClient` на уровне приложения.

`staleTime` задаёт, сколько данные считаются свежими:

- **в пределах срока** повторный показ компонента берёт данные из кеша без запроса;
- **после срока** компонент сразу показывает данные из кеша, а запрос идёт **в фоне** (`isFetching` — `true`). Это и есть stale-while-revalidate.

В проверке повторное монтирование в пределах `staleTime` обошлось без запроса, а после — первый же рендер показал «Товар 4» из кеша при `isFetching: true`.

### Мутации

После изменения на сервере кеш сбрасывают — и все компоненты с этим ключом загрузят свежие данные:

```js
const queryClient = useQueryClient();

const { mutate: rename } = useMutation({
  mutationFn: (title) => api.updateProduct(props.id, { title }),
  onSuccess: () => queryClient.invalidateQueries({ queryKey: ['product', props.id] }),
});
```

В проверке после мутации запрос повторился, и карточка показала новое название.

### Альтернативы

- **Pinia Colada** — библиотека загрузки данных от автора Pinia, построенная поверх Pinia: те же ключи, кеш и мутации, со стором в DevTools;
- **`useFetch` из VueUse** — загрузка с состоянием и отменой, но без общего кеша;
- **`useFetch` и `useAsyncData` в Nuxt** — о них ниже.

## Suspense и асинхронный setup

Без библиотеки данные можно загрузить прямо в `<script setup>` верхнеуровневым `await`. Компонент становится асинхронным, и его показывают внутри `Suspense` (подробно — во [Встроенных компонентах](/content/vuejs/built-in-components)):

```vue
<script setup>
const props = defineProps({ id: Number });
const product = await fetch(`/api/products/${props.id}`).then((r) => r.json());
</script>
```

Код короткий, но кеша, повторов и реакции на смену `id` нет: `setup` выполняется один раз. Это подходит для данных, которые не меняются за время жизни компонента, или как часть Nuxt, где `useFetch` добавляет остальное.

### Водопады

Асинхронный `setup` легко превращается в **водопад**: родитель ждёт свои данные, только потом рендерит ребёнка, который начинает загружать свои.

```text
ProductPage: await product   ──────►
                                     Reviews: await reviews  ──────►
```

Независимые запросы запускают параллельно — `Promise.all` в одном месте, загрузка на уровне маршрута до рендера страницы, или библиотека, которая начинает запрос по ключу, не дожидаясь родителя. Общий разбор — в [Загрузке данных React](/content/reactjs/data-fetching).

## Загрузка в Nuxt

При SSR страница рендерится на сервере, а потом гидратируется в браузере (подробно — в [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt)). Если загрузить данные обычным `$fetch` в `setup`, запрос выполнится **дважды**: на сервере для HTML и в браузере при гидратации.

`useFetch` и `useAsyncData` решают это:

```vue
<script setup>
const route = useRoute();

const { data: product, status, error, refresh } = await useFetch(
  () => `/api/products/${route.params.id}`,
);
</script>
```

- **payload:** результат, полученный на сервере, сериализуется в HTML, и клиент при гидратации берёт его оттуда, без повторного запроса;
- **ключи:** вызовы с одинаковым ключом делят `data`, `error` и `status`. У `useFetch` ключ строится из адреса, параметров и места вызова, поэтому для общих данных в разных компонентах передают явный `key`;
- **реактивность:** адрес-геттер и реактивные параметры `query` отслеживаются. Шаблонная строка `` `/api/products/${id.value}` `` построится один раз, нужен геттер;
- **`lazy: true`** не блокирует переход на страницу, и загрузку показывают по `status`: `idle`, `pending`, `success`, `error`;
- **`server: false`** загружает только в браузере, после гидратации.

В Nuxt 4 `data` — `shallowRef` (глубокая реактивность включается `deep: true`), а начальные `data` и `error` — `undefined`, а не `null`.

Для действий пользователя — отправки формы, кнопки «В корзину» — используют `$fetch`: payload и дедупликация там не нужны, а `useFetch` в обработчике события привязался бы к компоненту.

## Красные флаги в ответе

- **«Данные с сервера — в Pinia».** Это кеш чужих данных: загрузка, свежесть, дедупликация и инвалидация — задача библиотеки.
- **«`queryKey: ['product', props.id]` следит за пропсом».** Это снимок, нужен геттер или ref.
- **«Загрузка в `onMounted` достаточна».** Она не повторится при смене параметра маршрута, и нет ни отмены, ни кеша.
- **«`$fetch` в `setup` при SSR — нормально».** Запрос выполнится на сервере и снова в браузере, нужны `useFetch` или `useAsyncData`.
- **«`Suspense` заменяет библиотеку загрузки».** Он только ждёт асинхронный `setup`, без кеша, повторов и реакции на параметры.

## Как спрашивают на собеседовании

::question
Чем серверное состояние отличается от обычного?

#answer
Это копия данных, которыми владеет сервер. Она асинхронна, может устареть, её делят разные компоненты. Нужны загрузка, ошибки, кеш, обновление, дедупликация и инвалидация после изменений — у локального состояния этих задач нет.

#more
Поэтому серверные данные держат в библиотеке загрузки — TanStack Query, Pinia Colada, `useFetch` в Nuxt, — а не в сторе. После выноса серверного состояния в сторе обычно остаётся немного: корзина до оформления, черновики, настройки интерфейса.
::

::question
Чем плоха загрузка в onMounted или watchEffect?

#answer
`onMounted` не повторит загрузку, когда сменится пропс или параметр маршрута: компонент переиспользуется. `watch` следит за параметром, но гонки, отмену, ошибки, кеш и дедупликацию приходится писать вручную.

#more
Без отмены медленный ответ на старый запрос перезапишет новый. Без кеша возврат на страницу снова показывает загрузку. Без дедупликации два компонента делают одинаковые запросы. Если загрузка всё-таки ручная, её делают через `watch` с `onWatcherCleanup` и `AbortController`.
::

::question
Почему Vue Query не перезапрашивает данные при смене пропса?

#answer
Скорее всего, в ключе значение, а не реактивный источник: `['product', props.id]` — число на момент вызова. Нужен геттер `() => props.id` или ref — тогда библиотека заметит изменение ключа и загрузит новые данные.

#more
Vue Query разворачивает ref и геттеры в ключе и в других параметрах, например `enabled`. Результат `useQuery` — набор ref, поэтому в скрипте нужен `.value`. Это та же причина, по которой композаблы принимают `MaybeRefOrGetter` и читают через `toValue`.
::

::question
Что такое stale-while-revalidate?

#answer
Стратегия кеша: если данные устарели, сразу показать то, что есть в кеше, и параллельно загрузить свежие. Пользователь не видит индикатор загрузки, а данные обновляются через мгновение.

#more
В TanStack Query срок свежести задаёт `staleTime`: в его пределах повторный показ берёт кеш без запроса, после — показывает кеш и обновляет в фоне (`isFetching`). `gcTime` — сколько неиспользуемые данные хранятся в кеше. Обновление также запускается при возврате на вкладку и восстановлении сети.
::

::question
Как загрузить данные через Suspense во Vue?

#answer
Верхнеуровневый `await` в `<script setup>` делает компонент асинхронным, а `Suspense` выше по дереву показывает запасное содержимое, пока он не готов.

#more
Кеша, повторов и реакции на изменение параметров нет: `setup` выполняется один раз. Вложенные асинхронные компоненты легко дают водопад — каждый ждёт родителя. В Vue Query есть метод `suspense()` у результата запроса для работы с `Suspense`, а в Nuxt `await useFetch` работает так же и добавляет payload.
::

::question
Зачем в Nuxt useFetch, если есть $fetch?

#answer
`$fetch` в `setup` при SSR выполнится дважды: на сервере и при гидратации в браузере. `useFetch` и `useAsyncData` передают результат с сервера в payload, и клиент не повторяет запрос. Плюс общие данные по ключу и реактивные параметры.

#more
Вызовы с одним ключом делят `data`, `error` и `status`. `lazy` не блокирует переход, `server: false` грузит только в браузере. В Nuxt 4 `data` — `shallowRef`, а начальные значения — `undefined`. Для действий пользователя используют `$fetch`.
::

## Практика

::practice{title="Товар не меняется"}
Переход по ссылке на похожий товар меняет адрес, а карточка остаётся прежней:

```js
const props = defineProps({ id: Number });

const { data: product } = useQuery({
  queryKey: ['product', props.id],
  queryFn: () => api.product(props.id),
});
```

#solution
В ключ попало число на момент вызова `setup`. Роутер переиспользовал компонент, `props.id` изменился, а ключ — нет, и Vue Query считает, что данные те же.

```js
const { data: product } = useQuery({
  queryKey: ['product', () => props.id],   // геттер — ключ следит за пропсом
  queryFn: () => api.product(props.id),
});
```

`queryFn` вызывается при каждой загрузке, поэтому читает актуальный `props.id`. Можно и `const id = computed(() => props.id)` с ref в ключе. В проверке компонент с геттером загрузил «Товар 2», а с числом в ключе остался на «Товар 1».
::

::practice{title="Два одинаковых запроса"}
На странице товара карточка и блок «Купить» загружают один и тот же товар, и в Network два запроса:

```js
// ProductCard.vue
onMounted(async () => { product.value = await api.product(props.id); });

// BuyBox.vue
onMounted(async () => { price.value = (await api.product(props.id)).price; });
```

#solution
Каждый компонент загружает сам по себе, общего кеша нет. С библиотекой загрузки ключ объединяет запросы:

```js
// composables/useProduct.js
export function useProduct(id) {
  return useQuery({
    queryKey: ['product', id],
    queryFn: () => api.product(toValue(id)),
    staleTime: 30_000,
  });
}

// ProductCard.vue
const { data: product } = useProduct(() => props.id);

// BuyBox.vue
const { data: product } = useProduct(() => props.id);
const price = computed(() => product.value?.price);
```

Запросы с одинаковым ключом делят кеш, и второй компонент получает данные из первого запроса. Общий композабл держит ключ и функцию загрузки в одном месте, чтобы они не разошлись. В проверке два компонента с ключом `['product', 3]` вызвали загрузку один раз.
::
