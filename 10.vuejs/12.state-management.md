# Управление состоянием

Где хранить состояние во Vue-приложении и как устроен стор Pinia: setup- и options-сторы, `storeToRefs`, геттеры и действия, `$patch` и подписки, плагины и SSR. Спрашивают, как выбрать инструмент для состояния, чем Pinia отличается от Vuex и зачем `storeToRefs`. Глубже — почему у setup-стора нет `$reset`, почему невозвращённое состояние пропадает из DevTools и почему во Vue не нужны селекторы, как в Redux.

::tldr
- **Сначала разделяют состояние:** локальное — в компоненте, контекст поддерева — в `provide`, данные с сервера — в библиотеке загрузки с кешем, и только общее состояние клиента — в сторе.
- **Стор Pinia — это `reactive`-объект, созданный функцией `setup`:** ref становятся состоянием, `computed` — геттерами, функции — действиями. Ref в нём развёрнуты, поэтому деструктуризация теряет связь, и нужен `storeToRefs`.
- **Setup-стор должен вернуть всё своё состояние.** Невозвращённый ref не попадает в `pinia.state`: его не видят DevTools, плагины и SSR. И `$reset` у setup-стора нет — его пишут сами.
- **Селекторы не нужны:** компонент зависит только от полей стора, которые прочитал, и изменение соседнего поля его не перерисует.
- **Стор живёт в экземпляре Pinia, а Pinia — в приложении.** При SSR приложение и Pinia создают на каждый запрос, а `pinia.state.value` сериализуют в HTML для гидратации.
::

---

## Какое это состояние

Прежде чем выбирать стор, стоит понять, что за данные хранятся. Сквозной пример — интернет-магазин:

| Данные | Вид состояния | Где хранить |
| --- | --- | --- |
| открыт ли выпадающий список, значение поля | локальное | `ref` в компоненте |
| тема, валюта, плотность таблицы для части дерева | контекст поддерева | `provide`/`inject` |
| каталог, карточка товара, заказы | серверное: кеш чужих данных | библиотека загрузки ([Загрузка данных](/content/vuejs/data-fetching)) |
| фильтры, страница, сортировка | состояние в адресе | параметры URL ([Маршрутизация](/content/vuejs/routing)) |
| корзина до оформления, черновик формы, текущий пользователь | общее клиентское | стор |

Главная ошибка — класть в стор данные с сервера и вручную писать для них загрузку, кеш, повторные запросы и инвалидацию. Это переизобретение библиотеки загрузки данных (общий разбор — в [Архитектуре состояния и данных](/content/architecture/state-and-data-architecture)). Когда серверные данные уходят в свою библиотеку, а фильтры — в адрес, в сторе остаётся немного.

Решение лестницей: **компонент → поднять к общему родителю → `provide` → стор.** Стор нужен, когда состояние делят независимые части приложения, его меняют из разных мест и его нужно видеть вне компонентов — в навигационных хуках роутера, в обработчиках API.

## Pinia

Pinia — официальный стор Vue. Устроен он просто: это реактивность Vue, собранная в именованный синглтон.

### Setup-стор

```js
// stores/cart.js
import { defineStore } from 'pinia';
import { ref, computed } from 'vue';

export const useCartStore = defineStore('cart', () => {
  const items = ref([]);
  const coupon = ref(null);

  const total = computed(() => items.value.reduce((s, i) => s + i.price * i.qty, 0));

  function add(product) {
    const line = items.value.find((i) => i.sku === product.sku);
    if (line) line.qty++;
    else items.value.push({ ...product, qty: 1 });
  }

  async function checkout(api) {
    const order = await api.createOrder(items.value);
    items.value = [];
    return order;
  }

  return { items, coupon, total, add, checkout };
});
```

Это та же функция, что композабл (подробно — в [Композаблах](/content/vuejs/composables)): `ref` становятся **состоянием**, `computed` — **геттерами**, функции — **действиями**. Отличия от композабла — состояние одно на приложение, у стора есть имя, его видят :term[DevTools]{def="инструменты разработчика в браузере; для Vue есть расширение со стором, компонентами и событиями"}, плагины и :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"}.

### Options-стор

Тот же стор в стиле Options API:

```js
export const useCounterStore = defineStore('counter', {
  state: () => ({ count: 0, step: 1 }),
  getters: { double: (state) => state.count * 2 },
  actions: { inc() { this.count += this.step; } },
});
```

Он привычнее тем, кто пришёл из Vuex, и у него есть встроенный `$reset`. Setup-стор гибче: внутри можно использовать любые композаблы, `watch` и `inject` уровня приложения.

### Возвращай всё состояние

В setup-сторе Pinia узнаёт о состоянии только по тому, что вернула функция. Ref, который не вернули, работает внутри стора, но:

- не попадает в `pinia.state.value` — в проверке ключи состояния были только `items` и `coupon`, без внутреннего `secret`;
- не виден в DevTools;
- не сериализуется при SSR и теряется при гидратации;
- не доступен плагинам, например для сохранения в `localStorage`.

Приватное состояние в сторе — это ошибка, которую замечают только при SSR. Если что-то не должно меняться снаружи, его возвращают, а наружу документируют действия.

## Использование

```vue
<script setup>
import { storeToRefs } from 'pinia';
import { useCartStore } from '@/stores/cart';

const cart = useCartStore();
const { items, total } = storeToRefs(cart);
const { add } = cart;
</script>

<template>
  <p>В корзине на {{ total }} ₽</p>
  <button @click="add(product)">В корзину</button>
</template>
```

Стор — `reactive`-объект, поэтому ref в нём развёрнуты: `cart.total`, а не `cart.total.value`. Отсюда та же ловушка, что у `reactive` (подробно — в [Основах реактивности](/content/vuejs/reactivity-fundamentals)):

```js
const { total } = cart;              // копия числа, дальше не обновится
const { total } = storeToRefs(cart); // ref, связанный со стором
```

`storeToRefs` превращает в ref только состояние и геттеры. Действия в него не попадают — их деструктурируют напрямую, они привязаны к стору. Всё это проверено.

`useCartStore()` возвращает **один и тот же** экземпляр при каждом вызове. Вне компонента — в навигационном хуке роутера, в модуле API — стор вызывают внутри функции, после `app.use(pinia)`. Если вызвать его на уровне модуля до установки Pinia, будет ошибка `"getActivePinia()" was called but there was no active Pinia`.

### Изменение состояния

Состояние можно менять прямо: `cart.coupon = 'SALE'`. В Pinia нет мутаций, как в Vuex. Для нескольких изменений сразу — `$patch`:

```js
cart.$patch({ coupon: 'SALE' });                        // объектом
cart.$patch((state) => { state.items.push(line); });    // функцией — для массивов
```

Подписки помогают побочным эффектам:

- **`$subscribe`** вызывается при изменении состояния и сообщает тип: `direct`, `patch object`, `patch function`;
- **`$onAction`** вызывается при каждом действии, а `after` и `onError` — по его завершении или ошибке. Удобно для аналитики и логирования.

В проверке `$subscribe` различил все три типа изменений, а `$onAction` поймал и успешное оформление заказа, и ошибку оплаты.

### $reset

`$reset()` возвращает начальное состояние, но только у options-стора: там Pinia может снова вызвать `state()`. У setup-стора начальное состояние — внутри функции, и `$reset` бросает ошибку «built using the setup syntax and does not implement $reset()». Его пишут сами:

```js
function $reset() {
  items.value = [];
  coupon.value = null;
}
return { items, coupon, total, add, checkout, $reset };
```

### Сторы, которые используют другие сторы

Внутри стора можно вызвать другой стор: `const user = useUserStore()` в начале функции `setup` или внутри действия. Нельзя только читать друг друга по кругу во время создания — два стора, которые в `setup` сразу обращаются к состоянию друг друга, зациклятся.

## Селекторы не нужны

В Redux и Zustand компонент подписывается на стор через селектор, иначе он перерисуется от любого изменения (подробно — в [Управлении состоянием React](/content/reactjs/state-management)). Во Vue стор — реактивный объект, и компонент зависит только от полей, которые **прочитал в рендере**:

```text
компонент читает ui.count
ui.theme = 'dark'   → компонент не перерисовался
ui.count++          → перерисовался
```

Проверено на `onUpdated`. Роль мемоизированного селектора в Pinia играет геттер — это `computed` с кешем, который пересчитывается только при изменении своих зависимостей.

## Pinia и Vuex

Vuex — стор Vue 2 и ранних версий Vue 3. В новых проектах его не используют, но он встречается в легаси.

| | Vuex | Pinia |
| --- | --- | --- |
| Изменение состояния | только через мутации: `commit('setCoupon', v)` | напрямую или через действия |
| Асинхронность | действия: `dispatch('checkout')` | действия — обычные функции |
| Структура | один стор с вложенными модулями и пространствами имён | плоский набор независимых сторов |
| Доступ | строки: `store.getters['cart/total']` | импорт: `useCartStore().total` |
| TypeScript | слабый вывод типов | вывод типов из кода |
| Композиция | сложно | обычные функции и композаблы |

Главное упрощение — убрали мутации. Во Vuex они нужны были для отслеживания изменений в DevTools. Pinia отслеживает изменения сама, через реактивность.

## SSR и плагины

### Стор на каждый запрос

Экземпляр стора живёт в экземпляре Pinia, а Pinia устанавливается в приложение. На сервере приложение создают на каждый запрос — и Pinia вместе с ним. Тогда у каждого посетителя своё состояние, и утечки между запросами, как с переменной на уровне модуля, нет (подробно — в [Композаблах](/content/vuejs/composables)). В проверке два рендера с разными пользователями не смешались.

После рендера состояние сериализуют и кладут в HTML, а клиент восстанавливает его перед гидратацией:

```js
// сервер
const html = await renderToString(app);
const state = JSON.stringify(pinia.state.value);   // {"user":{"name":"Аня"}}

// клиент
pinia.state.value = JSON.parse(window.__PINIA_STATE__);
```

`JSON.stringify` для вставки в HTML небезопасен: строка `</script>` в данных закроет тег. Используют сериализацию с экранированием, например `devalue`, — Nuxt делает это сам (подробно — в [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt)).

### Плагины

Плагин — функция, которая получает каждый стор и может добавить свойства, подписки или обёртки:

```js
pinia.use(({ store }) => {
  const saved = localStorage.getItem(store.$id);
  if (saved) store.$patch(JSON.parse(saved));
  store.$subscribe((_, state) => localStorage.setItem(store.$id, JSON.stringify(state)));
});
```

Плагины применяются к сторам, созданным **после** `app.use(pinia)` — в проверке до установки Pinia в приложение плагин не сработал. Готовый плагин сохранения — `pinia-plugin-persistedstate`.

## Красные флаги в ответе

- **«Все данные приложения — в стор».** Серверные данные — в библиотеку загрузки с кешем, локальные — в компонент, фильтры — в адрес.
- **«`const { total } = store` работает».** Стор — `reactive`, деструктуризация копирует, нужен `storeToRefs`.
- **«В setup-сторе можно держать приватное состояние».** Невозвращённый ref пропадает из DevTools, плагинов и SSR.
- **«В Pinia, как в Redux, нужны селекторы».** Компонент зависит только от прочитанных полей, а роль мемоизации играют геттеры.
- **«Стор — обычный глобальный синглтон».** Он живёт в экземпляре Pinia, и при SSR Pinia создают на каждый запрос.

## Как спрашивают на собеседовании

::question
Как выбрать инструмент для состояния во Vue?

#answer
По виду состояния. Локальное — `ref` в компоненте. Контекст части дерева — `provide`/`inject`. Данные с сервера — библиотека загрузки с кешем. Фильтры и страница — параметры URL. Общее клиентское состояние, которое меняют разные части приложения, — стор Pinia.

#more
Типичная ошибка — хранить серверные данные в сторе и вручную писать кеш и инвалидацию. Когда серверное состояние вынесено, в сторе обычно остаются корзина до оформления, черновики, текущий пользователь и настройки интерфейса. Стор нужен и тогда, когда состояние читают вне компонентов — в хуках роутера или модуле API.
::

::question
Из чего состоит стор Pinia?

#answer
Из состояния, геттеров и действий. В setup-сторе это `ref`, `computed` и функции, которые возвращает функция `setup`. В options-сторе — опции `state`, `getters` и `actions`.

#more
Стор — `reactive`-объект и один экземпляр на Pinia. Setup-стор должен вернуть всё состояние, иначе его не увидят DevTools, плагины и SSR. У стора есть служебные методы: `$patch`, `$subscribe`, `$onAction`, `$reset` — последний только у options-стора.
::

::question
Чем Pinia отличается от Vuex?

#answer
В Pinia нет мутаций: состояние меняют напрямую или в действиях, а асинхронные действия — обычные функции. Вместо одного стора с модулями — независимые плоские сторы, которые импортируют, а не вызывают по строкам. Типы выводятся из кода.

#more
Мутации во Vuex нужны были для отслеживания изменений в DevTools, а Pinia отслеживает их через реактивность. Setup-сторы позволяют использовать композаблы и `watch` внутри стора. Vuex встречается в легаси, новые проекты используют Pinia.
::

::question
Зачем нужен storeToRefs?

#answer
Стор — `reactive`-объект, и деструктуризация `const { total } = store` копирует значение: дальше оно не обновится. `storeToRefs(store)` возвращает ref для каждого поля состояния и геттера, и связь сохраняется.

#more
Действия в `storeToRefs` не попадают — их деструктурируют из стора напрямую, они привязаны к нему. В шаблоне можно обойтись без деструктуризации и писать `cart.total`. Та же ловушка у любого `reactive`, решение там — `toRefs`.
::

::question
Нужны ли в Pinia селекторы, как в Redux?

#answer
Нет. Компонент зависит только от тех полей стора, которые прочитал в рендере, и изменение соседнего поля его не перерисует. В Redux и Zustand селекторы нужны, потому что без них компонент перерисуется от любого изменения стора.

#more
Роль мемоизированного селектора играет геттер — `computed` с кешем. Если производное значение нужно только одному компоненту, его считают `computed` в самом компоненте, а не добавляют в стор.
::

::question
Почему у setup-стора нет $reset?

#answer
Начальное состояние setup-стора создаётся внутри функции, и Pinia не может получить его заново. У options-стора есть функция `state()`, и `$reset` просто вызывает её снова.

#more
Для setup-стора `$reset` пишут сами — функцией, которая присваивает начальные значения, и возвращают её вместе с остальным. Удобно держать фабрику начального состояния и использовать её и при создании, и при сбросе.
::

::question
Как Pinia работает при SSR?

#answer
Pinia создаётся на каждый запрос вместе с приложением, поэтому у каждого посетителя своё состояние. После рендера `pinia.state.value` сериализуют в HTML, а клиент восстанавливает его до гидратации.

#more
Состояние, которое setup-стор не вернул, не сериализуется и при гидратации будет начальным. Для вставки в HTML нужна сериализация с экранированием, а не голый `JSON.stringify`. В Nuxt всё это делает модуль `@pinia/nuxt`. Стор на уровне модуля без Pinia — источник утечек между запросами.
::

## Практика

::practice{title="Итог не обновляется"}
```vue
<script setup>
import { useCartStore } from '@/stores/cart';

const { items, total, add } = useCartStore();
</script>

<template>
  <p>{{ total }} ₽</p>
  <button @click="add(product)">В корзину</button>
</template>
```

Кнопка добавляет товар, а сумма не меняется.

#solution
Стор — `reactive`-объект, и деструктуризация скопировала значения `items` и `total` в момент вызова. Действие `add` работает — оно меняет стор, но шаблон показывает копию.

```js
import { storeToRefs } from 'pinia';

const cart = useCartStore();
const { items, total } = storeToRefs(cart);   // ref, связанные со стором
const { add } = cart;                         // действия — напрямую
```

Или не деструктурировать вовсе и писать в шаблоне `cart.total`. В проверке деструктурированный `total` остался `980` после добавления товара, а ref из `storeToRefs` показал `2480`.
::

::practice{title="Корзина пустеет после перезагрузки страницы"}
Приложение с SSR. После загрузки страницы корзина на мгновение показывает товары, а после гидратации становится пустой. Стор:

```js
export const useCartStore = defineStore('cart', () => {
  const lines = ref([]);              // заполняется на сервере
  const items = computed(() => lines.value);
  return { items };
});
```

#solution
Стор вернул только геттер, а сам ref `lines` — нет. Pinia знает о состоянии только по возвращённым ref, поэтому `lines` не попал в `pinia.state.value`, не сериализовался в HTML, и на клиенте стор начал с пустого массива.

```js
export const useCartStore = defineStore('cart', () => {
  const lines = ref([]);
  const items = computed(() => lines.value);
  return { lines, items };   // состояние возвращают всегда
});
```

То же правило касается DevTools и плагинов сохранения: невозвращённое состояние они не видят. В проверке ключи `pinia.state.value.cart` включали только возвращённые ref, а состояние пользователя сериализовалось в `{"user":{"name":"Аня"}}`.
::
