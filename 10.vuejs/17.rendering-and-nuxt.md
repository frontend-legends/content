# Рендеринг и Nuxt

SSR во Vue и мета-фреймворк Nuxt: что выполняется на сервере, как гидратация оживляет готовый HTML, откуда берутся расхождения, стриминг и ленивая гидратация, режимы рендеринга по маршрутам и серверные компоненты. Спрашивают, что такое гидратация и какова её цена, что вызывает hydration mismatch и что даёт Nuxt поверх Vue. Глубже — что Vue делает с расхождением текста и атрибутов, почему `onMounted` не работает на сервере и чем `swr` отличается от `isr` в Nuxt.

::tldr
- **При SSR `setup` выполняется на сервере, а `onMounted` и наблюдатели — нет.** Данные для HTML загружают в `onServerPrefetch` или верхнеуровневым `await`, а работу с DOM и браузерными API — в `onMounted`.
- **Гидратация не перерисовывает HTML, а переиспользует узлы сервера** и навешивает на них обработчики и реактивность. Поэтому клиент обязан отрендерить ровно то же самое.
- **При расхождении Vue исправляет текст на клиентский, а атрибуты и классы оставляет серверными**, с предупреждением в режиме разработки. Ожидаемое расхождение помечают `data-allow-mismatch`.
- **Ленивая гидратация откладывает оживление части страницы** — до видимости, простоя или взаимодействия, через `defineAsyncComponent` с опцией `hydrate`. `useId` даёт одинаковые идентификаторы на сервере и клиенте.
- **Nuxt — Vue плюс сервер, файловая маршрутизация и загрузка данных.** Режим рендеринга задаётся для каждого маршрута через `routeRules`: SSR, предрендер, кеш `swr` и `isr`, только клиент.
::

## Где создаётся HTML

Стратегии в целом — CSR, SSR, SSG, ISR, стриминг — и их компромиссы одинаковы для всех фреймворков и разобраны в [Рендеринге и гидратации React](/content/reactjs/rendering-and-hydration). Коротко: SSR даёт готовый HTML с первым ответом — быстрее первый показ и лучше индексация, но страница становится интерактивной только после загрузки JavaScript и гидратации.

Сквозной пример — страница товара в магазине: название и цена должны быть в HTML сразу, кнопка «В корзину» — работать после гидратации, а блок отзывов внизу — не задерживать остальное.

## SSR во Vue

```js
// сервер
import { createSSRApp } from 'vue';
import { renderToString } from 'vue/server-renderer';

const app = createSSRApp(ProductPage, { id: 7 });
const html = await renderToString(app);
```

На сервере Vue создаёт приложение, выполняет `setup` компонентов и превращает дерево в строку HTML. Реактивность там не нужна: страница рендерится один раз. Поэтому, проверено:

- **`setup` выполняется**, и данные можно загрузить верхнеуровневым `await` или в `onServerPrefetch` — `renderToString` дождётся их;
- **`onMounted`, `onUpdated` и колбэки `watch` не выполняются** — DOM на сервере нет, обновлений тоже.

Отсюда правило: всё, что трогает `window`, `document`, `localStorage`, размеры экрана, — в `onMounted`. Код в `setup`, который обращается к `window`, упадёт на сервере с `window is not defined`.

Второе правило — **приложение на каждый запрос**. Сервер обслуживает многих посетителей, и состояние на уровне модуля общее для всех запросов (подробно — в [Композаблах](/content/vuejs/composables)). Поэтому `createSSRApp`, Pinia и роутер создают в фабрике на каждый запрос.

### Стриминг

`renderToString` ждёт всё дерево. `renderToWebStream` и `renderToNodeStream` отдают HTML **частями**: шапка и название товара уходят сразу, а асинхронный блок отзывов — когда будет готов. В проверке поток выдал несколько частей, которые вместе дали полный HTML. Браузер начинает разбирать и показывать страницу раньше, чем сервер закончит.

## Гидратация

```js
// клиент
const app = createSSRApp(ProductPage, window.__INITIAL_PROPS__);
app.mount('#app');   // в #app уже лежит HTML с сервера
```

`createSSRApp` на клиенте не создаёт DOM заново, а **проходит по готовому HTML**, сопоставляет его с деревом компонентов, привязывает к узлам обработчики событий и запускает реактивность. В проверке после гидратации кнопка осталась тем же DOM-узлом, а клик по ней увеличил счётчик.

Цена гидратации: клиент выполняет тот же код компонентов, что и сервер, и загружает весь их JavaScript. SSR ускоряет первый показ, но не время до интерактивности. Это лечат ленивой гидратацией и серверными компонентами — о них ниже.

### Расхождения

Раз гидратация переиспользует узлы, первый рендер на клиенте обязан совпасть с серверным. Если не совпал — **hydration mismatch**. Что делает Vue, проверено:

- **текст** исправляется на клиентский, с предупреждением «Hydration text content mismatch»;
- **атрибуты, классы и стили** остаются серверными, с предупреждением «Hydration class mismatch» — то есть на странице остаётся устаревшее значение;
- в конце Vue сообщает «Hydration completed but contains mismatches».

Предупреждения выводятся в режиме разработки. В продакшене расхождение молчит, и класс или атрибут просто остаются неправильными.

Откуда берутся расхождения:

- **время и случайность:** `new Date()`, `Math.random()`, `Date.now()` в рендере;
- **браузерные значения:** ширина окна, `localStorage`, часовой пояс и локаль пользователя;
- **разные данные:** сервер загрузил одно, клиент при гидратации — другое, если данные не переданы в HTML;
- **некорректный HTML:** `<div>` внутри `<p>` или `<tr>` без `<tbody>` — браузер перестроит дерево при разборе, и оно не совпадёт.

Лечат так: значения, зависящие от браузера, выставляют в `onMounted`, после гидратации; данные передают с сервера в HTML; браузерные куски оборачивают в `<ClientOnly>` в Nuxt. Если расхождение ожидаемо — например, время «5 минут назад», — атрибут `data-allow-mismatch` на элементе убирает предупреждение. В проверке с `data-allow-mismatch="text"` предупреждений не было. Значение указывает вид: `text`, `children`, `class`, `style`, `attribute`.

### useId

Идентификаторы для `label for` и `aria-describedby` должны совпадать на сервере и клиенте. Счётчик или `Math.random()` дадут разные значения. `useId()` строит идентификатор из положения компонента в дереве — в проверке два поля получили разные id, одинаковые при SSR и гидратации, без предупреждений.

### Ленивая гидратация

Блок отзывов внизу страницы не нужно оживлять сразу. Асинхронный компонент с опцией `hydrate` гидратируется по условию:

```js
import { defineAsyncComponent, hydrateOnVisible } from 'vue';

const Reviews = defineAsyncComponent({
  loader: () => import('./Reviews.vue'),
  hydrate: hydrateOnVisible(),   // ещё hydrateOnIdle, hydrateOnInteraction('click'), hydrateOnMediaQuery
});
```

HTML отзывов виден сразу, а код загружается и выполняется, только когда блок попадёт в зону видимости. Это сокращает работу при загрузке страницы без отказа от SSR.

## Nuxt

Nuxt — мета-фреймворк поверх Vue: сервер, сборка и соглашения, которые иначе пришлось бы собирать вручную.

| Что | Как в Nuxt |
| --- | --- |
| маршруты | файлы в `app/pages/`, вложенность — папками |
| рамки страниц | `app/layouts/` |
| загрузка данных | `useFetch`, `useAsyncData` с передачей в payload ([Загрузка данных](/content/vuejs/data-fetching)) |
| состояние | `useState` и `@pinia/nuxt` — на каждый запрос |
| серверная часть | `server/api/*` на Nitro, разворачивается на Node.js, бессерверных платформах и edge |
| импорты | автоимпорт компонентов, композаблов и API Vue |
| мета-теги и SEO | `useHead`, `useSeoMeta` |
| только клиент | `<ClientOnly>`, суффикс `.client.vue`, `import.meta.client` |

В Nuxt 4 исходники приложения лежат в `app/`, а `server/`, `public/` и `nuxt.config.ts` — в корне проекта.

### Режимы рендеринга по маршрутам

По умолчанию Nuxt рендерит универсально: SSR и гидратация. Но режим можно выбрать для каждого маршрута — это **гибридный рендеринг**:

```js
// nuxt.config.ts
export default defineNuxtConfig({
  routeRules: {
    '/': { prerender: true },              // HTML при сборке
    '/products/**': { swr: 3600 },         // кеш на сервере, обновление в фоне
    '/blog/**': { isr: true },             // как swr, но кеш и на CDN
    '/account/**': { ssr: false },         // только клиент
  },
});
```

- **`prerender`** — HTML создаётся при сборке, как статический сайт;
- **`swr`** — ответ кешируется на сервере или обратном прокси, после истечения срока отдаётся старый, а новый рендерится в фоне;
- **`isr`** — то же, но кеш может жить и на CDN, на платформах, которые это поддерживают; с `true` — до следующего деплоя;
- **`ssr: false`** — для разделов, где SEO не нужно, а данные личные: кабинет, админка.

Правила маршрутов — это настройка рендеринга, а не граница доступа: закрывать данные должен сервер.

### Серверные компоненты

Nuxt умеет рендерить отдельные компоненты **только на сервере**: компонент с суффиксом `.server.vue` или `<NuxtIsland>`, функция за флагом `experimental.componentIslands`. Его HTML приходит готовым, а JavaScript компонента не попадает в бандл и не гидратируется. Это «острова»: статичная страница с интерактивными вкраплениями. Общая идея и сравнение с React Server Components — в [RSC и React 19](/content/reactjs/rsc-and-react-19).

---

## Как выбрать

| Страница | Режим |
| --- | --- |
| лендинг, документация, статьи | `prerender` |
| каталог и карточка товара | SSR с `swr` или `isr` |
| поиск с фильтрами | SSR, кеш по параметрам с осторожностью |
| кабинет, админка, внутренние инструменты | `ssr: false` или обычное SPA |
| большая статичная страница с парой виджетов | острова или ленивая гидратация |

Если SEO и первый показ не важны, SSR добавляет сервер, расхождения и сложность — обычное SPA на Vite проще.

## Красные флаги в ответе

- **«`onMounted` выполнится и на сервере».** На сервере выполняется только `setup`, данные загружают в `onServerPrefetch` или через `await`.
- **«Гидратация заново рисует страницу».** Она переиспользует узлы сервера, поэтому клиентский рендер обязан совпасть.
- **«При расхождении Vue всё исправит».** Текст исправится, а атрибуты и классы останутся серверными.
- **«SSR делает страницу интерактивной быстрее».** Он ускоряет первый показ, интерактивность ждёт JavaScript и гидратацию.
- **«`routeRules` защищают раздел».** Это настройка рендеринга, а не контроль доступа.

## Как спрашивают на собеседовании

::question
Что такое гидратация и какова её цена?

#answer
Оживление HTML, пришедшего с сервера: Vue проходит по готовым узлам, сопоставляет их с деревом компонентов, навешивает обработчики и запускает реактивность. Узлы переиспользуются, а не создаются заново.

#more
Цена — клиент загружает и выполняет тот же код компонентов, что и сервер. SSR ускоряет первый показ, но интерактивность ждёт гидратации. Сокращают это ленивой гидратацией через `defineAsyncComponent` с `hydrate`, островами и серверными компонентами в Nuxt.
::

::question
Что вызывает hydration mismatch и что Vue с ним делает?

#answer
Расхождение первого клиентского рендера с серверным HTML: время и случайные значения, браузерные данные вроде ширины окна и `localStorage`, разные данные на сервере и клиенте, некорректная вложенность HTML.

#more
Vue исправляет расхождение текста на клиентское значение, а атрибуты, классы и стили оставляет серверными, и в продакшене молча. Лечат значениями в `onMounted`, передачей данных с сервера, `<ClientOnly>` и `useId` для идентификаторов. Ожидаемое расхождение помечают `data-allow-mismatch`.
::

::question
Что выполняется на сервере при SSR?

#answer
`setup` компонентов и `onServerPrefetch`, а также верхнеуровневый `await` в `<script setup>` — их сервер ждёт перед отправкой HTML. `onMounted`, `onUpdated` и колбэки наблюдателей на сервере не выполняются.

#more
Обращение к `window` или `document` в `setup` упадёт на сервере. Приложение, роутер и Pinia создают на каждый запрос, иначе состояние одного посетителя попадёт к другому. Стриминг через `renderToWebStream` отдаёт HTML частями.
::

::question
Что даёт Nuxt поверх Vue?

#answer
Сервер и SSR из коробки, файловую маршрутизацию, загрузку данных с передачей в payload, автоимпорт, серверные API на Nitro, мета-теги и выбор режима рендеринга для каждого маршрута.

#more
`useFetch` и `useAsyncData` не дублируют запросы при гидратации, `useState` и `@pinia/nuxt` создают состояние на каждый запрос. Nitro разворачивается на Node.js, бессерверных платформах и edge. В Nuxt 4 исходники лежат в `app/`.
::

::question
Что такое гибридный рендеринг в Nuxt?

#answer
Разные режимы рендеринга для разных маршрутов через `routeRules`: `prerender` при сборке, SSR с кешем `swr` или `isr`, `ssr: false` для клиентских разделов.

#more
`swr` кеширует ответ на сервере или обратном прокси и после истечения срока обновляет его в фоне, `isr` дополнительно кеширует на CDN. Правила не являются контролем доступа. Гибридный рендеринг недоступен при полностью статической генерации через `nuxt generate`.
::

::question
Что такое острова и зачем они нужны?

#answer
Компоненты, которые рендерятся только на сервере: их HTML приходит готовым, а JavaScript не загружается и не гидратируется. Страница остаётся в основном статичной, а интерактивны только отдельные «острова».

#more
В Nuxt это компоненты `.server.vue` и `<NuxtIsland>` за экспериментальным флагом `componentIslands`. Это сокращает объём JavaScript и стоимость гидратации. Похожие идеи — React Server Components и ленивая гидратация во Vue.
::

## Практика

::practice{title="Неверная тема после загрузки"}
Тема хранится в `localStorage`. На сервере её нет, и при гидратации кнопка остаётся со светлой темой, хотя текст на ней правильный:

```vue
<script setup>
const theme = typeof window !== 'undefined' ? localStorage.getItem('theme') : 'light';
</script>

<template>
  <button :class="theme">Тема: {{ theme }}</button>
</template>
```

#solution
Сервер отрендерил `light`, клиент при гидратации — `dark`. Vue исправил текст на клиентский, а класс оставил серверным — отсюда кнопка со светлым классом и надписью «Тема: dark».

```vue
<script setup>
import { ref, onMounted } from 'vue';

const theme = ref('light');            // одинаково на сервере и при гидратации
onMounted(() => {
  theme.value = localStorage.getItem('theme') ?? 'light';   // после гидратации — обычное обновление
});
</script>
```

Первый рендер совпадает, а настоящая тема применяется после монтирования. Чтобы не было вспышки светлой темы, тему кладут в cookie — её видит сервер — или выставляют класс на `html` маленьким встроенным скриптом до загрузки приложения. В проверке при расхождении текст стал клиентским, а класс остался серверным.
::

::practice{title="Тяжёлые отзывы задерживают страницу"}
На странице товара блок отзывов с графиками и фильтрами. Lighthouse показывает долгую загрузку JavaScript и задержку взаимодействия, хотя отзывы внизу и их редко открывают.

#solution
Отзывы гидратируются вместе со всей страницей: их код загружается и выполняется сразу. Им нужен HTML для поисковиков, но не немедленная интерактивность:

```js
import { defineAsyncComponent, hydrateOnVisible } from 'vue';

const Reviews = defineAsyncComponent({
  loader: () => import('./Reviews.vue'),
  hydrate: hydrateOnVisible({ rootMargin: '200px' }),
});
```

HTML отзывов приходит с сервера, а код загрузится, когда блок окажется рядом с зоной видимости. Если отзывы совсем не интерактивны, в Nuxt их делают серверным компонентом, и JavaScript не нужен вовсе. Стратегии `hydrateOnVisible`, `hydrateOnIdle` и `hydrateOnInteraction` экспортируются из `vue` — проверено.
::
