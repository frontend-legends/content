# Композаблы

Как переиспользовать логику с состоянием: функции-композаблы, их аргументы и возвращаемые значения, очистка ресурсов, общее состояние и библиотека VueUse. Спрашивают, что такое композабл, делят ли компоненты состояние одного композабла и чем композаблы лучше миксинов. Глубже — как сделать композабл, который реагирует на смену аргумента, почему возвращают объект из ref, а не `reactive`, и почему общее состояние в модуле опасно при SSR.

::tldr
- **Композабл — функция, которая использует Composition API и возвращает реактивное состояние.** Он переиспользует логику, а не состояние: каждый вызов создаёт своё.
- **Аргументы принимают как ref, геттер или значение и читают через `toValue` внутри `watch` или `computed`** — тогда композабл реагирует на изменения аргумента.
- **Возвращают обычный объект из ref-ов:** его можно деструктурировать без потери реактивности. `reactive`-объект при деструктуризации отдаёт копии.
- **Ресурсы освобождают в `onUnmounted` или `onScopeDispose`.** Второй работает и вне компонента, внутри `effectScope`.
- **Общее состояние — переменная на уровне модуля.** В браузере это синглтон, а на сервере — одно состояние на все запросы: данные одного посетителя достаются другому.
::

---

## Что такое композабл

Сквозной пример — загрузка товара, которая нужна странице товара, модальному окну быстрого просмотра и сравнению:

```js
// useProduct.js
import { ref, watch, toValue } from 'vue';

export function useProduct(id) {
  const product = ref(null);
  const error = ref(null);
  const loading = ref(false);

  watch(() => toValue(id), async (value) => {
    loading.value = true;
    error.value = null;
    try {
      product.value = await fetch(`/api/products/${value}`).then((r) => r.json());
    } catch (e) {
      error.value = e;
    } finally {
      loading.value = false;
    }
  }, { immediate: true });

  return { product, error, loading };
}
```

```vue
<script setup>
const props = defineProps({ id: Number });
const { product, loading, error } = useProduct(() => props.id);
</script>
```

Композабл — **обычная функция**, внутри которой используются `ref`, `computed`, `watch`, хуки жизненного цикла. Имя начинается с `use` — это соглашение, а не требование компилятора. Это прямой аналог кастомных хуков React (подробно — в [Продвинутых хуках](/content/reactjs/advanced-hooks)).

### Логика, а не состояние

Каждый вызов создаёт **своё** состояние:

```js
const a = useCounter();
const b = useCounter(10);
a.inc();
// a.count — 1, b.count — 10
```

Два компонента, вызвавшие `useProduct`, делят поведение, но не данные. Проверено. Если нужно общее состояние, это решается иначе — об этом ниже.

---

## Аргументы

Компонент передаёт `props.id`, и `id` может измениться: пользователь перешёл на соседний товар. Если композабл получит число, он об этом не узнает (подробно — в [Основах реактивности](/content/vuejs/reactivity-fundamentals)):

```js
useProduct(props.id);   // число — загрузится один раз
```

Соглашение: композабл принимает **ref, геттер или обычное значение** (тип `MaybeRefOrGetter`) и читает его через `toValue` **внутри реактивного контекста** — `watch`, `watchEffect` или `computed`:

```js
useProduct(productId);            // ref
useProduct(() => props.id);       // геттер — для пропсов
useProduct(7);                    // константа
```

В проверке все три варианта сработали, а при изменении ref и пропса композабл загрузил новый товар. Чтение `toValue(id)` снаружи `watch`, в теле композабла, снова дало бы снимок.

Для смены `id` во время загрузки нужна ещё отмена устаревшего запроса через `onWatcherCleanup` — подробно в [Computed и наблюдателях](/content/vuejs/computed-and-watchers). А библиотеки загрузки данных решают это вместе с кешем (подробно — в [Загрузке данных](/content/vuejs/data-fetching)).

---

## Что возвращать

Возвращают **обычный объект из ref-ов**:

```js
return { product, error, loading };
```

Его можно деструктурировать — каждое поле остаётся ref. Если вернуть `reactive({ … })`, деструктуризация `const { n } = useX()` отдаст копию значения, и связь пропадёт. Проверено на обоих вариантах.

Кому удобнее обращаться через точку без `.value`, оборачивает результат сам:

```js
const counter = reactive(useCounter());
counter.inc();
counter.count;   // число, ref развернулся
```

Если композабл возвращает одно значение, можно вернуть сам ref. Если только читаемое — `readonly(state)` или `computed`, чтобы потребитель не менял внутреннее состояние напрямую.

## Очистка

Композабл, который подписывается на что-то внешнее, должен отписаться, когда компонент уходит:

```js
export function useWindowEvent(type, handler) {
  onMounted(() => window.addEventListener(type, handler));
  onUnmounted(() => window.removeEventListener(type, handler));
}
```

Хуки жизненного цикла внутри композабла регистрируются в компоненте, который его вызвал, — поэтому композабл с хуками вызывают **синхронно в `setup`**, до первого `await` (подробно — в [Composition API](/content/vuejs/composition-api)). В проверке после размонтирования слушатель не срабатывал.

### onScopeDispose

`onUnmounted` работает только в компоненте. Если композабл может использоваться и вне компонента — в сторе, в тесте, внутри `effectScope`, — очистку регистрируют через `onScopeDispose`:

```js
export function useInterval(fn, ms) {
  const id = setInterval(fn, ms);
  onScopeDispose(() => clearInterval(id));
}
```

У компонента тоже есть область эффектов, и при размонтировании она останавливается, поэтому `onScopeDispose` срабатывает и там. В проверке таймер внутри `effectScope` перестал тикать после `scope.stop()`. `watch` и `computed`, созданные в композабле, останавливаются вместе с областью автоматически.

## Общее состояние

Иногда состояние действительно должно быть одно на всех: текущий пользователь, корзина, открытая модалка. Самый простой способ — объявить ref **вне функции**, на уровне модуля:

```js
// useCart.js
const items = ref([]);   // одно на модуль

export function useCart() {
  const add = (sku) => items.value.push(sku);
  return { items, add };
}
```

Все вызовы получают один и тот же `items`. В браузере это работает: модуль загружается один раз на вкладку.

### Опасность на сервере

При SSR сервер — один долгоживущий процесс, который обрабатывает запросы многих посетителей. Модуль загружается **один раз на процесс**, и переменная на уровне модуля общая для всех запросов:

```text
запрос 1: Аня вошла → currentUser = 'Аня' → HTML с «Аня»
запрос 2: гость      → currentUser всё ещё 'Аня' → HTML с «Аня»
```

В проверке второй рендер для другого посетителя показал имя первого. Это утечка данных между пользователями. Состояние, которое должно жить в пределах приложения, создают на каждый запрос: через `app.provide` при создании приложения или через стор Pinia, который создаётся вместе с приложением (подробно — в [Управлении состоянием](/content/vuejs/state-management) и [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt)). Вариант с `provide` проверен: у каждого запроса оказался свой пользователь.

## Композаблы, миксины и renderless-компоненты

| | Миксины | Renderless-компоненты | Композаблы |
| --- | --- | --- | --- |
| Источник свойств | неявный, через `this` | явный, пропсы слота | явный, возвращаемое значение |
| Конфликты имён | молчаливые | нет | нет, можно переименовать |
| Лишний компонент в дереве | нет | да | нет |
| Параметры | через опции | пропсы | аргументы функции |
| Типизация | слабая | средняя | обычные функции |

Миксины — наследие Options API (подробно — в [Composition API](/content/vuejs/composition-api)), renderless-компоненты — в [Слотах](/content/vuejs/slots).

Композаблы составляются друг из друга: `useProductPage` вызывает `useProduct`, `useCart` и `useRecentlyViewed` и возвращает то, что нужно странице. Это обычная композиция функций.

### Чем композаблы отличаются от хуков React

Композабл вызывается **один раз** в `setup`, а хук React — на каждый рендер. Поэтому у композаблов нет правила порядка вызовов: состояние живёт в ref, а не в ячейке, привязанной к номеру вызова. Ограничение одно — композаблы с хуками жизненного цикла, `inject` или `provide` вызывают синхронно в `setup`. И замыкания внутри композабла не устаревают: они читают `.value` в момент вызова.

## VueUse

[VueUse](https://vueuse.org/) — библиотека из сотен готовых композаблов. Прежде чем писать свой `useLocalStorage` или `useDebounce`, стоит проверить её:

| Композабл | Что делает |
| --- | --- |
| `useStorage`, `useLocalStorage` | ref, синхронизированный с `localStorage` |
| `refDebounced`, `useDebounceFn` | отложенное значение или функция |
| `useEventListener` | слушатель, который снимается сам |
| `useIntersectionObserver`, `useResizeObserver` | наблюдатели за элементом |
| `useFetch` | загрузка с состоянием и отменой |
| `createSharedComposable` | одно состояние на всех потребителей в пределах приложения |

В проверке `useStorage` записал значение в `localStorage`, `refDebounced` отдал только последнее значение после паузы, `useEventListener` снял слушатель при размонтировании, а `createSharedComposable` создал состояние один раз на два вызова. Почти все композаблы VueUse принимают `MaybeRefOrGetter` и безопасно работают при SSR, где нет `window`.

---

## Красные флаги в ответе

- **«Компоненты с одним композаблом делят состояние».** Каждый вызов создаёт своё, общее — только объявленное вне функции.
- **«Композаблу можно передать `props.id`».** Передано число, нужен геттер `() => props.id` или ref.
- **«Композабл должен возвращать `reactive`».** Деструктуризация `reactive` отдаёт копии, возвращают объект из ref.
- **«Состояние на уровне модуля — нормальный глобальный стор».** На сервере оно общее для всех запросов и утекает между пользователями.
- **«`onUnmounted` в композабле сработает где угодно».** Только в компоненте, вне его — `onScopeDispose`.

## Как спрашивают на собеседовании

::question
Что такое композабл?

#answer
Функция, которая использует Composition API — `ref`, `computed`, `watch`, хуки жизненного цикла — и возвращает реактивное состояние и функции. Нужна, чтобы переиспользовать логику с состоянием между компонентами. Имя по соглашению начинается с `use`.

#more
Аналог кастомных хуков React и замена миксинов и renderless-компонентов. Композабл с хуками жизненного цикла вызывают синхронно в `setup`, а композабл только с реактивностью работает и вне компонентов. Готовые композаблы — в VueUse.
::

::question
Делят ли компоненты состояние одного композабла?

#answer
Нет. Каждый вызов создаёт своё состояние: два компонента с `useCounter()` получают независимые счётчики. Композабл переиспользует логику, а не данные.

#more
Общее состояние получается, если объявить ref вне функции, на уровне модуля. В браузере это синглтон, но при SSR такая переменная общая для всех запросов и утекает между пользователями. Для общего состояния приложения берут Pinia или `provide` на уровне приложения.
::

::question
Как сделать композабл, который реагирует на изменение аргумента?

#answer
Принимать ref или геттер и читать через `toValue` внутри `watch`, `watchEffect` или `computed`: `watch(() => toValue(id), load, { immediate: true })`. Вызывать как `useProduct(() => props.id)`.

#more
Если передать `props.id` или прочитать `toValue(id)` в теле композабла, получится снимок, и смена аргумента ничего не изменит. Тип такого аргумента — `MaybeRefOrGetter<T>`. Для асинхронной работы добавляют отмену устаревших запросов через `onWatcherCleanup`.
::

::question
Почему композабл возвращает объект из ref, а не reactive?

#answer
Объект из ref можно деструктурировать: каждое поле остаётся ref и сохраняет связь. Деструктуризация `reactive` копирует значения, и реактивность теряется.

#more
Кому удобнее без `.value`, оборачивает результат сам: `reactive(useCounter())` развернёт ref-ы. Если состояние не должно меняться снаружи, возвращают `readonly` или `computed` и функции для изменения.
::

::question
Почему у композаблов нет правил хуков, как в React?

#answer
Композабл вызывается один раз в `setup`, а состояние хранится в ref, а не в ячейке, привязанной к порядку вызова. Поэтому композабл можно вызвать по условию или в цикле.

#more
Ограничение одно: композаблы с хуками жизненного цикла, `inject` и `provide` вызывают синхронно в `setup`, чтобы они привязались к текущему компоненту. После `await` в обычном `setup()` экземпляра уже нет. Замыкания внутри композабла не устаревают, потому что читают `.value` в момент вызова.
::

::question
Чем композаблы лучше миксинов?

#answer
У композабла явный источник: видно, какая функция что вернула, и имена можно переименовать при деструктуризации. Миксины подмешивают свойства в `this` неявно, а конфликты имён разрешаются молча.

#more
Композаблы принимают параметры как обычные функции, составляются друг из друга и хорошо типизируются. По сравнению с renderless-компонентами они не добавляют компонент в дерево. Миксины во Vue 3 работают, но в новом коде их не используют.
::

## Практика

::practice{title="Товар не меняется при переходе"}
На странице товара есть ссылки на похожие товары. При переходе адрес меняется, а товар — нет:

```js
export function useProduct(id) {
  const product = ref(null);
  onMounted(async () => {
    product.value = await loadProduct(id);
  });
  return { product };
}

// в компоненте
const { product } = useProduct(props.id);
```

#solution
Две проблемы. Композабл получил число, а не источник, и загрузка привязана к монтированию, а не к `id`. Роутер переиспользует компонент при смене параметра, поэтому `onMounted` второй раз не сработает.

```js
export function useProduct(id) {
  const product = ref(null);
  watch(() => toValue(id), async (value, _, onCleanup) => {
    let stale = false;
    onCleanup(() => { stale = true; });
    const data = await loadProduct(value);
    if (!stale) product.value = data;
  }, { immediate: true });
  return { product };
}

const { product } = useProduct(() => props.id);
```

Теперь загрузка следует за `id`, а флаг `stale` не даёт ответу на старый товар перезаписать новый. В проверке композабл загрузил новый товар при смене ref и пропса.
::

::practice{title="Чужое имя в шапке"}
Приложение с SSR. Иногда посетитель видит в шапке имя другого пользователя:

```js
// useUser.js
const currentUser = ref(null);

export function useUser() {
  return { currentUser, setUser: (u) => { currentUser.value = u; } };
}
```

#solution
`currentUser` объявлен на уровне модуля. На сервере модуль загружается один раз на процесс, и все запросы делят одну переменную. Рендер для гостя показал пользователя из прошлого запроса.

```js
// состояние на приложение, а не на процесс
const UserKey = Symbol('user');

export function createApp() {
  const app = createSSRApp(App);
  app.provide(UserKey, ref(null));   // своё для каждого запроса
  return app;
}

export function useUser() {
  const currentUser = inject(UserKey);
  return { currentUser, setUser: (u) => { currentUser.value = u; } };
}
```

Pinia решает то же самое: стор создаётся вместе с приложением на каждый запрос. Переменные модуля на сервере допустимы только для того, что действительно общее и неизменяемо: конфигурация, справочники. В проверке модульная версия показала «Аня» второму посетителю, версия с `provide` — «гость».
::
