# Provide и inject

Как передать данные через несколько уровней компонентов без пробрасывания пропсов: `provide` у предка, `inject` у потомка, реактивность значения, защита от изменений, значения по умолчанию и уровень приложения. Спрашивают, какую проблему решает `provide/inject`, как сделать значение реактивным и чем это лучше Context в React. Глубже — почему провайдер не видит своё значение, почему `provide(key, count.value)` перестаёт обновляться и когда брать стор вместо `inject`.

::tldr
- **`provide` делает значение доступным всему поддереву, `inject` достаёт его на любой глубине.** Побеждает ближайший предок с таким ключом, и сам провайдер своего значения не видит — `inject` ищет только у предков.
- **Реактивность передаётся, только если передан ref или `reactive`.** `provide(key, count.value)` передаёт число, и потомки больше не узнают об изменениях.
- **Изменения держат у владельца:** отдают `readonly`-обёртку и функции для изменения. Иначе любой потомок молча меняет общее состояние.
- **Без провайдера `inject` возвращает `undefined` с предупреждением,** если не задано значение по умолчанию. Ключи — символы, чтобы не было коллизий, а с `InjectionKey` — ещё и типы.
- **Потребители обновляются точечно:** перерисуется только тот, кто прочитал изменившееся поле, а не все, как у Context в React.
::

---

## Проблема

Сквозной пример — тема и валюта магазина. Они нужны карточке товара, которая лежит глубоко: `App → Catalog → ProductGrid → ProductCard → Price`. Передавать их пропсами через все уровни — **prop drilling**: промежуточные компоненты принимают и пробрасывают то, что им самим не нужно, и при каждом изменении API их приходится переписывать.

`provide` и `inject` решают это так:

```vue
<!-- App.vue -->
<script setup>
import { provide, ref } from 'vue';

const currency = ref('₽');
provide('currency', currency);
</script>
```

```vue
<!-- Price.vue — на любой глубине -->
<script setup>
import { inject } from 'vue';

defineProps({ value: Number });
const currency = inject('currency');
</script>

<template><span>{{ value }} {{ currency }}</span></template>
```

Промежуточные компоненты о валюте не знают.

## Как ищется значение

`inject` поднимается по цепочке **предков** и берёт значение у ближайшего, который предоставил этот ключ. Отсюда два правила, оба проверены:

- **ближайший провайдер побеждает:** если `Catalog` предоставил свою тему, потомки `Catalog` увидят её, а остальные — тему `App`. Так переопределяют значение для части дерева;
- **провайдер своего значения не видит:** `inject` внутри компонента, который сам вызвал `provide`, получит значение от **его** предка. Это позволяет компоненту прочитать значение сверху и предоставить вниз изменённое — например, увеличить уровень вложенности заголовков.

Оба вызова работают только синхронно в `setup` — как и хуки жизненного цикла (подробно — в [Composition API](/content/vuejs/composition-api)). После `await` в обычном `setup()` `inject` вернёт `undefined`.

### Уровень приложения

Значение можно предоставить всему приложению:

```js
const app = createApp(App);
app.provide('currency', '₽');
```

Так работают плагины: роутер, Pinia, i18n кладут свои объекты через `app.provide`, а композаблы `useRouter()`, `useI18n()` внутри вызывают `inject`. Вне компонента значение приложения можно получить через `app.runWithContext(() => inject('currency'))` — это используют навигационные хуки роутера и сторы. Проверено.

Значение нашлось. Но обновится ли `Price`, если валюта поменяется?

## Реактивность

`provide` передаёт **то, что ему дали**. Реактивность сохраняется, только если дали реактивный источник:

```js
provide('currency', currency);          // ref — потомки видят изменения
provide('currency', currency.value);    // строка — снимок на момент provide
provide('theme', { color: color.value });   // обычный объект — тоже снимок
```

В проверке после изменения `count` потребитель ref показал новое значение, а потребители `count.value` и обычного объекта — старое. Это то же правило, что и везде: реактивность теряется, когда значение копируется (подробно — в [Основах реактивности](/content/vuejs/reactivity-fundamentals)).

### Кто меняет данные

Если отдать потомкам изменяемый `reactive`-объект, любой из них может его изменить, и найти источник изменения будет трудно. Изменения оставляют владельцу:

```js
// CartProvider.vue
const cart = reactive({ items: [] });

provide('cart', {
  state: readonly(cart),
  add: (sku) => cart.items.push(sku),
  remove: (sku) => { cart.items = cart.items.filter((s) => s !== sku); },
});
```

Потомок читает `state` и вызывает `add`. Прямая запись в `readonly` отклоняется с предупреждением «target is readonly» — проверено. Это тот же однонаправленный поток, что у пропсов и событий, только через несколько уровней.

### Точечные обновления

Здесь главное отличие от Context в React. Там смена значения контекста перерисовывает **всех** потребителей, и это лечат разделением контекстов и мемоизацией (подробно — в [Context API](/content/reactjs/context-api)). Во Vue `inject` — просто способ получить ссылку на реактивные данные. Компонент зависит только от тех полей, которые прочитал в рендере:

```text
theme.color = 'red'
→ перерисовался потребитель, читающий theme.color
→ потребитель theme.size и сам провайдер — нет
```

Проверено на `onUpdated`: обновился только один потребитель.

## Ключи и значения по умолчанию

### Значения по умолчанию

Без провайдера `inject` возвращает `undefined` и предупреждает «injection not found». Значение по умолчанию убирает и то, и другое:

```js
const currency = inject('currency', '₽');
const config = inject('config', () => ({ precision: 2 }), true);   // фабрика: третий аргумент true
```

Фабрика нужна для объектов, чтобы каждый потребитель получил свой экземпляр, и для дорогих значений, чтобы не создавать их, когда провайдер есть.

Значение по умолчанию уместно, если компонент может работать сам по себе. Если без провайдера он бессмыслен — например, `Tab` без `Tabs`, — лучше явная ошибка:

```js
export function useTabs() {
  const ctx = inject(TabsKey);
  if (!ctx) throw new Error('useTabs must be used inside <Tabs>');
  return ctx;
}
```

### Ключи-символы

Строковые ключи могут совпасть у двух библиотек. Ключ-символ уникален:

```js
// keys.js
export const CurrencyKey = Symbol('currency');
```

Ключ экспортируют из одного модуля и импортируют и в провайдере, и в потребителе. С TypeScript ключ объявляют как `InjectionKey<Ref<string>>`, и `inject` выводит тип значения (подробно — в [TypeScript с Vue](/content/typescript/ts-with-vue)).

## Когда что использовать

| Задача | Решение |
| --- | --- |
| данные для прямого ребёнка | пропсы |
| настройка для поддерева: тема, валюта, локаль, плотность | `provide`/`inject` |
| связь составного компонента: `Tabs` и `Tab`, `Form` и `Field` | `provide`/`inject` с ключом-символом |
| общее состояние независимых частей приложения | стор Pinia ([Управление состоянием](/content/vuejs/state-management)) |
| глобальный сервис: роутер, i18n, клиент API | плагин с `app.provide` |

`provide/inject` привязан к дереву: значение видно только потомкам провайдера, и разные части дерева могут получить разные значения. Стор глобален, у него есть инструменты разработчика, SSR-поддержка и доступ вне компонентов. Если данные нужны «везде» и их меняют разные части приложения, — это стор. Если данные описывают контекст части дерева, — `provide`.

---

## Красные флаги в ответе

- **«`provide` передаёт значение, и оно реактивно само по себе».** Реактивен только ref или `reactive`, `count.value` — снимок.
- **«Компонент может прочитать то, что сам предоставил».** `inject` ищет только у предков.
- **«При изменении значения перерисуются все потребители, как с Context».** Перерисуются только те, кто прочитал изменившееся поле.
- **«Потомки могут менять предоставленное состояние напрямую».** Могут, если не защитить, — поэтому отдают `readonly` и функции изменения.
- **«`provide/inject` заменяет стор».** Он привязан к дереву, у стора другие задачи: глобальность, инструменты, доступ вне компонентов.

## Как спрашивают на собеседовании

::question
Какую проблему решает provide/inject?

#answer
Prop drilling: когда данные нужны глубоко вложенному компоненту, их приходится пробрасывать пропсами через уровни, которым они не нужны. `provide` у предка делает значение доступным всему поддереву, `inject` достаёт его на любой глубине.

#more
Побеждает ближайший провайдер, поэтому значение можно переопределить для части дерева. Сам провайдер своего значения не видит: `inject` ищет у предков. На уровне приложения значение даёт `app.provide` — так работают плагины, например роутер и Pinia.
::

::question
Как сделать инъекцию реактивной?

#answer
Предоставить реактивный источник: ref, `reactive` или `computed`. `provide('currency', currency)` с ref — потомки видят изменения. `provide('currency', currency.value)` передаёт строку, и обновлений не будет.

#more
Обычный объект с полями из `.value` — тоже снимок. Потомок, получивший ref, читает `.value` в скрипте, а в шаблоне ref разворачивается. Для производных значений предоставляют `computed`, чтобы потребители не пересчитывали одно и то же.
::

::question
Как запретить потомкам мутировать предоставленное состояние?

#answer
Отдать `readonly`-обёртку для чтения и функции для изменения: `provide('cart', { state: readonly(cart), add, remove })`. Прямая запись в `readonly` отклоняется с предупреждением.

#more
Так сохраняется однонаправленный поток: данные меняет только владелец, и источник изменений всегда один. Это тот же принцип, что пропсы вниз и события вверх, только через несколько уровней дерева.
::

::question
Зачем символы в качестве ключей?

#answer
Символ уникален, поэтому ключи двух библиотек не совпадут. Ключ экспортируют из одного модуля и импортируют в провайдере и потребителе.

#more
С TypeScript ключ объявляют как `InjectionKey<T>`, и `inject` выводит тип значения, а `provide` проверяет его. `inject` возвращает `T | undefined`, потому что провайдера может не быть, — либо значение по умолчанию, либо функция-обёртка, которая бросает понятную ошибку.
::

::question
Чем provide/inject во Vue лучше Context в React по перерисовкам?

#answer
В React смена значения контекста перерисовывает всех потребителей. Во Vue `inject` — ссылка на реактивные данные, и компонент зависит только от полей, которые прочитал. Изменение `theme.color` перерисует только тех, кто читает `color`.

#more
Поэтому во Vue не нужно разделять контексты и мемоизировать значение, как в React. Цена — нужно не потерять реактивность: предоставлять ref или `reactive`, а не `.value`.
::

::question
provide/inject или Pinia?

#answer
`provide/inject` — для контекста части дерева: тема, локаль, связь `Tabs` и `Tab`, `Form` и `Field`. Pinia — для общего состояния приложения, которое меняют разные независимые части.

#more
`provide` привязан к дереву: разные поддеревья могут получить разные значения, а вне дерева значение недоступно. У стора — глобальность, инструменты разработчика, поддержка SSR и доступ вне компонентов, например в навигационных хуках роутера.
::

## Практика

::practice{title="Валюта не переключается"}
```vue
<!-- App.vue -->
<script setup>
import { provide, ref } from 'vue';

const currency = ref('₽');
provide('currency', currency.value);

function switchCurrency() { currency.value = '$'; }
</script>
```

После `switchCurrency()` цены всё ещё в рублях.

#solution
`provide` получил строку `'₽'`, а не ref. Потомки держат снимок, и изменение `currency` до них не доходит.

```js
provide('currency', currency);                 // ref
// или только для чтения:
provide('currency', readonly(currency));
```

В потребителе `inject('currency')` вернёт ref: в шаблоне он развернётся, в скрипте нужен `.value`. В проверке потребитель ref обновился, а потребитель `.value` остался прежним.
::

::practice{title="Кто удалил товары?"}
Корзину предоставляют через `provide('cart', cart)`, где `cart = reactive({ items: [] })`. Иногда товары исчезают, и непонятно, какой компонент это делает.

#solution
Любой потомок может изменить `cart` напрямую — найти виновника можно только поиском по коду. Изменения нужно оставить у владельца:

```js
// CartProvider.vue
const cart = reactive({ items: [] });

provide(CartKey, {
  state: readonly(cart),
  add(sku) { cart.items.push(sku); },
  remove(sku) { cart.items = cart.items.filter((s) => s !== sku); },
  clear() { cart.items = []; },
});
```

Теперь прямая запись в `state` отклоняется с предупреждением «target is readonly», а все изменения проходят через три функции — там удобно поставить точку останова или лог. Если корзина нужна в разных частях приложения и вне компонентов, её переносят в стор Pinia. В проверке `push` в `readonly` не изменил корзину, а `add` — изменил.
::
