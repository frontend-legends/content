# Тестирование Vue

Как тестировать Vue-компоненты: Vue Test Utils и Testing Library, асинхронные обновления, события и `v-model`, заглушки и плагины, `Teleport`, запросы и композаблы. Спрашивают, зачем `await` перед проверками, чем Vue Test Utils отличается от Testing Library и как тестировать композабл. Глубже — почему одного `nextTick` мало после запроса, почему `wrapper.vm` видит внутреннее состояние закрытого компонента и где искать содержимое телепорта.

::tldr
- **Тест проверяет поведение, а не реализацию:** что пользователь видит и что компонент сообщает наружу. Внутренние переменные через `wrapper.vm` — путь к тестам, которые ломаются при рефакторинге.
- **Обновления DOM асинхронные,** поэтому `trigger` и `setValue` возвращают промис, и его ждут. После запроса одного `nextTick` мало — нужен `flushPromises` или `findBy` в Testing Library.
- **Контракт компонента — пропсы на входе, DOM и события на выходе.** `wrapper.emitted()` проверяет события, а `v-model` тестируют пропсом `modelValue` и обработчиком `onUpdate:modelValue`.
- **Testing Library ищет элементы по ролям и подписям и не даёт доступа к внутренностям,** Vue Test Utils даёт и то, и другое. Поведение удобнее проверять первой, контракт событий — второй.
- **Композабл без хуков проверяют напрямую в `effectScope`,** с хуками жизненного цикла и `inject` — через компонент-хозяина.
::

## Что проверять

Принципы — тестировать поведение, искать элементы как пользователь, подменять сеть, а не модули, — общие для фреймворков и разобраны в [Тестировании React](/content/reactjs/testing-react) и [Стратегии тестирования](/content/testing-deploying/testing-strategy-and-pyramid). Здесь — как это делается во Vue.

Сквозной пример — счётчик количества в корзине:

```vue
<!-- QtyStepper.vue -->
<script setup>
const qty = defineModel({ type: Number, default: 1 });
const note = defineModel('note', { default: '' });
const props = defineProps({ max: { type: Number, default: 3 } });
const emit = defineEmits(['limit']);

function inc() {
  if (qty.value >= props.max) return emit('limit', props.max);
  qty.value++;
}
</script>

<template>
  <button aria-label="Больше" @click="inc">+</button>
  <output>{{ qty }}</output>
  <input aria-label="Комментарий" v-model="note">
</template>
```

Его **контракт**: пропсы `modelValue`, `note`, `max` на входе; на выходе — DOM, события `update:modelValue`, `update:note` и `limit`. Тесты проверяют именно это.

## Vue Test Utils

```js
import { mount } from '@vue/test-utils';
import QtyStepper from './QtyStepper.vue';

test('увеличивает количество', async () => {
  const wrapper = mount(QtyStepper);
  await wrapper.find('button').trigger('click');
  expect(wrapper.find('output').text()).toBe('2');
});
```

`mount` создаёт компонент и возвращает обёртку: `find` ищет элемент по селектору, `trigger` вызывает событие, `setValue` вводит значение в поле, `text()` и `html()` возвращают содержимое.

### Почему await

Vue обновляет DOM не сразу, а в очереди, одним проходом (подробно — в [Продвинутой реактивности](/content/vuejs/reactivity-advanced)). `trigger` и `setValue` возвращают промис, который разрешается после обновления. Без `await` проверка увидит старый DOM — в проверке без ожидания счётчик ещё показывал `1`, после `nextTick` — `2`.

### События

```js
const wrapper = mount(QtyStepper, { props: { modelValue: 3, max: 3 } });
await wrapper.find('button').trigger('click');

expect(wrapper.emitted('limit')).toEqual([[3]]);       // массив вызовов, у каждого — массив аргументов
expect(wrapper.emitted('update:modelValue')).toBeUndefined();
```

`emitted()` — то, что компонент сообщил родителю. Это часть контракта, и проверять её нормально.

### v-model

Родителя в тесте нет, и обновлённое значение никто не передаст обратно. Его роль играет обработчик события:

```js
const wrapper = mount(QtyStepper, {
  props: {
    modelValue: 1,
    'onUpdate:modelValue': (value) => wrapper.setProps({ modelValue: value }),
  },
});

await wrapper.find('button').trigger('click');
expect(wrapper.props('modelValue')).toBe(2);
```

В проверке после клика проп стал `2`, а `setValue('позвонить')` в поле комментария вызвал `update:note` с этим значением.

### wrapper.vm

`wrapper.vm` даёт доступ к экземпляру. Подвох: в тестах он видит **внутренние переменные даже закрытого `<script setup>`**. В режиме разработки, в котором работают Vitest и dev-сервер, `setup` возвращает привязки отдельно от шаблона, и Vue Test Utils их открывает. В продакшен-сборке шаблон встроен в `setup`, и тех же переменных снаружи нет. В проверке `wrapper.vm.secret` был `42` для сборки в режиме разработки и `undefined` — для продакшен-сборки.

Тест, который читает `wrapper.vm.qty`, проверяет реализацию: переименование переменной сломает его, хотя поведение не изменилось. Проверяют DOM и события.

## Окружение компонента

### Плагины и провайдеры

Компоненту с `useRoute()` или стором нужны роутер и Pinia. Их передают через `global`:

```js
const router = createRouter({ history: createMemoryHistory(), routes });
router.push('/cart');
await router.isReady();

const wrapper = mount(CartBadge, {
  global: { plugins: [createPinia(), router], provide: { [ThemeKey]: 'dark' } },
});
```

`createMemoryHistory` не трогает адрес окна. Для стора есть `createTestingPinia` из `@pinia/testing`: действия по умолчанию подменены шпионами, а начальное состояние задаётся параметром. В проверке компонент с настоящими Pinia и роутером показал `2 · /cart`.

### Заглушки

`shallowMount` заменяет все дочерние компоненты заглушками — в проверке тяжёлый график стал `<heavy-chart-stub points="1,2">`. Это изолирует компонент, но проверяет его в отрыве от детей, и такой тест может пройти, когда страница сломана. Чаще используют `mount` и заглушают только тяжёлое или внешнее: `global: { stubs: { HeavyChart: true } }`.

### Teleport

Содержимое `Teleport` уходит в `body`, и `wrapper.find` его не видит — поиск идёт внутри обёртки компонента. В проверке `find('[role=dialog]')` ничего не нашёл, а `document.body.querySelector` — нашёл. Два способа:

- **заглушка** `global: { stubs: { teleport: true } }` рисует содержимое на месте, и `find` работает;
- **поиск по документу** — так делает Testing Library, у которой `screen` ищет по всему `document.body`.

## Асинхронность и запросы

```js
const wrapper = mount(ProductTitle);   // в onMounted загружает товар
await nextTick();
wrapper.text();                         // ещё «…»
await flushPromises();
wrapper.text();                         // «Улун»
```

`nextTick` ждёт один проход очереди Vue, а загрузка — это цепочка промисов: `fetch`, `json()`, присваивание. `flushPromises` ждёт, пока выполнятся все уже запланированные промисы. В проверке после `nextTick` заголовок был `…`, после `flushPromises` — «Улун». В Testing Library то же решают `findBy*`, которые повторяют поиск до появления элемента.

Сеть подменяют на уровне запросов через :term[MSW]{def="Mock Service Worker: перехватывает запросы и отвечает подготовленными данными"}, а не мокают модуль `fetch` или клиент API: так тест проверяет и сериализацию, и обработку ошибок (подробно — в [Тестировании React](/content/reactjs/testing-react)). Если компонент использует Vue Query, в тест передают свой `QueryClient` с `retry: false`, чтобы ошибка не повторялась трижды.

## Testing Library для Vue

```js
import { render, screen, fireEvent } from '@testing-library/vue';

test('увеличивает количество', async () => {
  render(QtyStepper, { props: { modelValue: 1 } });
  await fireEvent.click(screen.getByRole('button', { name: 'Больше' }));
  expect(screen.getByRole('status')).toHaveTextContent('2');
});
```

Testing Library построена поверх Vue Test Utils, но доступа к экземпляру не даёт: только DOM, роли и подписи. Это и ограничение, и защита — тест проверяет то, что видит пользователь, и заодно доступность: кнопку без подписи по имени не найти. `fireEvent` во Vue-версии асинхронный и ждёт обновления DOM. В проверке кнопка нашлась по `aria-label`, а `<output>` — по роли `status`.

Что выбрать: Testing Library — для поведения и сценариев пользователя, Vue Test Utils — когда нужно проверить контракт событий или настроить заглушки тонко. В одном проекте их совмещают.

## Композаблы

Композабл без хуков жизненного цикла — обычная функция с реактивностью. Его проверяют напрямую, а наблюдатели и `computed` собирают в `effectScope`, чтобы остановить после теста:

```js
test('не превышает максимум', () => {
  const scope = effectScope();
  const { n, inc } = scope.run(() => useCounter(2));
  inc(); inc(); inc();
  expect(n.value).toBe(2);
  scope.stop();
});
```

Если композабл использует `onMounted`, `inject` или `provide`, ему нужен экземпляр компонента. Создают компонент-хозяина:

```js
function withSetup(composable, options) {
  let result;
  const wrapper = mount(defineComponent({ setup() { result = composable(); return () => h('div'); } }), options);
  return [result, wrapper];
}

const [{ mounted }, wrapper] = withSetup(() => useMounted());
expect(mounted.value).toBe(true);
wrapper.unmount();   // проверить очистку
```

Оба способа проверены. `wrapper.unmount()` в конце проверяет, что композабл освобождает ресурсы.

## Что ещё

- **Тест-раннер** — обычно Vitest: он использует ту же конфигурацию Vite и компилирует `.vue` (подробно — в [Тест-раннерах](/content/testing-deploying/test-runners)). Окружение DOM — jsdom или happy-dom.
- **Компонентные тесты в браузере** — Vitest Browser Mode или Playwright Component Testing, когда важны настоящие стили, раскладка и браузерные API.
- **Сквозные тесты** проверяют приложение целиком через браузер (подробно — в [E2E-тестировании](/content/testing-deploying/e2e-testing)).
- **Проверка типов шаблонов** через `vue-tsc` ловит часть ошибок, которые иначе нашёл бы тест (подробно — в [TypeScript с Vue](/content/typescript/ts-with-vue)).

## Красные флаги в ответе

- **«Проверяю внутренние переменные через `wrapper.vm`».** Это тест реализации, и он работает только в сборке режима разработки.
- **«`trigger` без `await` — нормально».** DOM обновится асинхронно, и проверка увидит старое состояние.
- **«После запроса достаточно `nextTick`».** Это один проход очереди, а запрос — цепочка промисов, нужен `flushPromises` или `findBy`.
- **«`shallowMount` — лучший вариант для юнит-тестов».** Компонент проверяется без детей, и тест проходит, когда страница сломана.
- **«`find` найдёт содержимое модального окна».** Содержимое `Teleport` в `body`, вне обёртки компонента.

## Как спрашивают на собеседовании

::question
Какой главный принцип тестирования компонентов?

#answer
Проверять поведение, а не реализацию: что пользователь видит и что компонент сообщает наружу. Входы — пропсы и действия пользователя, выходы — DOM и события.

#more
Тест на внутренние переменные или вызовы методов ломается при рефакторинге, хотя поведение не изменилось. Элементы ищут по ролям и подписям, как пользователь, сеть подменяют на уровне запросов через MSW. Проверка `emitted()` — нормальная часть контракта.
::

::question
Зачем await перед проверками в Vue Test Utils?

#answer
Vue обновляет DOM асинхронно, одним проходом очереди. `trigger` и `setValue` возвращают промис, который разрешается после обновления. Без `await` проверка увидит старый DOM.

#more
`await nextTick()` ждёт один проход очереди. Если компонент загружает данные, этого мало: запрос — цепочка промисов, и нужен `flushPromises()` или `findBy*` в Testing Library. `setProps` тоже асинхронный.
::

::question
Чем отличаются Vue Test Utils и Testing Library?

#answer
Vue Test Utils даёт обёртку с доступом к экземпляру, пропсам, событиям `emitted()` и тонкой настройке заглушек. Testing Library работает только через DOM: роли, подписи, текст — и не даёт доступа к внутренностям.

#more
Testing Library подталкивает к тестам поведения и заодно проверяет доступность. Vue Test Utils удобен для контракта событий и `v-model`. Testing Library построена поверх Vue Test Utils, и в одном проекте их совмещают.
::

::question
Как тестировать v-model на компоненте?

#answer
Передать проп `modelValue` и обработчик `onUpdate:modelValue`, который обновляет проп через `setProps`. Так тест играет роль родителя: компонент испускает новое значение, и оно возвращается пропсом.

#more
Можно и просто проверить `emitted('update:modelValue')`, если важен только факт события. Для именованных моделей — `note` и `onUpdate:note`. В Testing Library то же делают обёрткой-родителем с настоящим `v-model`.
::

::question
Как тестировать композабл?

#answer
Композабл без хуков вызывают напрямую внутри `effectScope` и проверяют возвращённые ref, а потом останавливают область. Композабл с `onMounted`, `inject` или `provide` вызывают в `setup` компонента-хозяина, смонтированного через `mount`.

#more
`wrapper.unmount()` в конце проверяет очистку: снятые слушатели, остановленные таймеры. Зависимости — роутер, Pinia, `provide` — передают через `global` в опциях `mount`. Таймеры удобно контролировать фейковыми таймерами раннера.
::

::question
Почему тест не находит содержимое модального окна?

#answer
Окно, скорее всего, в `Teleport`, и его содержимое отрисовано в `body`, вне обёртки компонента. `wrapper.find` ищет внутри обёртки.

#more
Решения: заглушка `global: { stubs: { teleport: true } }`, которая рисует содержимое на месте, или поиск по `document.body` — так ищет `screen` в Testing Library. Если монтировать с `attachTo: document.body`, после теста нужен `unmount`, чтобы окно не осталось в документе.
::

## Практика

::practice{title="Тест проверяет устаревший DOM"}
```js
test('увеличивает количество', () => {
  const wrapper = mount(QtyStepper);
  wrapper.find('button').trigger('click');
  expect(wrapper.find('output').text()).toBe('2');   // падает: '1'
});
```

#solution
`trigger` вызвал обработчик, `qty` стал `2`, но DOM обновится только после прохода очереди Vue. Проверка выполнилась раньше. `trigger` возвращает промис обновления, его ждут:

```js
test('увеличивает количество', async () => {
  const wrapper = mount(QtyStepper);
  await wrapper.find('button').trigger('click');
  expect(wrapper.find('output').text()).toBe('2');
});
```

Если после клика компонент ещё загружает данные, добавляют `await flushPromises()`. В проверке без ожидания вывод был `1`, после ожидания — `2`.
::

::practice{title="Тест сломался после переименования"}
После переименования внутренней переменной `count` в `qty` тест упал, хотя компонент работает:

```js
const wrapper = mount(QtyStepper);
wrapper.vm.count = 3;
await nextTick();
expect(wrapper.vm.count).toBe(3);
```

#solution
Тест проверял реализацию: записывал и читал внутреннюю переменную через `wrapper.vm`. Переименование ничего не изменило для пользователя, но сломало тест. К тому же такой доступ работает только в сборке режима разработки — в проверке в продакшен-сборке `wrapper.vm` этих переменных не видел.

```js
const wrapper = mount(QtyStepper, { props: { modelValue: 3, max: 3 } });
await wrapper.find('button').trigger('click');

expect(wrapper.find('output').text()).toBe('3');
expect(wrapper.emitted('limit')).toEqual([[3]]);
```

Начальное состояние задают пропсами, действие — событием, результат проверяют по DOM и событиям. Такой тест переживёт любой рефакторинг, который сохраняет поведение.
::
