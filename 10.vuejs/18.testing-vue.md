# Тестирование Vue

Принцип тот же, что в React: **тестируй поведение, а не реализацию**. Меняются инструменты - **Vue Test Utils** (официальный) и **Testing Library** поверх него, на раннере **Vitest**.

> Стратегии, e2e и CI - в главе [тестирование и деплой](/content/testing-deploying). Здесь - Vue-специфика.

---

## Философия: behavior over implementation

Хороший тест проверяет то, что видит и делает пользователь, и не ломается при рефакторинге, пока поведение не изменилось. Хрупкий тест лезет во внутренности (имена данных, число рендеров) и падает от любого изменения кода.

Поэтому предпочтительный стиль - проверять отрисованный DOM и реакцию на действия, а не внутреннее состояние компонента.

## Vue Test Utils

Официальная библиотека: монтирует компонент и даёт «обёртку» (wrapper) для поиска элементов и взаимодействия.

```js
import { mount } from '@vue/test-utils';
import Counter from './Counter.vue';

test('счётчик увеличивается по клику', async () => {
  const wrapper = mount(Counter);

  await wrapper.find('button').trigger('click'); // await - дождаться обновления DOM
  expect(wrapper.text()).toContain('1');
});
```

- `mount` - полный рендер; `shallowMount` - с заглушками дочерних компонентов.
- `find`/`findComponent`, `trigger`, `setValue` - поиск и взаимодействие.
- **`await`** перед проверкой - потому что Vue обновляет DOM асинхронно ([nextTick](/content/vuejs/reactivity-advanced)).

### Проверка событий

```js
await wrapper.find('button').trigger('click');
expect(wrapper.emitted('submit')).toBeTruthy();           // событие было
expect(wrapper.emitted('submit')[0]).toEqual([{ id: 1 }]); // с таким payload
```

### Props и v-model

```js
const wrapper = mount(Input, { props: { modelValue: 'hi' } });
await wrapper.setValue('new'); // обновить значение поля
```

## Testing Library для Vue

`@testing-library/vue` - та же философия, что в React: искать элементы так, как их видит пользователь и скринридер.

```js
import { render, screen } from '@testing-library/vue';
import userEvent from '@testing-library/user-event';

test('форма отправляется', async () => {
  render(SearchForm);
  await userEvent.type(screen.getByLabelText('Запрос'), 'vue');
  await userEvent.click(screen.getByRole('button', { name: /искать/i }));
  expect(await screen.findByText('Результаты')).toBeInTheDocument();
});
```

Приоритет запросов тот же: `getByRole` → `getByLabelText` → `getByText` → `getByTestId` (последнее средство).

<b class="text-on-semi-light">VTU или Testing Library?</b> - <span class="text-gray">Vue Test Utils даёт доступ к внутренностям (`wrapper.vm`, emitted) - мощно, но провоцирует тесты на реализацию. Testing Library принципиально работает только через DOM и подталкивает к behavior-тестам. Хороший подход: Testing Library для поведения, VTU - когда нужно проверить контракт компонента (emitted-события).</span>

## Асинхронность

Vue обновляет DOM асинхронно, поэтому тесты ждут обновлений.

```js
import { flushPromises } from '@vue/test-utils';

await wrapper.find('button').trigger('click'); // trigger возвращает промис nextTick
await flushPromises();                          // дождаться всех микротасков (запросы)
expect(wrapper.text()).toContain('Загружено');
```

- `await trigger(...)`/`await nextTick()` - дождаться обновления DOM.
- `flushPromises()` - дождаться зависших промисов (асинхронная загрузка).
- В Testing Library - `findBy*` и `waitFor`, как в React.

## Тестирование composables

Composable без хуков жизненного цикла можно вызвать **напрямую** в тесте:

```js
import { useCounter } from './useCounter';

test('useCounter', () => {
  const { count, increment } = useCounter();
  increment();
  expect(count.value).toBe(1);
});
```

Если composable использует `onMounted`/`provide` и т.п., его монтируют внутри тестового компонента (helper `withSetup` или `mount` с минимальным компонентом-обёрткой), чтобы был контекст компонента.

## Моки и сеть

Как и в React, лучший подход к сети - **MSW**: перехват на сетевом уровне, тест не знает, что ответ замокан, и не завязан на способ загрузки. Модули мокают через `vi.mock` (Vitest).

```js
import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';

const server = setupServer(
  http.get('/api/users/1', () => HttpResponse.json({ name: 'Аня' }))
);
```

> **Vitest** - стандартный раннер для Vue (от автора Vite), API совместим с Jest. Pinia-сторы тестируют через `@pinia/testing`.

## Вопросы на собеседовании

<b class="text-on-semi-light">Главный принцип тестирования компонентов?</b>
<span class="text-gray">Тестировать поведение, как им пользуется пользователь, а не детали реализации. Тест не должен ломаться при рефакторинге без изменения поведения.</span>

<b class="text-on-semi-light">Зачем await перед проверками в VTU?</b>
<span class="text-gray">Vue обновляет DOM асинхронно. `await trigger()`/`nextTick()` дожидается применения изменений, `flushPromises()` - зависших промисов.</span>

<b class="text-on-semi-light">Чем отличаются Vue Test Utils и Testing Library?</b>
<span class="text-gray">VTU даёт доступ к внутренностям (vm, emitted) - удобно для контракта компонента, но провоцирует тесты на реализацию. Testing Library работает только через DOM и подталкивает к behavior-тестам.</span>

<b class="text-on-semi-light">Как тестировать composable?</b>
<span class="text-gray">Без хуков жизненного цикла - вызвать напрямую и проверить возвращённые ref'ы. С хуками - смонтировать внутри тестового компонента (withSetup/mount).</span>

<b class="text-on-semi-light">Почему MSW лучше мока fetch?</b>
<span class="text-gray">Мокает на уровне сети, а не реализации. Тест не меняется при смене способа загрузки (fetch/axios/Vue Query).</span>
