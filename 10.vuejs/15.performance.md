# Производительность

Что Vue оптимизирует сам и что остаётся разработчику: подсказки компилятора, `v-once` и `v-memo`, стабильность пропсов, большие списки, разбиение кода, Vapor mode и профилирование. Спрашивают, почему Vue обычно не нуждается в ручной мемоизации, что делают `v-once` и `v-memo` и что такое Vapor mode. Глубже — почему ребёнок перерисовывается от объекта в пропсе, хотя данные те же, и где во Vue настоящие узкие места.

::tldr
- **Большую часть работы Vue делает сам:** точечные обновления компонентов, вынос статичных узлов, patch flags и блоки, которые сравнивают только динамические узлы, и кеш встроенных обработчиков.
- **Ребёнок перерисовывается, если изменились его пропсы, — и объект, созданный в шаблоне заново, считается изменением.** Литерал с реактивным полем `:options="{ dense: isDense }"` перерисует ребёнка при любом рендере родителя. Полностью константный литерал компилятор выносит.
- **`v-once` рисует поддерево один раз, `v-memo` пропускает его обновление, пока не изменился массив зависимостей.** `v-memo` нужен для больших списков, где меняется одна строка.
- **Узкие места обычно не в рендере, а в объёме:** глубокая реактивность больших данных, тысячи узлов в DOM, большой бандл. Лечат `shallowRef`, виртуализацией и ленивыми компонентами.
- **Vapor mode компилирует шаблон прямо в операции с DOM, без virtual DOM.** Он пока в стадии RC, включается для отдельного компонента и не поддерживает Options API и `v-memo`.
::

## Что Vue делает сам

Модель обновления Vue уже экономна (подробно — во [Введении](/content/vuejs/introduction)): компонент перерисовывается, только если изменились данные, которые он прочитал, или его пропсы. Поэтому `memo`, `useMemo` и `useCallback` из React во Vue почти не нужны.

Вторая половина — компилятор. Шаблон известен до запуска, и компилятор оставляет рантайму подсказки. Проверено на выводе `@vue/compiler-dom`:

```vue
<div>
  <h2 class="title">Каталог</h2>
  <p :class="cls">{{ price }}</p>
  <button @click="buy">Купить</button>
</div>
```

```js
_cache[1] || (_cache[1] = _createElementVNode("h2", { class: "title" }, "Каталог", -1 /* CACHED */)),
_createElementVNode("p", { class: _normalizeClass(_ctx.cls) }, _toDisplayString(_ctx.price), 3 /* TEXT, CLASS */),
_createElementVNode("button", { onClick: _cache[0] || (_cache[0] = (...args) => (_ctx.buy && _ctx.buy(...args))) }, "Купить")
```

- **Статичные узлы создаются один раз** и кешируются: `h2` с флагом `CACHED` не сравнивается при обновлении. Статичные атрибуты динамического узла выносятся в константы `_hoisted_*`.
- **Patch flags** говорят, что сравнивать: у `p` — только текст и класс (`TEXT, CLASS`), остальные атрибуты не проверяются.
- **Блоки.** Корень шаблона и границы `v-if` и `v-for` — блоки, которые собирают в плоский массив только свои динамические узлы. При обновлении Vue обходит этот массив, а не всё дерево.
- **Кеш обработчиков.** Встроенный обработчик `@click="buy"` или `@pick="() => pick()"` сохраняется в `_cache`, и функция одна и та же между рендерами — поэтому ребёнок не перерисовывается из-за «нового» обработчика. Проверено на компоненте.

Шаблон с минимумом динамики — уже оптимизация. Где же Vue может делать лишнюю работу?

## Стабильность пропсов

Ребёнок перерисовывается, если изменились его пропсы, а пропсы сравниваются по ссылке. Объект, созданный в шаблоне, — **новый в каждом рендере родителя**:

```vue
<ProductGrid :options="{ dense: isDense }" />   <!-- новый объект — ProductGrid перерисуется при любом рендере родителя -->
<ProductGrid :options="gridOptions" />          <!-- тот же объект — не перерисуется -->
```

В проверке посторонняя перерисовка родителя перерисовала ребёнка с литералом `{ dense: isDense }`, а ребёнка со стабильным объектом — нет. Литерал **без реактивных полей**, например `{ dense: true }`, компилятор распознаёт как константу и выносит — он тоже не вызвал перерисовку. А встроенные обработчики событий кешируются всегда.

Исправление — объект в `computed` или константе в `<script setup>`:

```js
const gridOptions = computed(() => ({ dense: isDense.value }));
```

Это та же проблема, что у React со ссылочной стабильностью, только у Vue она касается объектов и массивов в пропсах, а не функций.

## v-once и v-memo

### v-once

`v-once` рисует элемент и всё внутри **один раз**. Дальше это статика, даже если данные изменились:

```vue
<footer v-once>© {{ year }} {{ shopName }}</footer>
```

В проверке после изменения значения элемент с `v-once` показывал старое, а соседний — новое. Подходит для действительно неизменяемого содержимого: юридический текст, разметка, которая зависит только от начальных данных.

### v-memo

`v-memo` пропускает обновление поддерева, пока не изменился массив зависимостей. Сценарий — длинный список, где при выборе меняются две строки:

```vue
<ProductRow
  v-for="item in items"
  :key="item.id"
  v-memo="[item.id === selectedId]"
  :item="item"
  :selected="item.id === selectedId"
/>
```

Без `v-memo` при смене `selectedId` Vue пройдёт по всем строкам, сравнит пропсы и выяснит, что изменились две. С `v-memo` он сравнивает только массивы зависимостей. В проверке на 100 строках посторонний рендер родителя не перерисовал ни одной строки, а смена выбранной — ровно две.

`v-memo` — оптимизация для больших списков с измеренной проблемой. Ошибка в массиве зависимостей даёт устаревший интерфейс: если строка показывает цену, а в `v-memo` её нет, новая цена не появится.

## Объём данных и DOM

Чаще всего интерфейс тормозит не из-за лишних рендеров, а из-за объёма.

**Глубокая реактивность больших данных.** Ответ API на 20 000 строк в `ref` — это прокси и зависимости на каждое прочитанное поле. Для данных, которые только показываются и заменяются целиком, — `shallowRef` (подробно — в [Продвинутой реактивности](/content/vuejs/reactivity-advanced)).

**Тысячи узлов в DOM.** Даже идеальный рендер не спасёт, если в DOM 10 000 строк: раскладка и отрисовка займут время браузера (подробно — в [Рендеринге](/content/web/rendering)). Решение — **виртуализация**: в DOM только видимые строки и немного запаса, остальное — пустое место нужной высоты. Готовые решения — `vue-virtual-scroller`, TanStack Virtual, `useVirtualList` из VueUse. CSS-альтернатива для длинных страниц без сложной логики — `content-visibility: auto`.

**Дорогие вычисления в шаблоне.** Метод в шаблоне выполняется на каждый рендер, а `computed` — только при изменении зависимостей (подробно — в [Computed и наблюдателях](/content/vuejs/computed-and-watchers)).

## Загрузка

Скорость первого экрана зависит от объёма JavaScript (общая картина — в [Производительности загрузки](/content/security-perfomance/loading-performance)):

- **ленивые страницы:** `component: () => import('./Page.vue')` в роутере (подробно — в [Маршрутизации](/content/vuejs/routing));
- **ленивые компоненты:** `defineAsyncComponent` для тяжёлых виджетов, которые не нужны сразу — редактор, график, карта (подробно — во [Встроенных компонентах](/content/vuejs/built-in-components));
- **сборка «только рантайм»:** шаблоны компилируются при сборке, и компилятор не попадает в бандл;
- **импорт по частям:** `import { ref } from 'vue'` позволяет сборщику выбросить неиспользуемое, то же для библиотек;
- **SSR и ленивая гидратация** — для страниц, где важен первый показ (подробно — в [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt)).

`KeepAlive` — оптимизация в другую сторону: он экономит повторное создание дорогих компонентов ценой памяти.

## Vapor mode

Vapor mode — новый способ компиляции компонентов. Вместо render-функции, которая создаёт virtual DOM, компилятор выдаёт код, который сразу создаёт DOM-узлы и подписывает каждый динамический узел на его данные. Сравнивать деревья больше не нужно: изменение `price` обновляет ровно один текстовый узел. Это та же идея, что у Solid и Svelte 5 (подробно — в [Сигналах и реактивности](/content/modern-dev/signals-and-reactivity)).

В Vue 3.6, который на ноябрь 2026 года в стадии RC, Vapor:

- **включается для компонента:** `<script setup vapor>` или `<template vapor>`;
- **работает только с `<script setup>` и шаблонами** — Options API, render-функции и JSX остаются на virtual DOM;
- **не поддерживает** `v-memo`, `app.config.globalProperties`, `getCurrentInstance()` и обращения через ссылку к `$el`, `$props`, `$slots`;
- **смешивается с обычными компонентами** через `vaporInteropPlugin`, а приложение целиком на Vapor создаётся через `createVaporApp()` и не тянет рантайм virtual DOM.

Вместе с Vapor в 3.6 ядро реактивности переписано на основе alien-signals, и это ускорение получают все приложения, без включения Vapor. Для существующих проектов Vapor — точечная оптимизация горячих компонентов, а не переписывание.

## Профилирование

Сначала измеряют, потом оптимизируют:

- **Vue DevTools** — вкладка производительности показывает время рендера компонентов, а таймлайн — события и обновления;
- **`app.config.performance = true`** в режиме разработки добавляет метки Vue в Performance API: в панели Performance браузера появятся меры `<ProductCard> render` и `<ProductCard> patch`. В проверке их поймал `PerformanceObserver`;
- **панель Performance браузера** показывает, где время на самом деле: скрипт, раскладка или отрисовка;
- **`onRenderTracked` и `onRenderTriggered`** в режиме разработки показывают, какие зависимости собрал компонент и что вызвало перерисовку.

Метрики пользователей — INP, LCP — и как их собирать, разобраны в [Core Web Vitals](/content/security-perfomance/core-web-vitals).

## Красные флаги в ответе

- **«Во Vue нужно мемоизировать компоненты, как в React».** Ребёнок с прежними пропсами и так не перерисовывается, обработчики кешируются компилятором.
- **«Объект в пропсе ничего не стоит».** Литерал с реактивным полем — новый объект в каждом рендере, и ребёнок перерисуется.
- **«`v-memo` — универсальное ускорение».** Это оптимизация для больших списков, и ошибка в зависимостях даёт устаревший интерфейс.
- **«Vue работает без virtual DOM».** Только в Vapor mode, который включается для отдельных компонентов.
- **«Тормозит — значит, лишние рендеры».** Чаще — объём: глубокая реактивность больших данных и тысячи узлов в DOM.

## Как спрашивают на собеседовании

::question
Что Vue оптимизирует сам?

#answer
Компонент перерисовывается только при изменении прочитанных данных или пропсов. Компилятор кеширует статичные узлы, помечает динамические patch flags, собирает динамические узлы в блоки и кеширует встроенные обработчики. Поэтому при обновлении сравнивается только то, что может измениться.

#more
Из-за этого ручная мемоизация компонентов и функций, как в React, во Vue почти не нужна. Остаются стабильность объектов в пропсах, объём данных и DOM, размер бандла. Vapor mode идёт дальше и убирает сравнение деревьев вовсе.
::

::question
Почему ребёнок перерисовывается, хотя данные не менялись?

#answer
Скорее всего, ему передаётся объект или массив, созданный в шаблоне: `:options="{ dense: isDense }"`. Такой литерал — новый объект в каждом рендере родителя, и пропсы сравниваются по ссылке.

#more
Объект выносят в `computed` или константу в `<script setup>`. Полностью константный литерал без реактивных полей компилятор выносит сам, а встроенные обработчики кеширует. Проверить причину помогают `onRenderTriggered` в ребёнке и Vue DevTools.
::

::question
Что делают v-once и v-memo?

#answer
`v-once` рисует поддерево один раз и дальше не обновляет. `v-memo="[deps]"` пропускает обновление поддерева, пока не изменился массив зависимостей.

#more
`v-memo` полезен в длинных списках, где при выборе меняются одна-две строки: Vue сравнивает массивы зависимостей вместо пропсов каждой строки. Если забыть зависимость, интерфейс покажет устаревшие данные. `v-memo` с пустым массивом работает как `v-once`. В Vapor mode `v-memo` не поддерживается.
::

::question
Как ускорить большой список?

#answer
Виртуализацией: в DOM держать только видимые строки и немного запаса. Данные для показа хранить в `shallowRef`, если они не мутируются. Для частичных обновлений — `v-memo` по выбранной строке.

#more
Готовые решения — `vue-virtual-scroller`, TanStack Virtual, `useVirtualList` из VueUse. Ключи строк должны быть стабильными. Если строки сложные, вычисления выносят в `computed`, а не в методы шаблона. Для длинных страниц без логики помогает `content-visibility: auto`.
::

::question
Что такое Vapor mode?

#answer
Режим компиляции, в котором шаблон превращается не в virtual DOM, а сразу в создание DOM-узлов и точечные подписки каждого динамического узла на его данные. Сравнивать деревья не нужно, изменение данных обновляет конкретный узел.

#more
В Vue 3.6 он в стадии RC и включается для компонента через `<script setup vapor>`. Работает только с `<script setup>` и шаблонами, не поддерживает Options API, `v-memo`, `getCurrentInstance`. С обычными компонентами смешивается через `vaporInteropPlugin`. Отдельно 3.6 переводит ядро реактивности на alien-signals.
::

::question
Как найти, что тормозит во Vue-приложении?

#answer
Измерить. Vue DevTools показывает время рендера компонентов, `app.config.performance = true` добавляет меры рендера и patch в панель Performance браузера, а она показывает, где время: скрипт, раскладка или отрисовка.

#more
`onRenderTriggered` показывает, какая зависимость вызвала перерисовку. Частые причины: объекты в пропсах, глубокая реактивность больших данных, тысячи узлов в DOM, тяжёлые методы в шаблоне, большой бандл без разбиения. Метрики пользователей — INP и LCP — собирают в продакшене.
::

## Практика

::practice{title="Таблица перерисовывается от поиска"}
Ввод в поле поиска перерисовывает тяжёлую таблицу, хотя её данные не меняются:

```vue
<template>
  <input v-model="query">
  <DataTable :rows="rows" :options="{ dense: isDense, pageSize: 50 }" />
</template>
```

#solution
`query` читает шаблон родителя, и каждое нажатие перерисовывает родителя. При этом литерал `{ dense: isDense, pageSize: 50 }` создаётся заново, и `DataTable` получает «новый» проп.

```vue
<script setup>
const tableOptions = computed(() => ({ dense: isDense.value, pageSize: 50 }));
</script>

<template>
  <input v-model="query">
  <DataTable :rows="rows" :options="tableOptions" />
</template>
```

Теперь объект меняется, только когда меняется `isDense`. Второй вариант — передавать примитивы отдельными пропсами: `:dense="isDense" :page-size="50"`. В проверке ребёнок с литералом с реактивным полем перерисовался от постороннего рендера родителя, а со стабильным объектом — нет.
::

::practice{title="Выбор строки в длинном списке"}
В списке из нескольких тысяч товаров выбор строки ощутимо задерживается. Строка — компонент `ProductRow` с пропсом `selected`.

#solution
При смене выбранной строки родитель перерисовывается и проходит по всем строкам: сравнивает пропсы каждой и находит две изменившиеся. Сравнение тысяч компонентов — заметная работа.

```vue
<ProductRow
  v-for="item in visibleItems"
  :key="item.id"
  v-memo="[item.id === selectedId, item.price]"
  :item="item"
  :selected="item.id === selectedId"
/>
```

`v-memo` сводит работу к сравнению коротких массивов, и перерисовываются ровно две строки. В массив входит всё, от чего зависит вид строки, — здесь ещё цена. Если строк действительно тысячи, к этому добавляют виртуализацию, чтобы в DOM было несколько десятков строк. В проверке на 100 строках смена выбора перерисовала ровно две строки.
::
