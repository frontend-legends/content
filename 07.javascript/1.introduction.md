# Введение в JavaScript

Вводная глава раздела: что за язык JavaScript, где кончается язык и начинается окружение, и что происходит с кодом от файла до выполнения. На собеседовании спрашивают не «что делает JS», а **почему он работает именно так**.

::tldr
- **JavaScript = язык (ECMAScript) + окружение.** `document`, `fetch`, `setTimeout`, `console` — не язык, а API окружения: браузера, Node.js, Deno.
- **Окружение решает, как загрузить файл,** — модулем или обычным скриптом. Модули всегда работают в strict mode, а он меняет семантику, а не только «запрещает плохое».
- **Движок — интерпретатор плюс JIT:** типы известны только во время выполнения, поэтому движок сначала наблюдает, потом оптимизирует, а при нарушении предположений откатывается.
- **Однопоточен агент, а не «JS вообще»:** у вкладки и у каждого воркера свой поток. Гонки всё равно бывают — на границах `await`.
- **Язык обновляется каждый год,** но «есть в стандарте» не значит «есть у твоих пользователей»: это решает их окружение.
::

## Что такое JavaScript

Классическое определение — «высокоуровневый, динамически и слабо типизированный, однопоточный, JIT-компилируемый, встраиваемый, мультипарадигменный». Каждое слово даёт следствие в коде:

- **Высокоуровневый** — память освобождает сборщик мусора. Поэтому утечки в JS — это «забытые ссылки»: подписка, замыкание или кэш держат объект живым.
- **Динамически типизированный** — тип принадлежит значению: `let x = 1; x = 'one'` легально. Ошибки типов видны только во время выполнения, отсюда TypeScript поверх того же языка.
- **Слабо типизированный** — `"5" + 3` даёт `"53"`, а `"5" - 3` даёт `2`. Правила приведения детерминированы, поэтому «странный» пример на собесе можно вывести, а не угадать. Подробно — в [типах и переменных](/content/javascript/types-and-variables).
- **Однопоточный** — пока выполняется твой код, страница не рисуется и не реагирует на клики.
- **JIT-компилируемый** — скорость зависит от предсказуемости кода, а не только от алгоритма.
- **Встраиваемый** — сети, файлов и экрана в языке нет, их даёт окружение. Поэтому один и тот же код ведёт себя по-разному в браузере и в Node.js.
- **Мультипарадигменный** — императивный код, прототипы и классы, функции как значения. Фронтенд-код в основном функциональный: компоненты, хуки, `map`/`filter`.

Четыре слова из этого списка — встраиваемый, JIT-компилируемый, однопоточный и динамически типизированный — определяют, как код вообще выполняется. Дальше пройдём по ним по порядку на одном примере — двух строках, которые могли бы стоять в начале любого фронтенд-модуля:

```js
const users = await fetch('/api/users').then((r) => r.json());
setTimeout(() => console.log(users.length), 0);
```

## Язык и окружение

Начнём с вопроса, который кажется странным: какая часть этих двух строк — JavaScript?

Язык здесь — это `const`, `await`, стрелочные функции, `.then` у промиса и сам `Promise`. А `fetch`, `setTimeout` и `console` в языке **не существуют**. Их даёт **окружение** — программа, внутри которой работает движок: браузер, Node.js, Deno, Bun. В спецификации окружение называется *host*, а всё, что оно определяет, — *host-defined*.

Язык описан в спецификации ECMA-262: синтаксис, типы, встроенные объекты (`Object`, `Promise`, `Map`) и правила выполнения. Всё, что связано с внешним миром, — сеть, таймеры, DOM, файлы, загрузка модулей — описывает уже окружение.

```text
┌───────────── Окружение: браузер / Node.js / Deno / Bun ────────────┐
│  event loop и очереди задач, таймеры, сеть, файлы, DOM, console    │
│  загрузка модулей (URL, node_modules), воркеры, structuredClone    │
│                                                                    │
│   ┌──────────── Движок: V8 / SpiderMonkey / JavaScriptCore ─────┐  │
│   │  ECMAScript: синтаксис, типы, Promise и jobs,               │  │
│   │  Map/Set, Proxy, модули (синтаксис и связывание), Intl      │  │
│   │  + реализация: парсер, JIT, сборщик мусора                  │  │
│   └─────────────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────────────┘
```

Граница проходит даже внутри одной фичи:

| Что | Чьё | Почему это важно |
| --- | --- | --- |
| `Promise`, `async`/`await` | язык | спека говорит «поставь задачу в очередь», а **когда** её выполнить, решает окружение |
| `setTimeout`, `queueMicrotask` | окружение | поэтому в Node `setTimeout` возвращает объект `Timeout`, а в браузере — число |
| `import`/`export` | язык + окружение | синтаксис — в спеке, а **как найти** модуль (URL, `node_modules`) — решает окружение |
| `structuredClone`, `fetch`, `console` | окружение | в «голом» движке их нет, и в списках фич ES20xx их не ищут |

> Event loop — тоже не часть языка: в ECMAScript есть только задачи (jobs) и точки, через которые окружение ставит их в очередь. Сам цикл описан в HTML-спецификации (браузер) и в :term[libuv]{def="C-библиотека, на которой построен Node.js: event loop, пул потоков, асинхронный ввод-вывод"} (Node.js). Подробно — в [Event Loop](/content/javascript/event-loop).

Раз окружение даёт половину возможностей, важно понимать, какие окружения бывают.

## Где выполняется код

Один и тот же движок может работать в разных окружениях, и наоборот:

| Окружение | Движок | Особенности |
| --- | --- | --- |
| **Браузер** | V8 / SpiderMonkey / JSC | DOM, Web APIs, event loop по HTML-спецификации, песочница безопасности |
| **Node.js** | V8 | libuv (event loop и пул потоков), `fs`, `http`, CommonJS и ESM |
| **Deno** | V8 | права доступа по умолчанию закрыты, TypeScript из коробки, Web-совместимые API |
| **Bun** | JavaScriptCore | рантайм, бандлер, тест-раннер и пакетный менеджер в одном, совместимость с Node API |
| **Edge** (Cloudflare Workers и др.) | V8 isolates | изоляты вместо процессов: холодный старт в миллисекундах, урезанный набор API |

**Движок ≠ рантайм.** V8 умеет только выполнять ECMAScript, а Node.js — это V8 плюс libuv, привязки к ОС и стандартная библиотека. Поэтому вопрос «чем Node отличается от Chrome» — про окружение, а не про язык: движок у них один.

> Edge-рантаймы — в [edge computing](/content/modern-dev/edge-computing), Electron и React Native — в [кросс-платформе](/content/additional-topics/cross-platform).

Окружение даёт не только API. Ещё до первой строки кода оно решает, **как загрузить файл**, и от этого зависит, по каким правилам код будет выполняться.

## Модуль или скрипт: strict mode

В нашем примере `await` стоит на верхнем уровне файла, вне функции. Так можно только в **ES-модуле**: в обычном скрипте это `SyntaxError`. Значит, окружение должно знать, что перед ним модуль:

- в браузере — `<script type="module">`, иначе это классический скрипт;
- в Node.js — расширение `.mjs` или `"type": "module"` в `package.json`, а `.cjs` всегда CommonJS. Современный Node к тому же сам распознаёт модуль по `import`/`export` в файле.

Выбор «модуль или скрипт» решает больше, чем доступ к `import`. **Модули всегда выполняются в strict mode**, а классические скрипты и CommonJS — нет, если не написать `"use strict"`. Strict mode — **другой диалект языка**: часть «тихих» ошибок становится исключениями, а семантика `this`, `arguments` и `eval` меняется.

| Ситуация | Sloppy mode | Strict mode |
| --- | --- | --- |
| Присваивание необъявленной переменной | создаёт глобальную | `ReferenceError` |
| Запись в read-only или frozen свойство | молча игнорируется | `TypeError` |
| `this` при вызове `f()` | `globalThis` | `undefined` |
| `this` при `f.call(5)` | объект-обёртка `Number` | примитив `5` |
| `arguments` и параметры | связаны | независимы |
| `with`, `0123`, `function f(a, a)` | разрешены | `SyntaxError` |

Strict mode включается автоматически в модулях и в телах классов, вручную — директивой `"use strict"` в начале скрипта или функции. Отсюда частая ловушка: один и тот же код ведёт себя по-разному в `.cjs` и `.mjs`.

::pitfall{title="После переезда на модули или классы «пропал» this"}
#symptom
Код годами работал в старом бандле, а после перехода на ESM или переписывания на `class` падает с `TypeError: Cannot read properties of undefined (reading '...')` в колбэке.
#cause
Метод передан как значение и вызван без получателя: `const { log } = logger; log()` или `button.onClick = this.handle`. В sloppy-режиме `this` был `globalThis`, и ошибка пряталась: читалось `window.prefix`, то есть `undefined`. Модули и классы всегда strict, поэтому `this === undefined`, и обращение к его свойству падает сразу.
#fix
Привязывай контекст явно: `this.handle = this.handle.bind(this)`, стрелочная функция в поле класса (`handle = () => {...}`) или обёртка `() => logger.log()`. Strict mode не создал баг, а показал его.
::

Файл загружен, режим выбран — теперь код выполняет движок.

## Что движок делает с кодом

Вспомни слово «динамически типизированный»: в `users.length` движок заранее не знает, что такое `users` — массив, объект или `undefined`. Это выяснится только во время выполнения. Поэтому все современные движки — :term[V8]{def="движок JavaScript от Google: Chrome, Edge, Node.js, Deno"}, :term[SpiderMonkey]{def="движок JavaScript от Mozilla, работает в Firefox"}, :term[JavaScriptCore]{def="движок JavaScript от Apple: Safari и Bun"} — работают по одной схеме: **быстро стартовать, понаблюдать за реальными типами и ускорить то, что выполняется часто.**

1. Исходник разбирается в :term[AST]{def="абстрактное синтаксическое дерево: код, разобранный в дерево узлов, с которым дальше работает движок"} и выполняется **интерпретатором байткода** — старт почти мгновенный.
2. Пока код работает, интерпретатор собирает **type feedback**: какие типы и формы объектов приходят в каждую операцию.
3. Горячие функции компилируются в машинный код **спекулятивно**: компилятор предполагает, что типы останутся прежними, и ставит проверки.
4. Если проверка не прошла, происходит **деоптимизация**: машинный код выбрасывается, выполнение возвращается в интерпретатор.

Чтобы `obj.x` не был поиском по словарю, движок даёт объекту **скрытый класс** (форму): объекты, созданные одинаково, делят одну форму, и свойство читается по известному смещению. Практический вывод — в горячем коде создавай объекты сразу со всеми полями и в одном порядке и не используй `delete`. Но это микрооптимизации: сначала профилировщик, потом переписывание.

### Уровни компиляции V8

У V8 четыре уровня. Функция поднимается по ним по мере того, как становится горячее:

| Уровень | Что это | Компромисс |
| --- | --- | --- |
| **Ignition** | интерпретатор байткода, собирает type feedback | мгновенный старт, медленное выполнение |
| **Sparkplug** (2021) | неоптимизирующий компилятор: байткод → машинный код «один в один» | компилирует почти бесплатно |
| **Maglev** (2023) | быстрый оптимизирующий компилятор | компилирует в разы быстрее TurboFan, код чуть медленнее |
| **TurboFan** | максимальные спекулятивные оптимизации: инлайнинг, escape analysis | дорогая компиляция, самый быстрый код |

У других движков та же схема: SpiderMonkey — интерпретатор, Baseline и оптимизирующий Warp; JavaScriptCore — LLInt и три JIT-уровня Baseline → DFG → FTL.

### Inline caches и деоптимизация

**Inline cache** — кэш в каждой точке доступа к свойству: «для такой формы свойство лежит по такому смещению». Он бывает **мономорфным** (одна форма, самый быстрый), **полиморфным** (в V8 — до 4 форм) и **мегаморфным** (больше 4: кэш сдаётся, доступ превращается в медленный поиск).

```js
function Point(x, y) { this.x = x; this.y = y; }

const a = new Point(1, 2);
const b = new Point(3, 4);   // та же форма, что у a
const c = { y: 1, x: 2 };    // другой порядок свойств → другая форма

b.z = 5;                     // b переходит на новую форму, a остаётся на старой
delete a.x;                  // a уходит в dictionary mode: медленные «словарные» свойства
```

Деоптимизация на живом примере:

```js
function add(a, b) { return a + b; }

for (let i = 0; i < 1e6; i++) add(i, 1); // горячо, всегда small integers (Smi)
add('a', 'b');                           // предположение «тут числа» нарушено
```

Вывод `node --trace-opt --trace-deopt` (Node 24, сокращено):

```text
[marking <JSFunction add> for optimization to MAGLEV, reason: hot and stable]
[marking <JSFunction add> for optimization to TURBOFAN_JS, reason: hot and stable]
[bailout (kind: deopt-eager, reason: not a Smi): begin. deoptimizing <JSFunction add>, <Code MAGLEV> ...]
```

До какого уровня функция успеет подняться перед деоптимизацией, зависит от прогрева: иногда `add` доходит до TurboFan и деоптимизируется уже из него. Формы объектов можно проверить в Node: `node --allow-natives-syntax`, затем `%HaveSameMap(a, b)` и `%HasFastProperties(a)`.

> Сборка мусора, утечки и профилирование — в [памяти и производительности](/content/javascript/memory-and-performance). Как код исполняет процессор — в [выполнении кода](/content/computer-science/running-the-code).

Всю эту работу — парсинг, выполнение, компиляцию горячих функций — движок делает в одном потоке с твоим кодом. Это главное ограничение для интерфейса.

## Один поток

Вернёмся к примеру. `fetch` отправляет запрос, но **не ждёт** ответа в этом потоке: сетью занимается окружение, а поток свободен. Когда ответ придёт, окружение поставит продолжение в очередь, и event loop выполнит его, как только поток освободится. С `setTimeout` то же самое: колбэк выполнится не «через 0 мс», а когда до него дойдёт очередь.

В спецификации поток выполнения принадлежит **агенту**. Вкладка — агент, каждый Web Worker — отдельный агент со своим стеком, очередями и одним потоком.

- **Внутри агента параллелизма нет.** Две функции не выполняются одновременно, поэтому мьютексы для обычных объектов не нужны. Зато долгий синхронный код блокирует всё: отрисовку, клики, таймеры.
- **Между агентами — сообщения.** `postMessage` копирует данные (structured clone) или передаёт владение (`ArrayBuffer` как transferable).
- **Общая память есть, но явная:** `SharedArrayBuffer` + `Atomics`.
- **Окружение при этом многопоточное.** Браузер декодирует картинки и ходит в сеть в других потоках, Node.js выполняет файловые операции в пуле потоков libuv.

### Детали: агенты, общая память, пул libuv

- **Один агент на группу окон.** Точнее, один агент обслуживает страницу вместе с её same-origin iframe и попапами. Cross-site iframe живёт в отдельном агенте.
- **`SharedArrayBuffer` в браузере** доступен только на cross-origin isolated страницах (заголовки COOP + COEP). Блокирующий `Atomics.wait` на главном потоке запрещён, там есть только `Atomics.waitAsync`.
- **Пул libuv** — по умолчанию 4 потока (`UV_THREADPOOL_SIZE`). Через него идут блокирующие вызовы ОС (файловая система, `dns.lookup`) и тяжёлые для CPU операции (`crypto.pbkdf2`, `scrypt`, `zlib`). Сетевые сокеты обходятся без пула — через epoll, kqueue или IOCP.

### Гонки без потоков

Один поток не значит «без гонок». Код выполняется без прерываний (run-to-completion) только **до ближайшего `await`**. Пока функция ждёт ответ, как наш `fetch`, может выполниться что угодно — в том числе второй вызов той же функции:

```js
// 1. Ответы приходят не в том порядке, в котором ушли запросы
async function search(q) {
  const res = await fetchResults(q); // 'r' отвечает за 50 мс, 're' — за 10 мс
  render(res);                       // последним отрисуется 'r' — устаревший результат
}
search('r');
search('re');

// 2. check-then-act через await
let balance = 100;
async function withdraw(n) {
  if (balance >= n) {   // оба вызова проверили баланс до списания
    await saveToServer();
    balance -= n;
  }
}
await Promise.all([withdraw(80), withdraw(80)]); // balance === -60
```

Защита — не мьютексы, а дисциплина вокруг `await`: отменять устаревшее (`AbortController`), игнорировать устаревшие ответы (`if (id !== lastRequestId) return`), выстраивать операции в очередь промисов, а инварианты проверять и менять **в одном синхронном участке** или на сервере.

> Воркеры и параллельные вычисления — в [Web Workers](/content/additional-topics/web-workers-and-concurrency).

Мы прошли путь кода от файла до выполнения. Осталось последнее: язык не стоит на месте, и то, что работает у тебя, может не работать у пользователя.

## Как язык меняется

Язык развивает комитет **TC39**, и каждое предложение проходит стадии:

| Stage | Что значит |
| --- | --- |
| **0–1** | идея и сформулированная проблема, есть «чемпион» в комитете |
| **2** | выбран дизайн, есть черновик спецификации |
| **2.7** | спецификация одобрена, пишутся тесты :term[test262]{def="официальный набор тестов на соответствие спецификации ECMAScript"} |
| **3** | рекомендовано к реализации, меняется только по фидбеку движков |
| **4** | две совместимые реализации и тесты → войдёт в ближайшую редакцию |

Каждый июнь Ecma выпускает новую редакцию: ES2015, ES2016 и так далее. **Stage 3 — ещё не стандарт:** API может поменяться. Хрестоматийный пример — декораторы: TypeScript, Angular и NestJS годами жили на legacy-версии (`experimentalDecorators`), а вариант, дошедший до Stage 3, оказался несовместим с ней. Что вошло в какую редакцию — в [современном JS](/content/javascript/modern-js).

Но редакция описывает язык, а не то, что есть у конкретного пользователя. Набор фич определяет его окружение — версия браузера или Node.js. Это та же граница «язык / окружение», с которой мы начали.

::pitfall{title="Фича есть в стандарте, но падает у части пользователей"}
#symptom
В Chrome всё работает, а в Sentry — `TypeError: a.union is not a function` от пользователей старого Safari или от серверного рендера на Node.
#cause
Стандарт описывает язык, а не то, что установлено у пользователя. Babel и TypeScript **транспилируют синтаксис** (`?.`, классы), но **не добавляют встроенные API** — `Set.prototype.union` в бандл никто не положит.
#fix
Смотри :term[Baseline]{def="метка web.dev и MDN: фича работает во всех основных браузерах"} (web.dev, MDN) и свой `browserslist`, а не номер ES-редакции. Для API нужны полифилы (`core-js` с `useBuiltIns: 'usage'` или точечные) или проверка наличия фичи. Для серверного кода фиксируй версию Node в `engines` и в CI.
::

**Legacy, которое всё ещё спрашивают:** `var` и hoisting, `arguments`, IIFE и module pattern, «классы» через функции-конструкторы и `prototype`, `==` с приведением типов. Так уже не пишут, но это проверка «понимает ли кандидат язык, а не синтаксис». Разбирается в [контексте выполнения](/content/javascript/execution-context), [замыканиях](/content/javascript/closures) и [прототипах](/content/javascript/prototypes-and-classes).

## Красные флаги в ответе

Фразы, после которых интервьюер начинает копать:

- **«JS — интерпретируемый язык».** Не совсем: движки компилируют горячий код в машинный, «чисто интерпретируемым» JS не был с 2008 года (V8).
- **«`setTimeout` и event loop — часть JavaScript».** Это API и механизм окружения, в ECMAScript их нет.
- **«Strict mode просто запрещает плохой код».** Он меняет семантику: `this` в функции без получателя — `undefined`, примитивы не оборачиваются.
- **«JS однопоточный, поэтому гонок нет».** Гонок данных внутри агента нет, а логические гонки на границах `await` — обычное дело.
- **«Stage 3 — значит, уже в стандарте».** Нет, в стандарт попадает только Stage 4.
- **«Babel добавит `Set.prototype.union`».** Babel переписывает синтаксис, а встроенные API приносит полифил.

## Как спрашивают на собеседовании

::question
Что такое JavaScript? Охарактеризуй язык.

#answer
Высокоуровневый (память управляется GC), динамически типизированный (тип у значения), слабо типизированный (неявное приведение), однопоточный (один поток выполнения, асинхронность через event loop), JIT-компилируемый, встраиваемый (возможности даёт окружение), мультипарадигменный.

#more
Сильный ответ — не перечисление, а следствия: GC → утечки через забытые ссылки; динамическая типизация → TypeScript и валидация на границах; однопоточность → долгие задачи блокируют UI; JIT → важна стабильность форм объектов. И отдельно — граница язык/окружение: event loop, таймеры и DOM не входят в ECMAScript.

#followups
- «Интерпретируемый или компилируемый?» → оба: интерпретатор байткода плюс JIT; «чисто интерпретируемым» JS не был с 2008 года (V8)
- «Почему тогда JS быстрый?» → спекулятивная оптимизация по type feedback, inline caches, скрытые классы
::

::question
Чем JavaScript отличается от ECMAScript? А движок от рантайма?

#answer
ECMAScript — спецификация (ECMA-262), JavaScript — её реализация плюс API окружения. Движок (V8, SpiderMonkey, JSC) выполняет ECMAScript, рантайм — это движок плюс API окружения: DOM и Web APIs в браузере, файлы и сеть в Node.

#more
Спека намеренно оставляет точки расширения для окружения (host hooks): промисы она ставит в очередь, но когда выполнять задачи, решает окружение; `import` описан, а поиск модуля по URL или в `node_modules` — нет. Отсюда разница Node и Chrome при одном движке: разные event loop (фазы libuv и `process.nextTick` против task/microtask/render), разные модульные системы, разные модели безопасности. Нюансы: `Intl` — отдельная спека ECMA-402, но реализует её движок; `structuredClone` — HTML-спека, а не ES2022, как часто пишут.

#followups
- «Где в спеке event loop?» → нигде: только задачи (jobs), цикл описан в HTML и в libuv
- «Есть ли в edge-рантайме `fs`?» → постоянного диска нет. Cloudflare Workers с `nodejs_compat` дают `node:fs`, но это виртуальная файловая система в памяти, не общая между запросами
::

::question
Что делает strict mode и где он включён?

#answer
Превращает тихие ошибки в исключения (необъявленные переменные, запись в read-only свойства), запрещает `with` и восьмеричные литералы; `this` в функции без получателя — `undefined`. Включается директивой `"use strict"`, автоматически — в ES-модулях и классах.

#more
Это изменение семантики, а не линтер: примитивный `this` не оборачивается (`f.call(5)` даёт `5`), `arguments` не связан с параметрами, `eval` не создаёт переменных снаружи. В CommonJS он не включён — отсюда разница `.cjs` и `.mjs`. Нюанс: `"use strict"` нельзя написать в функции с default-параметрами или деструктуризацией — это `SyntaxError`, потому что параметры разбираются раньше тела.

#followups
- «Какой `this` в колбэке `setTimeout` в strict mode?» → в браузере `window`: HTML-спека передаёт его явно; в Node — объект `Timeout`
::

::question
Как работает JIT-компиляция и что такое деоптимизация?

#answer
Движок сначала интерпретирует код, а горячие функции компилирует в оптимизированный машинный код. Если допущения оптимизации нарушаются, происходит деоптимизация — откат к интерпретатору.

#more
Оптимизация спекулятивна: по type feedback компилятор предполагает типы и формы объектов и ставит проверки. В V8 уровни Ignition → Sparkplug → Maglev → TurboFan. Скорость доступа к свойствам держится на скрытых классах и inline caches: мономорфный доступ — проверка формы и чтение по смещению, мегаморфный (больше 4 форм) — медленный поиск.

#followups
- «Как писать код, дружелюбный к JIT?» → стабильные формы объектов, без `delete`, однородные массивы — но только там, где профилировщик показал проблему
- «Как увидеть деоптимизацию?» → `node --trace-deopt`, в браузере — Performance panel
::

::question
JavaScript однопоточный? А как же воркеры и Node.js?

#answer
Код выполняется в одном потоке, а асинхронные операции выполняет окружение и возвращает результат через event loop. Воркеры — отдельные потоки со своим event loop.

#more
Однопоточен **агент**: у вкладки и каждого воркера свой поток, стек и очереди, общение — сообщениями. Разделяемая память — через `SharedArrayBuffer` + `Atomics`, в браузере только при cross-origin isolation. Окружение многопоточное: в Node файловые операции, `dns.lookup`, `crypto` и `zlib` идут через пул libuv из 4 потоков, а сеть — через асинхронные механизмы ОС.

#followups
- «Может ли быть гонка в JS?» → гонок данных внутри агента нет, но логические гонки на `await` — да: ответы не по порядку, check-then-act. Лечится отменой, игнором устаревших ответов и очередью
- «Почему `fs.readFile` в Node не блокирует?» → блокирующий вызов выполняется в пуле потоков libuv
- «Что будет с 10 тяжёлыми `crypto.pbkdf2` разом?» → 4 выполняются, остальные ждут свободный поток (можно поднять `UV_THREADPOOL_SIZE`)
::

::question
Как фича попадает в язык? Можно ли использовать Stage 3 в проде?

#answer
Через TC39: стадии от 0 до 4, на Stage 4 фича входит в ближайшую ежегодную редакцию. До этого её можно использовать через Babel или TypeScript.

#more
Stage 4 требует двух совместимых реализаций и тестов test262; с 2023 года есть промежуточная Stage 2.7. Stage 3 в проде допустим через транспиляцию, если ты готов к миграции, как это было с декораторами. И важно отличать синтаксис, который транспилируется, от встроенных API, которым нужен полифил.

#followups
- «Почему `?.` работал в старом Safari после Babel, а `Set.prototype.union` — нет?» → синтаксис переписывается, API — нет
::

## Практика

::practice{title="Что выведет?"}
```js
function f() { return typeof this; }
console.log(f(), f.call(5));
```

```js
'use strict';
function f() { return typeof this; }
console.log(f(), f.call(5));
```

#solution
Первый (sloppy, например CommonJS-файл в Node): `object object`. Без получателя `this` = `globalThis`, а примитив `5` оборачивается в объект `Number`.

Второй (strict): `undefined number`. `this` не подменяется на глобальный объект и не оборачивается.

Если положить первый вариант в ES-модуль (`.mjs` или `type="module"`), он тоже выведет `undefined number` — модули всегда strict.

На практике это всплывает, когда метод отрывают от объекта. В модуле или классе (оба strict) получаем `TypeError`, а не тихое чтение из `globalThis`:

```js
class Logger {
  prefix = '[app] ';
  log(m) { return this.prefix + m; }
}

const { log } = new Logger();
log('hi'); // TypeError: Cannot read properties of undefined (reading 'prefix')

const logger = new Logger();
const bound = logger.log.bind(logger);
bound('hi'); // '[app] hi'
```
::

::practice{title="Язык или окружение?"}
Разложи по колонкам «ECMAScript» и «API окружения»: `Promise`, `setTimeout`, `queueMicrotask`, `structuredClone`, `JSON.parse`, `console.log`, `fetch`, `Array.prototype.at`, `import()`, `Intl.DateTimeFormat`.

#solution
| API | Где описан | Комментарий |
| --- | --- | --- |
| `Promise` | ECMAScript | |
| `JSON.parse` | ECMAScript | |
| `Array.prototype.at` | ECMAScript | ES2022 |
| `import()` | ECMAScript | синтаксис и семантика в языке, загрузку модуля выполняет окружение |
| `Intl.DateTimeFormat` | ECMAScript (ECMA-402) | отдельная спека Intl того же комитета TC39 |
| `setTimeout` | окружение (HTML) | в Node своя реализация, возвращает объект `Timeout` |
| `queueMicrotask` | окружение (HTML) | кладёт задачу в ту же microtask-очередь, что и промисы |
| `structuredClone` | окружение (HTML) | |
| `console.log` | окружение (WHATWG Console) | |
| `fetch` | окружение (WHATWG Fetch) | |

Ловушка — `queueMicrotask` и `structuredClone`: их часто считают частью языка. Правило простое: если API описан в спеке HTML или WHATWG, это окружение, даже если он есть во всех средах.
::

::practice{title="Почему рендер списка тормозит?"}
Функция вызывается для 50 000 пользователей, а `renderName` в профилировщике выглядит подозрительно медленно:

```js
function makeUser(data) {
  const user = {};
  if (data.isAdmin) user.role = 'admin';
  if (data.avatar) user.avatar = data.avatar;
  user.name = data.name;
  user.id = data.id;
  return user;
}

const renderName = (user) => user.name.toUpperCase();
users.map(makeUser).forEach(renderName);
```

#solution
Объекты собираются в разном порядке и с разным набором полей: `{name, id}`, `{role, name, id}`, `{avatar, name, id}`, `{role, avatar, name, id}` — это 4 разные формы, и смещение `name` у них разное. Доступ `user.name` в `renderName` становится полиморфным, а пятый вариант формы сделает его мегаморфным.

Фикс — одна форма для всех: все поля сразу и в одном порядке.

```js
function makeUser(data) {
  return {
    id: data.id,
    name: data.name,
    role: data.isAdmin ? 'admin' : null,
    avatar: data.avatar ?? null,
  };
}
```

Бонус: такой код проще типизировать — у объекта один тип, а не четыре.

Проверить формы можно внутренней функцией V8 (только для экспериментов, не для прода):

```js
// node --allow-natives-syntax practice-shapes.cjs
const admin = { id: 1, name: 'Ann', isAdmin: true };
const guest = { id: 2, name: 'Bob', avatar: 'b.png' };

console.log(%HaveSameMap(makeUserBad(admin), makeUserBad(guest))); // false
console.log(%HaveSameMap(makeUser(admin), makeUser(guest)));       // true
```

Здесь `makeUserBad` — исходная версия, `makeUser` — исправленная.
::
