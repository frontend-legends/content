# Обработка ошибок

Ошибки - неизбежная часть любого приложения. Сервер может не ответить, пользователь введёт невалидные данные, API изменит формат. Разница между хрупким и надёжным приложением - в том, **как** оно обрабатывает ошибки. На собесе проверяют не только знание `try/catch`, но и умение выстроить стратегию обработки ошибок для всего приложения.

---

## try/catch/finally

Основная конструкция для перехвата ошибок в синхронном и async/await коде.

```js
try {
  // код, который может выбросить ошибку
  const data = JSON.parse(invalidJSON);
} catch (error) {
  // выполняется, если в try произошла ошибка
  console.error("Ошибка парсинга:", error.message);
} finally {
  // выполняется ВСЕГДА - и при успехе, и при ошибке
  cleanup();
}
```

### Порядок выполнения

```js
function example() {
  try {
    console.log("1 - try start");
    throw new Error("test");
    console.log("2 - не выполнится");
  } catch (error) {
    console.log("3 - catch");
  } finally {
    console.log("4 - finally");
  }
  console.log("5 - after try/catch");
}

// Порядок: 1, 3, 4, 5
```

### finally и return

`finally` выполняется **даже при return** из try или catch:

```js
function getValue() {
  try {
    return "from try";
  } finally {
    console.log("finally выполнился"); // выполнится!
  }
}

console.log(getValue()); // "finally выполнился", затем "from try"
```

⚠️ Если в `finally` есть свой `return` - он **перезапишет** return из try/catch:

```js
function dangerous() {
  try {
    return "try";
  } finally {
    return "finally"; // перезаписывает return из try!
  }
}

console.log(dangerous()); // "finally" - не "try"!
```

<b class="text-on-semi-light">Правило:</b> Никогда не используй `return` внутри `finally`. Это запутывает поток управления и маскирует ошибки. `finally` - для cleanup (закрытие соединений, скрытие лоадера, освобождение ресурсов).

### Опциональный catch binding

С ES2019 можно не указывать переменную ошибки, если она не нужна:

```js
try {
  JSON.parse(data);
} catch {
  // без (error) - если не нужна информация об ошибке
  console.log("Невалидный JSON");
}
```

## Объект Error

Все встроенные ошибки наследуют от `Error`. У объекта ошибки три ключевых свойства:

```js
const error = new Error("Что-то пошло не так");

console.log(error.name);    // "Error"
console.log(error.message); // "Что-то пошло не так"
console.log(error.stack);   // Stack trace - путь вызовов до ошибки
```

### Stack trace

```js
function a() {
  b();
}
function b() {
  c();
}
function c() {
  throw new Error("глубокая ошибка");
}

try {
  a();
} catch (e) {
  console.log(e.stack);
}
// Error: глубокая ошибка
//     at c (script.js:7)
//     at b (script.js:4)
//     at a (script.js:2)
//     at script.js:10
```

<span class="text-gray">Stack trace - главный инструмент отладки. Он показывает **цепочку вызовов**, которая привела к ошибке. Именно поэтому лучше бросать `Error` объекты, а не примитивы - у примитивов нет stack trace.</span>

## Встроенные типы ошибок

| Тип              | Когда возникает                                      | Пример                                  |
| ---------------- | ---------------------------------------------------- | --------------------------------------- |
| `TypeError`      | Операция с неправильным типом                        | `null.property`, `undefined()`          |
| `ReferenceError` | Обращение к несуществующей переменной                | `console.log(notDefined)`               |
| `SyntaxError`    | Невалидный синтаксис (при парсинге)                  | `JSON.parse("{broken}")`                |
| `RangeError`     | Значение вне допустимого диапазона                   | `new Array(-1)`, рекурсия              |
| `URIError`       | Неправильное использование URI-функций               | `decodeURI("%")`                        |
| `EvalError`      | Ошибка в `eval()` (почти не встречается)             | Устаревший тип                          |

```js
// TypeError - самый частый тип
const obj = null;
obj.name; // TypeError: Cannot read properties of null

// ReferenceError
console.log(myVar); // ReferenceError: myVar is not defined

// SyntaxError (при парсинге, не при выполнении)
JSON.parse("not json"); // SyntaxError: Unexpected token

// RangeError
function infinite() { infinite(); }
infinite(); // RangeError: Maximum call stack size exceeded
```

<b class="text-on-semi-light">На собесе:</b> Могут попросить объяснить разницу между `TypeError` и `ReferenceError`. `ReferenceError` - переменная **не существует** в scope. `TypeError` - переменная существует, но её значение **не поддерживает** операцию (например, вызвать `undefined` как функцию).

## Custom Errors

Для бизнес-логики часто нужны свои типы ошибок:

```js
class ValidationError extends Error {
  constructor(field, message) {
    super(message);
    this.name = "ValidationError";
    this.field = field;
  }
}

class NotFoundError extends Error {
  constructor(resource, id) {
    super(`${resource} с id ${id} не найден`);
    this.name = "NotFoundError";
    this.resource = resource;
    this.id = id;
    this.statusCode = 404;
  }
}

class AuthorizationError extends Error {
  constructor(message = "Нет доступа") {
    super(message);
    this.name = "AuthorizationError";
    this.statusCode = 403;
  }
}
```

### Использование

```js
function validateEmail(email) {
  if (!email.includes("@")) {
    throw new ValidationError("email", "Невалидный email");
  }
}

async function getUser(id) {
  const response = await fetch(`/api/users/${id}`);
  if (response.status === 404) {
    throw new NotFoundError("User", id);
  }
  if (response.status === 403) {
    throw new AuthorizationError();
  }
  return response.json();
}
```

### Проверка типа ошибки

```js
try {
  await getUser(123);
} catch (error) {
  if (error instanceof NotFoundError) {
    showNotFound(error.resource);
  } else if (error instanceof AuthorizationError) {
    redirectToLogin();
  } else if (error instanceof ValidationError) {
    showFieldError(error.field, error.message);
  } else {
    // неизвестная ошибка - логируем и показываем generic message
    logToService(error);
    showGenericError();
  }
}
```

<b class="text-on-semi-light">Зачем custom errors:</b> `instanceof` проверки дают типобезопасную обработку. Дополнительные поля (`field`, `statusCode`) несут контекст. Вместо `if (error.message.includes("not found"))` - чёткая типизация.

## throw - что можно бросать

Технически `throw` может бросить **любое значение**:

```js
throw "строка";           // работает, но плохо
throw 42;                 // работает, но плохо
throw { code: 404 };      // работает, но плохо
throw new Error("сообщение"); // правильно
```

<b class="text-on-semi-light">Всегда бросай Error (или наследника).</b> Причины:

- **Stack trace** - только у Error объектов есть `.stack`
- **Единообразие** - `catch(error)` всегда получает объект с `.name`, `.message`, `.stack`
- **instanceof** - можно проверять тип ошибки
- **Совместимость** - мониторинг ошибок (Sentry, etc.) ожидает Error объекты

## Ошибки в асинхронном коде

### Promise rejection

Ошибки в промисах не ловятся обычным try/catch (без await):

```js
// try/catch НЕ ПОЙМАЕТ ошибку из промиса
try {
  Promise.reject(new Error("async error"));
} catch (e) {
  // сюда НЕ попадём!
}

// Правильно - .catch()
Promise.reject(new Error("async error")).catch((e) => {
  console.error(e); // сюда попадём
});

// Или async/await + try/catch
try {
  await Promise.reject(new Error("async error"));
} catch (e) {
  console.error(e); // сюда попадём
}
```

### Unhandled rejection

Если у rejected промиса нет `.catch()` - это **unhandled rejection**. Браузер (и Node.js) это отслеживает:

```js
// Глобальный обработчик (браузер)
window.addEventListener("unhandledrejection", (event) => {
  console.error("Unhandled rejection:", event.reason);
  event.preventDefault(); // предотвращает вывод в консоль
});

// Node.js
process.on("unhandledRejection", (reason, promise) => {
  console.error("Unhandled rejection:", reason);
});
```

<span class="text-gray">В Node.js с версии 15+ unhandled rejection **крашит процесс** по умолчанию. В браузере - предупреждение в консоли. В обоих случаях это баг, который нужно исправить.</span>

### Глобальные обработчики ошибок

```js
// Синхронные ошибки и runtime errors (браузер)
window.addEventListener("error", (event) => {
  console.error("Global error:", event.error);
  // Отправить в мониторинг
  sendToSentry(event.error);
});

// window.onerror - старый API, но всё ещё используется
window.onerror = function (message, source, lineno, colno, error) {
  console.error("Error:", message, "at", source, lineno, colno);
  return true; // предотвращает вывод в консоль
};

// Unhandled promise rejections
window.addEventListener("unhandledrejection", (event) => {
  sendToSentry(event.reason);
});
```

<b class="text-on-semi-light">Стратегия:</b> Глобальные обработчики - это **последняя линия обороны**. Они ловят то, что проскочило через локальные try/catch. Используй их для логирования и мониторинга, но не как основной механизм обработки ошибок.

## Error Boundaries (React pattern)

В React обычные try/catch не ловят ошибки рендеринга. Для этого есть Error Boundaries - компоненты-обёртки на классах:

```js
class ErrorBoundary extends React.Component {
  state = { hasError: false, error: null };

  static getDerivedStateFromError(error) {
    return { hasError: true, error };
  }

  componentDidCatch(error, errorInfo) {
    // Отправить в мониторинг
    logErrorToService(error, errorInfo.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return <FallbackUI error={this.state.error} />;
    }
    return this.props.children;
  }
}
```

```js
// Использование
<ErrorBoundary>
  <App />
</ErrorBoundary>
```

<span class="text-gray">Error Boundaries ловят ошибки в: render, lifecycle methods, конструкторах потомков. НЕ ловят: event handlers (используй try/catch), async-код (используй .catch), серверный рендеринг, ошибки самого boundary.</span>

## Паттерны обработки ошибок

### Fail fast

Проверяй условия как можно раньше. Не продолжай выполнение с невалидными данными:

```js
function processOrder(order) {
  if (!order) {
    throw new ValidationError("order", "Order is required");
  }
  if (!order.items?.length) {
    throw new ValidationError("items", "Order must have items");
  }
  if (order.total < 0) {
    throw new RangeError("Total cannot be negative");
  }

  // основная логика - только если все проверки прошли
  return submitOrder(order);
}
```

### Graceful degradation

Приложение продолжает работать даже при ошибке - с ограниченной функциональностью:

```js
async function loadDashboard() {
  const [users, analytics, notifications] = await Promise.allSettled([
    fetchUsers(),
    fetchAnalytics(),
    fetchNotifications(),
  ]);

  // Даже если аналитика не загрузилась - показываем dashboard
  renderUsers(users.status === "fulfilled" ? users.value : []);
  renderAnalytics(
    analytics.status === "fulfilled" ? analytics.value : null
  );
  renderNotifications(
    notifications.status === "fulfilled" ? notifications.value : []
  );
}
```

### Error wrapping - добавление контекста

Ловим низкоуровневую ошибку, оборачиваем в более понятную:

```js
async function getUserProfile(userId) {
  try {
    const response = await fetch(`/api/users/${userId}`);
    const data = await response.json();
    return data;
  } catch (originalError) {
    // Оборачиваем с контекстом - "что делали" + "что пошло не так"
    const wrappedError = new Error(
      `Не удалось загрузить профиль пользователя ${userId}`
    );
    wrappedError.cause = originalError; // ES2022 - error cause
    throw wrappedError;
  }
}

// Или через options (ES2022)
throw new Error("Не удалось загрузить профиль", {
  cause: originalError,
});
```

<b class="text-on-semi-light">`error.cause` (ES2022):</b> стандартный способ сохранить оригинальную ошибку. Мониторинг (Sentry) поддерживает cause chain - можно видеть всю цепочку ошибок.

### Centralized error handling

Все ошибки обрабатываются в одном месте:

```js
// Централизованный обработчик
function handleError(error) {
  if (error instanceof AuthorizationError) {
    redirectToLogin();
    return;
  }
  if (error instanceof NotFoundError) {
    showNotFoundPage();
    return;
  }
  if (error instanceof ValidationError) {
    showValidationMessage(error.field, error.message);
    return;
  }

  // Неизвестные ошибки
  console.error("Unexpected error:", error);
  sendToMonitoring(error);
  showGenericErrorMessage();
}

// Использование по всему приложению
async function fetchData() {
  try {
    return await api.get("/data");
  } catch (error) {
    handleError(error);
  }
}
```

## Антипаттерны

### Пустой catch

```js
// ПЛОХО - ошибка молча проглочена
try {
  riskyOperation();
} catch (e) {
  // пусто
}

// ХОРОШО - хотя бы залогировать
try {
  riskyOperation();
} catch (e) {
  console.error("riskyOperation failed:", e);
}
```

### try/catch для control flow

```js
// ПЛОХО - исключения для обычной логики
function findUser(users, id) {
  try {
    return users.find((u) => u.id === id).name;
  } catch {
    return "Unknown";
  }
}

// ХОРОШО - проверка условия
function findUser(users, id) {
  const user = users.find((u) => u.id === id);
  return user ? user.name : "Unknown";
}
```

⚠️ `try/catch` предназначен для **исключительных ситуаций** (сеть, парсинг, внешние данные), а не для обычного control flow. `throw/catch` дороже обычного `if/else`.

### Catch and rethrow без причины

```js
// БЕССМЫСЛЕННО - ловим и бросаем то же самое
try {
  doSomething();
} catch (e) {
  throw e; // зачем ловили?
}

// ОСМЫСЛЕННО - добавляем контекст
try {
  doSomething();
} catch (e) {
  throw new Error("doSomething failed during init", { cause: e });
}
```

## Частые вопросы на собесе

**Что такое Error объект и какие у него свойства?**
`Error` - базовый класс ошибок. Свойства: `name` (тип), `message` (описание), `stack` (stack trace - цепочка вызовов). Всегда бросай Error (не строки или числа) - для stack trace и instanceof проверок.

**Разница между TypeError и ReferenceError?**
`ReferenceError` - переменная не существует в scope (`notDefined`). `TypeError` - переменная существует, но операция невозможна (`null.property`, `"string"()`).

**Как обрабатывать ошибки в async-коде?**
Два способа: 1) async/await + try/catch. 2) Promise chain + .catch(). Глобально: `window.addEventListener('unhandledrejection', handler)`. В React: Error Boundaries для ошибок рендеринга.

**Зачем нужны custom errors?**
Типизированная обработка через `instanceof`. Дополнительные поля (statusCode, field). Понятные сообщения. Вместо `if (e.message.includes("404"))` - чёткое `if (e instanceof NotFoundError)`.

**Что делает finally и когда он выполняется?**
`finally` выполняется **всегда** - и при успехе, и при ошибке, и даже при `return` из try/catch. Используй для cleanup: закрытие соединений, скрытие лоадеров. Не используй `return` внутри `finally` - он перезапишет return из try.

**Что такое error.cause?**
ES2022 фича: `new Error("message", { cause: originalError })`. Стандартный способ сохранить оригинальную ошибку при оборачивании. Создаёт цепочку ошибок для отладки.
