# Обработка ошибок

Как ошибки появляются, распространяются и где их ловить: `try`/`catch`/`finally`, объект `Error` и свои классы ошибок, ошибки в асинхронном коде и глобальные обработчики. На mid спрашивают разницу `TypeError` и `ReferenceError`, `finally` и ошибки в `async`-функциях. На senior — что делает `return` в `finally`, почему `fetch` не отклоняется на 404, что происходит с необработанным отклонением в Node.js и какие ошибки повторять.

::tldr
- **Исключение летит вверх по стеку вызовов до ближайшего `catch`.** Если его нет, в браузере ошибка уходит в консоль и `window.onerror`, а в Node.js процесс завершается.
- **`finally` выполняется всегда**, даже после `return`. Но `return` внутри `finally` перекрывает результат и **проглатывает** брошенную ошибку.
- **Бросают только `Error` и его наследников:** у них есть `name`, `message`, `stack`, а через `cause` — исходная причина. Свои классы ошибок дают проверку через `instanceof` вместо разбора строк.
- **`try` ловит только синхронные ошибки и `await`.** Ошибку из колбэка таймера и отклонённый промис без `await` он не видит. Необработанное отклонение в Node.js завершает процесс с кодом 1.
- **Ошибки бывают ожидаемые и неожиданные.** Ожидаемые (нет сети, 404, неверный ввод) обрабатывают на месте, неожиданные пропускают наверх — к границе ошибок и мониторингу. Повторяют только временные: сеть, 429, 5xx.
::

## Как летит исключение

Сквозной пример — оформление заказа: проверить форму, отправить платёж, разобрать ответ.

```js
async function checkout(form) {
  const order = validate(form);           // может бросить ValidationError
  const result = await pay(order);        // может упасть по сети или с 503
  showReceipt(result);
}
```

`throw` прерывает выполнение функции, и исключение летит **вверх по стеку вызовов**: из `validate` в `checkout`, из `checkout` в того, кто её вызвал, — до ближайшего `catch`. Если `catch` нет нигде, ошибка становится **необработанной**: в браузере она попадает в консоль и глобальный обработчик, в Node.js — завершает процесс.

### try, catch, finally

```js
try {
  const order = validate(form);
  await pay(order);
} catch (error) {
  showError(error);
} finally {
  hideSpinner();                          // при успехе, при ошибке, после return
}
```

- `try` — код, ошибки которого мы готовы обработать;
- `catch` — обработка. Параметр можно опустить (`catch { ... }`), если ошибка не нужна;
- `finally` — уборка, которая нужна в любом случае: закрыть соединение, скрыть индикатор, снять блокировку.

У `finally` есть ловушка. Он выполняется даже после `return` в `try`, и если в нём есть свой `return`, он **перекрывает** результат. Хуже того — `return` в `finally` **проглатывает исключение**:

```js
function save() {
  try {
    throw new Error('диск полон');
  } finally {
    return 'сохранено';                   // ошибка потеряна, вызывающий видит успех
  }
}
```

А ошибка, брошенная в `finally`, заменяет исходную. Поэтому в `finally` не пишут `return` и не бросают — только уборку.

Что именно мы ловим? Ошибки — объекты, и у них есть устройство.

## Объект Error

```js
const error = new Error('Платёж отклонён', { cause: originalError });
error.name;      // 'Error'
error.message;   // 'Платёж отклонён'
error.stack;     // 'Error: Платёж отклонён\n    at pay (checkout.js:12:11)\n ...'
error.cause;     // исходная ошибка
```

- **`message`** — описание для человека;
- **`name`** — тип ошибки. По нему и по классу ошибку различают в коде;
- **`stack`** — стек вызовов на момент создания объекта. Свойство нестандартное, но есть во всех движках, и это главный инструмент отладки;
- **`cause`** — исходная ошибка, если эту создали как обёртку. Позволяет добавить контекст, не теряя причину.

### Встроенные типы

| Тип | Когда | Пример |
| --- | --- | --- |
| `ReferenceError` | имени нет в области видимости или переменная во временной мёртвой зоне | `notDeclared` |
| `TypeError` | значение есть, но операция с ним невозможна | `null.price`, `(42)()` |
| `SyntaxError` | код или данные не разбираются | `JSON.parse('{price: 1}')` |
| `RangeError` | значение вне допустимого диапазона | `new Array(-1)`, переполнение стека |
| `URIError` | неверная кодировка URI | `decodeURIComponent('%')` |
| `AggregateError` | несколько ошибок сразу | `Promise.any`, где отклонились все |

Самая частая пара на собеседованиях: `ReferenceError` — «такого имени нет», `TypeError` — «имя есть, но с этим значением так нельзя».

### Бросай только Error

Бросить можно что угодно — строку, число, объект. Но у строки нет стека: в мониторинге будет `'Платёж отклонён'` без единой строчки о том, где это произошло. А код, который ловит, не сможет проверить `instanceof` или прочитать `cause`. Поэтому бросают только `Error` и его наследников. Если ловишь чужой код, который бросает что попало, проверяй: в ES2026 для этого есть `Error.isError(value)` — он отличает настоящую ошибку от объекта, похожего на неё.

Встроенных типов мало для бизнес-логики. «Неверный email» и «сервер вернул 503» обрабатываются по-разному, и это лучше выразить типами.

## Свои классы ошибок

```js
class ValidationError extends Error {
  name = 'ValidationError';
  constructor(field, message) {
    super(message);
    this.field = field;
  }
}

class HttpError extends Error {
  constructor(status, url, options) {
    super(`HTTP ${status} для ${url}`, options);
    this.name = 'HttpError';
    this.status = status;
  }
}
```

Свои классы дают три вещи:

- **проверку по типу** — `error instanceof HttpError` вместо хрупкого `error.message.includes('503')`;
- **данные** — поле с ошибкой, HTTP-статус, код ошибки для перевода;
- **понятный `name`** в стеке и мониторинге.

`name` нужно задать вручную — иначе он унаследуется как `'Error'`. Если код компилируется TypeScript в ES5, наследование от `Error` ломает `instanceof`: нужен `Object.setPrototypeOf(this, new.target.prototype)` в конструкторе. С современной целью компиляции это не нужно.

### Обёртка с причиной

На границе слоя ошибку низкого уровня оборачивают в ошибку предметной области и сохраняют исходную в `cause`:

```js
async function pay(order) {
  try {
    return await api.post('/pay', order);
  } catch (cause) {
    throw new PaymentError(`Не удалось оплатить заказ ${order.id}`, { cause });
  }
}
```

Интерфейс показывает понятное сообщение, а в мониторинге видна вся цепочка — от `TypeError: fetch failed` до `PaymentError`. Без `cause` исходный стек терялся бы.

Классы ошибок готовы. Но в оформлении заказа самое опасное место — асинхронное, и там правила другие.

## Ошибки в асинхронном коде

`try` ловит ошибки кода, который выполняется **внутри него**. Асинхронный код выполняется позже, когда `try` уже закончился:

```js
try {
  setTimeout(() => { throw new Error('в таймере'); }, 0);   // не поймается
  pay(order);                                               // отклонение без await — не поймается
} catch (error) {
  // сюда не попадём
}
```

Колбэк таймера выполняется в другой задаче, со своим стеком (подробно — в [Event Loop](/content/javascript/event-loop)). Отклонённый промис без `await` — это значение, а не исключение: `try` возвращает его и заканчивается. Правила:

- **в `async`-функциях** — `await` внутри `try`. Тогда отклонение превращается в исключение в этом месте;
- **с цепочками промисов** — `.catch()` в конце цепочки;
- **в колбэках** — `try` внутри самого колбэка.

`async`-функция никогда не бросает исключение в месте вызова: даже `throw` в её начале становится отклонённым промисом. Поэтому вызов без `await` и без `.catch()` — это потерянная ошибка. Как `return await` влияет на `catch` — в [Асинхронности](/content/javascript/async).

### fetch не отклоняется на 404

Частая ошибка в нашем примере:

```js
const res = await fetch('/api/pay', { method: 'POST', body });
const result = await res.json();          // 404 и 500 сюда тоже дойдут
```

`fetch` отклоняется только при **сетевой** ошибке: нет соединения, сбой DNS, CORS, отмена. Ответ с кодом 404 или 503 — успешно полученный ответ, и промис выполняется. Статус проверяют вручную через `res.ok`. Вторая ловушка — `res.json()` бросает `SyntaxError`, если сервер вернул HTML страницы обслуживания вместо JSON.

### Необработанные отклонения

Если отклонённый промис так никто и не обработал:

- **в браузере** — событие `unhandledrejection` на `window` и ошибка в консоли. Если обработчик добавят позже, придёт `rejectionhandled`. В проверке в Chromium пришли оба события;
- **в Node.js** — с версии 15 процесс **завершается** с кодом 1. В проверке скрипт с `Promise.reject` без обработчика упал раньше, чем успел выполниться следующий таймер. Изменить поведение можно обработчиком `process.on('unhandledRejection')` или флагом `--unhandled-rejections`.

Исключение в колбэке, которое никто не поймал, в браузере попадает в `window.onerror` и событие `error`, в Node.js — в `process.on('uncaughtException')`, без обработчика процесс тоже завершается. Глобальные обработчики — место для отправки ошибок в мониторинг, а не способ продолжить работу как ни в чём не бывало: после неожиданной ошибки состояние приложения может быть испорчено.

> Ошибки рендера React-компонентов ловят границы ошибок — в [Компонентах и JSX](/content/reactjs/components-and-jsx).

Мы знаем, как ловить. Осталось решить, **что** ловить и что с этим делать.

## Стратегия

### Ожидаемые и неожиданные ошибки

Ошибки делятся на два вида, и обрабатываются они по-разному:

- **ожидаемые** — неверный ввод, нет сети, 404, 409 «заказ уже оплачен». Это часть логики: их ловят **рядом**, показывают понятное сообщение и предлагают действие;
- **неожиданные** — баги: `TypeError` на `undefined`, нарушенный инвариант. Их **не ловят на месте**, а пропускают наверх — к границе ошибок, глобальному обработчику и в мониторинг, со стеком и контекстом.

Отсюда антипаттерны:

- **пустой `catch`** — ошибка исчезает, а приложение продолжает работать в испорченном состоянии;
- **`catch`, который ловит всё**, включая баги, и показывает «попробуйте позже» — баг никогда не попадёт в мониторинг;
- **исключения вместо условий** — `try { JSON.parse(x) } catch` для проверки, строка ли это, когда есть обычная проверка;
- **перехват ради `console.log` и повторного броска без контекста** — шум без пользы. Если перехватывать, то чтобы добавить контекст через `cause` или обработать.

### Повторять только временное

Повтор запроса помогает при временных сбоях и вредит при постоянных. Повторяют:

- сетевые ошибки и тайм-ауты;
- `429 Too Many Requests` — с учётом заголовка `Retry-After`;
- `5xx` — с растущей паузой (exponential backoff), чтобы не добить перегруженный сервер.

Не повторяют `4xx`: неверный запрос не станет верным от повтора. И не повторяют неидемпотентные операции (платёж) без ключа идемпотентности — иначе деньги спишутся дважды.

## Красные флаги в ответе

- **«`finally` не влияет на результат».** `return` в `finally` перекрывает результат и проглатывает ошибку.
- **«`try` вокруг асинхронного кода поймает его ошибки».** Только с `await`. Колбэки таймеров и промисы без `await` выполняются вне `try`.
- **«`fetch` отклоняется при ошибке сервера».** Только при сетевой ошибке. Статус проверяют через `res.ok`.
- **«Брошу строку — так проще».** У строки нет стека, `instanceof` и `cause`. Бросают `Error`.
- **«Поймаю все ошибки, чтобы приложение не падало».** Баги нужно видеть в мониторинге, а не прятать. Ловят ожидаемые ошибки.
- **«Повторю запрос три раза на любую ошибку».** 4xx от повтора не исправится, а неидемпотентный запрос выполнится дважды.

## Как спрашивают на собеседовании

::question{level="mid"}
Что такое объект Error и какие у него свойства?

#mid
Базовый класс ошибок. У него есть `name` (тип), `message` (описание) и `stack` (стек вызовов в момент создания). Бросают всегда `Error` или наследников, а не строки — ради стека и проверки через `instanceof`.

#senior
С ES2022 есть `cause` — исходная ошибка при обёртке: `new Error('...', { cause })`. Стек — нестандартное, но повсеместное свойство, в V8 его можно настроить через `Error.captureStackTrace`. Для «не одна ошибка» есть `AggregateError`, а для надёжной проверки чужого значения в ES2026 — `Error.isError`.
::

::question{level="mid"}
В чём разница между TypeError и ReferenceError?

#mid
`ReferenceError` — имени нет в области видимости: обращение к необъявленной переменной или к `let` до объявления. `TypeError` — имя есть, но операция с этим значением невозможна: чтение свойства у `null`, вызов не функции.

#senior
`ReferenceError` возникает на этапе разрешения имени, в том числе во временной мёртвой зоне. `TypeError` — при выполнении операции над значением: запись в замороженный объект в strict mode, `new` для стрелки, вызов класса без `new`. Самый частый `TypeError` в проде — `Cannot read properties of undefined`, его лечат проверками данных и `?.`, а не `try`.
::

::question{level="mid"}
Как обрабатывать ошибки в асинхронном коде?

#mid
В `async`-функциях — `try`/`catch` вокруг `await`. С цепочками промисов — `.catch()` в конце. Глобально — `unhandledrejection` в браузере и `process.on('unhandledRejection')` в Node.js.

#senior
`try` не видит ошибки из колбэков таймеров и отклонения промисов без `await`. `async`-функция никогда не бросает в месте вызова — даже `throw` в её начале становится отклонением. Необработанное отклонение в Node.js с версии 15 завершает процесс с кодом 1. `fetch` не отклоняется на 4xx и 5xx — нужен `res.ok`.
::

::question{level="mid"}
Зачем нужны свои классы ошибок?

#mid
Чтобы различать ошибки по типу через `instanceof`, а не по тексту сообщения, и добавлять данные: поле формы, HTTP-статус, код ошибки.

#senior
Классы задают язык ошибок предметной области: на границе слоя низкоуровневую ошибку оборачивают в `PaymentError` с `cause`, и интерфейс решает по типу, что показать. `name` нужно задать явно. При компиляции TypeScript в ES5 наследование от `Error` ломает `instanceof` — лечится `Object.setPrototypeOf(this, new.target.prototype)`.
::

::question{level="senior"}
Что делает finally и когда он выполняется?

#mid
Всегда: при успехе, при ошибке и даже после `return` в `try` или `catch`. Используется для уборки: скрыть индикатор, закрыть соединение.

#senior
`return` в `finally` перекрывает результат `try` и проглатывает брошенное исключение — вызывающий увидит успех. Ошибка, брошенная в `finally`, заменяет исходную. В промисах `.finally()` устроен иначе: он не получает значение и не меняет его, но тоже заменяет результат, если бросит.
::

::question{level="mid"}
Что такое error.cause?

#mid
Стандартный способ сохранить исходную ошибку при обёртке: `new Error('Не удалось оплатить', { cause: original })`. Получается цепочка ошибок для отладки.

#senior
Обёртка нужна на границе слоя: нижний слой знает про сеть, верхний — про заказы. Без `cause` исходный стек терялся бы, и в мониторинге была бы только верхняя ошибка. Мониторинги показывают цепочку причин, а `console.error` в Node.js и браузерах выводит `cause` вложенно.
::

::question{level="senior"}
Какие ошибки стоит повторять?

#mid
Временные: сетевые ошибки, тайм-ауты, 5xx и 429. Повторяют с растущей паузой. 4xx не повторяют — запрос не станет верным.

#senior
У 429 и 503 смотрят заголовок `Retry-After`. Паузу увеличивают экспоненциально и добавляют случайный разброс, чтобы клиенты не повторяли одновременно. Неидемпотентные операции (платёж, создание заказа) повторяют только с ключом идемпотентности, иначе действие выполнится дважды. Ограничивают и число попыток, и общее время, а на постоянные сбои отвечают circuit breaker.
::

## Практика

::practice{title="Что вернёт функция?"}
```js
function a() {
  try { return 'try'; } finally { console.log('finally a'); }
}

function b() {
  try { throw new Error('ошибка'); } finally { return 'finally b'; }
}

function c() {
  try { throw new Error('исходная'); } finally { throw new Error('из finally'); }
}

console.log(a());
console.log(b());
try { c(); } catch (e) { console.log(e.message); }
```

#solution
```text
finally a
try
finally b
из finally
```

- `finally` выполняется после `return`, но не меняет результат, если сам ничего не возвращает.
- `return` в `finally` перекрывает исключение: ошибка из `try` молча пропадает.
- Ошибка, брошенная в `finally`, заменяет исходную.
::

::practice{title="Почему оплата «успешна» при ошибке сервера?"}
Сервер вернул 503, а приложение показало чек с `undefined` вместо номера заказа. Иногда падает с `SyntaxError: Unexpected token '<'`:

```js
async function pay(order) {
  try {
    const res = await fetch('/api/pay', { method: 'POST', body: JSON.stringify(order) });
    const result = await res.json();
    showReceipt(result.receiptId);
  } catch (error) {
    showError('Нет соединения');
  }
}
```

#solution
`fetch` отклоняется только при сетевой ошибке. Ответ 503 — успешно полученный ответ, промис выполняется, и код идёт дальше с телом ошибки. Если сервер вернул HTML страницы обслуживания, `res.json()` бросает `SyntaxError`, а `catch` показывает «Нет соединения», хотя соединение есть.

```js
class HttpError extends Error {
  constructor(status, url, options) {
    super(`HTTP ${status} для ${url}`, options);
    this.name = 'HttpError';
    this.status = status;
  }
}

async function getJson(url, init) {
  let res;
  try {
    res = await fetch(url, init);
  } catch (cause) {
    throw new HttpError(0, url, { cause });           // сеть, CORS, отмена
  }
  if (!res.ok) throw new HttpError(res.status, url);
  try {
    return await res.json();
  } catch (cause) {
    throw new HttpError(res.status, url, { cause });  // ответ не JSON
  }
}

async function pay(order) {
  try {
    const result = await getJson('/api/pay', { method: 'POST', body: JSON.stringify(order) });
    showReceipt(result.receiptId);
  } catch (error) {
    if (error instanceof HttpError && error.status === 0) showError('Нет соединения');
    else if (error instanceof HttpError && error.status >= 500) showError('Сервис временно недоступен');
    else throw error;                                 // баг — пусть уйдёт в мониторинг
  }
}
```

Каждая причина различима по типу и статусу, исходная ошибка сохранена в `cause`, а неожиданные ошибки не проглатываются. В проверке на локальном сервере 404 дал `HttpError` со статусом, HTML вместо JSON — `HttpError` с `SyntaxError` в `cause`, а недоступный порт — статус 0 с `TypeError` в `cause`.
::

::practice{title="Повтор только временных ошибок"}
Напиши `withRetry(fn, { retries })`, которая повторяет `fn` с растущей паузой, но только при временных ошибках: сеть (статус 0), 429 и 5xx. Ошибки 4xx должны пробрасываться сразу.

#solution
```js
const isRetryable = (e) =>
  e instanceof HttpError && (e.status === 0 || e.status === 429 || e.status >= 500);

async function withRetry(fn, { retries = 3, baseDelay = 300 } = {}) {
  for (let attempt = 0; ; attempt++) {
    try {
      return await fn();
    } catch (error) {
      if (attempt >= retries || !isRetryable(error)) throw error;
      const jitter = Math.random() * baseDelay;
      await new Promise((r) => setTimeout(r, baseDelay * 2 ** attempt + jitter));
    }
  }
}

const product = await withRetry(() => getJson('/api/products/7'));
```

`return await` внутри `try` нужен, чтобы `catch` поймал отклонение `fn`. Пауза растёт в два раза с каждой попыткой, а случайная добавка не даёт тысячам клиентов повторять одновременно. В проверке запрос к нестабильному серверу удался с третьей попытки, а 404 не повторялся ни разу. Платёж через `withRetry` можно повторять только с ключом идемпотентности.
::
