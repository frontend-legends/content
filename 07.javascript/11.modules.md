# Модули

Модули - это способ разбить код на **изолированные, переиспользуемые части** с чётко определёнными интерфейсами. До модулей JavaScript жил в глобальном scope - любой скрипт мог перезаписать переменные другого. Сегодня ES Modules (ESM) - стандарт и в браузере, и в Node.js. На собесе спрашивают про разницу ESM и CommonJS, tree shaking, динамический import и циклические зависимости.

---

## Зачем модули

- **Инкапсуляция** - каждый модуль имеет свой scope, внутренние детали скрыты
- **Переиспользование** - один модуль можно импортировать в десятки файлов
- **Управление зависимостями** - явный import/export вместо «надеемся, что скрипт подключён»
- **Поддерживаемость** - маленькие файлы с одной ответственностью проще читать и тестировать
- **Tree shaking** - бандлер удаляет неиспользуемый код (только ESM)

## До модулей - как жили раньше

### Глобальные переменные

```js
// utils.js
var formatDate = function (date) {
  return date.toLocaleDateString();
};

// app.js
// надеемся, что utils.js подключён ДО app.js
var result = formatDate(new Date());
// Любой скрипт может перезаписать formatDate
```

Проблемы: конфликты имён, неявные зависимости, порядок подключения `<script>` критичен.

### IIFE (Immediately Invoked Function Expression)

```js
var MyModule = (function () {
  // приватная переменная - снаружи не видна
  var privateCounter = 0;

  // публичный API
  return {
    increment: function () {
      privateCounter++;
    },
    getCount: function () {
      return privateCounter;
    },
  };
})();

MyModule.increment();
console.log(MyModule.getCount()); // 1
console.log(MyModule.privateCounter); // undefined - приватный
```

<span class="text-gray">IIFE создаёт scope через замыкание. Это «модульный паттерн» (Module Pattern) - де-факто стандарт до CommonJS/ESM. jQuery, Lodash и многие библиотеки использовали именно его.</span>

### Namespace pattern

```js
// Всё под одним глобальным объектом
var App = App || {};
App.Utils = App.Utils || {};
App.Utils.formatDate = function (date) {
  return date.toLocaleDateString();
};
```

<b class="text-on-semi-light">Итог:</b> Все эти подходы - workarounds. Настоящие модули появились с CommonJS (2009, Node.js) и ES Modules (2015, спецификация).

## CommonJS (CJS)

Модульная система **Node.js**. Синхронная загрузка, подходит для серверного кода.

### Синтаксис

```js
// math.js - экспорт
function add(a, b) {
  return a + b;
}

function multiply(a, b) {
  return a * b;
}

module.exports = { add, multiply };
// или: exports.add = add; exports.multiply = multiply;

// app.js - импорт
const { add, multiply } = require("./math");
console.log(add(2, 3)); // 5
```

### Default export в CommonJS

```js
// logger.js
class Logger {
  log(msg) {
    console.log(`[LOG] ${msg}`);
  }
}

module.exports = Logger; // один объект

// app.js
const Logger = require("./logger");
const logger = new Logger();
```

### Как работает require

1. **Resolve** - находит путь к файлу (расширение `.js`/`.json`/`.node` пробуется автоматически)
2. **Load** - читает файл с диска
3. **Wrap** - оборачивает в функцию: `(function(exports, require, module, __filename, __dirname) { ... })`
4. **Execute** - выполняет код модуля
5. **Cache** - кэширует результат (повторный `require` вернёт кэш)

```js
// Кэширование - модуль выполняется ОДИН раз
const a = require("./counter"); // выполняет код
const b = require("./counter"); // возвращает кэш
console.log(a === b); // true - один и тот же объект
```

<span class="text-gray">`require` - синхронный. Файл читается с диска и выполняется сразу. Это нормально для сервера (файлы локальные), но неприемлемо для браузера (файлы нужно скачивать по сети).</span>

## ES Modules (ESM)

Стандарт ECMAScript. Работает в браузере и Node.js. Статический анализ, tree shaking, async loading.

### Синтаксис

```js
// math.js - named exports
export function add(a, b) {
  return a + b;
}

export function multiply(a, b) {
  return a * b;
}

// Или экспорт в конце файла
function subtract(a, b) {
  return a - b;
}
export { subtract };

// app.js - named imports
import { add, multiply } from "./math.js";
console.log(add(2, 3)); // 5
```

### Default export

```js
// logger.js
export default class Logger {
  log(msg) {
    console.log(`[LOG] ${msg}`);
  }
}

// app.js - имя при импорте может быть любым
import Logger from "./logger.js";
import MyLogger from "./logger.js"; // тоже работает
```

### Named exports vs default export

| Аспект                  | Named export                       | Default export                |
| ----------------------- | ---------------------------------- | ----------------------------- |
| Синтаксис экспорта      | `export function foo() {}`         | `export default function() {}`|
| Синтаксис импорта       | `import { foo } from "./mod"`      | `import foo from "./mod"`     |
| Имя при импорте         | Должно совпадать (или alias)       | Любое                         |
| Количество в файле      | Сколько угодно                     | Один                          |
| Переименование          | `import { foo as bar }`            | Имя произвольное              |
| Tree shaking            | Отлично работает                   | Работает хуже                 |
| Автокомплит IDE         | Да (IDE знает имена)               | Нет (имя произвольное)        |

<b class="text-on-semi-light">Рекомендация:</b> Предпочитай **named exports**. Они лучше для tree shaking, автокомплита и рефакторинга. Default export оправдан для главного экспорта файла (React-компонент, класс).

### Import alias

```js
import { add as sum, multiply as mul } from "./math.js";
console.log(sum(2, 3)); // 5
```

### Namespace import

```js
import * as math from "./math.js";
console.log(math.add(2, 3)); // 5
console.log(math.multiply(2, 3)); // 6
```

## CJS vs ESM - сравнение

| Аспект               | CommonJS (CJS)                | ES Modules (ESM)                  |
| -------------------- | ----------------------------- | --------------------------------- |
| Синтаксис            | `require` / `module.exports`  | `import` / `export`               |
| Загрузка             | Синхронная                    | Асинхронная                       |
| Анализ               | Динамический (runtime)        | Статический (parse time)          |
| Tree shaking         | Невозможен                    | Возможен                          |
| Браузер              | Нет (нужен бандлер)           | Да (нативная поддержка)           |
| Node.js              | Да (основной до ESM)          | Да (с v12+, стабильно v14+)      |
| `this` на верхнем уровне | `module.exports` (объект) | `undefined`                       |
| Strict mode          | Нет (по умолчанию)           | Да (всегда)                       |
| Расширение файла     | `.js`, `.cjs`                 | `.mjs` или `.js` с `"type": "module"` |
| Условный import      | Да (`if (x) require(...)`)   | Нет (только dynamic `import()`)  |
| Кэширование          | По пути файла                 | По URL                            |

<b class="text-on-semi-light">Ключевое отличие:</b> ESM анализируется **статически** - движок знает все imports/exports ещё до выполнения кода. Это позволяет tree shaking, ранние ошибки и оптимизации. CJS анализируется **динамически** - `require` может быть внутри `if`, в любом месте кода.

```js
// CJS - динамический, работает
if (process.env.NODE_ENV === "production") {
  module.exports = require("./prod.js");
} else {
  module.exports = require("./dev.js");
}

// ESM - статический, так нельзя
// if (condition) {
//   import { x } from "./mod.js"; // SyntaxError!
// }

// ESM - для условного импорта используй dynamic import
const mod = await import(
  condition ? "./prod.js" : "./dev.js"
);
```

## Re-exports

Удобный способ создать «barrel file» - единую точку входа для модуля:

```js
// components/Button.js
export function Button() { /* ... */ }

// components/Input.js
export function Input() { /* ... */ }

// components/Modal.js
export function Modal() { /* ... */ }

// components/index.js - barrel file
export { Button } from "./Button.js";
export { Input } from "./Input.js";
export { Modal } from "./Modal.js";

// Или всё сразу:
export * from "./Button.js";
export * from "./Input.js";

// Переименование при re-export
export { Button as PrimaryButton } from "./Button.js";

// Re-export default как named
export { default as Button } from "./Button.js";
```

```js
// Теперь можно импортировать всё из одного места
import { Button, Input, Modal } from "./components/index.js";
```

⚠️ Barrel files могут **ухудшить** tree shaking, если бандлер не справляется с `export *`. Webpack и Rollup обычно справляются, но будь внимателен с `sideEffects` в package.json.

## Dynamic imports

`import()` - **функция** (не statement), возвращает Promise. Позволяет загружать модули по требованию.

```js
// Загрузка по условию
async function loadEditor() {
  if (needsRichEditor) {
    const { Editor } = await import("./RichEditor.js");
    return new Editor();
  }
  return document.createElement("textarea");
}

// Загрузка по событию (code splitting)
button.addEventListener("click", async () => {
  const { openModal } = await import("./modal.js");
  openModal();
});
```

### Code splitting

Бандлеры (Webpack, Vite, Rollup) используют `import()` как точку разделения:

```js
// Webpack/Vite создаст отдельный chunk для heavy-module
const module = await import("./heavy-module.js");

// React lazy loading
const LazyComponent = React.lazy(() => import("./HeavyComponent"));
```

<b class="text-on-semi-light">На фронте:</b> Dynamic import - основа code splitting. Вместо одного огромного bundle.js загружаем код по мере необходимости. Route-based splitting (каждая страница - отдельный chunk) - стандартная практика в React/Vue/Angular.

## Import attributes

Новый синтаксис (Stage 3 -> включён в движки) для указания типа импортируемого ресурса:

```js
// Импорт JSON
import data from "./data.json" with { type: "json" };

// Импорт CSS (в некоторых средах)
import styles from "./styles.css" with { type: "css" };

// Dynamic import с атрибутами
const config = await import("./config.json", {
  with: { type: "json" },
});
```

<span class="text-gray">Import attributes (ранее назывались import assertions) пришли на смену синтаксису `assert`. Поддержка зависит от среды и бандлера. В Node.js JSON-импорт с `with { type: "json" }` работает с v21+.</span>

## Circular dependencies - циклические зависимости

Когда модуль A импортирует B, а B импортирует A.

### В CommonJS

```js
// a.js
console.log("a.js начал загрузку");
exports.done = false;
const b = require("./b.js"); // загружает b.js
console.log("в a.js: b.done =", b.done);
exports.done = true;
console.log("a.js закончил загрузку");

// b.js
console.log("b.js начал загрузку");
exports.done = false;
const a = require("./a.js"); // a.js ещё НЕ закончил - получаем ЧАСТИЧНЫЙ exports
console.log("в b.js: a.done =", a.done); // false (не true!)
exports.done = true;
console.log("b.js закончил загрузку");
```

```text
Вывод при require("./a.js"):
a.js начал загрузку
b.js начал загрузку
в b.js: a.done = false    // частичный exports!
b.js закончил загрузку
в a.js: b.done = true
a.js закончил загрузку
```

<b class="text-on-semi-light">CJS и циклы:</b> `require` возвращает **частично заполненный** объект exports. Модуль ещё не закончил выполнение, но то, что уже экспортировано - доступно. Это может приводить к трудноуловимым багам.

### В ESM

```js
// a.mjs
import { b } from "./b.mjs";
export const a = "a value";
console.log("в a.mjs: b =", b);

// b.mjs
import { a } from "./a.mjs";
export const b = "b value";
console.log("в b.mjs: a =", a); // ReferenceError или undefined!
```

<b class="text-on-semi-light">ESM и циклы:</b> ESM создаёт **live bindings** - ссылки на переменные. Но если переменная ещё не инициализирована (TDZ для `const`/`let`) - будет `ReferenceError`. ESM строже к циклам, чем CJS.

### Как избежать циклических зависимостей

1. **Вынести общий код** в третий модуль, который оба импортируют
2. **Dependency injection** - передавать зависимость как параметр
3. **Lazy require/import** - импортировать внутри функции, а не на верхнем уровне

```js
// Вместо циклического импорта - вынесли общее в shared.js
// a.js imports shared.js
// b.js imports shared.js
// Нет цикла!
```

## Tree Shaking

Tree shaking - удаление **неиспользуемого кода** при сборке. Работает только с ESM благодаря статическому анализу.

```js
// math.js
export function add(a, b) {
  return a + b;
}
export function multiply(a, b) {
  return a * b;
}
export function complexCalculation() {
  // 1000 строк тяжёлого кода
}

// app.js
import { add } from "./math.js";
console.log(add(2, 3));
// multiply и complexCalculation НЕ используются
// -> бандлер удалит их из финального bundle
```

### Почему не работает с CommonJS

```js
// CJS - динамический, бандлер не знает, что используется
const math = require("./math");
// math.add? math.multiply? Неизвестно до runtime
// Бандлер вынужден включить ВСЁ
```

### sideEffects в package.json

```json
{
  "name": "my-library",
  "sideEffects": false
}
```

<span class="text-gray">`"sideEffects": false` говорит бандлеру: «все файлы в этом пакете - pure modules без побочных эффектов. Если экспорт не используется - файл можно удалить целиком». Можно указать массив файлов с побочными эффектами: `"sideEffects": ["./src/polyfills.js", "*.css"]`.</span>

## Module Scope

Каждый модуль (ESM и CJS) имеет **свой scope**. Переменные, объявленные в модуле, не попадают в глобальный scope:

```js
// module.js
const secret = "hidden"; // не видна снаружи
export const visible = "public"; // доступна через import
```

```js
// В ESM:
console.log(this); // undefined (не window!)
console.log(typeof window); // "object" (в браузере всё ещё доступен)

// В CJS:
console.log(this); // {} (module.exports)
```

<b class="text-on-semi-light">Без модулей</b> (обычный `<script>`) - переменные `var` попадают в `window`. С модулями - scope изолирован. Это одна из причин, почему модули безопаснее.

## Модули в браузере - type="module"

```html
<!-- Обычный скрипт -->
<script src="app.js"></script>

<!-- ES Module -->
<script type="module" src="app.js"></script>
```

### Отличия type="module" от обычного script

| Аспект           | `<script>`                     | `<script type="module">`         |
| ---------------- | ------------------------------ | -------------------------------- |
| Загрузка         | Блокирует парсинг (без defer) | **defer** по умолчанию           |
| Strict mode      | Нет (по умолчанию)            | **Всегда** strict                |
| Scope            | Глобальный                     | **Module scope** (изолированный) |
| `this`           | `window`                       | `undefined`                      |
| Повторный import | Загружается каждый раз         | **Кэшируется** (один раз)       |
| CORS             | Не требует                     | **Требует** CORS-заголовки       |
| Выполнение       | В порядке подключения          | После парсинга HTML (defer)      |

```html
<!-- Module автоматически defer - не блокирует парсинг -->
<script type="module" src="app.js"></script>

<!-- Inline module тоже defer -->
<script type="module">
  import { init } from "./app.js";
  init();
</script>

<!-- nomodule - fallback для старых браузеров -->
<script nomodule src="legacy-bundle.js"></script>
```

<b class="text-on-semi-light">CORS:</b> `<script type="module">` требует CORS-заголовки даже для same-origin. Нельзя просто открыть `file://index.html` - нужен HTTP-сервер. Это частая ловушка при разработке без бандлера.

## Частые вопросы на собесе

**В чём разница между CommonJS и ES Modules?**
CJS - синхронный, динамический (`require` в runtime), нет tree shaking. ESM - асинхронный, статический (imports анализируются до выполнения), поддерживает tree shaking. CJS - `require/module.exports`. ESM - `import/export`.

**Что такое tree shaking?**
Удаление неиспользуемого кода при сборке. Работает только с ESM, потому что imports статичны - бандлер знает, что используется, ещё до выполнения. `"sideEffects": false` в package.json помогает бандлеру удалять целые неиспользуемые файлы.

**Что такое dynamic import и зачем он нужен?**
`import("./module.js")` возвращает Promise. Позволяет загружать модули по условию или событию. Основа code splitting - бандлер создаёт отдельные chunks для dynamic imports. React.lazy, route-based splitting - всё на dynamic import.

**Как работают циклические зависимости?**
CJS: `require` возвращает частично заполненный exports (что уже экспортировано). ESM: создаёт live bindings, но если переменная в TDZ - `ReferenceError`. Решение: вынести общий код в третий модуль.

**Named exports vs default export - что лучше?**
Named exports: лучше tree shaking, автокомплит IDE, рефакторинг (имена фиксированы). Default export: удобен для «главного» экспорта (React-компонент). Рекомендация: предпочитай named, используй default осознанно.

**Что даёт type="module" в HTML?**
Автоматический defer (не блокирует парсинг), strict mode, изолированный scope (не window), кэширование, требует CORS. По сути - правильное поведение по умолчанию, которого не было у обычных `<script>`.
