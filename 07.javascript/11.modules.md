# Модули

Как JavaScript делит код на файлы: ES-модули и CommonJS, чем они различаются на уровне механики, как работают циклические зависимости, динамический импорт и tree shaking. Спрашивают разницу `import` и `require`, named и default экспорт и что такое tree shaking. Глубже — почему импорт — живая привязка, а `require` — копия, что происходит при циклическом импорте, как top-level await задерживает другие модули и почему CommonJS плохо вычищается из бандла.

::tldr
- **Модуль — файл со своей областью видимости,** который выполняется один раз и явно объявляет, что отдаёт наружу. Повторный импорт возвращает тот же экземпляр.
- **ES-модули статичны:** импорты и экспорты известны до выполнения кода. Поэтому работают tree shaking, top-level await и раннее обнаружение ошибок. CommonJS — обычный вызов функции `require` во время выполнения.
- **Импорт ESM — живая привязка только для чтения:** импортёр видит текущее значение переменной модуля. `require` возвращает объект `module.exports`, и деструктуризация копирует значения в момент вызова.
- **Циклы разрешаются по-разному:** в CommonJS второй модуль получает недосчитанный `exports`, в ESM обращение к ещё не инициализированному `const` бросает `ReferenceError`, а объявления функций уже доступны.
- **Tree shaking удаляет неиспользуемые экспорты ESM** и оставляет побочные эффекты модулей. Из CommonJS бандлер не удаляет ничего, а `"sideEffects": false` разрешает выбросить неиспользуемый модуль целиком.
::

## Зачем модули

Сквозной пример — модуль корзины магазина:

```js
// cart.js
import { formatPrice } from './price.js';

let count = 0;
export function add(item) { count++; /* ... */ }
export { count };
export default function Cart() { /* компонент */ }
```

До модулей все скрипты страницы делили одну глобальную область видимости. Переменная `count` из одного скрипта конфликтовала с `count` из другого, порядок тегов `<script>` определял, что доступно, а зависимости были неявными. Решения появлялись сверху вниз:

- **IIFE и паттерн «модуль»** — функция, которая прячет переменные в замыкании и возвращает публичный API (подробно — в [Замыканиях](/content/javascript/closures));
- **CommonJS** — модули Node.js: `require` и `module.exports`;
- **AMD и UMD** — асинхронная загрузка в браузере и формат «работает везде»;
- **ES-модули** (ES2015) — модули на уровне языка, которые понимают и браузер, и Node.js.

Любой модуль даёт три вещи: собственную область видимости (переменные не утекают в глобальную), явный интерфейс (что экспортируется) и однократное выполнение — сколько бы раз модуль ни импортировали, его код выполнится один раз, а все получат один и тот же экземпляр. Поэтому модуль — естественный синглтон.

Сегодня живут два формата: ES-модули и CommonJS. Разница между ними — не только синтаксис.

## ES-модули

```js
// именованный экспорт
export const currency = '₽';
export function formatPrice(v) { return `${v} ${currency}`; }

// экспорт по умолчанию
export default function Cart() {}

// импорт
import Cart, { formatPrice as format } from './cart.js';
import * as price from './price.js';      // пространство имён
export { formatPrice } from './price.js'; // реэкспорт
```

### Статическая структура

`import` и `export` пишут только на верхнем уровне модуля, а путь — только строкой. Поэтому структура известна **до выполнения**: движок разбирает граф модулей, загружает их, связывает импорты с экспортами и только потом выполняет. Ошибка «такого экспорта нет» обнаруживается до запуска первой строки, а бандлер видит, какие экспорты используются, — на этом построен tree shaking.

Импорты поднимаются: модуль-зависимость выполняется до тела импортирующего модуля, даже если `import` написан в конце файла.

### Живые привязки

Импорт — не копия значения, а **живая привязка** к переменной модуля:

```js
// counter.js
export let count = 0;
export function inc() { count++; }

// main.js
import { count, inc } from './counter.js';
inc(); inc();
count;          // 2 — видно новое значение
count = 10;     // TypeError: Assignment to constant variable.
```

Импортёр видит текущее значение переменной, но изменить её не может: привязка только для чтения. Менять состояние модуля можно только через его функции. Пространство имён `import * as m` запечатано: в нём нельзя добавить или удалить свойство.

### Модули в браузере

`<script type="module">` ведёт себя иначе, чем обычный скрипт:

- **отложенное выполнение** — как `defer`: не блокирует разбор HTML и выполняется после него, по порядку;
- **strict mode** и `this === undefined` на верхнем уровне;
- **своя область видимости** — переменные не попадают в `window`;
- **CORS** — модуль с другого домена нужен с правильными заголовками, а открыть страницу через `file://` не получится;
- **однократная загрузка** — одинаковый URL загружается и выполняется один раз.

Голые имена пакетов (`import React from 'react'`) браузер без бандлера не понимает — для этого есть import maps, которые сопоставляют имена с URL.

ES-модули — стандарт. Но огромная часть npm написана на CommonJS, и его поведение отличается в важных местах.

## CommonJS

```js
const { formatPrice } = require('./price.cjs');
module.exports = { add, get count() { return count; } };
```

`require` — обычная функция, которая выполняется **во время работы кода**: прочитать файл, выполнить его в обёртке-функции, вернуть `module.exports`. Отсюда отличия:

| | ES-модули | CommonJS |
| --- | --- | --- |
| Синтаксис | `import` / `export` | `require` / `module.exports` |
| Когда разрешаются зависимости | до выполнения, статически | во время выполнения |
| Путь | только строка-литерал | любое выражение, можно в `if` |
| Что получает импортёр | живую привязку только для чтения | значение `module.exports` |
| Загрузка | асинхронная, графом | синхронная, по одному файлу |
| top-level `await` | есть | нет |
| `this` на верхнем уровне | `undefined` | `module.exports` |
| Tree shaking | да | практически нет |

Самое заметное отличие — **копия против привязки**. `const { count } = require('./counter.cjs')` копирует значение в момент вызова: после `inc()` переменная `count` у импортёра останется `0`. В проверке деструктуризация CommonJS сохранила старое значение, а импорт ESM показал новое.

### Взаимодействие форматов

В Node.js оба формата живут вместе:

- **ESM может импортировать CommonJS**: `module.exports` становится экспортом по умолчанию, а именованные импорты Node.js угадывает статическим анализом кода — не всегда успешно;
- **CommonJS может `require` ES-модуль** — в Node.js 22.12 и новее это работает без флагов, если в модуле нет top-level `await`. С ним `require` бросает `ERR_REQUIRE_ASYNC_MODULE`, потому что `require` синхронный. Проверено в Node.js 24;
- формат файла задают расширение (`.mjs`, `.cjs`) или поле `"type"` в `package.json`.

Разница форматов сильнее всего проявляется, когда модули импортируют друг друга по кругу.

## Циклические зависимости

`a` импортирует `b`, а `b` импортирует `a`. Кто-то из них неизбежно начнёт выполняться, пока другой не досчитан.

**В CommonJS** второй модуль получает **недосчитанный** `exports` первого — то, что успели записать до `require`:

```js
// a.cjs
exports.a = 'до require b';
const b = require('./b.cjs');
exports.a = 'готов';

// b.cjs
const a = require('./a.cjs');   // a ещё выполняется
exports.seenA = a.a;            // 'до require b'
```

Ошибки нет, но значение «не то» — и баг проявляется где-то дальше.

**В ESM** привязки уже созданы, но переменные во временной мёртвой зоне, пока модуль не дошёл до их объявления. Обращение к ещё не инициализированному `const` бросает `ReferenceError: Cannot access 'a' before initialization`. Объявления функций при этом уже готовы — они поднимаются целиком, — и их можно вызывать. В проверке модуль `b` смог вызвать функцию из `a`, а чтение константы из `a` бросило `ReferenceError`.

Лекарство одно — убрать цикл: вынести общий код в третий модуль, от которого зависят оба. Если цикл неизбежен, обращаться к значениям другого модуля только внутри функций, которые вызываются после загрузки, а не на верхнем уровне.

## Динамический импорт и top-level await

### import()

`import(path)` загружает модуль во время выполнения и возвращает промис с пространством имён:

```js
button.addEventListener('click', async () => {
  const { openEditor } = await import('./editor.js');
  openEditor();
});
```

В отличие от статического `import`, его можно вызвать где угодно и с вычисляемым путём. Бандлер выносит такой модуль в отдельный файл (chunk) — это основа разделения кода: тяжёлый редактор, график или страница загружаются, только когда нужны. `React.lazy` и ленивые маршруты построены на `import()` (подробно — в [Роутинге](/content/reactjs/routing)).

### Top-level await

В ES-модуле `await` можно писать на верхнем уровне:

```js
// config.js
const res = await fetch('/config.json');
export const config = await res.json();
```

Модуль с top-level `await` становится асинхронным: **все модули, которые его импортируют, ждут**, пока он досчитается. В проверке тело импортёра выполнилось только после того, как зависимость дождалась своего `await`. Это удобно для конфигурации и инициализации, но опасно: медленный запрос на верхнем уровне задерживает всё приложение, а цикл из модулей с top-level `await` может зависнуть навсегда.

### Атрибуты импорта

Нестандартные модули импортируют с атрибутом типа:

```js
import data from './currencies.json' with { type: 'json' };
```

Атрибут нужен для безопасности: сервер может отдать по адресу `.json` скрипт, и без явного типа он выполнился бы как код. В проверке Node.js отказался импортировать JSON без атрибута с ошибкой `ERR_IMPORT_ATTRIBUTE_MISSING`.

## Tree shaking

Tree shaking — удаление неиспользуемого кода при сборке. Бандлер строит граф импортов и выбрасывает экспорты, которые никто не импортирует. Это возможно только благодаря статической структуре ESM: бандлер знает, что используется, не выполняя код.

Проверка на esbuild:

- из ESM-модуля с двумя функциями, где импортирована одна, вторая **удалена**;
- побочный эффект верхнего уровня (`console.log` при загрузке модуля) **сохранён** — бандлер не может знать, что он не нужен;
- из CommonJS-модуля **не удалено ничего**: `module.exports` — обычный объект, и что из него используется, статически не определить.

Отсюда практические правила:

- **библиотеки в ESM.** `import { debounce } from 'lodash'` тянет всю CommonJS-библиотеку, а `lodash-es` — только `debounce`;
- **`"sideEffects": false` в `package.json`** говорит бандлеру, что модули пакета ничего не делают при загрузке: неиспользуемый модуль можно выбросить целиком, даже если в нём есть код верхнего уровня. В проверке модуль с таким флагом исчез из бандла полностью;
- **именованные экспорты** удобнее для анализа, чем объект в экспорте по умолчанию: свойства объекта бандлер не вычищает;
- **реэкспорты-«бочки»** (`index.js`, который реэкспортирует всё) не мешают tree shaking в production-сборке, но замедляют dev-сервер и тесты: импорт одной функции загружает весь граф.

> Как работают бандлеры и разделение кода — в главе [Инструменты сборки](/content/advanced-tooling/bundlers).

## Красные флаги в ответе

- **«`import` — это то же самое, что `require`, только новый синтаксис».** ESM статичен, асинхронен и даёт живые привязки; CommonJS выполняется во время работы и отдаёт значение.
- **«Импортированную переменную можно изменить».** Привязка только для чтения: присваивание бросает `TypeError`. Менять состояние модуля можно только его функциями.
- **«Модуль выполняется при каждом импорте».** Один раз; все импортёры получают один экземпляр.
- **«Tree shaking удаляет всё неиспользуемое».** Он не трогает побочные эффекты модулей и почти не работает с CommonJS.
- **«Циклический импорт — это ошибка».** Он работает, но опасен: в CommonJS — недосчитанный `exports`, в ESM — `ReferenceError` при обращении к неинициализированной переменной.

## Как спрашивают на собеседовании

::question
В чём разница между CommonJS и ES-модулями?

#answer
CommonJS — `require` и `module.exports`, синхронный и выполняется во время работы кода. ESM — `import` и `export`, статический: импорты известны до выполнения. Поэтому ESM поддерживает tree shaking и top-level `await`.

#more
Главная механическая разница: импорт ESM — живая привязка только для чтения к переменной модуля, а `require` возвращает объект `module.exports`, и деструктуризация копирует значения. ESM загружается графом асинхронно и связывается до выполнения, поэтому ошибки импорта видны сразу. В Node.js 22.12+ CommonJS может `require` ES-модуль без top-level `await`, иначе — `ERR_REQUIRE_ASYNC_MODULE`.
::

::question
Что такое tree shaking?

#answer
Удаление неиспользуемых экспортов при сборке. Работает с ES-модулями, потому что импорты статичны и бандлер видит, что используется. `"sideEffects": false` в `package.json` помогает выбросить неиспользуемые модули целиком.

#more
Бандлер не удаляет код с побочными эффектами верхнего уровня — он не может доказать, что это безопасно. CommonJS почти не вычищается: `module.exports` — обычный объект. Поэтому библиотеки публикуют в ESM (`lodash-es`), а функции помечают `/*#__PURE__*/`, если их вызов без использования результата можно выбросить. Свойства объекта в экспорте по умолчанию тоже не вычищаются — именованные экспорты удобнее.
::

::question
Что такое динамический импорт и зачем он нужен?

#answer
`import('./module.js')` загружает модуль во время выполнения и возвращает промис. Его используют, чтобы загружать код по условию или событию, и это основа разделения кода: бандлер выносит такой модуль в отдельный файл.

#more
`import()` можно вызвать где угодно, с вычисляемым путём, в том числе из CommonJS. На нём построены `React.lazy` и ленивые маршруты. Бандлеру нужен статически анализируемый путь (или шаблон с переменной частью), иначе он не создаст chunk. Модуль загружается один раз: повторный `import()` того же пути вернёт тот же экземпляр.
::

::question
Как работают циклические зависимости?

#answer
В CommonJS второй модуль получает недосчитанный `exports` первого. В ESM обращение к переменной, которая ещё не инициализирована, бросает `ReferenceError`. Лучшее решение — вынести общий код в третий модуль.

#more
В ESM привязки создаются при связывании, до выполнения, поэтому цикл не ломает загрузку, но переменные остаются во временной мёртвой зоне, пока модуль не дошёл до объявления. Объявления функций при этом уже готовы и вызываются. Если цикл неизбежен, к значениям другого модуля обращаются внутри функций, вызванных после загрузки, а не на верхнем уровне. Цикл из модулей с top-level `await` может зависнуть.
::

::question
Named или default export — что лучше?

#answer
Именованные: стабильные имена, автодополнение, удобный рефакторинг и tree shaking. Default — для единственного главного экспорта модуля, например компонента. Многие команды предпочитают только именованные.

#more
Default можно импортировать под любым именем, поэтому одна сущность расходится по проекту под разными именами, а переименование её не находит. Объект в default-экспорте бандлер не вычищает по свойствам. При взаимодействии с CommonJS default — это весь `module.exports`, а именованные импорты зависят от статического анализа и иногда не находятся.
::

::question
Как top-level await влияет на загрузку модулей?

#answer
Модуль с top-level `await` ждёт выполнения промиса перед тем, как досчитаться, и все модули, которые его импортируют, ждут вместе с ним.

#more
Асинхронный модуль задерживает выполнение всех, кто от него зависит, но соседние независимые ветки графа выполняются параллельно. Медленный запрос на верхнем уровне задерживает старт приложения, поэтому туда кладут только то, без чего модуль бесполезен. Такой модуль нельзя загрузить через `require` в Node.js — `ERR_REQUIRE_ASYNC_MODULE`.
::

::question
Что даёт type="module" в HTML?

#answer
Отложенное выполнение как у `defer`, strict mode, свою область видимости вместо `window`, однократную загрузку по URL и требование CORS для модулей с других доменов.

#more
Модули загружаются графом: браузер скачивает зависимости до выполнения, поэтому глубокие цепочки импортов без бандлера дают водопад запросов — помогает `<link rel="modulepreload">`. Голые имена пакетов разрешаются через import maps. `nomodule` позволяет отдать запасной скрипт старым браузерам.
::

## Практика

::practice{title="Что выведет?"}
```js
// counter.mjs
export let count = 0;
export function inc() { count++; }

// counter.cjs
let count = 0;
module.exports = { count, inc() { count++; } };

// main.mjs
import { count, inc } from './counter.mjs';
import { createRequire } from 'node:module';
const require = createRequire(import.meta.url);
const legacy = require('./counter.cjs');

inc(); inc();
legacy.inc(); legacy.inc();

console.log(count, legacy.count);
try { count = 5; } catch (e) { console.log(e.constructor.name); }
```

#solution
```text
2 0
TypeError
```

- ESM-импорт `count` — живая привязка: после двух `inc()` он равен 2.
- В CommonJS в `module.exports.count` записано значение в момент экспорта — `0`. Функция `inc` меняет локальную переменную модуля, а не свойство объекта.
- Присваивание импортированной привязке запрещено.

Чтобы CommonJS-модуль отдавал актуальное значение, экспортируют геттер: `module.exports = { get count() { return count; }, inc }`.
::

::practice{title="Почему падает при загрузке?"}
После рефакторинга приложение падает при старте с `ReferenceError: Cannot access 'DEFAULT_CURRENCY' before initialization`:

```js
// price.js
import { cartTotal } from './cart.js';
export const DEFAULT_CURRENCY = '₽';
export function format(v) { return `${v} ${DEFAULT_CURRENCY}`; }

// cart.js
import { format, DEFAULT_CURRENCY } from './price.js';
export const emptyLabel = `0 ${DEFAULT_CURRENCY}`;
export function cartTotal(items) { return format(items.reduce((s, i) => s + i.price, 0)); }

// main.js
import './price.js';
```

#solution
Цикл: `price.js` импортирует `cart.js`, а `cart.js` — `price.js`. `main.js` начинает с `price.js`, тот сначала выполняет свою зависимость `cart.js`. В этот момент `price.js` ещё не дошёл до `export const DEFAULT_CURRENCY`, и константа во временной мёртвой зоне. `cart.js` на верхнем уровне читает её в `emptyLabel` — `ReferenceError`. Функцию `format` при этом можно было бы вызвать: объявления функций поднимаются.

Лекарство — разорвать цикл, вынеся общее в отдельный модуль:

```js
// currency.js
export const DEFAULT_CURRENCY = '₽';
export function format(v) { return `${v} ${DEFAULT_CURRENCY}`; }

// cart.js
import { format, DEFAULT_CURRENCY } from './currency.js';
export const emptyLabel = `0 ${DEFAULT_CURRENCY}`;
export function cartTotal(items) { return format(items.reduce((s, i) => s + i.price, 0)); }

// price.js
import { cartTotal } from './cart.js';
export { format, DEFAULT_CURRENCY } from './currency.js';
```

Теперь граф без циклов: `currency.js` ни от кого не зависит. Найти циклы помогают `madge --circular` и правила линтера `import/no-cycle`.
::

::practice{title="Почему бандл такой большой?"}
В бандл попала вся библиотека утилит на 70 КБ, хотя используется одна функция. Ещё в бандле оказался модуль аналитики, который нигде не используется:

```js
import _ from 'lodash';
import './analytics';     // импорт «на будущее»

export const onSearch = _.debounce(search, 300);
```

#solution
Две причины:

1. **`lodash` — CommonJS, и импорт всего объекта.** Бандлер не может определить, какие свойства `module.exports` нужны, и включает всё. Нужна ESM-версия и именованный импорт: `import { debounce } from 'lodash-es'` — в бандл попадёт только `debounce` и его зависимости.
2. **Импорт ради побочных эффектов.** `import './analytics'` означает «выполни этот модуль», и бандлер обязан его оставить — вдруг модуль что-то регистрирует при загрузке. Если импорт не нужен, его удаляют. Если это библиотека без побочных эффектов, её `package.json` должен содержать `"sideEffects": false` — тогда неиспользуемый модуль выбрасывается целиком.

```js
import { debounce } from 'lodash-es';

export const onSearch = debounce(search, 300);
```

В проверке на esbuild неиспользуемая функция из ESM-модуля исчезла из бандла, из CommonJS — нет, а модуль с `"sideEffects": false` выбросился целиком. Проверять размер помогают анализаторы бандла: `rollup-plugin-visualizer`, `source-map-explorer`.
::
