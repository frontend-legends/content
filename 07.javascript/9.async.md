# Асинхронность

Как писать асинхронный код: колбэки, промисы, `async`/`await`, комбинаторы, гонки запросов и отмена. Механика очередей, в которых всё это выполняется, — в [Event Loop](/content/javascript/event-loop). На mid спрашивают разницу `Promise.all` и `allSettled`, параллельные запросы и почему `forEach` не ждёт `await`. На senior — что происходит с остальными запросами после отказа `Promise.all`, почему `return` без `await` в `try` пропускает ошибку, как ограничить параллельность и как избежать гонки ответов.

::tldr
- **Промис — объект будущего результата с тремя состояниями.** Исполнитель выполняется синхронно, состояние меняется один раз, а `then` всегда возвращает новый промис, поэтому ошибка идёт по цепочке до ближайшего `catch`.
- **`async`-функция всегда возвращает промис, а `await` приостанавливает только её**, не поток. Независимые операции запускают вместе и ждут через `Promise.all`, а не последовательными `await`.
- **Комбинаторы не отменяют операции.** `Promise.all` отклоняется на первой ошибке, `race` — на первом результате, но остальные запросы продолжают выполняться. Отменяет только `AbortController`.
- **`return promise` внутри `try` не ловит ошибку этого промиса — нужен `return await`.** А `forEach` не ждёт асинхронный колбэк вообще.
- **Гонка ответов — самый частый асинхронный баг интерфейса:** поздний ответ на старый запрос затирает новый. Лечится проверкой «последний ли это запрос» или отменой предыдущего.
::

## Зачем асинхронность

Сквозной пример — страница товара: загрузить товар, отзывы и рекомендации, при вводе в поиск показать подсказки, при оплате ждать ответа не дольше 10 секунд.

JavaScript выполняет код в одном потоке, а запрос к серверу длится сотни миллисекунд. Если ждать его синхронно, вкладка замрёт: ни кликов, ни прокрутки, ни отрисовки. Поэтому ожидание отдают окружению (браузеру или Node.js), а код получает результат позже — асинхронно (подробно — в [Event Loop](/content/javascript/event-loop)).

Вопрос в том, как этот «позже» выразить в коде. Исторически было три способа, и каждый решал проблемы предыдущего.

### Колбэки

Первый способ — передать функцию, которую вызовут, когда результат готов:

```js
loadProduct(id, (err, product) => {
  if (err) return showError(err);
  loadReviews(product.id, (err, reviews) => {
    if (err) return showError(err);
    loadRecommendations(product.category, (err, recs) => {
      if (err) return showError(err);
      render(product, reviews, recs);
    });
  });
});
```

В Node.js принято соглашение error-first: первый аргумент колбэка — ошибка или `null`. У колбэков три проблемы:

- **вложенность** («callback hell»): каждый следующий шаг сдвигается вправо;
- **ручная обработка ошибок** на каждом уровне — забыл проверку, и ошибка потерялась;
- **инверсия управления**: ты отдаёшь функцию чужому коду и надеешься, что он вызовет её ровно один раз, не синхронно и не дважды.

Промисы решили все три.

## Промисы

Промис — объект, который представляет будущий результат операции. У него три состояния: **ожидание** (pending), **выполнен** (fulfilled) со значением и **отклонён** (rejected) с причиной. Из ожидания промис переходит в одно из конечных состояний **один раз** и навсегда.

```js
const product = new Promise((resolve, reject) => {
  // исполнитель выполняется сразу, синхронно
  xhrGet(`/api/products/${id}`, resolve, reject);
});
```

Что важно знать о создании:

- **исполнитель вызывается синхронно** внутри `new Promise` — до строки после него;
- **повторные `resolve` и `reject` игнорируются**: первое решение окончательное;
- **исключение в исполнителе** превращается в отклонение промиса;
- `resolve(другойПромис)` не выполняет промис сразу, а «подписывает» его на результат другого промиса.

### Цепочки

`then` возвращает **новый** промис. Что вернул колбэк, тем новый промис и выполнится: значением, результатом другого промиса или отклонением, если колбэк бросил ошибку.

```js
loadProduct(id)
  .then((product) => loadReviews(product.id))   // вернули промис — цепочка его дождётся
  .then((reviews) => render(reviews))
  .catch((error) => showError(error))           // одна точка для ошибок всей цепочки
  .finally(() => hideSpinner());
```

Ошибка на любом шаге пропускает все следующие `then` и попадает в ближайший `catch`. `catch` — это `then(undefined, onRejected)`, и он возвращает **выполненный** промис: после него цепочка продолжается как успешная. `finally` не получает значение и не меняет результат — значение или ошибка проходят дальше. Исключение — ошибка внутри самого `finally`: она заменяет результат.

`await` и цепочки понимают не только промисы, но и любые **thenable** — объекты с методом `then`. Так промисы разных библиотек работают друг с другом.

Цепочки убрали вложенность, но код всё ещё не похож на обычный. Это исправил `async`/`await`.

## async и await

```js
async function showProduct(id) {
  try {
    const product = await loadProduct(id);
    const reviews = await loadReviews(product.id);
    render(product, reviews);
  } catch (error) {
    showError(error);
  }
}
```

`async`-функция **всегда возвращает промис**: значение из `return` становится результатом, а `throw` — отклонением, а не исключением в месте вызова. `await` приостанавливает **только эту функцию** до выполнения промиса и возвращает его значение или бросает его ошибку. Поток в это время свободен, а продолжение после `await` станет микрозадачей (подробно — в [Event Loop](/content/javascript/event-loop)).

В модулях `await` можно писать на верхнем уровне. Модуль с таким `await` задерживает выполнение всех модулей, которые его импортируют (подробно — в [Модулях](/content/javascript/modules)).

### return await

Внутри `try` есть разница между `return promise` и `return await promise`:

```js
async function pay() {
  try {
    return api.pay(order);         // промис возвращён как есть
  } catch (error) {
    return fallback(error);        // НЕ сработает при отказе api.pay
  }
}
```

`return promise` выходит из `try` сразу: промис ещё не отклонён, ловить нечего. Ошибка придёт позже и пролетит мимо `catch`. `return await api.pay(order)` дождётся результата внутри `try`, и `catch` поймает ошибку. Вне `try` разницы в поведении нет.

### Последовательно или параллельно

Самая частая ошибка с `await` — последовательные ожидания независимых операций:

```js
// ❌ водопад: каждый запрос ждёт предыдущий
const product = await loadProduct(id);
const reviews = await loadReviews(id);
const recs = await loadRecommendations(id);

// ✅ все три стартуют сразу
const [product, reviews, recs] = await Promise.all([
  loadProduct(id),
  loadReviews(id),
  loadRecommendations(id),
]);
```

В проверке три ожидания по 30 мс заняли 90 мс последовательно и 30 мс через `Promise.all`. Запрос стартует в момент **вызова** функции, а не в момент `await`, поэтому параллельность — это вызвать сразу, а ждать потом. Последовательно ждут только то, что действительно зависит от предыдущего результата.

### forEach не ждёт

```js
items.forEach(async (item) => {
  await save(item);
});
console.log('всё сохранено');   // выведется до сохранения
```

`forEach` вызывает колбэк и не смотрит на возвращённый промис: все сохранения стартуют разом, а код после `forEach` выполняется сразу. Для последовательной обработки — `for...of` с `await`, для параллельной — `await Promise.all(items.map(save))`. Тот же подвох у `filter` и `reduce` с асинхронными колбэками.

Параллельный запуск — это `Promise.all`. Но комбинаторов четыре, и разница между ними — частый вопрос.

## Комбинаторы

| Комбинатор | Выполняется | Отклоняется | Когда нужен |
| --- | --- | --- | --- |
| `Promise.all` | когда выполнились все — массив значений в порядке входа | на первой ошибке | все результаты нужны, без одного нет смысла |
| `Promise.allSettled` | когда завершились все — массив `{ status, value \| reason }` | никогда | независимые операции, каждую обработать отдельно |
| `Promise.race` | первым завершившимся — успехом или ошибкой | первой ошибкой, если она раньше | тайм-аут, «кто быстрее» |
| `Promise.any` | первым успехом | когда отклонились все — `AggregateError` | несколько источников, нужен любой рабочий |

Главное, что упускают: **комбинаторы ничего не отменяют.** `Promise.all` отклоняется на первой ошибке, но остальные операции продолжают выполняться — запросы уходят, побочные эффекты происходят. В проверке после отказа `Promise.all` вторая операция всё равно отработала через 30 мс. То же у `race`: «проигравший» запрос не прерывается. Если нужно остановить остальные, им передают общий `AbortSignal`.

Ещё один полезный инструмент — `Promise.withResolvers()`: он возвращает промис вместе с его `resolve` и `reject`. Это удобно, когда промис нужно завершить извне — из обработчика события или колбэка:

```js
const { promise, resolve } = Promise.withResolvers();
dialog.addEventListener('close', () => resolve(dialog.returnValue), { once: true });
const answer = await promise;
```

### Ограничение параллельности

`Promise.all` на тысячу файлов запустит тысячу загрузок разом: браузер упрётся в лимит соединений, сервер — в лимит запросов. Нужен пул — не больше N операций одновременно:

```js
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;

  async function worker() {
    while (next < items.length) {
      const i = next++;
      results[i] = await fn(items[i], i);
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

Запускается `limit` «рабочих», каждый берёт следующий элемент, пока они не кончатся. Индекс захватывается синхронно, до `await`, поэтому два рабочих не возьмут один элемент. В проверке одновременно выполнялось не больше двух операций, а результаты сохранили исходный порядок.

## Гонки и отмена

### Гонка ответов

Однопоточность не спасает от гонок. Поиск с подсказками: пользователь ввёл «ч», потом «ча». Ушли два запроса. Ответ на «ч» медленнее и приходит **последним** — и затирает подсказки для «ча». В проверке именно так и вышло: на экране остались результаты для «ч».

Два решения:

```js
// 1. Игнорировать устаревшие ответы
let latest = 0;
async function onInput(query) {
  const id = ++latest;
  const results = await search(query);
  if (id === latest) render(results);
}

// 2. Отменять предыдущий запрос
let controller;
async function onInput(query) {
  controller?.abort();
  controller = new AbortController();
  try {
    render(await search(query, { signal: controller.signal }));
  } catch (error) {
    if (error.name !== 'AbortError') throw error;
  }
}
```

Первое решение не экономит сеть, но работает с любым API. Второе обрывает лишний запрос — и браузер действительно закрывает его, если запрос ещё не завершился. В React та же задача решается флагом `ignore` в cleanup эффекта или библиотекой запросов (подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization)).

### AbortController

`AbortController` — стандартный механизм отмены: у контроллера есть `signal`, его передают в операцию, а `controller.abort()` её прерывает. Его понимают `fetch`, `addEventListener` (снимает слушатель), потоки и многие библиотеки.

```js
await fetch(url, { signal: controller.signal });           // AbortError при abort()
await fetch(url, { signal: AbortSignal.timeout(10_000) }); // TimeoutError через 10 секунд
await fetch(url, {
  signal: AbortSignal.any([controller.signal, AbortSignal.timeout(10_000)]),
});                                                         // что наступит раньше
```

В проверке с локальным медленным сервером все три варианта прервали настоящий `fetch`: ручная отмена дала `AbortError`, тайм-аут — `TimeoutError`. Тайм-аут через `Promise.race` с `setTimeout` хуже: он отклоняет промис, но запрос продолжает идти.

Свою асинхронную функцию делают отменяемой так же: принимают `signal`, проверяют `signal.aborted` между шагами и подписываются на событие `abort`, чтобы освободить ресурсы.

Что происходит с ошибками, которые никто не поймал, — `unhandledrejection` и падение процесса Node.js — разобрано в [Обработке ошибок](/content/javascript/error-handling).

## Красные флаги в ответе

- **«`await` блокирует поток».** Он приостанавливает только свою `async`-функцию, поток свободен.
- **«`Promise.all` отменяет остальные запросы при ошибке».** Он только перестаёт их ждать. Отменяет `AbortController`.
- **«`forEach` с `async` обработает элементы по очереди».** `forEach` не ждёт промисы: всё запустится разом, а код после него выполнится сразу.
- **«Запрос начинается, когда пишешь `await`».** Он начинается при вызове функции. Параллельность — вызвать сразу, дождаться потом.
- **«Однопоточный JS не знает гонок».** Гонки ответов — самый частый асинхронный баг интерфейса.
- **«Тайм-аут делаю через `Promise.race` с `setTimeout`».** Промис отклонится, но запрос продолжит идти. Нужен `AbortSignal.timeout`.

## Как спрашивают на собеседовании

::question{level="mid"}
Чем Promise.all отличается от Promise.allSettled?

#mid
`Promise.all` отклоняется на первой ошибке, и остальные результаты теряются. `Promise.allSettled` ждёт все промисы и возвращает для каждого `{ status, value }` или `{ status, reason }`. `allSettled` — для независимых операций, каждую из которых нужно обработать.

#senior
Оба ничего не отменяют: после отказа `Promise.all` остальные операции продолжают выполняться и делать побочные эффекты. Чтобы остановить их, всем передают общий `AbortSignal` и вызывают `abort()` в `catch`. Есть ещё `race` (первый завершившийся) и `any` (первый успешный, `AggregateError`, если все отклонились).
::

::question{level="mid"}
Что делает await внутри async-функции?

#mid
Приостанавливает выполнение этой функции, пока промис не выполнится, и возвращает его значение или бросает его ошибку. Поток при этом не блокируется, а код после `await` выполнится как микрозадача.

#senior
`async`-функция выполняется синхронно до первого `await`, а затем возвращает промис. `await` работает с любым thenable и даже на готовом значении отдаёт управление. Внутри `try` важна разница: `return promise` выходит из `try` до отклонения, поэтому `catch` не сработает, а `return await promise` ошибку поймает.
::

::question{level="mid"}
Как сделать параллельные запросы с async/await?

#mid
Вызвать все функции сразу и дождаться через `Promise.all`: `const [a, b] = await Promise.all([loadA(), loadB()])`. Последовательные `await` для независимых запросов — водопад.

#senior
Запрос стартует при вызове функции, поэтому можно и так: `const pa = loadA(); const pb = loadB(); const a = await pa; const b = await pb;`. Но тогда отклонение `pb`, пока ждём `pa`, на время окажется необработанным — `Promise.all` надёжнее. Для большого числа задач нужен пул с ограничением параллельности, иначе упрёмся в лимиты соединений и сервера.
::

::question{level="mid"}
Почему нельзя использовать forEach с async/await?

#mid
`forEach` не ждёт промис, который возвращает асинхронный колбэк. Все итерации запустятся одновременно, а код после `forEach` выполнится сразу. Для последовательной обработки — `for...of`, для параллельной — `Promise.all(arr.map(...))`.

#senior
Ошибки из таких колбэков ещё и становятся необработанными отклонениями: `forEach` их не возвращает. Те же проблемы у `filter`, `some`, `reduce` с асинхронными колбэками: `filter(async ...)` всегда оставит все элементы, потому что промис — truthy. Для асинхронных итерируемых источников есть `for await...of`.
::

::question{level="mid"}
Что такое callback hell и как его избежать?

#mid
Глубокая вложенность колбэков, где каждый асинхронный шаг уходит вправо. Решают промисами (цепочки вместо вложенности) и `async`/`await` (код выглядит синхронным).

#senior
Главная проблема колбэков не вложенность, а инверсия управления и ошибки. Колбэк отдают чужому коду, который может вызвать его дважды, синхронно или не вызвать вовсе, а ошибки нужно проверять вручную на каждом уровне. Промисы гарантируют одно решение, всегда асинхронный вызов колбэков и проброс ошибок по цепочке. Колбэк-API превращают в промисы через `util.promisify` или обёртку `new Promise`.
::

::question{level="senior"}
Как избежать гонки ответов в поиске?

#mid
Отменять предыдущий запрос через `AbortController` при каждом новом вводе или игнорировать ответы, которые пришли не на последний запрос.

#senior
Проверка «последний ли это запрос» (счётчик или сравнение с текущим запросом) работает с любым API, но не экономит сеть. `AbortController` обрывает запрос, и браузер закрывает его, если он ещё не завершён. На практике их сочетают с debounce, чтобы не отправлять запрос на каждую букву, и с кешем ответов. В React это флаг `ignore` в cleanup эффекта или библиотека запросов с ключами.
::

::question{level="mid"}
Как отменить fetch-запрос?

#mid
Создать `AbortController`, передать `controller.signal` в `fetch` и вызвать `controller.abort()`. Запрос отклонится с `AbortError`, его нужно отличать от настоящих ошибок в `catch`.

#senior
Для тайм-аута есть `AbortSignal.timeout(ms)` — он даёт `TimeoutError`, а для объединения причин — `AbortSignal.any([...])`. Тайм-аут через `Promise.race` хуже: промис отклонится, а запрос продолжит идти. Один сигнал можно передать нескольким операциям и слушателям событий, чтобы отменить всё разом.
::

## Практика

::practice{title="Что выведет?"}
```js
const p = new Promise((resolve) => {
  console.log('1');
  resolve('A');
  resolve('B');
});
console.log('2');

p.then((v) => {
  console.log('3', v);
  throw new Error('oops');
})
  .then(() => console.log('4'))
  .catch((e) => {
    console.log('5', e.message);
    return 'recovered';
  })
  .finally(() => console.log('6'))
  .then((v) => console.log('7', v));
```

#solution
```text
1
2
3 A
5 oops
6
7 recovered
```

- Исполнитель выполняется синхронно — `1` раньше `2`.
- Второй `resolve` игнорируется: промис уже выполнен со значением `A`.
- Ошибка в первом `then` пропускает второй `then` и попадает в `catch`.
- `catch` вернул значение — дальше цепочка успешная. `finally` не меняет результат, и `'recovered'` доходит до последнего `then`.
::

::practice{title="Ускорь загрузку"}
Страница товара открывается почти секунду, хотя каждый запрос занимает около 300 мс. Плюс после отправки отзывов индикатор пропадает до того, как они сохранились:

```js
async function openProduct(id) {
  const product = await loadProduct(id);
  const reviews = await loadReviews(id);
  const recs = await loadRecommendations(id);
  render(product, reviews, recs);
}

async function saveDrafts(drafts) {
  drafts.forEach(async (d) => {
    await saveReview(d);
  });
  hideSpinner();
}
```

#solution
**`openProduct`** — водопад: все три запроса зависят только от `id`, но каждый ждёт предыдущий. Время — сумма, а не максимум.

**`saveDrafts`** — `forEach` не ждёт промисы: сохранения стартуют, а `hideSpinner` выполняется сразу.

```js
async function openProduct(id) {
  const [product, reviews, recs] = await Promise.all([
    loadProduct(id),
    loadReviews(id),
    loadRecommendations(id),
  ]);
  render(product, reviews, recs);
}

async function saveDrafts(drafts) {
  try {
    await Promise.all(drafts.map((d) => saveReview(d)));
  } finally {
    hideSpinner();
  }
}
```

Теперь страница грузится за время самого долгого запроса, а индикатор пропадает после всех сохранений — и даже если одно из них упало. Если рекомендации не критичны, их грузят через `allSettled` или отдельно, чтобы их ошибка не роняла страницу.
::

::practice{title="Загрузка с ограничением"}
Нужно загрузить 500 фотографий на сервер, но не больше 4 одновременно. Результаты должны идти в том же порядке, что и файлы. Напиши `mapLimit(items, limit, fn)`.

#solution
```js
async function mapLimit(items, limit, fn) {
  const results = new Array(items.length);
  let next = 0;

  async function worker() {
    while (next < items.length) {
      const i = next++;                     // взять индекс до await
      results[i] = await fn(items[i], i);
    }
  }

  const workers = Array.from({ length: Math.min(limit, items.length) }, worker);
  await Promise.all(workers);
  return results;
}

const urls = await mapLimit(files, 4, (file) => upload(file));
```

Запускается не больше `limit` рабочих. Каждый берёт следующий индекс синхронно — до `await`, — поэтому два рабочих никогда не возьмут один файл. Результат пишется по индексу, и порядок сохраняется независимо от того, какая загрузка закончилась раньше. В проверке пик одновременных операций был ровно 2 при `limit = 2`. Если одна загрузка упадёт, `Promise.all` отклонится, но остальные рабочие продолжат — для отмены им передают общий `AbortSignal`.
::
