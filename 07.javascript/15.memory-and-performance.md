# Память и производительность

Понимание того, как JavaScript управляет памятью, как работает Garbage Collector и что вызывает утечки - это то, что отличает junior от middle/senior. На собеседованиях эти вопросы показывают, способен ли ты писать production-код, который не деградирует со временем.

---

## Как JS управляет памятью

JavaScript управляет памятью **автоматически**. Разработчик не выделяет и не освобождает байты вручную (как в C/C++). Но автоматическое управление не значит «можно не думать» - утечки происходят, когда ты случайно удерживаешь ссылки на объекты, которые уже не нужны.

Три этапа жизни данных в памяти:

1. <b class="text-on-semi-light">Allocation</b> - <span class="text-gray">создание переменной, объекта, массива, функции - движок выделяет память</span>
2. <b class="text-on-semi-light">Use</b> - <span class="text-gray">чтение, запись, передача в функции - работа с выделенной памятью</span>
3. <b class="text-on-semi-light">Release</b> - <span class="text-gray">когда данные больше не нужны - Garbage Collector освобождает память</span>

```js
// 1. Allocation
let user = { name: 'Alice', scores: [90, 85, 92] };

// 2. Use
console.log(user.name);
user.scores.push(88);

// 3. Release - когда?
user = null; // убираем ссылку -> GC может освободить память
```

## Garbage Collector в V8

V8 (Chrome, Node.js) использует **generational Garbage Collector** - основанный на наблюдении, что большинство объектов живут недолго.

### Mark-and-Sweep

Базовый алгоритм GC:

1. **Mark** - начиная с root (глобальный объект, стек вызовов), обходим все достижимые объекты по цепочке ссылок и помечаем их как «живые»
2. **Sweep** - все непомеченные объекты удаляем, освобождая память

<b class="text-on-semi-light">Достижимость (reachability)</b> - <span class="text-gray">ключевое понятие. Объект «жив», если до него можно добраться из root по цепочке ссылок. Root -> globalThis, текущий стек вызовов, активные closures.</span>

### Generational GC в V8

V8 разделяет heap на два поколения:

| Поколение             | Размер     | Алгоритм       | Описание                                    |
| --------------------- | ---------- | --------------- | ------------------------------------------- |
| **Young Generation**  | ~1-8 MB    | Scavenger       | Новые объекты. Большинство умирает быстро   |
| **Old Generation**    | До ~1.5 GB | Mark-Compact    | Объекты, пережившие 2+ сборки Young Gen     |

<b class="text-on-semi-light">Young Generation (Scavenger):</b>

- Делится на two semi-spaces: active и inactive
- Новые объекты создаются в active space
- При заполнении - живые объекты копируются в inactive, пространства меняются местами
- Объекты, пережившие 2 цикла, «продвигаются» (promoted) в Old Generation

<b class="text-on-semi-light">Old Generation (Mark-Compact):</b>

- Mark-Sweep помечает живые объекты
- Compact сдвигает живые объекты, устраняя фрагментацию
- Работает реже, но дольше

### Incremental и concurrent marking

Полная сборка Old Generation может занять десятки миллисекунд - это заметный lag. V8 решает это:

- <b class="text-on-semi-light">Incremental marking</b> - <span class="text-gray">разбивает фазу Mark на маленькие шаги, чередуя с выполнением JS. Вместо одного 50ms стопа - много пауз по 1-2ms</span>
- <b class="text-on-semi-light">Concurrent marking</b> - <span class="text-gray">фаза Mark выполняется в отдельном потоке параллельно с JS. Main thread не блокируется</span>
- <b class="text-on-semi-light">Lazy sweeping</b> - <span class="text-gray">освобождение памяти происходит по мере необходимости, а не сразу после mark</span>

## Типичные утечки памяти

Утечка памяти - ситуация, когда объект больше не нужен приложению, но GC не может его собрать, потому что на него **остаётся достижимая ссылка**.

### Глобальные переменные

```js
// Случайное создание глобальной переменной
function processData() {
  result = computeHeavyStuff(); // без let/const -> window.result
  // result никогда не будет собран GC
}

// Решение: 'use strict' или let/const
function processData() {
  'use strict';
  result = computeHeavyStuff(); // ReferenceError
}
```

### Забытые таймеры

```js
// Утечка: setInterval без clearInterval
function startPolling() {
  setInterval(() => {
    const data = fetchData();
    updateUI(data); // что если компонент уже unmounted?
  }, 5000);
}

// Решение: сохраняем id и очищаем
function startPolling() {
  const intervalId = setInterval(() => {
    const data = fetchData();
    updateUI(data);
  }, 5000);

  // При уничтожении компонента:
  return () => clearInterval(intervalId);
}
```

### Event listeners без removeEventListener

```js
// Утечка: listener добавляется при каждом вызове, но не удаляется
class Tooltip {
  show(element) {
    document.addEventListener('click', (e) => {
      if (!element.contains(e.target)) this.hide();
    });
  }
  // Каждый вызов show() добавляет новый listener!
}

// Решение: именованная функция + removeEventListener
class Tooltip {
  #handleClick = null;

  show(element) {
    this.#handleClick = (e) => {
      if (!element.contains(e.target)) this.hide();
    };
    document.addEventListener('click', this.#handleClick);
  }

  hide() {
    document.removeEventListener('click', this.#handleClick);
  }
}
```

### Closures, удерживающие большие объекты

```js
// Утечка: closure удерживает весь scope, включая largeData
function createHandler() {
  const largeData = new ArrayBuffer(100 * 1024 * 1024); // 100MB
  const id = getId(largeData);

  return function handler() {
    // Использует только id, но closure удерживает и largeData
    console.log(id);
  };
}

// Решение: обнулить ненужное
function createHandler() {
  let largeData = new ArrayBuffer(100 * 1024 * 1024);
  const id = getId(largeData);
  largeData = null; // явно освобождаем

  return function handler() {
    console.log(id);
  };
}
```

### Detached DOM nodes

```js
// Утечка: ссылка на DOM-элемент в JS после удаления из DOM
const elements = [];

function addItem() {
  const div = document.createElement('div');
  document.body.appendChild(div);
  elements.push(div); // JS-ссылка
}

function removeAllItems() {
  document.body.innerHTML = '';
  // DOM очищен, но elements[] всё ещё держит ссылки!
  // -> Detached DOM nodes не собираются GC
}

// Решение: очищать массив
function removeAllItems() {
  document.body.innerHTML = '';
  elements.length = 0; // убираем ссылки
}
```

### React-специфичные утечки

```js
// Stale closure в useEffect
useEffect(() => {
  const subscription = api.subscribe(data => {
    setItems(data); // что если компонент unmounted?
  });

  // Без cleanup -> подписка живёт вечно
  // return () => subscription.unsubscribe(); // FIX
}, []);
```

```js
// AbortController для fetch
useEffect(() => {
  const controller = new AbortController();

  fetch('/api/data', { signal: controller.signal })
    .then(res => res.json())
    .then(setData)
    .catch(err => {
      if (err.name !== 'AbortError') console.error(err);
    });

  return () => controller.abort(); // отменяем при unmount
}, []);
```

## Как находить утечки

Chrome DevTools предоставляет мощные инструменты для анализа памяти.

### Memory tab - основные инструменты

| Инструмент              | Что показывает                                    | Когда использовать                     |
| ----------------------- | ------------------------------------------------- | -------------------------------------- |
| **Heap snapshot**       | Снимок всех объектов в памяти                     | Сравнение «до» и «после» действия     |
| **Allocation timeline** | Объекты, созданные за период                      | Поиск утечек при интерактивных сценариях |
| **Allocation sampling** | Статистика выделения памяти по функциям            | Профилирование hot paths               |

### Методика поиска утечки

1. Открой Memory tab -> сделай Heap snapshot (baseline)
2. Выполни действие, которое подозреваешь в утечке (открой/закрой модалку, переключи страницу)
3. Принудительно запусти GC (кнопка с мусорным баком)
4. Сделай второй Heap snapshot
5. Сравни snapshots: выбери «Comparison» в фильтре
6. Ищи объекты с положительным delta в «# New» - это объекты, которые не были собраны

### Retained size vs Shallow size

- <b class="text-on-semi-light">Shallow size</b> - <span class="text-gray">размер самого объекта (его полей) без учёта ссылающихся объектов</span>
- <b class="text-on-semi-light">Retained size</b> - <span class="text-gray">суммарный размер объекта + всех объектов, которые будут собраны GC при его удалении. Retained size показывает реальное потребление памяти</span>

<span class="text-gray">Если retained size объекта намного больше shallow size - он удерживает большой граф зависимых объектов. Это кандидат на утечку.</span>

## Performance API

Браузер предоставляет API для точного измерения производительности.

### performance.now()

Возвращает время в миллисекундах с высокой точностью (до микросекунд):

```js
const start = performance.now();
heavyComputation();
const end = performance.now();
console.log(`Duration: ${end - start}ms`);
```

<span class="text-gray">`performance.now()` точнее `Date.now()` - не зависит от системных часов и имеет точность до 5 микросекунд (ограничено из-за Spectre mitigations).</span>

### performance.mark() и performance.measure()

```js
// Именованные метки для сложных сценариев
performance.mark('fetch-start');
const data = await fetch('/api/data');
performance.mark('fetch-end');

performance.mark('render-start');
renderUI(data);
performance.mark('render-end');

// Измерения между метками
performance.measure('fetch-duration', 'fetch-start', 'fetch-end');
performance.measure('render-duration', 'render-start', 'render-end');

// Получение результатов
const measures = performance.getEntriesByType('measure');
measures.forEach(m => console.log(`${m.name}: ${m.duration}ms`));
```

### PerformanceObserver

Наблюдатель за событиями производительности в реальном времени:

```js
// Отслеживание Long Tasks (блокировка main thread > 50ms)
const observer = new PerformanceObserver((list) => {
  list.getEntries().forEach(entry => {
    console.log(`Long task: ${entry.duration}ms`, entry);
  });
});

observer.observe({ type: 'longtask', buffered: true });
```

```js
// Отслеживание Largest Contentful Paint (LCP)
const lcpObserver = new PerformanceObserver((list) => {
  const entries = list.getEntries();
  const lastEntry = entries[entries.length - 1];
  console.log('LCP:', lastEntry.startTime);
});

lcpObserver.observe({ type: 'largest-contentful-paint', buffered: true });
```

## Оптимизация

### Debounce и throttle

Ограничение частоты вызова функции - одна из самых частых задач на собеседованиях:

```js
// Debounce: вызывает функцию после паузы в вызовах
// Пример: поиск - запрос отправляется когда пользователь перестал печатать
function debounce(fn, delay) {
  let timerId;
  return function (...args) {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn.apply(this, args), delay);
  };
}

const search = debounce((query) => {
  fetch(`/api/search?q=${query}`);
}, 300);

input.addEventListener('input', (e) => search(e.target.value));
```

```js
// Throttle: вызывает функцию не чаще чем раз в N ms
// Пример: scroll handler - не чаще 1 раз в 100ms
function throttle(fn, limit) {
  let lastCall = 0;
  return function (...args) {
    const now = Date.now();
    if (now - lastCall >= limit) {
      lastCall = now;
      fn.apply(this, args);
    }
  };
}

window.addEventListener('scroll', throttle(() => {
  updateScrollPosition();
}, 100));
```

| Паттерн      | Когда вызывается                    | Use case                     |
| ------------ | ----------------------------------- | ---------------------------- |
| **Debounce** | После паузы в вызовах               | Поиск, resize, валидация     |
| **Throttle** | Не чаще чем раз в N ms             | Scroll, mousemove, resize    |

### Virtual scrolling

Для списков с тысячами элементов - рендерим только видимые:

```js
// Концепция virtual scrolling
// Вместо 10,000 DOM-элементов рендерим ~20 видимых

function getVisibleRange(scrollTop, itemHeight, containerHeight) {
  const startIndex = Math.floor(scrollTop / itemHeight);
  const endIndex = Math.ceil((scrollTop + containerHeight) / itemHeight);
  return { startIndex, endIndex };
}

// Библиотеки: react-virtuoso, @tanstack/virtual, vue-virtual-scroller
```

<span class="text-gray">Virtual scrolling критичен для таблиц и списков с 1000+ элементов. Без него - DOM раздувается, memory растёт, scroll lag. Большинство UI-библиотек предоставляют готовые виртуализированные списки.</span>

### Web Workers

Тяжёлые вычисления блокируют main thread -> UI замирает. Web Workers выполняют код в отдельном потоке:

```js
// main.js
const worker = new Worker('worker.js');

worker.postMessage({ data: largeDataSet, operation: 'sort' });

worker.onmessage = (e) => {
  console.log('Sorted data:', e.data);
  renderUI(e.data);
};
```

```js
// worker.js
self.onmessage = (e) => {
  const { data, operation } = e.data;

  if (operation === 'sort') {
    const sorted = data.sort((a, b) => a.value - b.value);
    self.postMessage(sorted);
  }
};
```

⚠️ Workers не имеют доступа к DOM, window, document. Общение - только через `postMessage` (данные копируются через structured clone) или `SharedArrayBuffer`.

### requestAnimationFrame

Для визуальных обновлений - синхронизация с refresh rate экрана (~60fps = 16.6ms между кадрами):

```js
// Плохо: обновление в setInterval
setInterval(() => {
  element.style.left = `${pos++}px`; // может вызываться чаще/реже refresh rate
}, 16);

// Хорошо: requestAnimationFrame
function animate() {
  element.style.left = `${pos++}px`;
  if (pos < 300) {
    requestAnimationFrame(animate); // синхронизировано с экраном
  }
}
requestAnimationFrame(animate);
```

```js
// Батчинг DOM-обновлений
let needsUpdate = false;
let pendingData = null;

function scheduleUpdate(data) {
  pendingData = data;
  if (!needsUpdate) {
    needsUpdate = true;
    requestAnimationFrame(() => {
      renderUI(pendingData);
      needsUpdate = false;
    });
  }
}

// Даже если scheduleUpdate вызовется 100 раз -
// рендер произойдёт один раз в следующем кадре
```

Про инструменты отладки производительности -> [DevTools](/content/web/devtools). Про устройство памяти на более низком уровне -> [Память](/content/computer-science/memory).</span>

## Частые вопросы на собесе

**Как JavaScript управляет памятью?**
Автоматически через Garbage Collector. Разработчик создаёт объекты, GC определяет, какие из них «недостижимы» (нет цепочки ссылок от root), и освобождает их. Основной алгоритм - Mark-and-Sweep.

**Назови типичные утечки памяти**
Глобальные переменные, забытые setInterval/setTimeout, event listeners без removeEventListener, closures удерживающие большие объекты, detached DOM nodes, неочищенные подписки в React useEffect. Все они - случаи, когда ссылка на ненужный объект остаётся достижимой из root.

**Как найти утечку памяти?**
Chrome DevTools -> Memory tab. Сделай Heap snapshot до и после подозрительного действия, запусти GC, сравни snapshots в режиме Comparison. Ищи объекты с положительным delta. Retained size показывает реальный объём удерживаемой памяти.

**В чём разница между debounce и throttle?**
Debounce вызывает функцию после паузы в вызовах (пользователь перестал печатать -> отправляем запрос). Throttle вызывает функцию не чаще чем раз в N ms (scroll handler не чаще 100ms). Debounce для «финального» события, throttle для «регулярной» выборки.

**Зачем requestAnimationFrame вместо setTimeout?**
rAF синхронизирован с refresh rate экрана (обычно 60fps). setTimeout может вызваться чаще или реже, вызывая jank (рывки). rAF автоматически приостанавливается в фоновых вкладках, экономя ресурсы. Браузер может батчить DOM-обновления в один кадр.

**Что такое Web Worker?**
Отдельный поток для JavaScript, не блокирующий main thread. Нет доступа к DOM. Общение через postMessage (данные копируются). Используется для тяжёлых вычислений: парсинг данных, сортировка, криптография, обработка изображений.
