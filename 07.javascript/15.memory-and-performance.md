# Память и производительность

Как JavaScript управляет памятью, откуда берутся утечки и как их находить, а также как измерять производительность кода, а не гадать. На mid спрашивают, как работает сборщик мусора, и типичные утечки. На senior — почему циклические ссылки не мешают сборке, как устроены поколения в V8, когда нужны `WeakRef` и `FinalizationRegistry` и как найти утечку по снимкам кучи.

::tldr
- **Память освобождает сборщик мусора, и критерий — достижимость.** Объект жив, пока до него есть цепочка ссылок от корней: глобальный объект, стек, активные замыкания, обработчики. Циклы недостижимых объектов собираются.
- **Утечка — это ненужный объект, который остался достижимым.** Классика: слушатель на `window`, незакрытый интервал, отсоединённый DOM-узел в кеше, неограниченный кеш, замыкание, которое держит больше нужного.
- **V8 собирает мусор по поколениям:** молодые объекты — частой быстрой сборкой (Scavenge), пережившие её — редкой полной (Mark-Compact), большая часть работы идёт параллельно с JavaScript.
- **Слабые ссылки не держат объект:** `WeakMap` для данных, привязанных к объекту, `WeakRef` для кешей, `FinalizationRegistry` для уведомления о сборке. Момент сборки не гарантирован, и логику на нём не строят.
- **Производительность измеряют:** `performance.mark` и `measure`, вкладка Performance, наблюдение долгих задач. Утечки ищут сравнением снимков кучи до и после повторяемого действия.
::

## Как живёт объект

Сквозной пример — дашборд в SPA: пользователь открывает отчёт, уходит на другую страницу, возвращается. После десятка переходов вкладка занимает гигабайт.

JavaScript управляет памятью автоматически. Память выделяется при создании объекта, массива, замыкания, строки. Освобождает её **сборщик мусора** (garbage collector, GC), когда объект больше не нужен. Как он понимает, что «больше не нужен»?

### Достижимость

Критерий — **достижимость**. Есть набор корней (roots):

- глобальный объект;
- переменные в текущем стеке вызовов;
- активные замыкания, таймеры, обработчики событий, незавершённые промисы;
- в браузере — DOM-дерево документа.

Объект **жив**, если до него можно дойти от корня по цепочке ссылок. Всё остальное — мусор. Поэтому циклические ссылки не проблема: два объекта, которые ссылаются друг на друга, но недостижимы от корней, будут собраны. В проверке цикл из двух объектов исчез после сборки. Старые сборщики на подсчёте ссылок (в ранних IE для DOM-объектов) на таких циклах текли — отсюда миф, что циклы опасны.

### Mark-and-Sweep

Базовый алгоритм — пометка и очистка:

1. **пометить** — обойти граф от корней и пометить всё достижимое;
2. **очистить** — освободить всё непомеченное;
3. **уплотнить** (compact) — сдвинуть живые объекты, чтобы не было фрагментации.

Разработчик не вызывает сборку и не знает, когда она произойдёт. В Node.js есть флаг `--expose-gc` и `global.gc()`, но только для отладки и тестов.

### Поколения в V8

Большинство объектов умирает молодыми: временные массивы в `map`, объекты в обработчике, строки при форматировании. V8 использует это (generational hypothesis) и делит кучу на поколения:

- **молодое поколение** — небольшая область для новых объектов. Её собирает быстрый **Scavenge**: он копирует выживших в другую половину области, а всё остальное освобождает разом. Сборка частая и дешёвая;
- **старое поколение** — объекты, пережившие две сборки молодого. Его собирает полный **Mark-Compact** — реже и дороже.

В проверке с `--trace-gc` цикл на два миллиона временных объектов дал 35 сборок Scavenge и одну полную. Большая часть работы полной сборки идёт **параллельно** с JavaScript в фоновых потоках и **инкрементально** — маленькими шагами между задачами (система Orinoco), поэтому паузы обычно короткие.

Практический вывод: создавать короткоживущие объекты дёшево. Дорого — когда они переживают сборку и попадают в старое поколение. Например, огромный временный массив, который держится до конца долгой операции.

Сборщик освобождает недостижимое. Утечка — это когда ненужное остаётся достижимым.

## Утечки памяти

Утечка в JavaScript — не «забыли освободить», а «забыли **отпустить**»: на ненужный объект осталась ссылка от чего-то живого. Типичные случаи в нашем дашборде:

**Слушатель на долгоживущем объекте.** Отчёт подписался на `window.resize`, страницу закрыли, а слушатель остался. `window` → слушатель → замыкание → данные отчёта. В проверке данные жили, пока слушатель был подписан, и исчезли сразу после отписки.

**Незакрытый таймер.** `setInterval` держит свой колбэк, а колбэк — всё, что замыкает. Таймер живёт, пока его не остановят через `clearInterval`.

**Отсоединённые DOM-узлы.** Узел удалили со страницы, но ссылка на него осталась в массиве, `Map` или замыкании. Узел жив вместе со всеми детьми и слушателями. В проверке удалённый `<li>` жил, пока лежал в `Map`, и был собран после удаления записи. В DevTools такие узлы помечены как `Detached`.

**Неограниченный кеш.** Мемоизация по ключам из пользовательского ввода растёт бесконечно. Кешу нужен лимит или время жизни.

**Замыкание держит больше нужного.** Функции одного вызова в V8 делят общий контекст, и большой объект, нужный одной функции, живёт, пока жива другая (подробно — в [Замыканиях](/content/javascript/closures)).

**Глобальные переменные и синглтоны.** Всё, что положили в модульную переменную или глобальный стор, живёт до перезагрузки страницы.

Общее лекарство — **у каждой подписки есть отписка**. Удобнее всего — один `AbortController` на время жизни экрана:

```js
function mountReport(root) {
  const controller = new AbortController();
  const { signal } = controller;

  window.addEventListener('resize', onResize, { signal });
  const id = setInterval(refresh, 30_000);
  signal.addEventListener('abort', () => clearInterval(id));
  fetch('/api/report', { signal }).then(render);

  return () => controller.abort();   // при уходе со страницы — снимает всё разом
}
```

В React то же самое — cleanup эффектов (подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization)).

## Слабые ссылки

Иногда нужно связать данные с объектом, но не продлевать ему жизнь. Для этого есть слабые ссылки — они не мешают сборщику.

**`WeakMap` и `WeakSet`** — ключи держатся слабо. Метаданные DOM-узла, кеш вычислений по объекту, приватные данные: когда объект собран, запись исчезает сама. В проверке объект-ключ `WeakMap` был собран, хотя запись существовала. Обойти такую коллекцию нельзя — её содержимое зависит от сборщика (подробно — в [Объектах и массивах](/content/javascript/objects-and-arrays)).

**`WeakRef`** — слабая ссылка на один объект. `ref.deref()` возвращает объект, если он ещё жив, или `undefined`. Применение — кеш тяжёлых объектов, которые можно пересоздать:

```js
const previews = new Map();

function getPreview(id) {
  const cached = previews.get(id)?.deref();
  if (cached) return cached;
  const fresh = renderPreview(id);
  previews.set(id, new WeakRef(fresh));
  return fresh;
}
```

**`FinalizationRegistry`** вызывает колбэк после того, как зарегистрированный объект собран. Так можно убрать из `Map` записи с мёртвыми `WeakRef` или освободить внешний ресурс. В проверке колбэк сработал после принудительной сборки.

Главное правило: **момент сборки не гарантирован**. Объект может жить дольше, чем кажется, колбэк финализации может не вызваться вовсе (например, при закрытии вкладки). Логику, от которой зависит корректность, на слабых ссылках не строят — только оптимизации и уборку.

Утечки видно не по коду, а по поведению. Значит, их нужно уметь находить.

## Как найти утечку

Признак утечки — память растёт после **повторяемого** действия и не возвращается после сборки мусора. Методика в Chrome DevTools, вкладка Memory:

1. открыть страницу и один раз выполнить действие (прогрев кешей);
2. сделать **снимок кучи** (Heap snapshot);
3. повторить действие несколько раз: открыть отчёт и уйти со страницы;
4. сделать второй снимок и выбрать режим **Comparison**;
5. искать объекты, число которых выросло пропорционально числу повторов, — например, 10 новых `ReportView` после 10 переходов.

У каждого объекта две величины:

- **Shallow size** — память самого объекта;
- **Retained size** — сколько памяти освободится, если объект собрать, вместе со всем, что держится только через него. Утечку ищут по нему.

Для найденного объекта панель **Retainers** показывает цепочку ссылок до корня — кто держит объект. Обычно в конце цепочки слушатель, таймер, кеш или замыкание (`context` функции). Фильтр `Detached` показывает отсоединённые DOM-узлы.

Для слежения за памятью в работающем приложении есть `performance.measureUserAgentSpecificMemory()` (только в изолированных от других источников страницах) и `process.memoryUsage()` в Node.js. Устаревший `performance.memory` есть только в Chrome и неточен.

## Измерение производительности

Оптимизация без измерения — гадание. Сначала измеряют, где тратится время.

### Performance API

```js
performance.mark('filter:start');
const visible = products.filter(matches);
performance.mark('filter:end');
performance.measure('filter', 'filter:start', 'filter:end');

new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) report(entry.name, entry.duration);
}).observe({ type: 'measure' });
```

- `performance.now()` — монотонное время с дробными миллисекундами от начала страницы. В отличие от `Date.now()`, не прыгает при смене системных часов. Точность браузеры намеренно огрубляют для защиты от атак по времени;
- `mark` и `measure` — именованные отметки и интервалы. Они видны на вкладке Performance в DevTools, рядом с остальными событиями;
- `PerformanceObserver` подписывается на записи: измерения, загрузку ресурсов, отрисовку, долгие задачи.

### Долгие задачи

Задача длиннее 50 мс называется **долгой** (long task): пока она выполняется, страница не отвечает на ввод и не рисует (подробно — в [Event Loop](/content/javascript/event-loop)). Их можно наблюдать прямо в коде:

```js
new PerformanceObserver((list) => {
  for (const task of list.getEntries()) report('long task', task.duration);
}).observe({ type: 'longtask', buffered: true });
```

В проверке в Chromium задача на 120 мс попала в отчёт, а задача на 20 мс — нет. Долгие задачи напрямую ухудшают INP. Лечат их разбиением работы на части с уступкой потока, выносом вычислений в Web Worker (подробно — в [Воркерах и параллельности](/content/additional-topics/web-workers-and-concurrency)) и уменьшением работы: виртуализацией длинных списков, мемоизацией.

### Что оптимизировать в самом JavaScript

Узкое место обычно не в языке, а в количестве работы: лишние рендеры, раскладка страницы, тяжёлые библиотеки. Но есть и правила на уровне движка: объекты одной формы, без удаления свойств и смены типов, позволяют V8 оптимизировать доступ и вызовы (подробно — во [Введении](/content/javascript/introduction)). Микрооптимизации вроде «цикл `for` быстрее `forEach`» проверяют профилировщиком на реальных данных — результат часто противоположен ожиданиям.

## Красные флаги в ответе

- **«Циклические ссылки вызывают утечки».** Сборщик работает по достижимости: недостижимый цикл собирается.
- **«Удалил узел из DOM — память освободилась».** Если на узел есть ссылка из JavaScript, он жив вместе с детьми и слушателями.
- **«Вызову сборку мусора, когда нужно».** В браузере это невозможно, а `global.gc()` в Node.js — только для отладки.
- **«`WeakRef` гарантирует, что объект соберут».** Момент сборки не определён. Слабые ссылки — для оптимизаций, не для логики.
- **«Утечку ищу по росту памяти в диспетчере задач».** Нужны снимки кучи до и после повторяемого действия и цепочка Retainers.
- **«Оптимизирую код заранее».** Сначала измерение: `performance.measure`, вкладка Performance, долгие задачи.

## Как спрашивают на собеседовании

::question{level="mid"}
Как JavaScript управляет памятью?

#mid
Автоматически, через сборщик мусора. Объект живёт, пока он достижим от корней — глобального объекта, стека, активных замыканий и обработчиков. Недостижимые объекты сборщик освобождает. Базовый алгоритм — пометка и очистка (mark-and-sweep).

#senior
V8 использует поколения: молодые объекты собирает частый и быстрый Scavenge, выжившие переходят в старое поколение и собираются полным Mark-Compact. Большая часть работы идёт параллельно и инкрементально, поэтому паузы короткие. Короткоживущие объекты дешёвые, дорого — когда временные данные переживают сборку. Циклы недостижимых объектов собираются.
::

::question{level="mid"}
Назови типичные утечки памяти.

#mid
Слушатели на `window` или `document`, которые не сняли. Незакрытые `setInterval`. Отсоединённые DOM-узлы, на которые осталась ссылка. Неограниченные кеши. Глобальные переменные. Подписки в эффектах без cleanup.

#senior
Во всех случаях ненужный объект остался достижимым через что-то живое. Менее очевидная утечка — общий контекст замыканий в V8: большой объект живёт, пока жива любая функция того же вызова. Общее лекарство — отписка у каждой подписки, удобно через один `AbortController` на время жизни экрана, плюс лимиты для кешей.
::

::question{level="senior"}
Как найти утечку памяти?

#mid
В DevTools на вкладке Memory сделать снимок кучи до и после повторяемого действия и сравнить их. Искать объекты, количество которых растёт.

#senior
Сначала прогрев, потом несколько повторов действия, потом сравнение снимков в режиме Comparison: утечка видна как рост числа объектов пропорционально числу повторов. Смотреть Retained size и цепочку Retainers — она показывает, кто держит объект: слушатель, таймер, кеш, контекст замыкания. Отдельно — фильтр `Detached` для отсоединённых DOM-узлов. Для мониторинга в проде — `measureUserAgentSpecificMemory`.
::

::question{level="mid"}
В чём разница между Map и WeakMap с точки зрения памяти?

#mid
`Map` держит ключи сильно: пока запись есть, объект-ключ не будет собран. `WeakMap` держит ключи слабо: если объект больше нигде не нужен, он собирается, а запись исчезает.

#senior
Поэтому `WeakMap` подходит для данных, привязанных к чужим объектам, — метаданных DOM-узлов, кешей по объекту. Обойти его и узнать размер нельзя: содержимое зависит от сборщика. Ключами могут быть объекты и незарегистрированные символы, но не строки — для кешей по строке нужен `Map` с лимитом или `WeakRef` в значениях.
::

::question{level="senior"}
Когда использовать WeakRef и FinalizationRegistry?

#mid
`WeakRef` — когда нужна ссылка на объект, которая не мешает его сборке, например в кеше тяжёлых объектов. `FinalizationRegistry` — чтобы узнать, что объект собран, и убрать связанные записи.

#senior
Момент сборки не гарантирован: объект может жить дольше, колбэк финализации может не вызваться вовсе. Поэтому на них строят только оптимизации и уборку, но не логику. Типичная пара: `Map` с `WeakRef` в значениях плюс `FinalizationRegistry`, который удаляет записи с мёртвыми ссылками. `deref()` в одной синхронной задаче стабилен — объект не исчезнет посреди неё.
::

::question{level="mid"}
Как измерить производительность кода?

#mid
`performance.now()` для замеров, `performance.mark` и `measure` для именованных интервалов, вкладка Performance в DevTools для профиля. Сначала измерить, потом оптимизировать.

#senior
`PerformanceObserver` подписывается на измерения, долгие задачи, загрузку ресурсов и отрисовку — так метрики собирают в мониторинг. Задачи длиннее 50 мс видны через `longtask` и ухудшают INP. Замеры делают на реальных данных и в production-сборке: dev-режим фреймворков в разы медленнее. Микробенчмарки обманчивы из-за оптимизаций JIT.
::

## Практика

::practice{title="Найди утечки"}
После каждого открытия отчёта память растёт на десятки мегабайт и не возвращается:

```js
const rowsById = new Map();

function mountReport(root, report) {
  window.addEventListener('resize', () => layout(root, report));
  setInterval(() => refresh(report), 30_000);

  for (const row of report.rows) {
    const el = document.createElement('tr');
    rowsById.set(row.id, el);
    root.append(el);
  }

  return () => root.replaceChildren();   // «размонтирование»
}
```

#solution
Три утечки, и «размонтирование» убирает только DOM:

1. **Слушатель `resize`** на `window` не снят и держит `root` и весь `report`.
2. **`setInterval`** не остановлен и держит `report`.
3. **`rowsById`** — модульный `Map` с DOM-строками. После `replaceChildren` строки отсоединены от документа, но живы через `Map`.

```js
function mountReport(root, report) {
  const controller = new AbortController();
  const { signal } = controller;
  const rowsById = new Map();                    // время жизни — как у отчёта

  window.addEventListener('resize', () => layout(root, report), { signal });
  const id = setInterval(() => refresh(report), 30_000);
  signal.addEventListener('abort', () => clearInterval(id));

  for (const row of report.rows) {
    const el = document.createElement('tr');
    rowsById.set(row.id, el);
    root.append(el);
  }

  return () => {
    controller.abort();
    root.replaceChildren();
  };
}
```

Один `abort()` снимает слушатель и останавливает интервал, а `Map` теперь живёт столько же, сколько отчёт. В проверке на настоящем сборщике данные отчёта были собраны сразу после `abort()`. Убедиться в DevTools: снимки кучи до и после пяти открытий отчёта — число `HTMLTableRowElement` в режиме Comparison не должно расти.
::

::practice{title="Кеш с лимитом"}
Мемоизация форматирования цен растёт бесконечно: ключи — произвольные суммы. Напиши LRU-кеш на `Map` с методами `get` и `set`, который хранит не больше `limit` записей и вытесняет ту, к которой дольше всего не обращались.

#solution
`Map` хранит ключи в порядке вставки. Если при каждом обращении удалять и вставлять запись заново, самая давняя окажется первой:

```js
class LRU {
  #map = new Map();

  constructor(limit) {
    this.limit = limit;
  }

  get(key) {
    if (!this.#map.has(key)) return undefined;
    const value = this.#map.get(key);
    this.#map.delete(key);
    this.#map.set(key, value);              // переместить в конец — «свежая»
    return value;
  }

  set(key, value) {
    this.#map.delete(key);
    this.#map.set(key, value);
    if (this.#map.size > this.limit) {
      this.#map.delete(this.#map.keys().next().value);   // самая давняя — первая
    }
  }
}

const lru = new LRU(2);
lru.set('a', 1);
lru.set('b', 2);
lru.get('a');
lru.set('c', 3);    // вытеснен b
```

Все операции — за константное время, без отдельного списка. В проверке после обращения к `a` и вставки `c` в кеше остались `a` и `c`. Для кешей, привязанных к объектам, вместо лимита подходит `WeakMap`.
::
