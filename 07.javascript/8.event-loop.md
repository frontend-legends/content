# Event Loop

Event Loop - это **сердце** JavaScript-рантайма. Именно он позволяет однопоточному языку выполнять асинхронные операции, не блокируя интерфейс. На собеседованиях вопрос «расскажи как работает Event Loop» - один из самых частых, и здесь ожидают не поверхностное описание, а чёткое понимание порядка выполнения: синхронный код, microtasks, macrotasks, рендеринг. Разберём всё подробно.

---

## Однопоточность JavaScript

JavaScript - **однопоточный** язык. Это значит:

- Один **call stack** - одна инструкция выполняется в каждый момент времени
- Один **поток выполнения** - нет параллельного выполнения кода (без Workers)
- Если функция занимает 5 секунд - весь UI заблокирован на 5 секунд

```js
// Пока этот цикл выполняется - страница "мёртвая"
// Кнопки не кликаются, скролл не работает, анимации стоят
while (true) {
  // бесконечный цикл заблокировал единственный поток
}
```

<b class="text-on-semi-light">Зачем тогда однопоточность?</b> <span class="text-gray">Простота. Нет проблем с race conditions, мьютексами, deadlocks. Один поток - один контекст выполнения - предсказуемый порядок. А асинхронность решается через Event Loop, не через многопоточность.</span>

## Call Stack

Call Stack (стек вызовов) - это структура данных **LIFO** (Last In, First Out), которая отслеживает, какую функцию сейчас выполняет движок.

```js
function multiply(a, b) {
  return a * b;
}

function square(n) {
  return multiply(n, n);
}

function printSquare(n) {
  const result = square(n);
  console.log(result);
}

printSquare(4);
```

Состояние стека по шагам:

```text
Шаг 1: [printSquare(4)]
Шаг 2: [printSquare(4), square(4)]
Шаг 3: [printSquare(4), square(4), multiply(4, 4)]
Шаг 4: [printSquare(4), square(4)]          // multiply вернул 16
Шаг 5: [printSquare(4)]                     // square вернул 16
Шаг 6: [printSquare(4), console.log(16)]
Шаг 7: [printSquare(4)]                     // console.log завершился
Шаг 8: []                                   // printSquare завершился
```

Каждый вызов функции добавляет **frame** (кадр) в стек. Когда функция возвращает значение - её frame удаляется с вершины стека.

### Stack Overflow

Когда стек переполняется (слишком глубокая рекурсия) - получаем `RangeError: Maximum call stack size exceeded`.

```js
function recursive() {
  recursive(); // нет условия выхода
}

recursive(); // RangeError: Maximum call stack size exceeded
```

<span class="text-gray">Лимит стека зависит от движка: в V8 (Chrome/Node) обычно ~10 000-15 000 кадров. Это не точное число - зависит от размера каждого frame.</span>

## Web APIs и Node APIs

JavaScript-движок (V8, SpiderMonkey) сам по себе не знает про таймеры, HTTP-запросы или DOM-события. Эти возможности предоставляет **среда выполнения** (runtime environment):

- **Браузер** - Web APIs: `setTimeout`, `fetch`, `addEventListener`, `requestAnimationFrame`, Geolocation, DOM APIs
- **Node.js** - Node APIs: `fs.readFile`, `http.request`, `setTimeout` (своя реализация), `setImmediate`

Когда ты вызываешь `setTimeout(callback, 1000)`, происходит следующее:

1. Движок JS передаёт операцию Web API (браузерному коду на C++)
2. Call stack **свободен** - можно выполнять следующий код
3. Через 1000ms Web API помещает callback в **Task Queue**
4. Event Loop подбирает callback из очереди, когда call stack пуст

```js
console.log("start"); // 1. Выполняется сразу (call stack)

setTimeout(() => {
  console.log("timeout"); // 4. Выполняется после того, как стек опустеет
}, 0);

console.log("end"); // 2. Выполняется сразу (call stack)

// Порядок: "start", "end", "timeout"
```

<b class="text-on-semi-light">Ключевая идея:</b> `setTimeout(fn, 0)` не означает «выполнить немедленно». Это означает «выполнить, как только call stack будет пуст и Event Loop доберётся до Task Queue».

## Очереди задач

В Event Loop есть **две принципиально разные** очереди:

### Macrotask Queue (Task Queue)

Каждая итерация Event Loop берёт **одну** задачу из этой очереди.

Источники macrotasks:
- `setTimeout` / `setInterval`
- `setImmediate` (только Node.js)
- I/O callbacks (чтение файлов, сеть)
- UI rendering events
- `MessageChannel`
- `requestAnimationFrame` (технически отдельная очередь, но часто группируют)

### Microtask Queue

После выполнения каждой macrotask (и после синхронного кода) Event Loop выполняет **ВСЕ** microtasks из очереди до единой. Если microtask добавляет новую microtask - она тоже выполняется в этом же цикле.

Источники microtasks:
- `Promise.then()` / `.catch()` / `.finally()`
- `queueMicrotask()`
- `MutationObserver`
- `process.nextTick()` (Node.js - ещё более приоритетный, чем обычные microtasks)

### Ключевое различие

| Характеристика          | Macrotask                         | Microtask                             |
| ----------------------- | --------------------------------- | ------------------------------------- |
| Сколько за итерацию     | **Одна** задача                   | **Все** из очереди                    |
| Приоритет               | Ниже                              | Выше                                  |
| Когда выполняется       | После всех microtasks             | Сразу после текущей задачи            |
| Примеры                 | setTimeout, setInterval, I/O      | Promise.then, queueMicrotask          |
| Может блокировать paint | Нет (между macrotasks - рендеринг) | Да (все microtasks до рендеринга)    |

## Алгоритм Event Loop

Вот точный порядок работы Event Loop в браузере:

```text
1. Выполнить весь синхронный код (пока call stack не опустеет)
          |
          v
2. Выполнить ВСЕ microtasks из очереди
   (если microtask порождает новую microtask - выполнить и её тоже)
          |
          v
3. Если нужен рендеринг (прошло ~16ms для 60fps):
   a. Выполнить requestAnimationFrame callbacks
   b. Выполнить Layout
   c. Выполнить Paint
          |
          v
4. Взять ОДНУ macrotask из очереди и выполнить
          |
          v
5. Выполнить ВСЕ microtasks
          |
          v
6. Повторить с шага 3
```

<b class="text-on-semi-light">Критически важно запомнить:</b> Microtasks **всегда** выполняются перед следующей macrotask. И microtask queue полностью опустошается перед любым рендерингом или следующей macrotask.

⚠️ Это значит, что бесконечная генерация microtasks заблокирует рендеринг и macrotasks навсегда:

```js
// Это заблокирует страницу НАВСЕГДА
function loop() {
  Promise.resolve().then(loop);
}
loop();
// Microtask queue никогда не опустеет - рендеринг и macrotasks заблокированы
```

## Порядок выполнения - примеры

### Пример 1 - базовый

```js
console.log("1"); // синхронный

setTimeout(() => {
  console.log("2"); // macrotask
}, 0);

Promise.resolve().then(() => {
  console.log("3"); // microtask
});

console.log("4"); // синхронный
```

Порядок: `1`, `4`, `3`, `2`

Разбор:
1. `console.log("1")` - синхронный, сразу в call stack
2. `setTimeout` - callback отправлен в Web API, потом в macrotask queue
3. `Promise.resolve().then()` - callback в microtask queue
4. `console.log("4")` - синхронный, сразу в call stack
5. Call stack пуст -> выполняем все microtasks -> `"3"`
6. Все microtasks выполнены -> берём macrotask -> `"2"`

### Пример 2 - вложенные microtasks

```js
console.log("1");

setTimeout(() => console.log("2"), 0);

Promise.resolve()
  .then(() => {
    console.log("3");
    Promise.resolve().then(() => console.log("4"));
  })
  .then(() => console.log("5"));

console.log("6");
```

Порядок: `1`, `6`, `3`, `4`, `5`, `2`

Разбор:
1. `"1"` - синхронный
2. setTimeout callback -> macrotask queue
3. First `.then` callback -> microtask queue
4. `"6"` - синхронный
5. Call stack пуст. Выполняем microtasks:
   - Первый `.then`: выводит `"3"`, добавляет nested `.then` в microtask queue (`"4"`), возвращается - второй `.then` (`"5"`) тоже добавляется в microtask queue
   - Вложенный: выводит `"4"`
   - Второй `.then`: выводит `"5"`
6. Microtask queue пуста -> macrotask -> `"2"`

### Пример 3 - async/await

```js
async function foo() {
  console.log("foo start");
  await bar();
  console.log("foo end"); // это microtask! (код после await)
}

async function bar() {
  console.log("bar");
}

console.log("script start");
setTimeout(() => console.log("setTimeout"), 0);
foo();
console.log("script end");
```

Порядок: `script start`, `foo start`, `bar`, `script end`, `foo end`, `setTimeout`

Разбор:
1. `"script start"` - синхронный
2. setTimeout -> macrotask queue
3. `foo()` вызывается: `"foo start"` - синхронный
4. `await bar()`: вызов `bar()` - синхронный: `"bar"`. Затем `await` приостанавливает `foo` - код после `await` (`"foo end"`) попадает в microtask queue
5. `"script end"` - синхронный
6. Call stack пуст -> microtasks -> `"foo end"`
7. Macrotask -> `"setTimeout"`

<b class="text-on-semi-light">Важно:</b> `await` разбивает async-функцию на две части. Код **до** `await` (включая вызов awaited функции) - синхронный. Код **после** `await` - microtask (аналог `.then`).

### Пример 4 - комплексный

```js
console.log("1");

setTimeout(() => {
  console.log("2");
  Promise.resolve().then(() => console.log("3"));
}, 0);

setTimeout(() => {
  console.log("4");
}, 0);

Promise.resolve()
  .then(() => console.log("5"))
  .then(() => console.log("6"));

console.log("7");
```

Порядок: `1`, `7`, `5`, `6`, `2`, `3`, `4`

Разбор:
1. `"1"` - синхронный
2. Первый setTimeout -> macrotask queue (позиция 1)
3. Второй setTimeout -> macrotask queue (позиция 2)
4. `.then("5")` -> microtask queue
5. `"7"` - синхронный
6. Microtasks: `"5"`, потом `"6"` (цепочка)
7. Первая macrotask: `"2"`, порождает microtask `"3"`
8. Microtask: `"3"` (опустошаем очередь перед следующей macrotask)
9. Вторая macrotask: `"4"`

## requestAnimationFrame

`requestAnimationFrame(callback)` - специальный API, привязанный к циклу рендеринга браузера.

```js
function animate() {
  element.style.transform = `translateX(${x}px)`;
  x += 2;
  if (x < 300) {
    requestAnimationFrame(animate);
  }
}
requestAnimationFrame(animate);
```

### Место в Event Loop

```text
microtasks -> requestAnimationFrame -> Layout -> Paint -> следующая macrotask
```

- rAF callbacks выполняются **перед** paint, **после** microtasks
- Привязаны к частоте обновления экрана (обычно 60fps = ~16.6ms)
- Если вкладка неактивна - rAF **не вызывается** (экономия ресурсов)

<b class="text-on-semi-light">rAF vs setTimeout для анимаций:</b>

| Характеристика       | requestAnimationFrame          | setTimeout(fn, 16)          |
| -------------------- | ------------------------------ | --------------------------- |
| Синхронизация с экраном | Да                            | Нет                         |
| Точность тайминга    | Привязан к vsync               | Минимум ~4ms задержка       |
| Неактивная вкладка   | Пауза                          | Продолжает работать         |
| Батчинг              | Все rAF callbacks за один кадр | Каждый setTimeout отдельно  |

Всегда используй `requestAnimationFrame` для визуальных анимаций. `setTimeout` для анимаций - антипаттерн.

## requestIdleCallback

`requestIdleCallback(callback)` - вызывает callback, когда браузер **свободен** (idle period). Предназначен для низкоприоритетной работы.

```js
requestIdleCallback((deadline) => {
  // deadline.timeRemaining() - сколько мс осталось до следующего кадра
  while (deadline.timeRemaining() > 0 && tasks.length > 0) {
    doLowPriorityWork(tasks.pop());
  }
}, { timeout: 2000 }); // максимальное ожидание - 2 секунды
```

<span class="text-gray">`requestIdleCallback` не гарантирует вызов. Если страница постоянно занята - callback может не вызваться. Параметр `timeout` устанавливает крайний срок.</span>

<b class="text-on-semi-light">Типичные use cases:</b> аналитика, предзагрузка данных, логирование, non-critical DOM-обновления. Не используй для критичной логики.

## setTimeout(fn, 0) - почему не мгновенно?

Даже `setTimeout(fn, 0)` выполняется **не мгновенно** по нескольким причинам:

1. **Event Loop**: callback попадает в macrotask queue и ждёт, пока call stack опустеет и все microtasks выполнятся
2. **Минимальная задержка**: спецификация HTML требует минимум **4ms** для вложенных таймеров (глубина > 4). Браузеры реализуют clamping
3. **Неактивная вкладка**: браузер может увеличить интервал до **1000ms** для экономии ресурсов

```js
const start = performance.now();

setTimeout(() => {
  console.log(performance.now() - start); // обычно ~1-4ms, не 0
}, 0);

// Если есть тяжёлый синхронный код:
for (let i = 0; i < 1e9; i++) {} // блокирует ~1 секунду

setTimeout(() => {
  console.log(performance.now() - start); // ~1000ms, не 0
}, 0);
```

<b class="text-on-semi-light">Clamping в деталях:</b> <span class="text-gray">По спецификации HTML, если `setTimeout`/`setInterval` вложен более 4 уровней - минимальная задержка 4ms. На практике Chrome использует 1ms для top-level таймеров, 4ms для вложенных. Это защита от «busy-loop через setTimeout(fn, 0)».</span>

## Node.js Event Loop

В Node.js Event Loop устроен иначе - он основан на **libuv** и имеет **фазы** (phases):

```text
   ┌───────────────────────────┐
┌─>│         timers             │  <- setTimeout, setInterval callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │     pending callbacks      │  <- I/O callbacks (отложенные)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │       idle, prepare        │  <- внутренние (не используются напрямую)
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │           poll             │  <- I/O (fs, network), incoming connections
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │          check             │  <- setImmediate callbacks
│  └─────────────┬─────────────┘
│  ┌─────────────┴─────────────┐
│  │      close callbacks       │  <- socket.on('close'), etc.
│  └─────────────┬─────────────┘
│                │
└────────────────┘
```

### Ключевые отличия от браузера

| Аспект                 | Браузер                  | Node.js                          |
| ---------------------- | ------------------------ | -------------------------------- |
| Фазы                   | Нет явных фаз           | 6 фаз (timers, poll, check...)  |
| `setImmediate`         | Нет                      | Есть (check phase)              |
| `process.nextTick`     | Нет                      | Есть (выше приоритета microtasks)|
| Рендеринг              | Есть (paint step)        | Нет (нет UI)                    |
| `requestAnimationFrame`| Есть                     | Нет                              |
| Microtask timing       | После каждой macrotask   | После каждой фазы (Node >= 11)  |

### process.nextTick vs queueMicrotask в Node.js

```js
process.nextTick(() => console.log("nextTick")); // 1 - максимальный приоритет
Promise.resolve().then(() => console.log("promise")); // 2 - обычная microtask
queueMicrotask(() => console.log("queueMicrotask")); // 3 - обычная microtask
setTimeout(() => console.log("setTimeout"), 0); // 4 - macrotask (timers phase)
setImmediate(() => console.log("setImmediate")); // 5 - macrotask (check phase)
```

<span class="text-gray">`process.nextTick` имеет отдельную очередь, которая обрабатывается **перед** microtask queue. Злоупотребление `process.nextTick` может заблокировать I/O - предпочитай `queueMicrotask`.</span>

### setTimeout vs setImmediate в Node.js

```js
// Порядок непредсказуем в top-level коде!
setTimeout(() => console.log("timeout"), 0);
setImmediate(() => console.log("immediate"));
// Может быть timeout->immediate или immediate->timeout

// Но ВНУТРИ I/O callback - setImmediate всегда первый:
const fs = require("fs");
fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate"));
  // Всегда: immediate -> timeout
  // Потому что мы в poll phase, check (setImmediate) - следующая фаза
});
```

## queueMicrotask vs Promise.resolve().then()

Оба создают microtask, но есть нюансы:

```js
queueMicrotask(() => console.log("microtask"));
Promise.resolve().then(() => console.log("promise"));
```

| Аспект          | queueMicrotask               | Promise.resolve().then()      |
| --------------- | ---------------------------- | ----------------------------- |
| Создаёт Promise | Нет                          | Да (лишний объект)            |
| Семантика       | Низкоуровневая microtask     | Promise-based                 |
| Error handling  | Ошибка -> global error event | Ошибка -> unhandled rejection |
| Performance     | Чуть быстрее (нет Promise)   | Чуть медленнее                |

<b class="text-on-semi-light">Когда что:</b> Используй `queueMicrotask` для низкоуровневых задач (batching, cleanup). Используй `Promise.resolve().then()` когда работаешь с Promise chain. На собесе важно знать, что результат **одинаковый** - обе создают microtask.

## Визуализация полного цикла

Объединим всё в один пример:

```js
console.log("1 - sync");

setTimeout(() => {
  console.log("2 - macrotask");
}, 0);

requestAnimationFrame(() => {
  console.log("3 - rAF");
});

Promise.resolve().then(() => {
  console.log("4 - microtask");
});

queueMicrotask(() => {
  console.log("5 - microtask");
});

console.log("6 - sync");
```

Гарантированный порядок: `1`, `6`, `4`, `5`

Далее - `3` (rAF) выполнится перед paint, `2` (macrotask) - после. Но точный порядок между `3` и `2` зависит от тайминга рендеринга. Обычно: `1`, `6`, `4`, `5`, `3`, `2` - но `2` может оказаться перед `3`, если рендеринг не запланирован в этом цикле.

<b class="text-on-semi-light">Гарантии:</b> Sync всегда первый. Microtasks всегда после sync и перед macrotasks. rAF - перед paint. Macrotask - одна за итерацию. Это всё, что нужно помнить.

## Частые вопросы на собесе

**Что такое Event Loop и зачем он нужен?**
Event Loop - механизм, позволяющий однопоточному JS выполнять асинхронные операции. Он постоянно проверяет: call stack пуст -> выполнить все microtasks -> один macrotask -> снова microtasks -> рендеринг -> повторить.

**В чём разница между microtask и macrotask?**
Microtasks (Promise.then, queueMicrotask) выполняются **ВСЕ** после каждой задачи, до рендеринга и до следующей macrotask. Macrotasks (setTimeout, I/O) выполняются по **ОДНОЙ** за итерацию цикла. Microtasks имеют более высокий приоритет.

**Почему setTimeout(fn, 0) не выполняется мгновенно?**
Callback попадает в macrotask queue и ждёт: 1) пока call stack опустеет, 2) пока все microtasks выполнятся, 3) минимальная задержка ~1-4ms (clamping по спецификации). Если есть тяжёлый синхронный код - задержка ещё больше.

**Что будет, если microtask бесконечно порождает microtasks?**
Страница зависнет навсегда. Microtask queue опустошается полностью перед рендерингом и macrotasks. Бесконечные microtasks заблокируют и рендеринг, и все таймеры, и I/O.

**Где requestAnimationFrame в Event Loop?**
rAF callbacks выполняются после microtasks, перед layout и paint. Они привязаны к циклу рендеринга (~60fps). В неактивной вкладке rAF не вызывается.

**Чем Event Loop в Node.js отличается от браузерного?**
Node.js Event Loop имеет 6 фаз (timers, pending callbacks, poll, check, close). Есть `setImmediate` (check phase) и `process.nextTick` (выше приоритета microtasks). Нет рендеринга и rAF. С Node.js >= 11 microtasks выполняются после каждой фазы (как в браузере после каждой macrotask).

**Расскажи порядок: sync -> setTimeout -> Promise.then -> async/await.**
1) Весь синхронный код. 2) Код после `await` и `.then()` callbacks - microtasks (все). 3) `setTimeout` callback - macrotask (после всех microtasks).
