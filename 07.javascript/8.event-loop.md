# Event Loop

Как однопоточный JavaScript выполняет асинхронный код: стек вызовов, задачи и микрозадачи, место отрисовки в цикле и чем цикл Node.js отличается от браузерного. Спрашивают порядок вывода с `setTimeout`, `Promise.then` и `await`. Глубже — почему `setTimeout(fn, 0)` ждёт 4 мс, где выполняется `requestAnimationFrame`, почему микрозадачи при настоящем клике выполняются между слушателями и что будет, если микрозадачи не кончаются.

::tldr
- **Event loop — цикл окружения, а не языка.** Он берёт задачу из очереди, выполняет её до конца, затем выполняет все микрозадачи, и в браузере при необходимости рисует кадр. В спецификации ECMAScript есть только задания (jobs), а сам цикл описан в HTML и в libuv.
- **Задача (task) выполняется одна за итерацию, микрозадачи — все сразу.** Задачи — таймеры, события, сообщения. Микрозадачи — колбэки промисов, код после `await`, `queueMicrotask`. Микрозадача, порождённая микрозадачей, тоже выполнится до следующей задачи.
- **`setTimeout(fn, 0)` — не «сразу».** Колбэк ждёт конца текущей задачи и всех микрозадач, в браузере вложенные таймеры после пятого уровня ждут минимум 4 мс, в Node.js — минимум 1 мс.
- **Отрисовка идёт между задачами, а `requestAnimationFrame` — перед ней,** не чаще кадра. Долгая задача или бесконечные микрозадачи блокируют и отрисовку, и ввод.
- **У Node.js свой цикл из фаз** (таймеры, ввод-вывод, `setImmediate`), а `process.nextTick` выполняется раньше промисов — если текущий код не сам находится в микрозадаче.
::

## Один поток и стек вызовов

Сквозной пример — кнопка «В корзину»:

```js
button.addEventListener('click', async () => {
  button.disabled = true;                               // 1. обновить DOM
  setTimeout(() => analytics.track('add_to_cart'), 0);  // 2. аналитика «потом»
  Promise.resolve().then(() => updateBadge());          // 3. бейдж «сразу после»
  const res = await fetch('/api/cart', { method: 'POST' }); // 4. запрос
  showToast(await res.json());                          // 5. после ответа
});
```

JavaScript выполняет код в одном потоке: в каждый момент выполняется одна функция. Функции, которые сейчас выполняются, лежат в **стеке вызовов**: вызов кладёт кадр наверх, возврат — снимает (подробно — в [Контексте выполнения](/content/javascript/execution-context)). Пока в стеке есть хоть один кадр, ничего другого не происходит: ни другой JavaScript, ни в браузере — отрисовка.

Но `fetch` ждёт сеть сотни миллисекунд, и поток при этом не стоит. Ожиданием занимается **окружение** — браузер или Node.js: сеть, таймеры, файловая система, события пользователя работают вне JavaScript. Когда ожидание закончено, окружение кладёт колбэк в **очередь**, а **event loop** забирает его оттуда, когда стек пуст.

Event loop — часть окружения, а не языка. В спецификации ECMAScript есть только задания (jobs) — то, что выполняется после текущего кода. Сам цикл описан в спецификации HTML для браузеров и в библиотеке libuv для Node.js (подробно — во [Введении](/content/javascript/introduction)).

Очередей несколько, и у них разный приоритет. Это и определяет порядок в нашем обработчике.

## Задачи и микрозадачи

**Задача** (task, её ещё называют макрозадачей) — отдельная единица работы: колбэк таймера, обработчик события, сообщение `postMessage`, запуск скрипта.

**Микрозадача** (microtask) — работа, которую нужно сделать сразу после текущего кода, до всего остального: колбэки `then`, `catch` и `finally` у промисов, продолжение функции после `await`, `queueMicrotask`, `MutationObserver`.

Цикл работает так:

```text
1. взять одну задачу из очереди и выполнить её до конца
2. выполнить все микрозадачи — включая те, что появились по ходу
3. если пора — отрисовать кадр (браузер)
4. повторить
```

Главное различие: задача выполняется **одна** за итерацию, а очередь микрозадач опустошается **полностью**. Микрозадача, которая ставит новую микрозадачу, не уступает место: новая тоже выполнится до следующей задачи.

```js
console.log('1 sync');
setTimeout(() => console.log('5 timeout'), 0);
Promise.resolve().then(() => console.log('3 microtask')).then(() => console.log('4 microtask 2'));
console.log('2 sync');
```

Сначала весь синхронный код (1, 2), потом все микрозадачи, включая цепочку `then` (3, 4), и только потом задача таймера (5).

### await — это микрозадача

`async`-функция выполняется синхронно до первого `await`. Всё после `await` — продолжение, которое ставится в очередь микрозадач, когда ожидаемый промис выполнится:

```js
async function addToCart() {
  console.log('a: до await');
  await null;
  console.log('c: после await');
}

addToCart();
console.log('b: синхронный код дальше');
// a, b, c
```

Даже `await` на готовом значении отдаёт управление: продолжение не выполнится, пока не закончится текущий синхронный код. Как устроены промисы и `async`/`await` — в [Асинхронности](/content/javascript/async).

### Порядок в обработчике клика

Теперь можно разобрать сквозной пример. При клике:

1. обработчик выполняется синхронно до первого `await`: `button.disabled = true`, `setTimeout` ставит задачу, `then` — микрозадачу, `fetch` начинает запрос;
2. задача клика закончилась — выполняются микрозадачи: `updateBadge()`;
3. браузер может отрисовать кадр: кнопка уже неактивна, бейдж обновлён;
4. следующая задача — таймер аналитики;
5. когда придёт ответ сети, его обработка поставит микрозадачу с продолжением после `await`.

Аналитика «через 0 мс» выполнилась позже бейджа и даже после отрисовки. Почему таймер с нулём вообще ждёт?

## Таймеры

`setTimeout(fn, 0)` не значит «выполнить сейчас». Колбэк попадёт в очередь задач, и до него:

- должна закончиться текущая задача;
- должны выполниться все микрозадачи;
- должны выполниться задачи, которые в очереди раньше.

К этому добавляется минимальная задержка. В браузере вложенные таймеры **после пятого уровня вложенности** ждут минимум 4 мс — так требует спецификация HTML, чтобы рекурсивный `setTimeout(fn, 0)` не загружал процессор на 100%. В проверке в Chromium первые уровни срабатывали быстрее миллисекунды, а с шестого — с промежутком не меньше 4 мс. В Node.js `setTimeout(fn, 0)` превращается в 1 мс. В фоновой вкладке браузеры откладывают таймеры ещё сильнее — до раза в секунду и реже.

Для «выполнить сразу после текущего кода» есть `queueMicrotask`. Для «выполнить в следующей задаче без задержки» — `MessageChannel` или `scheduler.postTask`.

### setInterval

`setInterval` ставит задачу каждые N миллисекунд, но не гарантирует интервал между **выполнениями**. Если колбэк занимает дольше интервала, задачи не копятся бесконечно, а интервал между ними сокращается до нуля. Если колбэк асинхронный (запрос), следующий запуск начнётся, не дождавшись предыдущего. Поэтому опрос сервера пишут цепочкой `setTimeout`: следующий запуск планируется после завершения текущего.

Таймеры, события и колбэки — всё это задачи. Но браузеру нужно ещё и рисовать.

## Отрисовка

Браузер рисует кадр **между задачами**, не чаще частоты экрана (обычно 60 раз в секунду, на быстрых экранах — 120 и больше). Отрисовка — шаг цикла: стили, раскладка (layout), отрисовка (paint) и композиция.

Из этого следует главное правило производительности: **пока выполняется задача, страница заморожена**. Обработчик клика, который считает 200 мс, задерживает и отрисовку, и обработку следующего клика. В проверке клик, поставленный в очередь за долгой задачей, обработался только через 200 мс — столько длилась задача. Такие задачи длиннее 50 мс называют долгими (long tasks), и они ухудшают INP — метрику отзывчивости (подробно — в [Core Web Vitals](/content/web/core-web-vitals)).

### requestAnimationFrame

`requestAnimationFrame(cb)` вызывает колбэк **перед следующей отрисовкой**, один раз на кадр. Это правильное место для анимаций и чтения размеров перед изменениями:

```text
задача → микрозадачи → [rAF-колбэки → стили → layout → paint] → задача → ...
```

В отличие от `setTimeout(fn, 16)`, rAF синхронизирован с частотой экрана, не вызывается дважды за кадр и останавливается в фоновой вкладке. Изменение DOM в rAF попадёт ровно в ближайший кадр.

### Микрозадачи и пользовательские события

Есть тонкость, которую любят на собеседованиях. Если на кнопке два слушателя и каждый ставит микрозадачу, порядок зависит от того, **кто** кликнул:

```js
button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('micro 1'));
  console.log('listener 1');
});
button.addEventListener('click', () => {
  Promise.resolve().then(() => console.log('micro 2'));
  console.log('listener 2');
});
```

| Клик | Порядок |
| --- | --- |
| мышью | `listener 1`, `micro 1`, `listener 2`, `micro 2` |
| `button.click()` из кода | `listener 1`, `listener 2`, `micro 1`, `micro 2` |

При настоящем клике браузер вызывает каждый слушатель как отдельный колбэк, и после каждого стек пуст — микрозадачи выполняются сразу. При `button.click()` в стеке остаётся вызывающий скрипт, поэтому микрозадачи ждут, пока он закончится. Проверено в Chromium. Практический вывод: тест, который кликает через `el.click()`, может видеть другой порядок, чем пользователь.

### Бесконечные микрозадачи

Раз очередь микрозадач опустошается полностью, микрозадача, которая всё время ставит новую, никогда не отпустит цикл: не выполнятся таймеры, не обработается ввод, не нарисуется кадр — вкладка зависнет так же, как от `while (true)`. В проверке таймер с нулевой задержкой ждал 100 мс, пока крутились микрозадачи. Рекурсивный `setTimeout` такого не делает: между задачами браузер успевает рисовать и обрабатывать события.

## Цикл Node.js

В Node.js нет отрисовки, зато есть файлы, сокеты и процессы. Цикл libuv проходит по **фазам**, у каждой своя очередь:

```text
timers → pending callbacks → poll (ввод-вывод) → check (setImmediate) → close callbacks
```

- **timers** — колбэки `setTimeout` и `setInterval`, у которых истекло время;
- **poll** — колбэки ввода-вывода: прочитан файл, пришли данные из сети;
- **check** — колбэки `setImmediate`;
- микрозадачи выполняются после каждого колбэка, как в браузере после каждой задачи.

Отсюда порядок, о котором спрашивают. На верхнем уровне скрипта порядок `setTimeout(fn, 0)` и `setImmediate(fn)` не определён: зависит от того, истекла ли 1 мс к началу фазы таймеров. Но **внутри колбэка ввода-вывода** `setImmediate` всегда раньше: после фазы poll идёт check, а таймеры — только на следующем круге. Проверено в Node.js 24.

### process.nextTick

`process.nextTick(fn)` — отдельная очередь Node.js, которая опустошается раньше промисов. Из обычной задачи порядок такой: сначала все `nextTick`, потом микрозадачи промисов. Но если код сам выполняется **внутри микрозадачи** — например, после `await` или на верхнем уровне ES-модуля, — `nextTick` выполнится только после текущей очереди промисов. Проверено в обоих вариантах. Документация Node.js советует вместо `nextTick` использовать `queueMicrotask`, если нет особой причины.

## Красные флаги в ответе

- **«JavaScript асинхронный, поэтому `fetch` выполняется параллельно».** JavaScript однопоточный. Параллельно ждёт окружение, а колбэки выполняются по очереди в одном потоке.
- **«`setTimeout(fn, 0)` выполняется сразу после текущей функции».** После текущей задачи и всех микрозадач, плюс минимальная задержка: 1 мс в Node.js, 4 мс у вложенных таймеров в браузере.
- **«Микрозадачи выполняются по одной между задачами».** Очередь микрозадач опустошается полностью, включая новые микрозадачи.
- **«`requestAnimationFrame` — это `setTimeout(fn, 16)`».** rAF вызывается перед отрисовкой, синхронизирован с частотой экрана и не работает в фоновой вкладке.
- **«Event loop — часть JavaScript».** Это механизм окружения: HTML-спецификация в браузере, libuv в Node.js.

## Как спрашивают на собеседовании

::question
Что такое event loop и зачем он нужен?

#answer
Механизм, который позволяет однопоточному JavaScript выполнять асинхронный код. Окружение ждёт сеть и таймеры само, а готовые колбэки кладёт в очереди. Event loop берёт задачу, выполняет её, затем все микрозадачи, затем при необходимости отрисовывает кадр — и так по кругу.

#more
Цикл — часть окружения: в браузере он описан в HTML-спецификации, в Node.js — в libuv, а в ECMAScript есть только задания. Из модели «задача выполняется до конца» следует, что любая долгая задача блокирует ввод и отрисовку — отсюда INP и разбиение работы на части. В браузере есть несколько источников задач, и браузер вправе выбирать между ними, например отдавать приоритет вводу.
::

::question
В чём разница между задачей и микрозадачей?

#answer
Микрозадачи — колбэки промисов, код после `await`, `queueMicrotask` — выполняются все сразу после текущей задачи, до отрисовки и следующей задачи. Задачи — таймеры, события, сообщения — выполняются по одной за итерацию.

#more
Микрозадача, поставленная из микрозадачи, тоже выполнится до следующей задачи, поэтому бесконечная цепочка микрозадач вешает вкладку. Микрозадачи выполняются, когда стек пуст, поэтому при настоящем клике они идут между слушателями, а при `el.click()` из скрипта — после всех слушателей.
::

::question
Почему setTimeout(fn, 0) не выполняется мгновенно?

#answer
Колбэк попадает в очередь задач и ждёт, пока закончится текущий код, выполнятся все микрозадачи и задачи, которые в очереди раньше. Плюс есть минимальная задержка.

#more
В браузере вложенные таймеры после пятого уровня ждут минимум 4 мс по спецификации HTML, в фоновых вкладках — намного дольше. В Node.js ноль превращается в 1 мс. Для «сразу после текущего кода» есть `queueMicrotask`, для следующей задачи без задержки — `MessageChannel` или `scheduler.postTask`. `setInterval` не гарантирует промежуток между выполнениями, поэтому опрос пишут цепочкой `setTimeout`.
::

::question
Где requestAnimationFrame в event loop?

#answer
Колбэки rAF выполняются перед отрисовкой кадра, после задачи и микрозадач. Не чаще одного раза за кадр, в фоновой вкладке не вызываются.

#more
Шаг отрисовки — rAF-колбэки, потом стили, layout, paint и композиция — браузер выполняет между задачами, когда пора показать новый кадр. Поэтому изменения DOM в rAF гарантированно попадут в ближайший кадр, а чтение размеров в rAF перед изменениями не вызывает лишних пересчётов. `setTimeout(fn, 16)` не синхронизирован с экраном и может сработать дважды за кадр или пропустить кадр.
::

::question
Что будет, если микрозадача бесконечно порождает микрозадачи?

#answer
Вкладка зависнет: очередь микрозадач опустошается полностью до следующей задачи и отрисовки, поэтому таймеры, события и рендер не получат управление.

#more
Это то же, что бесконечный цикл, только асинхронный на вид. Рекурсивный `setTimeout` такого не делает: между задачами браузер обрабатывает ввод и рисует. В Node.js то же самое происходит с бесконечным `process.nextTick` — он блокирует даже ввод-вывод. Долгие вычисления дробят на задачи (`setTimeout`, `scheduler.yield`) или выносят в воркер.
::

::question
Чем event loop Node.js отличается от браузерного?

#answer
В Node.js цикл из фаз: таймеры, ввод-вывод, `setImmediate`, закрытие. Нет отрисовки и rAF. Есть `process.nextTick`, который выполняется раньше промисов.

#more
Микрозадачи в Node.js выполняются после каждого колбэка, как в браузере после каждой задачи. Внутри колбэка ввода-вывода `setImmediate` всегда раньше `setTimeout(0)`, потому что после фазы poll идёт check; на верхнем уровне порядок не определён. `nextTick` раньше промисов только из обычной задачи: из микрозадачи (после `await`, в ES-модуле) он выполнится после текущей очереди промисов.
::

::question
Расскажи порядок выполнения: синхронный код, setTimeout, Promise.then, async/await.

#answer
Сначала весь синхронный код, включая начало `async`-функций до первого `await`. Потом все микрозадачи: колбэки `then` и продолжения после `await`. Потом задачи — `setTimeout`.

#more
`await` даже на готовом значении отдаёт управление, и продолжение становится микрозадачей. Цепочка `then` выполняется в той же порции микрозадач, если каждый шаг готов. Разные `async`-функции чередуются шагами: продолжения встают в очередь в порядке, в котором выполнились ожидаемые промисы.
::

## Практика

::practice{title="Что выведет?"}
```js
console.log('A');

setTimeout(() => console.log('B'), 0);

Promise.resolve()
  .then(() => {
    console.log('C');
    setTimeout(() => console.log('D'), 0);
  })
  .then(() => console.log('E'));

(async () => {
  console.log('F');
  await null;
  console.log('G');
})();

queueMicrotask(() => console.log('H'));
console.log('I');
```

#solution
```text
A
F
I
C
G
H
E
B
D
```

- Синхронно: `A`, затем `async`-функция до `await` — `F`, затем `I`.
- Очередь микрозадач в порядке постановки: колбэк `then` (`C`), продолжение после `await` (`G`), `queueMicrotask` (`H`). Колбэк `C` ставит следующий `then` (`E`) — он выполнится в той же порции микрозадач.
- Задачи: таймер `B` поставлен раньше, таймер `D` — из микрозадачи, поэтому позже.
::

::practice{title="Почему зависает вкладка?"}
Функция обрабатывает 100 тысяч записей «асинхронно», чтобы не блокировать интерфейс. Но вкладка всё равно не отвечает, пока обработка не закончится:

```js
async function processAll(records) {
  for (const record of records) {
    await Promise.resolve();      // «дать браузеру подышать»
    process(record);
  }
}
```

#solution
`await Promise.resolve()` ставит продолжение в очередь **микрозадач**, а она опустошается полностью до отрисовки и следующей задачи. Цикл ни разу не отдаёт управление event loop: между итерациями браузер не рисует и не обрабатывает клики.

Уступать нужно задачей, а не микрозадачей, и не после каждой записи, а по времени:

```js
const yieldToMain = () =>
  globalThis.scheduler?.yield?.() ?? new Promise((resolve) => setTimeout(resolve, 0));

async function processAll(records) {
  let deadline = performance.now() + 50;
  for (const record of records) {
    process(record);
    if (performance.now() >= deadline) {
      await yieldToMain();                // отдать управление: ввод и отрисовка
      deadline = performance.now() + 50;
    }
  }
}
```

Работа идёт кусками по 50 мс, между ними браузер обрабатывает ввод и рисует кадр. `scheduler.yield` продолжает работу с приоритетом выше обычных задач, а `setTimeout` — запасной вариант. Если работа чисто вычислительная, её лучше вынести в Web Worker.
::

::practice{title="Почему тест видит другой порядок?"}
На кнопке два слушателя. Первый ставит флаг в микрозадаче, второй проверяет флаг. Пользователи жалуются, что флаг не сработал, а тест через `button.click()` проходит:

```js
let ready = false;
button.addEventListener('click', () => {
  Promise.resolve().then(() => { ready = true; });
});
button.addEventListener('click', () => {
  if (!ready) showError();
});
```

#solution
Наоборот: при клике мышью каждый слушатель — отдельный колбэк, после него стек пуст и микрозадачи выполняются сразу. Значит, у пользователя `ready` станет `true` **до** второго слушателя, и ошибки не будет. А при `button.click()` из теста в стеке остаётся вызывающий код, микрозадачи ждут его окончания, и второй слушатель видит `ready === false`.

Поведение зависит от способа клика, поэтому полагаться на порядок микрозадач между слушателями нельзя. Синхронное состояние ставят синхронно:

```js
button.addEventListener('click', () => {
  ready = true;
});
```

А в тестах пользовательские действия воспроизводят через `userEvent` или Playwright, которые генерируют настоящие события, а не `el.click()`.
::
