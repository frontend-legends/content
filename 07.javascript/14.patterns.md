# Паттерны

Приёмы, которыми в JavaScript решают повторяющиеся задачи и которые просят написать на live coding: debounce и throttle, мемоизация, каррирование и композиция, события и подписки, middleware. Спрашивают разницу debounce и throttle и что такое каррирование. Глубже — как мемоизировать асинхронную функцию, почему отписка во время `emit` теряет слушателей, как устроена «луковица» middleware и чем фабрика лучше класса.

::tldr
- **Debounce вызывает функцию после паузы в вызовах, throttle — не чаще раза в интервал.** Debounce — для поиска и автосохранения, throttle — для прокрутки и изменения размера. Оба хранят таймер в замыкании и должны сохранять `this` и аргументы.
- **Мемоизация кеширует результат по аргументам.** Ключ — примитив или `WeakMap` для объектов; асинхронную функцию мемоизируют промисом, а упавший промис из кеша удаляют.
- **Каррирование превращает `f(a, b, c)` в `f(a)(b)(c)`,** частичное применение фиксирует часть аргументов. `compose` и `pipe` собирают функцию из шагов. Каррирование по `fn.length` ломается от параметров по умолчанию.
- **Observer связывает источник и подписчиков напрямую, pub/sub — через посредника-шину.** У каждой подписки должна быть отписка, а `emit` обходит копию списка слушателей.
- **Middleware — цепочка обработчиков с `next()`.** Код до `next` выполняется по порядку, после — в обратном. На этом построены Koa, Redux и клиенты API.
::

## Debounce и throttle

Сквозной пример — страница каталога: поиск с подсказками, бесконечная прокрутка, корзина в шапке и клиент API.

Пользователь печатает «чай» — три события ввода за 300 мс. Отправлять запрос на каждую букву бессмысленно: ответы на «ч» и «ча» никому не нужны, а сервер получит втрое больше запросов. При прокрутке событие `scroll` приходит десятки раз в секунду, а подгружать следующую страницу нужно не чаще раза в 200 мс. Это две разные задачи.

**Debounce** откладывает вызов, пока вызовы не прекратятся на заданное время. Каждый новый вызов сбрасывает таймер:

```js
function debounce(fn, ms) {
  let timer = null;
  function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      fn.apply(this, args);
    }, ms);
  }
  debounced.cancel = () => clearTimeout(timer);
  return debounced;
}

input.addEventListener('input', debounce((e) => search(e.target.value), 300));
```

**Throttle** пропускает вызов не чаще раза в интервал: первый — сразу, промежуточные — отбрасывает, последний — в конце окна, чтобы не потерять финальное состояние:

```js
function throttle(fn, ms) {
  let last = 0;
  let timer = null;
  let pending = null;

  return function throttled(...args) {
    const remaining = ms - (Date.now() - last);
    if (remaining <= 0) {
      clearTimeout(timer);
      timer = null;
      last = Date.now();
      fn.apply(this, args);
    } else {
      pending = { self: this, args };
      timer ??= setTimeout(() => {
        last = Date.now();
        timer = null;
        fn.apply(pending.self, pending.args);
      }, remaining);
    }
  };
}
```

В проверке на настоящих таймерах три ввода с паузой 10 мс дали один вызов поиска с последней строкой «чай», а прокрутка в течение 175 мс при throttle 50 мс — около четырёх вызовов: первый сразу и последний с самыми свежими данными.

| | Debounce | Throttle |
| --- | --- | --- |
| Когда вызывает | после паузы во вызовах | не чаще раза в интервал |
| При непрерывных событиях | ни разу, пока события идут | регулярно |
| Для чего | поиск, автосохранение, проверка формы | прокрутка, `resize`, `mousemove`, бесконечная лента |

Детали, которые проверяют на собеседовании:

- **`this` и аргументы** — обычная функция и `fn.apply(this, args)`, иначе метод объекта потеряет контекст (подробно — в [Контексте выполнения](/content/javascript/execution-context));
- **`cancel`** — при уходе со страницы отложенный вызов нужно отменить, иначе он выполнится для уже удалённого компонента;
- **leading-вариант** debounce вызывает функцию сразу на первом событии и игнорирует остальные до паузы — так защищают кнопку от двойного клика;
- всё состояние — таймер, время, отложенные аргументы — живёт в **замыкании** (подробно — в [Замыканиях](/content/javascript/closures)).

Для анимаций при прокрутке throttle по времени хуже `requestAnimationFrame`, который синхронизирован с кадрами (подробно — в [Event Loop](/content/javascript/event-loop)).

Debounce и throttle уменьшают **число** вызовов. Если же вызовы повторяются с одними и теми же аргументами, их можно не выполнять вовсе.

## Мемоизация

Мемоизация — кеширование результата функции по её аргументам. Подходит только для **чистых** функций: результат зависит только от аргументов (подробно — в [Функциях](/content/javascript/functions)).

```js
function memoize(fn) {
  const cache = new Map();
  return (arg) => {
    if (!cache.has(arg)) cache.set(arg, fn(arg));
    return cache.get(arg);
  };
}

const formatPrice = memoize((v) => priceFormatter.format(v));
```

`has` вместо проверки `cache.get(arg) !== undefined` нужен, чтобы кешировать и `undefined`-результаты.

### Ключ кеша

С одним примитивным аргументом ключ — сам аргумент. С несколькими или с объектами начинаются сложности:

- **`JSON.stringify(args)`** — простой, но ненадёжный ключ: `{ a: 1, b: 2 }` и `{ b: 2, a: 1 }` дают разные строки, `undefined` превращается в `null`, функции и `Map` теряются;
- **объект-аргумент** лучше кешировать в `WeakMap`: запись исчезнет вместе с объектом, и кеш не станет утечкой памяти (подробно — в [Объектах и массивах](/content/javascript/objects-and-arrays));
- **неограниченный рост** — кеш с ключами из пользовательского ввода растёт бесконечно. Ограничивают размер (LRU — вытеснять давно не использованное) или время жизни записей.

### Асинхронная мемоизация

Для асинхронных функций кешируют **промис**, а не результат. Тогда два одновременных вызова с одним ключом получат один и тот же промис и сделают один запрос:

```js
function memoizeAsync(fn) {
  const cache = new Map();
  return (key) => {
    if (!cache.has(key)) {
      cache.set(key, fn(key).catch((error) => {
        cache.delete(key);          // ошибку не кешируем — следующий вызов попробует снова
        throw error;
      }));
    }
    return cache.get(key);
  };
}
```

В проверке два параллельных вызова сделали один запрос, после ошибки следующий вызов отправил новый, а успешный результат дальше брался из кеша. Без удаления упавшего промиса один сбой сети навсегда закешировал бы ошибку. Это ровно то, что делают библиотеки запросов, плюс устаревание данных (подробно — в [Загрузке данных](/content/reactjs/data-fetching)).

Мемоизация и debounce — функции, которые оборачивают другие функции. Обёртки — частный случай работы с функциями как с данными.

## Каррирование и композиция

### Каррирование и частичное применение

**Каррирование** превращает функцию от нескольких аргументов в цепочку функций от одного: `price(base, discount, tax)` → `price(base)(discount)(tax)`. **Частичное применение** фиксирует часть аргументов и возвращает функцию от остальных. `bind` делает частичное применение: `price.bind(null, 1000, 0)` вернёт функцию от `tax`.

```js
function curry(fn) {
  return function curried(...args) {
    return args.length >= fn.length
      ? fn.apply(this, args)
      : (...more) => curried.apply(this, [...args, ...more]);
  };
}

const price = curry((base, discount, tax) => Math.round(base * (1 - discount) * (1 + tax)));
price(1000)(0.1)(0.2);   // 1080
price(1000, 0.1)(0.2);   // 1080
```

Реализация опирается на `fn.length`, а он считает параметры **до первого со значением по умолчанию**. Каррированная `(base, tax = 0.2) => ...` вызовется сразу после первого аргумента — в проверке так и произошло. Это частая ловушка библиотек каррирования.

Зачем это на практике: «запекать» настройки (`withDiscount(10)`), передавать в `map` функции нужной арности, строить конвейеры обработки данных.

### compose и pipe

`pipe` применяет функции слева направо, `compose` — справа налево, как в математике:

```js
const pipe = (...fns) => (x) => fns.reduce((v, f) => f(v), x);
const compose = (...fns) => (x) => fns.reduceRight((v, f) => f(v), x);

const toSlug = pipe(
  (s) => s.trim(),
  (s) => s.toLowerCase(),
  (s) => s.replace(/\s+/g, '-'),
);
toSlug('  Зелёный Чай  ');   // 'зелёный-чай'
```

Вместо `replace(toLowerCase(trim(s)))` шаги читаются в порядке выполнения и легко переставляются. Каррированные функции хорошо ложатся в `pipe`, потому что каждый шаг — функция одного аргумента.

Функции, которые принимают и возвращают функции, решают задачи «внутри» компонента. Следующий класс задач — связь между частями приложения.

## События и подписки

Корзина изменилась — нужно обновить бейдж в шапке, показать подсказку и отправить аналитику. Корзина не должна знать обо всех, кому это интересно.

### Observer и pub/sub

- **Observer** — источник (subject) хранит список подписчиков и сам уведомляет их. Связь прямая: подписчик знает источник. Так работают `addEventListener` и реактивность.
- **Pub/sub** — между издателями и подписчиками стоит посредник (шина событий). Издатель публикует событие в канал и не знает, кто его слушает. Связанность ниже, но потоки данных труднее отследить.

Шина событий с `on`, `off`, `once` и `emit`:

```js
class Emitter {
  #handlers = new Map();

  on(event, fn) {
    const list = this.#handlers.get(event) ?? [];
    this.#handlers.set(event, [...list, fn]);
    return () => this.off(event, fn);          // функция отписки
  }

  off(event, fn) {
    const list = this.#handlers.get(event) ?? [];
    this.#handlers.set(event, list.filter((h) => h !== fn));
  }

  once(event, fn) {
    const off = this.on(event, (...args) => { off(); fn(...args); });
    return off;
  }

  emit(event, ...args) {
    for (const fn of [...(this.#handlers.get(event) ?? [])]) fn(...args);
  }
}
```

Две детали отличают рабочую реализацию от наивной:

- **`emit` обходит копию списка.** Если слушатель отписывается во время `emit` (как `once`), а обход идёт по «живому» массиву, индексы сдвигаются и следующий слушатель **пропускается**. В проверке наивная реализация так и потеряла слушателя после `once`;
- **`on` возвращает функцию отписки.** Каждая подписка — потенциальная утечка памяти, если её не снять (подробно — в [Памяти и производительности](/content/javascript/memory-and-performance)).

Отдельный вопрос — ошибка в одном слушателе. В простой реализации она прерывает `emit`, и остальные слушатели не вызываются. `EventTarget` в браузере вызывает всех и отправляет ошибку в глобальный обработчик. В Node.js у `EventEmitter` есть особое событие `error`: если на него никто не подписан, `emit('error')` бросает исключение.

### Middleware

Middleware — цепочка обработчиков, каждый из которых делает свою часть работы и передаёт управление дальше через `next()`. На этом построены :term[Koa]{def="минималистичный серверный фреймворк Node.js с цепочкой middleware"}, Express, :term[Redux]{def="библиотека состояния: одно хранилище, изменения только через действия и чистые редьюсеры"} и перехватчики клиентов API:

```js
function composeMiddleware(middlewares) {
  return (ctx) => {
    const dispatch = (i) =>
      i < middlewares.length
        ? Promise.resolve(middlewares[i](ctx, () => dispatch(i + 1)))
        : Promise.resolve();
    return dispatch(0);
  };
}

const request = composeMiddleware([
  async (ctx, next) => { ctx.headers.Authorization = `Bearer ${token}`; await next(); },
  async (ctx, next) => { const t = Date.now(); await next(); log(ctx.url, Date.now() - t); },
  async (ctx) => { ctx.response = await fetch(ctx.url, { headers: ctx.headers }); },
]);
```

Это модель «луковицы»: код до `await next()` выполняется по порядку (авторизация, затем логирование), код после — в обратном, когда ответ уже получен. В проверке порядок был именно таким: `auth in`, `log in`, запрос, `log out`, `auth out`. Middleware может не вызывать `next()` — например, отдать ответ из кеша — и тогда следующие слои не выполнятся.

## Объекты: фабрики, синглтон, стратегия

### Фабрика или класс

Фабричная функция создаёт и возвращает объект без `new`:

```js
function createCart() {
  const items = [];                       // приватно в замыкании
  return {
    add: (item) => items.push(item),
    get total() { return items.reduce((sum, i) => sum + i.price, 0); },
  };
}
```

Фабрика не зависит от `this` (методы можно передавать как колбэки), прячет состояние в замыкании и может вернуть объекты разной формы. Класс лучше, когда объектов много (методы живут один раз на прототипе, а у фабрики — в каждом объекте), нужна проверка `instanceof` или наследование (подробно — в [Прототипах и классах](/content/javascript/prototypes-and-classes)).

### Синглтон

Синглтон — единственный экземпляр на всё приложение. В JavaScript его даёт сам **модуль**: код модуля выполняется один раз, и все импортёры получают один и тот же экспорт (подробно — в [Модулях](/content/javascript/modules)). Отдельный класс с `getInstance` не нужен. Минус синглтонов прежний — скрытое глобальное состояние, которое мешает тестам и серверному рендеру, где на каждый запрос нужен свой экземпляр.

### Стратегия

Стратегия — набор взаимозаменяемых алгоритмов за одним интерфейсом. В JavaScript это объект или `Map` функций вместо цепочки `if` или `switch`:

```js
const shipping = {
  courier: (order) => (order.total > 3000 ? 0 : 300),
  pickup: () => 0,
  post: (order) => 200 + order.weight * 20,
};

const cost = shipping[order.delivery](order);
```

Новый способ доставки — новая функция в объекте, без правки остального кода.

## Красные флаги в ответе

- **«Debounce и throttle — одно и то же».** Debounce ждёт паузы, throttle ограничивает частоту. При непрерывных событиях debounce не сработает ни разу.
- **«В debounce можно использовать стрелку и `fn(...args)`».** Метод объекта потеряет `this`. Нужны обычная функция и `fn.apply(this, args)`.
- **«Мемоизирую всё, что медленно».** Только чистые функции, с продуманным ключом и ограничением размера. Асинхронную — промисом, с удалением ошибок.
- **«Каррирование по `fn.length` работает всегда».** Параметры по умолчанию и rest уменьшают `length`, и функция вызовется раньше времени.
- **«`emit` просто перебирает массив слушателей».** Отписка во время обхода сдвигает индексы — нужен обход копии.
- **«Синглтон пишу классом с `getInstance`».** Модуль уже выполняется один раз.

## Как спрашивают на собеседовании

::question
Чем debounce отличается от throttle?

#answer
Debounce вызывает функцию, когда вызовы прекратились на заданное время, — для поиска и автосохранения. Throttle вызывает не чаще раза в интервал — для прокрутки и `resize`.

#more
При непрерывном потоке событий debounce не вызовется ни разу, а throttle — регулярно. Хороший throttle вызывает первый вызов сразу и последний в конце окна, чтобы не потерять финальное состояние. Обе обёртки должны сохранять `this` и аргументы, иметь `cancel` для размонтирования, а состояние держат в замыкании. Для анимаций вместо throttle по времени — `requestAnimationFrame`.
::

::question
Как мемоизировать асинхронную функцию?

#answer
Кешировать не результат, а промис: тогда параллельные вызовы с одним ключом получат один и тот же промис и сделают один запрос.

#more
Упавший промис нужно удалять из кеша, иначе одна сетевая ошибка закешируется навсегда. Нужны ограничение размера (LRU) и время жизни — данные устаревают. Ключ — примитив или `WeakMap` для объектов, `JSON.stringify` ненадёжен из-за порядка свойств и потери `undefined`. Это ядро библиотек запросов вроде TanStack Query.
::

::question
В чём разница между каррированием и частичным применением?

#answer
Каррирование превращает `f(a, b, c)` в цепочку `f(a)(b)(c)` — по одному аргументу. Частичное применение фиксирует часть аргументов и возвращает функцию от остальных; `bind` делает частичное применение.

#more
Каррированная функция обычно принимает и несколько аргументов сразу, а решает, вызывать ли исходную, по `fn.length`. Параметры по умолчанию и rest уменьшают `length`, и функция вызывается раньше времени. Каррирование удобно для конвейеров в `pipe`: каждый шаг — функция одного аргумента.
::

::question
Объясни паттерн Observer. Чем он отличается от pub/sub?

#answer
Observer — источник хранит список подписчиков и уведомляет их при изменении. Связь прямая, как у `addEventListener`. В pub/sub между издателями и подписчиками есть посредник-шина, и они не знают друг о друге.

#more
Pub/sub снижает связанность, но потоки данных труднее отследить и отладить. Обязательные детали реализации: `on` возвращает отписку, `emit` обходит копию списка (иначе отписка во время обхода пропустит соседа), решение, что делать с ошибкой одного слушателя. В Node.js `emit('error')` без подписчиков бросает исключение.
::

::question
Когда фабричная функция лучше класса?

#answer
Когда не нужны `new`, `this`, `instanceof` и наследование. Фабрика прячет состояние в замыкании, её методы можно передавать как колбэки, и она может вернуть объекты разной формы.

#more
Цена фабрики — методы создаются для каждого объекта, а у класса живут один раз на прототипе, поэтому для тысяч объектов класс экономнее. Класс нужен для `instanceof`, наследования и приватных полей с проверкой бренда. Во фронтенде состояние чаще живёт в фабриках и хуках, классы — в моделях и SDK.
::

::question
Что такое middleware?

#answer
Цепочка функций, каждая из которых обрабатывает запрос и вызывает `next()`, чтобы передать управление дальше, или не вызывает, чтобы остановить цепочку. Так устроены Express, Koa, Redux.

#more
Асинхронный вариант — «луковица»: код до `await next()` выполняется в прямом порядке, после — в обратном, когда ответ готов. Поэтому логирование времени, обработка ошибок и повтор запроса естественно пишутся как middleware. Middleware может завершить запрос сам, например ответом из кеша, и тогда следующие слои не выполнятся.
::

::question
Зачем compose и pipe?

#answer
Собирают функцию из нескольких шагов без промежуточных переменных: `pipe(trim, toLowerCase, toSlug)` читается в порядке выполнения. `pipe` — слева направо, `compose` — справа налево.

#more
Обе строятся через `reduce` и `reduceRight`. Каждый шаг должен принимать один аргумент, поэтому их сочетают с каррированием. Для асинхронных шагов есть вариант с `await` в цикле. В TypeScript типизация `pipe` от произвольного числа шагов требует перегрузок, поэтому библиотеки ограничивают их число.
::

## Практика

::practice{title="Напиши debounce"}
Напиши `debounce(fn, ms)`: вызов происходит через `ms` после последнего вызова, с последними аргументами и правильным `this`. Добавь `cancel()`.

#solution
```js
function debounce(fn, ms) {
  let timer = null;

  function debounced(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      fn.apply(this, args);       // this и аргументы последнего вызова
    }, ms);
  }

  debounced.cancel = () => {
    clearTimeout(timer);
    timer = null;
  };

  return debounced;
}

const form = {
  value: 'чай',
  onInput: debounce(function () { search(this.value); }, 300),
};
```

Обычная функция `debounced` нужна, чтобы получить `this` вызова, а стрелка внутри `setTimeout` берёт его из `debounced`. Каждый вызов сбрасывает таймер, поэтому сработает только последний. В проверке три быстрых ввода дали один вызов с последним значением, а `cancel` отменил запланированный вызов.
::

::practice{title="Кеш запросов без дублей"}
Компоненты страницы одновременно запрашивают одного и того же пользователя. Напиши `memoizeAsync(fn)`, чтобы одновременные вызовы с одним id делали один запрос, а сетевая ошибка не кешировалась.

#solution
```js
function memoizeAsync(fn) {
  const cache = new Map();
  return (key) => {
    if (!cache.has(key)) {
      const promise = fn(key).catch((error) => {
        cache.delete(key);
        throw error;
      });
      cache.set(key, promise);
    }
    return cache.get(key);
  };
}

const loadUser = memoizeAsync((id) => fetch(`/api/users/${id}`).then((r) => r.json()));

await Promise.all([loadUser(7), loadUser(7)]);   // один запрос
```

Промис кладётся в кеш синхронно, до того как запрос завершится, поэтому второй вызов получит тот же промис. При ошибке запись удаляется, и следующий вызов попробует снова. В проверке параллельные вызовы сделали один запрос, после ошибки — новый, а успех дальше брался из кеша. Для production добавляют время жизни записей и ограничение размера.
::

::practice{title="Почему не все слушатели вызываются?"}
Шина событий иногда пропускает слушателя аналитики, если перед ним был слушатель, подписанный через `once`:

```js
class Bus {
  handlers = [];
  on(fn) { this.handlers.push(fn); }
  off(fn) { this.handlers.splice(this.handlers.indexOf(fn), 1); }
  once(fn) {
    const wrapper = (...args) => { this.off(wrapper); fn(...args); };
    this.on(wrapper);
  }
  emit(...args) {
    for (let i = 0; i < this.handlers.length; i++) this.handlers[i](...args);
  }
}
```

#solution
`emit` обходит тот же массив, который меняет `off`. Обёртка `once` на индексе `i` удаляет себя — следующий слушатель сдвигается на её место, цикл переходит к `i + 1` и **пропускает** его. В проверке наивная реализация так и потеряла слушателя после `once`.

Фикс — обходить копию списка:

```js
emit(...args) {
  for (const fn of [...this.handlers]) fn(...args);
}
```

Изменения списка во время `emit` теперь применяются к следующему событию. Заодно стоит вернуть из `on` функцию отписки и решить, что делать с ошибкой в слушателе: обернуть вызов в `try`, чтобы одна ошибка не прерывала остальных, и отправить её в мониторинг.
::
