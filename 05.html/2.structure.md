# Структура документа и рендеринг

Как устроен HTML-документ и что происходит, пока он приходит по сети: скелет страницы, DOM и его узлы, потоковый разбор и отрисовка, сканер предзагрузки, `readyState`, `DOMContentLoaded` и `load`. Спрашивают, из чего состоит минимальный документ, что такое DOM, чем `DOMContentLoaded` отличается от `load`. Глубже — почему `firstChild` возвращает перенос строки, почему картинка, добавленная скриптом, грузится позже картинки из разметки и почему стиль задерживает `DOMContentLoaded`.

::tldr
- **Минимальный документ:** `<!doctype html>`, `html` с `lang`, `head` с `meta charset`, `viewport` и `title`, затем `body`. `lang` нужен программам чтения с экрана, переносам и выбору начертаний.
- **DOM — дерево узлов, а не только элементов:** текст, комментарии и переносы строк между тегами — тоже узлы, поэтому `firstChild` часто оказывается `#text`.
- **HTML разбирается и рисуется потоком:** шапка появляется, пока остальной документ ещё идёт по сети. Стиль в `head` откладывает первую отрисовку целиком, стиль в `body` — только того, что ниже.
- **Пока синхронный скрипт держит разбор, сканер предзагрузки уже качает ресурсы ниже по разметке,** но ресурсы, которые создаёт JavaScript, он не видит.
- **`readyState` идёт так: `loading` → `interactive` → `complete`.** `DOMContentLoaded` — после разбора и отложенных скриптов, `load` — после картинок и стилей. Стиль перед синхронным скриптом задерживает `DOMContentLoaded`.
::

## Скелет документа

Сквозной пример — страница каталога магазина чая, которую сервер отдаёт частями: шапку сразу, список товаров — когда сходит в базу.

```html
<!doctype html>
<html lang="ru">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <title>Каталог чая — Улун и пуэр</title>
    <link rel="stylesheet" href="/app.css">
  </head>
  <body>
    <header>Магазин чая</header>
    <main>…</main>
  </body>
</html>
```

| Часть | Зачем |
| --- | --- |
| `<!doctype html>` | стандартный режим; без него — режим совместимости (подробно — в [Основах HTML](/content/html/markup-language)) |
| `lang` на `html` | язык страницы: программа чтения с экрана выбирает произношение, браузер — словарь переносов и проверки орфографии, а для китайского, японского и корейского — начертания иероглифов |
| `meta charset` | кодировка; должна быть в первых 1024 байтах |
| `meta viewport` | ширина страницы на телефоне (подробно — в [Адаптивном дизайне](/content/css/rwd)) |
| `title` | название во вкладке, в закладках, в выдаче поиска; программа чтения с экрана объявляет его первым |

`html`, `head` и `body` можно не писать — парсер создаст их сам. Но явная разметка делает исходник и DOM одинаковыми. Что ещё кладут в `head` и в каком порядке — в [Содержимом head](/content/html/head-content).

## DOM

Из разметки браузер строит **DOM** — дерево объектов, с которым работают CSS и JavaScript. Узлы бывают разные:

| Узел | `nodeType` | Пример |
| --- | --- | --- |
| документ | 9 | `document` |
| DOCTYPE | 10 | `document.doctype` |
| элемент | 1 | `html`, `li` |
| текст | 3 | содержимое и переносы строк |
| комментарий | 8 | `<!-- акция -->` |
| фрагмент | 11 | `DocumentFragment`, содержимое `template` |

Главная неожиданность — **текстовые узлы из пробелов**:

```html
<ul id="cart">
  <li>Улун</li>
  <!-- акция -->
  <li>Пуэр</li>
</ul>
```

У этого списка два элемента, но семь узлов: в проверке `childNodes` дал текст, `li`, текст, комментарий, текст, `li`, текст. Переносы строк и отступы между тегами — текстовые узлы. Поэтому `ul.firstChild` — это `#text`, а не первый товар. Для элементов есть свои свойства: `children`, `firstElementChild`, `nextElementSibling`. Методы для работы с деревом — поиск, вставка, события — разобраны в [DOM и событиях](/content/web/dom-events).

## Пока страница грузится

Браузер не ждёт весь HTML. Он разбирает байты по мере прихода, строит DOM и рисует то, что уже готово.

### Потоковая отрисовка

Сервер каталога отдал шапку и на 900 мс задумался над списком товаров. В проверке первая отрисовка с шапкой случилась на ~20 мс, а `DOMContentLoaded` — только после конца HTML, на ~900 мс. Пользователь видит страницу почти сразу. На этом построены потоковый серверный рендеринг и `Suspense` в серверных фреймворках: сначала каркас, потом данные (подробно — в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration)).

Что останавливает этот поток:

- **стиль в `head`** — браузер не рисует ничего, пока не получит CSS, иначе показал бы неоформленную страницу. В проверке стиль с задержкой 900 мс отодвинул первую отрисовку на ~900 мс;
- **стиль в `body`** — откладывает только то, что ниже него: шапка над таким стилем в проверке нарисовалась на ~20 мс. Chromium ещё и приостанавливает разбор до загрузки этого стиля, поэтому `DOMContentLoaded` пришёл на ~900 мс;
- **синхронный скрипт** — останавливает разбор: пока скрипт не загрузится и не выполнится, DOM ниже него не строится.

Почему CSS блокирует отрисовку, а скрипт — разбор, чем помогают `defer`, `async` и критический CSS — в [Производительности загрузки](/content/security-perfomance/loading-performance). Сам путь от DOM к пикселям — стили, раскладка, отрисовка, композиция — в [Рендеринге](/content/web/rendering).

### Сканер предзагрузки

Пока основной парсер стоит на синхронном скрипте, второй, упрощённый — **сканер предзагрузки** — бежит по сырому HTML дальше и запускает загрузку найденных ресурсов: картинок, стилей, скриптов.

```html
<header>Магазин чая</header>
<script src="/slow.js"></script>               <!-- грузится 900 мс -->
<img src="/below.png" alt="">                    <!-- сканер нашёл сразу -->
<script>
  const banner = new Image();
  banner.src = '/by-script.png';                 // сканер не видит
  document.body.append(banner);
</script>
```

В проверке картинка из разметки ниже медленного скрипта была запрошена на ~7 мс, параллельно скрипту. Картинка, которую создаёт JavaScript, — на ~920 мс, после того как разбор дошёл до создающего её скрипта. Сканер видит только разметку. Ресурсы из JavaScript, из CSS — фоновые картинки, шрифты — и из клиентского рендеринга он не найдёт. Поэтому главную картинку первого экрана ставят в HTML тегом `img`, а не создают скриптом и не задают фоном, или явно предзагружают через `<link rel="preload">`.

## Жизненный цикл документа

`document.readyState` проходит три состояния, и на каждое есть событие:

| `readyState` | Что готово | Событие |
| --- | --- | --- |
| `loading` | документ разбирается | — |
| `interactive` | разбор закончен, DOM построен | дальше выполняются отложенные скрипты, затем `DOMContentLoaded` |
| `complete` | загружены картинки, стили, iframe | `load` на `window` |

Порядок, записанный в проверке:

```text
loading → inline-скрипт → interactive → модуль → DOMContentLoaded → complete → load
```

Отложенные скрипты — `defer` и `type="module"` — выполняются уже в `interactive`, но до `DOMContentLoaded`. Картинка с задержкой 900 мс не задержала `DOMContentLoaded` (~12 мс), но отодвинула `load` до ~900 мс. Поэтому код, которому нужен только DOM, ждёт `DOMContentLoaded` или стоит в `defer`-скрипте, а `load` нужен редко — например, чтобы измерить размеры картинок.

### Стиль задерживает DOMContentLoaded

`DOMContentLoaded` ждёт синхронные скрипты, а скрипт ждёт стили, которые стоят перед ним: он может спросить `getComputedStyle`, и ответ должен учитывать CSS. В проверке:

```html
<link rel="stylesheet" href="/slow.css">   <!-- 900 мс -->
<script>window.__x = 1</script>
```

`DOMContentLoaded` пришёл только через ~900 мс, хотя скрипт тривиальный. Без скрипта после стиля — на ~9 мс. Инициализация, повешенная на `DOMContentLoaded`, неожиданно ждёт CSS. Поэтому синхронные скрипты не ставят после стилей в `head`, а код переносят в `defer` или модули.

### Уход со страницы

- **`pagehide` и `pageshow`** — уход и возврат, в том числе из кеша «назад/вперёд»; у `pageshow` есть флаг `persisted`;
- **`visibilitychange`** — вкладку свернули или переключили; последний надёжный момент отправить аналитику;
- **`beforeunload`** — только чтобы спросить «уйти без сохранения?»;
- **`unload`** не используют: он ненадёжен на телефонах и отключает кеш «назад/вперёд» (подробно — в [Производительности загрузки](/content/security-perfomance/loading-performance)).

Полный путь от ввода адреса до первого кадра — DNS, TCP, TLS, запрос, разбор, отрисовка — в [Жизненном цикле запроса](/content/network-api/request-lifecycle).

## Красные флаги в ответе

- **«`firstChild` — первый элемент».** Это первый узел, часто текстовый перенос строки; элемент — `firstElementChild`.
- **«Браузер покажет страницу, когда загрузит весь HTML».** Он рисует потоком, и шапка видна до конца ответа.
- **«CSS не влияет на `DOMContentLoaded`».** Стиль перед синхронным скриптом его задерживает.
- **«Картинку можно добавить скриптом — загрузится так же».** Сканер предзагрузки её не видит, загрузка начнётся только после выполнения скрипта.
- **«`DOMContentLoaded` ждёт картинки».** Картинки ждёт `load`.
- **«Аналитику отправляю в `unload`».** Он ненадёжен и отключает кеш «назад/вперёд»; для этого `visibilitychange` и `pagehide`.

## Как спрашивают на собеседовании

::question
Из чего состоит минимальный HTML-документ? Зачем атрибут lang?

#answer
`<!doctype html>`, `html` с `lang`, `head` с `meta charset`, `meta viewport` и `title`, затем `body`. `html`, `head` и `body` парсер создаст и сам, но явно их пишут, чтобы исходник совпадал с DOM.

#more
`lang` нужен программам чтения с экрана для произношения, браузеру — для переносов, проверки орфографии и выбора начертаний иероглифов, поисковикам и переводчикам. `charset` должен попасть в первые 1024 байта, иначе браузер может начать разбор в неверной кодировке. `title` объявляется программами чтения первым и виден в выдаче поиска.
::

::question
Что такое DOM? Чем узел отличается от элемента?

#answer
DOM — дерево объектов, которое браузер строит из HTML и через которое с документом работают CSS и JavaScript. Узлы бывают разных типов: документ, элементы, текст, комментарии, DOCTYPE. Элемент — только один из типов узла.

#more
Переносы строк и отступы между тегами — текстовые узлы, поэтому `childNodes` длиннее `children`, а `firstChild` часто `#text`. Для элементов есть `children`, `firstElementChild`, `nextElementSibling`. Типы различают по `nodeType`: 1 — элемент, 3 — текст, 8 — комментарий, 9 — документ.
::

::question
Как браузер показывает страницу, которая ещё грузится?

#answer
Он разбирает HTML потоком и рисует то, что уже готово: если сервер отдал шапку и задумался, шапка появится на экране до конца ответа. Отрисовку держат стили: в `head` — всю страницу, в `body` — только то, что ниже. Синхронный скрипт останавливает разбор.

#more
На потоковой отдаче построены потоковый SSR и `Suspense`: каркас и шапка приходят сразу, данные — позже, в том же ответе. Chromium приостанавливает и разбор после стиля в `body`. Поэтому критичные стили — в `head`, скрипты — `defer` или модули, а данные, которые долго считаются, отдают после каркаса.
::

::question
Что такое сканер предзагрузки? Что он не видит?

#answer
Пока основной парсер стоит на синхронном скрипте, упрощённый сканер бежит по сырому HTML дальше и запускает загрузку найденных картинок, стилей и скриптов. Поэтому ресурсы ниже скрипта начинают качаться параллельно с ним.

#more
Сканер видит только разметку. Ресурсы, которые создаёт JavaScript, фоновые картинки и шрифты из CSS, всё из клиентского рендеринга он не находит — они начинают грузиться поздно. Главную картинку первого экрана ставят тегом `img` в HTML или предзагружают через `<link rel="preload">` с `fetchpriority="high"`.
::

::question
Чем DOMContentLoaded отличается от load? Что такое readyState?

#answer
`DOMContentLoaded` — документ разобран и отложенные скрипты выполнены; картинки ещё могут грузиться. `load` — загружено всё: картинки, стили, iframe. `readyState` проходит `loading`, `interactive` (разбор закончен) и `complete` (всё загружено).

#more
Порядок: `interactive`, затем отложенные скрипты — `defer` и модули, — затем `DOMContentLoaded`, затем `complete` и `load`. Код, которому нужен только DOM, ставят в `defer`-скрипт или вешают на `DOMContentLoaded`. Если скрипт подключён после того, как событие уже прошло, обработчик не сработает, поэтому сначала проверяют `document.readyState`.
::

::question
Почему CSS может задержать DOMContentLoaded?

#answer
`DOMContentLoaded` ждёт выполнения синхронных скриптов, а синхронный скрипт ждёт загрузки стилей, стоящих перед ним: он может прочитать вычисленные стили, и ответ должен их учитывать. Медленный CSS перед скриптом отодвигает и разбор, и событие.

#more
Без скрипта после стиля `DOMContentLoaded` не ждёт CSS, хотя первая отрисовка ждёт в любом случае. Решение — не ставить синхронные скрипты после стилей в `head`, переводить код в `defer` или модули, а критичный CSS делать маленьким или встраивать.
::

## Практика

::practice{title="firstChild не тот"}
Скрипт подсвечивает первый товар корзины, но падает с ошибкой `Cannot read properties of undefined (reading 'add')`:

```html
<ul id="cart">
  <li>Улун</li>
  <li>Пуэр</li>
</ul>
```

```js
document.getElementById('cart').firstChild.classList.add('active');
```

#solution
Первый узел списка — перенос строки с отступом, текстовый узел `#text`. У текстового узла нет `classList`. Нужен первый **элемент**:

```js
document.getElementById('cart').firstElementChild.classList.add('active');
// или селектором
document.querySelector('#cart > li')?.classList.add('active');
```

В проверке у такого списка `childNodes` состоял из семи узлов — текст, `li`, текст, комментарий, текст, `li`, текст, — а `children` из двух. Минифицированный HTML без переносов «чинит» баг случайно, и он всплывает, когда разметку отформатируют.
::

::practice{title="Баннер первого экрана грузится последним"}
LCP на главной — 3 секунды, хотя баннер весит 60 КБ. В Network видно, что запрос баннера начинается только после загрузки бандла:

```html
<script src="/bundle.js"></script>
<!-- bundle.js: document.querySelector('.hero').style.backgroundImage = 'url(/hero.webp)' -->
```

#solution
Адрес баннера знает только JavaScript, а сканер предзагрузки видит лишь разметку. Запрос уходит после загрузки, разбора и выполнения бандла. Картинку ставят в HTML, чтобы сканер нашёл её сразу:

```html
<img src="/hero.webp" alt="Осенняя распродажа улуна" width="1200" height="400" fetchpriority="high">
<script src="/bundle.js" defer></script>
```

Если картинка действительно фоновая — предзагрузить её: `<link rel="preload" href="/hero.webp" as="image" fetchpriority="high">`. В проверке картинка из разметки ниже медленного скрипта запросилась на ~7 мс, а созданная скриптом — на ~920 мс.
::

::practice{title="Инициализация ждёт стили"}
Виджет корзины вешает обработчики на `DOMContentLoaded`, и на медленном 3G кнопки «мертвы» лишнюю секунду:

```html
<head>
  <link rel="stylesheet" href="/app.css">
  <script>window.dataLayer = window.dataLayer || [];</script>
</head>
```

```js
document.addEventListener('DOMContentLoaded', initCart);
```

#solution
Синхронный скрипт после стиля ждёт загрузки CSS, разбор стоит, а `DOMContentLoaded` приходит только после этого. В проверке медленный стиль перед тривиальным скриптом отодвинул `DOMContentLoaded` на ~900 мс, а без скрипта событие пришло на ~9 мс. Встроенный скрипт переносят выше стиля или в отложенный, а инициализацию — в модуль:

```html
<head>
  <script>window.dataLayer = window.dataLayer || [];</script>
  <link rel="stylesheet" href="/app.css">
  <script type="module" src="/cart.js"></script>
</head>
```

Модули выполняются после разбора, DOM к этому моменту готов, и ждать события не нужно.
::
