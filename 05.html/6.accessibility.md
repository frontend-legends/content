# Доступность

Доступность (accessibility, a11y) — чтобы интерфейсом могли пользоваться все: с программой чтения с экрана, только с клавиатуры, с увеличением, с плохим зрением или дрожащими руками. Спрашивают, что такое WCAG, ARIA и доступное имя, как сделать доступную кнопку-иконку и модалку, какие бывают `tabindex`. Глубже — почему `role="button"` не делает `div` кнопкой, почему `aria-hidden` на ссылке опасен и почему автоматическая проверка не находит половину проблем.

::tldr
- **Ориентир — WCAG уровня AA.** Программа чтения с экрана работает не с пикселями, а с деревом доступности: у каждого узла роль, имя и состояние.
- **Доступное имя считается по порядку:** `aria-labelledby`, `aria-label`, подпись — `label`, `alt`, текст содержимого, — затем `title` и `placeholder`. Кнопка-иконка без имени для программы чтения — просто «кнопка».
- **Первое правило ARIA — нативный элемент вместо ARIA.** `role="button"` меняет роль, но не поведение: `div` не получит ни фокуса, ни Enter, ни пробела.
- **Всё должно работать с клавиатуры:** порядок Tab идёт по DOM, `tabindex` больше нуля не используют, внутри составных виджетов ходят стрелками, а после перехода в одностраничном приложении фокус переносят.
- **Контраст текста — не меньше 4,5:1, у крупного и элементов интерфейса — 3:1.** Автоматические проверки вроде axe ловят только часть проблем; клавиатура и программа чтения — обязательная ручная проверка.
::

## Зачем и по каким правилам

Сквозной пример — оформление заказа в магазине чая: поле телефона, способ доставки, кнопка-крестик «удалить из корзины», уведомление «Добавлено в корзину» и ошибка оплаты.

Кому нужна доступность:

- **незрячим и слабовидящим** — программы чтения с экрана: VoiceOver, NVDA, JAWS, TalkBack; увеличение страницы до 200–400%;
- **тем, кто не может пользоваться мышью** — только клавиатура, голосовое управление, переключатели;
- **людям с нарушениями цветовосприятия** — им нужно больше, чем цвет;
- **всем в неудобной ситуации** — яркое солнце, сломанный тачпад, рука с ребёнком, видео без звука в метро.

Стандарт — **WCAG** (Web Content Accessibility Guidelines) от W3C, действующая версия — 2.2. Требования сгруппированы по четырём принципам:

| Принцип | Смысл | Пример требования |
| --- | --- | --- |
| воспринимаемость | информацию можно воспринять | текстовая альтернатива картинкам, контраст, субтитры |
| управляемость | интерфейсом можно управлять | всё с клавиатуры, видимый фокус, достаточно времени |
| понятность | интерфейс понятен | подписи и инструкции, понятные ошибки, предсказуемость |
| надёжность | работает со вспомогательными технологиями | корректные роли, имена и состояния |

У каждого требования уровень: A — минимум, AA — обычная цель законов и компаний, AAA — повышенный. В Евросоюзе с 2025 года действует European Accessibility Act: требования доступности распространяются на интернет-магазины, банки и транспорт. Подробнее о закрытии требований в процессах — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing).

## Дерево доступности

Браузер строит из DOM **дерево доступности** и отдаёт его программам чтения через API операционной системы. У каждого узла:

- **роль** — что это: кнопка, ссылка, заголовок второго уровня, поле, список;
- **имя** — как это называется: «Оформить заказ»;
- **состояние и свойства** — отмечено, развёрнуто, недоступно, обязательно;
- **описание** — дополнительный текст: подсказка или ошибка.

Программа чтения произносит «Оформить заказ, кнопка» и позволяет прыгать по заголовкам, ориентирам и полям. Роль даёт элемент — `button`, `a href`, `h2`, `nav` (подробно — в [Семантике и тегах](/content/html/tags)). Дерево смотрят в DevTools: вкладка Accessibility у элемента.

### Доступное имя

Имя вычисляется по алгоритму с приоритетами — в проверке Chromium выдал ровно такой порядок:

| Источник | Пример | Имя |
| --- | --- | --- |
| `aria-labelledby` | `<button aria-labelledby="cart-title" aria-label="Не это">×</button>` | «Корзина» — текст элемента с этим `id` |
| `aria-label` | `<button aria-label="Удалить улун">×</button>` | «Удалить улун» вместо «×» |
| подпись или содержимое | `<label for="phone">Телефон</label>`, `alt`, текст кнопки | «Телефон», текст `alt`, «Удалить» |
| `title` | `<button title="Удалить пуэр"><svg …></button>` | «Удалить пуэр» — последний запасной вариант |
| `placeholder` | `<input placeholder="Город">` | «Город», хотя на экране подсказка исчезает при вводе |

Самая частая ошибка — кнопка-иконка без имени: `<button><svg…></svg></button>` в проверке получила пустое имя, и программа чтения скажет просто «кнопка». `placeholder` формально даёт полю имя, но подписью не является: исчезает при вводе, обычно бледный и плохо контрастный. Нужен видимый `label`.

Картинке имя даёт `alt`: «Улун молочный, 100 г». Декоративной — пустой `alt=""`: в проверке такая картинка выпала из дерева доступности. Без `alt` вовсе картинка остаётся безымянным изображением, и часть программ чтения произносит вместо описания имя файла.

## ARIA

**ARIA** (Accessible Rich Internet Applications) — атрибуты, которые меняют то, что попадает в дерево доступности: `role`, `aria-label`, `aria-expanded`, `aria-describedby`, `aria-live` и другие.

### Первое правило ARIA

Не используй ARIA, если есть нативный элемент. ARIA меняет только **описание** в дереве — поведения она не добавляет.

```html
<div role="button" onclick="pay()">Оплатить</div>
<button onclick="pay()">Оплатить</button>
```

В проверке `div` получил роль «кнопка», но:

- Tab его пропустил и сразу попал на настоящую кнопку;
- `focus()` из кода не сработал — у `div` нет фокуса без `tabindex`;
- с `tabindex="0"` фокус появился, но Enter и пробел не вызвали `click`, а у настоящей кнопки оба вызвали.

Чтобы «починить» такой `div`, нужны `tabindex="0"`, обработчики Enter и пробела, стиль фокуса, состояние `disabled`, отправка формы. `button` даёт всё это сам.

Вторая сторона — **ARIA затирает семантику**. `<h2 role="button">` в проверке перестал быть заголовком: в дереве не осталось ни одного заголовка, и навигация по заголовкам его не найдёт.

### Частые атрибуты

| Атрибут | Для чего |
| --- | --- |
| `aria-label`, `aria-labelledby` | имя, когда нет видимой подписи или она в другом месте |
| `aria-describedby` | описание: подсказка к полю, текст ошибки |
| `aria-expanded`, `aria-controls` | раскрыто ли меню или аккордеон и чем управляет кнопка |
| `aria-current="page"` | текущая страница в навигации |
| `aria-invalid`, `aria-required` | ошибка и обязательность поля, если нет нативных `required` и валидации |
| `aria-hidden="true"` | скрыть декоративное от программ чтения: иконку рядом с текстом |
| `aria-live`, `role="status"`, `role="alert"` | объявлять изменения без переноса фокуса |

### aria-hidden и фокус

```html
<div aria-hidden="true"><a href="/promo">Акция</a></div>
```

`aria-hidden` прячет от программ чтения, но **не от клавиатуры**: в проверке Tab попал на ссылку «Акция», которой нет в дереве доступности. Пользователь программы чтения оказывается на «призраке» без имени и роли. Chromium в таком случае сам снимает `aria-hidden` с фокусированного элемента и пишет в консоль предупреждение «Blocked aria-hidden…» с советом использовать `inert`. Правильно — `inert`, который убирает и фокус, и элемент из дерева (подробно — в [Атрибутах](/content/html/attributes)).

## Клавиатура и фокус

Всё, что можно сделать мышью, должно быть доступно с клавиатуры: Tab и Shift+Tab между элементами, Enter и пробел для действия, Esc для закрытия, стрелки внутри составных виджетов.

### tabindex

| Значение | Что делает |
| --- | --- |
| нет атрибута | фокус только у интерактивных элементов: ссылок с `href`, кнопок, полей |
| `0` | добавить элемент в порядок Tab по месту в DOM |
| `-1` | фокус только из кода — `focus()`; Tab пропускает |
| больше `0` | вперёд всех остальных по номеру — ломает порядок, не используют |

Порядок Tab идёт **по DOM**. Если CSS переставил элементы — `order`, `flex-direction: row-reverse`, `grid-area`, — фокус прыгает по экрану в неожиданном порядке. Видимый фокус обязателен: стилизуют `:focus-visible`, а не убирают `outline` (подробно — в [Селекторах](/content/css/css-rules)).

### Составные виджеты

Внутри группы — вкладок, меню, списка вариантов — Tab делает **одну** остановку, а между элементами ходят стрелками. Это паттерн roving tabindex: у активного элемента `tabindex="0"`, у остальных `-1`, стрелки переносят фокус и меняют значения. Нативная группа переключателей так и устроена: в проверке Tab попал на выбранный «Курьер», стрелка вниз перенесла фокус и выбор на «Самовывоз», а следующий Tab ушёл к кнопке «Дальше», минуя остальные варианты. `fieldset` с `legend` дал группе имя «Доставка». Как реализовать вкладки, комбобокс и меню по паттернам ARIA — в [UI-компонентах](/content/common-coding-questions/ui-components-basics) и [системном дизайне](/content/architecture/system-design-examples).

### Управление фокусом

- **модальное окно** — фокус внутрь при открытии, удержание внутри, возврат на кнопку при закрытии; `dialog` с `showModal()` делает это сам (подробно — в [Семантике и тегах](/content/html/tags));
- **переход в одностраничном приложении** — страница не перезагрузилась, и программа чтения не узнала о новой. Фокус переносят на `h1` новой страницы с `tabindex="-1"` или объявляют переход через live-регион;
- **удаление элемента** — если удалили товар, на котором был фокус, фокус переносят на соседний товар или заголовок корзины, иначе он улетает в начало страницы;
- **ссылка «перейти к содержимому»** — первая в документе, видна при фокусе, ведёт к `main`.

## Live-регионы

Уведомление «Добавлено в корзину» появляется без перехода фокуса, и программа чтения его не заметит. Live-регион объявляет изменения своего содержимого:

```html
<div role="status">Добавлено в корзину</div>   <!-- вежливо, после текущей фразы -->
<div role="alert">Карта отклонена</div>        <!-- сразу, прерывая -->
```

`role="status"` и элемент `output` в проверке получили `aria-live="polite"`, `role="alert"` — `assertive`. Правила:

- **регион должен уже быть в DOM** до изменения: программы чтения следят за существующими регионами, а вставленный сразу с текстом могут не объявить. Пустой контейнер кладут заранее, текст меняют;
- **`assertive` — только для срочного:** ошибки, потери данных. Остальное — `polite`;
- **не заменяют фокус:** ошибку в форме объявляют, но фокус переносят на первое поле с ошибкой.

## Формы

- **У каждого поля — видимый `label`**, связанный через `for` и `id` или вложением. `placeholder` — не подпись;
- **группы** — `fieldset` и `legend`: «Доставка», «Оплата»;
- **ошибки** — текстом рядом с полем, связанным через `aria-describedby`, и с `aria-invalid="true"`; не только красной рамкой;
- **обязательность** — `required`, а не только звёздочка;
- **автозаполнение** — `autocomplete="tel"`, `"street-address"`: не нужно печатать и не нужно помнить.

Подробно о полях и валидации — в [Формах](/content/html/forms).

## Цвет и контраст

WCAG требует контраст текста к фону не меньше **4,5:1**, для крупного текста — от 24px или от 18,7px жирным — и для элементов интерфейса и иконок — **3:1**. Контраст считают по формуле относительной яркости:

```js
const contrast = (L1, L2) => (Math.max(L1, L2) + 0.05) / (Math.min(L1, L2) + 0.05);
```

В проверке серый `#777` на белом дал 4,48:1 — чуть меньше нормы, а `#767676` — 4,54:1 и проходит. Чёрный на белом — максимум, 21:1. Дизайн-системы проверяют пары токенов цвета заранее, а в DevTools контраст виден в подсказке пипетки.

Цвет не должен быть единственным носителем смысла: ошибку поля показывают текстом, а не только красной рамкой; ссылку в тексте — подчёркиванием, а не только цветом. Около 8% мужчин различают цвета хуже обычного.

## Проверка

- **автоматическая** — axe-core, Lighthouse, линтеры JSX. В проверке axe на плохой форме нашёл картинку без `alt`, поле без подписи, кнопку без имени и бледный текст, а на исправленной — ничего. Но «кнопку» из `div` с `onclick` он не заметил вовсе: для него это просто текст в `main`;
- **клавиатура** — пройти весь сценарий Tab, Enter, Esc и стрелками, не трогая мышь: видно ли фокус, всё ли достижимо, нет ли ловушек;
- **программа чтения** — VoiceOver на Mac и iPhone, NVDA на Windows, TalkBack на Android: что объявляется, в каком порядке, понятно ли без экрана;
- **увеличение** — 200% и 400%: ничего не обрезается и не требует горизонтальной прокрутки.

Автоматика ловит то, что видно по разметке: нет имени, нет подписи, мал контраст. Правильность ролей, порядок фокуса и смысл объявлений проверяет только человек. Как встроить проверки в CI — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing).

## Красные флаги в ответе

- **«`role="button"` делает `div` кнопкой».** Меняется только роль в дереве; фокус, Enter и пробел придётся писать самому.
- **«`aria-label` можно ставить всегда».** Он заменяет видимый текст: если не совпадает с подписью на экране, голосовое управление не найдёт кнопку по тому, что видно. А на `div` и `span` без роли спецификация ARIA его запрещает.
- **«`aria-hidden` — чтобы спрятать неактивный фон».** Фокус туда по-прежнему попадает; нужен `inert`.
- **«`placeholder` вместо `label` — норм».** Он исчезает при вводе и плохо контрастен.
- **«`tabindex="1"` поставлю на важное поле».** Положительный `tabindex` ломает порядок; порядок задают DOM.
- **«Lighthouse показывает 100 — значит, доступно».** Автоматика не видит неправильных ролей, порядка фокуса и смысла.

## Как спрашивают на собеседовании

::question
Что такое WCAG и уровни соответствия?

#answer
Рекомендации W3C по доступности, сгруппированные по четырём принципам: воспринимаемость, управляемость, понятность, надёжность. У каждого требования уровень A, AA или AAA; обычная цель законов и компаний — AA. Действующая версия — 2.2.

#more
AA включает контраст 4,5:1, работу с клавиатуры, видимый фокус, подписи у полей, увеличение до 200% без потерь. В 2.2 добавили, например, минимальный размер целей касания 24×24 и запрет скрывать фокус под липкими панелями. В Евросоюзе требования доступности для интернет-магазинов и банков закреплены законом с 2025 года.
::

::question
Что такое доступное имя и как оно вычисляется?

#answer
Имя, которое программа чтения произносит для элемента: «Оформить заказ, кнопка». Источники по приоритету: `aria-labelledby`, `aria-label`, затем подпись — `label`, `alt` — или текст содержимого, затем `title` и `placeholder`.

#more
У кнопки-иконки без текста имени нет, поэтому нужен `aria-label` или визуально скрытый текст, а саму иконку прячут `aria-hidden="true"`. `aria-labelledby` удобен, когда подпись уже есть на странице — заголовок окна. `aria-label` лучше не расходится с видимым текстом: голосовое управление ищет элемент по тому, что видно.
::

::question
Какое первое правило ARIA? Почему div с role="button" — плохая кнопка?

#answer
Не использовать ARIA, если есть нативный элемент. ARIA меняет только описание в дереве доступности, а не поведение: `div role="button"` объявляется кнопкой, но не попадает в порядок Tab и не реагирует на Enter и пробел.

#more
Чтобы такой `div` работал, нужны `tabindex="0"`, обработчики клавиш, стиль фокуса, поддержка `disabled` и отправки формы — `button` даёт это бесплатно. ARIA ещё и затирает семантику: `<h2 role="button">` перестаёт быть заголовком. ARIA нужна там, где нативного элемента нет: вкладки, комбобокс, дерево.
::

::question
Какие значения tabindex бывают и когда что использовать?

#answer
`0` добавляет элемент в порядок Tab по его месту в DOM. `-1` даёт фокус только из кода — для заголовка, на который переносят фокус после перехода, или для неактивных элементов составного виджета. Положительные значения ставят элемент вперёд всех и ломают порядок — их не используют.

#more
Интерактивным элементам `tabindex` не нужен — у них фокус есть. Внутри составных виджетов используют roving tabindex: `0` у активного, `-1` у остальных, стрелки переключают. Порядок фокуса задаёт DOM, поэтому визуальные перестановки через CSS его не меняют — и это ловушка.
::

::question
Как сделать доступное модальное окно?

#answer
`dialog` с `showModal()`: фокус внутрь, удержание фокуса, Esc, инертный фон и верхний слой браузер даёт сам. Остаётся имя окна через `aria-labelledby` на заголовок и возврат фокуса на кнопку, открывшую окно.

#more
Самописное окно требует всего этого вручную: перенос фокуса, ловушку Tab, `inert` на остальной странице — не `aria-hidden`, — Esc, `role="dialog"` и `aria-modal="true"`. Фокус при открытии ставят на первый осмысленный элемент; для подтверждения удаления — на «Отмену», а не на опасное действие.
::

::question
Как сообщить программе чтения об изменении на странице?

#answer
Live-регионом: `role="status"` или `aria-live="polite"` для обычных сообщений вроде «Добавлено в корзину», `role="alert"` или `assertive` для срочных ошибок. Программа чтения объявит изменение текста без переноса фокуса.

#more
Регион должен быть в DOM до изменения: пустой контейнер кладут заранее и меняют его текст. `assertive` прерывает пользователя, поэтому только для важного. Ошибки формы объявляют и переносят фокус на первое поле с ошибкой. После перехода в одностраничном приложении объявляют новую страницу или ставят фокус на её `h1`.
::

::question
Как проверять доступность?

#answer
Автоматикой — axe-core, Lighthouse, линтеры — и руками: пройти сценарий только с клавиатуры, послушать программой чтения с экрана, увеличить до 200–400%. Автоматика находит отсутствующие имена, подписи и низкий контраст, но не видит неправильных ролей и порядка фокуса.

#more
axe-core встраивают в компонентные и e2e-тесты, чтобы регрессии ловились в CI. Самописный `div` с `onclick` axe не замечает: для него это просто текст. Поэтому ручная проверка ключевых сценариев — оформление заказа, вход, поиск — входит в процесс, а не делается раз в год.
::

## Практика

::practice{title="Кнопка-крестик в корзине"}
Программа чтения на каждой строке корзины говорит «кнопка», и непонятно, что удаляется:

```html
<li>Улун молочный <button class="remove" onclick="remove(7)"><svg>…</svg></button></li>
```

#solution
У кнопки нет доступного имени: иконка не даёт текста. Добавляем имя с названием товара, а иконку прячем от дерева доступности:

```html
<li>
  Улун молочный
  <button class="remove" onclick="remove(7)" aria-label="Удалить улун молочный">
    <svg aria-hidden="true" focusable="false">…</svg>
  </button>
</li>
```

В проверке в Chromium кнопка с одной иконкой получила пустое имя, а с `aria-label` — «Удалить улун молочный». axe-core на исходной разметке сообщает нарушение `button-name`. После удаления фокус переносят на следующий товар или заголовок корзины, иначе он улетит в начало страницы.
::

::practice{title="Кнопка из div"}
Кнопка «Оплатить» не работает с клавиатуры, а axe-core ничего не находит:

```html
<div class="pay-button" onclick="pay()">Оплатить</div>
```

#solution
У `div` нет роли, фокуса и клавиатурного поведения, а axe-core не знает, что это должна быть кнопка: для него это текст. `role="button"` проблему не решает — в проверке такой `div` объявлялся кнопкой, но Tab его пропускал, а Enter и пробел не вызывали `click`. Нужен нативный элемент:

```html
<button type="button" class="pay-button" onclick="pay()">Оплатить</button>
```

Стили кнопки сбрасывают в CSS, если дизайн другой. Такие ошибки находит только ручная проверка клавиатурой, поэтому сценарий оплаты проходят без мыши перед каждым релизом.
::

::practice{title="Неактивный фон под самописным окном"}
Под самописным окном фон спрятали от программ чтения, но пользователи клавиатуры всё равно уходят табом на страницу:

```html
<main aria-hidden="true">…</main>
<div class="modal" role="dialog" aria-modal="true">…</div>
```

#solution
`aria-hidden` прячет только от дерева доступности, фокус по-прежнему попадает в `main`. Пользователь программы чтения оказывается на элементе без имени и роли. В проверке Tab попал на ссылку внутри `aria-hidden`, а Chromium снял скрытие с фокусированного элемента и предупредил в консоли. Нужен `inert`:

```html
<main inert>…</main>
<div class="modal" role="dialog" aria-modal="true" aria-labelledby="modal-title">…</div>
```

`inert` убирает из фона и фокус, и клики, и узлы дерева доступности. Ещё проще — `dialog` с `showModal()`, который делает фон инертным сам.
::
