# Моки и тестовые дублёры

Чтобы протестировать код в изоляции, его зависимости (сеть, время, тяжёлые модули) заменяют **тестовыми дублёрами**. «Mock» в быту значит любую подмену, но на собесе ценят знание точной таксономии и принципа **«не перемокать»**.

---

## Зачем подменять зависимости

Тест должен быть быстрым, детерминированным и проверять **именно** тестируемый код. Реальные зависимости мешают:

- **сеть** - медленно, нестабильно, зависит от бэкенда;
- **время/случайность** - недетерминированно;
- **тяжёлые модули** - аналитика, платежи, сторонние SDK;
- **побочные эффекты** - не хочется реально слать письмо в тесте.

Их заменяют управляемыми дублёрами.

---

## Таксономия дублёров

Классификация (Джерард Месарош, популяризировал Фаулер). «Mock» - частный случай, а не общий термин.

| Дублёр | Что делает |
|--------|-----------|
| **Dummy** | заглушка-наполнитель, не используется (просто чтобы передать аргумент) |
| **Stub** | возвращает заранее заданные ответы |
| **Spy** | записывает, как его вызывали (аргументы, число раз) |
| **Mock** | запрограммирован с ожиданиями и проверяет их |
| **Fake** | рабочая, но упрощённая реализация (in-memory БД вместо настоящей) |

<b class="text-on-semi-light">Кратко о различии</b> - <span class="text-gray">**Stub** даёт ответы («верни этого юзера»). **Spy** следит за вызовами («был ли вызван и с чем»). **Mock** объединяет: и подменяет, и проверяет ожидания. **Fake** - лёгкая, но настоящая реализация. На практике инструменты (`vi.fn`) совмещают роли spy+stub+mock.</span>

---

## Инструменты

### vi.fn() / jest.fn() - mock-функция

Функция, которая записывает вызовы и может возвращать заданное:

```js
const onClick = vi.fn();                  // spy
render(<Button onClick={onClick} />);
await userEvent.click(screen.getByRole('button'));
expect(onClick).toHaveBeenCalledOnce();   // проверяем вызов

const getUser = vi.fn().mockResolvedValue({ name: 'Аня' }); // stub
```

### vi.spyOn() - шпион на существующем методе

```js
const spy = vi.spyOn(console, 'error').mockImplementation(() => {});
// проверить, что что-то залогировало ошибку, не засоряя вывод
```

### vi.mock() - мок модуля

Подменяет **весь модуль** - для изоляции от тяжёлых/внешних зависимостей:

```js
vi.mock('./analytics', () => ({ track: vi.fn() })); // не слать реальную аналитику
```

## MSW для сети

Сеть **не** мокают через подмену `fetch` - это завязка на реализацию. Лучший подход - **MSW (Mock Service Worker)**: перехват на **сетевом уровне**.

```js
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users/1', () => HttpResponse.json({ name: 'Аня' }))
);
```

<b class="text-on-semi-light">Почему MSW лучше мока fetch</b> - <span class="text-gray">Мок `fetch`/модуля привязан к тому, **чем** грузят данные. MSW перехватывает на уровне сети - тест не знает, что ответ замокан, и не меняется при переходе с `fetch` на axios или React Query. Один мок работает и в unit, и в e2e.</span>

## Фейковое время

```js
vi.useFakeTimers();
vi.advanceTimersByTime(1000); // «промотать» 1 секунду без ожидания
vi.useRealTimers();
```

Для дебаунса, таймаутов, поллинга - чтобы тест не ждал реальные секунды.

---

## Главный принцип: не перемокать

| Мокать | Не мокать |
|--------|-----------|
| внешние границы: сеть, время, сторонние SDK | свою собственную логику |
| то, что медленно/недетерминированно | то, что тестируешь |

<b class="text-on-semi-light">Опасность over-mocking</b> - <span class="text-gray">Если замокать слишком много, тест проверяет **моки**, а не реальное взаимодействие - он зелёный, а в проде сломано. Мокай на **границах** системы (сеть, внешние сервисы), а внутреннюю логику тестируй по-настоящему. Чем больше моков - тем меньше уверенности даёт тест.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем отличаются stub, spy и mock?</b>
<span class="text-gray">Stub возвращает заданные ответы; spy записывает, как его вызывали; mock объединяет подмену и проверку ожиданий. Fake - упрощённая рабочая реализация. На практике `vi.fn` совмещает роли.</span>

<b class="text-on-semi-light">Зачем вообще нужны моки?</b>
<span class="text-gray">Изолировать тестируемый код от медленных/недетерминированных/внешних зависимостей (сеть, время, SDK), чтобы тест был быстрым, стабильным и проверял именно нужное.</span>

<b class="text-on-semi-light">Почему сеть лучше мокать через MSW, а не через мок fetch?</b>
<span class="text-gray">MSW перехватывает на уровне сети, не завися от способа загрузки - тест не меняется при смене fetch/axios/Query и переиспользуется в unit и e2e.</span>

<b class="text-on-semi-light">Чем опасно избыточное мокание?</b>
<span class="text-gray">Тест начинает проверять моки, а не реальное взаимодействие - зелёный при сломанном проде. Мокать нужно на границах (сеть, внешнее), а свою логику тестировать по-настоящему.</span>

<b class="text-on-semi-light">Как тестировать код с таймерами/датой?</b>
<span class="text-gray">Фейковые таймеры (`vi.useFakeTimers`, `advanceTimersByTime`) и фиксированная системная дата - чтобы не ждать реальное время и убрать недетерминированность.</span>
