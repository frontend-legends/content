# Моки и тестовые дублёры

Чем подменяют зависимости в тестах: виды дублёров — dummy, stub, spy, mock, fake, — функции `vi.fn` и `vi.spyOn`, подмена модулей, фейковое время и MSW для сети. Спрашивают, чем stub отличается от spy и mock, почему сеть подменяют через MSW, а не мок `fetch`, и чем опасно избыточное мокирование. Глубже — почему `vi.mock` не видит переменную, объявленную строкой выше, чем `clearAllMocks` отличается от `resetAllMocks` и `restoreAllMocks` и почему промотка таймеров не дошла до конца цепочки.

::tldr
- **Дублёр заменяет зависимость, которая медленна, недетерминирована или опасна:** сеть, время, случайность, платёжный SDK, отправку писем.
- **Виды:** dummy — заполнитель аргумента, stub — заранее заданный ответ, spy — запись вызовов, mock — ожидания, которые проверяются, fake — упрощённая рабочая реализация. `vi.fn` совмещает stub, spy и mock.
- **`vi.mock` поднимается в начало файла:** переменные, объявленные выше по тексту, внутри фабрики ещё не существуют — для них есть `vi.hoisted`.
- **Сеть подменяют на границе — MSW:** код делает настоящий запрос через `fetch` или axios, а ответ задаёт тест. Без `onUnhandledRequest: 'error'` неописанный запрос уходит в настоящую сеть.
- **Не перемокать:** подменяют внешние границы, а свою логику оставляют настоящей. Чем больше моков, тем больше тест проверяет сами моки.
::

---

## Зачем подменять

Сквозной пример — оформление заказа в магазине: модуль API, аналитика, которая шлёт события, поиск с задержкой ввода и повтор запроса после ошибки.

Тест должен быть быстрым и повторяемым и проверять тестируемый код, а не окружение. Мешают:

- **сеть** — медленная, нестабильная, зависит от бэкенда и данных в нём;
- **время и случайность** — результат меняется от запуска к запуску;
- **внешние SDK** — аналитика, платежи, карты;
- **побочные эффекты** — письма, списания, записи в чужие системы.

## Виды дублёров

Классификация Джерарда Месароша, которую популяризировал Мартин Фаулер. «Мок» в разговоре — любая подмена, но по классификации это лишь один из видов.

| Дублёр | Что делает | Пример в магазине |
| --- | --- | --- |
| dummy | передаётся, но не используется | пустой `logger` в конструктор |
| stub | возвращает заданные ответы | `getUser` всегда отдаёт Аню |
| spy | записывает вызовы | сколько раз и с чем вызван `track` |
| mock | заранее задаёт ожидания и проверяет их | «`charge` будет вызван один раз с 1200» |
| fake | упрощённая, но рабочая реализация | корзина в памяти вместо базы |

Stub отвечает на вопрос «что вернуть», spy — «как вызывали», mock — «что должно было произойти». Fake — не подмена ответов, а другая реализация: хранилище в `Map` вместо базы данных ведёт себя как настоящее, но быстро.

## Инструменты Vitest

### vi.fn

Функция, которая записывает вызовы и возвращает то, что задали:

```js
const getUser = vi.fn().mockResolvedValue({ name: 'Аня' });   // stub
const onLogin = vi.fn();                                      // spy

await login(7);

expect(getUser).toHaveBeenCalledWith(7);
expect(onLogin).toHaveBeenCalledExactlyOnceWith('Аня');
```

В Jest то же — `jest.fn`, API совпадает.

### vi.spyOn

Шпион на существующем методе объекта: можно только наблюдать или подменить ответ.

```js
const spy = vi.spyOn(console, 'error').mockImplementation(() => {});
```

### vi.mock и подъём

`vi.mock` подменяет модуль целиком — например, аналитику, которая не должна слать события из тестов:

```js
vi.mock('./analytics.js', () => ({ track: vi.fn() }));
```

Vitest поднимает вызов `vi.mock` в начало файла, выше импортов: модуль должен быть подменён до того, как его загрузит тестируемый код. Отсюда ловушка. В проверке:

```js
const track = vi.fn();
vi.mock('./analytics.js', () => ({ track }));
```

упало с `Cannot access 'track' before initialization` и подсказкой Vitest: `make sure there are no top level variables inside, since this call is hoisted to top of the file`. Переменную, нужную фабрике, тоже поднимают:

```js
const { track } = vi.hoisted(() => ({ track: vi.fn() }));
vi.mock('./analytics.js', () => ({ track }));
```

В Jest `jest.mock` поднимается так же, а переменные для фабрики должны начинаться с `mock`.

### clear, reset, restore

Три способа сбросить моки, и их часто путают. В проверке шпион на `api.price` возвращал `1`, а `vi.fn(() => 'impl')` — подменённое `'stub'`:

| Вызов | Что сделал в проверке |
| --- | --- |
| `vi.clearAllMocks()` | стёр историю вызовов, подменённые ответы остались: `1` и `'stub'` |
| `vi.resetAllMocks()` | ещё и сбросил ответы к исходным реализациям: `1200` и `'impl'`, но метод ещё шпион |
| `vi.restoreAllMocks()` | вернул на объект настоящий метод |

В Vitest это включают в конфиге — `clearMocks`, `mockReset`, `restoreMocks`, — чтобы подмены не протекали между тестами.

## Фейковое время

Таймеры подменяют, чтобы не ждать настоящие секунды. Поиск с задержкой ввода:

```js
vi.useFakeTimers();

onInput('п'); onInput('пу'); onInput('пуэр');
vi.advanceTimersByTime(299);
expect(search).not.toHaveBeenCalled();
vi.advanceTimersByTime(1);
expect(search).toHaveBeenCalledExactlyOnceWith('пуэр');
```

Ловушка — таймеры внутри асинхронного кода. Функция повтора ждёт секунду, увеличивает счётчик и ждёт ещё секунду:

```js
async function retry(state) {
  await wait(1000); state.tries++;
  await wait(1000); state.tries++;
  state.done = true;
}
```

В проверке `vi.advanceTimersByTime(2000)` оставил `tries: 0`: синхронная промотка сработала первый таймер, но продолжение после `await` — микрозадача — ещё не выполнилось, и второй таймер не был создан. `await vi.advanceTimersByTimeAsync(2000)` прошёл всю цепочку: `tries: 2, done: true`. Правило: если между таймерами есть промисы — асинхронные варианты промотки.

«Сейчас» фиксируют отдельно: `vi.setSystemTime(new Date('2026-11-15T10:00:00Z'))`, и `new Date()` в коде возвращает это время.

## Сеть: MSW

Подменять `fetch` или модуль API — значит привязать тест к тому, **чем** код ходит в сеть. MSW перехватывает запросы на уровне сети: в Node.js — `fetch` и модули `http`, в браузере — через Service Worker. Как подключать MSW в тестах компонентов — `listen`, `resetHandlers`, `server.use` для ответа в одном тесте, — разобрано в [Тестировании React](/content/reactjs/testing-react). Здесь — два свойства, которые видно в проверке.

**Один обработчик — любой клиент.** Обработчик `http.get('*/api/products/7')` ответил и `fetch`, и axios: код не знает, что ответ подменён, и переход с одного клиента на другой тесты не ломает.

**Неописанный запрос по умолчанию уходит в сеть.** Политика `onUnhandledRequest` по умолчанию — `'warn'`: в проверке запрос к `/api/reviews/7` без обработчика дошёл до настоящего сервера и получил настоящий ответ, а тест прошёл. С `onUnhandledRequest: 'error'` запрос до сервера не дошёл, и тест упал:

```js
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
```

Так забытый эндпоинт обнаруживается сразу, а не превращается в тест, зависящий от стенда.

## Не перемокать

| Подменять | Не подменять |
| --- | --- |
| границы с внешним миром: сеть, время, сторонние SDK | свою логику |
| медленное и недетерминированное | то, что тестируешь |
| опасное: платежи, письма | соседние модули, которые можно взять настоящими |

Если подменить слишком много, тест проверяет моки: в [Стратегии тестирования](/content/testing-deploying/testing-strategy-and-pyramid) модульные тесты с моком API были зелёными, а карточка показывала цену в сто раз больше. Признаки перемокирования — тест повторяет реализацию строка за строкой, ломается при рефакторинге и не падает, когда ломается соседний модуль.

---

## Красные флаги в ответе

- **«Mock — любая подмена».** Это один вид дублёров; stub, spy и fake отвечают на другие вопросы.
- **«Замокаю `fetch`».** Тест привязан к клиенту; MSW подменяет сеть, а не способ запроса.
- **«`vi.mock` выполняется там, где написан».** Он поднимается в начало файла, переменные снаружи фабрики ещё не созданы.
- **«`clearAllMocks` возвращает настоящие методы».** Он стирает только историю вызовов, методы возвращает `restoreAllMocks`.
- **«MSW сам не пустит запрос в сеть».** По умолчанию неописанный запрос уходит в сеть с предупреждением.
- **«Чем больше моков, тем изолированнее и лучше».** Тест начинает проверять моки, а не код.

## Как спрашивают на собеседовании

::question
Чем отличаются stub, spy и mock?

#answer
Stub возвращает заранее заданные ответы, spy записывает, как его вызывали, mock заранее задаёт ожидания и проверяет их. Ещё есть dummy — заполнитель аргумента — и fake — упрощённая рабочая реализация, например хранилище в памяти.

#more
`vi.fn` и `jest.fn` совмещают роли: `mockResolvedValue` делает stub, `toHaveBeenCalledWith` — проверку шпиона. Различие важно не для названий, а для того, что проверяет тест: результат или взаимодействие.
::

::question
Почему сеть подменяют через MSW, а не мок `fetch`?

#answer
Мок `fetch` или модуля API привязывает тест к тому, чем код ходит в сеть. MSW перехватывает запросы на уровне сети: код делает настоящий запрос и получает ответ, заданный в тесте, через `fetch`, axios или любой клиент.

#more
Те же обработчики подходят для тестов, Storybook и локальной разработки. Политику `onUnhandledRequest` ставят в `'error'`: по умолчанию неописанный запрос уходит в настоящую сеть с предупреждением.
::

::question
Почему `vi.mock` не видит переменную, объявленную выше?

#answer
Vitest поднимает `vi.mock` в начало файла, выше импортов, чтобы модуль был подменён до загрузки тестируемого кода. Переменная, объявленная выше по тексту, в этот момент ещё не создана — `Cannot access before initialization`.

#more
Нужные фабрике значения создают через `vi.hoisted` — он тоже поднимается. В Jest `jest.mock` поднимается так же, и переменные для фабрики должны начинаться с `mock`.
::

::question
Чем `clearAllMocks` отличается от `resetAllMocks` и `restoreAllMocks`?

#answer
`clearAllMocks` стирает историю вызовов, но оставляет подменённые ответы. `resetAllMocks` ещё и сбрасывает ответы к исходным реализациям. `restoreAllMocks` возвращает на объекты настоящие методы, подменённые через `spyOn`.

#more
Чтобы подмены не протекали между тестами, это включают в конфиге: `clearMocks`, `mockReset`, `restoreMocks` — или вызывают в `afterEach`.
::

::question
Как тестировать код с таймерами?

#answer
Фейковыми таймерами: `vi.useFakeTimers`, затем `advanceTimersByTime` проматывает время без ожидания, а `setSystemTime` фиксирует текущую дату.

#more
Если между таймерами есть промисы — `await` внутри повтора или поллинга, — синхронная промотка не выполняет продолжения, и следующий таймер не создаётся. Для этого есть `advanceTimersByTimeAsync` и `runAllTimersAsync`.
::

::question
Чем опасно избыточное мокирование?

#answer
Тест начинает проверять моки, а не взаимодействие частей: он зелёный, когда настоящий модуль ведёт себя иначе, и ломается при рефакторинге, когда поведение не изменилось.

#more
Подменяют границы — сеть, время, сторонние SDK, — а свои модули оставляют настоящими. Если для теста нужно подменить пять модулей, это сигнал о слишком связанном коде.
::

## Практика

::practice{title="Повтор запроса не досчитывает попытки"}
Функция повторяет запрос через секунду после ошибки, до двух раз. Тест с фейковыми таймерами всегда видит ноль попыток:

```js
vi.useFakeTimers();
retry(state);
vi.advanceTimersByTime(2000);
expect(state.tries).toBe(2);   // получено 0
```

#solution
Между таймерами стоит `await`. Синхронная промотка срабатывает первый таймер, но продолжение после `await` — микрозадача — выполнится только после неё, поэтому второй таймер ещё не создан. Нужна асинхронная промотка:

```js
test('две попытки', async () => {
  vi.useFakeTimers();
  retry(state);
  await vi.advanceTimersByTimeAsync(2000);
  expect(state).toEqual({ tries: 2, done: true });
});
```

В проверке синхронный вариант оставил `tries: 0`, а асинхронный прошёл всю цепочку.
::

::practice{title="Тесты зависят от стенда"}
Тесты страницы товара иногда падают по ночам, когда стенд перезапускается. MSW подключён, обработчики есть для товара, но не для отзывов.

#solution
Политика MSW по умолчанию — `'warn'`: запрос без обработчика уходит в настоящую сеть с предупреждением. В проверке запрос к отзывам без обработчика дошёл до настоящего сервера и тест прошёл — пока сервер был жив. Нужно:

```js
beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));

const server = setupServer(
  http.get('*/api/products/:id', () => HttpResponse.json(product)),
  http.get('*/api/products/:id/reviews', () => HttpResponse.json([])),
);
```

С `'error'` запрос в проверке до сервера не дошёл, и тест упал сразу — забытый эндпоинт виден при первом же прогоне, а тесты больше не зависят от стенда.
::
