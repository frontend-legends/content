# Тест-раннеры

Чем запускают тесты: что делает раннер, Vitest и Jest, встроенный `node:test`, окружения DOM, изоляция файлов, фильтры и режим наблюдения. Спрашивают, чем Vitest отличается от Jest, зачем нужен jsdom и хватает ли его для всех тестов. Глубже — почему Jest спотыкается на ESM и TypeScript, почему забытый `test.only` опасен и почему тесты в одном файле влияют друг на друга, а в разных — нет.

::tldr
- **Раннер находит тестовые файлы, запускает их изолированно, даёт `expect`, моки, покрытие и отчёт.** Для фронтенда это обычно Vitest или Jest.
- **Vitest использует трансформацию и конфиг Vite:** ESM и TypeScript работают сразу, API почти совпадает с Jest. Jest исторически строился на CommonJS и Babel, ESM и TypeScript требуют настройки.
- **В Node.js нет DOM:** jsdom и happy-dom его эмулируют, но без раскладки и отрисовки. Размеры, видимость и стили проверяют в настоящем браузере.
- **Каждый файл — отдельное окружение,** а тесты внутри файла делят модули и глобальные переменные. Зависимость тестов друг от друга — источник нестабильности.
- **Фильтры ускоряют цикл:** по имени, по файлу, по изменённым модулям. Забытый `.only` локально тихо пропускает остальные тесты, в CI Vitest на нём падает.
::

---

## Что делает раннер

Сквозной пример — тесты магазина: расчёт корзины, форматирование цен, компонент кнопки «Купить».

Раннер берёт на себя инфраструктуру:

- **находит** файлы по шаблону — `*.test.ts`, `*.spec.ts`;
- **запускает** их параллельно в отдельных воркерах и окружениях;
- даёт **проверки** — `expect(value).toBe(...)`, `toEqual`, `toThrow`;
- даёт **моки** и подмену времени (подробно — в [Моках и дублёрах](/content/testing-deploying/mocking-and-test-doubles));
- считает **покрытие** (подробно — в [Покрытии и TDD](/content/testing-deploying/coverage-and-tdd));
- подставляет **DOM** для компонентов;
- **следит** за файлами и перезапускает затронутые тесты.

### Анатомия теста

```js
import { describe, test, expect, beforeEach } from 'vitest';

describe('корзина', () => {
  let cart;
  beforeEach(() => { cart = new Cart(); });   // свежая корзина перед каждым тестом

  test('суммирует количество', () => {
    cart.add('tea'); cart.add('cup', 3);
    expect(cart.count()).toBe(4);
  });
});
```

`describe` группирует тесты, `test` (или `it`) — один случай, `beforeEach` и `afterEach` — подготовка и очистка вокруг каждого теста, `beforeAll` и `afterAll` — один раз на группу.

## Vitest и Jest

| | Jest | Vitest |
| --- | --- | --- |
| Откуда | Meta, эпоха webpack и Babel | команда Vite |
| Модули | CommonJS по умолчанию, ESM — с настройкой | ESM сразу |
| TypeScript | через ts-jest, Babel или SWC | сразу, трансформацией Vite |
| Конфиг | свой, со своими трансформациями | общий с Vite: алиасы, плагины |
| API | стандарт де-факто | совместим с Jest: `vi.fn` вместо `jest.fn` |

В проверке один и тот же тест на ESM:

```js
import { sum } from './sum.js';
test('сумма', () => { expect(sum(2, 3)).toBe(5); });
```

Jest без настройки отказался его загружать: `Must use import to load ES Module` — и предложил трансформацию через Babel, флаг `--experimental-vm-modules` или более новый Node.js. С флагом тест прошёл. Тест на TypeScript Jest не запустил вовсе — нужны ts-jest, Babel или SWC. Vitest с `globals: true` запустил оба файла без изменений: и ESM, и TypeScript, и глобальные `test` и `expect`, как в Jest.

| Событие | Версии |
| --- | --- |
| Jest сам загружает ESM через `require(esm)` | Jest 30 на Node.js 24.9 и новее |
| в проверке | Jest 30.5, Vitest 5.1, Node.js 24.7 |

Актуально на ноябрь 2026.

Главная причина выбора Vitest в Vite-проектах — **одна трансформация для приложения и тестов**: те же алиасы, плагины, обработка CSS и `import.meta.env`. С Jest эту конфигурацию повторяют отдельно, и она расходится со сборкой. Jest остаётся разумным выбором в существующих проектах на нём и там, где нет Vite, — например, в React Native.

### Другие раннеры

- **`node:test`** — встроенный в Node.js: без зависимостей, с моками и подменой времени. В проверке `node --test` запустил тест на TypeScript без сборки — Node.js сам удаляет типы. Хорош для библиотек и утилит без DOM.
- **Bun test** и **Deno test** — встроенные раннеры своих рантаймов, API похож на Jest.
- **Mocha с Chai**, **Jasmine** — старые раннеры, в новых проектах встречаются редко.

## Окружения DOM

Тесты идут в Node.js, где нет `document` и `window`. Раннер подставляет эмуляцию для файла или для всего проекта:

```js
// @vitest-environment jsdom
```

```js
// vitest.config.js
export default { test: { environment: 'jsdom' } };
```

- **jsdom** — полная и зрелая реализация DOM на JavaScript;
- **happy-dom** — легче и быстрее, покрывает большинство случаев, но местами отличается от стандарта.

В проверке тест в окружении `node` увидел `typeof document === 'undefined'`, а в jsdom и happy-dom — работающий DOM. Но кнопка со стилем `width: 200px` в jsdom вернула ширину `0`: раскладки и отрисовки нет. Поэтому размеры, видимость, перекрытие элементов, прокрутку и CSS проверяют в настоящем браузере — e2e или браузерным режимом Vitest (подробно — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing)).

## Изоляция

По умолчанию каждый тестовый файл получает своё окружение: модули загружаются заново, глобальные переменные чистые. Внутри файла тесты делят одни и те же модули.

В проверке модуль-счётчик `inc()` вернул в файле `a` сначала `1`, затем `2` — второй тест видел состояние после первого. Файл `b` получил свежий модуль (`inc()` снова `1`) и не увидел `globalThis.leak`, выставленную в `a`.

Отсюда правило: **тест не должен зависеть от другого теста**. Состояние сбрасывают в `beforeEach` или создают заново в каждом тесте, иначе тест проходит в одном порядке и падает в другом — особенно когда его запускают отдельно фильтром. Полная изоляция стоит времени: опции `isolate: false` и пулы потоков ускоряют прогон ценой общего состояния.

## Фильтры и наблюдение

```bash
vitest                     # режим наблюдения: перезапуск затронутых тестов
vitest run cart            # один прогон, файлы с «cart» в пути
vitest run -t "скидка"     # только тесты с «скидка» в имени
vitest related price.js    # только тесты, зависящие от файла
```

В проверке `-t "скидка"` запустил два теста из трёх, а `vitest related price.js` — один тестовый файл из двух: `Affected 1 of 2 test files (related to price.js)`. Раннер знает граф импортов, поэтому в режиме наблюдения после правки файла перезапускает только зависящие от него тесты.

### Забытый `.only`

`test.only` и `describe.only` удобны при отладке, но опасны в коммите: остальные тесты файла молча пропускаются. В проверке файл с `test.only` и сломанным соседним тестом локально прошёл зелёным. С переменной `CI=true` Vitest упал с `Unexpected .only modifier` — в CI `.only` запрещён по умолчанию. Для Jest и других раннеров то же правило ставят линтером: `no-only-tests` или правило плагина раннера.

## Красные флаги в ответе

- **«Vitest — это Jest, только быстрее».** Главное — общая с Vite трансформация и ESM без настройки.
- **«jsdom — это браузер».** В нём нет раскладки и отрисовки: ширина элемента — ноль.
- **«Порядок тестов в файле не важен, они независимы».** Тесты в файле делят модули — состояние нужно сбрасывать.
- **«`test.only` в коммите — мелочь».** Остальные тесты молча не запускаются.
- **«Для тестов нужен Jest или Vitest».** Для кода без DOM хватает встроенного `node:test`.

## Как спрашивают на собеседовании

::question
Что делает тестовый раннер?

#answer
Находит тестовые файлы, запускает их параллельно в изолированных окружениях, даёт проверки `expect`, моки и подмену времени, считает покрытие, подставляет эмуляцию DOM и перезапускает затронутые тесты в режиме наблюдения.

#more
Раннер знает граф импортов, поэтому может запустить только тесты, связанные с изменённым файлом, — `vitest related`. Отчёты в JUnit или JSON подхватывает CI.
::

::question
Чем Vitest отличается от Jest?

#answer
Vitest использует трансформацию и конфиг Vite: ESM и TypeScript работают сразу, алиасы и плагины общие с приложением. Jest исторически строился на CommonJS и Babel, ESM и TypeScript требуют настройки. API Vitest почти совпадает с Jest.

#more
Переход обычно сводится к замене `jest.fn` на `vi.fn` и включению `globals: true`. Jest разумен в существующих проектах и там, где нет Vite. Для кода без DOM есть встроенный `node:test`.
::

::question
Зачем нужен jsdom и хватает ли его?

#answer
Тесты идут в Node.js без `document` и `window`, а jsdom и happy-dom эмулируют DOM, чтобы рендерить компоненты и кликать по ним без браузера.

#more
Раскладки и отрисовки в эмуляции нет: размеры — нули, видимость и перекрытие не проверить. Это делают в настоящем браузере — e2e или браузерным режимом Vitest.
::

::question
Почему тест проходит в общем прогоне и падает отдельно?

#answer
Скорее всего, он зависит от состояния, которое оставил предыдущий тест того же файла: тесты внутри файла делят модули и глобальные переменные. При запуске по фильтру этого состояния нет.

#more
Решение — сбрасывать состояние в `beforeEach` или создавать его в каждом тесте. Между файлами раннер изолирует окружение сам: модули загружаются заново.
::

::question
Чем опасен `test.only`?

#answer
Он запускает только отмеченный тест, а остальные молча пропускает. Забытый в коммите, он делает набор зелёным, даже если сломанные тесты рядом.

#more
Vitest в CI падает на `.only` с `Unexpected .only modifier` — опция `allowOnly` по умолчанию выключена при `CI=true`. В Jest и других раннерах ставят правило линтера.
::

## Практика

::practice{title="Тесты Jest не видят import"}
Проект перевели на `"type": "module"`, и все тесты Jest упали с `Must use import to load ES Module`. Сборка через Vite работает.

#solution
Jest загружает тесты как CommonJS, а файлы стали ESM. Варианты:

```bash
# 1. включить экспериментальные VM-модули Node.js
NODE_OPTIONS=--experimental-vm-modules npx jest

# 2. трансформировать в CommonJS: babel-jest или @swc/jest

# 3. перейти на Vitest — та же трансформация, что у сборки
npx vitest run
```

В проверке тест упал в Jest без настройки, прошёл с `--experimental-vm-modules` и сразу прошёл в Vitest — вместе с тестом на TypeScript, который Jest без ts-jest или Babel не запустил. В проекте на Vite обычно проще третий вариант.
::

::practice{title="Сломанный тест не ловится"}
В файле с тестами корзины три теста, один сломан. Локально и в CI на Jest всё зелёное. Через неделю обнаружили, что в файле стоял `test.only`.

#solution
`.only` запускает только отмеченный тест, остальные пропускаются без ошибки. Защита — запретить его в CI:

```js
// vitest: в CI по умолчанию allowOnly: false
// eslint для Jest
rules: { 'jest/no-focused-tests': 'error' }
```

В проверке файл с `test.only` и сломанным соседом локально был зелёным, а с `CI=true` Vitest упал с `Unexpected .only modifier`. Правило линтера ловит это ещё раньше — в редакторе и git-хуке.
::
