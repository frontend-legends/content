# Хостинг и платформы

Где живёт собранный фронтенд: статика на CDN, серверный процесс для SSR, serverless- и edge-функции, платформы вроде Vercel, Netlify и Cloudflare и их связь с мета-фреймворками. Спрашивают, чем выкладка статики отличается от SSR, зачем SPA резервная отдача `index.html` и что такое холодный старт. Глубже — почему после выкладки страница пустая с ошибкой про MIME-тип, почему сайт в подпапке не находит скрипты и что теряется на edge.

::tldr
- **Главное различие — статика или сервер:** SPA и статически сгенерированный сайт — это файлы, которые раздаёт CDN; SSR и серверные компоненты требуют процесса, который рендерит HTML на запрос.
- **SPA нужна резервная отдача `index.html`:** маршруты рисует клиент, и прямой заход на `/products/7` без неё — 404. Но отдавать HTML вместо отсутствующего скрипта нельзя — браузер откажется его выполнять.
- **Serverless-функции** запускаются на запрос и масштабируются сами, цена — холодный старт. **Edge-функции** выполняются рядом с пользователем, но в урезанном рантайме на веб-API, без части Node.js.
- **Сайт в подпапке** собирают с `base`, иначе он ищет скрипты в корне домена.
- **Мета-фреймворки сами делят приложение** на статику и функции и выкладываются через адаптеры под платформу.
::

## Статика или сервер

Сквозной пример — магазин: каталог как SPA, маршрут `/products/7`, позже — SSR для страниц товаров ради SEO.

| | Статика | Сервер |
| --- | --- | --- |
| Что выкладываем | файлы: HTML, JavaScript, CSS, картинки | работающий процесс |
| Где живёт | CDN | сервер, контейнер, функции |
| Масштабирование | CDN раздаёт файлы с любого узла | нужно масштабировать процессы |
| Цена | дёшево | дороже, плюс эксплуатация |
| Когда | SPA, статически сгенерированные сайты | SSR, серверные компоненты, логика на сервере |

В проверке `vite build` дал ровно два файла — `index.html` и `assets/index-[hash].js`. Это и есть статическое приложение: его можно положить на любой хостинг файлов. Какой рендеринг даёт статику, а какой требует сервера, — в [Рендеринге и гидратации React](/content/reactjs/rendering-and-hydration).

## Статический хостинг

Платформы: **Cloudflare Pages**, **Netlify**, **Vercel**, **GitHub Pages**, облачное хранилище с CDN — **S3 и CloudFront**, **Cloud Storage и Cloud CDN**.

### Резервная отдача для SPA

У SPA один `index.html`, а маршруты обрабатывает клиентский роутер (подробно — в [Маршрутизации React](/content/reactjs/routing)). Переход по ссылке внутри приложения работает, а прямой заход или обновление страницы `/products/7` идёт на сервер — а такого файла нет.

В проверке:

- **без резервной отдачи** прямой заход на `/products/7` вернул **404**;
- **с отдачей `index.html` для путей без расширения** — 200 и «Товар 7».

Настройка на платформах:

```text
# Netlify: _redirects
/*    /index.html   200
```

```json
{ "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] }
```

Второй пример — `vercel.json`. Cloudflare Pages включает такой режим сам, если в сборке нет `404.html`. На GitHub Pages переписывания нет — используют копию `index.html` под именем `404.html` или маршрутизацию через `#`.

### Ловушка: HTML вместо скрипта

Правило «любой путь → `index.html`» ломается на ассетах. После выкладки открытая вкладка или закешированный HTML ссылаются на старый чанк `index-old123.js`, которого больше нет. Сервер отдаёт вместо него `index.html` со статусом 200, и браузер отказывается его выполнять:

```text
Failed to load module script: Expected a JavaScript-or-Wasm module script
but the server responded with a MIME type of "text/html".
```

В проверке так и вышло — пустая страница с этой ошибкой. При отдаче `index.html` только для путей без расширения отсутствующий файл получил честный 404: ошибку видно в мониторинге, и приложение может перезагрузиться. Как сохранять старые чанки после выкладки — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching).

### Подпапка и base

Сайт выкладывают не в корень домена — `shop.example/shop/` или `user.github.io/repo/`. Vite по умолчанию пишет в HTML абсолютные пути `/assets/…`, и браузер ищет скрипт в корне домена. В проверке такая сборка в подпапке `/shop/` дала пустую страницу и 404 на скрипт. Сборка с `--base /shop/` записала пути `/shop/assets/…` и открыла `/shop/products/7` как «Товар 7». Роутеру тоже передают базовый путь — в проверке код учитывал `import.meta.env.BASE_URL`.

## Сервер

SSR и серверные компоненты требуют процесса, который рендерит HTML на каждый запрос или по кешу. Варианты:

- **долгоживущий Node.js-сервер** — Render, Railway, Fly.io, свой сервер или контейнер в облаке (подробно — в [Контейнерах и Docker](/content/testing-deploying/containers-and-docker));
- **serverless-функции** — Vercel Functions, Netlify Functions, AWS Lambda, Cloud Run;
- **edge-функции** — Cloudflare Workers, Vercel и Netlify Edge Functions, Deno Deploy.

### Serverless

Функция не работает постоянно: платформа поднимает экземпляр на запрос, держит его какое-то время и гасит при простое. Плюсы — масштабирование без настройки и оплата за использование. Цена:

- **холодный старт** — первый запрос после простоя ждёт загрузку рантайма и кода, поэтому тяжёлые зависимости в функции ощутимы;
- **ограничения** — время выполнения, память, размер пакета;
- **нет общего состояния** между вызовами: кеш в памяти, соединения с базой и WebSocket живут не дольше экземпляра.

### Edge

Edge-функции выполняются в точках присутствия CDN рядом с пользователем — короткий путь до первого байта, где бы он ни был. Рантайм построен на веб-API — `fetch`, `Request`, `Response`, `crypto.subtle`, потоки — и запускает код в изолятах V8, а не в отдельных процессах Node.js, поэтому стартует быстро. Цена:

- **урезанный Node.js** — часть модулей недоступна или эмулируется, нативные расширения не работают;
- **лимиты** на процессорное время и размер кода;
- **данные далеко** — функция рядом с пользователем, а база в одном регионе: запрос к ней съедает выигрыш. Edge хорош для перенаправлений, A/B-разбиения, проверки токена, персонализации по заголовкам и для кешируемых ответов.

## Мета-фреймворки и платформы

Мета-фреймворки сами решают, что станет статикой, а что — функцией (подробно — в [Мета-фреймворках](/content/ecosystem-libs/meta-frameworks)):

- **Next.js** глубже всего интегрирован с Vercel, но работает в Node.js-сервере и контейнере (`output: 'standalone'`) и через адаптеры на других платформах; статический экспорт — `output: 'export'`, без серверных функций;
- **Nuxt** собирается сервером Nitro с пресетами под Node.js, Vercel, Netlify, Cloudflare и другие;
- **Astro**, **SvelteKit**, **React Router** — адаптеры под платформы, по умолчанию статика или Node.js.

Чем глубже приложение использует особенности платформы — кеш, изображения, edge-middleware, — тем сложнее переезд. Это та же цена удобства, что у сервисов авторизации (подробно — в [Библиотеках авторизации](/content/ecosystem-libs/auth-libraries)).

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| SPA или статически сгенерированный сайт | статический хостинг на CDN |
| SSR с мета-фреймворком, быстрый старт | платформа фреймворка: Vercel, Netlify, Cloudflare |
| ответы рядом с пользователем, лёгкая логика | edge-функции |
| долгие соединения, свой рантайм, контроль | Node.js-сервер или контейнер |
| требования к данным и размещению | своё облако или свои серверы |

---

## Красные флаги в ответе

- **«SPA — это сервер, который рендерит страницы».** Это файлы, нужна только раздача и резервная отдача `index.html`.
- **«Настрою отдачу `index.html` на любой путь».** Отсутствующие скрипты получат HTML со статусом 200 и ошибку MIME-типа.
- **«Выложу в подпапку как есть».** Без `base` приложение ищет ассеты в корне домена.
- **«Edge — это быстрее, переведём всё на edge».** База остаётся в одном регионе, и запросы к ней съедают выигрыш.
- **«В serverless сохраню кеш в памяти».** Экземпляры живут недолго и не делят память.

## Как спрашивают на собеседовании

::question
Чем выкладка статики отличается от выкладки SSR?

#answer
Статика — это файлы, которые раздаёт CDN: дёшево и масштабируется само. SSR требует процесса, который рендерит HTML на запрос, — сервера, контейнера или функций, — и его нужно масштабировать и сопровождать.

#more
Выбор следует из стратегии рендеринга. Мета-фреймворки часто смешивают: статически собранные страницы на CDN и функции для динамических маршрутов.
::

::question
Зачем SPA резервная отдача `index.html`?

#answer
Маршруты SPA обрабатывает клиентский роутер, а файлов для них нет. Без резервной отдачи прямой заход или обновление `/products/7` даёт 404 — сервер должен отдавать `index.html` для таких путей.

#more
Отдавать `index.html` нужно только для путей страниц, а не для ассетов. Иначе отсутствующий скрипт получает HTML со статусом 200, и браузер падает с ошибкой MIME-типа — пустая страница вместо понятного 404.
::

::question
Что такое холодный старт serverless?

#answer
Задержка первого запроса, когда платформа поднимает новый экземпляр функции после простоя или при росте нагрузки: загрузка рантайма, кода и зависимостей.

#more
Её уменьшают лёгкими зависимостями, меньшим пакетом, рантаймами на изолятах и платными «тёплыми» экземплярами. У serverless нет общего состояния между вызовами — кеш в памяти и соединения живут не дольше экземпляра.
::

::question
Что такое edge-функции и в чём компромисс?

#answer
Код, который выполняется в точках присутствия CDN рядом с пользователем, в рантайме на веб-API и изолятах V8. Быстрый старт и короткий путь до пользователя.

#more
Цена — урезанный Node.js, лимиты на время и размер и удалённость от данных: если функция ходит в базу в другом регионе, выигрыш теряется. Edge подходит для перенаправлений, проверки токена, A/B-разбиения и кешируемых ответов.
::

::question
Почему сайт в подпапке открывается пустым?

#answer
Сборка по умолчанию пишет абсолютные пути к ассетам от корня домена, и браузер ищет скрипт в `/assets/…`, а не в `/shop/assets/…`. Скрипт получает 404, страница пустая.

#more
Сборку делают с базовым путём — `base: '/shop/'` в Vite, `basePath` в Next.js, — и передают его роутеру. Это частая проблема на GitHub Pages, где сайт лежит в `/имя-репозитория/`.
::

## Практика

::practice{title="Пустая страница после выкладки"}
После очередной выкладки часть пользователей видит пустую страницу. В консоли: `Failed to load module script: Expected a JavaScript-or-Wasm module script but the server responded with a MIME type of "text/html"`. На хостинге настроено «любой путь → `/index.html`».

#solution
У пользователей закешированный или открытый старый `index.html`, который ссылается на чанк прошлой сборки. Файла больше нет, а правило отдаёт вместо него `index.html` со статусом 200 — браузер не выполняет HTML как модуль. В проверке именно так получилась пустая страница.

```js
// резервная отдача только для путей страниц
if (!fileExists && !extname(path)) return sendIndexHtml();
return notFound();
```

С таким правилом отсутствующий чанк в проверке получил честный 404. Дальше — две меры: хранить ассеты нескольких прошлых сборок и не кешировать `index.html` (подробно — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching)), а в приложении ловить ошибку загрузки чанка и перезагружать страницу.
::

::practice{title="Сайт на GitHub Pages не грузится"}
Приложение выложили на `user.github.io/shop/`. Главная пустая, в сети 404 на `/assets/index-….js`. Локально всё работает.

#solution
Сборка ссылается на ассеты от корня домена — `user.github.io/assets/…`, — а сайт лежит в `/shop/`. В проверке такая сборка в подпапке дала пустую страницу. Собирают с базовым путём:

```js
// vite.config.js
export default { base: '/shop/' };
```

```js
// роутеру тот же базовый путь
createBrowserRouter(routes, { basename: import.meta.env.BASE_URL });
```

В проверке сборка с `--base /shop/` записала пути `/shop/assets/…` и открыла `/shop/products/7`. Для прямых заходов на маршруты GitHub Pages нужна копия `index.html` под именем `404.html` — переписывания путей там нет.
::
