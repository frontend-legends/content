# Контейнеры и Docker

**Контейнер** упаковывает приложение вместе с его зависимостями и окружением в переносимую единицу, которая одинаково работает где угодно. Для фронтенда это решает «у меня работает» и нужно при своей инфраструктуре. На собесе спрашивают суть и multi-stage сборку.

---

## Что такое контейнер

Контейнер - изолированный пакет: код + зависимости + рантайм + системные библиотеки. Запускается одинаково на ноутбуке, на staging и в проде.

```
"работает у меня" → контейнер → "работает везде одинаково"
```

В отличие от виртуальной машины, контейнеры **лёгкие**: они разделяют ядро ОС хоста, а не тащат целую гостевую ОС - поэтому стартуют за секунды и занимают мало.

| | Контейнер | Виртуальная машина |
|--|-----------|--------------------|
| Изоляция | процесс + namespace | полная ОС |
| Вес | мегабайты, секунды | гигабайты, минуты |
| Ядро | общее с хостом | своё |

---

## Основы Docker

| Понятие | Что это |
|---------|---------|
| **Image** | неизменяемый шаблон (снимок файловой системы + команда запуска) |
| **Container** | запущенный экземпляр образа |
| **Dockerfile** | рецепт сборки образа |
| **Registry** | хранилище образов (Docker Hub, GHCR) |

## Фронтенд в контейнере

Здесь главная идея для собеса - **multi-stage build**. Для сборки фронтенда нужен Node и все dev-зависимости, но в **финальном** образе они не нужны - там должны лежать только готовые файлы.

```dockerfile
# Стадия 1: сборка (нужен Node и зависимости)
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build          # → /app/dist

# Стадия 2: раздача (только nginx + собранные файлы)
FROM nginx:alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

<b class="text-on-semi-light">Зачем multi-stage</b> - <span class="text-gray">Без него в образ попали бы Node, `node_modules` и исходники - сотни мегабайт и лишняя поверхность атаки. Multi-stage **отбрасывает** стадию сборки и кладёт в финальный образ только `dist` + лёгкий веб-сервер (nginx на Alpine - несколько мегабайт). Меньше образ - быстрее деплой, безопаснее.</span>

## nginx для SPA

Статику раздаёт веб-сервер (обычно **nginx**). Для SPA ему нужен **history fallback** - отдавать `index.html` на любой путь ([хостинг](/content/testing-deploying/hosting-and-platforms)):

```nginx
location / {
  try_files $uri $uri/ /index.html;  # неизвестный путь → index.html (SPA-роутинг)
}
```

Для **SSR**-приложения вторая стадия другая: вместо nginx запускают сам Node-сервер (`CMD ["node", "server.js"]`).

---

## Слои и кеш

Образ состоит из **слоёв**, и Docker их кеширует. Поэтому `COPY package*.json` и `npm ci` ставят **до** копирования всего кода: пока зависимости не менялись, этот тяжёлый слой берётся из кеша, а пересобирается только при изменении `package.json`. `.dockerignore` исключает `node_modules`, `.git` из контекста сборки.

## Когда контейнеры нужны

```
Статика на Vercel/Netlify           → Docker НЕ нужен (платформа сама раздаёт)
Своя инфра / Kubernetes             → контейнеры
Нужен полный контроль над окружением → контейнеры
SSR на своём сервере                 → контейнер с Node
Единое окружение dev = prod          → контейнеры
```

<b class="text-on-semi-light">Не каждому фронтенду нужен Docker</b> - <span class="text-gray">Если деплоишь статику на Vercel/Netlify - они сами всё раздают, контейнер избыточен. Docker оправдан при своей инфраструктуре, оркестрации (Kubernetes), строгом паритете окружений или контейнеризованном SSR.</span>

---

## Оркестрация

Когда контейнеров много, ими управляет **оркестратор** - **Kubernetes** (масштабирование, рестарты, балансировка, rolling-деплои). Это в основном зона DevOps; фронтендеру достаточно понимать, что его образ - один из сервисов в кластере.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое контейнер и чем отличается от VM?</b>
<span class="text-gray">Переносимый пакет приложения с зависимостями и окружением, работающий одинаково везде. В отличие от VM, контейнеры разделяют ядро хоста - лёгкие, стартуют за секунды.</span>

<b class="text-on-semi-light">Зачем multi-stage build для фронтенда?</b>
<span class="text-gray">Сборка требует Node и dev-зависимостей, но в финальном образе они не нужны. Multi-stage собирает в одной стадии, а в финальную кладёт только dist + лёгкий nginx - маленький и безопасный образ.</span>

<b class="text-on-semi-light">Как Docker раздаёт SPA и зачем nginx-конфиг?</b>
<span class="text-gray">Готовые файлы раздаёт nginx; нужен history fallback (`try_files ... /index.html`), чтобы любой путь SPA отдавал index.html, иначе прямой заход даст 404.</span>

<b class="text-on-semi-light">Почему package.json копируют до остального кода?</b>
<span class="text-gray">Ради кеша слоёв Docker: пока зависимости не менялись, тяжёлый слой `npm ci` берётся из кеша, и пересборка идёт только при изменении package.json.</span>

<b class="text-on-semi-light">Всегда ли фронтенду нужен Docker?</b>
<span class="text-gray">Нет. Для статики на Vercel/Netlify он избыточен - платформа сама раздаёт. Docker нужен при своей инфраструктуре, Kubernetes, строгом паритете окружений или контейнеризованном SSR.</span>
