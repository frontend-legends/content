# Контейнеры и Docker

Как упаковать фронтенд в контейнер: чем контейнер отличается от виртуальной машины, образы и Dockerfile, многоэтапная сборка, кеш слоёв и `.dockerignore`, nginx для SPA, конфигурация при запуске и когда Docker фронтенду вообще не нужен. Спрашивают, что такое контейнер, зачем многоэтапная сборка и почему `package.json` копируют раньше остального кода. Глубже — почему сборка образа тащит десятки мегабайт контекста, почему nginx отдаёт HTML вместо скрипта и как один образ работает на стенде и в продакшене.

::tldr
- **Контейнер — процесс в изолированном окружении со своей файловой системой из образа:** код, рантайм и библиотеки едут вместе, и приложение одинаково работает на ноутбуке, в CI и в продакшене. Ядро — общее с хостом, поэтому контейнер легче виртуальной машины.
- **Многоэтапная сборка:** Node.js и зависимости нужны только для сборки, а итоговый образ — веб-сервер и папка `dist`. Меньше размер и поверхность атаки.
- **Кеш слоёв:** `package.json` и lock-файл копируют и ставят зависимости до копирования кода — правка кода не переустанавливает зависимости. `.dockerignore` не пускает `node_modules` и `.git` в контекст сборки.
- **nginx для SPA:** `try_files $uri $uri/ /index.html` для маршрутов, честный 404 для `/assets/` и правильный `Cache-Control`.
- **Один образ — разные окружения:** конфигурация приходит переменными окружения при запуске. Для статики на Vercel или Netlify Docker не нужен.
::

## Что такое контейнер

Сквозной пример — тот же магазин, но выкладывается не на платформу, а в Kubernetes компании рядом с бэкендом.

Контейнер — обычный процесс хоста, изолированный механизмами ядра: своё дерево файлов из образа, свои процессы, сеть и ограничения ресурсов. Всё, что нужно приложению, лежит в образе, поэтому «у меня работает» превращается в «работает везде, где запущен этот образ».

| | Контейнер | Виртуальная машина |
| --- | --- | --- |
| Изоляция | процесс с пространствами имён и cgroups | целая гостевая ОС на гипервизоре |
| Ядро | общее с хостом | своё |
| Размер и старт | мегабайты, доли секунды | гигабайты, десятки секунд |
| Граница безопасности | слабее, общее ядро | сильнее |

На macOS и Windows Docker запускает лёгкую Linux-машину, и контейнеры работают внутри неё — ядро у них Linux.

## Основы Docker

| Понятие | Что это |
| --- | --- |
| образ | неизменяемый набор слоёв файловой системы и команда запуска |
| контейнер | запущенный экземпляр образа |
| Dockerfile | рецепт сборки образа по шагам |
| реестр | хранилище образов: Docker Hub, GitHub Container Registry, реестр облака |
| тег | имя версии образа: `shop-web:1.4.2` |

Каждый шаг Dockerfile даёт слой. Слои кешируются и переиспользуются между образами.

## Многоэтапная сборка

Для сборки фронтенда нужны Node.js, зависимости и исходники, а для раздачи — только готовые файлы и веб-сервер. Многоэтапная сборка разделяет эти задачи:

```text
# стадия 1: сборка
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# стадия 2: раздача
FROM nginx:1.29-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
```

Из первой стадии во вторую копируется только `dist`, а Node.js, `node_modules` и исходники остаются в выброшенной стадии. В проверке в итоговом образе `command -v node` ничего не нашёл, а в образе стадии сборки — нашёл. По `docker image inspect` стадия сборки весила 63 МБ, итоговый образ — 26 МБ, и это проект без зависимостей. В настоящем проекте с Vite и сотнями пакетов разница в разы больше.

Меньший образ быстрее загружается в реестр и на узлы, а без Node.js и исходников в нём меньше того, что можно атаковать и что нужно обновлять из-за уязвимостей.

## Кеш слоёв и контекст

### Порядок шагов

Docker перестраивает слой, если изменились входные файлы шага, и все слои после него. Поэтому зависимости ставят до копирования кода:

```text
COPY package*.json ./
RUN npm ci          ← пересобирается только при изменении package.json или lock-файла
COPY . .
RUN npm run build   ← пересобирается при любой правке кода
```

В проверке правка `src/main.js` пересобрала образ с отметкой `CACHED` у шага `RUN npm ci`, а правка `package.json` заставила его выполниться снова. При обратном порядке — `COPY . .` раньше `npm ci` — каждое изменение кода переустанавливало бы все зависимости.

### .dockerignore

Перед сборкой Docker отправляет демону **контекст** — папку проекта. В проверке без `.dockerignore` в контекст ушла папка `node_modules` на 20 МБ, а с ним — меньше мегабайта:

```text
# .dockerignore
node_modules
.git
dist
.env*
```

Кроме скорости это защита: без `.dockerignore` команда `COPY . .` кладёт в образ `.env` с секретами и историю git.

## nginx для SPA

Статику в контейнере обычно раздаёт :term[nginx]{def="веб-сервер и обратный прокси для статики и балансировки"}. Для :term[SPA]{def="одностраничное приложение: страница загружается раз, а экраны меняет JavaScript"} нужна резервная отдача `index.html` для маршрутов (подробно — в [Хостинге и платформах](/content/testing-deploying/hosting-and-platforms)), но не для ассетов:

```text
server {
  listen 80;
  root /usr/share/nginx/html;

  location /assets/ {
    try_files $uri =404;
    add_header Cache-Control "public, max-age=31536000, immutable";
  }
  location = /index.html {
    add_header Cache-Control "no-cache";
  }
  location / {
    try_files $uri $uri/ /index.html;
  }
}
```

В проверке контейнер с таким конфигом отдал на `/products/7` код 200 с `index.html`, на отсутствующий `/assets/main-old12345.js` — 404, а у `index.html` был `Cache-Control: no-cache`. С наивным конфигом — одна строка `try_files … /index.html` на всё — отсутствующий скрипт получил 200 и `text/html`: та самая пустая страница с ошибкой MIME-типа после выкладки. Схема кеширования — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching).

Для :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"} вторая стадия другая: вместо nginx — Node.js-сервер приложения, например `CMD ["node", "server.js"]` с выводом `output: 'standalone'` в Next.js.

## Один образ — разные окружения

Образ собирают один раз и запускают на стенде и в продакшене с разными переменными окружения (подробно — в [Окружениях и конфигурации](/content/testing-deploying/environments-and-config)). Но статический бандл переменные контейнера не видит — его собрали раньше. Конфигурацию генерируют при старте контейнера:

```sh
#!/bin/sh
# /docker-entrypoint.d/40-config.sh — образ nginx выполняет такие скрипты перед запуском
printf '{"apiUrl":"%s"}' "$API_URL" > /usr/share/nginx/html/config.json
```

```bash
docker run -e API_URL=https://api.staging.shop.example shop-web:1.4.2   # стенд
docker run -e API_URL=https://api.shop.example         shop-web:1.4.2   # продакшен
```

В проверке один и тот же образ отдал `config.json` с адресом стенда в одном контейнере и с адресом продакшена — в другом. Ассеты при этом с хешами и кешем на год, а `config.json` отдают с `no-cache`.

## Когда контейнеры нужны

| Ситуация | Нужен ли Docker |
| --- | --- |
| статика на Vercel, Netlify, Cloudflare Pages | нет, платформа раздаёт сама |
| своя инфраструктура, Kubernetes | да |
| SSR на своих серверах | да, образ с Node.js |
| одинаковое окружение для e2e в CI и локально | да, например образ Playwright |
| строгие требования к размещению и сети | да |

Когда контейнеров много, ими управляет **оркестратор** — Kubernetes, ECS, Nomad: перезапуски, масштабирование, балансировка, поочерёдная выкладка с проверками готовности (подробно — в [Стратегиях выкладки](/content/testing-deploying/deployment-strategies)). Это обычно зона инфраструктурной команды, а фронтендеру важно, что его образ — один из сервисов, и ассеты разных версий должны быть доступны во время выкладки.

## Красные флаги в ответе

- **«Контейнер — это маленькая виртуальная машина».** Это изолированный процесс с общим ядром хоста.
- **«Положу в образ Node.js и `node_modules`, чтобы раздавать статику».** Многоэтапная сборка оставляет только `dist` и веб-сервер.
- **«`COPY . .` первой строкой».** Каждая правка кода переустановит зависимости, а без `.dockerignore` в образ уйдут `.env` и `.git`.
- **«`try_files … /index.html` на всё».** Отсутствующий скрипт получит HTML со статусом 200.
- **«Соберу отдельный образ для стенда и продакшена».** Проверяли один образ, выкладываем другой — конфигурацию передают при запуске.
- **«Статике на Vercel нужен Docker».** Платформа раздаёт файлы сама.

## Как спрашивают на собеседовании

::question
Что такое контейнер и чем он отличается от виртуальной машины?

#answer
Контейнер — процесс хоста в изолированном окружении: своя файловая система из образа, свои процессы и сеть, ограничения ресурсов. Ядро общее с хостом, поэтому контейнер весит мегабайты и стартует за доли секунды. Виртуальная машина запускает целую гостевую ОС со своим ядром.

#more
Общее ядро делает границу безопасности контейнера слабее, чем у виртуальной машины. На macOS и Windows Docker работает внутри лёгкой Linux-машины.
::

::question
Зачем многоэтапная сборка для фронтенда?

#answer
Сборке нужны Node.js, зависимости и исходники, а раздаче — только готовые файлы и веб-сервер. Многоэтапная сборка собирает в одной стадии и копирует в итоговый образ только `dist` и, например, nginx.

#more
Итоговый образ в разы меньше и без Node.js, `node_modules` и исходников: быстрее загрузка и меньше уязвимостей для обновления. Для SSR во второй стадии — Node.js, но только с продакшен-зависимостями.
::

::question
Почему `package.json` копируют раньше остального кода?

#answer
Ради кеша слоёв: шаг `npm ci` пересобирается, только если изменились его входные файлы — `package.json` и lock-файл. Правка кода тогда пересобирает лишь последующие шаги, а зависимости берутся из кеша.

#more
`.dockerignore` дополняет это: в контекст сборки не уходят `node_modules`, `.git`, `dist` и `.env` — сборка быстрее, а секреты не попадают в образ.
::

::question
Как раздать SPA из контейнера?

#answer
nginx с `try_files $uri $uri/ /index.html` для маршрутов, чтобы прямой заход на `/products/7` получал `index.html`, и отдельным правилом `try_files $uri =404` для ассетов.

#more
Без отдельного правила отсутствующий скрипт получает HTML со статусом 200 и ломает страницу ошибкой MIME-типа. Там же задают кеш: ассетам — `immutable` на год, `index.html` — `no-cache`.
::

::question
Как один образ работает на стенде и в продакшене?

#answer
Конфигурацию передают при запуске — переменными окружения контейнера. Статический бандл их не видит, поэтому при старте скрипт генерирует `config.json`, который приложение загружает.

#more
Образ nginx выполняет скрипты из `/docker-entrypoint.d/` и умеет подставлять переменные в шаблоны конфига. Так соблюдается принцип «собрать один раз»: на стенде и в продакшене работает один и тот же проверенный образ.
::

## Практика

::practice{title="Образ на полгигабайта"}
Образ фронтенда весит 600 МБ, сборка в CI каждый раз ставит зависимости заново, а аудит нашёл в образе файл `.env`. Dockerfile:

```text
FROM node:24
WORKDIR /app
COPY . .
RUN npm install && npm run build
CMD ["npx", "serve", "dist"]
```

#solution
Три проблемы: одна стадия, неудачный порядок шагов и нет `.dockerignore`.

```text
FROM node:24-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.29-alpine
COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY --from=build /app/dist /usr/share/nginx/html
```

```text
# .dockerignore
node_modules
.git
dist
.env*
```

В проверке итоговый образ был без Node.js и меньше стадии сборки, правка кода не перезапускала `npm ci`, а `.dockerignore` сократил контекст с 20 МБ до меньше мегабайта. Попавший в образ `.env` считают утёкшим: секреты из него отзывают.
::

::practice{title="Стенд ходит в продакшен-API"}
Образ собирают с `VITE_API_URL=https://api.shop.example` и тот же образ запускают на стенде с `-e API_URL=https://api.staging.shop.example`. Стенд всё равно ходит в продакшен.

#solution
Переменная `VITE_API_URL` встроена в бандл при сборке, а переменные контейнера статический JavaScript не видит. Конфигурацию генерируют при старте контейнера:

```sh
#!/bin/sh
# /docker-entrypoint.d/40-config.sh
printf '{"apiUrl":"%s"}' "$API_URL" > /usr/share/nginx/html/config.json
```

```js
const { apiUrl } = await fetch('/config.json').then((r) => r.json());
```

В проверке один образ отдал адрес стенда в одном контейнере и продакшена — в другом. `config.json` отдают с `no-cache`, чтобы смена переменной сразу дошла до браузеров.
::
