# Покрытие и TDD

Покрытие кода - популярная, но **обманчивая** метрика; мутационное тестирование измеряет качество тестов честнее; а TDD - дисциплина «тест раньше кода». На собеседованиях ценят понимание **пределов** покрытия, а не цифры «у нас 90%».

---

## Метрики покрытия

**Code coverage** показывает, какая доля кода выполнилась во время тестов.

| Метрика | Что измеряет |
|---------|--------------|
| **Statement** | сколько инструкций выполнилось |
| **Branch** | сколько веток условий (`if/else`) пройдено |
| **Function** | сколько функций вызвано |
| **Line** | сколько строк выполнилось |

**Branch coverage** - самая полезная: показывает, проверены ли обе ветки условий, а не только «строка выполнилась».

```bash
vitest --coverage   # отчёт по всем метрикам
```

Измеряется **инструментированием**: раннер помечает код и считает, что выполнилось.

---

## Пределы покрытия

Главное, что нужно донести на собесе: **высокое покрытие ≠ хорошие тесты**.

```js
// 100% покрытия, ноль уверенности: код выполнился, но ничего не проверено
test('считает', () => {
  calculateTotal([1, 2, 3]); // вызвали - покрытие есть
  // ...но НЕТ ассершена! баг не поймается
});
```

<b class="text-on-semi-light">Почему покрытие обманчиво</b> - <span class="text-gray">Покрытие говорит, что код **выполнился**, но не что он **проверен на правильность**. Можно иметь 100% и пропускать баги (нет ассершенов, не проверены краевые случаи). Это пример **закона Гудхарта**: «когда метрика становится целью, она перестаёт быть хорошей метрикой» - команды начинают писать тесты ради процента, а не ради уверенности.</span>

> Используй покрытие как **пол** (не дать важному коду остаться вообще без тестов), а не как **цель**. Гнаться за 100% - убывающая отдача: последние проценты (обработка невозможных веток) стоят дорого и дают мало.

---

## Мутационное тестирование

Честнее измеряет **качество** тестов. Идея: инструмент вносит в код мелкие баги - **мутанты** (меняет `+` на `-`, `>` на `>=`, удаляет строку) - и смотрит, **поймают ли их тесты**.

```
исходный код → внести мутацию → прогнать тесты
  тесты упали → мутант «убит» ✅ (тесты работают)
  тесты прошли → мутант «выжил» ❌ (тесты дырявые)
```

<b class="text-on-semi-light">Что это даёт</b> - <span class="text-gray">Если изменить логику и **ни один тест не упал** - тесты бесполезны, даже при 100% покрытия. Мутационный балл показывает, насколько тесты реально **ловят** ошибки, а не просто исполняют код. Инструмент - **Stryker**. Минус - медленно (много прогонов), поэтому гоняют выборочно.</span>

---

## TDD

**Test-Driven Development** - писать тест **до** кода, цикл **red-green-refactor**:

```
1. RED      - написать падающий тест (кода ещё нет)
2. GREEN    - написать минимум кода, чтобы тест прошёл
3. REFACTOR - улучшить код, не ломая тест
   ↺ повторить
```

<b class="text-on-semi-light">Плюсы и границы</b> - <span class="text-gray">Плюсы: тесты пишутся гарантированно, код проектируется тестируемым, есть быстрая обратная связь, появляется уверенность для рефакторинга. Минусы: подходит не всегда - для исследовательской работы, прототипов и UI с неясными требованиями писать тест первым тяжело. TDD - инструмент, а не догма.</span>

---

## BDD

**Behavior-Driven Development** - развитие TDD с фокусом на **поведении на языке бизнеса**. Сценарии пишут в формате **Given-When-Then** (Gherkin), понятном не только разработчикам.

```gherkin
Given пользователь на странице логина
When он вводит верные данные и нажимает «Войти»
Then он видит свой дашборд
```

Инструменты: **Cucumber**. BDD ценен, когда нужно согласовать поведение с продактами/QA; для чисто технических тестов избыточен.

---

## Что отвечать про «сколько покрытия»

> Нет «правильной» цифры. Разумный пол (например, 70–80% на критичной логике) полезен, но 100% - не цель. Важнее **что** покрыто (критические пути, краевые случаи) и **есть ли ассершены**, а не сам процент.

## Вопросы на собеседовании

<b class="text-on-semi-light">Гарантирует ли 100% покрытия хорошие тесты?</b>
<span class="text-gray">Нет. Покрытие показывает, что код выполнился, но не что он проверен. Можно иметь 100% без единого ассершена и пропускать баги. Это закон Гудхарта: метрика-цель перестаёт быть хорошей.</span>

<b class="text-on-semi-light">Какая метрика покрытия полезнее всего?</b>
<span class="text-gray">Branch coverage - проверяет, пройдены ли обе ветки условий, а не просто «строка выполнилась».</span>

<b class="text-on-semi-light">Что такое мутационное тестирование?</b>
<span class="text-gray">Инструмент вносит мелкие баги (мутанты) и смотрит, поймают ли тесты. Если тесты не падают - они дырявые, даже при 100% покрытия. Измеряет качество тестов, а не только исполнение (Stryker).</span>

<b class="text-on-semi-light">Что такое TDD и его цикл?</b>
<span class="text-gray">Test-Driven Development - тест до кода. Цикл red-green-refactor: написать падающий тест, минимум кода чтобы прошёл, отрефакторить. Даёт тестируемый дизайн и уверенность, но подходит не для всякой задачи.</span>

<b class="text-on-semi-light">Чем BDD отличается от TDD?</b>
<span class="text-gray">BDD фокусируется на поведении на языке бизнеса (Given-When-Then, Gherkin), понятном продактам/QA. TDD - техническая практика «тест раньше кода».</span>
