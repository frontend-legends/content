# Покрытие и TDD

Как измерить, насколько тесты защищают код: метрики покрытия и их пределы, пороги в CI, мутационное тестирование, а также практики TDD и BDD. Спрашивают, гарантирует ли стопроцентное покрытие хорошие тесты, какая метрика полезнее и что такое цикл red-green-refactor. Глубже — почему тест без единой проверки даёт 100% строк, почему 100% ветвей не поймали ошибку на границе и как мутанты находят дыры, невидимые для покрытия.

::tldr
- **Покрытие показывает, какой код выполнился во время тестов,** — строки, инструкции, функции, ветви. Оно не знает, проверили ли тесты результат.
- **Ветви полезнее строк:** условие в одну строку покрыто на 100% по строкам и на 50% по ветвям, если проверена одна сторона.
- **Покрытие — пол, а не цель:** порог в CI не даёт важному коду остаться без тестов, а погоня за процентом рождает тесты без проверок — закон Гудхарта.
- **Мутационное тестирование измеряет сами тесты:** Stryker вносит мелкие ошибки и смотрит, падают ли тесты. Выживший мутант — место, где ошибку никто не заметит.
- **TDD — тест до кода, цикл red-green-refactor;** BDD — поведение на языке бизнеса в форме Given — When — Then. Инструменты, а не догма.
::

---

## Метрики покрытия

Сквозной пример — скидка в магазине: от десяти штук цена на 10% ниже.

```js
export function price(base, qty) {
  return qty >= 10 ? base * qty * 0.9 : base * qty;
}
```

| Метрика | Что считает |
| --- | --- |
| строки (lines) | сколько строк выполнилось |
| инструкции (statements) | сколько инструкций выполнилось |
| функции (functions) | сколько функций вызвано |
| ветви (branches) | сколько сторон условий пройдено: `if`, `else`, тернарный оператор, `&&`, `??` |

Раннер собирает покрытие инструментированием кода — `istanbul` — или встроенными счётчиками движка V8:

```bash
vitest run --coverage
```

## Пределы покрытия

В проверке был один тест, без единой проверки:

```js
test('считает', () => { price(100, 1); });
```

Отчёт Vitest с провайдером V8: строки, инструкции и функции — **100%**, ветви — **50%**. Функция выполнилась, поэтому покрытие по строкам полное, хотя тест не проверил ни одного результата. Ветви показали правду наполовину: сторона со скидкой ни разу не выполнилась.

Покрытие отвечает на вопрос «что выполнилось», а не «что проверено». Когда процент становится целью, появляются тесты, которые вызывают код ради цифры, — это закон Гудхарта: метрика, ставшая целью, перестаёт хорошо измерять.

### Порог в CI

Порог полезен как пол — чтобы новый код не уходил совсем без тестов:

```js
// vitest.config.js
export default {
  test: { coverage: { thresholds: { branches: 80, lines: 80 } } },
};
```

В проверке тест без проверок с порогом по ветвям в 80% уронил прогон: `Coverage for branches (50%) does not meet global threshold (80%)`. Разумный пол зависит от кода: для критичной логики выше, для обёрток над интерфейсом ниже. Последние проценты — обработка «невозможных» ошибок — обычно стоят больше, чем дают.

## Мутационное тестирование

Тесты переписали с проверками на одну и двадцать штук:

```js
test('одна штука — без скидки', () => { expect(price(100, 1)).toBe(100); });
test('двадцать штук — скидка', () => { expect(price(100, 20)).toBe(1800); });
```

Покрытие — 100% и по строкам, и по ветвям. Но хороши ли тесты?

**Мутационное тестирование** отвечает на это. Инструмент вносит в код мелкие ошибки — **мутанты**: меняет `>=` на `>`, `*` на `/`, условие на `true`, удаляет блок — и для каждого прогоняет тесты.

```text
мутант → тесты упали   → убит: тесты замечают такую ошибку
мутант → тесты прошли  → выжил: такую ошибку никто не заметит
```

В проверке Stryker создал 8 мутантов. На тесте без проверок не был убит ни один. На тестах с одной и двадцатью штуками выжили два — счёт 75%:

- **`qty > 10`** вместо `qty >= 10` — граница не проверена: ни 1, ни 20 не отличают «от десяти» от «больше десяти»;
- **`base / qty`** вместо `base * qty` — при `qty = 1` деление и умножение дают одно и то же. Тестовые данные с единицей скрыли арифметическую ошибку.

Тесты на три штуки и ровно десять убили всех мутантов — счёт 100%:

```js
test('три штуки — без скидки', () => { expect(price(100, 3)).toBe(300); });
test('ровно десять — уже скидка', () => { expect(price(100, 10)).toBe(900); });
```

Ни одна из этих дыр не видна в покрытии — оно было стопроцентным. Инструменты: **Stryker** для JavaScript и TypeScript с раннерами Vitest и Jest. Цена — время: каждый мутант — отдельный прогон тестов, поэтому мутационное тестирование запускают для критичных модулей или только для изменённых файлов.

## TDD

**Test-Driven Development** — тест пишут до кода, короткими циклами:

```text
red      — тест на ещё не написанное поведение, он падает
green    — минимум кода, чтобы тест прошёл
refactor — улучшить код, тесты остаются зелёными
↺
```

Красный шаг важен: тест, который ни разу не падал, может не проверять ничего (подробно — во [Введении](/content/testing-deploying/introduction)). В примере со скидкой цикл выглядел бы так: тест «ровно десять — уже скидка» красный, затем условие `qty >= 10`, затем вынос коэффициента в константу.

Что даёт TDD:

- тесты пишутся гарантированно, а не «потом»;
- код получается тестируемым — с явными входами и выходами;
- быстрая обратная связь и уверенность при рефакторинге;
- граничные случаи продумываются до кода.

Где тяжело: исследовательская работа и прототипы, интерфейс с неясными требованиями, код, который в основном склеивает внешние системы. TDD — инструмент для понятной логики, а не обязательный ритуал для всего.

## BDD

**Behavior-Driven Development** развивает идею TDD: поведение описывают на языке бизнеса в форме **Given — When — Then**, понятной продакту и тестировщику. Формат сценариев — Gherkin:

```text
Сценарий: скидка от десяти штук
  Допустим в корзине 10 упаковок пуэра по 100 ₽
  Когда покупатель открывает корзину
  Тогда сумма к оплате 900 ₽
```

Сценарии связывают с кодом шагов в Cucumber или плагинах для Playwright. BDD окупается, когда сценарии действительно обсуждают с бизнесом и они служат спецификацией. Если их читают только разработчики, проще писать обычные тесты в той же структуре подготовки, действия и проверки.

## Сколько покрытия нужно

Правильной цифры нет. Порог в 70–80% на логике — разумный пол, а важнее другое:

- **что** покрыто — критичные сценарии, границы, ошибки;
- **есть ли проверки** и проверяют ли они то, что важно;
- **ловят ли тесты ошибки** — это показывает мутационный счёт, а не процент строк.

---

## Красные флаги в ответе

- **«У нас 100% покрытия — значит, всё протестировано».** Тест без проверок тоже даёт 100% строк.
- **«Достаточно покрытия по строкам».** Условие в одну строку покрыто полностью при одной проверенной стороне.
- **«Поставим порог 100% и будем держать».** Появятся тесты ради цифры.
- **«Тестовые данные — единица и десять, этого хватит».** Единица скрывает ошибки умножения и деления, граница требует отдельного теста.
- **«TDD обязателен для всего».** Для прототипов и неясного интерфейса он тяжёл.

## Как спрашивают на собеседовании

::question
Гарантирует ли стопроцентное покрытие хорошие тесты?

#answer
Нет. Покрытие показывает, что код выполнился, но не что результат проверен. Тест, который вызывает функцию без единой проверки, даёт 100% строк и не ловит ни одной ошибки.

#more
Даже 100% ветвей с проверками не гарантирует, что проверены границы: мутант `>=` → `>` выживает, если тест не берёт ровно граничное значение. Когда процент становится целью, работает закон Гудхарта — пишут тесты ради цифры.
::

::question
Какая метрика покрытия полезнее всего?

#answer
Покрытие ветвей: оно показывает, пройдены ли обе стороны условий — `if` и `else`, тернарного оператора, `&&` и `??`. Покрытие строк считает строку выполненной, даже если проверена одна сторона условия в ней.

#more
Но и ветви говорят только о выполнении. Насколько тесты ловят ошибки, показывает мутационное тестирование.
::

::question
Что такое мутационное тестирование?

#answer
Инструмент вносит в код мелкие ошибки — мутанты: меняет операторы, условия, удаляет блоки — и для каждой прогоняет тесты. Если тесты упали, мутант убит; если прошли — выжил, и такую ошибку тесты не заметят.

#more
Выжившие мутанты указывают на конкретные дыры: непроверенную границу, тестовые данные, при которых ошибка не видна. Stryker работает с Vitest и Jest. Это медленно — по прогону на мутанта, — поэтому его запускают для критичных модулей или изменённых файлов.
::

::question
Что такое TDD и его цикл?

#answer
Test-Driven Development — тест пишут до кода. Цикл red-green-refactor: падающий тест на новое поведение, минимум кода, чтобы он прошёл, затем улучшение кода при зелёных тестах.

#more
TDD даёт тестируемый дизайн, продуманные границы и уверенность при рефакторинге. Тяжёл для прототипов, исследовательской работы и интерфейса с неясными требованиями — это инструмент, а не правило для всего кода.
::

::question
Чем BDD отличается от TDD?

#answer
TDD — техническая практика «тест раньше кода». BDD описывает поведение на языке бизнеса в форме Given — When — Then, чтобы сценарии понимали продакт и тестировщик и они служили спецификацией.

#more
Сценарии пишут на Gherkin и связывают с кодом шагов в Cucumber или плагинах Playwright. Если сценарии читают только разработчики, BDD добавляет слой без пользы.
::

::question
Нужен ли порог покрытия в CI?

#answer
Как пол — да: порог не даёт новому коду уйти совсем без тестов, и прогон падает, если покрытие ниже. Как цель — нет: высокий обязательный процент рождает тесты без проверок.

#more
Порог задают по ветвям и строкам, разный для логики и для интерфейсных обёрток. Полезнее порога — ревью, проверяющее, что тесты защищают важное поведение.
::

## Практика

::practice{title="100% покрытия, ошибка на границе"}
У функции скидки 100% покрытия по строкам и ветвям. После правки условия с `qty >= 10` на `qty > 10` покупатель, взявший ровно десять упаковок, заплатил без скидки. Тесты зелёные.

#solution
Тесты проверяли 1 и 20 штук — значения далеко от границы. Ни одно не различает «от десяти» и «больше десяти». Покрытие этого не видит, а мутационное тестирование — да:

```bash
npx stryker run
```

В проверке Stryker оставил выжившими два мутанта: `qty > 10` и `base / qty`. Второй выжил, потому что при одной штуке деление и умножение совпадают. Тесты на границу и не единичное количество убили обоих:

```js
test('ровно десять — уже скидка', () => { expect(price(100, 10)).toBe(900); });
test('три штуки — без скидки', () => { expect(price(100, 3)).toBe(300); });
```

Правило: проверять значения на границе и по обе стороны от неё и не брать в тестовые данные числа, при которых разные операции дают одинаковый результат.
::

::practice{title="Покрытие растёт, баги тоже"}
Команде поставили цель — 90% покрытия к концу квартала. Покрытие выросло с 60% до 92%, а число багов в продакшене не изменилось.

#solution
Цель по проценту привела к тестам ради цифры: вызвать код и не проверить результат — это законная стопроцентная строка. В проверке тест без единой проверки дал 100% строк и не убил ни одного мутанта из восьми. Что делать:

```js
// vitest.config.js — порог как пол, около текущего уровня
export default { test: { coverage: { thresholds: { branches: 60 } } } };
```

```js
// stryker.config.mjs — мутационный счёт для критичной логики
export default { testRunner: 'vitest', mutate: ['src/cart/**/*.js'], thresholds: { break: 80 } };
```

- на ревью смотреть, что тесты проверяют поведение и границы;
- каждый баг из продакшена — тест, который сначала падает.

Мерить стоит то, что важно: долю багов, пойманных до релиза, а не долю выполненных строк.
::
