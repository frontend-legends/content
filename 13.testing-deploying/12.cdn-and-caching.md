# CDN и кеширование

После сборки ассеты нужно **доставить** пользователям быстро и **закешировать** правильно. CDN раздаёт файлы рядом с пользователем, а грамотная стратегия кеширования делает повторные загрузки мгновенными - но требует аккуратности, чтобы пользователи получали свежий деплой.

> Механика HTTP-заголовков кеширования подробно - в [Network & API](/content/network-api). Здесь - **деплой-угол**: как кешировать ассеты фронтенда.

---

## CDN

**Content Delivery Network** - сеть серверов по всему миру, кеширующих твой контент **близко к пользователю**.

```
без CDN:  пользователь (Токио) → origin (Франкфурт)   ~250мс
с CDN:    пользователь (Токио) → edge-узел (Токио)     ~10мс
```

Что даёт: **низкая задержка** (файл рядом), **разгрузка origin** (CDN отвечает вместо твоего сервера), **устойчивость** к нагрузке и всплескам трафика. Статика фронтенда почти всегда раздаётся через CDN.

---

## Стратегия кеширования ассетов

Ключевой приём фронтенд-деплоя, который надо знать: **хешированные immutable-ассеты + некешируемый HTML**.

```
app.4f3a2b.js     → Cache-Control: max-age=31536000, immutable  (кешировать «вечно»)
index.html        → Cache-Control: no-cache                     (всегда проверять)
```

<b class="text-on-semi-light">Почему так работает</b> - <span class="text-gray">Имя бандла содержит **хеш содержимого** ([оптимизация](/content/advanced-tooling/optimization)): изменился код - изменился хеш - новое имя файла. Поэтому хешированные файлы можно кешировать на год (`immutable`) - они **никогда** не меняются под тем же именем. А `index.html` (который ссылается на эти файлы) кешировать **нельзя** - он должен подтягиваться свежим, чтобы указать на **новые** хешированные бандлы после деплоя. Так пользователь мгновенно получает неизменные ассеты из кеша и сразу видит новый деплой.</span>

```
деплой v2 → index.html обновился (no-cache) → ссылается на app.9c8d.js (новый хеш)
          → старый app.4f3a.js в кеше больше не запрашивается
```

---

## Заголовки Cache-Control

Кратко (детали - в [Network](/content/network-api)):

| Директива | Смысл |
|-----------|-------|
| `max-age=N` | кешировать N секунд |
| `immutable` | файл не изменится - не перепроверять |
| `no-cache` | кешировать, но **проверять** актуальность перед использованием |
| `no-store` | не кешировать вообще |
| `s-maxage` | срок для CDN/прокси (отдельно от браузера) |
| `stale-while-revalidate` | отдать из кеша, обновить в фоне |

> `no-cache` ≠ `no-store`. `no-cache` - «можно хранить, но сверяйся перед использованием»; `no-store` - «не храни совсем». Частая путаница на собесе.

---

## Cache busting

**Сброс кеша** через хеш в имени - то, что делает стратегию выше возможной. Не нужно вручную чистить кеш браузера: новое содержимое = новое имя = новый запрос. Старое имя просто перестаёт запрашиваться. Это работает в связке с [хешированием при сборке](/content/advanced-tooling/optimization).

---

## Инвалидация CDN

При деплое CDN должен начать отдавать **новые** файлы. Варианты:

- **Хешированные имена** - инвалидация не нужна (новый файл = новый URL).
- **Purge/invalidation** - явно сбросить кеш CDN для путей, которые кешируются под одним именем (например, `index.html`). Платформы (Vercel/Netlify) делают это автоматически при деплое.

> Атомарные деплои (Vercel/Netlify) совмещают загрузку новых ассетов и инвалидацию так, что пользователи не попадают на «полусломанное» состояние между версиями.

---

## Edge и динамика

CDN кешируют не только статику: можно кешировать на edge и **ответы** (страницы, API) с коротким TTL и `stale-while-revalidate` - близко к ISR. Edge-вычисления ([хостинг](/content/testing-deploying/hosting-and-platforms)) позволяют генерировать/персонализировать прямо на узле CDN.

---

## Ассеты и изображения

Изображения часто раздают через **image CDN** (Cloudinary, imgix, встроенные в Vercel/Netlify): on-the-fly ресайз, конвертация в WebP/AVIF, кеширование вариантов. Это снимает с фронтенда оптимизацию картинок.

## Вопросы на собеседовании

<b class="text-on-semi-light">Зачем нужен CDN?</b>
<span class="text-gray">Раздавать контент с серверов рядом с пользователем - низкая задержка, разгрузка origin, устойчивость к нагрузке. Статику фронтенда почти всегда отдают через CDN.</span>

<b class="text-on-semi-light">Как кешировать ассеты фронтенда правильно?</b>
<span class="text-gray">Хешированные бандлы (имя с хешем содержимого) - `immutable`, max-age на год; `index.html` - `no-cache`. Ассеты берутся из кеша мгновенно, а свежий HTML указывает на новые бандлы после деплоя.</span>

<b class="text-on-semi-light">Почему index.html нельзя кешировать надолго?</b>
<span class="text-gray">Он ссылается на хешированные бандлы. Если закешировать его, пользователь после деплоя продолжит грузить старые ассеты. HTML должен подтягиваться свежим, чтобы указать на новые файлы.</span>

<b class="text-on-semi-light">Чем no-cache отличается от no-store?</b>
<span class="text-gray">`no-cache` - можно хранить, но перед использованием проверять актуальность у сервера. `no-store` - не хранить вообще. Это разные вещи, часто путают.</span>

<b class="text-on-semi-light">Что такое cache busting и как он работает?</b>
<span class="text-gray">Сброс кеша через хеш содержимого в имени файла: изменился код - изменилось имя - браузер запрашивает новый файл. Чистить кеш вручную не нужно.</span>
