# CDN и кеширование при выкладке

Как раздавать фронтенд быстро и при этом сразу показывать новую версию: CDN, хешированные ассеты с долгим кешем и всегда свежий `index.html`, сброс кеша CDN, старые чанки после выкладки, кеш ответов на edge и CDN для изображений. Спрашивают, зачем CDN, как правильно кешировать ассеты и почему `index.html` нельзя кешировать надолго. Глубже — чем `no-cache` отличается от `no-store`, почему после выкладки пользователь видит старую версию и почему кнопка «Оформить» в открытой вкладке перестала работать.

::tldr
- **CDN раздаёт файлы с узлов рядом с пользователем:** меньше задержка, меньше нагрузка на свой сервер, устойчивость к всплескам.
- **Главная схема:** ассеты с хешем содержимого в имени — `public, max-age=31536000, immutable`, а `index.html` — `no-cache`. Ассеты берутся из кеша без запроса, а HTML проверяется каждый раз и указывает на новые файлы.
- **`no-cache` — хранить, но проверять перед использованием** — ответ 304 без тела; **`no-store`** — не хранить вовсе.
- **`index.html` с долгим кешем** держит пользователя на старой версии: браузер даже не спрашивает сервер.
- **Старые ассеты удалять сразу нельзя:** открытая вкладка догружает ленивые чанки своей версии. Их хранят несколько выкладок, а ошибку загрузки чанка ловят — в Vite событие `vite:preloadError`.
::

## CDN

Сквозной пример — магазин: `index.html`, бандл `index-[hash].js`, ленивый чанк оформления заказа `checkout-[hash].js`, картинки товаров.

**CDN** — сеть узлов по всему миру, которые хранят копии файлов рядом с пользователем:

```text
без CDN:  пользователь в Новосибирске → сервер во Франкфурте
с CDN:    пользователь в Новосибирске → ближайший узел CDN → (при промахе) сервер
```

Что даёт:

- **короткий путь** до первого байта и до файлов;
- **разгрузку источника** — узлы отвечают сами, на сервер доходят только промахи;
- **устойчивость** к всплескам трафика и части атак.

Статику фронтенда почти всегда раздают через CDN: платформы вроде :term[Cloudflare]{def="компания с собственной сетью CDN, защитой и вычислениями на edge"} Pages, Netlify и Vercel делают это сами, а при своём хранилище ставят :term[CloudFront]{def="CDN от Amazon Web Services"}, Cloudflare или аналог.

## Хешированные ассеты и свежий HTML

Ключевая схема выкладки фронтенда:

```text
assets/index-B2kX9f.js     Cache-Control: public, max-age=31536000, immutable
assets/checkout-Qa81.js    Cache-Control: public, max-age=31536000, immutable
index.html                 Cache-Control: no-cache
```

Имя ассета содержит хеш содержимого (подробно — в [Оптимизации](/content/advanced-tooling/optimization)): изменился код — изменилось имя. Под одним именем содержимое не меняется никогда, поэтому файл можно кешировать на год и не перепроверять. А `index.html` живёт под одним именем и ссылается на текущие ассеты — его проверяют при каждом заходе.

В проверке в Chromium при повторном переходе на страницу бандл не запрашивался вовсе, а `index.html` запрашивался оба раза, и второй ответ был **304** без тела: браузер прислал `If-None-Match`, сервер подтвердил, что HTML не изменился.

```text
выкладка v2 → новый index.html (no-cache, проверен) → ссылается на index-Nw3p.js
            → старый index-B2kX9f.js больше никто не запрашивает
```

Ручной сброс кеша не нужен: новое содержимое — новое имя — новый запрос. Это и называют **cache busting**.

### Заголовки

Механика HTTP-кеша — `max-age`, `ETag`, валидация, `Vary` — разобрана в [Кешировании](/content/network-api/caching). Для выкладки важны:

| Директива | Смысл |
| --- | --- |
| `max-age=N` | ответ свежий N секунд, запрос не нужен |
| `immutable` | не перепроверять даже при обновлении страницы |
| `no-cache` | хранить можно, но перед использованием проверять у сервера |
| `no-store` | не хранить вовсе |
| `s-maxage=N` | срок для CDN и прокси, отдельно от браузера |
| `stale-while-revalidate=N` | отдать устаревшее и обновить в фоне |

`no-cache` и `no-store` путают постоянно. В проверке с `no-cache` второй запрос HTML вернул 304, а с `no-store` — оба раза полный ответ без единого 304: браузер ничего не сохранил, сравнивать было не с чем.

## Ошибки с кешем

### Долгий кеш у index.html

В проверке `index.html` отдавали с `max-age=3600`. После выкладки v2 — новые хеши, старые ассеты удалены — обычный повторный переход показал **v1**, а сервер не получил ни одного запроса: HTML был свежим по кешу. Пользователь остаётся на старой версии, пока не истечёт срок, а если её ассеты уже удалены — видит сломанную страницу.

Поэтому `index.html` — `no-cache` или очень короткий `max-age`. На CDN его можно кешировать дольше через `s-maxage`, если при каждой выкладке CDN сбрасывают.

### Удалённые чанки

Пользователь открыл магазин до выкладки и нажал «Оформить» после неё. Вкладка выполняет старый бандл и просит ленивый чанк своей версии — а выкладка его удалила. В проверке клик закончился ошибкой:

```text
Failed to fetch dynamically imported module: http://…/assets/checkout-….js
```

Vite при этом отправил событие `vite:preloadError` — его ловят и перезагружают страницу:

```js
window.addEventListener('vite:preloadError', () => {
  window.location.reload();
});
```

Лучше, чтобы ошибки не было вовсе: **хранить ассеты нескольких прошлых выкладок**. В проверке, когда новые файлы положили рядом со старыми, вкладка v1 догрузила свой чанк и показала «Оформление v1». Неизменяемые выкладки на платформах хранят старые ассеты сами, а при своём хранилище новые файлы загружают поверх, не удаляя старые, и чистят по расписанию. Как обе версии живут одновременно — в [Стратегиях выкладки](/content/testing-deploying/deployment-strategies).

## Сброс кеша CDN

После выкладки CDN должен начать отдавать новые файлы:

- **хешированные ассеты** сброса не требуют — у них новые адреса;
- **файлы под постоянным именем** — `index.html`, `robots.txt`, `manifest.webmanifest`, `sw.js` — либо отдают с `no-cache`, либо сбрасывают на CDN при выкладке: purge по пути, тегу или целиком.

Порядок выкладки важен: сначала загрузить новые ассеты, затем — новый `index.html`, затем сбросить его в CDN. В обратном порядке пользователь получит HTML, ссылающийся на файлы, которых ещё нет. Платформы с неизменяемыми выкладками переключают версию атомарно.

## Кеш ответов на edge

CDN кеширует не только файлы, но и ответы — страницы и API — с коротким сроком:

```text
Cache-Control: public, s-maxage=60, stale-while-revalidate=300
```

Узел отдаёт страницу из кеша минуту, затем ещё пять минут отдаёт устаревшую и обновляет её в фоне. Так работает инкрементальная регенерация в мета-фреймворках (подробно — в [Мета-фреймворках](/content/ecosystem-libs/meta-frameworks)). Персональные ответы так не кешируют, а если ответ зависит от заголовка — языка, формата, — это указывают в `Vary`.

### Изображения

Картинки раздают через **CDN изображений** — Cloudinary, imgix, Cloudflare Images, встроенные оптимизаторы платформ: размер под устройство, формат :term[WebP]{def="формат изображений Google: меньше JPEG и PNG при том же качестве"} или :term[AVIF]{def="формат изображений на кодеке AV1: обычно ещё меньше WebP"} по заголовку `Accept`, кеш каждого варианта. Как выбирать форматы и размеры на странице — в [Оптимизации ассетов](/content/security-perfomance/asset-optimization).

## Красные флаги в ответе

- **«Закешируем всё на год, так быстрее».** `index.html` на год — пользователи не увидят новые выкладки.
- **«`no-cache` — значит, не кешировать».** Хранить можно, проверять нужно; не хранить — это `no-store`.
- **«Удалим старые ассеты при выкладке, чтобы не копились».** Открытые вкладки не догрузят свои чанки.
- **«После выкладки попросим пользователей почистить кеш».** Хеши в именах делают это ненужным.
- **«Сначала зальём index.html, потом ассеты».** В промежутке HTML ссылается на несуществующие файлы.

## Как спрашивают на собеседовании

::question
Зачем нужен CDN?

#answer
Чтобы раздавать файлы с узлов рядом с пользователем: короче путь до первого байта, меньше нагрузка на свой сервер, устойчивость к всплескам трафика.

#more
Узел хранит копию по правилам `Cache-Control` — `s-maxage` задаёт срок именно для CDN. Кроме статики CDN кеширует ответы с коротким сроком и `stale-while-revalidate`, а edge-функции выполняют код на узлах.
::

::question
Как правильно кешировать ассеты фронтенда?

#answer
Ассеты с хешем содержимого в имени — `public, max-age=31536000, immutable`: они никогда не меняются под тем же именем. `index.html` — `no-cache`: проверяется при каждом заходе и указывает на текущие ассеты.

#more
Повторный заход берёт бандлы из кеша без запросов, а HTML проверяется и возвращает 304, если не изменился. Хеш в имени и есть сброс кеша: новый код — новое имя.
::

::question
Почему `index.html` нельзя кешировать надолго?

#answer
Он ссылается на хешированные ассеты текущей версии. Если он закеширован, после выкладки браузер даже не спросит сервер и покажет старую версию, а если её ассеты уже удалены — сломанную страницу.

#more
На CDN его можно держать дольше через `s-maxage`, если при каждой выкладке CDN сбрасывают. В браузере — `no-cache` или очень короткий срок.
::

::question
Чем `no-cache` отличается от `no-store`?

#answer
`no-cache` разрешает хранить ответ, но требует проверить его у сервера перед использованием — сервер отвечает 304 без тела, если ничего не изменилось. `no-store` запрещает хранить вовсе — каждый раз полный ответ.

#more
Для `index.html` подходит `no-cache`: проверка дешёвая, а новая версия видна сразу. `no-store` — для ответов, которые нельзя оставлять на диске, например с персональными данными.
::

::question
Что происходит с открытой вкладкой после выкладки?

#answer
Она продолжает выполнять старый бандл и при переходе запрашивает ленивые чанки своей версии. Если выкладка их удалила, импорт падает с `Failed to fetch dynamically imported module`.

#more
Старые ассеты хранят несколько выкладок, а ошибку загрузки чанка ловят — в Vite событием `vite:preloadError` — и перезагружают страницу. Приложение может и само узнавать о новой версии через `/version.json`.
::

## Практика

::practice{title="Пользователи не видят новую версию"}
После выкладки часть пользователей ещё час видит старый интерфейс, а у некоторых страница сломана. Сервер отдаёт все файлы с `Cache-Control: max-age=3600`.

#solution
`index.html` закеширован на час: браузер при повторном заходе не спрашивает сервер. В проверке после выкладки v2 обычный переход показал v1, а запросов к серверу не было. У кого истёк кеш ассетов, а HTML ещё старый, страница ссылается на удалённые файлы.

```text
# nginx
location = /index.html { add_header Cache-Control "no-cache"; }
location /assets/      { add_header Cache-Control "public, max-age=31536000, immutable"; }
```

После этого в проверке HTML проверялся при каждом заходе и возвращал 304, а бандл не запрашивался повторно вовсе.
::

::practice{title="«Оформить» перестало работать после выкладки"}
Пользователь открыл магазин утром, днём прошла выкладка, вечером он нажал «Оформить» — ничего не произошло. В мониторинге: `Failed to fetch dynamically imported module: …/assets/checkout-….js`.

#solution
Вкладка выполняет утренний бандл и просит утренний чанк оформления, а выкладка удалила старые ассеты. В проверке это воспроизвелось точно, и Vite отправил `vite:preloadError`. Две меры:

```js
// 1. не терять пользователя: перезагрузить на новую версию
window.addEventListener('vite:preloadError', (event) => {
  event.preventDefault();
  window.location.reload();
});
```

```bash
# 2. не удалять старые ассеты при выкладке: загружать новые поверх
aws s3 sync dist/assets s3://shop/assets --cache-control "public, max-age=31536000, immutable"
aws s3 cp dist/index.html s3://shop/index.html --cache-control "no-cache"
```

В проверке, когда старые файлы остались рядом с новыми, та же вкладка догрузила свой чанк и показала оформление. Старые ассеты чистят по расписанию, через несколько выкладок.
::
