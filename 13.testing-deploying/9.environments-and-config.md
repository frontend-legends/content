# Окружения и конфигурация

Одно и то же приложение работает в нескольких **окружениях** - локально, на staging, в проде - с разными настройками (адреса API, ключи, фичефлаги). Как управлять этой конфигурацией, в чём разница build-time и runtime и почему секреты нельзя класть в бандл - частые вопросы про деплой.

---

## Окружения

| Окружение | Зачем |
|-----------|-------|
| **Development** | локальная разработка, hot reload, моки |
| **Staging / Preview** | копия прода для проверки перед релизом |
| **Production** | реальные пользователи |

<b class="text-on-semi-light">Принцип паритета</b> - <span class="text-gray">Staging должен быть **максимально похож** на прод (та же сборка, похожие данные), иначе «на staging работало» не значит «в проде заработает». Различаться должна только конфигурация, не код.</span>

Современные платформы добавляют **preview-окружения** на каждый PR (см. [стратегии деплоя](/content/testing-deploying/deployment-strategies)).

---

## Что различается между окружениями

Не код, а **конфигурация**:

- адреса API (`api.dev` / `api.prod`);
- ключи аналитики, публичные ключи сервисов;
- фичефлаги (что включено где);
- уровни логирования.

---

## Переменные окружения

Конфигурацию держат в **переменных окружения** (принцип 12-factor: «конфиг - в окружении, не в коде»), обычно через `.env`-файлы.

```bash
# .env.production
VITE_API_URL=https://api.example.com
```

```js
const api = import.meta.env.VITE_API_URL;
```

<b class="text-on-semi-light">Префиксы и публичность</b> - <span class="text-gray">Сборщики раскрывают клиенту только переменные с префиксом (`VITE_`, `NEXT_PUBLIC_`). Это **защита**: всё остальное не попадёт в бандл случайно. Но раскрытое - **публично** (см. ниже). `.env`-файлы с секретами **не коммитят** (в `.gitignore`), коммитят только `.env.example` с пустыми значениями.</span>

## Build-time vs runtime config

Ключевое различие для деплоя.

| | Build-time | Runtime |
|--|------------|---------|
| Когда читается | при сборке (инлайнится в бандл) | когда приложение работает |
| Смена окружения | нужна **пересборка** | один билд, разные env |
| Источник | `.env` при build | сервер, `window.__CONFIG__`, эндпоинт |
| Подходит для | статика, простые случаи | контейнеры, «build once» |

```js
// Build-time: значение «запекается» в бандл при сборке
const url = import.meta.env.VITE_API_URL; // фиксируется навсегда в этом билде

// Runtime: значение читается в браузере при запуске
const url = window.__APP_CONFIG__.apiUrl; // можно менять без пересборки
```

<b class="text-on-semi-light">Принцип «build once, deploy many»</b> - <span class="text-gray">Зрелый подход: собрать артефакт **один раз** и **продвигать** его через staging → prod без пересборки, меняя только runtime-конфиг. Так в прод попадает ровно то, что тестировали на staging. Build-time конфиг этому мешает (нужна отдельная сборка на каждое окружение), поэтому для контейнеров и строгого паритета предпочитают runtime-конфиг.</span>

## Секреты

Критический принцип безопасности.

```js
// ❌ КАТАСТРОФА: приватный ключ в клиентском коде = опубликованный ключ
const stripeSecret = import.meta.env.VITE_STRIPE_SECRET_KEY;
```

> Клиентский бандл **публичен** - любой откроет DevTools и увидит всё, что в него попало. На клиенте - **только публичные** значения (publishable-ключи, адреса API). Приватные ключи, токены, секреты БД - **только на сервере** (бэкенд, серверные функции, переменные окружения хостинга). Подробнее - в [безопасности React](/content/reactjs/security).

**Где хранить секреты:**

- секрет-менеджеры (Vault, Doppler, облачные secret managers);
- зашифрованные секреты CI (GitHub Actions secrets);
- переменные окружения хостинга - **никогда** в git и не в клиентском бандле.

## Вопросы на собеседовании

<b class="text-on-semi-light">Зачем нужны разные окружения и паритет?</b>
<span class="text-gray">dev/staging/prod разделяют разработку, проверку и реальных пользователей. Staging должен быть похож на прод (та же сборка), иначе «работало на staging» ненадёжно. Различаться должна только конфигурация.</span>

<b class="text-on-semi-light">В чём разница build-time и runtime конфигурации?</b>
<span class="text-gray">Build-time инлайнится в бандл при сборке - смена окружения требует пересборки. Runtime читается при работе приложения - один билд работает в разных окружениях.</span>

<b class="text-on-semi-light">Что значит «build once, deploy many»?</b>
<span class="text-gray">Собрать артефакт один раз и продвигать через окружения без пересборки, меняя runtime-конфиг. В прод попадает ровно то, что тестировали. Требует runtime-конфигурации.</span>

<b class="text-on-semi-light">Можно ли хранить API-ключи в переменных VITE_/NEXT_PUBLIC_?</b>
<span class="text-gray">Только публичные. Эти префиксы раскрывают значение в клиентский бандл, который публичен. Приватные ключи и секреты - только на сервере.</span>

<b class="text-on-semi-light">Почему .env с секретами не коммитят?</b>
<span class="text-gray">Это утечка секретов в историю git. Коммитят только `.env.example` с пустыми значениями; реальные секреты - в secret-менеджерах и переменных окружения хостинга/CI.</span>
