# Окружения и конфигурация

Как одно приложение работает локально, на стенде и в продакшене с разными настройками: окружения и их сходство, переменные окружения, конфигурация при сборке и при запуске, принцип «собрать один раз», секреты. Спрашивают, чем конфигурация при сборке отличается от конфигурации при запуске, можно ли класть ключи в переменные `VITE_` и почему `.env` не коммитят. Глубже — почему на стенде проверяли не ту сборку, что ушла в продакшен, почему режим `staging` — это всё ещё продакшен-сборка и почему удалённый `.env` по-прежнему опасен.

::tldr
- **Окружения отличаются конфигурацией, а не кодом:** адрес API, ключи публичных сервисов, флаги функций, уровень логов. Чем стенд ближе к продакшену, тем больше значит «на стенде работало».
- **Конфигурация при сборке встраивается в бандл строкой:** у каждого окружения своя сборка с другим хешем, и на стенде проверяют не тот файл, что уйдёт в продакшен.
- **Конфигурация при запуске** читается браузером из `config.json` или вставки в HTML: одна сборка продвигается через все окружения — «собрать один раз, выкладывать много раз».
- **Клиентский бандл публичен:** всё с префиксом `VITE_` или `NEXT_PUBLIC_` видит любой посетитель. Секреты живут только на сервере.
- **Секрет, однажды попавший в git, остаётся в истории** даже после удаления файла — его отзывают и выпускают новый.
::

## Окружения

Сквозной пример — магазин с API по адресу `api.shop.example` и стендом `api.staging.shop.example`, платёжным сервисом и аналитикой.

| Окружение | Зачем |
| --- | --- |
| локальное | разработка: dev-сервер, HMR, подменённый API |
| превью | отдельная выкладка каждого PR для ревью |
| стенд (staging) | копия продакшена для проверки перед релизом |
| продакшен | настоящие пользователи |

Различаться должна только **конфигурация**:

- адреса API и сторонних сервисов;
- публичные ключи — аналитики, карт, платёжной формы;
- флаги функций — что включено где (подробно — в [Стратегиях выкладки](/content/testing-deploying/deployment-strategies));
- уровень логов и отправка ошибок в мониторинг.

Принцип **сходства окружений**: стенд — та же сборка, похожие данные, та же схема CDN и заголовков. Чем больше различий, тем меньше значит зелёная проверка на стенде.

## Переменные окружения

Конфигурацию держат вне кода — в переменных окружения, по принципу «двенадцати факторов». Во фронтенде их обычно задают в `.env`-файлах по режимам:

```bash
# .env.staging
VITE_API_URL=https://api.staging.shop.example

# .env.production
VITE_API_URL=https://api.shop.example
```

```js
fetch(`${import.meta.env.VITE_API_URL}/products`);
```

Как Vite выбирает файлы и почему в код попадают только переменные с префиксом `VITE_` — в [Vite и dev-серверах](/content/advanced-tooling/vite-and-dev-servers). Важное для выкладки:

**Режим — не то же самое, что продакшен.** `vite build --mode staging` берёт `.env.staging`, но собирает продакшен-сборку. В проверке значения свернулись в строку `staging | true | https://api.staging.shop.example`: `MODE` — `'staging'`, а `PROD` — `true`. Поэтому «это стенд?» проверяют через `MODE` или свою переменную, а не через `PROD`.

## При сборке или при запуске

| | При сборке | При запуске |
| --- | --- | --- |
| Когда читается | сборщик встраивает значение в код | браузер загружает при старте |
| Сменить окружение | пересобрать | заменить конфиг |
| Источник | `.env`, переменные CI | `config.json`, вставка в HTML, ответ сервера |
| Подходит | статические сайты, одно окружение | несколько окружений, контейнеры |

### Конфигурация при сборке

```js
const api = import.meta.env.VITE_API_URL;
```

В проверке сборка для стенда и для продакшена дали **разные файлы**: в одном строка `https://api.staging.shop.example`, в другом `https://api.shop.example`, и у файлов разные хеши в именах. Значит, на стенде проверяли один бандл, а в продакшен ушёл другой — собранный отдельно, возможно, с другими версиями зависимостей.

### Конфигурация при запуске

```js
const config = await fetch('/config.json').then((r) => r.json());
fetch(`${config.apiUrl}/products`);
```

В проверке одна и та же сборка показала адрес стенда с одним `config.json` и адрес продакшена с другим, а в бандле адресов не было вовсе. Варианты источника:

- **`/config.json`** рядом с приложением — платформа или контейнер кладёт свой файл при выкладке; цена — лишний запрос до старта;
- **вставка в HTML** — сервер при отдаче `index.html` добавляет `<script>window.__APP_CONFIG__ = {…}</script>`;
- **переменные на сервере** — в мета-фреймворках серверный код читает `process.env` при запросе и передаёт клиенту нужное.

### Собрать один раз

Зрелый подход: артефакт собирают **один раз** и продвигают через стенд в продакшен без пересборки, меняя только конфигурацию при запуске. В продакшен уходит ровно тот файл, который проверили. Так же устроены контейнеры: один образ, разные переменные окружения (подробно — в [Контейнерах и Docker](/content/testing-deploying/containers-and-docker)).

## Секреты

Клиентский бандл — публичный файл. Всё, что в него попало, видно в DevTools любому посетителю.

```bash
# .env.production
VITE_PAYMENT_SECRET=sk_live_51Hx9
PAYMENT_SECRET=sk_live_server_only
```

В проверке `sk_live_51Hx9` оказался строкой в продакшен-бандле, а переменная без префикса — нет. Префикс `VITE_` — не «безопасная переменная», а «опубликовать в клиенте».

| Можно в клиенте | Только на сервере |
| --- | --- |
| публичный ключ платёжной формы, карт, аналитики | секретный ключ платёжного API |
| адрес API | токены доступа к сторонним API |
| DSN мониторинга ошибок | пароли баз данных, ключи подписи |

Если клиенту нужен результат приватного API, запрос идёт через свой сервер или серверную функцию, которая хранит ключ (подробно — в [Безопасности React](/content/reactjs/security)).

### Где хранить

- **локально** — `.env.local`, указанный в `.gitignore`; в репозиторий — `.env.example` с именами переменных без значений;
- **в CI** — зашифрованные секреты, доступные только нужным задачам (подробно — в [CI/CD](/content/advanced-tooling/ci-cd));
- **на хостинге** — переменные окружения платформы;
- **в инфраструктуре** — менеджеры секретов: Vault, Doppler, облачные Secret Manager.

### Если секрет попал в git

В проверке `.env` с ключом закоммитили, затем удалили из индекса и добавили в `.gitignore`. В текущем дереве файла не стало, но `git show HEAD~1:.env` вернул ключ целиком, а `git log -S` нашёл коммит с ним. Любой, у кого есть клон, получит секрет.

Порядок действий: **сначала отозвать ключ** и выпустить новый, затем при необходимости переписать историю (`git filter-repo`) и включить сканирование секретов — GitHub secret scanning, gitleaks в git-хуке и CI.

## Красные флаги в ответе

- **«Префикс `VITE_` делает переменную безопасной».** Наоборот, он публикует её в клиентском бандле.
- **«Режим `staging` — значит, не продакшен-сборка».** `PROD` в нём `true`, отличается только набор переменных.
- **«Соберём отдельно для стенда и для продакшена».** Проверяли один файл, выкладываем другой.
- **«Удалил `.env` из репозитория — проблема решена».** Секрет остаётся в истории, его нужно отозвать.
- **«Стенд может отличаться, главное — код тот же».** Отличия в окружении — причина «на стенде работало».

## Как спрашивают на собеседовании

::question
Зачем нужны разные окружения и почему важно их сходство?

#answer
Окружения разделяют разработку, проверку и настоящих пользователей: локальное, превью, стенд, продакшен. Отличаться должна только конфигурация — тогда успешная проверка на стенде что-то говорит о продакшене.

#more
Сходство — это та же сборка, похожие данные, те же заголовки и CDN. Превью на каждый PR даёт отдельное окружение для ревью до слияния.
::

::question
Чем конфигурация при сборке отличается от конфигурации при запуске?

#answer
При сборке значение встраивается в бандл строкой — смена окружения требует пересборки, и у каждого окружения свой файл. При запуске браузер загружает конфиг — `config.json` или вставку в HTML, — и одна сборка работает во всех окружениях.

#more
Конфигурация при запуске стоит лишнего запроса или серверной вставки, но позволяет продвигать один проверенный артефакт. Для простого статического сайта с одним окружением достаточно конфигурации при сборке.
::

::question
Что значит «собрать один раз, выкладывать много раз»?

#answer
Артефакт собирают один раз и продвигают через стенд в продакшен без пересборки, меняя только конфигурацию при запуске. В продакшен уходит ровно то, что проверили.

#more
При конфигурации при сборке это невозможно: сборки для стенда и продакшена — разные файлы с разными хешами. Контейнеры следуют тому же принципу — один образ, разные переменные окружения.
::

::question
Можно ли хранить ключи в переменных `VITE_` или `NEXT_PUBLIC_`?

#answer
Только публичные — ключ платёжной формы, карт, аналитики. Эти префиксы встраивают значение в клиентский бандл, который видит любой посетитель. Секретные ключи и токены — только на сервере.

#more
Если клиенту нужен приватный API, запрос идёт через свой сервер или серверную функцию, которая хранит ключ. Переменные без префикса Vite в клиентский код не встраивает.
::

::question
Почему `.env` с секретами не коммитят и что делать, если закоммитили?

#answer
Секрет попадает в историю git и остаётся в ней даже после удаления файла — любой клон его содержит. Коммитят только `.env.example` без значений, а секреты держат в CI, на хостинге или в менеджере секретов.

#more
Если секрет попал в историю, его сначала отзывают и выпускают новый — переписывание истории не помогает тем, кто уже склонировал. Затем `git filter-repo` и сканирование секретов в хуках и CI.
::

## Практика

::practice{title="На стенде работало, в продакшене — нет"}
Релиз проверили на стенде, а после выкладки в продакшен главная страница падает. Пайплайн собирает приложение дважды: `vite build --mode staging` для стенда и `vite build` для продакшена.

#solution
Это две разные сборки: в проверке у них разные файлы и хеши, а между сборками могли поменяться зависимости, данные из CMS или переменные CI. На стенде проверяли не то, что ушло в продакшен. Решение — собрать один раз и вынести различия в конфигурацию при запуске:

```js
const config = await fetch('/config.json').then((r) => r.json());
```

```bash
# выкладка: тот же dist, разный config.json
cp config.staging.json dist/config.json      # стенд
cp config.production.json dist/config.json   # продакшен
```

В проверке одна сборка показала адрес стенда или продакшена в зависимости от `config.json`, а в бандле адресов не было. Артефакт сборки сохраняют в CI и выкладывают его же на оба окружения.
::

::practice{title="Секретный ключ в бандле"}
Аудит безопасности нашёл в `assets/index-*.js` строку `sk_live_…` — секретный ключ платёжного сервиса. В `.env.production` он записан как `VITE_PAYMENT_SECRET`.

#solution
Префикс `VITE_` встраивает значение в клиентский код — в проверке ключ оказался строкой в бандле, а переменная без префикса — нет. Порядок:

1. отозвать ключ в кабинете платёжного сервиса и выпустить новый — старый уже публичен;
2. перенести платёжный вызов на сервер:

```js
// сервер или серверная функция
const res = await fetch('https://api.payments.example/charges', {
  method: 'POST',
  headers: { Authorization: `Bearer ${process.env.PAYMENT_SECRET}` },
  body: JSON.stringify({ amount, currency: 'RUB' }),
});
```

3. в клиенте оставить только публичный ключ платёжной формы;
4. добавить сканирование секретов в CI, чтобы строка вида `sk_live_` не проходила проверку.
::
