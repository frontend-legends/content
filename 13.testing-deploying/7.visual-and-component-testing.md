# Визуальное и компонентное тестирование

Функциональные тесты проверяют **логику**, но не ловят **визуальные** баги: съехавший лейаут, неверный цвет, наложение элементов. Для UI этого мало. Здесь - визуальная регрессия, Storybook и компонентное тестирование.

---

## Пробел функциональных тестов

```jsx
expect(screen.getByText('Купить')).toBeInTheDocument(); // ✅ кнопка есть...
// ...но она может быть белой на белом, съехать за экран или перекрыть текст
```

Testing Library проверит, что элемент **в DOM**, но не **как он выглядит**. Визуальные регрессии этот класс ошибок и закрывает.

---

## Визуальная регрессия

Идея: сделать **скриншот** компонента/страницы, сохранить как эталон (baseline), и при каждом прогоне **сравнивать** новый снимок с эталоном по пикселям. Отличия - на ревью человеку.

```
снимок → diff с baseline → есть отличия? → показать → человек одобряет/отклоняет
```

Инструменты:

- **Chromatic** - визуальное тестирование поверх Storybook (от его авторов).
- **Percy** (BrowserStack) - визуальная регрессия в CI.
- **Playwright** - встроенные скриншот-ассершены (`toHaveScreenshot`).
- **Applitools** - сравнение на основе ИИ (устойчивее к незначимым отличиям).

<b class="text-on-semi-light">Сложности</b> - <span class="text-gray">Скриншот-тесты **хрупкие**: рендеринг шрифтов, сглаживание, разные ОС/браузеры и динамический контент (даты, аватары) дают ложные отличия. Поэтому фиксируют окружение (один браузер в Docker), мокают динамику и используют пороги/ИИ-сравнение. Иначе тесты «шумят».</span>

## Storybook

**Storybook** - изолированная мастерская компонентов: каждый компонент и его состояния («stories») разрабатывают, показывают и тестируют **вне** приложения.

```jsx
// Button.stories.tsx
export const Primary = { args: { variant: 'primary', children: 'OK' } };
export const Disabled = { args: { disabled: true, children: 'OK' } };
```

Зачем:

- **Разработка в изоляции** - пилишь компонент без запуска всего приложения.
- **Живая документация** - каталог компонентов и их состояний для команды и дизайнеров.
- **Источник для тестов** - те же stories используются для визуальной регрессии (Chromatic), интеракционных и a11y-тестов.

> Это основа **component-driven development**: сначала компонент в Storybook со всеми состояниями, потом сборка из них приложения.

---

## Компонентное тестирование

Промежуточный уровень между интеграцией (jsdom) и e2e (полное приложение): рендер **отдельного компонента в реальном браузере**.

- **Playwright / Cypress component testing** - монтируют компонент в настоящем браузере и взаимодействуют.
- **Storybook test runner** - прогоняет stories как тесты (рендер без ошибок + play-функции).

<b class="text-on-semi-light">Зачем реальный браузер для компонента</b> - <span class="text-gray">jsdom - эмуляция: не считает реальный лейаут, размеры, не запускает настоящий CSS. Компонентное тестирование в браузере ловит то, что jsdom пропускает (видимость, перекрытия, реальные события), оставаясь быстрее полного e2e.</span>

---

## Snapshot-тестирование

Раннеры умеют сериализовать вывод (DOM/JSON) в **снапшот** и сравнивать при следующих прогонах:

```js
expect(render(<Button />).container).toMatchSnapshot();
```

<b class="text-on-semi-light">Осторожно со снапшотами</b> - <span class="text-gray">Снапшоты **переоценены и легко превращаются в шум**: большие, ломаются при любом изменении разметки, и их «обновляют не глядя» (`-u`), теряя смысл. Полезны для маленького стабильного вывода (сериализатор, конфиг), но не как замена осмысленным ассершенам. Это про сериализованную структуру, а визуальные баги ловит именно скриншот-регрессия.</span>

---

## Доступность

Доступность тоже автоматизируют: **axe-core** (`jest-axe`, аддон Storybook a11y, Playwright `@axe-core/playwright`) проверяет разметку на нарушения ARIA/контраста.

```js
const results = await axe(container);
expect(results).toHaveNoViolations();
```

Это ловит часть проблем автоматически, но не заменяет ручную проверку с клавиатурой и скринридером.

---

## Что когда использовать

```
Логика компонента/поведение     → integration (Testing Library)
Внешний вид не сломался          → визуальная регрессия (Chromatic/Percy)
Каталог + разработка компонентов → Storybook
Реальный браузер для компонента  → component testing (Playwright/Cypress)
Доступность                      → axe (+ ручная проверка)
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Что ловит визуальная регрессия, чего не ловят обычные тесты?</b>
<span class="text-gray">Визуальные баги: съехавший лейаут, неверный цвет, наложения. Функциональные тесты проверяют наличие элемента в DOM, но не его внешний вид. Скриншот сравнивается с эталоном.</span>

<b class="text-on-semi-light">Зачем нужен Storybook?</b>
<span class="text-gray">Разрабатывать и документировать компоненты в изоляции, каталогизировать их состояния и использовать те же stories как источник для визуальных, интеракционных и a11y-тестов.</span>

<b class="text-on-semi-light">Почему скриншот-тесты бывают хрупкими?</b>
<span class="text-gray">Рендеринг шрифтов, сглаживание, разные ОС/браузеры и динамический контент дают ложные отличия. Лечится фиксацией окружения (Docker), моком динамики и порогами/ИИ-сравнением.</span>

<b class="text-on-semi-light">В чём проблема snapshot-тестов?</b>
<span class="text-gray">Большие снапшоты ломаются при любом изменении разметки, и их обновляют не глядя, теряя смысл. Полезны для маленького стабильного вывода, но не как замена осмысленным ассершенам.</span>

<b class="text-on-semi-light">Зачем компонентное тестирование в реальном браузере?</b>
<span class="text-gray">jsdom не считает реальный лейаут и CSS. Браузер ловит видимость, перекрытия и реальные события, оставаясь быстрее полного e2e.</span>
