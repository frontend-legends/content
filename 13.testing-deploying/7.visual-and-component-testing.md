# Визуальные и компонентные тесты

Что проверить, кроме логики: внешний вид через сравнение скриншотов, компоненты в настоящем браузере, Storybook как каталог состояний, снапшоты и автоматическая проверка доступности. Спрашивают, что ловит визуальная регрессия, зачем Storybook и в чём проблема снапшотов. Глубже — почему скриншот-тест падает без изменений кода, почему эталоны хранят для каждой ОС и почему `-u` принимает настоящий баг вместе с косметикой.

::tldr
- **Функциональный тест знает, что кнопка есть, но не как она выглядит:** белая на белом, съехала, перекрыта. Это ловит сравнение скриншотов с эталоном.
- **Скриншот-тесты шумят:** даты, анимации, шрифты и сглаживание дают ложные отличия. Динамику маскируют, а окружение фиксируют — один браузер, одна ОС, часто в Docker.
- **Компонентный тест в настоящем браузере** — середина между jsdom и e2e: один компонент, но с настоящей раскладкой и CSS. Браузерный режим Vitest, компонентные тесты Playwright и Cypress.
- **Storybook** — каталог компонентов во всех состояниях, и те же истории — источник для визуальных, интерактивных и a11y-тестов.
- **Снапшот разметки ломается от любого изменения** и обновляется не глядя. Полезен для маленького стабильного вывода, а не вместо проверок. Автоматический axe находит часть проблем доступности, но не заменяет проверку клавиатурой и скринридером.
::

## Чего не видят функциональные тесты

Сквозной пример — карточка товара: заголовок, дата обновления, синяя кнопка «В корзину».

```js
expect(screen.getByRole('button', { name: 'В корзину' })).toBeTruthy();
```

Тест прошёл бы, будь кнопка белой на белом фоне, уехавшей за край или закрытой другим слоем. В jsdom нет раскладки и отрисовки (подробно — в [Тест-раннерах](/content/testing-deploying/test-runners)), а Testing Library проверяет DOM, а не картинку.

## Визуальная регрессия

Скриншот страницы или компонента сохраняют как **эталон**, а при каждом прогоне сравнивают с ним по пикселям. Отличие — повод для человека посмотреть и решить: это ошибка или задуманное изменение.

```js
await expect(page.locator('.card')).toHaveScreenshot('card.png', {
  mask: [page.locator('#now')],
});
```

В проверке с Playwright:

1. **Первый прогон** упал с `A snapshot doesn't exist … writing actual` и записал эталон. Файл получил имя `card-darwin.png` — Playwright хранит эталоны отдельно для каждой ОС, потому что шрифты и сглаживание отличаются.
2. **Второй прогон без изменений**: тест с маской на дате прошёл, а без маски упал — `N pixels (ratio … of all image pixels) are different`: в карточке выводится текущее время.
3. **Цвет кнопки сменили с синего на красный** — тест упал, хотя функционально ничего не изменилось. Рядом появилась картинка `-diff.png` с подсвеченными отличиями для ревью.
4. **Изменение задумано** — эталон обновили явно, `--update-snapshots`, и следующий прогон прошёл.

### Почему скриншоты шумят

- **динамика** — даты, случайные аватары, реклама: маскируют или подменяют данными;
- **анимации и мигающий курсор** — Playwright по умолчанию останавливает CSS-анимации при снимке, остальное отключают;
- **шрифты и сглаживание** различаются между ОС и версиями браузера: эталоны снимают в одном окружении — обычно в Docker-образе Playwright — и в нём же сравнивают;
- **мелкие отличия** допускают порогами: `maxDiffPixels`, `maxDiffPixelRatio`.

### Инструменты

- **Playwright** — `toHaveScreenshot` с эталонами в репозитории;
- **Chromatic** — облачное сравнение историй Storybook с интерфейсом ревью;
- **Percy**, **Applitools** — облачные сервисы, Applitools сравнивает с учётом структуры страницы, а не только пикселей.

Облачные сервисы снимают проблему разных окружений и дают удобное ревью отличий, но стоят денег и отправляют снимки наружу.

## Компоненты в настоящем браузере

Компонентный тест монтирует один компонент — не всё приложение — в настоящем браузере. Это середина между интеграционным тестом в jsdom и e2e.

В проверке один и тот же тест — ширина кнопки и баннер, перекрывающий её, — в jsdom упал с `expected +0 to be 200`, а в браузерном режиме Vitest прошёл: ширина 200, а `elementFromPoint` над кнопкой вернул баннер.

```js
// vitest.config.js
import { playwright } from '@vitest/browser-playwright';

export default defineConfig({
  test: {
    browser: { enabled: true, provider: playwright(), instances: [{ browser: 'chromium' }] },
  },
});
```

Варианты:

- **браузерный режим Vitest** — те же тесты и API, но в Chromium, Firefox или WebKit через Playwright;
- **компонентные тесты Playwright и Cypress** — монтирование компонента своим раннером;
- **Storybook** — истории запускаются как тесты.

Цена — медленнее jsdom и нужен браузер в CI. Поэтому в браузер переносят тесты, которым важны раскладка, CSS, фокус и настоящие события, а логику оставляют в jsdom.

## Storybook

**Storybook** — мастерская компонентов: каждый компонент и его состояния — истории — разрабатывают и показывают вне приложения.

```js
// Button.stories.js
export default { component: Button };

export const Primary = { args: { variant: 'primary', children: 'В корзину' } };
export const Disabled = { args: { disabled: true, children: 'В корзину' } };
export const Loading = { args: { loading: true, children: 'В корзину' } };
```

Зачем:

- **разработка в изоляции** — состояние «загрузка» или «ошибка» не нужно воспроизводить в приложении;
- **живой каталог** для команды и дизайнеров: все варианты компонентов в одном месте;
- **источник тестов** — истории становятся визуальными тестами в Chromatic, интерактивными через функцию `play` с действиями пользователя и a11y-проверками аддоном.

Подход «сначала компонент со всеми состояниями в Storybook, потом страница из компонентов» называют **component-driven development**. Каталог компонентов дизайн-системы — в [UI-библиотеках](/content/ecosystem-libs/ui-component-libraries).

## Снапшоты

Раннер сериализует вывод — разметку, объект — в файл и при следующих прогонах сравнивает:

```js
expect(card()).toMatchSnapshot();
```

В проверке у карточки было два теста: снапшот и явная проверка `expect(card()).toContain('<b>1 200 ₽</b>')`.

- Класс `card` переименовали в `product-card` — для пользователя ничего не изменилось, а снапшот упал: `Snapshot … mismatched`.
- Затем цена сломалась — `NaN ₽` — и тесты запустили с `-u`, «обновить снапшоты». Снапшот молча переписался вместе с `NaN`, и упала только явная проверка цены.

Так снапшоты и вырождаются: большие, ломаются от каждой правки разметки, их обновляют целиком, не читая разницу, и вместе с косметикой принимают настоящие ошибки. Они полезны для маленького стабильного вывода — сериализатора, сгенерированного конфига, сообщения об ошибке — и с `toMatchInlineSnapshot`, когда ожидаемое видно прямо в тесте. Для внешнего вида нужны скриншоты, а для поведения — явные проверки.

## Доступность

Часть проблем доступности находят автоматически. **axe-core** проверяет страницу по правилам WCAG — аддон Storybook, `@axe-core/playwright`, `vitest-axe`.

В проверке на странице с кнопкой «Купить» функциональный тест прошёл — кнопка видима и находится по роли. axe нашёл четыре нарушения:

| Правило | Что не так |
| --- | --- |
| `color-contrast` | светло-серый текст на белой кнопке |
| `button-name` | кнопка-иконка без доступного имени |
| `image-alt` | картинка без `alt` |
| `label` | поле email без подписи |

Автоматика не видит, понятен ли порядок фокуса, осмысленны ли подписи и удобно ли пользоваться с клавиатуры и скринридером, — это проверяют руками. Основы ARIA и доступных компонентов — в [Доступности](/content/html/accessibility).

## Что когда

| Вопрос | Инструмент |
| --- | --- |
| логика и поведение компонента | интеграционный тест в jsdom |
| раскладка, CSS, фокус, перекрытие | компонентный тест в браузере |
| внешний вид не сломался | скриншот-сравнение: Playwright, Chromatic |
| каталог и разработка состояний | Storybook |
| автоматические проблемы доступности | axe, затем ручная проверка |
| маленький стабильный вывод | снапшот, лучше встроенный |

---

## Красные флаги в ответе

- **«Тест нашёл кнопку — значит, её видно».** DOM не знает о цвете, раскладке и перекрытии.
- **«Скриншот-тест упал — обновлю эталон».** Сначала смотрят отличие: это может быть настоящая регрессия.
- **«Эталоны сниму на своём Mac, а сравнивать будет CI на Linux».** Шрифты и сглаживание отличаются, тесты будут шуметь.
- **«Снапшоты заменяют проверки».** `-u` переписывает их вместе с ошибками.
- **«axe зелёный — значит, доступно».** Автоматика находит только часть проблем.

## Как спрашивают на собеседовании

::question
Что ловит визуальная регрессия, чего не ловят обычные тесты?

#answer
Внешний вид: съехавшую раскладку, неверный цвет, обрезанный текст, перекрытие элементов. Функциональный тест проверяет наличие элемента в DOM, а скриншот сравнивается с эталоном по пикселям.

#more
Отличие — повод для ревью человеком: это ошибка или задуманное изменение. Задуманное принимают обновлением эталона, и он хранится в репозитории или облачном сервисе.
::

::question
Почему скриншот-тесты бывают нестабильными?

#answer
Динамические данные — даты, случайные картинки, — анимации и различия в отрисовке шрифтов между ОС и версиями браузера дают ложные отличия.

#more
Динамику маскируют или подменяют, анимации останавливают, эталоны снимают и сравнивают в одном окружении — обычно в Docker. Playwright хранит эталоны отдельно для каждой ОС. Мелкие отличия допускают порогами `maxDiffPixels` и `maxDiffPixelRatio`.
::

::question
Зачем нужен Storybook?

#answer
Разрабатывать и показывать компоненты вне приложения во всех состояниях, вести живой каталог для команды и дизайнеров и использовать те же истории как источник визуальных, интерактивных и a11y-тестов.

#more
Функция `play` описывает действия пользователя в истории, и её запускают как тест. Chromatic сравнивает скриншоты историй. Подход называют component-driven development.
::

::question
В чём проблема снапшот-тестов?

#answer
Большой снапшот разметки ломается от каждой правки, даже не меняющей поведение, и его обновляют целиком через `-u`, не читая разницу. Вместе с косметикой так принимают и настоящие ошибки.

#more
Снапшоты уместны для маленького стабильного вывода, лучше встроенные — `toMatchInlineSnapshot`, — где ожидаемое видно в тесте. Для поведения — явные проверки, для внешнего вида — скриншоты.
::

::question
Зачем тестировать компонент в настоящем браузере?

#answer
В jsdom нет раскладки и CSS: размеры — нули, перекрытие и видимость не проверить. Браузерный режим Vitest или компонентные тесты Playwright и Cypress монтируют один компонент в настоящем браузере и видят это, оставаясь быстрее e2e.

#more
В браузер переносят тесты, которым важны раскладка, стили, фокус и настоящие события. Логику оставляют в jsdom — так быстрее и не нужен браузер в каждом прогоне.
::

::question
Можно ли автоматизировать проверку доступности?

#answer
Частично: axe-core находит нарушения вроде низкого контраста, кнопок без имени, картинок без `alt` и полей без подписи. Его подключают в Storybook, Playwright и тестах компонентов.

#more
Автоматика не проверяет, логичен ли порядок фокуса, понятны ли подписи и удобно ли работать с клавиатуры и скринридером. Это ручная проверка, а axe — сетка от регрессий.
::

## Практика

::practice{title="Скриншот-тест падает каждый день"}
Скриншот-тест карточки товара падает на каждом прогоне, хотя код не меняли. В отчёте отличается небольшая область в середине карточки.

#solution
В карточке выводится дата обновления — каждый прогон новая. Динамику маскируют:

```js
await expect(page.locator('.card')).toHaveScreenshot('card.png', {
  mask: [page.locator('#now')],
});
```

В проверке тест без маски упал на втором прогоне без изменений кода, а с маской прошёл. Если тест падает только в CI, а локально проходит, причина обычно в другом: эталон снят на другой ОС. Эталоны снимают в том же Docker-образе, где идут тесты.
::

::practice{title="Снапшоты обновили вместе с багом"}
После рефакторинга упали двадцать снапшот-тестов. Разработчик запустил `vitest -u`, всё позеленело. В релиз ушла карточка с ценой «NaN ₽».

#solution
`-u` переписывает снапшоты на текущий вывод, каким бы он ни был. В проверке снапшот принял `NaN ₽`, а упала только явная проверка цены:

```js
test('цена в карточке', () => {
  expect(card()).toContain('<b>1 200 ₽</b>');
});
```

Важное поведение проверяют явными проверками, а снапшоты держат маленькими — тогда разницу при обновлении реально прочитать. Для внешнего вида карточки нужен скриншот-тест с ревью отличий, а не снапшот разметки.
::
