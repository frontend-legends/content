# Модульные и интеграционные тесты

Как писать повседневные тесты, которые не врут: что считать единицей, как искать элементы так, как их видит пользователь, принципы FIRST, изоляция, асинхронность и детерминированность. Спрашивают, чем модульный тест отличается от интеграционного, в чём главный принцип Testing Library и что делает тест хрупким. Глубже — почему тест без `await` бывает зелёным при неверном результате, почему тест падает только в CI и как найти тест, зависящий от порядка.

::tldr
- **Единица — не обязательно функция:** модульный тест проверяет кусок поведения изолированно, интеграционный — несколько частей вместе. Граница — в том, что подменено.
- **Ищи элементы как пользователь:** по роли и доступному имени, подписи, тексту. Такой тест переживает смену разметки и классов и заодно проверяет доступность.
- **FIRST:** быстрые, независимые, повторяемые, сами говорят «прошёл» или «упал» и пишутся вовремя.
- **Асинхронный тест должен дождаться результата:** проверка внутри `then` без `return` или `await` теряется, и тест зеленеет при любом ответе.
- **Детерминированность:** время, часовой пояс, локаль, случайность и сеть фиксируют или подменяют — иначе тест зелёный у разработчика и красный в CI.
::

## Модульный и интеграционный

Сквозной пример — карточка товара: `formatPrice`, модуль корзины, компонент с кнопкой «В корзину», запрос к API.

**Модульный тест** проверяет единицу поведения в изоляции:

```js
test('formatPrice', () => {
  expect(formatPrice(1200)).toBe('1 200 ₽');
});
```

**Интеграционный** — части вместе: компонент рендерится, пользователь кликает, корзина обновляется, сеть подменена на границе:

```js
test('кнопка добавляет товар в корзину', async () => {
  render(ProductCard, { product });
  await user.click(screen.getByRole('button', { name: 'В корзину' }));
  expect(screen.getByText('В корзине: 1')).toBeTruthy();
});
```

Что считать единицей — вопрос договорённости. «Одиночный» модульный тест подменяет всех соседей, «общительный» — оставляет настоящие модули и подменяет только внешний мир: сеть, время, хранилище. Чем меньше подменено, тем ближе тест к реальности, — в [Стратегии тестирования](/content/testing-deploying/testing-strategy-and-pyramid) модульные тесты с моками были зелёными при сломанной связке. Как тестировать компоненты React и Vue — в [Тестировании React](/content/reactjs/testing-react) и [Тестировании Vue](/content/vuejs/testing-vue).

## Как пользователь

Принцип Testing Library:

> The more your tests resemble the way your software is used, the more confidence they can give you.

Testing Library есть для DOM без фреймворка, React, Vue, Svelte, Angular. Она намеренно не даёт доступа к состоянию и пропсам компонента — только к DOM, — и ищет элементы по тому, что видит пользователь и скринридер:

| Запрос | Когда |
| --- | --- |
| `getByRole('button', { name: 'В корзину' })` | почти всегда: роль и доступное имя |
| `getByLabelText('Email')` | поля форм |
| `getByText('Корзина пуста')` | текст без роли |
| `getByTestId('cart-total')` | когда остальное не подходит |

В проверке кнопку искали двумя способами. После замены разметки — `<div class="card">` на `<article>`, класс `btn-primary` на `add-to-cart` — поиск по `.btn-primary` упал, а `getByRole('button', { name: 'В корзину' })` остался зелёным: для пользователя ничего не изменилось.

Поиск по роли — ещё и проверка доступности. Кнопку-иконку без подписи `getByRole` не нашёл: `Unable to find an accessible element with the role "button" and name "В корзину"`. Тест сообщает то же, что скринридер: у кнопки нет имени. Исправление — `aria-label` или видимый текст, а не `getByTestId`.

## FIRST

- **Fast** — быстрые, иначе их перестают запускать.
- **Independent** — не зависят от других тестов и порядка запуска.
- **Repeatable** — одинаковый результат на любой машине и при любом запуске.
- **Self-validating** — сами говорят «прошёл» или «упал», без чтения вывода глазами.
- **Timely** — пишутся вместе с кодом, а не через месяц.

### Независимость

Тесты одного файла делят модули (подробно — в [Тест-раннерах](/content/testing-deploying/test-runners)), поэтому состояние, оставленное одним тестом, видит следующий. В проверке тест «приветствие по имени» рассчитывал на пользователя, которого записал тест «вход сохраняет пользователя». По порядку всё было зелёным, а с `--sequence.shuffle` нашёлся порядок, в котором приветствие упало.

```bash
vitest run --sequence.shuffle
```

Перемешивание стоит включать периодически, чтобы находить такие связи. Исправление — каждый тест сам готовит свои данные, а общее состояние сбрасывается:

```js
beforeEach(() => { session.user = null; });
afterEach(() => { vi.restoreAllMocks(); });
```

## Асинхронность

Интерфейс и данные асинхронны, и тест должен дождаться результата. В проверке:

```js
const load = () => new Promise((r) => setTimeout(() => r(2), 10));

test('then без return', () => {
  load().then((v) => expect(v).toBe(3));
});
```

Тест прошёл, прогон завершился с кодом 0, хотя `2 !== 3`: функция теста вернулась сразу, раннер счёл его успешным, а проверка выполнилась позже — или не выполнилась вовсе. Правильно — `async` и `await`:

```js
test('загрузка', async () => {
  expect(await load()).toBe(2);
});
```

Vitest частично страхует: `expect(load()).resolves.toBe(3)` без `await` он отследил и пометил тест упавшим. Но промис внутри `then` без `return` не видит ни один раннер — помогает правило линтера `no-floating-promises` или `vitest/valid-expect`.

Для интерфейса Testing Library ждёт появления элемента сама: `findByText` и `waitFor` повторяют поиск, пока элемент не появится или не истечёт время (подробно — в [Тестировании React](/content/reactjs/testing-react)).

## Детерминированность

Тест не должен зависеть от того, когда, где и сколько раз его запускают.

### Часовой пояс и локаль

```js
const deliveryDate = (iso) =>
  new Intl.DateTimeFormat('ru', { day: 'numeric', month: 'long' }).format(new Date(iso));

expect(deliveryDate('2026-11-15T22:30:00Z')).toBe('16 ноября');
```

В проверке тест прошёл с `TZ=Europe/Moscow` — «у разработчика» — и упал с `TZ=UTC` — «в CI»: в UTC это ещё 15 ноября. Исправления: передавать часовой пояс явно (`timeZone: 'Europe/Moscow'` — этот вариант прошёл в обоих поясах) или фиксировать `TZ` для всего прогона в конфиге и CI. Локаль — то же: `toLocaleString()` без аргументов зависит от машины.

### Время, случайность и сеть

```js
vi.useFakeTimers();
vi.setSystemTime(new Date('2026-11-15T10:00:00Z'));   // «сейчас» в тесте

vi.spyOn(Math, 'random').mockReturnValue(0.5);         // предсказуемая «случайность»
```

Сеть подменяют на границе — MSW перехватывает запросы и отвечает заданными данными. Подробно о подмене времени, модулей и сети — в [Моках и дублёрах](/content/testing-deploying/mocking-and-test-doubles).

## Красные флаги в ответе

- **«Модульный тест — это тест одной функции».** Единица — кусок поведения, граница определяется тем, что подменено.
- **«Найду кнопку по классу».** Тест сломается при смене разметки, хотя для пользователя ничего не изменится.
- **«Проверю в `then`, зачем `await`».** Без `await` или `return` проверка теряется, и тест зелёный при любом результате.
- **«У меня проходит, значит, CI глючит».** Чаще всего тест зависит от часового пояса, локали, времени или порядка.
- **«Не нашёлся по роли — возьму `data-testid`».** Сначала стоит проверить, есть ли у элемента доступное имя.

## Как спрашивают на собеседовании

::question
Чем модульный тест отличается от интеграционного?

#answer
Модульный проверяет единицу поведения изолированно, интеграционный — несколько частей вместе: компонент, события, данные. Граница — в том, что подменено.

#more
«Общительный» модульный тест оставляет настоящих соседей и подменяет только внешний мир — сеть, время, хранилище, — и потому ловит несостыковки между модулями. Для интерфейса основа — интеграционные тесты.
::

::question
В чём главный принцип Testing Library?

#answer
Тест должен работать с интерфейсом так, как пользователь: искать элементы по роли, доступному имени, подписи и тексту и проверять видимый результат, а не состояние компонента.

#more
Поэтому библиотека не даёт доступа к состоянию и пропсам. Приоритет запросов — роль, подпись, текст, и только в крайнем случае `data-testid`. Если элемент не находится по роли и имени, скорее всего, у него проблема с доступностью.
::

::question
Что делает тест хрупким?

#answer
Зависимость от реализации — классов, структуры разметки, внутреннего состояния, — от порядка запуска, времени, часового пояса, случайности и сети. Такой тест падает без настоящей поломки.

#more
Каждое ложное падение учит команду игнорировать красные прогоны. Поиск по ролям, фиксированное время и пояс, независимые данные и подмена сети на границе убирают большинство причин.
::

::question
Почему асинхронный тест может пройти при неверном результате?

#answer
Если функция теста не ждёт промис — нет `await` и `return`, — раннер считает тест завершённым сразу, а проверка выполняется позже или не выполняется вовсе.

#more
Vitest отслеживает `expect(...).resolves` без `await` и помечает тест упавшим, но проверку внутри `then` без `return` не видит. Помогают правила линтера `no-floating-promises` и `vitest/valid-expect`.
::

::question
Как сделать тест детерминированным?

#answer
Зафиксировать всё, что зависит от окружения: время — фейковыми таймерами и `setSystemTime`, часовой пояс и локаль — явными параметрами или `TZ` в конфиге, случайность — подменой, сеть — MSW. И сбрасывать состояние между тестами.

#more
Скрытые зависимости от порядка находит запуск с перемешиванием — `--sequence.shuffle`. Тест должен давать одинаковый результат на машине разработчика и в CI.
::

::question
Что такое принципы FIRST?

#answer
Fast, Independent, Repeatable, Self-validating, Timely — быстрые, независимые, повторяемые, сами сообщают результат и пишутся вместе с кодом.

#more
Чаще всего нарушают Independent и Repeatable: общее состояние между тестами и зависимость от времени или часового пояса. Именно они делают тесты нестабильными.
::

## Практика

::practice{title="Тест падает только в CI"}
Тест даты доставки проходит у всех разработчиков, а в CI падает: ожидалось «16 ноября», получено «15 ноября».

```js
expect(deliveryDate('2026-11-15T22:30:00Z')).toBe('16 ноября');
```

#solution
`Intl.DateTimeFormat` без `timeZone` берёт часовой пояс машины. У разработчиков Москва, в CI — UTC, где это ещё 15 ноября. В проверке тот же тест прошёл с `TZ=Europe/Moscow` и упал с `TZ=UTC`.

```js
// 1. часовой пояс — часть контракта функции
new Intl.DateTimeFormat('ru', { day: 'numeric', month: 'long', timeZone: 'Europe/Moscow' });

// 2. или один пояс для всего прогона
// package.json: "test": "TZ=UTC vitest"
```

Первый вариант лучше: дата доставки зависит от пояса магазина, а не от компьютера, на котором запущен код. Вариант с явным поясом прошёл в обоих окружениях.
::

::practice{title="Зелёный тест, сломанная загрузка"}
Функция загрузки товара стала возвращать неверную цену, но тест остался зелёным:

```js
test('загружает цену', () => {
  loadProduct(7).then((p) => expect(p.price).toBe(1200));
});
```

#solution
Тест не ждёт промис: функция возвращается сразу, раннер засчитывает успех, а проверка выполняется позже или не выполняется. В проверке такой тест прошёл с кодом 0 при `2 !== 3`.

```js
test('загружает цену', async () => {
  const p = await loadProduct(7);
  expect(p.price).toBe(1200);
});
```

Чтобы ошибка не повторялась, включают правило линтера `@typescript-eslint/no-floating-promises` или `vitest/valid-expect` — они находят промис, который никто не ждёт.
::
