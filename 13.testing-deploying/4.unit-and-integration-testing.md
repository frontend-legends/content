# Unit и интеграционные тесты

Основа повседневного тестирования. Главный принцип, который проверяют на собесе: **тестируй поведение, а не реализацию**. Хороший тест переживает рефакторинг и падает только тогда, когда реально сломалось то, что важно пользователю.

> Фреймворк-специфика (React Testing Library, Vue Test Utils) - в [тестировании React](/content/reactjs/testing-react) и [Vue](/content/vuejs/testing-vue). Здесь - общие принципы.

---

## Unit vs integration

- **Unit** - проверяет **одну** единицу (функцию, хук, утилиту) в изоляции. Быстро, узко.
- **Integration** - проверяет **несколько** частей вместе: компонент + его события + данные. Ближе к реальности.

```js
// Unit: чистая функция в изоляции
test('formatPrice', () => {
  expect(formatPrice(1000)).toBe('1 000 ₽');
});
```

```jsx
// Integration: компонент + взаимодействие + результат
test('добавление в корзину обновляет счётчик', async () => {
  render(<Product />);
  await userEvent.click(screen.getByRole('button', { name: /в корзину/i }));
  expect(screen.getByText('В корзине: 1')).toBeInTheDocument();
});
```

---

## Философия Testing Library

```
"The more your tests resemble the way your software is used,
 the more confidence they can give you."
```

Testing Library (для React, Vue, Svelte и др.) реализует принцип: **взаимодействуй с UI как пользователь** - ищи элементы по тому, что видно (роль, текст, label), а не по классам и внутренним структурам, и проверяй видимый результат.

<b class="text-on-semi-light">Поэтому</b> - <span class="text-gray">Testing Library намеренно **не даёт** доступа к state/props компонента - только к DOM. Это заставляет тестировать поведение, а не реализацию. Приоритет поиска (`getByRole` → `getByLabelText` → `getByText` → `getByTestId`) завязан на доступность: ищешь так, как видит пользователь и скринридер.</span>

## Хороший тест vs хрупкий

| Хороший тест | Хрупкий тест |
|--------------|--------------|
| проверяет **поведение** | проверяет **реализацию** |
| переживает рефакторинг | падает при любом изменении кода |
| читается как описание фичи | завязан на внутренние имена/структуру |
| изолирован, детерминирован | зависит от порядка, flaky |

```jsx
// ❌ хрупкий: лезет во внутренний state и структуру
expect(wrapper.state().count).toBe(1);

// ✅ хороший: проверяет, что видит пользователь
expect(screen.getByText('Счёт: 1')).toBeInTheDocument();
```

## Принципы FIRST

Хорошие тесты следуют **FIRST**:

- **Fast** - быстрые (иначе их перестают гонять).
- **Independent** - не зависят друг от друга и от порядка.
- **Repeatable** - одинаковый результат при каждом запуске (нет случайности/времени/сети).
- **Self-validating** - сами говорят pass/fail, без ручной проверки.
- **Timely** - пишутся вовремя (рядом с кодом).

---

## Изоляция

Каждый тест должен начинаться с **чистого состояния**. Общий state между тестами - источник «работает по отдельности, падает вместе».

```js
afterEach(() => {
  cleanup();        // размонтировать компоненты
  vi.clearAllMocks(); // сбросить моки
});
```

Раннеры обычно изолируют тестовые файлы автоматически, но общий модульный state (синглтоны, кеши) нужно сбрасывать вручную.

---

## Асинхронность

UI и данные асинхронны - тесты это учитывают:

```jsx
// дождаться появления элемента после загрузки
expect(await screen.findByText('Загружено')).toBeInTheDocument();

// проверить отсутствие
expect(screen.queryByText('Ошибка')).not.toBeInTheDocument();
```

`findBy*` ждёт появления, `queryBy*` возвращает `null` (для проверки отсутствия), `waitFor` ждёт выполнения условия.

---

## Детерминированность

Тест не должен зависеть от **времени**, **случайности** или **сети** - иначе он flaky.

```js
vi.useFakeTimers();           // контролировать время
vi.setSystemTime(new Date('2026-01-01')); // фиксировать дату
// сеть мокать через MSW (см. следующую главу)
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем unit-тест отличается от интеграционного?</b>
<span class="text-gray">Unit проверяет одну единицу в изоляции (функция, хук), integration - несколько частей вместе (компонент + события + данные). Integration ближе к реальному использованию.</span>

<b class="text-on-semi-light">Главный принцип Testing Library?</b>
<span class="text-gray">Тестировать поведение, как им пользуется пользователь: искать элементы по роли/тексту/label, проверять видимый результат, а не внутренний state. Тест не должен ломаться при рефакторинге без изменения поведения.</span>

<b class="text-on-semi-light">Что делает тест хрупким?</b>
<span class="text-gray">Зависимость от реализации (внутренний state, имена, структура), от порядка выполнения, от времени/случайности/сети. Такой тест падает без реальной поломки.</span>

<b class="text-on-semi-light">Что такое принципы FIRST?</b>
<span class="text-gray">Fast, Independent, Repeatable, Self-validating, Timely - быстрые, независимые, воспроизводимые, самопроверяющиеся и написанные вовремя.</span>

<b class="text-on-semi-light">Как сделать тест детерминированным?</b>
<span class="text-gray">Убрать зависимость от времени (фейковые таймеры), случайности (фиксировать) и сети (мокать через MSW). Изолировать состояние между тестами.</span>
