# Введение в тестирование и деплой

Как изменение доходит от редактора до пользователя и где на этом пути ловят ошибки: проверка типов и линтер, модульные, интеграционные и e2e-тесты, выкладка с возможностью отката и мониторинг в продакшене. Спрашивают, зачем вообще писать тесты, гарантирует ли что-то стопроцентное покрытие и что такое «сдвиг влево». Глубже — какие ошибки ловит каждый слой, почему тест на баг пишут до исправления и почему хорошо протестированный код всё равно нужно уметь откатывать.

::tldr
- **Тесты и выкладка служат одной цели — уверенности:** тесты — что изменение не сломало поведение, выкладка и мониторинг — что оно работает у настоящих пользователей.
- **Каждый слой ловит свои ошибки:** типы — неверные данные без запуска кода, тесты — неверную логику, e2e — поломку целого сценария, мониторинг — то, что дошло до продакшена.
- **Тест стоит денег:** его пишут, поддерживают и ждут. Цель — больше уверенности за меньшую цену, а не больше тестов. Тест, проверяющий детали реализации, ломается при каждом рефакторинге и вредит.
- **Сдвиг влево:** ошибку дешевле найти раньше — в редакторе, в хуке, в CI, — чем на стенде или у пользователя.
- **Тесты не доказывают отсутствие ошибок,** поэтому выкладка должна уметь быстро откатываться, а продакшен — сообщать о сбоях.
::

---

## От коммита до продакшена

Сквозной пример главы — интернет-магазин: корзина считает сумму со скидкой, оформление заказа ходит в API оплаты, сайт выкладывается на CDN несколько раз в день.

Путь изменения:

```text
редактор → коммит → CI: линтер, типы, тесты, сборка → слияние → выкладка → мониторинг
            ▲ ловим до пользователей                                      ▲ ловим у пользователей
```

Как устроен сам конвейер CI — шаги, кеш, обязательные проверки — разобрано в [CI/CD](/content/advanced-tooling/ci-cd). Эта глава — о том, что в нём проверяется и что происходит после.

---

## Что ловит каждый слой

В проверке функция корзины содержала две ошибки: вызов с ценой-строкой `'1200'` и скидку, применённую дважды.

```ts
export function total(items: { price: number; qty: number }[], discount = 0): number {
  const sum = items.reduce((s, i) => s + i.price * i.qty, 0);
  const discounted = sum * (1 - discount);
  return Math.round(discounted * (1 - discount));   // скидка второй раз
}
```

- **Проверка типов** нашла строку без запуска кода: `Type 'string' is not assignable to type 'number'`. После исправления вызова `tsc` успокоился, хотя двойная скидка осталась: типы не знают, что 10% от 2000 — это 1800.
- **Тест** нашёл логику: `expected 1620 to be 1800`.
- **E2E-тест** нашёл бы то, чего не видят оба: кнопка «Оформить» не нажимается, потому что её перекрыл баннер.
- **Мониторинг** покажет то, что не воспроизвелось ни в одном тесте: падение в старом Safari или ошибку API оплаты под нагрузкой.

Ни один слой не заменяет остальные. Какие тесты писать и в какой пропорции — в [Стратегии тестирования](/content/testing-deploying/testing-strategy-and-pyramid).

## Уверенность и цена

Тесты окупаются тем, что дают:

- **менять код без страха:** рефакторинг и новые функции не ломают старое незаметно;
- **закрывать регрессии:** исправленный баг закрепляют тестом, и он не возвращается;
- **документировать поведение:** тест показывает, как код должен работать;
- **сигнал о дизайне:** код, который трудно протестировать, обычно слишком связан.

Но у каждого теста есть цена: время на написание, поддержку при изменениях и ожидание в CI. Плохой тест — медленный, нестабильный или проверяющий внутренности вместо поведения — стоит дороже, чем даёт: он падает при рефакторинге, когда для пользователя ничего не изменилось, и учит команду игнорировать красные прогоны. Почему стопроцентное покрытие не равно уверенности — в [Покрытии и TDD](/content/testing-deploying/coverage-and-tdd).

### Тест на найденный баг

Когда баг найден, сначала пишут тест, который его воспроизводит, и только потом исправляют. В проверке тест «скидка 10% применяется один раз» сначала упал — значит, он действительно ловит этот баг. После исправления он прошёл и дальше стережёт, чтобы баг не вернулся.

```ts
test('скидка 10% применяется один раз', () => {
  expect(total([{ price: 1000, qty: 2 }], 0.1)).toBe(1800);
});
```

Тест, написанный после исправления, может пройти и на сломанном коде — проверить это можно, только увидев его красным.

## Сдвиг влево

Чем позже найдена ошибка, тем дороже она обходится:

```text
дешевле ◄──────────────────────────────────────────► дороже
редактор → git-хук → CI → стенд → продакшен
секунды    минуты    минуты  часы    инцидент, откат, разбор
```

Отсюда принцип **сдвига влево**: переносить проверки ближе к моменту написания кода. Типы и линтер — в редакторе, быстрые проверки — в git-хуках (подробно — в [Git-хуках](/content/advanced-tooling/git-hooks-and-quality-gates)), тесты и сборка — в CI до слияния, e2e — на превью каждого PR.

---

## Надёжная выкладка

Безупречно протестированный код бесполезен, если выкладка роняет сайт. Вторая половина главы — о том, как изменение доходит до пользователя:

- **окружения и конфигурация** — одна сборка для стенда и продакшена, секреты вне клиентского кода;
- **хостинг** — статика на CDN, сервер, serverless или edge;
- **стратегии выкладки** — без простоя, с постепенным включением и быстрым откатом;
- **кеш** — хешированные ассеты надолго, `index.html` — всегда свежий;
- **контейнеры** — одинаковое окружение от CI до продакшена;
- **мониторинг** — ошибки и производительность у настоящих пользователей.

Тесты снижают вероятность сбоя, а выкладка и мониторинг — его цену: если ошибка всё-таки дошла, её быстро замечают и откатывают.

---

## Красные флаги в ответе

- **«Тесты гарантируют, что багов нет».** Они повышают уверенность, но не доказывают отсутствие ошибок.
- **«Есть TypeScript — тесты не нужны».** Типы ловят неверные данные, но не неверную логику.
- **«Чем больше тестов, тем лучше».** Хрупкие и медленные тесты стоят дороже, чем дают.
- **«Тест на баг напишу после исправления».** Не увидев его красным, нельзя знать, что он ловит этот баг.
- **«Всё протестировано, откат не нужен».** Часть ошибок проявляется только в продакшене.

## Как спрашивают на собеседовании

::question
Зачем писать тесты?

#answer
Чтобы менять код без страха: тесты ловят регрессии при рефакторинге и новых функциях, закрепляют исправленные баги, документируют поведение и подсвечивают слишком связанный код.

#more
Тесты не доказывают отсутствие ошибок — они повышают уверенность до разумного уровня за разумную цену. Поэтому важна не их численность, а то, какое поведение они защищают.
::

::question
Гарантирует ли стопроцентное покрытие отсутствие багов?

#answer
Нет. Покрытие показывает, какие строки выполнились во время тестов, но не то, проверили ли тесты результат. Можно выполнить каждую строку и не поймать ни одной ошибки.

#more
Покрытие полезно, чтобы найти непроверенный код, но плохо работает как цель. Качество тестов лучше показывает мутационное тестирование — подробно в истории про покрытие.
::

::question
Что значит баланс уверенности и цены?

#answer
Каждый тест стоит времени на написание, поддержку и ожидание в CI. Цель — максимум уверенности за минимум цены: тестировать важное для пользователя поведение и не тестировать детали реализации.

#more
Тест на внутренности падает при рефакторинге, когда поведение не изменилось, и приучает команду игнорировать красные прогоны. Нестабильный тест вреден по той же причине.
::

::question
Что такое сдвиг влево?

#answer
Принцип ловить ошибки как можно раньше: в редакторе, в git-хуке, в CI до слияния, а не на стенде и не у пользователей. Чем раньше найдена ошибка, тем дешевле её исправить.

#more
На практике это типы и линтер в редакторе, быстрые проверки в хуках, тесты и сборка как обязательные проверки PR, e2e на превью. Мониторинг продакшена — последняя линия, а не основная.
::

::question
Почему тест на баг пишут до исправления?

#answer
Чтобы убедиться, что тест действительно воспроизводит баг: он должен упасть на сломанном коде и пройти после исправления. Тест, написанный после, может проходить и без исправления.

#more
Этот тест остаётся в наборе и не даёт багу вернуться. Тот же цикл — красный, затем зелёный — лежит в основе TDD.
::

## Практика

::practice{title="Баг со скидкой вернулся"}
Месяц назад исправили двойное применение скидки в корзине. После рефакторинга расчёта баг вернулся, и заметили его только по жалобам покупателей.

#solution
Исправление не закрепили тестом. Порядок такой: сначала тест, воспроизводящий баг, затем исправление.

```ts
test('скидка 10% применяется один раз', () => {
  expect(total([{ price: 1000, qty: 2 }], 0.1)).toBe(1800);
});
```

В проверке этот тест на сломанной версии упал с `expected 1620 to be 1800`, а после исправления прошёл. Теперь рефакторинг, который снова применит скидку дважды, остановится в CI, а не у покупателей.
::

::practice{title="Строка вместо числа"}
Цена из API пришла строкой `'1200'`, корзина посчитала `'1200' * 1` правильно, но `'1200' + 300` дало `'1200300'`. Тесты прошли — в них цены были числами.

#solution
Тесты проверяют те данные, которые в них положили. Ошибку неверного типа ловит статическая проверка, если граница с API типизирована:

```ts
type Item = { price: number; qty: number };
total([{ price: '1200', qty: 1 }]);   // error TS2322
```

В проверке `tsc` нашёл это без запуска кода. Но типы — это обещание: если API может прислать строку, ответ проверяют на рантайме схемой (подробно — в [Формах и валидации](/content/ecosystem-libs/forms-and-validation)), а `tsc` запускают в CI как обязательную проверку.
::
