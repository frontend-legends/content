# Стратегии выкладки

Как выложить новую версию без простоя и с быстрым откатом: замена разом, поочерёдная, blue-green и canary, флаги функций и разделение выкладки и релиза, совместимость версий, откат и превью. Спрашивают, чем blue-green отличается от canary, как выкатить без простоя и зачем флаги функций. Глубже — почему во время поочерёдной выкладки страница бывает пустой, почему canary по случайному числу хуже, чем по пользователю, и почему поле API нельзя просто переименовать.

::tldr
- **Наивная выкладка — остановить старое и запустить новое** — даёт простой и медленный откат. Поочерёдная замена, blue-green и canary держат старую версию в работе, пока новая готовится.
- **Blue-green** переключает весь трафик на заранее поднятое окружение и так же быстро обратно. **Canary** показывает новую версию малой доле пользователей и расширяет её, следя за ошибками.
- **Выкладка — не релиз:** флаг функции позволяет доставить код выключенным и включать постепенно, а при поломке выключить без новой выкладки.
- **Во время выкладки работают две версии одновременно:** API меняют через expand–contract, а ассеты обеих версий должны быть доступны, иначе HTML от новой версии попросит чанк у старой.
- **Откат — переключение на прошлый неизменяемый артефакт,** а не пересборка. План отката готовят до выкладки.
::

---

## Почему выкладка рискованна

Сквозной пример — магазин выкатывает новое оформление заказа, а API одновременно переименовывает поле `price` в `amount`.

Самая простая выкладка — **замена разом**: остановить старую версию и запустить новую. Пока новая поднимается, пользователи видят ошибки, а если она сломана, откат — это ещё одна такая же выкладка. Стратегии ниже снижают оба риска.

---

## Стратегии

| Стратегия | Как | Простой | Откат |
| --- | --- | --- | --- |
| замена разом | остановить старое, запустить новое | да | новая выкладка |
| поочерёдная (rolling) | заменять экземпляры по одному | нет | постепенный |
| blue-green | поднять второе окружение, переключить трафик | нет | мгновенный |
| canary | новая версия для части пользователей, затем для всех | нет | быстрый, затронута доля |

### Поочерёдная

Экземпляры обновляют по одному: пока новые поднимаются и проходят проверку готовности, старые обслуживают трафик. Простоя нет, но какое-то время **работают обе версии**, и один пользователь может попасть на разные.

В проверке балансировщик по кругу раздавал запросы между экземплярами v1 и v2, и у каждого были свои ассеты. HTML пришёл от v2 и сослался на `index-v2.js`, а запрос скрипта ушёл на v1 — 404 и пустая страница. Когда ассеты обеих версий стали доступны с любого экземпляра — общее хранилище или CDN, — страница открылась как «магазин v2».

Правило для фронтенда: ассеты новой версии выкладывают **до** переключения HTML, а ассеты старой хранят **после** (подробно — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching)).

### Blue-green

Два одинаковых окружения: blue обслуживает трафик, green поднимают с новой версией и проверяют. Затем трафик переключают целиком, а blue остаётся запасным:

```text
blue (v1) ← трафик         green (v2) готовится и проверяется
              ── переключение ──►
blue (v1) запас            green (v2) ← трафик
```

Откат — переключение обратно. Цена — двойные ресурсы на время выкладки и общие зависимости: база данных у окружений одна, и её схема должна подходить обеим версиям.

### Canary

Новую версию получает малая доля пользователей — 1%, 5%, — команда смотрит на ошибки и метрики (подробно — в [Мониторинге](/content/testing-deploying/monitoring-and-observability)) и расширяет долю шагами:

```text
v2 → 1% → 5% → 25% → 50% → 100%
     на каждом шаге: ошибки, задержки, конверсия; хуже — откат
```

Группу выбирают **по пользователю**, а не по запросу. В проверке распределение по хешу идентификатора дало около 5% из 100 000 пользователей, каждый получал один и тот же ответ при каждом запросе, а при расширении до 25% все прежние участники остались в группе:

```js
const bucket = (userId) => createHash('sha256').update(`checkout-v2:${userId}`).digest().readUInt32BE(0) % 100;
const inCanary = (userId, percent) => bucket(userId) < percent;
```

Случайное число на каждый запрос в проверке перебросило между версиями больше 40% пользователей за два запроса: сегодня новое оформление, через минуту старое, и корзина, сохранённая в одном формате, читается другой версией.

## Флаги функций

**Флаг функции** — переключатель, который включает и выключает поведение без новой выкладки:

```js
const checkout = () => (flags.get('newCheckout') ? <NewCheckout /> : <OldCheckout />);
```

В проверке флаг, выключенный в панели, сразу вернул старое оформление, а неизвестный флаг — безопасное значение по умолчанию `false`.

### Выкладка и релиз

**Выкладка** доставляет код в продакшен, **релиз** делает его доступным пользователям. Флаги разносят их во времени:

- **тёмный запуск** — код выкладывают выключенным и проверяют в продакшене на сотрудниках;
- **постепенное включение** — для бета-группы, затем для процента пользователей — canary без отдельной инфраструктуры;
- **аварийный выключатель** — сломанную функцию выключают за секунды, не откатывая всю выкладку;
- **A/B-тесты** — две версии для разных групп и сравнение метрик;
- **разработка в основной ветке** — незаконченная функция сливается в `main` за выключенным флагом.

Инструменты: LaunchDarkly, Unleash, Flagsmith, PostHog, GrowthBook; стандарт API — OpenFeature. Цена флагов — ветвления в коде и долг: выключенные навсегда и включённые для всех флаги удаляют вместе со старой веткой.

## Две версии одновременно

При любой выкладке без простоя есть окно, когда работают обе версии. А во фронтенде оно длиннее: вкладка, открытая вчера, всё ещё выполняет старый бандл и ходит в новый API.

### Expand–contract

Ломающее изменение проводят в три шага:

1. **expand** — добавить новое рядом со старым: API отдаёт и `price`, и `amount`;
2. **migrate** — перевести клиентов на новое поле и дождаться, пока старые версии уйдут;
3. **contract** — удалить старое.

В проверке старый клиент работал с ответами v1 и expand, новый — с expand и contract, а удаление `price` сразу дало у старого клиента `undefined ₽`. Так же меняют схему базы данных при blue-green и canary. Ломающие изменения публичного API проводят через версии и объявление устаревания (подробно — в [REST](/content/network-api/rest)).

### Старые вкладки

Чтобы пользователь не сидел на старой версии неделями, приложение узнаёт о новой выкладке: опрашивает `/version.json` или получает событие, и при расхождении предлагает обновить страницу или обновляет её при следующем переходе. Ошибку загрузки удалённого чанка ловят и перезагружают страницу.

## Откат

- **Неизменяемые выкладки** — каждая выкладка хранится как отдельный артефакт, и откат — переключение указателя на прошлую, без пересборки. Так работают Vercel, Netlify и Cloudflare Pages, а с контейнерами — прошлый тег образа.
- **Флаг** — выключить сломанную функцию, не трогая остальное.
- **Автоматический откат** canary, если ошибки или задержки выше порога.
- **План заранее** — кто решает, как переключить, что делать с миграциями базы, которые не откатываются.

Откат кода не откатывает данные: если новая версия успела записать данные в новом формате, старая должна уметь их прочитать. Это ещё одна причина для expand–contract.

---

## Превью

На каждый PR платформа поднимает отдельную выкладку по своему адресу: ревьюер, дизайнер и тестировщик смотрят изменение вживую, e2e идут прямо на превью (подробно — в [CI/CD](/content/advanced-tooling/ci-cd)). Превью ходят в стенд или подменённый API, а не в продакшен-базу.

**Progressive delivery** — общее название подхода: canary, флаги и мониторинг вместе. Релиз — не одно событие, а постепенный процесс с наблюдением и откатом на каждом шаге.

---

## Красные флаги в ответе

- **«Остановим старое и запустим новое ночью».** Простой и долгий откат, а ночью кто-то всё равно покупает.
- **«В canary отправим случайные 5% запросов».** Пользователь будет прыгать между версиями, группу выбирают по пользователю.
- **«Переименуем поле в API и выкатим фронт и бэк вместе».** Старые вкладки и экземпляры увидят `undefined`.
- **«Откат — пересоберём прошлый коммит».** Это долго и даёт другой артефакт; откатываются переключением на прошлую выкладку.
- **«Флаги можно не удалять».** Они копятся и превращают код в лабиринт ветвлений.

## Как спрашивают на собеседовании

::question
Чем blue-green отличается от canary?

#answer
Blue-green поднимает второе окружение с новой версией и переключает на него весь трафик; откат — переключение обратно. Canary показывает новую версию малой доле пользователей и расширяет её шагами, следя за ошибками и метриками.

#more
Blue-green требует двойных ресурсов на время выкладки, но прост. Canary ограничивает число затронутых пользователей, но требует мониторинга и стабильного распределения по пользователю, а не по запросу.
::

::question
Как выкатить без простоя?

#answer
Держать старую версию в работе, пока новая готовится: поочерёдная замена экземпляров с проверкой готовности, blue-green или canary. Для статики — неизменяемые выкладки: новые файлы рядом со старыми и атомарное переключение `index.html`.

#more
Во всех вариантах какое-то время работают обе версии. Поэтому изменения API делают совместимыми, а ассеты обеих версий держат доступными — иначе HTML новой версии попросит чанк, которого нет на старом экземпляре.
::

::question
Что такое флаги функций и зачем они?

#answer
Переключатели поведения, которые меняются без новой выкладки. Они разделяют выкладку и релиз: код доставляют выключенным и включают постепенно — сотрудникам, бета-группе, проценту пользователей.

#more
Флаги дают аварийный выключатель, A/B-тесты и разработку в основной ветке. Цена — ветвления и долг: флаг удаляют вместе со старой веткой, когда он включён для всех.
::

::question
Почему во время выкладки важна обратная совместимость?

#answer
Старая и новая версии работают одновременно — при поочерёдной выкладке, canary, blue-green и во вкладках, открытых до выкладки. Если API сломал контракт, одна из версий сломается.

#more
Изменения проводят через expand–contract: добавить новое рядом со старым, перевести клиентов, затем удалить старое. Так же меняют схему базы: откат кода не откатывает данные.
::

::question
Как быстро откатиться?

#answer
Переключиться на прошлый неизменяемый артефакт — прошлую выкладку на платформе или прошлый тег образа, — без пересборки. Если сломана одна функция — выключить её флагом.

#more
План отката готовят заранее, включая миграции базы, которые нельзя отменить. Canary можно откатывать автоматически по порогу ошибок.
::

::question
Как выбрать пользователей для canary?

#answer
Детерминированно по пользователю: хеш идентификатора и соли функции даёт число от 0 до 99, и пользователь в группе, если число меньше процента. Он видит одну версию при каждом запросе, а при расширении доли прежние участники остаются в группе.

#more
Случайный выбор на каждый запрос перебрасывает пользователя между версиями. Соль на каждую функцию делает группы разных экспериментов независимыми.
::

## Практика

::practice{title="Пустая страница во время выкладки"}
Магазин работает на четырёх контейнерах за балансировщиком. Во время каждой поочерёдной выкладки несколько минут часть пользователей видит пустую страницу с 404 на `assets/index-….js`.

#solution
Каждый контейнер отдаёт только ассеты своей версии. HTML пришёл от обновлённого контейнера, а скрипт — со старого, где такого файла нет. В проверке балансировщик по кругу между v1 и v2 дал ровно это: 404 на `index-v2.js` и пустую страницу.

Решение — выносить ассеты в общее хранилище или CDN и загружать их **до** переключения HTML, не удаляя ассеты прошлых версий:

```bash
# 1. ассеты новой версии — в общее хранилище, старые не трогаем
aws s3 sync dist/assets s3://shop-assets/assets --cache-control "public, max-age=31536000, immutable"

# 2. только после этого — поочерёдная замена контейнеров с новым HTML
kubectl set image deployment/shop-web web=registry.shop.example/shop-web:v2
```

Привязка пользователя к экземпляру на время выкладки помогает хуже: она не спасает при перезапусках и открытых со вчера вкладках.

После того как ассеты обеих версий стали доступны с любого экземпляра, страница в проверке открылась без ошибок.
::

::practice{title="Новое оформление «мигает»"}
Новое оформление заказа включили для 10% трафика: балансировщик отправляет случайные 10% запросов на новую версию. Пользователи жалуются, что страница меняется при каждом обновлении, а корзина иногда пропадает.

#solution
Выбор по запросу, а не по пользователю: каждый запрос — новое случайное число. В проверке случайный выбор перебросил больше 40% пользователей между версиями всего за два запроса. Группу считают по пользователю:

```js
const bucket = (userId) => createHash('sha256').update(`checkout-v2:${userId}`).digest().readUInt32BE(0) % 100;
const variant = bucket(user.id) < 10 ? 'new' : 'old';
```

В проверке порог 5% дал около 5000 пользователей из 100 000, ответ не менялся между запросами, а при расширении до 25% все прежние участники остались в группе. Для анонимных пользователей идентификатор хранят в cookie. Корзина пропадала потому, что версии хранят её по-разному — формат данных тоже меняют через expand–contract.
::
