# Стратегии деплоя

Выкатка новой версии - рискованный момент: можно уронить прод для всех. Стратегии деплоя снижают риск: выкатывать **без даунтайма**, **постепенно** и с возможностью **мгновенного отката**. Их различия - стандартный senior-вопрос.

---

## Проблема

Наивный деплой - «остановить старое, запустить новое» (recreate) - даёт **даунтайм** (пользователи видят ошибку, пока новое поднимается) и **рискованный откат**. Стратегии ниже это решают.

---

## Основные стратегии

| Стратегия | Как | Даунтайм | Откат |
|-----------|-----|----------|-------|
| **Recreate** | стоп старое → старт новое | да | медленный |
| **Rolling** | заменять инстансы по одному | нет | постепенный |
| **Blue-green** | два окружения, переключить трафик | нет | мгновенный |
| **Canary** | выкатить части пользователей, потом всем | нет | быстрый |

### Rolling

Инстансы обновляются **по очереди**: пока новые поднимаются, старые ещё обслуживают трафик. Без даунтайма, но во время выката одновременно работают две версии (надо учитывать совместимость).

### Blue-green

Два **идентичных** окружения: «blue» (текущее) обслуживает трафик, «green» поднимают с новой версией. Когда green готово и проверено - трафик **переключают** на него одним движением. Сломалось - мгновенно переключаешь обратно.

```
blue (v1) ← трафик        green (v2) готовится
        ──── переключить ────►
blue (v1) запас            green (v2) ← трафик
```

### Canary

Новую версию показывают **малой доле** пользователей (5%), следят за метриками/ошибками ([мониторинг](/content/testing-deploying/monitoring-and-observability)), и при здоровых показателях **постепенно** наращивают до 100%. Проблема затронет немногих, и её видно рано.

```
v2 → 5% → 25% → 50% → 100%
     (мониторим ошибки на каждом шаге, при проблеме - откат)
```

## Feature flags

Отдельный и очень важный приём. **Фичефлаг** - переключатель, который включает/выключает функциональность **без передеплоя**.

```js
if (flags.newCheckout) {
  return <NewCheckout />;
}
return <OldCheckout />;
```

<b class="text-on-semi-light">Deploy ≠ release</b> - <span class="text-gray">Флаги **разделяют деплой и релиз**: код выкатывается в прод **выключенным** (dark launch), а включается отдельно - постепенно, для части пользователей, для бета-группы. Это даёт: безопасные релизы, A/B-тесты, **kill switch** (мгновенно выключить сломавшуюся фичу без отката деплоя), trunk-based разработку. Инструменты: LaunchDarkly, Unleash, PostHog, Flagsmith.</span>

> «Deploy» - доставить код в прод. «Release» - сделать его доступным пользователям. Флаги позволяют делать это в разное время.

---

## Обратная совместимость

Тонкость, которую упускают: при rolling/canary/blue-green **старая и новая версии работают одновременно**. Значит, изменения должны быть **обратно совместимы**, иначе пользователь на старой версии сломается, а на новой - не найдёт ещё не выкаченного API.

<b class="text-on-semi-light">Expand–contract (parallel change)</b> - <span class="text-gray">Безопасный паттерн миграций в три шага: **expand** - добавить новое, не ломая старое (поле/эндпоинт рядом со старым); **migrate** - перевести клиентов на новое; **contract** - удалить старое, когда им никто не пользуется. Так фронт и бэк деплоятся независимо без поломок. Нельзя удалять поле API/БД, пока есть клиенты, его читающие.</span>

> Фронтенд-следствие: новый фронт должен работать со старым бэком и наоборот в окне выката. Поэтому ломающие изменения API проводят через версионирование/депрекацию ([API и BFF](/content/architecture/api-and-bff)), а не «удалили и выкатили».

---

## Откат

Когда что-то сломалось, главное - **быстро вернуться** к рабочей версии.

- **Атомарные/immutable деплои** (Vercel, Netlify) хранят каждый деплой как неизменный артефакт - откат это переключение указателя на предыдущую версию, мгновенно.
- **Flag kill switch** - выключить фичу, не откатывая весь деплой.
- Заранее иметь план отката - часть зрелого процесса.

---

## Превью-деплои

На каждый PR платформа поднимает **отдельный деплой** с изменениями по уникальному URL. Ревьюеры и QA проверяют фичу вживую до мержа, без влияния на прод. Стандарт для фронтенда (Vercel/Netlify), тесно связан с [CI](/content/advanced-tooling/ci-cd).

---

## Progressive delivery

Зонтичный термин для современного подхода: **canary + feature flags + мониторинг** вместе. Релиз - не «бинарное событие», а **постепенный** процесс с наблюдением и возможностью отката на каждом шаге.

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем blue-green отличается от canary?</b>
<span class="text-gray">Blue-green - два окружения, трафик переключается на новое целиком (мгновенный откат). Canary - новую версию показывают малой доле пользователей и постепенно расширяют, наблюдая за метриками.</span>

<b class="text-on-semi-light">Как выкатить без даунтайма?</b>
<span class="text-gray">Rolling (замена инстансов по одному), blue-green (переключение трафика на готовое окружение) или canary - во всех старая версия обслуживает трафик, пока новая готовится.</span>

<b class="text-on-semi-light">Что такое feature flags и зачем они?</b>
<span class="text-gray">Переключатели функциональности без передеплоя. Разделяют деплой и релиз: код выкатывается выключенным, включается постепенно. Дают A/B-тесты, kill switch и безопасные релизы.</span>

<b class="text-on-semi-light">В чём разница deploy и release?</b>
<span class="text-gray">Deploy - доставить код в прод. Release - сделать его доступным пользователям. Фичефлаги позволяют разнести их во времени: задеплоить, но включить позже.</span>

<b class="text-on-semi-light">Как быстро откатиться при поломке?</b>
<span class="text-gray">Атомарные immutable-деплои - переключить указатель на предыдущую версию (мгновенно); или выключить фичу флагом без отката всего деплоя. Главное - заранее иметь план отката.</span>

<b class="text-on-semi-light">Почему при деплое важна обратная совместимость?</b>
<span class="text-gray">При rolling/canary/blue-green старая и новая версии работают одновременно. Изменения должны быть совместимы (expand-contract: сначала добавить новое, перевести клиентов, потом удалить старое), иначе пользователи на одной из версий сломаются.</span>
