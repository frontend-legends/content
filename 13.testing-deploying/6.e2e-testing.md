# E2E-тестирование

**End-to-end** тесты прогоняют реальный браузер через **полный пользовательский сценарий**: открыть страницу, залогиниться, заполнить форму, оформить заказ. Это самая реалистичная и самая дорогая проверка. Главные темы - выбор инструмента и борьба с **flaky**-тестами.

---

## Что такое e2e

В отличие от unit/integration (которые гоняются в jsdom), e2e работают в **настоящем браузере** и проверяют систему целиком - фронтенд, сеть, иногда бэкенд - как её видит пользователь.

```
открыть /login → ввести email/пароль → нажать «Войти»
→ дождаться редиректа на /dashboard → проверить приветствие
```

Максимум уверенности, но медленно и хрупко - поэтому таких тестов **немного** (вершина [пирамиды](/content/testing-deploying/testing-strategy-and-pyramid)).

---

## Playwright vs Cypress

Два главных инструмента.

| | Playwright | Cypress |
|--|------------|---------|
| Вендор | Microsoft | Cypress.io |
| Браузеры | Chromium, Firefox, **WebKit** | Chromium-семейство (+ Firefox) |
| Архитектура | управляет браузером извне | выполняется внутри браузера |
| Авто-ожидание | да, встроенное | да |
| Параллелизм | из коробки | в платном/настройке |
| Отладка | trace viewer | time-travel в UI |
| Тренд | растущий стандарт | зрелый, отличный DX |

```js
// Playwright
test('логин', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('a@b.com');
  await page.getByRole('button', { name: 'Войти' }).click();
  await expect(page.getByText('Привет')).toBeVisible(); // авто-ожидание
});
```

<b class="text-on-semi-light">Что выбрать</b> - <span class="text-gray">**Playwright** - кросс-браузерность (включая WebKit/Safari), скорость, параллелизм, несколько вкладок/контекстов; де-факто новый стандарт. **Cypress** - выдающийся DX и наглядная отладка (time-travel), но исторически слабее с мульти-браузерностью. Оба хороши; новые проекты чаще берут Playwright.</span>

## Селекторы

Как и в Testing Library, ищи элементы **устойчиво**: по роли, тексту, label или `data-testid` - не по CSS-классам и XPath, которые ломаются при любом изменении вёрстки.

```js
page.getByRole('button', { name: 'Купить' }); // ✅ устойчиво
page.locator('.btn-primary.css-1x2y3');        // ❌ хрупко
```

## Flaky-тесты

**Flaky** - тест, который то падает, то проходит без изменений кода. Бич e2e и постоянная тема собеседований.

| Причина | Решение |
|---------|---------|
| Гонки времени (проверка до загрузки) | **авто-ожидание** вместо `sleep` |
| Нестабильная сеть/данные | мок сети (MSW), стабильные тест-данные |
| Анимации | отключать анимации в тест-режиме |
| Общее состояние между тестами | изоляция, чистое состояние на каждый тест |
| Зависимость от порядка | независимые тесты |

<b class="text-on-semi-light">Главное правило</b> - <span class="text-gray">Никогда не используй фиксированные `sleep(1000)` - это и медленно, и ненадёжно. Современные инструменты **авто-ждут** появления элемента/условия. Флака-тесты опаснее отсутствия тестов: им перестают доверять и игнорируют красный CI. Их нужно либо чинить, либо удалять.</span>

> Помогает и **retry** упавших тестов в CI - но это лечение симптома; первопричину (гонку, общее состояние) надо устранять.

## Поддерживаемость e2e

E2E легко превращаются в хрупкий, нечитаемый набор. Senior-практики против этого:

- **Page Object Model (POM)** - инкапсулировать локаторы и действия страницы в модуль; тесты вызывают `loginPage.submit(user)`, а не дублируют селекторы. Изменилась вёрстка - правишь POM, а не сотню тестов.
- **Перехват сети** - вместо реального бэкенда мокать ответы на уровне сети (`page.route` в Playwright): быстрее, детерминированнее, можно проверять краевые случаи (500, пустой ответ) без подготовки данных.
- **Изоляция данных** - сидировать/изолировать тестовые данные, чтобы тесты не зависели от состояния общей БД.

```js
// Playwright: замокать ответ API на уровне сети
await page.route('/api/user', r => r.fulfill({ json: { name: 'Test' } }));
```

<b class="text-on-semi-light">Реальный бэкенд или мок</b> - <span class="text-gray">Полностью реальный стек - максимум доверия, но медленно и нестабильно. Мок сети - быстро и детерминированно, но не проверяет реальную интеграцию. Часто комбинируют: несколько «сквозных» тестов с реальным бэкендом + остальные с моканной сетью.</span>

## Что покрывать e2e

E2E дорогие, поэтому - только **критические пути**:

- логин/регистрация;
- оформление заказа/оплата;
- ключевой happy-path продукта.

Остальное (детали, краевые случаи) дешевле и стабильнее покрыть [интеграционными тестами](/content/testing-deploying/unit-and-integration-testing).

---

## Подготовка и скорость

- **Переиспользование авторизации** - залогиниться один раз, сохранить состояние (cookies/storage) и подставлять в тесты, не проходя логин каждый раз.
- **Фикстуры** - заранее подготовленные данные/состояние.
- **Параллелизм и шардинг** - гонять тесты параллельно и делить между машинами в CI.
- **Headless** в CI - без UI, быстрее.

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем e2e отличается от интеграционных тестов?</b>
<span class="text-gray">E2E гоняют реальный браузер через полный сценарий (макс. реалистичность), интеграционные - в jsdom, быстрее и стабильнее. E2E дорогие, поэтому их мало - только критические пути.</span>

<b class="text-on-semi-light">Playwright или Cypress?</b>
<span class="text-gray">Playwright - кросс-браузерность (включая WebKit), скорость, параллелизм; новый стандарт. Cypress - отличный DX и time-travel-отладка, но слабее с мульти-браузерностью. Оба валидны.</span>

<b class="text-on-semi-light">Что такое flaky-тест и как с ним бороться?</b>
<span class="text-gray">Тест, который непредсказуемо падает без изменения кода. Причины: гонки времени, нестабильная сеть, анимации, общее состояние. Лечится авто-ожиданием (не sleep), моком сети, изоляцией, отключением анимаций.</span>

<b class="text-on-semi-light">Почему нельзя использовать sleep в e2e?</b>
<span class="text-gray">Фиксированный sleep либо слишком короткий (флака), либо слишком длинный (медленно). Нужно авто-ожидание конкретного элемента/условия, которое умеют современные инструменты.</span>

<b class="text-on-semi-light">Какие сценарии стоит покрывать e2e?</b>
<span class="text-gray">Только критические пользовательские пути: логин, оплата, ключевой happy-path. Детали и краевые случаи дешевле покрыть интеграционными тестами.</span>

<b class="text-on-semi-light">Как держать e2e-тесты поддерживаемыми?</b>
<span class="text-gray">Page Object Model (локаторы и действия в одном месте), устойчивые селекторы (роль/текст/testid), перехват сети для детерминизма, изоляция тестовых данных. Меняется вёрстка - правишь POM, а не все тесты.</span>
