# E2E-тестирование

Как проверить сценарий целиком в настоящем браузере: Playwright и Cypress, локаторы, автоожидание и проверки с повторами, подмена сети, нестабильные тесты, изоляция и подготовка данных. Спрашивают, чем e2e отличается от интеграционных тестов, что выбрать — Playwright или Cypress — и как бороться с нестабильными тестами. Глубже — почему проверка без повтора видит пустой текст, что e2e ловит, а jsdom нет, и почему повтор упавшего теста не равен успеху.

::tldr
- **E2E-тест проходит сценарий пользователя в настоящем браузере** на собранном приложении: открыть страницу, войти, добавить в корзину, оформить. Самый реалистичный и самый дорогой слой — поэтому только критичные пути.
- **Playwright** управляет Chromium, Firefox и WebKit извне, параллелит тесты и даёт trace viewer. **Cypress** работает внутри браузера, с наглядной отладкой по шагам. Новые проекты чаще берут Playwright.
- **Ожидание встроено:** действия ждут, пока элемент видим, включён и не перекрыт, а проверки вида `await expect(locator).toHaveText()` повторяются до таймаута. Фиксированный `sleep` — причина и медленных, и нестабильных тестов.
- **Нестабильный тест** то падает, то проходит без изменений кода. Причины — гонки, общие данные, сеть, анимации. Повтор в CI прячет симптом, но отчёт помечает такой тест как flaky — его чинят.
- **Скорость и стабильность:** свой браузерный контекст на каждый тест, вход один раз через сохранённое состояние, подмена нестабильных API через `page.route`.
::

---

## Что такое e2e

Сквозной пример — магазин: страница товара с остатками на складе, кнопка «В корзину», вход в личный кабинет, баннер cookie.

Модульные и интеграционные тесты идут в Node.js с эмуляцией DOM. E2E-тест запускает настоящий браузер и работает с собранным приложением так, как пользователь:

```text
открыть товар → дождаться кнопки → «В корзину» → увидеть «В корзине: 1»
```

Это ловит то, чего не видит jsdom: раскладку, перекрытие элементов, реальную загрузку скриптов, переходы между страницами, cookie и хранилище. Цена — секунды на тест, браузер в CI и больше причин для нестабильности. Поэтому e2e немного — только сценарии, поломка которых стоит денег (подробно — в [Стратегии тестирования](/content/testing-deploying/testing-strategy-and-pyramid)).

## Playwright и Cypress

| | Playwright | Cypress |
| --- | --- | --- |
| Разработчик | Microsoft | Cypress.io |
| Браузеры | Chromium, Firefox, WebKit | Chromium-семейство, Firefox, WebKit экспериментально |
| Архитектура | управляет браузером извне по протоколу | код теста выполняется внутри страницы |
| Несколько вкладок и доменов | да | ограниченно |
| Параллельность | встроенная, шардинг | через Cypress Cloud или настройку |
| Отладка | trace viewer: шаги, DOM, сеть | пошаговый «откат во времени» в UI |

```js
import { test, expect } from '@playwright/test';

test('добавление в корзину', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'В корзину' }).click();
  await expect(page.getByRole('heading')).toHaveText('В корзине: 1');
});
```

Playwright выбирают за WebKit — движок Safari, — несколько контекстов в одном тесте и встроенную параллельность. Cypress — за удобство отладки, если хватает Chromium. Оба поддерживают компонентные тесты (подробно — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing)).

## Локаторы

Как и в Testing Library, элементы ищут по тому, что видит пользователь: `getByRole`, `getByLabel`, `getByText`, в крайнем случае `getByTestId`. CSS-классы и XPath ломаются при каждом изменении вёрстки.

Локаторы Playwright **строгие**: если под описание подходят несколько элементов, действие падает. В проверке на странице было две кнопки «Купить»:

```text
strict mode violation: getByRole('button', { name: 'Купить' }) resolved to 2 elements
```

Это защищает от клика не туда. Уточняют область — `page.getByRole('article', { name: 'Пуэр' }).getByRole('button', { name: 'Купить' })` — или выбирают явно через `.first()`, если порядок действительно важен.

## Ожидание

Страницы асинхронны: кнопка появляется после загрузки скрипта, текст — после ответа API. В проверке кнопка «В корзину» появлялась через 400 мс, а остатки на складе — через 300 мс после запроса.

### Действия ждут сами

`click()` перед нажатием ждёт, пока элемент появится, станет видимым, включённым, стабильным и будет получать события. Тест с кнопкой, появляющейся через 400 мс, прошёл без единой строки ожидания.

Та же проверка ловит настоящую ошибку интерфейса. Кнопку «Оформить» перекрыл баннер cookie с `position: fixed`. Playwright не стал кликать сквозь него и упал:

```text
<div style="position:fixed;inset:0;…">Мы используем cookie</div> intercepts pointer events
```

В jsdom такой клик прошёл бы: раскладки там нет, и перекрытие не существует.

### Проверки с повторами

```js
// без повтора: прочитать один раз и сравнить
expect(await page.locator('#stock').textContent()).toBe('На складе: 3');

// с повтором: повторять, пока не совпадёт или не истечёт таймаут
await expect(page.locator('#stock')).toHaveText('На складе: 3');
```

В проверке первая упала с `Received: ""` — текст ещё не пришёл, — вторая прошла. Правило: проверять состояние страницы только через `await expect(locator)…` — `toHaveText`, `toBeVisible`, `toHaveURL`, — а не читать значение и сравнивать.

Фиксированный `page.waitForTimeout(1000)` вместо этого плох дважды: на быстрой машине тест ждёт зря, на медленной CI — ждёт недостаточно.

## Нестабильные тесты

**Flaky** — тест, который то падает, то проходит без изменений кода. Он опаснее отсутствия теста: команда привыкает перезапускать CI и перестаёт верить красному.

| Причина | Решение |
| --- | --- |
| проверка раньше, чем страница готова | ожидание через локаторы и `expect`, а не `sleep` |
| нестабильный бэкенд или данные стенда | подмена API, свои данные на каждый тест |
| общее состояние между тестами | отдельный контекст и данные на тест |
| анимации и переходы | `reducedMotion: 'reduce'`, отключение анимаций в тестовом режиме |
| время и часовой пояс | `timezoneId`, `clock` для подмены времени |

### Повтор — не лечение

`retries: 2` в CI перезапускает упавший тест. В проверке тест упал с первой попытки и прошёл со второй — и отчёт пометил его не как успешный, а как `flaky`: `stats.flaky: 1`. Повтор не даёт нестабильности сломать сборку, но такие тесты собирают в список и чинят: причина гонки никуда не делась и однажды проявится у пользователя.

## Изоляция и подготовка

### Свой контекст на каждый тест

Playwright создаёт для каждого теста новый браузерный контекст — как свежий профиль: свои cookie, `localStorage`, кеш. В проверке первый тест записал корзину в `localStorage`, а второй увидел `null`. Контекст создаётся за миллисекунды, в отличие от запуска браузера.

### Вход один раз

Проходить форму входа в каждом тесте долго. Входят один раз, сохраняют состояние и подставляют его в остальные тесты:

```js
await page.getByRole('button', { name: 'Войти' }).click();
await context.storageState({ path: 'auth.json' });

// в других тестах или в конфиге
const context = await browser.newContext({ storageState: 'auth.json' });
```

В проверке контекст с `auth.json` открыл кабинет сразу как «Вы вошли», а новый контекст без него — как «Гость». Обычно это делает отдельный проект-настройка в конфиге, от которого зависят остальные.

### Подмена сети

```js
await page.route('**/api/stock', (route) => route.fulfill({ status: 500, body: '' }));
await page.goto('/');
await expect(page.locator('#stock')).toHaveText('Остаток неизвестен');
```

В проверке ответ 500 подставился без настоящего сервера, и страница показала запасной текст. Так проверяют ошибки, пустые ответы и медленную сеть, которые на стенде не воспроизвести. Обработчики MSW тоже работают в браузере (подробно — в [Моках и дублёрах](/content/testing-deploying/mocking-and-test-doubles)).

Полностью настоящий стек даёт больше уверенности в интеграции, но медленнее и нестабильнее. Обычно комбинируют: несколько сценариев против настоящего бэкенда на стенде и остальные — с подменённой сетью.

### Page Object

Локаторы и действия страницы собирают в один модуль — тесты вызывают `cartPage.checkout()`, а не повторяют селекторы. Изменилась вёрстка — правят одно место. Playwright для этого предлагает и фикстуры: объект страницы приходит в тест параметром.

### Скорость

- параллельные воркеры и шардинг между машинами в CI: `--shard=1/4`;
- браузер без интерфейса;
- данные готовят через API, а не через интерфейс: создать заказ запросом быстрее, чем кликами;
- e2e на превью каждого PR, а не только после слияния (подробно — в [CI/CD](/content/advanced-tooling/ci-cd)).

## Красные флаги в ответе

- **«Подожду секунду и проверю».** Фиксированное ожидание медленное и всё равно нестабильное, нужны проверки с повтором.
- **«Прочитаю текст и сравню через `toBe`».** Проверка выполняется один раз, до того как страница готова.
- **«Повтор в CI решает проблему».** Он прячет симптом, а причина гонки остаётся.
- **«Покроем e2e все случаи».** Медленно и хрупко; краевые случаи дешевле в интеграционных тестах.
- **«Найду элемент по классу».** Ломается при каждом изменении вёрстки.
- **«Тесты делят одного пользователя и корзину».** Порядок начинает влиять на результат.

## Как спрашивают на собеседовании

::question
Чем e2e отличается от интеграционных тестов?

#answer
E2E проходит сценарий в настоящем браузере на собранном приложении: раскладка, загрузка скриптов, переходы, cookie. Интеграционные тесты идут в Node.js с эмуляцией DOM — быстрее и стабильнее, но без раскладки и настоящего браузера.

#more
E2E ловит то, чего не видит jsdom, например кнопку, перекрытую баннером. Поэтому e2e оставляют для критичных сценариев, а краевые случаи проверяют уровнем ниже.
::

::question
Playwright или Cypress?

#answer
Playwright управляет Chromium, Firefox и WebKit извне, поддерживает несколько вкладок и доменов, параллелит тесты и даёт trace viewer. Cypress выполняет тест внутри страницы и удобен пошаговой отладкой. Оба рабочие, новые проекты чаще берут Playwright.

#more
WebKit важен, если много пользователей на Safari и iOS. Cypress ограничен в сценариях с несколькими вкладками и доменами из-за своей архитектуры.
::

::question
Что такое нестабильный тест и как с ним бороться?

#answer
Тест, который падает и проходит без изменений кода. Основные причины — проверка раньше, чем страница готова, общие данные и состояние, нестабильная сеть, анимации, время. Лечится ожиданием через локаторы и проверки с повтором, изоляцией, подменой сети, отключением анимаций.

#more
Повтор в CI не лечит, а прячет: Playwright помечает тест, прошедший со второй попытки, как flaky. Такие тесты собирают и чинят, иначе команда перестаёт доверять красному прогону.
::

::question
Почему нельзя использовать `sleep` в e2e?

#answer
Фиксированное ожидание либо слишком длинное — тест медленный, — либо слишком короткое на медленной машине — тест нестабильный. Нужно ждать конкретного состояния: элемента, текста, адреса.

#more
В Playwright действия ждут сами — видимость, доступность, отсутствие перекрытия, — а проверки `await expect(locator).toHaveText()` повторяются до таймаута. Чтение значения и сравнение через `toBe` выполняется один раз и не ждёт.
::

::question
Какие сценарии покрывать e2e?

#answer
Только критичные пути: вход и регистрация, поиск и добавление в корзину, оформление и оплата, ключевой сценарий продукта.

#more
Детали и краевые случаи — ошибки валидации, пустые состояния, ответы 500 — дешевле и стабильнее в интеграционных тестах. В e2e их проверяют точечно через подмену сети.
::

::question
Как держать e2e быстрыми и поддерживаемыми?

#answer
Отдельный контекст на тест, вход один раз через сохранённое состояние, подготовка данных через API, параллельность и шардинг. Для поддержки — устойчивые локаторы и Page Object или фикстуры с действиями страницы.

#more
Нестабильные внешние API подменяют через `page.route`, оставляя несколько сценариев против настоящего бэкенда. E2E запускают на превью каждого PR, чтобы ловить ошибки до слияния.
::

## Практика

::practice{title="Тест проходит локально и падает в CI"}
Тест страницы товара:

```js
await page.goto('/');
await page.waitForTimeout(200);
expect(await page.locator('#stock').textContent()).toBe('На складе: 3');
```

Локально проходит, в CI падает примерно в трети запусков с `Received: ""`.

#solution
Две проблемы: фиксированное ожидание и проверка без повтора. На быстрой машине ответ API успевает за 200 мс, в CI — нет. Проверка через локатор повторяется, пока текст не появится:

```js
await page.goto('/');
await expect(page.locator('#stock')).toHaveText('На складе: 3');
```

В проверке при ответе API через 300 мс вариант с `textContent()` и `toBe` упал с `Received: ""`, а `toHaveText` прошёл. Если API нестабилен на стенде, его подменяют через `page.route`, и тест перестаёт зависеть от стенда.
::

::practice{title="Покупатели не могут оформить заказ"}
После добавления баннера cookie часть покупателей жалуется, что кнопка «Оформить» не нажимается. Интеграционные тесты на jsdom зелёные.

#solution
Баннер с `position: fixed` на весь экран перекрывает кнопку. В jsdom нет раскладки, поэтому клик там проходит сквозь любой слой. E2E это видит:

```js
test('оформление доступно при баннере', async ({ page }) => {
  await page.goto('/checkout');
  await page.getByRole('button', { name: 'Оформить' }).click();
});
```

В проверке Playwright отказался кликать и упал с `… intercepts pointer events`. Исправление — баннер не должен перекрывать содержимое: внизу экрана без полноэкранной подложки или с кнопкой закрытия, которую тест нажимает первой.
::
