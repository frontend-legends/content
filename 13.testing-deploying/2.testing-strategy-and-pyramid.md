# Стратегия тестирования

Какие тесты писать и в какой пропорции: статические проверки, модульные, интеграционные и e2e-тесты, пирамида против трофея, что тестировать, а что нет, и как устроен сам тест. Спрашивают, какие бывают виды тестов, чем трофей отличается от пирамиды и что не нужно тестировать. Глубже — почему модульные тесты бывают зелёными при сломанном приложении, почему тест на внутренности хуже отсутствия теста и что делать с найденным багом.

::tldr
- **Четыре слоя:** статические проверки (типы и линтер) без запуска, модульные тесты — одна функция или модуль, интеграционные — несколько частей вместе, e2e — целый сценарий в браузере. Снизу вверх растут реалистичность, время и цена.
- **Пирамида** — много модульных, меньше интеграционных, мало e2e. **Трофей** для фронтенда смещает основу на интеграционные: пользователь работает с собранным интерфейсом, а не с функциями по отдельности.
- **Модульные тесты с моками проверяют допущения:** если две части ошибаются по-разному, каждая зелёная, а связка сломана. Это ловит интеграционный тест.
- **Тестируют поведение, а не реализацию:** что видит и делает пользователь, критичные сценарии, краевые случаи и найденные баги. Тест на внутренние поля падает при рефакторинге без изменения поведения.
- **Структура теста — подготовка, действие, проверка,** а имя описывает поведение: «пустая корзина показывает заглушку».
::

---

## Виды тестов

Сквозной пример — карточка товара в магазине: модуль API получает товар, `formatPrice` форматирует цену, `productCard` собирает строку для интерфейса.

| Слой | Что проверяет | Скорость | Насколько близко к реальности |
| --- | --- | --- | --- |
| статический | типы, очевидные ошибки, стиль | мгновенно, без запуска | низко |
| модульный | одна функция или модуль | миллисекунды | низко |
| интеграционный | несколько модулей или компонент с событиями и данными | десятки миллисекунд | средне |
| e2e | сценарий целиком в настоящем браузере | секунды | высоко |

- **Статический слой** — [TypeScript](/content/typescript) и [линтеры](/content/advanced-tooling/linting-and-formatting): ловят ошибки, не запуская код.
- **Модульный** — чистая логика: расчёт корзины, форматирование, утилиты.
- **Интеграционный** — части вместе: компонент рендерится, пользователь кликает, запрос уходит в подменённую сеть, на экране результат.
- **E2E** — браузер проходит сценарий от главной до оформления заказа на собранном приложении (подробно — в [E2E](/content/testing-deploying/e2e-testing)).

Где проходит граница между модульным и интеграционным тестом и что считать «единицей», — в [Модульных и интеграционных тестах](/content/testing-deploying/unit-and-integration-testing).

## Пирамида и трофей

### Пирамида

Классическая модель Майка Кона: внизу много быстрых и дешёвых модульных тестов, наверху мало медленных и дорогих e2e.

```text
         /\         e2e — мало
        /  \
       /----\       интеграционные — средне
      /      \
     /--------\     модульные — много
```

Логика простая: чем выше слой, тем дороже тест, поэтому их меньше.

### Трофей

Модель Кента Доддса для фронтенда меняет пропорции:

```text
         ____
        /e2e \          немного
       /------\
      / интегр.\        больше всего
     /----------\
     \ модульные/       сколько нужно
      \________/
      статический       фундамент
```

Причина видна в проверке. API отдаёт цену в копейках — `120000`, — а `formatPrice` ждёт рубли. Модульные тесты:

```js
test('formatPrice форматирует рубли', () => {
  expect(formatPrice(1200)).toBe('1 200 ₽');
});

vi.mock('./api.js', () => ({ fetchProduct: async (id) => ({ id, title: 'Пуэр', price: 1200 }) }));
test('productCard собирает строку', async () => {
  expect(await productCard(7)).toBe('Пуэр — 1 200 ₽');
});
```

Оба прошли: мок API вернул ту цену, которую ожидал автор теста. Интеграционный тест с настоящим модулем API упал — на экране оказалось `120 000 ₽`. Каждая часть верна относительно своих допущений, а несостыковка между ними видна только при проверке вместе.

Поэтому для интерфейса основа — интеграционные тесты: они близки к тому, как работает приложение, но быстрее и стабильнее e2e. Для сложной чистой логики — расчётов, парсеров, алгоритмов — пирамида с упором на модульные тесты остаётся уместной. Это не правильная и неправильная модели, а разный фокус.

## Что тестировать

- **Поведение, видимое пользователю:** что отрисовалось и что происходит после действия.
- **Критичные сценарии:** вход, оплата, отправка формы — то, поломка чего стоит денег.
- **Краевые случаи:** пустой список, ошибка сети, ноль, очень длинная строка, граничные значения.
- **Найденные баги:** сначала тест, который воспроизводит баг, потом исправление (подробно — во [Введении](/content/testing-deploying/introduction)).

## Что не тестировать

| Не тестировать | Почему |
| --- | --- |
| детали реализации: внутренние поля, приватные методы, имена функций | ломается при рефакторинге без изменения поведения |
| сторонние библиотеки и сам фреймворк | их тестируют авторы, а вашу интеграцию с ними — ваши тесты |
| тривиальный код: константы, геттеры | нечему ломаться |
| то, что уже гарантируют типы | дублирует статическую проверку |

### Почему тест на реализацию вреден

В проверке у корзины было два теста:

```js
test('реализация: повторный товар не добавляет элемент в _items', () => {
  cart.add('tea'); cart.add('tea');
  expect(cart._items).toHaveLength(1);
});

test('поведение: два раза один товар — два в корзине', () => {
  cart.add('tea'); cart.add('tea'); cart.add('cup', 3);
  expect(cart.count()).toBe(5);
});
```

Корзину переписали с массива на `Map` — для пользователя ничего не изменилось. Тест на поведение остался зелёным, тест на реализацию упал. Такой тест не защищает от ошибок, а мешает улучшать код, и каждое его ложное падение приучает команду не доверять красным прогонам.

## Структура теста

Тест читается как три шага — **подготовка, действие, проверка** (Arrange — Act — Assert, или Given — When — Then):

```js
test('скидка 10% применяется один раз', () => {
  const items = [{ price: 1000, qty: 2 }];   // подготовка
  const result = total(items, 0.1);          // действие
  expect(result).toBe(1800);                 // проверка
});
```

- одно поведение на тест — тогда по имени упавшего теста понятно, что сломалось;
- имя описывает поведение: «пустая корзина показывает заглушку», а не «тест Cart 3»;
- данные в тесте — минимальные и явные, без общей настройки, которую нужно искать в другом файле.

### Smoke- и регрессионные тесты

- **Smoke-тесты** — быстрый набор, проверяющий, что приложение вообще работает: главная открывается, вход проходит. Их гоняют сразу после выкладки.
- **Регрессионный набор** — все тесты, которые следят, что старое поведение не сломалось. Каждый тест на найденный баг пополняет его.

## Красные флаги в ответе

- **«Пирамида правильная, трофей — мода».** Это разные пропорции для разных задач: трофей — для интерфейса, пирамида — для сложной чистой логики.
- **«Всё покрыто модульными тестами — значит, работает».** Модульные тесты с моками проверяют допущения, а не связку.
- **«Проверю, что в state лежит правильный массив».** Это реализация, тест сломается при рефакторинге.
- **«Протестирую, что React рендерит компонент».** Фреймворк тестируют его авторы.
- **«Один тест на всё поведение компонента».** При падении непонятно, что сломалось.

## Как спрашивают на собеседовании

::question
Какие бывают виды тестов?

#answer
Статические проверки — типы и линтер — без запуска кода, модульные — одна функция или модуль, интеграционные — несколько частей вместе, e2e — целый сценарий в браузере. Снизу вверх растут реалистичность, время и цена.

#more
Граница между модульными и интеграционными размыта и зависит от того, что считать единицей. Отдельно стоят визуальные, нагрузочные и проверки доступности — они отвечают на другие вопросы, чем «работает ли логика».
::

::question
Чем тестовый трофей отличается от пирамиды?

#answer
Пирамида — много модульных тестов, меньше интеграционных, мало e2e. Трофей делает основой интеграционные тесты и добавляет снизу статический слой: для интерфейса они дают больше уверенности на единицу усилий.

#more
Модульные тесты с моками проверяют допущения автора: две части могут ошибаться по-разному, и обе будут зелёными. Интеграционный тест ловит такую несостыковку. Для сложных расчётов и парсеров пирамида по-прежнему уместна.
::

::question
Почему для фронтенда упор на интеграционные тесты?

#answer
Пользователь работает с собранным интерфейсом: компонент, события, данные и сеть вместе. Интеграционный тест проверяет это близко к реальности, но быстрее и стабильнее e2e.

#more
Чтобы тест был интеграционным и быстрым, подменяют только границу с внешним миром — сеть через MSW, — а свои модули оставляют настоящими. Подробно — в истории про моки.
::

::question
Что не нужно тестировать?

#answer
Детали реализации — внутренние поля, приватные методы, — сторонние библиотеки и сам фреймворк, тривиальный код и то, что уже гарантируют типы.

#more
Тест на реализацию падает при рефакторинге, когда поведение не изменилось: он мешает улучшать код и приучает игнорировать красные прогоны. Хороший тест переживает рефакторинг и падает только при поломке поведения.
::

::question
Что делать, когда нашли баг?

#answer
Написать тест, который его воспроизводит, убедиться, что он падает, затем исправить код и увидеть тест зелёным. Тест остаётся в регрессионном наборе.

#more
Если баг воспроизводится только сценарием целиком, тест может быть e2e, но обычно его удаётся поймать на уровень ниже — это быстрее и стабильнее.
::

::question
Как устроен хороший тест?

#answer
Три шага — подготовка, действие, проверка, — одно поведение на тест и имя, которое это поведение описывает. Данные минимальные и видны в самом тесте.

#more
По имени упавшего теста должно быть понятно, что сломалось, без чтения кода. Тест не зависит от других тестов и от порядка запуска.
::

## Практика

::practice{title="Зелёные тесты, сломанная карточка"}
У карточки товара 100% модульных тестов, все зелёные. После релиза на сайте цены в сто раз больше: «120 000 ₽» вместо «1 200 ₽».

#solution
Каждый модуль протестирован против мока соседей, а моки отражали допущения авторов: API в тесте возвращал рубли, а настоящий — копейки. Модульные тесты не видят несостыковку контрактов. Нужен интеграционный тест с настоящими модулями, где подменена только сеть:

```js
test('карточка с настоящим модулем API', async () => {
  expect(await productCard(7)).toBe('Пуэр — 1 200 ₽');
});
```

В проверке оба модульных теста прошли, а этот упал с `120 000 ₽` в выводе. Исправление — договориться о единицах на границе: перевести копейки в рубли в модуле API или назвать поле `priceKopecks`.
::

::practice{title="Тесты ломаются после рефакторинга"}
Корзину переписали с массива на `Map`, поведение не изменилось, но упала половина тестов. Команда тратит день на их исправление.

#solution
Тесты проверяли внутреннее устройство — `cart._items` — вместо поведения. Их переписывают через публичный интерфейс:

```js
// было
expect(cart._items).toHaveLength(1);

// стало
cart.add('tea'); cart.add('tea'); cart.add('cup', 3);
expect(cart.count()).toBe(5);
```

В проверке после перехода на `Map` тест на `_items` упал, а тест на `count()` остался зелёным. Для компонентов то же правило: искать по тому, что видит пользователь — тексту и ролям, — а не по внутреннему состоянию.
::
