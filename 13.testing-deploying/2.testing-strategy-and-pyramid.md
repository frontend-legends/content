# Стратегия тестирования

Прежде чем писать тесты, нужно понять **какие** тесты писать и **в какой пропорции**. Виды тестов, пирамида против «трофея» и принцип «что тестировать, а что нет» - один из любимых вопросов на собеседованиях.

---

## Виды тестов

| Тип | Что проверяет | Скорость | Реалистичность |
|-----|---------------|----------|----------------|
| **Static** | типы, очевидные баги | мгновенно | низкая |
| **Unit** | одну функцию/модуль изолированно | очень быстро | низкая |
| **Integration** | несколько частей вместе | быстро | средняя |
| **E2E** | весь сценарий в браузере | медленно | высокая |

- **Static** - не «тесты» в классическом смысле, а [TypeScript](/content/typescript) и [ESLint](/content/advanced-tooling/linting-and-formatting): ловят ошибки без запуска.
- **Unit** - чистая логика, утилиты, хуки в изоляции.
- **Integration** - компонент + его взаимодействия (клик → запрос → отрисовка), несколько модулей вместе.
- **E2E** - реальный браузер проходит пользовательский сценарий целиком.

---

## Пирамида тестирования

Классическая модель (Майк Кон): **много дешёвых unit-тестов внизу, мало дорогих e2e наверху**.

```
        /\        E2E      - мало (медленно, дорого, хрупко)
       /  \
      /----\      Integration - средне
     /      \
    /--------\    Unit     - много (быстро, дёшево)
```

Логика: чем выше - тем медленнее и дороже тест, поэтому таких меньше.

---

## Тестовый трофей

Современная модель для фронтенда (Kent C. Dodds) смещает акцент на **интеграционные** тесты:

```
        ____
       /E2E \       немного
      /------\
     / Integr.\     БОЛЬШЕ ВСЕГО  ← золотая середина
    /----------\
    \   Unit   /     сколько нужно
     \________/
      Static          фундамент (TS, ESLint)
```

<b class="text-on-semi-light">Почему трофей для фронтенда</b> - <span class="text-gray">Юнит-тест проверяет функцию в вакууме, но пользователь взаимодействует с **собранным** UI. Интеграционные тесты (компонент + события + данные) дают **больше уверенности на единицу усилий**: они близки к тому, как реально работает приложение, но быстрее и стабильнее e2e. Поэтому их делают основой.</span>

> Пирамида vs трофей - это не «правильно/неправильно», а смещение фокуса. Для бэкенд-логики пирамида уместна; для UI трофей часто практичнее.

---

## Что тестировать

- **Поведение, важное для пользователя** - что отрисовалось, что происходит по действию.
- **Критические пути** - логин, оплата, отправка формы (то, что нельзя сломать).
- **Краевые случаи** - пустые состояния, ошибки, граничные значения.
- **Регрессии** - на каждый найденный баг пишут тест, чтобы он не вернулся.

---

## Что НЕ тестировать

| Не тестируй | Почему |
|-------------|--------|
| Детали реализации | имена методов, внутренний state - ломается при рефакторинге |
| Сторонние библиотеки | React, lodash уже протестированы их авторами |
| Тривиальный код | геттеры, константы - нечего ломаться |
| Сам фреймворк | не твоя ответственность |

<b class="text-on-semi-light">Главный антипаттерн</b> - <span class="text-gray">Тестировать **реализацию**, а не поведение. Такой тест падает при любом рефакторинге, даже если для пользователя ничего не изменилось - и даёт отрицательную ценность. Хороший тест переживает рефакторинг и падает только при реальной поломке поведения.</span>

## Структура теста

Общая структура - **AAA** (Arrange-Act-Assert) или Given-When-Then:

```js
test('пустая корзина показывает заглушку', () => {
  render(<Cart items={[]} />);          // Arrange - подготовить
  // Act - действие (здесь не нужно)
  expect(screen.getByText('Корзина пуста')).toBeInTheDocument(); // Assert - проверить
});
```

Имя теста описывает **поведение** («что происходит при чём»), а не реализацию.

---

## Smoke и regression тесты

- **Smoke-тесты** - быстрая проверка, что критичное вообще работает (приложение запускается, главная грузится). Первая линия после деплоя.
- **Regression-тесты** - набор, гарантирующий, что старая функциональность не сломалась новыми изменениями.

## Вопросы на собеседовании

<b class="text-on-semi-light">Какие бывают виды тестов?</b>
<span class="text-gray">Static (типы, линт), unit (модуль в изоляции), integration (несколько частей вместе), e2e (полный сценарий в браузере). Снизу вверх растёт реалистичность и стоимость.</span>

<b class="text-on-semi-light">Чем тестовый трофей отличается от пирамиды?</b>
<span class="text-gray">Пирамида - много unit, мало e2e. Трофей смещает основу на интеграционные тесты, потому что для фронтенда они дают больше уверенности на единицу усилий, оставаясь быстрыми и стабильными.</span>

<b class="text-on-semi-light">Почему для фронтенда упор на интеграционные тесты?</b>
<span class="text-gray">Пользователь взаимодействует с собранным UI, а не с функциями в вакууме. Интеграционные тесты близки к реальному использованию, но быстрее и надёжнее e2e.</span>

<b class="text-on-semi-light">Что НЕ нужно тестировать?</b>
<span class="text-gray">Детали реализации, сторонние библиотеки, тривиальный код и сам фреймворк. Тест на реализацию ломается при рефакторинге без изменения поведения - это вред.</span>

<b class="text-on-semi-light">Что делать, когда нашли баг?</b>
<span class="text-gray">Написать тест, воспроизводящий баг, затем исправить код. Тест закрывает регрессию - баг не вернётся незаметно.</span>
