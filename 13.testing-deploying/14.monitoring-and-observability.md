# Мониторинг и наблюдаемость

Тесты прошли, деплой успешен - но пользователь всё равно столкнулся с ошибкой на устройстве, которого у тебя нет, при сети, которую ты не воспроизводил. **Мониторинг** показывает, что **реально** происходит в проде. Это вторая половина уверенности: тесты ловят до релиза, мониторинг - после.

---

## Зачем мониторинг

Прод непредсказуем: тысячи устройств, браузеров, сетей, краевых случаев. Никакие тесты не покроют всё. Мониторинг даёт **обратную связь из реального мира**:

- ловить ошибки, которых не было в тестах;
- видеть реальную производительность у пользователей;
- узнавать о проблеме **раньше**, чем напишут в поддержку;
- понимать, как фичи используются.

> Тесты - предсказание («должно работать»), мониторинг - факт («вот что у пользователей»). Зрелый процесс нужны оба.

---

## Трекинг ошибок

Инструменты вроде **Sentry** перехватывают исключения в проде и присылают подробный отчёт.

```js
import * as Sentry from '@sentry/react';
Sentry.init({ dsn: '...', tracesSampleRate: 0.1 });
```

Что даёт:

- **стектрейс** - и благодаря [source maps](/content/advanced-tooling/optimization) он указывает на **исходный** TS, а не минифицированный код;
- **контекст** - браузер, ОС, пользователь, маршрут;
- **breadcrumbs** - что пользователь делал до ошибки;
- **группировку** одинаковых ошибок и **алерты** при всплеске.

<b class="text-on-semi-light">Связь с error boundaries</b> - <span class="text-gray">[Error boundaries](/content/reactjs/patterns-and-component-design) React ловят падения рендера и показывают fallback - и в их обработчике ошибку **отправляют в Sentry**. Так пользователь видит запасной UI, а команда - отчёт. Без трекинга ошибки в проде просто теряются.</span>

---

## RUM - реальная производительность

**Real User Monitoring** измеряет производительность у **настоящих** пользователей (field data), а не в лабораторных условиях (как [Lighthouse](/content/advanced-tooling/devtools-and-debugging)).

Ключевые метрики - **Core Web Vitals**:

| Метрика | Что измеряет |
|---------|--------------|
| **LCP** | время до отрисовки основного контента |
| **CLS** | визуальная стабильность (скачет ли лейаут) |
| **INP** | отзывчивость на взаимодействия |

```js
import { onLCP, onCLS, onINP } from 'web-vitals';
onLCP(sendToAnalytics); onCLS(sendToAnalytics); onINP(sendToAnalytics);
```

<b class="text-on-semi-light">Lab vs field</b> - <span class="text-gray">Lighthouse в DevTools - лабораторные данные (одна машина, идеальная сеть). RUM - **полевые**: реальные устройства и сети пользователей. Часто расходятся: в лаборатории быстро, а у пользователей на слабых телефонах - нет. Оптимизируют по полевым данным.</span>

## Продуктовая аналитика

Отдельно от ошибок и перфоманса - **как пользователи используют** продукт: какие фичи, где отваливаются, конверсии. Инструменты: **PostHog**, Google Analytics, Amplitude. Часто связаны с [фичефлагами](/content/testing-deploying/deployment-strategies) для A/B-тестов.

---

## Логи, метрики, трейсы

Три «столпа» наблюдаемости (больше про сервер/edge, но фронтенд их касается):

- **Логи** - структурированные записи событий (на сервере/в edge-функциях; на клиенте логировать осторожно - попадает к пользователю).
- **Метрики** - числовые показатели во времени (частота ошибок, latency).
- **Трейсы** - путь запроса через систему (клиент → API → БД); OpenTelemetry.

---

## Алерты и uptime

- **Алерты** - автоматические уведомления при превышении порога (всплеск ошибок, рост latency, падение конверсии) - чтобы узнать о проблеме раньше пользователей.
- **Uptime / synthetic-мониторинг** - регулярные автоматические проверки «жив ли сайт» из разных регионов (Pingdom, Checkly). Дополняют RUM: ловят полное падение, даже когда живых пользователей мало.

---

## Замыкая круг

Эта глава прошла полный цикл - и мониторинг замыкает его:

```
ТЕСТЫ (до прода) → ДЕПЛОЙ → МОНИТОРИНГ (в проде)
        ▲                          │
        └─── баг найден → тест ◄────┘  обратная связь
```

> Нашли ошибку в проде через Sentry → воспроизвели → **написали тест** ([регрессия](/content/testing-deploying/testing-strategy-and-pyramid)) → исправили → задеплоили → следим. Тестирование и деплой - не два отдельных этапа, а единый цикл повышения надёжности.

## Вопросы на собеседовании

<b class="text-on-semi-light">Зачем мониторинг, если есть тесты?</b>
<span class="text-gray">Тесты не покроют все устройства, браузеры и сети реального мира. Мониторинг показывает фактические ошибки и производительность у пользователей и даёт знать о проблеме раньше поддержки.</span>

<b class="text-on-semi-light">Как работает трекинг ошибок (Sentry)?</b>
<span class="text-gray">Перехватывает исключения в проде и шлёт отчёт со стектрейсом (через source maps - в исходном коде), контекстом, breadcrumbs, группировкой и алертами. Error boundaries отправляют ошибки туда же.</span>

<b class="text-on-semi-light">Чем RUM отличается от Lighthouse?</b>
<span class="text-gray">Lighthouse - лабораторные данные (одна машина, идеальная сеть). RUM - полевые, у реальных пользователей. Они часто расходятся; оптимизировать нужно по полевым (Core Web Vitals: LCP, CLS, INP).</span>

<b class="text-on-semi-light">Что такое Core Web Vitals?</b>
<span class="text-gray">LCP (отрисовка основного контента), CLS (стабильность лейаута), INP (отзывчивость на взаимодействия) - ключевые метрики пользовательского опыта, измеряемые в проде.</span>

<b class="text-on-semi-light">Зачем нужны алерты и uptime-мониторинг?</b>
<span class="text-gray">Алерты уведомляют о всплеске ошибок/latency раньше пользователей. Uptime-проверки из разных регионов ловят полное падение сайта, даже когда живого трафика мало.</span>
