# Мониторинг и наблюдаемость

Что происходит с приложением у настоящих пользователей: трекинг ошибок, сбор метрик производительности в поле, логи, метрики и трейсы, алерты и синтетические проверки, личные данные в отчётах. Спрашивают, зачем мониторинг, если есть тесты, как работает трекинг ошибок и чем данные пользователей отличаются от Lighthouse. Глубже — почему в отчёте только «Script error.», как не потерять событие при закрытии страницы и почему алерт на каждую ошибку хуже, чем никакого.

::tldr
- **Тесты предсказывают, мониторинг показывает факт:** тысячи устройств, браузеров и сетей, которых нет в CI. Цель — узнать о проблеме раньше, чем напишут в поддержку.
- **Трекинг ошибок** — Sentry и аналоги — ловит необработанные исключения и отказы промисов, добавляет контекст и путь пользователя до ошибки, группирует одинаковые и показывает исходный код через source maps.
- **Скрипт с другого домена без `crossorigin` и CORS даёт только `Script error.`** — без сообщения, файла и строки.
- **Метрики в поле** — Core Web Vitals у настоящих пользователей через `web-vitals` — отправляют через `sendBeacon` при скрытии страницы, иначе последние данные теряются.
- **Алерт — на изменение, которое требует действия:** всплеск ошибок после выкладки, рост задержки, падение конверсии. Синтетические проверки ловят полное падение, когда пользователей мало. Личные данные вычищают до отправки.
::

---

## Зачем мониторинг

Сквозной пример — магазин после выкладки нового оформления заказа: ошибка в старом Safari, медленный API оплаты под нагрузкой и баннер, который сдвигает страницу.

Никакой набор тестов не повторит продакшен: устройства, расширения браузеров, мобильная сеть, данные, которых нет на стенде. Мониторинг даёт обратную связь из реального мира:

- ошибки, которых не было в тестах;
- производительность на настоящих устройствах и сетях;
- проблема видна раньше, чем о ней сообщат пользователи;
- после выкладки видно, стало лучше или хуже — на этом стоят canary и автоматический откат (подробно — в [Стратегиях выкладки](/content/testing-deploying/deployment-strategies)).

## Трекинг ошибок

**Sentry**, Bugsnag, Rollbar, встроенные решения Datadog и New Relic перехватывают ошибки в браузере и присылают отчёт:

```js
import * as Sentry from '@sentry/browser';

Sentry.init({
  dsn: 'https://…@o0.ingest.sentry.io/0',
  release: 'shop-web@1.4.2',
  environment: 'production',
  sampleRate: 1.0,
  tracesSampleRate: 0.1,
  beforeSend: (event) => scrub(event),
});
```

Что в отчёте:

- **стек** — с source maps он указывает на исходный TypeScript, а не на минифицированную строку; карты загружают в сервис при выкладке, а не на публичный сервер (подробно — в [Отладке и source maps](/content/advanced-tooling/devtools-and-debugging));
- **контекст** — браузер, ОС, адрес, версия выкладки (`release`), пользователь;
- **хлебные крошки** — клики, переходы, запросы и логи до ошибки;
- **группировка** — тысячи одинаковых ошибок становятся одной проблемой со счётчиком;
- **связь с выкладкой** — видно, в каком релизе ошибка появилась.

### Что перехватывается

SDK подписывается на глобальные события. В проверке:

```js
addEventListener('error', (e) => report(e.message));
addEventListener('unhandledrejection', (e) => report(e.reason.message));
```

- ошибка `null.price` в таймере пришла в `error`: `Cannot read properties of null (reading 'price')`;
- `Promise.reject(new Error('API оплаты ответил 502'))` без обработчика пришла в `unhandledrejection` — это отдельное событие, и обработчик `error` его не видит;
- запрос с `.catch()` не попал никуда: обработанные ошибки сервис не видит, их отправляют явно — `Sentry.captureException(error)`.

Ошибки рендера, пойманные границей ошибок React, тоже не всплывают до `window`: их отправляют из обработчика границы (подробно — в [Паттернах и дизайне компонентов](/content/reactjs/patterns-and-component-design)).

### Script error.

Скрипты часто лежат на CDN — другом источнике. В проверке скрипт с другого порта выбросил `TypeError`, а `onerror` страницы получил:

```text
msg: "Script error.", src: "", line: 0
```

Браузер скрывает детали ошибок чужих скриптов, чтобы страница не могла выведать данные другого источника. Исправление — два условия вместе:

```html
<script crossorigin="anonymous" src="https://cdn.shop.example/assets/index-B2kX9f.js"></script>
```

```text
Access-Control-Allow-Origin: https://shop.example
```

С ними в проверке пришло полное сообщение `TypeError: price is not a number`, файл и строка. Сборщики добавляют `crossorigin` к своим скриптам сами, а заголовок настраивают на CDN.

## Производительность в поле

**RUM** — сбор метрик у настоящих пользователей. Lighthouse измеряет одну машину в лаборатории, а пользователи — это медленные телефоны и плохая сеть, и цифры часто расходятся. Как устроены Core Web Vitals — LCP, INP, CLS — и что их ухудшает, разобрано в [Core Web Vitals](/content/security-perfomance/core-web-vitals), а лабораторные данные против полевых — в [Измерении и мониторинге](/content/security-perfomance/measuring-and-monitoring).

Сбор — библиотека `web-vitals`:

```js
import { onLCP, onINP, onCLS } from 'web-vitals';

const send = (metric) => navigator.sendBeacon('/rum', JSON.stringify({
  name: metric.name, value: metric.value, rating: metric.rating, page: location.pathname,
}));

onLCP(send); onINP(send); onCLS(send);
```

В проверке баннер высотой 300 пикселей, вставленный над заголовком через 300 мс, дал CLS больше 0,1, и `web-vitals` оценил его не как `good`. В лаборатории это бы не всплыло, если баннер приходит из рекламной сети только у части пользователей.

### Не потерять событие

CLS и INP окончательно известны только когда пользователь уходит, поэтому `web-vitals` сообщает их при скрытии страницы. Обычный `fetch` в этот момент браузер может прервать. `navigator.sendBeacon` ставит запрос в очередь браузера, и он уходит после закрытия страницы. В проверке маяк, отправленный в `pagehide`, сервер получил уже после перехода на другую страницу. Альтернатива — `fetch(url, { keepalive: true })`.

Отправляют по событию `visibilitychange` в состоянии `hidden` или `pagehide`, а не `unload`: на мобильных `unload` часто не срабатывает, а его наличие мешает кешу страниц браузера.

### Что смотреть

Данные агрегируют по **75-му процентилю** — так же, как Google в отчёте CrUX, — и делят по типу устройства, странице и стране. Среднее прячет медленный хвост.

## Логи, метрики, трейсы

Три источника наблюдаемости, больше серверных, но фронтенд с ними связан:

- **логи** — записи о событиях с контекстом; на клиенте их не пишут в консоль пачками, а отправляют выборочно как хлебные крошки или события;
- **метрики** — числа во времени: доля ошибок, задержка API, конверсия;
- **трейсы** — путь запроса через систему: клик в браузере → API → база. Стандарт — **OpenTelemetry**, а связь между фронтендом и бэкендом — заголовок `traceparent`, который клиент передаёт в запросе.

Трейс отвечает на вопрос «почему оформление заказа заняло 4 секунды»: в браузере — 200 мс, на API — 300 мс, а 3,5 секунды — ожидание платёжного шлюза.

## Алерты и синтетика

### Алерты

Алерт должен означать «нужно действие»:

- **рост доли ошибок** — особенно сразу после выкладки, в сравнении с прошлым релизом;
- **новая проблема** в трекинге ошибок, которой раньше не было;
- **ухудшение метрик** — p75 LCP или INP, задержка API, доля неуспешных платежей;
- **падение бизнес-метрики** — конверсия оформления заказа.

Алерт на каждую отдельную ошибку быстро превращается в шум, который все отключают. Пороги задают по доле и по изменению, а не по абсолютному числу.

### Синтетические проверки

**Синтетический мониторинг** — скрипт по расписанию из разных регионов: «главная открывается», «товар добавляется в корзину». Checkly, Datadog Synthetics, Grafana и обычные e2e-сценарии Playwright по расписанию. Он ловит полное падение ночью, когда пользователей мало и RUM молчит, и проверяет критичный путь сразу после выкладки — это те же smoke-тесты (подробно — в [Стратегии тестирования](/content/testing-deploying/testing-strategy-and-pyramid)).

## Личные данные

В отчёт об ошибке легко попадают email из адреса страницы, номер карты из текста ошибки, токен из заголовков. Это утечка и нарушение требований к персональным данным. В проверке очистка перед отправкой превратила

```text
Не удалось оплатить: anya@shop.example, карта 4111 1111 1111 1111
```

в `Не удалось оплатить: [email], карта [card]` — в том числе в адресе страницы. В SDK это делают в `beforeSend` и `beforeBreadcrumb`, а на стороне сервиса включают серверную очистку. Запись сессий маскирует поля ввода и текст по умолчанию.

## Замыкая круг

```text
тесты → выкладка → мониторинг
  ▲                    │
  └── тест на баг ◄────┘
```

Ошибку нашли в трекинге → воспроизвели → написали тест, который падает (подробно — во [Введении](/content/testing-deploying/introduction)) → исправили → выложили → проверили, что проблема ушла из отчётов. Тестирование и выкладка — один цикл повышения надёжности.

---

## Красные флаги в ответе

- **«Есть тесты — мониторинг не нужен».** Продакшен — это устройства и данные, которых нет в CI.
- **«В отчётах только `Script error.`, Sentry бесполезен».** Нужны `crossorigin` и CORS-заголовок у скриптов с CDN.
- **«Метрики отправлю в `unload` через `fetch`».** Событие ненадёжно, запрос может прерваться — нужны `visibilitychange` и `sendBeacon`.
- **«Смотрим среднее время загрузки».** Среднее прячет медленный хвост — смотрят 75-й процентиль по сегментам.
- **«Алерт на каждую ошибку».** Шум, который отключат; алерт — на изменение доли и новые проблемы.
- **«Отправляем всё как есть».** В отчёты попадут email, токены и номера карт.

## Как спрашивают на собеседовании

::question
Зачем мониторинг, если есть тесты?

#answer
Тесты проверяют предсказанные сценарии на своих данных и машинах, а продакшен — это тысячи устройств, браузеров, расширений и сетей. Мониторинг показывает фактические ошибки и производительность у пользователей и сообщает о проблеме раньше поддержки.

#more
Мониторинг замыкает цикл: ошибка из продакшена превращается в тест, а сравнение метрик до и после выкладки — в основу canary и автоматического отката.
::

::question
Как работает трекинг ошибок?

#answer
SDK подписывается на глобальные события `error` и `unhandledrejection`, собирает стек, контекст и хлебные крошки — действия пользователя до ошибки — и отправляет отчёт. Сервис группирует одинаковые ошибки и с помощью source maps показывает исходный код.

#more
Обработанные ошибки сервис не видит — их отправляют явно через `captureException`. Ошибки, пойманные границей ошибок React, тоже отправляют из её обработчика. Версия выкладки в отчёте связывает ошибку с релизом.
::

::question
Почему в отчёте только «Script error.»?

#answer
Скрипт загружен с другого источника — например, CDN — без CORS. Браузер скрывает детали ошибок чужих скриптов: сообщение, файл и строку.

#more
Нужны оба условия: атрибут `crossorigin="anonymous"` у тега `script` и заголовок `Access-Control-Allow-Origin` в ответе CDN. Тогда приходит полное сообщение с файлом и строкой.
::

::question
Чем RUM отличается от Lighthouse?

#answer
Lighthouse — лабораторное измерение на одной машине с заданной сетью. RUM — полевые данные у настоящих пользователей на их устройствах и сетях. Они часто расходятся, а оптимизируют по полевым.

#more
Полевые метрики собирают библиотекой `web-vitals`, отправляют через `sendBeacon` при скрытии страницы и смотрят 75-й процентиль по типу устройства и странице. Лаборатория остаётся инструментом поиска причин.
::

::question
Как надёжно отправить метрики при уходе пользователя?

#answer
Отправлять по `visibilitychange` в состоянии `hidden` или по `pagehide` через `navigator.sendBeacon` или `fetch` с `keepalive: true`. Браузер доставит такой запрос и после закрытия страницы.

#more
`unload` на мобильных часто не срабатывает и мешает кешу страниц. CLS и INP окончательно известны только при уходе, поэтому `web-vitals` сообщает их именно в этот момент.
::

::question
Какие алерты нужны фронтенду?

#answer
Те, что требуют действия: рост доли ошибок, особенно после выкладки, новая проблема в трекинге, ухудшение p75 Core Web Vitals, рост задержки API, падение конверсии ключевого сценария.

#more
Алерт на каждую ошибку становится шумом и его отключают. Синтетические проверки по расписанию дополняют алерты: ловят полное падение, когда пользователей мало, и проверяют критичный путь после выкладки.
::

## Практика

::practice{title="В Sentry только «Script error.»"}
После переезда статики на CDN `cdn.shop.example` все ошибки в Sentry превратились в `Script error.` без стека и строки.

#solution
Скрипты теперь с другого источника, и браузер скрывает детали их ошибок. В проверке скрипт с другого порта дал `onerror` только `Script error.`, пустой файл и строку 0. Нужны оба условия:

```html
<script type="module" crossorigin="anonymous" src="https://cdn.shop.example/assets/index-B2kX9f.js"></script>
```

```text
# ответ CDN
Access-Control-Allow-Origin: https://shop.example
```

С ними в проверке пришло полное `TypeError: price is not a number`, файл и строка. Vite добавляет `crossorigin` к модульным скриптам сам — остаётся заголовок на CDN. Без CORS-заголовка скрипт с `crossorigin` не загрузится вовсе, поэтому заголовок включают первым.
::

::practice{title="CLS в отчёте лучше, чем у пользователей"}
Команда отправляет CLS в аналитику из `window.onload`, и он почти всегда нулевой. Пользователи жалуются, что страница товара «прыгает».

#solution
CLS копится всё время жизни страницы: баннеры, шрифты и картинки сдвигают содержимое уже после `onload`. В проверке баннер, вставленный через 300 мс, дал CLS больше 0,1. Метрику отправляют, когда она окончательная, — при скрытии страницы:

```js
import { onCLS } from 'web-vitals';

onCLS((metric) => {
  navigator.sendBeacon('/rum', JSON.stringify({ name: metric.name, value: metric.value, page: location.pathname }));
});
```

`web-vitals` сам вызывает обработчик при скрытии страницы, а `sendBeacon` доставляет данные после её закрытия — в проверке маяк из `pagehide` пришёл после ухода со страницы. Исправление самого сдвига — зарезервировать место под баннер заранее (подробно — в [Core Web Vitals](/content/security-perfomance/core-web-vitals)).
::
