# Как подходить к любой задаче

Финальная глава раздела - не новые задачи, а **переносимый метод**. Конкретные функции забудутся, а навык «как разложить незнакомую задачу и довести до рабочего решения, не молча» останется. Это то, что реально оценивает интервьюер.

---

## Универсальный алгоритм решения

Один скелет работает для утилиты, компонента и output-задачи. Проговаривай его вслух:

1. **Уточни** - сигнатура, типы входа/выхода, ограничения, объёмы данных.
2. **Примеры** - обычный + краевой. Это спецификация и будущие тесты.
3. **Наивно** - сначала рабочее, потом красивое. Молчать нельзя.
4. **Оптимизируй** - сложность, лишние проходы, лишняя память.
5. **Краевые случаи** - пустота, `null`, дубликаты, гонки, отписка.
6. **Проверь** - прогони пример руками, будто ты отладчик.

> Этот цикл - не формальность. Интервьюер ставит галочки именно по нему: уточнил ли, привёл ли примеры, проверил ли сам.

## Уточняющие вопросы

Хорошие вопросы в начале - сигнал инженерной зрелости. Что почти всегда стоит спросить:

| Категория | Вопросы |
| --- | --- |
| **Вход** | Какие типы? Может ли быть пустым/`null`? Размер данных? |
| **Выход** | Новый объект или мутация на месте? Что при ошибке? |
| **Поведение** | Синхронно или async? Краевые режимы (один/несколько)? |
| **Окружение** | Можно ли использовать встроенные методы/библиотеки? |
| **Масштаб** | Сколько элементов? Важна производительность? |

> ⚠️ Не уточнить - частая причина провала. Кандидат решает не ту задачу, потому что додумал условие. 30 секунд вопросов экономят 10 минут не туда.

## Думай вслух

Главное отличие сильного кандидата - **непрерывная коммуникация**. Интервьюер должен слышать ход мысли:

```ts
// Вместо молчания:
"Так, на входе массив, на выходе новый без дублей.
 Возьму Set - O(n), но он не сработает для объектов...
 уточню: тут примитивы? Да -> Set подойдёт.
 Краевой случай - пустой массив вернёт []. Пишу."
const unique = <T>(arr: T[]): T[] => [...new Set(arr)];
```

- Озвучивай **выбор и компромиссы**, а не только финальный код.
- Застрял - **скажи об этом** и рассуждай вслух. Молчаливая пауза хуже честного «думаю над краевым случаем».
- Не знаешь API точно - проговори намерение: «здесь нужен метод, который...».

## Сложность не забывается

Фронтенд-задачи не отменяют Big-O - добавляют к нему платформу:

- Назови сложность своего решения **до того, как спросят**.
- Замечай скрытые квадраты: спред в цикле (`[...acc, x]`), вложенные `includes`, перерендеры списков.
- Помни про память: лишние копии, утечки таймеров/слушателей, незакрытые подписки.

```ts
// O(n²) - спред в reduce пересоздаёт массив каждый раз
arr.reduce((acc, x) => [...acc, fn(x)], []);
// O(n) - мутируем аккумулятор
arr.reduce((acc, x) => { acc.push(fn(x)); return acc; }, []);
```

## Частые ошибки

- **Сразу писать код молча** - оценивают процесс, а не только результат.
- **Не уточнить условие** - решение не той задачи.
- **Игнорировать краевые случаи** - пустота, `null`, гонки всплывут на проверке.
- **Сразу в стили/микрооптимизации** - сначала рабочая логика.
- **Стрелка вместо `function`** там, где нужен `this`.
- **Забыть cleanup** - утечки таймеров, слушателей, подписок.
- **Не проверить решение** - прогон примера ловит половину багов до интервьюера.

## Чеклист перед «готово»

Прежде чем сказать «решение готово», пройдись по списку:

- [ ] Уточнил вход/выход и краевые случаи.
- [ ] Привёл и прогнал хотя бы один пример руками.
- [ ] Обработал пустоту, `null`, границы.
- [ ] Для async - подумал о гонках и отмене.
- [ ] Для UI - подумал о a11y и cleanup.
- [ ] Назвал сложность по времени и памяти.
- [ ] Имена понятны, нет дублирования.

## Вопросы на собеседовании

<b class="text-on-semi-light">С чего ты начинаешь решать незнакомую задачу?</b>
<span class="text-gray">С уточняющих вопросов про вход/выход и краевые случаи, затем примеры, затем наивное рабочее решение и только потом оптимизация. И всё это вслух - чтобы интервьюер видел ход мысли.</span>

<b class="text-on-semi-light">Что делать, если застрял на интервью?</b>
<span class="text-gray">Не молчать. Проговорить, где затык, вернуться к примерам, попробовать наивный или частный случай. Честное рассуждение вслух ценится выше тихой паузы - интервьюер часто подсказывает направление.</span>

<b class="text-on-semi-light">Почему важно проговаривать решение вслух?</b>
<span class="text-gray">Оценивают процесс мышления и коммуникацию, а не только финальный код. Разговорчивое почти-идеальное решение производит лучшее впечатление, чем молчаливое идеальное - и помогает интервьюеру направить тебя.</span>

<b class="text-on-semi-light">Как не забыть про краевые случаи?</b>
<span class="text-gray">Держать стандартный список: пустой ввод, `null`/`undefined`, границы (первый/последний, один элемент), дубликаты, для async - гонки и отмену, для UI - cleanup и a11y. Прогнать пример руками перед «готово».</span>
