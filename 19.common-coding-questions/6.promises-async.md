# Промисы и асинхронность

Асинхронные задачи — визитная карточка фронтенд-собеседования: без них не написать ни одного реального приложения. Здесь — комбинаторы промисов руками (`all`, `allSettled`, `race`, `any`), `promisify`, `retry` с экспоненциальной задержкой, ограничение конкурентности и последовательная очередь. Спрашивают, как `Promise.all` сохраняет порядок, чем `race` отличается от `any` и как ограничить число одновременных запросов. Глубже — почему самописный `any` висит на пустом массиве, почему `all` должен принимать любой итерируемый объект и почему упавшая задача может навсегда остановить очередь.

::tldr
- **Promise.all пишет результат по индексу и резолвится по счётчику:** промисы завершаются в любом порядке, индекс сохраняет исходный. Первая ошибка сразу отклоняет весь результат.
- **Комбинаторы сверяют с нативными на краях:** в проверке самописный `any([])` висел вечно, а нативный сразу отклонился с `AggregateError`; самописный `all(new Set(…))` тоже висел — нативный принимает любой итерируемый объект.
- **race — первый исход, any — первый успех:** `race` завершается и ошибкой, `any` отклоняется только если упали все.
- **mapLimit держит ровно limit задач в полёте:** `limit` воркеров берут задачи из общего индекса. В проверке одновременно выполнялось не больше трёх, а результаты пришли в исходном порядке.
- **Очередь переживает упавшую задачу:** без `try/catch` вокруг задачи в проверке очередь навсегда осталась в состоянии «выполняется» и следующие задачи не запустились.
::

## Promise.all

`Promise.all` ждёт все промисы и возвращает массив результатов в исходном порядке; при первой ошибке отклоняется целиком. Как устроены промисы и комбинаторы как понятие — в [асинхронности](/content/javascript/async); здесь — как написать их самому.

```ts
function promiseAll<T>(iterable: Iterable<T | PromiseLike<T>>): Promise<Awaited<T>[]> {
  const items = Array.from(iterable);                // любой итерируемый, как нативный
  return new Promise((resolve, reject) => {
    const results: Awaited<T>[] = new Array(items.length);
    let completed = 0;
    if (items.length === 0) return resolve([]);
    items.forEach((p, index) => {
      Promise.resolve(p).then((value) => {
        results[index] = value as Awaited<T>;          // по индексу — исходный порядок
        if (++completed === items.length) resolve(results);
      }, reject);                                      // первая ошибка — сразу reject
    });
  });
}
```

Ключевые моменты:

1. **порядок** — результат пишется по индексу, а не через `push`. В проверке промисы завершились в обратном порядке, а результат пришёл как `['первый', 'второй', 'не промис']`;
2. **счётчик** — резолвим, когда завершились все, а не когда массив «выглядит полным»: у массива с дырами длина та же;
3. **пустой вход** — сразу `[]`;
4. **не-промисы** — оборачиваются в `Promise.resolve`;
5. **любой итерируемый** — нативный `Promise.all` принимает `Set`, генератор, что угодно итерируемое. Версия с `promises.length` и `forEach` на `Set` в проверке так и не завершилась: длины у `Set` нет, а его `forEach` передаёт вместо индекса само значение. `Array.from` в начале решает это.

При первой ошибке результат отклоняется, не дожидаясь остальных: в проверке отказ второго промиса отклонил `all`, хотя первый ещё не завершился.

## Promise.allSettled

`allSettled` ждёт все промисы и никогда не отклоняется: возвращает массив объектов `{ status, value }` или `{ status, reason }`. Нужен, когда важны все исходы — например, сохранить, какие из пачки загрузок удались.

```ts
function promiseAllSettled<T>(iterable: Iterable<T | PromiseLike<T>>) {
  return promiseAll(Array.from(iterable, (p) => Promise.resolve(p).then(
    (value) => ({ status: 'fulfilled' as const, value }),
    (reason) => ({ status: 'rejected' as const, reason }),
  )));
}
```

Трюк — превратить каждый промис во «всегда успешный» через `.then(onOk, onErr)`, и тогда `all` уже не отклонится. В проверке результат для набора из успеха, ошибки и не-промиса совпал с нативным `Promise.allSettled` один в один.

## Promise.race и Promise.any

`race` завершается первым завершившимся промисом — любым исходом. `any` — первым успешным, а отклоняется с `AggregateError`, только если упали все:

```ts
function promiseRace<T>(iterable: Iterable<T | PromiseLike<T>>): Promise<Awaited<T>> {
  return new Promise((resolve, reject) => {
    for (const p of iterable) Promise.resolve(p).then(resolve, reject); // кто первый — тот и решает
  });
}

function promiseAny<T>(iterable: Iterable<T | PromiseLike<T>>): Promise<Awaited<T>> {
  const items = Array.from(iterable);
  return new Promise((resolve, reject) => {
    const errors: unknown[] = new Array(items.length);
    let rejected = 0;
    if (items.length === 0) return reject(new AggregateError([], 'All promises were rejected'));
    items.forEach((p, i) => {
      Promise.resolve(p).then(resolve, (err) => {
        errors[i] = err;
        if (++rejected === items.length) reject(new AggregateError(errors, 'All promises were rejected'));
      });
    });
  });
}
```

В проверке `race` отклонился, когда первым завершился промис с ошибкой, а `any` при одной ошибке и одном успехе дал успех; при двух ошибках — `AggregateError` с ошибками в исходном порядке. Краевой случай — пустой вход, и здесь комбинаторы ведут себя по-разному:

- пустой `race` висит вечно — в проверке и самописный, и нативный остались в ожидании;
- пустой `any` нативно сразу отклоняется с `AggregateError`, ведь «все упали» для пустого набора истинно. Версия без явной проверки пустого массива в проверке не завершилась никогда: счётчик ошибок не может достичь нуля.

| Комбинатор | Выполняется | Отклоняется | Пустой вход |
| --- | --- | --- | --- |
| `all` | когда все успешны | при первой ошибке | сразу `[]` |
| `allSettled` | когда все завершились | никогда | сразу `[]` |
| `race` | первым исходом | первым исходом, если это ошибка | висит вечно |
| `any` | первым успехом | когда упали все (`AggregateError`) | сразу `AggregateError` |

## promisify

`promisify` превращает функцию с колбэком в стиле Node (`(err, data) => …` последним аргументом) в функцию, возвращающую промис:

```ts
type NodeCallback<T> = (err: unknown, data?: T) => void;
function promisify<A extends unknown[], T>(fn: (...args: [...A, NodeCallback<T>]) => void) {
  return function (this: unknown, ...args: A): Promise<T> {
    return new Promise((resolve, reject) => {
      fn.call(this, ...args, (err: unknown, data?: T) => {
        if (err != null) reject(err);   // null и undefined — успех
        else resolve(data as T);
      });
    });
  };
}
```

Две детали. Обёртка — обычная `function`, а вызов через `call`, чтобы промисифицированный метод сохранил `this`: в проверке `promisify(store.get).call(store, 'anna')` вернул `'u:anna'` с префиксом из объекта. И ошибкой считается любой `err`, кроме `null` и `undefined`, — проверка `if (err)` пропустила бы ошибку, переданную как `0` или пустая строка. В Node есть готовый `util.promisify`.

## sleep и retry

`sleep` — основа многих асинхронных задач, а `retry` повторяет операцию с паузой, обычно с экспоненциальной задержкой:

```ts
const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));

async function retry<T>(fn: () => Promise<T>, retries = 3, delay = 500): Promise<T> {
  try {
    return await fn();
  } catch (err) {
    if (retries <= 0) throw err;
    await sleep(delay);
    return retry(fn, retries - 1, delay * 2); // экспоненциальная задержка
  }
}
```

В проверке операция, которая падала дважды, выполнилась с третьей попытки, а паузы между попытками выросли вдвое. Стоит уточнить семантику: `retries = 3` — это три повтора, то есть четыре попытки всего. В проверке всегда падающая операция была вызвана четыре раза, и наружу ушла последняя ошибка. В реальных системах к задержке добавляют случайный разброс (jitter), чтобы много клиентов не повторяли запросы синхронно, и повторяют только то, что можно повторить безопасно.

## Ограничение конкурентности

Выполнить много асинхронных задач, но не больше `limit` одновременно, — классика «не положить сервер тысячей параллельных запросов»:

```ts
async function mapLimit<T, U>(items: T[], limit: number, fn: (item: T) => Promise<U>): Promise<U[]> {
  const results: U[] = new Array(items.length);
  let index = 0;
  async function worker() {
    while (index < items.length) {
      const current = index++;               // между чтением и инкрементом нет await
      results[current] = await fn(items[current]);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

Запускаем ровно `limit` воркеров, каждый в цикле берёт следующую свободную задачу из общего индекса. Гонки за индекс нет: JavaScript однопоточный, а между чтением `index` и инкрементом нет `await`, где другой воркер мог бы вклиниться. В проверке на восьми задачах разной длительности с лимитом 3 одновременно выполнялось ровно три, первыми стартовали первые три, а результаты пришли в исходном порядке, хотя задачи завершались вперемешку.

Уточняющий вопрос — что делать при ошибке. В этой версии первая ошибка отклоняет результат, но остальные воркеры продолжают брать задачи; если нужно остановиться, добавляют флаг отмены или `AbortSignal`.

## Очередь задач

Иногда нужно наоборот — выполнять задачи строго по одной, например сохранения, порядок которых важен:

```ts
class AsyncQueue {
  private queue: Array<() => Promise<void>> = [];
  private running = false;
  errors: unknown[] = [];
  add(task: () => Promise<void>) {
    this.queue.push(task);
    void this.run();
  }
  private async run() {
    if (this.running) return;            // уже крутится — второй цикл не запускаем
    this.running = true;
    try {
      while (this.queue.length) {
        const task = this.queue.shift()!;
        try { await task(); } catch (e) { this.errors.push(e); } // упавшая задача не останавливает очередь
      }
    } finally {
      this.running = false;
    }
  }
}
```

Без `try/catch` вокруг задачи ошибка выходит из цикла, флаг `running` остаётся `true`, и следующий `add` больше никогда не запустит обработку. В проверке такая версия выдала необработанную ошибку, а задача, добавленная после упавшей, так и не выполнилась. С исправлением задачи прошли строго по очереди — `A start`, `A end`, `C start`, `C end`, — а ошибка B попала в список ошибок, не остановив очередь.

## Красные флаги в ответе

- `results.push(value)` в `Promise.all` вместо записи по индексу — порядок теряется.
- Резолв, когда «массив заполнен», а не по счётчику завершённых.
- Нет обработки пустого входа — `any([])` висит вечно.
- Комбинаторы принимают только массивы, хотя нативные — любые итерируемые.
- `promisify` теряет `this` или считает ошибкой только «истинный» `err`.
- `mapLimit`, который запускает все задачи сразу, а лимит лишь «ждёт».
- Очередь без обработки ошибок задачи — застревает навсегда.

## Как спрашивают на собеседовании

::question
Как Promise.all сохраняет порядок результатов?

#answer
Записывает результат каждого промиса по его индексу (`results[index] = value`), а не через `push`: промисы завершаются в произвольном порядке, индекс сохраняет исходный. Резолвится по счётчику завершённых, а не по виду массива.

#more
В проверке промисы завершились в обратном порядке, а результат пришёл в исходном. Нативный `Promise.all` принимает любой итерируемый объект, поэтому в полифиле вход сначала превращают в массив через `Array.from`: версия с `.length` на `Set` не завершилась никогда.
::

::question
Чем allSettled отличается от all?

#answer
`all` отклоняется при первой ошибке. `allSettled` ждёт все и никогда не отклоняется, возвращая массив `{ status, value }` или `{ status, reason }`. Реализуется оборачиванием каждого промиса во «всегда успешный» через `.then(onOk, onErr)` и `all` поверх.

#more
`allSettled` нужен, когда важен каждый исход: какие файлы загрузились, какие запросы упали. В проверке результат самописной версии совпал с нативным. Для «нужны все, но если хоть один упал — остановить остальные» берут `all` плюс отмену через `AbortController`.
::

::question
В чём разница race и any?

#answer
`race` завершается первым завершившимся промисом — любым исходом, включая ошибку. `any` завершается первым успешным и отклоняется с `AggregateError`, только если упали все.

#more
На пустом входе они расходятся: пустой `race` висит вечно, пустой `any` сразу отклоняется с `AggregateError`. В проверке самописный `any` без явной проверки пустого массива не завершился никогда. `race` часто используют для таймаута: `Promise.race([fetch(url), timeout(5000)])`.
::

::question
Как ограничить число одновременных запросов?

#answer
Пул воркеров: запускаем `limit` асинхронных функций, каждая в цикле берёт следующую задачу по общему индексу. В полёте всегда не больше `limit` задач, а освободившийся воркер сразу берёт следующую. Результаты пишут по индексу задачи.

#more
Гонки за индекс нет: между чтением и инкрементом нет `await`, а поток один. В проверке с лимитом 3 одновременно выполнялось ровно три задачи. Альтернатива — запускать следующую задачу в `.finally` завершившейся. Готовые решения — `p-limit` и подобные.
::

::question
Как сделать retry с экспоненциальной задержкой?

#answer
Рекурсивно или в цикле: попытаться, при ошибке подождать `delay`, уменьшить счётчик повторов и удвоить задержку. Когда повторы кончились — пробросить последнюю ошибку.

#more
Важно договориться о семантике: `retries = 3` — это три повтора, то есть четыре попытки, что в проверке и подтвердилось. В реальности добавляют jitter, ограничивают максимальную задержку и повторяют только идемпотентные операции и временные ошибки — например, 503, но не 400.
::

::question
Почему очередь задач может «застрять»?

#answer
Если ошибка задачи выходит из цикла обработки, флаг `running` остаётся `true`, и следующий `add` видит «уже выполняется» и ничего не запускает. Каждую задачу оборачивают в `try/catch`, а сброс флага — в `finally`.

#more
В проверке версия без обработки ошибок выдала необработанную ошибку, и задача после упавшей не выполнилась, а исправленная прошла все задачи по очереди и сохранила ошибку. Ошибки складывают в список или передают в колбэк — молча их глотать тоже плохо.
::

## Практика

::practice{title="Загрузка аватаров по тысяче за раз"}
Страница загружает аватары тысячи пользователей одновременно, и сервер начинает отвечать 429. Нужно ограничить загрузку пятью одновременными запросами, сохранив порядок результатов.

#solution
Пул из пяти воркеров, которые берут задачи из общего индекса:

```ts
async function mapLimit<T, U>(items: T[], limit: number, fn: (item: T) => Promise<U>): Promise<U[]> {
  const results: U[] = new Array(items.length);
  let index = 0;
  async function worker() {
    while (index < items.length) {
      const current = index++;
      results[current] = await fn(items[current]);
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
const avatars = await mapLimit(users, 5, (u) => loadAvatar(u.id));
```

В проверке с лимитом 3 одновременно выполнялось ровно три задачи, а результаты пришли в исходном порядке, хотя задачи завершались вперемешку. Ошибки обрабатывают внутри `fn` (например, подставляют аватар-заглушку), чтобы одна неудачная загрузка не отклонила весь результат, а для 429 добавляют `retry` с задержкой.
::

::practice{title="Сохранения перестали отправляться"}
Черновики сохраняются через последовательную очередь, чтобы запросы не обгоняли друг друга. После одного неудачного сохранения все следующие перестали уходить на сервер:

```ts
private async run() {
  if (this.running) return;
  this.running = true;
  while (this.queue.length) await this.queue.shift()!();
  this.running = false;
}
```

#solution
Ошибка задачи выходит из `while` через `await`, строка `this.running = false` не выполняется, и флаг навсегда остаётся `true` — каждый следующий `run` сразу выходит. В проверке задача после упавшей так и не выполнилась. Обрабатывают ошибку каждой задачи и сбрасывают флаг в `finally`:

```ts
private async run() {
  if (this.running) return;
  this.running = true;
  try {
    while (this.queue.length) {
      const task = this.queue.shift()!;
      try { await task(); } catch (e) { this.errors.push(e); }
    }
  } finally {
    this.running = false;
  }
}
```

С этим исправлением в проверке очередь выполнила все задачи по порядку, а ошибка попала в список. Для черновиков ошибку ещё показывают пользователю и повторяют сохранение — молча терять данные нельзя.
::
