# Реализация Promise

«Напиши свой Promise» проверяет всё сразу: состояния, микрозадачи, цепочки `then`, обработку ошибок и то, как промис «принимает» результат другого промиса. Здесь — реализация, которая проходит официальный набор тестов Promises/A+, от состояний до процедуры разрешения, плюс `catch`, `finally` и статические методы. Спрашивают, какие у промиса состояния, почему `then` асинхронный и как работают цепочки. Глубже — почему колбэк, вернувший промис, ломает наивную реализацию, что такое thenable и почему `finally` ждёт промис из своего колбэка.

::tldr
- **Три состояния, один переход:** `pending` → `fulfilled` или `rejected`, ровно один раз. Повторные `resolve` и `reject` игнорируются.
- **then возвращает новый промис:** его разрешает результат колбэка; ошибка в колбэке отклоняет его; отсутствующий обработчик передаёт исход дальше по цепочке.
- **Процедура разрешения — сердце реализации:** если колбэк вернул промис или любой thenable, новый промис принимает его состояние. В исходной версии текста дальше по цепочке уходила функция вместо значения.
- **Колбэки — всегда в микрозадаче:** даже у уже выполненного промиса. Тогда порядок «синхронный код → микрозадачи → макрозадачи» совпадает с нативным.
- **Проверено стандартом:** реализация из этой истории проходит все 872 теста `promises-aplus-tests`, а синхронный вызов колбэков роняет 22 из них.
::

## Состояния и ядро

Промис — объект с одним из трёх состояний: `pending` (ожидает), `fulfilled` (выполнен со значением) и `rejected` (отклонён с причиной). Переход возможен только из `pending` и только один раз.

```ts
type State = 'pending' | 'fulfilled' | 'rejected';
type Executor<T> = (resolve: (value: T | PromiseLike<T>) => void, reject: (reason?: unknown) => void) => void;

class MyPromise<T> {
  private state: State = 'pending';
  private value: any;
  private handlers: Array<() => void> = [];   // подписчики, ждущие завершения

  constructor(executor: Executor<T>) {
    let called = false;                       // учитывается только первый вызов
    const resolve = (value: T | PromiseLike<T>) => { if (!called) { called = true; this.resolveWith(value); } };
    const reject = (reason?: unknown) => { if (!called) { called = true; this.settle('rejected', reason); } };
    try {
      executor(resolve, reject);
    } catch (err) {
      reject(err);                            // ошибка в executor — reject
    }
  }

  private settle(state: State, value: unknown) {
    if (this.state !== 'pending') return;     // переход только один раз
    this.state = state;
    this.value = value;
    this.handlers.forEach((h) => h());        // будим подписчиков
    this.handlers = [];
  }
}
```

В проверке промис, у которого executor вызвал `resolve('первый')`, затем `resolve('второй')` и `reject(…)`, выполнился со значением `'первый'` — остальные вызовы проигнорированы. Флаг `called` в конструкторе нужен потому, что `resolve` может начать «принимать» другой промис: состояние ещё `pending`, а повторный вызов уже должен игнорироваться.

## then и цепочки

Самая сложная часть: `then` возвращает новый промис, и значение или ошибку надо правильно передать дальше. Колбэки вызываются асинхронно, в микрозадаче:

```ts
then(onFulfilled?, onRejected?) {
  return new MyPromise((resolve, reject) => {
    const run = () => queueMicrotask(() => {          // всегда асинхронно
      const cb = this.state === 'fulfilled' ? onFulfilled : onRejected;
      if (typeof cb !== 'function') {                 // нет обработчика — передать исход дальше
        return this.state === 'fulfilled' ? resolve(this.value) : reject(this.value);
      }
      try {
        resolve(cb(this.value));                      // результат — даже промис — разрешает следующий
      } catch (err) {
        reject(err);                                  // ошибка в колбэке — reject следующего
      }
    });
    if (this.state === 'pending') this.handlers.push(run); // ещё не готов — подписаться
    else run();                                            // уже готов — запланировать
  });
}
```

Три правила цепочки: результат колбэка разрешает следующий промис; брошенная ошибка его отклоняет; отсутствующий обработчик передаёт исход дальше. В проверке `reject → then без onRejected → catch` донёс ошибку до `catch`, а ошибка, брошенная в колбэке `then`, попала в следующий `catch`.

## Процедура разрешения

Что делать, если колбэк вернул промис? Следующий промис должен дождаться его и принять его состояние. Наивная версия этого не делает. В исходной версии текста функция `resolveValue` возвращала `value.then.bind(value)` — то есть функцию, — и дальше по цепочке уходила эта функция вместо значения, что проверка и показала.

Правильно — процедура разрешения из спецификации Promises/A+. Она «принимает» не только наш класс, а любой thenable — объект или функцию с методом `then`. Так наш промис работает с нативными и библиотечными:

```ts
private resolveWith(x: any) {
  if (x === this) return this.settle('rejected', new TypeError('Chaining cycle detected for promise'));
  if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
    let then: unknown;
    try { then = x.then; } catch (e) { return this.settle('rejected', e); } // геттер then может бросить
    if (typeof then === 'function') {
      let called = false;                             // thenable может вызвать оба колбэка — берём первый
      try {
        then.call(x,
          (y: unknown) => { if (!called) { called = true; this.resolveWith(y); } }, // рекурсивно
          (r: unknown) => { if (!called) { called = true; this.settle('rejected', r); } });
      } catch (e) {
        if (!called) { called = true; this.settle('rejected', e); }
      }
      return;
    }
  }
  this.settle('fulfilled', x);                        // обычное значение
}
```

Каждая строка закрывает конкретный тест спецификации:

- **цикл** — промис, разрешённый самим собой, отклоняется с `TypeError`. В проверке `then`, вернувший свой же промис, дал именно его;
- **`then` читается один раз** и может бросить — при чтении через геттер;
- **thenable может вызвать колбэки несколько раз или оба** — учитывается первый вызов;
- **принятие рекурсивное** — thenable может разрешиться другим thenable.

В проверке цепочка `1 → +1 → промис с ×10 через setTimeout` дала 20: следующий `then` дождался возвращённого промиса. Нативный `Promise.all` принял наш промис как thenable, а наш `MyPromise.resolve` — нативный.

## Почему микрозадача

`queueMicrotask` ставит колбэк в очередь микрозадач: она выполняется после текущего синхронного кода, но до макрозадач вроде `setTimeout`. Колбэк `then` выполняется так даже у уже выполненного промиса — это требование спецификации, иначе порядок зависел бы от того, успел ли промис завершиться.

В проверке синхронный код, наш `then`, нативный `then` и `setTimeout(0)` выполнились в порядке `sync`, `MyPromise.then`, `Promise.then`, `setTimeout` — как и должно быть: обе реализации используют одну очередь микрозадач. Если планировать колбэки через `setTimeout`, они окажутся в очереди макрозадач и выполнятся после ранее запланированных таймеров, а не до них. Самая частая ошибка — вызывать колбэк синхронно: в проверке такая версия провалила 22 теста Promises/A+. Устройство очередей — в [event loop](/content/javascript/event-loop).

## catch, finally и статические методы

`catch` и `finally` — сахар над `then`:

```ts
catch(onRejected) {
  return this.then(undefined, onRejected);
}

finally(onFinally) {
  return this.then(
    (value) => MyPromise.resolve(onFinally()).then(() => value),             // ждём, отдаём исходное значение
    (reason) => MyPromise.resolve(onFinally()).then(() => { throw reason; }), // и исходную ошибку
  );
}

static resolve(value) {
  return value instanceof MyPromise ? value : new MyPromise((res) => res(value));
}
static reject(reason) {
  return new MyPromise((_, rej) => rej(reason));
}
```

Тонкость `finally`: если колбэк вернул промис, нативный `finally` дожидается его, но не меняет исход. Версия, которая просто вызывает `onFinally()` и возвращает значение, этого не делает. В проверке значение пришло только после завершения асинхронной очистки — как и у нативного `finally`, — а исходная ошибка дошла до `catch`, хотя колбэк `finally` вернул строку. Комбинаторы вроде `all` строятся поверх, как в [промисах и асинхронности](/content/common-coding-questions/promises-async).

## Проверка стандартом

Спецификация Promises/A+ поставляется с набором тестов `promises-aplus-tests`. Ему дают адаптер — как создать выполненный, отклонённый и отложенный промис:

```ts
const adapter = {
  resolved: (v) => MyPromise.resolve(v),
  rejected: (r) => MyPromise.reject(r),
  deferred: () => {
    let resolve, reject;
    const promise = new MyPromise((res, rej) => { resolve = res; reject = rej; });
    return { promise, resolve, reject };
  },
};
require('promises-aplus-tests')(adapter, (err) => { /* err.failures — число провалов */ });
```

Реализация из этой истории прошла все 872 теста. На интервью полную процедуру разрешения пишут редко, но знать, что она есть и что проверяет, — сильный сигнал.

## Красные флаги в ответе

- Колбэк `then` вызывается синхронно для уже выполненного промиса.
- `then` не возвращает новый промис или возвращает тот же.
- Колбэк вернул промис — а следующий `then` получает сам промис или функцию вместо значения.
- Нет защиты от повторного `resolve`/`reject`.
- Ошибка в колбэке не отклоняет следующий промис, а теряется.
- `setTimeout` вместо микрозадачи «потому что так проще».
- `finally`, который меняет значение или не ждёт промис из колбэка.

## Как спрашивают на собеседовании

::question
Какие состояния у промиса и какие переходы возможны?

#answer
`pending`, `fulfilled` и `rejected`. Переход возможен только из `pending` и ровно один раз — в `fulfilled` со значением или в `rejected` с причиной. После этого состояние и значение не меняются.

#more
В проверке повторные `resolve` и `reject` после первого игнорировались. В реализации нужен ещё флаг на уровне executor: пока промис «принимает» другой промис, состояние остаётся `pending`, но новые вызовы `resolve` уже должны игнорироваться.
::

::question
Почему колбэк then вызывается асинхронно?

#answer
Спецификация требует вызывать колбэки `then` в микрозадаче — даже у уже выполненного промиса. Тогда порядок предсказуем: сначала весь синхронный код, потом колбэки, и он не зависит от того, успел ли промис завершиться к моменту подписки. Реализуется через `queueMicrotask`.

#more
В проверке синхронный вызов колбэков провалил 22 теста Promises/A+. Порядок с нативными промисами совпал: обе реализации ставят колбэки в одну очередь микрозадач, которая выполняется раньше `setTimeout`.
::

::question
Что возвращает then и как работают цепочки?

#answer
`then` возвращает новый промис. Значение, которое вернул колбэк, разрешает его; если колбэк вернул промис или thenable — новый промис дожидается его и принимает его состояние; если колбэк бросил — новый промис отклоняется. Без обработчика исход передаётся дальше.

#more
«Принятие» состояния — процедура разрешения из спецификации, и это самая частая ошибка самописных реализаций: в исходной версии текста дальше уходила функция вместо значения. Процедура также защищает от цикла (промис, разрешённый сам собой, отклоняется с `TypeError`).
::

::question
Что такое thenable и зачем его поддерживать?

#answer
Любой объект или функция с методом `then`. Процедура разрешения принимает состояние любого thenable, а не только экземпляров своего класса. Благодаря этому промисы разных реализаций совместимы: `await`, нативный `Promise.all` и библиотеки понимают друг друга.

#more
В проверке нативный `Promise.all` принял наш промис, а наш `resolve` — нативный. Тонкости из спецификации: `then` читается один раз и может бросить, thenable может вызвать оба колбэка — учитывается первый, а принятие рекурсивное.
::

::question
Как реализованы catch и finally?

#answer
`catch(fn)` — это `then(undefined, fn)`. `finally(fn)` — `then` с двумя обработчиками, которые вызывают `fn` и передают дальше исходное значение или исходную ошибку, не меняя их.

#more
Если колбэк `finally` вернул промис, нативный `finally` ждёт его, поэтому в реализации результат `fn()` оборачивают в `MyPromise.resolve(...)` и продолжают после него. В проверке значение пришло только после асинхронной очистки, а ошибка дошла до `catch`, хотя колбэк вернул строку.
::

::question
Микрозадача или setTimeout для then?

#answer
Микрозадача — `queueMicrotask` или очередь промисов. `setTimeout` — макрозадача: она выполнится позже всех микрозадач и позже ранее запланированных таймеров, поэтому порядок относительно других промисов будет неверным.

#more
В проверке колбэк, запланированный через `setTimeout`, выполнился после чужого `setTimeout`, а нативный `then` — раньше обоих. Старые полифилы использовали `setTimeout` или `MutationObserver` за неимением `queueMicrotask` — последний как раз даёт микрозадачу.
::

## Практика

::practice{title="Цепочка отдаёт функцию вместо данных"}
Самописный промис работает с обычными значениями, но если колбэк `then` возвращает другой промис, следующий `then` получает функцию:

```ts
resolve(this.resolveValue(onFulfilled(this.value)));
// …
private resolveValue(value) {
  if (value instanceof MyPromise) return value.then.bind(value);
  return value;
}
```

#solution
`resolveValue` возвращает связанную функцию `then`, и `resolve` выполняет следующий промис с этой функцией как значением — в проверке дальше ушла именно функция. Нужно не передавать thenable как значение, а принять его состояние — подписаться на него и разрешить следующий промис его результатом:

```ts
private resolveWith(x) {
  if (x === this) return this.settle('rejected', new TypeError('Chaining cycle detected for promise'));
  if (x !== null && (typeof x === 'object' || typeof x === 'function')) {
    let then;
    try { then = x.then; } catch (e) { return this.settle('rejected', e); }
    if (typeof then === 'function') {
      let called = false;
      try {
        then.call(x,
          (y) => { if (!called) { called = true; this.resolveWith(y); } },
          (r) => { if (!called) { called = true; this.settle('rejected', r); } });
      } catch (e) { if (!called) { called = true; this.settle('rejected', e); } }
      return;
    }
  }
  this.settle('fulfilled', x);
}
```

Конструктор и `then` вызывают `resolveWith`, а не `settle` напрямую. В проверке цепочка с промисом внутри дала 20, а реализация прошла все 872 теста Promises/A+.
::

::practice{title="Порядок вывода отличается от нативного"}
Своя реализация выводит строки не в том порядке, что нативный `Promise`:

```ts
const p = new MyPromise((res) => res(1));
p.then(() => console.log('then'));
console.log('sync');
// своя реализация: then, sync — нативный: sync, then
```

#solution
Колбэк вызывается синхронно, если промис уже выполнен к моменту подписки. Спецификация требует асинхронного вызова — в микрозадаче — всегда:

```ts
const run = () => queueMicrotask(() => {
  // …вызов колбэка
});
if (this.state === 'pending') this.handlers.push(run);
else run();
```

В проверке после этого порядок стал `sync`, `MyPromise.then`, `Promise.then`, `setTimeout` — как у нативного. `setTimeout` вместо `queueMicrotask` тоже даст «sync, then», но колбэк окажется в очереди макрозадач и выполнится после уже запланированных таймеров и после всех нативных промисов. Синхронный вызов роняет 22 теста Promises/A+.
::
