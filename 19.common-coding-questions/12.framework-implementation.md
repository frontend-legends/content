# Реализация фреймворка

Раунд уровня «реализуй кусок React или Vue»: сигнал, `ref`, хук, портал, мини-VDOM или крошечный фреймворк целиком. Проверяют, понимаешь ли ты, как реактивность и рендеринг устроены под капотом, а не только используешь API. Здесь — сигналы с эффектами и вычисляемыми значениями, реактивность в стиле Vue на `Proxy`, `useState` и `useEffect` с нуля, кастомные хуки, порталы, мини-VDOM с `patch` и всё это вместе. Спрашивают, как сигнал узнаёт подписчиков, зачем `.value` в `ref` и почему хуки нельзя вызывать условно. Глубже — почему вложенный эффект ломает внешний, откуда глитч на «ромбе» зависимостей и почему замена DOM целиком теряет фокус.

::tldr
- **Сигнал подписывает того, кто читает:** глобальный «текущий читатель», чтение добавляет его в подписчики, запись будит их. В проверке исходная версия теряла внешний эффект, если внутри создавался вложенный, — текущего читателя держат стеком.
- **Две фазы обновления убирают глитч:** сначала пометить зависимых, потом выполнить эффекты, а `computed` пересчитывать лениво. В проверке исходный вариант показал промежуточное `4+3`, исправленный — только `4+6`, как Preact Signals.
- **Vue — тот же трекинг на `Proxy`:** перехват чтения и записи, глубина лениво, запись того же значения не уведомляет. В проверке поведение совпало с `@vue/reactivity`. `.value` у `ref` — потому что примитив нельзя проксировать.
- **Хуки — слоты по порядку вызова:** условный вызов сдвигает слоты. В проверке мини-версия отдала одному хуку состояние другого, а настоящий React упал с «Rendered fewer hooks than expected».
- **VDOM — сравнить деревья и применить разницу:** `patch` обновляет атрибуты и слушатели, удаляет лишних детей с конца и сохраняет узлы. В проверке замена DOM целиком потеряла фокус в поле ввода, `patch` — нет.
::

## Сигналы

Сигнал — значение, которое само отслеживает, кто его читает, и уведомляет читателей при изменении. Модель Solid, Preact Signals и Angular Signals. Что это даёт и чем отличается от перерисовки компонента — в [сигналах и реактивности](/content/modern-dev/signals-and-reactivity); здесь — как это написать.

### Наивная версия и её ошибки

Популярная реализация в тридцать строк держит один глобальный `currentEffect`, который эффект ставит перед запуском и обнуляет после. В проверке у неё нашлись две проблемы:

- **вложенный эффект ломает внешний.** Внутренний эффект в `finally` ставит `currentEffect = null`, и чтения внешнего эффекта после него уже никого не подписывают. В проверке внешний эффект, создавший внутренний, после изменения своего сигнала не перезапустился;
- **глитч на «ромбе».** `computed`, сделанный как эффект, пишущий в сигнал, пересчитывается сразу. Когда от одного сигнала зависят два вычисления, а эффект читает оба, эффект запускается между их пересчётами. В проверке для `x → 2·x` и `x → 3·x` эффект увидел `2+3`, потом несогласованное `4+3` и только потом `4+6`.

### Исправленная версия

Три изменения: стек текущего читателя, сбор зависимостей заново на каждом запуске и две фазы обновления — сначала пометить, потом выполнить:

```ts
type Reaction = { notify: () => void; deps: Set<Set<Reaction>> };
let current: Reaction | null = null;                     // кто сейчас читает
const queue = new Set<Reaction & { run: () => void }>();
let flushing = false;
function flush() {
  if (flushing) return;
  flushing = true;
  try { while (queue.size) { const [e] = queue; queue.delete(e); e.run(); } } finally { flushing = false; }
}
const track = (subs: Set<Reaction>) => { if (current) { subs.add(current); current.deps.add(subs); } };
const untrackAll = (r: Reaction) => { for (const dep of r.deps) dep.delete(r); r.deps.clear(); };

function signal<T>(initial: T) {
  let value = initial;
  const subs = new Set<Reaction>();
  const read = () => { track(subs); return value; };
  const write = (next: T) => {
    if (Object.is(next, value)) return;
    value = next;
    for (const r of [...subs]) r.notify();               // фаза 1: пометить зависимых
    flush();                                               // фаза 2: выполнить эффекты
  };
  return [read, write] as const;
}

function effect(fn: () => void) {
  const e = {
    deps: new Set<Set<Reaction>>(),
    notify: () => { queue.add(e); },                       // не бежит сразу — встаёт в очередь
    run: () => {
      untrackAll(e);                                       // зависимости собираются заново
      const prev = current; current = e;                   // стек: вложенный не сбрасывает внешний
      try { fn(); } finally { current = prev; }
    },
  };
  e.run();
  return () => untrackAll(e);                              // dispose
}

function computed<T>(fn: () => T) {
  let value: T;
  let dirty = true;
  const subs = new Set<Reaction>();
  const self: Reaction = {
    deps: new Set(),
    notify: () => { if (!dirty) { dirty = true; for (const r of [...subs]) r.notify(); } }, // пометить, не считать
  };
  return () => {
    track(subs);
    if (dirty) {                                           // ленивый пересчёт при чтении
      untrackAll(self);
      const prev = current; current = self;
      try { value = fn(); } finally { current = prev; }
      dirty = false;
    }
    return value;
  };
}
```

Запись сначала проходит по графу и только помечает: эффекты встают в очередь, вычисляемые значения становятся «грязными». Потом очередь выполняется, и каждый эффект, читая `computed`, получает уже согласованный пересчёт. В проверке:

- внешний эффект с вложенным перезапустился, как и должен;
- «ромб» дал `['2+3', '4+6']` — ровно то же, что `@preact/signals-core` на том же сценарии;
- эффект `flag() ? a() : b()` после переключения ветки перестал реагировать на `a` — старые зависимости снимаются перед каждым запуском, — а после `dispose` замолчал совсем;
- запись `NaN` поверх `NaN` эффект не перезапустила — сравнение через `Object.is`.

Это и есть точечная реактивность: перезапускается только тот код, что реально читал изменившееся значение.

## Реактивность Vue

Vue 3 отслеживает зависимости так же, но через `Proxy`: перехват чтения — `track`, перехват записи — `trigger`. Механика в самом Vue — в [продвинутой реактивности](/content/vuejs/reactivity-advanced).

```ts
let activeEffect: (() => void) | null = null;
const targetMap = new WeakMap<object, Map<PropertyKey, Set<() => void>>>();
const proxies = new WeakMap<object, object>();

function track(target: object, key: PropertyKey) {
  if (!activeEffect) return;
  let deps = targetMap.get(target);
  if (!deps) targetMap.set(target, (deps = new Map()));
  let dep = deps.get(key);
  if (!dep) deps.set(key, (dep = new Set()));
  dep.add(activeEffect);                                  // target.key → эффект
}
function trigger(target: object, key: PropertyKey) {
  const dep = targetMap.get(target)?.get(key);
  if (dep) for (const fn of [...dep]) fn();
}
function reactive<T extends object>(obj: T): T {
  const existing = proxies.get(obj);
  if (existing) return existing as T;                     // один прокси на объект
  const proxy = new Proxy(obj, {
    get(target, key, receiver) {
      track(target, key);
      const value = Reflect.get(target, key, receiver);
      return value !== null && typeof value === 'object' ? reactive(value) : value; // глубина — лениво
    },
    set(target, key, value, receiver) {
      const old = Reflect.get(target, key, receiver);
      const result = Reflect.set(target, key, value, receiver);
      if (!Object.is(old, value)) trigger(target, key);   // то же значение — без уведомления
      return result;
    },
  });
  proxies.set(obj, proxy);
  return proxy;
}
function watchEffect(fn: () => void) {
  const run = () => { const prev = activeEffect; activeEffect = run; try { fn(); } finally { activeEffect = prev; } };
  run();
}
```

Две детали отличают её от наивной: вложенные объекты оборачиваются при чтении — иначе `state.user.name = …` никого не уведомит, — а запись того же значения не будит эффекты. В проверке один и тот же сценарий — изменить вложенное поле, записать то же число, записать новое — дал на нашей версии и на `@vue/reactivity` одинаковое `['Анна:1', 'Борис:1', 'Борис:2']`. Одно расхождение стоит назвать: настоящий Vue перехватывает ещё `ownKeys`, `has` и удаление, поэтому эффект, перебиравший ключи, перезапускается при добавлении нового ключа. В проверке Vue перезапустил такой эффект, наша версия — нет.

### Зачем ref и .value

Примитив нельзя обернуть в `Proxy` — в проверке `new Proxy(0, {})` бросил `TypeError`, — а передаётся он по значению. Поэтому `ref` хранит значение в объекте и перехватывает доступ к его свойству `value`:

```ts
class RefImpl<T> {
  private _value: T;
  private dep = new Set<() => void>();
  constructor(value: T) { this._value = value; }
  get value() { if (activeEffect) this.dep.add(activeEffect); return this._value; }
  set value(next: T) { if (Object.is(next, this._value)) return; this._value = next; for (const fn of [...this.dep]) fn(); }
}
const ref = <T,>(value: T) => new RefImpl(value);
```

В проверке эффект увидел 0, затем 1, а повторная запись 1 его не потревожила.

| | Сигналы | Vue 3 | React |
| --- | --- | --- | --- |
| Что отслеживает | вызов геттера | доступ к свойствам через `Proxy` | ничего — перерисовка по `setState` |
| Гранулярность | эффект, вплоть до узла DOM | эффект или компонент | компонент целиком |
| Цена | подписки | `Proxy` на каждый доступ | сравнение деревьев |

## useState с нуля

`useState` с нуля объясняет, почему хуки нельзя вызывать условно: состояние хранится в массиве по порядковому номеру вызова. Как это устроено в настоящем React — в [механике хуков](/content/reactjs/hooks-mechanics).

```ts
function createHooksRuntime(Component: () => unknown) {
  const hooks: unknown[] = [];
  let index = 0;
  let pendingEffects: (() => void)[] = [];
  const runtime = {
    output: undefined as unknown,
    useState<T>(initial: T): [T, (next: T | ((prev: T) => T)) => void] {
      const i = index++;                                 // слот по порядку вызова
      if (!(i in hooks)) hooks[i] = initial;             // слот занят — даже если в нём null
      const setState = (next: T | ((prev: T) => T)) => {
        hooks[i] = typeof next === 'function' ? (next as (p: T) => T)(hooks[i] as T) : next;
        runtime.render();
      };
      return [hooks[i] as T, setState];
    },
    useEffect(fn: () => void | (() => void), deps: unknown[]) {
      const i = index++;
      const prev = hooks[i] as { deps: unknown[]; cleanup?: void | (() => void) } | undefined;
      const changed = !prev || deps.some((d, j) => !Object.is(d, prev.deps[j]));
      if (changed) pendingEffects.push(() => { prev?.cleanup?.(); hooks[i] = { deps, cleanup: fn() }; });
    },
    render() {
      index = 0;                                          // сброс номера перед каждым рендером
      runtime.output = Component();
      const effects = pendingEffects; pendingEffects = [];
      effects.forEach((run) => run());                   // эффекты — после рендера
    },
  };
  return runtime;
}
```

Тонкости, которые в проверке отличили рабочую версию от популярной:

- **занятость слота — по наличию, а не по значению.** Версия с `hooks[i] = hooks[i] ?? initial` после `setState(null)` на следующем рендере вернула начальное значение, а не `null`;
- **функциональное обновление.** Два вызова `setN((p) => p + 1)` подряд дали 2;
- **эффект — после рендера, очистка — перед следующим запуском.** Порядок в проверке: `рендер 0`, `эффект 0`, `рендер 1`, `очистка 0`, `эффект 1` и так далее.

### Почему хуки нельзя вызывать в условии

Условный вызов меняет число хуков между рендерами, и номера слотов сдвигаются. В проверке компонент с условным `useState('привет')` перед `useState('Москва')` после отключения условия показал `'—, привет'`: второй хук прочитал слот первого. Настоящий React такое ловит: в проверке он упал с ошибкой «Rendered fewer hooks than expected».

## Кастомные хуки

Частая разминка перед «реализуй useState» — прикладной хук:

```ts
function useDebounce<T>(value: T, delay = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

function usePrevious<T>(value: T): T | undefined {
  const ref = useRef<T | undefined>(undefined);   // в типах React 19 аргумент обязателен
  useEffect(() => { ref.current = value; }, [value]);
  return ref.current;                              // эффект обновит ref уже после рендера
}
```

В проверке на React 19 `useDebounce` при вводе «ч», «ча», «чай» за 299 мс ещё возвращал «ч», а через 300 мс — «чай». `usePrevious` вернул `undefined`, затем 1, затем 2 — значение прошлого рендера. В типах React 19 `useRef<T>()` без аргумента — ошибка TypeScript, поэтому начальное значение передают явно.

## Порталы

`createPortal` в React и `Teleport` во Vue рендерят содержимое в другой узел DOM — обычно `body`, — оставляя его на своём месте в дереве компонентов. Нужно для модалок, подсказок и уведомлений, чтобы вырваться из `overflow: hidden` и контекста наложения родителя.

```ts
function portal(content: HTMLElement, target: HTMLElement = document.body) {
  target.appendChild(content);                    // физически — в target
  return () => target.removeChild(content);       // cleanup
}
```

Ванильная версия переносит только узел. Особенность React — логическое место сохраняется. В проверке кнопка в портале физически лежала в `body`, но прочитала контекст `'тёмная'` от провайдера своего родителя. Клик по ней сработал в `onClick` родительского `div` — событие React всплыло по дереву компонентов, — а обычный DOM-слушатель на том же `div` клика не увидел: в DOM кнопка не его потомок.

## Мини-VDOM

Виртуальный DOM — JavaScript-описание интерфейса `{ type, props, children }`, которое рендерится в настоящий DOM, а при обновлении сравнивается со старым деревом. Как это делает React — в [согласовании и Fiber](/content/reactjs/reconciliation-and-fiber).

### Атрибуты и слушатели

Популярный `render` ставит любой проп через `setAttribute` — и в проверке `disabled: false` сделал кнопку неактивной: атрибут `disabled="false"` всё равно атрибут. Пропы разбирают по видам:

```ts
function setProp(el: HTMLElement, key: string, value: any, old?: any) {
  if (key.startsWith('on')) {
    const name = key.slice(2).toLowerCase();       // onClick → click
    if (old) el.removeEventListener(name, old);
    if (value) el.addEventListener(name, value);
  } else if (key === 'value' || key === 'checked') (el as any)[key] = value; // свойство, а не атрибут
  else if (value === false || value == null) el.removeAttribute(key);        // false — нет атрибута
  else el.setAttribute(key, value === true ? '' : String(value));
}

function renderVNode(vnode: VNode | string): Node {
  if (typeof vnode === 'string') return document.createTextNode(vnode);
  const el = document.createElement(vnode.type);
  for (const [key, value] of Object.entries(vnode.props)) setProp(el, key, value);
  vnode.children.forEach((child) => el.appendChild(renderVNode(child)));
  return el;
}
```

### patch

Наивный `patch` из популярных разборов в проверке ошибся дважды: при том же теге он не обновлял атрибуты (`class` остался `a`), а при удалении нескольких детей упал — после удаления первого лишнего узла индексы сдвинулись, и `removeChild` получил `undefined`. Исправленная версия обновляет пропы и удаляет лишних детей с конца:

```ts
function patch(parent: Node, oldV: VNode | string | undefined, newV: VNode | string | undefined, index = 0) {
  const existing = parent.childNodes[index];
  if (oldV === undefined) { parent.appendChild(renderVNode(newV!)); return; }
  if (newV === undefined) { parent.removeChild(existing); return; }
  if (changed(oldV, newV)) { parent.replaceChild(renderVNode(newV), existing); return; }
  if (typeof newV === 'string') return;
  const o = oldV as VNode, el = existing as HTMLElement;
  for (const key of new Set([...Object.keys(o.props), ...Object.keys(newV.props)])) {
    if (o.props[key] !== newV.props[key]) setProp(el, key, newV.props[key], o.props[key]); // атрибуты и слушатели
  }
  const common = Math.min(o.children.length, newV.children.length);
  for (let i = 0; i < common; i++) patch(el, o.children[i], newV.children[i], i);
  for (let i = common; i < newV.children.length; i++) patch(el, undefined, newV.children[i], i);
  for (let i = o.children.length - 1; i >= newV.children.length; i--) patch(el, o.children[i], undefined, i); // с конца
}
const changed = (a: VNode | string, b: VNode | string) =>
  typeof a !== typeof b || (typeof a === 'string' && a !== b) || (typeof a !== 'string' && a.type !== (b as VNode).type);
```

В проверке `patch` обновил `class`, удалил два лишних пункта без ошибки, переключил `disabled`, снял старый обработчик клика и поставил новый, а при смене только текста оставил тот же DOM-узел `<li>`. Чего здесь нет — ключей: без них элементы списка сопоставляются по позиции, и перестановка пересоздаёт узлы. Настоящие реализации сопоставляют детей по `key`.

## Мини-фреймворк

Финальный вопрос — связать сигналы и рендер. `mount` оборачивает рендер в эффект: компонент читает сигнал — эффект подписывается, сигнал меняется — эффект перерисовывает:

```ts
function mount(component: () => VNode, container: HTMLElement) {
  let prev: VNode | undefined;
  effect(() => {
    const next = component();
    patch(container, prev, next);   // применяем разницу, а не заменяем DOM
    prev = next;
  });
}
const [text, setText] = signal('');
mount(() => h('div', null,
  h('input', { value: text(), onInput: (e) => setText(e.target.value) }),
  h('p', null, `символов: ${text().length}`),
), document.getElementById('app')!);
```

Почему `patch`, а не замена DOM: в проверке вариант, который на каждое изменение очищал контейнер и вставлял новое дерево, обновил счётчик, но потерял фокус в поле ввода — поле было пересоздано, и печатать дальше пришлось бы, снова кликнув в него. С `patch` поле осталось тем же узлом, и фокус остался на месте. Ровно эту задачу и решают VDOM или точечные привязки сигналов к узлам.

## Красные флаги в ответе

- Один глобальный «текущий эффект» без стека — вложенные эффекты ломают внешние.
- Зависимости не пересобираются — эффект реагирует на ветку, которую больше не читает.
- `computed` как эффект, пишущий в сигнал, без оговорки про глитчи.
- `reactive` без глубины и с уведомлением на запись того же значения.
- `hooks[i] ?? initial` — `null` в состоянии сбрасывается в начальное.
- `useEffect`, который запускает эффект прямо во время рендера и без очистки.
- `setAttribute` для `false`, `value` и `checked`; `patch`, не обновляющий атрибуты.

Как сигнал узнаёт своих подписчиков?

#answer
Через глобальный «текущий читатель»: эффект перед запуском помечает себя активным, и каждое чтение сигнала добавляет активного читателя в свои подписчики. Запись перебирает подписчиков и будит их. Подписка происходит сама в момент чтения — это и называют отслеживанием зависимостей.

#more
Читателя держат стеком (сохраняют предыдущего и восстанавливают после), иначе вложенный эффект сбросит внешний — в проверке так и случилось. Зависимости собирают заново на каждом запуске, чтобы эффект с условием не реагировал на ветку, которую больше не читает.
::

::question
Откуда глитч на «ромбе» зависимостей и как его убрать?

#answer
Если вычисляемые значения пересчитываются сразу при изменении источника, эффект, читающий два из них, запускается между их пересчётами и видит несогласованную пару. Убирают двумя фазами: сначала пометить всех зависимых, потом выполнить эффекты, а вычисляемые значения пересчитывать лениво при чтении.

#more
В проверке наивная версия выдала промежуточное `4+3`, исправленная — только `4+6`, как Preact Signals. Подробно о глитчах и о том, как библиотеки их избегают, — в сигналах и реактивности. Тот же принцип у планировщиков фреймворков: изменения собираются, а применяются пачкой.
::

::question
Почему у ref во Vue нужен .value, а у reactive — нет?

#answer
`reactive` оборачивает объект в `Proxy` и перехватывает доступ к его свойствам. Примитив в `Proxy` не обернуть — он передаётся по значению, — поэтому `ref` хранит значение в объекте и перехватывает доступ к свойству `value`.

#more
В проверке `new Proxy(0, {})` бросил `TypeError`. В шаблонах Vue `.value` разворачивается автоматически, а в JavaScript — нет. `reactive` к тому же глубокий: вложенные объекты оборачиваются лениво при чтении — в проверке изменение `state.user.name` перезапустило эффект так же, как в `@vue/reactivity`.
::

::question
Почему хуки нельзя вызывать условно?

#answer
Состояние хуков хранится по порядковому номеру вызова, а не по имени. Условный вызов меняет число хуков между рендерами, номера сдвигаются, и хук получает состояние соседа. Поэтому порядок и число хуков должны быть одинаковыми на каждом рендере.

#more
В проверке мини-версия после отключения условия отдала второму хуку состояние первого. Настоящий React замечает изменение числа хуков и падает с ошибкой «Rendered fewer hooks than expected» — линтер `react-hooks` ловит это ещё до запуска.
::

::question
Чем сигналы отличаются от состояния React?

#answer
Сигналы точечны: при изменении перезапускается только код, читавший этот сигнал, вплоть до привязки к конкретному узлу DOM, без сравнения деревьев. React по `setState` перерисовывает компонент целиком и сравнивает результат с прошлым деревом.

#more
Цена у каждого своя: сигналам нужны подписки и граф зависимостей, React — сравнение деревьев и мемоизация, чтобы не перерисовывать лишнее. React Compiler сокращает разрыв, автоматически мемоизируя компоненты, но модель остаётся «перерисовать и сравнить».
::

::question
Как работает портал?

#answer
Содержимое физически вставляется в другой узел DOM, обычно `body`, но логически остаётся в дереве компонентов: контекст доступен, а события React всплывают по дереву компонентов. Нужно, чтобы модалка или подсказка вырвалась из `overflow: hidden` и `z-index` родителя.

#more
В проверке кнопка в портале лежала в `body`, но прочитала контекст родителя, а её клик дошёл до `onClick` родительского `div` — при том что DOM-слушатель на этом `div` клика не увидел. Это стоит помнить: стоп всплытия и «клик вне элемента» в порталах ведут себя по дереву React.
::

::question
Что такое согласование и зачем ключи?

#answer
Согласование — сравнение нового виртуального дерева со старым и применение к настоящему DOM только различий: обновить атрибуты, заменить узел при смене типа, добавить или удалить детей. Ключи помогают сопоставить элементы списка между рендерами, чтобы переиспользовать узлы, а не пересоздавать, и не терять их состояние и фокус.

#more
В проверке `patch` сохранил тот же узел при смене текста и не потерял фокус в поле, а замена DOM целиком — потеряла. Без ключей детей сопоставляют по позиции, и вставка в начало списка пересоздаёт все узлы. Удалять лишних детей нужно с конца, иначе сдвигаются индексы.
::

## Практика

::practice{title="Внешний эффект перестал реагировать"}
В самописной реактивности эффект, который внутри создаёт другой эффект, перестаёт реагировать на собственные сигналы:

```ts
function effect(fn) {
  const run = () => { currentEffect = run; try { fn(); } finally { currentEffect = null; } };
  run();
}
effect(() => { effect(() => b()); a(); }); // изменение a не перезапускает внешний
```

#solution
Вложенный эффект в `finally` обнуляет `currentEffect`, и чтение `a()` во внешнем эффекте после него уже никого не подписывает. В проверке внешний эффект после изменения `a` не перезапустился. Текущего читателя держат стеком — сохраняют предыдущего и восстанавливают:

```ts
function effect(fn) {
  const e = {
    deps: new Set(),
    run: () => {
      for (const dep of e.deps) dep.delete(e); e.deps.clear(); // заодно пересобираем зависимости
      const prev = current; current = e;
      try { fn(); } finally { current = prev; }
    },
  };
  e.run();
  return () => { for (const dep of e.deps) dep.delete(e); e.deps.clear(); };
}
```

С этим исправлением внешний эффект перезапустился, а сбор зависимостей заново на каждом запуске убрал вторую ошибку — реакцию на ветку условия, которую эффект больше не читает.
::

::practice{title="Список не обновляется и падает при удалении"}
Самописный `patch` для мини-VDOM меняет текст, но не меняет классы, а при уменьшении списка падает с `parameter 1 is not of type 'Node'`:

```ts
else if (newV.type) {
  const max = Math.max(oldV.children.length, newV.children.length);
  for (let i = 0; i < max; i++) patch(existing, oldV.children[i], newV.children[i], i);
}
```

#solution
Две ошибки. При том же теге пропы не сравниваются, поэтому атрибуты и слушатели остаются старыми. А удаление идёт вперёд по индексам: после удаления первого лишнего узла остальные сдвигаются, и `childNodes[i]` для следующего уже `undefined`. В проверке именно так `patch` и упал. Сравнивают пропы и удаляют с конца:

```ts
for (const key of new Set([...Object.keys(o.props), ...Object.keys(newV.props)])) {
  if (o.props[key] !== newV.props[key]) setProp(el, key, newV.props[key], o.props[key]);
}
const common = Math.min(o.children.length, newV.children.length);
for (let i = 0; i < common; i++) patch(el, o.children[i], newV.children[i], i);
for (let i = common; i < newV.children.length; i++) patch(el, undefined, newV.children[i], i);
for (let i = o.children.length - 1; i >= newV.children.length; i--) patch(el, o.children[i], undefined, i);
```

В проверке после этого `class` обновился, лишние пункты удалились без ошибки, старый обработчик клика снялся, а новый сработал. `setProp` при этом снимает прежний слушатель, прежде чем повесить новый, — иначе на каждом обновлении их становилось бы больше.
::
