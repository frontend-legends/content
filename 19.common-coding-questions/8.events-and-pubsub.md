# События и pub/sub

`EventEmitter`, шина событий, observable и мини-стор — всё это паттерн «издатель и подписчик», на котором стоят Node.js, события DOM, стейт-менеджеры и реактивность. Задача проверяет работу с коллекциями колбэков, отпиской и порядком вызова. Спрашивают, как реализовать `once`, почему при `emit` копируют список слушателей и как устроен Redux. Глубже — почему `once`, отписывающийся после вызова, уходит в рекурсию, почему `off` не находит once-слушателя и чем `Set` слушателей отличается от поведения Node.

::tldr
- **Хранилище — `Map` событий на `Set` слушателей:** удаление за O(1). `Set` отсекает повторную подписку той же функции — как `EventTarget`, но не как `node:events`, где дубль вызывается дважды.
- **emit работает по снимку:** слушатели, снятые или добавленные во время `emit`, не влияют на текущий вызов. В проверке поведение совпало с `node:events` на одном и том же сценарии.
- **once отписывается до вызова и помнит оригинал:** иначе повторный `emit` внутри обработчика уходит в рекурсию (в проверке «одноразовый» обработчик сработал 50 раз), а `off(original)` не находит обёртку.
- **Pub/sub возвращает функцию отписки:** её удобно вернуть из `useEffect`. Observable сразу отдаёт текущее значение и не уведомляет, если значение не изменилось по `Object.is`.
- **Ядро Redux — pub/sub поверх состояния:** в проверке мини-стор повёл себя как настоящий Redux: снимок подписчиков, запрет `dispatch` из редьюсера, `dispatch` возвращает action.
::

## EventEmitter

`EventEmitter` — объект, на события которого подписываются (`on`), отписываются (`off`) и которые генерируют (`emit`). Сердце Node.js и многих библиотек.

```ts
type Listener = ((...args: any[]) => void) & { listener?: Listener };

class EventEmitter {
  private events = new Map<string, Set<Listener>>();

  on(event: string, listener: Listener): this {
    if (!this.events.has(event)) this.events.set(event, new Set());
    this.events.get(event)!.add(listener);
    return this;                                          // чейнинг
  }

  off(event: string, listener: Listener): this {
    const set = this.events.get(event);
    if (!set) return this;
    for (const l of set) if (l === listener || l.listener === listener) { set.delete(l); break; } // и обёртка once
    return this;
  }

  emit(event: string, ...args: unknown[]): boolean {
    const listeners = this.events.get(event);
    if (!listeners || listeners.size === 0) return false;
    for (const l of [...listeners]) l.apply(this, args); // снимок
    return true;
  }

  once(event: string, listener: Listener): this {
    const wrapper: Listener = (...args) => {
      this.off(event, wrapper);                           // отписка ДО вызова
      listener.apply(this, args);
    };
    wrapper.listener = listener;                          // чтобы off нашёл обёртку по оригиналу
    return this.on(event, wrapper);
  }
}
```

### Снимок при emit

Слушатель может прямо во время `emit` отписать другого или подписать нового. Если обходить живую коллекцию, это меняет текущий обход: снятый слушатель пропускается, а добавленный вызывается — в худшем случае обход не заканчивается. Поэтому обходят копию. В проверке один и тот же сценарий — первый слушатель снимает второго и добавляет третьего — дал на нашей реализации и на `node:events` одинаковый результат: в текущем `emit` вызваны первый и снятый второй, а новый — только в следующем.

### once

`once` оборачивает слушатель функцией, которая снимает саму себя и вызывает оригинал. Две тонкости:

- **отписка до вызова.** Если снять обёртку после вызова оригинала, а оригинал внутри снова вызывает `emit` того же события, обёртка ещё подписана и сработает снова. В проверке такой «одноразовый» обработчик сработал 50 раз (остановил его только предохранитель), а с отпиской до вызова — один;
- **связь с оригиналом.** Подписана обёртка, а пользователь вызывает `off(event, original)`. Без ссылки `wrapper.listener = listener` такой `off` ничего не найдёт. В проверке once-слушатель снялся по оригиналу и не сработал — как в `node:events`, который хранит ту же ссылку.

### Дубли и ошибки

`Set` отсекает повторную подписку той же функции. Это совпадает с `EventTarget` — `addEventListener` с теми же аргументами не добавляет второй раз, — но расходится с `node:events`, где дубль вызывается дважды. В проверке на одном сценарии: наш эмиттер — 1 вызов, `EventTarget` — 1, `node:events` — 2. На интервью стоит назвать, какое поведение выбрано и почему. В Node есть и особое событие: `emit('error')` без слушателя бросает ошибку, чтобы сбой не остался незамеченным.

## Pub/sub

По сути то же самое, но подписка обычно возвращает функцию отписки — её удобно вернуть из `useEffect` или вызвать при размонтировании компонента:

```ts
class PubSub {
  private subscribers = new Map<string, Set<Listener>>();

  subscribe(event: string, callback: Listener): () => void {
    if (!this.subscribers.has(event)) this.subscribers.set(event, new Set());
    this.subscribers.get(event)!.add(callback);
    return () => { this.subscribers.get(event)?.delete(callback); }; // повторный вызов безопасен
  }

  publish(event: string, data?: unknown) {
    const subs = this.subscribers.get(event);
    if (subs) for (const cb of [...subs]) cb(data);      // тот же снимок
  }
}
```

В проверке после `unsub()` следующая публикация не дошла до подписчика, двойной вызов `unsub` ничего не сломал, а подписчик, добавленный из обработчика, не был вызван в той же публикации.

| | EventEmitter | Pub/sub |
| --- | --- | --- |
| Отписка | `off(event, listener)` | возвращённая функция |
| Стиль | Node.js | фронтенд и реактивность |
| Связанность | издатель владеет событиями | издатель и подписчик связаны только темой |

## Observable

Observable — значение, на изменения которого можно подписаться. Это мост к реактивности фреймворков, которая разобрана в [реализации фреймворков](/content/common-coding-questions/framework-implementation):

```ts
class Observable<T> {
  private observers = new Set<(value: T) => void>();
  constructor(private value: T) {}
  get(): T { return this.value; }
  set(next: T) {
    if (Object.is(next, this.value)) return;   // не изменилось — не уведомляем
    this.value = next;
    for (const fn of [...this.observers]) fn(next);
  }
  subscribe(fn: (value: T) => void): () => void {
    this.observers.add(fn);
    fn(this.value);                            // сразу отдаём текущее значение
    return () => { this.observers.delete(fn); };
  }
}
```

В проверке подписчик сразу получил текущую цену 100, повторный `set(100)` его не потревожил, `set(120)` — уведомил, а после отписки было тихо. Сравнение через `Object.is`, а не `===`: с `===` каждое `NaN` выглядит изменением, и в проверке такая версия уведомила дважды на двух одинаковых `NaN`, а с `Object.is` — ни разу.

## Мини-стор

Частое продолжение — «сделай Redux своими руками». Это pub/sub поверх состояния:

```ts
function createStore<S, A extends { type: string }>(reducer: (state: S, action: A) => S, initial: S) {
  let state = initial;
  let dispatching = false;
  const listeners = new Set<() => void>();
  return {
    getState: () => state,
    dispatch(action: A) {
      if (dispatching) throw new Error('Reducers may not dispatch actions.');
      try { dispatching = true; state = reducer(state, action); } finally { dispatching = false; }
      for (const l of [...listeners]) l();          // снимок подписчиков
      return action;
    },
    subscribe(listener: () => void) {
      listeners.add(listener);
      return () => { listeners.delete(listener); };
    },
  };
}
```

В проверке этот стор и настоящий `createStore` из Redux прогнали один сценарий и дали одинаковый результат: подписчик, добавленный во время `dispatch`, в нём не вызван; `dispatch` изнутри редьюсера бросил `Reducers may not dispatch actions.`; `dispatch` вернул сам action. Запрет на `dispatch` из редьюсера защищает от того, что редьюсер перестаёт быть чистой функцией состояния. Как стор вписывается в архитектуру приложения — в [архитектуре состояния и данных](/content/architecture/state-and-data-architecture); мемоизированные селекторы и подписка на часть состояния — в [кеше и состоянии](/content/common-coding-questions/caching-and-state).

## Красные флаги в ответе

- Обход живой коллекции в `emit` — отписка или подписка во время обхода ломает его.
- `once`, который снимает обёртку после вызова оригинала.
- `off(event, original)` не снимает once-слушателя.
- Массив слушателей с поиском через `indexOf` без мысли о дублях и сложности.
- Подписка без способа отписаться — утечка в компонентах.
- Observable на `===`, уведомляющий о каждом `NaN`.
- Мини-стор, который разрешает `dispatch` из редьюсера.

## Как спрашивают на собеседовании

::question
Почему при emit копируют список слушателей?

#answer
Слушатель может отписать другого или подписать нового прямо во время обработки события. Если обходить живую коллекцию, снятый пропустится, а добавленный вызовется — порядок становится непредсказуемым, а обход может не закончиться. Копия фиксирует состав на момент `emit`.

#more
Так же работает `node:events`: в проверке один и тот же сценарий дал одинаковый результат на нашей реализации и на нём — снятый во время `emit` слушатель ещё вызван, добавленный — нет. Redux делает то же со своими подписчиками.
::

::question
Как реализовать once?

#answer
Обернуть слушатель функцией, которая сначала снимает саму себя, потом вызывает оригинал, и запомнить в обёртке ссылку на оригинал. Отписка до вызова нужна, чтобы повторный `emit` внутри обработчика не вызвал его снова.

#more
В проверке обёртка, снимавшая себя после вызова, сработала 50 раз на рекурсивном `emit`, а правильная — один. Ссылка `wrapper.listener = original` нужна, чтобы `off(event, original)` нашёл обёртку: так устроен и `node:events`.
::

::question
Чем pub/sub отличается от EventEmitter?

#answer
Концептуально — ничем, это один паттерн. Различие в API и связанности: EventEmitter в стиле Node с `on`, `off`, `emit`, а pub/sub обычно возвращает функцию отписки и связывает издателя и подписчика только через тему.

#more
Функция отписки удобнее во фронтенде: её возвращают из `useEffect` или вызывают при размонтировании, не держа ссылку на исходный обработчик. Шина событий между модулями — удобный способ развязать их, но за ней труднее проследить поток данных, чем за явными вызовами.
::

::question
Как устроен Redux под капотом?

#answer
Это pub/sub поверх состояния: хранит `state`, `dispatch` прогоняет его через чистый редьюсер и уведомляет подписчиков, `subscribe` добавляет слушатель и возвращает отписку. Ядро — около двадцати строк.

#more
Детали, которые совпали с настоящим Redux в проверке: подписчики уведомляются по снимку, `dispatch` из редьюсера запрещён, `dispatch` возвращает action. Всё остальное — middleware, devtools, `combineReducers` — надстройки над этим ядром.
::

::question
Почему Set, а не массив для слушателей?

#answer
`Set` удаляет за O(1) и автоматически отсекает повторную подписку той же функции. С массивом пришлось бы искать индекс через `indexOf` и следить за дублями вручную.

#more
Отсекать дубли — решение, а не закон: `EventTarget` тоже отсекает, а `node:events` вызывает дубль дважды, что в проверке и показано. Если нужен порядок подписки — `Set` его сохраняет, как и массив.
::

::question
Почему observable сравнивает значения через Object.is?

#answer
Чтобы не уведомлять подписчиков, когда значение не изменилось. `Object.is` считает `NaN` равным `NaN`, а `===` — нет, поэтому с `===` каждое присваивание `NaN` выглядит изменением.

#more
В проверке версия на `===` уведомила дважды на двух одинаковых `NaN`, а на `Object.is` — ни разу. Так же сравнивают React (`useState` пропускает рендер при `Object.is`-равенстве) и большинство библиотек сигналов. Для объектов это сравнение по ссылке — новое состояние должно быть новым объектом.
::

## Практика

::practice{title="Обработчик once срабатывает много раз"}
Автосохранение подписано через самописный `once`, но иногда сохраняет много раз подряд — когда обработчик сам вызывает событие повторно:

```ts
once(event, listener) {
  const wrapper = (...args) => { listener(...args); this.off(event, wrapper); };
  this.on(event, wrapper);
}
```

#solution
Обёртка снимает себя только после вызова оригинала. Если оригинал внутри снова вызывает `emit` того же события, обёртка ещё подписана и срабатывает опять — в проверке так обработчик выполнился 50 раз. Отписываются до вызова и запоминают оригинал для `off`:

```ts
once(event, listener) {
  const wrapper = (...args) => {
    this.off(event, wrapper);   // сначала отписка
    listener.apply(this, args);
  };
  wrapper.listener = listener;  // off(event, listener) найдёт обёртку
  return this.on(event, wrapper);
}
```

С этой версией обработчик сработал один раз, а `off(event, listener)` до события снял его, хотя подписана была обёртка. Метод `off` при этом сравнивает и сам слушатель, и `l.listener`.
::

::practice{title="Подписчик компонента продолжает получать события"}
Компонент подписывается на шину в `useEffect`, но после размонтирования его обработчик продолжает вызываться, а в консоли — предупреждения об обновлении размонтированного компонента:

```ts
useEffect(() => {
  bus.subscribe('cart:changed', setCount);
}, []);
```

#solution
Подписка создаётся, но не снимается: обработчик остаётся в шине навсегда, держит замыкание компонента и вызывается после размонтирования. Pub/sub, возвращающий функцию отписки, решает это одной строкой:

```ts
useEffect(() => bus.subscribe('cart:changed', setCount), []); // возвращённая отписка — это и есть cleanup
```

`useEffect` вызовет её при размонтировании. В проверке после `unsub()` публикация до подписчика не дошла, а повторный вызов отписки ничего не сломал — это важно, потому что в StrictMode в режиме разработки React вызывает cleanup и повторяет эффект. Если шина не возвращает отписку, её приходится писать самому и хранить ссылку на обработчик.
::
