# Введение в фронтенд-задачи

Что такое фронтенд coding-раунд, чем он отличается от алгоритмического, что на нём оценивают на самом деле и как устроена эта глава. Спрашивают, чем фронтенд-задачи отличаются от алгоритмов, важна ли в них сложность и что главное в live coding. Глубже — почему даже в «простой» дедупликации можно получить квадратичную сложность и почему молчаливое идеальное решение хуже разговорчивого.

::tldr
- **Фронтенд-раунд — про реализацию, а не про идею:** просят написать утилиту, асинхронную функцию, работу с DOM или небольшой компонент. Что делать, обычно понятно сразу — оценивают, как это написано.
- **Проверяют пять вещей:** чистоту кода, краевые случаи, знание платформы (микрозадачи, `this`, события), коммуникацию и умение самому проверить решение.
- **Сложность никуда не делась:** в проверке дедупликация через `indexOf` внутри `filter` на 20 000 элементах оказалась в десятки раз медленнее, чем через `Set`, при одинаковом ответе.
- **Процесс важнее результата:** уточнить условие, привести примеры, написать простое рабочее решение, затем улучшить и проверить — всё вслух.
- **Глава идёт от простого к сложному:** утилиты и полифилы, асинхронность, события и DOM, компоненты, внутренности фреймворков, кеш и стор, задачи «что выведет».
::

---

## Что такое фронтенд-раунд

Фронтенд coding-раунд — формат собеседования, где просят написать рабочий код, специфичный для фронтенда: `debounce`, `Promise.all`, делегирование событий, автокомплит, мини-реактивность. В отличие от алгоритмического раунда, здесь редко нужна хитрая идея — решение обычно известно заранее. Проверяют, насколько чисто кандидат его напишет и насколько хорошо знает язык и платформу.

| Алгоритмы ([глава 02](/content/algorithms-data-structures)) | Фронтенд-задачи (эта глава) |
| --- | --- |
| два указателя, динамическое программирование, графы | `debounce`, `Promise.all`, автокомплит |
| главное — идея и сложность | главное — чистый код и знание API |
| абстрактные данные | DOM, события, промисы, React и Vue |
| чаще в больших компаниях | почти на любом фронтенд-собеседовании |

Готовиться стоит к обоим, но в большинстве продуктовых компаний именно фронтенд-задачи дают больше очков. Как устроены технические раунды в целом и где встречается live coding, take-home и задачи на отладку — в [техническом интервью](/content/preparing-for-interviews/technical-interview).

## Что проверяют на самом деле

Решение, которое «работает на примере», — только половина. Интервьюер смотрит на:

- **чистоту кода** — имена, разбиение на функции, отсутствие дублирования;
- **краевые случаи** — пустой ввод, `null`, дубликаты, гонки, отписка, повторный вызов;
- **знание платформы** — микрозадачи, `this`, прототипы, всплытие событий, утечки;
- **коммуникацию** — уточняет ли кандидат условие, проговаривает ли решение;
- **проверяемость** — может ли сам прогнать пример и найти свою ошибку.

### Сложность всё ещё важна

Фронтенд-задача не отменяет оценку сложности — она добавляет к ней знание браузера. Классический пример — дедупликация массива. Решение через `indexOf` внутри `filter` выглядит коротко и правильно, но для каждого элемента ищет его заново с начала массива, то есть работает за O(n²). Через `Set` — за O(n):

```js
const uniqueSlow = (arr) => arr.filter((x, i) => arr.indexOf(x) === i); // O(n²)
const uniqueFast = (arr) => [...new Set(arr)];                          // O(n)
```

В проверке на 20 000 элементах оба дали одинаковые 5000 уникальных значений, но первый вариант оказался более чем в десять раз медленнее. На интервью такую разницу ждут, что кандидат назовёт сам, не дожидаясь вопроса. То же с `debounce`, который забывает очищать таймер, или с рендером списка, где на каждый элемент ищут что-то во всём списке.

## Как подходить к задаче

Порядок, который работает почти для любой задачи, коротко:

1. уточнить сигнатуру, типы и ограничения;
2. привести обычный и краевой пример — это и спецификация, и будущие тесты;
3. написать простое рабочее решение, не молча;
4. улучшить сложность и разобрать краевые случаи;
5. прогнать пример руками, как отладчик.

На маленьком примере это выглядит так. Задача — убрать из массива пустые значения. Уточняющие вопросы дают спецификацию: возвращаем новый массив или меняем исходный, что считать пустым, что делать с пустым массивом. После этого решение — одна строка:

```js
// принимает массив, возвращает НОВЫЙ без falsy-значений; пустой массив → []
function compact(arr) {
  return arr.filter(Boolean);
}
```

В проверке `compact` убрал все falsy-значения — `0`, `false`, `''`, `null`, `undefined` и даже `NaN`, — оставил `[1, 2, 3, 'a']`, не изменил исходный массив и вернул `[]` для пустого. Каждый из этих пунктов и был бы вопросом интервьюера. Подробный разбор подхода — уточняющие вопросы, как думать вслух, частые ошибки и чеклист перед «готово» — в [последней истории главы](/content/common-coding-questions/how-to-approach).

## Красные флаги в ответе

- Сразу писать «финальный» код молча, без уточнений и примеров.
- Решение работает на одном примере, краевые случаи не рассмотрены.
- `indexOf` или `find` внутри цикла по тому же массиву без упоминания O(n²).
- Мутирует входные данные, хотя никто об этом не просил.
- «Готово» без прогона примера — ошибку находит интервьюер, а не кандидат.
- Знание API без понимания: «так пишут» вместо «потому что микрозадача выполнится раньше».

## Как спрашивают на собеседовании

::question
Чем фронтенд-задачи отличаются от алгоритмических?

#answer
Алгоритмы проверяют идею и сложность на абстрактных данных. Фронтенд-задачи — знание языка и платформы (промисы, DOM, события, React и Vue) и умение чисто это реализовать; идея обычно известна заранее, оценивают реализацию и краевые случаи.

#more
Граница не жёсткая: в автокомплите есть и дебаунс, и гонки запросов, и сложность фильтрации, а в LRU-кеше — структура данных. Поэтому сложность называют и во фронтенд-задаче. Готовиться стоит к обоим форматам, но во фронтенд-командах продуктовых компаний чаще встречается второй.
::

::question
Важна ли сложность во фронтенд-задачах?

#answer
Да. `indexOf` внутри `filter` даёт O(n²) там, где `Set` даёт O(n); `debounce`, который не очищает таймер, утекает; рендер списка с поиском по всему списку на каждый элемент тормозит. В проверке дедупликация через `indexOf` на 20 000 элементах была более чем в десять раз медленнее, чем через `Set`.

#more
К оценке Big-O на фронтенде добавляется знание браузера: сколько раз срабатывает раскладка, сколько создаётся слушателей, держит ли замыкание большие объекты. Хороший тон — самому назвать сложность решения и предложить, как её улучшить, если данные вырастут.
::

::question
Что главное в live coding?

#answer
Коммуникация. Уточнить условие, проговорить план, писать и объяснять одновременно, самому находить краевые случаи и прогонять пример. Молчаливое идеальное решение оценивают хуже, чем разговорчивое почти идеальное: интервьюер оценивает процесс мышления, а не только результат.

#more
Если застрял — говорить, в чём именно: интервьюер часто подсказывает, а подсказка, принятая и использованная, — нормальная часть раунда. Время распределяют так, чтобы рабочее решение было раньше идеального: улучшения можно обсудить и словами.
::

::question
С чего начать решение незнакомой задачи?

#answer
С уточнения сигнатуры и ограничений и с двух примеров — обычного и краевого. Потом простое рабочее решение, затем оптимизация и краевые случаи, в конце — прогон примера. Не молчать и не пытаться сразу написать «идеально».

#more
Примеры из уточнения становятся тестами: в проверке `compact` каждый вопрос — мутируем ли массив, что такое пустое значение, что вернуть для пустого входа — превратился в отдельную проверку. Если задача совсем незнакома, начинают с наивного решения и честно говорят о его недостатках.
::

::question
Как проверить своё решение, если код нельзя запустить?

#answer
Прогнать примеры руками, как отладчик: пройти по коду строка за строкой на обычном и краевом входе, проговаривая значения переменных. Отдельно проверить пустой вход, один элемент, повторы и асинхронный порядок — там чаще всего ошибки.

#more
Примеры из уточнения — готовые тесты: если в начале договорились, что пустой массив даёт `[]`, это первое, что проверяют в конце. Если редактор позволяет запуск, пишут пару `console.log` или `assert` прямо в нём. Найти свою ошибку самому — сильный сигнал, а не слабость.
::

## Практика

::practice{title="Дедупликация списка тормозит на больших данных"}
Функция убирает повторы из списка id, пришедших с сервера. На тысяче элементов всё быстро, на десятках тысяч страница подвисает:

```js
const unique = (ids) => ids.filter((id, i) => ids.indexOf(id) === i);
```

#solution
`indexOf` для каждого элемента ищет его с начала массива, поэтому на n элементах это n² сравнений. В проверке такой вариант на 20 000 элементах был более чем в десять раз медленнее варианта с `Set` при том же ответе:

```js
const unique = (ids) => [...new Set(ids)];
```

`Set` хранит значения в хеш-таблице и проверяет наличие за O(1), так что весь проход — O(n). Порядок первого вхождения сохраняется. Если нужно убирать дубликаты объектов по ключу, используют `Map` по ключу — такие варианты разобраны в [полифилах массивов](/content/common-coding-questions/array-polyfills).
::

::practice{title="Убрать пустые значения из массива"}
Попросили написать функцию, которая убирает из массива «пустые» значения. Что уточнить и как ответить?

#solution
Сначала вопросы: возвращать новый массив или менять исходный; что считать пустым — все falsy-значения или только `null` и `undefined`; что вернуть для пустого массива. Для варианта «новый массив без falsy»:

```js
function compact(arr) {
  return arr.filter(Boolean);
}
compact([0, 1, false, 2, '', 3, null, undefined, NaN, 'a']); // [1, 2, 3, 'a']
```

В проверке функция убрала и `NaN` (он тоже falsy), не изменила исходный массив и вернула `[]` для пустого. Если пустыми считать только `null` и `undefined` (а `0` и `''` оставить), фильтр другой: `arr.filter((x) => x != null)`. Разница между двумя ответами — ровно то, что выясняется уточняющим вопросом.
::
