# Кеши и маленькие системы

Промежуточный уровень между утилитой и системным дизайном: LRU-кеш, ограничитель частоты, мемоизированный селектор и мини-стор. Их просят, чтобы проверить выбор структур данных и понимание производительности на маленькой, но «системной» задаче. Спрашивают, как сделать LRU с операциями за O(1), какие бывают алгоритмы ограничения частоты и как устроен минимальный стейт-менеджер. Глубже — почему фиксированное окно пропускает вдвое больше запросов на стыке, почему селектор с нестабильным входом пересчитывается каждый раз и почему такой же селектор в `useSyncExternalStore` вешает React.

::tldr
- **LRU на `Map` — O(1) благодаря порядку вставки:** освежить — удалить и вставить заново, вытеснить — первый ключ. В проверке версия на `Map`, классическая на двусвязном списке и пакет `lru-cache` дали один и тот же ответ на примере LeetCode 146.
- **Ограничитель частоты выбирают по поведению на всплесках:** в проверке фиксированное окно пропустило 6 запросов за 2 мс при лимите 3 в секунду, скользящее окно — 3, а token bucket допустил всплеск до ёмкости и дальше ровный поток.
- **Селектор кеширует по ссылке на вход:** пересчёт только при смене входа — в проверке столько же пересчётов, сколько у `reselect`. Вход, создающий новый массив, ломает кеш.
- **Мини-стор — состояние плюс подписчики:** частичное и функциональное обновление, снимок слушателей — в проверке поведение совпало с `zustand/vanilla`.
- **В React стор подключают через `useSyncExternalStore`:** снимок должен быть стабильным. В проверке селектор, возвращающий новый объект, вызвал «The result of getSnapshot should be cached» и бесконечный цикл обновлений.
::

## LRU-кеш

LRU (least recently used) — кеш фиксированного размера, который при переполнении вытесняет давно не использованный элемент. Любимая задача: нужна структура с O(1) на чтение, запись и вытеснение.

### На Map

`Map` сохраняет порядок вставки: первый ключ итерации — самый старый. Освежают элемент, удаляя и вставляя его заново — он уходит в конец:

```ts
class LRUCache<K, V> {
  private cache = new Map<K, V>();
  constructor(private capacity: number) {}
  get(key: K): V | undefined {
    if (!this.cache.has(key)) return undefined;
    const value = this.cache.get(key)!;
    this.cache.delete(key);           // удалить и вставить — элемент становится свежим
    this.cache.set(key, value);
    return value;
  }
  put(key: K, value: V): void {
    if (this.cache.has(key)) this.cache.delete(key);
    this.cache.set(key, value);
    if (this.cache.size > this.capacity) {
      const oldest = this.cache.keys().next().value as K; // первый ключ итерации — самый старый
      this.cache.delete(oldest);
    }
  }
}
```

В TypeScript у `keys().next().value` тип `K | undefined` — итератор может быть пуст, — поэтому нужно приведение или проверка: в строгом режиме без них `delete` не скомпилируется.

### На двусвязном списке

На интервью могут попросить классическую реализацию, как в LeetCode 146: хеш-таблица ключ → узел и двусвязный список от свежего к старому. Перенос в начало и удаление с конца — O(1):

```ts
class LRUList<K, V> {
  private map = new Map<K, DNode<K, V>>();
  private head: DNode<K, V> | null = null;  // самый свежий
  private tail: DNode<K, V> | null = null;  // самый старый
  constructor(private capacity: number) {}
  private unlink(n: DNode<K, V>) {
    if (n.prev) n.prev.next = n.next; else this.head = n.next;
    if (n.next) n.next.prev = n.prev; else this.tail = n.prev;
    n.prev = n.next = null;
  }
  private pushFront(n: DNode<K, V>) {
    n.next = this.head;
    if (this.head) this.head.prev = n;
    this.head = n;
    if (!this.tail) this.tail = n;
  }
  get(key: K): V | undefined {
    const n = this.map.get(key);
    if (!n) return undefined;
    this.unlink(n); this.pushFront(n);
    return n.value;
  }
  put(key: K, value: V): void {
    const existing = this.map.get(key);
    if (existing) { existing.value = value; this.unlink(existing); this.pushFront(existing); return; }
    const n = { key, value, prev: null, next: null };
    this.map.set(key, n); this.pushFront(n);
    if (this.map.size > this.capacity && this.tail) { const old = this.tail; this.unlink(old); this.map.delete(old.key); }
  }
}
```

В проверке обе версии и пакет `lru-cache` на примере из LeetCode — ёмкость 2, `put(1)`, `put(2)`, `get(1)`, `put(3)`, `get(2)`, `put(4)`, `get(1)`, `get(3)`, `get(4)` — дали одинаковые `[1, -1, -1, 3, 4]`. И чтение, и обновление освежают ключ: в проверке после `get('a')` и `put('b', 20)` вытеснился `c`. Одна оговорка: если в кеше можно хранить `undefined`, снаружи «нет ключа» и «значение `undefined`» неразличимы — тогда нужен отдельный `has`.

## Ограничитель частоты

Ограничитель частоты пропускает не больше N действий за окно времени. Алгоритмы различаются поведением на всплесках, поэтому в проверке они идут на управляемых часах:

```ts
// скользящее окно: метки времени последних запросов
function slidingWindow(limit: number, windowMs: number) {
  let stamps: number[] = [];
  return () => {
    const now = Date.now();
    stamps = stamps.filter((t) => now - t < windowMs);
    if (stamps.length < limit) { stamps.push(now); return true; }
    return false;
  };
}

// фиксированное окно: счётчик на интервал
function fixedWindow(limit: number, windowMs: number) {
  let windowStart = -Infinity, count = 0;
  return () => {
    const now = Date.now();
    if (now - windowStart >= windowMs) { windowStart = now - (now % windowMs); count = 0; }
    if (count < limit) { count++; return true; }
    return false;
  };
}

// token bucket: токены доливаются с постоянной скоростью
function tokenBucket(capacity: number, refillPerSec: number) {
  let tokens = capacity, last = Date.now();
  return () => {
    const now = Date.now();
    tokens = Math.min(capacity, tokens + ((now - last) / 1000) * refillPerSec);
    last = now;
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
  };
}
```

| Алгоритм | Как работает | Что видно в проверке |
| --- | --- | --- |
| фиксированное окно | счётчик на интервал | на стыке окон 6 запросов за 2 мс при лимите 3 в секунду |
| скользящее окно | метки времени за последнее окно | на том же стыке — 3, точнее, но хранит метки |
| token bucket | ведро токенов с доливом | всплеск до ёмкости 5, потом токен каждые 500 мс |

Фиксированное окно простое и дешёвое, но в конце одного окна и начале следующего пропускает вдвое больше лимита. Скользящее точнее, но хранит метку на каждый запрос. Token bucket сглаживает поток и допускает контролируемые всплески: в проверке после выборки ёмкости за 250 мс накопилось полтокена — запрос отклонён, — за 500 мс ровно один, а после долгой паузы ведро наполнилось только до ёмкости. На фронтенде ограничитель защищает API от лишних запросов, но настоящая защита — на сервере: клиент можно обойти.

## Мемоизированный селектор

Селектор выводит данные из состояния. Мемоизированный — как `reselect` — пересчитывает только при изменении входа, и зависящий компонент не перерисовывается:

```ts
function createSelector<S, A, R>(inputFn: (state: S) => A, resultFn: (input: A) => R) {
  let lastInput: A, lastResult: R, hasRun = false;
  return (state: S): R => {
    const input = inputFn(state);
    if (!hasRun || input !== lastInput) {    // вход тот же по ссылке — отдаём кеш
      lastResult = resultFn(input);
      lastInput = input;
      hasRun = true;
    }
    return lastResult;
  };
}
const selectDone = createSelector((s: State) => s.todos, (todos) => todos.filter((t) => t.done));
```

В проверке при смене другого поля состояния (`filter`) селектор вернул тот же массив-результат, а пересчитался только при смене `todos` — столько же раз, сколько настоящий `reselect` на том же сценарии. Это требует неизменяемых обновлений: сравнение по ссылке осмысленно, только если изменённые данные — новые объекты.

Ловушка — вход, который сам создаёт новый массив: `(s) => s.todos.filter(...)`. Ссылка новая на каждый вызов, и в проверке такой селектор пересчитался на каждом из трёх вызовов. Фильтрацию переносят в функцию результата, а вход оставляют простым чтением. `reselect` в режиме разработки проверяет стабильность входов: в проверке он предупредил «An input selector returned a different result when passed same arguments». Размер кеша — ещё одно отличие. Наша версия помнит один вход, и при чередовании двух состояний в проверке пересчиталась все четыре раза. `reselect` 5 по умолчанию кеширует по ссылкам аргументов без ограничения (`weakMapMemoize`) и пересчитался дважды; в четвёртой версии кеш был на один вход.

## Мини-стор

Связка с [pub/sub](/content/common-coding-questions/events-and-pubsub) — контейнер состояния с подпиской, по сути ядро Zustand:

```ts
type Setter<S> = (partial: Partial<S> | ((s: S) => Partial<S>)) => void;
function createStore<S extends object>(initial: S) {
  let state = initial;
  const listeners = new Set<(s: S, prev: S) => void>();
  const setState: Setter<S> = (partial) => {
    const next = typeof partial === 'function' ? partial(state) : partial;
    if (Object.is(next, state)) return;
    const prev = state;
    state = { ...state, ...next };          // неизменяемое обновление
    for (const l of [...listeners]) l(state, prev);
  };
  return {
    getState: () => state,
    setState,
    subscribe(listener: (s: S, prev: S) => void) { listeners.add(listener); return () => { listeners.delete(listener); }; },
  };
}
```

В проверке тот же сценарий — частичное обновление, функциональное обновление, отписка — дал на этом сторе и на `zustand/vanilla` одинаковые уведомления `0→1` и `1→2`, а имя пользователя при частичном обновлении сохранилось.

### Подключение к React

В React внешний стор подключают через `useSyncExternalStore` — он корректно работает с конкурентным рендерингом:

```tsx
function useStore<T>(selector: (s: State) => T): T {
  return useSyncExternalStore(store.subscribe, () => selector(store.getState()));
}
function Counter() {
  const count = useStore((s) => s.count);
  return <p>счёт: {count}</p>;
}
```

В проверке компонент обновился при изменении `count` и не перерисовался при изменении другого поля: селектор вернул то же число, и React пропустил обновление. Требование — стабильный снимок: `getSnapshot` для того же состояния должен возвращать то же значение. Селектор `(s) => ({ count: s.count })` создаёт новый объект на каждый вызов, и в проверке React сначала предупредил «The result of getSnapshot should be cached to avoid an infinite loop», а затем упал с «Maximum update depth exceeded». Поэтому селекторы возвращают примитивы или уже существующие объекты, а составные значения мемоизируют. Как стор вписывается в архитектуру — в [архитектуре состояния и данных](/content/architecture/state-and-data-architecture).

## Красные флаги в ответе

- LRU через массив с `indexOf` и `splice` — O(n) на каждую операцию.
- LRU, который освежает элемент на `get`, но не на обновлении `put`.
- Фиксированное окно без оговорки про двойной всплеск на стыке.
- Ограничитель частоты только на клиенте как защита API.
- Селектор, во входной функции которого `filter` или `map`.
- Стор, мутирующий состояние на месте, — селекторы по ссылке перестают работать.
- `useSyncExternalStore` с селектором, возвращающим новый объект.

## Как спрашивают на собеседовании

::question
Как сделать LRU-кеш с операциями за O(1)?

#answer
Через `Map`, который хранит порядок вставки: `get` удаляет и заново вставляет элемент, освежая его, а при переполнении удаляется первый ключ итерации — самый старый. Классическая альтернатива — хеш-таблица и двусвязный список. Обе дают O(1).

#more
В проверке обе версии и пакет `lru-cache` дали одинаковый результат на примере LeetCode 146. На интервью стоит назвать оба варианта: `Map` короче, а список показывает понимание структуры и работает в языках без упорядоченных словарей. Обновление существующего ключа тоже должно освежать его.
::

::question
Почему для LRU Map, а не обычный объект?

#answer
`Map` гарантирует порядок вставки для любых ключей и даёт итерацию от старых к новым плюс `delete` и `set` за O(1). У объекта целочисленные ключи всегда идут первыми по возрастанию, независимо от порядка вставки, а ключами могут быть только строки и символы.

#more
Порядок ключей объекта описан в [объектах и массивах](/content/javascript/objects-and-arrays): с числовыми id LRU на объекте вытеснял бы не тот элемент. Ещё `Map` знает свой размер (`size`) без `Object.keys`, а ключами могут быть объекты — например, узлы DOM.
::

::question
Какие есть алгоритмы ограничения частоты?

#answer
Фиксированное окно — счётчик на интервал, просто, но на стыке окон пропускает вдвое больше лимита. Скользящее окно — метки времени за последнее окно, точнее, но хранит метку на запрос. Token bucket — токены доливаются с постоянной скоростью, допускает контролируемые всплески и сглаживает поток.

#more
В проверке фиксированное окно пропустило 6 запросов за 2 мс при лимите 3 в секунду, а скользящее — 3. Существует ещё leaky bucket — очередь с постоянной скоростью обработки. Выбор зависит от того, что важнее: точность, память или гладкость. Ограничение на клиенте — вежливость, защита — на сервере.
::

::question
Как работает мемоизированный селектор?

#answer
Запоминает последний вход и результат. Если вход не изменился по ссылке, возвращает прошлый результат, не пересчитывая, — и компонент, получающий его, не перерисовывается. Работает, только если состояние обновляется неизменяемо.

#more
Вход должен быть простым чтением: селектор с `filter` во входной функции в проверке пересчитывался каждый раз. `reselect` поддерживает несколько входов и сравнивает каждый по ссылке. В пятой версии он по умолчанию кеширует по ссылкам аргументов без ограничения размера — в проверке чередование двух состояний не вызвало лишних пересчётов, — а самописный селектор с кешем на один вход пересчитывается при каждом чередовании.
::

::question
Как устроен минимальный стейт-менеджер?

#answer
Состояние и множество подписчиков: `setState` неизменяемо обновляет состояние (частично или функцией от прошлого) и уведомляет подписчиков, `subscribe` возвращает отписку. Это ядро Zustand и Redux. В React его подключают через `useSyncExternalStore`.

#more
В проверке такой стор повёл себя как `zustand/vanilla`. Подписчиков уведомляют по снимку, чтобы отписка во время уведомления не сломала обход. В React снимок должен быть стабильным: селектор, возвращающий новый объект, в проверке привёл к бесконечному циклу обновлений.
::

::question
Почему useSyncExternalStore требует стабильный снимок?

#answer
React вызывает `getSnapshot` на каждом рендере и при уведомлении стора и сравнивает результат с прошлым через `Object.is`. Если для того же состояния функция возвращает новый объект, React считает, что данные изменились, перерисовывает компонент — и так по кругу.

#more
В проверке селектор `(s) => ({ count: s.count })` вызвал предупреждение «The result of getSnapshot should be cached to avoid an infinite loop» и ошибку «Maximum update depth exceeded». Решения — возвращать примитив или существующий объект, мемоизировать составное значение или использовать `useShallow` из Zustand.
::

## Практика

::practice{title="Ограничитель пропустил всплеск запросов"}
Клиент ограничивает поиск тремя запросами в секунду счётчиком, который сбрасывается каждую секунду. В логах сервера видно, что иногда за доли секунды приходит шесть запросов.

#solution
Это фиксированное окно: три запроса в конце одного окна и три в начале следующего укладываются в лимит каждого окна, но вместе это шесть запросов за миллисекунды. В проверке ровно так на стыке прошло 6 запросов за 2 мс. Если нужна гладкость, берут скользящее окно или token bucket:

```ts
function tokenBucket(capacity: number, refillPerSec: number) {
  let tokens = capacity, last = Date.now();
  return () => {
    const now = Date.now();
    tokens = Math.min(capacity, tokens + ((now - last) / 1000) * refillPerSec);
    last = now;
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
  };
}
```

Скользящее окно в проверке на том же стыке пропустило 3. Token bucket допускает всплеск до ёмкости, а потом пропускает ровно с заданной скоростью. Для поиска по вводу часто достаточно дебаунса — запрос уходит после паузы, — а лимит по-настоящему соблюдает сервер.
::

::practice{title="Компонент со стором уходит в бесконечный цикл"}
Компонент подписан на внешний стор через `useSyncExternalStore`, и при первом же рендере React падает с «Maximum update depth exceeded»:

```tsx
const user = useSyncExternalStore(store.subscribe, () => ({
  name: store.getState().name,
  role: store.getState().role,
}));
```

#solution
`getSnapshot` возвращает новый объект на каждый вызов. React сравнивает снимки через `Object.is`, видит «изменение», перерисовывает — и всё повторяется. В проверке такой селектор вызвал предупреждение «The result of getSnapshot should be cached to avoid an infinite loop» и затем эту же ошибку. Снимок делают стабильным:

```tsx
// читать поля отдельно — примитивы сравниваются по значению
const name = useSyncExternalStore(store.subscribe, () => store.getState().name);
const role = useSyncExternalStore(store.subscribe, () => store.getState().role);
// или вернуть объект, который уже лежит в состоянии
const user = useSyncExternalStore(store.subscribe, () => store.getState().user);
```

В проверке компонент с селектором примитива обновился при изменении своего поля и не перерисовался при изменении чужого. Если нужен составной объект, его мемоизируют по входам — тем же приёмом, что и мемоизированный селектор, — или используют `useShallow` из Zustand.
::
