# UI-компоненты: продвинутые

Вторая половина machine-coding — компоненты с асинхронностью и сложным состоянием: автокомплит, бесконечная прокрутка, пагинация, todo, крестики-нолики. К интерфейсу добавляются дебаунс, отмена запросов, гонки и `IntersectionObserver`. Как спроектировать те же задачи на уровне системы — в [примерах системного дизайна](/content/architecture/system-design-examples); здесь — как их написать. Спрашивают, как защититься от гонок в автокомплите, зачем `IntersectionObserver` и почему отфильтрованный список не хранят в состоянии. Глубже — почему проверка «последнего запроса» пропускает устаревший ответ после очистки поля, почему флаг `loading` в состоянии допускает двойную загрузку и где у пагинации краевые случаи.

::tldr
- **Автокомплит — дебаунс, отмена, клавиатура, ARIA:** в проверке серия ввода дала один запрос, а ответ на старый запрос, пришедший позже нового, был проигнорирован.
- **Устаревший ответ отбрасывают флагом эффекта, а не сравнением строк:** в проверке исходная версия после очистки поля всё равно показала подсказки — сравнение «последнего запроса» не знало, что поле стёрли.
- **Защиту от двойной загрузки держат в ref:** флаг `loading` из состояния в замыкании наблюдателя устаревает. В проверке два быстрых пересечения в исходной версии вызвали два запроса одной страницы.
- **У бесконечного списка есть конец и ошибки:** без `hasMore` наблюдатель грузит вечно, а без `finally` ошибка оставляет флаг загрузки навсегда.
- **Производное не хранят:** видимые задачи считают из списка и фильтра, чей ход в крестиках-ноликах — из доски. Два источника истины расходятся.
::

## Автокомплит

Самая частая «большая» задача. Соединяет [дебаунс](/content/common-coding-questions/higher-order-utils), асинхронность, гонки запросов, клавиатуру и доступность.

### Ловушка исходной версии

Популярная защита от гонок — помнить «последний запрос» в ref и сравнивать с ним:

```tsx
useEffect(() => {
  if (!query) { setResults([]); return; }
  const id = setTimeout(async () => {
    lastQuery.current = query;
    const data = await fetchSuggestions(query);
    if (lastQuery.current === query) setResults(data);
  }, 300);
  return () => clearTimeout(id);
}, [query]);
```

Она ловит случай «пришёл ответ на старый запрос», но пропускает другой. Если пользователь стёр поле, пока запрос в полёте, нового таймера нет, `lastQuery` остаётся прежним, и ответ на стёртый запрос проходит проверку. В проверке поле было пустым, а под ним показались две подсказки.

### Исправленная версия

Надёжнее — флаг конкретного эффекта: cleanup помечает его ответ устаревшим, что бы ни случилось дальше. Заодно запрос отменяется через `AbortController`:

```tsx
function Autocomplete({ fetchSuggestions, delay = 300 }: Props) {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState<string[]>([]);
  const [active, setActive] = useState(-1);
  const [status, setStatus] = useState<'idle' | 'loading' | 'error'>('idle');
  const chosen = useRef<string | null>(null);          // выбранное значение не ищем заново
  const listId = useId();

  useEffect(() => {
    if (!query.trim() || query === chosen.current) { setResults([]); setStatus('idle'); return; }
    let ignore = false;                                 // ответ этого эффекта устарел после cleanup
    const controller = new AbortController();
    const id = setTimeout(async () => {
      setStatus('loading');
      try {
        const data = await fetchSuggestions(query, controller.signal);
        if (!ignore) { setResults(data); setActive(-1); setStatus('idle'); }
      } catch (e) {
        if (!ignore && (e as Error).name !== 'AbortError') setStatus('error');
      }
    }, delay);
    return () => { ignore = true; clearTimeout(id); controller.abort(); };
  }, [query, fetchSuggestions, delay]);

  const choose = (value: string) => { chosen.current = value; setQuery(value); setResults([]); setActive(-1); };
  const open = results.length > 0;
  return (
    <div>
      <input
        role="combobox" aria-expanded={open} aria-controls={listId} aria-autocomplete="list"
        aria-activedescendant={active >= 0 ? `${listId}-${active}` : undefined}
        value={query}
        onChange={(e) => { chosen.current = null; setQuery(e.target.value); }}
        onKeyDown={(e) => {
          if (!open) return;
          if (e.key === 'ArrowDown') { e.preventDefault(); setActive((i) => (i + 1) % results.length); }
          else if (e.key === 'ArrowUp') { e.preventDefault(); setActive((i) => (i <= 0 ? results.length - 1 : i - 1)); }
          else if (e.key === 'Enter' && active >= 0) { e.preventDefault(); choose(results[active]); }
          else if (e.key === 'Escape') { setResults([]); setActive(-1); }
        }}
      />
      {status === 'error' && <p role="alert">Не удалось загрузить подсказки</p>}
      <ul role="listbox" id={listId}>
        {results.map((r, i) => (
          <li key={r} id={`${listId}-${i}`} role="option" aria-selected={i === active}
              onMouseDown={(e) => { e.preventDefault(); choose(r); }}>{r}</li>
        ))}
      </ul>
    </div>
  );
}
```

В проверке на настоящем React:

- **дебаунс** — ввод «ч», «ча», «чай» подряд дал один запрос, за «чай»;
- **гонка** — ответ на «чай» пришёл позже ответа на «чайн» и был проигнорирован, на экране остался «чайник»;
- **очистка** — стёртое поле не показало ответ на «к», пришедший после очистки;
- **клавиатура** — стрелки ходят по кругу, `aria-activedescendant` указывает на активный пункт, Enter подставил «Москва» и закрыл список, не запустив поиск по выбранному значению; Escape закрыл список;
- **ошибка** — сбой запроса показал сообщение с `role="alert"`.

Роль `combobox` — на самом поле, а не на обёртке: так требует :term[ARIA]{def="атрибуты, которые сообщают вспомогательным технологиям роль, состояние и имя элемента"} 1.2. Выбор мышью — на `mousedown` с `preventDefault`, чтобы поле не потеряло фокус до выбора. Отмена через `AbortController` экономит запросы, а флаг `ignore` защищает, даже если `fetchSuggestions` отмену не поддерживает.

## Бесконечная прокрутка

Следующую порцию подгружают, когда в зону видимости попадает пустой элемент-«маяк» внизу списка. `IntersectionObserver` эффективнее обработчика `scroll`: браузер сам считает пересечение, без обработчика на каждый пиксель прокрутки. Как он ведёт себя в браузере — в [системном дизайне](/content/architecture/system-design-examples); здесь — React-обёртка.

Исходная версия держала флаг загрузки в состоянии и проверяла его в колбэке наблюдателя. Колбэк замыкает значение того рендера, и два пересечения подряд до перерисовки оба видят `loading === false`. В проверке с управляемым наблюдателем два пересечения дали два запроса одной страницы. Флаг держат в ref — он читается синхронно:

```tsx
function InfiniteList({ loadPage }: { loadPage: (page: number) => Promise<{ items: Item[]; hasMore: boolean }> }) {
  const [items, setItems] = useState<Item[]>([]);
  const [hasMore, setHasMore] = useState(true);
  const [error, setError] = useState(false);
  const loading = useRef(false);
  const page = useRef(0);
  const sentinel = useRef<HTMLDivElement>(null);

  const loadMore = useCallback(async () => {
    if (loading.current) return;
    loading.current = true;
    setError(false);
    try {
      const { items: next, hasMore: more } = await loadPage(page.current);
      page.current += 1;
      setItems((prev) => [...prev, ...next]);
      setHasMore(more);
    } catch {
      setError(true);
    } finally {
      loading.current = false;                         // ошибка не оставляет флаг навсегда
    }
  }, [loadPage]);

  useEffect(() => {
    if (!hasMore || error || !sentinel.current) return; // в конце списка наблюдатель не нужен
    const observer = new IntersectionObserver(([entry]) => { if (entry.isIntersecting) loadMore(); });
    observer.observe(sentinel.current);
    return () => observer.disconnect();
  }, [loadMore, hasMore, error]);

  return (
    <div>
      {items.map((i) => <Row key={i.id} item={i} />)}
      {error && <button onClick={loadMore}>Повторить</button>}
      {hasMore ? <div ref={sentinel} /> : <p>Это всё</p>}
    </div>
  );
}
```

В проверке второе пересечение во время загрузки проигнорировалось; сбой сети показал кнопку «Повторить», и повтор загрузил страницу; на последней странице маяк исчез, появилось «Это всё», а следующие пересечения больше не вызывали запросов. `loadPage` из родителя передают стабильным (`useCallback`), иначе наблюдатель будет пересоздаваться на каждом рендере.

## Пагинация

Часто просят чистую функцию диапазона страниц с многоточием — `1 … 4 5 6 … 20`:

```ts
function getPaginationRange(current: number, total: number, siblings = 1): (number | '...')[] {
  if (total <= 0) return [];                            // нет страниц — нет кнопок
  const range: (number | '...')[] = [1];
  const left = Math.max(2, current - siblings);
  const right = Math.min(total - 1, current + siblings);
  if (left === 3) range.push(2);                        // многоточие вместо одной страницы бессмысленно
  else if (left > 3) range.push('...');
  for (let i = left; i <= right; i++) range.push(i);
  if (right === total - 2) range.push(total - 1);
  else if (right < total - 2) range.push('...');
  if (total > 1) range.push(total);
  return range;
}
getPaginationRange(5, 20); // [1, '...', 4, 5, 6, '...', 20]
```

Чистую функцию удобно проверять на краях — и исходная версия на них ошибалась. На странице 4 из 20 она давала `[1, '...', 3, 4, 5, '...', 20]`: многоточие прятало одну-единственную страницу 2, хотя кнопка «2» занимает столько же места. А для пустого результата поиска (0 страниц) возвращала кнопку «1». В проверке исправленная версия на странице 4 дала `[1, 2, 3, 4, 5, '...', 20]`, на 0 страниц — пустой массив, а на первой, последней, одной и трёх страницах — ожидаемые диапазоны.

## Todo

Классика :term[take-home]{def="домашнее задание: задачу решают сами, за несколько часов или дней"}. Главное — минимальное состояние, неизменяемые обновления и фильтрация как производное значение. Логику удобно держать чистыми функциями — их легко проверить без интерфейса:

```ts
const addTodo = (todos: Todo[], text: string): Todo[] =>
  text.trim() ? [...todos, { id: crypto.randomUUID(), text: text.trim(), done: false }] : todos;
const toggleTodo = (todos: Todo[], id: string) => todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t));
const removeTodo = (todos: Todo[], id: string) => todos.filter((t) => t.id !== id);
const visibleTodos = (todos: Todo[], filter: Filter) =>
  todos.filter((t) => (filter === 'all' ? true : filter === 'done' ? t.done : !t.done));

// в компоненте: const [todos, setTodos] = useState<Todo[]>([]); const visible = visibleTodos(todos, filter);
```

В проверке пустая задача из пробелов не добавилась, текст обрезался, переключение вернуло новый массив и не изменило старый (иначе React не увидит изменения), а фильтры дали выполненные и активные. Ключевой принцип — `visible` вычисляется из `todos` и `filter` при рендере, его не хранят отдельным состоянием: два источника истины рано или поздно расходятся. Подробнее о производном состоянии — в [React](/content/reactjs/derived-state-and-data-flow).

## Крестики-нолики

Любимая «логическая» задача: автомат состояний и проверка победителя. Победителя ищут по таблице выигрышных линий:

```ts
const LINES = [[0, 1, 2], [3, 4, 5], [6, 7, 8], [0, 3, 6], [1, 4, 7], [2, 5, 8], [0, 4, 8], [2, 4, 6]];

function getWinner(board: Cell[]): Cell {
  for (const [a, b, c] of LINES) if (board[a] && board[a] === board[b] && board[a] === board[c]) return board[a];
  return null;
}

function play(board: Cell[], index: number): Cell[] {
  if (board[index] || getWinner(board)) return board;   // занято или игра окончена
  const xs = board.filter((c) => c === 'X').length, os = board.filter((c) => c === 'O').length;
  const next = [...board];
  next[index] = xs === os ? 'X' : 'O';                  // чей ход — выводится из доски
  return next;
}
const isDraw = (board: Cell[]) => board.every(Boolean) && !getWinner(board);
```

В проверке каждая из восьми линий распознавалась как победа, ход в занятую клетку и ход после победы возвращали ту же доску, а заполненная доска без тройки была ничьей. Чей ход, не хранят отдельно — его выводят из числа крестиков и ноликов, и он не может разойтись с доской.

## Красные флаги в ответе

- Автокомплит без дебаунса и без защиты от устаревших ответов.
- Защита только сравнением «последнего запроса» — стёртое поле показывает старые подсказки.
- `role="combobox"` на обёртке, выбор мышью через `click` с потерей фокуса.
- Флаг загрузки в состоянии, проверяемый в колбэке наблюдателя, — двойные запросы.
- Бесконечный список без конца, без обработки ошибок и без `disconnect`.
- Пагинация, падающая или показывающая «1» при нуле страниц.
- Отфильтрованный список или «чей ход» в отдельном состоянии.

## Как спрашивают на собеседовании

::question
Как защититься от гонок запросов в автокомплите?

#answer
Помечать ответ устаревшим, когда эффект сменился: флаг `ignore` в замыкании эффекта, который cleanup выставляет в `true`, и отмена запроса через `AbortController`. Тогда медленный ответ на старый запрос не перезапишет свежий.

#more
Сравнение со «строкой последнего запроса» ловит не всё: в проверке после очистки поля ответ на стёртый запрос прошёл проверку и показался. Флаг эффекта не зависит от того, что именно пользователь сделал — ввёл, стёр или выбрал. Это тот же приём, что и для загрузки данных в эффектах вообще.
::

::question
Зачем в автокомплите дебаунс?

#answer
Чтобы не отправлять запрос на каждый символ, а дождаться паузы около 300 мс. Экономит запросы и нагрузку на API, а подсказки при этом не отстают от пользователя. Реализуется через `setTimeout` в эффекте с очисткой при новом вводе.

#more
В проверке ввод трёх символов подряд дал один запрос. Дебаунс не заменяет защиту от гонок: ответы всё равно могут прийти в другом порядке, если запросы ушли с паузой. Минимальная длина запроса и кеш по уже введённым строкам тоже снижают нагрузку.
::

::question
Почему IntersectionObserver лучше события scroll для бесконечной прокрутки?

#answer
Браузер сам асинхронно вычисляет пересечение маяка с областью видимости, без обработчика, который срабатывает на каждый пиксель прокрутки и заставляет мерить положение вручную. Это эффективнее и не требует `throttle`. Наблюдатель отключают при размонтировании.

#more
В React важно, где хранить флаг загрузки: в ref, а не в состоянии — в проверке флаг в состоянии допустил двойной запрос. Ещё нужны `hasMore` (иначе наблюдатель грузит вечно) и обработка ошибки с повтором. `rootMargin` позволяет начать загрузку заранее, до того как маяк дошёл до экрана.
::

::question
Почему отфильтрованный список не хранят в состоянии?

#answer
Это производное состояние: оно вычисляется из исходного списка и фильтра при рендере. Хранить его отдельно — значит держать два источника истины и синхронизировать их вручную, рискуя рассинхроном. Хранят только `todos` и `filter`.

#more
Если вычисление дорогое, его мемоизируют через `useMemo`, а не переносят в состояние. Тот же принцип в крестиках-ноликах: чей ход, выводится из доски, а не хранится отдельно. Обновления делают неизменяемыми — новый массив и новые объекты, — иначе React не увидит изменения.
::

::question
Как проверить победителя в крестиках-ноликах?

#answer
Заранее задать восемь выигрышных линий — индексы тройками: три ряда, три колонки, две диагонали — и проверить, есть ли линия с тремя одинаковыми непустыми клетками. Это чище, чем перебор координат вложенными циклами.

#more
Для доски N×N линии генерируют, а проверку можно делать только по линиям через последний ход — O(N) вместо обхода всей доски. Не забывают ничью (доска заполнена, победителя нет) и запрет хода в занятую клетку и после победы — в проверке оба хода вернули ту же доску.
::

::question
Какие краевые случаи у пагинации?

#answer
Ноль страниц (пустой результат — не показывать кнопку «1»), одна страница, текущая у края, и многоточие, которое прячет ровно одну страницу, — вместо него лучше показать саму страницу. Плюс текущая страница больше общего числа после смены фильтра.

#more
В проверке исходная функция на странице 4 из 20 прятала за многоточием только страницу 2, а при нуле страниц возвращала «1». Чистая функция диапазона отделена от интерфейса, поэтому такие случаи легко проверить таблицей входов и ожидаемых выходов.
::

## Практика

::practice{title="Подсказки остаются после очистки поля"}
Пользователь набирает «ч», быстро стирает ввод, а через мгновение под пустым полем появляются подсказки. Автокомплит защищается от гонок сравнением с последним запросом:

```tsx
lastQuery.current = query;
const data = await fetchSuggestions(query);
if (lastQuery.current === query) setResults(data);
```

#solution
При очистке поля новый таймер не создаётся, `lastQuery` остаётся «ч», и ответ на стёртый запрос проходит проверку. В проверке так под пустым полем показались две подсказки. Устаревшим считают ответ любого эффекта, который уже сменился:

```tsx
useEffect(() => {
  if (!query.trim()) { setResults([]); return; }
  let ignore = false;
  const controller = new AbortController();
  const id = setTimeout(async () => {
    const data = await fetchSuggestions(query, controller.signal);
    if (!ignore) setResults(data);
  }, 300);
  return () => { ignore = true; clearTimeout(id); controller.abort(); };
}, [query]);
```

Cleanup выполняется при любом изменении `query`, в том числе при очистке, и помечает ответ устаревшим. В проверке исправленная версия не показала ответ на «к», пришедший после очистки, и проигнорировала поздний ответ на старый запрос.
::

::practice{title="Лента дважды загружает одну страницу"}
В бесконечной ленте иногда повторяются посты: одна и та же страница приходит дважды. Флаг загрузки хранится в состоянии и проверяется в колбэке `IntersectionObserver`:

```tsx
const observer = new IntersectionObserver(async ([entry]) => {
  if (entry.isIntersecting && !loading) {
    setLoading(true);
    const next = await loadMore();
    setItems((prev) => [...prev, ...next]);
    setLoading(false);
  }
});
```

#solution
Колбэк замыкает `loading` того рендера, в котором создан наблюдатель. Если маяк пересёкся дважды до перерисовки, оба раза `loading` ещё `false`. В проверке два пересечения подряд дали два запроса. Флаг, который нужно читать синхронно, держат в ref:

```tsx
const loading = useRef(false);
const loadMore = useCallback(async () => {
  if (loading.current) return;
  loading.current = true;
  try {
    const { items: next, hasMore } = await loadPage(page.current++);
    setItems((prev) => [...prev, ...next]);
    setHasMore(hasMore);
  } catch {
    setError(true);
  } finally {
    loading.current = false;
  }
}, [loadPage]);
```

В проверке второе пересечение во время загрузки проигнорировалось, ошибка не заблокировала ленту, а после последней страницы запросы прекратились. Для отображения спиннера состояние загрузки можно держать и в `useState` — но решение «грузить ли» принимают по ref.
::
