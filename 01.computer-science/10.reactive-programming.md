# Реактивное программирование

Реактивная программа описывает не шаги, а зависимости: значение пересчитывается само, когда меняются его источники, как ячейка в таблице. Во фронтенде это две семьи инструментов: потоки событий во времени (RxJS, Observable) и графы состояния (сигналы, реактивность Vue). Спрашивают, что такое реактивность, чем Observable отличается от Promise и чем отличаются `switchMap`, `mergeMap`, `concatMap` и `exhaustMap`. Глубже — холодные и горячие потоки, противодавление и почему `combineLatest` на миг показывает состояние, которого не было.

::tldr
- **Реактивность — пересчёт по зависимостям.** Вместо «посчитать и запомнить» код объявляет «итог зависит от цены и количества», и среда обновляет итог сама.
- **Есть pull и push:** функция и итератор отдают значения, когда их просят; промис и Observable — когда значения появились. Observable — push для многих значений во времени.
- **Observable ленивый и обычно холодный:** без подписки ничего не происходит, а каждая подписка запускает источник заново. `share` делает один запуск на всех подписчиков.
- **Стратегия выравнивания — главный вопрос по RxJS:** `switchMap` отменяет прошлый запрос (поиск), `concatMap` ставит в очередь (сохранение по порядку), `mergeMap` выполняет параллельно, `exhaustMap` игнорирует новые, пока идёт текущий (кнопка оплаты).
- **Потоки и сигналы решают разные задачи:** потоки — для событий во времени и их композиции, сигналы — для состояния и производных значений без промежуточных несогласованных состояний.
::

## Значения, которые следят за источниками

Сквозной пример — страница товара: цена приходит с сервера и меняется в реальном времени, пользователь вводит количество и поисковый запрос, кнопка «Оплатить» отправляет заказ.

В обычном коде присваивание — это снимок:

```js
let price = 450, qty = 2;
let total = price * qty; // 900
qty = 3;
total;                   // всё ещё 900
```

Чтобы `total` был правильным, каждое место, которое меняет `qty`, должно не забыть пересчитать итог и обновить экран. Это та же проблема ручной синхронизации, что и в [Парадигмах](/content/computer-science/paradigms).

**Реактивное программирование** переворачивает ответственность: код объявляет зависимость один раз, а среда сама распространяет изменения. Классический пример — таблица: в ячейке `=B1*B2`, и она пересчитывается при изменении любой из двух.

Во фронтенде у этой идеи два воплощения:

- **граф состояния** — :term[сигналы]{def="реактивные значения, которые запоминают, кто их читает, и уведомляют зависимых при изменении"}, `ref` и `computed` во Vue, :term[MobX]{def="библиотека состояния на наблюдаемых объектах: производные значения и реакции пересчитываются сами"}. Значения хранят текущее состояние, производные пересчитываются по зависимостям. Подробно — в [Сигналах](/content/modern-dev/signals-and-reactivity) и [Основах реактивности Vue](/content/vuejs/reactivity-fundamentals);
- **потоки событий** — Observable и RxJS. Значение — не «текущая цена», а последовательность событий во времени: нажатия, ввод, ответы сервера, сообщения :term[WebSocket]{def="протокол постоянного двустороннего соединения браузера с сервером"}.

Дальше — о потоках, и начать нужно с того, кто кому отдаёт значения.

## Pull и push

Значения можно получать двумя способами. **Pull** — потребитель сам просит значение, когда оно ему нужно. **Push** — источник отдаёт значение, когда оно появилось, и потребитель реагирует.

| | Одно значение | Много значений |
| --- | --- | --- |
| **Pull** | функция | итератор, генератор |
| **Push** | Promise | Observable |

Observable занимает пустую клетку: это push-источник для **многих значений во времени**. Цена товара, клики, ответы на последовательные запросы — всё это потоки, которые промисом не описать: промис разрешается один раз.

У Observable три вида сигналов: `next` — очередное значение, `error` — ошибка, после которой поток закончен, `complete` — нормальное завершение. После `error` и `complete` значений больше не будет.

---

## Observable

Observable — функция, которая получает подписчика и отдаёт ему значения. Её можно написать за десяток строк — так и спрашивают на задачах по кодингу ([События и pub/sub](/content/common-coding-questions/events-and-pubsub)). Для понимания важны три свойства.

```js
const prices$ = new Observable((subscriber) => {
  subscriber.next(450);
  const id = setInterval(() => subscriber.next(fetchPrice()), 1000);
  return () => clearInterval(id);             // очистка при отписке
});
```

- **Ленивость.** Пока никто не подписался, функция не вызвана. В проверке после создания `prices$` счётчик запусков был нулём.
- **Отдельный запуск на каждую подписку.** Два `subscribe` — два вызова функции, два таймера, два набора значений. Такой поток называют **холодным**.
- **Очистка.** `subscribe` возвращает подписку, а `unsubscribe` вызывает функцию очистки. Забытая отписка — та же утечка, что и забытый `removeEventListener`.

Промис, наоборот, **энергичный** и **общий**: код в `new Promise` выполняется сразу, а все `then` получают один и тот же результат. Отменить промис нельзя — только игнорировать результат или передать `AbortSignal` в саму операцию.

### Холодные и горячие потоки

**Холодный** поток создаёт источник для каждого подписчика: HTTP-запрос в Observable отправится столько раз, сколько было подписок. **Горячий** поток существует сам по себе, а подписчики присоединяются к нему: клики, сообщения WebSocket. Опоздавший подписчик пропускает то, что было до него.

Холодный поток делают горячим операторами:

- **`share()`** — один запуск источника на всех текущих подписчиков. В проверке шапка и профиль, подписанные на данные пользователя через `share`, вызвали один запрос; без `share` — два;
- **`shareReplay(1)`** — то же, плюс запоминает последнее значение и сразу отдаёт его опоздавшим. Подходит для «текущего пользователя» и настроек.

Сами по себе потоки полезны мало. Сила RxJS — в операторах, которые их комбинируют.

## Операторы

Оператор — функция, которая берёт поток и возвращает новый. Цепочка операторов читается как описание обработки:

```js
const query$ = fromEvent(input, 'input').pipe(
  map((e) => e.target.value.trim()),
  debounceTime(300),              // ждём паузу в наборе
  filter((q) => q.length >= 2),
  distinctUntilChanged(),         // тот же запрос второй раз не отправляем
);
```

Операторы бывают на любой вкус: преобразование (`map`, `scan`), фильтрация (`filter`, `take`, `distinctUntilChanged`), время (`debounceTime`, `throttleTime`, `delay`), комбинирование (`merge`, `combineLatest`, `withLatestFrom`), ошибки (`catchError`, `retry`). Самый важный и самый частый вопрос — что делать, если на каждое событие нужно запустить асинхронную операцию.

## Стратегии выравнивания

На каждый поисковый запрос нужен HTTP-запрос — тоже поток. Получается поток потоков, и его нужно **выровнять** в один поток ответов. Вопрос в том, что делать, если новое событие пришло, пока старый запрос ещё идёт. Четыре оператора — четыре ответа.

Проверка на виртуальном времени RxJS: клики `a`, `b`, `c` в кадрах 0, 2 и 4, каждый запрос отвечает через 3 кадра.

| Оператор | Что делает с новым событием | Ответы | Когда использовать |
| --- | --- | --- | --- |
| `switchMap` | отменяет прошлый запрос | только `C` | поиск, автодополнение, переход по фильтрам |
| `mergeMap` | запускает параллельно | `A`, `B`, `C` | независимые операции, загрузка картинок |
| `concatMap` | ставит в очередь | `A`, `B`, `C` строго по очереди | сохранения, которые должны идти по порядку |
| `exhaustMap` | игнорирует, пока идёт текущий | только `A` | кнопка оплаты, вход, обновление токена |

Ошибка в выборе — источник реальных багов. `mergeMap` в поиске показывает результаты устаревшего запроса, если он ответил позже нового. `switchMap` на кнопке «Сохранить» отменяет предыдущее сохранение. `mergeMap` на кнопке оплаты отправляет два заказа при двойном клике.

`switchMap` отменяет не только подписку: если запрос сделан через `fetch` с `AbortSignal`, который срабатывает в функции очистки, браузер действительно прервёт соединение. Без этого отменяется только обработка ответа.

## Противодавление

Push-источник отдаёт значения в своём темпе. Если потребитель медленнее — датчик шлёт тысячу показаний в секунду, а график успевает нарисовать шестьдесят, — значения накапливаются в памяти или теряются. Задачу согласования скоростей называют **противодавлением** (backpressure).

Стратегии:

- **терять лишнее** — `throttleTime`, `auditTime`, `sampleTime`: брать одно значение за интервал. Для графиков и позиции мыши это правильно;
- **собирать пачками** — `bufferTime`: обработать сотню показаний за раз;
- **оставлять последнее** — `switchMap`: устаревшее неинтересно;
- **перейти на pull** — потребитель сам просит следующее значение.

Pull даёт противодавление «бесплатно». Асинхронный генератор не производит следующее значение, пока цикл `for await` его не попросил: в проверке медленный потребитель прочитал пять значений, и генератор произвёл ровно пять. На этом устроены потоки `fetch` и `ReadableStream` с их очередью и `highWaterMark` ([API браузера](/content/web/browser-apis)). Observable в RxJS — чистый push: `from` массива отдал все 1000 значений сразу.

## Потоки и сигналы

Потоки хорошо описывают **события**: что произошло и когда. Для **состояния** — что сейчас на экране — у них есть неприятная особенность. `combineLatest` выдаёт новую пару при изменении любого входа, и если оба входа зависят от одного источника, получается промежуточное значение, которого не должно быть:

```js
const a$ = new BehaviorSubject(1);
combineLatest([a$.pipe(map((x) => x * 2)), a$.pipe(map((x) => x + 1))]).subscribe(console.log);
a$.next(2);
// [2, 2], [4, 2], [4, 3] — пара [4, 2] не соответствует никакому a
```

Такое промежуточное значение называют **рывком** (glitch). Если его подписчик перерисовывает экран или отправляет запрос — это видимый баг. Сигналы решают проблему по-другому: производные значения пересчитываются после того, как все источники обновились, и эффект увидел только `[2, 2]` и `[4, 3]`. Как это устроено — в [Сигналах](/content/modern-dev/signals-and-reactivity).

Отсюда современное разделение труда: состояние интерфейса — в сигналах или реактивности фреймворка, события и асинхронные цепочки — в потоках. Angular так и устроен: HTTP-клиент и формы на RxJS, состояние компонентов — на сигналах, а `toSignal` и `toObservable` переводят одно в другое.

---

## Красные флаги в ответе

- **«Observable — это промис для нескольких значений».** Ещё и ленивый, и отменяемый, и обычно холодный: каждая подписка — свой запуск.
- **«`switchMap` и `mergeMap` — почти одно и то же».** Они по-разному обходятся с конкурирующими операциями, и неверный выбор даёт устаревшие результаты или двойные заказы.
- **«Отписываться не нужно, поток сам закончится».** Бесконечные потоки — интервалы, события, WebSocket — живут, пока не отпишешься, и держат замыкания.
- **«Реактивность — это RxJS»** или **«реактивность — это сигналы».** Это две разные модели: потоки событий и граф состояния.
- **«Два подписчика на HTTP-поток — один запрос».** Холодный поток запускается на каждую подписку; нужен `share` или `shareReplay`.

## Как спрашивают на собеседовании

::question
Что такое реактивное программирование?

#answer
Подход, при котором код объявляет зависимости между значениями, а среда сама распространяет изменения: поменялась цена — пересчитался итог и обновился экран. Пример вне программирования — формулы в таблице. Во фронтенде две модели: потоки событий во времени (RxJS) и граф состояния (сигналы, реактивность Vue).

#more
Реактивность заменяет ручную синхронизацию: не нужно помнить, в каких местах пересчитать производное значение. Цена — неявный поток управления: изменение запускает цепочку, которую не видно в месте присваивания, поэтому важны инструменты отладки и предсказуемый порядок обновлений.
::

::question
Чем Observable отличается от Promise?

#answer
Promise — одно значение, энергичный (выполняется при создании), общий для всех `then` и не отменяется. Observable — много значений во времени, ленивый (ничего не делает до подписки), обычно холодный (каждая подписка — свой запуск) и отменяемый через `unsubscribe` с функцией очистки.

#more
По таблице pull и push: функция и итератор — pull, промис и Observable — push; Observable — push для многих значений. Промис из Observable — `firstValueFrom` и `lastValueFrom`, обратно — `from(promise)`. Отмена в Observable отменяет обработку, а отмена самой операции требует `AbortSignal` в функции очистки.
::

::question
Чем холодный Observable отличается от горячего?

#answer
Холодный создаёт источник для каждого подписчика: два `subscribe` на HTTP-поток — два запроса. Горячий существует независимо от подписчиков, и они присоединяются к нему: клики, WebSocket. Опоздавший подписчик горячего потока пропускает прошлые значения.

#more
`share` делает холодный поток горячим: один запуск на всех текущих подписчиков, а когда все отписались — источник останавливается. `shareReplay(1)` ещё и отдаёт последнее значение опоздавшим — удобно для текущего пользователя и настроек, но без `refCount` держит подписку на источник вечно. `Subject` — горячий поток, в который можно писать вручную.
::

::question
Чем отличаются `switchMap`, `mergeMap`, `concatMap` и `exhaustMap`? Когда что использовать?

#answer
Все превращают каждое событие во внутренний поток и выравнивают результат, но по-разному обходятся с конкуренцией. `switchMap` отменяет прошлый внутренний поток — для поиска. `mergeMap` выполняет всё параллельно — для независимых операций. `concatMap` ставит в очередь — для сохранений по порядку. `exhaustMap` игнорирует новые события, пока идёт текущее, — для кнопки оплаты и входа.

#more
В проверке при кликах в кадрах 0, 2, 4 и ответах через 3 кадра: `switchMap` выдал только последний ответ, `mergeMap` — три вперемешку по времени, `concatMap` — три по очереди, `exhaustMap` — только первый. `mergeMap` принимает лимит параллельности вторым аргументом. Ошибки выбора: `mergeMap` в поиске показывает устаревшие результаты, `switchMap` на сохранении теряет данные.
::

::question
Что такое рывок (glitch) и почему его нет у сигналов?

#answer
Рывок — промежуточное несогласованное значение, когда производное значение пересчитывается после обновления одного источника, но до обновления другого. `combineLatest` двух потоков от одного источника на изменение источника выдаёт сначала пару с одним новым и одним старым значением. Сигналы помечают зависимые значения устаревшими и пересчитывают их, когда все источники уже обновлены, поэтому эффект видит только согласованное состояние.

#more
В проверке `combineLatest` выдал `[4, 2]` — пару, которой не соответствует ни одно значение источника, — а эффект на сигналах получил сразу `[4, 3]`. Поэтому потоки берут для событий и асинхронных цепочек, а состояние интерфейса — в сигналах или реактивности фреймворка.
::

::question
Что такое противодавление?

#answer
Ситуация, когда источник производит данные быстрее, чем потребитель их обрабатывает. В push-модели значения копятся или теряются; нужно выбрать стратегию: терять лишнее (`throttleTime`, `sampleTime`), собирать пачками (`bufferTime`), брать последнее (`switchMap`) или перейти на pull.

#more
В pull-модели противодавление встроено: асинхронный генератор не производит следующее значение, пока потребитель не попросил. Потоки `fetch` и `ReadableStream` используют очередь с `highWaterMark` и вызывают `pull`, только когда в ней есть место. В RxJS противодавления нет: это чистый push, и стратегию выбирают операторами.
::

::question
Как не допустить утечек подписок?

#answer
Отписываться, когда подписчик больше не нужен: при размонтировании компонента, уходе со страницы, закрытии модалки. Удобнее не хранить подписки по одной, а завершать поток оператором: `takeUntil(destroy$)`, `take(1)`, `first()`.

#more
Фреймворки делают это за тебя: `async` pipe и `takeUntilDestroyed` в Angular, `toSignal` отписывается вместе с контекстом. Во Vue и React подписку оформляют в `onUnmounted` или в функции очистки эффекта. Потоки, которые завершаются сами, — один HTTP-запрос — отписки не требуют, но бесконечные — интервалы, события, WebSocket — требуют всегда.
::

## Практика

::practice{title="Автодополнение показывает чужие результаты"}
Поиск по каталогу написан так:

```js
fromEvent(input, 'input').pipe(
  map((e) => e.target.value),
  mergeMap((q) => searchApi(q)),
).subscribe(render);
```

Пользователь быстро набирает «улун», а в списке иногда остаются результаты по «улу». Кроме того, сервер получает запрос на каждую букву. Как исправить?

#solution
`mergeMap` выполняет все запросы параллельно и отдаёт ответы в порядке прихода. Если запрос «улу» ответил позже запроса «улун», его результаты перерисуют список последними. Каждая буква — отдельный запрос, потому что нет паузы и фильтров.

```js
fromEvent(input, 'input').pipe(
  map((e) => e.target.value.trim()),
  debounceTime(300),                 // ждём паузу в наборе
  filter((q) => q.length >= 2),
  distinctUntilChanged(),            // тот же запрос повторно не отправляем
  switchMap((q) => searchApi(q)),    // новый запрос отменяет прошлый
).subscribe(render);
```

В проверке на виртуальном времени медленный запрос «улу» был отменён, когда пришёл «улун», повторный ввод «улу» не дошёл до сервера, и на экран попали только результаты «улун». Чтобы отменялся и сам HTTP-запрос, `searchApi` должен возвращать Observable, который вызывает `abort()` в функции очистки.
::

::practice{title="Двойной заказ при двойном клике"}
```js
fromEvent(payButton, 'click').pipe(
  mergeMap(() => createOrder(cart)),
).subscribe(showReceipt);
```

Нетерпеливые пользователи нажимают «Оплатить» дважды и получают два заказа. Какой оператор нужен?

#solution
`exhaustMap`: пока идёт создание заказа, новые клики игнорируются. `switchMap` здесь опасен — он отменит обработку первого заказа, но сам заказ на сервере уже мог создаться. `concatMap` создаст второй заказ после первого.

```js
fromEvent(payButton, 'click').pipe(
  exhaustMap(() => createOrder(cart)),
).subscribe(showReceipt);
```

В проверке клики, пришедшие до завершения первого запроса, были проигнорированы. Защита на клиенте не заменяет защиту на сервере: заказ создают с ключом идемпотентности, чтобы повтор запроса — из-за сети или второй вкладки — не создал дубль.
::

::practice{title="Два одинаковых запроса"}
Шапка и страница профиля подписаны на данные пользователя:

```js
const user$ = http.get('/api/me');
header.bind(user$);
profile.bind(user$);
```

В Network два одинаковых запроса `/api/me`. Почему и как сделать один?

#solution
`user$` — холодный Observable: каждая подписка запускает его заново и отправляет свой запрос. Нужен общий запуск:

```js
const user$ = http.get('/api/me').pipe(shareReplay({ bufferSize: 1, refCount: true }));
```

`share` дал бы один запрос для тех, кто подписан одновременно; `shareReplay(1)` ещё и отдаст ответ тем, кто подпишется позже, — например, странице, открытой после шапки. В проверке без `share` было два запроса, с `share` — один, а опоздавший подписчик `shareReplay` получил значение без нового запроса. `refCount: true` останавливает источник, когда подписчиков не осталось.
::
