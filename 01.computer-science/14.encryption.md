# Криптография

Криптография даёт три гарантии: никто посторонний не прочитает данные (конфиденциальность), никто не изменит их незаметно (целостность) и известно, кто их отправил (подлинность). Для этого есть всего несколько инструментов: хеш, симметричный шифр, обмен ключами и подпись — HTTPS, токены, пароли и подписи вебхуков собраны из них. Спрашивают, чем кодирование отличается от хеширования и шифрования, как хранить пароли и как работает HTTPS. Глубже — зачем соль и медленный хеш, почему AES-GCM, а не просто AES, и что такое прямая секретность.

::tldr
- **Кодирование обратимо без ключа, хеш необратим, шифрование обратимо только с ключом.** Base64 ничего не скрывает, SHA-256 нельзя «расшифровать», AES без ключа не прочитать.
- **Пароли хранят медленным хешем с солью** — argon2, scrypt, bcrypt, PBKDF2 с большим числом итераций. Быстрый SHA-256 без соли подбирается за минуты по словарю.
- **Симметричный шифр быстрый, но требует общего ключа; асимметричная криптография решает, как договориться о ключе и как подписать.** На практике их сочетают: TLS договаривается об общем ключе через ECDH и шифрует AES-GCM.
- **Шифрование без проверки целостности — ошибка.** AEAD-режимы вроде AES-GCM шифруют и обнаруживают подмену; nonce для одного ключа никогда не повторяют.
- **HTTPS защищает данные в пути, а не на концах.** Сертификат доказывает, что ты говоришь с владельцем домена; эфемерные ключи дают прямую секретность — украденный ключ сервера не раскроет прошлый трафик.
::

## Кодирование, хеширование, шифрование

Сквозной пример — интернет-магазин: пароли покупателей, адрес доставки в заметке к заказу, вебхук от платёжного сервиса, HTTPS и обновления приложения.

Три слова часто путают, а это разные вещи:

| | Обратимо? | Нужен ключ? | Зачем |
| --- | --- | --- | --- |
| **кодирование** (Base64, UTF-8, URL-кодирование) | да | нет | представить данные в другом формате |
| **хеширование** (SHA-256) | нет | нет | отпечаток данных фиксированной длины |
| **шифрование** (AES, RSA) | да | да | скрыть данные от тех, у кого нет ключа |

Base64 только меняет алфавит — его декодирует кто угодно. Поэтому «закодированный» пароль в `localStorage` и «зашифрованный» Base64 токен — это открытый текст ([Представление данных](/content/computer-science/data-representation)).

Ещё один инструмент — **подпись**: она не скрывает данные, а доказывает, кто их создал и что они не изменены. На ней держатся JWT, сертификаты и проверка обновлений.

## Хеш-функции

Криптографическая **хеш-функция** превращает данные любой длины в отпечаток фиксированной длины: у SHA-256 это 256 бит, 64 шестнадцатеричных символа, — и для строки `abc`, и для мегабайта нулей. Её свойства:

- **детерминированность** — одинаковый вход даёт одинаковый хеш;
- **лавинный эффект** — изменение одного символа меняет около половины битов. В проверке хеши строк «заказ 1000» и «заказ 1001» различались примерно в половине из 256 битов;
- **необратимость** — по хешу нельзя найти вход иначе как перебором;
- **стойкость к коллизиям** — нельзя найти два разных входа с одинаковым хешем.

MD5 и SHA-1 больше не стойки к коллизиям: для них умеют строить пары документов с одинаковым хешем. Для новых задач — SHA-256 и новее.

Где хеши во фронтенде: хеш содержимого в именах файлов сборки для кеширования ([Введение в тулинг](/content/advanced-tooling/introduction)), проверка целостности скриптов с :term[CDN]{def="сеть серверов по миру, которая отдаёт файлы с ближайшего к пользователю"} через атрибут `integrity` ([Цепочка поставок](/content/security-perfomance/supply-chain-and-vulnerabilities)), :term[ETag]{def="заголовок HTTP с отпечатком версии ресурса, по которому браузер проверяет кеш"}, дедупликация файлов.

```js
const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode('abc'));
// ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
```

### Пароли

Хранить пароль открытым текстом нельзя: утечка базы раскроет все пароли, а люди повторяют их на других сайтах. Хранить SHA-256 от пароля — почти так же плохо, и по двум причинам:

1. **одинаковые пароли дают одинаковые хеши.** Миллион пользователей с паролем `qwerty` видны одной строкой, а для популярных паролей хеши заранее посчитаны в таблицах;
2. **SHA-256 быстрый.** Видеокарта перебирает миллиарды вариантов в секунду, и словарь из популярных паролей проверяется за минуты.

Поэтому пароли хешируют иначе:

- **соль** — случайная строка, уникальная для каждого пароля и хранящаяся рядом с хешем. В проверке два одинаковых пароля с разной солью дали разные хеши, и заготовленные таблицы бесполезны;
- **медленная функция** — argon2id, scrypt, bcrypt или PBKDF2 с сотнями тысяч итераций. Она нарочно тратит время и память: в проверке scrypt считал один хеш в сотни раз дольше, чем SHA-256. Для входа пользователя это незаметно, для перебора миллиардов вариантов — смертельно;
- **сравнение за постоянное время** — `crypto.timingSafeEqual`, чтобы время ответа не подсказывало, сколько первых байтов совпало.

Пароли хеширует сервер. Хеширование на клиенте перед отправкой ничего не добавляет: хеш просто становится новым паролем. Как строить вход и хранить сессии — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens).

### HMAC

**HMAC** — хеш с секретным ключом: `HMAC(ключ, сообщение)`. Подделать его без ключа нельзя, поэтому HMAC подтверждает и целостность, и то, что сообщение создал владелец ключа. Так платёжные сервисы подписывают вебхуки: присылают тело и подпись в заголовке, а сервер магазина пересчитывает HMAC тем же общим секретом и сравнивает. В проверке подменённый статус заказа с `paid` на `refunded` не прошёл проверку подписи.

## Симметричное шифрование

**Симметричный** шифр шифрует и расшифровывает одним ключом. Стандарт — **AES** с ключом 128 или 256 бит: он быстрый, в процессорах есть аппаратные инструкции для него. Альтернатива для устройств без таких инструкций — :term[ChaCha20]{def="быстрый потоковый шифр, которому не нужна аппаратная поддержка, в отличие от AES"}.

Сам по себе AES шифрует блок из 16 байт, а для сообщений любой длины нужен **режим работы**. Старые режимы вроде CBC только скрывают данные: шифротекст можно испортить или подменить, и получатель расшифрует мусор, не заметив подвоха. Современный выбор — **AEAD**-режимы (authenticated encryption with associated data), которые шифруют и проверяют целостность одновременно. Главный — **AES-GCM**:

```js
const key = await crypto.subtle.generateKey({ name: 'AES-GCM', length: 256 }, false, ['encrypt', 'decrypt']);
const iv = crypto.getRandomValues(new Uint8Array(12));        // nonce: уникален для каждого сообщения
const sealed = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, data);
```

К шифротексту добавляется 16-байтный тег. В проверке изменение одного бита шифротекста привело к тому, что `decrypt` отклонился с `OperationError` вместо того, чтобы вернуть испорченные данные.

Главное правило GCM — **nonce не повторяется** для одного ключа. В проверке одинаковые ключ и nonce дали для одинаковых сообщений одинаковый шифротекст — так наблюдатель видит, что сообщения совпадают. Повтор nonce на разных сообщениях хуже: он раскрывает связь между открытыми текстами и позволяет подделывать теги. Поэтому nonce генерируют случайно для каждого сообщения или ведут счётчик.

Проблема симметричного шифра — **ключ**. Браузер и сервер магазина впервые видят друг друга; как им получить общий ключ, если канал прослушивается?

## Асимметричная криптография

В **асимметричной** криптографии у каждого пара ключей: **закрытый** хранится у владельца, **открытый** можно показывать всем. Что сделано одним, проверяется или отменяется другим. Это решает две задачи.

### Обмен ключами

Протокол **Диффи — Хеллмана** позволяет двум сторонам получить общий секрет, обменявшись только открытыми ключами. Наблюдатель видит оба открытых ключа, но вычислить секрет не может. Современный вариант на эллиптических кривых — **ECDH**, чаще всего на кривой X25519.

```js
const s1 = await crypto.subtle.deriveBits({ name: 'ECDH', public: bob.publicKey }, alice.privateKey, 256);
const s2 = await crypto.subtle.deriveBits({ name: 'ECDH', public: alice.publicKey }, bob.privateKey, 256);
// s1 и s2 совпадают
```

### Подпись

Подпись делается закрытым ключом, а проверяется открытым — значит, проверить может кто угодно, а подписать — только владелец. Алгоритмы: **Ed25519** и **ECDSA** на эллиптических кривых, **RSA** — старый и с длинными ключами. В проверке изменённое имя файла обновления не прошло проверку подписи обоими алгоритмами.

Подписи стоят за сертификатами TLS, обновлениями приложений, коммитами в git, passkeys и JWT. Важно: подписанный JWT не зашифрован — его содержимое читает любой. Как проверяют JWT и где хранят токены — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens).

Асимметричные операции в сотни раз медленнее AES, поэтому ими не шифруют данные, а договариваются о ключе и подписывают. Всё вместе работает в HTTPS.

## TLS и HTTPS

HTTPS — это HTTP поверх **TLS**. Рукопожатие TLS 1.3 за один круг сообщений решает три задачи:

1. **Обмен ключами.** Клиент сразу присылает свой эфемерный открытый ключ ECDH, сервер — свой. Обе стороны вычисляют общий секрет и выводят из него ключи шифрования.
2. **Подлинность сервера.** Сервер присылает сертификат и подписывает рукопожатие закрытым ключом из сертификата. Клиент проверяет подпись и то, что сертификат выдан на этот домен доверенным центром сертификации.
3. **Шифрование.** Дальше весь трафик идёт через AEAD-шифр: AES-GCM или ChaCha20-Poly1305.

В проверке на локальном сервере с самоподписанным сертификатом:

- клиент без доверия к сертификату отказался соединяться — `DEPTH_ZERO_SELF_SIGNED_CERT`;
- с явно доверенным сертификатом договорились о TLS 1.3 и шифре `TLS_AES_256_GCM_SHA384`, а `openssl s_client` показал эфемерную группу X25519;
- запрос по другому имени отклонён — `ERR_TLS_CERT_ALTNAME_INVALID`: сертификат выдан на `shop.test`.

### Сертификаты и цепочка доверия

**Сертификат** — открытый ключ сервера и имя домена, подписанные центром сертификации (CA). Подпись центра подтверждена сертификатом промежуточного центра, тот — корневого, а корневые сертификаты заранее встроены в браузер и ОС. Браузер проходит эту цепочку до доверенного корня; если звено не сходится, срок истёк или имя не совпадает, — страница ошибки. Let's Encrypt выдаёт сертификаты бесплатно и автоматически, проверяя, что ты управляешь доменом.

### Прямая секретность

Ключи обмена в TLS 1.3 **эфемерные**: новые для каждого соединения и выбрасываются после него. Ключ из сертификата используется только для подписи. Поэтому даже если закрытый ключ сервера украдут через год, записанный трафик прошлых сессий не расшифровать — это **прямая секретность** (forward secrecy). В старом TLS с обменом ключами через RSA её не было.

> **Актуально на ноябрь 2026:** браузеры по умолчанию используют гибридный обмен ключами X25519MLKEM768 — классический X25519 плюс постквантовый ML-KEM. Chrome включил его в версии 131; в проверке OpenSSL 3.6 выбрал ту же группу. Цель — чтобы трафик, записанный сегодня, не расшифровали будущие квантовые компьютеры.

### Что HTTPS не защищает

HTTPS шифрует данные **в пути**. Он не защищает от :term[XSS]{def="межсайтовый скриптинг: чужой скрипт попадает на страницу через непроверенные данные"} на странице, от утечки базы на сервере, от вредоносного расширения в браузере и не скрывает, с каким доменом ты соединяешься. Заголовки, которые заставляют браузер всегда ходить по HTTPS (HSTS), — в [CSP и заголовках безопасности](/content/security-perfomance/csp-and-security-headers), а сетевая сторона рукопожатия — в [Основах сетей](/content/network-api/networking-fundamentals).

## Криптография в браузере

**Web Crypto API** (`crypto.subtle`) даёт хеши, HMAC, AES-GCM, ECDH, подписи и вывод ключей из пароля. Он работает только в безопасном контексте — по HTTPS или на `localhost` ([Что такое веб](/content/web/what-is-web)).

- **Ключи можно сделать неизвлекаемыми** (`extractable: false`): операции с ними работают, а выгрузить их нельзя — `exportKey` отклоняется. Такой `CryptoKey` можно сохранить в :term[IndexedDB]{def="встроенная в браузер транзакционная база объектов с индексами"}, и XSS-скрипт сможет им пользоваться, пока страница открыта, но не унесёт сам ключ.
- **Случайность** — только `crypto.getRandomValues` и `crypto.randomUUID`. `Math.random` предсказуем и не годится для токенов, кодов и nonce.
- **Свою криптографию не пишут.** Даже правильные алгоритмы ломаются на деталях: повторный nonce, сравнение через `===`, отсутствие проверки целостности. Используют Web Crypto или проверенные библиотеки.

Клиентское шифрование полезно для сквозного шифрования (end-to-end): данные шифруются ключом пользователя до отправки, и сервер хранит то, что не может прочитать. Но если JavaScript-код приходит с того же сервера, защита держится на честности этого кода — поэтому такие приложения отдельно защищают доставку скриптов.

## Красные флаги в ответе

- **«Пароль зашифрован в Base64»** или **«токен зашифрован, это же JWT».** Base64 — кодирование, подписанный JWT читается кем угодно.
- **«Пароли храним SHA-256 — это же необратимо».** Быстрый хеш без соли подбирается по словарю; нужны соль и медленная функция вроде argon2id.
- **«Захешируем пароль на клиенте, чтобы не передавать его открыто».** Хеш становится паролем; защищает передачу HTTPS, а хранение — сервер.
- **«Шифруем AES, значит данные защищены от подмены».** Режимы без аутентификации подмену не замечают; нужен AEAD — AES-GCM.
- **«HTTPS защищает от XSS» или «HTTPS скрывает, на какой сайт я зашёл».** Он защищает данные в пути; имя сервера и IP видны.
- **«`Math.random` хватит для кода подтверждения».** Нужен криптографический генератор `crypto.getRandomValues`.

## Как спрашивают на собеседовании

::question
Чем кодирование отличается от хеширования и шифрования?

#answer
Кодирование меняет представление данных и обратимо без ключа: Base64, UTF-8, URL-кодирование. Хеширование превращает данные в отпечаток фиксированной длины и необратимо: SHA-256. Шифрование обратимо только с ключом: AES, RSA. Отдельно — подпись: она не скрывает данные, а доказывает автора и целостность.

#more
Отсюда типичные ошибки: Base64 как «шифрование» токена, хеш вместо шифрования там, где данные нужно восстановить, и шифрование там, где нужно сравнение — паролю нужен хеш, а не шифр, потому что расшифровывать его не нужно никогда.
::

::question
Как правильно хранить пароли?

#answer
Медленной функцией хеширования паролей с уникальной солью для каждого: argon2id, scrypt, bcrypt или PBKDF2 с сотнями тысяч итераций. Соль делает одинаковые пароли разными хешами и обесценивает заготовленные таблицы, а медленная функция делает перебор дорогим. При входе хеш пересчитывают и сравнивают за постоянное время.

#more
Быстрый SHA-256 даже с солью перебирается видеокартами со скоростью миллиардов вариантов в секунду. В проверке scrypt был в сотни раз медленнее SHA-256 — для одного входа это миллисекунды, для перебора — годы. Параметры функции хранят рядом с хешем, чтобы со временем их усиливать. Хеширование на клиенте ничего не даёт: хеш становится паролем.
::

::question
Почему AES-GCM, а не просто AES? Что такое nonce?

#answer
AES шифрует блоки по 16 байт, и для сообщений нужен режим работы. Старые режимы вроде CBC не проверяют целостность: подменённый шифротекст расшифруется в мусор без ошибки. GCM — AEAD-режим: шифрует и добавляет тег, по которому подмена обнаруживается. Nonce — уникальное для каждого сообщения значение, которое делает шифротекст одинаковых сообщений разным.

#more
В проверке изменение одного бита шифротекста дало `OperationError` при расшифровке, а одинаковые ключ и nonce дали одинаковый шифротекст для одинаковых сообщений. Повтор nonce в GCM на разных сообщениях позволяет связать открытые тексты и подделывать теги, поэтому nonce берут случайный 96-битный или счётчик. Альтернатива AES без аппаратной поддержки — ChaCha20-Poly1305.
::

::question
Как работает HTTPS?

#answer
Это HTTP поверх TLS. В рукопожатии TLS 1.3 клиент и сервер обмениваются эфемерными открытыми ключами ECDH и вычисляют общий секрет. Сервер присылает сертификат и подписывает рукопожатие его закрытым ключом, а клиент проверяет подпись, имя домена и цепочку до доверенного корневого центра. Дальше трафик шифруется симметричным AEAD-шифром.

#more
TLS 1.3 укладывается в один круг сообщений, а при повторном соединении может отправить данные сразу. Эфемерные ключи дают прямую секретность: украденный позже ключ сертификата не раскроет прошлый трафик. HTTPS не скрывает имя сервера и не защищает от XSS и утечек на концах.
::

::question
Что такое цифровая подпись и чем она отличается от HMAC?

#answer
Подпись создаётся закрытым ключом и проверяется открытым: подписать может только владелец, проверить — кто угодно. HMAC использует один общий секрет: подписать и проверить могут только те, у кого он есть. Подпись подходит, когда проверяющих много или им нельзя доверять секрет: сертификаты, обновления, JWT для сторонних сервисов. HMAC — когда две стороны делят секрет: вебхуки, сессионные токены своего сервера.

#more
Подпись даёт неотказуемость — автор не может отрицать, что подписал, потому что ключ был только у него. HMAC этого не даёт: ключ есть у обеих сторон. Алгоритмы подписи — Ed25519, ECDSA, RSA; в JWT им соответствуют `EdDSA`, `ES256` и `RS256`, а HMAC — `HS256`.
::

::question
Что такое прямая секретность?

#answer
Свойство протокола, при котором утечка долгосрочного ключа не раскрывает прошлые сессии. В TLS 1.3 ключи обмена эфемерные — новые для каждого соединения, — а ключ сертификата только подписывает рукопожатие. Записанный трафик нельзя расшифровать, даже получив позже закрытый ключ сервера.

#more
В старом TLS с обменом ключами через RSA клиент шифровал секрет открытым ключом сертификата, и утечка закрытого ключа раскрывала весь записанный трафик. Поэтому TLS 1.3 оставил только эфемерные варианты. Та же логика стоит за переходом на гибридный постквантовый обмен ключами: защититься от «записать сейчас, расшифровать потом».
::

## Практика

::practice{title="Подпись вебхука не сходится"}
Платёжный сервис подписывает вебхуки HMAC-SHA256 по телу запроса. Сервер магазина проверяет так:

```js
app.post('/webhook', express.json(), (req, res) => {
  const expected = createHmac('sha256', SECRET).update(JSON.stringify(req.body)).digest('hex');
  if (expected !== req.headers['x-signature']) return res.sendStatus(401);
  markPaid(req.body.order);
  res.sendStatus(200);
});
```

Часть настоящих вебхуков отклоняется. Найди две проблемы.

#solution
1. Подпись считается по `JSON.stringify(req.body)`, а сервис подписывал **сырые байты** тела. После разбора и сериализации пропадают пробелы, меняется порядок или формат чисел — байты другие, подпись не сходится. В проверке тело с пробелами и переводом строки после пересборки не прошло проверку.
2. Сравнение через `!==` останавливается на первом несовпавшем символе, и время ответа подсказывает, сколько символов угадано. Нужно сравнение за постоянное время.

```js
app.post('/webhook', express.raw({ type: 'application/json' }), (req, res) => {
  const expected = Buffer.from(createHmac('sha256', SECRET).update(req.body).digest('hex'));
  const got = Buffer.from(String(req.headers['x-signature'] ?? ''));
  if (got.length !== expected.length || !timingSafeEqual(got, expected)) return res.sendStatus(401);

  const event = JSON.parse(req.body);
  markPaid(event.order);
  res.sendStatus(200);
});
```

`timingSafeEqual` требует буферов одинаковой длины, поэтому длину проверяют заранее. Хорошие сервисы добавляют в подпись метку времени, а сервер отклоняет старые вебхуки — защита от повторной отправки.
::

::practice{title="Пароли в базе — SHA-256"}
В старом сервисе пароли хранятся как `sha256(password)`. Что не так и как перейти на правильную схему, не заставляя всех сменить пароль?

#solution
Одинаковые пароли дают одинаковые хеши, а SHA-256 быстрый: после утечки базы популярные пароли подбираются по словарю за минуты. Нужны соль и медленная функция.

```js
import { scrypt, randomBytes, timingSafeEqual } from 'node:crypto';
import { promisify } from 'node:util';
const scryptAsync = promisify(scrypt);

async function hashPassword(password) {
  const salt = randomBytes(16);
  const hash = await scryptAsync(password, salt, 32);
  return `scrypt$${salt.toString('hex')}$${hash.toString('hex')}`;
}

async function verifyPassword(password, stored) {
  const [, saltHex, hashHex] = stored.split('$');
  const hash = await scryptAsync(password, Buffer.from(saltHex, 'hex'), 32);
  return timingSafeEqual(hash, Buffer.from(hashHex, 'hex'));
}
```

Миграция без сброса паролей: при следующем успешном входе, когда пароль известен, пересчитать хеш новой схемой и сохранить. Чтобы не ждать входа всех, старые хеши сразу оборачивают: `scrypt(sha256(password))` — тогда слабых хешей в базе не остаётся. Асинхронный `scrypt` выполняется в пуле потоков и не блокирует главный поток.
::

::practice{title="Заметки, которые не может прочитать сервер"}
Нужно хранить личные заметки покупателя на сервере так, чтобы сервер не мог их прочитать: ключ получается из пароля, который знает только пользователь. Напиши шифрование и расшифровку на Web Crypto.

#solution
Ключ выводят из пароля медленной функцией с солью, шифруют AES-GCM со свежим IV. Соль и IV не секретны — их хранят рядом с шифротекстом.

```js
async function keyFromPassword(password, salt) {
  const base = await crypto.subtle.importKey('raw', new TextEncoder().encode(password), 'PBKDF2', false, ['deriveKey']);
  return crypto.subtle.deriveKey(
    { name: 'PBKDF2', salt, iterations: 600_000, hash: 'SHA-256' },
    base,
    { name: 'AES-GCM', length: 256 },
    false,                                   // неизвлекаемый
    ['encrypt', 'decrypt'],
  );
}

async function encryptNote(text, password) {
  const salt = crypto.getRandomValues(new Uint8Array(16));
  const iv = crypto.getRandomValues(new Uint8Array(12));
  const key = await keyFromPassword(password, salt);
  const data = await crypto.subtle.encrypt({ name: 'AES-GCM', iv }, key, new TextEncoder().encode(text));
  return { salt, iv, data: new Uint8Array(data) };
}

async function decryptNote({ salt, iv, data }, password) {
  const key = await keyFromPassword(password, salt);
  return new TextDecoder().decode(await crypto.subtle.decrypt({ name: 'AES-GCM', iv }, key, data));
}
```

В проверке неверный пароль дал `OperationError` — GCM обнаружил, что ключ не тот. 600 000 итераций — рекомендация OWASP для PBKDF2-SHA256. Ограничения схемы: забытый пароль — потерянные заметки, а защита держится на том, что сервер отдаёт честный JavaScript.
::
