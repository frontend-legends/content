# Как выполняется программа

Код разобран и скомпилирован — дальше он выполняется: операционная система запускает процесс, рантайм готовит окружение, функции вызывают друг друга через стек, исключения раскручивают его, а в конце процесс завершается с кодом выхода. Спрашивают, что происходит при запуске `node app.js`, что такое стек вызовов и кадр, когда процесс Node.js завершается сам. Глубже — почему глубина рекурсии разная для разных функций, почему в стеке ошибки из таймера нет вызывающего кода и как остановить сервер, не потеряв запросы.

::tldr
- **Запуск — это цепочка:** ОС создаёт процесс, рантайм поднимает движок и цикл событий, код разбирается и компилируется, выполняется верхний уровень модуля, а дальше работают обработчики событий.
- **Каждый вызов кладёт в стек кадр:** аргументы, локальные переменные, адрес возврата. Стек — фиксированный кусок памяти, поэтому глубина рекурсии зависит от размера кадров.
- **Стек ошибки собирается в момент создания `Error`.** `await` сохраняет асинхронную цепочку вызовов, а колбэк таймера или события начинается с пустого стека.
- **Процесс Node.js завершается сам, когда в цикле событий не осталось работы.** Таймеры, сокеты и серверы держат его; `unref()` отпускает.
- **Код выхода — ответ программы окружению:** 0 — успех, 1 — необработанная ошибка, 128 + номер сигнала — процесс убит. По нему CI решает, упала ли сборка, а оркестратор — перезапускать ли контейнер.
::

## От файла до процесса

Сквозной пример — скрипт ночного отчёта `report.js` на Node.js: он читает заказы из базы, считает выручку и отправляет письмо. Его запускает cron, а в другом режиме тот же код работает как HTTP-сервер.

Что происходит после `node report.js`:

1. **ОС создаёт процесс:** выделяет адресное пространство, загружает исполняемый файл `node` и передаёт управление его точке входа. Процессы и их память — в [Архитектуре ОС](/content/computer-science/os-architecture).
2. **Рантайм поднимает окружение:** движок V8, цикл событий libuv, пул потоков, глобальные объекты `process`, `Buffer`, `fetch`. Чем движок отличается от рантайма — в [Введении в JavaScript](/content/javascript/introduction).
3. **Код загружается и компилируется:** файл читается, разбирается в дерево, переводится в байткод. Как это работает — в [Языках и компиляторах](/content/computer-science/languages-and-compilers).
4. **Выполняется верхний уровень модуля** — от первой строки до последней, синхронно.
5. **Работает цикл событий:** вызывает обработчики таймеров, сокетов, промисов, пока работа не кончится.
6. **Процесс завершается** с кодом выхода.

В браузере первые шаги похожи — процесс рендерера, движок, разбор скрипта, — но шестого шага нет: страница живёт, пока пользователь не ушёл. Скрипт там выполняет верхний уровень и дальше только реагирует на события.

Пока код выполняется, функции вызывают друг друга. Как процессор помнит, куда вернуться?

## Стек вызовов

Каждый вызов функции кладёт в **стек вызовов** **кадр** (stack frame): аргументы, локальные переменные, адрес инструкции, к которой нужно вернуться, и сохранённые регистры. Возврат снимает кадр и продолжает выполнение по адресу возврата. Как именно аргументы передаются через регистры и стек, договорено в **соглашении о вызовах** платформы — это часть ABI, двоичного интерфейса, по которому код из разных компиляторов может вызывать друг друга.

Для отчёта стек в момент запроса к базе выглядит так:

```text
query            ← выполняется сейчас
loadOrders
buildReport
main
(верхний уровень модуля)
```

Стек — это не абстракция, а кусок памяти фиксированного размера: в Node.js около мегабайта, флаг `--stack-size` задаёт его в килобайтах. Значит, предельная глубина рекурсии — это размер стека, делённый на размер кадра. В проверке:

| Функция | Глубина до переполнения |
| --- | --- |
| `function f() { d++; f(); }` | около 10 000 |
| та же с четырьмя аргументами и локальной переменной | около 6 000 |
| первая с `--stack-size=200` | около 2 000 |

Поэтому «максимальная глубина рекурсии в JavaScript» — не константа: она зависит от функции, движка и платформы. Переполнение — `RangeError: Maximum call stack size exceeded`. Как заменять рекурсию циклом с явным стеком и почему хвостовые вызовы в V8 не спасают — в [Функциях](/content/javascript/functions).

Стек раскручивается не только возвратом. Исключение снимает много кадров сразу.

## Исключения и раскрутка стека

`throw` прерывает текущую функцию и снимает кадры один за другим, пока не найдёт `try` с подходящим `catch`. По пути выполняются блоки `finally`. Если обработчика нет до самого дна стека, ошибка становится необработанной, и окружение решает, что делать: браузер пишет её в консоль и вызывает `window.onerror`, Node.js завершает процесс. Правила `try`, `catch` и `finally` — в [Обработке ошибок](/content/javascript/error-handling).

### Откуда берётся стек ошибки

Свойство `stack` — снимок стека вызовов в момент **создания** объекта ошибки, а не в момент `throw`:

```js
const e = new Error('создана здесь');
function thrower() { throw e; }
try { thrower(); } catch (x) { x.stack; } // указывает на строку с new Error, thrower в стеке нет
```

В V8 снимок по умолчанию хранит 10 кадров — `Error.stackTraceLimit`. Ошибка в глубокой рекурсии покажет только 10 верхних вызовов.

### Асинхронный стек

Колбэк таймера, событие и ответ сети запускаются циклом событий с пустого стека: вызывающей функции к этому моменту давно нет. В проверке ошибка из `setTimeout` внутри `load()`, вызванной из `page()`, показала в стеке только колбэк и внутренние функции таймеров — ни `load`, ни `page`.

С `await` иначе. V8 восстанавливает цепочку асинхронных функций, которые ждут друг друга, и помечает её словом `async`:

```text
Error: в load
    at load ([eval]:1:42)
    at async page ([eval]:1:88)
```

Отсюда практическое правило для отчёта и любых сервисов: цепочки на `async`/`await` дают в Sentry полезные стеки, а колбэки и `.then` без `await` — обрывки. Где стека не хватает, ошибку оборачивают с `cause`, передавая контекст явно.

Отчёт посчитан, письмо отправлено. Почему процесс завершился, а сервер с тем же кодом — нет?

## Когда программа завершается

Процесс Node.js завершается сам, когда в цикле событий не осталось ничего, что может вызвать код: таймеров, открытых сокетов, серверов, незавершённых операций с файлами. Промис, который ждёт сам по себе, процесс не держит — держит только источник события, который его разрешит.

```js
console.log('a');
setTimeout(() => console.log('timer'), 30);
process.on('beforeExit', () => console.log('beforeExit'));
process.on('exit', (code) => console.log('exit', code));
console.log('b');
// a, b, timer, beforeExit, exit 0
```

- **`beforeExit`** — цикл опустел. Обработчик может запланировать новую работу, и процесс продолжит жить.
- **`exit`** — процесс уже завершается. Обработчик выполняется синхронно; таймер, поставленный в нём, не сработает никогда.
- **`unref()`** у таймера или сокета говорит «не держи процесс из-за меня»: `setTimeout(fn, 5000).unref()` не помешает скрипту закончиться.

Отсюда же «зависший» скрипт отчёта: незакрытый пул соединений с базой держит сокеты, и процесс не завершается, хотя работа сделана.

### Коды выхода

Код выхода — число, которым процесс сообщает окружению результат. Его читают оболочка (`$?`), CI, cron, Docker и Kubernetes.

| Код | Когда |
| --- | --- |
| 0 | цикл опустел, ошибок не было |
| 1 | необработанное исключение или необработанное отклонение промиса |
| любой | `process.exitCode = n` — завершиться с этим кодом, когда работа закончится |
| 128 + n | процесс убит сигналом n, без обработчика: SIGTERM (15) — 143, SIGKILL (9) — 137 |

`process.exitCode` предпочтительнее `process.exit(n)`: `exit` обрывает процесс сразу, и недописанный вывод, неотправленные логи и незакрытые соединения теряются.

### Сигналы и корректная остановка

При деплое оркестратор посылает процессу **SIGTERM** — просьбу завершиться — и через некоторое время **SIGKILL**, который перехватить нельзя. Без обработчика SIGTERM Node.js умирает сразу, и запросы, которые обрабатывались в этот момент, обрываются. В проверке оболочка увидела код 143.

С обработчиком сервер останавливается корректно (graceful shutdown): перестаёт принимать новые соединения, дожидается текущих запросов, закрывает базу и выходит с кодом 0. Как сигналы доставляет ОС — в [Архитектуре ОС](/content/computer-science/os-architecture), как это настраивают в контейнере — в [Docker](/content/testing-deploying/containers-and-docker).

## Красные флаги в ответе

- **«Максимальная глубина рекурсии в JavaScript — 10 000».** Она зависит от размера кадра, движка и размера стека: в проверке одна функция падала на 10 000, другая — на 6 000.
- **«Стек ошибки показывает, где её бросили».** Он показывает, где создан объект `Error`. Ошибку, созданную заранее и брошенную позже, это запутает.
- **«Асинхронный код теряет стек всегда».** Через `await` V8 восстанавливает цепочку `async`-функций; теряют стек колбэки таймеров и событий.
- **«Node.js завершается, когда выполнится последняя строка».** Он завершается, когда в цикле событий не осталось работы; открытый сокет или таймер держат процесс.
- **«`process.exit()` — нормальный способ закончить скрипт».** Он обрывает процесс и может потерять вывод и логи; правильнее `process.exitCode` и естественное завершение.
- **«Ошибку поймали и залогировали — значит, всё хорошо».** Если скрипт после этого завершается с кодом 0, CI и cron считают запуск успешным.

## Как спрашивают на собеседовании

::question
Что происходит, когда ты запускаешь `node app.js`?

#answer
ОС создаёт процесс и запускает исполняемый файл Node.js. Рантайм поднимает V8 и цикл событий libuv, читает файл, разбирает и компилирует его в байткод и выполняет верхний уровень модуля. Дальше цикл событий вызывает обработчики таймеров, сокетов и промисов, пока работа не кончится, и процесс завершается с кодом выхода.

#more
Модули ES загружаются в три фазы: построение графа импортов, связывание и выполнение, поэтому синтаксическая ошибка в любом импортированном файле не даст выполниться ничему. Горячие функции V8 по ходу работы компилирует в машинный код. В браузере последнего шага нет: страница реагирует на события, пока её не закрыли.
::

::question
Что хранится в кадре стека? Почему глубина рекурсии разная для разных функций?

#answer
В кадре — аргументы, локальные переменные, адрес возврата и сохранённые регистры. Стек — кусок памяти фиксированного размера, поэтому предельная глубина — размер стека, делённый на размер кадра. Функция с большим числом аргументов и локальных переменных переполнит стек раньше.

#more
В проверке простая рекурсия в Node.js падала на глубине около 10 000, с четырьмя аргументами и локальной переменной — около 6 000, а с `--stack-size=200` — около 2 000. Для структур неизвестной глубины рекурсию заменяют циклом с явным стеком.
::

::question
Почему в стеке ошибки из `setTimeout` нет функции, которая этот таймер поставила?

#answer
Колбэк таймера запускает цикл событий, когда стек уже пуст: функция, поставившая таймер, давно вернулась. Стек ошибки — снимок текущего стека, поэтому в нём только колбэк и внутренние функции таймеров.

#more
Через `await` V8 восстанавливает цепочку ожидающих `async`-функций и показывает её как `at async page`. Для колбэков DevTools умеет показывать асинхронные стеки при отладке, записывая место планирования, но в `error.stack` в продакшене их нет. Поэтому код переводят на `async`/`await`, а контекст передают через `cause` при обёртке ошибки.
::

::question
Когда процесс Node.js завершается сам?

#answer
Когда в цикле событий не осталось ничего, что может вызвать код: активных таймеров, открытых сокетов и серверов, незавершённых операций ввода-вывода. Перед этим срабатывает `beforeExit`, где можно запланировать ещё работу, а потом `exit`, где можно сделать только синхронное.

#more
Висящий промис сам процесс не держит: если его никто не разрешит, процесс завершится. `unref()` у таймера или сокета позволяет не держать процесс из-за него, `ref()` возвращает как было. Частая причина «скрипт не завершается» — незакрытый пул соединений с базой или открытый `setInterval`.
::

::question
Что такое код выхода и кто его читает?

#answer
Число, которым процесс сообщает результат: 0 — успех, всё остальное — ошибка. Его читают оболочка, CI, cron, Docker и Kubernetes: по нему шаг сборки становится красным, а контейнер перезапускается. Node.js выходит с 1 при необработанном исключении и необработанном отклонении промиса.

#more
`process.exitCode = n` задаёт код, с которым процесс завершится, когда закончит работу, — это лучше `process.exit(n)`, который обрывает процесс и может потерять вывод. Код 128 + n означает, что процесс убит сигналом n: 143 — SIGTERM, 137 — SIGKILL, часто от нехватки памяти в контейнере.
::

::question
Как остановить сервер при деплое, не потеряв запросы?

#answer
Обработать SIGTERM: перестать принимать новые соединения (`server.close()`), дождаться завершения текущих запросов, закрыть соединения с базой и очереди и выйти с кодом 0. Без обработчика процесс умирает сразу, и запросы в обработке обрываются.

#more
Оркестратор после SIGTERM ждёт отведённое время и посылает SIGKILL, поэтому в обработчике ставят свой таймер аварийного выхода. Балансировщик должен успеть убрать экземпляр из ротации: для этого проверка готовности начинает отвечать ошибкой. В контейнере сигнал должен дойти до Node.js — если процесс запущен через оболочку, она может его не передать.
::

## Практика

::practice{title="Что выведет?"}
```js
console.log('start');
setTimeout(() => console.log('timer'), 0);
process.on('beforeExit', () => console.log('beforeExit'));
process.on('exit', (code) => {
  setTimeout(() => console.log('late'), 0);
  console.log('exit', code);
});
console.log('end');
```

#solution
```text
start
end
timer
beforeExit
exit 0
```

Верхний уровень выполняется целиком, потом цикл событий вызывает таймер. Когда работы не осталось, срабатывает `beforeExit`, а за ним `exit`. Таймер внутри `exit` не сработает: процесс уже завершается, и обработчик `exit` выполняется только синхронно. Если в `beforeExit` поставить таймер, цикл оживёт и `beforeExit` сработает снова — так легко получить бесконечный процесс.
::

::practice{title="CI зелёный, хотя отчёт упал"}
Скрипт проверки отчёта в CI:

```js
async function main() {
  const report = await buildReport();
  if (!report.balanced) throw new Error('отчёт не сошёлся');
}
main().catch((e) => console.error(e.message));
```

Ошибка видна в логе, но шаг CI зелёный. Почему и как исправить?

#solution
`catch` обработал отклонение, процесс дошёл до конца без необработанных ошибок и завершился с кодом 0. CI смотрит на код выхода, а не на лог. В проверке такой скрипт вернул 0.

Исправление — задать код выхода:

```js
main().catch((e) => {
  console.error(e);
  process.exitCode = 1;
});
```

Без `catch` вообще Node.js тоже завершился бы с кодом 1 из-за необработанного отклонения, но явный обработчик лучше: можно напечатать понятное сообщение. `process.exit(1)` здесь хуже: он может оборвать вывод до того, как лог дошёл до CI.
::

::practice{title="Сервер теряет запросы при деплое"}
При каждом деплое часть пользователей получает ошибку соединения: старый экземпляр сервера отчётов убивается, пока обрабатывает запросы. Напиши обработку SIGTERM.

#solution
Без обработчика SIGTERM процесс завершается сразу. С обработчиком — перестаёт принимать новые соединения и ждёт текущие:

```js
const server = http.createServer(handler);
server.listen(port);

process.on('SIGTERM', () => {
  console.error('SIGTERM: новые запросы не принимаем');
  server.close(async () => {
    await db.end();                                  // закрыть пул соединений
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 10_000).unref(); // если не успели — выходим сами
});
```

В проверке запрос, начатый до сигнала, получил ответ, новое соединение после сигнала было отклонено (`ECONNREFUSED`), а процесс завершился с кодом 0. Аварийный таймер с `unref()` не держит процесс, но не даст ему висеть вечно, если какое-то соединение не закрывается. Время ожидания должно быть меньше, чем оркестратор ждёт до SIGKILL.
::
