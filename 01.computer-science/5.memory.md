# Память

Любая программа выделяет память под данные и должна её когда-то вернуть. Языки решают это по-разному: программист освобождает вручную, счётчик ссылок освобождает сразу, сборщик мусора ищет недостижимое, а компилятор Rust вычисляет момент освобождения заранее. Спрашивают, чем стек отличается от кучи, какие бывают модели управления памятью и почему подсчёт ссылок не справляется с циклами. Глубже — что такое безопасность памяти, почему «примитивы на стеке» — миф и куда девается буфер после отправки в воркер.

::tldr
- **Стек — память вызовов, куча — память для данных произвольного размера и времени жизни.** Стек освобождается сам при выходе из функции, куча требует управления.
- **Четыре модели управления памятью:** ручная (C), подсчёт ссылок (Swift, CPython), трассирующая сборка мусора (JavaScript, Java, Go) и владение, проверенное компилятором (Rust).
- **Подсчёт ссылок освобождает сразу, но не видит циклов.** Трассирующий сборщик собирает всё недостижимое, включая циклы, но в момент, который выбирает сам.
- **Сборщик мусора убирает висячие указатели и двойное освобождение, но не утечки.** Утечка в JavaScript — объект, который всё ещё достижим, хотя больше не нужен.
- **JavaScript — язык с безопасной памятью:** выход за границы массива не портит соседние данные, а перенесённый `ArrayBuffer` становится пустым, а не висячим.
::

## Стек и куча

Сквозной пример — редактор фотографий в браузере: открытое фото, история правок, кеш миниатюр и воркер, который применяет фильтры. Всё это — данные в памяти, и у каждого куска своё время жизни.

Память процесса делится на области:

- **код** — инструкции программы;
- **статические данные** — глобальные переменные и константы;
- **стек** — кадры вызовов функций: аргументы, локальные переменные, адрес возврата;
- **куча** — всё, что создаётся во время работы и живёт неизвестно сколько.

**Стек** работает по принципу «последним пришёл — первым ушёл». Вызов функции кладёт кадр, возврат снимает его, и всё, что было в кадре, исчезает автоматически. Это быстро — выделение сводится к сдвигу указателя, — но размер стека ограничен, а данные нельзя пережить функцию. Как стек вызовов выглядит в выполняющейся программе — в [Выполнении кода](/content/computer-science/running-the-code).

**Куча** хранит данные произвольного размера, которые должны пережить создавшую их функцию: фото, историю правок, объекты интерфейса. Выделить память в куче дороже, а главное — её кто-то должен вернуть. Как именно, и есть главный вопрос этой темы.

### «Примитивы на стеке, объекты в куче»

Эту фразу часто говорят про JavaScript, и это миф. Спецификация языка вообще не говорит о стеке и куче, а V8 решает сам. Малые целые он хранит прямо в регистрах и кадрах, а строки, дробные числа и переменные, захваченные замыканием, — в куче. В проверке строка из 10 миллионов символов в локальной переменной функции добавила в кучу 9,5 МБ.

Правильная модель для JavaScript — не «где лежит», а **семантика**: примитивы неизменяемы и сравниваются по значению, объекты сравниваются по ссылке, а в функцию передаётся копия ссылки. Подробно — в [Типах и переменных](/content/javascript/types-and-variables).

С кучей нужно что-то делать. Языки придумали четыре ответа.

## Ручное управление

В C программист сам просит память и сам её отдаёт: `malloc` и `free`. В C++ то же через `new` и `delete`, но обычно память привязывают к объекту на стеке, чей деструктор её освобождает (идиома RAII). Полный контроль и никаких накладных расходов — но каждая ошибка становится уязвимостью или падением:

| Ошибка | Что происходит |
| --- | --- |
| утечка | память не освобождена и больше не используется — процесс растёт |
| висячий указатель, use-after-free | память освобождена, а указатель на неё остался; запись портит чужие данные |
| двойное освобождение | `free` дважды ломает внутренние структуры распределителя |
| выход за границы | чтение или запись за концом буфера читает или портит соседние данные |

Последняя ошибка — источник знаменитых уязвимостей: в 2014 году Heartbleed в OpenSSL читал за границей буфера и отдавал наружу содержимое памяти сервера, включая ключи. По данным команды безопасности Chromium, около 70% серьёзных уязвимостей браузера — ошибки безопасности памяти. Поэтому в Chrome и Firefox всё больше кода пишут на Rust, а сами движки защищают песочницей.

Код без таких ошибок называют **безопасным по памяти** (memory safe). Следующие три модели добиваются этого автоматически.

## Подсчёт ссылок

У каждого объекта есть счётчик: сколько ссылок на него существует. Новая ссылка увеличивает его, исчезнувшая уменьшает, а на нуле объект освобождается **сразу**. Так работают Swift и Objective-C (ARC), CPython, `std::shared_ptr` в C++ и `Rc` в Rust.

Плюс — предсказуемость: ресурс освобождается в момент, когда исчезла последняя ссылка, без пауз. Минус — **циклы**. Если фото ссылается на историю правок, а история — обратно на фото, у обоих счётчик не меньше единицы, даже когда снаружи их никто не видит. Подсчёт ссылок такую пару не освободит никогда.

Проверка в CPython: обычный объект после `del` исчезает сразу. Два объекта со ссылками друг на друга после `del` живы, пока не отработает отдельный **сборщик циклов** — `gc.collect()`. В Swift сборщика циклов нет, поэтому обратную ссылку объявляют слабой (`weak`), и разрыв циклов — обязанность программиста.

Есть и цена в скорости: каждое присваивание ссылки меняет счётчик, а между потоками — атомарно.

## Трассирующая сборка мусора

JavaScript, Java, C# и Go не считают ссылки. Сборщик время от времени начинает с **корней** — глобального объекта, стека вызовов, регистров — и проходит по всем ссылкам. Всё, до чего он дошёл, **достижимо** и живёт. Остальное — мусор, даже если объекты ссылаются друг на друга.

Поэтому цикл не проблема. В проверке пара «заказ ↔ покупатель», созданная внутри функции, была собрана, и `FinalizationRegistry` сообщил об этом после сборки.

Цена — **недетерминированность** и паузы. Объект без ссылок живёт до следующей сборки: в проверке `WeakRef` на объект без единой сильной ссылки возвращал его, пока сборщик не запустился. Поэтому в языках со сборщиком нельзя закрывать файлы, сокеты и подписки в финализаторах — для этого есть явные `close()`, `try…finally` и `using`.

Сборщики разных языков устроены похоже: поколения (большинство объектов умирают молодыми, поэтому молодую память собирают часто и дёшево), инкрементальная и параллельная работа, чтобы сократить паузы. Как это сделано в V8 — Mark-and-Sweep, Scavenger, поколения — и как искать утечки, разобрано в [Памяти и производительности](/content/javascript/memory-and-performance).

Важно, чего сборщик **не** решает: утечек. Сборщик освобождает недостижимое, а утечка в JavaScript — это достижимое, но ненужное: кеш миниатюр без лимита, обработчик на `window`, забытый таймер с замыканием на фото.

## Владение

Rust пошёл четвёртым путём: момент освобождения вычисляет **компилятор**. У каждого значения ровно один владелец; когда владелец выходит из области видимости, значение освобождается. Значение можно **переместить** — тогда старая переменная больше недоступна, и компилятор не даст ей воспользоваться. Можно **одолжить** — много ссылок только для чтения или одну для записи, и ни одна не переживёт владельца.

Результат — безопасность памяти без сборщика и без счётчиков: все проверки сделаны при компиляции. Цена — строгая модель, к которой нужно привыкнуть, и сложности с графами, где у объекта несколько хозяев.

В JavaScript есть знакомое по смыслу место — **перенос** `ArrayBuffer`. Отправка буфера в воркер со списком переноса передаёт владение: байты не копируются, а исходный буфер становится пустым.

```js
const frame = new ArrayBuffer(8);
const moved = structuredClone(frame, { transfer: [frame] });
frame.byteLength;    // 0
frame.detached;      // true
moved.byteLength;    // 8
```

Попытка работать со старым представлением — не порча памяти, как в C, а понятная ошибка: `TypeError: Cannot perform %TypedArray%.prototype.fill on a detached ArrayBuffer`. Так редактор фото передаёт кадр в воркер с фильтрами без копирования мегабайтов. Подробно — в [Web Workers](/content/additional-topics/web-workers-and-concurrency).

| Модель | Когда освобождает | Циклы | Ошибки, которые остаются |
| --- | --- | --- | --- |
| ручная (C) | когда вызвали `free` | любые | все: утечки, висячие указатели, переполнения |
| подсчёт ссылок (Swift, CPython) | сразу при последней ссылке | утекают без слабых ссылок или сборщика циклов | циклы, накладные расходы на счётчики |
| трассирующая (JS, Java, Go) | при следующей сборке | собираются | утечки через достижимые ссылки, паузы |
| владение (Rust) | при выходе владельца из области | требуют `Rc` и `Weak` | почти никакие, но строгий компилятор |

## Память в JavaScript-приложении

У процесса браузера или Node.js память делится не только на стек и кучу V8.

- **Куча V8** — объекты, строки, замыкания. У неё есть предел; в Node.js его меняют флагом `--max-old-space-size`, а при его исчерпании процесс падает с «JavaScript heap out of memory».
- **Память вне кучи** — байты `ArrayBuffer`, `Buffer` в Node.js, декодированные картинки, видео, текстуры GPU. В проверке буфер на 50 МБ не изменил `heapUsed`, но добавил 50 МБ в `arrayBuffers` и `rss`. Поэтому снимок кучи может показывать мало, а процесс — занимать гигабайты.
- **Линейная память WebAssembly** — один большой `ArrayBuffer`, внутри которого код на C или Rust управляет памятью по своим правилам. Ошибки C остаются, но не выходят за пределы этого буфера ([WebAssembly](/content/additional-topics/webassembly)).

Безопасность памяти JavaScript видна на типизированных массивах. Запись за границу не портит соседние данные, а просто ничего не делает: `u8[10] = 1` у массива длины 4 оставляет его прежним. `DataView` в той же ситуации бросает `RangeError`.

## Красные флаги в ответе

- **«В JavaScript примитивы хранятся на стеке, а объекты в куче».** Спецификация этого не определяет, а V8 держит в куче строки, дробные числа и захваченные переменные. Модель для JavaScript — семантика значений и ссылок.
- **«Со сборщиком мусора утечек не бывает».** Сборщик освобождает только недостижимое; утечка — достижимое, но ненужное.
- **«Сборщик мусора не справляется с циклическими ссылками».** Это про подсчёт ссылок. Трассирующий сборщик начинает от корней, и цикл без внешних ссылок для него мусор.
- **«`WeakRef` и финализаторы — способ освобождать ресурсы».** Момент сборки не определён, финализатор может не вызваться вовсе. Ресурсы закрывают явно.
- **«Подсчёт ссылок — это сборка мусора, только быстрее».** Он детерминирован, но платит за каждое присваивание и не видит циклы.
- **«Ручное управление памятью — это просто быстрее».** Это ещё и целый класс уязвимостей: около 70% серьёзных багов безопасности Chromium — ошибки памяти.

## Как спрашивают на собеседовании

::question
Чем стек отличается от кучи?

#answer
Стек хранит кадры вызовов: аргументы, локальные переменные, адрес возврата. Он освобождается автоматически при возврате из функции, выделение почти бесплатное, но размер ограничен. Куча хранит данные произвольного размера и времени жизни, выделение дороже, и освобождением кто-то должен управлять.

#more
В JavaScript это деталь движка: спецификация не говорит, где что лежит. V8 держит в куче строки, дробные числа, объекты и переменные, захваченные замыканиями. Переполнение стека — `RangeError: Maximum call stack size exceeded` при глубокой рекурсии; исчерпание кучи — «JavaScript heap out of memory».
::

::question
Какие модели управления памятью бывают?

#answer
Ручная — программист вызывает `malloc` и `free` (C). Подсчёт ссылок — объект освобождается, когда счётчик ссылок упал до нуля (Swift, CPython). Трассирующая сборка мусора — сборщик обходит граф от корней и удаляет недостижимое (JavaScript, Java, Go). Владение — компилятор вычисляет, когда освободить (Rust).

#more
Компромиссы: ручная даёт контроль, но и все ошибки памяти; подсчёт ссылок детерминирован, но не видит циклов; трассирующая собирает всё, но в непредсказуемый момент и с паузами; владение безопасно без накладных расходов, но требует строгой дисциплины. Языки комбинируют: CPython — счётчики плюс сборщик циклов, C++ — RAII плюс `shared_ptr`.
::

::question
Почему подсчёт ссылок не справляется с циклами, а сборщик в JavaScript справляется?

#answer
В цикле каждый объект держит ссылку на другой, поэтому их счётчики не падают до нуля, даже когда снаружи на них ничего не ссылается. Трассирующий сборщик не считает ссылки: он идёт от корней и помечает достижимое. До цикла без внешних ссылок он не дойдёт, и цикл будет собран.

#more
В CPython для этого есть отдельный сборщик циклов, который можно вызвать `gc.collect()`. В Swift его нет, и обратные ссылки объявляют `weak` или `unowned`. В старом Internet Explorer DOM-объекты считались ссылками, а JavaScript-объекты — сборщиком, и цикл через обработчик события утекал; современные браузеры собирают DOM и JavaScript одним графом.
::

::question
Может ли быть утечка памяти в языке со сборщиком мусора?

#answer
Да. Сборщик освобождает только недостижимое, а утечка — это объект, который всё ещё достижим, но больше не нужен. Типичные причины во фронтенде: кеш без лимита, обработчики и подписки, которые не сняли, таймеры с замыканиями, отсоединённые DOM-узлы, на которые осталась ссылка.

#more
Утечку ищут сравнением снимков кучи: сделать действие несколько раз, собрать мусор и посмотреть, какие объекты растут и кто их удерживает — цепочку удерживающих ссылок показывает DevTools. Отдельно смотрят память вне кучи: `ArrayBuffer` и картинки не видны в `heapUsed`. Приёмы и примеры — в главе про память JavaScript.
::

::question
Что такое безопасность памяти? Почему JavaScript безопасен, а C — нет?

#answer
Безопасный по памяти код не может прочитать или записать память, которая ему не принадлежит: за границей буфера, после освобождения, через неинициализированный указатель. В C это ответственность программиста, и ошибки становятся уязвимостями. В JavaScript нет указателей, границы массивов проверяются, а память освобождает сборщик, поэтому таких ошибок в коде на JavaScript не бывает.

#more
Запись за границу типизированного массива просто игнорируется, `DataView` бросает `RangeError`, а работа с перенесённым буфером — `TypeError`. Сами движки написаны на C++, поэтому ошибки памяти остаются в них — от этого защищают песочница и изоляция сайтов. По данным Chromium, около 70% серьёзных уязвимостей браузера — ошибки памяти, поэтому новый код всё чаще пишут на Rust.
::

::question
Почему `ArrayBuffer` пустой после отправки в воркер?

#answer
Его отправили со списком переноса: `postMessage(buffer, [buffer])`. Перенос передаёт владение без копирования — байты переходят к воркеру, а исходный буфер отсоединяется и становится нулевой длины. Это защищает от одновременной записи из двух потоков.

#more
Это похоже на перемещение значения в Rust: у данных всегда один владелец. Если буфер нужен обоим, его копируют — отправляют без списка переноса или делают `slice()`. Если нужна общая память, используют `SharedArrayBuffer` и `Atomics`, а для них нужна изоляция страницы. Отсоединённый буфер — `detached: true`, методы его представлений бросают `TypeError`.
::

## Практика

::practice{title="Фото пропало после фильтра"}
Редактор отправляет кадр в воркер и тут же рисует превью:

```js
const pixels = ctx.getImageData(0, 0, w, h).data;      // Uint8ClampedArray
worker.postMessage({ pixels }, [pixels.buffer]);
drawPreview(pixels);                                    // превью пустое
```

Почему превью пустое и как исправить?

#solution
`pixels.buffer` в списке переноса: владение байтами ушло в воркер, исходный буфер отсоединён, и `pixels.length` стал 0. Рисовать нечего.

Варианта два. Если превью нужно до фильтра — нарисовать его до отправки или отправить копию:

```js
drawPreview(pixels);
worker.postMessage({ pixels }, [pixels.buffer]);       // после этого pixels не трогаем
```

Если оригинал нужен дальше — переносить копию, а оригинал оставить себе:

```js
const copy = pixels.slice();
worker.postMessage({ pixels: copy }, [copy.buffer]);
```

Воркер возвращает обработанный кадр тоже переносом, и владение возвращается в главный поток.
::

::practice{title="Процесс занимает гигабайт, а куча — 50 МБ"}
Сервис на Node.js, который ресайзит картинки, по метрикам занимает больше гигабайта, а снимок кучи показывает около 50 МБ. Где остальная память и как это проверить?

#solution
Куча V8 — только объекты JavaScript. Байты `Buffer` и `ArrayBuffer` живут вне кучи и в снимке видны как маленькие объекты-обёртки. `process.memoryUsage()` показывает их отдельно:

```js
const { rss, heapUsed, external, arrayBuffers } = process.memoryUsage();
```

В проверке буфер на 50 МБ не изменил `heapUsed`, но увеличил `arrayBuffers` и `rss` на 50 МБ. Если растут `arrayBuffers` и `external`, утечка в буферах: их держат очередь необработанных задач, кеш результатов без лимита или незакрытые потоки. Лечится лимитом очереди, потоковой обработкой вместо чтения файла целиком и лимитом кеша. Флаг `--max-old-space-size` здесь не поможет: он ограничивает только кучу.
::

::practice{title="Пул объектов для частиц"}
Анимация на canvas создаёт тысячи объектов-частиц в секунду, и в профиле видны частые паузы сборщика. Сделай пул, который переиспользует частицы вместо создания новых.

#solution
Пул хранит свободные объекты и отдаёт их вместо `new`. Мёртвая частица возвращается в пул, а не становится мусором:

```js
class Pool {
  #free = [];
  #create;
  constructor(create) { this.#create = create; }
  acquire() { return this.#free.pop() ?? this.#create(); }
  release(item) { this.#free.push(item); }
  get size() { return this.#free.length; }
}

const particles = new Pool(() => ({ x: 0, y: 0, vx: 0, vy: 0, life: 0 }));

function spawn(x, y) {
  const p = particles.acquire();
  p.x = x; p.y = y; p.vx = Math.random() - 0.5; p.vy = -1; p.life = 60;  // каждое поле заново
  return p;
}
```

Важно сбрасывать все поля: переиспользованный объект помнит старые значения. Пул нужен только там, где профиль показывает давление на сборщик: молодое поколение в V8 собирается дёшево, и для обычного кода пул — лишняя сложность и риск использовать объект после `release`.
