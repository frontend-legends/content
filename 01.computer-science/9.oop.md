# Объектно-ориентированное программирование

ООП строит программу из объектов: у каждого своё состояние и методы, которые его меняют, а снаружи видно только поведение. Идея — ограничить, кто может менять данные, и подменять реализации, не трогая код, который ими пользуется. Спрашивают четыре принципа, чем композиция лучше наследования и что такое принцип подстановки Лисков. Глубже — какие бывают виды полиморфизма, почему наследование от чужого класса хрупкое и почему фронтенд ушёл от классов в компонентах, но не от объектов.

::tldr
- **Объект — состояние плюс поведение за интерфейсом.** Код снаружи вызывает методы и не знает, как устроены данные внутри.
- **Четыре принципа:** абстракция (важное наружу, детали внутрь), инкапсуляция (менять состояние можно только через методы, которые держат инварианты), наследование (переиспользование через иерархию), полиморфизм (один вызов — разное поведение).
- **Полиморфизм бывает трёх видов:** подтипов (метод выбирается во время вызова), параметрический (дженерики) и специальный (перегрузки). В JavaScript ещё и по протоколу: всё, что умеет `Symbol.iterator`, работает в `for…of`.
- **Наследование — самая сильная связь между классами.** Наследник зависит от деталей родителя, поэтому иерархии ломаются при изменениях. Композиция — объект содержит другие и делегирует им — гибче.
- **Подстановка Лисков: наследник должен работать везде, где работает родитель.** «Квадрат — это прямоугольник» в математике, но не в коде, если у прямоугольника можно менять стороны по отдельности.
::

## Что такое объект

Сквозной пример — корзина интернет-магазина: товары, количество, сумма, способы оплаты и уведомления покупателю.

ООП выросло из проблемы процедурного кода: когда десятки функций меняют одну структуру данных, никто не отвечает за то, чтобы она осталась правильной. Ответ ООП — объединить данные и функции, которым разрешено их менять, в **объект**. Алан Кэй, придумавший термин, описывал объекты как маленькие компьютеры, которые обмениваются сообщениями: вызывающий код отправляет сообщение «добавь товар», а как объект его выполнит — его дело.

Объект выглядит снаружи как набор методов — **интерфейс**. Внутри — **состояние**, которое меняется только через этот интерфейс. Класс — шаблон для создания объектов с одинаковым интерфейсом.

В JavaScript ООП **прототипное**: объекты наследуют напрямую от других объектов, а `class` — синтаксис поверх цепочки прототипов. Как работают прототипы, `new` и поля классов — в [Прототипах и классах](/content/javascript/prototypes-and-classes). Здесь — о том, что ООП даёт как способ проектирования.

## Абстракция и инкапсуляция

**Абстракция** — показать наружу то, что важно для пользователя объекта, и спрятать остальное. Пользователю корзины важны «добавить», «удалить», «сумма». Хранятся ли товары массивом, `Map` или считается ли сумма заранее — неважно.

**Инкапсуляция** — механизм, который это обеспечивает: состояние закрыто, менять его можно только через методы. Главная польза не в секретности, а в **инвариантах** — правилах, которые всегда верны для объекта. Корзина гарантирует, что количество товара больше нуля, потому что другого пути к массиву нет:

```js
class Cart {
  #items = [];
  add(item) {
    if (item.qty <= 0) throw new RangeError('количество должно быть больше нуля');
    this.#items.push(item);
  }
  get total() {
    return this.#items.reduce((sum, i) => sum + i.price * i.qty, 0);
  }
}
```

Поле с `#` действительно недоступно снаружи: его нет в `Object.keys`, а обращение `cart.#items` вне класса — синтаксическая ошибка. Проверить, что объект — настоящая корзина, можно через `#items in obj`. До появления приватных полей то же делали замыканием: переменная в функции-фабрике видна только методам, созданным в ней.

Модификатор `private` в TypeScript — другое: это проверка компилятора, а во время выполнения поле доступно. Разница — в [Функциях и классах TypeScript](/content/typescript/functions-and-classes).

Инкапсуляция ограничивает изменения. Следующий вопрос — как переиспользовать поведение.

## Наследование

**Наследование** создаёт класс на основе другого: наследник получает методы родителя и может их переопределить или дополнить. `Card extends Payment` — оплата картой — это оплата, у которой своя подпись.

Наследование выражает отношение «является» (is-a) и даёт переиспользование кода «бесплатно». Но у него высокая цена: это самая сильная связь между классами. Наследник видит и зависит не только от интерфейса родителя, но и от деталей его реализации.

### Хрупкий базовый класс

Пример из проверки. Нужно множество тегов, которое считает, сколько раз в него добавляли:

```js
class CountingSet extends Set {
  count = 0;
  add(v) {
    this.count++;
    return super.add(v);
  }
}

const tags = new CountingSet(['улун', 'пуэр', 'сенча']);
tags.size;  // 3
tags.count; // 0
```

Конструктор `Set` добавляет начальные элементы, вызывая `this.add`, — то есть переопределённый метод наследника. Но поля наследника инициализируются после того, как отработал конструктор родителя, и `count = 0` затирает посчитанное. Код наследника правильный по отдельности и сломан деталью, которую родитель нигде не обещал. Это **проблема хрупкого базового класса**: изменение или особенность реализации родителя ломает наследников.

С массивами другая неожиданность: методы `map` и `filter` у наследника `Array` возвращают экземпляр наследника, а не обычный массив (механизм `Symbol.species`). Унаследовать от встроенного класса — значит унаследовать все его договорённости.

Отсюда правило из книги «Банды четырёх»: **предпочитай композицию наследованию**. Об этом ниже, а сначала — ради чего наследование вообще нужно.

## Полиморфизм

**Полиморфизм** — один и тот же вызов работает с разными типами. Код оформления заказа вызывает `payment.describe()` и не знает, карта это или наличные. Добавить новый способ оплаты — написать новый класс, а не править `switch` во всех местах.

| Вид | Как работает | Пример |
| --- | --- | --- |
| подтипов | метод выбирается во время вызова по реальному объекту | `payment.describe()` у `Card` и `Cash` |
| параметрический | один код для любых типов | дженерики: `Array<T>`, `Map<K, V>` |
| специальный (ad hoc) | разные реализации для разных типов под одним именем | перегрузки функций, `+` для чисел и строк |

**Полиморфизм подтипов** держится на **динамической диспетчеризации**: в JavaScript метод ищется по цепочке прототипов в момент вызова. В проверке замена `Card.prototype.label` изменила поведение всех существующих карт.

### Полиморфизм по протоколу

В JavaScript наследование для полиморфизма часто не нужно: достаточно, чтобы объект умел нужное сообщение. Это **утиная типизация**: «если крякает как утка — это утка».

- любой объект с методом `Symbol.iterator` работает в `for…of`, со spread и `Array.from` — массив, `Map`, строка, генератор или свой объект;
- любой объект с методом `then` можно ждать через `await`;
- любой объект с `toJSON` сериализуется по-своему.

Это тот же полиморфизм, только без общего родителя: договорённость — протокол, а не иерархия. TypeScript описывает такие договорённости структурными интерфейсами.

## Композиция вместо наследования

**Композиция** — объект содержит другие объекты и делегирует им работу. Связь «имеет» (has-a) вместо «является».

Пример с уведомлениями. Через наследование получается взрыв классов: `EmailNotifier`, `SmsNotifier`, `RetryingSmsNotifier`, `LoggedRetryingEmailNotifier` — по классу на каждую комбинацию. Через композицию — каналы и обёртки, которые собираются как угодно:

```js
const withRetry = (n, channel) => ({
  async send(msg) {
    for (let i = 0; ; i++) {
      try { return await channel.send(msg); } catch (e) { if (i >= n) throw e; }
    }
  },
});
const withLog = (channel) => ({
  send: (msg) => { log(msg); return channel.send(msg); },
});

const notify = withLog(withRetry(2, sms));
```

Каждая часть знает только интерфейс `send`. Это паттерны «Декоратор» и «Стратегия»; остальные классические паттерны и их функциональные версии — в [Паттернах](/content/javascript/patterns).

Хрупкий `CountingSet` тоже чинится композицией: класс хранит `Set` внутри и сам решает, какие методы показать. Зависимость от реализации `Set` исчезает — остаётся только от его публичных методов.

## Принципы проектирования

Принципы **SOLID** сформулированы для объектно-ориентированного проектирования: единственная ответственность, открытость для расширения и закрытость для изменения, подстановка, разделение интерфейсов и инверсия зависимостей. Как они применяются к компонентам и модулям фронтенда — в [Архитектурном мышлении](/content/architecture/architectural-thinking). Один из них напрямую про наследование, и его спрашивают отдельно.

### Принцип подстановки Лисков

Барбара Лисков сформулировала его так: объекты наследника должны подставляться вместо объектов родителя без изменения правильности программы. Наследник может расширять поведение, но не может нарушать то, на что рассчитывает код, работающий с родителем.

Классический пример — квадрат как наследник прямоугольника:

```js
class Rectangle {
  constructor(w, h) { this.w = w; this.h = h; }
  setWidth(w) { this.w = w; }
  setHeight(h) { this.h = h; }
  get area() { return this.w * this.h; }
}
class Square extends Rectangle {
  setWidth(w) { this.w = w; this.h = w; }
  setHeight(h) { this.w = h; this.h = h; }
}

function stretch(rect) {
  rect.setWidth(5);
  rect.setHeight(4);
  return rect.area; // для прямоугольника 20, для квадрата 16
}
```

Квадрат по отдельности правильный, но код, который рассчитывал на независимые стороны прямоугольника, с ним ломается. Наследование отражает не отношение «является» в жизни, а **совместимость поведения**. Признаки нарушения: наследник бросает `NotImplemented` на унаследованном методе, ужесточает требования к аргументам или ослабляет гарантии результата, а вызывающему коду приходится проверять `instanceof`.

Для фронтенда это значит: компонент `IconButton` должен работать везде, где работает `Button`, — принимать те же обработчики, фокусироваться и отправлять форму так же.

## ООП во фронтенде

Фронтенд прошёл через классы и во многом от них ушёл — но не от объектов:

- **Компоненты.** React перешёл от классовых компонентов к функциям с хуками: логику жизненного цикла, разнесённую по методам, стало удобнее собирать композицией хуков, а наследование компонентов так и не прижилось. Vue сделал то же с Composition API.
- **Angular** остаётся на классах и внедрении зависимостей: сервисы — объекты, которые фреймворк создаёт и передаёт.
- **Web Components** — классы, наследующие `HTMLElement`: здесь наследование от платформы обязательно.
- **Предметная область и инфраструктура** — естественная территория объектов: клиент API, соединение WebSocket, плеер, редактор, кеш с политикой вытеснения. У них есть состояние, жизненный цикл и инварианты.

Объектный стиль и функциональный не враждуют: объект отвечает за состояние и его правила, чистые функции — за вычисления. Подробнее о том, как стили сочетаются, — в [Парадигмах](/content/computer-science/paradigms).

## Красные флаги в ответе

- **«Инкапсуляция — это когда поля приватные».** Приватность — механизм; цель — держать инварианты объекта и не давать менять состояние в обход правил.
- **«Наследование нужно для переиспользования кода».** Для переиспользования есть функции и композиция; наследование оправдано, когда наследник действительно подставляется вместо родителя.
- **«Квадрат — это прямоугольник, значит `Square extends Rectangle`».** Наследование отражает совместимость поведения, а не отношения из жизни.
- **«Полиморфизм — это переопределение методов».** Это только полиморфизм подтипов; есть ещё параметрический и специальный, а в JavaScript — по протоколу.
- **«`private` в TypeScript скрывает поле».** Только от компилятора; во время выполнения поле доступно. Настоящая приватность — `#`.
- **«React отказался от ООП».** От классовых компонентов — да, от объектов, инкапсуляции и полиморфизма — нет.

## Как спрашивают на собеседовании

::question
Назови четыре принципа ООП и зачем каждый нужен.

#answer
Абстракция — показать важное и спрятать детали. Инкапсуляция — менять состояние только через методы, чтобы объект сам держал свои инварианты. Наследование — строить класс на основе другого и переиспользовать поведение. Полиморфизм — один вызов работает с разными типами, и новый тип добавляется без правки вызывающего кода.

#more
Хороший ответ говорит и о цене: наследование — самая сильная связь, наследник зависит от деталей родителя, поэтому глубокие иерархии ломаются при изменениях. Полиморфизм не требует наследования: в JavaScript достаточно, чтобы объект выполнял протокол — `Symbol.iterator`, `then`, `toJSON`.
::

::question
Что такое инкапсуляция и как её сделать в JavaScript?

#answer
Это ограничение доступа к состоянию: менять его можно только через методы, которые проверяют правила. Цель — инварианты: корзина гарантирует положительное количество, потому что другого пути к массиву товаров нет. В JavaScript — приватные поля `#`, недоступные снаружи, или замыкание: переменная внутри фабрики видна только её методам.

#more
`#items in obj` проверяет, что объект создан этим классом, — надёжнее `instanceof`, который обманывается подменой прототипа. TypeScript `private` — только проверка компилятора. Геттеры позволяют отдавать вычисляемые значения и копии вместо внутренних массивов, чтобы снаружи их нельзя было изменить по ссылке.
::

::question
Почему композицию предпочитают наследованию?

#answer
Наследник зависит не только от интерфейса родителя, но и от деталей его реализации, и изменения в родителе ломают наследников — проблема хрупкого базового класса. Иерархия фиксирует одну ось изменений, и комбинации поведения порождают взрыв классов. Композиция связывает объекты только через интерфейс, и части собираются в любых сочетаниях.

#more
Пример из проверки: наследник `Set`, считающий добавления, после `new CountingSet([1, 2, 3])` показывал `count` 0, потому что конструктор `Set` вызывает `add` до инициализации полей наследника. Обёртка, которая хранит `Set` внутри, этой проблемы не имеет. Наследование уместно, когда наследник действительно подставляется вместо родителя и иерархия неглубокая — или когда его требует платформа, как с `HTMLElement`.
::

::question
Что такое принцип подстановки Лисков? Приведи пример нарушения.

#answer
Объект наследника должен работать везде, где работает объект родителя, не ломая ожиданий вызывающего кода. Классический пример: `Square extends Rectangle`. Код, который ставит ширину 5 и высоту 4 и ждёт площадь 20, с квадратом получит 16, потому что квадрат меняет обе стороны.

#more
Признаки нарушения: наследник бросает исключение на унаследованном методе, требует больше от аргументов или гарантирует меньше в результате, а вызывающему коду приходится проверять `instanceof`. Решения — неизменяемые фигуры, где «изменить размер» возвращает новый объект, или отказ от общей иерархии в пользу общего интерфейса только с тем, что верно для обоих.
::

::question
Какие бывают виды полиморфизма?

#answer
Полиморфизм подтипов — метод выбирается во время вызова по реальному объекту. Параметрический — один код для любых типов, как дженерики. Специальный — разные реализации под одним именем для разных типов, как перегрузки и `+` для чисел и строк.

#more
В JavaScript важен ещё полиморфизм по протоколу — утиная типизация: `for…of` работает с любым объектом, у которого есть `Symbol.iterator`, а `await` — с любым объектом с `then`. Динамическая диспетчеризация в JavaScript — поиск метода по цепочке прототипов в момент вызова, поэтому изменение метода в прототипе меняет поведение всех экземпляров.
::

::question
Почему React ушёл от классовых компонентов? Значит ли это, что ООП во фронтенде не нужно?

#answer
Логика жизненного цикла в классах размазывалась по методам: одна подписка — в `componentDidMount`, `componentDidUpdate` и `componentWillUnmount`. Переиспользовать её можно было только обёртками и наследованием, которое не прижилось. Хуки собирают логику по смыслу и переиспользуются композицией.

#more
ООП при этом осталось: клиенты API, соединения, редакторы, сторы с инвариантами — объекты с состоянием и жизненным циклом. Angular построен на классах и внедрении зависимостей, Web Components наследуют `HTMLElement`. Вопрос не «ООП или ФП», а что подходит для конкретной части: состояние с правилами — объект, вычисление — чистая функция.
::

## Практика

::practice{title="Счётчик тегов показывает ноль"}
```js
class CountingSet extends Set {
  count = 0;
  add(v) {
    this.count++;
    return super.add(v);
  }
}

const tags = new CountingSet(['улун', 'пуэр', 'сенча']);
console.log(tags.size, tags.count);
tags.add('матча');
console.log(tags.count);
```

Что выведет код? Почему и как исправить?

#solution
```text
3 0
1
```

Конструктор `Set` добавляет начальные элементы через `this.add` — переопределённый метод наследника, и тот трижды увеличивает `count`. Но поля наследника инициализируются после `super()`, и `count = 0` затирает результат. Наследник зависит от того, как родитель реализовал конструктор, — хрупкий базовый класс.

Композиция убирает зависимость от реализации `Set`:

```js
class CountingTags {
  #set = new Set();
  count = 0;
  constructor(items = []) {
    for (const x of items) this.add(x);
  }
  add(v) {
    this.count++;
    this.#set.add(v);
    return this;
  }
  get size() { return this.#set.size; }
  has(v) { return this.#set.has(v); }
}
```

Теперь `new CountingTags(['улун', 'пуэр', 'сенча'])` даёт `size` 3 и `count` 3. Класс сам решает, какие методы показать наружу.
::

::practice{title="Квадрат ломает растягивание"}
Редактор баннеров растягивает фигуры функцией:

```js
function stretch(shape) {
  shape.setWidth(5);
  shape.setHeight(4);
  return shape.area;
}
```

Для прямоугольника возвращается 20, а для `Square extends Rectangle` — 16. Где ошибка проектирования и как её исправить?

#solution
`Square` нарушает принцип подстановки Лисков. `stretch` рассчитывает, что стороны прямоугольника меняются независимо, а квадрат при `setHeight` меняет и ширину. Каждый класс по отдельности правильный, сломана иерархия: квадрат не подставляется вместо прямоугольника.

Решения — не давать менять стороны по отдельности или не наследовать:

```js
const rect = (w, h) => ({ w, h, area: w * h, withSize: (w2, h2) => rect(w2, h2) });
const square = (s) => ({ ...rect(s, s), withSide: (s2) => square(s2) });

square(1).withSize(5, 4).area; // 20 — получился прямоугольник, и это честно
```

Неизменяемые фигуры возвращают новый объект: «изменить размеры квадрата на 5 × 4» даёт прямоугольник, а не испорченный квадрат. Общий интерфейс оставляют только для того, что верно для обеих фигур: `area`, `draw`.
::

::practice{title="Взрыв классов уведомлений"}
В проекте есть `EmailNotifier`, `SmsNotifier`, `RetryingSmsNotifier`, `LoggedEmailNotifier` и `LoggedRetryingSmsNotifier`. Нужно добавить push-уведомления с повтором и логированием. Как перестроить код?

#solution
Иерархия кодирует две независимые оси — канал и дополнительное поведение — в одном дереве, поэтому каждая комбинация требует класса. Композиция разделяет оси: каналы реализуют `send`, а обёртки добавляют поведение к любому каналу.

```js
const email = { send: async (msg) => mailer.send(msg) };
const push = { send: async (msg) => pushService.send(msg) };

const withRetry = (n, channel) => ({
  async send(msg) {
    for (let i = 0; ; i++) {
      try { return await channel.send(msg); } catch (e) { if (i >= n) throw e; }
    }
  },
});
const withLog = (channel) => ({
  send: (msg) => { logger.info(msg); return channel.send(msg); },
});

const notifyPush = withLog(withRetry(2, push));
```

Новый канал — один объект, новое поведение — одна обёртка, а комбинации собираются в месте использования. В проверке SMS-канал, падавший с первого раза, отправил сообщение через `withRetry`, а `withLog` записал обе отправки.
::
