# Языки и компиляторы

Процессор понимает только машинные инструкции, а люди пишут на языках, где есть переменные, функции и выражения. Между ними стоит компилятор или интерпретатор: он читает текст, проверяет его и превращает в то, что можно выполнить. Спрашивают, чем компилятор отличается от интерпретатора, интерпретируемый ли JavaScript, что такое AST и чем статическая типизация отличается от сильной. Глубже — из каких этапов состоит компилятор, как парсер учитывает приоритет операций и почему `return` с переводом строки возвращает `undefined`.

::tldr
- **Компилируемость — свойство реализации, а не языка.** JavaScript в V8 сначала превращается в байткод для интерпретатора, а горячий код — в машинный код JIT-компилятором.
- **Компилятор работает этапами:** лексер режет текст на токены, парсер строит дерево разбора (AST), семантический анализ проверяет имена и типы, оптимизатор упрощает, генератор выдаёт машинный код, байткод или другой язык.
- **AST — общая основа инструментов фронтенда:** Babel, TypeScript, ESLint, Prettier и бандлеры читают код как дерево, а не как текст.
- **Синтаксическая ошибка находится до выполнения:** скрипт с ошибкой в последней строке не выполнит и первую.
- **Статическая или динамическая типизация — когда проверяются типы, сильная или слабая — приводятся ли они неявно.** JavaScript динамический и слабый, TypeScript добавляет статическую проверку и стирается при сборке.
::

## Язык и его реализация

**Язык программирования** — формальная система: синтаксис говорит, какие тексты правильные, а семантика — что они означают. Чтобы на языке можно было записать любой алгоритм, ему нужны условия, повторение и неограниченная память — такой язык называют **Тьюринг-полным**. Подробно о том, что это значит и почему из этого следуют пределы любых инструментов, — в [Теории вычислений](/content/computer-science/theory-of-computation).

Языки различаются по уровню абстракции:

- **машинный код** — двоичные инструкции конкретного процессора;
- **ассемблер** — те же инструкции мнемониками: `add x0, x0, x1`;
- **языки высокого уровня** — C, Java, Python, JavaScript: переменные, функции, объекты вместо регистров и адресов;
- **предметно-ориентированные языки** (DSL) — SQL для данных, регулярные выражения для текста, CSS для стилей, GraphQL для запросов. Они решают одну задачу и обычно не годятся для общих программ.

Частая ошибка — называть язык «интерпретируемым» или «компилируемым». Это свойство **реализации**. У одного языка их бывает несколько:

| Язык | Как его выполняют |
| --- | --- |
| JavaScript | V8 и JavaScriptCore — байткод и JIT; Hermes в React Native компилирует в байткод заранее, при сборке |
| Python | CPython компилирует в байткод и интерпретирует его, PyPy — JIT |
| Java, Kotlin | компилятор в байткод JVM, а JVM — интерпретатор и JIT |
| C, Rust, Go | компиляция заранее в машинный код |
| TypeScript | транспиляция в JavaScript — а дальше как у JavaScript |

Чтобы увидеть, что делает каждый этап, проще всего собрать маленький компилятор самим.

## Сквозной пример: формула цены

В админке интернет-магазина менеджер задаёт формулу цены:

```text
price * (1 - discount / 100) + delivery
```

Посчитать её через `eval` нельзя: менеджер может ввести любой JavaScript, и он выполнится с правами страницы. Значит, нужен свой маленький язык формул — числа, переменные, четыре действия и скобки — и свой компилятор. Он проходит те же этапы, что Babel или V8. Код целиком проверен в `codes/`.

---

## Лексер: текст в токены

Первый этап — **лексический анализ**. Лексер идёт по символам и собирает **токены** — минимальные значимые единицы: число, имя, оператор, скобка. Пробелы и комментарии он выбрасывает.

```js
tokenize('price * 2');
// [{ type: 'name', value: 'price' }, { type: '*' }, { type: 'num', value: 2 }]
```

Лексер ловит ошибки уровня символов: `tokenize('price # 2')` бросает «Неожиданный символ «#» в позиции 6». Настоящий лексер JavaScript делает то же самое: `const total = price * qty + 10;` превращается в девять токенов — `const`, `total`, `=`, `price`, `*`, `qty`, `+`, `10`, `;`.

Токены — плоский список. Из него ещё не видно, что сначала умножать, а потом складывать.

---

## Парсер: токены в дерево

**Синтаксический анализ** строит из токенов дерево по **грамматике** языка. У формул она такая:

```text
expr   = term (('+' | '-') term)*
term   = factor (('*' | '/') factor)*
factor = число | имя | '(' expr ')' | '-' factor
```

Приоритет операций записан в самой грамматике: `term` собирает умножения раньше, чем `expr` доходит до сложения. Такой парсер называется **рекурсивным спуском** — каждое правило становится функцией:

```js
function expr() {
  let node = term();
  while (peek() === '+' || peek() === '-') {
    node = { type: 'bin', op: next().type, left: node, right: term() };
  }
  return node;
}
```

Результат — **абстрактное синтаксическое дерево**, AST. Для формулы цены корень — сложение, слева умножение, справа `delivery`:

```text
          +
        /   \
       *     delivery
     /   \
 price    -
        /   \
       1     /
           /   \
   discount     100
```

Скобок в дереве нет — они нужны только чтобы его построить. Цикл `while` даёт **левую ассоциативность**: `2 - 3 - 4` разбирается как `(2 - 3) - 4`.

### AST в инструментах фронтенда

Почти все инструменты фронтенда работают с AST: Babel и TypeScript разбирают код, меняют дерево и печатают обратно, ESLint ищет в дереве шаблоны, Prettier печатает дерево заново по своим правилам, бандлер находит в нём `import` и неиспользуемый код. Как пишут преобразования AST и кодмоды — в [Транспиляции](/content/advanced-tooling/transpilation).

### Парсер работает до выполнения

Парсер разбирает весь файл до того, как выполнится первая строка. Поэтому синтаксическая ошибка в конце скрипта означает, что не выполнится ничего: в проверке скрипт `globalThis.ran = true;` с `let x = ;` следующей строкой бросил `SyntaxError`, а `ran` так и осталось `undefined`.

Грамматика JavaScript содержит правило **автоматической вставки точки с запятой** (ASI), и оно влияет на дерево:

```js
function f() {
  return
  { ok: true }
}
f(); // undefined
```

После `return` перевод строки запрещён, и парсер вставляет точку с запятой. В проверке acorn построил `ReturnStatement` без аргумента, а `{ ok: true }` стал блоком с меткой `ok`. Код синтаксически верный, просто означает не то, что задумано.

Дерево построено и синтаксически верно. Но верно ли оно по смыслу?

## Семантический анализ

Синтаксис не знает, существует ли переменная `prise` и можно ли умножать строку на объект. Это проверяет **семантический анализ**: он связывает имена с объявлениями, выводит и проверяет типы, ищет недостижимый код.

В языке формул проверка простая — все имена должны быть из списка известных:

```js
check(parse(tokenize('prise * 2')), ['price', 'discount', 'delivery']);
// ReferenceError: Неизвестная переменная prise
```

Ошибка найдена при сохранении формулы, а не когда клиент открыл карточку товара. В этом смысл проверок до выполнения. JavaScript почти не делает семантических проверок заранее — опечатка в имени станет `ReferenceError` только при выполнении этой строки. Этот этап для JavaScript добавляет TypeScript: проверка типов — его семантический анализ.

## Оптимизация

Оптимизатор переписывает дерево или промежуточное представление в эквивалентное, но более быстрое. Простейшая оптимизация — **свёртка констант**: всё, что известно заранее, вычисляется при компиляции.

```js
fold(parse(tokenize('price * (1 - 15 / 100) + 100 * 3')));
// дерево для price * 0.85 + 300
```

Настоящие компиляторы для этого переводят AST в **промежуточное представление** (IR) — форму, удобную для анализа, — и делают десятки проходов: удаляют мёртвый код, выносят вычисления из циклов, встраивают маленькие функции на место вызова. Минификаторы и бандлеры делают то же с JavaScript на уровне исходников: свёртка констант и удаление неиспользуемого кода — это и есть tree shaking ([Оптимизация сборки](/content/advanced-tooling/optimization)).

Дерево готово и оптимизировано. Осталось его выполнить, и здесь пути расходятся.

## Выполнение: интерпретатор, байткод, машинный код

Из одного AST можно сделать три разные вещи.

**Интерпретатор обходит дерево** при каждом вычислении:

```js
function interpret(node, env) {
  switch (node.type) {
    case 'num': return node.value;
    case 'name': return env[node.name];
    case 'bin': return ops[node.op](interpret(node.left, env), interpret(node.right, env));
  }
}
interpret(ast, { price: 1000, discount: 15, delivery: 300 }); // 1150
```

Стартует мгновенно, но каждый раз заново ходит по объектам дерева.

**Компилятор в байткод** превращает дерево в плоский список простых команд для **виртуальной машины**. У стековой машины команды берут операнды со стека и кладут туда результат:

```text
load price, push 1, load discount, push 100, /, -, *, load delivery, +
```

Список компактнее дерева, его быстрее выполнять и легко сохранить. Так работают JVM, CPython и первый уровень V8 — интерпретатор Ignition. Его байткод для `function add(a, b) { return a + b }` в проверке — три команды:

```text
Ldar a1
Add a0, [0]
Return
```

V8 использует регистровую машину с аккумулятором: `Ldar` загружает аргумент в аккумулятор, `Add` прибавляет другой аргумент, `[0]` — ячейка, куда интерпретатор записывает, какие типы видел.

**Компилятор в машинный код** выдаёт инструкции процессора. Делать это можно заранее (**AOT**, ahead of time) — так работают C, Rust и Go — или во время выполнения (**JIT**, just in time). Наш язык формул может схитрить: сгенерировать JavaScript и отдать его движку, а тот сам скомпилирует его в машинный код.

```js
const compile = (ast) => new Function('env', `return ${toJs(ast)};`);
// ((env.price * (1 - (env.discount / 100))) + env.delivery)
```

Формула из админки разобрана своим парсером, поэтому в сгенерированный код попадают только числа, имена из списка и четыре оператора. Это не `eval` пользовательского ввода.

| | Интерпретатор | AOT-компилятор | JIT-компилятор |
| --- | --- | --- | --- |
| Запуск | мгновенный | после сборки | мгновенный, потом разгон |
| Пиковая скорость | низкая | высокая | высокая на горячем коде |
| Знает реальные типы | да, но не использует | нет, только статические | да, по профилю выполнения |
| Пример | Ignition в V8, CPython | Rust, Go, C | TurboFan и Maglev в V8, HotSpot в JVM |

JIT выигрывает у AOT для динамических языков: он видит, какие типы реально приходят, и компилирует под них. Если предположение нарушится, машинный код выбрасывается — это деоптимизация. Как это устроено в V8 — уровни компиляции, inline caches, скрытые классы — в [Введении в JavaScript](/content/javascript/introduction). Формат, который браузер компилирует сразу в машинный код, — [WebAssembly](/content/additional-topics/webassembly).

## Транспиляторы

**Транспилятор** — компилятор, у которого на выходе тоже исходный код, обычно на том же уровне абстракции. Фронтенд построен на них:

- **TypeScript → JavaScript:** типы стираются, а `enum` превращается в код. В проверке esbuild выдал JavaScript и для `const n: number = "строка"` — транспилятор не проверяет типы. Подробно — в [Введении в TypeScript](/content/typescript/introduction).
- **JSX → вызовы функций:** `<Button size="s">Купить</Button>` становится `jsx(Button, { size: "s", children: "Купить" })`.
- **Новый синтаксис → старый:** для `chrome 70` Babel переписал `user?.name ?? "гость"` через проверки на `null` и `void 0`.

Что можно и что нельзя понизить, полифилы и цели сборки — в [Транспиляции](/content/advanced-tooling/transpilation).

## Типизация

Языки классифицируют по двум независимым осям, и их часто путают.

**Статическая или динамическая — когда проверяются типы.** При статической — до запуска, у переменной есть тип: TypeScript не даст присвоить строку переменной, выведенной как `number`. При динамической тип есть только у значения, а переменная может хранить что угодно: в JavaScript `let x = 5; x = 'пять'` — нормальный код.

**Сильная или слабая — приводит ли язык типы неявно.** JavaScript приводит:

```js
'5' * 2;  // 10
'5' + 2;  // '52'
```

Python — тоже динамический, но сильный. В проверке `'5' + 2` там бросил `TypeError: can only concatenate str (not "int") to str`, а `'5' * 2` дал `'55'` — повтор строки, а не приведение к числу.

| | Слабая | Сильная |
| --- | --- | --- |
| Динамическая | JavaScript, PHP | Python, Ruby |
| Статическая | C | Java, Rust, Go, TypeScript |

TypeScript — особый случай: статическая проверка поверх JavaScript, которая стирается при сборке. Поэтому во время выполнения правила остаются правилами JavaScript, и данные из сети тип не проверяет. Ещё одна ось — **номинальная или структурная** типизация: совместимы ли типы по имени (Java) или по форме (TypeScript). Подробно — в [Введении в TypeScript](/content/typescript/introduction).

## Красные флаги в ответе

- **«JavaScript — интерпретируемый язык».** Интерпретируемой бывает реализация. V8 интерпретирует байткод и компилирует горячий код в машинный, Hermes компилирует JavaScript в байткод при сборке.
- **«Компилятор переводит код построчно»** или **«интерпретатор читает файл построчно».** Оба сначала разбирают весь текст: поэтому синтаксическая ошибка в конце файла не даёт выполниться началу.
- **«Сильная типизация — это статическая».** Это разные оси: Python динамический и сильный, C статический и слабый.
- **«TypeScript проверяет типы во время выполнения».** Типы стираются; во время выполнения работает обычный JavaScript.
- **«Чтобы посчитать формулу пользователя, хватит `eval` с проверкой регуляркой».** Пользовательский текст разбирают своим парсером с белым списком конструкций.
- **«AST — это что-то внутри компилятора».** С AST каждый день работают ESLint, Prettier, Babel и бандлеры.

## Как спрашивают на собеседовании

::question
Чем компилятор отличается от интерпретатора? JavaScript — интерпретируемый язык?

#answer
Компилятор переводит программу целиком в другую форму — машинный код, байткод или другой язык, — а выполняет её потом. Интерпретатор выполняет программу сам, обходя дерево или байткод. Интерпретируемость — свойство реализации: V8 компилирует JavaScript в байткод, интерпретирует его, а горячие функции компилирует JIT-компилятором в машинный код.

#more
Интерпретатор быстро стартует, компилятор даёт высокую пиковую скорость, JIT совмещает оба: начинает с интерпретации и собирает профиль типов, а потом компилирует то, что выполняется часто. Hermes в React Native компилирует JavaScript в байткод при сборке, чтобы приложение запускалось быстрее. Для динамического языка JIT может быть быстрее AOT: он видит реальные типы.

#followups
- «Что такое деоптимизация?» → JIT скомпилировал код под увиденные типы; пришёл другой тип — машинный код выбрасывается, выполнение возвращается в интерпретатор
::

::question
Из каких этапов состоит компилятор?

#answer
Лексер превращает текст в токены. Парсер строит из токенов дерево по грамматике — AST. Семантический анализ проверяет имена и типы. Оптимизатор упрощает программу, обычно на промежуточном представлении. Генератор выдаёт результат: машинный код, байткод или исходник на другом языке.

#more
Первые этапы называют фронтендом компилятора, последние — бэкендом; промежуточное представление между ними позволяет одному бэкенду обслуживать много языков, как в LLVM. Ошибки каждого этапа разные: недопустимый символ — лексер, непарная скобка — парсер, неизвестная переменная или несовместимый тип — семантика. Приоритет операций задаёт грамматика, а не отдельная таблица.
::

::question
Что такое AST и где фронтенд с ним сталкивается?

#answer
AST — абстрактное синтаксическое дерево: структура программы без лишних деталей текста вроде скобок и пробелов. Узлы — объявления, выражения, операторы. С ним работают Babel и TypeScript при транспиляции, ESLint при поиске проблем, Prettier при форматировании, бандлеры при поиске импортов и неиспользуемого кода.

#more
Кодмоды для массовых изменений кода тоже работают с AST, а не с регулярками: регулярка не отличит вызов функции от строки с таким же текстом. Посмотреть дерево можно в AST Explorer. Узлы хранят позиции в исходнике — поэтому линтер показывает строку и колонку, а source maps связывают собранный код с исходным.
::

::question
Что вернёт функция, если после `return` перенести объект на следующую строку? Почему?

#answer
`undefined`. Грамматика JavaScript запрещает перевод строки после `return`, и правило автоматической вставки точки с запятой ставит её сразу после `return`. Объект на следующей строке парсер разбирает как блок с меткой — код синтаксически верный, но недостижимый.

#more
Те же ограничения действуют после `throw`, `break`, `continue` и `yield`, перед постфиксными `++` и `--` и перед `=>`. Обратная проблема — строка, начинающаяся с `(`, `[` или шаблонной строки: точка с запятой не вставится, и она продолжит предыдущее выражение. Prettier и ESLint ловят оба случая.
::

::question
Чем статическая типизация отличается от сильной?

#answer
Это разные оси. Статическая или динамическая — когда проверяются типы: до запуска или во время выполнения. Сильная или слабая — приводит ли язык типы неявно. JavaScript динамический и слабый, Python динамический и сильный, Java статическая и сильная.

#more
В JavaScript `'5' * 2` даёт 10, а `'5' + 2` — `'52'`; в Python `'5' + 2` бросает `TypeError`. TypeScript добавляет статическую проверку, но после сборки остаётся JavaScript с его приведениями, поэтому данные на границе — из сети, из `localStorage` — проверяют в рантайме схемами. Третья ось — номинальная или структурная совместимость: TypeScript структурный.
::

::question
Что такое байткод и виртуальная машина? Зачем они нужны?

#answer
Байткод — компактный набор простых команд для программной машины, а не для конкретного процессора. Виртуальная машина выполняет его — интерпретацией или JIT-компиляцией. Так один скомпилированный файл работает на любой платформе, где есть машина, а исходник не нужно разбирать при каждом запуске.

#more
JVM, CLR, CPython и V8 устроены так. Машины бывают стековые (JVM, CPython: операнды на стеке) и регистровые (Ignition в V8: регистры и аккумулятор). Байткод V8 можно увидеть флагом `--print-bytecode`. WebAssembly — тоже формат для виртуальной машины, но спроектированный так, чтобы его можно было быстро скомпилировать в машинный код.
::

## Практика

::practice{title="Калькулятор без eval"}
На собеседовании просят: функция `calc('2 + 3 * (4 - 1)')` возвращает 11. Нельзя использовать `eval` и `new Function`. Поддержать числа, `+ - * /`, скобки и унарный минус.

#solution
Решение — лексер и парсер рекурсивным спуском. Каждый уровень приоритета — своя функция, цикл `while` даёт левую ассоциативность. Вычислять можно прямо в парсере, без отдельного дерева:

```js
function calc(src) {
  const tokens = src.match(/\d+(\.\d+)?|[-+*/()]/g) ?? [];
  if (tokens.join('') !== src.replace(/\s+/g, '')) throw new SyntaxError('Недопустимый символ');
  let pos = 0;
  const peek = () => tokens[pos];
  const next = () => tokens[pos++];

  function expr() {
    let value = term();
    while (peek() === '+' || peek() === '-') value = next() === '+' ? value + term() : value - term();
    return value;
  }
  function term() {
    let value = factor();
    while (peek() === '*' || peek() === '/') value = next() === '*' ? value * factor() : value / factor();
    return value;
  }
  function factor() {
    const t = next();
    if (t === '-') return -factor();
    if (t === '(') {
      const value = expr();
      if (next() !== ')') throw new SyntaxError('Ожидалась )');
      return value;
    }
    if (t !== undefined && /^\d/.test(t)) return Number(t);
    throw new SyntaxError(`Неожиданный токен ${t}`);
  }

  const result = expr();
  if (pos < tokens.length) throw new SyntaxError(`Лишний токен ${peek()}`);
  return result;
}

calc('2 + 3 * (4 - 1)'); // 11
calc('-(2 + 3) * 4');    // -20
calc('8 / 4 / 2');       // 1
```

Вопросы, которые обычно задают дальше: как добавить степень (правоассоциативна: `2 ^ 3 ^ 2` = 2^9 — правило вызывает само себя справа), как добавить переменные (токен-имя и объект окружения) и как сообщать позицию ошибки (хранить в токене индекс).
::

::practice{title="Найди баг: 2 − 3 − 4 = 3"}
Парсер формул написан так:

```js
function expr() {
  const left = term();
  if (peek() === '+' || peek() === '-') {
    return { type: 'bin', op: next().type, left, right: expr() };
  }
  return left;
}
```

`2 + 3 + 4` считается правильно, а `2 - 3 - 4` даёт 3 вместо −5. Почему?

#solution
Правая часть разбирается рекурсивным вызовом `expr()`, поэтому выражение группируется справа: `2 - (3 - 4)` = 3. Для сложения это незаметно, оно ассоциативно, а для вычитания и деления результат другой.

Левая ассоциативность получается циклом, который каждый раз делает текущее дерево левым операндом:

```js
function expr() {
  let node = term();
  while (peek() === '+' || peek() === '-') {
    node = { type: 'bin', op: next().type, left: node, right: term() };
  }
  return node;
}
```

Теперь `2 - 3 - 4` разбирается как `(2 - 3) - 4` = −5. Правая рекурсия нужна только для правоассоциативных операций — степени и присваивания.
::

::practice{title="Что вернёт функция?"}
```js
function getConfig() {
  return
  {
    theme: 'dark'
  }
}
console.log(getConfig());
```

#solution
`undefined`. После `return` перевод строки запрещён грамматикой, и парсер вставляет точку с запятой: функция возвращает `undefined`, а блок `{ theme: 'dark' }` с меткой `theme` недостижим.

Исправление — открывающая скобка на той же строке, что и `return`:

```js
function getConfig() {
  return {
    theme: 'dark',
  };
}
```

Prettier переносит скобку сам, а правило ESLint `no-unreachable` подсвечивает код после `return`.
::
