# Парадигмы программирования

Парадигма — способ думать о программе: как последовательность команд, как набор объектов, которые обмениваются сообщениями, как композицию функций или как описание желаемого результата. Языки обычно поддерживают несколько парадигм, а JavaScript — почти все. Спрашивают, чем императивный подход отличается от декларативного, какие парадигмы есть и к какой относится JavaScript. Глубже — где кончается декларативность React и почему декларативный код всё равно выполняется императивно.

::tldr
- **Императивный код говорит, как получить результат:** шаги, изменяемые переменные, порядок. **Декларативный — что нужно получить**, а как, решает исполнитель: база данных, браузер, фреймворк.
- **Главные семейства:** процедурное (функции над общими данными), объектно-ориентированное (объекты с состоянием и поведением), функциональное (чистые функции и неизменяемые данные), декларативные языки (SQL, HTML, CSS), реактивное (потоки изменений).
- **JavaScript мультипарадигменный:** функции — значения, есть прототипы и классы, замыкания, итераторы и промисы. Стиль выбирают под задачу, а не под язык.
- **Декларативность — слой поверх императивного кода.** `SELECT` выполняет план запроса, React — вызовы DOM API, CSS — раскладку. Когда абстракции не хватает, нужен выход в императивный слой: ref, эффект, хинт планировщику.
::

---

## Что такое парадигма

Сквозной пример — каталог чая: нужно показать названия чаёв в наличии дешевле 500 рублей, по возрастанию цены.

```js
const products = [
  { name: 'Улун', price: 450, inStock: true },
  { name: 'Пуэр', price: 900, inStock: true },
  { name: 'Сенча', price: 300, inStock: false },
  { name: 'Ассам', price: 250, inStock: true },
  { name: 'Матча', price: 480, inStock: true },
];
// нужно: ['Ассам', 'Улун', 'Матча']
```

Задачу можно решить по-разному, и разница не в синтаксисе, а в том, что программист держит в голове: шаги и переменные, объекты и их ответственность, преобразования данных или сам результат. Эти способы думать и называют **парадигмами**.

Парадигма — не свойство языка, а стиль. На C можно писать объектно, на Java — функционально. Язык лишь делает какой-то стиль удобнее: в Haskell нет изменяемых переменных, в Java всё живёт внутри классов, а в JavaScript функции — обычные значения.

Первое и главное деление — на императивный и декларативный подходы.

---

## Императивный подход

**Императивная** программа — последовательность команд, которые меняют состояние. Так работает процессор, и так написаны первые языки: присвоить, проверить, перейти.

```js
const result = [];
for (let i = 0; i < products.length; i++) {
  const p = products[i];
  if (p.inStock && p.price < 500) {
    let j = result.length;
    while (j > 0 && result[j - 1].price > p.price) j--;   // ищем место вставки
    result.splice(j, 0, p);
  }
}
const names = [];
for (const p of result) names.push(p.name);
```

Всё под контролем: порядок, память, ранний выход из цикла. Цена — чтобы понять, *что* делает код, надо мысленно выполнить *как*: индексы, вложенный цикл, промежуточные массивы. И каждая изменяемая переменная — место для ошибки.

### Процедурное программирование

**Процедурный** стиль — императивный код, разбитый на процедуры: функции, которые работают с общими данными. Так написаны C, Pascal и большинство скриптов. Данные и функции существуют отдельно: `applyDiscount(cart)`, `calcTotal(cart)`, `printReceipt(cart)`.

Это просто и прямолинейно, пока данных немного. Когда десятки функций меняют одну структуру, становится трудно понять, кто и когда её испортил. Два ответа на эту проблему — объединить данные с функциями, которые имеют право их менять (ООП), или перестать менять данные (функциональное программирование).

---

## Объектно-ориентированный подход

**ООП** складывает данные и операции над ними в объекты и прячет внутреннее состояние за методами. Корзина сама знает, как применить скидку и посчитать сумму, а снаружи видно только `cart.applyDiscount(code)` и `cart.total`. Кто может менять данные — ясно: только методы объекта.

ООП хорошо описывает сущности с жизненным циклом и состоянием: сущности предметной области, виджеты, соединения, игровые объекты. Принципы, наследование и его проблемы — в [ООП](/content/computer-science/oop).

---

## Функциональный подход

**Функциональный** стиль строит программу из **чистых функций** — результат зависит только от аргументов, побочных эффектов нет — и не меняет данные, а создаёт новые:

```js
const cheap = products
  .filter((p) => p.inStock && p.price < 500)
  .toSorted((a, b) => a.price - b.price)
  .map((p) => p.name);
```

Код читается как описание: отфильтровать, отсортировать, взять названия. Исходный массив не тронут — `toSorted` возвращает копию, тогда как `sort` сортирует на месте. Каждый шаг можно проверить отдельно. Цена — промежуточные массивы и непривычность для тех, кто думает шагами. Подробно — в [Функциональном программировании](/content/computer-science/fp).

Функциональный конвейер — уже шаг к декларативности: мы говорим, *что* сделать с данными, а не как обходить массив. Следующий шаг — не говорить и этого.

---

## Декларативный подход

**Декларативная** программа описывает желаемый результат, а способ его получить выбирает исполнитель. Та же задача на SQL:

```sql
SELECT name FROM products
WHERE in_stock = 1 AND price < 500
ORDER BY price;
```

Здесь нет ни цикла, ни сортировки — база данных сама решит, читать ли таблицу целиком или идти по индексу. В проверке запрос к SQLite вернул тот же список, что и оба варианта на JavaScript.

Фронтенд-разработчик пишет декларативно каждый день:

- **HTML** описывает структуру документа, а не команды построения DOM;
- **CSS** описывает, как должен выглядеть результат: `display: grid` вместо вычисления координат. Как браузер превращает это в пиксели — в [Рендеринге](/content/web/rendering);
- **шаблоны и JSX** описывают, каким должен быть интерфейс при данном состоянии.

### Декларативный интерфейс

Императивный интерфейс реагирует на каждое событие отдельной командой: добавили товар в корзину — вставить `<li>`, удалили — найти и убрать. Каждый новый переход — новый код, и стоит забыть один, как экран расходится с данными. В проверке товар удалили из массива, а обработчик удаления для DOM не написали — на экране осталось три товара при двух в корзине.

Декларативный интерфейс — функция от состояния. Код не знает о переходах, он описывает результат:

```js
function render(cart) {
  list.replaceChildren(...cart.map((item) => Object.assign(document.createElement('li'), { textContent: item })));
}
```

Любое изменение данных — снова `render`, и экран не может разойтись с состоянием. Пересоздавать DOM целиком дорого, поэтому React и Vue сравнивают описание с прошлым и применяют минимальные изменения. Подробно — в [Введении в React](/content/reactjs/introduction).

### Декларативность — слой поверх императивного

Под любым декларативным слоем работает императивный код: SQL выполняется планом запроса, CSS — алгоритмом раскладки, JSX — вызовами `appendChild` и `setAttribute`. Абстракция хороша, пока исполнитель угадывает намерение. Когда нет, нужен выход вниз:

- в базе — индекс или переписанный запрос, когда план выбран неудачно;
- в React — `ref` для фокуса, измерения и сторонних библиотек, эффект для синхронизации с внешним миром;
- в CSS — `will-change` или `contain` как подсказка движку.

Хороший ответ на собеседовании показывает, что ты видишь оба слоя.

## Другие парадигмы

- **Реактивная** — программа как граф зависимостей: значения пересчитываются, когда меняются источники. Таблицы в Excel, сигналы и RxJS. Подробно — в [Реактивном программировании](/content/computer-science/reactive-programming).
- **Событийная** — программа ждёт событий и реагирует обработчиками. Это модель браузера и Node.js: верхний уровень скрипта только подписывается, а работа идёт в обработчиках ([Event Loop](/content/javascript/event-loop)).
- **Логическая** — описываются факты и правила, а исполнитель ищет решение перебором. Prolog, Datalog; идеи живут в системах типов и движках правил.

Языки по основным парадигмам:

| Язык | Основное | Поддерживает |
| --- | --- | --- |
| C | процедурный | — |
| Java, C# | ООП | функциональные элементы: лямбды, потоки данных |
| Haskell | чистый функциональный | — |
| JavaScript, TypeScript | мультипарадигменный | процедурный, ООП на прототипах и классах, функциональный, событийный |
| Python | мультипарадигменный | процедурный, ООП, функциональные элементы |
| SQL | декларативный | — |

---

## Как выбирать стиль

Парадигмы не соревнуются — в одном приложении они живут слоями:

- **Описание интерфейса** — декларативно: шаблоны и компоненты как функции от состояния.
- **Бизнес-логика и преобразования данных** — функционально: чистые функции легко тестировать и переиспользовать.
- **Сущности с жизненным циклом** — объекты: соединение WebSocket, плеер, редактор.
- **Горячие циклы** — императивно: обработка миллиона точек графика в одном цикле без промежуточных массивов.

Признак зрелого ответа — не «ФП лучше ООП», а понимание, какую проблему решает каждая парадигма и чем за это платит.

---

## Красные флаги в ответе

- **«Декларативный код не выполняет команд».** Под ним всегда императивный исполнитель; декларативность — про то, кто решает, как именно.
- **«JavaScript — объектно-ориентированный (или функциональный) язык».** Он мультипарадигменный; стиль выбирают под задачу.
- **«ФП — это `map`, `filter` и `reduce`».** Это инструменты; суть — чистые функции, неизменяемость и композиция.
- **«ООП устарело, React отказался от классов».** React перешёл на функции для компонентов, но объекты и инкапсуляция никуда не делись: соединения, сторы, сущности предметной области.
- **«Декларативно всегда лучше».** Когда исполнитель ошибается — неудачный план запроса, лишние перерисовки, — нужен императивный контроль.

## Как спрашивают на собеседовании

::question
Чем императивный подход отличается от декларативного? Приведи пример из фронтенда.

#answer
Императивный код описывает, как получить результат: шаги, изменяемые переменные, порядок. Декларативный — что нужно получить, а как, решает исполнитель. Пример: вставлять и удалять `<li>` вручную на каждое изменение корзины — императивно; описать список как функцию от массива и отдать React — декларативно.

#more
Другие примеры: SQL против цикла по таблице, CSS Grid против расчёта координат в JavaScript, `filter` и `map` против `for` с `push`. Декларативность — не отсутствие команд, а перенос решений на исполнителя, который может выполнить их оптимальнее или проще для программиста. Когда он ошибается, нужен выход в императивный слой.
::

::question
Какие парадигмы программирования ты знаешь?

#answer
Императивная и её процедурный вариант — последовательность команд над общими данными. Объектно-ориентированная — объекты со скрытым состоянием и методами. Функциональная — чистые функции и неизменяемые данные. Декларативная — описание результата, как в SQL, HTML и CSS. Ещё реактивная, событийная и логическая.

#more
Парадигмы различаются тем, как они справляются с изменяемым состоянием: процедурный стиль его не ограничивает, ООП прячет за методами, ФП избегает, реактивный — распространяет изменения автоматически. Это хорошая ось, чтобы объяснить выбор стиля для конкретного кода.
::

::question
React декларативный — что это значит и где в нём императивный код?

#answer
Компонент описывает, каким должен быть интерфейс при данном состоянии, а не как перейти из одного состояния в другое. React сам вычисляет разницу с прошлым описанием и применяет минимальные изменения в DOM. Императивный код — внутри React (вызовы DOM API) и в выходах из абстракции: `ref` для фокуса и измерений, эффекты для синхронизации с внешними системами.

#more
Признак того, что выход в императивный слой оправдан, — работа с тем, что не описывается состоянием: фокус, прокрутка, анимация через Web Animations, сторонний виджет карты. Признак злоупотребления — эффект, который вычисляет одно состояние из другого: такое значение выводится прямо при отрисовке.
::

::question
JavaScript — функциональный или объектно-ориентированный язык?

#answer
Мультипарадигменный. Функции — значения первого класса, есть замыкания и методы массивов для функционального стиля; есть объекты, прототипы и классы для ООП; модель выполнения — событийная. На нём пишут и процедурные скрипты, и декларативные интерфейсы.

#more
ООП в JavaScript прототипное: классы — синтаксис поверх цепочки прототипов. Функциональный стиль ограничен тем, что данные изменяемы по умолчанию, а хвостовые вызовы в V8 не оптимизированы, поэтому неизменяемость поддерживают дисциплиной, `Object.freeze`, библиотеками вроде Immer и методами вроде `toSorted`, а рекурсию заменяют циклами.
::

::question
Когда декларативный подход становится проблемой?

#answer
Когда исполнитель принимает плохое решение, а повлиять на него трудно: база выбирает неудачный план, фреймворк лишний раз перерисовывает дерево, CSS-анимация запускает раскладку на каждом кадре. Отладка тоже сложнее: шаги скрыты, и нужно понимать модель исполнителя.

#more
Решения — подсказки исполнителю (индексы, `memo` и ключи, `will-change`) или выход в императивный слой там, где он оправдан. Знание того, как работает слой под абстракцией, — главное, что отличает пользователя фреймворка от инженера: это и есть содержание глав про рендеринг, реактивность и производительность.
::

## Практика

::practice{title="Сортировка испортила каталог"}
Функция для блока «Недорогие» сортирует товары по цене. После её вызова основной каталог тоже стал отсортирован по цене, хотя должен быть по популярности:

```js
function cheapest(list, n) {
  return list.sort((a, b) => a.price - b.price).slice(0, n);
}

const popular = await loadPopular();
showCheap(cheapest(popular, 3));
showCatalog(popular);  // уже отсортирован по цене
```

Почему и как переписать в функциональном стиле?

#solution
`sort` сортирует массив на месте и возвращает тот же массив. Функция выглядит как вычисление, а на деле меняет входные данные — побочный эффект, который виден в другом месте программы.

```js
function cheapest(list, n) {
  return list.toSorted((a, b) => a.price - b.price).slice(0, n);
}
```

`toSorted` возвращает новый массив, вход не меняется. Для старых окружений — `[...list].sort(...)`. Такие же пары есть для других мутирующих методов: `toReversed`, `toSpliced`, `with` вместо присваивания по индексу.
::

::practice{title="Удалённый товар остался на экране"}
Корзина обновляется так:

```js
function onAdd(item) {
  cart.push(item);
  const li = document.createElement('li');
  li.textContent = item.name;
  list.append(li);
}
function onRemove(id) {
  cart = cart.filter((item) => item.id !== id);
}
```

Пользователь удаляет товар, сумма меняется, а строка в списке остаётся. Почему и как устроить код, чтобы такой класс ошибок исчез?

#solution
Код императивный: каждое изменение данных должно сопровождаться своей командой для DOM. Для удаления её забыли — данные и экран разошлись. С ростом числа переходов (изменить количество, применить скидку, очистить корзину) таких мест становится всё больше.

Декларативное решение — одна функция, которая строит список из состояния, и одно правило: после любого изменения вызвать её.

```js
function render() {
  list.replaceChildren(...cart.map((item) => {
    const li = document.createElement('li');
    li.textContent = item.name;
    return li;
  }));
}

function onAdd(item) { cart.push(item); render(); }
function onRemove(id) { cart = cart.filter((item) => item.id !== id); render(); }
```

Теперь экран — всегда функция от `cart`. Пересоздание списка целиком дорого для больших списков и сбрасывает фокус и состояние полей, поэтому фреймворки сравнивают новое описание со старым и меняют только разницу — по ключам элементов.
::
