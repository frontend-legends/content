# Введение в базы данных

Почти все данные, которые показывает фронтенд, живут в базе: заказы, товары, пользователи. Фронтенд-разработчику базу проектировать не нужно, но нужно понимать, почему API отвечает медленно, почему «товар продан дважды» и что значат слова, которыми оперируют бэкенд-разработчики: транзакция, индекс, JOIN, N+1. Спрашивают, чем SQL отличается от NoSQL, что такое ACID и зачем индексы. Глубже — почему проверка «есть ли товар на складе» в коде не защищает от двойной продажи, когда индекс не работает и что говорит теорема CAP.

::tldr
- **Реляционная база хранит данные в таблицах со связями через ключи и отвечает на SQL-запросы.** Нормализация убирает дублирование, а JOIN собирает данные обратно; ограничения (`UNIQUE`, `CHECK`, внешние ключи) держат данные правильными на уровне базы.
- **Транзакция — группа операций по принципу «всё или ничего».** ACID: атомарность, согласованность, изоляция, долговечность. Проверку и изменение, которые должны быть одним целым, делают одной операцией базы или внутри транзакции.
- **Индекс — отсортированная структура (обычно B-дерево) для быстрого поиска.** Он превращает полный просмотр таблицы в поиск за O(log n), но замедляет запись и не работает, если запрос не совпадает с его левым префиксом или оборачивает колонку функцией.
- **N+1 — запрос на список и ещё по запросу на каждый элемент.** Лечится JOIN, `IN` или пакетной загрузкой; та же проблема у GraphQL-резолверов и у фронтенда, который грузит детали в цикле.
- **NoSQL — не «без SQL», а другие модели данных:** документы, ключ-значение, столбцы, графы. Выбор — компромисс между гибкостью схемы, масштабированием и гарантиями согласованности.
::

## Реляционная модель

Сквозной пример — интернет-магазин чая: покупатели, товары с остатком на складе и заказы.

**Реляционная** база хранит данные в **таблицах**: строка — запись, столбец — атрибут с типом. У каждой строки есть **первичный ключ** — уникальный идентификатор. Связи между таблицами — **внешние ключи**: в заказе хранится `customer_id`, а не имя и почта покупателя.

```sql
CREATE TABLE customers (id INTEGER PRIMARY KEY, email TEXT NOT NULL UNIQUE, name TEXT);
CREATE TABLE products  (id INTEGER PRIMARY KEY, title TEXT, price INTEGER, stock INTEGER CHECK (stock >= 0));
CREATE TABLE orders    (id INTEGER PRIMARY KEY,
                        customer_id INTEGER NOT NULL REFERENCES customers(id),
                        product_id INTEGER REFERENCES products(id), qty INTEGER);
```

**Нормализация** — раскладка данных так, чтобы каждый факт хранился в одном месте. Если хранить имя покупателя в каждом заказе, смена имени потребует обновить сотни строк, а пропущенная строка создаст противоречие. Нормальные формы формализуют это правило; на практике достаточно помнить: факт — в одном месте, связь — через ключ. Иногда данные сознательно **денормализуют** — дублируют ради скорости чтения, — и тогда отвечают за синхронизацию копий.

**Ограничения** держат данные правильными на уровне базы, а не только кода. В проверке SQLite отклонил второго покупателя с той же почтой (`UNIQUE`), заказ несуществующего покупателя (внешний ключ) и отрицательный остаток (`CHECK`). Проверка в коде приложения такую гарантию не даёт: код бывает разный, а база одна.

## SQL

SQL — декларативный язык: запрос описывает, какой результат нужен, а как его получить, решает планировщик базы ([Парадигмы](/content/computer-science/paradigms)). Команды делят на группы: описание схемы (`CREATE`, `ALTER`), работа с данными (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) и права (`GRANT`).

### JOIN

Нормализация разложила данные по таблицам, а **JOIN** собирает их обратно:

```sql
SELECT c.name, COUNT(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id;
```

- **INNER JOIN** — только пары, где нашлось совпадение. Покупатель без заказов в результат не попадёт;
- **LEFT JOIN** — все строки левой таблицы, а где пары нет — `NULL` справа. Так получают «всех покупателей и число их заказов, включая ноль»;
- **RIGHT** и **FULL** — зеркальные варианты, на практике редки.

В проверке `INNER JOIN` вернул двух покупателей, а `LEFT JOIN` — троих, с нулём заказов у Веры. Путаница между ними — частая причина «пропавших» строк в отчётах.

## Транзакции и ACID

Оформление заказа — две операции: создать заказ и уменьшить остаток. Если вторая упадёт, а первая останется, в базе будет заказ на товар, которого нет. **Транзакция** объединяет операции: либо выполняются все, либо ни одна.

```js
db.exec('BEGIN');
try {
  insertOrder.run(customerId, productId, qty);
  decreaseStock.run(qty, productId);   // CHECK (stock >= 0) не даст уйти в минус
  db.exec('COMMIT');
} catch (e) {
  db.exec('ROLLBACK');                 // заказ тоже отменён
  throw e;
}
```

В проверке заказ пяти чайников при трёх на складе нарушил `CHECK`, и после `ROLLBACK` в базе не осталось ни заказа, ни изменения остатка.

Гарантии транзакций описывает **ACID**:

- **атомарность** (Atomicity) — всё или ничего;
- **согласованность** (Consistency) — после транзакции выполнены все ограничения схемы;
- **изоляция** (Isolation) — параллельные транзакции не видят промежуточных состояний друг друга (насколько строго — зависит от уровня изоляции);
- **долговечность** (Durability) — после `COMMIT` данные переживут сбой и перезапуск.

### Изоляция и двойная продажа

Остался один пуэр, и два покупателя нажимают «Купить» одновременно. Сервер делает так:

```js
const { stock } = selectStock.get(productId);  // оба видят 1
if (stock > 0) updateStock.run(stock - 1, productId);
```

Это та же гонка «проверить, потом действовать», что и в [Потоках](/content/computer-science/threads): между чтением и записью успевает вмешаться другой запрос. В проверке два соединения с одной базой оба прочитали остаток 1 и оба продали товар.

Решение — сделать проверку и изменение одной операцией базы:

```sql
UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0;
-- изменилась одна строка — продали, ноль — товар закончился
```

В проверке первый покупатель получил товар, второй — отказ. Другие способы — блокировка строки (`SELECT … FOR UPDATE` в :term[PostgreSQL]{def="популярная открытая реляционная база данных"}), более строгий уровень изоляции или оптимистичная блокировка с номером версии.

**Уровни изоляции** определяют, какие аномалии параллельных транзакций допускаются:

| Уровень | Что ещё возможно |
| --- | --- |
| Read Uncommitted | чтение незафиксированных изменений чужой транзакции |
| Read Committed | повторное чтение той же строки даёт другой результат |
| Repeatable Read | появление новых строк, подходящих под условие (фантомы) |
| Serializable | ничего: результат как при последовательном выполнении |

По умолчанию PostgreSQL работает на Read Committed, MySQL (:term[InnoDB]{def="основной движок хранения MySQL с транзакциями и блокировками строк"}) — на Repeatable Read. Поэтому «у нас же транзакция» не защищает от двойной продажи: на Read Committed оба запроса внутри транзакций прочитают остаток 1.

## Индексы

Чтобы найти товары с ценой 4500, базе без индекса придётся прочитать каждую строку — **полный просмотр**, O(n). **Индекс** — отдельная отсортированная структура по значениям столбца со ссылками на строки, обычно **B-дерево**: широкое и неглубокое, поиск за O(log n) и несколько чтений с диска.

`EXPLAIN` показывает, как база собирается выполнить запрос. В проверке на 50 000 товаров:

```text
SELECT * FROM products WHERE price = 4500
без индекса:         SCAN products
CREATE INDEX products_price ON products(price)
с индексом:          SEARCH products USING INDEX products_price (price=?)
```

Индекс не бесплатный: каждая вставка и изменение обновляют все индексы таблицы, и индексы занимают место. Поэтому индексируют то, по чему ищут, сортируют и соединяют, а не всё подряд.

Когда индекс **не работает**:

- **запрос не использует левый префикс составного индекса.** Индекс `(category, price)` отсортирован сначала по категории. Он помогает в `WHERE category = 'чай' AND price < 100`, но не в `WHERE price = 4500` — в проверке такой запрос снова стал `SCAN`;
- **колонка обёрнута функцией.** `WHERE lower(email) = ?` не использует индекс по `email` — нужен индекс по выражению или хранение уже нормализованного значения;
- **условие выбирает почти всю таблицу** — планировщик сочтёт полный просмотр дешевле;
- **поиск по середине строки** — `LIKE '%чай%'` не использует обычный индекс; для этого есть полнотекстовые индексы.

## N+1

Страница «Покупатели» показывает число заказов у каждого. Простой код на сервере:

```js
const customers = db.prepare('SELECT id, name FROM customers').all();
for (const c of customers) {
  c.orders = db.prepare('SELECT COUNT(*) AS n FROM orders WHERE customer_id = ?').get(c.id).n;
}
```

Один запрос на список и ещё по одному на каждого покупателя — **N+1 запросов**. На тысяче покупателей это тысяча походов в базу, и каждый стоит сетевой задержки. В проверке на трёх покупателях вышло четыре запроса, а `LEFT JOIN` с `GROUP BY` дал тот же результат одним.

:term[ORM]{def="библиотека, которая отображает таблицы базы на объекты кода и сама строит SQL"} прячут эту проблему: обращение к связанному полю в цикле незаметно делает запрос. Поэтому в Prisma пишут `include`, в Mongoose — `populate`, а в GraphQL пакетные загрузчики вроде :term[DataLoader]{def="библиотека, которая собирает одиночные запросы за один такт событий в один пакетный"} собирают запросы резолверов в один ([GraphQL](/content/network-api/graphql)). Фронтенд делает то же самое, когда загружает список, а потом детали каждого элемента отдельным `fetch`: N+1 по сети ещё дороже.

### Параметры вместо склейки строк

Запрос, собранный склейкой строк с пользовательским вводом, позволяет вводу стать частью SQL — это **SQL-инъекция**. В проверке значение `x' OR '1'='1`, подставленное в строку запроса, превратило условие поиска в истинное для всех строк. Параметризованный запрос передаёт значение отдельно от текста запроса, и оно остаётся значением:

```js
db.prepare('SELECT name FROM customers WHERE email = ?').all(email);
```

Все драйверы и ORM поддерживают параметры; склеивать SQL с вводом нельзя никогда.

## NoSQL

**NoSQL** — общее название баз с другими моделями данных:

| Тип | Модель | Примеры | Когда |
| --- | --- | --- | --- |
| документные | JSON-документы с вложенностью | MongoDB, Firestore | данные читаются целиком и редко соединяются: карточка товара с атрибутами |
| ключ-значение | значение по ключу, часто в памяти | Redis, Memcached | кеш, сессии, счётчики, очереди |
| широкие столбцы | строки с множеством колонок, распределённые по узлам | Cassandra, ScyllaDB | огромные объёмы записи: логи, события |
| графовые | вершины и рёбра | Neo4j | связи важнее записей: рекомендации, соцграф |
| поисковые | инвертированный индекс | Elasticsearch, OpenSearch | полнотекстовый поиск, фильтры каталога |
| аналитические | хранение по столбцам | ClickHouse | агрегаты по миллиардам строк |

Граница размыта: PostgreSQL хранит JSON в `jsonb` с индексами, а :term[MongoDB]{def="документная NoSQL-база: хранит записи как JSON-подобные документы"} поддерживает транзакции. Практический выбор по умолчанию для данных с отношениями и деньгами — реляционная база; NoSQL добавляют под конкретную задачу: кеш, поиск, аналитику.

### CAP и масштабирование

Одна база упирается в один сервер. Масштабируют двумя способами:

- **репликация** — копии данных на нескольких серверах. Запись идёт в основной, чтение можно распределить по репликам. Реплики отстают, поэтому только что сохранённый заказ может не найтись при чтении с реплики;
- **шардирование** — данные делятся между серверами по ключу, например по покупателю. Запросы по одному шарду быстрые, а между шардами — сложные.

**Теорема CAP**: в распределённой системе при разрыве сети между узлами (partition) приходится выбирать между согласованностью (consistency — все видят одни данные) и доступностью (availability — каждый запрос получает ответ). Без разрыва сети можно иметь и то и другое; выбор — что делать, когда связь пропала. CP-системы отказывают в запросе, чтобы не отдать устаревшее; AP-системы отвечают, рискуя расхождением, которое потом сводят. Для интерфейса это значит: после записи данные могут какое-то время не отражаться в ответах, и экран должен это переживать — показывать сохранённое из ответа на запись, а не перечитывать список.

## Красные флаги в ответе

- **«Проверим остаток в коде перед списанием — двойной продажи не будет».** Между чтением и записью вмешивается другой запрос; нужна атомарная операция базы или блокировка.
- **«Транзакция защищает от всех гонок».** Только на уровне Serializable; по умолчанию PostgreSQL работает на Read Committed.
- **«Индекс ускоряет всё».** Он замедляет запись, занимает место и не работает без левого префикса или с функцией над колонкой.
- **«NoSQL быстрее SQL»** или **«NoSQL — это без схемы».** Схема переезжает в код приложения, а скорость зависит от модели доступа.
- **«ORM защищает от N+1».** ORM чаще всего его и создаёт: обращение к связи в цикле — отдельный запрос.
- **«Экранируем кавычки — и можно склеивать SQL».** Только параметры гарантируют, что ввод останется значением.

## Как спрашивают на собеседовании

::question
Чем SQL отличается от NoSQL? Когда что выбирать?

#answer
Реляционные базы хранят данные в таблицах со связями, держат строгую схему и ограничения и дают транзакции и JOIN — это выбор по умолчанию для заказов, пользователей и денег. NoSQL — другие модели: документы (MongoDB), ключ-значение (Redis), широкие столбцы (Cassandra), графы (Neo4j). Их берут под задачу: кеш и сессии, гибкие документы, огромный поток записи, связи.

#more
Граница размыта: PostgreSQL умеет `jsonb` с индексами, MongoDB — транзакции. В реальном продукте обычно несколько хранилищ: PostgreSQL как источник истины, Redis для кеша, поисковый движок для каталога. «Без схемы» значит, что схему проверяет код приложения, а не база.
::

::question
Что такое транзакция и ACID?

#answer
Транзакция — группа операций, которая выполняется целиком или не выполняется вовсе. ACID — её гарантии: атомарность (всё или ничего), согласованность (после транзакции выполнены ограничения схемы), изоляция (параллельные транзакции не видят промежуточных состояний друг друга) и долговечность (зафиксированное переживёт сбой).

#more
Изоляция бывает разной строгости: Read Committed, Repeatable Read, Serializable — чем строже, тем меньше аномалий и больше конфликтов. В проверке заказ, нарушивший ограничение остатка, откатился вместе со своей записью заказа. Распределённые системы часто заменяют одну большую транзакцию цепочкой локальных с компенсациями (сага).
::

::question
Как не продать последний товар дважды?

#answer
Сделать проверку остатка и списание одной атомарной операцией базы: `UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0` и проверить число изменённых строк. Если сначала прочитать остаток, а потом записать, два параллельных запроса оба увидят единицу и оба продадут.

#more
В проверке два соединения при чтении и записи по отдельности продали один товар дважды, а условное обновление — один раз. Другие способы — блокировка строки `SELECT … FOR UPDATE`, уровень Serializable с повтором при конфликте, оптимистичная блокировка с номером версии. Ограничение `CHECK (stock >= 0)` — последняя линия защиты. На клиенте блокировка кнопки защищает только от двойного клика.
::

::question
Зачем нужны индексы и когда они вредят?

#answer
Индекс — отсортированная структура (обычно B-дерево) по значениям столбцов: поиск, сортировка и JOIN по ним идут за O(log n) вместо полного просмотра таблицы. Вред — каждая запись обновляет все индексы таблицы, и они занимают место. Поэтому индексируют столбцы из условий, сортировок и соединений, а не всё подряд.

#more
Индекс не работает, если запрос не использует левый префикс составного индекса, оборачивает колонку функцией (`lower(email)`), ищет по середине строки (`LIKE '%…'`) или выбирает большую часть таблицы. Как база выполняет запрос, показывает `EXPLAIN`: в проверке `SCAN products` после создания индекса стал `SEARCH … USING INDEX`.
::

::question
Что такое проблема N+1 и как её решать?

#answer
Один запрос получает список, а потом для каждого из N элементов делается ещё по запросу за связанными данными — N+1 походов в базу. Лечится одним запросом с JOIN, запросом с `IN (…)` по всем идентификаторам сразу или пакетной загрузкой.

#more
ORM создают N+1 незаметно, когда связь читается в цикле; поэтому есть `include` в Prisma и `populate` в Mongoose. В GraphQL каждый резолвер поля делает свой запрос, и их собирает DataLoader. Фронтенд повторяет ту же ошибку по сети, загружая детали каждого элемента списка отдельным запросом, — тогда нужен эндпоинт, который отдаёт всё сразу.
::

::question
Что такое теорема CAP и что она значит для фронтенда?

#answer
В распределённой системе при разрыве сети между узлами нельзя одновременно гарантировать согласованность — все видят одни данные — и доступность — каждый запрос получает ответ. Приходится выбирать: отказать в запросе (CP) или ответить, возможно, устаревшими данными (AP). Без разрыва сети доступны оба свойства.

#more
Для интерфейса это означает итоговую согласованность: после записи чтение с реплики может ещё не видеть изменения. Поэтому экран показывает данные из ответа на запись, а не перечитывает список сразу, и использует оптимистичные обновления с откатом. Теорему часто упрощают до «выбери два из трёх» — это неточно: выбор возникает только при разрыве сети.
::

## Практика

::practice{title="Последний пуэр продан дважды"}
```js
app.post('/buy', (req, res) => {
  const { stock } = db.prepare('SELECT stock FROM products WHERE id = ?').get(req.body.productId);
  if (stock < 1) return res.status(409).send('Нет в наличии');
  db.prepare('UPDATE products SET stock = ? WHERE id = ?').run(stock - 1, req.body.productId);
  db.prepare('INSERT INTO orders (customer_id, product_id, qty) VALUES (?, ?, 1)').run(req.user.id, req.body.productId);
  res.send('Куплено');
});
```

При распродаже на складе оказывается отрицательный остаток или два заказа на один товар. Исправь.

#solution
Чтение и запись разделены: два запроса читают остаток 1, оба проходят проверку и оба списывают. К тому же заказ и списание — две независимые операции: сбой между ними оставит одно без другого.

```js
const buy = db.prepare('UPDATE products SET stock = stock - 1 WHERE id = ? AND stock > 0');
const addOrder = db.prepare('INSERT INTO orders (customer_id, product_id, qty) VALUES (?, ?, 1)');

app.post('/buy', (req, res) => {
  db.exec('BEGIN');
  try {
    if (buy.run(req.body.productId).changes === 0) {
      db.exec('ROLLBACK');
      return res.status(409).send('Нет в наличии');
    }
    addOrder.run(req.user.id, req.body.productId);
    db.exec('COMMIT');
    res.send('Куплено');
  } catch (e) {
    db.exec('ROLLBACK');
    throw e;
  }
});
```

Проверка и списание — одна операция базы, а списание и заказ — одна транзакция. В проверке при двух одновременных покупках условный `UPDATE` пропустил только первую. `CHECK (stock >= 0)` в схеме страхует от ошибок в другом коде.
::

::practice{title="Список покупателей грузится 8 секунд"}
Эндпоинт возвращает покупателей с числом их заказов:

```js
const customers = db.prepare('SELECT id, name FROM customers').all();
for (const c of customers) {
  c.orders = db.prepare('SELECT COUNT(*) AS n FROM orders WHERE customer_id = ?').get(c.id).n;
}
```

На 5000 покупателях ответ занимает секунды. Что не так и как исправить?

#solution
N+1: один запрос на список и 5000 запросов на подсчёт. Каждый — поход в базу со своей задержкой. Один запрос с соединением отдаёт то же:

```sql
SELECT c.id, c.name, COUNT(o.id) AS orders
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id;
```

`LEFT`, а не `INNER`, чтобы покупатели без заказов остались в списке с нулём. В проверке результат совпал с вариантом N+1, а запросов стало один вместо N+1. Чтобы подсчёт по `customer_id` был быстрым, на этот столбец нужен индекс — внешние ключи в PostgreSQL и SQLite сами его не создают.
::

::practice{title="Индекс есть, а запрос медленный"}
В таблице товаров есть индекс `(category, price)`. Запрос медленный:

```sql
SELECT * FROM products WHERE price BETWEEN 100 AND 500 ORDER BY price;
```

Почему индекс не помогает и что сделать?

#solution
Составной индекс отсортирован сначала по `category`, потом по `price` внутри категории. Запрос без условия на категорию не может использовать левый префикс: цены разбросаны по всем категориям. `EXPLAIN` показывает полный просмотр — в проверке запрос по одной цене при индексе `(category, price)` стал `SCAN products`.

Варианты:

```sql
-- если такие запросы частые — отдельный индекс по цене
CREATE INDEX products_price ON products(price);

-- если в интерфейсе фильтр всегда с категорией — добавить её в запрос
SELECT * FROM products WHERE category = 'чай' AND price BETWEEN 100 AND 500 ORDER BY price;
```

Порядок столбцов в составном индексе выбирают по запросам: сначала столбец с условием равенства, потом диапазон или сортировка. Лишние индексы замедляют запись, поэтому их добавляют под реальные запросы из профиля, а не впрок.
::
