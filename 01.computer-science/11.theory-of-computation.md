# Теория вычислений

Теория вычислений отвечает на вопросы, которые кажутся философскими, но объясняют вполне практические вещи: почему регуляркой нельзя разобрать HTML, почему одна регулярка вешает сервер, почему линтер не находит все бесконечные циклы и почему некоторые задачи решают только приближённо. Спрашивают, что такое конечный автомат, Тьюринг-полнота и проблема остановки. Глубже — что такое катастрофический возврат в регулярках, почему система типов TypeScript — тоже язык программирования и что значит «задача NP-полная».

::tldr
- **Модели вычислений различаются памятью:** у конечного автомата её нет, кроме текущего состояния; у автомата со стеком — стек; у машины Тьюринга — неограниченная лента. Чем больше памяти, тем больше языков модель распознаёт.
- **Регулярные выражения — конечные автоматы:** они не умеют считать без предела, поэтому не проверяют вложенные скобки и не разбирают HTML. Для вложенности нужен стек.
- **Регулярки в JavaScript работают перебором с возвратом:** вложенные квантификаторы вроде `/^(a+)+$/` дают экспоненциальное время на неудачной строке — это уязвимость ReDoS.
- **Тьюринг-полный язык выражает любой алгоритм** — и для него неразрешима проблема остановки. Поэтому линтеры, проверка типов и tree shaking консервативны: они пропускают часть ошибок или отвергают часть правильного кода.
- **P — задачи, которые решаются быстро, NP — которые быстро проверяются.** Для NP-полных задач быстрых точных алгоритмов не известно, и на практике их решают эвристиками.
::

## Модели вычислений

Сквозной пример — оформление заказа в интернет-магазине: поле цены в админке, промокоды, проверка формул и шаги «корзина → адрес → оплата».

Чтобы рассуждать о том, что можно вычислить, нужны простые модели вычислителя. Их различает главное — **память**:

| Модель | Память | Распознаёт | Пример на практике |
| --- | --- | --- | --- |
| конечный автомат | только текущее состояние | регулярные языки | регулярные выражения, лексер, шаги оформления заказа |
| автомат со стеком | стек | контекстно-свободные языки | парсер языка программирования, проверка скобок |
| машина Тьюринга | неограниченная лента | всё вычислимое | любой язык программирования |

Иерархию языков по этим моделям описал Ноам Хомский: каждый следующий класс шире предыдущего. Практический смысл в том, что для задачи нужно выбрать инструмент нужного класса: регулярное выражение для вложенных структур слабо, а полноценный парсер для проверки формата телефона избыточен.

## Конечные автоматы

**Конечный автомат** — набор состояний, переходы между ними по входным символам, начальное состояние и множество допускающих. Автомат читает строку символ за символом, и если в конце оказался в допускающем состоянии — строка принята.

Цена в админке — цифры, необязательная точка и до двух знаков после:

```js
const transitions = {
  start: { digit: 'int' },
  int:   { digit: 'int', dot: 'dot' },
  dot:   { digit: 'frac1' },
  frac1: { digit: 'frac2' },
  frac2: {},
};
const accepting = new Set(['int', 'frac1', 'frac2']);

function isPrice(s) {
  let state = 'start';
  for (const ch of s) {
    state = transitions[state][kind(ch)];  // kind: 'digit', 'dot' или 'other'
    if (!state) return false;
  }
  return accepting.has(state);
}
isPrice('349.90'); // true
isPrice('349.');   // false — dot не допускающее
```

Это ровно то же, что регулярка `/^\d+(\.\d{1,2})?$/`: в проверке оба способа дали одинаковый ответ на восьми строках. Регулярное выражение и есть компактная запись конечного автомата, а движок строит автомат из неё.

Автоматы во фронтенде не только про строки. Шаги оформления заказа — тоже конечный автомат: из корзины можно перейти к адресу, но не к оплате, а во время оплаты нельзя вернуться назад. Если интерфейс описан автоматом, недопустимые комбинации — «загружается и показывает ошибку одновременно» — просто невозможны. Как строить на этом состояние приложения — в [Состоянии и данных](/content/architecture/state-and-data-architecture).

### Чего автомат не умеет

У конечного автомата нет памяти, кроме номера состояния, а состояний конечное число. Значит, он не может **считать без предела**: проверить, что открывающих скобок столько же, сколько закрывающих, при любой глубине вложенности. Можно построить автомат для глубины 2, 10 или 100, но не для любой. В проверке регулярка для вложенности до двух уровней приняла `(())()`, но отвергла правильную строку `((()))`.

Отсюда известный ответ на вопрос «почему HTML нельзя разбирать регулярками»: теги вкладываются на любую глубину, а это язык не регулярный. Кроме того, HTML определён не грамматикой, а алгоритмом разбора с исправлением ошибок ([Основы HTML5](/content/html/markup-language)). Регулярки годятся, чтобы найти что-то плоское в тексте, но не чтобы понять структуру.

Для вложенности нужен **стек** — это автомат со стеком, следующая ступень:

```js
function balanced(s) {
  const pairs = { ')': '(', ']': '[', '}': '{' };
  const stack = [];
  for (const ch of s) {
    if ('([{'.includes(ch)) stack.push(ch);
    else if (ch in pairs && stack.pop() !== pairs[ch]) return false;
  }
  return stack.length === 0;
}
```

Так же работают парсеры языков программирования — подробно в [Языках и компиляторах](/content/computer-science/languages-and-compilers).

## Регулярки в JavaScript и катастрофический возврат

Регулярные выражения в JavaScript только называются регулярными. Обратная ссылка `/^(.+) \1$/` — «одно и то же слово дважды» — описывает язык, который конечный автомат распознать не может, и движок её поддерживает. Цена такой мощности — способ выполнения.

Движок V8 :term[Irregexp]{def="движок регулярных выражений в V8"} работает **перебором с возвратом** (backtracking): пробует вариант, а если дальше не совпало, возвращается и пробует другой. На большинстве регулярок это быстро. Но если одну и ту же строку можно разбить между квантификаторами многими способами, а совпадения нет, движок переберёт их все:

```js
/^(a+)+$/.test('a'.repeat(24) + '!');
```

Строку из 24 букв `a` можно разбить на группы 2^23 способами, и перед ответом `false` движок пробует каждый. В проверке каждые два дополнительных символа увеличивали время в четыре раза. Тридцать символов — секунды, сорок — часы.

Это уязвимость **ReDoS**: если регулярка с таким шаблоном проверяет пользовательский ввод на сервере Node.js, одна строка занимает поток целиком, и сервер перестаёт отвечать. В браузере то же самое замораживает вкладку. Признаки опасной регулярки — вложенные квантификаторы `(a+)+`, `(a*)*`, `(\w+\s?)+` и альтернативы, которые совпадают с одним и тем же: `(a|a)+`.

Защита:

- **переписать регулярку без неоднозначности** — `/^a+$/` описывает тот же язык и в проверке обработала миллион символов за миллисекунды;
- **ограничить длину ввода** до проверки регуляркой;
- **проверять регулярки линтером** — правила вроде `regexp/no-super-linear-backtracking` находят опасные шаблоны;
- **использовать движок без возврата.** В V8 есть экспериментальный линейный движок за флагом `--enable-experimental-regexp-engine` и флаг регулярки `l`: в проверке `new RegExp('^(a+)+$', 'l')` ответил мгновенно, а регулярку с обратной ссылкой отверг с ошибкой «Cannot be executed in linear time». Обратные ссылки и просмотр назад в линейном времени невозможны — это цена гарантии.

Конечные автоматы ограничены памятью. Что будет, если память не ограничивать?

## Тьюринг-полнота

**Машина Тьюринга** — автомат с бесконечной лентой, по которой он может двигаться, читать и писать. Тезис Чёрча — Тьюринга: всё, что можно вычислить алгоритмом, может вычислить машина Тьюринга. Язык, на котором можно смоделировать машину Тьюринга, называют **Тьюринг-полным**. Для этого достаточно условий, повторения без заранее известного предела и неограниченной памяти.

Все языки программирования Тьюринг-полны. Неожиданно — многое другое тоже:

- **система типов TypeScript** — :term[условные типы]{def="типы TypeScript вида A extends B ? X : Y, которые выбирают результат по условию"} с рекурсией вычисляют. В проверке `Add<2, 3>` на уровне типов дал `5`, а попытка построить кортеж из 5000 элементов остановилась ошибкой TS2589 «Type instantiation is excessively deep and possibly infinite»: компилятор ставит предел глубины, чтобы не зависнуть;
- **SQL с рекурсивными запросами** — `WITH RECURSIVE` в проверке посчитал числа Фибоначчи, чего обычный `SELECT` не может;
- **шаблонизаторы, системы сборки, конфиги с макросами** — часто случайно.

Тьюринг-полнота — не достижение, а предупреждение: у такого языка есть все проблемы языков программирования, включая главную.

## Проблема остановки

Можно ли написать функцию `halts(program, input)`, которая для любой программы скажет, завершится ли она? Алан Тьюринг доказал, что нет. Набросок доказательства на JavaScript:

```js
function paradox() {
  if (halts(paradox)) {
    while (true) {}   // если halts говорит «остановится» — зацикливаемся
  }
  // если halts говорит «зациклится» — сразу останавливаемся
}
```

Что бы `halts` ни ответила про `paradox`, ответ окажется неверным. Значит, такой функции не существует. Обобщение — **теорема Райса**: любое нетривиальное свойство поведения программы — вернёт ли она `null`, обратится ли к неопределённой переменной, есть ли у вызова побочный эффект — алгоритмически неразрешимо в общем случае.

Это не абстракция, а объяснение того, как устроены инструменты фронтенда. Раз точный ответ невозможен, любой анализатор **консервативен** — он ошибается в безопасную сторону:

- **проверка типов** отвергает часть правильных программ (приходится писать `as` или проверку) и пропускает часть неправильных (через `any` и утверждения типов);
- **линтер** находит недостижимый код после `return`, но не после цикла, условие которого никогда не станет ложным по причинам, которые видны только при выполнении;
- **:term[tree shaking]{def="удаление при сборке кода, который никто не импортирует и не вызывает"}** оставляет вызов функции, если не может доказать, что у него нет побочных эффектов, — поэтому существует пометка `/*#__PURE__*/` ([Оптимизация сборки](/content/advanced-tooling/optimization));
- **компилятор типов** ограничивает глубину рекурсии — как TS2589 выше.

Если инструмент обещает найти *все* ошибки определённого вида в Тьюринг-полном языке, он либо ошибается, либо отвергает правильные программы.

Неразрешимые задачи — крайний случай. Чаще задача разрешима, но вопрос в том, за какое время.

## Сложность: P и NP

Сколько шагов алгоритм делает в зависимости от размера входа, описывает О-нотация — она разобрана в [Математике для CS](/content/computer-science/math-for-cs). Теория сложности группирует задачи по тому, насколько быстро их вообще можно решить.

- **P** — задачи, которые решаются за полиномиальное время: O(n), O(n log n), O(n³). Сортировка, поиск пути в графе, проверка скобок.
- **NP** — задачи, решение которых можно **проверить** за полиномиальное время. Найти расписание без конфликтов трудно, а проверить готовое — легко.
- **NP-полные** — самые трудные задачи в NP: если одну из них решить быстро, быстро решатся все. Примеры: выполнимость логической формулы (SAT), раскраска графа, задача о рюкзаке, коммивояжёр.
- **P = NP?** — главный открытый вопрос информатики. Большинство исследователей считает, что нет, но доказательства нет.

Где это встречается рядом с фронтендом:

- **разрешение версий зависимостей** с ограничениями вида `^1.2.0` в общем случае NP-полное — к ней сводится SAT. Поэтому менеджеры пакетов используют эвристики и иногда ставят дубли пакета вместо поиска единственной версии ([Менеджеры пакетов](/content/ecosystem-libs/package-management));
- **оптимальное разбиение бандла на чанки** — вариант задачи об упаковке, бандлеры решают его эвристиками;
- **расписания, маршруты доставки, раскладка элементов** без пересечений.

Практический вывод: если задача NP-трудная, не ищут оптимум. Ограничивают размер входа, берут приближённый алгоритм с гарантией качества или эвристику, которая хорошо работает на реальных данных.

## Красные флаги в ответе

- **«HTML можно распарсить регуляркой, если постараться».** Вложенность произвольной глубины не регулярна; HTML к тому же определён алгоритмом с исправлением ошибок.
- **«Регулярки всегда работают за линейное время».** Движки с возвратом на неоднозначных шаблонах работают экспоненциально — это ReDoS.
- **«TypeScript гарантирует отсутствие ошибок типов во время выполнения».** Проверка консервативна и обходится через `any` и `as`, а данные из сети не проверяются вовсе.
- **«Можно написать линтер, который найдёт все бесконечные циклы».** Это проблема остановки, она неразрешима.
- **«NP — это „не полиномиальные“ задачи».** NP — задачи с быстро проверяемым решением; P входит в NP.
- **«Тьюринг-полнота — признак мощного языка».** Это признак того, что у языка будут проблемы любого языка программирования: зависания и неразрешимый анализ.

## Как спрашивают на собеседовании

::question
Что такое конечный автомат и где он встречается во фронтенде?

#answer
Это модель вычислений с конечным набором состояний и переходами по входным событиям; памяти, кроме текущего состояния, у неё нет. Во фронтенде это регулярные выражения (движок строит из них автомат), лексеры и логика интерфейса: шаги оформления заказа, состояния загрузки, где недопустимые переходы просто не описаны.

#more
Автомат вместо набора булевых флагов исключает невозможные комбинации вроде «загружается и показывает ошибку». Библиотеки вроде XState добавляют вложенные и параллельные состояния (statecharts). Ограничение автомата — он не умеет считать без предела, поэтому для вложенных структур нужен стек.
::

::question
Почему HTML нельзя разбирать регулярными выражениями?

#answer
Регулярное выражение — конечный автомат, а у него нет памяти, чтобы следить за вложенностью произвольной глубины. Проверить, что каждому открытому тегу соответствует закрывающий на любом уровне, может только автомат со стеком. Кроме того, HTML разбирается по алгоритму, который исправляет ошибки разметки, а регулярка этого не повторит.

#more
Регулярка для фиксированной глубины возможна, но ломается на следующем уровне. Для HTML используют `DOMParser` в браузере и парсеры вроде parse5 в Node.js. Регулярки уместны для плоских задач: найти дату, проверить формат кода, разбить строку.
::

::question
Что такое катастрофический возврат в регулярках и как от него защититься?

#answer
Движок регулярок в JavaScript перебирает варианты с возвратом. Если шаблон позволяет разбить строку между квантификаторами многими способами, как `/^(a+)+$/`, а совпадения нет, перебор экспоненциальный: в проверке каждые два символа увеличивали время в четыре раза. На сервере такая регулярка на пользовательском вводе — уязвимость ReDoS.

#more
Защита: переписать шаблон без вложенных квантификаторов и пересекающихся альтернатив (`/^a+$/` для того же языка), ограничить длину ввода, проверять регулярки линтером. У V8 есть экспериментальный линейный движок за флагом с флагом регулярки `l`, но он не поддерживает обратные ссылки — их нельзя выполнить за линейное время.
::

::question
Что такое Тьюринг-полнота? Приведи неожиданный пример.

#answer
Язык Тьюринг-полный, если на нём можно выразить любое вычисление, которое может выполнить машина Тьюринга: нужны условия, повторение без заранее известного предела и неограниченная память. Неожиданный пример — система типов TypeScript: рекурсивные условные типы вычисляют, например сложение чисел через длины кортежей.

#more
Ещё SQL с `WITH RECURSIVE` и многие шаблонизаторы и конфигурационные языки. Следствие — у таких языков есть проблема остановки: компилятор TypeScript ограничивает глубину рекурсии типов и выдаёт TS2589 вместо того, чтобы зависнуть. Поэтому языки конфигурации иногда намеренно делают не Тьюринг-полными.
::

::question
Что такое проблема остановки и что она значит для инструментов разработки?

#answer
Тьюринг доказал, что нельзя написать программу, которая для любой программы определит, остановится ли она. Теорема Райса обобщает: любое нетривиальное свойство поведения программы неразрешимо в общем случае. Поэтому анализаторы кода консервативны: они либо пропускают часть ошибок, либо отвергают часть правильного кода.

#more
Примеры: TypeScript требует `as` или проверки там, где программист знает больше, чем можно доказать, и пропускает ошибки через `any`; линтер находит только очевидно недостижимый код; tree shaking оставляет вызовы, если не может доказать отсутствие побочных эффектов. Это не недоработка инструментов, а математический предел.
::

::question
Что такое P и NP? Встречаются ли NP-полные задачи во фронтенде?

#answer
P — задачи, которые решаются за полиномиальное время. NP — задачи, решение которых проверяется за полиномиальное время. NP-полные — самые трудные в NP: для них неизвестны быстрые точные алгоритмы, и если найти такой для одной, он найдётся для всех. Равны ли P и NP — открытый вопрос.

#more
Рядом с фронтендом: разрешение версий зависимостей с ограничениями в общем случае NP-полное, оптимальное разбиение бандла — вариант задачи об упаковке. На практике их решают эвристиками и приближёнными алгоритмами, ограничивают размер входа или соглашаются на неоптимальный, но достаточно хороший ответ.
::

## Практика

::practice{title="Одна регулярка повесила сервер"}
Сервис на Node.js проверяет название товара:

```js
const titleRe = /^([a-zа-яё0-9]+\s?)+$/i;
if (!titleRe.test(req.body.title)) return res.status(400).send('Недопустимое название');
```

После запроса с длинным названием, которое кончается на `!`, сервер перестал отвечать. Почему и как исправить?

#solution
Группа `([a-zа-яё0-9]+\s?)+` позволяет разбить слово из букв на части множеством способов: `\s?` необязателен, поэтому внутренний `+` и внешний делят одни и те же буквы. На строке, которая в конце не совпадает, движок с возвратом перебирает все разбиения — экспоненциально. Поток Node.js один, поэтому зависает весь сервер.

Исправленная регулярка описывает тот же язык без неоднозначности — слова, разделённые одиночными пробелами:

```js
const titleRe = /^[a-zа-яё0-9]+(?:\s[a-zа-яё0-9]+)*\s?$/i;
if (req.body.title.length > 200 || !titleRe.test(req.body.title)) {
  return res.status(400).send('Недопустимое название');
}
```

Теперь каждый символ может совпасть только одним способом. Ограничение длины до регулярки — вторая линия защиты. В проверке исходный шаблон на строке из 24 символов работал дольше, чем исправленный на строке из миллиона.
::

::practice{title="Проверь скобки"}
Напиши `isBalanced(s)`: строка из `()[]{}` и других символов сбалансирована, если каждая открывающая скобка закрыта скобкой того же типа в правильном порядке. `'([]{})'` — да, `'([)]'` — нет, `'(('` — нет.

#solution
Конечного автомата тут недостаточно: глубина вложенности не ограничена. Нужен стек — открывающие скобки кладём, закрывающая должна совпасть с верхней:

```js
function isBalanced(s) {
  const pairs = { ')': '(', ']': '[', '}': '{' };
  const stack = [];
  for (const ch of s) {
    if ('([{'.includes(ch)) stack.push(ch);
    else if (ch in pairs && stack.pop() !== pairs[ch]) return false;
  }
  return stack.length === 0;
}
```

O(n) по времени и O(n) по памяти в худшем случае. Частые ошибки: забыть проверить, что стек пуст в конце (`'(('`), и не проверить тип скобки (`'(]'`). Если скобки одного типа, стек можно заменить счётчиком — но это и есть стек, где все элементы одинаковые.
::

::practice{title="Флаги вместо состояний"}
Форма оплаты хранит состояние флагами:

```js
let isLoading = false, isError = false, isSuccess = false;
```

В Sentry приходят ошибки «одновременно показаны спиннер и сообщение об ошибке», а повторный клик во время оплаты отправляет второй запрос. Перестрой состояние.

#solution
Три булевых флага дают восемь комбинаций, а допустимых состояний четыре: ожидание, оплата, ошибка, успех. Невозможные комбинации появляются, когда один из обработчиков забывает сбросить флаг.

Конечный автомат описывает только допустимые состояния и переходы:

```js
const machine = {
  idle:    { PAY: 'paying' },
  paying:  { SUCCESS: 'success', FAILURE: 'error' },  // PAY здесь не описан
  error:   { PAY: 'paying' },
  success: {},
};
let state = 'idle';
function send(event) {
  state = machine[state][event] ?? state;            // недопустимое событие игнорируется
  render(state);
}
```

Спиннер и ошибку нельзя показать одновременно — это разные значения одной переменной. Повторный `PAY` во время оплаты игнорируется, потому что перехода нет. Для сложных потоков — вложенных и параллельных состояний — берут XState.
::
