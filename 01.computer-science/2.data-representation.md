# Представление данных

Для компьютера всё — последовательность битов: число, строка, картинка, ответ сервера. Смысл битам придаёт формат: одни и те же 8 байт могут быть числом с плавающей точкой, двумя целыми или текстом. Спрашивают, что такое дополнительный код, как устроено число `double`, чем Unicode отличается от UTF-8 и что такое Base64. Глубже — почему `~~` ломается на больших числах, откуда берутся кракозябры и почему две одинаковые на вид строки не равны.

::tldr
- **Бит — 0 или 1, байт — 8 битов, 256 значений.** Смысл байтам придаёт формат: целое, число с плавающей точкой, символ в UTF-8, пиксель.
- **Отрицательные целые хранятся в дополнительном коде:** −1 — это все единицы. Побитовые операции в JavaScript работают с 32-битными целыми, поэтому `(2 ** 31) | 0` даёт отрицательное число.
- **`number` — 64-битный `double`:** 1 бит знака, 11 битов порядка, 52 бита мантиссы. Отсюда точные целые только до 2^53, ноль со знаком и `NaN`.
- **Unicode — номера символов, UTF-8 и UTF-16 — способы записать их байтами.** В UTF-8 символ занимает от 1 до 4 байтов, поэтому длина строки и размер в байтах — разные числа.
- **Base64 — запись байтов печатными символами:** 3 байта превращаются в 4 символа, данные растут на треть. Это кодирование, а не шифрование.
::

## Биты и байты

Сквозной пример — карточка товара в интернет-магазине чая: название «Чай Тегуаньинь», цена `349.90`, идентификатор из базы и фото. Сервер отдаёт её в JSON, браузер разбирает текст, превращает цену в число, а картинку распаковывает в пиксели. На каждом шаге одни и те же данные меняют представление.

**Бит** — минимальная единица информации: 0 или 1. Двоичная система прижилась потому, что электронике проще надёжно различать два состояния — есть напряжение или нет, — чем десять уровней. **Байт** — 8 битов: 2^8 = 256 значений, от 0 до 255. В n битах помещается 2^n разных значений, и это главная формула раздела.

Байт сам по себе ничего не значит. Значение `0xD0` — это 208 как беззнаковое целое, −48 как целое со знаком и первый байт буквы «Ж» в UTF-8. Что именно лежит в памяти, знает только код, который её читает.

В JavaScript сырые байты живут в `ArrayBuffer`, а читают их через типизированные массивы. Они по-разному обходятся со значениями, которые не помещаются в байт:

```js
new Uint8Array([256, -1, 300]);          // [0, 255, 44] — по модулю 256
new Uint8ClampedArray([256, -1, 300.6]); // [255, 0, 255] — прижимает к краям
new Int8Array([127, 128, 255]);          // [127, -128, -1] — байт со знаком
```

`Uint8ClampedArray` — тип пикселей `canvas`: яркость 300 становится 255, а не 44. Последняя строка — дополнительный код, о нём ниже.

С единицами тоже есть ловушка: килобайт по SI — 1000 байт, а по стандарту IEC кибибайт (KiB) — 1024. Производители дисков считают в SI, а операционная система часто показывает размер в двоичных единицах, поэтому диск на 64 ГБ выглядит как 59,6.

Байты есть, но человеку их нужно как-то записывать — отсюда системы счисления.

## Системы счисления

Позиционная система с основанием b: цифра в позиции k весит b^k. Двоичное `1011` — это 8 + 0 + 2 + 1 = 11. Программисты пользуются четырьмя основаниями:

| Система | Литерал в JS | Где встречается |
| --- | --- | --- |
| двоичная | `0b1010` | битовые маски, флаги |
| восьмеричная | `0o755` | права доступа в Unix: `chmod 755` |
| десятичная | `10` | всё, что видит человек |
| шестнадцатеричная | `0xff` | цвета `#ff0000`, байты в дампах, коды символов `U+0416` |

Шестнадцатеричная удобна потому, что одна цифра — ровно 4 бита, а байт — две цифры. Поэтому байты пишут как `d0 96`, а цвет `#ff8800` читается как три байта: красный 255, зелёный 136, синий 0.

Перевод в JavaScript — `toString(основание)` и `parseInt(строка, основание)`:

```js
(255).toString(2);    // '11111111'
(255).toString(16);   // 'ff'
parseInt('ff', 16);   // 255
parseInt(0.0000005);  // 5
```

Последняя строка — частый вопрос на «что выведет». `parseInt` принимает строку, поэтому сначала превращает число в строку, а `0.0000005` в строке — `'5e-7'`. Разбор идёт до первого неподходящего символа и останавливается на `e`. Числа в `parseInt` не передают; для строк вроде `'1e3'` нужен `Number`, он поймёт экспоненту и вернёт 1000.

Положительные числа понятны. Остаётся вопрос, как в тех же битах записать минус.

## Целые со знаком: дополнительный код

Процессоры хранят отрицательные целые в **дополнительном коде** (two's complement): старший бит весит не +2^(n−1), а −2^(n−1). В 8 битах `10000000` — это −128, а `11111111` — это −128 + 127 = −1. Диапазон n-битного целого со знаком — от −2^(n−1) до 2^(n−1) − 1, у байта это −128…127.

Чтобы получить −x, инвертируют все биты и прибавляют 1. Главное достоинство: сложение и вычитание работают одной схемой для чисел с любыми знаками, а ноль один. Обратная сторона — переполнение: 127 + 1 в байте со знаком даёт −128, отсюда `Int8Array([128])` выше.

### Побитовые операции в JavaScript

`number` в JavaScript — не целое, но побитовые операторы `|`, `&`, `^`, `~`, `<<`, `>>` сначала приводят операнды к **32-битному целому со знаком**, а `>>>` — к беззнаковому. Отсюда эффекты, которые выглядят как баги:

```js
(2 ** 31) | 0;     // -2147483648 — старший бит стал знаком
(2 ** 32) | 0;     // 0 — 33-й бит отброшен
~~3.7;             // 3 — «быстрое округление»
~~2147483648;      // -2147483648 — работает только до 2^31
-1 >>> 0;          // 4294967295 — те же 32 единицы, прочитанные без знака
-5 >> 1;           // -3 — сдвиг сохраняет знак
```

`~~x` и `x | 0` встречаются в старом коде как замена `Math.trunc`. На временных метках в миллисекундах, размерах файлов и идентификаторах они тихо ломаются, потому что эти значения давно больше 2^31.

Где побитовые операции уместны — флаги в одном числе. Так устроены права доступа в Unix, флаги React Fiber и маски событий:

```js
const READ = 1, WRITE = 2, EXEC = 4;  // по биту на флаг
let mode = READ | WRITE;              // установить
mode & WRITE;                         // проверить: 2, то есть есть
mode &= ~WRITE;                       // снять
```

Целые разобраны. Цена `349.90` — не целое, и для неё нужен другой формат.

## Числа с плавающей точкой

`number` в JavaScript — 64-битное число по стандарту IEEE 754, `double`. Оно записано как научная нотация в двоичной системе: **знак × 1.мантисса × 2^порядок**.

| Поле | Биты | Что хранит |
| --- | --- | --- |
| знак | 1 | 0 — плюс, 1 — минус |
| порядок | 11 | степень двойки со смещением 1023 |
| мантисса | 52 | дробная часть после неявной единицы |

Биты числа можно увидеть через `DataView`:

```js
const dv = new DataView(new ArrayBuffer(8));
const hex = (x) => { dv.setFloat64(0, x); return dv.getBigUint64(0).toString(16).padStart(16, '0'); };

hex(1);    // '3ff0000000000000' — порядок 1023 − 1023 = 0, мантисса пустая
hex(-2);   // 'c000000000000000' — знак 1, порядок 1
hex(0.1);  // '3fb999999999999a' — мантисса 1001 1001 …, округлённая в конце
hex(-0);   // '8000000000000000' — ноль со знаком
```

Из раскладки следуют все известные странности:

- **`0.1` не хранится точно.** В двоичной системе это бесконечная периодическая дробь, и мантисса обрезает её с округлением: `0.1.toFixed(20)` даёт `'0.10000000000000000555'`. Как это проявляется в сравнениях и деньгах — в [Типах и переменных](/content/javascript/types-and-variables).
- **Точные целые — до 2^53.** Мантисса — 52 бита плюс неявная единица, то есть 53 значащих бита. Дальше соседние `double` отстоят на 2: `2 ** 53 + 1 === 2 ** 53`. Поэтому `Number.MAX_SAFE_INTEGER` равен 2^53 − 1.
- **Шаг между числами растёт с порядком.** Возле единицы он равен 2^−52 — это `Number.EPSILON`, — а возле 2^53 уже 2. Относительная точность постоянная, около 15–16 десятичных знаков.
- **Ноль бывает со знаком.** `-0 === 0`, но `Object.is(-0, 0)` — `false`, а `1 / -0` — `-Infinity`.
- **Особые значения занимают максимальный порядок.** Все единицы в порядке и пустая мантисса — `Infinity`, непустая — `NaN`. Поэтому `NaN` — тоже число, и не одно.

`Float32Array` и `Math.fround` хранят 32-битное число: 24 значащих бита, около 7 десятичных знаков. `Math.fround(0.1)` — `0.10000000149011612`, а `Math.fround(16777217)` — уже `16777216`. В таком формате приходят координаты в WebGL и данные моделей машинного обучения.

Число разобрано на биты. Но в каком порядке эти байты лежат в памяти?

## Порядок байтов

Число из нескольких байтов можно записать старшим байтом вперёд (**big-endian**) или младшим (**little-endian**). Процессоры x86 и ARM в обычном режиме — little-endian, а сетевые протоколы и многие форматы файлов — big-endian.

```js
const one = new Uint32Array([1]);
new Uint8Array(one.buffer);                // [1, 0, 0, 0] — младший байт первым
new DataView(one.buffer).getUint32(0);     // 16777216 — прочитали как big-endian
new DataView(one.buffer).getUint32(0, true); // 1
```

Типизированные массивы используют порядок платформы, а `DataView` по умолчанию читает big-endian и принимает флаг `littleEndian`. Правило для разбора бинарных форматов — заголовка PNG, WAV, протокола поверх WebSocket — всегда `DataView` с явным порядком из спецификации формата, а не типизированный массив поверх чужого буфера.

С числами всё. Название товара — текст, и с ним ошибок на практике больше.

## Текст: Unicode и кодировки

Текст хранится как последовательность номеров символов. Здесь два разных понятия, которые часто путают:

- **Unicode** — таблица: каждому символу присвоен номер, **кодовая точка** (code point). «A» — `U+0041`, «Ж» — `U+0416`, «€» — `U+20AC`, скрипичный ключ «𝄞» — `U+1D11E`. Всего мест больше миллиона.
- **Кодировка** — способ записать номер байтами. Основные — UTF-8, UTF-16 и UTF-32.

ASCII — первые 128 номеров: латиница, цифры, знаки и управляющие символы. Старые однобайтовые кодировки вроде windows-1251 и KOI8-R использовали верхние 128 значений байта для кириллицы — каждая по-своему.

### UTF-8

UTF-8 записывает кодовую точку от 1 до 4 байтов. Номера до 127 — один байт, как в ASCII. Остальные — несколько: первый байт сообщает длину последовательности (`110…` — два байта, `1110…` — три, `11110…` — четыре), а продолжения начинаются с `10`.

| Символ | Кодовая точка | Байты UTF-8 | `length` в JS |
| --- | --- | --- | --- |
| A | U+0041 | `41` | 1 |
| Ж | U+0416 | `d0 96` | 1 |
| € | U+20AC | `e2 82 ac` | 1 |
| 𝄞 | U+1D11E | `f0 9d 84 9e` | 2 |

UTF-8 — кодировка веба: HTML, JSON, исходники, тела запросов. Она совместима с ASCII и не зависит от порядка байтов. Строки в JavaScript при этом хранятся в UTF-16, поэтому `length` считает 16-битные единицы, а не символы и не байты. Подробно про `length` и суррогатные пары — в [Типах и переменных](/content/javascript/types-and-variables).

Для карточки товара это значит: `'Привет'.length` — 6, а в UTF-8 это 12 байт. Лимиты, которые считаются в байтах, — размер заголовка, поле в базе, размер сообщения в очереди — нельзя проверять через `length`. Размер в байтах даёт `new TextEncoder().encode(s).length`.

### Кракозябры

Кракозябры появляются, когда байты записаны в одной кодировке, а прочитаны в другой. Так выглядит «Привет» в UTF-8, прочитанный как windows-1251:

```js
const bytes = new TextEncoder().encode('Привет');
new TextDecoder('windows-1251').decode(bytes); // 'РџСЂРёРІРµС‚'
```

Каждый символ занял два байта, и каждый байт стал отдельной буквой. Лечится это не перекодированием на клиенте, а заголовком `Content-Type: text/plain; charset=utf-8` и `<meta charset="utf-8">`.

Если байты обрезаны посреди символа, декодер ставит замену `U+FFFD` «�», а с опцией `{ fatal: true }` бросает `TypeError`. В начале файла может стоять метка порядка байтов, BOM: `TextDecoder` по умолчанию её убирает.

### Нормализация

Одна и та же буква может быть записана разными кодовыми точками. «й» — это `U+0439`, но также «и» плюс комбинируемый знак краткости `U+0306`. На экране одинаково, а строки разные:

```js
const composed = 'й';
const decomposed = 'и\u0306';
composed === decomposed;                         // false
composed.length;                                 // 1
decomposed.length;                               // 2
composed.normalize() === decomposed.normalize(); // true — NFC по умолчанию
```

Разложенная форма приходит из файловой системы macOS, из копирования текста из PDF и с некоторых клавиатур. Поиск, сравнение логинов и ключи в `Map` без `normalize` дают «пользователь не найден» на правильном имени. Сколько видимых символов в строке — отдельный вопрос, его решает `Intl.Segmenter` из [Современного JS](/content/javascript/modern-js).

Текст превращён в байты. Но некоторые каналы принимают только печатные символы — для них есть Base64.

## Base64

Base64 записывает произвольные байты 64 печатными символами: `A–Z`, `a–z`, `0–9`, `+` и `/`. Каждые 3 байта (24 бита) делятся на 4 группы по 6 битов, каждая группа — символ. Если в конце не хватает байтов, добавляется `=`:

```js
btoa('abc'); // 'YWJj'
btoa('ab');  // 'YWI='
btoa('a');   // 'YQ=='
```

Отсюда главное: **данные растут на треть.** Картинка 3 МБ в data URL весит 4 МБ, раздувает CSS или HTML, в котором лежит, и не кешируется отдельно. Поэтому data URL оправданы только для крошечных иконок.

**Base64url** заменяет `+` и `/` на `-` и `_` и обычно убирает `=`: такая строка безопасна в URL и имени файла. Так кодируются части JWT.

`btoa` принимает строку, где каждый символ — один байт (Latin-1). Кириллица в неё не помещается:

```js
btoa('Привет'); // InvalidCharacterError
```

Правильный путь — сначала получить байты UTF-8, потом кодировать байты. В браузерах для этого есть `Uint8Array.prototype.toBase64()` и `Uint8Array.fromBase64()`, в Node.js — `Buffer`.

> **Актуально на ноябрь 2026:** `toBase64` и `fromBase64` — Baseline с 2025 года (Chrome 140, Firefox 133, Safari 18.2). В Node.js 24 их ещё нет.

Base64 ничего не скрывает: любой декодирует строку обратно. Чем кодирование отличается от хеширования и шифрования — в [Шифровании](/content/computer-science/encryption).

## Картинки, звук и видео

**Картинка** в памяти — матрица пикселей, обычно 4 байта на пиксель: красный, зелёный, синий и прозрачность (RGBA). Фото 1920 × 1080 после распаковки занимает 1920 × 1080 × 4 = 8 294 400 байт — около 8 МБ, — даже если файл JPEG весил 200 КБ. Сжатие экономит сеть, но не память: браузер декодирует картинку перед отрисовкой. Поэтому десяток огромных фото в галерее съедает сотни мегабайт на телефоне.

**Звук** — значения амплитуды через равные промежутки времени. CD-качество — 44 100 отсчётов в секунду по 16 битов на двух каналах: 44 100 × 16 × 2 ≈ 1,4 Мбит/с без сжатия.

**Видео** — последовательность кадров и звук. Без сжатия минута Full HD при 30 кадрах в секунду и 3 байтах на пиксель весит около 11 ГБ, поэтому кодеки (H.264, VP9, AV1) хранят не кадры, а разницу между ними.

Форматы картинок и их вес — в [Оптимизации ресурсов](/content/security-perfomance/asset-optimization), видео и звук в браузере — в [Медиа и WebRTC](/content/additional-topics/media-and-webrtc).

## Красные флаги в ответе

- **«`~~x` — быстрый способ округлить».** Только до 2^31: побитовые операции приводят число к 32-битному целому со знаком, и `~~2147483648` даёт отрицательное число. Округление — `Math.trunc`.
- **«`0.1 + 0.2 !== 0.3` — баг JavaScript».** Это свойство двоичного `double` в любом языке: 0.1 в двоичной системе — бесконечная дробь.
- **«UTF-8 — это двухбайтовая кодировка» или «Unicode и UTF-8 — одно и то же».** Unicode — номера символов, UTF-8 — запись номера от 1 до 4 байтами.
- **«`str.length` — размер строки в байтах».** Это количество 16-битных единиц UTF-16. Байты в UTF-8 даёт `TextEncoder`.
- **«Base64 защищает данные» или «Base64 сжимает».** Он ничего не скрывает и увеличивает размер на треть.
- **«Картинка весит столько, сколько файл».** В памяти она занимает ширина × высота × 4 байта.

## Как спрашивают на собеседовании

::question
Почему компьютер работает в двоичной системе и сколько значений помещается в n битах?

#answer
Электронике надёжнее различать два состояния — есть напряжение или нет, — чем десять уровней: меньше ошибок из-за шума. В n битах помещается 2^n значений: в байте 256, в 32 битах около 4,3 миллиарда. Что эти значения означают, решает формат: целое, символ, пиксель.

#more
Шестнадцатеричную систему используют как компактную запись двоичной: одна цифра — 4 бита, байт — две цифры. Поэтому цвета `#ff8800`, дампы памяти и коды символов `U+0416` пишут в hex. Восьмеричная осталась в правах Unix: `755` — это `rwx r-x r-x`, по три бита на группу.
::

::question
Что такое дополнительный код? Почему `-1 >>> 0` равно 4294967295?

#answer
Это способ хранить целые со знаком: старший бит весит −2^(n−1). Тогда −1 — все единицы, сложение и вычитание делаются одной схемой, а ноль один. `>>>` приводит число к 32-битному беззнаковому, и те же 32 единицы читаются как 2^32 − 1.

#more
Все побитовые операторы, кроме `>>>`, работают с 32-битным целым со знаком. Поэтому `(2 ** 31) | 0` отрицательно, `(2 ** 32) | 0` равно нулю, а `~~x` как округление ломается на числах больше 2^31 — временных метках, размерах файлов. Типизированные массивы показывают то же переполнение: `new Int8Array([128])` даёт −128.
::

::question
Как устроено число в JavaScript? Почему `Number.MAX_SAFE_INTEGER` равен 2^53 − 1?

#answer
`number` — 64-битный `double` по IEEE 754: 1 бит знака, 11 битов порядка и 52 бита мантиссы. С неявной ведущей единицей это 53 значащих бита, поэтому все целые до 2^53 представимы точно, а дальше соседние числа отстоят на 2 и больше.

#more
Из той же раскладки — ноль со знаком (`Object.is(-0, 0)` — `false`), `Infinity` и `NaN` в максимальном порядке, и шаг между числами, который растёт с величиной: `Number.EPSILON` — шаг возле единицы. Идентификаторы из базы длиной 19 цифр нужно передавать строкой или читать как `BigInt`. Биты числа можно увидеть через `DataView.setFloat64` и `getBigUint64`.
::

::question
Чем Unicode отличается от UTF-8? Сколько байтов занимает строка «Привет»?

#answer
Unicode — таблица, которая присваивает символу номер, кодовую точку. UTF-8 — способ записать номер байтами: от 1 до 4, латиница — 1 байт, кириллица — 2, большинство иероглифов — 3. «Привет» — 6 символов и 12 байт в UTF-8.

#more
Строки JavaScript хранятся в UTF-16, поэтому `length` — 6, а для символов вне базовой плоскости — две единицы на символ. Размер в байтах считают через `new TextEncoder().encode(s).length`. Кракозябры — это байты одной кодировки, прочитанные в другой: «Привет» в UTF-8, прочитанный как windows-1251, превращается в «РџСЂРёРІРµС‚».
::

::question
Почему две одинаковые на вид строки не равны?

#answer
Одну букву можно записать разными последовательностями кодовых точек: «й» одной точкой или «и» плюс комбинируемый знак. Сравнение строк идёт по единицам UTF-16, поэтому они не равны. `normalize()` приводит обе к одной форме, по умолчанию NFC.

#more
Разложенная форма приходит из имён файлов macOS, копирования из PDF и с некоторых клавиатур. Нормализовать нужно на входе: в поиске, логинах, ключах кеша. Есть и формы совместимости NFKC и NFKD: они дополнительно сводят, например, полноширинные символы к обычным, и их используют для идентификаторов.
::

::question
Что такое порядок байтов и где он встречается во фронтенде?

#answer
Многобайтовое число можно записать старшим байтом вперёд (big-endian) или младшим (little-endian). Процессоры x86 и ARM — little-endian, сеть и многие форматы файлов — big-endian. Типизированные массивы используют порядок платформы, а `DataView` позволяет указать его явно.

#more
Во фронтенде порядок байтов встречается при разборе бинарных форматов: заголовки картинок и аудио, бинарные протоколы поверх WebSocket, WebAssembly-память (она little-endian). Ошибка выглядит как огромные или бессмысленные числа: единица, прочитанная не в том порядке, становится 16 777 216.
::

::question
Что такое Base64 и когда его использовать?

#answer
Base64 записывает байты 64 печатными символами: 3 байта превращаются в 4 символа, и размер растёт на треть. Его используют там, где канал принимает только текст: data URL, вложения в почте, бинарные поля в JSON, части JWT в варианте base64url.

#more
`btoa` принимает только символы Latin-1 и падает на кириллице: сначала текст переводят в байты через `TextEncoder`, потом кодируют байты. Картинки в data URL не кешируются отдельно и раздувают CSS и HTML, поэтому оправданы только для очень маленьких иконок. Base64 не шифрует — это обратимая запись.
::

## Практика

::practice{title="Что выведет?"}
```js
console.log(parseInt(0.0000005));
console.log((2 ** 31) | 0);
console.log(~~-3.7, Math.floor(-3.7));
console.log(new Uint8Array([300])[0], new Uint8ClampedArray([300])[0]);
console.log(2 ** 53 + 1 === 2 ** 53);
```

#solution
```text
5
-2147483648
-3 -4
44 255
true
```

- `parseInt` превращает число в строку `'5e-7'` и читает цифры до буквы `e`.
- Побитовое ИЛИ приводит 2^31 к 32-битному целому со знаком, и старший бит становится знаком.
- `~~` отбрасывает дробную часть к нулю, как `Math.trunc`, а `Math.floor` округляет вниз.
- `Uint8Array` берёт число по модулю 256, а `Uint8ClampedArray` прижимает к 255.
- После 2^53 соседние `double` отстоят на 2, и 2^53 + 1 округляется до 2^53.

Исправленные варианты — `Math.trunc(x)` вместо `~~x` и `Number(s)` или `parseFloat(s)` для строк с экспонентой.
::

::practice{title="Обрезка до 255 байт ломает текст"}
Сервер принимает название товара не длиннее 255 байт. Клиент обрезает так:

```js
function cut(name, limit = 255) {
  const bytes = new TextEncoder().encode(name);
  return new TextDecoder().decode(bytes.slice(0, limit));
}
```

На длинных русских названиях в конце появляется «�». Почему и как исправить?

#solution
Кириллица в UTF-8 занимает 2 байта, и граница в 255 байт может пройти посреди символа. Декодер видит неполную последовательность и ставит символ замены `U+FFFD`.

`encodeInto` пишет в буфер только целые символы и возвращает, сколько байтов записал:

```js
function cut(name, limit = 255) {
  const buffer = new Uint8Array(limit);
  const { written } = new TextEncoder().encodeInto(name, buffer);
  return new TextDecoder().decode(buffer.subarray(0, written));
}

cut('Привет', 5); // 'Пр' — 4 байта, третья буква не поместилась
```

Проверка `name.length <= 255` тоже не подходит: она считает единицы UTF-16, а 255 русских букв — 510 байт.
::

::practice{title="btoa падает на кириллице"}
Фильтры каталога сохраняются в URL как Base64 от JSON:

```js
const state = { query: 'улун', sort: 'price' };
location.hash = btoa(JSON.stringify(state)); // InvalidCharacterError
```

Почему падает и как исправить, чтобы строка ещё и не ломала URL?

#solution
`btoa` принимает строку, где каждый символ — один байт Latin-1, а «улун» туда не помещается. Нужно сначала получить байты UTF-8, потом кодировать байты. Для URL нужен алфавит base64url без `+`, `/` и `=`:

```js
const bytes = new TextEncoder().encode(JSON.stringify(state));
location.hash = bytes.toBase64({ alphabet: 'base64url', omitPadding: true });

const restored = JSON.parse(
  new TextDecoder().decode(Uint8Array.fromBase64(location.hash.slice(1), { alphabet: 'base64url' })),
);
```

Там, где `toBase64` нет, байты превращают в «байтовую строку» и отдают в `btoa`: `btoa(String.fromCharCode(...bytes))`, а обратно — `Uint8Array.from(atob(s), (c) => c.charCodeAt(0))` и `TextDecoder`. Сам `atob` возвращает байты как символы Latin-1, а не текст: без `TextDecoder` получатся кракозябры.
::
