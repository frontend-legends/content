# Архитектура компьютера

Архитектура — это то, как процессор выполняет инструкции и получает для них данные. Для фронтенда она важна не схемами транзисторов, а последствиями: два цикла одинаковой сложности могут отличаться по скорости в десять раз, потому что один дружит с кешем, а другой нет. Спрашивают, что такое кеш процессора и почему доступ к памяти медленный, что такое конвейер и предсказание переходов, чем ARM отличается от x86. Глубже — почему связный список медленнее массива при той же O(n), что такое ложное разделение и при чём тут Spectre к `SharedArrayBuffer`.

::tldr
- **Процессор быстрее памяти примерно в сто раз.** Обращение к регистру — доля наносекунды, к оперативной памяти — около 100 нс. Между ними кеши L1, L2, L3, и производительность зависит от того, попадают ли данные в кеш.
- **Кеш загружает память строками по 64 или 128 байт.** Последовательный обход использует каждую строку целиком, случайный — один элемент из строки. Отсюда разница в разы при той же асимптотике.
- **Процессор выполняет инструкции конвейером и наперёд:** предсказывает переходы, выполняет инструкции не по порядку и спекулятивно. Ошибка предсказания стоит десятков тактов.
- **Спекулятивное выполнение оставляет следы в кеше — это Spectre.** Поэтому браузеры изолируют сайты по процессам, огрубляют `performance.now()` и дают `SharedArrayBuffer` только изолированным страницам.
- **ARM и x86 — разные наборы инструкций.** Ноутбуки и телефоны на ARM, серверы и большинство ПК на x86; код на JavaScript переносим, потому что движок компилирует его под ту машину, где запущен.
::

## Процессор выполняет инструкции

Сквозной пример — таблица заказов на 100 000 строк: фильтр, сумма по колонке, сортировка. Код на JavaScript, но в итоге его выполняет процессор, и скорость таблицы зависит от того, как процессор получает данные.

Почти все компьютеры устроены по **модели фон Неймана**: программа и данные лежат в одной памяти, процессор берёт инструкцию, разбирает её, выполняет и переходит к следующей — цикл fetch, decode, execute. Инструкции простые: загрузить значение из памяти в регистр, сложить два регистра, сравнить, перейти по адресу. Цикл `for` по таблице превращается в несколько таких инструкций на каждую строку.

**Регистры** — самая быстрая память, несколько десятков ячеек прямо в процессоре. Арифметика работает только с ними, поэтому всё, что не в регистре, сначала нужно загрузить.

Набор инструкций, который понимает процессор, называется **архитектурой набора команд** (ISA). Сегодня их две основные:

| | x86-64 | ARM64 |
| --- | --- | --- |
| Где | большинство ПК и серверов | телефоны, ноутбуки Apple, всё больше серверов |
| Инструкции | сложные, разной длины (CISC) | простые, фиксированной длины (RISC) |
| Сильная сторона | совместимость с десятилетиями софта | производительность на ватт |

Внутри современные x86-процессоры тоже разбивают сложные инструкции на простые микрооперации, так что граница RISC и CISC давно размыта. Для фронтенда разница почти невидима: движок JavaScript компилирует код в машинные инструкции той платформы, где он запущен. Как именно — в [Языках и компиляторах](/content/computer-science/languages-and-compilers).

Тактовая частота — несколько гигагерц, то есть :term[такт]{def="один шаг тактового генератора процессора: при частоте 3 ГГц — треть наносекунды"} длится около трети наносекунды. Но выполнять по одной инструкции за такт процессору мешает простое обстоятельство: данные приходят из памяти гораздо медленнее.

## Иерархия памяти

Оперативная память отвечает примерно за 100 нс — это сотни тактов. Если бы процессор ждал память на каждой инструкции, он бы простаивал почти всё время. Это называют **узким местом фон Неймана**, и всё устройство памяти — попытка его обойти.

Решение — **иерархия**: маленькая быстрая память рядом с процессором и большая медленная дальше. Порядки величин (по таблице «Latency numbers every programmer should know», значения зависят от машины):

| Уровень | Объём | Задержка |
| --- | --- | --- |
| регистры | сотни байт | доля наносекунды |
| кеш L1 | десятки КБ на ядро | около 1 нс |
| кеш L2 | единицы МБ | несколько нс |
| кеш L3 | десятки МБ, общий для ядер | 10–20 нс |
| оперативная память | гигабайты | около 100 нс |
| SSD | терабайты | десятки–сотни микросекунд |
| сеть, запрос через океан | — | около 150 мс |

Если такт — одна секунда, то L1 — несколько секунд, память — несколько минут, а запрос к серверу на другом континенте — годы. Отсюда интуиция, которая пригодится везде: лишний сетевой запрос дороже любых вычислений в цикле, а лишний промах кеша дороже лишней арифметики.

### Кеш-линии и локальность

Кеш загружает память не байтами, а **кеш-линиями** — блоками по 64 байта на большинстве процессоров и по 128 байт на Apple M. Прочитал один `double` — в кеше оказались и соседние семь или пятнадцать. Вдобавок процессор замечает последовательный обход и подгружает следующие линии заранее (prefetch).

Поэтому кеш хорошо работает с двумя видами **локальности**:

- **пространственная** — после элемента нужен соседний: обход массива по порядку;
- **временная** — к тем же данным возвращаются скоро: внутренний цикл по маленькому массиву.

Проверка: сумма 8 миллионов чисел из `Float64Array` (64 МБ — больше любого кеша). Индексы по порядку и те же индексы, перемешанные:

```js
const sumBy = (ix) => { let s = 0; for (let i = 0; i < N; i++) s += values[ix[i]]; return s; };
sumBy(inOrder); // в проверке на Apple M4 — около 10 мс
sumBy(random);  // в 5–9 раз дольше: почти каждое чтение — промах кеша
```

Количество операций одинаковое, асимптотика одинаковая, а время отличается в разы. Тот же эффект у матрицы:

```js
// матрица 2048 × 2048 в одном Float64Array, строка за строкой
for (let r = 0; r < W; r++) for (let c = 0; c < W; c++) s += m[r * W + c]; // соседние элементы рядом
for (let c = 0; c < W; c++) for (let r = 0; r < W; r++) s += m[r * W + c]; // шаг 16 КБ, в проверке в 4 раза медленнее
```

### Что это значит для JavaScript

В JavaScript нет прямого управления памятью, но раскладка данных всё равно влияет:

- **Типизированные массивы** лежат в памяти сплошным блоком чисел. Это самый дружелюбный к кешу формат: графики, аудио, обработка картинок.
- **Обычный массив чисел** V8 тоже хранит сплошным блоком, пока в нём только числа: целые — как малые целые (SMI), дробные — как `double`. Строка, объект или дыра переводят массив в общий вид — массив ссылок, — и обратно он не возвращается: после `push(1.5)` и `pop()` массив целых остаётся массивом `double`.
- **Массив объектов** — это массив указателей, а сами объекты лежат где-то в куче. Обход — прыжки по памяти.
- **Связный список** — худший случай: каждый следующий узел может оказаться где угодно. В проверке обход двух миллионов узлов, связанных в случайном порядке, оказался медленнее обхода массива той же длины больше чем в сто раз, хотя оба — O(n).

Для таблицы заказов это значит: если колонку «сумма» нужно агрегировать часто и по миллиону строк, её выгодно держать отдельным `Float64Array` («структура массивов»), а не полем в каждом объекте («массив структур»). Для 100 строк разницы не будет — оптимизировать стоит только то, что видно в профиле.

Данные доставлены в процессор. Теперь — как процессор успевает выполнять несколько инструкций одновременно.

## Конвейер и предсказание переходов

Выполнение инструкции разбито на этапы: получить, декодировать, выполнить, записать результат. **Конвейер** (pipeline) запускает следующую инструкцию, не дожидаясь конца предыдущей, как на сборочной линии. Современные процессоры к тому же **суперскалярные** — запускают несколько инструкций за такт — и выполняют их **не по порядку** (out-of-order): если инструкция ждёт память, процессор берёт следующую, независимую.

Конвейеру мешают ветвления. На `if` процессор ещё не знает результат сравнения, а следующие инструкции нужно загружать уже сейчас. Поэтому он **предсказывает переход** по истории и выполняет выбранную ветку заранее — **спекулятивно**. Угадал — выигрыш. Не угадал — результаты выбрасываются, конвейер очищается, и это стоит десятков тактов.

Проверка: сумма элементов больше 128 в массиве случайных байтов, отсортированном и нет. Числа одни и те же, результат один и тот же:

```js
for (let i = 0; i < M; i++) if (d[i] >= 128) s += d[i];
// отсортированный массив: сначала все «нет», потом все «да» — предсказатель почти не ошибается
// случайный: ошибается в половине случаев — в проверке в 4 раза медленнее
```

На практике фронтенду об этом думать почти не приходится: компилятор движка сам убирает часть ветвлений. Полезно другое — понимать, что «тот же алгоритм на других данных» может работать с другой скоростью, и измерять на реальных данных.

У спекулятивного выполнения оказалась и цена, которая напрямую касается браузера.

## Spectre и защиты браузера

Спекулятивно выполненные инструкции отменяются, но их след остаётся: данные, которые они прочитали, уже загружены в кеш. В 2018 году показали, что по времени доступа к памяти можно узнать, что именно загрузилось, — и так прочитать данные, к которым у кода нет доступа. Этот класс уязвимостей назвали **Spectre**. Для браузера это значит, что скрипт со страницы мог бы читать память чужих сайтов в том же процессе.

Исправить это в процессорах полностью нельзя, поэтому браузеры защищаются архитектурно:

- **Изоляция сайтов.** Страницы разных сайтов работают в разных процессах, и чужих данных в памяти процесса просто нет. Подробно — в [Архитектуре браузера](/content/web/browser-engines).
- **Грубые таймеры.** Атаке нужен точный секундомер. В проверке `performance.now()` на обычной странице меняется шагами по 100 мкс.
- **`SharedArrayBuffer` только при изоляции.** Общая память между потоками позволяет собрать точный таймер, поэтому `SharedArrayBuffer` доступен, только если страница отдана с заголовками `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp`. Тогда `crossOriginIsolated` — `true`, а шаг таймера в проверке — 5 мкс.

Так архитектура процессора объясняет, почему для `SharedArrayBuffer` и многопоточного :term[WebAssembly]{def="двоичный формат кода, который браузер компилирует в машинный код и выполняет рядом с JavaScript"} нужно настраивать заголовки сервера. Как ими пользоваться — в [Web Workers](/content/additional-topics/web-workers-and-concurrency).

Ядер в процессоре несколько, и у них есть своя неожиданность.

## Несколько ядер

Частота процессоров почти перестала расти примерно с середины 2000-х: мешают нагрев и энергопотребление. Рост производительности ушёл в **ядра**: у ноутбука их 8–16, у сервера — десятки. `navigator.hardwareConcurrency` в браузере и `os.availableParallelism()` в Node.js показывают, сколько потоков можно выполнять одновременно.

У каждого ядра свои L1 и L2, а L3 общий. Если два ядра пишут в одну кеш-линию, протокол **когерентности кешей** гоняет её между ними, чтобы оба видели актуальные данные. Отсюда **ложное разделение** (false sharing): потоки пишут в разные переменные, но они лежат в одной линии, и ядра мешают друг другу.

Проверка: 4 потока Node.js увеличивают каждый свой счётчик в `SharedArrayBuffer`:

```js
const sab = new SharedArrayBuffer(4 * gap * threads);
// поток i пишет в ячейку i * gap
Atomics.add(new Int32Array(sab), slot, 1);
// gap = 1: счётчики соседние, одна кеш-линия — в проверке в 10 раз медленнее
// gap = 32: счётчики разнесены на 128 байт — каждый в своей линии
```

Вывод для практики: данные, которые потоки меняют независимо, раскладывают так, чтобы они не делили кеш-линию. Что такое потоки и гонки в общем виде — в [Потоках](/content/computer-science/threads).

## Специализированные вычислители

Универсальное ядро хорошо выполняет ветвистый последовательный код. Для массовых однотипных вычислений есть другое железо:

- **SIMD** — инструкции, которые обрабатывают сразу 4, 8 или 16 чисел. Движки и браузеры используют их внутри, а из веба они доступны через SIMD в [WebAssembly](/content/additional-topics/webassembly).
- **GPU** — тысячи простых ядер для одинаковых операций над пикселями и матрицами. Браузер рисует на нём слои страницы ([Рендеринг](/content/web/rendering)), а приложения получают его через WebGL и :term[WebGPU]{def="современный браузерный API для графики и вычислений на видеокарте"} ([Графика](/content/additional-topics/graphics-canvas-webgl)).
- **NPU** — блоки для нейросетей в телефонах и ноутбуках.

Ещё одно следствие для фронтенда: телефон пользователя медленнее ноутбука разработчика в разы — меньше кеш, ниже частота, троттлинг от нагрева. Поэтому производительность проверяют с замедлением CPU в [DevTools](/content/web/devtools) и на реальных устройствах.

## Красные флаги в ответе

- **«Если сложность одинаковая, то и скорость одинаковая».** O(n) последовательного обхода и O(n) прыжков по памяти отличаются в разы: асимптотика не учитывает промахи кеша.
- **«Связный список быстрее массива, потому что вставка O(1)».** Вставка — да, но поиск места для неё и обход — прыжки по памяти. На практике массив почти всегда быстрее.
- **«Оперативная память быстрая, медленный только диск».** Обращение к памяти — сотни тактов процессора; ради этого существуют кеши.
- **«Таймеры в браузере неточные из-за медленного JavaScript».** Их огрубили намеренно — это защита от Spectre.
- **«Больше потоков — всегда быстрее».** Потоки, которые пишут в одну кеш-линию или делят общий ресурс, мешают друг другу.

## Как спрашивают на собеседовании

::question
Что такое кеш процессора и зачем он нужен?

#answer
Это маленькая быстрая память рядом с ядром. Оперативная память отвечает около 100 нс — сотни тактов, — и без кеша процессор простаивал бы. Кеши L1, L2, L3 хранят недавно использованные данные и их соседей, поэтому повторный и последовательный доступ быстрый.

#more
Кеш загружает память линиями по 64 байта, на Apple M — по 128. Поэтому работает пространственная локальность (соседние данные) и временная (те же данные скоро снова). Процессор ещё и подгружает линии заранее, если видит последовательный обход. Когда данные не в кеше — промах, и процессор ждёт память.
::

::question
Почему обход матрицы по строкам быстрее, чем по столбцам?

#answer
Матрица лежит в памяти строка за строкой. При обходе по строкам соседние элементы находятся в одной кеш-линии, и каждая загрузка используется полностью. При обходе по столбцам шаг — целая строка, каждое чтение попадает в новую линию, и кеш почти не помогает.

#more
В проверке матрица 2048 × 2048 из `double` по столбцам обходилась в 4 раза медленнее при одинаковом числе операций. То же правило для любых данных: обходить в том порядке, в каком они лежат, а горячие поля держать вместе. Для колонок, которые часто агрегируют, выгодна «структура массивов» — отдельный типизированный массив на колонку.
::

::question
Почему связный список на практике медленнее массива?

#answer
Элементы массива лежат подряд, и обход использует кеш-линии и предзагрузку. Узлы списка разбросаны по куче, каждый переход по `next` — новое чтение из памяти и часто промах кеша. Асимптотика одинаковая, а время отличается на порядки.

#more
В проверке обход двух миллионов узлов, связанных в случайном порядке, был медленнее массива больше чем в сто раз. Вставка в середину списка O(1), но до места вставки нужно дойти за O(n), а сдвиг элементов массива — быстрое последовательное копирование. Поэтому в JavaScript списки почти не нужны, кроме случаев вроде LRU-кеша, где узел находят через `Map`.
::

::question
Что такое конвейер и предсказание переходов?

#answer
Конвейер выполняет инструкции поэтапно и запускает следующую, не дожидаясь конца предыдущей. На ветвлении процессор не знает результат заранее, поэтому угадывает переход по истории и выполняет ветку спекулятивно. Ошибка — очистка конвейера и потеря десятков тактов.

#more
Классическая демонстрация — сумма элементов больше порога в отсортированном и неотсортированном массиве: в проверке случайные данные обрабатывались в 4 раза медленнее при одинаковом результате. Ещё процессор выполняет независимые инструкции не по порядку, пока ждёт память. Всё это скрыто от программиста, но объясняет, почему скорость зависит от данных.
::

::question
Почему `SharedArrayBuffer` требует заголовков COOP и COEP, а `performance.now()` неточный?

#answer
Из-за Spectre: спекулятивное выполнение оставляет следы в кеше, и с точным таймером по ним можно прочитать чужую память в том же процессе. Браузеры огрубили таймеры — на обычной странице 100 мкс — и дают общую память, из которой собирается точный таймер, только изолированным страницам.

#more
Изолированная страница отдаётся с `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp` (или `credentialless`). Тогда `crossOriginIsolated` — `true`, а в проверке шаг таймера — 5 мкс. Цена — все сторонние ресурсы должны разрешить загрузку через CORS или CORP. Третья линия защиты — изоляция сайтов по процессам.
::

::question
Что такое ложное разделение?

#answer
Это когда потоки на разных ядрах пишут в разные переменные, которые лежат в одной кеш-линии. Протокол когерентности кешей гоняет линию между ядрами, и потоки тормозят друг друга, хотя логически не пересекаются.

#more
В проверке четыре потока с соседними счётчиками в `SharedArrayBuffer` работали в 10 раз медленнее, чем со счётчиками, разнесёнными на 128 байт. Лечится раскладкой: независимые данные потоков выравнивают по размеру кеш-линии. Во фронтенде это встречается в многопоточных вычислениях в воркерах и WebAssembly.
::

## Практика

::practice{title="Почему тормозит?"}
Тепловая карта кликов хранится в `Float64Array` размером 4000 × 4000, строка за строкой. Сумма по каждому столбцу считается так:

```js
const totals = new Float64Array(W);
for (let c = 0; c < W; c++) {
  for (let r = 0; r < H; r++) totals[c] += grid[r * W + c];
}
```

Код верный, но медленный. Почему и как ускорить, не меняя результата?

#solution
Внутренний цикл идёт по столбцу: шаг между соседними чтениями — целая строка, 32 КБ. Каждое чтение — новая кеш-линия, кеш почти не работает.

Достаточно поменять циклы местами: внешний по строкам, внутренний по столбцам. Тогда чтения идут подряд, а `totals` — маленький массив, который всё время в кеше:

```js
const totals = new Float64Array(W);
for (let r = 0; r < H; r++) {
  const row = r * W;
  for (let c = 0; c < W; c++) totals[c] += grid[row + c];
}
```

Результат тот же, число операций то же. В проверке на матрице 2048 × 2048 такой порядок был в 4 раза быстрее.
::

::practice{title="Почему список медленнее массива?"}
Для очереди задач написали связный список, «потому что удаление из начала массива — O(n)». Обход списка в профиле оказался в разы медленнее, чем был обход массива. Почему и что выбрать?

#solution
Узлы списка — отдельные объекты в куче. После работы приложения они разбросаны по памяти, и каждый `node.next` — чтение из новой кеш-линии. Массив лежит подряд, и его обход использует кеш и предзагрузку. В проверке обход двух миллионов узлов в случайном порядке был больше чем в сто раз медленнее массива.

Если нужна очередь с дешёвым удалением из начала, её делают на массиве с указателем головы:

```js
class Queue {
  #items = [];
  #head = 0;
  push(x) { this.#items.push(x); }
  shift() {
    if (this.#head === this.#items.length) return undefined;
    const x = this.#items[this.#head++];
    if (this.#head > 1024 && this.#head * 2 > this.#items.length) {
      this.#items = this.#items.slice(this.#head);              // изредка сжимаем
      this.#head = 0;
    }
    return x;
  }
}
```

Удаление — O(1) в среднем, данные лежат подряд.
::

::practice{title="Четыре воркера не быстрее одного"}
Подсчёт статистики разбили на 4 воркера. Каждый пишет свой результат в общий массив:

```js
const stats = new Int32Array(new SharedArrayBuffer(4 * 4));
// воркер i делает Atomics.add(stats, i, 1) миллионы раз
```

Ускорения почти нет. Почему и как исправить?

#solution
Четыре счётчика по 4 байта лежат в одной кеш-линии. Каждый `Atomics.add` заставляет ядро забрать линию себе, и ядра всё время отнимают её друг у друга — ложное разделение.

Разнести счётчики на размер кеш-линии с запасом — 128 байт, то есть 32 элемента `Int32Array`:

```js
const PAD = 32;
const stats = new Int32Array(new SharedArrayBuffer(4 * PAD * 4));
// воркер i пишет в stats[i * PAD]
```

Ещё лучше — копить сумму в локальной переменной воркера и записать в общий массив один раз в конце. В проверке разнесённые счётчики работали в 10 раз быстрее соседних.
::
