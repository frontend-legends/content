# Математика для CS

Фронтенду не нужен матанализ, но несколько разделов дискретной математики встречаются каждый день: оценка сложности кода, логические условия, множества, вероятность, графы зависимостей и матрицы трансформаций. Спрашивают, что такое O-нотация и какая сложность у `includes` и `Set.has`, как правильно перемешать массив и почему `-1 % 5` не равно 4. Глубже — что такое амортизированная сложность, почему короткие случайные ID совпадают раньше, чем кажется, и почему порядок функций в `transform` важен.

::tldr
- **O-нотация описывает, как растёт время с размером входа, без констант.** `includes` в цикле по другому массиву — O(n·m), то же через `Set` — O(n + m). Это главная оптимизация, которую ждут на собеседовании.
- **Амортизированная сложность — средняя стоимость в длинной серии операций.** `push` иногда копирует весь массив, но удвоение ёмкости делает среднюю стоимость O(1).
- **`sort(() => Math.random() - 0.5)` перемешивает неравномерно.** Правильный алгоритм — Фишер — Йетс, каждая перестановка с вероятностью 1/n!.
- **Совпадения случайных значений наступают на корне из размера пространства** — парадокс дней рождения. Из 1,7 миллиона четырёхсимвольных кодов первый повтор ждёт в среднем после 1600 штук.
- **Граф зависимостей модулей и задач сборки — ориентированный ацикличный граф.** Порядок сборки — топологическая сортировка, а цикл в графе — то, что она находит.
::

## О-нотация

Сквозной пример — каталог чая: фильтры, скрытые товары, перемешанные рекомендации, карусель, промокоды и анимации карточек.

Скрыть из списка заказов товары, которые сняли с продажи:

```js
const visible = orders.filter((o) => !hidden.includes(o.productId));
```

На тестовых данных всё мгновенно, а на 20 000 заказов и 5000 скрытых товаров страница подвисает. Чтобы предсказывать такое заранее, сложность оценивают **асимптотически**: как растёт число шагов, когда растёт вход, без учёта констант и мелких слагаемых. `f(n) = O(g(n))` значит, что с некоторого n функция f растёт не быстрее, чем g, умноженная на константу.

`includes` проходит массив, то есть O(m) на каждый из n заказов — всего O(n·m), 100 миллионов сравнений. `Set.has` в среднем O(1), поэтому та же фильтрация через множество — O(n + m):

```js
const hiddenSet = new Set(hidden);                         // O(m)
const visible = orders.filter((o) => !hiddenSet.has(o.productId)); // O(n)
```

В проверке результат одинаковый, а версия с `Set` быстрее в разы.

| Сложность | Пример | Удвоили вход — время |
| --- | --- | --- |
| O(1) | доступ по индексу, `Map.get`, `Set.has` в среднем | то же |
| O(log n) | двоичный поиск в отсортированном массиве | +1 шаг |
| O(n) | `includes`, `find`, `filter`, один проход | ×2 |
| O(n log n) | `sort` | чуть больше ×2 |
| O(n²) | вложенный цикл по тому же массиву, `includes` внутри `filter` | ×4 |
| O(2ⁿ) | перебор всех подмножеств, катастрофический возврат в регулярке | возводится в квадрат |

Несколько правил, которые спасают на собеседовании:

- **константы отбрасываются, но не исчезают.** Два прохода — тоже O(n), а O(1) у `Map` тяжелее O(1) у индекса массива. На маленьких n простой цикл часто быстрее «оптимальной» структуры;
- **оценивают худший случай**, если не сказано иное. У хеш-таблицы худший — O(n), но средний — O(1);
- **память тоже сложность.** `Set` из m элементов — O(m) дополнительной памяти, это и есть цена ускорения;
- **методы скрывают циклы.** `includes`, `indexOf`, `splice`, `shift`, spread и `slice` внутри цикла превращают O(n) в O(n²).

Почему в реальности одинаковая асимптотика может давать разное время — промахи кеша, — в [Архитектуре компьютера](/content/computer-science/computer-architecture). Структуры данных и алгоритмы подробно — в [Алгоритмах](/content/algorithms-data-structures).

### Логарифм

Логарифм появляется, когда задача **делится пополам** на каждом шаге. log₂ от миллиона — около 20: двоичный поиск по миллиону отсортированных элементов делает не больше 20 сравнений. В проверке самый длинный поиск уложился в 20 шагов. Поэтому O(log n) на практике почти не отличается от O(1), а сортировка за O(n log n) лишь немного медленнее одного прохода.

Основание логарифма в O-нотации не пишут: логарифмы по разным основаниям отличаются на константу.

### Амортизированная сложность

`push` в массив обычно O(1), но когда выделенная память кончается, массив копируется в новый буфер большего размера — O(n). Почему тогда `push` считают O(1)?

Потому что ёмкость **удваивается**. Копирования случаются при размерах 1, 2, 4, 8, … и в сумме дают меньше 2n копий на n вставок. Средняя стоимость одной вставки в длинной серии — константа. Это **амортизированная** оценка. В проверке самописный массив с удвоением при миллионе вставок сделал 2²⁰ − 1 копий — меньше двух на вставку.

Если бы ёмкость росла на фиксированную величину, а не в разы, суммарная стоимость была бы O(n²). Тот же приём — в хеш-таблицах при перестроении и в строках при сборке через конкатенацию.

## Логика

Логические условия в коде подчиняются булевой алгебре, и два её закона помогают упрощать условия и не ошибаться в отрицаниях. **Законы де Моргана**:

```text
!(a && b) === (!a || !b)
!(a || b) === (!a && !b)
```

«Не (в наличии и дешевле 500)» — это «нет в наличии **или** дороже 500». Ошибка в отрицании составного условия — частый баг фильтров. В проверке оба закона выполняются на всей таблице истинности.

В JavaScript `&&` и `||` к тому же **возвращают операнд**, а не `true` или `false`, и вычисляют правую часть, только если она нужна. Отсюда идиомы `a || defaultValue` и ловушка с нулём и пустой строкой, которую решает `??` ([Типы и переменные](/content/javascript/types-and-variables)).

## Множества

Множество — набор уникальных элементов без порядка. Операции над множествами описывают фильтры каталога и права доступа:

| Операция | Смысл | В JavaScript |
| --- | --- | --- |
| объединение A ∪ B | есть хотя бы в одном | `a.union(b)` |
| пересечение A ∩ B | есть в обоих | `a.intersection(b)` |
| разность A ∖ B | есть в A, нет в B | `a.difference(b)` |
| симметрическая разность | есть ровно в одном | `a.symmetricDifference(b)` |
| подмножество A ⊆ B | всё из A есть в B | `a.isSubsetOf(b)` |

«Чаи из подборки, которые есть на складе» — пересечение; «права пользователя покрывают права страницы» — подмножество.

> **Актуально на ноябрь 2026:** методы множеств — Baseline с июня 2024: Chrome 122, Firefox 127, Safari 17. В старых браузерах их приносит полифил, а не транспилятор.

## Комбинаторика и вероятность

### Как перемешать массив

Рекомендации на главной перемешивают так:

```js
items.sort(() => Math.random() - 0.5);
```

Кажется, что все порядки равновероятны, но нет. Алгоритм сортировки рассчитывает на согласованный компаратор и сравнивает элементы неравное число раз, поэтому одни перестановки выпадают чаще других. В проверке на 60 000 перемешиваний массива `[1, 2, 3]` исходный порядок выпал в 37% случаев вместо 16,7%.

Правильный алгоритм — **Фишер — Йетс**: идём с конца, меняем текущий элемент со случайным из ещё не обработанных.

```js
function shuffle(a) {
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1)); // 0 ≤ j ≤ i
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a;
}
```

Каждая из n! перестановок получается ровно одним способом, и все равновероятны: в проверке каждая из шести перестановок выпала в пределах 10% от ожидаемой доли. Сложность O(n) вместо O(n log n) у сортировки.

### Парадокс дней рождения

Промокоды из четырёх символов `[0-9a-z]` — 36⁴ ≈ 1,68 миллиона вариантов. Кажется, что совпадение маловероятно, пока кодов не сотни тысяч. На деле вероятность хотя бы одного совпадения среди k случайных значений из N примерно `1 − e^(−k²/2N)`, и половины она достигает при k ≈ 1,18·√N. Для промокодов это около 1500, а при 1000 кодов вероятность уже больше 25%. В проверке первое совпадение случалось в среднем после примерно 1600 кодов.

Отсюда практические правила:

- случайные идентификаторы делают длинными: у :term[UUID]{def="универсальный идентификатор из 128 бит; в версии 4 почти все биты случайные"} v4 122 случайных бита, и совпадение практически невозможно;
- короткие коды проверяют на уникальность при создании или генерируют из счётчика;
- то же правило определяет, когда начинают совпадать хеши: для 32-битного хеша — уже после десятков тысяч значений.

### Остаток от деления

Карусель листает карточки по кругу: индекс следующей — `(i + 1) % n`. Но назад с первой карточки получается `(0 − 1) % 5`, а это −1, а не 4: оператор `%` в JavaScript сохраняет знак делимого. Математический остаток, который всегда в диапазоне от 0 до n − 1:

```js
const mod = (a, n) => ((a % n) + n) % n;
mod(-1, 5); // 4
```

Модульная арифметика лежит в основе хеш-таблиц (номер корзины — :term[хеш]{def="число фиксированной длины, которое функция вычисляет по данным: одинаковые данные дают одинаковый хеш"} по модулю размера), циклических буферов и криптографии ([Шифрование](/content/computer-science/encryption)).

## Графы

**Граф** — вершины и рёбра между ними. Во фронтенде графы повсюду: DOM — дерево, модули с импортами — ориентированный граф, задачи в монорепозитории с зависимостями — тоже, маршруты и переходы между экранами — граф состояний.

Особенно важен **ориентированный ацикличный граф** (DAG): рёбра направлены, и нельзя вернуться в вершину, из которой вышел. Граф зависимостей сборки должен быть ацикличным, а порядок сборки — **топологическая сортировка**: каждая вершина идёт после всех, от которых она зависит.

```js
// модуль: от кого зависит
const modules = { app: ['cart', 'ui'], cart: ['api', 'ui'], ui: [], api: [] };
topoSort(modules); // ['ui', 'api', 'cart', 'app']
```

Алгоритм Кана берёт вершины, от которых никто не зависит, и убирает их рёбра, пока граф не опустеет. Если вершины остались, а брать нечего, — в графе **цикл**, и алгоритм может назвать его участников. Так монорепозиторные инструменты и бандлеры решают, что собирать первым, и находят циклические зависимости ([Модули](/content/javascript/modules), [Монорепозитории](/content/advanced-tooling/monorepo-tooling)).

Обход графа в ширину и в глубину, кратчайшие пути и другие алгоритмы — в главе [Алгоритмы](/content/algorithms-data-structures).

## Матрицы и трансформации

Каждая функция в `transform` — матрица, а цепочка функций — их **произведение**. Двумерное преобразование хранится матрицей 3 × 3, в CSS — шестью числами `matrix(a, b, c, d, e, f)`. Умножение матриц не коммутативно, поэтому порядок функций важен:

```css
.a { transform: translateX(100px) rotate(90deg); }
.b { transform: rotate(90deg) translateX(100px); }
```

В первом случае элемент сдвигается на 100 пикселей вправо и поворачивается. Во втором — сначала поворачивается система координат, и сдвиг «вправо» уходит вниз. В проверке точка (10, 0) в первом случае оказалась в (100, 10), во втором — в (0, 110). Вычисленный `transform` совпал с произведением матриц `DOMMatrix`.

Функции применяются к элементу справа налево — последняя в списке первой, — а система координат меняется слева направо. Это объясняет вопрос «почему анимация вращается вокруг другой точки»: виноват порядок или `transform-origin`. Матрицы 4 × 4 описывают 3D-трансформации в CSS и всю графику :term[WebGL]{def="браузерный API для графики на видеокарте"} ([Графика](/content/additional-topics/graphics-canvas-webgl)).

## Красные флаги в ответе

- **«`includes` — это O(1), он же встроенный».** Встроенный — не значит константный: `includes` проходит массив. Для частых проверок — `Set`.
- **«O(n) всегда быстрее O(n²)».** Только асимптотически: на маленьких n константы решают, а у кеша процессора своё мнение.
- **«`sort(() => Math.random() - 0.5)` перемешивает массив».** Распределение перекошено; правильно — Фишер — Йетс.
- **«`push` — O(1) всегда».** Иногда это O(n) копирования; O(1) — амортизированная оценка.
- **«Совпадение случайных ID маловероятно, вариантов же миллионы».** Совпадения начинаются на корне из числа вариантов.
- **«`%` — это остаток, всегда неотрицательный».** В JavaScript знак результата — как у делимого: `-1 % 5 === -1`.

## Как спрашивают на собеседовании

::question
Что такое O-нотация? Какая сложность у фильтрации массива по другому массиву через `includes`?

#answer
O-нотация описывает, как растёт число шагов с размером входа, без констант и мелких слагаемых. `includes` проходит массив, поэтому фильтрация n элементов с `includes` по массиву из m — O(n·m). Через `Set`: построить множество за O(m), проверять за O(1) в среднем — итого O(n + m) по времени и O(m) дополнительной памяти.

#more
Кроме времени, оценивают память. Константы отбрасываются, но на маленьких данных именно они решают: для десятка элементов `includes` быстрее `Set`. Скрытые циклы — `includes`, `indexOf`, `splice`, `shift`, spread внутри цикла — главный источник случайного O(n²) в коде интерфейса.
::

::question
Что такое амортизированная сложность? Почему `push` считают O(1)?

#answer
Амортизированная сложность — средняя стоимость операции в длинной серии, даже если отдельные операции дорогие. `push` иногда копирует весь массив в буфер большего размера, но ёмкость растёт в разы, поэтому на n вставок приходится меньше 2n копий — в среднем O(1) на вставку.

#more
Если бы ёмкость росла на фиксированную величину, серия вставок стоила бы O(n²). Амортизированная оценка — не средняя по случайным данным, а гарантия для любой последовательности операций. Для интерфейсов это значит: редкие дорогие операции всё равно бывают, и если важна каждая отдельная задержка (кадр анимации), нужна структура с гарантией худшего случая.
::

::question
Как правильно перемешать массив?

#answer
Алгоритмом Фишера — Йетса: идти с конца и менять текущий элемент со случайным из ещё не обработанных, включая сам текущий. Все n! перестановок равновероятны, сложность O(n). `sort(() => Math.random() - 0.5)` неправильный: сортировка ждёт согласованного компаратора, и распределение получается перекошенным.

#more
В проверке на массиве из трёх элементов «случайная» сортировка оставляла исходный порядок в 37% случаев вместо 16,7%. Частая ошибка в самом Фишере — Йетсе — брать `j` из всего массива, а не из `0…i`: тогда перестановок получается nⁿ вариантов на n! исходов, и распределение снова неравномерное. Для криптографических задач `Math.random` не годится — нужен `crypto.getRandomValues`.
::

::question
Почему короткие случайные коды начинают совпадать так рано?

#answer
Это парадокс дней рождения: вероятность, что среди k значений есть хотя бы два одинаковых, растёт с числом пар, а пар примерно k²/2. Поэтому совпадения начинаются при k порядка √N, а не N. Для четырёхсимвольных кодов из цифр и латиницы — 1,68 миллиона вариантов — первый повтор в проверке случался в среднем после 1600 кодов.

#more
Отсюда длина идентификаторов: UUID v4 с 122 случайными битами или nanoid из 21 символа практически не совпадают. Короткие коды для людей проверяют на уникальность в базе при создании. Тот же расчёт объясняет, почему 32-битные хеши не годятся как уникальные ключи для больших наборов.
::

::question
Что такое топологическая сортировка и где она во фронтенде?

#answer
Это порядок вершин ориентированного ацикличного графа, в котором каждая вершина идёт после всех, от которых зависит. Во фронтенде — порядок выполнения модулей, сборки пакетов в монорепозитории и задач в CI. Если отсортировать нельзя, в графе есть цикл.

#more
Алгоритм Кана берёт вершины без входящих зависимостей и убирает их рёбра, за O(V + E). Если вершины остались, а брать нечего, оставшиеся участвуют в цикле — так инструменты находят циклические зависимости. В ESM цикл не ошибка, но модуль может увидеть неинициализированную привязку соседа.
::

::question
Почему `rotate(90deg) translateX(100px)` и `translateX(100px) rotate(90deg)` дают разный результат?

#answer
Каждая функция трансформации — матрица, а цепочка — их произведение, а умножение матриц не коммутативно. Во втором случае элемент сдвигается вправо и поворачивается на месте. В первом сначала поворачивается система координат, и сдвиг вдоль новой оси x уходит вниз.

#more
В проверке точка (10, 0) в одном порядке попала в (100, 10), в другом — в (0, 110), а вычисленный `transform` совпал с произведением `DOMMatrix`. Поворот идёт вокруг `transform-origin`, по умолчанию центра элемента. Отдельные свойства `translate`, `rotate` и `scale` применяются в фиксированном порядке: сначала сдвиг, потом поворот, потом масштаб.
::

## Практика

::practice{title="Фильтр заказов подвисает"}
```js
const visible = orders.filter((o) => !hidden.includes(o.productId));
const total = visible.reduce((sum, o) => sum + o.price, 0);
```

На 20 000 заказов и 5000 скрытых товаров вкладка зависает на секунду. Оцени сложность и исправь.

#solution
`includes` внутри `filter` — O(n·m): 20 000 × 5000 = 100 миллионов сравнений. Множество даёт проверку за O(1) в среднем:

```js
const hiddenSet = new Set(hidden);
const visible = orders.filter((o) => !hiddenSet.has(o.productId));
const total = visible.reduce((sum, o) => sum + o.price, 0);
```

Итого O(n + m) по времени и O(m) по памяти. В проверке результат совпал, а время сократилось в разы. Если `hidden` меняется редко, множество строят один раз и хранят, а не пересоздают на каждой отрисовке.
::

::practice{title="Рекомендации всегда начинаются с одних и тех же"}
```js
function pickRecommendations(items, count) {
  return items.sort(() => Math.random() - 0.5).slice(0, count);
}
```

Маркетологи жалуются: первые товары каталога попадают в рекомендации заметно чаще остальных. Почему и как исправить?

#solution
Компаратор со случайным результатом нарушает требования сортировки, и распределение перестановок перекошено: в проверке исходный порядок трёх элементов выпадал в 37% случаев вместо 16,7%. Кроме того, `sort` меняет исходный массив `items`.

```js
function pickRecommendations(items, count) {
  const a = [...items];
  for (let i = a.length - 1; i > 0; i--) {
    const j = Math.floor(Math.random() * (i + 1));
    [a[i], a[j]] = [a[j], a[i]];
  }
  return a.slice(0, count);
}
```

Фишер — Йетс даёт равновероятные перестановки за O(n). Если нужны только `count` элементов из большого массива, цикл можно остановить после `count` шагов, перемешивая с начала: каждый шаг выбирает случайный элемент из оставшихся.
::

::practice{title="Карусель ломается при листании назад"}
```js
function prev(i, n) {
  return (i - 1) % n;
}
prev(0, 5); // ожидали 4
```

Что вернёт функция и как исправить?

#solution
`-1`. Оператор `%` в JavaScript — остаток с знаком делимого, а не математический модуль. Индекс −1 у массива — `undefined`, и карусель показывает пустую карточку.

```js
const mod = (a, n) => ((a % n) + n) % n;
const prev = (i, n) => mod(i - 1, n);
const next = (i, n) => mod(i + 1, n);

prev(0, 5); // 4
```

Для одного шага назад хватает и `(i - 1 + n) % n`, но `mod` работает для любого сдвига, в том числе на несколько карточек сразу. `Array.prototype.at(-1)` берёт элемент с конца, но индекс не нормализует.
::
