# Функциональное программирование

Функциональное программирование строит программу из чистых функций над неизменяемыми данными, а побочные эффекты выносит на край системы. Во фронтенде его идеи везде: компонент как функция от состояния, редьюсеры, неизменяемые обновления, `map` и `filter`. Спрашивают, что такое чистая функция и ссылочная прозрачность, зачем неизменяемость и что такое функции высшего порядка. Глубже — что такое функтор и монада на примере массива и промиса, чем `Result` лучше исключений и почему ленивые итераторы не обрабатывают лишнего.

::tldr
- **Чистая функция зависит только от аргументов и ничего не меняет снаружи.** Её вызов можно заменить результатом — это ссылочная прозрачность, на ней держатся мемоизация, тесты без моков и параллельные вычисления.
- **Эффекты не запрещены, а вынесены на край:** чистое ядро считает, тонкая оболочка ходит в сеть, читает время и пишет в DOM.
- **Неизменяемость не значит «копировать всё»:** новое состояние разделяет нетронутые части со старым, а изменение видно по смене ссылки.
- **Функтор — контейнер с `map`, монада — ещё и с `flatMap`.** Массив выполняет оба закона; `Promise.then` похож на монаду, но выравнивает вложенные промисы и усыновляет любые объекты с `then`.
- **Ошибки и отсутствие значения можно сделать значениями:** `Result` и `Option` заставляют обработать неудачу, а в TypeScript это размеченные объединения с проверкой полноты.
::

## Чистые функции

Сквозной пример — расчёт заказа в интернет-магазине чая: количество из формы, проверка остатка, скидка, итог.

**Чистая функция** удовлетворяет двум условиям: результат зависит только от аргументов, и функция не производит **побочных эффектов** — не меняет аргументы и внешние переменные, не ходит в сеть, не пишет в :term[DOM]{def="дерево объектов страницы, через которое JavaScript читает и меняет документ"} и консоль, не читает время и случайные числа.

```js
const priceWithVat = (price) => Math.round(price * 1.2);       // чистая
const now = () => Date.now();                                  // нечистая: каждый раз разное
const addItem = (cart, item) => { cart.items.push(item); };    // нечистая: меняет аргумент
```

Из чистоты следует **ссылочная прозрачность**: вызов можно заменить его результатом, и программа не изменится. `priceWithVat(100)` везде можно заменить на `120`. Отсюда практические следствия:

- **мемоизация** — результат можно кешировать по аргументам: в проверке три вызова мемоизированной функции выполнили её тело один раз;
- **тесты без моков** — вход и выход, никакого окружения;
- **порядок и параллельность** — независимые вызовы можно переставлять, откладывать и выполнять в разных потоках;
- **React** опирается на то же свойство: компонент вызывается столько раз, сколько React нужно, и должен возвращать одно и то же при тех же входных данных. Подробнее — в [Механике хуков](/content/reactjs/hooks-mechanics).

Где пишут функции и как работают замыкания — в [Функциях](/content/javascript/functions). Здесь главный вопрос другой: программа без эффектов бесполезна. Куда их деть?

## Эффекты на краю

ФП не запрещает эффекты, оно их **изолирует**. Архитектуру называют «функциональное ядро, императивная оболочка»: все решения принимает чистый код, а оболочка только собирает входные данные и исполняет результат.

```js
// ядро: чистое, время — аргумент
function discountAt(price, date) {
  const hour = date.getHours();
  return hour >= 15 && hour < 16 ? Math.round(price * 0.9) : price;
}

// оболочка: читает время, рисует
button.onclick = () => {
  priceEl.textContent = discountAt(product.price, new Date());
};
```

Ядро тестируется вызовом с любой датой, оболочка тонкая и тривиальная. Тот же принцип в Redux (редьюсер чистый, эффекты — в middleware), в React (отрисовка чистая, эффекты — в обработчиках и `useEffect`) и в бэкенде.

Второй источник проблем, кроме эффектов, — изменяемые данные.

## Неизменяемость

Если функция меняет объект, который видят другие части программы, — это тоже побочный эффект. Неизменяемость решает проблему радикально: данные не меняют, а создают новую версию.

Страх «копировать на каждое изменение дорого» снимает **структурное разделение**: новая версия переиспользует всё, что не изменилось. В проверке Immer изменил количество одного товара в корзине — и новое состояние разделило со старым объект пользователя и первый товар, а новыми стали только корзина, её массив и изменённый товар:

```js
const next = produce(state, (draft) => { draft.cart.items[1].qty = 3; });
next.user === state.user;                   // true — нетронутая ветка общая
next.cart.items[0] === state.cart.items[0]; // true
next.cart === state.cart;                   // false — путь к изменению новый
```

Отсюда дешёвая проверка «изменилось ли»: сравнить ссылки, а не обходить дерево. На этом построены `memo`, селекторы и `computed`. Как писать такие обновления руками — в [Объектах и массивах](/content/javascript/objects-and-arrays).

В языках с настоящими **персистентными структурами данных** (Clojure, Scala, библиотека Immutable.js) деревья устроены так, что изменение копирует O(log n) узлов. В JavaScript данные изменяемы по умолчанию, поэтому неизменяемость держится на дисциплине и инструментах: `Object.freeze` защищает только верхний уровень, `toSorted` и `with` не трогают исходный массив, Immer пишет мутации в черновик и собирает новую версию.

С данными разобрались. Следующая идея ФП — функции как строительный материал.

## Функции из функций

Функции — значения: их передают, возвращают и собирают. **Функции высшего порядка** принимают или возвращают функции: `map`, `filter`, `reduce`, `debounce`, middleware. **Композиция** собирает из маленьких функций большие: `pipe(parseQty, checkStock, total)`. **Каррирование** превращает функцию многих аргументов в цепочку функций одного, чтобы частично применять аргументы. Реализации `compose`, `pipe` и `curry` — в [Паттернах](/content/javascript/patterns).

Композиция хорошо работает, пока каждая функция возвращает обычное значение. Но `parseQty('много')` не может вернуть число. Бросать исключение — значит выйти из композиции. Нужен способ передавать по цепочке и неудачу.

## Функторы и монады

Эти слова пугают, но идея практическая: значение в «контейнере» с контекстом — список, будущее значение, возможное отсутствие, возможная ошибка — и единый способ работать с ним, не распаковывая.

**Функтор** — контейнер с `map`, который применяет функцию к содержимому и сохраняет форму. Законы: `map` тождественной функции ничего не меняет, а `map(f).map(g)` равно `map(x => g(f(x)))`. Массив — функтор, и проверка подтверждает оба закона.

**Монада** — функтор с операцией, которая применяет функцию, *возвращающую контейнер*, и выравнивает результат. У массива это `flatMap`. Законы: обернуть значение и сделать `flatMap(f)` — то же, что `f(x)`; `flatMap` с функцией-обёрткой ничего не меняет; цепочки `flatMap` можно группировать как угодно. Массив выполняет все три.

```js
[1, 2, 3].flatMap((x) => [x, -x]); // [1, -1, 2, -2, 3, -3]
```

### Promise почти монада

`then` работает и как `map`, и как `flatMap`: если функция вернула промис, `then` его дождётся. Поэтому `Promise<Promise<T>>` не бывает: `Promise.resolve(p)` для настоящего промиса возвращает его же.

Но законы нарушены. `Promise.resolve` **усыновляет** любой объект с методом `then` — это сделано для совместимости разных реализаций промисов. В проверке функция, получившая объект `{ then }` напрямую, увидела `'object'`, а через `Promise.resolve(x).then(fn)` — уже строку, которую этот `then` вернул. Для практики это значит: промис — удобный инструмент для асинхронности, но не надёжная абстракция «контейнер для любого значения».

### Option и Result

Отсутствие значения — `Option` (или `Maybe`): либо значение, либо ничего. В JavaScript его роль играют `?.` и `??`: `user.address?.city ?? 'город не указан'` не бросит исключение на `null`.

Ошибка как значение — `Result` (или `Either`): либо успех со значением, либо неудача с причиной. Цепочка шагов, каждый из которых может не удаться:

```js
const ok = (value) => ({ ok: true, value });
const err = (error) => ({ ok: false, error });
const chain = (r, f) => (r.ok ? f(r.value) : r);              // flatMap для Result

const parseQty = (s) => (/^\d+$/.test(s) ? ok(Number(s)) : err('количество — не число'));
const checkStock = (n) => (n <= 5 ? ok(n) : err('на складе только 5'));
const order = (s) => chain(chain(parseQty(s), checkStock), (n) => ok(n * 450));

order('2');     // { ok: true, value: 900 }
order('много'); // { ok: false, error: 'количество — не число' }
```

В отличие от исключения, неудача видна в типе функции, и её нельзя забыть обработать. Цепочка останавливается на первой ошибке без `try`. Так устроены `Result` в Rust, `Either` в :term[Haskell]{def="чисто функциональный язык с ленивыми вычислениями и строгой системой типов"} и библиотеки вроде :term[neverthrow]{def="библиотека TypeScript с типом Result: ошибки возвращаются значением, а не бросаются"} и :term[Effect]{def="библиотека TypeScript для эффектов, типизированных ошибок и конкурентности в функциональном стиле"} в TypeScript.

### Алгебраические типы данных

`Result` — пример **типа-суммы**: значение — один из вариантов. **Тип-произведение** — обычный объект, где есть все поля сразу. Вместе их называют алгебраическими типами данных. В TypeScript сумма — размеченное объединение, а **проверка полноты** через `never` превращает забытый вариант в ошибку компиляции:

```ts
type Payment = { kind: 'card'; last4: string } | { kind: 'sbp'; phone: string } | { kind: 'cash' };

function describe(p: Payment): string {
  switch (p.kind) {
    case 'card': return `карта •${p.last4}`;
    case 'sbp': return `СБП ${p.phone}`;
    case 'cash': return 'наличные';
    default: {
      const unreachable: never = p; // добавили вариант — здесь ошибка компиляции
      return unreachable;
    }
  }
}
```

Сужение типов и размеченные объединения подробно — в [Сужении типов](/content/typescript/type-narrowing).

## Ленивые вычисления

Цепочка методов массива **энергична**: `filter` проходит весь массив и создаёт новый, потом `map` проходит его. Если нужны первые три подходящих заказа из ста тысяч, это лишняя работа. **Ленивая** цепочка вычисляет элемент, только когда его запросили, и останавливается, как только результат готов.

В JavaScript ленивые цепочки дают итераторы и их вспомогательные методы:

```js
const firstBig = orders.values()
  .filter((o) => o.total > 900)
  .map((o) => o.id)
  .take(3)
  .toArray();
```

В проверке на 100 000 заказов энергичная цепочка вызвала `map` больше 9 000 раз, а ленивая — три. Ленивость позволяет работать и с бесконечными источниками: генератор заказов без конца отдал ровно 29 элементов, пока не нашлись три подходящих. Генераторы и протокол итераторов — в [Итераторах и генераторах](/content/javascript/iterators-and-generators).

> **Актуально на ноябрь 2026:** методы итераторов (`map`, `filter`, `take`, `drop`, `flatMap`, `toArray`) — Baseline с марта 2025: Chrome 122, Firefox 131, Safari 18.4; в Node.js — с версии 22.

В чисто функциональных языках ленивость бывает по умолчанию (Haskell): выражение вычисляется, только когда нужен его результат.

## ФП в JavaScript: что работает, а что нет

| Идея | В JavaScript |
| --- | --- |
| функции — значения, замыкания | полностью |
| чистые функции, композиция | дисциплиной и линтерами |
| неизменяемость | `toSorted`, `with`, `structuredClone`, Immer; по умолчанию данные изменяемы |
| рекурсия вместо циклов | ограничена стеком, хвостовые вызовы в V8 не оптимизированы ([Функции](/content/javascript/functions)) |
| алгебраические типы, проверка полноты | в TypeScript через размеченные объединения |
| сопоставление с образцом | нет; предложение TC39 на ранней стадии, пока `switch` по полю |
| ленивость | итераторы и генераторы |

Отсюда прагматичный стиль, который ждут на собеседовании: чистые функции и неизменяемые данные там, где это упрощает рассуждение, императивный цикл там, где он проще и быстрее, и никаких монад ради монад.

## Красные флаги в ответе

- **«Чистая функция — это функция без `this`»** или **«стрелочная функция чистая».** Чистота — про зависимость только от аргументов и отсутствие эффектов, синтаксис ни при чём.
- **«ФП запрещает побочные эффекты».** Оно их изолирует на краю программы; без эффектов программа ничего не делает.
- **«Неизменяемость — это глубокое копирование при каждом изменении».** Новая версия разделяет нетронутые части со старой.
- **«`Object.freeze` делает объект неизменяемым».** Только верхний уровень: вложенный массив внутри замороженного объекта меняется.
- **«Promise — это монада».** Почти: `then` смешивает `map` и `flatMap` и усыновляет любые объекты с `then`, поэтому законы монады не выполняются.
- **«Монада — это что-то из Haskell, на фронтенде не нужно».** Массив с `flatMap`, опциональная цепочка и `Result` в TypeScript — те же идеи.

## Как спрашивают на собеседовании

::question
Что такое чистая функция и ссылочная прозрачность?

#answer
Чистая функция возвращает результат, зависящий только от аргументов, и не делает побочных эффектов: не меняет аргументы и внешнее состояние, не обращается к сети, DOM, времени и случайным числам. Ссылочная прозрачность — следствие: вызов можно заменить результатом без изменения программы.

#more
Отсюда мемоизация, тесты без моков, возможность переставлять и откладывать вызовы. React требует чистой отрисовки, потому что может вызывать компонент повторно и отбрасывать результаты; в строгом режиме он нарочно вызывает её дважды. Частая скрытая нечистота — мутирующие методы вроде `sort` и `push` над аргументом.
::

::question
Как функциональный подход работает с побочными эффектами?

#answer
Изолирует их: решения принимает чистое ядро, а тонкая оболочка собирает входные данные — время, ответ сервера, ввод пользователя — и исполняет результат: пишет в DOM, отправляет запрос. Ядро тестируется вызовом функции, оболочка почти не содержит логики.

#more
Так устроены редьюсеры Redux и эффекты в middleware, отрисовка и `useEffect` в React, команды и события в архитектурах на автоматах состояний. Время и случайность передают аргументом или через внедрённую зависимость: тогда тест на «скидку счастливого часа» не зависит от того, когда его запустили.
::

::question
Зачем нужна неизменяемость? Не дорого ли копировать данные?

#answer
Неизменяемые данные нельзя испортить из другого места программы, а изменение видно по смене ссылки — сравнение за O(1) вместо обхода дерева. На этом работают `memo`, селекторы и отмена действий. Копировать всё не нужно: новая версия разделяет нетронутые части со старой.

#more
В проверке Immer после изменения одного товара оставил общими объект пользователя и остальные товары, а новыми сделал только путь от корня до изменения. Персистентные структуры данных в других языках копируют O(log n) узлов. Ограничение JavaScript — данные изменяемы по умолчанию, и `Object.freeze` поверхностный.
::

::question
Что такое функтор и монада? Есть ли они в JavaScript?

#answer
Функтор — контейнер с `map`, который применяет функцию к содержимому и сохраняет форму; монада — контейнер с `flatMap`, который применяет функцию, возвращающую контейнер, и выравнивает результат. Массив — и то и другое: `map` и `flatMap` выполняют законы.

#more
`Promise.then` работает и как `map`, и как `flatMap`, поэтому вложенных промисов не бывает, но законы монады нарушены: `Promise.resolve` усыновляет любой объект с `then`. `Option` и `Result` — монады для отсутствия значения и ошибки; в JavaScript их роль частично играют `?.` и `??`, в TypeScript — размеченные объединения.
::

::question
Чем `Result` лучше исключений?

#answer
Неудача становится частью типа: вызывающий код видит, что функция может не удаться, и не может забыть это обработать. Цепочка шагов через `flatMap` останавливается на первой ошибке без `try`, а ожидаемые ошибки — неверный ввод, нет на складе — не смешиваются с неожиданными.

#more
Исключения остаются для неожиданного: багов и падения окружения. Минус `Result` в JavaScript — нет синтаксиса вроде `?` из Rust, поэтому цепочки многословны; библиотеки вроде neverthrow и Effect это сглаживают. В TypeScript `Result` — размеченное объединение, и до проверки `ok` поле `value` недоступно.
::

::question
Что такое ленивые вычисления и где они есть в JavaScript?

#answer
Ленивое вычисление выполняется, только когда нужен его результат, и ровно настолько, насколько нужно. Методы массива энергичны: каждый шаг обрабатывает всё. Итераторы и генераторы ленивы: `values().filter().map().take(3)` остановится, как только найдёт три элемента.

#more
В проверке на 100 000 заказов энергичная цепочка вызвала `map` больше 9 000 раз, ленивая — три. Ленивость позволяет работать с бесконечными и потоковыми источниками: генераторами, чтением файла по частям, потоками `fetch`. Цена — накладные расходы на каждый элемент, поэтому на маленьких массивах энергичная цепочка быстрее.
::

## Практика

::practice{title="Тест скидки падает по вечерам"}
Тест проверяет скидку счастливого часа и проходит только с 15 до 16 часов:

```js
function discountedPrice(price) {
  const hour = new Date().getHours();
  return hour >= 15 && hour < 16 ? Math.round(price * 0.9) : price;
}

test('скидка 10%', () => {
  expect(discountedPrice(500)).toBe(450);
});
```

Почему и как переписать, чтобы функция стала чистой?

#solution
Функция читает текущее время — скрытый вход, который меняется между вызовами. Результат зависит не только от аргумента, поэтому функция нечистая и тест нестабильный.

Время делают аргументом, а читают его на краю программы:

```js
function discountAt(price, date) {
  const hour = date.getHours();
  return hour >= 15 && hour < 16 ? Math.round(price * 0.9) : price;
}

test('скидка в счастливый час', () => {
  expect(discountAt(500, new Date(2026, 10, 16, 15, 30))).toBe(450);
});
test('без скидки вечером', () => {
  expect(discountAt(500, new Date(2026, 10, 16, 18, 0))).toBe(500);
});

// оболочка
priceEl.textContent = discountAt(product.price, new Date());
```

Подмена системного времени в тестовом раннере тоже сработает, но это лечение симптома: зависимость от времени остаётся скрытой.
::

::practice{title="Проверки без try"}
Заказ проходит три шага: разобрать количество из строки, проверить остаток (не больше 5), посчитать сумму по 450 рублей. Сейчас каждый шаг бросает исключение, а вызывающий код забывает его ловить. Перепиши на `Result`, чтобы ошибка была значением.

#solution
```js
const ok = (value) => ({ ok: true, value });
const err = (error) => ({ ok: false, error });
const chain = (r, f) => (r.ok ? f(r.value) : r);

const parseQty = (s) => (/^\d+$/.test(s) ? ok(Number(s)) : err('количество — не число'));
const checkStock = (n) => (n <= 5 ? ok(n) : err('на складе только 5'));
const total = (n) => ok(n * 450);

const order = (s) => chain(chain(parseQty(s), checkStock), total);

order('2');     // { ok: true, value: 900 }
order('много'); // { ok: false, error: 'количество — не число' }
order('9');     // { ok: false, error: 'на складе только 5' }
```

`chain` — это `flatMap` для `Result`: если шаг удался, передаёт значение дальше, если нет — пропускает остальные шаги. Вызывающий код получает объект и вынужден посмотреть на `ok`. В TypeScript тип `{ ok: true; value: T } | { ok: false; error: E }` не даст прочитать `value` до проверки.
::

::practice{title="Почему обрабатываются все заказы?"}
Нужно найти номера первых трёх заказов дороже 900 рублей среди 100 000:

```js
const ids = orders.filter((o) => o.total > 900).map((o) => o.id).slice(0, 3);
```

Ответ правильный, но профиль показывает, что `map` вызывается тысячи раз. Почему и как исправить?

#solution
Методы массива энергичные: `filter` проходит все 100 000 заказов и создаёт массив из всех подходящих, `map` преобразует каждый из них, и только потом `slice` берёт три.

Ленивая цепочка на итераторе берёт элементы по одному и останавливается после третьего:

```js
const ids = orders.values()
  .filter((o) => o.total > 900)
  .map((o) => o.id)
  .take(3)
  .toArray();
```

В проверке энергичная версия вызвала `map` больше 9 000 раз, ленивая — три. Без методов итераторов то же делает обычный цикл с `break` — императивная версия здесь тоже хороший ответ.
::
