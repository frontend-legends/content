# Потоки и конкурентность

Конкурентность — когда несколько задач находятся в работе одновременно, параллельность — когда они буквально выполняются в один момент на разных ядрах. Как только задачи делят данные, появляются гонки, а их лечение — блокировки — приносит взаимные блокировки. Спрашивают, чем процесс отличается от потока, конкурентность от параллельности, что такое состояние гонки и deadlock. Глубже — почему однопоточный JavaScript тоже знает гонки, что такое критическая секция и почему восемь хешей паролей в Node.js считаются двумя волнами.

::tldr
- **Процесс — изолированная программа со своей памятью, поток — ход выполнения внутри процесса с общей памятью.** Потоки дешевле процессов, но общая память — источник гонок.
- **Конкурентность — структура программы, параллельность — способ выполнения.** Цикл событий JavaScript конкурентен, но не параллелен: две «асинхронные» вычислительные задачи всё равно идут по очереди.
- **Состояние гонки — результат зависит от порядка операций.** Лечится критической секцией: проверка и изменение выполняются целиком, без вмешательства, — мьютексом в потоках или очередью в асинхронном коде.
- **Взаимная блокировка — каждый ждёт замок, который держит другой.** Нужны четыре условия; проще всего убрать циклическое ожидание — захватывать замки всегда в одном порядке.
- **Модели конкурентности:** общая память с блокировками, обмен сообщениями (воркеры, акторы, каналы) и кооперативная многозадачность (цикл событий, `async`/`await`).
::

## Процессы и потоки

Сквозной пример — интернет-магазин: склад, баланс покупателя, оплата и сервис на Node.js, который хеширует пароли и считает отчёты.

**Процесс** — запущенная программа со своим адресным пространством: память одного процесса не видна другому без специальных механизмов. Браузер так изолирует сайты друг от друга ([Архитектура браузера](/content/web/browser-engines)). Как ОС создаёт процессы и переключает их — в [Архитектуре ОС](/content/computer-science/os-architecture).

**Поток** (thread) — независимый ход выполнения внутри процесса: свой стек и регистры, но общая куча. Потоки создавать и переключать дешевле, а общаться им проще — через ту же память. Именно это делает их опасными: два потока могут менять одни данные одновременно.

Третий уровень — **сопрограммы** (корутины) и **зелёные потоки**: лёгкие задачи, которые переключает не ОС, а среда выполнения. Горутины Go, корутины Kotlin и функции `async` в JavaScript — из этой семьи.

## Конкурентность и параллельность

Эти слова часто путают:

- **конкурентность** — несколько задач в работе одновременно: начали одну, переключились на другую, вернулись. Это про структуру программы;
- **параллельность** — несколько задач буквально выполняются в один момент на разных ядрах. Это про железо.

Один повар, который ставит воду, режет овощи, пока вода закипает, и помешивает соус, — конкурентность. Два повара — параллельность.

JavaScript в одном потоке конкурентен: пока ждёт ответ сервера, он обрабатывает клики. Но параллельности в нём нет. В проверке две вычислительные задачи по 150 мс, обёрнутые в `async` и запущенные через `Promise.all`, заняли 300 мс — по очереди. Те же задачи в двух потоках `worker_threads` выполнились почти одновременно. `async` помогает ждать, а не считать.

### Вытесняющая и кооперативная многозадачность

ОС переключает потоки **вытесняюще**: прерывает поток в любой момент по таймеру. Код не может рассчитывать, что между двумя его строками никто не вмешается.

Цикл событий JavaScript — **кооперативный**: задача выполняется до конца, пока сама не отдаст управление, — до конца функции или до `await`. Отсюда два следствия. Хорошее: внутри синхронного участка гонок нет. Плохое: долгий синхронный цикл блокирует всё, включая отрисовку и ввод. Подробно о цикле событий — в [Event Loop](/content/javascript/event-loop).

Когда задачи делят данные, порядок переключений начинает влиять на результат.

## Состояние гонки

**Состояние гонки** (race condition) — ошибка, при которой результат зависит от того, в каком порядке выполнились операции конкурентных задач. Классический шаблон — **проверить, потом действовать** (check-then-act): между проверкой и действием успевает вмешаться другая задача.

Перевод денег между двумя счетами из нескольких потоков:

```js
const a = acc[from], b = acc[to]; // прочитать оба счёта
acc[from] = a - 1;                // списать
acc[to] = b + 1;                  // зачислить
```

Каждая строка корректна, но поток может прочитать счёт, пока другой поток записывает свой результат. Одна из записей затрёт другую. В проверке четыре потока сделали по 200 000 переводов между двумя счетами, и сумма денег на счетах, которая не должна меняться никогда, разошлась. Частный случай — потерянное увеличение общего счётчика — разобран в [Web Workers](/content/additional-topics/web-workers-and-concurrency).

### Гонки без потоков

Однопоточный JavaScript защищает только синхронный участок. Как только между проверкой и действием появляется `await`, другая задача успевает выполниться:

```js
let balance = 100;
async function withdraw(n) {
  if (balance >= n) {   // оба вызова проверили до списания
    await save();
    balance -= n;
  }
}
await Promise.all([withdraw(80), withdraw(80)]); // balance === -60
```

Это та же гонка «проверить, потом действовать», только точки переключения видны в коде — это `await`. Гонки ответов сервера и их отмена разобраны в [Асинхронности](/content/javascript/async).

## Критическая секция и блокировки

Лечение гонки — сделать проверку и изменение **критической секцией**: участком, который в каждый момент выполняет только одна задача. Инструменты:

- **мьютекс** (mutual exclusion) — замок с одним ключом. Захватил — работаешь, остальные ждут, отпустил — заходит следующий;
- **семафор** — замок с N ключами: одновременно работают не больше N задач. Ограничение параллельных запросов — это семафор ([Асинхронность](/content/javascript/async));
- **блокировка чтения и записи** — читать могут многие сразу, писать — один и без читателей;
- **атомарные операции** — неделимые операции процессора вроде «сравнить и заменить», из которых строят остальное.

Мьютекс на общей памяти — несколько строк на `Atomics`:

```js
const lock = () => {
  while (Atomics.compareExchange(m, 0, 0, 1) !== 0) Atomics.wait(m, 0, 1); // занято — спим
};
const unlock = () => {
  Atomics.store(m, 0, 0);
  Atomics.notify(m, 0, 1);                                                 // разбудить одного
};
```

`compareExchange` атомарно записывает 1, только если там 0, — захватить замок может только один поток. Остальные засыпают в `Atomics.wait` и не тратят процессор. С таким мьютексом вокруг перевода сумма на счетах в проверке осталась ровно два миллиона.

В асинхронном JavaScript мьютекс — очередь промисов: следующая операция начинается после того, как закончилась предыдущая. А между вкладками одного сайта — **Web Locks API**: `navigator.locks.request('balance', fn)` выполнит `fn`, когда замок `balance` свободен во всех вкладках и воркерах этого origin. Так, например, только одна вкладка обновляет токен доступа.

> **Актуально на ноябрь 2026:** Web Locks API — Baseline с 2022 года; в Node.js `navigator.locks` тоже есть.

Блокировки решают гонки, но приносят свою проблему.

## Взаимная блокировка

Задача «заказ» захватывает склад, потом баланс. Задача «возврат» — баланс, потом склад. Если обе успели взять первый замок, каждая ждёт второй, который держит другая, — навсегда. Это **взаимная блокировка** (deadlock).

```js
reserve('заказ', 'stock', 'balance');
reserve('возврат', 'balance', 'stock');
```

В проверке на Web Locks `navigator.locks.query()` через 150 мс показал картину целиком: оба замка удерживаются, и оба запрошены повторно. Ни одна задача не закончится сама.

Взаимная блокировка возможна, только если выполнены все четыре **условия Коффмана**:

1. **взаимное исключение** — ресурс может держать только один;
2. **удержание и ожидание** — держа один ресурс, задача ждёт другой;
3. **нет вытеснения** — отобрать ресурс силой нельзя;
4. **циклическое ожидание** — A ждёт B, B ждёт A.

Достаточно сломать одно. Проще всего — четвёртое: **захватывать замки всегда в одном порядке**. Если и «заказ», и «возврат» берут сначала баланс, потом склад, цикла не бывает: в проверке обе задачи завершились. Другие способы — тайм-аут и отмена (`signal` в Web Locks), захват всех ресурсов сразу или попытка без ожидания (`ifAvailable`).

Родственники взаимной блокировки:

- **livelock** — задачи не стоят, а бесконечно уступают друг другу: обе отпускают замок, видя конфликт, и снова сталкиваются;
- **голодание** (starvation) — задача годами не получает ресурс, потому что его всё время забирают другие: например, писатель, которого вечно обгоняют читатели.

## Модели конкурентности

Общая память с блокировками — не единственный способ. Языки и платформы выбирают разные модели:

| Модель | Идея | Где |
| --- | --- | --- |
| общая память и блокировки | потоки меняют одни данные под замками | Java, C++, C#, `SharedArrayBuffer` и `Atomics` |
| обмен сообщениями, акторы | у каждого свои данные, общение только сообщениями | Erlang и Elixir, Web Workers и `postMessage` |
| каналы (CSP) | задачи передают значения через каналы | горутины и каналы Go |
| цикл событий | один поток, задачи по очереди, ожидание без блокировки | JavaScript в браузере и Node.js |

Обмен сообщениями убирает гонки по построению: нет общих данных — нечего портить. Поэтому в браузере основной способ — воркеры с `postMessage`, а общая память нужна редко ([Web Workers](/content/additional-topics/web-workers-and-concurrency)).

### Пул потоков

Создавать поток на каждую задачу дорого, поэтому серверы и среды выполнения держат **пул** — фиксированное число потоков, которые берут задачи из очереди. Node.js выполняет через пул libuv работу с файлами, `dns.lookup` и тяжёлую криптографию; по умолчанию в пуле 4 потока.

В проверке восемь одновременных вызовов `crypto.pbkdf2` при пуле из 4 потоков закончились двумя волнами: четыре — примерно через 50 мс, ещё четыре — через 100. С `UV_THREADPOOL_SIZE=8` все восемь закончились одной волной. Сервис, который хеширует пароли при входе, упирается в размер пула раньше, чем в процессор.

### Закон Амдала

Добавление потоков ускоряет только параллельную часть работы. Если доля параллельного кода p, то на N ядрах ускорение не больше `1 / ((1 − p) + p / N)`. При 90% параллельного кода четыре ядра дают ускорение в 3,08 раза, а тысяча — всего 9,91: предел — 10, его задают 10% последовательного кода. Поэтому оптимизацию начинают с последовательной части, а не с числа потоков.

## Красные флаги в ответе

- **«JavaScript однопоточный, поэтому гонок в нём нет».** Синхронный участок не прерывается, но каждый `await` — точка, где вмешивается другая задача.
- **«Асинхронный код выполняется параллельно».** Он конкурентный: ожидание идёт одновременно, а вычисления — по очереди в одном потоке.
- **«Конкурентность и параллельность — синонимы».** Конкурентность — структура программы, параллельность — одновременное выполнение на нескольких ядрах.
- **«Deadlock лечится перезапуском»** или **«добавим ещё один замок».** Лечится порядком захвата, тайм-аутами или отказом от удержания и ожидания.
- **«Больше потоков — быстрее».** Ускорение ограничено последовательной частью (закон Амдала), пулом и общими ресурсами.
- **«Атомарные операции решают любую гонку».** Атомарна одна операция; инвариант из нескольких шагов — списать и зачислить — требует критической секции.

## Как спрашивают на собеседовании

::question
Чем процесс отличается от потока?

#answer
Процесс — изолированная программа со своим адресным пространством, ресурсами и хотя бы одним потоком. Поток — ход выполнения внутри процесса: свой стек и регистры, но общая память с остальными потоками процесса. Потоки дешевле создавать и переключать и проще им общаться, но общая память открывает дорогу гонкам.

#more
Падение потока обычно роняет весь процесс, а падение процесса не трогает другие — поэтому браузер изолирует сайты процессами, а не потоками. Ещё легче потоков — сопрограммы и зелёные потоки, которые переключает не ОС, а среда выполнения: горутины, корутины Kotlin, `async`-функции.
::

::question
Чем конкурентность отличается от параллельности? Параллелен ли JavaScript?

#answer
Конкурентность — несколько задач в работе одновременно, с переключением между ними. Параллельность — одновременное выполнение на разных ядрах. Цикл событий JavaScript конкурентен: пока один запрос ждёт ответа, обрабатываются другие события. Но код выполняется в одном потоке, поэтому параллельности нет.

#more
В проверке две вычислительные задачи по 150 мс через `async` и `Promise.all` заняли 300 мс, а в двух воркерах — почти 150. Параллельность в JavaScript — Web Workers и `worker_threads`, а среда выполнения многопоточна и сама: сеть, декодирование картинок и пул libuv работают в других потоках.
::

::question
Что такое состояние гонки? Возможно ли оно в однопоточном JavaScript?

#answer
Ошибка, при которой результат зависит от порядка операций конкурентных задач. Типичный шаблон — «проверить, потом действовать»: между проверкой и изменением вмешивается другая задача. В JavaScript синхронный участок не прерывается, но `await` между проверкой и изменением открывает дверь: два списания по 80 с баланса 100 оба проходят проверку.

#more
Лечится критической секцией: в JavaScript — очередью промисов или Web Locks, проверкой и изменением в одном синхронном участке, а для данных на сервере — транзакцией или атомарной операцией в базе. Гонка ответов сервера — отдельный случай, где помогают отмена через `AbortController` и игнорирование устаревших ответов.
::

::question
Что такое мьютекс и семафор?

#answer
Мьютекс — замок, который в каждый момент держит одна задача: критическая секция выполняется целиком без вмешательства. Семафор — замок со счётчиком: одновременно работают не больше N задач. Пример семафора во фронтенде — ограничение параллельных загрузок до шести.

#more
Мьютекс строится на атомарной операции «сравнить и заменить»: в JavaScript `Atomics.compareExchange` плюс `Atomics.wait` и `Atomics.notify`, чтобы ждущие потоки спали, а не крутились в цикле. В асинхронном коде мьютекс — цепочка промисов, между вкладками — `navigator.locks.request`. Блокировка чтения и записи пускает многих читателей или одного писателя.
::

::question
Что такое взаимная блокировка и как её избежать?

#answer
Ситуация, когда задачи ждут друг друга по кругу: каждая держит ресурс, нужный другой. Нужны четыре условия Коффмана: взаимное исключение, удержание с ожиданием, отсутствие вытеснения и циклическое ожидание. Проще всего убрать цикл: захватывать замки всегда в одном и том же порядке.

#more
Другие способы: тайм-ауты и отмена ожидания, захват всех ресурсов сразу, попытка без ожидания с откатом. В проверке на Web Locks две задачи, захватившие «склад» и «баланс» в разном порядке, зависли, а `navigator.locks.query()` показал оба замка удерживаемыми и запрошенными. Родственные проблемы — livelock, когда задачи бесконечно уступают друг другу, и голодание.
::

::question
Какие бывают модели конкурентности?

#answer
Общая память с блокировками — потоки меняют одни данные под замками. Обмен сообщениями и акторы — у каждого свои данные, общение только сообщениями. Каналы (CSP) — задачи передают значения друг другу, как в Go. Цикл событий — один поток, задачи по очереди, ожидание без блокировки.

#more
Обмен сообщениями исключает гонки по построению, поэтому в браузере основной инструмент — воркеры с `postMessage`, а `SharedArrayBuffer` нужен редко и требует изоляции страницы. Цикл событий хорош для ввода-вывода, но любая долгая вычислительная задача блокирует его целиком, и её выносят в воркер.
::

## Практика

::practice{title="Двойное списание"}
```js
let balance = 100;

async function withdraw(n) {
  if (balance < n) throw new Error('недостаточно средств');
  await api.charge(n);
  balance -= n;
}

await Promise.all([withdraw(80), withdraw(80)]);
console.log(balance);
```

Что выведет код и как исправить, если вызовы могут прийти из разных обработчиков?

#solution
`-60`. Оба вызова проверяют баланс до первого `await`, видят 100 и оба проходят. Проверка и списание разделены `await`, поэтому это не одна критическая секция.

Асинхронный мьютекс выстраивает операции в очередь:

```js
class Mutex {
  #last = Promise.resolve();
  run(fn) {
    const result = this.#last.then(fn);
    this.#last = result.catch(() => {}); // ошибка одной операции не ломает очередь
    return result;
  }
}

const mutex = new Mutex();
const withdraw = (n) => mutex.run(async () => {
  if (balance < n) throw new Error('недостаточно средств');
  await api.charge(n);
  balance -= n;
});
```

В проверке первое списание прошло, второе отклонилось, баланс — 20. Если операция может прийти из другой вкладки, вместо своего мьютекса берут `navigator.locks.request('balance', fn)`. А настоящий баланс проверяет сервер в транзакции: клиентская защита — только от двойного клика.
::

::practice{title="Заказ и возврат зависают"}
```js
function order(id) {
  return locks.request('stock', () => locks.request('balance', () => doOrder(id)));
}
function refund(id) {
  return locks.request('balance', () => locks.request('stock', () => doRefund(id)));
}
```

Изредка заказ и возврат, пришедшие одновременно, зависают навсегда. Почему и как исправить?

#solution
Замки захватываются в разном порядке. Если `order` успел взять `stock`, а `refund` — `balance`, каждый ждёт замок другого — циклическое ожидание, взаимная блокировка. Ошибка редкая, потому что нужна неудачная последовательность переключений.

Единый порядок захвата во всём коде убирает цикл:

```js
const withBoth = (fn) => locks.request('balance', () => locks.request('stock', fn));

const order = (id) => withBoth(() => doOrder(id));
const refund = (id) => withBoth(() => doRefund(id));
```

В проверке с одинаковым порядком обе операции завершились. Страховка на будущее — тайм-аут: `locks.request(name, { signal: AbortSignal.timeout(5000) }, fn)` превратит зависание в ошибку, которую видно в мониторинге.
::

::practice{title="Вход тормозит под нагрузкой"}
Сервис на Node.js хеширует пароль при входе через `crypto.pbkdf2`. Процессор загружен на 30%, а при восьми одновременных входах половина ждёт вдвое дольше. Почему?

#solution
`pbkdf2` с колбэком выполняется не в главном потоке, а в пуле потоков libuv, где по умолчанию 4 потока. Восьмой вход ждёт, пока освободится поток, — вычисления идут волнами. В проверке восемь вызовов закончились двумя волнами по четыре, а с `UV_THREADPOOL_SIZE=8` — одной.

Решения:

```bash
UV_THREADPOOL_SIZE=8 node server.js   # размер пула задаётся до старта процесса
```

- увеличить пул переменной `UV_THREADPOOL_SIZE` при запуске процесса, ориентируясь на число ядер;
- вынести хеширование в отдельные `worker_threads` или сервис;
- не использовать синхронную `pbkdf2Sync` в обработчике запроса — она заблокирует главный поток и все остальные запросы.

Пул общий для файлов, `dns.lookup` и `zlib`, поэтому медленная криптография тормозит и их.
::
