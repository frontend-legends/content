# Структуры данных

Структура данных — способ хранить данные так, чтобы нужные операции были быстрыми. Одна и та же задача решается за O(n²) со списком и за O(n) с хеш-таблицей, поэтому выбор структуры — половина любого алгоритмического решения. На собеседовании спрашивают, как устроены массив, связный список, хеш-таблица, деревья и кучи, сколько стоят их операции и почему, и какую структуру взять для конкретной задачи. Эта тема — карта: здесь устройство структур, а приёмы решения задач с ними — в следующих темах главы.

::tldr
- **Структуру выбирают по операциям:** что делается чаще — чтение по индексу, поиск по ключу, вставка в середину, взятие минимума, обход по порядку.
- **Массив — непрерывный блок памяти:** доступ по индексу O(1), вставка в конец амортизированно O(1), в начало и середину — O(n) из-за сдвига. Он быстрее, чем обещает асимптотика, потому что дружит с кешем процессора.
- **Хеш-таблица — O(1) в среднем на поиск, вставку и удаление,** но не хранит порядок по ключам, тратит лишнюю память, а при плохом хеше вырождается в O(n).
- **Сбалансированное дерево поиска — O(log n) на всё и обход по порядку.** Без балансировки отсортированные вставки превращают его в список.
- **Куча отдаёт минимум за O(1) и снимает его за O(log n);** граф хранят списком смежности или матрицей в зависимости от плотности.
::

## Интерфейс и реализация

У каждой структуры две стороны. **Интерфейс** — какие операции она поддерживает: «очередь» — положить в конец и взять из начала, «словарь» — найти по ключу. **Реализация** — как они устроены внутри. Один интерфейс реализуется по-разному: очередь — массивом с указателем головы, кольцевым буфером или связным списком; словарь — хеш-таблицей или деревом поиска. Интерфейс с договорённостями о поведении называют абстрактным типом данных.

Отсюда вопрос, с которого начинается выбор: какие операции нужны и как часто. Если нужен только поиск по ключу — хеш-таблица. Если ещё и обход по возрастанию ключей — дерево. Если только минимум — куча. Стоимость операций в O-нотации и амортизированная оценка разобраны в [Математике для CS](/content/computer-science/math-for-cs).

## Массив

Массив — элементы подряд в непрерывном блоке памяти. Адрес элемента `i` вычисляется как `начало + i × размер элемента`, поэтому доступ по индексу — O(1) независимо от длины.

### Динамический массив

Статический массив имеет фиксированный размер. **Динамический** — `ArrayList` в Java, `vector` в C++, массив в JavaScript — держит запас ёмкости и, когда он кончается, выделяет блок больше в несколько раз и копирует элементы. Одно копирование стоит O(n), но случается всё реже, и средняя цена `push` — O(1) амортизированно.

Вставка и удаление **в начале или середине** сдвигают все элементы после позиции — O(n). Это относится и к `shift`, и к `unshift`, и к `splice`. Очередь на массиве с `shift` поэтому квадратична, что видно на реальных измерениях ([Обход дерева в ширину](/content/algorithms-data-structures/binary-tree-bfs)).

### Почему массив быстрее, чем кажется

Процессор читает память строками кеша по 64 байта и подгружает следующие заранее. Проход по массиву почти всегда попадает в кеш, а переход по ссылкам связного списка — нет. Поэтому при одинаковом O(n) обход массива бывает в разы быстрее обхода списка, а вставка в середину небольшого массива — быстрее, чем у списка, которому сначала нужно найти позицию. Подробно — в [Архитектуре компьютера](/content/computer-science/computer-architecture).

Массив в JavaScript — объект с числовыми ключами и `length`, у него бывают дырки, а движки хранят плотные массивы чисел как настоящий непрерывный блок ([Объекты и массивы](/content/javascript/objects-and-arrays)). Строка — тоже последовательность, но неизменяемая: любое изменение создаёт новую строку.

## Связный список

Связный список — узлы, каждый хранит значение и ссылку на следующий. **Двусвязный** хранит ещё ссылку на предыдущий, **кольцевой** замыкает последний узел на первый.

Сильная сторона списка — вставка и удаление за O(1), **если узел уже найден**: достаточно переставить ссылки, ничего не сдвигая. Слабые — доступ к k-му элементу за O(k), лишняя память на ссылки и плохая локальность. Поэтому чистый список в прикладном коде встречается редко, а в паре с хеш-таблицей — постоянно: LRU-кеш держит порядок использования двусвязным списком, а узлы находит по ключу через `Map` за O(1). Приёмы задач со списками — в [Связных списках](/content/algorithms-data-structures/linked-list).

**Список с пропусками** (skip list) — несколько уровней связных списков: нижний содержит все элементы, каждый следующий — случайную половину предыдущего. Поиск спускается с верхнего уровня и проходит O(log n) узлов в среднем. Это вероятностная альтернатива сбалансированному дереву, которую проще реализовать; так устроены отсортированные множества в Redis.

## Стек, очередь и дек

**Стек** (LIFO) — положить и взять сверху. Массив с `push` и `pop` — готовый стек за O(1). Стек вызовов, отмена действий, разбор скобок и выражений — всё стеки ([Стек](/content/algorithms-data-structures/stack)).

**Очередь** (FIFO) — положить в конец, взять из начала. **Дек** — класть и брать с обоих концов. На массиве с `shift` взятие из начала стоит O(n), поэтому очередь делают иначе.

### Кольцевой буфер

Массив фиксированной ёмкости, где голова и хвост движутся по кругу: индекс после последнего — снова 0. Все четыре операции дека — O(1), а когда место кончается, буфер удваивается и кольцо разворачивается в начало нового массива:

```ts
class RingDeque<T> {
  private buffer: (T | undefined)[] = new Array(4);
  private head = 0;                               // индекс первого элемента
  size = 0;

  private grow(): void {
    const old = this.buffer;
    this.buffer = new Array(old.length * 2);
    for (let i = 0; i < this.size; i++) this.buffer[i] = old[(this.head + i) % old.length];   // развернуть кольцо
    this.head = 0;
  }

  pushBack(value: T): void {
    if (this.size === this.buffer.length) this.grow();
    this.buffer[(this.head + this.size) % this.buffer.length] = value;
    this.size++;
  }

  pushFront(value: T): void {
    if (this.size === this.buffer.length) this.grow();
    this.head = (this.head - 1 + this.buffer.length) % this.buffer.length;   // шаг назад по кольцу
    this.buffer[this.head] = value;
    this.size++;
  }

  popFront(): T | undefined {
    if (this.size === 0) return undefined;
    const value = this.buffer[this.head];
    this.buffer[this.head] = undefined;           // не держать ссылку — иначе утечка
    this.head = (this.head + 1) % this.buffer.length;
    this.size--;
    return value;
  }

  popBack(): T | undefined {
    if (this.size === 0) return undefined;
    const i = (this.head + this.size - 1) % this.buffer.length;
    const value = this.buffer[i];
    this.buffer[i] = undefined;
    this.size--;
    return value;
  }
}
```

В проверке дек на случайных операциях вёл себя как массив с `push`, `unshift`, `shift` и `pop`, а очередь из 200 000 элементов прошла целиком быстрее чем за полсекунды. Так устроены `ArrayDeque` в Java и буферы потоков ввода-вывода; кольцевой буфер фиксированного размера — это ещё и «последние N событий» в логах и метриках. В задачах на JavaScript обычно хватает массива с указателем головы.

**Приоритетная очередь** — взять не первый пришедший, а самый важный элемент. Её реализуют кучей, о ней ниже.

## Хеш-таблица

Хеш-таблица хранит пары «ключ — значение» в массиве **корзин**. Хеш-функция превращает ключ в число, остаток от деления на число корзин — номер корзины. Если ключи распределяются равномерно, в каждой корзине мало элементов, и поиск, вставка и удаление стоят O(1) в среднем.

### Коллизии

Разные ключи могут попасть в одну корзину — это **коллизия**. Два способа их разрешать:

- **Цепочки** — корзина хранит список пар; при поиске проходят его. Так сделан `HashMap` в Java, который вдобавок превращает слишком длинную цепочку в дерево.
- **Открытая адресация** — все пары лежат прямо в массиве, а при занятой ячейке ищут следующую по правилу (линейно, квадратично, двойным хешированием). Так устроены словари в Python. Удаление здесь сложнее: оставляют отметку «удалено», иначе поиск оборвётся на дыре.

### Перестроение

Когда элементов становится слишком много на корзину — **коэффициент заполнения** выше порога, обычно около 0.75, — таблицу увеличивают вдвое и раскладывают все пары заново: номер корзины зависит от их числа. Перестроение стоит O(n), но, как и рост массива, амортизируется до O(1) на вставку. Вариант с цепочками:

```ts
class HashTable<V> {
  private buckets: [string, V][][] = Array.from({ length: 8 }, () => []);
  size = 0;
  resizes = 0;

  constructor(private hash: (key: string) => number = HashTable.fnv1a) {}

  static fnv1a(key: string): number {             // простой хеш строк: FNV-1a, 32 бита
    let h = 0x811c9dc5;
    for (let i = 0; i < key.length; i++) h = Math.imul(h ^ key.charCodeAt(i), 0x01000193);
    return h >>> 0;
  }

  private bucket(key: string): [string, V][] {
    return this.buckets[this.hash(key) % this.buckets.length];
  }

  set(key: string, value: V): void {
    const bucket = this.bucket(key);
    const entry = bucket.find(([k]) => k === key);
    if (entry) {
      entry[1] = value;
      return;
    }
    bucket.push([key, value]);
    this.size++;
    if (this.size > this.buckets.length * 0.75) this.rehash();   // коэффициент заполнения выше 0.75
  }

  get(key: string): V | undefined {
    return this.bucket(key).find(([k]) => k === key)?.[1];
  }

  delete(key: string): boolean {
    const bucket = this.bucket(key);
    const i = bucket.findIndex(([k]) => k === key);
    if (i === -1) return false;
    bucket.splice(i, 1);
    this.size--;
    return true;
  }

  private rehash(): void {
    const entries = this.buckets.flat();
    this.buckets = Array.from({ length: this.buckets.length * 2 }, () => []);
    for (const [k, v] of entries) this.bucket(k).push([k, v]);   // позиции меняются: другой модуль
    this.resizes++;
  }

  longestChain(): number {
    return Math.max(...this.buckets.map((b) => b.length));
  }
}
```

В проверке таблица на случайных операциях совпала с `Map`. 10 000 ключей вызвали 11 перестроений (8 корзин выросли до 16 384), и самая длинная цепочка была не больше 8 элементов. А с хеш-функцией, возвращающей константу, все 2 000 ключей легли в одну корзину — поиск стал линейным. Это и есть худший случай O(n): на нём построены атаки, когда злоумышленник подбирает ключи с одинаковым хешем, поэтому серверные языки делают хеш строк случайным для каждого запуска.

### Множество и Map

**Множество** — хеш-таблица только с ключами. **Мультимножество** — со счётчиком вхождений, в JavaScript это `Map<ключ, число>`. Спецификация требует, чтобы `Map` и `Set` работали в среднем быстрее линейного времени и обходились в порядке вставки, — движки делают их хеш-таблицами. Чем `Map` лучше объекта-словаря — в [Объектах и массивах](/content/javascript/objects-and-arrays), приёмы задач с подсчётом — в [Хеш-таблицах](/content/algorithms-data-structures/hashmap).

## Деревья

Дерево — узлы со ссылками на детей без циклов. DOM, файловая система, AST в компиляторе и виртуальный DOM — деревья, а обходы и рекурсия на них разобраны в [Двоичных деревьях](/content/algorithms-data-structures/binary-tree-general).

### Двоичное дерево поиска и балансировка

В двоичном дереве поиска (BST) слева от узла всё меньше, справа — больше. Поиск, вставка и удаление идут по одной ветви — O(высоты), а симметричный обход выдаёт ключи по порядку ([Двоичное дерево поиска](/content/algorithms-data-structures/binary-search-tree)). Высота зависит от порядка вставок: отсортированные данные дают дерево-цепочку высоты n.

**Самобалансирующиеся** деревья после каждой вставки и удаления восстанавливают малую высоту **поворотами** — локальными перестановками трёх ссылок, которые сохраняют порядок ключей:

```ts
type AvlNode = { key: number; height: number; left: AvlNode | null; right: AvlNode | null };

const height = (n: AvlNode | null) => n?.height ?? 0;
const update = (n: AvlNode) => {
  n.height = 1 + Math.max(height(n.left), height(n.right));
};

function rotateRight(y: AvlNode): AvlNode {
  const x = y.left!;                              //     y        x
  y.left = x.right;                               //    /    →     \
  x.right = y;                                    //   x            y
  update(y);
  update(x);
  return x;
}

function rotateLeft(x: AvlNode): AvlNode {
  const y = x.right!;
  x.right = y.left;
  y.left = x;
  update(x);
  update(y);
  return y;
}
```

**AVL-дерево** держит разницу высот поддеревьев каждого узла не больше 1. После вставки на пути вверх проверяют баланс и делают один или два поворота:

```ts
function avlInsert(node: AvlNode | null, key: number): AvlNode {
  if (!node) return { key, height: 1, left: null, right: null };
  if (key < node.key) node.left = avlInsert(node.left, key);
  else if (key > node.key) node.right = avlInsert(node.right, key);
  else return node;
  update(node);
  const balance = height(node.left) - height(node.right);
  if (balance > 1) {                              // перевес слева
    if (key > node.left!.key) node.left = rotateLeft(node.left!);   // случай «лево-право»
    return rotateRight(node);
  }
  if (balance < -1) {                             // перевес справа
    if (key < node.right!.key) node.right = rotateRight(node.right!);
    return rotateLeft(node);
  }
  return node;
}
```

В проверке 100 000 ключей, вставленных по возрастанию, дали AVL-дерево высоты 17; обычное BST на тех же данных было бы цепочкой высоты 100 000. Высота AVL-дерева не больше примерно 1,44 · log₂ n.

**Красно-чёрное дерево** балансирует слабее: высота до 2 · log₂(n + 1), зато вставка и удаление делают меньше поворотов. Оно лежит в основе `TreeMap` в Java и `std::map` в C++. **Splay-дерево** после каждого доступа поднимает узел в корень — часто используемые ключи становятся быстрыми, а оценка O(log n) получается амортизированной.

**B-дерево** — сильно ветвящееся дерево, где узел хранит сотни ключей и занимает страницу диска. Высота получается 3–4 даже для миллиардов записей, и каждый уровень — одно чтение с диска. На B-деревьях построены индексы баз данных и файловые системы.

### Префиксное дерево

Префиксное дерево (trie) хранит строки по символам: путь от корня — префикс. Поиск слова и проверка префикса — O(длины строки) независимо от числа слов. **Сжатое** префиксное дерево (radix tree) склеивает цепочки узлов с одним ребёнком в одно ребро со строкой — так экономят память роутеры и IP-маршрутизация. Реализация и задачи — в [Префиксном дереве](/content/algorithms-data-structures/trie).

### Деревья для запросов на отрезках

Когда массив меняется, а нужно часто спрашивать сумму, минимум или максимум на отрезке, префиксные суммы не годятся — каждое изменение пересчитывает их за O(n). **Дерево Фенвика** даёт и изменение, и префиксную сумму за O(log n) в массиве того же размера. Ячейка `i` отвечает за отрезок длины `i & -i` — младшей единицы индекса, и переходы — прибавить или вычесть её:

```ts
class Fenwick {
  private tree: number[];

  constructor(n: number) {
    this.tree = new Array(n + 1).fill(0);         // индексы с 1
  }

  add(i: number, delta: number): void {
    for (i++; i < this.tree.length; i += i & -i) this.tree[i] += delta;   // вверх по ответственным узлам
  }

  prefixSum(i: number): number {                  // сумма элементов 0..i
    let sum = 0;
    for (i++; i > 0; i -= i & -i) sum += this.tree[i];   // сбросить младшую единицу
    return sum;
  }
}
```

Сумма на отрезке `[l, r]` — `prefixSum(r) − prefixSum(l − 1)`. В проверке ответы совпали с прямым суммированием на случайных изменениях. **Дерево отрезков** универсальнее: каждый узел хранит ответ для своего отрезка, а запрос собирает его из O(log n) узлов. Оно умеет минимум, максимум и изменения сразу на отрезке, но кода в нём больше. **Дерево интервалов** хранит интервалы и находит все, пересекающие точку или другой интервал.

## Кучи

Двоичная куча — полное двоичное дерево в массиве, где родитель не больше детей (min-куча) или не меньше (max-куча). Минимум лежит в корне — O(1), вставка и снятие минимума просеивают элемент вверх или вниз — O(log n). Дети узла `i` — `2i + 1` и `2i + 2`, указатели не нужны. Это стандартная реализация приоритетной очереди: планировщики задач, алгоритм Дейкстры, слияние отсортированных потоков.

Построить кучу из готового массива можно за O(n), а не O(n log n): просеивать вниз узлы от середины к началу. Большинство узлов лежит в нижних уровнях и опускается недалеко, и сумма работы по уровням — линейная. На этом построена пирамидальная сортировка ([Сортировка](/content/algorithms-data-structures/sorting)).

**Фибоначчиева куча** уменьшает ключ элемента за O(1) амортизированно, и с ней алгоритм Дейкстры работает за O(E + V log V). На практике из-за большой константы её почти не используют — двоичная куча быстрее на реальных данных. Реализация двоичной кучи и задачи на неё — в [Куче](/content/algorithms-data-structures/heap).

## Графы

Граф — вершины и рёбра. **Ориентированный** различает направление ребра (подписка, импорт модуля), **неориентированный** — нет (дружба, дорога в обе стороны). **Взвешенный** приписывает рёбрам стоимость (расстояние, время). **DAG** — ориентированный граф без циклов: зависимости пакетов, задачи сборки, порядок курсов; его вершины можно выстроить в топологическом порядке.

Два способа хранения:

| Представление | Память | Есть ли ребро u — v | Соседи вершины | Когда брать |
| --- | --- | --- | --- | --- |
| Матрица смежности | O(V²) | O(1) | O(V) | плотный граф, частые проверки рёбер |
| Список смежности | O(V + E) | O(степени u) | O(степени) | разреженный граф — почти всегда |

Реальные графы почти всегда разреженные: у пользователя сотни друзей, а не миллионы. Поэтому по умолчанию — список смежности. Часто граф не хранят вовсе: соседи клетки поля или слова в словаре вычисляются на лету. Обходы и задачи — в [Графах](/content/algorithms-data-structures/graph-general), основы теории — в [Математике для CS](/content/computer-science/math-for-cs).

## Как выбрать структуру

Сводка средних оценок основных операций:

| Структура | Доступ по индексу | Поиск | Вставка | Удаление | Порядок ключей |
| --- | --- | --- | --- | --- | --- |
| Массив | O(1) | O(n) | O(1) в конец, O(n) в середину | O(1) с конца, O(n) из середины | нет |
| Отсортированный массив | O(1) | O(log n) | O(n) | O(n) | да |
| Связный список | O(n) | O(n) | O(1) по узлу | O(1) по узлу | нет |
| Хеш-таблица | — | O(1) | O(1) | O(1) | нет |
| Сбалансированное дерево | — | O(log n) | O(log n) | O(log n) | да |
| Двоичная куча | — | O(n) | O(log n) | O(log n) для минимума | только минимум |

Дальше решают детали:

- **Частые операции.** Много поисков по ключу — хеш-таблица. Нужен ещё порядок или диапазоны — дерево или отсортированный массив. Нужен только минимум или максимум — куча.
- **Память и константа.** Хеш-таблица и списки тратят память на корзины и ссылки. Массив компактен и дружит с кешем — на небольших данных линейный поиск по массиву часто быстрее всего остального.
- **Изменяемость.** Если данные меняются редко, а читаются часто, отсортированный массив с двоичным поиском проще дерева.
- **История изменений.** Для отмены действий и неизменяемого состояния используют **персистентные** структуры: изменение создаёт новую версию, переиспользуя неизменённые части старой. Так устроены неизменяемые обновления состояния во фронтенде — копируется путь к изменённому месту, а не всё дерево.
- **Диск и сеть.** Когда данные не помещаются в память, считают обращения к диску, а не операции: отсюда B-деревья в базах данных.

---

## Красные флаги в ответе

- **«Хеш-таблица — всегда O(1)».** В среднем; при плохом хеше или атаке коллизиями — O(n), плюс перестроения.
- **«Связный список экономит память».** Наоборот: на каждый элемент — ещё ссылка или две, и узлы разбросаны по памяти.
- **«Вставка в список — O(1)», без оговорки.** Только если узел уже найден; поиск позиции — O(n).
- **«Поиск в BST — O(log n)» без слова о балансировке.** Вырожденное дерево — O(n).
- **Очередь на `shift`** в коде, где очередь большая.
- **Не знать, на чём построены `Map` и `Set`,** и чем они отличаются от объекта.

## Как спрашивают на собеседовании

::question
Как устроена хеш-таблица и почему поиск в ней O(1)?

#answer
Это массив корзин. Хеш-функция превращает ключ в число, остаток от деления на число корзин даёт номер корзины, и поиск сразу идёт туда. Разные ключи иногда попадают в одну корзину — коллизии разрешают цепочками или открытой адресацией. Когда элементов становится много на корзину, таблицу увеличивают и раскладывают заново. При равномерном хеше в корзине O(1) элементов в среднем — отсюда O(1) на операцию.

#more
Худший случай — O(n), когда все ключи в одной корзине: плохая хеш-функция или подобранные ключи. Защита — случайная соль в хеше строк, а `HashMap` в Java превращает длинные цепочки в деревья. Перестроение стоит O(n), но амортизируется. Порядок ключей хеш-таблица не хранит; `Map` в JavaScript помнит порядок вставки, но не сортирует.
::

::question
Массив или связный список — что выбрать?

#answer
Почти всегда массив: доступ по индексу O(1), компактная память и проход, который попадает в кеш процессора. Список выигрывает, когда нужно часто вставлять и удалять в середине по уже известному узлу — тогда это O(1) без сдвига. Типичный случай — LRU-кеш: двусвязный список для порядка плюс хеш-таблица для поиска узла.

#more
Асимптотика обманчива: чтобы вставить в середину списка, позицию сначала нужно найти за O(n), а сдвиг небольшого массива — быстрая операция с памятью подряд. Поэтому даже очереди и деки обычно делают на кольцевом буфере, а не на списке.
::

::question
Зачем нужны самобалансирующиеся деревья?

#answer
Операции в дереве поиска стоят O(высоты). Если вставлять данные по возрастанию, обычное BST вырождается в цепочку, и всё становится O(n). Самобалансирующиеся деревья — AVL и красно-чёрные — после каждой вставки и удаления восстанавливают высоту O(log n) поворотами, сохраняя порядок ключей.

#more
AVL балансирует строже — поиск быстрее, вставки дороже. Красно-чёрное допускает высоту до 2 · log n, но делает меньше поворотов — поэтому оно в стандартных библиотеках. Для диска используют B-деревья: узел на страницу, высота 3–4. Без своего дерева в JavaScript упорядоченные данные держат отсортированным массивом с двоичным поиском.
::

::question
Как реализовать очередь, если есть только стеки?

#answer
Двумя стеками: в первый кладём, из второго берём. Когда второй пуст, перекладываем в него всё из первого — порядок разворачивается, и самый старый элемент оказывается сверху. Каждый элемент перекладывается один раз, поэтому операции O(1) амортизированно.

#more
Обратная задача — стек на очередях — решается за O(n) на одну из операций. Очередь на двух стеках встречается в функциональных языках, где неизменяемый список — естественный стек. Вариант с минимумом в каждом стеке даёт очередь, которая отвечает на «минимум в очереди» за O(1).
::

::question
Какую структуру данных вы возьмёте: для проверки, видели ли идентификатор запроса; для таблицы лидеров с частыми изменениями; для отмены и повтора действий; для задач с приоритетами; для автодополнения?

#answer
1. **Множество на хеш-таблице** — проверка O(1). Если идентификаторов слишком много для памяти, — вероятностный фильтр Блума с допустимыми ложными срабатываниями.
2. **Сбалансированное дерево или отсортированное множество** по очкам — изменение O(log n) и первые 10 обходом по порядку. Если нужен только топ-10 без изменения остальных, хватит min-кучи размера 10.
3. **Два стека**: `undo` снимает действие со стека истории и кладёт в стек повтора, новое действие очищает стек повтора.
4. **Куча** (приоритетная очередь) — взять самую срочную за O(log n).
5. **Префиксное дерево** — поиск слов на префикс за длину префикса; на небольших словарях — отсортированный массив и двоичный поиск границ префикса.

#more
Хороший ответ начинается с вопроса, какие операции нужны и с какой частотой, и только потом называет структуру. На небольших данных простой массив часто выигрывает у всего остального — стоит сказать, начиная с какого размера выбор начинает иметь значение.
::

::question
Как хранить граф: матрицей смежности или списками?

#answer
Списками смежности почти всегда: память O(V + E), и обход соседей стоит столько, сколько у вершины соседей. Матрица тратит O(V²) памяти и O(V) на обход соседей, зато проверяет наличие ребра за O(1) — она оправдана для плотных графов и маленького числа вершин.

#more
Реальные графы — соцсети, зависимости, дороги — разреженные, и матрица для них в основном из нулей. Есть и третий вариант — список рёбер, удобный для алгоритма Краскала и сортировки рёбер по весу. Часто граф вообще не строят: соседей вычисляют на лету, как клетки поля.
::

## Практика

::practice{title="Очередь на двух стеках"}
Реализуйте очередь с `enqueue` и `dequeue`, используя только два массива как стеки (`push` и `pop`). Каждая операция должна быть O(1) амортизированно.

#solution
Новые элементы кладём в `inbox`. Брать будем из `outbox`; если он пуст, перекладываем в него весь `inbox` — порядок разворачивается, и самый старый элемент оказывается сверху:

```ts
class TwoStackQueue<T> {
  private inbox: T[] = [];
  private outbox: T[] = [];

  enqueue(value: T): void {
    this.inbox.push(value);
  }

  dequeue(): T | undefined {
    if (this.outbox.length === 0) {
      while (this.inbox.length) this.outbox.push(this.inbox.pop()!);   // переложить — порядок развернётся
    }
    return this.outbox.pop();
  }
}
```

Отдельный `dequeue` может стоить O(n), но каждый элемент за всю жизнь перекладывается один раз — O(1) амортизированно. Перекладывать нужно только когда `outbox` пуст: иначе новые элементы обгонят старые. В проверке на случайных операциях очередь выдавала элементы в том же порядке, что эталонный массив.
::

::practice{title="Сумма на отрезке с изменениями"}
Есть массив цен по дням. Цены иногда исправляют задним числом, а сумму за любой отрезок дней спрашивают постоянно. Префиксные суммы отвечают за O(1), но каждое исправление пересчитывает их за O(n). Сделайте обе операции за O(log n).

#solution
Дерево Фенвика из раздела про деревья хранит префиксные суммы так, что изменение элемента затрагивает O(log n) ячеек. Сумма на отрезке — разность двух префиксов:

```ts
function rangeSum(fenwick: Fenwick, l: number, r: number): number {
  return fenwick.prefixSum(r) - (l > 0 ? fenwick.prefixSum(l - 1) : 0);   // [l, r] = [0, r] − [0, l − 1]
}
```

Использование:

```ts
  const prices = [5, 3, 8, 6, 2, 7, 4, 9];
  const fenwick = new Fenwick(prices.length);
  prices.forEach((p, i) => fenwick.add(i, p));
  rangeSum(fenwick, 1, 4);                        // 3 + 8 + 6 + 2 = 19
  fenwick.add(2, -5);                             // цена дня 2: 8 → 3
  rangeSum(fenwick, 1, 4);                        // 14
```

Исправление цены — это `add` с разницей между новой и старой. Если нужен минимум или максимум на отрезке, разность префиксов не работает — берут дерево отрезков. В проверке суммы на случайных отрезках совпали с прямым суммированием после каждого изменения.
::

::practice{title="Почему дерево стало списком"}
В BST по очереди вставили числа от 1 до 100 000. Какой будет высота, сколько сравнений займёт поиск 100 000, и что изменится, если дерево самобалансирующееся?

#solution
Каждое новое число больше всех предыдущих и уходит вправо — дерево становится цепочкой высоты 100 000, поиск последнего числа — 100 000 сравнений, вставка всех — O(n²). Рекурсивная вставка на такой глубине ещё и переполнит стек вызовов. AVL-дерево после каждой вставки поворачивает узлы и держит высоту около log₂ n:

```ts
  let root: AvlNode | null = null;
  for (let k = 1; k <= 100_000; k++) root = avlInsert(root, k);                                     // отсортированные вставки
  assert.equal(height(root), 17);                                                                   // обычное BST дало бы 100 000
```

Поиск — не больше 17 сравнений.
::
