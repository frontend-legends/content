# Поиск

Поиск элемента — самая частая операция с данными, и способ зависит от того, что о данных известно. Ничего не известно — остаётся перебор. Данные отсортированы — двоичный поиск отбрасывает половину на каждом шаге. Значения ещё и распределены равномерно — можно угадывать позицию, как ищут слово в бумажном словаре. Неизвестна длина — сначала ищут границу. На собеседовании спрашивают, чем эти алгоритмы отличаются, когда какой выбрать и как искать там, где обычный двоичный поиск не подходит напрямую.

::tldr
- **Линейный поиск — O(n), но без требований к данным;** на маленьких массивах он быстрее всего остального.
- **Двоичный поиск — O(log n) на отсортированных данных:** миллион элементов — не больше 20 сравнений.
- **Интерполяционный — O(log log n) на равномерно распределённых значениях, но O(n) на неравномерных.** Он угадывает позицию по значению, а не берёт середину.
- **Экспоненциальный ищет границу удвоением шага, а потом двоичный поиск внутри** — O(log i), где i — позиция ответа. Подходит для массивов неизвестной длины и потоков.
- **Если искать часто, данные готовят заранее:** хеш-таблица — O(1) для точного совпадения, сортировка — для диапазонов и ближайших.
::

## Линейный поиск

Перебрать элементы по порядку до совпадения — `indexOf`, `includes`, `find`. O(n) в худшем случае, но никаких требований: данные могут быть не отсортированы, сравнение может быть любым условием, а не равенством.

На маленьких массивах — до десятков и сотен элементов — линейный поиск часто быстрее двоичного: проход по памяти подряд хорошо ложится на кеш процессора и не требует ветвлений, которые трудно предсказать. Если по одним и тем же данным ищут много раз, перебор каждый раз — ошибка: один раз постройте `Set` или `Map` и ищите за O(1) ([Хеш-таблицы](/content/algorithms-data-structures/hashmap)).

## Двоичный поиск

На отсортированных данных сравнение с серединой отбрасывает половину: если середина меньше цели, ответ правее. Вариант с закрытым интервалом `[lo, hi]` и тремя исходами:

```ts
function binarySearch(arr: number[], target: number, lo = 0, hi = arr.length - 1): number {
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1;
    const v = arr[mid];
    if (v === target) return mid;
    if (v < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}
```

O(log n): в проверке поиск по миллиону чисел ни разу не прочитал больше 20 элементов — ⌈log₂ 10⁶⌉ = 20. Поиск границ, позиции вставки, поиск в повёрнутом массиве и поиск по ответу — в [Двоичном поиске](/content/algorithms-data-structures/binary-search): там шаблон с полуинтервалом, который не ошибается на краях.

## Интерполяционный поиск

Ищем слово «яблоко» в словаре — открываем ближе к концу, а не посередине. Интерполяционный поиск делает так же: оценивает позицию пропорционально значению — где цель лежала бы, если значения растут равномерно от `arr[lo]` до `arr[hi]`:

```ts
function interpolationSearch(arr: number[], target: number): number {
  let lo = 0;
  let hi = arr.length - 1;
  while (lo <= hi) {
    const low = arr[lo];
    const high = arr[hi];
    if (target < low || target > high) return -1;
    if (high === low) return low === target ? lo : -1;
    // угадать позицию по значению, как ищут слово в бумажном словаре
    const pos = lo + Math.floor(((target - low) * (hi - lo)) / (high - low));
    const v = arr[pos];
    if (v === target) return pos;
    if (v < target) lo = pos + 1;
    else hi = pos - 1;
  }
  return -1;
}
```

На равномерно распределённых значениях — O(log log n) шагов: для миллиона чисел это единицы проб. В проверке на миллионе равномерных чисел среднее число чтений было меньше 15 — по три на шаг. Но на неравномерных данных оценка ошибается систематически: на кубах чисел от 0 до 99 999 поиск элемента с индексом 1000 сдвигал пробу на одну позицию за шаг и сделал 1001 шаг, а двоичный поиск нашёл его не больше чем за 17 сравнений. Худший случай — O(n). Проверка `high === low` защищает от деления на ноль на одинаковых значениях.

Поэтому интерполяционный поиск используют, когда распределение известно: равномерные идентификаторы, метки времени с ровным шагом, хеши.

## Экспоненциальный поиск

Если ответ, скорее всего, близко к началу или длина массива неизвестна, сначала ищут границу: проверяют позиции 1, 2, 4, 8… пока значение не станет не меньше цели. Ответ — между предыдущей и текущей границей, и там работает обычный двоичный поиск:

```ts
function exponentialSearch(arr: number[], target: number): number {
  if (arr.length === 0) return -1;
  let bound = 1;
  while (bound < arr.length && arr[bound] < target) bound *= 2;   // 1, 2, 4, 8… пока не перешагнули
  return binarySearch(arr, target, bound >> 1, Math.min(bound, arr.length - 1));
}
```

O(log i), где i — позиция ответа: удвоений log i, и интервал для двоичного поиска длины не больше i. В проверке элемент с индексом 5 в массиве из миллиона нашёлся не больше чем за 8 чтений. Тот же приём — **галопирующий режим** TimSort при слиянии и поиск в потоках, где длина заранее неизвестна.

## Поиск прыжками

Идём блоками длины √n, пока последний элемент блока меньше цели, а внутри найденного блока — линейно:

```ts
function jumpSearch(arr: number[], target: number): number {
  const n = arr.length;
  const step = Math.max(1, Math.floor(Math.sqrt(n)));
  let prev = 0;
  let next = step;
  while (prev < n && arr[Math.min(next, n) - 1] < target) {   // прыгать блоками по √n
    prev = next;
    next += step;
  }
  for (let i = prev; i < Math.min(next, n); i++) {   // линейно внутри блока
    if (arr[i] === target) return i;
  }
  return -1;
}
```

O(√n): до √n прыжков и до √n шагов в блоке — на миллионе элементов это до двух тысяч чтений против 20 у двоичного. Смысл алгоритма — в носителях, где шаг назад дорог: прыжки идут только вперёд, и назад возвращаются не больше чем на один блок. Сегодня его спрашивают скорее как пример компромисса между линейным и двоичным поиском.

## Как выбрать

| Данные | Алгоритм | Время |
| --- | --- | --- |
| не отсортированы, поиск один раз | линейный | O(n) |
| не отсортированы, поисков много | построить `Set` или `Map` | O(n) один раз, потом O(1) |
| отсортированы | двоичный | O(log n) |
| отсортированы и равномерны | интерполяционный | O(log log n) в среднем, O(n) в худшем |
| отсортированы, длина неизвестна или ответ у начала | экспоненциальный | O(log i) |
| нужны диапазоны и ближайшие | отсортированный массив или дерево поиска | O(log n) |
| нужен поиск по префиксу строки | префиксное дерево | O(длины префикса) |

Поиск подстроки в строке — отдельная задача со своими алгоритмами, разобранными в [Строках и массивах](/content/algorithms-data-structures/strings-arrays).

## Красные флаги в ответе

- **Двоичный поиск по неотсортированным данным** — или сортировка ради одного поиска: O(n log n) вместо O(n).
- **Линейный поиск в цикле** — `includes` внутри обхода даёт O(n²), когда хватает `Set`.
- **«Интерполяционный всегда быстрее двоичного».** Только на равномерных данных; на неравномерных — O(n).
- **Не уметь искать без известной длины** — экспоненциальный поиск границы.
- **Ошибки на краях двоичного поиска** — бесконечный цикл на двух элементах, промах на единицу.

## Как спрашивают на собеседовании

::question
Чем двоичный поиск отличается от линейного и когда линейный лучше?

#answer
Двоичный требует отсортированных данных и отбрасывает половину на каждом шаге — O(log n). Линейный проверяет всё по порядку — O(n), зато работает на любых данных и с любым условием. Линейный лучше на маленьких массивах, для одного поиска по неотсортированным данным и когда условие — не сравнение с ключом.

#more
Сортировка ради одного поиска не окупается: O(n log n) против O(n). Окупается, если поисков много: k поисков — O(n log n + k log n) против O(k · n). Если нужно только точное совпадение, ещё лучше хеш-таблица — O(n) на построение и O(1) на поиск.
::

::question
Как работает интерполяционный поиск и почему он может быть медленнее двоичного?

#answer
Он оценивает позицию цели пропорционально её значению между `arr[lo]` и `arr[hi]`, а не берёт середину. На равномерных данных оценка точная, и шагов O(log log n). Но если значения растут неравномерно — например, экспоненциально или как кубы, — оценка систематически промахивается, проба сдвигается на один элемент за шаг, и худший случай — O(n).

#more
Есть гибриды: делать интерполяционный шаг, а при плохом прогрессе — двоичный, что гарантирует O(log n). Нужно следить за делением на ноль на одинаковых значениях и за переполнением произведения в языках с фиксированными целыми.
::

::question
Как искать в отсортированном массиве, длина которого неизвестна?

#answer
Экспоненциальным поиском: проверять позиции 1, 2, 4, 8… пока значение не окажется не меньше цели или не выйдем за конец. Тогда ответ в последнем удвоенном интервале, и в нём работает двоичный поиск. Удвоений — O(log i), поиск — O(log i), где i — позиция ответа.

#more
Так ищут в потоках, бесконечных последовательностях и при поиске по ответу без известной верхней границы. Если ответ близко к началу, экспоненциальный поиск быстрее двоичного по всему массиву даже при известной длине.
::

::question
Как искать в матрице, отсортированной по строкам и по столбцам?

#answer
Начать с правого верхнего угла. Если значение больше цели, весь столбец ниже ещё больше — сдвигаемся влево. Если меньше, вся строка левее ещё меньше — сдвигаемся вниз. Каждый шаг отбрасывает строку или столбец, поэтому O(m + n).

#more
Двоичный поиск по каждой строке — O(m log n), хуже при квадратной матрице. Если матрица отсортирована целиком (каждая строка начинается после конца предыдущей), её читают как один массив и ищут двоичным поиском за O(log(m · n)).
::

::question
Как найти первую версию, после которой всё сломалось?

#answer
Версии упорядочены, и свойство «сломано» монотонно: после первой плохой все плохие. Значит, двоичный поиск по номеру версии: середина плохая — первая не правее её, иначе — правее. Проверок O(log n): из тысячи версий хватит десяти.

#more
Так работает `git bisect`: он делит диапазон коммитов пополам, а разработчик или скрипт отмечает каждый как хороший или плохой. Если проверка дорогая — сборка, прогон тестов, — разница между n и log n проверок огромна.
::

## Практика

::practice{title="702. Search in a Sorted Array of Unknown Size"}
Отсортированный массив различных чисел доступен только через `reader.get(i)`; за концом массива он возвращает 2^31 − 1. Найти индекс `target` или −1 за O(log n). [Задача на LeetCode](https://leetcode.com/problems/search-in-a-sorted-array-of-unknown-size/)

#solution
Интерфейс чтения:

```ts
interface ArrayReader {
  get(index: number): number;                     // за концом — 2^31 − 1
}
```

Экспоненциальный поиск: удваиваем `hi`, пока значение меньше цели, — значение за концом огромно и само остановит удвоение. Потом двоичный поиск между `hi / 2` и `hi`:

```ts
function searchUnknown(reader: ArrayReader, target: number): number {
  let hi = 1;
  while (reader.get(hi) < target) hi *= 2;        // найти границу, за которой target уже не может быть
  let lo = hi >> 1;
  while (lo <= hi) {
    const mid = (lo + hi) >>> 1;
    const v = reader.get(mid);
    if (v === target) return mid;
    if (v < target) lo = mid + 1;
    else hi = mid - 1;
  }
  return -1;
}
```

O(log i), где i — позиция цели. В проверке ответ совпал с `indexOf` на случайных массивах.
::

::practice{title="278. First Bad Version"}
Версии от 1 до n; после первой плохой все плохие. Найти первую плохую, вызывая `isBad(version)` как можно меньше раз. [Задача на LeetCode](https://leetcode.com/problems/first-bad-version/)

#solution
Двоичный поиск первой позиции, где условие истинно:

```ts
function firstBadVersion(n: number, isBad: (version: number) => boolean): number {
  let lo = 1;
  let hi = n;
  while (lo < hi) {
    const mid = lo + Math.floor((hi - lo) / 2);
    if (isBad(mid)) hi = mid;                     // mid плохая — первая не правее
    else lo = mid + 1;
  }
  return lo;
}
```

⌈log₂ n⌉ вызовов: в проверке на n до 1000 их ни разу не было больше. `lo + (hi − lo) / 2` вместо `(lo + hi) / 2` — привычка из языков с 32-битными целыми, где сумма двух больших номеров переполняется; в JavaScript сумма точна, и в проверке поиск среди 2^31 − 1 версий отработал верно.
::

::practice{title="240. Search a 2D Matrix II"}
В матрице каждая строка отсортирована слева направо, каждый столбец — сверху вниз. Есть ли в ней `target`? [Задача на LeetCode](https://leetcode.com/problems/search-a-2d-matrix-ii/)

#solution
Из правого верхнего угла каждое сравнение отбрасывает целую строку или целый столбец:

```ts
function searchMatrixII(matrix: number[][], target: number): boolean {
  let r = 0;
  let c = matrix[0].length - 1;                   // правый верхний угол
  while (r < matrix.length && c >= 0) {
    const v = matrix[r][c];
    if (v === target) return true;
    if (v > target) c--;                          // весь столбец ниже ещё больше — отбросить
    else r++;                                     // вся строка левее ещё меньше — отбросить
  }
  return false;
}
```

O(m + n). Из левого нижнего угла работает так же, а из левого верхнего — нет: оба соседа больше, и непонятно, куда идти. В проверке ответ совпал с поиском по всем элементам на случайных матрицах.
::
