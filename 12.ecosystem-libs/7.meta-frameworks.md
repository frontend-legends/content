# Мета-фреймворки

Что добавляет мета-фреймворк поверх React, Vue или Svelte и чем они различаются: Next.js, React Router в режиме фреймворка, TanStack Start, Nuxt, SvelteKit, Astro — их модели рендеринга, данные и серверный код. Спрашивают, зачем нужен мета-фреймворк, чем Next.js отличается от Astro и когда брать обычное SPA. Глубже — откуда фреймворк знает, что страницу можно собрать заранее, почему серверный код не попадает в браузер и что такое острова.

::tldr
- **Мета-фреймворк — UI-библиотека плюс сервер и соглашения:** маршрутизация по файлам, рендеринг на сервере и при сборке, загрузка данных, серверные функции, сборка и выкладка. То, что в SPA собирают из десятка библиотек.
- **Фреймворк сам решает, как отдавать каждую страницу:** собрать HTML заранее, если страница не зависит от запроса, или рендерить на каждый запрос, если читает cookies, заголовки или параметры. Next.js показывает это прямо в выводе сборки.
- **Серверный код остаётся на сервере:** в Next.js серверные компоненты не попадают в браузерный бандл, туда уходят только компоненты с `'use client'`.
- **Astro по умолчанию отдаёт HTML без JavaScript,** а интерактивные компоненты подключаются островами с `client:load`, `client:visible` и другими. Это лучший выбор для контентных сайтов.
- **Выбор — по типу продукта и UI-библиотеке:** приложение на React — Next.js, React Router или TanStack Start; на Vue — Nuxt; на Svelte — SvelteKit; контентный сайт — Astro; внутренний инструмент без SEO — обычное SPA на Vite.
::

---

## Что добавляет мета-фреймворк

React и Vue рисуют интерфейс. Всё остальное приложению нужно собрать самому: роутер, загрузку данных, рендеринг на сервере, гидратацию, API, сборку, разделение кода, мета-теги, выкладку. Мета-фреймворк даёт это как единое целое с соглашениями:

| Задача | Что даёт фреймворк |
| --- | --- |
| маршруты | файлы и папки становятся адресами, вложенные макеты |
| рендеринг | на сервере, при сборке, с кешем, на клиенте — для каждого маршрута |
| данные | загрузка на сервере до рендера, без водопадов на клиенте |
| серверный код | API-маршруты, серверные функции, middleware |
| оптимизация | разделение по маршрутам, предзагрузка ссылок, картинки, шрифты |
| выкладка | адаптеры под Node.js, бессерверные платформы и edge |

Стратегии рендеринга — CSR, SSR, SSG, ISR, стриминг — и их компромиссы разобраны в [Рендеринге и гидратации React](/content/reactjs/rendering-and-hydration), устройство Nuxt — в [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt). Здесь — сравнение фреймворков.

Сквозной пример — магазин: каталог (одинаков для всех, важно SEO), страница заказов (своя у каждого пользователя), кнопка «В корзину» (интерактивная).

## Как фреймворк решает, как отдавать страницу

В Next.js маршрут — файл в папке `app`:

```jsx
// app/page.jsx — каталог
import AddToCart from './add-to-cart';
export default function Page() {
  return <main><h1>Каталог</h1><AddToCart /></main>;
}

// app/orders/page.jsx — заказы
import { cookies } from 'next/headers';
export default async function Orders() {
  const c = await cookies();
  return <p>Заказы для {c.get('user')?.value ?? 'гостя'}</p>;
}
```

Разработчик нигде не указал режим. Фреймворк смотрит, **от чего зависит** страница: каталог не читает ничего из запроса — его можно собрать при сборке; заказы читают cookies — их нужно рендерить на каждый запрос. В проверке вывод `next build` отметил главную знаком `○` (статическая, собрана заранее, в сборке лежит готовый `index.html` с `<h1>Каталог</h1>`), а `/orders` — знаком `ƒ` (динамическая).

Кеширование в Next.js 16 стало явным: директива `'use cache'` помечает страницу, компонент или функцию, результат которых можно кешировать, а включённые Cache Components позволяют совмещать на одной странице статичную оболочку и динамические части со стримингом.

### Серверный код остаётся на сервере

```jsx
// app/add-to-cart.jsx
'use client';
import { useState } from 'react';
export default function AddToCart() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>В корзине: {n}</button>;
}
```

Компоненты в Next.js по умолчанию **серверные**: они выполняются на сервере, и их код не попадает в браузер. В браузер уходят только компоненты с `'use client'` и то, что они импортируют. В проверке строка из серверного компонента не нашлась ни в одном браузерном файле сборки, а текст клиентской кнопки — нашёлся. Граница `'use client'`, что можно через неё передавать и серверные функции — в [RSC и React 19](/content/reactjs/rsc-and-react-19).

## Острова: Astro

Astro идёт от обратного: **по умолчанию страница — HTML без JavaScript**. Компоненты React, Vue, Svelte или Solid рендерятся на сервере в HTML, а в браузере оживают только те, у которых явно указана директива загрузки:

```astro
---
import AddToCart from '../components/AddToCart.jsx';
---
<h1>Улун</h1>
<p>Китайский чай</p>
<AddToCart client:visible />
```

| Директива | Когда загружается код компонента |
| --- | --- |
| нет | никогда — компонент только HTML |
| `client:load` | сразу |
| `client:idle` | когда браузер свободен |
| `client:visible` | когда компонент попадает в зону видимости |
| `client:media` | при совпадении медиазапроса |
| `client:only` | только в браузере, без серверного рендера |

В проверке страница с компонентом без директивы получила готовую кнопку в HTML и ни одного `<script>`, а страница с `client:visible` — элемент `astro-island` и код для его оживления. React загружается только ради острова. Для контентных сайтов — блогов, документации, маркетинговых страниц, каталогов — это минимальный JavaScript без усилий. Astro также умеет **серверные острова** — части страницы, которые рендерятся на сервере отдельно и подставляются позже, — и коллекции контента с типизированной схемой.

Та же идея во Vue — ленивая гидратация и серверные компоненты Nuxt (подробно — в [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt)).

## Ландшафт

Актуально на ноябрь 2026.

| Фреймворк | UI | Модель | Особенность |
| --- | --- | --- | --- |
| Next.js 16 | React | серверные компоненты, SSR, SSG, кеш через `'use cache'` | самый распространённый, Turbopack по умолчанию, тесная связь с Vercel |
| React Router 8 (режим фреймворка) | React | загрузчики и действия маршрутов, SSR, предрендер | наследник Remix, близок к веб-стандартам: `Request`, `Response`, формы |
| TanStack Start 1 | React, Solid | SSR, серверные функции, на Vite | типобезопасная маршрутизация TanStack Router, клиент-ориентированный |
| Nuxt 4 | Vue | SSR, SSG, гибридный рендеринг по маршрутам | стандарт для Vue, Nitro для сервера |
| SvelteKit 3 | Svelte | SSR, SSG, загрузчики, формы | компилятор Svelte, маленький бандл |
| Astro 7 | любой, острова | HTML по умолчанию, острова, серверные острова | контентные сайты, минимум JavaScript |
| SolidStart 2 | Solid | SSR, серверные функции | сигналы без virtual DOM |
| Remix 3 | свой | веб-стандарты | новый фреймворк без React; прежний Remix продолжился как React Router |

Сервер у многих общий: Nuxt, SolidStart и TanStack Start используют Nitro или похожие слои, которые собирают приложение под Node.js, бессерверные функции и edge одной сборкой (подробно — в [Edge-вычислениях](/content/modern-dev/edge-computing) и [Хостинге и платформах](/content/testing-deploying/hosting-and-platforms)).

## Как выбрать

| Продукт | Выбор |
| --- | --- |
| контентный сайт, блог, документация, маркетинг | Astro |
| приложение на React с SEO и серверным рендером | Next.js или React Router в режиме фреймворка |
| React-приложение, где важна типобезопасность маршрутов и клиентская логика | TanStack Start |
| приложение на Vue | Nuxt |
| приложение на Svelte | SvelteKit |
| внутренний инструмент, админка, кабинет без SEO | SPA на Vite — без сервера и его сложностей |

Дополнительно смотрят:

- **где будет работать:** самостоятельный сервер, бессерверные функции, edge, статический хостинг — у фреймворков разная поддержка;
- **привязка к платформе:** часть возможностей Next.js лучше всего работает на Vercel, у остальных — адаптеры под разные платформы;
- **сложность модели:** серверные компоненты, кеш и граница клиент-сервер требуют обучения команды;
- **стабильность API:** мажорные версии мета-фреймворков меняют соглашения чаще, чем UI-библиотеки.

Мета-фреймворк — это сервер, который нужно эксплуатировать, мониторить и масштабировать. Если SEO и первый показ не важны, SPA проще.

---

## Красные флаги в ответе

- **«Next.js нужен для любого React-приложения».** Для внутреннего инструмента без SEO SPA на Vite проще.
- **«Статическая или динамическая страница — настройка, которую выбирают вручную».** Next.js выводит режим из того, что страница читает из запроса.
- **«Весь код компонента попадёт в браузер».** Серверные компоненты остаются на сервере, в бандл уходят только клиентские.
- **«Astro — генератор статических сайтов без интерактивности».** Интерактивность приходит островами там, где она нужна.
- **«Remix и React Router — разные проекты».** Прежний Remix продолжился как React Router в режиме фреймворка, а Remix 3 — новый фреймворк.

## Как спрашивают на собеседовании

::question
Зачем нужен мета-фреймворк?

#answer
UI-библиотека рисует интерфейс, а приложению нужны ещё маршрутизация, рендеринг на сервере и при сборке, загрузка данных, серверный код, разделение кода, мета-теги и выкладка. Мета-фреймворк даёт это единым набором с соглашениями вместо десятка отдельно собранных библиотек.

#more
Главная ценность — рендеринг и данные на сервере: HTML с первым ответом для SEO и быстрого показа, загрузка данных без водопадов на клиенте, разный режим для разных маршрутов. Цена — сервер, который нужно эксплуатировать, и более сложная модель для команды.
::

::question
Как Next.js решает, собирать страницу заранее или рендерить на каждый запрос?

#answer
По тому, от чего страница зависит. Если она не читает ничего из запроса — cookies, заголовки, параметры поиска, — её можно собрать при сборке, и в выводе сборки она отмечена как статическая. Если читает — рендерится на каждый запрос и отмечена как динамическая.

#more
В Next.js 16 кеширование явное: `'use cache'` помечает кешируемые страницы, компоненты и функции, а Cache Components позволяют совмещать статичную оболочку и динамические части со стримингом. Динамическая функция в общем макете делает динамическими все страницы под ним.
::

::question
Чем Next.js отличается от Astro?

#answer
Next.js — фреймворк для приложений на React: серверные компоненты, клиентские компоненты, серверные функции и кеширование. Astro — фреймворк для контентных сайтов: по умолчанию HTML без JavaScript, а интерактивность приходит островами с директивами `client:*`.

#more
Astro поддерживает компоненты разных UI-библиотек на одной странице и серверные острова, Next.js — только React, зато с полной моделью приложения. Для блога и документации Astro даёт минимум JavaScript, для приложения с большим количеством интерактива — Next.js или аналоги.
::

::question
Что такое острова?

#answer
Подход, при котором страница — статичный HTML, а интерактивные компоненты оживают отдельно, каждый со своим кодом. В Astro компонент без директивы остаётся только HTML, а с `client:visible` загружается, когда попадает в зону видимости.

#more
Это уменьшает JavaScript и стоимость гидратации: React загружается только ради острова, а не ради всей страницы. Похожие идеи — серверные острова в Astro, серверные компоненты Nuxt, ленивая гидратация во Vue, частичная гидратация в других фреймворках.
::

::question
Как выбрать мета-фреймворк?

#answer
По типу продукта и UI-библиотеке. Контентный сайт — Astro. Приложение на React — Next.js, React Router в режиме фреймворка или TanStack Start. На Vue — Nuxt, на Svelte — SvelteKit. Внутренний инструмент без SEO — SPA на Vite.

#more
Дальше — где будет работать приложение и как сильно оно будет привязано к платформе, насколько команда готова к серверным компонентам и кешу, как часто фреймворк меняет соглашения между мажорными версиями.
::

::question
Когда мета-фреймворк не нужен?

#answer
Когда не нужны SEO и быстрый первый показ: админки, внутренние инструменты, кабинеты за авторизацией. SPA на Vite проще: статика на CDN, нет сервера, гидратации и границы клиент-сервер.

#more
Если позже понадобится SEO для части страниц, их выносят в отдельный сайт на Astro или переносят приложение на фреймворк. Многие продукты так и устроены: маркетинговые страницы на Astro, само приложение — SPA.
::

## Практика

::practice{title="Каталог рендерится на каждый запрос"}
В Next.js каталог товаров одинаков для всех пользователей, но сборка отмечает его как динамический, и каждая загрузка нагружает сервер. В корневом макете есть:

```jsx
// app/layout.jsx
import { cookies } from 'next/headers';
export default async function Layout({ children }) {
  const theme = (await cookies()).get('theme')?.value ?? 'light';
  return <html data-theme={theme}><body>{children}</body></html>;
}
```

#solution
Макет читает cookies, и все страницы под ним стали зависеть от запроса — в том числе каталог. Фреймворк больше не может собрать их заранее. Чтение запроса переносят туда, где оно нужно:

```jsx
// app/layout.jsx — без обращения к запросу
export default function Layout({ children }) {
  return <html><body>{children}</body></html>;
}
```

```jsx
// app/theme-switcher.jsx
'use client';
// тема читается в браузере — из cookie или localStorage, — и применяется к html после загрузки
```

Тогда каталог снова статический, а тема применяется на клиенте; чтобы не мигала, её ставят маленьким встроенным скриптом до отрисовки. В Next.js 16 с Cache Components зависящую от запроса часть можно отрендерить отдельно внутри `Suspense`, оставив статичной остальную страницу. В проверке страница без чтения запроса собралась как статическая, а страница с `cookies()` — как динамическая.
::

::practice{title="Блог грузит React на каждой статье"}
Блог компании сделан на Next.js: статьи статичные, интерактивна только кнопка «Поделиться». Lighthouse показывает сотни килобайт JavaScript на каждой странице.

#solution
Для контентного сайта основная работа JavaScript — оживить страницу, которой почти не нужна интерактивность. Два пути:

```astro
---
// Astro: статья — HTML, кнопка — остров
import Share from '../components/Share.jsx';
---
<article><slot /></article>
<Share client:visible />
```

```jsx
// Next.js: статья — серверный компонент, кнопка — единственный клиентский
export default function Article({ post }) {
  return <article>{post.html}<Share /></article>;   // Share — с 'use client'
}
```

В Astro React загрузится только ради кнопки и только когда она появится на экране. В Next.js серверные компоненты не уходят в браузер, но рантайм React и гидратация всё равно нужны. Для блога и документации Astro обычно выигрывает. В проверке страница Astro без острова не содержала JavaScript вовсе, а с `client:visible` — только код острова.
::
