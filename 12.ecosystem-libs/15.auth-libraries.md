# Библиотеки авторизации

Какие продукты берут для входа пользователей: библиотеки, которые работают на вашем сервере и в вашей базе, — Better Auth, Auth.js, Passport, — и сервисы вроде Clerk, Auth0, Supabase Auth и Firebase Auth. Плюс то, что остаётся фронтенду при любом выборе. Спрашивают, почему авторизацию не пишут с нуля, чем библиотека отличается от сервиса и защищает ли что-то проверка маршрута на клиенте. Глубже — почему `jwt-decode` ничего не проверяет, зачем SPA нужен PKCE и почему параллельные запросы выкидывают пользователя из системы при обновлении токена.

::tldr
- **Авторизацию не пишут с нуля:** хеширование паролей, сессии, OAuth, сброс пароля, защита от перебора и подделки — много мест для ошибки, цена которой — чужие аккаунты.
- **Библиотека или сервис:** библиотека работает на вашем сервере и хранит пользователей в вашей базе, сервис хранит их у себя, даёт готовые экраны и берёт плату за активных пользователей.
- **Декодировать токен — не значит проверить:** `jwt-decode` читает любой токен, в том числе поддельный. Подпись проверяет сервер, например через `jose`.
- **Проверка маршрута на клиенте — удобство, а не защита.** Права на каждую операцию проверяет сервер.
- **На фронтенде остаются:** где живёт сессия, OAuth с PKCE, обновление токена одним запросом на все параллельные 401 и состояние «вошёл или нет» в интерфейсе.
::

---

## Почему не писать самому

Сквозной пример — магазин: вход по почте и паролю, «Войти через Google», личный кабинет и админка для сотрудников.

Минимальный список того, что нужно сделать правильно:

- хранить пароль медленным хешем с солью — scrypt, argon2, bcrypt, — а не открытым текстом и не быстрым SHA;
- выдавать сессию в cookie с `HttpOnly`, `Secure`, `SameSite`, уметь её отозвать;
- провести :term[OAuth]{def="протокол, которым приложение получает доступ к данным пользователя в другом сервисе без его пароля"} и :term[OpenID Connect]{def="протокол входа поверх OAuth: сервис подтверждает, кто пользователь"} с проверкой `state`, :term[PKCE]{def="защита OAuth для публичных клиентов: одноразовый секрет доказывает, что код обменивает тот же клиент"} и подписи `id_token`;
- подтверждение почты, сброс пароля одноразовыми ссылками, ограничение попыток входа;
- двухфакторный вход, passkeys, привязка нескольких способов входа к одному аккаунту.

Как устроены сессии, JWT, OAuth и хранение токенов — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens) и [Авторизации в сети](/content/network-api/auth). Здесь — продукты, которые это реализуют.

## Библиотека или сервис

| | Библиотека | Сервис |
| --- | --- | --- |
| Где пользователи | ваша база | у провайдера |
| Экраны входа | свои или из примеров | готовые компоненты |
| Цена | своя инфраструктура | подписка, часто по активным пользователям |
| Контроль и перенос | полный | ограничен платформой, переезд сложен |
| Примеры | Better Auth, Auth.js, Passport | Clerk, Auth0, WorkOS, Supabase Auth, Firebase Auth |

Сервис запускает вход за день и снимает заботы об инфраструктуре, но пользователи и их хеши паролей живут у провайдера, и переезд — отдельный проект. Библиотека бесплатна и хранит всё у вас, но базу, почту и обновления безопасности ведёте вы.

## Библиотеки

### Better Auth

Библиотека на TypeScript для любого фреймворка: вход по паролю, OAuth-провайдеры, двухфакторный вход, passkeys, организации — через плагины, а хранилище — адаптеры к Postgres, MySQL, SQLite, :term[Prisma]{def="ORM для TypeScript со схемой и сгенерированным клиентом"}, :term[Drizzle]{def="лёгкий ORM для TypeScript, близкий к SQL"}.

В проверке после регистрации Better Auth выдал cookie:

```text
__Secure-better-auth.session_token=…; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax
```

Пароль в базе лежал хешем — открытого текста в хранилище не было. Подделанная cookie не дала сессии, а после выхода сессия удалилась на сервере, и старая cookie перестала работать. Это и есть преимущество сессии в базе перед долгоживущим JWT: её можно отозвать.

### Auth.js

**Auth.js**, бывший NextAuth.js, — библиотека с десятками OAuth-провайдеров, сессиями в базе или в зашифрованном JWT и адаптерами к базам, для Next.js, SvelteKit, Express. С осени 2025 её поддерживает команда Better Auth и рекомендует Better Auth для новых проектов.

### Passport и Lucia

**Passport** — библиотека для Node.js-бэкенда на Express: «стратегии» для каждого способа входа. Зрелая, но сессии, базу и всё остальное собирают вокруг неё сами.

**Lucia** была лёгкой библиотекой сессий, но в марте 2025 автор прекратил её как пакет и превратил в учебник о том, как реализовать сессии и OAuth самому. Её материалы полезны, чтобы понимать, что делают библиотеки внутри.

| Событие | Когда |
| --- | --- |
| Lucia прекращена как библиотека, стала учебником | март 2025 |
| Auth.js перешла под поддержку команды Better Auth | осень 2025 |

Актуально на ноябрь 2026.

## Сервисы

- **Clerk** — готовые компоненты входа и профиля, организации, двухфакторный вход; тесная интеграция с Next.js.
- **Auth0** — корпоративная платформа идентификации: единый вход, правила, соответствие требованиям.
- **WorkOS** — единый вход через SAML и синхронизация пользователей по SCIM, когда продукт продают крупным компаниям.
- **Supabase Auth**, **Firebase Auth**, **Appwrite** — вход как часть BaaS — «бэкенда как сервиса» с базой, хранилищем и реалтаймом. Удобно для MVP и команд без своего бэкенда.
- **Keycloak**, **Zitadel**, **Ory** — свои серверы идентификации с открытым кодом: как сервис по возможностям, но развёрнуты у вас.

## Что остаётся фронтенду

### Декодировать — не значит проверить

JWT — три части в base64url: заголовок, данные и подпись (подробно — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens)). Прочитать данные может кто угодно:

```js
import { jwtDecode } from 'jwt-decode';

jwtDecode(token).role;   // 'admin'
```

В проверке токен с подменённой ролью `admin` и чужой подписью `jwt-decode` прочитал без возражений, как и токен с `alg: "none"` без подписи. `jose` оба отверг:

```js
import { jwtVerify } from 'jose';

await jwtVerify(forged, secret);   // ERR_JWS_SIGNATURE_VERIFICATION_FAILED
```

Поэтому на клиенте декодирование годится только для интерфейса — показать имя или скрыть кнопку, — а решения принимает сервер, проверяя подпись, срок (`ERR_JWT_EXPIRED` для истёкшего), издателя и аудиторию. Токены от провайдера проверяют его открытыми ключами из JWKS: в проверке `id_token` с чужой аудиторией `jose` отклонил.

### OAuth в SPA: PKCE

SPA не может хранить секрет клиента — код открыт. Поэтому вход через провайдера идёт по Authorization Code с **PKCE**: приложение создаёт случайный `code_verifier`, отправляет провайдеру `code_challenge` — его хеш SHA-256 в base64url, — а при обмене кода на токен показывает исходный `code_verifier`. Перехваченный код без него бесполезен.

```js
import * as oauth from 'oauth4webapi';

const verifier = oauth.generateRandomCodeVerifier();
const challenge = await oauth.calculatePKCECodeChallenge(verifier);
```

В проверке `challenge` совпал с `sha256(verifier)` в base64url, посчитанным вручную. Сам поток — в [Авторизации в сети](/content/network-api/auth). Библиотеки — `oauth4webapi`, `oidc-client-ts`, клиенты Auth0 и Clerk — делают это сами, а часто вход проводит сервер, оставляя браузеру только cookie.

### Обновление токена

При схеме с коротким access-токеном и refresh-токеном с ротацией есть ловушка. Страница отправляет три запроса, все получают 401, и каждый сам запускает обновление. Первое обновление выдаёт новую пару и отзывает старый refresh-токен, второе приходит со старым — сервер видит повторное использование и отзывает всю цепочку. Пользователь вылетает из системы.

В проверке наивный клиент сделал три обновления, и сервер выкинул пользователя. Исправление — одно обновление на всех:

```js
let pending = null;

async function request(url) {
  let res = await fetch(url, withToken());
  if (res.status !== 401) return res;

  pending ??= refreshTokens().finally(() => { pending = null; });
  await pending;

  return fetch(url, withToken());
}
```

Все три запроса дождались одного обновления и прошли. В HTTP-клиентах это делают в перехватчике — `onResponseError` в ofetch, `afterResponse` в ky, interceptor в axios.

### Защита маршрутов

Гард маршрута на клиенте прячет страницу админки и перенаправляет на вход, но код страницы и запросы доступны любому. Это удобство, а не защита: каждую операцию сервер проверяет сам. В мета-фреймворках проверку сессии делают на сервере — в middleware, загрузчике данных или серверном компоненте, — чтобы закрытая страница вообще не рендерилась.

| Ситуация | Выбор |
| --- | --- |
| свой бэкенд на TypeScript, пользователи в своей базе | Better Auth |
| существующий проект на Auth.js | оставить, новые — на Better Auth |
| быстро и с готовыми экранами | Clerk, Auth0 |
| продажи крупным компаниям: SAML, SCIM | WorkOS, Auth0 |
| MVP без своего бэкенда | Supabase Auth, Firebase Auth |

## Красные флаги в ответе

- **«Напишу авторизацию сам за вечер».** Хеширование, сессии, OAuth, сброс пароля и защита от перебора — много мест для ошибки.
- **«Проверю роль из токена через `jwt-decode`».** Он не проверяет подпись, поддельный токен читается так же.
- **«Гард маршрута защищает админку».** Он прячет интерфейс, права проверяет сервер.
- **«Токен положу в `localStorage`».** Его прочитает любой скрипт при XSS, предпочтительна cookie с `HttpOnly`.
- **«При 401 каждый запрос обновит токен сам».** С ротацией параллельные обновления отзывают сессию.
- **«Сервис бесплатен».** Обычно платят за активных пользователей, а переезд с пользователями сложен.

## Как спрашивают на собеседовании

::question
Почему авторизацию не пишут с нуля?

#answer
Цена ошибки — чужие аккаунты, а мест для неё много: хеширование паролей, сессии и их отзыв, OAuth с проверкой `state`, PKCE и подписи, сброс пароля, защита от перебора, двухфакторный вход. Берут проверенную библиотеку или сервис.

#more
Свою реализацию оправдывает понимание и особые требования — для этого есть учебные материалы Lucia. Но даже тогда криптографию и хеширование берут из готовых пакетов.
::

::question
Чем библиотека вроде Better Auth отличается от сервиса вроде Clerk?

#answer
Библиотека работает на вашем сервере и хранит пользователей в вашей базе: полный контроль, нет платы за пользователей, но инфраструктура и обновления — ваши. Сервис хранит пользователей у себя, даёт готовые экраны и управление, но берёт плату по активным пользователям и привязывает к себе.

#more
Между ними — серверы идентификации с открытым кодом вроде Keycloak и Zitadel: возможности сервиса, но развёрнуты у вас. Auth.js с осени 2025 поддерживает команда Better Auth.
::

::question
Можно ли доверять данным из JWT на клиенте?

#answer
Только для интерфейса. `jwt-decode` и `atob` читают любой токен, в том числе с подменёнными данными и чужой подписью. Решения о доступе принимает сервер, проверяя подпись, срок, издателя и аудиторию.

#more
Проверяют библиотеками вроде `jose`: `jwtVerify` отклоняет неверную подпись, `alg: "none"` и истёкший токен. Токены провайдера проверяют его открытыми ключами из JWKS.
::

::question
Защита маршрутов на клиенте — это безопасность?

#answer
Нет, удобство: гард прячет страницу и перенаправляет на вход, но код страницы и API доступны напрямую. Каждую операцию авторизует сервер.

#more
В мета-фреймворках сессию проверяют на сервере — в middleware, загрузчике или серверном компоненте, — тогда закрытая страница не рендерится вовсе. Данные для неё всё равно защищает проверка в самом API.
::

::question
Зачем SPA нужен PKCE?

#answer
SPA не может хранить секрет клиента. PKCE заменяет его одноразовым `code_verifier`: провайдер получает его хеш при начале входа, а при обмене кода на токен приложение показывает сам `code_verifier`. Перехваченный код без него бесполезен.

#more
`code_challenge` — SHA-256 от `code_verifier` в base64url. Библиотеки `oauth4webapi` и `oidc-client-ts` делают это сами. Часто обмен кода проводит сервер, и браузер получает только cookie сессии.
::

::question
Что такое BaaS и когда он уместен?

#answer
Backend-as-a-Service — Supabase, Firebase, Appwrite: вход, база, хранилище и реалтайм без своего бэкенда. Уместен для MVP и небольших команд.

#more
Права доступа в BaaS задают правилами на стороне сервиса — row level security в Supabase, security rules в Firebase. Без них данные доступны любому клиенту с публичным ключом.
::

## Практика

::practice{title="Админка открывается подменой токена"}
Админка проверяет роль на клиенте:

```js
const { role } = jwtDecode(localStorage.getItem('token'));
if (role === 'admin') showAdmin();
```

API отдаёт заказы всем, у кого есть любой токен. Тестировщик вручную собрал токен с `role: "admin"` и получил доступ.

#solution
Три ошибки: `jwt-decode` не проверяет подпись, решение принимается на клиенте, а API не проверяет права. В проверке токен с подменённой ролью и чужой подписью `jwt-decode` прочитал как настоящий, а `jose` отверг:

```js
// на сервере, в каждом защищённом обработчике
const { payload } = await jwtVerify(token, key, { issuer, audience });
if (payload.role !== 'admin') return forbidden();
```

На клиенте роль из токена можно использовать только чтобы спрятать кнопки. Токен лучше хранить в cookie с `HttpOnly` — тогда его не прочитает и скрипт при XSS.
::

::practice{title="Пользователей выкидывает из системы"}
После перехода на короткие access-токены с ротацией refresh-токенов пользователи жалуются, что их иногда выкидывает из системы — чаще на страницах с несколькими виджетами.

#solution
Каждый виджет получает 401 и сам обновляет токен. Второе обновление идёт со старым refresh-токеном, сервер считает это кражей и отзывает сессию. В проверке три параллельных запроса дали три обновления и выход из системы. Нужно одно общее обновление:

```js
let pending = null;

async function withRefresh(doRequest) {
  const res = await doRequest();
  if (res.status !== 401) return res;
  pending ??= refreshTokens().finally(() => { pending = null; });
  await pending;
  return doRequest();
}
```

После исправления в проверке было одно обновление, и все три запроса прошли. Если access-токен не нужен в JavaScript, проще держать сессию в cookie с `HttpOnly`, как делают Better Auth и Auth.js.
::
