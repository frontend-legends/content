# За рамками: создавать и патчить

Последний шаг главы — перестать быть только потребителем библиотек: читать их код, чинить чужой пакет патчем или форком, выпускать свою библиотеку и строить её как ядро с адаптерами. Спрашивают, что делать с багом в зависимости, когда фикса нет, что важно в `package.json` публикуемой библиотеки и как одна библиотека работает и в React, и во Vue. Глубже — почему патч ломает установку после обновления, почему `types` в `exports` идёт первым и что попадёт в пакет без поля `files`.

::tldr
- **Библиотека — такой же JavaScript, как ваш код:** её исходник лежит в `node_modules`, и при странном поведении его читают и ставят в нём точки останова.
- **Баг в зависимости чинят патчем:** `pnpm patch` или patch-package сохраняют разницу в репозиторий и применяют её при каждой установке. Патч привязан к версии и после обновления требует внимания. Параллельно — исправление в исходный репозиторий.
- **Своя библиотека — это `package.json`:** `exports` с `types` первым, фреймворк в `peerDependencies`, `files` со списком того, что публикуется, `sideEffects` для tree shaking. Проверяют publint и `npm pack --dry-run`.
- **Собирают tsdown, Rolldown или Vite в режиме библиотеки:** ESM, объявления типов, фреймворк — внешний импорт.
- **Ядро без фреймворка и тонкие адаптеры** — так устроены TanStack и Zag: логика одна, а хук или composable — небольшая обёртка.
::

## Это всё JavaScript

React, Vue и любая библиотека из этой главы — модули в `node_modules`, которые выполняет тот же движок, что и ваш код. Границы между «моим кодом» и «библиотекой» для рантайма нет.

Отсюда практический навык. Когда библиотека ведёт себя странно:

- перейти к определению функции в редакторе — часто попадаешь в `.d.ts`, а рядом лежит настоящий код в `dist`;
- открыть файл из стека ошибки и поставить точку останова прямо в библиотеке — source maps пакета показывают исходник;
- прочитать код в репозитории на нужном теге версии, а не в ветке `main`;
- найти issue: часто баг уже известен, и в обсуждении есть обходной путь.

Сквозной пример — магазин и библиотека `ms`, которая превращает `'1.5h'` в миллисекунды. Пользователи вводят время с запятой — `'1,5h'`, — а библиотека возвращает `undefined`. Ждать новую версию некогда.

## Патч зависимости

### pnpm patch

```bash
pnpm patch ms@2.1.3              # копия пакета во временной папке
# правим index.js в этой папке
pnpm patch-commit <папка>        # сохранить разницу
```

В проверке после `patch-commit` появились:

- `patches/ms@2.1.3.patch` — обычный diff, который читается на ревью;
- запись `patchedDependencies` с путём к патчу в `pnpm-workspace.yaml` и хеш патча в `pnpm-lock.yaml`.

После удаления `node_modules` чистая установка с `--frozen-lockfile` применила патч сама: `ms('1,5h')` вернул `5400000`.

### patch-package

Для npm и Yarn — **patch-package**: правят файл прямо в `node_modules`, сохраняют патч и применяют его в `postinstall`:

```bash
# правим node_modules/ms/index.js
npx patch-package ms             # создаст patches/ms+2.1.3.patch
```

```json
{ "scripts": { "postinstall": "patch-package" } }
```

В проверке `npm ci` после удаления `node_modules` применил патч через `postinstall`. Yarn Berry и Bun тоже умеют патчить сами: `yarn patch` и `bun patch`.

| Где хранится ссылка на патч в pnpm | Версия |
| --- | --- |
| `pnpm.patchedDependencies` в `package.json` | pnpm 7–9 |
| `patchedDependencies` в `pnpm-workspace.yaml` | pnpm 11, проверено |

Актуально на ноябрь 2026.

### Патч — временная мера

Патч привязан к версии. В проверке после обновления `ms` до другой версии `pnpm install` упал с `ERR_PNPM_UNUSED_PATCH`: патч к `ms@2.1.3` больше не к чему применять. Это полезно — забытый патч не потеряется молча, — но значит, что при каждом обновлении патч нужно проверить, перенести или удалить.

Поэтому вместе с патчем:

- отправляют issue и исправление в исходный репозиторий;
- пишут в патче или рядом ссылку на issue, чтобы знать, когда его убрать;
- держат патч минимальным — одну правку, а не переписанный модуль.

### Форк

Для большой правки или заброшенного проекта — **форк**, указанный как зависимость:

```json
{ "dependencies": { "ms": "github:shop/ms#comma-decimal" } }
```

При установке из git npm запускает скрипт `prepare` пакета, поэтому форк должен уметь собраться сам или хранить собранный `dist`. Для постоянного использования форк публикуют под своим именем в реестр компании. Подмену зависимости в зависимостях — `overrides` в npm, `pnpm.overrides`, `resolutions` в Yarn — разбирает [Управление пакетами](/content/ecosystem-libs/package-management).

## Своя библиотека

Когда один и тот же код — UI-кит, форматирование цен, хуки — нужен в нескольких проектах, его выносят в пакет. В монорепозитории это внутренний пакет (подробно — в [Монорепозиториях](/content/advanced-tooling/monorepo-tooling)), между командами и вовне — публикуемый.

### package.json библиотеки

Пакет `@shop/price` с функцией `formatPrice` и хуком `usePrice`:

```json
{
  "name": "@shop/price",
  "version": "1.0.0",
  "type": "module",
  "exports": {
    ".": {
      "types": "./dist/index.d.mts",
      "import": "./dist/index.mjs"
    }
  },
  "files": ["dist"],
  "sideEffects": false,
  "peerDependencies": { "react": ">=18" }
}
```

- **`exports`** — публичные точки входа; что не перечислено, импортировать нельзя (подробно — в [Модульных системах](/content/advanced-tooling/module-systems)). Условия проверяются по порядку, и **`types` ставят первым**, иначе TypeScript может выбрать JavaScript-файл и остаться без типов.
- **`peerDependencies`** — фреймворк даёт приложение, а не библиотека: иначе две копии React со сломанными хуками (подробно — в [Управлении пакетами](/content/ecosystem-libs/package-management)).
- **`files`** — что попадёт в пакет. Без него публикуется почти всё, что не исключено `.gitignore` или `.npmignore`.
- **`sideEffects: false`** — разрешение бандлеру выбросить неиспользуемые модули (подробно — в [Оптимизации](/content/advanced-tooling/optimization)).

### Сборка

Библиотеку не минифицируют и не вклеивают в неё зависимости — это задача приложения (подробно — в [Бандлерах](/content/advanced-tooling/bundlers)). Инструменты:

- **tsdown** — сборщик библиотек на Rolldown: ESM, CommonJS при необходимости, объявления типов; для переезда с tsup есть `tsdown-migrate`;
- **tsup** на esbuild — предшественник, ещё во многих проектах;
- **Vite в режиме библиотеки** — когда в пакете компоненты Vue или React со стилями;
- **unbuild**, **Rollup** — альтернативы.

В проверке `tsdown src/index.ts --format esm --dts` собрал `dist/index.mjs` и `dist/index.d.mts`. В собранном файле осталось `import { useMemo } from "react"` — React не вклеен, и весь файл меньше килобайта.

### Проверить пакет перед публикацией

Первая версия `package.json` в проверке выглядела так, как её часто пишут:

```json
"exports": { ".": { "import": "./dist/index.js", "types": "./dist/index.d.ts" } }
```

**publint** нашёл три ошибки и подсказку:

```text
error       EXPORTS_TYPES_SHOULD_BE_FIRST   types стоит после import
error       FILE_DOES_NOT_EXIST             ./dist/index.js — сборщик написал index.mjs
error       FILE_DOES_NOT_EXIST             ./dist/index.d.ts — на деле index.d.mts
suggestion  USE_FILES                       в пакет попадёт src/index.test.ts
```

`npm pack --dry-run` показывает список файлов пакета: без `files` в нём были исходники, тесты и `tsconfig.json`. После исправления publint не нашёл ничего, а в пакете остались `README.md`, `package.json` и два файла `dist`. Проверку типов с точки зрения потребителя добавляет **Are the Types Wrong** (`attw`): как пакет видят разные режимы `moduleResolution`.

### Публикация

```bash
npm version minor               # поднять версию по semver
npm publish --access public     # пакеты со scope по умолчанию приватные
```

- Версия — по [semver](/content/ecosystem-libs/package-management): ломающее изменение — major.
- В монорепозитории версии и changelog ведёт **Changesets** (подробно — в [Монорепозиториях](/content/advanced-tooling/monorepo-tooling)).
- Публикуют из :term[CI]{def="непрерывная интеграция: сервер, который собирает и тестирует код на каждое изменение"} с подтверждением происхождения (`--provenance`) и без долгоживущих токенов — через trusted publishing; аккаунт — с двухфакторной аутентификацией (подробно — в [Цепочке поставок](/content/security-perfomance/supply-chain-and-vulnerabilities)).

## Ядро и адаптеры

Современные библиотеки пишут логику на чистом TypeScript, а под каждый фреймворк делают тонкий адаптер:

```text
            @tanstack/query-core       ← кеш, запросы, повторы, инвалидация
          ┌──────────┼──────────┬──────────┐
    react-query   vue-query   solid-query   svelte-query   ← хук или composable
```

В проверке `@tanstack/react-query` и `@tanstack/vue-query` зависели от одного и того же `@tanstack/query-core`, а у самого ядра не было зависимостей — ни React, ни Vue. Ядро весило около 8,8 KB :term[gzip]{def="алгоритм сжатия, которым сервер обычно отдаёт текстовые файлы"}, а React-адаптер с `useQuery` и `QueryClientProvider` поверх него — около 1 KB.

Адаптер делает одно: подписывает компонент на изменения ядра средствами фреймворка — `useSyncExternalStore` в React, `shallowRef` и `watch` во Vue — и отписывает при размонтировании. Так устроены TanStack Query, Table, Virtual и Form, Zag.js и Ark UI с логикой компонентов как машин состояний, XState с `@xstate/react` и `@xstate/vue`.

Отсюда и переносимость знаний: кеш серверных данных, виртуализация, формы, машины состояний в React и Vue — одни и те же идеи, часто один и тот же код ядра. Меняется обёртка.

## Красные флаги в ответе

- **«Библиотека — чёрный ящик, внутрь не смотрю».** Её код в `node_modules`, и его можно читать и отлаживать.
- **«Поправлю файл в `node_modules`».** Правка исчезнет при следующей установке — нужен патч в репозитории.
- **«Патч навсегда».** Он привязан к версии, при обновлении его проверяют, а исправление отправляют в исходный репозиторий.
- **«React в `dependencies` библиотеки».** У приложения окажутся две копии — фреймворк идёт в `peerDependencies`.
- **«`types` в `exports` можно в любом месте».** Условия проверяются по порядку, `types` ставят первым.
- **«Публикую без `files`».** В пакет попадут исходники, тесты и конфиги.

## Как спрашивают на собеседовании

::question
Что делать, если в библиотеке баг, а исправления нет?

#answer
Проверить issue — может, есть обходной путь или готовый фикс в новой версии. Если нет — патч: `pnpm patch` или patch-package сохраняют разницу в репозиторий и применяют её при каждой установке. Параллельно — issue и исправление в исходный репозиторий.

#more
Патч привязан к версии: pnpm при обновлении пакета падает с `ERR_PNPM_UNUSED_PATCH`, и патч нужно перенести или удалить. Для крупных правок или заброшенного проекта — форк, установленный из git или опубликованный под своим именем.
::

::question
Что важно в `package.json` публикуемой библиотеки?

#answer
`exports` с точками входа и `types` первым условием, фреймворк в `peerDependencies`, `files` со списком публикуемого, `sideEffects` для tree shaking, `type: "module"` и версия по semver.

#more
Перед публикацией пакет проверяют publint, `attw` и `npm pack --dry-run`: частые ошибки — пути в `exports`, не совпадающие с тем, что написал сборщик, `types` после `import` и тесты в пакете без `files`. Публикуют из CI с provenance.
::

::question
Зачем `peerDependencies` в библиотеке?

#answer
Чтобы библиотека использовала фреймворк приложения, а не ставила свою копию. Две копии React ломают хуки и контекст, две копии Vue — `provide` и `inject`.

#more
При сборке такие пакеты делают внешними — они остаются импортом, а не вклеиваются. Менеджер пакетов проверяет совместимость версий и при конфликте даёт `ERESOLVE` в npm.
::

::question
Как одна библиотека работает и в React, и во Vue?

#answer
Логика живёт в ядре на чистом TypeScript без зависимостей от фреймворков, а под каждый фреймворк есть тонкий адаптер — хук или composable, — который подписывает компонент на изменения ядра.

#more
Так устроены TanStack Query, Table и Virtual, Zag.js и Ark UI, XState. У TanStack Query ядро весит около 8,8 KB gzip, а React-адаптер — около 1 KB: почти вся работа в общем коде.
::

::question
Почему знание React помогает быстро освоить Vue?

#answer
Большинство задач — состояние, загрузка и кеширование данных, формы, маршрутизация, виртуализация — решаются одинаковыми идеями, а нередко и одним кодом ядра с разными адаптерами. Меняются синтаксис и модель реактивности, а не суть.

#more
Главное отличие — как фреймворк узнаёт об изменениях: React перезапускает компонент, Vue отслеживает чтение реактивных значений. Поняв это, остальное переносится почти напрямую.
::

## Практика

::practice{title="Правка исчезла после установки"}
Разработчик исправил баг в `node_modules/ms/index.js` — время с запятой `'1,5h'` стало разбираться. Через день у коллеги и в CI баг вернулся.

#solution
`node_modules` пересоздаётся при каждой установке, правка в нём живёт только на одной машине. Её сохраняют патчем:

```bash
pnpm patch ms@2.1.3 --edit-dir .edit-ms
# правка в .edit-ms/index.js
pnpm patch-commit .edit-ms
```

```diff
 function parse(str) {
+  str = String(str).replace(",", ".");
   str = String(str);
```

В проверке патч лёг в `patches/ms@2.1.3.patch`, а чистая установка с `--frozen-lockfile` применила его сама. Для npm — patch-package с `postinstall`. И issue в репозиторий `ms`, чтобы патч однажды удалить.
::

::practice{title="Пакет без типов"}
Библиотека `@shop/price` опубликована, но в приложениях TypeScript пишет, что у неё нет типов, а Vite не находит `./dist/index.js`. В пакете зачем-то лежат тесты.

```json
"exports": { ".": { "import": "./dist/index.js", "types": "./dist/index.d.ts" } }
```

#solution
publint в проверке нашёл всё сразу: `types` после `import`, файлов `index.js` и `index.d.ts` нет — tsdown написал `index.mjs` и `index.d.mts`, — и нет `files`. Исправление:

```json
{
  "exports": { ".": { "types": "./dist/index.d.mts", "import": "./dist/index.mjs" } },
  "files": ["dist"],
  "sideEffects": false
}
```

После этого publint не нашёл ошибок, а `npm pack --dry-run` показал только `README.md`, `package.json` и `dist`. Эти проверки ставят в CI перед `npm publish`.
::
