# За рамками: создавать и патчить

Финал главы - и важный сдвиг в мышлении. Всё, что мы перечислили, - чужие библиотеки. Но ты не обязан быть только **потребителем**. Любую из них можно прочитать, починить и форкнуть, а свою - написать и опубликовать. Потому что **в конце концов это всё JavaScript**.

---

## Это всё JavaScript

React, Vue, Svelte, любая библиотека из этой главы - в итоге **обычный JS, выполняющийся в том же рантайме**, что и твой код. Никакой магии: фреймворк - это код, который кто-то написал, и ты можешь его открыть.

```
твой код  ─┐
React      ├─►  всё это - JavaScript-модули в node_modules,
Vue        │    исполняемые одним движком (V8 и т.п.)
любая lib ─┘
```

<b class="text-on-semi-light">Практический вывод</b> - <span class="text-gray">`node_modules` - не чёрный ящик, а читаемый код. Когда библиотека ведёт себя странно, **зайди в её исходник** (по стеку ошибки, через «go to definition», точкой останова в дебаггере). Понимание, что границы между «моим кодом» и «библиотекой» нет, - то, что отличает инженера от пользователя фреймворка.</span>

---

## Патчинг чужих зависимостей

Нашёл баг в библиотеке - не обязательно ждать, пока его починят в апстриме (это могут быть месяцы). Можно **пропатчить локально**.

### patch-package / pnpm patch

```bash
# pnpm: открыть пакет на редактирование
pnpm patch some-lib
# (правишь файлы во временной папке)
pnpm patch-commit <path>   # сохраняет патч в проект

# npm/yarn: правишь в node_modules и фиксируешь
npx patch-package some-lib
```

Патч сохраняется в репозиторий и **применяется автоматически** при каждой установке (через `postinstall`). Команда получает фикс, не дожидаясь релиза.

<b class="text-on-semi-light">Когда патчить</b> - <span class="text-gray">Срочный баг или нужное мелкое изменение, а апстрим молчит. Патч - временная мера: его держат до выхода официального фикса, иначе он «протухнет» при обновлении версии. Всегда параллельно стоит послать PR в апстрим.</span>

### Форк

Для серьёзных изменений - **форкнуть** репозиторий и указать форк как зависимость:

```jsonc
"dependencies": {
  "some-lib": "github:my-org/some-lib#fix-branch"
}
```

### Контрибьютить обратно

Лучшее, что можно сделать с найденным багом, - **починить в апстриме** через Pull Request. Это убирает патч, помогает всем и прокачивает тебя. Open source держится на этом.

## Своя библиотека

Когда один и тот же код (UI-кит, утилиты, хуки) нужен в нескольких проектах или командах - его **выносят в библиотеку**.

### package.json библиотеки

```jsonc
{
  "name": "@my-org/ui",
  "version": "1.0.0",
  "type": "module",
  "exports": { ".": { "types": "./dist/index.d.ts", "import": "./dist/index.js" } },
  "files": ["dist"],                 // что попадёт в npm-пакет
  "sideEffects": false,              // разрешить tree-shaking
  "peerDependencies": { "react": ">=18" } // не тащить свой React
}
```

Ключевое: **`exports`** (точки входа + типы), **`peerDependencies`** (React/Vue предоставляет приложение - иначе две копии), **`sideEffects: false`** (для tree-shaking), публикация и ESM, и типов (`.d.ts`).

### Сборка

Библиотеку собирают специальными сборщиками:

- **tsup** - простой сборщик на esbuild: ESM + CJS + типы одной командой.
- **Vite (library mode)** / **unbuild** - альтернативы.

### Публикация

```bash
npm version minor   # поднять версию по semver
npm publish --access public   # опубликовать (scoped → нужен --access)
```

- Соблюдай **semver** ([управление пакетами](/content/ecosystem-libs/package-management)): ломающее - major.
- Для монорепо версионирование автоматизируют **Changesets**.
- **Provenance** и 2FA - чтобы пакет не угнали (supply-chain безопасность).

## Framework-agnostic ядро + адаптеры

Лучшее доказательство тезиса «это всё JS, а vue/react - тонкие слои сверху» - архитектура современных библиотек. Логику пишут на **чистом TypeScript**, а под каждый фреймворк делают **тонкий адаптер**.

```
        ┌─────────────────────────┐
        │   core (чистый TS)       │  ← вся логика здесь
        └───────────┬──────────────┘
     ┌──────┬───────┼───────┬────────┐
   React   Vue    Solid   Svelte   Angular   ← тонкие адаптеры (хуки/composables)
```

<b class="text-on-semi-light">Кто так делает</b> - <span class="text-gray">**TanStack** (Query, Table, Router, Virtual) - одно ядро, адаптеры под React/Vue/Solid/Svelte. **Ark UI**, **Zag.js** - UI-логика как машины состояний, тонкие обёртки под фреймворки. Это и есть наглядная демонстрация: React и Vue - тонкая прослойка над общей JS-логикой. Понял ядро - переносишь знание между фреймворками.</span>

> Поэтому переход React → Vue (и наоборот) - это в основном смена синтаксиса адаптера, а не переучивание с нуля. Server-state, виртуализация, формы - концептуально одинаковы; меняется лишь обёртка.

---

## Главная мысль

> Библиотеки - не священные чёрные ящики. Это код таких же инженеров. Ты можешь его **читать**, **патчить**, **форкать**, **улучшать** и **писать свой**. Экосистема - не магазин, где ты только покупаешь, а общее пространство, в котором ты участник.

Это и есть переход от «джуна, который гуглит, какую библиотеку поставить» к «инженеру, который понимает, выбирает, чинит и при необходимости пишет сам».

## Вопросы на собеседовании

<b class="text-on-semi-light">Что делать, если в библиотеке баг, а фикса нет?</b>
<span class="text-gray">Пропатчить локально (patch-package / pnpm patch) - патч сохраняется в репо и применяется при установке. Для крупных правок - форк как зависимость. Параллельно - PR в апстрим, чтобы убрать патч в будущем.</span>

<b class="text-on-semi-light">Зачем peerDependencies при публикации библиотеки?</b>
<span class="text-gray">Чтобы не тащить свою копию React/Vue. Приложение предоставляет один экземпляр - иначе две копии React сломают хуки и контекст.</span>

<b class="text-on-semi-light">Что важно в package.json публикуемой библиотеки?</b>
<span class="text-gray">`exports` (точки входа и типы), `peerDependencies`, `sideEffects: false` для tree-shaking, `files` (что в пакете), публикация ESM и `.d.ts`, корректный semver.</span>

<b class="text-on-semi-light">Как одна библиотека работает и в React, и во Vue?</b>
<span class="text-gray">Логика в фреймворк-агностичном ядре на TS, а под каждый фреймворк - тонкий адаптер (хук/composable). Так устроены TanStack, Ark/Zag - доказательство, что фреймворки лишь тонкий слой над общим JS.</span>

<b class="text-on-semi-light">Почему знание React помогает быстро освоить Vue?</b>
<span class="text-gray">Большинство концепций (server-state, виртуализация, формы, роутинг) одинаковы и часто живут в одном ядре с адаптерами. Меняется синтаксис обёртки, а не суть - всё сводится к JavaScript.</span>
