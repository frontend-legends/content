# Управление пакетами

**npm** - реестр и менеджер пакетов, на котором держится вся экосистема. Понимание `package.json`, semver, lockfile и различий между npm/yarn/pnpm - база, которую проверяют почти на каждом собесе, даже не «про библиотеки».

---

## Менеджеры пакетов

| | npm | yarn | pnpm |
|--|-----|------|------|
| Статус | стандарт, идёт с Node | classic (1.x) + berry (2+) | растущий фаворит |
| node_modules | плоский, дублирование | плоский (или PnP) | **символьные ссылки** на общий стор |
| Диск | много дублей | много дублей | **экономный** (один стор на машину) |
| Строгость | нестрогий | нестрогий | **строгий** (нет phantom-зависимостей) |

<b class="text-on-semi-light">Чем хорош pnpm</b> - <span class="text-gray">Хранит пакеты в одном **content-addressable** сторе на диске, а в проектах создаёт жёсткие/символьные ссылки. Это экономит гигабайты и ускоряет установку. Плюс он **строгий**: пакет видит только явно объявленные зависимости - ловит «phantom dependencies» (когда код использует то, что не указано в `package.json`).</span>

> Yarn Berry с **Plug'n'Play (PnP)** вообще отказывается от `node_modules`, резолвя пакеты через свой механизм. Мощно, но ломает часть инструментов - поэтому распространён умеренно.

## package.json - ключевые поля

```json
{
  "name": "my-app",
  "version": "1.2.3",
  "type": "module",            // ESM по умолчанию (или "commonjs")
  "scripts": { "dev": "vite", "build": "vite build" },
  "dependencies": { "react": "^19.0.0" },
  "devDependencies": { "vite": "^6.0.0" },
  "peerDependencies": { "react": ">=18" },
  "exports": { ".": "./dist/index.js" },
  "engines": { "node": ">=20" }
}
```

### Типы зависимостей

| Поле | Что кладут | Попадает в прод-бандл |
|------|-----------|------------------------|
| `dependencies` | нужно в рантайме (React, lodash) | да |
| `devDependencies` | инструменты сборки/тестов (Vite, ESLint) | нет |
| `peerDependencies` | то, что предоставляет **хост** (плагин ждёт React от приложения) | нет, не дублируется |
| `optionalDependencies` | необязательные (установка не упадёт, если не встанет) | если есть |

<b class="text-on-semi-light">peerDependencies - частый вопрос</b> - <span class="text-gray">Библиотека-плагин (например, React-компонент) указывает React в `peerDependencies`, а не в `dependencies`, чтобы **не тащить вторую копию** React. Приложение предоставляет один React всем плагинам - иначе хуки сломаются (два разных React).</span>

## Semver

**Semantic Versioning** - `MAJOR.MINOR.PATCH`.

- **MAJOR** (`2.0.0`) - ломающие изменения.
- **MINOR** (`1.3.0`) - новая функциональность, совместимо.
- **PATCH** (`1.2.4`) - багфиксы, совместимо.

Диапазоны в `package.json`:

```jsonc
"react": "^19.1.0"  // ^ - совместимые: >=19.1.0 <20.0.0 (фикс major)
"react": "~19.1.0"  // ~ - только патчи: >=19.1.0 <19.2.0
"react": "19.1.0"   // точная версия
"react": "*"        // любая (опасно)
```

`^` (caret) - дефолт npm: разрешает minor/patch, фиксируя major. Это компромисс между свежестью и стабильностью.

## Lockfile

`package-lock.json` (npm), `yarn.lock`, `pnpm-lock.yaml` фиксируют **точные** версии **всего дерева** зависимостей (включая транзитивные).

<b class="text-on-semi-light">Зачем коммитить lockfile</b> - <span class="text-gray">`package.json` задаёт диапазоны (`^19.1.0`), а lockfile - конкретные установленные версии. Без него у разработчиков и CI установятся **разные** версии транзитивных зависимостей - «у меня работает, у тебя нет». Lockfile делает установку **детерминированной**. Его всегда коммитят; в CI используют `npm ci` (ставит строго по lockfile).</span>

## npx и dlx

`npx` запускает CLI-пакет **без глобальной установки** - скачивает и выполняет разово.

```bash
npx create-vite my-app   # запустить генератор, не устанавливая его навсегда
pnpm dlx shadcn add button
```

## npm-скрипты и жизненный цикл

`scripts` в `package.json` - команды проекта, запускаются через `npm run <name>`.

```json
"scripts": {
  "dev": "vite",
  "build": "vite build",
  "prepare": "husky",        // lifecycle-хук: выполнится после install
  "postinstall": "patch-package"
}
```

<b class="text-on-semi-light">Lifecycle-хуки</b> - <span class="text-gray">Префиксы `pre`/`post` запускают скрипты до/после: `prebuild` перед `build`, `postinstall` после установки зависимостей. На `postinstall` живёт, например, [патчинг зависимостей](/content/ecosystem-libs/building-and-patching). Но `postinstall`-скрипты в чужих пакетах - **вектор атаки** (выполняются при установке), поэтому экосистема относится к ним настороженно.</span>

## Разрешение модулей

Когда код пишет `import x from 'lib'`, среда ищет пакет, поднимаясь по `node_modules` вверх по дереву каталогов до первого совпадения. Современные пакеты управляют точками входа через поле **`exports`** в `package.json` (что и как импортируется, включая отдельные типы для ESM/CJS).

> «Phantom dependency» - когда код использует пакет, который не указан в `package.json`, но оказался в плоском `node_modules` как транзитивная зависимость. Работает случайно и ломается при обновлении. pnpm это запрещает строгой структурой.

## Безопасность зависимостей

Большая часть кода в проекте - чужая. Это **supply chain**-риск.

- **`npm audit`** - проверка известных уязвимостей в дереве зависимостей.
- **Минимизируй** число зависимостей и их транзитивную глубину.
- **Lockfile + `npm ci`** в CI - воспроизводимость и защита от подмены версий.
- **Provenance / 2FA** при публикации - чтобы пакет не угнали.
- Инструменты: Dependabot/Renovate (авто-обновления), Snyk (аудит).

> Атаки через скомпрометированный популярный пакет (или его `postinstall`) - реальный сценарий. Поэтому обновления зависимостей - не только про фичи, но и про безопасность.

## Workspaces и монорепы

**Workspaces** - несколько пакетов в одном репозитории с общим `node_modules` и взаимными ссылками. Поддерживают npm, yarn, pnpm.

```json
// корневой package.json
{ "workspaces": ["packages/*", "apps/*"] }
```

Поверх workspaces работают **оркестраторы монорепо**:

- **Turborepo** - кеширование задач, параллельный запуск, инкрементальные сборки.
- **Nx** - то же + генераторы, граф зависимостей, плагины.

> Монорепа полезна, когда несколько приложений/библиотек делят код (UI-кит, утилиты). Цена - сложнее CI и инструменты. pnpm + Turborepo - популярная связка 2026.

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем pnpm отличается от npm?</b>
<span class="text-gray">pnpm хранит пакеты в одном content-addressable сторе и ссылается на них из проектов - экономит диск и ускоряет установку. Он строгий: код видит только явные зависимости, что ловит phantom deps.</span>

<b class="text-on-semi-light">В чём разница dependencies, devDependencies и peerDependencies?</b>
<span class="text-gray">`dependencies` нужны в рантайме, `devDependencies` - только для сборки/тестов, `peerDependencies` предоставляет хост-приложение (чтобы не дублировать, например, React).</span>

<b class="text-on-semi-light">Что означает ^ в версии?</b>
<span class="text-gray">Caret разрешает minor и patch обновления, фиксируя major: `^19.1.0` это `>=19.1.0 <20.0.0`. Дефолт npm.</span>

<b class="text-on-semi-light">Зачем нужен и коммитится lockfile?</b>
<span class="text-gray">Он фиксирует точные версии всего дерева зависимостей, делая установку детерминированной. Без него разные машины/CI получат разные транзитивные версии.</span>

<b class="text-on-semi-light">Почему React в библиотеке-плагине идёт в peerDependencies?</b>
<span class="text-gray">Чтобы не установить вторую копию React. Две копии ломают хуки и контекст - приложение должно предоставить один React всем плагинам.</span>

<b class="text-on-semi-light">Что такое phantom dependency?</b>
<span class="text-gray">Использование пакета, которого нет в `package.json`, но он оказался в плоском node_modules как транзитивный. Работает случайно и ломается при обновлении. pnpm запрещает это строгой структурой.</span>

<b class="text-on-semi-light">Чем опасны postinstall-скрипты и зависимости в целом?</b>
<span class="text-gray">Это supply-chain-риск: `postinstall` чужого пакета выполняется при установке и может быть вредоносным. Защита - минимум зависимостей, lockfile + `npm ci`, аудит (npm audit, Snyk), provenance/2FA при публикации.</span>
