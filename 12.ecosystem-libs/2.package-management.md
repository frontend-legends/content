# Управление пакетами

Как устроена установка зависимостей: npm, pnpm, Yarn и Bun, поля `package.json` и типы зависимостей, semver и диапазоны версий, lock-файл, peer-зависимости и их конфликты, скрипты и жизненный цикл, безопасность установки. Спрашивают, чем pnpm отличается от npm, в чём разница `dependencies`, `devDependencies` и `peerDependencies` и что означает `^` в версии. Глубже — почему `^0.2.3` не обновится до `0.3.0`, откуда ошибка `ERESOLVE` и почему pnpm отказался выполнять `postinstall`.

::tldr
- **`package.json` задаёт диапазоны версий, lock-файл — точные версии всего дерева.** Lock коммитят, иначе у каждого разработчика и в CI будет свой набор пакетов.
- **`^1.2.3` разрешает минорные и патч-обновления до `2.0.0`, `~1.2.3` — только патчи.** До `1.0.0` правила строже: `^0.2.3` не пустит `0.3.0`, потому что в нулевой мажорной версии минорная — это ломающая.
- **`peerDependencies` — то, что пакет ожидает от приложения,** а не ставит сам: плагин React требует React приложения. Несовместимая версия даёт при установке ошибку `ERESOLVE`.
- **Скрипты жизненного цикла выполняются при установке, и это главный путь атак через пакеты.** npm выполняет `postinstall` зависимостей по умолчанию, pnpm — только для пакетов из разрешённого списка.
- **pnpm хранит каждую версию пакета один раз и даёт пакету видеть только объявленные зависимости,** поэтому экономит место и ловит «призрачные» импорты, которые npm пропускает.
::

## Менеджеры пакетов

| | npm | pnpm | Yarn | Bun |
| --- | --- | --- | --- | --- |
| Раскладка `node_modules` | плоская, зависимости подняты в корень | изолированная: ссылки в `.pnpm` | плоская или Plug'n'Play без `node_modules` | плоская |
| Хранение | копия в каждом проекте | общее хранилище по содержимому, жёсткие ссылки | кеш, PnP-архивы | общий кеш |
| Необъявленные импорты | работают случайно | не находятся | в PnP запрещены | работают случайно |
| Скрипты зависимостей | выполняет | только разрешённые | выполняет | только разрешённые |
| Lock-файл | `package-lock.json` | `pnpm-lock.yaml` | `yarn.lock` | `bun.lock` |

**pnpm** хранит каждую версию пакета один раз в общем хранилище и подключает её в проекты жёсткими ссылками, поэтому десять проектов с одним Vue не занимают десять копий. В `node_modules` пакета видны только его объявленные зависимости: в проверке прямая зависимость оказалась символической ссылкой в `node_modules/.pnpm`. Это ловит **призрачные зависимости** — импорты, которые работают в npm только потому, что пакет случайно поднят в корень (подробно — в [Монорепо](/content/advanced-tooling/monorepo-tooling)).

**Corepack** — инструмент, который выбирает менеджер и его версию по полю `packageManager` в `package.json`, чтобы у всех разработчиков была одна версия pnpm или Yarn.

Сквозной пример — магазин с зависимостями: библиотека денег, UI-кит, тестовый набор и плагин к фреймворку.

## package.json и типы зависимостей

Поля, которые спрашивают:

- **`name`, `version`** — идентификатор пакета; для приложения, которое не публикуется, ставят `"private": true`;
- **`type`** — как читать `.js`: `"module"` — ESM, иначе CommonJS (подробно — в [Модульных системах](/content/advanced-tooling/module-systems));
- **`exports`, `main`, `types`** — точки входа пакета;
- **`scripts`** — команды проекта;
- **`engines`** — поддерживаемые версии Node.js;
- **`packageManager`** — менеджер и его версия для Corepack;
- **`overrides`** (npm), `pnpm.overrides`, `resolutions` (Yarn) — принудительная версия пакета во всём дереве.

### Типы зависимостей

| Поле | Что значит | Когда ставится |
| --- | --- | --- |
| `dependencies` | нужно для работы | всегда |
| `devDependencies` | нужно для разработки: сборщик, линтер, тесты | не ставится с `--omit=dev` и у потребителей пакета |
| `peerDependencies` | пакет ожидает, что это даст приложение | ставит приложение, менеджер проверяет совместимость |
| `optionalDependencies` | может не установиться, и это не ошибка | платформенные бинарники нативных инструментов |

В проверке `npm install --omit=dev` поставил библиотеку денег и пропустил тестовый набор. Для приложения, которое собирается целиком, деление на `dependencies` и `devDependencies` почти не влияет на результат — всё нужное попадает в бандл. Оно важно для **библиотек** и серверного кода: потребитель библиотеки не получит её `devDependencies`.

### peerDependencies

Плагин к фреймворку не должен ставить свою копию фреймворка — иначе у приложения окажутся две копии, два контекста, сломанные хуки (подробно — в [Бандлерах](/content/advanced-tooling/bundlers)). Поэтому плагин объявляет фреймворк в `peerDependencies`: «я работаю с вашим React версии `^19`».

npm с седьмой версии ставит недостающие peer-зависимости сам и **проверяет совместимость**. В проверке плагин требовал хост `^2.0.0`, а в приложении был `3.5.0`, и установка упала:

```text
npm error code ERESOLVE
npm error Could not resolve dependency:
npm error peer host@"^2.0.0" from plugin@1.0.0
```

Флаг `--legacy-peer-deps` отключает проверку, и установка проходит — но плагин будет работать с версией, которую не поддерживает. Это временная мера, а не решение: правильно обновить плагин или найти совместимую версию.

## Semver

Версия — `MAJOR.MINOR.PATCH`:

- **MAJOR** — ломающие изменения;
- **MINOR** — новые возможности без поломок;
- **PATCH** — исправления.

Диапазоны в `package.json`, проверенные библиотекой `semver`, которую использует npm:

| Диапазон | Что разрешает |
| --- | --- |
| `1.2.3` | ровно эту версию |
| `^1.2.3` | `>=1.2.3 <2.0.0` — минорные и патчи |
| `~1.2.3` | `>=1.2.3 <1.3.0` — только патчи |
| `^0.2.3` | `>=0.2.3 <0.3.0` — в нулевой мажорной минорная считается ломающей |
| `^0.0.3` | `>=0.0.3 <0.0.4` — только эта патч-версия |
| `*` | любую |

Тонкости:

- **пререлизы** вроде `1.3.0-beta.1` диапазоном `^1.2.3` не подхватываются — их нужно указать явно;
- из доступных версий менеджер берёт **наибольшую подходящую**: для `^1.2.3` среди `1.2.3`, `1.4.0`, `1.10.2`, `2.0.0` — это `1.10.2`, версии сравниваются как числа, а не как строки;
- semver — **обещание автора**, а не гарантия. Минорная версия тоже может что-то сломать, поэтому обновления проверяют тестами.

## Lock-файл

`package.json` хранит диапазоны, а **lock-файл** — точные версии и источники **всех** пакетов дерева, включая транзитивные. С ним установка воспроизводима: сегодня и через год, у разработчика и в :term[CI]{def="непрерывная интеграция: сервер, который собирает и тестирует код на каждое изменение"} получается один и тот же набор.

Правила:

- **lock-файл коммитят** — и в приложениях, и в библиотеках, для воспроизводимой разработки (потребители библиотеки его не получают);
- **в CI ставят строго по нему** — `npm ci`, `pnpm install --frozen-lockfile`; он падает, если `package.json` разошёлся с lock (подробно — в [CI/CD](/content/advanced-tooling/ci-cd));
- **обновляют явно** — `npm update` или отдельными PR через Renovate и Dependabot, которые проходят CI;
- **один менеджер на проект:** два разных lock-файла — гарантированное расхождение.

## Скрипты

```json
{
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "prebuild": "node scripts/check-env.js",
    "postbuild": "node scripts/check-size.js",
    "test": "vitest"
  }
}
```

`npm run build` запускает `prebuild`, `build` и `postbuild` по порядку — в проверке так и было. Скрипты видят бинарники из `node_modules/.bin` без пути. `npx имя` и `pnpm dlx имя` запускают бинарник пакета: сначала ищут локальный, а если его нет — скачивают во временную папку.

### Скрипты при установке

Пакет может объявить `preinstall`, `install` и `postinstall` — они выполняются **при установке пакета**. Изначально это для сборки нативных модулей. На практике это главный путь атак через npm: взломанный пакет в `postinstall` крадёт токены и переменные окружения машины разработчика или CI, а иногда публикует заражённые версии других пакетов от имени жертвы (подробно — в [Цепочке поставок](/content/security-perfomance/supply-chain-and-vulnerabilities)).

Поведение менеджеров, проверено на локальном пакете с `postinstall`:

- **npm** выполняет скрипты зависимостей по умолчанию;
- **`npm install --ignore-scripts`** не выполняет ничего — но и нужные нативные сборки тоже;
- **pnpm** выполняет скрипты только у пакетов из разрешённого списка. Остальные он пропускает, а в pnpm 11 это ошибка установки: `ERR_PNPM_IGNORED_BUILDS` с подсказкой выполнить `pnpm approve-builds`.

Разрешённый список хранится в репозитории и проходит ревью — так видно, какие пакеты выполняют код при установке. Bun тоже выполняет скрипты только доверенных пакетов.

### Ещё о безопасности

- `npm audit` и аналоги сверяют дерево с базой известных уязвимостей;
- задержка перед установкой новых версий — например, `minimumReleaseAge` в pnpm — защищает от свежеопубликованных заражённых версий, которые обычно находят и снимают за часы;
- `overrides` закрывает уязвимую транзитивную версию, пока прямая зависимость не обновилась;
- токены публикации — с двухфакторной аутентификацией и публикация из CI с подтверждением происхождения (provenance).

## Красные флаги в ответе

- **«`^` означает любую новую версию».** Только до следующей мажорной, а до `1.0.0` — ещё уже.
- **«Lock-файл можно не коммитить».** Без него у каждого свой набор транзитивных версий.
- **«peerDependencies ставит сам пакет».** Их даёт приложение, менеджер только проверяет совместимость.
- **«`--legacy-peer-deps` решает конфликт».** Он отключает проверку, а несовместимость остаётся.
- **«Установка пакета безопасна, пока его не импортировали».** Скрипты жизненного цикла выполняются уже при установке.

## Как спрашивают на собеседовании

::question
Чем pnpm отличается от npm?

#answer
pnpm хранит каждую версию пакета один раз в общем хранилище и подключает её жёсткими ссылками, поэтому экономит место и время. `node_modules` у него изолированные: пакет видит только объявленные зависимости, и призрачные импорты не работают.

#more
npm поднимает зависимости в корень, и пакет может случайно импортировать чужую зависимость. pnpm по умолчанию не выполняет скрипты установки зависимостей без разрешения. В CI он сам включает строгую установку по lock-файлу. Для монорепо у него удобные workspaces с протоколом `workspace:*`.
::

::question
В чём разница dependencies, devDependencies и peerDependencies?

#answer
`dependencies` нужны для работы и ставятся всегда. `devDependencies` — для разработки: сборщик, линтер, тесты; их не получают потребители пакета и не ставит `--omit=dev`. `peerDependencies` — то, что пакет ожидает от приложения, например React у плагина.

#more
Для приложения, которое собирается целиком, разница между первыми двумя невелика: всё нужное попадает в бандл. Для библиотек и серверного кода она важна. npm ставит недостающие peer-зависимости и падает с `ERESOLVE` при несовместимой версии.
::

::question
Что означают ^ и ~ в версии?

#answer
`^1.2.3` разрешает версии от `1.2.3` до `2.0.0`, не включая её: минорные обновления и патчи. `~1.2.3` — от `1.2.3` до `1.3.0`: только патчи.

#more
До `1.0.0` правила строже: `^0.2.3` разрешает только `0.2.x`, а `^0.0.3` — только `0.0.3`, потому что в нулевой мажорной версии минорная считается ломающей. Пререлизы диапазон не подхватывает. Менеджер берёт наибольшую подходящую версию, сравнивая числа, а не строки.
::

::question
Зачем нужен lock-файл и почему его коммитят?

#answer
`package.json` задаёт диапазоны, а lock-файл фиксирует точные версии всего дерева, включая транзитивные. С ним установка воспроизводима у всех разработчиков и в CI.

#more
В CI ставят строго по нему через `npm ci` или `--frozen-lockfile`, и установка падает при расхождении с `package.json`. Обновляют его явно — отдельными PR через Renovate или Dependabot. Два lock-файла разных менеджеров в одном проекте — источник расхождений.
::

::question
Почему React в библиотеке-плагине идёт в peerDependencies?

#answer
Чтобы плагин использовал React приложения, а не принёс свою копию. Две копии React — это два контекста, сломанные хуки и лишний размер.

#more
Плагин объявляет диапазон версий, с которыми работает, а менеджер проверяет совместимость: при несовпадении — `ERESOLVE`. В сборке библиотеки React выносят в `external`. Флаг `--legacy-peer-deps` отключает проверку, но не делает версии совместимыми.
::

::question
Чем опасны скрипты установки?

#answer
`preinstall` и `postinstall` выполняются при установке пакета — до того, как его кто-то импортировал. Взломанный пакет может украсть токены и переменные окружения разработчика или CI и опубликовать заражённые версии других пакетов.

#more
npm выполняет такие скрипты по умолчанию, `--ignore-scripts` отключает их все. pnpm и Bun выполняют только разрешённые, и в pnpm неразрешённый скрипт — ошибка установки с подсказкой `pnpm approve-builds`. Дополнительно — задержка установки свежих версий, аудит и двухфакторная аутентификация для публикации.
::

## Практика

::practice{title="Установка падает с ERESOLVE"}
После обновления фреймворка до новой мажорной версии `npm install` падает:

```text
npm error code ERESOLVE
npm error peer host@"^2.0.0" from plugin@1.0.0
```

Коллега предлагает добавить `--legacy-peer-deps` в `.npmrc`.

#solution
Плагин объявил, что работает только с хостом версии 2, а в проекте теперь 3. `--legacy-peer-deps` отключит проверку, и установка пройдёт, но плагин будет работать с версией, которую не поддерживает, — сломается он при выполнении, а не при установке.

```bash
npm view plugin peerDependencies   # какая версия плагина поддерживает host@3
npm install plugin@latest
```

Правильно — обновить плагин до версии с поддержкой новой мажорной версии хоста. Если такой нет, варианты — дождаться, предложить исправление автору, найти альтернативу или временно отложить обновление хоста. В проверке установка с несовместимой peer-зависимостью упала с `ERESOLVE`, а с `--legacy-peer-deps` прошла молча.
::

::practice{title="pnpm не выполнил postinstall"}
После перехода на pnpm установка падает, а нативный модуль для работы с изображениями не собрался:

```text
[ERR_PNPM_IGNORED_BUILDS] Ignored build scripts: sharp
Run "pnpm approve-builds" to pick which dependencies should be allowed to run scripts.
```

#solution
pnpm выполняет скрипты установки только у пакетов из разрешённого списка. Это защита: скрипт установки может выполнить что угодно на машине разработчика и в CI. Пакету с нативной сборкой разрешение дают явно:

```bash
pnpm approve-builds   # выбрать пакеты, которым можно выполнять скрипты
```

Выбор сохраняется в конфигурации репозитория и проходит ревью, поэтому всегда видно, какие пакеты выполняют код при установке. Разрешать стоит только пакеты, которым это действительно нужно, — нативные модули и бинарники. В проверке pnpm не выполнил `postinstall` локального пакета и завершил установку этой ошибкой, а npm тот же скрипт выполнил.
::
