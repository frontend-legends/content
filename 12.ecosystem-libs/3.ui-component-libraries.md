# UI-библиотеки

Три подхода к готовым компонентам — библиотеки со стилями, headless-библиотеки и копирование кода в проект, — что каждый даёт и чем за это платят, как на них строят дизайн-систему и когда библиотека не нужна вовсе. Спрашивают, чем headless-библиотека отличается от обычной, что такое shadcn/ui и как выбрать UI-библиотеку. Глубже — что на самом деле сложного в модальном окне и выпадающем списке и почему «сделаем сами за день» обычно оборачивается месяцем.

::tldr
- **Главная ценность UI-библиотеки — поведение и доступность, а не внешний вид:** фокус, клавиатура, ARIA, блокировка прокрутки, позиционирование, мобильные особенности. Самодельная модалка на `div` обычно не умеет ничего из этого.
- **Библиотека со стилями даёт готовый вид и скорость,** но с ней трудно сделать свой дизайн и легко получить тяжёлый бандл и зависимость от её системы тем.
- **Headless-библиотека даёт поведение без стилей:** Radix, React Aria, Base UI, Ark UI, Reka UI для Vue. Внешний вид полностью твой — это основа своей дизайн-системы.
- **Копирование кода, как в shadcn/ui, кладёт компоненты в твой репозиторий:** поверх headless-примитивов и Tailwind. Ты владеешь кодом и меняешь что угодно, но и обновляешь сам.
- **Выбор зависит от того, есть ли свой дизайн:** нет — библиотека со стилями; есть — headless или копирование; нужно для нескольких продуктов — дизайн-система поверх headless.
::

## Что сложного в компоненте

Сквозной пример — окно быстрого просмотра товара. Самодельная версия выглядит как модалка:

```jsx
{open && (
  <div className="modal">
    <h2>Улун</h2>
    <button onClick={close}>×</button>
  </div>
)}
```

В проверке эта модалка не сообщила скринридеру, что она диалог, оставила фокус на кнопке под ней и не закрылась по Escape. Список того, что нужно настоящему модальному окну:

- роль `dialog` и подпись заголовком через `aria-labelledby`;
- перенос фокуса внутрь при открытии и **ловушка фокуса** — Tab не уходит на страницу под окном;
- возврат фокуса на кнопку, которая открыла окно;
- закрытие по Escape и по клику вне окна;
- скрытие остальной страницы от скринридера;
- блокировка прокрутки страницы под окном — с учётом ширины полосы прокрутки, чтобы страница не прыгала;
- вывод в `body` через портал, чтобы окно не обрезал `overflow` родителя.

Выпадающий список, комбобокс, меню, всплывающая подсказка и выбор даты — в разы сложнее: навигация стрелками, поиск по первой букве, позиционирование у края экрана, сенсорные экраны. Именно поэтому UI-библиотеки существуют. Основы доступности — в [Доступности](/content/html/accessibility), порталы и фокус в React — в [Рефах, порталах и доступности](/content/reactjs/refs-portals-a11y).

## Три подхода

### Библиотеки со стилями

:term[MUI]{def="библиотека компонентов React в стиле Material Design"}, Mantine, Ant Design, Chakra UI, Vuetify, PrimeVue, Naive UI, Quasar — компоненты с готовым дизайном, темами и десятками готовых сложных виджетов: таблицы, выбор дат, деревья.

- **плюсы:** быстрый старт, единый вид, богатый набор, документация;
- **минусы:** свой дизайн делается через переопределение тем и стилей и рано или поздно упирается в границы библиотеки; часть библиотек тянет свою систему стилизации — например, :term[CSS-in-JS]{def="подход, при котором стили описывают в JavaScript, а библиотека генерирует и вставляет их на страницу"} во время выполнения, — и это отражается на размере и совместимости с серверными компонентами (подробно — в [Стилизации](/content/ecosystem-libs/styling-solutions));
- **когда:** внутренние инструменты, админки, MVP, продукты без своего дизайна.

### Headless-библиотеки

Radix Primitives, React Aria, Base UI, Ark UI, Headless UI, а для Vue — Reka UI. Они дают **поведение и доступность без внешнего вида**. Тот же диалог на Radix:

```jsx
import * as Dialog from '@radix-ui/react-dialog';

<Dialog.Root>
  <Dialog.Trigger>Быстрый просмотр</Dialog.Trigger>
  <Dialog.Portal>
    <Dialog.Overlay className="overlay" />
    <Dialog.Content className="modal">
      <Dialog.Title>Улун</Dialog.Title>
      <Dialog.Description>Китайский чай, 100 г</Dialog.Description>
      <Dialog.Close>×</Dialog.Close>
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
```

В проверке в jsdom он:

- выставил кнопке `aria-haspopup="dialog"` и `aria-expanded`;
- отрисовал `role="dialog"`, подписанный заголовком и описанием;
- перенёс фокус внутрь, скрыл остальную страницу через `aria-hidden` и заблокировал прокрутку;
- закрылся по Escape, вернул фокус на кнопку и снял блокировку прокрутки.

Внешний вид — только классы, которые передал разработчик. Единственный стиль, который Radix добавил сам, — правило блокировки прокрутки для `body`.

- **плюсы:** любой дизайн, проверенная доступность, небольшой размер, компоненты как кирпичи;
- **минусы:** весь внешний вид — работа команды, сложных готовых виджетов вроде таблиц меньше;
- **когда:** свой дизайн, своя дизайн-система.

Есть и более низкий уровень — хуки и автоматы состояний без компонентов: React Aria Hooks, Zag.js (на нём построен Ark UI), Floating UI для позиционирования всплывающих элементов.

### Копирование кода

**shadcn/ui** — не библиотека, а набор компонентов, которые командой CLI копируются **в твой проект**: `npx shadcn add dialog` создаёт файл `components/ui/dialog.tsx`. Внутри — headless-примитив, исторически Radix, и классы Tailwind. Аналог для Vue — shadcn-vue на Reka UI.

- **плюсы:** код твой — меняешь что угодно, нет зависимости от релизов библиотеки, хорошая доступность из примитивов;
- **минусы:** обновления тоже твои — исправление в исходных компонентах само не придёт, его нужно перенести; без дисциплины копии расходятся;
- **когда:** свой дизайн на Tailwind без желания строить всё с нуля.

## Дизайн-система

**Дизайн-система** — общий для продуктов компании набор токенов (цвета, отступы, типографика), компонентов, правил и документации. На фронтенде её обычно строят слоями:

```text
токены (CSS-переменные)            — 6.09 Архитектура CSS
  ↓
headless-примитивы (Radix, Reka)   — поведение и доступность
  ↓
свои компоненты с дизайном         — пакет @shop/ui
  ↓
продукты                           — используют только @shop/ui
```

Продукты импортируют только свои компоненты, а не примитивы напрямую — тогда смена примитива или исправление доступности делается в одном месте. Компоненты документируют и проверяют в Storybook, а изменения внешнего вида ловят визуальными тестами (подробно — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing)). Токены и методологии CSS — в [Архитектуре CSS](/content/css/architecture), устройство пакетов — в [Монорепо](/content/advanced-tooling/monorepo-tooling).

## Когда библиотека не нужна

Платформа закрывает больше, чем кажется:

- **`<dialog>` с `showModal()`** — модальное окно с фокусом внутри, Escape, слоем поверх страницы и `::backdrop`;
- **атрибут `popover`** — всплывающие элементы с закрытием по клику вне и по Escape;
- **CSS anchor positioning** — привязка подсказки к элементу без JavaScript там, где поддерживается;
- **`<details>` и `<summary>`** — раскрывающиеся блоки;
- **нативные поля** — `<input type="date">`, `<select>`, причём `<select>` в новых браузерах получил настраиваемый внешний вид.

Если продукту нужны три простых компонента, нативные элементы и немного CSS могут оказаться лучше любой зависимости. Подробно о новых возможностях — в [Современном CSS](/content/css/modern-css) и [Будущем веба](/content/web/future-of-web).

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| админка, внутренний инструмент, MVP без дизайнера | библиотека со стилями: MUI, Mantine, Ant Design, Vuetify, PrimeVue |
| свой дизайн, одно приложение на Tailwind | shadcn/ui или shadcn-vue |
| свой дизайн, несколько продуктов | своя дизайн-система поверх Radix, React Aria, Base UI или Reka UI |
| максимальные требования к доступности и интернационализации | React Aria |
| несколько фреймворков с одним поведением | Ark UI на автоматах Zag.js |
| несколько простых компонентов | нативные `dialog`, `popover`, `details` |

Дополнительно проверяют совместимость с серверными компонентами и :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"}, размер нужных компонентов, поддержку :term[RTL]{def="письмо справа налево, как в арабском и иврите"} и тем, качество типов и активность поддержки (подробно о критериях — во [Введении в экосистему](/content/ecosystem-libs/introduction)).

## Красные флаги в ответе

- **«Модалку проще сделать самому».** Фокус, Escape, ARIA, блокировка прокрутки и портал — это неделя работы и типичные ошибки доступности.
- **«Headless — это библиотека без стилей, значит, бесполезная».** Её ценность в поведении и доступности, внешний вид — осознанно твой.
- **«shadcn/ui — это библиотека, её обновляют через npm».** Код копируется в проект, обновления переносят вручную.
- **«Библиотека со стилями подходит для любого дизайна».** Свой дизайн через переопределения тем быстро упирается в её границы.
- **«Без библиотеки модальное окно не сделать».** `<dialog>` с `showModal()` даёт фокус, Escape и слой поверх страницы.

## Как спрашивают на собеседовании

::question
Чем headless-библиотека отличается от обычной UI-библиотеки?

#answer
Обычная даёт компоненты с готовым дизайном и темами. Headless даёт поведение и доступность без внешнего вида: фокус, клавиатуру, ARIA, состояние открытия, блокировку прокрутки. Внешний вид полностью задаёт команда.

#more
Headless — основа своей дизайн-системы: Radix, React Aria, Base UI, Ark UI, Headless UI, для Vue — Reka UI. Есть уровень ниже — хуки и автоматы без компонентов: React Aria Hooks, Zag.js, Floating UI. Библиотеки со стилями быстрее на старте, но свой дизайн через переопределения тем упирается в их границы.
::

::question
Что такое shadcn/ui?

#answer
Набор компонентов, которые CLI копирует прямо в проект: на headless-примитивах, исторически Radix, и классах Tailwind. Это не зависимость, а твой код, который можно менять как угодно.

#more
Плюс — полный контроль и отсутствие зависимости от релизов библиотеки. Минус — исправления в исходных компонентах сами не придут, их переносят вручную. Для Vue есть shadcn-vue на Reka UI. Подход хорош для одного продукта на Tailwind со своим дизайном.
::

::question
Что сложного в модальном окне?

#answer
Роль `dialog` и подпись, перенос фокуса внутрь и ловушка фокуса, возврат фокуса на кнопку, закрытие по Escape и клику вне, скрытие остальной страницы от скринридера, блокировка прокрутки без прыжка страницы и вывод через портал.

#more
Самодельная модалка на `div` обычно не делает ничего из этого — её не видит скринридер, а клавиатурой из неё можно уйти на страницу. Нативный `<dialog>` с `showModal()` даёт часть поведения из коробки. Выпадающие списки и комбобоксы ещё сложнее: стрелки, поиск по букве, позиционирование у края экрана.
::

::question
Как выбрать UI-библиотеку?

#answer
Сначала — есть ли свой дизайн. Нет — библиотека со стилями: MUI, Mantine, Ant Design, Vuetify, PrimeVue. Есть — headless или shadcn/ui. Несколько продуктов — своя дизайн-система поверх headless-примитивов.

#more
Дальше проверяют доступность, совместимость с SSR и серверными компонентами, размер нужных компонентов, RTL, темы, типы и поддержку. Для простых случаев сначала смотрят на нативные `dialog`, `popover` и `details`.
::

::question
Как устроена дизайн-система на фронтенде?

#answer
Слоями: токены в CSS-переменных, headless-примитивы для поведения, свои компоненты с дизайном в отдельном пакете и продукты, которые используют только этот пакет.

#more
Продукты не импортируют примитивы напрямую, поэтому замена примитива или исправление доступности делается в одном месте. Компоненты документируют в Storybook и проверяют визуальными тестами. В монорепо пакет дизайн-системы — внутренний пакет workspaces.
::

## Практика

::practice{title="Модалка, которой не видит скринридер"}
В аудите доступности: окно быстрого просмотра не объявляется скринридером, Tab уходит на страницу под ним, Escape не работает. Код:

```jsx
{open && (
  <div className="modal">
    <h2>{product.title}</h2>
    <button onClick={() => setOpen(false)}>×</button>
  </div>
)}
```

#solution
Это `div` с видом модалки, но без её поведения. Два пути. Headless-примитив:

```jsx
import * as Dialog from '@radix-ui/react-dialog';

<Dialog.Root open={open} onOpenChange={setOpen}>
  <Dialog.Portal>
    <Dialog.Overlay className="overlay" />
    <Dialog.Content className="modal">
      <Dialog.Title>{product.title}</Dialog.Title>
      <Dialog.Close aria-label="Закрыть">×</Dialog.Close>
    </Dialog.Content>
  </Dialog.Portal>
</Dialog.Root>
```

Или нативный `<dialog>` с `showModal()` — он тоже даёт фокус внутри, Escape и слой поверх страницы, но подписи и возврат фокуса при закрытии стоит проверить вручную. Классы и внешний вид остаются прежними. В проверке наивная модалка не получила роли, не переняла фокус и не закрылась по Escape, а Radix сделал всё это и вернул фокус на кнопку.
::

::practice{title="Дизайн не помещается в библиотеку"}
Продукт на MUI. Дизайнеры прислали новый дизайн, и каждый компонент приходится переопределять через тему, `sx` и `!important`. Половина стилей борется со стилями библиотеки.

#solution
Библиотека со стилями хороша, пока дизайн близок к её собственному. Когда дизайн свой, переопределения становятся дороже, чем компоненты с нуля. Переход делают постепенно:

```text
1. токены дизайна → CSS-переменные
2. новые компоненты — на headless-примитивах (Base UI, Radix, React Aria) со своими стилями
3. компоненты кладут в пакет @shop/ui, продукт импортирует только его
4. старые компоненты MUI заменяют по одному, начиная с самых переопределённых
```

Для одного приложения на Tailwind быстрее shadcn/ui — компоненты сразу в репозитории. Важно не смешивать бесконечно: пока продукт использует обе системы, у него два набора стилей и две темы. Сроки перехода закладывают в план, а не делают «по пути».
::
