# Формы и валидация

Формы - обманчиво сложная тема: состояние полей, валидация (синхронная и асинхронная), массивы полей, ошибки, производительность при больших формах. Поэтому существует целый класс библиотек. Отдельно стоит **схемная валидация**, которая в 2026 стала почти обязательной.

---

## Зачем библиотека для форм

Своя форма на `useState` быстро упирается в:

- **производительность** - каждый ввод перерисовывает всю форму (controlled-поля);
- **валидацию** - правила, зависимости между полями, async-проверки (занят ли email);
- **сложные структуры** - динамические массивы полей, вложенность;
- **UX** - когда показывать ошибку (на blur? на submit?), touched/dirty-состояния.

Библиотеки решают всё это и дают предсказуемый API.

---

## react-hook-form

Стандарт для React. Главная идея - **неуправляемые поля через рефы**: библиотека не хранит значение каждого поля в state, а читает из DOM, поэтому ввод **не вызывает ререндер всей формы**.

```jsx
import { useForm } from 'react-hook-form';

function SignupForm() {
  const { register, handleSubmit, formState: { errors } } = useForm();

  return (
    <form onSubmit={handleSubmit((data) => console.log(data))}>
      <input {...register('email', { required: 'Обязательно' })} />
      {errors.email && <span>{errors.email.message}</span>}
      <button>Отправить</button>
    </form>
  );
}
```

<b class="text-on-semi-light">Почему быстрый</b> - <span class="text-gray">Поля «регистрируются» через `register` и работают как uncontrolled - значение живёт в DOM, а не в React-state. Ввод в одно поле не перерисовывает остальные. Для больших форм это решающее преимущество перед controlled-подходом.</span>

## Formik и другие

- **Formik** - был стандартом до RHF. Хранит значения в state (**controlled**), поэтому медленнее на больших формах и провоцирует лишние ререндеры. Сейчас развивается слабо - **legacy-выбор**, который всё ещё встречается.
- **TanStack Form** - новое поколение: **кросс-фреймворк** (React/Vue/Solid), полностью типобезопасный, headless. Растущая альтернатива.
- **Final Form** - ещё одна зрелая, но менее популярная библиотека.

### Vue

- **VeeValidate** - самая распространённая для Vue, интегрируется со схемами.
- **FormKit** - формы «из коробки» с готовыми инпутами и валидацией.

| Библиотека       | Модель полей | Фреймворк      | Статус            |
| ---------------- | ------------ | -------------- | ----------------- |
| react-hook-form  | uncontrolled | React          | стандарт          |
| Formik           | controlled   | React          | legacy            |
| TanStack Form    | гибкая       | кросс-фреймворк| растущий          |
| VeeValidate      | -            | Vue            | стандарт для Vue  |

## Схемная валидация

Тренд - описывать форму **схемой** один раз и переиспользовать её и для валидации, и для типов. Библиотеки форм интегрируются со схемами через «резолверы».

### Zod

Де-факто стандарт. TypeScript-first: из схемы **выводится тип**, отдельно описывать его не нужно.

```ts
import { z } from 'zod';

const schema = z.object({
  email: z.string().email(),
  age: z.number().min(18),
});

type FormData = z.infer<typeof schema>; // тип выводится из схемы автоматически
```

```jsx
import { zodResolver } from '@hookform/resolvers/zod';
const { register } = useForm({ resolver: zodResolver(schema) }); // валидация из схемы
```

### Остальные

- **Yup** - предшественник Zod, объектные схемы; всё ещё популярен с Formik.
- **Valibot** - как Zod, но модульный и **очень лёгкий** (важно для бандла) - выбирают, когда критичен размер.
- **Joi** - мощный, но ориентирован на Node/бэкенд.
- **Стандарт Schema** - совместная инициатива (Zod/Valibot/ArkType) по единому интерфейсу схем, чтобы библиотеки могли принимать любую.

<b class="text-on-semi-light">Почему Zod так зашёл</b> - <span class="text-gray">Одна схема - источник истины: и валидация в рантайме, и статический тип через `z.infer`. Не нужно дублировать интерфейс и правила. Та же схема валидирует данные на клиенте, на сервере и в API.</span>

---

## Валидация на клиенте и на сервере

Критически важный принцип, который проверяют на собесе.

> Клиентская валидация - это **UX** (быстрая обратная связь), но **не безопасность**. Её можно обойти (отключить JS, послать запрос напрямую). Сервер **обязан** валидировать заново.

Схема Zod здесь удобна: один и тот же `schema.parse(data)` используется и в форме на клиенте, и в обработчике на сервере.

---

## Как выбрать

```
React, большие/частые формы        → react-hook-form + Zod
Vue                                → VeeValidate + Zod/Yup
Кросс-фреймворк, строгие типы       → TanStack Form
Критичен размер бандла              → Valibot вместо Zod
Legacy-проект                       → возможно Formik + Yup
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Зачем нужна библиотека для форм?</b>
<span class="text-gray">Она решает производительность (ререндеры), валидацию (правила, async, зависимости), сложные структуры (массивы полей) и UX (touched/dirty, момент показа ошибок) - то, что на голом useState быстро разрастается.</span>

<b class="text-on-semi-light">Почему react-hook-form быстрее Formik?</b>
<span class="text-gray">RHF использует uncontrolled-поля через рефы - значение в DOM, ввод не перерисовывает форму. Formik хранит значения в state (controlled), что вызывает ререндеры на каждый ввод.</span>

<b class="text-on-semi-light">Что такое схемная валидация и зачем Zod?</b>
<span class="text-gray">Описать форму схемой один раз и переиспользовать. Zod TS-first: из схемы выводится тип через `z.infer`, та же схема валидирует на клиенте и сервере. Нет дублирования типов и правил.</span>

<b class="text-on-semi-light">Чем Valibot отличается от Zod?</b>
<span class="text-gray">Тот же подход, но модульный и заметно легче по размеру бандла. Выбирают, когда вес критичен.</span>

<b class="text-on-semi-light">Достаточно ли клиентской валидации?</b>
<span class="text-gray">Нет. Клиентская - это UX, её можно обойти. Сервер обязан валидировать заново. Удобно переиспользовать одну Zod-схему на обеих сторонах.</span>

<b class="text-on-semi-light">Как сделать форму controlled или uncontrolled и что выбрать?</b>
<span class="text-gray">Controlled - значение в state (валидация на лету, но ререндеры); uncontrolled - в DOM через ref (быстрее). Для больших форм предпочитают uncontrolled - на нём построен RHF.</span>
