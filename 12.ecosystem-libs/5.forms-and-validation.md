# Формы и валидация

Зачем формам библиотеки и какие они: react-hook-form, TanStack Form, Formik, VeeValidate и FormKit для Vue, Actions в React 19 — и схемы валидации Zod, Valibot, ArkType с общим интерфейсом Standard Schema. Спрашивают, зачем библиотека для форм, почему react-hook-form быстрее и достаточно ли клиентской валидации. Глубже — сколько рендеров даёт контролируемая форма, почему число из поля приходит строкой и как одна схема работает и в форме, и на сервере.

::tldr
- **Форма — это состояние, валидация, ошибки, отправка и доступность,** и в большой форме каждая часть множится на десятки полей. Библиотеки берут это на себя.
- **Контролируемая форма на `useState` перерисовывается на каждый символ.** react-hook-form хранит значения в самих полях и перерисовывает форму, только когда меняется то, что на экране: ошибки, состояние отправки.
- **Схема валидации — один источник правды:** проверка, сообщения об ошибках, преобразование строк из полей в числа и тип TypeScript выводятся из неё. Одну схему запускают и в форме, и на сервере.
- **Standard Schema — общий интерфейс Zod, Valibot, ArkType и других.** Библиотеки форм и роутеры принимают любую совместимую схему, и смена библиотеки валидации не трогает формы.
- **Клиентская валидация — удобство, серверная — защита.** Запрос можно отправить в обход формы, поэтому сервер проверяет данные всегда.
::

---

## Зачем библиотека

Сквозной пример — оформление заказа: email, адрес, количество, промокод.

Что нужно форме, кроме значений полей:

- **валидация** — при отправке, при уходе с поля, при вводе; синхронная и асинхронная («email уже занят»);
- **ошибки** — у каждого поля, показ только после того, как пользователь дотронулся до поля;
- **состояние** — какие поля изменены, идёт ли отправка, сколько попыток;
- **доступность** — связь ошибки с полем через `aria-describedby`, фокус на первое поле с ошибкой;
- **сложная структура** — динамические списки полей, вложенные объекты, шаги мастера.

Для формы из двух полей это несколько строк. Для формы из тридцати — главный источник багов, поэтому её отдают библиотеке. Нативная валидация HTML тоже никуда не делась, о ней ниже, а сами элементы формы — в [Формах HTML](/content/html/forms).

## Контролируемая форма и её цена

Привычный способ в React — хранить значения в состоянии:

```jsx
function Checkout() {
  const [form, setForm] = useState({ email: '', address: '' });
  return (
    <form>
      <input value={form.email} onChange={(e) => setForm({ ...form, email: e.target.value })} />
      <input value={form.address} onChange={(e) => setForm({ ...form, address: e.target.value })} />
    </form>
  );
}
```

Каждый символ меняет состояние, и **вся форма** перерисовывается. В проверке ввод 12 символов дал 12 рендеров формы. Для двух полей это незаметно, для формы с тридцатью полями, условной логикой и тяжёлыми компонентами — заметные задержки при вводе. Как устроены контролируемые и неконтролируемые поля — в [Состоянии и событиях React](/content/reactjs/state-and-events).

## Библиотеки форм

### react-hook-form

```jsx
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';

function Checkout() {
  const { register, handleSubmit, formState: { errors } } = useForm({ resolver: zodResolver(Order) });
  return (
    <form onSubmit={handleSubmit(placeOrder)}>
      <input {...register('email')} aria-invalid={!!errors.email} />
      {errors.email && <p role="alert">{errors.email.message}</p>}
      <input {...register('address')} />
      <button>Оформить</button>
    </form>
  );
}
```

`register` подключает поле как **неконтролируемое**: значение живёт в DOM, а библиотека читает его через `ref` при проверке и отправке. Форма перерисовывается, только когда меняется то, что она показывает, и только если это состояние прочитано — `formState` устроен как прокси-подписка. В проверке ввод в поле не дал ни одного рендера, а отправка с ошибками — один-два рендера, чтобы показать сообщения. Корректные данные пришли в `handleSubmit` уже проверенными схемой.

Для контролируемых компонентов из UI-библиотек есть `Controller`, а для динамических списков — `useFieldArray`.

### Другие

| Библиотека | Особенность |
| --- | --- |
| TanStack Form | типобезопасная, без привязки к фреймворку: React, Vue, Solid, Angular, Svelte |
| Conform | постепенное улучшение: форма работает без JavaScript и с Actions и серверными функциями |
| Formik | исторически популярная, контролируемая модель, активного развития нет |
| VeeValidate | стандарт для Vue: композаблы `useForm` и `useField`, схемы через Standard Schema |
| FormKit | Vue: генерация форм по схеме, готовые поля и доступность |

### Actions в React 19

В React 19 у формы есть встроенный путь без библиотеки: `<form action={fn}>`, `useActionState` для результата и ожидания, `useFormStatus` для кнопки отправки. Это удобно для форм, которые отправляются на сервер и показывают результат, особенно с серверными функциями (подробно — в [RSC и React 19](/content/reactjs/rsc-and-react-19)). Для сложной клиентской логики — зависимых полей, мастеров, мгновенной валидации — библиотека форм остаётся удобнее, и они сочетаются: Conform и :term[react-hook-form]{def="библиотека форм для React на неуправляемых полях"} работают с Actions.

## Схемы валидации

Вместо проверок вручную в каждом обработчике — **схема**: описание формы данных, из которого выводится всё остальное.

```js
import { z } from 'zod';

export const Order = z.object({
  email: z.email('Некорректный email'),
  qty: z.coerce.number().int().min(1).max(10),
  promo: z.string().trim().toUpperCase().optional(),
});

export type Order = z.infer<typeof Order>;
```

Схема делает три работы сразу, все проверены:

- **проверяет** — `{ email: 'anna', qty: '0' }` дал ошибки по двум полям, а `z.flattenError` превратил их в объект «поле — сообщения» для показа под полями;
- **преобразует** — из `FormData` и `URLSearchParams` всё приходит строками, и `z.coerce.number()` превратил `'3'` в `3`, а `trim().toUpperCase()` превратил `' sale '` в `'SALE'`;
- **даёт тип** — `z.infer` выводит тип TypeScript, и он не расходится с проверкой (подробно — в [Асинхронности и DOM в TypeScript](/content/typescript/async-and-dom)).

### Библиотеки

Размер одной и той же схемы в бандле, по проверке:

| Библиотека | gzip | Особенность |
| --- | --- | --- |
| Zod | ≈21 КБ | цепочки методов, богатый набор, де-факто стандарт |
| Zod Mini | ≈5 КБ | тот же Zod функциями, которые вычищаются при сборке |
| Valibot | ≈1,5 КБ | отдельные функции и `pipe`, минимальный размер |
| ArkType | — | схемы строками в синтаксисе TypeScript, быстрая проверка |

Цепочка методов Zod удобна, но не позволяет бандлеру выбросить неиспользуемые проверки: все методы живут на одном объекте. Zod Mini и Valibot устроены отдельными функциями, и в бандл попадают только используемые. Для серверного кода размер неважен, для формы в браузере — заметен.

### Standard Schema

**Standard Schema** — общий интерфейс, который реализуют Zod, Valibot, :term[ArkType]{def="библиотека проверки данных с синтаксисом, похожим на типы TypeScript"} и другие: у схемы есть свойство `~standard` с функцией `validate`. Код, принимающий схему, не зависит от библиотеки:

```js
async function validate(schema, input) {
  const result = await schema['~standard'].validate(input);
  return result.issues ? { ok: false, issues: result.issues } : { ok: true, value: result.value };
}
```

В проверке одна и та же функция работала и со схемой Zod, и со схемой Valibot. Поэтому TanStack Form, :term[VeeValidate]{def="библиотека форм и валидации для Vue"}, TanStack Router, :term[tRPC]{def="типизированные вызовы сервера из клиента на TypeScript без отдельной схемы API"} и многие другие принимают любую совместимую схему, и выбор библиотеки валидации — локальное решение.

## Клиент и сервер

Клиентская валидация — **удобство**: мгновенная подсказка, меньше запросов с ошибками. Но запрос можно отправить в обход формы — через DevTools, `curl` или скрипт. Поэтому **сервер проверяет данные всегда**, а для доступа и цен — только сервер.

Удобнее всего, когда клиент и сервер используют **одну схему**: в монорепо или полном стеке на TypeScript её импортируют обе стороны (подробно — в [Сквозной типобезопасности](/content/modern-dev/end-to-end-typesafety)). Ошибки, которые знает только сервер — «email уже зарегистрирован», «товар закончился», — возвращают в форму и показывают у нужного поля так же, как клиентские.

### Нативная валидация

HTML умеет многое сам:

```html
<input name="email" type="email" required>
<input name="qty" type="number" min="1" max="10">
```

Браузер не отправит форму с пустым обязательным полем и покажет сообщение. В JavaScript доступно состояние каждого поля: в проверке `validity.valueMissing`, `typeMismatch` и `rangeOverflow` сработали ровно на своих случаях, а `form.checkValidity()` вернул `false`. Своя ошибка — например, ответ сервера — задаётся через `setCustomValidity`, и поле считается невалидным, пока её не сбросят пустой строкой.

Нативную валидацию часто отключают атрибутом `novalidate`, чтобы показывать свои сообщения, но её атрибуты оставляют: они дают правильную клавиатуру на мобильных и подсказки для автозаполнения и скринридеров.

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| простая форма, отправка на сервер | нативная валидация или Actions в React 19, схема на сервере |
| сложная форма в React: много полей, зависимости, мастер | react-hook-form или TanStack Form |
| форма с серверными функциями и работой без JavaScript | Conform |
| Vue | VeeValidate, для генерации форм — FormKit |
| схема в браузере, важен размер | Valibot или Zod Mini |
| схема на сервере или в общем пакете | Zod или Valibot — по вкусу, через Standard Schema |

---

## Красные флаги в ответе

- **«Клиентской валидации достаточно».** Запрос отправляют в обход формы, сервер проверяет всегда.
- **«Форма на `useState` — это нормально для любого размера».** Каждый символ перерисовывает всю форму.
- **«`qty` из формы — число».** Из `FormData` всё приходит строками, нужно явное преобразование.
- **«Валидация и тип TypeScript описываются отдельно».** Тип выводится из схемы, иначе они разойдутся.
- **«Смена Zod на Valibot потребует переписать формы».** Через Standard Schema формы не зависят от библиотеки схем.

## Как спрашивают на собеседовании

::question
Зачем нужна библиотека для форм?

#answer
Форма — это не только значения, но и валидация с разными моментами срабатывания, ошибки по полям, состояние изменений и отправки, динамические списки, доступность ошибок. В большой форме это множится на десятки полей, и библиотека берёт рутину на себя.

#more
Для простых форм хватает нативной валидации и Actions в React 19. Для сложных — react-hook-form, TanStack Form, в Vue — VeeValidate. Схему валидации подключают к библиотеке через резолвер или Standard Schema.
::

::question
Почему react-hook-form быстрее контролируемой формы?

#answer
Контролируемая форма хранит значения в состоянии и перерисовывается на каждый символ. react-hook-form подключает поля как неконтролируемые: значения живут в DOM, библиотека читает их через `ref`, а форма перерисовывается, только когда меняются показываемые ошибки или состояние.

#more
`formState` — прокси-подписка: компонент перерисуется от изменения поля состояния, только если его прочитал. Для контролируемых компонентов UI-библиотек есть `Controller`, но он возвращает рендеры этого поля. Formik использует контролируемую модель и медленнее на больших формах.
::

::question
Что такое схемная валидация и зачем Zod?

#answer
Описание формы данных схемой, из которой выводятся проверка, сообщения об ошибках, преобразование строк из полей в нужные типы и тип TypeScript. Одна схема — один источник правды для формы, сервера и типов.

#more
Zod — самая распространённая библиотека схем, Valibot и Zod Mini — маленькие альтернативы из отдельных функций, которые вычищаются при сборке. `z.coerce.number()` превращает строку из поля в число. Через Standard Schema формы и роутеры принимают любую совместимую схему.
::

::question
Чем Valibot отличается от Zod?

#answer
Zod строит схемы цепочками методов, и все проверки живут на одном объекте, поэтому бандлер не может выбросить неиспользуемые. Valibot — набор отдельных функций с `pipe`, и в бандл попадают только используемые.

#more
Одна и та же схема заняла около 21 КБ gzip в Zod, 5 КБ в Zod Mini и 1,5 КБ в Valibot. Для серверного кода разница не важна, для формы в браузере заметна. Оба реализуют Standard Schema и взаимозаменяемы для библиотек форм.
::

::question
Достаточно ли клиентской валидации?

#answer
Нет. Клиентская валидация — удобство: быстрая обратная связь и меньше запросов с ошибками. Запрос можно отправить в обход формы, поэтому сервер проверяет данные всегда.

#more
Удобно использовать одну схему на клиенте и сервере. Ошибки, известные только серверу, — занятый email, закончившийся товар, — возвращают и показывают у нужного поля. Права, цены и лимиты проверяются только на сервере.
::

::question
Что умеет нативная валидация HTML?

#answer
Атрибуты `required`, `type="email"`, `min`, `max`, `pattern`, `minlength` браузер проверяет сам и не отправляет форму с ошибками. В JavaScript доступны `validity`, `checkValidity()` и `setCustomValidity()` для своих ошибок.

#more
Своё сообщение держится, пока его не сбросят пустой строкой. Нативные сообщения часто заменяют своими через `novalidate`, но атрибуты оставляют: они дают правильную клавиатуру на мобильных и подсказки для автозаполнения.
::

## Практика

::practice{title="Форма тормозит при вводе"}
Анкета из сорока полей заметно отстаёт при наборе текста. Все поля в одном `useState`, а форма рендерит тяжёлый блок предпросмотра.

#solution
Каждый символ меняет общее состояние и перерисовывает всю форму вместе с предпросмотром — в проверке 12 символов дали 12 рендеров формы. Переход на неконтролируемые поля:

```jsx
const { register, handleSubmit, control } = useForm({ resolver: zodResolver(Profile) });

<input {...register('firstName')} />
<input {...register('lastName')} />
<Preview control={control} />   {/* подписка только внутри предпросмотра */}
```

```jsx
function Preview({ control }) {
  const name = useWatch({ control, name: ['firstName', 'lastName'] });
  return <ExpensiveCard name={name.join(' ')} />;
}
```

Ввод больше не перерисовывает форму, а предпросмотр подписан только на нужные поля через `useWatch`. В проверке react-hook-form не дал ни одного рендера формы при вводе.
::

::practice{title="Количество приходит строкой"}
Обработчик заказа сравнивает количество с остатком, который тоже лежит в форме скрытым полем, и заказ на 10 штук проходит при остатке 9:

```js
const data = Object.fromEntries(formData);   // { qty: '10', stock: '9' }
if (data.qty > data.stock) throw new Error('Недостаточно товара');
```

#solution
Из `FormData` все значения — строки, и `'10' > '9'` — `false`: строки сравниваются посимвольно, а `'1'` меньше `'9'`. Данные формы разбирают схемой с явным преобразованием, а остаток берут на сервере, а не из формы:

```js
const Order = z.object({
  email: z.email(),
  qty: z.coerce.number().int().min(1),
});

const { qty } = Order.parse(Object.fromEntries(formData));
const stock = await db.stock(productId);   // число из базы, а не из формы
if (qty > stock) throw new Error('Недостаточно товара');
```

`z.coerce.number()` превращает строку в число, а `.int().min(1)` отсекает `'1.5'` и `'-3'`. Остаток из скрытого поля к тому же можно подделать — такие значения берут на сервере. Та же схема подходит для формы на клиенте. В проверке `'3'` из `URLSearchParams` стал числом `3`, а `'0'` дал ошибку по полю `qty`.
::
