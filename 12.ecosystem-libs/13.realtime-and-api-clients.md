# Реалтайм и API-клиенты

Какие библиотеки стоят между фронтендом и бэкендом: клиенты из OpenAPI-схемы для REST, GraphQL-клиенты от `graphql-request` до Apollo и Relay, tRPC для TypeScript с обеих сторон, Socket.io и готовые сервисы для живых обновлений. Спрашивают, как получить типы для REST API, что даёт tRPC и чем Socket.io отличается от WebSocket. Глубже — почему GraphQL-ошибка приходит со статусом 200, почему `openapi-fetch` не бросает на 404 и почему обычный WebSocket не подключится к серверу Socket.io.

::tldr
- **Протоколы — в главе про сеть,** здесь библиотеки поверх них: REST, GraphQL, RPC и реалтайм.
- **Типы для REST дают генерацией из OpenAPI:** openapi-typescript строит типы путей и ответов, а openapi-fetch или orval по ним проверяют пути, параметры и поля при компиляции.
- **GraphQL-клиенты различаются кешем:** `graphql-request` только отправляет запрос, urql и Apollo добавляют кеш, Relay — нормализованный кеш и фрагменты на уровне компилятора. Ошибки GraphQL приходят в теле ответа, часто со статусом 200.
- **tRPC выводит типы клиента из серверного роутера без схемы и генерации,** но только когда фронтенд и бэкенд на TypeScript в одном репозитории.
- **Socket.io — свой протокол поверх WebSocket:** переподключение, буфер событий, комнаты, запасной long-polling. Цена — Socket.io нужен и на сервере.
::

## Три стиля API

Сквозной пример — магазин: карточка товара, страница заказа со статусом оплаты, который меняется на сервере, и чат с поддержкой.

| Стиль | Суть | Клиенты |
| --- | --- | --- |
| REST | ресурсы и HTTP-методы | `fetch`, ky, ofetch, клиенты из OpenAPI |
| GraphQL | один адрес, клиент выбирает поля | `graphql-request`, urql, Apollo, Relay |
| RPC | вызов серверных функций | tRPC, gRPC-Web, Connect |

Сами протоколы разобраны в главе про сеть: [REST](/content/network-api/rest), [GraphQL](/content/network-api/graphql), [Реалтайм](/content/network-api/realtime). HTTP-клиенты вроде ky и ofetch — в [Утилитах](/content/ecosystem-libs/utility-libraries), кеш серверных данных — в [Состоянии и данных](/content/ecosystem-libs/state-and-data-libraries).

## REST с типами: OpenAPI

У бэкенда часто есть **OpenAPI-схема** — описание путей, параметров и ответов в JSON или YAML. Вручную описывать те же типы на фронтенде — значит, что они разойдутся при первом изменении API.

### Генерация типов

**openapi-typescript** строит из схемы TypeScript-типы:

```bash
npx openapi-typescript https://api.shop.example/openapi.json -o src/api/schema.d.ts
```

В проверке из схемы с путём `/products/{id}` получился тип `paths` с этим путём, параметром `id: number` и ответами 200 и 404.

### Клиент по типам

**openapi-fetch** — тонкая обёртка над `fetch`, которая берёт эти типы:

```ts
import createClient from 'openapi-fetch';
import type { paths } from './schema';

const api = createClient<paths>({ baseUrl: '/api' });

const { data, error } = await api.GET('/products/{id}', { params: { path: { id: 1 } } });
```

При компиляции ловятся опечатка в пути (`/product/{id}`), в поле ответа (`data.titel`), забытый или неправильного типа параметр — в проверке все четыре случая дали ошибки `tsc`.

Клиент **не бросает** исключение на 4xx и 5xx: в проверке ответ 404 вернул `data: undefined` и `error: { message: 'Товар не найден' }` с типом из схемы. Ошибку разбирают как обычное значение, а не через `try`.

Другие генераторы:

- **orval**, **Kubb**, **@hey-api/openapi-ts** — генерируют не только типы, но и функции запросов, хуки TanStack Query и схемы zod для проверки ответов;
- типы из схемы проверяют только код фронтенда; что сервер действительно отвечает по схеме, проверяют на рантайме схемами zod или valibot (подробно — в [Формах и валидации](/content/ecosystem-libs/forms-and-validation)).

## GraphQL-клиенты

GraphQL-запрос — обычно `POST` с телом `{ query, variables }` на один адрес. Клиенты отличаются тем, что делают сверх отправки:

| Клиент | Что даёт |
| --- | --- |
| `graphql-request` | только запрос и ответ, кеш — у TanStack Query |
| urql | документный кеш по умолчанию, нормализованный через Graphcache, плагины-exchanges |
| Apollo Client | нормализованный кеш, оптимистичные обновления, подписки, инструменты |
| Relay | нормализованный кеш, фрагменты у компонентов, компилятор запросов |

Нормализованный кеш против документного разобран в [Состоянии и данных](/content/ecosystem-libs/state-and-data-libraries). Типы запросов генерирует **GraphQL Code Generator** или `gql.tada`, который выводит их из схемы без генерации.

### Ошибки приходят в теле

GraphQL может вернуть часть данных и ошибки одновременно. Если упал резолвер отзывов, название товара всё равно придёт:

```json
{
  "data": { "product": { "title": "Пуэр", "reviews": null } },
  "errors": [{ "message": "Сервис отзывов недоступен", "path": ["product", "reviews"] }]
}
```

В проверке такой ответ шёл со статусом 200, и `fetch` считал его успешным: `response.ok === true`. Проверка `if (!response.ok)` ошибку не увидит — смотреть нужно поле `errors`.

Библиотеки решают это по-разному. `graphql-request` в проверке бросил `ClientError` при любом `errors`, даже с частичными данными, — данные остаются в `error.response.data`. В Apollo поведение задаёт `errorPolicy`: отбросить данные, вернуть их вместе с ошибками или проигнорировать ошибки.

## tRPC

**tRPC** убирает схему и генерацию: клиент получает тип серверного роутера и вызывает процедуры как функции.

```ts
// сервер
const appRouter = t.router({
  product: t.router({
    byId: t.procedure
      .input(z.object({ id: z.number().int() }))
      .query(({ input }) => db.product(input.id)),
  }),
});
export type AppRouter = typeof appRouter;

// клиент
const trpc = createTRPCClient<AppRouter>({ links: [httpBatchLink({ url: '/trpc' })] });
const product = await trpc.product.byId.query({ id: 1 });
```

Импортируется только **тип** `AppRouter`, серверный код в бандл не попадает. В проверке `p.titel` и `{ id: '1' }` дали ошибки компиляции без единого сгенерированного файла.

Что ещё в проверке:

- **пакетирование:** с `httpBatchLink` два параллельных вызова ушли одним HTTP-запросом, с `httpLink` — двумя;
- **проверка входа:** `{ id: 1.5 }` отклонил zod на сервере, клиент получил `TRPCClientError` с кодом `BAD_REQUEST`;
- **ошибки:** `TRPCError` с кодом `NOT_FOUND` пришёл со статусом 404.

Ограничение — фронтенд и бэкенд на TypeScript и в одном репозитории или с общим пакетом типов. Для публичного API, мобильных клиентов и бэкенда на другом языке нужен контракт, который не зависит от TypeScript, — OpenAPI или GraphQL. Похожую идею для любых языков дают gRPC-Web и Connect со схемой Protobuf.

## Реалтайм-библиотеки

Транспорты — опрос, long-polling, SSE, WebSocket — разобраны в [Реалтайме](/content/network-api/realtime). Коротко: SSE — односторонний поток от сервера поверх HTTP, WebSocket — двусторонний канал. Здесь — что добавляют библиотеки.

### Socket.io

**Socket.io** — библиотека и протокол поверх WebSocket. В проверке сырой WebSocket к адресу `/socket.io/` получил такие кадры:

```text
0{"sid":"…","upgrades":[],…}     открытие соединения Engine.IO
40{"sid":"…"}                    подключение к пространству имён
42["welcome","hi"]               событие welcome с данными
```

Обычный WebSocket к серверу Socket.io без этого протокола не подключился. Поэтому Socket.io нужен с обеих сторон.

Что он даёт, и всё это было в проверке:

- **переподключение:** после обрыва транспорта клиент подключился снова сам;
- **буфер:** событие, отправленное без связи, сервер получил после восстановления;
- **комнаты:** `io.to('order:42').emit(...)` получил только клиент в комнате;
- **запасной транспорт:** с `transports: ['polling']` клиент подключился через HTTP long-polling — для сетей, где WebSocket режут прокси.

Нативный WebSocket всего этого не делает: переподключение с задержкой, повторную отправку и подписки пишут сами (пример — в главе про сеть).

### SSE и потоковые ответы

`EventSource` умеет только `GET` без тела и заголовков, а потоковые ответы — например, ответ языковой модели — обычно требуют `POST` с запросом и токеном. Поэтому такие ответы читают через `fetch` и `response.body` или библиотеки поверх него — `@microsoft/fetch-event-source`, SDK провайдеров.

### Готовые сервисы

Когда не хочется держать свои серверы соединений:

- **Pusher**, **Ably** — управляемые каналы публикации и подписки;
- **Supabase Realtime**, **Firebase** — изменения базы данных в реальном времени;
- **Liveblocks**, **Yjs** с провайдерами — совместное редактирование: присутствие, курсоры, слияние правок через CRDT.

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| REST с OpenAPI-схемой | openapi-typescript и openapi-fetch, или orval с хуками |
| GraphQL без сложного кеша | `graphql-request` и TanStack Query |
| GraphQL, одни сущности во многих местах | Apollo, urql с Graphcache, Relay |
| TypeScript с обеих сторон, один репозиторий | tRPC |
| поток событий от сервера | SSE, `fetch` с потоком для `POST` |
| чат, двусторонний обмен, комнаты | Socket.io или WebSocket со своей обвязкой |
| без своей инфраструктуры | Pusher, Ably, Supabase Realtime |
| совместное редактирование | Yjs, Liveblocks |

---

## Красные флаги в ответе

- **«Типы для API опишу руками».** Они разойдутся с бэкендом — типы генерируют из схемы или выводят через tRPC.
- **«Сгенерированные типы гарантируют, что сервер так ответит».** Они проверяют только код фронтенда, на рантайме нужна схема.
- **«Ошибку GraphQL поймаю через `response.ok`».** Ошибки приходят в теле, часто со статусом 200.
- **«tRPC подойдёт для публичного API».** Он завязан на тип TypeScript-роутера, публичному API нужен контракт вроде OpenAPI.
- **«Socket.io — это и есть WebSocket».** Это свой протокол поверх него, обычный WebSocket к серверу Socket.io не подключится.
- **«Для стриминга ответа модели возьму `EventSource`».** Он не умеет `POST` и заголовки, нужен `fetch` с потоком.

## Как спрашивают на собеседовании

::question
Как получить типобезопасность для REST API?

#answer
Сгенерировать типы из OpenAPI-схемы бэкенда — openapi-typescript — и использовать клиент, который их понимает: openapi-fetch или сгенерированный orval. Тогда опечатки в путях, параметрах и полях ответа ловит компилятор.

#more
Генераторы вроде orval и Kubb создают ещё функции запросов, хуки TanStack Query и схемы zod. Типы проверяют только код фронтенда; соответствие ответа сервера схеме проверяют на рантайме. Генерацию запускают в CI, чтобы изменение API сразу ломало сборку.
::

::question
Что такое tRPC и когда он уместен?

#answer
RPC-библиотека для TypeScript: клиент импортирует тип серверного роутера и вызывает процедуры как функции, а типы аргументов и результатов выводятся без схемы и генерации. Уместен, когда фронтенд и бэкенд на TypeScript в одном репозитории.

#more
Вход проверяет схема zod на сервере, вызовы пакетируются в один HTTP-запрос через `httpBatchLink`. Для публичного API, мобильных клиентов и бэкенда на другом языке нужен независимый контракт — OpenAPI, GraphQL или Protobuf с Connect.
::

::question
Заменяет ли GraphQL-клиент TanStack Query?

#answer
Apollo, urql и Relay кешируют сами и закрывают слой серверных данных целиком — TanStack Query рядом не нужен. С `graphql-request`, который только отправляет запрос, кешированием занимается TanStack Query.

#more
Выбор — между нормализованным кешем Apollo или Relay, где изменение сущности видят все запросы, и документным кешем TanStack Query с инвалидацией по ключам. Нормализованный окупается, когда одни сущности показаны во многих местах.
::

::question
Почему GraphQL-ошибку не видно через `response.ok`?

#answer
GraphQL возвращает ошибки в поле `errors` тела, часто со статусом 200, и может прислать частичные данные вместе с ошибками. `fetch` считает такой ответ успешным.

#more
Клиенты решают это по-своему: `graphql-request` бросает `ClientError` при любых ошибках, а частичные данные кладёт в `error.response.data`; Apollo управляет этим через `errorPolicy`. Ошибки сети и разбора запроса при этом могут прийти и с кодами 4xx и 5xx.
::

::question
Что даёт Socket.io поверх нативного WebSocket?

#answer
Переподключение, буфер событий на время обрыва, комнаты и пространства имён, именованные события и запасной транспорт через long-polling. Цена — собственный протокол, поэтому Socket.io нужен и на сервере.

#more
На проводе это кадры вида `42["event",data]`, и обычный WebSocket к серверу Socket.io не подключится. Если сервер не на Node.js или нужен стандартный протокол, берут нативный WebSocket и пишут обвязку сами или используют готовый сервис вроде Ably.
::

::question
Когда выбрать WebSocket, а когда SSE?

#answer
SSE — для одностороннего потока от сервера: уведомления, лента, прогресс, потоковые ответы. WebSocket — для двустороннего обмена: чат, игры, совместное редактирование.

#more
SSE работает поверх обычного HTTP и переподключается сам, но `EventSource` не умеет `POST` и заголовки, поэтому потоковые ответы моделей читают через `fetch`. Подробно о транспортах — в главе про сеть.
::

## Практика

::practice{title="Ошибка, которую никто не видит"}
Страница товара показывает название, но блок отзывов пустой, а в логах ошибок фронтенда тишина. Код:

```js
const response = await fetch('/graphql', { method: 'POST', body: JSON.stringify({ query }) });
if (!response.ok) throw new Error('Request failed');
const { data } = await response.json();
render(data);
```

#solution
Сервер вернул частичные данные и ошибку со статусом 200: `reviews: null` и `errors` с путём `['product', 'reviews']`. Проверка `response.ok` её не замечает, а поле `errors` никто не читает:

```js
const { data, errors } = await response.json();
if (errors?.length) report(errors);   // в мониторинг, с путём поля
render(data);                          // частичные данные можно показать
```

В проверке ответ шёл со статусом 200 и `response.ok === true`. Готовые клиенты делают это сами: `graphql-request` бросает `ClientError` с данными в `error.response.data`, Apollo — по `errorPolicy`.
::

::practice{title="Фронтенд разошёлся с API"}
Бэкенд переименовал поле `price` в `amount`. Фронтенд собрался без ошибок, а на проде в карточке «undefined ₽». Типы ответов описаны вручную в `types.ts`.

#solution
Ручные типы ничего не знают об изменении. Типы генерируют из схемы бэкенда и запускают генерацию в CI:

```bash
npx openapi-typescript ./openapi.json -o src/api/schema.d.ts
```

```ts
const api = createClient<paths>({ baseUrl: '/api' });
const { data } = await api.GET('/products/{id}', { params: { path: { id } } });
data?.price;   // после обновления схемы — ошибка компиляции
```

В проверке опечатка в поле ответа, пути и параметре давала ошибку `tsc`. Если бэкенд может ответить не по схеме, ответ дополнительно проверяют схемой zod — типы на рантайме не работают.
::

::practice{title="Сообщения теряются при плохой связи"}
Чат поддержки на нативном WebSocket. В метро сообщения пользователя пропадают: `send` вызывается, но до сервера ничего не доходит.

#solution
После обрыва `WebSocket` переходит в `CLOSED`, а `send` в закрытый сокет данные не отправит. Нужны переподключение и очередь неотправленного. Socket.io делает это сам:

```js
const socket = io('/support', { reconnectionDelay: 500 });
socket.emit('message', text);   // без связи событие ждёт в буфере
```

В проверке событие, отправленное во время обрыва, сервер получил после переподключения. На нативном WebSocket то же пишут сами: очередь, повторное подключение с растущей задержкой и подтверждения от сервера, чтобы не терять и не дублировать сообщения.
::
