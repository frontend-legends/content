# Реалтайм и API-клиенты

Как фронтенд общается с бэкендом - через REST, GraphQL или RPC - и как получает **живые** обновления (чат, нотификации, presence). Под каждый протокол есть свои клиенты, а под реалтайм - свой набор транспортов.

> Сами протоколы (HTTP, WebSocket, REST vs GraphQL) разбираются в главе [Network & API](/content/network-api). Здесь - **библиотеки и клиенты** поверх них.

---

## Три парадигмы API

| Парадигма | Суть                          | Клиенты                         |
| --------- | ----------------------------- | ------------------------------- |
| **REST**  | ресурсы и HTTP-методы          | fetch, axios, ky, codegen       |
| **GraphQL** | один эндпоинт, запрос полей   | Apollo, urql, Relay             |
| **RPC**   | вызов функций                  | tRPC                            |

---

## REST-клиенты

Базовые HTTP-клиенты (`fetch`, `axios`, `ky`) разобраны в [утилитах](/content/ecosystem-libs/utility-libraries). Для REST с типами полезен **кодген из OpenAPI**:

- **openapi-typescript** - генерирует TS-типы из OpenAPI-схемы.
- **orval** / **openapi-codegen** - генерируют типизированные клиенты и даже хуки React Query прямо из спецификации.

<b class="text-on-semi-light">Зачем кодген</b> - <span class="text-gray">Если у бэкенда есть OpenAPI-схема, типы клиента генерируются из неё автоматически - фронт и бэк не расходятся, а ошибки в полях ловятся компилятором. Это «типобезопасность» для REST без ручного описания типов.</span>

---

## GraphQL-клиенты

GraphQL даёт запрашивать ровно нужные поля одним запросом. Клиенты различаются «тяжестью» и кэшем:

- **Apollo Client** - полнофункциональный: **нормализованный кэш**, оптимистичные обновления, подписки. Мощный, но тяжёлый.
- **urql** - легче и модульнее Apollo, расширяется плагинами (exchanges).
- **Relay** - клиент Meta, максимально оптимизирован, но требует строгой схемы и дисциплины; высокий порог.
- **graphql-request** - минималистичный: просто шлёт запрос, без кэша (часто в паре с TanStack Query).
- **GraphQL Code Generator** - генерирует типы и хуки из схемы и запросов.

> GraphQL-клиент часто **совмещает** роль data-fetching-слоя (кэш) - тогда отдельный TanStack Query не нужен. Либо берут лёгкий `graphql-request` + Query.

## tRPC

**tRPC** - типобезопасный RPC для TypeScript-монорепо: вызываешь серверные процедуры как обычные функции, и **типы аргументов и результата выводятся end-to-end без кодгена и без схемы**.

```ts
// сервер определяет процедуры; клиент вызывает их типобезопасно
const user = await trpc.user.byId.query({ id: 1 }); // тип user известен из сервера
```

<b class="text-on-semi-light">Когда tRPC</b> - <span class="text-gray">Фулстек на TypeScript в одной кодовой базе (Next.js, монорепо), где фронт и бэк твои. Даёт «GraphQL-уровень» типобезопасности без схемы и генерации. Не подходит, если API публичный или бэкенд не на TS.</span>

## Реалтайм-транспорты

Когда нужны **живые** обновления (а не запрос-ответ), выбирают транспорт по характеру данных.

| Транспорт      | Направление       | Когда                              |
| -------------- | ----------------- | ---------------------------------- |
| **Polling**    | клиент опрашивает | простейший фолбэк, редкие обновления |
| **SSE**        | сервер → клиент   | односторонний поток (лента, нотификации) |
| **WebSocket**  | двусторонний      | чат, игры, совместное редактирование |
| **WebTransport** | двусторонний (новый) | низкая задержка поверх HTTP/3   |

### WebSocket и Socket.io

`WebSocket` - нативный двусторонний канал. **Socket.io** - библиотека поверх него: авто-переподключение, комнаты, фолбэк на long-polling, события. Берут, когда нужны надёжность и удобный API; цена - свой протокол (нужен Socket.io и на сервере).

### SSE

**Server-Sent Events** (`EventSource`) - простой **односторонний** поток с сервера: нотификации, live-лента, прогресс. Легче WebSocket, работает поверх обычного HTTP, авто-переподключение из коробки. Сейчас популярен для **стриминга ответов LLM**.

### Hosted-решения

Когда не хочется поднимать realtime-инфраструктуру:

- **Pusher**, **Ably** - managed pub/sub.
- **Supabase Realtime** - реалтайм поверх Postgres.
- **PartyKit** - реалтайм на edge.
- **Liveblocks**, **Yjs** - совместное редактирование (presence, CRDT).

---

## Как выбрать

```
Запрос-ответ, REST                  → fetch/axios (+ кодген из OpenAPI)
Гибкие запросы полей                → GraphQL (Apollo/urql)
Фулстек на TS, свои фронт+бэк        → tRPC
Односторонний поток (нотификации, LLM) → SSE
Двусторонний (чат, игры)            → WebSocket / Socket.io
Не хочу свою инфру                  → Pusher / Ably / Supabase
Совместное редактирование           → Liveblocks / Yjs
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Когда выбрать WebSocket, а когда SSE?</b>
<span class="text-gray">WebSocket - двусторонний (чат, игры, совместное редактирование). SSE - односторонний поток сервер→клиент (нотификации, лента, стриминг LLM): проще, поверх HTTP, с авто-переподключением.</span>

<b class="text-on-semi-light">Что даёт Socket.io поверх нативного WebSocket?</b>
<span class="text-gray">Авто-переподключение, комнаты, события, фолбэк на long-polling. Цена - собственный протокол, нужен Socket.io и на сервере.</span>

<b class="text-on-semi-light">Что такое tRPC и когда он уместен?</b>
<span class="text-gray">Типобезопасный RPC для TS-монорепо: серверные процедуры вызываются как функции с end-to-end типами без схемы и кодгена. Подходит, когда фронт и бэк твои на TypeScript; не для публичного API.</span>

<b class="text-on-semi-light">Заменяет ли GraphQL-клиент TanStack Query?</b>
<span class="text-gray">Apollo/urql имеют свой кэш и часто закрывают слой данных целиком. С лёгким graphql-request кэширование берёт на себя Query.</span>

<b class="text-on-semi-light">Как получить типобезопасность для REST API?</b>
<span class="text-gray">Кодген из OpenAPI-схемы (openapi-typescript, orval) - типы и клиент генерируются из спецификации, фронт и бэк не расходятся.</span>
