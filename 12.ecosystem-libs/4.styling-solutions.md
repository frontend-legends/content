# Решения для стилизации

Способов стилизовать компоненты во фронтенде - десяток, и выбор между ними - вечный спор. Понимать **категории** (а не конкретные библиотеки) и их компромиссы по производительности, DX и совместимости с серверными компонентами - то, что отличает зрелого инженера.

> Основы каскада, специфичности и современного CSS - в главе [CSS](/content/css). Здесь - именно **инструменты и подходы** к стилизации в компонентном мире.

---

## Категории

| Подход                  | Где живут стили        | Примеры                          |
| ----------------------- | ---------------------- | -------------------------------- |
| **Обычный CSS / Sass**  | глобальные `.css`      | BEM, Sass, PostCSS               |
| **CSS Modules**         | локальные `.module.css`| встроено в Vite/Next             |
| **Utility-first**       | классы в разметке      | Tailwind, UnoCSS                 |
| **CSS-in-JS (runtime)** | JS-объекты в рантайме  | styled-components, Emotion       |
| **CSS-in-JS (zero-runtime)** | JS → статический CSS при сборке | vanilla-extract, Panda, Linaria |

---

## Обычный CSS и Sass

Базовый вариант: глобальные стили с методологией именования. Главная проблема - **глобальная область видимости**: класс из одного места случайно затронет другое.

- **БЭМ** (`block__element--modifier`) - конвенция именования против коллизий.
- **Sass/SCSS** - вложенность, переменные, миксины (хотя нативный CSS уже многое из этого умеет: вложенность, `var()`, `@layer`).
- **PostCSS** - постобработка CSS плагинами (автопрефиксы, современный синтаксис).

> Обычный CSS не устарел - для небольших проектов и контентных сайтов он проще любого инструмента. Проблемы начинаются на масштабе, где трудно гарантировать изоляцию.

---

## CSS Modules

`.module.css`-файлы, в которых имена классов **локализуются** при сборке - превращаются в уникальные (`Button_root_x7f3`). Решает проблему глобальной области без рантайма.

```css
/* Button.module.css */
.root { padding: 8px 16px; }
```

```jsx
import styles from './Button.module.css';
<button className={styles.root}>OK</button>;
```

<b class="text-on-semi-light">Плюсы и минусы</b> - <span class="text-gray">Плюс - изоляция, нулевой рантайм, обычный CSS (легко мигрировать). Поддерживается из коробки в Vite и Next. Минус - динамические стили от пропсов неудобны (нужно переключать классы), нет «темизации» из коробки. Надёжный, скучный, проверенный выбор.</span>

---

## Utility-first: Tailwind

**Tailwind** - доминирующий подход 2024–2026. Вместо своих классов ты собираешь стиль из готовых **утилит** прямо в разметке.

```jsx
<button className="px-4 py-2 rounded bg-blue-600 text-white hover:bg-blue-700">
  OK
</button>
```

<b class="text-on-semi-light">Как работает</b> - <span class="text-gray">Tailwind сканирует разметку и генерирует **только используемые** классы - финальный CSS маленький независимо от размера дизайн-системы. Нет рантайма, нет придумывания имён, единые токены (отступы, цвета) из конфига. **Tailwind v4** (движок Oxide) ускорил сборку и перешёл на CSS-first конфигурацию (`@theme` в CSS вместо JS-конфига).</span>

**Плюсы:** скорость разработки, консистентность через токены, маленький бандл, нет мёртвого CSS, отлично с RSC.
**Минусы:** «грязная» разметка (длинные строки классов), порог входа (надо выучить утилиты), сложные селекторы неудобны.

> Повторяющиеся наборы утилит выносят в компоненты (а не в `@apply`, которым злоупотребляют). Tailwind хорошо дружит с headless-библиотеками - отсюда популярность shadcn/ui.

**UnoCSS** - альтернативный atomic-движок: тот же подход, но настраиваемый и часто быстрее, с режимом «on-demand».

---

## CSS-in-JS: runtime

**styled-components** и **Emotion** позволяют писать стили в JS, привязывая их к пропсам.

```jsx
import styled from 'styled-components';

const Button = styled.button`
  padding: 8px 16px;
  background: ${(props) => (props.primary ? 'blue' : 'gray')};
`;
```

<b class="text-on-semi-light">Цена рантайма</b> - <span class="text-gray">Стили вычисляются и вставляются **в браузере во время рендера** - это нагрузка на исполнение и проблема с гидратацией. Главное: runtime CSS-in-JS **не работает в React Server Components** (нужен клиент). Поэтому индустрия отходит от него - **styled-components в режиме поддержки** (активная разработка свёрнута), а команды мигрируют на Tailwind или zero-runtime.</span>

Плюсы остаются: динамическая темизация, стили рядом с компонентом, полный JS. Но для нового кода с RSC это уже не первый выбор.

---

## CSS-in-JS: zero-runtime

Тот же DX «стили в JS», но извлечение в **статический CSS на этапе сборки** - без рантайма и совместимо с RSC.

- **vanilla-extract** - стили в `.css.ts`, типобезопасные, извлекаются в обычный CSS.
- **Panda CSS** - от создателей Chakra; рецепты, токены, zero-runtime.
- **Linaria** / **Compiled** - извлекают шаблонные литералы в статический CSS.

```ts
// styles.css.ts (vanilla-extract) - типобезопасно, компилируется в статический CSS
import { style } from '@vanilla-extract/css';
export const button = style({ padding: '8px 16px', background: 'blue' });
```

> Это «лучшее из двух миров»: эргономика CSS-in-JS без рантайм-стоимости и без конфликта с серверными компонентами. Растущий выбор для дизайн-систем.

---

## Сдвиг из-за RSC

Главный нарратив последних лет: **React Server Components сломали runtime CSS-in-JS**. Серверный компонент не выполняет JS в браузере, а значит, не может вычислить стили в рантайме.

```
Раньше:   styled-components / Emotion - стандарт
Сейчас:   Tailwind или zero-runtime (vanilla-extract / Panda) - для RSC-совместимости
```

<b class="text-on-semi-light">Вывод для собеса</b> - <span class="text-gray">Если проект на Next.js App Router / RSC - runtime CSS-in-JS избегают. Безопасные выборы: Tailwind, CSS Modules, zero-runtime CSS-in-JS.</span>

---

## Как выбрать

```
Серверные компоненты (Next App Router)   → Tailwind / CSS Modules / zero-runtime
Быстрая разработка, единые токены          → Tailwind
Простота и изоляция без рантайма           → CSS Modules
Своя дизайн-система с типобезопасностью     → vanilla-extract / Panda
Маленький сайт                             → обычный CSS/Sass
Legacy на styled-components                 → поддерживать, новое не писать
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Какие есть подходы к стилизации в компонентном фронтенде?</b>
<span class="text-gray">Обычный CSS/Sass, CSS Modules (локальные классы), utility-first (Tailwind), runtime CSS-in-JS (styled-components/Emotion) и zero-runtime CSS-in-JS (vanilla-extract/Panda).</span>

<b class="text-on-semi-light">Что решают CSS Modules?</b>
<span class="text-gray">Глобальную область видимости: локализуют имена классов при сборке, давая изоляцию без рантайма. Обычный CSS, легко мигрировать.</span>

<b class="text-on-semi-light">В чём плюсы и минусы Tailwind?</b>
<span class="text-gray">Плюсы: скорость, консистентность через токены, маленький бандл (генерируются только используемые классы), нет рантайма, дружит с RSC. Минусы: длинные строки классов и порог входа.</span>

<b class="text-on-semi-light">Почему отходят от runtime CSS-in-JS?</b>
<span class="text-gray">Стили вычисляются в браузере (нагрузка, гидратация) и не работают в серверных компонентах. styled-components в режиме поддержки; мигрируют на Tailwind/zero-runtime.</span>

<b class="text-on-semi-light">Что такое zero-runtime CSS-in-JS?</b>
<span class="text-gray">Стили пишутся в JS, но извлекаются в статический CSS при сборке (vanilla-extract, Panda, Linaria) - эргономика CSS-in-JS без рантайма и совместимо с RSC.</span>

<b class="text-on-semi-light">Как RSC повлияли на выбор стилизации?</b>
<span class="text-gray">Серверные компоненты не выполняют JS в браузере, поэтому runtime CSS-in-JS не работает. Это сделало Tailwind, CSS Modules и zero-runtime безопасными выборами.</span>

<b class="text-on-semi-light">Когда обычный CSS лучше инструмента?</b>
<span class="text-gray">Для маленьких сайтов и контентных страниц - меньше зависимостей и сложности. Проблемы изоляции проявляются только на масштабе.</span>
