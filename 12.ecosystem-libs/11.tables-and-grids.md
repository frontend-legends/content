# Таблицы и гриды

Как показывать много табличных данных: headless-таблицы вроде TanStack Table против полных гридов вроде AG Grid, сортировка, фильтрация и страницы на клиенте или на сервере, виртуализация длинных списков и доступность. Спрашивают, чем headless-таблица отличается от грида, что такое виртуализация и когда обработку данных переносить на сервер. Глубже — почему виртуализированную таблицу не находит Ctrl+F и скринридер, что ломает виртуализацию и сколько строк реально в DOM.

::tldr
- **Таблица сложнее, чем выглядит:** сортировка по нескольким колонкам, фильтры, страницы, выбор строк, закрепление и изменение ширины колонок, группировка, редактирование ячеек, клавиатура. Отсюда две категории библиотек.
- **Headless-таблица считает модель строк, а разметку пишешь ты:** TanStack Table по данным и состоянию отдаёт отсортированные, отфильтрованные строки текущей страницы. Полный грид — AG Grid, MUI X Data Grid — даёт готовый интерфейс со всем этим.
- **Виртуализация держит в DOM только видимые строки и небольшой запас,** а прокрутку имитирует контейнером полной высоты. 100 000 строк — это пара десятков узлов вместо ста тысяч.
- **Виртуализация ломает то, что полагается на DOM:** поиск браузера, печать, подсчёт строк скринридером. Число строк сообщают через `aria-rowcount` и `aria-rowindex`.
- **Данных больше, чем разумно отправлять клиенту, — обработка на сервере:** сортировка, фильтр и страницы становятся параметрами запроса, а таблица только показывает страницу.
::

---

## Почему таблицы сложные

Сквозной пример — список товаров в админке магазина: тысяча товаров, сортировка по цене, фильтр «в наличии», страницы по 20, выбор строк для массового изменения цен.

Список задач растёт быстро: сортировка по нескольким колонкам, фильтры разных типов, глобальный поиск, страницы, выбор строк, раскрытие вложенных строк, группировка и агрегаты, закрепление и перестановка колонок, изменение ширины, редактирование ячеек, навигация клавиатурой, экспорт. Каждая из них взаимодействует с остальными: фильтр меняет число страниц, сортировка — порядок выделенных строк.

## Headless и полный грид

### Headless: TanStack Table

TanStack Table не рисует ничего. Он получает данные, колонки и состояние, а отдаёт **модель строк** — какие строки, в каком порядке, на какой странице. В девятой версии возможности регистрируются явно, и в бандл попадают только используемые:

```js
import {
  constructTable, tableFeatures, createColumnHelper,
  rowSortingFeature, createSortedRowModel, sortFn_basic,
  columnFilteringFeature, createFilteredRowModel, filterFn_equals,
  rowPaginationFeature, createPaginatedRowModel,
} from '@tanstack/table-core';

const features = tableFeatures({
  rowSortingFeature, sortedRowModel: createSortedRowModel(), sortFns: { basic: sortFn_basic },
  columnFilteringFeature, filteredRowModel: createFilteredRowModel(), filterFns: { equals: filterFn_equals },
  rowPaginationFeature, paginatedRowModel: createPaginatedRowModel(),
});

const table = constructTable({
  features,
  columns,
  data: products,
  initialState: {
    sorting: [{ id: 'price', desc: true }],
    columnFilters: [{ id: 'inStock', value: true }],
    pagination: { pageIndex: 0, pageSize: 20 },
  },
});

table.getRowModel().rows;   // 20 строк в наличии, по убыванию цены
```

В проверке в Node.js, без всякого DOM, модель вернула 20 строк, все в наличии и отсортированные по убыванию цены, а после `nextPage()` — следующие 20, продолжающие сортировку. Разметку — `<table>`, `<tr>`, `<td>` или div-ы с ролями — пишет разработчик через адаптер для React, Vue, Solid, Svelte, Angular.

- **плюсы:** полный контроль над внешним видом и поведением, небольшой размер, один и тот же движок в разных фреймворках;
- **минусы:** интерфейс каждой функции — сортировочные иконки, фильтры, изменение ширины — нужно сделать самому.

### Полные гриды

**AG Grid**, **MUI X Data Grid**, **Handsontable**, **Glide Data Grid** дают готовый интерфейс: сортировку по клику, фильтры в заголовках, закрепление, перетаскивание колонок, редактирование, экспорт, виртуализацию строк и колонок, навигацию клавиатурой.

- **плюсы:** сложный табличный интерфейс за дни, а не месяцы;
- **минусы:** вес, своя система стилей, лицензия на часть функций — у AG Grid и MUI X есть платные редакции с группировкой, сводными таблицами и серверной моделью строк.

Выбор — как с UI-библиотеками (подробно — в [UI-библиотеках](/content/ecosystem-libs/ui-component-libraries)): свой дизайн и умеренные требования — headless; функции уровня Excel — полный грид.

## Виртуализация

Тысяча строк по десять ячеек — десять тысяч элементов DOM; сто тысяч строк — миллион. Браузер тратит память и время на раскладку каждого, даже невидимого.

**Виртуализация** рендерит только видимые строки и небольшой запас сверху и снизу. Контейнер получает полную высоту — число строк, умноженное на высоту строки, — и полоса прокрутки ведёт себя как обычно, а строки позиционируются по смещению.

```text
контейнер высотой 3 600 000 px (100 000 × 36 px)
  ┌──────────────┐
  │  пусто       │ ← не в DOM
  ├──────────────┤
  │ строка 50000 │ ← в DOM: видимые плюс запас
  │ строка 50001 │
  │ …            │
  ├──────────────┤
  │  пусто       │ ← не в DOM
  └──────────────┘
```

В проверке TanStack Virtual для 100 000 строк по 36 px в окне высотой 600 px посчитал полную высоту 3 600 000 px и отдал меньше 30 элементов: около 17 видимых и запас `overscan: 5`. После прокрутки к середине строка 50 000 оказалась в наборе со смещением 1 800 000 px.

Библиотеки: **TanStack Virtual** (headless, для любого фреймворка), **react-window** и **react-virtuoso** для React, `vue-virtual-scroller` и `useVirtualList` из :term[VueUse]{def="библиотека из сотен готовых композаблов для Vue"} для Vue. Полные гриды виртуализируют сами. Для длинных страниц без сложной логики похожий эффект даёт CSS-свойство `content-visibility: auto` — браузер пропускает отрисовку элементов за экраном, оставляя их в DOM.

### Что ломает виртуализация

Строк, которых нет в DOM, для браузера не существует:

- **поиск Ctrl+F** находит только отрисованные строки — нужен свой поиск по данным;
- **печать** выводит только видимое;
- **скринридер** считает строки по DOM и скажет «таблица из 22 строк»;
- **якоря и прокрутка к элементу** — к строке, которой нет, нужно прокрутить через API виртуализатора;
- **строки разной высоты** требуют измерения после отрисовки, и неточная оценка даёт скачки полосы прокрутки.

Для скринридера реальные размеры сообщают атрибутами:

```html
<div role="grid" aria-rowcount="100001">
  <div role="row" aria-rowindex="50002">…</div>
</div>
```

`aria-rowcount` — сколько строк всего, включая заголовок, `aria-rowindex` — номер строки. Основы :term[ARIA]{def="атрибуты, которые сообщают вспомогательным технологиям роль, состояние и имя элемента"} — в [Доступности](/content/html/accessibility).

## На клиенте или на сервере

| | Клиентская обработка | Серверная обработка |
| --- | --- | --- |
| Данные | все строки загружены в браузер | только текущая страница |
| Сортировка и фильтр | мгновенно, в браузере | запрос на каждое изменение |
| Предел | тысячи — десятки тысяч строк | любой объём |
| Состояние | в таблице | в параметрах запроса и URL |

Граница — не число, а сумма: сколько весят все строки, как быстро их загрузить и сколько памяти они займут. Десятки тысяч строк по нескольку полей — обычно клиент. Миллионы, или данные, которые нельзя отдать целиком по правам, — сервер.

При серверной обработке таблица переводится в ручной режим: состояние сортировки, фильтров и страницы становится частью ключа запроса, а таблице передают страницу и общее число строк:

```js
const { data } = useQuery({ queryKey: ['products', { sorting, filters, page }], queryFn: () => api.products({ sorting, filters, page }) });

constructTable({ features, columns, data: data.rows, manualSorting: true, manualFiltering: true, manualPagination: true, rowCount: data.total });
```

Состояние таблицы удобно держать в URL: ссылка открывает тот же вид, а «Назад» возвращает прежнюю сортировку (подробно — в [Загрузке данных React](/content/reactjs/data-fetching) и [Маршрутизации React](/content/reactjs/routing)).

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| своя таблица с сортировкой, фильтрами и страницами | TanStack Table |
| админка с функциями уровня Excel: группировка, сводные, редактирование | AG Grid, MUI X Data Grid |
| электронная таблица с формулами | Handsontable |
| длинный список без табличной логики | TanStack Virtual, react-virtuoso, `useVirtualList` |
| миллионы строк | серверная модель строк и виртуализация |

---

## Красные флаги в ответе

- **«TanStack Table — это компонент таблицы».** Он считает модель строк, разметку пишет разработчик.
- **«Виртуализация бесплатна».** Она ломает поиск браузера, печать и подсчёт строк скринридером.
- **«Сто тысяч строк можно просто отрисовать».** Это миллион узлов DOM, нужна виртуализация или серверная обработка.
- **«Серверная таблица — та же клиентская с другим источником».** Сортировка, фильтр и страница становятся параметрами запроса, а таблица — в ручном режиме.
- **«`div` с флексами — нормальная таблица».** Без ролей `grid`, `row`, `gridcell` скринридер не поймёт её структуру.

## Как спрашивают на собеседовании

::question
Почему для таблиц берут библиотеку, а не пишут свою на `<table>`?

#answer
Потому что сама разметка — меньшая часть работы. Сортировка по нескольким колонкам, фильтры, страницы, выбор строк, изменение ширины и порядка колонок, редактирование и производительность на больших данных взаимодействуют друг с другом, и самописная таблица быстро превращается в маленький фреймворк.

#more
Библиотека не обязательно рисует таблицу: headless-вариант берёт на себя только эту логику, а `<table>` с вашей разметкой остаётся. Своя реализация оправдана, когда нужна одна-две функции — например, только сортировка по клику.
::

::question
Чем headless-таблица отличается от грида?

#answer
Headless-таблица, например TanStack Table, по данным, колонкам и состоянию считает модель строк — сортировку, фильтрацию, страницы, выбор, — а разметку и стили пишет разработчик. Грид, например AG Grid, даёт готовый интерфейс со всеми этими функциями.

#more
Headless даёт полный контроль над видом и небольшой размер, но каждый элемент интерфейса делается вручную. Грид экономит месяцы на сложных функциях — группировка, сводные таблицы, редактирование, — ценой веса, своей системы стилей и платных редакций.
::

::question
Что такое виртуализация списка?

#answer
Рендер только видимых строк и небольшого запаса вместо всего списка. Контейнер получает полную высоту, а строки позиционируются по смещению, поэтому прокрутка выглядит обычной.

#more
Для 100 000 строк в DOM остаётся пара десятков элементов. Цена — сломанные Ctrl+F, печать и подсчёт строк скринридером, сложность со строками разной высоты. Реальное число строк сообщают через `aria-rowcount` и `aria-rowindex`. Библиотеки — TanStack Virtual, react-window, react-virtuoso, `vue-virtual-scroller`.
::

::question
Когда переносить сортировку и фильтрацию на сервер?

#answer
Когда данных больше, чем разумно загрузить в браузер, или их нельзя отдать целиком по правам доступа. Тогда сортировка, фильтры и страница — параметры запроса, а таблица показывает одну страницу и общее число строк.

#more
Граница определяется весом данных и памятью, а не числом: десятки тысяч лёгких строк обычно обрабатывают на клиенте. При серверной обработке таблицу переводят в ручной режим, состояние кладут в ключ запроса и в URL.
::

::question
Как сделать таблицу доступной?

#answer
Использовать `<table>` с `<th scope>` для обычной таблицы или роли `grid`, `row`, `gridcell` для интерактивного грида с навигацией стрелками. Сортировку объявлять через `aria-sort` на заголовке.

#more
При виртуализации — `aria-rowcount` и `aria-rowindex`, чтобы скринридер знал реальный размер. Фокус внутри грида — одна точка входа и перемещение стрелками, а не Tab по каждой ячейке. Полные гриды делают это сами, в headless-таблице — работа разработчика.
::

::question
Почему виртуализированный список прыгает при прокрутке?

#answer
Скорее всего, строки разной высоты, а виртуализатор считает их по оценке. Когда настоящая высота отличается, полная высота контейнера и смещения пересчитываются, и полоса прокрутки скачет.

#more
Решения — фиксированная высота строк, измерение после отрисовки, которое поддерживают TanStack Virtual и react-virtuoso, и точная оценка `estimateSize`. Изображения в строках дают ту же проблему, если у них нет размеров заранее.
::

## Практика

::practice{title="Таблица заказов тормозит"}
Админка показывает все 40 000 заказов одной таблицей. Прокрутка дёргается, а открытие страницы занимает несколько секунд.

#solution
40 000 строк по десять ячеек — около 400 000 узлов DOM. Варианты по возрастанию объёма данных:

```js
// 1. виртуализация: в DOM только видимые строки
const virtualizer = useVirtualizer({
  count: rows.length,
  getScrollElement: () => scrollRef.current,
  estimateSize: () => 36,
  overscan: 8,
});
```

```html
<div role="grid" aria-rowcount="40001">…</div>
```

```js
// 2. серверная обработка: загружается одна страница
const { data } = useQuery({ queryKey: ['orders', { sorting, filters, page }], queryFn: () => api.orders({ sorting, filters, page }) });
```

40 000 заказов с адресами и составом — это ещё и мегабайты JSON, поэтому для такой админки обычно правильна серверная обработка, а виртуализация — для длинных списков внутри страницы. В проверке виртуализатор для 100 000 строк держал меньше 30 элементов.
::

::practice{title="Скринридер говорит «22 строки»"}
После виртуализации таблицы товаров пользователь со скринридером слышит, что в таблице 22 строки, хотя товаров 5000.

#solution
Скринридер считает строки по DOM, а в DOM только видимые. Реальные размеры сообщают атрибутами:

```html
<div role="grid" aria-rowcount="5001" aria-label="Товары">
  <div role="row" aria-rowindex="1">…заголовки…</div>
  <div role="row" aria-rowindex="2141">…</div>
  <div role="row" aria-rowindex="2142">…</div>
</div>
```

`aria-rowcount` — общее число строк, включая заголовок, `aria-rowindex` — номер каждой отрисованной строки, начиная с 1. Для поиска добавляют своё поле, которое фильтрует данные, а не DOM, — Ctrl+F невидимые строки не найдёт. В проверке в DOM была одна строка, а `aria-rowcount` сообщал реальный размер.
::
