# Состояние и данные

«Какой стейт-менеджер выбрать?» - вопрос-ловушка. Правильный ответ начинается с **классификации состояния**: половина библиотек в этой категории решают разные задачи и не конкурируют. Здесь - карта всего ландшафта; механику конкретных решений см. в главах [React](/content/reactjs/state-management) и [Vue](/content/vuejs/state-management).

---

## Главное различие: client vs server state

| | Client state | Server state |
|--|--------------|--------------|
| Что это | UI-состояние приложения | кэш данных с бэкенда |
| Примеры | тема, открытый модал, корзина | список товаров, профиль |
| Особенности | синхронное, твоё | асинхронное, устаревает, разделяемое |
| Инструменты | Redux, Zustand, Jotai, Pinia | TanStack Query, SWR, Apollo |

<b class="text-on-semi-light">Ключевой инсайт</b> - <span class="text-gray">Большая часть «глобального состояния» - это **серверные данные**. Их не нужно класть в Redux и вручную вести `loading/error/data` - для этого есть кэширующие библиотеки. После выноса server state «глобального состояния» часто почти не остаётся.</span>

---

## Менеджеры client-state

### Сторы

- **Redux Toolkit (RTK)** - стандарт «классического» Redux: единый стор, чистые редьюсеры, мощный DevTools с time-travel, middleware. Бойлерплейт убран через `createSlice`. Для крупных приложений и команд.
- **Zustand** - минималистичный стор на хуках, без провайдеров и бойлерплейта, селекторы для точечных подписок. Самый популярный «лёгкий» выбор.

### Атомарные

- **Jotai** - состояние как набор маленьких **атомов**, подписка по атомам, производные атомы. Подход «снизу вверх».
- **Recoil** - первопроходец атомарного подхода от Meta, но фактически **заброшен** - в новом коде не берут.

### Proxy / реактивные

- **Valtio** - мутабельный стор на Proxy: меняешь объект напрямую, подписчики реагируют (близко к Vue-реактивности).
- **MobX** - реактивность через наблюдаемые объекты, ООП-стиль. Зрелый, но доля падает; больше в legacy.

### State machines

- **XState** - состояние как **конечный автомат**: явные состояния и переходы. Незаменим для сложных потоков (визард, плеер, чекаут), где важно исключить невозможные состояния.

| Библиотека | Модель           | Подписки      | Когда                       |
| ---------- | ---------------- | ------------- | --------------------------- |
| Redux RTK  | единый стор      | селекторы     | крупное, командное          |
| Zustand    | стор на хуках    | селекторы     | большинство приложений      |
| Jotai      | атомы            | по атомам     | дробное состояние           |
| Valtio     | proxy-мутации    | авто          | любители мутабельного стиля |
| XState     | конечный автомат | -             | сложные потоки/визарды      |

> Во Vue эту нишу занимает **Pinia** (заменил Vuex); тонкая реактивность Vue даёт точечные подписки без ручных селекторов.

## Библиотеки server-state

Это **кэш удалённых данных** с дедупликацией, фоновым обновлением и инвалидацией.

- **TanStack Query** (React/Vue/Solid/Svelte) - стандарт. Кэш по ключу, stale-while-revalidate, refetch, мутации, оптимистичные обновления. Не привязан к протоколу (REST, GraphQL - любой `queryFn`).
- **SWR** - лёгкая альтернатива от Vercel, тот же принцип (stale-while-revalidate), проще и меньше.
- **RTK Query** - часть Redux Toolkit; если уже на Redux, даёт кэширование данных в той же экосистеме.

### GraphQL-клиенты

- **Apollo Client** - полнофункциональный GraphQL-клиент с нормализованным кэшем; тяжёлый, но мощный.
- **urql** - легче Apollo, модульный.
- **Relay** - клиент от Meta, максимально оптимизирован, но со строгими требованиями к схеме; высокий порог входа.

| Библиотека    | Протокол | Вес     | Особенность                  |
| ------------- | -------- | ------- | ---------------------------- |
| TanStack Query| любой    | средний | стандарт server-state        |
| SWR           | любой    | лёгкий  | минимализм                   |
| Apollo Client | GraphQL  | тяжёлый | нормализованный кэш          |
| urql          | GraphQL  | лёгкий  | модульность                  |

## Нормализованный vs документный кэш

Важное senior-различие между двумя моделями кэша server-state:

- **Документный кэш** (TanStack Query, SWR) - хранит ответы **как есть**, по ключу запроса. Просто и предсказуемо, но одна сущность (юзер) может лежать в нескольких кэшах и **рассинхрониться** при обновлении одного из них.
- **Нормализованный кэш** (Apollo, Relay, urql graphcache) - разбирает ответы на **сущности по id** (как нормализация в Redux) и хранит каждую один раз. Обновил юзера в одном месте - он обновился **везде**, где упоминается.

<b class="text-on-semi-light">Компромисс</b> - <span class="text-gray">Документный проще и хватает большинству; согласованность обеспечивают **инвалидацией** ключей. Нормализованный даёт автоматическую согласованность сущностей по всему UI ценой сложности и веса - оправдан для сильно связанных данных (соцсети, где объект в десятках мест). Это выбор архитектуры данных, а не просто «какая библиотека».</span>

## Как выбрать

```
Серверные данные (REST/любой)     → TanStack Query (или SWR для простоты)
Серверные данные (GraphQL)        → Apollo / urql
Глобальное UI-состояние, лёгкое    → Zustand
Глобальное UI-состояние, крупное   → Redux Toolkit
Дробное независимое состояние      → Jotai
Сложные потоки с переходами        → XState
Vue                                → Pinia + TanStack Query
```

<b class="text-on-semi-light">Правильный порядок мышления</b> - <span class="text-gray">Сначала вынеси server state в Query/SWR. Потом локальное состояние оставь в компонентах. И только то, что реально глобально и часто меняется, - в стор. Стор не должен быть выбором по умолчанию.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем client state отличается от server state?</b>
<span class="text-gray">Client state - синхронное UI-состояние приложения (тема, модал). Server state - асинхронный кэш данных бэкенда, который устаревает и разделяется. Для них разные инструменты.</span>

<b class="text-on-semi-light">Почему не держать серверные данные в Redux?</b>
<span class="text-gray">Это переизобретение кэша: ручные loading/error/data, нет дедупликации и фонового обновления. TanStack Query/SWR дают это из коробки.</span>

<b class="text-on-semi-light">Чем отличаются атомарный подход (Jotai) и стор (Redux)?</b>
<span class="text-gray">Redux - единый стор, доступ через селекторы. Jotai - множество маленьких атомов, подписка по конкретным атомам. Атомарный удобен для дробного независимого состояния.</span>

<b class="text-on-semi-light">Когда нужен XState?</b>
<span class="text-gray">Для сложных потоков с явными состояниями и переходами (визарды, плееры, чекаут), где важно исключить невозможные комбинации состояний - конечный автомат делает это явным.</span>

<b class="text-on-semi-light">TanStack Query или Apollo?</b>
<span class="text-gray">Query - универсальный server-state для любого протокола (включая REST). Apollo - специализированный GraphQL-клиент с нормализованным кэшем, тяжелее. Для GraphQL без сложного кэша часто хватает Query/urql.</span>

<b class="text-on-semi-light">Нужен ли вообще стейт-менеджер?</b>
<span class="text-gray">Часто нет: после выноса server state в Query и хранения локального в компонентах глобального состояния остаётся мало - его покрывает Context или лёгкий Zustand.</span>

<b class="text-on-semi-light">Чем нормализованный кэш отличается от документного?</b>
<span class="text-gray">Документный (Query/SWR) хранит ответы по ключу запроса как есть - просто, но сущность может рассинхрониться между кэшами. Нормализованный (Apollo/Relay) хранит сущности по id один раз - обновление отражается везде, но сложнее и тяжелее.</span>
