# Библиотеки состояния и данных

Ландшафт библиотек состояния поперёк фреймворков: сторы, атомы, прокси, сигналы и автоматы состояний для клиентского состояния, библиотеки серверного состояния и два способа хранить данные с сервера — нормализованный и документный кеш. Спрашивают, чем клиентское состояние отличается от серверного, почему не держать данные сервера в Redux и нужен ли стейт-менеджер вообще. Глубже — когда автомат состояний лучше набора флагов и почему после переименования товара карточка обновилась, а каталог — нет.

::tldr
- **Сначала вид состояния, потом библиотека.** Данные с сервера — кеш чужих данных, им нужна библиотека загрузки. Для клиентского состояния часто хватает компонента, URL и контекста.
- **Клиентские сторы различаются моделью обновления:** стор с действиями (Redux, Zustand, Pinia), атомы (Jotai, Nano Stores), прокси, где меняешь объект напрямую (Valtio, MobX), сигналы с точечными зависимостями (Preact Signals, Solid), автоматы состояний (XState).
- **Автомат состояний описывает допустимые переходы,** и невозможный переход просто не происходит: оплатить из корзины нельзя, даже если кнопку нажали.
- **Нормализованный кеш хранит каждую сущность один раз по типу и ID,** и изменение видят все запросы с ней — так работают Apollo и urql с Graphcache. **Документный кеш хранит ответ целиком по ключу запроса,** и после изменения связанные запросы инвалидируют — так работают TanStack Query, SWR и Pinia Colada.
- **Документный кеш проще и подходит большинству приложений,** нормализованный окупается, когда одни и те же сущности показываются во многих запросах сразу.
::

## Какое это состояние

Различие клиентского и серверного состояния — главное, что спрашивают, и оно разобрано подробно в [Управлении состоянием React](/content/reactjs/state-management) и [Управлении состоянием Vue](/content/vuejs/state-management), а архитектурно — в [Архитектуре состояния и данных](/content/architecture/state-and-data-architecture). Коротко:

| | Клиентское | Серверное |
| --- | --- | --- |
| Чьё | приложения | сервера, у клиента — копия |
| Примеры | открытая панель, черновик, корзина до оформления, тема | каталог, заказы, профиль |
| Устаревает | нет | да |
| Нужно | хранить и менять | загружать, кешировать, обновлять, инвалидировать |
| Инструменты | состояние компонента, URL, контекст, стор | TanStack Query, SWR, Pinia Colada, Apollo, urql |

Когда серверное состояние уходит в библиотеку загрузки, глобального клиентского состояния обычно остаётся мало. Сквозной пример — магазин: каталог и карточка товара с сервера, корзина и оформление заказа на клиенте.

## Клиентское состояние

### Сторы с действиями

Состояние в одном объекте, изменения через действия или функции стора: **Redux Toolkit**, **Zustand**, **Pinia**. Предсказуемо, удобно отлаживать — в DevTools видна каждая операция. В React компонент подписывается на часть стора селектором, во Vue — на прочитанные поля автоматически. Подробно о Redux Toolkit, Zustand и Jotai — в [Управлении состоянием React](/content/reactjs/state-management), о Pinia — в [Управлении состоянием Vue](/content/vuejs/state-management).

### Атомы

Состояние из маленьких независимых единиц, производные — атомы от атомов: **Jotai**, **Nano Stores**. Компонент подписан только на свои атомы. Nano Stores — несколько сотен байт и работает в любом фреймворке, поэтому его используют в Astro и для общего состояния между островами.

### Прокси

Меняешь объект напрямую, а библиотека отслеживает изменения через Proxy: **Valtio**, **MobX**. Это та же идея, что реактивность Vue (подробно — в [Основах реактивности Vue](/content/vuejs/reactivity-fundamentals)), но для React.

```js
import { proxy, subscribe, snapshot } from 'valtio/vanilla';

const cart = proxy({ items: [], coupon: null });
cart.items.push({ sku: 'tea' });   // обычная мутация
```

В проверке две мутации подряд дали одно уведомление подписчику, а `snapshot` вернул снимок только для чтения: запись в него бросила `TypeError`, а изменения исходного объекта снимок не тронули. В React компонент читает снимок через `useSnapshot`, а меняет исходный прокси.

### Сигналы

Значение с подписчиками и точными зависимостями: **Preact Signals**, **Solid**, `ref` во Vue, сигналы в Angular. Производное значение пересчитывается лениво, а эффект зависит только от того, что прочитал. В проверке изменение темы, которую эффект не читал, его не запустило. Сигналы как общее направление и предложение TC39 — в [Сигналах и реактивности](/content/modern-dev/signals-and-reactivity).

### Автоматы состояний

Процесс оформления заказа — это не набор флагов `isLoading`, `isPaying`, `hasError`, а **конечный набор состояний и переходов** между ними. **XState** описывает их явно:

```js
import { createMachine, createActor } from 'xstate';

const checkout = createMachine({
  initial: 'cart',
  states: {
    cart: { on: { CHECKOUT: 'address' } },
    address: { on: { BACK: 'cart', SUBMIT: 'payment' } },
    payment: { on: { PAY: 'paying' } },
    paying: { on: { SUCCESS: 'done', FAIL: 'payment' } },
    done: { type: 'final' },
  },
});
```

В проверке событие `PAY` в состоянии `cart` ничего не сделало — такого перехода нет, — а цепочка `CHECKOUT → SUBMIT → PAY → FAIL → PAY → SUCCESS` привела в `done`, откуда назад уже нельзя. С флагами то же правило пришлось бы проверять в каждом обработчике, и комбинация «оплачивается и вернулся в корзину» была бы возможна. Автомат окупается в сложных процессах: оформление заказа, мастера, загрузка файлов, видеоплеер, сложные компоненты. Для простого состояния — избыточен. Та же идея лежит в основе Zag.js и Ark UI (подробно — в [UI-библиотеках](/content/ecosystem-libs/ui-component-libraries)).

## Нормализованный и документный кеш

Пользователь переименовал товар. Его название показано в двух местах: в каталоге и в карточке. Что обновится?

### Нормализованный

Кеш разбирает ответы на **сущности** и хранит каждую один раз по ключу «тип и ID»:

```text
ROOT_QUERY.products → [ссылка на Product:7]
ROOT_QUERY.product  → ссылка на Product:7
Product:7           → { title: 'Улун', price: 490 }
```

Ответ мутации `renameProduct` с тем же `Product:7` обновляет одну запись, и **оба запроса** сразу видят новое название — без повторной загрузки. В проверке Apollo хранил ровно одну запись `Product:7` для каталога и карточки, а после мутации оба запроса прочитали из кеша «Пуэр».

Цена: каждой сущности нужен `__typename` и стабильный `id`, кеш сложнее устроен и отлаживается, а изменение списков — добавить товар в каталог, удалить из него — всё равно приходится описывать вручную, потому что кеш не знает, в какие списки попадает новая сущность. Это естественно для GraphQL, где у ответов есть схема и типы.

### Документный

Кеш хранит **ответ целиком** по ключу запроса:

```text
['catalog']     → [{ id: 7, title: 'Улун' }]
['product', 7]  → { id: 7, title: 'Улун' }
```

Обновление одного ключа не трогает другие: в проверке после `setQueryData` для карточки каталог по-прежнему показывал «Улун». Связанные запросы **инвалидируют** — помечают устаревшими, и они загружаются заново: после `invalidateQueries(['catalog'])` каталог получил новое название.

Цена — лишние запросы после изменений и необходимость помнить, какие ключи связаны. Зато модель простая, работает с любым API — REST, RPC, GraphQL — и легко отлаживается.

| | Нормализованный | Документный |
| --- | --- | --- |
| Единица хранения | сущность по типу и ID | ответ по ключу запроса |
| После изменения | обновляются все запросы с сущностью | связанные запросы инвалидируют и загружают заново |
| Требования | `__typename` и `id`, схема ответов | только ключ запроса |
| Списки | обновляются вручную | загружаются заново |
| Подходит | GraphQL, одни сущности во многих местах | REST и большинство приложений |

## Как выбрать

1. **Серверные данные** — в библиотеку загрузки: TanStack Query, SWR, Pinia Colada; для GraphQL — Apollo, urql или Relay.
2. **Состояние в адресе** — фильтры, вкладки, страница — в URL.
3. **Локальное** — в компоненте.
4. **Общее для поддерева** — контекст или `provide`.
5. **Общее для приложения** — стор: Zustand или Redux Toolkit в React, Pinia во Vue, Nano Stores между фреймворками и островами.
6. **Сложный процесс с этапами** — автомат состояний.

Стейт-менеджер для приложения бывает не нужен вовсе: если серверные данные в библиотеке загрузки, а фильтры в URL, остаются корзина и пара настроек — их хватает контекста или маленького стора.

---

## Красные флаги в ответе

- **«Данные с сервера кладу в Redux».** Это кеш чужих данных: загрузка, свежесть и инвалидация — задача библиотеки серверного состояния.
- **«Нормализованный кеш всегда лучше».** Он сложнее и требует ID и типов, документный проще и подходит большинству.
- **«После мутации всё обновится само».** В документном кеше связанные запросы нужно инвалидировать.
- **«Автомат состояний — это для игр».** Он полезен везде, где есть этапы и невозможные комбинации: оформление заказа, мастера, загрузки.
- **«Без стейт-менеджера нельзя строить большое приложение».** Чаще всего его место занимают библиотека загрузки и URL.

## Как спрашивают на собеседовании

::question
Чем клиентское состояние отличается от серверного?

#answer
Клиентское принадлежит приложению: открытые панели, черновики, корзина до оформления. Серверное — копия данных сервера, которая устаревает и которую делят компоненты: каталог, заказы, профиль. Ему нужны загрузка, кеш, обновление и инвалидация.

#more
Поэтому серверное состояние держат в библиотеке загрузки, а клиентское — в компоненте, URL, контексте или сторе. После выноса серверного состояния глобального клиентского обычно остаётся немного.
::

::question
Почему не держать серверные данные в Redux?

#answer
Пришлось бы вручную писать загрузку, состояния загрузки и ошибки, кеш, повторные запросы, обновление при фокусе, дедупликацию и инвалидацию. Библиотеки серверного состояния делают это из коробки.

#more
В экосистеме Redux для этого есть RTK Query — документный кеш с тегами инвалидации. В остальных случаях берут TanStack Query, SWR или Apollo, а стор оставляют для клиентского состояния.
::

::question
Чем отличаются стор, атомы, прокси и сигналы?

#answer
Стор — одно состояние и изменения через действия: Redux, Zustand, Pinia. Атомы — маленькие независимые единицы и производные от них: Jotai, Nano Stores. Прокси — меняешь объект напрямую, библиотека отслеживает изменения: Valtio, MobX. Сигналы — значения с точными зависимостями и ленивыми производными: Preact Signals, Solid, Vue.

#more
Различаются тем, кто и как узнаёт об изменениях: селекторы в сторе, подписка на атом, перехват записи прокси, граф зависимостей сигналов. Выбор — по команде и модели фреймворка: во Vue реактивность уже прокси и сигналы, в React атомы и прокси экономят селекторы.
::

::question
Когда нужен XState?

#answer
Когда у процесса есть этапы и правила переходов: оформление заказа, мастер, загрузка файлов, плеер. Автомат описывает допустимые состояния и переходы явно, и невозможный переход просто не происходит.

#more
Набор флагов допускает невозможные комбинации — «оплачивается и в корзине», — и правила приходится проверять в каждом обработчике. Автомат можно визуализировать и протестировать по переходам. Для простого состояния он избыточен, там хватает размеченного объединения.
::

::question
Чем нормализованный кеш отличается от документного?

#answer
Нормализованный хранит каждую сущность один раз по типу и ID, и изменение сразу видят все запросы с ней. Документный хранит ответ целиком по ключу запроса, и после изменения связанные запросы инвалидируют и загружают заново.

#more
Нормализованный — у Apollo, Relay, urql с Graphcache; требует `__typename` и `id`, а списки всё равно обновляются вручную. Документный — у TanStack Query, SWR, Pinia Colada; проще и работает с любым API. Большинству приложений достаточно документного.
::

::question
Нужен ли вообще стейт-менеджер?

#answer
Часто нет. Если серверные данные в библиотеке загрузки, фильтры в URL, а локальное состояние в компонентах, общего клиентского состояния остаётся мало — корзина, тема, настройки, — и его хватает контекста или маленького стора.

#more
Стор нужен, когда общее состояние меняют разные независимые части приложения и его читают вне компонентов. Начинают с простого и добавляют стор, когда появилась реальная потребность.
::

## Практика

::practice{title="Название не обновилось в каталоге"}
Приложение на TanStack Query. После переименования товара карточка показывает новое название, а каталог — старое, пока не перезагрузить страницу:

```js
const rename = useMutation({
  mutationFn: (title) => api.renameProduct(id, title),
  onSuccess: (product) => queryClient.setQueryData(['product', id], product),
});
```

#solution
Кеш документный: каждый ключ хранит свой ответ, а мутация обновила только ключ карточки. Каталог хранит свою копию товара и об изменении не знает — в проверке после `setQueryData` для карточки каталог остался со старым названием.

```js
const rename = useMutation({
  mutationFn: (title) => api.renameProduct(id, title),
  onSuccess: (product) => {
    queryClient.setQueryData(['product', id], product);                 // карточка — сразу
    queryClient.invalidateQueries({ queryKey: ['catalog'] });           // каталог — загрузить заново
  },
});
```

Ключи стоит строить иерархией (`['products', 'list']`, `['products', 'detail', id]`), тогда `invalidateQueries({ queryKey: ['products'] })` инвалидирует всё связанное разом. В нормализованном кеше Apollo то же изменение обновило бы оба запроса само — в проверке так и было, — но ценой требований к `id` и `__typename`.
::

::practice{title="Флаги оформления заказа"}
Оформление заказа хранится флагами, и в продакшене бывает состояние «идёт оплата», хотя пользователь вернулся в корзину:

```js
const [step, setStep] = useState('cart');
const [isPaying, setIsPaying] = useState(false);
const [error, setError] = useState(null);
```

#solution
Три независимых значения допускают комбинации, которых не должно быть, и правила разбросаны по обработчикам. Процесс описывают автоматом:

```js
const checkout = createMachine({
  initial: 'cart',
  states: {
    cart: { on: { CHECKOUT: 'address' } },
    address: { on: { BACK: 'cart', SUBMIT: 'payment' } },
    payment: { on: { PAY: 'paying' } },
    paying: { on: { SUCCESS: 'done', FAIL: 'payment' } },
    done: { type: 'final' },
  },
});
```

Теперь «оплата» — это одно состояние, из которого есть только два выхода: успех или ошибка, — и вернуться в корзину во время оплаты невозможно. Ошибку оплаты хранят в контексте автомата. Если процесс простой, той же цели достигает размеченное объединение одного `useState`. В проверке `PAY` из корзины ничего не изменил, а полный путь привёл в `done`.
::
