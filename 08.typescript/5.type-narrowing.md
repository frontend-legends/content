# Сужение типов

Как TypeScript понимает, какой тип у значения в конкретной строке: анализ потока управления, проверки `typeof`, `instanceof`, `in` и сравнения, размеченные объединения, предикаты, функции-утверждения и проверка полноты через `never`. Спрашивают, что такое сужение, размеченное объединение и как написать свой type guard. Глубже — где сужение теряется, почему предикат может соврать и что компилятор выводит сам.

::tldr
- **Сужение — вывод более узкого типа в ветке кода по проверке.** Компилятор следит за потоком управления: после `if (typeof x === 'string')` внутри ветки `x` — строка, после `return` — уже нет.
- **Размеченное объединение — главный приём.** Общее поле-литерал (`status`, `kind`, `type`) позволяет сузить объединение одним сравнением, а `never` в `default` ловит необработанный вариант.
- **Предикат `x is T` и утверждение `asserts x is T` — обещания, а не проверки.** Компилятор верит им на слово, и неполная проверка внутри ломает типизацию.
- **Сужение может потеряться:** в колбэке для `let`, который переприсваивается дальше. И может устареть: после вызова функции сужение свойства объекта не сбрасывается, хотя функция могла его изменить.
- **Многое выводится само:** сохранённое в константу условие, деструктуризация размеченного объединения, предикат стрелки в `filter(x => x !== undefined)`.
::

## Как работает сужение

Тип переменной объявлен один раз, но в разных строках компилятор знает о ней разное:

```ts
function format(value: string | number | null) {
  if (value === null) return '—';
  // value: string | number

  if (typeof value === 'string') {
    // value: string
    return value.toUpperCase();
  }
  // value: number
  return value.toFixed(2);
}
```

Это **анализ потока управления** (control flow analysis). Компилятор проходит по веткам, `return`, `throw`, присваиваниям и для каждой точки вычисляет тип. Проверка, после которой тип сужается, называется **защитником типа** (type guard).

В рантайме ничего не меняется: это обычные проверки JavaScript, а TypeScript только читает их смысл. Значит, сузить можно лишь тем, что проверяется в рантайме. Интерфейс в рантайме не существует, и проверить «это `User`?» напрямую нельзя — только по признакам значения.

Какие проверки компилятор понимает?

## Встроенные защитники

### typeof

Для примитивов: `'string'`, `'number'`, `'bigint'`, `'boolean'`, `'symbol'`, `'undefined'`, `'object'`, `'function'`. Ловушка — `typeof null === 'object'`, и компилятор это знает: после `typeof v === 'object'` у `string[] | null` остаётся `null`.

### Истинность

`if (value)` отсекает `null` и `undefined`, но вместе с ними `0`, `''` и `NaN`. Для чисел и строк это частая ошибка:

```ts
function label(count: number | undefined) {
  return count ? `${count} шт.` : 'нет';
}
label(0);   // 'нет' — ноль товаров превратился в «нет данных»
```

Если `0` и `''` — допустимые значения, сравнивают явно: `count !== undefined` или `count != null`.

### Равенство

`===`, `!==`, `==`, `!=` сужают до общего типа. `value != null` отсекает и `null`, и `undefined` — редкий случай, где нестрогое сравнение уместно.

### instanceof и Array.isArray

`instanceof` сужает до класса, `Array.isArray` — до массива:

```ts
const toDate = (v: string | Date) => (v instanceof Date ? v : new Date(v));
const first = (v: string | string[]) => (Array.isArray(v) ? v[0] : v);
```

`instanceof` работает только с тем, что существует в рантайме, — с классами, не с интерфейсами. И ломается между realm: массив из iframe не `instanceof Array` этого окна, поэтому для массивов — `Array.isArray`.

### in

Проверяет наличие свойства. Если свойство есть в одном из вариантов объединения, `in` выбирает этот вариант. Если его нет ни в одном, тип дополняется: `'id' in x` для `x: object` даёт `object & Record<'id', unknown>`. Это удобно для данных из `unknown`, о которых ниже.

Проверки на отдельные признаки работают, но для объектов есть способ надёжнее.

## Размеченные объединения

Состояние загрузки — классика:

```ts
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: string[] }
  | { status: 'error'; error: Error };
```

Общее поле с литеральным типом — **дискриминант**. Одно сравнение выбирает вариант, и в ветке доступны его поля:

```ts
function render(state: State): string {
  switch (state.status) {
    case 'idle': return '';
    case 'loading': return '...';
    case 'success': return state.data.join(', ');
    case 'error': return state.error.message;
  }
}
```

Сравните с «плоским» типом `{ loading: boolean; data?: string[]; error?: Error }`. Он допускает невозможные комбинации — `loading: true` вместе с `error` — и заставляет проверять `data` на `undefined` даже после успеха. Размеченное объединение описывает только реальные состояния.

Компилятор понимает дискриминант и при деструктуризации, если поля взяты из одного объекта:

```ts
type Action = { type: 'add'; payload: number } | { type: 'reset'; payload: null };

function reduce(n: number, { type, payload }: Action) {
  if (type === 'add') return n + payload;   // payload: number
  return 0;
}
```

### Проверка полноты

Когда все варианты обработаны, в `default` остаётся тип `never`. Если присвоить его тому, что ждёт `never`, добавление нового варианта сломает компиляцию:

```ts
function assertNever(value: never): never {
  throw new Error(`Unexpected: ${JSON.stringify(value)}`);
}

function area(s: Shape): number {
  switch (s.kind) {
    case 'circle': return Math.PI * s.r ** 2;
    case 'square': return s.side ** 2;
    default: return assertNever(s);
    // добавили 'rect' — ошибка: Argument of type '{ kind: "rect"; ... }' is not assignable to parameter of type 'never'
  }
}
```

`assertNever` полезен вдвойне: компилятор ловит забытый вариант, а в рантайме функция бросает ошибку, если пришло значение, которого нет в типе (например, сервер добавил статус). Короткая форма без рантайм-проверки — `return s satisfies never`.

Сужения по признакам и дискриминанту хватает, пока проверка помещается в условие. Когда она сложнее — её выносят в функцию.

## Предикаты и утверждения

### Предикат `x is T`

Функция, возвращающая `boolean`, ничего не говорит компилятору. Возвращаемый тип `x is T` говорит: «если `true` — `x` типа `T`»:

```ts
type User = { id: number; name: string };

function isUser(x: unknown): x is User {
  return (
    typeof x === 'object' && x !== null &&
    'id' in x && typeof x.id === 'number' &&
    'name' in x && typeof x.name === 'string'
  );
}
```

Здесь пригодился `in` с отсутствующим свойством: после `'id' in x` можно читать `x.id` без `as`.

Главное — компилятор **не проверяет**, что тело соответствует обещанию. Неполная проверка проходит компиляцию:

```ts
function isUserLie(x: unknown): x is User {
  return typeof x === 'object' && x !== null;   // поля не проверены
}

const raw: unknown = { id: 1 };
if (isUserLie(raw)) raw.name.toUpperCase();   // TypeError в рантайме: name — undefined
```

Предикат — это `as` в обёртке функции. Для данных из сети его заменяют схемой (zod, valibot), где тип выводится из проверки и не может с ней разойтись (подробно — в [Асинхронности и DOM](/content/typescript/async-and-dom)).

### Выведенные предикаты

Компилятор умеет вывести предикат сам, если тело стрелки — проверка, которая однозначно сужает параметр:

```ts
const ids = [1, undefined, 3].filter((x) => x !== undefined);   // number[]

const truthy = [1, 0, undefined].filter((x) => !!x);   // (number | undefined)[]
```

Во втором случае предикат не выводится: `false` означает «`0` или `undefined`», и из ложного результата нельзя заключить, что `x` — `undefined`. Предикат выводится, только если и `true`, и `false` что-то точно говорят о типе.

### Утверждение `asserts x is T`

Функция-утверждение не возвращает результат, а бросает исключение, если условие не выполнено. После вызова тип сужен до конца блока:

```ts
function assertDefined<T>(v: T, msg = 'value is required'): asserts v is NonNullable<T> {
  if (v === null || v === undefined) throw new Error(msg);
}

function useOrderId(id: string | null) {
  assertDefined(id, 'orderId required');
  return id.toUpperCase();   // id: string
}
```

| | Предикат | Утверждение |
| --- | --- | --- |
| Возвращаемый тип | `x is T` | `asserts x is T` или `asserts x` |
| Результат | `boolean` | ничего или исключение |
| Где | в условии `if`, тернарнике, `filter` | отдельной инструкцией |
| Ветки | две: истина и ложь | одна: после вызова |

У утверждений есть ограничение: имя функции должно иметь явный тип. Стрелка `const assertStr = (v: unknown): asserts v is string => ...` при вызове даёт ошибку TS2775 «Assertions require every name in the call target to be declared with an explicit type annotation». Помогает объявление через `function` или аннотация константы: `const assertStr: (v: unknown) => asserts v is string = ...`.

Утверждения и предикаты обещают тип явно. Но и обычные проверки компилятор помнит не везде.

## Где сужение теряется и где устаревает

### Сохранённое условие

Условие можно сохранить в константу — сужение сработает:

```ts
const isString = typeof v === 'string';
if (isString) v.length;   // v: string
```

Работает, если и условие, и проверяемое значение — `const` или параметры, которые не переприсваиваются.

### Замыкания

Колбэк может выполниться позже, когда переменная уже другая. Поэтому для `let`, который переприсваивается после создания колбэка, сужение в колбэке не действует:

```ts
function run(input: string | undefined) {
  let b = input;
  if (b === undefined) return;
  const g = () => b.toUpperCase();   // ошибка: b possibly undefined
  b = input;                         // из-за этой строки
  return g();
}
```

Если присваиваний после создания колбэка нет, компилятор сохраняет сужение. Самое простое решение — `const` или копия в `const` перед колбэком.

### Свойства после вызова функции

Обратная ситуация: сужение остаётся, хотя уже неверно.

```ts
const cart: { coupon: string | null } = { coupon: 'SALE' };
function clearCoupon() { cart.coupon = null; }

function applyCoupon(c: typeof cart) {
  if (c.coupon !== null) {
    clearCoupon();
    return c.coupon.toUpperCase();   // c.coupon: string, а в рантайме null — TypeError
  }
}
```

Если бы компилятор сбрасывал сужение после каждого вызова, проверки пришлось бы повторять постоянно. Поэтому он сознательно считает, что вызовы не трогают свойства. Это одно из мест, где система типов нестрогая (подробно — во [Введении](/content/typescript/introduction)). Решение — прочитать значение в локальную константу до вызова.

### catch

Под `strict` переменная в `catch` — `unknown`: бросить можно что угодно, не только `Error`. Её сужают через `instanceof Error` или проверку формы.

---

## Красные флаги в ответе

- **«Type guard проверяет тип в рантайме».** Проверяет код внутри guard, а `x is T` — обещание, которое компилятор не сверяет с телом.
- **«`if (value)` — нормальная проверка на `undefined`».** Она отсекает и `0`, и `''`.
- **«`instanceof` подходит для интерфейсов».** Интерфейсов в рантайме нет, `instanceof` работает только с классами и конструкторами.
- **«Флаги `isLoading`, `isError` и опциональные поля — нормальный тип состояния».** Он допускает невозможные комбинации, размеченное объединение их исключает.
- **«Если тип сужен, значение точно такое».** Сужение свойства не сбрасывается после вызова функции, которая могла его изменить.

## Как спрашивают на собеседовании

::question
Что такое сужение типов?

#answer
Вывод более узкого типа в конкретной ветке кода по проверке. После `typeof x === 'string'` внутри ветки `x` — строка. Компилятор отслеживает `if`, `switch`, `return`, `throw` и присваивания — это анализ потока управления.

#more
Сужают `typeof`, `instanceof`, `in`, `Array.isArray`, сравнения, истинность, дискриминант объединения, предикаты и утверждения. Сужение — только рантайм-проверки: интерфейс проверить нельзя. Оно теряется в колбэке для переприсваиваемого `let` и не сбрасывается для свойств после вызова функции.
::

::question
Что такое размеченное объединение?

#answer
Объединение объектов с общим полем-литералом (`status: 'success' | 'error'`). Одно сравнение по этому полю выбирает вариант, и в ветке доступны его поля.

#more
В отличие от типа с флагами и опциональными полями, оно не допускает невозможных состояний. Дискриминант работает и при деструктуризации. С `never` в `default` даёт проверку полноты. Так описывают состояния загрузки, экшены редьюсера, события, ответы API.
::

::question
Как написать свой type guard?

#answer
Функция с возвращаемым типом `x is T`, которая возвращает `boolean`. Если вернула `true`, компилятор сужает аргумент до `T`.

#more
Компилятор не проверяет тело: неполная проверка — тот же `as`, ошибка всплывёт в рантайме. Для `unknown` удобен `in`: после `'id' in x` можно читать `x.id`. Простые проверки вида `x => x !== undefined` компилятор превращает в предикат сам. Для данных извне надёжнее схема (zod), где тип выводится из проверки.
::

::question
Что такое проверка полноты?

#answer
Приём, при котором в `default` значение передают в функцию с параметром `never`. Если обработаны не все варианты объединения, тип там не `never`, и компиляция падает.

#more
`assertNever(value: never): never` ещё и бросает ошибку в рантайме, если пришло значение, которого нет в типе. Короткая форма без рантайм-части — `value satisfies never`. Альтернатива `switch` — объект-обработчик `Record<State['status'], ...>`: компилятор требует все ключи.
::

::question
Чем type guard отличается от функции-утверждения?

#answer
Предикат `x is T` возвращает `boolean` и используется в условии — две ветки. Утверждение `asserts x is T` ничего не возвращает и бросает ошибку — после вызова одна ветка, где тип сужен.

#more
Утверждения удобны для предусловий в начале функции и в тестах. Ограничение: имя функции должно иметь явный тип, стрелка без аннотации даёт TS2775. Обе формы — обещания, которые компилятор не сверяет с реализацией.
::

::question
Почему сужение не работает внутри колбэка?

#answer
Колбэк может выполниться позже, когда переменная уже переприсвоена. Для `let`, которому присваивают значение после создания колбэка, компилятор сбрасывает сужение.

#more
Если присваиваний после колбэка нет, сужение сохраняется. Решение — `const` или копия в константу перед колбэком. Обратный случай: сужение свойства объекта не сбрасывается после вызова функции, хотя та могла его изменить — компилятор сознательно так делает, чтобы не требовать повторных проверок.
::

## Практика

::practice{title="Состояние загрузки без невозможных комбинаций"}
Компонент хранит состояние так, и в коде повсюду `data!`:

```ts
type State = {
  loading: boolean;
  error?: string;
  data?: Product[];
};
```

Перепиши тип и функцию отрисовки, чтобы `!` не понадобился, а добавление нового состояния ломало компиляцию.

#solution
```ts
type State =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: Product[] }
  | { status: 'error'; error: string };

function assertNever(value: never): never {
  throw new Error(`Unexpected state: ${JSON.stringify(value)}`);
}

function render(state: State): string {
  switch (state.status) {
    case 'idle': return '';
    case 'loading': return 'Загрузка...';
    case 'success': return state.data.map((p) => p.title).join(', ');
    case 'error': return `Ошибка: ${state.error}`;
    default: return assertNever(state);
  }
}
```

В ветке `success` поле `data` существует по типу, без `!`. Состояние «загружается и с ошибкой» больше нельзя выразить. Добавишь `{ status: 'empty' }` — `assertNever(state)` не скомпилируется, пока ветка не появится. В проверке ветка `default` с необработанным вариантом дала ошибку компиляции, а рантайм-вызов с неизвестным статусом бросил исключение.
::

::practice{title="Почему тип есть, а значения нет?"}
Компилятор доволен, а в рантайме `Cannot read properties of undefined (reading 'toUpperCase')`:

```ts
function isUser(x: unknown): x is User {
  return typeof x === 'object' && x !== null;
}

const data: unknown = await res.json();
if (isUser(data)) greet(data.name.toUpperCase());
```

#solution
Предикат проверяет только «это объект», а обещает `User`. Компилятор не сверяет тело с `x is User` и поверил. Проверка должна охватывать то, что используется:

```ts
function isUser(x: unknown): x is User {
  return (
    typeof x === 'object' && x !== null &&
    'id' in x && typeof x.id === 'number' &&
    'name' in x && typeof x.name === 'string'
  );
}
```

Надёжнее — схема, где тип выводится из проверки:

```ts
import { z } from 'zod';
const UserSchema = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof UserSchema>;

const user = UserSchema.parse(await res.json());   // либо User, либо исключение с описанием
```

Тогда тип и проверка не разойдутся: меняешь схему — меняется тип. В проверке «врущий» предикат пропустил `{ id: 1 }`, и вызов `toUpperCase` бросил `TypeError`, а полный — вернул `false`.
::

::practice{title="Отфильтруй и сохрани тип"}
Нужно получить из списка только товары со скидкой и сразу работать с `discount` как с числом:

```ts
type Product = { id: number; title: string; discount: number | null };
declare const products: Product[];

const discounted = products.filter((p) => p.discount !== null);
discounted.map((p) => p.discount * 100);   // ошибка: 'p.discount' is possibly 'null'
```

#solution
Выведенный предикат сужает только сам параметр, а не его свойство: `filter` вернул `Product[]`, и `discount` остался `number | null`. Нужно явно описать, во что превращается элемент:

```ts
type Discounted = Product & { discount: number };

const discounted = products.filter((p): p is Discounted => p.discount !== null);
discounted.map((p) => p.discount * 100);   // ок: discount — number
```

Или преобразовать за один проход, чтобы предикат не понадобился:

```ts
const percents = products.flatMap((p) => (p.discount === null ? [] : [p.discount * 100]));
```

Явный предикат — снова обещание: если условие и тип разойдутся, компилятор не заметит. `flatMap` безопаснее, потому что тип выводится из кода. В проверке без предиката обращение к `p.discount * 100` не скомпилировалось, с предикатом и с `flatMap` — прошло и дало верный результат.
