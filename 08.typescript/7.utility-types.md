# Утилитарные типы

Встроенные дженерик-типы, которые строят новые типы из существующих: `Partial`, `Required`, `Readonly`, `Pick`, `Omit`, `Record`, `Exclude`, `Extract`, `NonNullable`, `Parameters`, `ReturnType`, `Awaited` и другие. Спрашивают разницу `Pick` и `Omit`, зачем `Partial` и как устроен `Exclude`. Глубже — почему `Omit` ломает размеченные объединения и не проверяет ключи, почему `Partial` и `Readonly` поверхностные и что `ReturnType` делает с перегрузками.

::tldr
- **Утилиты — обычные дженерик-типы из стандартной библиотеки,** написанные на mapped и условных типах. Их можно прочитать в `lib.es5.d.ts` и написать самому.
- **`Partial`, `Required`, `Readonly` меняют модификаторы свойств, и только на верхнем уровне.** Вложенные объекты остаются как были.
- **`Pick` проверяет ключи, `Omit` — нет:** опечатка в `Omit` молча ничего не убирает. На объединении `Omit` оставляет только общие ключи и теряет дискриминант.
- **`Exclude` и `Extract` фильтруют объединение,** потому что условный тип над параметром распределяется по вариантам.
- **`Parameters`, `ReturnType`, `Awaited` выводят типы из функций,** чтобы не дублировать их. У перегруженной функции берётся последняя сигнатура.
::

---

## Зачем утилиты

Сквозной пример — товар в магазине:

```ts
type Product = {
  id: number;
  title: string;
  price: number;
  tags?: string[];
  meta: { color: string };
};
```

Для формы создания нужен товар без `id`, для обновления — `id` и любые поля, для карточки — только название и цена. Описывать каждый тип заново — значит разойтись с `Product` при первом же изменении. Утилиты выводят производные типы из одного источника:

```ts
type CreateProduct = Omit<Product, 'id'>;
type UpdateProduct = Pick<Product, 'id'> & Partial<Omit<Product, 'id'>>;
type ProductCard = Pick<Product, 'title' | 'price'>;
```

Добавишь поле в `Product` — оно появится во всех производных типах.

Утилиты не встроены в компилятор: это обычные объявления в `lib.es5.d.ts`. Например:

```ts
type Partial<T> = { [P in keyof T]?: T[P] };
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Exclude<T, U> = T extends U ? never : T;
```

Как устроены mapped и условные типы, разобрано в [Продвинутых типах](/content/typescript/advanced-types). Здесь — что делает каждая утилита и где она подводит. Начнём с модификаторов.

## Модификаторы свойств

### Partial

Делает все свойства необязательными. Типичное место — патч для обновления:

```ts
function updateProduct(id: number, patch: Partial<Product>) { /* ... */ }
updateProduct(1, { price: 100 });
```

Две тонкости. Первая — **`Partial` поверхностный**: `{ meta: {} }` не подходит, `meta.color` по-прежнему обязателен. Рекурсивный вариант пишут сами (`DeepPartial` — в [Продвинутых типах](/content/typescript/advanced-types)).

Вторая — **необязательное свойство принимает явный `undefined`**, и при слиянии он затирает значение:

```ts
const patch: Partial<Product> = { title: undefined };
const merged = { ...product, ...patch };
// по типу merged.title — string, в рантайме — undefined
```

Компилятор считает, что необязательное свойство либо отсутствует, либо содержит `string`, и при спреде оставляет `string`. Опция `exactOptionalPropertyTypes` запрещает явный `undefined` в необязательном свойстве и закрывает эту дыру (подробно — в [Настройке проекта](/content/typescript/project-setup)).

### Required

Обратная операция — убирает `?`. Вместе с ним уходит и `undefined`, который `?` добавлял: `Required<{ a?: string }>` — `{ a: string }`. Пример — конфиг с заполненными значениями по умолчанию: на входе `Partial<Config>`, после слияния — `Required<Config>`.

### Readonly

Запрещает присваивание свойствам:

```ts
const frozen: Readonly<Product> = product;
frozen.price = 1;              // ошибка: read-only property
frozen.meta.color = 'red';     // компилируется: вложенное не защищено
```

`Readonly` тоже поверхностный и существует только в типах: в рантайме объект изменяем. `Object.freeze` замораживает в рантайме (тоже на один уровень) и возвращает `Readonly<T>`. Для массивов есть `ReadonlyArray<T>` или `readonly T[]` — без `push` и `sort`.

Модификаторы меняют свойства. Следующая группа выбирает, какие свойства оставить.

## Выбор свойств

### Pick и Omit

`Pick<T, K>` оставляет перечисленные ключи, `Omit<T, K>` убирает их. Похоже на зеркальную пару, но объявлены они по-разному:

```ts
type Pick<T, K extends keyof T> = { [P in K]: T[P] };
type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>;
```

У `Pick` ключи ограничены `keyof T`, у `Omit` — любыми строками. Поэтому опечатка в `Omit` не ловится:

```ts
type BadPick = Pick<Product, 'colour'>;   // ошибка: 'colour' нет в Product
type NoId = Omit<Product, 'idd'>;         // компилируется, id остался
```

Так сделано намеренно: `Omit` используют и в дженериках, где ключ может отсутствовать. Если нужна проверка, пишут строгий вариант:

```ts
type StrictOmit<T, K extends keyof T> = Omit<T, K>;
```

### Omit и объединения

Главная ловушка. `keyof` объединения — только **общие** ключи, а `Omit` строится через `keyof T`:

```ts
type Shape =
  | { kind: 'circle'; r: number; id: string }
  | { kind: 'square'; side: number; id: string };

type ShapeNoId = Omit<Shape, 'id'>;   // { kind: 'circle' | 'square' } — r и side пропали
```

Вместо объединения двух вариантов получился один объект с общим полем. Решение — применить `Omit` к каждому варианту отдельно, через распределяющий условный тип:

```ts
type DistributiveOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;

type ShapeNoId = DistributiveOmit<Shape, 'id'>;
// { kind: 'circle'; r: number } | { kind: 'square'; side: number }
```

Это частая проблема с пропсами компонентов, которые описаны объединением: обёртка через `Omit<Props, 'className'>` незаметно ломает их.

### Record

`Record<K, V>` — объект с ключами `K` и значениями `V`. С объединением литералов он требует все ключи, со `string` — описывает словарь:

```ts
type Stock = Record<'tea' | 'pot', number>;
const st: Stock = { tea: 1 };   // ошибка: Property 'pot' is missing

const prices: Record<string, number> = {};
prices.missing;   // number — хотя в рантайме undefined
```

Во втором случае тип обманывает: чтение несуществующего ключа даёт `number`. `noUncheckedIndexedAccess` добавляет `undefined` к чтению по индексу. Для словаря, где ключи появляются и исчезают, честнее `Map<string, number>` или `Partial<Record<string, number>>`.

От объектов перейдём к объединениям.

## Фильтрация объединений

```ts
type Status = 'idle' | 'loading' | 'success' | 'error';

type Active = Exclude<Status, 'idle'>;                  // 'loading' | 'success' | 'error'
type Circle = Extract<Shape, { kind: 'circle' }>;       // вариант circle целиком
type Defined = NonNullable<string | null | undefined>;  // string
```

`Exclude<T, U>` убирает из `T` варианты, совместимые с `U`, `Extract` — оставляет их. Оба работают на объединениях, а не на свойствах объекта: для свойств — `Omit` и `Pick`.

Как одна строка `T extends U ? never : T` фильтрует объединение? Условный тип над «голым» параметром **распределяется**: для `'idle' | 'loading'` он вычисляется отдельно для каждого варианта и результаты объединяются, а `never` из объединения исчезает:

```text
Exclude<'idle' | 'loading', 'idle'>
= ('idle' extends 'idle' ? never : 'idle') | ('loading' extends 'idle' ? never : 'loading')
= never | 'loading'
= 'loading'
```

`NonNullable<T>` сейчас объявлен как `T & {}`: пересечение с `{}` убирает `null` и `undefined`, а остальные типы не меняет.

Остаётся последняя группа — типы, которые выводятся из функций и классов.

## Типы из функций и классов

```ts
function createOrder(userId: number, items: string[], promo?: string) {
  return { id: 1, userId, items, promo };
}

type Args = Parameters<typeof createOrder>;      // [userId: number, items: string[], promo?: string]
type Items = Parameters<typeof createOrder>[1];  // string[]
type Order = ReturnType<typeof createOrder>;     // { id: number; userId: number; items: string[]; promo: string | undefined }
```

Это способ получить тип, который библиотека не экспортирует: аргументы колбэка, результат фабрики, тип стора.

`typeof` обязателен: утилиты принимают **тип** функции, а `createOrder` — значение.

### Перегрузки

У перегруженной функции `Parameters` и `ReturnType` берут **последнюю** сигнатуру:

```ts
function parse(v: string): number;
function parse(v: number): string;
function parse(v: string | number) { /* ... */ }

type R = ReturnType<typeof parse>;   // string — только из последней перегрузки
```

Условный тип с `infer` не умеет перебирать перегрузки, поэтому выбирает последнюю. Для перегруженных функций тип пишут явно.

### Awaited

`ReturnType` асинхронной функции — `Promise<T>`. Чтобы получить `T`, нужен `Awaited`:

```ts
async function loadUser() { return { id: 1, name: 'Аня' }; }

type User = Awaited<ReturnType<typeof loadUser>>;   // { id: number; name: string }
```

`Awaited` рекурсивен: `Awaited<Promise<Promise<number>>>` — `number`. Он же моделирует `await` и `Promise.all` в стандартной библиотеке.

### Классы

```ts
class ApiClient {
  constructor(public baseUrl: string, public timeout = 5000) {}
}

type Args = ConstructorParameters<typeof ApiClient>;   // [baseUrl: string, timeout?: number]
type Client = InstanceType<typeof ApiClient>;          // ApiClient
```

`typeof ApiClient` — тип конструктора, `ApiClient` в позиции типа — тип экземпляра. `InstanceType` нужен, когда класс передаётся как значение, например в фабрику `create<T extends new (...args: any) => any>(ctor: T): InstanceType<T>`.

### Строки и прочее

`Uppercase`, `Lowercase`, `Capitalize`, `Uncapitalize` работают с литералами и вместе с шаблонными типами строят имена: `` `on${Capitalize<'click' | 'focus'>}` `` — `'onClick' | 'onFocus'`. Ещё есть `NoInfer` (запрет вывода, подробно — в [Дженериках](/content/typescript/generics)), `ThisParameterType` и `OmitThisParameter` для функций с `this`.

## Красные флаги в ответе

- **«`Partial` делает необязательными все поля, включая вложенные».** Только верхний уровень.
- **«`Readonly` защищает объект».** Только в типах и только верхний уровень, в рантайме объект изменяем.
- **«`Omit` — то же, что `Pick`, только наоборот».** `Omit` не проверяет ключи и на объединении теряет варианты.
- **«`Exclude` убирает свойства из объекта».** Он фильтрует варианты объединения.
- **«`ReturnType` перегруженной функции — объединение всех вариантов».** Берётся последняя сигнатура.

## Как спрашивают на собеседовании

::question
В чём разница между Pick и Omit?

#answer
`Pick<T, K>` оставляет указанные ключи, `Omit<T, K>` — все, кроме указанных. `Omit` удобнее, когда убрать нужно меньше, чем оставить.

#more
`Pick` ограничивает ключи `keyof T`, а `Omit` принимает любые строки, поэтому опечатка в `Omit` не ловится — помогает `StrictOmit<T, K extends keyof T>`. На объединении `Omit` оставляет только общие ключи и теряет дискриминант, для объединений пишут распределяющий вариант `T extends unknown ? Omit<T, K> : never`.
::

::question
Зачем Partial, если можно поставить ? на каждое свойство?

#answer
Чтобы не дублировать тип. `Partial<Product>` выводится из `Product` и обновляется вместе с ним, а копия с `?` разойдётся с оригиналом при первом изменении.

#more
`Partial` поверхностный, для вложенных объектов нужен свой `DeepPartial`. Необязательное свойство принимает явный `undefined`, и при слиянии `{ ...product, ...patch }` он затирает значение, хотя тип остаётся `string`. `exactOptionalPropertyTypes` это запрещает.
::

::question
Как работает Exclude?

#answer
`type Exclude<T, U> = T extends U ? never : T`. Условный тип над параметром распределяется по вариантам объединения: каждый вариант, совместимый с `U`, превращается в `never`, а `never` из объединения исчезает.

#more
Распределение происходит только для «голого» параметра: `[T] extends [U]` проверяет объединение целиком. На этом же механизме построены `Extract` и распределяющий `Omit`. `NonNullable` сейчас объявлен как `T & {}`, без условного типа.
::

::question
Можно ли комбинировать утилитарные типы?

#answer
Да, это обычные дженерики: `Pick<Product, 'id'> & Partial<Omit<Product, 'id'>>` — обязательный `id` и любые другие поля. Так из одного типа выводят типы для создания, обновления и отображения.

#more
Длинные комбинации называют отдельным псевдонимом, иначе подсказки в редакторе становятся нечитаемыми. Если комбинация повторяется, её оформляют своей утилитой: `type WithRequired<T, K extends keyof T> = T & Required<Pick<T, K>>`.
::

::question
Как получить тип, который библиотека не экспортирует?

#answer
Вывести из того, что экспортировано: `Parameters<typeof fn>[0]` — тип первого аргумента, `ReturnType<typeof createStore>` — тип стора, `Awaited<ReturnType<typeof load>>` — результат асинхронной функции.

#more
У перегруженной функции берётся последняя сигнатура. Для классов — `ConstructorParameters` и `InstanceType`. Для пропсов компонентов — `ComponentProps<typeof Button>` в React (подробно — в [TypeScript с React](/content/typescript/ts-with-react)).
::

::question
Защищает ли Readonly объект от изменения?

#answer
Только на этапе компиляции и только верхний уровень. Присваивание `frozen.price` — ошибка, а `frozen.meta.color` компилируется. В рантайме объект изменяем.

#more
Для рантайм-защиты — `Object.freeze`, тоже поверхностный, он возвращает `Readonly<T>`. Для массивов — `readonly T[]`: без `push` и `sort`. Глубокий `DeepReadonly` пишут рекурсивным mapped-типом. `as const` делает литерал глубоко `readonly` в типах.
::

## Практика

::practice{title="Типы для CRUD из одной модели"}
Есть модель пользователя. Опиши типы для создания (без `id` и `createdAt`), обновления (`id` обязателен, остальное нет) и списка (только `id`, `name`, `role`), не повторяя поля.

```ts
type User = {
  id: number;
  name: string;
  email: string;
  role: 'admin' | 'user';
  createdAt: Date;
};
```

#solution
```ts
type ServerFields = 'id' | 'createdAt';

type CreateUser = Omit<User, ServerFields>;
type UpdateUser = Pick<User, 'id'> & Partial<Omit<User, ServerFields>>;
type UserListItem = Pick<User, 'id' | 'name' | 'role'>;

const create: CreateUser = { name: 'Аня', email: 'a@shop.ru', role: 'user' };
const update: UpdateUser = { id: 1, role: 'admin' };
const item: UserListItem = { id: 1, name: 'Аня', role: 'user' };
```

`ServerFields` вынесен, чтобы список полей, которые заполняет сервер, жил в одном месте. Для `Omit` с важными ключами лучше строгий вариант, иначе переименование поля в `User` молча сломает `CreateUser`. В проверке обновление без `id` и создание с `id` не скомпилировались.
::

::practice{title="Почему пропал radius?"}
Обёртка над компонентом фигуры убирает `id` и передаёт остальное. После этого обращение к `r` не компилируется:

```ts
type ShapeProps =
  | { kind: 'circle'; r: number; id: string }
  | { kind: 'square'; side: number; id: string };

type WrapperProps = Omit<ShapeProps, 'id'>;

function Wrapper(props: WrapperProps) {
  if (props.kind === 'circle') return props.r;   // ошибка: r не существует
}
```

#solution
`Omit` строится через `keyof ShapeProps`, а `keyof` объединения — только общие ключи `kind` и `id`. Результат — один объект `{ kind: 'circle' | 'square' }`, и сужение по `kind` уже не к чему применить.

```ts
type DistributiveOmit<T, K extends PropertyKey> = T extends unknown ? Omit<T, K> : never;

type WrapperProps = DistributiveOmit<ShapeProps, 'id'>;

function Wrapper(props: WrapperProps) {
  if (props.kind === 'circle') return props.r;   // ок
}
```

Условный тип над параметром распределяется: `Omit` применяется к каждому варианту отдельно, и объединение сохраняется. В проверке `keyof Omit<ShapeProps, 'id'>` оказался `'kind'`, а распределяющий вариант сохранил `r` в ветке `circle`.
::

::practice{title="Тип результата без дублирования"}
Функция загрузки корзины объявлена в модуле API. Опиши тип корзины и тип аргументов для обёртки с повтором запроса, не копируя их.

```ts
export async function loadCart(userId: number, opts?: { signal?: AbortSignal }) {
  return { userId, items: [{ sku: 'tea', qty: 2 }], total: 980 };
}
```

#solution
```ts
type Cart = Awaited<ReturnType<typeof loadCart>>;
type LoadCartArgs = Parameters<typeof loadCart>;

async function withRetry(...args: LoadCartArgs): Promise<Cart> {
  try {
    return await loadCart(...args);
  } catch {
    return loadCart(...args);
  }
}
```

`ReturnType` даёт `Promise<...>`, `Awaited` его разворачивает. `Parameters` — кортеж с именами и необязательностью, поэтому `...args` сохраняет сигнатуру. Изменится `loadCart` — обёртка обновится сама. В проверке `Cart['items'][number]['qty']` оказался `number`, а `withRetry(1)` вернул корзину.
::
