# Введение в TypeScript

Что такое TypeScript, что он проверяет и, главное, чего не проверяет. Спрашивают, чем TS отличается от JS, что такое стирание типов и структурная типизация, когда писать аннотации. Глубже — где система типов намеренно нестрогая, почему `as` ничего не преобразует и как устроены инструменты после выхода нативного компилятора TypeScript 7.

::tldr
- **TypeScript — JavaScript со статическими типами, которые существуют только при проверке.** Компилятор стирает их, и в рантайме остаётся обычный JavaScript без информации о типах.
- **Типизация структурная:** тип совместим, если у значения есть нужные свойства, а имя типа неважно. Лишние свойства запрещены только в свежих объектных литералах.
- **TypeScript проверяет то, что знает, и намеренно нестрог в нескольких местах:** индексы массивов, ковариантные массивы, бивариантные методы, `as` и `any`. Данные из сети типизированы только на словах — их проверяют в рантайме.
- **`as` — подсказка компилятору, а не преобразование.** Значение не меняется, и если подсказка неверна, ошибка случится при выполнении.
- **Проверка типов и превращение в JavaScript — разные задачи.** Типы проверяет `tsc` (с версии 7 — нативный и в разы быстрее), а код для запуска собирают esbuild, SWC или сам Node.js, просто стирая типы.
::

---

## Что такое TypeScript

Сквозной пример — клиент API магазина:

```ts
interface Product {
  id: number;
  title: string;
  price: number;
}

async function getProduct(id: number): Promise<Product> {
  const res = await fetch(`/api/products/${id}`);
  return res.json();
}

function formatPrice(product: Product): string {
  return `${product.price.toLocaleString('ru-RU')} ₽`;
}
```

TypeScript — надмножество JavaScript: любой корректный JavaScript-код — корректный TypeScript, а сверху добавлены **аннотации типов**. Компилятор читает их, проверяет, что код использует значения правильно — `formatPrice` получает объект с `price`, `getProduct` вызывают с числом, — и сообщает об ошибках до запуска.

Почему это полезно, хорошо видно на этом примере:

- переименовали `price` в `cost` — компилятор покажет все места, которые нужно поправить;
- автодополнение знает, какие поля есть у товара;
- сигнатура функции — документация, которая не устаревает, потому что её проверяют.

### Типы стираются

После проверки компилятор удаляет все типы, и остаётся JavaScript. В проверке `tsc` превратил функцию с `interface Product` и аннотациями `: number` в `export function total(items) { ... }` — без единого упоминания типов. Отсюда главное свойство языка: **в рантайме типов нет**. Нельзя спросить у значения, является ли оно `Product`, нельзя перегрузить функцию по типу аргумента, а аннотация не превращает строку в число.

Почти весь синтаксис TypeScript можно просто стереть. Исключения — конструкции, которые порождают код: `enum`, `namespace` с кодом, параметры-свойства в конструкторе (`constructor(private id: number)`). Их нельзя убрать, не написав взамен JavaScript. Это стало важно, когда Node.js научился запускать `.ts` напрямую: он только стирает типы, и файл с `enum` падает с `ERR_UNSUPPORTED_TYPESCRIPT_SYNTAX`. Проверено в Node.js 24. Опция `erasableSyntaxOnly` запрещает такой синтаксис, чтобы код работал с любым инструментом стирания.

Если типы стираются, по каким правилам компилятор решает, что типы совместимы?

## Структурная типизация

TypeScript сравнивает типы по **структуре**, а не по имени:

```ts
class Teapot {
  id = 7;
  title = 'Чайник';
  price = 2490;
  volume = 1.7;
}

const product: Product = new Teapot();   // можно: у Teapot есть id, title и price
```

`Teapot` нигде не объявлен как `Product`, но у него есть все нужные свойства — значит, он подходит. Лишние свойства не мешают. Это естественно для JavaScript, где объекты создают литералами и передают как угодно. В Java или C# совместимость определяется объявлением (`implements`), и такой код не скомпилировался бы.

Обратная сторона — два разных по смыслу типа с одинаковой структурой взаимозаменяемы: `UserId` и `ProductId`, если оба — `number`. Номинальную типизацию эмулируют брендами (подробно — в [Продвинутых типах](/content/typescript/advanced-types)).

### Проверка лишних свойств

Есть исключение, которое удивляет. Свежий объектный литерал с лишним свойством — ошибка:

```ts
const tea: Product = { id: 1, title: 'Чай', price: 490, sale: true };
// Object literal may only specify known properties, and 'sale' does not exist in type 'Product'

const draft = { id: 1, title: 'Чай', price: 490, sale: true };
const ok: Product = draft;   // ошибки нет
```

Это не нарушение структурной типизации, а отдельная проверка: лишнее свойство в литерале, который сразу присвоен типу, почти всегда опечатка (`tilte` вместо `title`). Через переменную объект может использоваться и в других местах, поэтому проверки нет. Это частый вопрос на собеседовании.

Структура определяет совместимость. А откуда компилятор знает типы, если аннотаций почти нет?

## Вывод и аннотации

Большую часть типов компилятор **выводит** сам:

```ts
const status = 'paid';    // тип 'paid' — const не изменится
let state = 'paid';       // тип string — let может измениться
const total = [490, 2490].reduce((a, b) => a + b, 0);   // number
```

Аннотации пишут там, где вывод не справляется или где тип — контракт:

- **параметры функций** — их тип не из чего вывести;
- **возвращаемые типы публичных функций** — чтобы случайное изменение реализации не изменило API;
- **пустые значения**, которые заполнятся позже: `const items: Product[] = []`;
- **сложные выражения**, где выведенный тип слишком широкий или нечитаемый.

Локальные переменные и колбэки обычно не аннотируют: вывод точнее и не устаревает.

### as — подсказка, а не преобразование

Утверждение типа `value as Product` говорит компилятору: «поверь, здесь `Product`». Значение при этом **не меняется** — в отличие от приведения типов в C++ или Java, никакого преобразования нет. Компилятор пропускает `as` только между совместимыми типами: `42 as string` — ошибка, а двойное `42 as unknown as string` — уже нет, и это прямой путь к падению в рантайме. Оператор `!` (`user!.name`) — то же утверждение: «здесь не `null`».

`as` уместен, когда ты знаешь больше компилятора, например после проверки, которую он не видит. Во всех остальных случаях он прячет ошибки.

Мы подошли к главному вопросу: насколько вообще можно доверять типам?

## Где TypeScript не защищает

Система типов TypeScript намеренно **нестрогая** (unsound): некоторые ошибки она пропускает ради удобства и совместимости с JavaScript. Все примеры ниже проходят проверку `tsc` в строгом режиме и падают при выполнении — это проверено:

- **данные извне.** `res.json()` возвращает `any`, и `getProduct` из примера «возвращает» `Product`, что бы ни прислал сервер. Если пришёл `{ "id": "7" }` без `title`, обращение к `title.toUpperCase()` упадёт. Типы описывают ожидания, а не проверяют данные;
- **индекс массива.** `prices[0]` имеет тип `number`, даже если массив пуст. Опция `noUncheckedIndexedAccess` делает его `number | undefined`;
- **ковариантные массивы.** Массив кошек можно присвоить переменной типа «массив животных» и положить туда собаку — у кошки в массиве не окажется метода `meow`;
- **бивариантные методы.** Метод, объявленный в интерфейсе через синтаксис метода, принимает обработчик с более узким параметром, и вызов с другим событием падает;
- **`any` и `as`** выключают проверку там, где их написали, и заражают всё, что из них выводится.

Практический вывод: доверять типам можно внутри кода, который ты контролируешь. На **границах** — ответ сервера, `localStorage`, параметры URL, сообщения из `postMessage` — данные проверяют в рантайме, например схемой Zod, которая заодно выводит тип (подробно — в [Асинхронности и DOM](/content/typescript/async-and-dom)).

## Компилятор и инструменты

У `tsc` две роли: **проверить типы** и **выдать JavaScript**. В современных проектах их разделяют:

- **сборку** делают быстрые инструменты, которые просто стирают типы: :term[esbuild]{def="быстрый сборщик и транспилятор JavaScript и TypeScript на Go"} и :term[SWC]{def="быстрый компилятор JavaScript и TypeScript на Rust"} внутри :term[Vite]{def="сборщик и dev-сервер фронтенда на ES-модулях"} и Next.js, сам Node.js для `.ts`-файлов. Они не проверяют типы и работают с каждым файлом отдельно;
- **проверку** делает `tsc --noEmit` в редакторе и в CI.

Отсюда настройки вроде `isolatedModules` и `verbatimModuleSyntax`: они запрещают конструкции, которые нельзя правильно превратить в JavaScript, глядя на один файл. Как устроен этот конвейер — в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling), а смысл опций tsconfig — в [Настройке проекта](/content/typescript/project-setup).

В 2026 году инструменты сильно изменились. TypeScript 6.0 стал последней версией компилятора на JavaScript и поменял значения по умолчанию: `strict` теперь включён сразу. TypeScript 7.0 — тот же язык, но компилятор переписан на Go: проверка типов в больших проектах ускорилась примерно на порядок. У нативного компилятора пока нет программного API, поэтому инструменты, которые встраиваются в компилятор (`vue-tsc`, часть правил typescript-eslint), продолжают работать на TypeScript 6. Все примеры этой главы проверены на TypeScript 7.

## Красные флаги в ответе

- **«TypeScript проверяет типы в рантайме».** Типы стираются при компиляции. В рантайме — обычный JavaScript.
- **«`as` преобразует значение».** Это подсказка компилятору. Значение не меняется, и неверная подсказка — ошибка при выполнении.
- **«Если код скомпилировался, ошибок типов не будет».** Система типов намеренно нестрогая: индексы массивов, ковариантные массивы, `any`, данные извне.
- **«Типы совместимы, если совпадают имена».** Типизация структурная: важны свойства, а не имя.
- **«Ответ API типизирован, раз я написал `Promise<Product>`».** Это обещание. Данные извне проверяют в рантайме.

## Как спрашивают на собеседовании

::question
Что такое TypeScript и чем он отличается от JavaScript?

#answer
Надмножество JavaScript со статическими типами. Компилятор проверяет типы до запуска и удаляет их, поэтому в рантайме остаётся обычный JavaScript. Дают раннее обнаружение ошибок, автодополнение и безопасный рефакторинг.

#more
Почти весь синтаксис TS стирается без генерации кода. Исключения — `enum`, `namespace` с кодом и параметры-свойства, их не понимают инструменты, которые только стирают типы, включая Node.js. Проверку и сборку разделяют: типы проверяет `tsc`, а JavaScript собирают esbuild и SWC.
::

::question
Что такое стирание типов?

#answer
При компиляции все аннотации, интерфейсы и псевдонимы типов удаляются. В рантайме нет информации о типах TypeScript: нельзя проверить, что значение «является» интерфейсом.

#more
Поэтому проверки в рантайме пишут вручную или схемами (Zod), которые выводят тип из схемы. Нельзя перегрузить функцию по типу аргумента — перегрузки TS описывают одну реализацию. Синтаксис, который требует генерации кода, запрещает опция `erasableSyntaxOnly`.
::

::question
Что такое структурная типизация?

#answer
Совместимость типов определяется набором свойств и их типов, а не именем типа. Объект подходит под интерфейс, если у него есть нужные свойства, даже если он нигде не объявлен как этот интерфейс.

#more
Лишние свойства не мешают — кроме свежего объектного литерала, который сразу присвоен типу: там TS проверяет лишние свойства, потому что это почти всегда опечатка. Через переменную проверки нет. Из-за структурности разные по смыслу типы с одной формой взаимозаменяемы, и номинальность эмулируют брендами.
::

::question
Чем утверждение типа отличается от приведения типов?

#answer
Утверждение `value as Type` только говорит компилятору, какой тип у значения, и ничего не меняет в рантайме. Приведение в C++ или Java действительно преобразует значение.

#more
TS пропускает `as` только между совместимыми типами, двойное `as unknown as` снимает и это ограничение. Неверное утверждение — ошибка при выполнении, которую компилятор не увидит. `!` — тоже утверждение: «не `null`». Вместо `as` лучше сужение проверкой или валидация схемой.
::

::question
Когда писать аннотации типов, а когда полагаться на вывод?

#answer
Аннотации — для параметров функций, возвращаемых типов публичных функций и пустых значений, которые заполнятся позже. Вывод — для локальных переменных и колбэков.

#more
Явный возвращаемый тип публичной функции фиксирует контракт: изменение реализации не изменит API незаметно, а ошибка покажется в функции, а не у всех вызывающих. `const` сужает литералы до точного значения, `let` расширяет до общего типа.
::

::question
Где TypeScript не защищает от ошибок?

#answer
На границах с внешним миром: ответ сервера, `localStorage`, параметры URL. Типы описывают ожидания, а не проверяют данные. Плюс `any` и `as`, которые выключают проверку.

#more
Система намеренно нестрогая: индекс массива имеет тип элемента даже для пустого массива (лечится `noUncheckedIndexedAccess`), массивы ковариантны и позволяют положить «не того» потомка, методы проверяются бивариантно. Данные на границах проверяют в рантайме, а строгость повышают опциями компилятора.
::

## Практика

::practice{title="Почему упало, если компилятор молчал?"}
Код проходит `tsc --strict`, но в проде падает с `Cannot read properties of undefined (reading 'toUpperCase')`:

```ts
interface Product { id: number; title: string; price: number }

async function getProduct(id: number): Promise<Product> {
  const res = await fetch(`/api/products/${id}`);
  return res.json();
}

const product = await getProduct(7);
heading.textContent = product.title.toUpperCase();
```

#solution
`res.json()` возвращает `any`, и функция «обещает» `Product`, ничего не проверяя. Сервер прислал объект без `title` (или с другим именем поля), и тип оказался неправдой. Компилятор не может проверить данные, которых нет при компиляции.

Данные на границе проверяют в рантайме. Схема Zod делает это и выводит тип сама:

```ts
import { z } from 'zod';

const ProductSchema = z.object({
  id: z.number(),
  title: z.string(),
  price: z.number(),
});
type Product = z.infer<typeof ProductSchema>;

async function getProduct(id: number): Promise<Product> {
  const res = await fetch(`/api/products/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return ProductSchema.parse(await res.json());   // бросит, если данные не те
}
```

Теперь ошибка формата данных случается в одном месте и с понятным сообщением, а не где-то в интерфейсе. Тип `Product` не дублируется — он выводится из схемы.
::

::practice{title="Что пропустит компилятор?"}
Какие строки дадут ошибку компиляции в строгом режиме, а какие упадут только при выполнении?

```ts
interface Product { id: number; title: string }

const a: Product = { id: 1, title: 'Чай', price: 490 };
const b = { id: 1, title: 'Чай', price: 490 };
const c: Product = b;
const d = 42 as string;
const e: number = ([] as number[])[0];
const f = JSON.parse('{}') as Product;
```

#solution
- `a` — **ошибка компиляции**: лишнее свойство `price` в свежем литерале.
- `c` — **без ошибки**: объект пришёл через переменную, лишние свойства разрешены структурной типизацией.
- `d` — **ошибка компиляции**: `number` и `string` несовместимы, `as` такое не пропускает.
- `e` — **без ошибки компиляции**, но в рантайме `undefined` в переменной типа `number`: индекс массива без `noUncheckedIndexedAccess`.
- `f` — **без ошибки компиляции**, но у объекта нет ни `id`, ни `title`: `as` ничего не проверяет.

Все утверждения проверены `tsc` 7 в строгом режиме с `@ts-expect-error` на ожидаемых ошибках.
::
