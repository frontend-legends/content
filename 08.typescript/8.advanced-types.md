# Продвинутые типы

Программирование на уровне типов: mapped-типы, условные типы и `infer`, распределение по объединению, шаблонные литеральные типы, рекурсивные типы и брендирование. Спрашивают, как работает `infer`, что такое распределяющий условный тип и зачем нужны брендированные типы. Глубже — почему `IsNever<never>` даёт `never`, какие модификаторы сохраняет mapped-тип и где у рекурсии предел.

::tldr
- **Mapped-тип перебирает ключи:** `{ [K in keyof T]: ... }`. Над `keyof T` он сохраняет `readonly` и `?`, модификаторы снимаются через `-readonly` и `-?`, ключи переименовываются и отфильтровываются через `as`.
- **Условный тип — `if` для типов:** `T extends U ? X : Y`. `infer` внутри условия объявляет переменную, которую компилятор выводит из сопоставления.
- **Условный тип над голым параметром распределяется по объединению.** Отключается обёрткой `[T] extends [U]`. `never` — пустое объединение, поэтому распределение по нему даёт `never`.
- **Шаблонные литеральные типы строят и разбирают строки:** `` `${Size}-${Color}` `` перемножает варианты, а `infer` в шаблоне вытаскивает параметры из `'/items/:id'`.
- **Брендирование имитирует номинальную типизацию:** `string & { [brand]: 'UserId' }` не перепутать с обычной строкой и `OrderId`. В рантайме бренда нет.
::

## Зачем программировать на типах

Утилиты из стандартной библиотеки (подробно — в [Утилитарных типах](/content/typescript/utility-types)) покрывают частые случаи. Но в реальном коде нужны и свои: типизированные параметры маршрута из строки `'/items/:id'`, геттеры `getName` для каждого поля, ID, которые нельзя перепутать.

Система типов TypeScript — небольшой функциональный язык. Псевдоним с параметрами — функция, условный тип — ветвление, рекурсия — цикл. Этот язык работает только во время компиляции и стирается, поэтому каждый приём ниже — про проверки и подсказки, а не про рантайм.

Первый инструмент — перебор ключей.

---

## Mapped-типы

```ts
type Clone<T> = { [K in keyof T]: T[K] };
```

Для каждого ключа `K` из `keyof T` создаётся свойство с типом `T[K]`. Так устроены `Partial`, `Readonly`, `Pick` и `Record`.

### Модификаторы

Mapped-тип над `keyof T` называется **гомоморфным** и сохраняет модификаторы исходного типа:

```ts
type Product = { readonly id: number; title: string; tags?: string[] };

type C = Clone<Product>;   // { readonly id: number; title: string; tags?: string[] }
```

Модификаторы добавляют `+` (или без знака) и снимают `-`:

```ts
type Mutable<T> = { -readonly [K in keyof T]: T[K] };   // убрать readonly
type Concrete<T> = { [K in keyof T]-?: T[K] };          // убрать ?, как Required
```

Если перебирать не `keyof T`, а произвольное объединение ключей, модификаторы не переносятся: `{ [K in 'id' | 'title']: Product[K] }` даёт `{ id: number; title: string }` без `readonly`. Ещё одно свойство гомоморфных типов — на массивах и кортежах они дают массив и кортеж, а не объект с ключами `length` и `push`: `{ [K in keyof T]: string }` от `[number, boolean]` — `[string, string]`.

### Переименование и фильтрация ключей

Конструкция `as` после ключа задаёт новое имя:

```ts
type Getters<T> = { [K in keyof T as `get${Capitalize<string & K>}`]: () => T[K] };

type G = Getters<{ name: string; age: number }>;
// { getName: () => string; getAge: () => number }
```

`string & K` нужен потому, что ключ может быть числом или символом, а `Capitalize` принимает только строки. Если `as` даёт `never`, ключ исчезает — так фильтруют свойства по типу значения:

```ts
type OnlyFunctions<T> = { [K in keyof T as T[K] extends (...a: any[]) => any ? K : never]: T[K] };

type Api = { base: string; get(): void; post(): void };
type Methods = keyof OnlyFunctions<Api>;   // 'get' | 'post'
```

Здесь внутри mapped-типа появилось условие `T[K] extends ... ? K : never`. Это второй инструмент.

## Условные типы и infer

```ts
type IsString<T> = T extends string ? true : false;
```

`T extends U ? X : Y` — если `T` совместим с `U`, результат `X`, иначе `Y`. Само по себе это проверка. Сила появляется с `infer`: он объявляет переменную, которую компилятор **выводит** из сопоставления с образцом.

```ts
type ElementOf<T> = T extends readonly (infer E)[] ? E : never;
ElementOf<string[]>;   // string

type MyReturnType<T> = T extends (...args: any[]) => infer R ? R : never;
MyReturnType<() => Promise<number>>;   // Promise<number>
```

Образец — любой тип с «дырами»: элемент массива, возвращаемое значение, аргумент промиса, часть строки. Если тип не совпал с образцом, выбирается ветка «иначе».

`infer` можно вызывать рекурсивно и ограничивать:

```ts
type UnwrapPromise<T> = T extends Promise<infer U> ? UnwrapPromise<U> : T;
UnwrapPromise<Promise<Promise<string>>>;   // string

type FirstNum<T> = T extends [infer N extends number, ...unknown[]] ? N : never;
FirstNum<[42, 'a']>;   // 42
FirstNum<['a']>;       // never — первый элемент не число

type ToNumber<S> = S extends `${infer N extends number}` ? N : never;
ToNumber<'42'>;        // 42 — литерал-число из литерала-строки
```

Условные типы ведут себя неожиданно в одном важном случае — когда на вход приходит объединение.

## Распределение по объединению

```ts
type ToArray<T> = T extends unknown ? T[] : never;

ToArray<string | number>;   // string[] | number[], а не (string | number)[]
```

Если в условии слева стоит **голый параметр типа**, а на вход пришло объединение, условие вычисляется для каждого варианта отдельно и результаты объединяются. На этом построены `Exclude`, `Extract` и распределяющий `Omit`.

Чтобы проверить объединение целиком, параметр оборачивают в кортеж:

```ts
type ToArrayNonDist<T> = [T] extends [unknown] ? T[] : never;
ToArrayNonDist<string | number>;   // (string | number)[]
```

Распределяется только голый параметр: `{ v: T } extends { v: string }` уже не распределяется и для `string | number` даёт ветку «нет».

### Ловушки распределения

**`never`.** Для компилятора `never` — пустое объединение. Распределение по нему не вызывает условие ни разу и возвращает `never`:

```ts
type IsNeverNaive<T> = T extends never ? true : false;
IsNeverNaive<never>;   // never, а не true

type IsNever<T> = [T] extends [never] ? true : false;
IsNever<never>;        // true
```

**`boolean`.** Это `true | false`, поэтому `T extends true ? 'y' : 'n'` от `boolean` даёт `'y' | 'n'`.

Распределение работает и в шаблонных строках — там оно строит декартово произведение.

## Шаблонные литеральные типы

```ts
type Size = 'sm' | 'md';
type Color = 'red' | 'blue';

type ButtonClass = `${Size}-${Color}`;   // 'sm-red' | 'sm-blue' | 'md-red' | 'md-blue'
```

В шаблон можно подставить и примитив: `` `${number}px` `` принимает `'12px'` и отвергает `'abcpx'`. Но осторожно с размером: объединения перемножаются, и три объединения по 20 вариантов дают 8000 строк.

С `infer` шаблон работает в обратную сторону — разбирает строку. Параметры маршрута:

```ts
type RouteParams<S extends string> =
  S extends `${string}:${infer P}/${infer Rest}`
    ? { [K in P | keyof RouteParams<`/${Rest}`>]: string }
    : S extends `${string}:${infer P}`
      ? { [K in P]: string }
      : {};

type P = RouteParams<'/shop/:category/items/:id'>;   // { category: string; id: string }
```

Тип отрезает первый параметр, рекурсивно обрабатывает остаток и объединяет ключи. Так типизируют параметры в роутерах, например в Hono: опечатка в `params.categry` ловится по строке маршрута.

Рекурсия здесь не случайна — это третий инструмент.

## Рекурсивные типы

Тип может ссылаться на себя. Классика — JSON и глубокие версии утилит:

```ts
type Json = string | number | boolean | null | Json[] | { [key: string]: Json };

type DeepPartial<T> = T extends object ? { [K in keyof T]?: DeepPartial<T[K]> } : T;
type DeepReadonly<T> = { readonly [K in keyof T]: DeepReadonly<T[K]> };

type Settings = { theme: { color: string; dark: boolean }; locale: string };
const patch: DeepPartial<Settings> = { theme: { dark: true } };   // ок
```

`T extends object` в `DeepPartial` останавливает рекурсию на примитивах. Массивы обрабатываются корректно, потому что mapped-тип гомоморфный: `DeepPartial<string[]>` — `(string | undefined)[]`. Функции, `Date` и `Map` тоже объекты, и для них рекурсия порождает странные типы, поэтому в реальных библиотеках `DeepPartial` исключает их явно.

### Предел глубины

У рекурсии есть предел. Если тип раскрывается слишком глубоко, компилятор останавливается с ошибкой TS2589 «Type instantiation is excessively deep and possibly infinite». Обычная рекурсия, где результат собирается после рекурсивного вызова (`` `${S}${Repeat<...>}` ``), упирается в предел уже на нескольких десятках уровней. **Хвостовая** рекурсия, где рекурсивный вызов — весь результат ветки, а промежуточное состояние копится в параметре-аккумуляторе, разрешена до 999 уровней:

```ts
type BuildTuple<N extends number, Acc extends unknown[] = []> =
  Acc['length'] extends N ? Acc : BuildTuple<N, [...Acc, unknown]>;

BuildTuple<500>['length'];   // 500
```

Если тип упёрся в предел, это повод упростить его, а не наращивать хитрости: сложные типы замедляют редактор у всей команды.

От вычислений на типах перейдём к обратной задаче — сделать тип строже, чем позволяет структура.

## Брендированные типы

Типизация в TypeScript структурная: `UserId` и `OrderId`, объявленные как `string`, взаимозаменяемы (подробно — во [Введении](/content/typescript/introduction)). Перепутать ID — реальная ошибка, которую компилятор не видит.

Бренд добавляет к типу фиктивное свойство, которого нет в рантайме:

```ts
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };

type UserId = Brand<string, 'UserId'>;
type OrderId = Brand<string, 'OrderId'>;

function loadUser(id: UserId) { /* ... */ }

loadUser('u1');                  // ошибка: string — не UserId
loadUser('o1' as OrderId);       // ошибка: OrderId — не UserId
loadUser('u1' as UserId);        // ок
```

`unique symbol` в качестве ключа не даёт подделать бренд обычным объектом и не мешает подсказкам. Значение остаётся строкой: `uid.toUpperCase()` работает, `typeof uid` — `'string'`.

`as UserId` в каждом месте — слабое место. Бренд полезен, когда его выдаёт **одна функция с проверкой**:

```ts
type Email = Brand<string, 'Email'>;

function parseEmail(s: string): Email {
  if (!/^[^@\s]+@[^@\s]+$/.test(s)) throw new Error('bad email');
  return s as Email;
}
```

Теперь `sendEmail(to: Email)` нельзя вызвать с непроверенной строкой. Тот же приём — у `z.email().brand<'Email'>()` в zod. Так бренды кодируют не только «это ID пользователя», но и «это значение прошло проверку»: положительное число, санитизированный HTML, нормализованный телефон.

---

## Красные флаги в ответе

- **«Условный тип проверяет объединение целиком».** Над голым параметром он распределяется по вариантам, целиком — только `[T] extends [U]`.
- **«`T extends never` проверяет, что `T` — `never`».** Для `never` результат — `never`, проверка — `[T] extends [never]`.
- **«Бренд — это рантайм-метка».** Бренд существует только в типах, в рантайме значение обычное.
- **«Mapped-тип всегда теряет `readonly` и `?`».** Гомоморфный (над `keyof T`) их сохраняет, снимать надо явно через `-`.
- **«Чем сложнее тип, тем лучше».** Глубокие рекурсивные типы упираются в предел и тормозят редактор, а читать их тяжело.

## Как спрашивают на собеседовании

::question
Что такое распределяющий условный тип и как его отключить?

#answer
Условный тип с голым параметром слева от `extends`, применённый к объединению, вычисляется для каждого варианта отдельно, результаты объединяются: `ToArray<string | number>` — `string[] | number[]`. Отключается обёрткой в кортеж: `[T] extends [U]`.

#more
На распределении построены `Exclude`, `Extract` и распределяющий `Omit`. Ловушки: `never` — пустое объединение, поэтому `T extends never ? ...` от `never` даёт `never`, а `boolean` — это `true | false`. Распределяется только голый параметр: `{ v: T } extends ...` уже нет.
::

::question
Как работает infer?

#answer
`infer` объявляет переменную типа внутри условия `extends`. Компилятор сопоставляет тип с образцом и выводит переменную: `T extends Promise<infer U> ? U : T` достаёт тип из промиса. Так устроены `ReturnType` и `Parameters`.

#more
`infer` работает в любой позиции образца: элемент массива, кортежа, аргумент, часть шаблонной строки. Переменную можно ограничить: `infer N extends number` в кортеже или `` `${infer N extends number}` `` превращает строку `'42'` в число `42`. Рекурсивный `infer` разворачивает вложенные промисы.
::

::question
Зачем нужны брендированные типы?

#answer
Чтобы структурно одинаковые типы стали несовместимыми: `UserId` и `OrderId` — строки, но перепутать их нельзя. Бренд — фиктивное свойство, которое есть только в типах: `string & { [brand]: 'UserId' }`.

#more
Интерфейсы не помогают: типизация структурная, и два одинаковых интерфейса взаимозаменяемы. Бренд выдают через одну функцию с проверкой (`parseEmail`), тогда тип означает «значение прошло проверку». Ключ `unique symbol` защищает от подделки. В zod — `.brand()`.
::

::question
В чём разница между mapped и условным типом?

#answer
Mapped-тип перебирает ключи и строит объект: `{ [K in keyof T]: ... }`. Условный тип выбирает ветку по проверке совместимости: `T extends U ? X : Y`. Первый трансформирует форму, второй — ветвление и извлечение через `infer`.

#more
Их часто совмещают: условие внутри mapped-типа фильтрует ключи через `as ... ? K : never`, а mapped-тип внутри условного даёт рекурсивные `DeepPartial`. Гомоморфный mapped-тип сохраняет модификаторы и работает с массивами как с массивами.
::

::question
Что такое шаблонные литеральные типы?

#answer
Типы-строки с подстановками: `` `${Size}-${Color}` `` даёт все комбинации, `` `${number}px` `` принимает только строки вида «число + px». Вместе с `Capitalize` строят имена вроде `onClick` из `click`.

#more
С `infer` шаблон разбирает строки: параметры маршрута из `'/items/:id'`, части CSS-значения. Объединения в шаблоне перемножаются, и большие комбинации тормозят компилятор. Ключи mapped-типов переименовывают через `as` с шаблоном.
::

::question
Где предел у рекурсивных типов?

#answer
Компилятор ограничивает глубину раскрытия и останавливается с ошибкой TS2589 «Type instantiation is excessively deep and possibly infinite». Обычная рекурсия упирается в предел на нескольких десятках уровней.

#more
Хвостовая рекурсия — рекурсивный вызов как весь результат ветки, состояние в параметре-аккумуляторе — разрешена до 999 уровней. Но упор в предел — обычно сигнал упростить тип: тяжёлые типы замедляют проверку и подсказки у всей команды.
::

## Практика

::practice{title="Типизированные параметры маршрута"}
Функция `buildUrl` подставляет параметры в шаблон маршрута. Сделай так, чтобы набор параметров выводился из строки:

```ts
buildUrl('/shop/:category/items/:id', { category: 'tea', id: '7' });   // ок
buildUrl('/shop/:category/items/:id', { category: 'tea' });            // ошибка: нет id
buildUrl('/about', {});                                                // ок
```

#solution
```ts
type RouteParams<S extends string> =
  S extends `${string}:${infer P}/${infer Rest}`
    ? { [K in P | keyof RouteParams<`/${Rest}`>]: string }
    : S extends `${string}:${infer P}`
      ? { [K in P]: string }
      : {};

function buildUrl<const S extends string>(route: S, params: RouteParams<S>): string {
  return route.replace(/:(\w+)/g, (_, key: string) =>
    encodeURIComponent((params as Record<string, string>)[key]),
  );
}

buildUrl('/shop/:category/items/:id', { category: 'tea', id: '7' });   // '/shop/tea/items/7'
```

Шаблон с `infer` отрезает первый параметр до `/`, рекурсивно разбирает остаток и объединяет ключи. Внутри функции тип `RouteParams<S>` неизвестен до вызова, поэтому для чтения по ключу нужен `as`. В проверке вызов без `id` не скомпилировался, а результат подстановки совпал.
::

::practice{title="Почему IsNever не работает?"}
Тип должен вернуть `true` для `never`, но возвращает `never`:

```ts
type IsNever<T> = T extends never ? true : false;
type A = IsNever<never>;   // never
```

#solution
Условный тип с голым параметром распределяется по объединению, а `never` — пустое объединение. Распределять нечего, условие не вычисляется ни разу, результат — пустое объединение, то есть `never`. Обёртка в кортеж отключает распределение:

```ts
type IsNever<T> = [T] extends [never] ? true : false;

type A = IsNever<never>;    // true
type B = IsNever<string>;   // false
```

Это же правило объясняет, почему `ToArray<string | number>` даёт `string[] | number[]`, а не `(string | number)[]`. В проверке наивная версия вернула `never`, обёрнутая — `true` и `false`.
::

::practice{title="Деньги нельзя складывать с количеством"}
В корзине `price` в копейках и `qty` в штуках — оба `number`. Ошибка `total += item.qty` прошла ревью. Сделай так, чтобы компилятор её ловил, а цены создавались только через проверку.

#solution
```ts
declare const brand: unique symbol;
type Brand<T, B extends string> = T & { readonly [brand]: B };

type Kopecks = Brand<number, 'Kopecks'>;
type Qty = Brand<number, 'Qty'>;

function kopecks(n: number): Kopecks {
  if (!Number.isInteger(n) || n < 0) throw new RangeError('price must be a non-negative integer');
  return n as Kopecks;
}

function addMoney(a: Kopecks, b: Kopecks): Kopecks {
  return (a + b) as Kopecks;
}

function lineTotal(price: Kopecks, qty: Qty): Kopecks {
  return (price * qty) as Kopecks;
}

let total = kopecks(0);
total = addMoney(total, lineTotal(kopecks(490), 2 as Qty));   // ок
total = addMoney(total, 2 as Qty);                            // ошибка: Qty — не Kopecks
```

Арифметика над брендами даёт обычный `number`, поэтому операции оборачивают в функции, которые возвращают бренд. Это стоит делать для значений, где путаница дорога: деньги, единицы измерения, ID. В проверке сложение с `Qty` не скомпилировалось, `kopecks(-1)` бросил `RangeError`, итог равен `980`.
