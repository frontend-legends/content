# Функции и классы

Как типизировать функции и классы: сигнатуры, перегрузки, `void` и `this`, модификаторы доступа, абстрактные классы, `implements` и декораторы. Спрашивают разницу `private` и `#`, `void` и `undefined`, зачем перегрузки. Глубже — почему `private` обходится через квадратные скобки, почему метод в интерфейсе проверяется слабее, чем свойство-функция, и чем стандартные декораторы отличаются от «экспериментальных».

::tldr
- **Тип функции описывает параметры и результат:** `(price: number) => string`. Параметры аннотируют всегда, возвращаемый тип — у публичных функций, чтобы зафиксировать контракт.
- **Перегрузки — несколько сигнатур над одной реализацией.** Снаружи видны только сигнатуры, реализация скрыта. Если хватает объединения или дженерика, перегрузки не нужны.
- **`void` в типе колбэка значит «результат не используется», поэтому колбэк может что-то вернуть.** Методы в интерфейсах проверяются бивариантно, а свойства-функции — строго.
- **`private` и `protected` существуют только при проверке и обходятся через `obj['field']`. `#field` — приватность в рантайме.** `implements` проверяет класс, но не задаёт типы его параметрам.
- **Стандартные декораторы (TS 5+) — функции `(value, context)`,** которые возвращают замену. Устаревшие `experimentalDecorators` — другой API, на нём держатся Angular и NestJS.
::

## Типы функций

Сквозной пример — модуль цен и корзины:

```ts
type PriceRule = (price: number) => number;

function applyRules(price: number, rules: PriceRule[]): number {
  return rules.reduce((p, rule) => rule(p), price);
}

const withDiscount = (percent: number): PriceRule => (price) => price * (1 - percent / 100);
```

Тип функции записывают как `(параметры) => результат`. В объектных типах то же самое можно выразить сигнатурой вызова — так описывают функции, у которых есть ещё и свойства:

```ts
interface Formatter {
  (value: number): string;    // сигнатура вызова
  currency: string;           // и свойство
}
```

Что аннотировать:

- **параметры** — всегда, их не из чего вывести. Исключение — колбэк в контексте: в `rules.reduce((p, rule) => ...)` типы `p` и `rule` известны из сигнатуры `reduce` (контекстная типизация);
- **возвращаемый тип** — у публичных и экспортируемых функций. Он фиксирует контракт: если реализация случайно начнёт возвращать `number | undefined`, ошибка покажется в функции, а не у всех вызывающих;
- **необязательные параметры** — `currency?: string` или со значением по умолчанию `currency = 'RUB'`. Необязательные идут после обязательных;
- **rest-параметры** — массивом или кортежем: `(...prices: number[])`.

Одна функция иногда ведёт себя по-разному в зависимости от аргументов. Для этого есть перегрузки.

## Перегрузки

```ts
function parsePrice(input: string): number;
function parsePrice(input: number, currency: 'RUB' | 'USD'): string;
function parsePrice(input: string | number, currency?: 'RUB' | 'USD'): number | string {
  return typeof input === 'string' ? Number(input) : `${input} ${currency}`;
}

parsePrice('490');          // number
parsePrice(490, 'RUB');     // string
parsePrice('490', 'RUB');   // ошибка: такой сигнатуры нет
```

Первые две строки — **сигнатуры перегрузки**, третья — **реализация**. Снаружи видны только сигнатуры: реализация с широкими типами скрыта, и вызов, который подходит только под неё, — ошибка. В проверке `parsePrice('490', 'RUB')` не скомпилировался, хотя реализация такие аргументы принимает.

Правила:

- реализация должна быть совместима со **всеми** сигнатурами, но компилятор не проверяет, что ветки внутри соответствуют сигнатурам — это остаётся на авторе;
- сигнатуры проверяются **сверху вниз**, выбирается первая подходящая, поэтому конкретные пишут выше общих;
- если результат зависит от типа аргумента линейно, лучше дженерик или объединение: перегрузки плохо сочетаются с вызовом через объединение аргументов.

Перегрузки — про то, *что* функция принимает. Отдельный вопрос — как типизируют её результат, когда он не нужен.

## void и колбэки

`void` означает «возвращаемое значение не используется». На этом строятся два правила, которые на первый взгляд противоречат друг другу:

```ts
const onSave: () => void = () => items.push(price);   // ок: push возвращает число, но его проигнорируют

function done(): void {
  return 42;                                           // ошибка: объявлено, что возвращать нечего
}
```

Тип колбэка `() => void` разрешает передать функцию, которая что-то возвращает: вызывающий всё равно не использует результат. Иначе нельзя было бы написать `arr.forEach((x) => other.push(x))`. А функция, **объявленная** с `void`, не может вернуть значение — это её собственный контракт.

`undefined` как возвращаемый тип строже: функция обязана вернуть именно `undefined` (явно или без `return`), и вызывающий может на это полагаться.

### Бивариантность методов

При `strictFunctionTypes` (часть `strict`) параметры функций проверяются **контравариантно**: обработчик кликов нельзя передать туда, где ожидается обработчик любых событий, потому что ему могут передать событие без координат. Но правило действует только для **свойств-функций**. Методы, объявленные синтаксисом метода, проверяются бивариантно — для совместимости с DOM и старыми библиотеками:

```ts
interface WithMethod { handle(e: BaseEvent): void }
interface WithProperty { handle: (e: BaseEvent) => void }

const a: WithMethod = { handle(e: ClickEvent) {} };     // ок — и это дыра
const b: WithProperty = { handle: (e: ClickEvent) => {} }; // ошибка
```

Поэтому в собственных интерфейсах колбэки описывают свойствами-функциями: так проверка строже.

### Параметр this

Если функция использует `this`, его тип объявляют первым «параметром», который стирается при компиляции:

```ts
function onClick(this: HTMLButtonElement, e: MouseEvent) {
  this.disabled = true;
}
button.addEventListener('click', onClick);   // this — кнопка
onClick(new MouseEvent('click'));            // ошибка: вызов без нужного this
```

С `noImplicitThis` (часть `strict`) обращение к `this` с неизвестным типом — ошибка. Как `this` определяется в рантайме — в [Контексте выполнения](/content/javascript/execution-context).

Функции типизированы. Теперь — классы, где у TypeScript есть свои модификаторы.

## Классы

```ts
class CartService {
  readonly items: CartItem[] = [];
  private discount = 0;
  #token: string;

  constructor(token: string) {
    this.#token = token;
  }

  add(item: CartItem): void {
    this.items.push(item);
  }

  protected total(): number {
    return this.items.reduce((sum, i) => sum + i.price, 0) - this.discount;
  }
}
```

### private против #

У TypeScript свои модификаторы доступа: `public` (по умолчанию), `protected` (класс и наследники), `private` (только класс). Они существуют **только при проверке** и стираются: в рантайме это обычные свойства. Мало того, проверка привязана к записи через точку — через квадратные скобки `private` доступен прямо в TypeScript: в проверке `w['balance']` скомпилировался без ошибок. Это осознанная лазейка для тестов.

`#field` — приватное поле JavaScript: его нет в рантайме ни для кого снаружи класса, ни через скобки, ни через `Object.keys` (подробно — в [Прототипах и классах](/content/javascript/prototypes-and-classes)).

| | `private` | `#field` |
| --- | --- | --- |
| Где работает | только при проверке типов | в рантайме |
| Доступ через `obj['x']` | разрешён | невозможен |
| Видно в `JSON.stringify`, `Object.keys` | да | нет |
| Наследники | не видят, но имя занято | не видят, имена независимы |
| Через `Proxy` | работает | ломается |

Выбор: `#` — когда приватность важна (библиотеки, токены), `private` — когда достаточно договорённости, а объект должен работать с прокси и сериализацией.

### Параметры-свойства

Сокращение `constructor(private id: number) {}` объявляет поле и присваивает его. Это удобно, но это **не стираемый** синтаксис: при компиляции появляется присваивание `this.id = id`. С `erasableSyntaxOnly` он запрещён — в проверке `tsc` выдал ошибку TS1294 и для параметра-свойства, и для `enum`. Для запуска через стирание типов (Node.js, некоторые бандлеры) поля объявляют явно.

### readonly, abstract, override

- **`readonly`** запрещает переприсваивание после конструктора. Как и у объектов, только на уровне типа и только поверхностно: в массив `readonly items` можно сделать `push`. Для запрета — `readonly CartItem[]`.
- **`abstract`** — класс, который нельзя создать напрямую, с методами без реализации, которые наследник обязан реализовать. Это способ описать общий каркас с частичной реализацией.
- **`override`** явно помечает переопределённый метод. С `noImplicitOverride` метод, который переопределяет родительский без `override`, — ошибка: это ловит опечатку в имени и удаление метода у родителя.

### implements

`class Discount implements PriceRule` проверяет, что класс подходит под интерфейс. Но `implements` **не задаёт типы** членам класса: параметр метода без аннотации останется `any`, а не возьмёт тип из интерфейса. В проверке `apply(price)` в классе с `implements PriceRule` дал ошибку неявного `any`. Аннотировать нужно и в классе.

Ещё одна тонкость: у класса два типа. `Product` — тип **экземпляра**, `typeof Product` — тип **самого класса** с конструктором и статическими членами. Фабрике, которая принимает класс, нужен `typeof Product` или `new (...args: any[]) => Product`.

## Декораторы

Декоратор — функция, которая оборачивает класс или его член. С TypeScript 5.0 поддерживаются **стандартные** декораторы JavaScript (Stage 3 в TC39):

```ts
function logged<This, Args extends unknown[], Return>(
  method: (this: This, ...args: Args) => Return,
  context: ClassMethodDecoratorContext,
) {
  return function (this: This, ...args: Args): Return {
    console.log(`${String(context.name)}(${args.join(', ')})`);
    return method.apply(this, args);
  };
}

class Cart {
  @logged
  add(price: number) { /* ... */ }
}
```

Декоратор метода получает сам метод и **контекст**: имя, вид члена, статический ли он, и `addInitializer` — колбэк, который выполнится при создании экземпляра. Он возвращает замену метода. Через `addInitializer` пишут, например, `@bound`, который привязывает `this` — в проверке оторванный от объекта метод с `@bound` вернул правильную сумму.

Есть и **устаревшие** декораторы — опция `experimentalDecorators`. Это другой API: декоратор метода получает `(target, key, descriptor)`, есть декораторы параметров и метаданные (`emitDecoratorMetadata`). На нём построены :term[Angular]{def="фреймворк Google для фронтенда, целиком на TypeScript"} (до недавних версий) и :term[NestJS]{def="серверный фреймворк Node.js на TypeScript с декораторами и внедрением зависимостей"}, поэтому в таких проектах эта опция включена. Два вида несовместимы: декоратор, написанный для одного API, не работает с другим.

Во фронтенде на React и Vue декораторы встречаются редко: логику там делят функциями и хуками (подробно — в [Паттернах](/content/javascript/patterns)).

## Красные флаги в ответе

- **«`private` делает поле недоступным».** Только при проверке и только через точку: `obj['field']` компилируется, а в рантайме поле обычное. Приватность в рантайме — `#field`.
- **«`void` значит, что функция ничего не возвращает».** В типе колбэка `void` значит «результат не используется» — колбэк может что-то вернуть.
- **«`implements` типизирует методы класса».** Он только проверяет совместимость. Параметры в классе аннотируют отдельно.
- **«Перегрузки проверяют реализацию по каждой сигнатуре».** Реализация должна быть совместима со всеми сигнатурами, но соответствие веток — на авторе.
- **«Декораторы в TypeScript — одни».** Стандартные (TS 5+) и `experimentalDecorators` — разные API, несовместимые друг с другом.

## Как спрашивают на собеседовании

::question
Чем private отличается от #?

#answer
`private` — модификатор TypeScript: проверяется только при компиляции и стирается, в рантайме поле доступно. `#field` — приватное поле JavaScript, недоступное снаружи класса и в рантайме.

#more
`private` к тому же обходится внутри TypeScript через квадратные скобки: `obj['field']` компилируется. `#`-поля не видны в `JSON.stringify` и `Object.keys`, но ломаются, если объект обёрнут в `Proxy`: метод на прокси не найдёт приватное поле. Наследники не конфликтуют с `#`-полями родителя по именам, а с `private` — конфликтуют.
::

::question
Что такое перегрузки функций?

#answer
Несколько сигнатур для одной функции, за которыми стоит одна реализация. TypeScript выбирает первую подходящую сигнатуру, а реализация снаружи не видна.

#more
Реализация должна быть совместима со всеми сигнатурами, но компилятор не проверяет, что каждая ветка отдаёт тип своей сигнатуры. Порядок важен: конкретные сигнатуры выше общих. Вызов с объединением аргументов, который не подходит ни под одну сигнатуру целиком, — ошибка. Если результат линейно зависит от аргумента, проще дженерик или условный тип.
::

::question
Чем void отличается от undefined в возвращаемом типе?

#answer
`void` — «результат не используется». Функцию, которая что-то возвращает, можно передать туда, где ожидается колбэк `() => void`. `undefined` — функция обязана вернуть именно `undefined`.

#more
Правило про колбэки нужно, чтобы работало `arr.forEach((x) => other.push(x))`. Но функция, объявленная с `: void`, сама вернуть значение не может. Из-за этого `() => void` нельзя использовать, чтобы запретить возврат значения: для этого тип результата делают `undefined`.
::

::question
Зачем нужны абстрактные классы?

#answer
Чтобы описать общий каркас с частичной реализацией: общие методы реализованы, а абстрактные обязаны реализовать наследники. Абстрактный класс нельзя создать через `new`.

#more
В отличие от интерфейса, абстрактный класс существует в рантайме и даёт общий код через наследование. `abstract` — проверка TypeScript, в JavaScript остаётся обычный класс. Во фронтенде часто удобнее интерфейс плюс композиция: глубокие иерархии классов мешают тестам и переиспользованию.
::

::question
Что даёт implements?

#answer
Проверку при компиляции, что класс соответствует интерфейсу: у него есть все нужные члены с совместимыми типами. В рантайме `implements` ничего не делает.

#more
`implements` не переносит типы из интерфейса в класс: параметры методов без аннотаций останутся `any`. Класс совместим с интерфейсом и без `implements` — типизация структурная, — `implements` лишь переносит ошибку в место объявления. У класса два типа: тип экземпляра (`Product`) и тип конструктора (`typeof Product`).
::

::question
Как типизировать this в функции?

#answer
Первым параметром с именем `this`: `function onClick(this: HTMLButtonElement, e: MouseEvent)`. Он не становится настоящим параметром и стирается, а компилятор проверяет, что функцию вызывают с нужным `this`.

#more
С `noImplicitThis` использование `this` неизвестного типа — ошибка. Параметр `this` помогает в обработчиках DOM и в функциях, которые присваивают объектам как методы. Для методов классов `this` выводится сам, а для отрыва метода от объекта нужны стрелки или `bind`.
::

::question
Чем стандартные декораторы отличаются от experimentalDecorators?

#answer
Стандартные (TS 5+) — функции `(value, context)`, которые возвращают замену члена класса. `experimentalDecorators` — старый API с `(target, key, descriptor)`, декораторами параметров и метаданными, на нём построены Angular и NestJS.

#more
API несовместимы, и декоратор, написанный под один, не работает с другим. В стандартных нет декораторов параметров и `emitDecoratorMetadata`, зато есть `context.addInitializer` и доступ к имени и виду члена. Поля декорируются иначе: декоратор поля возвращает функцию-инициализатор значения.
::

## Практика

::practice{title="Почему обработчик падает?"}
Интерфейс шины событий позволяет подписать обработчик кликов на любые события, и он падает на событии прокрутки:

```ts
interface AppEvent { type: string }
interface ClickEvent extends AppEvent { x: number; y: number }

interface Listener {
  handle(e: AppEvent): void;
}

const clicks: Listener = {
  handle(e: ClickEvent) {
    console.log(e.x.toFixed(0));
  },
};

clicks.handle({ type: 'scroll' });   // TypeError: Cannot read properties of undefined
```

#solution
`handle` объявлен синтаксисом метода, а методы проверяются **бивариантно**: обработчик с более узким параметром (`ClickEvent`) принимается туда, где ожидается любой `AppEvent`. Компилятор молчит, а событие прокрутки без `x` роняет код.

Фикс — описать обработчик свойством-функцией, тогда работает строгая проверка `strictFunctionTypes`:

```ts
interface Listener {
  handle: (e: AppEvent) => void;
}

const clicks: Listener = {
  handle: (e: ClickEvent) => {},     // ошибка: ClickEvent уже, чем AppEvent
};
```

Правильно сделать слушателя, который сам сужает событие или подписывается на конкретный тип: `on<T extends AppEvent['type']>(type: T, handler: (e: EventMap[T]) => void)` — подробно в [Дженериках](/content/typescript/generics).
::

::practice{title="Напиши декоратор"}
Напиши стандартный декоратор `@bound`, который привязывает метод к экземпляру, чтобы его можно было передавать как колбэк.

```ts
class Cart {
  items: number[] = [];

  @bound
  total() {
    return this.items.reduce((s, p) => s + p, 0);
  }
}

const { total } = new Cart();
total();   // должно работать без потери this
```

#solution
```ts
function bound<This, T extends (this: This, ...args: any[]) => any>(
  method: T,
  context: ClassMethodDecoratorContext<This, T>,
) {
  context.addInitializer(function (this: This) {
    (this as any)[context.name] = method.bind(this);
  });
}
```

`addInitializer` выполняется при создании каждого экземпляра: метод из прототипа привязывается к объекту и кладётся на сам экземпляр. В проверке метод, извлечённый деструктуризацией, вернул правильную сумму. Это стандартный API: с `experimentalDecorators` декоратор получал бы `(target, key, descriptor)` и такой код бы не работал. Альтернатива без декораторов — поле-стрелка `total = () => ...`.
::
