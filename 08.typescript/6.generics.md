# Дженерики

Как писать функции и типы, которые работают с разными типами и не теряют связь между входом и выходом: параметры типа и их вывод, ограничения `extends` и `keyof`, значения по умолчанию, `const`-параметры, `NoInfer` и вариантность. Спрашивают, зачем нужны дженерики, что значит `K extends keyof T` и зачем запятая в `<T,>`. Глубже — почему нельзя вернуть «какой-то объект» вместо `T`, почему нет частичного вывода и где вариантность пропускает ошибки.

::tldr
- **Дженерик связывает типы:** `first<T>(arr: T[]): T` говорит, что выход того же типа, что элементы входа. `any` эту связь теряет.
- **Параметр типа обычно выводится из аргументов.** Указал один параметр явно — нужно указать все, у которых нет значения по умолчанию: частичного вывода нет.
- **`extends` — ограничение, а не наследование:** `T extends { length: number }` разрешает только типы со свойством `length`, а `K extends keyof T` — только ключи `T`.
- **`T` — тип, который выберет вызывающий, а не «что-то подходящее под ограничение».** Поэтому вернуть из функции новый объект как `T` нельзя.
- **Вариантность определяет, когда `Box<Dog>` подходит вместо `Box<Animal>`.** Возвращаемые значения ковариантны, параметры функций контравариантны, а методы и массивы — дыры в строгости.
::

## Зачем нужны дженерики

Функция берёт первый элемент массива. Без дженериков два плохих варианта: написать её для каждого типа или принять `any`:

```ts
function firstAny(arr: any[]) { return arr[0]; }
firstAny([1, 2]);   // any — тип потерян
```

С параметром типа:

```ts
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

first([1, 2]);      // number | undefined
first(['a']);       // string | undefined
```

`T` — переменная на уровне типов. При вызове компилятор подставляет вместо неё конкретный тип, и функция сохраняет **связь** между входом и выходом. В этом весь смысл: дженерик нужен, когда тип одного места зависит от типа другого.

Отсюда практическое правило: **параметр типа должен встречаться хотя бы дважды.** `function log<T>(v: T): void` ничего не связывает — достаточно `v: unknown`.

Параметры типа есть не только у функций:

```ts
type ApiResponse<T> = { data: T; status: number };
interface Repository<T> { getById(id: string): Promise<T | null> }
class Stack<T> { private items: T[] = []; push(v: T) { this.items.push(v); } }
```

Откуда компилятор берёт `T`, если его не указали?

## Вывод параметров

Компилятор смотрит на аргументы и подбирает `T`, при котором вызов корректен. Если кандидатов несколько и они несовместимы, вызов — ошибка:

```ts
function pair<T>(a: T, b: T): [T, T] { return [a, b]; }

pair(1, 'a');                     // ошибка: 'string' is not assignable to 'number'
pair<number | string>(1, 'a');    // ок: тип указан явно
```

Компилятор не объединяет кандидатов в `number | string` сам: чаще это ошибка в коде, чем намерение.

### Частичного вывода нет

Если указать параметры явно, нужно указать все, у которых нет значения по умолчанию:

```ts
function request<TBody, TResult>(body: TBody): TResult { /* ... */ }

request<{ id: number }>({ id: 1 });   // ошибка: Expected 2 type arguments, but got 1
```

Хочется задать только `TResult`, а `TBody` вывести из аргумента, но так нельзя. Обход — разделить функцию на две (каррирование): первая принимает явный параметр, вторая выводит остальные.

```ts
const requestFor = <TResult,>() => <TBody,>(body: TBody): TResult => { /* ... */ };
requestFor<{ ok: boolean }>()({ id: 1 });   // TResult указан, TBody выведен
```

Так устроены API вроде `createSelector` и некоторые билдеры схем.

### Значения по умолчанию

`T = string` срабатывает, когда вывести не из чего:

```ts
function makeStore<T = string>(initial?: T) { /* ... */ }
makeStore();      // T = string
makeStore(5);     // T = number — вывод важнее значения по умолчанию
```

Для типов по умолчанию часто ставят `unknown`: `ApiResponse` без параметра честно говорит «данные не описаны».

### Запятая в .tsx

В `.tsx` стрелка `<T>(v: T) => v` читается как открывающий JSX-тег `T` — ошибка «JSX element 'T' has no corresponding closing tag». Запятая `<T,>` или ограничение `<T extends unknown>` подсказывают парсеру, что это дженерик. В `.ts` запятая не нужна.

Вывод находит `T`. Но пока о `T` ничего не известно, с ним почти ничего нельзя делать.

## Ограничения

Внутри `first<T>` нельзя прочитать `arr[0].length`: `T` может быть числом. Ограничение `extends` сужает допустимые типы:

```ts
function getLength<T extends { length: number }>(v: T) {
  return v.length;
}

getLength('abc');      // ок
getLength([1, 2]);     // ок
getLength(42);         // ошибка: у number нет length
```

`extends` здесь не наследование классов, а «`T` должен быть совместим с этим типом». Подходит любой тип с нужными свойствами — структурная типизация (подробно — во [Введении](/content/typescript/introduction)).

### keyof в ограничении

Главный приём — параметр, ограниченный ключами другого:

```ts
function prop<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const user = { name: 'Аня', age: 30 };
prop(user, 'age');     // number
prop(user, 'email');   // ошибка: такого ключа нет
```

`K` — конкретный ключ, а `T[K]` — тип его значения. Так же типизируют обработчики событий:

```ts
type Events = { add: { id: number; qty: number }; clear: void };

function createEmitter<E extends Record<string, unknown>>() {
  return {
    on<K extends keyof E>(event: K, fn: (payload: E[K]) => void) { /* ... */ },
    emit<K extends keyof E>(event: K, payload: E[K]) { /* ... */ },
  };
}

const bus = createEmitter<Events>();
bus.on('add', (p) => p.qty);        // p: { id: number; qty: number }
bus.emit('add', { id: 1 });         // ошибка: нет qty
bus.on('remove', () => {});         // ошибка: нет такого события
```

### T выбирает вызывающий

Частая ошибка — вернуть из функции новый объект, подходящий под ограничение:

```ts
function withDefaults<T extends { retries: number }>(opts: T): T {
  return { retries: 3 };
  // ошибка: '{ retries: number; }' is assignable to the constraint of type 'T',
  // but 'T' could be instantiated with a different subtype of constraint '{ retries: number; }'
}
```

`T` — не «какой-нибудь тип с `retries`», а **конкретный** тип, который выбрал вызывающий, например `{ retries: number; url: string }`. Объект `{ retries: 3 }` под ограничение подходит, но `url` в нём нет. Правильно — построить результат из входа:

```ts
function withDefaults<T extends { retries: number }>(opts: T): T {
  return { ...opts, retries: opts.retries || 3 };
}

withDefaults({ retries: 0, url: '/api' });   // { retries: number; url: string }
```

Ограничения задают, что подходит. Иногда нужно ещё управлять тем, как именно компилятор выводит тип.

## Управление выводом

### const-параметры

По умолчанию литералы расширяются: `['/', '/about']` выводится как `string[]`. Модификатор `const` выводит тип так, будто аргумент написан с `as const`:

```ts
function routes<const T extends readonly string[]>(paths: T) { return paths; }
routes(['/', '/about']);    // readonly ['/', '/about']

function defineConfig<const T>(c: T) { return c; }
defineConfig({ mode: 'production' });   // { readonly mode: 'production' }
```

Тонкости. С ограничением `string[]` без `readonly` выводится изменяемый кортеж `['/', '/about']`, поэтому для массивов ограничение обычно пишут `readonly`. И `const` действует только на литерал в месте вызова: если передать переменную `const paths = ['/', '/about']`, её тип уже расширен до `string[]`, и `const` не поможет.

### NoInfer

Иногда параметр не должен участвовать в выводе:

```ts
function createLight<C extends string>(colors: C[], initial: C) { /* ... */ }
createLight(['red', 'green'], 'blue');   // компилируется: C = 'red' | 'green' | 'blue'
```

Компилятор вывел `C` из обоих аргументов, и опечатка в `initial` расширила тип. `NoInfer<C>` запрещает выводить из этого места:

```ts
function createLight<C extends string>(colors: C[], initial: NoInfer<C>) { /* ... */ }
createLight(['red', 'green'], 'blue');   // ошибка: '"blue"' is not assignable to '"red" | "green"'
```

Теперь `C` берётся только из `colors`, а `initial` проверяется по нему. Типичные места — значение по умолчанию для списка вариантов, начальный шаг машины состояний, ключ из списка.

Осталось последнее: когда один дженерик-тип подходит вместо другого.

## Вариантность

Если `Dog` — подтип `Animal`, подходит ли `Box<Dog>` туда, где ждут `Box<Animal>`? Зависит от того, как `Box` использует параметр.

- **Ковариантность** — параметр только «выходит»: `() => Dog` подходит вместо `() => Animal`. Кто ждёт животное, получит собаку — это нормально.
- **Контравариантность** — параметр только «входит»: `(a: Animal) => void` подходит вместо `(d: Dog) => void`. Функция, которая умеет обработать любое животное, справится и с собакой. Обратное неверно: `(d: Dog) => d.bark()` нельзя передать туда, где придёт кошка.
- **Инвариантность** — параметр и входит, и выходит: подходит только точное совпадение.

Контравариантность параметров проверяется под `strictFunctionTypes` (входит в `strict`). Но есть две известные дыры:

```ts
// методы проверяются бивариантно даже под strict
type WithMethod = { handle(a: Animal): void };
const m: WithMethod = { handle: (d: Dog) => d.bark() };   // компилируется
m.handle({ name: 'кот' });                                // TypeError

// массивы ковариантны, хотя в них можно писать
const dogs: Dog[] = [];
const animals: Animal[] = dogs;
animals.push({ name: 'кот' });
dogs[0].bark();                                           // TypeError
```

Бивариантность методов оставлена ради совместимости: иначе `Array<Dog>` не подходил бы под `Array<Animal>` из-за метода `push`. Если нужна строгая проверка, колбэк объявляют свойством-функцией (`handle: (a: Animal) => void`), а не методом.

Компилятор выводит вариантность сам, но её можно задать явно аннотациями `out` и `in`:

```ts
interface Producer<out T> { get(): T }
interface Consumer<in T> { put(v: T): void }
```

Аннотации документируют намерение, ускоряют проверку сложных рекурсивных типов и дают ошибку, если тело противоречит заявленной вариантности.

## Красные флаги в ответе

- **«Дженерик — это `any`, только красивее».** `any` выключает проверку, дженерик сохраняет связь между типами и проверяет каждый вызов.
- **«`T extends X` — наследование».** Это ограничение: подходит любой структурно совместимый тип.
- **«Можно указать один параметр типа, а остальные выведутся».** Частичного вывода нет: явно указывают все параметры без значений по умолчанию.
- **«Функция `<T extends X>(...): T` может вернуть любой `X`».** `T` выбирает вызывающий, и новый объект с полями `X` — не обязательно `T`.
- **«`strict` гарантирует контравариантность всех колбэков».** Методы проверяются бивариантно, массивы ковариантны.

## Как спрашивают на собеседовании

::question
Что такое дженерики и зачем они нужны?

#answer
Параметры на уровне типов. Позволяют написать функцию, класс или тип один раз для разных типов и сохранить связь между ними: `first<T>(arr: T[]): T` возвращает тот же тип, что элементы массива. С `any` эта связь теряется.

#more
Параметр обычно выводится из аргументов. Полезное правило: параметр типа должен встречаться хотя бы дважды, иначе он ничего не связывает и его заменяет `unknown`. Дженерики стираются при компиляции, в рантайме `T` недоступен — проверить «`x` типа `T`?» нельзя.
::

::question
Что значит `K extends keyof T`?

#answer
`K` ограничен ключами `T`: если `T = { name: string; age: number }`, то `K` — `'name'`, `'age'` или их объединение. Вместе с `T[K]` даёт типобезопасный доступ к свойству: `prop(user, 'age')` возвращает `number`.

#more
`extends` в параметре — ограничение, а не наследование. Так же типизируют обработчики событий `on<K extends keyof Events>(e: K, fn: (p: Events[K]) => void)`, формы и `pick`. Ключи с индексной сигнатурой `string` дают `string | number`.
::

::question
Зачем запятая в `<T,>` в стрелочных функциях?

#answer
В `.tsx` парсер читает `<T>` перед стрелкой как открывающий JSX-тег. Запятая подсказывает, что это список параметров типа. В `.ts` она не нужна.

#more
Альтернатива — ограничение `<T extends unknown>`, которое тоже однозначно читается как дженерик. Или объявить функцию через `function`, где такой неоднозначности нет.
::

::question
Можно ли задать значение по умолчанию для параметра типа?

#answer
Да: `<T = string>`. Оно используется, когда параметр не указан явно и его не из чего вывести. Если аргумент есть, вывод важнее значения по умолчанию.

#more
Значения по умолчанию позволяют указывать только часть параметров: те, что с умолчанием, можно пропустить. Без них частичного вывода нет — указал один параметр явно, указывай все. Обход — каррирование: первая функция принимает явный параметр, вторая выводит остальные.
::

::question
Что такое const-параметры типа?

#answer
Модификатор `const` перед параметром заставляет выводить литеральный тип, как с `as const`: `defineConfig({ mode: 'production' })` даёт `{ readonly mode: 'production' }`, а не `{ mode: string }`.

#more
Для массивов ограничение пишут `readonly string[]`, иначе выводится изменяемый кортеж. Модификатор действует только на литерал в месте вызова: переменная уже расширена до `string[]`. Родственный инструмент — `NoInfer<T>`, который запрещает выводить параметр из конкретного аргумента.
::

::question
Почему функция `<T extends X>` не может вернуть объект типа `X` как `T`?

#answer
`T` выбирает вызывающий, и это может быть подтип `X` с дополнительными полями. Новый объект `{ ...поля X }` подходит под ограничение, но не под конкретный `T`, поэтому ошибка «'T' could be instantiated with a different subtype».

#more
Результат строят из входа — `{ ...opts, retries: 3 }`, — либо меняют сигнатуру и возвращают `X`, если связь с входом не нужна. `as T` убирает ошибку, но обманывает вызывающего.
::

::question
Что такое ковариантность и контравариантность?

#answer
Ковариантность: `Box<Dog>` подходит вместо `Box<Animal>`, если `T` только выходит — как возвращаемое значение. Контравариантность — наоборот, для входящих параметров: функция для любого `Animal` подходит туда, где ждут функцию для `Dog`.

#more
Контравариантность параметров проверяется под `strictFunctionTypes`, но методы остаются бивариантными, а массивы — ковариантными, и оба случая пропускают ошибки. Колбэк, объявленный свойством-функцией, проверяется строго. Аннотации `in` и `out` задают вариантность явно.
::

## Практика

::practice{title="Типобезопасный pick"}
Напиши функцию `pick(obj, keys)`, которая возвращает объект только с указанными ключами. Неверный ключ — ошибка компиляции, а тип результата содержит только выбранные поля.

```ts
const product = { id: 1, title: 'Чай', price: 490, stock: 12 };
const card = pick(product, ['title', 'price']);
// card: { title: string; price: number }
```

#solution
```ts
function pick<T extends object, K extends keyof T>(obj: T, keys: readonly K[]): Pick<T, K> {
  const result = {} as Pick<T, K>;
  for (const key of keys) result[key] = obj[key];
  return result;
}

const card = pick(product, ['title', 'price']);   // Pick<{...}, 'title' | 'price'>
pick(product, ['title', 'color']);                // ошибка: 'color' нет среди ключей
```

`K` выводится из массива ключей как объединение литералов `'title' | 'price'`: литерал в позиции, ограниченной `keyof T`, не расширяется до `string`. `as Pick<T, K>` для пустого объекта неизбежен: компилятор не может доказать, что цикл заполнит все поля. В проверке результат равен `{ title: 'Чай', price: 490 }`, а лишний ключ не скомпилировался.
::

::practice{title="Почему опечатка в начальном значении компилируется?"}
Хук принимает список вкладок и начальную. Опечатка не ловится:

```ts
function useTabs<T extends string>(tabs: T[], initial: T) {
  let active = initial;
  return { tabs, get active() { return active; }, select(t: T) { active = t; } };
}

const t = useTabs(['cart', 'favorites'], 'favourites');
t.select('profile');   // тоже компилируется
```

#solution
`T` выводится из обоих аргументов, и `'favourites'` просто добавился в объединение: `T = 'cart' | 'favorites' | 'favourites'`. Нужно запретить выводить `T` из `initial`:

```ts
function useTabs<T extends string>(tabs: T[], initial: NoInfer<T>) { /* ... */ }

useTabs(['cart', 'favorites'], 'favourites');   // ошибка
const t = useTabs(['cart', 'favorites'], 'cart');
t.select('profile');                             // ошибка: T = 'cart' | 'favorites'
```

`NoInfer` оставляет `initial` в проверке, но исключает из вывода. Без него помогли бы два параметра типа (`<T extends string, I extends T>`), но `NoInfer` проще читается. В проверке без `NoInfer` опечатка прошла, с ним — нет.
::

::practice{title="Колбэк, который сломал рантайм"}
Компилятор пропустил ошибку, хотя `strict` включён:

```ts
type Animal = { name: string };
type Dog = Animal & { bark(): void };

interface Listener {
  handle(a: Animal): void;
}

const listener: Listener = { handle: (d: Dog) => d.bark() };
listener.handle({ name: 'кот' });   // TypeError: d.bark is not a function
```

#solution
Параметры методов проверяются бивариантно даже под `strictFunctionTypes`: компилятор принял функцию для `Dog` там, где придёт любой `Animal`. Если объявить `handle` свойством-функцией, проверка станет строгой:

```ts
interface Listener {
  handle: (a: Animal) => void;
}

const listener: Listener = { handle: (d: Dog) => d.bark() };   // ошибка
```

Синтаксис метода в интерфейсе — не стиль, а другая проверка. Для колбэков, которые передают снаружи, безопаснее свойство-функция. В проверке вариант с методом скомпилировался и бросил `TypeError`, вариант со свойством не скомпилировался.
::
