# Асинхронность и DOM

TypeScript на границах приложения: типы промисов и асинхронных функций, ответы `fetch` и проверка данных извне, отмена запросов, типы DOM — `querySelector`, события, формы. Спрашивают, что возвращает асинхронная функция, почему `querySelector` возвращает `null` и как получить `value` из поля. Глубже — почему `res.json()` превращает проверку в формальность, чем `target` отличается от `currentTarget` и где компилятор пропускает забытый `await`.

::tldr
- **Асинхронная функция всегда возвращает `Promise<T>`,** а комбинаторы сохраняют типы: `await Promise.all([a, b])` даёт кортеж с типом каждого элемента.
- **`res.json()` и `JSON.parse` возвращают `any`.** Дженерик `fetchJson<T>()` — тот же `as`: компилятор верит, а в рантайме может прийти что угодно. Данные извне проверяют схемой, и тип выводится из неё.
- **В `.catch((e) => ...)` параметр — `any` даже под `strict`.** `unknown` получает только переменная в `try/catch`.
- **`querySelector('input')` знает тип по имени тега, `querySelector('#email')` — только `Element`.** Оба могут вернуть `null`, а дженерик `querySelector<T>()` ничего не проверяет.
- **Тип события выводится по имени:** `'keydown'` — `KeyboardEvent`. Но `currentTarget` и `target` — просто `EventTarget | null`, элемент получают через `instanceof`.
::

## Типы промисов

```ts
async function total() {
  return 980;
}
// () => Promise<number>
```

Асинхронная функция всегда возвращает промис, поэтому аннотация обязана быть `Promise<T>`:

```ts
async function wrong(): number { return 1; }
// TS1064: The return type of an async function or method must be the global Promise<T> type
```

Функция без `return` — `Promise<void>`. Тип значения внутри промиса достаёт `Awaited` (подробно — в [Утилитарных типах](/content/typescript/utility-types)).

### new Promise

У конструктора промиса тип результата не выводится из `resolve`:

```ts
const p1 = new Promise((resolve) => resolve(1));           // Promise<unknown>
const p2 = new Promise<number>((resolve) => resolve(1));   // Promise<number>
```

`resolve()` без аргумента разрешён только для `Promise<void>`. Для `Promise<number>` компилятор подсказывает: «Did you forget to include 'void' in your type argument to 'Promise'?».

### Комбинаторы

`Promise.all` сохраняет тип каждой позиции:

```ts
const [user, count] = await Promise.all([loadUser(), loadCount()]);
// user: User, count: number
```

`Promise.allSettled` возвращает массив `PromiseSettledResult<T>` — размеченное объединение по полю `status`. После `status === 'fulfilled'` доступно `value`, после `'rejected'` — `reason`, и он `any`.

### Ошибки

Тут несимметрия. Под `strict` переменная в `try/catch` — `unknown`, а параметр колбэка `.catch` — `any`:

```ts
promise.catch((e) => e.message);   // e: any — компилируется, даже если бросили строку

try { await promise; } catch (e) {
  e.message;   // ошибка: 'e' is of type 'unknown'
}
```

`.catch` типизирован в стандартной библиотеке как `(reason: any) => ...`, и флаг `useUnknownInCatchVariables` на него не действует. Безопасно — аннотировать явно: `.catch((e: unknown) => ...)`.

### Забытый await

Компилятор не ловит промис, который создали и бросили:

```ts
function handler() {
  save();   // промис никто не ждёт — ошибка сохранения потеряется
}
```

Это ловит правило линтера `@typescript-eslint/no-floating-promises`. Сам компилятор ловит только явные случаи вроде промиса в условии: `if (isReady())` — TS2801 `This condition will always return true since this 'Promise<boolean>' is always defined`.

Типы промисов надёжны, пока данные создаёт сам код. Когда они приходят из сети — нет.

## Граница данных

```ts
const res = await fetch('/api/user');
const data = await res.json();   // any
```

`json()` возвращает `Promise<any>`, и `any` расползается по коду: его можно присвоить любому типу без ошибки. Привычная «типизация» fetch — дженерик-обёртка:

```ts
async function fetchJson<T>(url: string): Promise<T> {
  const res = await fetch(url);
  return res.json() as Promise<T>;
}

const user = await fetchJson<User>('/api/user');   // User — по заявлению, не по факту
```

Это не проверка, а утверждение. Если сервер вернёт `{ id: "1" }` или поле переименуют, тип останется `User`, а ошибка всплывёт далеко от места загрузки. В проверке обёртка вернула объект без `email` под типом `{ email: string }`, и `email.toUpperCase()` бросил `TypeError`.

Тип в TypeScript существует только при компиляции (подробно — во [Введении](/content/typescript/introduction)), поэтому проверить данные в рантайме может только код. Его не пишут вручную, а описывают схемой:

```ts
import { z } from 'zod';

const User = z.object({ id: z.number(), name: z.string() });
type User = z.infer<typeof User>;   // { id: number; name: string } — из схемы

async function fetchUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return User.parse(await res.json());   // либо User, либо ZodError с описанием
}
```

Тип и проверка не расходятся: меняется схема — меняется тип. `parse` бросает исключение, `safeParse` возвращает размеченный результат `{ success: true; data } | { success: false; error }`. То же самое делают :term[valibot]{def="лёгкая библиотека для описания и проверки схем данных"}, :term[ArkType]{def="библиотека проверки данных с синтаксисом, похожим на типы TypeScript"} и другие библиотеки — все реализуют общий интерфейс Standard Schema, поэтому формы и роутеры принимают любую из них.

Проверка стоит на **границе**: там, где данные входят в приложение. Это ответы API, `localStorage`, `postMessage`, параметры URL, `JSON.parse`. Внутри приложения после проверки типы снова надёжны. Кодогенерация типов из :term[OpenAPI]{def="формат описания REST API, по которому генерируют клиенты и типы"} или GraphQL-схемы помогает держать типы в синхроне с сервером, но рантайм-проверку не заменяет: она описывает, что сервер обещает, а не что он прислал.

### Ошибки как значения

Исключение в TypeScript не видно в типе функции: `fetchUser` может бросить что угодно. Если вызывающему важно обработать ошибку, её возвращают значением:

```ts
type Result<T, E = Error> = { ok: true; value: T } | { ok: false; error: E };

async function safe<T>(p: Promise<T>): Promise<Result<T>> {
  try {
    return { ok: true, value: await p };
  } catch (e) {
    return { ok: false, error: e instanceof Error ? e : new Error(String(e)) };
  }
}
```

Компилятор не даст прочитать `value`, пока не проверен `ok` (подробно — в [Сужении типов](/content/typescript/type-narrowing)).

### Отмена

Запрос, ответ которого уже не нужен, отменяют через `AbortSignal`:

```ts
const controller = new AbortController();
fetch('/api/search?q=чай', { signal: controller.signal });
controller.abort();   // fetch отклонится с DOMException, name === 'AbortError'

fetch('/api/search', { signal: AbortSignal.timeout(5000) });   // name === 'TimeoutError'
```

В `catch` ошибка — `unknown`, и отмену отличают от сбоя:

```ts
function isAbort(e: unknown) {
  return e instanceof DOMException && (e.name === 'AbortError' || e.name === 'TimeoutError');
}
```

Отмену при размонтировании компонента и гонки запросов разбирают в главах про фреймворки, здесь важна только типизация.

Данные из сети проверены. Вторая граница приложения — DOM.

## DOM

### querySelector

Тип результата зависит от селектора:

```ts
document.querySelector('input');      // HTMLInputElement | null
document.querySelector('img');        // HTMLImageElement | null
document.querySelector('#email');     // Element | null
document.querySelector('img.logo');   // Element | null
document.getElementById('email');     // HTMLElement | null
```

Точный тип выводится только для селектора из одного имени тега: стандартная библиотека сопоставляет строку с картой `HTMLElementTagNameMap`. Любой другой селектор — `Element`, у которого нет `value`, `src` и `disabled`.

`null` в типе — честный: элемента может не быть. Его убирают проверкой или `!`, если элемент гарантирован разметкой.

Для уточнения типа есть дженерик:

```ts
const select = document.querySelector<HTMLSelectElement>('#email');   // HTMLSelectElement | null
```

Но это утверждение, а не проверка: в проверке под видом `HTMLSelectElement` пришёл `input`, и `options` оказался `undefined`. Надёжно — `instanceof`:

```ts
const el = document.querySelector('#email');
if (el instanceof HTMLInputElement) {
  el.value;   // string
}
```

### События

`addEventListener` выводит тип события по имени из карты событий элемента:

```ts
input.addEventListener('keydown', (e) => e.key);   // e: KeyboardEvent
input.addEventListener('input', (e) => e.data);    // e: InputEvent
button.addEventListener('click', (e) => e.clientX);   // e: PointerEvent
```

Имя, которого нет в карте, даёт просто `Event`. А вот `currentTarget` и `target` типизированы одинаково — `EventTarget | null`, без элемента:

```ts
button.addEventListener('click', (e) => {
  e.currentTarget.disabled;   // ошибка: у EventTarget нет disabled
});
```

Почему так? `target` — элемент, на котором произошло событие, и это может быть любой потомок: клик по иконке внутри кнопки даёт `target` — иконку. `currentTarget` — элемент с обработчиком, его тип известен, но стандартная библиотека этого не выражает. В проверке клик по кнопке внутри формы дал `target` — `BUTTON`, `currentTarget` — `FORM`.

Решения: `instanceof` для `target`, `this` в обычной функции-обработчике (его тип — элемент, на котором вызван `addEventListener`), или замыкание на переменную с элементом.

### Формы

```ts
form.addEventListener('submit', (e) => {
  e.preventDefault();
  const data = new FormData(form);
  const email = data.get('email');   // FormDataEntryValue | null, то есть File | string | null
});
```

`FormData.get` возвращает `string`, `File` или `null`, потому что поле может быть файлом или отсутствовать. Значения формы — тоже граница данных: их проверяют той же схемой, что и ответы API. `dataset.sku` — всегда `string | undefined`, числа и булевы значения из атрибутов нужно разбирать.

### Свои события

Для своего события расширяют карту событий — интерфейсы стандартной библиотеки сливаются с объявлением (подробно — в [Составных типах](/content/typescript/composing-types)):

```ts
declare global {
  interface DocumentEventMap {
    'cart:updated': CustomEvent<{ count: number }>;
  }
}

document.addEventListener('cart:updated', (e) => {
  e.detail.count;   // number
});
document.dispatchEvent(new CustomEvent('cart:updated', { detail: { count: 3 } }));
```

Для событий на элементах расширяют `HTMLElementEventMap`, на `window` — `WindowEventMap`.

## Красные флаги в ответе

- **«`fetchJson<User>()` типизирует ответ».** Это `as`: компилятор верит, рантайм не проверяет.
- **«Под `strict` ошибки в `.catch` — `unknown`».** В `.catch` — `any`, `unknown` только в `try/catch`.
- **«`querySelector<HTMLInputElement>()` гарантирует тип».** Дженерик ничего не проверяет, надёжно — `instanceof`.
- **«`e.target` — элемент с обработчиком».** Это элемент, на котором произошло событие, обработчик — на `currentTarget`, и оба типизированы как `EventTarget | null`.
- **«TypeScript ловит забытый `await`».** Плавающие промисы ловит линтер, компилятор — только явные случаи вроде промиса в условии.

## Как спрашивают на собеседовании

::question
Что возвращает асинхронная функция?

#answer
Всегда `Promise<T>`, где `T` — тип того, что она возвращает через `return`. Аннотация должна быть `Promise<T>`, иначе TS1064. Без `return` — `Promise<void>`.

#more
Тип значения внутри достаёт `Awaited<T>`, он рекурсивен. Комбинаторы сохраняют типы: `Promise.all` — кортеж, `Promise.allSettled` — массив размеченных `PromiseSettledResult`. `new Promise` без параметра типа — `Promise<unknown>`.
::

::question
Безопасно ли `r.json() as Promise<User>` после fetch?

#answer
Нет. `json()` возвращает `any`, а `as User` — обещание компилятору без проверки. Если сервер пришлёт другую форму, тип останется `User`, а ошибка всплывёт далеко от загрузки.

#more
Данные на границе проверяют схемой (zod, valibot): `User.parse(await res.json())`, тип выводится через `z.infer`. Кодогенерация из OpenAPI синхронизирует типы с контрактом, но не проверяет, что пришло. Перед разбором тела проверяют `res.ok`: `fetch` не отклоняется на 404 и 500.
::

::question
Почему querySelector возвращает null?

#answer
Элемента с таким селектором может не быть, и тип это честно отражает. Перед использованием нужна проверка или `!`, если элемент гарантирован разметкой.

#more
Для селектора из имени тега выводится точный тип (`'input'` — `HTMLInputElement`), для остальных — `Element`. Дженерик `querySelector<T>()` — утверждение без проверки. Надёжный способ получить и тип, и проверку — `instanceof HTMLInputElement`.
::

::question
Как получить value из input в обработчике события?

#answer
`e.target` и `e.currentTarget` типизированы как `EventTarget | null`, и у них нет `value`. Нужно сузить: `if (e.target instanceof HTMLInputElement) e.target.value`.

#more
`target` — элемент, где произошло событие, он может быть потомком. `currentTarget` — элемент с обработчиком. В обычной функции-обработчике `this` типизирован как элемент. В React события типизированы иначе: `ChangeEvent<HTMLInputElement>` и `currentTarget.value` (подробно — в [TypeScript с React](/content/typescript/ts-with-react)).
::

::question
Какой тип у ошибки в catch?

#answer
В `try/catch` под `strict` — `unknown`: бросить можно что угодно, не только `Error`. Сужают через `instanceof Error`. В колбэке `.catch` у промиса — `any`, флаг на него не действует.

#more
Для `.catch` тип пишут явно: `(e: unknown) => ...`. Отмену запроса отличают по `e instanceof DOMException && e.name === 'AbortError'` (или `'TimeoutError'` для `AbortSignal.timeout`). Если ошибку нужно видеть в типе, её возвращают значением — `Result<T, E>`.
::

::question
Как типизировать своё событие?

#answer
Расширить карту событий стандартной библиотеки: `declare global { interface DocumentEventMap { 'cart:updated': CustomEvent<{ count: number }> } }`. Тогда `addEventListener('cart:updated', e => e.detail.count)` типизирован.

#more
Интерфейсы сливаются с объявлением из `lib.dom.d.ts`. Для элементов — `HTMLElementEventMap`, для `window` — `WindowEventMap`. Объявление должно быть в модуле (`export {}`) и входить в проект. Создаётся событие через `new CustomEvent(name, { detail })`.
::

## Практика

::practice{title="Загрузка с проверкой и понятной ошибкой"}
Напиши `getJson(url, schema)`: загружает JSON, проверяет схемой и возвращает типизированный результат. Ошибки HTTP, отмена и неверные данные должны различаться.

#solution
```ts
import { z } from 'zod';

type LoadError =
  | { kind: 'http'; status: number }
  | { kind: 'aborted' }
  | { kind: 'invalid'; issues: z.core.$ZodIssue[] }
  | { kind: 'network'; error: unknown };

type Result<T> = { ok: true; value: T } | { ok: false; error: LoadError };

async function getJson<S extends z.ZodType>(url: string, schema: S, signal?: AbortSignal): Promise<Result<z.infer<S>>> {
  let res: Response;
  try {
    res = await fetch(url, { signal });
  } catch (e) {
    if (e instanceof DOMException && (e.name === 'AbortError' || e.name === 'TimeoutError')) {
      return { ok: false, error: { kind: 'aborted' } };
    }
    return { ok: false, error: { kind: 'network', error: e } };
  }
  if (!res.ok) return { ok: false, error: { kind: 'http', status: res.status } };

  const parsed = schema.safeParse(await res.json());
  if (!parsed.success) return { ok: false, error: { kind: 'invalid', issues: parsed.error.issues } };
  return { ok: true, value: parsed.data };
}

const Product = z.object({ id: z.number(), title: z.string() });
const r = await getJson('/api/products/1', Product);
if (r.ok) r.value.title;                        // string
else if (r.error.kind === 'http') r.error.status;
```

Тип результата выводится из переданной схемы. Каждая ошибка — вариант размеченного объединения, и вызывающий может обработать каждую. В проверке ответ 404 дал `kind: 'http'`, неверное поле — `kind: 'invalid'`, `AbortSignal.timeout` — `kind: 'aborted'`.
::

::practice{title="Почему обработчик не компилируется?"}
```ts
document.querySelector('#search').addEventListener('input', (e) => {
  search(e.target.value);
});
```

Ошибки: `Object is possibly 'null'` и `Property 'value' does not exist on type 'EventTarget'`.

#solution
Две разных причины. `querySelector('#search')` — `Element | null`: селектор не имя тега, элемента может не быть. `e.target` — `EventTarget | null`: компилятор не знает, на каком элементе произошло событие.

```ts
const input = document.querySelector('#search');
if (!(input instanceof HTMLInputElement)) throw new Error('#search not found');

input.addEventListener('input', () => {
  search(input.value);   // input: HTMLInputElement — замыкание на проверенную переменную
});
```

`instanceof` одновременно проверяет наличие и тип. Внутри обработчика читаем `input` из замыкания, а не `e.target`: тип уже сужен, а `const` сохраняет сужение в колбэке. В проверке `#search` без `instanceof` давал `Element`, после — `HTMLInputElement`.
::
