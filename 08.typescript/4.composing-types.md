# Составные типы

Как собирать типы из других типов: объединения и пересечения, `type` и `interface`, индексные сигнатуры, операторы `keyof`, `typeof` и индексный доступ, расширение чужих типов. Спрашивают разницу `type` и `interface`, что такое слияние объявлений и когда брать объединение, а когда пересечение. Глубже — почему пересечение с конфликтом даёт `never`, почему интерфейс не подходит под `Record<string, unknown>` и как расширить тип из `node_modules`.

::tldr
- **Объединение `A | B` — значение одного из типов,** и без сужения доступны только общие члены. **Пересечение `A & B` — значение сразу обоих типов,** у него все свойства, а конфликтующие свойства становятся `never`.
- **`interface` и `type` почти взаимозаменяемы для объектов.** `interface` сливается с одноимёнными объявлениями и проверяет совместимость при `extends`. `type` выражает объединения, кортежи, mapped и условные типы.
- **Интерфейс не подходит под `Record<string, unknown>`:** у него нет неявной индексной сигнатуры, потому что его могут дополнить. Псевдоним типа — подходит.
- **`keyof`, `typeof` и индексный доступ `T['key']` выводят типы из других типов и значений.** Так тип живёт в одном месте, а не копируется.
- **Чужие типы расширяют через слияние объявлений:** `declare module 'lib'` для пакетов и `declare global` для глобальных объектов вроде `Window`.
::

## Объединения и пересечения

Сквозной пример — оплата заказа: карта, наличные или СБП.

```ts
type Card = { kind: 'card'; last4: string; pay(): Promise<void> };
type Cash = { kind: 'cash'; change: number; pay(): Promise<void> };
type Sbp = { kind: 'sbp'; phone: string; pay(): Promise<void> };

type PaymentMethod = Card | Cash | Sbp;
```

### Объединение

`A | B` — значение **одного из** типов. Пока неизвестно какого, доступны только члены, которые есть у всех вариантов:

```ts
function checkout(method: PaymentMethod) {
  method.pay();       // есть у всех
  method.kind;        // есть у всех: 'card' | 'cash' | 'sbp'
  method.last4;       // ошибка: есть только у карты
}
```

Чтобы добраться до `last4`, тип нужно **сузить** — проверить `method.kind === 'card'`. Общее поле-литерал `kind` превращает объединение в размеченное, и это самый удобный способ описать «одно из нескольких состояний» (подробно — в [Сужении типов](/content/typescript/type-narrowing)).

### Пересечение

`A & B` — значение, которое **одновременно** `A` и `B`. Для объектов это означает «все свойства обоих»:

```ts
type WithId = { id: number };
type Timestamps = { createdAt: Date; updatedAt: Date };
type Entity<T> = T & WithId & Timestamps;
```

Если свойства с одним именем конфликтуют, пересечение не падает с ошибкой, а делает свойство `never`:

```ts
type Conflict = { id: string } & { id: number };
// Conflict['id'] — never: значения, которое одновременно строка и число, нет
```

Такой тип невозможно создать — в проверке присваивание `{ id: 1 }` типу `Conflict` не скомпилировалось. Ошибка проявляется не в объявлении, а при использовании, поэтому её легко пропустить. Для примитивов пересечение несовместимых типов — просто `never`: `string & number`.

Правило выбора: **объединение** — когда значение бывает разным («карта или наличные»), **пересечение** — когда нужно собрать тип из частей («сущность = данные + id + даты»).

Собрать объект из частей можно и через `interface` с `extends`. Когда что брать?

## type и interface

```ts
interface Product {
  id: number;
  title: string;
}

type ProductType = {
  id: number;
  title: string;
};
```

Для описания формы объекта они почти взаимозаменяемы. Различия:

| | `interface` | `type` |
| --- | --- | --- |
| Объекты и функции | да | да |
| Объединения, кортежи, примитивы | нет | да |
| Mapped и условные типы | нет | да |
| Расширение | `extends` — проверяет совместимость | `&` — конфликт молча даёт `never` |
| Слияние объявлений | да | нет: повторное имя — ошибка |
| Подходит под `Record<string, unknown>` | нет | да |

### Слияние объявлений

Два `interface` с одним именем в одной области **сливаются** в один:

```ts
interface Settings { theme: string }
interface Settings { locale: string }
// Settings — { theme: string; locale: string }
```

Это не случайность, а механизм расширения: так библиотеки позволяют дополнять свои типы (о нём ниже). Обратная сторона — случайное совпадение имён с глобальным интерфейсом незаметно его дополнит.

### extends против &

`interface Derived extends Base` **проверяет**, что переопределённые свойства совместимы: `id: number` вместо `id: string` — ошибка в месте объявления. Пересечение `Base & { id: number }` то же самое молча превратит в `never`. Поэтому для иерархий объектов `extends` безопаснее.

### Неявная индексная сигнатура

Самое практическое отличие. Псевдоним типа подходит туда, где ожидается `Record<string, unknown>`, а интерфейс с теми же полями — нет:

```ts
declare const t: ProductType;
declare const i: Product;

const a: Record<string, unknown> = t;   // ок
const b: Record<string, unknown> = i;   // ошибка: Index signature for type 'string' is missing
```

Интерфейс открыт для слияния: в него могут добавить свойство любого типа, поэтому компилятор не может гарантировать, что все его значения — `unknown`-совместимые по индексной сигнатуре. Псевдоним закрыт, и для него такая гарантия есть. Это всплывает, когда функция логирования или сериализации принимает `Record<string, unknown>`.

### Что выбрать

Работают оба. Распространённое соглашение:

- **`interface`** — для публичных объектных контрактов, которые могут расширять (пропсы компонентов библиотеки, сущности API);
- **`type`** — для всего остального: объединений, производных и вычисляемых типов.

Главное — единообразие в проекте. Миф «`interface` быстрее» имеет основу (компилятор кеширует отношения интерфейсов, и у очень больших пересечений проверка медленнее), но в обычном коде это не заметно.

Типы объектов описаны. Следующий шаг — типы, где ключи заранее неизвестны.

## Индексные сигнатуры

Словарь цен по артикулу:

```ts
type PriceList = { [sku: string]: number };
// то же, что Record<string, number>
```

Индексная сигнатура описывает **любые** ключи данного типа. Особенности:

- **известные свойства должны ей соответствовать:** `{ [key: string]: number; title: string }` — ошибка, `title` не число;
- **чтение по ключу всегда даёт `number`**, даже если ключа нет. Опция `noUncheckedIndexedAccess` делает тип `number | undefined` и заставляет проверить (подробно — в [Настройке проекта](/content/typescript/project-setup));
- **ключи-шаблоны:** `{ [key: `data-${string}`]: string }` описывает только атрибуты с префиксом.

Если ключи известны, но их много, вместо индексной сигнатуры — `Record<'tea' | 'pot', number>`: тогда компилятор проверит, что заданы все.

## Типы из типов и значений

Три оператора позволяют не копировать типы, а выводить их.

**`typeof`** в позиции типа берёт тип значения:

```ts
const defaults = { currency: 'RUB', retries: 3, features: ['cart', 'promo'] };
type Defaults = typeof defaults;
// { currency: string; retries: number; features: string[] }
```

**`keyof`** — объединение ключей типа:

```ts
type ProductKey = keyof Product;     // 'id' | 'title'
```

У типа с индексной сигнатурой `string` `keyof` даёт `string | number`: в JavaScript числовые ключи всё равно превращаются в строки, поэтому `obj[7]` допустим.

**Индексный доступ** `T[K]` — тип свойства:

```ts
type Retries = Defaults['retries'];             // number
type Feature = Defaults['features'][number];    // string — тип элемента массива
type Item = (typeof cartItems)[number];         // тип элемента массива-значения
```

Вместе они дают главный приём: тип живёт в одном месте, а остальные из него выводятся. `keyof typeof` и `(typeof X)[keyof typeof X]` — основа замены `enum` на объект `as const` (подробно — в [Базовых типах](/content/typescript/basic-types)). Дальше эти операторы используются в дженериках и mapped-типах (подробно — в [Дженериках](/content/typescript/generics) и [Продвинутых типах](/content/typescript/advanced-types)).

## Расширение чужих типов

Слияние объявлений позволяет дополнить типы, которые ты не можешь изменить.

**Глобальные объекты.** Приложение кладёт версию в `window`:

```ts
// global.d.ts или любой модуль
declare global {
  interface Window {
    __APP_VERSION__: string;
  }
}

export {};   // чтобы файл был модулем
```

Интерфейс `Window` из стандартной библиотеки слился с объявлением, и `window.__APP_VERSION__` типизирован. `declare global` работает только внутри модуля — отсюда пустой `export {}`.

**Модули пакетов.** Так дополняют типы библиотек, которые для этого и сделаны расширяемыми:

```ts
// vue: глобальные свойства компонентов
declare module 'vue' {
  interface ComponentCustomProperties {
    $formatPrice: (value: number) => string;
  }
}
```

Аналогично добавляют поле `user` в `Request` в Express или свои переменные окружения в `ImportMetaEnv` в Vite. Расширять можно только интерфейсы: `type` не сливается. Объявление должно быть в файле, который входит в проект (`include` в tsconfig), иначе компилятор его не увидит.

---

## Красные флаги в ответе

- **«`type` и `interface` — одно и то же».** Для объектов почти, но `interface` сливается, проверяет совместимость при `extends` и не подходит под `Record<string, unknown>`; `type` описывает объединения и вычисляемые типы.
- **«Пересечение с конфликтом — ошибка».** Ошибки нет: конфликтующее свойство становится `never`, и проблема вылезет при использовании.
- **«У объединения доступны все свойства вариантов».** Только общие — до сужения.
- **«`keyof` словаря с `string`-ключами — `string`».** Это `string | number`.
- **«Тип из пакета нельзя изменить».** Интерфейсы расширяют через `declare module` и `declare global`.

## Как спрашивают на собеседовании

::question
В чём разница между type и interface?

#answer
Оба описывают объекты. `interface` можно расширять через `extends` и сливать одноимёнными объявлениями. `type` может описать объединение, кортеж, примитив, mapped и условный тип.

#more
`extends` проверяет совместимость переопределённых свойств, а `&` молча даёт `never` при конфликте. Интерфейс не имеет неявной индексной сигнатуры и не подходит под `Record<string, unknown>`, псевдоним — подходит. Соглашение: `interface` для расширяемых объектных контрактов, `type` для всего остального.
::

::question
Что такое слияние объявлений?

#answer
Несколько `interface` с одним именем в одной области объединяются в один со всеми свойствами. Так дополняют типы библиотек и глобальные объекты.

#more
Сливаются интерфейсы, пространства имён, а также интерфейс с классом и функция с пространством имён. `type` не сливается — повторное имя ошибка. Расширение пакетов — `declare module 'pkg' { interface X { ... } }`, глобальных объектов — `declare global` внутри модуля. Случайное совпадение имени с глобальным интерфейсом тоже сольётся, поэтому глобальные имена выбирают уникальными.
::

::question
Когда использовать объединение, а когда пересечение?

#answer
Объединение — значение бывает одним из нескольких типов («карта или наличные»). Пересечение — значение одновременно обладает свойствами нескольких типов («данные плюс id плюс даты»).

#more
У объединения без сужения доступны только общие члены, поэтому варианты помечают общим полем-литералом. У пересечения конфликтующие свойства становятся `never` без ошибки в объявлении. Пересечение функций ведёт себя как перегрузки, а пересечение несовместимых примитивов — `never`.
::

::question
Что делает keyof?

#answer
Возвращает объединение ключей типа: `keyof { id: number; title: string }` — `'id' | 'title'`. Используется в дженериках для типобезопасного доступа к свойствам.

#more
Для типа с индексной сигнатурой `string` `keyof` даёт `string | number`, потому что числовые ключи в JavaScript — строки. Вместе с `typeof` (тип значения) и индексным доступом `T[K]` позволяет выводить типы из одного источника: `(typeof X)[keyof typeof X]` — объединение значений объекта.
::

::question
Можно ли расширить типы из node_modules?

#answer
Да, если в пакете интерфейс: через слияние объявлений в `declare module 'pkg' { interface X { ... } }`. Глобальные объекты — через `declare global`.

#more
Файл с расширением должен входить в проект через `include`, а для `declare global` — быть модулем (`export {}`). Расширять можно только интерфейсы, поэтому библиотеки, которые ждут расширения, объявляют точки расширения интерфейсами: `ComponentCustomProperties` во Vue, `Request` в Express, `ImportMetaEnv` в Vite.
::

::question
Почему интерфейс не подходит под `Record<string, unknown>`?

#answer
У интерфейса нет неявной индексной сигнатуры. Компилятор не может гарантировать, что у интерфейса нет других свойств, ведь его могут дополнить слиянием. Псевдоним типа закрыт и подходит.

#more
Проблема всплывает в функциях логирования, сериализации и аналитики, которые принимают `Record<string, unknown>`. Решения: объявить данные через `type`, расширить функцию до `object` или дженерика `<T extends object>`, или добавить в интерфейс явную индексную сигнатуру, если она действительно нужна.
::

## Практика

::practice{title="Почему не вызывается логирование?"}
Функция аналитики принимает любые параметры события. С объектом заказа вызов не компилируется:

```ts
function track(event: string, params: Record<string, unknown>) { /* ... */ }

interface Order {
  id: number;
  total: number;
}

const order: Order = { id: 7, total: 4980 };
track('checkout', order);
// Index signature for type 'string' is missing in type 'Order'
```

#solution
У интерфейса нет неявной индексной сигнатуры: его можно дополнить слиянием, поэтому компилятор не считает его словарём `Record<string, unknown>`. Псевдоним типа подошёл бы.

Варианты:

```ts
// 1. функция принимает любой объект
function track<T extends object>(event: string, params: T) { /* ... */ }

// 2. данные описаны псевдонимом
type Order = { id: number; total: number };

// 3. копия в месте вызова — литерал совместим
track('checkout', { ...order });
```

Лучше первый: функции не нужно знать, что это словарь, ей достаточно объекта. В проверке псевдоним с теми же полями присвоился `Record<string, unknown>`, а интерфейс — нет.
::

::practice{title="Выведи типы из одного источника"}
Конфигурация доставки хранится объектом. Опиши тип способа доставки (`'courier' | 'pickup' | 'post'`) и тип цены доставки, не повторяя их вручную, а функция `cost` должна принимать только существующие способы.

```ts
const DELIVERY = {
  courier: { price: 300, days: 1 },
  pickup: { price: 0, days: 0 },
  post: { price: 200, days: 5 },
};
```

#solution
```ts
const DELIVERY = {
  courier: { price: 300, days: 1 },
  pickup: { price: 0, days: 0 },
  post: { price: 200, days: 5 },
} as const satisfies Record<string, { price: number; days: number }>;

type DeliveryMethod = keyof typeof DELIVERY;                 // 'courier' | 'pickup' | 'post'
type DeliveryPrice = (typeof DELIVERY)[DeliveryMethod]['price'];  // 300 | 0 | 200

function cost(method: DeliveryMethod): number {
  return DELIVERY[method].price;
}

cost('pickup');    // 0
cost('drone');     // ошибка: такого способа нет
```

`typeof` берёт тип значения, `keyof` — его ключи, индексный доступ — тип поля. `as const` сохраняет литералы, а `satisfies` проверяет, что у каждого способа есть цена и срок. Добавишь способ в объект — типы обновятся сами.
::
