# Настройка проекта

Что означают опции `tsconfig.json`: семейство `strict` и флаги сверх него, `target` и `lib`, `module` и `moduleResolution`, `types` и `paths`, файлы объявлений `.d.ts` и пакеты `@types`. Спрашивают, что даёт `strict`, зачем нужны `.d.ts` и что такое `moduleResolution: bundler`. Глубже — какие флаги стоит включить сверх `strict`, почему после обновления пропали типы Node.js и чем `nodenext` отличается от `bundler`.

::tldr
- **`strict` — набор проверок, без которых TypeScript ловит мало:** `null` и `undefined`, неявный `any`, инициализация полей, `unknown` в `catch`. В новых версиях он включён по умолчанию.
- **Сверх `strict` стоит включить `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`:** первый добавляет `undefined` к чтению по индексу, второй различает «свойства нет» и «свойство равно `undefined`».
- **`target` — до какого синтаксиса понижать код, `lib` — какие API считаются существующими.** Это разные вещи: можно писать для старого синтаксиса и при этом описать DOM.
- **`moduleResolution` описывает, кто ищет модули.** `bundler` — сборщик: расширения не нужны. `nodenext` — Node.js: в ESM нужен `.js` в относительных импортах.
- **`.d.ts` описывает типы без кода.** Типы библиотек — в самом пакете или в `@types/*`, а для модулей без типов и ассетов пишут `declare module`.
::

## Что настраивает tsconfig

`tsconfig.json` отвечает на три вопроса: **какие файлы** входят в проект (`include`, `exclude`, `files`), **насколько строго** их проверять и **в каком окружении** код будет работать — какой синтаксис и API доступны и как ищутся модули.

```json
{
  "compilerOptions": {
    "strict": true,
    "target": "es2023",
    "lib": ["es2023", "dom", "dom.iterable"],
    "module": "preserve",
    "moduleResolution": "bundler",
    "types": ["vite/client"],
    "noUncheckedIndexedAccess": true,
    "exactOptionalPropertyTypes": true,
    "verbatimModuleSyntax": true,
    "skipLibCheck": true,
    "noEmit": true
  },
  "include": ["src"]
}
```

Это типичный конфиг фронтенд-приложения, которое собирает :term[Vite]{def="сборщик и dev-сервер фронтенда на ES-модулях"}: `tsc` только проверяет (`noEmit`), а JavaScript выдаёт сборщик. Как проверка и сборка делят работу и зачем `isolatedModules` и `verbatimModuleSyntax`, разобрано в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling). Здесь — что означают сами опции, начиная с главной.

## strict

`strict` — не одна проверка, а флаг, который включает семейство:

| Флаг | Что ловит |
| --- | --- |
| `strictNullChecks` | `null` и `undefined` — отдельные типы, `find()` возвращает `T \| undefined` |
| `noImplicitAny` | параметр без типа, который не из чего вывести |
| `strictFunctionTypes` | контравариантность параметров функций |
| `strictBindCallApply` | типы аргументов в `bind`, `call`, `apply` |
| `strictPropertyInitialization` | поле класса не инициализировано в конструкторе |
| `noImplicitThis` | `this` с неявным `any` |
| `useUnknownInCatchVariables` | переменная в `catch` — `unknown`, а не `any` |
| `alwaysStrict` | `"use strict"` в каждом файле |
| `strictBuiltinIteratorReturn` | `undefined` в результате встроенных итераторов |

Самый важный — `strictNullChecks`. Без него `null` и `undefined` совместимы с любым типом, и главный класс ошибок JavaScript — «Cannot read properties of undefined» — компилятор не видит:

```ts
const el = [1, 2].find((n) => n > 5);
el.toFixed();   // со strict: 'el' is possibly 'undefined'; без — компилируется и падает
```

С TypeScript 6 `strict` включён по умолчанию: проект без единой опции уже проверяет неявный `any`. Флаги семейства можно выключать по одному (`"strict": true, "strictPropertyInitialization": false`), и так делают при переводе старого кода. Новые проверки, которые появляются в следующих версиях, тоже добавляются в `strict`, поэтому обновление TypeScript может принести новые ошибки — это ожидаемо.

`strict` закрывает не всё. Несколько флагов стоит включить отдельно.

## Строже, чем strict

### noUncheckedIndexedAccess

Без него чтение по индексу или ключу словаря возвращает тип значения, как будто элемент всегда есть:

```ts
const prices: Record<string, number> = {};
prices.tea.toFixed();   // компилируется, падает
[1][5].toFixed();       // компилируется, падает
```

С флагом результат — `number | undefined`, и компилятор требует проверку. Цена — проверки там, где программист точно знает, что элемент есть (`arr[0]` после `arr.length > 0`). Для перебора лучше `for...of` и методы массива: у них лишних `undefined` не появляется.

### exactOptionalPropertyTypes

По умолчанию `title?: string` принимает и отсутствие свойства, и явный `undefined`. Для патчей это ловушка: `{ ...product, ...{ title: undefined } }` затирает значение, а тип остаётся `string` (подробно — в [Утилитарных типах](/content/typescript/utility-types)). С флагом явный `undefined` в необязательном свойстве — ошибка TS2375. Если `undefined` действительно допустим, его пишут явно: `title?: string | undefined`.

### Остальные

- **`noImplicitOverride`** — переопределение метода родителя требует `override`. Ловит ситуацию, когда метод в родителе переименовали, а наследник «переопределяет» уже несуществующий.
- **`noPropertyAccessFromIndexSignature`** — ключи словаря читаются только через `env['API_URL']`, а точка остаётся для известных свойств. Видно, где обращение может вернуть `undefined`.
- **`noFallthroughCasesInSwitch`**, **`noImplicitReturns`** — стилевые проверки потока управления.

`tsc --init` в TypeScript 7 сразу включает `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes` — это сигнал, что их считают стандартом для нового кода.

Строгость настроена. Дальше — описание окружения.

## target и lib

**`target`** — до какой версии ECMAScript понижать синтаксис при выводе: с `es2015` `async/await` превратится в генераторы, с `es2022` останется как есть. Если JavaScript выдаёт сборщик, `target` в tsconfig влияет в основном на проверку, а реальный уровень задаёт сборщик (подробно — в [Транспиляции](/content/advanced-tooling/transpilation)). `target: es5` в TypeScript 7 удалён.

**`lib`** — какие встроенные API считаются существующими. По умолчанию выводится из `target` и включает DOM. Если указать вручную без `dom`, `document` пропадёт:

```text
error TS2584: Cannot find name 'document'. Do you need to change your target library?
```

`lib` не добавляет полифилы: `lib: ["es2025"]` разрешает писать `Iterator.prototype.map`, но в старом браузере его не будет. Описание API и его наличие в рантайме — разные вещи.

### types

Типы глобальных окружений — `process`, `describe`, `import.meta.env` — приходят из пакетов `@types/*` и подобных. Раньше TypeScript подключал **все** пакеты из `node_modules/@types` автоматически. С TypeScript 6 значение по умолчанию — `types: []`, и после обновления типичная ошибка:

```text
error TS2591: Cannot find name 'process'. Do you need to install type definitions for node?
```

Решение — перечислить нужные окружения явно: `"types": ["node"]` для серверного кода, `"types": ["vite/client"]` для приложения на Vite. Явный список ещё и защищает от конфликтов: типы Jest и Vitest объявляют одинаковые глобальные `describe` и `it`.

Окружение описано. Осталось понять, как компилятор находит импортированные модули.

## Модули

Две опции, которые часто путают:

- **`module`** — в каком формате модули (ESM, CommonJS) и как `tsc` их выводит;
- **`moduleResolution`** — по каким правилам строка `'./utils'` или `'react'` превращается в файл.

Правильное значение зависит от того, **кто выполняет импорты** в итоге.

### Код собирает сборщик

Vite, webpack, esbuild разрешают импорты сами и прощают многое: импорт без расширения, импорт папки, `exports` из `package.json`. Для этого:

```json
{ "module": "preserve", "moduleResolution": "bundler" }
```

`preserve` оставляет импорты как написаны — их обработает сборщик. `bundler` ищет модули так, как это делают сборщики. Это вариант для фронтенд-приложений.

### Код запускает Node.js

Node.js строже: в ESM относительный импорт должен содержать расширение. `nodenext` воспроизводит эти правила:

```ts
import { b } from './b';      // TS2835: Relative import paths need explicit file extensions
import { b } from './b.js';   // ок — даже если на диске b.ts
```

Расширение `.js` для файла `b.ts` выглядит странно, но так и задумано: TypeScript не переписывает пути при выводе (точнее, переписывает только с `rewriteRelativeImportExtensions`), и в рантайме будет файл `b.js`. Формат каждого файла `nodenext` определяет как Node.js: по полю `"type"` в ближайшем `package.json` и по расширениям `.mts` (всегда ESM) и `.cts` (всегда CommonJS).

Это вариант для серверного кода, :term[CLI]{def="программа с интерфейсом командной строки"} и библиотек, которые запускаются в Node.js без сборки. Старые режимы `moduleResolution: node` (он же `node10`) и `classic` в TypeScript 7 удалены.

### paths

Алиасы импортов — `@/components/Button` вместо `../../../components/Button`:

```json
{ "paths": { "@/*": ["./src/*"] } }
```

`paths` только сообщает компилятору, где искать. Сборщику алиас нужно настроить отдельно (`resolve.alias` в Vite), иначе проверка пройдёт, а сборка — нет. Раньше `paths` работали относительно `baseUrl`. В TypeScript 7 `baseUrl` удалён, а `paths` считаются от расположения `tsconfig.json`.

Компилятор нашёл файл модуля. Но что, если у модуля нет типов?

## Файлы объявлений

**`.d.ts`** содержит только типы — без кода. Это «заголовочный файл» для JavaScript: реализация в `.js`, описание в `.d.ts`.

Откуда берутся типы библиотек:

1. **Из самого пакета.** Пакет указывает типы в `package.json` (`"types"` или условие `"types"` в `"exports"`). Так поставляются React 19, Vue, zod.
2. **Из DefinitelyTyped.** Для пакетов без своих типов сообщество поддерживает `@types/<имя>`: `@types/node`, `@types/lodash`. Версия `@types` должна соответствовать версии пакета.
3. **Самостоятельно,** если нет ни того, ни другого.

### declare module

Для модуля без типов достаточно объявить его форму:

```ts
// src/legacy.d.ts
declare module 'legacy-slug' {
  export function slugify(s: string): string;
}
```

Тот же приём для импортов ассетов, которые обрабатывает сборщик:

```ts
// src/assets.d.ts
declare module '*.svg' {
  const src: string;
  export default src;
}
```

Без этих объявлений `import logo from './logo.svg'` даёт TS2307 «Cannot find module». Шаблоны Vite подключают такие объявления через `vite/client`. Если типы нужны срочно, а описывать лень, `declare module 'legacy-slug';` без тела делает весь модуль `any` — это временная мера.

Отдельный случай — **импорты ради побочного эффекта**: `import './styles.css'`. С TypeScript 6 включён `noUncheckedSideEffectImports`, и опечатка в пути `'./stlyes.css'` — ошибка, а не тихий пропуск. Для CSS-файлов, которые обрабатывает сборщик, нужно объявление `declare module '*.css'`, его тоже даёт `vite/client`.

### skipLibCheck

`skipLibCheck: true` не проверяет `.d.ts` из зависимостей. Это заметно ускоряет проверку и спасает от конфликтов между `@types`, которые не исправить в своём коде. Цена — ошибка в собственных `.d.ts` проекта тоже пропускается, поэтому свои объявления держат минимальными.

Расширение типов чужих пакетов через `declare module` и `declare global` — в [Составных типах](/content/typescript/composing-types).

## Эволюция

Актуально на ноябрь 2026.

| Версия | Изменение |
| --- | --- |
| TypeScript 5.0 | `moduleResolution: bundler`, `verbatimModuleSyntax` |
| TypeScript 5.4 | `module: preserve` |
| TypeScript 6.0 | последний компилятор на JavaScript; по умолчанию `strict: true`, `types: []`, `noUncheckedSideEffectImports`; `baseUrl`, `target: es5`, `moduleResolution: node10`, AMD и UMD объявлены устаревшими |
| TypeScript 7.0 | нативный компилятор на Go; устаревшие в 6.0 опции удалены; `tsc --init` включает `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes` |

Инструменты, которым нужен программный API компилятора (`vue-tsc`, часть правил typescript-eslint), пока работают с TypeScript 6. Конфиг, который проходит TypeScript 7 без ошибок, подходит и для 6.

## Красные флаги в ответе

- **«`strict` — это одна проверка на `null`».** Это семейство флагов, и новые проверки добавляются в него с версиями.
- **«`lib: ['es2025']` — значит, методы ES2025 будут работать в браузере».** `lib` описывает API, но не добавляет полифилы.
- **«`paths` настраивает алиасы для сборки».** Только для компилятора, сборщику нужна своя настройка.
- **«`.js` в импорте `.ts`-файла — ошибка».** Под `nodenext` это правильный путь к файлу, который будет в рантайме.
- **«`skipLibCheck` проверяет только мои файлы и ничего не теряет».** Он пропускает и собственные `.d.ts` проекта.

## Как спрашивают на собеседовании

::question
Что даёт strict: true?

#answer
Включает семейство строгих проверок: `strictNullChecks`, `noImplicitAny`, `strictFunctionTypes`, `strictPropertyInitialization`, `useUnknownInCatchVariables` и другие. Самая важная — `strictNullChecks`: без неё `null` и `undefined` подходят под любой тип, и компилятор не видит самых частых ошибок.

#more
С TypeScript 6 `strict` включён по умолчанию. Флаги можно выключать по одному при миграции. Новые проверки добавляются в семейство с версиями, поэтому обновление может дать новые ошибки. Сверх `strict` стоит включить `noUncheckedIndexedAccess` и `exactOptionalPropertyTypes`.
::

::question
Зачем нужны .d.ts файлы?

#answer
Они описывают типы без реализации: функции, классы, модули. Так JavaScript-код получает типы — библиотека поставляет `.js` и рядом `.d.ts`. Для пакетов без своих типов есть `@types/*` из DefinitelyTyped.

#more
Для модуля без типов пишут `declare module 'pkg' { ... }`, для ассетов — `declare module '*.svg'`. Глобальные типы окружений подключаются через `types`, и с TypeScript 6 по умолчанию это пустой список. `skipLibCheck` не проверяет `.d.ts` зависимостей — быстрее, но и свои `.d.ts` пропускаются.
::

::question
Что такое moduleResolution: bundler?

#answer
Режим поиска модулей, который повторяет правила сборщиков: импорты без расширений, `exports` и `imports` из `package.json`. Подходит, когда код собирает Vite, webpack или esbuild. Обычно в паре с `module: preserve`.

#more
Для кода, который запускает Node.js без сборки, — `nodenext`: он требует расширения `.js` в относительных ESM-импортах и определяет формат файла по `"type"` в `package.json` и расширениям `.mts` и `.cts`. Старый `node10` в TypeScript 7 удалён.
::

::question
В чём разница между tsc и esbuild или SWC?

#answer
`tsc` проверяет типы и может выдать JavaScript. esbuild и SWC только стирают типы, без проверки, зато пофайлово и в десятки раз быстрее. Поэтому сборку делают они, а проверку — `tsc --noEmit` в редакторе и CI.

#more
Пофайловое стирание не поддерживает конструкции, которым нужна вся программа, — отсюда `isolatedModules` и `verbatimModuleSyntax`. TypeScript 7 на Go сильно ускорил проверку, но разделение ролей осталось. Подробно — в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling).
::

::question
Чем target отличается от lib?

#answer
`target` — до какой версии ECMAScript понижать синтаксис при выводе. `lib` — какие встроенные API компилятор считает существующими: версии ECMAScript, DOM, Web Worker.

#more
По умолчанию `lib` выводится из `target` и включает DOM. Указанный вручную `lib` без `dom` убирает `document`. `lib` не добавляет полифилы: описать API в типах не значит получить его в старом браузере. Если код собирает сборщик, реальный уровень синтаксиса задаёт его настройка.
::

::question
Почему после обновления TypeScript пропали типы process и describe?

#answer
С TypeScript 6 значение `types` по умолчанию — пустой список. Раньше компилятор подключал все пакеты из `node_modules/@types`, теперь — только перечисленные. Решение — `"types": ["node"]` или `["vite/client", "vitest/globals"]`.

#more
Явный список лучше: окружения не смешиваются (типы Jest и Vitest объявляют одинаковые глобальные функции), а в разных частях проекта — свои окружения через несколько tsconfig. Ошибка выглядит как TS2591 «Cannot find name 'process'. Do you need to install type definitions for node?».
::

## Практика

::practice{title="Проект перестал собираться после обновления"}
После обновления TypeScript до 7 проверка падает:

```text
tsconfig.json: error TS5102: Option 'baseUrl' has been removed.
tsconfig.json: error TS5108: Option 'moduleResolution=node10' has been removed.
src/env.ts: error TS2591: Cannot find name 'process'.
```

Конфиг:

```json
{
  "compilerOptions": {
    "target": "es2020",
    "module": "esnext",
    "moduleResolution": "node",
    "baseUrl": ".",
    "paths": { "@/*": ["src/*"] }
  }
}
```

#solution
Три изменения TypeScript 6 и 7: удалены `baseUrl` и `moduleResolution: node`, а `types` по умолчанию пустой.

```json
{
  "compilerOptions": {
    "target": "es2020",
    "module": "preserve",
    "moduleResolution": "bundler",
    "paths": { "@/*": ["./src/*"] },
    "types": ["node", "vite/client"]
  }
}
```

`paths` теперь считаются от `tsconfig.json`, поэтому путь начинается с `./`. Для приложения на сборщике `node` меняют на `bundler`, для кода на Node.js — на `nodenext`. `strict` теперь включён по умолчанию, поэтому после исправления конфига могут появиться ошибки типов в коде — их исправляют или временно выключают отдельные флаги. В проверке старый конфиг дал TS5102 и TS5108, новый прошёл, а `process` без `types: ["node"]` дал TS2591.
::

::practice{title="Где компилятор пропустил undefined?"}
Код компилируется под `strict`, но падает. Какие флаги поймали бы обе ошибки?

```ts
const discounts: Record<string, number> = { tea: 0.1 };

function price(sku: string, base: number) {
  return base * (1 - discounts[sku]);   // NaN для неизвестного sku
}

type Patch = { title?: string };
function apply(product: { title: string }, patch: Patch) {
  return { ...product, ...patch };
}
apply({ title: 'Чай' }, { title: undefined }).title.toUpperCase();   // TypeError
```

#solution
- `noUncheckedIndexedAccess`: `discounts[sku]` становится `number | undefined`, и компилятор требует обработать отсутствие: `discounts[sku] ?? 0`.
- `exactOptionalPropertyTypes`: `{ title: undefined }` больше не подходит под `title?: string` — ошибка TS2379 в месте вызова.

```ts
function price(sku: string, base: number) {
  return base * (1 - (discounts[sku] ?? 0));
}
```

Оба флага не входят в `strict`, потому что дают много ошибок в существующем коде. В новых проектах их включают сразу — `tsc --init` в TypeScript 7 так и делает. В проверке без флагов код компилировался, с ними — дал TS2532 «Object is possibly undefined» и TS2379.
::

::practice{title="Импорт SVG и пакета без типов"}
В приложении на Vite две ошибки TS2307 «Cannot find module»:

```ts
import logo from './logo.svg';
import { slugify } from 'legacy-slug';   // старый пакет без типов и без @types
```

#solution
Для ассета — объявление шаблона модуля. В проекте на Vite оно уже есть в `vite/client`, достаточно подключить: `"types": ["vite/client"]`. Вручную:

```ts
// src/assets.d.ts
declare module '*.svg' {
  const src: string;
  export default src;
}
```

Для пакета — объявление его формы, только то, что используется:

```ts
// src/legacy.d.ts
declare module 'legacy-slug' {
  export function slugify(s: string): string;
}
```

Файлы должны входить в проект через `include`. Объявление — обещание, которое компилятор не проверяет: если `slugify` на самом деле возвращает объект, ошибка проявится в рантайме. В проверке без объявлений было две ошибки TS2307, с ними — ни одной.
::
