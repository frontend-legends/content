# Настройка проекта

Знать типы - это одно, а правильно настроить TypeScript-проект - совсем другое. tsconfig.json, strict mode, declaration files, сборка - тут много нюансов, которые влияют на DX и безопасность типов. Разберём всё по порядку.

---

## Структура tsconfig.json

```ts
// tsconfig.json (на самом деле это JSONC - с комментариями)
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "lib": ["DOM", "ES2020"],
    "outDir": "./dist",
    "rootDir": "./src",
    "strict": true,
    "esModuleInterop": true,
    "moduleResolution": "bundler",
    "jsx": "react-jsx"
  },
  "include": ["src/**/*.ts", "src/**/*.tsx"],
  "exclude": ["node_modules", "dist"]
}
```

- <b class="text-on-semi-light">compilerOptions</b> - <span class="text-gray">основные настройки компилятора</span>
- <b class="text-on-semi-light">include</b> - <span class="text-gray">какие файлы компилировать (glob-паттерны)</span>
- <b class="text-on-semi-light">exclude</b> - <span class="text-gray">какие файлы исключить</span>

Если `include` не указан, TypeScript возьмёт все `.ts` и `.tsx` файлы в директории и поддиректориях.

## Ключевые опции компилятора

### target - целевая версия JavaScript

```ts
{
  "target": "ES2020" // Какой JS генерировать
}
```

| <b class="text-on-semi-light">Значение</b> | <span class="text-gray">Описание</span> |
|---|---|
| `ES5` | Для старых браузеров, async/await превращается в генераторы |
| `ES2015` (ES6) | Классы, стрелочные функции, let/const |
| `ES2020` | Optional chaining, nullish coalescing, BigInt |
| `ESNext` | Самые свежие фичи, всегда последняя версия |

Для большинства проектов с бандлером (Vite, webpack) подходит `ES2020` или `ESNext` - бандлер сам транспилирует дальше.

### module - система модулей

```ts
{
  "module": "ESNext" // Какие import/export генерировать
}
```

| <b class="text-on-semi-light">Значение</b> | <span class="text-gray">Когда использовать</span> |
|---|---|
| `CommonJS` | Node.js проекты без ESM |
| `ESNext` | Фронтенд с бандлером |
| `NodeNext` | Node.js с нативными ESM-модулями |

### lib - доступные API

```ts
{
  "lib": ["DOM", "ES2020", "DOM.Iterable"]
}
```

`lib` определяет, какие типы глобальных API будут доступны. Для браузерного проекта нужен `DOM`, для Node.js - нет.

### moduleResolution - как искать модули

```ts
{
  "moduleResolution": "bundler" // Или "node", "node16", "nodenext"
}
```

| <b class="text-on-semi-light">Значение</b> | <span class="text-gray">Когда использовать</span> |
|---|---|
| `node` | Классический алгоритм Node.js |
| `node16` / `nodenext` | Для Node.js с ESM-модулями |
| `bundler` | Для Vite, webpack, esbuild - самый гибкий |

`bundler` - лучший выбор для фронтенда. Он позволяет не указывать расширения файлов и работает с path aliases.

### esModuleInterop

```ts
{
  "esModuleInterop": true
}
```

Позволяет использовать default import из CommonJS-модулей:

```ts
// Без esModuleInterop:
import * as express from 'express';

// С esModuleInterop:
import express from 'express';
```

Почти всегда ставь `true`.

### jsx

```ts
{
  "jsx": "react-jsx" // React 17+ с автоматическим runtime
}
```

| <b class="text-on-semi-light">Значение</b> | <span class="text-gray">Описание</span> |
|---|---|
| `react` | `React.createElement` (классический, нужен import React) |
| `react-jsx` | Новый JSX runtime (React 17+, не нужен import React) |
| `preserve` | Оставить JSX как есть (для Babel или другого трансформера) |

### Пути: outDir, rootDir, baseUrl, paths

```ts
{
  "outDir": "./dist",        // Куда складывать скомпилированные файлы
  "rootDir": "./src",        // Откуда считать корень исходников
  "baseUrl": ".",            // Базовая директория для неотносительных импортов
  "paths": {
    "@/*": ["./src/*"],      // import { Button } from '@/components/Button'
    "@utils/*": ["./src/utils/*"]
  }
}
```

⚠️ `paths` работает только на этапе проверки типов. Для реального разрешения путей в рантайме нужна настройка в бандлере (Vite: `resolve.alias`, webpack: `resolve.alias`).

## Strict mode

`"strict": true` - одна настройка, которая включает сразу несколько проверок.

### Что включает strict: true

| <b class="text-on-semi-light">Флаг</b> | <span class="text-gray">Что делает</span> |
|---|---|
| `strictNullChecks` | `null` и `undefined` - отдельные типы, не присваиваются к другим |
| `noImplicitAny` | Ошибка, если TypeScript не может вывести тип и подставляет any |
| `strictFunctionTypes` | Контравариантная проверка параметров функций |
| `strictBindCallApply` | Типизированные `bind`, `call`, `apply` |
| `noImplicitThis` | Ошибка, если `this` имеет тип any |
| `alwaysStrict` | Добавляет `"use strict"` в каждый файл |
| `strictPropertyInitialization` | Свойства классов должны быть инициализированы в конструкторе |
| `useUnknownInCatchVariables` | `catch(e)` - e имеет тип unknown, а не any |

### strictNullChecks - самый важный флаг

```ts
// Без strictNullChecks:
const user: User = getUser(); // Может быть null, но TS не ругается
user.name; // Потенциальный runtime crash

// С strictNullChecks:
const user: User | null = getUser();
user.name; // Ошибка: Object is possibly 'null'

if (user) {
  user.name; // OK - TypeScript знает, что user не null
}
```

### noImplicitAny

```ts
// Без noImplicitAny:
function process(data) { // data: any - тихо подставился
  return data.something; // Никакой проверки
}

// С noImplicitAny:
function process(data) { // Ошибка: Parameter 'data' implicitly has an 'any' type
  return data.something;
}

function process(data: unknown) { // Явно указали тип - OK
  // ...
}
```

### strictPropertyInitialization

```ts
class UserService {
  private client: HttpClient; // Ошибка: не инициализировано

  // Три способа исправить:

  // 1. Инициализация в конструкторе
  constructor() {
    this.client = new HttpClient();
  }

  // 2. Значение по умолчанию
  private client = new HttpClient();

  // 3. Definite assignment assertion (если инициализация где-то ещё)
  private client!: HttpClient; // ! говорит "я знаю, что инициализирую позже"
}
```

Рекомендация: всегда начинай новый проект с `"strict": true`. Включать strict постфактум в большом проекте - болезненно.

## Declaration files (.d.ts)

### Что это такое

Declaration files содержат только определения типов без реализации. Они нужны, чтобы TypeScript понимал структуру JavaScript-библиотек.

```ts
// math-utils.d.ts
export declare function add(a: number, b: number): number;
export declare function multiply(a: number, b: number): number;
export declare const PI: number;
```

### Написание .d.ts для JS-библиотеки

```ts
// types/legacy-lib.d.ts
declare module 'legacy-lib' {
  export interface Options {
    timeout: number;
    retries?: number;
  }

  export function init(options: Options): void;
  export function getData(key: string): Promise<unknown>;
}
```

### declare keyword

```ts
// Объявление глобальной функции
declare function gtag(command: string, ...args: any[]): void;

// Объявление модуля (для CSS modules, изображений и т.д.)
declare module '*.css' {
  const classes: Record<string, string>;
  export default classes;
}

declare module '*.svg' {
  const content: string;
  export default content;
}

// Расширение глобального пространства
declare global {
  interface Window {
    __APP_VERSION__: string;
    analytics: {
      track(event: string, data?: Record<string, unknown>): void;
    };
  }
}

export {}; // Нужно, чтобы файл был модулем
```

## DefinitelyTyped и @types

Когда у библиотеки нет встроенных типов, типы обычно есть в репозитории DefinitelyTyped:

```ts
// Установка типов
npm install --save-dev @types/lodash
npm install --save-dev @types/express
npm install --save-dev @types/node
```

TypeScript автоматически находит типы из `@types` в `node_modules`. Можно ограничить, какие `@types` подтягиваются:

```ts
{
  "compilerOptions": {
    "typeRoots": ["./node_modules/@types", "./types"], // Где искать типы
    "types": ["node", "jest"] // Какие @types включать (по умолчанию - все)
  }
}
```

Если указать `types`, TypeScript подключит только перечисленные пакеты из `@types`. Остальные будут доступны только при явном импорте.

## ESM vs CJS в TypeScript

### Node.js с ESM

```ts
{
  "compilerOptions": {
    "module": "NodeNext",
    "moduleResolution": "nodenext"
  }
}
```

При `module: "NodeNext"` TypeScript различает ESM и CJS по расширению файла:

| <b class="text-on-semi-light">Расширение</b> | <span class="text-gray">Система модулей</span> |
|---|---|
| `.mts` -> `.mjs` | ESM |
| `.cts` -> `.cjs` | CJS |
| `.ts` -> `.js` | Зависит от `"type"` в package.json |

```ts
// package.json
{
  "type": "module" // Все .ts файлы считаются ESM
}
```

⚠️ При `module: "NodeNext"` в ESM-файлах нужно указывать расширения в импортах:

```ts
// Нужно писать расширение .js (даже для .ts файлов!)
import { helper } from './utils.js';
```

## Инструменты сборки

### tsc - компилятор TypeScript

```ts
// Компиляция
npx tsc

// Watch mode
npx tsc --watch

// Проверка типов без генерации файлов
npx tsc --noEmit
```

`tsc` проверяет типы и генерирует JS. Но он медленный для больших проектов.

### Быстрые альтернативы

| <b class="text-on-semi-light">Инструмент</b> | <span class="text-gray">Особенности</span> |
|---|---|
| `ts-node` | Запуск .ts напрямую в Node.js, JIT-компиляция |
| `tsx` | Быстрая альтернатива ts-node на базе esbuild |
| `SWC` | Rust-компилятор, в 20-70x быстрее tsc (без проверки типов) |
| `esbuild` | Go-компилятор, невероятно быстрая сборка (без проверки типов) |

Типичная стратегия для продакшена:

```ts
// package.json
{
  "scripts": {
    "dev": "tsx watch src/index.ts",       // Быстрый dev-сервер
    "typecheck": "tsc --noEmit",            // Проверка типов отдельно
    "build": "tsc --noEmit && esbuild src/index.ts --bundle --outfile=dist/index.js"
  }
}
```

Проверку типов запускают отдельно (`tsc --noEmit`), а сборку делают быстрым инструментом (esbuild, SWC). Так получается и быстро, и безопасно.

## Project references

Для монорепозиториев и больших проектов TypeScript поддерживает project references - разделение на подпроекты с инкрементальной сборкой.

```ts
// tsconfig.json (корневой)
{
  "references": [
    { "path": "./packages/shared" },
    { "path": "./packages/client" },
    { "path": "./packages/server" }
  ]
}
```

```ts
// packages/shared/tsconfig.json
{
  "compilerOptions": {
    "composite": true,       // Обязательно для referenced проектов
    "declaration": true,     // Генерировать .d.ts
    "declarationMap": true,  // Source maps для .d.ts
    "outDir": "./dist"
  }
}
```

```ts
// packages/client/tsconfig.json
{
  "compilerOptions": {
    "composite": true
  },
  "references": [
    { "path": "../shared" }  // Зависимость от shared
  ]
}
```

Сборка:

```ts
// Собрать все проекты с учётом зависимостей
npx tsc --build

// Инкрементальная сборка (пересобирает только изменённое)
npx tsc --build --incremental
```

Преимущества: каждый пакет компилируется отдельно, инкрементальная сборка работает на уровне пакетов, `tsc --build` автоматически определяет порядок сборки.

## Частые вопросы на собесе

<b class="text-on-semi-light">Что даёт strict: true?</b>
<span class="text-gray">Включает набор строгих проверок: strictNullChecks, noImplicitAny, strictFunctionTypes и другие. Главное - null и undefined становятся отдельными типами, а implicit any вызывает ошибку. Это ловит большинство типичных ошибок на этапе компиляции.</span>

<b class="text-on-semi-light">Зачем нужны .d.ts файлы?</b>
<span class="text-gray">Declaration files описывают типы для JavaScript-кода. Они нужны, когда: 1) используешь JS-библиотеку без встроенных типов, 2) пишешь библиотеку и хочешь предоставить типы, 3) нужно описать глобальные переменные (window, process). Файлы .d.ts содержат только типы - никакой реализации.</span>

<b class="text-on-semi-light">В чём разница между tsc и esbuild/SWC?</b>
<span class="text-gray">tsc - единственный инструмент, который проверяет типы. esbuild и SWC только убирают аннотации типов и транспилируют, но не проверяют типы. Поэтому обычно используют оба: tsc --noEmit для проверки типов, esbuild/SWC для быстрой сборки.</span>

<b class="text-on-semi-light">Что такое moduleResolution: bundler?</b>
<span class="text-gray">Это режим разрешения модулей, оптимизированный для бандлеров (Vite, webpack). Он позволяет импортировать без расширений файлов, поддерживает exports/imports из package.json, и не требует странных хаков, которые нужны для node16/nodenext.</span>
