# Базовые типы

Из каких типов строится всё остальное: примитивы, `any`, `unknown`, `never` и `void`, литеральные типы, `enum`, массивы и кортежи, а также два инструмента, которые управляют выводом типов, — `as const` и `satisfies`. Спрашивают разницу `any` и `unknown`, `enum` против `as const` и что делает `satisfies`. Глубже — почему `{}` принимает число, когда литерал расширяется до `string`, почему числовой `enum` — это объект в рантайме и как испортить кортеж через `push`.

::tldr
- **`any` выключает проверку и заражает всё, что из него выводится. `unknown` — безопасный «что угодно»:** присвоить можно всё, использовать — только после сужения.
- **`never` — пустой тип:** присваивается чему угодно, а ему — ничего. Это тип функций, которые не возвращаются, невозможных пересечений и проверки полноты.
- **Литеральные типы и расширение:** `const` сохраняет `'paid'`, а `let` и свойства объекта расширяют его до `string`. `as const` замораживает литералы и делает всё `readonly`.
- **`enum` порождает код и объект в рантайме,** строковый `enum` не принимает строки. Обычно вместо него берут объединение литералов или объект `as const`.
- **`satisfies` проверяет значение по типу, не расширяя его.** Аннотация `: T` заменяет выведенный тип на `T` и теряет детали.
::

## Примитивы и пустые значения

Сквозной пример — заказ в магазине: статус, валюта, позиции и конфигурация маршрутов.

```ts
type OrderStatus = 'draft' | 'paid' | 'shipped';

interface Order {
  id: number;
  status: OrderStatus;
  total: number;
  promo?: string;
  paidAt: Date | null;
}
```

Примитивные типы повторяют JavaScript: `string`, `number`, `bigint`, `boolean`, `symbol`, `undefined`, `null` (подробно о самих значениях — в [Типах и переменных](/content/javascript/types-and-variables)). С включённым `strictNullChecks` (часть `strict`) `null` и `undefined` — отдельные типы: в переменную `number` их не положить. «Может отсутствовать» пишут явно: `paidAt: Date | null`.

Необязательное свойство `promo?: string` и свойство `promo: string | undefined` — не одно и то же. Первое можно не указывать вовсе, второе обязано присутствовать, пусть и со значением `undefined`. Разницу строго проверяет опция `exactOptionalPropertyTypes` (подробно — в [Настройке проекта](/content/typescript/project-setup)).

Примитивы просты. Сложнее — типы, которых нет в JavaScript.

## any, unknown, never, void

### any и unknown

Оба принимают любое значение. Разница — в том, что можно сделать с ним дальше:

```ts
declare const fromAny: any;
declare const fromUnknown: unknown;

fromAny.deep.call();          // компилируется — и упадёт при выполнении
fromUnknown.toUpperCase();    // ошибка: 'fromUnknown' is of type 'unknown'

if (typeof fromUnknown === 'string') {
  fromUnknown.toUpperCase();  // после проверки — можно
}
```

`any` **выключает** проверку и **заражает**: результат любой операции с `any` — тоже `any`, и он присваивается чему угодно. Одно `any` в начале цепочки делает непроверяемой всю цепочку. `unknown` — «что угодно, но докажи». Это правильный тип для данных извне: `JSON.parse`, ответов сервера, `catch (error)`. С `useUnknownInCatchVariables` (часть `strict`) ошибка в `catch` — `unknown`, а не `any`.

### never

`never` — тип без значений. У него обратные свойства:

- `never` присваивается **чему угодно** — это «нижний» тип;
- `never` **ничего** не присваивается, кроме самого `never`.

Где он встречается:

- функция, которая никогда не возвращается: бросает исключение или работает бесконечно, — `function fail(msg: string): never`;
- невозможное пересечение: `string & number` — это `never`;
- пустое объединение, например после того, как сужение исключило все варианты. На этом построена проверка полноты `switch` (подробно — в [Сужении типов](/content/typescript/type-narrowing)).

### void

`void` — «возвращаемое значение не используется». Функция с типом `() => void` может что-то вернуть, если её присвоили переменной такого типа: поэтому `[1, 2].forEach((x) => arr.push(x))` компилируется, хотя `push` возвращает число. Подробно — в [Функциях и классах](/content/typescript/functions-and-classes).

### {} и object

Частая ловушка:

- **`{}`** — любое значение, кроме `null` и `undefined`, **включая примитивы**: `const a: {} = 42` компилируется;
- **`object`** — любое не-примитивное значение: объект, массив, функция;
- **`Object`** — тип обёртки, на практике совпадает с `{}`, использовать не нужно.

Для «любого объекта со свойствами» пишут `Record<string, unknown>`, а для «чего угодно, кроме пустоты» — `NonNullable<unknown>`.

Специальные типы описывают крайние случаи. Повседневная работа — с конкретными значениями, и здесь важны литеральные типы.

## Литеральные типы и расширение

Литеральный тип — тип с одним значением: `'paid'`, `42`, `true`. Объединение литералов описывает конечный набор: `type OrderStatus = 'draft' | 'paid' | 'shipped'`.

Тонкость — в **расширении** (widening). Вывод типов решает, сохранить литерал или расширить его до общего типа:

```ts
const status = 'paid';                   // 'paid' — const не изменится
let mutable = 'paid';                    // string — let может измениться
const order = { status: 'paid' };        // { status: string } — свойство можно переписать

setStatus(status);         // ок
setStatus(mutable);        // ошибка: string не подходит под OrderStatus
setStatus(order.status);   // ошибка: то же
```

Компилятор рассуждает просто: значение, которое может измениться, не должно быть привязано к одному литералу. Свойство объекта может измениться, поэтому `{ status: 'paid' }` получает тип `{ status: string }`. Это главный источник ошибок вида «`string` is not assignable to `'paid' | 'shipped'`».

### as const

`as const` запрещает расширение целиком:

```ts
const order = { status: 'paid', items: ['tea'] } as const;
// { readonly status: 'paid'; readonly items: readonly ['tea'] }
```

Все свойства становятся `readonly`, строки и числа — литералами, массивы — `readonly`-кортежами, на всю глубину. Это не заморозка в рантайме (в отличие от `Object.freeze`), а только тип.

Главное применение — вывести объединение из значений, чтобы список жил в одном месте:

```ts
const ORDER_STATUS = { Draft: 'draft', Paid: 'paid', Shipped: 'shipped' } as const;
type OrderStatus = (typeof ORDER_STATUS)[keyof typeof ORDER_STATUS];
// 'draft' | 'paid' | 'shipped'
```

`typeof` берёт тип значения, `keyof` — его ключи, индексный доступ — типы значений (подробно — в [Составных типах](/content/typescript/composing-types)). Этот приём — основная альтернатива `enum`.

## enum

```ts
enum Status { Draft, Paid, Shipped }
enum Currency { Rub = 'RUB', Usd = 'USD' }
```

`enum` — единственная часть базовых типов, которая **порождает код**. Числовой `enum` превращается в объект с обратным отображением: в проверке `Object.keys(Status)` вернул `['0', '1', '2', 'Draft', 'Paid', 'Shipped']`, а `Status[1]` — `'Paid'`.

Особенности, о которых спрашивают:

- **числовой `enum` с TypeScript 5.0 строже:** число вне набора (`const s: Status = 42`) — ошибка. Раньше подходило любое число;
- **строковый `enum` номинален:** `const c: Currency = 'RUB'` — ошибка, нужно `Currency.Rub`. Значение из ответа сервера приходится приводить;
- **`enum` не стирается:** его не понимают инструменты, которые только удаляют типы, включая запуск `.ts` в Node.js (подробно — во [Введении](/content/typescript/introduction));
- **`const enum`** подставляет значения при компиляции, но ломается при раздельной компиляции файлов (`isolatedModules`), поэтому в библиотеках его избегают.

Альтернатива — объединение литералов или объект `as const`. Они стираются без следа, принимают строки из API напрямую и дают тот же автокомплит. `enum` оправдан, когда нужен именно объект в рантайме с обратным отображением — например, для старого кода или битовых флагов.

## Массивы, кортежи и объекты

### Массивы и кортежи

Массив — `number[]` или `Array<number>`. Неизменяемый — `readonly number[]`: у него нет `push`, `splice` и других мутирующих методов.

**Кортеж** — массив фиксированной длины с типом для каждой позиции:

```ts
type Line = [sku: string, qty: number];         // именованные элементы
type Range = [from: number, to?: number];       // необязательная позиция
type Path = [root: string, ...rest: string[]];  // хвост произвольной длины
```

Кортежи часто возвращают из функций: `useState` в React возвращает `[state, setState]`. У них есть дыра: метод `push` разрешён, и в проверке `const pair: [number, string] = [7, 'Чайник']; pair.push(8)` скомпилировалось и сделало длину 3. Закрывает её `readonly [number, string]`.

### Объекты

Объектные типы описывают через `interface` или `type`: обязательные и необязательные (`?`) свойства, `readonly`, методы. `readonly` — поверхностный и только для типа: вложенные объекты остаются изменяемыми, а в рантайме ничего не замораживается. Как выбирать между `interface` и `type`, индексные сигнатуры и составные типы — в [Составных типах](/content/typescript/composing-types).

Когда описываешь конкретный объект — конфигурацию, словарь, таблицу маршрутов, — встаёт вопрос: аннотировать его типом или оставить вывод? Здесь помогает `satisfies`.

---

## satisfies

Маршруты магазина:

```ts
type Route = { path: string; auth?: boolean };

const annotated: Record<string, Route> = {
  home: { path: '/' },
  cart: { path: '/cart', auth: true },
};

const checked = {
  home: { path: '/' },
  cart: { path: '/cart', auth: true },
} satisfies Record<string, Route>;
```

Обе записи проверяют, что каждый маршрут подходит под `Route`. Разница — в итоговом типе:

- **аннотация** заменяет выведенный тип на `Record<string, Route>`. Ключи становятся просто `string` (опечатку `routes.chekout` компилятор не поймает), а `annotated.cart.auth` — `boolean | undefined`, хотя мы его задали;
- **`satisfies`** проверяет значение по типу, но **оставляет выведенный тип**: ключи — ровно `home` и `cart`, а `checked.cart.auth` — `boolean`.

В проверке присваивание `annotated.cart.auth` переменной типа `boolean` дало ошибку, а `checked` с неверным полем `url` вместо `path` тоже не прошёл — `satisfies` проверяет форму.

Правило выбора:

- **`: T`** — когда значение должно иметь ровно тип `T` и детали не нужны (параметры, публичный API);
- **`satisfies T`** — когда нужна проверка и сохранение точного типа (конфигурации, словари, таблицы);
- **`as T`** — когда ты знаешь больше компилятора, и это ничего не проверяет.

`satisfies` хорошо сочетается с `as const`: `{ ... } as const satisfies Config` даёт и проверку, и литеральные типы.

## Красные флаги в ответе

- **«`any` и `unknown` — одно и то же».** `any` выключает проверку и заражает, `unknown` требует сужения перед использованием.
- **«`{}` — это пустой объект».** Это любое не-nullish значение, включая числа и строки. Объект — `object` или `Record<string, unknown>`.
- **«`enum` — просто набор констант».** Он порождает объект в рантайме, не стирается, а строковый `enum` не принимает строки из API.
- **«`as const` замораживает объект».** Только тип. Для заморозки в рантайме — `Object.freeze`.
- **«`satisfies` — то же, что аннотация».** Аннотация заменяет выведенный тип, `satisfies` его сохраняет.

## Как спрашивают на собеседовании

::question
В чём разница между any и unknown?

#answer
`any` отключает проверку типов: с значением можно делать что угодно. `unknown` принимает любое значение, но использовать его можно только после сужения — проверки типа. Для данных извне — `unknown`.

#more
`any` заражает: результат любой операции с ним тоже `any` и присваивается куда угодно, поэтому одно `any` выключает проверку целой цепочки. `unknown` — верхний тип системы: ему можно присвоить всё, а его — только `unknown` и `any`. С `strict` переменная в `catch` — `unknown`. Для поиска `any` в коде — правила `no-explicit-any` и `no-unsafe-*` в typescript-eslint.
::

::question
Когда используется never?

#answer
Для функций, которые никогда не возвращаются (всегда бросают ошибку), для проверки полноты в `switch` и как результат невозможных типов, например `string & number`.

#more
`never` — нижний тип: присваивается всему, ему — ничего. Объединение с `never` его поглощает (`A | never` — это `A`), поэтому `never` используют, чтобы выбрасывать варианты в условных и mapped-типах. Проверка полноты: в `default` присвоить значение переменной типа `never` — если добавят новый вариант, присваивание станет ошибкой.
::

::question
Enum или объединение литералов и as const?

#answer
Обычно объединение литералов или объект `as const`: они стираются при компиляции, принимают строки из API напрямую и дают тот же автокомплит. `enum` порождает объект в рантайме.

#more
Строковый `enum` номинален: строку `'RUB'` нельзя присвоить `Currency` без приведения. Числовой с TS 5.0 не принимает числа вне набора, но имеет обратное отображение. `enum` и `const enum` не дружат с раздельной компиляцией и запуском через стирание типов. `enum` оправдан для битовых флагов и старого кода.
::

::question
Что делает satisfies?

#answer
Проверяет, что значение подходит под тип, но сохраняет выведенный тип значения. Аннотация `: T` вместо этого заменяет тип на `T`.

#more
С аннотацией `Record<string, Route>` ключи становятся `string`, и опечатка в имени ключа не ловится, а необязательные поля остаются необязательными, даже если заданы. `satisfies` сохраняет точные ключи и литералы, при этом проверка формы остаётся. Хорошо сочетается с `as const`: `as const satisfies Config`.
::

::question
Чем кортеж отличается от массива?

#answer
У кортежа фиксированная длина и свой тип у каждой позиции: `[string, number]`. Массив — произвольная длина элементов одного типа.

#more
Кортежи бывают с именованными элементами, необязательными позициями и rest-хвостом. Изменяемый кортеж можно испортить через `push`: длина в типе не изменится. Поэтому из функций возвращают `readonly`-кортежи, а `as const` превращает литерал массива в `readonly`-кортеж.
::

::question
Что такое as const и когда расширяются литеральные типы?

#answer
`as const` делает все свойства `readonly`, а строки и числа — литеральными типами, на всю глубину. Без него `let` и свойства объекта расширяют литерал до общего типа: `{ status: 'paid' }` получает `status: string`.

#more
Расширение — защита: значение, которое может измениться, не привязывается к одному литералу. Отсюда ошибки «`string` is not assignable to union». `as const` позволяет хранить список значений в одном месте и выводить из него тип: `(typeof X)[keyof typeof X]`. Это только тип — объект в рантайме не замораживается.
::

## Практика

::practice{title="Почему не компилируется?"}
Функция принимает статус заказа. Почему вызов с объектом из конфигурации не компилируется, хотя значение правильное?

```ts
type OrderStatus = 'draft' | 'paid' | 'shipped';
function setStatus(status: OrderStatus) { /* ... */ }

const defaults = { status: 'paid', currency: 'RUB' };
setStatus(defaults.status);
// Argument of type 'string' is not assignable to parameter of type 'OrderStatus'
```

#solution
Свойство объекта может измениться, поэтому вывод типов расширил `'paid'` до `string`: тип `defaults` — `{ status: string; currency: string }`. А `string` шире, чем `OrderStatus`.

Три варианта, от лучшего:

```ts
// 1. проверить и сохранить точный тип
const defaults = { status: 'paid', currency: 'RUB' } satisfies { status: OrderStatus; currency: string };

// 2. зафиксировать литералы целиком
const defaults = { status: 'paid', currency: 'RUB' } as const;

// 3. аннотировать — работает, но тип станет ровно этим
const defaults: { status: OrderStatus; currency: string } = { status: 'paid', currency: 'RUB' };
```

`satisfies` заодно поймает опечатку в значении (`'piad'`), а `as const` — нет: он просто сохранит литерал. `as OrderStatus` в месте вызова тоже скомпилируется, но ничего не проверит.
::

::practice{title="Замени enum"}
Замени `enum` на конструкцию, которая стирается при компиляции, принимает строки из API без приведения и даёт тип-объединение:

```ts
enum PaymentMethod {
  Card = 'card',
  Sbp = 'sbp',
  Cash = 'cash',
}

function pay(method: PaymentMethod) { /* ... */ }
pay(response.method);   // ошибка: string не присваивается PaymentMethod
```

#solution
```ts
const PaymentMethod = {
  Card: 'card',
  Sbp: 'sbp',
  Cash: 'cash',
} as const;

type PaymentMethod = (typeof PaymentMethod)[keyof typeof PaymentMethod];
// 'card' | 'sbp' | 'cash'

function pay(method: PaymentMethod) { /* ... */ }

pay(PaymentMethod.Sbp);   // как раньше
pay('cash');              // литерал подходит напрямую

function isPaymentMethod(value: string): value is PaymentMethod {
  return Object.values(PaymentMethod).includes(value as PaymentMethod);
}
if (isPaymentMethod(response.method)) pay(response.method);
```

Значение и тип называются одинаково — TypeScript различает их по контексту, и импорт `PaymentMethod` даёт оба. Объект нужен только если значения перебирают в рантайме, иначе хватит объединения `type PaymentMethod = 'card' | 'sbp' | 'cash'`. Строку из API сначала проверяют — тип-предикат сужает её до объединения (подробно — в [Сужении типов](/content/typescript/type-narrowing)).
::
