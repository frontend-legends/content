# API браузера

API, которые браузер даёт помимо DOM: наблюдатели за видимостью, размером и изменениями DOM, потоки данных, общение между вкладками, приоритеты задач и разрешения. Спрашивают, чем `IntersectionObserver` лучше обработчика прокрутки, как синхронизировать вкладки и как обработать большой ответ по частям. Глубже — почему колбэк наблюдателя срабатывает сразу после `observe`, откуда в Sentry ошибка «ResizeObserver loop completed» и почему ответ `fetch` нельзя прочитать дважды.

::tldr
- **Наблюдатели заменяют опрос и обработчики прокрутки:** `IntersectionObserver` — видимость, `ResizeObserver` — размер, `MutationObserver` — изменения DOM. Все асинхронные, и первые два сразу сообщают текущее состояние.
- **`MutationObserver` копит изменения и вызывает колбэк одной микрозадачей,** а `ResizeObserver`, который сам меняет размер в колбэке, получает ошибку «loop completed with undelivered notifications».
- **Тело ответа `fetch` — поток:** его читают по частям, пока сервер ещё отвечает, пропускают через `TransformStream` и прочитать можно только один раз.
- **Вкладки одного origin общаются через `BroadcastChannel` и событие `storage`,** которое приходит в другие вкладки, но не в ту, что записала.
- **`scheduler.postTask` выполняет задачи по приоритету, `requestIdleCallback` — в простое,** а Permissions API показывает состояние разрешения, не спрашивая пользователя.
::

## Наблюдатели

Сквозной пример — каталог магазина чая: ленивые картинки и бесконечная лента товаров, график продаж в личном кабинете, который подстраивается под ширину, корзина, синхронная между вкладками, и выгрузка заказов, которая приходит строками.

Раньше видимость и размер узнавали опросом: обработчик прокрутки с `getBoundingClientRect()` на каждом событии, `setInterval` для проверки размеров. Это нагружает основной поток и вызывает принудительную раскладку (подробно — в [Рендеринге](/content/web/rendering)). Наблюдатели делают ту же работу внутри браузера и сообщают только об изменениях.

### IntersectionObserver

```js
const observer = new IntersectionObserver((entries) => {
  for (const entry of entries) {
    if (!entry.isIntersecting) continue;
    loadMore();
    observer.unobserve(entry.target);
  }
}, { rootMargin: '200px', threshold: 0 });

observer.observe(sentinel);
```

| Параметр | Что задаёт |
| --- | --- |
| `root` | область, с которой сравнивают: по умолчанию окно, или прокручиваемый контейнер |
| `rootMargin` | расширение области: `'200px'` — срабатывать за 200px до появления |
| `threshold` | при какой доле видимости вызывать: `0`, `0.5`, `[0, 0.5, 1]` |

Что важно знать, проверено в Chromium:

- **колбэк асинхронный** — во время `observe` он не вызвался ни разу;
- **первый вызов приходит сразу** для каждого элемента с текущим состоянием — даже невидимого, с `isIntersecting: false`. Код, который на первый вызов делает «элемент ушёл», срабатывает зря;
- **`rootMargin`** — картинка, лежащая сразу под нижним краем экрана, с `rootMargin: '200px'` сразу считалась видимой, без него — нет. Так загрузку начинают заранее;
- **`intersectionRatio`** — блок, наполовину вылезший за край, дал ровно 0,5.

Применения — ленивая загрузка (для картинок и фреймов её даёт `loading="lazy"`, подробно — в [Медиа](/content/html/media)), бесконечная лента, учёт показов рекламы, запуск анимаций при появлении.

### ResizeObserver

```js
new ResizeObserver((entries) => {
  for (const entry of entries) chart.resize(entry.contentRect.width);
}).observe(chartContainer);
```

`ResizeObserver` сообщает о смене размера конкретного элемента — не окна. В проверке первый вызов пришёл сразу после `observe` с текущим размером: содержимое 300px, а бокс с `padding` и рамкой — 324px (`borderBoxSize`). После изменения ширины — 500 и 524. Для оформления по размеру контейнера есть :term[container queries]{def="правила CSS, которые зависят от размера контейнера, а не окна"} в CSS (подробно — в [Адаптивном дизайне](/content/css/rwd)); `ResizeObserver` нужен для логики: перерисовать график, пересчитать виртуальный список.

Если колбэк меняет размер наблюдаемого элемента, браузер получает новое изменение в том же кадре. Чтобы не уйти в бесконечный цикл, он откладывает доставку и сообщает ошибку: в проверке `window` получил событие `error` с текстом «ResizeObserver loop completed with undelivered notifications». Это та самая ошибка, которая засоряет трекеры ошибок. Её устраняют — меняют размер в `requestAnimationFrame` или так, чтобы он сходился, — а в трекере отфильтровывают, если цикл безвреден.

### MutationObserver

```js
new MutationObserver((records) => {
  for (const r of records) console.log(r.type, r.target, r.oldValue);
}).observe(cart, { childList: true, attributes: true, attributeOldValue: true, subtree: true });
```

`MutationObserver` сообщает об изменениях DOM: добавлении и удалении узлов, атрибутах, тексте. Записи копятся и доставляются **одной микрозадачей** после текущего скрипта: в проверке два добавленных товара и смена `data-count` пришли одним вызовом с тремя записями — после строки «конец скрипта», но раньше таймера `setTimeout(…, 0)`. Со старым значением атрибута — `0`, раз включён `attributeOldValue`.

Применения — реагировать на DOM, который меняет чужой код: виджеты сторонних сервисов, расширения, разметка от :term[CMS]{def="система управления контентом: админка, где редакторы правят страницы без кода"}. В своём приложении изменения DOM обычно вызывает собственный код, и наблюдать за ними не нужно.

## Потоки

Ответ `fetch` не обязательно ждать целиком. `response.body` — это `ReadableStream`, и данные можно обрабатывать по мере прихода:

```js
const res = await fetch('/orders.ndjson');
const orders = res.body
  .pipeThrough(new TextDecoderStream())        // байты → текст
  .pipeThrough(splitLines())                     // текст → строки → объекты
;
for await (const order of orders) renderOrder(order);
```

`splitLines` — свой `TransformStream`, который копит текст и выдаёт целые строки. В проверке сервер отдавал три заказа с паузой 300 мс: первый заказ был разобран через несколько миллисекунд после запроса, второй — через 300, третий — через 600, когда сервер ещё не закончил отправку. Так работают потоковые ответы ИИ-ассистентов (подробно — в [ИИ во фронтенде](/content/additional-topics/ai-in-the-frontend)), выгрузки больших файлов и потоковый серверный рендеринг.

| Примитив | Что делает |
| --- | --- |
| `ReadableStream` | источник: тело ответа, файл, свой генератор данных |
| `WritableStream` | приёмник: файл, сокет, своя обработка |
| `TransformStream` | преобразование по пути: `TextDecoderStream`, `CompressionStream`, своя логика |
| `pipeThrough`, `pipeTo` | соединяют звенья; давление (backpressure) само притормаживает источник, если приёмник не успевает |

Тело ответа — поток, а поток читается **один раз**. В проверке второй `res.json()` бросил `TypeError`, а `res.bodyUsed` стал `true`. Если тело нужно дважды — например, залогировать и разобрать, — `res.clone()` делают **до** чтения.

## Общение между вкладками

Пользователь открыл магазин в двух вкладках и добавил товар в одной — счётчик корзины должен обновиться во второй. Для вкладок одного origin:

```js
const channel = new BroadcastChannel('cart');
channel.postMessage({ type: 'item-added' });
channel.onmessage = (e) => updateCartBadge(e.data);
```

- **`BroadcastChannel`** — сообщения всем вкладкам, фреймам и :term[воркерам]{def="скриптам в отдельных потоках браузера, которые общаются со страницей сообщениями"} того же origin, подписанным на канал. Отправителю его же сообщение не приходит: в проверке вторая вкладка получила `item-added`, а первая — нет;
- **событие `storage`** — приходит в **другие** вкладки при изменении `localStorage`, но не в ту, что записала. В проверке запись `cart-count` дала событие только во второй вкладке. Это частая ошибка: подписались на `storage` в той же вкладке и ждут событие;
- **`SharedWorker`** — один воркер на все вкладки, например одно WebSocket-соединение вместо десяти.

Для общения с фреймами и окнами других origin — `postMessage` с проверкой `event.origin` (подробно — в [CORS и same-origin](/content/security-perfomance/cors-and-same-origin)).

## Приоритеты задач

```js
scheduler.postTask(() => renderPrices(), { priority: 'user-blocking' });
scheduler.postTask(() => sendAnalytics(), { priority: 'background' });
requestIdleCallback((deadline) => prefetchNextPage(deadline), { timeout: 2000 });
```

- **`scheduler.postTask`** ставит задачу с приоритетом `user-blocking`, `user-visible` или `background` и возвращает промис. В проверке задачи, поставленные в порядке «фоновая, видимая, блокирующая», выполнились в обратном: блокирующая, видимая, фоновая. Задачу можно отменить через `TaskController`;
- **`requestIdleCallback`** вызывает колбэк в простое браузера и передаёт `deadline.timeRemaining()`. Если простоя нет долго, `timeout` гарантирует вызов;
- **`scheduler.yield()`** — уступить поток посреди долгой работы, чтобы браузер обработал ввод (подробно — в [Производительности выполнения](/content/security-perfomance/runtime-performance)).

Как задачи, микрозадачи и `requestAnimationFrame` встроены в цикл событий — в [Event Loop](/content/javascript/event-loop).

## Разрешения и другие API

Мощные возможности — геолокация, камера, микрофон, уведомления, буфер обмена — спрашивают пользователя и работают только в безопасном контексте (подробно — в [Что такое веб](/content/web/what-is-web)). Permissions API показывает состояние, **не спрашивая**:

```js
const status = await navigator.permissions.query({ name: 'geolocation' });
status.state;                 // 'prompt', 'granted' или 'denied'
status.onchange = () => updateDeliveryButton(status.state);
```

В проверке состояние было `prompt`, а после выдачи разрешения — `granted`. Так интерфейс решает, показать кнопку «определить адрес доставки» или подсказку, как включить доступ в настройках, — без внезапного системного окна.

Остальные API разобраны там, где они работают:

| API | Где |
| --- | --- |

## Красные флаги в ответе

- **«Видимость проверю на `scroll` через `getBoundingClientRect`».** Это нагрузка на каждый кадр прокрутки и принудительная раскладка; `IntersectionObserver` делает это внутри браузера.
- **«Колбэк `IntersectionObserver` вызывается, только когда элемент появился».** Первый вызов приходит сразу, с текущим состоянием.
- **«`MutationObserver` срабатывает на каждое изменение».** Изменения копятся и приходят пакетом одной микрозадачей.
- **«Ответ `fetch` можно прочитать сколько угодно раз».** Тело — поток; второй раз — `TypeError`, нужен `clone()` заранее.
- **«Подпишусь на `storage` и узнаю о своих изменениях».** Событие приходит только в другие вкладки.
- **«Ошибку ResizeObserver loop можно просто игнорировать».** Она означает, что колбэк меняет размер наблюдаемого элемента; цикл исправляют, а потом фильтруют безвредные.

## Как спрашивают на собеседовании

::question
Чем IntersectionObserver лучше обработчика прокрутки?

#answer
Обработчик прокрутки срабатывает десятки раз в секунду в основном потоке, а `getBoundingClientRect()` в нём может вызывать принудительную раскладку. `IntersectionObserver` считает пересечения внутри браузера и вызывает колбэк асинхронно, только когда видимость пересекает заданные пороги.

#more
`rootMargin` позволяет начинать загрузку заранее, `threshold` — реагировать на долю видимости, `root` — следить внутри прокручиваемого контейнера. Первый вызов приходит сразу после `observe` с текущим состоянием. Для ленивых картинок и фреймов достаточно `loading="lazy"`, наблюдатель нужен для ленты, учёта показов и своей логики.
::

::question
Зачем нужен ResizeObserver, если есть событие resize и container queries?

#answer
`resize` — только про окно, а `ResizeObserver` сообщает о размере конкретного элемента: панель сайдбара сжалась, контейнер графика изменился. Container queries меняют только стили, а `ResizeObserver` нужен для логики — перерисовать canvas, пересчитать виртуальный список.

#more
Первый вызов приходит сразу. Если колбэк меняет размер наблюдаемого элемента, браузер откладывает доставку и сообщает ошибку «ResizeObserver loop completed with undelivered notifications». Изменения в колбэке переносят в `requestAnimationFrame` или делают сходящимися.
::

::question
Как работает MutationObserver и когда он нужен?

#answer
Наблюдает за изменениями DOM — узлами, атрибутами, текстом — в выбранном поддереве. Записи копятся и доставляются пакетом одной микрозадачей после текущего скрипта, с типом изменения, целью и, по желанию, старым значением.

#more
Нужен, когда DOM меняет чужой код: сторонние виджеты, CMS, расширения. Свой код обычно знает, что меняет. Наблюдение за большим поддеревом со `subtree` и `characterData` дорогое, поэтому область сужают и вызывают `disconnect()`, когда наблюдение больше не нужно.
::

::question
Как обработать большой ответ сервера по частям?

#answer
Читать `response.body` как поток: `getReader()` или `for await`, текст — через `TextDecoderStream`, разбор строк или событий — своим `TransformStream`. Данные обрабатываются, пока сервер ещё отправляет остальное, и не держатся в памяти целиком.

#more
Так работают потоковые ответы ИИ-ассистентов, выгрузки на миллионы строк, Server-Sent Events вручную. `pipeThrough` и `pipeTo` учитывают давление: медленный приёмник притормаживает источник. Тело читается один раз; если нужно дважды — `response.clone()` до чтения.
::

::question
Как синхронизировать состояние между вкладками?

#answer
Для вкладок одного origin — `BroadcastChannel`: сообщение получают все подписанные вкладки, кроме отправителя. Или событие `storage`: оно приходит в другие вкладки при изменении `localStorage`. Для общего соединения на все вкладки — `SharedWorker`.

#more
Событие `storage` не приходит в ту вкладку, что записала, — обновление в ней делают сами. `localStorage` синхронный и строковый, поэтому большие данные передают через `BroadcastChannel` или IndexedDB. Для разных origin — `postMessage` с проверкой `event.origin`.
::

::question
Как выполнить работу с нужным приоритетом?

#answer
`scheduler.postTask` с приоритетом `user-blocking`, `user-visible` или `background`: задачи выполняются по приоритету, а не по порядку постановки, и их можно отменить. Некритичную работу в простое — `requestIdleCallback` с `timeout`, чтобы она не откладывалась вечно.

#more
Долгую работу дробят и уступают поток через `scheduler.yield()`, чтобы браузер успевал обрабатывать ввод. Визуальные изменения — в `requestAnimationFrame`. Фоновую аналитику — с приоритетом `background` или в простое, а при уходе со страницы — через `navigator.sendBeacon`.
::

::question
Как узнать, разрешил ли пользователь доступ к геолокации?

#answer
`navigator.permissions.query({ name: 'geolocation' })` возвращает состояние `prompt`, `granted` или `denied`, не показывая системное окно. Событие `change` сообщает, если пользователь изменил решение в настройках.

#more
По состоянию строят интерфейс: при `prompt` — кнопку с объяснением, зачем доступ, при `denied` — подсказку, как включить в настройках, при `granted` — сразу использовать. Запрос разрешения показывают в ответ на действие пользователя, а не при загрузке страницы. Мощные API доступны только в безопасном контексте.
::

## Практика

::practice{title="Лента грузит страницу дважды"}
Бесконечная лента товаров на `IntersectionObserver` при открытии сразу загружает вторую страницу, хотя пользователь ничего не прокручивал, а иногда — дважды:

```js
const io = new IntersectionObserver(() => loadNextPage());
io.observe(sentinel);
```

#solution
Первый вызов колбэка приходит сразу после `observe` с текущим состоянием — даже если датчик невидим. Колбэк не смотрит на `isIntersecting` и грузит страницу на каждый вызов, включая уход датчика с экрана. В проверке первый вызов пришёл для обоих элементов с `isIntersecting: false`. Проверяем состояние и защищаемся от параллельной загрузки:

```js
let loading = false;
const io = new IntersectionObserver(async ([entry]) => {
  if (!entry.isIntersecting || loading) return;
  loading = true;
  try { await loadNextPage(); } finally { loading = false; }
}, { rootMargin: '400px' });
io.observe(sentinel);
```

`rootMargin` начинает загрузку заранее, чтобы пользователь не упирался в конец ленты.
::

::practice{title="Тысячи ошибок ResizeObserver в Sentry"}
После добавления адаптивного блока с отзывами Sentry завален ошибкой «ResizeObserver loop completed with undelivered notifications»:

```js
new ResizeObserver(([entry]) => {
  const columns = entry.contentRect.width > 600 ? 2 : 1;
  reviews.style.height = `${Math.ceil(count / columns) * 120}px`;   // меняет размер наблюдаемого элемента
}).observe(reviews);
```

#solution
Колбэк меняет размер того же элемента, за которым наблюдает. Браузер получает новое изменение в том же кадре и, чтобы не уйти в бесконечный цикл, откладывает доставку и сообщает ошибку событием `error` на `window` — в проверке она пришла ровно с этим текстом. Варианты:

```js
// 1. наблюдать за родителем, а менять ребёнка
new ResizeObserver(([entry]) => {
  const columns = entry.contentRect.width > 600 ? 2 : 1;
  reviews.style.height = `${Math.ceil(count / columns) * 120}px`;
}).observe(reviewsContainer);

// 2. или отложить изменение на следующий кадр
new ResizeObserver(([entry]) => {
  requestAnimationFrame(() => applyLayout(entry.contentRect.width));
}).observe(reviews);
```

А раскладку в колонки лучше отдать CSS: Grid или container queries сделают это без JavaScript.
::

::practice{title="Ответ не читается второй раз"}
После добавления логирования запросов перестали работать все экраны: `TypeError: Failed to execute 'json' on 'Response': body stream already read`.

```js
async function api(url) {
  const res = await fetch(url);
  log(url, await res.json());   // логирование
  return res;                   // дальше код вызывает res.json()
}
```

#solution
Тело ответа — поток, и его можно прочитать один раз: логирование прочитало его, и второй `res.json()` падает. В проверке второе чтение бросило ровно эту ошибку, а `res.bodyUsed` стал `true`. Копию делают до чтения:

```js
async function api(url) {
  const res = await fetch(url);
  res.clone().json().then((data) => log(url, data)).catch(() => {});
  return res;
}
```

Или читают один раз и возвращают уже разобранные данные. `clone()` удваивает буферизацию, поэтому для больших ответов его избегают.
