# SEO для фронтенд-разработчика

SEO — то, как страницы попадают в поиск и как выглядят в выдаче и превью ссылок. От фронтенда зависит техническая часть: что получает робот, может ли он перейти по ссылкам, какой адрес считать основным и что сообщает код ответа. Спрашивают, почему одностраничное приложение плохо индексируется, зачем `canonical`, `sitemap.xml` и структурированные данные. Глубже — что такое мягкая 404, почему `noindex` не работает вместе с запретом в `robots.txt` и почему товар с «неудачным» названием ломает разметку для поиска.

::tldr
- **Google обрабатывает страницу в три этапа: сканирование, рендеринг, индексация.** Страница с кодом 200 ждёт рендеринга в очереди; боты превью и часть роботов видят только HTML ответа, поэтому важное отдают с сервера.
- **Робот не кликает и не прокручивает.** Ссылки — только `a` с `href`, контент не должен ждать действий пользователя, у каждого экрана — свой адрес через History API, а не фрагмент.
- **Код ответа — сигнал:** несуществующая страница с кодом 200 — мягкая 404. В одностраничном приложении её исправляют переходом на адрес с настоящим 404 или `noindex`.
- **Дубли сводят к одному адресу:** постоянный редирект или `link rel="canonical"` с абсолютным адресом. `robots.txt` управляет сканированием, а не индексацией: страница с запретом в нём не увидит свой `noindex`.
- **Структурированные данные — JSON-LD:** данные, а не скрипт, описывают только видимое на странице и экранируются при вставке. Sitemap — абсолютные адреса, экранирование XML и честный `lastmod`.
::

## Что видит робот

Сквозной пример — магазин чая: каталог с фильтрами и страницами, карточки товаров, версии на русском, английском и казахском.

Google обрабатывает страницы в три этапа:

1. **Сканирование** — робот скачивает HTML по адресу, находит в нём ссылки и ставит их в очередь;
2. **Рендеринг** — все страницы с кодом 200 попадают в очередь рендеринга; Chromium выполняет JavaScript и строит итоговый DOM. В очереди страница может пробыть несколько секунд, а может и дольше;
3. **Индексация** — текст, метаданные и ссылки итогового DOM попадают в индекс.

Робот Google выполняет JavaScript в актуальной версии Chromium, но на это нельзя полагаться целиком: рендеринг откладывается, ресурсы, запрещённые в `robots.txt`, не загружаются, а боты превью ссылок в мессенджерах и соцсетях и другие поисковики не обязаны выполнять скрипты вообще. Надёжно все видят только **HTML ответа сервера**.

В проверке страница товара с клиентским рендерингом отдавала оболочку: `div id="app"`, скрипт и общий заголовок «Магазин чая». В сыром HTML не было ни `h1`, ни `og:title`, ни `canonical`. В Chromium с выключенным JavaScript страница была пустой, с включённым — появились заголовок товара, `h1` и `canonical`. Та же страница с серверным рендерингом отдала всё сразу, и без JavaScript выглядела так же, как с ним.

Отсюда главный выбор: страницы, которые должны быть в поиске, — каталог, товары, статьи — рендерят на сервере или заранее при сборке. Личный кабинет и корзину можно рендерить на клиенте: их и так не индексируют. Как устроены :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"}, :term[SSG]{def="статическая генерация: HTML страниц собирается заранее, при сборке"} и гидратация — в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration) и [Рендеринге и Nuxt](/content/vuejs/rendering-and-nuxt); где лежат метатеги и почему `canonical` из `body` может не учитываться — в [Содержимом head](/content/html/head-content).

## Ссылки и адреса

Робот находит страницы по ссылкам и не взаимодействует со страницей: не кликает по кнопкам, не печатает и не прокручивает.

- **Ссылка — это `a` с `href`.** `span` с обработчиком клика, `button` с `router.push`, `a` без `href` или с `href="javascript:…"` робот надёжно не распознает. Компоненты ссылок роутеров рендерят обычный `a href` — ими и пользуются;
- **у каждого экрана свой адрес через History API.** Фрагмент после `#` на сервер не уходит (подробно — в [Что такое веб](/content/web/what-is-web)), и Google фрагменты игнорирует: `/#/tea/oolong` и `/#/tea/puer` для него — одна страница;
- **контент не ждёт действий.** Кнопка «Показать ещё» без ссылок — товары после первой порции робот не найдёт. Ленивую загрузку делают по появлению в области видимости — `loading="lazy"` или `IntersectionObserver` (подробно — в [API браузера](/content/web/browser-apis)), а не по событию прокрутки;
- **пагинация — отдельные адреса.** `?page=2`, `?page=3` со ссылками `a href` на следующую страницу; бесконечная лента при прокрутке меняет адрес через History API. Каждая страница пагинации — со своим `canonical`, а не с первой страницей. `rel="next"` и `rel="prev"` Google больше не использует.

## Код ответа и мягкая 404

Код ответа — первый сигнал роботу: 200 — страница есть, 404 и 410 — нет (Google обрабатывает их одинаково), 301 и 308 — переехала навсегда, 302 и 307 — временно, 5xx — ошибка сервера: робот замедляет сканирование, а страницы, которые продолжают отвечать ошибкой, со временем выпадают из индекса.

Одностраничное приложение обычно настроено так, что сервер на любой адрес отдаёт `index.html` с кодом 200, а «не найдено» показывает уже клиентский роутер. Для робота это страница с текстом «Товар не найден» и кодом 200 — **мягкая 404** (soft 404). Такие страницы попадают в отчёт Search Console как «Soft 404». В проверке адрес несуществующего товара ответил 200, а на странице было «Товар не найден».

Исправления, которые рекомендует Google:

- **переход на адрес с настоящим 404** — `location.replace('/not-found')`, а сервер на `/not-found` отвечает кодом 404. В проверке после перехода ответ был 404;
- **`noindex` на странице ошибки**, добавленный скриптом: `meta name="robots" content="noindex"`;
- **лучше всего — правильный код с сервера**: при серверном рендеринге сервер знает, что товара нет, и сразу отвечает 404.

Обратное правило: если страницу нужно индексировать, `noindex` не должно быть в исходном HTML. Встретив его, Google может не рендерить страницу вовсе, и убрать `noindex` скриптом не получится.

## Дубли и основной адрес

Один товар доступен по многим адресам: со слешем в конце и без, с метками рассылок `utm_*`, с сортировкой, с `www` и без. Поисковик выбирает основной адрес сам, если ему не подсказать, и сигналы делятся между дублями. Сигналы по силе:

| Способ | Сила |
| --- | --- |
| постоянный редирект 301 или 308 | сильный: основной — адрес назначения |
| `link rel="canonical"` в `head` или в заголовке `Link` | сильный |
| адрес в sitemap | слабый |

`canonical` — абсолютный адрес, один и тот же во всех источниках, в HTML ответа, и скрипт его не меняет. Канонический адрес строят из текущего: убирают метки и фрагмент, оставляют только параметры, которые меняют содержимое, в одном порядке:

```js
const CONTENT_PARAMS = new Set(['page', 'type']);

function canonical(input) {
  const url = new URL(input);
  url.hash = '';
  const kept = [...url.searchParams]
    .filter(([key]) => CONTENT_PARAMS.has(key))
    .sort(([a], [b]) => a.localeCompare(b));
  url.search = new URLSearchParams(kept).toString();
  if (url.pathname.length > 1 && url.pathname.endsWith('/')) url.pathname = url.pathname.slice(0, -1);
  return url.href;
}
```

В проверке `https://Shop.Example:443/tea/oolong/?utm_source=tg&sort=price#reviews` превратился в `https://shop.example/tea/oolong`: регистр хоста и порт по умолчанию нормализовал сам `URL`, а метки, сортировку, фрагмент и слеш убрала функция. Путь функция не приводит к нижнему регистру: он чувствителен к регистру, и `/Tea/Oolong` — другой адрес.

### robots.txt и noindex

| Инструмент | Что делает |
| --- | --- |
| `robots.txt` | запрещает **сканирование** адресов |
| `meta name="robots" content="noindex"` | запрещает **индексацию** страницы |
| заголовок `X-Robots-Tag: noindex` | то же для любых файлов, включая PDF и картинки |

Частая ошибка — закрыть страницу и в `robots.txt`, и `noindex`. Запрет в `robots.txt` не даёт роботу скачать страницу, он не увидит `noindex`, и адрес может остаться в выдаче, если на него ссылаются. Чтобы убрать страницу из поиска, её оставляют доступной для сканирования с `noindex`. Для выбора основного адреса не используют ни `robots.txt`, ни `noindex` — для этого есть `canonical`.

## Структурированные данные

Структурированные данные описывают сущность страницы для поисковика: товар с ценой и наличием, статью, хлебные крошки, вопросы и ответы. Google рекомендует формат :term[JSON-LD]{def="формат структурированных данных: JSON со ссылками на словарь, вставленный в страницу"} по словарю schema.org:

```html
<script type="application/ld+json">
{ "@context": "https://schema.org", "@type": "Product", "name": "Улун молочный",
  "offers": { "@type": "Offer", "price": "890", "priceCurrency": "RUB", "availability": "https://schema.org/InStock" } }
</script>
```

- **это данные, а не скрипт** — браузер блок не выполняет: в проверке JSON-LD не вызвал ошибок, а `JSON.parse(block.textContent)` вернул объект;
- **описывают только видимое** — цена и отзывы в разметке должны быть на странице; разметка не гарантирует расширенный сниппет, она лишь делает страницу допустимой для него;
- **можно вставлять скриптом** — Google читает и JSON-LD, добавленный JavaScript, но надёжнее отдавать его в HTML;
- **проверяют** в Rich Results Test и отчётах Search Console.

JSON-LD собирают из данных :term[CMS]{def="система управления контентом: админка, где редакторы правят страницы без кода"} через `JSON.stringify` — и тут ловушка. `JSON.stringify` не экранирует `<`, а HTML-парсер заканчивает `script` на первом `</script>` внутри, не глядя на JSON. В проверке товар с названием «Улун `</script>` молочный» оборвал блок: `JSON.parse` бросил `SyntaxError`, а хвост `молочный"}` появился на странице текстом. Исправление — заменить `<` на `\u003c`: для JSON это тот же символ, а для HTML-парсера тега больше нет. В проверке после замены название разобралось целиком, а лишнего текста на странице не осталось. Это же экранирование закрывает и XSS через данные в `script` (подробно — в [XSS](/content/security-perfomance/xss)).

### Превью ссылок

Заголовок, описание и картинку для превью в мессенджерах и соцсетях берут из метатегов Open Graph (`og:title`, `og:description`, `og:image`), что это за теги — в [Содержимом head](/content/html/head-content). Для превью, как и для поиска, надёжно работает только то, что пришло в HTML: в проверке у клиентской страницы `og:title` в ответе сервера не было. `og:image` — абсолютный адрес картинки.

## Sitemap и языковые версии

`sitemap.xml` перечисляет адреса, которые нужно сканировать:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <url>
    <loc>https://shop.example/catalog?page=2&amp;type=oolong</loc>
    <lastmod>2026-11-10</lastmod>
  </url>
</urlset>
```

- **абсолютные адреса** — относительные не работают;
- **не больше 50 000 адресов и 50 МБ** без сжатия на файл; больше — несколько файлов и индексный sitemap;
- **`lastmod` — только честный:** Google учитывает его, если он стабильно совпадает с реальными изменениями содержимого. `priority` и `changefreq` Google игнорирует;
- **UTF-8 и экранирование XML:** `&` в адресе — `&amp;`. В проверке адрес с неэкранированным `&` сделал весь файл невалидным XML, а с экранированием — разобрался, и `loc` вернул исходный адрес.

Адрес sitemap указывают в `robots.txt` строкой `Sitemap:` и в Search Console.

### hreflang

Языковые версии страницы связывают ссылками `link rel="alternate" hreflang="…"` в `head`, заголовком `Link` или в sitemap. Где хранить язык в адресе — в [Интернационализации](/content/ecosystem-libs/i18n). Правила:

- **каждая версия перечисляет себя и все остальные**;
- **связи взаимны** — если две страницы не ссылаются друг на друга, ссылки игнорируются;
- **`x-default`** — версия для тех, чей язык не подошёл ни к одной;
- **коды** — язык по ISO 639-1 и, по желанию, регион по ISO 3166-1: `ru`, `en-GB`, `kk`. Регион без языка не работает.

## Скорость и удобство

Core Web Vitals входят в сигналы ранжирования, но релевантность содержимого важнее: быстрая, но бесполезная страница не поднимется. Что измеряют метрики — в [Core Web Vitals](/content/security-perfomance/core-web-vitals), как браузер их считает — в [Измерении Core Web Vitals](/content/web/core-web-vitals). На поиск работают и вещи, которые разобраны в главе про HTML: `title` и `meta description`, уникальные для каждой страницы, один `h1` и логичные заголовки, `alt` у картинок, `meta viewport` для мобильных.

Проверяют техническое SEO в Search Console: инструмент проверки URL показывает HTML после рендеринга, отчёты — мягкие 404, дубли без канонического адреса и ошибки структурированных данных. Lighthouse даёт быстрый аудит метатегов, ссылок и `robots.txt` в лаборатории.

## Красные флаги в ответе

- **«Google выполняет JavaScript, значит SSR для SEO не нужен».** Рендеринг откладывается, боты превью и часть роботов скрипты не выполняют; надёжно видно только HTML ответа.
- **«Навигация через `onClick` с `router.push` — нормально».** Робот находит страницы только по `a` с `href`.
- **«Закрою страницу в `robots.txt`, и она уйдёт из поиска».** `robots.txt` запрещает сканирование: робот не увидит `noindex`, и адрес может остаться в выдаче.
- **«SPA отдаёт 200 на всё — не страшно».** Это мягкие 404: несуществующие страницы выглядят для робота существующими.
- **«Все страницы пагинации — с `canonical` на первую».** У каждой страницы свой `canonical`; иначе Google посчитает остальные страницы дублями первой, и товары с них могут не попасть в индекс.
- **«`rel="next"` и `rel="prev"` помогут Google понять пагинацию».** Google их больше не использует; нужны отдельные адреса и обычные ссылки.

## Как спрашивают на собеседовании

::question
Почему одностраничное приложение плохо индексируется и что с этим делать?

#answer
Сервер отдаёт пустую оболочку, а содержимое, заголовок, `canonical` и метатеги появляются после выполнения JavaScript. Google рендерит страницы, но откладывает это в очередь, а боты превью и часть роботов скрипты не выполняют. Решение — серверный рендеринг или генерация при сборке для страниц, которые должны быть в поиске.

#more
Ещё ломают индексацию навигация без `a href`, адреса на фрагментах `#/`, загрузка контента по кнопке или прокрутке и мягкие 404 от сервера, который отдаёт `index.html` с кодом 200 на любой адрес. Проверяют инструментом проверки URL в Search Console: он показывает HTML после рендеринга.
::

::question
Какие ссылки видит поисковый робот?

#answer
Только `a` с атрибутом `href`, в том числе добавленные JavaScript. `span` или `button` с обработчиком клика, `a` без `href` или с `javascript:` робот надёжно не распознает. Робот не кликает, не печатает и не прокручивает.

#more
Компоненты ссылок роутеров рендерят обычный `a href`, поэтому ими и пользуются вместо `navigate` в обработчике. Фрагменты после `#` Google игнорирует, поэтому каждому экрану нужен свой адрес через History API. Текст ссылки должен описывать цель; для ссылки-картинки текстом служит `alt`.
::

::question
Что такое мягкая 404 и как её исправить в SPA?

#answer
Несуществующая страница, которая отвечает кодом 200 и показывает «не найдено». В SPA так бывает, когда сервер отдаёт `index.html` на любой адрес. Исправления: скрипт переходит на адрес, для которого сервер отвечает 404, или добавляет на страницу ошибки `meta name="robots" content="noindex"`.

#more
Лучше всего, когда правильный код отдаёт сервер: при SSR он знает, что товара нет. Переехавшие страницы — постоянный редирект 301 или 308, а не 200 с текстом «страница переехала». Ответ 5xx замедляет сканирование; уже проиндексированные страницы сохраняются, но выпадают, если ошибка не проходит.
::

::question
Зачем нужен canonical и чем он отличается от редиректа?

#answer
`canonical` сообщает, какой адрес основной, когда одно содержимое доступно по нескольким: с метками `utm`, сортировкой, слешем. Редирект переводит и пользователя, и робота на основной адрес и сильнее как сигнал. Без них поисковик выбирает основной адрес сам и делит сигналы между дублями.

#more
`canonical` — абсолютный адрес, в HTML ответа, один и тот же в разметке, заголовке `Link` и sitemap; скрипт его не меняет. Для выбора основного адреса не используют `robots.txt` и `noindex`. Страницы пагинации каноничны сами себе, а не первой странице.
::

::question
Чем robots.txt отличается от noindex?

#answer
`robots.txt` запрещает сканирование адресов, `noindex` — индексацию страницы. Если закрыть страницу в `robots.txt`, робот её не скачает и не увидит `noindex`, а адрес может остаться в выдаче по внешним ссылкам. Чтобы убрать страницу из поиска, её оставляют доступной и ставят `noindex`.

#more
Для файлов, где нет HTML, — PDF, картинки — `noindex` передают заголовком `X-Robots-Tag`. `noindex` в `robots.txt` Google не поддерживает. Если страницу нужно индексировать, `noindex` не должно быть в исходном HTML: увидев его, Google может не выполнять JavaScript вовсе.
::

::question
Что такое структурированные данные и как их добавить?

#answer
Описание сущности страницы для поисковика по словарю schema.org: товар с ценой и наличием, статья, хлебные крошки. Рекомендуемый формат — JSON-LD в `script type="application/ld+json"`. Разметка делает страницу допустимой для расширенного сниппета, но не гарантирует его.

#more
Разметка описывает только то, что видно на странице. Google читает и JSON-LD, вставленный скриптом. При сборке из данных `JSON.stringify` не экранирует `<`, и `</script>` в названии обрывает блок — заменяют `<` на `\u003c`. Проверяют в Rich Results Test.
::

::question
Как сделать sitemap правильно?

#answer
XML в UTF-8 с абсолютными адресами, не больше 50 000 адресов и 50 МБ на файл, иначе — несколько файлов и индексный sitemap. Значения экранируются как в XML: `&` — `&amp;`. Адрес sitemap указывают в `robots.txt` и Search Console.

#more
Google учитывает `lastmod`, только если он честно отражает изменения содержимого, а `priority` и `changefreq` игнорирует. В sitemap — только канонические адреса, которые отвечают 200. Для языковых версий в sitemap можно перечислить `hreflang`-связи.
::

## Практика

::practice{title="Каталог проиндексирован не целиком"}
В поиске есть только первые 24 товара каталога. Остальные подгружаются так:

```jsx
<ProductGrid items={items} />
<button onClick={() => loadMore()}>Показать ещё</button>
```

#solution
Робот не кликает: товары после первой порции он не увидит, а ссылок на следующие порции нет. Нужны отдельные адреса для каждой порции и обычная ссылка, которую кнопка улучшает для пользователя:

```jsx
<ProductGrid items={items} />
<a
  href={`/catalog?page=${page + 1}`}
  onClick={(e) => {
    e.preventDefault();
    loadMore();
    history.pushState(null, '', `/catalog?page=${page + 1}`);
  }}
>
  Показать ещё
</a>
```

Страница `/catalog?page=2` должна отдавать вторую порцию с сервера и иметь `canonical` на себя, а не на первую страницу. Это рекомендация Google для пагинации и бесконечной ленты: у каждой порции постоянный адрес, ссылки между порциями — `a href`, при прокрутке адрес обновляется через History API.
::

::practice{title="Несуществующие товары в поиске"}
Search Console показывает сотни мягких 404, хотя все удалённые товары показывают «Товар не найден». Сервер — `nginx` с `try_files $uri /index.html`, роутинг клиентский. Что исправить?

#solution
Сервер отдаёт `index.html` с кодом 200 на любой адрес, и для робота «Товар не найден» — обычная страница. В проверке так и было: адрес несуществующего товара ответил 200. Варианты:

```js
// на клиенте, когда API ответил 404
if (!product) {
  location.replace('/not-found');   // а сервер на /not-found отвечает 404
}
```

```js
// или пометить страницу ошибки
const meta = document.createElement('meta');
meta.name = 'robots';
meta.content = 'noindex';
document.head.append(meta);
```

В проверке после перехода на `/not-found` ответ был 404. Надёжнее всего — серверный рендеринг страниц товаров: сервер узнаёт об отсутствии товара до ответа и сразу отдаёт 404.
::

::practice{title="Разметка товара пропала из Rich Results"}
После загрузки нового каталога у части товаров пропали звёзды и цена в выдаче, а внизу их страниц появился непонятный текст. JSON-LD собирается так:

```js
const jsonLd = `<script type="application/ld+json">${JSON.stringify(productSchema)}</script>`;
```

#solution
В названиях или описаниях товаров из CMS есть `</script>`. `JSON.stringify` не экранирует `<`, а HTML-парсер закрывает `script` на первом `</script>`: блок обрывается, JSON становится невалидным, а хвост выводится на страницу текстом. В проверке так и вышло — `SyntaxError` и `молочный"}` на странице. Экранируем `<`:

```js
const json = JSON.stringify(productSchema).replace(/</g, '\\u003c');
const jsonLd = `<script type="application/ld+json">${json}</script>`;
```

`\u003c` — тот же символ `<` для JSON, поэтому данные не меняются: в проверке название разобралось целиком. Ту же замену рекомендует документация Next.js по JSON-LD — фреймворк сам её не делает, когда строка вставляется через `dangerouslySetInnerHTML`.
::
