# Рендеринг в браузере

Как браузер превращает DOM и CSS в пиксели: стили, раскладка, отрисовка и композиция, что запускает каждый этап и что такое слои. Спрашивают, из каких этапов состоит рендеринг, чем раскладка отличается от перерисовки и почему `transform` дешевле `top`. Глубже — какие чтения из JavaScript заставляют браузер считать раскладку немедленно, почему `getComputedStyle(el).color` её не вызывает, а `.width` — вызывает, и почему `will-change` на всём подряд вредит.

::tldr
- **Кадр проходит этапы: стили → раскладка → отрисовка → композиция.** Изменение запускает конвейер с того этапа, который затронуло, и всё после него.
- **Геометрия — `width`, `top`, `margin`, `font-size` — запускает раскладку и всё дальше.** Цвет и тени — только отрисовку. `transform` и `opacity` на своём слое — только композицию.
- **Браузер копит изменения до кадра, но чтение геометрии после записи заставляет посчитать раскладку сразу.** Это принудительная синхронная раскладка; в цикле она превращается в layout thrashing.
- **Не всякое чтение дорого:** `getComputedStyle(el).color` требует только стилей, а `offsetWidth`, `getBoundingClientRect()` и `getComputedStyle(el).width` — раскладки.
- **Слой — отдельная картинка, которую композитор двигает без перерисовки.** Его дают `will-change`, видео, `canvas`, анимации `transform` и `opacity`, но каждый слой стоит видеопамяти.
::

## Конвейер кадра

Сквозной пример — каталог магазина чая: сетка карточек, выезжающая панель корзины, бейджи «−20%» и список из пятидесяти товаров, у которых скрипт подгоняет ширину.

Когда HTML разобран в DOM, а CSS — в CSSOM (подробно — в [Структуре документа](/content/html/structure)), браузер рисует кадр в несколько этапов:

| Этап | Что делает | Результат |
| --- | --- | --- |
| стили (Recalculate Style) | сопоставляет селекторы с элементами и считает вычисленные значения каждого свойства | вычисленные стили |
| раскладка (Layout) | считает размер и положение каждого бокса | дерево раскладки с геометрией |
| отрисовка (Paint) | превращает боксы в списки команд рисования: фон, рамка, текст, тень — в порядке наложения | списки отрисовки по слоям |
| растеризация | выполняет команды и получает пиксели плиток слоёв | растровые плитки |
| композиция (Composite) | собирает слои в кадр с учётом `transform`, `opacity`, прокрутки | кадр на экране |

В дерево раскладки попадает не весь DOM: элементы `head`, `script` и всё с `display: none` боксов не получают, а псевдоэлементы `::before` и `::after` — получают. Поэтому у скрытого через `display: none` элемента нет размеров, а у `visibility: hidden` есть (подробно о способах скрыть — в [Раскладке и потоке](/content/css/flow)).

Где кадр стоит в цикле событий — после задачи и микрозадач, вместе с `requestAnimationFrame`, — разобрано в [Event Loop](/content/javascript/event-loop). Отрисовку браузер делает не чаще частоты экрана, обычно 60 раз в секунду, — на всё про всё около 16 мс.

## Что запускает каждый этап

Изменение начинает конвейер с первого затронутого этапа:

| Что меняется | Стили | Раскладка | Отрисовка | Композиция |
| --- | --- | --- | --- | --- |
| `width`, `height`, `margin`, `padding`, `top`, `left`, `font-size`, `display`, текст, добавление элементов | да | да | да | да |
| `color`, `background`, `box-shadow`, `border-color`, `visibility` | да | — | да | да |
| `transform`, `opacity` у элемента со своим слоем | да | — | — | да |

В проверке это видно по счётчикам Chromium. Десять кадров анимации `left` у карточки дали не меньше десяти раскладок, а та же анимация через `transform` — ни одной. Смена цвета фона вызвала перерисовку слоя, а сдвиг `transform` у элемента со своим слоем — ни одной перерисовки. Поэтому движение анимируют `transform`, а исчезновение — `opacity` (подробно — в [Производительности выполнения](/content/security-perfomance/runtime-performance)).

Тонкость: первый переход `transform` из `none` в значение один раз меняет раскладку — элемент становится контекстом наложения и containing block для своих потомков. В проверке это дало ровно одну раскладку, а дальнейшие кадры — ни одной. Если анимация начинается часто, начальное `transform: translateX(0)` задают заранее.

### Раскладка и перерисовка

Старые названия — **reflow** для раскладки и **repaint** для перерисовки. Раскладка дороже: изменение размера одного элемента может сдвинуть соседей, родителя и всё ниже по странице. Перерисовка обходится без пересчёта геометрии, но на большой площади — например, тень на весь экран — тоже заметна. Раскладка всегда тянет за собой перерисовку, обратное неверно.

## Браузер копит изменения

Браузер не пересчитывает раскладку на каждое присваивание — он помечает стили и раскладку как «грязные» и считает их один раз перед кадром:

```js
card.style.width = '110px';
card.style.color = 'blue';
// здесь браузер ещё ничего не пересчитал
```

В проверке такие записи в одном скрипте не вызвали ни пересчёта стилей, ни раскладки — всё отложилось до кадра.

### Принудительная синхронная раскладка

Но если после записи **прочитать** геометрию, браузер обязан ответить точно — и считает раскладку прямо сейчас:

```js
card.style.width = '120px';
card.offsetWidth;   // раскладка прямо здесь, внутри скрипта
```

Счётчик раскладок вырос на 1, и `offsetWidth` вернул 120. Раскладку принудительно вызывают чтения геометрии:

- `offsetWidth`, `offsetHeight`, `offsetTop`, `offsetLeft`, `offsetParent`;
- `clientWidth`, `clientHeight`, `scrollWidth`, `scrollHeight`, `scrollTop`;
- `getBoundingClientRect()`, `getClientRects()`;
- `getComputedStyle(el)` для свойств, зависящих от раскладки: `width`, `height`, `top` и подобных;
- `innerWidth`, `innerHeight`, `scrollIntoView()`, `focus()`.

Не всякое чтение дорого. `getComputedStyle(card).color` после изменения ширины и цвета в проверке вызвал только пересчёт стилей, без раскладки: цвету геометрия не нужна. А `getComputedStyle(card).width` — уже раскладку. Повторное чтение без новых изменений ничего не пересчитывает.

### Layout thrashing

Самая частая ошибка — чередовать запись и чтение в цикле:

```js
for (const el of items) {
  el.style.width = el.offsetWidth + 1 + 'px';   // чтение после предыдущей записи
}
```

На списке из пятидесяти товаров в проверке это дало 49 раскладок прямо в цикле: первое чтение пришлось на чистую раскладку, а каждое следующее — после записи. Если сначала прочитать всё, потом записать всё, — одна раскладка на все чтения. Сколько это стоит по времени — в [Производительности выполнения](/content/security-perfomance/runtime-performance), где тот же приём ускорил цикл в сотни раз. Во фреймворках чтения выносят в `useLayoutEffect` или `onMounted`, а частые измерения — в `ResizeObserver`.

## Слои и композиция

Страница рисуется не одной картинкой, а **слоями**: каждый слой растеризуется отдельно, а композитор складывает их в кадр. Если слой сдвинулся или стал прозрачнее, его не нужно перерисовывать — композитор просто рисует ту же картинку в другом месте. Поэтому анимация `transform` и `opacity` может работать в потоке композитора, без основного потока (подробно о потоках — в [Архитектуре браузера](/content/web/browser-engines)).

Свой слой получают:

- элементы с `will-change: transform` или `will-change: opacity`;
- элементы с идущей анимацией `transform` или `opacity`;
- `video`, `canvas` с аппаратным ускорением, `iframe`;
- элементы с `position: fixed` и прокручиваемые области — чтобы прокрутка не требовала перерисовки;
- элементы, которые накладываются поверх других слоёв.

В проверке через дерево слоёв протокола DevTools карточка с `will-change: transform` получила свой слой, а соседняя карточка без него рисовалась в слое страницы.

### Цена слоя

Каждый слой — растровая картинка в видеопамяти: карточка 300×200 на экране с плотностью 3 — это 900×600 пикселей по 4 байта, больше двух мегабайт. `will-change` на всех элементах «для скорости» создаёт сотни слоёв, расходует память и замедляет композицию — особенно на телефонах. `will-change` ставят точечно, на то, что будет анимироваться, и снимают после. Как это сказывается на анимациях — в [Анимациях и переходах](/content/css/animations).

---

## Как это смотреть

- **Performance** в DevTools — запись кадров: блоки Recalculate Style, Layout, Paint, Composite Layers на основном потоке. Предупреждение «Forced reflow» указывает на строку, которая вызвала принудительную раскладку;
- **Rendering** — Paint flashing подсвечивает перерисовываемые области, Layout Shift Regions — сдвиги, Layer borders — границы слоёв;
- **Layers** — список слоёв, причина создания каждого и его память.

Подробно о панелях — в [DevTools](/content/web/devtools).

### Virtual DOM

Фреймворки с виртуальным DOM сравнивают описания интерфейса и применяют к настоящему DOM только изменения — но дальше работает тот же конвейер: стили, раскладка, отрисовка. Virtual DOM не делает рендеринг браузера быстрее; он избавляет от ручных обновлений и пакетирует их, а неудачный компонент так же может вызвать layout thrashing в эффекте. Как это устроено — в [Реализации фреймворка](/content/common-coding-questions/framework-implementation).

## Красные флаги в ответе

- **«Каждое изменение стиля сразу перерисовывает страницу».** Браузер копит изменения до кадра, если не заставить его чтением.
- **«Любое чтение из DOM дорогое».** Дороги чтения геометрии после изменений; `getComputedStyle(el).color` раскладку не вызывает.
- **«`transform` не вызывает ничего».** Он обновляет стили и композицию, а первый переход из `none` один раз меняет раскладку.
- **«`will-change: transform` на всё — и будет быстрее».** Каждый слой стоит видеопамяти, сотни слоёв замедляют композицию.
- **«Virtual DOM быстрее браузера».** Он работает поверх того же конвейера и экономит работу разработчика, а не браузера.
- **«Раскладка и перерисовка — одно и то же».** Раскладка считает геометрию и тянет за собой перерисовку; перерисовка обходится без раскладки.

## Как спрашивают на собеседовании

::question
Какие этапы проходит браузер, чтобы нарисовать кадр?

#answer
Стили — сопоставить селекторы и посчитать вычисленные значения; раскладка — размеры и положения боксов; отрисовка — списки команд рисования; растеризация — пиксели плиток; композиция — сборка слоёв в кадр. Перед этим HTML разбирается в DOM, а CSS в CSSOM.

#more
Изменение запускает конвейер с первого затронутого этапа: геометрия — с раскладки, цвет — с отрисовки, `transform` и `opacity` на своём слое — только композицию. Кадр рисуется между задачами цикла событий, не чаще частоты экрана, и на всё есть около 16 мс при 60 кадрах в секунду.
::

::question
Чем раскладка (reflow) отличается от перерисовки (repaint)?

#answer
Раскладка пересчитывает геометрию — размеры и положения элементов — и может затронуть соседей, родителей и всё ниже. Перерисовка заново рисует пиксели без изменения геометрии: цвет, фон, тень. Раскладка всегда влечёт перерисовку, обратное неверно.

#more
Раскладку вызывают `width`, `height`, `margin`, `top`, `font-size`, изменение текста и DOM. Перерисовку — цвета, тени, фон, `visibility`. Оба этапа выполняются в основном потоке. Смотреть их — в панели Performance и Rendering с Paint flashing.
::

::question
Почему анимировать transform дешевле, чем top или left?

#answer
`top` и `left` меняют геометрию, и браузер на каждом кадре пересчитывает раскладку, перерисовывает и композирует. `transform` у элемента со своим слоем меняет только то, как композитор рисует готовую картинку: ни раскладки, ни перерисовки.

#more
Композиция может идти в отдельном потоке, поэтому такая анимация плавная даже при занятом основном потоке. Анимация `transform` сама получает слой, а `will-change: transform` создаёт его заранее, чтобы старт был без рывка. Первый переход `transform` из `none` один раз меняет раскладку — его можно убрать начальным `translateX(0)`.
::

::question
Что такое принудительная синхронная раскладка?

#answer
Когда скрипт меняет стили, а потом читает геометрию — `offsetWidth`, `getBoundingClientRect()`, `getComputedStyle(el).width`, — браузер обязан посчитать раскладку прямо сейчас, а не перед кадром. В цикле чередование записи и чтения даёт раскладку на каждой итерации — layout thrashing.

#more
Лечение — сначала все чтения, потом все записи, или запись в `requestAnimationFrame`, а измерения — через `ResizeObserver`. Не всякое чтение дорого: `getComputedStyle(el).color` требует только стилей. В DevTools такие места отмечены как «Forced reflow» со ссылкой на строку кода.
::

::question
Что такое композитный слой? Когда его создавать?

#answer
Отдельная растровая картинка части страницы, которую композитор может сдвигать, масштабировать и делать прозрачнее без перерисовки. Слои получают элементы с `will-change`, анимациями `transform` и `opacity`, `video`, `canvas`, `position: fixed`, прокручиваемые области.

#more
`will-change` ставят на то, что скоро будет анимироваться, и снимают после. Каждый слой занимает видеопамять — ширина × высота × плотность² × 4 байта, — и сотни слоёв замедляют композицию на слабых устройствах. Слои видны в панели Layers с причиной создания.
::

::question
Как найти, что тормозит рендеринг?

#answer
Записать взаимодействие в панели Performance и посмотреть на основной поток: долгие блоки Recalculate Style, Layout, Paint и предупреждения «Forced reflow». Во вкладке Rendering включить Paint flashing и Layer borders, в Layers — проверить число и размер слоёв.

#more
Дальше — по ситуации: большая раскладка — найти, что её вызывает, и разделить чтения и записи; частая перерисовка большой области — вынести анимацию на `transform` или в свой слой; длинная задача — дробить и уступать поток. Проверять нужно с замедлением процессора, как на слабом телефоне.
::

::question
Ускоряет ли Virtual DOM рендеринг?

#answer
Нет. Virtual DOM сравнивает описания интерфейса и применяет к DOM только изменения, но дальше работает тот же конвейер браузера. Он экономит работу разработчика и пакетирует обновления, а ручное точечное изменение DOM может быть быстрее.

#more
Фреймворки на сигналах обновляют конкретные узлы без сравнения деревьев. Любой подход может вызвать layout thrashing, если в эффектах чередовать чтения и записи геометрии. Производительность рендеринга определяют количество изменённых узлов, затронутые этапы конвейера и размер DOM.
::

## Практика

::practice{title="Сколько раз браузер посчитает раскладку?"}
Скрипт подгоняет ширину пятидесяти карточек:

```js
for (const el of document.querySelectorAll('.item')) {
  el.style.width = el.offsetWidth + 1 + 'px';
}
```

#solution
49 раз прямо в цикле: первое чтение `offsetWidth` попадает на уже посчитанную раскладку, а каждое следующее идёт после записи и заставляет браузер пересчитать раскладку синхронно. В проверке счётчик Chromium показал ровно 49. Разделяем чтения и записи:

```js
const items = [...document.querySelectorAll('.item')];
const widths = items.map((el) => el.offsetWidth);          // все чтения
items.forEach((el, i) => { el.style.width = widths[i] + 1 + 'px'; }); // все записи
```

Теперь не больше одной раскладки на все чтения, а записи применятся в кадре. Если ширина нужна от содержимого, надёжнее CSS — `width: fit-content` — без JavaScript вовсе.
::

::practice{title="Какие строки вызывают раскладку?"}
После `card.style.width = '130px'` выполняется одна из строк. Какие из них заставят браузер посчитать раскладку прямо сейчас?

```js
getComputedStyle(card).color;
getComputedStyle(card).width;
card.getBoundingClientRect();
card.classList.contains('active');
```

#solution
Вторая и третья. `getComputedStyle(card).width` и `getBoundingClientRect()` возвращают геометрию, и браузер обязан посчитать раскладку. `getComputedStyle(card).color` требует только пересчёта стилей — цвету геометрия не нужна. `classList` вообще не касается конвейера: это чтение атрибута. В проверке в Chromium после изменения ширины чтение цвета дало один пересчёт стилей и ноль раскладок, а чтение ширины — одну раскладку.

Если геометрия нужна, её читают до записи, пока раскладка ещё посчитана:

```js
const { height } = card.getBoundingClientRect();   // чтение до изменений
card.style.width = '130px';                         // запись — применится в кадре
tooltip.style.top = `${height + 8}px`;
```
::

::practice{title="Панель корзины дёргается"}
Панель корзины выезжает рывками на телефонах:

```css
.drawer { position: fixed; top: 0; right: -400px; width: 400px; transition: right 0.3s; }
.drawer.open { right: 0; }
.drawer, .card, .badge, .price { will-change: transform; }
```

#solution
Две проблемы. Анимируется `right` — свойство геометрии, и каждый кадр идёт через раскладку и перерисовку. А `will-change` стоит на сотнях элементов: каждый — отдельный слой в видеопамяти, и композиция на телефоне захлёбывается.

```css
.drawer { position: fixed; top: 0; right: 0; width: 400px; transform: translateX(100%); transition: transform 0.3s; }
.drawer.open { transform: translateX(0); }
```

`will-change` убираем отовсюду: идущая анимация `transform` получает слой сама. В проверке десять кадров анимации `left` дали не меньше десяти раскладок, а `transform` — ни одной.
::
