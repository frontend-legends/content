# Progressive Web Apps

PWA — сайт, который ведёт себя как приложение: устанавливается на экран и рабочий стол, открывается в своём окне, работает без сети и присылает уведомления. Держится он на двух вещах — манифесте и Service Worker. Спрашивают, что нужно для установки, как устроен жизненный цикл Service Worker и как сделать офлайн-режим. Глубже — почему первая страница не попадает под контроль Service Worker, почему пользователи неделями сидят на старой версии и почему `respondWith` после `await` ничего не делает.

::tldr
- **PWA — сайт с манифестом и Service Worker на HTTPS.** Манифест описывает приложение для установки, Service Worker перехватывает запросы страниц в своей области (scope) и управляет кешем.
- **Service Worker проходит `installing → installed → activating → activated`, а страница, которая его зарегистрировала, остаётся без контроля** до перезагрузки или `clients.claim()`.
- **Новая версия ставится и ждёт, пока закроются все вкладки со старой;** обычная перезагрузка её не включает. Для быстрого обновления — `skipWaiting()` по команде пользователя и перезагрузка на `controllerchange`.
- **`respondWith` вызывают синхронно в обработчике `fetch`,** а `cache.addAll` при установке атомарен: один неудачный ответ срывает всю установку.
- **Манифест разбирается строго:** `start_url` с чужого origin и `scope`, который не содержит `start_url`, игнорируются, а относительные адреса считаются от адреса манифеста.
::

---

## Из чего состоит PWA

Сквозной пример — магазин чая: каталог должен открываться в метро без сети, приложение — ставиться на телефон, а уведомление «заказ в пути» — приходить, даже когда вкладка закрыта.

| Часть | Что даёт |
| --- | --- |
| HTTPS | Service Worker и мощные API работают только в безопасном контексте; `localhost` тоже считается безопасным (подробно — в [Что такое веб](/content/web/what-is-web)) |
| манифест | имя, иконки, стартовый адрес, режим окна — для установки |
| Service Worker | перехват запросов, кеш, офлайн, push |

Chrome предлагает установку, когда страница на HTTPS, приложение ещё не установлено, пользователь хоть раз кликнул по странице и провёл на ней не меньше 30 секунд, а манифест содержит `name` или `short_name`, иконки 192 и 512 пикселей, `start_url` и `display` со значением `fullscreen`, `standalone`, `minimal-ui` или `window-controls-overlay`. Safari на iOS ставит любой сайт через «Поделиться → На экран «Домой»», а своего окна-приглашения к установке не показывает. Когда PWA хватает, а когда нужен :term[React Native]{def="фреймворк для нативных мобильных приложений на React"} или обёртка, — в [Кроссплатформе](/content/additional-topics/cross-platform).

## Жизненный цикл Service Worker

Service Worker — скрипт, который браузер запускает отдельно от страницы, без доступа к DOM. Он живёт между страницей и сетью и просыпается на события: установку, активацию, запросы, push.

```js
if ('serviceWorker' in navigator) {
  navigator.serviceWorker.register('/sw.js');
}
```

В проверке новый воркер прошёл состояния `installing`, `installed`, `activating`, `activated`:

- **install** — подготовка: обычно кладут в кеш оболочку приложения. Пока промис из `event.waitUntil` не выполнится, установка не закончена;
- **activate** — воркер стал главным: чистят кеши старых версий, включают navigation preload;
- **fetch**, **message**, **push** — работа.

### Первая загрузка без контроля

После активации страница, которая зарегистрировала воркер, им **не контролируется**: в проверке `navigator.serviceWorker.controller` после `activated` был `null`, а после перезагрузки — появился. Страница начинала загружаться без воркера, и браузер не меняет ей хозяина на ходу. Чтобы взять под контроль уже открытые страницы, в `activate` вызывают `self.clients.claim()`: в проверке страница получила событие `controllerchange` и запрос пошёл через воркер без перезагрузки.

### Область действия

Воркер контролирует страницы внутри своей **области** (scope), по умолчанию — папки, где лежит скрипт. В проверке `/scoped/sw.js` получил область `/scoped/`, а попытка зарегистрировать его на `/` упала с `SecurityError`. Расширить область можно заголовком `Service-Worker-Allowed` в ответе на скрипт, но проще класть `sw.js` в корень сайта. Отсюда частая ошибка: сборщик кладёт `sw.js` в `/assets/`, и он контролирует только `/assets/`.

### Установка атомарна

```js
self.addEventListener('install', (event) => {
  event.waitUntil(caches.open('static-v2').then((cache) => cache.addAll(['/', '/offline.html', '/app.css'])));
});
```

`cache.addAll` либо кладёт всё, либо ничего. В проверке список с одной отсутствующей картинкой провалил установку: воркер ушёл в состояние `redundant`, и даже `app.css` в кеш не попал. Опечатка в списке предзагрузки или удалённый файл молча оставляют пользователей без офлайна, поэтому список генерирует сборщик, а не человек.

## Обновление

При каждой навигации и при `registration.update()` браузер скачивает `sw.js` и сравнивает побайтово. Сам скрипт воркера по умолчанию проверяется мимо HTTP-кеша: в проверке `sw.js` отдавался с `Cache-Control: max-age=3600`, и всё равно новая версия была найдена сразу. Скрипты из `importScripts` берутся из HTTP-кеша — это задаёт параметр `updateViaCache`.

Новая версия устанавливается и **ждёт** (`waiting`), пока не закроются все вкладки, которые контролирует старая. Две версии кода одновременно управлять страницами не могут, иначе старая страница получила бы ответы, рассчитанные на новую. В проверке после установки второй версии ответы по-прежнему шли от первой, а **перезагрузка страницы ничего не изменила**: новая страница начинает загружаться до того, как старая уходит, и вкладка не освобождается ни на миг. Поэтому пользователь, который держит магазин открытым во вкладке, неделями видит старую версию.

Обычный способ — спросить пользователя:

```js
// страница
const reg = await navigator.serviceWorker.register('/sw.js');
reg.addEventListener('updatefound', () => {
  const next = reg.installing;
  next.addEventListener('statechange', () => {
    if (next.state === 'installed' && navigator.serviceWorker.controller) {
      showBanner('Доступна новая версия', () => next.postMessage('skipWaiting'));
    }
  });
});
navigator.serviceWorker.addEventListener('controllerchange', () => location.reload());

// sw.js
self.addEventListener('message', (e) => { if (e.data === 'skipWaiting') self.skipWaiting(); });
```

В проверке после сообщения `skipWaiting` страница получила `controllerchange`, ответы пошли от второй версии, а в `activate` старый кеш удалился — остался только `static-v2`. Вызывать `skipWaiting()` сразу при установке тоже можно, но тогда открытая страница старой версии может запросить файлы, которых в новом кеше уже нет.

## Перехват запросов

```js
self.addEventListener('fetch', (event) => {
  if (event.request.mode !== 'navigate') return;
  event.respondWith((async () => {
    try {
      return (await event.preloadResponse) ?? (await fetch(event.request));
    } catch {
      return (await caches.match(event.request)) ?? caches.match('/offline.html');
    }
  })());
});
```

- **`respondWith` — синхронно.** Решение о перехвате принимается, пока выполняется обработчик; асинхронную работу передают промисом внутрь `respondWith`. В проверке обработчик с `await` перед `respondWith` получил `InvalidStateError: … The event handler is already finished`, а запрос ушёл в сеть мимо воркера;
- **без `respondWith`** запрос идёт в сеть как обычно — так пропускают всё, что воркер не обрабатывает;
- **офлайн** — в проверке при «выключенной сети» главная открылась из кеша, положенного при установке, а незнакомый `/catalog` получил запасную страницу «Нет сети».

Какую стратегию взять для какого ресурса — :term[cache-first]{def="стратегия: брать ответ из кеша, а в сеть идти только при промахе"} для статики с хешами, :term[network-first]{def="стратегия: сначала сеть, а кеш — только если сеть недоступна"} для HTML и API, :term[stale-while-revalidate]{def="стратегия: сразу отдать копию из кеша и в фоне обновить её из сети"} для того, что можно показать чуть устаревшим, — разобрано в [Стратегиях кеширования](/content/security-perfomance/caching-strategies). Для типовых случаев есть Workbox: он генерирует список предзагрузки из сборки и реализует стратегии.

### Navigation preload

Когда воркер спит, на его запуск уходит время, и навигация ждёт, пока он проснётся и сделает `fetch`. Navigation preload запускает запрос страницы параллельно с запуском воркера, а воркер забирает готовый ответ из `event.preloadResponse`. Включают в `activate`: `self.registration.navigationPreload.enable()`. Сервер видит такой запрос по заголовку `Service-Worker-Navigation-Preload` — в проверке навигация на главную пришла с ним.

## Манифест

```json
{
  "name": "Магазин чая",
  "short_name": "Чай",
  "id": "/",
  "start_url": "/?source=pwa",
  "scope": "/",
  "display": "standalone",
  "theme_color": "#3b6d11",
  "background_color": "#ffffff",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icon-maskable.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
```

Подключают в `head`: `link rel="manifest" href="/manifest.webmanifest"`. Браузер разбирает его строго и молча отбрасывает неверное — в проверке это видно в списке ошибок разбора, том же, что показывает DevTools в Application → Manifest:

- **`start_url` с другого origin** игнорируется, и стартовой становится текущая страница;
- **`scope`, который не содержит `start_url`,** игнорируется — область сужается до папки `start_url`;
- **неизвестное значение `display`** игнорируется;
- **относительные адреса считаются от адреса манифеста,** а не страницы: `"start_url": "?source=pwa"` в манифесте из `/static/` дал `/static/relative.webmanifest?source=pwa` — приложение открывалось бы на файле манифеста;
- **`id`** по умолчанию равен `start_url`. Его задают явно: иначе смена `start_url` превращает приложение в другое, и установленные копии не обновятся.

`maskable` — иконка с запасом по краям, которую система обрезает в круг или скруглённый квадрат.

## Push-уведомления

Push работает, даже когда вкладка закрыта: сервер отправляет сообщение в сервис push браузера, тот будит Service Worker, а воркер показывает уведомление.

```js
// страница — по нажатию кнопки «Сообщать о заказе»
const permission = await Notification.requestPermission();
if (permission === 'granted') {
  const subscription = await reg.pushManager.subscribe({
    userVisibleOnly: true,
    applicationServerKey: VAPID_PUBLIC_KEY,
  });
  await fetch('/api/push/subscribe', { method: 'POST', body: JSON.stringify(subscription) });
}

// sw.js
self.addEventListener('push', (event) => {
  const { title, body } = event.data.json();
  event.waitUntil(self.registration.showNotification(title, { body, icon: '/icon-192.png' }));
});
self.addEventListener('notificationclick', (event) => {
  event.notification.close();
  event.waitUntil(clients.openWindow('/orders'));
});
```

- **разрешение — в ответ на действие пользователя**, а не при загрузке: браузеры прячут или блокируют навязчивые запросы, а отказ потом почти невозможно отменить;
- **`userVisibleOnly: true`** — обещание показывать уведомление на каждый push; Chrome принимает только такие подписки;
- **VAPID** — пара ключей сервера: публичный передают в `subscribe`, приватным сервер подписывает отправку;
- **на iOS и iPadOS** push работает только у веб-приложения, добавленного на экран «Домой», и разрешение запрашивается по нажатию.

## Ограничения

- **возможности браузера** — часть API устройства недоступна или есть не везде, особенно на iOS: проверяют наличие API, а не браузер;
- **хранилище не вечное** — браузер может очистить кеш и IndexedDB при нехватке места; `navigator.storage.persist()` просит не удалять (подробно — в [Хранилищах](/content/network-api/storage));
- **воркер не живёт постоянно** — браузер останавливает его без событий, поэтому глобальные переменные в `sw.js` не годятся для состояния;
- **ошибка в воркере живёт долго** — неудачная версия управляет сайтом у всех, кто его открывал. Аварийный выход — выложить новый `sw.js`, который в `activate` удаляет кеши и вызывает `self.registration.unregister()`.

Отлаживают воркер в DevTools на вкладке Application: состояние, Update on reload, Bypass for network, кеши и манифест (подробно — в [DevTools](/content/web/devtools)).

## Красные флаги в ответе

- **«После регистрации Service Worker сразу перехватывает запросы страницы».** Страница, которая его зарегистрировала, без контроля до перезагрузки или `clients.claim()`.
- **«Выложили новую версию — пользователи увидят её при перезагрузке».** Новая версия ждёт, пока закроются все вкладки; перезагрузка её не включает.
- **«В `fetch` сначала `await caches.match()`, потом `respondWith`».** `respondWith` вызывают синхронно, иначе `InvalidStateError` и запрос уходит в сеть.
- **«`sw.js` положим в `/assets/` вместе со сборкой».** Область по умолчанию — папка скрипта; воркер не будет контролировать страницы сайта.
- **«Запросим разрешение на уведомления при входе на сайт».** Только по действию пользователя, иначе отказ или блокировка.
- **«PWA работает одинаково везде».** На iOS установка только вручную, push — только у установленного приложения.

## Как спрашивают на собеседовании

::question
Что нужно, чтобы сайт стал PWA и его можно было установить?

#answer
HTTPS, манифест и, для офлайна, Service Worker. В манифесте для установки в Chrome — `name` или `short_name`, иконки 192 и 512, `start_url` и `display`: `standalone`, `fullscreen`, `minimal-ui` или `window-controls-overlay`. Chrome предлагает установку, когда пользователь хоть раз кликнул по странице и провёл на ней 30 секунд.

#more
В Chromium есть событие `beforeinstallprompt`: его откладывают и показывают своё приглашение в удобный момент. Safari такого события не даёт — установка через «На экран «Домой»». `id` в манифесте задают явно, чтобы смена `start_url` не делала приложение новым.
::

::question
Расскажите о жизненном цикле Service Worker.

#answer
Регистрация, затем `installing` — событие `install`, где кладут оболочку в кеш; `installed` — установлен и, если есть старая версия, ждёт; `activating` — событие `activate`, где чистят старые кеши; `activated` — перехватывает `fetch`. Неудачная установка переводит воркер в `redundant`.

#more
Страница, которая зарегистрировала воркер, им не контролируется до перезагрузки, если воркер не вызвал `clients.claim()`. `event.waitUntil` продлевает событие до выполнения промиса. Область действия — папка скрипта; шире — только с заголовком `Service-Worker-Allowed`.
::

::question
Как обновляется Service Worker и почему пользователи сидят на старой версии?

#answer
Браузер проверяет `sw.js` побайтово при навигации и `update()`. Новая версия устанавливается и ждёт, пока закроются все вкладки со старой, — перезагрузка не помогает, потому что вкладка не освобождается. Пока у пользователя открыт сайт, работает старая версия.

#more
Обычное решение — показать «Доступна новая версия», по нажатию отправить воркеру сообщение, он вызывает `skipWaiting()`, а страница на `controllerchange` перезагружается. `skipWaiting()` сразу при установке опасен: старая страница может запросить файлы, которых нет в новом кеше. Сам `sw.js` проверяется мимо HTTP-кеша, а `importScripts` — по `updateViaCache`.
::

::question
Как сделать офлайн-режим?

#answer
При `install` положить в кеш оболочку приложения и запасную страницу. В `fetch` для навигаций пробовать сеть, а при ошибке отдавать страницу из кеша или запасную. Статику с хешами в имени — из кеша, данные — из сети с кешем на случай ошибки.

#more
`respondWith` вызывают синхронно, асинхронную работу передают промисом. `cache.addAll` атомарен — список предзагрузки генерирует сборщик. Navigation preload убирает задержку на запуск воркера. Данные, которые пользователь меняет офлайн, хранят в IndexedDB и отправляют при появлении сети.
::

::question
Что такое scope Service Worker?

#answer
Область адресов, страницы которой воркер контролирует. По умолчанию — папка, где лежит скрипт: `/sw.js` контролирует весь сайт, `/assets/sw.js` — только `/assets/`. Зарегистрировать с более широкой областью без разрешения сервера нельзя — будет `SecurityError`.

#more
Расширить область можно заголовком `Service-Worker-Allowed` в ответе на скрипт воркера. На одном origin может быть несколько воркеров с разными областями; страницу контролирует воркер с самой длинной подходящей областью. Область в манифесте `scope` — отдельная вещь: она задаёт, какие адреса открываются внутри окна приложения.
::

::question
Как работают push-уведомления в вебе?

#answer
Страница по действию пользователя запрашивает разрешение и подписывается через `pushManager.subscribe` с публичным VAPID-ключом, подписка уходит на сервер. Сервер отправляет сообщение в сервис push браузера, тот будит Service Worker, и воркер в событии `push` показывает уведомление.

#more
`userVisibleOnly: true` обязательно — каждое сообщение должно показать уведомление. Клик обрабатывают в `notificationclick` и открывают нужную страницу через `clients.openWindow`. На iOS push доступен только приложению, добавленному на экран «Домой». Подписки истекают — сервер удаляет те, на которые сервис push ответил ошибкой.
::

## Практика

::practice{title="Пользователи не видят исправление"}
Исправление в корзине выложено неделю назад, но у части пользователей ошибка осталась. В `sw.js` — предзагрузка оболочки и cache-first для статики, ничего про обновление. Что происходит и как исправить?

#solution
Новая версия воркера установилась и ждёт, пока закроются все вкладки, которые контролирует старая. Пользователи, которые держат магазин открытым или только перезагружают вкладку, остаются на старой версии со старым кешем. В проверке после установки второй версии и перезагрузки страницы ответы по-прежнему шли от первой. Нужно дать пользователю обновиться:

```js
// sw.js
self.addEventListener('message', (e) => { if (e.data === 'skipWaiting') self.skipWaiting(); });

// страница
const reg = await navigator.serviceWorker.register('/sw.js');
if (reg.waiting) offerUpdate(reg.waiting);
reg.addEventListener('updatefound', () => {
  const next = reg.installing;
  next.addEventListener('statechange', () => {
    if (next.state === 'installed' && navigator.serviceWorker.controller) offerUpdate(next);
  });
});
navigator.serviceWorker.addEventListener('controllerchange', () => location.reload());

function offerUpdate(worker) {
  showBanner('Доступна новая версия', () => worker.postMessage('skipWaiting'));
}
```

В проверке после сообщения воркер активировался, страница получила `controllerchange`, а старый кеш удалился в `activate`.
::

::practice{title="Кеш не работает, хотя код правильный"}
Ответы API должны отдаваться из кеша, если он есть, но все запросы уходят в сеть, а в консоли воркера — `InvalidStateError`:

```js
self.addEventListener('fetch', async (event) => {
  if (!event.request.url.includes('/api/')) return;
  const cached = await caches.match(event.request);
  event.respondWith(cached ?? fetch(event.request));
});
```

#solution
`respondWith` вызван после `await`: к этому моменту обработчик уже завершился, браузер отправил запрос в сеть, и вызов бросает `InvalidStateError: … The event handler is already finished`. В проверке так и было: ошибка в воркере, а ответ — из сети. `respondWith` вызывают синхронно и передают в него промис:

```js
self.addEventListener('fetch', (event) => {
  if (!event.request.url.includes('/api/')) return;
  event.respondWith((async () => {
    const cached = await caches.match(event.request);
    return cached ?? fetch(event.request);
  })());
});
```

То же правило для `event.waitUntil`: асинхронный обработчик — `async`-функция — возвращает управление браузеру на первом `await`, и событие считается обработанным.
::

::practice{title="Приложение открывается на странице с JSON"}
После установки PWA открывается не на главной, а на странице, которая показывает текст манифеста. Манифест лежит в `/static/manifest.webmanifest`:

```json
{ "name": "Магазин чая", "start_url": "?source=pwa", "display": "standalone", "icons": [] }
```

#solution
Относительные адреса в манифесте разрешаются от адреса **манифеста**, а не страницы. `?source=pwa` от `/static/manifest.webmanifest` — это `/static/manifest.webmanifest?source=pwa`. В проверке Chromium разобрал такой `start_url` именно так, а область стала `/static/`. Пишут путь от корня и задают `id` явно:

```json
{
  "name": "Магазин чая",
  "id": "/",
  "start_url": "/?source=pwa",
  "scope": "/",
  "display": "standalone",
  "icons": [
    { "src": "/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }
  ]
}
```

Без иконок 192 и 512 Chrome ещё и не предложит установку. Проверяют в DevTools: Application → Manifest показывает разобранные значения и ошибки.
::
