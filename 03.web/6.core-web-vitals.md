# Как браузер измеряет Core Web Vitals

Что такое LCP, CLS и INP, какие у них пороги и как их улучшать, разобрано в [Core Web Vitals](/content/security-perfomance/core-web-vitals). Здесь — устройство измерения: какие записи отдаёт браузер, как из них получается каждая метрика и как по ним найти причину. Спрашивают, как собрать метрики с реальных пользователей и чем `web-vitals` отличается от ручного `PerformanceObserver`. Глубже — почему LCP перестаёт обновляться после клика, почему CLS — не сумма всех сдвигов, как разложить INP на фазы и почему чужая картинка в Resource Timing отдаёт нули.

::tldr
- **Браузер отдаёт сырьё для метрик через `PerformanceObserver`:** `largest-contentful-paint`, `layout-shift`, `event`, `navigation`, `resource`, `long-animation-frame`. Подписываются с `buffered: true`, чтобы получить и записи, случившиеся до подписки.
- **LCP — последняя запись кандидата до первого ввода.** Каждый новый, более крупный отрисованный элемент даёт новую запись, а после клика или нажатия клавиши запись прекращается.
- **CLS — не сумма всех сдвигов, а худшее окно:** сдвиги объединяются в сессии с паузами меньше секунды и длиной до пяти секунд. Сдвиги сразу после ввода пользователя не считаются.
- **INP строится из записей Event Timing:** события одного действия делят `interactionId`, длительность — от ввода до следующего кадра, и её раскладывают на задержку ввода, обработку и задержку отрисовки.
- **TTFB и время ресурсов — из Navigation и Resource Timing.** Чужие ресурсы без `Timing-Allow-Origin` отдают нули, а `Server-Timing` передаёт в браузер время, проведённое на сервере.
::

## Откуда берутся числа

Сквозной пример — страница товара в магазине чая: заголовок, фото, баннер скидки, который появляется после загрузки, кнопка «В корзину» с тяжёлым обработчиком и картинки с CDN на другом домене.

Метрики не считаются где-то в облаке — их считает сам браузер и отдаёт записями Performance Timeline. Подписка — `PerformanceObserver`:

```js
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) send(entry);
}).observe({ type: 'largest-contentful-paint', buffered: true });
```

| Тип записи | Из чего метрика |
| --- | --- |
| `navigation` | TTFB, загрузка документа, `DOMContentLoaded` |
| `resource` | время каждого запроса: картинок, скриптов, `fetch` |
| `paint` | первая отрисовка и первая содержательная отрисовка — FCP |
| `largest-contentful-paint` | кандидаты LCP |
| `layout-shift` | сдвиги макета для CLS |
| `event` | задержки событий для INP |
| `long-animation-frame` | долгие кадры с разбором, какой скрипт виноват |

`buffered: true` отдаёт и записи, которые случились до подписки, — без него код аналитики, подключённый позже, потеряет начало загрузки. В проверке подписка на `largest-contentful-paint` после загрузки страницы без `buffered` не получила ни одной записи, а с ним — получила все. Базовые приёмы Performance API — `mark`, `measure`, долгие задачи — в [Памяти и производительности](/content/javascript/memory-and-performance).

На практике метрики собирают библиотекой `web-vitals`: она реализует правила, о которых ниже, учитывает фоновые вкладки и кеш «назад/вперёд» и отправляет итоговое значение, когда страница уходит в фон. Все проверки ниже сверяют ручной расчёт по записям с её результатом.

## LCP

Пока страница грузится, браузер отмечает **кандидатов**: каждый раз, когда отрисован элемент крупнее предыдущего самого крупного, появляется новая запись `largest-contentful-paint`. Кандидатами бывают картинки, постеры видео, элементы с фоновой картинкой и блоки текста. LCP — время последней записи.

В проверке среди первых кандидатов была картинка 200×100, а когда скрипт добавил фото товара 600×400, последней записью стало оно.

Запись **прекращается при первом вводе** — клике, нажатии клавиши, прокрутке: дальше пользователь уже взаимодействует со страницей, и «загрузка» для него закончилась. В проверке после клика большая картинка, добавленная скриптом, кандидатом не стала. Поэтому ленивые баннеры, появляющиеся после действий пользователя, LCP не портят, а слайдер, который сам перелистывает крупные картинки до первого клика, — портит.

### Из чего складывается LCP

Значение LCP раскладывают на четыре части:

```text
LCP = TTFB + задержка начала загрузки + загрузка ресурса + задержка отрисовки
```

- **TTFB** — пока пришёл первый байт HTML;
- **задержка начала загрузки** — пока браузер нашёл картинку и начал её качать: если её создаёт JavaScript или задаёт CSS, задержка большая;
- **загрузка ресурса** — сколько качалась сама картинка;
- **задержка отрисовки** — от конца загрузки до отрисовки: блокирующие стили, скрипты, шрифты.

Атрибуция `web-vitals` возвращает эти части: в проверке картинка, которую сервер отдавал 300 мс, дала загрузку ресурса не меньше 280 мс, а сумма четырёх частей совпала со значением LCP. Так ясно, что лечить: сервер, обнаружение картинки, вес или блокировку. Способы — в [Производительности загрузки](/content/security-perfomance/loading-performance).

## CLS

Каждый неожиданный сдвиг даёт запись `layout-shift` со значением — произведением доли экрана, которую затронул сдвиг, на долю экрана, на которую элементы сдвинулись. CLS — **не сумма всех записей**. Сдвиги объединяются в **окна сессий**:

- следующий сдвиг входит в окно, если после предыдущего прошло меньше 1 секунды;
- окно длится не больше 5 секунд;
- CLS — сумма самого «тяжёлого» окна.

В проверке баннер сдвинул описание дважды с интервалом 200 мс, а через 1,3 секунды — ещё раз. Получилось два окна: первое с двумя сдвигами, второе с одним. CLS равен сумме первого окна — меньше суммы всех трёх сдвигов, — и `web-vitals` выдал то же значение, что ручной расчёт по окнам. Так долгоживущее одностраничное приложение не накапливает CLS бесконечно.

Сдвиги в течение 500 мс после ввода пользователя помечаются `hadRecentInput: true` и не считаются: в проверке сдвиг сразу после клика по «Ещё» пришёл с этим флагом. Причины сдвигов — в записи есть `sources` с элементами, которые сдвинулись.

## INP

Каждое событие ввода, обработка которого заняла заметное время, даёт запись `event` в API **Event Timing**. Одно действие пользователя — несколько событий: клик мышью — это `pointerdown`, `pointerup` и `click`. Их объединяет общий `interactionId`: в проверке у всех трёх событий клика по «В корзину» он был одинаковым.

Длительность взаимодействия — от ввода до **следующей отрисовки**, округлённая до 8 мс: в проверке длительности всех событий делились на 8. Её раскладывают на три фазы:

| Фаза | Что это | Почему растёт |
| --- | --- | --- |
| задержка ввода | от ввода до начала обработчиков | поток занят другой задачей |
| обработка | выполнение обработчиков | тяжёлый код в обработчике |
| задержка отрисовки | от конца обработчиков до кадра | большая раскладка и отрисовка, микрозадачи, фреймворк перерисовывает много |

В проверке обработчик клика держал поток 150 мс: длительность события была не меньше 150 мс, `web-vitals` насчитал INP не меньше 150 мс, атрибуция показала обработку не меньше 140 мс, а три фазы в сумме совпали со значением INP. INP страницы — почти худшее взаимодействие за визит: при множестве действий отбрасывается по одному худшему на каждые 50.

Какой именно код виноват, показывают записи `long-animation-frame`: в них есть список скриптов кадра с типом вызова, вызывающим и адресом файла. В проверке атрибуция INP привела долгий кадр со скриптом типа `event-listener` и вызывающим `BUTTON#buy.onclick` — тем самым тяжёлым слушателем. Как дробить работу и уступать поток — в [Производительности выполнения](/content/security-perfomance/runtime-performance).

## Navigation и Resource Timing

Запись `navigation` раскладывает загрузку документа по шагам: перенаправления, DNS, соединение, TLS, запрос, ответ, разбор, события. **TTFB** — `responseStart`: в проверке сервер, задумавшийся на 300 мс, дал `responseStart` не меньше 290 мс.

### Server-Timing

Сервер может рассказать браузеру, на что ушло время:

```http
Server-Timing: db;dur=180;desc="catalog", render;dur=40
```

В проверке `performance.getEntriesByType('navigation')[0].serverTiming` вернул обе записи — `db` 180 мс и `render` 40 мс. Так полевые данные TTFB связывают с конкретными этапами сервера: база, рендер, кеш. Видно это и во вкладке Network в DevTools.

### Чужие ресурсы

Записи `resource` есть для каждого запроса страницы, но для ресурсов с **другого origin** браузер скрывает детали: время DNS, соединения, ответа и размер передачи — нули. Иначе страница могла бы узнать, что пользователь заходил на чужой сайт, по скорости загрузки из кеша. В проверке картинка с другого origin без заголовка дала `transferSize` и `responseStart` равные 0 — только общая длительность `duration` была настоящей, — а та же картинка с `Timing-Allow-Origin: *` отдала все значения. Свой CDN отдаёт этот заголовок, иначе мониторинг загрузки картинок слеп.

## Красные флаги в ответе

- **«Метрики считает Google».** Их считает браузер на устройстве пользователя; Google собирает их в CrUX, а свои пользователи — в RUM.
- **«LCP — самый большой элемент страницы».** Это последний кандидат до первого ввода; после клика запись прекращается.
- **«CLS — сумма всех сдвигов».** Это худшее окно сессии; иначе долгая сессия набирала бы CLS бесконечно.
- **«INP — время обработчика».** Это от ввода до следующего кадра: плюс задержка ввода и отрисовка после обработчика.
- **«Resource Timing покажет время любой картинки».** Для чужого origin без `Timing-Allow-Origin` детали скрыты.
- **«Подпишусь на `PerformanceObserver`, когда загрузится аналитика».** Без `buffered: true` записи, случившиеся до подписки, не придут, и начало загрузки потеряется.

## Как спрашивают на собеседовании

::question
Как собрать Core Web Vitals с реальных пользователей?

#answer
Через `PerformanceObserver` на записи `largest-contentful-paint`, `layout-shift`, `event` с `buffered: true` — или, на практике, библиотекой `web-vitals`, которая реализует правила метрик и отправляет итоговые значения в аналитику, когда страница уходит в фон.

#more
Отправляют через `navigator.sendBeacon` или `fetch` с `keepalive`, на событии `visibilitychange`, а не `unload`. Атрибуционная сборка `web-vitals` добавляет причины: элемент LCP и его части, источники сдвигов, фазы INP и скрипты долгих кадров. Данные агрегируют по 75-му перцентилю и разрезают по типам страниц и устройствам.
::

::question
Как браузер определяет LCP?

#answer
Каждый раз, когда отрисован элемент крупнее предыдущего самого крупного — картинка, постер видео, блок текста, элемент с фоном, — появляется запись-кандидат. LCP — время последнего кандидата. После первого ввода пользователя кандидаты больше не записываются.

#more
LCP раскладывают на TTFB, задержку начала загрузки, загрузку ресурса и задержку отрисовки — это показывает, что лечить. Карусель, которая сама меняет крупные картинки до первого действия, растягивает LCP. Видимый размер элемента считается в пределах экрана, а не по натуральному размеру картинки.
::

::question
Как считается CLS?

#answer
Из записей `layout-shift`: сдвиги объединяются в окна сессий — пауза между ними меньше секунды, окно не длиннее пяти секунд, — и CLS равен сумме самого тяжёлого окна. Сдвиги в течение 500 мс после ввода пользователя не учитываются.

#more
Значение каждого сдвига — доля затронутой области экрана, умноженная на долю экрана, на которую элементы сдвинулись. Окна защищают долгие сессии одностраничных приложений от бесконечного накопления. В записи есть `sources` — какие элементы сдвинулись и откуда куда, — по ним находят виновника.
::

::question
Как разложить INP на части и найти причину?

#answer
INP — длительность взаимодействия от ввода до следующего кадра. Её раскладывают на задержку ввода — поток был занят, обработку — сами обработчики, и задержку отрисовки — работа после обработчиков до кадра. Данные дают записи Event Timing и атрибуция `web-vitals`.

#more
Большая задержка ввода — долгие задачи в момент клика: дробить работу и уступать поток. Большая обработка — тяжёлый обработчик: переносить работу после отрисовки. Большая задержка отрисовки — огромная раскладка или перерисовка всего дерева фреймворком. Конкретный скрипт показывают записи `long-animation-frame`.
::

::question
Почему Resource Timing показывает нули для картинок с CDN?

#answer
Для ресурсов с другого origin браузер скрывает детали — время соединения, ответа, размер передачи, — чтобы страница не могла по таймингам узнать историю и кеш пользователя. Сервер ресурса открывает их заголовком `Timing-Allow-Origin`.

#more
Свой CDN настраивают отдавать `Timing-Allow-Origin` для своего домена, иначе мониторинг загрузки картинок и скриптов видит только общую длительность. Длительность `duration` для чужих ресурсов доступна всегда. Для документа серверные этапы передают заголовком `Server-Timing`.
::

::question
Что такое Server-Timing?

#answer
Заголовок ответа, в котором сервер описывает свои этапы: `Server-Timing: db;dur=180, render;dur=40`. Браузер показывает их в DevTools и отдаёт в `serverTiming` записей Navigation и Resource Timing.

#more
Так полевой TTFB связывают с причинами: долгий запрос к базе, промах кеша, рендер. Метрики отправляют в RUM вместе с остальными. Описания не должны раскрывать лишнего: заголовок видят все, кто открыл страницу. Для ресурсов чужого origin он виден только с `Timing-Allow-Origin`.
::

## Практика

::practice{title="CLS в аналитике больше, чем в Search Console"}
Своя аналитика считает CLS так и получает значения в разы выше, чем в отчётах Google:

```js
let cls = 0;
new PerformanceObserver((list) => {
  for (const e of list.getEntries()) cls += e.value;
}).observe({ type: 'layout-shift', buffered: true });
addEventListener('pagehide', () => send({ cls }));
```

#solution
Три ошибки. Складываются все сдвиги, а CLS — худшее окно сессии: пауза меньше секунды, окно до пяти секунд. Сдвиги после ввода пользователя с `hadRecentInput: true` тоже попали в сумму. И `pagehide` на телефонах срабатывает ненадёжно. В проверке три сдвига дали два окна, и CLS был меньше их суммы, а `web-vitals` совпал с расчётом по окнам. Проще не повторять правила вручную:

```js
import { onCLS, onINP, onLCP } from 'web-vitals';

const send = (metric) => navigator.sendBeacon('/rum', JSON.stringify(metric));
onCLS(send);
onINP(send);
onLCP(send);
```

Библиотека отправляет значение, когда страница уходит в фон, и учитывает возврат из кеша «назад/вперёд».
::

::practice{title="INP плохой, а обработчик быстрый"}
Профилирование обработчика кнопки фильтра показывает 15 мс, а INP на этой странице — 400 мс. Где искать?

#solution
INP — от ввода до следующего кадра, а не время обработчика. Атрибуция `web-vitals` раскладывает его на три фазы:

```js
import { onINP } from 'web-vitals/attribution';

onINP(({ value, attribution }) => {
  const { inputDelay, processingDuration, presentationDelay, longAnimationFrameEntries } = attribution;
  send({ value, inputDelay, processingDuration, presentationDelay, scripts: longAnimationFrameEntries.flatMap((f) => f.scripts.map((s) => s.sourceURL)) });
});
```

При быстром обработчике время ушло в задержку ввода — поток был занят, например, разбором ответа или аналитикой в момент клика, — или в задержку отрисовки: фильтр перерисовал всю таблицу на тысячи строк. В проверке фазы в сумме совпали со значением INP, а при тяжёлом обработчике основную часть заняла обработка. Скрипты из `long-animation-frame` показывают конкретного виновника.
::
