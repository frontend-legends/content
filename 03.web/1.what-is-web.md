# Что такое веб

Веб — приложение поверх интернета: адрес (URL), протокол (HTTP), документ (HTML) и браузер, который их соединяет и выполняет код из сети в песочнице. Спрашивают, чем интернет отличается от веба, что происходит после ввода адреса, кто стандартизирует веб и чем веб-приложение отличается от нативного. Глубже — как браузер разбирает URL и почему один адрес можно записать десятком способов, чем origin отличается от site и почему камера не работает на тестовом стенде по `http`.

::tldr
- **Интернет — сеть, веб — приложение поверх неё.** Интернет передаёт пакеты по IP и TCP, веб добавляет адреса страниц, протокол HTTP, документы HTML и браузер.
- **URL браузер разбирает по стандарту WHATWG:** схема и хост приводятся к нижнему регистру, порт по умолчанию отбрасывается, `..` в пути схлопываются, остальное кодируется. Фрагмент после `#` на сервер не уходит.
- **Origin — схема, хост и порт; это граница безопасности.** Site — схема и регистрируемый домен; по нему работают куки `SameSite` и изоляция процессов браузера.
- **Стандарты пишут несколько организаций:** WHATWG — HTML, DOM, Fetch, URL; W3C — CSS и доступность; TC39 — JavaScript; IETF — HTTP и TLS. Возможность готова к использованию, когда её поддерживают все основные браузеры.
- **Браузер — песочница.** Мощные API — камера, Service Worker, Web Crypto, буфер обмена — работают только в безопасном контексте: по HTTPS или на `localhost`.
::

## Интернет и веб

Сквозной пример — интернет-магазин чая `shop.example`: каталог, поиск, страница товара и тестовый стенд на `http://shop.test`.

Слова «интернет» и «веб» часто путают, но это разные уровни:

- **интернет** — сеть сетей: компьютеры, кабели, маршрутизаторы и протоколы IP, TCP, UDP. По нему ходит почта, мессенджеры, игры, обновления приложений;
- **веб** — одно из приложений поверх интернета. Его придумал Тим Бернерс-Ли в CERN в 1989–1991 годах, и он стоит на трёх идеях: **URL** — у каждого документа есть адрес, **HTTP** — как документ запросить, **HTML** — как описать документ со ссылками на другие.

Браузер соединяет всё вместе. Когда пользователь вводит `https://shop.example/tea/oolong`, браузер разбирает адрес, находит сервер через DNS, устанавливает соединение TCP и TLS, отправляет HTTP-запрос, разбирает полученный HTML, загружает стили, скрипты и картинки и рисует страницу. Каждый шаг разобран отдельно:

| Шаг | Где подробно |
| --- | --- |
| разбор адреса | ниже |
| DNS, TCP, TLS, запрос и ответ | [Жизненный цикл запроса](/content/network-api/request-lifecycle) |
| разбор HTML, загрузка ресурсов, события документа | [Структура документа](/content/html/structure) |
| стили, раскладка, отрисовка, композиция | [Рендеринг](/content/web/rendering) |
| где создаётся HTML — сервер, сборка или браузер | [Рендеринг и гидратация](/content/reactjs/rendering-and-hydration) |

## URL

Адрес страницы — **URL** (Uniform Resource Locator). Как его разбирать, описывает URL Standard от WHATWG, и браузеры, Node.js и Deno реализуют один и тот же алгоритм через класс `URL`.

```text
https://user:pass@shop.example.com:8080/tea/oolong?sort=price&page=2#reviews
└─┬─┘   └───┬───┘ └──────┬───────┘ └┬─┘└────┬────┘└─────────┬───────┘└──┬──┘
схема  учётные      хост          порт   путь       строка запроса   фрагмент
        данные
```

### Нормализация

Один и тот же адрес можно записать многими способами, и браузер приводит их к одному виду:

```js
const u = new URL('HTTPS://Shop.Example.COM:443/catalog/../tea/улун молочный?sort=price#reviews');
u.href;
// 'https://shop.example.com/tea/%D1%83%D0%BB%D1%83%D0%BD%20%D0%BC%D0%BE…?sort=price#reviews'
```

В проверке в Chromium:

- схема и хост приведены к нижнему регистру — `https`, `shop.example.com`;
- порт 443 для HTTPS — порт по умолчанию, и он отброшен; нестандартный `:8080` сохраняется;
- `catalog/..` схлопнулось, путь стал `/tea/…`;
- пробел и кириллица в пути закодированы процентами;
- домен на кириллице `чай.рф` превратился в `xn--80as4b.xn--p1ai` — это **punycode**, запись международных доменов ASCII-символами для DNS.

Поэтому адреса сравнивают после разбора, а не как строки: `https://Shop.example:443/a` и `https://shop.example/a` — один адрес.

### Относительные адреса

`new URL(относительный, базовый)` разрешает ссылку так же, как браузер — `href` в разметке. Для базового адреса `https://shop.example/catalog/tea/oolong?page=2`:

| Ссылка | Результат |
| --- | --- |
| `milk` | `https://shop.example/catalog/tea/milk` |
| `../coffee` | `https://shop.example/catalog/coffee` |
| `/cart` | `https://shop.example/cart` |
| `?page=3` | `https://shop.example/catalog/tea/oolong?page=3` |
| `#reviews` | `https://shop.example/catalog/tea/oolong?page=2#reviews` |
| `//cdn.example/tea.png` | `https://cdn.example/tea.png` — та же схема, другой хост |

`URL.canParse('/tea')` без базового адреса в проверке вернул `false` — это удобный способ проверить ввод пользователя без `try/catch`.

### Фрагмент

Всё после `#` — **фрагмент** — остаётся в браузере. В проверке запрос `…/tea/oolong?sort=price#reviews` пришёл на сервер как `/tea/oolong?sort=price`, а смена `location.hash` не вызвала запроса вовсе. Фрагментом прокручивают к элементу с `id`, а старые одностраничные приложения хранили в нём маршрут — `#/cart`, — потому что смена фрагмента не перезагружает страницу. Сегодня для маршрутов используют History API и обычные пути.

### Строка запроса

Параметры склеивать строкой нельзя:

```js
new URL('https://shop.example/search?q=' + 'чай & молоко 100%').searchParams.get('q');  // 'чай '
```

Символ `&` разрезал значение на параметры, а `%` начал бы испорченную escape-последовательность. `URLSearchParams` кодирует значения сам: в проверке поиск «чай & молоко 100%» сохранился целиком. Есть тонкость: в строке запроса `+` означает пробел — `URLSearchParams` пишет пробел как `+` и читает `+` как пробел, а `encodeURIComponent` кодирует пробел как `%20`. Сервер, который разбирает строку запроса не по стандарту, может прочитать «чай+с+молоком» буквально.

## Origin и site

Два понятия, на которых держится безопасность веба.

**Origin** — тройка «схема, хост, порт». В проверке:

| Адрес | Тот же origin, что `https://shop.example`? |
| --- | --- |
| `https://shop.example:443/b?x#y` | да — путь, запрос и фрагмент не важны, 443 — порт по умолчанию |
| `http://shop.example` | нет — другая схема |
| `https://api.shop.example` | нет — другой хост |
| `https://shop.example:8443` | нет — другой порт |
| `data:text/html,…` | нет — у таких документов непрозрачный origin `null` |

Скрипт может читать данные только своего origin; чужой — через CORS, если тот разрешил. Хранилища — `localStorage`, IndexedDB, Cache API — разделены по origin.

**Site** — схема и **регистрируемый домен**: домен на один уровень ниже публичного суффикса. `shop.example` и `api.shop.example` — один site, хотя origin разные. Публичные суффиксы берут из Public Suffix List: в нём есть не только `com` и `рф`, но и `github.io`, поэтому `alice.github.io` и `bob.github.io` — разные сайты. По site работают куки `SameSite` и изоляция процессов браузера. Как эти границы защищают от атак — в [CORS и same-origin](/content/security-perfomance/cors-and-same-origin).

## Кто делает стандарты

Веб — не продукт одной компании, а набор открытых стандартов:

| Организация | Что стандартизирует |
| --- | --- |
| WHATWG | HTML, DOM, Fetch, URL, Streams, Encoding |
| W3C | CSS, доступность (WCAG, ARIA), WebRTC, WebGPU, метрики производительности |
| TC39 | ECMAScript — язык JavaScript |
| IETF | HTTP, TLS, QUIC, протокол WebSocket |
| Khronos | WebGL |

Новая возможность проходит путь: идея и обсуждение → черновик спецификации → реализация за флагом или в **origin trial** — когда сайт может включить экспериментальное API для своих пользователей по токену → включение по умолчанию в одном браузере → в остальных. Производители публикуют позиции по предложениям, и возможность, которую поддерживает один Chromium, — ещё не возможность веба. У JavaScript свой процесс — стадии TC39 (подробно — в [Современном JavaScript](/content/javascript/modern-js)).

Пользоваться можно, когда возможность есть во всех основных браузерах. Это отмечает **Baseline**: «newly available» — поддержка появилась везде, «widely available» — прошло 30 месяцев (подробно — в [Развитии платформы](/content/modern-dev/web-platform-evolution)). А в коде поддержку проверяют напрямую — `'serviceWorker' in navigator`, `CSS.supports()` — а не по строке User-Agent: строка врёт и ломается при каждом обновлении браузера.

## Браузер как песочница

Браузер выполняет код с любого сайта, который открыл пользователь, поэтому ограничивает его:

- **origin** — данные чужих сайтов недоступны без их согласия;
- **разрешения** — камера, микрофон, геолокация, уведомления только после запроса пользователю;
- **нет доступа к файлам и процессам** — только к тому, что пользователь выбрал сам;
- **изоляция процессов** — сайты работают в разных процессах (подробно — в [Архитектуре браузера](/content/web/browser-engines)).

### Безопасный контекст

Мощные API доступны только в **безопасном контексте**: страница пришла по HTTPS, с `localhost` или `127.0.0.1`. На обычном `http` их нет вовсе. В проверке на `http://localhost` `isSecureContext` был `true`, а на тестовом стенде `http://shop.test`:

| API | `localhost` | `http://shop.test` |
| --- | --- | --- |
| `isSecureContext` | `true` | `false` |
| `crypto.subtle` | есть | `undefined` |
| `navigator.serviceWorker` | есть | нет |
| `navigator.mediaDevices` — камера и микрофон | есть | `undefined` |
| `navigator.clipboard` | есть | `undefined` |

Отсюда классика: на машине разработчика `localhost` всё работает, а на стенде по `http` камера, офлайн-режим и копирование в буфер «сломаны». Стенды поднимают с HTTPS.

### Веб и нативные приложения

| | Веб | Нативное приложение |
| --- | --- | --- |
| распространение | ссылка, без установки | магазин приложений, установка |
| обновление | при следующей загрузке | через магазин, не у всех сразу |
| доступ к устройству | через API с разрешениями | полный, по разрешениям ОС |
| платформы | любая с браузером | отдельная сборка под каждую |
| производительность | JIT, песочница, один основной поток | нативный код |

Граница размывается: PWA устанавливаются и работают офлайн (подробно — в [PWA](/content/web/pwa)), а WebAssembly и WebGPU дают почти нативную скорость там, где она нужна. Как выбирать между вебом и кроссплатформенными приложениями — в [Кроссплатформенной разработке](/content/additional-topics/cross-platform).

## Красные флаги в ответе

- **«Интернет и веб — одно и то же».** Веб — приложение поверх интернета, как почта или мессенджеры.
- **«Фрагмент `#…` отправляется на сервер».** Он остаётся в браузере; сервер его не видит.
- **«Строку запроса соберу конкатенацией».** `&`, `#`, `%` и пробелы её ломают; для этого `URLSearchParams`.
- **«Origin — это домен».** Это схема, хост и порт: `http` и `https`, разные порты и поддомены — разные origin.
- **«Определю браузер по User-Agent».** Проверяют поддержку возможности, а не строку браузера.
- **«На стенде по `http` всё будет как на `localhost`».** `localhost` — безопасный контекст, обычный `http` — нет, и мощные API там отсутствуют.

## Как спрашивают на собеседовании

::question
Чем интернет отличается от веба?

#answer
Интернет — сеть: компьютеры и протоколы IP, TCP, UDP, по которым ходят пакеты. Веб — приложение поверх интернета: документы с адресами (URL), протокол их получения (HTTP), язык документов со ссылками (HTML) и браузер.

#more
Через интернет работают и почта, и мессенджеры, и игры — веб лишь одно из приложений, хотя самое заметное. Веб придумал Тим Бернерс-Ли в CERN в 1989–1991 годах. Сегодня веб — ещё и платформа приложений: браузер выполняет JavaScript, хранит данные, работает офлайн и с устройствами.
::

::question
Что происходит, когда вводишь адрес в браузере?

#answer
Браузер разбирает URL, находит IP через DNS, устанавливает TCP- и TLS-соединение, отправляет HTTP-запрос, получает HTML. Дальше разбирает HTML в DOM, загружает стили, скрипты и картинки, считает стили и раскладку, рисует и собирает кадр.

#more
Каждый шаг можно развернуть: кеш DNS и `preconnect`, HTTP/2 и HTTP/3, потоковый разбор HTML и сканер предзагрузки, блокировка отрисовки стилями, раскладка и композиция. Хороший ответ показывает, где на этом пути теряется время и чем его сокращают: CDN, кешем, сжатием, серверным рендерингом, подсказками браузеру.
::

::question
Из чего состоит URL и как браузер его нормализует?

#answer
Из схемы, необязательных учётных данных, хоста, порта, пути, строки запроса и фрагмента. Браузер разбирает его по URL Standard: приводит схему и хост к нижнему регистру, отбрасывает порт по умолчанию, схлопывает `.` и `..` в пути, кодирует пробелы и не-ASCII символы, а международные домены переводит в punycode.

#more
Фрагмент после `#` на сервер не отправляется. Относительные адреса разрешаются от базового — `new URL('../coffee', base)`. Параметры собирают через `URLSearchParams`: он кодирует `&`, `%` и пробелы, причём пробел в строке запроса — это `+`. Адреса сравнивают после разбора, а не как строки.
::

::question
Что такое origin и чем он отличается от site?

#answer
Origin — схема, хост и порт: `https://shop.example:443`. Это граница безопасности: скрипт читает данные только своего origin, хранилища разделены по origin. Site — схема и регистрируемый домен: `api.shop.example` и `shop.example` — разные origin, но один site.

#more
Регистрируемый домен считают по Public Suffix List, поэтому `alice.github.io` и `bob.github.io` — разные сайты. По site работают куки `SameSite` и изоляция процессов в браузере. У документов из `data:` и фреймов с `sandbox` без `allow-same-origin` непрозрачный origin `null`.
::

::question
Кто разрабатывает веб-стандарты и как возможность попадает в браузер?

#answer
WHATWG ведёт HTML, DOM, Fetch и URL, W3C — CSS, доступность и многие API, TC39 — JavaScript, IETF — сетевые протоколы. Возможность проходит путь от обсуждения и черновика спецификации через реализацию за флагом или origin trial до включения по умолчанию во всех браузерах.

#more
Возможность одного браузера — ещё не стандарт: другие публикуют свою позицию и могут не реализовать её. Baseline отмечает, что поддержка есть во всех основных браузерах, а через 30 месяцев — что возможность «широко доступна». В коде поддержку проверяют напрямую, а не по User-Agent.
::

::question
Что такое безопасный контекст?

#answer
Страница, пришедшая по HTTPS, с `localhost` или `127.0.0.1`. Только в нём доступны мощные API: Service Worker, Web Crypto, камера и микрофон, буфер обмена, геолокация. На обычном `http` эти API отсутствуют — `navigator.serviceWorker` и `crypto.subtle` просто нет.

#more
Проверяется через `isSecureContext`. `localhost` считается безопасным, поэтому разработка идёт гладко, а тестовый стенд по `http` внезапно «ломается». Встроенные во фреймы документы безопасны, только если безопасны и они сами, и все их предки. Решение — HTTPS везде, включая стенды.
::

::question
Чем веб-приложение отличается от нативного?

#answer
Веб распространяется ссылкой без установки, обновляется при следующей загрузке и работает везде, где есть браузер. Нативное приложение ставится из магазина, получает полный доступ к устройству через ОС и обычно быстрее.

#more
Веб ограничен песочницей: origin, разрешения, безопасный контекст, один основной поток. Граница размывается: PWA устанавливаются и работают офлайн, WebAssembly и WebGPU дают почти нативную скорость. Выбор зависит от нужного доступа к устройству, требований магазинов и стоимости поддержки нескольких платформ.
::

## Практика

::practice{title="Что выведет?"}
Что вернёт каждая строка?

```js
const base = 'https://Shop.example:443/catalog/tea/oolong?page=2';
new URL(base).origin;
new URL('../coffee', base).href;
new URL('#reviews', base).href;
new URL('//cdn.example/tea.png', base).href;
```

#solution
```text
https://shop.example
https://shop.example/catalog/coffee
https://shop.example/catalog/tea/oolong?page=2#reviews
https://cdn.example/tea.png
```

Хост приведён к нижнему регистру, порт 443 отброшен как порт по умолчанию. `../coffee` поднялся на уровень выше от каталога `tea/`. `#reviews` сохранил путь и строку запроса. `//cdn.example/…` — адрес без схемы: схема берётся от базового, а хост новый. В проверке в Chromium все четыре значения совпали.
::

::practice{title="Поиск ломается на «&»"}
Поиск по «чай & молоко» находит только «чай», а «скидка 100%» падает с ошибкой на сервере:

```js
const url = '/search?q=' + query + '&page=' + page;
const res = await fetch(url);
```

#solution
Значение вставлено в строку как есть. `&` в запросе начинает новый параметр, и `q` обрывается на «чай », а `%` начинает процентную escape-последовательность, которую сервер не может разобрать. В проверке такая склейка вернула `q` равным `'чай '`. Параметры собирают через `URLSearchParams`:

```js
const url = new URL('/search', location.origin);
url.searchParams.set('q', query);
url.searchParams.set('page', String(page));
const res = await fetch(url);
```

С ним «чай & молоко 100%» дошёл целиком: `?q=%D1%87%D0%B0%D0%B9+%26+…+100%25`. Сервер должен разбирать строку запроса по стандарту и читать `+` как пробел.
::

::practice{title="Камера не работает на стенде"}
Сканер штрихкодов для склада работает у разработчика, а на тестовом стенде `http://192.168.1.20:3000` падает с `Cannot read properties of undefined (reading 'getUserMedia')`.

#solution
`http://localhost` — безопасный контекст, а `http://192.168.1.20` — нет, и `navigator.mediaDevices` там просто отсутствует. В проверке на обычном `http` `isSecureContext` был `false`, а `mediaDevices`, `crypto.subtle`, `serviceWorker` и `clipboard` — `undefined`. Стенд поднимают с HTTPS — самоподписанным сертификатом или локальным центром сертификации вроде mkcert, — а в коде проверяют контекст заранее:

```js
if (!window.isSecureContext || !navigator.mediaDevices) {
  showMessage('Сканер работает только по HTTPS');
  return;
}
const stream = await navigator.mediaDevices.getUserMedia({ video: { facingMode: 'environment' } });
```

Отключать проверку флагами браузера можно только для отладки на своей машине.
::
