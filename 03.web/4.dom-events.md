# DOM и события

DOM — программный интерфейс документа: поиск, создание и изменение узлов. События — способ, которым действия пользователя и браузера доходят до кода: путь события по дереву, фазы, отмена действий, делегирование. Спрашивают, как работают всплытие и перехват, чем `stopPropagation` отличается от `preventDefault`, что такое делегирование и passive-слушатели. Глубже — почему после `innerHTML +=` перестали работать кнопки, почему цикл по `getElementsByClassName` обрабатывает половину элементов и почему `focus` не ловится на форме.

::tldr
- **Поиск возвращает разное:** `querySelectorAll` — статичный снимок, `getElementsByClassName` и `getElementsByTagName` — живые коллекции, которые меняются вместе с DOM. `innerHTML +=` пересоздаёт всё содержимое и теряет обработчики.
- **Событие проходит три фазы:** перехват от `window` вниз, цель, всплытие обратно. На самой цели слушатели перехвата срабатывают раньше слушателей всплытия, в каком бы порядке их ни добавили.
- **`stopPropagation` останавливает путь события, `stopImmediatePropagation` — ещё и остальных слушателей этого элемента, `preventDefault` отменяет действие браузера** — но не в passive-слушателе.
- **Делегирование — один слушатель на предке и `closest`.** `focus`, `blur`, `mouseenter` не всплывают: для них `focusin`, `mouseover` или фаза перехвата.
- **`dispatchEvent` выполняет слушателей синхронно и создаёт недоверенное событие:** `isTrusted` равен `false`, и часть действий браузера — например, ввод текста по `keydown` — не происходит.
::

## Поиск и изменение DOM

Сквозной пример — корзина магазина чая: список товаров, кнопки «удалить», поле промокода и форма оформления.

DOM — дерево узлов, которое браузер строит из HTML (подробно о типах узлов — в [Структуре документа](/content/html/structure)). JavaScript работает с ним через API.

### Поиск

| Метод | Возвращает | Живая? |
| --- | --- | --- |
| `getElementById('cart')` | элемент или `null` | — |
| `querySelector('.item')` | первый элемент или `null` | — |
| `querySelectorAll('.item')` | `NodeList` | нет, снимок |
| `getElementsByClassName('item')` | `HTMLCollection` | да |
| `getElementsByTagName('li')` | `HTMLCollection` | да |
| `element.children` | `HTMLCollection` | да |
| `closest('.card')` | ближайший предок, включая сам элемент | — |

**Живая** коллекция отражает DOM в момент обращения: в проверке после добавления пятого товара живая коллекция показала 5, а снимок `querySelectorAll` — по-прежнему 4. Это ловушка в циклах:

```js
const items = document.getElementsByClassName('item');
for (let i = 0; i < items.length; i++) items[i].classList.remove('item');
```

Снятый класс убирает элемент из коллекции, индексы сдвигаются, и цикл перескакивает через каждый второй. В проверке из пяти товаров класс сняли только у трёх, два остались. Для изменений в цикле берут снимок — `querySelectorAll` или `[...items]`.

### Создание и вставка

```js
const li = document.createElement('li');
li.textContent = 'Улун';               // текст — всегда через textContent
list.append(li);                        // append, prepend, before, after, replaceWith
list.replaceChildren(...newItems);      // заменить всё содержимое
list.insertAdjacentHTML('beforeend', '<li>Пуэр</li>');
```

- **`DocumentFragment`** — контейнер для сборки нескольких узлов: при вставке переносит детей и пустеет. В проверке после `append(fragment)` в нём осталось 0 узлов, а в списке появились оба товара;
- **`innerHTML +=`** не «добавляет» HTML, а читает всё содержимое строкой, склеивает и разбирает заново. Старые узлы уничтожаются вместе с обработчиками и состоянием полей: в проверке кнопка «Купить» после `innerHTML += '<li>…</li>'` перестала реагировать. `insertAdjacentHTML` и `append` существующие узлы не трогают — обработчик сохранился;
- **`innerHTML` с чужими данными** — путь к XSS; для текста — `textContent` (подробно — в [XSS](/content/security-perfomance/xss)).

Пакетная вставка через фрагмент не нужна ради производительности: браузер и так копит изменения до кадра. Дорого другое — чередовать изменения с чтением геометрии (подробно — в [Рендеринге](/content/web/rendering)).

## Путь события

Когда пользователь нажимает «В корзину», событие `click` проходит путь от `window` до кнопки и обратно:

```text
window → document → html → body → .card → button   перехват (capture)
                                           button   цель (target)
button → .card → body → html → document → window   всплытие (bubble)
```

`addEventListener(type, handler)` по умолчанию слушает всплытие, а `{ capture: true }` — перехват. В проверке порядок был: `window` — перехват, `.card` — перехват, кнопка — перехват, кнопка — всплытие, `.card` — всплытие, `document` — всплытие. На самой цели перехват сработал раньше всплытия, хотя слушатель всплытия добавили первым.

### Остановка и отмена

| Метод | Что делает |
| --- | --- |
| `event.stopPropagation()` | событие не пойдёт к следующим узлам пути; остальные слушатели этого узла сработают |
| `event.stopImmediatePropagation()` | то же и не вызовет оставшихся слушателей этого узла |
| `event.preventDefault()` | отменит действие браузера: переход по ссылке, отправку формы, прокрутку, ввод символа |

В проверке после `stopPropagation` в первом слушателе кнопки второй слушатель сработал, а родитель — нет; после `stopImmediatePropagation` не сработал никто. `stopPropagation` не отменяет действие браузера: ссылка всё равно откроется. И наоборот, `preventDefault` не останавливает всплытие. Злоупотреблять `stopPropagation` опасно — он ломает делегирование, аналитику и закрытие выпадающих меню по клику мимо.

### Параметры слушателя

```js
el.addEventListener('click', handler, {
  capture: false,          // фаза всплытия
  once: true,              // снять после первого вызова
  passive: true,           // обещание не вызывать preventDefault
  signal: controller.signal, // снять через controller.abort()
});
```

`signal` снимает сразу все слушатели, привязанные к контроллеру, — удобно для очистки компонента (подробно об `AbortController` — в [Асинхронности](/content/javascript/async)). В проверке слушатель с `signal` сработал до `abort()` и перестал после, а с `once` — ровно один раз.

### Passive-слушатели

Перед прокруткой по колёсику или пальцу браузер должен узнать, не отменит ли её обработчик, — и ждёт, пока тот выполнится. Тяжёлый обработчик `wheel` или `touchmove` делает прокрутку рывками. `passive: true` — обещание не вызывать `preventDefault`, и браузер прокручивает сразу.

Обещание проверяется: `preventDefault` в passive-слушателе в проверке не отменил событие — `defaultPrevented` остался `false`, — а Chrome написал в консоль «Unable to preventDefault inside passive event listener». Слушатели `wheel`, `touchstart` и `touchmove` на `window`, `document` и `body` пассивны по умолчанию: в проверке `preventDefault` в таком слушателе `wheel` прокрутку не остановил, а с явным `passive: false` — остановил. Запретить жесты прокрутки декларативно можно CSS-свойством `touch-action`.

## Делегирование

Вместо слушателя на каждой кнопке «удалить» вешают один на список:

```js
cart.addEventListener('click', (event) => {
  const button = event.target.closest('.remove');
  if (!button || !cart.contains(button)) return;
  removeFromCart(button.closest('li').dataset.id);
});
```

- **`event.target`** — самый глубокий элемент, по которому кликнули: часто иконка внутри кнопки, а не кнопка. `closest` поднимается к нужному предку. В проверке клик по `b` внутри кнопки нашёл кнопку и товар 1, а клик по названию товара мимо кнопки ничего не удалил;
- **новые элементы работают сразу** — в проверке товар, добавленный после навешивания слушателя, удалился без своего слушателя;
- **один слушатель вместо сотен** — меньше памяти и не нужно снимать слушатели при удалении строк.

Не всплывают `focus`, `blur`, `mouseenter`, `mouseleave`, `load`, `scroll` на элементах. Для них делегирование делают через парные всплывающие события — `focusin` и `focusout`, `mouseover` и `mouseout` — или в фазе перехвата: в проверке слушатель `focus` на форме в фазе всплытия не сработал, а в фазе перехвата и `focusin` — сработали. Как написать делегирование самому — в [Задачах на DOM](/content/common-coding-questions/dom-tasks).

## Свои события

```js
item.dispatchEvent(new CustomEvent('cart:remove', {
  bubbles: true,          // по умолчанию false!
  cancelable: true,
  detail: { id: 7 },
}));
```

- **по умолчанию не всплывает:** в проверке `CustomEvent` без `bubbles` до `document` не дошёл;
- **синхронно:** `dispatchEvent` вызывает всех слушателей и только потом возвращает управление. В проверке слушатель `document` для всплывающего события сработал раньше, чем выполнилась следующая строка после `dispatchEvent`;
- **отмена:** `dispatchEvent` возвращает `false`, если слушатель вызвал `preventDefault` у события с `cancelable: true`, — так компонент спрашивает «можно ли удалить?».

Чтобы событие вышло из Shadow DOM, нужно `composed: true` (подробно — в [Веб-компонентах](/content/html/web-components)).

### Доверенные события

У событий, вызванных пользователем, `event.isTrusted` равен `true`, у созданных кодом — `false`: в проверке клик мышью дал `true`, а `button.click()` — `false`. Браузер не выполняет для недоверенных событий часть своих действий: `KeyboardEvent('keydown', { key: 'a' })` в проверке не напечатал в поле ни символа, а настоящее нажатие — напечатало. Действия, требующие участия пользователя, — полноэкранный режим, открытие окна, звук, — тоже не разрешаются из синтетических событий. Порядок слушателей и микрозадач тоже отличается: при настоящем клике микрозадачи выполняются между слушателями, а при `click()` из кода — после всех (подробно — в [Event Loop](/content/javascript/event-loop)).

## Красные флаги в ответе

- **«`innerHTML +=` просто добавляет разметку».** Он пересоздаёт всё содержимое, и старые узлы теряют обработчики и состояние.
- **«`getElementsByClassName` и `querySelectorAll` возвращают одно и то же».** Первое — живая коллекция, второе — снимок; удаление в цикле по живой коллекции пропускает элементы.
- **«`stopPropagation` отменит переход по ссылке».** Действие браузера отменяет `preventDefault`.
- **«`preventDefault` в любом слушателе работает».** В passive-слушателе, а это по умолчанию `wheel` и `touch*` на `window`, он игнорируется.
- **«Повешу `focus` на форму — поймаю все поля».** `focus` не всплывает; нужен `focusin` или фаза перехвата.
- **«`requestAnimationFrame` всегда срабатывает раньше `setTimeout(fn, 0)`».** Порядок не задан и зависит от того, когда наступит кадр.

## Как спрашивают на собеседовании

::question
Чем живая коллекция отличается от статичной?

#answer
Живая — `HTMLCollection` из `getElementsByClassName`, `getElementsByTagName`, `children` — отражает DOM в момент обращения. Статичная — `NodeList` из `querySelectorAll` — снимок на момент вызова. После изменения DOM живая коллекция меняется, снимок — нет.

#more
Ловушка — удаление или снятие класса в цикле по живой коллекции: индексы сдвигаются, и цикл пропускает элементы. Для изменений в цикле берут снимок — `querySelectorAll` или `[...collection]`. `childNodes` тоже живой `NodeList`. У `NodeList` из `querySelectorAll` есть `forEach`, у `HTMLCollection` — нет.
::

::question
Как событие проходит по DOM? Что такое всплытие и перехват?

#answer
Три фазы: перехват — от `window` вниз до родителя цели, цель, всплытие — от цели обратно вверх. `addEventListener` по умолчанию слушает всплытие, с `{ capture: true }` — перехват.

#more
На самой цели слушатели перехвата срабатывают раньше слушателей всплытия, даже если добавлены позже. Перехват полезен, чтобы обработать событие раньше потомков или поймать то, что не всплывает: `focus`, `blur`, `scroll`. `event.target` — где событие началось, `event.currentTarget` — чей слушатель сейчас выполняется.
::

::question
Чем отличаются stopPropagation, stopImmediatePropagation и preventDefault?

#answer
`stopPropagation` останавливает путь события к следующим узлам, но остальные слушатели текущего узла сработают. `stopImmediatePropagation` останавливает и их. `preventDefault` отменяет действие браузера — переход, отправку, прокрутку, ввод — и не влияет на распространение.

#more
`stopPropagation` ломает делегирование, аналитику и закрытие меню по клику мимо, поэтому его используют осторожно. `preventDefault` работает только у события с `cancelable: true` и не работает в passive-слушателе. Проверить, отменено ли событие, — `event.defaultPrevented`.
::

::question
Что такое делегирование событий и где оно не работает?

#answer
Один слушатель на общем предке вместо слушателя на каждом элементе: событие всплывает до предка, а `event.target.closest('.remove')` находит нужный элемент. Работает и для элементов, добавленных позже, и экономит память.

#more
Не всплывают `focus`, `blur`, `mouseenter`, `mouseleave`, `load`, `scroll` на элементах — для них `focusin`, `focusout`, `mouseover`, `mouseout` или фаза перехвата. `closest` нужно ограничивать контейнером, чтобы не найти кнопку снаружи. React подписывается на события у корня приложения, а не у каждого элемента.
::

::question
Что такое passive-слушатели и зачем они?

#answer
`{ passive: true }` — обещание не вызывать `preventDefault`. Браузер не ждёт обработчика перед прокруткой по `wheel` и `touchmove` и прокручивает сразу, без рывков от тяжёлого кода.

#more
`preventDefault` в passive-слушателе игнорируется, и браузер пишет предупреждение. На `window`, `document` и `body` слушатели `wheel`, `touchstart` и `touchmove` пассивны по умолчанию, поэтому для отмены прокрутки нужен явный `passive: false`. Часто вместо этого подходит CSS `touch-action` или `overscroll-behavior`.
::

::question
Как создать своё событие? Чем оно отличается от настоящего?

#answer
`new CustomEvent('cart:remove', { detail, bubbles: true, cancelable: true })` и `element.dispatchEvent(event)`. По умолчанию своё событие не всплывает. `dispatchEvent` выполняет слушателей синхронно и возвращает `false`, если событие отменили.

#more
У событий из кода `isTrusted` равен `false`, и браузер не выполняет для них часть действий: синтетический `keydown` не печатает символ, а действия, требующие участия пользователя, не разрешаются. Для выхода из Shadow DOM нужно `composed: true`. При `el.click()` микрозадачи выполняются после всех слушателей, а при настоящем клике — между ними.
::

::question
Почему после `innerHTML +=` перестали работать кнопки?

#answer
`innerHTML +=` читает содержимое строкой, добавляет новую разметку и разбирает всё заново. Старые узлы уничтожаются, а с ними — обработчики, состояние полей, фокус и ссылки на элементы из кода.

#more
Добавлять нужно, не трогая существующее: `append`, `insertAdjacentHTML('beforeend', …)`, `insertAdjacentElement`. Для замены всего содержимого — `replaceChildren`. Делегирование делает список устойчивым к пересозданию: слушатель висит на контейнере, который не меняется.
::

## Практика

::practice{title="Половина товаров не очистилась"}
Кнопка «Снять выделение» должна снять класс `selected` со всех товаров, но снимает примерно с половины:

```js
const selected = document.getElementsByClassName('selected');
for (let i = 0; i < selected.length; i++) {
  selected[i].classList.remove('selected');
}
```

#solution
`getElementsByClassName` возвращает живую коллекцию. Сняв класс с `selected[0]`, цикл убирает элемент из коллекции, второй элемент становится нулевым, а `i` уже равен 1 — и он пропущен. В проверке из пяти элементов класс сняли только у трёх. Берут снимок:

```js
for (const el of document.querySelectorAll('.selected')) {
  el.classList.remove('selected');
}
```

Или идут по живой коллекции, пока она не опустеет: `while (selected.length) selected[0].classList.remove('selected');`.
::

::practice{title="Кнопки перестали работать после добавления товара"}
После добавления товара в корзину перестают работать кнопки «удалить» у старых строк:

```js
document.querySelectorAll('.remove').forEach((btn) => btn.addEventListener('click', onRemove));

function addItem(item) {
  cart.innerHTML += `<li data-id="${item.id}">${item.name} <button class="remove">×</button></li>`;
}
```

#solution
`innerHTML +=` пересоздаёт все строки: старые кнопки уничтожены вместе со слушателями, новые — без них. В проверке кнопка после `innerHTML +=` перестала реагировать, а после `insertAdjacentHTML` — работала. Заодно в разметку попадает название товара как HTML — это XSS. Исправление — делегирование и создание узлов без разбора строк:

```js
cart.addEventListener('click', (e) => {
  const btn = e.target.closest('.remove');
  if (btn && cart.contains(btn)) removeFromCart(btn.closest('li').dataset.id);
});

function addItem(item) {
  const li = document.createElement('li');
  li.dataset.id = item.id;
  li.append(item.name, ' ');
  const btn = document.createElement('button');
  btn.className = 'remove';
  btn.textContent = '×';
  btn.setAttribute('aria-label', `Удалить ${item.name}`);
  li.append(btn);
  cart.append(li);
}
```
::

::practice{title="Что выведет?"}
Порядок вывода:

```js
console.log('sync');
setTimeout(() => console.log('setTimeout'), 0);
Promise.resolve().then(() => console.log('microtask'));
requestAnimationFrame(() => console.log('rAF'));
```

#solution
Первыми — `sync`, затем `microtask`: микрозадачи выполняются сразу после текущего скрипта. Дальше порядок `setTimeout` и `rAF` **не задан**: таймер — следующая задача, а `rAF` вызывается перед ближайшим кадром, и всё зависит от того, когда этот кадр наступит. В проверке в Chromium в разных прогонах выходило и `setTimeout → rAF`, и `rAF → setTimeout`. Если важно сделать что-то перед отрисовкой — `requestAnimationFrame`; если после — `requestAnimationFrame` и внутри `setTimeout`:

```js
requestAnimationFrame(() => {
  setTimeout(() => console.log('после отрисовки кадра'), 0);
});
```

Как кадр встроен в цикл событий — в [Event Loop](/content/javascript/event-loop).
::
