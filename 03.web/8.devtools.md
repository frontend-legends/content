# DevTools и профилирование

Chrome DevTools — инструменты, которыми разбирают, что происходит на странице: разметку и стили, консоль, отладчик, сеть, производительность, память. Спрашивают, как найти, кто меняет DOM, почему запрос медленный, где тормозит клик и чем logpoint отличается от `console.log`. Глубже — почему `console.log` показывает объект «из будущего», почему `debugger` в продакшене никого не останавливает и почему 70% неиспользованного CSS в Coverage — ещё не повод его удалять.

::tldr
- **DevTools — клиент Chrome DevTools Protocol.** Каждая панель — набор команд протокола; те же команды используют Playwright, Puppeteer и Lighthouse, и через них можно проверить всё, что показывает DevTools.
- **Свёрнутая строка в консоли — снимок на момент вызова, а раскрытый объект читается заново.** Утилиты `$0`, `$$`, `getEventListeners`, `copy` есть только в консоли, а не в коде страницы.
- **Точки останова бывают не только на строке:** условные, logpoint, на изменение DOM, на событие, на запрос, на исключения. `debugger` останавливает, только когда подключён отладчик.
- **Network показывает фазы запроса и умеет менять сеть:** задержка, блокировка запросов, отключение кеша, подмена ответов. «Ожидание ответа сервера» — время до первого байта.
- **Performance показывает долгие задачи и принудительные раскладки со стеком вызова;** записывают с замедлением процессора, потому что машина разработчика в разы быстрее телефона пользователя.
::

## Как DevTools разговаривает с браузером

Сквозной пример — страница корзины магазина чая: список товаров, кнопка «В корзину», запросы к `/api/cart`, скрипт аналитики.

Сам DevTools — веб-приложение, которое общается с браузером по **Chrome DevTools Protocol** (CDP): отправляет команды и получает события. Протокол поделён на домены:

| Панель | Домены протокола |
| --- | --- |
| Elements | `DOM`, `CSS`, `Overlay`, `DOMDebugger` |
| Console | `Runtime`, `Log` |
| Sources | `Debugger` |
| Network | `Network`, `Fetch` |
| Performance | `Tracing` |
| Memory | `HeapProfiler` |
| Coverage | `Profiler`, `CSS` |
| Rendering, Sensors | `Emulation`, `Overlay` |
| Application | `Storage`, `IndexedDB`, `CacheStorage`, `ServiceWorker` |

По тому же протоколу работают :term[Puppeteer]{def="библиотека для управления Chrome из Node.js через протокол DevTools"}, Playwright в Chromium и :term[Lighthouse]{def="инструмент Google, который проверяет страницу и ставит оценки производительности, доступности и SEO"}, а удалённая отладка Chrome на Android идёт через `chrome://inspect`. Все примеры этой главы проверены командами протокола в Chromium — ровно тем, что делает DevTools, когда нажимаешь кнопки. Как этим пользуются в тестах — в [E2E-тестировании](/content/testing-deploying/e2e-testing).

## Elements

Панель показывает живой DOM, а не исходный HTML: всё, что добавили скрипты, и то, как браузер исправил разметку.

- **Computed** — итоговые значения свойств и правило, которое победило в каскаде;
- **принудительное состояние** — `:hover`, `:focus`, `:active` без мыши. В проверке `CSS.forcePseudoState` с `hover` сменил фон кнопки на красный из правила `#buy:hover`, а снятие состояния вернуло синий;
- **Event Listeners** — слушатели элемента с флагами. В проверке у кнопки было два: `click` и `wheel` с `passive: true`;
- **Break on** — пауза, когда скрипт меняет поддерево, атрибуты или удаляет узел (подробно — ниже, в точках останова).

## Console

### Снимок и живой объект

```js
const cart = { items: 1 };
console.log(cart);
cart.items = 5;
```

Свёрнутая строка в консоли покажет `{items: 1}`, а раскрытый объект — `items: 5`. Свёрнутое превью снимается в момент вызова, а при раскрытии DevTools запрашивает свойства объекта заново. В проверке превью в событии консоли содержало `items: 1`, а запрос свойств того же объекта через `Runtime.getProperties` вернул 5. Чтобы зафиксировать состояние, логируют копию — `structuredClone(cart)` или `JSON.stringify(cart)` — или ставят точку останова.

### Методы console

| Метод | Что делает |
| --- | --- |
| `console.table(rows)` | массив объектов таблицей |
| `console.group()` и `groupEnd()` | сворачиваемая группа |
| `console.count(label)` | счётчик вызовов: в проверке — «клик: 1», «клик: 2» |
| `console.time(label)` и `timeEnd(label)` | длительность: «загрузка: … ms» |
| `console.assert(cond, msg)` | сообщение только при ложном условии: в проверке `assert(true)` ничего не вывел |
| `console.trace()` | стек вызова |
| `console.dir(el)` | элемент как объект, а не как разметка |

### Утилиты командной строки

В консоли есть функции, которых нет в коде страницы: `$0` — выбранный в Elements элемент, `$_` — результат последнего выражения, `$('sel')` и `$$('sel')` — `querySelector` и массив из `querySelectorAll`, `copy(value)` — в буфер обмена, `getEventListeners(el)`, `monitorEvents(el, 'click')`, `debug(fn)` — пауза при вызове функции, `queryObjects(Class)` — все экземпляры класса. Их подставляет консоль при вычислении выражения: в проверке `getEventListeners` и `$$` работали в `Runtime.evaluate` с `includeCommandLineAPI`, а без него и в коде страницы были `undefined`. Скрипт, который «работал в консоли», в приложении упадёт.

**Live expressions** — выражение, которое консоль пересчитывает постоянно: например, `document.activeElement`, чтобы видеть, куда уходит фокус.

## Sources: точки останова

| Точка | Когда останавливает |
| --- | --- |
| на строке | при выполнении строки |
| условная | строка и условие истинно |
| logpoint | не останавливает, а пишет в консоль |
| DOM: subtree, attributes, removal | скрипт меняет поддерево, атрибуты или удаляет узел |
| слушатель события | вызов слушателя `click`, `keydown`, таймера и других |
| XHR и fetch | запрос, адрес которого содержит строку |
| исключения | брошено неперехваченное или любое исключение |
| `debugger` в коде | отладчик подключён |

В проверке каждая точка сработала со своей причиной в событии `Debugger.paused`:

- **условная** `qty > 10` на строке `addToCart` не остановила вызов с `qty = 1` и остановила с `qty = 20`. На паузе выражение `qty`, вычисленное в кадре, вернуло 20 — так работают панели Scope и Watch;
- **logpoint** — через протокол это условная точка с условием `console.log('qty =', qty), false`: `console.log` пишет, а `false` отменяет паузу. В проверке паузы не было, а в консоли появилось «qty = 3». В отличие от `console.log` в коде, logpoint не требует пересборки и не попадёт в коммит;
- **DOM** — добавление `li` в список остановило с причиной `DOM` и типом `subtree-modified`, а стек показывает, чей код это сделал;
- **слушатель события** `click` — причина `EventListener`, событие `listener:click`;
- **fetch** с адресом `/api/cart` — причина `XHR`;
- **исключения**: перехваченный `SyntaxError` из `JSON.parse` в режиме «неперехваченные» паузу не вызвал, а в режиме «все» — вызвал.

`debugger` в коде — обычная инструкция, которая ничего не делает, пока отладчик не подключён: в проверке без `Debugger.enable` функция с `debugger` выполнилась до конца, а с ним — остановилась. Поэтому забытый `debugger` в продакшене останавливает только тех, у кого открыт DevTools, и его вычищают правилом линтера `no-debugger`.

Минифицированный код читают через :term[source maps]{def="карты, которые связывают собранный и сжатый код с исходниками для отладки"}, а библиотеки скрывают из стека списком игнорирования (Ignore list) — подробно об этом и об ошибках из продакшена в [Отладке и source maps](/content/advanced-tooling/devtools-and-debugging).

## Network

### Водопад

Каждый запрос раскладывается на фазы:

| Фаза | Что происходит |
| --- | --- |
| Queueing, Stalled | ждёт очереди: лимит соединений, приоритет |
| DNS Lookup | поиск IP |
| Initial connection, SSL | TCP и TLS |
| Request sent | отправка запроса |
| Waiting for server response | от отправки до первого байта ответа — TTFB |
| Content Download | загрузка тела |

В проверке сервер, задумавшийся на 300 мс, дал в данных запроса не меньше 290 мс между концом отправки и началом заголовков ответа — это и есть «Waiting for server response». Большое ожидание — проблема сервера, долгая загрузка тела — размер ответа, длинные Queueing и Stalled — слишком много запросов сразу. Как устроены соединения и протоколы — в главе про сеть.

### Изменить сеть

- **Throttling** — задержка и пропускная способность. В проверке запрос без замедления занял меньше 200 мс, а с задержкой 400 мс — не меньше 400;
- **Block request URL** — проверить, что страница переживёт отказ скрипта аналитики или CDN. В проверке `fetch` заблокированного `/analytics.js` упал с «Failed to fetch», а протокол указал причину блокировки — `inspector`;
- **Disable cache** — каждый запрос идёт на сервер. В проверке картинка с `max-age` второй раз пришла из кеша, а с отключённым кешем оба запроса дошли до сервера;
- **Overrides** — подменить ответ или заголовки без бэкенда. В проверке подменённый ответ `/api/cart` вернул `{ items: 0 }` вместо настоящего;
- **Copy as fetch / cURL** — повторить запрос из кода или терминала с теми же заголовками.

## Performance

Запись показывает, чем был занят основной поток. Перед записью включают **замедление процессора**: в проверке одна и та же работа с замедлением в 4 раза шла не меньше чем в 2,5 раза дольше. Машина разработчика быстрее бюджетного телефона в разы, и без замедления проблемы не видны.

Как читать запись:

- **задачи** длиннее 50 мс помечены красным углом — это долгие задачи, которые задерживают ввод. В проверке синхронная работа на 120 мс дала в трейсе задачу не короче 100 мс;
- **цвета** — жёлтый скрипт, фиолетовые стили и раскладка, зелёная отрисовка;
- **принудительная раскладка** (Forced reflow) — раскладка внутри скрипта со ссылкой на код. В трейсе у каждой такой записи `Layout` есть стек вызова: в проверке полсотни раскладок указывали на функцию `resizeAll`, которая в цикле читала `offsetHeight` после записи высоты. Почему это дорого и как исправить — в [Рендеринге](/content/web/rendering);
- **Bottom-up и Call tree** — где ушло время по функциям;
- **живые метрики** — LCP, CLS и INP прямо во время работы со страницей; как браузер их считает — в [Измерении Core Web Vitals](/content/web/core-web-vitals).

Для React есть Profiler в React DevTools — он показывает рендеры компонентов, а не задачи браузера (подробно — в [Производительности React](/content/reactjs/performance)).

## Rendering, Coverage и остальное

**Rendering** — подсветка перерисованных областей (Paint flashing), областей сдвигов макета (Layout Shift Regions), границ слоёв, а также эмуляция медиа: тёмная тема, `prefers-reduced-motion`, печать, нарушения цветового зрения. В проверке после эмуляции `matchMedia('(prefers-color-scheme: dark)')` и `matchMedia('(prefers-reduced-motion: reduce)')` вернули `true`.

**Coverage** — сколько загруженного JS и CSS выполнилось. В проверке функция `unused` получила 0 вызовов, а `used` — 1; из CSS использованными оказались только `.used` и `#buy`, а `.unused` и `#buy:hover` — нет. Отсюда главная оговорка: `#buy:hover` не использован, пока никто не навёл мышь. Coverage показывает, что не нужно **при первой загрузке**, — повод разделить код и загрузить остальное позже, а не удалить.

**Memory** — снимки кучи и поиск утечек (подробно — в [Памяти и производительности](/content/javascript/memory-and-performance)). **Application** — хранилища, cookie, Service Worker и манифест (подробно — в [Хранилищах](/content/network-api/storage) и [PWA](/content/web/pwa)). **Lighthouse** — лабораторный аудит (подробно — в [Измерении и мониторинге](/content/security-perfomance/measuring-and-monitoring)).

## Красные флаги в ответе

- **«`console.log` показывает состояние на момент вызова».** Только свёрнутое превью; раскрытый объект читается в момент раскрытия.
- **«Отлаживаю только через `console.log`».** Logpoint, условные точки и точки на DOM, события и запросы находят причину без правок кода.
- **«`debugger` в проде остановит всех пользователей».** Он срабатывает, только когда подключён отладчик.
- **«Профилирую на своём ноутбуке без замедления».** Проблемы бюджетных телефонов так не видны.
- **«Coverage показал 70% неиспользованного CSS — удалю».** Это неиспользованное при текущем сценарии; `:hover`, модальные окна и другие страницы его используют.
- **«`$$` и `copy` можно использовать в коде».** Это утилиты консоли, в коде страницы их нет.

## Как спрашивают на собеседовании

::question
Как найти, какой код меняет элемент на странице?

#answer
В Elements на элементе выбрать Break on — subtree modifications, attribute modifications или node removal. Когда скрипт изменит элемент, отладчик остановится, и в Call Stack будет видно, чей код это сделал.

#more
Если меняют стили — точка на attribute modifications ловит и `el.style`, и `classList`: в проверке оба изменения остановили выполнение. Для событий — точки на слушатели событий в Sources. Если элемент меняет библиотека, её скрывают списком игнорирования, чтобы стек показывал свой код. Через протокол это `DOMDebugger.setDOMBreakpoint`, и пауза приходит с причиной `DOM`.
::

::question
Почему console.log показывает не то значение объекта?

#answer
Свёрнутое превью снимается в момент вызова, а при раскрытии DevTools запрашивает свойства заново. Если объект изменили после `console.log`, раскрытый объект покажет новое значение.

#more
Чтобы увидеть состояние на момент вызова, логируют копию — `structuredClone(obj)` или `JSON.stringify(obj)` — или ставят точку останова и смотрят Scope. Возле раскрытого объекта DevTools показывает значок, что значение вычислено только что.
::

::question
Какие бывают точки останова?

#answer
На строке, условные, logpoint, на изменение DOM, на слушатели событий, на XHR и fetch по части адреса, на исключения — перехваченные или все, и инструкция `debugger` в коде. Плюс `debug(fn)` в консоли — пауза при вызове функции.

#more
Logpoint пишет в консоль без паузы и без правки кода; через протокол это условная точка с условием `console.log(…), false`. На паузе в Scope видны переменные, в Watch — выражения, а в консоли можно вычислить любое выражение в контексте кадра. `debugger` срабатывает, только если отладчик подключён.
::

::question
Как понять, почему запрос медленный?

#answer
В Network открыть Timing запроса. Длинный Queueing или Stalled — очередь из-за лимита соединений и приоритетов; долгие DNS, connection и SSL — новое соединение; долгое Waiting for server response — медленный сервер; долгий Content Download — большой ответ.

#more
Для времени на сервере помогает заголовок `Server-Timing`, он виден в той же вкладке. Проверить поведение на медленной сети — Throttling; без кеша — Disable cache; при падении стороннего ресурса — Block request URL. Initiator показывает, кто вызвал запрос.
::

::question
Как найти, почему тормозит клик?

#answer
Включить замедление процессора в 4–6 раз, записать Performance, кликнуть и найти задачу с красным углом. Внутри — какие функции заняли время, есть ли принудительные раскладки и долгая отрисовка после обработчика.

#more
Bottom-up показывает, какие функции дорогие суммарно. Принудительная раскладка отмечена предупреждением со ссылкой на строку. Живая метрика INP в Performance показывает задержку взаимодействия и её фазы. Для React — ещё React Profiler: он показывает, какие компоненты перерендерились.
::

::question
Что показывает Coverage и как им пользоваться?

#answer
Сколько байт загруженного JS и CSS выполнилось или применилось с начала записи. Красным — неиспользованное. Помогает найти код, который не нужен при первой загрузке, и вынести его в отдельные чанки.

#more
Неиспользованное при одном сценарии не значит лишнее: `:hover`, модальные окна, другие маршруты используют свой код. Запись начинают с перезагрузки, чтобы учесть загрузку страницы. Удаляют только то, что не нужно ни в каком сценарии, — это лучше проверять анализатором бандла.
::

## Практика

::practice{title="В логе корзина уже пустая"}
Разработчик ищет, почему корзина очищается, и логирует её перед отправкой. В консоли в раскрытом объекте `items` уже пустой массив, хотя очистка идёт после отправки:

```js
console.log('перед отправкой', cart);
await sendOrder(cart);
cart.items = [];
```

#solution
Раскрытый объект в консоли читается в момент раскрытия, а не вызова `console.log`. В проверке свёрнутое превью показало старое значение, а запрос свойств — новое. Логируют копию или останавливаются:

```js
console.log('перед отправкой', structuredClone(cart));
```

Или ставят logpoint на строке с `sendOrder` с выражением `JSON.stringify(cart)` — без правки кода. Ещё лучше — точка останова на этой строке и Scope: видно всё состояние на момент вызова.
::

::practice{title="Кто-то удаляет товары из списка"}
Иногда из списка корзины пропадают строки. В коде корзины удаление есть только по кнопке, но строки пропадают и без неё. Как найти виновника?

#solution
В Elements на `ul` списка — Break on, subtree modifications. При следующем удалении отладчик остановится на коде, который меняет список, и Call Stack покажет цепочку вызовов. В проверке изменение поддерева остановило выполнение с причиной `DOM` и типом `subtree-modified`. Через протокол то же самое:

```js
await cdp.send('DOMDebugger.setDOMBreakpoint', { nodeId, type: 'subtree-modified' });
```

Если в стеке только код библиотеки, её добавляют в список игнорирования, и стек показывает, какой свой вызов к этому привёл. Виновником может оказаться повторный рендер с устаревшими данными или сторонний виджет, который перерисовывает контейнер.
::

::practice{title="Изменение размеров списка тормозит"}
На телефонах при раскрытии корзины интерфейс замирает. Как найти причину в Performance и что, скорее всего, будет в записи для такого кода?

```js
function resizeAll() {
  for (const li of document.querySelectorAll('#cart li')) {
    li.style.height = `${li.offsetHeight + 1}px`;
  }
}
```

#solution
Включить замедление процессора, записать раскрытие корзины и найти задачу с красным углом. Внутри будут десятки фиолетовых `Layout` с предупреждением Forced reflow и ссылкой на `resizeAll`. В проверке на 50 строк трейс содержал полсотни раскладок, и у каждой в стеке была `resizeAll`. Чтение `offsetHeight` после записи высоты заставляет браузер пересчитывать раскладку на каждой итерации. Сначала все чтения, потом все записи:

```js
function resizeAll() {
  const items = [...document.querySelectorAll('#cart li')];
  const heights = items.map((li) => li.offsetHeight);
  items.forEach((li, i) => { li.style.height = `${heights[i] + 1}px`; });
}
```

Почему так работает конвейер — в [Рендеринге](/content/web/rendering).
::
