# Транспиляция

**Транспиляция** - превращение кода из одного варианта JS/синтаксиса в другой: TypeScript → JS, JSX → JS, новый ES → старый ES. Без неё браузер не понял бы ни типы, ни JSX, ни свежий синтаксис. Понимать разницу между транспиляцией и полифилами - частый вопрос.

---

## Что это и зачем

Транспайлер - это **source-to-source компилятор**: на вход исходник, на выход - другой исходник (а не машинный код). Нужен для трёх задач:

- **Расширения языка:** TypeScript, JSX, `.vue` - синтаксис, которого нет в JS, превращается в обычный JS.
- **Совместимость:** новый синтаксис (`async/await`, опциональная цепочка, decorators) «опускается» (lowering) до того, что понимают старые браузеры.
- **Цель платформы:** один код - сборки под разные уровни поддержки браузеров.

---

## Как работает

Под капотом у всех транспайлеров один конвейер:

```
Исходный код
   ▼ 1. Parse    → построить AST (абстрактное синтаксическое дерево)
   ▼ 2. Transform → менять узлы AST (JSX→вызовы, async→генераторы, убрать типы)
   ▼ 3. Generate → сгенерировать новый код из изменённого AST
Выходной JS
```

**AST** - дерево-представление кода. Все трансформации (и линтеры, и кодмоды) работают именно над ним, а не над текстом.

## Транспиляция vs полифил

Критически важное различие, которое путают.

| | Транспиляция | Полифил |
|--|--------------|---------|
| Что чинит | **синтаксис** | **отсутствующие API/методы** |
| Примеры | `=>`, `async/await`, `?.`, JSX | `Promise`, `Array.prototype.flat`, `fetch`, `Object.groupBy` |
| Как | переписать код | добавить реализацию в рантайм |
| Цена | размер кода | размер кода + рантайм |

```js
// Транспиляция СИНТАКСИСА: arrow → function
const f = () => 1;        →   var f = function () { return 1; };

// Полифил API: метода нет в старом браузере → подкладываем реализацию
[1, [2]].flat();          →   нужен полифил Array.prototype.flat (из core-js)
```

<b class="text-on-semi-light">Суть</b> - <span class="text-gray">Транспайлер переписывает **синтаксис**, но не может «дописать» отсутствующий метод - для этого нужен **полифил** (готовый код, обычно из **core-js**), добавляемый в бандл. `@babel/preset-env` умеет подключать нужные полифилы автоматически по targets.</span>

## Targets и browserslist

Сколько транспилировать - зависит от того, **какие браузеры** поддерживаем. Это задаётся **browserslist** (`.browserslistrc` или поле в `package.json`):

```
> 0.5%
last 2 versions
not dead
```

Чем старее цель - тем больше lowering и полифилов (больше бандл). Чем современнее - тем меньше трансформаций (меньше вес). Browserslist читают и Babel (preset-env), и Autoprefixer, и Lightning CSS.

## Инструменты

| Транспайлер | Язык | Скорость | Проверяет типы | Где |
|-------------|------|----------|----------------|-----|
| **Babel** | JS | медленный | нет | классика, огромная экосистема плагинов |
| **SWC** | Rust | быстрый | нет | Next.js, Jest, замена Babel |
| **esbuild** | Go | очень быстрый | нет | Vite, трансформы |
| **tsc** | JS | медленный | **да** | проверка типов (+ может эмитить) |

### Babel

Классический транспайлер с архитектурой **пресетов и плагинов**: `@babel/preset-env` (lowering по targets + полифилы), `preset-react` (JSX), `preset-typescript` (срезать типы). Гибкий, но медленный (на JS). Огромная экосистема.

### SWC и esbuild

**SWC** (Rust) и **esbuild** (Go) делают то же, но **в разы быстрее**. SWC почти совместим с Babel и используется в Next.js. esbuild - внутри Vite. Цена скорости - меньше плагинов, чем у Babel.

---

## Главная ловушка: они НЕ проверяют типы

esbuild, SWC и Babel **срезают** типы TypeScript, но **не проверяют** их - просто выкидывают аннотации.

```ts
const x: number = "строка"; // esbuild/SWC СОБЕРУТ это без ошибки - типы не проверяются!
```

<b class="text-on-semi-light">Следствие</b> - <span class="text-gray">Быстрая сборка (Vite/SWC) не ловит ошибки типов - она лишь удаляет аннотации. Проверку типов запускают **отдельно** через `tsc --noEmit` (обычно в IDE и CI). Это разделение - тема [тулинга TypeScript](/content/advanced-tooling/typescript-tooling).</span>

---

## AST и кодмоды

Раз трансформации идут по AST, тем же способом делают **codemods** - автоматические массовые правки кода (миграция API библиотеки, переименование). Инструменты: **jscodeshift**, ts-morph. Полезно при больших рефакторингах и обновлениях мажорных версий.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое транспиляция?</b>
<span class="text-gray">Source-to-source компиляция: TS→JS, JSX→JS, новый синтаксис→старый. Через парсинг в AST, трансформацию узлов и генерацию кода. Нужна для расширений языка и совместимости.</span>

<b class="text-on-semi-light">Чем транспиляция отличается от полифила?</b>
<span class="text-gray">Транспиляция переписывает синтаксис (arrow, async, JSX). Полифил добавляет в рантайм реализацию отсутствующего API/метода (Promise, Array.flat) - переписать его нельзя, нужен готовый код (core-js).</span>

<b class="text-on-semi-light">Чем SWC/esbuild отличаются от Babel?</b>
<span class="text-gray">Делают то же (транспиляция), но на Rust/Go - в разы быстрее. Цена - меньше плагинов. Babel гибче за счёт огромной экосистемы.</span>

<b class="text-on-semi-light">Почему быстрая сборка не ловит ошибки типов?</b>
<span class="text-gray">esbuild/SWC/Babel срезают типы, но не проверяют их - просто удаляют аннотации. Проверка типов делается отдельно через `tsc --noEmit`.</span>

<b class="text-on-semi-light">Что определяет, насколько сильно транспилировать код?</b>
<span class="text-gray">Browserslist (targets) - список поддерживаемых браузеров. Старее цель → больше lowering и полифилов → больше бандл; современнее → меньше трансформаций.</span>
