# Модульные системы

Модули глазами инструментов: как `import 'pkg'` находит файл, что делает поле `exports` в `package.json` и его условия, как Node.js решает, ESM перед ним или CommonJS, как форматы импортируют друг друга, что такое двойной пакет и почему бандлер и Node.js по-разному понимают `default`. Спрашивают, чем ESM отличается от CommonJS, как импорт находит пакет и в чём боль совместимости. Глубже — почему глубокий импорт перестал работать после обновления пакета, почему `instanceof` не срабатывает между двумя копиями библиотеки и почему импорт CommonJS даёт объект вместо функции.

::tldr
- **Голый импорт `'pkg'` ищется в `node_modules` вверх по папкам,** а файл внутри пакета выбирает поле `exports` в `package.json` — или старое `main`, если `exports` нет.
- **`exports` — публичный API пакета:** всё, что не перечислено, импортировать нельзя (`ERR_PACKAGE_PATH_NOT_EXPORTED`). Условия `import`, `require`, `browser`, `types`, `default` выбирают файл под окружение, и побеждает первое подходящее.
- **Формат файла решают расширение и поле `"type"`:** `.mjs` — всегда ESM, `.cjs` — всегда CommonJS, `.js` — по `"type"` ближайшего `package.json`.
- **ESM импортирует CommonJS: `default` — это весь `module.exports`,** а именованные экспорты Node.js находит статическим анализом и пропускает созданные динамически. CommonJS загружает ESM через `require(esm)`, если в нём нет top-level await.
- **Двойной пакет с ESM- и CommonJS-версией может загрузиться дважды:** две копии модуля, два класса, два состояния. Бандлеры, в отличие от Node.js, учитывают флаг `__esModule`, и один импорт даёт в них разный результат.
::

## Модули как язык и как инструменты

Сами форматы — ES-модули с их статической структурой и живыми привязками, CommonJS с `require`, циклы, динамический `import()` и top-level await — разобраны в [Модулях](/content/javascript/modules). Коротко: ESM — стандарт языка, `import` и `export` статичны, а `require` в CommonJS — обычная функция, которую можно вызвать где угодно.

Здесь — другая сторона: язык не говорит, **где лежит** модуль `'vue'` и **какой файл** взять из пакета. Это решают окружение и инструменты: Node.js, бандлер, TypeScript. И именно здесь ломаются сборки.

Сквозной пример — пакет `price-kit`, который приложение импортирует так:

```js
import { Money } from 'price-kit';
import { format } from 'price-kit/format';
```

Все утверждения ниже проверены на Node.js 24 и Rolldown с настоящими пакетами во временной папке.

## Как импорт находит пакет

Для **относительного** импорта (`./price.js`) путь считается от текущего файла. Для **голого** (`'price-kit'`) — алгоритм Node.js, который повторяют бандлеры и TypeScript:

1. Искать папку `node_modules/price-kit` рядом с файлом, затем в родительской папке и выше до корня диска.
2. Прочитать `package.json` пакета.
3. Если есть `exports` — выбрать файл по нему. Если нет — взять `main`, а если нет и его — `index.js`.

Поиск вверх по папкам объясняет многое в монорепо: пакет, установленный в корне, виден всем вложенным проектам, а «призрачная» зависимость, не указанная в `package.json`, работает, пока её случайно не перестанут ставить в корень. pnpm с изолированными `node_modules` такие зависимости запрещает (подробно — в [Управлении пакетами](/content/ecosystem-libs/package-management)).

### Поле exports

```json
{
  "name": "price-kit",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/esm/index.js",
      "require": "./dist/cjs/index.cjs"
    },
    "./format": "./dist/esm/format.js",
    "./package.json": "./package.json"
  }
}
```

`exports` делает две вещи.

**Ограничивает доступ.** Импортировать можно только перечисленные пути. `import 'price-kit/dist/esm/internal.js'` даёт `ERR_PACKAGE_PATH_NOT_EXPORTED` — в проверке так и вышло. Поэтому обновление библиотеки на `exports` ломает код, который полагался на глубокие импорты: внутренние файлы перестали быть API.

**Выбирает файл по условиям.** В проверке один и тот же пакет через `import` отдал ESM-версию, а через `require` — CommonJS. Основные условия:

| Условие | Когда срабатывает |
| --- | --- |
| `types` | TypeScript ищет объявления типов, ставится первым |
| `import` | загрузка через `import` |
| `require` | загрузка через `require` |
| `browser` | сборка для браузера бандлером |
| `node` | Node.js |
| `development`, `production` | режим, если инструмент их поддерживает — Vite поддерживает |
| `default` | запасной вариант, ставится последним |

Условия проверяются **по порядку записи**, и побеждает первое подходящее. Поэтому `default` всегда последний, а `types` — первый.

### Формат файла

Node.js решает, ESM перед ним или CommonJS, не по содержимому, а по имени и `package.json`:

- `.mjs` — всегда ESM, `.cjs` — всегда CommonJS;
- `.js` — по полю `"type"` ближайшего `package.json`: `"module"` — ESM, `"commonjs"` или отсутствие поля — CommonJS.

В ESM нет `require`, `module`, `__dirname`: в проверке `typeof require` в `.js` при `"type": "module"` дал `undefined`. Вместо них — `import.meta.url`, `import.meta.dirname` и `createRequire`.

TypeScript повторяет эти правила в режиме `moduleResolution: nodenext`, а в режиме `bundler` — правила сборщиков (подробно — в [Настройке проекта TypeScript](/content/typescript/project-setup)).

Файл найден. Но если пакет в одном формате, а приложение — в другом?

## Совместимость форматов

### ESM импортирует CommonJS

```js
// legacy/index.js — CommonJS
exports.add = (a, b) => a + b;
module.exports.version = '1.0';
Object.assign(exports, { dynamicName: 1 });
```

```js
import legacy, { add, version } from 'legacy';
```

- **`default`** — это `module.exports` целиком: `legacy.add` работает;
- **именованные экспорты** Node.js находит **статическим анализом** исходника: `exports.add = …` и `module.exports.version = …` распознаются, а `dynamicName`, добавленный через `Object.assign`, — нет. В проверке `dynamicName` в пространстве имён не оказалось.

Отсюда ошибка «does not provide an export named», когда библиотека собирает экспорты динамически. Обходной путь — импорт по умолчанию и деструктуризация: `import pkg from 'legacy'; const { dynamicName } = pkg;`.

### CommonJS загружает ESM

Раньше CommonJS-код не мог загрузить ESM синхронно — только через `await import()`. Это и было главной болью перехода на ESM. Теперь `require(esm)` работает во всех поддерживаемых версиях Node.js:

```js
const m = require('esm-only');   // { __esModule: true, default: [Function], named: 1 }
```

`require` возвращает **пространство имён** модуля, и Node.js добавляет к нему `__esModule: true`, чтобы старый код, рассчитанный на скомпилированный ESM, правильно понял `default`. Ограничение одно: если в модуле есть **top-level await**, синхронно его не загрузить, и `require` бросит `ERR_REQUIRE_ASYNC_MODULE`. Оба случая проверены. Поэтому библиотеки всё чаще публикуются только в ESM — так поступили Babel 8, Pinia 4 и многие другие.

### Флаг __esModule

Когда ESM-код компилируют в CommonJS (TypeScript, Babel), `export default` превращается в `exports.default = …`, и рядом ставится флаг `exports.__esModule = true`. Инструменты понимают его по-разному:

```js
import greet from 'compiled';   // compiled — CommonJS с __esModule и exports.default
```

- **Node.js флаг игнорирует:** `greet` — это весь `module.exports`, объект, а функция лежит в `greet.default`;
- **бандлеры исторически флаг учитывают:** `greet` — сама функция `exports.default`. Так ведут себя webpack, esbuild и Rolldown, если их не настраивать;
- **Vite 8 выбирает по импортирующему файлу:** если он ESM по расширению `.mjs` или полю `"type": "module"`, `default` — весь `module.exports`, как в Node.js, иначе — `exports.default`.

В проверке Node.js дал объект, Rolldown — функцию, а Vite 8 — объект в проекте с `"type": "module"` и функцию без него. Это классическое «в сборке работает, в тестах на Node.js — `greet is not a function`», или наоборот. При переходе на Vite 8 часть таких импортов начала давать объект вместо функции, и временно вернуть старое поведение можно опцией `legacy.inconsistentCjsInterop`.

## Двойной пакет

Чтобы поддержать и ESM, и CommonJS, библиотека публикует две сборки и выбирает их условиями `import` и `require`. Если в одном приложении пакет загрузят **обоими способами** — один модуль через `import`, другой через `require`, — это **две разные копии** модуля:

```js
import { Money as M1 } from 'price-kit';              // ESM-версия
const { Money: M2 } = require('price-kit');           // CommonJS-версия

M1 === M2;                       // false
new M1() instanceof M2;          // false
```

В проверке так и вышло. Последствия — два экземпляра состояния (два стора, два реестра плагинов), сломанный `instanceof`, двойной размер в бандле. Это называют **dual package hazard**.

Как избегают:

- публиковать **только ESM** — теперь, с `require(esm)`, это работает и для CommonJS-потребителей;
- держать состояние в одном файле, а вторую сборку делать тонкой обёрткой над ним;
- в приложении — следить, чтобы библиотеку загружали одним способом, и проверять бандл на дубли (подробно — в [Оптимизации](/content/advanced-tooling/optimization)).

## Модули в браузере

Браузер понимает ES-модули через `<script type="module">`, но не понимает голые импорты: `import 'vue'` без подсказки даст ошибку. Подсказка — **import map**:

```html
<script type="importmap">
{ "imports": { "vue": "https://cdn.jsdelivr.net/npm/vue@3.5.45/dist/vue.esm-browser.prod.js" } }
</script>
<script type="module">import { createApp } from 'vue';</script>
```

Import map сопоставляет голые имена с адресами. Это позволяет обойтись без сборки в маленьких проектах и прототипах. В больших приложениях сборка всё равно выигрывает: меньше запросов, tree shaking, минификация.

**UMD** — старый формат, который работал и как CommonJS, и как AMD, и как глобальная переменная через `<script>`. Его ещё публикуют для подключения через CDN без сборки, но для новых библиотек он не нужен.

## Красные флаги в ответе

- **«`import 'pkg'` берёт файл из поля `main`».** Если есть `exports`, решает оно, а `main` игнорируется.
- **«Любой файл пакета можно импортировать по пути».** `exports` закрывает всё, что не перечислено.
- **«Формат определяется по синтаксису файла».** По расширению и полю `"type"` ближайшего `package.json`.
- **«CommonJS не может загрузить ESM».** `require(esm)` работает, если в модуле нет top-level await.
- **«`import x from 'cjs'` везде даёт одно и то же».** Node.js игнорирует `__esModule`, многие бандлеры учитывают, Vite 8 смотрит на формат импортирующего файла.

## Как спрашивают на собеседовании

::question
Чем ESM отличается от CommonJS с точки зрения инструментов?

#answer
`import` и `export` в ESM статичны, поэтому граф зависимостей известен до выполнения: бандлер может выбросить неиспользуемое и разбить код на чанки. `require` в CommonJS — функция, её результат известен только при выполнении.

#more
Node.js различает форматы по расширению и полю `"type"`, а не по синтаксису. В ESM нет `require` и `__dirname`, есть `import.meta`. Совместимость в обе стороны: ESM импортирует CommonJS с `default` = `module.exports`, а CommonJS загружает ESM через `require(esm)`. Подробности языка — в [Модулях](/content/javascript/modules).
::

::question
Как import 'lib' находит пакет?

#answer
Ищет папку `node_modules/lib` рядом с файлом, потом в родительских папках до корня. В найденном пакете читает `package.json`: если есть `exports`, выбирает файл по нему и условиям, иначе берёт `main` или `index.js`.

#more
Бандлеры и TypeScript в режиме `bundler` повторяют этот алгоритм и добавляют свои условия, например `browser` и `development`. Поиск вверх по папкам даёт «призрачные» зависимости в монорепо, а pnpm с изолированными `node_modules` их запрещает. В браузере без сборки голые имена сопоставляет import map.
::

::question
Зачем поле exports в package.json?

#answer
Оно задаёт публичный API пакета и выбирает файл под окружение. Импортировать можно только перечисленные пути, остальное даёт `ERR_PACKAGE_PATH_NOT_EXPORTED`. Условия `import`, `require`, `types`, `browser`, `default` отдают разные файлы для разных потребителей.

#more
Условия проверяются по порядку, побеждает первое подходящее: `types` ставят первым, `default` — последним. Обновление библиотеки на `exports` ломает глубокие импорты внутренних файлов. Для доступа к самому `package.json` его тоже перечисляют в `exports`.
::

::question
В чём проблема совместимости ESM и CommonJS?

#answer
При импорте CommonJS из ESM `default` — весь `module.exports`, а именованные экспорты Node.js находит статическим анализом и пропускает динамические. Бандлеры и Node.js по-разному понимают флаг `__esModule`, поэтому `import x from 'cjs'` даёт в них разное.

#more
Раньше CommonJS не мог синхронно загрузить ESM — теперь есть `require(esm)`, кроме модулей с top-level await. Двойные пакеты с ESM- и CommonJS-версией могут загрузиться дважды. Индустрия движется к пакетам только в ESM.
::

::question
Что такое dual package hazard?

#answer
Пакет публикует ESM- и CommonJS-версию, и в одном приложении его загружают обоими способами. Получаются две копии модуля: два класса, два состояния, `instanceof` между ними не работает.

#more
Проявляется как два экземпляра стора или реестра, ошибки «не тот экземпляр» и дубли в бандле. Решения — публиковать только ESM, держать состояние в одном файле и делать вторую сборку обёрткой, а в приложении загружать библиотеку одним способом.
::

::question
Почему импорт по умолчанию из CommonJS дал объект вместо функции?

#answer
Пакет собран из ESM в CommonJS: функция лежит в `exports.default`, а рядом флаг `__esModule`. Node.js этот флаг игнорирует и отдаёт как `default` весь `module.exports` — объект с полем `default`.

#more
Многие бандлеры флаг учитывают и отдают саму функцию, поэтому код работает в сборке и падает в Node.js — например, в тестах или при SSR. Vite 8 в ESM-проекте ведёт себя как Node.js. Решения — использовать ESM-версию пакета, обновить пакет до публикации в ESM или явно брать `.default`.
::

## Практика

::practice{title="Глубокий импорт сломался после обновления"}
После обновления библиотеки сборка падает:

```js
import { formatMoney } from 'price-kit/dist/utils/format.js';
// Error [ERR_PACKAGE_PATH_NOT_EXPORTED]: Package subpath './dist/utils/format.js' is not defined by "exports"
```

#solution
В новой версии у пакета появилось поле `exports`, и всё, что в нём не перечислено, стало закрытым. Глубокий путь был внутренней деталью, а не API.

```js
import { formatMoney } from 'price-kit/format';   // путь из exports
```

Нужно найти публичный путь в `package.json` пакета или в его документации. Если нужной функции в публичном API нет, правильно попросить автора добавить её, а до тех пор — зафиксировать версию или временно пропатчить пакет (подробно — в [Сборке и патчинге](/content/ecosystem-libs/building-and-patching)). В проверке импорт внутреннего файла дал `ERR_PACKAGE_PATH_NOT_EXPORTED`, а путь из `exports` сработал.
::

::practice{title="В тестах greet is not a function"}
Приложение собирается и работает, а тест в Node.js падает:

```js
import greet from 'greeting-lib';   // CommonJS, собран из ESM
greet('Аня');
// TypeError: greet is not a function
```

#solution
`greeting-lib` — CommonJS с `exports.default = function …` и флагом `__esModule`. Бандлер приложения учитывает флаг и отдаёт функцию. Тест выполняется в Node.js, который флаг игнорирует: `greet` — весь `module.exports`, а функция в `greet.default`. Та же ошибка появится и в сборке после перехода на Vite 8 в проекте с `"type": "module"`.

```js
import * as lib from 'greeting-lib';
const greet = lib.default?.default ?? lib.default;   // работает в обоих окружениях
```

Лучше — избавиться от расхождения: взять ESM-версию пакета, если она есть, или настроить тест-раннер обрабатывать зависимость так же, как бандлер. В проверке Node.js отдал объект, Rolldown — функцию, Vite 8 в ESM-проекте — объект.
::
