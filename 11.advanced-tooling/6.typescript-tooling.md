# Тулинг TypeScript

Главное, что нужно понять про TypeScript в сборке: **проверка типов и транспиляция - это две разные задачи**, и современные сборки их разделяют. На этом разделении строятся быстрые билды, и про него спрашивают на собесе.

> Сам язык типов (generics, utility types) - в главе [TypeScript](/content/typescript). Здесь - **инструментальный** угол: как TS встраивается в конвейер.

---

## Две роли tsc

Компилятор `tsc` умеет две вещи:

1. **Проверять типы** (type-checking) - анализирует всю программу и находит ошибки типов.
2. **Эмитить JS** (transpile) - срезает типы и выдаёт JavaScript.

Исторически `tsc` делал и то, и другое. Но проверка типов **медленная** (нужен анализ всей программы целиком), а транспиляция должна быть быстрой.

---

## Современное разделение

Поэтому сегодня роли **разводят**:

```
Транспиляция (быстро, пофайлово)  → esbuild / SWC  → срезают типы, выдают JS
Проверка типов (медленно, целиком) → tsc --noEmit   → только проверяет, не эмитит
```

- **Сборка** (Vite/Next) использует esbuild/SWC: они мгновенно срезают типы, но **не проверяют** их.
- **Проверка типов** делается отдельно: `tsc --noEmit` в IDE и в [CI](/content/advanced-tooling/ci-cd).

<b class="text-on-semi-light">Зачем так</b> - <span class="text-gray">Если бы каждая пересборка ждала полной проверки типов, dev был бы медленным. Разделив, получаем: мгновенную сборку (esbuild) + надёжную проверку (tsc) параллельно. Цена - сборка сама по себе **не остановится** на ошибке типа; её ловит отдельный шаг.</span>

> Практическое следствие: «у меня собралось, но типы кривые» - нормально для Vite. Поэтому `tsc --noEmit` обязателен в CI как отдельный гейт, иначе ошибки типов уедут в прод.

## isolatedModules

Раз esbuild/SWC транспилируют **каждый файл независимо** (без знания всей программы), некоторые возможности TS, требующие глобального контекста, ломаются. Флаг `isolatedModules: true` включает проверки, гарантирующие, что код безопасен для пофайловой транспиляции.

```ts
// при isolatedModules нужно явно помечать импорт ТИПА,
// иначе пофайловый транспайлер не отличит тип от значения
import type { User } from './types';
import { type Role, getRole } from './roles';
```

Также под запретом оказываются `const enum` и неоднозначные ре-экспорты. `verbatimModuleSyntax` развивает эту идею, делая поведение импортов предсказуемым.

## Ключевые опции tsconfig

| Опция | Зачем |
|-------|-------|
| `strict` | включить все строгие проверки (обязательно) |
| `target` | уровень синтаксиса вывода (если эмитит tsc) |
| `module` / `moduleResolution` | формат модулей; для бандлеров - `"bundler"` |
| `noEmit` | только проверять, не генерировать JS |
| `isolatedModules` | совместимость с пофайловой транспиляцией |
| `skipLibCheck` | не проверять `.d.ts` зависимостей (ускоряет) |
| `paths` | алиасы импортов (`@/*`) |

> `moduleResolution: "bundler"` - современный режим: говорит TS, что модули резолвит бандлер (Vite), а не Node, - совпадает с реальностью сборки.

## Проверка типов в CI

Поскольку сборка типы не проверяет, в [CI](/content/advanced-tooling/ci-cd) добавляют отдельный шаг:

```bash
tsc --noEmit   # упадёт, если есть ошибки типов - гейт перед мержем
```

Для Vue-проектов - **`vue-tsc`** (понимает `.vue`-файлы). Это критичный гейт качества: без него типобезопасность - иллюзия.

---

## Генерация .d.ts

При публикации **библиотеки** нужно отдать типы потребителям - файлы деклараций `.d.ts`. Их генерирует `tsc` (`declaration: true`) или специализированные инструменты (vue-tsc, dts-плагины сборщиков). Сам JS при этом часто собирают esbuild/Rollup, а типы - отдельно через tsc (см. [сборку библиотек](/content/ecosystem-libs/building-and-patching)).

## Language Server

Подсветка типов и автодополнение в IDE дают **tsserver** (TypeScript Language Server) - тот же движок, что и `tsc`, работающий в фоне редактора. Поэтому ошибки в IDE и в `tsc --noEmit` совпадают.

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему проверку типов отделяют от транспиляции?</b>
<span class="text-gray">Проверка типов медленная (анализ всей программы), транспиляция должна быть быстрой и пофайловой. Разделив, получают мгновенную сборку (esbuild/SWC) + проверку (tsc --noEmit) - параллельно, без замедления dev.</span>

<b class="text-on-semi-light">Почему Vite собирает код с ошибкой типа?</b>
<span class="text-gray">esbuild срезает типы, но не проверяет их. Проверку делает отдельный `tsc --noEmit`. Поэтому его обязательно добавляют в CI, иначе ошибки типов уедут в прод.</span>

<b class="text-on-semi-light">Что такое isolatedModules и зачем он нужен?</b>
<span class="text-gray">Флаг, гарантирующий, что код безопасно транспилируется пофайлово (как делают esbuild/SWC). Требует помечать импорты типов `import type`, запрещает `const enum` и неоднозначные ре-экспорты.</span>

<b class="text-on-semi-light">Зачем `import type`?</b>
<span class="text-gray">Чтобы пофайловый транспайлер однозначно понимал, что импорт - только тип, и удалял его, не оставляя рантайм-импорта. Важно при isolatedModules/verbatimModuleSyntax.</span>

<b class="text-on-semi-light">Как обеспечить типобезопасность в CI?</b>
<span class="text-gray">Отдельный шаг `tsc --noEmit` (или `vue-tsc` для Vue) как гейт перед мержем. Сборка типы не проверяет, поэтому без этого шага типобезопасность - иллюзия.</span>
