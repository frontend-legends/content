# Инструменты TypeScript

Как TypeScript встраивается в конвейер: проверка типов отдельно от стирания, почему пофайловая трансформация требует `isolatedModules` и `verbatimModuleSyntax`, выпуск `.d.ts` и `isolatedDeclarations`, инкрементальная проверка, project references, CI и языковой сервер — и что изменил нативный TypeScript 7. Спрашивают, почему проверку типов отделяют от сборки, почему Vite собирает код с ошибкой типа и зачем `import type`. Глубже — как реэкспорт типа ломает приложение в рантайме и зачем библиотекам `isolatedDeclarations`.

::tldr
- **У `tsc` две роли — проверить типы и выдать JavaScript,** и в современных проектах их разделяют. Сборку делают быстрые инструменты, которые стирают типы пофайлово, а проверку — `tsc --noEmit` в редакторе и CI.
- **Пофайловое стирание не видит другие файлы.** Реэкспорт типа без `export type` остаётся в JavaScript и падает при загрузке. `isolatedModules` и `verbatimModuleSyntax` запрещают такие конструкции при проверке.
- **`isolatedDeclarations` требует явных типов у экспортов,** чтобы `.d.ts` можно было выпустить пофайлово, без проверки всей программы. Это ускоряет сборку библиотек.
- **Инкрементальность и project references** проверяют только изменившееся: `.tsbuildinfo` хранит результат прошлой проверки, `tsc -b` собирает граф проектов.
- **Нативный компилятор на Go в разы быстрее прежнего** и использует несколько ядер, но пока без программного API — инструменты, которые встраиваются в компилятор, работают на прежней версии.
::

---

## Две роли tsc

Компилятор `tsc` умеет:

1. **проверить типы** — проанализировать всю программу и найти ошибки;
2. **выдать JavaScript** — стереть типы и, если нужно, понизить синтаксис.

Проверка требует знать типы из всех модулей и поэтому медленная. Выдача JavaScript — простое преобразование одного файла. Раньше `tsc` делал обе работы, и каждая пересборка ждала полной проверки.

Сейчас роли разведены:

```text
сборка   — esbuild, SWC, Oxc в Vite и Next.js, Node.js для .ts: стирают типы пофайлово, быстро
проверка — tsc --noEmit (vue-tsc для .vue): вся программа, только ошибки, без вывода
```

Сборка **не останавливается** на ошибке типа: трансформатор её просто не видит (подробно — в [Транспиляции](/content/advanced-tooling/transpilation)). Поэтому «у меня собралось, но типы сломаны» — нормальная ситуация для Vite, и проверка типов обязана быть отдельным шагом CI. Иначе ошибки типов уедут в продакшен.

Сквозной пример — модуль типов магазина и реэкспорт:

```ts
// types.ts
export interface User { id: number }
export const ROLE = 'admin';

// index.ts
export { User, ROLE } from './types';
```

## Ограничения пофайловой трансформации

Трансформатор видит только `index.ts`. Ему неизвестно, что `User` — интерфейс, который исчезнет при стирании, а `ROLE` — значение. Он оставляет строку как есть:

```js
export { User, ROLE } from './types.js';
```

При загрузке модуль `types.js` экспортирует только `ROLE`, и браузер или Node.js бросают `SyntaxError: The requested module './types.js' does not provide an export named 'User'`. В проверке esbuild выдал именно такой код, и Node.js упал с этой ошибкой. `tsc` такой проблемы не имеет — он видит всю программу.

### isolatedModules

Опция `isolatedModules` говорит проверке: «код будут транспилировать пофайлово, запрещай то, что так не сработает». С ней тот же реэкспорт — ошибка TS1205 «Re-exporting a type when 'isolatedModules' is enabled requires using 'export type'». Исправление явно говорит трансформатору, что стирать:

```ts
export type { User } from './types';
export { ROLE } from './types';
```

Проверено: после исправления ошибок нет. Под тот же запрет попадают `const enum` из других файлов и `namespace` с кодом.

### verbatimModuleSyntax

Следующий шаг — `verbatimModuleSyntax`: импорты и экспорты остаются в JavaScript **ровно как написаны**, кроме помеченных `type`. Тогда импорт только типа без `type` — ошибка TS1484 «'User' is a type and must be imported using a type-only import» (проверено):

```ts
import type { User } from './types';     // стирается целиком
import { type User, ROLE } from './types';   // стирается только User
```

Правило простое и предсказуемое: что без `type`, то останется. Это то же поведение, что у стирания типов в Node.js (подробно — во [Введении в TypeScript](/content/typescript/introduction)). Смысл самих опций и остальных настроек `tsconfig` — в [Настройке проекта](/content/typescript/project-setup).

## Объявления типов

Библиотека отдаёт потребителям не только JavaScript, но и `.d.ts` — описание типов. Классически их выпускает `tsc` с `declaration: true`, и для этого он тоже проверяет всю программу: тип возвращаемого значения нужно вывести.

```ts
export function total(items: { price: number }[]) {
  return items.reduce((s, i) => s + i.price, 0);   // тип результата выводится из reduce
}
```

**`isolatedDeclarations`** требует, чтобы у экспортов были **явные** типы — те, что нельзя получить без вывода. Для функции выше `tsc` выдал TS9013 «Expression type can't be inferred with --isolatedDeclarations». С аннотацией `: number` ошибки нет, и объявление получилось точным:

```ts
export declare function total(items: { price: number; }[]): number;
```

Зачем это нужно: когда типы экспортов явные, `.d.ts` можно выпустить **пофайлово**, как JavaScript, — без проверки программы. Так делают Oxc и сборщики библиотек вроде tsdown: объявления генерируются за доли секунды, а проверка типов идёт отдельно и параллельно. Для приложений опция не нужна, для библиотек — заметно ускоряет сборку.

Как публиковать типы в пакете — поля `types` и `exports` — в [Модульных системах](/content/advanced-tooling/module-systems).

## Скорость проверки

### Инкрементальность

`incremental: true` сохраняет результат проверки в файл `.tsbuildinfo`, и следующий запуск перепроверяет только изменившиеся файлы и их зависимых. В проверке файл появился после первого запуска. В CI его кешируют между сборками вместе с `node_modules`.

### Project references

Большой код делят на **проекты** — отдельные `tsconfig.json` для пакетов или слоёв приложения со ссылками друг на друга:

```json
{
  "files": [],
  "references": [{ "path": "./packages/ui" }, { "path": "./packages/app" }]
}
```

`tsc -b` строит граф проектов и проверяет их в правильном порядке, пропуская неизменённые. Типы соседнего проекта берутся из его `.d.ts`, а не из исходников, поэтому изменение внутри `ui` без изменения его API не заставит перепроверять `app`. Это основной инструмент для монорепо (подробно — в [Монорепо](/content/advanced-tooling/monorepo-tooling)).

### TypeScript 7

TypeScript 7 — тот же язык и те же проверки, но компилятор переписан на Go и использует несколько ядер. В проверке на проекте из 300 файлов `tsc` 7 справился примерно в 3 раза быстрее `tsc` 6, а на больших проектах команда TypeScript сообщает об ускорении около 10 раз.

Цена — у нативного компилятора пока нет программного API. Инструменты, которые встраиваются в компилятор, — `vue-tsc`, правила typescript-eslint, использующие типы, часть плагинов, — продолжают работать на TypeScript 6. В проекте может понадобиться обе версии: 7 для `tsc --noEmit` в CI и 6 для `vue-tsc` или линтера. Как это сделано в проверках этой книги, — в [TypeScript с Vue](/content/typescript/ts-with-vue).

## Проверка в CI и в редакторе

В CI проверка — отдельный шаг, который блокирует слияние:

```yaml
- run: npx tsc --noEmit          # или vue-tsc --noEmit для Vue
```

Она идёт параллельно с линтингом и тестами, а не перед сборкой: сборке типы не нужны (подробно — в [CI/CD](/content/advanced-tooling/ci-cd)). `skipLibCheck: true` пропускает проверку `.d.ts` из зависимостей и заметно её ускоряет.

В редакторе ошибки и подсказки даёт **языковой сервер** — тот же компилятор, работающий в фоне и проверяющий открытые файлы. Поэтому ошибки в редакторе совпадают с `tsc` в CI, если обе стороны используют одну версию TypeScript и один `tsconfig`. Частая причина расхождений — редактор взял встроенную версию TypeScript, а проект — свою; в VS Code выбирают «Use Workspace Version».

## Красные флаги в ответе

- **«Vite проверяет типы при сборке».** Он стирает их без проверки, нужен отдельный `tsc --noEmit`.
- **«`import type` — вопрос стиля».** Без него пофайловый трансформатор не знает, что стирать, и реэкспорт типа падает при загрузке.
- **«`isolatedModules` ускоряет проверку».** Он запрещает конструкции, которые нельзя транспилировать пофайлово.
- **«Объявления типов выпускаются так же быстро, как JavaScript».** Только с `isolatedDeclarations`, иначе нужна проверка программы.
- **«С TypeScript 7 TypeScript 6 больше не нужен».** Инструментам с программным API компилятора он пока нужен.

## Как спрашивают на собеседовании

::question
Почему проверку типов отделяют от сборки?

#answer
Проверка анализирует всю программу и медленная, а стирание типов — пофайловое и быстрое. Сборку делают esbuild, SWC или Oxc, а проверку — `tsc --noEmit` в редакторе и CI, параллельно с остальными шагами.

#more
Пересборка не ждёт проверки, поэтому разработка мгновенная. Цена — сборка не остановится на ошибке типа, и без отдельного шага в CI ошибки уедут в продакшен. Пофайловое стирание требует `isolatedModules` и `import type`.
::

::question
Почему Vite собирает код с ошибкой типа?

#answer
Vite стирает типы пофайлово без проверки — трансформатор не знает типов из других файлов. Проверку делает отдельный `tsc --noEmit` или `vue-tsc --noEmit`.

#more
Для обратной связи в разработке есть плагины вроде `vite-plugin-checker`, которые запускают проверку параллельно и показывают ошибки в браузере. Но главная защита — шаг в CI, который блокирует слияние.
::

::question
Что такое isolatedModules и зачем он нужен?

#answer
Опция проверки, которая запрещает конструкции, невозможные при пофайловой транспиляции: реэкспорт типа без `export type`, `const enum` из других файлов, `namespace` с кодом. Трансформатор видит один файл и не может решить, что стирать.

#more
Без неё `export { User } from './types'` для интерфейса `User` останется в JavaScript, и модуль упадёт при загрузке с «does not provide an export named». `verbatimModuleSyntax` строже: всё без `type` остаётся в выводе как есть.
::

::question
Зачем нужен import type?

#answer
Он явно говорит, что импорт — только тип и его нужно стереть. Пофайловый трансформатор не знает, тип это или значение, а `import type` снимает вопрос.

#more
С `verbatimModuleSyntax` импорт типа без `type` — ошибка TS1484. Можно помечать отдельные имена: `import { type User, ROLE }`. Это убирает лишние рантайм-импорты и побочные эффекты модулей, которые нужны были только ради типов.
::

::question
Что такое isolatedDeclarations?

#answer
Опция, которая требует явных типов у всего экспортируемого, чтобы `.d.ts` можно было выпустить пофайлово, без проверки программы. Невыводимое выражение в экспорте — ошибка, например TS9013.

#more
Тогда объявления генерируют быстрые инструменты — Oxc, сборщики библиотек вроде tsdown — параллельно с проверкой типов. Для библиотек это заметное ускорение сборки, для приложений опция обычно не нужна.
::

::question
Как ускорить проверку типов в большом проекте?

#answer
Инкрементальная проверка с `.tsbuildinfo`, project references и `tsc -b` для монорепо, `skipLibCheck`, кеш в CI. И переход на TypeScript 7, который в разы быстрее и использует несколько ядер.

#more
С project references соседние проекты проверяются по их `.d.ts`, и изменение внутри пакета без изменения API не перепроверяет зависимых. Инструменты на программном API компилятора — `vue-tsc`, часть правил typescript-eslint — пока требуют TypeScript 6.
::

## Практика

::practice{title="Приложение упало после рефакторинга"}
После выноса типов в отдельный файл сборка прошла, а в браузере белый экран:

```text
SyntaxError: The requested module '/src/types.ts' does not provide an export named 'User'
```

```ts
// src/index.ts
export { User, ROLE } from './types';
```

#solution
`User` — интерфейс, он исчезает при стирании. Трансформатор Vite видит только `index.ts` и не знает этого, поэтому оставил реэкспорт `User` в JavaScript. Браузер не нашёл такого экспорта в `types.ts`.

```ts
export type { User } from './types';
export { ROLE } from './types';
```

Чтобы такое ловилось до запуска, в `tsconfig.json` включают `isolatedModules` или `verbatimModuleSyntax`, а `tsc --noEmit` ставят в CI. В проверке esbuild выдал код с реэкспортом `User`, Node.js упал с этой ошибкой, а `tsc` с `isolatedModules` сообщил TS1205.
::

::practice{title="Сборка библиотеки идёт минуту"}
Монорепо с дизайн-системой. JavaScript собирается за секунды, а выпуск `.d.ts` через `tsc --declaration` — около минуты, и это блокирует остальные пакеты.

#solution
`tsc` выпускает объявления только после проверки всей программы: ему нужно вывести типы экспортов. Если сделать типы экспортов явными, объявления можно выпустить пофайлово:

```json
{
  "compilerOptions": {
    "isolatedDeclarations": true,
    "declaration": true
  }
}
```

```ts
export function total(items: { price: number }[]): number {
  return items.reduce((s, i) => s + i.price, 0);
}
```

Теперь `.d.ts` выпускают быстрые инструменты вроде tsdown или Oxc, а `tsc --noEmit` проверяет типы отдельным параллельным шагом. Плюс project references с `tsc -b`, чтобы пакеты, у которых не изменился API, не перепроверялись. В проверке без аннотации `tsc` выдал TS9013, с аннотацией — точное объявление `export declare function total(…): number`.
::
