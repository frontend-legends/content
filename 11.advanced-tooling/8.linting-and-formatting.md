# Линтинг и форматирование

Два разных инструмента качества кода: линтер ищет ошибки и опасные паттерны, форматтер приводит код к одному виду. Как устроен ESLint и его flat config, как написать своё правило, что делают Prettier, Biome и Oxlint и где всё это запускать. Спрашивают, чем линтер отличается от форматтера, зачем разделять ESLint и Prettier и как ESLint находит ошибки. Глубже — почему после обновления ESLint перестал видеть конфигурацию, чем правило с автоисправлением отличается от предупреждения и насколько быстрее нативные линтеры.

::tldr
- **Линтер ищет проблемы смысла:** неиспользуемые переменные, `debugger`, `==` вместо `===`, нарушения правил хуков. **Форматтер меняет только вид:** отступы, кавычки, переносы, — и не трогает логику.
- **ESLint разбирает код в AST и запускает правила-посетители узлов.** Своё правило — объект с `create`, который подписывается на типы узлов и сообщает о проблеме через `context.report`.
- **Конфигурация ESLint теперь только `eslint.config.js`:** массив объектов настроек. Старый `.eslintrc` больше не читается.
- **Форматирование отдают форматтеру, а не правилам линтера.** Стилистические правила ESLint устарели, Prettier, Biome или Oxfmt форматируют код целиком и одинаково при каждом запуске.
- **Нативные инструменты на порядки быстрее:** Oxlint и Biome написаны на Rust, и на большом проекте разница — секунды против долей секунды. ESLint остаётся там, где нужны его плагины и правила с типами.
::

## Линтер и форматтер

Сквозной пример — функция корзины, в которой есть и ошибки, и беспорядок:

```js
export function total(items) {
  let sum = 0
  for (const item of items) { if (item.price == null) continue; sum += item.price }
  const unused = 1
  debugger
  return sum
}
```

**Форматтер** расставит точки с запятой, переносы и отступы, но `debugger` и неиспользуемая `unused` останутся — это не вопрос вида. В проверке Prettier оставил обе строки, а повторный запуск на уже отформатированном коде ничего не изменил: результат стабилен.

**Линтер** найдёт `debugger` и `unused` — потенциальные ошибки. Вид кода его не интересует.

| | Линтер | Форматтер |
| --- | --- | --- |
| Что ищет | ошибки, опасные паттерны, нарушения договорённостей | расхождения со стилем |
| Меняет логику | может предложить исправление | никогда |
| Настройки | сотни правил, плагины | несколько опций |
| Инструменты | ESLint, Oxlint, Biome, Stylelint | Prettier, Biome, Oxfmt |

Форматтер убирает споры о стиле из ревью: вид решает инструмент, а не люди. Линтер ловит ошибки до запуска.

## ESLint

### Как он находит ошибки

ESLint разбирает файл в **AST** (подробно о дереве — в [Транспиляции](/content/advanced-tooling/transpilation)) и обходит его. Каждое правило — **посетитель**: подписывается на нужные типы узлов и сообщает о проблеме. Правило `no-debugger` подписывается на узел `DebuggerStatement`, `eqeqeq` — на `BinaryExpression` с `==`.

### Flat config

С ESLint 9 конфигурация — файл `eslint.config.js` с **массивом** объектов настроек. В ESLint 10 старый формат удалён полностью: файл `.eslintrc` больше не читается, а без нового ESLint сообщает «ESLint couldn't find an eslint.config.* file» — в проверке так и было, хотя `.eslintrc.json` лежал рядом.

```js
// eslint.config.js
import js from '@eslint/js';
import vue from 'eslint-plugin-vue';
import tseslint from 'typescript-eslint';

export default [
  { ignores: ['dist/**'] },
  js.configs.recommended,
  ...tseslint.configs.recommended,
  ...vue.configs['flat/recommended'],
  {
    files: ['src/**/*.{js,ts,vue}'],
    rules: {
      eqeqeq: ['error', 'always', { null: 'ignore' }],
      'no-console': ['warn', { allow: ['error', 'warn'] }],
    },
  },
];
```

Объекты применяются по порядку, и поздние перекрывают ранние. `files` ограничивает настройки путями, `ignores` без других ключей исключает пути глобально. Плагины подключаются как обычные импорты — без строковых имён и магии разрешения, как было в `.eslintrc`. Файл `.eslintignore` тоже больше не читается.

В проверке с такой конфигурацией ESLint нашёл `no-debugger` и `no-unused-vars`, а `item.price == null` пропустил: настройка `null: 'ignore'` разрешает удобную проверку на `null` и `undefined` сразу.

### Автоисправление

`eslint --fix` применяет исправления, которые правила считают безопасными. В проверке `var x` превратился сначала в `let`, а затем в `const`: исправления применяются в несколько проходов, пока код не перестанет меняться. Правила, где исправление может изменить смысл, дают только **предложение** — его применяет человек в редакторе.

### Своё правило

Договорённости команды тоже можно проверять. Пример — деньги в копейках должны получаться через `Math.round`, иначе `1.15 * 100` даст `114.99999999999999` (подробно — в [Типах данных](/content/javascript/types-and-variables)):

```js
const noFloatMoney = {
  meta: { type: 'problem', messages: { round: 'Копейки из рублей — только через Math.round()' } },
  create(context) {
    return {
      BinaryExpression(node) {
        if (node.operator !== '*') return;
        const isPrice = (n) => n.type === 'MemberExpression' && n.property.name === 'price';
        const isHundred = (n) => n.type === 'Literal' && n.value === 100;
        if (!(isPrice(node.left) && isHundred(node.right))) return;
        const p = node.parent;
        const rounded = p.type === 'CallExpression' && p.callee.object?.name === 'Math' && p.callee.property?.name === 'round';
        if (!rounded) context.report({ node, messageId: 'round' });
      },
    };
  },
};
```

```js
// eslint.config.js
export default [{ plugins: { shop: { rules: { 'no-float-money': noFloatMoney } } }, rules: { 'shop/no-float-money': 'error' } }];
```

В проверке `item.price * 100` дал ошибку с этим сообщением, а `Math.round(item.price * 100)` прошёл. Так проверяют архитектурные границы — запрет импорта из соседнего модуля, — использование устаревших API и правила дизайн-системы.

### Правила с типами

Некоторые правила `typescript-eslint` используют типы: «не забыть `await` у промиса» (`no-floating-promises`), «не передавать промис туда, где ждут функцию» (`no-misused-promises`). Им нужна программа TypeScript целиком, поэтому они медленнее обычных и зависят от программного API компилятора, которого у TypeScript 7 пока нет (подробно — в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling)).

## Форматтеры

**Prettier** — стандарт форматирования. Он не исправляет отдельные места, а перепечатывает весь файл по своим правилам, поэтому результат не зависит от того, как код был написан. Опций мало намеренно: ширина строки, кавычки, точки с запятой, запятые в конце.

```bash
prettier --write .   # отформатировать
prettier --check .   # проверить, для CI: ненулевой код, если что-то не отформатировано
```

В проверке `--check` на неотформатированном файле завершился с кодом 1.

### ESLint и Prettier вместе

Раньше ESLint содержал правила форматирования, и они спорили с Prettier: одно правило требовало одно, форматтер делал другое. С ESLint 8.53 стилистические правила устарели и вынесены в отдельный проект `@stylistic`. Современный подход: **форматирование — форматтеру, ошибки — линтеру**, а если в старой конфигурации остались стилистические правила, их отключает `eslint-config-prettier`.

## Нативные инструменты

**Biome** — линтер и форматтер в одном инструменте на Rust, с одной конфигурацией и одной командой `biome check`. В проверке он сообщил и о `noDebugger`, и о неотформатированном коде.

**Oxlint** — линтер на Rust из проекта Oxc. Он реализует сотни правил ESLint и популярных плагинов — React, TypeScript, Vue, Jest, import — и запускается без настройки. **Oxfmt** — форматтер того же проекта, совместимый по результату с Prettier.

Разница в скорости — на порядки. В проверке на 1000 файлах по 40 функций ESLint работал около 5,5 секунды, Oxlint — меньше 0,1 секунды, разница — в десятки раз. На проекте, где ESLint идёт минуту, это меняет привычки: линтер можно запускать на каждое сохранение, а не только в CI.

Практичная схема для большого проекта:

- **Oxlint или Biome** — основные правила, быстро, на каждое сохранение и в git-хуке;
- **ESLint** — только то, чего нет в нативном инструменте: правила с типами, редкие плагины, свои правила. Плагин `eslint-plugin-oxlint` выключает в ESLint правила, которые уже проверил Oxlint.

Единые тулчейны вроде Vite+ объединяют Oxlint, Oxfmt, тесты и сборку в одну команду (подробно — в [Rust и будущем тулинга](/content/advanced-tooling/rust-and-the-future)).

### Stylelint

Для CSS — Stylelint: ошибки вроде неизвестных свойств и дублей селекторов, порядок свойств, правила дизайн-системы — например, запрет цветов вне токенов. Biome тоже проверяет CSS, но с меньшим набором правил.

## Где запускать

| Место | Что | Зачем |
| --- | --- | --- |
| редактор | линтер и форматтер при сохранении | мгновенная обратная связь |
| git-хук | только изменённые файлы | не пустить ошибку в коммит ([Git-хуки](/content/advanced-tooling/git-hooks-and-quality-gates)) |
| CI | весь проект, `--check` и без `--fix` | гарантия: обойти хук можно, CI — нет ([CI/CD](/content/advanced-tooling/ci-cd)) |

Важно, чтобы везде работали **одни и те же** версии и конфигурация — инструменты ставят в `devDependencies`, а не глобально.

## Красные флаги в ответе

- **«Prettier найдёт ошибки».** Он меняет только вид кода, `debugger` и неиспользуемые переменные останутся.
- **«`.eslintrc` — стандартная конфигурация».** В ESLint 10 читается только `eslint.config.js`.
- **«Форматирование удобно настроить правилами ESLint».** Стилистические правила устарели и спорят с форматтером.
- **«`--fix` исправит всё».** Он применяет только безопасные исправления, остальное — предложения.
- **«Нативные линтеры — игрушки».** Oxlint и Biome покрывают основные правила ESLint и работают в десятки раз быстрее.

## Как спрашивают на собеседовании

::question
Чем линтер отличается от форматтера?

#answer
Линтер ищет проблемы смысла: неиспользуемые переменные, `debugger`, опасные сравнения, нарушения правил хуков и договорённостей команды. Форматтер приводит код к одному виду — отступы, кавычки, переносы — и логику не трогает.

#more
Форматтер перепечатывает файл целиком, и результат не зависит от исходного вида. Линтер может предложить исправление, но часть правил только сообщает. Форматирование отдают форматтеру, а не правилам линтера.
::

::question
Зачем разделять ESLint и Prettier?

#answer
Чтобы инструменты не спорили. Стилистические правила ESLint и Prettier требовали разного, и код менялся по кругу. Сейчас форматирование — задача форматтера, а ESLint — только ошибки и договорённости.

#more
Стилистические правила ESLint устарели и вынесены в `@stylistic`. В старых конфигурациях их отключает `eslint-config-prettier`. Biome делает и то, и другое одним инструментом, поэтому конфликтов в нём нет.
::

::question
Как ESLint находит ошибки?

#answer
Разбирает код в AST и обходит дерево. Каждое правило подписывается на типы узлов — `DebuggerStatement`, `BinaryExpression`, `CallExpression` — и через `context.report` сообщает о проблеме, иногда с исправлением.

#more
Своё правило — объект с `meta` и `create`, который возвращает обработчики узлов. Правила с типами из `typescript-eslint` дополнительно используют программу TypeScript и поэтому медленнее. Кодмоды и правила линтера используют одно и то же представление кода.
::

::question
Что изменилось в ESLint 9 и 10?

#answer
Конфигурация стала flat config — файл `eslint.config.js` с массивом объектов настроек, где плагины подключаются обычными импортами. В ESLint 10 старый `.eslintrc` и `.eslintignore` удалены окончательно.

#more
Объекты применяются по порядку, `files` ограничивает пути, `ignores` исключает. Без `eslint.config.js` ESLint 10 сообщает, что не нашёл конфигурацию, даже если `.eslintrc` лежит рядом. Стилистические правила устарели ещё раньше.
::

::question
Что такое Biome и Oxlint и зачем они?

#answer
Линтеры на Rust: Biome — линтер и форматтер в одном, Oxlint — линтер из проекта Oxc с сотнями правил ESLint и популярных плагинов. Они работают в десятки раз быстрее ESLint.

#more
Скорость позволяет запускать линтер на каждое сохранение и в git-хуке без задержек. ESLint остаётся для правил с типами, редких плагинов и своих правил, а `eslint-plugin-oxlint` убирает дубли. Форматтеры на Rust — Biome и Oxfmt.
::

::question
Где запускают линтер и форматтер?

#answer
В редакторе при сохранении — для мгновенной обратной связи, в git-хуке на изменённых файлах — чтобы не пустить ошибку в коммит, и в CI на всём проекте — как гарантию, потому что хук можно обойти.

#more
В CI запускают без `--fix`, с `--check` для форматтера: сборка должна упасть, а не тихо исправить. Везде одни версии из `devDependencies` и одна конфигурация, иначе результаты будут расходиться.
::

## Практика

::practice{title="ESLint перестал работать после обновления"}
После обновления на ESLint 10 команда `eslint .` падает, хотя `.eslintrc.json` на месте:

```text
ESLint couldn't find an eslint.config.* file.
```

#solution
ESLint 10 больше не читает `.eslintrc`. Конфигурацию переписывают во flat config:

```js
// eslint.config.js
import js from '@eslint/js';
import globals from 'globals';

export default [
  { ignores: ['dist/**', 'coverage/**'] },   // вместо .eslintignore
  js.configs.recommended,
  {
    files: ['**/*.js'],
    languageOptions: { globals: globals.browser },   // вместо env: { browser: true }
    rules: { eqeqeq: ['error', 'always', { null: 'ignore' }] },
  },
];
```

`env` заменяют `languageOptions.globals`, `extends` — элементы массива, `plugins` — объект с импортированными плагинами. Для переноса есть `npx @eslint/migrate-config .eslintrc.json`. В проверке без `eslint.config.js` ESLint сообщил эту ошибку, а с ним нашёл `no-debugger` и `no-unused-vars`.
::

::practice{title="Правило для дизайн-системы"}
В проекте договорились, что деньги в копейках получают только через `Math.round(price * 100)`, но в ревью это постоянно пропускают. Автоматизируй проверку.

#solution
Своё правило ESLint подписывается на умножение и проверяет, что оно обёрнуто в `Math.round`:

```js
const noFloatMoney = {
  meta: { type: 'problem', messages: { round: 'Копейки из рублей — только через Math.round()' } },
  create(context) {
    return {
      BinaryExpression(node) {
        const isPrice = (n) => n.type === 'MemberExpression' && n.property.name === 'price';
        if (node.operator !== '*' || !isPrice(node.left) || node.right.value !== 100) return;
        const p = node.parent;
        const rounded = p.type === 'CallExpression' && p.callee.object?.name === 'Math' && p.callee.property?.name === 'round';
        if (!rounded) context.report({ node, messageId: 'round' });
      },
    };
  },
};

export default [{ plugins: { shop: { rules: { 'no-float-money': noFloatMoney } } }, rules: { 'shop/no-float-money': 'error' } }];
```

Правило живёт в репозитории как локальный плагин и работает в редакторе, хуке и CI. Если таких договорённостей много, их выносят в общий пакет конфигурации для всех проектов команды. В проверке `item.price * 100` дал ошибку, а `Math.round(item.price * 100)` — нет.
::
