# Оптимизация сборки

Цель прод-сборки - **наименьший бандл, который грузится максимально быстро**. Для этого бандлер применяет набор оптимизаций: минификация, tree-shaking, code splitting, хеширование. Эти термины - постоянные гости собеседований.

---

## Минификация

Уменьшение размера кода без изменения поведения: убрать пробелы и комментарии, укоротить имена переменных, упростить выражения.

```js
// до
function calculateTotal(price, quantity) {
  const total = price * quantity;
  return total;
}
// после
function c(t,n){return t*n}
```

Инструменты: **terser** (классика для JS), **esbuild**-минификатор (быстрее), **Lightning CSS**/cssnano для CSS. В современных сборках минификация включена в prod по умолчанию.

---

## Tree-shaking

Удаление **неиспользуемого кода** из бандла. Название - «потрясти дерево», чтобы опали мёртвые «листья»-экспорты.

```js
// utils.js экспортирует add и subtract
import { add } from './utils.js'; // используем только add
// → subtract НЕ попадёт в бандл
```

<b class="text-on-semi-light">Условия работы</b> - <span class="text-gray">Tree-shaking требует **статических ESM** (бандлер видит, что используется) и **отсутствия побочных эффектов**. Если модуль при импорте что-то делает (меняет глобал, регистрирует), бандлер боится его выкинуть - поэтому пакеты помечают `"sideEffects": false`. На CJS tree-shaking не работает (динамический require). См. [модульные системы](/content/advanced-tooling/module-systems).</span>

**Dead Code Elimination (DCE)** - смежная оптимизация: выкидывает недостижимый код (`if (false) {...}`, ветки по статическим флагам, напр. `process.env.NODE_ENV`).

---

## Code splitting

Разбиение бандла на **чанки**, которые грузятся по требованию, а не всё сразу. Уменьшает **начальную** загрузку и время до интерактивности.

```js
// динамический импорт → отдельный чанк, грузится при переходе
const Dashboard = () => import('./Dashboard.js');
```

Стратегии:

- **По маршрутам** - каждый роут в своём чанке (самое эффективное).
- **Вынос вендоров** - редко меняющиеся зависимости в отдельный чанк (лучше кешируется).
- **По компонентам** - тяжёлый виджет грузится лениво.

Это основа `React.lazy`/ленивых маршрутов ([производительность React](/content/reactjs/performance)).

---

## Scope hoisting

Бандлеры (Rollup, и Webpack в этом режиме) умеют **склеивать модули в одну область видимости** вместо оборачивания каждого в функцию-обёртку. Меньше оверхеда, меньше размер, быстрее исполнение. Работает благодаря статичности ESM.

---

## Хеширование и кеш

В прод имена файлов содержат **хеш содержимого**: `app.4f3a2b.js`. Если файл не изменился - хеш тот же, браузер берёт из кеша; изменился - новый хеш, кеш сбрасывается (cache busting).

```
app.[contenthash].js   →   app.4f3a2b.js
```

> Поэтому вендоры выносят отдельно: код приложения меняется часто, а React - редко. Разделение даёт пользователям перекачивать только изменившееся.

---

## Сжатие

Поверх минификации сервер отдаёт ассеты в сжатом виде - **gzip** или **brotli** (brotli сжимает сильнее). Это уровень сервера/CDN, не бандлера, но часть общей картины: минифицированный + brotli-сжатый бандл - то, что реально качает пользователь. Сравнивать размеры зависимостей нужно именно в min+gzip.

## Source maps

Минифицированный код нечитаем. **Source map** - файл, сопоставляющий собранный код с исходником, чтобы в DevTools и в стектрейсах видеть оригинал.

| Тип | Что делает |
|-----|-----------|
| inline | карта внутри бандла (удобно в dev, тяжело) |
| external | отдельный `.map`-файл |
| hidden | карта есть, но не ссылается из бандла (для загрузки в трекер ошибок) |

<b class="text-on-semi-light">Source maps в проде</b> - <span class="text-gray">Их **не выкладывают публично** (раскрывают исходник), но **генерируют** и загружают в трекеры ошибок (Sentry), чтобы расшифровывать минифицированные стектрейсы. Вариант - `hidden` source maps. Подробнее об использовании в отладке - в [DevTools и отладке](/content/advanced-tooling/devtools-and-debugging).</span>

## Когда tree-shaking не срабатывает

На практике tree-shaking часто «не работает» по конкретным причинам - и senior умеет их диагностировать:

- **Barrel-файлы** (`index.ts`, реэкспортирующий всё) - импорт одной функции может затащить **весь** модуль, если бандлер не доказал отсутствие побочных эффектов. На больших barrel'ах бьёт по бандлу и скорости сборки.
- **Побочные эффекты при импорте** - модуль, который при загрузке что-то регистрирует/мутирует глобал, нельзя выкинуть. Без `"sideEffects": false` бандлер осторожничает.
- **CommonJS-зависимости** - динамический `require` не анализируется статически; CJS-пакет дерево-трясётся плохо.
- **Импорт всей библиотеки** - `import _ from 'lodash'` тянет всё; нужен `lodash-es` или точечный импорт.

<b class="text-on-semi-light">Аннотация PURE</b> - <span class="text-gray">Комментарий `/*#__PURE__*/` перед вызовом говорит бандлеру «вызов без побочных эффектов, можно выкинуть, если результат не используется». Библиотеки расставляют его, чтобы хорошо трясти дерево. Если своя «чистая» функция не выкидывается - возможно, не хватает этой пометки или `sideEffects`.</span>

## Анализ бандла

Чтобы понять, **что раздувает** бандл, используют визуализаторы:

- **rollup-plugin-visualizer** (Vite/Rollup), **webpack-bundle-analyzer** - карта размеров модулей.
- Находят дубли, случайно включённые тяжёлые зависимости, не сработавший tree-shaking.

> Типичная находка: затащили `lodash` целиком вместо точечного импорта, или две версии одной библиотеки. Анализ - первый шаг оптимизации размера.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое tree-shaking и какие условия для него?</b>
<span class="text-gray">Удаление неиспользуемых экспортов из бандла. Требует статических ESM и отсутствия побочных эффектов (`sideEffects: false`). На CJS не работает из-за динамического require.</span>

<b class="text-on-semi-light">Что даёт code splitting?</b>
<span class="text-gray">Разбивает бандл на чанки, грузящиеся по требованию (по маршрутам, динамическим импортам). Уменьшает начальную загрузку и время до интерактивности.</span>

<b class="text-on-semi-light">Зачем хеши в именах файлов?</b>
<span class="text-gray">Cache busting: имя зависит от содержимого. Не изменился - браузер берёт из кеша; изменился - новый хеш сбрасывает кеш. Поэтому редко меняющиеся вендоры выносят отдельно.</span>

<b class="text-on-semi-light">Зачем нужны source maps и можно ли их в прод?</b>
<span class="text-gray">Сопоставляют минифицированный код с исходником для отладки и стектрейсов. Публично в прод не выкладывают (раскрытие кода), но генерируют и грузят в трекер ошибок (Sentry), часто hidden.</span>

<b class="text-on-semi-light">Как найти, что раздувает бандл?</b>
<span class="text-gray">Анализаторы (rollup-plugin-visualizer, webpack-bundle-analyzer) показывают карту размеров - находят тяжёлые зависимости, дубли, несработавший tree-shaking.</span>

<b class="text-on-semi-light">Чем минификация отличается от сжатия (gzip)?</b>
<span class="text-gray">Минификация переписывает код короче (на этапе сборки). Сжатие (gzip/brotli) - алгоритм на уровне сервера поверх минифицированного файла. Размер для пользователя - это min+brotli.</span>

<b class="text-on-semi-light">Почему tree-shaking иногда не убирает неиспользуемый код?</b>
<span class="text-gray">Частые причины: barrel-файлы (тянут весь модуль), побочные эффекты при импорте, CommonJS-зависимости, импорт всей библиотеки вместо точечного, отсутствие `sideEffects: false`. Лечится точечными импортами, пометкой sideEffects и `/*#__PURE__*/`.</span>
