# Git-хуки и гейты качества

Как не пустить ошибку в репозиторий: git-хуки и почему они не попадают в репозиторий сами, husky и `core.hooksPath`, lint-staged для проверки только изменённого, Conventional Commits и commitlint — и почему хуки не заменяют CI. Спрашивают, что такое git-хуки и зачем husky, зачем lint-staged и что дают Conventional Commits. Глубже — почему хук работает у одного разработчика и не работает у другого, что lint-staged делает с частично подготовленным файлом и что не стоит класть в `pre-commit`.

::tldr
- **Git-хук — скрипт, который git запускает на событии:** перед коммитом, при проверке сообщения, перед пушем. Ненулевой код выхода отменяет действие.
- **Папка `.git/hooks` не версионируется,** поэтому хуки не доходят до коллег. husky и lefthook хранят их в репозитории и указывают на них через `core.hooksPath`, а ставятся скриптом `prepare` при `npm install`.
- **lint-staged проверяет только подготовленные к коммиту файлы** и только их подготовленную версию: изменения, которые не в индексе, он не трогает, а исправления форматтера добавляет в коммит.
- **Conventional Commits — формат сообщений `тип(область): описание`.** По нему генерируют changelog и повышают версию по semver, а commitlint проверяет формат в хуке `commit-msg`.
- **Хуки — удобство, а не гарантия:** `git commit --no-verify` их обходит. Гарантию даёт CI с защитой веток.
::

## Что такое git-хуки

Git запускает скрипт с определённым именем, когда происходит событие. Основные для фронтенда:

| Хук | Когда | Что обычно делают |
| --- | --- | --- |
| `pre-commit` | перед созданием коммита | линтер и форматтер на изменённых файлах |
| `commit-msg` | после ввода сообщения | проверка формата сообщения |
| `pre-push` | перед отправкой на сервер | быстрые тесты, проверка типов |
| `post-merge`, `post-checkout` | после слияния и переключения ветки | `npm install`, если изменился lock-файл |

Если скрипт завершился с ненулевым кодом, git отменяет действие. В проверке хук `pre-commit` с `exit 1` не дал создать коммит и вывел своё сообщение.

### Почему хуки не доходят до коллег

Хуки по умолчанию лежат в `.git/hooks`, а эта папка **не входит в репозиторий** — её нет в истории, и при клонировании она создаётся пустой, с примерами. Хук, положенный туда, работает только у его автора.

Решение — хранить хуки в обычной папке репозитория и сказать git, где их искать:

```bash
git config core.hooksPath .githooks
```

В проверке после этого git запускал хук из `.githooks`, а старый хук в `.git/hooks` перестал использоваться. Остаётся одна проблема: `core.hooksPath` — настройка локальной копии, её тоже нужно выставить у каждого. Это и автоматизирует husky.

## husky

```bash
npx husky init
```

Команда, проверено:

- создаёт `.husky/pre-commit` с примером `npm test`;
- выставляет `core.hooksPath` на `.husky/_` — служебную папку husky;
- добавляет в `package.json` скрипт `"prepare": "husky"`.

Скрипт `prepare` npm запускает после `npm install`. Поэтому каждый, кто склонировал репозиторий и поставил зависимости, автоматически получает хуки. Сами хуки — обычные shell-скрипты в `.husky/`, и они в репозитории:

```bash
# .husky/pre-commit
npx lint-staged

# .husky/commit-msg
npx --no -- commitlint --edit "$1"
```

В CI хуки не нужны: там переменная `HUSKY=0` отключает установку.

**lefthook** — альтернатива на Go: хуки описываются в `lefthook.yml`, команды могут выполняться параллельно, есть свои фильтры файлов без lint-staged. Для монорепо его выбирают чаще.

Хуки установлены. Что запускать перед коммитом?

---

## lint-staged

Если перед каждым коммитом линтить весь проект, коммит займёт минуту, и разработчики начнут обходить хук. Нужно проверять **только то, что входит в коммит**.

```json
{
  "lint-staged": {
    "*.{js,ts,vue}": ["oxlint", "prettier --write"],
    "*.css": "stylelint --fix"
  }
}
```

lint-staged берёт файлы из **индекса** — подготовленные через `git add` — и запускает для каждого шаблона свои команды со списком этих файлов. В проверке были изменены два файла, подготовлен один, и скрипт-логгер получил только его.

### Частично подготовленные файлы

Важная деталь: в коммит идёт **подготовленная версия** файла, а не та, что сейчас на диске. Если разработчик подготовил часть изменений файла, проверять надо именно её. lint-staged поэтому:

1. временно прячет неподготовленные изменения;
2. запускает команды на подготовленной версии;
3. добавляет исправления команд — например, форматирование — в индекс;
4. возвращает спрятанные изменения на место.

В проверке после хука в индексе оказалась отформатированная версия подготовленного файла, а неподготовленный файл остался ровно таким, каким был. Если команда упала, lint-staged откатывает всё к исходному состоянию, и работа не теряется.

### Что не класть в pre-commit

Хук должен укладываться в секунды. Не стоит запускать:

- **весь набор тестов и полную проверку типов** — минуты на каждый коммит. Их место — `pre-push` или CI;
- **сборку** — она не про качество кода;
- **команды с сетью** — коммит не должен зависеть от интернета.

Быстрые нативные линтеры (подробно — в [Линтинге и форматировании](/content/advanced-tooling/linting-and-formatting)) хорошо подходят для `pre-commit`: на подготовленных файлах они работают за доли секунды.

## Conventional Commits и commitlint

**Conventional Commits** — формат сообщений:

```text
feat(cart): добавить промокод
fix: округление копеек в итоге
refactor(api)!: перейти на новый клиент

BREAKING CHANGE: цены теперь в копейках
```

`тип(область): описание`, где тип — `feat`, `fix`, `docs`, `refactor`, `test`, `chore` и другие. `!` после типа или строка `BREAKING CHANGE:` в теле помечают несовместимое изменение.

Зачем строгий формат: по истории можно **автоматически**

- сгенерировать changelog, сгруппированный по типам;
- выбрать следующую версию по semver: `fix` — патч, `feat` — минорная, несовместимое изменение — мажорная (подробно о semver — в [Управлении пакетами](/content/ecosystem-libs/package-management));
- выпустить релиз — так работают semantic-release и Changesets.

**commitlint** проверяет сообщение в хуке `commit-msg`:

```js
// commitlint.config.js
export default { extends: ['@commitlint/config-conventional'] };
```

В проверке `feat(cart): добавить промокод` и `fix:` с `BREAKING CHANGE` прошли, а «поправил всё» — нет: у сообщения не нашлось ни типа, ни описания.

При слиянии через squash сообщение коммита в основной ветке берётся из заголовка pull request — поэтому формат часто проверяют и в CI по заголовку PR, а не только в хуке.

## Оборона в глубину

Хук — локальная проверка на машине разработчика, и её можно обойти:

```bash
git commit --no-verify -m "срочно"
```

В проверке `--no-verify` создал коммит, хотя хук возвращал ошибку. Хук не запустится и там, где husky не установлен: в веб-редакторе GitHub, у разработчика, который поставил зависимости с `--ignore-scripts`.

Поэтому проверки дублируются на нескольких уровнях:

| Уровень | Что проверяет | Можно обойти |
| --- | --- | --- |
| редактор | линтер и типы при сохранении | да |
| `pre-commit` | линтер и форматтер на подготовленных файлах | да, `--no-verify` |
| `commit-msg` | формат сообщения | да |
| `pre-push` | быстрые тесты, типы | да |
| CI | всё: линтер, типы, тесты, сборка, размер | нет, если ветка защищена |
| защита ветки | обязательные проверки CI и ревью перед слиянием | нет |

Хуки экономят время: ошибка найдена за секунду, а не через десять минут ожидания CI. Но гарантию даёт только CI с защитой основной ветки (подробно — в [CI/CD](/content/advanced-tooling/ci-cd)).

---

## Красные флаги в ответе

- **«Положил хук в `.git/hooks` — у команды тоже работает».** Эта папка не версионируется, нужен `core.hooksPath` через husky или lefthook.
- **«Хуки гарантируют качество кода в репозитории».** `--no-verify` их обходит, гарантию даёт CI.
- **«В `pre-commit` надо запускать все тесты».** Коммит станет медленным, и хук начнут обходить.
- **«lint-staged проверяет изменённые файлы на диске».** Он проверяет подготовленную версию и не трогает неподготовленное.
- **«Формат коммитов — вопрос вкуса».** По нему автоматически генерируют changelog и выбирают версию.

## Как спрашивают на собеседовании

::question
Что такое git-хуки и зачем husky?

#answer
Скрипты, которые git запускает на событиях — перед коммитом, при проверке сообщения, перед пушем. Ненулевой код выхода отменяет действие. husky хранит хуки в репозитории и ставит их всем через скрипт `prepare` при `npm install`.

#more
Папка `.git/hooks` не версионируется, поэтому без инструмента хуки есть только у автора. husky выставляет `core.hooksPath` на свою папку. Альтернатива — lefthook на Go с параллельным запуском команд. В CI установку хуков отключают через `HUSKY=0`.
::

::question
Зачем lint-staged?

#answer
Запускает проверки только на файлах, подготовленных к коммиту, а не на всём проекте. Коммит остаётся быстрым, и хук не хочется обходить.

#more
Он проверяет именно подготовленную версию: прячет неподготовленные изменения, запускает команды, добавляет исправления форматтера в индекс и возвращает спрятанное. При ошибке всё откатывается. Команды задаются по шаблонам файлов.
::

::question
Что дают Conventional Commits?

#answer
Единый формат `тип(область): описание`, по которому история читается машиной. Из неё автоматически генерируют changelog и выбирают следующую версию по semver: `fix` — патч, `feat` — минорная, несовместимое изменение — мажорная.

#more
Несовместимое изменение помечают `!` после типа или строкой `BREAKING CHANGE:` в теле. Формат проверяет commitlint в хуке `commit-msg`, а при слиянии через squash — проверка заголовка PR в CI. На формате работают semantic-release и Changesets.
::

::question
Почему нельзя полагаться только на pre-commit хуки?

#answer
Хуки локальные и обходятся: `git commit --no-verify`, правка в веб-интерфейсе, установка зависимостей без скриптов. Они ускоряют обратную связь, но не гарантируют, что в основной ветке нет ошибок.

#more
Гарантию даёт CI, который запускает все проверки на сервере, и защита ветки, которая не даёт слить код без зелёного CI и ревью. Хуки, CI и защита ветки — уровни одной обороны.
::

::question
Что не стоит класть в pre-commit?

#answer
Всё медленное: полный набор тестов, полную проверку типов, сборку, команды с сетью. Коммит должен занимать секунды, иначе хук будут обходить.

#more
В `pre-commit` — линтер и форматтер на подготовленных файлах. Тесты и типы — в `pre-push` или только в CI. Нативные линтеры позволяют проверять больше без замедления.
::

## Практика

::practice{title="Хук работает только у автора"}
Тимлид настроил проверку перед коммитом, но коллеги коммитят код с ошибками линтера. У тимлида хук срабатывает.

#solution
Хук лежит в `.git/hooks` у тимлида. Эта папка не версионируется, и у коллег её нет. Хуки переносят в репозиторий и ставят автоматически:

```bash
npx husky init
```

```bash
# .husky/pre-commit
npx lint-staged
```

```json
{
  "scripts": { "prepare": "husky" },
  "lint-staged": { "*.{js,ts,vue}": ["oxlint", "prettier --write"] }
}
```

Теперь у каждого, кто выполнит `npm install`, хуки появятся сами. И главное — добавить ту же проверку в CI с обязательным статусом для слияния: хук можно обойти. В проверке husky выставил `core.hooksPath` на `.husky/_` и добавил скрипт `prepare`.
::

::practice{title="Форматтер испортил коммит"}
Разработчик подготовил к коммиту только часть изменений файла, а хук с `prettier --write src` закоммитил весь файл целиком, включая незаконченный код.

#solution
`prettier --write src` форматирует файлы на диске, а хук затем делает `git add`, добавляя всё. Нужно проверять и исправлять только подготовленную версию — это делает lint-staged:

```json
{
  "lint-staged": { "*.{js,ts,vue}": "prettier --write" }
}
```

```bash
# .husky/pre-commit
npx lint-staged
```

lint-staged прячет неподготовленные изменения, форматирует подготовленную версию, добавляет результат в индекс и возвращает спрятанное. В проверке в коммит пошла отформатированная подготовленная версия, а неподготовленный файл остался нетронутым.
::
