# Git-хуки и контроль качества

**Git-хуки** - скрипты, которые Git автоматически запускает на событиях (перед коммитом, перед пушем). Их используют, чтобы поймать проблемы **до** того, как плохой код попадёт в историю: прогнать линтер, форматтер, проверить сообщение коммита.

---

## Что такое git-хуки

Git умеет запускать скрипты в ключевые моменты своего жизненного цикла:

| Хук | Когда срабатывает | Типичное использование |
|-----|-------------------|------------------------|
| `pre-commit` | перед созданием коммита | линт + формат изменённых файлов |
| `commit-msg` | после ввода сообщения | проверка формата сообщения |
| `pre-push` | перед отправкой в remote | прогон тестов |

Проблема «голых» хуков - они лежат в `.git/hooks` и **не версионируются**: их нельзя расшарить с командой. Эту проблему решает husky.

---

## husky

**husky** делает git-хуки **частью репозитория**: хуки лежат в коде, версионируются и автоматически устанавливаются у всех (через `prepare`-скрипт при `npm install`).

```bash
# .husky/pre-commit
npx lint-staged
```

Теперь у каждого разработчика перед коммитом сработает один и тот же набор проверок - без ручной настройки.

---

## lint-staged

Запускать линтер на **всём** проекте при каждом коммите - медленно. **lint-staged** прогоняет инструменты **только на файлах в staging** (тех, что коммитятся).

```jsonc
// package.json
"lint-staged": {
  "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
  "*.css": ["stylelint --fix"]
}
```

<b class="text-on-semi-light">Почему только staged</b> - <span class="text-gray">Коммит должен быть быстрым, иначе разработчики начнут обходить проверки. lint-staged проверяет и автофиксит лишь изменённые файлы - секунды вместо минут. Тяжёлое (полный type-check, все тесты) выносят в [CI](/content/advanced-tooling/ci-cd).</span>

---

## Conventional Commits и commitlint

**Conventional Commits** - конвенция формата сообщений коммитов:

```
feat: добавить поиск по тегам
fix: исправить гонку в загрузке профиля
docs: обновить README
chore(deps): обновить vite
```

**commitlint** (на хуке `commit-msg`) проверяет, что сообщение соответствует формату, и **отклоняет** коммит, если нет.

<b class="text-on-semi-light">Зачем формат</b> - <span class="text-gray">Структурированные сообщения позволяют **автоматизировать**: генерировать changelog, определять версию по semver (`feat` → minor, `fix` → patch, `BREAKING CHANGE` → major). Инструменты вроде changesets и semantic-release строят релизы на этом. Плюс история становится читаемой.</span>

## Оборона в глубину

Качество защищают на **трёх уровнях**, и каждый важен:

```
1. Редактор   → подсветка + автофикс при сохранении (мгновенно)
2. pre-commit → lint-staged на изменённых файлах (быстро, локально)
3. CI         → полная проверка: lint, typecheck, test, build (авторитетно)
```

<b class="text-on-semi-light">Почему нельзя полагаться только на хуки</b> - <span class="text-gray">Локальные хуки **можно обойти** (`git commit --no-verify`), их можно не установить, окружения различаются. Поэтому **настоящий гейт - это CI**: он запускается на сервере, его не обойти, и именно он решает, можно ли мержить. Хуки дают быструю локальную обратную связь, CI - финальную гарантию.</span>

---

## Что куда

- **pre-commit (быстро):** формат, линт изменённых файлов, автофикс.
- **commit-msg:** проверка формата сообщения.
- **pre-push (опционально):** быстрые тесты затронутого.
- **CI (полно):** полный линт, `tsc --noEmit`, все тесты, сборка.

> Не клади в pre-commit полный прогон тестов или type-check всего проекта - это замедлит коммит и спровоцирует `--no-verify`. Тяжёлое - в CI.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое git-хуки и зачем husky?</b>
<span class="text-gray">Скрипты, запускаемые Git на событиях (pre-commit, commit-msg). husky делает их частью репозитория - версионируемыми и автоустанавливаемыми у всей команды, в отличие от «голых» хуков в .git/hooks.</span>

<b class="text-on-semi-light">Зачем lint-staged?</b>
<span class="text-gray">Прогонять линтер/форматтер только на staged-файлах, а не на всём проекте - чтобы коммит был быстрым. Тяжёлые проверки выносят в CI.</span>

<b class="text-on-semi-light">Что дают Conventional Commits?</b>
<span class="text-gray">Структурированный формат сообщений (feat/fix/...) позволяет автоматизировать changelog и определение версии по semver. commitlint проверяет формат на commit-msg.</span>

<b class="text-on-semi-light">Почему нельзя полагаться только на pre-commit хуки?</b>
<span class="text-gray">Их можно обойти (`--no-verify`), не установить, окружения различаются. Настоящий гейт - CI на сервере: его не обойти, и он решает возможность мержа. Хуки - лишь быстрая локальная обратная связь.</span>

<b class="text-on-semi-light">Что не стоит класть в pre-commit?</b>
<span class="text-gray">Полный прогон тестов и type-check всего проекта - они медленные и провоцируют обход хука. Это работа CI; в pre-commit - только быстрые проверки изменённых файлов.</span>
