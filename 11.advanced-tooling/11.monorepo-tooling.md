# Тулинг монорепо

**Монорепо** - несколько приложений и библиотек в одном репозитории, с общим кодом и инструментами. На масштабе это удобно, но порождает проблему: как **не пересобирать и не перетестировать всё** при каждом изменении. Её решают оркестраторы задач - Turborepo и Nx.

---

## Монорепо vs полирепо

| | Монорепо | Полирепо |
|--|----------|----------|
| Структура | всё в одном репозитории | репозиторий на пакет |
| Общий код | импортируется напрямую | через публикацию в npm |
| Атомарные изменения | один PR меняет всё | синхронизация между репо |
| Версии зависимостей | единые | расходятся |
| Сложность тулинга | выше | ниже на пакет |

<b class="text-on-semi-light">Зачем монорепо</b> - <span class="text-gray">Общий UI-кит, утилиты и конфиги переиспользуются без публикации; изменение в библиотеке и в использующем её приложении делается **одним атомарным PR**; единые версии зависимостей. Цена - нужен специальный тулинг, иначе сборки/тесты разрастаются.</span>

---

## Workspaces - основа

Базу даёт менеджер пакетов: **workspaces** связывают локальные пакеты, чтобы они импортировали друг друга как обычные зависимости (разобрано в [управлении пакетами](/content/ecosystem-libs/package-management)).

```
my-monorepo/
├─ apps/
│  ├─ web/        → импортирует @repo/ui
│  └─ admin/
├─ packages/
│  ├─ ui/         (@repo/ui)
│  └─ config/
└─ package.json   ("workspaces": ["apps/*", "packages/*"])
```

Workspaces решают **связывание**, но не **скорость** задач - для этого нужен оркестратор.

---

## Проблема масштаба

В монорепо десятки пакетов. Наивно: `npm run build` во всех. Но:

- большинство пакетов **не изменились** - пересобирать их бессмысленно;
- задачи зависят друг от друга (приложение нельзя собрать раньше его библиотеки);
- в CI это превращается в минуты-десятки минут на каждый PR.

## Оркестраторы задач

### Turborepo

Описываешь **граф задач** (что от чего зависит), а Turborepo прогоняет их **параллельно**, **в правильном порядке** и с **кешированием**.

```jsonc
// turbo.json
"tasks": {
  "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
  "test":  { "dependsOn": ["build"] }
}
```

`^build` значит «сначала собери зависимости пакета». Turborepo сам строит порядок.

### Nx

То же ядро (граф задач + кеш) плюс больше: **генераторы** кода, визуализация графа зависимостей, плагины под фреймворки, продвинутый анализ затронутого. Тяжелее Turborepo, но мощнее для крупных организаций.

---

## Кеширование задач

Ключевая идея, ради которой всё затевается. Оркестратор считает **хеш входов** задачи (исходники, зависимости, конфиг). Если хеш уже встречался - результат берётся **из кеша**, задача **не выполняется**.

```
build пакета ui:
  входы не менялись → CACHE HIT → мгновенно (взять dist из кеша)
  входы изменились  → выполнить заново → закешировать
```

<b class="text-on-semi-light">Remote cache</b> - <span class="text-gray">Кеш может быть **общим** (remote cache): собрал коллега или CI - ты и все остальные получают готовый результат, не пересобирая. Это радикально ускоряет CI: если пакет не трогали, его сборка/тесты переиспользуются из общего кеша. Главная причина брать Turborepo/Nx.</span>

---

## Affected / инкрементальность

По графу зависимостей оркестратор знает, **что затронуто** изменением, и гоняет задачи только для затронутых пакетов и их зависимых.

```
изменил packages/ui → пересобрать ui + приложения, которые его используют
                       (остальное не трогать)
```

В [CI](/content/advanced-tooling/ci-cd) это означает: проверять не весь монорепо, а только то, что реально изменилось.

---

## Внутренние пакеты

Типичные общие пакеты в монорепо: `@repo/ui` (компоненты), `@repo/utils`, `@repo/eslint-config`, `@repo/tsconfig`. Они переиспользуются всеми приложениями и версионируются вместе (для публикуемых - через **Changesets**).

---

## Когда монорепо

```
Несколько приложений делят код (UI-кит, утилиты)   → монорепо
Команда хочет атомарные изменения через границы     → монорепо
Один продукт, одно приложение                       → обычный репозиторий
Независимые команды/релизы, мало общего кода         → полирепо
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое монорепо и зачем оно?</b>
<span class="text-gray">Несколько приложений/библиотек в одном репозитории. Даёт переиспользование общего кода без публикации, атомарные изменения через границы пакетов и единые версии. Цена - нужен специальный тулинг.</span>

<b class="text-on-semi-light">Зачем нужны Turborepo/Nx, если есть workspaces?</b>
<span class="text-gray">Workspaces связывают пакеты, но не решают скорость задач. Оркестраторы добавляют граф задач, параллельный запуск в правильном порядке, кеширование и сборку только затронутого.</span>

<b class="text-on-semi-light">Как работает кеширование задач?</b>
<span class="text-gray">Считается хеш входов задачи (код, зависимости, конфиг). Совпал с прошлым - результат берётся из кеша, задача не выполняется. Remote cache делит кеш между командой и CI.</span>

<b class="text-on-semi-light">Что такое affected-сборки?</b>
<span class="text-gray">По графу зависимостей оркестратор определяет, что затронуто изменением, и гоняет задачи только для затронутых пакетов и зависимых - в CI это огромная экономия.</span>

<b class="text-on-semi-light">Монорепо или полирепо - когда что?</b>
<span class="text-gray">Монорепо - когда несколько приложений делят код и нужны атомарные изменения. Полирепо - независимые команды и релизы с малым количеством общего кода.</span>
