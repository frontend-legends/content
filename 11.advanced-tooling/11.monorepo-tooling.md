# Монорепо

Как держать несколько пакетов и приложений в одном репозитории: workspaces и ссылки между пакетами, «призрачные» зависимости, оркестраторы задач с графом и кешем, запуск только затронутого и внутренние пакеты. Спрашивают, зачем монорепо, зачем Turborepo или Nx, если есть workspaces, и как работает кеш задач. Глубже — почему код работает в npm и падает в pnpm, от чего зависит хеш задачи и когда монорепо — плохая идея.

::tldr
- **Монорепо — несколько пакетов в одном репозитории с общей историей.** Одно изменение затрагивает UI-кит и все приложения сразу, без публикации версий и синхронизации.
- **Workspaces связывают локальные пакеты символическими ссылками в `node_modules`:** `import '@shop/ui'` ведёт прямо в `packages/ui`. Это умеют npm, pnpm, Yarn и Bun.
- **При поднятых зависимостях работает и необъявленная зависимость — до первой смены менеджера или раскладки.** pnpm держит `node_modules` изолированными, и такой импорт падает сразу.
- **Оркестратор строит граф задач по зависимостям пакетов,** запускает их в правильном порядке и параллельно, а результат кеширует по хешу входов: исходников, зависимостей, конфигурации.
- **На масштабе важен запуск только затронутого:** пакеты, изменённые с базовой ветки, и их зависимые — остальное берётся из локального или удалённого кеша.
::

## Зачем монорепо

Сквозной пример — магазин из трёх пакетов:

```text
packages/utils   — форматирование денег и дат
packages/ui      — компоненты, используют utils
apps/web         — приложение, использует ui
```

В **полирепо** каждый пакет в своём репозитории. Исправить форматирование цены — это изменить `utils`, опубликовать версию, обновить её в `ui`, опубликовать `ui`, обновить в `web`. Три репозитория, три :term[PR]{def="pull request: предложение влить изменения ветки в основную, с обсуждением и проверками"}, и до конца цепочки приложения живут на разных версиях.

В **монорепо** то же изменение — один коммит, который сразу проверяется со всеми потребителями. Плюсы:

- **атомарные изменения** — API и все его использования меняются вместе;
- **общие конфигурации** — линтер, `tsconfig`, CI в одном месте;
- **видимость** — поиск по всему коду, рефакторинг через границы пакетов.

Минусы появляются на масштабе: долгие сборки и тесты всего подряд, сложная настройка прав, большой репозиторий. Их и решают инструменты ниже.

## Workspaces

```json
{
  "name": "shop",
  "private": true,
  "workspaces": ["packages/*", "apps/*"]
}
```

`npm install` в корне находит пакеты по шаблонам и **связывает** их: `node_modules/@shop/ui` — символическая ссылка на `packages/ui`. В проверке ссылка вела ровно в папку пакета. Импорт `@shop/ui` из `apps/web` идёт в исходники, и изменение в `ui` сразу видно приложению, без публикации.

Команды для пакетов:

```bash
npm run build -w @shop/ui           # в одном пакете
npm run build --workspaces          # во всех
pnpm --filter @shop/web build       # pnpm
```

В pnpm workspaces описываются в `pnpm-workspace.yaml`, а локальную зависимость указывают протоколом `workspace:*` — при публикации он заменится на конкретную версию.

### Призрачные зависимости

`apps/web` в примере импортирует `@shop/utils` напрямую, но в своём `package.json` его не указал — зависимость есть только у `ui`.

**В npm это работает.** npm поднимает зависимости в корневой `node_modules`, а поиск модуля идёт вверх по папкам (подробно — в [Модульных системах](/content/advanced-tooling/module-systems)), и `utils` находится. В проверке `web` запустился и вывел цену.

**В pnpm это падает** с `Cannot find package '@shop/utils'`. pnpm кладёт в `node_modules` пакета только то, что он объявил, а остальное — в изолированное хранилище. После явного объявления зависимости в проверке всё заработало.

Это и есть **призрачная зависимость** — та, что работает случайно. В npm она сломается, когда `ui` перестанет зависеть от `utils` или когда раскладка `node_modules` изменится. pnpm ловит её сразу, поэтому его часто выбирают для монорепо. Подробнее о менеджерах пакетов — в [Управлении пакетами](/content/ecosystem-libs/package-management).

## Оркестраторы задач

Workspaces умеют запустить скрипт во всех пакетах, но не знают:

- **порядок** — `ui` нужно собрать до `web`, а `utils` до `ui`;
- **что уже сделано** — `utils` не менялся, пересобирать его незачем;
- **что затронуто** — изменение в `ui` не касается других приложений.

Это добавляют оркестраторы — **Turborepo** и **Nx**:

```json
// turbo.json
{
  "tasks": {
    "build": { "dependsOn": ["^build"], "outputs": ["dist/**"] },
    "test": { "dependsOn": ["build"] },
    "lint": {}
  }
}
```

`"^build"` означает «сначала `build` у всех зависимостей пакета». По `package.json` пакетов оркестратор строит **граф задач** и выполняет его: независимые задачи — параллельно, зависимые — по порядку. В проверке Turborepo собрал пакеты в порядке `utils`, `ui`, `web`.

### Кеш задач

Перед запуском задачи оркестратор считает **хеш её входов**: исходники пакета, хеши зависимостей, `package.json`, lock-файл, переменные окружения, указанные в конфигурации. Если такой хеш уже встречался, задача не выполняется, а её результат — файлы из `outputs` и вывод в консоль — восстанавливается из кеша.

Проверено на трёх запусках:

| Запуск | Что изменилось | Результат |
| --- | --- | --- |
| первый | — | собраны все три пакета |
| второй | ничего | «3 cached, 3 total», ни одна задача не запускалась |
| третий | правка в `ui` | `utils` из кеша, пересобраны `ui` и зависимый `web` |

Изменение `ui` меняет хеш `ui`, а через него — хеш `web`. `utils` от `ui` не зависит, и его хеш прежний.

**Удалённый кеш** хранит результаты на сервере, общем для команды и CI. Собрал один разработчик — у остальных и в CI задача придёт из кеша. Turborepo использует Vercel Remote Cache или свой сервер, Nx — Nx Cloud.

Ловушка кеша — **неучтённый вход**. Если сборка читает переменную окружения, которой нет в конфигурации задачи, оркестратор её не видит и вернёт из кеша сборку со старым значением. Переменные окружения перечисляют в `env` задачи.

### Только затронутое

В CI проверять весь монорепо на каждый PR — долго. Оркестратор запускает задачи только для пакетов, изменённых относительно базы, и тех, кто от них зависит:

```bash
turbo run build test --filter=...[origin/main]   # изменённые с main и их зависимые
nx affected -t build test                        # то же в Nx
```

В проверке изменение `utils` в последнем коммите дало план на `utils`, `ui` и `web` — все, кто прямо или через другой пакет от него зависит.

### Turborepo и Nx

| | Turborepo | Nx |
| --- | --- | --- |
| Подход | минимальный: граф задач и кеш поверх workspaces | платформа: генераторы, плагины, граф проекта |
| Настройка | один `turbo.json` | больше конфигурации, но и больше автоматики |
| Удалённый кеш | Vercel Remote Cache или свой сервер | Nx Cloud или свой сервер |
| Когда | нужен быстрый кеш без перестройки проекта | большой монорепо, единые генераторы и правила |

## Внутренние пакеты

Пакет внутри монорепо можно потреблять двумя способами:

- **собранным** — у пакета свой шаг сборки в `dist`, приложение импортирует результат. Это честная граница, но каждое изменение требует пересборки пакета, и без кеша это медленно;
- **из исходников** — `exports` пакета указывает прямо на `src/index.ts`, а собирает и транспилирует приложение. Нет отдельной сборки и проще разработка, но пакет нельзя опубликовать как есть, а приложение должно уметь компилировать его код.

Для TypeScript в монорепо используют **project references**: каждый пакет — свой проект, и `tsc -b` проверяет их по графу, переиспользуя результат для неизменённых (подробно — в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling)).

Публикуемые пакеты версионируют через **Changesets**: разработчик описывает изменение, а при релизе инструмент повышает версии изменённых пакетов и их зависимых и пишет changelog (подробно о формате коммитов — в [Git-хуках](/content/advanced-tooling/git-hooks-and-quality-gates)).

## Когда монорепо

Подходит:

- несколько приложений с общим UI-китом и утилитами;
- фронтенд и бэкенд на одном языке, которые делят типы и контракты (подробно — в [Сквозной типобезопасности](/content/modern-dev/end-to-end-typesafety));
- общая команда, которая меняет связанный код одновременно.

Не подходит или требует осторожности:

- независимые проекты разных команд без общего кода — монорепо добавит только связность и общую очередь CI;
- очень разные стеки и циклы выпуска;
- строгие требования к правам доступа на уровне кода.

Монорепо — это не про число репозиториев, а про то, как часто код меняется вместе. Организационные стороны — владение кодом, команды и границы — в [Масштабировании и командах](/content/architecture/scalability-and-teams).

## Красные флаги в ответе

- **«Монорепо — это просто одна папка с проектами».** Без workspaces и оркестратора это все минусы монорепо без плюсов.
- **«Если импорт работает, зависимость в порядке».** В npm работает и необъявленная зависимость — до смены раскладки, pnpm её ловит.
- **«Кеш задач — это кеш `node_modules`».** Он хранит результаты задач по хешу их входов.
- **«Turborepo пересоберёт только изменённый пакет».** Ещё и всех, кто от него зависит.
- **«Монорепо подходит всем».** Без общего кода оно добавляет только связность и общую очередь CI.

## Как спрашивают на собеседовании

::question
Что такое монорепо и зачем оно?

#answer
Несколько пакетов и приложений в одном репозитории с общей историей. Изменение общего кода и всех его потребителей — один атомарный коммит, без публикации промежуточных версий. Плюс общие конфигурации и CI.

#more
Цена на масштабе — долгие сборки и тесты, если запускать всё подряд, сложнее права доступа. Это решают workspaces, оркестраторы задач с кешем и запуск только затронутого. Альтернатива — полирепо, где пакеты связаны через публикацию версий.
::

::question
Зачем Turborepo или Nx, если есть workspaces?

#answer
Workspaces связывают пакеты и запускают скрипты во всех сразу, но не знают порядка, не помнят, что уже сделано, и не определяют, что затронуто. Оркестратор строит граф задач по зависимостям, выполняет его параллельно и по порядку и кеширует результат.

#more
`"dependsOn": ["^build"]` в Turborepo — собрать зависимости раньше пакета. Удалённый кеш делит результаты между разработчиками и CI. `--filter=...[origin/main]` или `nx affected` запускают задачи только для изменённых пакетов и их зависимых.
::

::question
Как работает кеш задач?

#answer
Перед запуском оркестратор считает хеш входов задачи: исходники пакета, хеши зависимостей, `package.json`, lock-файл, указанные переменные окружения. Если хеш уже встречался, задача не выполняется — её выходные файлы и лог восстанавливаются из кеша.

#more
Изменение пакета меняет его хеш и хеши всех зависимых, поэтому пересобирается цепочка, а остальное берётся из кеша. Удалённый кеш хранит результаты на сервере. Неучтённая переменная окружения — частая ошибка: кеш вернёт сборку со старым значением.
::

::question
Что такое призрачная зависимость?

#answer
Пакет импортирует зависимость, которую не объявил в своём `package.json`, и это работает, потому что менеджер поднял её в корневой `node_modules` ради другого пакета. Работает случайно и сломается при смене раскладки.

#more
npm и Yarn с поднятыми зависимостями её пропускают, pnpm держит `node_modules` изолированными и падает с «Cannot find package». Поэтому pnpm часто выбирают для монорепо. Обнаружить такие импорты помогают правила линтера, например `import/no-extraneous-dependencies`.
::

::question
Что такое affected-сборки?

#answer
Запуск задач только для пакетов, изменённых относительно базовой ветки, и всех, кто от них зависит. Остальное в CI не проверяется или берётся из кеша.

#more
В Turborepo — `--filter=...[origin/main]`, в Nx — `nx affected`. Граф зависимостей нужен, чтобы найти и прямых, и транзитивных зависимых. Изменение общего файла вроде корневого `tsconfig` или lock-файла затрагивает все пакеты.
::

::question
Монорепо или полирепо — когда что?

#answer
Монорепо — когда код часто меняется вместе: приложения с общим UI-китом, фронтенд и бэкенд с общими типами, одна команда. Полирепо — для независимых проектов разных команд с разными стеками и циклами выпуска.

#more
Монорепо требует инструментов — workspaces, оркестратор, кеш, — иначе CI становится общей пробкой. Полирепо требует дисциплины версий и публикации. Решают по частоте совместных изменений, а не по моде.
::

## Практика

::practice{title="В CI падает импорт, а локально работает"}
Проект перевели с npm на pnpm, и сборка приложения упала:

```text
Error: Cannot find package '@shop/utils' imported from apps/web/index.js
```

#solution
`apps/web` импортирует `@shop/utils`, но в своём `package.json` его не объявил. В npm пакет находился в корневом `node_modules`, потому что от него зависел `ui`. pnpm кладёт в `node_modules` пакета только объявленное, и призрачная зависимость перестала находиться.

```json
{
  "name": "@shop/web",
  "dependencies": {
    "@shop/ui": "workspace:*",
    "@shop/utils": "workspace:*"
  }
}
```

Объявляют всё, что импортируют напрямую. pnpm здесь не мешает, а показывает ошибку, которая в npm жила незаметно. В проверке npm-версия запустилась, pnpm-версия упала с этой ошибкой, а после объявления зависимости заработала.
::

::practice{title="Сборка из кеша со старым адресом API"}
После смены переменной окружения `API_URL` в CI выложилась сборка со старым адресом. Turborepo показал, что `build` взят из кеша.

#solution
Сборка читает `API_URL`, но Turborepo не знает об этом: переменной нет во входах задачи. Хеш не изменился, и оркестратор вернул прошлый результат. Переменные, от которых зависит результат, перечисляют:

```json
{
  "tasks": {
    "build": {
      "dependsOn": ["^build"],
      "outputs": ["dist/**"],
      "env": ["API_URL", "VITE_*"]
    }
  }
}
```

Теперь смена значения меняет хеш, и задача выполнится заново. Turborepo в строгом режиме по умолчанию скрывает от задач неперечисленные переменные, чтобы такие ошибки было видно сразу. В проверке кеш срабатывал, пока входы задачи не менялись, а правка исходника пересобрала пакет и его зависимых.
::
