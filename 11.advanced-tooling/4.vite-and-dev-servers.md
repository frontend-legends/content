# Vite и dev-серверы

Как устроен Vite: dev-сервер, который не собирает приложение, пребандлинг зависимостей, HMR и его границы, переменные окружения, ассеты и продакшен-сборка на Rolldown. Спрашивают, почему Vite быстрый, что такое пребандлинг и HMR и почему Vite не собирает бандл в разработке, но собирает в продакшене. Глубже — когда HMR перезагружает страницу целиком, почему переменная окружения оказалась `undefined` и чем Vite 8 отличается от предыдущих версий.

::tldr
- **В разработке Vite не собирает приложение:** браузер запрашивает модули по `<script type="module">`, а сервер преобразует только запрошенный файл. Поэтому запуск не зависит от размера проекта.
- **Зависимости из `node_modules` пребандлятся один раз:** CommonJS превращается в ESM, а пакет из сотен файлов — в один модуль. Голые импорты переписываются на `/node_modules/.vite/deps/…`.
- **HMR заменяет изменённый модуль без перезагрузки страницы,** поднимаясь по графу до ближайшей границы — модуля, который принимает обновление. Нет границы — страница перезагрузится целиком.
- **В код попадают только переменные `VITE_*`.** Остальные из `.env` в бандл не встраиваются, а всё встроенное — публично.
- **Продакшен Vite собирает:** с Vite 8 и в разработке, и в продакшене работает один бандлер на Rust — Rolldown, вместо пары esbuild и Rollup.
::

---

## Старая проблема

Классический dev-сервер — webpack-dev-server — перед запуском **собирает всё приложение** в бандл в памяти. При изменении файла пересобирает затронутую часть и отдаёт обновление. На маленьком проекте это секунды. На большом — минута запуска и секунды на каждое сохранение: время растёт вместе с размером кода.

Vite исходит из двух наблюдений:

1. **Браузеры понимают ES-модули.** Собирать граф может сам браузер, запрашивая файлы по `import`.
2. **Код делится на две части.** Исходники приложения меняются постоянно, но их немного на одной странице. Зависимости из `node_modules` огромные, но почти не меняются.

Сквозной пример — магазин на Vue: `main.js` импортирует `vue`, свой модуль `counter.js`, картинки и лениво — корзину. Всё ниже проверено на Vite 8.

## Разработка без сборки

```text
браузер: GET /src/main.js
сервер:  преобразовать main.js → отдать
браузер: видит import → GET /src/counter.js, GET /node_modules/.vite/deps/vue.js
сервер:  преобразовать counter.js → отдать; vue.js уже готов в кеше
```

Сервер преобразует **только запрошенный** модуль: стирает типы, компилирует `.vue` и JSX, подставляет переменные окружения, переписывает импорты в адреса. Модули, которые не нужны текущей странице, не трогаются вовсе. Поэтому запуск не зависит от размера проекта.

В проверке `transformRequest('/src/main.js')` вернул модуль с переписанным импортом `vue` и без кода соседних модулей.

### Пребандлинг зависимостей

Отдавать зависимости как есть нельзя по двум причинам:

- **многие пакеты в CommonJS**, а браузер понимает только ESM;
- **пакет может состоять из сотен файлов:** `lodash-es` — это сотни модулей, и импорт одной функции превратился бы в сотни запросов.

Поэтому при первом запуске Vite находит зависимости в исходниках и **пребандливает** их: каждый пакет собирается в один ESM-файл в `node_modules/.vite/deps`. Голые импорты в коде переписываются на эти файлы:

```js
import { createApp, h } from 'vue';
// →
import { createApp, h } from "/node_modules/.vite/deps/vue.js?v=1a2b3c4d";
```

Параметр `?v=` — хеш состояния зависимостей. Браузер кеширует такие файлы надолго, а после обновления пакетов хеш меняется. Если Vite нашёл новую зависимость уже после запуска, он пребандлит её и перезагрузит страницу — отсюда редкие перезагрузки при первом открытии новых страниц. `optimizeDeps.include` заранее перечисляет такие зависимости.

## HMR

**Hot Module Replacement** — замена изменённого модуля в работающей странице без перезагрузки. Состояние приложения — введённые данные, открытая модалка — сохраняется.

Как это работает:

1. Сервер следит за файлами. Сохранили `counter.js` — сервер находит его в **графе модулей**.
2. Ищет **границу HMR**: модуль, который объявил, что умеет принять обновление, — сам изменённый модуль или один из тех, кто его импортирует, вверх по графу.
3. Отправляет браузеру по :term[WebSocket]{def="протокол постоянного двустороннего соединения браузера с сервером"} сообщение: какие модули загрузить заново.
4. Браузер загружает новую версию модуля, и граница применяет её.

Граница объявляется через `import.meta.hot`:

```js
// counter.js
export const counter = () => 1;
if (import.meta.hot) import.meta.hot.accept();   // принимаю свои обновления
```

В проверке Vite отметил такой модуль как принимающий обновления, а модуль без `accept` — нет, и граф знал, кто импортирует `counter.js`. Если при подъёме по графу граница не нашлась, Vite **перезагружает страницу**.

Руками `accept` почти никто не пишет: плагины фреймворков вставляют его сами. `@vitejs/plugin-vue` делает каждый `.vue`-файл границей и заменяет компонент с сохранением состояния. Для React то же делает React Refresh. Поэтому обновление компонента — мгновенно, а изменение обычного модуля, который импортируют многие, например файла с константами, может перезагрузить страницу целиком.

Время HMR **не зависит от размера проекта**: обновляется один модуль и его граница, а не пересобирается бандл.

## Окружение и ассеты

### Переменные окружения

```bash
# .env
VITE_API_URL=https://api.shop.example
DB_PASSWORD=secret123
```

```js
import.meta.env.VITE_API_URL;   // 'https://api.shop.example'
import.meta.env.DB_PASSWORD;    // undefined
import.meta.env.DEV, import.meta.env.PROD, import.meta.env.MODE;
```

В код встраиваются только переменные с префиксом `VITE_`. Это защита от случайной утечки: в проверке `DB_PASSWORD` не попал ни в модуль dev-сервера, ни в продакшен-бандл. Но всё, что с префиксом, — **публично**: оно лежит в JavaScript, который скачивает любой посетитель (подробно — в [Безопасности Vue](/content/vuejs/security)). Файлы `.env.production`, `.env.development` и `.env.local` выбираются по режиму, а `.env.local` не коммитят.

### Ассеты

```js
import logo from './logo.svg';     // строка-адрес
import photo from './photo.png';
```

Импорт картинки даёт её адрес. В продакшене:

- **маленькие файлы** — меньше `build.assetsInlineLimit`, по умолчанию 4 КБ, — встраиваются в код как `data:`-адрес, без отдельного запроса;
- **большие** копируются в `dist/assets` с хешем в имени;
- **папка `public/`** копируется как есть, без хешей — для `robots.txt`, `favicon.ico` и файлов, на которые ссылаются по точному имени.

Все три случая проверены: SVG стал `data:image/svg+xml`, PNG — `assets/photo-[hash].png`, а `robots.txt` лёг в корень `dist`.

### Остальное

- **`server.proxy`** перенаправляет `/api` на бэкенд и избавляет от CORS в разработке;
- **CSS** — `import './style.css'` подключает стили с HMR, `*.module.css` — CSS Modules, препроцессоры работают после установки пакета;
- **Environment API** позволяет одному серверу обслуживать несколько окружений — браузер, :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"}, :term[edge]{def="код, который выполняется на серверах CDN рядом с пользователем"}, — на нём построены Nuxt, :term[SvelteKit]{def="мета-фреймворк для Svelte: маршруты, серверный рендеринг, сборка"} и другие мета-фреймворки.

## Продакшен-сборка

В продакшене Vite **собирает** приложение: без сборки пользователь получил бы водопад запросов по глубине графа (подробно — в [Бандлерах](/content/advanced-tooling/bundlers)).

До Vite 8 сборка была двухмоторной: в разработке пребандлинг и трансформации делал **esbuild**, а продакшен собирал **Rollup**. Это давало быстрый dev, хороший продакшен-вывод и редкие, но неприятные расхождения: код работал в разработке и ломался в сборке, потому что их делали разные инструменты.

С Vite 8 оба режима работают на **Rolldown** — бандлере на Rust, совместимом с плагинами Rollup. Трансформации делает Oxc, минификацию CSS — Lightning CSS. Сборка в разы быстрее, а разработка и продакшен используют один инструмент. В проверке Vite 8 сообщил версию Rolldown, на котором работает.

Что Vite добавляет в сборку сам:

- **хеши в именах** и переписанные пути в `index.html`;
- **предзагрузку чанков:** при ленивом `import()` Vite заранее запрашивает зависимости ленивого чанка через `modulepreload`, чтобы они не грузились водопадом — в проверке такая предзагрузка оказалась в коде точки входа;
- **разбиение CSS** по чанкам — стили ленивой страницы загружаются вместе с ней;
- **выбрасывание кода для разработки** и минификацию.

`vite preview` запускает локальный сервер для собранного `dist`, чтобы проверить продакшен-сборку перед выкладкой.

## Vite и webpack-dev-server

| | webpack-dev-server | Vite |
| --- | --- | --- |
| Запуск | собирает всё приложение | отдаёт модули по запросу |
| Время запуска | растёт с размером проекта | почти не зависит от размера |
| Обновление | пересборка затронутого графа | замена одного модуля |
| Зависимости | в бандле вместе с кодом | пребандлинг один раз, долгий кеш |
| Продакшен | тот же webpack | Rolldown |

Слабые места Vite в разработке — очень большие страницы с тысячами модулей, где водопад запросов к локальному серверу становится заметным, и первые открытия, когда нужен пребандлинг новых зависимостей. Против первого помогает `server.warmup` — заранее преобразовать часто используемые модули.

## Как менялся Vite

Актуально на ноябрь 2026.

| Версия | Изменения |
| --- | --- |
| Vite 1–2 (2020–2021) | dev-сервер на нативных ES-модулях, пребандлинг через esbuild, сборка через Rollup |
| Vite 5 (2023) | Rollup 4, CommonJS-API Node.js объявлен устаревшим |
| Vite 6 (2024) | Environment API для SSR и нескольких окружений |
| Vite 7 (2025) | минимальный Node.js 20.19, цель по умолчанию — Baseline Widely Available |
| Vite 8 (2026) | Rolldown вместо esbuild и Rollup, Oxc для трансформаций, Lightning CSS для минификации CSS |

## Красные флаги в ответе

- **«Vite быстрый, потому что esbuild быстрый».** Главное — отсутствие сборки в разработке: сервер преобразует только запрошенное.
- **«HMR пересобирает бандл быстрее».** Он заменяет один модуль до ближайшей границы, бандла в разработке нет.
- **«Все переменные из `.env` доступны в коде».** Только `VITE_*`, и они публичны.
- **«Раз в dev работает без сборки, можно и в продакшене».** Без сборки — водопад запросов, нет tree shaking и долгого кеша.
- **«В Vite разные инструменты для dev и prod».** Так было до Vite 8, теперь оба режима на Rolldown.

## Как спрашивают на собеседовании

::question
Почему Vite быстрый в разработке?

#answer
Он не собирает приложение. Браузер запрашивает модули сам по `<script type="module">`, а сервер преобразует только запрошенные файлы. Зависимости пребандлятся один раз и кешируются. Время запуска и обновления не растёт с размером проекта.

#more
Трансформации делает нативный инструмент — в Vite 8 это Oxc и Rolldown, раньше esbuild. HMR заменяет один модуль до ближайшей границы. Узкие места — страницы с тысячами модулей и пребандлинг новых зависимостей, который перезагружает страницу.
::

::question
Что такое пребандлинг зависимостей?

#answer
При первом запуске Vite находит импорты из `node_modules` и собирает каждый пакет в один ESM-файл в `node_modules/.vite/deps`. Это превращает CommonJS в ESM и заменяет сотни внутренних модулей пакета одним запросом.

#more
Голые импорты переписываются на `/node_modules/.vite/deps/vue.js?v=хеш`, и браузер кеширует их надолго. Новая зависимость, найденная после запуска, вызывает повторный пребандлинг и перезагрузку страницы, поэтому такие зависимости перечисляют в `optimizeDeps.include`.
::

::question
Почему Vite не собирает бандл в dev, но собирает в prod?

#answer
В разработке сервер локальный, водопад запросов терпим, а важнее мгновенный запуск и обновление. У пользователя водопад по глубине графа стоит секунды, а без сборки нет tree shaking, минификации, хешей и разбиения на чанки.

#more
Раньше это делали разные инструменты — esbuild в разработке и Rollup в продакшене, — и иногда поведение расходилось. С Vite 8 оба режима на Rolldown. В сборку Vite добавляет предзагрузку чанков через `modulepreload`, чтобы ленивые страницы не грузились водопадом.
::

::question
Что такое HMR и когда он перезагружает страницу?

#answer
Замена изменённого модуля в работающей странице без перезагрузки и с сохранением состояния. Сервер находит модуль в графе, поднимается к ближайшей границе — модулю с `import.meta.hot.accept` — и браузер загружает новую версию.

#more
Если границы нет до самой точки входа, страница перезагружается целиком. Плагины фреймворков делают границей каждый компонент, поэтому правки компонентов применяются мгновенно, а правка общего модуля без границы, например файла конфигурации, может перезагрузить страницу.
::

::question
Почему переменная окружения undefined?

#answer
В код встраиваются только переменные с префиксом `VITE_`. `import.meta.env.API_URL` без префикса будет `undefined` — это защита от случайной утечки секретов.

#more
Другие причины — файл `.env` не того режима, переменная добавлена без перезапуска сервера, обращение через `process.env` вместо `import.meta.env`. Всё с префиксом `VITE_` попадает в бандл и публично, поэтому секреты в нём не хранят.
::

::question
Что изменилось в Vite 8?

#answer
Сборщиком и в разработке, и в продакшене стал Rolldown — бандлер на Rust, совместимый с плагинами Rollup. Раньше dev работал на esbuild, а продакшен — на Rollup.

#more
Трансформации делает Oxc, CSS минифицирует Lightning CSS, опции `esbuild` устарели. Сборка в разы быстрее, и разработка ведёт себя как продакшен. Изменились правила импорта по умолчанию из CommonJS, и при обновлении это стоит проверить.
::

## Практика

::practice{title="HMR перезагружает страницу"}
При правке файла `src/config.js` с константами страница перезагружается целиком, и пропадает заполненная форма. Правки компонентов применяются мгновенно.

#solution
`config.js` — обычный модуль без `import.meta.hot.accept`. Vite поднимается по графу к модулям, которые его импортируют: если среди них есть компоненты, граница найдётся, но если конфигурацию импортирует `main.js` или другой модуль без границы, подъём дойдёт до точки входа, и Vite перезагрузит страницу.

```js
// config.js — принять обновление и сообщить подписчикам
export let config = { currency: '₽' };

if (import.meta.hot) {
  import.meta.hot.accept((next) => {
    config = next.config;
    window.dispatchEvent(new CustomEvent('config-updated'));
  });
}
```

Чаще проще ничего не делать: перезагрузка на правку конфигурации — нормальная цена. Важное — понимать, почему одни правки мгновенны, а другие нет. В проверке модуль с `accept` Vite отметил как принимающий обновления, а модуль без него — нет.
::

::practice{title="Пароль от базы в бандле"}
Разработчик добавил в `.env` строку `VITE_DB_PASSWORD=…`, потому что без префикса переменная была `undefined`.

#solution
Префикс `VITE_` — это не способ «разрешить» переменную, а пометка «эта переменная публична». Она встраивается в JavaScript, который скачивает каждый посетитель. Пароль теперь в бандле.

```bash
# .env — только публичные значения
VITE_API_URL=https://api.shop.example

# секреты — только на сервере, в переменных окружения сервера
DB_PASSWORD=…
```

Клиент обращается к своему серверу или BFF, а тот — к базе с паролем (подробно — в [API и BFF](/content/architecture/api-and-bff)). Пароль нужно сменить: он уже мог утечь вместе с выложенной сборкой. В проверке переменная без префикса не попала ни в dev-модуль, ни в продакшен-бандл.
::
