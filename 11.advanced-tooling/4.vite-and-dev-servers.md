# Vite и dev-серверы

**Vite** - современный дефолт для фронтенд-разработки, и «почему Vite быстрый» - один из самых частых вопросов 2024–2026. Ответ в том, что Vite **переосмыслил dev-сборку**: в режиме разработки он почти ничего не бандлит.

---

## Старая проблема

Классический подход (`webpack-dev-server`): чтобы показать приложение в dev, бандлер **сначала собирает весь граф**, и только потом отдаёт. Чем больше приложение, тем дольше холодный старт и пересборка - на крупных проектах это десятки секунд ожидания.

```
webpack-dev-server: собрать ВЕСЬ бандл → потом отдать → потом показать
(растёт линейно с размером приложения)
```

---

## Идея Vite

Браузеры давно поддерживают **нативные ES-модули** (`<script type="module">`). Значит, в dev можно **не бандлить вообще**: отдавать модули по запросу, а браузер сам их подтянет по `import`'ам.

```
Vite dev: отдать запрошенный модуль → браузер сам идёт по import'ам → трансформ по требованию
(не зависит от размера приложения)
```

---

## Архитектура dev-режима

Vite в разработке делает две вещи:

### 1. Пребандлинг зависимостей (esbuild)

Зависимости из `node_modules` (React, lodash) Vite **предварительно бандлит** через **esbuild** (на Go - очень быстро):

- конвертирует CJS-пакеты в ESM (браузер понимает только ESM);
- склеивает пакеты из сотен мелких файлов в несколько (иначе сотни HTTP-запросов);
- кеширует результат - повторный старт мгновенный.

### 2. Отдача исходников по требованию

Твой код (`src/`) Vite **не бандлит**, а отдаёт как нативные модули, трансформируя **каждый файл по запросу** в момент, когда браузер его просит.

```
браузер запросил App.tsx → Vite на лету: TS+JSX → JS → отдал
(трансформируется только то, что реально открыто)
```

<b class="text-on-semi-light">Почему быстро</b> - <span class="text-gray">Нет бандлинга в dev (браузер сам собирает через ESM), зависимости пребандлятся один раз сверхбыстрым esbuild, а исходники трансформируются лениво - только запрошенные файлы. Поэтому старт и пересборка почти не зависят от размера проекта.</span>

---

## HMR - Hot Module Replacement

**HMR** обновляет изменённый модуль **на месте**, без полной перезагрузки страницы, **сохраняя состояние** приложения (открытую вкладку, введённый текст).

```
изменил Button.tsx → Vite заменяет только этот модуль → состояние приложения цело
```

Как работает: модули образуют границы; при изменении файла dev-сервер по WebSocket шлёт браузеру обновление, и затрагивается только нужный модуль и его «принимающие» зависимости. В нативном ESM это особенно точечно. Фреймворк-плагины (React Fast Refresh, Vue HMR) сохраняют ещё и состояние компонентов.

> Без HMR любое изменение = full reload и потеря состояния. HMR - ключевая часть быстрого DX.

---

## Prod-сборка

В продакшене Vite **бандлит** - через **Rollup**. Возникает вопрос: почему в dev не бандлим, а в prod бандлим?

<b class="text-on-semi-light">Почему prod бандлят</b> - <span class="text-gray">Если отдать сотни нативных ESM-модулей в прод, браузер устроит «водопад» запросов (модуль грузит модуль, тот - следующий) - медленно для пользователя. Поэтому в prod нужен бандлинг, tree-shaking, минификация, code splitting. В dev этим можно пренебречь ради скорости разработки - там один разработчик на localhost, а не миллион пользователей.</span>

> Два движка (esbuild в dev, Rollup в prod) - историческое решение; оно может давать мелкие расхождения dev/prod. Новый бандлер **Rolldown** (Rust) призван унифицировать оба режима в Vite.

---

## Другие функции dev-сервера

- **Proxy** - проксировать `/api` на бэкенд, обходя CORS в разработке.
- **Переменные окружения** (`import.meta.env`, `.env`-файлы) - помни, что всё с префиксом (`VITE_`) попадает в клиентский бандл и **публично** (см. [безопасность](/content/reactjs/security)).
- Отдача статики, поддержка TS/JSX/CSS-модулей из коробки.

---

## Vite vs webpack-dev-server

| | webpack-dev-server | Vite (dev) |
|--|--------------------|------------|
| Подход | бандлит всё, потом отдаёт | нативный ESM, без бандла |
| Холодный старт | растёт с размером | почти мгновенный |
| Трансформы | свои loaders (JS) | esbuild (Go) |
| HMR | есть, но медленнее на масштабе | точечный, быстрый |
| Prod | Webpack | Rollup |

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему Vite быстрый в разработке?</b>
<span class="text-gray">Он не бандлит исходники в dev, а отдаёт их как нативные ESM-модули, трансформируя по запросу. Зависимости пребандлятся один раз через esbuild (Go) и кешируются. Скорость не зависит от размера приложения.</span>

<b class="text-on-semi-light">Что такое пребандлинг зависимостей?</b>
<span class="text-gray">Vite заранее прогоняет пакеты из node_modules через esbuild: конвертирует CJS в ESM и склеивает множество мелких файлов в несколько, чтобы избежать сотен HTTP-запросов. Результат кешируется.</span>

<b class="text-on-semi-light">Почему Vite не бандлит в dev, но бандлит в prod?</b>
<span class="text-gray">В dev нативный ESM позволяет не бандлить - быстрее. В prod сотни ESM-модулей вызвали бы водопад запросов у пользователя, поэтому нужны бандлинг, tree-shaking и минификация (Rollup).</span>

<b class="text-on-semi-light">Что такое HMR?</b>
<span class="text-gray">Hot Module Replacement - замена изменённого модуля на месте без полной перезагрузки, с сохранением состояния приложения. Dev-сервер по WebSocket шлёт обновление только затронутого модуля.</span>

<b class="text-on-semi-light">Какой минус у двух движков (esbuild dev / Rollup prod)?</b>
<span class="text-gray">Возможны мелкие расхождения поведения dev и prod. Поэтому появился Rolldown (Rust), чтобы унифицировать оба режима в Vite.</span>
