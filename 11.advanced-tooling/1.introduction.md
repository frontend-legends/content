# Введение в тулинг

Вводная история главы: зачем между исходниками и браузером стоит конвейер инструментов, из каких шагов он состоит, чем разработка отличается от продакшен-сборки и из чего собирают тулчейн в 2026 году. Спрашивают, зачем фронтенду сборка, из каких этапов она состоит и чем dev отличается от prod. Глубже — почему dev-сервер не собирает бандл, откуда в именах файлов хеши и куда пропадает код для разработки.

::tldr
- **Браузер исполняет HTML, CSS и JavaScript, а пишут на TypeScript, JSX, `.vue` и модулях из `node_modules`.** Тулинг закрывает этот разрыв: стирает типы, разрешает импорты, собирает и оптимизирует.
- **Сборка — конвейер:** разрешить модули и построить граф, преобразовать каждый файл, собрать граф в чанки, оптимизировать и выдать файлы с хешами в именах.
- **В разработке нужна скорость обратной связи, в продакшене — размер и кеш.** Dev-сервер отдаёт модули по одному и обновляет их на лету, продакшен-сборка минифицирует, выбрасывает неиспользуемое и код для разработки.
- **Хеш содержимого в имени файла** позволяет кешировать ассеты навсегда: изменился код — изменилось имя, неизменённые файлы остаются в кеше браузера.
- **Тулчейн смещается к нативным инструментам:** Vite собирает на Rust-бандлере Rolldown, компилятор TypeScript переписан на Go, а линтеры и форматтеры на Rust в десятки раз быстрее JavaScript-аналогов.
::

## Зачем нужен тулинг

Браузер умеет немного: HTML, CSS, JavaScript и WebAssembly. А код приложения выглядит иначе:

- **TypeScript, JSX, `.vue`, `.svelte`** — браузер их не понимает, нужна трансформация в JavaScript;
- **импорты из `node_modules`** — `import { ref } from 'vue'` браузер не разрешит: он не знает, где лежит пакет;
- **сотни модулей** — загружать каждый отдельным запросом долго, особенно на мобильной сети;
- **новый синтаксис** — для старых браузеров его понижают, а недостающие API добавляют полифилами;
- **Sass, PostCSS, CSS Modules** — нужно скомпилировать в обычный CSS;
- **оптимизация** — минификация, удаление неиспользуемого, разбиение на части, хеши для кеша.

Тулинг закрывает разрыв между тем, как удобно писать, и тем, что можно быстро загрузить и выполнить у пользователя.

Сквозной пример — маленькое приложение на Vite:

```text
index.html                 <script type="module" src="/src/main.ts">
src/main.ts                импортирует style.css и price.ts, выводит цену
src/price.ts               formatPrice и неиспользуемая unused
src/style.css
```

Все утверждения этой истории проверены на нём настоящим Vite 8.

## Конвейер сборки

Любая сборка — последовательность шагов:

```text
исходники (.ts, .tsx, .vue, .css)
   │ 1. разрешение   — найти файл по каждому импорту и построить граф зависимостей
   │ 2. трансформация — TS, JSX, .vue → JavaScript; Sass → CSS
   │ 3. сборка        — граф → один или несколько чанков
   │ 4. оптимизация   — минификация, tree shaking, разбиение, сжатие
   ▼
dist/: index.html, assets/index-[hash].js, assets/index-[hash].css
```

Каждый шаг — свой класс инструментов. Разрешение и сборка — [бандлеры](/content/advanced-tooling/bundlers), правила поиска модулей — [модульные системы](/content/advanced-tooling/module-systems), трансформация — [транспиляция](/content/advanced-tooling/transpilation), оптимизация — [оптимизация сборки](/content/advanced-tooling/optimization).

После `vite build` в проверке:

- в JavaScript нет аннотаций типов — их стёр трансформатор;
- функции `unused` нет — её никто не импортировал, и бандлер её выбросил;
- код записан в одну-две строки — минификация;
- `index.html` ссылается на `assets/index-[hash].js` и `.css` — сборщик сам переписал пути.

Проверку типов этот конвейер **не** делает: трансформатор стирает типы, не проверяя их. Типы проверяет отдельный шаг — `tsc --noEmit` в редакторе и CI (подробно — в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling)).

Тот же проект можно запустить и без сборки. Чем это отличается?

## Разработка и продакшен

Разработка и продакшен решают **разные задачи**:

| | Разработка | Продакшен |
| --- | --- | --- |
| Цель | мгновенная обратная связь | быстрая загрузка у пользователя |
| Модули | отдаются по одному, по запросу | собраны в чанки |
| Обновление | HMR: модуль заменяется без перезагрузки страницы | — |
| Минификация | нет | да |
| Код для разработки | есть: предупреждения, проверки, отладка | выброшен |
| Source maps | всегда, подробные | по выбору, часто только для мониторинга ошибок |
| Хеши в именах | не нужны | обязательны для кеша |

В проверке dev-сервер Vite отдал `main.ts` как отдельный модуль: типы стёрты, импорты переписаны в адреса `/src/price.ts` и `/src/style.css`, а код соседнего модуля не вклеен — браузер запросит его сам. Это и делает запуск мгновенным: сервер не собирает приложение, а преобразует только тот файл, который запросил браузер (подробно — в [Vite и dev-серверах](/content/advanced-tooling/vite-and-dev-servers)).

### Код для разработки

`import.meta.env.DEV`, `import.meta.env.PROD` и `process.env.NODE_ENV` при сборке заменяются **константами**:

```js
if (import.meta.env.DEV) console.log('отладка: только в разработке');
// в продакшене → if (false) console.log(…) → удалено минификатором
```

В проверке строки с отладкой в продакшен-бандле не оказалось. Так фреймворки выбрасывают свои предупреждения и проверки: dev-сборка Vue и React заметно тяжелее и медленнее продакшен-сборки. Отсюда частая ошибка — развернуть dev-сборку и удивиться медленному сайту.

### Хеши

Имя `index-[hash].js` строится из **содержимого** файла. Это позволяет отдавать ассеты с заголовком кеширования «навсегда» (`Cache-Control: max-age=31536000, immutable`): пока файл не изменился, браузер не скачивает его снова. Изменился код — изменился хеш — изменилось имя, и браузер скачает новую версию. А `index.html` кешируют коротко, потому что именно он ссылается на актуальные имена (подробно — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching)).

В проверке после изменения `price.ts` имя JavaScript-файла стало другим, а имя CSS-файла не изменилось — его содержимое осталось прежним.

Инструменты одного шага взаимозаменяемы, и именно поэтому стоит понимать шаги, а не конкретный инструмент.

### Ноль настроек — не ноль конвейера

Vite, Next.js, Nuxt работают без конфигурации. Это не отсутствие сборки, а **разумные значения по умолчанию** поверх того же конвейера. Когда что-то ломается — пакет не находится, импорт CommonJS даёт `undefined`, бандл неожиданно вырос, — чинит это понимание шагов, а не поиск нового флага.

## Куда движется тулинг

Долго фронтенд-инструменты писали на JavaScript, и на больших проектах они стали узким местом: сборка — минуты, линтинг — десятки секунд. Сейчас их переписывают на нативные языки:

- **Vite 8** собирает на **Rolldown** — бандлере на Rust, который заменил и esbuild в разработке, и Rollup в продакшене;
- **TypeScript 7** — компилятор на Go, проверка типов в разы быстрее;
- **Oxlint и Biome** проверяют код на Rust, **Oxfmt и Biome** форматируют;
- **единые тулчейны** вроде Vite+ собирают dev-сервер, сборку, тесты, линтинг и форматирование в одну команду.

Почему именно сейчас и чем за это платят — в [Rust и будущем тулинга](/content/advanced-tooling/rust-and-the-future).

## Как менялся тулинг

Актуально на ноябрь 2026.

| Период | Что происходило |
| --- | --- |
| 2010-е, начало | конкатенация скриптов, Grunt и Gulp как исполнители задач |
| 2014–2020 | webpack и Babel — стандарт сборки и трансформации |
| 2020 | esbuild показывает сборку на Go в десятки раз быстрее, Vite — dev-сервер на нативных ES-модулях |
| 2022–2024 | SWC и Turbopack в Next.js, Rspack, Biome; Vite — основной выбор для новых проектов |
| 2026 | Vite 8 на Rolldown, Rolldown 1.0, TypeScript 7 на Go, ESLint 10 только с flat config, Babel 8 только ESM |

## Красные флаги в ответе

- **«Сборка проверяет типы».** Трансформатор стирает типы без проверки, нужен отдельный `tsc --noEmit`.
- **«Dev-сервер собирает то же, что и продакшен, только без минификации».** Он отдаёт модули по одному и не собирает бандл.
- **«Хеши в именах — для уникальности».** Они нужны, чтобы кешировать ассеты навсегда и сбрасывать кеш изменением имени.
- **«Без конфигурации — значит, без сборки».** Конвейер тот же, просто со значениями по умолчанию.
- **«Можно выложить dev-сборку, разница только в размере».** В ней предупреждения и проверки фреймворка, она медленнее.

## Как спрашивают на собеседовании

::question
Зачем фронтенду процесс сборки?

#answer
Браузер исполняет HTML, CSS и JavaScript, а пишут на TypeScript, JSX, `.vue`, с импортами из `node_modules` и сотнями модулей. Сборка стирает типы и преобразует синтаксис, разрешает импорты, собирает модули в небольшое число файлов и оптимизирует их.

#more
Плюс понижение синтаксиса для старых браузеров, компиляция CSS, выбрасывание кода для разработки и хеши в именах для долгого кеша. Сейчас браузеры понимают ES-модули, и в разработке можно отдавать модули без сборки, но в продакшене сборка по-прежнему выигрывает по числу запросов и размеру.
::

::question
Из каких этапов состоит сборка?

#answer
Разрешение модулей и построение графа зависимостей, трансформация каждого файла, сборка графа в чанки, оптимизация — минификация, tree shaking, разбиение на части — и выдача файлов с хешами в именах.

#more
На каждом шаге свои инструменты: бандлер отвечает за граф и чанки, трансформатор — за TypeScript и JSX, минификатор — за размер. Проверка типов в этот конвейер не входит, это отдельный шаг. Плагины бандлера встраиваются в шаги разрешения и трансформации.
::

::question
Чем dev-сборка отличается от prod?

#answer
В разработке важна скорость обратной связи: модули отдаются по одному, обновляются через HMR без перезагрузки, есть подробные source maps и предупреждения фреймворка. В продакшене — размер и кеш: минификация, удаление неиспользуемого и кода для разработки, разбиение на чанки, хеши в именах.

#more
`import.meta.env.DEV` и `process.env.NODE_ENV` заменяются константами, и ветки для разработки удаляются минификатором. Поэтому выложенная dev-сборка фреймворка медленнее и тяжелее. В Vite 8 разработка и продакшен используют один инструмент — Rolldown, что сокращает расхождения между режимами.
::

::question
Зачем хеши в именах файлов?

#answer
Хеш строится из содержимого. Файл можно кешировать навсегда, а при изменении кода меняется хеш, а значит, и имя — браузер скачает новую версию, а неизменённые файлы останутся в кеше.

#more
`index.html` кешируют коротко или проверяют на сервере, потому что он ссылается на актуальные имена. Если хеш зависит не только от своего содержимого — например, от порядка модулей или идентификаторов чанков, — изменение одного файла сбросит кеш многих.
::

::question
Ноль настроек — это отсутствие сборки?

#answer
Нет. Это разумные значения по умолчанию поверх того же конвейера: разрешение, трансформация, сборка, оптимизация. Процесс скрыт, но никуда не делся.

#more
Когда что-то ломается — пакет не разрешается, импорт CommonJS даёт `undefined`, бандл вырос, сборка расходится с dev, — чинить приходится, понимая шаги. Поэтому на собеседовании спрашивают механику, а не флаги конкретного инструмента.
::

## Практика

::practice{title="Почему пользователи видят старую версию?"}
После деплоя часть пользователей видит старый интерфейс, пока не обновит страницу с очисткой кеша. Сервер отдаёт всё с `Cache-Control: max-age=31536000`.

#solution
Долгий кеш поставили и на `index.html`. Браузер не запрашивает его снова и продолжает ссылаться на старые чанки, которые тоже лежат в кеше.

```text
/assets/*      → Cache-Control: public, max-age=31536000, immutable   (имя меняется вместе с содержимым)
/index.html    → Cache-Control: no-cache                              (каждый раз проверять у сервера)
```

Хешированные ассеты кешируют навсегда, потому что новая версия придёт под новым именем. HTML проверяют при каждом заходе: если он не изменился, сервер ответит `304`, и это дёшево. Старые чанки держат на сервере какое-то время после деплоя, чтобы открытые вкладки могли догрузить ленивые части. В проверке изменение `price.ts` дало новое имя JavaScript-файла, а CSS сохранил прежнее.
::

::practice{title="Отладка в продакшене"}
В консоли продакшен-сайта видны сообщения `[debug] state: …`, хотя они нужны только разработчикам:

```js
console.log('[debug] state:', state);
```

#solution
Обычный `console.log` ничем не отличается для сборщика от остального кода и попадает в продакшен. Код только для разработки помечают условием, которое при сборке становится константой:

```js
if (import.meta.env.DEV) {
  console.log('[debug] state:', state);
}
```

В продакшене условие превращается в `if (false)`, и минификатор удаляет ветку целиком — вместе со строкой. Так же устроены предупреждения во Vue и React. Убрать все `console.*` при сборке можно и настройкой минификатора, но условие лучше: оно оставляет отладку в разработке. В проверке строки с отладкой в продакшен-бандле не оказалось, а в модуле dev-сервера она была.
::
