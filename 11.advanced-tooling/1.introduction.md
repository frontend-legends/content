# Введение в тулинг

Современный фронтенд почти не пишут так, чтобы код напрямую исполнялся браузером. Между исходником и продакшеном стоит **конвейер сборки**: набор инструментов, которые превращают удобный для разработчика код в оптимизированные ассеты, понятные браузеру.

---

## Зачем вообще нужен тулинг

Браузер умеет немного: HTML, CSS, JavaScript (и WASM). А пишем мы на другом:

- **TypeScript / JSX / `.vue`** - браузер их не понимает, нужна трансформация в JS.
- **Модули в сотнях файлов** - грузить каждый отдельным запросом медленно, нужна сборка.
- **Новый синтаксис** (свежий ES) - на старых браузерах надо «опускать» (транспиляция + полифилы).
- **Sass / PostCSS** - нужно компилировать в обычный CSS.
- **Оптимизация** - минификация, tree-shaking, code splitting, хеши для кеша.

> Тулинг закрывает разрыв между **developer experience** (модули, типы, синтаксический сахар) и **тем, что реально исполняется** у пользователя.

---

## Конвейер сборки

Любая сборка - это последовательность трансформаций. Упрощённо:

```
Исходники (.ts, .tsx, .vue, .scss, ...)
        │  1. Разрешение модулей   → построить граф зависимостей
        │  2. Трансформация        → TS/JSX/новый синтаксис → обычный JS (транспиляция)
        │  3. Бандлинг             → собрать граф в один/несколько файлов
        │  4. Оптимизация          → минификация, tree-shaking, code splitting
        ▼
Ассеты (.js, .css с хешами) → браузер
```

Каждый шаг - отдельный класс инструментов: разрешение и бандлинг - [бандлеры](/content/advanced-tooling/bundlers), трансформация - [транспайлеры](/content/advanced-tooling/transpilation), оптимизация - [оптимизация сборки](/content/advanced-tooling/optimization).

## Dev vs prod

Ключевое различие, которое спрашивают: **сборка для разработки и для продакшена решают разные задачи.**

| | Development | Production |
|--|-------------|------------|
| Цель | скорость пересборки, удобство отладки | размер, скорость загрузки у пользователя |
| Source maps | полные | по желанию (для логов ошибок) |
| Минификация | нет | да |
| HMR | да (мгновенное обновление) | неактуально |
| Оптимизации | минимум | tree-shaking, code splitting, хеши |

<b class="text-on-semi-light">Почему так</b> - <span class="text-gray">В dev важно, чтобы изменение появлялось на экране мгновенно - поэтому минимум трансформаций и [HMR](/content/advanced-tooling/vite-and-dev-servers). В prod важен пользователь - поэтому максимум оптимизаций, даже если сборка идёт дольше. Современные инструменты (Vite) используют для этих режимов даже **разные движки**.</span>

## Из чего состоит тулчейн

| Категория | Что делает | Примеры |
|-----------|-----------|---------|
| Менеджер пакетов | зависимости | npm, pnpm ([экосистема](/content/ecosystem-libs/package-management)) |
| Транспайлер | новый/типизированный код → JS | Babel, SWC, esbuild, tsc |
| Бандлер | граф модулей → ассеты | Vite, Webpack, Rollup, esbuild |
| Dev-сервер | мгновенная разработка | Vite, webpack-dev-server |
| Линтер / форматтер | качество и стиль кода | ESLint, Prettier, Biome |
| Type checker | проверка типов | tsc, vue-tsc |
| CI/CD | автоматизация проверок | GitHub Actions |
| DevTools | отладка в браузере | Chrome DevTools, React/Vue DevTools |

---

## «Zero-config» и почему он не магия

Современные инструменты (Vite, Parcel, Next.js) работают «из коробки» без конфигов. Но это не отсутствие конвейера - это **разумные дефолты** поверх того же процесса. Когда что-то ломается, понимание конвейера - единственный способ починить. Поэтому знать механику важнее, чем помнить опции конфига.

## Вопросы на собеседовании

<b class="text-on-semi-light">Зачем фронтенду нужен build-процесс?</b>
<span class="text-gray">Браузер понимает только HTML/CSS/JS, а пишем на TS/JSX/Vue с модулями и новым синтаксисом. Тулинг транспилирует, собирает в бандлы, оптимизирует и компилирует стили - закрывает разрыв между DX и тем, что исполняется.</span>

<b class="text-on-semi-light">Из каких этапов состоит сборка?</b>
<span class="text-gray">Разрешение модулей (граф зависимостей) → трансформация (транспиляция TS/JSX) → бандлинг → оптимизация (минификация, tree-shaking, code splitting) → ассеты с хешами.</span>

<b class="text-on-semi-light">Чем dev-сборка отличается от prod?</b>
<span class="text-gray">Dev оптимизирует скорость пересборки и отладку (HMR, source maps, без минификации). Prod оптимизирует пользователя (минификация, tree-shaking, code splitting, хеши кеша), даже ценой более долгой сборки.</span>

<b class="text-on-semi-light">«Zero-config» инструменты - это отсутствие сборки?</b>
<span class="text-gray">Нет, это разумные дефолты поверх того же конвейера. Процесс никуда не делся - просто скрыт. Чинить проблемы без понимания механики невозможно.</span>
