# Rust и будущее тулинга

Почему фронтенд-инструменты переписывают на Rust и Go, что это дало на практике, чем за это платят — совместимостью плагинов, порогом входа, раздачей бинарников — и к чему ведёт консолидация в единые тулчейны. Спрашивают, почему тулинг уходит с JavaScript, какой инструмент начал этот тренд и какие есть нативные замены классических инструментов. Глубже — почему JavaScript-плагин замедляет нативный бандлер, зачем хукам фильтры и почему TypeScript выбрал Go, а не Rust.

::tldr
- **JavaScript-инструменты упёрлись не в алгоритмы, а в среду:** один поток, сборщик мусора, разогрев JIT и повторный разбор кода каждым инструментом. Нативный код использует все ядра и память без накладных расходов.
- **Выигрыш — десятки раз:** Rolldown собирает граф в десятки раз быстрее Rollup, Oxlint проверяет код в десятки раз быстрее ESLint, компилятор TypeScript на Go проверяет типы в разы быстрее.
- **Главная цена — граница с JavaScript.** Плагины на JavaScript работают в нативных инструментах, но каждый вызов хука — переход между языками. Фильтры в описании хука позволяют не вызывать JavaScript для неподходящих модулей.
- **Тулинг консолидируется:** один парсер и одно представление кода для сборки, линтинга, форматирования и тестов — Oxc внутри Vite, Rolldown, Oxlint и Oxfmt, плюс единые команды вроде Vite+.
- **Бинарники раздаются платформенными пакетами npm:** под каждую ОС и архитектуру свой пакет в `optionalDependencies`, а для остальных — сборка в WebAssembly.
::

## Почему JavaScript-тулинг был медленным

Сборщик, линтер и форматтер на JavaScript делают одно и то же: разбирают код в AST и обходят его. На проекте из тысяч файлов это упирается в устройство среды:

- **один поток.** Node.js выполняет JavaScript в одном потоке, а разбор тысяч независимых файлов — идеальная задача для всех ядер. Воркеры помогают, но дорого: данные приходится копировать между ними;
- **сборщик мусора.** AST — миллионы мелких объектов, и сборка мусора занимает заметную долю времени;
- **разогрев JIT.** Код сначала интерпретируется и оптимизируется по ходу работы, а короткоживущая команда не успевает разогреться (подробно о движке — во [Введении в JavaScript](/content/javascript/introduction));
- **повторная работа.** Каждый инструмент разбирает код сам: Babel, ESLint, Prettier, бандлер — четыре парсера и четыре AST одного файла.

Нативный код на Rust или Go не имеет этих ограничений: компилируется заранее, управляет памятью без пауз сборщика и распараллеливает работу по ядрам.

---

## Что это дало

Сквозной пример — один и тот же граф из 1500 модулей, собранный двумя бандлерами с совместимым API:

```text
Rollup (JavaScript)   ~2000 мс
Rolldown (Rust)       ~35 мс
```

В проверке оба выдали одинаковый по смыслу результат — tree shaking выбросил неиспользуемые экспорты, — а разница в скорости составила несколько десятков раз. Другие замеры этой главы:

| Задача | JavaScript | Нативный | Проверка |
| --- | --- | --- | --- |
| трансформация | Babel | SWC, esbuild | в 10 с лишним раз ([Транспиляция](/content/advanced-tooling/transpilation)) |
| проверка типов | TypeScript 6 | TypeScript 7 на Go | в 3 раза на 300 файлах ([Инструменты TypeScript](/content/advanced-tooling/typescript-tooling)) |
| линтинг | ESLint | Oxlint | в десятки раз на 1000 файлах ([Линтинг](/content/advanced-tooling/linting-and-formatting)) |
| сборка | Rollup | Rolldown | в десятки раз на 1500 модулях |

Скорость меняет не только время :term[CI]{def="непрерывная интеграция: сервер, который собирает и тестирует код на каждое изменение"}, но и привычки: линтер на каждое сохранение, проверка типов в git-хуке, сборка, которую не нужно ждать.

---

## Как к этому пришли

**esbuild** (2020, Go) первым показал, что сборщик может быть в сто раз быстрее. Он стал движком Vite в разработке и надолго — стандартным быстрым трансформатором.

Дальше пошла волна **Rust**:

| Классический инструмент | Нативная замена |
| --- | --- |
| Babel | SWC, Oxc |
| webpack | Rspack (совместим с webpack), Turbopack (Next.js) |
| Rollup | Rolldown (совместим с Rollup, внутри Vite 8) |
| ESLint | Oxlint, Biome |
| Prettier | Biome, Oxfmt |
| PostCSS, cssnano | Lightning CSS |
| Terser | Oxc minifier, SWC minifier |
| `tsc` | TypeScript 7 на Go |

Почему TypeScript выбрал **Go**, а не Rust: команда **портировала** существующий компилятор, а не переписывала с нуля. Структура кода и модель памяти Go — со сборщиком мусора, — ближе к исходному коду на TypeScript, и перенос шёл почти построчно, с сохранением поведения проверки. Rust потребовал бы перепроектировать структуры данных.

---

## Консолидация

Следующий шаг — не просто быстрые замены по одной, а **общее ядро**. Проект Oxc даёт парсер, трансформатор, минификатор, линтер и форматтер на одном представлении кода. На нём построены:

- **Rolldown** — бандлер Vite 8;
- **Oxlint и Oxfmt** — линтер и форматтер;
- **Vite+** — единая команда `vp`, которая объединяет dev-сервер, сборку, тесты на Vitest, линтинг, форматирование и кеш задач в одном инструменте.

Похожие экосистемы — **Biome** (линтер и форматтер в одном) и **Rspack** с Rsbuild и Rslib от ByteDance. Рантаймы тоже собирают инструменты в себя: **Bun** — менеджер пакетов, бандлер и тест-раннер, **Deno** — форматтер, линтер и проверку типов, а Node.js научился стирать типы TypeScript сам.

Направление понятно: вместо десятка JavaScript-инструментов, каждый со своим парсером и конфигурацией, — одно нативное ядро и одна команда. Общая картина изменений во фронтенде — в [Будущем фронтенда](/content/modern-dev/the-future-of-frontend).

## Цена

### Граница с JavaScript

Экосистема плагинов написана на JavaScript, и нативные инструменты стараются её сохранить: Rolldown выполняет плагины Rollup, Rspack — загрузчики webpack. Но каждый вызов JavaScript-хука из Rust — переход между языками с передачей кода в обе стороны. Если хук `transform` вызывается для каждого модуля, нативный бандлер тратит время на ожидание JavaScript.

Поэтому у хуков появились **фильтры**: плагин заранее описывает, какие модули ему нужны, и Rust вызывает JavaScript только для них:

```js
const plugin = {
  name: 'only-svg',
  transform: {
    filter: { id: /\.svg$/ },              // Rust проверяет сам, без перехода в JS
    handler(code, id) { /* … */ },
  },
};
```

В проверке хук без фильтра вызывался для каждого из 1500 модулей, а с фильтром — только для ста подходящих. Для авторов плагинов это новое правило: фильтр в описании хука вместо проверки `if (!id.endsWith('.svg')) return` внутри.

### Остальное

- **порог входа:** чтобы исправить ошибку в инструменте или написать нативный плагин, нужен Rust или Go. JavaScript-разработчиков, способных это сделать, меньше;
- **совместимость не стопроцентная:** редкие плагины и опции работают иначе или не работают, и миграция требует проверки — например, правила импорта :term[CommonJS]{def="система модулей Node.js с require и module.exports"} в Vite 8 изменились (подробно — в [Модульных системах](/content/advanced-tooling/module-systems));
- **программный API:** у TypeScript 7 его пока нет, и инструменты, которые встраиваются в компилятор, остаются на TypeScript 6;
- **раздача бинарников:** нативный код нужно собрать под каждую платформу.

### Как приходит бинарник

npm раздаёт JavaScript, а нативному инструменту нужен машинный код под конкретную ОС и процессор. Решение — **платформенные пакеты**: у `rolldown` в `optionalDependencies` десятки пакетов вида `@rolldown/binding-darwin-arm64`, `@rolldown/binding-linux-x64-gnu`, и менеджер пакетов ставит только подходящий по полям `os` и `cpu`. Для платформ без бинарника есть `@rolldown/binding-wasm32-wasi` — сборка в :term[WebAssembly]{def="двоичный формат кода, который браузер компилирует в машинный код и выполняет рядом с JavaScript"}. Всё это проверено на установленном Rolldown.

Отсюда частая ошибка в CI и Docker: `node_modules`, установленные на macOS, скопировали в Linux-контейнер, и нужного бинарника нет. Зависимости ставят внутри той платформы, где они будут работать, а lock-файл не должен выбрасывать `optionalDependencies`.

## Что это значит для разработчика

- **понимать конвейер важнее, чем знать инструмент:** шаги — разрешение, трансформация, сборка, оптимизация, проверка — остаются, меняются реализации (подробно — во [Введении в тулинг](/content/advanced-tooling/introduction));
- **совместимые API облегчают переход:** Rolldown — вместо Rollup, Rspack — вместо webpack, Oxlint — рядом с ESLint, без переписывания конфигурации с нуля;
- **писать плагины с фильтрами** и без лишней работы в JavaScript;
- **не гнаться за новым ради нового:** выигрыш в скорости сборки окупается на больших проектах, а на маленьких главное — стабильность.

---

## Красные флаги в ответе

- **«Rust-инструменты быстрее, потому что Rust быстрый язык».** Главное — параллельность, отсутствие пауз сборщика мусора и разогрева, общий разбор кода.
- **«Нативные инструменты не поддерживают плагины».** Поддерживают JavaScript-плагины совместимых API, но каждый вызов — переход между языками.
- **«TypeScript переписали на Rust».** На Go — ради почти построчного переноса существующего компилятора.
- **«Бинарник одинаков для всех платформ».** Под каждую ОС и архитектуру свой пакет, плюс запасная сборка в WebAssembly.
- **«Скоро JavaScript-инструментов не останется».** ESLint, Babel и Rollup остаются там, где нужны их плагины и API.

## Как спрашивают на собеседовании

::question
Почему фронтенд-тулинг переписывают на Rust и Go?

#answer
JavaScript-инструменты упёрлись в среду: один поток, паузы сборщика мусора, разогрев JIT и повторный разбор кода каждым инструментом. Нативный код использует все ядра, управляет памятью без пауз и работает сразу на полной скорости. Выигрыш — в десятки раз.

#more
На проектах из тысяч файлов это разница между минутой и секундой для сборки и линтинга. Скорость меняет привычки: линтер на каждое сохранение, проверки в git-хуках. Следующий шаг — общее ядро: один парсер для сборки, линтинга и форматирования.
::

::question
Какой инструмент запустил этот тренд?

#answer
esbuild на Go в 2020 году: он показал сборку и трансформацию в десятки и сотни раз быстрее JavaScript-аналогов и стал движком Vite в разработке.

#more
Потом пошла волна Rust: SWC в Next.js, Rspack, Turbopack, Lightning CSS, Biome, Oxc с Oxlint и Rolldown. В Vite 8 и разработка, и продакшен работают на Rolldown. TypeScript 7 переписан на Go.
::

::question
Назови нативные замены классических инструментов.

#answer
Babel — SWC и Oxc, webpack — Rspack и Turbopack, Rollup — Rolldown, ESLint — Oxlint и Biome, Prettier — Biome и Oxfmt, PostCSS и cssnano — Lightning CSS, Terser — минификаторы Oxc и SWC, `tsc` — TypeScript 7 на Go.

#more
Многие совместимы с API предшественника: Rolldown выполняет плагины Rollup, Rspack — загрузчики и плагины webpack, Oxfmt даёт результат как Prettier. Это делает переход постепенным, а не переписыванием.
::

::question
Почему JavaScript-плагин замедляет нативный бандлер?

#answer
Каждый вызов хука — переход из Rust в JavaScript и обратно с передачей кода. Если `transform` вызывается для каждого модуля, нативный бандлер ждёт JavaScript на каждом файле.

#more
Решение — фильтры в описании хука: `transform: { filter: { id: /\.svg$/ }, handler }`. Rust проверяет фильтр сам и вызывает JavaScript только для подходящих модулей. Проверка `if` внутри хука не помогает: переход в JavaScript уже произошёл.
::

::question
Что значит консолидация тулинга?

#answer
Переход от десятка отдельных JavaScript-инструментов со своими парсерами и конфигурациями к общему нативному ядру и одной команде. Oxc даёт парсер, трансформатор, минификатор, линтер и форматтер, на нём построены Rolldown и Vite, а Vite+ объединяет всё в одну команду.

#more
Похожие экосистемы — Biome, Rspack с Rsbuild и Rslib, рантаймы Bun и Deno со встроенными инструментами. Код разбирается один раз, конфигурация одна, а инструменты согласованы между собой.
::

::question
В чём минусы перехода на нативные инструменты?

#answer
Граница с JavaScript замедляет плагины, совместимость не стопроцентная, исправить инструмент или написать нативный плагин сложнее, нужны бинарники под каждую платформу. У TypeScript 7 пока нет программного API.

#more
Бинарники раздаются платформенными пакетами в `optionalDependencies` с запасной сборкой в WebAssembly. Частая ошибка — скопировать `node_modules` с macOS в Linux-контейнер. Миграцию проверяют на реальном проекте, а не по таблицам совместимости.
::

## Практика

::practice{title="Сборка в Docker не находит бинарник"}
Сборка работает на ноутбуке, а в Docker-образе падает:

```text
Error: Cannot find module '@rolldown/binding-linux-x64-gnu'
```

В `Dockerfile` есть `COPY . .` после `npm install`, выполненного на macOS.

#solution
`node_modules` с ноутбука на macOS попали в Linux-образ. Внутри лежит `@rolldown/binding-darwin-arm64`, а для Linux нужен другой платформенный пакет. Зависимости ставят внутри образа и не копируют с хоста:

```text
# .dockerignore
node_modules
```

```text
# Dockerfile
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build
```

`npm ci` внутри образа поставит бинарник под платформу контейнера. Если lock-файл создавали с `--omit=optional` или вручную вычищали `optionalDependencies`, нужные платформенные пакеты пропадут и там — lock-файл должен содержать их все. В проверке у `rolldown` в `optionalDependencies` были пакеты для каждой платформы и WebAssembly-сборка.
::

::practice{title="Плагин тормозит сборку"}
После перехода на Vite 8 свой плагин для иконок замедлил сборку большого проекта:

```js
export default function icons() {
  return {
    name: 'icons',
    transform(code, id) {
      if (!id.endsWith('.svg')) return;
      return `export default ${JSON.stringify(optimize(code))}`;
    },
  };
}
```

#solution
Хук `transform` вызывается для **каждого** модуля проекта, и для каждого Rolldown переходит в JavaScript — даже если плагин тут же возвращается на первой строке. Фильтр в описании хука переносит проверку в Rust:

```js
export default function icons() {
  return {
    name: 'icons',
    transform: {
      filter: { id: /\.svg$/ },
      handler(code) {
        return `export default ${JSON.stringify(optimize(code))}`;
      },
    },
  };
}
```

Теперь JavaScript вызывается только для SVG. Этот формат понимают и Rollup, и Vite, поэтому плагин остаётся совместимым. В проверке хук без фильтра вызвался для каждого из 1500 модулей, а с фильтром — для ста подходящих.
::
