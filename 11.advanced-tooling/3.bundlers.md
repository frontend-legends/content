# Бандлеры

**Бандлер** берёт твой граф из сотен модулей и собирает его в небольшое число оптимизированных файлов, которые грузит браузер. Это сердце сборки. Понимание, **как** он работает (а не какие опции у Webpack), - то, что проверяют на собесе.

---

## Зачем бандлить

Исторически - чтобы не грузить сотни мелких файлов отдельными запросами (дорого по HTTP). Сегодня, даже с HTTP/2 и нативным ESM, бандлер всё равно нужен для:

- **трансформации** - TS/JSX/Vue/Sass браузер не понимает, их надо превратить в JS/CSS;
- **tree-shaking и минификации** - убрать неиспользуемое и сжать;
- **разрешения зависимостей** из `node_modules` (bare-импорты браузер сам не находит);
- **code splitting** - разбить на чанки для ленивой загрузки;
- **хеширования** имён для кеширования.

> «Раз есть HTTP/2 и ESM, бандлер не нужен?» - нужен. Запросов меньше - всё ещё лучше, а трансформации и оптимизации никуда не делись.

---

## Как работает бандлер

Принцип у всех общий:

```
1. Entry point (точка входа, напр. src/main.ts)
        ▼
2. Построить ГРАФ ЗАВИСИМОСТЕЙ
   - распарсить файл, найти import'ы
   - рекурсивно обойти все зависимости
        ▼
3. ТРАНСФОРМАЦИЯ каждого модуля (loaders/plugins)
   - .ts → js, .vue → js, .scss → css, .svg → ...
        ▼
4. Собрать граф в BUNDLE(ы) + оптимизировать
        ▼
5. Output: .js/.css с хешами
```

<b class="text-on-semi-light">Ключевая идея</b> - <span class="text-gray">Бандлер - это «обходчик графа»: от точки входа он идёт по `import`'ам, строит дерево зависимостей, трансформирует каждый узел и склеивает результат. Всё остальное (loaders, plugins, splitting) - надстройки над этим обходом.</span>

---

## Базовые понятия

| Понятие | Что это |
|---------|---------|
| **Entry** | откуда начинать обход графа (одна или несколько точек) |
| **Output** | куда и как писать результат (имена, хеши, формат) |
| **Loader / transform** | превращает не-JS в модуль (`.scss` → CSS, `.ts` → JS) |
| **Plugin** | подключается к этапам сборки (анализ, генерация, оптимизация) |
| **Resolve** | как находить модули (алиасы, расширения, `node_modules`) |
| **Chunk** | отдельный выходной файл (для code splitting) |

Терминология чуть отличается между инструментами (Webpack - «loaders», Rollup/Vite - «plugins»), но суть одна.

## Ландшафт

| Бандлер | Язык | Сильная сторона | Где |
|---------|------|------------------|-----|
| **Webpack** | JS | зрелость, гибкость, экосистема loaders/plugins | legacy, энтерпрайз |
| **Rollup** | JS | чистый ESM-вывод, tree-shaking, для библиотек | библиотеки, prod в Vite |
| **esbuild** | Go | экстремальная скорость | трансформы, пребандл |
| **Parcel** | JS | zero-config | быстрый старт |
| **Rspack** | Rust | совместимость с Webpack, но быстрее | замена Webpack |
| **Turbopack** | Rust | скорость, Next.js | Next |
| **Rolldown** | Rust | замена Rollup, будущее Vite | новое поколение |

### Webpack

Долго был стандартом: максимально гибкий, огромная экосистема loaders/plugins, code splitting. Минусы - сложный конфиг и медленная сборка на JS. Постепенно уступает, но в legacy и энтерпрайзе всё ещё доминирует.

### Rollup

Пионер tree-shaking и ESM-вывода; даёт чистый, компактный бандл. Стандарт для **библиотек**. Vite использует Rollup для прод-сборки.

### esbuild

Написан на Go, **в 10–100 раз быстрее** JS-бандлеров. Используется не столько как самостоятельный бандлер приложений, сколько как сверхбыстрый **трансформер** и пребандлер (в т.ч. внутри Vite).

> Rust/Go-инструменты (Rspack, Turbopack, Rolldown) - отдельная тема [Rust и будущее](/content/advanced-tooling/rust-and-the-future).

## Бандлер приложения vs библиотеки

Важное различие:

- **Приложение** бандлят в самодостаточные чанки со всеми зависимостями, минификацией, splitting'ом - чтобы быстро грузилось у пользователя.
- **Библиотеку** бандлят иначе: внешние зависимости **не** включают (`external`, `peerDependencies`), отдают ESM (+CJS) и типы, не минифицируют агрессивно - чтобы приложение-потребитель само оптимизировало. Для библиотек берут Rollup или [tsup](/content/ecosystem-libs/building-and-patching).

---

## Vite

Современный дефолт для приложений - **Vite**: в dev использует нативный ESM + esbuild, в prod - Rollup. Он настолько меняет модель, что разобран отдельно в [Vite и dev-серверы](/content/advanced-tooling/vite-and-dev-servers).

## Вопросы на собеседовании

<b class="text-on-semi-light">Как работает бандлер?</b>
<span class="text-gray">От точки входа строит граф зависимостей (рекурсивно по import'ам), трансформирует каждый модуль (loaders/plugins), собирает в бандлы и оптимизирует. По сути - обход графа с трансформацией узлов.</span>

<b class="text-on-semi-light">Нужен ли бандлер при HTTP/2 и нативном ESM?</b>
<span class="text-gray">Да. Запросов меньше - всё ещё лучше, а трансформация (TS/JSX), tree-shaking, минификация, разрешение node_modules и code splitting никуда не делись.</span>

<b class="text-on-semi-light">Что такое loader и plugin?</b>
<span class="text-gray">Loader/transform превращает не-JS файл в модуль (.scss → CSS, .ts → JS). Plugin подключается к этапам сборки для анализа, генерации и оптимизации.</span>

<b class="text-on-semi-light">Чем Webpack отличается от Rollup?</b>
<span class="text-gray">Webpack - гибкий бандлер приложений с богатой экосистемой loaders, но тяжёлый. Rollup - ESM-first, чистый вывод и tree-shaking, стандарт для библиотек; используется в prod-сборке Vite.</span>

<b class="text-on-semi-light">Чем сборка библиотеки отличается от сборки приложения?</b>
<span class="text-gray">Библиотека не включает внешние зависимости (external/peerDeps), отдаёт ESM+CJS и типы, без агрессивной минификации - оптимизирует уже приложение-потребитель.</span>
