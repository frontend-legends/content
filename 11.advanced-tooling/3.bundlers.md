# Бандлеры

Как работает бандлер: граф модулей от точки входа, чанки и разбиение по динамическому импорту, плагины, scope hoisting, обёртки для CommonJS — и чем сборка библиотеки отличается от сборки приложения. Спрашивают, как работает бандлер, нужен ли он при HTTP/2 и нативных ES-модулях и чем webpack отличается от Rollup. Глубже — откуда берётся общий чанк, почему модуль CommonJS увеличивает бандл и почему у библиотеки `react` должен остаться внешним.

::tldr
- **Бандлер обходит граф зависимостей от точки входа** и превращает сотни модулей в несколько файлов-чанков. Модуль, до которого не дошёл обход, в сборку не попадёт.
- **Динамический `import()` — граница чанка:** код за ним загружается отдельно и позже. Модуль, общий для нескольких ленивых чанков, бандлер выносит в отдельный общий чанк, чтобы не дублировать.
- **Плагины встраиваются в шаги сборки:** найти модуль (`resolveId`), прочитать его (`load`), преобразовать (`transform`). У Rollup, Rolldown и Vite это один API.
- **ES-модули склеиваются в одну область видимости без обёрток** — scope hoisting, — а модуль CommonJS получает функцию-обёртку, потому что его экспорты известны только при выполнении.
- **Бандл приложения содержит всё, бандл библиотеки — только её код:** зависимости остаются внешними, иначе у пользователя окажутся две копии React или Vue.
::

## Зачем бандлить

Браузер умеет загружать ES-модули сам, через `<script type="module">`. Зачем тогда собирать?

Сквозной пример — магазин: `main.js` импортирует форматирование цены, а корзина и оформление заказа загружаются по клику:

```js
// main.js
import { formatPrice } from './price.js';
document.title = formatPrice(980);
cartButton.onclick = () => import('./cart.js').then((m) => m.open());
checkoutButton.onclick = () => import('./checkout.js').then((m) => m.start());
```

```js
// cart.js и checkout.js оба импортируют shared.js
import { money } from './shared.js';
```

Без сборки браузер сначала скачает `main.js`, разберёт его и только тогда узнает про `price.js`. Скачает его — узнает про его импорты. Каждый уровень графа — новый запрос **после** предыдущего, это **водопад**. HTTP/2 позволяет качать много файлов параллельно, но не помогает узнать о файле раньше, чем прочитан импортирующий. В реальном приложении граф из сотен модулей и пакетов из `node_modules` даёт десятки уровней.

Сборка решает это и ещё многое:

- **меньше запросов и уровней** — модули склеены в чанки;
- **голые импорты** `import 'vue'` превращаются в пути или вклеиваются;
- **tree shaking** — неиспользуемый код выбрасывается до того, как попадёт к пользователю;
- **трансформации** — TypeScript, JSX, `.vue`, CSS, картинки;
- **хеши и разбиение** — для кеша и ленивой загрузки.

В разработке водопад терпим — сервер локальный, — поэтому Vite в dev-режиме отдаёт модули без сборки (подробно — в [Vite и dev-серверах](/content/advanced-tooling/vite-and-dev-servers)).

## Как работает бандлер

```text
1. точка входа main.js
2. разрешение    — для каждого import найти файл (правила — в «Модульных системах»)
3. загрузка      — прочитать файл
4. трансформация — TS/JSX/.vue → JS, разобрать в AST, найти новые import
5. повторить 2–4 для каждого нового модуля → граф
6. оптимизация   — tree shaking, слияние областей видимости
7. разбиение     — граф → чанки по точкам входа и import()
8. выдача        — код чанков, хеши в именах, source maps
```

Бандлер — это обход графа. Модуль, до которого обход не дошёл по `import`, в сборку не попадёт. Поэтому код, который подключается «как-то иначе» — строкой в `require(name)` с переменной, — бандлер не видит и не может собрать. Правила разрешения импортов — в [Модульных системах](/content/advanced-tooling/module-systems).

### Чанки

После обхода граф делится на **чанки** — файлы, которые браузер загрузит одним запросом:

- **точка входа** — `main.js` и всё, что он импортирует статически;
- **ленивые чанки** — каждый динамический `import()` начинает новый: `cart` и `checkout`;
- **общие чанки** — модуль, который нужен нескольким ленивым чанкам, выносится отдельно, чтобы не загружать его дважды.

В проверке и Rolldown, и Rollup собрали пример в четыре чанка: точку входа, два ленивых и общий с `shared.js`, причём код `shared.js` оказался только в общем чанке. Управлять разбиением можно вручную — например, вынести тяжёлые зависимости в отдельный чанк-вендор, — подробно об этом в [Оптимизации](/content/advanced-tooling/optimization).

### Scope hoisting

Как склеить модули в один файл? Старый способ — обернуть каждый модуль в функцию и вызывать их через маленький рантайм-реестр. Это работает, но каждая обёртка стоит места и времени выполнения.

ES-модули позволяют больше: их импорты и экспорты статичны, поэтому бандлер может **переписать имена** и положить код модулей в **одну область видимости** — без обёрток. В проверке `formatPrice` из `price.js` оказался в чанке точки входа обычной константой, а неиспользуемая функция из того же файла — выброшена.

С :term[CommonJS]{def="система модулей Node.js с require и module.exports"} так нельзя: его экспорты известны только после выполнения. Поэтому модуль CommonJS бандлер оборачивает в функцию-обёртку — в выводе Rolldown это вызов `__commonJS` — и выполняет её при первом обращении. Отсюда правило: зависимости в ESM дают меньший и более оптимизируемый бандл.

## Плагины

Бандлер умеет из коробки только JavaScript и JSON. Всё остальное — плагины, которые встраиваются в шаги сборки:

```js
const plugin = {
  name: 'demo',
  resolveId(id) {                       // шаг разрешения: найти модуль
    return id === 'virtual:build-info' ? '\0build-info' : null;
  },
  load(id) {                            // шаг загрузки: отдать исходник
    return id === '\0build-info' ? 'export default { built: "сборка" }' : null;
  },
  transform(code, id) {                 // шаг трансформации: изменить исходник
    return id.endsWith('.txt') ? `export default ${JSON.stringify(code)};` : null;
  },
};
```

Здесь два приёма, на которых держатся настоящие плагины:

- **виртуальный модуль** — импорт, у которого нет файла. Плагин сам решает, что за ним лежит: маршруты из файлов страниц, иконки, переменные окружения;
- **преобразование по типу файла** — `.vue`, `.svg`, `.md`, `.txt` превращаются в JavaScript-модули.

Этот объект без изменений сработал и в Rollup, и в Rolldown — проверено. Тот же API использует Vite, поэтому большинство плагинов Rollup работают в Vite, а Rolldown создавался совместимым с ними.

### Загрузчики и плагины в webpack

У webpack два понятия:

- **loader** преобразует один файл: `ts-loader`, `css-loader`, `vue-loader`. Он работает как `transform` у Rollup;
- **plugin** подписывается на события всей сборки: генерирует HTML, извлекает CSS в файлы, анализирует бандл.

Плагины webpack и Rollup несовместимы. Rspack повторяет API webpack, поэтому плагины и загрузчики webpack в нём в основном работают.

Актуально на ноябрь 2026.

| Бандлер | На чём | Где используется | Особенность |
| --- | --- | --- | --- |
| Vite | Rolldown | новые SPA, Vue, Svelte, Astro, Nuxt, SvelteKit | dev-сервер без сборки, один инструмент для dev и prod |
| Rolldown | Rust | внутри Vite, отдельно — для библиотек | совместим с плагинами Rollup |
| Rollup | JavaScript | библиотеки, старые версии Vite | эталон tree shaking и вывода ESM |
| webpack | JavaScript | большие легаси-приложения | гибкость, огромная экосистема загрузчиков |
| Rspack | Rust | миграция с webpack | совместим с конфигурацией и плагинами webpack |
| Turbopack | Rust | Next.js | инкрементальная сборка на уровне функций |
| esbuild | Go | сборка утилит, библиотек, как трансформатор | очень быстрый, минимум возможностей |
| Parcel, Bun | Rust, Zig | проекты без конфигурации, рантайм Bun | работают почти без настройки |

Для нового приложения стандарт — Vite или сборщик мета-фреймворка: Next.js использует :term[Turbopack]{def="сборщик от Vercel на Rust, встроенный в Next.js"}, Nuxt и :term[SvelteKit]{def="мета-фреймворк для Svelte: маршруты, серверный рендеринг, сборка"} — Vite. Для большого webpack-проекта путь ускорения без переписывания — Rspack. Причины переезда на Rust и Go — в [Rust и будущем тулинга](/content/advanced-tooling/rust-and-the-future).

## Приложение и библиотека

Задачи разные:

| | Приложение | Библиотека |
| --- | --- | --- |
| Что в бандле | всё: код и зависимости | только код библиотеки |
| Зависимости | вклеены | внешние: `import { ref } from 'vue'` остаётся |
| Формат | ESM для браузера, чанки, хеши | ESM, иногда CommonJS, плюс `.d.ts` |
| Минификация | да | обычно нет — минифицирует приложение |
| Tree shaking | у себя | у потребителя: библиотека должна его позволять |

Главное — **внешние зависимости**. Если библиотека вклеит Vue в свой бандл, у приложения окажутся две копии Vue: двойной размер, две системы реактивности, сломанные `provide` и `inject`. В проверке библиотека с `external: ['vue']` дала несколько строк с импортом `vue`, а без него — десятки килобайт с Vue внутри. Зависимости библиотеки объявляют в `peerDependencies` и выносят в `external`.

Библиотеки собирают Rolldown, Rollup, tsdown или tsup, а `package.json` описывает точки входа через `exports` (подробно — в [Модульных системах](/content/advanced-tooling/module-systems) и [Сборке и патчинге](/content/ecosystem-libs/building-and-patching)).

## Красные флаги в ответе

- **«С HTTP/2 и ES-модулями бандлер не нужен».** Параллельная загрузка не убирает водопад обнаружения импортов, и остаются tree shaking, трансформации и хеши.
- **«Каждый `import()` дублирует общие зависимости».** Бандлер выносит общий модуль в отдельный чанк.
- **«Бандлер склеивает файлы подряд».** ES-модули сливаются в одну область видимости с переименованием, CommonJS оборачивается в функцию.
- **«Библиотека должна собирать свои зависимости внутрь».** Зависимости остаются внешними, иначе у потребителя будут две копии.
- **«Плагины Rollup не работают в Vite».** Vite и Rolldown используют тот же API плагинов.

## Как спрашивают на собеседовании

::question
Как работает бандлер?

#answer
Начинает с точки входа, разрешает каждый импорт в файл, загружает и преобразует его, находит новые импорты и так строит граф зависимостей. Потом оптимизирует граф — выбрасывает неиспользуемое, сливает модули — делит на чанки и выдаёт файлы с хешами и source maps.

#more
Модуль, до которого обход не дошёл по `import`, в сборку не попадёт. Динамический `import()` начинает новый чанк, общие модули выносятся отдельно. ES-модули сливаются в одну область видимости, CommonJS оборачивается в функцию. Плагины встраиваются в шаги разрешения, загрузки и трансформации.
::

::question
Нужен ли бандлер при HTTP/2 и нативных ES-модулях?

#answer
В продакшене — да. HTTP/2 качает файлы параллельно, но браузер узнаёт об импорте, только скачав и разобрав импортирующий файл, — получается водопад по глубине графа. Плюс без сборки нет tree shaking, трансформаций, хешей и разбиения на чанки.

#more
В разработке Vite отдаёт модули без сборки: сервер локальный, водопад терпим, а запуск мгновенный. Для маленьких сайтов без сборки достаточно import map. `modulepreload` сокращает водопад, но знание о графе всё равно должно откуда-то взяться — обычно его даёт сборка.
::

::question
Что такое loader и plugin?

#answer
В webpack loader преобразует один файл — TypeScript, CSS, `.vue` — в модуль, а plugin подписывается на события сборки целиком: генерирует HTML, извлекает CSS, анализирует бандл. В Rollup, Rolldown и Vite одно понятие — плагин с хуками `resolveId`, `load`, `transform` и другими.

#more
Плагины Rollup в основном работают в Vite и Rolldown. Плагины и загрузчики webpack работают в Rspack. Типичные приёмы плагина — виртуальный модуль без файла и преобразование файлов по расширению.
::

::question
Чем webpack отличается от Rollup и Vite?

#answer
webpack — гибкий сборщик приложений с загрузчиками, плагинами и своим рантаймом модулей, стандарт прошлого десятилетия. Rollup делает чистый ESM-вывод и сильный tree shaking и стал стандартом для библиотек. Vite — dev-сервер без сборки плюс продакшен-сборка, сейчас на Rolldown.

#more
Rolldown — Rollup-совместимый бандлер на Rust, Rspack — webpack-совместимый на Rust, Turbopack — сборщик Next.js. Для нового приложения обычно берут Vite или сборщик мета-фреймворка, для ускорения большого webpack-проекта — Rspack.
::

::question
Чем сборка библиотеки отличается от сборки приложения?

#answer
Приложение собирают со всеми зависимостями, минифицируют и делят на чанки. Библиотеку собирают без зависимостей — они остаются внешними и объявлены в `peerDependencies`, — обычно без минификации, в ESM и с объявлениями типов.

#more
Если библиотека вклеит React или Vue, у приложения будет две копии: лишний размер и сломанный контекст. Библиотека должна позволять tree shaking: ESM, отсутствие побочных эффектов при импорте, поле `sideEffects`. Точки входа описывают в `exports`.
::

::question
Что такое scope hoisting?

#answer
Слияние ES-модулей в одну область видимости: бандлер переименовывает переменные, чтобы не было конфликтов, и кладёт код модулей подряд, без функций-обёрток и рантайм-реестра модулей.

#more
Это возможно благодаря статичности `import` и `export`. Результат меньше и быстрее выполняется, а минификатору проще выбрасывать неиспользуемое. CommonJS так слить нельзя: его экспорты известны только после выполнения, поэтому он остаётся в обёртке.
::

## Практика

::practice{title="Две копии Vue"}
Приложение использует компонент из внутренней библиотеки, и `inject` в нём не видит значение, предоставленное приложением. В бандле две копии Vue.

#solution
Библиотека собрана вместе с Vue. В приложении работают два экземпляра Vue со своими системами `provide` и реактивности, и значение, предоставленное одним, не видно другому.

```js
// сборка библиотеки
export default {
  input: 'src/index.js',
  external: ['vue'],   // или все зависимости из peerDependencies
};
```

```json
{
  "peerDependencies": { "vue": "^3.5.0" }
}
```

`external` оставляет `import { ref } from 'vue'` в коде библиотеки, и приложение подставит свою копию. `peerDependencies` говорит менеджеру пакетов не ставить вторую. В проверке библиотека с `external` содержала только импорт `vue`, а без него — весь Vue внутри.
::

::practice{title="Ленивые страницы стали тяжелее"}
Корзина и оформление заказа загружаются через `import()`. Аналитика бандла показывает, что у обоих чанков внутри одна и та же библиотека форматирования денег.

#solution
Обычно бандлер сам выносит общий модуль в отдельный чанк — в проверке `shared.js` оказался в общем чанке, а не в каждом ленивом. Если дубли всё же есть, частые причины:

- **две разные версии** библиотеки в `node_modules` — для бандлера это разные модули. Проверяют `npm ls money-lib` и выравнивают версии;
- **двойной пакет:** одна часть кода импортирует ESM-версию, другая — CommonJS (подробно — в [Модульных системах](/content/advanced-tooling/module-systems));
- **ручное разбиение** в конфигурации, которое положило модуль в оба чанка.

```bash
npm ls money-lib
# ├── money-lib@3.2.0
# └─┬ checkout-widget@1.4.0
#   └── money-lib@2.9.1      ← вторая версия
```

```json
{
  "overrides": { "money-lib": "3.2.0" }
}
```

`overrides` в npm (в pnpm — `pnpm.overrides`) заставляет поставить одну версию, если она совместима. После исправления общий модуль загружается один раз и кешируется для обоих маршрутов.
::
