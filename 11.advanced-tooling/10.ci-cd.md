# CI/CD

Как устроен конвейер проверок и выкладки фронтенда: этапы и их порядок, GitHub Actions, воспроизводимая установка зависимостей, кеш, гейты качества, защита веток и превью. Спрашивают, чем CI отличается от CD, из каких шагов состоит пайплайн фронтенда и как его ускорить. Глубже — почему `npm ci`, а не `npm install`, от чего зависит ключ кеша и как поймать рост бандла до выкладки.

::tldr
- **CI проверяет каждое изменение автоматически,** CD доводит проверенное до окружения: continuous delivery — готово к выкладке по кнопке, continuous deployment — выкладывается само.
- **Пайплайн фронтенда:** установка зависимостей, затем параллельно линтер, проверка типов, тесты и сборка, после — e2e и выкладка. Независимые шаги идут одновременно, зависимые ждут через `needs`.
- **В CI ставят зависимости через `npm ci`:** строго по lock-файлу и с ошибкой при рассинхроне с `package.json`. Так сборка воспроизводима, а lock-файл не переписывается тайком.
- **Ускорение — кеш и пропуск лишнего:** кеш зависимостей с ключом от хеша lock-файла, отмена устаревших прогонов, проверка только затронутых пакетов в монорепо.
- **Гейт работает, только если он обязателен:** защита ветки требует зелёных проверок и ревью перед слиянием. Это то, чего не дают локальные git-хуки.
::

---

## CI и CD

**CI** (continuous integration) — каждое изменение автоматически проверяется: линтер, типы, тесты, сборка. Цель — узнать о поломке через минуты после пуша, а не через неделю при релизе.

**CD** — две разные практики с одной аббревиатурой:

- **continuous delivery** — каждое изменение в основной ветке **готово** к выкладке, а выкладывает человек по кнопке;
- **continuous deployment** — каждое изменение, прошедшее проверки, **выкладывается само**.

Как именно выкладывать — сине-зелёный деплой, канареечный, флаги функций, откат, — разобрано в [Стратегиях деплоя](/content/testing-deploying/deployment-strategies), а куда — в [Хостинге и платформах](/content/testing-deploying/hosting-and-platforms). Здесь — сам конвейер.

## Пайплайн фронтенда

```text
push / pull request
   │
   ▼
установка зависимостей (npm ci, кеш)
   │
   ├── линтер ──┐
   ├── типы ────┤ параллельно
   ├── тесты ───┤
   └── сборка ──┘
                │
                ▼
         e2e на собранном приложении, бюджет размера
                │
                ▼
         превью (PR) / выкладка (main)
```

Порядок подчинён одному правилу: **быстрые и независимые шаги — раньше и параллельно**, медленные и зависимые — позже. Линтер падает за секунды, и незачем ждать десять минут e2e, чтобы узнать о точке с запятой.

### GitHub Actions

Сквозной пример — конфигурация CI магазина:

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
  push:
    branches: [main]

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npm run lint

  typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npx tsc --noEmit

  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-node@v5
        with: { node-version: 24, cache: npm }
      - run: npm ci
      - run: npm test

  deploy:
    if: github.ref == 'refs/heads/main'
    needs: [lint, typecheck, test]
    runs-on: ubuntu-latest
    steps:
      - run: npm ci && npm run build
      # выкладка на платформу
```

- **workflow** — файл в `.github/workflows`, **триггеры** — `on`;
- **jobs** без `needs` идут **параллельно** на разных машинах, а `deploy` ждёт трёх проверок;
- **steps** внутри задачи выполняются по порядку, упавший шаг роняет задачу;
- **`concurrency` с `cancel-in-progress`** отменяет устаревший прогон, когда в ту же ветку пришёл новый пуш.

Структура этого файла разобрана в проверке: три задачи без зависимостей, деплой с `needs` на все три и `npm ci` в каждой проверке.

Каждая задача — чистая машина, поэтому установка повторяется в каждой. Это цена параллельности, и её снижает кеш.

## Воспроизводимая установка

```bash
npm ci        # в CI
npm install   # на машине разработчика
```

`npm install` может **обновить** lock-файл, если `package.json` разрешает более новые версии. В CI это означает, что сборка проверяет не тот набор зависимостей, что у разработчика, и может сломаться от выхода новой версии пакета.

`npm ci`:

- удаляет `node_modules` и ставит **строго** по `package-lock.json`;
- **падает**, если `package.json` и lock-файл разошлись — например, зависимость добавили, а lock не закоммитили;
- никогда не переписывает lock-файл.

В проверке после добавления зависимости без обновления lock-файла `npm ci` упал с сообщением «can only install packages when your package.json and package-lock.json are in sync», а lock-файл остался прежним. Аналоги — `pnpm install --frozen-lockfile` и `yarn install --immutable`, причём pnpm в CI включает этот режим сам. О lock-файлах — в [Управлении пакетами](/content/ecosystem-libs/package-management).

## Ускорение

### Кеш зависимостей

`setup-node` с `cache: npm` кеширует папку загрузок npm. Ключ кеша строится из **хеша lock-файла**: пока зависимости не менялись, ключ тот же, и пакеты не скачиваются заново. Изменилась версия пакета — изменился хеш — кеш собирается заново. В проверке ключ от одного и того же lock-файла совпал, а от изменённой версии одного пакета — нет.

Кешируют и результаты инструментов: `.tsbuildinfo` для инкрементальной проверки типов, кеш :term[ESLint]{def="линтер JavaScript и TypeScript: проверяет код по настраиваемым правилам"}, браузеры Playwright.

### Не делать лишнего

- **отменять устаревшие прогоны** через `concurrency`;
- **фильтры путей:** изменение только документации не запускает тесты (`paths` и `paths-ignore` в триггерах);
- **в монорепо — только затронутое:** Turborepo и Nx проверяют пакеты, которые изменились, и их зависимых, и берут результат остальных из удалённого кеша (подробно — в [Монорепо](/content/advanced-tooling/monorepo-tooling));
- **шардирование тестов:** e2e делятся на части и идут на нескольких машинах;
- **быстрые инструменты:** нативные линтеры, TypeScript 7 и Vite 8 сокращают сами шаги (подробно — в [Rust и будущем тулинга](/content/advanced-tooling/rust-and-the-future)).

## Гейты качества

Кроме линтера, типов и тестов, у фронтенда есть свои проверки:

- **бюджет размера** — точка входа не должна вырасти выше порога;
- **Lighthouse CI** — метрики производительности и доступности на собранных страницах (подробно — в [Измерении и мониторинге](/content/security-perfomance/measuring-and-monitoring));
- **визуальная регрессия** — скриншоты компонентов сравниваются с эталоном (подробно — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing));
- **аудит зависимостей** — известные уязвимости (подробно — в [Цепочке поставок](/content/security-perfomance/supply-chain-and-vulnerabilities));
- **формат заголовка PR** — если коммиты сливаются через squash (подробно — в [Git-хуках](/content/advanced-tooling/git-hooks-and-quality-gates)).

### Бюджет размера

Бандл растёт незаметно: каждая новая зависимость добавляет килобайты, и через полгода главная грузится вдвое дольше. Гейт ловит рост в момент, когда его добавили:

```js
// scripts/check-size.js
const bytes = gzipSync(readFileSync(entryFile)).length;
if (bytes > LIMIT_KB * 1024) {
  console.error(`точка входа ${(bytes / 1024).toFixed(1)} КБ gzip > бюджета ${LIMIT_KB} КБ`);
  process.exit(1);
}
```

Ненулевой код выхода роняет шаг CI. В проверке маленькая точка входа уложилась в бюджет, а с подключённым Vue — нет, и скрипт выдал сообщение о превышении. Готовые инструменты — `size-limit` и бюджеты в Lighthouse CI — ещё и пишут разницу размера в комментарий к PR.

### Защита веток

Гейт работает, только если его **нельзя пропустить**. В настройках репозитория для основной ветки включают:

- обязательные проверки CI — без зелёного статуса кнопка слияния недоступна;
- обязательное ревью;
- запрет прямого пуша и принудительного пуша;
- актуальность ветки перед слиянием.

Это то, что отличает CI от локальных хуков: хук обходится `--no-verify`, защищённая ветка — нет.

## Превью и выкладка

**Превью** — отдельная выкладка каждого PR по своему адресу: ревьюер, дизайнер и тестировщик смотрят изменение вживую до слияния. Vercel, Netlify и Cloudflare Pages делают это из коробки, а e2e можно запускать прямо на превью.

**Выкладка** после слияния в основную ветку:

1. сборка — та же, что проверялась, а не новая с другими зависимостями: артефакт собирают один раз и выкладывают его;
2. загрузка ассетов с хешами и долгим кешем на :term[CDN]{def="сеть серверов по миру, которая отдаёт файлы с ближайшего к пользователю"};
3. обновление `index.html`, который ссылается на новые ассеты;
4. сохранение старых ассетов какое-то время, чтобы открытые вкладки догрузили ленивые чанки;
5. загрузка source maps в мониторинг ошибок, а не на публичный сервер (подробно — в [Отладке](/content/advanced-tooling/devtools-and-debugging)).

Секреты для выкладки хранят в настройках CI, а не в репозитории, и выдают только задачам, которым они нужны. Для облачных платформ надёжнее :term[OIDC]{def="OpenID Connect: протокол, по которому CI получает от облака короткоживущий токен вместо ключа"} — короткоживущие токены вместо постоянных ключей.

## Красные флаги в ответе

- **«CD — это когда код сам выкладывается».** Это continuous deployment, а continuous delivery — готовность к выкладке по кнопке.
- **«В CI достаточно `npm install`».** Он может обновить зависимости, нужен `npm ci` строго по lock-файлу.
- **«Шаги надо выполнять по очереди».** Независимые проверки идут параллельно, иначе пайплайн медленный.
- **«Хватит хуков, CI можно не делать».** Хуки обходятся, гарантию даёт CI с защитой ветки.
- **«Для деплоя собираем заново».** Выкладывают тот артефакт, который прошёл проверки.

## Как спрашивают на собеседовании

::question
Чем CI отличается от CD?

#answer
CI — автоматическая проверка каждого изменения: линтер, типы, тесты, сборка. CD — доведение проверенного до окружения: continuous delivery держит код готовым к выкладке по кнопке, continuous deployment выкладывает автоматически.

#more
CI отвечает «код не сломан», CD — «код у пользователей». Continuous deployment требует хороших тестов, мониторинга и быстрого отката, поэтому часто его сочетают с флагами функций и канареечными выкладками.
::

::question
Из каких шагов состоит пайплайн фронтенда?

#answer
Установка зависимостей через `npm ci`, затем параллельно линтер, проверка типов, тесты и сборка, после них e2e на собранном приложении и гейты вроде бюджета размера, в конце — превью для PR или выкладка из основной ветки.

#more
Быстрые и независимые шаги — раньше и параллельно, медленные и зависимые — позже через `needs`. Типы проверяются отдельно от сборки, потому что сборка их не проверяет. Выкладывают тот артефакт, который проверили.
::

::question
Почему в CI npm ci, а не npm install?

#answer
`npm ci` ставит строго по lock-файлу, падает при рассинхроне с `package.json` и никогда не переписывает lock. `npm install` может обновить зависимости в рамках диапазонов, и CI проверит не то, что у разработчика.

#more
Рассинхрон — частая ошибка: зависимость добавили, а lock-файл не закоммитили. `npm ci` ловит её сразу. Аналоги — `pnpm install --frozen-lockfile` и `yarn install --immutable`. Ключ кеша зависимостей строят по хешу lock-файла.
::

::question
Как ускорить CI?

#answer
Параллельные задачи, кеш зависимостей и результатов инструментов, отмена устаревших прогонов через `concurrency`, фильтры путей и шардирование тестов. В монорепо — проверка только затронутых пакетов с удалённым кешем.

#more
Ключ кеша от хеша lock-файла сохраняет его между прогонами, пока зависимости не меняются. Кешируют `.tsbuildinfo`, кеш линтера, браузеры Playwright. Быстрые инструменты сокращают и сами шаги.
::

::question
Какие проверки специфичны для фронтенда?

#answer
Бюджет размера бандла, Lighthouse CI для производительности и доступности, визуальная регрессия компонентов, e2e в браузере и аудит зависимостей.

#more
Бюджет размера ловит рост бандла в момент, когда его добавили, а не через полгода. `size-limit` пишет разницу в комментарий к PR. Визуальные тесты требуют стабильного окружения — одинаковых шрифтов и браузеров, — иначе дают ложные срабатывания.
::

::question
Как сделать так, чтобы проверки нельзя было пропустить?

#answer
Защита основной ветки: обязательные проверки CI, обязательное ревью, запрет прямого и принудительного пуша. Без зелёного статуса слить код нельзя.

#more
Локальные хуки обходятся `--no-verify`, поэтому они — удобство, а гарантия — защищённая ветка. Обязательными делают быстрые и стабильные проверки: нестабильный тест в обязательных учит команду нажимать «перезапустить» вместо исправления.
::

## Практика

::practice{title="Сборка в CI сломалась сама"}
Вчера CI был зелёным, сегодня без единого коммита сборка падает в зависимости, которую никто не обновлял. В CI шаг `npm install`.

#solution
`npm install` поставил более новую версию пакета, разрешённую диапазоном `^` в `package.json`, — вышла версия с ошибкой. У разработчиков локально старая версия из lock-файла.

```yaml
- uses: actions/setup-node@v5
  with: { node-version: 24, cache: npm }
- run: npm ci
```

`npm ci` ставит ровно то, что записано в lock-файле, и сборка воспроизводима. Обновления зависимостей делают явно — отдельным PR, который проходит CI, удобно через Renovate или Dependabot. В проверке `npm ci` упал при рассинхроне `package.json` и lock-файла и не переписал lock.
::

::practice{title="Главная грузится вдвое дольше"}
За полгода точка входа выросла с 80 до 170 КБ gzip, и никто не заметил когда. Сделай так, чтобы рост ловился в момент добавления.

#solution
Гейт в CI, который падает, если точка входа превысила бюджет:

```js
// scripts/check-size.js
import { readFileSync, readdirSync } from 'node:fs';
import { gzipSync } from 'node:zlib';

const LIMIT_KB = 100;
const entry = readdirSync('dist/assets').find((f) => /^index-.*\.js$/.test(f));
const bytes = gzipSync(readFileSync(`dist/assets/${entry}`)).length;

if (bytes > LIMIT_KB * 1024) {
  console.error(`точка входа ${(bytes / 1024).toFixed(1)} КБ gzip > бюджета ${LIMIT_KB} КБ`);
  process.exit(1);
}
```

```yaml
- run: npm run build
- run: node scripts/check-size.js
```

Теперь PR, который добавил тяжёлую зависимость, не сольётся без обсуждения: либо зависимость лениво загружается, либо бюджет осознанно поднимают. `size-limit` делает то же и пишет разницу в комментарий к PR. В проверке маленькая точка входа прошла, а с подключённым Vue — нет. Найти, что именно выросло, помогает анализатор бандла (подробно — в [Оптимизации](/content/advanced-tooling/optimization)).
::
