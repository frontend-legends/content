# CI/CD

**CI/CD** автоматизирует путь кода от коммита до продакшена. **CI** (Continuous Integration) - автоматическая проверка каждого изменения; **CD** (Continuous Delivery/Deployment) - автоматическая доставка в продакшен. Для фронтенда это пайплайн «линт → типы → тесты → сборка → деплой».

> Цели деплоя и хостинг (Vercel, Netlify, контейнеры) разобраны в [тестировании и деплое](/content/testing-deploying). Здесь - **сам пайплайн и гейты качества**.

---

## CI и CD

- **Continuous Integration** - разработчики часто вливают изменения в общую ветку, и **каждое** изменение автоматически проверяется (линт, типы, тесты, сборка). Цель - ловить поломки рано, а не на релизе.
- **Continuous Delivery** - код всегда в состоянии, готовом к релизу (деплой - по кнопке).
- **Continuous Deployment** - каждый прошедший проверки мерж **автоматически** выкатывается в прод.

## Пайплайн фронтенда

Типичный набор шагов, запускаемых на push и pull request:

```
push / PR
   ▼
1. Checkout кода
2. Установить зависимости (npm ci - строго по lockfile)
3. Линт            (eslint .)
4. Проверка типов   (tsc --noEmit)
5. Тесты           (unit/integration)
6. Сборка          (build - убедиться, что собирается)
7. (E2E, bundle-size, деплой превью)
   ▼
✅ можно мержить
```

Каждый шаг - **гейт**: упал - мерж блокируется. Это и есть «настоящий» гейт качества, который, в отличие от [git-хуков](/content/advanced-tooling/git-hooks-and-quality-gates), нельзя обойти.

## GitHub Actions

Самая распространённая CI-платформа для фронтенда. Пайплайн описывается YAML в `.github/workflows/`.

```yaml
name: CI
on: [push, pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20, cache: 'pnpm' }
      - run: pnpm install --frozen-lockfile
      - run: pnpm lint
      - run: pnpm typecheck      # tsc --noEmit
      - run: pnpm test
      - run: pnpm build
```

> `--frozen-lockfile` / `npm ci` - установка **строго по lockfile**, без обновлений. В CI всегда так: детерминированно и быстрее.

## Фронтенд-специфичные гейты

| Гейт | Чем |
|------|-----|
| Стиль и баги | ESLint, Prettier `--check` |
| Типы | `tsc --noEmit` / `vue-tsc` |
| Тесты | Vitest/Jest (unit/integration), Playwright (e2e) |
| Сборка | прод-build должен пройти |
| Размер бандла | size-limit / bundlewatch - не дать бандлу распухнуть |
| Доступность/визуал | a11y-проверки, visual regression |

<b class="text-on-semi-light">Почему `tsc --noEmit` обязателен</b> - <span class="text-gray">Сборка (Vite/esbuild) типы не проверяет - только срезает ([тулинг TypeScript](/content/advanced-tooling/typescript-tooling)). Без отдельного шага проверки типов ошибки уедут в прод. В CI это критичный гейт.</span>

## Ускорение пайплайна

CI должен быть быстрым, иначе тормозит разработку:

- **Кеширование** - кешировать стор пакетов (pnpm/npm) и артефакты сборки между запусками.
- **Параллелизация** - линт, типы и тесты в параллельных job'ах.
- **Fail fast** - падать на первой ошибке, не гоняя остальное зря.
- **Матрицы** - запуск на нескольких версиях Node/браузерах при необходимости.
- **Affected-сборки** в [монорепо](/content/advanced-tooling/monorepo-tooling) - проверять только затронутые пакеты.

## Branch protection

Гейты работают только если их **требуют**: в настройках репозитория включают **обязательные проверки** - нельзя смержить PR, пока CI не зелёный. Без этого пайплайн - рекомендация, а не гарантия.

---

## Превью-деплои

Платформы (Vercel, Netlify) на каждый PR создают **превью-деплой** - живую версию с изменениями по уникальному URL. Ревьюеры видят результат вживую до мержа. Очень удобно для фронтенда; деплой-часть - в [тестировании и деплое](/content/testing-deploying).

---

## CD

После зелёного CI и мержа в `main` запускается **деплой**: сборка прода и публикация на хостинг/CDN. Артефакты сборки могут передаваться между job'ами. Конкретные цели деплоя - тема главы 14.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое CI/CD?</b>
<span class="text-gray">CI - автоматическая проверка каждого изменения (линт, типы, тесты, сборка) при частых вливаниях. CD - автоматическая доставка готового кода в прод (delivery - по кнопке, deployment - автоматически на каждый мерж).</span>

<b class="text-on-semi-light">Какие гейты в CI для фронтенда?</b>
<span class="text-gray">Линт, `tsc --noEmit`, тесты (unit/e2e), успешная сборка, проверка размера бандла. Каждый блокирует мерж при падении.</span>

<b class="text-on-semi-light">Почему в CI нужен отдельный шаг проверки типов?</b>
<span class="text-gray">Сборка срезает типы, но не проверяет их. Без `tsc --noEmit` ошибки типов уедут в прод, ведь билд их не остановит.</span>

<b class="text-on-semi-light">Зачем npm ci / --frozen-lockfile в CI?</b>
<span class="text-gray">Детерминированная установка строго по lockfile, без обновлений версий - воспроизводимость и скорость. Гарантирует, что CI ставит ровно то же, что и разработчики.</span>

<b class="text-on-semi-light">Чем CI-гейт надёжнее git-хука?</b>
<span class="text-gray">Хук локальный и обходится (`--no-verify`). CI запускается на сервере, его не обойти, и с branch protection он реально блокирует мерж до зелёного статуса.</span>

<b class="text-on-semi-light">Что такое превью-деплой?</b>
<span class="text-gray">Живая версия приложения с изменениями PR по отдельному URL (Vercel/Netlify) - ревьюеры видят результат вживую до мержа.</span>
