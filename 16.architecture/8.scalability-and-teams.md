# Масштабируемость и команды

Масштабирование фронтенда - это **две** задачи: масштаб **кода** (приложение растёт) и масштаб **команд** (людей становится больше). Архитектура должна выдерживать оба. На senior-уровне ждут понимания, что код и организация - связаны.

---

## Два измерения масштаба

```
Масштаб кода   → больше фич, файлов, бандла → нужны границы, code splitting
Масштаб команд → больше людей → нужны владение, автономия, согласованность
```

Они переплетены: плохие границы кода = команды наступают друг другу на ноги.

---

## Закон Конвея

> «Организации проектируют системы, копирующие их структуру коммуникации». - Мелвин Конвей

<b class="text-on-semi-light">Практический вывод</b> - <span class="text-gray">Структура кода стремится повторить структуру команд. Это можно использовать: осознанно выровнять **границы модулей под границы команд** (каждая команда владеет своими фичами/пакетами). «Обратный манёвр Конвея» - перестроить команды под желаемую архитектуру. Игнорировать связь команд и кода - значит получить трение там, где границы не совпадают.</span>

## Масштаб кода

### Границы и модульность

Чёткие [границы модулей/фич](/content/architecture/project-structure) - основа: команды меняют свою часть, не задевая чужую. Низкая связанность = независимость работы.

### Стратегия code splitting

Большой бандл - враг. Разбивай ([оптимизация](/content/advanced-tooling/optimization)):

- **по маршрутам** - каждая страница своим чанком;
- **по фичам** - тяжёлые фичи лениво;
- **общий вендор-чанк** - кешируется отдельно.

### Бюджеты производительности

**Performance budget** - лимит на размер бандла/метрики, который CI проверяет ([CI](/content/advanced-tooling/ci-cd)). Не даёт приложению незаметно «распухнуть» по мере роста.

## Масштаб команд

### Владение

Явные **границы владения**: какая команда отвечает за какую часть (`CODEOWNERS`-файлы, кто ревьюит что). Без этого общий код становится «ничьим» и деградирует.

### Общий код и платформенная команда

Общие части (ui-kit, утилиты, конфиги) - узкое место: их меняют все, ломают все. Решение - **выделенный владелец** (платформенная команда) и строгий API общих пакетов.

### Монорепо

[Монорепо](/content/advanced-tooling/monorepo-tooling) - частый ответ на масштаб: общий код без публикации, атомарные изменения через границы, единые версии. Цена - нужна оркестрация (Turborepo/Nx) и дисциплина границ. Часто проще [микрофронтендов](/content/architecture/micro-frontends).

## Согласованность через governance

Чтобы независимые команды не разъехались, вводят **правила, проверяемые автоматически**:

- **линт-правила** и [форматтеры](/content/advanced-tooling/linting-and-formatting) - единый стиль;
- **правила зависимостей** - кто что может импортировать (направление зависимостей);
- **конвенции** структуры, именования;
- **дизайн-система** - визуальная согласованность.

> Согласованность на масштабе достигается не уговорами, а **автоматизацией**: то, что проверяет CI, соблюдается; то, что «на словах», - разъезжается.

---

## Документация и решения

С ростом команд знание не помещается в головах. Нужны:

- **документация** архитектуры и конвенций;
- **ADR** (записи архитектурных решений) - почему сделано так ([архитектурные решения](/content/architecture/architectural-decisions));
- **онбординг** - структура, которую новый человек освоит быстро.

Понятная структура - это тоже масштабируемость: новый разработчик включается без месяцев погружения.

## Team Topologies

Современная модель организации команд (книга «Team Topologies»), напрямую влияющая на архитектуру:

| Тип команды | Роль |
|-------------|------|
| **Stream-aligned** | владеет потоком ценности (фичей/доменом) end-to-end |
| **Platform** | строит внутреннюю платформу/инструменты для других |
| **Enabling** | помогает командам освоить новое (наставники) |
| **Complicated-subsystem** | владеет сложной узкоспециализированной частью |

Большинство продуктовых команд - stream-aligned; их поддерживает платформенная команда (ui-kit, тулинг, paved roads).

## Paved roads и fitness functions

- **Paved road / golden path** - рекомендованный, хорошо поддержанный способ делать типовое (стартеры, шаблоны, утверждённый стек). Свернуть можно, но «по дороге» - легко и безопасно. Масштабирует согласованность без диктата.
- **Inner source** - внутренний open source: команды контрибьютят в общие пакеты по модели OSS (PR, мейнтейнеры), снимая узкое место платформенной команды.
- **Fitness functions** - автоматические проверки архитектурных свойств в CI (размер бандла, запрет циклов, границы зависимостей) - не дают архитектуре деградировать незаметно.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое закон Конвея и как его применяют?</b>
<span class="text-gray">Структура системы копирует структуру коммуникации организации. Применяют осознанно: выравнивают границы модулей под границы команд, чтобы каждая владела своей частью независимо.</span>

<b class="text-on-semi-light">Как масштабировать фронтенд-кодовую базу?</b>
<span class="text-gray">Чёткие границы модулей/фич (низкая связанность), стратегия code splitting (по маршрутам/фичам), performance budgets в CI, часто монорепо для общего кода. Плюс автоматизированные правила согласованности.</span>

<b class="text-on-semi-light">Как несколько команд работают над одним фронтендом без хаоса?</b>
<span class="text-gray">Явные границы владения (CODEOWNERS), автономия через модульные границы, выделенный владелец общего кода (платформенная команда), и governance через линт/правила зависимостей/дизайн-систему, проверяемые CI.</span>

<b class="text-on-semi-light">Как поддерживать согласованность между независимыми командами?</b>
<span class="text-gray">Автоматизацией: линт-правила, правила зависимостей, конвенции, дизайн-система, проверяемые в CI. «На словах» правила разъезжаются; то, что проверяет CI, соблюдается.</span>

<b class="text-on-semi-light">Монорепо или микрофронтенды для масштаба?</b>
<span class="text-gray">Монорепо с хорошими границами часто проще: общий код, атомарные изменения, автономия владения без рантайм-сложности микрофронтендов. Микрофронтенды - когда нужна именно независимость деплоя у больших организаций.</span>
