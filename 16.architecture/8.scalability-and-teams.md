# Масштабируемость и команды

Как архитектура выдерживает рост: кода становится больше, людей — тоже, и второе ломает проект чаще первого. Здесь — закон Конвея и обратный манёвр, границы владения и `CODEOWNERS`, общий код и платформенная команда, согласованность через автоматические проверки, «мощёные дороги», функции пригодности и Team Topologies. Спрашивают, как несколько команд работают в одном фронтенде без хаоса и как держать согласованность. Глубже — почему правило владения в конце файла отдаёт весь репозиторий одной команде и как по истории git найти границу, проведённую не там.

::tldr
- **У масштаба два измерения:** растёт код — нужны границы и разделение бандла; растут команды — нужны владение, автономия и согласованность. Плохие границы кода превращаются в конфликты между людьми.
- **Закон Конвея:** система повторяет структуру общения в организации. Границы модулей выравнивают под границы команд, а иногда перестраивают команды под нужную архитектуру.
- **Владение явное:** у каждого файла есть команда, которая его ревьюит, — `CODEOWNERS`, где побеждает последнее совпавшее правило. Общий код без владельца деградирует.
- **Согласованность — автоматикой, а не уговорами:** линт-правила, правила зависимостей, бюджеты, проверка владельцев в CI. Что проверяет CI, соблюдается; что договорено на словах — расходится.
- **Удобный путь вместо запретов:** платформенная команда делает правильный способ самым простым — шаблоны, общие пакеты, правила с подсказкой, куда идти.
::

## Два измерения масштаба

Сквозной пример — магазин, который вырос из одной команды в пять: каталог, корзина и оформление, личный кабинет, отзывы и платформа (ui-kit, сборка, CI).

```text
Масштаб кода   → больше фич, файлов, бандл тяжелее → границы, разделение кода, бюджеты
Масштаб команд → больше людей и решений          → владение, автономия, согласованность
```

Первое решается техникой, второе — организацией, но они связаны. Если граница между каталогом и корзиной проведена плохо, каждая задача требует правок у обеих команд — и техническая проблема становится очередью на ревью, конфликтами и созвонами.

### Почему люди дороже кода

Между n людьми n(n−1)/2 возможных каналов общения. Пять человек — 10 каналов, десять — 45, пятьдесят — 1225. Пять команд по десять человек внутри себя держат 225 каналов, а между командами общаются через договорённые интерфейсы. Поэтому большой фронтенд делят не ради красоты кода, а чтобы большинство решений принималось внутри одной команды.

## Закон Конвея

Мелвин Конвей в 1968 году сформулировал: организации проектируют системы, которые копируют структуру их коммуникации. Если каталог и корзину делают разные команды, между ними появится граница — хорошая или плохая.

Из этого два практических вывода:

- **выровнять код под команды** — каждая команда владеет своими фичами или пакетами, граница модуля совпадает с границей ответственности;
- **обратный манёвр Конвея** — если нужна другая архитектура, сначала перестраивают команды: пока оформлением заказа занимаются три команды, единого модуля оформления не получится.

Игнорировать эту связь — значит получить трение именно там, где граница кода и граница команд не совпадают. Крайняя форма выравнивания — [микрофронтенды](/content/architecture/micro-frontends), где у каждой команды ещё и своя выкладка.

## Масштаб кода

Код масштабируется за счёт тех же приёмов, что разобраны в других главах, — здесь важно, что каждый из них снимает нагрузку с людей:

- **границы модулей** — [структура проекта](/content/architecture/project-structure) с публичным API у каждой фичи: команда меняет внутренности, не задевая соседей;
- **разделение кода** — по маршрутам и тяжёлым фичам, чтобы рост одной части не замедлял загрузку всех ([оптимизация](/content/advanced-tooling/optimization));
- **бюджеты размера** — проверка в CI, которая не даёт бандлу незаметно распухнуть ([CI/CD](/content/advanced-tooling/ci-cd));
- **монорепо** — общий код без публикации пакетов и атомарные изменения через границы, а оркестратор с кешем запускает задачи только для изменённых пакетов ([тулинг монорепо](/content/advanced-tooling/monorepo-tooling)).

Но границы в коде ничего не значат, пока не ясно, кто за какую часть отвечает.

## Владение

Код без владельца — общий, а общий быстро становится ничьим: каждый добавляет «свой случай», никто не удаляет старое, ревью делает тот, кто оказался рядом.

### CODEOWNERS

Файл `CODEOWNERS` сопоставляет пути с командами. GitHub ищет его в `.github/`, в корне и в `docs/` — в этом порядке, берёт первый найденный. Шаблоны похожи на `.gitignore`, но без отрицания `!` и диапазонов `[ ]`. Главное правило: **побеждает последнее совпавшее**, поэтому файл пишут от общего к частному.

```text
*               @shop/platform
/src/catalog/   @shop/catalog
/src/cart/      @shop/cart
/src/checkout/  @shop/cart
/src/shared/ui/ @shop/platform @shop/design
*.css           @shop/design
```

В проверке так `ProductCard.tsx` достался каталогу, `pay.ts` — корзине, `Button.tsx` — сразу двум командам, а `button.css` — дизайну: строка `*.css` ниже правила папки и перекрывает его. Папка отзывов своей строки не получила и ушла общему владельцу.

Вместе с правилом защиты ветки «Require review from Code Owners» владение становится обязательным: PR не сольётся без одобрения команды-владельца. Если владельцев несколько, достаточно одобрения любого из них.

### Проверка, что у каждого файла есть владелец

Без строки `*` новая папка остаётся без владельца, и этого никто не замечает. В проверке у файла без общего правила таких набралось три из семи: оформление, отзывы и `package.json`. Это типичная **функция пригодности** — автоматическая проверка архитектурного свойства, которую запускают в CI: «у каждого файла есть владелец», «нет циклов между фичами», «точка входа меньше бюджета».

### Общий код и платформенная команда

Ui-kit, утилиты, конфиги сборки меняют все — и ломают все. Решение — **явный владелец** и узкий публичный API. Платформенная команда отвечает за общие пакеты, но не должна становиться узким местом: если каждое изменение кнопки ждёт её неделю, команды начнут копировать кнопку к себе.

Эту проблему снимает **inner source** — внутренний open source: любая команда может прислать PR в общий пакет, платформа выступает мейнтейнером — ревьюит, держит стандарты и выпускает версии.

## Где граница проведена не там

Владение по папкам легко назначить и трудно проверить: граница может выглядеть правильно, а работа всё равно идёт через две команды. Это видно по истории — файлы, которые часто меняются в одних и тех же коммитах, связаны, даже если в коде между ними нет импорта.

```bash
git log --name-only --format=format:--
```

По этому выводу считают пары файлов, изменённых вместе, и долю совместных изменений. В проверке на семи коммитах самая связанная пара — `src/catalog/ProductCard.tsx` и `src/cart/addToCart.ts`: 3 из 4 изменений корзинной функции шли вместе с карточкой каталога. Это файлы разных команд, значит каждая такая задача требует двух ревью и согласования выкладки. Пара `addToCart.ts` и `CartBadge.tsx` тоже менялась вместе, но внутри одной команды — это нормально.

Вывод из такой пары — не «запретить менять вместе», а переместить знание. Если карточка каталога каждый раз меняется ради корзины, значит в ней живёт логика корзины — например, расчёт цены со скидкой. Её выносят в публичный API корзины, а каталог только вызывает его.

## Согласованность через автоматику

Пять автономных команд за год разъедутся: разные библиотеки дат, разные способы запросов, разные кнопки. Уговоры и вики не помогают — помогают правила, которые проверяет CI:

- **линт-правила и форматтер** — единый стиль без споров на ревью ([линтинг и форматирование](/content/advanced-tooling/linting-and-formatting));
- **правила зависимостей** — кто кого может импортировать, внутренности чужой фичи закрыты;
- **проверка владельцев** и бюджеты — как выше;
- **дизайн-система** — общие компоненты и токены вместо своих версий в каждой команде.

### Мощёная дорога

**Мощёная дорога** (paved road, golden path) — поддержанный платформой способ делать типовые вещи: шаблон новой фичи, общий клиент API, утверждённая библиотека дат. Свернуть можно, но по дороге проще и безопаснее. Хорошее правило не только запрещает, но и показывает, куда идти:

```js
// eslint.config.js
export default [{
  files: ['src/**/*.js'],
  rules: {
    'no-restricted-imports': ['error', {
      paths: [{ name: 'moment', message: 'Даты — через date-fns, см. docs/dates.md' }],
      patterns: [{ group: ['@shop/*/internal/*'], message: 'Импортируйте публичный API пакета команды' }],
    }],
  },
}];
```

В проверке ESLint на импорт `moment` и внутреннего модуля корзины выдал две ошибки — `'moment' import is restricted from being used. Даты — через date-fns, см. docs/dates.md` и подсказку про публичный API, — а исправленный файл прошёл. Причина дороги измерима: та же задача форматирования даты через `moment` весит около 20 КБ gzip, через `format` из `date-fns` — около 5 КБ.

Если правило нужно обойти, это делают явно — комментарием-исключением с причиной, который увидит ревьюер, или предложением изменить правило.

## Team Topologies

Книга «Team Topologies» (Мэтью Скелтон и Мануэль Паис) описывает четыре типа команд — удобный язык для разговора о том, кто чем владеет:

| Тип команды | Роль | Во фронтенде |
|-------------|------|--------------|
| **Stream-aligned** | владеет потоком ценности от начала до конца | каталог, корзина, личный кабинет |
| **Platform** | делает внутреннюю платформу, которой пользуются другие | ui-kit, сборка, CI, шаблоны |
| **Enabling** | помогает командам освоить новое и уходит | внедрение доступности или тестов |
| **Complicated-subsystem** | владеет сложной специализированной частью | редактор, карты, видео |

Большинство команд — stream-aligned. Платформа нужна, чтобы им не приходилось решать одни и те же задачи по пять раз. Взаимодействия в книге тоже три: совместная работа на время, «X как сервис» — один пользуется продуктом другого — и помощь. Платформа, с которой каждая команда вынуждена постоянно работать совместно, — признак слишком сырого API.

## Знание на масштабе

С ростом команд решения перестают помещаться в головах. Нужны:

- **записи решений** — почему выбрано так, какие варианты отвергнуты ([архитектурные решения](/content/architecture/architectural-decisions));
- **документация конвенций** рядом с кодом, а не в забытой вики;
- **онбординг через структуру** — новый разработчик находит нужное по папкам и владельцам, а не по расспросам.

Понятная структура тоже масштабирует: новый человек начинает работать за дни, а не за месяцы.

## Красные флаги в ответе

- «Масштабируемость — это про производительность сервера» — на фронтенде это прежде всего рост кода и числа команд.
- Закон Конвея как курьёз, без вывода про выравнивание границ и обратный манёвр.
- Общий код «все поддерживают вместе» — без владельца и узкого API.
- `CODEOWNERS` с общим правилом в конце файла, которое перекрывает все командные.
- Согласованность через вики и договорённости, без проверок в CI.
- Платформенная команда как обязательный согласующий для каждого изменения — узкое место вместо дороги.
- Микрофронтенды как первый ответ на любой рост, хотя монорепо с границами решает большинство случаев.

## Как спрашивают на собеседовании

::question
Что такое закон Конвея и как его применяют?

#answer
Системы повторяют структуру общения организаций, которые их делают. Поэтому границы модулей выравнивают под границы команд: каждая владеет своими фичами или пакетами, большинство решений принимается внутри команды, а между командами — через договорённый публичный API.

#more
Обратный манёвр Конвея: чтобы получить нужную архитектуру, сначала меняют структуру команд. Несовпадение видно по истории — файлы разных команд, которые постоянно меняются вместе, показывают границу, проведённую не там. Каналов общения n(n−1)/2, поэтому деление на команды с интерфейсами между ними и есть способ масштабироваться.
::

::question
Как масштабировать фронтенд-кодовую базу?

#answer
Чёткие границы фич с публичным API и правилами зависимостей, разделение кода по маршрутам и тяжёлым фичам, бюджеты размера в CI. Общий код — в пакетах с владельцем, часто в монорепо, где изменение через границу делается одним PR.

#more
Масштаб кода быстро становится масштабом людей: без владения и автоматических проверок границы размываются. Функции пригодности — циклы, направление зависимостей, бюджет, владельцы — фиксируют архитектурные свойства так же, как тесты фиксируют поведение.
::

::question
Как несколько команд работают над одним фронтендом без хаоса?

#answer
Явное владение — `CODEOWNERS` и обязательное ревью владельца, автономия через границы фич, выделенный владелец общего кода и правила, которые проверяет CI: линт, зависимости, дизайн-система. Каждая команда может менять своё, не ожидая остальных.

#more
В `CODEOWNERS` побеждает последнее совпавшее правило — пишут от общего к частному, иначе строка `*` в конце отдаёт всё одной команде. Проверка «у каждого файла есть владелец» ловит новые папки без хозяина. Чтобы платформа не стала узким местом — inner source: команды присылают PR в общие пакеты, платформа ревьюит и выпускает.
::

::question
Как поддерживать согласованность между независимыми командами?

#answer
Автоматикой: линт-правила, правила зависимостей, бюджеты, проверка владельцев и общая дизайн-система, которые запускаются в CI. Что проверяет CI, соблюдается; что договорено на словах — расходится.

#more
Лучше всего работает мощёная дорога: правильный способ — самый простой. Правило линтера не только запрещает `moment`, но и в сообщении говорит, что использовать вместо него и где почитать. Отклонения допустимы, но явно — исключением с причиной или изменением правила.
::

::question
Монорепо или микрофронтенды для масштаба?

#answer
Чаще монорепо с хорошими границами: общий код без публикации, атомарные изменения, владение по папкам, и всё это без цены рантайм-композиции. Микрофронтенды нужны, когда командам требуется именно независимая выкладка и они готовы платить за общие зависимости и контракт интеграции.

#more
Многие проблемы, которые приписывают монолиту, — это отсутствие границ и владения, и микрофронтенды их не решают. Независимую выкладку можно частично получить и в монорепо — выкладывая отдельные приложения. Подробно о цене — в [Микрофронтендах](/content/architecture/micro-frontends).
::

::question
Что такое платформенная команда и мощёная дорога?

#answer
Платформенная команда делает внутренний продукт для других команд: ui-kit, сборку, CI, шаблоны, общий клиент API. Мощёная дорога — поддержанный ею способ делать типовые вещи, по которому идти проще, чем в обход.

#more
По Team Topologies это platform team, а продуктовые команды — stream-aligned. Взаимодействие с платформой в идеале — «X как сервис»: команда пользуется готовым, не согласуя каждый шаг. Если платформа стала обязательным согласующим, команды начинают копировать её код к себе — значит API платформы неудобен.
::

## Практика

::practice{title="Платформа одобряет все PR в репозитории"}
После того как в репозиторий добавили `CODEOWNERS`, каждый PR — даже в каталог — требует одобрения платформенной команды, а команду каталога GitHub не зовёт вовсе. Файл:

```text
/src/catalog/   @shop/catalog
/src/cart/      @shop/cart
/src/checkout/  @shop/cart
/src/shared/    @shop/platform
*               @shop/platform
```

#solution
В `CODEOWNERS` побеждает последнее совпавшее правило, а `*` совпадает с любым файлом. В проверке с таким порядком все семь файлов достались платформе. Общее правило переносят в начало, частные — ниже:

```text
*               @shop/platform
/src/catalog/   @shop/catalog
/src/cart/      @shop/cart
/src/checkout/  @shop/cart
/src/shared/ui/ @shop/platform @shop/design
```

Строку `*` не удаляют совсем: без неё новые папки остаются без владельца — в проверке так оказались без хозяина оформление, отзывы и `package.json`. Чтобы это не повторилось, в CI добавляют проверку, что у каждого файла есть владелец.
::

::practice{title="Каждая задача каталога требует правок у корзины"}
Команда каталога жалуется: почти любая задача по карточке товара ждёт ревью и выкладки команды корзины. В коде импорт идёт только в одну сторону — карточка вызывает `addToCart`. Как понять, что не так с границей, и что исправить?

#solution
Посмотреть историю совместных изменений:

```bash
git log --name-only --format=format:--
```

По выводу считают пары файлов, изменённых в одних коммитах. В проверке самая связанная пара — `ProductCard.tsx` и `addToCart.ts`: три из четырёх изменений корзинной функции шли вместе с карточкой, и это файлы разных команд. Значит, знание лежит не там: карточка содержит логику корзины — например, расчёт цены со скидкой, — и каждое изменение правила трогает оба места.

Логику переносят в публичный API корзины — функцию или компонент кнопки с ценой, — а карточка только передаёт товар. После этого изменения правила остаются внутри одной команды. Если такая связанность системная, это повод пересмотреть и границы команд — обратный манёвр Конвея.
::
