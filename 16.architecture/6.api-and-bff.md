# API и BFF

Как форма API влияет на фронтенд: лишние и недостающие данные, водопады запросов, проблема многих сервисов, BFF — бэкенд под конкретный клиент, его отличие от шлюза, BFF на edge и в мета-фреймворке, контракты и контрактные тесты, совместимость изменений, слой защиты от чужой модели, федерация и интерфейс, управляемый сервером. Спрашивают, что такое over-fetching и under-fetching, зачем нужен BFF и чем он отличается от API Gateway. Глубже — откуда берётся лишний круг по мобильной сети, почему экран товара весит в тридцать раз больше, чем нужно, и какое изменение API можно выкатить без согласования с фронтендом.

::tldr
- **Форма API определяет производительность клиента:** лишние поля — лишний трафик, недостающие — несколько запросов подряд, где каждый ждёт предыдущий.
- **BFF — тонкий сервер под конкретный клиент:** собирает экран из нескольких сервисов внутри дата-центра, отдаёт ровно нужные поля, прячет ключи и внутреннюю структуру сервисов.
- **Шлюз — общий вход для всех клиентов** с маршрутизацией, авторизацией и лимитами; BFF — логика конкретного интерфейса. Часто их ставят вместе.
- **Контракт — источник истины:** OpenAPI, GraphQL-схема или tRPC дают типы, а контрактный тест потребителя ловит несовместимое изменение до выкладки.
- **Добавить поле — совместимо, переименовать или удалить — нет:** такие изменения проводят через новую версию или устаревание с переходным периодом.
::

## Форма API

Сквозной пример — экран товара в мобильном вебе: название, цена, наличие и продавец. Данные лежат в трёх сервисах — каталоге, складе и продавцах.

| Подход | Что получает фронтенд |
| --- | --- |
| REST по ресурсам | просто и кешируется, но лишние поля и несколько запросов на экран |
| GraphQL | ровно нужные поля одним запросом; сложнее сервер и кеширование |
| RPC, tRPC | вызовы с типами; удобно в одном TypeScript-репозитории |

Сами протоколы разобраны в [REST](/content/network-api/rest) и [GraphQL](/content/network-api/graphql), клиенты — в [Реалтайме и API-клиентах](/content/ecosystem-libs/realtime-and-api-clients). Здесь — как форма API влияет на архитектуру клиента.

### Лишнее и недостающее

- **over-fetching** — запись товара пришла с сорока полями, экрану нужны четыре;
- **under-fetching** — чтобы собрать экран, нужно несколько запросов, и часть из них ждёт результата предыдущего: продавца нельзя запросить, пока не пришёл товар с `sellerId`.

---

## Много сервисов

Если фронтенд сам собирает экран из сервисов, он знает их адреса, форматы, версии и правила авторизации. Каждый новый сервис — изменения в клиенте, а мобильная сеть платит за каждый круг.

В проверке «браузер» с задержкой 80 мс на круг собирал экран из трёх сервисов: сначала товар, затем параллельно склад и продавец. Это два круга по мобильной сети — около **300 мс** — и **2349 байт** ответа, из которых экрану нужна малая часть.

---

## BFF

**Backend for Frontend** — тонкий сервер, выделенный под конкретный клиент. Он собирает данные из сервисов, преобразует их под экран и отдаёт готовый ответ:

```js
// BFF: один запрос от клиента, сборка внутри дата-центра
app.get('/screens/product/:id', async (req, res) => {
  const product = await catalog.get(req.params.id);
  const [stock, seller] = await Promise.all([inventory.get(product.id), sellers.get(product.sellerId)]);
  res.json({ id: product.id, title: product.title, price: product.price, inStock: stock.count > 0, seller: seller.name });
});
```

В проверке тот же экран через BFF занял один круг по мобильной сети — около **200 мс** — и **73 байта** ответа: в тридцать с лишним раз меньше. Запросы к сервисам никуда не делись, но они идут внутри дата-центра, где круг — миллисекунды, а не десятки миллисекунд.

Что ещё делает BFF:

- **прячет секреты и авторизацию** — ключи сервисов и токены остаются на сервере (подробно — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens));
- **развязывает** — внутренние сервисы перестраиваются, а контракт экрана не меняется;
- **адаптирует** под клиент — веб-BFF и мобильный BFF отдают разное: мобильному — компактнее, с другими размерами картинок.

### BFF и шлюз

| | API Gateway | BFF |
| --- | --- | --- |
| Для кого | все клиенты | конкретный интерфейс |
| Что делает | маршрутизация, авторизация, лимиты, TLS | сборка экранов, преобразование, кеш под клиент |
| Кто владеет | платформа или инфраструктура | команда фронтенда или продукта |

Часто ставят оба: шлюз на входе, BFF за ним. Типичная ошибка — превратить BFF в место для бизнес-логики, которая должна жить в сервисах: тогда он становится ещё одним монолитом.

### Где живёт BFF

- **серверные маршруты мета-фреймворка** — Next.js, Nuxt, SvelteKit, — серверные компоненты и серверные функции фактически играют роль BFF (подробно — в [Мета-фреймворках](/content/ecosystem-libs/meta-frameworks));
- **отдельный сервис** на Node.js рядом с сервисами;
- **edge** — для сборки из кешируемых данных; с далёкой базой выигрыш теряется (подробно — в [Edge-вычислениях](/content/modern-dev/edge-computing)).

## Контракты

Чтобы клиент и сервер не расходились, API описывают **контрактом** — единым источником истины:

- **OpenAPI** — для REST, с генерацией типов и клиентов;
- **GraphQL-схема** — с генерацией типов запросов;
- **tRPC** — вывод типов без генерации в TypeScript-монорепо.

Подробно с проверками — в [Сквозной типобезопасности](/content/modern-dev/end-to-end-typesafety).

### Контрактный тест потребителя

Типы проверяют код клиента, но не то, что сервер действительно отдаёт. **Контрактный тест** фиксирует, что именно потребитель читает из ответа, и проверяется в :term[CI]{def="непрерывная интеграция: сервер, который собирает и тестирует код на каждое изменение"} провайдера: если сервер собирается сломать контракт, падает его сборка, а не прод. Инструмент для этого — Pact; в простом случае — схема потребителя, которой проверяют ответ сервера.

```js
const ProductScreenContract = z.object({ id: z.number(), title: z.string(), price: z.number(), inStock: z.boolean(), seller: z.string() });
```

В проверке:

- ответ BFF прошёл контракт;
- **добавленное** поле `deliveryDays` контракт пропустил — потребитель его просто не читает;
- **переименованное** `price → amount` контракт отклонил с путём `price`;
- **сменённый тип** `inStock: 3` — тоже отклонил.

Это принцип **терпимого читателя**: потребитель проверяет только то, что использует, поэтому сервер может добавлять поля без согласования.

## Совместимость изменений

| Изменение | Совместимо |
| --- | --- |
| добавить поле, необязательный параметр, новый эндпоинт | да |
| удалить или переименовать поле | нет |
| сменить тип или формат поля | нет |
| сделать необязательный параметр обязательным | нет |

Несовместимое изменение проводят по шагам: добавить новое рядом со старым, перевести клиентов, объявить старое устаревшим, удалить после переходного периода (подробно — в [Стратегиях выкладки](/content/testing-deploying/deployment-strategies)). Для публичного API — версии в пути или заголовке; в GraphQL вместо версий помечают поля `@deprecated` (подробно о версионировании — в [Паттернах API](/content/network-api/api-patterns)).

## Слой защиты от чужой модели

Внешний или унаследованный API часто устроен неудобно: `PRODUCT_ID` строкой, цена в копейках, названия с пробелами. **Слой защиты** — идея из предметно-ориентированного проектирования — переводит его в свою модель один раз на границе:

```js
const fromLegacy = (raw) => ({
  id: Number(raw.PRODUCT_ID),
  title: raw.NAME_RU.trim(),
  price: Math.round(Number(raw.PRICE_KOP) / 100),
});
```

В проверке запись `{ PRODUCT_ID: '7', NAME_RU: ' Пуэр ', PRICE_KOP: '120000' }` превратилась в `{ id: 7, title: 'Пуэр', price: 1200 }`. Дальше приложение работает со своей моделью, а странности внешнего API не расползаются по компонентам. Этот слой живёт в BFF или в слое данных клиента (подробно — в [Состоянии и данных](/content/architecture/state-and-data-architecture)).

## Федерация и интерфейс от сервера

- **GraphQL Federation** — единый граф из схем разных сервисов: клиент видит один API, а команды владеют своими частями. Это BFF, собранный из частей.
- **Интерфейс, управляемый сервером** — сервер описывает не только данные, но и сам интерфейс: какие блоки, в каком порядке. Клиент — исполнитель описания. Так меняют витрину без выпуска новой версии мобильного приложения; цена — сложный контракт и меньше свободы клиента.

---

## Красные флаги в ответе

- **«Фронтенд сам сходит в десять сервисов».** Клиент знает про всю внутреннюю структуру и платит кругами по мобильной сети.
- **«Положим бизнес-логику в BFF».** Он превратится в ещё один монолит; правила живут в сервисах.
- **«Типы есть — контрактный тест не нужен».** Типы проверяют клиент, а не реальный ответ сервера.
- **«Переименуем поле, фронтенд поправит».** Старые клиенты и открытые вкладки сломаются.
- **«GraphQL решит все проблемы».** Он убирает лишнее и недостающее, но добавляет сложность сервера и кеширования.
- **«BFF и шлюз — одно и то же».** Шлюз общий для всех, BFF — под конкретный интерфейс.

## Как спрашивают на собеседовании

::question
Что такое over-fetching и under-fetching?

#answer
Over-fetching — сервер отдаёт больше полей, чем нужно экрану, и клиент тратит трафик. Under-fetching — для экрана нужно несколько запросов, часть из которых ждёт предыдущий, и каждый — отдельный круг по сети.

#more
GraphQL решает обе проблемы запросом ровно нужных полей; BFF — сборкой экрана на сервере. На мобильной сети главная цена — число последовательных кругов, а не объём.
::

::question
Что такое BFF и зачем он нужен?

#answer
Backend for Frontend — тонкий сервер под конкретный клиент. Он собирает экран из нескольких сервисов внутри дата-центра, отдаёт ровно нужные поля, прячет ключи и внутреннюю структуру сервисов.

#more
Клиент делает один запрос вместо цепочки, а сервисы можно перестраивать без изменений клиента. Часто делают отдельные BFF для веба и мобильных приложений. Роль BFF играют и серверные маршруты мета-фреймворков.
::

::question
Чем BFF отличается от API Gateway?

#answer
Шлюз — общий вход для всех клиентов: маршрутизация, авторизация, лимиты, TLS. BFF — логика конкретного интерфейса: сборка экранов, преобразование, кеш под клиент.

#more
Шлюзом обычно владеет платформа, BFF — команда интерфейса. Часто их ставят вместе: шлюз на входе, BFF за ним. Бизнес-логику не кладут ни туда, ни туда.
::

::question
Как фронтенд и бэкенд не расходятся по API?

#answer
Общим контрактом — OpenAPI, GraphQL-схемой или tRPC — с генерацией или выводом типов, и контрактным тестом потребителя, который проверяет реальный ответ сервера в CI провайдера.

#more
Потребитель описывает только то, что читает, поэтому добавление полей совместимо, а переименование и смена типа ловятся до выкладки. Инструмент — Pact или схема потребителя.
::

::question
Какие изменения API совместимы?

#answer
Добавление поля, необязательного параметра или нового эндпоинта. Несовместимы удаление и переименование поля, смена его типа и превращение необязательного параметра в обязательный.

#more
Несовместимые изменения проводят через новое рядом со старым, переход клиентов и удаление после переходного периода. Для публичного API — версии, в GraphQL — `@deprecated`.
::

::question
Что такое интерфейс, управляемый сервером?

#answer
Сервер описывает не только данные, но и состав интерфейса — какие блоки и в каком порядке, — а клиент отображает это описание набором известных компонентов.

#more
Так меняют экраны без выпуска новой версии мобильного приложения и проводят эксперименты. Цена — сложный контракт, версии компонентов на клиенте и меньше свободы интерфейса.
::

## Практика

::practice{title="Экран товара грузится долго на мобильных"}
Экран товара в мобильном вебе делает три запроса: товар, затем склад и продавец по идентификаторам из ответа. На медленной сети экран появляется через секунду, хотя каждый сервис отвечает быстро.

#solution
Главная цена — последовательные круги по мобильной сети, а не сами сервисы. В проверке с задержкой 80 мс на круг экран без BFF занял около 300 мс и 2349 байт, а через BFF — около 200 мс и 73 байта. Экран собирают на сервере:

```js
// серверный маршрут мета-фреймворка или отдельный BFF
export async function GET(_req, { params }) {
  const product = await catalog.get(params.id);
  const [stock, seller] = await Promise.all([inventory.get(product.id), sellers.get(product.sellerId)]);
  return Response.json({ id: product.id, title: product.title, price: product.price, inStock: stock.count > 0, seller: seller.name });
}
```

Внутри дата-центра запросы почти бесплатны, а клиент делает один круг и получает только нужные поля. Ответ BFF удобно кешировать на CDN, если он не персональный.
::

::practice{title="Бэкенд переименовал поле"}
Команда каталога переименовала `price` в `amount` в ответе BFF. Тесты бэкенда зелёные, фронтенд узнал об этом из жалоб пользователей.

#solution
Тесты бэкенда проверяют его логику, а не то, что ждёт потребитель. Нужен контрактный тест потребителя в CI провайдера:

```js
// фронтенд публикует контракт того, что читает
export const ProductScreenContract = z.object({
  id: z.number(), title: z.string(), price: z.number(), inStock: z.boolean(), seller: z.string(),
});

// CI бэкенда проверяет свой ответ против контракта
test('экран товара соответствует контракту фронтенда', async () => {
  expect(ProductScreenContract.safeParse(await getProductScreen(7)).success).toBe(true);
});
```

В проверке контракт пропустил добавленное поле и отклонил переименование с путём `price`. Само переименование проводят совместимо: отдавать оба поля, перевести фронтенд, затем удалить `price`. Для этого есть Pact с брокером контрактов, но идея та же.
::
