# API и BFF

Как фронтенд общается с бэкендом - архитектурный вопрос, а не только технический. Форма API определяет производительность, связанность и сложность клиента. А паттерн **BFF** (Backend-for-Frontend) - частый ответ на проблему «фронтенд тонет в десятке микросервисов».

> Протоколы (HTTP, REST, GraphQL) - в [Network & API](/content/network-api). Здесь - **архитектурный** взгляд: как форма API влияет на фронтенд.

---

## Форма API влияет на фронтенд

| Подход | Для фронтенда |
|--------|---------------|
| **REST** | просто, но over/under-fetching, водопады |
| **GraphQL** | запрашиваешь ровно нужные поля, один запрос |
| **RPC (tRPC)** | типобезопасные вызовы в TS-монорепо |

### Over-fetching и under-fetching

```
Over-fetching:  GET /users/1 вернул 50 полей, нужно 2 (лишний трафик)
Under-fetching: чтобы собрать экран, нужно 5 запросов к разным эндпоинтам (водопад)
```

<b class="text-on-semi-light">Что решает GraphQL</b> - <span class="text-gray">GraphQL даёт запросить **ровно нужные поля** одним запросом, объединив данные из разных источников, - убирает over-fetching и водопады under-fetching. Цена - сложность сервера и кеширования. REST проще, но требует либо много эндпоинтов, либо агрегации на сервере.</span>

---

## Проблема многих сервисов

В микросервисной архитектуре бэкенда фронтенду пришлось бы знать про десяток сервисов, собирать данные из них, обрабатывать разные форматы и версии. Это сильная связанность и сложный клиент.

```
Фронтенд → users-service
        → orders-service
        → catalog-service
        → ... (клиент знает про все, агрегирует сам)
```

---

## BFF - Backend-for-Frontend

**BFF** - тонкий бэкенд-слой, выделенный **под конкретный фронтенд**. Он агрегирует данные из сервисов, преобразует их под нужды клиента и отдаёт готовый ответ.

```
Фронтенд → BFF → users / orders / catalog (BFF собирает и отдаёт готовое)
```

<b class="text-on-semi-light">Зачем BFF</b> - <span class="text-gray">Развязывает фронтенд и микросервисы: клиент общается с одним BFF, а не с десятком сервисов. BFF **агрегирует** (собирает экран одним запросом), **преобразует** (формат под клиент), **оптимизирует** (отдаёт ровно нужное, убирая over-fetching), прячет **секреты** и авторизацию на сервере. Меняется внутренняя структура сервисов - фронтенд не трогаем, правим BFF.</span>

### BFF под каждый клиент

Часто делают **отдельный BFF на платформу**: web-BFF и mobile-BFF отдают разные данные (мобайлу - компактнее), потому что у клиентов разные потребности.

---

## BFF vs API Gateway

Похожи, но не одно:

- **API Gateway** - общая точка входа ко всем сервисам (роутинг, auth, rate limiting) для **всех** клиентов.
- **BFF** - заточен под **конкретный** фронтенд, содержит клиент-специфичную агрегацию и преобразование.

Часто используются вместе: gateway + BFF поверх него.

---

## Edge как BFF

Современный вариант - размещать BFF на **edge** ([edge-вычисления](/content/modern-dev/edge-computing)): агрегация и преобразование близко к пользователю. Мета-фреймворки (серверные роуты Next/Nuxt, server actions) часто играют роль лёгкого BFF.

---

## Контракты

Чтобы фронт и бэк не расходились, API описывают **типизированным контрактом** - единым источником истины:

- **OpenAPI** (REST) → кодген типов клиента;
- **GraphQL schema** → кодген хуков и типов;
- **tRPC** → инференс типов без кодгена (TS-монорепо).

Это основа [сквозной типобезопасности](/content/modern-dev/end-to-end-typesafety): изменение контракта подсвечивает поломку на фронте до запуска.

---

## Версионирование

API эволюционирует; чтобы не ломать клиентов:

- **версии** (`/v1`, `/v2`) или версионирование в заголовках;
- **обратная совместимость** - добавлять поля, не удалять резко;
- GraphQL предпочитает **депрекацию полей** вместо версий.

---

## Federation и server-driven UI

Продвинутые подходы на стыке фронта и бэка:

- **GraphQL Federation / schema stitching** - собрать единый граф из схем многих сервисов; фронтенд видит один API, а команды владеют своими частями графа (микросервисы на уровне GraphQL).
- **Server-driven UI (SDUI)** - сервер описывает **не данные, а сам UI** (какие компоненты, в каком порядке); клиент - «рендерер» этого описания. Позволяет менять UI без релиза (особенно в мобайле); цена - меньше гибкости клиента и сложный контракт.
- **Anti-corruption layer** - слой на клиенте, переводящий «корявый» внешний API в удобную доменную модель, чтобы беспорядок бэкенда не протёк в приложение (идея из DDD).

---

## Контрактное тестирование

Типов мало - они стираются в рантайме. **Contract testing** (например, **Pact**) проверяет, что фронт и бэк реально соблюдают согласованный контракт: потребитель описывает ожидания, провайдер верифицирует их в своём CI. Ловит рассинхрон до прода без полного e2e.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое over-fetching и under-fetching?</b>
<span class="text-gray">Over-fetching - сервер вернул больше полей, чем нужно (лишний трафик). Under-fetching - чтобы собрать экран, нужно несколько запросов (водопад). GraphQL решает оба, отдавая ровно нужное одним запросом.</span>

<b class="text-on-semi-light">Что такое BFF и зачем он нужен?</b>
<span class="text-gray">Backend-for-Frontend - тонкий бэкенд под конкретный клиент. Агрегирует данные из микросервисов, преобразует под нужды фронтенда, оптимизирует payload, прячет секреты. Развязывает фронт и сервисы.</span>

<b class="text-on-semi-light">Чем BFF отличается от API Gateway?</b>
<span class="text-gray">Gateway - общая точка входа ко всем сервисам для всех клиентов (роутинг, auth). BFF заточен под конкретный фронтенд с клиент-специфичной агрегацией. Часто используются вместе.</span>

<b class="text-on-semi-light">REST или GraphQL для фронтенда?</b>
<span class="text-gray">GraphQL - когда экраны собирают данные из многих источников и важно убрать over/under-fetching; цена - сложность сервера и кеша. REST проще, но требует агрегации (на сервере или BFF). Зависит от сложности данных.</span>

<b class="text-on-semi-light">Как фронт и бэк не расходятся по API?</b>
<span class="text-gray">Типизированный контракт как источник истины: OpenAPI/GraphQL-схема с кодгеном или tRPC с инференсом. Изменение контракта подсвечивает поломку на фронте до запуска (сквозная типобезопасность).</span>

<b class="text-on-semi-light">Что такое server-driven UI?</b>
<span class="text-gray">Сервер описывает не только данные, но и сам UI (какие компоненты и в каком порядке); клиент рендерит это описание. Позволяет менять UI без релиза приложения; цена - сложный контракт и меньше гибкости клиента.</span>

<b class="text-on-semi-light">Зачем контрактное тестирование?</b>
<span class="text-gray">Типы стираются в рантайме. Contract testing (Pact) проверяет, что фронт и бэк соблюдают согласованный контракт: потребитель описывает ожидания, провайдер верифицирует их в CI. Ловит рассинхрон до прода без полного e2e.</span>
