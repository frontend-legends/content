# Архитектурное мышление

Принципы, на которых держится любая архитектура фронтенда — от компонента до системы: разделение ответственности, связанность и сцепление, направление зависимостей и инверсия, абстракции и их цена, SOLID применительно к компонентам, DRY и «неправильная абстракция», композиция, существенная и случайная сложность, проектирование под изменение. Спрашивают, что такое связанность и сцепление, как SOLID применяется во фронтенде и когда DRY вредит. Глубже — как увидеть циклические зависимости, почему зависимость от параметра упрощает тест и почему функция с пятью флагами хуже трёх похожих функций.

::tldr
- **Цель архитектуры — дешёвые изменения:** понимать кусок кода, не держа в голове весь проект, и менять его, не ломая остальное.
- **Слабая связанность, сильное сцепление:** модули мало знают друг о друге, а внутри модуля лежит то, что меняется вместе. Циклические зависимости — главный признак, что границы проведены неверно.
- **Зависимости направлены к стабильному:** правила и данные не знают об интерфейсе; конкретику — сеть, хранилище, вывод — передают параметром. Так код тестируется без моков и переносится.
- **Абстракция стоит денег:** каждый слой — косвенность. Повторение дешевле неправильной абстракции; функция, обросшая флагами, — сигнал разделить её обратно.
- **Сложность бывает существенной и случайной:** первую диктует задача, вторую приносят решения команды — её и нужно сокращать.
::

## Разделение ответственности

Сквозной пример — корзина магазина: список товаров, правило скидки «10% от десяти позиций», вывод итога в шапке.

Каждая часть кода отвечает за одно: данные, правила, состояние, отображение — разные заботы.

```jsx
// всё вместе: запрос, правило и разметка в одном месте
function Cart() {
  const [items, setItems] = useState([]);
  useEffect(() => { fetch('/api/cart').then((r) => r.json()).then(setItems); }, []);
  const total = items.reduce((s, p) => s + p.price - (items.length >= 10 ? p.price * 0.1 : 0), 0);
  return <p>Итого: {total} ₽</p>;
}

// разделено: данные, правило, отображение
function Cart() {
  const { data: items = [] } = useCart();           // данные
  const total = cartTotal(items);                    // правило — чистая функция
  return <CartTotal value={total} />;                // отображение
}
```

Правило скидки теперь можно проверить модульным тестом без React, а интерфейс — без сети. Как это раскладывается по слоям и папкам — в [Структуре проекта](/content/architecture/project-structure) и [Архитектурных паттернах](/content/architecture/architectural-patterns).

## Связанность и сцепление

- **Связанность** (coupling) — насколько модули зависят друг от друга. Нужна **низкая**: изменение одного не тянет за собой другие.
- **Сцепление** (cohesion) — насколько связано содержимое **внутри** модуля. Нужно **высокое**: вместе лежит то, что меняется вместе.

### Как это увидеть

В проверке первая версия корзины — три модуля — прошла через :term[dependency-cruiser]{def="инструмент, который строит граф зависимостей модулей и проверяет правила импорта"}:

```text
cart.js    → pricing.js, ui.js
pricing.js → cart.js        (берёт список товаров напрямую)
ui.js      → cart.js, pricing.js
```

Инструмент нашёл циклы `cart.js → pricing.js` и `cart.js → ui.js`. Цикл значит, что модули нельзя понять, протестировать и изменить по отдельности: правило скидки зависит от корзины, корзина — от интерфейса, интерфейс — от обоих.

Во второй версии правило скидки стало чистой функцией от товара и количества, а корзина получила обработчик изменений параметром:

```js
// pricing.js — ни от чего не зависит
export const discountFor = (p, count) => (count >= 10 ? p.price * 0.1 : 0);

// cart.js — знает только правило
export function createCart(onChange) { /* … */ }

// ui.js — собирает всё вместе
const cart = createCart(() => render(cart.total()));
```

Циклов не стало, `pricing.js` не зависит ни от чего, `cart.js` — только от правила, а `ui.js` никто не импортирует: зависимости направлены внутрь, к стабильному. Такие правила проверяют в :term[CI]{def="непрерывная интеграция: сервер, который собирает и тестирует код на каждое изменение"} автоматически (подробно — в [Структуре проекта](/content/architecture/project-structure)).

## Направление зависимостей

Код меняется с разной скоростью: правило скидки — раз в квартал, вёрстка корзины — каждую неделю, способ загрузки данных — при смене API. Устойчивое правило: **изменчивое зависит от стабильного, а не наоборот**.

### Инверсия зависимостей

Если модулю нужна конкретика — сеть, хранилище, аналитика, — он получает её **параметром**, а не импортирует сам:

```js
export function createSearch({ fetchProducts }) {
  return async (query) => (query.trim().length < 2 ? [] : fetchProducts(query.trim()));
}
```

В проверке поиск протестирован без единого мока сети: в тест передали функцию-заглушку и проверили, что короткий запрос не уходит в сеть, а пробелы обрезаются. Тот же поиск в приложении получает настоящий API-клиент, а в Storybook — фиктивные данные. Во фронтенде инверсия — это пропсы, аргументы функций, контекст и провайдеры (подробно о подмене зависимостей в тестах — в [Моках и дублёрах](/content/testing-deploying/mocking-and-test-doubles)).

## Абстракция и её цена

Абстракция прячет сложность за простым интерфейсом: `useCart()` скрывает запрос, кеш, повтор и ошибки. Хорошая абстракция экономит больше, чем добавляет.

- **дырявая абстракция** — детали реализации просачиваются наружу: чтобы пользоваться `useCart`, нужно знать, как устроен кеш;
- **лишний слой** — обёртка, которая ничего не прячет, а только добавляет файл и имя.

### Неправильная абстракция

Две похожие функции объединили в «общую», а потом каждое новое требование добавляло флаг. В проверке у `formatPrice` оказалось пять флагов — 32 сочетания поведения, — и флаги начали мешать друг другу: `formatPrice(1200, { short: true, forEmail: true })` вернул `'1к'`, проигнорировав формат для писем. Никто не тестирует 32 варианта, и каждое изменение рискует сломать какой-то из них.

Сэнди Метц сформулировала это так: повторение дешевле неправильной абстракции. Если общая функция обросла флагами, её разделяют обратно на несколько простых. Обобщать стоит, когда видны три и больше одинаковых случаев с одинаковой причиной изменений, а не просто похожий код.

### DRY, KISS, YAGNI

| Принцип | Смысл | Ловушка |
| --- | --- | --- |
| DRY | одно знание — в одном месте | объединять похожий код с разными причинами изменений |
| KISS | простое решение, пока сложное не оправдано | «простота» за счёт скрытой сложности в другом месте |
| YAGNI | не строить то, что может понадобиться | не продумать то, что точно понадобится скоро |

:term[DRY]{def="Don't Repeat Yourself: каждое знание о системе должно жить в одном месте"} — про знание, а не про текст: одинаковые три строки в форме входа и форме заказа — не дублирование, если меняются по разным причинам.

## SOLID для компонентов

| Принцип | Во фронтенде |
| --- | --- |
| единственная ответственность | компонент, хук или модуль меняется по одной причине |
| открытость и закрытость | расширение через пропсы, слоты и композицию, а не правку внутренностей |
| подстановка | компоненты с одним интерфейсом взаимозаменяемы: любой `Button` работает в форме |
| разделение интерфейсов | маленькие наборы пропсов вместо «компонента-бога» с тридцатью опциями |
| инверсия зависимостей | зависимость от абстракций — пропсов, контекста, — а не от конкретного API |

Как это выглядит в API компонентов — слоты, составные компоненты, управляемый режим — в [Паттернах и дизайне компонентов React](/content/reactjs/patterns-and-component-design) и [Архитектуре компонентов](/content/architecture/component-architecture).

## Композиция

Сложное во фронтенде собирают **композицией**: компоненты из компонентов, хуки из хуков, функции из функций. Наследование создаёт жёсткую иерархию, где изменение базового класса задевает всех наследников. Композиция позволяет собрать нужное сочетание без иерархии — поэтому наследование компонентов почти исчезло из React и Vue.

---

## Сложность

Фредерик Брукс разделил сложность на два вида:

- **существенная** — присуща самой задаче: скидки, налоги, правила доставки в разных странах; её не убрать;
- **случайная** — привнесена решениями: запутанные зависимости, лишние слои, неподходящий инструмент, «умный» код.

Цель архитектуры — уменьшать случайную сложность, чтобы силы шли на существенную.

### Когнитивная нагрузка

Практический критерий — сколько нужно держать в голове, чтобы понять или изменить кусок кода. Её снижают **локальность** — связанное рядом, — узкие интерфейсы и предсказуемость. Если для правки одной строки нужно разобраться в половине проекта, связанность слишком высока. Код читают чаще, чем пишут, поэтому понятное многословное решение лучше плотного «умного».

---

## Проектирование под изменение

Группируют код не только по типу — компоненты, хуки, утилиты, — но и по тому, **что меняется вместе и почему**. То, что меняется по одной причине и в одно время, держат рядом и прячут за стабильным интерфейсом. Это и есть единственная ответственность на уровне модулей.

**Закон Деметры** — «не разговаривай с незнакомцами»: модуль работает с ближайшими соседями и не лезет вглубь чужих структур вроде `order.customer.address.city.name`. Тогда изменение внутренней структуры заказа не ломает далёких потребителей.

---

## Красные флаги в ответе

- **«Сделаем один универсальный компонент на всё».** Он обрастёт флагами и сочетаниями, которые никто не тестирует.
- **«Модули импортируют друг друга, но работает».** Циклы делают их неразделимыми и непредсказуемыми при загрузке.
- **«Вынесу общее после второго повтора».** Похожий код с разными причинами изменений лучше держать раздельно.
- **«Для теста замокаю модуль API».** Проще передать зависимость параметром.
- **«Архитектура — это структура папок».** Структура — следствие; суть — границы и направление зависимостей.
- **«Чем больше слоёв, тем чище».** Каждый слой — косвенность, которую должен окупать.

## Как спрашивают на собеседовании

::question
Что такое связанность и сцепление?

#answer
Связанность — насколько модули зависят друг от друга, её держат низкой. Сцепление — насколько связано содержимое внутри модуля, его держат высоким. Вместе это позволяет понимать и менять часть, не трогая остальное.

#more
Видимый признак проблемы — циклические зависимости: инструменты вроде dependency-cruiser и madge находят их автоматически, а правила о направлении зависимостей проверяют в CI.
::

::question
Что такое разделение ответственности?

#answer
Каждая часть отвечает за одно: данные, бизнес-правила, состояние, отображение. Правило скидки — чистая функция, загрузка — хук, разметка — компонент.

#more
Это упрощает тестирование — правило проверяется без React и сети, — и изменение: смена API не трогает вёрстку.
::

::question
Как SOLID применяется во фронтенде?

#answer
Единственная ответственность — компонент меняется по одной причине; открытость — расширение пропсами и композицией; подстановка — компоненты с одним интерфейсом взаимозаменяемы; разделение интерфейсов — маленькие наборы пропсов; инверсия — зависимость от пропсов и контекста, а не от конкретного API.

#more
Чаще всего на практике важны первый и последний: компоненты-«боги» и модули, которые сами импортируют сеть и хранилище, — главные источники связанности.
::

::question
Когда DRY вредит?

#answer
Когда объединяют похожий код с разными причинами изменений. Общая функция обрастает флагами, их сочетания никто не тестирует, и каждое изменение рискует сломать чужой случай.

#more
Повторение дешевле неправильной абстракции. Объединяют знание, а не текст, и после того, как видно несколько одинаковых случаев. Если абстракция обросла флагами, её разделяют обратно.
::

::question
Что такое инверсия зависимостей во фронтенде?

#answer
Модуль получает конкретику — сеть, хранилище, аналитику — параметром, пропсом или через контекст, а не импортирует её сам. Он зависит от интерфейса, а реализацию выбирает тот, кто его использует.

#more
Так модуль тестируется без моков модулей — достаточно передать заглушку, — и переиспользуется: тот же поиск работает с настоящим API, фиктивными данными в Storybook и кешем офлайн.
::

::question
Чем существенная сложность отличается от случайной?

#answer
Существенная присуща задаче — бизнес-правила, домен; её не убрать. Случайная привнесена решениями — запутанные зависимости, лишние слои, неподходящие инструменты; её можно и нужно сокращать.

#more
Практический показатель — когнитивная нагрузка: сколько нужно держать в голове для изменения. Её снижают локальностью, узкими интерфейсами и предсказуемостью.
::

## Практика

::practice{title="Корзина, которую нельзя тестировать"}
Модуль корзины импортирует модуль цен, тот импортирует корзину, чтобы узнать число позиций, а корзина ещё и вызывает перерисовку шапки. Тест на скидку требует поднять половину приложения.

#solution
Циклы делают модули неразделимыми. В проверке dependency-cruiser нашёл `cart.js → pricing.js` и `cart.js → ui.js`. Исправление — направить зависимости к стабильному:

```js
// правило — чистая функция, ни от чего не зависит
export const discountFor = (p, count) => (count >= 10 ? p.price * 0.1 : 0);

// корзина знает только правило, а об изменениях сообщает через параметр
export function createCart(onChange) {
  const items = [];
  return {
    add: (p) => { items.push(p); onChange(); },
    total: () => items.reduce((s, p) => s + p.price - discountFor(p, items.length), 0),
  };
}
```

После переделки циклов не осталось, правило тестируется одной строкой, а корзина — с любым обработчиком изменений. Запрет циклов добавляют в CI правилом dependency-cruiser.
::

::practice{title="Функция форматирования с пятью флагами"}
`formatPrice(value, { currency, withSpace, short, forEmail, roundUp })` используется в двадцати местах. Новое требование — формат для PDF-чеков — опять просят добавить флагом.

#solution
Пять флагов — 32 сочетания, и они уже конфликтуют: в проверке `short` и `forEmail` вместе дали `'1к'`, забыв про формат письма. Функцию разделяют по причинам изменений:

```js
const rub = new Intl.NumberFormat('ru', { style: 'currency', currency: 'RUB', maximumFractionDigits: 0 });

export const priceOnSite = (v) => rub.format(v);
export const priceShort = (v) => (v >= 1000 ? `${Math.round(v / 1000)} тыс. ₽` : rub.format(v));
export const priceInEmail = (v) => `${Math.round(v)} руб.`;
export const priceOnReceipt = (v) => rub.format(Math.ceil(v));
```

Каждая функция простая, её легко проверить, а новый формат — новая функция, которая ничего не ломает. Общая часть — `Intl.NumberFormat` — переиспользуется без флагов.
::
