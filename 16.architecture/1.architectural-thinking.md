# Архитектурное мышление

Прежде чем выбирать паттерны и структуру папок, нужно понять **принципы**, которые работают на любом уровне - от компонента до системы. Это язык, на котором обсуждают архитектуру, и то, что проверяют, когда спрашивают «как бы ты это спроектировал».

---

## Разделение ответственности

**Separation of Concerns (SoC)** - каждая часть отвечает за одно. UI, бизнес-логика, доступ к данным, состояние - разные «заботы», которые не стоит смешивать в одном месте.

```jsx
// ❌ всё в одном: запрос, логика, разметка перемешаны
function UserList() {
  const [users, setUsers] = useState([]);
  useEffect(() => { fetch('/api/users').then(r => r.json()).then(setUsers); }, []);
  const active = users.filter(u => u.lastSeen > Date.now() - DAY);
  return <ul>{active.map(...)}</ul>;
}

// ✅ разделено: данные (хук), логика (функция), представление (компонент)
function UserList() {
  const { data } = useUsers();          // слой данных
  const active = selectActive(data);    // логика
  return <UserListView users={active} />; // представление
}
```

## Связанность и сцепление

Главная пара метрик архитектуры.

- **Coupling (связанность)** - насколько модули зависят друг от друга. Цель - **низкая**: изменение одного не ломает другие.
- **Cohesion (сцепление)** - насколько связаны вещи **внутри** модуля. Цель - **высокая**: в модуле лежит то, что меняется вместе.

```
Хорошо:  low coupling + high cohesion
         модули независимы, внутри каждого - связанное по смыслу
Плохо:   high coupling + low cohesion
         всё зависит от всего, а внутри - случайный набор
```

<b class="text-on-semi-light">Почему это центрально</b> - <span class="text-gray">Хорошая архитектура = слабая связанность + сильное сцепление. Это позволяет менять одну часть, не задевая остальные, и понимать модуль, не держа в голове весь проект. Большинство архитектурных решений сводятся к этому балансу.</span>

## Абстракция

Скрыть сложность за понятным интерфейсом. `useUsers()` прячет fetch, кеш, обработку ошибок - снаружи виден простой контракт.

- **Правильный уровень** - абстрагируй то, что меняется или повторяется; не прячь то, что и так просто.
- **Дырявые абстракции (leaky)** - когда детали реализации «протекают» наружу, абстракция не выполняет работу.

> Абстракция - не бесплатна: каждый слой добавляет косвенность. Хорошая абстракция **экономит** больше сложности, чем добавляет.

## SOLID для фронтенда

Принципы ООП ([глава](/content/computer-science)) переносятся на компоненты и модули:

| Принцип | Во фронтенде |
|---------|--------------|
| **SRP** (single responsibility) | компонент/хук делает одно |
| **OCP** (open/closed) | расширяй через props/композицию, не правя внутренности |
| **LSP** (substitution) | компоненты с одним интерфейсом взаимозаменяемы |
| **ISP** (interface segregation) | маленькие props-интерфейсы, не «god-компонент» |
| **DIP** (dependency inversion) | зависишь от абстракций (props, контекст), не от конкретики |

```jsx
// DIP: компонент зависит от абстракции (проп onSearch), а не от конкретного API
function SearchBar({ onSearch }) { ... }  // не знает, откуда данные
```

## DRY, KISS, YAGNI

| Принцип | Смысл |
|---------|-------|
| **DRY** | не повторяйся - выноси общее |
| **KISS** | делай проще - сложность оправдывай |
| **YAGNI** | не строй то, что «может понадобится» |

<b class="text-on-semi-light">Осторожно с DRY</b> - <span class="text-gray">Преждевременная абстракция **хуже** дублирования. Две похожие функции, которые **расходятся** в будущем, лучше держать раздельно, чем втиснуть в одну «универсальную» с флагами. Правило трёх: абстрагируй, когда увидел паттерн **трижды**, а не дважды. «Немного дублирования дешевле неправильной абстракции».</span>

## Границы

Где проводить линии - между модулями, фичами, слоями. Хорошая граница:

- инкапсулирует связанное (high cohesion);
- имеет узкий понятный интерфейс (low coupling);
- меняется по одной причине.

Плохие границы рождают «god-модули» и спагетти-зависимости. О практике границ - в [структуре проекта](/content/architecture/project-structure).

---

## Композиция > наследование

Во фронтенде сложное собирают **композицией** (компоненты из компонентов, хуки из хуков), а не наследованием. Это даёт гибкость без жёсткой иерархии ([паттерны React](/content/reactjs/patterns-and-component-design)).

---

## Поддерживаемость > «умность»

<b class="text-on-semi-light">Финальный принцип</b> - <span class="text-gray">Код читают чаще, чем пишут. Понятная, чуть более многословная архитектура лучше «умной» и плотной. Цель архитектуры - не впечатлить, а **снизить стоимость изменений** в будущем. Если решение нельзя объяснить junior'у за пару минут - возможно, оно слишком сложное.</span>

---

## Сложность: существенная и случайная

Брукс («Мифический человеко-месяц») разделил сложность на два вида:

- **Существенная (essential)** - присуща самой задаче, домен реально сложен. Её не убрать.
- **Случайная (accidental)** - привнесена инструментами, кодом, плохими решениями. Её **можно и нужно** сокращать.

<b class="text-on-semi-light">Цель архитектуры</b> - <span class="text-gray">минимизировать случайную сложность, чтобы силы команды уходили на существенную (бизнес-задачу), а не на борьбу с собственным кодом. Запутанная структура, лишние абстракции, «умный» код - это accidental complexity, налог на каждое изменение.</span>

---

## Когнитивная нагрузка

Связанный критерий - сколько нужно держать в голове, чтобы понять или изменить кусок кода. Хорошая архитектура **снижает когнитивную нагрузку**: локальностью (связанное рядом), узкими интерфейсами, предсказуемостью. Если для правки одной строки надо понять пол-проекта - связанность слишком высока.

---

## Проектирование под изменение

Зрелый принцип - **декомпозиция по волатильности** (volatility-based decomposition): изолируй то, что меняется **вместе** и **часто**, за стабильными интерфейсами. Группируй не по «что это» (UI/логика/данные), а по «как часто и почему меняется». То, что меняется по одной причине, - в одном модуле (это SRP на уровне модулей).

> **Закон Деметры** («не разговаривай с незнакомцами»): модуль знает только ближайших соседей и не лезет вглубь чужих структур (`a.b.c.d`). Это снижает связанность - изменение внутренней структуры не ломает далёких потребителей.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое coupling и cohesion?</b>
<span class="text-gray">Coupling - зависимость модулей друг от друга (нужна низкая), cohesion - связанность внутри модуля (нужна высокая). Хорошая архитектура = слабая связанность + сильное сцепление: меняешь часть, не задевая остальное.</span>

<b class="text-on-semi-light">Что такое разделение ответственности?</b>
<span class="text-gray">Каждая часть отвечает за одно: UI, логика, данные, состояние разделены. Это упрощает понимание, тестирование и изменение каждой части независимо.</span>

<b class="text-on-semi-light">Как SOLID применяется во фронтенде?</b>
<span class="text-gray">SRP - компонент делает одно; OCP - расширение через props/композицию; LSP - взаимозаменяемость по интерфейсу; ISP - маленькие props; DIP - зависимость от абстракций (props/контекст), не конкретики.</span>

<b class="text-on-semi-light">Когда DRY вредит?</b>
<span class="text-gray">Когда абстрагируешь преждевременно: две похожие, но расходящиеся вещи втискиваешь в одну универсальную с флагами. Неправильная абстракция дороже дублирования. Правило трёх: выноси после третьего повторения.</span>

<b class="text-on-semi-light">Почему композиция предпочтительнее наследования?</b>
<span class="text-gray">Композиция даёт гибкость без жёсткой иерархии: сложное собирается из простого через props/children и хуки. Наследование сцепляет и плохо масштабируется в UI.</span>

<b class="text-on-semi-light">Чем существенная сложность отличается от случайной?</b>
<span class="text-gray">Существенная присуща самой задаче (домен сложен), её не убрать. Случайная привнесена кодом, инструментами и решениями - её можно и нужно сокращать. Цель архитектуры - минимизировать случайную, чтобы силы шли на бизнес-задачу.</span>

<b class="text-on-semi-light">Что значит декомпозиция по волатильности?</b>
<span class="text-gray">Группировать код по тому, что меняется вместе и часто, изолируя изменчивое за стабильными интерфейсами, а не по техническому типу (UI/логика/данные). Что меняется по одной причине - в одном модуле.</span>
