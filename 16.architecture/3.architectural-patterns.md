# Архитектурные паттерны

Паттерны уровня приложения — как устроить поток данных и слои: MVC и почему фронтенд от него ушёл, MVP и MVVM, Flux и однонаправленный поток, редьюсеры и Elm-архитектура, компонентная модель, слои, чистая и гексагональная архитектура, CQRS и шина событий, humble object. Спрашивают, почему фронтенд перешёл от MVC к однонаправленному потоку, что такое Flux и когда нужна гексагональная архитектура. Глубже — как двусторонние связи уходят в пинг-понг обновлений, почему редьюсер позволяет «путешествовать во времени» и почему сценарий оформления заказа не должен знать про `fetch`.

::tldr
- **MVC в большом интерфейсе запутывается:** модели и представления обновляют друг друга в обе стороны, и трудно понять, откуда пришло изменение и когда оно остановится.
- **Однонаправленный поток — действие → состояние → представление:** у изменения один путь, порядок понятен, отладка простая. Это Flux, Redux, `useReducer` и сама модель React.
- **Редьюсер — чистая функция от состояния и действия:** одинаковый журнал действий всегда даёт одинаковое состояние, его можно воспроизвести до любого шага.
- **Vue и Angular ближе к MVVM:** реактивное состояние связано с шаблоном, а двусторонняя привязка остаётся локальной — `v-model` у поля.
- **Гексагональная архитектура — бизнес-сценарий в центре, мир через порты:** платёжный шлюз, хранилище и время передаются адаптерами. Полная версия редко нужна фронтенду, а принцип «логика без фреймворка» полезен всегда.
::

## MVC

Сквозной пример — корзина и оформление заказа: количество товаров, сумма, промокод, оплата.

**Model — View — Controller**: модель хранит данные, представление показывает, контроллер связывает их и обрабатывает ввод. Паттерн пришёл из десктопных приложений и серверных фреймворков, где он работает хорошо.

В большом интерфейсе связи становятся двусторонними: модель обновляет представление, представление — модель, модели — друг друга. В проверке две связанные модели — количество пересчитывает сумму, а пересчёт суммы по другому правилу меняет количество — сделали 50 обновлений подряд, пока их не остановили искусственно. В реальном приложении это зацикленные обновления, мерцание и вопрос «кто поменял это значение», на который нет ответа без отладчика. Именно эта боль в больших интерфейсах Facebook породила Flux.

## MVP и MVVM

- **MVP** — представитель содержит логику отображения, представление пассивно и только показывает.
- **MVVM** — модель представления связана с шаблоном: изменение данных обновляет интерфейс, ввод пользователя — данные.

Vue и Angular идейно близки к MVVM: реактивное состояние автоматически связано с шаблоном (подробно — в [Основах реактивности Vue](/content/vuejs/reactivity-fundamentals)). Но двусторонняя привязка в них локальна — `v-model` у поля ввода, — а между компонентами данные идут однонаправленно: пропсы вниз, события вверх.

## Однонаправленный поток

```text
действие → обработка (диспетчер, редьюсер) → новое состояние → представление
   ▲                                                              │
   └────────────────────── пользователь ──────────────────────────┘
```

У изменения **один путь**: представление не меняет состояние напрямую, а отправляет действие. Поэтому всегда понятно, откуда пришло обновление и в каком порядке. Это **Flux** от Facebook, его популярная реализация **Redux** и модель React целиком: состояние сверху, пропсы вниз, изменения — через функции обновления (подробно — во [Введении в React](/content/reactjs/introduction)).

### Редьюсер

```js
const reducer = (state, action) => {
  switch (action.type) {
    case 'add': return { ...state, items: [...state.items, action.item] };
    case 'remove': return { ...state, items: state.items.filter((i) => i.id !== action.id) };
    case 'promo': return { ...state, promo: action.code };
    default: return state;
  }
};

const final = log.reduce(reducer, initial);
```

В проверке журнал из четырёх действий — добавить пуэр, добавить улун, применить промокод, убрать улун — дал сумму 1080. Повторный прогон того же журнала дал то же состояние, а журнал до третьего шага — 1800: состояние в любой момент можно восстановить. На этом строятся отладка с «путешествием во времени» в Redux DevTools, воспроизведение ошибок по журналу действий и тесты редьюсера без интерфейса. Исходное состояние при этом не изменилось — редьюсер возвращает новое.

### Семейство

- **The Elm Architecture** — модель, представление, обновление; строгая версия однонаправленного потока, вдохновившая Redux;
- **`useReducer`** и **Zustand с действиями** — тот же принцип в меньшем масштабе;
- **автоматы состояний** — XState: действия меняют состояние только по разрешённым переходам (подробно — в [Состоянии и данных](/content/architecture/state-and-data-architecture)).

## Компонентная модель

Современный фронтенд делит приложение не на слои MVC, а на **дерево компонентов**: каждый со своим отображением, локальным состоянием и поведением. Логику выносят в хуки и composables, данные — в слой данных.

```text
App
├── Header
│   └── CartBadge
├── Catalog
│   └── ProductCard
└── Checkout
```

Как проводить границы компонентов и проектировать их API — в [Архитектуре компонентов](/content/architecture/component-architecture).

## Слои

Независимо от фреймворка приложение полезно мыслить слоями:

```text
отображение     компоненты, страницы
     ↓
сценарии        оформить заказ, применить промокод — правила и порядок шагов
     ↓
данные          API-клиент, кеш, хранилище
```

Верхние слои зависят от нижних, а не наоборот. Это разделение ответственности из [Архитектурного мышления](/content/architecture/architectural-thinking) на уровне приложения.

### Чистая и гексагональная архитектура

Шаг дальше — **сценарии в центре**, а всё внешнее — фреймворк, API, хранилище, время — на краях, за **портами**. Зависимости направлены внутрь: сценарий не знает ни про React, ни про `fetch`.

```js
// сценарий: никаких импортов, мир приходит параметрами
async function placeOrder({ cart, payments, orders, clock }) {
  if (cart.items.length === 0) throw new Error('Корзина пуста');
  const amount = cart.items.reduce((s, i) => s + i.price * i.qty, 0);
  const payment = await payments.charge(amount);
  if (!payment.ok) return { status: 'declined' };
  const order = await orders.save({ items: cart.items, amount, paidAt: clock() });
  return { status: 'paid', orderId: order.id, amount };
}
```

В проверке один и тот же сценарий отработал с адаптерами в памяти — в тесте — и с HTTP-адаптерами к настоящему серверу: `paid`, заказ, сумма 2400. Отклонённая оплата вернула `declined` и не дошла до сохранения заказа. В коде сценария нет `fetch`, `localStorage` и React — его можно перенести на сервер, в воркер или в другой фреймворк без изменений.

Цена — больше слоёв и косвенности. Полная чистая архитектура оправдана в больших долгоживущих приложениях со сложными правилами: банковские интерфейсы, конструкторы, офлайн-приложения. Для типичного интерфейса над API она избыточна, но **принцип** — бизнес-правила отдельно от фреймворка — полезен везде.

## CQRS и события

- **CQRS** — разделение команд, которые меняют состояние, и запросов, которые читают. Во фронтенде это мутации и запросы в библиотеках серверного состояния: мутация меняет данные на сервере и помечает запросы устаревшими (подробно — в [Состоянии и данных](/content/ecosystem-libs/state-and-data-libraries)).
- **Шина событий** — модули общаются событиями, не зная друг о друге: аналитика, уведомления, связь микрофронтендов.

У шины своя ловушка — забытая отписка. В проверке два виджета подписались на `cart:changed`, а при «размонтировании» отписался только тот, кто передал `signal` от `AbortController`. Второй продолжил получать события — утечка и лишняя работа:

```js
const controller = new AbortController();
bus.addEventListener('cart:changed', onChange, { signal: controller.signal });
// при размонтировании
controller.abort();
```

Шиной заменяют прямые связи там, где модули действительно независимы. Для данных внутри приложения однонаправленный поток прозрачнее: в шине трудно понять, кто и почему отправил событие.

## Humble object

Паттерн тестируемости: вся логика — в обычных функциях и сценариях, а компонент, связанный с фреймворком и DOM, — тонкая «скромная» оболочка, которая только вызывает их и показывает результат. Логику проверяют модульными тестами без рендера, оболочку — немногими интеграционными. Это и есть сценарий `placeOrder` выше: компонент кнопки «Оплатить» лишь вызывает его с настоящими адаптерами.

## Как устроено на практике

Большинство фронтенд-приложений сегодня:

```text
компонентная модель + однонаправленный поток + слой серверного состояния
```

Полная чистая архитектура встречается редко, но её принципы — слои, направление зависимостей, сценарии без фреймворка — применяют дозированно, там, где правила сложные и живут долго. Задача не «внедрить паттерн», а убрать конкретную проблему связанности или масштаба.

---

## Красные флаги в ответе

- **«Сделаем двустороннюю привязку между всеми моделями».** Обновления начнут гонять друг друга по кругу.
- **«Компонент сам поменяет общее состояние, так быстрее».** У изменения появляется второй путь, отладка ломается.
- **«Редьюсер может изменить состояние на месте».** Тогда журнал не воспроизводит историю, а сравнение ссылок не видит изменений.
- **«Введём чистую архитектуру с пятью слоями для лендинга».** Косвенность не окупится.
- **«Сценарий оформления сам вызовет `fetch`».** Он станет нетестируемым без моков и непереносимым.
- **«Шина событий решит все связи».** Без отписки — утечки, а поток данных становится непрозрачным.

## Как спрашивают на собеседовании

::question
Почему фронтенд ушёл от MVC к однонаправленному потоку?

#answer
В большом интерфейсе связи MVC становятся двусторонними: модели и представления обновляют друг друга, обновления ходят по кругу, и неясно, откуда пришло изменение. Однонаправленный поток — действие, новое состояние, представление — даёт один путь изменения и предсказуемый порядок.

#more
Это ответ Facebook на сложность больших интерфейсов — Flux, — и основа React и Redux. Vue сохраняет локальную двустороннюю привязку для полей, но между компонентами данные тоже идут однонаправленно.
::

::question
Что такое Flux и как он связан с Redux?

#answer
Flux — паттерн однонаправленного потока: действие → диспетчер → хранилище → представление. Redux — его упрощённая реализация, где хранилище одно, а состояние меняет чистая функция-редьюсер.

#more
Редьюсер детерминирован: одинаковый журнал действий даёт одинаковое состояние, поэтому возможны воспроизведение ошибок и отладка с «путешествием во времени». Похожие идеи — Elm-архитектура и `useReducer`.
::

::question
К какому паттерну близки Vue и Angular?

#answer
К MVVM: реактивное состояние связано с шаблоном, изменение данных обновляет интерфейс, а ввод — данные.

#more
Двусторонняя привязка в них локальна — `v-model` или `[(ngModel)]` у поля, — а между компонентами данные идут пропсами вниз и событиями вверх, то есть однонаправленно.
::

::question
Что такое чистая или гексагональная архитектура и когда она нужна?

#answer
Бизнес-сценарии в центре, а фреймворк, API, хранилище и время — на краях, за портами, через заменяемые адаптеры. Зависимости направлены внутрь: сценарий не знает ни про React, ни про `fetch`.

#more
Это даёт тестирование без моков и перенос логики между фреймворками и средами. Цена — слои и косвенность, поэтому полную версию применяют в больших долгоживущих приложениях со сложными правилами, а для обычного интерфейса берут только принцип.
::

::question
Как устроено большинство современных фронтенд-приложений?

#answer
Компонентная модель, однонаправленный поток данных и слой серверного состояния — библиотека загрузки и кеша. Бизнес-правила выносят в функции и хуки, а сложные процессы — в автоматы состояний.

#more
Полная чистая архитектура встречается редко; её принципы применяют там, где правила сложные. Выбор паттерна — ответ на конкретную проблему, а не цель.
::

## Практика

::practice{title="Сумма и количество меняют друг друга"}
В корзине поле количества и поле суммы связаны двусторонне: меняешь количество — пересчитывается сумма, меняешь сумму — пересчитывается количество по цене со скидкой. Иногда страница зависает, а значения скачут.

#solution
Две модели обновляют друг друга, и при неудачном округлении обновления не останавливаются. В проверке такая пара сделала 50 обновлений подряд. Исправление — один источник истины и производное значение:

```js
const reducer = (state, action) => {
  switch (action.type) {
    case 'setQty': return { ...state, qty: Math.max(1, action.qty) };
    default: return state;
  }
};

const total = (state) => state.qty * state.price * (state.qty >= 10 ? 0.9 : 1);   // производное, не хранится
```

Количество — состояние, сумма вычисляется. Если нужно ввести сумму, это отдельное действие, которое вычисляет количество один раз, а не подписка в обратную сторону.
::

::practice{title="Оформление заказа нельзя протестировать"}
Компонент кнопки «Оплатить» сам вызывает `fetch` к платёжному шлюзу, пишет заказ в API и читает `Date.now()`. Тест требует мокать `fetch`, время и модули, и всё равно ломается при каждом изменении вёрстки.

#solution
Логику выносят в сценарий, а мир передают адаптерами:

```js
// сценарий — чистый и переносимый
export async function placeOrder({ cart, payments, orders, clock }) { /* … */ }

// компонент — тонкая оболочка
function PayButton({ cart }) {
  const run = () => placeOrder({ cart, payments: httpPayments, orders: httpOrders, clock: () => new Date().toISOString() });
  return <button onClick={run}>Оплатить</button>;
}

// тест — адаптеры в памяти
await placeOrder({ cart, payments: { charge: async () => ({ ok: true }) }, orders: memoryOrders, clock: () => '2026-11-15' });
```

В проверке сценарий прошёл и с адаптерами в памяти, и с HTTP-адаптерами к настоящему серверу, а отклонённая оплата не дошла до сохранения заказа. Компонент теперь проверяют одним интеграционным тестом, а правила — быстрыми модульными.
::
