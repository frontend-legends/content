# Архитектурные паттерны

Паттерны уровня **приложения** - как организовать поток данных и слои. Это не GoF-паттерны ([ООП](/content/computer-science), [паттерны JS](/content/javascript)), а способы устроить приложение целиком: MVC, MVVM, Flux, слоистая и clean-архитектура. Понимать их эволюцию - значит понимать, **почему** современный фронтенд устроен так, как устроен.

---

## MVC

**Model-View-Controller** - классика: модель (данные), представление (UI), контроллер (логика, связывает их). Пришёл из десктопа/бэкенда.

```
Controller ↔ Model
     ↕
   View
```

<b class="text-on-semi-light">Проблема MVC во фронтенде</b> - <span class="text-gray">При росте приложения связи между View, Model и Controller становятся **двусторонними и запутанными** - изменение в одном месте каскадом тянет другие, и трудно отследить, откуда пришло обновление. Именно эта боль (в больших UI Facebook) породила Flux.</span>

---

## MVP и MVVM

- **MVP** (Model-View-Presenter) - presenter содержит логику представления, view пассивна.
- **MVVM** (Model-View-ViewModel) - **двусторонняя привязка** между View и ViewModel: меняется модель - обновляется UI, и наоборот.

Vue и Angular идейно близки к **MVVM** - реактивные данные автоматически связаны с шаблоном ([реактивность Vue](/content/vuejs/reactivity-fundamentals)).

---

## Flux и однонаправленный поток

Ответ Facebook на хаос MVC: данные текут **в одну сторону**.

```
Action → Dispatcher → Store → View
   ▲                            │
   └──────── (новый action) ────┘
```

<b class="text-on-semi-light">Почему однонаправленность победила</b> - <span class="text-gray">В Flux изменение всегда идёт по одному маршруту: действие → стор → представление. Нет двусторонних связей, поэтому **всегда понятно, откуда пришло обновление** и в каком порядке. Это предсказуемо и отлаживаемо. **Redux** - реализация Flux; вся модель React построена на однонаправленном потоке ([введение в React](/content/reactjs/introduction)).</span>

> Сдвиг от MVC (двусторонние связи) к Flux (однонаправленный поток) - ключевая эволюция фронтенд-архитектуры. Современные фреймворки наследуют именно эту идею.

---

## Компонентная архитектура

Современный дефолт (React, Vue) - не слои MVC, а **дерево компонентов**. UI = композиция самодостаточных компонентов, каждый со своим состоянием, представлением и поведением.

```
App
├── Header
├── ProductList
│   └── ProductCard
└── Cart
```

Логика делится не на «контроллеры/модели», а на компоненты, хуки/composables и слой данных. Подробнее - в [архитектуре компонентов](/content/architecture/component-architecture).

---

## Слоистая архитектура

Независимо от фреймворка, приложение полезно мыслить **слоями**:

```
Presentation (UI, компоненты)
      ↓
Business logic (правила, сценарии)
      ↓
Data access (API, кеш, хранилище)
```

Верхние слои зависят от нижних, не наоборот. Это разделение ответственности из [архитектурного мышления](/content/architecture/architectural-thinking) на уровне приложения.

---

## Clean / Hexagonal архитектура

Продвинутый подход: в **центре** - бизнес-логика (домен), на **краях** - фреймворк, UI, API. Зависимости направлены **внутрь** - домен не знает про React или конкретный API.

```
        ┌─────────────────────┐
        │   Домен (логика)     │  ← не знает про React/API
        └──────────┬──────────┘
     адаптеры:  UI │ API │ хранилище  ← заменяемы
```

<b class="text-on-semi-light">Зачем и когда</b> - <span class="text-gray">Hexagonal (Ports & Adapters) держит бизнес-логику **независимой от фреймворка**: можно сменить React на другой UI или REST на GraphQL, не трогая ядро. Цена - много слоёв и косвенности. Оправдано в **больших, долгоживущих** приложениях со сложной логикой; для типичного фронтенда - оверкилл. Но **принцип** (логика отдельно от фреймворка) полезен везде.</span>

---

## Современная реальность

Большинство фронтенд-приложений 2026 - это:

```
компонентная архитектура + однонаправленный поток + слой данных (server-state)
```

Полная clean-архитектура встречается редко, но её **принципы** (разделение слоёв, независимость логики, направление зависимостей) применяют дозированно. Главное - не «внедрить паттерн», а решить реальные проблемы связанности и масштаба.

---

## Производные паттерны потока

Однонаправленный поток породил семейство паттернов:

- **Reducer-паттерн** - состояние меняется чистой функцией `(state, action) => state` (Redux, `useReducer`): предсказуемо, тестируемо, дружит с time-travel.
- **The Elm Architecture (MVU)** - Model-View-Update: строгая версия однонаправленности, вдохновившая Redux.
- **CQRS** - разделение **команд** (меняют состояние) и **запросов** (читают). Во фронтенде - разделение мутаций и чтений в data-слое (mutations vs queries в React Query).
- **Event-driven / pub-sub** - модули общаются событиями через шину, не зная друг о друге: слабая связанность для кросс-модульного взаимодействия (аналитика, уведомления).

---

## Humble Object

Паттерн тестируемости: вынеси **всю логику** из трудно-тестируемого слоя (компонент, привязанный к фреймворку/DOM) в обычные функции, оставив в компоненте «скромную» тонкую оболочку. Логику покрываешь юнит-тестами без рендера.

<b class="text-on-semi-light">Связь с архитектурой</b> - <span class="text-gray">Это и есть основа «логика вне компонентов» из [состояния и данных](/content/architecture/state-and-data-architecture): чем тоньше оболочка, привязанная к React, тем больше кода тестируется быстро и тем легче сменить фреймворк.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему фронтенд ушёл от MVC к однонаправленному потоку?</b>
<span class="text-gray">В MVC двусторонние связи между View/Model/Controller на масштабе запутываются - неясно, откуда пришло обновление. Flux/однонаправленный поток (action → store → view) делает поток данных предсказуемым и отлаживаемым.</span>

<b class="text-on-semi-light">Что такое Flux и как связан с Redux?</b>
<span class="text-gray">Flux - паттерн однонаправленного потока данных (Action → Dispatcher → Store → View). Redux - его популярная реализация. Модель React построена на этой однонаправленности.</span>

<b class="text-on-semi-light">К какому паттерну близки Vue/Angular?</b>
<span class="text-gray">К MVVM: реактивная ViewModel двусторонне связана с шаблоном - изменение данных обновляет UI автоматически.</span>

<b class="text-on-semi-light">Что такое clean/hexagonal архитектура и когда она нужна?</b>
<span class="text-gray">Бизнес-логика в центре, фреймворк/UI/API - заменяемые адаптеры по краям, зависимости направлены внутрь. Держит логику независимой от фреймворка. Оправдана для больших долгоживущих приложений; для обычного фронта избыточна, но принцип полезен.</span>

<b class="text-on-semi-light">Как устроено большинство современных фронтенд-приложений?</b>
<span class="text-gray">Компонентная архитектура + однонаправленный поток данных + слой данных (server-state). Полная clean-архитектура редка, её принципы применяют дозированно по необходимости.</span>
