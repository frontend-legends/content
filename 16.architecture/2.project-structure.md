# Структура проекта

Как разложить файлы, чтобы проект оставался понятным при росте? Плоская куча компонентов превращается в хаос, а правильная структура - это **навигация и границы**. Вопрос «как ты организуешь большой проект» - частый на архитектурных собесах.

---

## Два подхода

### По типам (layer-based)

Папки по **роли** файла:

```
src/
├── components/   # все компоненты
├── hooks/        # все хуки
├── services/     # все API
└── utils/
```

Просто на старте, но фича «корзина» **размазана** по всем папкам: компонент в `components/`, хук в `hooks/`, API в `services/`. На масштабе тяжело найти всё, что относится к одной фиче.

### По фичам (feature-based)

Папки по **домену/фиче**:

```
src/
├── features/
│   ├── cart/      # всё про корзину: компоненты, хуки, api, типы
│   ├── auth/
│   └── search/
└── shared/        # переиспользуемое между фичами
```

<b class="text-on-semi-light">Почему feature-based масштабируется</b> - <span class="text-gray">Всё, что относится к фиче, лежит **рядом** (колокация). Чтобы понять/изменить/удалить корзину, идёшь в одну папку, а не охотишься по всему проекту. Структура «кричит» о том, **что делает приложение** (домены), а не на каком фреймворке написано. На больших проектах это решающе.</span>

---

## Колокация

Базовый принцип: **держи связанное близко**. Компонент, его тест, стили, локальный хук - в одной папке.

```
Button/
├── Button.tsx
├── Button.test.tsx
├── Button.module.css
└── index.ts
```

Чем ближе файлы, которые меняются вместе, тем меньше прыжков по дереву и тем легче удалять/переносить.

---

## Feature-Sliced Design

Популярная методология структуры (особенно в русскоязычном сообществе) - **FSD**. Делит проект на **слои** с правилами импорта:

```
app/       # инициализация, провайдеры, роутинг
pages/      # страницы (композиция из нижних слоёв)
widgets/    # самостоятельные блоки UI
features/   # действия пользователя (фичи)
entities/   # бизнес-сущности (user, product)
shared/     # переиспользуемое: ui-kit, утилиты, api
```

<b class="text-on-semi-light">Главное правило FSD</b> - <span class="text-gray">Слои импортируют **только вниз**: `pages` могут использовать `features`/`entities`/`shared`, но не наоборот, и слои одного уровня **не импортируют друг друга** напрямую. Это задаёт строгое направление зависимостей и предотвращает спагетти. FSD - не единственный путь, но хороший пример того, как формализуют границы.</span>

## Границы модулей

У фичи должен быть **публичный API** - то, что разрешено импортировать снаружи. Остальное - внутреннее.

```ts
// features/cart/index.ts - публичный интерфейс фичи
export { CartButton } from './ui/CartButton';
export { useCart } from './model/useCart';
// внутренние файлы наружу не торчат
```

Правило: **не импортируй внутренности чужой фичи**. Только через её публичный `index`. Это держит связанность низкой - можно менять внутренности фичи, не ломая других.

---

## Barrel-файлы

`index.ts`, реэкспортирующий содержимое модуля (как выше), - **barrel**.

- **Плюс:** чистые импорты (`import { useCart } from '@/features/cart'`), явный публичный API.
- **Минус:** могут мешать tree-shaking, провоцировать **циклические зависимости** и замедлять сборку, если злоупотреблять.

> Используй barrel для **публичного API модуля**, но не оборачивай в них всё подряд - особенно большие пакеты, где это бьёт по бандлу.

---

## Направление зависимостей

Ключевая идея независимо от методологии: зависимости должны идти в **одну сторону** и не образовывать циклов.

```
shared ← features ← pages ← app
(стрелка = «можно импортировать»; назад - нельзя)
```

`shared` ничего не знает о фичах; фичи не знают друг о друге. Это и есть низкая связанность из [архитектурного мышления](/content/architecture/architectural-thinking) на уровне файлов.

---

## Когда менять структуру

Структура - не догма. Начинай просто (layer-based ок для маленького), переходи к feature-based, когда фич становится много и они «размазываются». Рефактори, когда стало трудно **находить** и **удалять** код, а не ради красоты.

---

## Принуждение границ инструментами

Границы, держащиеся «на договорённости», разъезжаются. На масштабе их **автоматизируют**:

- **Правила импортов ESLint** (`no-restricted-imports`, `eslint-plugin-boundaries`, `@feature-sliced/steiger`) - запрет импортировать внутренности чужих фич или вверх по слоям.
- **dependency-cruiser** / **madge** - визуализация графа зависимостей и **поиск циклов**.
- Проверка в [CI](/content/advanced-tooling/ci-cd) - нарушение границы валит сборку.

<b class="text-on-semi-light">Почему это senior-практика</b> - <span class="text-gray">Одни код-ревью не удержат архитектуру на масштабе - кто-нибудь импортирует напрямую «чтобы быстро». Линтер границ делает правильное лёгким, а неправильное - невозможным. Архитектура, не закреплённая инструментами, деградирует.</span>

---

## Вертикальные срезы

Feature-based - частный случай идеи **вертикальных срезов**: фича пронизывает все технические слои (UI → логика → данные) и живёт как единое целое, вместо горизонтального деления на слои. Это упрощает удаление фичи (удалил папку), тестирование и владение командой (команда владеет вертикалью end-to-end) - что прямо связано с [законом Конвея](/content/architecture/scalability-and-teams).

## Вопросы на собеседовании

<b class="text-on-semi-light">Layer-based или feature-based структура?</b>
<span class="text-gray">Layer-based (по типам) проста для малых проектов, но размазывает фичу по папкам. Feature-based (по доменам) держит всё про фичу рядом (колокация) и лучше масштабируется - структура отражает, что делает приложение.</span>

<b class="text-on-semi-light">Что такое колокация и зачем она?</b>
<span class="text-gray">Держать связанное близко: компонент, тест, стили, локальный хук в одной папке. Меньше прыжков по дереву, легче понимать, переносить и удалять код.</span>

<b class="text-on-semi-light">Как задать границы между фичами?</b>
<span class="text-gray">У фичи есть публичный API (index/barrel) - наружу торчит только он. Импортировать внутренности чужой фичи нельзя; зависимости идут в одну сторону без циклов. Так связанность остаётся низкой.</span>

<b class="text-on-semi-light">Что такое Feature-Sliced Design?</b>
<span class="text-gray">Методология структуры со слоями (app/pages/widgets/features/entities/shared) и правилом импорта только вниз; слои одного уровня не зависят друг от друга. Формализует направление зависимостей.</span>

<b class="text-on-semi-light">Плюсы и минусы barrel-файлов?</b>
<span class="text-gray">Плюс - чистые импорты и явный публичный API. Минус - могут мешать tree-shaking, провоцировать циклические зависимости и замедлять сборку. Использовать для публичного API модуля, не для всего подряд.</span>
