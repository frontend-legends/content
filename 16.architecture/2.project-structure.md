# Структура проекта

Как разложить код, чтобы проект оставался понятным при росте: структура по типам и по фичам, колокация, Feature-Sliced Design, публичный API модуля, barrel-файлы и их цена, направление зависимостей, проверка границ инструментами и вертикальные срезы. Спрашивают, как организовать большой проект, что такое колокация и как задать границы между фичами. Глубже — почему одна кнопка из `shared/ui` загружает в dev-сервере пятьдесят модулей, откуда `Cannot access before initialization` и как сделать, чтобы нарушение границы роняло CI.

::tldr
- **По типам — просто на старте, по фичам — масштабируется:** в структуре по фичам всё про корзину лежит в одной папке, её можно понять, перенести и удалить целиком.
- **Колокация:** то, что меняется вместе, лежит рядом — компонент, тест, стили, хук.
- **У модуля есть публичный API:** снаружи импортируют только его `index`, внутренности — нет. Слои импортируют только вниз, фичи не знают друг о друге.
- **Barrel-файлы — для публичного API, а не для всего подряд:** в dev-сервере импорт одной кнопки через barrel загружает все реэкспортированные модули, а импорт своей же фичи через её barrel создаёт цикл.
- **Границы проверяют инструменты, а не договорённости:** правила dependency-cruiser, ESLint или Steiger роняют проверку при импорте чужих внутренностей или вверх по слоям.
::

---

## По типам и по фичам

Сквозной пример — магазин: каталог, корзина, оформление заказа, общий UI-кит.

### По типам

```text
src/
  components/   все компоненты
  hooks/        все хуки
  api/          все запросы
  utils/
```

Просто на старте, но корзина размазана по всем папкам: компонент в `components/`, хук в `hooks/`, запросы в `api/`. Чтобы изменить или удалить её, нужно пройти по всему дереву.

### По фичам

```text
src/
  features/
    cart/        всё про корзину: компоненты, хуки, запросы, типы, тесты
    checkout/
    catalog/
  shared/        переиспользуемое: UI-кит, форматирование, API-клиент
  app/           маршруты, провайдеры, инициализация
```

Структура показывает, **что делает приложение**, а не на каком фреймворке написано, — Роберт Мартин называл это «кричащей архитектурой». Начинать можно со структуры по типам и переходить к фичам, когда находить и удалять код становится трудно.

### Колокация

```text
CartBadge/
  CartBadge.tsx
  CartBadge.test.tsx
  CartBadge.module.css
  useCartCount.ts
```

Чем ближе файлы, которые меняются вместе, тем меньше переходов по дереву и тем проще удалить фичу: удалил папку — и не осталось хвостов.

## Feature-Sliced Design

Популярная методология, особенно в русскоязычном сообществе, — **FSD**. Она делит проект на слои с правилами импорта:

```text
app        инициализация, провайдеры, маршрутизация
pages      страницы — композиция нижних слоёв
widgets    самостоятельные блоки интерфейса
features   действия пользователя: добавить в корзину, применить промокод
entities   бизнес-сущности: товар, пользователь, заказ
shared     UI-кит, утилиты, API-клиент
```

Главное правило — **импорт только вниз**: страница может использовать фичи и сущности, но не наоборот, а модули одного слоя не импортируют друг друга. Внутри каждого слоя модуль делится на сегменты — `ui`, `model`, `api`, `lib` — и наружу отдаёт публичный API. FSD — не единственный путь, но хороший пример того, как формализуют направление зависимостей.

---

## Публичный API модуля

```ts
// features/cart/index.ts — то, что можно импортировать снаружи
export { CartButton } from './ui/CartButton';
export { useCart } from './model/useCart';
```

Правило: **чужой модуль — только через его `index`**. Тогда внутренности фичи можно переписать, не трогая других. Это низкая связанность из [Архитектурного мышления](/content/architecture/architectural-thinking) на уровне файлов. Для пакетов в монорепозитории то же самое делает поле `exports` в `package.json` (подробно — в [Модульных системах](/content/advanced-tooling/module-systems)).

## Barrel-файлы

`index.js`, который реэкспортирует содержимое модуля, — **barrel**. Он даёт короткие импорты и явный публичный API, но у него есть цена.

### Dev-сервер загружает всё

В проверке UI-кит из 50 компонентов и кнопки отдавался через общий barrel. В dev-сервере Vite импорт одной кнопки через `shared/ui/index.js` загрузил **52 модуля** — сам barrel и всё, что он реэкспортирует. Прямой импорт `shared/ui/Button.js` — **один**. На большом проекте это сотни лишних запросов при каждой перезагрузке и медленный старт страницы в разработке. В продакшен-сборке tree shaking обычно убирает лишнее, если модули без побочных эффектов (подробно — в [Оптимизации](/content/advanced-tooling/optimization)), но и сборка тратит время на разбор всех файлов.

### Циклы через собственный barrel

В проверке компонент `CartBadge` внутри фичи корзины импортировал форматирование через `../index.js` — barrel своей же фичи:

```text
main.js → cart/index.js → ui/CartBadge.js → cart/index.js   (цикл)
```

Загрузка упала с `ReferenceError: Cannot access 'formatCount' before initialization`: модуль `CartBadge` выполнился раньше, чем barrel успел экспортировать `formatCount`. После замены на прямой импорт `../model/format.js` всё заработало.

Правила:

- barrel — для **публичного API** модуля, внутри модуля — прямые импорты;
- не делать barrel на весь UI-кит или все утилиты, если их импортируют по одной;
- в библиотеках — точки входа через `exports` и отдельные подпути вместо одного огромного `index`.

## Направление зависимостей

```text
shared ← entities ← features ← widgets ← pages ← app
стрелка — «можно импортировать», в обратную сторону нельзя
```

`shared` ничего не знает о фичах, сущности — о действиях пользователя, фичи — друг о друге. Если двум фичам нужно общее, это общее опускается слоем ниже, а связь между ними собирается на уровне выше — в виджете или странице.

## Границы проверяют инструменты

Границы, которые держатся на договорённости, расползаются: кто-нибудь импортирует внутренности «чтобы быстро». На масштабе их автоматизируют.

В проверке dependency-cruiser с тремя правилами — только публичный API чужой фичи, `entities` и `shared` не импортируют `features`, никаких циклов — пропустил правильный проект. После двух «быстрых» правок он упал:

```text
error feature-internals: src/features/checkout/index.js → src/features/cart/model/add.js
error no-upward: src/entities/product/index.js → src/features/cart/index.js
```

Инструменты:

- **dependency-cruiser** — правила, поиск циклов, граф зависимостей;
- **ESLint** — `no-restricted-imports`, `eslint-plugin-boundaries`, `import/no-cycle`;
- **Steiger** — линтер методологии FSD;
- **оркестраторы монорепо** — Nx и Turborepo с правилами между пакетами (подробно — в [Монорепозиториях](/content/advanced-tooling/monorepo-tooling)).

Проверка в CI делает правильное лёгким, а нарушение — видимым до слияния (подробно — в [CI/CD](/content/advanced-tooling/ci-cd)).

## Вертикальные срезы

Структура по фичам — частный случай **вертикальных срезов**: фича проходит через все технические слои — интерфейс, логика, данные — и живёт целиком в одном месте. Это упрощает удаление фичи, тестирование и владение: команда отвечает за вертикаль целиком, а не за слой «все компоненты» (подробно — в [Масштабировании и командах](/content/architecture/scalability-and-teams)).

---

## Красные флаги в ответе

- **«Положу все компоненты в `components/`».** На масштабе фича размазывается по проекту.
- **«Импортирую файл из чужой фичи напрямую, так быстрее».** Связанность растёт, внутренности нельзя менять.
- **«Сделаю barrel на весь UI-кит».** В разработке каждый импорт тянет все компоненты.
- **«Внутри фичи импортирую через её же index».** Это цикл и ошибка инициализации.
- **«Границы держим на ревью».** Без проверки инструментами они расползаются.
- **«Переложим всё по FSD за неделю».** Структуру меняют постепенно, когда текущая мешает находить и удалять код.

## Как спрашивают на собеседовании

::question
Структура по типам или по фичам?

#answer
По типам — `components`, `hooks`, `api` — проще на старте, но фича размазывается по папкам. По фичам — всё про корзину в одной папке — лучше масштабируется: фичу проще понять, изменить и удалить, а структура показывает, что делает приложение.

#more
Обычно сочетают: фичи плюс `shared` для переиспользуемого и `app` для инициализации. Переходят, когда находить и удалять код стало трудно, а не ради красоты.
::

::question
Что такое колокация и зачем она?

#answer
Держать рядом то, что меняется вместе: компонент, его тест, стили и локальный хук в одной папке. Меньше переходов по дереву, проще перенос и удаление.

#more
Колокация работает на всех уровнях: файлы компонента, модули фичи, данные рядом с местом использования (подробно о состоянии — в истории про данные).
::

::question
Как задать границы между фичами?

#answer
У каждой фичи есть публичный API — `index`, через который её импортируют снаружи; внутренности чужой фичи не импортируют. Зависимости идут в одну сторону, без циклов, а общее опускается в нижний слой.

#more
Правила проверяют инструментами — dependency-cruiser, ESLint с `boundaries`, Steiger для FSD, — и проверка в CI роняет сборку при нарушении.
::

::question
Что такое Feature-Sliced Design?

#answer
Методология структуры со слоями `app`, `pages`, `widgets`, `features`, `entities`, `shared` и правилом импорта только вниз; модули одного слоя не импортируют друг друга. Внутри модуля — сегменты `ui`, `model`, `api`, `lib` и публичный API.

#more
Это формализация направления зависимостей. Методологию проверяет линтер Steiger; на маленьком проекте она может быть избыточной.
::

::question
Плюсы и минусы barrel-файлов?

#answer
Плюсы — короткие импорты и явный публичный API модуля. Минусы — в dev-сервере импорт одного элемента загружает всё, что реэкспортирует barrel, а импорт своей же фичи через её barrel создаёт цикл и ошибку инициализации.

#more
Barrel оставляют для публичного API фичи, а внутри модуля импортируют напрямую. Огромные barrel на весь UI-кит заменяют прямыми путями или подпутями в `exports`.
::

## Практика

::practice{title="Медленная разработка из-за UI-кита"}
После обновления страницы в разработке браузер делает сотни запросов, хотя на странице три компонента. Все компоненты импортируются из `@/shared/ui`.

#solution
`@/shared/ui/index.ts` реэкспортирует весь UI-кит, и dev-сервер загружает каждый модуль, на который ссылается barrel. В проверке одна кнопка через barrel потянула 52 модуля, прямой импорт — один.

```ts
// было
import { Button } from '@/shared/ui';

// стало
import { Button } from '@/shared/ui/button';
```

```json
{
  "exports": {
    "./button": "./src/button/index.ts",
    "./dialog": "./src/dialog/index.ts"
  }
}
```

Если UI-кит — пакет монорепо, подпути в `exports` делают прямые импорты единственно возможными. Правило ESLint `no-restricted-imports` запрещает импорт из корня `@/shared/ui`.
::

::practice{title="Cannot access before initialization"}
После рефакторинга корзины приложение падает при загрузке: `ReferenceError: Cannot access 'formatCount' before initialization`. Внутри фичи все импорты переписали на `@/features/cart`.

#solution
Модули внутри фичи импортируют её собственный barrel, а barrel импортирует их — цикл. Модуль выполняется раньше, чем barrel успел экспортировать нужное. В проверке ровно так упал `CartBadge`, а прямой импорт `../model/format.js` это исправил.

```ts
// внутри features/cart — прямые относительные импорты
import { formatCount } from '../model/format';

// снаружи — только публичный API
import { CartBadge } from '@/features/cart';
```

Чтобы не повторилось, в CI добавляют правило против циклов:

```json
{ "forbidden": [{ "name": "no-cycles", "severity": "error", "from": {}, "to": { "circular": true } }] }
```
::
