# Архитектура компонентов

Как организовать сотни компонентов в большом приложении: уровни от примитивов до страниц, Atomic Design, дизайн-системы и токены, контейнеры и представления, API компонента, переиспользование против специфичности, когда делить компонент, общая библиотека и инверсия управления. Спрашивают, как организовать компоненты, что такое контейнер и презентационный компонент и когда выносить компонент в общий. Глубже — как одно значение токена перекрашивает всё приложение и как дать родителю изменить правило компонента, не добавляя ему новый флаг.

::tldr
- **Уровни абстракции:** примитивы без бизнес-логики — кнопка, поле, диалог — внизу, составные компоненты выше, компоненты фич с данными и страницы — наверху. Кнопка, которая сама ходит в API, не переиспользуется.
- **Дизайн-система — токены, компоненты и документация:** цвета, отступы и радиусы — переменными, компоненты — на них, каталог — в Storybook. Одно изменение токена меняет весь интерфейс.
- **Данные отдельно от отображения:** логика и загрузка — в хуках и контейнерах, отображение — в компонентах, которые получают всё пропсами и легко тестируются.
- **Хороший API компонента — минимум обязательных пропсов, композиция через `children` и слоты** вместо десятка булевых флагов.
- **Инверсия управления:** управляемый режим, `stateReducer`, prop getters и headless-компоненты отдают решения родителю — один компонент покрывает разные случаи без раздувания API.
::

## Уровни

Сквозной пример — интерфейс магазина: кнопки и поля UI-кита, карточка товара, виджет корзины, страница каталога.

```text
примитивы       Button, Input, Dialog, Stepper  — без бизнес-логики, только UI и доступность
     ↓
составные       SearchField, ProductCard        — собраны из примитивов, данные пропсами
     ↓
компоненты фич  CartWidget, CheckoutForm        — свои данные, правила, запросы
     ↓
страницы        CatalogPage                      — композиция всего выше
```

Примитивы ничего не знают о домене и переиспользуются везде; компоненты фич содержат логику и данные. Смешивание уровней — главная причина непереиспользуемых компонентов: `Button` с зашитым запросом к корзине нельзя поставить в форму входа.

### Atomic Design

Методология Брэда Фроста называет уровни так: атомы — кнопка, поле; молекулы — поле поиска; организмы — шапка, карточка; шаблоны — каркас страницы; страницы — шаблон с реальными данными. Полезна как общий язык с дизайнерами; следовать ей буквально не обязательно — граница между молекулой и организмом часто спорная.

## Дизайн-система

На масштабе компоненты оформляют в **дизайн-систему**:

- **токены** — цвета, отступы, типографика, радиусы, тени как именованные значения;
- **компоненты** — на токенах, с доступностью и состояниями;
- **документация** — каталог в Storybook с примерами и правилами использования (подробно — в [Визуальных и компонентных тестах](/content/testing-deploying/visual-and-component-testing)).

### Токены

```css
:root { --color-accent: rgb(37, 99, 235); --radius-control: 8px; --space-2: 8px; }
[data-theme="sale"] { --color-accent: rgb(220, 38, 38); }

.button { background: var(--color-accent); border-radius: var(--radius-control); padding: var(--space-2); }
.badge  { color: var(--color-accent); }
```

В проверке в Chromium кнопка, бейдж и ссылка получили один и тот же акцентный цвет из токена, а кнопка в разделе распродажи — красный из темы. После изменения одного значения `--color-accent` перекрасились все три компонента, а тема распродажи сохранила свой цвет. Так делают ребрендинг, тёмную тему и брендирование под разные продукты без правки компонентов (подробно о CSS-переменных — в [Современном CSS](/content/css/modern-css)).

Токены обычно хранят в формате, из которого генерируют CSS, константы для JavaScript и переменные для Figma, — чтобы дизайн и код не расходились. Сами компоненты строят на headless-примитивах или копируя готовые (подробно — в [UI-библиотеках](/content/ecosystem-libs/ui-component-libraries)).

## Данные и отображение

Классическое разделение — **контейнер** занимается данными и логикой, **представление** только показывает:

```jsx
function CartWidgetContainer() {
  const { data: items = [] } = useCart();
  const remove = useRemoveFromCart();
  return <CartWidget items={items} onRemove={remove.mutate} />;
}

function CartWidget({ items, onRemove }) {
  return <ul>{items.map((i) => <li key={i.id}>{i.title}<button onClick={() => onRemove(i.id)}>Убрать</button></li>)}</ul>;
}
```

С хуками жёсткое разделение размылось — логику выносят в хуки, а не в контейнеры, — но принцип остаётся: компонент, который получает всё пропсами, переиспользуется, показывается в Storybook с любыми данными и тестируется без сети.

## API компонента

Компонент — это интерфейс. Хороший API:

- **минимум обязательных пропсов** и разумные значения по умолчанию;
- **композиция** через `children` и слоты вместо флагов вроде `withIcon`, `iconRight`, `iconOnly`;
- **управляемый и неуправляемый режимы**, где это уместно;
- **проброс атрибутов и `ref`** на корневой элемент;
- **понятные имена событий** — `onChange`, `onOpenChange`, — как у встроенных элементов.

Паттерны — составные компоненты, слоты, управляемый режим, headless — разобраны с кодом в [Паттернах и дизайне компонентов React](/content/reactjs/patterns-and-component-design) и [Слотах Vue](/content/vuejs/slots).

### Переиспользование и специфичность

Соблазн сделать «универсальный» компонент с пятнадцатью пропсами под все случаи даёт компонент, который трудно понять и страшно менять — флаги начинают конфликтовать (подробно — в [Архитектурном мышлении](/content/architecture/architectural-thinking)). Простой специфичный компонент лучше переусложнённого общего. В общий выносят, когда видно несколько одинаковых случаев с одной причиной изменений.

### Когда делить

- компонент делает несколько несвязанных вещей;
- его части меняются по разным причинам;
- часть нужна отдельно в другом месте;
- файл трудно прочитать целиком.

Но дробить ради дробления тоже вредно: двадцать микрокомпонентов по три строки усложняют навигацию сильнее одного понятного файла.

## Инверсия управления

Вместо того чтобы компонент сам решал всё и обрастал пропсами под каждый случай, решения отдают **родителю**:

- **управляемый режим** — состояние держит родитель: `value` и `onChange`;
- **`stateReducer`** — родитель переопределяет, как компонент меняет своё состояние, не копируя его код; паттерн описал Кент Доддс;
- **prop getters** — компонент отдаёт функции вроде `getIncrementProps()`, которые навешивают нужные атрибуты и обработчики на разметку родителя;
- **headless** — вся логика и доступность без разметки и стилей.

В проверке хук количества `useQuantity` отдавал prop getters и принимал `stateReducer`:

```js
const { qty, getIncrementProps, getDecrementProps } = useQuantity({
  stateReducer: (state, change) => (change.type === 'inc' && change.qty > stock ? state : change),
});

<button {...getIncrementProps({ onClick: trackClick })}>+</button>
```

Родитель ограничил количество остатком на складе — после пяти нажатий осталось 3, — и добавил свой обработчик аналитики, который вызывался вместе с внутренним. `aria-label` пришёл от хука. Второй интерфейс — ссылка «ещё» — на той же логике работал без ограничения. В хуке нет ни флага `maxQty`, ни флага `onAnalytics`: новые правила появляются у потребителя, а не в API компонента.

## Общая библиотека

В больших проектах UI-кит выносят в отдельный пакет монорепозитория или публикуемую библиотеку (подробно — в [Создавать и патчить](/content/ecosystem-libs/building-and-patching)). Это требует:

- **строгого публичного API** — только то, что экспортировано, остальное можно менять;
- **версий по semver** и журнала изменений — ломающее изменение кнопки затрагивает все приложения;
- **документации и визуальных тестов** — каталог в Storybook и скриншоты защищают от случайных изменений;
- **владельца** — команды платформы или дизайн-системы, которая принимает изменения (подробно — в [Масштабировании и командах](/content/architecture/scalability-and-teams)).

## Красные флаги в ответе

- **«Кнопка сама загрузит данные корзины».** Примитив с бизнес-логикой не переиспользуется.
- **«Сделаем один `Card` на все случаи с двадцатью пропсами».** Флаги будут конфликтовать, компонент перестанут понимать.
- **«Цвета прямо в стилях компонентов».** Ребрендинг и темы потребуют править каждый компонент.
- **«Нужно новое поведение — добавлю флаг».** Сначала стоит отдать решение родителю: слот, `stateReducer`, управляемый режим.
- **«Разобьём компонент на двадцать мелких».** Дробление ради дробления ухудшает навигацию.
- **«Общий UI-кит без версий и владельца».** Каждое изменение будет ломать чужие приложения.

## Как спрашивают на собеседовании

::question
Как организовать сотни компонентов в большом приложении?

#answer
По уровням абстракции: примитивы без бизнес-логики, составные компоненты, компоненты фич с данными и правилами, страницы. Примитивы и составные часто оформляют в дизайн-систему с токенами и документацией.

#more
Главное правило — не смешивать уровни: логика и данные живут в компонентах фич и хуках, а не в примитивах. Atomic Design даёт общий язык уровней, но следовать ему буквально не обязательно.
::

::question
Что такое контейнер и презентационный компонент?

#answer
Контейнер получает данные и описывает логику, презентационный компонент только показывает то, что пришло пропсами, и сообщает о действиях событиями.

#more
С хуками контейнеры часто заменяются хуками данных, но принцип остаётся: компонент без собственной загрузки переиспользуется, показывается в Storybook с любыми данными и тестируется без сети.
::

::question
Что такое дизайн-токены и зачем они?

#answer
Именованные значения дизайна — цвета, отступы, типографика, радиусы, — на которых строятся компоненты. Изменение токена меняет все компоненты сразу, а тема переопределяет токены без правки стилей.

#more
Токены обычно хранят в одном источнике и генерируют из него CSS-переменные, константы для JavaScript и переменные для дизайн-инструмента, чтобы дизайн и код не расходились.
::

::question
Когда выносить компонент в переиспользуемый?

#answer
Когда видно несколько одинаковых случаев с одной причиной изменений, а не заранее. Преждевременное обобщение даёт компонент с множеством флагов, которые конфликтуют.

#more
Простой специфичный компонент лучше переусложнённого общего. Если общий компонент обрастает флагами, решения отдают родителю — слотами, управляемым режимом или `stateReducer`.
::

::question
Что такое инверсия управления в компонентах?

#answer
Компонент отдаёт решения потребителю вместо того, чтобы предусматривать каждый случай флагом: управляемый режим, `stateReducer`, prop getters, headless-компоненты.

#more
`stateReducer` позволяет родителю изменить правило — например, ограничить количество остатком на складе — без копирования логики. Prop getters объединяют обработчики родителя и компонента и добавляют атрибуты доступности на разметку родителя.
::

## Практика

::practice{title="Ребрендинг за один день"}
Компания меняет фирменный цвет. В проекте 120 компонентов, цвет `#2563eb` встречается в стилях 340 раз, плюс тёмная тема копирует часть стилей с другими значениями.

#solution
Цвета переводят на токены, а компоненты — на переменные:

```css
:root { --color-accent: #2563eb; --color-accent-contrast: #fff; }
[data-theme="dark"] { --color-accent: #60a5fa; --color-accent-contrast: #0b1020; }

.button { background: var(--color-accent); color: var(--color-accent-contrast); }
```

```bash
# найти оставшиеся «сырые» цвета в стилях; в CI — правило stylelint color-no-hex
grep -rnE "#[0-9a-fA-F]{3,8}\b" src --include=*.css
```

В проверке изменение одного значения `--color-accent` перекрасило кнопку, бейдж и ссылку, а тема распродажи сохранила своё значение. Дальше ребрендинг — одна правка токена, а тёмная тема — набор переопределений, а не копия стилей.
::

::practice{title="Флаг maxQty для степпера"}
UI-кит содержит `Stepper` для количества. Команда корзины просит флаг `maxQty`, команда опта — `step`, команда аналитики — `onAnyClick`. Через полгода у компонента двенадцать пропсов.

#solution
Решения отдают потребителю через `stateReducer` и prop getters, а компонент остаётся маленьким:

```js
function useQuantity({ initial = 1, stateReducer = (state, change) => change } = {}) {
  const [state, setState] = useState({ qty: initial });
  const dispatch = (type) => setState((s) => stateReducer(s, { type, qty: type === 'inc' ? s.qty + 1 : Math.max(1, s.qty - 1) }));
  return {
    qty: state.qty,
    getIncrementProps: ({ onClick, ...rest } = {}) => ({ 'aria-label': 'Увеличить', onClick: (e) => { onClick?.(e); dispatch('inc'); }, ...rest }),
  };
}

// корзина: ограничение остатком
useQuantity({ stateReducer: (s, c) => (c.type === 'inc' && c.qty > stock ? s : c) });
```

В проверке родитель ограничил количество остатком и добавил аналитику, а другой интерфейс на той же логике работал без ограничений. Новые требования больше не меняют компонент.
::
