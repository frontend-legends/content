# Архитектура компонентов

Компонент - базовый кирпич, но **как организовать их сотни** в большом приложении - вопрос архитектуры. Иерархия компонентов, дизайн-системы, atomic design и правильные границы определяют, останется ли UI поддерживаемым на масштабе.

---

## Иерархия компонентов

Компоненты выстраиваются по уровням абстракции:

```
Примитивы (ui-kit)   → Button, Input, Modal — без бизнес-логики
        ↓
Композитные           → SearchBar, UserCard — собраны из примитивов
        ↓
Фичевые               → CartWidget — со своей логикой и данными
        ↓
Страницы              → композиция всего вышеперечисленного
```

<b class="text-on-semi-light">Зачем уровни</b> - <span class="text-gray">Примитивы переиспользуются везде и ничего не знают о домене; фичевые компоненты содержат логику и данные. Смешивать их - ошибка: кнопка с зашитым запросом к API не переиспользуема. Чистые примитивы внизу + умные компоненты выше - основа масштабируемого UI.</span>

---

## Atomic Design

Популярная методология уровней (Брэд Фрост):

```
Atoms      → кнопка, инпут, иконка
Molecules  → поле поиска (инпут + кнопка)
Organisms  → шапка, карточка товара
Templates  → каркас страницы
Pages      → страница с реальными данными
```

Полезна как **ментальная модель** уровней абстракции; не обязательно следовать буквально, но идея «от мелких к крупным» помогает структурировать дизайн-систему.

---

## Дизайн-системы

На масштабе компоненты оформляют в **дизайн-систему**: единые **токены** (цвета, отступы, типографика) + компоненты на их основе + документация ([Storybook](/content/testing-deploying/visual-and-component-testing)).

- **Консистентность** - один язык дизайна во всех частях и командах.
- **Скорость** - не изобретать кнопку каждый раз.
- **Поддерживаемость** - изменение токена меняет всё приложение.

Строят на headless-примитивах или копи-паст подходе ([UI-библиотеки](/content/ecosystem-libs/ui-component-libraries)).

---

## Контейнер и представление

Классическое разделение: **умный** компонент-контейнер занимается данными и логикой, **глупый** презентационный - только отображением.

```jsx
// Контейнер: данные + логика
function UserListContainer() {
  const { data } = useUsers();
  return <UserListView users={data} onSelect={...} />;
}
// Представление: только разметка, переиспользуемо и тестируемо
function UserListView({ users, onSelect }) { ... }
```

> С хуками жёсткое разделение размылось (логику выносят в хуки, а не контейнеры), но **принцип** - отделять данные от отображения - остаётся ценным: презентационные компоненты легко переиспользовать и тестировать.

## Дизайн API компонента

Компонент - это **интерфейс**. Хороший API:

- **минимум обязательных props**, разумные дефолты;
- **композиция через `children`** вместо десятка булевых флагов;
- поддержка **controlled и uncontrolled** где уместно;
- проброс `...rest`/`ref` для гибкости.

Подробно паттерны (compound components, slots, render props) - в [паттернах React](/content/reactjs/patterns-and-component-design).

## Переиспользование vs специфичность

Баланс, который проверяют на собесе.

<b class="text-on-semi-light">Не абстрагируй раньше времени</b> - <span class="text-gray">Соблазн сделать «универсальный» компонент с 15 пропсами под все случаи приводит к монстру, который тяжело понять и менять. Лучше специфичный простой компонент, чем переусложнённый универсальный. Выноси в общий, когда увидел реальное повторение (правило трёх) - см. [архитектурное мышление](/content/architecture/architectural-thinking).</span>

## Границы компонента

Когда дробить компонент? Признаки, что пора:

- делает **слишком много** (нарушение single responsibility);
- огромный файл, который тяжело читать;
- часть его **переиспользуется** отдельно;
- части меняются **по разным причинам**.

Но не дроби ради дробления - преждевременное разбиение на десятки микрокомпонентов тоже усложняет навигацию.

## Общая библиотека компонентов

В больших проектах/организациях ui-kit выносят в **отдельный пакет** ([монорепо](/content/architecture/scalability-and-teams)), который переиспользуют приложения. Это требует строгого API, версионирования и документации ([своя библиотека](/content/ecosystem-libs/building-and-patching)).

## Инверсия управления

Senior-приём гибких компонентов: вместо того чтобы компонент сам решал всё (и оброс пропсами под каждый случай), **отдай управление наружу**.

- **Control props** - родитель управляет состоянием компонента (`value`/`onChange`), компонент не настаивает на своём.
- **State reducer** (Кент Доддс) - родитель передаёт свой reducer и переопределяет, как компонент меняет внутреннее состояние, не форкая его.
- **Prop getters** - компонент отдаёт функции (`getInputProps()`), навешивающие нужные пропсы/обработчики на твою разметку.
- **Headless-компоненты** - вся логика и доступность, ноль разметки/стилей; пользователь рендерит сам ([UI-библиотеки](/content/ecosystem-libs/ui-component-libraries)).

<b class="text-on-semi-light">Зачем</b> - <span class="text-gray">Чем больше «вариантов» компонент пытается покрыть булевыми пропсами, тем он негибче и сложнее. Инверсия управления отдаёт контроль потребителю - один headless-компонент покрывает бесконечно много UI без раздувания API. Это масштабируемый способ строить переиспользуемые компоненты.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Как организовать сотни компонентов в большом приложении?</b>
<span class="text-gray">По уровням абстракции: примитивы (ui-kit без логики) → композитные → фичевые (с данными/логикой) → страницы. Чистые переиспользуемые примитивы внизу, умные компоненты выше. Часто оформляют в дизайн-систему.</span>

<b class="text-on-semi-light">Что такое контейнер и презентационный компонент?</b>
<span class="text-gray">Контейнер занимается данными и логикой, презентационный - только отображением (получает данные через props). С хуками логику выносят в хуки, но принцип отделять данные от вида остаётся: презентационные легко переиспользовать и тестировать.</span>

<b class="text-on-semi-light">Что такое atomic design?</b>
<span class="text-gray">Методология уровней: atoms → molecules → organisms → templates → pages. Ментальная модель «от мелких к крупным» для структурирования дизайн-системы.</span>

<b class="text-on-semi-light">Когда выносить компонент в переиспользуемый?</b>
<span class="text-gray">При реальном повторении (правило трёх), а не заранее. Преждевременная универсализация рождает монстра с десятком пропсов. Специфичный простой компонент лучше переусложнённого универсального.</span>

<b class="text-on-semi-light">Как понять, что компонент пора разбить?</b>
<span class="text-gray">Делает слишком много, огромный файл, часть переиспользуется отдельно, части меняются по разным причинам. Но не дробить ради дробления - избыток микрокомпонентов тоже вредит.</span>
