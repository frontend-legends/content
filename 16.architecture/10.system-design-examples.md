# Примеры системного дизайна

Пять задач, которые чаще всего дают на фронтенд-раунде системного дизайна, — автокомплит, лента с бесконечной прокруткой, чат, таблица на десятки тысяч строк и доступный выпадающий список — разобранные по каркасу [RADIO](/content/architecture/frontend-system-design). В каждой — что уточнить, как устроить компоненты, данные и API и в чём главная ловушка. Ловушки проверены настоящим кодом: гонка ответов в автокомплите, дубли при постраничной выдаче через offset, прыжок экрана при подгрузке истории чата, тысячи строк в DOM и «дропдаун из div», который автоматическая проверка доступности не замечает.

::tldr
- **Автокомплит:** дебаунс ввода, отмена устаревшего запроса, кеш по запросу, минимум символов и роль combobox. Без отмены медленный ответ на старый запрос затирает новые подсказки.
- **Лента:** курсорная пагинация, сторожевой элемент с `IntersectionObserver`, виртуализация, оптимистичные действия. Offset при новом посте показывает дубль, при удалении — теряет пост.
- **Чат:** WebSocket для новых сообщений и REST для истории, сообщения по id, оптимистичная отправка со статусом, дедупликация после переподключения, подгрузка вверх с сохранением позиции.
- **Таблица:** виртуализация — в DOM только видимые строки с запасом; сортировка и фильтр на сервере, когда данных много.
- **Combobox:** доступность и есть задача — роли, `aria-expanded`, `aria-activedescendant`, полная клавиатура, фокус в поле. Автоматические проверки ловят не всё.
::

## Как читать разборы

Каждый разбор идёт по шагам :term[RADIO]{def="каркас ответа на системный дизайн: требования, архитектура, модель данных, интерфейсы, оптимизации"}, но не пересказывает каркас: в нём только то, что специфично для задачи, — уточняющие вопросы, которые меняют дизайн, дерево компонентов, данные, API и главная ловушка. На интервью ни одну задачу не успеть пройти так подробно; цель — знать, куда углубляться, когда интервьюер спросит «а что если…».

## Автокомплит

Поле поиска с подсказками по мере ввода. Самая частая задача: небольшая, но в ней сразу сеть, гонки, кеш и доступность.

**Что уточнить.** Сколько подсказок, источник — сервер или локальный список, нужна ли подсветка совпадения, недавние запросы, мобильные устройства, что происходит по Enter — переход или поиск.

**Компоненты.**

```text
SearchAutocomplete
├── Input              ← role="combobox", дебаунс
├── SuggestionsList    ← role="listbox"
│   └── Suggestion     ← role="option", подсветка
└── useSuggestions     ← запрос, отмена, кеш
```

**Данные.** Текущий запрос, подсказки, индекс активной подсказки, состояние загрузки и кеш `запрос → подсказки`.

**API.** `GET /suggest?q=чай&limit=8` → массив подсказок. Запрос нормализуют — обрезают пробелы и приводят к нижнему регистру, — чтобы кеш срабатывал на «Чай » и «чай».

### Гонка ответов

Пользователь печатает быстро, запросы уходят один за другим, а ответы приходят в любом порядке. Широкий запрос «ч» обрабатывается дольше, чем «ча». В проверке без защиты ответ на «ч» пришёл последним и затёр подсказки — на экране остались результаты для запроса, которого в поле уже нет.

Решение — отменять предыдущий запрос при новом вводе:

```js
let timer, controller;
function onInput(raw) {
  const q = raw.trim().toLowerCase();
  clearTimeout(timer);
  controller?.abort();                         // ответ на прошлый ввод больше не нужен
  if (q.length < 2) return show([]);
  if (cache.has(q)) return show(cache.get(q));
  timer = setTimeout(async () => {
    controller = new AbortController();
    try {
      const items = await suggest(q, { signal: controller.signal });
      cache.set(q, items);
      show(items);
    } catch (e) {
      if (e.name !== 'AbortError') showError(e);
    }
  }, 300);
}
```

В проверке пять нажатий быстрее дебаунса дали один запрос вместо пяти; запрос «ч», ушедший в сеть до ввода «чайник», был отменён, и его ответ так и не попал на экран; возврат к «ЧАЙ П » взял подсказки из кеша без сети. Это те же гонки, что в эффектах React ([эффекты и синхронизация](/content/reactjs/effects-and-synchronization)), только на уровне архитектуры: отмену делает слой данных, а не каждый компонент.

**Ещё оптимизации.** Минимум символов, ограничение размера кеша, предзагрузка популярных запросов, сохранение недавних. Доступность — как у [combobox](#combobox) ниже.

## Лента с бесконечной прокруткой

Лента постов или товаров с подгрузкой при прокрутке, лайками и комментариями.

**Что уточнить.** Появляются ли новые посты, пока пользователь листает; медиа в постах; нужна ли кнопка «показать новые»; надо ли вернуться на ту же позицию после перехода в пост и назад.

**Компоненты.**

```text
Feed
├── NewPostsBanner        ← «12 новых постов»
├── FeedList              ← виртуализация
│   └── PostCard          ← лайк, комментарии
├── Sentinel              ← триггер подгрузки
└── useFeed               ← страницы, курсор, кеш
```

**Данные.** Посты нормализованы — `{ [id]: post }`, порядок — массив id, курсор следующей страницы. Один пост может встретиться в ленте, в избранном и в открытой карточке, и лайк должен обновить его везде ([архитектура состояния и данных](/content/architecture/state-and-data-architecture)).

**API.** `GET /feed?cursor=X&limit=20` → `{ items, nextCursor }`, лайк — `POST /posts/:id/like`.

### Offset или курсор

С offset клиент просит «посты с 20-го по 40-й», а лента тем временем меняется. В проверке:

| Событие между страницами | Offset | Курсор |
|--------------------------|--------|--------|
| сверху опубликован новый пост | последний пост первой страницы пришёл второй раз | вторая страница продолжилась ровно с места остановки |
| удалён пост с первой страницы | следующий пост сдвинулся на первую страницу и не показан никогда | ничего не потерялось |

Курсор — это «после поста с id 21», а не «после двадцатого места», поэтому вставки и удаления выше него не сдвигают выдачу. Цена — нельзя перейти сразу на десятую страницу, но ленте это и не нужно. Для таблицы с номерами страниц offset по-прежнему уместен. Подробнее о форматах пагинации — в [паттернах API](/content/network-api/api-patterns).

### Когда грузить следующую страницу

Внизу ленты стоит пустой элемент-сторож, а `IntersectionObserver` сообщает, когда он подходит к экрану. Обработчик `scroll` для этого не нужен — он срабатывает десятки раз в секунду и заставляет мерить положение вручную.

```js
new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting) loadNextPage();
}, { rootMargin: '200px' }).observe(sentinel);
```

В проверке в Chromium первая страница не вызвала второй запрос, пока сторож был ниже экрана с запасом 200 px; прокрутка до конца — ровно один запрос и ещё десять постов; небольшая прокрутка после этого — ни одного.

**Ещё оптимизации.** Виртуализация, когда постов сотни, — иначе тысячи узлов не укладываются в кадр ([оценки в системном дизайне](/content/architecture/frontend-system-design)). Оптимистичный лайк с откатом при ошибке. Ленивые картинки с заданными размерами, чтобы не прыгала раскладка. Состояния: конец ленты, ошибка догрузки с кнопкой «повторить», пустая лента. Новые посты — баннером «показать новые», а не вставкой над тем, что читает пользователь.

## Чат

Мессенджер: список диалогов, сообщения в реальном времени, история.

**Что уточнить.** Личные диалоги или группы, вложения, статусы «доставлено» и «прочитано», индикатор набора текста, офлайн, поиск по истории.

**Компоненты.**

```text
Chat
├── ConversationList     ← непрочитанные, последние сообщения
├── MessageList          ← история вверх, новые снизу
│   └── Message          ← статус: отправляется, отправлено, ошибка
├── MessageInput
└── useChat              ← WebSocket, история, очередь отправки
```

**Данные.** Сообщения по диалогам, нормализованы по id; у каждого — порядковый номер от сервера и статус. Своё сообщение до ответа сервера живёт под временным `clientId`.

**API.** Два канала: WebSocket — новые сообщения, статусы, набор текста; :term[REST]{def="стиль API: ресурсы с адресами, методы HTTP по смыслу, статусы ответа"} — история `GET /conversations/:id/messages?before=<id>&limit=50`. Реалтайм-протоколы и переподключение — в [реалтайме](/content/network-api/realtime) и [клиентах реалтайма](/content/ecosystem-libs/realtime-and-api-clients).

### Порядок, дубли и оптимистичная отправка

Сообщения приходят из трёх мест — сокет, история и собственная отправка, — и одно и то же сообщение может прийти дважды: эхо своего сообщения, повтор после переподключения. Поэтому состояние держат как словарь по id, а порядок строят по номеру от сервера:

```js
case 'receive': {
  const fresh = action.messages.filter((m) => !state.byId[m.id]);   // уже есть — пропустить
  const byId = { ...state.byId, ...Object.fromEntries(fresh.map((m) => [m.id, m])) };
  const order = [...state.order, ...fresh.map((m) => m.id)]
    .sort((a, b) => (byId[a].seq ?? Infinity) - (byId[b].seq ?? Infinity));
  return { byId, order };
}
```

В проверке своё сообщение появилось сразу со статусом «отправляется» и стояло внизу, пока не пришёл ответ сервера; после подтверждения оно получило серверный id и встало на своё место по номеру; повтор трёх последних сообщений после переподключения не дал ни одного дубля. Сообщение, которое не ушло, осталось в ленте со статусом «ошибка» — пользователь видит «не отправлено, повторить», а не теряет текст.

### Подгрузка истории вверх

Когда пользователь долистал до начала, сверху добавляют более старые сообщения — и экран прыгает: прокрутка осталась на нуле, а над ней появилось новое содержимое. В проверке после добавления двадцати сообщений сверху вместо «Сообщения 100» наверху оказалось «Сообщение 80». Поправка — сдвинуть прокрутку на высоту добавленного:

```js
const before = list.scrollHeight;
list.prepend(...olderMessages);
list.scrollTop += list.scrollHeight - before;
```

Если прокрутка не в самом верху, Chromium держит позицию сам — это привязка прокрутки, `overflow-anchor`. В проверке при отступе 40 px видимое сообщение не сдвинулось, а с `overflow-anchor: none` — прыгнуло на двадцать. Но на нуле привязка не работает, а это и есть момент подгрузки, поэтому ручная поправка нужна всё равно.

**Ещё оптимизации.** Переподключение с экспоненциальной задержкой и догрузкой пропущенного по последнему известному id. Очередь неотправленных сообщений в офлайне. Виртуализация длинной истории. Набор текста — с ограничением частоты, а не на каждое нажатие.

## Таблица на десятки тысяч строк

Таблица с сортировкой, фильтрами и прокруткой по большому набору данных.

**Что уточнить.** Сколько строк, где сортировка и фильтр — на клиенте или сервере, нужно ли редактирование ячеек, закреплённые колонки и заголовок, выделение строк, экспорт.

**Компоненты.** `Table → Header (сортировка) → VirtualRows → Row → Cell`; логика таблицы — headless, отдельно от отрисовки (готовые решения — в [таблицах и гридах](/content/ecosystem-libs/tables-and-grids)).

**Данные.** Параметры сортировки и фильтров — в URL, видимый диапазон строк, кеш загруженных страниц.

**API.** Пока данных тысячи — можно загрузить всё и сортировать на клиенте. Когда сотни тысяч — сортировка, фильтр и пагинация на сервере: `GET /orders?sort=-date&status=paid&cursor=…`, а клиент только передаёт параметры.

### Виртуализация

В DOM — только видимые строки с небольшим запасом, а пустой контейнер полной высоты держит правильный ползунок прокрутки:

```js
const start = Math.max(0, Math.floor(viewport.scrollTop / ROW) - OVERSCAN);
const end = Math.min(ROWS, Math.ceil((viewport.scrollTop + viewport.clientHeight) / ROW) + OVERSCAN);
// рисуем строки start…end с top = i * ROW внутри контейнера высотой ROWS * ROW
```

В проверке таблица на 50 000 строк по 32 px имела высоту прокрутки 1 600 000 px, а в DOM было 25 строк в начале и 30 после прокрутки к середине — 5 запаса сверху, 20 видимых, 5 снизу; наверху окна была ровно «Строка 25000». Цена: поиск браузера по странице не находит невидимые строки, а строки разной высоты требуют измерения.

**Ещё оптимизации.** Мемоизация ячеек, дебаунс фильтра, закреплённые колонки через `position: sticky`, доступность таблицы — роли `grid` и навигация стрелками, если ячейки интерактивные.

## Combobox

Выпадающий список с поиском — задача на глубину в доступности. Собрать выпадающий список легко, собрать доступный — десятки деталей.

**Что уточнить.** Одиночный или множественный выбор, поиск по вариантам, асинхронная загрузка, свой ввод вне списка, длинные списки.

**Компоненты.** Поле, всплывающий список и логика клавиатуры — headless, отдельно от стилей. Всплывающий слой позиционируют так, чтобы он не уходил за край экрана.

### Доступность — это и есть задача

Скринридер должен понять, что поле открывает список, сколько в нём вариантов и какой сейчас активен. Для этого:

```html
<label for="city">Город</label>
<input id="city" role="combobox" aria-expanded="true"
       aria-controls="list" aria-activedescendant="o0" aria-autocomplete="list">
<ul id="list" role="listbox" aria-label="Города">
  <li id="o0" role="option" aria-selected="true">Москва</li>
  <li id="o1" role="option" aria-selected="false">Казань</li>
</ul>
```

Фокус всё время остаётся в поле, а активный вариант указывает `aria-activedescendant` — так можно печатать и листать варианты одновременно. Клавиатура: стрелки вниз и вверх по кругу, Enter выбирает и закрывает, Escape закрывает, Home и End — к краям. Роли и атрибуты подробно — в [доступности](/content/html/accessibility).

В проверке в Chromium «дропдаун из div» с полем и вариантами в обычных блоках прошёл axe без единого нарушения: placeholder засчитан как имя поля. Но дерево доступности показало, что услышит скринридер, — `textbox "Город"` и текст «Москва Казань», ни списка, ни вариантов. Правильная разметка дала `combobox "Город" [expanded]` и `listbox` с тремя `option`, axe тоже молчал, а клавиатура вела себя как положено: стрелка вниз открыла список, после последнего варианта активным снова стал первый, Enter записал «Самара» в поле и закрыл список, фокус остался в поле.

Вывод для интервью: автоматическая проверка ловит отсутствующие атрибуты, но не отсутствующее поведение. Доступность проверяют клавиатурой и деревом доступности, а не только линтером.

## Общий чеклист

По любой задаче пройтись хотя бы кратко:

```text
[ ] уточнил требования и границы
[ ] компоненты и поток данных
[ ] форма состояния, где живёт каждое, нормализация
[ ] API: пагинация, реалтайм, ошибки
[ ] производительность: виртуализация, дебаунс, вес первого экрана
[ ] сеть: отмена гонок, кеш, оптимистичные обновления, повтор
[ ] доступность: роли, клавиатура, фокус
[ ] состояния: загрузка, ошибка, пусто, офлайн
[ ] назвал компромиссы выбранных решений
```

## Красные флаги в ответе

- Автокомплит без отмены или проверки устаревших ответов.
- Запрос на каждое нажатие клавиши, без дебаунса и минимума символов.
- Offset-пагинация в ленте, где посты появляются в реальном времени.
- Обработчик `scroll` для подгрузки вместо `IntersectionObserver`.
- Чат, где сообщения хранятся массивом без id и дублируются после переподключения.
- Подгрузка истории вверх без сохранения позиции прокрутки.
- 50 000 строк таблицы целиком в DOM.
- Combobox из div и «доступность проверим линтером».

## Как спрашивают на собеседовании

::question
Как спроектировать автокомплит?

#answer
Поле с ролью combobox, список подсказок и слой данных. Ввод дебаунсят и нормализуют, короткие запросы не отправляют, предыдущий запрос отменяют через `AbortController`, ответы кешируют по запросу. Плюс клавиатура, `aria-activedescendant` и состояния загрузки, пустого ответа и ошибки.

#more
Отмену и кеш делает слой данных, а не каждый компонент. Кеш ограничивают по размеру и нормализуют ключ — регистр, пробелы. Часто добавляют недавние запросы и предзагрузку популярных. Для мобильных — меньше подсказок и больший дебаунс.
::

::question
Зачем отменять запросы в автокомплите?

#answer
Быстрый набор отправляет несколько запросов, а ответы приходят в любом порядке: широкий запрос обрабатывается дольше. Без отмены медленный ответ на старый запрос приходит последним и затирает подсказки к текущему.

#more
`AbortController` ещё и экономит сеть и сервер — запрос прерывается, а не только игнорируется. Если отменить нельзя, сравнивают запрос ответа с текущим значением поля и отбрасывают устаревший. Отменённый запрос даёт `AbortError`, его нельзя показывать пользователю как ошибку.
::

::question
Как правильно сделать бесконечную прокрутку?

#answer
Сторожевой элемент внизу и `IntersectionObserver` с запасом `rootMargin` вместо обработчика `scroll`, курсорная пагинация, виртуализация при сотнях элементов, нормализованные посты и состояния конца ленты, ошибки догрузки и пустой ленты.

#more
Новые посты показывают баннером «показать новые», а не вставкой над тем, что читает пользователь. Позицию сохраняют при возврате назад. Бесконечная прокрутка плохо сочетается с футером и поиском по странице — иногда кнопка «показать ещё» честнее.
::

::question
Offset или курсорная пагинация?

#answer
Для лент — курсор. Offset считает места, а лента меняется: новый пост сверху сдвигает выдачу, и последний пост страницы приходит второй раз, удалённый — и следующий пост не покажется никогда. Курсор — «после поста с таким id», вставки и удаления выше него на выдачу не влияют.

#more
Цена курсора — нельзя перейти сразу на нужную страницу и показать общее число страниц. Для таблицы с номерами страниц и редко меняющимися данными offset уместен. Курсор обычно непрозрачная строка от сервера, чтобы клиент не зависел от того, как он устроен.
::

::question
Как спроектировать чат?

#answer
WebSocket для новых сообщений и статусов, REST для истории. Сообщения нормализованы по id и упорядочены по номеру от сервера. Своё сообщение показывается сразу со статусом «отправляется» и временным id, ответ сервера его подтверждает. История подгружается вверх с сохранением позиции прокрутки.

#more
Дубли неизбежны — эхо своих сообщений и повтор после переподключения, — поэтому добавление идемпотентно по id. При переподключении догружают пропущенное по последнему известному id. Неотправленное — в очередь и со статусом ошибки, текст не теряется. Длинную историю виртуализируют.
::

::question
Как сделать доступный выпадающий список с поиском?

#answer
Подпись у поля, `role="combobox"` с `aria-expanded` и `aria-controls`, список `role="listbox"` с `role="option"`, активный вариант через `aria-activedescendant` при фокусе в поле. Клавиатура: стрелки, Enter, Escape, Home, End.

#more
Автоматические проверки ловят не всё: «дропдаун из div» с placeholder может пройти axe без нарушений, хотя скринридер не услышит ни списка, ни вариантов. Проверяют деревом доступности и клавиатурой. Готовые headless-библиотеки обычно надёжнее своей реализации.
::

## Практика

::practice{title="Подсказки не совпадают с запросом"}
В автокомплите иногда видны подсказки к запросу, который пользователь уже стёр: в поле «чайник», а в списке — результаты для «ч». Код:

```js
input.addEventListener('input', async (e) => {
  const items = await suggest(e.target.value);
  render(items);
});
```

#solution
Каждый ввод отправляет запрос, а ответы приходят в любом порядке — запрос «ч» сервер обрабатывает дольше. В проверке ответ на старый запрос пришёл последним и затёр подсказки. Нужно отменять предыдущий запрос и заодно не отправлять каждое нажатие:

```js
let timer, controller;
input.addEventListener('input', (e) => {
  const q = e.target.value.trim().toLowerCase();
  clearTimeout(timer);
  controller?.abort();
  if (q.length < 2) return render([]);
  timer = setTimeout(async () => {
    controller = new AbortController();
    try {
      render(await suggest(q, { signal: controller.signal }));
    } catch (err) {
      if (err.name !== 'AbortError') renderError(err);
    }
  }, 300);
});
```

В проверке так пять быстрых нажатий дали один запрос, а отменённый запрос не попал на экран. Кеш по нормализованному запросу убирает и повторные запросы.
::

::practice{title="История чата прыгает при подгрузке"}
Когда пользователь долистывает чат до начала, сверху подгружаются старые сообщения — и экран перескакивает: пользователь теряет сообщение, которое читал.

#solution
Прокрутка осталась на нуле, а над ней появилось новое содержимое — видимым стало самое старое из подгруженных. В проверке после добавления двадцати сообщений наверху вместо «Сообщения 100» оказалось «Сообщение 80». Привязка прокрутки браузера здесь не помогает: в проверке в Chromium она держала позицию, только когда прокрутка была не в самом верху. Поправка — сдвинуть прокрутку на высоту добавленного:

```js
const before = list.scrollHeight;
list.prepend(...older);
list.scrollTop += list.scrollHeight - before;
```

В проверке при следующей подгрузке с этой поправкой наверху осталось то же сообщение, что и до неё. Подгрузку запускают заранее — сторожем у верхнего края с запасом, — чтобы пользователь не упирался в начало списка.
::
