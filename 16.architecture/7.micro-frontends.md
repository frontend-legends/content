# Микрофронтенды

**Микрофронтенды** - разбиение фронтенд-монолита на независимо разрабатываемые и деплоящиеся части, которыми владеют разные команды. Это перенос идеи микросервисов на фронтенд. Мощный, но дорогой подход - и senior должен знать, **когда он оправдан, а когда нет**.

---

## Проблема, которую решают

Большое приложение + много команд = боль:

- **связанность деплоя** - одна команда не может выкатиться, не дождавшись других;
- **merge hell** - все в одной кодовой базе;
- **узкое место** - общий релиз-поезд тормозит всех;
- разные команды хотят разный темп и иногда стек.

Микрофронтенды дают командам **автономию**: своя часть, свой деплой, свои решения.

---

## Зачем (и закон Конвея)

| Выгода | Суть |
|--------|------|
| Автономия команд | владеют частью end-to-end |
| Независимый деплой | выкатывают свою часть отдельно |
| Гибкость стека | (теоретически) разные технологии |
| Масштаб организации | много команд параллельно |

<b class="text-on-semi-light">Закон Конвея</b> - <span class="text-gray">«Системы копируют структуру коммуникации организации». Микрофронтенды **сознательно** выравнивают архитектуру под команды: каждая команда владеет своим микрофронтендом end-to-end. Это про **масштабирование организации**, а не про технологию. Если у тебя одна команда - микрофронтенды не нужны.</span>

---

## Способы композиции

```
Build-time     → собираются как пакеты (НЕ независимый деплой, по сути монолит)
Server-side     → собираются на сервере/edge (SSI, edge-композиция)
Run-time/client → собираются в браузере (Module Federation, iframe, web components)
```

### Module Federation

Главная технология (Webpack/Rspack): приложения, **собранные отдельно**, делятся модулями **в рантайме**. Одно приложение подгружает компонент/модуль другого на лету.

```
Host (app shell) ──рантайм──► Remote A (каталог)
                 ──рантайм──► Remote B (корзина)
```

### App shell

Типовая структура: **оболочка** (shell) с роутингом и общими частями (шапка, навигация), в которую подгружаются микрофронтенды по маршрутам.

### iframe и web components

- **iframe** - максимальная изоляция, но неуклюже (стили, общение, UX).
- **Web components** - кросс-фреймворковые кастомные элементы как контейнеры микрофронтендов.

## Сложности

Цена автономии высока:

| Проблема | Суть |
|----------|------|
| **Дублирование зависимостей** | каждый тащит свой React → раздутый бандл |
| **Консистентность** | единый дизайн между независимыми частями |
| **Производительность** | несколько бандлов, общая загрузка |
| **Общее состояние/общение** | как микрофронтенды обмениваются данными |
| **Сложность** | инфраструктура, версионирование, отладка |

<b class="text-on-semi-light">Дублирование React - частый вопрос</b> - <span class="text-gray">Если каждый микрофронтенд включает свой React, пользователь грузит его несколько раз, а два экземпляра React ломают контекст/хуки. Поэтому общие зависимости **шарят** (shared в Module Federation) - но это вновь сцепляет независимые части по версиям. Баланс автономии и общего - главная сложность.</span>

---

## Когда использовать

```
Большая организация, много команд, огромное приложение  → возможно, микрофронтенды
Одна-две команды, обычное приложение                     → НЕ нужны (оверкилл)
Нужна автономия деплоя независимых частей                → кандидат
Просто хочется «модно»                                    → красный флаг
```

<b class="text-on-semi-light">Антипаттерн «распределённый монолит»</b> - <span class="text-gray">Худший исход - микрофронтенды, которые **зависят друг от друга** и не деплоятся по-настоящему независимо: вся сложность распределённой системы без её выгод. Если части нельзя выкатывать раздельно - микрофронтенды не нужны, это распределённый монолит.</span>

## Альтернатива - монорепо

Часто **монорепо с хорошими границами** ([масштабируемость](/content/architecture/scalability-and-teams)) даёт командам автономию владения без рантайм-сложности микрофронтендов. Прежде чем дробить на микрофронтенды, стоит исчерпать модульный монолит/монорепо - он проще и покрывает большинство случаев.

---

## Интеграция и общее состояние

Самостоятельные микрофронтенды должны как-то общаться и делить общее - и это главная сложность:

- **Браузерные события / шина** - слабая связанность: микрофронтенд кидает `CustomEvent`, другие слушают, не зная друг о друге.
- **URL как общее состояние** - маршрут и параметры доступны всем и нейтральны.
- **Общий стор** - сильнее сцепляет (общая зависимость и контракт состояния); используют осторожно.
- **Дизайн-токены и shell** - единый ui-kit/токены через shell, чтобы части выглядели как одно приложение.

## Способы загрузки

- **Module Federation** (Webpack/Rspack) - рантайм-шеринг модулей и общих зависимостей (один React).
- **Import maps + Native Federation** - на веб-стандартах, без привязки к Webpack.
- **single-spa** - оркестратор маршрутов между микрофронтендами на разных фреймворках.

<b class="text-on-semi-light">Senior-вывод</b> - <span class="text-gray">Чем больше микрофронтенды делят (стор, зависимости, токены), тем меньше они независимы - и тем ближе к распределённому монолиту. Хорошая интеграция - минимум общего: события и URL вместо общего стора. Контракт интеграции важнее технологии загрузки.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое микрофронтенды и зачем они?</b>
<span class="text-gray">Разбиение фронтенд-монолита на независимо деплоящиеся части, которыми владеют разные команды. Дают автономию деплоя и масштабирование организации (закон Конвея). Нужны большим командам, не маленьким.</span>

<b class="text-on-semi-light">Как реализуют микрофронтенды?</b>
<span class="text-gray">Композиция в рантайме (Module Federation - шеринг модулей между отдельно собранными приложениями), на сервере/edge, через iframe или web components. App shell с роутингом подгружает микрофронтенды.</span>

<b class="text-on-semi-light">Какие главные проблемы у микрофронтендов?</b>
<span class="text-gray">Дублирование зависимостей (несколько React), консистентность дизайна, производительность (много бандлов), общее состояние и общение, общая сложность инфраструктуры.</span>

<b class="text-on-semi-light">Что такое «распределённый монолит»?</b>
<span class="text-gray">Антипаттерн: микрофронтенды, зависящие друг от друга и не деплоящиеся независимо. Получаешь сложность распределённой системы без её выгод. Если части нельзя выкатывать раздельно - подход не оправдан.</span>

<b class="text-on-semi-light">Когда НЕ стоит использовать микрофронтенды?</b>
<span class="text-gray">Одна-две команды, обычное приложение - цена (инфраструктура, дублирование, сложность) превышает выгоду. Часто монорепо с хорошими границами даёт автономию проще.</span>

<b class="text-on-semi-light">Как микрофронтенды обмениваются данными и делят состояние?</b>
<span class="text-gray">Предпочтительна слабая связанность: браузерные CustomEvents/шина и URL как общее состояние. Общий стор сильнее сцепляет (общий контракт состояния) и приближает к распределённому монолиту - используют осторожно.</span>
