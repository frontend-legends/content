# Микрофронтенды

Разбиение фронтенда на части, которые разные команды разрабатывают и выкладывают независимо: какую проблему это решает и при чём тут закон Конвея, способы композиции — при сборке, на сервере, в браузере, — оболочка приложения, Module Federation и import maps, общие зависимости и их версии, изоляция стилей, общение между частями, цена подхода и монорепо как альтернатива. Спрашивают, что такое микрофронтенды, как их реализуют и когда они не нужны. Глубже — почему корзина в шапке не видит товаров, добавленных в каталоге, почему обновление общей библиотеки ломает чужой микрофронтенд и что такое распределённый монолит.

::tldr
- **Микрофронтенды решают организационную проблему:** много команд в одном приложении мешают друг другу при выкладке. Каждая команда владеет своей частью от начала до конца и выкладывает её сама.
- **Это закон Конвея, применённый сознательно:** архитектура повторяет структуру команд. При одной-двух командах микрофронтенды не нужны.
- **Композиция:** при сборке — это просто пакеты без независимой выкладки; на сервере или edge — сборка страницы из фрагментов; в браузере — Module Federation, import maps, веб-компоненты, iframe.
- **Общие зависимости — главная сложность:** своя копия библиотеки в каждой части — двойной вес и раздельное состояние; общая — связывает части по версиям.
- **Чем больше части делят, тем меньше они независимы:** события и URL вместо общего стора, контракт интеграции важнее технологии. Части, которые нельзя выкатить по отдельности, — распределённый монолит.
::

---

## Проблема

Сквозной пример — магазин, над которым работают пять команд: каталог, корзина и оформление, личный кабинет, отзывы, промо.

В одном приложении у них общие:

- **выкладка** — команда отзывов ждёт, пока каталог починит упавший тест;
- **релизный поезд** — всё выходит раз в неделю вместе;
- **кодовая база** — конфликты слияния, общие зависимости, споры о правилах;
- **стек** — обновление React или сборщика нужно согласовать со всеми.

Микрофронтенды дают командам **автономию**: своя часть, свой репозиторий или пакет, своя выкладка.

### Закон Конвея

Мелвин Конвей заметил, что системы повторяют структуру коммуникации организаций, которые их создают. Микрофронтенды делают это намеренно: граница части проходит там же, где граница команды (подробно — в [Масштабировании и командах](/content/architecture/scalability-and-teams)). Поэтому это решение о масштабе организации, а не о технологии: если команда одна, независимая выкладка частей ничего не даёт.

## Способы композиции

| Где собирается | Как | Независимая выкладка |
| --- | --- | --- |
| при сборке | части — пакеты, приложение их импортирует | нет: нужна пересборка приложения |
| на сервере или edge | страница собирается из фрагментов HTML: SSI, ESI, серверная композиция | да |
| в браузере | оболочка загружает части во время работы | да |

### Оболочка приложения

Типичная структура браузерной композиции — **оболочка**: маршрутизация, общие части — шапка, навигация, авторизация — и загрузка нужного микрофронтенда по маршруту.

```text
оболочка: маршрутизатор, шапка, авторизация
   /catalog/*   → микрофронтенд каталога
   /cart        → микрофронтенд корзины
   /account/*   → микрофронтенд кабинета
```

### Технологии загрузки

- **Module Federation** — сборщики webpack, Rspack и Vite через плагины собирают части отдельно, а во время работы они загружают модули друг друга и делят общие зависимости;
- **import maps** — стандарт браузера: оболочка сопоставляет имя модуля с адресом, и все части получают один и тот же экземпляр; на нём построен Native Federation;
- **веб-компоненты** — каждая часть регистрирует свой элемент, оболочка просто вставляет `<shop-reviews>`;
- **iframe** — максимальная изоляция ценой неудобств: размеры, общение через `postMessage`, доступность, производительность;
- **single-spa** — оркестратор, который монтирует и размонтирует части на разных фреймворках по маршрутам.

## Общие зависимости

В проверке в Chromium два микрофронтенда — каталог и шапка с корзиной — использовали одну библиотеку состояния корзины.

**Своя копия в каждой части.** Каталог и шапка «вклеили» библиотеку в свои сборки. После двух нажатий «В корзину» в каталоге шапка показала «Корзина: 0»: у каждой части свой экземпляр модуля и своё состояние. То же происходит с двумя копиями React — сломанные хуки и контекст (подробно — в [Бандлерах](/content/advanced-tooling/bundlers)) — плюс двойной вес у пользователя.

**Общий модуль через import map.** Оболочка объявила:

```html
<script type="importmap">
  { "imports": { "shop-store": "/libs/store@2.0.0.js" } }
</script>
```

Обе части импортировали `shop-store` по имени — и получили один экземпляр: после нажатий в каталоге и в промо шапка показала «Корзина: 4».

**Цена общего.** Когда оболочка отдала версию 1.0, промо, которому нужна функция `addMany` из 2.0, не загрузилось вовсе: `The requested module 'shop-store' does not provide an export named 'addMany'`. Остальные части продолжили работать. Общие зависимости снова связывают независимые команды — по версиям, — и обновление библиотеки требует согласования. Module Federation даёт настройки `singleton` и `requiredVersion` для таких случаев, но саму связь не убирает.

## Изоляция и общение

### Стили

Стили одной части не должны ломать другие. В проверке микрофронтенд отзывов как веб-компонент с **Shadow DOM** сохранил свой зелёный цвет кнопки, хотя оболочка задала всем кнопкам красный, а стиль отзывов не перекрасил кнопку оболочки. Другие варианты — CSS-модули, префиксы классов, `@layer` с порядком слоёв (подробно — в [Архитектуре CSS](/content/css/architecture)).

Изоляция не должна мешать единому виду: общие **токены дизайна** — CSS-переменные — проходят и в Shadow DOM, и через границы частей (подробно — в [Архитектуре компонентов](/content/architecture/component-architecture)).

### Общение

Части должны обмениваться событиями, не завися от кода друг друга:

- **события в окне** — `CustomEvent` с префиксом имени: в проверке событие `shop:cart-changed` из Shadow DOM с `composed: true` дошло до оболочки;
- **URL** — маршрут и параметры видны всем и не принадлежат никому;
- **общий стор** — самая сильная связь: общий контракт состояния и версия библиотеки; используют осторожно.

Минимум общего — главный принцип: чем больше части делят, тем ближе они к одному приложению, разрезанному на куски.

## Цена

| Проблема | Суть |
| --- | --- |
| вес | несколько сборок, дублирующиеся зависимости |
| единый вид | дизайн-система и токены должны быть общими |
| производительность | больше запросов, водопады загрузки частей |
| общение и состояние | контракты событий и данных между командами |
| инфраструктура | выкладка, версии, отладка через границы, локальная разработка |
| согласованность | разные версии библиотек и подходов у разных частей |

### Распределённый монолит

Худший исход — части, которые **нельзя выкатить по отдельности**: общий стор с жёстким контрактом, общие версии всего, обязательный совместный релиз. Это вся сложность распределённой системы без её выгод. Признак — команды снова договариваются о дате выкладки.

---

## Альтернатива — модульный монолит

Часто **монорепозиторий с хорошими границами** даёт командам владение своими частями без сложности сборки во время работы: пакеты с публичным API, правила зависимостей, владельцы кода и проверка только затронутого (подробно — в [Монорепозиториях](/content/advanced-tooling/monorepo-tooling) и [Структуре проекта](/content/architecture/project-structure)). Выкладка остаётся общей, но быстрой и частой.

| Ситуация | Выбор |
| --- | --- |
| одна-две команды | модульный монолит |
| много команд, общий темп выкладки устраивает | монорепо с границами и владельцами |
| много команд, независимая выкладка критична | микрофронтенды |
| встраивание чужого приложения или старого кода | iframe или веб-компонент |
| постепенный переезд со старого фронтенда | микрофронтенды как переходный этап |

Последний случай частый: новая часть живёт рядом со старой, пока та постепенно заменяется (подробно — в [Архитектурных решениях](/content/architecture/architectural-decisions)).

## Красные флаги в ответе

- **«Сделаем микрофронтенды, это современно».** Это решение для многих команд, а не для одной.
- **«Каждый микрофронтенд на своём фреймворке».** Технически возможно, но это вес, разный вид и сложная поддержка.
- **«Общий стор между частями».** Самая сильная связь, путь к распределённому монолиту.
- **«Каждый вклеит свой React».** Двойной вес и, если они пересекаются, сломанные хуки и контекст.
- **«Обновим общую библиотеку — все подтянут».** Части разных команд ломаются на несовпадении версий.
- **«Собираем части как пакеты при сборке — это микрофронтенды».** Без независимой выкладки это модульный монолит.

## Как спрашивают на собеседовании

::question
Что такое микрофронтенды и зачем они?

#answer
Разбиение фронтенда на части, которые разные команды разрабатывают и выкладывают независимо. Это решает проблему многих команд в одном приложении: общая выкладка, релизный поезд, конфликты.

#more
Это закон Конвея, применённый сознательно: границы частей совпадают с границами команд. При одной-двух командах выгоды нет, а цена — вес, инфраструктура и контракты — остаётся.
::

::question
Как реализуют микрофронтенды?

#answer
Композицией на сервере или edge — страница из фрагментов, — или в браузере: оболочка загружает части через Module Federation, import maps, веб-компоненты или iframe. Сборка из пакетов при сборке даёт модули, но не независимую выкладку.

#more
Оболочка обычно отвечает за маршрутизацию, шапку и авторизацию. Single-spa оркестрирует части на разных фреймворках, Native Federation строится на import maps.
::

::question
Какие главные проблемы у микрофронтендов?

#answer
Общие зависимости — дублирование или связь по версиям, — единый вид, производительность из-за нескольких сборок, общение и состояние между частями, инфраструктура выкладки и отладки.

#more
Своя копия библиотеки в каждой части — двойной вес и раздельное состояние; общая через Module Federation или import map — один экземпляр, но обновление требует согласования версий.
::

::question
Что такое распределённый монолит?

#answer
Микрофронтенды, которые нельзя выкатить по отдельности: общий стор, общие версии, совместный релиз. Сложность распределённой системы без её выгод.

#more
Признак — команды снова согласуют даты выкладки. Лечится минимумом общего — события и URL вместо общего стора — или честным возвратом к модульному монолиту.
::

::question
Как микрофронтенды обмениваются данными?

#answer
Через слабые связи: события в окне с понятными именами и URL как общее состояние. Общий стор — самая сильная связь, его используют осторожно.

#more
События из Shadow DOM должны идти с `composed: true`, чтобы выйти наружу. Контракт событий документируют и версионируют, как API между сервисами.
::

::question
Когда микрофронтенды не нужны?

#answer
Когда команд одна-две, приложение обычного размера или общая выкладка не мешает. Модульный монолит или монорепо с границами даёт владение частями без сложности композиции во время работы.

#more
Оправданы они при многих командах с разным темпом, при встраивании чужих приложений и как переходный этап при замене старого фронтенда.
::

## Практика

::practice{title="Корзина в шапке не обновляется"}
Микрофронтенд каталога добавляет товар в корзину через общую библиотеку `@shop/cart-store`, а шапка из оболочки показывает ноль. Обе части импортируют одну и ту же библиотеку.

#solution
Каждая часть вклеила свою копию библиотеки в сборку — и у каждой свой экземпляр состояния. В проверке так и было: два нажатия в каталоге, а шапка показывала «Корзина: 0». Общую зависимость отдают одной копией:

```html
<!-- оболочка: одна версия на всё приложение -->
<script type="importmap">
  { "imports": { "@shop/cart-store": "/libs/cart-store@2.0.0.js" } }
</script>
```

```js
// сборка микрофронтенда: не вклеивать, оставить внешней
export default { build: { rollupOptions: { external: ['@shop/cart-store'] } } };
```

С import map в проверке обе части получили один экземпляр, и шапка показала правильное число. В Module Federation то же делает `shared` с `singleton: true`. Ещё слабее связь — не делить стор вовсе, а отправлять событие `shop:cart-changed`, которое слушает шапка.
::

::practice{title="Обновление общей библиотеки сломало промо"}
Команда промо перешла на функцию `addMany` из новой версии `@shop/cart-store`. После её выкладки промо-блок перестал появляться на сайте, а в консоли — `does not provide an export named 'addMany'`.

#solution
Оболочка всё ещё отдаёт старую версию общей зависимости. В проверке при версии 1.0 в import map промо не загрузилось с той же ошибкой, а остальные части продолжили работать. Варианты:

Первый вариант — оболочка обновляет общую версию, проверив, что старое API сохранено:

```json
{ "imports": { "@shop/cart-store": "/libs/cart-store@2.0.0.js" } }
```

Второй — часть проверяет возможность и деградирует, а не падает:

```js
import * as store from '@shop/cart-store';
const addMany = store.addMany ?? ((n) => { for (let i = 0; i < n; i++) store.add(); });
```

Системно — общие зависимости обновляют совместимо по semver, а контрактные тесты каждой части запускают против версии из оболочки в CI. Это и есть цена общего: независимые части связаны версиями.
::
