# Системный дизайн фронтенда

Отдельный раунд интервью для mid+/senior: спроектировать фронтенд-приложение или сложный компонент **на масштабе**. Здесь нет правильного ответа - оценивают, как ты **рассуждаешь, структурируешь и обсуждаешь компромиссы**. Главный инструмент - фреймворк, который ведёт разговор.

---

## Чем отличается от бэкенд-дизайна

Классический system design - про базы, масштабирование, распределённые системы. **Фронтенд** system design - про другое:

| Бэкенд SD | Фронтенд SD |
|-----------|-------------|
| масштабирование серверов, БД | архитектура компонентов |
| шардирование, репликация | управление состоянием |
| очереди, кеш на сервере | загрузка данных, кеш на клиенте |
| consistency, CAP | рендеринг, производительность UI |
| - | доступность, UX, отзывчивость |

> Не уходи в бэкенд (базы, шардинг) - интервьюер ждёт **фронтенд**: компоненты, состояние, данные, рендеринг, производительность, доступность.

---

## Фреймворк RADIO

Структурированный подход (популяризирован GreatFrontEnd). Ведёт от требований к деталям:

```
R — Requirements    — что и для кого строим (уточнить!)
A — Architecture     — высокоуровневая структура, компоненты, поток данных
D — Data model       — какие данные на клиенте, форма состояния
I — Interface (API)  — клиент-серверный API + интерфейсы компонентов
O — Optimizations    — производительность, доступность, краевые случаи
```

### R — Requirements

**Начни с уточнения**, не бросайся проектировать. Раздели:

- **Функциональные** - что должно делать (какие фичи в скоупе?).
- **Нефункциональные** - масштаб, устройства (мобайл?), офлайн, производительность, доступность, локализация.
- **Ограничения и скоуп** - что НЕ делаем (явно отрезать лишнее).

<b class="text-on-semi-light">Это важнейший этап</b> - <span class="text-gray">Кандидаты теряют баллы, бросаясь кодить без уточнений. Хороший инженер сначала **задаёт вопросы**: кто пользователи, какой масштаб, какие устройства, что в приоритете. Это показывает зрелость и сужает задачу до решаемой.</span>

### A — Architecture

Высокоуровневая структура: разбиение на **компоненты**, их иерархия, **поток данных** между ними, где живёт состояние. Нарисуй дерево компонентов и стрелки данных ([архитектура компонентов](/content/architecture/component-architecture)).

### D — Data model

Какие **сущности** на клиенте, форма состояния, что серверное (кеш), что локальное (UI). Нормализация при необходимости ([состояние и данные](/content/architecture/state-and-data-architecture)).

### I — Interface / API

Два интерфейса:

- **Клиент ↔ сервер** - какие эндпоинты, формат, пагинация, реалтайм ([API и BFF](/content/architecture/api-and-bff)).
- **Компонент ↔ компонент** - props, события, публичный API компонентов.

### O — Optimizations

Глубокое погружение в **сквозные аспекты**:

- **производительность** - рендеринг, виртуализация, мемоизация, бандл;
- **сеть** - кеш, пагинация, prefetch, оптимистичные обновления;
- **доступность** - клавиатура, ARIA, фокус;
- **краевые случаи** - загрузка, ошибки, пустые состояния, оффлайн.

---

## Оси, которые держать в голове

В любой задаче проговори (хотя бы кратко) эти аспекты - они и есть сигнал seniority:

```
Производительность · Доступность · Сеть/данные · Состояние
Загрузка/ошибки/пустое · Адаптивность · Безопасность · Локализация
```

Не нужно глубоко по всем - но **упомянуть** и углубиться в релевантные показывает широту.

---

## Как вести разговор

- **Уточняй первым** - вопросы перед проектированием.
- **Думай вслух** и **структурируй** (идёшь по RADIO - видно систему в мышлении).
- **Веди** разговор сам, а не жди вопросов.
- **Обсуждай компромиссы** - «можно так или так; беру это, потому что…». Это главное, что оценивают.
- **Управляй временем** - не зарывайся в одну деталь, покрой картину, потом углубляйся, куда направит интервьюер.

<b class="text-on-semi-light">Компромиссы - суть оценки</b> - <span class="text-gray">Нет «правильного» дизайна. Senior виден в фразах «вариант A даёт X ценой Y, вариант B - наоборот; в этих требованиях выбираю A». Уверенное жонглирование вариантами с обоснованием важнее, чем «знание единственно верного ответа».</span>

## Оценки «на салфетке» для фронтенда

Бэкенд-дизайн считает QPS и хранилище; у фронтенда - **свои** количественные ориентиры, и senior умеет ими оперировать:

- **Бюджет кадра ~16мс** (60fps) - сколько работы влезает в один кадр; тяжёлый рендер/скрипт его превышает → дёрганья.
- **Размер payload** - вес начального бандла и данных; прикинуть JS/изображения против бюджета (например, < 200KB JS gzip на критичном пути).
- **Количество DOM-узлов** - тысячи узлов тормозят → отсюда виртуализация.
- **Память** - длинные списки и кеши растут → стратегия вытеснения.
- **Сетевые раунд-трипы** - сколько запросов до первого экрана → убрать водопады.

<b class="text-on-semi-light">Зачем числа</b> - <span class="text-gray">Конкретика показывает зрелость: не «сделаем быстро», а «бюджет кадра 16мс, поэтому виртуализируем; начальный JS держим под N КБ, поэтому код-сплит по маршрутам». Количественное обоснование - сильный сигнал senior.</span>

---

## Не забыть нефункциональное

Слабые кандидаты проектируют только «счастливый путь». Сильные **всегда** проговаривают сквозные оси: доступность (клавиатура, скринридеры, ARIA), интернационализация (RTL, форматы, плюрализация), безопасность (XSS, авторизация на сервере), наблюдаемость (метрики, ошибки в проде), офлайн/ошибки/пустые состояния. Покрытие этих осей часто и отличает middle от senior на этом раунде.

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем фронтенд system design отличается от бэкенда?</b>
<span class="text-gray">Бэкенд - про базы, шардинг, распределённые системы. Фронтенд - про компонентную архитектуру, состояние, загрузку данных, рендеринг, производительность UI, доступность и UX. Не уходить в серверную часть.</span>

<b class="text-on-semi-light">Какой фреймворк использовать на system design?</b>
<span class="text-gray">RADIO: Requirements (уточнить функциональные и нефункциональные), Architecture (компоненты, поток данных), Data model (форма состояния), Interface (API клиент-сервер и компонентов), Optimizations (производительность, доступность, краевые случаи).</span>

<b class="text-on-semi-light">С чего начинать ответ?</b>
<span class="text-gray">С уточнения требований, а не с проектирования. Спросить про пользователей, масштаб, устройства, приоритеты и явно отрезать вне-скоупа. Это показывает зрелость и сужает задачу.</span>

<b class="text-on-semi-light">Какие аспекты всегда стоит проговорить?</b>
<span class="text-gray">Производительность, доступность, сеть/данные, управление состоянием, состояния загрузки/ошибки/пустое, адаптивность, безопасность, локализация. Глубоко - по релевантным, остальные хотя бы упомянуть.</span>

<b class="text-on-semi-light">Что оценивают на system design?</b>
<span class="text-gray">Не правильный ответ (его нет), а структурированное мышление, покрытие аспектов и - главное - обсуждение компромиссов: какие варианты есть и почему выбран этот под данные требования.</span>

<b class="text-on-semi-light">Как количественно обосновать решения на system design?</b>
<span class="text-gray">Оперировать ориентирами: бюджет кадра ~16мс (60fps), размер начального JS (например, <200KB gzip на критичном пути), число DOM-узлов (тысячи тормозят → виртуализация), сетевые раунд-трипы до первого экрана. Числа показывают зрелость.</span>
