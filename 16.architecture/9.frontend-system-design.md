# Системный дизайн фронтенда

Раунд, на котором просят спроектировать фронтенд-приложение или сложный компонент: ленту, чат, автокомплит, таблицу. Здесь — чем он отличается от бэкенд-дизайна, каркас RADIO по шагам, оценки «на салфетке» с цифрами, которые можно защитить, нефункциональные требования и как вести разговор. Спрашивают, с чего начать и какие аспекты проговорить. Глубже — как количественно обосновать решение: сколько стоит лишний раунд-трип, тысяча DOM-узлов и задача длиннее 50 мс.

::tldr
- **Фронтенд-дизайн — не про базы и шардинг:** про компоненты, состояние, загрузку данных, рендеринг, производительность интерфейса и доступность.
- **RADIO ведёт разговор:** Requirements — уточнить, Architecture — компоненты и поток данных, Data model — форма состояния, Interface — API с сервером и между компонентами, Optimizations — производительность, доступность, краевые случаи.
- **Начинают с вопросов:** кто пользователи, какие устройства, масштаб, что в приоритете и чего явно не делаем. Бросаться рисовать без этого — главная ошибка.
- **Решения обосновывают цифрами:** кадр 16,7 мс при 60 Гц, каждый последовательный запрос — ещё один RTT, тысячи DOM-узлов не укладываются в кадр, задача длиннее 50 мс блокирует ввод.
- **Оценивают ход мысли и компромиссы, а не «правильный ответ»:** «вариант A даёт X ценой Y, при этих требованиях беру A».
::

---

## Чем отличается от бэкенд-дизайна

Классический системный дизайн — про серверы, хранилища и распределённые системы. Фронтенд-раунд смотрит на то же приложение с другой стороны:

| Бэкенд-дизайн | Фронтенд-дизайн |
|---------------|-----------------|
| масштабирование серверов и баз | архитектура компонентов |
| шардирование, репликация | управление состоянием на клиенте |
| очереди, серверный кеш | загрузка данных, клиентский кеш, пагинация |
| согласованность данных, CAP | стратегия рендеринга, производительность интерфейса |
| пропускная способность, QPS | время до первого экрана, отзывчивость, доступность |

Частая ошибка — уйти в серверную часть: выбирать базу, рисовать балансировщики. Интервьюер ждёт другого: какие компоненты, где живёт состояние, как приходят данные, что произойдёт на медленной сети и как это работает с клавиатуры. Сервер описывают на уровне API, который нужен клиенту.

## Каркас RADIO

Каркас популяризировал GreatFrontEnd. Он не обязателен, но даёт разговору порядок — и интервьюер видит систему в мышлении:

```text
R — Requirements   что и для кого строим, что в приоритете, чего не делаем
A — Architecture    компоненты, их связи, поток данных, где живёт состояние
D — Data model      сущности на клиенте, серверное и локальное состояние
I — Interface       API клиент — сервер и API компонентов
O — Optimizations   производительность, сеть, доступность, краевые случаи
```

Сквозной пример — лента товаров маркетплейса с фильтрами и бесконечной прокруткой.

### R — требования

Сначала вопросы, потом проектирование. Требования делят на три группы:

- **функциональные** — что делает: лента карточек, фильтры, добавление в избранное. Нужна ли сортировка, поиск, офлайн?
- **нефункциональные** — масштаб, устройства, скорость сети, первый экран, доступность, языки;
- **границы** — чего не делаем: «оплату и личный кабинет не проектируем», «авторизация уже есть».

Хорошие вопросы меняют дизайн: если 70% пользователей с телефонов на медленной сети, важнее вес первого экрана, чем анимации; если нужна индексация поисковиками — нужен серверный рендеринг. Ответы записывают и потом на них ссылаются: «требовали работу на слабых телефонах — поэтому виртуализация».

### A — архитектура

Высокоуровневая структура: дерево компонентов, поток данных и где живёт состояние. Детали компонентного дизайна — в [Архитектуре компонентов](/content/architecture/component-architecture).

```text
FeedPage                      ← состояние фильтров в URL
├── Filters                   ← меняет URL
├── ProductList               ← данные: useFeed(filters) — серверный кеш
│   └── ProductCard × окно    ← виртуализация, видимые карточки
└── FavoriteButton            ← оптимистичное обновление
```

Здесь же решают, как рендерить: лента для поисковиков — серверный рендеринг первой страницы, остальное — на клиенте ([рендеринг и гидратация](/content/reactjs/rendering-and-hydration)).

### D — модель данных

Какие сущности на клиенте и где хранится каждое состояние: серверные данные — в кеше запросов, фильтры — в URL, открытая модалка — локально в компоненте. Нормализация, если одна сущность встречается в нескольких местах. Подробно — в [Архитектуре состояния и данных](/content/architecture/state-and-data-architecture).

```ts
type Product = { id: string; title: string; price: number; image: string; isFavorite: boolean };
type FeedPage = { items: Product[]; nextCursor: string | null };
type Filters = { category?: string; priceTo?: number; sort: 'popular' | 'cheap' };
```

### I — интерфейсы

Два интерфейса:

- **клиент — сервер:** эндпоинты, формат, пагинация (для ленты — курсор, а не номер страницы), реалтайм, ошибки ([API и BFF](/content/architecture/api-and-bff));
- **компонент — компонент:** пропсы, события, что компонент обещает снаружи.

```text
GET /feed?category=tea&sort=cheap&cursor=abc&limit=20
→ { items: Product[], nextCursor: "def" }
```

### O — оптимизации

Углубление в сквозные аспекты — туда, куда направит интервьюер: производительность рендеринга, сеть и кеш, доступность, состояния загрузки, ошибки и пустые ответы. Именно здесь пригодятся цифры.

## Оценки «на салфетке»

Бэкенд считает запросы в секунду и терабайты. У фронтенда свои количественные ориентиры — с ними решение звучит как инженерное, а не вкусовое.

### Бюджет кадра

Экран с частотой 60 Гц показывает кадр раз в 1000 / 60 ≈ 16,7 мс, со 120 Гц — раз в 8,3 мс. В этот интервал браузер должен успеть выполнить скрипт, пересчитать стили, раскладку и отрисовать. Если работа длиннее кадра, прокрутка и анимации дёргаются.

### DOM-узлы

Каждый узел — память, стили и раскладка. В проверке в Chromium таблица из 10 000 строк по четыре ячейки — 50 000 элементов — отрисовалась с раскладкой примерно за 200 мс, больше десяти кадров. Окно из 30 строк, которое рисует виртуализация, — 150 элементов и меньше миллисекунды. Отсюда решение для ленты: рисовать видимое окно с запасом, а не все загруженные карточки (как устроена виртуализация — в [таблицах и гридах](/content/ecosystem-libs/tables-and-grids)).

### Длинные задачи

Задачу дольше 50 мс браузер считает длинной: пока она идёт, клик и ввод ждут. В проверке одна непрерывная работа на 150 мс дала одну запись `longtask` в `PerformanceObserver`, а та же работа частями по 10 мс с возвратом управления между ними — ни одной. Решение — дробить тяжёлую обработку, переносить её в воркер или на сервер ([производительность выполнения](/content/security-perfomance/runtime-performance)).

### Раунд-трипы

Каждый последовательный запрос добавляет полный RTT, и на мобильной сети это стоит дороже трафика. В проверке с задержкой сервера 80 мс главная страница из четырёх запросов:

| Как загружать | Время |
|---------------|-------|
| последовательно, каждый ждёт предыдущий | ~330 мс — четыре RTT |
| по зависимостям: пользователь, затем его заказы и рекомендации параллельно, баннеры сразу | ~175 мс — два RTT |
| один агрегирующий запрос к BFF | ~80 мс — один RTT |

```js
await Promise.all([
  getMe().then((user) => Promise.all([getOrders(user.id), getRecommendations(user.id)])),
  getBanners(),
]);
```

На интервью это звучит так: «первый экран — не больше двух раунд-трипов, поэтому независимые запросы параллельно, а зависимые сводим в один через BFF».

### Вес и память

- **Вес первого экрана** — JS, CSS, шрифты и картинки на критическом пути. Бюджет называют явно и проверяют в CI ([CI/CD](/content/advanced-tooling/ci-cd)).
- **Данные** — 20 карточек по полкилобайта — около 10 КБ, но со всеми полями сущности — в разы больше. Отдавать только нужное — задача BFF.
- **Память** — бесконечная лента, кеш и чат растут без конца: сколько страниц держать, что вытеснять.

Точность не важна — важно, что за решением стоит порядок величины.

## Нефункциональное, которое легко забыть

Слабый ответ проектирует только успешный сценарий. Сильный проходит по сквозным осям хотя бы кратко, а в релевантные углубляется:

```text
Производительность · Доступность · Сеть и кеш · Состояние
Загрузка, ошибка, пустой ответ · Офлайн · Адаптивность
Безопасность · Локализация · Наблюдаемость
```

- **доступность** — управление с клавиатуры, фокус, роли и подписи для скринридеров;
- **локализация** — длинные строки, RTL, форматы дат и чисел, множественное число;
- **безопасность** — экранирование пользовательского контента, авторизация на сервере, а не скрытием кнопок;
- **наблюдаемость** — ошибки и метрики из продакшена, чтобы узнать о проблеме раньше пользователей;
- **состояния** — скелетон, повтор после ошибки, пустая выдача по фильтру, медленная сеть.

## Как вести разговор

- **Уточнять первым** — вопросы до рисования, ответы записать.
- **Думать вслух и по порядку** — шаги RADIO видны интервьюеру.
- **Вести самому** — не ждать вопросов, а предлагать следующий шаг: «теперь модель данных».
- **Называть компромиссы** — «курсор вместо номеров страниц: не будет дублей при новых товарах, но нельзя перейти на десятую страницу; для ленты это не нужно».
- **Следить за временем** — требования за несколько минут, затем вся картина крупно и только потом углубление туда, куда направит интервьюер. Час на одну кнопку — провал, даже если кнопка идеальна.

Разборы конкретных задач по этому каркасу — в [Примерах системного дизайна](/content/architecture/system-design-examples), формат раунда в целом — в [Техническом интервью](/content/preparing-for-interviews/technical-interview).

## Красные флаги в ответе

- Начать рисовать компоненты без единого уточняющего вопроса.
- Уйти в базы, шардинг и балансировщики вместо клиента.
- Один «правильный» вариант без альтернатив и цены.
- «Сделаем быстро» без цифр: ни бюджета кадра, ни числа запросов, ни объёма данных.
- Только успешный сценарий: нет загрузки, ошибок, пустых ответов, медленной сети.
- Доступность и локализация не упомянуты вовсе.
- Двадцать минут на детали одного компонента, а до данных и API дело не дошло.

## Как спрашивают на собеседовании

::question
Чем фронтенд-системный дизайн отличается от бэкенд-дизайна?

#answer
Бэкенд-дизайн — про серверы, хранилища, шардирование и распределённые системы. Фронтенд — про архитектуру компонентов, состояние, загрузку и кеширование данных на клиенте, стратегию рендеринга, производительность интерфейса, доступность и UX. Сервер описывают на уровне API, который нужен клиенту.

#more
Метрики тоже свои: не запросы в секунду, а время до первого экрана, бюджет кадра, число раунд-трипов, вес критического пути. Требования вроде «слабые телефоны» или «индексация поисковиками» меняют дизайн сильнее, чем число пользователей.
::

::question
Какой каркас использовать на системном дизайне?

#answer
RADIO: Requirements — уточнить функциональные и нефункциональные требования и границы, Architecture — компоненты и поток данных, Data model — сущности и где живёт каждое состояние, Interface — API клиент — сервер и между компонентами, Optimizations — производительность, сеть, доступность, краевые случаи.

#more
Каркас нужен, чтобы вести разговор и ничего не забыть, а не чтобы проговорить пять букв. Шаги можно совмещать и возвращаться к ним. Лучше всего каркас работает, когда каждое решение на следующих шагах ссылается на требование из первого.
::

::question
С чего начинать ответ?

#answer
С уточнения требований: кто пользователи, какие устройства и сеть, масштаб, что в приоритете, нужна ли индексация, офлайн, локализация — и что явно вне задачи. Ответы записать, они станут основанием для решений.

#more
Хороший вопрос меняет дизайн: если важна индексация — серверный рендеринг первой страницы, если пользователи на слабых телефонах — виртуализация и меньший бандл. Отрезать лишнее так же важно: «оплату не проектируем» экономит время на то, что оценивают.
::

::question
Какие аспекты всегда стоит проговорить?

#answer
Производительность, доступность, сеть и кеш, состояние, загрузку, ошибки и пустые ответы, адаптивность, безопасность, локализацию и наблюдаемость. Глубоко — в релевантные для задачи, остальные хотя бы упомянуть.

#more
По этим осям видна широта: кандидат, который сам вспомнил про фокус в модалке, медленную сеть и пустую выдачу по фильтру, выглядит человеком, который выпускал такое в продакшен. Безопасность на клиенте — экранирование контента, а права проверяет сервер.
::

::question
Что оценивают на системном дизайне?

#answer
Не правильный ответ — его нет, — а структурированное мышление, покрытие аспектов и обсуждение компромиссов: какие есть варианты, чего стоит каждый и почему выбран этот при данных требованиях.

#more
Ещё оценивают, как кандидат ведёт разговор: задаёт вопросы, распределяет время, принимает подсказки интервьюера и меняет решение при новых требованиях. Хорошая фраза: «вариант A даёт X ценой Y; при этих требованиях беру A, а если появится Z — перейду на B».
::

::question
Как количественно обосновать решения?

#answer
Оценками порядка величины: кадр 16,7 мс при 60 Гц, задача дольше 50 мс блокирует ввод, тысячи DOM-узлов не укладываются в кадр, каждый последовательный запрос добавляет RTT, вес первого экрана сравнивают с бюджетом.

#more
Например: 10 000 строк — это 50 000 элементов и сотни миллисекунд отрисовки, поэтому виртуализация; четыре последовательных запроса по 80 мс — это 320 мс до данных, а по зависимостям — два RTT, через BFF — один. Точность не важна, важно, что за решением стоит расчёт.
::

## Практика

::practice{title="Главная страница долго показывает данные"}
Главная загружает пользователя, его заказы, рекомендации и баннеры. Сервер отвечает за 80 мс, но данные появляются только через треть секунды. Код:

```js
const user = await getMe();
const orders = await getOrders(user.id);
const recs = await getRecommendations(user.id);
const banners = await getBanners();
```

#solution
Каждый `await` ждёт предыдущий запрос, хотя от пользователя зависят только заказы и рекомендации, а баннеры не зависят ни от чего. В проверке так набралось около 330 мс — четыре RTT. Запросы строят по зависимостям:

```js
const [[orders, recs], banners] = await Promise.all([
  getMe().then((user) => Promise.all([getOrders(user.id), getRecommendations(user.id)])),
  getBanners(),
]);
```

Это два RTT — около 175 мс в проверке. Если и этого много, BFF собирает главную одним запросом — один RTT, около 80 мс. На медленной мобильной сети с RTT 300 мс разница между четырьмя и одним раунд-трипом — почти секунда.
::

::practice{title="Спроектируйте ленту товаров"}
На интервью просят спроектировать ленту маркетплейса: карточки с фото и ценой, фильтры, бесконечная прокрутка, кнопка «в избранное». Как построить ответ?

#solution
По шагам RADIO, каждый раз ссылаясь на требования:

```text
R  мобильные, медленная сеть, индексация первой страницы; оплату не проектируем
A  FeedPage → Filters, ProductList → ProductCard, FavoriteButton
   первая страница — серверный рендеринг, дальше — клиент
D  серверный кеш страниц ленты, фильтры в URL, избранное — оптимистично
I  GET /feed?…&cursor=…&limit=20 → { items, nextCursor }
O  виртуализация, ленивые картинки с размерами, предзагрузка следующей страницы,
   скелетон, повтор при ошибке, пустая выдача, фокус и клавиатура
```

Цифры: 20 карточек на страницу; после сотни прокруток в DOM были бы тысячи карточек — поэтому окно с запасом. Курсор вместо номера страницы — новые товары сверху не дают дублей. Подробные разборы ленты, чата и автокомплита — в [Примерах системного дизайна](/content/architecture/system-design-examples).
::
