# Архитектура состояния и данных

Архитектурный взгляд на состояние: какие бывают виды состояния и где каждый живёт, слой данных между компонентами и API, где держать бизнес-логику, один источник истины и производные значения, нормализация, автоматы состояний вместо флагов, команды и журнал событий, кеш как часть архитектуры. Спрашивают, как организовать состояние в большом приложении, зачем отделять слой данных и где должна жить логика. Глубже — почему три булева флага дают восемь сочетаний из которых осмысленны четыре, почему переименованный товар остался старым в корзине и как сделать отмену действий.

::tldr
- **Сначала классифицировать:** локальное состояние интерфейса — в компоненте, данные с сервера — в кеше библиотеки загрузки, общее клиентское — в сторе или контексте, фильтры и страница — в URL, ввод формы — в библиотеке форм.
- **Большая часть «состояния» — это кеш данных сервера.** Когда его выносят в отдельный слой, глобального клиентского состояния остаётся мало.
- **Компоненты не знают про API:** слой данных скрывает адреса, формат и транспорт за функциями и хуками. Бизнес-правила — в функциях и сценариях, а не в компонентах.
- **Один источник истины на каждый факт:** производное вычисляют, сущности хранят нормализованно по идентификатору — тогда изменение видят все списки.
- **Сложные процессы — автоматами состояний,** а не набором флагов: невозможные сочетания и переходы просто не существуют. Отмена и история — через команды и журнал событий.
::

## Виды состояния

Сквозной пример — магазин: открытое меню, каталог с сервера, корзина, фильтры каталога, форма оформления заказа.

| Вид | Пример | Где живёт |
| --- | --- | --- |
| локальное интерфейса | открыто ли меню, наведение | в компоненте |
| данные сервера | каталог, заказы, профиль | кеш библиотеки загрузки: TanStack Query, SWR, Pinia Colada |
| общее клиентское | тема, корзина до оформления, авторизация | стор или контекст |
| состояние адреса | фильтры, сортировка, страница, выбранный товар | URL |
| ввод формы | поля оформления заказа | библиотека форм или локальное состояние |

Ошибка, с которой начинаются проблемы, — смешать данные сервера с клиентским состоянием: класть каталог в общий стор и вручную вести загрузку, ошибки и обновление. Библиотеки серверного состояния делают это кешем с инвалидацией, повторами и дедупликацией (подробно — в [Состоянии и данных](/content/ecosystem-libs/state-and-data-libraries)). После этого в общем сторе остаются тема, авторизация и немного флагов интерфейса — и вопрос «нужен ли Redux» часто решается сам.

### Состояние в адресе

Фильтры, сортировка и страница — часть адреса: ссылка открывает тот же вид, кнопка «Назад» возвращает прежний, а перезагрузка ничего не теряет. В проверке фильтры `{ q: 'пуэр', category: 'tea', page: 2 }` превратились в адрес без значений по умолчанию и обратно — в тот же объект:

```js
toUrl(filters);   // 'q=%D0%BF%D1%83%D1%8D%D1%80&category=tea&page=2'
fromUrl(qs);      // { q: 'пуэр', category: 'tea', sort: 'popular', page: 2 }
```

Маршрутизаторы и библиотеки вроде nuqs и TanStack Router дают для этого типизированные помощники (подробно — в [Маршрутизации React](/content/reactjs/routing)).

## Слой данных

Компоненты не должны знать, по какому адресу и в каком формате приходят данные:

```jsx
// компонент знает про API
fetch('/api/v2/products?category=tea&active=true').then((r) => r.json()).then(setProducts);

// компонент знает только, что ему нужно
const { data: products } = useProducts({ category: 'tea' });
```

Слой данных — это шаблон **репозитория**: функции и хуки, за которыми спрятаны адреса, версия API, преобразование ответа и кеш. Переход с REST на GraphQL или переименование поля правится в одном месте, а не в сотне компонентов. Типы и проверка ответа на этой границе — в [Сквозной типобезопасности](/content/modern-dev/end-to-end-typesafety), сам API для фронтенда — в [API и BFF](/content/architecture/api-and-bff).

## Где живёт логика

Бизнес-правила — в функциях, хуках и сценариях, а компонент только показывает результат:

```js
const total = cartTotal(items, promo);   // чистая функция, тестируется без рендера
```

Так правило переиспользуется в корзине, письме и чеке, а тестируется одной строкой. Сложные сценарии — оформление заказа с оплатой — выносят целиком, передавая внешний мир адаптерами (подробно — в [Архитектурных паттернах](/content/architecture/architectural-patterns)).

## Один источник истины

- **у каждого факта один владелец** — цена товара хранится в одном месте, а не копируется в корзину и заказ;
- **производное вычисляют** — сумма корзины считается из позиций, а не хранится рядом с ними (подробно — в [Производном состоянии React](/content/reactjs/derived-state-and-data-flow));
- **данные текут однонаправленно** — вниз пропсами, изменения — действиями.

### Нормализация

Если один и тот же товар лежит копиями в каталоге, корзине и избранном, после изменения копии расходятся. В проверке переименование товара в «каталоге» оставило в «корзине» старое название.

Нормализация хранит сущность один раз по идентификатору, а списки — только идентификаторы:

```js
const products = createEntityAdapter();   // Redux Toolkit
// состояние: { ids: [7, 8], entities: { 7: {…}, 8: {…} }, catalogIds: [7, 8], cartIds: [7] }
```

В проверке с Redux Toolkit после переименования товара 7 и каталог, и корзина показали «Шу пуэр»: они читают одну запись. Нормализованные кеши GraphQL-клиентов делают то же самое автоматически по `__typename` и `id`; документные кеши вроде TanStack Query хранят ответы целиком и решают задачу инвалидацией по ключам (подробно — в [Состоянии и данных](/content/ecosystem-libs/state-and-data-libraries)).

### Как близко к месту использования

Состояние держат как можно ниже и поднимают, только когда его нужно разделить:

```text
слишком высоко   лишние перерисовки, передача пропсов через несколько уровней
слишком низко    нельзя разделить между компонентами
в самый раз      ближайший общий родитель тех, кому оно нужно
```

## Автоматы состояний

Три булева флага — `isLoading`, `isError`, `isSuccess` — дают 8 сочетаний. В проверке осмысленных оказалось 4: остальные — «загрузка и ошибка одновременно» и подобные, — и каждая такая комбинация когда-нибудь появляется на экране из-за забытого сброса флага.

**Автомат состояний** описывает состояния и разрешённые переходы явно:

```js
const checkout = createMachine({
  initial: 'cart',
  states: {
    cart: { on: { NEXT: 'shipping' } },
    shipping: { on: { NEXT: 'payment', BACK: 'cart' } },
    payment: { on: { PAY: 'paying', BACK: 'shipping' } },
    paying: { on: { SUCCESS: 'paid', FAILURE: 'payment' } },
    paid: { type: 'final' },
  },
});
```

В проверке на XState событие «оплатить» из корзины ничего не сделало — такого перехода нет, — а второе «оплатить» во время оплаты тоже было проигнорировано: двойной клик не создаёт двух платежей. Для менее сложных случаев хватает размеченного объединения в TypeScript — `{ status: 'loading' } | { status: 'error', error } | { status: 'success', data }`, — которое тоже делает невозможные сочетания невыразимыми.

## Команды и журнал событий

### Команды

Действие оформляют объектом, который умеет выполниться и откатиться. В проверке две смены цены — 1100, затем 990 — отменились и повторились по порядку, а две отмены вернули исходные 1200:

```js
const setPrice = (id, price) => {
  let prev;
  return { do: (s) => { prev = s[id]; return { ...s, [id]: price }; }, undo: (s) => ({ ...s, [id]: prev }) };
};
```

Это основа отмены и повтора в редакторах, очередей офлайн-действий и пакетной отправки изменений.

### Журнал событий

Вместо текущего состояния хранят **события**, а состояние получают их свёрткой. В проверке журнал «добавлен 7 — добавлен 8 — изменено количество 7 — удалён 8» дал корзину `{ 7: 3 }`, а первые два события — состояние на тот момент. Это история и аудит из коробки: видно, кто и когда удалял. Так устроены совместные редакторы и local-first синхронизация (подробно — в [Local-first приложениях](/content/modern-dev/local-first-software)). Цена — журнал растёт, поэтому периодически сохраняют снимок состояния.

## Кеш как архитектура

Стратегия кеша — архитектурное решение, а не настройка библиотеки:

- **что источник истины** — сервер, а клиент держит копию с понятным сроком свежести;
- **когда данные устаревают** — время, события, мутации;
- **как синхронизировать** — инвалидация, обновление ответом мутации, подписка на изменения;
- **оптимистичные изменения** — показать сразу и откатить при ошибке (подробно — в [Загрузке данных React](/content/reactjs/data-fetching)).

---

## Красные флаги в ответе

- **«Всё положим в глобальный стор».** Данные сервера — в кеш библиотеки, локальное — в компонент, фильтры — в URL.
- **«Компонент сам сходит по адресу API».** Смена API потребует правки сотни компонентов.
- **«Сумму корзины храним рядом с позициями».** Производное значение расходится с источником.
- **«Скопируем товар в корзину».** После изменения копии разойдутся — храним идентификатор.
- **«`isLoading`, `isError`, `isSuccess` — три флага».** Половина сочетаний невозможна, но достижима.
- **«Фильтры в состоянии компонента».** Ссылка и кнопка «Назад» перестают работать.

## Как спрашивают на собеседовании

::question
Как организовать состояние в большом приложении?

#answer
Классифицировать: локальное интерфейса — в компоненте, данные сервера — в кеше библиотеки загрузки, общее клиентское — в сторе или контексте, фильтры и навигация — в URL, ввод — в библиотеке форм. Большую часть «состояния» составляет кеш сервера, его выносят первым.

#more
После этого глобального состояния остаётся мало — тема, авторизация, корзина, — и тяжёлый стор часто не нужен. Состояние держат как можно ближе к месту использования.
::

::question
Зачем отделять слой данных от компонентов?

#answer
Чтобы компоненты не знали адреса, формат и транспорт API. Слой данных — функции и хуки вроде `useProducts` — скрывает детали, и смена API правится в одном месте.

#more
На этой же границе проверяют ответ схемой и преобразуют формат сервера в удобный интерфейсу. Слой легко подменить в тестах и Storybook.
::

::question
Что такое нормализация состояния и зачем она?

#answer
Хранить сущности один раз по идентификатору, а в списках — только идентификаторы. Тогда изменение сущности видят все места, где она показана, и копии не расходятся.

#more
В Redux Toolkit для этого есть `createEntityAdapter`, нормализованные кеши GraphQL-клиентов делают это автоматически. Документные кеши решают ту же задачу инвалидацией связанных запросов.
::

::question
Где должна жить бизнес-логика?

#answer
В функциях, хуках и сценариях вне компонентов. Компонент показывает результат и отправляет действия.

#more
Чистые функции правил тестируются без рендера и переиспользуются в разных местах — корзина, письмо, чек. Сложные сценарии получают внешний мир адаптерами.
::

::question
Когда использовать автомат состояний?

#answer
Для процессов с явными шагами и переходами — оформление заказа, мастер, плеер, загрузка с повторами, — где важно, чтобы невозможные сочетания и переходы не существовали.

#more
Набор флагов допускает противоречия: из трёх булевых флагов осмысленны четыре сочетания из восьми. Автомат или размеченное объединение делают их невыразимыми, а лишние события — например, двойной клик «Оплатить» — просто игнорируются.
::

::question
Как реализовать отмену действий?

#answer
Командами: каждое действие — объект с выполнением и откатом, история — стек выполненных и стек отменённых. Или журналом событий, где состояние — свёртка событий до нужного момента.

#more
Для неизменяемого состояния проще всего хранить снимки или патчи Immer. Новое действие после отмены очищает стек повтора.
::

## Практика

::practice{title="Старое название в корзине"}
Менеджер переименовал товар в админке. В каталоге новое название, а в корзине и избранном — старое, пока не перезагрузишь страницу. Товар при добавлении копируется в массив корзины целиком.

#solution
Копии расходятся. В проверке переименование в каталоге оставило в корзине старое название. Хранят сущность один раз, а в корзине — идентификаторы:

```js
const products = createEntityAdapter();
const slice = createSlice({
  name: 'products',
  initialState: products.getInitialState({ cartIds: [] }),
  reducers: {
    addToCart: (state, { payload: id }) => { state.cartIds.push(id); },
    renamed: (state, { payload: { id, title } }) => { products.updateOne(state, { id, changes: { title } }); },
  },
});

const cartItems = (state) => state.products.cartIds.map((id) => state.products.entities[id]);
```

В проверке после переименования и каталог, и корзина показали новое название. Если товары — данные сервера в TanStack Query, то же решают инвалидацией: корзина хранит идентификаторы и количество, а данные товара читаются из кеша по ключу.
::

::practice{title="Двойная оплата"}
В оформлении заказа состояние описано флагами `isSubmitting`, `isPaid`, `hasError`. Пользователи иногда видят одновременно «Ошибка оплаты» и «Заказ оплачен», а быстрый двойной клик создаёт два платежа.

#solution
Флаги допускают противоречия, и никто не запрещает повторную отправку. Автомат описывает разрешённые переходы:

```js
const checkout = createMachine({
  initial: 'payment',
  states: {
    payment: { on: { PAY: 'paying' } },
    paying: { invoke: { src: 'charge', onDone: 'paid', onError: 'failed' } },
    failed: { on: { RETRY: 'paying' } },
    paid: { type: 'final' },
  },
});
```

В проверке второе событие «оплатить» во время оплаты было проигнорировано, а оплата из корзины без перехода к оплате — невозможна. Сервер дополнительно защищается ключом идемпотентности: повторный запрос с тем же ключом не создаёт второй платёж.
::
