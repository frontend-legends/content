# Архитектура состояния и данных

На уровне приложения главные вопросы - **где живёт состояние**, **как текут данные** и **где находится логика**. Плохие ответы рождают prop drilling, рассинхрон и компоненты, набитые бизнес-логикой. Это архитектурный взгляд на то, что в [React](/content/reactjs/state-management)/[Vue](/content/vuejs/state-management) разбиралось механически.

---

## Таксономия состояния

Архитектура начинается с классификации - разные типы живут в разных местах:

| Тип | Где живёт |
|-----|-----------|
| **Local UI** | в компоненте (`useState`) |
| **Server state** | кеш данных (React Query/SWR) |
| **Global client** | стор/контекст (тема, юзер) |
| **URL state** | роутер (фильтры, страница) |

<b class="text-on-semi-light">Главный архитектурный инсайт</b> - <span class="text-gray">Большая часть «состояния» - это **серверные данные** (кеш), а не состояние приложения. Спутать их - корень многих проблем: ручное ведение loading/error в сторе вместо кеширующей библиотеки. Сначала вынеси server state в кеш-слой, и «глобального состояния» останется мало.</span>

---

## Слой данных

Ключ к чистой архитектуре - **отделить доступ к данным от UI**. Компоненты не должны знать про эндпоинты и формат API.

```jsx
// ❌ компонент знает про API напрямую
fetch('/api/v2/users?active=true').then(...)

// ✅ слой данных скрывает детали за понятным интерфейсом
const { data } = useActiveUsers();   // компонент не знает про URL, версию, формат
```

Это аналог **repository pattern**: слой между приложением и источником данных. Меняешь API (URL, REST→GraphQL) - правишь один слой, не сотни компонентов.

---

## Где живёт логика

Бизнес-логику держат **вне** компонентов - в хуках, сервисах, доменном слое. Компонент отвечает за отображение, а не за правила.

```jsx
// ❌ логика расчёта скидки внутри компонента
// ✅ логика в функции/хуке, компонент только показывает результат
const total = calculateTotal(cart);  // чистая тестируемая логика отдельно
```

Это и есть [разделение ответственности](/content/architecture/architectural-thinking): UI - тонкий, логика - переиспользуема и тестируема без рендера.

---

## Поток данных

Архитектурные принципы потока:

- **Однонаправленность** - данные вниз, события вверх ([Flux](/content/architecture/architectural-patterns)).
- **Single source of truth** - у каждого куска данных один владелец.
- **Производное состояние** - вычисляй из существующего, не дублируй ([производное состояние](/content/reactjs/derived-state-and-data-flow)).

---

## Нормализация

Для реляционных данных в сторе/кеше - **нормализация**: хранить плоско по `id`, а не вложенными копиями.

```js
// ❌ дублирование: один user в десяти местах → рассинхрон
posts: [{ id, author: { id, name } }, ...]

// ✅ нормализовано: ссылки по id, объект в одном месте
users: { 1: { id: 1, name } },
posts: [{ id, authorId: 1 }]
```

<b class="text-on-semi-light">Зачем</b> - <span class="text-gray">Если один объект (юзер) лежит копиями в разных местах, обновить его согласованно трудно - возникает рассинхрон. Нормализация (хранить по id, ссылаться по id) даёт один источник истины для каждой сущности. Так устроены нормализованные кеши Redux и Apollo.</span>

---

## Колокация vs глобальное

Архитектурное правило: **держи состояние как можно ниже**, поднимай только когда нужно делить.

```
Слишком высоко → лишние ререндеры, prop drilling
Слишком низко  → нельзя разделить
Правильно      → ближайший общий родитель тех, кому нужно
```

Глобальный стор - не для всего, а для действительно общего и часто меняющегося. Подробнее - [производное состояние](/content/reactjs/derived-state-and-data-flow).

---

## Сложные потоки - state machines

Для состояний со сложными переходами (визард, плеер, чекаут) - **конечные автоматы** ([XState](/content/reactjs/state-management)): явные состояния и переходы исключают невозможные комбинации (нельзя «оплачено» без «подтверждено»). Архитектурно надёжнее, чем россыпь булевых флагов.

---

## Кеширование как архитектура

Стратегия кеша - часть архитектуры данных: что кешировать, на сколько (`staleTime`), когда инвалидировать, оптимистичные обновления. Это решает [React Query/SWR](/content/reactjs/data-fetching), но **решения** (где источник истины, как синхронизировать) - архитектурные.

---

## Server-state изменил архитектуру данных

Главный сдвиг последних лет: раньше серверные данные тащили в глобальный стор (Redux) и вручную вели loading/error. Теперь **server-state - отдельный слой** (React Query/SWR) с кешем, инвалидацией, дедупликацией.

<b class="text-on-semi-light">Архитектурное следствие</b> - <span class="text-gray">После выноса server-state в кеш-слой **глобального client-state почти не остаётся** - тема, юзер, UI-флаги. Поэтому «нужен ли Redux» в 2026 чаще «нет»: server-cache + немного контекста/Zustand. Это переосмысление того, что вообще считать «состоянием приложения».</span>

---

## Команды, события и оптимистичность

Для сложных доменов применяют идеи из бэкенда:

- **Command pattern** - действие как объект (что сделать), отделённое от исполнения; удобно для undo/redo, очередей, оффлайна.
- **Event sourcing** (облегчённо) - хранить **поток событий**, а не только текущее состояние; состояние - свёртка событий. Даёт историю, undo, аудит (так работают коллаборативные редакторы, [local-first](/content/modern-dev/local-first-software)).
- **Оптимистичная конкурентность** - применять изменение локально сразу, разрешать конфликты при синхронизации (версии, CRDT).

## Вопросы на собеседовании

<b class="text-on-semi-light">Как организовать состояние в большом приложении?</b>
<span class="text-gray">Классифицировать: local UI → в компоненте, server state → кеш (React Query), global client → стор/контекст, URL state → роутер. Большая часть «состояния» - серверный кеш, его выносят первым.</span>

<b class="text-on-semi-light">Зачем отделять слой данных от компонентов?</b>
<span class="text-gray">Чтобы компоненты не знали про эндпоинты и формат API. Слой данных (repository) скрывает детали; смена API правится в одном месте, а не в сотнях компонентов. Плюс логику легче тестировать.</span>

<b class="text-on-semi-light">Что такое нормализация состояния и зачем она?</b>
<span class="text-gray">Хранить реляционные данные плоско по id, ссылаясь по id, а не вложенными копиями. Даёт один источник истины для каждой сущности и избегает рассинхрона при обновлении. Так устроены кеши Redux/Apollo.</span>

<b class="text-on-semi-light">Где должна жить бизнес-логика?</b>
<span class="text-gray">Вне компонентов - в хуках, сервисах, доменном слое. Компонент отвечает за отображение. Логика отдельно переиспользуема и тестируема без рендера.</span>

<b class="text-on-semi-light">Когда использовать конечный автомат для состояния?</b>
<span class="text-gray">Для сложных потоков с явными переходами (визард, плеер, чекаут), где важно исключить невозможные комбинации. State machine надёжнее россыпи булевых флагов.</span>

<b class="text-on-semi-light">Как server-state изменил архитектуру состояния?</b>
<span class="text-gray">Серверные данные вынесли в отдельный кеш-слой (React Query/SWR) с инвалидацией и дедупликацией. После этого глобального client-state почти не остаётся - часто Redux не нужен, хватает server-cache + контекст/Zustand.</span>
