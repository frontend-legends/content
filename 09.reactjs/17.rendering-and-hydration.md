# Стратегии рендеринга и гидратация

Где формируется HTML - в браузере или на сервере - определяет скорость первой загрузки, SEO и сложность приложения. Это большая senior-тема, и почти всегда за ней следует вопрос про **гидратацию**.

---

## Четыре стратегии

| | Когда генерируется HTML | Плюсы | Минусы |
|--|--------------------------|-------|--------|
| **CSR** | в браузере, после загрузки JS | просто, дёшево, SPA-навигация | пустой экран до JS, слабый SEO, медленный FCP |
| **SSR** | на сервере, на каждый запрос | быстрый контент, SEO, свежие данные | нагрузка на сервер, нужна гидратация |
| **SSG** | заранее, при сборке | максимально быстро, дёшево (CDN) | данные «застывают», долгая сборка на больших сайтах |
| **ISR** | при сборке + перегенерация по триггеру/интервалу | свежесть SSG + скорость CDN | привязка к платформе (Next.js) |

---

## CSR - client-side rendering

Сервер отдаёт почти пустой `index.html` и бандл. React строит весь UI в браузере.

```html
<body>
  <div id="root"></div> <!-- пусто, пока не загрузится и не выполнится JS -->
  <script src="/bundle.js"></script>
</body>
```

<b class="text-on-semi-light">Минусы</b> - <span class="text-gray">Пользователь видит белый экран, пока грузится и парсится JS. Поисковики хуже индексируют пустой HTML. Плохие метрики FCP/LCP на слабых устройствах.</span> Подходит для приложений за авторизацией (дашборды), где SEO не важен.

---

## SSR - server-side rendering

Сервер выполняет React и отдаёт **готовый HTML**. Пользователь сразу видит контент, затем подгружается JS и «оживляет» страницу.

```
запрос → сервер рендерит React в HTML строку → браузер показывает HTML (быстрый FCP)
       → грузится JS → гидратация → страница интерактивна
```

Быстрее «первый экран» и лучше SEO ценой нагрузки на сервер и необходимости гидратации.

---

## SSG и ISR

- **SSG** - HTML генерируется **на этапе сборки**, раздаётся с CDN. Идеален для контента, который меняется редко: блоги, доки, лендинги.
- **ISR** (Incremental Static Regeneration, Next.js) - страница статическая, но **перегенерируется** в фоне по интервалу или по требованию. Свежесть без полной пересборки сайта.

---

## Гидратация

**Гидратация** - процесс «оживления» серверного HTML на клиенте. React не перерисовывает разметку заново, а **проходит по существующему DOM**, строит дерево фиберов и **навешивает обработчики событий**.

```jsx
import { hydrateRoot } from 'react-dom/client';
hydrateRoot(document.getElementById('root'), <App />); // не render, а hydrate
```

До гидратации HTML виден, но **не интерактивен** - клики не работают. Это «зловещая долина»: контент есть, а кнопки ещё мертвы.

### Hydration mismatch

Главный класс багов SSR. React ожидает, что HTML с сервера **в точности совпадёт** с тем, что отрендерит клиент при первом проходе. Если нет - hydration error.

```jsx
// ❌ сервер и клиент дадут разный HTML → mismatch
<span>{new Date().toLocaleTimeString()}</span>
<span>{Math.random()}</span>
{typeof window !== 'undefined' && <ClientOnly />}
```

Причины: время/случайность, обращение к `window`/`localStorage` при рендере, неверная HTML-вложенность (`<div>` внутри `<p>`), расширения браузера. Лечение - выносить такое в эффект (`useEffect` запускается только на клиенте) или паттерн «mounted».

<b class="text-on-semi-light">Цена гидратации</b> - <span class="text-gray">Чтобы навесить обработчики, клиенту нужно выполнить тот же JS-компонентов, что и на сервере. То есть код фактически «рендерится дважды». Поэтому SSR ускоряет FCP, но не TTI (время до интерактивности) - и именно эту проблему решают RSC и стриминг.</span>

---

## Streaming SSR

React 18 умеет отдавать HTML **потоком** (`renderToPipeableStream`) и не ждать готовности всей страницы. Медленные части оборачивают в `<Suspense>` - на их месте сразу уходит fallback, а реальный контент **дострименивается** позже.

```jsx
<Suspense fallback={<Skeleton />}>
  <SlowComments />  {/* приедет потоком, когда будет готово */}
</Suspense>
```

Это даёт и **selective hydration**: React гидратирует готовые куски, не дожидаясь медленных, и приоритизирует те, с которыми пользователь взаимодействует.

---

## Как выбрать

- **Контент-сайт, блог, лендинг, доки** → SSG/ISR.
- **Главная, каталог, страница товара** (SEO + свежесть) → SSR / RSC.
- **Дашборд за логином**, SEO не нужен → CSR (или SSR ради скорости).
- На практике страницы **смешивают** стратегии - это и предлагают мета-фреймворки.

> Руками всё это редко настраивают - используют **Next.js** или **Remix**: роутинг, выбор стратегии на уровне страницы, серверная загрузка данных из коробки.

Логичное продолжение SSR - **React Server Components**, которые меняют саму модель: часть компонентов вообще не попадает в браузер. Об этом - в [RSC и React 19](/content/reactjs/rsc-and-react-19).

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем CSR отличается от SSR?</b>
<span class="text-gray">CSR строит HTML в браузере (пустой экран до JS, слабый SEO). SSR отдаёт готовый HTML с сервера (быстрый контент, SEO), но требует гидратации.</span>

<b class="text-on-semi-light">Что такое гидратация?</b>
<span class="text-gray">Процесс, в котором React на клиенте проходит по серверному HTML, строит дерево и навешивает обработчики, делая статичную разметку интерактивной.</span>

<b class="text-on-semi-light">Что такое hydration mismatch и почему он возникает?</b>
<span class="text-gray">Серверный HTML не совпал с первым клиентским рендером (время, random, window, неверная вложенность тегов). React ругается и может перерисовать поддерево. Лечится выносом в эффект.</span>

<b class="text-on-semi-light">Почему SSR ускоряет FCP, но не TTI?</b>
<span class="text-gray">Контент виден сразу, но для интерактивности клиент должен выполнить тот же JS (гидратация) - код по сути рендерится дважды.</span>

<b class="text-on-semi-light">Чем SSG отличается от ISR?</b>
<span class="text-gray">SSG генерирует HTML при сборке и он застывает. ISR перегенерирует страницы в фоне по интервалу/триггеру - свежесть без полной пересборки.</span>

<b class="text-on-semi-light">Что даёт streaming SSR?</b>
<span class="text-gray">HTML отдаётся потоком; медленные части в Suspense заменяются fallback и дострименивается позже, плюс selective hydration по готовности и приоритету.</span>
