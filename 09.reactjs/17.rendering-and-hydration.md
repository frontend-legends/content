# Рендеринг и гидратация

Где формируется HTML — в браузере, на сервере при запросе или заранее при сборке — и как серверная разметка становится интерактивной. Спрашивают разницу CSR и SSR и что такое гидратация. Глубже — что React делает при расхождении серверного и клиентского HTML, почему SSR ускоряет первый экран, но не интерактивность, как работают стриминг и выборочная гидратация и зачем нужен `useId`.

::tldr
- **Стратегия рендера — это вопрос «где и когда создаётся HTML»:** в браузере (CSR), на сервере при каждом запросе (SSR), при сборке (SSG) или при сборке с фоновым обновлением (ISR). Разные страницы одного приложения могут использовать разные стратегии.
- **Гидратация — подключение React к готовому HTML.** React не пересоздаёт разметку: он заново рендерит компоненты, сверяет результат с DOM и вешает обработчики. До этого страница видна, но не реагирует.
- **Первый клиентский рендер должен совпасть с серверным.** При расхождении текста React бросает ошибку гидратации и рендерит поддерево заново на клиенте. При расхождении атрибутов — только предупреждает, а в DOM остаётся серверное значение.
- **SSR ускоряет первый экран, но не интерактивность:** чтобы гидратировать, браузер должен загрузить и выполнить код тех же компонентов. Стриминг и выборочная гидратация через `Suspense` убирают ожидание самого медленного куска.
- **`useId` даёт одинаковые id на сервере и клиенте**, потому что строит их по позиции в дереве, а не по счётчику.
::

## Где создаётся HTML

Сквозной пример — страница товара: название и цена, отзывы с медленного сервиса, кнопка «в корзину» и блок «вы недавно смотрели» из `localStorage`.

| Стратегия | Когда создаётся HTML | Сильные стороны | Слабые стороны |
| --- | --- | --- | --- |
| CSR | в браузере, после загрузки JS | простой хостинг, быстрые переходы | пустой экран до загрузки JS, хуже SEO и LCP |
| SSR | на сервере, на каждый запрос | контент сразу, свежие данные, SEO | нагрузка на сервер, нужна гидратация |
| SSG | при сборке | быстрее всего, раздаётся с CDN | данные «застывают» до следующей сборки |
| ISR | при сборке, плюс перегенерация в фоне | скорость SSG и свежесть по таймеру или событию | зависит от платформы, данные могут отставать |

**CSR** — сервер отдаёт пустой `<div id="root">` и бандл, а интерфейс строит React в браузере. Пока JS не загрузится и не выполнится, пользователь видит пустой экран. Это нормально для кабинета за авторизацией, где :term[SEO]{def="поисковая оптимизация: как сделать страницу понятной поисковым системам"} не важен.

**SSR** — сервер выполняет компоненты и отдаёт готовый HTML. Страница товара видна сразу, поисковик получает текст, а данные всегда свежие. Цена — сервер на каждый запрос и гидратация на клиенте.

**SSG** — HTML собирают заранее и кладут на CDN. Подходит для документации, блога, лендингов. Страница товара с меняющейся ценой — нет: цена «застынет» до следующей сборки.

**ISR** — компромисс: страница статическая, но фреймворк перегенерирует её в фоне по интервалу или по событию (товар изменили в админке). Посетитель всегда получает быстрый HTML с CDN, а свежесть отстаёт на время перегенерации.

Выбор делают по страницам, а не для всего приложения: главная и каталог — SSG или ISR, карточка товара — SSR, корзина и кабинет — клиентский рендер внутри серверного макета. Фреймворки (Next.js, React Router в режиме фреймворка) дают выбирать это на уровне маршрута.

Все стратегии, кроме CSR, отдают готовый HTML. Но HTML без JavaScript — это картинка: кнопка «в корзину» не работает. Её нужно оживить.

## Гидратация

Гидратация — процесс, в котором React подключается к HTML, пришедшему с сервера:

```jsx
import { hydrateRoot } from 'react-dom/client';

hydrateRoot(document.getElementById('root'), <ProductPage product={product} />);
```

`hydrateRoot` вместо `createRoot` говорит React: разметка уже есть, не создавай её заново. React рендерит компоненты как обычно, но вместо создания DOM-узлов идёт по существующим, связывает их с fiber и вешает обработчики событий. В проверке после гидратации кнопка осталась тем же DOM-узлом, а клик по ней до гидратации ничего не делал.

Отсюда главное следствие: **SSR ускоряет первый экран, но не интерактивность.** Чтобы гидратировать страницу, браузер должен скачать, разобрать и выполнить код всех её компонентов — тех же, что уже выполнил сервер. На медленном телефоне между «страница видна» и «кнопка работает» могут пройти секунды. Пользователь нажимает «в корзину» — и ничего не происходит.

Чтобы гидратация работала, у неё есть одно жёсткое условие.

## Первый рендер должен совпасть

React ожидает, что первый рендер на клиенте даст тот же HTML, что и на сервере. Если нет — серверная разметка не подходит к клиентскому дереву.

### Что React делает при расхождении

Проверка показывает, что React 19 обрабатывает расхождения по-разному:

| Что разошлось | Что делает React |
| --- | --- |
| текст | ошибка `Hydration failed because the server rendered text didn't match the client`, поддерево до ближайшего `Suspense` (или весь корень) рендерится заново на клиенте |
| атрибут (`className`, `id`, `href`) | только предупреждение в dev: `A tree hydrated but some attributes ... didn't match`. **В DOM остаётся серверное значение** |
| структура (лишний или отсутствующий элемент) | ошибка гидратации и клиентский рендер поддерева |

Второй пункт — ловушка. Если `className` на сервере и клиенте разный, React не исправляет его: в проверке после гидратации у элемента остался серверный класс. Интерфейс выглядит не так, как ожидает код, а в production даже предупреждения нет.

### Откуда берутся расхождения

```jsx
<span>{new Date().toLocaleTimeString()}</span>           // время на сервере и клиенте разное
<span>{Math.random()}</span>                              // случайность
{typeof window !== 'undefined' && <RecentlyViewed />}     // ветвление по окружению
<p><div>…</div></p>                                       // недопустимая вложенность
```

- **Время, случайность, локаль.** Сервер в другом часовом поясе форматирует дату иначе.
- **Ветвление по окружению.** `typeof window` даёт разный результат на сервере и клиенте — это и есть расхождение.
- **Данные браузера.** `localStorage`, размер окна, тема системы недоступны на сервере.
- **Недопустимая вложенность.** `<div>` внутри `<p>` сервер отдаёт как есть, но HTML-парсер браузера закрывает `<p>` раньше и получает `<p></p><div>…</div><p></p>`. Клиентское дерево и DOM расходятся. В dev React предупреждает: `In HTML, <div> cannot be a descendant of <p>`.
- **Расширения браузера и сторонние скрипты**, которые вставляют элементы в разметку до гидратации.

### Как это лечат

Значения, которых нет на сервере, показывают **после гидратации**: первый клиентский рендер совпадает с серверным, а клиентские данные приходят вторым рендером.

```jsx
function RecentlyViewed() {
  const items = useSyncExternalStore(subscribeToStorage, readRecent, () => []);
  if (items.length === 0) return null;
  return <ProductStrip items={items} />;
}
```

`useSyncExternalStore` с серверным снимком делает ровно это: при гидратации использует серверное значение (`[]`), а потом переключается на клиентское. Подробно — в [State management](/content/reactjs/state-management). Старый вариант того же приёма — флаг `mounted`, который ставится в эффекте.

Для одного значения, которое заведомо разное (время «обновлено в 10:00»), есть `suppressHydrationWarning`. Но он только отключает предупреждение для текста одного элемента: в проверке текст остался серверным, React его не обновил. Это способ признать расхождение, а не исправить его.

### useId

Частый источник расхождения атрибутов — генерация id для связки `label` и `input`:

```jsx
let counter = 0;
function Field({ label }) {
  const id = `field-${++counter}`;      // ❌ сервер и клиент считают с разного места
  return <><label htmlFor={id}>{label}</label><input id={id} /></>;
}
```

Счётчик на сервере живёт между запросами, а на клиенте начинается заново — id расходятся. Так как это атрибут, React его не исправит: в проверке у `input` остался серверный id, а `label` на клиенте ссылается на другой, и связь сломана.

`useId` решает это:

```jsx
function Field({ label }) {
  const id = useId();
  return <><label htmlFor={id}>{label}</label><input id={id} /></>;
}
```

`useId` строит id из позиции компонента в дереве, а не из порядка вызовов во времени. Позиция одинакова на сервере и клиенте, поэтому id совпадают. Формат id — внутренняя деталь, которая менялась между версиями, на него не полагаются. `useId` не подходит для ключей списков — ключ должен идти из данных (подробно — в [Компонентах и JSX](/content/reactjs/components-and-jsx)).

Совпадение HTML решает корректность. Остаётся скорость: весь HTML ждёт самый медленный запрос, а гидратация — весь JS.

## Стриминг и выборочная гидратация

На странице товара отзывы грузятся с медленного сервиса. С обычным `renderToString` сервер ждёт их, прежде чем отдать хоть байт. А если компонент отзывов приостанавливается, `renderToString` просто отдаёт fallback и никогда не дорисует отзывы — в проверке так и было.

### Стриминг

`renderToPipeableStream` (в Node.js) и `renderToReadableStream` (в Web Streams) отдают HTML по частям. Медленный кусок оборачивают в `Suspense`:

```jsx
<main>
  <h1>{product.title}</h1>
  <Price value={product.price} />
  <Suspense fallback={<p>загружаем отзывы…</p>}>
    <Reviews productId={product.id} />
  </Suspense>
</main>
```

Сервер отдаёт **оболочку** — всё, кроме приостановленных частей, — с fallback на их месте. Когда отзывы готовы, в тот же ответ дописывается скрытый блок с их разметкой и маленький скрипт, который ставит его на место fallback. В проверке оболочка ушла через 3 мс, а отзывы — отдельным куском через 100 мс, когда «сервис» ответил. Пользователь видит название и цену, не дожидаясь отзывов.

### Выборочная гидратация

`Suspense` разбивает и гидратацию. Каждую границу React гидратирует отдельно, как только пришли её HTML и код, не дожидаясь остальных. Если пользователь кликнул в ещё не гидратированную часть, React повышает её приоритет и гидратирует первой. По описанию рабочей группы React 18, сам клик React запоминает и воспроизводит после гидратации.

Так «страница видна, но не работает» сжимается до отдельных блоков: шапка и кнопка «в корзину» оживают, пока отзывы ещё грузятся.

### Что дальше

Стриминг и выборочная гидратация уменьшают ожидание, но не объём. Код всех компонентов всё равно нужно скачать и выполнить. Даже компонент, который просто выводит описание товара и никогда не меняется, гидратируется и тянет свои зависимости в бандл. Server Components решают и это: такие компоненты выполняются только на сервере, а в браузер не попадает их код. Это следующая тема — [RSC и React 19](/content/reactjs/rsc-and-react-19).

## Как менялись SSR и гидратация

Актуально на ноябрь 2026.

| Версия | Что изменилось |
| --- | --- |
| React 16 (2017) | `hydrate` отдельно от `render`, `renderToNodeStream` |
| React 18 (2022) | `hydrateRoot`, стриминг через `renderToPipeableStream` и `renderToReadableStream`, `Suspense` на сервере, выборочная гидратация, `useId` |
| React 19 (декабрь 2024) | одна понятная ошибка расхождения с диффом вместо серии предупреждений, терпимость к сторонним элементам в `head` и `body`, `prerender` для статической генерации со стримингом, Server Components |

## Красные флаги в ответе

- **«Гидратация — это повторный рендер страницы на клиенте».** React рендерит компоненты, но переиспользует серверный DOM: связывает его с fiber и вешает обработчики.
- **«SSR делает страницу быстрее».** Он ускоряет первый экран, но не интерактивность: код всех компонентов всё равно выполняется в браузере.
- **«При расхождении React всё исправит».** Текст и структуру он перерендерит с ошибкой, а расхождение атрибутов оставит как есть — в DOM будет серверное значение.
- **«`typeof window !== 'undefined'` — способ отрендерить что-то только на клиенте».** Это и есть расхождение. Клиентские значения показывают после гидратации.
- **«Id для полей сгенерирую счётчиком».** Сервер и клиент посчитают по-разному. Для этого есть `useId`.

## Как спрашивают на собеседовании

::question
Чем CSR отличается от SSR?

#answer
При CSR HTML строится в браузере после загрузки JS — до этого пустой экран, хуже SEO. При SSR сервер отдаёт готовый HTML — контент виден сразу, но потом нужна гидратация, чтобы страница стала интерактивной.

#more
SSR улучшает первый экран и LCP, но добавляет нагрузку на сервер и время до первого байта, а интерактивность всё равно зависит от загрузки и выполнения JS. Поэтому стратегию выбирают по страницам: статика и ISR для контента, SSR для персональных и часто меняющихся страниц, клиентский рендер для интерфейсов за авторизацией. Стриминг и Server Components снимают часть цены SSR.
::

::question
Что такое гидратация?

#answer
Процесс, в котором React на клиенте подключается к HTML с сервера: рендерит те же компоненты, связывает их с существующим DOM и вешает обработчики. До гидратации страница видна, но не реагирует на действия.

#more
`hydrateRoot` вместо создания узлов идёт по существующему DOM и сверяет его с результатом рендера. Поэтому первый клиентский рендер должен совпасть с серверным. Цена — тот же код компонентов выполняется второй раз, теперь в браузере. Отсюда разрыв между «видно» и «работает» на медленных устройствах, который уменьшают выборочная гидратация и Server Components.
::

::question
Что такое hydration mismatch и что React делает при нём?

#answer
Серверный HTML не совпал с первым клиентским рендером — из-за времени, случайных значений, `window`, `localStorage` или недопустимой вложенности тегов. React сообщает об ошибке и перерисовывает часть страницы на клиенте.

#more
В React 19 расхождение текста или структуры — ошибка гидратации: поддерево до ближайшего `Suspense` рендерится заново на клиенте, и это дорого. Расхождение атрибутов React не исправляет — только предупреждает в dev, а в DOM остаётся серверное значение. Лечение — сделать первый рендер детерминированным, а клиентские значения показывать после гидратации (`useSyncExternalStore` с серверным снимком, эффект). `suppressHydrationWarning` отключает предупреждение для текста одного элемента, но не обновляет его.
::

::question
Почему SSR ускоряет первый экран, но не интерактивность?

#answer
Контент виден сразу, но для интерактивности браузер должен загрузить и выполнить JS тех же компонентов — гидратацию. Компоненты по сути выполняются дважды: на сервере и на клиенте.

#more
Время до интерактивности определяется размером бандла и скоростью устройства, а не сервером. Помогают выборочная гидратация (`Suspense`-границы оживают независимо, приоритет у тех, где пользователь кликнул), разделение кода и Server Components, которые убирают из бандла код компонентов без интерактивности.
::

::question
Как работает стриминг SSR?

#answer
Сервер отдаёт HTML по частям: сначала оболочку страницы с fallback на месте медленных частей, обёрнутых в `Suspense`, потом — их содержимое, когда оно готово.

#more
`renderToPipeableStream` и `renderToReadableStream` отправляют оболочку, как только она готова. Каждая приостановленная граница позже приходит в том же ответе: скрытый блок с разметкой и скрипт, который ставит его на место fallback. `renderToString` так не умеет — он отдаёт fallback навсегда. Вместе со стримингом работает выборочная гидратация: каждая граница гидратируется независимо.
::

::question
Зачем нужен useId?

#answer
Чтобы генерировать уникальные id для связки `label` и `input`, `aria-describedby` и подобного, одинаковые на сервере и клиенте.

#more
Счётчик на сервере живёт между запросами, а на клиенте начинается с нуля, поэтому id расходятся, и React не исправит атрибут при гидратации — связь `label` с полем ломается. `useId` строит id из позиции компонента в дереве, которая одинакова на сервере и клиенте. Для ключей списков он не подходит: ключ должен идти из данных.
::

::question
Чем SSG отличается от ISR?

#answer
SSG генерирует HTML при сборке, и он не меняется до следующей сборки. ISR перегенерирует страницы в фоне по интервалу или событию — свежесть без полной пересборки.

#more
При ISR посетитель получает закешированную версию, а перегенерация идёт в фоне. Данные могут отставать на интервал, а при перегенерации по событию — на время её выполнения. Это механизм платформы и фреймворка (Next.js, хостинг), а не React. Для страницы с ценой, которая должна быть точной, нужен SSR или клиентская догрузка цены.
::

## Практика

::practice{title="Почему ломается гидратация?"}
Страница товара даёт ошибку гидратации и мигает при загрузке:

```jsx
function ProductPage({ product }) {
  const recent = JSON.parse(localStorage.getItem('recent') ?? '[]');
  return (
    <main>
      <h1>{product.title}</h1>
      <p className="price">
        {product.price} ₽
        <div className="badge">Обновлено в {new Date().toLocaleTimeString()}</div>
      </p>
      {typeof window !== 'undefined' && <RecentlyViewed items={recent} />}
    </main>
  );
}
```

#solution
Четыре проблемы:

1. **`localStorage` в рендере** — на сервере его нет, рендер упадёт.
2. **`<div>` внутри `<p>`** — браузер закроет `<p>` раньше, и DOM не совпадёт с деревом.
3. **Время в рендере** — сервер и клиент покажут разное.
4. **`typeof window`** — на сервере блока нет, на клиенте есть.

```jsx
function ProductPage({ product, renderedAt }) {
  return (
    <main>
      <h1>{product.title}</h1>
      <div className="price">
        {product.price} ₽
        <span className="badge">Обновлено в {renderedAt}</span>
      </div>
      <RecentlyViewed />
    </main>
  );
}

function RecentlyViewed() {
  const items = useSyncExternalStore(subscribeToStorage, readRecent, () => []);
  if (items.length === 0) return null;
  return <ProductStrip items={items} />;
}
```

Время приходит с сервера как данные (`renderedAt`), поэтому одинаково при гидратации. Блок «недавно смотрели» при гидратации пуст на обеих сторонах, а потом показывает данные `localStorage`. `readRecent` должен возвращать тот же массив, пока хранилище не менялось, иначе `useSyncExternalStore` зациклится.
::

::practice{title="Почему клик по label не фокусирует поле?"}
После перехода на SSR клик по подписи перестал ставить фокус в поле, хотя ошибок в консоли production нет:

```jsx
let nextId = 0;

function Field({ label, ...props }) {
  const id = `field-${nextId++}`;
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} {...props} />
    </>
  );
}
```

#solution
Счётчик на сервере не обнуляется между запросами, а на клиенте начинается с нуля, поэтому сервер и клиент дают разные id. Это расхождение атрибутов: React 19 его не исправляет, а только предупреждает в dev. В DOM у полей остаются серверные id, а клиентские `label` получили другие значения `htmlFor` — связь сломана, и в production об этом ничего не говорит.

Фикс — `useId`:

```jsx
function Field({ label, ...props }) {
  const id = useId();
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} {...props} />
    </>
  );
}
```

`useId` строит id из позиции в дереве, поэтому сервер и клиент дают одно значение. В проверке с `useId` id совпали, а со счётчиком у поля остался серверный id.
::

::practice{title="Отзывы задерживают всю страницу"}
Страница товара отдаётся через 2 секунды, потому что сервис отзывов медленный. Название и цена готовы за 50 мс:

```jsx
export async function render(req, res) {
  const product = await api.product(req.params.id);
  const reviews = await api.reviews(req.params.id);   // 2 секунды
  res.send(renderToString(<ProductPage product={product} reviews={reviews} />));
}
```

#solution
`renderToString` и `await` перед ним ждут все данные, поэтому самый медленный запрос задерживает весь ответ.

Фикс — стриминг и `Suspense` вокруг отзывов. Отзывы не ждут, а читаются в компоненте:

```jsx
export function render(req, res) {
  const productPromise = api.product(req.params.id);
  const reviewsPromise = api.reviews(req.params.id);   // стартует сразу, не ждём

  const { pipe } = renderToPipeableStream(
    <ProductPage productPromise={productPromise} reviewsPromise={reviewsPromise} />,
    { onShellReady() { res.setHeader('content-type', 'text/html'); pipe(res); } },
  );
}

function ProductPage({ productPromise, reviewsPromise }) {
  const product = use(productPromise);
  return (
    <main>
      <h1>{product.title}</h1>
      <Suspense fallback={<p>загружаем отзывы…</p>}>
        <Reviews reviewsPromise={reviewsPromise} />
      </Suspense>
    </main>
  );
}
```

Оболочка с названием и ценой уходит, как только готов товар, а отзывы приходят в том же ответе позже. В проверке оболочка ушла через 3 мс, а отзывы — отдельным куском через 100 мс. Во фреймворках это делается так же: медленный блок оборачивают в `Suspense`, остальное фреймворк берёт на себя.
::
