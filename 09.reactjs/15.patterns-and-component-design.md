# Паттерны и дизайн компонентов

Паттерны React - это способы **переиспользовать логику** и **проектировать API компонентов**. Часть из них (HOC, render props) сегодня legacy, но их спрашивают: важно понимать, какую проблему они решали и почему их заменили хуки.

---

## Композиция - основа всего

Главный паттерн React: собирать сложное из простого через `children` и props-слоты, а не через наследование.

```jsx
function Page({ header, sidebar, children }) {
  return (
    <div className="layout">
      <header>{header}</header>
      <aside>{sidebar}</aside>
      <main>{children}</main>
    </div>
  );
}
```

Передавая компоненты как props/`children`, ты избегаешь жёсткой связанности и prop drilling - контент «прокидывается» сразу на нужное место.

---

## Container / Presentational

Классическое разделение: **presentational** компонент отвечает за внешний вид (получает данные через props), **container** - за данные и логику.

```jsx
function UserListView({ users, onSelect }) { /* только разметка */ }

function UserListContainer() {
  const { data } = useQuery(['users'], fetchUsers); // логика
  return <UserListView users={data} onSelect={...} />;
}
```

<b class="text-on-semi-light">Актуальность</b> - <span class="text-gray">С хуками жёсткое разделение размылось - логику выносят в кастомные хуки, а не в контейнер-компонент. Но как способ мыслить «отдели данные от вида» паттерн полезен и его спрашивают.</span>

---

## HOC - higher-order component (legacy-теория)

**HOC** - функция, которая принимает компонент и возвращает новый компонент с добавленным поведением.

```jsx
function withAuth(Component) {
  return function Wrapped(props) {
    const { user } = useAuth();
    if (!user) return <Login />;
    return <Component {...props} user={user} />;
  };
}

const ProtectedDashboard = withAuth(Dashboard);
```

**Проблемы**, из-за которых от HOC ушли:

- **Wrapper hell** - дерево обрастает обёртками (`withAuth(withTheme(withRouter(...)))`).
- **Коллизии пропсов** - два HOC могут передать prop с одним именем.
- **Непрозрачность** - неясно, откуда у компонента взялись props.

---

## Render props (legacy-теория)

Компонент принимает **функцию** как проп (часто `children`) и вызывает её, передавая данные. Так делятся логикой.

```jsx
function MouseTracker({ render }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return <div onMouseMove={(e) => setPos({ x: e.clientX, y: e.clientY })}>
    {render(pos)}
  </div>;
}

<MouseTracker render={({ x, y }) => <p>{x}, {y}</p>} />
```

Гибче HOC, но порождает **вложенность** («callback hell» в JSX) при комбинировании.

---

## Кастомные хуки - современная замена

И HOC, и render props решали одну задачу - **переиспользование логики с состоянием**. Хуки делают это без обёрток и вложенности.

```jsx
function useMouse() {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  useEffect(() => {
    const h = (e) => setPos({ x: e.clientX, y: e.clientY });
    window.addEventListener('mousemove', h);
    return () => window.removeEventListener('mousemove', h);
  }, []);
  return pos;
}

const { x, y } = useMouse(); // без обёрток и вложенности
```

> На собесе: «HOC и render props переиспользуют логику через композицию компонентов; хуки - через композицию функций. Хуки победили, потому что нет wrapper hell и коллизий пропсов».

## Compound components

Набор компонентов, которые работают вместе и **делят неявное состояние** через контекст. API получается выразительным, как у нативного `<select>/<option>`.

```jsx
<Tabs defaultValue="a">
  <Tabs.List>
    <Tabs.Trigger value="a">Первый</Tabs.Trigger>
    <Tabs.Trigger value="b">Второй</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Panel value="a">...</Tabs.Panel>
</Tabs>
```

Внутри `Tabs` через контекст раздаёт активное значение, а `Trigger`/`Panel` его читают. Пользователь компонует структуру, не зная про внутреннее состояние. Так устроены Radix, Headless UI.

---

## Controlled vs uncontrolled компонент

При проектировании **своего** компонента решаешь, кто владеет состоянием. Хороший дизайн поддерживает оба режима, как нативные инпуты.

```jsx
function Toggle({ checked, defaultChecked, onChange }) {
  const isControlled = checked !== undefined;
  const [internal, setInternal] = useState(defaultChecked ?? false);
  const value = isControlled ? checked : internal;
  const toggle = () => {
    if (!isControlled) setInternal((v) => !v);
    onChange?.(!value);
  };
  // ...
}
```

<b class="text-on-semi-light">Принцип</b> - <span class="text-gray">`value` + `onChange` → управляемый родителем; `defaultValue` → неуправляемый, состояние внутри. Это та же дихотомия, что у форм ([состояние и события](/content/reactjs/state-and-events)), применённая к дизайну API.</span>

## Полиморфные компоненты

Компонент, который рендерится как разный HTML-тег через проп `as` - для гибких UI-примитивов.

```jsx
<Box as="a" href="/home">ссылка</Box>
<Box as="button" onClick={...}>кнопка</Box>
```

Типобезопасная реализация через generics разобрана в главе [TS с React](/content/typescript/ts-with-react). Использовать дозированно - в дизайн-системе, не везде.

## Error boundaries

**Error boundary** - компонент, который ловит ошибки рендера в дочернем дереве и показывает запасной UI вместо «белого экрана». До сих пор реализуется **только классом** - хука-эквивалента нет.

```jsx
class ErrorBoundary extends React.Component {
  state = { hasError: false };

  static getDerivedStateFromError() {     // обновить state → показать fallback
    return { hasError: true };
  }
  componentDidCatch(error, info) {        // сайд-эффект: залогировать
    logToService(error, info);
  }
  render() {
    if (this.state.hasError) return this.props.fallback;
    return this.props.children;
  }
}

<ErrorBoundary fallback={<Error />}>
  <Page />
</ErrorBoundary>
```

<b class="text-on-semi-light">Что НЕ ловит error boundary</b> - <span class="text-gray">Ошибки в обработчиках событий, в асинхронном коде (`setTimeout`, промисы), на сервере при SSR и в самом error boundary. Только ошибки во время рендера дочерних компонентов.</span>

На практике используют библиотеку **`react-error-boundary`** - она даёт хуки и удобный сброс. Связка с Suspense для загрузки - в [загрузке данных](/content/reactjs/data-fetching).

## Принципы дизайна API компонента

- **Минимум обязательных props**, разумные дефолты.
- **Композиция через `children`** вместо десятка булевых флагов конфигурации.
- **Один способ сделать одно** - не давай противоречивых путей.
- Поддержи **controlled и uncontrolled**, где уместно.
- Пробрасывай `...rest` и `ref` на корневой элемент - для гибкости.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое HOC и какие у него проблемы?</b>
<span class="text-gray">Функция, оборачивающая компонент и добавляющая поведение. Проблемы: wrapper hell, коллизии пропсов, непрозрачность источника props. Заменены кастомными хуками.</span>

<b class="text-on-semi-light">Чем render props отличаются от HOC?</b>
<span class="text-gray">Оба переиспользуют логику. HOC оборачивает компонент, render props передаёт функцию-рендер. Render props гибче, но дают вложенность в JSX. Оба вытеснены хуками.</span>

<b class="text-on-semi-light">Что такое compound components?</b>
<span class="text-gray">Набор компонентов, делящих неявное состояние через контекст (Tabs.List, Tabs.Trigger). Дают выразительный декларативный API.</span>

<b class="text-on-semi-light">Как спроектировать компонент с controlled и uncontrolled режимами?</b>
<span class="text-gray">Если передан `value` - управляемый родителем; иначе хранить состояние внутри от `defaultValue`. Как у нативных инпутов.</span>

<b class="text-on-semi-light">Что такое error boundary и что он не ловит?</b>
<span class="text-gray">Класс, ловящий ошибки рендера детей и показывающий fallback. Не ловит ошибки в обработчиках событий, в async-коде и в самом себе.</span>

<b class="text-on-semi-light">Почему хуки победили HOC и render props?</b>
<span class="text-gray">Переиспользование логики через композицию функций - без обёрток, вложенности и коллизий пропсов, с прозрачным источником данных.</span>
