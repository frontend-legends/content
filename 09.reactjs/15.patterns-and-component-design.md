# Паттерны и дизайн компонентов

Как спроектировать API переиспользуемого компонента и как делиться логикой между компонентами: композиция, compound components, управляемый и неуправляемый режимы, headless-компоненты, а также HOC и render props — что они решали и почему их заменили хуки. На mid спрашивают, что такое HOC и render props. На senior — почему `cloneElement` хрупок, как сделать компонент, который работает в обоих режимах, и где ставить границы ошибок.

::tldr
- **Композиция — основной инструмент.** Слоты через `children` и props-элементы заменяют десятки булевых флагов, а наследование компонентов в React не нужно.
- **Compound components делят состояние через контекст**, как `<select>` и `<option>`. Вариант на `cloneElement` ломается, как только между родителем и ребёнком появляется обёртка.
- **Хороший компонент работает и управляемым, и неуправляемым:** `value` и `onChange` — состояние у родителя, `defaultValue` — внутри. Копировать prop в state нельзя.
- **HOC и render props решали переиспользование логики** и платили за это обёртками, коллизиями props и вложенностью. Кастомные хуки делают то же через композицию функций.
- **Границы ошибок ставят по смысловым зонам**, а сбрасывают сменой `key` — сама граница помнит ошибку.
::

## Задача: компонент вкладок

Сквозной пример темы — компонент вкладок для дизайн-системы. Первая версия, которую пишут почти все:

```jsx
<Tabs
  items={[
    { id: 'desc', label: 'Описание', content: <Description /> },
    { id: 'reviews', label: 'Отзывы', content: <Reviews />, badge: 12 },
  ]}
  defaultActive="desc"
  showBadges
  tabClassName="tab"
  onTabChange={track}
/>
```

Через месяц приходят запросы: иконка у одной вкладки, тултип у другой, вкладки справа от заголовка, ленивое содержимое, управление активной вкладкой из URL. Каждый запрос — новый prop: `iconPosition`, `tooltipFor`, `renderLabel`, `lazy`. Компонент превращается в конфигуратор, где флаги конфликтуют, а нужного всё равно нет.

Проблема не в количестве props, а в том, что компонент **владеет разметкой**, которую должен определять пользователь. Решение — отдать разметку обратно.

## Композиция и слоты

Главный приём React — передавать готовые элементы, а не описание того, что нарисовать:

```jsx
function Card({ title, actions, children }) {
  return (
    <article className="card">
      <header>{title}{actions}</header>
      <div className="body">{children}</div>
    </article>
  );
}

<Card title={<h3>Заказ №42</h3>} actions={<Menu />}>
  Доставка завтра
</Card>
```

`children` и props-элементы — это **слоты**: компонент решает, *где* показать содержимое, а пользователь — *что* показать. Иконка, тултип или бейдж — это просто другой элемент в слоте, без нового флага.

У композиции есть и второй плюс — производительность и prop drilling. Элемент, переданный через `children`, создан выше по дереву и не рендерится при рендере компонента-обёртки, а данные идут прямо туда, где элемент создан, минуя промежуточные слои (подробно — в [Context API](/content/reactjs/context-api)).

Наследование компонентов в React не используют: документация прямо говорит, что не нашла случаев, где оно лучше композиции. «Особая карточка» — это компонент, который рендерит `Card` с нужными слотами.

Для вкладок одних слотов мало: триггеры и панели должны знать, какая вкладка активна. Им нужно общее состояние.

## Compound components

Compound components — набор компонентов, которые работают вместе и делят неявное состояние. API выглядит как разметка:

```jsx
<Tabs defaultValue="desc">
  <Tabs.List>
    <Tabs.Trigger value="desc">Описание</Tabs.Trigger>
    <Tooltip text="12 новых">
      <Tabs.Trigger value="reviews">Отзывы</Tabs.Trigger>
    </Tooltip>
  </Tabs.List>
  <Tabs.Panel value="desc"><Description /></Tabs.Panel>
  <Tabs.Panel value="reviews"><Reviews /></Tabs.Panel>
</Tabs>
```

Пользователь сам собирает структуру: оборачивает триггер в тултип, меняет порядок, добавляет что угодно между вкладками. Как `Trigger` узнаёт, какая вкладка активна?

### Через cloneElement — хрупко

Старый способ — родитель перебирает детей и добавляет им props:

```jsx
function Tabs({ children }) {
  const [active, setActive] = useState('desc');
  return Children.map(children, (child) => cloneElement(child, { active, onSelect: setActive }));
}
```

Это работает, только пока триггеры — **прямые** дети. Тултип в примере выше получит `active` и `onSelect` вместо триггера. В проверке кнопка внутри тултипа осталась без `onSelect`: клик по ней падает в обработчике, и вкладка не переключается. Фрагмент тоже ломает этот подход: `Children.count` видит `<>...</>` одним ребёнком. Документация React относит `Children` и `cloneElement` к редко нужным API именно из-за этой хрупкости.

### Через контекст — устойчиво

```jsx
const TabsContext = createContext(null);

function Tabs({ defaultValue, children }) {
  const [active, setActive] = useState(defaultValue);
  const value = useMemo(() => ({ active, setActive }), [active]);
  return <TabsContext value={value}>{children}</TabsContext>;
}

function useTabs() {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error('Tabs.Trigger нужно использовать внутри <Tabs>');
  return ctx;
}

function Trigger({ value, children }) {
  const { active, setActive } = useTabs();
  return (
    <button role="tab" aria-selected={active === value} onClick={() => setActive(value)}>
      {children}
    </button>
  );
}

Tabs.Trigger = Trigger;
```

Контекст доходит до триггера на любой глубине, поэтому тултипы, фрагменты и любые обёртки не мешают — в проверке вкладка внутри тултипа переключилась. Использование `Tabs.Trigger` вне `Tabs` даёт понятную ошибку, а не молчаливо сломанное поведение. Так устроены Radix UI, Headless UI и Ark UI.

Вкладки умеют хранить активное значение. Но иногда им нужно управлять снаружи — например, из URL.

## Управляемый и неуправляемый режимы

Нативный `<input>` работает в двух режимах: с `value` и `onChange` значение у родителя, с `defaultValue` — внутри (подробно — в [State и событиях](/content/reactjs/state-and-events)). Хороший компонент поддерживает оба так же:

```jsx
<Tabs defaultValue="desc" />                                 // неуправляемый: состояние внутри
<Tabs value={tab} onValueChange={setTab} />                  // управляемый: состояние у родителя
<Tabs value={params.get('tab')} onValueChange={setTabInUrl} /> // например, в URL
```

Логику удобно вынести в хук:

```jsx
function useControllableState({ value, defaultValue, onChange }) {
  const [inner, setInner] = useState(defaultValue);
  const isControlled = value !== undefined;
  const current = isControlled ? value : inner;

  const set = (next) => {
    if (!isControlled) setInner(next);   // в неуправляемом режиме храним сами
    onChange?.(next);                    // в любом режиме сообщаем наружу
  };

  return [current, set];
}
```

В управляемом режиме компонент не меняется сам: если родитель не обновил `value` в ответ на `onChange`, вкладка останется прежней. В проверке управляемый переключатель без обновления от родителя не переключился, а с обновлением — следовал за родителем, в том числе когда родитель сбрасывал значение извне.

Частая ошибка — копировать prop в состояние:

```jsx
function BadTabs({ value }) {
  const [active, setActive] = useState(value);   // ❌ value читается только при монтировании
}
```

Компонент выглядит управляемым, но после монтирования перестаёт слушать родителя: в проверке родитель выключил переключатель, а тот остался включённым. Почему так и что делать вместо этого — в [Производном состоянии](/content/reactjs/derived-state-and-data-flow).

## Headless: логика без разметки

Последний шаг — отделить поведение от вида целиком. Headless-компонент или хук отвечает за состояние, клавиатуру и ARIA, а разметку и стили даёт пользователь:

```jsx
function useTabs({ defaultValue }) {
  const [active, setActive] = useState(defaultValue);
  return {
    active,
    getTriggerProps: (value) => ({
      role: 'tab',
      'aria-selected': active === value,
      tabIndex: active === value ? 0 : -1,
      onClick: () => setActive(value),
    }),
    getPanelProps: (value) => ({ role: 'tabpanel', hidden: active !== value }),
  };
}
```

Компонент дизайн-системы берёт из хука поведение и рисует вкладки по своим макетам. Сложная часть — доступность: управление стрелками, роли, связи `aria-controls` — написана один раз. Готовые headless-библиотеки (Radix UI, React Aria, Headless UI, Ark UI) — стандартная основа дизайн-систем.

### Полиморфный компонент

Ещё один частый приём дизайн-систем — prop `as`, который меняет тег корневого элемента: `<Button as="a" href="/cart">`. Он удобен, но типизировать его аккуратно непросто (подробно — в [TypeScript с React](/content/typescript/ts-with-react)). В Radix UI для этого есть альтернатива `asChild`: компонент передаёт своё поведение единственному ребёнку.

Мы разобрали, как проектировать API компонента. Осталась вторая половина темы — как делиться *логикой* между разными компонентами. У неё длинная история.

## Переиспользование логики: от HOC к хукам

До хуков у функциональных компонентов не было состояния, и логику с состоянием делили через компоненты-обёртки.

### HOC

Higher-order component — функция, которая принимает компонент и возвращает новый с добавленным поведением:

```jsx
function withAuth(Component) {
  return function WithAuth(props) {
    const user = useAuth();
    if (!user) return <Login />;
    return <Component {...props} user={user} />;
  };
}

export default withAuth(Dashboard);
```

Проблемы HOC:

- **Обёртки.** `withAuth(withTheme(withRouter(Dashboard)))` — три лишних слоя в дереве и DevTools.
- **Коллизии props.** Два HOC, которые кладут prop с одним именем, молча затирают друг друга: в проверке `data` от одного HOC пропал без ошибки.
- **Непрозрачность.** По коду компонента не видно, откуда пришли props.
- **Статические методы теряются.** `Dashboard.loadData` у обёртки становится `undefined`, их нужно копировать вручную.

Раньше к этому списку добавлялась потеря `ref`: он не проходил через обёртку без `forwardRef`. В React 19 `ref` — обычный prop, и `{...props}` пробрасывает его сам — в проверке ref через HOC дошёл до `<input>`.

### Render props

Компонент принимает функцию и вызывает её со своими данными:

```jsx
<DataLoader url="/api/cart" render={({ data, loading }) => (loading ? <Spinner /> : <Cart items={data} />)} />
```

Это гибче HOC: видно, откуда данные, нет коллизий. Но несколько render props дают вложенную «лесенку» в JSX, а функция, созданная в рендере, — новая на каждый рендер и отменяет `memo` у получателя.

### Кастомные хуки

Хуки решают ту же задачу через композицию функций, без обёрток:

```jsx
function Dashboard() {
  const user = useAuth();
  const { data, loading } = useData('/api/cart');
  // ...
}
```

Нет лишних слоёв, видно, откуда пришло каждое значение, коллизий нет — значения называет сам компонент. HOC остаются уместны в редких случаях, где нужно обернуть именно компонент: границы ошибок вокруг страницы, интеграции со старым кодом.

> Как писать кастомные хуки, что из них возвращать и когда хук не нужен — в [Хуках](/content/reactjs/advanced-hooks).

## Границы ошибок в дизайне приложения

Как устроена граница ошибок и что она ловит — в [Компонентах и JSX](/content/reactjs/components-and-jsx). Здесь — где их ставить.

Одна граница в корне превращает любую ошибку в экран «что-то пошло не так» для всего приложения. Поэтому границы ставят по **смысловым зонам**: страница, виджет на дашборде, блок рекомендаций, сторонний компонент. Ошибка в рекомендациях не должна ломать оформление заказа.

Граница помнит ошибку, пока не размонтирована. Если данные исправились, а граница осталась на месте, она так и показывает запасной UI — в проверке после исправления данных с тем же `key` граница продолжала показывать ошибку. Сбрасывают её сменой `key` или через `resetKeys` в `react-error-boundary`:

```jsx
<ErrorBoundary FallbackComponent={WidgetError} resetKeys={[widgetId]}>
  <Widget id={widgetId} />
</ErrorBoundary>
```

Вместе с `Suspense` границы ошибок задают, как страница загружается и падает по частям (подробно — в [Загрузке данных](/content/reactjs/data-fetching)).

## Принципы API компонента

- **Слоты вместо флагов.** Если prop описывает, *что* нарисовать, скорее всего, нужен слот.
- **Оба режима для состояния:** `value` / `defaultValue` / `onValueChange`, как у нативных полей.
- **Пробрасывай остальное.** `...rest` и `ref` на корневой элемент: пользователю нужны `data-*`, `aria-*`, обработчики, ref для измерений.
- **Один способ сделать одно.** Два пути к одному результату (`items` и `children`) рано или поздно разойдутся.
- **Понятные ошибки.** Компонент вне своего контекста должен падать с объяснением, а не молча работать неправильно.

---

## Красные флаги в ответе

- **«Сделаю компонент с флагами на все случаи».** Каждый флаг увеличивает число комбинаций. Слоты и композиция масштабируются, флаги — нет.
- **«Compound components делаю через `cloneElement`».** Первая же обёртка между родителем и ребёнком сломает передачу props. Нужен контекст.
- **«Чтобы компонент был управляемым, скопирую prop в `useState`».** Копия перестаёт слушать родителя после монтирования.
- **«HOC — современный способ переиспользовать логику».** Это способ до хуков. Сейчас — кастомные хуки, HOC — для редких случаев обёртки компонента.
- **«Одной границы ошибок в корне достаточно».** Тогда любая ошибка роняет всё приложение. Границы ставят по смысловым зонам.

## Как спрашивают на собеседовании

::question{level="mid"}
Что такое HOC и какие у него проблемы?

#mid
Функция, которая принимает компонент и возвращает новый с добавленным поведением, например `withAuth(Dashboard)`. Проблемы: лишние обёртки в дереве, коллизии props, непрозрачность источника данных. Сейчас вместо HOC пишут кастомные хуки.

#senior
Коллизии молчаливые: два HOC с одинаковым именем prop затирают друг друга без ошибки. Статические методы обёрнутого компонента теряются. Раньше терялся и `ref` — в React 19 он стал обычным prop и проходит через `{...props}`. HOC уместны, когда нужно обернуть именно компонент: граница ошибок вокруг страницы, интеграция со старым кодом или библиотекой.
::

::question{level="mid"}
Чем render props отличаются от HOC?

#mid
Оба паттерна переиспользуют логику. HOC оборачивает компонент снаружи, render props передаёт функцию, которая получает данные и возвращает разметку. Render props прозрачнее, но несколько штук дают вложенность в JSX.

#senior
С render props видно, откуда пришли данные, и коллизий имён нет — значения называет вызывающий код. Цена — «лесенка» при комбинировании и новая функция на каждом рендере, которая отменяет `memo` у получателя. Оба паттерна — композиция компонентов, а хуки — композиция функций без лишних узлов в дереве.
::

::question{level="mid"}
Что такое compound components?

#mid
Набор компонентов, которые работают вместе и делят состояние через контекст: `Tabs`, `Tabs.List`, `Tabs.Trigger`, `Tabs.Panel`. Пользователь собирает структуру как разметку.

#senior
Состояние живёт в корневом компоненте и раздаётся через контекст, поэтому части работают на любой глубине и с любыми обёртками. Вариант на `Children.map` и `cloneElement` ломается при первой обёртке (props достаются ей, а не триггеру) и не видит детей внутри фрагмента. Хук доступа к контексту бросает понятную ошибку при использовании вне корня. Так устроены Radix UI и Headless UI.
::

::question{level="senior"}
Как спроектировать компонент с управляемым и неуправляемым режимами?

#mid
Если передан `value` — компонент управляемый, значение у родителя, изменения сообщаются через `onChange`. Если нет — компонент хранит состояние сам, начиная с `defaultValue`.

#senior
Режим определяется по `value !== undefined`, и его не меняют во время жизни компонента — как у нативных полей. В управляемом режиме компонент не меняет себя сам: если родитель не обновил `value`, ничего не происходит. `onChange` вызывается в обоих режимах. Логику выносят в хук вроде `useControllableState`. Копия prop в `useState` — ошибка: она перестаёт следовать за родителем после монтирования.
::

::question{level="senior"}
Что такое headless-компоненты и зачем они дизайн-системам?

#mid
Компоненты или хуки, которые дают поведение (состояние, клавиатуру, ARIA), но не разметку и стили. Внешний вид определяет тот, кто их использует.

#senior
Сложная часть виджетов — доступность и клавиатура: стрелки во вкладках, фокус в меню, роли и связи `aria-*`. Headless-библиотеки (Radix UI, React Aria, Headless UI) реализуют это один раз и отдают через prop getters или compound components, а дизайн-система рисует компоненты по своим макетам. Так поведение не приходится переписывать при редизайне.
::

::question{level="mid"}
Где ставить границы ошибок?

#mid
Не только в корне, а по смысловым зонам: страница, виджет, сторонний компонент. Тогда ошибка в одном блоке не роняет весь интерфейс.

#senior
Граница помнит ошибку, пока не размонтирована, поэтому после исправления данных её сбрасывают сменой `key` или через `resetKeys`. Расстановка границ вместе с `Suspense` — это дизайн того, как страница загружается и деградирует по частям. Ошибки обработчиков и асинхронного кода границы не видят: их ловят отдельно или пробрасывают в рендер через состояние.
::

::question{level="mid"}
Почему хуки победили HOC и render props?

#mid
Они переиспользуют логику без обёрток и вложенности, без коллизий props, и видно, откуда пришло каждое значение.

#senior
HOC и render props делили логику через компоненты, и каждый уровень логики добавлял узел в дерево. Хуки делят логику через функции: вызовы встраиваются в список хуков компонента, дерево не растёт, а значения названы явно. Цена — правила хуков и модель снимков, которую нужно понимать.
::

## Практика

::practice{title="Раздутый компонент"}
Модальное окно обросло флагами. Перепиши его API так, чтобы новые требования не добавляли props:

```jsx
<Modal
  title="Удалить товар?"
  showCloseButton
  showFooter
  primaryButtonText="Удалить"
  secondaryButtonText="Отмена"
  onPrimary={remove}
  onSecondary={close}
  primaryButtonVariant="danger"
  headerIcon={<TrashIcon />}
/>
```

#solution
Компонент владеет разметкой шапки и подвала, поэтому каждое отличие — новый флаг. Отдаём разметку пользователю через слоты:

```jsx
function Modal({ title, footer, onClose, children }) {
  return (
    <dialog open aria-labelledby="modal-title">
      <header>
        <h2 id="modal-title">{title}</h2>
        {onClose && <button aria-label="Закрыть" onClick={onClose}>×</button>}
      </header>
      <div>{children}</div>
      {footer && <footer>{footer}</footer>}
    </dialog>
  );
}

<Modal
  title={<><TrashIcon /> Удалить товар?</>}
  onClose={close}
  footer={
    <>
      <Button variant="danger" onClick={remove}>Удалить</Button>
      <Button onClick={close}>Отмена</Button>
    </>
  }
>
  Товар пропадёт из каталога.
</Modal>
```

Девять props стали четырьмя, и иконка, третья кнопка или ссылка в подвале больше не требуют изменений в `Modal`.
::

::practice{title="Почему вкладка в тултипе не переключается?"}
После того как одну вкладку обернули в тултип, она перестала переключаться:

```jsx
function Tabs({ children }) {
  const [active, setActive] = useState('desc');
  return <div>{Children.map(children, (child) => cloneElement(child, { active, onSelect: setActive }))}</div>;
}

function Trigger({ value, active, onSelect, children }) {
  return <button aria-selected={active === value} onClick={() => onSelect(value)}>{children}</button>;
}

<Tabs>
  <Trigger value="desc">Описание</Trigger>
  <Tooltip text="12 новых"><Trigger value="reviews">Отзывы</Trigger></Tooltip>
</Tabs>
```

#solution
`cloneElement` добавляет props только прямым детям. Второй прямой ребёнок — `Tooltip`, он и получает `active` и `onSelect`. `Trigger` внутри тултипа остаётся без них: `onSelect` — `undefined`, клик падает в обработчике, вкладка не переключается.

Фикс — передавать состояние через контекст, который доходит на любую глубину:

```jsx
const TabsContext = createContext(null);

function Tabs({ defaultValue, children }) {
  const [active, setActive] = useState(defaultValue);
  const value = useMemo(() => ({ active, setActive }), [active]);
  return <TabsContext value={value}><div>{children}</div></TabsContext>;
}

function Trigger({ value, children }) {
  const ctx = useContext(TabsContext);
  if (!ctx) throw new Error('Trigger нужно использовать внутри <Tabs>');
  return (
    <button aria-selected={ctx.active === value} onClick={() => ctx.setActive(value)}>
      {children}
    </button>
  );
}
```

В проверке с контекстом вкладка внутри тултипа переключилась, а `Trigger` вне `Tabs` падает с понятной ошибкой.
::

::practice{title="Переключатель не слушается родителя"}
Родитель сбрасывает настройки, но переключатель остаётся включённым:

```jsx
function Switch({ checked, onChange }) {
  const [on, setOn] = useState(checked);
  return (
    <button role="switch" aria-checked={on} onClick={() => { setOn(!on); onChange(!on); }} />
  );
}
```

#solution
`useState(checked)` читает prop только при монтировании. Дальше у переключателя своя копия, и изменения `checked` от родителя её не трогают. Компонент притворяется управляемым, но на деле неуправляемый.

Фикс — поддержать оба режима явно:

```jsx
function Switch({ checked, defaultChecked = false, onChange }) {
  const [on, setOn] = useControllableState({ value: checked, defaultValue: defaultChecked, onChange });
  return <button role="switch" aria-checked={on} onClick={() => setOn(!on)} />;
}

// управляемый: родитель владеет значением и может сбросить его извне
<Switch checked={settings.sound} onChange={(v) => update({ sound: v })} />

// неуправляемый: состояние внутри
<Switch defaultChecked />
```

`useControllableState` — хук из раздела про режимы. В проверке управляемый переключатель следовал за родителем, в том числе при сбросе извне, а неуправляемый переключался сам.
::
