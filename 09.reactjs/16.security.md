# Безопасность в React

React **по умолчанию защищает от XSS**, но даёт лазейки, через которые уязвимость легко вернуть. Знать эти места - частый вопрос на собесе, особенно на senior.

---

## XSS и автоэкранирование

**XSS (Cross-Site Scripting)** - внедрение чужого скрипта, который выполнится в браузере жертвы. Главная защита React: **всё, что вставляется в JSX как текст, экранируется автоматически**.

```jsx
const userInput = '<img src=x onerror="alert(document.cookie)">';
return <div>{userInput}</div>;
// React выведет это как ТЕКСТ, а не как HTML - скрипт не выполнится
```

React превращает `<`, `>`, `&` в HTML-сущности. Поэтому обычный рендеринг пользовательских данных безопасен.

---

## dangerouslySetInnerHTML

Лазейка, чтобы вставить **сырой HTML**. Название с «dangerously» - намеренное предупреждение.

```jsx
// ⚠️ опасно, если html содержит пользовательский ввод
<div dangerouslySetInnerHTML={{ __html: html }} />
```

Если в `html` попадёт ввод пользователя - получаем XSS. Решение - **санитизация** перед вставкой:

```jsx
import DOMPurify from 'dompurify';

<div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />
```

<b class="text-on-semi-light">Правило</b> - <span class="text-gray">Никогда не передавай в `dangerouslySetInnerHTML` неочищенные данные. Санитизируй через DOMPurify (или рендери на доверенном бэкенде). Лучше вообще избегать сырого HTML.</span>

---

## Инъекции через URL

Автоэкранирование **не защищает атрибуты-ссылки**. `javascript:`-URL в `href`/`src` выполнит код при клике.

```jsx
// ⚠️ если user.website = "javascript:alert(1)"
<a href={user.website}>сайт</a>
```

Защита - валидировать протокол:

```jsx
function safeHref(url) {
  try {
    const u = new URL(url, window.location.origin);
    return ['http:', 'https:', 'mailto:'].includes(u.protocol) ? url : '#';
  } catch {
    return '#';
  }
}
```

> Современные React предупреждают про `javascript:`-URL в dev, но полагаться на это нельзя - проверяй сам.

## target="_blank" и tabnabbing

Ссылка с `target="_blank"` без защиты даёт открытой странице доступ к `window.opener` - она может подменить исходную вкладку (reverse tabnabbing).

```jsx
<a href={url} target="_blank" rel="noopener noreferrer">внешняя ссылка</a>
```

> Современные браузеры подразумевают `noopener` для `_blank` по умолчанию, но `rel="noopener noreferrer"` ставят явно.

## Секреты не живут на клиенте

Весь клиентский бандл - **публичный**. Любая «переменная окружения», попавшая в сборку (`VITE_*`, `NEXT_PUBLIC_*`), видна в DevTools.

```js
// ❌ Секрет в клиентском коде = опубликованный секрет
const apiKey = import.meta.env.VITE_SECRET_KEY;
```

<b class="text-on-semi-light">Принцип</b> - <span class="text-gray">На клиенте только публичные ключи (например, publishable-ключ Stripe). Приватные ключи и токены - только на сервере (бэкенд, серверные функции, RSC). Авторизация и проверка прав - всегда на сервере; клиентские проверки - это UX, не безопасность.</span>

## Прочее

- **Зависимости (supply chain).** Большая часть кода - чужие npm-пакеты. Регулярно `npm audit`, обновляй, минимизируй зависимости.
- **CSP (Content-Security-Policy)** - заголовок, ограничивающий источники скриптов; сильно снижает урон от XSS. Настраивается на сервере.
- **Хранение токенов.** `localStorage` доступен из JS (уязвим к XSS); httpOnly-cookie недоступны скриптам, но требуют защиты от CSRF. Компромисс разбирается в [безопасности и производительности](/content/security-perfomance).

## Вопросы на собеседовании

<b class="text-on-semi-light">Как React защищает от XSS по умолчанию?</b>
<span class="text-gray">Любые данные, вставленные как текст в JSX, экранируются - спецсимволы превращаются в HTML-сущности, скрипт не исполняется.</span>

<b class="text-on-semi-light">Чем опасен dangerouslySetInnerHTML?</b>
<span class="text-gray">Вставляет сырой HTML в обход экранирования. С пользовательским вводом - прямой XSS. Нужно санитизировать (DOMPurify) или не использовать.</span>

<b class="text-on-semi-light">Защищает ли React от javascript:-ссылок?</b>
<span class="text-gray">Нет, экранирование текста не касается атрибутов href/src. Нужно самому валидировать протокол URL.</span>

<b class="text-on-semi-light">Можно ли хранить API-ключи в React-приложении?</b>
<span class="text-gray">Только публичные. Клиентский бандл открыт всем; приватные ключи и авторизацию держат на сервере.</span>

<b class="text-on-semi-light">Зачем rel="noopener" для target="_blank"?</b>
<span class="text-gray">Чтобы открытая вкладка не получила доступ к window.opener и не подменила исходную страницу (tabnabbing).</span>
