# Безопасность в React

Что React защищает сам и где эта защита заканчивается. Спрашивают, как React защищает от XSS и чем опасен `dangerouslySetInnerHTML`. Глубже — какие ссылки React блокирует, а какие нет, почему нельзя раскладывать пользовательские данные в props, как не сломать страницу состоянием при серверном рендере и почему серверные функции — публичные эндпоинты.

::tldr
- **React экранирует всё, что попадает в разметку как текст или значение атрибута.** Строка с `<script>` или `onerror` будет показана как текст, а не выполнена.
- **`javascript:`-ссылки React блокирует**, подменяя их на URL, который бросает ошибку. Другие схемы, например `data:`, он не трогает — протокол ссылок из пользовательских данных нужно проверять.
- **`dangerouslySetInnerHTML` вставляет HTML как есть.** Пользовательский HTML перед этим очищают (DOMPurify) или не вставляют вовсе.
- **Spread пользовательских данных в props — дыра:** вместе с ними приходят `dangerouslySetInnerHTML`, `href` и обработчики. В props раскладывают только то, что проверено.
- **Всё, что в клиентском бандле, — публично,** а серверные функции и эндпоинты доступны напрямую. Секреты и проверка прав — только на сервере.
::

## Что React защищает сам

Сквозной пример — страница профиля, где почти всё приходит от пользователя: имя, описание с форматированием, ссылка на сайт.

```jsx
function Profile({ user }) {
  return (
    <article>
      <h1 title={user.name}>{user.name}</h1>
      <Bio html={user.bioHtml} />
      <a href={user.website}>Сайт</a>
    </article>
  );
}
```

Главная защита React — **экранирование по умолчанию**. Всё, что вставлено в JSX как текст или значение атрибута, превращается в безопасную строку:

```jsx
const name = '<img src=x onerror="alert(1)">';
<p>{name}</p>
// <p>&lt;img src=x onerror=&quot;alert(1)&quot;&gt;</p>
```

`<`, `>`, `&` и кавычки становятся HTML-сущностями. Значение атрибута тоже экранируется: имя с кавычкой не может «выйти» из `title` и добавить свой обработчик. React вставляет текст через DOM-свойства (`textContent`), а не через сборку HTML-строки, поэтому на клиенте такой текст никогда не разбирается как разметка.

Ещё одна защита — объекты, которые не являются React-элементами, нельзя отрендерить. Если сервер вернёт JSON `{ "type": "img", "props": {...} }` и он попадёт в JSX, React не отрисует его как элемент, потому что у JSON нет `Symbol` в поле `$$typeof` (подробно — во [Введении в React](/content/reactjs/introduction)).

Это закрывает самый частый вектор :term[XSS]{def="межсайтовый скриптинг: чужой скрипт попадает на страницу через непроверенные данные"} — вывод пользовательских строк. Остальные векторы — места, где React либо не может знать, что безопасно, либо где разработчик сам отключает защиту.

> Что такое XSS, какие бывают виды и как работают защиты браузера — в главе [XSS](/content/security-perfomance/xss).

## Ссылки

Экранирование не помогает, если опасно само значение. Ссылка `javascript:alert(document.cookie)` — корректная строка, и экранировать в ней нечего. Но при клике код выполнится в контексте страницы.

React 19 такие ссылки **блокирует**. Если `href` начинается со схемы `javascript:` (в любом регистре, в том числе с пробелами впереди), React подменяет его на URL, который при переходе бросает ошибку:

```text
javascript:throw new Error('React has blocked a javascript: URL as a security precaution.')
```

В проверке так было и на клиенте, и при серверном рендере. Но это защита от одной схемы. `data:text/html,...`, `vbscript:` и ссылки на чужие домены React пропускает как есть. Поэтому ссылки из пользовательских данных проверяют по белому списку протоколов:

```jsx
function safeUrl(url) {
  try {
    const u = new URL(url, window.location.origin);
    return ['http:', 'https:', 'mailto:'].includes(u.protocol) ? u.href : undefined;
  } catch {
    return undefined;
  }
}

<a href={safeUrl(user.website)} target="_blank" rel="noopener noreferrer">Сайт</a>
```

`rel="noopener"` не даёт открытой странице получить доступ к `window.opener` и подменить исходную вкладку. Современные браузеры подразумевают его для `target="_blank"`, но явный атрибут ничего не стоит. `noreferrer` дополнительно не передаёт адрес страницы.

Ссылки — значения, которые React не может проверить. Следующее место — то, где разработчик сам отключает экранирование.

## dangerouslySetInnerHTML

Описание профиля пришло из редактора с форматированием — это HTML. Чтобы вставить его как разметку, React даёт специальный prop с говорящим именем:

```jsx
function Bio({ html }) {
  return <div className="bio" dangerouslySetInnerHTML={{ __html: html }} />;
}
```

React записывает строку в `innerHTML` без проверок. В проверке `<img src=x onerror="alert(1)">` попал в DOM вместе с обработчиком. Имя «dangerously» и неудобный объект `{ __html }` сделаны специально — чтобы такой код было видно на ревью.

Если HTML хоть частично приходит от пользователя, его очищают перед вставкой:

```jsx
import DOMPurify from 'dompurify';

function Bio({ html }) {
  return <div className="bio" dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(html) }} />;
}
```

DOMPurify разбирает HTML и выбрасывает всё, что может выполнить код: скрипты, обработчики `on*`, опасные URL. В проверке `<img onerror>` превратился в `<img src="x">`, а `<b>` остался. Очищать лучше на клиенте прямо перед вставкой, потому что сервер не знает, как именно браузер разберёт строку. Ещё надёжнее — не хранить HTML вовсе: хранить Markdown или структуру документа и рендерить её компонентами.

На уровне всей страницы запись в `innerHTML` можно ограничить браузерным механизмом Trusted Types: через :term[CSP]{def="Content Security Policy: правила, откуда странице можно загружать и выполнять код"} разрешаются только значения, прошедшие доверенную политику. Это страховка на случай, если опасная строка всё-таки дойдёт до `dangerouslySetInnerHTML`.

## Spread пользовательских props

Удобный приём — разложить объект в props:

```jsx
<div {...settings.widgetProps} />
```

Если объект пришёл от пользователя или из базы, которую пользователь может изменить, вместе с безобидным `className` в нём может оказаться `dangerouslySetInnerHTML`, `href`, `style` или `onClick`. В проверке JSON с полем `dangerouslySetInnerHTML` после spread вставил `<img onerror>` в DOM. React не отличает props, которые написал разработчик, от props, которые пришли из данных.

Правило — раскладывать в props только объекты, которые собрал сам код, а данные пользователя передавать в конкретные поля:

```jsx
<div className={pickAllowedClass(settings.theme)} title={settings.title} />
```

Это частый корень XSS в конструкторах страниц и CMS, где «настройки блока» хранятся как произвольный JSON.

## Серверный рендер

На сервере React тоже экранирует текст и атрибуты: `renderToString` выводит пользовательские строки как сущности. Но вокруг React-разметки сервер обычно собирает HTML сам, и тут появляется своя классическая ошибка — передача состояния клиенту:

```js
const html = `
  <div id="root">${appHtml}</div>
  <script>window.__STATE__ = ${JSON.stringify(state)}</script>
`;
```

`JSON.stringify` не экранирует `</script>`. Если в состоянии есть описание `</script><script>alert(1)</script>`, браузер закроет тег на первом `</script>` внутри строки, и следующий скрипт выполнится. Фикс — экранировать `<` при сериализации:

```js
const json = JSON.stringify(state).replace(/</g, '\\u003c');
```

`<` внутри строки JSON — тот же символ `<`, поэтому данные после разбора не меняются, но HTML-парсер больше не видит `</script>`. Фреймворки делают это сами, а при ручном SSR это нужно помнить.

### Серверные функции — публичные эндпоинты

Server Functions (Server Actions) выглядят как обычные функции, которые компонент вызывает напрямую. На деле фреймворк превращает каждую в HTTP-эндпоинт, и его можно вызвать без интерфейса — с любыми аргументами. Поэтому внутри серверной функции проверяют аутентификацию, права и входные данные, как в любом API. Кнопка, которую видят только админы, не защищает функцию, которую она вызывает.

Это не теоретический риск: в декабре 2025 года в пакетах React Server Components нашли уязвимость CVE-2025-55182 с максимальной оценкой :term[CVSS]{def="шкала тяжести уязвимостей от 0 до 10"} 10.0. Небезопасная десериализация в протоколе серверных функций позволяла выполнить код на сервере без аутентификации, и затронуты были приложения на Next.js и других фреймворках с :term[RSC]{def="React Server Components: компоненты, которые выполняются только на сервере"}. Главный вывод для собеседования — серверная часть React-приложения — это сервер, со всеми его рисками, а зависимости фреймворка нужно обновлять сразу после выхода исправлений.

> Как устроены серверные функции и что в них проверять — в [RSC и React 19](/content/reactjs/rsc-and-react-19).

## Секреты и границы доверия

Всё, что попало в клиентский бандл, — публично. Переменные окружения с префиксами `VITE_` и `NEXT_PUBLIC_` встраиваются в JavaScript и видны любому в DevTools:

```js
const key = import.meta.env.VITE_PAYMENT_SECRET;   // опубликованный секрет
```

На клиенте — только ключи, которые и задуманы публичными (publishable key платёжной системы, ключ карт с ограничением по домену). Приватные ключи, токены доступа к API третьих сторон и проверки прав — на сервере.

Клиентские проверки — `if (user.isAdmin)` перед кнопкой, защищённый маршрут — это удобство интерфейса. Любой вызов API нужно проверять на сервере так, как будто клиента не существует (подробно — в [Роутинге](/content/reactjs/routing)).

Остальные темы безопасности фронтенда не специфичны для React и разобраны в отдельной главе:

- где хранить токены и почему httpOnly-cookie требуют защиты от :term[CSRF]{def="подделка межсайтового запроса: чужой сайт отправляет запрос от имени пользователя с его куками"} — [Аутентификация и токены](/content/security-perfomance/authentication-and-tokens), [CSRF](/content/security-perfomance/csrf);
- Content-Security-Policy, которая ограничивает источники скриптов и снижает ущерб от XSS — [CSP и заголовки безопасности](/content/security-perfomance/csp-and-security-headers);
- зависимости и атаки на цепочку поставок — [Supply chain](/content/security-perfomance/supply-chain-and-vulnerabilities).

## Красные флаги в ответе

- **«React полностью защищает от XSS».** Он экранирует текст и атрибуты и блокирует `javascript:`. `dangerouslySetInnerHTML`, `data:`-ссылки, spread пользовательских props и ручной SSR остаются на разработчике.
- **«`javascript:` в ссылках — опасно, React только предупреждает».** React 19 такие ссылки блокирует. Но проверка протокола по белому списку всё равно нужна: другие схемы проходят.
- **«Очищу HTML регулярным выражением».** HTML не разбирается регулярками, обходов десятки. Нужен парсер-санитайзер вроде DOMPurify.
- **«Server Action вызывается только из моей формы».** Это HTTP-эндпоинт, его можно вызвать напрямую с любыми данными.
- **«Секретный ключ в переменной окружения — значит, скрыт».** Всё с префиксом `VITE_` или `NEXT_PUBLIC_` попадает в бандл.

## Как спрашивают на собеседовании

::question
Как React защищает от XSS по умолчанию?

#answer
Всё, что вставлено в JSX как текст или значение атрибута, экранируется: `<`, `>`, `&` и кавычки становятся HTML-сущностями, поэтому строка с тегами показывается как текст и не выполняется.

#more
На клиенте React пишет текст через DOM-свойства, а не собирает HTML, поэтому строка не разбирается как разметка. На сервере `renderToString` экранирует текст и атрибуты. Объекты, похожие на элементы, но пришедшие из JSON, React не отрисует: у них нет `Symbol` в `$$typeof`. Защита заканчивается там, где HTML вставляют напрямую, где опасно само значение (URL) и где HTML собирают вручную вокруг React.
::

::question
Чем опасен dangerouslySetInnerHTML?

#answer
Он вставляет HTML как есть, без экранирования. Если в строке есть пользовательские данные, это прямой путь к XSS. HTML нужно очищать санитайзером (DOMPurify) или не использовать этот prop.

#more
Очищают на клиенте перед вставкой: сервер не знает, как именно браузер разберёт строку, а различия в разборе — классический способ обойти фильтр. Регулярные выражения для этого не подходят. Надёжнее хранить контент как Markdown или структуру документа и рендерить компонентами. На уровне страницы запись в `innerHTML` дополнительно ограничивают через Trusted Types и CSP.
::

::question
Защищает ли React от опасных ссылок?

#answer
Частично. React 19 блокирует ссылки со схемой `javascript:` — подменяет их на URL, который бросает ошибку. Остальные схемы он пропускает, поэтому ссылки из пользовательских данных проверяют по белому списку протоколов.

#more
Блокировка работает и на клиенте, и при серверном рендере, в любом регистре и с пробелами перед схемой. Но `data:text/html` в `iframe src` или ссылке, `vbscript:` и редиректы на чужие домены React не проверяет. Правильно — разобрать URL через `new URL()` и пропускать только `http:`, `https:`, `mailto:`. Для внешних ссылок с `target="_blank"` — `rel="noopener noreferrer"`.
::

::question
Почему нельзя раскладывать пользовательские данные в props через spread?

#answer
Вместе с безобидными полями в объекте могут прийти опасные props: `dangerouslySetInnerHTML`, `href`, обработчики. React не отличает props, которые написал разработчик, от пришедших из данных.

#more
Это частый корень XSS в конструкторах страниц и CMS, где настройки блоков хранятся как произвольный JSON и раскладываются в компоненты. Даже `style` может быть опасен — оверлей поверх страницы для фишинга. Данные пользователя передают в конкретные проверенные поля, а объект для spread собирает только код.
::

::question
Как безопасно передать состояние с сервера на клиент при SSR?

#answer
Сериализовать в JSON и экранировать `<`, чтобы строка `</script>` внутри данных не закрыла тег скрипта раньше времени.

#more
`JSON.stringify` не экранирует `</script>`, и данные пользователя могут выйти из тега и выполнить свой скрипт. Замена `<` на `<` сохраняет данные (это тот же символ внутри строки JSON), но HTML-парсер его не видит. Фреймворки делают это сами, при ручном SSR — нужно помнить. Альтернатива — `<script type="application/json">` и чтение через `JSON.parse(el.textContent)`.
::

::question
Можно ли хранить API-ключи в React-приложении?

#answer
Только публичные. Всё, что попадает в клиентский бандл, включая переменные окружения с префиксами `VITE_` и `NEXT_PUBLIC_`, видно любому пользователю.

#more
Приватные ключи живут на сервере: в бэкенде, серверных функциях, Server Components. Клиент вызывает свой сервер, а тот — сторонний API с ключом. Серверные функции при этом — публичные HTTP-эндпоинты: в них проверяют аутентификацию, права и входные данные, как в любом API.
::

## Практика

::practice{title="Найди уязвимости"}
Компонент карточки автора в блоге. Найди все уязвимости:

```jsx
function AuthorCard({ author }) {
  return (
    <div {...author.cardProps}>
      <h3>{author.name}</h3>
      <div dangerouslySetInnerHTML={{ __html: author.bio }} />
      <a href={author.website} target="_blank">Сайт автора</a>
    </div>
  );
}
```

#solution
Три проблемы, `author.name` — в порядке: текст экранируется.

1. **`{...author.cardProps}`** — пользовательский объект в props. В нём может оказаться `dangerouslySetInnerHTML`, `href`, `style`.
2. **`dangerouslySetInnerHTML` с `author.bio`** — HTML без очистки.
3. **`href={author.website}`** — `javascript:` React 19 заблокирует, но `data:`-ссылку пропустит. Плюс нет `rel` у `target="_blank"`.

```jsx
import DOMPurify from 'dompurify';

const THEMES = { light: 'card card--light', dark: 'card card--dark' };

function safeUrl(url) {
  try {
    const u = new URL(url);
    return ['http:', 'https:'].includes(u.protocol) ? u.href : undefined;
  } catch {
    return undefined;
  }
}

function AuthorCard({ author }) {
  const website = safeUrl(author.website);
  return (
    <div className={THEMES[author.cardTheme] ?? THEMES.light}>
      <h3>{author.name}</h3>
      <div dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(author.bio) }} />
      {website && <a href={website} target="_blank" rel="noopener noreferrer">Сайт автора</a>}
    </div>
  );
}
```

Вместо произвольных props — выбор из белого списка тем, HTML очищен, ссылка проверена по протоколу.
::

::practice{title="Почему на странице выполнился чужой скрипт?"}
Сервер рендерит страницу и передаёт данные клиенту. После того как пользователь сохранил странное описание профиля, у всех посетителей страницы выполняется его скрипт, хотя весь вывод идёт через JSX:

```js
app.get('/u/:id', async (req, res) => {
  const user = await db.user(req.params.id);
  const appHtml = renderToString(<Profile user={user} />);
  res.send(`
    <div id="root">${appHtml}</div>
    <script>window.__USER__ = ${JSON.stringify(user)}</script>
    <script src="/client.js"></script>
  `);
});
```

#solution
JSX тут ни при чём: `renderToString` экранировал всё правильно. Дыра в ручной вставке состояния. `JSON.stringify` не экранирует `</script>`, и описание `</script><script>steal()</script>` закрывает тег раньше времени — следующий тег `<script>` выполняется как код страницы.

Фикс — экранировать `<` при сериализации:

```js
const json = JSON.stringify(user).replace(/</g, '\\u003c');
res.send(`
  <div id="root">${appHtml}</div>
  <script>window.__USER__ = ${json}</script>
  <script src="/client.js"></script>
`);
```

Внутри строки JSON `<` — тот же `<`, поэтому `window.__USER__` получит исходные данные, а HTML-парсер больше не увидит закрывающий тег. Заодно стоит передавать клиенту только нужные поля, а не весь объект из базы: в нём легко оказаться e-mail или хешу пароля.
::
