# Производное состояние и поток данных

Какое состояние хранить, какое вычислять и в каком компоненте его держать. Большинство багов с состоянием — не сломанная логика, а лишнее состояние, которое разошлось с другим. Спрашивают про lifting state up и сброс через `key`. Глубже — почему состояние «прилипает» к месту в дереве, чем опасна копия props в state и как поменять состояние при смене props без эффекта.

::tldr
- **Храни минимум, остальное вычисляй в рендере.** Если значение выводится из props или другого состояния, отдельный `useState` для него рано или поздно разойдётся с источником.
- **Храни идентификатор, а не копию объекта.** Копия выбранного товара устареет, как только товар изменится в списке.
- **У каждого значения один владелец.** Общее состояние поднимают в ближайшего общего родителя, а лишнее — опускают к месту использования.
- **Состояние привязано к позиции в дереве.** Тот же тип на том же месте сохраняет состояние, другой тип или другой `key` — сбрасывает. Компонент, объявленный внутри компонента, сбрасывается на каждом рендере.
- **`useState(props.x)` читает prop один раз.** Чтобы сбросить состояние при смене данных, меняют `key`, а скорректировать часть состояния можно прямо в рендере — без эффекта.
::

## Хранить или вычислять

Сквозной пример — страница каталога:

```jsx
function Catalog({ products }) {
  const [query, setQuery] = useState('');
  const [selectedId, setSelectedId] = useState(null);

  const visible = products.filter((p) => p.title.toLowerCase().includes(query.toLowerCase()));
  const selected = products.find((p) => p.id === selectedId);

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ProductList items={visible} onSelect={setSelectedId} />
      <Details product={selected} />
    </>
  );
}
```

Здесь два куска состояния: строка поиска и id выбранного товара. Всё остальное — `visible`, `selected`, количество найденных — **производное**: оно вычисляется в рендере из props и состояния.

Перед каждым `useState` стоит спросить: можно ли получить это значение из того, что уже есть? Если да, отдельное состояние — это второй источник истины, который нужно синхронизировать вручную:

```jsx
// ❌ два источника: при каждом изменении items нужно не забыть обновить total
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);

// ✅ total вычисляется при рендере и всегда верен
const total = items.reduce((sum, i) => sum + i.price, 0);
```

Синхронизировать через эффект ещё хуже. Эффект выполняется после commit, поэтому сначала на экран попадает старое значение, потом идёт второй рендер с новым. В проверке фильтрация через эффект дала два commit — сначала со старым списком, потом с новым. Вычисление в рендере даёт один.

> Почему эффект для производных данных — анти-паттерн и чем его заменить — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization). Если вычисление действительно дорогое, его кешируют через `useMemo` — когда и зачем, в [Производительности](/content/reactjs/performance).

### Идентификатор, а не копия

В каталоге хранится `selectedId`, а не сам выбранный товар. Почему не проще положить объект?

```jsx
const [selected, setSelected] = useState(null);
<ProductList items={visible} onSelect={setSelected} />  // кладём объект
```

Товар — часть `products`. Если его переименуют, в списке будет новое название, а в `selected` — копия со старым. В проверке после переименования «Чайник» → «Чайник 2.0» список показал новое имя, а панель деталей — старое. С `selectedId` объект каждый раз ищется в актуальном списке, и расхождения быть не может.

Производные значения разобраны. Но и у того, что хранить нужно, есть правила формы.

## Как устроить само состояние

Документация React сводит это к пяти правилам:

1. **Группируй то, что меняется вместе.** Координаты `x` и `y` — один объект, если всегда обновляются вместе.
2. **Избегай противоречий.** Три флага `isLoading`, `isError`, `isSuccess` допускают невозможные комбинации — например, загрузка и ошибка одновременно.
3. **Избегай избыточности.** Не храни то, что вычисляется.
4. **Избегай дублирования.** Один объект в двух местах состояния — это две копии, которые разойдутся. Храни id.
5. **Избегай глубокой вложенности.** Плоскую структуру (`{ byId, ids }`) проще обновлять иммутабельно, чем дерево.

Второе правило на собеседованиях любят больше всего:

```jsx
// ❌ 8 комбинаций флагов, из которых осмысленны 4
const [isLoading, setIsLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);

// ✅ одно поле — одно состояние из перечня
const [state, setState] = useState({ status: 'idle' });
// { status: 'loading' } | { status: 'success', data } | { status: 'error', error }
```

Со вторым вариантом невозможно оказаться в «загрузке с ошибкой», а TypeScript-объединение делает `data` доступным только при `status: 'success'`. Когда переходов много, такое состояние удобно вести через `useReducer` — подробно в [Хуках](/content/reactjs/advanced-hooks).

Форма состояния понятна. Следующий вопрос — в каком компоненте оно должно жить.

## Где живёт состояние

### Один владелец

У каждого значения один компонент-владелец. Остальные получают его через props и сообщают об изменениях через колбэки. В каталоге `selectedId` нужен и списку (подсветить выбранный), и панели деталей. Если каждый будет хранить свою копию, они разойдутся. Поэтому состояние живёт в их общем родителе `Catalog`.

### Поднять состояние

Когда двум соседям нужно общее значение, его **поднимают** (lifting state up) в ближайшего общего родителя:

```jsx
function TemperatureApp() {
  const [celsius, setCelsius] = useState(0);
  return (
    <>
      <CelsiusInput value={celsius} onChange={setCelsius} />
      <FahrenheitView celsius={celsius} />
    </>
  );
}
```

`CelsiusInput` стал **управляемым компонентом**: значение приходит сверху, изменения уходят наверх. Это тот же приём, что с управляемым `<input>` (подробно — в [Состоянии и событиях](/content/reactjs/state-and-events)), только для своего компонента.

### Опустить состояние

Обратная ошибка — держать состояние выше, чем нужно. Флаг «подсказка открыта» нужен только кнопке, и если он лежит в `App`, каждое наведение рендерит всё приложение. Правило — колокация: состояние живёт в самом нижнем компоненте, которому оно нужно. Это и первое лекарство от лишних рендеров (подробно — в [Производительности](/content/reactjs/performance)).

Если значение нужно далеко внизу, а поднимать его приходится через пять уровней, которые сами его не используют, это prop drilling. Его решают композицией через `children`, [контекстом](/content/reactjs/context-api) или [стором](/content/reactjs/state-management).

Мы выбрали, где состояние живёт в коде. Но у React есть ещё одно правило: где оно живёт **в дереве**.

---

## Состояние живёт в позиции

React хранит состояние не «в компоненте» и не «в функции», а в **месте дерева**, где компонент отрисован. Пока на этом месте тот же тип компонента, состояние сохраняется. Это даёт поведение, которое удивляет:

```jsx
{isCompany ? <Field label="ИНН" /> : <Field label="Паспорт" />}
```

Пользователь ввёл номер паспорта и переключил «юрлицо». Поле поменяло подпись на «ИНН», но номер остался. Для React ничего не поменялось: на той же позиции тот же тип `Field`, изменились только props.

Состояние сбрасывается, когда меняется идентичность места:

| Что изменилось | Состояние |
| --- | --- |
| тот же тип на той же позиции (тернарник) | сохраняется |
| другой `key` | сбрасывается |
| разные позиции: `{a && <Field />}{!a && <Field />}` | сбрасывается |
| другой тип на позиции или выше по дереву (`div` → `section`) | сбрасывается всё поддерево |

### Компонент внутри компонента

Отсюда частый баг:

```jsx
function Page() {
  const [n, setN] = useState(0);

  function Search() {                       // ❌ объявлен внутри Page
    const [q, setQ] = useState('');
    return <input value={q} onChange={(e) => setQ(e.target.value)} />;
  }

  return <Search />;
}
```

На каждом рендере `Page` функция `Search` создаётся заново — это **другой тип**. React видит на позиции новый тип, размонтирует старый `Search` и монтирует новый. Ввод и фокус пропадают при любом обновлении `Page`. Компоненты объявляют на верхнем уровне модуля.

### Сброс через key

Позицию можно сделать уникальной вручную — ключом:

```jsx
<ProfileForm key={user.id} user={user} />
```

При смене пользователя ключ другой, и форма монтируется заново с чистым состоянием. Это штатный способ «начать заново», без эффектов, которые обнуляют поля по одному.

Ключ сбрасывает всё. А если при смене props нужно поменять только часть состояния?

## Состояние из props

### useState(prop) не следит за prop

```jsx
function Price({ initial }) {
  const [value, setValue] = useState(initial);
  // ...
}
```

Начальное значение `useState` читается только при монтировании. Если родитель передаст новый `initial`, компонент его проигнорирует: в проверке после смены `10` → `20` на экране осталось `10`. Это «зеркалирование props в state», и почти всегда это ошибка. Варианты:

- **значение не нужно менять внутри** — не заводить состояние, читать prop напрямую;
- **это действительно начальное значение** — назвать prop `initialValue` или `defaultValue`, чтобы было видно, что обновления не будет;
- **при смене данных нужно начать заново** — `key`;
- **при смене prop нужно поправить часть состояния** — корректировка в рендере.

### Корректировка в рендере

Список с выделением: при смене `items` выделение нужно сбросить, а остальное состояние (например, режим сортировки) сохранить. С эффектом сначала отрисуется старое выделение, потом пройдёт второй рендер. Документация React предлагает другой путь — запомнить прошлые props и поправить состояние прямо в рендере:

```jsx
function List({ items }) {
  const [prevItems, setPrevItems] = useState(items);
  const [selected, setSelected] = useState(null);

  if (items !== prevItems) {
    setPrevItems(items);
    setSelected(null);
  }
  // ...
}
```

`setState` во время рендера своего же компонента React обрабатывает особым образом: выбрасывает результат текущего вызова и сразу вызывает компонент снова, до commit. Кадра со старым выделением не будет: в проверке компонент был вызван дважды, а в commit попало только новое значение. Условие обязательно — без него получится бесконечный цикл и ошибка `Too many re-renders`.

Это редкий приём. Сначала стоит проверить, нельзя ли вычислить значение (хранить `selectedId` и проверять, есть ли он в `items`) или сбросить всё через `key`.

## Красные флаги в ответе

- **«Синхронизирую производное значение через `useEffect`».** Это лишний рендер и кадр со старыми данными. Производное значение вычисляют в рендере.
- **«Храню выбранный объект в состоянии».** Копия устареет при изменении списка. Хранят id.
- **«Чем выше состояние, тем лучше — всё в одном месте».** Состояние высоко в дереве рендерит всё под ним. Его держат в ближайшем общем родителе тех, кому оно нужно.
- **«`useState(props.value)` синхронизирует состояние с prop».** Начальное значение читается один раз.
- **«Компоненты можно объявлять внутри других для удобства».** Каждый рендер создаёт новый тип, и вложенный компонент теряет состояние.

## Как спрашивают на собеседовании

::question
Как понять, что значение не нужно хранить в состоянии?

#answer
Если его можно вычислить из props или другого состояния во время рендера, это производное значение. Его не хранят, а вычисляют: так невозможен рассинхрон.

#more
Лишнее состояние — второй источник истины, который нужно синхронизировать вручную. Через эффект это ещё и лишний рендер с кадром старых данных. Дорогое вычисление кешируют через `useMemo`, а не через состояние. Тот же принцип для объектов: храним id выбранного элемента, а объект находим в актуальном списке.
::

::question
Почему несколько булевых флагов хуже одного status?

#answer
Флаги допускают невозможные комбинации: загрузка и ошибка одновременно. Одно поле `status` с перечислением значений исключает противоречия.

#more
Три флага дают восемь комбинаций, осмысленны из них четыре. Каждый обработчик должен помнить, какие флаги сбросить. Состояние как размеченное объединение (`{ status: 'success', data }`) делает данные доступными только в нужном состоянии, и TypeScript это проверяет. При многих переходах удобен `useReducer`: переходы описаны в одном месте.
::

::question
Что такое lifting state up и колокация состояния?

#answer
Lifting state up — перенос общего состояния двух компонентов в их ближайшего общего родителя, который передаёт значение и колбэк вниз. Колокация — обратное правило: держать состояние как можно ниже, рядом с тем, кто его использует.

#more
Это два направления одного решения: у значения должен быть один владелец, и он должен быть как можно ниже. Слишком высоко — лишние рендеры и prop drilling, слишком низко — состояние нельзя разделить. Prop drilling решают композицией через `children`, контекстом или стором, а не подъёмом в корень.
::

::question
Почему состояние сохраняется, когда тернарник показывает «другой» компонент?

#answer
React хранит состояние в позиции дерева. Если на той же позиции тот же тип компонента, React считает его тем же экземпляром и сохраняет состояние, меняются только props.

#more
`{a ? <Field label="ИНН" /> : <Field label="Паспорт" />}` — одна позиция и один тип, состояние общее. Сбросить можно разными `key` или разными позициями (`{a && <Field />}{!a && <Field />}`). Смена типа на позиции или выше (`div` → `section`) сбрасывает всё поддерево. Отсюда баг с компонентом, объявленным внутри другого: новая функция на каждом рендере — новый тип, состояние и фокус теряются.
::

::question
Как сбросить состояние компонента при смене данных?

#answer
Передать `key`, который меняется вместе с данными: `<ProfileForm key={user.id} />`. React размонтирует старый экземпляр и создаст новый с чистым состоянием.

#more
`key` сбрасывает всё состояние поддерева, включая DOM, и это обычно правильно для форм. Если нужно поменять только часть состояния при смене prop, документация предлагает корректировку в рендере: запомнить прошлый prop в состоянии и при отличии вызвать сеттеры прямо в рендере. React выбросит текущий вызов и сразу повторит его до commit — без кадра со старыми данными. Эффект здесь хуже: лишний commit со старым состоянием.
::

::question
Почему `useState(props.value)` не обновляется при смене prop?

#answer
Аргумент `useState` — только начальное значение, он читается при монтировании. Дальше состояние живёт своей жизнью.

#more
Это «зеркалирование props в state», и в большинстве случаев состояние вообще не нужно — достаточно читать prop. Если значение действительно начальное, prop называют `initialValue` или `defaultValue`. Если при смене данных нужно начать заново — `key`. Если нужно поправить часть состояния — корректировка в рендере. Эффект `useEffect(() => setValue(props.value), [props.value])` даёт лишний рендер и затирает ввод пользователя.
::

::question
Что значит single source of truth?

#answer
У каждого куска данных один владелец — компонент, который его хранит. Остальные получают данные через props и меняют через колбэки владельца.

#more
Две копии одних данных всегда расходятся: копия выбранного объекта, состояние, продублированное из props, локальная копия серверных данных без инвалидации. Поэтому храним минимум и идентификаторы, а всё остальное вычисляем. Для серверных данных источник истины — сервер, и его кеш держит библиотека загрузки, а не `useState` (подробно — в [Загрузке данных](/content/reactjs/data-fetching)).
::

## Практика

::practice{title="Найди баг"}
После переименования товара в списке панель деталей показывает старое название:

```jsx
function Catalog() {
  const [products, setProducts] = useState(initialProducts);
  const [selected, setSelected] = useState(null);

  function rename(id, title) {
    setProducts((list) => list.map((p) => (p.id === id ? { ...p, title } : p)));
  }

  return (
    <>
      <ProductList items={products} onSelect={setSelected} onRename={rename} />
      <Details product={selected} />
    </>
  );
}
```

#solution
В `selected` лежит копия объекта, сделанная в момент выбора. `rename` создаёт новый объект в `products`, а `selected` указывает на старый. Два источника истины разошлись.

Фикс — хранить id, а объект находить в актуальном списке:

```jsx
function Catalog() {
  const [products, setProducts] = useState(initialProducts);
  const [selectedId, setSelectedId] = useState(null);
  const selected = products.find((p) => p.id === selectedId);

  function rename(id, title) {
    setProducts((list) => list.map((p) => (p.id === id ? { ...p, title } : p)));
  }

  return (
    <>
      <ProductList items={products} onSelect={(p) => setSelectedId(p.id)} onRename={rename} />
      <Details product={selected} />
    </>
  );
}
```

Бонус: если выбранный товар удалят, `selected` станет `undefined` сам, без отдельной логики сброса.
::

::practice{title="Почему поиск теряет ввод?"}
Каждую секунду на странице обновляются часы, и вместе с ними очищается поле поиска:

```jsx
function Page() {
  const now = useNow(); // состояние, которое меняется раз в секунду

  function Search() {
    const [q, setQ] = useState('');
    return <input value={q} onChange={(e) => setQ(e.target.value)} />;
  }

  return (
    <main>
      <time>{now}</time>
      <Search />
    </main>
  );
}
```

#solution
`Search` объявлен внутри `Page`. На каждом рендере `Page` создаётся новая функция — для React это новый тип компонента. На той же позиции другой тип, поэтому старый `Search` размонтируется вместе с состоянием, а новый монтируется с пустой строкой и без фокуса.

Фикс — объявить компонент на верхнем уровне модуля:

```jsx
function Search() {
  const [q, setQ] = useState('');
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}

function Page() {
  const now = useNow();
  return (
    <main>
      <time>{now}</time>
      <Search />
    </main>
  );
}
```

Теперь `Search` — один и тот же тип, и рендер `Page` сохраняет его состояние.
::

::practice{title="Убери эффекты"}
Перепиши компонент без `useEffect`. При смене `items` выделение должно сбрасываться, а фильтр — сохраняться:

```jsx
function List({ items }) {
  const [filter, setFilter] = useState('');
  const [visible, setVisible] = useState(items);
  const [selected, setSelected] = useState(null);

  useEffect(() => {
    setVisible(items.filter((i) => i.includes(filter)));
  }, [items, filter]);

  useEffect(() => {
    setSelected(null);
  }, [items]);

  // ...
}
```

#solution
`visible` — производное значение, его вычисляют в рендере. Сброс выделения — корректировка состояния при смене prop, её делают в рендере через запомненный прошлый `items`:

```jsx
function List({ items }) {
  const [filter, setFilter] = useState('');
  const [selected, setSelected] = useState(null);
  const [prevItems, setPrevItems] = useState(items);

  if (items !== prevItems) {
    setPrevItems(items);
    setSelected(null);
  }

  const visible = items.filter((i) => i.includes(filter));
  // ...
}
```

Было: при смене фильтра два commit (старый список, потом новый), при смене `items` — кадр со старым выделением. Стало: один commit со свежими данными. Если сохранять фильтр не нужно, всё решает `<List key={listId} items={items} />` без единой строки логики.
::
