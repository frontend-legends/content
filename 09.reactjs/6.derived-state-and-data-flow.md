# Производное состояние и поток данных

Самый недооценённый навык в React - **не добавлять состояние**. Большая часть багов это не сломанная логика, а лишнее состояние, которое рассинхронизировалось с другим состоянием. Правило: храни минимум, остальное **вычисляй**.

---

## Производное vs хранимое состояние

Прежде чем писать `useState`, спроси: **можно ли это вычислить из того, что уже есть?** Если да - это производное значение, его не хранят.

```jsx
// ❌ Дублирующее состояние - два источника истины, рассинхрон неизбежен
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
// при каждом изменении items надо не забыть обновить total...

// ✅ total - производное, вычисляется при рендере
const [items, setItems] = useState([]);
const total = items.reduce((sum, i) => sum + i.price, 0);
```

<b class="text-on-semi-light">Почему это важно</b> - <span class="text-gray">Каждый дополнительный кусок состояния - это потенциальный рассинхрон. Если `total` можно посчитать из `items`, то отдельный `useState` для него гарантированно когда-нибудь разойдётся с реальностью.</span>

---

## Принципы хорошего состояния

Официальные правила «structuring state» из документации React:

1. **Группируй связанное.** Если две переменные всегда меняются вместе - объедини в объект.
2. **Избегай противоречий.** `isLoading` + `isError` + `isSuccess` тремя булями допускают невозможные комбинации. Лучше один `status: 'idle' | 'loading' | 'success' | 'error'`.
3. **Избегай избыточности.** Не храни то, что выводится из props или другого state.
4. **Избегай дублирования.** Один и тот же объект в двух местах state - источник рассинхрона. Храни `id`, а объект ищи по нему.
5. **Не вкладывай глубоко.** Плоское состояние проще обновлять иммутабельно.

```jsx
// ❌ Невозможные состояния возможны
const [isLoading, setLoading] = useState(false);
const [error, setError] = useState(null);
const [data, setData] = useState(null);

// ✅ Один источник истины - конечный автомат
const [status, setStatus] = useState('idle'); // idle | loading | success | error
```

## Single source of truth

У каждого куска данных должен быть **один владелец** - один компонент, который хранит это состояние. Остальные получают его через props.

```jsx
// ❌ Выбранный id хранят и список, и панель - кто прав?
// ✅ Поднять до общего родителя - один источник истины
function App() {
  const [selectedId, setSelectedId] = useState(null);
  return (
    <>
      <List selectedId={selectedId} onSelect={setSelectedId} />
      <Details id={selectedId} />
    </>
  );
}
```

## Колокация состояния

Обратная сторона: **не поднимай состояние выше, чем нужно**. Держи его как можно ближе к месту использования.

```jsx
// ❌ Состояние тултипа живёт в App, хотя нужно только кнопке
// ✅ Пусть состояние живёт внутри компонента, который им пользуется
function Button() {
  const [hovered, setHovered] = useState(false);
  // ...
}
```

<b class="text-on-semi-light">Баланс</b> - <span class="text-gray">Поднимай состояние только до **ближайшего общего родителя** тех компонентов, которым оно реально нужно. Слишком высоко - лишние ререндеры и prop drilling; слишком низко - не получится разделить.</span>

> Колокация - первое лекарство от проблем с производительностью: состояние, живущее низко, перерисовывает маленькое поддерево вместо всего приложения.

---

## Lifting state up

Когда двум компонентам нужно общее состояние - его **поднимают** в общего родителя, а вниз передают значение и колбэк. Это базовый паттерн обмена данными между «соседями».

```jsx
function TemperatureApp() {
  const [celsius, setCelsius] = useState(0);
  return (
    <>
      <CelsiusInput value={celsius} onChange={setCelsius} />
      <FahrenheitView celsius={celsius} />
    </>
  );
}
```

Когда prop drilling становится болезненным (данные тащат через много уровней) - на сцену выходят [контекст](/content/reactjs/context-api) и [стейт-менеджеры](/content/reactjs/state-management).

---

## Сброс состояния через key

Иногда состояние нужно **сбросить** при смене данных. Не эффектом, а через `key`: смена ключа заставляет React уничтожить старый компонент и создать новый с чистым состоянием.

```jsx
// При смене userId форма полностью пересоздаётся с нуля
<ProfileForm key={userId} userId={userId} />
```

<b class="text-on-semi-light">Почему это лучше эффекта</b> - <span class="text-gray">Альтернатива - `useEffect`, который вручную обнуляет поля при смене `userId`. Это лишний эффект и источник багов. `key` решает задачу декларативно: новый ключ = новый компонент.</span>

---

## Дорогие вычисления

Если производное значение считается **дорого** (тяжёлый фильтр/сортировка больших данных), его кешируют через `useMemo` - но только когда профайлер показал, что это узкое место.

```jsx
const sorted = useMemo(
  () => bigList.sort(expensiveCompare),
  [bigList]
);
```

> Не оборачивай в `useMemo` всё подряд: для дешёвых вычислений мемоизация дороже самого вычисления. Подробнее - в [производительности](/content/reactjs/performance).

## Однонаправленный поток - итог

```
       state (один владелец)
          │  props ↓
   ┌──────┴──────┐
 Child A       Child B
   │ callback ↑   │
   └─────── setState ───────┘
```

Данные идут вниз через props, изменения идут вверх через колбэки, состояние живёт в одном месте. Это вся модель потока данных в React.

## Вопросы на собеседовании

<b class="text-on-semi-light">Как понять, что значение не нужно хранить в state?</b>
<span class="text-gray">Если его можно вычислить из props или другого state - это производное значение, вычисляй при рендере, а не дублируй в state.</span>

<b class="text-on-semi-light">Почему три булевых флага состояния хуже одного status?</b>
<span class="text-gray">Несколько булей допускают невозможные комбинации (loading + error одновременно). Один `status` с перечислением исключает противоречивые состояния.</span>

<b class="text-on-semi-light">Что такое колокация состояния и зачем она нужна?</b>
<span class="text-gray">Держать состояние максимально близко к месту использования. Это уменьшает prop drilling и ререндеры - меняется только маленькое поддерево.</span>

<b class="text-on-semi-light">Как сбросить состояние компонента при смене данных?</b>
<span class="text-gray">Передать новый `key` - React пересоздаст компонент с чистым состоянием. Это лучше, чем обнулять поля эффектом.</span>

<b class="text-on-semi-light">Что значит single source of truth?</b>
<span class="text-gray">У каждого куска данных один владелец-компонент. Остальные получают данные через props, чтобы не было рассинхрона между копиями.</span>
