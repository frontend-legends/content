# Context API

Как передать значение глубоко вниз по дереву без prop drilling и чем за это платишь. На mid спрашивают, какую проблему решает контекст и почему объект в `value` перерисовывает всех. На senior — как обновление контекста проходит сквозь `memo`, почему у контекста нет частичной подписки и почему он не заменяет стор.

::tldr
- **Контекст доставляет значение любому потомку провайдера** без передачи через промежуточные компоненты. Компонент читает ближайший провайдер выше себя, без провайдера — значение по умолчанию.
- **При смене `value` рендерятся все компоненты, которые читают контекст**, даже если они под `memo`. Значения сравниваются через `Object.is`.
- **Объект-литерал в `value` — новая ссылка на каждом рендере провайдера**, и все потребители рендерятся без причины. Лечится `useMemo` или вынесением провайдера в отдельный компонент с `children`.
- **Частичной подписки нет:** компонент, которому нужен `user`, рендерится и при смене `theme`. Решение — разделить контекст по частоте изменений.
- **Контекст — транспорт, а не стор.** Он подходит для редко меняющихся значений (тема, язык, текущий пользователь, зависимости), а частые обновления с многими потребителями — задача стора с селекторами.
::

---

## Зачем нужен контекст

Тема оформления нужна кнопке глубоко внизу, а живёт в корне приложения:

```jsx
<App theme="dark">
  <Layout theme="dark">
    <Sidebar theme="dark">
      <Button theme="dark" />
```

`Layout` и `Sidebar` тему не используют, но обязаны принять её и передать дальше. Это **prop drilling**: каждый промежуточный компонент знает о данных, которые ему не нужны, и любое переименование проходит через все уровни.

Сначала стоит проверить, нужен ли контекст вообще. Часто prop drilling — признак того, что компоненты разбиты неудачно, и его решает композиция: если `Layout` принимает готовые элементы через `children`, тема передаётся прямо туда, где создаётся `Button`:

```jsx
<Layout>
  <Sidebar>
    <Button theme={theme} />
  </Sidebar>
</Layout>
```

Если данные действительно нужны многим компонентам на разной глубине — тема, текущий пользователь, язык, — нужен контекст. Сквозной пример темы — приложение с темой и авторизацией.

---

## Как работает контекст

Три шага: создать контекст, поставить провайдер, прочитать значение.

```jsx
const ThemeContext = createContext('light');      // 1. значение по умолчанию

function App() {
  const [theme, setTheme] = useState('dark');
  return (
    <ThemeContext value={theme}>                   {/* 2. провайдер */}
      <Layout />
    </ThemeContext>
  );
}

function Button() {
  const theme = useContext(ThemeContext);          // 3. ближайший провайдер выше
  return <button className={theme}>OK</button>;
}
```

С React 19 провайдером служит сам контекст: `<ThemeContext value>`. Старая запись `<ThemeContext.Provider>` работает так же — в React 19 `ThemeContext.Provider` и есть `ThemeContext`.

Правила чтения:

- **Ближайший провайдер выше.** Провайдеры можно вкладывать: внутренний переопределяет внешний для своего поддерева. Так делают «светлую карточку» внутри тёмной страницы.
- **Значение по умолчанию — только без провайдера.** Аргумент `createContext` используется, если выше нет ни одного провайдера. Это не «начальное значение», и обычно его появление — ошибка: забыли провайдер.
- **Компонент не видит своё же значение.** `useContext` ищет провайдер *выше* компонента. `App`, который рендерит `<ThemeContext value="dark">`, сам прочитает внешнее значение или значение по умолчанию.
- **Условное чтение — через `use`.** `use(ThemeContext)` читает контекст так же, но его можно вызвать в условии (подробно — в [Механике хуков](/content/reactjs/hooks-mechanics)).

### Кастомный хук с защитой

Значение по умолчанию `null` и хук, который падает без провайдера, превращают тихую ошибку в громкую:

```jsx
const AuthContext = createContext(null);

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth должен вызываться внутри <AuthProvider>');
  return ctx;
}

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const value = useMemo(() => ({ user, login: setUser, logout: () => setUser(null) }), [user]);
  return <AuthContext value={value}>{children}</AuthContext>;
}
```

Потребитель пишет `const { user } = useAuth()` и не знает про контекст вообще. API контекста можно поменять в одном месте.

Значение дошло до потребителя. Что происходит, когда оно меняется?

---

## Что происходит при смене значения

Когда провайдер рендерится с новым `value`, React сравнивает его со старым через `Object.is`. Если значения разные, React находит в поддереве провайдера все компоненты, которые читают этот контекст, и планирует их рендер. Факт чтения записан на fiber компонента в момент `useContext` — подробно в [Механике хуков](/content/reactjs/hooks-mechanics).

Важная деталь — **обновление проходит сквозь `memo`**:

```jsx
const Sidebar = memo(function Sidebar() {
  return <ThemedButton />;                // читает ThemeContext
});

function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext value={theme}>
      <Sidebar />
      {children}
    </ThemeContext>
  );
}
```

При смене темы в проверке:

| Компонент | Рендеров после смены темы |
| --- | --- |
| `Sidebar` (`memo`, контекст не читает) | 0 — пропущен |
| `ThemedButton` внутри него (читает контекст) | 1 — обновился, несмотря на `memo` выше |
| другой `memo`-компонент без контекста | 0 |
| компонент из `children` | 0 — элемент создан выше, не изменился |

`memo` останавливает рендер, который идёт от родителя, но не обновление контекста. Потребитель обновится, где бы он ни был. Это правильно: иначе `memo` где-нибудь посередине ломал бы тему.

Отсюда понятно, как контекст может стоить дорого. Каждое изменение `value` рендерит **всех** потребителей. Проблема в том, что `value` может меняться гораздо чаще, чем кажется.

## Ловушка: новый объект в value

```jsx
function App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const [query, setQuery] = useState('');

  return (
    <AppContext value={{ user, theme }}>         {/* ❌ новый объект на каждом рендере */}
      <SearchInput value={query} onChange={setQuery} />
      <Page />
    </AppContext>
  );
}
```

Пользователь печатает в поиске, `App` рендерится на каждую букву, и литерал `{ user, theme }` создаёт новый объект. `Object.is` видит новое значение, и все потребители `AppContext` рендерятся, хотя ни `user`, ни `theme` не менялись. В проверке три буквы в поле дали потребителю три лишних рендера, даже под `memo`.

Два решения:

```jsx
// 1. мемоизировать value
const value = useMemo(() => ({ user, theme }), [user, theme]);
<AppContext value={value}>

// 2. вынести провайдер в свой компонент: он рендерится только при смене своего состояния
function AppProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const value = useMemo(() => ({ user, theme, setUser, setTheme }), [user, theme]);
  return <AppContext value={value}>{children}</AppContext>;
}
```

Второй вариант лучше. Состояние `query` больше не живёт рядом с провайдером, а `children` приходят сверху и не рендерятся при смене темы. React Compiler мемоизирует такой литерал сам, но структуру это не заменяет.

`useMemo` убирает ложные изменения. Но остаются настоящие — и с ними связано главное ограничение контекста.

---

## Нет частичной подписки

Контекст передаёт одно значение целиком. Компонент, который читает из `{ user, theme }` только `user`, всё равно рендерится при смене `theme`: React не знает, какую часть значения компонент использовал. В проверке смена темы перерисовала компонент, который показывает только имя пользователя.

### Разделить контексты

Главный приём — разбить один контекст на несколько по частоте изменений и по потребителям:

```jsx
const StateContext = createContext(null);
const DispatchContext = createContext(null);

function TodosProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <StateContext value={state}>
      <DispatchContext value={dispatch}>{children}</DispatchContext>
    </StateContext>
  );
}
```

`dispatch` из `useReducer` стабилен и никогда не меняется. Кнопка «Добавить», которой нужен только `dispatch`, не рендерится при изменении списка: в проверке после двух кликов счётчик отрендерился трижды, а кнопка — один раз, при монтировании. Так же разделяют тему и пользователя, данные и методы.

### Селектор вручную

Если разделить нельзя, а потребитель тяжёлый, чтение контекста отделяют от рендера:

```jsx
function UserCard() {
  const { user } = useContext(AppContext);   // лёгкая обёртка: рендерится на любое изменение
  return <HeavyUserCard user={user} />;      // memo: рендерится, только если user изменился
}

const HeavyUserCard = memo(function HeavyUserCard({ user }) {
  /* дорогой рендер */
});
```

Обёртка рендерится при каждой смене контекста, но это дёшево. Тяжёлый компонент получает только свой срез и под `memo` пропускает рендер. В проверке две смены темы не перерисовали `HeavyUserCard` ни разу.

Есть и библиотеки с селекторами поверх контекста (`use-context-selector`). Но если подписка на части значения нужна постоянно, это знак, что нужен не контекст.

---

## Контекст — не стейт-менеджер

Контекст часто называют «встроенным Redux», и это неверно. Контекст — **транспорт**: он доставляет значение вниз по дереву. Хранит состояние `useState` или `useReducer` в провайдере, а подписки у контекста нет вообще — только «рендерить всех потребителей при смене значения».

| | Контекст | Стор (Zustand, Redux Toolkit, Jotai) |
| --- | --- | --- |
| Что это | доставка значения вниз | хранилище с подписками |
| Подписка | на всё значение | на срез через селектор |
| Кто рендерится при изменении | все потребители | только те, чей срез изменился |
| Где живут данные | в React-дереве, у провайдера | вне React, доступны и вне компонентов |
| Подходит для | тема, язык, пользователь, зависимости (клиент API, конфиг) | большое и часто меняющееся состояние |

Хорошее правило: контекст — для значений, которые меняются редко и нужны многим (или меняются часто, но нужны немногим). Для форм на сотню полей, состояния редактора или данных реального времени берут стор с селекторами. Серверные данные — вообще отдельная задача: их держит кеш библиотеки загрузки.

> Как устроены сторы и как они подписываются на изменения через `useSyncExternalStore` — в [State management](/content/reactjs/state-management). Как измерять лишние рендеры — в [Производительности](/content/reactjs/performance).

---

## Красные флаги в ответе

- **«Контекст заменяет Redux».** Контекст — транспорт без подписок на часть значения. Хранилище и селекторы — это стор.
- **«`memo` защищает от перерисовки при смене контекста».** Обновление контекста проходит сквозь `memo` до каждого потребителя.
- **«Значение по умолчанию — начальное значение контекста».** Оно используется, только если выше нет провайдера.
- **«Положу всё приложение в один контекст».** Каждое изменение любого поля рендерит всех потребителей. Контексты разделяют.
- **«`value={{ user, theme }}` — нормально».** Это новый объект на каждом рендере провайдера и лишние рендеры всех потребителей.

## Как спрашивают на собеседовании

::question{level="mid"}
Какую проблему решает контекст?

#mid
Prop drilling — передачу данных через промежуточные компоненты, которым они не нужны. Контекст доставляет значение любому потомку провайдера напрямую.

#senior
Сначала стоит попробовать композицию: если промежуточные компоненты принимают готовые элементы через `children`, данные передаются туда, где создаётся потребитель, и контекст не нужен. Контекст оправдан, когда значение нужно многим компонентам на разной глубине: тема, язык, пользователь, зависимости вроде клиента API. Цена — неявная зависимость компонента от провайдера и рендер всех потребителей при изменении.
::

::question{level="mid"}
Что произойдёт при изменении value провайдера?

#mid
Перерисуются все компоненты, которые читают этот контекст, независимо от того, какую часть значения они используют.

#senior
React сравнивает старое и новое значение через `Object.is`. Если они разные, React находит в поддереве провайдера всех потребителей (факт чтения записан на их fiber) и планирует их рендер — сквозь `memo`-границы. Компоненты, которые контекст не читают, при этом не рендерятся, если их не рендерит родитель: `memo`-компоненты и элементы из `children` остаются нетронутыми.
::

::question{level="mid"}
Почему контекст с объектом в value вызывает лишние рендеры?

#mid
Литерал `{ user, theme }` создаёт новую ссылку на каждом рендере провайдера. React сравнивает по ссылке и считает, что значение изменилось. Лечится `useMemo` для value.

#senior
Лишние рендеры случаются при любом рендере компонента с провайдером — например, когда рядом есть состояние поля ввода. Лучшее решение структурное: вынести провайдер в отдельный компонент, который получает остальное дерево через `children`. Тогда провайдер рендерится только при смене своего состояния, а `children` не рендерятся вовсе. `useMemo` нужен в любом случае, если value — объект или функция.
::

::question{level="mid"}
Как уменьшить рендеры от контекста?

#mid
Мемоизировать value, разделить контекст на несколько (например, состояние и `dispatch` отдельно), а для часто меняющихся данных взять стор с селекторами.

#senior
Разделяют по частоте изменений и по потребителям: `dispatch` из `useReducer` стабилен, поэтому компоненты, которым нужен только он, не рендерятся при изменении состояния. Если разделить нельзя, отделяют чтение от рендера: лёгкая обёртка читает контекст и передаёт срез в `memo`-компонент. Провайдер выносят в свой компонент с `children`, чтобы чужое состояние его не рендерило.
::

::question{level="senior"}
Почему memo не спасает от рендера при смене контекста?

#mid
`memo` сравнивает props и останавливает рендер, который идёт от родителя. Обновление контекста идёт не через props: React сам находит компоненты, которые читают контекст, и рендерит их.

#senior
`memo`-компонент, который сам не читает контекст, будет пропущен, но его потомки-потребители всё равно обновятся. Это намеренно: иначе любая `memo`-граница посередине ломала бы тему или язык. Если потребитель тяжёлый, чтение выносят в лёгкую обёртку, а тяжёлую часть делают `memo`-компонентом, который получает нужное поле через props.
::

::question{level="mid"}
Заменяет ли контекст Redux или Zustand?

#mid
Нет. Контекст передаёт значение вниз, но не умеет подписку на часть значения: при любом изменении рендерятся все потребители. Сторы хранят состояние и дают селекторы, обновляя только тех, чей срез изменился.

#senior
Состояние в контексте всё равно хранит `useState` или `useReducer` провайдера, а данные живут внутри React-дерева — к ним нет доступа вне компонентов. Сторы живут вне React и подключаются через `useSyncExternalStore`, который рендерит компонент только при изменении его селектора. Контекст хорош для редких изменений и для внедрения зависимостей. Часто их комбинируют: в контексте лежит экземпляр стора, а подписка идёт через селекторы стора.
::

::question{level="mid"}
Зачем оборачивать useContext в кастомный хук?

#mid
Чтобы не повторять `useContext` в каждом компоненте, дать понятную ошибку при отсутствии провайдера и спрятать устройство контекста за простым API.

#senior
Значение по умолчанию `null` плюс проверка в хуке превращают забытый провайдер из тихого бага (компонент молча получает значение по умолчанию) в понятную ошибку. Хук — единая точка, где можно поменять устройство: разделить контекст на два, перейти на стор, добавить селектор, не трогая потребителей.
::

## Практика

::practice{title="Почему тормозит ввод?"}
При вводе в поиск подтормаживает вся страница. В профайлере видно, что на каждую букву рендерятся все компоненты, которые читают `AppContext`:

```jsx
function App() {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const [query, setQuery] = useState('');

  return (
    <AppContext value={{ user, theme, setUser, setTheme }}>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <Page query={query} />
    </AppContext>
  );
}
```

#solution
`App` рендерится на каждую букву из-за `query`. Каждый рендер создаёт новый объект для `value`, и React считает, что контекст изменился: все потребители рендерятся, даже под `memo`.

Фикс — вынести провайдер в свой компонент и мемоизировать значение:

```jsx
function AppProvider({ children }) {
  const [user, setUser] = useState(null);
  const [theme, setTheme] = useState('dark');
  const value = useMemo(() => ({ user, theme, setUser, setTheme }), [user, theme]);
  return <AppContext value={value}>{children}</AppContext>;
}

function App() {
  const [query, setQuery] = useState('');
  return (
    <AppProvider>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <Page query={query} />
    </AppProvider>
  );
}
```

Теперь ввод рендерит `App` и `Page`, а `AppProvider` получает те же `children`-элементы с новыми props только у `Page`. Значение контекста — та же ссылка, и потребители, которым не нужен `query`, не рендерятся.
::

::practice{title="Почему memo не помог?"}
Карточка пользователя под `memo`, но рендерится при каждом переключении темы:

```jsx
const UserCard = memo(function UserCard() {
  const { user } = useContext(AppContext);   // AppContext = { user, theme }
  return <ExpensiveProfile user={user} />;
});
```

#solution
`memo` останавливает рендер от родителя, но не обновление контекста. `UserCard` читает `AppContext`, а значение — объект `{ user, theme }`. При смене темы объект новый, и React рендерит каждого потребителя, независимо от того, какое поле он взял.

Два варианта. Первый — разделить контекст:

```jsx
<UserContext value={user}>
  <ThemeContext value={theme}>{children}</ThemeContext>
</UserContext>
```

Второй — отделить чтение от тяжёлого рендера, если контекст разделить нельзя:

```jsx
function UserCard() {
  const { user } = useContext(AppContext);
  return <ExpensiveProfile user={user} />;
}

const ExpensiveProfile = memo(function ExpensiveProfile({ user }) {
  /* дорогой рендер */
});
```

Обёртка по-прежнему рендерится при смене темы, но это дёшево. `ExpensiveProfile` получает тот же `user` и пропускает рендер.
::

::practice{title="Что выведет?"}
```jsx
const Theme = createContext('light');

function Label() {
  return <i>{useContext(Theme)}</i>;
}

function App() {
  const theme = useContext(Theme);
  return (
    <Theme value="dark">
      <b>{theme}</b>
      <Label />
      <Theme value="contrast">
        <Label />
      </Theme>
    </Theme>
  );
}

root.render(<><App /><Label /></>);
```

#solution
```text
light dark contrast light
```

- `<b>` — `light`: `App` читает контекст выше себя, а провайдер `dark` стоит ниже, внутри его разметки. Выше провайдера нет, значит, значение по умолчанию.
- первый `Label` — `dark`: ближайший провайдер выше.
- второй `Label` — `contrast`: внутренний провайдер переопределяет внешний.
- `Label` вне `App` — `light`: провайдера выше нет.

Если `App` нужно своё значение, его берут не из контекста, а из переменной, которую он сам передаёт в `value`.
::
