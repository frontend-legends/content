# Context API

**Context** решает проблему **prop drilling** - когда данные приходится протаскивать через десяток промежуточных компонентов, которым они не нужны. Context позволяет «телепортировать» значение вниз по дереву любому потомку напрямую.

---

## Проблема prop drilling

```jsx
// theme нужен только Button, но тащится через всех
<App theme="dark">
  <Layout theme="dark">
    <Sidebar theme="dark">
      <Button theme="dark" />
```

Промежуточные компоненты вынуждены принимать и передавать `theme`, хотя сами им не пользуются. Это шумно и хрупко.

---

## Как работает Context

Три части: создать контекст, обернуть поддерево провайдером, прочитать значение хуком.

```jsx
import { createContext, useContext, useState } from 'react';

const ThemeContext = createContext('light'); // 1. создаём (дефолт)

function App() {
  const [theme, setTheme] = useState('dark');
  return (
    <ThemeContext.Provider value={theme}>  {/* 2. предоставляем */}
      <Layout />
    </ThemeContext.Provider>
  );
}

function Button() {
  const theme = useContext(ThemeContext); // 3. читаем напрямую
  return <button className={theme}>OK</button>;
}
```

Любой потомок провайдера получает значение через `useContext`, минуя промежуточные уровни. React ищет **ближайший** провайдер выше по дереву.

<b class="text-on-semi-light">Дефолтное значение</b> - <span class="text-gray">аргумент `createContext(default)` используется, только если потомок читает контекст **без** провайдера выше. Часто это признак ошибки - поэтому многие ставят `null` и кидают ошибку (см. ниже).</span>

> React 19: можно рендерить `<ThemeContext>` напрямую как провайдер вместо `<ThemeContext.Provider>`.

---

## Паттерн: кастомный хук + защита

Чтобы не дублировать `useContext` и ловить отсутствие провайдера, оборачивают в кастомный хук.

```jsx
const AuthContext = createContext(null);

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth должен использоваться внутри <AuthProvider>');
  return ctx;
}

export function AuthProvider({ children }) {
  const [user, setUser] = useState(null);
  const login = (u) => setUser(u);
  const logout = () => setUser(null);
  return (
    <AuthContext.Provider value={{ user, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}
```

Так потребитель пишет `const { user } = useAuth()` и сразу получает понятную ошибку, если забыл провайдер.

---

## Главное ограничение: ререндеры

Это то, ради чего вопрос про контекст вообще задают. **Когда значение провайдера меняется, перерисовываются ВСЕ компоненты, которые читают этот контекст** - независимо от того, какую часть значения они используют.

```jsx
// value - объект с двумя полями
<AppContext.Provider value={{ user, theme }}>
```

Если изменился `theme`, перерисуются даже компоненты, которым нужен только `user`. Context не умеет «частичную» подписку, как стейт-менеджеры.

---

## Ловушка: новый объект каждый рендер

```jsx
// ❌ value - новый объект на каждом рендере App
<AppContext.Provider value={{ user, theme }}>
```

Даже если `user` и `theme` не менялись, литерал `{ user, theme }` создаёт **новую ссылку** каждый рендер. React сравнивает по ссылке -> все потребители перерисовываются всегда.

```jsx
// ✅ Мемоизируем значение
const value = useMemo(() => ({ user, theme }), [user, theme]);
<AppContext.Provider value={value}>
```

---

## Разделение контекстов

Чтобы уменьшить ререндеры, контекст **разбивают**. Классика - отделить редко меняющийся `dispatch` от часто меняющегося `state`.

```jsx
const StateContext = createContext(null);
const DispatchContext = createContext(null); // dispatch стабилен - не вызывает ререндеры

function Provider({ children }) {
  const [state, dispatch] = useReducer(reducer, initial);
  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>
        {children}
      </DispatchContext.Provider>
    </StateContext.Provider>
  );
}
```

Компоненты, которым нужен только `dispatch`, не перерисовываются при смене `state`.

---

## Оптимизация: children не перерисовываются

Тонкий приём: то, что передано провайдеру как `children`, **не пересоздаётся** при его собственном рендере - значит, не ререндерится при смене значения.

```jsx
function ThemeProvider({ children }) {
  const [theme, setTheme] = useState('dark');
  const value = useMemo(() => ({ theme, setTheme }), [theme]);
  return <Ctx.Provider value={value}>{children}</Ctx.Provider>;
  // children пришли сверху и не зависят от theme → не ререндерятся при его смене
}
```

## Проблема селектора

Context не умеет подписку на **часть** значения: читаешь контекст - ререндеришься на **любое** его изменение. Когда это узкое место:

- **разделить контекст** на несколько по частоте изменения (как выше);
- библиотека **`use-context-selector`** - подписка на срез (как селекторы стора);
- перейти на стейт-менеджер с селекторами ([управление состоянием](/content/reactjs/state-management)).

<b class="text-on-semi-light">Senior-вывод</b> - <span class="text-gray">Контекст для **часто меняющегося** значения с многими потребителями - антипаттерн по производительности (нет точечных подписок). Либо дроби контекст, либо бери стор. Контекст идеален для **редко** меняющегося: тема, юзер, локаль.</span>

---

## Context - это не стейт-менеджер

Частое заблуждение. Context - это **транспорт** (механизм доставки значения вниз), а не хранилище с оптимизированными подписками.

| | Context | Стейт-менеджер (Redux/Zustand) |
|--|---------|-------------------------------|
| Назначение | доставка значения вниз | хранение + подписки |
| Подписка | весь объект, любой consumer | селекторы, точечная |
| Ререндеры | все потребители при смене value | только подписчики нужного среза |
| Подходит для | тема, локаль, текущий юзер, i18n | большой часто меняющийся стейт |

<b class="text-on-semi-light">Когда брать что</b> - <span class="text-gray">Context хорош для редко меняющихся глобальных данных (тема, авторизация, язык). Для часто меняющегося состояния с тысячами обновлений берут стейт-менеджер с селекторами - см. [управление состоянием](/content/reactjs/state-management).</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Какую проблему решает Context?</b>
<span class="text-gray">Prop drilling - проброс данных через промежуточные компоненты, которым они не нужны. Context доставляет значение напрямую любому потомку.</span>

<b class="text-on-semi-light">Что произойдёт при изменении value провайдера?</b>
<span class="text-gray">Перерисуются все компоненты, читающие этот контекст, независимо от того, какую часть value они используют.</span>

<b class="text-on-semi-light">Почему контекст с объектом-значением вызывает лишние ререндеры?</b>
<span class="text-gray">Литерал объекта создаёт новую ссылку каждый рендер, и все потребители перерисовываются. Лечится `useMemo` для value.</span>

<b class="text-on-semi-light">Как уменьшить ререндеры от контекста?</b>
<span class="text-gray">Мемоизировать value, разбивать контекст (state и dispatch отдельно), либо использовать стейт-менеджер с селекторами.</span>

<b class="text-on-semi-light">Заменяет ли Context Redux?</b>
<span class="text-gray">Нет. Context - транспорт без точечных подписок. Redux/Zustand хранят состояние и дают селекторы, обновляя только нужных подписчиков.</span>

<b class="text-on-semi-light">Зачем оборачивать useContext в кастомный хук?</b>
<span class="text-gray">Чтобы не дублировать код, дать понятную ошибку при отсутствии провайдера и инкапсулировать API контекста.</span>
