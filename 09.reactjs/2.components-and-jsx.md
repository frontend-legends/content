# Компоненты и JSX

Компонент - это строительный блок React: функция, которая принимает **props** и возвращает описание UI. А **JSX** - это синтаксис, в котором мы это описание пишем. Выглядит как HTML, но это JavaScript.

---

## JSX под капотом

JSX - не часть JavaScript. Это синтаксический сахар, который Babel/SWC компилируют в вызовы функций.

```jsx
const el = <h1 className="title">Привет</h1>;
```

компилируется (в современном JSX-трансформе React 17+) в:

```js
import { jsx as _jsx } from 'react/jsx-runtime';
const el = _jsx('h1', { className: 'title', children: 'Привет' });
```

Результат - обычный **React-элемент**: лёгкий объект-описание, а не DOM-узел.

```js
{ type: 'h1', props: { className: 'title', children: 'Привет' }, key: null }
```

<b class="text-on-semi-light">Главный вывод</b> - <span class="text-gray">JSX-элемент это просто объект. Он ничего не рендерит сам по себе - это описание того, что должно появиться на экране. Поэтому в JSX нельзя писать инструкции (`if`, `for`) - только выражения.</span>

---

## Правила JSX

- **Один корневой узел.** Несколько элементов оборачивают во `<>...</>` (Fragment), чтобы не плодить лишние `div`.
- **`className` вместо `class`**, `htmlFor` вместо `for` - потому что `class`/`for` зарезервированы в JS.
- **camelCase для атрибутов:** `onClick`, `tabIndex`, `strokeWidth`.
- **Выражения в `{}`:** `{user.name}`, `{2 + 2}`, тернарники. Но не инструкции.
- **Теги закрываются:** `<img />`, `<br />`.

```jsx
function Profile({ user }) {
  return (
    <>
      <img src={user.avatar} alt={user.name} />
      <span className="name">{user.name}</span>
    </>
  );
}
```

## Props - входные данные компонента

Props **только для чтения**. Компонент никогда не мутирует свои props - это нарушение однонаправленного потока данных.

```jsx
function Badge({ text, color = 'gray' }) {  // дефолтное значение через деструктуризацию
  return <span className={`badge badge-${color}`}>{text}</span>;
}

<Badge text="new" color="green" />
<Badge text="beta" />  // color = 'gray'
```

<b class="text-on-semi-light">props.children</b> - <span class="text-gray">особый prop: всё, что передано между открывающим и закрывающим тегом. Основа композиции.</span>

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}

<Card>
  <h3>Заголовок</h3>
  <p>Текст</p>
</Card>
```

## Композиция вместо наследования

В React не наследуют компоненты - их **композируют**: передают другие компоненты через `children` или через props.

```jsx
function Dialog({ title, footer, children }) {
  return (
    <div className="dialog">
      <header>{title}</header>
      <div className="body">{children}</div>
      <footer>{footer}</footer>
    </div>
  );
}
```

> Официальная позиция React: композиция покрывает все кейсы, для которых в ООП используют наследование. Подробнее - в [паттернах](/content/reactjs/patterns-and-component-design).

## Условный рендеринг

```jsx
function Status({ user }) {
  return (
    <div>
      {user ? <span>Привет, {user.name}</span> : <a href="/login">Войти</a>}
      {user?.isAdmin && <AdminPanel />}
    </div>
  );
}
```

⚠️ <b class="text-on-semi-light">Ловушка с `&&` и числами</b> - <span class="text-gray">`{count && <List />}` при `count === 0` отрендерит `0` на экране, а не «ничего». `0` - falsy, но это валидный React-узел. Пиши `{count > 0 && <List />}` или `{count ? <List /> : null}`.</span>

## Списки и ключи

Списки рендерят через `map`. Каждому элементу нужен **`key`** - стабильный идентификатор.

```jsx
function TodoList({ todos }) {
  return (
    <ul>
      {todos.map((todo) => (
        <li key={todo.id}>{todo.text}</li>
      ))}
    </ul>
  );
}
```

`key` нужен React для **согласования**: по нему он понимает, какой элемент сохранить, какой добавить, а какой удалить, когда список меняется.

### Почему `index` как `key` - это баг

Использование индекса массива как ключа - классическая ошибка, которую разбирают на собесах.

```jsx
// ❌ Антипаттерн
{todos.map((todo, i) => <TodoItem key={i} todo={todo} />)}
```

Если в начало списка вставить элемент, индексы **сдвинутся**: то, что было `key={0}`, станет `key={1}`. React сопоставит старый узел `0` с новым элементом `0` (это уже другой todo) и **переиспользует не тот DOM/состояние**. Результат - перепутанные значения в `input`, неправильный фокус, «прыгающие» данные.

<b class="text-on-semi-light">Когда index допустим?</b> - <span class="text-gray">Только если список статичен: не переупорядочивается, не фильтруется, элементы не добавляются/удаляются в середину. В остальных случаях - стабильный `id` из данных.</span>

> `key` должен быть **уникальным среди соседей** и **стабильным между рендерами**. Не используй `Math.random()` - он меняется каждый рендер и убивает всю оптимизацию.

## Классовые компоненты (legacy-теория)

До хуков (2019) состояние и жизненный цикл жили в **классах**. В новом коде их не пишут, но на собесах спрашивают - и в legacy-проектах их полно.

```jsx
class Counter extends React.Component {
  state = { count: 0 };                      // состояние

  componentDidMount() {                       // после монтирования
    document.title = `Счёт: ${this.state.count}`;
  }
  componentDidUpdate() {                      // после обновления
    document.title = `Счёт: ${this.state.count}`;
  }
  componentWillUnmount() {                    // перед удалением (cleanup)
    document.title = 'React App';
  }

  render() {
    return (
      <button onClick={() => this.setState({ count: this.state.count + 1 })}>
        {this.state.count}
      </button>
    );
  }
}
```

### Основные методы жизненного цикла и их аналоги в хуках

| Классовый метод | Когда вызывается | Аналог на хуках |
|-----------------|------------------|-----------------|
| `constructor` | при создании | инициализация `useState` |
| `render` | каждый рендер | тело функции-компонента |
| `componentDidMount` | после первого рендера | `useEffect(fn, [])` |
| `componentDidUpdate` | после обновления | `useEffect(fn, [deps])` |
| `componentWillUnmount` | перед удалением | `return` из `useEffect` (cleanup) |
| `shouldComponentUpdate` | перед ререндером | `React.memo` |
| `getDerivedStateFromError` / `componentDidCatch` | при ошибке в детях | **только классы** (error boundary) |

<b class="text-on-semi-light">Почему перешли на хуки?</b> - <span class="text-gray">Классы путали с `this`, размазывали связанную логику по разным методам жизненного цикла (подписка в `didMount`, отписка в `willUnmount`) и плохо переиспользовали логику. Хуки группируют логику по смыслу и переиспользуются через кастомные хуки.</span>

> Один случай, где классы всё ещё незаменимы - **error boundaries** (`getDerivedStateFromError`). Хука-эквивалента нет. Подробнее - в [паттернах](/content/reactjs/patterns-and-component-design).

## Компоненты должны быть чистыми

Во время рендера компонент обязан быть **чистой функцией**: одинаковые props/state -> одинаковый JSX, никаких побочных эффектов.

```jsx
// ❌ Нельзя: мутация во время рендера, побочный эффект
function Bad({ items }) {
  items.push('new');           // мутируем props - запрещено
  document.title = 'rendered'; // побочный эффект в рендере - запрещено
  return <List items={items} />;
}
```

Побочные эффекты выносят в [эффекты](/content/reactjs/effects-and-synchronization) или обработчики событий. Чистота рендера - то, на чём держится конкурентный рендеринг React.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое JSX и во что он компилируется?</b>
<span class="text-gray">Синтаксический сахар над `React.createElement` (или `jsx()` в новом трансформе). Результат - объект-описание элемента, а не DOM-узел.</span>

<b class="text-on-semi-light">Зачем нужны ключи в списках?</b>
<span class="text-gray">Чтобы React при согласовании понимал идентичность элементов: какой сохранить, добавить, удалить. Ключ должен быть уникальным среди соседей и стабильным.</span>

<b class="text-on-semi-light">Почему нельзя использовать индекс как ключ?</b>
<span class="text-gray">При вставке/удалении/сортировке индексы сдвигаются, React переиспользует не тот DOM и состояние - получаем перепутанные значения и фокус. Допустимо только для статичных списков.</span>

<b class="text-on-semi-light">Чем `&&` опасен в условном рендеринге?</b>
<span class="text-gray">Если слева число `0`, оно отрендерится как «0». Используй явное `count > 0 && ...` или тернарник с `null`.</span>

<b class="text-on-semi-light">Чем классовые компоненты отличаются от функциональных?</b>
<span class="text-gray">Классы хранят состояние в `this.state`, используют методы жизненного цикла и `this`. Функциональные используют хуки. Логика в хуках группируется по смыслу и переиспользуется. Error boundary до сих пор только класс.</span>

<b class="text-on-semi-light">Почему компонент должен быть чистым при рендере?</b>
<span class="text-gray">React может вызвать рендер несколько раз, отложить или прервать его (конкурентность). Побочные эффекты и мутации в рендере ломают эти гарантии.</span>
