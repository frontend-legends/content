# Компоненты и JSX

Из чего собирается React-приложение: компоненты, props, `children`, условия и списки в JSX, ключи, классовые компоненты и error boundary. Спрашивают про ключи и ловушку с `&&`. Глубже — чем компонент отличается от элемента, почему индекс в ключе ломает состояние и что умеет только класс.

::tldr
- **Компонент — функция, элемент — её описание в дереве, экземпляр — fiber со своим состоянием.** Состояние принадлежит месту в дереве, а не функции.
- **Props — только для чтения:** React замораживает их в dev. Значения по умолчанию задают в деструктуризации, `defaultProps` у функций больше не работает.
- **JSX — это выражения.** `false`, `null`, `undefined` и `true` ничего не рисуют, а `0` и `NaN` рисуются. Отсюда ловушка `{count && <List />}`.
- **`key` — идентичность элемента среди соседей.** Индекс массива в ключе привязывает состояние к позиции, и после вставки оно оказывается у чужой строки. Смена `key` создаёт компонент заново.
- **Error boundary — пока только класс.** Он ловит ошибки рендера потомков, но не ошибки в обработчиках событий и асинхронном коде.
::

## Компонент, элемент, экземпляр

Сквозной пример темы — каталог товаров:

```jsx
function ProductCard({ product, onBuy }) {
  return (
    <article className="card">
      <h3>{product.title}</h3>
      {product.sale && <span className="badge">Скидка</span>}
      <button onClick={() => onBuy(product.id)}>Купить</button>
    </article>
  );
}

function ProductList({ products, onBuy }) {
  return (
    <section>
      {products.map((p) => (
        <ProductCard key={p.id} product={p} onBuy={onBuy} />
      ))}
    </section>
  );
}
```

На собеседовании часто путают три понятия:

- **Компонент** — функция `ProductCard`. Она принимает props и возвращает описание интерфейса.
- **Элемент** — объект `{ type: ProductCard, props: {...}, key }`, который возвращает JSX `<ProductCard ... />`. Это описание «здесь должен быть `ProductCard` с такими props» (подробно — во [Введении](/content/reactjs/introduction)).
- **Экземпляр** — конкретное место в дереве, где React отрисовал этот компонент. Для каждого экземпляра React хранит fiber, а на нём — состояние хуков.

Одна функция `ProductCard` даёт столько экземпляров, сколько товаров в списке, и у каждого своё состояние. Состояние привязано к **месту в дереве**, а не к функции. Это объясняет и ключи, и сброс состояния, к которым мы придём ниже.

Имя компонента пишут с большой буквы, и это не стиль, а синтаксис. Компилятор превращает `<card />` в строку `'card'` — HTML-тег, а `<Card />` — в ссылку на переменную `Card`. Компонент с маленькой буквы React попытается отрисовать как неизвестный DOM-элемент.

Компонент получает данные через props. С них и начнём.

## Props — входные данные

Props — объект аргументов, который React передаёт компоненту. Компонент его только читает:

```jsx
function Badge({ text, color = 'gray' }) {
  return <span className={`badge badge-${color}`}>{text}</span>;
}

<Badge text="new" color="green" />
<Badge text="beta" />          {/* color = 'gray' */}
```

- **Props нельзя менять.** В dev React замораживает объект props: в модулях и классах (strict mode) присваивание бросает `TypeError`, в остальном коде молча не срабатывает. Если компоненту нужно менять значение, это не prop, а состояние — его или поднимают к родителю, или заводят своё.
- **Значения по умолчанию — в деструктуризации.** `defaultProps` у функциональных компонентов в React 19 убран: JSX его больше не применяет. Старый `React.createElement` ещё применяет, поэтому в смешанном коде поведение разное. У классов `static defaultProps` работает.
- **Props — это и данные, и функции.** `onBuy` — колбэк, через который карточка сообщает родителю о клике. Так устроен однонаправленный поток данных: данные вниз, события вверх.

### children — содержимое между тегами

`children` — обычный prop, в который попадает всё, что написано между открывающим и закрывающим тегом:

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}

<Card>
  <h3>Заголовок</h3>
  <p>Текст</p>
</Card>
```

В `children` может быть что угодно: строка, элемент, массив элементов, функция. Компонент не знает и не должен знать, что внутри, — он только решает, где это показать.

Через `children` и другие props в React собирают сложные компоненты из простых. Это основной механизм переиспользования.

## Композиция вместо наследования

В React компоненты не наследуют друг от друга — их **композируют**: передают одни компоненты в другие. Если нужно несколько «дыр» для содержимого, их делают обычными props:

```jsx
function Dialog({ title, footer, children }) {
  return (
    <div className="dialog" role="dialog">
      <header>{title}</header>
      <div className="body">{children}</div>
      <footer>{footer}</footer>
    </div>
  );
}

<Dialog title="Удалить товар?" footer={<button>Удалить</button>}>
  Товар пропадёт из каталога.
</Dialog>
```

Документация React прямо пишет, что не нашла случаев, где наследование компонентов лучше композиции. Специализацию («`DangerDialog` — это `Dialog` с красной кнопкой») делают компонентом, который рендерит `Dialog` с нужными props.

> Паттерны композиции — compound components, render props, HOC, headless-компоненты — в [Паттернах и дизайне компонентов](/content/reactjs/patterns-and-component-design).

Props и `children` описывают, *что* передать. Как в JSX выразить *условие* и *список*?

## JSX — это выражения

JSX компилируется в вызовы функций, поэтому внутри `{}` можно писать только **выражения** — то, что даёт значение. `if`, `for` и `switch` — инструкции, и в JSX их нет. Условия и списки записывают выражениями: тернарником, `&&`, `map`.

Правила, которые из этого следуют:

- **Один корень.** Функция возвращает одно значение, поэтому несколько элементов оборачивают во фрагмент `<>...</>` — он не создаёт лишний DOM-узел.
- **`className` и `htmlFor`** вместо `class` и `for`: JSX-атрибуты становятся ключами объекта props, а имена соответствуют свойствам DOM.
- **camelCase** для атрибутов и событий: `onClick`, `tabIndex`, `strokeWidth`. Исключение — `aria-*` и `data-*`, они пишутся как в HTML.
- **`style` — объект**, а не строка. Числа для размеров получают `px`: `style={{ width: 10 }}` даёт `width: 10px`.
- **Boolean-атрибуты:** `disabled={false}` не попадает в DOM вовсе, `readOnly` без значения — это `readOnly={true}`.

> `dangerouslySetInnerHTML` и почему React экранирует текст по умолчанию — в [Безопасности](/content/reactjs/security).

### Что рисуется из значений

| Значение в `{}` | На экране |
| --- | --- |
| строка, число | текст, в том числе `0` и `NaN` |
| `''` | ничего (пустой текст) |
| `false`, `true`, `null`, `undefined` | ничего |
| элемент, массив элементов | элементы |
| обычный объект | ошибка `Objects are not valid as a React child` |

Компонент тоже может вернуть `null` или `undefined` — тогда он ничего не рисует, но остаётся в дереве со своим состоянием.

### Условия

```jsx
{product.sale ? <span className="badge">Скидка</span> : null}
{product.sale && <span className="badge">Скидка</span>}
```

`&&` возвращает левую часть, если она ложна. Для `false` это безопасно, а для числа — нет:

```jsx
{items.length && <List items={items} />}   // при пустом списке на экране «0»
{items.length > 0 && <List items={items} />} // ничего
```

`0` — ложное значение, но React его рисует. Слева от `&&` должен стоять boolean: сравнение, `Boolean(x)` или `!!x`. Если условий много, проще вынести логику до `return` или вернуть `null` ранним возвратом.

Условия разобраны. Остался `map` из сквозного примера — и вопрос, зачем каждой карточке `key`.

## Списки и ключи

Список рисуют через `map`, и каждому элементу нужен `key` — стабильный идентификатор среди соседей:

```jsx
{products.map((p) => (
  <ProductCard key={p.id} product={p} onBuy={onBuy} />
))}
```

Когда список меняется, React сопоставляет новые элементы со старыми. Без ключей он может опираться только на позицию. С ключами он понимает: «элемент с `key="42"` был и остался, его нужно сохранить вместе с DOM и состоянием». Без `key` в dev будет предупреждение `Each child in a list should have a unique "key" prop.`

### Почему индекс в ключе — баг

Индекс массива — это позиция, а не идентичность. Пусть в каждой строке есть своё состояние — например, заметка:

```jsx
{items.map((item, i) => <Row key={i} item={item} />)}
```

Пользователь оставил заметку к Ann, потом в начало списка добавили Eve:

```text
key = index: Eve — «заметка к Ann», Ann — пусто, Bob — пусто
key = id:    Eve — пусто,           Ann — «заметка к Ann», Bob — пусто
```

С индексом новая строка получила `key={0}` — тот же ключ, что раньше был у Ann. React решил, что это тот же экземпляр, сохранил его состояние и просто передал новые props. Заметка «уехала» на Eve. С тем же успехом уезжают значения неконтролируемых `input`, фокус и анимации.

Индекс допустим, только если список никогда не переупорядочивается, не фильтруется и элементы не вставляются в середину. В остальных случаях ключ берут из данных. `Math.random()` в ключе — тоже баг: ключ меняется на каждом рендере, и React каждый раз пересоздаёт все строки с потерей состояния.

Ещё про ключи:

- **Ключ уникален среди соседей**, а не глобально: в двух разных списках ключи могут совпадать.
- **Ключ не передаётся в props.** Если id нужен компоненту, его передают отдельно.
- **Фрагменту в списке ключ ставят через полную запись** `<Fragment key={id}>`: короткая `<>` атрибутов не принимает.

### key вне списков: сброс состояния

Раз `key` определяет идентичность, им можно управлять и вне списков. Смена ключа означает «это другой экземпляр»: React размонтирует старый и смонтирует новый с чистым состоянием.

```jsx
<ProfileForm key={user.id} user={user} />
```

При переходе от одного пользователя к другому форма начинает с нуля, а не держит черновик предыдущего. Это штатный способ сбросить состояние без эффектов.

> Как React сравнивает деревья, почему смена типа элемента пересоздаёт поддерево и как ключи участвуют в алгоритме — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber).

Всё выше — про функциональные компоненты. Но в старом коде и на собеседованиях встречаются классы.

## Классовые компоненты

До хуков состояние и жизненный цикл были только у классов. Новый код на классах не пишут, но они поддерживаются, их полно в старых проектах, и их спрашивают:

```jsx
class Counter extends React.Component {
  state = { count: 0 };

  componentDidMount() {
    document.title = `Счёт: ${this.state.count}`;
  }

  componentDidUpdate(prevProps, prevState) {
    if (prevState.count !== this.state.count) {
      document.title = `Счёт: ${this.state.count}`;
    }
  }

  componentWillUnmount() {
    document.title = 'Каталог';
  }

  render() {
    return (
      <button onClick={() => this.setState({ count: this.state.count + 1 })}>
        {this.state.count}
      </button>
    );
  }
}
```

Порядок вызовов при монтировании, одном клике и размонтировании: `render 0` → `componentDidMount` → `render 1` → `componentDidUpdate 0→1` → `componentWillUnmount`.

| Метод класса | Когда вызывается | На хуках |
| --- | --- | --- |
| `constructor`, поле `state` | при создании | `useState` |
| `render` | каждый рендер | тело функции |
| `componentDidMount` | после первого commit | `useEffect(fn, [])` |
| `componentDidUpdate` | после каждого обновления | `useEffect(fn, [deps])` |
| `componentWillUnmount` | перед удалением | cleanup из `useEffect` |
| `shouldComponentUpdate`, `PureComponent` | перед рендером | `memo` |
| `getDerivedStateFromError`, `componentDidCatch` | ошибка в потомках | **аналога нет** |

Соответствие приблизительное. Метод `componentDidMount` выполняется синхронно в commit, а `useEffect` — обычно после отрисовки, ближе к нему `useLayoutEffect`. Главное различие — модель: класс читает текущее `this.state`, а функция видит снимок своего рендера (подробно — в [Механике хуков](/content/reactjs/hooks-mechanics)).

Почему перешли на хуки: связанная логика в классах разъезжалась по методам (подписка в `componentDidMount`, отписка в `componentWillUnmount`), `this` терялся в колбэках, а переиспользование через :term[HOC]{def="компонент высшего порядка: функция, которая принимает компонент и возвращает обёрнутый"} и render props давало глубокие обёртки. Хуки группируют логику по смыслу.

### Error boundary — то, что умеет только класс

Если компонент бросает ошибку во время рендера, React размонтирует всё дерево, и пользователь видит пустой экран. Error boundary перехватывает ошибку и показывает запасной UI:

```jsx
class ErrorBoundary extends React.Component {
  state = { error: null };

  static getDerivedStateFromError(error) {
    return { error };                 // показать запасной UI
  }

  componentDidCatch(error, info) {
    logToSentry(error, info.componentStack); // сообщить о сбое
  }

  render() {
    return this.state.error ? <p>Что-то сломалось</p> : this.props.children;
  }
}
```

Хука для этого нет — это единственное, что функциональный компонент не умеет. На практике берут готовую обёртку, например библиотеку `react-error-boundary`.

Граница ловит ошибки **рендера, методов жизненного цикла и эффектов** своих потомков. Не ловит:

- ошибки в обработчиках событий — они происходят вне рендера, их обрабатывают обычным `try/catch`;
- ошибки в асинхронном коде (`setTimeout`, промисы), если их не пробросить в рендер;
- ошибки в самой границе и ошибки рендера на сервере.

> Где ставить границы и как сочетать их с Suspense — в [Паттернах и дизайне компонентов](/content/reactjs/patterns-and-component-design).

И классы, и функции подчиняются одному правилу — рендер должен быть чистым.

## Рендер должен быть чистым

Компонент во время рендера — чистая функция: одинаковые props и состояние дают одинаковый результат, и рендер ничего не меняет снаружи.

```jsx
function Bad({ items }) {
  items.push('new');           // мутация props
  document.title = 'rendered'; // побочный эффект в рендере
  return <List items={items} />;
}
```

React может вызвать рендер несколько раз, отложить его или выбросить результат, а в dev :term[StrictMode]{def="режим разработки React, который дважды вызывает рендер и эффекты, чтобы выявить побочные эффекты"} специально вызывает его дважды. Побочный эффект в рендере в таких условиях выполнится непредсказуемое число раз. Побочные эффекты выполняют в обработчиках событий и в [эффектах](/content/reactjs/effects-and-synchronization). Почему это не стиль, а требование механизма — в [Механике хуков](/content/reactjs/hooks-mechanics).

## Красные флаги в ответе

- **«Компонент и элемент — одно и то же».** Компонент — функция, элемент — объект-описание, экземпляр — место в дереве с состоянием.
- **«Индекс в ключе — нормально, предупреждение же пропало».** Предупреждение пропало, а состояние привязалось к позиции. Ключ должен идентифицировать данные.
- **«`key` нужен для производительности».** В первую очередь — для корректности: он определяет, какой экземпляр с каким состоянием сохранить.
- **«`{count && <List />}` — нормальное условие».** При `count === 0` на экране будет `0`.
- **«Error boundary ловит любые ошибки».** Только ошибки рендера, жизненного цикла и эффектов потомков. Обработчики и асинхронный код — нет.
- **«Классы устарели и не работают».** Они поддерживаются, и error boundary до сих пор можно написать только классом.

## Как спрашивают на собеседовании

::question
Чем компонент отличается от элемента?

#answer
Компонент — функция (или класс), которая принимает props и возвращает разметку. Элемент — объект, который создаёт JSX: описание того, что нужно отрисовать (`type`, `props`, `key`).

#more
Есть и третье понятие — экземпляр: место в дереве, где React отрисовал компонент. Для каждого экземпляра хранится fiber с состоянием хуков. Одна функция даёт много экземпляров, и состояние принадлежит месту в дереве. Поэтому вызов компонента как функции (`{Card()}`) ломает хуки: отдельного экземпляра нет, и хуки становятся хуками родителя.
::

::question
Зачем нужны ключи в списках?

#answer
Чтобы React при обновлении списка понимал, какой элемент какой: какие сохранить, какие добавить, какие удалить. Ключ должен быть уникальным среди соседей и стабильным между рендерами.

#more
Ключ — идентичность экземпляра. React переиспользует DOM и состояние элемента с тем же ключом и типом, а при смене ключа размонтирует старый экземпляр и создаёт новый. Отсюда приём `key={user.id}` для сброса состояния формы. Ключ не попадает в props, уникален только среди соседей, а для фрагмента в списке нужна запись `<Fragment key>`.

#followups
- «Что будет с `key={Math.random()}`?» → новый ключ на каждом рендере: все строки пересоздаются, теряют состояние и фокус
::

::question
Почему нельзя использовать индекс массива как ключ?

#answer
При вставке, удалении или сортировке индексы сдвигаются, и React сопоставляет старое состояние с другим элементом. Значения в полях, фокус и локальное состояние «переезжают» на соседние строки.

#more
Индекс описывает позицию, а не данные. После вставки в начало новый элемент получает ключ `0`, который был у бывшего первого. React считает его тем же экземпляром: сохраняет состояние и передаёт новые props. Ошибки нет, предупреждения нет — просто неверные данные на экране. Индекс допустим, только если список статичен: не сортируется, не фильтруется, вставки только в конец.
::

::question
Чем опасен `&&` в условном рендеринге?

#answer
Если слева число `0`, React нарисует `0`. `{count && <List />}` при пустом списке покажет «0» вместо пустоты.

#more
`&&` возвращает левую часть, если она ложна. `false`, `null` и `undefined` React не рисует, а числа рисует, включая `0` и `NaN`. Слева должен стоять boolean: `count > 0`, `Boolean(count)`. В TypeScript это не ловится: `number && JSX.Element` — допустимый тип для children.
::

::question
Чем классовые компоненты отличаются от функциональных?

#answer
Классы хранят состояние в `this.state`, используют методы жизненного цикла и `this`. Функциональные компоненты используют хуки. Новый код пишут на функциях, но классы поддерживаются.

#more
Разница в модели: класс читает текущее `this.state` и `this.props`, поэтому асинхронный колбэк увидит самые свежие значения, а функция видит снимок своего рендера. Методы жизненного цикла соответствуют эффектам лишь приблизительно: `componentDidMount` синхронен в commit, `useEffect` обычно идёт после отрисовки. Только классом можно написать error boundary (`getDerivedStateFromError`, `componentDidCatch`).
::

::question
Что ловит error boundary, а что нет?

#answer
Ошибки во время рендера дочерних компонентов: вместо пустого экрана показывается запасной UI. Пишется классом с `getDerivedStateFromError`.

#more
Ловит ошибки рендера, методов жизненного цикла и эффектов потомков. Не ловит ошибки в обработчиках событий (они вне рендера — нужен `try/catch`), в асинхронном коде, в самой границе и при серверном рендере. `getDerivedStateFromError` переключает UI, `componentDidCatch` — место для логирования со стеком компонентов. Границы ставят по смысловым зонам (страница, виджет), чтобы ошибка в одном блоке не роняла весь экран.

#followups
- «Как поймать ошибку из обработчика в границе?» → поймать в `try/catch` и сохранить в состояние, чтобы бросить её в рендере
::

::question
Почему компонент должен быть чистым во время рендера?

#answer
React может вызвать рендер несколько раз, отложить или прервать его, а в StrictMode вызывает дважды. Побочные эффекты и мутации в рендере выполнятся непредсказуемое число раз.

#more
На чистоте рендера держатся concurrent rendering (рендер можно выбросить), перепроигрывание апдейтов и React Compiler, который мемоизирует, считая рендер чистым. Мутация props или внешней переменной в рендере даёт баги, которые проявляются только при определённом порядке рендеров. Побочные эффекты — в обработчиках и эффектах.
::

## Практика

::practice{title="Что будет на экране?"}
```jsx
function Cart({ items }) {
  return (
    <div>
      {items.length && <ul>{items.map((i) => <li key={i.id}>{i.title}</li>)}</ul>}
    </div>
  );
}

<Cart items={[]} />
```

#solution
`<div>0</div>`. `items.length` равно `0`, `&&` возвращает `0`, и React рисует число.

Фикс — boolean слева:

```jsx
function Cart({ items }) {
  return (
    <div>
      {items.length > 0 && <ul>{items.map((i) => <li key={i.id}>{i.title}</li>)}</ul>}
    </div>
  );
}
```

Теперь пустая корзина даёт `<div></div>`.
::

::practice{title="Найди баг"}
В каждой строке можно оставить заметку. После добавления нового пользователя в начало списка заметки оказываются не у тех людей:

```jsx
function Row({ item }) {
  const [note, setNote] = useState('');
  return <li onClick={() => setNote(`заметка к ${item.name}`)}>{item.name} {note}</li>;
}

function List() {
  const [items, setItems] = useState([{ id: 1, name: 'Ann' }, { id: 2, name: 'Bob' }]);
  const addEve = () => setItems((list) => [{ id: 3, name: 'Eve' }, ...list]);

  return <ul>{items.map((item, i) => <Row key={i} item={item} />)}</ul>;
}
```

#solution
Ключ — индекс. После вставки Eve получает `key={0}`, который раньше был у Ann. React сохраняет состояние экземпляра с ключом `0` и передаёт ему новые props, поэтому «заметка к Ann» показывается в строке Eve.

Фикс — ключ из данных:

```jsx
return <ul>{items.map((item) => <Row key={item.id} item={item} />)}</ul>;
```

Теперь заметка остаётся у Ann, а у новой строки Eve состояние пустое.
::

::practice{title="Что покажет граница ошибок?"}
```jsx
function Broken() {
  throw new Error('render failed');
}

function Clicky() {
  return <button onClick={() => { throw new Error('click failed'); }}>x</button>;
}

<ErrorBoundary><Broken /></ErrorBoundary>
<ErrorBoundary><Clicky /></ErrorBoundary>
```

`ErrorBoundary` — класс из раздела выше. Что будет на экране сразу и после клика по кнопке?

#solution
Первая граница сразу показывает «Что-то сломалось»: ошибка брошена во время рендера `Broken`, `getDerivedStateFromError` переключил UI, а `componentDidCatch` получил ошибку для логирования.

Вторая граница рисует кнопку, и после клика она остаётся на месте: ошибка брошена в обработчике события, вне рендера, и граница её не видит. Ошибка уходит в глобальный `window.onerror`.

Если ошибку обработчика нужно показать границей, её ловят и пробрасывают в рендер через состояние:

```jsx
function Clicky() {
  const [error, setError] = useState(null);
  if (error) throw error; // теперь это ошибка рендера — граница её поймает

  return (
    <button
      onClick={() => {
        try {
          riskyAction();
        } catch (e) {
          setError(e);
        }
      }}
    >
      x
    </button>
  );
}
```
::
