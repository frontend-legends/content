# Механика хуков

Как работает любой хук: где React хранит его данные, почему важен порядок вызовов, что происходит после `setState` и когда выполняются эффекты. На mid спрашивают правила хуков и stale closure. На senior — **почему** правила именно такие и что сломается, если их нарушить.

::tldr
- **У каждого компонента в дереве есть fiber со списком ячеек — по одной на вызов хука.** Ячейки сопоставляются с вызовами по порядку, без имён и ключей. Отсюда правило «не вызывай хуки в условиях».
- **Хук из пакета `react` — переадресация в диспетчер**, который рендерер выставляет только на время рендера. Вне рендера стоит заглушка, поэтому хук в эффекте или обработчике падает с `Invalid hook call`.
- **`setState` не меняет значение, а кладёт апдейт в очередь хука.** Новое значение посчитается на следующем рендере, и все апдейты одного события попадут в один рендер.
- **Каждый рендер — снимок.** Функции, созданные в рендере, видят его props и state. Функция, пережившая рендер, видит устаревшие значения — это stale closure.
- **Рендер должен быть чистым:** React может повторить его, выбросить или выполнить дважды. На этом допущении построены StrictMode, приоритеты и React Compiler.
::

## Как useState помнит значение

Компонент — обычная функция. React вызывает её заново на каждый рендер, и все локальные переменные прошлого вызова к этому моменту уже исчезли. Но вот это работает:

```jsx
function Form() {
  const [name, setName] = useState('');
  const [age, setAge] = useState(0);
  useEffect(() => {
    document.title = name;
  }, [name]);

  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}
```

После ввода буквы `Form` вызывается снова, `useState('')` снова получает `''` в аргументе, но возвращает уже введённый текст. Значит, значение хранится не в функции, а снаружи — у React. Остаются два вопроса: где именно и как React понимает, что первому `useState` нужно отдать `name`, а второму — `age`, если имён переменных он не видит.

Этот пример пройдёт через всю тему.

## Где лежит память: список ячеек на fiber

Для каждого экземпляра компонента React держит между рендерами объект **fiber** (подробно — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber)). У функционального компонента поле `fiber.memoizedState` указывает на **связный список ячеек**: каждый вызов хука при монтировании добавляет в него одну ячейку.

```text
fiber <Form>
  memoizedState ─► { memoizedState: '',     queue, next } ─ useState('')
                     │
                     ▼
                   { memoizedState: 0,      queue, next } ─ useState(0)
                     │
                     ▼
                   { memoizedState: effect, next: null }  ─ useEffect(...)
```

Ячейка — объект с полями `memoizedState` (данные хука), `queue` (очередь апдейтов, если она нужна), `baseState` и `baseQueue` (для перепроигрывания апдейтов, о нём ниже) и `next` (следующая ячейка).

### Что лежит в ячейке у каждого хука

Все хуки устроены одинаково: каждый хранит в своих ячейках ровно то, что ему нужно помнить между рендерами. Таблица снята с настоящего fiber в React 19:

| Хук | Ячеек | Что в ячейке |
| --- | --- | --- |
| `useState`, `useReducer`, `useOptimistic` | 1 | значение и очередь апдейтов |
| `useRef` | 1 | объект `{ current }` — один и тот же на всех рендерах |
| `useMemo`, `useCallback` | 1 | пара `[значение, deps]` |
| `useEffect`, `useLayoutEffect`, `useInsertionEffect` | 1 | объект эффекта: функция, cleanup, deps и флаги |
| `useImperativeHandle` | 1 | тот же объект эффекта: под капотом это layout-эффект |
| `useId`, `useDeferredValue` | 1 | строка id; последнее показанное значение |
| `useEffectEvent` | 1 | `{ impl }` — актуальная версия функции |
| `useTransition` | 2 | состояние `isPending` и функция `startTransition` |
| `useSyncExternalStore` | 2 | снимок стора и эффект подписки |
| `useActionState` | 3 | состояние, флаг ожидания, функция action |
| `useContext`, `use`, `useDebugValue` | 0 | ячейки нет |

Из таблицы следует несколько вещей, которые спрашивают на собеседовании:

- **`useCallback(fn, deps)` — это `useMemo(() => fn, deps)`.** Ячейка одна и та же: `[fn, deps]`. Функция при этом создаётся на каждом рендере, `useCallback` лишь возвращает старую, пока deps не поменялись. Когда это вообще нужно — в [Производительности](/content/reactjs/performance).
- **Эффект живёт в двух местах.** Объект эффекта лежит в ячейке, и он же добавлен в кольцевой список `fiber.updateQueue`. Commit идёт по этому списку, а не по ячейкам. Если deps не изменились, у эффекта нет флага `HasEffect`, и commit его пропускает.
- **Составные хуки — это несколько простых.** `useSyncExternalStore` — это состояние плюс эффект подписки, `useTransition` — состояние плюс стабильная функция.
- **`useContext` ничего не хранит в списке.** Он читает значение ближайшего провайдера и записывает в `fiber.dependencies`, что компонент зависит от этого контекста: так React находит, кого перерендерить, когда значение изменится (подробно — в [Context API](/content/reactjs/context-api)). `use` тоже ячейку не занимает — к нему вернёмся в следующем разделе.

> Как `useId` выдаёт одинаковые id на сервере и в браузере — в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration).

Ячейки лежат в списке без имён. Как React понимает, что вторая ячейка — это `age`?

## Порядок вызовов вместо имён

При повторном рендере React идёт по списку **параллельно с вызовами хуков**: первый вызов получает первую ячейку, второй — вторую. Курсор просто сдвигается на `next`. Ключей нет, поэтому порядок вызовов обязан совпадать на каждом рендере.

Почему не ключи? Хуки задуманы для композиции: кастомный хук можно вызвать дважды в одном компоненте, два разных хука могут внутри использовать одинаковые имена. С ключами это порождало бы конфликты, а порядок вызовов уникален всегда. Подробно этот выбор разбирает Дэн Абрамов в «Why Do React Hooks Rely on Call Order?».

Отсюда и **кастомные хуки**: это обычные функции, а их вызовы хуков встраиваются в список того компонента, который их вызвал. Два компонента с `useToggle()` получают два независимых набора ячеек — кастомный хук делит **логику**, а не состояние. Префикс `use` рантайму не нужен: по нему линтер и компилятор понимают, что к функции применяются правила хуков.

### Модель в 50 строк

Упрощённая, но рабочая модель того, что делает React. В ней нет приоритетов и двух версий fiber, зато видны список, курсор и два диспетчера:

```js
let fiber = null;        // компонент, который сейчас рендерится
let cursor = null;       // последняя пройденная ячейка
let dispatcher = null;   // в React — ReactSharedInternals.H

const useState = (initial) => resolve().useState(initial);
function resolve() {
  if (dispatcher === null) throw new Error('Invalid hook call');
  return dispatcher;
}

const onMount = {
  useState(initial) {
    const hook = nextHook(true);
    hook.memoizedState = typeof initial === 'function' ? initial() : initial;
    const owner = fiber;
    hook.queue = [];
    hook.dispatch = (action) => {      // создаётся один раз — поэтому стабильна
      hook.queue.push(action);         // значение не меняется сразу
      scheduleRender(owner);
    };
    return [hook.memoizedState, hook.dispatch];
  },
};

const onUpdate = {
  useState() {
    const hook = nextHook(false);
    for (const action of hook.queue) {   // очередь — по порядку
      hook.memoizedState = typeof action === 'function' ? action(hook.memoizedState) : action;
    }
    hook.queue = [];
    return [hook.memoizedState, hook.dispatch];
  },
};

function nextHook(mounting) {
  const next = cursor ? cursor.next : fiber.memoizedState;
  if (mounting) {
    const hook = { memoizedState: null, queue: null, next: null };
    if (cursor) cursor.next = hook; else fiber.memoizedState = hook;
    return (cursor = hook);
  }
  if (!next) throw new Error('Rendered more hooks than during the previous render.');
  return (cursor = next);
}

function render(f) {
  fiber = f;
  cursor = null;
  dispatcher = f.memoizedState === null ? onMount : onUpdate;
  try {
    return f.type(f.props);
  } finally {
    dispatcher = null;                  // вне рендера хуки не работают
    fiber = cursor = null;
  }
}
```

Проверим на условном хуке:

```js
function Form({ show }) {
  const [name] = useState('Ann');
  if (show) useState('hidden');
  const [age] = useState(30);
  return `${name}, ${age}`;
}
// render с show: true  → 'Ann, 30'
// render с show: false → 'Ann, hidden': age прочитал чужую ячейку
```

В модели `age` молча получает чужое значение. Настоящий React сверяет количество и типы хуков и падает с понятной ошибкой.

### Что ты увидишь, если правило нарушено

| Сообщение | Что произошло |
| --- | --- |
| `Rendered more hooks than during the previous render.` | условный хук начал вызываться: ячеек не хватило |
| `Rendered fewer hooks than expected. This may be caused by an accidental early return statement.` | ранний `return` перед хуком: ячейки остались непройденными |
| `React has detected a change in the order of Hooks called by X` | dev-предупреждение: количество то же, порядок типов другой. Дальше часто падает `Should have a queue. You are likely calling Hooks conditionally` — хук получил ячейку другого типа |
| `Do not call Hooks inside useEffect(...), useMemo(...), or other built-in Hooks` | dev-предупреждение: хук внутри колбэка, который выполняется во время рендера (`useMemo`, инициализатор, редьюсер) |
| `Invalid hook call. Hooks can only be called inside of the body of a function component...` | хук вне рендера: в эффекте, обработчике, классе. Или две копии React — о них в следующем разделе |
| `Too many re-renders. React limits the number of renders to prevent an infinite loop.` | безусловный `setState` прямо в рендере |

Ловить это до запуска помогает `eslint-plugin-react-hooks`: правила `rules-of-hooks` и `exhaustive-deps`, а также правила на базе компилятора (`purity`, `refs`, `set-state-in-render`, `set-state-in-effect`).

### Исключение: use

`use` можно вызывать в условиях и циклах (но не внутри `try/catch`): ячейку он не занимает, поэтому сдвинуть курсор не может.

- **`use(context)`** читает контекст так же, как `useContext`.
- **`use(promise)`** хранит результат на самом промисе: React записывает в объект `status` и `value`. Поэтому промис должен быть **стабильным** — из кеша, из props, из Server Component. Промис, созданный в рендере клиентского компонента, каждый раз новый, и компонент снова и снова приостанавливается.

`useContext` тоже ячейку не занимает, но правило на него действует: dev-проверка порядка учитывает все хуки и при условном `useContext` выдаёт то же предупреждение. Если контекст нужно читать по условию, для этого есть `use`.

Порядок объясняет первое правило хуков. Второе — «только в компонентах и других хуках» — объясняет то, кто вообще отвечает на вызов `useState`.

## Кто отвечает на вызов: диспетчер

Сам пакет `react` хуки не реализует. `useState` из `react` — переадресация:

```js
// react/src/ReactHooks.js (упрощённо)
export function useState(initialState) {
  const dispatcher = ReactSharedInternals.H;
  return dispatcher.useState(initialState);
}
```

Реализацию подставляет **рендерер** (react-dom, react-native) на время вызова компонента:

- **mount-диспетчер** создаёт ячейки;
- **update-диспетчер** идёт по существующим ячейкам и применяет очереди;
- **после рендера** ставится заглушка, которая на любой хук бросает `Invalid hook call`. Поэтому хук в колбэке эффекта или в обработчике события падает: в этот момент рендера нет.

Так React и отличает первый рендер от повторного: это два разных объекта-диспетчера с разными реализациями одних и тех же хуков.

### Две копии React

Внутреннее поле `ReactSharedInternals` лежит в пакете `react`. Если в бандле две копии пакета — из-за `npm link`, монорепы или библиотеки, которая положила React себе в `dependencies`, — react-dom выставляет диспетчер в одной копии, а компонент читает его из другой. Там диспетчер `null`, и код, написанный по всем правилам, падает:

```text
Invalid hook call. Hooks can only be called inside of the body of a function component...
3. You might have more than one copy of React in the same app

TypeError: Cannot read properties of null (reading 'useState')
```

Первое сообщение — только в dev. В проде в мониторинге будет один `TypeError`.

::pitfall{title="Invalid hook call в правильном коде"}
#symptom
Компонент из своей UI-библиотеки или соседнего пакета монорепы падает, хотя хуки вызываются по всем правилам. В Sentry — `TypeError: Cannot read properties of null (reading 'useState')`. В Storybook самой библиотеки всё работает.
#cause
В бандле две копии `react`. react-dom выставляет диспетчер в своей копии, а хук библиотеки читает его из другой, где диспетчер всегда `null`.
#fix
`npm ls react` покажет копии. React в библиотеке — только `peerDependency`. В монорепе — одна версия в корне. В Vite — `resolve.dedupe: ['react', 'react-dom']`, в webpack — `resolve.alias`.
::

Мы разобрали, как хук находит свою ячейку. Теперь — как ячейка меняется: что происходит после `setState`.

## Что делает setState

Вернёмся к `Form`: пользователь ввёл букву, вызвался `setName('a')`.

1. **Создаётся апдейт** — действие и приоритет (lane). Он попадает в очередь хука, а значение в ячейке пока не меняется. Приоритет зависит от источника: ввод и клик — срочные, апдейт внутри `startTransition` — низкий.
2. **Eager bailout.** Если у компонента нет других ожидающих апдейтов, React сразу считает новое значение и сравнивает его со старым через `Object.is`. Совпало — рендер не планируется вообще.
3. **Иначе рендер планируется.** Все апдейты одного события (а также в промисах и таймерах) склеиваются в один рендер — это автоматический батчинг.
4. **На рендере update-диспетчер применяет очередь по порядку.** Функция-апдейтер получает результат предыдущего апдейта, значение просто его заменяет.
5. **Если итоговое значение равно старому**, React выходит из рендера (bailout): дети не рендерятся, эффекты не запускаются.

Отсюда классический вопрос: в обработчике `setN(n + 1); setN(n + 1); setN((x) => x + 1)` при `n === 0` даёт `2`, а не `3`. `n` — константа текущего рендера, поэтому оба первых вызова — это `setN(1)`. Очередь применяется так: `1` → `1` → `1 + 1 = 2`. Рендер при этом один.

### Почему компонент иногда вызывается при том же значении

Eager bailout возможен, только если ни на одной из двух версий fiber нет незавершённых апдейтов. React держит две версии каждого fiber: `current` — то, что на экране, и `workInProgress` — то, что сейчас рендерится. Сразу после апдейта одна из версий ещё помечена, поэтому повторный `setState(2)` при уже показанном `2` один раз вызывает компонент. React видит то же значение и выходит, не трогая детей.

```text
set(1) при state 1 → компонент не вызван
set(2)             → рендер компонента и детей
set(2)             → компонент вызван ещё раз, дети — нет
set(2)             → не вызван
```

Документация говорит об этом прямо: React «может вызвать компонент перед тем, как пропустить детей». Это не баг и не повод для оптимизации.

### Начальное значение и функции в state

- **Начальное значение используется только при монтировании.** Но выражение в аргументе вычисляется на каждом рендере: `useState(expensive())` вызывает `expensive()` всегда. Ленивый инициализатор `useState(() => expensive())` вызывается один раз.
- **Функция в `setState` — всегда апдейтер.** `setHandler(fn)` вызовет `fn(prev)` и положит в state результат. Чтобы сохранить саму функцию, оберни её: `setHandler(() => fn)`.
- **Мутация не запускает рендер.** `user.name = 'Bob'; setUser(user)` — та же ссылка, `Object.is` вернёт `true`, и сработает bailout. Нужен новый объект: `setUser({ ...user, name: 'Bob' })`.

### Приоритеты: очередь переигрывается

Пункт 4 скрывает важную деталь: апдейты с низким приоритетом могут быть **пропущены** срочным рендером и применены позже. Чтобы итог не зависел от порядка рендеров, React хранит в ячейке `baseState` и `baseQueue` и при необходимости перепроигрывает очередь с начала:

```jsx
const [x, setX] = useState(1);

startTransition(() => setX((v) => v + 1)); // низкий приоритет
flushSync(() => setX((v) => v * 10));      // срочный, после него
```

На экране последовательно будет `1 → 10 → 20`. Срочный рендер пропускает transition-апдейт и считает только `1 * 10 = 10`. Потом рендер transition перепроигрывает очередь от `baseState` в исходном порядке: `(1 + 1) * 10 = 20`. Итог такой же, как при синхронном применении, но апдейтер `v * 10` вызван **дважды**.

Поэтому апдейтеры и редьюсеры обязаны быть чистыми: React вправе вызвать их несколько раз. По той же причине прерванный или выброшенный рендер ничего не портит: он писал в `workInProgress`, а `current` — то, что на экране, — остался прежним.

Новое значение посчитано, рендер закончен, DOM обновлён. Но эффект из третьей ячейки `Form` ещё не выполнился — когда это происходит?

## Когда выполняются эффекты

Рендер только вычисляет, что должно быть на экране. Всё, что меняет внешний мир, происходит в **commit** — после того как React применил изменения к DOM:

```text
render ─► commit ──────────────────────────────────────► браузер ─► useEffect
(чистая     изменения DOM      ─► useLayoutEffect           рисует     (обычно после
 фаза)      + useInsertionEffect   (синхронно, до кадра)    кадр       отрисовки)
```

- **Commit идёт по списку эффектов fiber** и выполняет только те, у которых есть флаг `HasEffect`: deps изменились или их нет вовсе. Deps сравниваются поэлементно через `Object.is`.
- **Порядок на апдейте:** сначала cleanup предыдущей версии эффекта, потом setup новой. Для каждого вида — «все cleanup, потом все setup».
- **`useInsertionEffect`** выполняется вместе с изменениями DOM, раньше всех layout-эффектов. Он нужен библиотекам CSS-in-JS, чтобы вставить стили до того, как кто-то начнёт измерять DOM.
- **`useLayoutEffect`** выполняется синхронно, до отрисовки: в нём можно измерить DOM и поправить его без мигания. Тяжёлая работа в нём задерживает кадр.
- **`useEffect`** обычно выполняется после отрисовки и не блокирует кадр. Исключение — апдейт от дискретного события (клик, ввод): тогда React выполняет эффекты синхронно в конце commit, чтобы результат клика был готов до следующего события.

В `Form` это значит: `document.title` поменяется уже после того, как буква появилась в поле.

Объект, массив или функция, созданные в рендере, — каждый раз новая ссылка. Если такой объект стоит в deps, флаг `HasEffect` будет на каждом рендере, и эффект будет перезапускаться без конца.

::pitfall{title="Эффект перезапускается в цикле и спамит запросами"}
#symptom
Network забит одинаковыми запросами. Предупреждения в консоли может не быть: `Maximum update depth exceeded` появляется только для синхронного `setState` в эффекте, а цикл через `fetch` асинхронный.
#cause
Эффект зависит от объекта, который заново создаёт тот же компонент, чей рендер вызывает `setState`:

```jsx
function Page() {
  const [items, setItems] = useState([]);
  const filters = { status: 'open' };              // новый объект на каждый рендер Page
  return <List filters={filters} onLoaded={setItems} />;
}

function List({ filters, onLoaded }) {
  useEffect(() => {
    fetchItems(filters).then(onLoaded);            // setItems → рендер Page → новый filters
  }, [filters, onLoaded]);                         // → эффект снова → новый запрос
}
```
#fix
Зависеть от примитивов (`filters.status`), вынести константу из компонента или мемоизировать объект у источника (`useMemo` или React Compiler). Не выключать `exhaustive-deps`: это спрячет баг, а не исправит его.
::

> Как правильно синхронизироваться с внешним миром, чистить подписки и когда эффект вообще не нужен — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization).

Эффект выполняется после рендера, но видит значения **своего** рендера. Отсюда главный баг хуков.

## Каждый рендер — снимок

Каждый вызов компонента видит свой набор props и state, и все функции, созданные в этом вызове, замыкают именно их. Пока функция живёт один рендер, это незаметно. Если она переживает рендер — интервал, подписка, колбэк, сохранённый в эффекте, — она видит **устаревшие** значения:

```jsx
function Timer() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1); // count навсегда 0 → всегда setCount(1)
    }, 1000);
    return () => clearInterval(id);
  }, []); // эффект создан в рендере, где count === 0
}
```

Счётчик дойдёт до 1 и остановится. Это не баг React, а обычное [замыкание](/content/javascript/closures): эффект создан один раз и замкнул первый рендер.

Три решения, от простого к точному:

```jsx
// 1. Апдейтер не зависит от замкнутого значения
setCount((c) => c + 1);

// 2. Честные зависимости: эффект пересоздаётся при каждом изменении count
useEffect(() => { /* ... */ }, [count]);

// 3. useEffectEvent: логика, которой нужны свежие значения, но не нужна реакция на них
function ChatRoom({ roomId, theme }) {
  const onConnected = useEffectEvent(() => {
    showNotification('Подключено', theme); // всегда свежая theme
  });

  useEffect(() => {
    const connection = createConnection(roomId);
    connection.on('connected', () => onConnected());
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]); // смена темы не переподключает чат
}
```

`useEffectEvent` работает за счёт своей ячейки `{ impl }`: на каждом commit React кладёт туда свежую версию функции. Функция, которую вернул хук, при вызове берёт из ячейки актуальную версию, поэтому эффект с `[roomId]` видит свежую `theme`. Ограничения следуют из этого:
- вызывать её можно только из эффектов — в рендере будет `A function wrapped in useEffectEvent can't be called during rendering`;
- сама возвращённая функция новая на каждом рендере, поэтому в deps её не кладут;
- в другие компоненты её не передают.

Раньше ту же задачу решали через ref с последним значением: `latest.current = value` прямо в рендере. Но запись в ref во время рендера нарушает чистоту, и линтер с компилятором на неё ругаются. Читать и писать `ref.current` в рендере вообще нельзя, кроме ленивой инициализации (`if (ref.current === null) ref.current = new Thing()`): React не отслеживает ref, и компонент покажет устаревшие данные.

Всё, что выше, держится на одном допущении: рендер — чистый вызов, который можно повторить или выбросить. Это допущение React проверяет.

## Чистота: StrictMode и React Compiler

Правила React (Rules of React) сводятся к трём:

1. Хуки — только на верхнем уровне. Следует из порядка ячеек.
2. Хуки — только из компонентов и других хуков. Следует из диспетчера.
3. Компоненты и хуки чистые: одинаковые входы дают одинаковый результат, в рендере нет побочных эффектов, props, state и значения из хуков не мутируются. Следует из того, что рендер можно повторить, прервать и перепроиграть.

**StrictMode** в development проверяет третье правило на практике:

- тело компонента, инициализаторы `useState` и `useReducer`, функции `useMemo` и апдейтеры вызываются **дважды** — нечистый код проявится расхождением;
- при монтировании эффекты проходят цикл **setup → cleanup → setup** — забытый cleanup проявится утечкой или двойной подпиской.

В production ничего этого нет. Двойной mount — не прихоть: React умеет прятать и восстанавливать поддеревья с сохранением state (`<Activity>`, Fast Refresh), и эффекты должны это переживать.

**React Compiler** опирается на те же правила: он мемоизирует компоненты, значения и функции на этапе сборки, считая рендер чистым. Если находит нарушение, он **пропускает** компонент, а не ломает его. Поэтому правила линтера на базе компилятора важнее, чем кажется: они показывают, где автоматическая мемоизация не сработает.

::pitfall{title="«В dev данные грузятся два раза, давайте поставим флаг»"}
#symptom
В dev каждый запрос из эффекта уходит дважды, аналитика шлёт двойные события. Кто-то «чинит» это через `const didRun = useRef(false)`.
#cause
StrictMode специально монтирует компонент, размонтирует и монтирует снова. Если эффект без cleanup ломается от этого, он сломается и в проде: при быстрой навигации, в `<Activity>`, при Fast Refresh.
#fix
Написать cleanup: `AbortController` для `fetch`, флаг `ignore` для устаревших ответов, отписку. Данные лучше грузить через библиотеку с кешем (TanStack Query) или фреймворк. Ref-флаг маскирует отсутствие cleanup.
::

## Как менялась механика

Актуально на ноябрь 2026.

| Версия | Что изменилось |
| --- | --- |
| React 16.8 (2019) | хуки: `useState`, `useEffect`, `useContext`, `useReducer`, `useRef`, `useMemo` и другие |
| React 18 (2022) | concurrent rendering и приоритеты, автоматический батчинг в промисах и таймерах, двойной mount эффектов в StrictMode, `useSyncExternalStore`, `useId`, `useTransition`, `useDeferredValue`, `useInsertionEffect` |
| React 19 (декабрь 2024) | `use`, хуки Actions (`useActionState`, `useOptimistic`, `useFormStatus`), `ref` как обычный prop |
| React 19.2 (октябрь 2025) | `useEffectEvent`, `<Activity>` |
| React Compiler 1.0 (октябрь 2025) | автоматическая мемоизация при сборке на основе Rules of React |

Соответствие хуков методам жизненного цикла классов (`componentDidMount` ≈ `useEffect(..., [])`) до сих пор спрашивают, но оно неточное: эффект выполняется после отрисовки и замыкает свой рендер. Подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization).

## Красные флаги в ответе

- **«setState асинхронный».** Он не асинхронный, а отложенный: апдейт кладётся в очередь, и значение посчитается на следующем рендере. Даже после `flushSync` переменная `n` в обработчике останется прежней — это константа рендера.
- **«React хранит хуки в массиве по именам переменных».** Имён React не видит. Ячейки — связный список на fiber, сопоставление идёт по порядку вызовов.
- **«Правила хуков — требование линтера».** Линтер их только проверяет. Правила следуют из устройства рантайма: порядок ячеек и диспетчер, который есть только во время рендера.
- **«`useCallback` ускоряет компонент».** Он хранит `[fn, deps]` и сравнивает deps на каждом рендере. Функция всё равно создаётся заново. Польза есть, только если стабильная ссылка кому-то нужна: `memo`-ребёнку или deps эффекта.
- **«Эффект дважды в dev — баг, поставлю ref-флаг».** Это проверка StrictMode, а флаг прячет отсутствие cleanup.
- **«Кастомный хук — способ поделиться состоянием между компонентами».** Он делит логику: у каждого вызывающего компонента свои ячейки. Общее состояние — это контекст или стор.

## Как спрашивают на собеседовании

::question{level="mid"}
Почему хуки нельзя вызывать в условиях и циклах?

#mid
React не знает имён переменных и сопоставляет данные с хуком по порядку вызова. Если хук вызвать условно, порядок на разных рендерах будет разным, и данные «съедут» на чужой хук.

#senior
Данные лежат в связном списке на `fiber.memoizedState`. На повторном рендере update-диспетчер сдвигает курсор по списку синхронно с вызовами. Если ячеек не хватило или остались лишние, React бросает `Rendered more hooks...` или `Rendered fewer hooks...`. При том же количестве, но другом порядке типов в dev будет предупреждение, а дальше — падение на ячейке чужого типа. Порядок вместо ключей выбран ради композиции: кастомные хуки можно вызывать много раз без конфликтов имён.

#followups
- «Почему тогда `use()` можно вызывать в условии?» → он не занимает ячейку: контекст читается напрямую, результат промиса хранится на самом промисе
- «А `useContext`?» → ячейки у него тоже нет, но dev-проверка порядка его учитывает; для условного чтения есть `use`
::

::question{level="senior"}
Что происходит после вызова setState?

#mid
React не меняет значение сразу, а планирует новый рендер. Несколько `setState` в одном обработчике склеиваются в один рендер. Новое значение компонент увидит при следующем вызове.

#senior
Создаётся апдейт с приоритетом и попадает в очередь хука. Если у fiber нет ожидающей работы, React сразу считает новое значение и при `Object.is`-равенстве вообще не планирует рендер (eager bailout). Иначе рендер планируется по приоритету. На рендере update-диспетчер применяет очередь по порядку. Апдейты с низким приоритетом срочный рендер может пропустить, а потом перепроиграть очередь от `baseState`, поэтому апдейтеры обязаны быть чистыми. Если результат равен старому state, React выходит из рендера без детей и эффектов.

#followups
- «Почему `console.log(count)` сразу после `setCount` показывает старое значение?» → `count` — константа текущего рендера
- «Почему `setCount(5)` при `count === 5` иногда всё равно вызывает компонент?» → на одной из двух версий fiber ещё висит недавний апдейт, eager-проверка невозможна; React вызовет компонент, но не детей
::

::question{level="mid"}
Откуда берётся «Invalid hook call», если хуки вызваны правильно?

#mid
Обычно хук вызван не в компоненте и не в другом хуке: в обработчике, эффекте, классе.

#senior
Хуки из `react` — переадресация в диспетчер, который рендерер выставляет только на время рендера. Причины из текста ошибки: несовместимые версии `react` и `react-dom`, нарушение правил хуков и две копии React в бандле. Последняя самая коварная: код корректен, но компонент читает диспетчер из копии, которую react-dom не трогал, и в проде видно только `TypeError: Cannot read properties of null (reading 'useState')`. Диагностика — `npm ls react`, лечение — `peerDependencies` у библиотек и дедупликация в бандлере.
::

::question{level="senior"}
Что React хранит для useMemo, useRef и useEffect? Чем useCallback отличается от useMemo?

#mid
`useMemo` хранит значение и зависимости, `useRef` — объект `{ current }`, `useEffect` — эффект с зависимостями. `useCallback(fn, deps)` — то же, что `useMemo(() => fn, deps)`.

#senior
У каждого хука своя ячейка в списке fiber: у `useMemo` и `useCallback` — `[value, deps]`, у `useRef` — один и тот же объект на все рендеры, у эффектов — объект с функцией, cleanup, deps и флагами. Эффект ещё и добавлен в кольцевой список `fiber.updateQueue`, по которому идёт commit: выполняются только эффекты с флагом `HasEffect`, то есть с изменившимися deps. Составные хуки — несколько ячеек: `useTransition` — две, `useSyncExternalStore` — состояние и эффект подписки. `useContext` ячейки не занимает — он записывает зависимость в `fiber.dependencies`.

#followups
- «Создаётся ли функция заново при `useCallback`?» → да, на каждом рендере; хук лишь возвращает старую, пока deps те же
::

::question{level="mid"}
Что такое stale closure в хуках и как с ним бороться?

#mid
Функция, созданная в одном рендере, замкнула его state. Если она переживает рендер (интервал, подписка), она видит устаревшие значения. Лечится функциональным апдейтером, честными зависимостями или `useEffectEvent`.

#senior
Это следствие модели «рендер — снимок»: замыкание держит окружение конкретного вызова компонента. Выбор решения зависит от задачи: апдейтер — когда нужен только предыдущий state; deps — когда эффект действительно должен пересоздаться; `useEffectEvent` — когда в эффекте нужно свежее значение, но реагировать на его изменение не нужно. Хак с `ref.current = value` в рендере нарушает чистоту, и компилятор пропустит такой компонент.

#followups
- «Почему нельзя просто выключить `exhaustive-deps`?» → пропущенная зависимость — это эффект со старыми данными
::

::question{level="mid"}
Почему в dev эффект запускается дважды?

#mid
Это StrictMode: в development он монтирует компонент, размонтирует и монтирует снова, чтобы проверить cleanup. В production эффект выполняется один раз.

#senior
StrictMode ещё дважды вызывает тело компонента, инициализаторы, `useMemo` и апдейтеры, чтобы показать нечистый рендер. Двойной mount нужен потому, что React умеет прятать и восстанавливать поддеревья с сохранением state (`<Activity>`, Fast Refresh), и эффекты должны это переживать. Правильная реакция — cleanup, а не ref-флаг «уже запускали».
::

::question{level="senior"}
Почему два компонента с одним кастомным хуком не делят состояние?

#mid
Кастомный хук — обычная функция. Каждый компонент вызывает её сам, и у каждого свои данные.

#senior
Вызовы хуков внутри кастомного хука встраиваются в список ячеек того компонента, который его вызвал: для React нет «ячеек хука», есть только ячейки компонента. Поэтому кастомный хук делит логику, а не состояние. Общее состояние — контекст, стор с `useSyncExternalStore` или поднятый state. Префикс `use` нужен линтеру и компилятору, чтобы применять к функции правила хуков.
::

## Практика

::practice{title="Что будет на экране и в консоли после одного клика?"}
```jsx
function Counter() {
  const [n, setN] = useState(0);

  function handleClick() {
    setN(n + 1);
    setN(n + 1);
    setN((x) => x + 1);
    console.log(n);
  }

  return <button onClick={handleClick}>{n}</button>;
}
```

#solution
В консоли `0`, на экране `2`.

`n` — константа текущего рендера, поэтому `console.log` видит `0`, и оба `setN(n + 1)` — это `setN(1)`. В очереди три апдейта, они применяются по порядку: `1` → `1` → `1 + 1 = 2`. Рендер один.

Как получить `3` и увидеть новое значение:

```jsx
function handleClick() {
  // каждый апдейтер получает результат предыдущего: 0 → 1 → 2 → 3
  setN((x) => x + 1);
  setN((x) => x + 1);
  setN((x) => x + 1);
}

// новое значение видно только в следующем рендере — например, в эффекте
useEffect(() => {
  console.log(n); // 0 при монтировании, 3 после клика
}, [n]);
```

Если новое значение нужно прямо в обработчике — посчитай его в переменной: `const next = n + 3; setN(next); send(next);`.
::

::practice{title="В каком порядке появятся логи?"}
Компонент монтируется с `v = 1`, затем родитель передаёт `v = 2`, затем компонент размонтируется. StrictMode выключен.

```jsx
function Item({ v }) {
  console.log('render', v);

  useLayoutEffect(() => {
    console.log('layout', v);
    return () => console.log('layout cleanup', v);
  }, [v]);

  useEffect(() => {
    console.log('effect', v);
    return () => console.log('effect cleanup', v);
  }, [v]);

  return null;
}
```

#solution
```text
render 1
layout 1
effect 1
render 2
layout cleanup 1
layout 2
effect cleanup 1
effect 2
layout cleanup 2
effect cleanup 2
```

Cleanup видит **старое** значение `v` — своё замыкание. Layout-эффекты всегда раньше обычных.

Со StrictMode в dev повторы есть только на монтировании и в рендерах. Обновление и размонтирование идут как без него:

```text
render 1
render 1            ← повторный рендер
layout 1
effect 1
layout cleanup 1    ← StrictMode проверяет, что cleanup всё убирает
effect cleanup 1
layout 1
effect 1
render 2
render 2            ← каждый рендер вызывается дважды
layout cleanup 1
layout 2
effect cleanup 1
effect 2
layout cleanup 2
effect cleanup 2
```
::

::practice{title="Найди баг"}
Профиль работает, но падает, когда пользователь выходит из аккаунта (`user` становится `null`):

```jsx
function Profile({ user }) {
  const [tab, setTab] = useState('posts');
  if (!user) return <LoginPrompt />;

  const [draft, setDraft] = useState(user.bio);
  useEffect(() => { document.title = user.name; }, [user.name]);

  return <ProfileView user={user} tab={tab} draft={draft} />;
}
```

#solution
Ранний `return` перед хуками. Пока `user` есть, вызывается три хука, после выхода — один:

```text
# выход: было 3 хука, стало 1
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.

# вход: было 1, стало 3 (в dev сначала предупреждение, потом ошибка)
React has detected a change in the order of Hooks called by Profile.
Error: Rendered more hooks than during the previous render.
```

Фикс — вынести всё, что требует `user`, в отдельный компонент. Снаружи только проверка, внутри `user` гарантированно есть:

```jsx
function Profile({ user }) {
  const [tab, setTab] = useState('posts');
  if (!user) return <LoginPrompt />;

  return <AuthorizedProfile key={user.id} user={user} tab={tab} />;
}

function AuthorizedProfile({ user, tab }) {
  const [draft, setDraft] = useState(user.bio);
  useEffect(() => { document.title = user.name; }, [user.name]);

  return <ProfileView user={user} tab={tab} draft={draft} />;
}
```

`key={user.id}` — вопрос на senior. Без него при смене аккаунта (Ann → Bob без выхода) `AuthorizedProfile` остаётся тем же экземпляром, и `draft` хранит био Ann: начальное значение `useState` читается только при монтировании. С ключом React создаёт новый fiber с новым списком ячеек, и состояние сбрасывается.
::
