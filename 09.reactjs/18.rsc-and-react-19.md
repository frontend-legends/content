# Server Components и React 19

Компоненты, которые выполняются только на сервере, серверные функции, Actions для форм и мутаций, `use` и остальные возможности React 19. Спрашивают, чем Server Components отличаются от SSR и что делает `'use client'`. Глубже — что на самом деле уходит в браузер, почему нельзя передать функцию в клиентский компонент, чем опасны серверные функции и как работают `useActionState` и `useOptimistic`.

::tldr
- **Server Component выполняется только на сервере, и его код не попадает в бандл.** В браузер уходит результат — сериализованное дерево (RSC payload). Компонент может быть `async` и читать базу напрямую, но у него нет состояния, эффектов и обработчиков.
- **RSC и SSR решают разные задачи.** SSR превращает клиентские компоненты в HTML для первого экрана, но их код всё равно гидратируется. RSC убирает код компонентов из браузера вовсе. Их используют вместе.
- **`'use client'` отмечает границу:** модуль и всё, что он импортирует, становится клиентским. Props через границу должны сериализоваться — функцию передать нельзя, а серверную функцию можно: уйдёт ссылка.
- **Серверная функция (`'use server'`) — публичный HTTP-эндпоинт.** Внутри проверяют пользователя, права и входные данные, как в любом API.
- **Actions — асинхронные переходы для мутаций.** `<form action={fn}>`, `useActionState`, `useFormStatus` и `useOptimistic` дают ожидание, результат, оптимистичный интерфейс и сброс формы без ручных флагов.
::

## Проблема, которую решают Server Components

В конце темы про [гидратацию](/content/reactjs/rendering-and-hydration) осталась нерешённая проблема. :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"} показывает страницу быстро, но браузер всё равно скачивает и выполняет код **всех** компонентов, чтобы их гидратировать. Даже тех, что просто выводят текст и никогда не меняются.

Сквозной пример — страница товара:

```jsx
export default async function ProductPage({ id }) {
  const product = await db.product(id);          // база — прямо в компоненте
  const html = renderMarkdown(product.description); // тяжёлая библиотека Markdown

  return (
    <article>
      <h1>{product.title}</h1>
      <p>{product.price} ₽</p>
      <div dangerouslySetInnerHTML={{ __html: html }} />
      <LikeButton productId={product.id} />
      <AddToCart productId={product.id} />
    </article>
  );
}
```

Из всей страницы интерактивны две кнопки. Описание, цена, библиотека Markdown и код доступа к базе браузеру не нужны. В классическом SSR они всё равно оказались бы в бандле и гидратировались. Server Components позволяют их туда не отправлять.

## Что уходит в браузер

Server Component — обычный компонент, который выполняется только в серверном окружении. Он может быть `async`: React дождётся промиса прямо в рендере. Результат React сериализует в **RSC payload** — строчный формат, который описывает дерево элементов. Для простого компонента в production проверка показала одну строку:

```text
0:["$","h1",null,{"children":"Чайник"}]
```

Это описание `<h1>Чайник</h1>`, а не код компонента и не HTML. Клиентская часть React читает payload и строит из него дерево, как если бы элементы создали клиентские компоненты. Что из этого следует:

- **Кода компонента в бандле нет.** Ни `ProductPage`, ни `db`, ни библиотеки Markdown браузер не скачивает.
- **Данные остаются на сервере**, если их не отрендерили. Поле `supplierSecret` из базы не попало в payload — в нём только то, что компонент вывел.
- **Нет состояния и эффектов.** В серверном окружении у `react` нет `useState` и `useEffect` — в проверке они `undefined`. Нет и обработчиков событий: их нечем выполнять.
- **В dev payload богаче.** Для React DevTools туда добавляется отладочная информация: имя компонента, его props, стек. В production — только результат.

### RSC и SSR — не одно и то же

| | SSR | Server Components |
| --- | --- | --- |
| Что рендерит | клиентские компоненты в HTML | серверные компоненты в RSC payload |
| Код в браузере | да, для гидратации | нет |
| Когда работает | первый запрос страницы | первый запрос и каждая навигация |
| Зачем | быстрый первый экран, SEO | меньше JS, данные рядом с сервером |

Фреймворк использует оба механизма вместе. На первом запросе сервер рендерит серверные компоненты в payload, а потом payload и клиентские компоненты — в HTML. При навигации клиент запрашивает только payload новой страницы и обновляет дерево, сохраняя состояние клиентских компонентов.

Серверные компоненты не умеют реагировать на клик. Значит, кнопки должны быть клиентскими — и между двумя мирами появляется граница.

## Граница: 'use client'

Клиентский компонент отмечают директивой в начале файла:

```jsx
'use client';

import { useState } from 'react';

export function LikeButton({ productId }) {
  const [liked, setLiked] = useState(false);
  return <button onClick={() => setLiked(!liked)}>{liked ? '♥' : '♡'}</button>;
}
```

`'use client'` помечает **модуль** как точку входа в клиентский код. Всё, что этот модуль импортирует, тоже попадает в бандл. Серверный компонент, который рендерит `<LikeButton>`, получает не код, а ссылку на модуль: в payload проверка показала ссылку на `./LikeButton.js`, имя чанка и props `{"productId":7}`. Браузер загрузит чанк и отрендерит компонент сам.

Директиву ставят как можно ниже по дереву: не на страницу целиком, а на кнопку. Всё, что выше, остаётся серверным.

### Что можно передать через границу

Props от серверного компонента к клиентскому едут в payload, поэтому должны сериализоваться: примитивы, массивы, простые объекты, `Date`, `Map`, `Set`, промисы, JSX. Функции — нет:

```text
<LikeButton onLike={() => …} />          → Event handlers cannot be passed to Client Component props.
<PriceTag format={(p) => `${p} ₽`} />    → Functions cannot be passed directly to Client Components
```

Исключение — **серверные функции**. Их тоже нельзя сериализовать, но можно передать ссылкой: в проверке вместо тела функции в payload ушёл идентификатор `actions.js#likeProduct`. Клиент вызовет её по этому идентификатору, и выполнится она на сервере.

Важно, что сериализуется **всё**, что передано в props. `<UserMenu user={user} />` с полным объектом из базы отправит в браузер и хеш пароля, и внутренние поля. В клиентский компонент передают только нужные поля.

### Как совмещать серверное и клиентское

Клиентский компонент не может импортировать серверный: импорт в клиентском модуле делает импортируемое клиентским. Но он может **принять серверный компонент через props** — как `children`:

```jsx
// Tabs.jsx — клиентский, хранит активную вкладку
'use client';
export function Tabs({ children }) { /* useState, переключение */ }

// ProductPage.jsx — серверный
<Tabs>
  <Description productId={id} />   {/* серверный компонент, рендерится на сервере */}
  <Reviews productId={id} />
</Tabs>
```

`Description` и `Reviews` отрендерятся на сервере и придут в `Tabs` готовыми элементами — та же композиция через слоты, что и в [Паттернах](/content/reactjs/patterns-and-component-design).

Чтение данных разобрано. Но кнопка «в корзину» должна их **изменить** — на сервере.

## Серверные функции

Директива `'use server'` отмечает асинхронную функцию, которая выполняется на сервере, но её можно вызвать с клиента:

```jsx
// actions.js
'use server';

export async function addToCart(formData) {
  const user = await getSessionUser();               // кто вызывает
  if (!user) throw new Error('Нужно войти');
  const productId = Number(formData.get('productId'));
  if (!Number.isInteger(productId)) throw new Error('Неверный товар');
  await db.cart.add(user.id, productId);
}
```

Фреймворк превращает такую функцию в эндпоинт: клиент получает ссылку на неё, а вызов отправляет POST-запрос с аргументами. Отсюда правила:

- **Это публичный эндпоинт.** Его можно вызвать без интерфейса, с любыми аргументами. Проверка пользователя, прав и данных — внутри функции, всегда. То, что кнопку видят только админы, ничего не защищает.
- **Аргументы и результат сериализуются**, как props через границу.
- **Это сервер со всеми его рисками.** В декабре 2025 года в протоколе серверных функций нашли критическую уязвимость с удалённым выполнением кода (подробно — в [Безопасности](/content/reactjs/security)). Зависимости фреймворка обновляют сразу.

Серверную функцию удобнее всего вызывать из формы. Для этого React 19 добавил Actions.

## Actions

**Action** — асинхронная функция, запущенная в переходе (transition). React отслеживает её от начала до конца, включая все `await`, и даёт интерфейсу знать, что идёт работа. Самый частый способ запустить Action — форма:

```jsx
<form action={addToCart}>
  <input type="hidden" name="productId" value={product.id} />
  <SubmitButton />
</form>
```

`action` у формы принимает функцию. При отправке React сам вызывает её с `FormData`, без `onSubmit` и `preventDefault`. После успешного завершения React **сбрасывает неуправляемые поля формы** — в проверке поле ввода очистилось после добавления задачи. Если функция серверная, форма работает и до загрузки JS: браузер отправит её обычным POST-запросом.

### useActionState: результат и ожидание

```jsx
function AddTodo() {
  const [state, formAction, isPending] = useActionState(addTodo, { items: [], error: null });

  return (
    <form action={formAction}>
      <input name="text" />
      <SubmitButton />
      {state.error && <p role="alert">{state.error}</p>}
      <ul>{state.items.map((t) => <li key={t}>{t}</li>)}</ul>
    </form>
  );
}

async function addTodo(prev, formData) {
  const text = formData.get('text');
  if (!text) return { ...prev, error: 'Пустая задача' };
  await api.addTodo(text);
  return { items: [...prev.items, text], error: null };
}
```

Функция действия получает прошлое состояние и данные формы и возвращает новое состояние — как редьюсер, только асинхронный. `isPending` — идёт ли действие. Ошибки валидации возвращают в состоянии, а не бросают: в проверке пустая отправка показала «Пустая задача».

### useFormStatus: статус из глубины формы

```jsx
import { useFormStatus } from 'react-dom';

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Добавляем…' : 'Добавить'}</button>;
}
```

`useFormStatus` читает состояние **родительской** формы. Кнопку можно вынести в дизайн-систему, и ей не нужно передавать `isPending` через props. Хук работает только внутри `<form>` — в компоненте, который сам рендерит форму, он вернёт `pending: false`.

### useOptimistic: показать результат до ответа

```jsx
function Like({ liked, onSave }) {
  const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);
  const [, startTransition] = useTransition();

  const toggle = () =>
    startTransition(async () => {
      setOptimisticLiked(!liked);   // сразу на экране
      await onSave(!liked);         // запрос; родитель обновит liked, если успех
    });

  return <button onClick={toggle}>{optimisticLiked ? '♥' : '♡'}</button>;
}
```

`useOptimistic` показывает временное значение, пока идёт Action. Когда Action завершится, оптимистичное значение исчезает, и экран показывает реальное состояние. Если сохранение прошло и родитель обновил `liked`, ничего не мигает. Если упало, реальное состояние не изменилось, и экран возвращается к нему сам — в проверке сердечко погасло до ответа и загорелось снова, когда «сервер» вернул ошибку. Отката руками писать не нужно.

> Оптимистичные обновления в кеше запросов (TanStack Query) — в [Загрузке данных](/content/reactjs/data-fetching).

## use

`use` читает ресурс прямо в рендере:

```jsx
function Reviews({ reviewsPromise }) {
  const reviews = use(reviewsPromise);   // приостановит компонент до готовности
  return <ul>{reviews.map((r) => <li key={r.id}>{r.text}</li>)}</ul>;
}

// серверный компонент начинает загрузку и передаёт промис, не дожидаясь
<Suspense fallback={<p>загружаем отзывы…</p>}>
  <Reviews reviewsPromise={db.reviews(id)} />
</Suspense>
```

Пока промис не готов, компонент приостанавливается, и React показывает ближайший `Suspense`. Серверный компонент может начать загрузку и передать промис в клиентский компонент — он сериализуется и «досчитается» в браузере. Промис должен быть стабильным: созданный в рендере клиентского компонента, он каждый раз новый.

`use` можно вызывать в условиях и циклах, в отличие от остальных хуков, и он же читает контекст: `use(ThemeContext)`. Почему ему можно — в [Механике хуков](/content/reactjs/hooks-mechanics).

## Остальное в React 19

- **Метаданные документа.** `<title>`, `<meta>` и `<link>` можно рендерить в любом компоненте — React поднимет их в `<head>`. В проверке `<title>` из компонента страницы оказался в `head`, а не внутри `<article>`.
- **Таблицы стилей и предзагрузка.** `<link rel="stylesheet" precedence>` с порядком загрузки, функции `preload` и `preinit` из `react-dom` для ресурсов, которые понадобятся позже.
- **`ref` — обычный prop**, а callback ref может вернуть cleanup — в [Refs, порталах и доступности](/content/reactjs/refs-portals-a11y).
- **`<Context>` как провайдер** вместо `<Context.Provider>` — в [Context API](/content/reactjs/context-api).
- **Понятные ошибки гидратации** — одна ошибка с диффом вместо серии предупреждений, в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration).

Актуально на ноябрь 2026.

| Версия | Что изменилось |

## Красные флаги в ответе

- **«Server Components — это и есть SSR».** SSR рендерит клиентские компоненты в HTML, и их код гидратируется. Код серверных компонентов в браузер не попадает вовсе.
- **«`'use client'` значит, что компонент рендерится только в браузере».** Клиентские компоненты тоже рендерятся на сервере при SSR. Директива означает, что код компонента попадёт в бандл и будет гидратирован.
- **«Передам в клиентский компонент колбэк из серверного».** Функции не сериализуются. Можно передать только серверную функцию — ссылкой.
- **«Серверную функцию вызывает только моя форма».** Это публичный эндпоинт: внутри — проверка пользователя, прав и данных.
- **«Передам в клиентский компонент объект пользователя целиком».** Всё, что ушло в props, сериализуется в payload и видно в браузере.

## Как спрашивают на собеседовании

::question
Что такое React Server Components?

#answer
Компоненты, которые выполняются только на сервере. Их код не попадает в браузер, а в браузер уходит результат рендера. Они могут быть `async` и читать данные напрямую, но у них нет состояния, эффектов и обработчиков событий.

#more
Результат сериализуется в RSC payload — описание дерева элементов со ссылками на клиентские модули, а не HTML. Клиентский React строит из него дерево и при навигации обновляет только то, что пришло, сохраняя состояние клиентских компонентов. Выигрыш — меньше JS, данные рядом с базой, секреты остаются на сервере. Цена — граница сериализации, необходимость фреймворка и сервер со своими рисками.
::

::question
Чем RSC отличается от SSR?

#answer
SSR рендерит клиентские компоненты в HTML для быстрого первого экрана, но их код всё равно загружается для гидратации. Server Components в браузер не отправляются вообще, их результат приходит как RSC payload.

#more
Это ортогональные механизмы, и фреймворк использует оба: на первом запросе серверные компоненты дают payload, а он вместе с клиентскими компонентами рендерится в HTML через SSR. При клиентской навигации SSR не участвует — приходит только payload новой страницы. SSR отвечает на вопрос «когда рендерить», RSC — «где живёт компонент».
::

::question
Что делает директива 'use client'?

#answer
Отмечает модуль как клиентский: его компоненты и всё, что он импортирует, попадают в бандл, гидратируются и могут использовать состояние, эффекты и обработчики.

#more
Это граница модулей, а не «рендер только в браузере»: клиентские компоненты тоже рендерятся на сервере при SSR. Серверный компонент, который рендерит клиентский, отправляет в payload ссылку на модуль и сериализованные props. Директиву ставят как можно ниже, на интерактивные листья. Клиентский компонент не может импортировать серверный, но может получить его готовым через `children`.
::

::question
Почему нельзя передать функцию из серверного компонента в клиентский?

#answer
Props через границу сериализуются в payload, а функцию сериализовать нельзя. React бросит ошибку `Functions cannot be passed directly to Client Components`.

#more
Для обработчиков с именем `on*` ошибка своя: `Event handlers cannot be passed to Client Component props`. Исключение — серверные функции: они уходят ссылкой с идентификатором, а при вызове клиент отправляет запрос на сервер. Та же сериализация означает, что всё переданное в props видно в браузере, поэтому объекты из базы целиком в клиентские компоненты не передают.
::

::question
Что такое серверные функции и как их защищать?

#answer
Функции с `'use server'`, которые выполняются на сервере, но вызываются с клиента — например, через `<form action>`. Это мутации без ручного API.

#more
Фреймворк делает из каждой функции HTTP-эндпоинт, и его можно вызвать напрямую с любыми аргументами. Внутри — аутентификация, проверка прав на конкретный объект и валидация данных (схемы вроде Zod), как в любом API. Аргументы и результат сериализуются. Уязвимость декабря 2025 года в протоколе серверных функций показала, что это полноценная серверная поверхность атаки, и зависимости фреймворка нужно обновлять сразу.
::

::question
Как работают useActionState и useFormStatus?

#answer
`useActionState` оборачивает функцию действия: даёт текущее состояние (результат последнего вызова), функцию для `action` формы и флаг ожидания. `useFormStatus` читает статус родительской формы из вложенного компонента — например, чтобы заблокировать кнопку.

#more
Функция действия получает прошлое состояние и `FormData` и возвращает новое — как асинхронный редьюсер. Ошибки валидации возвращают в состоянии. Action выполняется в переходе, поэтому `isPending` держится через все `await`. После успешного завершения React сбрасывает неуправляемые поля формы. `useFormStatus` работает только внутри `<form>` и не видит форму, которую рендерит тот же компонент.
::

::question
Зачем нужен useOptimistic?

#answer
Чтобы показать ожидаемый результат действия сразу, до ответа сервера. Когда действие завершится, экран покажет реальное состояние — при ошибке оптимистичное значение пропадёт само.

#more
Оптимистичное значение живёт, пока идёт Action. После завершения React возвращается к реальному состоянию: если родитель обновил его при успехе, мигания нет, если нет — значение откатывается без ручного кода. Поэтому `setOptimistic` вызывают внутри перехода (`startTransition` или Action формы). В отличие от оптимистичных обновлений кеша TanStack Query, здесь нет снимка и отката — источник истины остаётся в обычном состоянии.
::

## Практика

::practice{title="Что уйдёт в браузер?"}
Страница профиля в приложении с Server Components. Что окажется в браузере: какой код и какие данные? Что не так?

```jsx
// ProfilePage.jsx — серверный компонент
import { db } from './db';
import { UserMenu } from './UserMenu';   // 'use client'

export default async function ProfilePage() {
  const user = await db.users.current(); // { id, name, email, passwordHash, role }
  return (
    <main>
      <h1>{user.name}</h1>
      <UserMenu user={user} onLogout={() => db.sessions.end(user.id)} />
    </main>
  );
}
```

#solution
В бандл попадёт код `UserMenu` и всего, что он импортирует. Код `ProfilePage` и модуль `db` в браузер не уйдут. В payload попадёт `<h1>` с именем и props `UserMenu`.

Две проблемы:

1. **`user={user}`** — объект целиком сериализуется в payload, включая `email` и `passwordHash`. Всё, что передано клиентскому компоненту, видно в браузере.
2. **`onLogout={() => …}`** — функцию нельзя передать через границу: `Event handlers cannot be passed to Client Component props`.

```jsx
// actions.js
'use server';
export async function logout() {
  const user = await getSessionUser();
  if (user) await db.sessions.end(user.id);
}

// ProfilePage.jsx
import { logout } from './actions';

export default async function ProfilePage() {
  const user = await db.users.current();
  return (
    <main>
      <h1>{user.name}</h1>
      <UserMenu name={user.name} role={user.role} logout={logout} />
    </main>
  );
}
```

Клиенту — только нужные поля, а выход — серверная функция, которая уйдёт ссылкой и сама определит пользователя по сессии, не доверяя аргументам.
::

::practice{title="Форма без лишнего состояния"}
Перепиши форму на Actions: без `useState` для полей, без ручного флага загрузки и с сообщением об ошибке.

```jsx
function Subscribe() {
  const [email, setEmail] = useState('');
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState(null);

  async function handleSubmit(e) {
    e.preventDefault();
    setLoading(true);
    try {
      await api.subscribe(email);
      setEmail('');
    } catch (err) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={email} onChange={(e) => setEmail(e.target.value)} />
      <button disabled={loading}>Подписаться</button>
      {error && <p>{error}</p>}
    </form>
  );
}
```

#solution
```jsx
async function subscribe(prev, formData) {
  try {
    await api.subscribe(formData.get('email'));
    return { error: null, done: true };
  } catch (err) {
    return { error: err.message, done: false };
  }
}

function SubmitButton() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>{pending ? 'Подписываем…' : 'Подписаться'}</button>;
}

function Subscribe() {
  const [state, formAction] = useActionState(subscribe, { error: null, done: false });

  return (
    <form action={formAction}>
      <input name="email" type="email" required />
      <SubmitButton />
      {state.error && <p role="alert">{state.error}</p>}
      {state.done && <p>Готово!</p>}
    </form>
  );
}
```

Поле неуправляемое: значение React берёт из `FormData`, а после успешного действия сам очищает форму. Ожидание даёт `useFormStatus`, ошибка приходит в состоянии. В проверке поле очистилось после добавления, а пустая отправка показала ошибку из состояния. Если `subscribe` — серверная функция, форма работает даже до загрузки JS.
::
