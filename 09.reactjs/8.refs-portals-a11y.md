# Refs, порталы и доступность

Где декларативной модели не хватает и как из неё правильно выйти: ссылки на DOM-узлы, императивный API компонента, рендер вне своего DOM-родителя и доступность. Всё это собирается в одной задаче, которую любят давать на собеседовании, — доступная модалка. Спрашивают, чем ref отличается от состояния и зачем портал. Глубже — когда заполняется `ref.current`, как работают callback ref и cleanup и почему клик внутри портала доходит до React-родителя.

::tldr
- **Ref — изменяемый ящик, который переживает рендеры и не вызывает рендер.** Для DOM-узлов, id таймеров и значений, которые не влияют на разметку. Читать и писать `ref.current` в рендере нельзя.
- **`ref.current` заполняется в commit:** в рендере его ещё нет, в `useLayoutEffect` и `useEffect` узел уже есть, после размонтирования — `null`. Поэтому фокус сразу после `setState` падает.
- **`ref` — обычный prop функционального компонента, `forwardRef` больше не нужен**, а callback ref может вернуть cleanup. `useImperativeHandle` отдаёт наружу свой API вместо DOM-узла.
- **Портал рендерит в другой DOM-узел, но остаётся в дереве React:** события всплывают до React-родителя, контекст доходит.
- **React не делает интерфейс доступным сам.** Доступность — это семантические элементы, подписи, ARIA и управление фокусом, а для модалки — нативный `<dialog>` или готовые примитивы.
::

## Задача: доступная модалка

Нужно сделать модальное окно подтверждения:

- оно открывается по кнопке и показывается поверх всей страницы;
- фокус переходит внутрь, `Tab` не уходит на фон, `Esc` закрывает;
- после закрытия фокус возвращается на кнопку;
- родитель может открыть его из кода, например после ошибки сохранения.

Декларативно «фокус на этом поле» или «покажи поверх всего, игнорируя `overflow: hidden` родителя» не опишешь. Нужен доступ к DOM — и с него начнём.

## Ref — ящик, который переживает рендеры

`useRef` возвращает объект `{ current }`, который React хранит между рендерами и всегда отдаёт тот же:

```jsx
function SearchInput() {
  const inputRef = useRef(null);
  return <input ref={inputRef} />;
}
```

Чем ref отличается от состояния:

| | `useState` | `useRef` |
| --- | --- | --- |
| Изменение | через сеттер, планирует рендер | присваивание `ref.current = x`, рендера нет |
| Значение в рендере | снимок этого рендера | общее для всех рендеров, может измениться в любой момент |
| Для чего | всё, что влияет на разметку | DOM-узлы, id таймеров, подписки, «последнее значение» для колбэков |

Правило: если значение должно появиться на экране — это состояние. Если оно нужно только обработчикам и эффектам — ref. Читать и писать `ref.current` во время рендера нельзя (кроме ленивой инициализации): React не отслеживает ref, и компонент покажет устаревшие данные. Почему так — в [Механике хуков](/content/reactjs/hooks-mechanics).

### Когда в ref появляется узел

Атрибут `ref={inputRef}` просит React положить в `inputRef.current` DOM-узел. Делает он это в commit — после изменения DOM и до layout-эффектов:

```text
рендер              → ref.current === null (узла ещё нет)
commit: DOM готов   → ref.current = <input>
useLayoutEffect     → узел доступен
useEffect           → узел доступен
размонтирование     → ref.current = null
```

Отсюда частый баг: сразу после `setState` узла ещё нет.

```jsx
function startEditing() {
  setEditing(true);
  inputRef.current.focus(); // TypeError: поле появится только после рендера
}
```

Варианты: перевести фокус в эффекте, который зависит от `editing`; принудительно закоммитить через `flushSync(() => setEditing(true))` перед `focus()`; или поставить `autoFocus` на поле, которое появляется.

### Callback ref

Вместо объекта в `ref` можно передать функцию. React вызовет её с узлом, когда тот появится:

```jsx
<div ref={(node) => {
  const observer = new ResizeObserver(() => measure(node));
  observer.observe(node);
  return () => observer.disconnect(); // React 19: cleanup при отсоединении
}} />
```

Callback ref нужен, когда узел может появиться и исчезнуть (условный рендер, список) и при этом нужно что-то сделать: подписаться, измерить, передать узел библиотеке.

Как часто он вызывается, зависит от того, меняется ли функция:

| Callback ref | Вызовы при монтировании, одном рендере и размонтировании |
| --- | --- |
| новая функция на каждом рендере, без cleanup | `node`, `null`, `node`, `null` |
| стабильная (`useCallback`) | `node`, `null` |
| новая функция, возвращает cleanup | `node`, cleanup, `node`, cleanup |

Новая функция для React — новый ref: старый отсоединяется, новый присоединяется. В React 19 callback может вернуть cleanup, и тогда при отсоединении вызывается он, а не колбэк с `null`.

Для модалки у нас есть способ дотянуться до узла. Но как родителю получить доступ к узлу или API своего компонента?

## Ref на свой компонент

### ref как prop

В React 19 функциональный компонент получает `ref` как обычный prop и сам решает, к какому узлу его привязать:

```jsx
function TextField({ label, ref }) {
  return (
    <label>
      {label}
      <input ref={ref} />
    </label>
  );
}

<TextField label="Email" ref={emailRef} />   // emailRef.current — это <input>
```

До React 19 `ref` был зарезервирован и до компонента не доходил, поэтому его пробрасывали через `forwardRef`. `forwardRef` по-прежнему работает, но в новом коде не нужен. Если компонент `ref` не использует, ссылка останется `null` — никакой магии.

### useImperativeHandle: свой API вместо узла

Иногда родителю нужен не DOM-узел, а несколько действий. Отдавать весь узел — значит позволить снаружи делать с ним что угодно. `useImperativeHandle` кладёт в ref свой объект:

```jsx
function ConfirmDialog({ ref, title, onConfirm }) {
  const dialogRef = useRef(null);

  useImperativeHandle(ref, () => ({
    open: () => dialogRef.current.showModal(),
    close: () => dialogRef.current.close(),
  }), []);

  return (
    <dialog ref={dialogRef} aria-labelledby="confirm-title">
      <h2 id="confirm-title">{title}</h2>
      <button onClick={onConfirm}>Удалить</button>
      <button onClick={() => dialogRef.current.close()}>Отмена</button>
    </dialog>
  );
}

// родитель
const confirm = useRef(null);
useEffect(() => {
  if (saveFailed) confirm.current.open();
}, [saveFailed]);
```

Под капотом это layout-эффект, поэтому API готов к моменту эффектов родителя. Список зависимостей работает как у эффектов: без него объект пересоздаётся на каждом рендере.

Императивный API нарушает однонаправленный поток: состояние «открыто» прячется внутри компонента. Поэтому он оправдан для действий, которые плохо выражаются состоянием: фокус, прокрутка, воспроизведение видео, открытие нативного `<dialog>`. Если можно передать `open` через props — передавай через props.

Модалку можно открыть из кода. Осталось показать её поверх всего.

## Порталы

Модалка, тултип или выпадающее меню внутри карточки с `overflow: hidden` будут обрезаны, а `z-index` не поможет вырваться из контекста наложения родителя. Нужно, чтобы в DOM элемент лежал в другом месте — обычно прямо в `body`. Для этого есть `createPortal`:

```jsx
import { createPortal } from 'react-dom';

function Modal({ onClose, children }) {
  return createPortal(
    <div className="overlay" onClick={(e) => e.target === e.currentTarget && onClose()}>
      <div role="dialog" aria-modal="true">{children}</div>
    </div>,
    document.body,
  );
}
```

В DOM разметка модалки лежит в `body`. В дереве React портал остаётся ребёнком компонента, который его отрендерил. Из этого следуют три вещи:

- **Контекст доходит.** Модалка внутри провайдера темы получает тему, хотя в DOM она вне провайдера.
- **События всплывают по дереву React.** Клик по кнопке внутри модалки дойдёт до `onClick` карточки, в которой модалка отрендерена. В проверке клик внутри портала вызвал обработчик карточки.
- **Нативные слушатели DOM-родителя событие не видят.** Слушатель, повешенный через `addEventListener` на карточку, клик из портала не получил: в DOM модалка не внутри неё.

Второе часто становится багом: карточка товара открывает страницу по клику, а клик по кнопке в модалке, отрендеренной внутри карточки, тоже открывает страницу. Решения: рендерить модалку вне кликабельной области, проверять `e.target` в обработчике карточки или останавливать всплытие на корне модалки.

Закрытие по клику на оверлей требует того же внимания: клик по содержимому всплывает до оверлея. Поэтому оверлей проверяет, что клик был именно по нему: `e.target === e.currentTarget`.

> Как React обрабатывает события через корень приложения — в [State и событиях](/content/reactjs/state-and-events).

### Нативный dialog

Для модалок у браузера есть свой элемент. `dialog.showModal()` открывает `<dialog>` в верхнем слое (top layer): он показывается поверх всего без портала и `z-index`, остальная страница становится инертной (на неё не попасть ни кликом, ни `Tab`), фокус переходит внутрь, а `Esc` закрывает окно. Поэтому в `ConfirmDialog` выше нет ни портала, ни ручного focus trap. Портал по-прежнему нужен для того, что не является модальным окном: тултипов, выпадающих меню, тостов.

Модалка показана и управляется. Остался последний пункт задачи — чтобы ею мог пользоваться каждый.

## Доступность

React рендерит обычный DOM, поэтому доступность — это в первую очередь правильный HTML. React не добавляет её сам, но и не мешает. Есть несколько вещей, специфичных для React-приложений.

### Семантика вместо div с onClick

```jsx
<div onClick={save}>Сохранить</div>       // ❌ нет фокуса, Enter, Space и роли
<button onClick={save}>Сохранить</button> // ✅ всё это — бесплатно
```

`div` с обработчиком недоступен с клавиатуры и не объявлен скринридеру как кнопка. Чтобы это исправить, нужны `role="button"`, `tabIndex={0}` и обработка клавиш — то есть повторить `<button>` вручную. Линтер `eslint-plugin-jsx-a11y` ловит такие места до ревью.

### ARIA и подписи в JSX

- **`aria-*` и `data-*` пишутся через дефис**, как в HTML, в отличие от остальных атрибутов в camelCase: `aria-expanded={isOpen}`, `aria-controls="menu"`.
- **Подпись поля — через `htmlFor`:** `<label htmlFor="email">`. Если компонент используется на странице несколько раз, id не хардкодят, а генерируют `useId` — он одинаков на сервере и клиенте (подробно — в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration)).
- **Первое правило ARIA — не использовать ARIA**, если есть нативный элемент. `<button>`, `<dialog>`, `<details>` уже несут нужные роли и поведение.

### Фокус в SPA

В многостраничном сайте браузер сам сбрасывает фокус при переходе на новую страницу. В SPA страница не перезагружается, и фокус остаётся на ссылке, по которой кликнули, или теряется вместе с удалённым узлом. Управлять им приходится вручную:

- **после открытия модалки** фокус — внутрь (нативный `<dialog>` делает это сам), после закрытия — обратно на триггер;
- **после смены маршрута** — фокус на заголовок новой страницы или объявление через live region, чтобы скринридер узнал о переходе;
- **после удаления элемента** — фокус на соседний элемент, иначе он улетит в `body`.

Возврат фокуса на триггер вручную выглядит так:

```jsx
function useReturnFocus(open) {
  useEffect(() => {
    if (!open) return;
    const trigger = document.activeElement;  // кто был в фокусе до открытия
    return () => trigger?.focus();           // вернуть при закрытии
  }, [open]);
}
```

Для сложных виджетов — комбобоксов, меню, табов, дата-пикеров — правильное поведение клавиатуры и ARIA описаны в WAI-ARIA Authoring Practices, и писать их самому долго. Обычно берут готовые примитивы без стилей: Radix UI, React Aria, Headless UI.

> Семантика, роли и ARIA подробно — в главе [HTML: доступность](/content/html/accessibility).

## Красные флаги в ответе

- **«Ref — это способ хранить состояние без рендера, буду показывать его в разметке».** То, что видно на экране, должно быть состоянием. Ref в рендере — устаревшие данные.
- **«`ref.current` доступен сразу после `setState`».** Узел появится только в commit. Фокус — в эффекте, через `flushSync` или `autoFocus`.
- **«Для ref на свой компонент нужен `forwardRef`».** В React 19 `ref` — обычный prop функционального компонента.
- **«Портал выносит компонент из дерева React».** Только из DOM-дерева. Контекст и всплытие событий идут по дереву React.
- **«Доступность — это `aria-label` на всём».** Сначала семантические элементы и подписи, ARIA — только где нативного элемента нет.

## Как спрашивают на собеседовании

::question
Когда использовать ref вместо состояния?

#answer
Когда значение не влияет на то, что видно на экране: DOM-узел, id таймера, подписка, предыдущее значение для колбэка. Изменение ref не вызывает рендер, а значение сохраняется между рендерами.

#more
Ref — один объект на всё время жизни компонента, в отличие от снимка состояния. Поэтому в колбэке, который пережил рендер, ref даёт актуальное значение, а состояние — устаревшее. Цена — React не знает об изменениях: читать и писать `ref.current` в рендере нельзя, иначе разметка не обновится, а React Compiler и StrictMode сломают такую логику.
::

::question
Когда в ref появляется DOM-узел?

#answer
После того как React вставил элемент в DOM. В рендере `ref.current` ещё `null`, в эффектах — уже узел.

#more
Refs присоединяются в commit после мутаций DOM и до layout-эффектов, отсоединяются при удалении узла (`ref.current = null`). Поэтому `setEditing(true); ref.current.focus()` падает: рендера ещё не было. Решения — эффект, `flushSync` перед `focus()` или `autoFocus`. Callback ref вызывается в тот же момент. Если функция новая на каждом рендере, React отсоединяет старую (вызов с `null` или cleanup в React 19) и присоединяет новую.

#followups
- «Как подписаться на ResizeObserver для узла, который появляется по условию?» → callback ref с cleanup: подписка при появлении узла, отписка при удалении
::

::question
Что изменилось с ref в React 19?

#answer
`ref` стал обычным prop функционального компонента, `forwardRef` больше не нужен. Callback ref может вернуть cleanup-функцию.

#more
Раньше `ref` вырезался из props, и компоненту нужен был `forwardRef`, чтобы получить его. Теперь компонент сам привязывает `ref` к нужному узлу или передаёт его в `useImperativeHandle`. Cleanup у callback ref заменяет вызов с `null`: подписка и отписка пишутся рядом, как в эффекте.
::

::question
Зачем нужен useImperativeHandle?

#answer
Чтобы отдать родителю через ref не DOM-узел, а свой набор методов: `open`, `close`, `focus`. Родитель вызывает `ref.current.open()`.

#more
Это способ ограничить императивный доступ: снаружи доступны только объявленные действия, а не весь узел. Под капотом это layout-эффект, API готов к эффектам родителя, а список зависимостей решает, когда объект пересоздаётся. Использовать стоит для действий, которые плохо выражаются состоянием (фокус, прокрутка, воспроизведение, `showModal`). Если открытие можно передать через props — это лучше: не прячет состояние от родителя.
::

::question
Зачем нужен createPortal?

#answer
Чтобы отрендерить элемент в другой DOM-узел, обычно `body`. Тогда модалка или тултип не обрезаются `overflow: hidden` и не зависят от `z-index` родителя.

#more
Портал меняет только место в DOM: в дереве React элемент остаётся ребёнком компонента, поэтому получает контекст и состояние родителя. Для модальных окон сегодня часто достаточно нативного `<dialog>` с `showModal()`: он рендерится в верхнем слое без портала, делает фон инертным, переводит фокус и закрывается по `Esc`.
::

::question
Как всплывают события из портала?

#answer
По дереву React, а не по DOM. Клик внутри модалки, которая в DOM лежит в `body`, дойдёт до `onClick` React-родителя портала.

#more
React обрабатывает события сам, проходя по дереву fiber, а портал в этом дереве — ребёнок своего компонента. Поэтому React-обработчики родителя срабатывают, а нативный `addEventListener` на DOM-родителе — нет. Типичный баг: кликабельная карточка реагирует на клики внутри модалки, отрендеренной в ней. Лечится выносом модалки, проверкой `e.target` или `stopPropagation` на корне модалки.
::

::question
Что нужно для доступной модалки?

#answer
Роль `dialog` и `aria-modal`, заголовок через `aria-labelledby`, перевод фокуса внутрь, запрет `Tab` на фон, закрытие по `Esc` и возврат фокуса на кнопку после закрытия.

#more
Нативный `<dialog>` с `showModal()` даёт большую часть из коробки: верхний слой, инертный фон, фокус внутри, `Esc`. Вручную остаётся вернуть фокус на триггер и подписать окно. Если `<dialog>` не подходит, берут готовые примитивы (Radix UI, React Aria), а не пишут focus trap сами: там много крайних случаев — вложенные окна, порталы внутри окна, мобильные скринридеры.
::

## Практика

::practice{title="Почему не ставится фокус?"}
По клику на заголовок он превращается в поле ввода, но фокус в поле не попадает, а в консоли ошибка:

```jsx
function EditableTitle({ value, onSave }) {
  const [editing, setEditing] = useState(false);
  const inputRef = useRef(null);

  function startEditing() {
    setEditing(true);
    inputRef.current.focus();
  }

  return editing
    ? <input ref={inputRef} defaultValue={value} onBlur={(e) => { onSave(e.target.value); setEditing(false); }} />
    : <h2 onClick={startEditing}>{value}</h2>;
}
```

#solution
`setEditing(true)` только планирует рендер. В момент `focus()` поля ещё нет в DOM, `inputRef.current` равен `null`, и вызов бросает `TypeError: Cannot read properties of null`.

Три варианта по возрастанию явности:

```jsx
// 1. autoFocus: поле само получит фокус при появлении
<input ref={inputRef} autoFocus defaultValue={value} />

// 2. эффект, который реагирует на переход в режим редактирования
useEffect(() => {
  if (editing) inputRef.current.focus();
}, [editing]);

// 3. закоммитить синхронно и сразу поставить фокус
function startEditing() {
  flushSync(() => setEditing(true));
  inputRef.current.focus();
}
```

`flushSync` выходит из батчинга и рендерит синхронно — им пользуются точечно, когда без немедленного DOM не обойтись.
::

::practice{title="Модалка открывает страницу товара"}
Карточка товара переходит на страницу товара по клику. Внутри карточки есть кнопка «Быстрый просмотр», которая открывает модалку в портале. Клик по кнопкам внутри модалки тоже переходит на страницу товара:

```jsx
function ProductCard({ product }) {
  const [preview, setPreview] = useState(false);

  return (
    <article onClick={() => navigate(`/p/${product.id}`)}>
      <h3>{product.title}</h3>
      <button onClick={(e) => { e.stopPropagation(); setPreview(true); }}>Быстрый просмотр</button>
      {preview && (
        <Modal onClose={() => setPreview(false)}>
          <button>В корзину</button>
        </Modal>
      )}
    </article>
  );
}
```

#solution
В DOM модалка лежит в `body`, но в дереве React она — ребёнок `<article>`. React всплывает по своему дереву, поэтому клик по «В корзину» доходит до `onClick` карточки.

Лучший фикс — рендерить модалку вне кликабельной области:

```jsx
function ProductCard({ product }) {
  const [preview, setPreview] = useState(false);

  return (
    <>
      <article onClick={() => navigate(`/p/${product.id}`)}>
        <h3>{product.title}</h3>
        <button onClick={(e) => { e.stopPropagation(); setPreview(true); }}>Быстрый просмотр</button>
      </article>
      {preview && (
        <Modal onClose={() => setPreview(false)}>
          <button>В корзину</button>
        </Modal>
      )}
    </>
  );
}
```

Теперь модалка — сосед карточки и в дереве React, и клики из неё до карточки не доходят. Отдельно стоит поправить и саму карточку: кликабельный `<article>` недоступен с клавиатуры. Обычно заголовок делают ссылкой, а кликабельность всей карточки — растянутой на неё псевдоэлементом ссылкой.
::

::practice{title="Почему ref-колбэк вызывается на каждом рендере?"}
Компонент измеряет блок через callback ref. Подписка на `ResizeObserver` создаётся и удаляется при каждом вводе в поле рядом:

```jsx
function Panel() {
  const [text, setText] = useState('');
  const [height, setHeight] = useState(0);

  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <div ref={(node) => {
        if (!node) return;
        const ro = new ResizeObserver(() => setHeight(node.offsetHeight));
        ro.observe(node);
      }}>
        Высота: {height}
      </div>
    </>
  );
}
```

#solution
Колбэк — новая функция на каждом рендере. Для React это новый ref: старый отсоединяется (вызов с `null`), новый присоединяется (вызов с узлом). Каждая буква создаёт новый `ResizeObserver`, а старые никто не отключает — они копятся.

Два фикса. Стабильная функция плюс cleanup из React 19:

```jsx
const measureRef = useCallback((node) => {
  const ro = new ResizeObserver(() => setHeight(node.offsetHeight));
  ro.observe(node);
  return () => ro.disconnect();
}, []);

<div ref={measureRef}>Высота: {height}</div>
```

Со стабильным колбэком он вызывается один раз при появлении узла, а cleanup отключает наблюдатель при удалении. Если узел есть всегда, подписку можно перенести в эффект с обычным `useRef`.
::
