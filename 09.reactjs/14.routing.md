# Роутинг

React сам по себе не умеет роутинг - это библиотека для UI, у неё нет понятия «страница». Навигацию добавляют отдельно. Понимание, **как работает клиентский роутинг** и чем он отличается от серверного, - стандартная тема собеса.

---

## Что такое SPA-роутинг

В классическом сайте каждый переход - это новый запрос к серверу и полная перезагрузка страницы. В **SPA** загрузка происходит один раз, а дальше навигация идёт **на клиенте**: меняется URL и рендерится другой компонент, без перезагрузки.

Под капотом это **History API** браузера:

```js
history.pushState(state, '', '/about'); // меняем URL без перезагрузки
window.addEventListener('popstate', handler); // ловим назад/вперёд
```

Роутер подписывается на изменения URL и сопоставляет путь с компонентом.

<b class="text-on-semi-light">Плюсы и минусы</b> - <span class="text-gray">Плюс - мгновенные переходы, сохранение состояния. Минус - всё на клиенте: дольше первая загрузка, нужен SSR для SEO, маршрутизацию надо настраивать на сервере (любой путь должен отдавать `index.html` - history fallback).</span>

## React Router

Самая распространённая библиотека. Маршруты описываются декларативно, могут быть **вложенными**.

```jsx
import { createBrowserRouter, RouterProvider, Outlet, Link, NavLink } from 'react-router-dom';

const router = createBrowserRouter([
  {
    path: '/',
    element: <Layout />,
    children: [
      { index: true, element: <Home /> },
      { path: 'users/:id', element: <User /> }, // динамический сегмент
      { path: '*', element: <NotFound /> },      // 404
    ],
  },
]);

<RouterProvider router={router} />;
```

### Вложенные маршруты и Outlet

Родительский маршрут рендерит общий layout, а `<Outlet />` - место, куда подставляется дочерний маршрут.

```jsx
function Layout() {
  return (
    <div>
      <nav><Link to="/users/1">User</Link></nav>
      <Outlet /> {/* сюда рендерится текущий дочерний роут */}
    </div>
  );
}
```

### Навигация и параметры

```jsx
const { id } = useParams();              // :id из URL
const navigate = useNavigate();          // программный переход
const [params, setParams] = useSearchParams(); // ?query=...

navigate('/users/2');
```

> `<Link>`/`<NavLink>` вместо `<a>`: они делают клиентский переход без перезагрузки. `NavLink` ещё умеет подсвечивать активный пункт.

## Ленивые маршруты

Роутинг - естественное место для **code splitting**: грузим код страницы только при переходе на неё (см. [производительность](/content/reactjs/performance)).

```jsx
const Dashboard = lazy(() => import('./Dashboard'));

{ path: 'dashboard', element: (
  <Suspense fallback={<Spinner />}><Dashboard /></Suspense>
) }
```

## Загрузка данных на уровне роута

Современный React Router (data API, v6.4+) умеет грузить данные **до** рендера через `loader` - это убирает водопады «отрендерился → начал грузить».

```jsx
{
  path: 'users/:id',
  loader: ({ params }) => fetchUser(params.id), // данные грузятся параллельно с переходом
  element: <User />,
}

function User() {
  const user = useLoaderData(); // данные уже здесь
}
```

`action` аналогично обрабатывает отправку форм. Это сдвиг к модели «данные привязаны к маршруту», которую развивают мета-фреймворки.

## Защищённые маршруты

Стандартный паттерн - обёртка, которая проверяет авторизацию и редиректит.

```jsx
function RequireAuth({ children }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" replace />;
  return children;
}

{ path: 'admin', element: <RequireAuth><Admin /></RequireAuth> }
```

> Защита на клиенте - это UX, **не безопасность**. Реальная авторизация всегда проверяется на сервере; клиентский гард лишь прячет UI.

---

## URL как состояние

Фильтры, номер страницы, поисковый запрос, активный таб логично хранить **в URL** (query params), а не в React-состоянии.

<b class="text-on-semi-light">Зачем</b> - <span class="text-gray">URL становится «шарабельным»: ссылку можно скопировать, обновить страницу, нажать «назад» - состояние сохранится. Это часто забывают, дублируя в `useState` то, что должно быть в URL.</span>

---

## Альтернативы

- **TanStack Router** - типобезопасный роутинг: параметры и поиск строго типизированы.
- **Next.js / Remix** - роутинг **по файловой системе** + серверная загрузка данных из коробки. В мета-фреймворках отдельная библиотека роутинга не нужна (см. [рендеринг](/content/reactjs/rendering-and-hydration)).

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем клиентский роутинг отличается от серверного?</b>
<span class="text-gray">Серверный отдаёт новую страницу на каждый переход. Клиентский меняет URL через History API и рендерит компонент без перезагрузки. SPA требует history fallback на сервере и SSR для SEO.</span>

<b class="text-on-semi-light">Зачем Link вместо обычного a?</b>
<span class="text-gray">`<a>` делает полную перезагрузку. `<Link>` выполняет клиентский переход через History API, сохраняя состояние приложения.</span>

<b class="text-on-semi-light">Что такое вложенные маршруты и Outlet?</b>
<span class="text-gray">Маршруты образуют иерархию: родитель рендерит общий layout, `<Outlet>` - точка вставки дочернего маршрута.</span>

<b class="text-on-semi-light">Зачем loader на уровне роута?</b>
<span class="text-gray">Грузить данные параллельно с навигацией, до рендера, убирая водопад «рендер → fetch». Данные привязаны к маршруту.</span>

<b class="text-on-semi-light">Защищённые маршруты на клиенте - это безопасность?</b>
<span class="text-gray">Нет, только UX. Прячут UI от неавторизованных, но реальную проверку всегда делает сервер.</span>

<b class="text-on-semi-light">Почему фильтры лучше хранить в URL?</b>
<span class="text-gray">URL становится шарабельным и переживает перезагрузку и навигацию назад/вперёд. Это естественный источник истины для такого состояния.</span>
