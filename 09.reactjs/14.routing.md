# Роутинг

Как устроена навигация в одностраничном приложении: History API, сопоставление URL с деревом маршрутов, вложенные макеты, загрузка данных на уровне маршрута, защита страниц и URL как хранилище состояния. Спрашивают, чем `<Link>` отличается от `<a>` и что такое вложенные маршруты. Глубже — почему загрузчики убирают водопады, где проверять доступ и что должен сделать сервер, чтобы SPA не отдавала 404 при перезагрузке.

::tldr
- **В React нет роутинга** — его дают библиотеки и фреймворки. Клиентский роутер меняет URL через History API и рендерит другой компонент без перезагрузки страницы.
- **`pushState` не вызывает `popstate`.** Роутер сам рендерит после своего перехода, а `popstate` ловит только «назад» и «вперёд». Сервер должен отдавать `index.html` на любой путь, иначе перезагрузка страницы даст 404.
- **Маршруты — дерево, URL выбирает в нём ветку.** Родитель рендерит общий макет, а `<Outlet>` — место для дочернего маршрута.
- **Загрузчики маршрутов запускаются до рендера и параллельно** для всей ветки. Это убирает водопады, а после `action` данные перезагружаются сами.
- **Защита маршрута на клиенте — это UX, а не безопасность.** Проверку доступа делает сервер. Фильтры, сортировку и страницу хранят в URL.
::

## Клиентский роутинг

В классическом сайте каждая ссылка — запрос к серверу и новая страница. В SPA приложение загружается один раз, а дальше навигация происходит **на клиенте**: меняется URL, рендерится другой компонент, состояние приложения сохраняется.

У React нет понятия «страница» — это библиотека для интерфейса. Навигацию добавляют библиотеки (React Router, TanStack Router) или фреймворки (Next.js, React Router в режиме фреймворка). Сквозной пример темы — магазин: макет с меню, каталог по категориям, карточка товара, личный кабинет.

### History API

Под капотом любого браузерного роутера — History API:

```js
history.pushState({ page: 'product' }, '', '/product/42');   // новая запись, URL сменился
history.replaceState(null, '', '/catalog?sort=price');        // заменить текущую запись
window.addEventListener('popstate', (e) => render(location.pathname)); // «назад» и «вперёд»
```

Важные детали:

- **`pushState` и `replaceState` не перезагружают страницу и не вызывают `popstate`.** Это событие приходит только при навигации по истории: кнопки «назад» и «вперёд», `history.back()`. Поэтому роутер после своего `pushState` сам обновляет React-состояние, а на `popstate` подписан отдельно.
- **`replaceState` не добавляет запись.** Его используют, когда новое состояние не должно появиться в «назад»: например, при каждом изменении фильтра.
- **Сервер должен знать про SPA.** Пользователь открыл `/product/42` и нажал F5 — браузер запрашивает у сервера `/product/42`, которого на сервере нет. Хостинг настраивают так, чтобы на любой неизвестный путь отдавался `index.html` (history fallback), а дальше маршрут разберёт клиент.

Хеш-роутинг (`/#/product/42`) обходит последнюю проблему — часть после `#` на сервер не уходит, — поэтому встречается в старых приложениях и там, где сервер не настроить. Цена — некрасивые URL и плохая поддержка серверного рендера.

### Link вместо a

```jsx
<Link to="/catalog/tea">Чай</Link>
```

`<Link>` рендерит обычный `<a href>` — ссылку можно открыть в новой вкладке, её видят поисковики и скринридеры. Но при обычном клике `<Link>` отменяет переход браузера и делает клиентский `pushState`. Простой `<a>` на внутреннюю страницу перезагрузит приложение и сбросит всё состояние. `<NavLink>` дополнительно знает, активна ли ссылка, и ставит `aria-current="page"`.

Переход произошёл, URL новый. Теперь роутеру нужно решить, что рендерить.

## Маршруты — это дерево

Маршруты описывают деревом, и URL выбирает в нём ветку:

```jsx
const router = createBrowserRouter([
  {
    path: '/',
    element: <Layout />,                     // шапка и меню на всех страницах
    children: [
      { index: true, element: <Home /> },
      {
        path: 'catalog/:category',
        element: <Category />,               // список товаров категории
        children: [
          { path: ':id', element: <Product /> }, // товар поверх списка
        ],
      },
      { path: '*', element: <NotFound /> },
    ],
  },
]);
```

Для `/catalog/coffee/7` совпадает ветка `Layout → Category → Product`. Каждый родитель рендерит свою часть и `<Outlet />` — место, куда React Router подставит дочерний маршрут:

```jsx
function Layout() {
  return (
    <>
      <nav><NavLink to="/catalog/tea">Чай</NavLink></nav>
      <main><Outlet /></main>
    </>
  );
}
```

Вложенные маршруты — это вложенные макеты. При переходе между товарами одной категории `Layout` и `Category` остаются смонтированными и сохраняют состояние (прокрутку списка, раскрытые фильтры), а меняется только `Product`. Правила, по которым React сохраняет и сбрасывает состояние на одной позиции, — в [Производном состоянии](/content/reactjs/derived-state-and-data-flow).

Данные из URL читают хуками:

```jsx
const { category, id } = useParams();                // сегменты :category и :id
const [searchParams, setSearchParams] = useSearchParams(); // ?sort=price
const navigate = useNavigate();                      // переход из кода
```

Дерево маршрутов определяет, *что* рендерить. Но страницам нужны данные — и самое интересное в современном роутере связано именно с ними.

## Данные на уровне маршрута

Если каждая страница грузит данные в своём компоненте, получается водопад: `Category` загрузилась, отрендерилась, только тогда `Product` начал свою загрузку (подробно о водопадах — в [Загрузке данных](/content/reactjs/data-fetching)). Роутер знает всю ветку маршрутов ещё до рендера, поэтому может запустить загрузку раньше:

```jsx
{
  path: 'catalog/:category',
  element: <Category />,
  loader: ({ params }) => api.category(params.category),
  children: [
    {
      path: ':id',
      element: <Product />,
      loader: ({ params }) => api.product(params.id),
      action: async ({ request }) => api.like(await request.formData()),
    },
  ],
}

function Product() {
  const product = useLoaderData();     // данные уже здесь, без isLoading
  return (
    <article>
      {product.title}
      <Form method="post"><button>♥</button></Form>
    </article>
  );
}
```

- **Загрузчики всей ветки стартуют одновременно** — при переходе, до рендера. В проверке загрузчики категории и товара начались в одну миллисекунду, хотя товар вложен в категорию.
- **Компонент получает готовые данные** через `useLoaderData`. Состояние «загрузки» живёт на уровне навигации: `useNavigation()` говорит, идёт ли переход, и старая страница остаётся на экране, пока новая не готова.
- **`action` обрабатывает отправку формы маршрута**, после чего роутер сам перезапускает загрузчики. В проверке после лайка счётчик обновился без единой строчки инвалидации — данные перезагрузились.
- **Ошибки — тоже на уровне маршрута:** `errorElement` показывает ошибку загрузчика или рендера в месте этого маршрута, а макет остаётся.

Это модель «загрузка → рендер» вместо «рендер → загрузка». Фреймворки идут дальше: в Next.js и React Router в режиме фреймворка загрузчики выполняются на сервере, а данные можно стримить по мере готовности.

### Ленивые маршруты

Маршрут — естественная граница для разделения кода: код страницы нужен, только когда на неё переходят.

```jsx
{ path: 'stats', lazy: () => import('./routes/stats') }   // модуль экспортирует Component, loader
```

В проверке модуль статистики не загружался, пока не было перехода на `/stats`. Свойство `lazy` маршрута лучше, чем `React.lazy` в элементе: роутер загружает код и данные маршрута параллельно, а не код, потом рендер, потом данные.

## Защищённые маршруты

Классический вариант — компонент-обёртка, который проверяет пользователя и перенаправляет:

```jsx
function RequireAuth({ children }) {
  const { user } = useAuth();
  if (!user) return <Navigate to="/login" replace />;
  return children;
}
```

Он работает, но проверка происходит в рендере: страница успевает начать загрузку своих данных и может мелькнуть. С загрузчиками проверку ставят раньше — в загрузчик маршрута:

```jsx
{
  path: 'account',
  loader: async () => {
    const user = await getUser();
    if (!user) throw redirect('/login?next=/account');
    return user;
  },
  element: <Account />,
}
```

Переход на `/account` без входа сразу заканчивается на `/login?next=/account` — страница кабинета не рендерится и её данные не запрашиваются.

Но любая проверка на клиенте — это **удобство, а не безопасность**. Код клиента можно изменить, а API кабинета можно вызвать напрямую. Доступ к данным проверяет сервер на каждом запросе. Клиентская защита лишь не показывает интерфейс, которым пользователь всё равно не смог бы воспользоваться.

> Как устроены сессии и токены — в главе [Безопасность и производительность](/content/security-perfomance/authentication-and-tokens).

## URL как состояние

Фильтры каталога, сортировка, страница, поисковый запрос, открытая вкладка — это состояние, которое пользователь хочет сохранить в ссылке. Если держать его в `useState`, ссылку на «чай, сортировка по цене, страница 3» не отправить, а перезагрузка или «назад» его сбросят.

```jsx
function Filters() {
  const [params, setParams] = useSearchParams();
  const sort = params.get('sort') ?? 'popular';

  return (
    <select
      value={sort}
      onChange={(e) => setParams((p) => { p.set('sort', e.target.value); return p; }, { replace: true })}
    >
      <option value="popular">Популярные</option>
      <option value="price">По цене</option>
    </select>
  );
}
```

URL становится источником истины: компонент не хранит копию, а читает значение из адреса. `replace: true` нужен, чтобы каждое изменение фильтра не добавляло запись в историю — иначе «назад» будет листать фильтры, а не страницы. Какое состояние в URL, а какое нет — в [State management](/content/reactjs/state-management).

### Фокус и прокрутка

Браузер при обычном переходе сбрасывает прокрутку и фокус, а SPA — нет. После клиентского перехода пользователь может оказаться посередине новой страницы, а скринридер не узнает, что страница сменилась. Роутеры решают прокрутку (`<ScrollRestoration />` в React Router), а фокус обычно переводят на заголовок новой страницы (подробно — в [Refs, порталах и доступности](/content/reactjs/refs-portals-a11y)).

## Какой роутер выбрать

| | Что это | Сильная сторона |
| --- | --- | --- |
| React Router | роутер в трёх режимах: декларативный, с загрузчиками, фреймворк (бывший Remix) | стандарт, загрузчики и actions, путь к серверному рендеру |
| TanStack Router | роутер с типами | строго типизированные параметры и search params, встроенный кеш загрузчиков |
| Next.js App Router | роутинг фреймворка по файлам | Server Components, стриминг, загрузка данных на сервере |

Внутри фреймворка отдельная библиотека роутинга не нужна: маршруты задаются файлами, а загрузка данных и рендер на сервере встроены (подробно — в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration)).

## Красные флаги в ответе

- **«`<a>` и `<Link>` — одно и то же».** `<a>` перезагружает приложение и сбрасывает состояние, `<Link>` делает клиентский переход.
- **«Роутер ловит переходы через `popstate`».** `pushState` не вызывает `popstate`. Роутер обновляет состояние сам, а `popstate` — только для «назад» и «вперёд».
- **«SPA работает на любом хостинге без настройки».** Без history fallback перезагрузка на `/product/42` даст 404.
- **«Защищённый маршрут защищает данные».** Он прячет интерфейс. Доступ проверяет сервер на каждом запросе.
- **«Фильтры храню в `useState`».** Ими нельзя поделиться, они теряются при перезагрузке. Их место — в URL.

## Как спрашивают на собеседовании

::question
Чем клиентский роутинг отличается от серверного?

#answer
Серверный отдаёт новую страницу на каждый переход. Клиентский меняет URL через History API и рендерит другой компонент без перезагрузки — состояние приложения сохраняется.

#more
Клиентский роутер вызывает `pushState`, сам рендерит новую ветку маршрутов и подписан на `popstate` для «назад» и «вперёд» — `pushState` этого события не вызывает. Цена: сервер должен отдавать `index.html` на любой путь, роутер должен сам управлять прокруткой и фокусом, а для SEO и первого экрана нужен серверный рендер. Современные фреймворки совмещают оба подхода: первая страница рендерится на сервере, дальше навигация клиентская.
::

::question
Зачем Link вместо обычного a?

#answer
`<a>` перезагружает страницу, и приложение начинает с нуля. `<Link>` делает клиентский переход через History API, состояние сохраняется.

#more
`<Link>` рендерит настоящий `<a href>`, поэтому работают открытие в новой вкладке, копирование ссылки, индексация и доступность. При обычном клике он отменяет действие браузера и вызывает навигацию роутера, а клики с модификаторами (`Ctrl`, `Cmd`) пропускает браузеру. Роутеры с загрузчиками могут предзагружать код и данные страницы при наведении на `<Link>`.
::

::question
Что такое вложенные маршруты и Outlet?

#answer
Маршруты образуют дерево: родитель рендерит общий макет, а `<Outlet>` — место, куда подставляется дочерний маршрут. URL выбирает ветку этого дерева.

#more
Вложенность маршрутов — это вложенность макетов и данных. При переходе внутри ветки родители остаются смонтированными и сохраняют состояние, меняются только дети. У каждого уровня свой загрузчик и свой `errorElement`, поэтому ошибка в товаре не роняет каталог. Загрузчики всей ветки запускаются параллельно.
::

::question
Зачем загрузчики на уровне маршрута?

#answer
Чтобы загружать данные до рендера и параллельно с навигацией, а не после того, как компонент отрисовался. Компонент получает готовые данные через `useLoaderData`.

#more
Роутер знает всю совпавшую ветку до рендера, поэтому запускает загрузчики родителя и детей одновременно — водопад «рендер → загрузка → рендер ребёнка → загрузка» исчезает. Старая страница остаётся на экране, пока новая не готова (`useNavigation` показывает состояние перехода). После `action` роутер перезапускает загрузчики, и данные не нужно инвалидировать вручную. В фреймворках загрузчики выполняются на сервере, рядом с данными.
::

::question
Почему SPA отдаёт 404 при перезагрузке на внутренней странице?

#answer
Браузер запрашивает у сервера путь вроде `/product/42`, а на сервере такого файла нет — есть только `index.html`. Сервер нужно настроить, чтобы на любой неизвестный путь он отдавал `index.html`.

#more
Это history fallback: на неизвестные пути — `index.html` с кодом 200, а маршрут разбирает клиент. При этом настоящие 404 (несуществующий товар) показывает уже клиентский роутер, и для поисковиков это «мягкий 404» — ещё один аргумент за серверный рендер. Хеш-роутинг обходит проблему, потому что часть после `#` не уходит на сервер, но ухудшает URL и SSR.
::

::question
Защищённые маршруты на клиенте — это безопасность?

#answer
Нет. Они прячут интерфейс от пользователя без доступа, но данные защищает только проверка на сервере.

#more
Клиентский код можно изменить, а API вызвать напрямую, поэтому сервер проверяет права на каждом запросе. На клиенте проверку лучше делать в загрузчике маршрута, а не в компоненте: `redirect` случается до рендера, страница не мелькает и не запрашивает свои данные. Компонент-обёртка с `<Navigate>` проверяет уже в рендере.
::

::question
Почему фильтры лучше хранить в URL?

#answer
Ссылкой можно поделиться, состояние переживает перезагрузку и работает с кнопками «назад» и «вперёд». URL становится источником истины для этого состояния.

#more
Компонент читает фильтры из `useSearchParams` и не хранит копию — нет второго источника истины. Изменения фильтров пишут через `replace`, чтобы не засорять историю. Значения из URL — строки от пользователя, их нужно разбирать и проверять. TanStack Router типизирует search params, React Router оставляет это приложению.
::

## Практика

::practice{title="Страница кабинета мелькает"}
Неавторизованный пользователь открывает `/account`: на долю секунды видно кабинет со спиннером, в сети уходит запрос заказов, и только потом происходит переход на вход.

```jsx
{ path: 'account', element: <RequireAuth><Account /></RequireAuth> }

function RequireAuth({ children }) {
  const { data: user, isPending } = useQuery({ queryKey: ['me'], queryFn: api.me });
  if (isPending) return children;            // пока проверяем — показываем страницу
  if (!user) return <Navigate to="/login" replace />;
  return children;
}
```

#solution
Проверка идёт в рендере, и пока запрос `me` не вернулся, рендерится `Account` — со своим спиннером и запросом заказов. Перенаправление случается только после ответа.

Фикс — проверить доступ в загрузчике маршрута, до рендера:

```jsx
{
  path: 'account',
  loader: async ({ request }) => {
    const user = await api.me();
    if (!user) {
      const next = new URL(request.url).pathname;
      throw redirect(`/login?next=${encodeURIComponent(next)}`);
    }
    return user;
  },
  element: <Account />,
}
```

Переход на `/account` без входа сразу заканчивается на `/login?next=/account`: кабинет не рендерится и его данные не запрашиваются. Заказы при этом всё равно защищает сервер — клиентская проверка только убирает лишний экран.
::

::practice{title="Почему «назад» не уходит со страницы?"}
Пользователь подвигал ползунок цены, и теперь кнопка «назад» по одному откатывает значения фильтра, а не уходит на предыдущую страницу:

```jsx
function PriceFilter() {
  const [params, setParams] = useSearchParams();
  return (
    <input
      type="range"
      value={params.get('max') ?? 1000}
      onChange={(e) => setParams({ max: e.target.value })}
    />
  );
}
```

#solution
Каждое изменение ползунка — новая запись в истории: `setParams` по умолчанию делает `pushState`. Ползунок за секунду создаёт десятки записей. Заодно `setParams({ max })` затирает остальные параметры — сортировку и категорию.

Фикс — заменять текущую запись и сохранять остальные параметры:

```jsx
function PriceFilter() {
  const [params, setParams] = useSearchParams();
  return (
    <input
      type="range"
      value={params.get('max') ?? 1000}
      onChange={(e) =>
        setParams((p) => {
          p.set('max', e.target.value);
          return p;
        }, { replace: true })
      }
    />
  );
}
```

Теперь фильтр живёт в URL и переживает перезагрузку, но история содержит только переходы между страницами.
::

::practice{title="Убери водопад"}
Карточка товара открывается через секунду, хотя категория и товар загружаются по 500 мс:

```jsx
function Category() {
  const { category } = useParams();
  const { data } = useQuery({ queryKey: ['category', category], queryFn: () => api.category(category) });
  if (!data) return <Spinner />;
  return <><List items={data.items} /><Outlet /></>;
}

function Product() {
  const { id } = useParams();
  const { data } = useQuery({ queryKey: ['product', id], queryFn: () => api.product(id) });
  if (!data) return <Spinner />;
  return <article>{data.title}</article>;
}
```

#solution
`Product` — дочерний маршрут, он рендерится только внутри `<Outlet>` категории, а `Category` показывает `<Outlet>` после загрузки своих данных. Запрос товара стартует только через 500 мс.

Фикс — загрузчики маршрутов: роутер запустит оба запроса при переходе, параллельно:

```jsx
{
  path: 'catalog/:category',
  element: <Category />,
  loader: ({ params }) => api.category(params.category),
  children: [
    { path: ':id', element: <Product />, loader: ({ params }) => api.product(params.id) },
  ],
}

function Product() {
  const product = useLoaderData();
  return <article>{product.title}</article>;
}
```

В проверке загрузчики категории и товара стартовали одновременно. Если нужен ещё и кеш TanStack Query, загрузчик вызывает `queryClient.ensureQueryData(...)`, а компонент читает тот же ключ — запрос уже в кеше.
::
