# Reconciliation и Fiber

Как React сравнивает новое дерево элементов со старым, какие изменения DOM из этого получаются и как устроен движок, который умеет прерывать рендер. На mid спрашивают эвристики сравнения и разницу render и commit. На senior — как React сопоставляет списки и сколько перемещений DOM даёт перестановка, что такое fiber и lanes, как рендер уступает поток браузеру и в каком порядке выполняются эффекты родителя и детей.

::tldr
- **Reconciliation — сравнение нового дерева элементов со старым.** Точный алгоритм стоил бы O(n³), поэтому React использует эвристики и работает за O(n): другой тип — новое поддерево, тот же тип — обновить props, списки — по `key`.
- **Списки сравниваются в два прохода, а перемещения считаются относительно последнего оставшегося на месте элемента.** Перенос последнего элемента в начало двигает все остальные, перенос первого в конец — один.
- **Fiber — единица работы и узел дерева.** Дерево fiber — связный список (`child`, `sibling`, `return`), который React обходит циклом и может остановить между узлами. Две версии дерева — `current` и `workInProgress`.
- **Render можно прервать, commit — нет.** В transition React работает квантами около 5 мс и уступает поток. Приоритеты задают lanes — биты в маске.
- **Эффекты выполняются от детей к родителю**, при размонтировании cleanup идёт от родителя к детям. Refs присоединяются до layout-эффектов.
::

---

## Задача: превратить дерево в изменения DOM

После `setState` React вызывает компоненты и получает новое дерево элементов. Старое дерево он помнит — оно отрисовано на экране. Задача reconciliation: найти минимальный набор изменений DOM, который превращает старое в новое.

Сквозной пример — список задач, которые можно перетаскивать, с режимом редактирования:

```jsx
function Board({ tasks, editing }) {
  return (
    <ul>
      {tasks.map((t) => (
        <li key={t.id}>
          {editing ? <input defaultValue={t.title} /> : <span>{t.title}</span>}
        </li>
      ))}
    </ul>
  );
}
```

Точное решение такой задачи для произвольных деревьев — минимальное редактирование дерева — стоит O(n³). Для тысячи элементов это миллиард операций на каждое обновление. Поэтому React решает задачу не точно, а эвристически.

> Что такое рендер и commit и чем элемент отличается от DOM-узла — во [Введении в React](/content/reactjs/introduction).

## Эвристики сравнения

React делает два допущения, которые почти всегда верны для реальных интерфейсов:

1. **Элементы разных типов дают разные деревья.** Если на месте `<span>` стал `<input>` или `Profile` сменился на `Feed`, React не ищет сходство внутри. Он удаляет старое поддерево со всем DOM и состоянием и создаёт новое.
2. **Ключ задаёт идентичность среди соседей.** В списке React сопоставляет элементы по `key`, а без ключа — по позиции.

Остальное просто: **тот же тип на той же позиции** — React переиспользует узел и обновляет только изменившиеся props. Для DOM-элемента это изменённые атрибуты, для компонента — новый вызов с новыми props.

В сквозном примере переключение `editing` меняет `<span>` на `<input>`: разные типы, поэтому каждая строка пересоздаёт свой узел. С `<input>` на `<input>` при смене `defaultValue` узел остался бы тем же.

Сравнение идёт **по уровням**: React не ищет, не переехал ли узел на другой уровень дерева. Если обернуть список в новый `<div>`, всё под ним будет создано заново.

> Как эти правила проявляются в состоянии компонентов — тернарник с одинаковым типом, компонент внутри компонента, сброс через `key` — в [Производном состоянии](/content/reactjs/derived-state-and-data-flow) и [Компонентах и JSX](/content/reactjs/components-and-jsx).

Правило для одного узла простое. Самое интересное — что происходит, когда меняется порядок в списке.

## Как сравниваются списки

У списка детей нет «позиции» в строгом смысле: элементы могут вставляться, удаляться и меняться местами. React сравнивает массив новых детей со старым в два прохода:

1. **Первый проход — по порядку.** React идёт по новому и старому спискам одновременно, пока ключи совпадают. Это быстрый путь для самого частого случая: элементы дописали в конец или изменили на месте.
2. **Второй проход — по ключам.** На первом несовпадении оставшиеся старые элементы складываются в `Map` по ключу. Для каждого нового элемента React ищет старый с тем же ключом. Нашёл — переиспользует, не нашёл — создаёт. Всё, что осталось в `Map`, удаляется.

Самое неочевидное — как React решает, какие из найденных элементов **переместить** в DOM. Он запоминает индекс последнего элемента, который остался на месте (`lastPlacedIndex`). Если старый индекс очередного элемента меньше этого значения, элемент «уехал левее», и его нужно переместить. Иначе он остаётся, а `lastPlacedIndex` сдвигается.

Проверим на списке `A B C D E`:

| Перестановка | Что React переместил в DOM |
| --- | --- |
| `E` в начало: `E A B C D` | `A`, `B`, `C`, `D` — четыре перемещения |
| `A` в конец: `B C D E A` | `A` — одно перемещение |
| обмен `B` и `D`: `A D C B E` | `C`, `B` — два перемещения |

В первом случае `E` (старый индекс 4) стал первым и «остался на месте», `lastPlacedIndex = 4`. Все следующие элементы имеют меньший старый индекс, и каждый перемещается. Во втором случае `B`, `C`, `D`, `E` идут по возрастанию старых индексов, двигается только `A`.

DOM-узлы во всех случаях те же — React их переставляет, а не пересоздаёт, и состояние строк сохраняется. Но число операций разное. Vue 3 для той же задачи ищет наибольшую возрастающую подпоследовательность и при переносе `E` в начало двигает один узел. React выбрал более простой алгоритм: перенос элемента из конца в начало встречается реже, чем дописывание.

### Почему ключ решает всё

Без ключей второй проход сопоставляет по индексу. Вставка в начало тогда выглядит как «у всех строк поменялся текст, и в конце появилась новая». DOM-узлы и состояние остаются на своих позициях, а данные сдвигаются — отсюда баг с индексом в ключе. С ключами вставка в начало — это одна новая строка и ноль изменений в остальных.

> Почему индекс в ключе ломает состояние и как ключ сбрасывает компонент — в [Компонентах и JSX](/content/reactjs/components-and-jsx).

Алгоритм сравнения описан. Но где React хранит старое дерево и почему он может бросить сравнение на полпути?

## Fiber: дерево как связный список

До React 16 сравнение было рекурсивным: React заходил в компонент, потом в его детей и не мог остановиться, пока не обойдёт всё дерево. Большое обновление блокировало поток на десятки миллисекунд, и ввод в это время не обрабатывался.

Fiber — переписанный движок, где каждый узел дерева стал отдельной **единицей работы**. Fiber — объект на каждый компонент и DOM-элемент:

```text
Fiber {
  type, key            // что это: функция компонента, 'li', 'div'
  stateNode            // DOM-узел или экземпляр класса
  child, sibling, return  // первый ребёнок, следующий сосед, родитель
  pendingProps, memoizedProps
  memoizedState        // у функционального компонента — список хуков
  flags                // что сделать в commit: вставить, обновить, удалить
  lanes                // какие апдейты ждут в этом узле
  alternate            // вторая версия этого же узла
}
```

Ссылки `child`, `sibling` и `return` превращают дерево в связный список, по которому можно идти циклом, а не рекурсией. Цикл можно остановить на любом узле и продолжить позже — состояние обхода хранится в указателе на текущий fiber, а не в стеке вызовов.

### Две версии дерева

React держит две версии каждого fiber, связанные через `alternate`:

- **`current`** — то, что сейчас на экране;
- **`workInProgress`** — то, что строится в текущем рендере.

Рендер пишет только в `workInProgress`. Если рендер прервали или выбросили, `current` не тронут, и пользователь видит старый целый интерфейс. В конце commit корень просто переключает указатель: `workInProgress` становится `current`. Этот приём называют двойной буферизацией, как в графике.

Отсюда же объяснение «лишнего» вызова компонента при том же значении состояния: у двух версий fiber свои пометки об апдейтах (подробно — в [Механике хуков](/content/reactjs/hooks-mechanics)).

### Цикл работы

Рендер — это цикл по fiber:

1. **`beginWork`** для узла: вызвать компонент (или взять props DOM-элемента), сравнить детей со старыми и создать fiber для новых. Если props и состояние не изменились и контекст тоже, React делает **bailout**: пропускает компонент и, если в поддереве нет работы, всё поддерево.
2. Перейти к `child`. Если детей нет — **`completeWork`**: для DOM-элемента подготовить узел и список изменённых атрибутов. Потом к `sibling`, а если соседей нет — вверх по `return`.

Bailout объясняет, почему элемент из `children` не рендерится при рендере родителя: React видит тот же объект props и пропускает узел. `memo` расширяет то же правило до поверхностного сравнения props (подробно — в [Производительности](/content/reactjs/performance)).

Цикл можно прервать между узлами. Остался вопрос: кто и когда решает, что пора прерываться?

## Прерываемый рендер и lanes

### Кванты времени

В срочном рендере (клик, ввод) React обходит дерево до конца без остановок. В несрочном — внутри `startTransition`, при `useDeferredValue` — после каждого fiber проверяет, не вышло ли время. Квант в планировщике React — 5 мс. Когда время вышло, React уступает поток: браузер обрабатывает события, рисует кадр, а рендер продолжается в следующей задаче.

Проверка: 40 компонентов по 2 мс каждый. В синхронном рендере таймер с нулевой задержкой выполнился только после всех 40. В transition — уже после третьего: React порезал работу на кусочки.

Это не параллельность — JavaScript по-прежнему один поток. Рендер просто разбит на шаги, между которыми может выполниться другая работа.

### Lanes

Приоритеты в React — **lanes**: каждый тип обновления занимает бит в 31-битной маске. Дискретные события вроде клика и ввода — синхронная lane, непрерывные (прокрутка, движение мыши) — своя, обычные обновления — default, transitions — несколько отдельных lanes, фоновая работа — idle.

Маска позволяет дёшево работать с группами: «есть ли в этом поддереве срочная работа» — одна побитовая операция по полю `lanes` всех fiber на пути. Когда приходит обновление с более высоким приоритетом, React бросает незаконченный рендер с низким, выполняет срочный и потом начинает низкий заново — с перепроигрыванием очереди апдейтов, как в примере `1 → 10 → 20` из [Механики хуков](/content/reactjs/hooks-mechanics).

> Как этим пользоваться — `useTransition`, `useDeferredValue` и чем они отличаются от debounce — в [Производительности](/content/reactjs/performance).

### Suspense — тоже прерывание

Если компонент во время рендера ждёт данные (`use(promise)` или ленивый компонент), он **приостанавливается**. React показывает ближайший `<Suspense fallback>` и продолжит рендер этого поддерева, когда промис разрешится. Состояние поддерева, которое приостановилось при первом монтировании, не сохраняется: при повторе оно рендерится с нуля. Как это используют для загрузки данных — в [Загрузке данных](/content/reactjs/data-fetching).

Рендер закончился, `workInProgress` готов. Дальше — commit, и его прервать уже нельзя.

## Commit и порядок эффектов

Commit синхронный: изменения DOM должны появиться разом, иначе пользователь увидит наполовину обновлённый интерфейс. Он проходит этапы:

```text
1. before mutation  — getSnapshotBeforeUpdate у классов (прочитать DOM до изменений)
2. mutation         — изменения DOM, useInsertionEffect, cleanup layout-эффектов, отсоединение refs
3. layout           — присоединение refs, useLayoutEffect, componentDidMount/DidUpdate
   ── браузер рисует кадр ──
4. passive          — cleanup и setup useEffect
```

Порядок внутри этапа идёт **от детей к родителю**: обход дерева заканчивает работу с ребёнком раньше, чем с родителем. Проверка для `P` с детьми `A` и `B`:

```text
монтирование:   render P, render A, render B,
                layout A, layout B, layout P,
                effect A, effect B, effect P

обновление:     render P, render A, render B,
                layout cleanup A, B, P → layout A, B, P,
                effect cleanup A, B, P → effect A, B, P

размонтирование: layout cleanup P, A, B → effect cleanup P, A, B
```

Рендер идёт сверху вниз, эффекты — снизу вверх. Поэтому в эффекте родителя DOM и эффекты детей уже готовы: родитель может измерить детей или вызвать их императивный API. При размонтировании cleanup идёт сверху вниз: родитель убирает свои подписки раньше детей.

Refs присоединяются в этапе layout до layout-эффектов, поэтому в `useLayoutEffect` ref уже содержит узел (подробно — в [Refs и порталах](/content/reactjs/refs-portals-a11y)). Чем `useLayoutEffect` отличается от `useEffect` с точки зрения пользователя — в [Эффектах](/content/reactjs/effects-and-synchronization).

## Красные флаги в ответе

- **«React сравнивает DOM с Virtual DOM».** Сравниваются два дерева элементов (fiber), реальный DOM в сравнении не участвует.
- **«React находит минимальный набор изменений».** Он находит достаточно хороший за O(n) по эвристикам. Перенос последнего элемента в начало двигает все остальные.
- **«Fiber — это потоки, React рендерит параллельно».** Поток один. Fiber позволяет разбить рендер на кусочки и прерывать его между узлами.
- **«Commit тоже можно прервать».** Нет — иначе пользователь увидел бы наполовину изменённый DOM.
- **«Эффекты выполняются сверху вниз, как рендер».** Эффекты идут от детей к родителю, cleanup при размонтировании — от родителя к детям.

## Как спрашивают на собеседовании

::question{level="mid"}
Что такое reconciliation?

#mid
Сравнение нового дерева элементов со старым, чтобы найти, какие изменения внести в DOM. React использует эвристики: другой тип — пересоздать поддерево, тот же тип — обновить props, списки — сопоставить по ключам.

#senior
Точное минимальное редактирование дерева стоит O(n³), эвристики дают O(n). Цена — неоптимальность в редких случаях: React не замечает переезд узла на другой уровень и пересоздаёт поддерево при смене типа, даже если внутри всё то же самое. В списках перемещения считаются относительно последнего оставшегося на месте элемента, поэтому перенос элемента из конца в начало двигает все остальные узлы.
::

::question{level="senior"}
Как React сравнивает списки детей?

#mid
По ключам. Элементы с тем же ключом React переиспользует вместе с DOM и состоянием, новые создаёт, исчезнувшие удаляет. Без ключей сравнение идёт по позиции.

#senior
Два прохода. Первый идёт по порядку, пока ключи совпадают, — быстрый путь для дописывания в конец. Второй складывает оставшиеся старые элементы в `Map` по ключу и ищет каждый новый элемент там. Перемещение определяется через `lastPlacedIndex`: элемент со старым индексом меньше индекса последнего оставшегося на месте переставляется. Поэтому `A B C D E → E A B C D` даёт четыре перемещения DOM, а `→ B C D E A` — одно. Vue 3 ищет наибольшую возрастающую подпоследовательность и двигает минимум.
::

::question{level="mid"}
Что такое Fiber и зачем он понадобился?

#mid
Движок React с версии 16. Он разбивает рендер на единицы работы — fiber-узлы, — которые можно выполнять с паузами. Это позволило прерывать и приоритизировать рендер — основа concurrent-возможностей.

#senior
Старый рекурсивный алгоритм не мог остановиться до конца дерева. Fiber хранит дерево как связный список (`child`, `sibling`, `return`) и обходит его циклом, так что состояние обхода — указатель на текущий узел, а не стек вызовов. У каждого узла две версии (`current` и `workInProgress` через `alternate`): рендер пишет в незавершённую версию, и прерванная работа не видна. Fiber хранит и состояние хуков, и пометки о работе (`flags`, `lanes`).
::

::question{level="mid"}
Чем render-фаза отличается от commit-фазы?

#mid
Render вызывает компоненты и вычисляет изменения, DOM не трогает, его можно прервать или повторить. Commit применяет изменения к DOM синхронно, без перерывов, и запускает эффекты.

#senior
Render чистый, поэтому React может выбросить его результат — при прерывании срочным апдейтом, при приостановке Suspense, в StrictMode. Commit состоит из этапов: before mutation (`getSnapshotBeforeUpdate`), mutation (DOM, insertion-эффекты, cleanup layout-эффектов), layout (refs, `useLayoutEffect`, `componentDidMount`), затем браузер рисует, и только потом passive-эффекты (`useEffect`).
::

::question{level="senior"}
Как React прерывает рендер? Что такое lanes?

#mid
В несрочных обновлениях (transitions) React после каждого компонента проверяет, не пора ли уступить поток браузеру. Если пришло срочное обновление, текущий рендер бросается и начинается заново позже.

#senior
Планировщик даёт рендеру квант около 5 мс, после него React уступает поток и продолжает в следующей задаче. Срочные обновления рендерятся без пауз. Приоритеты кодируются lanes — битами в маске, поэтому проверки вроде «есть ли в поддереве срочная работа» — одна побитовая операция. Прерванный низкоприоритетный рендер начинается заново, а очередь апдейтов перепроигрывается от `baseState`. Это не многопоточность: поток один, работа просто нарезана.
::

::question{level="senior"}
В каком порядке выполняются эффекты родителя и детей?

#mid
Сначала эффекты детей, потом родителя. Рендер идёт сверху вниз, а эффекты — снизу вверх.

#senior
В commit обход заканчивает работу с ребёнком раньше, чем с родителем, поэтому и layout-эффекты, и `useEffect` идут от детей к родителю: в эффекте родителя DOM детей и их эффекты уже готовы. Все layout-эффекты выполняются до всех passive. При размонтировании cleanup идёт от родителя к детям. Refs присоединяются до layout-эффектов, поэтому в `useLayoutEffect` родителя ref на DOM ребёнка уже заполнен.
::

::question{level="mid"}
Что такое двойная буферизация в React?

#mid
React держит две версии дерева: `current` — на экране, и `workInProgress` — строится сейчас. В конце commit они меняются местами.

#senior
Рендер пишет только в `workInProgress`, поэтому прерванный или выброшенный рендер не портит отображаемое дерево. Версии связаны через `alternate` и переиспользуются между рендерами, чтобы не создавать fiber заново. Переключение — смена одного указателя у корня. У двух версий свои пометки об апдейтах, и это объясняет редкие «лишние» вызовы компонента при том же значении состояния.
::

## Практика

::practice{title="Сколько DOM-операций?"}
Список из пяти задач с ключами. Пользователь перетаскивает последнюю задачу наверх. Сколько DOM-узлов React переместит? А если перетащить первую вниз?

```jsx
function Board({ tasks }) {
  return <ul>{tasks.map((t) => <li key={t.id}>{t.title}</li>)}</ul>;
}

// было:  A B C D E
// стало: E A B C D   (последнюю наверх)
// стало: B C D E A   (первую вниз)
```

#solution
Последнюю наверх — четыре перемещения (`A`, `B`, `C`, `D`), первую вниз — одно (`A`).

React идёт по новому списку и запоминает старый индекс последнего элемента, оставшегося на месте. `E` (старый индекс 4) встаёт первым и остаётся на месте, `lastPlacedIndex = 4`. У `A`, `B`, `C`, `D` старые индексы меньше 4 — каждый перемещается. Во втором случае `B`, `C`, `D`, `E` идут с возрастающими старыми индексами, а двигается только `A`.

Проверить это можно `MutationObserver` на списке — каждое перемещение видно как повторная вставка узла:

```js
const moved = [];
new MutationObserver((records) => {
  for (const r of records) r.addedNodes.forEach((n) => moved.push(n.textContent));
}).observe(ul, { childList: true });
// после перестановки E A B C D: moved = ['A', 'B', 'C', 'D']
```

Все узлы при этом переиспользуются, ничего не пересоздаётся. Для пяти строк разница не важна. Для длинного списка с тяжёлыми строками (видео, iframe — перемещение может их перезагрузить) стоит знать, что React двигает элементы, «уехавшие влево».
::

::practice{title="В каком порядке логи?"}
```jsx
function Child({ name }) {
  useEffect(() => {
    console.log('effect', name);
    return () => console.log('cleanup', name);
  }, []);
  return null;
}

function Parent() {
  useEffect(() => {
    console.log('effect Parent');
    return () => console.log('cleanup Parent');
  }, []);
  return <><Child name="A" /><Child name="B" /></>;
}

// root.render(<Parent />), затем root.unmount()
```

#solution
```text
effect A
effect B
effect Parent
cleanup Parent
cleanup A
cleanup B
```

При монтировании эффекты идут от детей к родителю: обход в commit заканчивает работу с ребёнком раньше, чем с родителем. При размонтировании cleanup идёт от родителя к детям.

Практическое следствие: в эффекте родителя можно полагаться на то, что дети уже смонтированы и их эффекты отработали — например, подписки детей уже на месте, а их refs заполнены.
::

::practice{title="Почему тормозит ввод?"}
При вводе в поиск фильтруется список из 5000 строк, и поле заметно подтормаживает:

```jsx
function Search({ items }) {
  const [query, setQuery] = useState('');
  const visible = items.filter((i) => i.title.includes(query));

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <List items={visible} />
    </>
  );
}
```

#solution
Каждая буква — синхронный рендер всего списка. Срочный рендер React не прерывает, поэтому пока список не отрисован, браузер не обработает следующую букву и не обновит поле.

Ввод должен остаться срочным, а список можно сделать несрочным. Тогда React отрисует поле сразу, а список — квантами по 5 мс, прерывая работу, если пришла новая буква:

```jsx
function Search({ items }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const visible = useMemo(
    () => items.filter((i) => i.title.includes(deferredQuery)),
    [items, deferredQuery],
  );

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <List items={visible} />
    </>
  );
}
```

`List` нужно обернуть в `memo`, иначе срочный рендер с новым `query` всё равно отрендерит его со старыми данными. Подробно про `useDeferredValue`, `useTransition` и виртуализацию длинных списков — в [Производительности](/content/reactjs/performance).
::
