# Согласование и Fiber

Это глава «под капотом». Здесь живёт самый важный senior-вопрос - **«почему компонент перерисовался?»** - и понимание того, как React превращает твой JSX в точечные изменения DOM, не перерисовывая всё подряд.

---

## Render и commit

Каждое обновление проходит две фазы:

1. **Render-фаза** - React вызывает компоненты, строит новое дерево элементов и вычисляет разницу. Чистая, **может быть прервана** или повторена. DOM ещё не трогается.
2. **Commit-фаза** - React применяет вычисленные изменения к реальному DOM. Синхронная, **непрерываемая**. После неё запускаются `useLayoutEffect`, затем браузер рисует, затем `useEffect`.

> «Рендер» в React ≠ «отрисовка в браузере». Рендер - это вызов компонентов и diffing. Браузерный paint происходит уже после commit.

---

## Reconciliation (согласование)

При изменении состояния React строит новое виртуальное дерево и сравнивает его со старым - это **reconciliation**. Точный diff двух деревьев стоил бы O(n³), поэтому React использует **эвристики** и получает O(n):

1. **Разный тип элемента → выбрасываем поддерево.** Если на месте `<div>` стал `<span>` (или `Profile` сменился на `Feed`), React не пытается переиспользовать - он уничтожает старый узел со всем состоянием и строит новый.
2. **Одинаковый тип → переиспользуем узел, обновляем пропсы.** `<div className="a">` → `<div className="b">` - тот же DOM-узел, меняется только атрибут.
3. **Списки сопоставляются по `key`.** Без ключей React сравнивает по позиции; с ключами - понимает перестановки, вставки и удаления (см. [компоненты и JSX](/content/reactjs/components-and-jsx)).

```jsx
// Смена типа уничтожает состояние внутри
{isEditing ? <input defaultValue={text} /> : <textarea defaultValue={text} />}
// input и textarea - разные типы: при переключении состояние теряется
```

<b class="text-on-semi-light">Следствие про идентичность</b> - <span class="text-gray">React определяет «тот же это компонент или новый» по **позиции в дереве и типу**, а не по содержимому. Поэтому условный рендер разных типов в одной позиции сбрасывает состояние, а `key` позволяет этим управлять.</span>

## Архитектура Fiber

**Fiber** - это внутренний движок React (с версии 16), переписанный ради **прерываемого рендеринга**. Старый рекурсивный reconciler шёл по дереву синхронно и не мог остановиться - длинный рендер блокировал поток и подвешивал интерфейс.

Fiber разбивает работу на **единицы** и выполняет их в цикле, который может приостанавливаться.

- **Fiber-узел** - объект на каждый компонент/элемент. Хранит тип, props, состояние (хуки!), ссылки на родителя/детей/соседа и **указатель работы**.
- Дерево фиберов - это связный список (child/sibling/return), по которому React идёт итеративно, а не рекурсией.

```
Fiber {
  type, key,
  stateNode,        // DOM-узел или инстанс
  child, sibling, return,  // навигация по дереву
  memoizedState,    // хуки компонента
  pendingProps, memoizedProps,
  flags,            // что сделать в commit (Placement, Update, Deletion)
  lane              // приоритет
}
```

### Прерываемость и приоритеты

В render-фазе React обрабатывает фиберы по одному и **проверяет, не пора ли уступить** браузеру (например, для обработки ввода). Если пришла более срочная работа - текущий рендер можно отбросить и начать заново. Это и есть фундамент **конкурентного рендеринга** (`useTransition`, `useDeferredValue` из [продвинутых хуков](/content/reactjs/advanced-hooks)).

Приоритеты выражены через **lanes** - битовые «дорожки», по которым React понимает, какие обновления срочные (ввод), а какие можно отложить (переходы, фоновые данные).

### Double buffering

React держит **два дерева**: `current` (то, что на экране) и `workInProgress` (то, что строится). Новые изменения собираются в `workInProgress`, и при commit два дерева **меняются местами** одним переключением указателя - как двойная буферизация в графике. Поэтому незавершённый прерванный рендер не виден пользователю.

## Почему компонент перерисовался

Главный практический вывод главы. Компонент рендерится заново, если выполнено хотя бы одно:

1. **Изменилось его состояние** (`setState`/`dispatch`).
2. **Перерисовался его родитель** - по умолчанию ререндер родителя рендерит **всех** детей, даже если их props не менялись.
3. **Изменился контекст**, который компонент читает.
4. **Сменился `key`** - тогда это не ререндер, а полное пересоздание.

<b class="text-on-semi-light">Частое заблуждение</b> - <span class="text-gray">«Ребёнок перерисовался, потому что изменились его props». Нет. По умолчанию ребёнок рендерится из-за рендера **родителя**, независимо от props. Чтобы пропускать ререндер при неизменных props, нужен `React.memo` - см. [производительность](/content/reactjs/performance).</span>

> Ререндер сам по себе не «дорогой» и не значит изменение DOM. React всё равно сделает diff и тронет DOM, только если что-то реально изменилось. Бороться стоит не с каждым рендером, а с теми, что заметно тормозят.

## Ловушка: компонент, определённый в рендере

Тонкий, но частый баг. Если объявить компонент **внутри** другого компонента, при каждом рендере родителя это **новая функция-тип**:

```jsx
function Parent() {
  function Child() { return <input />; } // ❌ новый тип на каждом рендере Parent
  return <Child />;
}
```

<b class="text-on-semi-light">Что происходит</b> - <span class="text-gray">React сравнивает по **типу**; новая функция `Child` каждый рендер - «другой тип», поэтому React **размонтирует и пересоздаёт** поддерево: теряется состояние (`input` обнуляется), фокус, заново идут эффекты. Правило: объявляй компоненты **на верхнем уровне модуля**, а не внутри других компонентов.</span>

## Фазы commit

Commit-фаза, хоть и синхронная, делится на под-фазы - это объясняет тайминг эффектов и refs:

```
1. Before mutation — снимок (getSnapshotBeforeUpdate)
2. Mutation        — изменения в DOM, отвязка старых refs
3. Layout          — привязка новых refs, useLayoutEffect (DOM готов, ДО paint)
   ↓ браузер рисует (paint)
4. Passive         — useEffect (ПОСЛЕ paint, асинхронно)
```

<b class="text-on-semi-light">Почему важно</b> - <span class="text-gray">`useLayoutEffect` видит обновлённый DOM до отрисовки - можно измерить и поправить layout без «прыжка»; `useEffect` срабатывает после paint и не блокирует отрисовку. Refs устанавливаются в layout-фазе, поэтому в `useLayoutEffect` ref уже актуален. Это и есть тайминг из [главы про эффекты](/content/reactjs/effects-and-synchronization).</span>

## Батчинг

React группирует несколько обновлений состояния в **один** проход render+commit - это батчинг. С React 18 он автоматический во всех контекстах (события, промисы, таймеры). Подробнее - в [состоянии и событиях](/content/reactjs/state-and-events).

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое reconciliation?</b>
<span class="text-gray">Процесс сравнения нового виртуального дерева со старым и вычисления минимальных изменений DOM. Использует эвристики (тип, ключи) ради O(n) вместо O(n³).</span>

<b class="text-on-semi-light">Что происходит, если у элемента меняется тип?</b>
<span class="text-gray">React уничтожает старое поддерево вместе с состоянием и строит новое - переиспользования не происходит.</span>

<b class="text-on-semi-light">Что такое Fiber и зачем он понадобился?</b>
<span class="text-gray">Переписанный движок React, который разбивает рендер на прерываемые единицы работы. Это позволило приоритизировать и откладывать обновления - основа конкурентного рендеринга.</span>

<b class="text-on-semi-light">Чем render-фаза отличается от commit-фазы?</b>
<span class="text-gray">Render - вызов компонентов и diffing, может прерываться, DOM не трогается. Commit - синхронное применение изменений к DOM, прервать нельзя.</span>

<b class="text-on-semi-light">Почему перерисовался дочерний компонент?</b>
<span class="text-gray">Изменилось его state, перерисовался родитель, изменился используемый контекст, или сменился key. Рендер родителя по умолчанию рендерит всех детей.</span>

<b class="text-on-semi-light">Что такое double buffering в React?</b>
<span class="text-gray">Два дерева фиберов - current и workInProgress. Изменения строятся в workInProgress и атомарно становятся current при commit, поэтому незавершённый рендер не виден.</span>
