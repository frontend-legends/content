# Управление состоянием

Какое состояние бывает в приложении, когда нужен стор и как он вообще подключается к React. На mid спрашивают, как выбрать стейт-менеджер и чем стор отличается от контекста. На senior — как стор живёт вне React, что такое tearing, зачем `useSyncExternalStore` и почему селектор, который возвращает новый объект, зацикливает рендер.

::tldr
- **Состояние бывает разным:** локальное, серверное, глобальное клиентское, состояние URL и формы. Большая часть «глобального состояния» — это серверные данные, и им нужен кеш, а не стор.
- **Стор живёт вне React** и даёт три вещи: прочитать состояние, изменить его и подписаться на изменения. Компонент подписывается на срез через селектор и рендерится, только когда срез изменился.
- **`useSyncExternalStore` — мост между внешним стором и React.** Он подписывает компонент и защищает от tearing — ситуации, когда при прерываемом рендере части экрана показывают разные версии данных.
- **Снимок и результат селектора должны быть стабильными.** Новый объект на каждый вызов — это «значение изменилось» на каждом рендере и бесконечный цикл.
- **Начинай с `useState`, поднимай выше по необходимости.** Redux Toolkit, Zustand и Jotai — ответ на большое и часто меняющееся клиентское состояние, а не выбор по умолчанию.
::

---

## Какое бывает состояние

Вопрос «какой стейт-менеджер взять?» на собеседовании проверяет, видишь ли ты, что состояние бывает разным и требует разных инструментов. Сквозной пример — интернет-магазин:

| Тип | Пример в магазине | Чем управлять |
| --- | --- | --- |
| Локальное UI-состояние | открыт ли дропдаун, активная вкладка | `useState`, `useReducer` |
| Серверное | каталог, профиль, заказы | кеш запросов: TanStack Query, SWR, загрузчики фреймворка |
| Глобальное клиентское | корзина до оформления, тема, черновик | контекст или стор |
| Состояние URL | фильтры, страница, поисковый запрос | роутер, query-параметры |
| Состояние формы | значения полей, ошибки валидации | форма, `FormData`, react-hook-form |

Главная ошибка — держать серверные данные в глобальном сторе вручную: флаги `loading`, `error`, `data`, перезапрос при фокусе, инвалидация после мутаций. Это заново написанный кеш. Серверные данные асинхронны, устаревают и принадлежат серверу, поэтому ими управляет библиотека загрузки (подробно — в [Загрузке данных](/content/reactjs/data-fetching)). Фильтры каталога — в URL, чтобы ссылкой можно было поделиться (подробно — в [Роутинге](/content/reactjs/routing)).

Когда серверное состояние и URL вынесены в свои инструменты, глобального клиентского состояния часто остаётся совсем немного: корзина, тема, пользователь. Для него и выбирают между контекстом и стором.

## Лестница решений

Сложность поднимают по мере необходимости:

1. **`useState` и `useReducer`** — состояние одного компонента.
2. **Поднять состояние** в общего родителя — общее для нескольких компонентов (подробно — в [Производном состоянии](/content/reactjs/derived-state-and-data-flow)).
3. **Контекст** — значение, которое нужно многим на разной глубине и меняется редко: тема, язык, пользователь.
4. **Стор с селекторами** — состояние большое, меняется часто, и разным компонентам нужны разные его части.

Почему контекста становится мало: он рендерит всех потребителей при любом изменении значения и не умеет подписку на часть (подробно — в [Context API](/content/reactjs/context-api)). Корзина в контексте означает, что добавление товара перерисует и шапку, и промо-блок, и всех, кто читает корзину. Нужно, чтобы шапка, которой нужно только количество товаров, рендерилась при изменении количества и больше никогда. Для этого состояние уносят из React.

## Стор вне React

Стор — обычный объект в модуле, который живёт вне дерева компонентов. Ядро любого стора умещается в несколько строк:

```js
function createStore(initial) {
  let state = initial;
  const listeners = new Set();

  return {
    getState: () => state,
    setState: (fn) => {
      state = { ...state, ...fn(state) };   // новый объект — новая ссылка
      listeners.forEach((l) => l());
    },
    subscribe: (listener) => {
      listeners.add(listener);
      return () => listeners.delete(listener);
    },
  };
}

const cart = createStore({ items: [], promo: '' });
```

Чтобы компонент показывал данные стора, React должен уметь три вещи: прочитать текущее значение, узнать об изменении и решить, нужно ли рендерить компонент. Наивное решение — подписка в эффекте и `useState`:

```jsx
function useStoreNaive(store, selector) {
  const [value, setValue] = useState(() => selector(store.getState()));
  useEffect(() => store.subscribe(() => setValue(selector(store.getState()))), [store]);
  return value;
}
```

Это работает, пока рендер синхронный. Но React умеет прерывать рендер, и тут наивная подписка ломается.

### Tearing

В несрочном рендере (transition) React работает кусками и между ними отдаёт поток браузеру (подробно — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber)). Если в паузе внешний стор изменился, компоненты, отрендеренные до паузы, прочитали старое значение, а после паузы — новое. В commit попадает интерфейс, разорванный между двумя версиями данных. Это и есть **tearing**.

Проверка: 30 компонентов читают число из стора во время transition-рендера, а через 10 мс стор меняется с `0` на `1`. При прямом чтении на экране оказались и `0`, и `1` одновременно. У React-состояния такой проблемы нет: React сам управляет его версиями. Проблема только у данных вне React.

## useSyncExternalStore

`useSyncExternalStore` — встроенный хук, который правильно подключает внешний стор к React:

```jsx
function useStore(store, selector) {
  return useSyncExternalStore(
    store.subscribe,                       // как подписаться
    () => selector(store.getState()),      // снимок для клиента
    () => selector(store.getState()),      // снимок для сервера
  );
}

function CartCount() {
  const count = useStore(cart, (s) => s.items.length);
  return <b>{count}</b>;
}
```

Что он делает:

- **Подписывается и отписывается** вместе с жизнью компонента. Эффект руками писать не нужно.
- **Рендерит компонент только при изменении снимка.** После каждого уведомления стора React вызывает `getSnapshot` и сравнивает результат с прошлым через `Object.is`. Не изменился — рендера нет. В проверке шапка с количеством отрендерилась при добавлении товаров, но не при смене промокода, а промо-блок — наоборот.
- **Защищает от tearing.** Если стор изменился во время прерываемого рендера, React замечает несовпадение снимков и перерендеривает синхронно, без пауз. В той же проверке с `useSyncExternalStore` на экране было только `1`. Цена — в этот момент рендер перестаёт быть прерываемым.
- **Поддерживает серверный рендер** через третий аргумент. Без него `renderToString` бросит `Missing getServerSnapshot`. Серверный снимок должен совпадать с первым клиентским, иначе гидратация разойдётся.

### Снимок должен быть стабильным

`getSnapshot` вызывается часто, и React сравнивает результаты по ссылке. Если он каждый раз возвращает новый объект, React считает, что данные изменились, перерендеривает, снова получает новый объект — и так до ошибки:

```jsx
// ❌ новый объект на каждый вызов
useSyncExternalStore(store.subscribe, () => ({ a: store.getState().a, b: store.getState().b }));
```

```text
The result of getSnapshot should be cached to avoid an infinite loop
Error: Maximum update depth exceeded.
```

Снимок должен возвращать то, что уже лежит в сторе (тот же объект, пока стор не менялся), или примитив. Отсюда правило для селекторов в сторах: селектор, который собирает новый объект или массив (`s => ({ items: s.items, promo: s.promo })`, `s => s.items.filter(...)`), нужно либо разбить на несколько селекторов с примитивами, либо обернуть в поверхностное сравнение — в Zustand это `useShallow`.

Сам `useSyncExternalStore` в прикладном коде пишут редко: его используют библиотеки. Но именно на нём держатся React Redux, Zustand и другие сторы, и вопрос про tearing задают, чтобы проверить, понимаешь ли ты, как они устроены.

Механизм понятен. Теперь — какие сторы бывают и чем они отличаются.

## Сторы на практике

### Redux Toolkit

Единый стор, изменения только через действия и чистые редьюсеры. Классический Redux критиковали за количество шаблонного кода, Redux Toolkit — современный стандарт, который его убирает:

```js
const cartSlice = createSlice({
  name: 'cart',
  initialState: { items: [] },
  reducers: {
    added: (state, action) => {
      state.items.push(action.payload);     // Immer: «мутация» черновика
    },
  },
});

export const { added } = cartSlice.actions; // тип действия — 'cart/added'
export const store = configureStore({ reducer: { cart: cartSlice.reducer } });
```

```jsx
const count = useSelector((s) => s.cart.items.length);
const dispatch = useDispatch();
dispatch(added(product));
```

Внутри `createSlice` работает Immer: код «мутирует» черновик, а на выходе получается новый объект, и старое состояние не меняется. `useSelector` построен на `useSyncExternalStore`. Сильные стороны — предсказуемость (все изменения — действия), Redux DevTools с путешествием во времени, middleware и RTK Query для серверных данных. Слабая — больше церемоний, чем нужно небольшому приложению.

### Zustand

Стор на хуке без провайдера и без действий. По сути — ядро из раздела выше с удобным API:

```js
const useCart = create((set) => ({
  items: [],
  add: (item) => set((s) => ({ items: [...s.items, item] })),
}));

const count = useCart((s) => s.items.length);   // подписка на срез
const add = useCart((s) => s.add);
```

Селектор — это подписка: компонент рендерится, только если изменился его результат. Методы можно вызывать и вне React: `useCart.getState().add(item)`. Популярен за простоту и маленький размер.

### Jotai

Атомарный подход «снизу вверх»: состояние — набор маленьких атомов, компонент подписан на те атомы, которые читает. Производный атом вычисляется из других и пересчитывается сам:

```js
const priceAtom = atom(100);
const qtyAtom = atom(1);
const totalAtom = atom((get) => get(priceAtom) * get(qtyAtom));

const total = useAtomValue(totalAtom);   // 300 после setQty(3)
```

Удобен, когда состояние естественно дробится на независимые части с зависимостями между ними, как ячейки таблицы.

### Сравнение

| | Redux Toolkit | Zustand | Jotai | Контекст |
| --- | --- | --- | --- | --- |
| Модель | один стор, действия, редьюсеры | стор на хуке | атомы | транспорт значения |
| Подписка | селектор | селектор | по атомам | на всё значение |
| Провайдер | нужен | не нужен | необязателен | нужен |
| Инструменты | DevTools, middleware, RTK Query | минимум | минимум | нет |
| Когда брать | большое приложение, много команд, строгий поток данных | большинство приложений | состояние из многих связанных частей | редко меняющиеся значения |

Recoil — атомарный стор от Meta — больше не развивается: в январе 2025 года его репозиторий переведён в архив. MobX (наблюдаемые объекты и мутации) встречается в старых проектах. Для нового кода выбирают из таблицы.

## Красные флаги в ответе

- **«Положу всё состояние в Redux».** Серверные данные — в кеш запросов, фильтры — в URL, локальное — в компонент. В стор — только глобальное клиентское.
- **«Контекст — это встроенный стейт-менеджер».** Контекст — транспорт без подписки на часть. Стор нужен, когда разным компонентам нужны разные части часто меняющегося состояния.
- **«Подпишусь на стор в `useEffect` и положу значение в `useState`».** При прерываемом рендере это даёт tearing. Подключение — через `useSyncExternalStore`.
- **«Селектор может вернуть новый объект, React разберётся».** Новый объект на каждом вызове — бесконечный цикл. Нужны примитивы или поверхностное сравнение.
- **«Redux устарел».** Устарел шаблонный код классического Redux. Redux Toolkit — актуальный выбор для больших приложений со строгим потоком данных.

## Как спрашивают на собеседовании

::question{level="mid"}
Как выбрать стейт-менеджер?

#mid
Сначала понять, какое это состояние. Серверные данные — в TanStack Query или SWR, локальное — в `useState`, редко меняющееся глобальное — в контекст, большое и часто меняющееся клиентское — в стор с селекторами.

#senior
Стор — не выбор по умолчанию. После выноса серверного состояния в кеш запросов, фильтров — в URL, а форм — в форму клиентского глобального состояния обычно остаётся немного. Дальше выбор по модели: Redux Toolkit — строгий поток действий, DevTools и много команд; Zustand — минимальный стор с селекторами; Jotai — состояние из связанных атомов. Все три подключаются через `useSyncExternalStore` и дают подписку на срез.
::

::question{level="mid"}
Почему серверные данные не стоит держать в Redux?

#mid
Это кеш удалённых данных: асинхронный, устаревающий, общий для разных экранов. Если держать его в Redux вручную, придётся заново писать загрузку, ошибки, повторы, инвалидацию и дедупликацию запросов.

#senior
У серверных данных источник истины — сервер, и главный вопрос — актуальность копии: когда перезапросить, что инвалидировать после мутации, как не сделать два одинаковых запроса. TanStack Query и SWR решают это из коробки, а RTK Query — то же самое внутри Redux. Ручные флаги `loading` / `error` / `data` в слайсе — источник гонок и устаревших данных.
::

::question{level="senior"}
Что такое tearing и как его избегают?

#mid
Ситуация, когда разные части экрана показывают разные версии одних данных. Возникает при прерываемом рендере, если внешний стор меняется посреди него. Сторы подключаются через `useSyncExternalStore`, который это предотвращает.

#senior
В transition React рендерит квантами и уступает поток. Компоненты, которые прочитали внешний стор до паузы, видят старое значение, после паузы — новое, и в commit попадает «разорванный» интерфейс. С React-состоянием этого нет — React управляет его версиями. `useSyncExternalStore` после рендера сверяет снимок и при несовпадении перерендеривает синхронно. Цена — потеря прерываемости в этот момент.
::

::question{level="senior"}
Как работает useSyncExternalStore?

#mid
Принимает `subscribe`, `getSnapshot` и `getServerSnapshot`. Подписывает компонент на стор и рендерит его, когда снимок изменился.

#senior
После уведомления стора React вызывает `getSnapshot` и сравнивает результат с прошлым через `Object.is`: тот же — рендера нет. Поэтому снимок должен быть стабильным: новый объект на каждый вызов даёт предупреждение `The result of getSnapshot should be cached` и бесконечный цикл. Хук защищает от tearing и нужен для SSR: без серверного снимка `renderToString` падает. В прикладном коде его используют для браузерных API (размер окна, `online`), а сторы — внутри себя.
::

::question{level="mid"}
Чем стор отличается от контекста по рендерам?

#mid
Стор даёт селекторы — подписку на срез: рендерятся только компоненты, чей срез изменился. Контекст рендерит всех потребителей при любом изменении значения.

#senior
Стор живёт вне React, и каждый подписчик сам решает, изменилось ли то, что ему нужно, — сравнивает результат селектора. Контекст передаёт одно значение целиком, и разделить его можно только на несколько контекстов. Их часто комбинируют: контекст доставляет экземпляр стора (удобно для тестов и SSR, где на каждый запрос нужен свой стор), а подписка идёт через селекторы стора.
::

::question{level="mid"}
Чем Redux Toolkit лучше классического Redux?

#mid
Он убирает шаблонный код: `createSlice` генерирует действия и редьюсеры, Immer позволяет писать редьюсеры «мутирующим» кодом, `configureStore` настраивает стор и DevTools. Есть RTK Query для серверных данных.

#senior
Immer даёт черновик через Proxy и собирает новое неизменяемое состояние по изменённым путям, поэтому `state.items.push(x)` в редьюсере безопасен, а прошлое состояние остаётся нетронутым. `configureStore` включает в dev проверки на мутации и несериализуемые значения. `useSelector` построен на `useSyncExternalStore` и сравнивает результат селектора по ссылке, поэтому селекторы, которые собирают новые объекты, мемоизируют (`createSelector`).
::

::question{level="mid"}
Когда стор вообще не нужен?

#mid
Когда серверные данные в библиотеке загрузки, а остальное — локальное состояние или редко меняющиеся глобальные значения в контексте.

#senior
Признаки, что стор нужен: одно клиентское состояние читают и меняют далёкие друг от друга части интерфейса, оно меняется часто, и разным компонентам нужны разные его части (редактор, корзина с промо и доставкой, сложный фильтр без URL). Если ничего из этого нет, стор добавляет абстракцию без пользы.
::

## Практика

::practice{title="Почему зацикливается?"}
Компонент читает корзину из Zustand, и при монтировании страница падает с `Maximum update depth exceeded`:

```jsx
const useCart = create((set) => ({ items: [], promo: '' /* ... */ }));

function CartSummary() {
  const { items, promo } = useCart((s) => ({ items: s.items, promo: s.promo }));
  return <p>{items.length} товаров, промокод {promo}</p>;
}
```

#solution
Селектор каждый раз создаёт новый объект. Zustand подключается через `useSyncExternalStore`, который сравнивает результат с прошлым через `Object.is`. Новый объект — «значение изменилось» — рендер — снова новый объект, и так до ошибки.

Два решения:

```jsx
// 1. отдельные селекторы с примитивами или существующими ссылками
const items = useCart((s) => s.items);
const promo = useCart((s) => s.promo);

// 2. поверхностное сравнение полей
import { useShallow } from 'zustand/react/shallow';
const { items, promo } = useCart(useShallow((s) => ({ items: s.items, promo: s.promo })));
```

Второе удобно, когда полей много. То же правило для `useSelector` в Redux: селектор, который собирает объект или фильтрует массив, мемоизируют через `createSelector`.
::

::practice{title="Хук размера окна"}
Напиши хук `useWindowWidth`, который не даёт tearing и работает при серверном рендере.

#solution
```jsx
function subscribe(callback) {
  window.addEventListener('resize', callback);
  return () => window.removeEventListener('resize', callback);
}

export function useWindowWidth() {
  return useSyncExternalStore(subscribe, () => window.innerWidth, () => 1024);
}
```

`subscribe` объявлен вне компонента, чтобы React не переподписывался на каждом рендере. Снимок — число, поэтому сравнение по `Object.is` работает. Серверное значение должно совпадать с тем, что клиент покажет при гидратации, иначе будет расхождение; поэтому иногда безопаснее показать на сервере нейтральную разметку.
::

::practice{title="Напиши стор на 20 строк"}
Реализуй минимальный стор с хуком `useStore(selector)`, чтобы компонент рендерился только при изменении своего среза. Без сторонних библиотек.

#solution
```jsx
function createStore(initial) {
  let state = initial;
  const listeners = new Set();
  const store = {
    getState: () => state,
    setState: (fn) => {
      state = { ...state, ...fn(state) };
      listeners.forEach((l) => l());
    },
    subscribe: (l) => {
      listeners.add(l);
      return () => listeners.delete(l);
    },
  };

  function useStore(selector) {
    return useSyncExternalStore(
      store.subscribe,
      () => selector(store.getState()),
      () => selector(store.getState()),
    );
  }

  return [store, useStore];
}

const [cart, useCart] = createStore({ items: [], promo: '' });

function CartCount() {
  return <b>{useCart((s) => s.items.length)}</b>;  // не рендерится при смене promo
}
```

В проверке после двух добавлений и смены промокода счётчик отрендерился три раза (монтирование и два добавления), а промо-блок — два. Важно, что `setState` создаёт новый объект состояния: если мутировать `state` на месте, снимки по ссылке не изменятся. Так устроено ядро Zustand.
::
