# Загрузка данных

Как загружать серверные данные в React-приложении: почему одного `useEffect` мало, что делает библиотека запросов, как устроены кеш и инвалидация, оптимистичные обновления, Suspense и водопады запросов. Спрашивают, чем плох `fetch` в эффекте и что такое stale-while-revalidate. Глубже — разницу `staleTime` и `gcTime`, откуда берутся водопады и как их убирать на уровне архитектуры.

::tldr
- **Серверные данные — это кеш, а не состояние.** Источник истины — сервер, локальная копия устаревает, и её нужно кешировать, делить между компонентами и обновлять.
- **`fetch` в `useEffect` решает только первую загрузку.** Гонки, кеш, дедупликацию, повторы и инвалидацию приходится писать руками — их дают TanStack Query, SWR и загрузчики фреймворков.
- **Stale-while-revalidate:** показать данные из кеша сразу, даже устаревшие, и обновить их в фоне. `staleTime` — сколько данные считаются свежими, `gcTime` — сколько неиспользуемый кеш хранится в памяти.
- **После мутации ключ инвалидируют**, и активные запросы перезапрашиваются. Оптимистичное обновление меняет кеш сразу и откатывается при ошибке.
- **Водопад — запросы, которые ждут друг друга без причины.** Он возникает, когда загрузка начинается в рендере вложенных компонентов. Лечится параллельной загрузкой на уровне страницы, предзагрузкой и загрузчиками маршрутов.
::

---

## Почему серверные данные особенные

Сквозной пример — страница профиля: пользователь, его посты, друзья и кнопка «лайк» у поста.

Профиль пользователя на клиенте — не «состояние», которым владеет приложение. Это **копия** данных с сервера, и у неё особые свойства:

- **асинхронная** — её нужно дождаться, загрузка может упасть;
- **общая** — тот же пользователь нужен шапке, профилю и комментариям;
- **устаревает** — на сервере данные меняются без ведома клиента;
- **принадлежит серверу** — после изменения правильное значение знает только сервер.

Поэтому задача не «хранить», а **кешировать**: когда перезапросить, что показать, пока идёт запрос, как не сделать один запрос дважды и как узнать, что копия устарела.

> Какое ещё бывает состояние и почему серверные данные не кладут в глобальный стор — в [State management](/content/reactjs/state-management).

## Загрузка в эффекте и что с ней не так

Первое, что пишут все:

```jsx
function User({ id }) {
  const [user, setUser] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    let ignore = false;
    fetch(`/api/users/${id}`)
      .then((r) => r.json())
      .then((data) => { if (!ignore) setUser(data); })
      .catch((e) => { if (!ignore) setError(e); });
    return () => { ignore = true; };
  }, [id]);
  // ...
}
```

Флаг `ignore` уже защищает от гонки, когда быстрый перебор `id` перезаписывает новые данные старым ответом. Почему без него получается гонка и как работает `AbortController` — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization). Но даже с ним проблем остаётся много:

- **нет кеша** — вернулся на страницу, и снова спиннер, хотя данные были секунду назад;
- **нет дедупликации** — шапка и профиль запросят одного пользователя дважды;
- **нет фонового обновления** — данные устарели, а компонент об этом не знает;
- **нет повторов** — один сбой сети, и пользователь видит ошибку;
- **нет инвалидации** — после редактирования профиля остальные экраны показывают старое имя;
- **водопады** — вложенные компоненты начинают загрузку по очереди (о них ниже).

Всё это — устройство кеша, и писать его в каждом компоненте не нужно. Для этого есть библиотеки запросов.

---

## Библиотека запросов

TanStack Query (бывший React Query) — самый распространённый вариант:

```jsx
function User({ id }) {
  const { data, isPending, error, isFetching } = useQuery({
    queryKey: ['user', id],
    queryFn: () => fetch(`/api/users/${id}`).then((r) => r.json()),
  });

  if (isPending) return <Spinner />;
  if (error) return <ErrorMessage error={error} />;
  return <Profile user={data} refreshing={isFetching} />;
}
```

Главная идея — **ключ запроса**. `['user', id]` — адрес данных в кеше. Всё, что библиотека делает, она делает по ключу:

- **Дедупликация.** Шапка и профиль вызывают `useQuery` с одним ключом — уходит один запрос, оба получают результат. В проверке два компонента с ключом `['user', 1]` дали один вызов сервера.
- **Кеш.** Вернулся на страницу — данные из кеша показываются сразу, без спиннера.
- **Гонки.** Ответ всегда пишется под свой ключ, и компонент читает данные текущего ключа. Старый ответ не может перезаписать новый.
- **Повторы.** Упавший запрос по умолчанию повторяется 3 раза с растущей паузой. В проверке запрос, который всегда падает, был вызван 4 раза, прежде чем компонент получил `error`.
- **Состояния.** `isPending` — данных ещё нет, `isFetching` — идёт запрос (в том числе фоновый при уже показанных данных).

Ключ должен содержать всё, от чего зависит результат: `['posts', userId, { page, sort }]`. Если забыть параметр, разные запросы попадут в одну ячейку кеша.

SWR от Vercel устроен по той же идее и проще по API. Внутри фреймворков (Next.js, React Router) серверные данные часто грузят загрузчики маршрутов или Server Components, и библиотека нужна для клиентских запросов и мутаций.

Ключевой вопрос любого кеша — когда считать данные устаревшими.

## Кеш: свежие и устаревшие данные

TanStack Query использует стратегию **stale-while-revalidate**: показать то, что есть в кеше, а если данные устарели — в фоне запросить новые и обновить экран.

```text
запрос завершён ──► данные свежие ──(staleTime)──► данные устаревшие
                                                     │
              новый компонент с этим ключом,         │
              фокус окна, переподключение сети  ─────┴──► фоновый перезапрос,
                                                          на экране — кеш
```

Две настройки, которые путают:

| | Что означает | По умолчанию |
| --- | --- | --- |
| `staleTime` | сколько данные считаются свежими: свежие не перезапрашиваются | 0 — устаревают сразу |
| `gcTime` | сколько данные без подписчиков хранятся в памяти, прежде чем их удалят | 5 минут |

В проверке со `staleTime: 0` повторное монтирование профиля сразу показало старое имя `Ann` с флагом фоновой загрузки, а через мгновение — новое `Anna`. Со `staleTime: 60_000` второго запроса не было вовсе.

По умолчанию `staleTime: 0`, и это осознанный выбор: данные всегда «могли устареть», поэтому библиотека перезапрашивает их при каждом удобном случае — монтировании, фокусе окна, восстановлении сети. Для справочников, которые меняются редко, `staleTime` поднимают до минут.

Кеш обновляется сам при фоновых перезапросах. Но если данные изменил сам пользователь, ждать не нужно.

## Мутации и инвалидация

После изменения данных на сервере нужно сказать кешу, какие ключи устарели:

```jsx
function EditName({ id }) {
  const queryClient = useQueryClient();
  const rename = useMutation({
    mutationFn: (name) => api.updateUser(id, { name }),
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ['user'] }),
  });

  return <button onClick={() => rename.mutate('Bob')}>Переименовать</button>;
}
```

`invalidateQueries` помечает все ключи, которые начинаются с `['user']`, как устаревшие и сразу перезапрашивает те, что сейчас на экране. В проверке после мутации профиль перезапросился и показал новое имя. Неактивные запросы обновятся, когда снова понадобятся.

Инвалидация по префиксу — причина строить ключи иерархически: `['user', id]`, `['user', id, 'posts']`. Тогда `['user', id]` инвалидирует всё, что связано с пользователем.

### Оптимистичное обновление

Лайк должен появиться сразу, а не через полсекунды, когда ответит сервер. Оптимистичное обновление меняет кеш до ответа и откатывает при ошибке:

```jsx
const like = useMutation({
  mutationFn: () => api.like(postId),
  onMutate: async () => {
    await queryClient.cancelQueries({ queryKey: ['post', postId] });   // не дать фоновому ответу затереть
    const prev = queryClient.getQueryData(['post', postId]);
    queryClient.setQueryData(['post', postId], (p) => ({ ...p, liked: !p.liked }));
    return { prev };                                                    // контекст для отката
  },
  onError: (_error, _vars, ctx) => queryClient.setQueryData(['post', postId], ctx.prev),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['post', postId] }),
});
```

В проверке сердечко загорелось до ответа, а когда сервер вернул ошибку, вернулось обратно. `cancelQueries` нужен, чтобы фоновый перезапрос, начатый до клика, не пришёл позже и не затёр оптимистичное значение. `onSettled` в конце сверяет кеш с сервером в любом случае.

> В React 19 для оптимистичного интерфейса в формах и Actions есть встроенный `useOptimistic` — в [RSC и React 19](/content/reactjs/rsc-and-react-19).

Кеш, мутации и инвалидация решают «что показать». Остаётся «как показать загрузку» — и здесь есть альтернатива флагам `isPending`.

## Suspense для данных

Вместо проверки `isPending` в каждом компоненте можно отдать загрузку и ошибки React. Компонент приостанавливается, пока данных нет, и пишет только «счастливый путь»:

```jsx
function User({ id }) {
  const { data } = useSuspenseQuery({ queryKey: ['user', id], queryFn: () => api.user(id) });
  return <Profile user={data} />;               // data всегда есть
}

<ErrorBoundary fallback={<ErrorMessage />}>
  <Suspense fallback={<Spinner />}>
    <User id={id} />
  </Suspense>
</ErrorBoundary>
```

Ответственность разделена: `Suspense` показывает fallback, пока поддерево ждёт данные, граница ошибок — запасной UI, если загрузка упала. В проверке одна ветка показала «загрузка», потом имя, другая — «загрузка», потом «ошибка: 500».

Границы ставят по смысловым зонам: один `Suspense` на всю страницу даёт один большой спиннер, отдельные — независимые блоки, которые появляются по мере готовности.

> Как React приостанавливает и повторяет рендер под капотом — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber). Чтение промиса через `use` — в [RSC и React 19](/content/reactjs/rsc-and-react-19).

Но у Suspense есть ловушка: два запроса в одном компоненте идут не параллельно. Это частный случай главной проблемы загрузки данных.

## Водопады

Водопад (waterfall) — запросы, которые идут последовательно, хотя могли бы параллельно. Классический источник — загрузка в рендере вложенных компонентов:

```jsx
function ProfilePage() {
  const user = useData(api.user);            // 1. загрузить пользователя
  return user ? <Posts /> : <Spinner />;
}

function Posts() {
  const posts = useData(api.posts);          // 2. начнётся, только когда отрисуются Posts
  return posts ? <Friends /> : <Spinner />;
}

function Friends() {
  const friends = useData(api.friends);      // 3. и только потом — друзья
  // ...
}
```

Каждый компонент начинает загрузку, только когда отрисовался, а отрисовывается, только когда загрузил родитель свои данные. Три запроса по 50 мс в проверке дали 160 мс. Те же три запроса, запущенные сразу на уровне страницы, — 57 мс.

С Suspense водопад прячется внутри одного компонента:

```jsx
const user = useSuspenseQuery({ queryKey: ['user'], queryFn: api.user }).data;
const posts = useSuspenseQuery({ queryKey: ['posts'], queryFn: api.posts }).data; // стартует после user
```

Первый вызов приостанавливает компонент. Второй выполнится только при повторном рендере, когда первый запрос завершится. В проверке второй запрос стартовал на 40 мс позже первого. Решения — `useSuspenseQueries` для параллельной загрузки или разнесение запросов по разным компонентам под одним `Suspense`.

### Как убирают водопады

- **Параллелить независимое.** Если посты не зависят от данных пользователя, они не должны его ждать: `useQueries`, `Promise.all` или разные компоненты-соседи.
- **Начинать загрузку раньше рендера.** Предзагрузка при наведении на ссылку (`queryClient.prefetchQuery`), загрузка в обработчике клика до перехода.
- **Грузить на уровне маршрута.** Загрузчики React Router и Next.js знают о данных всей страницы до рендера и запускают всё параллельно. Это переход от «загрузка в рендере» к «загрузка, потом рендер», а лучше — к «рендер по мере загрузки» со стримингом.
- **Перенести на сервер.** Server Components грузят данные рядом с базой, где цепочка запросов стоит миллисекунды, а не сотни миллисекунд по сети (подробно — в [RSC и React 19](/content/reactjs/rsc-and-react-19)).

Настоящие зависимости — посты, которые нельзя запросить без id пользователя, — остаются последовательными. В TanStack Query их выражают явно: `enabled: Boolean(user)`. Но такую цепочку часто лучше превратить в один запрос на сервере.

## Красные флаги в ответе

- **«Загружаю данные в `useEffect` с `useState` — этого достаточно».** Это только первая загрузка. Кеш, дедупликация, повторы, инвалидация и гонки остаются на тебе.
- **«Положу ответ сервера в Redux и буду обновлять руками».** Это ручной кеш без инвалидации. Серверным данным нужна библиотека запросов.
- **«`staleTime` и `gcTime` — одно и то же».** Первое — когда данные перестают быть свежими, второе — когда неиспользуемый кеш удаляется из памяти.
- **«Оптимистичное обновление — просто сразу поменять состояние».** Нужны отмена фоновых запросов, откат при ошибке и сверка с сервером в конце.
- **«Suspense сам распараллелит запросы».** Два запроса в одном компоненте под Suspense идут последовательно.

## Как спрашивают на собеседовании

::question
Чем серверное состояние отличается от обычного?

#answer
Оно асинхронное, общее для разных частей приложения, устаревает и принадлежит серверу. Это кеш удалённых данных, а не состояние приложения, и для него нужны кеширование, дедупликация и обновление.

#more
Главный вопрос серверных данных — актуальность копии: когда перезапросить, что показать во время запроса, что инвалидировать после мутации. Локальное состояние меняет сам клиент, серверное — кто угодно. Поэтому для него нужна не «запись и чтение», а политика кеша: stale-while-revalidate, повторы, перезапрос при фокусе окна и восстановлении сети, инвалидация по ключам.
::

::question
Чем плоха загрузка данных в useEffect?

#answer
Нужно самому защищаться от гонок запросов, а кеша, дедупликации, повторов и инвалидации нет. Вложенные компоненты, которые грузят данные в эффектах, дают водопады. Плюс одинаковый код `loading` / `error` в каждом компоненте.

#more
Эффект запускает загрузку только после рендера и commit, то есть поздно: сначала рендер со спиннером, потом запрос. Вложенность превращает это в цепочку последовательных запросов. Флаг `ignore` или `AbortController` решают гонку, но не кеш. Поэтому react.dev рекомендует фреймворк или библиотеку запросов, а в эффекте грузить данные — только если других вариантов нет.
::

::question
Что такое stale-while-revalidate?

#answer
Показать данные из кеша сразу, даже если они могли устареть, и одновременно перезапросить их в фоне. Когда придёт ответ, экран обновится.

#more
Пользователь не видит спиннер при возврате на страницу, но получает свежие данные. В TanStack Query этим управляют `staleTime` (сколько данные свежие, по умолчанию 0) и `gcTime` (сколько неиспользуемый кеш живёт в памяти, по умолчанию 5 минут). Фоновый перезапрос устаревших данных случается при монтировании нового наблюдателя, фокусе окна и восстановлении сети. `isPending` означает «данных нет», а `isFetching` — «идёт запрос», в том числе фоновый.
::

::question
Что такое инвалидация кеша и когда она нужна?

#answer
Пометить данные в кеше устаревшими, чтобы они перезапросились. Обычно после мутации, которая изменила данные на сервере.

#more
`invalidateQueries({ queryKey: ['user'] })` помечает устаревшими все ключи с этим префиксом и сразу перезапрашивает активные, остальные — при следующем использовании. Поэтому ключи строят иерархически. Альтернатива инвалидации — записать ответ мутации прямо в кеш через `setQueryData`, если сервер вернул обновлённый объект: это экономит запрос.
::

::question
Как сделать оптимистичное обновление правильно?

#answer
Изменить кеш сразу в `onMutate`, сохранить прошлое значение и восстановить его в `onError`, если сервер вернул ошибку.

#more
Порядок: отменить фоновые запросы этого ключа (`cancelQueries`), иначе ответ, начатый до клика, затрёт оптимистичное значение; сохранить снимок; записать новое значение; вернуть снимок как контекст. В `onError` — откат, в `onSettled` — инвалидация, чтобы сверить кеш с сервером. При нескольких быстрых мутациях откат к снимку может стереть успех соседней мутации — тогда вместо отката лучше инвалидировать.
::

::question
Как Suspense и граница ошибок делят ответственность при загрузке?

#answer
`Suspense` показывает fallback, пока данные грузятся, граница ошибок — запасной UI, если загрузка упала. Компонент пишет только код для готовых данных.

#more
Компонент с `useSuspenseQuery` или `use(promise)` приостанавливается, и React показывает ближайший `Suspense`. Ошибка запроса бросается в рендере и доходит до ближайшей границы ошибок. Расстановка границ — дизайн загрузки страницы: одна граница даёт один спиннер, несколько — независимые блоки. Ловушка: несколько запросов в одном компоненте под Suspense идут последовательно, нужен `useSuspenseQueries` или разные компоненты.
::

::question
Что такое водопад запросов и как его убрать?

#answer
Запросы, которые идут последовательно, хотя могли бы параллельно. Например, вложенные компоненты, каждый из которых начинает загрузку после того, как отрисовался родитель. Лечится параллельной загрузкой, предзагрузкой и загрузкой на уровне маршрута.

#more
Источник — загрузка в рендере: компонент узнаёт о своих данных, только когда отрисовался. Решения: поднять загрузку на уровень страницы и запустить независимые запросы вместе, предзагружать при наведении или в обработчике, использовать загрузчики маршрутов, которые знают данные страницы до рендера, или Server Components, где цепочка запросов идёт рядом с базой. Настоящие зависимости остаются последовательными — их выражают через `enabled` или переносят в один серверный запрос.
::

## Практика

::practice{title="Почему профиль грузится три раза дольше?"}
Страница профиля открывается за 600 мс, хотя каждый из трёх запросов занимает 200 мс:

```jsx
function ProfilePage({ id }) {
  const { data: user } = useQuery({ queryKey: ['user', id], queryFn: () => api.user(id) });
  if (!user) return <Spinner />;
  return <Posts userId={id} />;
}

function Posts({ userId }) {
  const { data: posts } = useQuery({ queryKey: ['posts', userId], queryFn: () => api.posts(userId) });
  if (!posts) return <Spinner />;
  return <Friends userId={userId} />;
}

function Friends({ userId }) {
  const { data: friends } = useQuery({ queryKey: ['friends', userId], queryFn: () => api.friends(userId) });
  // ...
}
```

#solution
Водопад. `Posts` монтируется только после загрузки пользователя, а `Friends` — после загрузки постов. Каждый запрос ждёт предыдущий, хотя все три зависят только от `id`, который известен сразу.

Фикс — запустить все запросы на уровне страницы:

```jsx
function ProfilePage({ id }) {
  const [user, posts, friends] = useQueries({
    queries: [
      { queryKey: ['user', id], queryFn: () => api.user(id) },
      { queryKey: ['posts', id], queryFn: () => api.posts(id) },
      { queryKey: ['friends', id], queryFn: () => api.friends(id) },
    ],
  });

  if (user.isPending) return <Spinner />;
  return <Profile user={user.data} posts={posts.data} friends={friends.data} />;
}
```

Теперь страница готова за время самого долгого запроса. В проверке три запроса по 50 мс шли 160 мс водопадом и 57 мс параллельно. Ещё лучше — загрузчик маршрута, который запустит запросы до рендера, или предзагрузка при наведении на ссылку.
::

::practice{title="Почему после сохранения старое имя?"}
Пользователь меняет имя в настройках. Форма показывает «Сохранено», но в шапке остаётся старое имя до перезагрузки страницы:

```jsx
function NameForm({ id }) {
  const save = useMutation({ mutationFn: (name) => api.updateUser(id, { name }) });
  return <form action={(fd) => save.mutate(fd.get('name'))}>...</form>;
}

function Header() {
  const { data } = useQuery({ queryKey: ['user', 'me'], queryFn: api.me, staleTime: Infinity });
  return <span>{data?.name}</span>;
}
```

#solution
Мутация изменила данные на сервере, но кеш об этом не знает. Шапка читает `['user', 'me']` со `staleTime: Infinity` — данные никогда не устаревают и сами не перезапросятся.

Фикс — инвалидировать связанные ключи после успешной мутации или записать ответ прямо в кеш:

```jsx
function NameForm({ id }) {
  const queryClient = useQueryClient();
  const save = useMutation({
    mutationFn: (name) => api.updateUser(id, { name }),
    onSuccess: (updatedUser) => {
      queryClient.setQueryData(['user', 'me'], updatedUser);         // если сервер вернул пользователя
      queryClient.invalidateQueries({ queryKey: ['user'] });         // и пометить остальное
    },
  });
  return <form action={(fd) => save.mutate(fd.get('name'))}>...</form>;
}
```

Иерархические ключи (`['user', ...]`) позволяют одной строкой инвалидировать всё, что связано с пользователем.
::

::practice{title="Лайк мигает обратно"}
Оптимистичный лайк иногда загорается, гаснет и загорается снова, хотя сервер отвечает успешно:

```jsx
const like = useMutation({
  mutationFn: () => api.like(postId),
  onMutate: () => {
    queryClient.setQueryData(['post', postId], (p) => ({ ...p, liked: true }));
  },
});
```

#solution
В момент клика уже шёл фоновый перезапрос поста — например, после фокуса окна. Оптимистичное значение записалось в кеш, затем пришёл ответ того запроса со старым `liked: false` и перезаписал кеш, а потом следующий перезапрос вернул `true`. Плюс нет отката при ошибке.

Фикс — полный цикл оптимистичного обновления:

```jsx
const like = useMutation({
  mutationFn: () => api.like(postId),
  onMutate: async () => {
    await queryClient.cancelQueries({ queryKey: ['post', postId] });
    const prev = queryClient.getQueryData(['post', postId]);
    queryClient.setQueryData(['post', postId], (p) => ({ ...p, liked: true }));
    return { prev };
  },
  onError: (_e, _v, ctx) => queryClient.setQueryData(['post', postId], ctx.prev),
  onSettled: () => queryClient.invalidateQueries({ queryKey: ['post', postId] }),
});
```

`cancelQueries` отменяет запросы, начатые до клика, `onError` откатывает при ошибке, `onSettled` сверяет кеш с сервером. В проверке значение стало `true` до ответа и вернулось в `false`, когда сервер ответил ошибкой.
