# Загрузка данных

Загрузка данных - это работа с **server state**: данными, которые живут на сервере, а в приложении существуют как **кэш**. Понимание, чем server state отличается от обычного состояния, - то, что отличает middle от junior в этом вопросе.

---

## Почему server state особенный

Серверные данные нельзя обрабатывать как обычный `useState`, потому что они:

- **асинхронные** - приходят с задержкой, могут упасть;
- **разделяемые** - один и тот же ресурс нужен в разных местах;
- **устаревают** - на сервере данные меняются, локальная копия протухает;
- требуют **кэш, дедупликацию, фоновое обновление**.

Это не «состояние», а **кэш удалённого источника**. Поэтому для него отдельный класс инструментов.

---

## Наивный fetching и его проблемы

```jsx
function User({ id }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    setLoading(true);
    fetch(`/api/users/${id}`)
      .then((r) => r.json())
      .then(setUser)
      .catch(setError)
      .finally(() => setLoading(false));
  }, [id]);
  // ...
}
```

Что здесь не так на масштабе:

- **Гонки запросов** - быстрый перебор `id` может перезаписать новые данные старым ответом (нужен флаг отмены, см. [эффекты](/content/reactjs/effects-and-synchronization)).
- **Нет кэша** - тот же запрос в другом компоненте идёт заново.
- **Нет дедупликации** - два компонента дёрнут один и тот же эндпоинт дважды.
- **Водопады (waterfalls)** - вложенные компоненты грузят данные последовательно.
- **Ручные loading/error** в каждом компоненте.

> Поэтому в проде fetching в `useEffect` почти не пишут руками - берут библиотеку.

## React Query / SWR

**TanStack Query** (React Query) и **SWR** - стандарт работы с server state. Они дают кэш, дедупликацию и фоновое обновление из коробки.

```jsx
import { useQuery } from '@tanstack/react-query';

function User({ id }) {
  const { data, isLoading, error } = useQuery({
    queryKey: ['user', id],                       // ключ кэша
    queryFn: () => fetch(`/api/users/${id}`).then((r) => r.json()),
  });

  if (isLoading) return <Spinner />;
  if (error) return <Error />;
  return <Profile user={data} />;
}
```

Что решается автоматически:

- **Кэш по `queryKey`** - повторный запрос отдаёт данные мгновенно.
- **Дедупликация** - параллельные запросы с тем же ключом сливаются в один.
- **Stale-while-revalidate** - показываем кэш сразу, в фоне обновляем.
- **Refetch** на фокус окна, реконнект, по интервалу.
- **Отмена гонок** - библиотека отслеживает актуальность.

## Кэш и инвалидация

**Stale-while-revalidate** - центральная идея: данные считаются «свежими» (`fresh`) какое-то время (`staleTime`), потом «протухшими» (`stale`). Протухшие всё ещё показываются из кэша, но триггерят фоновое обновление.

**Инвалидация** - явно пометить кэш устаревшим, чтобы перезапросить (обычно после мутации).

```jsx
const queryClient = useQueryClient();

const mutation = useMutation({
  mutationFn: (data) => api.updateUser(data),
  onSuccess: () => {
    queryClient.invalidateQueries({ queryKey: ['user', id] }); // перезапросить
  },
});
```

> «Инвалидация кэша» - один из «двух сложных вопросов в CS». На практике это просто: пометил ключ stale → библиотека перезапросит при следующем использовании.

## Оптимистичные обновления

UI обновляется **сразу**, не дожидаясь ответа сервера; при ошибке откатывается. Создаёт ощущение мгновенности.

```jsx
useMutation({
  mutationFn: toggleLike,
  onMutate: async (id) => {
    await queryClient.cancelQueries({ queryKey: ['post', id] });
    const prev = queryClient.getQueryData(['post', id]);
    queryClient.setQueryData(['post', id], (p) => ({ ...p, liked: !p.liked }));
    return { prev }; // для отката
  },
  onError: (_e, id, ctx) => queryClient.setQueryData(['post', id], ctx.prev),
});
```

В React 19 для этого есть встроенный хук [`useOptimistic`](/content/reactjs/rsc-and-react-19).

## Suspense для данных и обработка ошибок

Библиотеки умеют интегрироваться с **Suspense**: вместо `if (isLoading)` компонент «приостанавливается», а ближайший `<Suspense>` показывает fallback. Ошибки ловит **error boundary**.

```jsx
<ErrorBoundary fallback={<Error />}>
  <Suspense fallback={<Spinner />}>
    <User id={id} />   {/* приостановится, пока грузятся данные */}
  </Suspense>
</ErrorBoundary>
```

<b class="text-on-semi-light">Разделение ответственности</b> - <span class="text-gray">`Suspense` отвечает за состояние загрузки (fallback), error boundary - за состояние ошибки. Компонент пишет «счастливый путь», как будто данные уже есть. Error boundary - классовый компонент (`getDerivedStateFromError`), см. [паттерны](/content/reactjs/patterns-and-component-design).</span>

## Водопады запросов

**Waterfall** - запросы идут последовательно, потому что зависят друг от друга или вложены в дерево, которое рендерится по очереди.

```jsx
// ❌ Waterfall: сначала грузится user, только потом - его posts
const user = useQuery(['user', id]);
const posts = useQuery(['posts', user.data?.id], { enabled: !!user.data });
```

Лечение: **параллелить** независимые запросы, **префетчить** заранее, поднимать загрузку к роуту. На сервере waterfalls особенно дороги - там помогают RSC и loader'ы фреймворков ([рендеринг](/content/reactjs/rendering-and-hydration)).

## React 19: use()

Хук `use()` умеет **читать промис** прямо в рендере, интегрируясь с Suspense, - подробнее в [RSC и React 19](/content/reactjs/rsc-and-react-19).

```jsx
function Comments({ commentsPromise }) {
  const comments = use(commentsPromise); // приостановит до резолва
  return comments.map((c) => <p key={c.id}>{c.text}</p>);
}
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем server state отличается от обычного состояния?</b>
<span class="text-gray">Он асинхронный, разделяемый, устаревает и требует кэша/дедупликации. Это кэш удалённых данных, а не локальное состояние - для него отдельные инструменты.</span>

<b class="text-on-semi-light">Чем плох fetching в useEffect?</b>
<span class="text-gray">Гонки запросов, отсутствие кэша и дедупликации, водопады, ручные loading/error в каждом компоненте. React Query решает это из коробки.</span>

<b class="text-on-semi-light">Что такое stale-while-revalidate?</b>
<span class="text-gray">Стратегия: показать данные из кэша сразу (даже устаревшие), а в фоне перезапросить и обновить. Быстрый UI без ожидания сети.</span>

<b class="text-on-semi-light">Что такое инвалидация кэша?</b>
<span class="text-gray">Пометить кэшированные данные устаревшими, чтобы они перезапросились - обычно после мутации, изменившей данные на сервере.</span>

<b class="text-on-semi-light">Как Suspense и error boundary делят ответственность при загрузке?</b>
<span class="text-gray">Suspense показывает fallback во время загрузки, error boundary - при ошибке. Компонент пишет только «счастливый путь».</span>

<b class="text-on-semi-light">Что такое request waterfall и как его убрать?</b>
<span class="text-gray">Последовательные зависимые запросы. Лечится параллелизацией независимых запросов, префетчем и загрузкой на уровне роута/сервера.</span>
