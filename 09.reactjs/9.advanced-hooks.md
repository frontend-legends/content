# Хуки: карта и свои хуки

Карта всех встроенных хуков React по задачам: что делает каждый, где с ним ошибаются и где он разобран подробно. И три темы, которые живут здесь: `useReducer`, кастомные хуки и `useDebugValue`. Спрашивают «какие хуки знаешь и когда `useReducer` вместо `useState`». Глубже — почему редьюсер обязан быть чистым, что кастомный хук должен возвращать и как написать `useMediaQuery` без эффекта.

::tldr
- **Хук выбирают по задаче, а не по названию.** Меняет экран — state, не меняет — ref, считается из props — вычисление в рендере, внешний источник — `useSyncExternalStore`, синхронизация с внешней системой — эффект.
- **`useReducer` — тот же state, но переходы описаны одной чистой функцией.** Его берут для связанных полей и переходов по событиям. `dispatch` стабилен по ссылке, поэтому его удобно отдавать через контекст.
- **Редьюсер вызывается во время рендера, а не в момент `dispatch`.** Поэтому он видит свежие props, StrictMode вызывает его дважды, а мутация `state` в нём даёт задвоенные данные.
- **Кастомный хук — функция с префиксом `use`, которая вызывает другие хуки.** Его код выполняется на каждом рендере, он делит логику, а не состояние. Функции, которые он возвращает, должны быть стабильными, иначе ломаются deps у того, кто его вызывает.
- **`useDebugValue` подписывает кастомный хук в React DevTools.** Функция форматирования вызывается, только когда DevTools смотрит на компонент.
::

## Какие хуки есть и какой брать под задачу

Вопрос из первых минут собеседования по React: «Какие хуки ты знаешь?» Перечислить названия может каждый. Интервьюер ждёт другого: что ты знаешь, какой хук **под какую задачу**, и где у каждого грабли.

Возьмём экран, который пройдёт через всю тему, — доску задач:

```jsx
function TaskBoard() {
  const [tasks, setTasks] = useState([]);
  const [status, setStatus] = useState('idle'); // 'idle' | 'loading' | 'error'
  const [error, setError] = useState(null);
  const [query, setQuery] = useState('');
  // + запомнить настройки доски (сортировка, скрыть выполненные) между перезагрузками
  // + компактный вид на узком экране
  // + фокус в поле после добавления задачи
  // + форма добавления с индикатором отправки

  return (
    <>
      <label htmlFor="search">Поиск</label>
      <input id="search" value={query} onChange={(e) => setQuery(e.target.value)} />
      <TaskList tasks={tasks} query={query} />
    </>
  );
}
```

У каждой строки-комментария своя задача, и у каждой задачи свой хук. Встроенных хуков около двадцати: в пакете `react` 18 хуков и API `use`, в `react-dom` — `useFormStatus`. Запоминать их списком бесполезно, группами по задаче — легко. Каждая группа отвечает на один вопрос о компоненте: что он помнит, с чем синхронизируется, на что ссылается, что не пересчитывает, чему уступает, что читает снаружи, как получает id, как отправляет формы и как выглядит в DevTools.

Пройдём по группам.

## Карта встроенных хуков

Почти у каждого хука есть дом — тема, где он разобран полностью. Здесь — задача, главные грабли и ссылка. Как хук хранит данные (ячейки на fiber, порядок вызовов, очередь апдейтов) — общее для всех и разобрано в [Механике хуков](/content/reactjs/hooks-mechanics).

### Состояние: что компонент помнит

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useState` | значение, изменение которого перерисовывает экран | начальное значение читается только при монтировании; мутация объекта не запускает рендер |
| `useReducer` | связанное состояние с переходами по событиям | редьюсер вызывается в рендере и обязан быть чистым |
| `useContext` | значение ближайшего провайдера без проброса props | при смене значения перерисовываются все читатели; объект-литерал в `value` — новое значение на каждом рендере провайдера |

`useState` подробно — в [State and events](/content/reactjs/state-and-events), `useContext` — в [Context API](/content/reactjs/context-api). `useReducer` живёт здесь, к нему вернёмся в следующем разделе: у `TaskBoard` как раз три поля, которые меняются вместе.

### Эффекты: с чем компонент синхронизируется

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useEffect` | синхронизация с системой вне React после отрисовки: подписка, запрос, таймер | объект или функция из рендера в deps перезапускают эффект на каждом рендере; без cleanup — утечки и гонки |
| `useLayoutEffect` | измерить DOM и поправить его до отрисовки кадра | выполняется синхронно и задерживает кадр, поэтому только для измерений |
| `useInsertionEffect` | вставить стили раньше всех layout-эффектов; нужен библиотекам CSS-in-JS | ref на первом запуске ещё не прикреплён; `setState` внутри запрещён |
| `useEffectEvent` | логика в эффекте, которой нужны свежие props, но не нужна реакция на их изменение | вызывать только из эффектов: в рендере бросает ошибку; в deps не кладётся |

Прежде чем выбирать эффект, стоит проверить, нужен ли он вообще: производные данные считаются в рендере, а реакция на клик — в обработчике. Подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization).

### Ссылки и DOM: на что компонент ссылается

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useRef` | значение между рендерами, которое не влияет на экран: DOM-узел, id таймера | изменение `current` не перерисовывает; читать и писать `current` в рендере нельзя, кроме ленивой инициализации (`if (ref.current === null) ref.current = …`) |
| `useImperativeHandle` | отдать родителю через ref свой API (`focus`, `open`) вместо DOM-узла | ломает декларативность: сначала попробуй управлять через props |

Фокус в поле после добавления задачи — это `useRef` на `input`. Подробно — в [Refs, порталах и a11y](/content/reactjs/refs-portals-a11y).

### Производительность: что компонент не пересчитывает

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useMemo` | не пересчитывать дорогое значение и сохранить ссылку на объект | если вычисление дешёвое и ссылка никому не важна (нет `memo`-ребёнка, нет deps), только добавляет работу |
| `useCallback` | сохранить ссылку на функцию; то же, что `useMemo(() => fn, deps)` | функция всё равно создаётся на каждом рендере; ребёнок без `memo` перерисуется в любом случае |

Обе задачи всё чаще решает :term[React Compiler]{def="плагин сборки, который сам мемоизирует компоненты, значения и функции по правилам React"}. Когда ручная мемоизация нужна — в [Производительности](/content/reactjs/performance).

### Приоритеты: чему компонент уступает

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useTransition` | пометить несрочным отдельный апдейт (`startTransition(() => setTab(next))`) и получить `isPending` | не подходит для значения текстового поля; апдейт после `await` нужно снова обернуть в `startTransition` |
| `useDeferredValue` | отложенная копия значения: само значение остаётся срочным, тяжёлый потребитель отстаёт | объект, созданный в рендере, — каждый раз новое значение и лишние фоновые рендеры |

Разница в том, сколько у тебя состояний. `useTransition` нужен, когда несрочную часть можно вынести в свой `setState` и обернуть его в `startTransition`: срочный `setQuery`, несрочный `setResults`. `useDeferredValue` — когда значение одно, и оно должно оставаться срочным, а отставать должен тяжёлый потребитель. Так же он работает со значением, которое пришло через prop и сеттера которого у тебя нет. Для поиска в `TaskBoard` подходит второй. `query` — значение поля, его нельзя менять в transition, иначе при быстром вводе теряются буквы. Поэтому `query` остаётся срочным, а длинный список фильтруется по отложенной копии. Подробно — в [Производительности](/content/reactjs/performance).

### Внешние сторы: что компонент читает снаружи

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useSyncExternalStore` | подписаться на источник вне React: стор, `matchMedia`, `localStorage`, `navigator.onLine` | `getSnapshot` обязан возвращать тот же результат, пока источник не изменился, иначе бесконечный цикл; `subscribe`, созданный в рендере, переподписывается на каждом рендере |

Почему это отдельный хук, а не `useState` с `useEffect`, и что такое :term[tearing]{def="рассинхрон: разные части экрана в одном рендере показывают разные версии внешних данных"} — в [State management](/content/reactjs/state-management). Для `TaskBoard` это строительный блок: на нём построим `useMediaQuery` и `useLocalStorage`.

### Идентификаторы

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useId` | уникальный id для `htmlFor`, `aria-describedby`, одинаковый на сервере и в браузере | не для `key` в списке |

В `TaskBoard` id `"search"` захардкожен: два экземпляра доски на странице дадут два одинаковых id. `useId` выдаёт свой id каждому экземпляру и сохраняет его между рендерами. Почему он совпадает на сервере и в браузере — в [Рендеринге и гидратации](/content/reactjs/rendering-and-hydration).

### React 19: Actions и use

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `use` | прочитать промис или контекст; можно в условиях | промис, созданный в рендере клиентского компонента, приостанавливает его снова и снова |
| `useActionState` | состояние, которое обновляет action формы: результат, ошибка, `isPending` | вызов `dispatch` вне формы и вне `startTransition` — предупреждение, и `isPending` не обновляется |
| `useOptimistic` | показать результат до ответа сервера | значение откатывается, когда action завершился; апдейт вне transition — предупреждение |
| `useFormStatus` | статус отправки родительской формы: `pending`, `data` | работает только в компоненте внутри `form`, а не в том, кто форму рендерит |

`use` формально не хук, а API: он не занимает ячейку, поэтому его можно вызывать по условию. Форма добавления задачи с кнопкой «Сохраняю…» — это `useActionState` и `useFormStatus`. Подробно — в [RSC и React 19](/content/reactjs/rsc-and-react-19).

### Отладка: как хук выглядит в DevTools

| Хук | Задача | Главные грабли |
| --- | --- | --- |
| `useDebugValue` | подпись кастомного хука в React DevTools | дорогое форматирование передают вторым аргументом-функцией, а не считают в рендере |

Дом у него здесь, ему посвящён последний раздел темы.

### Как выбрать

Порядок вопросов, которым удобно пройтись по любому требованию:

```text
Значение меняет то, что на экране?
  да  → useState; связанные поля и переходы → useReducer
  нет → useRef
Значение можно посчитать из props и state?
  да  → посчитай в рендере; дорого → useMemo
Нужно читать источник вне React, у которого есть текущее значение?
  → useSyncExternalStore
Нужно синхронизироваться с системой вне React?
  → useEffect; измерение DOM до кадра → useLayoutEffect
Интерфейс тормозит при вводе?
  несрочное вынесено в отдельный setState → useTransition
  одно значение срочное, тяжёлый потребитель отстаёт → useDeferredValue
Форма отправляет данные на сервер?
  → useActionState, useOptimistic, useFormStatus
```

Производные данные — отдельный частый вопрос, он разобран в [Derived state](/content/reactjs/derived-state-and-data-flow).

Карта раздала хуки всем комментариям в `TaskBoard`. Осталось то, с чего компонент начинается: три `useState`, которые описывают одну загрузку. Это задача `useReducer`.

## useState или useReducer

Посмотрим, как `TaskBoard` загружает задачи с тремя `useState`:

```jsx
async function load() {
  setStatus('loading');
  try {
    setTasks(await fetchTasks());
    setStatus('idle');
  } catch (e) {
    setError(e);
    setStatus('error');
  }
}
```

Через месяц кто-то добавит повторную загрузку и забудет `setError(null)`. На экране окажутся одновременно свежие задачи и старая ошибка. Каждое поле по отдельности корректно, а их сочетание — нет. Три сеттера позволяют собрать :term[невозможное состояние]{def="сочетание значений, которого по смыслу быть не может: загрузка завершена и ошибка одновременно"}, и защиты от этого нет.

`useReducer` описывает **переходы** вместо полей. Компонент сообщает, что случилось, а как от этого меняется состояние, решает одна функция:

```jsx
const initialState = { tasks: [], status: 'idle', error: null };

function tasksReducer(state, action) {
  switch (action.type) {
    case 'load':
      return { ...state, status: 'loading', error: null };
    case 'loaded':
      return { tasks: action.tasks, status: 'idle', error: null };
    case 'failed':
      return { ...state, status: 'error', error: action.error };
    case 'added':
      return { ...state, tasks: [...state.tasks, action.task] };
    case 'toggled':
      return {
        ...state,
        tasks: state.tasks.map((t) => (t.id === action.id ? { ...t, done: !t.done } : t)),
      };
    default:
      throw new Error(`Unknown action: ${action.type}`);
  }
}

function TaskBoard() {
  const [state, dispatch] = useReducer(tasksReducer, initialState);

  async function load() {
    dispatch({ type: 'load' });
    try {
      dispatch({ type: 'loaded', tasks: await fetchTasks() });
    } catch (error) {
      dispatch({ type: 'failed', error });
    }
  }
  // ...
}
```

Ошибка сбрасывается в одном месте, и забыть это при новом сценарии нельзя: все переходы видны в одной функции.

Переходы защищают от забытого сброса, но сама форма `{ tasks, status, error }` невозможное сочетание всё ещё допускает: ничто не мешает записать `status: 'idle'` вместе с ошибкой. Следующий шаг — сделать состояние :term[размеченным объединением]{def="тип из нескольких вариантов, где вариант определяется значением одного поля-метки"} по `status`. В TypeScript это discriminated union для `state` и для `action`:

```ts
type TasksState =
  | { status: 'idle' | 'loading'; tasks: Task[] }
  | { status: 'error'; tasks: Task[]; error: Error };

type TasksAction =
  | { type: 'load' }
  | { type: 'loaded'; tasks: Task[] }
  | { type: 'failed'; error: Error };
```

Теперь `{ status: 'idle', tasks, error }` не компилируется, `state.error` читается только после проверки `status === 'error'`, а `switch (action.type)` в каждой ветке сужает действие до его полей. Невозможное состояние становится непредставимым.

### Когда брать useReducer

- **Поля меняются вместе.** `status`, `error` и `tasks` — одно состояние загрузки, а не три независимых значения.
- **Следующее состояние зависит от предыдущего и от события.** «Переключить задачу с этим id» — переход, а не новое значение.
- **Переходов много, и их хочется проверить отдельно.** Редьюсер — обычная функция, её тестируют без React: `tasksReducer(state, { type: 'failed', error })`.
- **Обработчики становятся тоньше.** Компонент описывает, что произошло (`'added'`), а не как пересобрать массив.

Для независимых простых значений — флаг «меню открыто», текст поиска — `useState` короче и понятнее. `query` в `TaskBoard` остаётся отдельным `useState`: он не связан с загрузкой.

Разница между хуками меньше, чем кажется. На апдейте `useState` в React — это `useReducer` со встроенным редьюсером `basicStateReducer`, который вызывает функцию-апдейтер или возвращает новое значение. У обоих одна ячейка с очередью. Но одно отличие есть, и оно следует из того, **когда** вызывается редьюсер.

### Редьюсер вызывается в рендере

`dispatch` ничего не считает. Он кладёт действие в очередь хука и планирует рендер. Редьюсер вызывается, когда React рендерит компонент и применяет очередь:

```text
dispatch({ type: 'added' })   → действие в очереди, state не изменился
console.log(state)            → старое значение: константа текущего рендера
рендер TaskBoard              → tasksReducer(state, action) → новое state
```

Из этого следуют четыре вещи.

**Редьюсер видит свежие props.** Если объявить его внутри компонента, он замкнёт props того рендера, в котором применяется очередь:

```jsx
function Counter({ step }) {
  const [n, dispatch] = useReducer((n) => n + step, 0);
  // step был 1, родитель передал 10, потом dispatch() → n === 10
}
```

Так можно, но редьюсер вне компонента проще читать и тестировать. Если ему нужны props, передай их в действии: `dispatch({ type: 'add', step })`.

**Тот же state: компонент вызывается, дети — нет.** У `useState` есть eager bailout: `setState` сразу считает новое значение и, если оно равно текущему, даже не планирует рендер. Срабатывает он, только когда на fiber нет других ожидающих апдейтов (подробно — в [Механике хуков](/content/reactjs/hooks-mechanics)). Считать заранее можно, потому что редьюсер у `useState` встроенный и никогда не меняется. Редьюсер `useReducer` может замыкать props и в следующем рендере быть другим — это предыдущий пункт. Результат, посчитанный в `dispatch` старым редьюсером, мог бы не совпасть с тем, что даст редьюсер рендера. Поэтому `dispatch` ничего не считает заранее, и действие, которое возвращает тот же `state`, каждый раз вызывает компонент. Потом React сравнивает результат через `Object.is` и не трогает детей.

**Редьюсер обязан быть чистым.** React вправе вызвать его несколько раз: при перепроигрывании очереди после срочного апдейта, а в StrictMode — дважды на каждое действие. Результат одного из вызовов отбрасывается. Чистому редьюсеру это ничего не меняет, а мутирующему — да.

**Побочным эффектам в нём не место.** Запрос, `localStorage`, аналитика, `dispatch` изнутри — всё это выполнится столько раз, сколько React вызовет редьюсер. Асинхронная работа делается в обработчике или эффекте, а редьюсер получает уже готовый результат, как `'loaded'` выше.

В dev после добавления задачи в списке две одинаковые строки, в проде — одна. В консоли React предупреждает о повторяющемся `key`.
#cause
Редьюсер мутирует состояние: `state.tasks.push(action.task); return { ...state }`. StrictMode вызывает редьюсер дважды с одним и тем же `state`. Оба вызова пушат в один и тот же массив, и в нём оказываются две копии.
#fix
Возвращать новые объекты: `tasks: [...state.tasks, action.task]`. Если вложенность глубокая — Immer (`useImmerReducer`): мутирующий синтаксис поверх копии. Выключать StrictMode нельзя: в проде тот же редьюсер сломается при перепроигрывании очереди.
::

### Начальное состояние и init

Начальное состояние, как и у `useState`, используется только при монтировании. Но выражение в аргументе вычисляется на каждом рендере:

```jsx
useReducer(tasksReducer, createInitialState(initialTasks)); // считает на каждом рендере
useReducer(tasksReducer, initialTasks, createInitialState); // init(initialTasks) — только при монтировании
```

Здесь `initialTasks` — prop, а `createInitialState(tasks)` собирает `{ tasks, status: 'idle', error: null }`. Третий аргумент — функция `init`: начальное состояние будет `init(initialArg)`. Её же удобно звать для сброса: `case 'reset': return init(action.payload)`. В StrictMode `init` тоже вызывается дважды, поэтому и она должна быть чистой.

### dispatch стабилен

`dispatch` создаётся один раз при монтировании и возвращается одним и тем же объектом на каждом рендере. Поэтому его можно передать `memo`-ребёнку без `useCallback` и отдать через контекст. Линтер (`exhaustive-deps`) не требует класть его в deps, только если `dispatch` получен прямо из `useReducer` в том же компоненте. Полученный из кастомного хука или из контекста он для линтера обычная переменная. Такой `dispatch` кладут в deps, и это безопасно: ссылка не меняется, эффект не перезапустится.

Последнее — классический приём для форм и виджетов, где действия нужны глубоко в дереве. `state` и `dispatch` кладут в **разные** контексты:

```jsx
const TasksContext = createContext(null);
const TasksDispatchContext = createContext(null);

function TasksProvider({ children }) {
  const [state, dispatch] = useReducer(tasksReducer, initialState);
  return (
    <TasksContext value={state}>
      <TasksDispatchContext value={dispatch}>{children}</TasksDispatchContext>
    </TasksContext>
  );
}
```

Кнопка «Добавить» читает только `TasksDispatchContext`. Значение этого контекста никогда не меняется, поэтому при новом `state` кнопка не перерисовывается из-за контекста. Если оба значения положить в один объект `{ state, dispatch }`, кнопка будет перерисовываться на каждое действие. Как контекст решает, кого перерисовать, и другие способы его разделить — в [Context API](/content/reactjs/context-api).

### Чего useReducer не умеет

`useReducer` — не Redux. У него нет middleware, devtools с историей действий, селекторов и общего состояния между независимыми частями приложения. Это локальное состояние одного компонента. Если «редьюсер в контексте» разрастается до глобального стора, пора смотреть на библиотеки — в [State management](/content/reactjs/state-management).

Состояние `TaskBoard` теперь в порядке. Но в компоненте по-прежнему лежат загрузка, сохранение в `localStorage` и проверка ширины экрана. Всё это логика, которую хочется вынести и переиспользовать.

## Кастомные хуки

Кастомный хук — обычная функция, которая вызывает другие хуки. Его вызовы встраиваются в список ячеек компонента, который его вызвал. Поэтому два компонента с `useTasks()` получают независимые данные: хук делит **логику**, а не состояние. Как это устроено — в [Механике хуков](/content/reactjs/hooks-mechanics). Почему хуки вытеснили HOC и render props — в [Паттернах](/content/reactjs/patterns-and-component-design).

Для `TaskBoard` первый кандидат — всё, что связано с задачами:

```jsx
function useTasks() {
  const [state, dispatch] = useReducer(tasksReducer, initialState);

  const load = useCallback(async () => {
    dispatch({ type: 'load' });
    try {
      dispatch({ type: 'loaded', tasks: await fetchTasks() });
    } catch (error) {
      dispatch({ type: 'failed', error });
    }
  }, []);

  return { ...state, load, dispatch };
}
```

### Правила и имя

- **Имя — `use` и заглавная буква:** `useTasks`, `useMediaQuery`. Рантайму префикс не нужен. По нему линтер и React Compiler понимают, что к функции применяются правила хуков: вызов только на верхнем уровне, только из компонентов и других хуков.
- **Функция без хуков внутри — не хук.** `useSorted(items)`, который просто сортирует, должен называться `getSorted`. Иначе на него зря распространяются правила хуков: его нельзя вызвать в условии или в цикле.
- **Код хука выполняется на каждом рендере** вызывающего компонента. Это часть тела компонента, поэтому хук обязан быть таким же чистым, как компонент.
- **Хук получает свежие аргументы на каждом рендере.** Если хук принимает обработчик и вызывает его из эффекта, класть обработчик в deps плохо: эффект будет перезапускаться. Обработчик оборачивают в `useEffectEvent` внутри хука. Подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization).

### Когда хук не нужен

- **Обёртка над одним `useState`.** `useInput()` вокруг одного `useState` — лишний слой. Небольшое дублирование лучше, чем абстракция, которую нужно открыть, чтобы понять.
- **Хуки «жизненного цикла».** `useMount(fn)`, `useEffectOnce(fn)`, `useUpdateEffect(fn)` прячут `useEffect` с фиксированными deps. Линтер проверяет deps только у прямых вызовов `useEffect`, поэтому `useMount(() => connect(roomId))` молча не переподключится при смене `roomId`.
- **Имя не придумывается.** Хороший хук называется по задаче: `useTasks`, `useChatRoom(roomId)`, `useMediaQuery(query)`. Если имя не складывается, логика ещё слишком переплетена с компонентом.

Хороший сигнал, что хук нужен, — эффект. Эффект означает выход за пределы React, и хук с понятным именем объясняет, зачем этот выход и какие данные через него идут.

### Что возвращать

**Кортеж или объект.** Пара «значение и сеттер» — кортеж, как у `useState`: вызывающий сам назовёт элементы (`const [theme, setTheme] = useLocalStorage('theme', 'light')`). Три значения и больше — объект: по именам, порядок не важен.

**Стабильные функции.** Компонент, который вызывает хук, вправе положить результат в deps эффекта. Если хук на каждом рендере возвращает новую функцию, эффект перезапускается на каждом рендере. Поэтому `load` в `useTasks` обёрнут в `useCallback`, а `dispatch` стабилен сам. Сам объект `{ ...state, load, dispatch }` при этом новый на каждом рендере. Хук может стабилизировать и его через `useMemo`, как в задаче про `useApi` ниже. Но надёжнее, когда вызывающий кладёт в deps отдельные поля (`load`), а не весь объект: тогда ему неважно, мемоизирован объект или нет. С React Compiler мемоизацию внутри хука расставит сборка, но правило для вызывающего остаётся.

**Минимум.** Хук возвращает то, что нужно вызывающему, а не всё, что у него внутри. Чем меньше наружу, тем свободнее менять устройство хука. `useTasks` отдаёт `dispatch` осознанно: набор действий редьюсера становится частью API хука, зато `dispatch` стабилен без `useCallback`, и его сразу можно положить в контекст. Если этот протокол хочется скрыть, хук возвращает узкие функции `add(task)` и `toggle(id)` в `useCallback`.

### useDebouncedValue: эффект с cleanup

Самая частая live-coding задача по кастомным хукам — «напиши debounce». Если поиск по задачам уйдёт на сервер, он не должен слать запрос на каждую букву:

```jsx
function useDebouncedValue(value, delay = 300) {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delay);
    return () => clearTimeout(id);
  }, [value, delay]);
  return debounced;
}

const serverQuery = useDebouncedValue(query, 300); // меняется после паузы в вводе
```

Всё держится на cleanup. Каждая новая буква меняет `value`, React перед новым запуском эффекта вызывает cleanup, и прошлый таймер отменяется. Если ввести `a`, `ab`, `abc` быстрее 300 мс, `serverQuery` станет `'abc'` один раз. Без `clearTimeout` таймеры доживают, и запросы уходят на каждую букву, просто с задержкой.

`useDeferredValue` эту задачу не решает: отложенный рендер начинается сразу и число запросов не сокращает. Он только не даёт тяжёлому рендеру блокировать ввод. Разница — в [Производительности](/content/reactjs/performance).

Таймер — внешняя система без текущего значения, поэтому здесь эффект на месте. У ширины экрана текущее значение есть, и для неё нужен другой строительный блок.

### useMediaQuery: хук поверх внешнего источника

Вторая строка `TaskBoard` — компактный вид на узком экране. Первое, что приходит в голову, — `useState` и подписка в `useEffect`. Но у `matchMedia` уже есть текущее значение, и копировать его в state не нужно. Для источника со своим текущим значением есть `useSyncExternalStore`: он берёт снимок прямо из источника и перерисовывает компонент, когда тот сообщает об изменении.

```jsx
function useMediaQuery(query) {
  const subscribe = useCallback(
    (onChange) => {
      const mql = window.matchMedia(query);
      mql.addEventListener('change', onChange);
      return () => mql.removeEventListener('change', onChange);
    },
    [query],
  );

  return useSyncExternalStore(
    subscribe,
    () => window.matchMedia(query).matches, // снимок в браузере
    () => false,                             // снимок при SSR
  );
}

const isNarrow = useMediaQuery('(max-width: 600px)');
```

Три детали, на которых этот хук ломают:

- **`subscribe` стабилен.** Функция, созданная прямо в рендере, — каждый раз новая, и React отписывается и подписывается заново на каждом рендере. `useCallback` с `[query]` переподписывает только при смене запроса.
- **Снимок — примитив.** `matches` — boolean. Два одинаковых boolean равны через `Object.is`, поэтому лишних рендеров нет.
- **Третий аргумент — снимок для сервера.** На сервере нет `window`. Без `getServerSnapshot` серверный рендер бросает ошибку `Missing getServerSnapshot`. С ним сервер и гидратация отрисуют `false`, разметка совпадёт, а сразу после гидратации React перерисует компонент с настоящим значением.

Почему для этого нужен отдельный хук, а не `useState` с `useEffect`, — в [State management](/content/reactjs/state-management). Здесь важно, что внутри кастомного хука он работает как строительный блок.

### useLocalStorage: снимок должен быть стабильным

Настройки доски, которые переживают перезагрузку, — тот же приём. Задачи в хранилище не кладём: их источник истины — сервер, а в компоненте они живут в редьюсере `useTasks`. Копия в `localStorage` стала бы вторым источником, и пришлось бы решать, какой из двух главный. В хранилище — только то, что принадлежит этому браузеру: сортировка и флаг «скрыть выполненные».

Но и здесь есть ловушка: `localStorage` хранит строки, а компоненту нужен объект `{ sort, hideDone }`.

```jsx
// Не так: JSON.parse объекта или массива возвращает новый объект на каждом вызове getSnapshot
useSyncExternalStore(subscribe, () => JSON.parse(localStorage.getItem(key)));
```

React вызывает `getSnapshot` несколько раз — в рендере и после commit — и сравнивает результаты через `Object.is`. Новый объект при каждом вызове выглядит как «источник всё время меняется». React перерендеривает снова и снова, а потом останавливается с ошибкой. Коварство в том, что ошибка проявляется не сразу. Пока хранилище пустое, `JSON.parse(null)` даёт `null`, а примитив вроде `'"dark"'` равен сам себе, и цикла нет. Падает первая загрузка страницы после того, как пользователь сохранил настройки.

```text
The result of getSnapshot should be cached to avoid an infinite loop
Error: Maximum update depth exceeded.
```

Решение — снимком сделать саму строку. Строки сравниваются по значению, а парсить её можно один раз на каждое изменение:

```jsx
const listeners = new Set();

function subscribe(onChange) {
  listeners.add(onChange);
  window.addEventListener('storage', onChange); // изменения из других вкладок
  return () => {
    listeners.delete(onChange);
    window.removeEventListener('storage', onChange);
  };
}

function useLocalStorage(key, initialValue) {
  const raw = useSyncExternalStore(
    subscribe,
    () => localStorage.getItem(key),
    () => null,
  );
  const value = useMemo(() => (raw === null ? initialValue : JSON.parse(raw)), [raw, initialValue]);

  const setValue = useCallback(
    (next) => {
      localStorage.setItem(key, JSON.stringify(next));
      listeners.forEach((l) => l()); // своя вкладка: storage сюда не придёт
    },
    [key],
  );

  return [value, setValue];
}
```

- **`subscribe` объявлен вне компонента** и поэтому стабилен без `useCallback`.
- **Событие `storage` приходит только в другие вкладки** того же origin, а не в ту, что изменила хранилище. Поэтому `setValue` сам оповещает подписчиков своей вкладки.
- **`initialValue` в deps `useMemo`.** Если вызывающий передаёт литерал `{ sort: 'created', hideDone: false }`, это новый объект на каждом рендере, и при пустом хранилище `value` тоже будет новым. Вызывающему лучше передавать константу, как `DEFAULT_SETTINGS` ниже.

Теперь `TaskBoard` собирается из хуков, каждый из которых делает одно дело:

```jsx
const DEFAULT_SETTINGS = { sort: 'created', hideDone: false };

function TaskBoard() {
  const { tasks, status, error, load, dispatch } = useTasks();
  const [settings, setSettings] = useLocalStorage('board-settings', DEFAULT_SETTINGS);
  const isNarrow = useMediaQuery('(max-width: 600px)');
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const searchId = useId();
  // ...
}
```

У каждого значения один источник истины: задачи приходят с сервера и живут в редьюсере `useTasks`, настройки — в `localStorage`, ширина экрана — в `matchMedia`. Ни одно значение не хранится в двух местах.

Хуки вынесены в общий пакет, ими пользуется вся команда. Коллега открывает React DevTools и выбирает `TaskBoard`. Кастомные хуки там видны по именам — `Tasks`, `LocalStorage`, `MediaQuery`, — но чтобы узнать, что `MediaQuery` сейчас вернул, нужно раскрывать вложенные `SyncExternalStore` и `Callback`. Показать главное значение хука сразу — задача последнего хука этой темы.

## useDebugValue: подпись для DevTools

`useDebugValue` добавляет кастомному хуку подпись в React DevTools. Вызывается внутри хука, на верхнем уровне:

```jsx
function useMediaQuery(query) {
  // ...
  const matches = useSyncExternalStore(subscribe, getSnapshot, getServerSnapshot);
  useDebugValue(matches, (m) => `${query}: ${m ? 'да' : 'нет'}`);
  return matches;
}
```

В панели хуков выбранного компонента DevTools покажет кастомный хук `MediaQuery` сразу с подписью `(max-width: 600px): да`: имя DevTools берёт из имени функции без префикса `use`, а подпись — из `useDebugValue`.

### Почему форматирование отложено

Второй аргумент — функция форматирования. DevTools вызывает её, только когда ты выбираешь компонент. При обычном рендере она не выполняется, поэтому дорогое форматирование — `date.toDateString()`, сериализация объекта — ничего не стоит пользователям.

Это следует из устройства хука. `useDebugValue` не занимает ячейку, а в рендерере React его реализация ничего не делает. Значения хуков DevTools собирает иначе: при инспекции он заново вызывает функцию компонента со своим диспетчером. Тот читает ячейки с fiber, записывает, какие хуки вызваны и что в них лежит, а сеттеры подменяет пустышками, так что состояние не меняется. В этот момент и вызывается форматтер.

### Когда он нужен

Не в каждом хуке. Подпись окупается в хуках общей библиотеки со сложным внутренним состоянием: `useLocalStorage` с ключом, `useQuery` со статусом запроса, хуки форм. В хуке приложения, который вызывается в одном месте, проще посмотреть на state в DevTools.

Тесты для кастомных хуков пишут через `renderHook`: хук нельзя вызвать вне компонента, и тестовая обёртка рендерит его в служебном компоненте. Подробно — в [Тестировании React](/content/reactjs/testing-react).

## Красные флаги в ответе

- **«`useReducer` — это мини-Redux для глобального состояния».** Это локальный state одного компонента. В контексте он становится общим для поддерева, но без middleware, селекторов и истории действий.
- **«Редьюсер вызывается при `dispatch`».** `dispatch` кладёт действие в очередь, а редьюсер вызывается в рендере. Поэтому он видит свежие props и может вызываться несколько раз.
- **«Ничего страшного, если редьюсер немного мутирует state, я же возвращаю новый объект».** Возвращённый объект делит вложенный массив с прежним. StrictMode вызывает редьюсер дважды, и мутация попадает в массив два раза.
- **«Сделаю `useMount`, чтобы было как `componentDidMount`».** Хуки жизненного цикла прячут deps от линтера: эффект молча перестаёт реагировать на изменения.
- **«`getSnapshot` может вернуть `JSON.parse(...)`».** Новый объект на каждый вызов — бесконечный цикл рендеров. Снимок должен быть примитивом или закешированным объектом.
- **«`useDebugValue` логирует значение и замедляет прод».** Он ничего не выводит, а форматтер вызывается только при инспекции в DevTools.

## Как спрашивают на собеседовании

::question
Какие встроенные хуки ты знаешь? Для чего каждый?

#answer
Назвать группы, а не список. Состояние — `useState`, `useReducer`, `useContext`. Эффекты — `useEffect`, `useLayoutEffect`, `useInsertionEffect`, `useEffectEvent`. Ссылки — `useRef`, `useImperativeHandle`. Мемоизация — `useMemo`, `useCallback`. Приоритеты — `useTransition`, `useDeferredValue`. Внешние сторы — `useSyncExternalStore`. Id — `useId`. Формы и Actions — `useActionState`, `useOptimistic`, `useFormStatus` и API `use`. Отладка — `useDebugValue`.

#more
К каждой группе — главные грабли. Эффект часто не нужен вовсе: производные данные считаются в рендере. `useMemo` нужен для дорогого вычисления или для ссылки, которая важна потребителю (`memo`-ребёнок, deps); в остальных случаях он только добавляет работу, а React Compiler расставляет мемоизацию сам. `useRef` не читают и не пишут в рендере, кроме ленивой инициализации. `useSyncExternalStore` требует стабильного `getSnapshot`. `useFormStatus` видит только родительскую форму. Выбор начинается с вопроса «влияет ли значение на экран»: да — state, нет — ref.

#followups
- «Чем `useTransition` отличается от `useDeferredValue`?» → `useTransition` — когда несрочную часть можно вынести в отдельный `setState` и обернуть в `startTransition`; `useDeferredValue` — когда значение одно и должно остаться срочным (значение поля, prop), а отставать должен тяжёлый потребитель
- «Можно ли `useId` для `key`?» → нет: он для связки атрибутов доступности; ключи берут из данных
::

::question
Когда useReducer лучше useState?

#answer
Когда поля меняются вместе и следующее состояние зависит от предыдущего и от события: загрузка со статусом и ошибкой, многошаговая форма, корзина. Переходы собраны в одной чистой функции, её легко тестировать без React. `dispatch` стабилен, его удобно передавать вниз.

#more
Главный аргумент — невозможные состояния. Несколько `useState` позволяют собрать сочетание, которого быть не может, а редьюсер описывает переходы целиком. Для независимых простых значений `useState` лучше. Внутри React разница небольшая: на апдейте `useState` — это `useReducer` со встроенным редьюсером. Отличие — eager bailout: `setState` с тем же значением может не планировать рендер вовсе, а `dispatch` с тем же результатом всё равно вызовет компонент. Заранее посчитать нельзя: редьюсер текущего рендера может замыкать новые props и отличаться от прошлого, а встроенный редьюсер `useState` не меняется никогда.
::

::question
Когда React вызывает редьюсер и почему он должен быть чистым?

#answer
Редьюсер вызывается во время рендера, когда React применяет очередь действий. Сразу после `dispatch` state ещё старый. В StrictMode редьюсер вызывается дважды, поэтому мутации и побочные эффекты в нём проявляются задвоением.

#more
`dispatch` только кладёт действие в очередь хука и планирует рендер. Поэтому редьюсер, объявленный в компоненте, видит props того рендера, в котором применяется очередь. React вправе вызвать его несколько раз: StrictMode проверяет это намеренно, а в проде низкоприоритетные апдейты перепроигрываются после срочных. Значит, никаких запросов, записи в хранилище и мутаций — асинхронная работа идёт в обработчике или эффекте, редьюсер получает готовый результат.

#followups
- «Можно ли вызвать `dispatch` внутри редьюсера?» → нет: это побочный эффект в рендере; следующее состояние возвращают из того же вызова
::

::question
Зачем при useReducer + context делают два провайдера?

#answer
В один контекст кладут `state`, в другой — `dispatch`. Компоненты, которым нужно только отправлять действия, читают второй и не перерисовываются при каждом изменении `state`.

#more
Перерисовка читателей контекста происходит, когда меняется его значение. `dispatch` создаётся один раз и не меняется, поэтому значение второго контекста стабильно. Если положить в контекст `{ state, dispatch }`, объект новый при каждом изменении `state`, и перерисуются все читатели, включая кнопки. Это не стейт-менеджер: у читателей `state` нет селекторов, любой переход перерисовывает их всех.
::

::question
Когда стоит выносить логику в кастомный хук? Как его назвать и что вернуть?

#answer
Когда логика с хуками повторяется или когда эффект синхронизирует компонент с внешней системой: хук с понятным именем объясняет намерение. Имя начинается с `use` и называет задачу: `useMediaQuery`, `useChatRoom`. Пара значений — кортеж, больше — объект.

#more
Не нужен для обёртки над одним `useState`, для функции без хуков (её называют без `use`) и в виде хуков жизненного цикла вроде `useMount`: линтер не проверит deps внутри них. Возвращаемые функции должны быть стабильными (`useCallback`, `dispatch` или React Compiler), иначе deps у вызывающего ломаются. Обработчики, которые хук вызывает из эффекта, оборачивают в `useEffectEvent`. Код хука выполняется на каждом рендере, поэтому он подчиняется той же чистоте, что и компонент.

#followups
- «Делят ли два компонента состояние одного хука?» → нет: вызовы хуков встраиваются в ячейки каждого компонента отдельно
- «Как его протестировать?» → `renderHook` из Testing Library
- «Напиши `useDebouncedValue`» → `useState` для отложенной копии и эффект с `setTimeout`, deps `[value, delay]`; cleanup `clearTimeout` отменяет прошлый таймер, без него запрос уходит на каждую букву
::

::question
Напиши useMediaQuery. Почему не useState + useEffect?

#answer
`useSyncExternalStore(subscribe, () => matchMedia(query).matches, () => false)`, где `subscribe` вешает обработчик `change` на `MediaQueryList`. Хук сам берёт текущее значение и перерисовывает компонент при изменении.

#more
У `matchMedia` есть текущее значение, копия в state не нужна. Вариант с эффектом подписывается только после отрисовки: изменение между рендером и эффектом теряется, если не перечитать значение в эффекте. Инициализатор `useState`, который читает `window`, падает при SSR. А при конкурентном рендере разные компоненты могут прочитать разные версии значения — это tearing. Грабли `useSyncExternalStore`: `subscribe` должен быть стабильным (`useCallback` с `[query]` или вне компонента), снимок — примитивом, иначе бесконечный цикл, а для SSR нужен `getServerSnapshot`. Для `localStorage` снимком делают строку и парсят в `useMemo`, а свою вкладку оповещают сами: событие `storage` приходит только в другие вкладки.

#followups
- «Зачем `useDebugValue` в таком хуке?» → подпись `(max-width: 600px): да` в DevTools; форматтер вызывается только при инспекции
::

## Практика

::practice{title="Найди баг: задача добавляется дважды"}
В dev после нажатия «Добавить» в списке две одинаковые задачи. В проде — одна.

```jsx
function tasksReducer(state, action) {
  switch (action.type) {
    case 'added':
      state.tasks.push(action.task);
      return { ...state };
    default:
      return state;
  }
}
```

#solution
Редьюсер мутирует `state.tasks`. StrictMode вызывает редьюсер дважды с одним и тем же `state`, и оба вызова пушат в один массив. `{ ...state }` — новый объект, но `tasks` в нём тот же массив:

```text
render  []
dispatch({ type: 'added', task: 'a' })
render  ['a', 'a']
```

В проде двойного вызова нет, но тот же редьюсер задвоит задачу, когда React перепроиграет очередь после срочного апдейта. Исправление — новый массив:

```jsx
function tasksReducer(state, action) {
  switch (action.type) {
    case 'added':
      return { ...state, tasks: [...state.tasks, action.task] };
    default:
      return state;
  }
}
```
::

::practice{title="Почему useLocalStorage падает?"}
Пока пользователь ничего не сохранял, доска работает. Но как только в хранилище появились настройки (объект), страница падает при первом же рендере.

```jsx
function useLocalStorage(key, initialValue) {
  const value = useSyncExternalStore(
    (onChange) => {
      window.addEventListener('storage', onChange);
      return () => window.removeEventListener('storage', onChange);
    },
    () => JSON.parse(localStorage.getItem(key)) ?? initialValue,
  );
  // ...
}
```

#solution
Две ошибки. Главная — `getSnapshot` возвращает новый объект на каждый вызов: `JSON.parse` объекта каждый раз создаёт новый объект, `Object.is` видит изменение, и React рендерит компонент снова. Пока хранилище пустое, снимок — `initialValue`, одна и та же ссылка в пределах рендера, поэтому баг и не виден до первого сохранения:

```text
The result of getSnapshot should be cached to avoid an infinite loop
Error: Maximum update depth exceeded.
```

Вторая — `subscribe` создаётся в рендере, поэтому на каждом рендере происходит отписка и новая подписка.

Снимком делаем строку, парсим в `useMemo`, `subscribe` выносим из хука:

```jsx
function subscribe(onChange) {
  window.addEventListener('storage', onChange);
  return () => window.removeEventListener('storage', onChange);
}

function useLocalStorage(key, initialValue) {
  const raw = useSyncExternalStore(subscribe, () => localStorage.getItem(key), () => null);
  return useMemo(() => (raw === null ? initialValue : JSON.parse(raw)), [raw, initialValue]);
}
```
::

::practice{title="Почему запросы идут без остановки?"}
Список задач загружается, а в Network — бесконечный поток одинаковых запросов.

```jsx
function useApi(baseUrl) {
  const get = (path) => fetch(baseUrl + path).then((r) => r.json());
  return { get };
}

function Tasks() {
  const api = useApi('/api');
  const [tasks, setTasks] = useState([]);

  useEffect(() => {
    api.get('/tasks').then(setTasks);
  }, [api]);

  return <TaskList tasks={tasks} />;
}
```

#solution
`useApi` на каждом рендере возвращает новый объект с новой функцией. `setTasks` вызывает рендер, `api` — новая ссылка, эффект перезапускается и снова вызывает `setTasks` с новым массивом. Цикл.

Хук должен возвращать стабильные значения, а вызывающий — зависеть от отдельных функций, а не от объекта:

```jsx
function useApi(baseUrl) {
  const get = useCallback((path) => fetch(baseUrl + path).then((r) => r.json()), [baseUrl]);
  return useMemo(() => ({ get }), [get]);
}

function Tasks() {
  const { get } = useApi('/api');
  const [tasks, setTasks] = useState([]);

  useEffect(() => {
    get('/tasks').then(setTasks);
  }, [get]);

  return <TaskList tasks={tasks} />;
}
```

Теперь запрос уходит один раз и повторяется только при смене `baseUrl`. Эффект без cleanup здесь для краткости: защита от гонки ответов — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization).
::
