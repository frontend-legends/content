# Состояние и события

**Состояние (state)** - это память компонента: данные, которые меняются со временем и при изменении вызывают перерисовку. **События** - то, как пользователь это состояние меняет. Звучит просто, но именно здесь живёт большинство тонких вопросов на собесе: иммутабельность, снапшоты, батчинг.

---

## useState

```jsx
function Counter() {
  const [count, setCount] = useState(0); // [значение, сеттер]
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}
```

`useState` возвращает текущее значение и функцию-сеттер. Вызов сеттера **планирует ререндер** - React заново вызовет компонент, и `useState` вернёт уже новое значение.

<b class="text-on-semi-light">Состояние ≠ обычная переменная</b> - <span class="text-gray">Обычная переменная сбрасывается при каждом вызове функции и не вызывает перерисовку. Состояние React **сохраняет** между рендерами и **триггерит** ререндер при изменении.</span>

---

## Состояние - это снапшот

Ключевая ментальная модель: **значение состояния зафиксировано на время одного рендера**. Сеттер не меняет переменную «на лету» - он планирует следующий рендер с новым значением.

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }
  // count увеличится на 1, а не на 3!
  return <button onClick={handleClick}>{count}</button>;
}
```

В этом рендере `count === 0`, поэтому все три вызова - это `setCount(0 + 1)`. React видит три раза «поставь 1».

### Функциональный апдейтер

Если новое значение зависит от предыдущего - передавай функцию. React применит их по очереди к актуальному состоянию.

```jsx
function handleClick() {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
  setCount((c) => c + 1);
}
// теперь +3: каждая функция получает результат предыдущей
```

> Правило: если следующее состояние зависит от предыдущего - используй updater-функцию `setX(prev => ...)`.

## Иммутабельность

Состояние нельзя **мутировать** - его нужно **заменять** новым значением. React сравнивает ссылки (`Object.is`), и если ссылка та же, он не увидит изменений.

```jsx
// ❌ Мутация - React не заметит, ререндера не будет
state.items.push(newItem);
setItems(state.items);

// ✅ Новый массив
setItems([...items, newItem]);

// ❌ Мутация объекта
user.name = 'Аня';
setUser(user);

// ✅ Новый объект
setUser({ ...user, name: 'Аня' });
```

<b class="text-on-semi-light">Почему именно так?</b> - <span class="text-gray">React сравнивает старое и новое состояние по ссылке - это дёшево. Мутация оставляет ссылку прежней, поэтому изменение «теряется». Плюс иммутабельность нужна для корректной работы мемоизации и конкурентного рендеринга.</span>

Для глубоко вложенных структур помогает **Immer** (`produce`) - он даёт писать «мутирующий» код, а под капотом создаёт новые объекты.

## События

React оборачивает нативные DOM-события в **SyntheticEvent** - кросс-браузерную обёртку с тем же API (`e.target`, `e.preventDefault()`, `e.stopPropagation()`).

```jsx
function Form() {
  function handleSubmit(e) {
    e.preventDefault();        // отменяем перезагрузку страницы
    console.log('submit');
  }
  return <form onSubmit={handleSubmit}>...</form>;
}
```

- Обработчики - в camelCase: `onClick`, `onChange`, `onSubmit`.
- В JSX передают **ссылку** на функцию (`onClick={handleClick}`), а не вызов (`onClick={handleClick()}`).
- React навешивает не отдельные слушатели на каждый узел, а **делегирование** на корень приложения (с React 17 - на корневой контейнер, а не на `document`).

<b class="text-on-semi-light">Event pooling</b> - <span class="text-gray">До React 17 синтетические события переиспользовались из пула, и `e` нельзя было читать асинхронно. В React 17+ пулинг убран - событие можно использовать как обычно.</span>

## Controlled vs uncontrolled

Это про то, кто хранит значение поля формы - React или сам DOM. Частый вопрос на собесе.

### Controlled (управляемый)

Значение живёт в state, поле читает его из `value`, а изменения идут через `onChange`. **Источник истины - React.**

```jsx
function Search() {
  const [q, setQ] = useState('');
  return <input value={q} onChange={(e) => setQ(e.target.value)} />;
}
```

### Uncontrolled (неуправляемый)

Значение хранит сам DOM, React читает его при необходимости через `ref`. **Источник истины - DOM.**

```jsx
function Search() {
  const inputRef = useRef(null);
  function handleSubmit() {
    console.log(inputRef.current.value); // читаем по требованию
  }
  return <input ref={inputRef} defaultValue="" />;
}
```

| | Controlled | Uncontrolled |
|--|------------|--------------|
| Источник истины | React state | DOM |
| Значение | `value` | `defaultValue` |
| Доступ | из state | через `ref` |
| Когда | валидация на лету, зависимые поля, форматирование | простые формы, интеграция с не-React кодом, файловый `<input type="file">` |

<b class="text-on-semi-light">Что выбирать?</b> - <span class="text-gray">По умолчанию controlled - предсказуемо и легко валидировать. Но при каждом нажатии клавиши идёт ререндер; для больших форм это причина брать неуправляемый подход или библиотеки вроде react-hook-form (uncontrolled под капотом). Файловый input всегда uncontrolled.</span>

> Нельзя смешивать: задать одновременно `value` без `onChange` - получишь warning «controlled to uncontrolled» и поле, которое нельзя редактировать.

## Батчинг

React **группирует** несколько обновлений состояния в один ререндер - это батчинг.

```jsx
function handleClick() {
  setCount((c) => c + 1);
  setFlag((f) => !f);
  // один ререндер, а не два
}
```

<b class="text-on-semi-light">Automatic batching (React 18+)</b> - <span class="text-gray">До 18 батчинг работал только внутри обработчиков React-событий. С React 18 он автоматический везде - в промисах, `setTimeout`, нативных обработчиках. Раньше там было по ререндеру на каждый `setState`.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему три `setCount(count + 1)` подряд дают +1, а не +3?</b>
<span class="text-gray">Состояние - снапшот: в текущем рендере `count` фиксирован. Все три вызова используют одно значение. Нужно `setCount(c => c + 1)` - тогда +3.</span>

<b class="text-on-semi-light">Почему нельзя мутировать состояние напрямую?</b>
<span class="text-gray">React сравнивает по ссылке через `Object.is`. Мутация не меняет ссылку - изменение теряется, ререндера нет. Нужно создавать новый объект/массив.</span>

<b class="text-on-semi-light">Когда нужен функциональный апдейтер `setX(prev => ...)`?</b>
<span class="text-gray">Когда следующее значение зависит от предыдущего, особенно при нескольких обновлениях подряд или в асинхронном коде/замыканиях.</span>

<b class="text-on-semi-light">В чём разница controlled и uncontrolled полей?</b>
<span class="text-gray">В controlled значение хранит React state (`value` + `onChange`), в uncontrolled - сам DOM (`defaultValue` + `ref`). Controlled - для валидации и зависимых полей, uncontrolled - для простоты и производительности.</span>

<b class="text-on-semi-light">Что такое SyntheticEvent?</b>
<span class="text-gray">Кросс-браузерная обёртка React над нативным событием с тем же API. React использует делегирование на корень приложения вместо слушателей на каждом узле.</span>

<b class="text-on-semi-light">Что изменилось в батчинге в React 18?</b>
<span class="text-gray">Появился automatic batching: обновления группируются в один ререндер не только в обработчиках, но и в промисах, таймерах, нативных событиях.</span>
