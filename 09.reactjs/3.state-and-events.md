# Состояние и события

Как компонент запоминает данные и как пользователь их меняет: `useState`, снимки состояния, иммутабельные обновления, события React и формы. На mid спрашивают, почему три `setCount(count + 1)` дают +1 и чем управляемое поле отличается от неуправляемого. На senior — почему мутация «иногда работает», как React вешает обработчики и почему `stopPropagation` иногда ломает клики.

::tldr
- **Состояние — память компонента между рендерами.** Обычная переменная живёт один вызов и не вызывает рендер, состояние сохраняется и при изменении запускает рендер.
- **Каждый рендер видит снимок состояния.** Сеттер не меняет переменную, а планирует рендер с новым значением. Если следующее значение зависит от текущего — апдейтер `setX(prev => ...)`.
- **Состояние заменяют, а не мутируют.** React сравнивает по ссылке: мутация с той же ссылкой не даёт рендера, а мутация вложенного объекта портит прошлые снимки и ломает `memo`.
- **React вешает один слушатель на корень приложения**, а не на каждый узел. События всплывают по дереву React, а `onChange` срабатывает на каждый ввод, а не на потерю фокуса.
- **Управляемое поле хранит значение в состоянии, неуправляемое — в DOM.** `value` без `onChange` делает поле нередактируемым, а `value={undefined}` превращает его в неуправляемое.
::

## Переменная или состояние

Сквозной пример темы — список дел:

```jsx
function Todos() {
  const [text, setText] = useState('');
  const [todos, setTodos] = useState([]);

  function handleSubmit(e) {
    e.preventDefault();
    setTodos([...todos, { id: crypto.randomUUID(), title: text, done: false }]);
    setText('');
  }

  return (
    <form onSubmit={handleSubmit}>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <ul>
        {todos.map((t) => <li key={t.id}>{t.title}</li>)}
      </ul>
    </form>
  );
}
```

Почему нельзя обойтись обычной переменной? Попробуем:

```jsx
function Counter() {
  let count = 0;
  return <button onClick={() => count++}>{count}</button>;
}
```

После клика на экране по-прежнему `0`, и для этого есть две причины:

1. **Изменение переменной не запускает рендер.** React не знает, что `count` изменился, и не вызывает компонент.
2. **Переменная не переживает рендер.** Даже если компонент вызовут по другой причине, `let count = 0` выполнится заново.

`useState` решает обе проблемы. Он хранит значение у React, а не в функции, и возвращает пару: текущее значение и сеттер, который просит React отрендерить компонент заново.

> Где именно React хранит это значение и как сопоставляет его с вызовом `useState` — в [Механике хуков](/content/reactjs/hooks-mechanics).

Состояние привязано к месту компонента в дереве. Пока `Todos` отрисован в том же месте, его `todos` живут. Если компонент убрать из дерева и вернуть, состояние начнётся заново (подробно — в [Компонентах и JSX](/content/reactjs/components-and-jsx)).

Значение хранится у React. Но что видит код, который выполняется после вызова сеттера?

## Состояние — это снимок

Внутри одного рендера значение состояния не меняется. Сеттер не переписывает переменную, а планирует следующий рендер, в котором `useState` вернёт новое значение:

```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setCount(count + 1);
    setCount(count + 1);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

После клика будет `1`, а не `3`. В этом рендере `count === 0`, и все три вызова — это `setCount(1)`.

Снимок виден и в асинхронном коде. Функция, созданная в рендере, запоминает значения этого рендера:

```jsx
function handleClick() {
  setCount(count + 1);
  setTimeout(() => alert(count), 3000);
}
```

Если кликнуть дважды, второй `alert` покажет `1`: он создан в рендере, где `count` был `1`, хотя на экране к этому моменту уже `2`. Это не баг, а модель: каждый рендер — отдельный вызов функции со своими константами.

### Апдейтер: когда нужно предыдущее значение

Если новое значение вычисляется из текущего, передают функцию. React вызовет её с самым свежим значением из очереди:

```jsx
function handleClick() {
  setCount((c) => c + 1);
  setCount((c) => c + 1);
  setCount((c) => c + 1); // +3: каждый апдейтер получает результат предыдущего
}
```

Апдейтер нужен, когда:

- в одном обработчике несколько обновлений одного значения;
- обновление происходит в таймере, подписке или после `await` — то есть в функции, которая могла замкнуть старый снимок;
- сеттер передают в дочерний компонент, и тот не должен знать текущее значение.

Если новое значение не зависит от старого (`setText('')`), апдейтер не нужен.

### Батчинг

Обновления внутри одного события React собирает в один рендер. В примере выше `setTodos` и `setText` дают один рендер, а не два. С React 18 так же работают промисы, таймеры и нативные обработчики: два сеттера внутри `setTimeout` — тоже один рендер.

> Как сеттер кладёт апдейт в очередь, когда React пропускает рендер при том же значении и как приоритеты перепроигрывают очередь — в [Механике хуков](/content/reactjs/hooks-mechanics).

Для чисел и строк этого достаточно. Но `todos` — массив объектов, и тут появляется новая ловушка.

## Состояние заменяют, а не мутируют

React сравнивает старое и новое значение через `Object.is`, то есть для объектов и массивов — по ссылке. Мутация оставляет ссылку прежней:

```jsx
todos.push(newTodo);
setTodos(todos);            // та же ссылка → рендера нет

setTodos([...todos, newTodo]); // новый массив → рендер
```

Хуже, когда мутация «иногда работает». Если после неё случается любой другой рендер, мутированные данные появятся на экране, и баг будет выглядеть случайным: в проверке `push` + `setTodos(todos)` ничего не произошло, а следующий корректный `setTodos([...todos, ...])` показал оба добавленных элемента.

### Операции с массивами без мутации

| Нужно | Мутирует (не использовать) | Возвращает новый массив |
| --- | --- | --- |
| добавить | `push`, `unshift` | `[...arr, x]`, `[x, ...arr]` |
| удалить | `splice`, `pop`, `shift` | `filter` |
| заменить элемент | `arr[i] = x` | `map` |
| вставить в середину | `splice` | `[...arr.slice(0, i), x, ...arr.slice(i)]` или `toSpliced` |
| отсортировать, развернуть | `sort`, `reverse` | `toSorted`, `toReversed`, или копия перед `sort` |

### Вложенные объекты

Спред копирует только верхний уровень. Вложенные объекты остаются общими:

```jsx
const next = { ...user };
next.address.city = 'Oslo';  // это тот же address, что и в прошлом состоянии
setUser(next);
```

Экран обновится — ссылка на `user` новая. Но прошлое состояние тоже изменилось: объект `address` у них один. Это ломает всё, что опирается на прошлые значения: «отменить», сравнение в эффекте, `memo`-компонент, которому передают `user.address`. Правильно копировать каждый уровень, который меняется:

```jsx
setUser({ ...user, address: { ...user.address, city: 'Oslo' } });
```

Для глубоких структур помогает Immer: в `produce` пишут «мутирующий» код, а он собирает новые объекты по изменённому пути.

### Мутация и memo

Вернёмся к спискам дел. Отметим задачу выполненной:

```jsx
// ❌ новый массив, но тот же объект задачи
todos[0].done = true;
setTodos([...todos]);

// ✅ новый объект для изменённой задачи
setTodos(todos.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
```

С мутацией `Todos` перерендерится (массив новый), но строка в `memo` получит тот же объект `todo` и пропустит рендер — галочка не появится. Иммутабельность нужна не для красоты: на сравнении ссылок держатся `memo`, зависимости эффектов и React Compiler.

> Какое состояние вообще не нужно хранить, а можно вычислить, и куда его поднимать — в [Производном состоянии и потоке данных](/content/reactjs/derived-state-and-data-flow).

Данные готовы. Теперь — откуда приходят изменения: события.

## События

В JSX обработчик передают как функцию в prop с именем в camelCase: `onClick`, `onSubmit`, `onChange`. Передают **функцию**, а не её вызов: `onClick={handleClick}`, а не `onClick={handleClick()}` — второе вызовет обработчик во время рендера.

Обработчик получает объект события React (SyntheticEvent). У него тот же API, что у нативного: `target`, `currentTarget`, `preventDefault()`, `stopPropagation()`. Нативное событие доступно в `e.nativeEvent`.

### Делегирование: один слушатель на корень

React не вешает слушатель на каждую кнопку. При `createRoot(container)` он регистрирует на контейнере слушатели всех событий — для фазы погружения и для всплытия. Когда нативное событие доходит до контейнера, React находит fiber узла, на котором оно случилось, и сам проходит по дереву React, вызывая обработчики `onClickCapture` сверху вниз и `onClick` снизу вверх.

Из этого следуют вещи, которые спрашивают на senior:

- **Всплытие идёт по дереву React, а не DOM.** Для обычной разметки это одно и то же. Для порталов — нет: клик внутри модалки, отрисованной в `document.body`, всплывает до React-родителя модалки. Подробно — в [Refs, порталах и доступности](/content/reactjs/refs-portals-a11y).
- **Нативный `stopPropagation` ниже корня глушит React.** Если сторонний скрипт повесил на промежуточный DOM-узел слушатель с `e.stopPropagation()`, событие не дойдёт до контейнера, и React-обработчики не вызовутся.
- **`e.stopPropagation()` в React останавливает всплытие по дереву React.** Обработчики родителей с `onClick` не вызовутся, но `onClickCapture` родителей уже отработали.
- **Несколько корней на странице не мешают друг другу:** с React 17 слушатели висят на контейнере корня, а не на `document`.

### Отличия от DOM

- **`onChange` срабатывает на каждый ввод.** В DOM событие `change` у текстового поля приходит при потере фокуса, а React-овский `onChange` слушает событие `input`. Поэтому управляемые поля обновляются по каждой букве.
- **`onScroll` не всплывает** — как и в браузере. До React 17 родитель получал `onScroll` от прокрутки дочернего блока.
- **Пулинга событий нет.** До React 17 объект события переиспользовался и обнулялся после обработчика, поэтому читать его асинхронно было нельзя (`e.persist()`). Сейчас это обычный объект.

События меняют состояние. Особый случай — поля форм, где у значения два возможных хозяина.

## Управляемые и неуправляемые поля

У поля ввода своё состояние в DOM — текущее значение. Вопрос в том, кто источник истины: React или DOM.

**Управляемое поле** (controlled) получает значение из состояния и сообщает об изменениях через `onChange`:

```jsx
<input value={text} onChange={(e) => setText(e.target.value)} />
```

Источник истины — React. После каждого ввода React возвращает DOM значение из `value`. Поэтому управляемое поле можно форматировать на лету: `setText(e.target.value.toUpperCase())` — и пользователь сразу видит заглавные буквы.

**Неуправляемое поле** (uncontrolled) хранит значение само, а React читает его, когда нужно:

```jsx
function Search() {
  const inputRef = useRef(null);
  return (
    <form onSubmit={(e) => { e.preventDefault(); search(inputRef.current.value); }}>
      <input ref={inputRef} defaultValue="" />
    </form>
  );
}
```

| | Управляемое | Неуправляемое |
| --- | --- | --- |
| Источник истины | состояние React | DOM |
| Начальное значение | `value` | `defaultValue` |
| Чтение | из состояния | через `ref` или `FormData` |
| Подходит для | валидация на лету, форматирование, зависимые поля | простые формы, файлы, интеграция с не-React кодом |

Управляемое поле — это рендер на каждую букву. Для одной формы это неважно, для формы на сотню полей — заметно, поэтому библиотеки вроде react-hook-form построены на неуправляемых полях. `<input type="file">` всегда неуправляемый: его значение нельзя задать из кода. А в React 19 формы с `action` читают значения через `FormData`, и поля можно не держать в состоянии вовсе — подробно в [RSC и React 19](/content/reactjs/rsc-and-react-19).

### Два частых бага

- **`value` без `onChange`.** React предупреждает `You provided a value prop to a form field without an onChange handler` и после каждого ввода возвращает значение из props — поле выглядит сломанным. Нужен `onChange`, `readOnly` или `defaultValue`.
- **`value={undefined}`.** Пока значение `undefined`, поле неуправляемое. Когда приходит строка, оно становится управляемым, и React предупреждает `A component is changing an uncontrolled input to be controlled`. Начальное значение должно быть строкой: `value={name ?? ''}`.

---

## Красные флаги в ответе

- **«`setState` асинхронный, поэтому значение не обновилось».** Значение — константа рендера, сеттер планирует следующий рендер. После `await` переменная тоже останется старой.
- **«Мутировать можно, если потом вызвать сеттер».** С той же ссылкой рендера не будет. С новой внешней ссылкой рендер будет, но прошлые снимки испорчены и `memo`-дети не обновятся.
- **«React вешает обработчик на каждый элемент».** Один слушатель на корневой контейнер, дальше React сам проходит по своему дереву.
- **«`onChange` — то же, что DOM-событие `change`».** React-овский `onChange` срабатывает на каждый ввод.
- **«Управляемые поля всегда лучше».** Они дают рендер на каждый ввод. Для больших форм и файлов берут неуправляемые поля или `FormData`.

## Как спрашивают на собеседовании

::question{level="mid"}
Почему три `setCount(count + 1)` подряд увеличивают счётчик на 1, а не на 3?

#mid
`count` — снимок текущего рендера, он не меняется после вызова сеттера. Все три вызова — это `setCount(1)`. Чтобы получить +3, нужен апдейтер `setCount(c => c + 1)`: каждый получает результат предыдущего.

#senior
Сеттер кладёт апдейт в очередь хука и планирует рендер, все три апдейта применяются по порядку в одном рендере. Значение `1` трижды даёт `1`, апдейтеры дают `1 → 2 → 3`. Та же модель объясняет, почему функция в `setTimeout` после клика видит старое значение: она замкнула снимок своего рендера.

#followups
- «Как увидеть новое значение сразу после сеттера?» → посчитать его в переменной (`const next = count + 1`) и использовать её; новое состояние доступно только в следующем рендере
::

::question{level="mid"}
Почему нельзя мутировать состояние напрямую?

#mid
React сравнивает старое и новое значение по ссылке через `Object.is`. Мутация не меняет ссылку, поэтому React считает, что ничего не изменилось, и рендера нет. Нужен новый объект или массив.

#senior
Мутация опасна и тогда, когда рендер всё-таки происходит. Мутированные данные «всплывают» при следующем постороннем рендере, и баг выглядит случайным. Мутация вложенного объекта при поверхностной копии меняет и прошлые снимки: ломаются «отменить», сравнения в эффектах и `memo`-дети, которые получают тот же вложенный объект. На сравнении ссылок держатся `memo`, deps и React Compiler.
::

::question{level="mid"}
Когда нужен функциональный апдейтер `setX(prev => ...)`?

#mid
Когда новое значение зависит от предыдущего: несколько обновлений подряд, обновление в таймере, подписке или после `await`.

#senior
Апдейтер не зависит от замкнутого значения, поэтому снимает проблему stale closure: эффект с `[]` и `setCount(c => c + 1)` в интервале работает правильно. Он позволяет не класть значение в deps эффекта и передавать сеттер детям без текущего значения. Апдейтеры должны быть чистыми: React может вызвать их повторно при перепроигрывании очереди.
::

::question{level="mid"}
Чем управляемое поле отличается от неуправляемого?

#mid
В управляемом значение хранится в состоянии React (`value` + `onChange`), в неуправляемом — в самом DOM (`defaultValue`, чтение через `ref`). Управляемые — для валидации и форматирования на лету, неуправляемые — для простых форм и файлов.

#senior
Управляемое поле после каждого ввода получает значение обратно из `value`, поэтому его можно форматировать и ограничивать, но это рендер на каждую букву. Ошибки: `value` без `onChange` (поле не редактируется) и `undefined` в `value` (переход между режимами с предупреждением). React 19 добавил формы с `action`, где значения читаются из `FormData`, и состояние полей часто не нужно.
::

::question{level="senior"}
Как React обрабатывает события? Что такое SyntheticEvent?

#mid
SyntheticEvent — кроссбраузерная обёртка React над нативным событием с тем же API. React не вешает обработчики на каждый элемент, а использует делегирование.

#senior
При `createRoot` React регистрирует на контейнере слушатели всех событий в обеих фазах. Когда событие доходит до контейнера, React находит fiber цели и проходит по дереву React: `onXCapture` сверху вниз, `onX` снизу вверх. Поэтому всплытие идёт по дереву React — клик в портале всплывает до React-родителя. Нативный `stopPropagation` на промежуточном DOM-узле не даёт событию дойти до контейнера, и React-обработчики не срабатывают.

#followups
- «Почему с React 17 слушатели на корне, а не на `document`?» → чтобы несколько версий React и несколько корней на странице не мешали друг другу
::

::question{level="mid"}
Что изменилось в батчинге в React 18?

#mid
Появился автоматический батчинг: обновления состояния собираются в один рендер не только в обработчиках событий React, но и в промисах, таймерах и нативных обработчиках.

#senior
До React 18 батчинг работал только внутри обработчиков React, а в `setTimeout` и после `await` каждый сеттер давал отдельный рендер. С `createRoot` батчинг везде. Выйти из него можно через `flushSync` — например, чтобы DOM обновился до прокрутки к новому элементу. Это дорого и нужно редко.
::

::question{level="senior"}
Почему клик по кнопке перестал работать после подключения стороннего скрипта?

#mid
Скорее всего, скрипт останавливает всплытие события. Обработчики React работают через делегирование и не получат событие, если оно не дошло до корня.

#senior
React слушает события на корневом контейнере. Если сторонний код повесил на промежуточный DOM-узел слушатель с `stopPropagation()` (или `stopImmediatePropagation()` на том же узле), нативное событие не доходит до контейнера, и React-обработчики не вызываются. Диагностика — Event Listeners в DevTools на узлах между целью и корнем. Обратная ситуация: слушатель на `document` (например, «закрыть меню по клику снаружи») срабатывает после React-обработчиков, потому что корень лежит ниже `document`. А `e.stopPropagation()` в React-обработчике останавливает и нативное всплытие от корня, поэтому такой слушатель не получит событие.
::

## Практика

::practice{title="Что покажет alert?"}
```jsx
function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    setTimeout(() => alert(count), 3000);
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

Пользователь быстро кликает дважды. Что будет на экране и что покажут два `alert`?

#solution
На экране `2`, `alert` покажут `0` и `1`. Каждый клик выполняется в своём рендере: первый в рендере с `count === 0`, второй — с `count === 1`. Функция в `setTimeout` замкнула значение своего рендера.

Если через три секунды нужно актуальное значение, его хранят там, где оно не зависит от снимка, — в ref, который обновляется после каждого commit:

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  const latest = useRef(count);

  useEffect(() => {
    latest.current = count;
  });

  function handleClick() {
    setCount(count + 1);
    setTimeout(() => alert(latest.current), 3000); // актуальное значение
  }

  return <button onClick={handleClick}>{count}</button>;
}
```

Чаще это знак, что логика с задержкой должна жить в эффекте или в обработчике, который получает значение аргументом, а не читает его из замыкания.
::

::practice{title="Галочка не ставится"}
Строки списка обёрнуты в `memo`. После клика по задаче массив обновляется, но галочка не появляется:

```jsx
const Row = memo(function Row({ todo, onToggle }) {
  return <li onClick={() => onToggle(todo.id)}>{todo.done ? '✓' : '○'} {todo.title}</li>;
});

function Todos() {
  const [todos, setTodos] = useState(initial);

  function toggle(id) {
    const todo = todos.find((t) => t.id === id);
    todo.done = !todo.done;
    setTodos([...todos]);
  }

  return <ul>{todos.map((t) => <Row key={t.id} todo={t} onToggle={toggle} />)}</ul>;
}
```

#solution
Массив новый, поэтому `Todos` рендерится. Но объект задачи тот же, только мутированный, а `memo` сравнивает props по ссылке: `todo` не изменился с его точки зрения, и строка пропускает рендер. На экране старый кружок.

Фикс — новый объект для изменённой задачи:

```jsx
function toggle(id) {
  setTodos((list) => list.map((t) => (t.id === id ? { ...t, done: !t.done } : t)));
}
```

Теперь строка получает новый `todo` и рендерится. Апдейтер здесь — плюс: `toggle` не зависит от снимка `todos`, и его можно стабилизировать для `memo` без пересоздания.
::

::practice{title="Поле не даёт ввести текст"}
Форма профиля загружает пользователя асинхронно. В консоли предупреждение, а в одной версии поле вообще не редактируется:

```jsx
// версия 1
function Name({ user }) {
  return <input value={user.name} />;
}

// версия 2
function Name({ user }) {
  const [name, setName] = useState(user?.name);
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}
```

#solution
**Версия 1:** `value` без `onChange`. React предупреждает `You provided a value prop to a form field without an onChange handler` и после каждого ввода возвращает значение из props — поле не редактируется. Нужен `onChange` с состоянием, `readOnly` для поля только для чтения или `defaultValue`, если поле неуправляемое.

**Версия 2:** пока пользователь не загружен, `name` равен `undefined`, и поле неуправляемое. После первого ввода значение становится строкой, и React предупреждает `A component is changing an uncontrolled input to be controlled`.

Фикс — всегда строка в `value`:

```jsx
function Name({ user }) {
  const [name, setName] = useState(user?.name ?? '');
  return <input value={name} onChange={(e) => setName(e.target.value)} />;
}
```

Если пользователь приходит позже первого рендера, `useState` уже не подхватит его имя: начальное значение читается только при монтировании. Тогда форму монтируют после загрузки или сбрасывают через `key={user.id}`.
::
