# Тестирование React

Как тестировать React-компоненты так, чтобы тесты ловили баги, а не ломались от рефакторинга: React Testing Library, запросы по ролям, асинхронность и `act`, пользовательские события, сеть через MSW и провайдеры. Спрашивают разницу `getBy`, `queryBy` и `findBy` и почему `getByRole` лучше `data-testid`. Глубже — что на самом деле означает предупреждение про `act`, чем `userEvent` отличается от `fireEvent`, почему тест ошибки загрузки падает по таймауту и как тестировать то, что React Testing Library не умеет рендерить.

::tldr
- **Тест проверяет поведение, а не реализацию.** Он смотрит на DOM глазами пользователя и не должен ломаться, если поведение не изменилось. React Testing Library намеренно не даёт доступа к состоянию и props.
- **Элементы ищут как пользователь:** сначала `getByRole` с доступным именем, потом `getByLabelText`, `getByText`, и только в крайнем случае `getByTestId`. Если элемент не находится по роли, это часто проблема доступности.
- **`getBy` бросает, `queryBy` возвращает `null`, `findBy` ждёт.** Асинхронное поведение проверяют через `findBy` и `waitFor`, а предупреждение `not wrapped in act` значит, что обновление случилось, когда тест его уже не ждал.
- **`userEvent` воспроизводит действие целиком** — фокус, клавиши, ввод, а `fireEvent` отправляет одно событие. По умолчанию — `userEvent`.
- **Сеть мокают на уровне сети через MSW**, а не модуль загрузки. Тестовый клиент TanStack Query создают без повторов, иначе ошибка не успеет появиться.
::

## Что значит хороший тест

Сквозной пример — карточка товара: название, цена, поле количества и кнопка «В корзину», которая отправляет запрос.

Есть два способа проверить, что кнопка работает. Первый — заглянуть внутрь: вызвать обработчик, проверить, что состояние `quantity` стало 2, что `addToCart` вызван с нужными аргументами. Второй — сделать то, что делает пользователь: ввести 2, нажать «В корзину», увидеть «Добавлено».

Первый тест сломается, если переименовать состояние, вынести логику в хук или заменить `useState` на `useReducer`, — хотя для пользователя ничего не изменилось. Второй сломается, только если сломалось поведение. Отсюда принцип React Testing Library:

> Чем больше тест похож на то, как пользуются программой, тем больше уверенности он даёт. — Kent C. Dodds

Поэтому библиотека рендерит компонент в настоящий DOM (jsdom) и даёт искать элементы только так, как их находит пользователь: по роли, подписи, тексту. Доступа к состоянию, props и экземпляру компонента нет — специально.

> Пирамида тестов, раннеры, покрытие и TDD — общие темы, они разобраны в главе [Тестирование и деплой](/content/testing-deploying). Здесь — то, что специфично для React.

## Как искать элементы

```jsx
test('добавляет товар в корзину', async () => {
  const user = userEvent.setup();
  render(<ProductCard product={teapot} />);

  await user.clear(screen.getByRole('spinbutton', { name: 'Количество' }));
  await user.type(screen.getByRole('spinbutton', { name: 'Количество' }), '2');
  await user.click(screen.getByRole('button', { name: 'В корзину' }));

  expect(await screen.findByText('Добавлено: 2 шт.')).toBeInTheDocument();
});
```

Запросы выбирают в порядке того, как элемент воспринимает пользователь и скринридер:

| Приоритет | Запрос | Для чего |
| --- | --- | --- |
| 1 | `getByRole('button', { name })` | почти всё: кнопки, поля, ссылки, заголовки, диалоги |
| 2 | `getByLabelText` | поля формы по подписи |
| 3 | `getByPlaceholderText`, `getByText`, `getByDisplayValue` | некликабельный текст, значения полей |
| 4 | `getByAltText`, `getByTitle` | картинки и подсказки |
| 5 | `getByTestId` | когда иначе не достать |

`getByRole` — запрос по умолчанию по двум причинам. Он устойчив: роль и доступное имя кнопки меняются, только если меняется смысл интерфейса. И он проверяет доступность: `<div onClick>` с текстом «Купить» не найдётся как кнопка — в проверке `queryByRole('button', { name: 'Купить' })` вернул `null`. Если тест не может найти элемент по роли, скорее всего, скринридер тоже не может (подробно — в [Refs, порталах и доступности](/content/reactjs/refs-portals-a11y)).

### get, query, find

| Вариант | Если не найдено | Для чего |
| --- | --- | --- |
| `getBy…` | бросает ошибку с деревом DOM | элемент должен быть сейчас |
| `queryBy…` | возвращает `null` | проверить, что элемента **нет** |
| `findBy…` | промис, ждёт до 1 секунды | элемент появится позже |

```jsx
expect(screen.queryByRole('alert')).not.toBeInTheDocument();      // ошибки нет
expect(await screen.findByText('Добавлено: 2 шт.')).toBeInTheDocument(); // появится после ответа
```

`getBy` для отсутствующего элемента бросает `Unable to find an element with the text: ...` и выводит текущий DOM — это лучшая подсказка при отладке. Поэтому `getBy` не оборачивают в `try/catch`, а для проверки отсутствия берут `queryBy`.

Элемент найден. Дальше с ним нужно взаимодействовать — и здесь первая развилка.

## userEvent и fireEvent

`fireEvent` отправляет **одно** DOM-событие:

```jsx
fireEvent.change(input, { target: { value: '2' } });
```

`userEvent` воспроизводит **действие** так, как его делает браузер: наведение, фокус, `keydown`, `keypress`, `input`, `keyup` для каждой клавиши, проверка, что по элементу вообще можно кликнуть (например, у него нет `pointer-events: none`).

```jsx
const user = userEvent.setup();
await user.type(input, '2');
```

В проверке `fireEvent.change` поменял значение поля, но обработчик `onKeyDown` не вызвался ни разу. `userEvent.type` вызвал его на каждую букву. Если в компоненте есть логика на клавишах (Enter отправляет, Escape закрывает, маска ввода), `fireEvent.change` её пропустит, и тест будет зелёным при сломанном поведении.

`userEvent` асинхронный — его вызовы нужно ждать через `await`. `fireEvent` оставляют для событий, которые пользователь не вызывает напрямую: `scroll`, `resize`, события медиа.

После клика компонент отправит запрос и обновит экран позже. Как тест должен этого дождаться?

## Асинхронность и act

### act

Обновление состояния в React не применяется мгновенно: React планирует рендер, а эффекты выполняет после commit. В тестах это означает, что сразу после клика DOM может быть ещё старым. `act` решает это: всё, что происходит внутри `act`, React применяет до выхода из него — рендеры, эффекты, микрозадачи.

React Testing Library оборачивает в `act` всё сама: `render`, события `userEvent` и `fireEvent`, ожидание в `findBy` и `waitFor`. Поэтому `act` вручную пишут редко — например, при вызове методов хука в `renderHook`.

Предупреждение

```text
An update to Component inside a test was not wrapped in act(...)
```

означает: состояние обновилось, когда тест этого не ждал. Обычно это ответ сервера или таймер, который сработал после последней проверки. В проверке компонент с `setTimeout` в эффекте дал это предупреждение, когда тест ждал таймер обычным `setTimeout`, вне `act`. Лечится не оборачиванием всего подряд в `act`, а ожиданием результата, который это обновление показывает:

```jsx
expect(await screen.findByText('Добавлено: 2 шт.')).toBeInTheDocument();
```

### waitFor и findBy

`findBy` — это `waitFor` плюс `getBy`: повторяет поиск, пока элемент не появится или не выйдет время (1 секунда по умолчанию). `waitFor` нужен для проверок, которые не сводятся к поиску элемента:

```jsx
await waitFor(() => expect(analytics.track).toHaveBeenCalledWith('add_to_cart'));
```

Внутри `waitFor` — только проверки, без действий: колбэк вызывается много раз, и клик внутри него нажмётся много раз.

Взаимодействие и ожидание разобраны. Осталось главное — откуда в тесте берутся данные.

## Сеть: MSW вместо моков fetch

Карточка товара загружает остатки на складе и отправляет запрос «в корзину». Мокать для этого `fetch` или модуль `api` плохо: тест знает, *чем* компонент ходит в сеть. Перешли с `fetch` на клиент с кешем — тесты сломались, хотя поведение то же.

MSW (Mock Service Worker) перехватывает запросы на уровне сети: в браузере — через Service Worker, в Node — через перехват `fetch` и модулей `http`. Компонент делает настоящий запрос и получает ответ, который описан в тесте:

```jsx
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users/1', () => HttpResponse.json({ name: 'Аня' })),
);

beforeAll(() => server.listen({ onUnhandledRequest: 'error' }));
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test('показывает ошибку, если сервер упал', async () => {
  server.use(http.get('/api/users/1', () => new HttpResponse(null, { status: 500 })));
  renderWithClient(<User id={1} />);
  expect(await screen.findByRole('alert')).toHaveTextContent('Не удалось загрузить');
});
```

`onUnhandledRequest: 'error'` роняет тест на запросе без обработчика: забытый эндпоинт не уйдёт в реальную сеть. `server.use` переопределяет ответ в одном тесте, а `resetHandlers` возвращает исходные. Те же обработчики можно использовать в Storybook и при локальной разработке.

> Виды тестовых двойников и когда мок лучше, а когда хуже — в [Моках и тестовых двойниках](/content/testing-deploying/mocking-and-test-doubles).

## Провайдеры и тестовая обвязка

Компоненты редко живут сами по себе: им нужны роутер, клиент запросов, тема, стор. Вместо копирования провайдеров в каждый тест делают свою функцию рендера:

```jsx
function renderWithProviders(ui, { route = '/' } = {}) {
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });
  const router = createMemoryRouter([{ path: '*', element: ui }], { initialEntries: [route] });

  return render(
    <QueryClientProvider client={queryClient}>
      <RouterProvider router={router} />
    </QueryClientProvider>,
  );
}
```

Две детали, на которых спотыкаются:

- **Новый клиент запросов на каждый тест.** Общий клиент переносит кеш между тестами: второй тест получит данные первого и не сделает запрос.
- **`retry: false`.** По умолчанию TanStack Query повторяет упавший запрос 3 раза с растущей паузой (подробно — в [Загрузке данных](/content/reactjs/data-fetching)). В проверке тест ошибки с клиентом по умолчанию не дождался `role="alert"` за секунду — `findByRole` упал по таймауту, хотя компонент работает правильно. С `retry: false` ошибка появилась сразу.

### Хуки

Кастомный хук нельзя вызвать вне компонента. `renderHook` рендерит его внутри тестового компонента:

```jsx
const { result } = renderHook(() => useCounter());
act(() => result.current.increment());
expect(result.current.count).toBe(1);
```

Если хук используется в одном компоненте, тест компонента обычно лучше: он проверяет поведение, а не API хука. `renderHook` нужен для хуков, которые сами являются продуктом — в библиотеке или дизайн-системе.

## Что React Testing Library не покрывает

- **Server Components.** Async-компонент нельзя отрендерить на клиенте — React сообщит, что `is an async Client Component. Only Server Components can be async`. Серверные компоненты проверяют e2e-тестами или выносят логику в функции и тестируют их отдельно.
- **Настоящий браузер.** jsdom не считает раскладку: размеры, прокрутка, `IntersectionObserver`, CSS-анимации не работают. Для этого — компонентные тесты в браузере (Vitest Browser Mode, Playwright Component Testing) или e2e.
- **Визуальные регрессии.** Снимки DOM (`toMatchSnapshot`) ломаются от любой правки разметки и обычно обновляются не глядя. Внешний вид проверяют скриншотами — подробно в [Визуальном и компонентном тестировании](/content/testing-deploying/visual-and-component-testing).

Основная масса тестов React-приложения — интеграционные тесты компонентов через React Testing Library: они дают лучшее соотношение уверенности и стоимости. Чистую логику проверяют unit-тестами, ключевые сценарии целиком — e2e в браузере (подробно — в [E2E-тестировании](/content/testing-deploying/e2e-testing)).

## Красные флаги в ответе

- **«Проверю, что состояние стало `true`».** Тест реализации ломается от рефакторинга. Проверяют то, что видит пользователь.
- **«Повешу `data-testid` на всё».** Это последнее средство. `getByRole` устойчивее и заодно проверяет доступность.
- **«Предупреждение про `act` убираю, оборачивая всё в `act`».** Предупреждение говорит о недождавшемся обновлении. Нужно дождаться его результата через `findBy` или `waitFor`.
- **«`fireEvent` и `userEvent` — одно и то же».** `fireEvent` отправляет одно событие, `userEvent` — всю последовательность, как в браузере.
- **«Замокаю `fetch` через `jest.fn`».** Тест привязан к способу загрузки. MSW мокает сеть, и тест переживает смену клиента.

## Как спрашивают на собеседовании

::question
Какой главный принцип React Testing Library?

#answer
Тестировать поведение так, как им пользуется пользователь, а не детали реализации. Тест смотрит на DOM, а не на состояние и props, поэтому не ломается при рефакторинге без изменения поведения.

#more
Библиотека намеренно не даёт доступа к экземпляру, состоянию и props компонента — только к DOM. Это смещает фокус на интеграционные тесты: компонент с детьми, хуками и провайдерами проверяется как единое целое. Цена — тесты медленнее unit-тестов и требуют обвязки (провайдеры, MSW), зато ловят баги на стыках, которые unit-тесты пропускают.
::

::question
Почему getByRole предпочтительнее getByTestId?

#answer
`getByRole` ищет элемент так, как его воспринимают пользователь и скринридер — по роли и доступному имени. Это устойчиво к изменениям разметки и заодно проверяет доступность. `data-testid` — последнее средство.

#more
Если элемент не находится по роли, это обычно проблема доступности: `<div onClick>` не кнопка ни для теста, ни для скринридера. `testid` привязывает тест к разметке, а не к смыслу, и не говорит ничего о том, как элемент доступен. Его оставляют для элементов без семантики — например, контейнера графика.
::

::question
В чём разница getBy, queryBy и findBy?

#answer
`getBy` бросает ошибку, если элемента нет, — для того, что должно быть сейчас. `queryBy` возвращает `null` — для проверки отсутствия. `findBy` возвращает промис и ждёт появления — для асинхронного.

#more
`findBy` — это `waitFor` плюс `getBy`, по умолчанию с таймаутом в 1 секунду. Ошибка `getBy` выводит текущий DOM, поэтому её не глушат `try/catch`. Варианты `getAllBy` и `findAllBy` для нескольких элементов. Внутри `waitFor` — только проверки, без действий: колбэк вызывается многократно.
::

::question
Что означает предупреждение «not wrapped in act»?

#answer
Состояние компонента обновилось, когда тест этого не ждал, — обычно после ответа сервера или таймера. Нужно дождаться результата через `findBy` или `waitFor`.

#more
`act` гарантирует, что рендеры, эффекты и микрозадачи применены до проверок. React Testing Library оборачивает в него `render`, события и ожидания. Предупреждение появляется, когда обновление случилось вне этих границ — тест закончился или проверял раньше. Оборачивать всё в `act` вручную — способ спрятать проблему: тест может проверить промежуточное состояние. Правильно — ждать видимого результата обновления.
::

::question
Чем userEvent отличается от fireEvent?

#answer
`fireEvent` отправляет одно DOM-событие. `userEvent` воспроизводит действие пользователя целиком: фокус, нажатия клавиш, ввод, отпускание. По умолчанию используют `userEvent`.

#more
`fireEvent.change` меняет значение поля, но не вызывает `keydown` — логика на клавишах (Enter, Escape, маски) не проверяется. `userEvent` проверяет и ограничения браузера: клик по элементу с `pointer-events: none` бросит ошибку, как и в браузере клик туда не попадёт. Он асинхронный, вызовы ждут через `await`. `fireEvent` оставляют для событий без прямого действия пользователя: `scroll`, `resize`.
::

::question
Почему тест ошибки загрузки падает по таймауту?

#answer
Скорее всего, библиотека запросов повторяет упавший запрос. TanStack Query по умолчанию делает 3 повтора с растущей паузой, и ошибка не успевает появиться за секунду ожидания `findBy`.

#more
В тестовом клиенте выключают повторы: `new QueryClient({ defaultOptions: { queries: { retry: false } } })`. Клиент создают заново в каждом тесте, иначе кеш переносится между тестами. Обвязку выносят в функцию `renderWithProviders`, чтобы не повторять провайдеры. Сеть мокают через MSW с `onUnhandledRequest: 'error'`, чтобы забытый эндпоинт не ушёл в реальную сеть.
::

::question
Почему MSW лучше мока fetch?

#answer
MSW мокает на уровне сети, а не реализации. Компонент делает настоящий запрос, а тест не зависит от того, чем именно компонент ходит в сеть, — fetch, axios или библиотека запросов.

#more
Мок модуля или `fetch` повторяет устройство кода, и тест ломается при рефакторинге без изменения поведения. MSW описывает API: те же обработчики работают в тестах, в Storybook и при локальной разработке. `server.use` подменяет ответ в одном тесте, `resetHandlers` возвращает исходные, а `onUnhandledRequest: 'error'` ловит неописанные запросы.
::

## Практика

::practice{title="Перепиши тест"}
Тест проверяет реализацию и ломается при каждом рефакторинге. Перепиши его так, чтобы он проверял поведение:

```jsx
test('счётчик корзины', () => {
  const { container } = render(<CartButton />);
  const button = container.querySelector('.cart-btn');
  fireEvent.click(button);
  expect(container.querySelector('.cart-btn__count').textContent).toBe('1');
  expect(screen.getByTestId('cart-state').dataset.items).toBe('1');
});
```

#solution
Тест ищет по CSS-классам и `testid` и проверяет внутренний атрибут состояния. Переименование класса или перенос счётчика в хук сломает тест без изменения поведения.

```jsx
test('добавляет товар в корзину', async () => {
  const user = userEvent.setup();
  render(<CartButton />);

  await user.click(screen.getByRole('button', { name: 'В корзину' }));

  expect(screen.getByRole('status')).toHaveTextContent('В корзине: 1');
});
```

Кнопка ищется по роли и имени, клик — через `userEvent`, проверка — по тому, что видит пользователь. Если для счётчика нет роли, это повод добавить `role="status"` или подпись: тогда изменение объявит и скринридер.
::

::practice{title="Почему тест ошибки падает?"}
Компонент показывает ошибку, если сервер вернул 500. В приложении работает, а тест падает с `Unable to find role="alert"`:

```jsx
const queryClient = new QueryClient();

function renderWithClient(ui) {
  return render(<QueryClientProvider client={queryClient}>{ui}</QueryClientProvider>);
}

test('показывает ошибку', async () => {
  server.use(http.get('/api/users/1', () => new HttpResponse(null, { status: 500 })));
  renderWithClient(<User id={1} />);
  expect(await screen.findByRole('alert')).toHaveTextContent('Не удалось загрузить');
});
```

#solution
Две проблемы.

1. **Повторы.** Клиент по умолчанию повторяет упавший запрос 3 раза с паузами 1, 2 и 4 секунды. Ошибка появится через 7 секунд, а `findByRole` ждёт одну. В проверке с клиентом по умолчанию поиск упал по таймауту, а с `retry: false` ошибка появилась сразу.
2. **Общий клиент.** Он создан один раз на файл, и кеш переходит из теста в тест: если раньше был тест с успешным ответом, этот получит данные из кеша и не сделает запрос вовсе.

```jsx
function renderWithClient(ui) {
  const queryClient = new QueryClient({
    defaultOptions: { queries: { retry: false } },
  });
  return render(<QueryClientProvider client={queryClient}>{ui}</QueryClientProvider>);
}
```

Новый клиент без повторов на каждый тест — стандартная обвязка для компонентов с TanStack Query.
::
