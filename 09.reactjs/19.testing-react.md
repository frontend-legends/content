# Тестирование React

Тестирование React-компонентов строится вокруг одной идеи: **тестируй поведение, а не реализацию**. Тест должен проверять то, что видит и делает пользователь, а не внутреннее состояние или названия методов. Это философия React Testing Library и главный тезис на собесе.

> Деплой, CI и e2e-инструменты подробно - в главе [тестирование и деплой](/content/testing-deploying). Здесь - React-специфика.

---

## Философия: behavior over implementation

```
"The more your tests resemble the way your software is used,
 the more confidence they can give you." — Kent C. Dodds
```

- **Хороший тест** не сломается при рефакторинге, если поведение не изменилось.
- **Хрупкий тест** проверяет внутренности (имя стейта, число рендеров) и падает от любого изменения кода.

Поэтому RTL принципиально **не даёт** доступа к state/props компонента - только к тому, что видно в DOM.

---

## React Testing Library

Рендерит компонент в jsdom и даёт искать элементы так, как их находит пользователь.

```jsx
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';

test('счётчик увеличивается по клику', async () => {
  render(<Counter />);

  const button = screen.getByRole('button', { name: /increment/i });
  await userEvent.click(button);

  expect(screen.getByText('1')).toBeInTheDocument();
});
```

`render` монтирует компонент, `screen` ищет элементы, `userEvent` имитирует реальные действия пользователя (клики, ввод).

---

## Приоритет запросов

RTL предлагает искать элементы в порядке «как это делает пользователь и скринридер». Это напрямую завязано на доступность.

| Приоритет | Запрос | Когда |
|-----------|--------|-------|
| 1 | `getByRole` | почти всегда - кнопки, поля, заголовки (по роли + имени) |
| 2 | `getByLabelText` | поля форм |
| 3 | `getByText` | некликабельный текст |
| 4 | `getByTestId` | крайний случай, когда иначе не достать |

<b class="text-on-semi-light">getByRole - выбор по умолчанию</b> - <span class="text-gray">Если до элемента нельзя добраться по роли - часто это сигнал проблемы с доступностью. `data-testid` - последнее средство, а не первое.</span>

### Варианты: get / query / find

- `getBy...` - бросает ошибку, если не найдено (для того, что должно быть).
- `queryBy...` - возвращает `null` (для проверки **отсутствия**).
- `findBy...` - возвращает промис, ждёт появления (для **асинхронного**).

```jsx
expect(screen.queryByText('Ошибка')).not.toBeInTheDocument(); // нет ошибки
expect(await screen.findByText('Загружено')).toBeInTheDocument(); // появится позже
```

## Асинхронность и act

Многое в React происходит асинхронно: загрузка данных, эффекты, обновления состояния. `findBy*` и `waitFor` ждут результата.

```jsx
test('показывает пользователя после загрузки', async () => {
  render(<User id="1" />);
  expect(screen.getByText(/loading/i)).toBeInTheDocument();
  expect(await screen.findByText('Аня')).toBeInTheDocument(); // дождались
});
```

<b class="text-on-semi-light">Что такое act?</b> - <span class="text-gray">`act()` гарантирует, что все обновления состояния и эффекты применились перед проверкой - иначе тест увидит промежуточное состояние. RTL **оборачивает свои методы в act автоматически**, поэтому вручную его пишут редко. Warning «not wrapped in act» обычно значит асинхронное обновление, которое тест не дождался - лечится `findBy`/`waitFor`.</span>

## Тестирование хуков

Кастомный хук нельзя вызвать вне компонента. `renderHook` рендерит его в тестовом компоненте.

```jsx
import { renderHook, act } from '@testing-library/react';

test('useCounter', () => {
  const { result } = renderHook(() => useCounter());
  act(() => result.current.increment());
  expect(result.current.count).toBe(1);
});
```

> Если хук используется внутри одного компонента - часто лучше тестировать сам компонент через RTL, а не хук изолированно.

## Моки и сеть

Запросы не должны бить в реальный бэкенд. Лучший подход - **MSW (Mock Service Worker)**: перехватывает запросы на сетевом уровне, тест не знает, что ответ замокан.

```jsx
import { http, HttpResponse } from 'msw';
import { setupServer } from 'msw/node';

const server = setupServer(
  http.get('/api/users/1', () => HttpResponse.json({ name: 'Аня' }))
);
```

<b class="text-on-semi-light">Почему MSW лучше мока fetch</b> - <span class="text-gray">Мок `fetch`/модуля завязан на реализацию (чем именно грузят данные). MSW мокает на уровне сети - тест не меняется при переходе с `fetch` на axios или React Query.</span>

## Пирамида тестов

| Тип | Что проверяет | Инструмент |
|-----|---------------|-----------|
| Unit | чистая логика, утилиты, хуки | Vitest / Jest |
| Integration | компонент + взаимодействия | RTL (основной фокус) |
| E2E | сценарий в реальном браузере | Playwright / Cypress |

> RTL смещает фокус с unit на **интеграционные** тесты: они дают больше уверенности на единицу усилий. E2E - в [тестировании и деплое](/content/testing-deploying).

## Что тестировать

- ✅ Поведение, видимое пользователю: что отрисовалось, что происходит по клику/вводу.
- ✅ Условный рендер, обработку ошибок и загрузки, граничные случаи.
- ❌ Внутреннее состояние, имена пропсов, количество рендеров, детали реализации.
- ❌ Сам React и сторонние библиотеки - они уже протестированы.

## Вопросы на собеседовании

<b class="text-on-semi-light">Главный принцип React Testing Library?</b>
<span class="text-gray">Тестировать поведение, как им пользуется пользователь, а не детали реализации. Тест не должен ломаться при рефакторинге без изменения поведения.</span>

<b class="text-on-semi-light">Почему getByRole предпочтительнее getByTestId?</b>
<span class="text-gray">`getByRole` ищет так, как видит пользователь и скринридер, и заодно проверяет доступность. `testid` - последнее средство, когда иначе не достать.</span>

<b class="text-on-semi-light">В чём разница getBy, queryBy и findBy?</b>
<span class="text-gray">`getBy` бросает ошибку при отсутствии, `queryBy` возвращает null (проверка отсутствия), `findBy` возвращает промис и ждёт появления (асинхронность).</span>

<b class="text-on-semi-light">Зачем нужен act и почему его редко пишут вручную?</b>
<span class="text-gray">`act` гарантирует применение обновлений и эффектов до проверок. RTL оборачивает методы в act сама; warning обычно значит недождавшееся async-обновление - лечится findBy/waitFor.</span>

<b class="text-on-semi-light">Почему MSW лучше мока fetch?</b>
<span class="text-gray">Мокает на уровне сети, а не реализации. Тест не меняется при смене способа загрузки (fetch/axios/React Query).</span>

<b class="text-on-semi-light">Какие тесты писать для React и в какой пропорции?</b>
<span class="text-gray">В основном интеграционные через RTL (лучшее соотношение уверенности к усилиям), unit для чистой логики, немного e2e для ключевых сценариев.</span>
