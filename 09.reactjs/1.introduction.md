# Введение в React

Вводная тема главы: что такое React, что на самом деле возвращает компонент, как описание интерфейса превращается в DOM и что заставляет React перерисовывать экран. На собеседовании с этого начинают: «React — фреймворк или библиотека?», «Что такое Virtual DOM?», «Когда компонент перерендеривается?». Хороший ответ объясняет механизм, а не пересказывает лозунги.

::tldr
- **React — библиотека для построения интерфейсов:** ты описываешь, как UI выглядит при текущем состоянии, а React сам приводит DOM к этому виду. Роутинг, данные и сборку дают фреймворки и экосистема.
- **Компонент возвращает не DOM, а React-элементы** — лёгкие неизменяемые объекты `{ type, props, key }`. JSX — синтаксис для вызовов `jsx()`, которые создают эти объекты.
- **Обновление идёт в две фазы:** render вызывает компоненты и строит новое дерево элементов, commit применяет к DOM только разницу со старым. Существующие узлы переиспользуются.
- **Рендер запускает изменение состояния**, а не изменение props: когда рендерится родитель, рендерятся и все его дети, если их не остановить.
- **Данные текут сверху вниз:** props от родителя к детям, изменения — через колбэки наверх. У каждого значения один источник истины.
::

## Что такое React

React — библиотека для построения пользовательских интерфейсов. Её главная идея умещается в формулу **UI = f(state)**: интерфейс — функция от состояния. Ты описываешь, как должен выглядеть экран при данных, которые есть сейчас, а React решает, какие изменения внести в DOM, чтобы страница стала такой.

Почему «библиотека», а не «фреймворк»: React отвечает только за интерфейс — компоненты, состояние, рендер. Роутинг, загрузку данных, работу с формами на сервере и сборку он не решает. Это делают фреймворки поверх React (Next.js, React Router), и с них же react.dev советует начинать новый проект.

Сам React состоит из двух частей:

- **пакет `react`** — компоненты, хуки, элементы. Он не знает, куда рисовать;
- **рендерер** — `react-dom` для браузера, `react-native` для мобильных платформ, `react-dom/server` для HTML на сервере. Рендерер превращает описание интерфейса в настоящие узлы конкретной платформы.

Поэтому одни и те же компоненты и хуки работают и в браузере, и в нативном приложении. Пройдём весь путь на одном примере — кнопке «лайк»:

```jsx
function LikeButton() {
  const [liked, setLiked] = useState(false);
  return (
    <button className={liked ? 'active' : ''} onClick={() => setLiked(!liked)}>
      {liked ? 'Liked' : 'Like'}
    </button>
  );
}
```

В этом коде нет ни одной операции с DOM: ни `classList`, ни `textContent`. Как тогда меняется страница? Начнём с того, чем такой код отличается от привычного.

## Декларативно, а не императивно

Та же кнопка без React:

```js
const button = document.querySelector('#like');
let liked = false;

button.addEventListener('click', () => {
  liked = !liked;
  button.textContent = liked ? 'Liked' : 'Like';
  button.classList.toggle('active', liked);
});
```

Это **императивный** код: ты описываешь шаги, которые переводят DOM из одного состояния в другое. Для двух состояний это просто. Но шагов становится больше с каждой новой зависимостью: счётчик лайков в шапке, `aria-pressed`, блокировка кнопки во время запроса. Каждое место нужно обновить в каждом обработчике, и одно забытое место — это рассинхрон данных и экрана.

В React код **декларативный**: ты описываешь результат для любого состояния, а не переходы между ними. Состояний может быть сколько угодно — функция одна, и каждое место на экране выводится из одних и тех же данных. Цена этого подхода — кто-то должен сам вычислять переходы. Это и есть работа React.

Чтобы понять, как он это делает, нужно посмотреть, что на самом деле возвращает `LikeButton`.

## Что возвращает компонент

JSX — не HTML и не шаблон. Это синтаксис, который компилятор (Babel, esbuild, SWC, TypeScript) превращает в вызовы функций:

```jsx
<LikeButton liked={true} key="a">Like</LikeButton>
```

```js
import { jsx } from "react/jsx-runtime";
jsx(LikeButton, { liked: true, children: "Like" }, "a");
```

Раньше JSX компилировался в `React.createElement(...)`, поэтому в каждом файле с JSX был `import React from 'react'`. С новым JSX-трансформом импорт добавляет компилятор.

Вызов `jsx()` возвращает **React-элемент** — обычный объект:

```js
{
  $$typeof: Symbol(react.transitional.element),
  type: LikeButton,          // функция-компонент или строка 'button'
  key: 'a',
  props: { liked: true, children: 'Like' },
}
```

Из этого следует несколько важных вещей:

- **Элемент — описание, а не экземпляр.** Создать элемент — значит создать объект. Компонент при этом не вызывается: `<LikeButton />` сам по себе ничего не рендерит.
- **Элементы неизменяемы.** В dev-сборке React замораживает их (`Object.freeze`). Чтобы изменить экран, создаётся новое дерево элементов, а не правится старое.
- **Элементы дешёвые.** Это несколько маленьких объектов, поэтому строить их заново при каждом изменении нормально.
- **`$$typeof` — защита от XSS.** Это `Symbol`, а символ нельзя передать через JSON. Если сервер по ошибке вернёт объект `{ type: 'img', props: {...} }` и он попадёт в разметку, React его не отрисует: `Objects are not valid as a React child`.

Компонент вызывается, получает props и возвращает дерево таких объектов. Остаётся вопрос: кто и когда превращает это дерево в DOM?

## Рендер и commit

Когда `LikeButton` нужно обновить, React проходит две фазы:

```text
setLiked(true)
   │
   ▼
render: React вызывает компоненты и получает новое дерево элементов
   │
   ▼
reconciliation: новое дерево сравнивается с прошлым
   │
   ▼
commit: в DOM применяется только разница
```

- **Render** — чистая фаза. React вызывает компоненты, получает элементы и вычисляет, что поменялось. DOM здесь не трогается, поэтому эту фазу можно прервать, отложить или повторить.
- **Commit** — фаза изменений. React применяет к DOM найденную разницу и запускает эффекты.

В случае с `LikeButton` после клика React не пересоздаёт кнопку. Тот же узел `<button>` и тот же текстовый узел остаются на месте, а в DOM уходят ровно две мутации: атрибут `class` и текст. Это проверено через `MutationObserver`.

Отсюда главное различие, которое путают на собеседованиях: **рендер — это вызов компонента, а не обновление DOM.** Компонент может отрендериться, а DOM — не измениться вовсе, если новое дерево совпало со старым.

### Virtual DOM — это не про скорость

Дерево элементов в памяти и называют Virtual DOM. Распространённый миф: «React быстрый, потому что Virtual DOM быстрее DOM». Это неверно. Построить дерево и сравнить его — дополнительная работа поверх той же записи в DOM. Ручной точечный `textContent = ...` всегда быстрее, а библиотеки без Virtual DOM (Svelte, Solid) обновляют DOM напрямую.

Virtual DOM даёт другое: возможность писать декларативно и при этом не пересоздавать DOM целиком. Разработчик описывает результат, React вычисляет минимальные изменения. Для большинства интерфейсов это достаточно быстро и гораздо надёжнее ручной синхронизации.

> Как именно React сравнивает деревья, зачем нужны ключи и что такое Fiber — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber).

Теперь понятно, что происходит при обновлении. Но что вообще заставляет React запустить render?

## Что запускает рендер

Компонент рендерится по трём причинам:

1. **Изменилось его состояние** — вызван `setState`. Это единственный способ начать обновление «изнутри».
2. **Отрендерился его родитель.** Когда родитель вызван заново, он возвращает новые элементы для детей, и React вызывает детей тоже.
3. **Изменился контекст**, который компонент читает.

Важно, чего в этом списке нет: **изменения props**. Props — это аргументы, их меняет только рендер родителя. И наоборот, ребёнок рендерится вместе с родителем, даже если его props остались теми же:

```jsx
function Parent({ children }) {
  const [n, setN] = useState(0);
  return (
    <div onClick={() => setN(n + 1)}>
      {n}
      <Child label="same" />            {/* рендерится каждый раз */}
      <MemoChild label="same" />        {/* memo: props те же — пропуск */}
      {children}                        {/* элемент создан выше — пропуск */}
    </div>
  );
}
```

После двух кликов `Child` отрендерится 3 раза (монтирование и два обновления), а `MemoChild` и компонент из `children` — по одному. `memo` сравнивает props и пропускает рендер, если они равны. Элемент из `children` создан в другом компоненте и не изменился, поэтому React его тоже пропускает.

Обычно это не проблема: рендер дешёвый, а лишние рендеры не трогают DOM. Проблемой это становится, когда внизу тяжёлое дерево. Как это измерять и чинить — в [Производительности](/content/reactjs/performance). Как именно `setState` планирует рендер — в [Механике хуков](/content/reactjs/hooks-mechanics).

Рендер идёт сверху вниз, от компонента, где изменилось состояние, к его детям. Тем же путём идут и данные.

## Однонаправленный поток данных

Данные в React текут **сверху вниз**. Родитель передаёт детям props, и ребёнок не может их изменить. Чтобы повлиять на родителя, ребёнок вызывает колбэк, который родитель передал ему тем же способом:

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return <Counter count={count} onIncrement={() => setCount(count + 1)} />;
}

function Counter({ count, onIncrement }) {
  return <button onClick={onIncrement}>{count}</button>;
}
```

Состояние `count` живёт в одном месте — в `Parent`. `Counter` только показывает его и сообщает о кликах. Если значение нужно двум соседним компонентам, состояние поднимают в их общего родителя (lifting state up) и раздают через props.

Так у каждого значения один **источник истины**, и всегда понятно, кто его меняет. Противоположный подход — двусторонняя привязка (two-way binding), когда поле ввода и модель меняют друг друга напрямую. В Vue `v-model` выглядит как двусторонняя привязка, но под капотом это тот же prop плюс событие.

> Как устроено состояние и события — в [State и события](/content/reactjs/state-and-events). Где держать состояние и когда его поднимать — в [Производном состоянии и потоке данных](/content/reactjs/derived-state-and-data-flow).

Компоненты, элементы, рендер, поток данных — вот и всё, что даёт сам React. Остальное — экосистема.

## Что не входит в React

Многое из того, что называют «реактом», — сторонние решения:

| Задача | Чем решают | Где в книге |
| --- | --- | --- |
| Роутинг | React Router, TanStack Router, роутинг фреймворка | [Роутинг](/content/reactjs/routing) |
| Загрузка и кеш данных | TanStack Query, SWR, загрузчики фреймворков | [Загрузка данных](/content/reactjs/data-fetching) |
| Глобальное состояние | Zustand, Redux Toolkit, Jotai | [State management](/content/reactjs/state-management) |
| SSR, сборка, серверная часть | Next.js, React Router в режиме фреймворка | [Рендеринг и гидратация](/content/reactjs/rendering-and-hydration) |

С другими инструментами React сравнивают так:

| | React | Vue | Angular |
| --- | --- | --- | --- |
| Что это | библиотека UI | прогрессивный фреймворк | фреймворк «всё включено» |
| Разметка | JSX — это JavaScript | шаблоны в SFC | HTML-шаблоны и директивы |
| Реактивность | явная: `setState`, рендер компонента целиком | прокси, трекинг зависимостей | сигналы (раньше — Zone.js) |
| Что даёт из коробки | минимум | официальные роутер и стор | роутер, формы, DI, HTTP |

Главное отличие модели: Vue и Angular с сигналами знают, какое значение где используется, и обновляют точечно. React при изменении состояния заново вызывает компонент целиком и сравнивает результат. Отсюда и важность `memo` и React Compiler.

> Подробно Vue — в [главе про Vue](/content/vuejs). Сигналы и реактивность как идея — в [Сигналах и реактивности](/content/modern-dev/signals-and-reactivity).

## Как менялся React

Актуально на ноябрь 2026.

| Год | Что произошло |
| --- | --- |
| 2013 | React открыт в open source, вместе с JSX |
| 2015 | React Native: тот же подход для мобильных платформ |
| 2017 | React 16: новая архитектура Fiber |
| 2019 | React 16.8: хуки, состояние и эффекты в функциональных компонентах |
| 2022 | React 18: concurrent rendering, автоматический батчинг, `useTransition` |
| 2024 | React 19: Server Components и Actions стабильны, `use`, `ref` как обычный prop |
| 2025 | React 19.2, React Compiler 1.0; Create React App выведен из поддержки, react.dev рекомендует начинать с фреймворка |
| 2025–2026 | React и React Native переходят из Meta в React Foundation при Linux Foundation |

Главный поворот — хуки. До них состояние и жизненный цикл жили только в классовых компонентах, а логику между компонентами делили через HOC и render props. Хуки перенесли всё это в функции и дали кастомные хуки для переиспользования логики. Классы остались в старом коде, и про них всё ещё спрашивают — см. [Компоненты и JSX](/content/reactjs/components-and-jsx).

## Красные флаги в ответе

- **«React — фреймворк».** React — библиотека для UI. Фреймворком приложение делают Next.js, React Router и экосистема.
- **«Virtual DOM быстрее DOM».** Это дополнительная работа поверх DOM. Его ценность — декларативный код без пересоздания DOM, а не скорость.
- **«JSX — это HTML внутри JavaScript».** JSX компилируется в вызовы `jsx()`, которые возвращают объекты. Поэтому `className` вместо `class` и выражения в `{}`.
- **«Рендер — это обновление DOM».** Рендер — вызов компонента. DOM меняется только в commit и только там, где новое дерево отличается от старого.
- **«Компонент перерендеривается, когда меняются его props».** Его рендерит рендер родителя, независимо от того, изменились props или нет. Останавливает это `memo`.

## Как спрашивают на собеседовании

::question
React — это фреймворк или библиотека?

#answer
Библиотека для построения интерфейсов. Она отвечает за компоненты, состояние и рендер. Роутинг, загрузку данных, SSR и сборку дают фреймворки (Next.js, React Router) и сторонние библиотеки.

#more
React разделён на пакет `react` (компоненты, хуки, элементы) и рендереры (`react-dom`, `react-native`, `react-dom/server`). Поэтому одна модель работает на разных платформах. Сегодня граница сдвигается: Server Components и Actions — часть React, но работают только внутри фреймворка, который даёт сервер и сборку. Поэтому react.dev рекомендует начинать новый проект с фреймворка, а не с голой сборки.

#followups
- «Почему тогда Create React App больше не рекомендуют?» → он не решает роутинг, загрузку данных и SSR, и его вывели из поддержки; вместо него — фреймворк или Vite
::

::question
Чем декларативный подход лучше императивного?

#answer
В императивном коде ты описываешь шаги, которые меняют DOM, и сам следишь, чтобы все места на экране обновились. В декларативном — описываешь результат для текущего состояния, а синхронизацию делает React. Меньше ручных шагов — меньше рассинхронов.

#more
Число переходов между состояниями растёт гораздо быстрее, чем число состояний: каждый обработчик должен знать обо всех местах, которые от него зависят. Декларативный код описывает одну функцию от состояния, и каждое место на экране выводится из одних данных. Цена — вычисление разницы между деревьями и лишние рендеры, которые иногда приходится останавливать через `memo` или компилятор.
::

::question
Что такое Virtual DOM? Он делает React быстрее?

#answer
Это дерево React-элементов в памяти. При изменении состояния React строит новое дерево, сравнивает его со старым и применяет к реальному DOM только разницу.

#more
Сам по себе Virtual DOM не ускоряет: построить и сравнить дерево — работа поверх той же записи в DOM, и точечный ручной код всегда быстрее. Он даёт декларативную модель без пересоздания DOM: существующие узлы переиспользуются, меняются только атрибуты и текст, которые отличаются. Библиотеки без Virtual DOM (Svelte, Solid) компилируют шаблоны в точечные обновления и обходятся без сравнения деревьев.

#followups
- «Как React понимает, что элемент тот же?» → по позиции в дереве и типу, в списках — по `key`
::

::question
Во что компилируется JSX? Что такое React-элемент?

#answer
JSX компилируется в вызовы `jsx()` из `react/jsx-runtime` (раньше — `React.createElement`). Вызов возвращает React-элемент — объект с `type`, `props` и `key`, который описывает, что нужно отрисовать.

#more
Элемент — описание, а не экземпляр: при его создании компонент не вызывается. Элементы неизменяемы (в dev заморожены) и дешёвые, поэтому дерево строится заново на каждый рендер. Поле `$$typeof` — это `Symbol`, его нельзя передать через JSON, поэтому объект, пришедший с сервера и похожий на элемент, React не отрисует. Это защита от XSS.

#followups
- «Почему раньше нужно было импортировать React в каждом файле с JSX?» → JSX компилировался в `React.createElement`; новый трансформ сам импортирует `jsx` из `react/jsx-runtime`
::

::question
Когда компонент перерендеривается?

#answer
Когда меняется его состояние, когда рендерится родитель и когда меняется контекст, который он читает.

#more
Изменение props само по себе рендер не запускает: props меняются только рендером родителя, и ребёнок рендерится вместе с ним, даже если props те же. Остановить это можно `memo` (сравнение props), передачей элементов через `children` (элемент создан выше и не меняется) или опусканием состояния ниже по дереву. Рендер не равен изменению DOM: commit применяет только разницу.
::

::question
Что значит «однонаправленный поток данных»?

#answer
Данные идут от родителя к детям через props. Ребёнок не меняет props, а сообщает родителю о событиях через колбэки, и родитель меняет своё состояние.

#more
У каждого значения один источник истины и один владелец, поэтому изменение легко отследить. Общее состояние соседей поднимают в общего родителя. При двусторонней привязке источник истины размывается: поле и модель меняют друг друга. Даже `v-model` во Vue — это prop плюс событие, то есть тот же однонаправленный поток.
::

::question
Почему хуки стали поворотным моментом в React?

#answer
Они перенесли состояние и побочные эффекты из классов в функции и позволили переиспользовать логику через кастомные хуки — без HOC и render props.

#more
В классах связанная логика была разбросана по методам жизненного цикла (подписка в `componentDidMount`, отписка в `componentWillUnmount`), а переиспользование через HOC и render props давало «wrapper hell». Хуки группируют логику по смыслу, а кастомный хук — обычная функция, которая встраивает свои хуки в компонент. Цена — правила хуков и модель «каждый рендер — снимок», которую нужно понимать, чтобы не ловить stale closure.
::

## Практика

::practice{title="Почему тормозит список?"}
Часы на странице обновляются каждую секунду, и вместе с ними каждую секунду рендерится тяжёлый список:

```jsx
function Page() {
  const [now, setNow] = useState(Date.now());

  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);

  return (
    <main>
      <time>{new Date(now).toLocaleTimeString()}</time>
      <ExpensiveList />
    </main>
  );
}
```

#solution
Состояние часов живёт в `Page`, поэтому каждая секунда — это рендер `Page`, а значит, и всех его детей. `ExpensiveList` ничего не получает от часов, но рендерится вместе с родителем.

Лучший фикс — опустить состояние туда, где оно нужно. Тогда секунда рендерит только `Clock`:

```jsx
function Clock() {
  const [now, setNow] = useState(Date.now());

  useEffect(() => {
    const id = setInterval(() => setNow(Date.now()), 1000);
    return () => clearInterval(id);
  }, []);

  return <time>{new Date(now).toLocaleTimeString()}</time>;
}

function Page() {
  return (
    <main>
      <Clock />
      <ExpensiveList />
    </main>
  );
}
```

После трёх тиков `ExpensiveList` отрендерился один раз — при монтировании. Обернуть список в `memo` тоже сработало бы, но это лечит симптом: структура, где состояние лежит рядом с тем, кто его использует, не требует мемоизации вовсе.
::

::practice{title="Найди баг"}
Шапка падает, когда пользователь выходит из аккаунта:

```jsx
function Avatar({ user }) {
  const [big, setBig] = useState(false);
  return <img alt={user.name} width={big ? 96 : 32} onClick={() => setBig(!big)} />;
}

function Header({ user }) {
  const [menuOpen, setMenuOpen] = useState(false);
  return <header>{user ? Avatar({ user }) : 'Гость'}</header>;
}
```

#solution
`Avatar` вызван как обычная функция, а не как компонент. Для React это не отдельный компонент, а часть `Header`: хук `useState` внутри `Avatar` становится вторым хуком `Header`. Пока пользователь есть, у `Header` два хука, после выхода — один:

```text
Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

Фикс — создать элемент, а не вызывать функцию. Тогда `Avatar` получит свой fiber и свой список хуков:

```jsx
function Header({ user }) {
  const [menuOpen, setMenuOpen] = useState(false);
  return <header>{user ? <Avatar user={user} /> : 'Гость'}</header>;
}
```

Почему хуки «съезжают» на родителя — в [Механике хуков](/content/reactjs/hooks-mechanics).
::

::practice{title="Перепиши декларативно"}
Количество товаров в корзине показывается в двух местах. Найди, где императивный код рассинхронизируется, и перепиши его на React:

```js
let count = 0;
const badge = document.querySelector('#badge');
const buy = document.querySelector('#buy');

function addToCart() {
  count++;
  badge.textContent = count;
  buy.disabled = false;
}

function clearCart() {
  count = 0;
  badge.textContent = 0;
}
```

#solution
`clearCart` не обновляет кнопку: после очистки «Купить» остаётся активной, а текст кнопки вообще нигде не обновляется. Каждый новый обработчик должен помнить обо всех местах на экране.

В React все места выводятся из одного состояния, и забыть одно из них невозможно:

```jsx
function Shop() {
  const [items, setItems] = useState([]);

  return (
    <div>
      <span id="badge">{items.length}</span>
      <button id="buy" disabled={items.length === 0}>
        Купить ({items.length})
      </button>
      <button onClick={() => setItems([...items, 'book'])}>Добавить</button>
      <button onClick={() => setItems([])}>Очистить</button>
    </div>
  );
}
```

После двух добавлений: в бейдже `2`, на кнопке «Купить (2)», кнопка активна. После очистки всё возвращается к пустой корзине без отдельного кода.
::
