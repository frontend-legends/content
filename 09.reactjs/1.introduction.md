# Введение в React

**React** - это библиотека для построения пользовательских интерфейсов, созданная в Facebook (ныне Meta) и выпущенная в open source в 2013 году. Её главная идея умещается в одну формулу:

> **UI = f(state)** - интерфейс это функция от состояния.

Ты описываешь, **как** должен выглядеть UI при текущем состоянии, а React сам решает, **какие** изменения внести в DOM, чтобы привести страницу к этому виду. Тебе не нужно вручную дёргать `element.appendChild` или `node.textContent` - ты меняешь состояние, а React досинхронизирует DOM.

---

## Императивный vs декларативный подход

Это фундаментальное различие, с которого начинается любой разговор про React.

```js
// Императивно (vanilla JS): ты описываешь ПОШАГОВО, что делать
const button = document.querySelector('#like');
let liked = false;
button.addEventListener('click', () => {
  liked = !liked;
  button.textContent = liked ? 'Liked' : 'Like';
  button.classList.toggle('active', liked);
});
```

```jsx
// Декларативно (React): ты описываешь РЕЗУЛЬТАТ для текущего состояния
function LikeButton() {
  const [liked, setLiked] = useState(false);
  return (
    <button className={liked ? 'active' : ''} onClick={() => setLiked(!liked)}>
      {liked ? 'Liked' : 'Like'}
    </button>
  );
}
```

<b class="text-on-semi-light">В чём разница?</b> - <span class="text-gray">В императивном коде ты сам синхронизируешь DOM с данными и легко забываешь какой-то шаг (например, `classList`). В декларативном ты описываешь конечный вид для каждого состояния, а синхронизацию берёт на себя React. Меньше шагов - меньше багов.</span>

## Компонентная модель

React-приложение - это дерево **компонентов**. Компонент - это функция, которая принимает входные данные (**props**) и возвращает описание UI (**JSX**).

```jsx
function UserCard({ name, role }) {
  return (
    <div className="card">
      <h3>{name}</h3>
      <p>{role}</p>
    </div>
  );
}

function App() {
  return (
    <main>
      <UserCard name="Аня" role="Frontend" />
      <UserCard name="Петя" role="Backend" />
    </main>
  );
}
```

Компоненты **композируются**: большие собираются из маленьких. Это даёт переиспользование, изоляцию и предсказуемость - каждый компонент отвечает за свой кусок UI.

## Однонаправленный поток данных

Данные в React текут **сверху вниз**: родитель передаёт props детям. Ребёнок не может изменить props напрямую - чтобы повлиять на родителя, он вызывает переданный сверху колбэк.

```jsx
function Parent() {
  const [count, setCount] = useState(0);
  return <Child count={count} onIncrement={() => setCount(count + 1)} />;
}

function Child({ count, onIncrement }) {
  return <button onClick={onIncrement}>{count}</button>;
}
```

<b class="text-on-semi-light">Зачем это нужно?</b> - <span class="text-gray">Однонаправленный поток делает приложение предсказуемым: всегда понятно, откуда пришли данные и кто их меняет. Это противоположность двусторонней привязке (two-way binding), где источник истины размывается.</span>

## Virtual DOM в двух словах

React не перерисовывает всю страницу при каждом изменении. Вместо этого он держит в памяти лёгкое JS-представление UI - **Virtual DOM**. При изменении состояния React строит новое виртуальное дерево, сравнивает его со старым (**diffing**) и применяет к реальному DOM только разницу.

```
state изменился
   ↓
новый Virtual DOM
   ↓
diff со старым деревом (reconciliation)
   ↓
минимальные точечные изменения в реальном DOM
```

Реальный DOM медленный (особенно reflow/repaint), а операции с JS-объектами - дешёвые. Подробно разберём этот механизм и архитектуру Fiber в главе [согласование и Fiber](/content/reactjs/reconciliation-and-fiber).

> Важно: Virtual DOM - не «магия ускорения». Это способ описать UI декларативно и применить минимальный набор изменений. Иногда прямой императивный код быстрее - но он не масштабируется по сложности.

## Краткая история

| Год | Веха |
|-----|------|
| 2013 | Релиз React в open source, JSX |
| 2015 | React Native - тот же подход для мобильных |
| 2016 | Fiber-архитектура (внутренний rewrite, релиз в 16.0) |
| 2019 | **Hooks** (16.8) - состояние и логика в функциональных компонентах |
| 2022 | **Concurrent React** (18) - `useTransition`, automatic batching, Suspense на SSR |
| 2024-2025 | **React 19** - Server Components стабильны, Actions, `use()`, React Compiler |

Главный сдвиг - **хуки**: до них состояние и жизненный цикл жили в классовых компонентах, после - в функциях. Классы остались в коде legacy-проектов, и их всё ещё спрашивают на собесах (см. [компоненты и JSX](/content/reactjs/components-and-jsx)).

## React vs Angular vs Vue

| | React | Angular | Vue |
|--|-------|---------|-----|
| Тип | Библиотека (UI) | Фреймворк (всё включено) | Прогрессивный фреймворк |
| Шаблоны | JSX (JS) | HTML-шаблоны + директивы | SFC (`.vue`) |
| Реактивность | Явная (`setState`/хуки) | Zones / Signals | Прокси + сигналы |
| Что выбирает за тебя | Минимум (роутинг, fetch - сторонние) | Почти всё (DI, router, forms) | Среднее (есть официальные router/store) |

<b class="text-on-semi-light">Главный тезис для собеса</b> - <span class="text-gray">React - это именно UI-библиотека, а не фреймворк. Роутинг, загрузка данных, управление состоянием - это сторонние решения. Это и плюс (гибкость), и минус (нужно собирать стек самому).</span>

## Что НЕ входит в React

Частая путаница: многое, что считают «реактом», - это экосистема, а не сам React.

- **Роутинг** - React Router, TanStack Router ([роутинг](/content/reactjs/routing)).
- **Загрузка данных** - React Query, SWR ([загрузка данных](/content/reactjs/data-fetching)).
- **Глобальное состояние** - Redux, Zustand, Jotai ([управление состоянием](/content/reactjs/state-management)).
- **Мета-фреймворк** - Next.js, Remix (SSR, роутинг, сборка из коробки).

Сам React даёт только компоненты, состояние, хуки и рендеринг.

## Вопросы на собеседовании

<b class="text-on-semi-light">React - это фреймворк или библиотека?</b>
<span class="text-gray">Библиотека для построения UI. Роутинг, data-fetching и стейт-менеджмент - сторонние. Фреймворком его делает экосистема (например, Next.js).</span>

<b class="text-on-semi-light">Чем декларативный подход лучше императивного?</b>
<span class="text-gray">Ты описываешь конечный вид UI для состояния, а не последовательность мутаций DOM. Меньше шагов синхронизации - меньше рассинхронов и багов.</span>

<b class="text-on-semi-light">Что такое Virtual DOM и зачем он нужен?</b>
<span class="text-gray">Лёгкое JS-представление UI в памяти. React диффит новое дерево со старым и применяет к реальному DOM только разницу. Это не про «скорость любой ценой», а про декларативность и минимальные изменения.</span>

<b class="text-on-semi-light">Что значит «однонаправленный поток данных»?</b>
<span class="text-gray">Данные текут от родителя к детям через props; ребёнок меняет состояние родителя только через колбэки. Источник истины всегда один и понятен.</span>

<b class="text-on-semi-light">Почему хуки стали поворотным моментом?</b>
<span class="text-gray">Они перенесли состояние и побочные эффекты из классов в функции, позволили переиспользовать логику (кастомные хуки) без HOC/render props и упростили модель.</span>
