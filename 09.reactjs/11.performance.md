# Производительность

Почему React-приложение тормозит, как найти причину и чем её чинить: `memo`, `useMemo`, `useCallback`, React Compiler, структура компонентов, приоритеты и виртуализация. На mid спрашивают, что делает `memo` и когда нужен `useCallback`. На senior — **почему** мемоизация не сработала, что из этого делает компилятор и что именно прерывает `useTransition`.

::tldr
- **Рендер — это вызов компонента и сравнение результата, а не обновление DOM.** В DOM попадает только разница. Тормозит, когда рендеров много или каждый тяжёлый.
- **Ребёнок рендерится вместе с родителем, даже если его props не менялись.** Пропустить его можно двумя способами: `memo` со стабильными props или тот же объект элемента — его дают `children`, вынесенные наверх, и React Compiler.
- **`memo` сравнивает каждый prop через `Object.is`,** поэтому объект, функция или JSX, созданные в рендере, ломают его. `useMemo` и `useCallback` нужны ради стабильной ссылки или дорогого вычисления, иначе это лишняя работа.
- **React Compiler мемоизирует при сборке, опираясь на Rules of React.** Компонент, нарушающий правила, он пропускает и оставляет как есть, а не ломает. Ручные `useMemo` остаются как запасной выход.
- **`useTransition` и `useDeferredValue` не ускоряют рендер, а делают его прерываемым.** Более срочный апдейт (ввод, клик, `flushSync`) прерывает рендер transition, и тот начинается заново. Обычный апдейт и другой transition его не прерывают, а один долгий компонент и commit не прерываются вовсе.
::

## Почему React-приложение тормозит

Страница поиска по каталогу:

```jsx
function SearchPage({ products }) {          // 5000 товаров
  const [query, setQuery] = useState('');
  const visible = products.filter((p) => p.name.includes(query));

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <Chart data={products} />
      <ProductList items={visible} onSelect={(id) => track(id)} />
    </div>
  );
}
```

Пользователь печатает, и буквы появляются в поле с задержкой. Почему?

Браузер рисует кадр, только когда главный поток свободен. Пока выполняется JavaScript, он не обрабатывает ввод и не рисует. Каждая буква здесь — `setQuery`, за ним рендер `SearchPage`, а за ним рендер `Chart` и всех 5000 строк `ProductList`. Если это занимает 150 мс, буква появится через 150 мс.

У React-приложения четыре источника тормозов, и лечатся они по-разному:

| Что тормозит | Пример | Чем лечится |
| --- | --- | --- |
| лишние рендеры | `Chart` рендерится на каждую букву, хотя его данные не менялись | структура, `memo`, компилятор |
| тяжёлый нужный рендер | список честно пересчитывается под новый `query` | `useMemo` для вычисления, приоритеты |
| много DOM | 5000 узлов: дорогие commit, layout и paint | виртуализация |
| большой бандл | долгие загрузка и парсинг JS до первого клика | code splitting |

Последний пункт — про загрузку, а не про работу после неё. Ленивые маршруты — в [Роутинге](/content/reactjs/routing), бюджет загрузки — в [Производительности загрузки](/content/security-perfomance/loading-performance). Дальше тема о том, что происходит, когда приложение уже загружено.

Первые два пункта упираются в один вопрос: что вообще заставляет компонент рендериться и сколько стоит рендер?

## Рендер — не обновление DOM

**Рендер** — это вызов функции компонента и сравнение того, что она вернула, с прошлым результатом. **Commit** — применение найденной разницы к DOM. Подробно обе фазы разобраны в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber).

В нашем примере `Chart` рендерится на каждую букву, но его DOM-узел остаётся тем же объектом, и `MutationObserver` не видит в нём ни одной мутации. В DOM попало только новое `value` у `input`. Поэтому «ребёнок перерендерился» — ещё не проблема. Проблема — когда таких рендеров тысячи или один из них тяжёлый.

### Откуда берутся рендеры

Компонент рендерится по трём причинам:

1. **Изменился его state.** Сюда же относятся внешние сторы через `useSyncExternalStore`.
2. **Отрендерился родитель.** Это главный источник лишних рендеров. React не смотрит, изменились ли props: родитель вернул новый элемент `<Chart />`, и React вызывает `Chart` снова. `Chart` в нашем примере рендерится на каждую букву, хотя `products` тот же.
3. **Изменился контекст,** который компонент читает. Этот рендер проходит даже сквозь `memo` (подробно — в [Context API](/content/reactjs/context-api)).

«Изменились props» в списке нет. Props меняются только потому, что отрендерился родитель, — это та же вторая причина.

### Когда React пропускает ребёнка

У второй причины есть исключение, на котором держится почти вся оптимизация. JSX — это вызов `createElement`, и он каждый раз создаёт **новый объект элемента** с новым объектом props. Если же родитель вернул **тот же объект элемента**, что и в прошлый раз, React понимает, что для этого ребёнка ничего не изменилось, и пропускает его вместе с поддеревом:

```jsx
const chart = <Chart />;          // создан один раз, вне рендера

function App() {
  const [n, setN] = useState(0);
  return <div>{n}{chart}</div>;   // Chart не рендерится при смене n
}
```

Пропустить ребёнка можно двумя способами, а третий способ — вообще не пускать его в поддерево, которое рендерится. Дальше разберём каждый:

- **`memo`** — React сравнивает props по отдельности;
- **тот же элемент** — его дают `children`, созданные выше, и React Compiler, который кеширует JSX;
- **state ниже** — ребёнка просто нет в поддереве, которое рендерится.

Прежде чем выбирать способ, нужно найти, какие рендеры тормозят на самом деле.

## Сначала измерь

Оптимизация без измерения — угадывание, и угадывают обычно неверно: самый подозрительный компонент часто стоит 0,1 мс, а тормозит соседний.

### React DevTools

- **Profiler** записывает сценарий и показывает каждый commit: какие компоненты рендерились и сколько это стоило (flamegraph и отсортированный список).
- **Record why each component rendered while profiling** — настройка профайлера. С ней для каждого рендера видна причина: изменились props (какие именно), state, хук, контекст или отрендерился родитель.
- **Highlight updates when components render** — подсвечивает рендеры прямо в интерфейсе. Быстрый способ увидеть, что на одну букву мигает вся страница.
- **Бейдж `Memo ✨`** во вкладке Components — компонент обработан React Compiler. К нему вернёмся ниже.

### Profiler в коде

Компонент `<Profiler>` даёт те же цифры программно — например, для отправки в мониторинг:

```jsx
<Profiler id="Search" onRender={(id, phase, actualDuration, baseDuration) => {
  report({ id, phase, actualDuration, baseDuration });
}}>
  <SearchPage products={products} />
</Profiler>
```

- `phase` — `"mount"`, `"update"` или `"nested-update"`.
- `actualDuration` — сколько миллисекунд реально ушло на рендер поддерева в этом commit.
- `baseDuration` — оценка, сколько стоил бы рендер всего поддерева без оптимизаций.

Сравнение двух чисел показывает, работает ли мемоизация. В проверке с `memo`-ребёнком на 20 мс mount занимает около 20 мс, а update — меньше миллисекунды при `baseDuration` около 20 мс: ребёнок пропущен. В production-сборке профилирование выключено. Для замеров на проде нужна специальная сборка `react-dom/profiling`.

### Performance panel и INP

Профайлер React видит только React. Обработчики событий, layout, paint и сторонние скрипты видны в **Performance panel** браузера: там же видны **long tasks** — задачи дольше 50 мс, которые блокируют ввод. В трассе Chrome React добавляет свои дорожки (Performance Tracks): Scheduler с приоритетами Blocking, Transition, Suspense, Idle и Components с flamegraph рендеров. Дорожки есть в development-сборке и в `react-dom/profiling` (там Components по умолчанию показывает только поддеревья под `<Profiler>`), а в production их нет.

Пользовательская метрика отзывчивости — :term[INP]{def="Interaction to Next Paint: задержка от взаимодействия пользователя до следующего кадра"}. Наш лагающий поиск — это плохой INP: от нажатия клавиши до кадра проходит весь рендер. Сама метрика и её фазы — в [Core Web Vitals](/content/security-perfomance/core-web-vitals), разбивка long tasks — в [Производительности в рантайме](/content/security-perfomance/runtime-performance).

Два правила честного замера: включи замедление CPU в DevTools (твой ноутбук быстрее телефона пользователя) и меряй production-сборку, потому что development-сборка React заметно медленнее.

### А why-did-you-render?

Библиотека жива и поддерживает React 19, но работает через monkey-patching React, только в development, и автор прямо пишет, что с React Compiler её не тестировали и, скорее всего, они несовместимы. Её главная задача — найти рендер с props, равными по значению, но новыми по ссылке. DevTools с настройкой «why each component rendered» показывает только, какой prop сменил ссылку, а равен ли он по значению, решаешь сам. Сам этот класс проблем убирает React Compiler.

Профайлер показал: `Chart` рендерится на каждую букву, и ничего в нём не меняется. Первое, что приходит в голову, — `memo`.

## memo: пропустить рендер ребёнка

`memo` оборачивает компонент и говорит React: если props не изменились, не вызывай его, возьми прошлый результат.

```jsx
const Chart = memo(function Chart({ data }) { /* ... */ });
```

«Не изменились» — это сравнение **каждого** prop с прошлым значением через `Object.is`. Для `Chart` этого достаточно: `products` приходит сверху той же ссылкой, и на ввод в поле `Chart` больше не рендерится.

А вот `ProductList` в нашем примере `memo` не спасёт:

```jsx
<ProductList items={visible} onSelect={(id) => track(id)} />
```

- `visible` — результат `filter`, новый массив на каждый рендер;
- `onSelect` — стрелочная функция, тоже новая на каждый рендер.

`Object.is(prev, next)` для них всегда `false`, и `memo` честно рендерит компонент. Ломают `memo` любые значения, созданные в рендере:

| Prop | Почему новый | Чем стабилизировать |
| --- | --- | --- |
| `style={{ color: 'red' }}` | литерал объекта | константа вне компонента или `useMemo` |
| `onSelect={() => ...}` | стрелочная функция | `useCallback` |
| `items={list.filter(...)}` | результат вычисления | `useMemo` |
| `<Row><b>Ann</b></Row>` | `children` — тоже prop, и JSX каждый раз новый | вынести элемент или не мемоизировать `Row` |

Проверка с четырьмя `memo`-компонентами это подтверждает: за три рендера родителя компоненты со `style`-литералом, стрелкой и JSX-`children` отрендерились по 4 раза, а со стабильными ссылками — один раз, при монтировании.

### Чего memo не делает

- **Не защищает от собственного state.** Изменился state внутри — компонент рендерится.
- **Не защищает от контекста.** Потребитель контекста рендерится при смене значения, даже под `memo`.
- **Не гарантирует пропуск.** Документация называет `memo` оптимизацией, а не гарантией: код, который ломается без `memo`, сломан и с ним.

Вторым аргументом `memo` принимает свою функцию сравнения `arePropsEqual(prev, next)`. У неё две ловушки. Глубокое сравнение может стоить дороже самого рендера. А если пропускать в сравнении функции-props, ребёнок останется со старым обработчиком, который замкнул props и state прошлого рендера, — это [stale closure](/content/reactjs/hooks-mechanics). Сравнивать нужно все props, включая функции.

Значит, `memo` работает только в паре со стабильными ссылками. Получить их и есть работа `useMemo` и `useCallback`.

## useMemo и useCallback: когда они нужны

`useMemo(fn, deps)` вызывает `fn` на первом рендере и потом возвращает сохранённый результат, пока `deps` равны прошлым через `Object.is`. `useCallback(fn, deps)` — то же самое для самой функции: это `useMemo(() => fn, deps)`. Оба хранят в ячейке пару `[значение, deps]` — устройство ячеек разобрано в [Механике хуков](/content/reactjs/hooks-mechanics).

```jsx
const visible = useMemo(
  () => products.filter((p) => p.name.includes(query)),
  [products, query],
);
const onSelect = useCallback((id) => track(id), []);
```

### Три случая, когда это окупается

1. **Стабильная ссылка для `memo`-ребёнка.** Без `memo` у получателя стабильная ссылка ничего не даёт: он рендерится вместе с родителем.
2. **Значение в deps другого хука.** Объект в deps эффекта, созданный в рендере, перезапускает эффект на каждом рендере. Как это превращается в спам запросами — в [Механике хуков](/content/reactjs/hooks-mechanics).
3. **Заметно дорогое вычисление** при редко меняющихся deps. Ориентир из документации: оберни вычисление в `console.time`, и если набегает 1 мс и больше, мемоизация имеет смысл. Обычно это тысячи объектов, а не `filter` по двадцати элементам.

В остальных случаях пользы нет. Есть только цена.

### Цена

- **Функция создаётся всё равно.** `useCallback` не экономит создание функции: стрелка создаётся на каждом рендере, хук лишь возвращает старую, пока deps те же.
- **Первый рендер не быстрее,** а немного медленнее: вычисление плюс сохранение.
- **На каждом рендере** сравниваются deps, и в памяти лежит прошлое значение.
- **Кеш на одно значение.** Хранится только последний результат: `tab` меняется `all → done → all`, и `all` считается заново.
- **Кеш — не гарантия.** React вправе выбросить кеш, например если компонент приостановился при первом монтировании. Если без кеша код ломается, нужен state или ref, а не `useMemo`.
- **Код сложнее,** и каждый массив deps — место для ошибки.

Ручная мемоизация в итоге — это работа: найти профайлером, где нужна стабильная ссылка, и поддерживать deps в актуальном виде. Именно эту работу на себя берёт компилятор.

## React Compiler

React Compiler — плагин сборки (Babel), который переписывает компоненты и хуки так, чтобы они сами кешировали значения, функции и JSX. Вот что он сделал с `SearchPage`. Это настоящий вывод, сокращённый для чтения: временные переменные переименованы, `createElement` показан как JSX.

```js
import { c as _c } from 'react/compiler-runtime';

function SearchPage({ products }) {
  const $ = _c(16);                         // кеш на 16 слотов
  const [query, setQuery] = useState('');

  let visible;
  if ($[0] !== products || $[1] !== query) {
    visible = products.filter((p) => p.name.includes(query));
    $[0] = products; $[1] = query; $[2] = visible;
  } else {
    visible = $[2];
  }

  let chart;
  if ($[8] !== products) {
    chart = <Chart data={products} />;      // элемент пересоздаётся только при смене products
    $[8] = products; $[9] = chart;
  } else {
    chart = $[9];
  }

  let list;
  if ($[10] !== visible) {
    list = <ProductList items={visible} onSelect={_temp} />;
    $[10] = visible; $[11] = list;
  } else {
    list = $[11];
  }
  // ... так же input и div
}

function _temp(id) { return track(id); }    // стрелка ничего не замыкала — вынесена из компонента
```

Что здесь происходит:

- **`_c(16)`** — хук `useMemoCache`: массив слотов, который живёт на fiber компонента (поле `updateQueue.memoCache`), а не в списке ячеек хуков.
- **Каждое значение мемоизировано по своим зависимостям,** а не одним `useMemo` на весь компонент. Компилятор сам вывел, что `visible` зависит от `products` и `query`, а элемент `Chart` — только от `products`.
- **`<Chart>` возвращается тем же объектом элемента,** поэтому на ввод в поле `Chart` не рендерится. Это не `memo`, а тот самый пропуск по одному и тому же элементу. Документация описывает результат как эквивалент `memo` для всех компонентов.
- **Функция без замыканий вынесена наружу,** поэтому `onSelect` стабилен без `useCallback`.

На настоящем выводе компилятора три разные буквы в поле дают один рендер `Chart` (монтирование), четыре рендера `ProductList` (`visible` каждый раз новый) и одну и ту же функцию `onSelect` во всех них.

### На чём он держится

Компилятор переиспользует результат, если входы не изменились. Это корректно, только если компонент — чистая функция от props, state и контекста. То есть компилятор опирается на **Rules of React**: рендер без побочных эффектов, props и state не мутируются, хуки вызываются по правилам (откуда эти правила — в [Механике хуков](/content/reactjs/hooks-mechanics)).

Если компилятор видит код, который может нарушать правила, он **пропускает компонент**: оставляет исходный код как есть, без мемоизации. Сборка не падает, поведение не меняется:

```jsx
function SkippedPage({ products }) {
  const [query, setQuery] = useState('');
  products.lastQuery = query;        // мутация props
  // ... дальше как в SearchPage
}
```

Для такого компонента компилятор сообщает `This value cannot be modified` и выдаёт исходник без изменений. На вводе он ведёт себя как обычный компонент: `Chart` рендерится на каждую букву, `onSelect` каждый раз новый. Так же он пропускает чтение и запись `ref.current` в рендере (`Cannot access refs during render`).

Узнать, что компонент обработан, можно по бейджу `Memo ✨` в React DevTools: нет бейджа — компилятор его пропустил. Причины пропусков показывают правила `eslint-plugin-react-hooks` на базе компилятора (`refs`, `purity`, `set-state-in-render` и другие) — они работают и без самого компилятора. Директива `'use no memo'` в начале функции выключает компиляцию одного компонента: так проверяют, не в компиляторе ли дело.

### Чего компилятор не делает

- **Не делает нужную работу дешевле.** `query` изменился — `visible` честно пересчитывается, это новый массив, и `ProductList` рендерит все 5000 строк. Компилятор убирает лишние рендеры, а не тяжёлые.
- **Не делит кеш между компонентами.** Мемоизация локальна для экземпляра компонента или хука. Дорогая функция, которую вызывают десять компонентов, посчитается десять раз.
- **Не трогает обычные функции,** только компоненты и хуки.
- **Не обходит контекст:** потребитель всё равно рендерится при смене значения.

### Нужен ли ручной useMemo

Для нового кода документация рекомендует полагаться на компилятор, а `useMemo` и `useCallback` оставить для точного контроля. Типичный случай — значение в deps эффекта, когда эффект не должен перезапускаться, даже если компилятор решит мемоизировать иначе. Ещё ручная мемоизация нужна в коде, который компилятор не обработал.

Старые `useMemo` массово удалять не стоит: компилятор учитывает существующую мемоизацию, и её удаление может поменять результат компиляции. Если компонент пропущен, удалённый `useMemo` значит новый объект на каждый рендер и перезапуск эффекта. Документация советует оставить существующую мемоизацию или удалять её только с тестами.

Компилятор убирает лишние рендеры автоматически. Но многие из них можно убрать и без всякой мемоизации — правильной структурой.

## Структура вместо мемоизации

Лишний рендер — это компонент, который оказался в поддереве, где меняется state. Самый дешёвый фикс — сделать так, чтобы он туда не попадал.

### Спустить state вниз

`query` нужен только полю и списку, а живёт в `SearchPage` — поэтому рендерится и `Chart`. Вынесем поле и список в свой компонент:

```jsx
function SearchPage({ products }) {
  return (
    <div>
      <ProductSearch products={products} />   {/* query живёт здесь */}
      <Chart data={products} />                {/* ввод его больше не касается */}
    </div>
  );
}
```

Теперь `setQuery` рендерит только `ProductSearch`. `Chart` не рендерится ни разу после монтирования, и для этого не понадобились ни `memo`, ни компилятор.

### children как props

Обратная ситуация: state у обёртки, а тяжёлое содержимое внутри. Например, раскрывающаяся панель:

```jsx
function Panel({ children }) {
  const [open, setOpen] = useState(true);
  return (
    <section hidden={!open}>
      <button onClick={() => setOpen(!open)}>Свернуть</button>
      {children}
    </section>
  );
}

<Panel><HeavyTree /></Panel>
```

Элемент `<HeavyTree />` создан в родителе `Panel`, а не в самой `Panel`. Когда меняется `open`, рендерится только `Panel`, и `children` — тот же объект элемента, что и в прошлый раз. Это тот же пропуск, что у компилятора, только руками: два переключения — три рендера `Panel` и один `HeavyTree`.

### Разделить контекст

Если в одном контексте лежат `user` и `theme`, смена `user` будит всех, кто читает `theme`. Два провайдера — два независимых списка потребителей. Этот приём и `useMemo` для значения провайдера разобраны в [Context API](/content/reactjs/context-api), а сторы с селекторами, которые будят только подписчиков на изменившуюся часть, — в [State management](/content/reactjs/state-management).

Но у `ProductList` рендер не лишний: на каждую букву список действительно должен стать другим. Ни структура, ни мемоизация этого не отменят. Остаётся сделать так, чтобы этот рендер не мешал вводу.

## Приоритеты: useTransition и useDeferredValue

Идея: ввод в поле — срочный, его нужно показать в следующем кадре. Список — несрочный, он может отстать на кадр-другой. Нужно сказать React, какой апдейт какой.

```jsx
function SearchPage({ products }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const visible = useMemo(
    () => products.filter((p) => p.name.includes(deferredQuery)),
    [products, deferredQuery],
  );
  const onSelect = useCallback((id) => track(id), []);
  const isStale = query !== deferredQuery;

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <Chart data={products} />                                {/* Chart — memo, см. выше */}
      <div style={{ opacity: isStale ? 0.5 : 1 }}>
        <ProductList items={visible} onSelect={onSelect} />   {/* ProductList — memo */}
      </div>
    </div>
  );
}
```

На каждую букву теперь два рендера. Первый — срочный: `query` уже новый, `deferredQuery` ещё старый. Поле обновляется сразу, `visible` взят из кеша, и `memo`-список пропускается. Второй — фоновый, с новым `deferredQuery`: он и рендерит 5000 строк.

В `useDeferredValue` передают примитив или объект, созданный вне рендера. Объект, созданный в рендере, каждый раз новый, и каждый рендер родителя, даже без смены `query`, добавляет лишний фоновый рендер. На первом рендере `useDeferredValue` ничего не откладывает: прошлого значения ещё нет. Второй аргумент `initialValue` позволяет отложить и его: первый рендер идёт с `initialValue` (например, пустым списком), а настоящее значение рендерится фоном.

### Что прерывается, а что нет

Фоновый рендер **прерываемый**. React рендерит компоненты по одному и примерно каждые 5 мс проверяет, не пора ли уступить поток. Если за это время пришёл ввод, React обрабатывает его и **начинает фоновый рендер заново** с новым значением. Брошенная работа выбрасывается и на экран не попадает.

В проверке это видно так. Пользователь ввёл `a`, рендер списка из 50 строк по 2 мс начат, через 20 мс он ввёл `ab`. Из 50 строк для `a` успел отрендериться примерно десяток, потом React бросил этот рендер, обработал ввод и отрендерил все 50 строк для `ab`. Список с `a` в DOM так и не появился.

Не прерываются:

- **Один компонент.** React уступает поток только между компонентами. Компонент, который считает 60 мс, отработает все 60 мс: таймер на 10 мс в проверке срабатывает примерно через 60 мс. Тяжёлый компонент нужно разбить на части или вынести вычисление в [воркер](/content/additional-topics/web-workers-and-concurrency).
- **Commit.** Изменения DOM применяются целиком и синхронно.
- **Срочные апдейты.** Рендер от ввода и клика не прерывается ничем. Поэтому `memo` у списка обязателен: без него срочный рендер тоже рендерит все строки со старым значением, и выигрыша нет. В проверке без `memo` строки рендерятся в обоих проходах.
- **Обычные апдейты и другие transitions.** `setState` из `setTimeout` или из ответа сервера transition не прерывает: React дорендерит его, а апдейт применит следом. Новый transition тоже не прерывает начатый: все transitions рендерятся вместе, и начатый рендер доделывается. Прерывает transition только апдейт с более высоким приоритетом: срочный `setState` из ввода или клика, `flushSync`, непрерывные события вроде прокрутки и движения мыши.

`useTransition` и `useDeferredValue` не делают рендер быстрее. Работа та же и в том же потоке: она просто перестаёт блокировать ввод.

### useTransition: обернуть свой апдейт

`useDeferredValue` откладывает **значение**, которое пришло готовым: prop или state, сеттер которого ты не контролируешь. Если апдейт вызываешь ты сам, его можно сразу пометить несрочным:

```jsx
const [isPending, startTransition] = useTransition();
const [tab, setTab] = useState('posts');

function selectTab(next) {
  startTransition(() => setTab(next));
}
```

`isPending` даёт обратную связь. После клика сначала идёт срочный рендер с `isPending === true` и старой вкладкой, затем рендер transition с `isPending === false` и новой. Пока он идёт, интерфейс отвечает: второй клик по другой вкладке бросит недоделанный рендер первой. Бросит именно потому, что `isPending = true` — срочный апдейт, а срочный апдейт прерывает transition.

Есть и отдельная функция `startTransition` из `react` — то же самое без `isPending`, для кода вне компонентов (например, в библиотеке данных). С ней второй клик ничего не прерывает: срочного апдейта нет, и React доделает и закоммитит рендер первой вкладки, а вторую отрендерит следом. В проверке со списком из 50 строк хук бросает первую вкладку примерно на десятой строке, а голый `startTransition` рендерит обе по 50.

Ограничения из документации:

- **Нельзя управлять текстовым полем через transition.** Если `value` у поля — state, который меняется в `startTransition`, React после события вернёт полю старое значение и покажет новое только после рендера transition. При быстром вводе буквы теряются. Поле — срочный state, тяжёлое — отдельный state в transition или `useDeferredValue`.
- **`startTransition` выполняет функцию сразу и помечает только апдейты внутри неё.** `setState` в `setTimeout` внутри — уже не transition. После `await` апдейт нужно снова обернуть в `startTransition`.
- **Функция может быть async.** Такой transition документация называет Action: `isPending` остаётся `true`, пока не закончатся все `await`, и сбрасывается в одном рендере с результатом. На этом построены формы и `useActionState` — подробно в [Server Components и React 19](/content/reactjs/rsc-and-react-19).
- **Несколько одновременных transitions** сейчас склеиваются в один.

### Transitions и Suspense

Приоритет решает и вторую проблему — лишние индикаторы загрузки. Если обычный апдейт приостанавливает уже показанный контент внутри `<Suspense>`, React прячет контент и показывает fallback: вкладка на мгновение сменяется спиннером. Тот же апдейт в transition уже показанный контент за fallback не прячет: на экране остаётся старая вкладка, `isPending === true`, а новая появится, когда данные загрузятся. `useDeferredValue` работает так же: поле показывает новый `query`, а под `<Suspense>` остаются старые результаты, которые удобно приглушить через `isStale`. Ждёт transition только ради уже показанного контента. Новая граница `<Suspense>`, которая появилась впервые, показывает свой fallback сразу, и commit её не ждёт.

### Чем это отличается от debounce

Debounce откладывает рендер на фиксированное время, но сам рендер остаётся **блокирующим**: через 300 мс начнётся тот же рендер на 150 мс, и ввод в это время всё так же ждёт. Задержка одинаковая на быстром и медленном устройстве.

Отложенный рендер начинается сразу. На быстром ноутбуке его не заметно, на медленном телефоне список отстаёт ровно настолько, насколько медленное устройство. Новая буква прерывает его, а не ждёт.

Но `useDeferredValue` не уменьшает число **запросов**: если список грузится с сервера, запрос уходит на каждую букву. Для сети debounce по-прежнему нужен, и его часто сочетают с отложенным рендером.

> Под капотом приоритет апдейта — :term[lane]{def="бит в маске приоритетов React: у каждого апдейта своя дорожка, у ввода и transition — разные"}: у ввода — синхронная дорожка, у `setTimeout` — обычная, у transitions — свои. Как планировщик выбирает, какие дорожки рендерить, и почему прерванный рендер не виден, — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber).

Приоритеты спасают ввод, но 5000 строк всё равно рендерятся и попадают в DOM. Последний шаг — не рендерить то, чего не видно.

## Длинные списки: виртуализация и ключи

5000 строк — это 5000 компонентов на каждый рендер и тысячи DOM-узлов, которые браузер раскладывает и рисует. `memo` помогает на обновлении, но монтирование и смена фильтра всё равно стоят всех строк.

### Виртуализация

**Виртуализация** рендерит только строки, попадающие в окно прокрутки, плюс небольшой запас сверху и снизу. При фиксированной высоте строки окно считается арифметикой:

```js
function getRange({ scrollTop, viewport, rowHeight, count, overscan = 3 }) {
  const first = Math.floor(scrollTop / rowHeight);
  const visible = Math.ceil(viewport / rowHeight);
  const start = Math.max(0, first - overscan);
  const end = Math.min(count, first + visible + overscan);
  return { start, end, offsetTop: start * rowHeight, totalHeight: count * rowHeight };
}

getRange({ scrollTop: 4000, viewport: 600, rowHeight: 40, count: 10000 });
// { start: 97, end: 118, offsetTop: 3880, totalHeight: 400000 } — 21 строка вместо 10 000
```

Контейнер получает высоту `totalHeight`, чтобы полоса прокрутки была честной, а видимые строки сдвигаются на `offsetTop`. Готовые решения — TanStack Virtual и react-window: они же измеряют строки разной высоты.

У виртуализации есть цена. Поиск браузера по странице не находит строки, которых нет в DOM. Скринридер видит только часть списка, поэтому нужны `aria-setsize` и `aria-posinset`. Строки переменной высоты нужно измерять, иначе прокрутка прыгает. Для длинной страницы без сложной логики иногда хватает CSS `content-visibility: auto` — о нём в [Производительности в рантайме](/content/security-perfomance/runtime-performance).

### Ключи

Ключ говорит React, какой элемент списка — какой между рендерами. Что ключ-индекс ломает корректность — state и DOM строки переезжают к соседу, — разобрано в [Компонентах и JSX](/content/reactjs/components-and-jsx). Здесь важна вторая половина: он ломает и `memo`.

Вставка одной строки в начало списка из 1000 `memo`-строк:

| Ключ | Сколько строк отрендерилось | Почему |
| --- | --- | --- |
| `key={index}` | 1001 | под каждым ключом теперь другой `item`, `memo` не срабатывает ни разу |
| `key={item.id}` | 1 | 1000 знакомых строк с теми же props и одна новая |

С индексом вставка в начало стоит столько же, сколько рендер всего списка с нуля, и никакая мемоизация строк это не исправит. Как React сопоставляет детей по ключам — в [Reconciliation и Fiber](/content/reactjs/reconciliation-and-fiber).

## Красные флаги в ответе

- **«Ререндер — это перерисовка DOM».** Рендер — вызов функции и сравнение результата. В DOM уходит только разница, а рендер с тем же результатом DOM не трогает вовсе.
- **«Компонент перерендерился, потому что изменились его props».** По умолчанию ребёнок рендерится потому, что отрендерился родитель, независимо от props. Сравнивать props начинает только `memo`.
- **«Оберну всё в `useMemo` и `useCallback` на всякий случай».** Без `memo`-получателя, deps или дорогого вычисления это лишняя работа на каждом рендере и лишний код.
- **«С React Compiler можно удалить все `useMemo`».** Компилятор пропускает компоненты с нарушениями правил, а удаление существующей мемоизации может поменять результат компиляции и поведение эффектов.
- **«`useTransition` выполняет рендер в фоне, в другом потоке».** Поток тот же и работа та же. Рендер стал прерываемым, но один долгий компонент и commit всё равно блокируют поток.
- **«`useDeferredValue` — это встроенный debounce».** Задержки нет, рендер начинается сразу и прерывается вводом. Число запросов он не уменьшает.

## Как спрашивают на собеседовании

::question{level="mid"}
Интерфейс тормозит при вводе в поле поиска. С чего начнёшь?

#mid
С замера: React DevTools Profiler с записью причин рендера покажет, что рендерится на каждую букву и сколько это стоит. Обычно вместе с полем рендерится вся страница, потому что state лежит слишком высоко. Дальше — спустить state, `memo` для тяжёлых детей, отложить тяжёлый рендер.

#senior
Сначала понять, что именно тормозит: лишние рендеры, нужный, но тяжёлый рендер, или commit и layout из-за огромного DOM. Profiler отвечает на первое (`actualDuration` против `baseDuration` показывает, работает ли мемоизация), Performance panel — на остальное: long tasks, layout, сторонние скрипты. Замер — на production-сборке с замедлением CPU, итоговая метрика — INP. Лишние рендеры лечатся структурой и мемоизацией, нужный тяжёлый — `useDeferredValue` или `useTransition` плюс `memo`, большой DOM — виртуализацией.

#followups
- «Перерендер — это всегда плохо?» → нет, рендер с тем же результатом не трогает DOM; плохо, когда рендеров много или они тяжёлые
- «Почему замер в dev врёт?» → development-сборка React медленнее и делает лишние проверки; профилирование в проде — через `react-dom/profiling`
::

::question{level="mid"}
Что делает memo и почему он часто не срабатывает?

#mid
`memo` пропускает рендер компонента, если ни один prop не изменился по `Object.is`. Не срабатывает, когда родитель передаёт объект, массив или функцию, созданные в рендере: это новая ссылка каждый раз.

#senior
К тому же списку относятся `children`: JSX внутри тега — тоже prop и тоже новый объект. `memo` не защищает от собственного state и от контекста, который компонент читает. Своя функция сравнения опасна дважды: глубокое сравнение бывает дороже рендера, а пропущенная функция-проп оставляет ребёнку stale closure. И `memo` — оптимизация, а не гарантия: код, которому он нужен для корректности, уже сломан.

#followups
- «Как сделать props стабильными?» → константа вне компонента, `useMemo`, `useCallback` или React Compiler
::

::question{level="mid"}
Когда useMemo и useCallback нужны, а когда нет?

#mid
Нужны, когда стабильная ссылка кому-то важна: `memo`-ребёнку или deps эффекта. И для дорогого вычисления с редко меняющимися deps. В остальных случаях они не ускоряют, а добавляют работу.

#senior
Цена: первый рендер немного медленнее, на каждом рендере сравниваются deps, в памяти лежит прошлое значение, а `useCallback` не экономит создание функции. Кеш хранит только последнее значение и может быть выброшен, так что на `useMemo` нельзя строить логику. «Дорого» — это измеримо: `console.time` вокруг вычисления, ориентир от 1 мс. Часто правильнее не мемоизировать, а изменить структуру: спустить state или передать тяжёлое как `children`.
::

::question{level="senior"}
Нужны ли useMemo и useCallback, если есть React Compiler?

#mid
Компилятор сам мемоизирует значения, функции и JSX на этапе сборки, поэтому в новом коде ручные `useMemo` и `useCallback` обычно не нужны.

#senior
Компилятор опирается на Rules of React: компонент, который их нарушает (мутация props, чтение ref в рендере), он пропускает и оставляет без изменений, а не ломает. Ручная мемоизация остаётся запасным выходом: когда нужна гарантированно стабильная ссылка (deps эффекта, внешняя библиотека, которая сравнивает по ссылке) и в коде, который компилятор не обработал. Массово удалять старые `useMemo` не стоит: это может поменять результат компиляции и поведение эффектов. Документация советует оставить их или удалять с тестами. Компилятор не делает нужную работу дешевле и не делит кеш между компонентами.

#followups
- «Как понять, что компилятор обработал компонент?» → бейдж `Memo ✨` в React DevTools; нет бейджа — компонент пропущен, причину покажут правила `eslint-plugin-react-hooks`
- «Как исключить один компонент?» → директива `'use no memo'` в начале функции
::

::question{level="mid"}
Как уменьшить ререндеры без memo?

#mid
Спустить state туда, где он используется, чтобы его изменение рендерило маленькое поддерево. И передать тяжёлый контент как `children`: он создан выше и не рендерится, когда меняется state обёртки.

#senior
Оба приёма работают на одном механизме: React пропускает ребёнка, если родитель вернул тот же объект элемента. `children`, созданные выше, — тот же объект, пока не отрендерился тот, кто их создал. Компилятор делает то же автоматически, кешируя JSX. Для контекста — разделить его на независимые провайдеры или перейти на стор с селекторами.
::

::question{level="senior"}
Что прерывают useTransition и useDeferredValue и чем они отличаются от debounce?

#mid
Они помечают апдейт как несрочный. Срочный ввод показывается сразу, тяжёлый рендер идёт следом и прерывается новым вводом. Debounce просто откладывает рендер на фиксированное время, а сам рендер остаётся блокирующим.

#senior
Прерывается рендер transition между компонентами: React уступает поток примерно каждые 5 мс и, если пришёл более срочный апдейт (ввод, клик, `flushSync`), бросает работу и начинает заново. Не прерываются один долгий компонент, commit и срочные рендеры. Обычный апдейт из `setTimeout` и новый transition начатый рендер не прерывают, а ждут его. Второй клик по вкладке с `useTransition` всё же бросает первую, потому что `isPending = true` — срочный апдейт; с голым `startTransition` первая вкладка доделывается. Поэтому `useDeferredValue` работает только с `memo` у тяжёлого ребёнка, иначе срочный рендер тоже рендерит его целиком. `isPending` — отдельный срочный рендер с `true` и старым state. Через transition нельзя управлять текстовым полем. И запросы `useDeferredValue` не откладывает — для сети debounce остаётся.

#followups
- «`useTransition` или `useDeferredValue`?» → `useTransition`, когда апдейт вызываешь ты; `useDeferredValue`, когда значение пришло готовым (prop, чужой state)
- «Что будет, если рендер transition приостановится в `Suspense`?» → уже показанный контент не сменится fallback-ом: на экране старое, `isPending === true`; новая граница `Suspense` покажет свой fallback сразу
- «Что с `isPending`, если в `startTransition` async-функция?» → он остаётся `true`, пока не закончатся все `await`
::

::question{level="mid"}
Как ускорить длинный список?

#mid
Виртуализация: рендерить только видимые строки плюс запас, остальное заменить пустым местом нужной высоты. Библиотеки — TanStack Virtual, react-window.

#senior
Виртуализация убирает стоимость монтирования и DOM, `memo` у строки — стоимость обновлений, но только со стабильными ключами. Ключ-индекс при вставке в начало меняет `item` у каждого ключа, и `memo` не срабатывает ни для одной строки, а state и DOM остаются у позиции. Цена виртуализации — поиск по странице, доступность (`aria-setsize`, `aria-posinset`), измерение строк разной высоты. Иногда достаточно пагинации или `content-visibility: auto`.
::

## Практика

::practice{title="Найди баг: memo не помогает"}
`ProductList` обёрнут в `memo`, но профайлер показывает его рендер на каждую букву в поле поиска. Почему?

```jsx
const ProductList = memo(function ProductList({ items, filters, onSelect }) { /* ... */ });

function Page({ products }) {
  const [query, setQuery] = useState('');
  const [selected, setSelected] = useState(null);

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ProductList
        items={products}
        filters={{ inStock: true }}
        onSelect={(id) => setSelected(id)}
      />
    </div>
  );
}
```

#solution
`filters` и `onSelect` создаются заново на каждый рендер `Page`. `Object.is` для них всегда `false`, и `memo` честно рендерит список: на три буквы — 4 рендера вместе с монтированием.

Константу выносим из компонента, функцию стабилизируем:

```jsx
const DEFAULT_FILTERS = { inStock: true };

function Page({ products }) {
  const [query, setQuery] = useState('');
  const [selected, setSelected] = useState(null);
  const onSelect = useCallback((id) => setSelected(id), []);

  return (
    <div>
      <input value={query} onChange={(e) => setQuery(e.target.value)} />
      <ProductList items={products} filters={DEFAULT_FILTERS} onSelect={onSelect} />
    </div>
  );
}
```

Теперь на ввод список не рендерится: один рендер при монтировании. Ещё лучше — спустить `query` в отдельный компонент поля: тогда `Page` не рендерится на ввод вовсе. С React Compiler обе ссылки стабилизирует он сам.
::

::practice{title="Найди баг: поле лагает и теряет буквы"}
Чтобы ввод не тормозил, поиск перевели на transition. Теперь поле ведёт себя странно: буквы появляются с опозданием, при быстром наборе часть теряется.

```jsx
function Search() {
  const [query, setQuery] = useState('');

  return (
    <>
      <input
        value={query}
        onChange={(e) => startTransition(() => setQuery(e.target.value))}
      />
      <Results query={query} />
    </>
  );
}
```

#solution
Поле контролируемое, а его `value` — state, который меняется только в transition. После события React возвращает полю текущее значение state, то есть старое. Новое появится, когда докоммитится рендер transition, а если в это время пользователь нажал следующую клавишу, браузер применит её к старому тексту. Документация прямо запрещает управлять текстовым полем через transition.

Поле — срочный state, тяжёлое — отложенное значение:

```jsx
function Search() {
  const [text, setText] = useState('');
  const deferredText = useDeferredValue(text);

  return (
    <>
      <input value={text} onChange={(e) => setText(e.target.value)} />
      <Results query={deferredText} />   {/* Results — memo */}
    </>
  );
}
```

Тот же результат даёт пара состояний: `setText` срочно и `startTransition(() => setQuery(...))` для списка.
::

::practice{title="Почему тормозит: вставка в начало списка"}
Лента из 1000 карточек, каждая карточка — `memo` и хранит раскрыта ли она. Новое сообщение добавляется сверху, после этого интерфейс подвисает, а раскрытой оказывается не та карточка.

```jsx
function Feed({ messages }) {
  return (
    <ul>
      {messages.map((m, i) => <Card key={i} message={m} />)}
    </ul>
  );
}
```

#solution
Ключ — индекс. После вставки сверху под ключом `0` новое сообщение, под ключом `1` — бывшее первое и так далее. У каждой карточки новый `message`, и `memo` не срабатывает ни разу: рендерятся все 1001 карточка. Отсюда и подвисание. А «раскрыто» переезжает к соседу, потому что state остаётся у ключа, то есть у позиции (подробно — в [Компонентах и JSX](/content/reactjs/components-and-jsx)).

```jsx
{messages.map((m) => <Card key={m.id} message={m} />)}
```

С `key={m.id}` React узнаёт 1000 старых карточек и рендерит одну новую, а state остаётся у своего сообщения. Если лента длинная, следующий шаг — виртуализация.
::
