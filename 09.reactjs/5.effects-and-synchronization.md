# Эффекты и синхронизация

`useEffect` - самый недопонятый хук. Его воспринимают как «сделать что-то после рендера» и заваливают им всё подряд. Правильная модель другая: **эффект синхронизирует компонент с внешней системой**. Если внутри нет внешней системы - скорее всего, эффект не нужен.

---

## Что такое эффект

Рендер должен быть чистым - без побочных эффектов. Но реальному приложению нужно взаимодействовать с миром за пределами React: DOM-API, подписки, таймеры, сеть, сторонние виджеты. Это и есть работа `useEffect`.

```jsx
useEffect(() => {
  // эффект: синхронизация с внешней системой
  const id = setInterval(() => console.log('tick'), 1000);

  return () => clearInterval(id); // cleanup: отмена синхронизации
}, []); // зависимости: когда пересинхронизировать
```

<b class="text-on-semi-light">Ментальная модель</b> - <span class="text-gray">Не «запусти после рендера», а «держи внешнюю систему в синхроне с этим состоянием». React сам решает, когда синхронизировать (после коммита) и когда рассинхронизировать (cleanup).</span>

---

## Зависимости

Второй аргумент управляет тем, **когда** эффект перезапускается.

```jsx
useEffect(() => { /* ... */ });          // после каждого рендера
useEffect(() => { /* ... */ }, []);      // один раз после монтирования
useEffect(() => { /* ... */ }, [userId]); // при изменении userId
```

Зависимости подчиняются тому же правилу `exhaustive-deps`, что и в [механике хуков](/content/reactjs/hooks-mechanics): всё реактивное, что используется внутри, должно быть в массиве.

---

## Cleanup

Функция, возвращённая из эффекта, - это **отмена синхронизации**. React вызывает её:

- перед повторным запуском эффекта (когда изменились зависимости);
- при размонтировании компонента.

```jsx
useEffect(() => {
  const sub = chatRoom.connect(roomId);
  return () => sub.disconnect(); // отписка перед сменой roomId и при unmount
}, [roomId]);
```

> Без cleanup получаешь утечки: дублирующиеся подписки, висящие таймеры, обработчики на удалённых элементах. Если эффект что-то «включает» - он почти всегда должен это «выключать».

### Двойной запуск в StrictMode

В dev-режиме `<StrictMode>` монтирует компонент дважды (mount → unmount → mount), чтобы проверить, что cleanup корректен. Если после двойного запуска что-то ломается - у тебя пропущен или неправильный cleanup. В проде этого нет.

## You Might Not Need an Effect

Самый важный раздел для senior-уровня. Половина эффектов в реальном коде - лишние. Признак: эффект **не работает с внешней системой**, а просто пересчитывает или копирует состояние.

### ❌ Антипаттерн 1: производное состояние через эффект

```jsx
const [items, setItems] = useState([]);
const [count, setCount] = useState(0);

useEffect(() => {
  setCount(items.length); // лишнее состояние + лишний рендер
}, [items]);
```

```jsx
// ✅ Просто вычисляй при рендере
const count = items.length;
```

### ❌ Антипаттерн 2: синхронизация состояния с props

```jsx
useEffect(() => {
  setFiltered(items.filter((i) => i.active)); // дубль данных
}, [items]);
```

```jsx
// ✅ Производная во время рендера (при необходимости - useMemo)
const filtered = items.filter((i) => i.active);
```

### ❌ Антипаттерн 3: обработка события внутри эффекта

```jsx
useEffect(() => {
  if (submitted) showToast('Готово'); // логика события «уехала» в эффект
}, [submitted]);
```

```jsx
// ✅ Делай это в обработчике события, где и произошло действие
function handleSubmit() {
  submit();
  showToast('Готово');
}
```

<b class="text-on-semi-light">Правило</b> - <span class="text-gray">Если данные можно **вычислить из существующего состояния** - вычисляй при рендере, не храни и не синхронизируй эффектом. Если что-то происходит **в ответ на действие пользователя** - это обработчик события, а не эффект. Подробнее - в [производном состоянии](/content/reactjs/derived-state-and-data-flow).</span>

---

## Когда эффект действительно нужен

- Подписки: WebSocket, `addEventListener`, обсерверы (`IntersectionObserver`).
- Императивное управление не-React виджетами (карты, чарты, video-плееры).
- Синхронизация с браузерными API: `document.title`, `localStorage`, фокус.
- Загрузка данных - но лучше через библиотеки ([загрузка данных](/content/reactjs/data-fetching)).

## useLayoutEffect

Отличается от `useEffect` **временем запуска**.

| | `useEffect` | `useLayoutEffect` |
|--|-------------|-------------------|
| Когда | после отрисовки (paint), асинхронно | после DOM-мутаций, **до** paint, синхронно |
| Блокирует отрисовку | нет | да |
| Для чего | большинство эффектов | измерить/поправить layout до того, как пользователь увидит |

```jsx
useLayoutEffect(() => {
  const { height } = ref.current.getBoundingClientRect();
  setTooltipTop(height); // поправили позицию до paint - нет «прыжка»
}, []);
```

> По умолчанию - `useEffect`. `useLayoutEffect` бери только когда нужно измерить DOM и синхронно поправить его до отрисовки, иначе блокируешь paint.

---

## Гонки запросов

Классический баг при загрузке данных в эффекте: быстрые смены зависимости приводят к тому, что ответ на **старый** запрос приходит позже нового и перезатирает данные.

```jsx
useEffect(() => {
  let ignore = false;             // флаг отмены
  fetchUser(userId).then((data) => {
    if (!ignore) setUser(data);   // игнорируем ответ устаревшего запроса
  });
  return () => { ignore = true; }; // cleanup помечает запрос неактуальным
}, [userId]);
```

Cleanup помечает предыдущий запрос «протухшим». В реальных проектах это берут на себя React Query/SWR.

---

## Связь с жизненным циклом классов

Эффекты не равны методам жизненного цикла, но дают аналоги: `useEffect(fn, [])` ≈ `componentDidMount`, cleanup ≈ `componentWillUnmount`, `useEffect(fn, [dep])` ≈ `componentDidUpdate`. Полная таблица - в [компонентах и JSX](/content/reactjs/components-and-jsx).

> Разница в мышлении: классы думают «момент жизненного цикла», эффекты - «синхронизация с состоянием». Перенос «один-в-один» из класса часто рождает лишние эффекты.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что на самом деле делает useEffect?</b>
<span class="text-gray">Синхронизирует компонент с внешней системой после коммита и рассинхронизирует через cleanup. Это не «callback после рендера».</span>

<b class="text-on-semi-light">Когда вызывается cleanup-функция?</b>
<span class="text-gray">Перед повторным запуском эффекта (при смене зависимостей) и при размонтировании компонента.</span>

<b class="text-on-semi-light">Почему в StrictMode эффект запускается дважды?</b>
<span class="text-gray">React в dev монтирует/размонтирует компонент, чтобы проверить корректность cleanup. Если двойной запуск ломает логику - cleanup неправильный.</span>

<b class="text-on-semi-light">Приведи пример, когда эффект НЕ нужен.</b>
<span class="text-gray">Производное состояние (`count = items.length`), фильтрация/трансформация данных, реакция на действие пользователя - всё это решается вычислением при рендере или в обработчике.</span>

<b class="text-on-semi-light">Чем useLayoutEffect отличается от useEffect?</b>
<span class="text-gray">`useLayoutEffect` выполняется синхронно после DOM-мутаций, но до paint, и блокирует отрисовку. Нужен для измерения/правки layout без визуального «прыжка».</span>

<b class="text-on-semi-light">Как избежать гонки запросов в эффекте?</b>
<span class="text-gray">Флаг `ignore`, который ставится в cleanup, либо `AbortController`; устаревший ответ игнорируется. На практике - React Query/SWR.</span>
