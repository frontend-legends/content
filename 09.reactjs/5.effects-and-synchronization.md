# Эффекты и синхронизация

`useEffect` — самый недопонятый хук: его считают «колбэком после рендера» и кладут в него всё подряд. Спрашивают, когда вызывается cleanup, как избежать гонки запросов и чем `useLayoutEffect` отличается от `useEffect`. Глубже — когда эффект вообще не нужен, почему линтер прав насчёт зависимостей и что делает `useEffectEvent`.

::tldr
- **Эффект синхронизирует компонент с внешней системой:** сетью, подпиской, браузерным API, сторонним виджетом. Нет внешней системы — скорее всего, эффект не нужен.
- **У эффекта два действия, а не три метода жизненного цикла:** начать синхронизацию (setup) и остановить её (cleanup). Зависимости говорят, с чем именно синхронизируемся, и не выбираются, а следуют из кода.
- **Cleanup отменяет всё, что сделал setup:** отписка, таймеры, соединения, запросы. Цепочка setup → cleanup → setup не должна отличаться от одного setup — это проверяют StrictMode и `<Activity>`.
- **Производные данные считают в рендере, реакцию на действие пишут в обработчике, сброс состояния делают через `key`.** Эффект в этих местах даёт лишний рендер и commit с несогласованными данными, а если апдейт пришёл не от клика или ввода, этот commit может попасть на экран.
- **`useLayoutEffect` выполняется до отрисовки и гарантирует, что промежуточный кадр не увидят**, `useInsertionEffect` — ещё раньше, для CSS-in-JS. `useEffectEvent` читает свежие значения, не делая их зависимостями.
::

## Что такое эффект и когда он нужен

Частый первый вопрос: «Что делает `useEffect`?» Ответ «выполняет код после рендера» формально верен, но из него не следует, когда эффект нужен, а когда нет. Начнём с того, какой вообще бывает код в компоненте.

- **Рендер** вычисляет разметку из props и state. Он обязан быть чистым: React может повторить его или выбросить (почему — в [Механике хуков](/content/reactjs/hooks-mechanics)).
- **Обработчик события** — побочный эффект, вызванный конкретным действием пользователя: кликнул «Отправить» — ушёл запрос.
- **Эффект** — побочный эффект, вызванный самим фактом показа: пока окно чата на экране, должно быть открыто соединение с комнатой. Пользователь ничего не нажимал, причина — то, что компонент отрисован с такими props.

Отсюда рабочее определение. Эффект синхронизирует компонент с :term[внешней системой]{def="всё, чем React не управляет: сеть, WebSocket, таймеры, браузерные API, DOM вне React, сторонние виджеты"}. Тест для любого эффекта — один вопрос: *что стало причиной?* Действие пользователя — это код для обработчика. «Компонент показан с такими данными» — это эффект.

Пример, который пройдёт через всю тему:

```jsx
const serverUrl = 'wss://chat.example';

function ChatRoom({ roomId }) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.on('message', (msg) => setMessages((list) => [...list, msg]));
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);

  return <MessageList messages={messages} />;
}
```

Здесь всё по делу: соединение — внешняя система, React им не управляет. Эффект выполняется после commit, когда разметка уже в DOM. Точный момент разобран в [Механике хуков](/content/reactjs/hooks-mechanics). Каждый эффект хранится в ячейке на fiber, а commit выполняет только те, у которых изменились зависимости.

Эффект описывает синхронизацию. Как думать о его жизни: когда он начинается и когда заканчивается?

## Синхронизация, а не жизненный цикл

Пройдём сценарий: `ChatRoom` показан с комнатой `general`, пользователь переключился на `travel`, потом закрыл чат. Лог соединений:

```text
connect general
disconnect general
connect travel
disconnect travel
```

У компонента три события: монтирование, обновление, размонтирование. У эффекта их нет. Он умеет только две вещи — **начать синхронизацию** (setup) и **остановить её** (cleanup). Смена комнаты для эффекта — не «обновление», а «остановить синхронизацию с `general`, начать с `travel`». Рендер с тем же `roomId` эффект не трогает вовсе.

Сравни с классом, где то же поведение размазано по трём методам:

```jsx
class ChatRoom extends Component {
  componentDidMount() {
    this.connection = createConnection(serverUrl, this.props.roomId);
    this.connection.connect();
  }
  componentDidUpdate(prevProps) {
    if (prevProps.roomId !== this.props.roomId) {
      this.connection.disconnect();
      this.connection = createConnection(serverUrl, this.props.roomId);
      this.connection.connect();
    }
  }
  componentWillUnmount() {
    this.connection.disconnect();
  }
}
```

Забудь `componentDidUpdate` — и после переключения чат молча останется в `general`. Классический баг классовых компонентов. У эффекта такой ветки нет: один и тот же код описывает синхронизацию для любого `roomId`.

### Почему «`useEffect(fn, [])` — это `componentDidMount`» неточно

Соответствие до сих пор спрашивают, и его надо уметь опровергнуть:

- **Момент другой.** `componentDidMount` выполняется синхронно до отрисовки, `useEffect` — обычно после. Ближе к `componentDidMount` по времени `useLayoutEffect`.
- **Замыкание.** Эффект видит props и state своего рендера, а не «текущие» `this.props`.
- **«Один раз» не гарантирован.** В StrictMode эффект пройдёт setup → cleanup → setup, а `<Activity>` остановит и запустит его снова без размонтирования.
- **Пустой массив означает не «при монтировании», а «эффект ни от чего реактивного не зависит».**

Таблица методов классов и их аналогов — в [Компонентах и JSX](/content/reactjs/components-and-jsx). Переносить код из класса один в один — верный способ получить лишние эффекты.

React перезапускает синхронизацию, когда меняется то, с чем синхронизируемся. Как он узнаёт, что это поменялось?

## Зависимости описывают, с чем синхронизируемся

Массив зависимостей — не расписание «когда запускать», а **список реактивных значений, которые эффект читает**. После каждого рендера React поэлементно сравнивает его с прошлым через `Object.is`. Если хоть одно значение поменялось, он выполняет cleanup и setup заново.

| Запись | Что значит |
| --- | --- |
| `useEffect(fn)` | синхронизироваться после каждого commit |
| `useEffect(fn, [])` | эффект не читает реактивных значений |
| `useEffect(fn, [roomId])` | пересинхронизироваться, когда меняется `roomId` |

### Что реактивно, а что нет

**Реактивные значения** — всё, что может измениться между рендерами: props, state и всё, что вычислено в теле компонента, включая объекты и функции. **Нереактивные** — константы вне компонента (`serverUrl` в нашем примере), функция `setState` и объект ref: React отдаёт их одними и теми же на всех рендерах, и линтер это знает. Запись в `ref.current` не вызывает рендер, поэтому и эффект не перезапустит: React ref не отслеживает.

Теперь пусть пользователь выбирает сервер, и `serverUrl` пришёл из props:

```jsx
function ChatRoom({ roomId, serverUrl }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]); // React Hook useEffect has a missing dependency: 'serverUrl'
}
```

Пользователь переключил сервер с `eu` на `us`, а соединение осталось с `eu`: React не знает, что эффект зависит от `serverUrl`. Предупреждение `exhaustive-deps` — не придирка. Линтер читает код эффекта и видит, что сказанное в массиве не совпадает с тем, что эффект делает.

### Зависимость убирают из кода, а не из массива

Если зависимость мешает, меняют код так, чтобы она стала не нужна:

- **Состояние нужно только для следующего состояния — апдейтер.** С `setMessages([...messages, msg])` в deps пришлось бы добавить `messages`, и каждое входящее сообщение переподключало бы чат. С `setMessages((list) => [...list, msg])` зависимости нет.
- **Объект или функция из рендера — создай внутри эффекта.** Созданные в теле компонента, они на каждом рендере новые, `Object.is` со старыми не совпадает, и эффект перезапускался бы после любого рендера. Внутри эффекта они никому не мешают, а в deps остаются примитивы.
- **Значение не меняется — вынеси его из компонента.** Константа вне компонента нереактивна.
- **Значение нужно прочитать, но реагировать на него не нужно — `useEffectEvent`.** О нём в конце темы.

::pitfall{title="eslint-disable над массивом зависимостей"}
#symptom
Фильтр в отчёте поменяли, а график показывает старые данные. Перезагрузка страницы помогает. В коде над массивом — `// eslint-disable-next-line react-hooks/exhaustive-deps`.
#cause
Эффект читает значение, которого нет в deps. React сравнивает только то, что указано, и не перезапускает синхронизацию: эффект продолжает работать со значениями рендера, в котором был создан.
#fix
Убрать отключение и сделать одно из четырёх: добавить значение в deps, перенести вычисление внутрь эффекта, перейти на апдейтер или вынести чтение в `useEffectEvent`. Если после этого эффект перезапускается слишком часто, причина в нестабильном объекте, а не в линтере.
::

Пересинхронизация начинается с остановки старой синхронизации. Что именно обязан сделать cleanup?

## Cleanup: что он обязан убрать

React вызывает cleanup в двух случаях: перед повторным setup, когда изменились зависимости, и при удалении компонента. Cleanup — функция из того же рендера, что и его setup, поэтому видит **старые** значения: `connection.disconnect()` закроет именно соединение с `general`, даже если на экране уже `travel`.

Требование к cleanup одно: **после него внешняя система выглядит так, будто setup не выполнялся**. Тогда цепочка setup → cleanup → setup для пользователя неотличима от одного setup.

| Setup делает | Cleanup обязан |
| --- | --- |
| `addEventListener`, подписка на стор | снять **ту же** функцию, отписаться |
| `setInterval`, `setTimeout` | `clearInterval`, `clearTimeout` |
| соединение, WebSocket | закрыть |
| `fetch` | отменить запрос или пометить ответ ненужным |
| `IntersectionObserver`, `ResizeObserver` | `disconnect()` |
| сторонний виджет: карта, график | уничтожить экземпляр |
| анимация | вернуть начальное состояние |

Не всем эффектам нужен cleanup. Идемпотентная запись вроде `document.title = name` при повторе ничего не ломает. Аналитика «страницу посмотрели» в development отправится дважды, и в документации React советуют оставить её как есть: в production двойного запуска нет.

### Эффект не может быть async

Cleanup — это возвращаемое значение, поэтому `useEffect(async () => { ... })` не работает: async-функция возвращает промис. React предупредит: `useEffect must not return anything besides a function, which is used for clean-up. It looks like you wrote useEffect(async () => ...) or returned a Promise.` Асинхронную функцию объявляют внутри эффекта и вызывают, а cleanup возвращают из самого эффекта.

### Кто проверяет cleanup: StrictMode и Activity

**StrictMode** в development при монтировании прогоняет эффекты как setup → cleanup → setup. В логе это `connect general`, `disconnect general`, `connect general`. При обновлениях и размонтировании повторов нет. Подробно, вместе с двойным рендером, — в [Механике хуков](/content/reactjs/hooks-mechanics).

**`<Activity mode="hidden">`** прячет поддерево, не размонтируя его. DOM получает `display: none`, state сохраняется, а эффекты, включая layout-эффекты, проходят cleanup. При `mode="visible"` эффекты снова проходят setup. Поэтому cleanup — это не «код для размонтирования», а «остановить синхронизацию», и вызываться он может у живого компонента.

::pitfall{title="Обработчик resize копится при каждом обновлении"}
#symptom
Со временем страница тормозит при изменении размера окна. В профайлере на одно событие `resize` — десятки вызовов, в том числе от компонентов, которых уже нет на экране.
#cause
Cleanup снимает не ту функцию:

```jsx
useEffect(() => {
  window.addEventListener('resize', () => setWidth(measure(unit)));
  return () => window.removeEventListener('resize', () => setWidth(measure(unit)));
}, [unit]);
```

Две стрелки с одинаковым текстом — две разные функции. `removeEventListener` ничего не находит, и каждый перезапуск эффекта добавляет обработчик, который переживает даже размонтирование.
#fix
Сохранить функцию в переменную и снимать её же:

```jsx
useEffect(() => {
  const onResize = () => setWidth(measure(unit));
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, [unit]);
```

Для подписок вроде размеров окна лучше подходит `useSyncExternalStore` — он сам подписывается и отписывается (подробно — в [Управлении состоянием](/content/reactjs/state-management)).
::

Таймер или подписку отменить просто. Труднее с тем, что уже запущено и закончится само, когда захочет: с сетевым запросом.

## Гонки запросов

Добавим в чат загрузку истории сообщений:

```jsx
function History({ roomId }) {
  const [messages, setMessages] = useState([]);

  useEffect(() => {
    fetchHistory(roomId).then(setMessages);
  }, [roomId]);

  return <MessageList messages={messages} />;
}
```

Пользователь открыл `general` и сразу переключился на `travel`. Ушли два запроса. Сервер ответил на `travel` быстрее, а ответ про `general` пришёл позже и перезаписал state. На экране комната `travel`, а в ней история `general`. Ответы приходят в любом порядке, и последним выигрывает не последний запрос, а самый медленный.

### Флаг ignore

Cleanup не может отозвать промис, но может пометить его ответ как ненужный:

```jsx
useEffect(() => {
  let ignore = false;
  fetchHistory(roomId).then((data) => {
    if (!ignore) setMessages(data);
  });
  return () => { ignore = true; };
}, [roomId]);
```

Каждый запуск эффекта получает свою переменную `ignore` в своём [замыкании](/content/javascript/closures). При переключении на `travel` cleanup ставит `ignore = true` для запуска с `general`, и его поздний ответ отбрасывается.

### AbortController

Флаг игнорирует ответ, но запрос продолжает идти и занимать сеть. `AbortController` отменяет сам запрос:

```jsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/rooms/${roomId}/history`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setMessages)
    .catch((e) => {
      if (e.name !== 'AbortError') setError(e);
    });
  return () => controller.abort();
}, [roomId]);
```

После `abort()` промис `fetch` отклоняется с `AbortError`. Это не ошибка, а отмена, поэтому её отфильтровывают: иначе каждое переключение комнаты показывало бы ошибку. Флаг и `AbortController` решают одну задачу. Флаг подходит к любому промису, контроллер дополнительно освобождает сеть.

`setState` после размонтирования, кстати, не опасен: раньше React предупреждал «Can't perform a React state update on an unmounted component», но предупреждение убрали. Утечки нет, лишний вызов просто игнорируется. Гонка — другое дело: это неверные данные на экране живого компонента.

### Почему данные лучше грузить не в голом эффекте

Даже с отменой у загрузки в эффекте остаются системные проблемы:

- **Эффекты не выполняются на сервере.** При SSR HTML уходит со «Загрузка…», а данные начнут грузиться только после гидратации.
- **Водопады.** Дочерний компонент начинает свой запрос, только когда родитель загрузился и отрисовал его.
- **Нет кеша и дедупликации.** Возврат на страницу — снова запрос. Два компонента с одной историей — два одинаковых запроса.

Поэтому в production данные грузят через фреймворк (загрузчики маршрутов, Server Components) или библиотеку с кешем — TanStack Query, SWR. Внутри у них те же отмена и игнорирование. Подробно — в [Загрузке данных](/content/reactjs/data-fetching).

До сих пор эффект был оправдан: соединение и сеть — внешние системы. Но в реальном коде много эффектов, где внешней системы нет вовсе.

## Когда эффект не нужен

Признак лишнего эффекта: внутри нет внешней системы, только `setState` по другому state или props. У такого эффекта цена всегда одна. React сначала коммитит DOM со старым значением, потом выполняет эффект, а тот запускает второй рендер и второй commit. Между ними DOM, refs и другие эффекты видят несогласованные данные.

Увидит ли это пользователь, зависит от причины апдейта. После клика или ввода React выполняет эффекты сразу в конце commit, и второй commit проходит в той же задаче: отрисовать промежуточный браузер не успевает. Если апдейт пришёл из сети, таймера или от наведения мыши, между двумя commit заканчивается задача, и браузер может показать кадр со старым значением.

| Задача | Через эффект | Без эффекта |
| --- | --- | --- |
| Значение из state или props | state + эффект с `setState` | вычислить в рендере |
| Реакция на действие пользователя | флаг в state + эффект | код в обработчике |
| Сброс state при смене prop | эффект с `setX(initial)` | `key` |
| Сообщить родителю об изменении | эффект, вызывающий `onChange` | вызвать `onChange` в обработчике |

### Производные данные

```jsx
// лишний state и лишний рендер
const [unread, setUnread] = useState(0);
useEffect(() => {
  setUnread(messages.filter((m) => !m.read).length);
}, [messages]);

// вычисление в рендере
const unread = messages.filter((m) => !m.read).length;
```

Пришли два непрочитанных сообщения. С эффектом компонент рендерится дважды, и первый commit кладёт в DOM `0` — старое число рядом с новым списком. Сообщения пришли из сети, а не от клика, поэтому этот commit браузер может отрисовать: счётчик мигнёт нулём. С вычислением — один рендер и сразу `2`. Если вычисление дорогое, его мемоизируют (`useMemo` или React Compiler, подробно — в [Производительности](/content/reactjs/performance)). Синхронное `setState` в эффекте ловит правило линтера `set-state-in-effect`.

### Обработчики событий

```jsx
useEffect(() => {
  if (messages.length > 0) showToast('Сообщение отправлено');
}, [messages.length]);
```

Эффект знает, *что* изменилось, но не знает *почему*. Список вырос и от отправки, и от входящего сообщения собеседника — и тост «Сообщение отправлено» покажется на чужое сообщение. Логика, привязанная к действию, живёт там, где действие произошло:

```jsx
function handleSend() {
  setMessages((list) => [...list, draft]);
  showToast('Сообщение отправлено');
}
```

### Сброс состояния через key

Вернёмся к `ChatRoom`. При переключении с `general` на `travel` компонент остаётся тем же экземпляром, и в `messages` лежат сообщения из `general`. Сброс эффектом `useEffect(() => setMessages([]), [roomId])` сработает, но вторым проходом. Первый commit под `travel` ещё содержит сообщения `general`, и с ними же выполняются эффекты новой комнаты: отметка о прочтении, прокрутка вниз. Даже если комнату переключили кликом и кадра со старыми сообщениями никто не увидел, эти эффекты уже отработали на чужих данных. Правильно отдать комнату в `key`:

```jsx
<ChatRoom key={roomId} roomId={roomId} />
```

Новый `key` — новый экземпляр компонента с чистым state, и первый же commit показывает пустую комнату. Подробно о том, что хранить и что вычислять, — в [Производном состоянии](/content/reactjs/derived-state-and-data-flow).

Остались только настоящие эффекты. Для большинства из них подходит `useEffect`. Но иногда браузер успевает отрисовать кадр между commit и эффектом, и нужен другой момент запуска.

## useLayoutEffect: измерить до отрисовки

Подсказка над кнопкой: если сверху не хватает места, её надо показать снизу. Но высоту подсказки можно узнать, только когда она уже в DOM.

```jsx
function Tooltip({ anchor, children }) {
  const ref = useRef(null);
  const [height, setHeight] = useState(0);

  useLayoutEffect(() => {
    setHeight(ref.current.getBoundingClientRect().height);
  }, []);

  // не помещается сверху — показываем снизу
  const top = anchor.top - height < 0 ? anchor.bottom : anchor.top - height;
  return <div ref={ref} style={{ position: 'fixed', top }}>{children}</div>;
}
```

Пусть у кнопки `top: 10` и `bottom: 30`, а подсказка высотой 40px. Первый рендер идёт с `height = 0`, подсказка встаёт на `top: 10` и наезжает на кнопку. Дальше всё решает момент измерения:

```text
useLayoutEffect: commit (top: 10) → измерение → setState → рендер → commit (top: 30) → кадр
useEffect:       commit (top: 10) → кадр? → измерение → setState → рендер → commit (top: 30) → кадр
```

**`useLayoutEffect` выполняется синхронно после изменения DOM, до того как браузер отрисует кадр.** `setState` внутри него вызывает повторный рендер и commit там же, в той же задаче, поэтому промежуточное положение пользователь не увидит. Это видно и в проверочном коде: микрозадача, поставленная в layout-эффекте, выполняется уже после второго commit. Попутно React сразу выполняет и оставшиеся `useEffect` этого commit — с ещё не исправленными значениями.

**С `useEffect` всё зависит от того, чем открыли подсказку.** После клика или нажатия клавиши React выполняет обычные эффекты синхронно в конце commit, повторный рендер проходит в той же задаче, и мигания нет. Если подсказку открыли наведением мыши, таймером или по ответу сети, измерение идёт отдельной задачей. Между commit и эффектом браузер может отрисовать кадр, где подсказка наезжает на кнопку: мигание. Проверочный код показывает оба расписания на одном и том же компоненте.

Отсюда вывод для собеседования: `useEffect` иногда не мигает случайно, из-за приоритета апдейта. Стоит открыть ту же подсказку наведением мыши, и она замигает. `useLayoutEffect` — гарантия, от причины апдейта она не зависит.

### Порядок: от детей к родителю

Эффекты одного commit выполняются по видам: сначала insertion-эффекты всего дерева, потом layout-эффекты, потом обычные. Внутри каждого вида ребёнок идёт раньше родителя. Поэтому к `useLayoutEffect` родителя DOM детей уже на месте и их layout-эффекты отработали: родитель может измерить то, что они нарисовали и поправили.

### Цена: кадр ждёт

Всё, что сделано в layout-эффекте, и все рендеры, которые он запустил, выполняются до отрисовки. Тяжёлая работа там задерживает кадр после клика и бьёт по :term[INP]{def="Interaction to Next Paint: метрика Core Web Vitals, задержка от действия пользователя до следующей отрисовки"} (подробно — в [Core Web Vitals](/content/web/core-web-vitals)). Поэтому по умолчанию — `useEffect`, а `useLayoutEffect` — только когда без него пользователь увидит неверный кадр: измерение и позиционирование, синхронный скролл, фокус.

Но и `useEffect` не всегда уступает кадр. Как видно на подсказке, после клика или нажатия клавиши обычные эффекты тоже выполняются до отрисовки: React делает это, чтобы результат действия был виден сразу. Тяжёлая работа в таком эффекте задерживает кадр и ухудшает INP так же, как в layout-эффекте. Её откладывают явно: в отдельную задачу через `setTimeout`, а апдейт, который она запускает, помечают `startTransition` (подробно — в [Производительности](/content/reactjs/performance)).

### На сервере эффектов нет

Ни `useEffect`, ни `useLayoutEffect` при серверном рендеринге не выполняются. Для `useLayoutEffect` это особенно заметно: на сервере нет раскладки, HTML приходит с подсказкой на месте по умолчанию, и после гидратации она прыгает. Раньше React предупреждал об этом в консоли сервера, сейчас — молча. Варианты из документации:

- заменить на `useEffect`, если начальный HTML можно показать как есть;
- рендерить такой компонент только на клиенте: флаг `isMounted`, который ставится в `useEffect`, или fallback ближайшего `<Suspense>`;
- если `useLayoutEffect` нужен для подписки на внешний стор, а не для измерений, — `useSyncExternalStore`, он поддерживает SSR.

Layout-эффекты измеряют DOM. Но если стили для этого DOM вставляет библиотека, они должны появиться ещё раньше.

## useInsertionEffect: стили раньше всех

Библиотеки :term[CSS-in-JS]{def="подход, при котором стили описывают в JavaScript, а библиотека генерирует и вставляет их на страницу"} с вставкой стилей в рантайме создают `<style>` во время работы приложения. Если вставлять их в `useLayoutEffect`, они опоздают: layout-эффекты детей выполняются раньше родительских и измерят DOM без нужных стилей. Если вставлять в рендере, при конкурентном рендеринге браузер будет пересчитывать стили на каждом кадре.

`useInsertionEffect` выполняется до всех layout-эффектов: в проверке на двух компонентах сначала оба insertion-эффекта, потом оба layout-эффекта, потом обычные эффекты. К этому моменту стили уже на странице. Ограничения следуют из того, как рано он выполняется:

- refs ещё не привязаны: при монтировании `ref.current` равен `null`, при обновлении в нём узел с прошлого commit, так что на refs не опираются;
- менять state нельзя — React предупредит `useInsertionEffect must not schedule updates.`;
- на точное состояние DOM опираться нельзя: эффект может выполниться как до, так и после его изменения.

В прикладном коде он не нужен. React рекомендует статические CSS-файлы для статических стилей и inline-стили для динамических, а `useInsertionEffect` — для авторов библиотек, которые без вставки в рантайме не обходятся.

Последний вопрос — эффекту нужно значение, на изменение которого он реагировать не должен.

## useEffectEvent: прочитать, но не реагировать

В чат добавили звук на новое сообщение, его можно выключить:

```jsx
function ChatRoom({ roomId, soundEnabled }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.on('message', (msg) => {
      setMessages((list) => [...list, msg]);
      if (soundEnabled) playSound();
    });
    connection.connect();
    return () => connection.disconnect();
  }, [roomId, soundEnabled]);
}
```

Линтер прав: эффект читает `soundEnabled`, и без него в deps обработчик видел бы старое значение — звук не выключался бы. Но с ним выключение звука переподключает чат, а сообщения, пришедшие, пока соединения нет, могут потеряться. Синхронизироваться с `soundEnabled` эффект не должен: это значение нужно только в момент события «пришло сообщение».

`useEffectEvent` отделяет такую логику от эффекта:

```jsx
function ChatRoom({ roomId, soundEnabled }) {
  const onMessage = useEffectEvent((msg) => {
    setMessages((list) => [...list, msg]);
    if (soundEnabled) playSound(); // всегда свежее значение
  });

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.on('message', (msg) => onMessage(msg));
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]); // выключение звука не переподключает чат
}
```

:term[Effect Event]{def="функция из useEffectEvent: часть логики эффекта, которая ведёт себя как обработчик события"} похож на обработчик события, только вызывает его эффект. Он видит props и state последнего **закоммиченного** рендера и при этом не входит в зависимости. Свежую версию функции React кладёт в ячейку хука во время commit, до всех layout-эффектов (как устроена ячейка — в [Механике хуков](/content/reactjs/hooks-mechanics)). Рендер, который прервали или выбросили, туда не попадёт: если переход ждёт данных и ещё не закоммичен, Effect Event видит значения с экрана.

Правила из документации:

- **вызывать только из эффектов и других Effect Events.** Вызов в рендере падает с `A function wrapped in useEffectEvent can't be called during rendering.`;
- **не класть в deps.** Функция новая на каждом рендере, это сделано намеренно, и эффект перезапускался бы всегда. `eslint-plugin-react-hooks` предупредит, если положить;
- **не передавать в другие компоненты и хуки.** Для колбэков в props есть обычные функции и `useCallback`.

### Не способ заглушить линтер

Если завернуть в Effect Event значение, на которое эффект *должен* реагировать, баг вернётся:

```jsx
const onMount = useEffectEvent(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
});
useEffect(() => onMount(), []); // смена roomId больше не переподключает
```

Линтер молчит, а чат остаётся в старой комнате — тот же баг, что у класса без `componentDidUpdate`. Вопрос для проверки: должна ли смена этого значения перезапустить синхронизацию? Да — оно в deps. Нет, оно нужно только в момент события — оно в Effect Event.

### Чем он лучше ref с последней функцией

До `useEffectEvent` ту же задачу решали ref-ом с последней версией функции. Два варианта, и у обоих есть изъян:

- **Запись в ref прямо в рендере** (`latest.current = fn`). Нарушает чистоту рендера: линтер на неё ругается, а React Compiler пропускает такой компонент. И версия из рендера, который потом выбросили, всё равно окажется в ref: эффект вызовет функцию с данными, которых на экране нет.
- **Запись в `useLayoutEffect`** — аккуратный вариант самописного `useEvent` или `useLatest`. Рендер чистый, но layout-эффекты детей выполняются раньше родительских. Ребёнок, который вызвал такой колбэк из своего layout-эффекта, получит прошлую версию.

Effect Event обновляет ячейку раньше любых layout-эффектов и только из закоммиченного рендера, поэтому у него нет ни той, ни другой проблемы.

## Как менялись эффекты

Актуально на ноябрь 2026.

| Версия | Что изменилось |
| --- | --- |
| React 16.8 (2019) | хуки: `useEffect`, `useLayoutEffect` |
| React 17 (2020) | cleanup `useEffect` выполняется асинхронно; все cleanup выполняются до всех новых эффектов |
| React 18 (2022) | `useEffect` после дискретных событий выполняется синхронно; StrictMode повторно запускает эффекты при монтировании; `useInsertionEffect`; убрано предупреждение о `setState` в размонтированном компоненте |
| React 19 (декабрь 2024) | убрано предупреждение о `useLayoutEffect` при SSR |
| React 19.2 (октябрь 2025) | `useEffectEvent`; `<Activity>`, который останавливает эффекты скрытого поддерева |

## Красные флаги в ответе

- **«useEffect — это componentDidMount, componentDidUpdate и componentWillUnmount в одном».** У эффекта нет трёх фаз — только начать и остановить синхронизацию. Он выполняется обычно после отрисовки, видит свой рендер и может быть перезапущен без размонтирования.
- **«Пустой массив зависимостей — чтобы выполнилось один раз».** Пустой массив говорит, что эффект не читает реактивных значений. Если читает — это баг со старыми данными, а «один раз» не гарантируют ни StrictMode, ни `<Activity>`.
- **«Линтер иногда ошибается, отключу `exhaustive-deps`».** Линтер сверяет массив с кодом эффекта. Лишнюю зависимость убирают, меняя код: апдейтер, объект внутри эффекта, `useEffectEvent`.
- **«Чтобы посчитать значение из state, нужен эффект».** Его считают в рендере. Эффект даёт лишний рендер и commit со старым значением, которое видят DOM и другие эффекты, а при апдейте из сети или таймера — и пользователь.
- **«Гонки нет, потому что запросы уходят по порядку».** Ответы приходят в любом порядке. Без флага `ignore` или `AbortController` побеждает самый медленный ответ.
- **«useLayoutEffect быстрее, потому что раньше».** Он блокирует кадр: всё, что в нём и после его `setState`, выполняется до отрисовки и ухудшает INP.

## Как спрашивают на собеседовании

::question
Что на самом деле делает useEffect? Когда он нужен?

#answer
Синхронизирует компонент с внешней системой: соединением, подпиской, браузерным API, сторонним виджетом. Setup начинает синхронизацию, cleanup останавливает. Если внутри нет внешней системы — например, только `setState` по другому state, — эффект не нужен.

#more
Главный тест — причина побочного эффекта. Если его вызвало действие пользователя, это обработчик. Если сам факт показа компонента с этими данными — эффект. С точки зрения эффекта нет монтирования и обновления: есть «начать синхронизацию с текущими значениями» и «остановить». Поэтому код получается один на все `roomId`, а не три метода жизненного цикла, где легко забыть ветку обновления. Выполняется он после commit, обычно после отрисовки, и на сервере не выполняется вовсе.

#followups
- «Чем `useEffect(fn, [])` отличается от `componentDidMount`?» → выполняется обычно после отрисовки, замыкает свой рендер, в StrictMode и `<Activity>` перезапускается
::

::question
Линтер требует добавить зависимость, а с ней эффект перезапускается слишком часто. Что делать?

#answer
Не отключать линтер. Пропущенная зависимость — это эффект со старыми данными. Нужно поменять код так, чтобы зависимость стала не нужна.

#more
Deps не выбираются, а следуют из кода: это все реактивные значения, которые читает эффект. Варианты: если состояние нужно только для следующего — апдейтер `setX((prev) => ...)`. Если в deps объект или функция из рендера — создать их внутри эффекта и оставить примитивы. Если значение не меняется — вынести из компонента. Если его нужно прочитать в момент события, но синхронизироваться с ним не нужно — `useEffectEvent`. Проверочный вопрос: должна ли смена значения перезапустить синхронизацию? Если да, его место в deps, и прятать его в Effect Event — тот же баг.

#followups
- «Почему `setState` и `ref` можно не указывать?» → React отдаёт их одними и теми же на всех рендерах, линтер это знает
- «Почему Effect Event нельзя класть в deps?» → функция намеренно новая на каждом рендере, эффект перезапускался бы всегда
::

::question
Когда вызывается cleanup и что он должен убрать?

#answer
Перед повторным запуском эффекта, когда изменились зависимости, и при удалении компонента. Убрать он должен всё, что сделал setup: отписаться, снять обработчики, очистить таймеры, закрыть соединение, отменить запрос.

#more
Cleanup — функция из того же рендера, что и setup, и видит его значения, поэтому закрывает именно старое соединение. Критерий правильности: setup → cleanup → setup неотличим от одного setup. В development это проверяет StrictMode: при монтировании он прогоняет такую цепочку. `<Activity mode="hidden">` вызывает cleanup у живого компонента с сохранённым state. Частая ошибка — `removeEventListener` с новой стрелкой вместо той же функции: обработчик не снимается и копится.

#followups
- «Почему в development эффект выполняется дважды?» → это StrictMode проверяет cleanup; в production повтора нет, а ref-флаг «уже запускали» прячет отсутствие cleanup
- «Почему нельзя `useEffect(async () => ...)`?» → async-функция возвращает промис, а React ждёт функцию cleanup; React предупредит в консоли
::

::question
Как избежать гонки запросов в эффекте?

#answer
Флаг `ignore`, который cleanup выставляет в `true`: ответ устаревшего запроса игнорируется. Или `AbortController`: cleanup вызывает `abort()`, и запрос отменяется.

#more
Ответы приходят в любом порядке, поэтому без отмены побеждает самый медленный, а не последний. Флаг работает с любым промисом, но запрос продолжает идти. `AbortController` освобождает сеть, а промис отклоняется с `AbortError`, который надо отфильтровать в `catch`, иначе каждое переключение покажет ошибку. В production загрузку чаще отдают фреймворку или TanStack Query: эффекты не выполняются на сервере, создают водопады и не кешируют.

#followups
- «А `setState` после размонтирования — утечка?» → нет, React игнорирует такой вызов и больше не предупреждает; опасна именно гонка на живом компоненте
::

::question
Приведи примеры, когда эффект не нужен.

#answer
Значение, которое вычисляется из state или props: его считают прямо в рендере. Реакция на клик или отправку формы — это код обработчика. Сброс state при смене prop — через `key`.

#more
Общая цена лишнего эффекта: React коммитит DOM со старым значением, потом эффект делает `setState`, и нужен второй рендер — лишний проход и commit, в котором DOM, refs и другие эффекты видят несогласованные данные. После клика или ввода второй commit успевает до отрисовки, но при апдейте из сети, таймера или hover браузер может показать промежуточный кадр. Эффект ещё и теряет причину: тост «отправлено», привязанный к длине списка, сработает и на входящее сообщение. То же с `onChange` родителю из эффекта: он вызовется на монтировании и при смене данных, которые пользователь не трогал. Синхронное `setState` в эффекте ловит правило линтера `set-state-in-effect`.
::

::question
Чем useLayoutEffect отличается от useEffect?

#answer
`useLayoutEffect` выполняется синхронно после изменения DOM, до того как браузер отрисует кадр. `useEffect` обычно выполняется после отрисовки. `useLayoutEffect` нужен, чтобы измерить DOM и поправить его без мигания, например спозиционировать тултип.

#more
Оба выполняются в commit после изменений DOM. Layout-эффекты синхронны и блокируют отрисовку: всё, что в них, и рендеры от их `setState` задерживают кадр и ухудшают INP. Обычные эффекты идут отдельной задачей, кроме апдейтов от дискретных событий (клик, ввод): тогда React выполняет их синхронно в конце commit. Поэтому `useEffect` иногда не мигает случайно — подсказка, открытая кликом, встанет на место до кадра, а по hover мигнёт; `useLayoutEffect` — гарантия. Обратная сторона: после клика тяжёлая работа в `useEffect` тоже задерживает кадр, её откладывают явно. Внутри каждого вида эффекты идут от детей к родителю. Порядок на обновлении: cleanup предыдущих layout-эффектов, setup новых, потом то же для обычных. На сервере не выполняется ни один из них, поэтому раскладка, посчитанная в `useLayoutEffect`, после гидратации прыгает.

#followups
- «Что будет, если вызвать `setState` в `useLayoutEffect`?» → синхронный повторный рендер и commit до отрисовки; заодно сразу выполнятся оставшиеся `useEffect` этого commit
- «А `useInsertionEffect`?» → ещё раньше всех layout-эффектов, для вставки стилей CSS-in-JS; refs ещё не привязаны, `setState` нельзя
::

::question
Что такое useEffectEvent и когда его нельзя использовать?

#answer
Хук, который выносит из эффекта логику, которой нужны свежие props и state, но на изменение которых эффект реагировать не должен. Например, звук на новое сообщение: настройка звука нужна в момент события, но её смена не должна переподключать чат.

#more
Effect Event видит значения последнего закоммиченного рендера и не входит в deps: React обновляет его ячейку в commit, до всех layout-эффектов. Вызывать его можно только из эффектов, в рендере он падает с ошибкой. Его нельзя передавать в другие компоненты, а функция намеренно новая на каждом рендере. Главное ограничение — не прятать в нём реактивное значение, с которым эффект должен синхронизироваться: если обернуть подключение к `roomId`, линтер замолчит, а смена комнаты перестанет переподключать. Раньше ту же задачу решали ref-ом с последней функцией. Запись в рендере нарушает чистоту и захватывает версию из выброшенного рендера. Запись в `useLayoutEffect` чистая, но layout-эффекты детей выполняются раньше родительских и видят прошлую версию.
::

## Практика

::practice{title="Найди баг: результаты поиска не совпадают с запросом"}
Пользователь быстро печатает «react». Иногда под полем остаются результаты для «re», а в Network на каждую букву свой запрос.

```jsx
function SearchResults({ query }) {
  const [results, setResults] = useState([]);

  useEffect(() => {
    fetch(`/api/search?q=${query}`)
      .then((r) => r.json())
      .then(setResults);
  }, [query]);

  return <ResultList items={results} />;
}
```

#solution
Две проблемы. Первая — гонка: ответ на «re» пришёл после ответа на «react» и перезаписал state. Вторая — запрос на каждую букву, хотя нужен только последний. Обе решает один cleanup: он снимает таймер debounce, если пользователь печатает дальше, и отменяет запрос, если тот уже ушёл.

```jsx
function SearchResults({ query }) {
  const [results, setResults] = useState([]);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    const timer = setTimeout(() => {
      fetch(`/api/search?q=${encodeURIComponent(query)}`, { signal: controller.signal })
        .then((r) => r.json())
        .then((data) => {
          setResults(data);
          setError(null);
        })
        .catch((e) => {
          if (e.name !== 'AbortError') setError(e); // отмена — не ошибка
        });
    }, 300);

    return () => {
      clearTimeout(timer);
      controller.abort();
    };
  }, [query]);

  if (error) return <ErrorMessage error={error} />;
  return <ResultList items={results} />;
}
```

Почему `catch` стоит в конце цепочки, а не сразу после `fetch`? Отмена может застать запрос и после прихода заголовков, пока читается тело. Тогда `fetch` уже выполнился, а с `AbortError` отклоняется `r.json()`. Один `catch` в конце ловит оба случая.

Ошибку кладут в state, а не пробрасывают через `throw` из `catch`: исключение в промисе — это unhandled rejection, Error Boundary его не поймает. Попутно добавлен `encodeURIComponent`: без него запрос с `&` или `#` сломает URL. Кеш ответов, чтобы стирание буквы не отправляло запрос повторно, даёт TanStack Query.
::

::practice{title="Почему чат переподключается при наборе сообщения?"}
В Network видно, что на каждое нажатие клавиши в поле черновика WebSocket закрывается и открывается заново.

```jsx
function ChatRoom({ roomId }) {
  const [draft, setDraft] = useState('');
  const options = { serverUrl, roomId };

  useEffect(() => {
    const connection = createConnection(options);
    connection.connect();
    return () => connection.disconnect();
  }, [options]);

  return <input value={draft} onChange={(e) => setDraft(e.target.value)} />;
}
```

#solution
Каждое нажатие меняет `draft` и вызывает рендер. На каждом рендере `options` — новый объект, `Object.is` его со старым не совпадает, и React перезапускает эффект: три символа — три переподключения. Объект создают внутри эффекта, а в deps остаётся примитив:

```jsx
useEffect(() => {
  const options = { serverUrl, roomId };
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

Теперь черновик чат не трогает, а смена комнаты переподключает — как и должна. Если объект приходит из props, достают его примитивные поля до эффекта: `const { serverUrl, roomId } = options`.
::

::practice{title="Убери лишние эффекты"}
Форма профиля работает, но рендерится дважды на каждую правку, а родитель получает `onChange` сразу при открытии формы.

```jsx
function ProfileForm({ user, onChange }) {
  const [firstName, setFirstName] = useState(user.firstName);
  const [lastName, setLastName] = useState(user.lastName);
  const [fullName, setFullName] = useState('');

  useEffect(() => {
    setFullName(firstName + ' ' + lastName);
  }, [firstName, lastName]);

  useEffect(() => {
    setFirstName(user.firstName);
    setLastName(user.lastName);
  }, [user.id]);

  useEffect(() => {
    onChange({ firstName, lastName });
  }, [firstName, lastName]);

  return (
    <>
      <h2>{fullName}</h2>
      <input value={firstName} onChange={(e) => setFirstName(e.target.value)} />
    </>
  );
}
```

#solution
Ни в одном эффекте нет внешней системы:

- `fullName` — производное значение, его считают в рендере;
- сброс при смене пользователя — `key` у родителя;
- `onChange` — реакция на правку, ему место в обработчике. Эффект вызывает его и на монтировании, и при смене пользователя, хотя никто ничего не правил.

```jsx
function ProfileForm({ user, onChange }) {
  const [firstName, setFirstName] = useState(user.firstName);
  const [lastName, setLastName] = useState(user.lastName);
  const fullName = firstName + ' ' + lastName;

  function handleFirstName(e) {
    setFirstName(e.target.value);
    onChange({ firstName: e.target.value, lastName });
  }

  return (
    <>
      <h2>{fullName}</h2>
      <input value={firstName} onChange={handleFirstName} />
    </>
  );
}

// у родителя
<ProfileForm key={user.id} user={user} onChange={save} />
```

Один рендер на правку, `onChange` — только когда пользователь что-то поменял, смена пользователя сразу показывает его данные.
::
