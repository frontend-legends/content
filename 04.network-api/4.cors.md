# CORS

CORS — протокол из заголовков, по которому сервер разрешает страницам с других origin читать свои ответы. Браузер решает, отправить ли запрос сразу или сначала спросить разрешения, и по ответу решает, отдать ли его коду. Спрашивают, когда происходит preflight, какие заголовки нужны и как работают куки в межсайтовых запросах. Глубже — почему `Content-Type: application/json` удваивает число запросов, почему заголовок из ответа читается как `null` и почему CDN ломает CORS для второго сайта.

::tldr
- **Same-Origin Policy запрещает скрипту читать ответы с другого origin, а CORS — способ сервера это разрешить** заголовком `Access-Control-Allow-Origin`. Запрос при этом может дойти до сервера — браузер блокирует только чтение.
- **Простые запросы уходят сразу, остальные — после preflight `OPTIONS`.** Простой — GET, HEAD или POST только с безопасными заголовками и `Content-Type` из трёх значений; `application/json`, `PUT`, `DELETE` и свои заголовки требуют preflight.
- **Ответ на preflight кешируется на `Access-Control-Max-Age`**, без заголовка — на пять секунд. Preflight не несёт кук и авторизации и должен вернуть 2xx, иначе основной запрос не уйдёт.
- **Код видит только безопасные заголовки ответа;** остальные открывают через `Access-Control-Expose-Headers`.
- **С куками (`credentials: 'include'`) нужен точный origin вместо `*` и `Access-Control-Allow-Credentials: true`;** ответ, который зависит от origin, помечают `Vary: Origin`.
::

## Зачем нужен CORS

Сквозной пример — магазин на `https://shop.example` ходит в API на `https://api.shop.example`. Для браузера это разные **origin**: origin — схема, хост и порт вместе ([Что такое веб](/content/web/what-is-web)).

**Same-Origin Policy** (SOP) запрещает скрипту одного origin читать ответы другого. Без неё любой сайт мог бы сделать `fetch` в банк, где пользователь залогинен, и прочитать ответ. Встраивать чужие ресурсы — картинки, скрипты, стили — и отправлять формы SOP разрешает: так веб работал всегда. Запрещено именно **чтение** ответа скриптом. Почему это граница безопасности и чем origin отличается от site — в [CORS и same-origin](/content/security-perfomance/cors-and-same-origin).

**CORS** (Cross-Origin Resource Sharing) — протокол, по которому сервер разрешает конкретным origin читать свои ответы. Решение принимает браузер по заголовкам ответа:

```text
GET /products HTTP/1.1
Host: api.shop.example
Origin: https://shop.example

HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://shop.example
Content-Type: application/json
```

Браузер сам добавляет `Origin` к межсайтовому запросу. Если `Access-Control-Allow-Origin` совпадает с ним или равен `*`, код получает ответ. Если нет — `fetch` отклоняется с `TypeError: Failed to fetch`, а подробности видны только в консоли: скрипту нельзя узнать даже статус, иначе это была бы утечка.

Важно: CORS защищает пользователя от чужого скрипта, а не сервер. Запрос мог уже дойти и выполниться — браузер не отдал только ответ. А `curl` и серверный код CORS не проверяют вовсе.

## Простые запросы и preflight

Браузер делит запросы на два вида по тому, мог ли такой запрос отправить сайт и без CORS — формой или картинкой.

**Простой запрос** уходит сразу, без вопросов. Условия:

- метод `GET`, `HEAD` или `POST`;
- только безопасные заголовки: `Accept`, `Accept-Language`, `Content-Language`, `Content-Type` и ещё несколько;
- `Content-Type` — только `text/plain`, `application/x-www-form-urlencoded` или `multipart/form-data`.

Всё остальное — **непростой запрос**, и перед ним браузер отправляет **preflight**: запрос `OPTIONS` с вопросом «можно ли?»:

```text
OPTIONS /cart HTTP/1.1
Origin: https://shop.example
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: content-type, x-request-id

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://shop.example
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: content-type, x-request-id
Access-Control-Max-Age: 600
```

Только если ответ разрешает метод и заголовки, браузер отправляет настоящий запрос. В проверке в Chromium сервер увидел:

| Запрос | Preflight |
| --- | --- |
| `GET` | нет |
| `POST` с `text/plain` | нет |
| `POST` с формой `x-www-form-urlencoded` | нет |
| `GET` с `Accept-Language` | нет |
| `POST` с `application/json` | да |
| `GET` с заголовком `X-Request-Id` | да |
| `PUT`, `DELETE` | да |

Самое частое на практике: **любой JSON-запрос к API на другом origin — это два запроса**, потому что `application/json` не входит в список. Почему так: форма никогда не могла отправить JSON, значит, старые серверы не ожидают такого запроса с чужого сайта, и браузер сначала спрашивает разрешения.

### Кеш preflight

Ответ на preflight браузер кеширует для пары «origin и URL» на время из `Access-Control-Max-Age`. В проверке с `Max-Age: 600` второй `PUT` на тот же адрес ушёл без `OPTIONS`, с `Max-Age: 0` — preflight был каждый раз, а без заголовка кеш жил пять секунд. Браузеры ограничивают срок сверху: Chromium — двумя часами.

Кеш привязан к URL, поэтому API вида `/cart/items/17`, `/cart/items/18` получает preflight на каждый новый адрес. Это одна из причин держать API на том же origin — через прокси или BFF.

### Правила для preflight

- **Preflight идёт без кук и без `Authorization`** даже при `credentials: 'include'` — в проверке у `OPTIONS` их не было. Поэтому middleware авторизации, который отвечает 401 на всё без токена, ломает CORS: в проверке после 401 на preflight основной `POST` не отправился вовсе.
- **Ответ должен быть 2xx.** Редирект или ошибка на `OPTIONS` — запрос заблокирован.
- **`Access-Control-Allow-Headers: *`** разрешает любые заголовки для запросов без кук. По спецификации Fetch `Authorization` под звёздочку не попадает и должен быть указан явно. В проверке Chromium пропустил `Authorization` и со звёздочкой, но полагаться на это нельзя — перечисляй `Authorization` явно.

## Что код видит в ответе

Даже разрешённый ответ показывается скрипту не целиком. Без дополнительных разрешений доступны только безопасные заголовки ответа: `Cache-Control`, `Content-Language`, `Content-Length`, `Content-Type`, `Expires`, `Last-Modified`, `Pragma`. Остальные — `X-Total-Count`, `ETag`, `Link` для пагинации, `Retry-After` — `headers.get` вернёт как `null`.

```text
Access-Control-Expose-Headers: X-Total-Count, ETag
```

В проверке `X-Total-Count: 42` без этого заголовка читался как `null`, а с ним — как `'42'`. Классический баг пагинации: сервер отдаёт общее число записей в заголовке, в DevTools оно видно, а код его не получает.

### Режим no-cors

`fetch(url, { mode: 'no-cors' })` часто советуют как «исправление» CORS-ошибки. На деле запрос уходит, но ответ становится **непрозрачным**: `type: 'opaque'`, `status: 0`, ни заголовков, ни тела — в проверке так и вышло. Этот режим нужен Service Worker, чтобы кешировать чужие картинки и скрипты, но прочитать данные он не позволяет.

## Куки и учётные данные

По умолчанию `fetch` отправляет куки только на свой origin (`credentials: 'same-origin'`). Чтобы межсайтовый запрос нёс куки и HTTP-авторизацию, нужны две стороны:

```js
fetch('https://api.shop.example/me', { credentials: 'include' });
```

```text
Access-Control-Allow-Origin: https://shop.example
Access-Control-Allow-Credentials: true
```

С учётными данными `*` запрещена — и в `Allow-Origin`, и в `Allow-Headers`, и в `Allow-Methods`: только явные значения. В проверке запрос с `credentials: 'include'` и `Allow-Origin: *` был заблокирован, а с точным origin и `Allow-Credentials: true` прошёл.

Есть и третья сторона — сами куки. Для межсайтового запроса кука должна быть `SameSite=None; Secure`, иначе браузер её не приложит, как бы ни были настроены заголовки CORS ([Аутентификация](/content/network-api/auth)). А браузеры всё строже ограничивают сторонние куки, поэтому для API, которому нужны куки, надёжнее тот же сайт, чем `credentials: 'include'` на чужой.

## CORS и кеши

Если сервер разрешает несколько origin, он отвечает каждому своим `Access-Control-Allow-Origin`. Ответ зависит от заголовка запроса `Origin` — и кеш должен это знать:

```text
Access-Control-Allow-Origin: https://shop.example
Vary: Origin
```

Без `Vary: Origin` CDN закеширует ответ с разрешением для первого сайта и отдаст его второму. В проверке «кеш» без учёта origin отдал второму сайту заголовок, выписанный для первого, и браузер заблокировал ответ. Ошибка выглядит как «CORS сломан у части пользователей, и то не всегда».

### Редиректы

Межсайтовый запрос может следовать за редиректом, но после перехода на другой origin браузер заменяет `Origin` на `null` — цепочка уже «запачкана» чужим origin. В проверке сервер после редиректа увидел `Origin: null`. Второй сервер должен разрешать `null` или, лучше, редиректа на другой origin в API быть не должно.

## Как обычно чинят CORS-ошибки

| Ошибка в консоли | Причина | Исправление |
| --- | --- | --- |
| No 'Access-Control-Allow-Origin' header | сервер не выдал разрешение, часто — упал с 500 без CORS-заголовков | добавить заголовки, в том числе в ответы с ошибками |
| Response to preflight request doesn't pass access control check | `OPTIONS` не обработан или вернул 401 | обработать `OPTIONS` до авторизации |
| Request header field X is not allowed | заголовок не перечислен в `Allow-Headers` | добавить его |
| The value must not be the wildcard '*' when credentials mode is 'include' | `*` вместе с куками | явный origin и `Allow-Credentials` |

В разработке CORS обходят прокси dev-сервера: Vite отправляет `/api` на бэкенд, и для браузера всё с одного origin. В продакшене то же делает обратный прокси, CDN или BFF ([API и BFF](/content/architecture/api-and-bff)). Расширения браузера, отключающие CORS, ничего не исправляют — у пользователей их нет.

Какие ошибки настройки CORS опасны — отражение любого `Origin`, `null` в списке разрешённых, — в [CORS и same-origin](/content/security-perfomance/cors-and-same-origin).

## Красные флаги в ответе

- **«CORS защищает сервер от чужих запросов».** Запрос доходит до сервера; CORS решает только, отдать ли ответ скрипту.
- **«Добавлю `mode: 'no-cors'`, и ошибка пропадёт».** Пропадёт и ответ: он станет непрозрачным, без статуса и тела.
- **«Preflight бывает только у PUT и DELETE».** Любой `application/json` или свой заголовок требуют preflight, даже у POST и GET.
- **«Сервер прислал заголовок, значит, код его прочитает».** Без `Access-Control-Expose-Headers` код видит только безопасные заголовки.
- **«С куками поставлю `Access-Control-Allow-Origin: *`».** С учётными данными звёздочка запрещена.
- **«CORS — настройка фронтенда».** Это заголовки сервера; на клиенте её не исправить.

## Как спрашивают на собеседовании

::question
Что такое CORS и зачем он нужен?

#answer
Same-Origin Policy запрещает скрипту читать ответы с другого origin — схемы, хоста и порта. CORS — протокол заголовков, которым сервер разрешает конкретным origin читать свои ответы. Браузер добавляет к межсайтовому запросу `Origin`, а по `Access-Control-Allow-Origin` в ответе решает, отдать ли ответ коду.

#more
Запрос при этом может дойти до сервера и выполниться — CORS ограничивает чтение, а не отправку, поэтому от CSRF он не защищает. Вне браузера CORS не действует. Ошибку CORS скрипт видит только как `TypeError: Failed to fetch`, без статуса — подробности в консоли.
::

::question
Когда браузер отправляет preflight?

#answer
Для любого непростого запроса. Простой — `GET`, `HEAD` или `POST` только с безопасными заголовками и `Content-Type` из трёх значений: `text/plain`, `application/x-www-form-urlencoded`, `multipart/form-data`. Всё остальное — `application/json`, `PUT`, `DELETE`, `PATCH`, свои заголовки вроде `Authorization` или `X-Request-Id` — сначала идёт `OPTIONS` с вопросом о методе и заголовках.

#more
Логика: простой запрос сайт мог отправить и раньше, формой, поэтому сервер обязан с ним справляться; остальные — новые возможности, о которых сервер должен явно сказать «да». В проверке `POST` с `text/plain` ушёл без preflight, а с `application/json` — после `OPTIONS`. Ответ на preflight кешируется на `Access-Control-Max-Age`.
::

::question
Почему каждый JSON-запрос к API — это два запроса? Как это исправить?

#answer
`Content-Type: application/json` не входит в список простых типов, поэтому перед каждым запросом браузер отправляет preflight `OPTIONS`. Если сервер не ставит `Access-Control-Max-Age`, ответ на preflight кешируется всего на пять секунд, а для каждого нового URL — заново.

#more
Исправления: `Access-Control-Max-Age` на сервере (Chromium ограничивает его двумя часами), но кеш всё равно привязан к URL, и `/items/17`, `/items/18` получают свой preflight. Радикально — API на том же origin через прокси или BFF: тогда CORS и preflight исчезают. Переходить на `text/plain` ради обхода preflight — плохая идея: сервер должен разбирать тип, а не угадывать.
::

::question
Почему заголовок ответа виден в DevTools, но `headers.get` возвращает `null`?

#answer
Для межсайтовых ответов скрипт видит только безопасные заголовки: `Content-Type`, `Content-Length`, `Cache-Control`, `Expires`, `Last-Modified`, `Content-Language`, `Pragma`. Остальные сервер должен перечислить в `Access-Control-Expose-Headers`.

#more
Классические жертвы — `X-Total-Count` для пагинации, `ETag` для условных запросов, `Retry-After` для повторов, `Link`. В проверке `X-Total-Count` без открытия читался как `null`, с ним — как значение. В ответах с куками звёздочка в `Expose-Headers` не работает — нужен явный список.
::

::question
Как отправить куки в межсайтовом запросе?

#answer
На клиенте — `credentials: 'include'` в `fetch` или `withCredentials` в XHR. На сервере — `Access-Control-Allow-Credentials: true` и точный origin в `Access-Control-Allow-Origin`, без звёздочки. Сама кука должна быть `SameSite=None; Secure`, иначе браузер её не приложит.

#more
Preflight кук не несёт, поэтому его нельзя закрывать авторизацией. Сторонние куки браузеры всё сильнее ограничивают, поэтому API, которому нужны куки, лучше держать на том же сайте: поддомен того же регистрируемого домена — уже same-site, и `SameSite=Lax` работает. Ответы, зависящие от origin, помечают `Vary: Origin`.
::

::question
Можно ли обойти CORS на клиенте?

#answer
Нет: это правило браузера, и решение принимает сервер своими заголовками. `mode: 'no-cors'` даёт непрозрачный ответ без статуса и тела. Обход на практике — не делать запрос межсайтовым: прокси dev-сервера в разработке и обратный прокси, CDN или BFF на том же origin в продакшене.

#more
Прокси работает, потому что CORS действует только между браузером и сервером, а сервер-прокси может ходить куда угодно. Расширения, отключающие проверки, ничего не исправляют для пользователей. Публичные «CORS-прокси» опасны: через них проходят данные и токены.
::

::question
Почему CORS работает у одних пользователей и ломается у других?

#answer
Частая причина — кеш без `Vary: Origin`. Сервер отвечает каждому сайту своим `Access-Control-Allow-Origin`, CDN кеширует первый ответ и отдаёт его всем. Пользователи второго сайта получают разрешение для первого, и браузер блокирует ответ.

#more
В проверке кеш без учёта origin отдал второму сайту заголовок первого, и `fetch` упал. Другие причины «плавающей» ошибки: CORS-заголовки есть в успешных ответах, но не в ответах с ошибками — тогда любая 500 выглядит как CORS-ошибка; кеш preflight, который ещё помнит старые разрешения.
::

## Практика

::practice{title="Число товаров не приходит"}
Сервер каталога на `api.shop.example` отдаёт заголовок `X-Total-Count`, и в DevTools он виден. Код пагинации:

```js
const res = await fetch('https://api.shop.example/products?page=2');
const total = Number(res.headers.get('X-Total-Count')); // 0
```

Почему ноль и как исправить?

#solution
Ответ межсайтовый, и скрипт видит только безопасные заголовки. `X-Total-Count` к ним не относится, поэтому `headers.get` возвращает `null`, а `Number(null)` — 0. Сервер должен открыть заголовок:

```text
Access-Control-Allow-Origin: https://shop.example
Access-Control-Expose-Headers: X-Total-Count
```

В проверке без `Expose-Headers` значение читалось как `null`, с ним — как `'42'`. Альтернатива — отдавать общее число в теле ответа вместе с данными, тогда CORS не мешает.
::


::practice{title="Заказ не отправляется, а сервер не видит POST"}
После добавления проверки токена на сервере перестало работать оформление заказа с `shop.example`. В логах сервера — только `OPTIONS /orders 401`, а сам `POST` не приходит:

```js
app.use((req, res, next) => {
  if (!req.headers.authorization) return res.status(401).end();
  next();
});
app.use(cors({ origin: 'https://shop.example' }));
```

Почему и как исправить?

#solution
`POST` с `application/json` и `Authorization` требует preflight. Preflight `OPTIONS` идёт **без** `Authorization` — браузер никогда не прикладывает к нему учётные данные. Middleware авторизации стоит раньше CORS и отвечает 401, браузер считает preflight проваленным и не отправляет `POST`. В проверке после 401 на preflight сервер больше ничего не получил.

CORS и ответ на `OPTIONS` должны идти до авторизации:

```js
app.use(cors({
  origin: 'https://shop.example',
  allowedHeaders: ['content-type', 'authorization'],
  maxAge: 600,
}));
app.use((req, res, next) => {
  if (req.method === 'OPTIONS') return next();
  if (!req.headers.authorization) return res.status(401).end();
  next();
});
```

Пакет `cors` сам отвечает на `OPTIONS` и не передаёт его дальше. `Authorization` перечисляют в `allowedHeaders` явно: по спецификации звёздочка его не покрывает.
::

::practice{title="Половина пользователей получает CORS-ошибку"}
API отдаёт `Access-Control-Allow-Origin` по списку разрешённых origin: `shop.example` и `partner.example`. После подключения CDN примерно половина запросов с `partner.example` падает с CORS-ошибкой, а с `shop.example` всё работает. Что случилось?

#solution
CDN кеширует ответ по URL. Первым его запросил `shop.example`, и в кеш попал ответ с `Access-Control-Allow-Origin: https://shop.example`. Этот же ответ CDN отдаёт `partner.example`, и браузер блокирует его. В проверке «кеш» без учёта origin воспроизвёл именно это.

Ответ зависит от заголовка `Origin`, значит, сервер обязан сказать об этом кешу:

```js
res.setHeader('Access-Control-Allow-Origin', allowed.has(origin) ? origin : 'null');
res.setHeader('Vary', 'Origin');
```

С `Vary: Origin` CDN хранит отдельный вариант для каждого origin. Если ответ одинаков для всех и не требует кук, можно отдавать `Access-Control-Allow-Origin: *` — тогда `Vary` не нужен.
