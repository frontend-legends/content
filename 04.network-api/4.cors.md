# CORS и Same-Origin Policy

Каждый фронтенд-разработчик хотя бы раз видел красную ошибку в консоли: «Access to fetch has been blocked by CORS policy». Это не баг - это защитный механизм браузера. Чтобы перестать «лечить» CORS вслепую, нужно понять, как работают Same-Origin Policy и CORS на уровне заголовков и preflight-запросов.

---

## Same-Origin Policy (SOP)

<b class="text-on-semi-light">Origin</b>

<span class="text-gray">Origin - это комбинация **scheme** (протокол) + **host** (домен) + **port**. Два URL имеют одинаковый origin, только если все три части совпадают.</span>

```text
https://example.com:443/path/page

scheme: https
host:   example.com
port:   443
```

### Примеры сравнения origin

| URL A                  | URL B                   | Одинаковый origin? | Причина                |
| ---------------------- | ----------------------- | ------------------ | ---------------------- |
| `https://app.com`      | `https://app.com/about` | Да                 | Путь не влияет         |
| `https://app.com`      | `http://app.com`        | Нет                | Разный scheme          |
| `https://app.com`      | `https://api.app.com`   | Нет                | Разный host (субдомен) |
| `https://app.com:443`  | `https://app.com`       | Да                 | 443 - дефолт для HTTPS |
| `https://app.com:3000` | `https://app.com:4000`  | Нет                | Разный port            |

<b class="text-on-semi-light">Same-Origin Policy</b>

<span class="text-gray">SOP - политика безопасности браузера, которая запрещает скриптам одного origin читать данные с другого origin. Это защита пользователя: без SOP любой сайт мог бы отправить запрос к твоему банку и прочитать ответ (куки отправятся автоматически).</span>

### Что SOP блокирует и что нет

| Ресурс / Действие               | Разрешено cross-origin? | Пояснение                                                |
| ------------------------------- | ----------------------- | -------------------------------------------------------- |
| `<img src="...">`               | Да                      | Изображения загружаются свободно                         |
| `<script src="...">`            | Да                      | Скрипты исполняются, но их код нельзя прочитать через JS |
| `<link rel="stylesheet">`       | Да                      | CSS загружается свободно                                 |
| `<video>`, `<audio>`            | Да                      | Медиа загружается свободно                               |
| `<form action="...">`           | Да                      | Форма отправляет данные (навигация)                      |
| `fetch()` / `XMLHttpRequest`    | Нет (без CORS)          | Ответ блокируется браузером                              |
| `<iframe>` содержимое           | Частично                | Загрузка - да, доступ к DOM - нет                        |
| `<canvas>` + cross-origin image | Нет (`tainted`)         | Canvas становится «загрязнённым», нельзя читать пиксели  |
| Чтение cookies другого origin   | Нет                     | Куки привязаны к origin                                  |

> SOP блокирует **чтение** ответа, а не **отправку** запроса. Запрос уходит на сервер - но браузер не отдаёт ответ скрипту.

## CORS - Cross-Origin Resource Sharing

CORS - механизм, позволяющий серверу **явно разрешить** cross-origin доступ к своим ресурсам. Это ослабление SOP через HTTP-заголовки.

Логика простая: браузер спрашивает сервер «можно ли этому origin читать твой ответ?», а сервер отвечает через заголовок `Access-Control-Allow-Origin`.

---

## Simple Requests vs Preflight

Не все cross-origin запросы одинаковы. Браузер делит их на **простые** (simple) и **требующие preflight**.

<b class="text-on-semi-light">Simple Request (простой запрос)</b>

<span class="text-gray">Отправляется напрямую, без предварительного OPTIONS-запроса. Должен соответствовать **всем** условиям:</span>

- Метод: `GET`, `HEAD` или `POST`
- Заголовки: только CORS-safelisted (`Accept`, `Accept-Language`, `Content-Language`, `Content-Type`)
- `Content-Type`: только `application/x-www-form-urlencoded`, `multipart/form-data` или `text/plain`
- Нет event listeners на `XMLHttpRequest.upload`
- Нет `ReadableStream` в запросе

```js
// Это simple request - preflight не будет
fetch("https://api.example.com/data");

// Это тоже simple request
fetch("https://api.example.com/form", {
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
  body: "name=John&age=30",
});
```

<b class="text-on-semi-light">Preflight Request (предварительный запрос)</b>

<span class="text-gray">Если запрос не подходит под «простой», браузер сначала отправляет `OPTIONS`-запрос, чтобы узнать, разрешён ли реальный запрос. Только после положительного ответа отправляется основной запрос.</span>

```js
// Это вызовет preflight - Content-Type: application/json не в safelisted
fetch("https://api.example.com/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "John" }),
});

// Это тоже вызовет preflight - метод PUT
fetch("https://api.example.com/users/1", {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Jane" }),
});
```

### Как выглядит preflight

```text
1. Браузер отправляет OPTIONS:
   OPTIONS /users HTTP/1.1
   Origin: https://app.example.com
   Access-Control-Request-Method: POST
   Access-Control-Request-Headers: Content-Type, Authorization

2. Сервер отвечает:
   HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: https://app.example.com
   Access-Control-Allow-Methods: GET, POST, PUT, DELETE
   Access-Control-Allow-Headers: Content-Type, Authorization
   Access-Control-Max-Age: 86400

3. Браузер отправляет реальный запрос:
   POST /users HTTP/1.1
   Origin: https://app.example.com
   Content-Type: application/json
   Authorization: Bearer eyJhbG...
```

## Access-Control-\* заголовки

### Заголовки ответа (сервер устанавливает)

| Заголовок                          | Кто задаёт | Что делает                                                          |
| ---------------------------------- | ---------- | ------------------------------------------------------------------- |
| `Access-Control-Allow-Origin`      | Сервер     | Какой origin может читать ответ. `*` - любой, или конкретный origin |
| `Access-Control-Allow-Methods`     | Сервер     | Разрешённые HTTP-методы (в preflight-ответе)                        |
| `Access-Control-Allow-Headers`     | Сервер     | Разрешённые заголовки запроса (в preflight-ответе)                  |
| `Access-Control-Allow-Credentials` | Сервер     | `true` - разрешить отправку cookies/auth                            |
| `Access-Control-Expose-Headers`    | Сервер     | Какие заголовки ответа доступны JS (по умолчанию только safelisted) |
| `Access-Control-Max-Age`           | Сервер     | Сколько секунд кэшировать preflight (не повторять OPTIONS)          |

### Заголовки запроса (браузер добавляет автоматически)

| Заголовок                        | Кто задаёт | Что делает                                |
| -------------------------------- | ---------- | ----------------------------------------- |
| `Origin`                         | Браузер    | Текущий origin страницы                   |
| `Access-Control-Request-Method`  | Браузер    | Метод реального запроса (в preflight)     |
| `Access-Control-Request-Headers` | Браузер    | Заголовки реального запроса (в preflight) |

> `Access-Control-Allow-Origin` - единственный **обязательный** CORS-заголовок для любого cross-origin ответа. Без него браузер заблокирует ответ.

## Credentials и куки в cross-origin запросах

По умолчанию cross-origin запросы **не отправляют** cookies, HTTP-авторизацию и TLS-сертификаты клиента. Чтобы это включить, нужны настройки и на клиенте, и на сервере.

<b class="text-on-semi-light">На клиенте</b>

```js
// fetch
fetch("https://api.example.com/me", {
  credentials: "include", // отправлять cookies cross-origin
});

// XMLHttpRequest
const xhr = new XMLHttpRequest();
xhr.withCredentials = true;
```

<b class="text-on-semi-light">На сервере</b>

```text
Access-Control-Allow-Credentials: true
Access-Control-Allow-Origin: https://app.example.com   // НЕ * !
```

⚠️ **Критическое ограничение:** если `Access-Control-Allow-Credentials: true`, то `Access-Control-Allow-Origin` **не может** быть `*`. Сервер обязан указать конкретный origin. То же самое касается `Access-Control-Allow-Headers` и `Access-Control-Allow-Methods` - в credentialed-запросах `*` не работает как wildcard.

> Подробнее о cookies и аутентификации - [Аутентификация](/content/network-api/auth).

## Типичные ошибки и как их решать

### Ошибка 1: «No 'Access-Control-Allow-Origin' header is present»

Сервер не отдаёт CORS-заголовки. Решение - настроить сервер:

```js
// Express.js
const cors = require("cors");
app.use(
  cors({
    origin: "https://app.example.com",
    credentials: true,
  }),
);
```

### Ошибка 2: «The value of the 'Access-Control-Allow-Origin' header must not be the wildcard '\*'»

Ты используешь `credentials: 'include'`, но сервер отвечает `Access-Control-Allow-Origin: *`. Нужен конкретный origin.

```js
// Динамический origin на сервере
app.use(
  cors({
    origin: (origin, callback) => {
      const allowedOrigins = [
        "https://app.example.com",
        "https://staging.example.com",
      ];
      if (!origin || allowedOrigins.includes(origin)) {
        callback(null, origin);
      } else {
        callback(new Error("Not allowed by CORS"));
      }
    },
    credentials: true,
  }),
);
```

### Ошибка 3: «Request header field authorization is not allowed»

Сервер не разрешает кастомный заголовок в preflight-ответе. Нужно добавить его в `Access-Control-Allow-Headers`.

### Ошибка 4: Preflight на каждый запрос - тормоза

Сервер не задаёт `Access-Control-Max-Age`. Браузер повторяет OPTIONS перед каждым запросом. Добавь кэширование:

```text
Access-Control-Max-Age: 86400   // кэшировать preflight на 24 часа
```

### Обходное решение: прокси

Если ты не контролируешь сервер, используй прокси на своём бэкенде или dev-сервере:

```js
// vite.config.js - прокси для разработки
export default {
  server: {
    proxy: {
      "/api": {
        target: "https://external-api.com",
        changeOrigin: true,
        rewrite: (path) => path.replace(/^\/api/, ""),
      },
    },
  },
};
```

<span class="text-gray">Прокси работает на сервере, а не в браузере - SOP и CORS к нему не применяются. Запрос идёт `browser -> твой сервер -> внешний API`, и для браузера это same-origin.</span>

> Подробнее о fetch и запросах - [Fetching](/content/network-api/fetching). Про HTTP-заголовки - [HTTP](/content/network-api/http).

## Частые вопросы на собесе

**Что такое origin и чем отличается от domain?**
Origin = scheme + host + port. Domain - только host-часть. Два URL с одинаковым domain, но разным портом - разные origin.

**Почему SOP не блокирует `<img>` и `<script>`, но блокирует `fetch()`?**
Исторически теги `<img>`, `<script>`, `<link>` всегда загружали ресурсы cross-origin (так работает веб с 90-х). SOP блокирует **программный доступ** к ответу через JS API. Тег загрузит скрипт и выполнит его, но JS не может прочитать его текст.

**Когда происходит preflight?**
Когда запрос не является «простым»: кастомные заголовки (`Authorization`, `Content-Type: application/json`), методы кроме GET/HEAD/POST, или наличие `ReadableStream`.

**Можно ли обойти CORS на клиенте?**
Нет. CORS - механизм браузера, его нельзя отключить из JS. Единственное решение - настроить сервер или использовать прокси.
