# Основы сетей для фронтендера

Ты пишешь `fetch('/api/users')` и получаешь данные. Но между твоим вызовом и ответом сервера происходит целая цепочка сетевых событий: DNS-резолвинг, TCP-соединение, TLS-шифрование, маршрутизация через CDN. На собеседованиях эти знания проверяют постоянно - и не потому, что ты должен настраивать роутеры, а потому что понимание сетевого стека помогает диагностировать проблемы, оптимизировать загрузку и принимать архитектурные решения.

---

## Клиент-серверная модель

<b class="text-on-semi-light">Client</b>

<span class="text-gray">Программа, которая инициирует запрос. В нашем случае - браузер, мобильное приложение или Node.js-скрипт. Клиент знает, **куда** обратиться (адрес), **что** попросить (запрос) и **как** интерпретировать ответ.</span>

<b class="text-on-semi-light">Server</b>

<span class="text-gray">Программа, которая слушает входящие запросы и отвечает на них. Один сервер может обслуживать тысячи клиентов одновременно. Физически это может быть один компьютер или кластер за load balancer.</span>

```text
Client (браузер)                    Server (backend)
     │                                    │
     │──── HTTP Request ────────────────>│
     │     GET /api/users                 │
     │                                    │
     │<──── HTTP Response ──────────────│
     │      200 OK + JSON body            │
```

## IP-адреса и порты

<b class="text-on-semi-light">IP-адрес</b>

<span class="text-gray">Уникальный числовой идентификатор устройства в сети. Как почтовый адрес - без него невозможно доставить пакет данных.</span>

| Версия   | Формат                      | Пример         | Количество адресов |
| -------- | --------------------------- | -------------- | ------------------ |
| **IPv4** | 4 октета (32 бит)           | `192.168.1.1`  | ~4.3 миллиарда     |
| **IPv6** | 8 групп по 16 бит (128 бит) | `2001:0db8::1` | 3.4 × 10^38        |

<span class="text-gray">IPv4-адресов давно не хватает - поэтому существует NAT (Network Address Translation), который позволяет нескольким устройствам в локальной сети использовать один публичный IP. IPv6 решает проблему нехватки адресов, но переход идёт медленно - на практике большинство веб-серверов поддерживают оба протокола (dual stack).</span>

<b class="text-on-semi-light">Порт</b>

<span class="text-gray">Числовой идентификатор (0–65535), который указывает **конкретный сервис** на машине. IP-адрес - это адрес дома, порт - номер квартиры.</span>

| Порт             | Сервис               |
| ---------------- | -------------------- |
| 80               | HTTP                 |
| 443              | HTTPS                |
| 22               | SSH                  |
| 3000, 5173, 8080 | Типичные dev-серверы |

```text
https://example.com:443/api/users
         │           │      │
     hostname      port    path
```

<span class="text-gray">Если порт не указан в URL, браузер подставляет дефолтный: 80 для HTTP, 443 для HTTPS.</span>

## TCP vs UDP

Два основных транспортных протокола. Фронтендеру важно понимать разницу, потому что HTTP работает поверх TCP (а HTTP/3 - поверх QUIC, который построен на UDP).

| Характеристика        | TCP                                     | UDP                                    |
| --------------------- | --------------------------------------- | -------------------------------------- |
| **Соединение**        | Connection-oriented (handshake)         | Connectionless                         |
| **Надёжность**        | Гарантирует доставку и порядок          | Не гарантирует ни доставку, ни порядок |
| **Контроль потока**   | Есть (flow control, congestion control) | Нет                                    |
| **Скорость**          | Медленнее из-за overhead                | Быстрее (меньше overhead)              |
| **Применение в вебе** | HTTP/1.1, HTTP/2, WebSocket             | HTTP/3 (QUIC), WebRTC, DNS (иногда)    |
| **Handshake**         | 3-way (SYN -> SYN-ACK -> ACK)           | Нет                                    |

<b class="text-on-semi-light">TCP 3-way handshake</b>

```text
Client                Server
  │── SYN ──────────>│     1. Клиент хочет соединиться
  │<── SYN-ACK ─────│     2. Сервер подтверждает и отвечает
  │── ACK ──────────>│     3. Клиент подтверждает - соединение установлено
```

<span class="text-gray">Каждый TCP handshake - это 1 RTT (round-trip time). Для HTTPS добавляется ещё TLS handshake. Именно поэтому повторное использование соединений (keep-alive, connection pooling) критически важно для производительности.</span>

## DNS: как домен превращается в IP

Когда ты вводишь `example.com`, браузер не знает, куда отправлять запрос - ему нужен IP-адрес. DNS (Domain Name System) - это «телефонная книга» интернета.

<b class="text-on-semi-light">Шаги DNS-резолвинга</b>

```text
1. Кэш браузера        - может, мы уже знаем IP?
2. Кэш ОС              - может, другое приложение уже резолвило?
3. Роутер / ISP кэш    - ближайший кэш провайдера
4. Recursive resolver   - ISP или публичный DNS (8.8.8.8, 1.1.1.1)
5. Root nameserver      - "Кто знает про .com?"
6. TLD nameserver       - "Кто знает про example.com?"
7. Authoritative NS     - "example.com = 93.184.216.34"
```

<span class="text-gray">На практике большинство запросов разрешаются из кэша на шагах 1–4. Полный путь от root до authoritative проходится только для новых доменов или после истечения TTL (Time to Live).</span>

<b class="text-on-semi-light">DNS-записи, которые стоит знать</b>

| Тип записи | Назначение         | Пример                               |
| ---------- | ------------------ | ------------------------------------ |
| **A**      | Домен -> IPv4      | `example.com -> 93.184.216.34`       |
| **AAAA**   | Домен -> IPv6      | `example.com -> 2606:2800:220:1:...` |
| **CNAME**  | Алиас домена       | `www.example.com -> example.com`     |
| **MX**     | Почтовый сервер    | `example.com -> mail.example.com`    |
| **TXT**    | Произвольный текст | SPF, DKIM, верификация домена        |
| **NS**     | Nameserver домена  | `example.com -> ns1.example.com`     |

<b class="text-on-semi-light">Оптимизация DNS для фронтенда</b>

```html
<!-- Заранее зарезолвить DNS для стороннего домена -->
<link rel="dns-prefetch" href="https://api.example.com" />

<!-- DNS + TCP + TLS - полное предварительное соединение -->
<link rel="preconnect" href="https://fonts.googleapis.com" />
```

<span class="text-gray">`dns-prefetch` стоит использовать для доменов, к которым ты точно обратишься, но не сразу. `preconnect` - для критических ресурсов: API-домена, CDN шрифтов.</span>

## TLS/HTTPS: шифрование на транспортном уровне

<b class="text-on-semi-light">Зачем нужен HTTPS</b>

<span class="text-gray">HTTP передаёт данные открытым текстом - любой, кто находится между клиентом и сервером (провайдер, Wi-Fi роутер, MITM-атакующий), может прочитать и подменить данные. TLS (Transport Layer Security) добавляет шифрование, аутентификацию сервера и проверку целостности.</span>

```text
HTTP:   Client ────── plaintext ──────> Server
HTTPS:  Client ══════ encrypted ══════> Server (TLS tunnel)
```

<b class="text-on-semi-light">TLS handshake (упрощённо, TLS 1.3)</b>

```text
Client                              Server
  │── ClientHello ────────────────>│  (cipher suites, key share)
  │<── ServerHello + Certificate ──│  (выбранный cipher, сертификат, key share)
  │── Finished ───────────────────>│
  │<══ Encrypted data ════════════>│
```

<span class="text-gray">TLS 1.3 устанавливает шифрованное соединение за **1 RTT** (в TLS 1.2 было 2 RTT). При повторном подключении возможен **0-RTT** - клиент отправляет данные сразу, используя сохранённые ключи от предыдущей сессии.</span>

<b class="text-on-semi-light">Сертификаты и цепочка доверия</b>

```text
Root CA (встроен в ОС/браузер)
  └── Intermediate CA (подписан Root CA)
        └── Сертификат сайта (подписан Intermediate CA)
```

<span class="text-gray">Браузер проверяет цепочку: сертификат сайта -> intermediate -> root. Если цепочка не выстраивается - появляется предупреждение «соединение не защищено». Бесплатные сертификаты можно получить через **Let's Encrypt**.</span>

> Подробнее о шифровании, алгоритмах и JWT - [Шифрование и безопасность](/content/computer-science/encryption).

## CDN: ускорение доставки контента

<b class="text-on-semi-light">Content Delivery Network</b>

<span class="text-gray">Сеть серверов (edge nodes), распределённых по миру. Вместо того чтобы каждый раз обращаться к origin-серверу в одном дата-центре, пользователь получает контент с ближайшего edge-сервера. Это снижает latency и разгружает origin.</span>

```text
Без CDN:
  Пользователь (Москва) ──── 150ms ────> Origin (Нью-Йорк)

С CDN:
  Пользователь (Москва) ──── 20ms ────> Edge (Москва) ── cache hit
                                         │
                                         └── cache miss ──> Origin (Нью-Йорк)
```

<b class="text-on-semi-light">Что CDN кэширует</b>

- Статические файлы: JS-бандлы, CSS, изображения, шрифты
- HTML-страницы (при SSG/SSR с правильными заголовками)
- API-ответы (с `Cache-Control`)

<b class="text-on-semi-light">Стратегии инвалидации</b>

| Стратегия           | Как работает                                                  |
| ------------------- | ------------------------------------------------------------- |
| **Content hashing** | Файл `app.a1b2c3.js` - меняется хэш при изменении содержимого |
| **Cache-Control**   | `max-age`, `s-maxage`, `stale-while-revalidate`               |
| **Purge API**       | Принудительная очистка кэша CDN через API                     |

<span class="text-gray">Популярные CDN: Cloudflare, AWS CloudFront, Fastly, Vercel Edge Network, Akamai. Если ты деплоишь на Vercel или Netlify - CDN уже настроен автоматически.</span>

> О HTTP-кэшировании и заголовках подробнее - [Кэширование](/content/network-api/caching).

## Модель OSI и TCP/IP - кратко

На собеседованиях иногда спрашивают про модель OSI. Не нужно заучивать все 7 уровней - достаточно понимать, на каком уровне работает то, с чем ты сталкиваешься.

| Уровень TCP/IP  | Уровни OSI                                     | Что здесь                        | Примеры                     |
| --------------- | ---------------------------------------------- | -------------------------------- | --------------------------- |
| **Application** | 7 (Application), 6 (Presentation), 5 (Session) | Протоколы приложений             | HTTP, HTTPS, DNS, WebSocket |
| **Transport**   | 4 (Transport)                                  | Доставка данных между процессами | TCP, UDP, QUIC              |
| **Internet**    | 3 (Network)                                    | Маршрутизация пакетов            | IP, ICMP                    |
| **Link**        | 2 (Data Link), 1 (Physical)                    | Физическая передача              | Ethernet, Wi-Fi             |

<span class="text-gray">Для фронтенд-разработчика критичны верхние два уровня: Application (HTTP, WebSocket) и Transport (TCP, UDP/QUIC). Нижние уровни - зона ответственности сетевых инженеров.</span>

## Часто спрашивают на собеседовании

<b class="text-on-semi-light">Чем TCP отличается от UDP?</b>

<span class="text-gray">TCP - надёжный, с гарантией доставки и порядка, но медленнее (handshake, retransmission). UDP - быстрый, без гарантий, используется там, где скорость важнее надёжности (видео, игры, QUIC). HTTP/3 работает поверх QUIC (UDP), но QUIC сам реализует надёжность на уровне протокола.</span>

<b class="text-on-semi-light">Что такое DNS и зачем он нужен?</b>

<span class="text-gray">DNS преобразует доменное имя в IP-адрес. Без DNS пришлось бы запоминать числовые адреса. Резолвинг проходит через цепочку кэшей (браузер -> ОС -> ISP -> recursive resolver) и серверов (root -> TLD -> authoritative).</span>

<b class="text-on-semi-light">Что даёт HTTPS по сравнению с HTTP?</b>

<span class="text-gray">Шифрование (никто не прочитает данные), аутентификация (ты разговариваешь именно с тем сервером), целостность (данные не подменены в пути). Без HTTPS не работают Service Workers, Geolocation API, Web Crypto API и другие secure-only API.</span>

<b class="text-on-semi-light">Зачем нужен CDN?</b>

<span class="text-gray">CDN уменьшает latency, раздавая контент с ближайшего edge-сервера. Разгружает origin-сервер, защищает от DDoS, ускоряет TTFB. Для статических ресурсов с content hashing - must-have.</span>
