# Основы сетей

Каждый `fetch` опирается на стопку протоколов: IP доставляет пакеты между компьютерами, TCP или UDP — между программами, DNS превращает имя в адрес, а поверх работают TLS и HTTP. Спрашивают, чем TCP отличается от UDP, что такое порт и как работает DNS. Глубже — почему TCP не знает, где кончается одно сообщение, почему `localhost` иногда не находит запущенный сервер и почему задержка важнее ширины канала.

::tldr
- **Сеть устроена слоями:** IP доставляет пакеты до компьютера, TCP и UDP — до программы на нём по номеру порта, прикладные протоколы (HTTP, DNS, WebSocket) работают поверх.
- **TCP — надёжный упорядоченный поток байтов, а не сообщений.** Две записи могут прийти одним куском, одна — несколькими, поэтому протоколы поверх TCP сами размечают границы: `Content-Length`, кадры WebSocket, перевод строки.
- **UDP — отдельные датаграммы без гарантий доставки и порядка, зато без установки соединения.** На нём работают DNS, видеозвонки и HTTP/3.
- **DNS переводит имя в IP-адрес через цепочку серверов и кеширует ответы на время TTL.** Поэтому смена адреса сервера доходит до пользователей не сразу.
- **Скорость загрузки страниц ограничивает задержка (RTT), а не ширина канала.** Каждый круг «запрос — ответ» стоит десятки и сотни миллисекунд, и их число важнее мегабит.
::

## Слои сети

Сквозной пример — интернет-магазин чая: сайт на `shop.example`, API на `api.shop.example`, разработка на `localhost:5173`.

Когда браузер отправляет запрос к API, данные проходят через несколько уровней. Каждый решает свою задачу и не знает о деталях соседних:

| Уровень (модель TCP/IP) | Задача | Протоколы | Адрес |
| --- | --- | --- | --- |
| прикладной | смысл обмена | HTTP, DNS, WebSocket, TLS | URL, имя |
| транспортный | доставка до программы | TCP, UDP, QUIC | порт |
| сетевой | доставка до компьютера через маршрутизаторы | IP | IP-адрес |
| канальный и физический | передача по проводу или радио | Ethernet, Wi-Fi | MAC-адрес |

Каждый уровень заворачивает данные верхнего в свой конверт с заголовком, а получатель разворачивает их в обратном порядке. Классическая модель OSI делит то же на семь уровней, но на практике говорят о четырёх уровнях TCP/IP. Для фронтенда важны верхние три.

## IP-адреса и порты

**IP-адрес** определяет компьютер в сети. IPv4 — 32 бита, четыре числа: `93.184.216.34`. Их всего около четырёх миллиардов, и они давно закончились. Поэтому дома и в офисах компьютеры получают **частные адреса** (`192.168.x.x`, `10.x.x.x`), а маршрутизатор подменяет их на один публичный — это **NAT**. IPv6 — 128 бит, `2606:2800:220:1::`, — адресов хватит всем, но переход идёт десятилетиями.

Особые адреса: `127.0.0.1` в IPv4 и `::1` в IPv6 — **loopback**, свой же компьютер. Имя `localhost` указывает на оба.

**Порт** — номер от 0 до 65535, который определяет программу на компьютере. HTTP по умолчанию на 80, HTTPS — на 443, dev-сервер Vite — на 5173. Пара «адрес и порт» с обеих сторон и протокол однозначно определяют соединение. Два процесса не могут слушать один порт на одном адресе: в проверке второй сервер получил `EADDRINUSE`. Соединение с портом, который никто не слушает, ОС сразу отклоняет — `ECONNREFUSED`.

Порт — часть origin, поэтому `localhost:5173` и `localhost:3000` для браузера — разные источники, и запрос между ними подчиняется CORS ([CORS](/content/network-api/cors)).

### localhost — это два адреса

`localhost` разрешается и в `::1`, и в `127.0.0.1`, и современные ОС часто отдают IPv6 первым. В проверке Node.js получил `::1` первым адресом. Если бэкенд слушает только `127.0.0.1`, а клиент идёт на `localhost` и пробует только первый адрес, соединение отклоняется, хотя сервер запущен. Node.js по умолчанию перебирает адреса по очереди (алгоритм Happy Eyeballs) и спасает ситуацию, а инструменты с отключённым перебором — нет. Это частая причина «прокси dev-сервера не видит бэкенд».

## TCP

**TCP** доставляет данные между программами надёжно и по порядку. Для этого он:

- **устанавливает соединение** тройным рукопожатием: SYN, SYN-ACK, ACK. Это один круг туда и обратно до первого байта данных;
- **нумерует байты и требует подтверждений** — потерянное отправляется заново, перепутанное складывается по порядку;
- **регулирует скорость** — начинает осторожно и разгоняется, пока не начнутся потери. Первое окно — около 10 сегментов, примерно 14 КБ: столько сервер может отправить в первый круг, не дожидаясь подтверждений.

Главное, что упускают: TCP передаёт **поток байтов, а не сообщений**. Он не знает, где кончается одно сообщение и начинается следующее. В проверке клиент сделал две записи JSON, а сервер получил их одним куском — `JSON.parse` на нём падает. Большая запись, наоборот, пришла несколькими кусками.

```text
отправлено: {"type":"price","value":450}  +  {"type":"price","value":480}
получено:   {"type":"price","value":450}{"type":"price","value":480}
```

Поэтому протоколы поверх TCP размечают границы сами: HTTP — заголовком `Content-Length` или кусками с длиной, WebSocket — кадрами с длиной, построчные протоколы — переводом строки.

Цена надёжности — **блокировка начала очереди** (head-of-line blocking): если потерялся один пакет, все следующие ждут его повтора, даже если относятся к другим запросам. Эта проблема и привела к HTTP/3 ([HTTP](/content/network-api/http)).

## UDP

**UDP** просто отправляет датаграммы: без соединения, без подтверждений, без порядка. Пакет может потеряться, прийти дважды или раньше предыдущего — программа разбирается сама. Зато нет рукопожатия и ожидания повторов, а границы сообщений сохраняются: в проверке две отправки пришли двумя отдельными сообщениями.

| | TCP | UDP |
| --- | --- | --- |
| Соединение | есть, рукопожатие перед данными | нет |
| Доставка и порядок | гарантированы | не гарантированы |
| Единица данных | поток байтов | датаграмма |
| Потеря пакета | задерживает всё следующее | теряется только он |
| Где | HTTP/1.1, HTTP/2, WebSocket, базы данных | DNS, видео и звонки, игры, QUIC и HTTP/3 |

Для звонка в WebRTC опоздавший кадр бесполезен, поэтому UDP подходит лучше: проще потерять кадр, чем остановить разговор ([Медиа и WebRTC](/content/additional-topics/media-and-webrtc)). QUIC — протокол HTTP/3 — реализует надёжность сам поверх UDP, но для каждого потока отдельно, чтобы потеря в одном не тормозила другие.

## DNS

Люди помнят имена, а сеть работает с адресами. **DNS** — распределённая база, которая переводит `api.shop.example` в IP-адрес.

Разрешение имени идёт по цепочке:

1. **Кеши** — браузера, ОС, роутера. Если ответ есть и не истёк, сеть не нужна.
2. **Рекурсивный резолвер** — сервер провайдера или публичный (`1.1.1.1`, `8.8.8.8`). Он проходит цепочку за клиента.
3. **Корневой сервер** отвечает, кто отвечает за зону `.example`.
4. **Сервер зоны** `.example` называет сервер, отвечающий за `shop.example`.
5. **Авторитетный сервер** `shop.example` возвращает адрес.

Основные записи:

| Запись | Что хранит |
| --- | --- |
| `A` / `AAAA` | IPv4 и IPv6 адрес |
| `CNAME` | псевдоним: `www.shop.example` → `shop.example` |
| `MX` | почтовый сервер |
| `TXT` | произвольный текст: подтверждение владения доменом, SPF |
| `NS` | какие серверы отвечают за зону |

У каждой записи есть **TTL** — сколько секунд её можно кешировать. Переезд на новый сервер с TTL в сутки дойдёт до части пользователей только через сутки, поэтому перед переездом TTL заранее уменьшают. Обычный DNS идёт открытым текстом по UDP; DNS-over-HTTPS скрывает запросы от сети.

Браузер может разрешить имя заранее — подсказки `dns-prefetch` и `preconnect` разобраны в [Производительности загрузки](/content/security-perfomance/loading-performance). Весь путь запроса от DNS до ответа — в [Жизненном цикле запроса](/content/network-api/request-lifecycle).

## Задержка и пропускная способность

У канала две характеристики:

- **пропускная способность** — сколько байтов в секунду: 100 Мбит/с;
- **задержка** — сколько идёт сигнал. Обычно говорят об **RTT** (round-trip time) — времени туда и обратно: в пределах города — единицы миллисекунд, между континентами — 100–300 мс, в мобильной сети — добавляется ещё десятки.

Для веба почти всегда важнее задержка. Свет в оптоволокне не ускорить, а страница делает много кругов: DNS, TCP, TLS, сам запрос, потом запросы, найденные в ответе. Десять последовательных запросов при RTT 150 мс — полторы секунды ожидания при любом канале; те же запросы параллельно — 150 мс.

Отсюда приёмы, которые встречаются по всей книге: меньше последовательных кругов (параллельные запросы, отсутствие водопадов), ближе к пользователю (CDN — [CDN и кеширование](/content/testing-deploying/cdn-and-caching)), меньше рукопожатий (повторное использование соединений, HTTP/2, TLS 1.3) и важное содержимое в первых 14 КБ ответа.

Шифрование соединения — следующий слой поверх TCP; как устроен TLS — в [Криптографии](/content/computer-science/encryption).

## Красные флаги в ответе

- **«TCP передаёт сообщения».** Он передаёт поток байтов; границы сообщений размечает протокол поверх него.
- **«UDP ненадёжный, поэтому его не используют».** DNS, звонки, игры и HTTP/3 работают на UDP: надёжность там либо не нужна, либо реализована поверх.
- **«Поменяли IP в DNS — все сразу пойдут на новый сервер».** Старый ответ живёт в кешах до истечения TTL.
- **«Медленно, потому что у пользователя слабый интернет».** Чаще виновата задержка и число последовательных кругов, а не ширина канала.
- **«`localhost` — это `127.0.0.1`».** Это и `::1`, и сервер на одном адресе не виден по другому.
- **«Порт не важен для браузера».** Порт — часть origin: разные порты — разные источники для CORS и хранилищ.

## Как спрашивают на собеседовании

::question
Чем TCP отличается от UDP?

#answer
TCP устанавливает соединение, гарантирует доставку и порядок и регулирует скорость, но передаёт поток байтов без границ сообщений, а потеря одного пакета задерживает все следующие. UDP отправляет отдельные датаграммы без соединения и гарантий: быстрее и проще, границы сообщений сохраняются, но потери и порядок — забота программы.

#more
TCP — для HTTP/1.1, HTTP/2, WebSocket и всего, где важна целостность. UDP — для DNS, звонков, игр и QUIC, на котором построен HTTP/3: QUIC реализует надёжность поверх UDP для каждого потока отдельно и убирает блокировку начала очереди TCP. Рукопожатие TCP стоит один круг до первого байта данных.
::

::question
Почему через TCP нельзя просто отправлять JSON-сообщения одно за другим?

#answer
TCP — поток байтов: он не сохраняет границы записей. Два сообщения могут прийти одним куском, а одно — несколькими, и `JSON.parse` на таком куске упадёт. Протокол поверх TCP должен сам размечать границы: длиной перед сообщением, разделителем вроде перевода строки или кадрами.

#more
HTTP указывает длину тела в `Content-Length` или передаёт тело кусками с длиной каждого, WebSocket упаковывает сообщения в кадры с длиной в заголовке. Получатель накапливает байты в буфере и вынимает из него целые сообщения. В проверке две записи JSON пришли одним куском, а запись в 2 МБ — несколькими.
::

::question
Как работает DNS?

#answer
Браузер сначала смотрит в свой кеш и кеш ОС. Если ответа нет, запрос идёт к рекурсивному резолверу, который проходит цепочку: корневой сервер называет сервер зоны верхнего уровня, тот — авторитетный сервер домена, а он возвращает адрес. Ответ кешируется на время TTL на всех уровнях.

#more
Записи: `A` и `AAAA` — адреса, `CNAME` — псевдоним, `MX` — почта, `TXT` — проверки владения, `NS` — серверы зоны. TTL объясняет, почему смена адреса применяется не сразу: перед переездом его уменьшают. `dns-prefetch` и `preconnect` позволяют разрешить имя заранее. Обычный DNS не шифруется; DNS-over-HTTPS это исправляет.
::

::question
Что такое порт и почему `localhost:3000` и `localhost:5173` — разные origin?

#answer
Порт — номер, по которому ОС определяет программу на компьютере: один процесс слушает 3000, другой — 5173. Origin в браузере — схема, хост и порт вместе, поэтому разные порты — разные источники. Запрос с фронтенда на 5173 к API на 3000 — межсайтовый для CORS, хотя компьютер один.

#more
Отсюда прокси в dev-сервере: Vite проксирует `/api` на бэкенд, и для браузера всё идёт с одного origin. Хранилища тоже разделены по origin: `localStorage` на разных портах разный. Ошибки уровня порта: `EADDRINUSE` — порт уже занят, `ECONNREFUSED` — никто не слушает.
::

::question
Что важнее для скорости загрузки страницы: ширина канала или задержка?

#answer
Чаще задержка. Страница делает много кругов «запрос — ответ»: DNS, TCP, TLS, HTML, потом стили, скрипты и данные. Каждый круг стоит RTT — от единиц до сотен миллисекунд, — и при последовательных запросах они складываются. Широкий канал этого не ускорит.

#more
Десять последовательных запросов при RTT 150 мс — полторы секунды. Поэтому оптимизации направлены на число кругов: параллельные запросы, отсутствие водопадов, повторное использование соединений, HTTP/2, TLS 1.3, CDN ближе к пользователю. Первое окно TCP — около 14 КБ: столько сервер отправит в первый круг, поэтому критичное содержимое держат в начале ответа.
::

::question
Что такое NAT и зачем нужен IPv6?

#answer
Адресов IPv4 около четырёх миллиардов, и они закончились. NAT позволяет многим устройствам с частными адресами выходить в интернет через один публичный: маршрутизатор подменяет адреса и порты и помнит, кому вернуть ответ. IPv6 со 128-битными адресами снимает дефицит, и каждому устройству хватает своего публичного адреса.

#more
NAT мешает входящим соединениям: снаружи нельзя просто подключиться к устройству за ним. Поэтому WebRTC для звонков использует STUN, чтобы узнать свой внешний адрес, и TURN как ретранслятор, если прямое соединение невозможно. Переход на IPv6 идёт долго, и сети работают в обоих протоколах сразу — отсюда двойные ответы DNS и перебор адресов при подключении.
::

## Практика

::practice{title="Сообщения от сервера склеиваются"}
Сервис цен отправляет по TCP-сокету JSON-сообщения. Клиент на Node.js:

```js
socket.on('data', (chunk) => {
  const message = JSON.parse(chunk.toString());
  updatePrice(message);
});
```

Иногда приходит `SyntaxError: Unexpected token '{'`, а иногда — `Unexpected end of JSON input`. Почему и как исправить?

#solution
TCP — поток байтов, а `data` — произвольный кусок этого потока. Два сообщения могут прийти одним куском (`}{` посередине), а одно — разрезанным на два. Нужен формат кадров. Если сервер отделяет сообщения переводом строки, клиент накапливает буфер и вынимает целые строки:

```js
function lines(onMessage) {
  let buffer = '';
  return (chunk) => {
    buffer += chunk;
    let i;
    while ((i = buffer.indexOf('\n')) !== -1) {
      onMessage(JSON.parse(buffer.slice(0, i)));
      buffer = buffer.slice(i + 1);
    }
  };
}

socket.setEncoding('utf8');                          // не резать многобайтовые символы
socket.on('data', lines(updatePrice));
```

В проверке сообщение, разрезанное посередине и склеенное со следующим, разобралось правильно. Для бинарных данных вместо разделителя ставят длину перед сообщением. В браузере эту работу делает WebSocket: он сам собирает кадры в сообщения.
::

::practice{title="Прокси dev-сервера не видит бэкенд"}
Бэкенд запущен командой `app.listen(3000, '127.0.0.1')`, в браузере `http://127.0.0.1:3000/api/health` отвечает. А инструмент, который ходит на `http://localhost:3000`, получает `ECONNREFUSED`. Почему?

#solution
`localhost` разрешается в два адреса, `::1` и `127.0.0.1`, и ОС может вернуть IPv6 первым. Сервер слушает только IPv4. Клиент, который пробует только первый адрес, стучится на `::1:3000`, где никого нет. В проверке соединение на `localhost` без перебора адресов отклонилось с `ECONNREFUSED`, а с перебором — прошло.

Исправить можно с любой стороны:

```js
app.listen(3000, '::');            // слушать все адреса, IPv6 и IPv4
// или в настройке прокси — явный адрес
proxy: { '/api': 'http://127.0.0.1:3000' }
```

`'0.0.0.0'` слушает все IPv4-адреса, `'::'` в большинстве систем — и IPv6, и IPv4. Явный `127.0.0.1` в конфиге клиента убирает неоднозначность.
::

::practice{title="Каталог грузится секунды при быстром интернете"}
Страница каталога делает запросы последовательно:

```js
const user = await api('/me');
const cart = await api('/cart');
const categories = await api('/categories');
const products = await api(`/products?category=${categories[0].id}`);
```

У пользователей в Австралии (RTT до сервера около 300 мс) страница загружается больше секунды, хотя ответы крошечные. Что делать?

#solution
Каждый `await` — полный круг до сервера. Четыре последовательных запроса — минимум 4 × 300 = 1200 мс, и ширина канала тут ни при чём. Независимые запросы запускают параллельно, а зависимые — сокращают:

```js
const [user, cart, categories] = await Promise.all([api('/me'), api('/cart'), api('/categories')]);
const products = await api(`/products?category=${categories[0].id}`);
```

Теперь два круга вместо четырёх. Дальше — убрать и второй: сервер может сразу отдать товары первой категории в ответе `/categories` или страница может получить всё одним запросом к BFF ([API и BFF](/content/architecture/api-and-bff)). А CDN и сервер ближе к пользователю уменьшают сам RTT.
