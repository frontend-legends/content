# Хранилища браузера

У браузера несколько мест, где страница может хранить данные: куки, `localStorage`, `sessionStorage`, IndexedDB, Cache API и файловая система origin. Они различаются объёмом, временем жизни, тем, синхронны ли они и видны ли из воркеров и других вкладок. Спрашивают, чем отличаются `localStorage`, `sessionStorage` и куки и когда нужен IndexedDB. Глубже — что будет при переполнении, почему транзакция IndexedDB «умирает» после `await fetch` и почему новая версия приложения не может обновить базу, пока открыта старая вкладка.

::tldr
- **Все хранилища привязаны к origin** — схеме, хосту и порту, — а внутри чужого фрейма ещё и к сайту страницы, в которую фрейм встроен.
- **`localStorage` — синхронные строки, около 5 миллионов символов на origin**, общие для всех вкладок и живущие бессрочно. Объект без `JSON.stringify` превращается в `'[object Object]'`, переполнение — `QuotaExceededError`, в воркерах его нет.
- **`sessionStorage` живёт в одной вкладке**, переживает перезагрузку, а `window.open` получает его копию.
- **IndexedDB — асинхронная база объектов с индексами и транзакциями** на сотни мегабайт: хранит `Date`, `Map`, `Blob`. Транзакция закрывается, как только ей нечего делать, поэтому ждать `fetch` внутри неё нельзя.
- **Место ограничено квотой и может быть очищено браузером:** `navigator.storage.estimate()` показывает занятое, `persist()` просит не удалять данные.
::

## Что где хранить

Сквозной пример — интернет-магазин: тема оформления, черновик формы оформления заказа, каталог для офлайна, фото к отзыву и сессия пользователя.

| | Куки | `localStorage` | `sessionStorage` | IndexedDB | Cache API |
| --- | --- | --- | --- | --- | --- |
| Объём | ~4 КБ на куку | ~5 млн символов | ~5 млн символов | сотни МБ и больше, по квоте | по квоте |
| Что хранит | строки | строки | строки | объекты, файлы | пары запрос — ответ |
| Интерфейс | заголовки, `document.cookie` | синхронный | синхронный | асинхронный | асинхронный |
| Время жизни | по `Max-Age` | бессрочно | пока жива вкладка | бессрочно | бессрочно |
| Уходит на сервер | с каждым запросом | нет | нет | нет | нет |
| В воркерах | нет | нет | нет | да | да |

Правила выбора:

- **сессия и всё, что нужно серверу** — куки ([Аутентификация](/content/network-api/auth));
- **маленькие настройки** — тема, язык, закрытые подсказки — `localStorage`;
- **состояние одной вкладки** — шаг оформления, черновик формы — `sessionStorage`;
- **много данных, офлайн, файлы** — IndexedDB;
- **ответы сети для офлайна** — Cache API из Service Worker ([PWA](/content/web/pwa));
- **большие файлы и базы вроде SQLite в WebAssembly** — файловая система origin (OPFS).

Где хранить токены и почему `localStorage` для них опасен — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens): любой скрипт на странице, включая внедрённый через :term[XSS]{def="межсайтовый скриптинг: чужой скрипт попадает на страницу через непроверенные данные"}, читает все эти хранилища.

## localStorage

`localStorage` — пары «строка — строка» для origin. Общий для всех вкладок этого origin и хранится, пока его не очистят.

```js
localStorage.setItem('theme', 'dark');
localStorage.getItem('theme');   // 'dark'
```

Три свойства, которые приводят к багам:

- **только строки.** Число станет строкой, объект — строкой `'[object Object]'`. В проверке `setItem('qty', 5)` вернул `'5'`, а сохранённая корзина — `'[object Object]'`. Объекты сохраняют через `JSON.stringify` и читают через `JSON.parse` в `try`: в хранилище может оказаться что угодно от старой версии приложения;
- **синхронный.** Каждое чтение и запись блокируют главный поток, а данные читаются с диска. Для настроек это незаметно, для мегабайтов — тормоза при старте страницы;
- **ограничен.** В Chromium — 5 242 880 символов на origin вместе с ключами, независимо от алфавита: в проверке строка на один символ длиннее бросила `QuotaExceededError`. Запись нужно оборачивать в `try`.

`localStorage` нет в воркерах — в проверке `typeof localStorage` в Web Worker дал `'undefined'`. Об изменении `localStorage` в другой вкладке сообщает событие `storage` ([API браузера](/content/web/browser-apis)).

## sessionStorage

Тот же интерфейс, но данные принадлежат **вкладке**: две вкладки с одним сайтом видят разные `sessionStorage`. Данные переживают перезагрузку и закрываются вместе с вкладкой.

Тонкость — открытие нового окна. Окно, открытое через `window.open`, получает **копию** `sessionStorage` открывшей вкладки, и дальше они независимы. В проверке шаг оформления «адрес» скопировался в новое окно, изменение там на «оплату» не повлияло на исходную вкладку, а вкладка, открытая заново, получила пустое хранилище. Поэтому `sessionStorage` хорош для черновика формы, но не для данных, которые должны быть общими.

## IndexedDB

IndexedDB — асинхронная база объектов. Данные лежат в **хранилищах объектов** (аналог таблиц) с ключами и **индексами**, а любое чтение и запись идут в **транзакции**.

```js
const open = indexedDB.open('shop', 1);
open.onupgradeneeded = () => {
  const store = open.result.createObjectStore('orders', { keyPath: 'id' });
  store.createIndex('byNumber', 'number', { unique: true });
};
open.onsuccess = () => {
  const tx = open.result.transaction('orders', 'readwrite');
  tx.objectStore('orders').put({ id: 1, number: 'A-100', created: new Date(), receipt: blob });
};
```

Значения сохраняются **структурным клонированием**, а не JSON: в проверке `Date` вернулся `Date`, `Map` — `Map`, а `Blob` с чеком прочитался обратно. Уникальный индекс отклонил второй заказ с тем же номером ошибкой `ConstraintError`. Интерфейс построен на событиях, поэтому в коде обычно используют обёртку на промисах вроде idb или Dexie.

### Транзакции закрываются сами

Транзакция IndexedDB живёт, пока в ней есть ожидающие запросы. Как только текущая задача закончилась и запросов нет, браузер её фиксирует. Если внутри транзакции подождать что-то постороннее — `fetch`, таймер, — она закроется раньше:

```js
const tx = db.transaction('orders', 'readwrite');
const store = tx.objectStore('orders');
const price = await fetch('/api/price').then((r) => r.json()); // транзакция уже закрыта
store.put({ id: 3, price });                                   // TransactionInactiveError
```

В проверке именно так и вышло. Правило — сначала получить все данные, потом открыть транзакцию и сделать в ней только операции с базой.

### Обновление схемы

Схема меняется только при открытии базы с новым номером версии, в обработчике `upgradeneeded`. Но если в другой вкладке открыта старая версия приложения с соединением к базе, обновление **ждёт**: новая вкладка получает событие `blocked`, а старая — `versionchange`. В проверке открытие версии 2 остановилось на `blocked`, пока старая вкладка не закрыла соединение.

Поэтому каждая вкладка должна уступать:

```js
db.onversionchange = () => {
  db.close();
  showBanner('Приложение обновилось — перезагрузите страницу');
};
```

## Cache API и файловая система origin

**Cache API** хранит пары «запрос — ответ» и доступен и из страницы, и из Service Worker. Это основа офлайна: Service Worker кладёт в кеш оболочку приложения и отвечает из него без сети. В отличие от HTTP-кеша, ничего здесь не устаревает само — содержимое удаляет только код. Стратегии — в [Стратегиях кеширования](/content/security-perfomance/caching-strategies).

**Файловая система origin** (OPFS, `navigator.storage.getDirectory()`) — приватные файлы сайта с быстрым доступом. В проверке файл с черновиком отзыва записался и прочитался обратно. В воркере есть синхронный доступ к файлам, поэтому на OPFS строят SQLite в WebAssembly и редакторы больших документов.

---

## Квота и очистка

У каждого сайта есть **квота** — доля свободного места на диске, обычно очень большая. `navigator.storage.estimate()` показывает квоту и занятое место: в проверке три мегабайта в Cache API сразу отразились в `usage`. IndexedDB, Cache API и OPFS делят эту квоту, а `localStorage` ограничен отдельно.

Данные бывают двух видов хранения:

- **best-effort** — по умолчанию. При нехватке места браузер удаляет данные сайтов, которые давно не открывали, целиком по origin. Safari к тому же стирает данные сайтов, которые пользователь не посещал неделю, если они записаны скриптом;
- **persistent** — после `navigator.storage.persist()` браузер не удаляет данные сам. Разрешение браузер даёт по своим правилам: установленным PWA, сайтам в закладках, часто посещаемым. В проверке без запроса `persisted()` вернул `false`.

Вывод: хранилище браузера — кеш, а не источник истины. Важное — заказы, черновики, которые жалко потерять, — синхронизируют с сервером ([Local-first](/content/modern-dev/local-first-software)).

### Разделение по сайту

Сайт может быть открыт во фрейме внутри другого сайта: виджет чата, оплата, видео. Хранилище такого фрейма разделено по сайту страницы: у виджета внутри `shop.example` и у того же виджета внутри `other.example` — разные `localStorage` и IndexedDB, и обе отличаются от хранилища виджета, открытого напрямую. В проверке запись виджета во фрейме на одном сайте была видна только там же. Так браузеры не дают сторонним сервисам следить за пользователем между сайтами.

## Красные флаги в ответе

- **«Положу объект в `localStorage`».** Сохранится `'[object Object]'`; нужен `JSON.stringify`, а чтение — в `try`.
- **«`localStorage` безлимитный» или «запись всегда успешна».** Около 5 миллионов символов, дальше `QuotaExceededError`.
- **«`sessionStorage` общий для вкладок сайта».** Он свой у каждой вкладки; `window.open` получает копию.
- **«В транзакции IndexedDB можно подождать ответ сервера».** Транзакция закроется, следующая операция бросит `TransactionInactiveError`.
- **«Данные в IndexedDB останутся навсегда».** Браузер может удалить их при нехватке места, если хранилище не persistent.
- **«Храню токен в `localStorage` — это безопасно, сервер его не видит».** Его видит любой скрипт на странице.

## Как спрашивают на собеседовании

::question
Чем отличаются куки, `localStorage`, `sessionStorage` и IndexedDB?

#answer
Куки — маленькие строки, которые уходят на сервер с каждым запросом; их задаёт сервер, срок — атрибутами. `localStorage` — синхронные строки на origin, общие для вкладок и бессрочные, около 5 миллионов символов. `sessionStorage` — то же, но своя у каждой вкладки и до её закрытия. IndexedDB — асинхронная база объектов с индексами и транзакциями, сотни мегабайт, доступна в воркерах.

#more
Выбор по задаче: сессия — куки, настройки — `localStorage`, черновик одной вкладки — `sessionStorage`, офлайн-данные и файлы — IndexedDB, ответы сети — Cache API, большие файлы и SQLite — OPFS. Все хранилища, кроме `HttpOnly`-кук, доступны любому скрипту на странице, поэтому секреты в них не держат.
::

::question
Что будет, если места не хватит?

#answer
`localStorage` бросит `QuotaExceededError` — в Chromium после 5 242 880 символов на origin. IndexedDB и Cache API делят квоту сайта, которую показывает `navigator.storage.estimate()`, и при её превышении операция тоже отклонится. Запись в хранилища оборачивают в обработку ошибок.

#more
При нехватке места на диске браузер удаляет данные сайтов в режиме best-effort — целиком по origin, начиная с давно не открытых. `navigator.storage.persist()` просит не удалять данные; браузер решает сам, обычно разрешает установленным PWA. Поэтому хранилище браузера — кеш, а важные данные синхронизируют с сервером.
::

::question
Почему `localStorage` может тормозить страницу?

#answer
Он синхронный: каждое `getItem` и `setItem` выполняется в главном потоке, а данные хранятся на диске. Маленькие настройки читаются незаметно, но мегабайты JSON, которые читают при старте и перезаписывают при каждом изменении, задерживают первую отрисовку и ввод.

#more
Большие и часто меняющиеся данные переносят в IndexedDB: он асинхронный и пишет частями, а не перезаписывает целый JSON. Ещё одна причина — `JSON.parse` огромной строки тоже блокирует поток. В воркерах `localStorage` нет вовсе, а IndexedDB есть, поэтому тяжёлую работу с данными можно вынести из главного потока.
::

::question
Как работают транзакции IndexedDB?

#answer
Любое чтение и запись идут в транзакции над набором хранилищ, в режиме `readonly` или `readwrite`. Транзакция атомарна: либо применяются все её операции, либо ни одна. Она фиксируется автоматически, как только в ней не осталось ожидающих запросов и закончилась текущая задача.

#more
Из-за автофиксации нельзя ждать внутри транзакции что-то постороннее: после `await fetch` следующая операция бросит `TransactionInactiveError` — в проверке так и вышло. Сначала получают данные, потом открывают транзакцию. Транзакции `readwrite` над одним хранилищем выполняются по очереди, `readonly` — параллельно.
::

::question
Как обновить схему IndexedDB, если у пользователя открыто несколько вкладок?

#answer
Схему меняют, открывая базу с большим номером версии, в обработчике `upgradeneeded`. Если другая вкладка держит соединение со старой версией, новая получает событие `blocked` и ждёт, а старая — событие `versionchange`. Старая вкладка должна закрыть соединение и предложить перезагрузку.

#more
В проверке открытие версии 2 остановилось на `blocked`, пока старая вкладка не вызвала `db.close()`. Обработчик `onversionchange` с закрытием соединения ставят сразу при открытии базы. Миграции пишут по шагам от каждой старой версии к следующей, потому что пользователь мог пропустить несколько релизов.
::

::question
Почему виджет во фрейме не видит свои данные, сохранённые на другом сайте?

#answer
Хранилища фреймов с другого сайта разделены по сайту страницы, в которую фрейм встроен. Виджет внутри `shop.example` и тот же виджет внутри `other.example` получают разные `localStorage`, IndexedDB и Cache API. Так браузер мешает сторонним сервисам узнавать пользователя на разных сайтах.

#more
В проверке запись виджета была видна только во фрейме на том же сайте и не видна ни на другом, ни при открытии виджета напрямую. Сторонние куки браузеры тоже ограничивают; для законных сценариев есть `Partitioned`-куки и Storage Access API, через который фрейм может попросить доступ к своим неразделённым данным.
::

## Практика

::practice{title="Корзина теряется после обновления"}
```js
function saveCart(cart) {
  localStorage.setItem('cart', cart);
}
function loadCart() {
  return localStorage.getItem('cart') ?? { items: [] };
}
```

После перезагрузки корзина пустая, а в Sentry иногда появляется `QuotaExceededError`. Найди проблемы и исправь.

#solution
1. `setItem` превращает объект в строку `'[object Object]'` — в проверке именно так. После перезагрузки `loadCart` возвращает эту строку вместо объекта.
2. Запись не защищена: при переполнении `setItem` бросает `QuotaExceededError`, и обработчик падает.
3. Нет версии формата: после изменения структуры корзины старые данные сломают код.

```js
const KEY = 'cart:v2';

function saveCart(cart) {
  try {
    localStorage.setItem(KEY, JSON.stringify(cart));
  } catch (e) {
    if (e.name === 'QuotaExceededError') reportStorageFull();
  }
}

function loadCart() {
  try {
    const parsed = JSON.parse(localStorage.getItem(KEY) ?? 'null');
    return Array.isArray(parsed?.items) ? parsed : { items: [] };
  } catch {
    return { items: [] };
  }
}
```

Корзину залогиненного пользователя лучше хранить на сервере, а `localStorage` использовать как быстрый кеш для гостя.
::

::practice{title="TransactionInactiveError"}
```js
async function saveOrder(db, order) {
  const tx = db.transaction('orders', 'readwrite');
  const store = tx.objectStore('orders');
  const { price } = await fetch(`/api/price/${order.productId}`).then((r) => r.json());
  store.put({ ...order, price });
}
```

Почему падает и как исправить?

#solution
Пока шёл `fetch`, в транзакции не было ожидающих запросов, и браузер её зафиксировал. `store.put` после `await` выполняется над закрытой транзакцией и бросает `TransactionInactiveError` — в проверке ровно так.

Сначала всё постороннее, потом транзакция только с операциями базы:

```js
async function saveOrder(db, order) {
  const { price } = await fetch(`/api/price/${order.productId}`).then((r) => r.json());
  const tx = db.transaction('orders', 'readwrite');
  tx.objectStore('orders').put({ ...order, price });
  await new Promise((resolve, reject) => {
    tx.oncomplete = resolve;
    tx.onerror = () => reject(tx.error);
  });
}
```

Ожидание `oncomplete` нужно, чтобы узнать, что запись действительно сохранилась. Внутри транзакции можно ждать только запросы к самой базе.
::

::practice{title="Новая версия не может обновить базу"}
После релиза новая версия приложения добавляет в IndexedDB хранилище отзывов, но у части пользователей загрузка зависает на открытии базы. В логах — событие `blocked`. Почему и как исправить?

#solution
У пользователя открыта ещё одна вкладка со старой версией приложения, и она держит соединение с базой версии 1. Открытие версии 2 ждёт, пока все старые соединения закроются, и получает `blocked`. Старая вкладка при этом получает `versionchange`, но никак на него не реагирует. В проверке ровно так: обновление ждало, пока старая вкладка не вызвала `close()`.

Каждая вкладка должна уступать при обновлении, а новая — сообщать, что ждёт:

```js
function openDb() {
  return new Promise((resolve, reject) => {
    const request = indexedDB.open('shop', 2);
    request.onupgradeneeded = (e) => {
      const db = request.result;
      if (e.oldVersion < 1) db.createObjectStore('orders', { keyPath: 'id' });
      if (e.oldVersion < 2) db.createObjectStore('reviews', { keyPath: 'id' });
    };
    request.onblocked = () => showBanner('Закройте другие вкладки магазина, чтобы завершить обновление');
    request.onsuccess = () => {
      const db = request.result;
      db.onversionchange = () => {
        db.close();
        showBanner('Вышла новая версия — перезагрузите страницу');
      };
      resolve(db);
    };
    request.onerror = () => reject(request.error);
  });
}
```

Миграции по шагам `oldVersion < N` обновляют базу с любой старой версии.
