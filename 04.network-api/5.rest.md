# REST

REST — архитектурный стиль, на котором построено большинство HTTP API: данные — это ресурсы с адресами, а действия с ними — стандартные методы HTTP со стандартными кодами ответа. Фронтенду нужно уметь читать и проектировать такие API: какие адреса, какие методы, какие статусы. Спрашивают, что такое REST, чем PUT отличается от PATCH и какой статус вернуть. Глубже — почему REST не стандарт, как не потерять изменения при одновременном редактировании и в каком виде отдавать ошибки.

::tldr
- **REST — стиль, а не протокол и не стандарт:** ресурсы с адресами, единый интерфейс через методы HTTP, сервер без состояния между запросами, кешируемые ответы. На практике «REST API» — это JSON поверх HTTP, организованный вокруг ресурсов.
- **Адреса — существительные, действие задаёт метод:** `GET /cart-items`, `POST /cart-items`, `PATCH /cart-items/1`, `DELETE /cart-items/1`, а не `/getCart` и `/deleteItem?id=1`.
- **PUT заменяет ресурс целиком, PATCH меняет часть.** PUT без поля удаляет это поле, в JSON Merge Patch поле удаляют значением `null`.
- **Статус говорит о результате, тело — о деталях:** 201 и `Location` после создания, 204 без тела, 422 для ошибок данных, 409 для конфликта, 412 для устаревшей версии. Ошибки удобно отдавать в едином формате Problem Details.
- **Одновременные правки ловят условными запросами:** `ETag` при чтении, `If-Match` при записи, и устаревшая запись получает 412 вместо того, чтобы молча затереть чужую.
::

## Что такое REST

Сквозной пример — API корзины интернет-магазина: позиции корзины, товары, заказы.

REST (Representational State Transfer) описал Рой Филдинг в диссертации 2000 года как архитектурный стиль веба. Это набор ограничений, а не формат или протокол:

- **клиент и сервер** разделены и развиваются независимо;
- **без состояния** — каждый запрос несёт всё нужное для его обработки: кто пользователь, что нужно. Сервер не помнит «предыдущий шаг» клиента между запросами;
- **кешируемость** — ответ сообщает, можно ли его кешировать;
- **единый интерфейс** — ресурсы определяются адресами, с ними работают через представления (JSON, HTML), сообщения самоописательны, а ответы содержат ссылки на следующие действия (HATEOAS);
- **слоистость** — между клиентом и сервером могут стоять прокси, кеши, шлюзы, и клиент этого не замечает.

В индустрии «REST API» обычно значит меньше: JSON поверх HTTP, адреса-ресурсы, методы и статусы по смыслу. Ссылки на действия в ответах (HATEOAS) встречаются редко. Модель зрелости Ричардсона описывает эту лестницу: уровень 0 — один адрес и POST на всё (как RPC), 1 — ресурсы с адресами, 2 — методы и статусы HTTP по назначению, 3 — ссылки в ответах. Большинство хороших API живут на втором уровне.

REST — не единственный стиль. RPC-подход (gRPC, tRPC, JSON-RPC) вызывает функции, GraphQL отдаёт клиенту язык запросов ([GraphQL](/content/network-api/graphql)). Как выбирают между ними и какие для них есть клиенты — в [Клиентах API](/content/ecosystem-libs/realtime-and-api-clients).

## Ресурсы и адреса

**Ресурс** — то, о чём можно говорить отдельно: позиция корзины, товар, заказ, пользователь. У ресурса есть адрес, а у набора ресурсов — свой:

```text
GET    /cart-items          список позиций
POST   /cart-items          добавить позицию
GET    /cart-items/1        одна позиция
PUT    /cart-items/1        заменить позицию
PATCH  /cart-items/1        изменить часть позиции
DELETE /cart-items/1        удалить позицию
GET    /products?category=oolong&sort=-price
```

Правила, которые делают API предсказуемым:

- **существительные во множественном числе**, глагол — это метод: не `/getCartItems`, не `/deleteItem?id=1`;
- **вложенность неглубокая**: `/orders/42/items` — нормально, `/users/5/orders/42/items/7/reviews` — уже трудно поддерживать, лучше `/reviews?itemId=7`;
- **фильтры, сортировка, выбор полей и пагинация — в параметрах запроса**, а не в пути. Пагинация подробно — в [Паттернах API](/content/network-api/api-patterns);
- **действия, которые не ложатся на CRUD**, оформляют как изменение состояния или как ресурс-событие: отмена заказа — `PATCH /orders/42` с `{"status": "cancelled"}` или `POST /orders/42/cancellation`.

## Методы

Методы несут смысл, и клиенты, прокси и кеши на него опираются. Безопасность и идемпотентность методов разобраны в [HTTP](/content/network-api/http); в дизайне API важно, что делает каждый с ресурсом.

**POST** создаёт ресурс в наборе. Сервер сам выбирает идентификатор и отвечает `201 Created` с адресом нового ресурса в `Location`. В проверке ответ на создание позиции пришёл с `201` и `Location: /cart-items/1`.

**PUT** заменяет ресурс **целиком** тем, что пришло. Чего нет в теле — того нет в ресурсе. В проверке `PUT` без поля `note` удалил заметку, а `PUT` только с количеством не прошёл проверку: обязательных полей не хватило.

**PATCH** меняет **часть** ресурса. Формат изменения задаёт `Content-Type`:

- **JSON Merge Patch** (`application/merge-patch+json`) — объект с изменёнными полями; `null` значит «удалить поле», массив заменяется целиком. Просто, но нельзя записать в поле сам `null`;
- **JSON Patch** (`application/json-patch+json`) — список операций `add`, `remove`, `replace`, `move` с путями. Точнее, но многословнее.

```js
// JSON Merge Patch
await fetch('/cart-items/1', {
  method: 'PATCH',
  headers: { 'content-type': 'application/merge-patch+json' },
  body: JSON.stringify({ qty: 3, note: null }), // количество — 3, заметку удалить
});
```

**DELETE** удаляет ресурс и отвечает `204 No Content` или `200` с телом. Он идемпотентен по состоянию, но не по ответу: в проверке второй `DELETE` вернул `404`, а состояние осталось тем же — позиции нет.

Метод, который ресурс не поддерживает, — `405 Method Not Allowed` с заголовком `Allow`, перечисляющим допустимые.

## Статусы и ошибки

Статус — первое, на что смотрит клиент, мониторинг и кеш. Для REST API достаточно небольшого набора:

| Ситуация | Статус |
| --- | --- |
| прочитано, изменено | 200 OK |
| создано | 201 Created и `Location` |
| принято, будет выполнено позже | 202 Accepted |
| выполнено, тела нет | 204 No Content |
| запрос не разобран: битый JSON, неверный параметр | 400 Bad Request |
| нет или неверна аутентификация | 401 Unauthorized |
| аутентифицирован, но нельзя | 403 Forbidden |
| ресурса нет | 404 Not Found |
| метод не поддерживается | 405 и `Allow` |
| конфликт с текущим состоянием: дубликат, неверный переход | 409 Conflict |
| версия ресурса устарела | 412 Precondition Failed |
| тип тела не поддерживается | 415 Unsupported Media Type |
| данные разобраны, но не прошли проверку | 422 Unprocessable Content |
| слишком много запросов | 429 и `Retry-After` |
| сбой сервера | 500, 502, 503, 504 |

400 против 422: 400 — запрос не понят (битый JSON, неизвестный формат), 422 — понят, но данные неверны (количество ноль). В проверке тело `{"qty":` получило 400, а `qty: 0` — 422.

### Формат ошибок

Статус говорит, что случилось в целом; детали — в теле. Если каждый эндпоинт придумывает свой формат, фронтенду приходится писать десяток обработчиков. Стандарт **Problem Details** (RFC 9457) задаёт общий вид с типом `application/problem+json`:

```json
{
  "type": "https://shop.example/problems/422",
  "title": "Данные не прошли проверку",
  "status": 422,
  "errors": [{ "field": "qty", "message": "количество — целое больше нуля" }]
}
```

`type`, `title`, `status`, `detail` и `instance` — стандартные поля, остальное — расширения вроде `errors` для ошибок по полям. Один формат на весь API позволяет сделать один обработчик ошибок на клиенте: показать `title`, а ошибки полей — рядом с полями формы.

## Одновременные изменения

Менеджер Алиса и менеджер Боб открыли одну позицию заказа. Алиса меняет количество, Боб — заметку, оба сохраняют. Без защиты второе сохранение затрёт первое — **потерянное обновление**.

HTTP решает это **условными запросами**. При чтении сервер отдаёт версию ресурса в `ETag`, при записи клиент возвращает её в `If-Match`. Если ресурс с тех пор изменился, сервер отвечает `412 Precondition Failed` и ничего не меняет:

```js
const res = await fetch('/cart-items/1');
const version = res.headers.get('etag');
const item = await res.json();

const saved = await fetch('/cart-items/1', {
  method: 'PATCH',
  headers: { 'content-type': 'application/merge-patch+json', 'if-match': version },
  body: JSON.stringify({ note: 'к пятнице' }),
});
if (saved.status === 412) {
  // ресурс изменился: перечитать, показать отличия, предложить сохранить заново
}
```

В проверке Алиса и Боб прочитали одну версию; правка Алисы прошла, правка Боба получила 412, и количество, которое поставила Алиса, сохранилось. Для API на другом origin `ETag` нужно открыть через `Access-Control-Expose-Headers` ([CORS](/content/network-api/cors)). Как `ETag` работает в кеше — в [Кешировании](/content/network-api/caching).

## Без состояния

Ограничение «без состояния» значит, что запрос самодостаточен: сервер не хранит контекст диалога с клиентом, кроме данных в базе. Кто пользователь, сервер узнаёт из куки или токена в каждом запросе ([Аутентификация](/content/network-api/auth)), какую страницу списка вернуть — из параметров, а не из «где остановились в прошлый раз».

Это позволяет поставить за балансировщиком сколько угодно одинаковых серверов и отправлять запрос любому, повторять запросы после сбоев и кешировать ответы. Ответы `GET` можно кешировать в браузере, CDN и прокси, если сервер это разрешил.

## Описание API

Договор между фронтендом и бэкендом удобно держать в машиночитаемом виде. **OpenAPI** описывает адреса, методы, параметры, схемы тел и ответов. Из него генерируют документацию, типы и клиент для фронтенда, моки для тестов и проверки на сервере ([Клиенты API](/content/ecosystem-libs/realtime-and-api-clients)). Как менять API, не ломая клиентов, и как проверять договор контрактными тестами — в [API и BFF](/content/architecture/api-and-bff).

## Красные флаги в ответе

- **«REST — это стандарт» или «REST — это JSON поверх HTTP».** Это архитектурный стиль с ограничениями; JSON и HTTP — обычный, но не обязательный способ его реализовать.
- **«PUT и PATCH — одно и то же».** PUT заменяет ресурс целиком, и пропущенные поля пропадают; PATCH меняет часть.
- **«`/getUsers`, `/createOrder`, `/deleteItem?id=1` — это REST».** Это RPC через HTTP: действие должно быть в методе, а в адресе — ресурс.
- **«На любую ошибку — 400 или 500».** Статус должен различать ситуации: 401 и 403, 404, 409, 412, 422, 429.
- **«Последний сохранивший прав».** Без `ETag` и `If-Match` одновременные правки молча теряются.
- **«Сервер запомнит, на какой странице остановился клиент».** Это нарушает отсутствие состояния; страница и фильтры — в параметрах запроса.

## Как спрашивают на собеседовании

::question
Что такое REST? Это стандарт?

#answer
Это архитектурный стиль, который описал Рой Филдинг: клиент и сервер разделены, сервер не хранит состояние между запросами, ответы кешируемы, интерфейс единый — ресурсы с адресами и стандартные методы, — система может состоять из слоёв. Стандартом REST не является: нет спецификации формата, есть только ограничения.

#more
На практике «REST API» — JSON поверх HTTP с адресами-ресурсами, методами и статусами по смыслу; это второй уровень модели Ричардсона. Третий — ссылки на действия в ответах (HATEOAS) — встречается редко. Договор описывают в OpenAPI. Альтернативы — RPC (gRPC, tRPC) и GraphQL.
::

::question
Чем PUT отличается от PATCH?

#answer
PUT заменяет ресурс целиком: что не пришло в теле, того не будет в ресурсе. PATCH меняет только указанные части. PUT идемпотентен — повтор даёт то же состояние; PATCH может быть неидемпотентным, например «увеличить количество на 1».

#more
В проверке `PUT` без поля `note` удалил заметку, а `PATCH` с `note: null` в формате JSON Merge Patch — тоже удалил, но остальные поля не тронул. Форматы PATCH — JSON Merge Patch (объект изменений, `null` удаляет, массивы заменяются целиком) и JSON Patch (список операций с путями). Частая ошибка — реализовать PUT как частичное обновление: тогда клиент не может удалить поле.
::

::question
Как проектировать адреса в REST API?

#answer
Адрес называет ресурс существительным во множественном числе, действие задаёт метод: `GET /orders`, `POST /orders`, `PATCH /orders/42`. Фильтры, сортировка и пагинация — в параметрах запроса. Вложенность — не глубже одного-двух уровней.

#more
Действия, которые не ложатся на CRUD, оформляют как изменение поля состояния или как ресурс-событие: `POST /orders/42/cancellation`, `POST /payments`. Идентификаторы лучше непрозрачные, чтобы клиент их не собирал сам. Версию API обычно несут в пути или заголовке, а совместимость изменений важнее способа версионирования.
::

::question
Какие статусы возвращать и как отдавать ошибки?

#answer
201 и `Location` после создания, 204 без тела, 400 для непонятого запроса, 422 для данных, не прошедших проверку, 401 без аутентификации, 403 без прав, 404, 409 при конфликте с состоянием, 412 при устаревшей версии, 429 при превышении лимита, 5xx при сбое сервера. Детали ошибки — в теле в едином формате, например Problem Details с `application/problem+json`.

#more
Единый формат позволяет написать один обработчик на клиенте: заголовок ошибки показать пользователю, ошибки полей — рядом с полями. 200 с ошибкой в теле ломает мониторинг, кеш и повторы. 404 против 403 для чужого ресурса — осознанный выбор: 404 не раскрывает, что ресурс существует.
::

::question
Как не потерять изменения, если два пользователя редактируют одно и то же?

#answer
Условными запросами: сервер отдаёт версию ресурса в `ETag`, клиент возвращает её в `If-Match` при записи. Если ресурс изменился, сервер отвечает `412 Precondition Failed` и не применяет изменение. Клиент перечитывает данные и решает, что делать: показать отличия или объединить.

#more
В проверке правка второго редактора со старым `ETag` получила 412, и правка первого сохранилась. Это оптимистичная блокировка: никто не держит замок, конфликт обнаруживается при записи. Вместо `ETag` можно передавать номер версии в теле. `If-None-Match: *` делает обратное — создать, только если ресурса ещё нет.
::

::question
Что значит «сервер без состояния» и зачем это нужно?

#answer
Каждый запрос несёт всё нужное для обработки: аутентификацию, параметры, страницу. Сервер не помнит контекст диалога с клиентом — только данные в базе. Поэтому любой из серверов за балансировщиком может обработать любой запрос, а запросы можно повторять и кешировать.

#more
Сессия в куке не противоречит этому, если её данные лежат в общем хранилище, а не в памяти конкретного сервера. Нарушение — «сервер помнит курсор пагинации» или «второй шаг формы работает только на том же сервере». JWT позволяет проверять пользователя вообще без обращения к хранилищу, но усложняет отзыв токенов.
::

## Практика

::practice{title="Правка Боба стёрла правку Алисы"}
Админка заказов сохраняет позицию так:

```js
const item = await (await fetch(`/cart-items/${id}`)).json();
// ... пользователь редактирует форму несколько минут ...
await fetch(`/cart-items/${id}`, {
  method: 'PUT',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ ...item, ...formChanges }),
});
```

Два менеджера открыли одну позицию: Алиса поменяла количество, Боб через минуту — заметку. Количество вернулось к старому. Почему и как исправить?

#solution
Боб отправил `PUT` со всем ресурсом, прочитанным до правки Алисы. PUT заменяет ресурс целиком, и старое количество из его копии затёрло новое — потерянное обновление.

Два исправления, лучше оба:

```js
const res = await fetch(`/cart-items/${id}`);
const version = res.headers.get('etag');
const item = await res.json();

const saved = await fetch(`/cart-items/${id}`, {
  method: 'PATCH',                                    // отправляем только изменённое
  headers: { 'content-type': 'application/merge-patch+json', 'if-match': version },
  body: JSON.stringify(formChanges),
});
if (saved.status === 412) {
  showConflict(await (await fetch(`/cart-items/${id}`)).json(), formChanges);
}
```

`PATCH` не трогает поля, которые пользователь не менял, а `If-Match` ловит случай, когда менялось то же поле. В проверке второй редактор с устаревшим `ETag` получил 412, и правка первого сохранилась.
::

::practice{title="Что останется в ресурсе?"}
Позиция корзины: `{ "id": 1, "productId": 7, "qty": 2, "note": "без сахара" }`. Что будет в ресурсе после каждого запроса, если выполнять их по отдельности к исходному состоянию?

```js
fetch('/cart-items/1', { method: 'PATCH', body: JSON.stringify({ qty: 3 }) });
fetch('/cart-items/1', { method: 'PATCH', body: JSON.stringify({ note: null }) });
fetch('/cart-items/1', { method: 'PUT', body: JSON.stringify({ productId: 7, qty: 5 }) });
```

PATCH — в формате JSON Merge Patch.

#solution
```text
PATCH { qty: 3 }       → { id: 1, productId: 7, qty: 3, note: "без сахара" }
PATCH { note: null }   → { id: 1, productId: 7, qty: 2 }
PUT   { productId, qty }→ { id: 1, productId: 7, qty: 5 }
```

PATCH меняет только указанные поля, а `null` в Merge Patch значит «удалить поле». PUT заменяет ресурс целиком: `note` не передан — значит, его нет. В проверке сервер вёл себя именно так, а `PUT` с одним `qty` отклонил с 422: обязательный `productId` отсутствовал. Если нужно записать в поле настоящий `null`, Merge Patch не подходит — тогда JSON Patch с операцией `replace`.
::

::practice{title="Перепроектируй API"}
Бэкенд корзины сделан так:

```text
GET  /getCart
POST /addToCart          { productId, qty }
POST /updateCartItem     { id, qty }
GET  /removeFromCart?id=1
POST /cart/clearAll
```

Что здесь не так и как переписать в стиле REST?

#solution
Действия записаны в адресах, а методы не соответствуют смыслу. Опаснее всего `GET /removeFromCart`: GET должен быть безопасным, а его вызывают предзагрузка ссылок, роботы и повтор при обрыве — товар удалится сам.

```text
GET    /cart-items            список              200
POST   /cart-items            добавить            201 + Location, 409 если уже есть
PATCH  /cart-items/{id}       изменить количество 200, 412 при устаревшей версии
DELETE /cart-items/{id}       удалить позицию     204, 404 если нет
DELETE /cart-items            очистить корзину    204
```

Теперь методы говорят, что безопасно повторять (`GET`, `PATCH` с абсолютным значением, `DELETE`), кеши и клиенты понимают запросы без документации, а ошибки различаются статусами. Повторное добавление после обрыва связи защищают ключом идемпотентности ([Паттерны API](/content/network-api/api-patterns)).
::
