# REST API

REST (Representational State Transfer) - архитектурный стиль для проектирования API, основанный на HTTP. Это не протокол и не стандарт, а набор принципов (constraints). Если API им следует - его называют RESTful. На собеседованиях спрашивают не только «что такое REST», а про идемпотентность, правильный дизайн URL, пагинацию и формат ошибок.

---

## Constraints REST

Рой Филдинг описал шесть ограничений. API считается RESTful, если соблюдает все шесть:

<b class="text-on-semi-light">Client-Server</b>

<span class="text-gray">Клиент и сервер разделены. Клиент не знает о хранении данных, сервер не знает о UI. Это позволяет развивать их независимо.</span>

<b class="text-on-semi-light">Stateless</b>

<span class="text-gray">Каждый запрос содержит **всю** информацию, необходимую для его обработки. Сервер не хранит контекст между запросами. Аутентификация - через токен в каждом запросе, а не через серверную сессию.</span>

<b class="text-on-semi-light">Cacheable</b>

<span class="text-gray">Ответы должны явно указывать, можно ли их кэшировать. Это снижает нагрузку и ускоряет повторные запросы (через HTTP-кэш заголовки: `Cache-Control`, `ETag`).</span>

<b class="text-on-semi-light">Uniform Interface</b>

<span class="text-gray">Единообразный интерфейс - ключевой constraint. Ресурсы идентифицируются через URI, манипулируются через представления (JSON), а взаимодействие - self-descriptive (метод + заголовки + тело описывают всё).</span>

<b class="text-on-semi-light">Layered System</b>

<span class="text-gray">Клиент не знает, обращается ли он к конечному серверу или к промежуточному слою (load balancer, CDN, API gateway). Слои не влияют на контракт.</span>

<b class="text-on-semi-light">Code on Demand (опционально)</b>

<span class="text-gray">Сервер может передавать исполняемый код клиенту (JavaScript). Единственный необязательный constraint - на практике редко упоминается.</span>

## Дизайн ресурсов

### URL Naming Conventions

Ресурс - это сущность (пользователь, заказ, статья), а не действие. URL описывает **что**, а HTTP-метод - **что делать**.

```text
Хорошо (существительные, множественное число):
  GET    /users
  GET    /users/42
  POST   /users
  PUT    /users/42
  DELETE /users/42

Плохо (глаголы в URL):
  GET    /getUser?id=42
  POST   /createUser
  POST   /deleteUser/42
```

### Правила именования

- Множественное число: `/users`, `/orders`, `/articles`
- Kebab-case для составных: `/order-items`, `/user-profiles`
- Вложенность для связанных ресурсов: `/users/42/orders`
- Не более 2 уровней вложенности - дальше становится нечитаемо
- Фильтрация через query params: `/users?role=admin&status=active`
- Версионирование в URL или заголовках: `/v1/users` или `Accept: application/vnd.api+json;version=1`

```text
GET /users/42/orders          - заказы пользователя 42
GET /users/42/orders/7        - конкретный заказ
GET /orders?userId=42         - альтернативный подход через фильтрацию

// Слишком глубоко - лучше вынести:
GET /users/42/orders/7/items/3/reviews   // плохо
GET /reviews?itemId=3                     // лучше
```

## Методы и CRUD

| HTTP-метод | CRUD-операция      | Описание                | Тело запроса           | Тело ответа         |
| ---------- | ------------------ | ----------------------- | ---------------------- | ------------------- |
| `GET`      | Read               | Получить ресурс(ы)      | Нет                    | Ресурс / коллекция  |
| `POST`     | Create             | Создать ресурс          | Данные нового ресурса  | Созданный ресурс    |
| `PUT`      | Update (полный)    | Заменить ресурс целиком | Полное представление   | Обновлённый ресурс  |
| `PATCH`    | Update (частичный) | Обновить часть ресурса  | Только изменяемые поля | Обновлённый ресурс  |
| `DELETE`   | Delete             | Удалить ресурс          | Обычно нет             | Обычно пустой (204) |

```js
// GET - получить список
const users = await fetch("/api/users").then((r) => r.json());

// POST - создать
const newUser = await fetch("/api/users", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "Alice", email: "alice@example.com" }),
}).then((r) => r.json());

// PUT - заменить целиком
await fetch("/api/users/42", {
  method: "PUT",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({
    name: "Alice",
    email: "new@example.com",
    role: "admin",
  }),
});

// PATCH - обновить частично
await fetch("/api/users/42", {
  method: "PATCH",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ role: "admin" }),
});

// DELETE - удалить
await fetch("/api/users/42", { method: "DELETE" });
```

## Идемпотентность и безопасность

Два важных свойства HTTP-методов, которые часто спрашивают на собесе.

<b class="text-on-semi-light">Безопасный (safe)</b>

<span class="text-gray">Метод не изменяет состояние сервера. Можно вызвать сколько угодно раз без побочных эффектов.</span>

<b class="text-on-semi-light">Идемпотентный (idempotent)</b>

<span class="text-gray">Повторный вызов с теми же параметрами даёт тот же результат, что и первый. Сервер может измениться при первом вызове, но повторные вызовы ничего не изменят.</span>

| Метод     | Безопасный? | Идемпотентный? | Пояснение                                                 |
| --------- | ----------- | -------------- | --------------------------------------------------------- |
| `GET`     | Да          | Да             | Только чтение                                             |
| `HEAD`    | Да          | Да             | Как GET, но без тела ответа                               |
| `OPTIONS` | Да          | Да             | Метаинформация о ресурсе                                  |
| `PUT`     | Нет         | Да             | Повторный PUT перезапишет тем же - результат не изменится |
| `DELETE`  | Нет         | Да             | Повторный DELETE - ресурс уже удалён, результат тот же    |
| `POST`    | Нет         | **Нет**        | Каждый POST может создать новый ресурс                    |
| `PATCH`   | Нет         | **Нет\***      | Зависит от реализации (обычно не гарантируется)           |

<span class="text-gray">\*`PATCH` **может** быть идемпотентным (например, `{ "role": "admin" }` - всегда устанавливает роль). Но спецификация не гарантирует этого, поэтому формально - нет.</span>

> Идемпотентность важна для retry-логики: если `PUT`-запрос упал по таймауту, ты можешь смело повторить его. С `POST` - рискуешь создать дубликат.

## Статус-коды в контексте REST

| Код                         | Значение             | Когда                                             |
| --------------------------- | -------------------- | ------------------------------------------------- |
| `200 OK`                    | Успех                | GET, PUT, PATCH - ресурс в теле                   |
| `201 Created`               | Создано              | POST - новый ресурс + заголовок `Location`        |
| `204 No Content`            | Успех, тело пустое   | DELETE, иногда PUT/PATCH                          |
| `400 Bad Request`           | Невалидный запрос    | Ошибки валидации, неправильный JSON               |
| `401 Unauthorized`          | Не аутентифицирован  | Нет токена или токен невалидный                   |
| `403 Forbidden`             | Нет прав             | Аутентифицирован, но доступ запрещён              |
| `404 Not Found`             | Ресурс не найден     | Несуществующий ID или путь                        |
| `409 Conflict`              | Конфликт             | Дубликат (email уже существует)                   |
| `422 Unprocessable Entity`  | Семантическая ошибка | JSON валиден, но данные не проходят бизнес-логику |
| `429 Too Many Requests`     | Rate limiting        | Слишком много запросов                            |
| `500 Internal Server Error` | Ошибка сервера       | Непредвиденная ошибка                             |

> Подробнее о статус-кодах и заголовках - [HTTP](/content/network-api/http).

## Пагинация

### Offset-based

```text
GET /articles?page=3&limit=20
GET /articles?offset=40&limit=20   // то же самое (offset = (page-1) * limit)
```

### Cursor-based

```text
GET /articles?limit=20
GET /articles?limit=20&cursor=eyJpZCI6MTAwfQ==
```

### Сравнение

| Критерий                              | Offset                                        | Cursor                            |
| ------------------------------------- | --------------------------------------------- | --------------------------------- |
| Реализация                            | Простая (`OFFSET` в SQL)                      | Сложнее (нужен стабильный cursor) |
| Переход на произвольную страницу      | Да                                            | Нет (только next/prev)            |
| Производительность при больших offset | Деградирует (БД сканирует пропущенные строки) | Стабильная                        |
| Стабильность при вставках/удалениях   | Элементы могут дублироваться или пропадать    | Стабильная                        |
| Подходит для                          | Панели администратора, таблицы                | Ленты, бесконечный скролл         |

```js
// Ответ сервера с cursor-пагинацией
{
  "data": [ ... ],
  "pagination": {
    "next_cursor": "eyJpZCI6MTAwfQ==",
    "has_more": true
  }
}
```

## Формат ошибок

Единообразный формат ошибок - признак зрелого API. Стандарт RFC 7807 (Problem Details for HTTP APIs) описывает формат:

```js
// RFC 7807 Problem Details
{
  "type": "https://api.example.com/errors/validation",
  "title": "Validation Error",
  "status": 422,
  "detail": "Email address is already registered",
  "instance": "/users",
  "errors": [
    {
      "field": "email",
      "message": "Email already exists"
    }
  ]
}
```

| Поле       | Описание                                                           |
| ---------- | ------------------------------------------------------------------ |
| `type`     | URI, идентифицирующий тип ошибки (можно ссылаться на документацию) |
| `title`    | Краткое человекочитаемое описание                                  |
| `status`   | HTTP status code                                                   |
| `detail`   | Подробное описание конкретной ошибки                               |
| `instance` | URI запроса, вызвавшего ошибку                                     |

<span class="text-gray">На практике не все API следуют RFC 7807, но единообразная структура ошибок - must have. Как минимум: `status`, `message` и массив `errors` для валидации полей.</span>

## Best Practices для фронтендера

<b class="text-on-semi-light">Всегда проверяй response.ok</b>

<span class="text-gray">`fetch()` не выбрасывает ошибку при 4xx/5xx - только при сетевой ошибке. Проверяй статус вручную.</span>

```js
async function api(url, options) {
  const response = await fetch(url, options);
  if (!response.ok) {
    const error = await response.json().catch(() => ({}));
    throw new ApiError(
      response.status,
      error.message || "Unknown error",
      error,
    );
  }
  return response.status === 204 ? null : response.json();
}
```

<b class="text-on-semi-light">Используй AbortController для отмены</b>

<span class="text-gray">Незавершённые запросы при смене страницы или повторном поиске - утечка ресурсов и race conditions.</span>

<b class="text-on-semi-light">Retry для идемпотентных методов</b>

<span class="text-gray">GET, PUT, DELETE безопасно повторять при таймауте. POST - только с идемпотентным ключом (`Idempotency-Key` заголовок).</span>

<b class="text-on-semi-light">Оптимистичные обновления</b>

<span class="text-gray">Обновляй UI до ответа сервера (для PUT/PATCH/DELETE). Если сервер вернул ошибку - откатывай. Это делает интерфейс отзывчивым.</span>

> Подробнее о паттернах работы с API - [Паттерны API](/content/network-api/api-patterns). Сравнение с GraphQL - [GraphQL](/content/network-api/graphql).

## Частые вопросы на собесе

**PUT vs PATCH - в чём разница?**
PUT заменяет ресурс **целиком** - ты отправляешь полное представление. PATCH обновляет **часть** - отправляешь только изменяемые поля. Если отправить PUT без поля - оно сбросится. С PATCH - останется прежним.

**Почему POST не идемпотентный?**
Потому что каждый POST может создать новый ресурс. Два одинаковых POST `/users` с `{ name: "Alice" }` могут создать двух Alice. PUT `/users/42` дважды - перезапишет одного и того же.

**REST - это стандарт?**
Нет, это архитектурный стиль (набор constraints). Нет RFC для REST. JSON API, OpenAPI - это стандарты/спецификации, построенные поверх REST-принципов.

**Что лучше: REST или GraphQL?**
Зависит от задачи. REST проще, лучше кэшируется на уровне HTTP, подходит для CRUD. GraphQL гибче, решает проблему over/under-fetching, лучше для сложных связанных данных. Подробнее - [GraphQL](/content/network-api/graphql).
