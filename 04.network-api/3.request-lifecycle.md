# Жизненный цикл запроса

«Что происходит, когда вводишь адрес в браузере?» — самый известный вопрос фронтенд-собеседования. Сетевая половина ответа — путь от адреса до первого байта ответа: проверка адреса и кешей, DNS, соединение TCP, рукопожатие TLS, запрос, работа сервера и ответ. Спрашивают этот путь по шагам и что такое TTFB. Глубже — сколько кругов до сервера стоит каждый шаг, почему первый запрос к новому домену медленнее следующих и почему цепочка редиректов съедает секунду на мобильной сети.

::tldr
- **До первого байта ответа браузер проходит шаги:** разбор адреса и HSTS, Service Worker и HTTP-кеш, DNS, соединение TCP, рукопожатие TLS, запрос, обработка на сервере, ответ.
- **Сетевые шаги стоят кругов (RTT):** TCP — один, TLS 1.3 — ещё один, сам запрос — ещё один. На новом домене это минимум три круга до первого байта, на мобильной сети — сотни миллисекунд.
- **Повторный запрос к тому же origin идёт по уже открытому соединению:** без DNS, TCP и TLS — только один круг.
- **Каждый редирект — ещё один полный круг**, а редирект на другой домен — ещё и новые DNS, TCP и TLS.
- **TTFB — время до первого байта:** сеть плюс работа сервера. Дальше браузер разбирает HTML потоком, находит ресурсы и рисует страницу — это уже не сеть.
::

---

## От адреса до запроса

Сквозной пример — пользователь вводит `shop.example/catalog` и нажимает Enter. Страница — на `shop.example`, API — на `api.shop.example`.

Сначала браузер работает сам, без сети:

1. **Разбирает ввод.** Строка без схемы и с точкой похожа на адрес — браузер достраивает `https://` (или `http://` в старых версиях) и нормализует URL по стандарту ([Что такое веб](/content/web/what-is-web)). Строка без точки уходит в поисковик.
2. **Проверяет HSTS.** Если сайт раньше прислал заголовок `Strict-Transport-Security` или входит во встроенный список HSTS preload, браузер сразу заменяет `http://` на `https://`, не отправляя открытого запроса. Это защищает от подмены первого запроса в чужой сети ([CSP и заголовки безопасности](/content/security-perfomance/csp-and-security-headers)).
3. **Ищет готовый ответ.** Сначала Service Worker, если он контролирует страницу ([PWA](/content/web/pwa)), потом HTTP-кеш ([Кеширование](/content/network-api/caching)). Свежий ответ из кеша — и сеть не нужна вовсе.

Если ответа нет, начинается сеть.

---

## DNS

Браузер переводит `shop.example` в IP-адрес: свой кеш, кеш ОС, потом рекурсивный резолвер ([Основы сетей](/content/network-api/networking-fundamentals)). Холодный запрос DNS стоит от единиц до сотен миллисекунд; ответ из кеша — ноль. Кеш живёт столько, сколько разрешил TTL записи.

У браузера есть и свой резолвер, и предварительное разрешение: он может разрешить имена из ссылок на странице заранее, а `<link rel="dns-prefetch">` и `preconnect` просят его об этом явно.

---

## Соединение: TCP и TLS

**TCP** открывает соединение тройным рукопожатием — SYN, SYN-ACK, ACK. Данные можно отправлять с третьим пакетом, поэтому рукопожатие стоит **один круг**.

**TLS** договаривается о ключах и проверяет сертификат сервера ([Криптография](/content/computer-science/encryption)). TLS 1.3 укладывается в **один круг**: клиент сразу присылает свою часть обмена ключами, сервер отвечает своей, сертификатом и подписью. TLS 1.2 требовал два круга. При возобновлении сессии TLS 1.3 может отправить запрос сразу (0-RTT), но только для безопасных к повтору запросов.

Проверка в Chromium: HTTPS-сервер за прокси, который задерживает каждый кусок данных на 50 мс в каждую сторону, — RTT 100 мс. Navigation Timing показал:

| Шаг | Время |
| --- | --- |
| TCP до прокси (на одной машине) | 0 мс |
| рукопожатие TLS 1.3 | около 105 мс — один круг |
| запрос и первый байт ответа | около 110 мс — один круг |

В реальной сети TCP добавил бы ещё один круг. Итого на новом домене: DNS, плюс три круга, плюс работа сервера — до первого байта. При RTT 150 мс в мобильной сети это полсекунды до того, как сервер вообще начал отвечать.

QUIC в HTTP/3 объединяет транспорт и TLS: соединение устанавливается за один круг вместо двух ([HTTP](/content/network-api/http)).

## Запрос и ответ

Когда соединение готово, браузер отправляет запрос: метод, путь, заголовки, куки этого сайта. Сервер обрабатывает его — проверяет сессию, ходит в базу, рендерит HTML — и начинает отвечать.

**TTFB** (time to first byte) — время от отправки запроса до первого байта ответа. В него входят один круг сети и время работы сервера. Высокий TTFB при маленьком RTT — проблема на сервере: медленная база, рендеринг, холодный старт функции. Разложить время сервера на части помогает заголовок `Server-Timing`, а сами поля Navigation Timing разобраны в [Измерении Core Web Vitals](/content/web/core-web-vitals).

Сервер не обязан ждать, пока страница готова целиком. Он может отправить `head` со ссылками на стили и скрипты сразу, а остальное — по мере готовности. Браузер разбирает HTML **потоком** и начинает загружать найденные ресурсы ещё до конца ответа ([Структура документа](/content/html/structure)). Ответ `103 Early Hints` позволяет подсказать важные ресурсы ещё до основного ответа.

### Редиректы

Каждый редирект — это полный ответ, после которого браузер отправляет новый запрос. В проверке редирект `301` с `/old` на `/new` добавил около 100 мс — ровно круг. Редирект на другой домен стоит дороже: новые DNS, TCP и TLS.

Классическая цепочка `http://shop.example` → `https://shop.example` → `https://www.shop.example` → `https://www.shop.example/ru/` — три лишних круга до первого полезного байта. Лечится одним редиректом сразу на конечный адрес и HSTS, который убирает первый шаг.

---

## Повторные запросы

Открытое соединение не закрывается после ответа: HTTP/1.1 держит его для следующих запросов (keep-alive), а HTTP/2 вообще пускает все запросы к origin по одному соединению. Поэтому повторный запрос к тому же origin стоит **одного круга**. В проверке вторая навигация на тот же HTTPS-origin показала нулевое время TCP и TLS, а в CDP запросы к тому же серверу пришли с `connectionReused: true`. Если же сервер отвечает `Connection: close`, каждое обращение открывает соединение заново — и платит за рукопожатия каждый раз.

Отсюда практика:

- **API на отдельном домене** платит за DNS, TCP и TLS при первом обращении. `<link rel="preconnect" href="https://api.shop.example">` открывает соединение заранее, пока браузер разбирает HTML ([Производительность загрузки](/content/security-perfomance/loading-performance));
- **ресурсы на том же origin** приходят по уже открытому соединению;
- **лишние домены** — аналитика, шрифты, CDN картинок — каждый стоит своих рукопожатий.

---

## Дальше — браузер

Когда приходят первые байты HTML, сеть отходит на второй план, хотя продолжает работать для ресурсов:

1. **Разбор HTML** в DOM потоком; сканер предзагрузки заранее находит стили, скрипты и картинки ([Структура документа](/content/html/structure)).
2. **Загрузка ресурсов** — снова через кеш, соединения и запросы, только уже без рукопожатий для того же origin. Блокирующие стили и скрипты задерживают отрисовку ([Производительность загрузки](/content/security-perfomance/loading-performance)).
3. **Отрисовка** — стили, раскладка, отрисовка и композиция ([Рендеринг](/content/web/rendering)).
4. **Скрипты** — выполнение, `DOMContentLoaded`, `load`, запросы к API из кода.

Хороший ответ на собеседовании идёт по этим шагам, но не перечисляет всё подряд одинаково подробно, а называет стоимость каждого и то, что на неё влияет.

---

## Красные флаги в ответе

- **«Браузер сначала делает DNS-запрос».** Сначала — разбор адреса, HSTS, Service Worker и HTTP-кеш; при свежем кеше сети нет вообще.
- **«TLS — это одно рукопожатие, оно быстрое».** Это целый круг до сервера, а в TLS 1.2 — два; на мобильной сети это сотни миллисекунд.
- **«Каждый запрос открывает новое соединение».** Соединения переиспользуются: повторный запрос к тому же origin стоит одного круга.
- **«Редирект — это мгновенно».** Каждый редирект — полный круг, а на другой домен — ещё и новые рукопожатия.
- **«TTFB — время работы сервера».** Это сеть плюс сервер; при большом RTT TTFB высокий и у быстрого сервера.
- **«Когда пришёл ответ, страница почти готова».** Дальше — разбор, загрузка ресурсов и отрисовка, и они часто дольше сети.

## Как спрашивают на собеседовании

::question
Что происходит, когда вводишь адрес сайта и нажимаешь Enter?

#answer
Браузер разбирает адрес, при HSTS сразу переходит на HTTPS, проверяет Service Worker и HTTP-кеш. Если готового ответа нет — DNS переводит имя в адрес, TCP открывает соединение за круг, TLS договаривается о ключах ещё за круг, потом уходит HTTP-запрос. Сервер отвечает, браузер разбирает HTML потоком, загружает стили, скрипты и картинки, строит DOM и CSSOM, раскладывает и рисует страницу.

#more
Сильный ответ называет стоимость шагов: DNS из кеша — ноль, холодный — десятки миллисекунд; TCP и TLS 1.3 — по кругу, TLS 1.2 — два; повторный запрос по открытому соединению — один круг. И что на них влияет: HSTS, `preconnect`, HTTP/2 и HTTP/3, кеш, CDN, потоковый ответ сервера и `103 Early Hints`.
::

::question
Что такое TTFB и из чего он складывается?

#answer
Time to first byte — время от отправки запроса до первого байта ответа. Он складывается из одного круга сети и времени работы сервера. Для навигации на новый домен к нему добавляются DNS, TCP и TLS, если считать от начала навигации.

#more
Высокий TTFB при маленьком RTT — проблема сервера: база, рендеринг, холодный старт. Высокий при быстром сервере — сеть: далёкий сервер, лишние редиректы. Разделить помогает `Server-Timing` с временем этапов сервера и поля Navigation Timing. Снижают TTFB CDN и кеш на краю сети, потоковая отдача HTML и `103 Early Hints`.
::

::question
Почему первый запрос к новому домену медленнее следующих?

#answer
Первому нужно разрешить имя через DNS, открыть TCP-соединение и пройти рукопожатие TLS — это два круга до сервера сверх самого запроса. Следующие запросы к тому же origin идут по уже открытому соединению и стоят одного круга.

#more
В проверке вторая навигация на тот же HTTPS-origin показала нулевое время TCP и TLS. Поэтому API на отдельном домене делает первый запрос медленнее, и его соединение открывают заранее через `preconnect`, или ставят API на тот же origin через прокси или BFF. Каждый сторонний домен на странице стоит своих рукопожатий.
::

::question
Что такое HSTS и зачем он нужен?

#answer
Заголовок `Strict-Transport-Security` говорит браузеру: ходи на этот домен только по HTTPS указанное время. После него браузер сам заменяет `http://` на `https://` до отправки запроса. Это закрывает окно, когда первый открытый запрос можно перехватить и подменить, и экономит круг на редиректе с HTTP.

#more
Первый визит до получения заголовка остаётся уязвимым — для этого есть HSTS preload: список доменов, встроенный в браузеры. `includeSubDomains` распространяет правило на поддомены, поэтому его включают, только когда все поддомены готовы к HTTPS. HSTS не работает для IP-адресов.
::

::question
Почему цепочка редиректов вредит производительности?

#answer
Каждый редирект — полный ответ сервера, после которого браузер делает новый запрос: минимум один круг. Редирект на другой домен добавляет DNS, TCP и TLS. Цепочка из трёх редиректов на мобильной сети — сотни миллисекунд до первого полезного байта.

#more
В проверке один редирект `301` добавил ровно круг — около 100 мс при RTT 100 мс. Лечится одним редиректом сразу на конечный адрес, HSTS вместо редиректа с HTTP, правильными ссылками внутри сайта без лишних редиректов. Редиректы видно в Navigation Timing: `redirectCount` и время `redirectStart`–`redirectEnd`.
::

::question
Как Service Worker и кеш меняют этот путь?

#answer
Они стоят в самом начале: перед любой сетью браузер спрашивает Service Worker, если он контролирует страницу, а потом HTTP-кеш. Свежий ответ из кеша возвращается без DNS, соединений и запроса. Service Worker может ответить из своего кеша, пойти в сеть или скомбинировать — это основа офлайна.

#more
При ответе `304 Not Modified` сеть всё же нужна, но тело не передаётся. Service Worker добавляет своё время запуска, поэтому для навигаций есть navigation preload: запрос в сеть идёт параллельно со стартом воркера. Стратегии кеширования — в главе про производительность, жизненный цикл воркера — в главе про PWA.
::

## Практика

::practice{title="Секунда до первого байта на мобильном"}
По RUM у мобильных пользователей начало загрузки главной занимает около секунды до первого байта. Ссылка в рекламе ведёт на `http://shop.example`. Navigation Timing показывает `redirectCount: 3`. Что происходит и что исправить?

#solution
Цепочка: `http://shop.example` → `https://shop.example` → `https://www.shop.example` → `https://www.shop.example/ru/`. Каждый редирект — полный круг, а переход на `www` — ещё и новое соединение с DNS и TLS. При RTT 150 мс это легко полсекунды до первого полезного запроса. В проверке один редирект стоил ровно круг.

Исправления:

```text
# один редирект сразу на конечный адрес
http://shop.example/*  →  301  https://www.shop.example/ru/*

# HSTS: следующие визиты сразу идут по HTTPS, без редиректа
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

И ссылки в рекламе — сразу на конечный адрес. Измерять — по `redirectCount` и `redirectEnd - redirectStart` в Navigation Timing у реальных пользователей.
::

::practice{title="Первый запрос к API медленный"}
Страница на `shop.example` загружает данные с `api.shop.example`. В водопаде у первого запроса к API длинные полосы DNS, Initial connection и SSL, а следующие запросы быстрые. Как ускорить первый?

#solution
Первый запрос к новому домену платит за DNS, TCP и TLS — два лишних круга. Следующие идут по открытому соединению.

Вариант 1 — открыть соединение заранее, пока браузер разбирает HTML и грузит скрипты:

```html
<link rel="preconnect" href="https://api.shop.example" crossorigin>
```

`crossorigin` нужен, если запросы к API идут с CORS без кук: браузер держит для них отдельный пул соединений, и без атрибута заранее открытое соединение не пригодится ([web.dev о preconnect](https://web.dev/articles/preconnect-and-dns-prefetch)). В headless-сборке Chromium `preconnect` соединений не открывал, поэтому этот эффект проверен по документации, а не замером.

Вариант 2 — убрать отдельный домен: проксировать `/api` через тот же origin (BFF, правило CDN). Тогда API пойдёт по уже открытому соединению страницы, а заодно исчезнут CORS и preflight. В проверке повторные обращения к тому же серверу шли с `connectionReused: true`.
::

::practice{title="Разложи навигацию по шагам"}
Напиши функцию, которая по записи Navigation Timing возвращает время каждого сетевого шага: редиректы, DNS, TCP, TLS, ожидание ответа и загрузку тела.

#solution
```js
function phases(n = performance.getEntriesByType('navigation')[0]) {
  return {
    redirect: n.redirectEnd - n.redirectStart,
    dns: n.domainLookupEnd - n.domainLookupStart,
    tcp: (n.secureConnectionStart || n.connectEnd) - n.connectStart,
    tls: n.secureConnectionStart ? n.connectEnd - n.secureConnectionStart : 0,
    ttfb: n.responseStart - n.requestStart,
    download: n.responseEnd - n.responseStart,
  };
}
```

TLS начинается с `secureConnectionStart`, поэтому время TCP считают до него, а для HTTP он равен нулю. Если соединение переиспользовано, `connectStart` и `connectEnd` совпадают, и TCP с TLS дают ноль. В проверке за прокси с RTT 100 мс функция показала TLS около 105 мс, ожидание ответа около 110 мс, а при повторной навигации — нулевые TCP и TLS. Для ресурсов на других origin без `Timing-Allow-Origin` поля будут нулями.
::
