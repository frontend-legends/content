# Жизненный цикл запроса

«Что происходит, когда ты вводишь URL в адресную строку?» - это, пожалуй, самый классический вопрос на собеседованиях по фронтенду. Ответ может занять 2 минуты или 20 - в зависимости от глубины. Здесь мы разберём каждый этап, покажем, где тратится время, и свяжем это с метриками производительности.

---

## Полная цепочка: от URL до пикселей

```text
  Ввод URL
     │
     ▼
  1. URL parsing + HSTS check
     │
     ▼
  2. DNS Lookup           ← 20–120ms (или 0ms из кэша)
     │
     ▼
  3. TCP Handshake        ← 1 RTT (~20–100ms)
     │
     ▼
  4. TLS Handshake        ← 1 RTT (TLS 1.3) / 2 RTT (TLS 1.2)
     │
     ▼
  5. HTTP Request         ← отправка запроса
     │
     ▼
  6. Server Processing    ← 50–500ms+ (зависит от бэкенда)
     │
     ▼
  7. HTTP Response        ← первый байт (TTFB)
     │
     ▼
  8. HTML Parsing + DOM   ← инкрементальный парсинг
     │
     ▼
  9. Загрузка субресурсов ← CSS, JS, шрифты, изображения
     │
     ▼
  10. Rendering Pipeline   ← DOM + CSSOM -> Render Tree -> Layout -> Paint -> Composite
     │
     ▼
  Пользователь видит страницу
```

Разберём каждый шаг.

---

## 1. URL parsing и HSTS check

<b class="text-on-semi-light">Что делает браузер с URL</b>

<span class="text-gray">Браузер разбирает введённую строку: это URL или поисковый запрос? Если URL - парсит протокол, домен, порт, путь, параметры, фрагмент.</span>

```text
https://api.example.com:443/users?page=1#top
  │          │           │    │      │     │
scheme    hostname     port  path  query fragment
```

<b class="text-on-semi-light">HSTS (HTTP Strict Transport Security)</b>

<span class="text-gray">Если домен есть в HSTS-списке (браузер помнит из предыдущего визита или из preload list) - браузер **автоматически** заменяет `http://` на `https://`, даже если ты вбил URL без протокола. Это происходит до DNS-запроса и предотвращает передачу данных по незащищённому соединению.</span>

---

## 2. DNS Lookup

<b class="text-on-semi-light">Цепочка кэшей</b>

```text
1. Кэш браузера          ← мгновенно (if cached)
2. Кэш ОС (hosts file)   ← мгновенно
3. Кэш роутера / ISP     ← <1ms
4. Recursive resolver     ← если нет в кэше -> идём дальше
5. Root -> TLD -> Authoritative nameserver
```

<span class="text-gray">DNS-резолвинг занимает от 0ms (кэш браузера) до 100+ ms (cold lookup с обходом всей цепочки). Для мобильных сетей задержки ещё выше.</span>

<b class="text-on-semi-light">Влияние на производительность</b>

<span class="text-gray">Каждый новый домен на странице (API, CDN, аналитика, шрифты) - это отдельный DNS lookup. Сократи количество доменов или используй `dns-prefetch` / `preconnect` для критических.</span>

```html
<link rel="dns-prefetch" href="https://cdn.example.com" />
<link rel="preconnect" href="https://api.example.com" crossorigin />
```

> Подробнее о DNS - [Основы сетей](/content/network-api/networking-fundamentals).

## 3. TCP Handshake

<b class="text-on-semi-light">3-way handshake = 1 RTT</b>

```text
Client                    Server
  │── SYN ──────────────>│     ~0ms
  │<── SYN-ACK ─────────│     ~50ms (1/2 RTT)
  │── ACK ──────────────>│     ~100ms (1 RTT)
  │    Соединение установлено
```

<span class="text-gray">RTT (Round-Trip Time) - время, за которое пакет доходит до сервера и обратно. Для пользователя в Москве до сервера в Нью-Йорке RTT ~ 100–150ms. До CDN edge-сервера в том же регионе - 5–20ms.</span>

<b class="text-on-semi-light">TCP Slow Start</b>

<span class="text-gray">Новое TCP-соединение не передаёт данные на полной скорости сразу. Протокол начинает с маленького окна (congestion window ~14KB) и увеличивает его с каждым ACK. Это значит, что первые пакеты данных передаются медленно - ещё одна причина держать critical CSS и HTML маленькими.</span>

---

## 4. TLS Handshake

<b class="text-on-semi-light">TLS 1.3 = ещё 1 RTT</b>

```text
Client                                     Server
  │── ClientHello + key_share ───────────>│
  │<── ServerHello + key_share + cert ────│
  │── Finished ──────────────────────────>│
  │    Зашифрованное соединение установлено
```

<span class="text-gray">Итого к этому моменту: DNS (0–100ms) + TCP (1 RTT) + TLS (1 RTT) = **минимум 2 RTT** до отправки первого HTTP-запроса. С HTTP/3 (QUIC) TCP и TLS handshake объединены в **1 RTT**, а при повторном визите - **0 RTT**.</span>

| Сценарий                 | Handshakes                | Задержка |
| ------------------------ | ------------------------- | -------- |
| HTTP/1.1 + TLS 1.2       | TCP (1 RTT) + TLS (2 RTT) | 3 RTT    |
| HTTP/1.1 + TLS 1.3       | TCP (1 RTT) + TLS (1 RTT) | 2 RTT    |
| HTTP/2 + TLS 1.3         | TCP (1 RTT) + TLS (1 RTT) | 2 RTT    |
| HTTP/3 (QUIC)            | QUIC (1 RTT, включая TLS) | 1 RTT    |
| HTTP/3 (повторный визит) | QUIC 0-RTT                | 0 RTT    |

## 5. HTTP Request

<b class="text-on-semi-light">Отправка запроса</b>

<span class="text-gray">Браузер формирует HTTP-запрос: метод (`GET`), путь, заголовки (`Host`, `User-Agent`, `Accept`, `Cookie`, `Accept-Encoding`). Запрос уходит по установленному TCP/TLS-соединению.</span>

```text
GET / HTTP/2
Host: example.com
Accept: text/html
Accept-Encoding: gzip, br
Cookie: session_id=abc123
```

<span class="text-gray">При первой загрузке страницы это обычно `GET` для HTML-документа. Если в `Cache-Control` или `ETag` есть кэшированная версия - браузер отправляет conditional request (`If-None-Match`, `If-Modified-Since`) и может получить `304 Not Modified` без тела.</span>

---

## 6. Server Processing

<b class="text-on-semi-light">Что происходит на сервере</b>

```text
Запрос -> Load balancer -> Web server -> Application -> Database -> Response
```

<span class="text-gray">Время обработки зависит от сложности: статический HTML - микросекунды, SSR React-приложения - 50–300ms, сложный API-запрос с несколькими SQL - 100–500ms+. Фронтенд-разработчик не контролирует этот этап напрямую, но может влиять: оптимизировать запросы (пагинация, batch, GraphQL), использовать CDN-кэширование, выбрать SSG вместо SSR где возможно.</span>

---

## 7. HTTP Response (TTFB)

<b class="text-on-semi-light">Time to First Byte</b>

<span class="text-gray">TTFB - время от отправки запроса до получения первого байта ответа. Включает: время в сети (RTT) + время обработки на сервере. Хороший TTFB для документа - **менее 800ms** (рекомендация web.dev), идеально - **200–500ms**.</span>

```text
Из чего складывается TTFB:
  DNS lookup + TCP + TLS + Server processing + Network latency
      20ms      50ms  50ms      200ms              50ms       = ~370ms
```

<b class="text-on-semi-light">Streaming response</b>

<span class="text-gray">Сервер может начать отдавать HTML ещё до того, как весь документ готов (chunked transfer encoding, HTTP streaming). Браузер начнёт парсить и рендерить первые байты, пока остальное ещё приходит. Это ключевая оптимизация для SSR.</span>

---

## 8. HTML Parsing и построение DOM

<b class="text-on-semi-light">Инкрементальный парсинг</b>

<span class="text-gray">Браузер не ждёт загрузки всего HTML. Он начинает парсить по мере поступления байтов: tokenization -> tree construction -> DOM. Параллельно preload scanner сканирует HTML вперёд и ставит в очередь загрузку обнаруженных ресурсов.</span>

```text
Bytes -> Characters -> Tokens -> Nodes -> DOM Tree
                                        │
                                        ├── <link href="style.css">  -> загрузка CSS -> CSSOM
                                        ├── <script src="app.js">    -> загрузка JS
                                        └── <img src="hero.webp">    -> загрузка изображения
```

<b class="text-on-semi-light">Блокирующие ресурсы</b>

- **CSS** - render-blocking: браузер не отрисует ничего, пока не построит CSSOM
- **JS без defer/async** - parser-blocking: парсинг HTML останавливается до выполнения скрипта
- **JS с `defer`** - загружается параллельно, выполняется после парсинга HTML
- **JS с `async`** - загружается параллельно, выполняется сразу после загрузки

> Подробнее о рендеринге, Render Tree, Layout, Paint, Composite - [Rendering](/content/web/rendering).

## 9. Загрузка субресурсов

<b class="text-on-semi-light">Параллельная загрузка</b>

<span class="text-gray">Найденные в HTML ресурсы загружаются параллельно. Браузер приоритизирует их: CSS и шрифты для видимой части - высокий приоритет; изображения ниже fold - низкий; скрипты с `defer` - средний.</span>

```text
Timeline загрузки:
──────────────────────────────────────────────────────
HTML:     ██████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
CSS:           ████████████░░░░░░░░░░░░░░░░░░░░░░░░░
JS (defer):    ██████████████████░░░░░░░░░░░░░░░░░░░
Font:               ████████████░░░░░░░░░░░░░░░░░░░░
LCP image:               ██████████████░░░░░░░░░░░░░
Below-fold img:                         ████████████░
──────────────────────────────────────────────────────
               FP    FCP        LCP
```

<b class="text-on-semi-light">Connection reuse и multiplexing</b>

| Стратегия                   | HTTP/1.1                                                             | HTTP/2+                             |
| --------------------------- | -------------------------------------------------------------------- | ----------------------------------- |
| **Keep-Alive**              | Соединение переиспользуется для следующего запроса (последовательно) | Всегда включено                     |
| **Multiplexing**            | Нет - 1 запрос за раз на соединение                                  | Да - множество запросов параллельно |
| **Параллельные соединения** | До 6 на домен                                                        | 1 соединение, множество потоков     |
| **Приоритизация**           | Нет                                                                  | Да (weight и dependency)            |

<span class="text-gray">В HTTP/1.1 keep-alive позволяет не тратить время на повторный TCP+TLS handshake, но запросы идут последовательно. В HTTP/2 одно соединение обслуживает все запросы параллельно - это main reason, почему domain sharding больше не нужен.</span>

## 10. Rendering Pipeline

<b class="text-on-semi-light">От DOM до пикселей</b>

```text
DOM + CSSOM -> Render Tree -> Layout -> Paint -> Composite -> Экран
```

1. **Render Tree** - объединение DOM и CSSOM, только видимые элементы
2. **Layout (Reflow)** - вычисление позиций и размеров каждого элемента
3. **Paint** - преобразование layout в пиксели (слоями)
4. **Composite** - сборка слоёв на GPU и вывод на экран

<span class="text-gray">Первый рендер - самый дорогой. Последующие обновления (взаимодействие пользователя, SPA navigation) могут быть гораздо дешевле, если затрагивают только composite-свойства (`transform`, `opacity`).</span>

> Полный разбор каждого этапа rendering pipeline - [Rendering](/content/web/rendering).

## Связь с Core Web Vitals

Каждый этап жизненного цикла запроса влияет на конкретные метрики.

| Метрика                             | Что измеряет                    | Какие этапы влияют                                  |
| ----------------------------------- | ------------------------------- | --------------------------------------------------- |
| **TTFB**                            | Время до первого байта ответа   | DNS, TCP, TLS, Server Processing                    |
| **FCP** (First Contentful Paint)    | Первый контент на экране        | TTFB + HTML parsing + CSSOM + первый render         |
| **LCP** (Largest Contentful Paint)  | Самый большой элемент отрисован | Всё выше + загрузка LCP-ресурса (изображение/шрифт) |
| **INP** (Interaction to Next Paint) | Отзывчивость на действия        | JS execution time, main thread availability         |
| **CLS** (Cumulative Layout Shift)   | Визуальная стабильность         | Поздняя загрузка ресурсов, динамические вставки     |

<b class="text-on-semi-light">Где теряется время (типичные bottlenecks)</b>

```text
Bottleneck                     Метрика        Решение
─────────────────────────────────────────────────────────────────
Медленный DNS                  TTFB           dns-prefetch, preconnect
Далёкий сервер                 TTFB           CDN, edge computing
Тяжёлый SSR                   TTFB           Caching, streaming SSR, SSG
Большой CSS (render-blocking)  FCP            Critical CSS inline, async rest
Большой JS (parser-blocking)   FCP, INP       Code splitting, defer, lazy load
Тяжёлое LCP-изображение       LCP            Preload, responsive images, WebP/AVIF
Поздняя загрузка шрифтов      FCP, CLS       preload font, font-display: swap
Нет size у img/iframe          CLS            width/height атрибуты, aspect-ratio
Long tasks в JS                INP            Yield to main thread, Web Workers
```

> Подробнее - [Core Web Vitals](/content/web/core-web-vitals).

## Повторная навигация и кэш

<span class="text-gray">При повторном посещении многие этапы пропускаются или ускоряются: DNS из кэша (~0ms), TCP keep-alive (0ms), TLS session resumption (0ms), conditional request с `304 Not Modified`. Итого: первый визит ~700ms, повторный ~100ms.</span>

<b class="text-on-semi-light">Service Worker</b>

<span class="text-gray">Service Worker перехватывает запрос **до** сети и может ответить из Cache API - мгновенно или даже офлайн. Стратегии: cache-first, network-first, stale-while-revalidate.</span>

<b class="text-on-semi-light">SPA-навигация</b>

<span class="text-gray">В SPA переход между страницами не вызывает полный цикл. JavaScript перехватывает навигацию, делает `fetch()` за данными и обновляет DOM на месте. Поэтому критичен первый визит (загрузка JS-бандла), а последующие переходы быстрые. Оптимизация: code splitting, SSR/SSG, prefetch кода следующих страниц.</span>

## Ответ на собеседовании

> Вопрос «что происходит, когда ты вводишь URL?» - это возможность показать глубину знаний. Начни с high-level (DNS, TCP, TLS, HTTP, рендеринг), а потом углубляйся в те области, где ты силён. Не нужно перечислять всё - лучше качественно раскрыть 3–4 этапа, чем скороговоркой пробежать все 10.

<b class="text-on-semi-light">Структура ответа</b>

```text
1. "Браузер парсит URL и проверяет HSTS"
2. "DNS резолвит домен в IP - через цепочку кэшей"
3. "Устанавливается TCP-соединение (3-way handshake)"
4. "TLS handshake - обмен ключами, проверка сертификата"
5. "Отправляется HTTP-запрос, сервер обрабатывает"
6. "Приходит ответ - браузер начинает инкрементальный парсинг HTML"
7. "Строится DOM, параллельно CSSOM, загружаются субресурсы"
8. "Render Tree -> Layout -> Paint -> Composite -> пиксели на экране"
```

<span class="text-gray">Интервьюер может углубиться в любой шаг. Будь готов рассказать про DNS caching, TCP slow start, TLS 1.3 vs 1.2, HTTP/2 multiplexing, critical rendering path, или Core Web Vitals - в зависимости от направления разговора.</span>
