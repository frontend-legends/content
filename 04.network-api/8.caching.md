# HTTP-кеш

HTTP-кеш — механизм, по которому браузер, прокси и CDN повторно используют уже полученные ответы. Правила задаёт сервер заголовками: сколько ответ свежий, кому его можно хранить, как проверить, не изменился ли он. Спрашивают, что значат `max-age`, `no-cache` и `no-store`, как работают `ETag` и 304 и зачем `Vary`. Глубже — почему API без заголовков кеша вдруг кешируется на сутки, почему CDN «съедает» свежесть ответа и чем `stale-while-revalidate` отличается от обычного `max-age`.

::tldr
- **Ответ либо свежий — берётся из кеша без запроса, — либо устаревший — тогда кеш спрашивает сервер.** Свежесть задаёт `Cache-Control: max-age`, а уже прожитое время в других кешах — заголовок `Age`.
- **Проверка устаревшего ответа — условный запрос:** `If-None-Match` с `ETag` или `If-Modified-Since` с `Last-Modified`. Не изменилось — `304 Not Modified` без тела.
- **`no-cache` значит «храни, но проверяй каждый раз», `no-store` — «не храни вовсе».** `private` запрещает общим кешам, `s-maxage` задаёт свежесть для CDN отдельно.
- **Без `Cache-Control` браузер решает сам:** ответ с `Last-Modified` он кеширует эвристически — обычно на десятую часть его возраста. API без заголовков может внезапно отдавать устаревшие данные.
- **`Vary` делает заголовки запроса частью ключа кеша**, а сам кеш браузера разделён по сайту страницы: общая библиотека с CDN для каждого сайта скачивается заново.
::

## Где живут кеши

Сквозной пример — интернет-магазин: HTML страниц, собранные скрипты и стили, картинки товаров, API каталога и корзины.

Ответ может быть сохранён в нескольких местах по пути:

- **кеш браузера** — личный, на устройстве пользователя;
- **общие кеши** — CDN, обратный прокси, корпоративный прокси. Один сохранённый ответ получают многие пользователи.

Есть и другие слои — Service Worker, кеш данных в приложении, кеш назад-вперёд. Как они складываются в стратегию и что такое cache-first — в [Стратегиях кеширования](/content/security-perfomance/caching-strategies). Здесь — сам HTTP-кеш, который работает по заголовкам без единой строки кода на клиенте.

Кешируются в основном ответы на GET. В проверке два одинаковых POST с `max-age=60` оба дошли до сервера.

## Свежесть

Сохранённый ответ бывает **свежим** — его можно отдать сразу, не спрашивая сервер, — или **устаревшим**. Свежесть задаёт сервер:

```text
Cache-Control: max-age=60
```

60 секунд ответ отдаётся из кеша, даже если на сервере уже другая версия. В проверке после смены версии на сервере повторный `fetch` вернул старую, и сервер второго запроса не увидел.

Возраст ответа считается от момента, когда его создал сервер, а не когда он попал в браузер. Если ответ полежал в CDN, тот добавляет заголовок `Age` с прожитыми секундами. `max-age=60` и `Age: 59` — ответ свеж ещё одну секунду: в проверке через 1,2 секунды браузер снова пошёл на сервер. Отсюда ловушка — «поставили `max-age=3600`, а браузер всё равно ходит»: ответ долго лежал в CDN.

### Эвристическая свежесть

Если `Cache-Control` и `Expires` нет, спецификация разрешает кешу назначить свежесть самому — **эвристически**. Если есть `Last-Modified`, обычно берут десятую часть времени, прошедшего с изменения. Ответ, изменённый десять дней назад, будет считаться свежим около суток.

В проверке ответ без `Cache-Control`, но с `Last-Modified` десятидневной давности второй раз взялся из кеша, а ответ без обоих заголовков — дважды из сети. Отсюда реальный баг: фреймворк или прокси ставит `Last-Modified` на ответы API, никто не пишет `Cache-Control`, и пользователи видят вчерашние цены. Правило — **у каждого ответа должен быть явный `Cache-Control`**, для API обычно `no-store` или `no-cache`.

## Проверка: ETag и 304

Устаревший ответ не обязательно скачивать заново. Кеш спрашивает сервер **условным запросом**: «вот версия, которая у меня есть, — она ещё актуальна?»

- **`ETag`** — идентификатор версии, обычно хеш содержимого. Кеш присылает его в `If-None-Match`.
- **`Last-Modified`** — дата изменения. Кеш присылает её в `If-Modified-Since`. Точность — секунда, поэтому `ETag` надёжнее.

Если версия та же, сервер отвечает **`304 Not Modified`** без тела, и кеш продлевает сохранённый ответ. Если нет — обычный `200` с новым телом.

```text
GET /catalog                 → 200, ETag: "v1", тело 40 КБ
GET /catalog
If-None-Match: "v1"          → 304, без тела
```

`ETag` бывает сильным (`"v1"` — байт в байт) и слабым (`W/"v1"` — смысл тот же, байты могут отличаться, например после сжатия). Тот же `ETag` используют для защиты от потерянных обновлений с `If-Match` ([REST](/content/network-api/rest)).

## Директивы Cache-Control

| Директива | Смысл |
| --- | --- |
| `max-age=N` | свежий N секунд |
| `s-maxage=N` | свежесть для общих кешей (CDN), браузер её игнорирует |
| `no-cache` | хранить можно, но перед каждым использованием проверять у сервера |
| `no-store` | не хранить нигде |
| `private` | только кеш браузера, не CDN и прокси |
| `public` | можно общим кешам, даже если запрос был с авторизацией |
| `must-revalidate` | устаревший ответ нельзя отдать без проверки, даже при недоступном сервере |
| `immutable` | не меняется никогда, не проверять даже при перезагрузке |
| `stale-while-revalidate=N` | N секунд после устаревания отдавать старое сразу и обновлять в фоне |
| `stale-if-error=N` | N секунд отдавать старое, если сервер отвечает ошибкой |

Самая частая путаница — **`no-cache` против `no-store`**. `no-cache` не запрещает кеш, а требует проверки: ответ хранится, и при неизменной версии сервер ответит 304 без тела. В проверке ответ с `no-cache` и `ETag` второй раз пришёл условным запросом с `If-None-Match`. `no-store` — для данных, которые нельзя оставлять на диске: персональные данные, банковские выписки.

**`private`** обязателен для всего, что зависит от пользователя, если CDN кеширует ответы: иначе корзина одного покупателя окажется у другого.

### stale-while-revalidate

`max-age=1, stale-while-revalidate=60` — ответ свеж секунду, а следующую минуту его можно отдать устаревшим, одновременно запросив свежий в фоне. Пользователь не ждёт сеть, а следующий запрос уже получит новые данные. В проверке через 1,3 секунды браузер мгновенно вернул старую версию, в фоне сходил на сервер, и следующий `fetch` вернул новую. Ту же идею повторяют библиотеки запросов на уровне приложения ([Загрузка данных в React](/content/reactjs/data-fetching)).

## Vary

Ключ кеша по умолчанию — метод и URL. Если ответ зависит от заголовка запроса — языка, сжатия, origin, — сервер перечисляет его в `Vary`, и значение заголовка становится частью ключа:

```text
Vary: Accept-Encoding, Accept-Language
```

В проверке ответ с `Vary: X-Lang` для `ru` второй раз взялся из кеша, а запрос с `en` пошёл на сервер. Без `Vary` CDN отдал бы англоязычному пользователю русский вариант. Самый частый случай — `Vary: Origin` для CORS ([CORS](/content/network-api/cors)). Слишком широкий `Vary`, например `Vary: Cookie` или `Vary: User-Agent`, разбивает кеш на столько вариантов, что попаданий почти не остаётся.

## Кеш браузера

Несколько особенностей браузерного кеша, которые влияют на код.

**Перезагрузка страницы.** Обычная перезагрузка перепроверяет сам документ, а подресурсы со свежим `max-age` Chromium берёт из кеша без запросов. В проверке после `reload()` сервер увидел только запрос HTML, а скрипт и картинка не запрашивались. Firefox при перезагрузке перепроверяет и подресурсы — `immutable` придумали именно для этого, и он экономит запросы. Жёсткая перезагрузка (Ctrl+Shift+R) идёт мимо кеша.

**Режимы `cache` у `fetch`** управляют кешем для одного запроса:

| Режим | Поведение |
| --- | --- |
| `default` | по заголовкам |
| `no-store` | мимо кеша и не сохранять |
| `reload` | мимо кеша, но сохранить ответ |
| `no-cache` | всегда проверить у сервера, даже свежий |
| `force-cache` | взять из кеша даже устаревшее, в сеть — только если нет |
| `only-if-cached` | только из кеша, иначе ошибка; только для same-origin |

В проверке `force-cache` вернул старую версию, `no-store` — новую, не тронув кеш, а `reload` — новую и сохранил её.

**Разделение по сайту.** Кеш браузера разделён по сайту страницы, на которой сделан запрос: один и тот же URL, запрошенный с двух сайтов, хранится дважды. В проверке ресурс, закешированный на одном сайте, на другом снова пошёл в сеть. Это защита от слежки через кеш, и она означает, что «общая библиотека с публичного CDN уже есть у пользователя в кеше» — больше не аргумент: для вашего сайта она всё равно скачается.

**Кеш назад-вперёд** (bfcache) — не HTTP-кеш: он хранит страницу целиком в памяти, вместе с состоянием JavaScript, и мешают ему другие вещи — например, обработчик `unload` ([Производительность загрузки](/content/security-perfomance/loading-performance)).

## Что как кешировать

| Ресурс | Заголовок | Почему |
| --- | --- | --- |
| собранные файлы с хешем в имени (`app.4f3a.js`) | `public, max-age=31536000, immutable` | имя меняется вместе с содержимым |
| HTML-страницы | `no-cache` и `ETag` | всегда свежая версия, но без лишнего тела |
| публичный API каталога | `public, max-age=60, stale-while-revalidate=300` | данные немного могут отстать |
| персональные данные: корзина, профиль | `private, no-cache` или `no-store` | не попасть в общий кеш |
| картинки товаров без хеша в имени | `max-age=86400` и `ETag` | меняются редко, проверка дешёвая |

Как это выглядит при выкладке, почему старые чанки пропадают после релиза и как сбрасывают кеш CDN — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching).

## Красные флаги в ответе

- **«`no-cache` — не кешировать».** Это «хранить, но проверять перед использованием»; не хранить — `no-store`.
- **«Нет заголовков — нет кеша».** С `Last-Modified` браузер кеширует эвристически, на десятую часть возраста ответа.
- **«`max-age=3600` — значит, час».** Время, прожитое в CDN, вычитается через `Age`.
- **«304 — это ошибка».** Это успешная проверка: версия не изменилась, тело не нужно.
- **«Персональный ответ можно кешировать, он же за авторизацией».** Без `private` CDN может отдать его другому пользователю.
- **«jQuery с публичного CDN уже есть в кеше у всех».** Кеш браузера разделён по сайтам.

## Как спрашивают на собеседовании

::question
Чем `no-cache` отличается от `no-store`?

#answer
`no-cache` разрешает хранить ответ, но требует перепроверять его у сервера перед каждым использованием. Если версия не изменилась, сервер отвечает 304 без тела, и экономится трафик. `no-store` запрещает хранить ответ где-либо: каждый запрос идёт за полным ответом.

#more
`no-cache` — для HTML и данных, которые должны быть свежими, но часто не меняются; `no-store` — для конфиденциального: выписки, персональные данные. В проверке ответ с `no-cache` второй раз пришёл условным запросом с `If-None-Match`. Ещё есть `must-revalidate`: устаревший ответ нельзя отдать без проверки даже при недоступном сервере.
::

::question
Как работают `ETag` и `304 Not Modified`?

#answer
Сервер отдаёт с ответом `ETag` — идентификатор версии, обычно хеш содержимого. Когда ответ в кеше устаревает или требует проверки, кеш отправляет запрос с `If-None-Match: <etag>`. Если версия та же, сервер отвечает 304 без тела, и кеш использует сохранённый ответ; если нет — 200 с новым телом.

#more
Альтернатива — `Last-Modified` и `If-Modified-Since`, но с точностью до секунды. Слабый `ETag` (`W/"..."`) означает смысловую, а не побайтовую эквивалентность. Тот же `ETag` с `If-Match` защищает от потерянных обновлений при записи. Если `ETag` считать по-разному на разных серверах за балансировщиком, условные запросы перестанут срабатывать.
::

::question
Почему ответ API кешируется, хотя мы не ставили заголовков кеша?

#answer
Без `Cache-Control` и `Expires` кешу разрешено назначить свежесть эвристически. Если в ответе есть `Last-Modified`, браузер обычно считает его свежим десятую часть времени с момента изменения: документ, изменённый десять дней назад, — около суток. Фреймворк или прокси может добавлять `Last-Modified` сам.

#more
В проверке ответ только с `Last-Modified` второй раз пришёл из кеша, а ответ без него — из сети. Лечится явным `Cache-Control` на каждом ответе API: `no-store` для персональных данных, `no-cache` с `ETag` или короткий `max-age` для публичных. Отсутствие заголовков — тоже решение, только принятое не тобой.
::

::question
Зачем нужен заголовок `Vary`?

#answer
Он сообщает кешам, от каких заголовков запроса зависит ответ, и они становятся частью ключа кеша. `Vary: Accept-Encoding` — отдельные варианты для разного сжатия, `Vary: Accept-Language` — для языков, `Vary: Origin` — для разных `Access-Control-Allow-Origin`. Без него CDN отдаст одному клиенту вариант, приготовленный для другого.

#more
В проверке ответ с `Vary` для другого значения заголовка пошёл на сервер, а для того же — из кеша. Слишком широкий `Vary` — `Cookie`, `User-Agent` — разбивает кеш на почти уникальные варианты и убивает попадания. Иногда вместо `Vary` вариант кладут в URL: `/ru/catalog` и `/en/catalog`.
::

::question
Что такое `stale-while-revalidate`?

#answer
Директива `Cache-Control`, которая разрешает в течение N секунд после устаревания отдать старый ответ сразу и параллельно запросить свежий. Пользователь не ждёт сеть, а следующий запрос получает обновлённые данные. Это компромисс между скоростью и свежестью для данных, которые могут немного отставать.

#more
В проверке через 1,3 секунды после `max-age=1` браузер мгновенно вернул старую версию, сходил на сервер в фоне, и следующий запрос получил новую. CDN тоже поддерживают эту директиву. Та же модель — устаревшие данные сразу и фоновое обновление — лежит в основе библиотек запросов вроде TanStack Query и SWR.
::

::question
Как кешировать ассеты, HTML и ответы API?

#answer
Собранные файлы с хешем содержимого в имени — `public, max-age=31536000, immutable`: при изменении меняется имя, и кеш не мешает. HTML — `no-cache` с `ETag`: всегда проверка, чтобы пользователь получил ссылки на новые ассеты. Публичный API — короткий `max-age` или `no-cache`, иногда со `stale-while-revalidate`; персональные данные — `private` или `no-store`.

#more
Подресурсы со свежим `max-age` Chromium при обычной перезагрузке не перепроверяет, а Firefox перепроверяет — `immutable` убирает эти лишние запросы. `s-maxage` позволяет кешировать на CDN дольше, чем в браузере, и сбрасывать CDN при релизе. Кеш браузера разделён по сайту, поэтому общий публичный CDN для библиотек больше не экономит загрузку.
::

## Практика

::practice{title="Вчерашние цены"}
API каталога отвечает так, и `Cache-Control` никто не ставил:

```text
HTTP/1.1 200 OK
Content-Type: application/json
Last-Modified: Mon, 01 Sep 2026 10:00:00 GMT
```

После изменения цен часть пользователей до следующего дня видит старые. Почему и как исправить?

#solution
Без `Cache-Control` браузер вправе назначить свежесть эвристически, и с `Last-Modified` двухмесячной давности он считает ответ свежим несколько дней — десятую часть возраста. В проверке ответ только с `Last-Modified` второй раз пришёл из кеша без запроса.

Нужно явно сказать, как кешировать:

```js
res.setHeader('Cache-Control', 'no-cache');   // хранить, но проверять каждый раз
res.setHeader('ETag', `"${hash(body)}"`);       // проверка дешёвая: 304 без тела
// или для данных, которые могут отставать на минуту:
// res.setHeader('Cache-Control', 'public, max-age=60, stale-while-revalidate=300');
```

Правило для API — явный `Cache-Control` на каждом ответе, выставленный общим middleware, чтобы никакой эндпоинт не остался без него.
::

::practice{title="max-age на час, а запросы каждую минуту"}
Сервер отдаёт каталог с `Cache-Control: max-age=3600`, CDN перед ним кеширует с `s-maxage=3600`. По логам браузеры пользователей перезапрашивают каталог почти каждую минуту. Почему?

#solution
Свежесть отсчитывается с момента создания ответа на сервере. Когда браузер получает ответ, пролежавший в CDN 59 минут, CDN добавляет `Age: 3540`, и для браузера ответ свеж всего минуту. В проверке ответ с `max-age=60` и `Age: 59` устарел через секунду, и браузер пошёл в сеть.

Если браузеру нужно хранить ответ дольше, чем он живёт в CDN, задают свежесть отдельно:

```text
Cache-Control: public, max-age=3600, s-maxage=600
```

CDN держит ответ 10 минут и часто обновляет, браузер — час с момента создания ответа. Для данных, которые могут отставать, добавляют `stale-while-revalidate`, чтобы пользователь не ждал перепроверку.
::

::practice{title="Корзина чужого покупателя"}
После подключения CDN покупатель увидел в шапке чужое имя и чужую корзину. Ответ `/api/me` отдаётся так:

```text
Cache-Control: max-age=60
Content-Type: application/json
```

Что не так?

#solution
`max-age` без `private` разрешает хранить ответ любым кешам, включая CDN. Первый пользователь закешировал свой профиль на CDN, и следующие минуту его получали все. Ответы, зависящие от пользователя, должны запрещать общие кеши:

```text
Cache-Control: private, no-cache
```

Или `no-store`, если данные не должны оставаться и в браузере. Дополнительно CDN настраивают не кешировать запросы с куками сессии и заголовком `Authorization`, а персональные эндпоинты держат на отдельном пути, который CDN не кеширует вовсе. После инцидента нужно сбросить кеш CDN — иначе чужие данные продолжат раздаваться до истечения срока.
::
