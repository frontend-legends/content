# Кэширование

Кэширование - один из самых мощных инструментов оптимизации производительности веб-приложений. Правильно настроенный кэш снижает время загрузки страницы, уменьшает трафик и нагрузку на сервер. На собеседованиях часто просят объяснить разницу между `no-cache` и `no-store`, рассказать про стратегии инвалидации и описать, как кэшируют статику в production.

> Эта тема тесно связана с HTTP - если чувствуешь пробелы, начни с [HTTP](/content/network-api/http).

---

## Зачем кэшировать

<b class="text-on-semi-light">Производительность</b>

<span class="text-gray">Ответ из кэша приходит за 0–5 мс вместо 50–500 мс по сети. Для повторных визитов это драматическая разница.</span>

<b class="text-on-semi-light">Трафик</b>

<span class="text-gray">Если файл не изменился - зачем скачивать его заново? Экономия трафика критична на мобильных сетях и для пользователей с лимитированным интернетом.</span>

<b class="text-on-semi-light">UX</b>

<span class="text-gray">Мгновенная загрузка закэшированных страниц создаёт ощущение «быстрого» приложения. Stale-while-revalidate показывает контент сразу, обновляя данные в фоне.</span>

<b class="text-on-semi-light">Нагрузка на сервер</b>

<span class="text-gray">Каждый запрос, обслуженный из кэша - это запрос, который не дошёл до бэкенда. При высоком трафике это может сократить нагрузку на порядок.</span>

---

## HTTP-кэш: Cache-Control

<b class="text-on-semi-light">Главный заголовок управления кэшированием</b>

<span class="text-gray">`Cache-Control` - HTTP-заголовок ответа, определяющий правила кэширования ресурса. Пришёл на замену `Expires` и даёт гораздо более тонкий контроль.</span>

### Основные директивы

| Директива                   | Описание                                                                                                          |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `max-age=3600`              | Ресурс считается свежим 3600 секунд (1 час). В течение этого времени браузер использует кэш без запроса к серверу |
| `no-cache`                  | Кэшировать **можно**, но перед использованием **обязательно** проверить свежесть у сервера (revalidation)         |
| `no-store`                  | **Не кэшировать** вообще. Ни браузер, ни CDN, ни proxy. Для чувствительных данных                                 |
| `immutable`                 | Ресурс никогда не изменится. Браузер не будет revalidate даже при обновлении страницы                             |
| `public`                    | Ответ можно кэшировать везде: браузер, CDN, прокси                                                                |
| `private`                   | Только браузер пользователя. CDN и прокси не кэшируют (для персонализированных данных)                            |
| `s-maxage=3600`             | Как `max-age`, но только для shared caches (CDN, прокси). Переопределяет `max-age` для CDN                        |
| `stale-while-revalidate=60` | Разрешить отдать устаревший ответ, пока в фоне идёт revalidation (в течение 60 сек после истечения max-age)       |
| `must-revalidate`           | После истечения `max-age` - обязательно revalidate. Не отдавать stale-ответ                                       |

### Типичные комбинации

```text
# Статика с хэшем в имени (app.a1b2c3.js) - кэшировать навсегда
Cache-Control: public, max-age=31536000, immutable

# HTML-страница - всегда проверять свежесть
Cache-Control: no-cache

# API с персональными данными - не кэшировать
Cache-Control: no-store

# Публичный API - кэш на 5 минут, CDN на 1 час
Cache-Control: public, max-age=300, s-maxage=3600

# API с SWR - 10 минут кэш, 1 минута stale grace period
Cache-Control: max-age=600, stale-while-revalidate=60
```

> Частая ошибка на собеседованиях: путать `no-cache` и `no-store`. `no-cache` = кэшируй, но проверяй. `no-store` = не кэшируй совсем.

## Валидация кэша: ETag и Last-Modified

Когда `max-age` истёк (или стоит `no-cache`), браузер отправляет **условный запрос** (conditional request) - спрашивает у сервера, изменился ли ресурс. Если нет - сервер отвечает **304 Not Modified** без тела, и браузер использует кэш.

### ETag (Entity Tag)

```text
Первый запрос:
  GET /api/users -> 200 OK
  ETag: "abc123"
  Cache-Control: no-cache

Повторный запрос:
  GET /api/users
  If-None-Match: "abc123"

  -> 304 Not Modified (ресурс не изменился, тело не передаётся)
  -> или 200 OK с новым ETag (ресурс изменился)
```

<span class="text-gray">ETag - это «отпечаток» содержимого. Может быть хэшем контента (strong ETag) или версией/датой (weak ETag, начинается с `W/`).</span>

### Last-Modified

```text
Первый запрос:
  GET /style.css -> 200 OK
  Last-Modified: Mon, 01 Jan 2025 00:00:00 GMT

Повторный запрос:
  GET /style.css
  If-Modified-Since: Mon, 01 Jan 2025 00:00:00 GMT

  -> 304 Not Modified или 200 OK с обновлённым телом
```

<span class="text-gray">`Last-Modified` менее точен (разрешение - 1 секунда), поэтому `ETag` предпочтительнее. Если оба присутствуют, сервер проверяет оба условия.</span>

| Механизм          | Заголовок ответа        | Заголовок условного запроса | Точность            |
| ----------------- | ----------------------- | --------------------------- | ------------------- |
| **ETag**          | `ETag: "abc123"`        | `If-None-Match: "abc123"`   | Побайтовая (strong) |
| **Last-Modified** | `Last-Modified: <date>` | `If-Modified-Since: <date>` | 1 секунда           |

## Expires (legacy)

```text
Expires: Thu, 01 Dec 2025 16:00:00 GMT
```

<span class="text-gray">Устаревший заголовок, задающий абсолютную дату истечения кэша. Проблемы: зависит от синхронизации часов клиента и сервера, менее гибкий. **Если одновременно присутствуют `Cache-Control: max-age` и `Expires` - `Cache-Control` имеет приоритет.** Ты можешь увидеть `Expires` в legacy-системах, но в новых проектах используй только `Cache-Control`.</span>

## CDN-кэширование

<b class="text-on-semi-light">Edge-серверы</b>

<span class="text-gray">CDN (Content Delivery Network) - сеть серверов по всему миру. Когда пользователь в Токио запрашивает файл, CDN отдаёт его с ближайшего edge-сервера (например, из Японии), а не с origin-сервера в Европе. Время ответа падает с 200+ мс до 10–30 мс.</span>

<b class="text-on-semi-light">Origin vs Edge</b>

<span class="text-gray">**Origin** - твой основной сервер. **Edge** - серверы CDN, расположенные ближе к пользователям. CDN кэширует ответы origin-сервера на edge и отдаёт их напрямую.</span>

### Стратегии CDN-кэширования

| Стратегия | Описание                                                      | Когда использовать                       |
| --------- | ------------------------------------------------------------- | ---------------------------------------- |
| **Pull**  | CDN запрашивает у origin при первом обращении, потом кэширует | Статика (JS, CSS, изображения)           |
| **Push**  | Ты загружаешь файлы на CDN заранее                            | Большие файлы, видео                     |
| **Purge** | Принудительная очистка кэша CDN                               | Деплой новой версии, срочные исправления |

<span class="text-gray">Заголовок `s-maxage` управляет TTL кэша на CDN отдельно от браузерного `max-age`. Можно дать CDN кэш на 1 день, а браузеру - на 5 минут.</span>

> CDN-кэширование особенно важно для [Core Web Vitals](/content/web/core-web-vitals) - TTFB напрямую зависит от расстояния до сервера.

## Браузерный кэш

Браузер использует несколько уровней кэша. Понимание их поведения помогает отлаживать проблемы с кэшированием.

<b class="text-on-semi-light">Memory Cache</b>

<span class="text-gray">Хранит ресурсы в оперативной памяти текущей вкладки. Самый быстрый, но живёт только пока вкладка открыта. Используется для preloaded-ресурсов и ресурсов, которые нужны повторно на той же странице.</span>

<b class="text-on-semi-light">Disk Cache (HTTP Cache)</b>

<span class="text-gray">Хранит ресурсы на диске. Переживает перезагрузку вкладки и браузера. Именно этим кэшем управляют заголовки `Cache-Control`, `ETag` и `Last-Modified`.</span>

<b class="text-on-semi-light">Service Worker Cache (Cache API)</b>

<span class="text-gray">Программируемый кэш, управляемый через Service Worker. Ты сам решаешь, что кэшировать, когда обновлять и как обслуживать offline-запросы. Подробнее - [PWA](/content/web/pwa).</span>

<b class="text-on-semi-light">Back/Forward Cache (bfcache)</b>

<span class="text-gray">Браузер сохраняет **полный снимок** страницы (вместе с JS-heap) при навигации назад/вперёд. Страница восстанавливается мгновенно, без перезагрузки. Может ломаться из-за `unload`-обработчиков, `Cache-Control: no-store` и открытых WebSocket-соединений.</span>

```text
Приоритет (от быстрого к медленному):
  1. Memory Cache (~0 мс)
  2. Service Worker Cache (~1-5 мс)
  3. Disk Cache (~5-20 мс)
  4. CDN / Network (~20-200+ мс)
```

В DevTools (вкладка Network) в колонке **Size** видно, откуда пришёл ресурс: `(memory cache)`, `(disk cache)`, `(ServiceWorker)` или реальный размер (из сети).

## Application-level кэш

Помимо HTTP-кэша, приложение может кэшировать данные на уровне JavaScript.

<b class="text-on-semi-light">localStorage / sessionStorage</b>

<span class="text-gray">Простейший key-value кэш. Подходит для настроек, токенов, небольших данных. Не подходит для больших объёмов - синхронный API блокирует main thread. Подробнее - [Браузерное хранилище](/content/network-api/storage).</span>

<b class="text-on-semi-light">TanStack Query (React Query)</b>

<span class="text-gray">Управляет серверным состоянием: кэширует ответы, автоматически revalidate, дедуплицирует одновременные запросы к одному endpoint. Поддерживает stale time, garbage collection, optimistic updates и prefetching.</span>

<b class="text-on-semi-light">SWR (Vercel)</b>

<span class="text-gray">Похожий подход - stale-while-revalidate из коробки. Легковеснее TanStack Query, но и менее функциональный (нет встроенных мутаций, pagination helpers).</span>

```js
// TanStack Query - пример
const { data, isLoading, error } = useQuery({
  queryKey: ["users", userId],
  queryFn: () => fetch(`/api/users/${userId}`).then((r) => r.json()),
  staleTime: 5 * 60 * 1000, // данные считаются свежими 5 минут
  gcTime: 30 * 60 * 1000, // удалить из кэша через 30 минут неиспользования
});
```

## Cache Invalidation

<b class="text-on-semi-light">Самая сложная проблема в Computer Science</b>

<span class="text-gray">«There are only two hard things in Computer Science: cache invalidation and naming things.» - Phil Karlton. Проблема в том, что кэш по своей природе показывает устаревшие данные. Нужны стратегии, чтобы минимизировать stale-период.</span>

### Стратегии инвалидации

<b class="text-on-semi-light">Content Hashing (versioned URLs)</b>

<span class="text-gray">Самая надёжная стратегия для статики. Webpack/Vite добавляют хэш содержимого в имя файла. Изменился файл - изменился хэш - изменился URL - браузер загружает новую версию.</span>

```text
app.js       -> app.a1b2c3d4.js    (хэш содержимого)
styles.css   -> styles.e5f6g7h8.css

# Cache-Control для таких файлов:
Cache-Control: public, max-age=31536000, immutable
```

<span class="text-gray">HTML-файл (index.html) при этом **не кэшируется** (`no-cache`), потому что именно он ссылается на файлы с хэшами. Обновляется HTML - подтягиваются новые версии JS и CSS.</span>

<b class="text-on-semi-light">Query String (cache busting)</b>

<span class="text-gray">Добавление `?v=123` к URL. Менее надёжно - некоторые CDN и прокси игнорируют query string при кэшировании. Content hashing предпочтительнее.</span>

```text
# Менее надёжно:
/styles.css?v=2

# Более надёжно:
/styles.a1b2c3.css
```

<b class="text-on-semi-light">CDN Purge</b>

<span class="text-gray">Принудительная очистка кэша CDN через API или панель управления. Используется для API-ответов и страниц, которые нельзя версионировать через URL.</span>

<b class="text-on-semi-light">TTL-based (time-based expiration)</b>

<span class="text-gray">Просто ждать, пока `max-age` истечёт. Подходит для данных, где небольшая задержка обновления допустима (каталог товаров, список статей).</span>

## Полная картина: кэширование при деплое

```text
Запрос: index.html
├── Cache-Control: no-cache
├── Браузер всегда проверяет свежесть (ETag / Last-Modified)
└── HTML ссылается на -> app.x7y8z9.js, styles.a1b2c3.css

Запрос: app.x7y8z9.js
├── Cache-Control: public, max-age=31536000, immutable
├── Файл с хэшем - кэшируется навсегда
└── При новом деплое HTML будет ссылаться на app.NEW_HASH.js

Запрос: /api/users (динамические данные)
├── Cache-Control: private, max-age=0, must-revalidate
├── ETag: "abc123"
└── При повторном запросе -> 304 Not Modified (если не изменились)
```
