# GraphQL

GraphQL - язык запросов для API и runtime для их выполнения. Создан Facebook в 2012, открыт в 2015. Главная идея: клиент сам описывает, **какие** данные ему нужны, а сервер возвращает **ровно** эти данные - не больше и не меньше. На собесах спрашивают не синтаксис (его можно посмотреть), а **зачем** GraphQL, чем отличается от REST, и когда его выбирать.

---

## Проблемы REST, которые решает GraphQL

<b class="text-on-semi-light">Over-fetching</b>

<span class="text-gray">REST-эндпоинт возвращает **всё** - даже если клиенту нужны два поля из двадцати. Для мобильных сетей это критично.</span>

```text
GET /users/42
-> { id, name, email, avatar, bio, settings, preferences, createdAt, ... }
// Тебе нужны только name и avatar
```

<b class="text-on-semi-light">Under-fetching</b>

<span class="text-gray">Для одного экрана нужны данные из нескольких эндпоинтов - каждый запрос это отдельный round-trip.</span>

```text
// Страница профиля: 3 запроса вместо 1
GET /users/42
GET /users/42/posts
GET /users/42/followers
```

<b class="text-on-semi-light">Жёсткая структура эндпоинтов</b>

<span class="text-gray">В REST каждый экран может потребовать свой набор данных. Бэкенд либо делает кучу эндпоинтов (`/users/42/with-posts`), либо фронтенд дёргает несколько и склеивает. GraphQL решает это одним запросом.</span>

## Queries

Query - запрос на чтение данных. Ты описываешь **форму** ответа, и сервер возвращает данные ровно в этой форме.

```graphql
# Простой query
query {
  user(id: 42) {
    name
    avatar
  }
}
```

```json
{
  "data": {
    "user": {
      "name": "Alice",
      "avatar": "https://cdn.example.com/alice.jpg"
    }
  }
}
```

### Вложенность - один запрос вместо трёх

```graphql
query UserProfile {
  user(id: 42) {
    name
    avatar
    posts(last: 5) {
      title
      comments {
        text
        author {
          name
        }
      }
    }
    followers {
      totalCount
    }
  }
}
```

### Переменные и aliases

```graphql
# Переменные - вместо хардкода значений
query GetUser($userId: ID!, $postsLimit: Int = 10) {
  user(id: $userId) {
    name
    posts(limit: $postsLimit, orderBy: CREATED_AT_DESC) {
      title
    }
  }
}

# Aliases - один field несколько раз с разными аргументами
query {
  currentUser: user(id: 42) {
    name
  }
  otherUser: user(id: 99) {
    name
  }
}
```

## Mutations

Mutation - запрос на изменение данных (аналог POST/PUT/PATCH/DELETE в REST).

```graphql
mutation CreatePost($input: CreatePostInput!) {
  createPost(input: $input) {
    id
    title
    createdAt
  }
}
```

```graphql
# Обновление и удаление
mutation {
  updateUser(id: 42, input: { name: "Alice Cooper" }) {
    id
    name
  }
}
mutation {
  deletePost(id: 100) {
    success
  }
}
```

<b class="text-on-semi-light">Mutation возвращает данные</b>

<span class="text-gray">В отличие от REST, после mutation ты сразу получаешь обновлённый объект (запрашиваешь нужные поля). Не нужен отдельный GET-запрос, чтобы обновить UI.</span>

## Subscriptions

Subscription - real-time обновления через WebSocket. Клиент подписывается на событие и получает данные, когда оно происходит.

```graphql
subscription OnNewMessage($chatId: ID!) {
  messageAdded(chatId: $chatId) {
    id
    text
    author {
      name
    }
    createdAt
  }
}
```

<span class="text-gray">Под капотом subscriptions обычно работают через WebSocket (протокол `graphql-ws`). Клиент открывает постоянное соединение и получает push-уведомления от сервера.</span>

> Подробнее о WebSocket и SSE - [Real-time](/content/network-api/realtime).

## Schema и Type System

GraphQL API определяется **схемой** (schema) - типизированным контрактом между клиентом и сервером.

```graphql
type User {
  id: ID!
  name: String!
  email: String!
  avatar: String
  posts: [Post!]!
}

input CreatePostInput {
  title: String!
  body: String!
  published: Boolean
}

enum PostOrderBy {
  CREATED_AT_ASC
  CREATED_AT_DESC
  TITLE_ASC
}

# Точки входа
type Query {
  user(id: ID!): User
  posts(limit: Int, orderBy: PostOrderBy): [Post!]!
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
  deletePost(id: ID!): DeleteResult!
}
```

### Ключевые концепции типов

| Концепция      | Синтаксис                                 | Значение                                   |
| -------------- | ----------------------------------------- | ------------------------------------------ |
| Non-null       | `String!`                                 | Поле обязательное, не может быть `null`    |
| List           | `[Post]`                                  | Массив (элементы могут быть `null`)        |
| Non-null list  | `[Post!]!`                                | Обязательный массив обязательных элементов |
| Scalar types   | `ID`, `String`, `Int`, `Float`, `Boolean` | Встроенные примитивы                       |
| Custom scalars | `DateTime`, `JSON`, `URL`                 | Определяются сервером                      |

<b class="text-on-semi-light">Resolvers</b>

<span class="text-gray">Для каждого поля в schema сервер определяет **resolver** - функцию, которая знает, откуда взять данные. Resolver для `User.posts` может сходить в БД, в кэш или в другой сервис. Фронтенду это не важно - ты работаешь только со schema.</span>

## Fragments

Fragment - переиспользуемый набор полей. Помогает избежать дублирования в больших запросах.

```graphql
fragment UserCard on User {
  id
  name
  avatar
}

query {
  currentUser: user(id: 42) {
    ...UserCard
    email
  }
  topUsers(limit: 5) {
    ...UserCard
    postsCount
  }
}
```

<b class="text-on-semi-light">Inline Fragments</b>

<span class="text-gray">Для union types и interfaces - когда поле может вернуть разные типы:</span>

```graphql
query Feed {
  feed {
    ... on Post {
      title
      body
    }
    ... on Image {
      url
      caption
    }
    ... on Video {
      url
      duration
    }
  }
}
```

## Сравнение с REST

| Критерий              | REST                           | GraphQL                                                  |
| --------------------- | ------------------------------ | -------------------------------------------------------- |
| Количество эндпоинтов | Много (по ресурсу)             | Один (`/graphql`)                                        |
| Формат ответа         | Фиксирован сервером            | Определяется клиентом                                    |
| Over-fetching         | Частая проблема                | Решено (запрашиваешь только нужное)                      |
| Under-fetching        | Несколько запросов             | Один запрос с вложенностью                               |
| Кэширование           | HTTP-кэш из коробки (GET)      | Сложнее (POST-запросы, нужны клиентские инструменты)     |
| Версионирование       | `/v1/`, `/v2/`                 | Эволюция schema (deprecation полей)                      |
| Загрузка файлов       | Просто (`multipart/form-data`) | Сложнее (нужна спецификация `graphql-multipart-request`) |
| Мониторинг            | По URL и статус-коду           | Сложнее (всё через POST 200, нужен анализ query)         |
| Обучение              | Низкий порог                   | Выше (schema, types, resolvers)                          |
| Типизация             | OpenAPI/Swagger (опционально)  | Встроенная (schema IS the contract)                      |
| Real-time             | Отдельно (WebSocket, SSE)      | Subscriptions - часть спецификации                       |

## Клиентские библиотеки

<b class="text-on-semi-light">Apollo Client</b>

<span class="text-gray">Самый популярный GraphQL-клиент. Нормализованный кэш, optimistic updates, pagination helpers, интеграция с React/Vue/Angular. Мощный, но тяжёлый (~35-50 KB gzipped).</span>

```js
import { useQuery, gql } from "@apollo/client";

const GET_USER = gql`
  query GetUser($id: ID!) {
    user(id: $id) {
      name
      avatar
      posts {
        title
      }
    }
  }
`;

function UserProfile({ userId }) {
  const { data, loading, error } = useQuery(GET_USER, {
    variables: { id: userId },
  });
  if (loading) return <Spinner />;
  if (error) return <Error message={error.message} />;
  return <Profile user={data.user} />;
}
```

<b class="text-on-semi-light">urql</b>

<span class="text-gray">Лёгкая альтернатива (~8 KB gzipped). Модульная архитектура - добавляешь только нужные exchanges (кэш, auth, retry). Проще для небольших проектов.</span>

<b class="text-on-semi-light">TanStack Query + graphql-request</b>

<span class="text-gray">Если тебе не нужен нормализованный кэш - можно использовать `graphql-request` (минимальный клиент) вместе с TanStack Query для кэширования и состояния запросов.</span>

## Когда REST лучше, когда GraphQL

### Выбирай REST, когда:

- Простой CRUD без сложных связей
- Нужен HTTP-кэш из коробки (CDN, browser cache по GET)
- Публичный API для внешних потребителей (REST - привычнее)
- Команда маленькая и не хочет тратить время на schema/resolvers
- Загрузка файлов - основная операция

### Выбирай GraphQL, когда:

- Сложные связанные данные (графовая структура)
- Много разных клиентов (web, mobile, TV) с разными потребностями
- Over/under-fetching становится проблемой
- Нужен real-time (subscriptions)
- Фронтенд хочет двигаться независимо от бэкенда (schema как контракт)

> Это не взаимоисключающие технологии. Многие проекты используют REST для простых CRUD-операций и GraphQL для сложных data-driven экранов. Подробнее о REST - [REST API](/content/network-api/rest).

## Частые вопросы на собесе

**Как GraphQL решает N+1 problem?**
На сервере - через DataLoader (batching + caching). Вместо N отдельных SQL-запросов для N авторов постов, DataLoader собирает все ID и делает один `WHERE id IN (...)`. Фронтенду это прозрачно, но полезно знать для общей картины.

**GraphQL всегда возвращает 200?**
Да, даже при ошибках. Ошибки приходят в поле `errors` рядом с `data`. Это усложняет мониторинг - нельзя просто смотреть на HTTP status. Клиентские библиотеки парсят `errors` автоматически.

```json
{
  "data": { "user": null },
  "errors": [
    {
      "message": "User not found",
      "path": ["user"],
      "extensions": { "code": "NOT_FOUND" }
    }
  ]
}
```

**Что такое introspection?**
GraphQL-сервер может описать свою schema через специальный query `__schema`. Это позволяет инструментам (GraphiQL, Apollo Studio) автогенерировать документацию и автодополнение. В production introspection обычно отключают из соображений безопасности.

**Как кэшировать GraphQL?**
HTTP-кэш не работает (все запросы - POST на один URL). Клиентские библиотеки (Apollo, urql) реализуют **нормализованный кэш**: каждая сущность хранится по `__typename + id`, и при обновлении одного объекта обновляются все места, где он используется.

> Подробнее о получении данных - [Fetching](/content/network-api/fetching).
