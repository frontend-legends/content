# GraphQL

GraphQL — язык запросов к API: сервер описывает схему типов, а клиент в одном запросе перечисляет ровно те поля, которые ему нужны, и получает ответ той же формы. Спрашивают, чем GraphQL отличается от REST, что такое схема, запрос, мутация и подписка и как решают проблему N+1. Глубже — почему ошибка в одном поле обнуляет соседние, почему GraphQL трудно кешировать и как сервер защищается от тяжёлых запросов.

::tldr
- **Схема — договор:** типы, поля и их связи описаны на языке схемы, и сервер проверяет каждый запрос по ней до выполнения. Один адрес вместо множества эндпоинтов.
- **Клиент выбирает поля, ответ повторяет форму запроса.** Нет лишних полей и нет догрузки связанных данных отдельными запросами — то, что в REST называют over-fetching и under-fetching.
- **На каждое поле — свой резолвер, поэтому наивный сервер делает N+1 обращений к базе.** Пакетный загрузчик (DataLoader) собирает ключи за один проход цикла событий и делает один запрос.
- **Ошибки приходят в теле рядом с частичными данными, обычно со статусом 200.** Ошибка в поле с типом «не null» обнуляет ближайшего родителя, который может быть `null`.
- **Один адрес и POST мешают HTTP-кешу;** кеширование переезжает в клиент (нормализованный кеш) или делается через сохранённые запросы по GET. Сервер ограничивает глубину и сложность запросов.
::

## Схема и запросы

Сквозной пример — карточка товара в интернет-магазине чая: название, цена, категория, отзывы, поставщик.

В REST карточка собирается из нескольких запросов: `/products/1`, `/categories/2`, `/products/1/reviews` — или из одного, который отдаёт сразу всё, включая ненужное. GraphQL переворачивает отношения: сервер описывает, что вообще есть, а клиент говорит, что нужно сейчас.

**Схема** описывает типы на своём языке (SDL):

```graphql
type Product {
  id: ID!
  title: String!
  price: Int!
  category: Category!
  reviews: [Review!]
  supplier: Supplier
}
type Query {
  products(first: Int = 10): [Product!]!
  product(id: ID!): Product
}
type Mutation {
  addToCart(productId: ID!): Int!
}
```

`!` означает «не null». Корневые типы — точки входа: **Query** для чтения, **Mutation** для изменений, **Subscription** для событий в реальном времени.

**Запрос** перечисляет поля, и ответ повторяет его форму:

```graphql
query Card($id: ID!) {
  main: product(id: $id) { ...Short price }
  other: product(id: "2") { ...Short }
}
fragment Short on Product { title category { title } }
```

```json
{ "data": {
  "main": { "title": "Чай 1", "category": { "title": "Улуны" }, "price": 300 },
  "other": { "title": "Чай 2", "category": { "title": "Пуэры" } }
} }
```

- **переменные** (`$id`) передаются отдельно от текста запроса — текст остаётся постоянным и его можно кешировать;
- **псевдонимы** (`main:`, `other:`) позволяют запросить одно поле дважды с разными аргументами;
- **фрагменты** — переиспользуемые наборы полей; в клиентах вроде Relay каждый компонент объявляет свой фрагмент, и запрос страницы собирается из них.

В проверке graphql-js вернул ровно такую форму. Запрос отправляется обычно `POST /graphql` с JSON `{ query, variables }`; подписки — по WebSocket или SSE ([Реальное время](/content/network-api/realtime)).

## Как сервер выполняет запрос

Сервер сначала **разбирает и проверяет** запрос по схеме: несуществующее поле, неверный тип аргумента — ошибка ещё до выполнения. Потом **выполняет**: для каждого поля вызывает **резолвер** — функцию, которая возвращает значение поля. Резолвер `product` находит товар, резолвер `category` у товара находит категорию, и так по дереву запроса.

Порядок выполнения разный для разных операций. Поля запроса выполняются параллельно, а поля мутации — строго по очереди, сверху вниз. В проверке в мутации `addToCart` закончилась раньше, чем начался `checkout`, хотя была медленнее, а в обычном запросе второе поле началось, не дожидаясь первого. Поэтому несколько изменений в одной мутации выполняются предсказуемо.

### Проблема N+1

Резолвер на каждое поле — источник главной проблемы производительности GraphQL. Запрос «десять товаров с категориями» вызывает резолвер `products` один раз и резолвер `category` — десять раз, по разу на товар. Если каждый ходит в базу, получается **1 + N** запросов. В проверке так и вышло: десять обращений к базе за категориями.

Решение — **пакетная загрузка**. Резолверы не ходят в базу сами, а просят загрузчик: «дай категорию 1», «дай категорию 2». Загрузчик копит ключи, пока выполняется текущий шаг, и в конце делает один запрос за всеми:

```js
function createLoader(batch) {
  let queue = [];
  return (key) => new Promise((resolve, reject) => {
    queue.push({ key, resolve, reject });
    if (queue.length === 1) queueMicrotask(async () => {
      const current = queue;
      queue = [];
      const keys = [...new Set(current.map((q) => q.key))];
      try {
        const values = await batch(keys);                  // один запрос: WHERE id IN (...)
        current.forEach((q) => q.resolve(values[keys.indexOf(q.key)]));
      } catch (e) { current.forEach((q) => q.reject(e)); }
    });
  });
}

const loadCategory = createLoader((ids) => db.categoriesByIds(ids));
const resolvers = { Product: { category: (p) => loadCategory(p.categoryId) } };
```

В проверке те же десять товаров дали одно обращение к базе `categories 1,2` — с повторяющимися ключами, схлопнутыми в два. Это идея библиотеки DataLoader; загрузчик создают заново на каждый запрос, чтобы кеш не перетекал между пользователями. Та же проблема N+1 в базах данных и ORM — в [Введении в базы данных](/content/computer-science/intro-to-db).

## Ошибки и null

GraphQL возвращает **частичный результат**: если упал резолвер отзывов, название товара всё равно придёт, а в `errors` будет сообщение и путь к полю.

```json
{
  "data": { "product": { "title": "Чай 3", "reviews": null } },
  "errors": [{ "message": "Сервис отзывов недоступен", "path": ["product", "reviews"] }]
}
```

Статус такого ответа обычно 200, поэтому `response.ok` ошибку не видит. Как с этим обходятся клиенты — в [Клиентах API](/content/ecosystem-libs/realtime-and-api-clients).

Неочевидное правило касается полей с `!`. Поле «не null» не может стать `null` — значит, при ошибке в нём `null` **всплывает** к ближайшему родителю, который может быть `null`. В проверке у поставщика упал резолвер `name: String!`, и в ответе обнулился весь `supplier`. Если бы и `supplier` был `Supplier!`, обнулился бы товар, а в списке `[Product!]!` — весь список и, дальше, весь `data`.

Отсюда практика проектирования: поля, которые зависят от других сервисов и могут упасть, делают **nullable**, чтобы ошибка в отзывах не обнуляла карточку товара. `!` ставят там, где значение гарантировано: `id`, обязательные скаляры.

## Кеширование

В REST у каждого ресурса свой адрес, и HTTP-кеш, CDN и браузер кешируют `GET /products/1` без участия кода ([Кеширование](/content/network-api/caching)). В GraphQL один адрес и обычно POST — HTTP-кеш не работает. Кеширование переезжает:

- **в клиент** — нормализованный кеш Apollo и Relay раскладывает ответы на сущности по `__typename` и `id`. Изменили товар в мутации — обновились все запросы, где он встречается. Как устроены такие кеши — в [Библиотеках данных](/content/ecosystem-libs/state-and-data-libraries);
- **в сохранённые запросы** — клиент при сборке регистрирует тексты запросов на сервере, а во время работы отправляет только хеш: `GET /graphql?id=<sha256>&variables=...`. Такой адрес короткий и одинаковый у всех — его кеширует CDN. Заодно сервер выполняет только известные запросы;
- **на сервер** — кеш резолверов и данных, как в любом бэкенде.

## Защита сервера

Язык запросов отдаёт клиенту много власти, и сервер должен её ограничивать:

- **глубина и сложность** — рекурсивные связи позволяют написать `me { friends { friends { friends ... } } }` и положить сервер одним запросом. Правило проверки отклоняет запрос до выполнения: в проверке запрос глубиной 7 при лимите 4 получил ошибку «Глубина запроса 7 больше 4». Сложность считают точнее — с учётом размеров списков;
- **интроспекция** — запрос `__schema` возвращает всю схему. В разработке это основа автодополнения и генерации типов, в продакшене её часто отключают правилом проверки `NoSchemaIntrospectionCustomRule`, чтобы не показывать устройство API;
- **только известные запросы** — сохранённые запросы из белого списка;
- **лимиты** — тайм-ауты, ограничение размера ответа и частоты запросов.

## GraphQL или REST

| | REST | GraphQL |
| --- | --- | --- |
| Адреса | по ресурсу на адрес | один адрес |
| Что приходит | что решил сервер | что попросил клиент |
| Связанные данные | несколько запросов или специальные эндпоинты | в одном запросе |
| HTTP-кеш | работает из коробки | нужен клиентский кеш или сохранённые запросы |
| Ошибки | статусы HTTP | `errors` в теле, обычно 200 |
| Типы | по описанию OpenAPI | схема встроена, интроспекция |
| Сложность сервера | проще | резолверы, N+1, лимиты |

GraphQL выигрывает, когда клиентов много и им нужны разные срезы данных — веб, мобильные приложения, партнёры, — а данные сильно связаны. REST проще, когда ресурсы простые, важен HTTP-кеш и CDN, а команда маленькая. Часто между фронтендом и сервисами ставят BFF, который отдаёт каждому клиенту нужную форму данных ([API и BFF](/content/architecture/api-and-bff)).

Схема GraphQL меняется без версий: новые поля добавляют, старые помечают `@deprecated` и удаляют, когда клиенты перестали их запрашивать.

## Красные флаги в ответе

- **«GraphQL — это база данных» или «GraphQL заменяет SQL».** Это слой API; данные резолверы берут откуда угодно.
- **«GraphQL решает проблему N+1».** Наивный сервер на резолверах её как раз создаёт; решают её загрузчики.
- **«Ошибку видно по статусу ответа».** Ошибки приходят в `errors`, часто вместе с частичными данными и статусом 200.
- **«Поставим `!` на все поля — так надёжнее».** Ошибка в таком поле обнулит родителя, а то и весь ответ.
- **«GraphQL кешируется как REST».** Один адрес и POST отключают HTTP-кеш; нужны клиентский кеш или сохранённые запросы.
- **«Клиент может спросить что угодно — это удобно».** Без лимитов глубины и сложности один запрос кладёт сервер.

## Как спрашивают на собеседовании

::question
Чем GraphQL отличается от REST?

#answer
В REST у каждого ресурса свой адрес, а состав ответа определяет сервер. В GraphQL один адрес и схема типов, а клиент в запросе перечисляет нужные поля, включая связанные данные, и получает ответ той же формы. Это убирает лишние поля и цепочки запросов, но переносит сложность на сервер — резолверы, N+1, лимиты — и ломает HTTP-кеш.

#more
GraphQL хорош, когда разным клиентам нужны разные срезы связанных данных. REST проще для простых ресурсов и выигрывает в кешировании через CDN. Ошибки в GraphQL — в теле ответа, обычно со статусом 200. Схема встроена и доступна через интроспекцию, поэтому типы для клиента генерируются автоматически.
::

::question
Что такое схема, запрос, мутация и подписка?

#answer
Схема описывает типы, поля и связи на языке SDL и служит договором: сервер проверяет каждый запрос по ней. Query — чтение, Mutation — изменения, Subscription — поток событий, обычно по WebSocket. У каждого поля есть резолвер, который возвращает его значение.

#more
Поля запроса выполняются параллельно, а поля мутации — по очереди сверху вниз; в проверке мутация `checkout` началась только после завершения `addToCart`. Переменные передают отдельно от текста запроса, псевдонимы позволяют запросить одно поле с разными аргументами, фрагменты — переиспользовать наборы полей.
::

::question
Что такое проблема N+1 в GraphQL и как её решают?

#answer
Резолвер вызывается на каждое поле каждого объекта. Список из N товаров с категориями даёт один запрос за товарами и N запросов за категориями. Решение — пакетный загрузчик вроде DataLoader: резолверы просят значения по ключу, загрузчик копит ключи за один проход цикла событий и делает один запрос с `IN (...)`.

#more
В проверке десять товаров дали десять обращений к базе без загрузчика и одно — с ним, а повторяющиеся ключи схлопнулись. Загрузчик создают на каждый запрос, чтобы кеш не делился между пользователями. Альтернатива — анализировать запрос заранее и строить один SQL с JOIN, как делают некоторые серверные библиотеки.
::

::question
Почему ошибка в одном поле может обнулить весь объект?

#answer
Поле с типом «не null» (`String!`) не может вернуть `null`. Если его резолвер упал, `null` всплывает к ближайшему родителю, который может быть `null`, и обнуляется уже он. В цепочке из обязательных полей ошибка может дойти до корня и обнулить весь `data`.

#more
В проверке ошибка в `supplier.name: String!` обнулила весь `supplier`. Поэтому поля, которые зависят от внешних сервисов, делают nullable: упали отзывы — карточка товара всё равно покажется. Ошибки при этом приходят в `errors` с путём к полю.
::

::question
Как кешировать GraphQL?

#answer
HTTP-кеш почти не работает: один адрес и POST. Поэтому кешируют в клиенте — нормализованный кеш Apollo и Relay раскладывает ответы по `__typename` и `id` и обновляет все запросы, где встречается сущность. Для CDN используют сохранённые запросы: клиент отправляет GET с хешем вместо текста запроса, и такой адрес можно кешировать.

#more
Сохранённые запросы ещё и защищают: сервер выполняет только зарегистрированные тексты. Ответы с данными пользователя кешировать в CDN нельзя, поэтому публичные данные — каталог — отделяют от персональных. Серверный кеш резолверов и данных работает как в любом бэкенде.
::

::question
Как защитить GraphQL-сервер от тяжёлых запросов?

#answer
Ограничить глубину и сложность запроса правилами проверки до выполнения, поставить тайм-ауты и лимиты частоты. В продакшене часто разрешают только сохранённые запросы и отключают интроспекцию. Связи, которые позволяют рекурсию вроде `friends { friends { ... } }`, особенно требуют лимита глубины.

#more
В проверке правило глубины отклонило запрос глубиной 7 при лимите 4 ещё до выполнения. Сложность считают точнее: стоимость поля, умноженная на размер списка из аргумента `first`. Пагинация списков обязательна — `products` без лимита может вернуть всю базу. Отключение интроспекции не заменяет проверку прав в резолверах.
::

## Практика

::practice{title="Каталог делает сотню запросов к базе"}
Резолверы каталога:

```js
const resolvers = {
  Query: { products: () => db.query('SELECT * FROM products LIMIT 100') },
  Product: { category: (p) => db.query('SELECT * FROM categories WHERE id = $1', [p.categoryId]) },
};
```

Запрос `{ products { title category { title } } }` отвечает медленно, в логах базы — 101 запрос. Почему и как исправить?

#solution
Резолвер `category` вызывается для каждого из ста товаров отдельно — классическая проблема N+1. Нужен пакетный загрузчик, который соберёт идентификаторы и сделает один запрос:

```js
import DataLoader from 'dataloader';

function createLoaders() {
  return {
    category: new DataLoader(async (ids) => {
      const rows = await db.query('SELECT * FROM categories WHERE id = ANY($1)', [ids]);
      const byId = new Map(rows.map((r) => [r.id, r]));
      return ids.map((id) => byId.get(id) ?? null);   // порядок как у ключей
    }),
  };
}

const resolvers = {
  Product: { category: (p, args, ctx) => ctx.loaders.category.load(p.categoryId) },
};
// на каждый HTTP-запрос: context: () => ({ loaders: createLoaders() })
```

Два запроса вместо ста одного. Функция пакетной загрузки обязана вернуть значения в том же порядке и количестве, что и ключи. В проверке мини-версия такого загрузчика свела десять обращений к одному.
::

::practice{title="Упали отзывы — пропала карточка"}
Схема:

```graphql
type Product { id: ID!, title: String!, reviews: [Review!]! }
type Query { product(id: ID!): Product! }
```

Когда сервис отзывов недоступен, карточка товара целиком показывает ошибку, хотя название и цена есть. Почему?

#solution
Резолвер `reviews` бросил ошибку. Поле `reviews` объявлено как `[Review!]!` — не может быть `null`, — поэтому `null` всплывает к родителю `product`. Но и `product` объявлен как `Product!`, и `null` всплывает дальше, до `data`. Клиент получает `data: null` и ошибку.

Поля, которые зависят от внешних сервисов, делают nullable:

```graphql
type Product { id: ID!, title: String!, reviews: [Review!] }
type Query { product(id: ID!): Product }
```

Теперь при сбое приходит `{ "product": { "title": "...", "reviews": null } }` и ошибка в `errors` с путём `["product", "reviews"]`. Интерфейс показывает карточку и заглушку вместо отзывов. В проверке ошибка в поле с `!` обнулила родителя, а в nullable-поле — только его само.
::

::practice{title="Один запрос положил сервер"}
Схема соцсети магазина позволяет запрашивать друзей пользователя, а у друга — снова друзей. После релиза кто-то отправил запрос с вложенностью в двадцать уровней, и сервер перестал отвечать. Как защититься?

#solution
Рекурсивные связи позволяют построить запрос, объём работы которого растёт экспоненциально с глубиной. Защита — проверка до выполнения. Правило глубины на graphql-js:

```js
import { validate, specifiedRules, GraphQLError, Kind } from 'graphql';

const maxDepth = (limit) => (context) => ({
  OperationDefinition(node) {
    const depth = (set, d) => (set?.selections ?? []).reduce(
      (max, s) => Math.max(max, s.kind === Kind.FIELD ? depth(s.selectionSet, d + 1) : depth(s.selectionSet, d)), d);
    const d = depth(node.selectionSet, 0);
    if (d > limit) context.reportError(new GraphQLError(`Глубина запроса ${d} больше ${limit}`));
  },
});

const errors = validate(schema, document, [...specifiedRules, maxDepth(6)]);
```

В проверке запрос глубиной 7 при лимите 4 был отклонён. Фрагменты в этой упрощённой версии не разворачиваются — в продакшене берут готовые правила глубины и сложности. Плюс обязательная пагинация списков, тайм-аут на выполнение и, если клиенты свои, — только сохранённые запросы.
