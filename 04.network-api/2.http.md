# HTTP глубоко

HTTP (HyperText Transfer Protocol) - основа всего веба. Каждый раз, когда ты открываешь страницу, отправляешь форму или делаешь `fetch()` - под капотом работает HTTP. На собеседованиях ожидают, что ты знаешь не только методы и статус-коды, но и разницу между версиями протокола, ключевые заголовки и как это всё влияет на производительность.

---

## Структура HTTP-запроса и ответа

<b class="text-on-semi-light">Request</b>

```text
GET /api/users?page=1 HTTP/1.1        ← Request line (метод, путь, версия)
Host: api.example.com                  ← Заголовки
Authorization: Bearer eyJhbG...
Accept: application/json
Content-Type: application/json

{"name": "Alice"}                      ← Тело (body) - не у всех методов
```

<b class="text-on-semi-light">Response</b>

```text
HTTP/1.1 200 OK                        ← Status line (версия, код, текст)
Content-Type: application/json          ← Заголовки
Cache-Control: max-age=3600
Content-Length: 82

{"users": [{"id": 1, "name": "Alice"}]} ← Тело (body)
```

<span class="text-gray">HTTP - текстовый протокол (в версиях 1.x). Каждый запрос - независимый (stateless): сервер не помнит предыдущие запросы. Состояние хранится через cookies, токены, сессии.</span>

## HTTP-методы

| Метод       | Описание                                 | Тело запроса | Идемпотентный | Safe |
| ----------- | ---------------------------------------- | ------------ | ------------- | ---- |
| **GET**     | Получить ресурс                          | Нет          | Да            | Да   |
| **POST**    | Создать ресурс / отправить данные        | Да           | Нет           | Нет  |
| **PUT**     | Полностью заменить ресурс                | Да           | Да            | Нет  |
| **PATCH**   | Частично обновить ресурс                 | Да           | Нет           | Нет  |
| **DELETE**  | Удалить ресурс                           | Редко        | Да            | Нет  |
| **OPTIONS** | Узнать поддерживаемые методы (preflight) | Нет          | Да            | Да   |
| **HEAD**    | Как GET, но без тела ответа              | Нет          | Да            | Да   |

<b class="text-on-semi-light">Идемпотентность (Idempotent)</b>

<span class="text-gray">Повторный запрос с теми же параметрами даёт тот же результат. `PUT /users/1 {name: "Alice"}` - сколько ни отправляй, результат один. `POST /users {name: "Alice"}` - каждый раз может создаваться новый пользователь.</span>

<b class="text-on-semi-light">Safe-методы</b>

<span class="text-gray">Не изменяют состояние сервера. GET и HEAD - только чтение. Это важно: браузер может prefetch'ить GET-запросы, повторять их при ошибке сети, кэшировать. POST повторять автоматически нельзя.</span>

> На собеседовании часто спрашивают: «Чем PUT отличается от PATCH?» PUT заменяет ресурс целиком (нужно отправить все поля), PATCH - частичное обновление (только изменённые поля).

## Статус-коды

### 1xx - Informational

| Код | Значение            | Когда встретишь   |
| --- | ------------------- | ----------------- |
| 101 | Switching Protocols | WebSocket upgrade |

### 2xx - Success

| Код | Значение   | Когда встретишь                      |
| --- | ---------- | ------------------------------------ |
| 200 | OK         | Успешный GET, PUT, PATCH             |
| 201 | Created    | Успешный POST (ресурс создан)        |
| 204 | No Content | Успешный DELETE (тело ответа пустое) |

### 3xx - Redirection

| Код | Значение                   | Когда встретишь                 |
| --- | -------------------------- | ------------------------------- |
| 301 | Moved Permanently          | SEO-редирект, смена домена      |
| 302 | Found (временный редирект) | Временная переадресация         |
| 304 | Not Modified               | Кэш валиден, тело не передаётся |
| 307 | Temporary Redirect         | Как 302, но сохраняет метод     |
| 308 | Permanent Redirect         | Как 301, но сохраняет метод     |

<span class="text-gray">Разница между 301/308 и 302/307: старые 301 и 302 позволяли браузеру менять метод (POST -> GET) при редиректе. 307 и 308 гарантируют сохранение метода. На практике это важно для POST-запросов.</span>

### 4xx - Client Error

| Код | Значение             | Типичная причина                          |
| --- | -------------------- | ----------------------------------------- |
| 400 | Bad Request          | Невалидное тело запроса, битый JSON       |
| 401 | Unauthorized         | Нет токена / токен протух                 |
| 403 | Forbidden            | Токен есть, но прав недостаточно          |
| 404 | Not Found            | Ресурс не существует                      |
| 405 | Method Not Allowed   | POST на endpoint, где разрешён только GET |
| 409 | Conflict             | Конфликт версий (optimistic locking)      |
| 422 | Unprocessable Entity | Валидация не прошла                       |
| 429 | Too Many Requests    | Rate limiting сработал                    |

### 5xx - Server Error

| Код | Значение              | Типичная причина                              |
| --- | --------------------- | --------------------------------------------- |
| 500 | Internal Server Error | Баг на сервере, необработанное исключение     |
| 502 | Bad Gateway           | Прокси/nginx не может достучаться до upstream |
| 503 | Service Unavailable   | Сервер перегружен, maintenance                |
| 504 | Gateway Timeout       | Upstream не ответил вовремя                   |

> 401 vs 403 - частый вопрос. **401** - «Кто ты? Представься» (нет аутентификации). **403** - «Я знаю, кто ты, но тебе нельзя» (нет авторизации).

## Ключевые заголовки

### Request headers

| Заголовок         | Назначение                              | Пример                  |
| ----------------- | --------------------------------------- | ----------------------- |
| `Host`            | Домен сервера (обязательный в HTTP/1.1) | `Host: api.example.com` |
| `Authorization`   | Токен аутентификации                    | `Bearer eyJhbG...`      |
| `Accept`          | Какой формат ответа клиент хочет        | `application/json`      |
| `Content-Type`    | Формат тела запроса                     | `application/json`      |
| `Cookie`          | Cookies, отправляемые серверу           | `session_id=abc123`     |
| `User-Agent`      | Информация о клиенте                    | `Mozilla/5.0 ...`       |
| `Accept-Encoding` | Поддерживаемые сжатия                   | `gzip, br`              |
| `If-None-Match`   | ETag для conditional request            | `"abc123"`              |

### Response headers

| Заголовок                     | Назначение                  | Пример                             |
| ----------------------------- | --------------------------- | ---------------------------------- |
| `Content-Type`                | Формат тела ответа          | `application/json; charset=utf-8`  |
| `Cache-Control`               | Инструкции кэширования      | `max-age=3600, public`             |
| `Set-Cookie`                  | Установить cookie           | `session_id=abc; HttpOnly; Secure` |
| `ETag`                        | Версия ресурса              | `"v1-abc123"`                      |
| `Access-Control-Allow-Origin` | CORS - кому разрешён доступ | `https://app.example.com`          |
| `Content-Encoding`            | Сжатие тела ответа          | `gzip`, `br`                       |
| `Location`                    | URL для редиректа (3xx)     | `https://example.com/new-page`     |

### Content Negotiation

<b class="text-on-semi-light">Accept / Content-Type</b>

<span class="text-gray">`Accept` в запросе говорит: «Я хочу получить ответ в таком формате». `Content-Type` в запросе говорит: «Я отправляю тело в таком формате». `Content-Type` в ответе говорит: «Вот формат того, что я тебе отдаю».</span>

```js
// Отправляем JSON, хотим получить JSON
fetch("/api/users", {
  method: "POST",
  headers: {
    "Content-Type": "application/json", // тело запроса - JSON
    Accept: "application/json", // хотим JSON в ответе
  },
  body: JSON.stringify({ name: "Alice" }),
});
```

<b class="text-on-semi-light">Custom headers</b>

<span class="text-gray">Можно добавлять свои заголовки с префиксом `X-` (устаревшее соглашение) или без него. Часто используются для передачи request ID, версии API, feature flags. На CORS-запросах кастомные заголовки требуют `Access-Control-Allow-Headers` от сервера.</span>

## HTTP/1.1 vs HTTP/2 vs HTTP/3

| Характеристика            | HTTP/1.1                     | HTTP/2                            | HTTP/3                      |
| ------------------------- | ---------------------------- | --------------------------------- | --------------------------- |
| **Транспорт**             | TCP                          | TCP                               | QUIC (UDP)                  |
| **Формат**                | Текстовый                    | Бинарный                          | Бинарный                    |
| **Мультиплексирование**   | Нет (1 запрос на соединение) | Да (потоки в одном TCP)           | Да (потоки в одном QUIC)    |
| **Head-of-line blocking** | На уровне соединения         | На уровне TCP (при потере пакета) | Нет (потоки независимы)     |
| **Сжатие заголовков**     | Нет                          | HPACK                             | QPACK                       |
| **Server Push**           | Нет                          | Да (но почти не используется)     | Да (удалён из спецификации) |
| **Шифрование**            | Опционально (HTTPS)          | Фактически обязательно            | Встроено в QUIC             |
| **Установка соединения**  | TCP + TLS = 2-3 RTT          | TCP + TLS = 2-3 RTT               | 1 RTT (0-RTT при повторном) |

<b class="text-on-semi-light">HTTP/1.1: проблемы</b>

<span class="text-gray">Один запрос за раз на одно TCP-соединение. Браузеры открывают 6 параллельных соединений к одному домену - это породило хаки: domain sharding, sprite sheets, конкатенация файлов. С HTTP/2 эти хаки стали антипаттернами.</span>

<b class="text-on-semi-light">HTTP/2: мультиплексирование</b>

<span class="text-gray">Множество запросов и ответов передаются параллельно в одном TCP-соединении через потоки (streams). Не нужно ждать, пока предыдущий ответ завершится. Но если TCP-пакет потерялся - блокируются **все** потоки (TCP-level head-of-line blocking).</span>

<b class="text-on-semi-light">HTTP/3: QUIC</b>

<span class="text-gray">Решает проблему TCP HOL blocking - QUIC реализует потоки на уровне транспорта, и потеря пакета в одном потоке не влияет на остальные. Плюс: быстрая установка соединения (1 RTT, 0-RTT при повторном визите), встроенное шифрование, лучшая работа при смене сети (Wi-Fi -> мобильная).</span>

```text
HTTP/1.1:  ──req1──resp1──req2──resp2──req3──resp3──  (последовательно)

HTTP/2:    ──req1──req2──req3──                        (параллельно в одном TCP)
           ──resp2──resp1──resp3──

HTTP/3:    ──stream1──stream2──stream3──               (параллельно, каждый независим)
           потеря в stream1 не блокирует stream2
```

> На практике: если твой сервер за Cloudflare или на Vercel - HTTP/2 и HTTP/3 уже включены. Для собеседования важно объяснить **зачем** каждая версия появилась и какую проблему решает.

## HTTPS: что добавляет TLS

<span class="text-gray">HTTPS = HTTP + TLS. Протокол HTTP не меняется - он просто работает внутри зашифрованного TLS-туннеля. Все заголовки и тело запроса зашифрованы. Видно только: IP-адрес назначения и (до ECH) домен в SNI.</span>

Что HTTPS защищает:

- **Конфиденциальность** - данные зашифрованы, перехватчик видит «мусор»
- **Целостность** - данные нельзя подменить в пути (MAC проверка)
- **Аутентификация** - сертификат подтверждает, что ты говоришь с настоящим сервером

> Подробнее о TLS handshake, сертификатах и шифровании - [Основы сетей](/content/network-api/networking-fundamentals).

## Сжатие

<b class="text-on-semi-light">Content-Encoding</b>

<span class="text-gray">Сервер сжимает тело ответа, браузер автоматически распаковывает. Это уменьшает объём передаваемых данных в 3–10 раз для текстовых ресурсов (JS, CSS, HTML, JSON).</span>

| Алгоритм   | Заголовок                | Степень сжатия      | Скорость                             |
| ---------- | ------------------------ | ------------------- | ------------------------------------ |
| **gzip**   | `Content-Encoding: gzip` | Хорошая             | Быстрый                              |
| **Brotli** | `Content-Encoding: br`   | Лучше на 15–25%     | Медленнее сжатие, быстрая распаковка |
| **zstd**   | `Content-Encoding: zstd` | Сопоставим с Brotli | Быстрее сжатие                       |

```js
// Браузер автоматически сообщает, что поддерживает:
// Accept-Encoding: gzip, deflate, br

// Сервер выбирает лучший и указывает в ответе:
// Content-Encoding: br
```

<span class="text-gray">Brotli доступен только через HTTPS. Для статических ресурсов Brotli - лучший выбор (можно предварительно сжать на этапе билда). Для динамических API-ответов gzip может быть предпочтительнее из-за скорости сжатия.</span>

## Часто спрашивают на собеседовании

<b class="text-on-semi-light">Чем GET отличается от POST?</b>

<span class="text-gray">GET - для получения данных, safe, идемпотентный, кэшируется, параметры в URL. POST - для отправки данных, может менять состояние, не кэшируется, параметры в body. GET-запрос можно повторить безопасно, POST - нет.</span>

<b class="text-on-semi-light">Что такое идемпотентность?</b>

<span class="text-gray">Повторный вызов с теми же параметрами не меняет результат. GET, PUT, DELETE - идемпотентные. POST - нет (каждый вызов может создать новый ресурс). PATCH - формально нет, хотя на практике часто реализуется идемпотентно.</span>

<b class="text-on-semi-light">Зачем нужен HTTP/2?</b>

<span class="text-gray">Мультиплексирование: много запросов в одном соединении без head-of-line blocking на уровне HTTP. Сжатие заголовков (HPACK). Бинарный формат. Устраняет необходимость в хаках HTTP/1.1 (domain sharding, sprites, бандл всего в один файл).</span>
