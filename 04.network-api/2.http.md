# HTTP

HTTP — протокол «запрос — ответ», на котором работает веб: браузер просит ресурс методом и заголовками, сервер отвечает статусом, заголовками и телом. Спрашивают, чем GET отличается от POST, что такое идемпотентность, какие бывают коды ответа и чем HTTP/2 лучше HTTP/1.1. Глубже — почему форма после редиректа теряет данные, почему картинки при HTTP/1.1 грузятся волнами по шесть и зачем HTTP/3 ушёл на UDP.

::tldr
- **HTTP-сообщение — стартовая строка, заголовки, пустая строка и тело.** В HTTP/1.1 это текст поверх TCP; длину тела задаёт `Content-Length` или передача кусками (`chunked`).
- **Методы различаются гарантиями:** безопасные (GET, HEAD) ничего не меняют, идемпотентные (ещё PUT и DELETE) можно безопасно повторить, POST не гарантирует ни того, ни другого.
- **Статус сообщает результат классом:** 2xx — успех, 3xx — перенаправление, 4xx — ошибка клиента, 5xx — ошибка сервера. После 301 и 302 браузер превращает POST в GET, после 307 и 308 — нет.
- **HTTP/1.1 обрабатывает на соединении один запрос за раз, и браузер держит не больше шести соединений на хост.** HTTP/2 мультиплексирует все запросы в одном соединении, HTTP/3 делает то же поверх QUIC на UDP без блокировки начала очереди TCP.
- **Сжатие и согласование содержимого идут через заголовки:** клиент сообщает `Accept-Encoding` и `Accept`, сервер отвечает `Content-Encoding` и `Content-Type` и добавляет `Vary`.
::

## Как выглядит сообщение

Сквозной пример — API интернет-магазина чая: каталог `/products`, корзина `/cart`, оформление заказа `/orders`.

HTTP/1.1 — текстовый протокол. Запрос, который браузер отправляет по TCP-соединению:

```text
GET /products?category=oolong HTTP/1.1
Host: api.shop.example
Accept: application/json
Accept-Encoding: gzip, br
Cookie: session=abc123

```

Первая строка — **метод, путь и версия**. Дальше **заголовки** по одному на строку, потом пустая строка и **тело** (у GET его обычно нет). Ответ устроен так же, только первая строка — **версия, код статуса и текст**:

```text
HTTP/1.1 200 OK
Content-Type: application/json
Content-Encoding: br
Content-Length: 2143
Vary: Accept-Encoding

{"items":[...]}
```

В проверке запрос, набранный руками и отправленный в обычный TCP-сокет, получил от Node.js настоящий ответ `HTTP/1.1 404 Not Found`. Заголовок `Host` обязателен: на одном IP-адресе живут сотни сайтов, и сервер выбирает нужный по нему.

### Где кончается тело

TCP — поток байтов без границ ([Основы сетей](/content/network-api/networking-fundamentals)), поэтому HTTP сам сообщает длину тела:

- **`Content-Length: 2143`** — тело ровно столько байтов;
- **`Transfer-Encoding: chunked`** — длина заранее неизвестна, тело идёт кусками, у каждого своя длина, нулевой кусок — конец. Так сервер начинает отдавать HTML или поток данных, пока остальное ещё готовится. В проверке ответ, который сервер писал в два приёма, пришёл с `chunked` и без `Content-Length`.

Имена заголовков не зависят от регистра: `headers.get('Content-Type')` и `headers.get('content-type')` дают одно и то же, а HTTP/2 вообще передаёт их строчными.

## Методы

Метод говорит серверу, что сделать с ресурсом. Важнее списка методов — их **гарантии**:

| Метод | Назначение | Безопасный | Идемпотентный |
| --- | --- | --- | --- |
| GET | получить ресурс | да | да |
| HEAD | то же без тела — только заголовки | да | да |
| POST | создать или выполнить действие | нет | нет |
| PUT | заменить ресурс целиком | нет | да |
| PATCH | изменить часть ресурса | нет | не обязательно |
| DELETE | удалить | нет | да |
| OPTIONS | узнать возможности, preflight CORS | да | да |

- **Безопасный** метод не меняет состояние на сервере. Поэтому браузер, поисковый робот и prefetch могут вызывать GET когда угодно. Ссылка «Удалить» на GET — баг: её «нажмёт» любой робот.
- **Идемпотентный** метод даёт тот же результат при повторе: `DELETE /cart/items/7` дважды — товар удалён один раз. Поэтому идемпотентные запросы можно повторять после сетевой ошибки, а POST «оформить заказ» — нет: повтор создаст второй заказ. Как сделать POST безопасным для повтора — ключом идемпотентности ([Паттерны API](/content/network-api/api-patterns)).

GET от POST отличается не «тем, что параметры в URL», а смыслом: GET читает и кешируется, POST меняет и не кешируется. Данные GET видны в адресе, истории и логах серверов, поэтому секреты в нём не передают. HEAD в проверке вернул тот же `Content-Length`, что и GET, но с пустым телом — так узнают размер файла, не скачивая его.

Как методы и статусы складываются в дизайн API — в [REST](/content/network-api/rest).

## Коды ответа

Первая цифра — класс результата:

| Класс | Смысл | Частые коды |
| --- | --- | --- |
| 1xx | промежуточный ответ | 101 Switching Protocols — переход на WebSocket, 103 Early Hints |
| 2xx | успех | 200 OK, 201 Created, 204 No Content |
| 3xx | перенаправление или «используй кеш» | 301, 302, 303, 307, 308, 304 Not Modified |
| 4xx | ошибка клиента | 400, 401, 403, 404, 409, 422, 429 Too Many Requests |
| 5xx | ошибка сервера | 500, 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout |

Мониторинг, кеши, повторные попытки и `fetch` полагаются на класс: `response.ok` — это просто «статус от 200 до 299». API, который отдаёт `200` с `{ "error": "..." }` в теле, ломает всё это сразу. 401 против 403 — в [Аутентификации](/content/network-api/auth), 304 и кеш — в [Кешировании](/content/network-api/caching).

### Редиректы и смена метода

Перенаправления различаются двумя свойствами: постоянное оно или временное и сохраняет ли метод.

| Код | Постоянный | Метод после POST |
| --- | --- | --- |
| 301 Moved Permanently | да | браузер меняет на GET |
| 302 Found | нет | браузер меняет на GET |
| 303 See Other | нет | всегда GET — так задумано |
| 307 Temporary Redirect | нет | сохраняется вместе с телом |
| 308 Permanent Redirect | да | сохраняется вместе с телом |

Смена POST на GET после 301 и 302 — историческое поведение браузеров, которое спецификация потом узаконила. В проверке в Chromium POST с телом `qty=2` после 301, 302 и 303 дошёл до цели как GET без тела, а после 307 и 308 — как POST с телом. Отсюда правило: API, который переехал, перенаправляют кодом 308, а не 301, иначе POST-запросы молча превратятся в GET.

303 используют намеренно в шаблоне **Post/Redirect/Get**: после отправки формы сервер отвечает 303 на страницу результата, и обновление страницы не отправит форму второй раз.

Постоянные редиректы браузер кеширует: после 301 он может больше не спрашивать старый адрес, поэтому ошибочный 301 трудно отменить.

## Заголовки и согласование

Заголовки несут всё, кроме самих данных. Основные группы:

- **о содержимом** — `Content-Type`, `Content-Length`, `Content-Encoding`, `Content-Language`;
- **о клиенте и его желаниях** — `Accept`, `Accept-Encoding`, `Accept-Language`, `User-Agent`;
- **кеш** — `Cache-Control`, `ETag`, `If-None-Match`, `Vary` ([Кеширование](/content/network-api/caching));
- **куки и авторизация** — `Cookie`, `Set-Cookie`, `Authorization` ([Аутентификация](/content/network-api/auth));
- **CORS** — `Origin`, `Access-Control-*` ([CORS](/content/network-api/cors));
- **безопасность** — `Content-Security-Policy`, `Strict-Transport-Security` ([CSP и заголовки](/content/security-perfomance/csp-and-security-headers)).

**Согласование содержимого**: клиент перечисляет, что умеет, сервер выбирает. По `Accept` один адрес может отдать HTML или JSON — в проверке так и вышло. Если ответ зависит от заголовка запроса, сервер обязан указать его в **`Vary`**, иначе кеш или CDN отдаст другому клиенту чужой вариант.

### Сжатие

Текст — HTML, CSS, JS, JSON — сжимается в разы. Клиент сообщает `Accept-Encoding: gzip, br, zstd`, сервер сжимает и ставит `Content-Encoding`. Браузер и `fetch` распаковывают прозрачно: код получает уже исходные данные. В проверке каталог из 300 товаров в JSON занимал около 18 КБ, в gzip — около 2 КБ, а brotli — меньше 1 КБ.

Картинки, видео и шрифты WOFF2 уже сжаты, повторное сжатие их только замедляет. Как настраивают сжатие при сборке и на CDN — в [Оптимизации сборки](/content/advanced-tooling/optimization).

## Версии HTTP

Смысл сообщений — методы, заголовки, статусы — во всех версиях одинаков. Меняется способ передачи.

### HTTP/1.1

По одному TCP-соединению за раз идёт один запрос: следующий ждёт, пока придёт ответ на предыдущий. Соединение переиспользуется (keep-alive), но параллельности на нём нет. Поэтому браузеры открывают **до шести соединений на хост**. В проверке Chromium отправил двенадцать запросов к медленному серверу по HTTP/1.1, и сервер ни разу не видел больше шести одновременно — запросы шли двумя волнами.

Обходные приёмы эпохи HTTP/1.1 — склейка файлов в бандлы, спрайты, раздача с нескольких поддоменов (domain sharding) — объясняются именно этим ограничением.

### HTTP/2

HTTP/2 — бинарный протокол. Сообщения режутся на **кадры**, а кадры разных запросов перемешиваются в одном соединении — это **мультиплексирование**. Заголовки сжимаются (HPACK), и повторяющиеся куки не передаются каждый раз целиком. В проверке те же двенадцать запросов по HTTP/2 сервер обрабатывал одновременно, а `nextHopProtocol` в Resource Timing показал `h2`. Браузеры поддерживают HTTP/2 только поверх TLS.

С HTTP/2 domain sharding вредит: каждый поддомен — новое соединение, рукопожатие и потеря приоритетов. А блокировка осталась на уровне ниже: HTTP/2 работает поверх TCP, и потеря одного пакета задерживает все потоки соединения.

### HTTP/3

HTTP/3 переехал на **QUIC** — транспорт поверх UDP, в который встроен TLS 1.3:

- **нет блокировки начала очереди** — потоки независимы, потеря пакета задерживает только свой поток;
- **быстрее установка** — транспорт и шифрование договариваются за один круг, а при повторном соединении данные можно отправить сразу (0-RTT);
- **переживает смену сети** — соединение определяется идентификатором, а не адресом, поэтому переход с Wi-Fi на мобильную сеть не рвёт загрузку.

Браузер узнаёт о поддержке HTTP/3 из заголовка `Alt-Svc` или DNS-записи `HTTPS` и при следующих запросах переходит на него. Выигрыш заметнее всего в мобильных сетях с потерями.

## Красные флаги в ответе

- **«GET отличается от POST тем, что параметры в URL».** Главное — смысл: GET безопасен и кешируется, POST меняет состояние и не повторяется автоматически.
- **«PUT и POST — одно и то же, просто договорённость».** PUT идемпотентен, его можно повторить после сетевой ошибки; POST — нет.
- **«301 и 308 — одно и то же».** После 301 браузер превращает POST в GET и теряет тело, 308 сохраняет метод.
- **«Отдадим 200 и ошибку в теле — фронтенд разберётся».** Кеши, мониторинг, `response.ok` и повторы ориентируются на статус.
- **«HTTP/2 быстрее, потому что бинарный».** Главное — мультиплексирование и сжатие заголовков; от потерь TCP он не спасает, это делает HTTP/3.
- **«Для HTTP/2 по-прежнему нужно раздавать файлы с разных поддоменов».** Это приём HTTP/1.1; с HTTP/2 он добавляет соединений и вредит.

## Как спрашивают на собеседовании

::question
Чем GET отличается от POST?

#answer
GET — безопасный и идемпотентный метод для чтения: он не меняет состояние сервера, его можно повторять, кешировать и вызывать заранее. POST создаёт или выполняет действие: он не безопасен и не идемпотентен, поэтому браузер и прокси не повторяют его сами, а ответ по умолчанию не кешируется. Параметры GET идут в URL, данные POST — в теле.

#more
Из-за URL параметры GET видны в истории, логах и заголовке Referer — секреты в нём не передают. Длина URL на практике ограничена серверами и прокси. Ссылки и prefetch вызывают GET без спроса, поэтому действия вроде удаления на GET — баг. Безопасный повтор POST делают ключом идемпотентности.
::

::question
Что такое идемпотентность и какие методы идемпотентны?

#answer
Идемпотентный запрос при повторе даёт тот же результат на сервере, что и при одном вызове. Идемпотентны GET, HEAD, OPTIONS, PUT и DELETE. POST — нет: повтор «оформить заказ» создаст второй заказ. PATCH может быть и тем и другим в зависимости от операции.

#more
Идемпотентность важна для повторов: после обрыва соединения клиент не знает, дошёл ли запрос, и повторять можно только идемпотентное. Идемпотентность — про состояние сервера, а не про ответ: второй `DELETE` может вернуть 404, но ресурс удалён один раз. Для POST её добавляют заголовком `Idempotency-Key`, по которому сервер узнаёт повтор.
::

::question
Чем отличаются коды 301, 302, 303, 307 и 308?

#answer
301 и 308 — постоянные перенаправления, 302, 303 и 307 — временные. После 301 и 302 браузер превращает POST в GET и теряет тело, после 303 всегда делает GET, а 307 и 308 сохраняют метод и тело. Поэтому переехавший API перенаправляют 308, а после отправки формы отвечают 303.

#more
В проверке в Chromium POST с телом после 301, 302 и 303 пришёл на цель как GET без тела, после 307 и 308 — как POST с телом. Постоянные редиректы браузер кеширует, и ошибочный 301 потом трудно отменить. Шаблон Post/Redirect/Get через 303 защищает от повторной отправки формы при обновлении страницы.
::

::question
Чем HTTP/2 отличается от HTTP/1.1, а HTTP/3 — от HTTP/2?

#answer
HTTP/1.1 обрабатывает на соединении один запрос за раз, поэтому браузер держит до шести соединений на хост. HTTP/2 бинарный, режет сообщения на кадры и мультиплексирует все запросы в одном соединении, сжимает заголовки. HTTP/3 работает поверх QUIC на UDP: потоки независимы, и потеря пакета не задерживает остальные, соединение устанавливается быстрее и переживает смену сети.

#more
В проверке двенадцать запросов по HTTP/1.1 шли двумя волнами по шесть, а по HTTP/2 — все сразу. Браузеры поддерживают HTTP/2 только поверх TLS. Приёмы эпохи HTTP/1.1 — domain sharding, агрессивная склейка всего в один файл — с HTTP/2 теряют смысл или вредят. Server Push из HTTP/2 Chrome и Firefox убрали, его место заняли `103 Early Hints` и `preload`.
::

::question
Что такое `Vary` и зачем он нужен?

#answer
`Vary` перечисляет заголовки запроса, от которых зависит ответ: `Vary: Accept-Encoding` — разные варианты для разного сжатия, `Vary: Accept` — HTML или JSON. Кеши и CDN используют эти заголовки как часть ключа. Без `Vary` кеш отдаст сжатый brotli ответ клиенту, который его не понимает, или JSON вместо HTML.

#more
`Vary: Origin` нужен, когда `Access-Control-Allow-Origin` зависит от origin запроса, — иначе CDN закеширует разрешение для одного сайта и отдаст его другому. `Vary: Cookie` фактически отключает общий кеш, потому что куки у всех разные. Чем больше заголовков в `Vary`, тем меньше попаданий в кеш.
::

::question
Как сервер передаёт ответ, длина которого заранее неизвестна?

#answer
В HTTP/1.1 — кусками: заголовок `Transfer-Encoding: chunked`, у каждого куска своя длина, нулевой кусок означает конец. В HTTP/2 и HTTP/3 кадры несут данные потока, и отдельный механизм не нужен. Так сервер начинает отдавать HTML до того, как страница готова целиком, и так работают потоковые ответы.

#more
Потоковая передача позволяет браузеру начать разбор `head` и загрузку стилей, пока сервер ещё ходит в базу, — это основа потокового серверного рендеринга. В JavaScript такой ответ читают по частям через `response.body.getReader()`. Если же известен `Content-Length`, клиент может показать прогресс загрузки.
::

## Практика

::practice{title="Данные заказа потерялись после переезда API"}
API переехал с `/api/v1/orders` на `/api/v2/orders`. Чтобы не ломать старые клиенты, на старом адресе настроили редирект 301. После этого старые клиенты при оформлении заказа получают список заказов вместо создания нового. Почему?

#solution
После 301 (и 302) браузер повторяет POST как GET и отбрасывает тело. Запрос `POST /api/v1/orders` с данными заказа превращается в `GET /api/v2/orders` — получение списка. В проверке в Chromium POST после 301 пришёл на цель как GET без тела.

Для перенаправления, которое должно сохранить метод и тело, есть 308 (постоянное) и 307 (временное):

```js
app.all('/api/v1/*', (req, res) => {
  res.redirect(308, req.originalUrl.replace('/api/v1/', '/api/v2/'));
});
```

С 308 тот же POST с телом дошёл до цели как POST. Но лучше, если клиенты сразу ходят на новый адрес: каждый редирект — лишний круг до сервера.
::

::practice{title="Двенадцать превью грузятся волнами"}
Каталог показывает 12 превью товаров, каждое генерируется на сервере около 300 мс. В водопаде DevTools видно, что первые шесть идут одновременно, а остальные ждут. Сервер отдаёт их по HTTP/1.1. Почему так и как исправить?

#solution
В HTTP/1.1 соединение обрабатывает один запрос за раз, а браузер открывает не больше шести соединений на хост. Седьмой запрос ждёт, пока освободится соединение. В проверке сервер при двенадцати запросах по HTTP/1.1 ни разу не видел больше шести одновременно, и загрузка заняла две волны.

Исправление — включить HTTP/2 на сервере или CDN (браузеры требуют для него TLS). Тогда все запросы идут одним соединением параллельно — в проверке все двенадцать обрабатывались одновременно:

```js
import http2 from 'node:http2';
const server = http2.createSecureServer({ key, cert, allowHTTP1: true }, app);
```

Обычно HTTP/2 включают не в Node.js, а на балансировщике или CDN перед ним. Раздавать картинки с нескольких поддоменов, как делали при HTTP/1.1, не нужно: с HTTP/2 это лишние соединения.
::

::practice{title="Мониторинг не видит ошибок"}
API оплаты при отказе банка отвечает так:

```js
res.status(200).json({ success: false, error: 'card_declined' });
```

Графики ошибок в мониторинге пустые, повторная попытка в клиентской библиотеке не срабатывает, а CDN однажды закешировал такой ответ. Что не так?

#solution
Статус — главный сигнал для всей инфраструктуры. Мониторинг считает 4xx и 5xx, библиотеки повторяют по статусу, `response.ok` проверяет диапазон 200–299, кеш хранит успешные ответы. Ответ 200 с ошибкой в теле для всех них — успех.

```js
res.status(402).json({ type: 'card_declined', title: 'Банк отклонил оплату' });
// или 422 для ошибки в данных, 409 для конфликта, 503 при недоступности банка
```

Клиент тогда различает ситуации без разбора тела:

```js
const res = await fetch('/api/payments', { method: 'POST', body });
if (!res.ok) {
  const problem = await res.json();
  showError(problem.title);
}
```

Формат тела ошибки стоит договорить один на весь API — например, Problem Details из [REST](/content/network-api/rest). Исключение из правила — GraphQL, где ошибки по соглашению приходят в теле со статусом 200.
