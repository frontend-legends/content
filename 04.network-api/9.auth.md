# Аутентификация и авторизация

На каждом втором собеседовании спрашивают: «Чем аутентификация отличается от авторизации?», «Где хранить токены?», «Как работает OAuth?». Тема на стыке фронтенда и бэкенда, но от фронтенд-разработчика ожидают понимания полного цикла - от логина до refresh-токена. Здесь разберём все ключевые механизмы: cookies, sessions, JWT, OAuth 2.0 и стратегии хранения токенов.

---

## Аутентификация vs Авторизация

|                         | Аутентификация (Authentication)                      | Авторизация (Authorization)                   |
| ----------------------- | ---------------------------------------------------- | --------------------------------------------- |
| **Вопрос**              | «Кто ты?»                                            | «Что тебе разрешено?»                         |
| **Процесс**             | Проверка личности (логин + пароль, отпечаток, OAuth) | Проверка прав доступа (роли, permissions)     |
| **Когда**               | Первый шаг - установить личность                     | Второй шаг - после аутентификации             |
| **Пример**              | Ввод логина/пароля на сайте                          | Доступ к admin-панели только для роли `admin` |
| **HTTP-код при ошибке** | 401 Unauthorized                                     | 403 Forbidden                                 |

<span class="text-gray">Запомни мнемонику: **authn** (authentication) = кто ты, **authz** (authorization) = что можешь.</span>

> Название HTTP-кода 401 «Unauthorized» - историческая ошибка. По смыслу это «Unauthenticated» - ты не подтвердил личность. 403 - вот настоящий «unauthorized» (нет прав).

## Cookies

<b class="text-on-semi-light">Основной транспорт для аутентификации в вебе</b>

<span class="text-gray">Cookie - пара «ключ=значение», которую сервер отправляет через заголовок `Set-Cookie`, а браузер автоматически прикрепляет к каждому последующему запросу. Для аутентификации в cookie обычно хранят session ID или токен.</span>

### Атрибуты Cookie

| Атрибут    | Значение               | Зачем                                                                |
| ---------- | ---------------------- | -------------------------------------------------------------------- |
| `HttpOnly` | `true / false`         | Запрещает доступ из JavaScript (`document.cookie`). Защита от XSS    |
| `Secure`   | `true / false`         | Cookie отправляется только по HTTPS                                  |
| `SameSite` | `Strict / Lax / None`  | Защита от CSRF. Контролирует отправку cookie при cross-site запросах |
| `Path`     | `/api`                 | Cookie отправляется только для запросов по указанному пути           |
| `Domain`   | `.example.com`         | Cookie доступен для домена и поддоменов                              |
| `Max-Age`  | `3600` (секунды)       | Время жизни cookie. `0` - удалить немедленно                         |
| `Expires`  | `Thu, 01 Dec 2025 ...` | Абсолютная дата истечения (legacy, предпочитай `Max-Age`)            |

### SameSite подробнее

| Значение        | Поведение                                                                                 | CSRF-защита                |
| --------------- | ----------------------------------------------------------------------------------------- | -------------------------- |
| `Strict`        | Cookie не отправляется при **любых** cross-site запросах (даже при переходе по ссылке)    | Максимальная               |
| `Lax` (default) | Cookie отправляется при **навигации** (ссылки, GET), но не при POST/fetch с других сайтов | Хорошая                    |
| `None`          | Cookie отправляется всегда. **Требует** `Secure`                                          | Никакая (нужен CSRF-токен) |

```text
Set-Cookie: session_id=abc123; HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=86400
```

<span class="text-gray">`SameSite=Lax` - разумный default для большинства приложений. `Strict` может ломать UX (пользователь кликает ссылку на твой сайт из email - cookie не отправится, и он окажется «незалогинен»).</span>

## Sessions (серверные сессии)

<b class="text-on-semi-light">Классический подход к аутентификации</b>

<span class="text-gray">Сервер создаёт сессию (объект с данными пользователя) и хранит её у себя (в памяти, Redis, БД). Клиенту отправляется **session ID** в cookie. При каждом запросе сервер ищет сессию по ID.</span>

```text
1. POST /login { email, password }
2. Сервер проверяет credentials
3. Создаёт сессию: { userId: 42, role: "admin" }
4. Отправляет: Set-Cookie: sid=xyz789; HttpOnly; Secure
5. Браузер автоматически прикрепляет cookie к каждому запросу
6. Сервер читает sid -> находит сессию -> знает, кто пользователь
```

| Плюсы                                                                | Минусы                                                       |
| -------------------------------------------------------------------- | ------------------------------------------------------------ |
| Просто отозвать (удалил сессию на сервере - пользователь разлогинен) | Состояние на сервере (нужно хранилище)                       |
| Session ID короткий и непрозрачный                                   | Сложнее масштабировать (sticky sessions или общее хранилище) |
| Работает из коробки с cookies                                        | Не подходит для mobile/API без cookies                       |

## JWT (JSON Web Token)

<b class="text-on-semi-light">Stateless-токен с подписью</b>

<span class="text-gray">JWT - самодостаточный токен, содержащий данные (claims) и подпись. Серверу не нужно хранить сессию - достаточно проверить подпись. Структура: `header.payload.signature`, каждая часть закодирована в Base64URL.</span>

### Структура JWT

```js
// Header
{ "alg": "HS256", "typ": "JWT" }

// Payload (claims)
{
  "sub": "user_42",         // subject - кто
  "role": "admin",          // кастомные данные
  "iat": 1700000000,        // issued at - когда выдан
  "exp": 1700003600         // expires - когда истекает
}

// Signature
HMAC-SHA256(
  base64url(header) + "." + base64url(payload),
  secret
)
```

```text
Результат:
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyXzQyIiwicm9sZSI6ImFkbWluIn0.SIGNATURE
```

### Плюсы и минусы JWT

| Плюсы                                                   | Минусы                                                  |
| ------------------------------------------------------- | ------------------------------------------------------- |
| Stateless - сервер не хранит сессии                     | Нельзя отозвать до истечения `exp` (без blocklist)      |
| Масштабируется - любой сервер с ключом может проверить  | Размер: JWT >> session ID (каждый запрос несёт payload) |
| Содержит данные - не нужен запрос в БД на каждый запрос | Payload виден всем (Base64 - не шифрование!)            |
| Работает без cookies (через `Authorization` header)     | Сложнее безопасно хранить на клиенте                    |

<b class="text-on-semi-light">Подводные камни JWT</b>

<span class="text-gray">**JWT не шифрует данные** - payload легко декодируется. Никогда не клади туда пароли, номера карт или чувствительные данные. Используй JWE, если нужно шифрование.</span>

<span class="text-gray">**Размер** - JWT с десятком claims легко вырастает до 1+ КБ. Этот килобайт летит с **каждым** запросом. Для cookies есть лимит ~4 КБ.</span>

<span class="text-gray">**Отзыв** - чтобы «разлогинить» пользователя до истечения токена, нужен blocklist на сервере. А blocklist - это уже server-side state, и ты теряешь главное преимущество JWT.</span>

> Подробнее о структуре JWT и алгоритмах подписи - [Шифрование](/content/computer-science/encryption).

## OAuth 2.0

<b class="text-on-semi-light">Делегированная авторизация</b>

<span class="text-gray">OAuth 2.0 - протокол, позволяющий приложению получить ограниченный доступ к ресурсам пользователя **без** передачи его пароля. Когда ты нажимаешь «Войти через Google» - это OAuth.</span>

### Роли в OAuth

| Роль                     | Описание                               | Пример         |
| ------------------------ | -------------------------------------- | -------------- |
| **Resource Owner**       | Пользователь, чьи данные запрашиваются | Ты             |
| **Client**               | Приложение, запрашивающее доступ       | Твоё SPA       |
| **Authorization Server** | Сервер, выдающий токены                | Google, GitHub |
| **Resource Server**      | Сервер с данными пользователя          | Google API     |

### Authorization Code + PKCE (для SPA)

<span class="text-gray">Рекомендуемый flow для SPA и мобильных приложений. PKCE (Proof Key for Code Exchange) защищает от перехвата authorization code - критично для публичных клиентов, где нельзя хранить client_secret.</span>

```text
1. Пользователь нажимает «Войти через Google»

2. Приложение генерирует:
   - code_verifier (случайная строка)
   - code_challenge = SHA256(code_verifier), закодированный в Base64URL

3. Редирект на Authorization Server:
   GET https://accounts.google.com/authorize?
     response_type=code&
     client_id=YOUR_CLIENT_ID&
     redirect_uri=https://app.com/callback&
     scope=openid email profile&
     code_challenge=CHALLENGE&
     code_challenge_method=S256

4. Пользователь логинится в Google, даёт согласие

5. Google редиректит обратно:
   https://app.com/callback?code=AUTH_CODE

6. Приложение обменивает code на токены:
   POST https://oauth2.googleapis.com/token
   { code, code_verifier, client_id, redirect_uri, grant_type }

7. Получает: { access_token, refresh_token, id_token }
```

<span class="text-gray">**Зачем PKCE?** Без него злоумышленник мог перехватить `AUTH_CODE` (через redirect URI или историю браузера) и обменять на токен. С PKCE нужен ещё `code_verifier`, который знает только оригинальное приложение.</span>

## Refresh Tokens

<b class="text-on-semi-light">Обновление access token без повторного логина</b>

<span class="text-gray">Access token живёт недолго (15 мин - 1 час). Когда он истекает, приложение использует refresh token, чтобы получить новый access token без участия пользователя.</span>

```text
Access Token:  короткоживущий (15 мин), используется для API-запросов
Refresh Token: долгоживущий (дни/недели), используется ТОЛЬКО для получения нового access token
```

### Стратегии обновления

<b class="text-on-semi-light">Silent Refresh</b>

<span class="text-gray">Приложение отправляет refresh token на `/token/refresh` и получает новую пару токенов. Происходит в фоне, пользователь ничего не замечает.</span>

```js
async function fetchWithAuth(url, options = {}) {
  let res = await fetch(url, {
    ...options,
    headers: {
      ...options.headers,
      Authorization: `Bearer ${accessToken}`,
    },
  });

  if (res.status === 401) {
    // Access token истёк - обновляем
    const newTokens = await refreshTokens();
    accessToken = newTokens.access_token;

    // Повторяем запрос с новым токеном
    res = await fetch(url, {
      ...options,
      headers: {
        ...options.headers,
        Authorization: `Bearer ${accessToken}`,
      },
    });
  }

  return res;
}
```

<b class="text-on-semi-light">Rotation (ротация refresh-токенов)</b>

<span class="text-gray">При каждом обновлении сервер выдаёт **новый** refresh token и инвалидирует старый. Если злоумышленник украл refresh token и использовал его - сервер обнаружит повторное использование инвалидированного токена и отзовёт всю цепочку.</span>

```text
Запрос:   POST /token/refresh  { refresh_token: "RT_1" }
Ответ:    { access_token: "AT_new", refresh_token: "RT_2" }
          RT_1 больше не действует

Если кто-то попробует использовать RT_1 снова:
          -> Сервер обнаруживает reuse -> отзывает все токены семейства
          -> Пользователь перелогинивается
```

## Где хранить токены

Один из самых обсуждаемых вопросов на собеседованиях. Идеального решения нет - каждый вариант имеет trade-offs.

| Хранилище                  | XSS                           | CSRF                                    | Persistence                      | Авто-отправка          |
| -------------------------- | ----------------------------- | --------------------------------------- | -------------------------------- | ---------------------- |
| **httpOnly Cookie**        | Защищён (JS не имеет доступа) | Уязвим (нужен SameSite или CSRF-токен)  | До `Max-Age` / `Expires`         | Да (автоматически)     |
| **localStorage**           | Уязвим (JS имеет доступ)      | Защищён (не отправляется автоматически) | Постоянно                        | Нет (вручную в header) |
| **sessionStorage**         | Уязвим (JS имеет доступ)      | Защищён                                 | До закрытия вкладки              | Нет (вручную в header) |
| **In-memory (переменная)** | Защищён (нет в storage)       | Защищён                                 | Теряется при обновлении страницы | Нет (вручную в header) |

### Рекомендации

<b class="text-on-semi-light">Лучший вариант: httpOnly Cookie + SameSite</b>

<span class="text-gray">Access token (или session ID) в `httpOnly; Secure; SameSite=Lax` cookie. JavaScript не имеет доступа к токену - XSS-атака не может его украсть. `SameSite` защищает от CSRF. Браузер отправляет cookie автоматически - не нужно вручную прикреплять заголовок.</span>

<b class="text-on-semi-light">Если httpOnly cookie невозможен (сторонний API, CORS)</b>

<span class="text-gray">Храни токен в памяти (переменная или closure). При обновлении страницы - делай silent refresh через httpOnly refresh token cookie. Это «BFF-паттерн» (Backend for Frontend): твой бэкенд проксирует запросы и управляет токенами.</span>

> localStorage - удобно, но любая XSS-уязвимость даёт атакующему полный доступ к токену. Для серьёзных приложений это неприемлемый риск.

```text
Архитектура BFF:

SPA ─── cookie (httpOnly) ───> BFF (твой бэкенд)
                                 │
                                 ├── хранит access_token и refresh_token
                                 └── проксирует запросы к API с Authorization header
```

<span class="text-gray">BFF-паттерн: фронтенд вообще не видит токены. Cookie содержит session ID, а бэкенд подставляет access token при проксировании запросов к API. Это самый безопасный подход для SPA.</span>

## Что спрашивают на собеседованиях

> - «Чем аутентификация отличается от авторизации?» - authn = кто ты, authz = что можешь.
> - «Где хранить токены?» - httpOnly cookie + SameSite. Объясни trade-offs.
> - «JWT vs Sessions?» - JWT stateless (масштабируется), но сложнее отзывать. Sessions stateful, но легко инвалидировать.
> - «Как работает OAuth?» - опиши Authorization Code + PKCE flow.
> - «Что такое CSRF и как защититься?» - SameSite cookie, CSRF-токены. Подробнее в [CORS](/content/network-api/cors).
> - «Что будет, если XSS на сайте с localStorage-токеном?» - атакующий получит полный доступ к токену и аккаунту.
