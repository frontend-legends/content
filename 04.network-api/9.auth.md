# Аутентификация в HTTP

HTTP не помнит пользователя между запросами: каждый запрос должен сам сказать, от кого он. Для этого есть два канала — куки, которые браузер прикладывает сам, и заголовок `Authorization`, который ставит код, — и протоколы входа вроде OAuth, которые выдают учётные данные. Спрашивают, чем 401 отличается от 403, какие атрибуты бывают у кук и как устроен вход через OAuth. Глубже — почему кука не удаляется при выходе, когда кука уходит на другой сайт и зачем в OAuth параметр `state`.

::tldr
- **Учётные данные едут в каждом запросе:** кукой, которую браузер прикладывает автоматически, или заголовком `Authorization: Bearer <токен>`, который ставит код. 401 — «не знаю, кто ты», 403 — «знаю, но нельзя».
- **Атрибуты куки задают, куда и когда она уходит:** `Domain` и `Path` — адреса, `Secure` — только HTTPS, `HttpOnly` — недоступна скрипту, `SameSite` — межсайтовые запросы, `Max-Age` — срок. Без `Domain` кука живёт только на своём хосте.
- **Удалить куку можно только с теми же `Domain` и `Path`, с какими её ставили.** Иначе браузер создаёт рядом другую, а сессия остаётся.
- **Без `SameSite` браузер считает куку `Lax`:** она не уходит в межсайтовые `fetch` и картинки, но уходит при переходе по ссылке на сайт.
- **OAuth 2.0 Authorization Code — обмен через браузер редиректами:** сервер авторизации возвращает одноразовый код на зарегистрированный `redirect_uri`, клиент проверяет `state` и меняет код на токены. OpenID Connect добавляет `id_token` — подписанный JWT о пользователе.
::

## Кто ты и что тебе можно

Сквозной пример — интернет-магазин на `shop.example`, API на `api.shop.example`, вход через внешний сервис авторизации.

HTTP не хранит состояние: сервер не знает, что два запроса пришли от одного человека. Поэтому каждый запрос несёт **учётные данные** — идентификатор сессии или токен. Как сервер хранит сессии, чем они отличаются от JWT, где хранить токен и как обновлять его — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens). Здесь — как это выглядит на уровне HTTP.

Два кода ответа, которые путают:

- **401 Unauthorized** — учётных данных нет или они неверны: «я не знаю, кто ты». Ответ обязан содержать `WWW-Authenticate` с подсказкой, как аутентифицироваться;
- **403 Forbidden** — пользователь известен, но прав не хватает: «я знаю, кто ты, и тебе нельзя». Повтор с теми же учётными данными не поможет.

В проверке ресурс без токена ответил `401` с `WWW-Authenticate: Bearer error="invalid_token"`, а с токеном без нужного права — `403` с `error="insufficient_scope"`. На фронтенде это разные реакции: 401 — обновить токен или отправить на вход, 403 — показать «нет доступа».

## Куки

Сервер ставит куку заголовком ответа, браузер сохраняет её и прикладывает к подходящим запросам:

```text
HTTP/1.1 200 OK
Set-Cookie: session=s1; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=2592000

GET /catalog HTTP/1.1
Cookie: session=s1; theme=dark
```

Атрибуты — правила хранения и отправки:

| Атрибут | Что делает |
| --- | --- |
| `Domain` | на какие хосты отправлять; без него — только на хост, который поставил |
| `Path` | для каких путей отправлять |
| `Max-Age`, `Expires` | срок; без них кука живёт до закрытия браузера |
| `Secure` | только по HTTPS; по HTTP её не поставить |
| `HttpOnly` | не видна в `document.cookie` |
| `SameSite` | отправлять ли в запросах с других сайтов: `Strict`, `Lax`, `None` |
| `Partitioned` | отдельная копия для каждого сайта, внутри которого открыт сервис |

### Domain и Path

Кука **без `Domain`** — host-only: уходит только на тот хост, который её поставил. Кука с `Domain=shop.example` уходит на `shop.example` и все поддомены. В проверке кука без `Domain`, поставленная на `shop.test`, не ушла на `api.shop.test`, а с `Domain=shop.test` — ушла. Поставить куку чужому домену нельзя: `api.shop.test` не смог поставить куку с `Domain=other.test`.

Отсюда правило: сессию держат без `Domain` — чем меньше хостов её получают, тем меньше риск, что какой-нибудь поддомен с уязвимостью её прочитает. Если API на поддомене, удобнее поставить сессию на тот хост, куда идут запросы.

`Path=/admin` ограничивает отправку путями, начинающимися с `/admin`. Это не защита: страница того же origin может открыть `/admin` во фрейме и прочитать куку — в проверке так и вышло. `Path` — способ не отправлять лишнее.

**Порт кука не учитывает**: `localhost:3000` и `localhost:5173` делят одни куки, хотя это разные origin. В проверке кука, поставленная на одном порту, ушла на сервер на другом.

### Удаление куки

Удалить куку — значит поставить её заново с истёкшим сроком: `Max-Age=0`. Ключ куки — имя, `Domain` и `Path`, поэтому удаление должно повторить их в точности. В проверке кука с `Path=/shop` после `cart=; Max-Age=0` без `Path` осталась на месте, и удалилась только командой с тем же `Path=/shop`. Это частая причина «выход не работает»: сессию ставили с одними атрибутами, а удаляют с другими.

Надёжный способ выйти — заголовок ответа `Clear-Site-Data: "cookies"`: браузер удаляет все куки этого сайта. В проверке после такого ответа на `localhost` не осталось ни одной куки. И главное — сессию нужно завершить на сервере, а не только стереть куку.

### Secure, HttpOnly и префиксы

- **`Secure`** — кука уходит только по HTTPS, а по HTTP её нельзя даже поставить: в проверке `Secure` с `http://shop.test` не сохранилась. Исключение — `localhost`, он считается безопасным контекстом.
- **`HttpOnly`** — скрипт не видит куку. В проверке `document.cookie` показал только `theme`, а `session` пришла на сервер. Это защищает сессию от кражи через XSS, но не от запросов, которые XSS-скрипт сделает от имени пользователя.
- **Префиксы имени** — браузер проверяет атрибуты сам. `__Secure-` требует `Secure`, `__Host-` — ещё и `Path=/` без `Domain`. Кука `__Host-sid` гарантированно поставлена этим хостом по HTTPS, и поддомен её не подменит. В проверке `__Host-` с `Domain` и без `Secure` отклонились.

Размер куки ограничен примерно 4 КБ вместе с именем: в проверке кука на 4,2 КБ была отброшена. И все куки уходят с каждым запросом к хосту, включая картинки и скрипты, поэтому большие куки — это лишние байты в каждом запросе.

### SameSite

`SameSite` решает, уходит ли кука в запрос, который инициировала страница **другого сайта** (сайт — схема и регистрируемый домен, [Что такое веб](/content/web/what-is-web)):

- **`Strict`** — только в запросы со своего сайта. Даже переход по ссылке с другого сайта придёт без куки — в проверке так и вышло, — и пользователь увидит себя разлогиненным;
- **`Lax`** — ещё и при переходе верхнего уровня методом GET: клик по ссылке, ввод адреса. Межсайтовые `fetch`, картинки, фреймы и POST-формы — без куки;
- **`None`** — всегда, но только вместе с `Secure`.

Без атрибута браузеры считают куку `Lax`. В проверке кука без `SameSite` не ушла в `fetch` со страницы `other.test`, а при переходе по ссылке с `other.test` на `shop.test` — ушла. Это главная защита от CSRF — как именно, в [CSRF](/content/security-perfomance/csrf).

Куки, поставленные внутри чужого сайта — виджет поддержки, встроенная оплата, — называются **сторонними**, и браузеры их ограничивают или блокируют. Для законных встроенных сервисов есть `Partitioned`: кука хранится отдельно для каждого сайта, в который встроен сервис, и не годится для слежки.

## Заголовок Authorization

Вторая схема — учётные данные в заголовке, который ставит код:

```text
Authorization: Bearer eyJhbGciOiJFUzI1NiJ9...
```

- **Bearer** — «предъявитель»: кто держит токен, тот и пользователь. Так передают токены доступа OAuth и JWT;
- **Basic** — `Basic base64(логин:пароль)`. Это кодирование, а не шифрование: строка декодируется обратно в пароль, поэтому Basic допустим только по HTTPS и для служебных доступов.

Отличие от кук — браузер не прикладывает заголовок сам. Это убирает CSRF (чужой сайт не может заставить браузер добавить токен), но требует хранить токен там, где его видит JavaScript, — и делает его доступным для XSS. Компромисс и рекомендации — в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens).

Учётные данные в самом адресе (`https://user:pass@api.example/`) `fetch` не принимает: в проверке такой запрос отклонился с `TypeError`.

## OAuth 2.0 и OpenID Connect

**OAuth 2.0** — протокол делегированного доступа: приложение получает токен на действия от имени пользователя, не видя его пароля. «Войти через Google» — это **OpenID Connect** (OIDC), надстройка над OAuth, которая добавляет `id_token` — подписанный JWT с данными о пользователе. OAuth отвечает «что приложению можно», OIDC — «кто пользователь».

Роли: **пользователь**, **клиент** (наш магазин), **сервер авторизации** (выдаёт токены), **сервер ресурсов** (API, которое принимает токены).

### Authorization Code по шагам

1. **Клиент отправляет браузер на сервер авторизации:**

   ```text
   GET https://auth.example/authorize?response_type=code
       &client_id=shop-web
       &redirect_uri=https://shop.example/callback
       &scope=openid email orders:read
       &state=Zx8…        ← случайная строка, клиент её запомнил
       &nonce=Qp3…        ← для проверки id_token
       &code_challenge=E9…&code_challenge_method=S256
   ```

2. **Пользователь входит и соглашается** на странице сервера авторизации — клиент пароль не видит.
3. **Сервер авторизации возвращает браузер** на зарегистрированный адрес с одноразовым кодом: `302 Location: https://shop.example/callback?code=…&state=Zx8…`.
4. **Клиент проверяет `state`** — совпадает ли с тем, что он запомнил.
5. **Клиент меняет код на токены** прямым запросом:

   ```text
   POST https://auth.example/token
   Content-Type: application/x-www-form-urlencoded

   grant_type=authorization_code&code=…&redirect_uri=https://shop.example/callback
   &client_id=shop-web&code_verifier=…
   ```

   Ответ: `access_token`, `token_type: Bearer`, `expires_in`, `id_token`, часто `refresh_token`, и `Cache-Control: no-store`.
6. **Клиент проверяет `id_token`**: подпись по ключам сервера авторизации, `iss` — тот ли сервер, `aud` — выдан ли он этому клиенту, `exp` и `nonce`.

В проверке на маленьком сервере авторизации этот путь прошёл целиком, а защитные шаги сработали так:

- **код одноразовый** — повторный обмен вернул `invalid_grant`;
- **`redirect_uri` сверяется точно** — запрос с чужим адресом получил 400 без редиректа. Иначе код ушёл бы на сайт атакующего;
- **`state` проверяет клиент** — колбэк с кодом от другого входа был отвергнут. Без этой проверки атакующий может подсунуть жертве свой код и залогинить её в свой аккаунт;
- **`code_verifier`** — без него перехваченный код не обменять; как устроен PKCE, разобрано в [Аутентификации и токенах](/content/security-perfomance/authentication-and-tokens);
- **`aud` в `id_token`** — токен, выданный другому приложению, проверку не прошёл.

Другие потоки: **Client Credentials** — сервер обращается к API от своего имени, без пользователя; **Device Code** — вход на телевизоре через код на телефоне. Устаревший Implicit, который возвращал токен прямо в адресе, для новых приложений не используют. Для SPA принятая схема — Authorization Code с PKCE, а ещё лучше — обмен кода на сервере (BFF), чтобы токены вообще не попадали в браузер. Готовые библиотеки и сервисы — в [Библиотеках аутентификации](/content/ecosystem-libs/auth-libraries).

## Красные флаги в ответе

- **«401 и 403 — одно и то же».** 401 — неизвестно, кто ты; 403 — известно, но нельзя.
- **«Для выхода удалю куку `Max-Age=0`».** Без тех же `Domain` и `Path` удалится не та кука, а сессия на сервере останется живой.
- **«`HttpOnly` защищает от XSS».** Она защищает куку от чтения; XSS-скрипт всё равно отправит запросы с ней.
- **«Basic-аутентификация шифрует пароль».** Это Base64; без HTTPS пароль виден.
- **«`state` в OAuth не обязателен, есть же PKCE».** `state` защищает клиента от подставленного входа, PKCE — от перехвата кода; это разные атаки.
- **«OAuth — протокол аутентификации».** OAuth — про доступ; кто пользователь, говорит OpenID Connect через `id_token`.

## Как спрашивают на собеседовании

::question
Чем 401 отличается от 403?

#answer
401 Unauthorized — запрос без учётных данных или с неверными: сервер не знает, кто это. Ответ содержит `WWW-Authenticate` с подсказкой, как аутентифицироваться. 403 Forbidden — пользователь известен, но прав нет; повтор с теми же данными не поможет.

#more
На клиенте реакции разные: 401 — обновить токен или отправить на вход, 403 — показать «нет доступа». OAuth-ресурсы уточняют причину в `WWW-Authenticate`: `error="invalid_token"` для 401 и `error="insufficient_scope"` для 403, как в проверке. Для чужого ресурса иногда отвечают 404, чтобы не раскрывать, что он существует.
::

::question
Какие атрибуты бывают у куки и зачем каждый?

#answer
`Domain` и `Path` — на какие хосты и пути отправлять; без `Domain` кука только для своего хоста. `Max-Age` или `Expires` — срок, без них кука живёт до закрытия браузера. `Secure` — только HTTPS. `HttpOnly` — недоступна скрипту. `SameSite` — отправлять ли в запросах с других сайтов. `Partitioned` — отдельная копия для каждого сайта, в который встроен сервис.

#more
Префиксы имени заставляют браузер проверить атрибуты: `__Host-` требует `Secure`, `Path=/` и запрещает `Domain` — такую куку не подменит поддомен. Кука ограничена примерно 4 КБ и уходит с каждым запросом к хосту, включая картинки. Порт куки не учитывают: `localhost:3000` и `localhost:5173` делят куки.
::

::question
Почему кука не удаляется при выходе из аккаунта?

#answer
Ключ куки — имя, `Domain` и `Path`. Удаление — это `Set-Cookie` с тем же ключом и `Max-Age=0`; если `Path` или `Domain` отличаются, браузер считает это другой кукой и старая остаётся. В проверке кука с `Path=/shop` пережила удаление без `Path`.

#more
Надёжные варианты — повторить атрибуты в точности или ответить `Clear-Site-Data: "cookies"`, которое стирает все куки сайта. Но удаление куки — только половина: сессию нужно завершить на сервере, иначе украденный идентификатор продолжит работать. `HttpOnly`-куку скрипт удалить не может вообще — только сервер.
::

::question
Когда кука уходит на другой сайт?

#answer
Решает `SameSite`. `Strict` — только в запросы, инициированные своим сайтом. `Lax`, режим по умолчанию, — ещё и при переходе по ссылке методом GET, но не в межсайтовые `fetch`, картинки, фреймы и POST-формы. `None` — всегда, но только с `Secure`.

#more
В проверке кука без атрибута не ушла в `fetch` с другого сайта, но ушла при переходе по ссылке. Сайт — схема и регистрируемый домен, поэтому `api.shop.example` и `shop.example` — один сайт, и `Lax` между ними работает. Сторонние куки внутри чужих сайтов браузеры ограничивают; встроенным сервисам оставлены `Partitioned`-куки.
::

::question
Как передавать токен: в куке или в заголовке `Authorization`?

#answer
Кука уходит автоматически, может быть `HttpOnly` и недоступной скрипту, но требует защиты от CSRF — `SameSite` и токенов. Заголовок `Authorization: Bearer` ставит код: CSRF не страшен, но токен хранится там, где его видит JavaScript, и уязвим для XSS. Для браузерных приложений обычно предпочитают `HttpOnly`-куку с `SameSite`.

#more
Схема Basic в `Authorization` — просто Base64 логина и пароля, без HTTPS это открытый текст. Межсайтовая отправка кук требует `credentials: 'include'` и CORS с точным origin, а заголовок `Authorization` вызывает preflight. Подробное сравнение и ротация токенов — в главе про безопасность.
::

::question
Как устроен вход через OAuth 2.0 Authorization Code?

#answer
Клиент отправляет браузер на `/authorize` с `client_id`, `redirect_uri`, `scope`, `state` и `code_challenge`. Пользователь входит у сервера авторизации, и тот возвращает браузер на зарегистрированный `redirect_uri` с одноразовым кодом и тем же `state`. Клиент проверяет `state` и обменивает код на токены POST-запросом к `/token` с `code_verifier`. С OpenID Connect приходит ещё `id_token`, который клиент проверяет по подписи, `iss`, `aud` и `nonce`.

#more
Каждый параметр закрывает свою атаку: точная проверка `redirect_uri` не даёт отправить код атакующему, одноразовый код — использовать его дважды, `state` — подставить чужой вход, PKCE — обменять перехваченный код, `aud` — принять токен чужого приложения. Все эти проверки в проверке сработали. Implicit flow устарел; для SPA — код с PKCE или обмен через BFF.
::

## Практика

::practice{title="Выход из аккаунта не работает"}
При входе сервер ставит сессию:

```text
Set-Cookie: session=abc; Domain=shop.example; Path=/; HttpOnly; Secure
```

Выход реализован так:

```js
app.post('/logout', (req, res) => {
  res.setHeader('Set-Cookie', 'session=; Max-Age=0');
  res.sendStatus(204);
});
```

После выхода пользователь по-прежнему залогинен. Почему и как исправить?

#solution
Удаление не повторяет атрибуты: без `Domain` браузер считает это host-only кукой `session` — другой, чем поставленная с `Domain=shop.example`. Старая кука остаётся. В проверке кука с одним `Path` пережила удаление с другим. И сессия на сервере не завершена.

```js
app.post('/logout', async (req, res) => {
  await sessions.destroy(req.cookies.session);                         // завершить на сервере
  res.setHeader('Set-Cookie', 'session=; Domain=shop.example; Path=/; Max-Age=0; HttpOnly; Secure');
  res.setHeader('Clear-Site-Data', '"cookies"');                       // на всякий случай — все куки сайта
  res.sendStatus(204);
});
```

`Clear-Site-Data` в проверке стёр все куки сайта. Лучше с самого начала ставить сессию без `Domain` и с префиксом `__Host-`: тогда атрибуты фиксированы, и удалить её правильно проще.
::

::practice{title="Кука не ставится"}
Сервер отвечает заголовками, но в DevTools кук нет. Почему не сохранилась каждая?

```text
Set-Cookie: a=1; Secure                        (страница по http://shop.test)
Set-Cookie: __Host-b=1; Secure; Path=/; Domain=shop.example
Set-Cookie: c=1; SameSite=None
Set-Cookie: d=<4200 символов>
Set-Cookie: e=1; Domain=other.example          (ответ от api.shop.example)
```

#solution
- `a` — `Secure` по HTTP не ставится, кроме `localhost`. В проверке такая кука не сохранилась.
- `__Host-b` — префикс `__Host-` запрещает `Domain`. В проверке отклонена.
- `c` — `SameSite=None` требует `Secure`; без него браузер отклоняет куку.
- `d` — больше 4 КБ; в проверке отброшена.
- `e` — хост может поставить куку только себе и своим родительским доменам, не чужому. В проверке `api.shop.test` не смог поставить куку для `other.test`.

Рабочие варианты:

```text
Set-Cookie: a=1; Secure                        (по HTTPS)
Set-Cookie: __Host-b=1; Secure; Path=/
Set-Cookie: c=1; SameSite=None; Secure
```

Большие данные кладут не в куку, а на сервер или в хранилище браузера. Причину отказа DevTools показывает на вкладке Network, в колонке Cookies ответа.
::

::practice{title="Колбэк OAuth без проверки state"}
Обработчик возврата с сервера авторизации:

```js
app.get('/callback', async (req, res) => {
  const tokens = await exchangeCode(req.query.code);
  req.session.user = await verifyIdToken(tokens.id_token);
  res.redirect('/');
});
```

Что может сделать атакующий и как исправить?

#solution
Обработчик принимает любой код. Атакующий начинает вход в своём браузере, останавливается на шаге с кодом и отправляет жертве ссылку `https://shop.example/callback?code=<его код>`. Жертва переходит — и оказывается залогинена в аккаунт атакующего: сохранённая карта, адреса и заказы попадут к нему. Это подставленный вход (login CSRF).

`state` связывает колбэк с входом, который начал этот браузер:

```js
app.get('/login', (req, res) => {
  const state = randomBytes(16).toString('base64url');
  res.cookie('oauth_state', state, { httpOnly: true, secure: true, sameSite: 'lax', maxAge: 600_000 });
  res.redirect(buildAuthorizeUrl({ state }));
});

app.get('/callback', async (req, res) => {
  const expected = req.cookies.oauth_state;
  res.clearCookie('oauth_state');
  if (!expected || req.query.state !== expected) return res.status(400).send('Вход не совпал');
  const tokens = await exchangeCode(req.query.code);
  req.session.user = await verifyIdToken(tokens.id_token);
  res.redirect('/');
});
```

`SameSite=Lax` нужен, чтобы кука пришла при возврате с другого сайта. В проверке колбэк с кодом от чужого входа был отвергнут. `nonce` в `id_token` и PKCE — дополнительные слои, но `state` они не заменяют.
::
