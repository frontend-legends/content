# Запросы из браузера

`fetch` — основной способ ходить в сеть из браузера: он отправляет запрос, возвращает промис ответа и отдаёт тело потоком. Простота обманчива: промис выполняется и на 404, тело запроса меняет заголовки, а повтор после ошибки может создать второй заказ. Спрашивают, когда `fetch` отклоняет промис, как отправить JSON и файлы и как повторять запросы. Глубже — почему прогресс загрузки показывает 600%, почему сервер не видит поля формы и как отправить аналитику, когда пользователь закрывает вкладку.

::tldr
- **`fetch` отклоняет промис только когда ответа нет:** сетевая ошибка, блокировка CORS, отмена. На 404 и 500 промис выполняется, а проверять нужно `response.ok` или `status`.
- **Тело запроса задаёт `Content-Type`:** строка уходит как `text/plain`, `URLSearchParams` — как форма, `FormData` — как `multipart/form-data` с границей, которую `fetch` вписывает сам. Ручной `Content-Type` для `FormData` ломает разбор на сервере.
- **Повторять можно только идемпотентные запросы и только временные ошибки:** сеть, 429, 5xx. Задержка растёт экспоненциально со случайным разбросом и учитывает `Retry-After`.
- **У `fetch` нет прогресса выгрузки, а прогресс скачивания по `Content-Length` врёт при сжатии.** Для выгрузки с прогрессом — `XMLHttpRequest`.
- **Данные при уходе со страницы отправляют `sendBeacon` или `fetch` с `keepalive`:** запрос переживёт закрытие вкладки, но тело ограничено 64 КБ.
::

## Что делает fetch

Сквозной пример — интернет-магазин: поиск по каталогу, загрузка фото отзыва, оформление заказа и аналитика.

```js
const res = await fetch('/api/products?q=улун', {
  method: 'GET',              // по умолчанию
  headers: { accept: 'application/json' },
  credentials: 'same-origin', // по умолчанию: куки только своему origin
  signal,                     // отмена и тайм-аут
});
const products = await res.json();
```

`fetch` возвращает промис, который выполняется, **как только пришли заголовки ответа**. Тело ещё идёт по сети, и `res.json()`, `res.text()`, `res.blob()` возвращают свои промисы — они дочитывают тело до конца. Тело — поток, и прочитать его можно один раз; подробнее про потоки и `clone()` — в [API браузера](/content/web/browser-apis).

Главные параметры:

| Параметр | Значения | Что меняет |
| --- | --- | --- |
| `method`, `headers`, `body` | — | сам запрос |
| `credentials` | `same-origin`, `include`, `omit` | отправлять ли куки и HTTP-авторизацию; межсайтовые — в [CORS](/content/network-api/cors) |
| `mode` | `cors`, `same-origin`, `no-cors` | правила для чужих origin |
| `redirect` | `follow`, `manual`, `error` | что делать с перенаправлением |
| `cache` | `default`, `no-store`, `reload`, `no-cache`, `force-cache` | как использовать HTTP-кеш ([Кеширование](/content/network-api/caching)) |
| `signal` | `AbortSignal` | отмена и тайм-аут |
| `keepalive` | `true` | запрос переживёт уход со страницы |
| `priority` | `high`, `low`, `auto` | подсказка приоритета загрузки |

Отмена через `AbortController`, тайм-аут через `AbortSignal.timeout` и гонки ответов разобраны в [Асинхронности](/content/javascript/async).

## Когда промис отклоняется

Самая частая ошибка — ждать исключения на ошибке сервера. `fetch` отклоняет промис только когда **ответа нет**:

| Ситуация | Результат |
| --- | --- |
| 404 Not Found | выполнен, `ok: false`, `status: 404` |
| 502 Bad Gateway | выполнен, `ok: false`, `status: 502` |
| сервер недоступен | `TypeError: Failed to fetch` |
| CORS заблокировал ответ | `TypeError: Failed to fetch` |
| отмена | `AbortError` |
| тайм-аут `AbortSignal.timeout` | `TimeoutError` |

Так выглядело в проверке в Chromium. Отдельная ловушка — ответ с ошибкой от прокси или балансировщика приходит HTML-страницей, и `res.json()` падает с `SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON`. Это не «битый JSON», а непроверенный статус.

Поэтому вокруг `fetch` пишут обёртку, которая превращает не-2xx в исключение с полезными данными:

```js
class HttpError extends Error {
  constructor(response, body) {
    super(`HTTP ${response.status}`);
    this.name = 'HttpError';
    this.status = response.status;
    this.body = body;
  }
}

async function api(url, init) {
  const res = await fetch(url, init);
  if (!res.ok) throw new HttpError(res, await res.text());
  return res.headers.get('content-type')?.includes('json') ? res.json() : res.text();
}
```

Axios делает то же из коробки: промис отклоняется на любом статусе вне 2xx — в проверке `axios.get` на 404 бросил ошибку с `error.response.status`, а `fetch` вернул ответ.

## Тело запроса

`fetch` выбирает `Content-Type` по типу тела, если заголовок не задан явно. В проверке сервер получил:

| Тело | `Content-Type` |
| --- | --- |
| строка, в том числе `JSON.stringify(...)` | `text/plain;charset=UTF-8` |
| `URLSearchParams` | `application/x-www-form-urlencoded;charset=UTF-8` |
| `FormData` | `multipart/form-data; boundary=----WebKitFormBoundary…` |
| `Blob` и `File` | тип самого `Blob` |

Отсюда два правила.

**JSON нужно объявлять.** Строка из `JSON.stringify` без заголовка уходит как текст, и сервер с разбором JSON по `Content-Type` получит пустое тело:

```js
await fetch('/api/orders', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ items, address }),
});
```

**Для `FormData` заголовок не ставят.** Многочастное тело разделено случайной строкой-границей, и `fetch` вписывает её в заголовок: `multipart/form-data; boundary=…`. Если указать `Content-Type: multipart/form-data` руками, граница пропадёт, и сервер не сможет разобрать тело — в проверке разбор такого тела упал, а тело с границей от `fetch` разобралось с полем `title` и файлом `tea.png`.

```js
const form = new FormData();
form.append('title', 'Улун');
form.append('photo', fileInput.files[0]);
await fetch('/api/reviews', { method: 'POST', body: form }); // без content-type
```

## Редиректы

По умолчанию `fetch` следует за перенаправлениями сам: `res.redirected` — `true`, `res.url` — конечный адрес. Режим `redirect: 'manual'` возвращает непрозрачный ответ с `type: 'opaqueredirect'` и `status: 0` — узнать адрес перенаправления скрипт не может. `redirect: 'error'` превращает любой редирект в `TypeError`. Как браузер меняет метод при редиректах — в [HTTP](/content/network-api/http).

Частый случай — сессия истекла, и API отвечает редиректом на страницу входа. `fetch` молча идёт за ним и получает HTML вместо JSON. API для фронтенда должен отвечать 401, а не редиректом.

## Повторы

Сеть ненадёжна, и запросы иногда стоит повторить. Но слепой повтор вредит дважды: может выполнить действие второй раз и добить сервер, которому и так плохо.

Правила:

1. **Повторять только временные ошибки:** сетевые, 408, 429, 500, 502, 503, 504. Ошибки 4xx — проблема запроса, повтор вернёт то же самое.
2. **Повторять только идемпотентные запросы** — GET, PUT, DELETE — или POST с ключом идемпотентности, по которому сервер узнает повтор ([Паттерны API](/content/network-api/api-patterns)).
3. **Ждать всё дольше:** экспоненциальная задержка — 100, 200, 400 мс — с **полным разбросом** (случайное значение от нуля до этой границы), чтобы тысячи клиентов после сбоя не ударили по серверу одновременно.
4. **Уважать `Retry-After`** — сервер сам говорит, когда приходить.
5. **Ограничить число попыток** и не повторять отменённое.

```js
const RETRIABLE = new Set([408, 429, 500, 502, 503, 504]);
const IDEMPOTENT = new Set(['GET', 'HEAD', 'PUT', 'DELETE', 'OPTIONS']);

async function request(url, { retries = 3, baseDelay = 100, ...init } = {}) {
  const method = (init.method ?? 'GET').toUpperCase();
  const canRetry = IDEMPOTENT.has(method) || init.headers?.['idempotency-key'];
  for (let attempt = 0; ; attempt++) {
    try {
      const res = await fetch(url, init);
      if (res.ok) return res;
      throw new HttpError(res, await res.text());
    } catch (e) {
      if (e.name === 'AbortError') throw e;
      const retriable = e instanceof HttpError ? RETRIABLE.has(e.status) : true;
      if (!canRetry || !retriable || attempt >= retries) throw e;
      const retryAfter = Number(e.retryAfter) * 1000 || 0;
      await sleep(Math.max(retryAfter, Math.random() * baseDelay * 2 ** attempt));
    }
  }
}
```

В проверке сервер, отвечавший дважды 503, на третьей попытке отдал данные; 429 с `Retry-After: 1` выдержал паузу в секунду; 400 и POST без ключа не повторялись, а POST с ключом — повторялся.

### Одинаковые запросы

Три компонента на странице одновременно просят каталог — три одинаковых запроса. Простая дедупликация хранит промис запроса, пока он в пути:

```js
const inFlight = new Map();
function getOnce(url) {
  if (!inFlight.has(url)) {
    inFlight.set(url, fetch(url).then((r) => r.json()).finally(() => inFlight.delete(url)));
  }
  return inFlight.get(url);
}
```

В проверке три одновременных вызова дали один запрос. Кеш между запросами, устаревание и инвалидацию берут на себя библиотеки серверного состояния ([Загрузка данных в React](/content/reactjs/data-fetching)).

## Прогресс

**Скачивание.** Тело — поток, и его можно читать по частям, считая байты:

```js
const res = await fetch(url);
const total = Number(res.headers.get('content-length'));
const reader = res.body.getReader();
let loaded = 0;
for (;;) {
  const { done, value } = await reader.read();
  if (done) break;
  loaded += value.length;
  onProgress(loaded / total);
}
```

Ловушка — сжатие. `Content-Length` — размер сжатого тела, а поток отдаёт уже распакованные байты. В проверке ответ в gzip показал прогресс больше 500%. Для сжатых ответов процент не посчитать; показывают индикатор без процентов или отдают несжатый размер отдельным заголовком.

**Выгрузка.** У `fetch` нет события прогресса отправки. Потоковое тело запроса возможно, но требует `duplex: 'half'` и HTTP/2, и прогресс всё равно приходится считать вручную. Для загрузки файла с полосой прогресса по-прежнему используют `XMLHttpRequest`:

```js
const xhr = new XMLHttpRequest();
xhr.upload.onprogress = (e) => onProgress(e.loaded / e.total);
xhr.open('POST', '/api/reviews/photo');
xhr.send(file);
```

В проверке выгрузка 5 МБ через XHR дала события прогресса, последнее — `5242880 / 5242880`.

## Запросы при уходе со страницы

Аналитика «пользователь ушёл с каталога» должна уйти, даже когда вкладка закрывается. Обычный `fetch` в этот момент браузер может отменить вместе со страницей. Для этого есть два способа:

- **`navigator.sendBeacon(url, data)`** — ставит POST в очередь браузера и сразу возвращает `true`. Ответ не прочитать, заголовки не задать: строка уходит как `text/plain;charset=UTF-8`, что и показала проверка;
- **`fetch` с `keepalive: true`** — обычный запрос, который переживёт страницу, с любыми заголовками и методом. Сумма тел таких запросов в пути ограничена 64 КБ: в проверке запрос на 70 КБ отклонился с `TypeError` и не ушёл.

Отправляют в событии `visibilitychange` при `document.visibilityState === 'hidden'` или в `pagehide`. Событие `unload` ненадёжно на мобильных и мешает кешу назад-вперёд, поэтому на нём ничего не делают.

## fetch, XMLHttpRequest и axios

| | `fetch` | `XMLHttpRequest` | axios |
| --- | --- | --- | --- |
| Интерфейс | промисы | события и колбэки | промисы |
| Ошибка на 4xx и 5xx | нет | нет | да |
| Прогресс выгрузки | нет | да | да, через XHR в браузере |
| Потоковое чтение тела | да | нет | нет |
| Перехватчики | обёртка вручную | нет | есть |
| Отмена | `AbortSignal` | `abort()` | `AbortSignal` |

Новый код пишут на `fetch` с тонкой обёрткой; XHR остаётся для прогресса выгрузки, axios — по привычке проекта и ради перехватчиков. Обзор клиентов и обёрток — в [Клиентах API](/content/ecosystem-libs/realtime-and-api-clients).

## Красные флаги в ответе

- **«`fetch` бросит исключение, если сервер ответил 500».** Промис выполнится; ошибку нужно распознать по `ok` или `status`.
- **«Поставлю `Content-Type: multipart/form-data` для `FormData`».** Пропадёт граница частей, и сервер не разберёт тело.
- **«`JSON.stringify` в `body` — и сервер получит JSON».** Без заголовка `application/json` тело уходит как `text/plain`.
- **«Повторяем запрос три раза при любой ошибке».** Повторяют только временные ошибки и только идемпотентные запросы, с растущей задержкой и разбросом.
- **«Прогресс считаю по `Content-Length`».** При сжатии длина — сжатая, а байты — распакованные.
- **«Аналитику отправляю в `unload` обычным `fetch`».** Запрос может отмениться; нужны `sendBeacon` или `keepalive` в `visibilitychange`.

## Как спрашивают на собеседовании

::question
Когда `fetch` отклоняет промис?

#answer
Только когда ответа нет: сетевая ошибка, блокировка CORS, отмена через `AbortSignal` или тайм-аут. Любой полученный ответ, включая 404 и 500, выполняет промис; проверять результат нужно по `response.ok` или `status`.

#more
Сетевая ошибка и CORS выглядят одинаково — `TypeError: Failed to fetch`, без подробностей: скрипту нельзя различить их из соображений безопасности. Отмена — `AbortError`, тайм-аут `AbortSignal.timeout` — `TimeoutError`. Обёртку, которая превращает не-2xx в исключение с телом ошибки, пишут один раз на проект; axios делает так по умолчанию.
::

::question
Как отправить JSON, форму и файлы через `fetch`?

#answer
JSON — `JSON.stringify` в `body` и заголовок `content-type: application/json`; без него строка уходит как `text/plain`. Форму — `URLSearchParams`, заголовок `fetch` поставит сам. Файлы — `FormData` с `append`, и заголовок `Content-Type` не задают вручную: `fetch` сам добавит `multipart/form-data` с границей частей.

#more
Ручной `multipart/form-data` без `boundary` ломает разбор на сервере — в проверке такое тело не разобралось. Один файл можно отправить и как есть, телом-`Blob`, тогда заголовок возьмётся из его типа. Большие файлы режут на части или загружают напрямую в хранилище по подписанной ссылке.
::

::question
Как правильно повторять запросы?

#answer
Повторять только временные ошибки — сетевые, 408, 429 и 5xx — и только идемпотентные запросы или POST с ключом идемпотентности. Задержка растёт экспоненциально со случайным разбросом, учитывает `Retry-After`, число попыток ограничено, отменённые запросы не повторяются.

#more
Разброс нужен, чтобы клиенты после сбоя не вернулись одновременно и не устроили новую волну нагрузки. Повтор 400 бессмыслен, а повтор POST без ключа может создать второй заказ. Для массовых ошибок добавляют предохранитель (circuit breaker): после серии отказов запросы какое-то время не отправляются вовсе.
::

::question
Как показать прогресс скачивания и загрузки файла?

#answer
Скачивание — читать `response.body.getReader()` и считать байты относительно `Content-Length`. Загрузку на сервер `fetch` не показывает, поэтому для полосы прогресса используют `XMLHttpRequest` и событие `xhr.upload.onprogress`.

#more
При сжатии `Content-Length` — размер сжатого тела, а поток отдаёт распакованные байты, и процент уходит за 100: в проверке он превысил 500%. Если длина неизвестна (`chunked`), показывают неопределённый индикатор. Потоковое тело запроса в `fetch` требует `duplex: 'half'` и HTTP/2 и не даёт готового события прогресса.
::

::question
Как отправить аналитику, когда пользователь закрывает вкладку?

#answer
`navigator.sendBeacon` или `fetch` с `keepalive: true` в обработчике `visibilitychange` при `hidden` или в `pagehide`. Такие запросы браузер доводит до конца, даже если страница уже закрыта. Обычный `fetch` в этот момент может быть отменён.

#more
`sendBeacon` — всегда POST без чтения ответа и без своих заголовков: строка уходит как `text/plain`. `keepalive` позволяет любой метод и заголовки, но общий размер тел в пути ограничен 64 КБ — в проверке запрос на 70 КБ отклонился. `unload` не используют: на мобильных он часто не срабатывает и ломает кеш назад-вперёд.
::

::question
Чем `fetch` отличается от `XMLHttpRequest` и axios?

#answer
`fetch` — промисы, потоковое тело ответа, `AbortSignal`, режимы CORS и кеша, но нет прогресса выгрузки и ошибки на 4xx и 5xx. XHR — старый интерфейс на событиях, зато с прогрессом выгрузки. Axios — библиотека с промисами, ошибкой на не-2xx, перехватчиками и прогрессом через XHR в браузере.

#more
В проверке axios отклонил промис на 404, а `fetch` вернул ответ со статусом 404. Перехватчики axios — удобное место для токена и обработки 401; в `fetch` то же делает своя обёртка. Для потокового чтения ответа — например, ответа ИИ-модели по частям — нужен `fetch`.
::

## Практика

::practice{title="Unexpected token '<'"}
Обработчик оформления заказа:

```js
const res = await fetch('/api/orders', { method: 'POST', body: JSON.stringify(order) });
const data = await res.json();
showReceipt(data);
```

В Sentry ошибка `SyntaxError: Unexpected token '<', "<!doctype "... is not valid JSON`, а иногда пользователь видит пустой чек. Найди проблемы.

#solution
1. Статус не проверяется. Когда бэкенд недоступен, балансировщик отвечает 502 HTML-страницей, и `res.json()` падает на ней — в проверке ровно с таким сообщением. А ответ 422 с ошибкой в JSON разбирается успешно и показывается как чек.
2. Нет `content-type: application/json`: тело уходит как `text/plain`, и сервер, который разбирает JSON по заголовку, получает пустой объект.

```js
const res = await fetch('/api/orders', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify(order),
});
if (!res.ok) {
  const isJson = res.headers.get('content-type')?.includes('json');
  const problem = isJson ? await res.json() : { title: `Сервер ответил ${res.status}` };
  throw new HttpError(res, problem);
}
showReceipt(await res.json());
```

Ошибку `HttpError` ловит общий обработчик и показывает `problem.title`.
::

::practice{title="Сервер не видит поля формы"}
Загрузка фото к отзыву:

```js
const form = new FormData();
form.append('text', text);
form.append('photo', file);
await fetch('/api/reviews', {
  method: 'POST',
  headers: { 'Content-Type': 'multipart/form-data' },
  body: form,
});
```

Сервер отвечает, что полей нет. Почему?

#solution
Многочастное тело делится на части строкой-границей, и сервер находит её в заголовке: `multipart/form-data; boundary=...`. `fetch` сам вычисляет границу и пишет её в заголовок, но только если заголовок не задан. Здесь он задан руками без `boundary`, и сервер не может разобрать тело. В проверке разбор такого тела упал с `TypeError`, а с заголовком от `fetch` поля и файл разобрались.

Исправление — убрать заголовок:

```js
await fetch('/api/reviews', { method: 'POST', body: form });
```

То же правило в axios и других клиентах: для `FormData` тип не задают, его ставит браузер.
::

::practice{title="Повторы добили сервер"}
После минутного сбоя API все открытые вкладки начали повторять запросы:

```js
async function load(url) {
  for (;;) {
    try {
      const res = await fetch(url);
      if (res.ok) return res.json();
    } catch {}
    await sleep(1000);
  }
}
```

Сервер поднялся, но тут же упал снова. Почему и как исправить?

#solution
Повторы бесконечные, с одинаковой задержкой и без разброса: после сбоя все клиенты стучатся каждую секунду синхронно, и восстановившийся сервер получает волну нагрузки. К тому же повторяются и 4xx, которые никогда не пройдут.

```js
async function load(url, { retries = 5, baseDelay = 500 } = {}) {
  for (let attempt = 0; ; attempt++) {
    const res = await fetch(url).catch(() => null);
    if (res?.ok) return res.json();
    const retriable = !res || [408, 429, 500, 502, 503, 504].includes(res.status);
    if (!retriable || attempt >= retries) throw new Error(`Не удалось загрузить: ${res?.status ?? 'сеть'}`);
    const retryAfter = Number(res?.headers.get('retry-after')) * 1000 || 0;
    await sleep(Math.max(retryAfter, Math.random() * baseDelay * 2 ** attempt));
  }
}
```

Задержка растёт вдвое, случайный разброс рассеивает клиентов во времени, `Retry-After` позволяет серверу управлять нагрузкой, число попыток ограничено. В проверке такая схема пережила два ответа 503 и выдержала `Retry-After: 1`. Для фоновых обновлений ещё полезно не повторять, пока вкладка скрыта.
::
