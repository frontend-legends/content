# Получение данных на клиенте

Умение правильно получать данные - одна из ключевых компетенций фронтенд-разработчика. На собеседованиях спрашивают не просто «как сделать fetch», а как обрабатывать ошибки, отменять запросы, бороться с race conditions и выстраивать стратегию кэширования. В этом разделе разберём fetch API в деталях, типичные подводные камни и паттерны, которые отличают production-код от учебных примеров.

> Предполагается, что ты знаком с основами HTTP - методы, статус-коды, заголовки. Если нет - сначала загляни в [HTTP](/content/network-api/http).

## fetch API

<b class="text-on-semi-light">Нативный API для сетевых запросов</b>

<span class="text-gray">`fetch()` - встроенная функция браузера, возвращающая Promise. Пришла на смену `XMLHttpRequest`, работает с Streams и поддерживает modern patterns.</span>

### Базовый синтаксис

```js
const response = await fetch(url, options);
```

### Основные options

| Параметр      | Тип                                         | Описание                                                      |
| ------------- | ------------------------------------------- | ------------------------------------------------------------- |
| `method`      | `string`                                    | HTTP-метод: `'GET'`, `'POST'`, `'PUT'`, `'DELETE'`, `'PATCH'` |
| `headers`     | `Headers \| object`                         | Заголовки запроса                                             |
| `body`        | `string \| FormData \| Blob \| ArrayBuffer` | Тело запроса (не для GET/HEAD)                                |
| `mode`        | `string`                                    | `'cors'` (по умолчанию), `'no-cors'`, `'same-origin'`         |
| `credentials` | `string`                                    | `'same-origin'` (по умолчанию), `'include'`, `'omit'`         |
| `signal`      | `AbortSignal`                               | Сигнал для отмены запроса                                     |
| `cache`       | `string`                                    | `'default'`, `'no-store'`, `'reload'`, `'force-cache'`        |

### Полный пример: POST-запрос

```js
const response = await fetch("/api/users", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
    Authorization: `Bearer ${token}`,
  },
  body: JSON.stringify({ name: "Alex", role: "admin" }),
  credentials: "include", // отправить cookies
});

const data = await response.json();
```

### Чтение ответа

```js
const response = await fetch(url);

// Тело можно прочитать ОДИН раз - выбери нужный метод:
response.json(); // парсит JSON
response.text(); // строка
response.blob(); // Blob (файлы, изображения)
response.arrayBuffer(); // ArrayBuffer (бинарные данные)
response.formData(); // FormData
```

<span class="text-gray">`response.body` - это ReadableStream. Можно читать данные по частям (полезно для прогресса загрузки больших файлов).</span>

## Обработка ошибок

<b class="text-on-semi-light">fetch НЕ бросает исключение на 4xx/5xx</b>

<span class="text-gray">Это главный подводный камень fetch. Promise reject'ится **только** при сетевой ошибке (нет интернета, DNS не резолвится, CORS-блок). Ответ с кодом 404 или 500 считается **успешным** промисом.</span>

```js
// Неправильно - не ловит HTTP-ошибки
try {
  const res = await fetch("/api/data");
  const data = await res.json(); // упадёт, если ответ не JSON
} catch (err) {
  // Сюда попадёт только сетевая ошибка!
}

// Правильно - проверяем response.ok
async function fetchJSON(url, options) {
  const res = await fetch(url, options);

  if (!res.ok) {
    // res.ok === true для статусов 200-299
    const errorBody = await res.text();
    throw new Error(`HTTP ${res.status}: ${errorBody}`);
  }

  return res.json();
}
```

> На собеседовании часто спрашивают: «В чём отличие fetch от axios при обработке ошибок?» Ответ: axios автоматически reject'ит Promise для 4xx/5xx, а fetch - нет.

## AbortController: отмена запросов

<b class="text-on-semi-light">Механизм отмены асинхронных операций</b>

<span class="text-gray">`AbortController` - универсальный способ отменять fetch-запросы, addEventListener'ы и другие асинхронные операции. Создаёшь контроллер, передаёшь его `signal` в fetch, и вызываешь `abort()` когда нужно отменить.</span>

```js
const controller = new AbortController();

fetch("/api/data", { signal: controller.signal })
  .then((res) => res.json())
  .catch((err) => {
    if (err.name === "AbortError") {
      console.log("Запрос отменён");
    }
  });

// Отменить запрос
controller.abort();
```

### Очистка в React (useEffect cleanup)

```js
useEffect(() => {
  const controller = new AbortController();

  async function loadData() {
    try {
      const res = await fetch(`/api/users/${userId}`, {
        signal: controller.signal,
      });
      const data = await res.json();
      setUsers(data);
    } catch (err) {
      if (err.name !== "AbortError") {
        setError(err.message);
      }
    }
  }

  loadData();

  return () => controller.abort(); // cleanup при unmount или смене userId
}, [userId]);
```

## Race Conditions

<b class="text-on-semi-light">Проблема устаревших ответов</b>

<span class="text-gray">Если пользователь быстро переключается между элементами (например, табами или поиском), несколько запросов уходят параллельно. Ответы приходят не в том порядке, в котором отправлены - и данные «мерцают» или отображается неактуальный результат.</span>

```text
Клик таб A -> запрос A (медленный) ───────────────> ответ A (устаревший!)
Клик таб B -> запрос B (быстрый) ──> ответ B (актуальный)

Без защиты: ответ A приходит позже и перезаписывает корректные данные B
```

### Решение: AbortController

```js
function useData(id) {
  const [data, setData] = useState(null);

  useEffect(() => {
    const controller = new AbortController();

    fetch(`/api/items/${id}`, { signal: controller.signal })
      .then((res) => res.json())
      .then(setData)
      .catch((err) => {
        if (err.name !== "AbortError") throw err;
      });

    // При смене id предыдущий запрос отменяется
    return () => controller.abort();
  }, [id]);

  return data;
}
```

<span class="text-gray">Другой подход - boolean-флаг (`let cancelled = false`), но AbortController предпочтительнее: он реально отменяет сетевой запрос, а не просто игнорирует ответ.</span>

## Таймауты

<b class="text-on-semi-light">AbortSignal.timeout()</b>

<span class="text-gray">Встроенный способ задать таймаут для fetch без создания AbortController вручную. Поддерживается в современных браузерах.</span>

```js
// Простой таймаут
const res = await fetch("/api/data", {
  signal: AbortSignal.timeout(5000), // 5 секунд
});
```

### Комбинация таймаута и ручной отмены

```js
const controller = new AbortController();

// AbortSignal.any - комбинирует несколько сигналов
const signal = AbortSignal.any([
  controller.signal, // ручная отмена
  AbortSignal.timeout(10000), // таймаут 10 сек
]);

const res = await fetch("/api/data", { signal });
```

## Retry-стратегии

<b class="text-on-semi-light">Exponential Backoff</b>

<span class="text-gray">При сетевых ошибках или 5xx-ответах имеет смысл повторить запрос. Exponential backoff увеличивает задержку между попытками: 1с -> 2с -> 4с -> 8с. Это снижает нагрузку на сервер и повышает шанс успеха.</span>

```js
async function fetchWithRetry(url, options = {}, maxRetries = 3) {
  for (let attempt = 0; attempt <= maxRetries; attempt++) {
    try {
      const res = await fetch(url, options);

      // Повторяем только для серверных ошибок
      if (res.status >= 500 && attempt < maxRetries) {
        throw new Error(`Server error: ${res.status}`);
      }

      return res;
    } catch (err) {
      if (attempt === maxRetries) throw err;

      // Exponential backoff с jitter
      const delay = Math.min(1000 * 2 ** attempt + Math.random() * 1000, 30000);
      await new Promise((resolve) => setTimeout(resolve, delay));
    }
  }
}
```

<span class="text-gray">**Jitter** (случайная добавка) - важная деталь. Без него тысячи клиентов будут повторять запросы одновременно (thundering herd), что усугубит проблему.</span>

> Не повторяй 4xx-ошибки - они идемпотентны и не исправятся при повторе (кроме 429 Too Many Requests).

## Паттерн SWR (Stale-While-Revalidate)

<b class="text-on-semi-light">Сначала кэш, потом свежие данные</b>

<span class="text-gray">SWR - стратегия, при которой ты мгновенно отдаёшь закэшированные (stale) данные, а в фоне делаешь запрос за свежими. Когда свежие данные придут - обновляешь UI. Пользователь видит контент сразу, без лоадера.</span>

```text
1. Показать данные из кэша (stale) -> мгновенный UI
2. Отправить запрос за свежими данными (revalidate)
3. Обновить кэш и UI при получении ответа
```

<span class="text-gray">Этот паттерн реализован в библиотеках SWR (Vercel) и React Query (TanStack Query). Подробнее о кэшировании - [Кэширование](/content/network-api/caching).</span>

## Обзор библиотек для запросов

| Библиотека           | Размер | Особенности                                                 |
| -------------------- | ------ | ----------------------------------------------------------- |
| **fetch** (нативный) | 0 КБ   | Встроен в браузер, минимальный API, нет retry/interceptors  |
| **axios**            | ~13 КБ | Interceptors, автоматический JSON, cancel tokens, progress  |
| **ky**               | ~3 КБ  | Обёртка над fetch, retry, timeout, hooks, JSON по умолчанию |
| **ofetch**           | ~4 КБ  | Универсальный (browser + Node), auto-parse, retry, от UnJS  |

<b class="text-on-semi-light">Когда использовать нативный fetch</b>

<span class="text-gray">Если у тебя есть обёртка-helper для обработки ошибок и JSON-парсинга - fetch хватит в большинстве случаев. Библиотеки нужны для interceptors (добавление токена, логирование), retry-логики и прогресса загрузки.</span>

<b class="text-on-semi-light">Когда брать библиотеку</b>

<span class="text-gray">Если проект требует interceptors (подставить auth-заголовок в каждый запрос), глобальную обработку ошибок, retry из коробки или ты работаешь с файлами и нужен прогресс загрузки.</span>

> Для кэширования, дедупликации и управления серверным состоянием используй **TanStack Query** (React Query) или **SWR** - они работают поверх любого fetch-клиента.
