# Real-time коммуникация

Классический HTTP работает по модели «запрос-ответ» - клиент спрашивает, сервер отвечает. Но что если серверу нужно **сообщить клиенту** о чём-то без запроса? Чаты, уведомления, live-дашборды, collaborative editing - всё это требует real-time связи. На собеседованиях часто просят сравнить подходы и объяснить, когда какой использовать.

> Для понимания этого раздела полезно знать основы [HTTP](/content/network-api/http) и [Fetching](/content/network-api/fetching).

---

## Зачем нужен real-time

- **Мессенджеры и чаты** - мгновенная доставка сообщений
- **Нотификации** - новый заказ, новое сообщение, изменение статуса
- **Live-дашборды** - графики, мониторинг, котировки
- **Collaborative editing** - Google Docs, Figma, Miro
- **Мультиплеер** - онлайн-игры, cursor sharing
- **Streaming** - потоковая передача данных от LLM, live-логи

## Short Polling

<b class="text-on-semi-light">Простейший подход: спрашивай сервер по таймеру</b>

<span class="text-gray">Клиент периодически отправляет обычные HTTP-запросы (через `setInterval`) и проверяет, есть ли новые данные. Сервер отвечает мгновенно - либо с данными, либо с пустым ответом.</span>

```js
const POLL_INTERVAL = 5000;

async function poll() {
  try {
    const res = await fetch("/api/notifications");
    const data = await res.json();
    if (data.length > 0) {
      renderNotifications(data);
    }
  } catch (err) {
    console.error("Polling error:", err);
  }
}

const intervalId = setInterval(poll, POLL_INTERVAL);

// Cleanup
// clearInterval(intervalId);
```

| Плюсы                           | Минусы                                                |
| ------------------------------- | ----------------------------------------------------- |
| Максимально просто в реализации | Задержка = интервал опроса                            |
| Работает с любым сервером/CDN   | Лишние запросы, когда данных нет                      |
| Легко дебажить                  | Высокая нагрузка на сервер при большом числе клиентов |
| Stateless                       | Не подходит для instant-обновлений                    |

<span class="text-gray">Подходит для: некритичных обновлений с интервалом от 10+ секунд - проверка статуса заказа, обновление курса валют на странице, проверка новых email.</span>

## Long Polling

<b class="text-on-semi-light">Сервер держит соединение, пока не появятся данные</b>

<span class="text-gray">Клиент отправляет запрос, а сервер **не отвечает сразу** - он ждёт, пока появятся новые данные (или истечёт таймаут). Как только сервер ответил, клиент немедленно отправляет новый запрос.</span>

```js
async function longPoll() {
  try {
    const res = await fetch("/api/events?timeout=30000");
    const data = await res.json();
    handleEvents(data);
  } catch (err) {
    // При ошибке ждём перед повторной попыткой
    await new Promise((r) => setTimeout(r, 3000));
  }
  // Сразу начинаем новый цикл
  longPoll();
}

longPoll();
```

| Плюсы                             | Минусы                                  |
| --------------------------------- | --------------------------------------- |
| Почти мгновенная доставка данных  | Сервер держит открытые соединения       |
| Работает через стандартный HTTP   | Сложнее масштабировать                  |
| Проходит через прокси и файрволлы | Таймауты прокси/балансировщиков         |
| Просто для клиента                | Сервер должен поддерживать hold-паттерн |

<span class="text-gray">Long polling использовали до появления WebSocket и SSE. Сейчас это fallback-вариант, когда другие технологии недоступны (старые прокси, корпоративные сети).</span>

## Server-Sent Events (SSE)

<b class="text-on-semi-light">Однонаправленный поток событий от сервера</b>

<span class="text-gray">SSE - стандартный механизм для push-уведомлений от сервера к клиенту. Основан на HTTP, использует формат `text/event-stream`. Клиент открывает соединение через `EventSource`, а сервер отправляет события по мере их появления.</span>

### Ключевые особенности

- **Однонаправленный** - только сервер -> клиент
- **Автоматический reconnect** - браузер сам переподключается при обрыве
- **Event ID** - сервер может нумеровать события, при reconnect клиент отправляет `Last-Event-ID`
- **Работает поверх HTTP** - проходит через прокси, CDN, файрволлы
- Формат: простой текстовый протокол

### Формат данных

```text
event: notification
data: {"type": "message", "text": "Hello"}
id: 42

event: heartbeat
data: ping

```

<span class="text-gray">Каждое событие разделяется пустой строкой. Поле `event` задаёт тип (можно слушать через `addEventListener`), `data` - полезная нагрузка, `id` - идентификатор для восстановления.</span>

### Клиентский API

```js
const source = new EventSource("/api/stream");

// Общий обработчик (событие "message" по умолчанию)
source.onmessage = (e) => {
  const data = JSON.parse(e.data);
  console.log("New event:", data);
};

// Слушаем конкретный тип события
source.addEventListener("notification", (e) => {
  const data = JSON.parse(e.data);
  showNotification(data);
});

// Обработка ошибок и reconnect
source.onerror = (e) => {
  console.log("SSE error, reconnecting...");
  // Браузер автоматически переподключится
};

// Закрытие соединения
source.close();
```

<span class="text-gray">SSE поддерживает передачу cookies (в отличие от WebSocket), что упрощает аутентификацию. Для авторизации через заголовки (Bearer token) используй `fetch()` + ReadableStream вместо EventSource.</span>

> SSE отлично подходит для streaming-ответов от LLM (ChatGPT-like интерфейсы), live-логов, нотификаций, обновления дашбордов.

## WebSocket

<b class="text-on-semi-light">Двунаправленная persistent-связь</b>

<span class="text-gray">WebSocket устанавливает постоянное двунаправленное соединение между клиентом и сервером. После HTTP-handshake (upgrade) протокол переключается на `ws://` (или `wss://` для TLS), и обе стороны могут отправлять сообщения в любой момент.</span>

### Жизненный цикл

1. Клиент отправляет HTTP-запрос с заголовком `Upgrade: websocket`
2. Сервер отвечает `101 Switching Protocols`
3. Устанавливается persistent TCP-соединение
4. Обе стороны обмениваются фреймами (text или binary)
5. Любая сторона может закрыть соединение

### Клиентский API

```js
const ws = new WebSocket("wss://api.example.com/ws");

ws.onopen = () => {
  console.log("Connected");
  ws.send(JSON.stringify({ type: "subscribe", channel: "chat" }));
};

ws.onmessage = (e) => {
  const data = JSON.parse(e.data);
  handleMessage(data);
};

ws.onerror = (e) => {
  console.error("WebSocket error:", e);
};

ws.onclose = (e) => {
  console.log(`Closed: code=${e.code}, reason=${e.reason}`);
  // Ручной reconnect
  setTimeout(() => connectWebSocket(), 3000);
};

// Отправка данных
ws.send(JSON.stringify({ type: "message", text: "Hello!" }));

// Проверка состояния
// ws.readyState: 0=CONNECTING, 1=OPEN, 2=CLOSING, 3=CLOSED

// Закрытие
ws.close(1000, "User left");
```

### Reconnect с exponential backoff

<span class="text-gray">WebSocket не переподключается автоматически (в отличие от SSE). Нужно реализовать reconnect-логику самостоятельно.</span>

```js
function createSocket(url) {
  let retries = 0;

  function connect() {
    const ws = new WebSocket(url);

    ws.onopen = () => {
      retries = 0; // сбрасываем счётчик после успешного подключения
    };

    ws.onclose = (e) => {
      if (e.code !== 1000) {
        // 1000 = нормальное закрытие
        const delay = Math.min(1000 * 2 ** retries, 30000);
        retries++;
        setTimeout(connect, delay);
      }
    };

    return ws;
  }

  return connect();
}
```

## Сравнительная таблица

| Метод             | Направление      | Протокол | Overhead    | Auto-reconnect | Use case               |
| ----------------- | ---------------- | -------- | ----------- | -------------- | ---------------------- |
| **Short Polling** | Client -> Server | HTTP     | Высокий     | Нет (вручную)  | Некритичные обновления |
| **Long Polling**  | Server -> Client | HTTP     | Средний     | Нет (вручную)  | Fallback-вариант       |
| **SSE**           | Server -> Client | HTTP     | Низкий      | Да (браузер)   | Нотификации, стриминг  |
| **WebSocket**     | Двунаправленный  | WS/WSS   | Минимальный | Нет (вручную)  | Чаты, игры, collab     |

## Когда что использовать

<b class="text-on-semi-light">Практические рекомендации</b>

- **Обновления раз в 30+ секунд, простой бэкенд** -> Short Polling
- **Уведомления, live-feed, стриминг от LLM** -> SSE
- **Чат, collaborative editing, двусторонний обмен** -> WebSocket
- **Корпоративная сеть, старые прокси** -> Long Polling как fallback

<span class="text-gray">Не усложняй: если тебе нужен только поток событий от сервера - SSE проще WebSocket (автоматический reconnect, работа через HTTP-инфраструктуру). WebSocket оправдан, когда клиент тоже активно отправляет данные.</span>

> В GraphQL для real-time используют **subscriptions**, которые обычно реализованы поверх WebSocket. Подробнее - [GraphQL](/content/network-api/graphql).

## Типичные вопросы на собеседовании

> **Чем SSE отличается от WebSocket?**
> SSE - однонаправленный (сервер -> клиент), работает поверх HTTP, автоматически переподключается. WebSocket - двунаправленный, использует отдельный протокол, требует ручного reconnect.

> **Почему не всегда WebSocket?**
> WebSocket сложнее в настройке (отдельный сервер, прокси-конфигурация, reconnect-логика). Если данные идут только от сервера к клиенту - SSE проще и надёжнее. К тому же SSE проходит через CDN и прокси без дополнительной конфигурации.

> **Как реализовать reconnect для WebSocket?**
> Слушай событие `onclose`, проверяй code (не 1000), реализуй exponential backoff с максимальным пределом. При reconnect пересылай последний известный event ID для получения пропущенных сообщений.
