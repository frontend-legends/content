# Реальное время

HTTP устроен как «спросил — получил ответ», а чатам, уведомлениям, ценам и статусам заказа нужно, чтобы сервер сообщал сам. Для этого есть четыре приёма: частый опрос, длинный опрос, поток событий Server-Sent Events и двусторонний канал WebSocket. Спрашивают, чем они отличаются и когда что выбрать. Глубже — как не потерять события при переподключении, почему седьмая вкладка с SSE перестаёт грузиться и почему WebSocket нужно защищать проверкой `Origin`.

::tldr
- **Частый опрос прост, но тратит запросы впустую; длинный опрос держит запрос, пока не появятся новости,** и работает везде, где работает HTTP.
- **SSE — поток событий от сервера по обычному HTTP:** текстовый формат, автоматическое переподключение и продолжение с `Last-Event-ID`. Только от сервера к клиенту.
- **WebSocket — двусторонний канал поверх одного TCP-соединения** после рукопожатия `Upgrade` и ответа `101`. Сообщения в обе стороны с малыми накладными расходами, но переподключение, проверка живости и продолжение — на тебе.
- **По HTTP/1.1 браузер держит не больше шести соединений на хост,** и каждый открытый SSE занимает одно. С HTTP/2 потоки делят одно соединение.
- **Обрывы — норма:** клиент переподключается с растущей задержкой, догоняет пропущенное по последнему номеру события, а сервер WebSocket проверяет `Origin` — CORS на него не действует.
::

## Опрос

Сквозной пример — интернет-магазин: статус заказа, цены на распродаже, чат с поддержкой.

**Частый опрос** (short polling) — спрашивать сервер по таймеру:

```js
setInterval(async () => {
  const status = await (await fetch('/api/orders/42/status')).json();
  render(status);
}, 5000);
```

Просто и надёжно, но почти все запросы возвращают «ничего нового», а событие доходит с задержкой до интервала. Подходит для редких обновлений, когда секунды задержки неважны.

**Длинный опрос** (long polling) — сервер держит запрос открытым, пока не появятся новости или не истечёт тайм-аут, а клиент сразу отправляет следующий. Событие приходит почти мгновенно, а пустых ответов мало. Важно передавать **курсор** — номер последнего полученного события, — иначе события, случившиеся между ответом и следующим запросом, потеряются:

```js
let after = 0;
for (;;) {
  const batch = await (await fetch(`/api/events?after=${after}`)).json();
  for (const e of batch) { handle(e); after = e.id; }
}
```

В проверке два события, опубликованные одно за другим, пока клиент обрабатывал предыдущее, пришли следующим ответом — ничего не потерялось. Длинный опрос работает через любые прокси и балансировщики и остаётся запасным вариантом в библиотеках вроде Socket.io.

## Server-Sent Events

**SSE** — поток событий от сервера по обычному HTTP-ответу с типом `text/event-stream`. Сервер не закрывает ответ и дописывает в него события:

```text
retry: 3000

id: 41
event: price
data: {"productId":7,"price":450}

id: 42
data: строка 1
data: строка 2

```

- событие кончается пустой строкой;
- `data:` — данные; несколько строк склеиваются через перевод строки;
- `event:` — имя события; без него событие называется `message`;
- `id:` — номер события; браузер запомнит его;
- `retry:` — через сколько миллисекунд переподключаться.

Клиент — `EventSource`:

```js
const es = new EventSource('/api/prices');
es.addEventListener('price', (e) => updatePrice(JSON.parse(e.data)));
es.onmessage = (e) => console.log(e.data);   // только события без имени
```

Ловушка — `onmessage` получает только события без `event:`; именованные слушают через `addEventListener`. В проверке событие `price` пришло в свой обработчик, а многострочное событие без имени — в `onmessage` как `'строка 1\nстрока 2'`.

### Переподключение без потерь

Главное преимущество SSE — встроенное переподключение. Если соединение оборвалось, браузер через `retry` миллисекунд открывает его снова и сам присылает заголовок `Last-Event-ID` с номером последнего полученного события. Сервер продолжает с него. В проверке сервер оборвал поток после события 2, а второе подключение пришло с `Last-Event-ID: 2` и получило событие 3.

Чтобы закончить поток навсегда, сервер отвечает `204 No Content` — в проверке после него `EventSource` перешёл в `CLOSED` и не переподключался. Ответ с ошибкой или неверным типом тоже закрывает поток насовсем.

Ограничения SSE: только от сервера к клиенту (отправлять — обычными запросами), только текст, и `EventSource` не умеет ставить свои заголовки — авторизация через куки. Поэтому для потоков с токеном в заголовке, вроде ответов ИИ-моделей, вместо `EventSource` читают `fetch` потоком ([ИИ во фронтенде](/content/additional-topics/ai-in-the-frontend)). Прокси и сжатие на сервере иногда буферизуют поток — тогда события приходят пачками.

### Шесть соединений

По HTTP/1.1 браузер держит не больше шести соединений на хост ([HTTP](/content/network-api/http)), а открытый `EventSource` занимает одно постоянно. Шесть вкладок с SSE — и все остальные запросы к этому хосту ждут. В проверке при шести открытых потоках `fetch` к тому же серверу не получил ответа, пока один поток не закрыли. С HTTP/2 все потоки идут внутри одного соединения, и проблема исчезает.

## WebSocket

**WebSocket** — двусторонний канал поверх одного TCP-соединения. Он начинается как HTTP-запрос с просьбой сменить протокол:

```text
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
Origin: https://shop.example
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
```

`Sec-WebSocket-Accept` — `base64(sha1(ключ + фиксированный GUID))`: так клиент убеждается, что ответил сервер, понимающий WebSocket, а не кеширующий прокси. В проверке значение совпало с вычисленным по этой формуле. После `101` то же TCP-соединение несёт **кадры** WebSocket в обе стороны.

```js
const ws = new WebSocket('wss://shop.example/chat');
ws.onopen = () => ws.send(JSON.stringify({ type: 'join', room: 'order-42' }));
ws.onmessage = (e) => render(JSON.parse(e.data));
ws.onclose = (e) => console.log(e.code, e.reason, e.wasClean);
```

Свойства, которые важны на практике:

- **границы сообщений сохраняются** — в отличие от сырого TCP, каждое `send` приходит отдельным `message`. Текст и бинарные данные (`ArrayBuffer`, `Blob`);
- **противодавление вручную** — `send` не ждёт отправки, данные копятся в буфере, а `bufferedAmount` показывает, сколько байтов ещё не ушло. В проверке после отправки 20 МБ он сразу стал больше нуля. Поток данных быстрее сети съест память, если не смотреть на `bufferedAmount`;
- **проверка живости** — сервер шлёт кадр `ping`, браузер отвечает `pong` сам (в проверке так и было), но из JavaScript отправить `ping` нельзя. Поэтому клиенты дополнительно шлют свои сообщения-«сердцебиения», чтобы заметить повисшее соединение, которое ОС ещё считает открытым;
- **коды закрытия** — `1000` — нормальное закрытие, `1001` — уход со страницы, `1006` — соединение оборвалось без закрывающего кадра (в проверке так выглядел обрыв на сервере), `4000–4999` — свои коды приложения. В проверке сервер закрыл соединение кодом `4001` с причиной «сессия истекла», и клиент получил и то и другое.

### Авторизация и Origin

Браузер не даёт задать свои заголовки в рукопожатии: второй аргумент `WebSocket` — список подпротоколов, и объект с заголовками в проверке дал `SyntaxError`. Поэтому авторизуют так:

- **куки** — уходят в рукопожатии сами, если адрес на том же сайте: в проверке сессия пришла в запросе `Upgrade`;
- **одноразовый билет** — получить коротко живущий токен обычным запросом и передать в адресе или первым сообщением.

На WebSocket **не действует CORS**: страница любого сайта может открыть соединение. Куки с `SameSite=Lax` в межсайтовое рукопожатие не уйдут, но с `SameSite=None` — уйдут, а сервер может узнавать пользователя и иначе. Поэтому сервер обязан сам проверять заголовок `Origin` в рукопожатии. В проверке страница с другого сайта подключилась к серверу без проверки, а сервер с белым списком origin отклонил рукопожатие. Без этого чужой сайт читает и пишет в чат от имени пользователя — это перехват WebSocket между сайтами.

### Переподключение

`WebSocket` сам не переподключается. Клиент делает это с растущей задержкой и разбросом, а после подключения **догоняет пропущенное** — передаёт номер последнего полученного сообщения:

```js
function connect(lastId = 0, attempt = 0) {
  const ws = new WebSocket(`wss://shop.example/feed?after=${lastId}`);
  ws.onopen = () => { attempt = 0; };
  ws.onmessage = (e) => {
    const m = JSON.parse(e.data);
    if (m.id <= lastId) return;                    // дубль после переподключения
    lastId = m.id;
    handle(m);
  };
  ws.onclose = () => {
    const delay = Math.min(30_000, 500 * 2 ** attempt) * (0.5 + Math.random() / 2);
    setTimeout(() => connect(lastId, attempt + 1), delay);
  };
}
```

В проверке сервер дважды рвал соединение, клиент переподключался с курсором и получил все семь событий ровно по одному разу. Socket.io и подобные библиотеки делают это за тебя, но требуют свой протокол на сервере ([Клиенты API](/content/ecosystem-libs/realtime-and-api-clients)).

## Что выбрать

| | Частый опрос | Длинный опрос | SSE | WebSocket |
| --- | --- | --- | --- | --- |
| Направление | клиент спрашивает | клиент спрашивает | сервер → клиент | в обе стороны |
| Задержка | до интервала | почти сразу | сразу | сразу |
| Переподключение | не нужно | своё | встроенное, с `Last-Event-ID` | своё |
| Через прокси и CDN | да | да | обычно, если не буферизуют | нужна поддержка `Upgrade` |
| Авторизация | любая | любая | куки | куки или билет |
| Когда | редкие обновления | совместимость | уведомления, цены, статусы, потоковые ответы | чаты, совместное редактирование, игры |

Правило: если данные идут только от сервера — SSE: он проще, работает по HTTP/2 и переподключается сам. Если клиент часто шлёт данные в ответ — WebSocket. Для видео и звука между пользователями — WebRTC ([Медиа и WebRTC](/content/additional-topics/media-and-webrtc)). Вкладкам одного сайта не обязательно держать по соединению: одна вкладка или SharedWorker держит поток и раздаёт события через `BroadcastChannel` ([API браузера](/content/web/browser-apis)).

## Красные флаги в ответе

- **«Для уведомлений нужен WebSocket».** Если данные идут только от сервера, SSE проще и сам переподключается.
- **«SSE и WebSocket сами не теряют события».** SSE продолжает с `Last-Event-ID`, только если сервер присылает `id` и умеет продолжать; WebSocket — только если ты передаёшь курсор сам.
- **«CORS защитит WebSocket от чужих сайтов».** На WebSocket CORS не действует; сервер проверяет `Origin`.
- **«Токен передам в заголовке WebSocket».** Браузер не даёт задать заголовки рукопожатия: куки или билет.
- **«Соединение открыто — значит, живое».** Повисшее TCP-соединение выглядит открытым; нужны ping, сердцебиения и тайм-ауты.
- **«Переподключаюсь сразу и каждую секунду».** После сбоя сервера все клиенты придут одновременно; нужны растущая задержка и разброс.

## Как спрашивают на собеседовании

::question
Какие есть способы получать обновления с сервера в реальном времени?

#answer
Частый опрос — запросы по таймеру. Длинный опрос — сервер держит запрос, пока не появятся новости. SSE — поток событий от сервера по HTTP с автоматическим переподключением. WebSocket — двусторонний канал поверх одного соединения. Для медиа между пользователями — WebRTC.

#more
Выбор по направлению и частоте: редкие обновления — опрос, поток от сервера — SSE, частый обмен в обе стороны — WebSocket. Длинный опрос остаётся запасным вариантом там, где прокси режут долгие соединения. Новый вариант — WebTransport поверх HTTP/3, с потоками и датаграммами, но поддерживается не везде.
::

::question
Чем SSE отличается от WebSocket?

#answer
SSE — поток от сервера к клиенту по обычному HTTP-ответу, текстовый формат, встроенное переподключение с `Last-Event-ID`; отправлять данные на сервер — обычными запросами. WebSocket — двусторонний канал после рукопожатия `Upgrade`, текст и бинарные данные, но переподключение, проверку живости и продолжение после обрыва пишет клиент.

#more
SSE проще проходит через прокси и CDN и по HTTP/2 делит одно соединение с остальными запросами; по HTTP/1.1 каждый поток занимает одно из шести соединений на хост. `EventSource` не умеет свои заголовки, поэтому авторизация — куками, а для потоков с токеном читают `fetch` потоком. WebSocket нужен, когда клиент тоже часто шлёт данные: чат, совместное редактирование, игры.
::

::question
Как SSE переподключается и не теряет события?

#answer
Если сервер присылает у событий `id:`, браузер запоминает последний. После обрыва он ждёт `retry` миллисекунд, переподключается и присылает заголовок `Last-Event-ID`. Сервер по нему отдаёт пропущенное и продолжает поток.

#more
В проверке второе подключение пришло с `Last-Event-ID: 2` и получило событие 3. Сервер должен хранить недавние события, чтобы их было откуда отдать. Закончить поток навсегда — ответ 204; любой другой ответ кроме 200 с `text/event-stream` тоже закрывает `EventSource` без переподключения.
::

::question
Как устроено WebSocket-соединение?

#answer
Клиент отправляет HTTP-запрос с `Upgrade: websocket` и случайным `Sec-WebSocket-Key`. Сервер отвечает `101 Switching Protocols` и `Sec-WebSocket-Accept` — хешем ключа с фиксированной строкой. После этого то же TCP-соединение несёт кадры WebSocket в обе стороны: текстовые, бинарные, служебные `ping`, `pong` и `close`.

#more
Кадры сохраняют границы сообщений, в отличие от сырого TCP. Кадры от клиента маскируются, чтобы старые прокси не приняли их за HTTP. `wss://` — то же поверх TLS. Код закрытия 1006 означает обрыв без закрывающего кадра — его видно, когда сервер упал или сеть пропала.
::

::question
Как авторизовать WebSocket и защитить его от чужих сайтов?

#answer
Свои заголовки в рукопожатии браузер задать не даёт, поэтому авторизуют куками, которые уходят в рукопожатии сами, или одноразовым билетом, полученным обычным запросом и переданным в адресе или первым сообщением. CORS на WebSocket не действует, поэтому сервер обязан проверять `Origin` в рукопожатии по белому списку.

#more
В проверке страница с другого сайта подключилась к серверу без проверки `Origin`, а сервер с белым списком её отклонил. Без проверки чужой сайт подключается с куками пользователя и действует от его имени. Билет делают короткоживущим и одноразовым, потому что адрес попадает в логи. Истечение сессии во время соединения сервер сообщает своим кодом закрытия.
::

::question
Как надёжно переподключаться?

#answer
Переподключаться с экспоненциально растущей задержкой и случайным разбросом, сбрасывать счётчик после успешного подключения, а после подключения догонять пропущенное: передавать номер последнего полученного события и отбрасывать дубли. Повисшие соединения находить сердцебиениями и тайм-аутами.

#more
В проверке клиент пережил два обрыва и получил все события ровно по разу. Без разброса после сбоя сервера все клиенты переподключаются одновременно и кладут его снова. Скрытые вкладки можно переподключать реже, а при возвращении `online` и `visibilitychange` — сразу.
::

## Практика

::practice{title="Седьмая вкладка не грузится"}
Магазин показывает уведомления через `new EventSource('/api/notifications')`. Пользователи, которые открывают много товаров во вкладках, жалуются: после нескольких вкладок новые страницы не загружаются, пока не закроешь старые. Сервер работает по HTTP/1.1. Почему и что сделать?

#solution
Каждая вкладка держит постоянное соединение SSE, а браузер открывает не больше шести соединений по HTTP/1.1 к одному хосту. Шесть вкладок заняли все, и запросы седьмой ждут. В проверке при шести открытых потоках `fetch` к тому же серверу не получил ответа, пока один поток не закрыли.

Решения, от простого к сложному:

- **HTTP/2 на сервере или CDN** — все потоки и запросы идут по одному соединению;
- **поток на отдельном поддомене** (`events.shop.example`) — свой лимит соединений, но это обход, а не решение;
- **один поток на все вкладки** — его держит одна вкладка, а события раздаются остальным:

```js
const channel = new BroadcastChannel('notifications');
navigator.locks.request('notifications-leader', () => new Promise(() => {
  // эта вкладка — ведущая, пока открыта
  const es = new EventSource('/api/notifications');
  es.onmessage = (e) => channel.postMessage(e.data);
}));
channel.onmessage = (e) => showNotification(e.data);
```

Замок Web Locks достаётся одной вкладке; когда её закрывают, замок переходит следующей, и она открывает поток. В проверке три вкладки держали один поток на сервере, все получали события, а после закрытия ведущей поток открыла следующая.
::

::practice{title="Сообщения пропадают после обрыва"}
Чат поддержки на WebSocket:

```js
function connect() {
  const ws = new WebSocket('wss://shop.example/support');
  ws.onmessage = (e) => appendMessage(JSON.parse(e.data));
  ws.onclose = () => setTimeout(connect, 1000);
}
```

Если пропадает мобильная сеть, часть сообщений оператора пользователь так и не видит. Почему и как исправить?

#solution
После переподключения сервер шлёт только новые сообщения, а пришедшие во время обрыва никто не досылает. Кроме того, задержка фиксированная: после сбоя сервера все клиенты придут одновременно.

```js
function connect(lastId = 0, attempt = 0) {
  const ws = new WebSocket(`wss://shop.example/support?after=${lastId}`);
  ws.onopen = () => { attempt = 0; };
  ws.onmessage = (e) => {
    const m = JSON.parse(e.data);
    if (m.id <= lastId) return;            // дубль
    lastId = m.id;
    appendMessage(m);
  };
  ws.onclose = () => {
    const delay = Math.min(30_000, 500 * 2 ** attempt) * (0.5 + Math.random() / 2);
    setTimeout(() => connect(lastId, attempt + 1), delay);
  };
}
```

Сервер по `after` досылает всё, что новее. Сообщениям нужны возрастающие номера, а серверу — хранить недавнюю историю. В проверке клиент пережил два обрыва и получил все семь событий ровно по одному разу.
::

::practice{title="Чат принимает сообщения с чужого сайта"}
Сервер чата на `ws`:

```js
const wss = new WebSocketServer({ server });
wss.on('connection', (ws, req) => {
  const user = sessionFromCookie(req.headers.cookie);
  ws.on('message', (data) => sendToOperator(user, data));
});
```

Аудит показал, что страница на любом сайте может открыть этот чат от имени залогиненного пользователя. Как исправить?

#solution
На WebSocket не действует CORS, а браузер прикладывает куки к рукопожатию. Чужая страница открывает соединение, сервер узнаёт пользователя по куке и принимает сообщения. В проверке страница с другого сайта подключилась к серверу без проверки.

Сервер проверяет `Origin` в рукопожатии по белому списку:

```js
const allowed = new Set(['https://shop.example']);
const wss = new WebSocketServer({
  server,
  verifyClient: ({ origin }) => allowed.has(origin),
});
```

В проверке сервер с таким списком отклонил рукопожатие с чужого сайта. Дополнительно сессионную куку ставят с `SameSite=Lax` или `Strict`, а для чувствительных действий требуют одноразовый билет, полученный обычным запросом со страницы своего сайта.
::
