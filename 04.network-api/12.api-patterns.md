# Паттерны API

Кроме ресурсов и методов, у любого живого API есть повторяющиеся задачи: отдать длинный список по частям, не создать заказ дважды при повторе, не дать клиенту перегрузить сервер, запустить операцию на минуты и загрузить большой файл. У каждой есть устоявшееся решение. Спрашивают, чем пагинация по смещению отличается от курсорной, что такое идемпотентность запроса и как обработать 429. Глубже — почему при прокрутке ленты товары повторяются, как ключ идемпотентности спасает от двойной оплаты и как получить результат операции, которая идёт десять минут.

::tldr
- **Пагинация по смещению (`offset`) проста, но ломается на изменяющихся данных** — записи повторяются или пропадают — и тормозит на дальних страницах. Курсорная пагинация продолжает «после последней записи» и стабильна.
- **Ключ идемпотентности делает POST безопасным для повтора:** клиент генерирует ключ на операцию, сервер запоминает ответ и на повтор с тем же ключом возвращает его, не выполняя действие снова.
- **Лимит частоты сервер сообщает ответом 429 и `Retry-After`;** клиент ждёт и сам сглаживает поток запросов — например, ведром токенов.
- **Долгая операция — `202 Accepted` с адресом статуса в `Location`:** клиент опрашивает его или ждёт события, а не держит запрос открытым.
- **Большие файлы загружают напрямую в хранилище по подписанной ссылке или частями с возобновлением,** а много мелких запросов собирают в один пакет.
::

## Пагинация

Сквозной пример — каталог чая с лентой новинок, оформление заказа с оплатой, выгрузка заказов в CSV и фото товаров.

Отдавать весь каталог одним ответом нельзя: десятки тысяч записей — это мегабайты JSON, секунды на сервере и в браузере. Список отдают **страницами**.

### По смещению

```text
GET /products?sort=-created&limit=20&offset=40
```

Сервер выполняет `ORDER BY created DESC LIMIT 20 OFFSET 40`. Просто, можно перейти на любую страницу и показать «страница 3 из 50». Но есть две проблемы.

**Данные сдвигаются.** Пока пользователь читает первую страницу ленты новинок, в каталог добавляют три товара. Вторая страница начинается на три позиции раньше, и последние три товара первой страницы показываются снова. Если товары удалили — наоборот, часть записей не попадёт ни на одну страницу. В проверке на SQLite ровно так: после добавления трёх записей вторая страница повторила три, а после удаления одна запись не попала никуда.

**Дальние страницы медленные.** `OFFSET 190000` заставляет базу найти и отбросить 190 000 строк. В проверке на 200 000 строк такой запрос был примерно в сто раз медленнее запроса «после записи 190 000».

### Курсорная

Курсорная пагинация (keyset) продолжает **после последней полученной записи**:

```text
GET /products?sort=-created&limit=20&after=eyJjcmVhdGVkIjoyMSwiaWQiOjIxfQ
```

```sql
SELECT * FROM products
WHERE (created, id) < (:created, :id)     -- после последней записи
ORDER BY created DESC, id DESC
LIMIT 20;
```

- **курсор — значения ключа сортировки последней записи** плюс уникальный `id`, чтобы различать записи с одинаковой датой;
- **для клиента курсор непрозрачен** — строка в Base64, которую он только передаёт обратно. Так сервер может поменять его устройство;
- **база идёт по индексу** сразу к нужному месту — в проверке план показал `SEARCH ... USING INDEX`, а не просмотр.

В проверке после добавления трёх товаров между страницами курсорная пагинация дала ровно следующие десять записей — без повторов и пропусков. Цена — нельзя прыгнуть на «страницу 37», только вперёд и назад. Для бесконечной ленты и подгрузки по прокрутке это и не нужно.

Ответ удобно строить так, чтобы клиенту не приходилось собирать адреса самому:

```json
{
  "items": [ ... ],
  "nextCursor": "eyJjcmVhdGVkIjoxMSwiaWQiOjExfQ",
  "hasMore": true
}
```

Общее число записей (`total`) — отдельный дорогой `COUNT`; часто его не отдают или считают приблизительно. Если число отдают в заголовке, его нужно открыть через `Access-Control-Expose-Headers` ([CORS](/content/network-api/cors)). Как виртуализировать длинный список на клиенте — в [Таблицах и гридах](/content/ecosystem-libs/tables-and-grids).

## Идемпотентность

Пользователь нажимает «Оплатить», запрос уходит, сервер создаёт заказ и списывает деньги — а ответ теряется в мобильной сети. Клиент не знает, прошёл ли запрос. Повторить — рискнуть двойной оплатой, не повторять — рискнуть потерянным заказом.

POST не идемпотентен ([HTTP](/content/network-api/http)), но его можно сделать таким **ключом идемпотентности**:

```js
const key = crypto.randomUUID();                 // один ключ на одну операцию, включая повторы
await request('/api/orders', {
  method: 'POST',
  headers: { 'content-type': 'application/json', 'idempotency-key': key },
  body: JSON.stringify(order),
});
```

Сервер хранит ключ вместе с ответом. Пришёл запрос с известным ключом — сервер возвращает сохранённый ответ и ничего не выполняет повторно. Тот же ключ с другим телом — ошибка: это не повтор, а ошибка клиента. В проверке повтор вернул тот же заказ с тем же статусом 201, второй заказ не создался, тот же ключ с другой корзиной получил 422, а новый ключ создал новый заказ.

Важные детали:

- **ключ создают один раз на действие пользователя** и переиспользуют во всех повторах — не на каждый запрос;
- **сервер записывает ключ атомарно с действием**, иначе два параллельных повтора всё равно пройдут оба;
- **ключи хранят ограниченное время** — сутки достаточно для повторов.

Так устроены API платёжных систем, и так фронтенд может безопасно применять повторы с растущей задержкой из [Запросов из браузера](/content/network-api/fetching).

## Лимиты частоты

Сервер защищает себя от слишком частых запросов: одного клиента, ключа API или IP. Превышение лимита — **`429 Too Many Requests`**, а заголовок **`Retry-After`** говорит, через сколько секунд можно снова. Часто сервер сообщает и остаток: `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`.

Распространённый алгоритм — **ведро токенов**: в ведре помещается N токенов, они пополняются с постоянной скоростью, каждый запрос забирает один. Это разрешает короткие всплески до N запросов, но ограничивает среднюю скорость. В проверке сервер с ведром на три токена и пополнением два в секунду пропустил три запроса подряд и на четвёртый ответил 429 с `Retry-After: 1`.

Клиент делает две вещи:

- **уважает `Retry-After`** — ждёт, а не повторяет сразу;
- **сам сглаживает поток** — тем же ведром токенов, `debounce` поиска или ограничением параллельных запросов.

```js
function tokenBucket(rate, burst) {
  let tokens = burst, last = Date.now();
  return async function take() {
    for (;;) {
      const now = Date.now();
      tokens = Math.min(burst, tokens + ((now - last) / 1000) * rate);
      last = now;
      if (tokens >= 1) { tokens -= 1; return; }
      await new Promise((r) => setTimeout(r, ((1 - tokens) / rate) * 1000));
    }
  };
}

const take = tokenBucket(1.8, 3);       // чуть медленнее лимита сервера
await take();
await fetch('/api/search?q=улун');
```

В проверке клиент с таким ведром отправил шесть запросов подряд, и ни один не получил 429. Ограничение параллельности и `debounce` — в [Асинхронности](/content/javascript/async) и [Паттернах](/content/javascript/patterns).

## Долгие операции

Выгрузка всех заказов в CSV занимает минуты. Держать HTTP-запрос открытым столько нельзя: его оборвут прокси, балансировщик или мобильная сеть. Вместо этого сервер **принимает задачу** и сразу отвечает:

```text
POST /exports
→ 202 Accepted
  Location: /exports/exp1
  { "id": "exp1", "status": "running" }
```

Клиент узнаёт результат одним из способов:

- **опрашивает** адрес из `Location` с паузами, пока статус не станет `done` или `failed`. В проверке опрос каждые 50 мс дождался `done` со ссылкой на файл;
- **ждёт события** — SSE или WebSocket присылает «выгрузка готова» ([Реальное время](/content/network-api/realtime));
- **получает уведомление** по почте или пушем, если пользователь мог уйти со страницы.

Задача живёт на сервере независимо от вкладки, поэтому пользователь может закрыть страницу и вернуться — статус по адресу сохранится.

## Загрузка файлов

Фото к отзыву или прайс-лист поставщика — это мегабайты, а иногда и гигабайты:

- **`multipart/form-data` на свой сервер** — просто, подходит для небольших файлов. Сервер принимает весь файл через себя ([Запросы из браузера](/content/network-api/fetching));
- **подписанная ссылка** — сервер выдаёт короткоживущий адрес в объектное хранилище (S3 и подобные), браузер загружает файл прямо туда, минуя бэкенд, а потом сообщает серверу, что загрузка закончена. Сервер не тратит на файл ни памяти, ни канала;
- **загрузка частями с возобновлением** — файл режется на части по несколько мегабайт, каждая загружается отдельно и повторяется при ошибке; после обрыва загрузка продолжается с последней принятой части. Для больших файлов и плохих сетей — протоколы tus, multipart upload в S3.

Проверять тип и размер файла нужно на сервере: атрибут `accept` у поля и проверка на клиенте — только удобство.

## Пакетные запросы

Каталог из 20 карточек, и каждая сама загружает свой товар — 20 запросов. Даже при HTTP/2 у каждого своя обработка на сервере и свой круг. Решение — **пакетирование**: собрать запросы, сделанные в одном тике, и отправить один:

```js
function batcher(load) {
  let pending = null;
  return (id) => {
    if (!pending) {
      pending = { ids: [], promise: null };
      pending.promise = new Promise((resolve) => queueMicrotask(async () => {
        const batch = pending;
        pending = null;
        resolve(await load(batch.ids));
      }));
    }
    pending.ids.push(id);
    return pending.promise.then((items) => items.find((x) => x.id === String(id)));
  };
}

const getProduct = batcher((ids) => fetch(`/api/products?ids=${ids.join(',')}`).then((r) => r.json()));
```

В проверке десять одновременных `getProduct` дали один запрос к серверу. Это та же идея, что DataLoader в [GraphQL](/content/network-api/graphql). Если экрану нужны данные из нескольких сервисов, их собирает BFF ([API и BFF](/content/architecture/api-and-bff)).

## Красные флаги в ответе

- **«`offset` — нормальная пагинация для ленты».** На изменяющихся данных записи повторяются и пропадают, а дальние страницы медленные.
- **«Повторим POST после обрыва — сервер разберётся».** Без ключа идемпотентности повтор создаст второй заказ или вторую оплату.
- **«Ключ идемпотентности генерирую на каждый запрос».** Тогда повтор — новый ключ, и защиты нет; ключ — на действие.
- **«На 429 повторяю сразу».** Сервер сказал, когда вернуться, — `Retry-After`; немедленный повтор только продлевает блокировку.
- **«Выгрузку сделаем одним запросом, просто поставим большой тайм-аут».** Прокси и сеть оборвут его; нужен 202 и статус.
- **«Файлы гоним через бэкенд».** Для больших файлов — подписанные ссылки и загрузка частями.

## Как спрашивают на собеседовании

::question
Чем пагинация по смещению отличается от курсорной?

#answer
По смещению сервер пропускает `offset` записей и отдаёт `limit` следующих — можно прыгнуть на любую страницу, но если данные меняются между запросами, записи повторяются или пропадают, а дальние страницы медленные. Курсорная продолжает после последней полученной записи по значению ключа сортировки — стабильна при изменениях и быстра по индексу, но позволяет идти только вперёд и назад.

#more
В проверке после добавления трёх товаров страница по смещению повторила три записи, а курсорная — нет; `OFFSET 190000` был примерно в сто раз медленнее поиска по ключу. Курсор включает уникальный `id`, чтобы различать записи с одинаковым значением сортировки, и отдаётся клиенту непрозрачной строкой. Смещение оставляют для админок с номерами страниц и небольших таблиц.
::

::question
Что такое ключ идемпотентности и зачем он нужен?

#answer
Уникальный ключ, который клиент генерирует на одно действие и отправляет в заголовке `Idempotency-Key` со всеми повторами. Сервер запоминает ключ и ответ; запрос с известным ключом получает сохранённый ответ без повторного выполнения. Так POST — оплату, создание заказа — можно безопасно повторить после обрыва.

#more
В проверке повтор вернул тот же заказ и второй не создал, а тот же ключ с другим телом получил 422. Ключ создают при нажатии кнопки, а не при каждом запросе. Сервер должен записывать ключ в одной транзакции с действием, иначе два параллельных повтора пройдут оба. Ключи хранят ограниченное время.
::

::question
Как обрабатывать лимиты частоты?

#answer
Сервер отвечает 429 и сообщает в `Retry-After`, когда можно снова; клиент ждёт это время, а не повторяет сразу. Заранее клиент сглаживает поток сам: `debounce` поиска, ограничение параллельных запросов, ведро токенов чуть медленнее лимита сервера.

#more
Ведро токенов разрешает короткие всплески и ограничивает среднюю скорость: в проверке сервер с ведром на три токена пропустил три запроса подряд, а четвёртому ответил 429 с `Retry-After: 1`. Заголовки `RateLimit-*` показывают остаток заранее. Для фоновых запросов повторы после 429 делают с растущей задержкой и разбросом.
::

::question
Как организовать операцию, которая длится минуты?

#answer
Сервер принимает задачу и сразу отвечает `202 Accepted` с адресом статуса в `Location`. Клиент опрашивает этот адрес с паузами или получает событие по SSE или WebSocket, а когда задача готова — забирает результат по ссылке. HTTP-запрос не держат открытым всё это время.

#more
Задача живёт на сервере, поэтому пользователь может уйти и вернуться. Опрос делают с растущим интервалом и прекращают при `failed`. Для отмены есть `DELETE` на адрес задачи. Повторный запуск той же выгрузки защищают ключом идемпотентности, чтобы двойной клик не запустил две задачи.
::

::question
Как загружать большие файлы?

#answer
Небольшие — `multipart/form-data` на свой сервер. Большие — напрямую в объектное хранилище по подписанной ссылке, которую выдаёт сервер, чтобы файл не шёл через бэкенд. Очень большие и на плохой сети — частями с возобновлением: каждая часть загружается и повторяется отдельно, а после обрыва загрузка продолжается.

#more
Прогресс загрузки показывают через `XMLHttpRequest`, потому что у `fetch` нет события прогресса отправки. Подписанная ссылка живёт минуты и разрешает только одну операцию с одним файлом. Тип, размер и содержимое файла проверяет сервер: клиентские проверки обходятся.
::

## Практика

::practice{title="Товары повторяются в ленте"}
Бесконечная лента новинок подгружает страницы так:

```js
let page = 0;
async function loadMore() {
  const items = await api(`/products?sort=-created&limit=20&offset=${page * 20}`);
  page++;
  appendToFeed(items);
}
```

В часы, когда менеджеры добавляют товары, пользователи видят в ленте дубли, а React ругается на одинаковые ключи. Почему и как исправить?

#solution
Новые товары появляются в начале списка, и всё сдвигается вниз. Следующая страница по смещению начинается раньше, чем кончилась предыдущая, и повторяет записи. В проверке после добавления трёх товаров вторая страница повторила три последние записи первой.

Курсорная пагинация продолжает после последней полученной записи:

```js
let cursor = null;
async function loadMore() {
  const url = `/products?sort=-created&limit=20${cursor ? `&after=${cursor}` : ''}`;
  const { items, nextCursor, hasMore } = await api(url);
  cursor = nextCursor;
  appendToFeed(items);
  return hasMore;
}
```

```sql
SELECT * FROM products
WHERE (created, id) < (:created, :id)
ORDER BY created DESC, id DESC
LIMIT 20;
```

В проверке курсорная пагинация после тех же изменений дала следующие записи без повторов. Индекс по `(created DESC, id DESC)` делает запрос быстрым на любой глубине.
::

::practice{title="Двойная оплата"}
```js
async function pay(order) {
  for (let attempt = 0; attempt < 3; attempt++) {
    try {
      return await api('/api/payments', { method: 'POST', body: JSON.stringify(order) });
    } catch {
      await sleep(1000);
    }
  }
}
```

В поддержку пишут о двойных списаниях на мобильном интернете. Почему и как исправить?

#solution
Если сервер принял оплату, а ответ потерялся, клиент получает ошибку и повторяет POST — сервер видит новую оплату и списывает снова. Повтор неидемпотентного запроса без защиты.

Ключ идемпотентности, один на всю операцию:

```js
async function pay(order) {
  const key = crypto.randomUUID();                       // до цикла: общий для всех повторов
  for (let attempt = 0; ; attempt++) {
    try {
      return await api('/api/payments', {
        method: 'POST',
        headers: { 'content-type': 'application/json', 'idempotency-key': key },
        body: JSON.stringify(order),
      });
    } catch (e) {
      if (attempt >= 2 || (e.status && e.status < 500 && e.status !== 429)) throw e;
      await sleep(Math.random() * 500 * 2 ** attempt);
    }
  }
}
```

Сервер на повтор с тем же ключом возвращает сохранённый ответ, а не списывает снова. В проверке повтор вернул тот же заказ, и второй не создался. Ошибки 4xx не повторяются, а пауза растёт с разбросом.
::

::practice{title="Двадцать запросов на одну страницу"}
Каждая карточка в списке «Вы смотрели» загружает свой товар:

```js
function ProductCard({ id }) {
  const product = useProduct(id); // внутри — fetch(`/api/products/${id}`)
  ...
}
```

На странице 20 карточек — 20 запросов. Как сократить до одного, не меняя компоненты?

#solution
Пакетировать: запросы, сделанные в одном тике, собрать и отправить одним вызовом с несколькими `id`, а результат раздать вызывающим.

```js
function batcher(load) {
  let pending = null;
  return (id) => {
    if (!pending) {
      pending = { ids: [], promise: null };
      pending.promise = new Promise((resolve) => queueMicrotask(async () => {
        const batch = pending;
        pending = null;
        resolve(await load(batch.ids));
      }));
    }
    pending.ids.push(id);
    return pending.promise.then((items) => items.find((x) => x.id === String(id)));
  };
}

const getProduct = batcher((ids) => fetch(`/api/products?ids=${ids.join(',')}`).then((r) => r.json()));
// useProduct внутри вызывает getProduct(id)
```

В проверке десять одновременных вызовов дали один запрос. Серверу нужен эндпоинт, который принимает список `id`. Если компоненты рендерятся не в одном тике, окно собирания делают чуть шире — несколько миллисекунд через `setTimeout`.
::
