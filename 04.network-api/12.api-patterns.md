# Паттерны работы с API

Когда ты уже знаешь [REST](/content/network-api/rest), [GraphQL](/content/network-api/graphql) и [fetch](/content/network-api/fetching), встаёт вопрос: как организовать работу с API в реальном приложении? Версионирование, пагинация, оптимистичные обновления, обработка ошибок, абстракция сетевого слоя - именно эти паттерны спрашивают на собеседованиях.

---

## Версионирование API

<b class="text-on-semi-light">Как менять API, не ломая старых клиентов</b>

<span class="text-gray">Когда API эволюционирует, нужен способ поддерживать старые версии для существующих клиентов и предоставлять новый функционал. Есть три основных подхода.</span>

| Подход          | Пример                                | Плюсы                                          | Минусы                            |
| --------------- | ------------------------------------- | ---------------------------------------------- | --------------------------------- |
| **URL path**    | `/api/v1/users`                       | Наглядно, легко кэшировать, легко проксировать | URL меняется, дублирование роутов |
| **Header**      | `Accept: application/vnd.api.v2+json` | URL стабильный, чистый дизайн                  | Сложнее дебажить, не видно в URL  |
| **Query param** | `/api/users?version=2`                | Просто добавить                                | Плохо кэшируется, не REST-way     |

<span class="text-gray">На практике **URL path** (`/v1/`, `/v2/`) - самый распространённый подход. Его проще всего понять, задокументировать и поддерживать. Header-based версионирование чаще встречается в enterprise API.</span>

> Как фронтендер, ты чаще **используешь** версионированные API, чем проектируешь их. Но понимание подходов помогает в код-ревью и при обсуждении контрактов с бэкендом.

## Пагинация

<b class="text-on-semi-light">Как получать большие списки данных по частям</b>

<span class="text-gray">Возвращать все 100 000 записей в одном ответе - плохая идея. Пагинация разбивает данные на страницы. Три основных подхода отличаются по надёжности и сложности.</span>

### Offset-based

```text
GET /api/users?offset=20&limit=10
```

<span class="text-gray">Самый простой подход. Сервер пропускает `offset` записей и возвращает `limit` следующих.</span>

### Cursor-based

```text
GET /api/users?cursor=eyJpZCI6NDJ9&limit=10
```

<span class="text-gray">Клиент получает `nextCursor` из предыдущего ответа. Cursor - непрозрачный токен (обычно base64-encoded ID/timestamp). Сервер начинает выборку с позиции курсора.</span>

### Keyset (seek-based)

```text
GET /api/users?after_id=42&limit=10
```

<span class="text-gray">Как cursor, но ключ видимый - `after_id=42` означает «записи после ID 42». Работает по индексу БД.</span>

### Сравнение

| Подход     | Jump to page | Вставки/удаления             | Производительность      | Сложность |
| ---------- | ------------ | ---------------------------- | ----------------------- | --------- |
| **Offset** | Да           | Пропуск/дубли при изменениях | O(offset) - деградирует | Простая   |
| **Cursor** | Нет          | Стабильная                   | O(1)                    | Средняя   |
| **Keyset** | Нет          | Стабильная                   | O(1)                    | Средняя   |

<span class="text-gray">Offset подходит для админок и небольших списков. Для infinite scroll, лент и чатов - используй cursor-based пагинацию: она не ломается при добавлении/удалении записей.</span>

```js
// Пример: загрузка страниц с cursor-based пагинацией
async function loadPage(cursor = null) {
  const url = cursor
    ? `/api/posts?cursor=${cursor}&limit=20`
    : "/api/posts?limit=20";

  const res = await fetch(url);
  const { data, nextCursor } = await res.json();

  renderPosts(data);

  if (nextCursor) {
    loadMoreBtn.onclick = () => loadPage(nextCursor);
  } else {
    loadMoreBtn.disabled = true;
  }
}
```

## Rate Limiting на клиенте

<b class="text-on-semi-light">Debounce и throttle для запросов к API</b>

<span class="text-gray">Пользователь печатает в поле поиска - не нужно отправлять запрос на каждый символ. Debounce и throttle ограничивают частоту вызовов.</span>

<b class="text-on-semi-light">Debounce</b> - вызывает функцию только после паузы (пользователь перестал печатать).

```js
function debounce(fn, delay) {
  let timerId;
  return (...args) => {
    clearTimeout(timerId);
    timerId = setTimeout(() => fn(...args), delay);
  };
}

const searchInput = document.querySelector("#search");
const debouncedSearch = debounce(async (query) => {
  const res = await fetch(`/api/search?q=${encodeURIComponent(query)}`);
  const results = await res.json();
  renderResults(results);
}, 300);

searchInput.addEventListener("input", (e) => debouncedSearch(e.target.value));
```

<b class="text-on-semi-light">Throttle</b> - вызывает функцию не чаще, чем раз в N миллисекунд.

```js
function throttle(fn, limit) {
  let lastCall = 0;
  return (...args) => {
    const now = Date.now();
    if (now - lastCall >= limit) {
      lastCall = now;
      fn(...args);
    }
  };
}

// Throttle запросов аналитики при скролле
const throttledTrack = throttle((pos) => {
  fetch("/api/analytics", {
    method: "POST",
    body: JSON.stringify({ scrollPosition: pos }),
  });
}, 2000);
```

| Приём        | Когда срабатывает | Use case                        |
| ------------ | ----------------- | ------------------------------- |
| **Debounce** | После паузы       | Поисковый input, автосохранение |
| **Throttle** | Не чаще N мс      | Scroll-трекинг, resize, drag    |

## Optimistic Updates

<b class="text-on-semi-light">Обновляй UI до ответа сервера</b>

<span class="text-gray">Optimistic update - UX-паттерн, при котором ты обновляешь интерфейс **сразу**, не дожидаясь подтверждения от сервера. Если запрос провалится - откатываешь изменение. Пользователь чувствует, что приложение работает мгновенно.</span>

Типичные сценарии: лайк, добавление в избранное, удаление элемента из списка, отправка сообщения в чат.

```js
async function toggleLike(postId) {
  // 1. Запоминаем текущее состояние (для отката)
  const previousState = getPostState(postId);

  // 2. Оптимистично обновляем UI
  updatePostUI(postId, { liked: !previousState.liked });

  try {
    // 3. Отправляем запрос
    await fetch(`/api/posts/${postId}/like`, { method: "POST" });
  } catch (err) {
    // 4. При ошибке - откатываем
    updatePostUI(postId, previousState);
    showError("Не удалось обновить. Попробуй ещё раз.");
  }
}
```

<span class="text-gray">В React Query / TanStack Query есть встроенная поддержка optimistic updates через `onMutate` и `onError` callbacks. В Redux Toolkit - через dispatch + revert action.</span>

> Паттерн optimistic updates тесно связан с обработкой ошибок - без хорошего error handling откат будет незаметен для пользователя.

## Error Handling

<b class="text-on-semi-light">Централизованная обработка сетевых ошибок</b>

<span class="text-gray">Обрабатывать ошибки в каждом `fetch`-вызове - утомительно и приводит к дублированию. Лучше выстроить стратегию на уровне API-слоя.</span>

### Типы ошибок

| Тип               | Пример                     | Как обрабатывать                               |
| ----------------- | -------------------------- | ---------------------------------------------- |
| **Network error** | Нет интернета, DNS-ошибка  | Retry + показать «нет связи»                   |
| **Timeout**       | Сервер не ответил за N сек | Retry с backoff                                |
| **4xx**           | 400, 401, 403, 404, 422    | Показать пользователю (валидация, нет доступа) |
| **5xx**           | 500, 502, 503              | Retry + «Попробуйте позже»                     |

### Пример: централизованный error handler

```js
async function apiRequest(url, options = {}) {
  const res = await fetch(url, options);

  if (!res.ok) {
    const error = new Error(`HTTP ${res.status}`);
    error.status = res.status;

    try {
      error.data = await res.json();
    } catch {}

    // Централизованная обработка
    if (res.status === 401) {
      redirectToLogin();
      return;
    }

    throw error;
  }

  return res.json();
}
```

<span class="text-gray">Error boundaries (в React) перехватывают ошибки рендеринга, но **не ловят** ошибки в async-коде. Для сетевых ошибок используй try/catch в API-слое или onError-callbacks в React Query.</span>

## API-слой в приложении

<b class="text-on-semi-light">Абстракция поверх fetch</b>

<span class="text-gray">Вместо вызова `fetch` напрямую из компонентов создай API-клиент. Он инкапсулирует базовый URL, заголовки, обработку ошибок и retry-логику.</span>

```js
class ApiClient {
  constructor(baseURL) {
    this.baseURL = baseURL;
  }

  async request(endpoint, options = {}) {
    const config = {
      headers: { "Content-Type": "application/json", ...options.headers },
      ...options,
    };

    // Interceptor: auth header
    const token = getAuthToken();
    if (token) config.headers["Authorization"] = `Bearer ${token}`;

    const res = await fetch(`${this.baseURL}${endpoint}`, config);

    // Interceptor: обработка 401 - refresh и retry
    if (res.status === 401) {
      await refreshToken();
      return this.request(endpoint, options);
    }

    if (!res.ok) {
      const error = new Error(`API Error: ${res.status}`);
      error.status = res.status;
      try {
        error.data = await res.json();
      } catch {}
      throw error;
    }

    return res.json();
  }

  get(endpoint) {
    return this.request(endpoint);
  }

  post(endpoint, data) {
    return this.request(endpoint, {
      method: "POST",
      body: JSON.stringify(data),
    });
  }
}

const api = new ApiClient("https://api.example.com");
const users = await api.get("/users");
await api.post("/users", { name: "Alex" });
```

<b class="text-on-semi-light">Retry Logic</b>

<span class="text-gray">Для нестабильных сетей и 5xx ошибок добавляй автоматические повторные попытки с exponential backoff.</span>

```js
async function fetchWithRetry(url, options = {}, retries = 3) {
  for (let i = 0; i < retries; i++) {
    try {
      const res = await fetch(url, options);
      if (res.ok || res.status < 500) return res; // не ретраим 4xx
    } catch (err) {
      if (i === retries - 1) throw err;
    }
    await new Promise((r) => setTimeout(r, 1000 * 2 ** i)); // exponential backoff
  }
}
```

## OpenAPI / Swagger

<b class="text-on-semi-light">Машиночитаемое описание API</b>

<span class="text-gray">OpenAPI (ранее Swagger) - спецификация для описания REST API в формате JSON/YAML. Для фронтендера это не абстрактный стандарт, а практический инструмент.</span>

Что это даёт фронтендеру:

- **Codegen** - автоматическая генерация API-клиента и TypeScript-типов из спецификации
- **Документация** - Swagger UI для интерактивного просмотра эндпоинтов
- **Валидация** - проверка запросов/ответов по схеме на этапе разработки
- **Contract-first** - бэкенд и фронтенд договариваются о контракте до начала разработки

```text
# Генерация TypeScript-клиента из OpenAPI-спецификации
npx openapi-typescript https://api.example.com/openapi.json -o ./src/api/schema.d.ts

# Генерация полного клиента
npx @openapitools/openapi-generator-cli generate \
  -i https://api.example.com/openapi.json \
  -g typescript-fetch \
  -o ./src/api/generated
```

<span class="text-gray">Популярные инструменты: **openapi-typescript** (только типы), **orval** (клиент + React Query хуки), **openapi-generator** (полные клиенты для любого стека).</span>

## Типичные вопросы на собеседовании

> **Как реализовать пагинацию для бесконечного скролла?**
> Cursor-based пагинация. Сервер возвращает `nextCursor` вместе с данными. При скролле к низу списка (IntersectionObserver) загружаешь следующую страницу с курсором. Offset-based не подходит - вставки/удаления ломают порядок.

> **Что такое optimistic update и когда его использовать?**
> Обновляешь UI до ответа сервера, при ошибке откатываешь. Используй для действий с высокой вероятностью успеха (лайк, добавление в корзину). Не используй для критических операций (оплата, удаление аккаунта).

> **Зачем нужен API-слой?**
> Единое место для базового URL, auth-заголовков, обработки ошибок, retry и логирования. Компоненты не знают про fetch - они вызывают `api.getUsers()`. Легче тестировать, рефакторить и менять имплементацию.
