# Стандарт глав Frontend Legends

Frontend Legends — справочник для подготовки к фронтенд-собеседованиям. Он один для всех уровней: материал не делится на «для mid» и «для senior». Каждая глава — это рассказ о теме, к которому возвращаются перед собесом: что спросят, почему оно так работает и где на этом ошибаются в проде.

Эталон, на который равняться: [`07.javascript/1.introduction.md`](07.javascript/1.introduction.md).

---

## Структура главы

Разделы идут в этом порядке:

1. **Frontmatter** — см. ниже.
2. **`# Заголовок`** на русском.
3. **Вводный абзац** — 2–3 предложения: о чём глава и что на эту тему спрашивают.
4. **`::tldr`** — 4–5 пунктов. Каждый пункт — самостоятельный факт, который можно сказать на собесе. Без номеров версий.
5. **Основной рассказ** — разделы `##`, см. «Рассказ, а не набор разделов».
6. **`## Красные флаги в ответе`** — 4–6 фраз, после которых интервьюер начинает копать, и почему они неверны.
7. **`## Как спрашивают на собеседовании`** — 5–7 блоков `::question`. Порядок вопросов совпадает с порядком рассказа.
8. **`## Практика`** — 2–3 блока `::practice`: «что выведет», «найди баг», «почему тормозит».
9. **`## Полезные ссылки`** — 5–8 ссылок: сначала соседние главы книги, потом спецификации и первоисточники.

Между крупными разделами ставится `---`.

### Frontmatter

```yaml
---
title: "Introduction"     # на английском, как у всех глав: это название на карте и в навигации
date: 2026-11-14          # дата последнего изменения текста
reviewed: 2026-11-14      # дата проверки по этому стандарту (факты, код, ссылки)
order: 7.01               # номер главы . номер темы — от него зависит навигация
---
```

`order` у страницы главы — целое число (`7`), у тем — с двумя знаками (`7.01`, `7.16`).

### Страница главы (`0.index.md`)

Короткая страница-вход в главу, без компонентов:

1. `# Название главы` и абзац: о чём глава и почему её спрашивают на собеседовании.
2. `## Что спрашивают` — 4–6 пунктов, сгруппированных по темам (основа, механика, архитектура), а не по уровням.
3. `## Темы главы` — нумерованный список всех тем по порядку: ссылка и одна фраза о том, что в теме. Список совпадает с реальными файлами главы.
4. `## С чем связано` — 2–4 ссылки на соседние главы книги, на которые глава опирается.

Страница главы переписывается последней, когда темы уже готовы.

### Облегчённый шаблон: главы 18 и 20

Главы про карьеру и подготовку к собеседованиям. Нужны вводный абзац, `::tldr`, рассказ и `## Полезные ссылки`. Разделы «Красные флаги в ответе», «Как спрашивают на собеседовании» и «Практика» необязательны: ставь их, только если они естественны для темы (например, вопросы HR-скрининга). Проверочного кода нет.

### Шаблон главы 02: алгоритмы

Глава 02 разбирает задачи списка LeetCode Top Interview 150 по категориям: одна тема — одна категория (два указателя, скользящее окно, стек, деревья…). Темы 1–3 (структуры данных, сортировка, поиск) и 27 (прочие техники и как решать задачи) — общие, по обычному стандарту.

Тема-категория устроена так:

1. **Вводный абзац** и **`::tldr`** — как и везде.
2. **`## Как узнать паттерн`** — признаки в условии, по которым видно, что задача на эту технику.
3. **`## Шаблон`** — общий код техники на TypeScript и его сложность. Дальше — разделы о вариантах и ловушках, если нужны.
4. **`## Задачи`** — таблица задач категории (задача, идея, время, память), потом каждая задача — блок `::practice{title="88. Merge Sorted Array"}`: условие своими словами (тексты LeetCode не копируем) и ссылка на задачу. В `#solution` — идея, код на TypeScript, сложность и частые ошибки. Решение свёрнуто: читатель сначала решает сам.
5. **`## Красные флаги в ответе`**, **`## Как спрашивают на собеседовании`** (3–5 `::question`) и **`## Полезные ссылки`**.

Каждое решение лежит в `codes/02.algorithms-data-structures/<тема>/` и проверяется на примерах из условия и на случайных данных против решения перебором. Код решения в тексте совпадает с кодом в `codes/` — это проверяет `codes/02.algorithms-data-structures/sync.mjs`.

## Рассказ, а не набор разделов

Глава читается сверху вниз как одна история. Признак набора разделов: их можно переставить, и ничего не сломается. Так быть не должно.

- **Первый раздел — главный вопрос темы.** Обычно это частый вопрос собеса («Что такое JavaScript?»), и сразу разбор.
- **Каждый следующий раздел отвечает на вопрос, который возник в конце предыдущего.** Последний абзац раздела — короткий переход: «Файл загружен, режим выбран — теперь код выполняет движок».
- **Сквозной пример.** Небольшой фрагмент кода в начале, к которому рассказ возвращается в следующих разделах.
- **Глубина остаётся в тексте.** Подробности — обычные подразделы `###`. Не прячь материал в свёрнутые блоки и не дели текст по уровням: никаких «на mid спрашивают», «для senior», «вопрос на senior». Линтер это ловит.
- **Одно понятие — одно слово.** Выбери термин и держись его по всей главе. Например, «окружение», а не попеременно «хост», «среда» и «платформа». Английский термин из спецификации дай один раз при первом упоминании.

## Одна тема — одна глава

Книга не повторяет сама себя. У каждой темы есть «дом» — глава, где она разобрана полностью.

Перед тем как писать про понятие, найди, где оно уже разобрано: в [`TOPICS.md`](TOPICS.md) (заголовки всех глав) и поиском по тексту.

```bash
grep -rli "event loop" --include="*.md" .
```

Пересекаться темам можно, пересказывать — нельзя:

- **Можно — тот же предмет с другой стороны.** Например, `fetch` в главе про сеть (HTTP, CORS, кеш) и в главе про React (гонки запросов в эффекте). Каждая глава говорит о своём.
- **Можно — коротко и со ссылкой.** Два-три предложения: что это и почему важно здесь, плюс ссылка туда, где разобрано подробно. Как в 7.01: «Event loop — тоже не часть языка: в ECMAScript есть только задачи (jobs) и точки, через которые окружение ставит их в очередь. Сам цикл описан в HTML-спецификации (браузер) и в libuv (Node.js). Подробно — в [Event Loop](/content/javascript/event-loop).»
- **Нельзя — второй полный разбор:** те же примеры, те же таблицы, тот же порядок объяснения. Если тема разобрана в двух местах, она остаётся в той главе, которой ближе по смыслу, а во второй — короткий контекст и ссылка.

## Компоненты

### `::tldr` — главное за 30 секунд

```md
::tldr
- **JavaScript = язык (ECMAScript) + окружение.** `fetch` и `setTimeout` — API окружения.
- **Модули всегда работают в strict mode.**
::
```

### `::question` — вопрос с собеседования

Ответ свёрнут: читатель сначала отвечает сам. Ответы не делятся по уровням: `#answer` — хороший ответ, `#more` — что к нему добавить.

```md
::question
JavaScript однопоточный? А как же воркеры?

#answer
Хороший ответ: 2–3 предложения, которые закрывают вопрос.

#more
Что добавить: механизм, компромиссы, грабли. Не пересказывай текст главы — добавь то, чего в хорошем ответе нет.

#followups
- «Уточняющий вопрос» → короткий ответ
::
```

### `::practice` — задача

```md
::practice{title="Что выведет?"}
Условие и код.

#solution
Ответ, объяснение и **исправленный код**: решения пишутся с кодом, не только словами.
::
```

### `::pitfall` — грабли в проде

Реальная ошибка из продакшена, а не «можно ошибиться».

```md
::pitfall{title="Короткое имя бага"}
#symptom
Что видно: ошибка в Sentry, поведение, жалоба пользователя.
#cause
Почему так происходит.
#fix
Как чинить и как не надо.
::
```

### `:term` — термин с определением

Для слов, которые читатель может не знать: определение показывается тултипом при наведении или тапе. Ставится на **первое** упоминание в главе. Определение — одна короткая фраза, без ссылок и кода.

```md
Движки :term[V8]{def="движок JavaScript от Google: Chrome, Edge, Node.js, Deno"} и :term[JavaScriptCore]{def="движок JavaScript от Apple: Safari и Bun"} …
```

Внутри `def` не используй двойные кавычки.

### Обычный markdown

- **Код** — блок с языком: ` ```js `, ` ```jsx `, ` ```ts `. Вывод, логи, ошибки и ASCII-схемы — ` ```text ` (в них нет номеров строк, длинные строки переносятся).
- **Таблицы** — для сравнений «X против Y» и списков свойств. Не больше 4 колонок.
- **Цитата `>`** — заметка или ссылка на соседнюю главу, а не цитата.
- **Термин с пояснением в списке** — `- **Термин** — пояснение.`

## Стиль

- **Без HTML-тегов.** Никаких `<b class="…">`, `<span class="…">`: только markdown и компоненты. Старые главы с тегами при переработке переводятся на markdown.
- **Тире** — длинное с пробелами « — », не дефис « - ». Кавычки — «ёлочки», в коде — как в коде.
- **Короткие предложения**, активный залог, без воды. Обращение на «ты».
- **Версии и даты** — только там, где они нужны по смыслу: в таблице эволюции, с пометкой «актуально на ноябрь 2026». В TL;DR и ответах на вопросы номеров версий нет.
- **Факты** — только проверенные. Не уверен — не пиши, либо найди первоисточник: спецификацию, документацию, исходники.
- **Эмодзи** не используются, в том числе в комментариях к коду.

## Код проверяется

Каждый пример, у которого есть вывод или поведение, запускается. Скрипты лежат в `codes/` в той же структуре, что главы:

```
codes/07.javascript/1.introduction/races.mjs
```

- Скрипт проверяет значения из текста через `node:assert`, а не просто печатает.
- Первые строки — комментарий: какую часть главы проверяет и как запустить. Нужные флаги node — строкой `// flags: --allow-natives-syntax`.
- Запуск всего: `cd codes && npm install && npm test`, одной главы: `node run.mjs 07.javascript/1.introduction`.

Чем проверять, в зависимости от того, что утверждает текст:

| Утверждение | Файл | Как |
| --- | --- | --- |
| Поведение JS, Node.js | `.mjs` / `.cjs` | `node:assert` на значения из текста |
| TypeScript: «это скомпилируется», «здесь ошибка типов» | `.ts` / `.tsx` | `tsc` в строгом режиме проверяет каждый файл; ожидаемая ошибка — строка с `// @ts-expect-error`. Только типы, без запуска — `// types-only` в заголовке |
| React | `.tsx` / `.jsx` / `.cjs` | `react-dom/server` или `react-dom/client` + jsdom; `act` для эффектов |
| Vue | `.mjs` | `vue` (с компилятором шаблонов), `vue/server-renderer`, jsdom |
| Типы во Vue: `.vue`, шаблоны, макросы | `.mjs` + `.vue` | `vue-tsc` в изолированном проекте `_vue/` со своим `package.json` и TypeScript 6 (у TypeScript 7 нет API для `vue-tsc`); ожидаемая ошибка в шаблоне — `<!-- @vue-expect-error -->`. Пример — `codes/08.typescript/12.ts-with-vue/` |
| Ошибка конфигурации, кода ошибки, флаги tsconfig | `.mjs` | временный проект + `tsc -p`, сверка кодов `TSxxxx`; чистое браузерное окружение без типов Node — `tsc --ignoreConfig --lib dom` |
| DOM, события, CSS, раскладка | `.mjs` | `withPage` из `codes/_lib/browser.mjs`: настоящий Chromium, `getComputedStyle`, `getBoundingClientRect` |

Утверждения, которые кодом не проверить (архитектура, история, «как принято»), проверяются по первоисточникам: спецификации, документации, исходникам.

## Проверки

```bash
node tools/lint.mjs 07.javascript/2.types    # структура, разметка, внутренние ссылки — одна тема
node tools/lint.mjs                          # все темы с `reviewed`
node tools/lint.mjs --report                 # сводка по всей книге
node tools/links.mjs 07.javascript           # внешние ссылки (нужна сеть)
node tools/topics.mjs                        # пересобрать TOPICS.md
cd codes && node run.mjs 07.javascript/2     # проверочный код темы
```

`lint.mjs` проверяет то, что можно проверить без чтения смысла:
- frontmatter, порядок разделов, количество пунктов TL;DR, вопросов и задач;
- незакрытые `::` и неизвестные компоненты и слоты;
- HTML-теги, эмодзи, дефис вместо тире, блоки кода без языка;
- внутренние ссылки и `:term` без определения;
- объём рассказа и наличие папки в `codes/`.

Ошибки (`error`) нужно исправить; предупреждения (`warn`) — повод перечитать. Рассказ, точность и повторы линтер не видит — за них отвечает автор.

CI (`.github/workflows/check.yml`) прогоняет `lint.mjs` и `codes/` на каждой ветке и PR. В `main` напрямую не пушим: пуш в `main` сразу деплоит сайт.
