# Селекторы и at-rules

Селектор решает, к каким элементам относится правило, а at-rules — при каких условиях и в какой группе оно действует. Спрашивают, чем `:is()` отличается от `:where()`, что умеет `:has()`, зачем `:focus-visible` и почему псевдоэлементу нужен `content`. Глубже — почему браузер читает селектор справа налево, почему одна строка с `::-moz-` в списке выключает всё правило в Chrome и как `@scope` решает спор вложенных тем.

::tldr
- **Браузер сопоставляет селектор справа налево:** берёт крайнюю правую часть и только для подошедших элементов проверяет предков. `.nav a` проверяется на каждой ссылке страницы.
- **Ошибка в одном селекторе списка выбрасывает всё правило:** `.price, .price::-moz-range-thumb` в Chrome не применится и к `.price`. Прощающие списки — только у `:is()` и `:where()`.
- **`:has()` выбирает элемент по тому, что внутри или после него:** карточку с картинкой, форму с ошибкой, заголовок перед абзацем. Стиль обновляется сам при изменении DOM, но `:has()` нельзя вкладывать в `:has()`.
- **`:focus-visible` — фокус, который нужно показать:** после клика мышью по кнопке его нет, после Tab — есть. Кольцо фокуса не убирают, а стилизуют через `:focus-visible`.
- **Псевдоэлемент без `content` не существует,** а текст из `content` попадает в доступное имя элемента. `@supports` проверяет поддержку свойства и селектора, `@scope` ограничивает стили областью и отдаёт победу ближайшей.
::

## Что выбирает селектор

Сквозной пример — страница оформления заказа: список товаров, форма с почтой и телефоном, кнопка «Оплатить».

```html
<form class="checkout">
  <label for="email">Почта</label>
  <input id="email" type="email" required>
  <button>Оплатить</button>
</form>
```

Простые селекторы — по типу (`input`), классу (`.checkout`), id (`#email`), атрибуту (`[required]`) и универсальный `*`. Склеенные без пробела, они дают составной селектор: `input.field[required]` — один элемент, у которого есть всё сразу. Комбинаторы соединяют составные селекторы отношениями:

| Комбинатор | Пример | Что выбирает |
| --- | --- | --- |
| пробел | `.checkout input` | любой потомок |
| `>` | `ul > li` | прямой потомок |
| `+` | `label + input` | следующий сосед сразу после |
| `~` | `h2 ~ p` | любой следующий сосед |

Комбинаторы смотрят только вниз и вперёд по дереву: выбрать родителя или предыдущего соседа раньше было нельзя. Это закрыл `:has()`, о нём ниже.

### Атрибуты

| Селектор | Значение атрибута |
| --- | --- |
| `[href]` | атрибут есть |
| `[type="email"]` | равно |
| `[href^="https://"]` | начинается с |
| `[href$=".pdf"]` | заканчивается на |
| `[class*="card"]` | содержит подстроку |
| `[data-state~="open"]` | содержит слово через пробел |
| `[lang\|="en"]` | равно `en` или начинается с `en-` |

Флаг `i` перед закрывающей скобкой отключает регистр: в проверке `a[href$=".pdf" i]` совпал со ссылкой на `doc.PDF`. Атрибуты `data-*` удобны для состояний: `[data-state="open"]` читается лучше набора классов `is-open`.

## Как браузер сопоставляет селекторы

Интуитивно `.checkout input` читается слева направо: найти форму, потом поля в ней. Браузер делает наоборот. Движок Blink раскладывает правила по корзинам по **крайней правой части** селектора — классу, id, тегу — и для элемента сразу берёт только правила из подходящих корзин. Остаток селектора проверяется от элемента вверх по предкам.

Справа налево выгоднее: у элемента один путь к корню, а потомков у узла может быть тысячи. Большинство правил отсекаются по правой части без обхода дерева.

Отсюда практические выводы:

- `.checkout input` проверяется на **каждом** `input` страницы, а `.checkout-field` — только на элементах с этим классом;
- длинные цепочки потомков медленнее и хрупче одного класса;
- на обычной странице сопоставление редко бывает узким местом — дороже частые пересчёты стилей большого :term[DOM]{def="дерево объектов страницы, через которое JavaScript читает и меняет документ"}. Проверяют в панели Performance: этап Recalculate Style и статистика селекторов (подробно — в [Рендеринге](/content/web/rendering)).

## Псевдоклассы

Псевдокласс выбирает элемент по состоянию или положению, которого нет в разметке как атрибута.

### Положение среди соседей

`:first-child`, `:last-child`, `:only-child` и `:nth-child(An+B)`, где `n` пробегает 0, 1, 2:

```css
li:nth-child(2n)      /* чётные, то же что even */
li:nth-child(2n + 1)  /* нечётные, odd */
li:nth-child(-n + 3)  /* первые три */
li:nth-child(n + 4)   /* с четвёртого */
```

Две ловушки:

- **`:nth-child` считает всех соседей**, включая скрытых. В таблице заказов со скрытой строкой «зебра» съезжает. Синтаксис `of S` считает только подходящих: `tr:nth-child(even of :not([hidden]))`;
- **`:nth-of-type` считает по тегу, а не по классу.** `.item:nth-of-type(2)` — это второй `p` среди соседей, если у него есть `.item`, а не второй `.item`. В проверке стиль получил первый товар, потому что перед ним стоял `p.intro`.

`:empty` срабатывает только на элементе совсем без потомков. Пробел или перевод строки — уже текстовый узел: в проверке `<div class="msg"> </div>` не скрылся, а `<div class="msg"></div>` и вариант с одним комментарием — скрылись.

### Взаимодействие

`:hover`, `:active`, `:focus`, `:focus-within` (фокус на элементе или внутри него), `:target` (элемент, чей `id` совпал с якорем в адресе), `:visited`. У `:visited` из соображений приватности можно менять только цвета, а `getComputedStyle` отдаёт стиль непосещённой ссылки — иначе сайт узнал бы историю браузера.

Отдельно — `:focus-visible`. `:focus` срабатывает при любом фокусе, `:focus-visible` — когда браузер считает, что фокус нужно показать. В проверке клик мышью по кнопке дал `:focus` без `:focus-visible`, переход по Tab — оба, а поле ввода получило `:focus-visible` и от клика: в поле пользователь будет печатать и должен видеть, где курсор. Стиль браузера по умолчанию уже рисует кольцо только для `:focus-visible`, поэтому старый приём

```css
button:focus { outline: none; }
```

ничего не даёт мышиным пользователям и отнимает кольцо у тех, кто ходит с клавиатуры. Свой стиль фокуса пишут через `:focus-visible`.

### Формы

`:required`, `:optional`, `:checked`, `:disabled`, `:placeholder-shown`, `:autofill`, `:valid` и `:invalid`. Последние два работают на ограничениях из разметки — `required`, `type="email"`, `pattern` (подробно — в [Формах](/content/html/forms)). Ловушка `:invalid`: пустое обязательное поле невалидно сразу после загрузки, и форма встречает пользователя красными рамками. `:user-invalid` срабатывает только после взаимодействия: в проверке поле почты было `:invalid` с самого начала, а `:user-invalid` — только после ввода «не почта» и ухода из поля.

### `:is()`, `:where()` и `:not()`

```css
:is(header, footer, nav) a:hover { color: var(--accent); }
```

`:is()` и `:where()` группируют варианты вместо повторения всей цепочки. Разница — в специфичности: `:is()` берёт самый сильный аргумент, `:where()` — ноль (подробно — в [Каскаде](/content/css/styling)). `:not()` принимает список: `input:not([type="checkbox"], [type="radio"])`.

Есть и вторая разница, менее известная. Обычный список селекторов через запятую **неделим**: если браузер не понял хоть один, он выбрасывает правило целиком.

```css
.price, .price::-moz-range-thumb { color: red; }
```

В проверке в Chromium цена осталась чёрной: `::-moz-range-thumb` Chrome не знает, и правило не применилось и к `.price`. Списки внутри `:is()` и `:where()` **прощающие**: неизвестный аргумент просто пропускается. Псевдоэлементы внутри `:is()` недопустимы, поэтому вендорные псевдоэлементы пишут отдельными правилами.

### `:has()`

`:has()` выбирает элемент, если внутри него или после него есть что-то, подходящее под аргумент:

```css
.card:has(img) { display: grid; }                     /* карточка с картинкой */
form:has(:user-invalid) button { opacity: 0.5; }      /* форма с ошибкой */
h2:has(+ p) { margin-bottom: 4px; }                   /* заголовок, за которым абзац */
ul:has(> li:nth-child(4)) { columns: 2; }             /* список из четырёх и больше */
```

Все четыре сработали в проверке. Главное — стиль **обновляется сам**: когда в карточку без картинки добавили `img`, она стала сеткой, а кнопка потускнела, как только поле стало `:user-invalid`. Раньше для этого писали обработчик, который переключает класс на родителе.

Ограничения:

- `:has()` нельзя вкладывать в `:has()`, а псевдоэлементы внутри него недопустимы — такое правило браузер выбрасывает;
- каждое изменение DOM может заставить браузер перепроверить `:has()` на предках. Широкие якоря вроде `body:has(...)` или `:has()` без класса слева стоят дороже, чем `.card:has(...)`.

## Псевдоэлементы

Псевдоэлемент — часть элемента, которой нет в DOM: `::before`, `::after`, `::marker`, `::placeholder`, `::selection`, `::backdrop` у модального `dialog`, `::first-line`, `::first-letter`, `::file-selector-button`.

```css
label.required::after { content: " *"; color: red; }
```

`::before` и `::after` без `content` не создаются вовсе: в проверке `getComputedStyle(el, '::after').content` у правила без `content` вернул `none`, и ширина с `display` не дали бокса. Даже для чисто декоративного элемента пишут `content: ""`.

Два двоеточия отличают псевдоэлементы от псевдоклассов. Старые четыре — `:before`, `:after`, `:first-line`, `:first-letter` — работают и с одним для совместимости. Новые — только с двумя: `li:marker` в проверке оказался невалидным селектором.

Текст из `content` видят программы чтения с экрана. Кнопка-крестик `button.del::before { content: "×" }` в проверке получила доступное имя «×». Альтернативный текст задают после косой черты:

```css
.del::before { content: "×" / "Удалить"; }
```

И кнопка стала «Удалить». Смысловой текст в `content` не кладут: его нельзя выделить и скопировать, а переводчики страниц его пропускают.

## At-rules

At-rule — инструкция с `@`. Большинство из них разобраны там, где работают:

| At-rule | Назначение | Где подробно |
| --- | --- | --- |
| `@media`, `@container` | стили по условиям экрана или контейнера | [Адаптивный дизайн](/content/css/rwd) |
| `@layer` | порядок групп в каскаде | [Каскад](/content/css/styling) |
| `@keyframes`, `@starting-style` | анимации и стиль появления | [Анимации](/content/css/animations) |
| `@font-face` | подключение шрифта | [Типографика](/content/css/typography) |
| `@property` | типизированная CSS-переменная | [Современный CSS](/content/css/modern-css) |
| `@import` | подключение файла, с `layer()` и `supports()` | [Каскад](/content/css/styling) |
| `@supports`, `@scope` | ниже | |

### @supports

Проверяет, поддерживает ли браузер объявление или селектор, и применяет блок только тогда:

```css
@supports (display: grid) { … }
@supports selector(:has(a)) { … }
@supports not (backdrop-filter: blur(4px)) { .overlay { background: rgb(0 0 0 / 0.8); } }
```

Условия комбинируются через `and`, `or`, `not`. В проверке блоки с `display: grid` и `selector(:has(a))` применились, а с `display: nonsense` — нет. Это основа прогрессивного улучшения: базовый вариант работает везде, улучшение — где поддерживается. Из JavaScript то же самое проверяет `CSS.supports()`.

### @scope

`@scope` ограничивает стили областью без длинных селекторов и без :term[Shadow DOM]{def="скрытое поддерево элемента со своей разметкой и стилями, изолированное от страницы"}:

```css
@scope (.card) to (.card-slot) {
  p { color: var(--card-text); }
}
```

Правило действует внутри `.card`, но не заходит в `.card-slot` — туда вставляют чужое содержимое. Такую область с дыркой называют «пончиком». В проверке абзац самой карточки получил стиль, абзац в слоте — нет. Специфичность селекторов внутри `@scope` не растёт от корня области.

Вторая возможность — **близость**. Вложенные темы с обычными селекторами ломаются:

```css
.light p { color: black; }
.dark p  { color: white; }
```

Светлый блок внутри тёмного внутри светлого: оба правила подходят, специфичность равна, побеждает последнее — и текст в светлом блоке стал белым. С `@scope (.light)` и `@scope (.dark)` при равной специфичности побеждает правило с **ближайшим** корнем области — в проверке текст в светлом блоке стал чёрным независимо от порядка. Черновик каскада следующего уровня вставляет этот шаг между специфичностью и порядком появления.

Как `@scope` сравнивается с :term[CSS Modules]{def="CSS-файлы, классы которых сборщик переименовывает в уникальные, чтобы не было конфликтов"} и Shadow DOM для изоляции компонентов — в [CSS-архитектуре](/content/css/architecture).

## Красные флаги в ответе

- **«`.nav a` сначала находит `.nav`, потом ссылки в нём».** Браузер идёт справа налево: от каждой ссылки к её предкам.
- **«Если один селектор в списке не поддерживается, пропустится только он».** Обычный список неделим — выбрасывается всё правило. Прощают только `:is()` и `:where()`.
- **«`:nth-of-type` считает элементы с этим классом».** Он считает по тегу среди соседей.
- **«`:empty` сработает на пустом с виду блоке».** Пробел или перевод строки — это потомок.
- **«`button:focus { outline: none }`, если сделали свой стиль».** Так убирают кольцо у пользователей клавиатуры; стиль фокуса пишут через `:focus-visible`.
- **«`::before` можно стилизовать и без `content`».** Без `content` псевдоэлемента нет.

## Как спрашивают на собеседовании

::question
Как браузер сопоставляет селекторы? Важна ли их скорость?

#answer
Справа налево: правила разложены по крайней правой части селектора — классу, тегу, id, — и для элемента проверяются только подходящие, а остаток селектора проверяется вверх по предкам. Так большинство правил отсекается без обхода дерева.

#more
`.checkout input` проверяется на каждом `input`, а `.checkout-field` — только на элементах с классом. На обычных страницах это редко узкое место: дороже частые пересчёты стилей большого DOM и широкие `:has()`, которые браузер перепроверяет при изменениях. Смотрят в Performance — Recalculate Style и статистику селекторов.
::

::question
Чем отличаются `:is()`, `:where()` и `:not()`?

#answer
`:is()` и `:where()` группируют варианты селекторов и совпадают с элементом, если подошёл любой. Разница в специфичности: `:is()` берёт самый сильный аргумент, `:where()` — ноль. `:not()` исключает элементы, подходящие под аргументы, и берёт специфичность самого сильного аргумента.

#more
Списки внутри `:is()` и `:where()` прощающие: неизвестный селектор пропускается, а не выбрасывает всё правило, как обычный список через запятую. Псевдоэлементы внутри них недопустимы. `:where()` используют для сбросов и стилей библиотек, которые должен легко перебить любой класс.
::

::question
Что умеет `:has()` и какие у него ограничения?

#answer
`:has()` выбирает элемент по тому, что внутри или после него: `.card:has(img)`, `form:has(:user-invalid) button`, `h2:has(+ p)` — то есть родителя и предыдущего соседа, чего раньше CSS не умел. Стиль обновляется сам при изменении DOM, без JavaScript.

#more
`:has()` нельзя вкладывать в `:has()`, псевдоэлементы внутри недопустимы. Специфичность — самого сильного аргумента. Каждое изменение DOM может заставить перепроверить `:has()` на предках, поэтому якорь лучше узкий: `.card:has(...)`, а не `body:has(...)`. Через `:has()` делают и «количественные» стили: `ul:has(> li:nth-child(4))`.
::

::question
Чем `:focus` отличается от `:focus-visible`? Можно ли убрать `outline`?

#answer
`:focus` срабатывает при любом фокусе, `:focus-visible` — когда фокус нужно показать: после Tab, но не после клика мышью по кнопке. Поля ввода получают `:focus-visible` при любом фокусе. Кольцо не убирают, а стилизуют через `:focus-visible`.

#more
Стиль браузера по умолчанию уже рисует кольцо только для `:focus-visible`, поэтому `button:focus { outline: none }` ничего не даёт мыши, но отнимает видимый фокус у клавиатуры — это нарушение доступности. `:focus-within` срабатывает на контейнере, если фокус где-то внутри: удобно для подсветки поля поиска с кнопкой.
::

::question
Почему поле с ошибкой красное сразу при загрузке? Как это исправить?

#answer
`:invalid` срабатывает по ограничениям из разметки сразу: пустое `required`-поле невалидно до того, как пользователь его коснулся. `:user-invalid` срабатывает только после взаимодействия — ввода и ухода из поля или попытки отправить форму.

#more
Для подсветки ошибок используют `:user-invalid`, а для кнопки отправки — `form:has(:user-invalid) button`. Сообщение об ошибке при этом связывают с полем через `aria-describedby`, иначе цвет увидят не все. Подробно о валидации — в главе про формы.
::

::question
Чем псевдокласс отличается от псевдоэлемента? Зачем `::before` нужен `content`?

#answer
Псевдокласс выбирает существующий элемент в особом состоянии или положении — `:hover`, `:nth-child()`. Псевдоэлемент — часть элемента, которой нет в DOM, — `::before`, `::marker`, `::placeholder`. `::before` и `::after` без `content` не создаются, поэтому даже декоративным пишут `content: ""`.

#more
Двойное двоеточие отличает псевдоэлементы; одно работает только у четырёх старых — `:before`, `:after`, `:first-line`, `:first-letter`. Текст из `content` попадает в доступное имя элемента, альтернативу задают через косую черту: `content: "×" / "Удалить"`. Смысловой текст в `content` не кладут — его нельзя выделить и скопировать.
::

::question
Что такое `@supports` и `@scope`?

#answer
`@supports` применяет блок, только если браузер поддерживает объявление или селектор: `@supports (display: grid)`, `@supports selector(:has(a))`. `@scope` ограничивает стили областью с необязательной нижней границей: `@scope (.card) to (.card-slot)`.

#more
`@supports` — основа прогрессивного улучшения, из JavaScript есть `CSS.supports()`. У `@scope` два плюса перед длинными селекторами: стили не заходят во вложенное чужое содержимое, а при равной специфичности побеждает ближайший корень области — так вложенные светлые и тёмные темы работают независимо от порядка правил.
::

## Практика

::practice{title="Зебра съехала после фильтра"}
В таблице заказов чётные строки закрашены. После фильтра часть строк скрывается атрибутом `hidden`, и полосы идут подряд одного цвета:

```css
tr:nth-child(even) { background: var(--row-alt); }
```

#solution
`:nth-child` считает всех соседей, включая скрытые строки, поэтому видимые строки 1, 3 и 4 получают цвета «нечётная, нечётная, чётная». Синтаксис `of` считает только подходящих:

```css
tr:nth-child(even of :not([hidden])) { background: var(--row-alt); }
```

В проверке в Chromium без `of` закрасилась четвёртая строка, а с ним — третья, вторая по счёту среди видимых. Если строки убирают из DOM, а не скрывают, хватает и обычного `:nth-child`.
::

::practice{title="Стиль ползунка не применяется в Chrome"}
Дизайнер просил одинаковый цвет у ползунка во всех браузерах. В Chrome он не перекрасился, а вместе с ним пропал и стиль самого поля:

```css
.range,
.range::-webkit-slider-thumb,
.range::-moz-range-thumb {
  accent-color: var(--accent);
  background: var(--accent);
}
```

#solution
Обычный список селекторов неделим: Chrome не знает `::-moz-range-thumb` и выбрасывает правило целиком. Так же поступит любой браузер, которому незнаком хотя бы один псевдоэлемент из списка. В проверке правило `.price, .price::-moz-range-thumb` не применилось к `.price` в Chromium. Вендорные селекторы пишут отдельными правилами:

```css
.range { accent-color: var(--accent); }
.range::-webkit-slider-thumb { background: var(--accent); }
.range::-moz-range-thumb { background: var(--accent); }
```

Для обычных селекторов с неуверенной поддержкой подходит прощающий `:is()`, но псевдоэлементы в нём недопустимы.
::

::practice{title="Форма встречает ошибками"}
На пустой форме оплаты все поля сразу с красной рамкой, а кнопка серая:

```css
input:invalid { border-color: red; }
form:has(:invalid) button { opacity: 0.5; }
```

#solution
`:invalid` смотрит на ограничения разметки, и пустое `required`-поле невалидно до любого действия. Нужен `:user-invalid`, который срабатывает после взаимодействия:

```css
input:user-invalid { border-color: red; }
form:has(:user-invalid) button { opacity: 0.5; }
```

В проверке поле почты было `:invalid` сразу после загрузки, а `:user-invalid` стало только после ввода и перехода по Tab; вместе с ним потускнела кнопка. Кнопку при этом не блокируют `pointer-events: none`: по клику браузер покажет, какое поле не заполнено.
::
