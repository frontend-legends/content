# CSS-архитектура

Как организовать стили, чтобы проект на сотни компонентов и несколько команд не превратился в войну специфичности: методологии именования, механизмы изоляции, каскадные слои, токены и порядок подключения. Спрашивают, что такое BEM и нужен ли он сейчас, чем CSS Modules отличаются от `scoped` во Vue и Shadow DOM и как организовать глобальные стили. Глубже — почему `p` в CSS-модуле красит всё приложение, почему стиль родителя во Vue попадает в дочерний компонент и почему легаси-CSS перебивает утилиты.

::tldr
- **CSS глобален:** любое правило может задеть любой элемент, а конфликт решают специфичность и порядок подключения. Архитектура отвечает на два вопроса: как не пересечься именами и как предсказуемо решить конфликт.
- **BEM — изоляция договорённостью:** `блок__элемент--модификатор` и один класс в селекторе, специфичность у всех правил одинаковая. Технически ничто не мешает двум командам назвать блок одинаково.
- **Инструменты изолируют по-разному:** CSS Modules хешируют только классы, и `p {}` в модуле остаётся глобальным; `scoped` во Vue помечает селекторы атрибутом, и стиль родителя достаёт корень дочернего компонента; Shadow DOM закрывает компонент, но наследуемые свойства и CSS-переменные проходят внутрь.
- **Каскадные слои — порядок групп стилей:** сброс, база, компоненты, утилиты. Легаси и чужой CSS кладут в свои слои, иначе стили вне слоёв перебивают всё.
- **Токены в три уровня — палитра, смысл, компонент — на CSS-переменных:** тема меняет смысловой уровень, вариант компонента — свой токен, а компоненты не знают о конкретных цветах.
::

## Почему CSS трудно масштабировать

Сквозной пример — интернет-магазин, который вырос: каталог, корзина и личный кабинет делают три команды, есть общий UI-кит, легаси-страницы на старом CSS и виджет оплаты от партнёра.

В CSS одно пространство имён на всю страницу. Пока проект маленький, это удобно. Потом появляются типичные проблемы:

- **конфликт имён** — команда корзины и команда каталога независимо пишут `.card`, и стили складываются;
- **война специфичности** — чтобы перебить чужое правило, селектор удлиняют или ставят `!important`, и следующему приходится идти дальше (подробно — в [Каскаде](/content/css/styling));
- **зависимость от порядка** — при равной специфичности побеждает подключённое позже, и результат зависит от порядка импортов;
- **страх удалять** — неизвестно, где ещё используется правило, поэтому мёртвый CSS копится годами;
- **неявные связи** — правило `.sidebar .title` ломается, когда заголовок переносят в другое место.

Все подходы ниже решают две задачи: **ограничить область действия** правила и **сделать исход конфликта предсказуемым**.

## Методологии

### BEM

BEM делит интерфейс на блоки, элементы и модификаторы и кодирует это в имени класса:

```css
.product-card { … }                  /* блок — самостоятельный компонент */
.product-card__title { … }           /* элемент — часть блока, вне его смысла не имеет */
.product-card__price { … }
.product-card--featured { … }        /* модификатор — вариант блока */
.product-card__price--sale { … }     /* модификатор элемента */
```

Правила BEM:

- **один класс в селекторе** — специфичность всех правил одинаковая, (0, 1, 0), и конфликт решает порядок внутри одного файла блока;
- **никаких селекторов по тегу и вложенности** — `.product-card h3` сломается, когда заголовок станет `h2`;
- **блок не задаёт себе внешних отступов и позиции** — это делает родитель, иначе блок нельзя переставить.

Сила BEM — в предсказуемости и читаемости: по `product-card__price--sale` в DOM понятно, где искать стиль. Слабость — изоляция только на договорённости: уникальность имени блока никто не проверяет, а имена длинные. С инструментами изоляции BEM-имена уже не нужны, но мышление «блок, элемент, модификатор» и правило одного класса остаются полезными в любом подходе.

### Другие методологии

| Методология | Идея |
| --- | --- |
| OOCSS | отделить структуру от оформления и контейнер от содержимого: `.media` раскладывает, `.skin-dark` красит |
| SMACSS | категории правил: база, раскладка, модули, состояния (`is-open`), темы |
| ITCSS | перевёрнутый треугольник: от общих правил с низкой специфичностью к частным — настройки, инструменты, сброс, элементы, объекты, компоненты, утилиты |
| атомарный CSS | один класс — одно свойство: `.mt-0`, `.flex`; из него выросли утилитарные фреймворки |

ITCSS — предок каскадных слоёв: он упорядочивал стили по специфичности и порядку файлов, а `@layer` делает тот же порядок явным и независимым от специфичности. Утилитарный подход и выбор между :term[Tailwind]{def="CSS-фреймворк из готовых утилитарных классов: стили пишут прямо в разметке"}, CSS Modules и :term[CSS-in-JS]{def="подход, при котором стили описывают в JavaScript, а библиотека генерирует и вставляет их на страницу"} как инструментами — в [Стилизации](/content/ecosystem-libs/styling-solutions).

## Изоляция

Методология защищает договорённостью, инструменты — механизмом. Механизмы разные, и у каждого своя дыра.

| Механизм | Как изолирует | Что проходит |
| --- | --- | --- |
| BEM | уникальные имена по договорённости | всё: имя может повториться |
| CSS Modules | хеш в именах классов при сборке | селекторы типа, `:global` |
| `scoped` во Vue | атрибут `data-v-…` на элементах и в селекторах | стиль родителя на корне ребёнка, `:deep()` |
| Shadow DOM | отдельное дерево, внешние селекторы не видят его | наследуемые свойства, CSS-переменные, `::part` |
| `@scope` | область с корнем и границей | всё, что вне границы правила не трогает |

### CSS Modules

Файл `card.module.css` — обычный CSS, но при сборке каждое имя класса получает уникальный хеш, а JavaScript получает объект с итоговыми именами:

```css
/* card.module.css */
.card { composes: base from "./shared.module.css"; background: white; }
.featured { composes: card; border: 2px solid; }
.title { font-weight: 700; }
p { margin: 0; }
:global(.is-open) .title { color: red; }
```

В проверке сборкой Vite `.title` превратился в `._title_…`, а `:global(.is-open)` остался как есть — так стилизуют глобальное состояние. `composes` не копирует правила, а добавляет классы: элемент с `s.featured` получил три класса — `featured`, `card` и `base`.

Главная дыра: **хешируются только классы**. `p { margin: 0 }` в модуле карточки в сборке остался `p{margin:0}` — глобальным правилом для всех абзацев приложения. В модулях пишут только селекторы классов. Неиспользуемые классы модули тоже не удаляют.

### scoped во Vue

`<style scoped>` во Vue работает через атрибуты: компилятор добавляет к каждому элементу шаблона атрибут вида `data-v-7ba5bd90`, а к каждому селектору — `[data-v-7ba5bd90]`. В проверке `vue/compiler-sfc` превратил `.label` в `.label[data-v-7ba5bd90]`, причём и селектор типа `p` — в `p[data-v-7ba5bd90]`: в отличие от CSS Modules, здесь он тоже изолирован.

Особенность, которую спрашивают: **корень дочернего компонента получает атрибут родителя**. В проверке после монтирования корень `div.child` дочернего компонента был помечен атрибутом родителя, а элементы внутри ребёнка — нет. В Chromium стиль родителя `.child { border }` применился к корню ребёнка, а `.label` до элемента внутри ребёнка не дошёл. Так задумано: родитель может расположить ребёнка. Стилизовать глубже — через `:deep()`, который переносит атрибут на предка: `.wrap :deep(.label)` стал `.wrap[data-v-…] .label` и достал элемент внутри ребёнка. Подробно о стилях во Vue — во [Введении в Vue](/content/vuejs/introduction).

### Shadow DOM

Shadow DOM — отдельное дерево внутри элемента, и внешние селекторы в него не заходят. Так делают виджеты, которые встраиваются в чужие страницы, — как виджет оплаты партнёра в нашем магазине. В проверке `.title { color: red }` страницы не тронул `.title` внутри виджета.

Граница проницаема в трёх местах:

- **наследуемые свойства** — `color`, `font` хоста переходят внутрь: заголовок виджета получил зелёный цвет хоста;
- **CSS-переменные** — наследуются тоже: `--pay-accent`, заданная на `pay-widget`, перекрасила кнопку внутри. Это официальный способ темизации;
- **`::part()`** — компонент помечает элементы атрибутом `part`, и страница стилизует их снаружи: `pay-widget::part(button) { border-radius: 12px }` сработал.

Цена — стили внутри нужно подключать в каждое теневое дерево, а глобальная тема доходит только через переменные.

### @scope

`@scope (.card) to (.card-slot)` ограничивает правила областью с нижней границей, а при конфликте побеждает ближайший корень области. Это изоляция без сборщика и без Shadow DOM, но и без гарантий от совпадения имён внутри области. Подробно — в [Селекторах и at-rules](/content/css/css-rules).

## Слои как архитектура

Изоляция убирает случайные пересечения, но общие стили — сброс, типографика, утилиты — всё равно глобальные. Каскадные слои задают им порядок, который не зависит от специфичности и от того, в каком порядке собрались файлы:

```css
@layer reset, tokens, base, vendor, legacy, components, utilities;

@import url("normalize.css") layer(reset);
@import url("datepicker.css") layer(vendor);
@import url("old-pages.css") layer(legacy);
```

- **`reset` и `base`** — сброс и стили элементов по умолчанию, самые слабые;
- **`vendor`** — стили библиотек: любой свой компонент их перебивает;
- **`legacy`** — старый CSS, пока его переписывают;
- **`components`** — стили компонентов;
- **`utilities`** — утилиты вроде `.mt-0` и `.visually-hidden` последними: им не нужен `!important`, они побеждают компоненты по порядку слоёв.

Главная ловушка при внедрении — **стили вне слоёв сильнее любого слоя**. В проверке легаси-правило `.catalog h2 { margin-top: 24px }` вне слоёв перебило утилиту `.mt-0` из последнего слоя. После того как легаси обернули в слой `legacy`, утилита победила. Поэтому слои вводят сверху вниз: сначала оборачивают в слои всё старое и чужое, потом раскладывают своё. Как устроены слои в каскаде и почему `!important` в них работает в обратном порядке — в [Каскаде](/content/css/styling).

## Токены

Сотня мест с `#2563eb` в коде — это сотня мест, которые нужно найти при ребрендинге. **Токены** — именованные значения дизайн-системы: цвета, отступы, радиусы, шрифты, тени. В CSS их хранят в переменных и разделяют на уровни:

```css
:root {
  /* палитра — что есть */
  --blue-600: rgb(37 99 235);
  --red-600: rgb(220 38 38);
  --gray-50: rgb(249 250 251);

  /* смысл — для чего */
  --color-action: var(--blue-600);
  --color-surface: var(--gray-50);
  --space-2: 8px;
}
[data-theme="sale"] { --color-action: var(--red-600); }

/* компонент — свой токен с умолчанием из смыслового */
.button { --button-bg: var(--color-action); background: var(--button-bg); }
.button.danger { --button-bg: var(--red-600); }
.link { color: var(--color-action); }
```

- **палитра** — все цвета и размеры, без смысла; компоненты к ней не обращаются;
- **смысловые токены** — `--color-action`, `--color-surface`, `--color-text-muted`: тема и тёмный режим переопределяют только этот уровень;
- **токены компонента** — `--button-bg`: точка настройки варианта без нового селектора.

В проверке кнопка и ссылка взяли синий из `--color-action`, в разделе распродажи обе стали красными одной строкой темы, а вариант `danger` поменял только свой токен. Токены хранят в формате, из которого генерируют CSS, константы для JavaScript и переменные Figma, — чтобы дизайн и код не расходились. Как токены живут в дизайн-системе — в [Архитектуре компонентов](/content/architecture/component-architecture), о самих переменных — в [Современном CSS](/content/css/modern-css).

## Порядок и мёртвый код

Два источника проблем остаются при любом подходе.

**Порядок подключения.** При равной специфичности побеждает правило, подключённое позже. Когда CSS разбит по чанкам, порядок зависит от того, какие чанки загрузились раньше: стиль страницы может выглядеть по-разному при прямом заходе и при переходе из другого раздела. Защита — не держать конфликтующие правила одной специфичности в разных файлах: у каждого элемента один хозяин-компонент, общие стили — в слоях.

**Мёртвый CSS.** Глобальный CSS страшно удалять, CSS Modules не выбрасывают неиспользуемые классы. Помогают колокация — стиль лежит рядом с компонентом и удаляется вместе с ним, — панель Coverage в :term[DevTools]{def="инструменты разработчика в браузере: элементы, сеть, производительность, отладчик"} и линтер стилей. Правила линтера, которые держат архитектуру: ограничение специфичности, запрет id в селекторах и `!important` вне утилит, неизвестные CSS-переменные (подробно о линтерах — в [Линтинге и форматировании](/content/advanced-tooling/linting-and-formatting)).

### Что выбрать

| Ситуация | Подход |
| --- | --- |
| проект на React со сборщиком | CSS Modules или Tailwind; слои для глобальных стилей; токены в переменных |
| проект на Vue | `<style scoped>` или CSS Modules; токены в переменных |
| виджет для чужих страниц | Shadow DOM, тема через переменные и `::part` |
| легаси без сборщика | BEM, слои и `@scope` |
| несколько команд, общий UI-кит | токены в три уровня, слои, линтер на специфичность |

Главное правило — один основной способ на проект. Подробно о выборе инструмента и его цене — в [Стилизации](/content/ecosystem-libs/styling-solutions).

## Красные флаги в ответе

- **«CSS Modules полностью изолируют стили».** Хешируются только классы; селекторы типа и `:global` остаются глобальными.
- **«`scoped` не даёт стилям родителя попасть в дочерний компонент».** Корень ребёнка получает атрибут родителя, и его стили применяются.
- **«Shadow DOM полностью закрыт».** Наследуемые свойства и CSS-переменные проходят внутрь, а `::part` открывает стилизацию снаружи.
- **«Утилиты делают через `!important`».** Со слоями им достаточно последнего слоя.
- **«Включу слои для своего CSS — и всё».** Стили вне слоёв, в том числе легаси, перебьют все слои; старое оборачивают первым.
- **«Компоненты берут цвета из палитры».** Компоненты ссылаются на смысловые токены, иначе тема и тёмный режим требуют правки каждого компонента.

## Как спрашивают на собеседовании

::question
Почему CSS трудно поддерживать в большом проекте?

#answer
У CSS одно глобальное пространство имён: любое правило может задеть любой элемент, а конфликт решают специфичность и порядок подключения. Отсюда конфликты имён, война специфичности, зависимость от порядка файлов и мёртвый CSS, который страшно удалять.

#more
Архитектура отвечает на две задачи: ограничить область действия правила — методологией или механизмом изоляции — и сделать исход конфликта предсказуемым — плоской специфичностью и каскадными слоями. Плюс токены, чтобы значения жили в одном месте, и линтер, который держит правила.
::

::question
Что такое BEM и нужен ли он сейчас?

#answer
Соглашение об именах: блок, элемент и модификатор в одном классе — `product-card__price--sale`. Один класс в селекторе даёт плоскую специфичность, а имя показывает, к какому компоненту относится стиль.

#more
Изоляция в BEM держится на договорённости — уникальность имён никто не проверяет. С CSS Modules, `scoped` или Shadow DOM длинные имена не нужны, но принципы остаются: один класс в селекторе, никаких селекторов по тегу и вложенности, блок не задаёт себе внешних отступов. В проектах без сборщика BEM вместе со слоями — рабочий выбор.
::

::question
Чем CSS Modules отличаются от scoped во Vue и Shadow DOM?

#answer
CSS Modules при сборке добавляют хеш к именам классов. `scoped` во Vue помечает элементы атрибутом `data-v-…` и добавляет его к селекторам. Shadow DOM создаёт отдельное дерево, в которое внешние селекторы не заходят.

#more
У каждого своя дыра. В модулях селектор типа `p {}` остаётся глобальным. В `scoped` корень дочернего компонента получает атрибут родителя, а `:deep()` намеренно стилизует глубже. В Shadow DOM проходят наследуемые свойства и CSS-переменные, а `::part` открывает отдельные элементы для стилизации снаружи. Shadow DOM — для виджетов на чужих страницах, модули и `scoped` — для своих приложений.
::

::question
Как организовать глобальные стили?

#answer
Каскадными слоями: `@layer reset, base, vendor, components, utilities;`. Порядок слоёв сильнее специфичности, поэтому утилиты в последнем слое побеждают компоненты без `!important`, а стили библиотек в слое `vendor` перебивает любой свой компонент.

#more
Стили вне слоёв сильнее всех слоёв, поэтому при внедрении сначала оборачивают легаси и чужой CSS: `@import url(old.css) layer(legacy)`. Глобальными остаются только сброс, стили элементов, токены и утилиты; всё остальное — в изолированных стилях компонентов. Это современная форма ITCSS.
::

::question
Что такое токены и как их организовать?

#answer
Именованные значения дизайн-системы — цвета, отступы, радиусы, шрифты — в CSS-переменных. Их делят на уровни: палитра — какие цвета есть, смысловые токены — для чего цвет, токены компонента — точки его настройки.

#more
Компоненты ссылаются на смысловые токены, а не на палитру: тогда тёмная тема и тема распродажи переопределяют только смысловой уровень одной строкой. Вариант компонента меняет свой токен — `--button-bg` у `.danger`. Токены хранят в формате, из которого генерируют CSS, JavaScript и переменные Figma.
::

::question
Почему стили в продакшене выглядят иначе, чем при разработке?

#answer
Чаще всего из-за порядка подключения CSS: при равной специфичности побеждает правило, подключённое позже. В разработке стили вставляются по мере импорта модулей, в продакшене они собраны в файлы и чанки, и порядок может быть другим — в том числе зависеть от того, какие чанки загрузились раньше.

#more
Защита — не полагаться на порядок между файлами: один хозяин у каждого элемента, конфликтующие стили в одном компоненте, общие — в слоях с явным порядком. Сюда же относятся селекторы типа в CSS-модулях, которые тихо применяются ко всему приложению.
::

::question
Как держать CSS в порядке в команде?

#answer
Линтер стилей с правилами на архитектуру: максимальная специфичность, запрет id в селекторах и `!important` вне утилит, неизвестные CSS-переменные. Колокация: стиль рядом с компонентом и удаляется вместе с ним. И один основной способ стилизации на проект.

#more
Мёртвый CSS ищут панелью Coverage в DevTools, но с осторожностью: правила для состояний и редких страниц на одном заходе не используются. Визуальные регрессионные тесты ловят случайные изменения от правок общих стилей. Токены не дают значениям расползаться по коду.
::

## Практика

::practice{title="Модуль перекрасил всё приложение"}
После добавления карточки отзывов у абзацев по всему приложению пропали отступы:

```css
/* review-card.module.css */
.card { padding: 16px; }
p { margin: 0; }
```

#solution
CSS Modules хешируют только имена классов. Селектор типа `p` уходит в сборку как есть и действует на все абзацы. В проверке сборкой Vite в итоговом CSS было глобальное `p{margin:0}`. В модуле пишут только классы:

```css
.card { padding: 16px; }
.text { margin: 0; }
```

```jsx
<div className={s.card}><p className={s.text}>{review.text}</p></div>
```

Или ограничивают селектор классом модуля: `.card p { margin: 0; }`. Такие правила ловит линтер стилей запретом селекторов типа в `*.module.css`.
::

::practice{title="Стиль родителя ломает дочерний компонент"}
В компоненте корзины заголовок стал огромным, хотя в нём самом стили не менялись:

```vue
<!-- CartPage.vue -->
<template>
  <section class="cart"><h2 class="title">Корзина</h2><CartSummary /></section>
</template>
<style scoped>
.title { font-size: 32px; }
</style>
```

```vue
<!-- CartSummary.vue: корень — заголовок с тем же классом -->
<template><h3 class="title">Итого: 2 990 ₽</h3></template>
```

#solution
В `scoped` корневой элемент дочернего компонента получает атрибут родителя, и правило `.title[data-v-родителя]` подходит к корню `CartSummary`. В проверке корень дочернего компонента был помечен атрибутом родителя и получил его стиль, а элементы глубже — нет. Имена классов внутри компонентов делают уникальными:

```vue
<!-- CartPage.vue -->
<style scoped>
.cart-title { font-size: 32px; }
</style>
```

Корень ребёнка родитель может стилизовать намеренно — например, отступы через класс на теге компонента, — а всё глубже — только через `:deep()` или пропсы компонента.
::

::practice{title="Легаси перебивает утилиты"}
В проект добавили слои, утилиты положили в последний слой, но `.mt-0` на заголовках каталога не работает:

```css
@layer reset, components, utilities;
@layer utilities { .mt-0 { margin-top: 0; } }

/* old-catalog.css, подключён как раньше */
.catalog h2 { margin-top: 24px; }
```

#solution
Старый CSS остался вне слоёв, а стили вне слоёв сильнее любого слоя — независимо от специфичности. Легаси оборачивают в слой, который стоит до компонентов и утилит:

```css
@layer reset, legacy, components, utilities;
@import url("old-catalog.css") layer(legacy);
```

В проверке в Chromium без слоя заголовок получил `margin-top: 24px` из легаси, в слое `legacy` — `0` из утилиты. Слой легаси потом постепенно пустеет по мере переписывания страниц.
::
