# Техническое интервью

Сердце процесса — раунды, где проверяют, как ты решаешь задачи, пишешь код и рассуждаешь о системе. Здесь — форматы технического интервью во фронтенде, как вести себя на живом кодинге шаг за шагом, что делать, если застрял, как сделать домашнее задание, как подготовиться к проектированию системы и что на самом деле оценивают. Правильный ответ важен, но решение чаще принимают по тому, как ты к нему шёл.

::tldr
- **Форматов много:** живой кодинг, сборка компонента, вопросы на понимание, отладка, ревью кода, домашнее задание, проектирование фронтенд-системы. Формат стоит спросить у рекрутера заранее.
- **Порядок на живом кодинге:** уточнить требования, проговорить план, сделать простое рабочее решение, проверить на примерах, обсудить улучшения. Молчаливое идеальное решение оценивают хуже проговорённого.
- **Застрял — говори:** где затык, какие идеи, упрости задачу, попроси подсказку. Реакция на подсказку тоже оценивается, а частичное решение лучше пустого.
- **Домашнее задание — по требованиям, чисто и соразмерно,** с README о решениях и компромиссах.
- **Сильный ответ — с компромиссами и краями:** альтернативы, сложность, доступность, производительность, что бы сделал с большим временем.
::

## Форматы

| Формат | Что это | Как готовиться |
| --- | --- | --- |
| живой кодинг | задача при интервьюере: утилита, алгоритм, асинхронность | [Частые задачи](/content/common-coding-questions), решать вслух на время |
| сборка компонента | автокомплит, табы, модальное окно, бесконечная лента — на чистом JavaScript или фреймворке | DOM, события, доступность, состояния загрузки и ошибки |
| вопросы на понимание | замыкания, event loop, рендеринг React, каскад CSS, кеширование | вся книга: блоки «главное за 30 секунд» и вопросы глав |
| отладка | найти и исправить баг в готовом коде | читать код, ставить гипотезы, проверять по одной |
| ревью кода | разобрать чужой PR | логика, крайние случаи, безопасность, тесты, читаемость |
| домашнее задание | небольшое приложение за несколько часов или дней | см. ниже |
| проектирование системы | спроектировать фронтенд: ленту, чат, дизайн-систему, редактор | [Проектирование фронтенд-систем](/content/architecture/frontend-system-design) |
| онлайн-тест | автоматическая проверка на платформе | короткие задачи на время |

Чистые алгоритмические задачи во фронтенде встречаются реже, чем у бэкенда, но бывают — особенно в больших технологических компаниях. Чаще дают фронтенд-специфичное: `debounce`, глубокое сравнение, свой `Promise.all`, событийную шину, компонент с асинхронными данными. Базу для этого дают главы про [JavaScript](/content/javascript) и [алгоритмы](/content/algorithms-data-structures).

## Живой кодинг шаг за шагом

Оценивают процесс мышления не меньше результата. Порядок, который работает почти всегда:

### 1. Уточнить требования

Не начинать писать сразу. Пример для задачи «напишите `debounce`»:

```text
— Нужен ли вызов на переднем фронте (leading) или только после паузы?
— Должен ли сохраняться this и аргументы последнего вызова?
— Нужны ли cancel и flush?
— Что вернуть из обёртки — результат или ничего?
```

Вопросы показывают, что ты думаешь о крайних случаях до кода, и спасают от решения не той задачи. Намеренно неполные условия часто и проверяют, задаёшь ли ты такие вопросы.

### 2. Проговорить план

«Буду хранить идентификатор таймера в замыкании, при каждом вызове сбрасывать его и ставить новый; в таймере вызову исходную функцию с последними аргументами». Интервьюер может поправить направление до того, как ты потратишь десять минут.

### 3. Простое рабочее решение

Сначала — работающее, потом — оптимальное. Попытка сразу написать идеал часто кончается ступором.

```js
function debounce(fn, ms) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), ms);
  };
}
```

### 4. Думать вслух

Интервьюер не читает мысли. «Здесь нужна обычная функция, а не стрелочная, чтобы получить `this` вызова», — фраза, которая показывает понимание, а не угадывание.

### 5. Проверить

Пройти код руками на примере: три вызова подряд, пауза, вызов после паузы. Назвать крайние случаи: нулевая задержка, вызов после `cancel`, исключение внутри `fn`.

### 6. Обсудить улучшения

Сложность, альтернативы, что бы добавил: `leading`, `cancel`, `flush`, типы, тесты на фейковых таймерах (подробно — в [Моках и дублёрах](/content/testing-deploying/mocking-and-test-doubles)).

## Если застрял

Ступор бывает у всех. Плохо не застрять, а замолчать.

- **Скажи, где затык:** «не понимаю, как отменить уже запущенные запросы, — думаю про AbortController».
- **Упрости:** реши частный случай — без отмены, для одного элемента, без асинхронности — и двигайся от него.
- **Вернись к примеру:** пройди руками небольшой ввод, часто решение видно на нём.
- **Попроси подсказку:** это не провал. Как ты используешь подсказку, тоже оценивают.
- **Частичное решение лучше пустого:** рабочая простая версия и понятный план, как её довести.

## Сборка компонента

Задача «сделайте автокомплит» проверяет сразу много:

- **состояния** — пусто, загрузка, результаты, ничего не найдено, ошибка;
- **асинхронность** — задержка ввода, отмена устаревших запросов, гонка ответов;
- **клавиатура и доступность** — стрелки, Enter, Escape, роли `combobox` и `listbox` (подробно — в [Доступности](/content/html/accessibility));
- **производительность** — длинные списки, лишние перерисовки;
- **структура** — разделение логики и отображения.

Даже если не успеваешь всё, назови то, что не сделал: «здесь нужна отмена предыдущего запроса через AbortController, и клавиатурная навигация» — это показывает, что ты видишь задачу целиком.

## Домашнее задание

- **Плюсы:** спокойная обстановка, ближе к реальной работе, можно показать качество.
- **Минусы:** время, часто неоплачиваемое. Задание на несколько дней — повод уточнить объём или отказаться.

Как сделать хорошо:

- выполнить **требования**, а не придумать свои;
- держать код **чистым и соразмерным** задаче: без лишней архитектуры для трёх экранов;
- добавить **несколько осмысленных тестов** на главную логику;
- написать **README**:

```text
## Как запустить
npm ci && npm run dev

## Что сделано
- поиск с задержкой ввода и отменой устаревших запросов
- сохранение фильтров в URL

## Решения и компромиссы
- состояние фильтров в URL, а не в сторе: ссылка открывает тот же вид
- без виртуализации: в задании до 200 элементов, при тысячах — добавил бы

## Что сделал бы с большим временем
- e2e на оформление, обработку офлайна, i18n
```

Раздел о решениях и компромиссах часто весит больше самого кода: по нему видно суждение. На следующем этапе домашнее задание обычно обсуждают — будь готов объяснить каждое решение и сказать, что бы изменил.

## Проектирование системы

Раунд, где нужно спроектировать фронтенд целиком: новостную ленту, чат, редактор документов, дизайн-систему, дашборд. Здесь нет единственно правильного ответа — оценивают структуру мышления, компромиссы и глубину.

Удобный каркас — **RADIO**: требования, архитектура, модель данных, интерфейсы, оптимизации. Подробно — в [Проектировании фронтенд-систем](/content/architecture/frontend-system-design), а примеры — в [Примерах системного дизайна](/content/architecture/system-design-examples).

Что выделяет сильный ответ:

- **уточнение требований** — функциональных и нефункциональных: сколько пользователей, офлайн, реальное время, доступность, SEO;
- **ведение разговора** — ты сам структурируешь время и переходишь от общего к деталям;
- **компромиссы вслух** — «пагинация курсором, а не смещением, потому что лента меняется во время прокрутки»;
- **края** — ошибки сети, медленные устройства, большие объёмы, безопасность.

---

## Что оценивают

- **решение задач** — декомпозиция, подход, работа с крайними случаями;
- **качество кода** — читаемость, имена, структура;
- **коммуникация** — ясность рассуждений, вопросы, реакция на уточнения;
- **фундамент** — понимание языка, платформы и браузера;
- **обучаемость** — как используешь подсказки и реагируешь на ошибку.

Один и тот же код может звучать по-разному: «работает» — хорошо, «работает, а вот где он сломается и что я бы поменял при большой нагрузке» — сильно. Глубина, видение краёв и компромиссов — то, что поднимает оценку.

---

## Подготовка

- **Спросить формат** у рекрутера — часто рассказывают подробно.
- **Фундамент** — главы книги: понимание сильнее заучивания.
- **Руками** — решать задачи и собирать компоненты, а не только читать решения.
- **Пробные интервью** — с другом или на платформах; рассуждать вслух под давлением — отдельный навык.
- **Окружение** — редактор, браузер, звук и камера проверены до звонка, если интервью удалённое.
- **Отдых** — выспаться полезнее, чем ночь перед интервью над задачами.

---

## Красные флаги

- **Писать код, не уточнив задачу** — решить не ту задачу.
- **Молчать** — интервьюер не видит рассуждений.
- **Сразу оптимальное решение** — застрять на старте вместо простого рабочего.
- **Замереть при ступоре** — тишина хуже, чем «я застрял здесь, думаю так».
- **Спорить с подсказкой** — интервьюер обычно ведёт к решению.
- **Лишняя архитектура в домашнем задании** — несоразмерность — тоже минус.

#answer

## Практика

::practice{title="Задача на живом кодинге"}
Интервьюер говорит: «Напишите функцию, которая выполняет асинхронные задачи с ограничением по числу одновременных».

#solution
Сначала вопросы, затем план, затем код:

```text
— Задачи — функции, возвращающие промис? — Да.
— Порядок результатов должен совпадать с порядком задач? — Да.
— Если одна задача упадёт — остальные продолжают или всё падает? — Падает, как Promise.all.
План: держу индекс следующей задачи и запускаю limit «работников»,
каждый берёт следующую задачу, пока они есть.
```

```js
async function runWithLimit(tasks, limit) {
  const results = new Array(tasks.length);
  let next = 0;
  async function worker() {
    while (next < tasks.length) {
      const i = next++;
      results[i] = await tasks[i]();
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, tasks.length) }, worker));
  return results;
}
```

Потом — проверка на примере из трёх задач с лимитом 2, крайние случаи (пустой список, лимит больше числа задач) и улучшения: отмена через AbortSignal, режим «собрать все ошибки». Похожие задачи с разбором — в [Промисах и асинхронности](/content/common-coding-questions/promises-async).
::
