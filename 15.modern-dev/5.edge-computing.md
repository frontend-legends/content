# Edge-вычисления

**Edge** - выполнение кода не в одном центральном дата-центре, а на множестве узлов сети **рядом с пользователем** (в тех же точках, где CDN раздаёт статику). Это сдвигает вычисления ближе к людям ради скорости и становится стандартной частью современного стека.

> Базовое сравнение хостинга (static/SSR/serverless/edge) - в [хостинге и платформах](/content/testing-deploying/hosting-and-platforms). Здесь - **edge как парадигма** и её компромиссы.

---

## Зачем edge

```
обычный сервер:  пользователь (Токио) → origin (США)        ~200мс
edge:            пользователь (Токио) → edge-узел (Токио)    ~10мс
```

- **Низкая задержка** - код выполняется в десятках миллисекунд от пользователя.
- **Масштабируемость** - запросы распределяются по сотням точек.
- **Разгрузка origin** - часть логики не доходит до центрального сервера.

---

## Edge vs serverless

Оба - «нет своего сервера», но разные:

| | Serverless (regional) | Edge |
|--|------------------------|------|
| Где | в одном регионе | сотни точек по миру |
| Задержка | зависит от близости региона | минимальная везде |
| Рантайм | полный Node | ограниченный (web-стандарты) |
| Время/память | щедрее | жёсткие лимиты |
| Для чего | тяжёлая логика, доступ к БД | быстрые лёгкие операции |

---

## Ограничения edge-рантайма

Платой за глобальность и скорость идут **ограничения**:

- **Не полный Node** - только web-стандартные API (`fetch`, `Request`/`Response`, Web Crypto); многие Node-модули недоступны.
- **Лимиты CPU/памяти** и времени выполнения - edge не для долгих тяжёлых задач.
- Нет постоянного состояния между запросами.

```js
// edge-функция: web-стандарты, без полного Node
export default function handler(request) {
  const country = request.headers.get('cf-ipcountry');
  return new Response(`Привет из ${country}`);
}
```

<b class="text-on-semi-light">WinterCG</b> - <span class="text-gray">Edge-рантаймы (Cloudflare Workers, Vercel Edge, Deno) сходятся на **web-стандартных API** - инициатива WinterCG. Поэтому код для edge переносим между платформами и совпадает по API с браузером (тот же `fetch`, `Request`). Это часть тренда «один стандарт везде».</span>

## Edge-рендеринг

SSR и стриминг можно выполнять **на edge** - HTML генерируется рядом с пользователем, давая быстрый TTFB по всему миру. Связано с [рендерингом и гидратацией](/content/reactjs/rendering-and-hydration): мета-фреймворки умеют рендерить отдельные маршруты на edge.

---

## Edge middleware

Лёгкая логика **перед** тем, как запрос дойдёт до приложения, прямо на edge:

- авторизация и редиректы;
- A/B-тесты и фичефлаги;
- персонализация и геотаргетинг (по стране/городу);
- защита и rate limiting.

Next.js Middleware, Cloudflare Workers - типичные места для этого. Решение принимается мгновенно и близко к пользователю.

---

## Проблема данных на edge

Главный компромисс, который спрашивают: **код глобальный, а база - обычно центральная**.

```
edge-узел (Токио) → запрос в БД (США)  ~200мс
→ преимущество edge по задержке съедается походом к далёкой БД
```

<b class="text-on-semi-light">Как решают</b> - <span class="text-gray">Edge-вычисления выгодны, только если **данные тоже близко**. Решения: **edge-БД и реплики** (Turso/libSQL, Cloudflare D1, PlanetScale, Upstash Redis), глобальное кеширование на edge, региональное размещение данных, вынос только не-зависящей-от-БД логики (auth, редиректы) на edge, а тяжёлых запросов - в регион ближе к БД. Игнорировать локальность данных - типичная ошибка с edge.</span>

---

## Когда использовать edge

```
Персонализация/редиректы/auth до приложения   → edge middleware
Глобально быстрый TTFB                         → edge-рендеринг (+ близкие данные)
Лёгкие API без тяжёлой БД-логики                → edge-функции
Тяжёлая логика, доступ к центральной БД          → обычный serverless/регион
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое edge-вычисления?</b>
<span class="text-gray">Выполнение кода на узлах сети рядом с пользователем (где CDN раздаёт статику), а не в центральном дата-центре. Даёт низкую задержку, масштабируемость и разгрузку origin.</span>

<b class="text-on-semi-light">Чем edge отличается от обычного serverless?</b>
<span class="text-gray">Serverless работает в одном регионе с полным Node; edge - в сотнях точек по миру с минимальной задержкой, но ограниченным web-стандартным рантаймом и жёсткими лимитами CPU/памяти.</span>

<b class="text-on-semi-light">Какие ограничения у edge-рантайма?</b>
<span class="text-gray">Не полный Node - только web-стандартные API (fetch, Request/Response, Web Crypto), лимиты времени/памяти, нет долгих задач и постоянного состояния. Поэтому edge - для лёгких быстрых операций.</span>

<b class="text-on-semi-light">В чём главная сложность edge?</b>
<span class="text-gray">Локальность данных: код глобальный, а БД обычно центральная - поход к далёкой базе съедает выигрыш по задержке. Нужны edge-БД/реплики, кеш или вынос на edge только логики, не зависящей от БД.</span>

<b class="text-on-semi-light">Что хорошо подходит для edge middleware?</b>
<span class="text-gray">Авторизация, редиректы, A/B-тесты, геотаргетинг, rate limiting - лёгкие решения перед приложением, принимаемые мгновенно рядом с пользователем.</span>
