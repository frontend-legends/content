# Edge-вычисления

Edge как модель вычислений: код в точках присутствия CDN рядом с пользователем, рантайм на веб-API и его ограничения, переносимость кода между платформами, рендеринг и middleware на edge, состояние изолятов и главная проблема — данные далеко. Спрашивают, что такое edge, чем он отличается от обычного serverless и в чём его главная сложность. Глубже — почему на edge нет `process` и `fs`, почему глобальная переменная то сохраняется между запросами, то нет, и почему страница на edge оказалась втрое медленнее сервера.

::tldr
- **Edge — выполнение кода в сотнях точек сети рядом с пользователем,** там же, где CDN раздаёт статику. Короткий путь до первого байта из любой страны.
- **Рантайм построен на веб-API:** `fetch`, `Request`, `Response`, `URL`, `crypto.subtle`, потоки, кеш. `process`, `require` и `fs` нет; часть Node.js-модулей включается флагом совместимости.
- **Один модуль на веб-API переносим:** в проверке одно и то же middleware дало одинаковые ответы в рантайме Cloudflare Workers и в Node.js.
- **Состояние изолята не гарантировано:** глобальная переменная может пережить запрос, но новый изолят начинает с нуля. Данные между запросами — во внешнем хранилище.
- **Edge выигрывает, когда данных не нужно или они рядом:** редиректы, проверка сессии, A/B, кеш. Несколько запросов к базе на другом континенте съедают выигрыш многократно.
::

## Зачем edge

Сквозной пример — магазин с покупателями в России, Казахстане и Японии, сервером и базой во Франкфурте.

```text
обычный сервер: пользователь в Токио → сервер во Франкфурте  → сотни миллисекунд на круг
edge:           пользователь в Токио → узел сети в Токио     → единицы и десятки миллисекунд
```

- **задержка** — код выполняется близко к пользователю, где бы он ни был;
- **масштаб** — нагрузка распределена по сотням точек;
- **разгрузка источника** — часть запросов решается на узле и не доходит до сервера.

Где edge в спектре вариантов выкладки — статика, сервер, serverless — разобрано в [Хостинге и платформах](/content/testing-deploying/hosting-and-platforms). Здесь — edge как модель и её компромиссы.

## Edge и serverless

| | Serverless в регионе | Edge |
| --- | --- | --- |
| Где выполняется | один или несколько выбранных регионов | сотни точек присутствия |
| Рантайм | полный Node.js или другой язык | веб-API в изолятах V8, Node.js — частично |
| Старт | контейнер или микро-ВМ, холодный старт заметен | изолят, старт в миллисекундах |
| Лимиты | щедрее по времени и памяти | жёсткие лимиты процессорного времени и размера |
| Рядом с базой | можно разместить рядом | обычно далеко |

Платформы: Cloudflare Workers, Vercel и Netlify Edge Functions, Deno Deploy, Fastly Compute — у последнего код компилируется в WebAssembly (подробно — в [WebAssembly](/content/additional-topics/webassembly)).

## Рантайм на веб-API

Edge-рантаймы не запускают отдельный процесс Node.js на запрос, а выполняют код в **изолятах V8** — лёгких песочницах внутри одного процесса. Поэтому старт быстрый, а набор API — веб-стандарты, тот же, что в браузере.

В проверке рантайм Cloudflare Workers — `workerd`, запущенный локально через Miniflare, — показал:

| Что | Есть |
| --- | --- |
| `process`, `require`, `fs` | нет — `undefined` |
| `crypto.subtle`, `caches`, `fetch` | да |
| `import { Buffer } from 'node:buffer'` | без флага — модуль не разрешается; с `nodejs_compat` — работает |

Флаг совместимости добавляет часть модулей Node.js — `buffer`, `crypto`, `stream`, `async_hooks` и другие, — но не превращает edge в полный Node.js: нативные расширения, долгие процессы и свободный доступ к файловой системе остаются недоступны. Библиотеки, завязанные на Node.js, на edge часто не работают — это первое, что проверяют при выборе.

### Один код в разных рантаймах

```js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    const country = request.cf?.country ?? request.headers.get('x-country');
    if (country === 'KZ' && !url.pathname.startsWith('/kz')) {
      return Response.redirect(new URL(`/kz${url.pathname}`, url), 302);
    }
    return new Response('ok');
  },
};
```

В проверке этот модуль middleware магазина выполнился в `workerd` и в Node.js с одинаковыми ответами: редирект `/catalog → /kz/catalog` для Казахстана, редирект на вход для `/orders/7` без сессии, одна и та же группа A/B для одного посетителя. Работать одинаково везде помогает стандартизация: инициатива WinterCG, перешедшая в комитет Ecma TC55, описывает общий минимум веб-API для серверных рантаймов. Фреймворки вроде Hono строятся прямо на `Request` и `Response` и запускаются на любом из них.

## Middleware на edge

Лёгкая логика **до** приложения — самое удачное применение edge:

- **редиректы** — по стране, языку, устаревшим адресам;
- **проверка сессии** — закрытые разделы без cookie сразу на вход, не нагружая сервер;
- **A/B и флаги** — стабильная группа по идентификатору посетителя (подробно — в [Стратегиях выкладки](/content/testing-deploying/deployment-strategies));
- **персонализация по заголовкам** — валюта, язык, регион;
- **защита** — ограничение частоты, блокировка ботов, заголовки безопасности.

В Next.js это `middleware.ts`, на Cloudflare — Workers перед источником. Всё это не требует базы данных — и поэтому выигрывает от близости к пользователю.

### Рендеринг на edge

SSR и потоковый рендеринг тоже можно выполнять на edge: HTML собирается рядом с пользователем (подробно — в [Рендеринге и гидратации React](/content/reactjs/rendering-and-hydration)). Мета-фреймворки позволяют выбрать рантайм для отдельного маршрута. Выигрыш есть, только если данные для страницы тоже близко или закешированы — см. ниже.

## Состояние изолята

Изолят может обработать несколько запросов подряд, и глобальные переменные между ними сохраняются. В проверке счётчик в глобальной переменной в одном изоляте показал `1`, затем `2`, а в новом — снова `1`. На реальной платформе изоляты создаются и уничтожаются когда угодно, в каждой точке присутствия свои, поэтому:

- глобальные переменные — только для кеша, который можно потерять: разобранная конфигурация, скомпилированные регулярные выражения;
- состояние между запросами — во внешнем хранилище: KV, Durable Objects, Redis-совместимые сервисы, база данных;
- счётчики, лимиты частоты и сессии — в хранилище с понятной согласованностью, а не в памяти.

---

## Данные далеко

Главный компромисс edge: **код глобальный, а база обычно в одном регионе**. Каждый запрос к базе — круг через полмира.

Модель из проверки — пользователь в Токио, база во Франкфурте, круг между континентами 240 мс, внутри дата-центра 2 мс:

| Где выполняется | Без запросов к базе | Три запроса к базе |
| --- | --- | --- |
| edge в Токио | 10 мс | 730 мс |
| сервер во Франкфурте | 240 мс | 246 мс |

Без данных edge выигрывает в 24 раза, с тремя последовательными запросами к далёкой базе — проигрывает втрое. Цифры — модель, но порядок величин реальный, и именно эту ошибку чаще всего делают при переезде на edge.

Как с этим работают:

- **держать на edge только то, что не ходит в базу** — middleware, редиректы, кеш;
- **кешировать ответы** на edge с `stale-while-revalidate` (подробно — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching));
- **реплики для чтения рядом с пользователями** — Turso и libSQL, Cloudflare D1, глобальные Postgres-сервисы, KV для редко меняющихся данных;
- **выполнять рендеринг в регионе базы**, а на edge — только маршрутизацию; платформы позволяют закрепить функцию за регионом;
- **один запрос вместо нескольких** — агрегировать данные на сервере рядом с базой.

## Когда edge

| Задача | Где выполнять |
| --- | --- |
| редиректы, проверка сессии, A/B, заголовки | edge middleware |
| ответы, которые хорошо кешируются | edge с кешем |
| SSR со всеми данными в кеше или в репликах рядом | edge-рендеринг |
| страница с несколькими запросами к центральной базе | регион рядом с базой |
| тяжёлые вычисления, долгие задачи, нативные модули | обычный сервер или serverless в регионе |

---

## Красные флаги в ответе

- **«Edge — это просто быстрый serverless».** Это другой рантайм: веб-API, изоляты, жёсткие лимиты.
- **«Любая npm-библиотека заработает на edge».** Завязанные на Node.js — нет, часть модулей — только с флагом совместимости.
- **«Сохраню счётчик в глобальной переменной».** Изолят может смениться в любой момент, а точек присутствия сотни.
- **«Перенесём весь SSR на edge, будет быстрее».** С далёкой базой каждый запрос — круг через полмира.
- **«Edge-код привязан к платформе».** Код на веб-API переносим между рантаймами.

## Как спрашивают на собеседовании

::question
Что такое edge-вычисления?

#answer
Выполнение кода в точках присутствия сети рядом с пользователем, там же, где CDN раздаёт статику, а не в одном центральном регионе. Это даёт короткий путь до первого байта из любой страны, распределённую нагрузку и разгрузку источника.

#more
Рантаймы — Cloudflare Workers, Vercel и Netlify Edge, Deno Deploy, Fastly Compute — выполняют код в изолятах V8 или WebAssembly, поэтому стартуют за миллисекунды.
::

::question
Чем edge отличается от обычного serverless?

#answer
Serverless в регионе запускает полный Node.js или другой язык в выбранном регионе, с более щедрыми лимитами. Edge выполняет код в сотнях точек, в рантайме на веб-API с жёсткими лимитами процессорного времени и размера кода.

#more
Edge стартует почти мгновенно, но далёк от базы данных. Serverless в регионе можно разместить рядом с базой, и он подходит для тяжёлой логики и нативных модулей.
::

::question
Какие ограничения у edge-рантайма?

#answer
Только веб-API — `fetch`, `Request`, `Response`, `crypto.subtle`, потоки, кеш. Нет `process`, `require` и `fs`, часть модулей Node.js доступна только с флагом совместимости, лимиты на время и память жёсткие.

#more
Глобальное состояние изолята не гарантировано между запросами: изолят может смениться в любой момент. Состояние держат во внешних хранилищах — KV, Durable Objects, базе.
::

::question
В чём главная сложность edge?

#answer
Локальность данных: код рядом с пользователем, а база обычно в одном регионе. Несколько последовательных запросов к далёкой базе делают страницу на edge медленнее, чем сервер рядом с базой.

#more
Решения — держать на edge только логику без базы, кешировать ответы, использовать реплики для чтения рядом с пользователями или закреплять рендеринг за регионом базы.
::

::question
Что хорошо подходит для edge middleware?

#answer
Лёгкие решения до приложения без обращения к базе: редиректы по стране и языку, проверка cookie сессии, стабильные группы A/B, заголовки, ограничение частоты и блокировка ботов.

#more
Эти решения принимаются рядом с пользователем за миллисекунды и не нагружают сервер. Для группы A/B важно стабильное распределение по идентификатору посетителя, а не случайное на каждый запрос.
::

## Практика

::practice{title="Страница товара на edge стала медленнее"}
Страницу товара перенесли на edge-рендеринг ради скорости. У пользователей в Японии время до первого байта выросло с 300 до 800 мс. Страница делает три запроса к базе во Франкфурте: товар, остатки, отзывы.

#solution
Рендеринг стал ближе к пользователю, но каждый запрос к базе теперь идёт через полмира. В модели из проверки три последовательных запроса дали 730 мс против 246 мс на сервере рядом с базой. Варианты:

```ts
// 1. рендерить страницу рядом с базой, на edge — только маршрутизация
export const preferredRegion = 'fra1';

// 2. или один запрос вместо трёх — агрегирующий эндпоинт рядом с базой
const product = await fetch(`https://api.shop.example/products/${id}?include=stock,reviews`);

// 3. или кеш на edge: страница товара меняется редко
return new Response(html, { headers: { 'cache-control': 'public, s-maxage=60, stale-while-revalidate=600' } });
```

Edge оставляют для того, что не ходит в базу: редиректов, проверки сессии, A/B. Остатки, которые меняются часто, можно подгружать на клиенте отдельным запросом.
::

::practice{title="Ограничение частоты не работает"}
Middleware на edge ограничивает вход до пяти попыток в минуту с одного IP через объект `attempts` в глобальной переменной. Боты легко перебирают пароли.

#solution
Счётчик живёт в памяти одного изолята: изолятов много, они в разных точках присутствия и пересоздаются когда угодно. В проверке новый изолят начинал счётчик с нуля. Счётчик держат во внешнем хранилище с атомарным увеличением:

```js
export default {
  async fetch(request, env) {
    const ip = request.headers.get('cf-connecting-ip');
    const { success } = await env.LOGIN_LIMITER.limit({ key: ip });   // привязка Rate Limiting в Workers
    if (!success) return new Response('Слишком много попыток', { status: 429 });
    return fetch(request);
  },
};
```

На Cloudflare для этого есть привязка ограничения частоты и Durable Objects с согласованным состоянием, на других платформах — Redis-совместимые сервисы с атомарным `INCR`, например Upstash. Глобальная переменная годится только для кеша, который не жалко потерять.
::
