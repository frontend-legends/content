# Сквозная типобезопасность

Современный тренд - чтобы типы текли **через весь стек**: от базы данных через бэкенд и API до фронтенда и формы, как **единый источник истины**. Тогда изменение на одном конце сразу подсвечивает ошибку на другом - до запуска, а не в проде.

> Сам TypeScript - в главе [TypeScript](/content/typescript). Здесь - **сквозная** типобезопасность как парадигма современной разработки.

---

## Проблема, которую решает

Классическая боль: фронт и бэк **расходятся**. Бэкенд переименовал поле - фронтенд узнаёт об этом **в рантайме**, у пользователя. Типы дублируются вручную (интерфейс на фронте + модель на бэке) и рассинхронизируются.

```
бэкенд изменил API → фронт ничего не знает → ошибка в проде ❌
```

Сквозная типобезопасность делает так, что такое изменение - **ошибка компиляции**, видимая сразу.

---

## Слои типобезопасности

```
БД  →  бэкенд  →  API-контракт  →  фронтенд  →  форма
 │        │            │              │           │
Prisma  типы      tRPC/OpenAPI    инференс     Zod-схема
Drizzle                            типов
```

### БД → типы

ORM и типизированные построители запросов генерируют типы **из схемы БД**: **Prisma**, **Drizzle**, **Kysely**. Запрос к базе возвращает строго типизированный результат - опечатка в поле не скомпилируется.

### Типизированный контракт API

- **tRPC** - для **TS-монорепо**: клиент **выводит типы прямо с сервера**, без кодгена и схемы. Вызов процедуры на клиенте знает типы аргументов и результата.
- **OpenAPI codegen** / **GraphQL codegen** - генерируют типы клиента из схемы (работает и между языками).

```ts
// tRPC: тип user выведен из серверной процедуры, без ручных интерфейсов
const user = await trpc.user.byId.query({ id: 1 }); // user типизирован end-to-end
```

### Схема как источник истины

**Zod** (или Valibot) описывает данные **один раз**, а из схемы выводятся и типы, и рантайм-валидация ([формы и валидация](/content/ecosystem-libs/forms-and-validation)). Одна схема валидирует ответ API, форму и переменные окружения.

## Runtime vs compile-time

Критический нюанс. Типы TypeScript **стираются при компиляции** - в рантайме их нет ([тулинг TS](/content/advanced-tooling/typescript-tooling)). Поэтому на **границах** с внешним миром (ответ API, ввод формы, env) одних типов мало - нужна **рантайм-валидация**.

```ts
// ❌ ложная уверенность: каст не проверяет реальные данные
const user = (await res.json()) as User; // если API вернул другое - молчаливый баг

// ✅ рантайм-проверка на границе
const user = UserSchema.parse(await res.json()); // упадёт, если структура не та
```

<b class="text-on-semi-light">Правило</b> - <span class="text-gray">Внутри своего кода типы дают статические гарантии. Но всё, что приходит **извне** (сеть, пользователь, окружение), - не доверенное: его валидируют в рантайме (Zod) на входе. После валидации тип гарантирован и течёт дальше по стеку.</span>

---

## Движение «typesafe full-stack»

Сложился целый подход и популярные стеки - например, **T3** (Next.js + tRPC + Prisma + Zod + Tailwind): типы тянутся от схемы БД до JSX без единого ручного интерфейса. Это эталон сквозной типобезопасности в TS-экосистеме 2026.

---

## Выгоды

- **Ошибки в компиляции**, а не в проде.
- **Уверенность при рефакторинге** - переименовал поле, компилятор показал все места.
- **Автодополнение** через весь стек.
- **Самодокументируемость** - типы описывают контракты.

---

## Границы подхода

- **Только TypeScript** - tRPC-инференс работает TS↔TS в одной кодовой базе.
- **Связанность** - tRPC сцепляет фронт и бэк (монорепо); для публичного или кросс-языкового API нужны OpenAPI/GraphQL-кодген.
- Рантайм-валидация на границах всё равно обязательна - типы её не заменяют.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое сквозная типобезопасность?</b>
<span class="text-gray">Типы текут через весь стек (БД → бэкенд → API → фронт → форма) как единый источник истины. Изменение на одном конце даёт ошибку компиляции на другом - до запуска, без ручного дублирования типов.</span>

<b class="text-on-semi-light">Как tRPC обеспечивает типобезопасность без кодгена?</b>
<span class="text-gray">В TS-монорепо клиент напрямую выводит типы серверных процедур - вызов знает типы аргументов и результата. Работает только TS↔TS в одной кодовой базе; для кросс-языкового API нужен OpenAPI/GraphQL codegen.</span>

<b class="text-on-semi-light">Почему типов TypeScript недостаточно на границах?</b>
<span class="text-gray">Типы стираются при компиляции - в рантайме их нет. Внешние данные (API, формы, env) не доверены: их валидируют в рантайме (Zod). Каст `as User` не проверяет реальную структуру.</span>

<b class="text-on-semi-light">Как одна схема даёт и типы, и валидацию?</b>
<span class="text-gray">Zod-схема описывает данные один раз; из неё выводится статический тип (`z.infer`) и выполняется рантайм-проверка. Та же схема используется на клиенте, сервере и в формах.</span>

<b class="text-on-semi-light">Какие выгоды у сквозной типобезопасности?</b>
<span class="text-gray">Ошибки в компиляции вместо прода, уверенность при рефакторинге, автодополнение через стек и самодокументируемые контракты - меньше рассинхрона фронта и бэка.</span>
