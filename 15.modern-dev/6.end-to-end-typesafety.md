# Сквозная типобезопасность

Как сделать, чтобы типы шли через весь стек — от базы данных через сервер и API до компонента и формы: слои, общий источник истины, граница между статическими типами и проверкой на рантайме, сериализация, популярные стеки и пределы подхода. Спрашивают, что такое сквозная типобезопасность, почему типов TypeScript недостаточно на границах и как одна схема даёт и типы, и проверку. Глубже — почему переименование поля в схеме не сломало сервер при компиляции, почему `as User` хуже, чем ничего, и почему `Date` приходит строкой.

::tldr
- **Один источник истины для данных:** схема базы, схема валидации или серверный роутер, а типы остальных слоёв выводятся из него, а не пишутся руками.
- **Изменение на одном конце — ошибка компиляции на другом:** переименовали поле в общей схеме — компилятор показывает все места, где его читают.
- **Типы стираются при сборке:** на границах — ответ API, форма, переменные окружения, хранилище — данные проверяют схемой. `as User` ничего не проверяет и прячет ошибку.
- **JSON теряет типы:** `Date`, `Map`, `BigInt` превращаются в строки или ломаются. Нужен сериализатор вроде superjson или приведение схемой.
- **Подход ограничен TypeScript и общей кодовой базой:** для публичного API и других языков нужен независимый контракт — OpenAPI, GraphQL, Protobuf.
::

---

## Проблема

Сквозной пример — магазин в монорепозитории: база с товарами, сервер, общий пакет схем, карточка товара и форма редактирования в админке.

Классическая история: бэкенд переименовал `price` в `amount`, фронтенд собрался без ошибок, а на проде в карточке `undefined ₽`. Типы на фронтенде и модель на бэкенде описаны отдельно и разошлись при первом изменении (подробно о генерации типов из OpenAPI — в [Реалтайме и API-клиентах](/content/ecosystem-libs/realtime-and-api-clients)).

Сквозная типобезопасность превращает такое изменение в ошибку компиляции, которую видно до слияния.

## Слои

```text
база        →  сервер     →  контракт API      →  клиент           →  форма
Prisma,        функции       tRPC, OpenAPI,       выведенные типы     та же схема
Drizzle,       со схемами    GraphQL codegen      без ручных          для проверки
Kysely                                            интерфейсов         ввода
```

### Общая схема

В проверке схема товара жила в общем пакете, а сервер и клиент импортировали из неё и проверку, и тип:

```ts
// shared/product.ts
export const Product = z.object({ id: z.number(), title: z.string(), price: z.number().positive() });
export type Product = z.infer<typeof Product>;

// client/card.ts
export const priceLabel = (p: Product) => `${p.title} — ${p.price} ₽`;
```

После переименования `price` в `amount` в схеме `tsc` сразу показал клиент: `Property 'price' does not exist on type`. А вот сервер, который собирал объект и проверял его `Product.parse({ …, price: 1200 })`, компилятор **не** показал: `parse` принимает что угодно и проверяет только на рантайме. Ошибку на сервере поймала бы проверка — `safeParse` вернул `success: false`, — но уже при запуске. Чтобы и здесь ошибка была при компиляции, объект описывают через `satisfies`:

```ts
export const sample = { id: 7, title: 'Пуэр', price: 1200 } satisfies Product;
// error TS2353: Object literal may only specify known properties, and 'price' does not exist in type
```

В проверке так и вышло. Правило: свои объекты — через типы и `satisfies`, чужие данные — через схему.

### База данных

ORM и построители запросов выводят типы из схемы базы: **Prisma** генерирует клиент, **Drizzle** и **Kysely** описывают схему в TypeScript. В проверке Kysely с описанной таблицей `products` принял правильный запрос — тип результата содержал `title: string`, — а опечатку `select(['titel'])` отклонил при компиляции.

```ts
const rows = await db.selectFrom('products').select(['id', 'title']).where('price', '>', 1000).execute();
rows[0].title;   // string
```

Типы базы описывают ожидание, а не реальность: если миграцию не применили или в таблице оказались другие данные, компилятор об этом не узнает. Типы генерируют из миграций или из самой базы и проверяют в CI.

### Контракт API

- **tRPC** — в TypeScript-монорепо клиент выводит типы прямо из серверного роутера, без схемы и генерации;
- **OpenAPI и GraphQL с генерацией** — типы клиента из схемы API, работают между языками.

Оба варианта с проверкой разобраны в [Реалтайме и API-клиентах](/content/ecosystem-libs/realtime-and-api-clients): опечатки в путях, полях и аргументах там ловил `tsc`.

### Форма

Та же схема проверяет ввод в форме — обычно через резолвер библиотеки форм (подробно — в [Формах и валидации](/content/ecosystem-libs/forms-and-validation)). Сервер проверяет её ещё раз: проверка на клиенте — удобство, а не защита.

## Граница: типы и рантайм

Типы TypeScript **стираются при сборке** (подробно — в [Инструментах TypeScript](/content/advanced-tooling/typescript-tooling)). Всё, что приходит извне, — ответ API, ввод пользователя, `localStorage`, переменные окружения, сообщения из воркера, — компилятор не видел.

```ts
const product = (await res.json()) as Product;   // ничего не проверено
const product = Product.parse(await res.json()); // упадёт, если данные не те
```

В проверке ответ с ценой строкой `"1200 ₽"`, приведённый через `as`, дал `price + 300 === '1200 ₽300'` — ошибка ушла дальше по коду, далеко от места, где её можно понять. Проверка схемой отклонила тот же ответ и указала путь `price`.

Отсюда правило: **проверить на входе, дальше доверять типам**. После `parse` тип гарантирован и идёт дальше без повторных проверок.

## Сериализация

JSON поддерживает только строки, числа, логические значения, `null`, массивы и объекты. Остальное теряется:

```ts
const order = { id: 1, createdAt: new Date('2026-11-15T10:00:00Z') };
JSON.parse(JSON.stringify(order)).createdAt;   // строка '2026-11-15T10:00:00.000Z'
```

В проверке `createdAt` после JSON стал строкой, и `createdAt.getTime()` упал с `TypeError`, хотя тип на клиенте говорил `Date`. Это частая ложь типов на границе: тип описан на сервере, а по сети пришло другое.

Решения:

- **сериализатор** — superjson передаёт `Date`, `Map`, `Set`, `BigInt` с метаданными; в проверке дата вернулась как `Date` с тем же временем. В tRPC его подключают как `transformer`;
- **приведение схемой** — `z.coerce.date()` превращает строку в дату на границе;
- **строки в контракте** — передавать дату ISO-строкой и честно описать её как `string`.

Сложились популярные сборки — например, стек T3: Next.js, tRPC, Prisma или Drizzle, Zod и Tailwind, где типы идут от схемы базы до JSX без ручных интерфейсов. ## Выгоды и пределы

**Выгоды:**

- ошибки контракта видны при компиляции, а не у пользователей;
- переименование поля показывает все места использования — рефакторинг без страха;
- автодополнение через весь стек;
- типы документируют контракт.

**Пределы:**

- **только TypeScript и общая кодовая база** — вывод типов tRPC работает между TypeScript-сервером и TypeScript-клиентом;
- **связанность** — клиент и сервер выкатывают согласованно; для публичного API, мобильных клиентов и других языков нужен независимый контракт;
- **проверка на рантайме остаётся обязательной** на всех границах;
- **цена компиляции** — глубокий вывод типов через весь стек замедляет `tsc` и редактор в больших проектах.

---

## Красные флаги в ответе

- **«У нас TypeScript, данные с сервера типизированы».** Типы стёрты, ответ сервера никто не проверил.
- **«Напишу `as Product`».** Приведение прячет ошибку и переносит её туда, где её труднее понять.
- **«`parse` проверит и при компиляции».** Он проверяет только на рантайме; свои объекты — через `satisfies`.
- **«`Date` прилетит как `Date`».** После JSON это строка.
- **«tRPC подойдёт для публичного API».** Ему нужен общий TypeScript-код, публичному API — независимый контракт.
- **«Типы базы гарантируют данные в базе».** Они описывают ожидание; расхождение с миграциями компилятор не видит.

## Как спрашивают на собеседовании

::question
Что такое сквозная типобезопасность?

#answer
Типы идут через весь стек — база, сервер, API, клиент, форма — из одного источника истины: схемы базы, схемы валидации или серверного роутера. Изменение на одном конце даёт ошибку компиляции на другом, без ручного дублирования типов.

#more
Источник истины выбирают так, чтобы из него выводилось остальное: Zod-схема даёт и тип, и проверку; tRPC-роутер — типы клиента; Prisma или Drizzle — типы запросов к базе.
::

::question
Почему типов TypeScript недостаточно на границах?

#answer
Типы стираются при сборке и не проверяют, что пришло на самом деле. Ответ API, ввод пользователя, хранилище и переменные окружения проверяют схемой на входе, а дальше доверяют типам.

#more
`as User` ничего не проверяет: неверные данные проходят дальше, и ошибка всплывает далеко от причины. `parse` или `safeParse` падает на границе с понятным путём к полю.
::

::question
Как одна схема даёт и типы, и проверку?

#answer
Схему описывают один раз, например в Zod, — из неё выводят статический тип через `z.infer` и выполняют проверку на рантайме. Та же схема работает в форме на клиенте, на сервере и при разборе ответа API.

#more
Если схема лежит в общем пакете, переименование поля ломает компиляцию всех, кто его читает. Объекты, которые собирает сам код, описывают через `satisfies`, — тогда и они проверяются при компиляции.
::

::question
Какие данные теряются при передаче через JSON?

#answer
Всё, кроме строк, чисел, логических значений, `null`, массивов и объектов: `Date` становится строкой, `Map` и `Set` — пустыми объектами, `BigInt` вызывает ошибку, `undefined` пропадает.

#more
Тип при этом может по-прежнему говорить `Date`. Решения — сериализатор вроде superjson, приведение схемой `z.coerce.date()` или честный тип `string` в контракте.
::

::question
Где пределы подхода?

#answer
Вывод типов через весь стек работает в TypeScript и общей кодовой базе. Для публичного API, мобильных клиентов и сервисов на других языках нужен независимый контракт — OpenAPI, GraphQL или Protobuf.

#more
Кроме того, клиент и сервер становятся связаны — их выкатывают согласованно, — а проверка на рантайме на границах остаётся обязательной. В больших проектах глубокий вывод типов замедляет компиляцию.
::

## Практика

::practice{title="Сервер собрался, а API отдаёт ошибку"}
В общей схеме переименовали `price` в `amount`. Клиент сразу перестал компилироваться, его исправили. Сервер собрался без ошибок, а после выкладки эндпоинт товара отвечает 500.

```ts
export function getProduct(id: number): Product {
  return Product.parse({ id, title: row.title, price: row.price });
}
```

#solution
`parse` принимает `unknown` и проверяет только при выполнении: компилятор не видит, что объект собран по старой схеме. В проверке `tsc` показал клиент, но не этот сервер, а `safeParse` на тех же данных вернул ошибку. Свой объект описывают через тип:

```ts
export function getProduct(id: number): Product {
  const product = { id, title: row.title, amount: row.price } satisfies Product;
  return product;
}
```

С `satisfies` в проверке старое поле дало ошибку компиляции `TS2353`. `parse` оставляют там, где данные чужие: ответ внешнего API, ввод пользователя, строка из базы без типизированного клиента.
::

::practice{title="Дата заказа ломает страницу"}
Тип заказа на клиенте — `{ createdAt: Date }`, а `order.createdAt.toLocaleDateString()` падает с `TypeError: … is not a function`.

#solution
Сервер отдаёт `Date`, но JSON превращает её в строку, а тип на клиенте об этом не знает. В проверке `createdAt` после `JSON.parse` был строкой, и вызов метода даты упал. Варианты:

```ts
// 1. приведение на границе схемой
const Order = z.object({ id: z.number(), createdAt: z.coerce.date() });
const order = Order.parse(await res.json());

// 2. сериализатор, сохраняющий типы: в tRPC — transformer
const t = initTRPC.create({ transformer: superjson });
```

В проверке оба способа вернули настоящий `Date`. Третий вариант — описать в контракте `createdAt: string` и преобразовывать там, где дата нужна: честный тип лучше удобного, но ложного.
::
