# Local-first приложения

**Local-first** - подход, где данные живут **сначала локально** на устройстве, а синхронизация с сервером идёт в фоне. Такие приложения мгновенные, работают офлайн и поддерживают совместное редактирование «из коробки». Это растущее движение и заметный тренд senior-уровня.

---

## Проблема облачно-центричных приложений

В классической модели каждое действие идёт через сервер:

```
клик → запрос на сервер → ждём (спиннер) → ответ → обновили UI
       ломается офлайн, тормозит на плохой сети, данные не у тебя
```

Спиннеры на каждое действие, неработоспособность без сети, задержки, зависимость от сервера. Local-first переворачивает это.

---

## Идея

```
действие → мгновенно меняем ЛОКАЛЬНОЕ хранилище (источник истины)
         → в фоне синхронизируем с сервером и другими устройствами
```

Локальная база (IndexedDB/SQLite в браузере) - **основной** источник, UI читает и пишет в неё **мгновенно**, а sync-движок незаметно согласует данные между устройствами и сервером.

<b class="text-on-semi-light">Семь идеалов local-first</b> - <span class="text-gray">Сформулированы Ink & Switch: **быстро** (нет ожидания сети), **мультиустройство**, **офлайн**, **совместная работа**, **долговечность** (данные переживут сервис), **приватность**, **владение данными** пользователем. Не каждое приложение достигает всех, но это ориентир.</span>

---

## CRDT - сердце подхода

Главная техническая идея и частый вопрос. **CRDT (Conflict-free Replicated Data Type)** - структуры данных, которые **автоматически сливают** параллельные правки **без конфликтов**.

```
Устройство A (офлайн): правит документ
Устройство B (офлайн): правит тот же документ
→ оба онлайн → CRDT детерминированно сливает обе правки без конфликта
```

<b class="text-on-semi-light">Почему это нужно</b> - <span class="text-gray">Если двое (или один на двух устройствах) меняют данные офлайн, при синхронизации возникает конфликт. CRDT решают его **математически**: операции коммутативны и сходятся к одному результату независимо от порядка. Это и делает возможными офлайн-редактирование и многопользовательскую работу в реальном времени. Реализации: **Yjs** (стандарт для коллаборации), **Automerge**.</span>

Альтернативы разрешения конфликтов: **last-write-wins** (проще, но теряет данные) и **OT** (Operational Transform - старый подход Google Docs, сложнее CRDT).

---

## Sync-движки

Писать синхронизацию и CRDT руками тяжело - есть готовые движки и платформы:

| Инструмент | Фокус |
|-----------|-------|
| **Yjs** | совместное редактирование (CRDT) |
| **Automerge** | CRDT-документы |
| **ElectricSQL** | синхронизация Postgres ↔ локальный SQLite |
| **Zero** / **Replicache** | sync с оптимистичными мутациями |
| **Liveblocks** | presence + коллаборация |
| **Convex**, **Triplit**, **Jazz** | реактивные синхронизируемые БД |

## Выгоды

- **Мгновенный UX** - нет спиннеров, всё локально.
- **Офлайн** - приложение работает без сети, синхронизируется потом.
- **Реалтайм-коллаборация** - несколько пользователей сразу.
- **Устойчивость** - сбой сети/сервера не блокирует работу.

Так работают «быстрые» приложения вроде **Linear** и **Figma** - ощущение мгновенности именно от local-first-архитектуры.

---

## Сложности

- **Сложность синхронизации** - конфликты, порядок, частичные данные.
- **Авторизация и права** - кто что может синхронизировать и видеть.
- **Лимиты хранилища** браузера, **миграции схемы** локальных данных.
- **Не для всего** - там, где сервер обязан быть единственным источником истины (банковский баланс, билеты), local-first не подходит.

---

## Когда использовать

```
Редакторы, доски, заметки, таск-трекеры      → local-first (мгновенность + коллаборация)
Совместное редактирование в реальном времени  → CRDT (Yjs)
Офлайн-критичные приложения                    → local-first
Строгая консистентность, сервер - истина        → классическая клиент-сервер модель
```

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое local-first?</b>
<span class="text-gray">Подход, где данные живут сначала локально (источник истины на устройстве), а синхронизация с сервером идёт в фоне. Даёт мгновенный UX, офлайн и совместную работу.</span>

<b class="text-on-semi-light">Что такое CRDT и зачем они нужны?</b>
<span class="text-gray">Conflict-free Replicated Data Types - структуры, автоматически сливающие параллельные правки без конфликтов (операции коммутативны и сходятся). Делают возможными офлайн-редактирование и реалтайм-коллаборацию. Реализации - Yjs, Automerge.</span>

<b class="text-on-semi-light">Чем CRDT отличается от last-write-wins?</b>
<span class="text-gray">Last-write-wins выбирает одну правку и теряет другую. CRDT детерминированно сливают обе без потери данных, независимо от порядка. CRDT сложнее, но сохраняют изменения.</span>

<b class="text-on-semi-light">Почему local-first приложения ощущаются мгновенными?</b>
<span class="text-gray">UI читает и пишет в локальное хранилище без ожидания сети (оптимистично), а синхронизация идёт в фоне. Нет спиннеров на каждое действие - как в Linear/Figma.</span>

<b class="text-on-semi-light">Когда local-first не подходит?</b>
<span class="text-gray">Когда нужна строгая консистентность и сервер обязан быть единственным источником истины (финансовые балансы, бронирования). Там классическая клиент-серверная модель надёжнее.</span>
