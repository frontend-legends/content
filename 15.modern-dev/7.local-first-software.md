# Local-first приложения

Подход, при котором данные живут сначала на устройстве, а синхронизация идёт в фоне: чем он отличается от «каждое действие через сервер», принципы local-first, CRDT и как они сливают параллельные правки, альтернативы — «последняя запись побеждает» и операционные преобразования, движки синхронизации, хранилище в браузере, выгоды, сложности и когда подход не подходит. Спрашивают, что такое local-first и CRDT и чем CRDT отличается от «последней записи». Глубже — почему CRDT сохранил обе правки текста, но только одну цену, и почему local-first не годится для баланса счёта.

::tldr
- **Источник истины — на устройстве:** интерфейс читает и пишет в локальное хранилище мгновенно, а синхронизация с сервером и другими устройствами идёт в фоне. Нет спиннеров, работает офлайн.
- **CRDT — структуры данных, которые сходятся сами:** правки, сделанные офлайн на разных устройствах, после обмена дают одинаковый результат при любом порядке и повторах.
- **Для текста и списков CRDT сохраняет обе правки,** для одного и того же поля — выбирает одно значение по детерминированному правилу. Это не магия против конфликтов, а гарантия, что все придут к одному.
- **«Последняя запись побеждает» проще, но теряет данные:** правка, пришедшая чуть раньше, исчезает целиком.
- **Не для всего:** где сервер обязан быть единственным арбитром — деньги, остатки, бронирования, — нужна классическая модель с проверкой на сервере.
::

---

## Проблема

Сквозной пример — редактор описаний товаров в админке магазина: два контент-менеджера, ноутбук в поезде без сети, черновики и совместная правка одного описания.

```text
классика: клик → запрос → ожидание → ответ → обновление интерфейса
          без сети не работает, на плохой сети тормозит, данные — у сервера
```

Оптимистичные обновления в библиотеках загрузки данных частично прячут ожидание (подробно — в [Загрузке данных React](/content/reactjs/data-fetching)), но источник истины остаётся на сервере: без сети приложение всё равно бесполезно.

---

## Идея

```text
действие → сразу меняем локальную базу → интерфейс обновился
         → в фоне: синхронизация с сервером и другими устройствами
```

Локальная база — IndexedDB, SQLite в WebAssembly с OPFS — **основной** источник данных для интерфейса. В проверке черновик, записанный в IndexedDB в Chromium, пережил перезагрузку страницы, а `navigator.storage.estimate()` вернул ненулевую квоту. Движок синхронизации обменивается изменениями с сервером и другими устройствами, когда есть сеть.

### Принципы

Исследовательская лаборатория Ink & Switch сформулировала семь идеалов local-first:

- **быстро** — без ожидания сети;
- **несколько устройств** — данные везде;
- **офлайн** — работа без сети;
- **совместная работа** — несколько человек одновременно;
- **долговечность** — данные переживают сервис;
- **приватность** — шифрование, данные не обязательно читаемы сервером;
- **владение** — пользователь контролирует свои данные.

Не каждое приложение достигает всех, но это ориентир.

## CRDT

**CRDT** — conflict-free replicated data types, реплицируемые типы данных без конфликтов. Их операции устроены так, что реплики, получившие одинаковый набор изменений, приходят к одинаковому состоянию — **независимо от порядка и повторов**.

### Текст

В проверке описание «Пуэр из Юньнани.» было у двух менеджеров. Офлайн Аня дописала « Выдержка 5 лет.» в конец, Петя — «Новинка! » в начало. После обмена изменениями на :term[Yjs]{def="библиотека CRDT для совместного редактирования"}:

```js
Y.applyUpdate(docA, updateFromB);
Y.applyUpdate(docB, updateFromA);
docA.getText('description').toString();
// 'Новинка! Пуэр из Юньнани. Выдержка 5 лет.'
```

У обоих — одинаковый текст с **обеими** правками. Ещё две реплики, получившие изменения в другом порядке и одно — дважды, пришли к тому же результату. Повтор безопасен, порядок не важен — это и делает синхронизацию через ненадёжную сеть простой.

### Одно поле

В том же документе оба менеджера офлайн поменяли цену: Аня поставила 1100, Петя — 1300. После обмена у обоих оказалось **1300**: реплики сошлись, но одна правка проиграла. Для одиночного значения CRDT не может «слить» два числа — он гарантирует, что все выберут одно и то же по детерминированному правилу (в Yjs — по идентификатору клиента).

Отсюда практический вывод: CRDT убирает расхождение реплик, но не смысловые конфликты. Если важно не потерять параллельное изменение цены, его моделируют иначе — журналом изменений, отдельными полями или явным подтверждением.

### Альтернативы

| Подход | Как решает конфликт | Цена |
| --- | --- | --- |
| последняя запись побеждает | побеждает правка с большим временем | правка, пришедшая раньше, теряется целиком |
| операционные преобразования | сервер пересчитывает операции относительно друг друга | нужен центральный сервер, сложные правила |
| CRDT | структура данных сходится сама | метаданные, сложность реализации |

В проверке «последняя запись побеждает» для того же описания оставила «Новинка! Пуэр из Юньнани.» — и «Выдержка 5 лет» пропала. Операционные преобразования исторически использовал Google Docs; CRDT не требует центрального сервера, поэтому подходит для офлайна и прямого обмена между устройствами.

### Цена CRDT

Каждый символ и элемент несёт метаданные — кто и после чего его вставил, — а удалённое оставляет след, чтобы поздние правки нашли своё место. Yjs хорошо сжимает такие следы: в проверке пустой текст после 2000 вставок и удалений занял 16 байт против 2 у нового пустого документа. Но в документах с долгой историей и множеством авторов размер растёт, и это учитывают при хранении и загрузке.

## Движки синхронизации

Писать синхронизацию самому тяжело: порядок, повторы, частичная загрузка, права, миграции. Готовые решения:

| Инструмент | Модель |
| --- | --- |
| Yjs, Automerge, Loro | CRDT-документы: текст, списки, словари |
| Liveblocks | совместная работа и присутствие как сервис |
| ElectricSQL, PowerSync | синхронизация Postgres с локальной базой |
| Zero, Replicache | синхронизация с оптимистичными изменениями и сервером-арбитром |
| Jazz, Triplit, Instant | синхронизируемые базы с реактивными запросами |

Две модели: **CRDT без арбитра** — подходит для документов и офлайна — и **сервер-арбитр с оптимистичными изменениями** — клиент применяет изменение сразу, сервер подтверждает или откатывает. Вторая проще для бизнес-правил и прав доступа.

Совместное редактирование с курсорами в редакторах — Yjs поверх :term[ProseMirror]{def="библиотека для построения текстовых редакторов в браузере"}, :term[TipTap]{def="редактор на основе ProseMirror с готовыми расширениями"} или :term[Lexical]{def="библиотека текстового редактора от Meta"} (подробно — в [Контенте и взаимодействиях](/content/ecosystem-libs/rich-content-and-interactions)).

## Выгоды

- **мгновенный интерфейс** — нет ожидания сети на каждое действие;
- **офлайн** — работа без сети, синхронизация потом;
- **совместная работа** — несколько человек одновременно, с курсорами и присутствием;
- **устойчивость** — сбой сервера не останавливает работу.

Так устроены приложения, известные ощущением мгновенности, — например, Linear с локальной базой и синхронизацией и Figma с совместным редактированием.

---

## Сложности

- **права доступа** — что можно синхронизировать на устройство и что пользователь может изменить; проверка остаётся на сервере;
- **частичная загрузка** — весь каталог на телефон не положить; нужны правила, что синхронизировать;
- **миграции схемы** — данные на тысячах устройств в старом формате;
- **хранилище браузера** — квоты, вытеснение при нехватке места, `navigator.storage.persist()` для защиты от удаления;
- **отладка** — состояние распределено по устройствам, ошибки воспроизводятся трудно;
- **смысловые конфликты** — CRDT сводит реплики, но не решает, какая цена правильная.

---

## Когда подходит

| Ситуация | Подход |
| --- | --- |
| редакторы, заметки, доски, трекеры задач | local-first |
| совместное редактирование документа | CRDT: Yjs, Automerge |
| полевые приложения, склад, работа без стабильной сети | local-first с синхронизацией |
| деньги, остатки, бронирования, билеты | сервер — единственный арбитр |
| каталог и заказы в магазине | классика с кешем и оптимистичными обновлениями |

В магазине local-first естественен для админки — черновики описаний, совместная правка, — но не для оформления заказа: два покупателя не должны «сойтись» на одной последней упаковке. Это проверяет сервер транзакцией (подробно — в [За пределами фронтенда](/content/additional-topics/beyond-frontend)).

## Красные флаги в ответе

- **«CRDT решает все конфликты».** Реплики сходятся, но для одного поля одна правка проигрывает.
- **«Last-write-wins — тоже нормально».** Правка, пришедшая раньше, теряется целиком.
- **«Local-first — это кеш на клиенте».** Это другой источник истины: локальная база, а не копия ответа сервера.
- **«Сделаем на local-first оплату».** Деньги и остатки требуют сервера-арбитра.
- **«Права проверим на клиенте, данные же локальные».** Синхронизация доставит изменения на сервер — проверка там.
- **«IndexedDB хранит навсегда».** Браузер может вытеснить данные без `persist()`.

## Как спрашивают на собеседовании

::question
Что такое local-first?

#answer
Подход, при котором источник истины — локальная база на устройстве: интерфейс читает и пишет в неё мгновенно, а синхронизация с сервером и другими устройствами идёт в фоне. Это даёт мгновенный интерфейс, работу офлайн и совместное редактирование.

#more
Локальное хранилище — IndexedDB или SQLite в WebAssembly с OPFS. Ink & Switch сформулировали семь идеалов: скорость, несколько устройств, офлайн, совместная работа, долговечность, приватность и владение данными.
::

::question
Что такое CRDT и зачем они нужны?

#answer
Реплицируемые типы данных, у которых реплики, получившие одинаковый набор изменений, приходят к одинаковому состоянию независимо от порядка и повторов. Это позволяет править данные офлайн на разных устройствах и сливать изменения без центрального арбитра.

#more
Для текста и списков сохраняются все правки, для одного поля выбирается одно значение по детерминированному правилу. Реализации — Yjs, Automerge, Loro.
::

::question
Чем CRDT отличается от «последней записи»?

#answer
«Последняя запись побеждает» оставляет правку с большим временем и теряет другую целиком. CRDT для текста и списков сохраняет обе правки, а для одного значения детерминированно выбирает одно, — но всегда так, что все реплики сходятся.

#more
«Последняя запись» ещё и зависит от часов устройств, которые могут расходиться. CRDT опирается на структуру изменений, а не на время.
::

::question
Почему local-first приложения ощущаются мгновенными?

#answer
Каждое действие сразу меняет локальную базу и интерфейс, без ожидания сети. Синхронизация идёт в фоне, и пользователь не видит ни спиннеров, ни задержек.

#more
Это отличается от оптимистичных обновлений поверх серверного источника истины: там без сети приложение бесполезно, а в local-first продолжает работать.
::

::question
Когда local-first не подходит?

#answer
Когда сервер должен быть единственным арбитром: деньги, остатки на складе, бронирования, билеты. Там два пользователя не должны «сойтись» на одном ресурсе — это решает транзакция на сервере.

#more
Ещё сложности — права доступа, частичная загрузка больших данных и миграции локальных схем. Часто разумен смешанный вариант: local-first для черновиков и редактирования, классика для операций с последствиями.
::

## Практика

::practice{title="Пропала правка описания"}
Админка хранит описание товара строкой и при синхронизации берёт версию с большим временем изменения. Менеджер дописала абзац в поезде, её коллега в офисе поправил первую фразу — после синхронизации абзац исчез.

#solution
Это «последняя запись побеждает»: в проверке так пропала «Выдержка 5 лет». Описание переводят на CRDT-текст:

```js
import * as Y from 'yjs';

const doc = new Y.Doc();
const description = doc.getText('description');

doc.on('update', (update) => queue.push(update));          // офлайн — копим изменения
online(() => queue.flush((u) => api.post('/sync', u)));    // онлайн — отправляем
api.on('update', (u) => Y.applyUpdate(doc, u));            // чужие изменения — применяем
```

В проверке те же правки на Yjs сошлись в «Новинка! Пуэр из Юньнани. Выдержка 5 лет.» у всех реплик, независимо от порядка и повторов. Для редактора с форматированием Yjs подключают к TipTap или ProseMirror, а изменения сохраняют в базе как обновления документа.
::

::practice{title="Две скидки на один товар"}
После перехода на CRDT два менеджера офлайн поставили разные цены на один товар. После синхронизации у обоих одна цена, но одна из правок «тихо» пропала, и никто об этом не узнал.

#solution
CRDT для одного поля выбирает одно значение: в проверке параллельные 1100 и 1300 сошлись в 1300 у обоих. Реплики согласованы, а смысловой конфликт не решён. Варианты:

```js
// 1. цену меняет только сервер — с проверкой прав и журналом
await api.post(`/products/7/price`, { price: 1100, reason: 'распродажа' });

// 2. или хранить предложения, а не значение, и показывать конфликт человеку
doc.getArray('priceProposals').push([{ price: 1100, by: 'anya', at: Date.now() }]);
```

Описание и черновики остаются local-first, а цена — бизнес-данные с последствиями — проходит через сервер-арбитр. Это обычный смешанный вариант для админок.
::
