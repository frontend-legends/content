# Сигналы и реактивность

Один из самых заметных сдвигов в фреймворках 2023–2026 - **конвергенция на сигналах**. Solid, Vue, Svelte, Angular, Preact - все пришли к **fine-grained реактивности**, а TC39 обсуждает встраивание сигналов в сам JavaScript. Понимать этот тренд - сильный senior-сигнал.

---

## Что такое сигнал

**Сигнал** - контейнер реактивного значения. Чтение **отслеживает** зависимость, запись **оповещает** подписчиков. Из сигналов строят производные значения и эффекты.

```js
const count = signal(0);
const double = computed(() => count.value * 2); // авто-зависит от count
effect(() => console.log(double.value));        // перезапустится при изменении

count.value = 5; // double пересчитается, effect выполнится - автоматически
```

Это та же идея, что в [реактивности Vue](/content/vuejs/reactivity-fundamentals) (`ref` - по сути сигнал) и в `computed`/`watch`.

---

## Fine-grained реактивность

Ключевое отличие от модели React. Сигналы обновляют **ровно то, что зависит** от изменившегося значения - конкретный текстовый узел, а не весь компонент.

```
React (VDOM):     state изменился → перерисовать компонент → продиффить → обновить DOM
Сигналы:          signal изменился → обновить ТОЛЬКО зависящие места DOM напрямую
```

<b class="text-on-semi-light">Почему это важно</b> - <span class="text-gray">Нет ре-рендера компонента и diffing'а виртуального дерева - изменение «хирургически» применяется туда, где значение реально используется. Меньше работы, выше производительность, и **не нужна ручная мемоизация** (`memo`/`useMemo`), потому что нет лишних ре-рендеров по определению.</span>

---

## Кто перешёл на сигналы

| Фреймворк | Реализация |
|-----------|-----------|
| **SolidJS** | сигналы - ядро, пионер подхода |
| **Vue** | `ref`/`reactive` - сигналы под капотом (давно) |
| **Svelte 5** | **runes**: `$state`, `$derived`, `$effect` |
| **Angular** | сигналы с версии 16/17 |
| **Preact** | `@preact/signals` |
| **Qwik** | сигналы + resumability |

```js
// Svelte 5 runes
let count = $state(0);
let double = $derived(count * 2);
$effect(() => console.log(double));
```

> Даже **React** движется к похожему результату с другой стороны - через [React Compiler](/content/reactjs/performance), который авто-мемоизирует, добиваясь точечных обновлений без ручной работы.

---

## TC39 Signals proposal

Самое значимое: сигналы предлагают **стандартизировать в самом JavaScript** (TC39 proposal, ранняя стадия). Идея - единый **примитив реактивности** в языке, на котором смогут строиться все фреймворки.

<b class="text-on-semi-light">Зачем стандарт</b> - <span class="text-gray">Сейчас у каждого фреймворка своя реализация сигналов - несовместимые и дублирующие. Общий примитив в языке дал бы интероперабельность (библиотеки, работающие в любом фреймворке) и единую, оптимизированную браузером основу. То, что конкуренты согласились работать над общим стандартом, - сильный знак, что сигналы «победили» как модель.</span>

---

## Под капотом: ленивость и согласованность

Сигналы - не просто «значение + колбэки». Качественная реализация решает две тонкие задачи:

- **Ленивые вычисления (push-pull)** - производный сигнал (`computed`) пересчитывается **при чтении** результата, а не сразу при изменении источника, и кеширует его. Если `double` никто не читает - он не считается. Запись лишь помечает зависимые «грязными» (push), пересчёт происходит при чтении (pull).
- **Glitch-free (проблема ромба)** - если `c` зависит от `a` и `b`, а оба производны от `x`, наивная реализация пересчитала бы `c` дважды и на миг показала бы несогласованное промежуточное значение («глитч»). Хорошие сигналы пересчитывают в **топологическом порядке** ровно один раз - всегда согласованно.

<b class="text-on-semi-light">Зачем это знать</b> - <span class="text-gray">Ленивость и glitch-free отличают «настоящие» сигналы от наивного pub-sub и объясняют, почему их выделяют в TC39-стандарт - это нетривиальный алгоритм, который не стоит переизобретать. На собесе про сигналы хороший признак - упомянуть автоматическое отслеживание зависимостей, ленивые computed и согласованность.</span>

## Сигналы vs VDOM

Две философии обновления UI:

| | Сигналы (fine-grained) | VDOM (React) |
|--|------------------------|--------------|
| Единица обновления | конкретное место в DOM | компонент → diff |
| Отслеживание зависимостей | автоматическое | ручное (deps-массивы) |
| Мемоизация | не нужна | нужна (или компилятор) |
| Ментальная модель | «значение и его подписчики» | «снапшот и ре-рендер» |

<b class="text-on-semi-light">Ставки</b> - <span class="text-gray">React сделал ставку на VDOM + компилятор (авто-мемоизация). Остальные - на сигналы (точечные обновления by design). Обе ведут к одной цели: минимум лишней работы без ручной оптимизации. Индустрия в основном склонилась к сигналам как к более прямому пути - этому учат Solid, Vue и старый Knockout.</span>

---

## Ментальная модель

С сигналами производное состояние **отслеживается само** - не нужно перечислять зависимости (как в `useEffect`/`useMemo`). Меньше ловушек вроде stale closure и забытых зависимостей. Связано с темой «[не нужен Effect](/content/reactjs/effects-and-synchronization)»: многое решается производными сигналами.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое сигнал?</b>
<span class="text-gray">Контейнер реактивного значения: чтение отслеживает зависимость, запись оповещает подписчиков. Из сигналов строят производные (computed) и эффекты, которые обновляются автоматически.</span>

<b class="text-on-semi-light">Чем fine-grained реактивность отличается от модели React?</b>
<span class="text-gray">Сигналы обновляют ровно зависящие места DOM напрямую, без ре-рендера компонента и diffing'а VDOM. Поэтому выше производительность и не нужна ручная мемоизация.</span>

<b class="text-on-semi-light">Почему индустрия сходится на сигналах?</b>
<span class="text-gray">Точечные обновления, более простая модель, отсутствие ручной мемоизации и dependency-массивов. К сигналам пришли Solid, Vue, Svelte 5, Angular, Preact; React добивается похожего через компилятор.</span>

<b class="text-on-semi-light">Что такое TC39 Signals proposal?</b>
<span class="text-gray">Предложение стандартизировать сигналы в самом JavaScript - единый примитив реактивности для всех фреймворков. Дал бы интероперабельность и общую оптимизированную основу.</span>

<b class="text-on-semi-light">Сигналы или VDOM - кто «прав»?</b>
<span class="text-gray">Обе модели стремятся к минимуму лишней работы без ручной оптимизации: React - через VDOM + компилятор, остальные - через сигналы by design. Индустрия в основном склонилась к сигналам как более прямому пути.</span>

<b class="text-on-semi-light">Как сигналы избегают лишних пересчётов и «глитчей»?</b>
<span class="text-gray">Производные сигналы ленивы (pull): пересчитываются при чтении и кешируются, а запись лишь помечает зависимые «грязными» (push-pull). При ромбовидных зависимостях пересчёт идёт в топологическом порядке ровно один раз - glitch-free, без несогласованных промежуточных значений.</span>
