# Сигналы и реактивность

Почему фреймворки сошлись на сигналах: что такое сигнал, производные значения и эффекты, точечная реактивность против перерисовки компонента, кто как реализовал сигналы, чем настоящие сигналы отличаются от наивной подписки — ленивость и отсутствие промежуточных состояний, — предложение TC39 и что это значит для React. Спрашивают, что такое сигнал, чем точечная реактивность отличается от модели React и почему индустрия сходится на сигналах. Глубже — что такое «ромб» зависимостей, почему `computed` не считается до чтения и почему в стандарте нет `effect`.

::tldr
- **Сигнал — значение с подписчиками:** чтение запоминает, кто зависит, запись уведомляет. Из сигналов строят производные значения (`computed`) и эффекты, которые сами знают свои зависимости.
- **Точечная реактивность обновляет только то, что зависит от изменения** — конкретный текстовый узел, а не компонент целиком. Нет перерисовки детей, нет сравнения деревьев, мемоизация вручную не нужна.
- **Настоящие сигналы — не просто подписка:** производные значения ленивы и кешируются, а при «ромбе» зависимостей пересчёт идёт один раз и без промежуточных несогласованных значений.
- **Сигналы есть почти везде:** Solid, Vue (`ref`), Svelte 5 (`$state`, `$derived`), Angular, Preact, Qwik. React идёт другим путём — перерисовка с автоматической мемоизацией компилятором.
- **TC39 обсуждает сигналы в языке:** `Signal.State`, `Signal.Computed` и `Watcher` как общий примитив для фреймворков. Эффекты и планирование остаются за фреймворками.
::

## Что такое сигнал

Сквозной пример — шапка магазина со счётчиком корзины и итогом заказа с налогом и скидкой.

```js
import { signal, computed, effect } from '@preact/signals-core';

const count = signal(0);
const label = computed(() => `В корзине: ${count.value}`);
effect(() => console.log(label.value));   // «В корзине: 0»

count.value = 2;                          // «В корзине: 2» — само
```

- **сигнал** — значение; чтение `count.value` внутри `computed` или `effect` записывает зависимость, запись уведомляет зависимых;
- **производное** — значение, вычисляемое из других сигналов;
- **эффект** — действие при изменении: обновить DOM, записать в хранилище, отправить метрику.

Зависимости не перечисляют руками, как в массиве зависимостей `useEffect`, — они собираются при выполнении. Во Vue `ref` и `computed` устроены так же (подробно — в [Основах реактивности Vue](/content/vuejs/reactivity-fundamentals)).

## Точечная реактивность

| | Сигналы | React |
| --- | --- | --- |
| Что происходит при изменении | обновляются места, которые прочитали значение | компонент выполняется заново, вывод сравнивается с прошлым |
| Единица обновления | текстовый узел, атрибут, свойство | компонент и его поддерево |
| Зависимости | собираются автоматически | перечисляются руками или выводятся компилятором |
| Мемоизация | не нужна | `memo`, `useMemo` или React Compiler |

В проверке у шапки с состоянием счётчика в React одно изменение перезапустило все три функции — `Header`, `Badge` и `ProductList`, хотя список товаров от счётчика не зависит. Вариант на сигналах выполнил функции разметки один раз, а дальше на два изменения счётчика поменял только текст в бейдже — `'0' → '1' → '2'`; узел списка остался тем же объектом.

В React такую лишнюю работу убирают `memo` или компилятор (подробно — в [Производительности React](/content/reactjs/performance)). В модели сигналов её нет по построению: функция компонента выполняется один раз и связывает сигналы с узлами DOM.

## Кто использует

| Фреймворк | Сигналы |
| --- | --- |
| SolidJS | `createSignal`, `createMemo`, `createEffect` — ядро фреймворка |
| Vue | `ref`, `computed`, `watchEffect` — давно и под капотом |
| Svelte 5 | руны `$state`, `$derived`, `$effect` |
| Angular | `signal`, `computed`, `effect`; переход от Zone.js к сигналам |
| Preact | `@preact/signals` |
| Qwik | сигналы плюс возобновление вместо гидратации |
| Lit | `@lit-labs/signals` поверх предложения TC39 |

```js
// Svelte 5
let count = $state(0);
let label = $derived(`В корзине: ${count}`);
$effect(() => console.log(label));
```

Синтаксис разный, модель одна. Сигналы как способ хранить клиентское состояние среди других библиотек — в [Состоянии и данных](/content/ecosystem-libs/state-and-data-libraries).

## Больше, чем подписка

Наивная реализация — «значение плюс список колбэков, при записи вызвать всех». Её недостатки видны на **ромбе** зависимостей:

```text
         price
        ↙     ↘
   withTax   discount
        ↘     ↙
         total
```

В проверке наивная версия при смене цены со 100 на 200 пересчитала `total` **дважды**: сначала `230` — новый налог со старой скидкой, такого значения не должно было существовать, — потом правильные `220`. Эффект, который рисует итог, показал бы пользователю мелькнувшую неверную цену или отправил бы её на сервер. Это называют **глитчем**.

Настоящие сигналы решают это двумя приёмами:

- **сначала пометить, потом пересчитать** — запись только помечает зависимых устаревшими, а пересчёт идёт при чтении, в порядке зависимостей и один раз. В проверке :term[Preact]{def="лёгкая альтернатива React с тем же API"} Signals дал эффекту ровно `110`, затем `220` — без промежуточных `230`;
- **ленивость** — производное значение не считается, пока его не прочитали, и кеширует результат. В проверке две записи в список товаров не вызвали ни одного вычисления суммы, а два последующих чтения — одно.

### Динамические зависимости

Зависимости пересобираются при каждом выполнении. В проверке эффект `showDelivery ? delivery : price` сначала не реагировал на `delivery` — он его не читал, — а после переключения стал реагировать на `delivery` и перестал на `price`. Подписок на то, что больше не читается, не остаётся.

### Пакеты изменений

Несколько записей подряд объединяют, чтобы эффекты сработали один раз: в проверке `batch` с двумя записями дал один запуск эффекта. Фреймворки делают это сами — обновления DOM собираются и применяются в микрозадаче (подробно — в [Продвинутой реактивности Vue](/content/vuejs/reactivity-advanced)).

## Предложение TC39

Сигналы предлагают добавить в сам JavaScript как общий примитив — чтобы библиотеки работали поверх одного механизма, а не своих несовместимых реализаций. Над предложением вместе работают авторы Angular, Solid, Vue, Svelte, Preact, :term[Ember]{def="фреймворк для больших SPA с соглашениями вместо настроек"} и других. Стадия ранняя, но существует полифил:

```js
import { Signal } from 'signal-polyfill';

const price = new Signal.State(100);
const total = new Signal.Computed(() => price.get() * 1.2 - price.get() * 0.1);
total.get();   // 110
```

В проверке в полифиле были `State`, `Computed` и `subtle.Watcher`, а `Signal.effect` — нет. Это сознательно: **когда** и **как** выполнять эффекты — сразу, в микрозадаче, перед кадром — решает фреймворк. `Watcher` только сообщает, что что-то устарело. В проверке эффект на `Watcher` с откладыванием в микрозадачу на две записи подряд перерисовал итог один раз — сразу правильным `330`.

| Событие | Состояние |
| --- | --- |
| предложение TC39 Signals | ранняя стадия, полифил `signal-polyfill` |
| в проверке | `signal-polyfill` 0.2, `@preact/signals-core` 1.14 |

Актуально на ноябрь 2026. Как читать стадии предложений — в [Современном JavaScript](/content/javascript/modern-js).

## Сигналы и React

React сознательно держится модели «снимок состояния и перерисовка»: компонент — функция от пропсов и состояния, каждый рендер видит согласованный снимок. Лишнюю работу убирает **React Compiler**, автоматически мемоизируя значения и компоненты. Цели у подходов общие — минимум лишней работы без ручной оптимизации, — пути разные:

| | Сигналы | React с компилятором |
| --- | --- | --- |
| Что гарантирует согласованность | порядок пересчёта графа | снимок состояния на рендер |
| Где цена | граф зависимостей в памяти, правила чтения значений | выполнение функций и сравнение вывода |
| Ловушки | потеря реактивности при деструктуризации, чтение вне отслеживания | лишние рендеры без компилятора, устаревшие замыкания |

В React внешнее изменяемое состояние, в том числе сигналы, подключают через `useSyncExternalStore` (подробно — в [Управлении состоянием React](/content/reactjs/state-management)).

## Ментальная модель

С сигналами производное состояние описывают один раз — как `computed`, — и оно всегда актуально. Это снимает класс ошибок: забытые зависимости эффекта, устаревшие замыкания, эффекты для синхронизации одного состояния с другим (подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization)). Взамен появляются свои правила: значение нужно **читать** внутри отслеживаемого контекста — деструктуризация `const { value } = count` или чтение в обработчике вне эффекта теряет связь.

## Красные флаги в ответе

- **«Сигнал — это просто EventEmitter».** Наивная подписка даёт промежуточные состояния и лишние пересчёты.
- **«`computed` считается при каждой записи».** Он ленивый и считается при чтении.
- **«С сигналами компонент перерисовывается быстрее».** Он не перерисовывается — обновляются конкретные узлы.
- **«React тоже на сигналах».** React держится перерисовки и снимков, лишнюю работу убирает компилятор.
- **«В стандарте будет `effect`».** Планирование эффектов оставлено фреймворкам, в предложении — `Watcher`.
- **«Достану значение деструктуризацией».** Связь с сигналом теряется.

## Как спрашивают на собеседовании

::question
Что такое сигнал?

#answer
Значение с подписчиками: чтение внутри производного значения или эффекта запоминает зависимость, запись уведомляет зависимых. Из сигналов строят `computed` и эффекты, которые сами знают свои зависимости.

#more
Зависимости собираются при выполнении и пересобираются каждый раз, поэтому эффект зависит только от того, что прочитал. Во Vue это `ref` и `computed`, в Svelte 5 — `$state` и `$derived`.
::

::question
Чем точечная реактивность отличается от модели React?

#answer
Сигналы обновляют только места, прочитавшие изменившееся значение, — текстовый узел или атрибут. React выполняет компонент заново и сравнивает вывод с прошлым, затрагивая всё поддерево.

#more
Поэтому с сигналами не нужна ручная мемоизация, а в React лишние рендеры убирают `memo` или компилятор. Взамен сигналы требуют читать значения внутри отслеживаемого контекста.
::

::question
Как сигналы избегают лишних пересчётов и промежуточных значений?

#answer
Запись только помечает зависимых устаревшими, а пересчёт идёт при чтении, в порядке зависимостей и один раз. Производные значения ленивы и кешируются: не читают — не считают.

#more
На ромбе зависимостей наивная подписка пересчитывает итог дважды и на миг выдаёт несогласованное значение — глитч. Настоящие реализации дают одно согласованное значение, а пакеты изменений объединяют записи в один запуск эффектов.
::

::question
Что такое предложение TC39 Signals?

#answer
Предложение добавить в JavaScript общий примитив реактивности — `Signal.State`, `Signal.Computed` и `Signal.subtle.Watcher`, — чтобы фреймворки и библиотеки строились на одном механизме. Над ним вместе работают авторы многих фреймворков.

#more
Эффектов в предложении нет: когда их выполнять, решает фреймворк поверх `Watcher`. Стадия ранняя, для экспериментов есть `signal-polyfill`.
::

::question
Почему индустрия сходится на сигналах, а React — нет?

#answer
Сигналы дают точечные обновления без ручной мемоизации и массивов зависимостей — к ним пришли Solid, Vue, Svelte, Angular, Preact. React держится модели снимков и перерисовки, где согласованность гарантирует снимок, а лишнюю работу убирает компилятор.

#more
У обеих моделей одна цель — минимум лишней работы без ручной оптимизации. Ловушки разные: у сигналов — потеря реактивности при неправильном чтении, у React — лишние рендеры и устаревшие замыкания без компилятора.
::

## Практика

::practice{title="Итог заказа мелькает неверной суммой"}
Итог корзины на самописной реактивности на долю секунды показывает странное число при смене количества, а в аналитику иногда уходит неверная сумма.

```js
const total = derived([withTax, discount], () => withTax.get() - discount.get());
total.subscribe((v) => { render(v); track('total', v); });
```

#solution
Самописная подписка пересчитывает итог при каждом изменении источника. `withTax` и `discount` зависят от одной цены — ромб, — и итог сначала считается с новым налогом и старой скидкой. В проверке так получилось `230` перед правильными `220`.

```js
import { signal, computed, effect } from '@preact/signals-core';

const price = signal(100);
const withTax = computed(() => price.value * 1.2);
const discount = computed(() => price.value * 0.1);
const total = computed(() => withTax.value - discount.value);

effect(() => { render(total.value); track('total', total.value); });
```

С библиотекой сигналов в проверке эффект увидел только `110` и `220`. Свою реактивность для таких графов не пишут — порядок пересчёта и ленивость нетривиальны.
::

::practice{title="Счётчик корзины тормозит каталог"}
На странице каталога с тысячей карточек каждое добавление в корзину заметно подтормаживает. Счётчик хранится в состоянии корневого компонента и передаётся в шапку.

#solution
Состояние в корне заставляет перерисовываться всё поддерево. В проверке изменение счётчика в React перезапустило и список товаров, который от него не зависит. Варианты по порядку:

```jsx
// 1. опустить состояние туда, где оно нужно, — в шапку или отдельный стор
const useCart = create((set) => ({ count: 0, add: () => set((s) => ({ count: s.count + 1 })) }));
function Badge() { const count = useCart((s) => s.count); return <span>{count}</span>; }

// 2. включить React Compiler или memo для тяжёлых веток
const ProductList = memo(function ProductList({ products }) { /* … */ });
```

Подписка на срез стора обновляет только `Badge` — это тот же принцип, что у сигналов: обновляется то, что прочитало значение. Во фреймворке на сигналах — Vue, Solid, Svelte — проблемы не было бы вовсе: в проверке сигнал поменял только текстовый узел.
::
