# Основы производительности

Производительность - не «приятный бонус», а **бизнес-метрика**: медленный сайт теряет пользователей и деньги. Но оптимизировать нужно **осознанно**: сначала измерить, потом чинить узкое место, а не угадывать. Этот образ мышления - база для всей второй половины главы.

---

## Зачем это важно

- **Конверсия и доход** - каждые лишние ~100мс загрузки измеримо снижают конверсию; крупные сайты теряют проценты выручки на задержках.
- **Удержание** - медленный сайт повышает отказы (bounce); пользователи уходят за секунды.
- **SEO** - Core Web Vitals влияют на ранжирование Google.
- **Доступность для всех** - на слабых телефонах и медленных сетях разница между «работает» и «невыносимо».

> Производительность - это про пользователя, а не про цифры в Lighthouse. Цель - чтобы **людям было быстро**, особенно на слабых устройствах.

---

## Восприятие важнее цифр

Ощущаемая скорость иногда важнее реальной. Те же миллисекунды воспринимаются по-разному:

- **скелетоны и плейсхолдеры** создают ощущение прогресса;
- **оптимистичный UI** показывает результат сразу, не дожидаясь сервера;
- мгновенная **реакция на действие** (даже спиннер за <100мс) важнее общей длительности.

<b class="text-on-semi-light">Вывод</b> - <span class="text-gray">Оптимизируй не только абсолютные метрики, но и **восприятие**: покажи что-то быстро, дай обратную связь, не блокируй интерфейс. Пользователь судит по ощущению, а не по секундомеру.</span>

---

## Сначала измерь

Главный принцип: **не оптимизируй вслепую**. Интуиция обманывает - «узкое место» часто не там, где кажется.

```
1. Измерь (профайлер, Lighthouse, RUM) → найди реальное узкое место.
2. Оптимизируй именно его.
3. Измерь снова → подтверди эффект.
```

Правило 80/20: обычно небольшая часть проблем даёт большую часть тормозов. Профайлинг находит её; угадывание - тратит время на неважное. Инструменты - в [измерении и мониторинге](/content/security-perfomance/measuring-and-monitoring).

---

## Что происходит при загрузке

Чтобы оптимизировать, надо понимать последовательность:

```
DNS → TCP/TLS → запрос → HTML → парсинг
  → загрузка CSS/JS (блокирующие?) → построение DOM/CSSOM
  → рендеринг (paint) → выполнение JS → интерактивность
```

Каждый этап - возможность ускорить: меньше байтов, раньше начать, не блокировать, кешировать. Детали - в [загрузке](/content/security-perfomance/loading-performance) и [рантайме](/content/security-perfomance/runtime-performance).

---

## Три рычага

Любая оптимизация сводится к одному из:

```
Меньше работы       → меньше байтов, кода, запросов, узлов DOM
Позже               → ленивая загрузка, откладывание несрочного
Не в главном потоке → web workers, GPU, асинхронность
Кеш                 → не делать повторно
```

---

## Модель RAIL

Пользователе-центричные ориентиры (Google):

| | Цель |
|--|------|
| **Response** | реакция на ввод < 100мс |
| **Animation** | кадр за ~16мс (60fps) |
| **Idle** | использовать простой для фоновой работы |
| **Load** | интерактивность за разумное время |

---

## Perf budget

**Бюджет производительности** - заданные лимиты (размер бандла, метрики), которые **проверяет CI** ([измерение](/content/security-perfomance/measuring-and-monitoring)). Не даёт приложению незаметно деградировать: превысил бюджет - сборка падает. Без бюджета производительность «уезжает» с каждой фичей.

---

## Не переусердствуй

<b class="text-on-semi-light">Баланс</b> - <span class="text-gray">Преждевременная оптимизация - тоже зло: усложняет код ради выигрыша, которого пользователь не заметит. Оптимизируй то, что **измеримо** влияет на пользователя, а не ради красивой цифры. Часто простые меры (сжатие, ленивая загрузка, кеш) дают 90% эффекта без микрооптимизаций.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему производительность важна?</b>
<span class="text-gray">Прямой бизнес-импакт: задержки снижают конверсию и удержание, влияют на SEO (Core Web Vitals) и доступность на слабых устройствах. Это про пользователя, а не про цифры в Lighthouse.</span>

<b class="text-on-semi-light">С чего начинать оптимизацию?</b>
<span class="text-gray">С измерения, а не догадок: профайлер/Lighthouse/RUM находят реальное узкое место. Оптимизировать его, затем измерить снова. Интуиция обманывает - тормозит часто не то, что кажется.</span>

<b class="text-on-semi-light">Что такое perceived performance?</b>
<span class="text-gray">Ощущаемая скорость: скелетоны, оптимистичный UI, мгновенная реакция на действие создают ощущение быстроты даже при тех же миллисекундах. Восприятие иногда важнее абсолютных метрик.</span>

<b class="text-on-semi-light">Что такое performance budget?</b>
<span class="text-gray">Заданные лимиты (размер бандла, метрики), проверяемые в CI. Не дают приложению деградировать: превышение валит сборку. Без бюджета производительность уезжает с каждой фичей.</span>

<b class="text-on-semi-light">Какие основные рычаги оптимизации?</b>
<span class="text-gray">Меньше работы (байтов, кода, узлов), отложить несрочное (lazy), вынести из главного потока (workers), кешировать. Любая оптимизация - один из этих рычагов.</span>
