# Основы производительности

Образ мышления, на котором держится вся вторая половина главы: производительность — это бизнес-метрика, оптимизируют по измерению, а не по догадке, и судят по ощущению пользователя, а не по цифре в отчёте. Здесь — зачем это важно в деньгах, восприятие против секундомера, принцип «сначала измерь», три рычага любой оптимизации, модель RAIL и бюджет производительности. Спрашивают, с чего начинать оптимизацию и что такое perceived performance. Глубже — почему узкое место почти всегда не там, где кажется, и как это показывает профайлер.

::tldr
- **Скорость — это деньги:** задержки снижают конверсию и удержание, влияют на SEO и на то, работает ли сайт на слабом телефоне. В A/B-тесте Vodafone улучшение LCP на 31% дало 8% продаж.
- **Сначала измерь:** интуиция обманывает. Код, который выглядит тяжёлым, часто дешёв, а «безобидная» строка в цикле — настоящее узкое место. Профайлер находит его, угадывание тратит время.
- **Три рычага:** меньше работы, кеш, позже или не в главном потоке. Любая оптимизация сводится к одному из них.
- **Восприятие важнее секундомера:** скелетон, оптимистичный интерфейс и мгновенная реакция делают те же миллисекунды быстрее на ощущение.
- **Бюджет держит форму:** лимит на размер и метрики, который проверяет CI. Без него производительность уезжает с каждой фичей.
::

---

## Зачем это важно

Производительность — не приятный бонус, а свойство, которое прямо влияет на бизнес:

- **конверсия и доход** — медленная загрузка измеримо снижает конверсию. В опубликованном A/B-тесте Vodafone (2021) улучшение LCP на 31% дало 8% продаж, +15% к переходам из лидов и +11% из корзины;
- **удержание** — пользователи уходят за секунды, растёт доля отказов;
- **SEO** — Core Web Vitals входят в сигналы ранжирования Google;
- **доступность для всех** — на слабом телефоне и медленной сети разница между «работает» и «невозможно пользоваться».

Поэтому цель — чтобы людям было быстро, особенно на слабых устройствах, а не чтобы цифра в Lighthouse была красивой.

---

## Сначала измерь

Главный принцип: не оптимизируй вслепую. Узкое место почти всегда не там, где подсказывает интуиция.

В проверке это показано на двух функциях. `buildHeader` выглядит тяжёлой — много условий и цикл по тегам, — но вызывается один раз на отрисовку заказа. Форматирование цены выглядит безобидно — одна строка, — но создаёт новый `Intl.NumberFormat` на каждый из тысяч товаров:

```js
const formatPerCall = (p) => new Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' }).format(p);
```

Замер в проверке показал, что список форматируется больше чем в десять раз дольше, чем строится «сложная» шапка. Создание форматтера — дорогая операция, и вся цена спрятана за коротким и привычным кодом. Поэтому порядок такой:

```text
1. Измерь → найди реальное узкое место (профайлер, Lighthouse, полевые данные).
2. Оптимизируй именно его.
3. Измерь снова → подтверди эффект.
```

Обычно небольшая часть кода даёт большую часть тормозов; профайлинг её находит. Инструменты — в [измерении и мониторинге](/content/security-perfomance/measuring-and-monitoring).

### Что происходит при загрузке

Чтобы понимать, где искать, полезно держать в голове путь от адреса до интерактивности:

```text
DNS → TCP/TLS → запрос → HTML приходит и парсится
  → блокирующие CSS и JS → построение DOM и CSSOM
  → первая отрисовка → выполнение JS и гидратация → интерактивность
```

Каждый этап — это и возможность ускорить (меньше байтов, раньше начать, не блокировать, кешировать), и возможность замедлить. Узкое место на разных проектах разное: у одного — тяжёлый JS в главном потоке, у другого — водопад запросов, у третьего — незакешированные шрифты. Поэтому и нужен замер, а не общий рецепт. Как разложить загрузку на этапы и что на каждом делать — в [загрузке](/content/security-perfomance/loading-performance), а что происходит уже после неё — в [производительности выполнения](/content/security-perfomance/runtime-performance).

## Три рычага

Любая оптимизация — это один из трёх ходов:

```text
Меньше работы       → меньше байтов, кода, запросов, узлов DOM, пересчётов
Кеш                 → не делать повторно то, что уже сделано
Позже / не в потоке → ленивая загрузка, откладывание, web worker, GPU
```

### Меньше работы

Тот же пример: один форматтер вместо тысячи. Результат не меняется, но в проверке переиспользование ускорило форматирование списка больше чем в пять раз:

```js
const nf = new Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' }); // один раз
for (const it of items) render(nf.format(it.price));
```

### Кеш

Если значения повторяются — а цены в каталоге повторяются, — результат запоминают. В проверке на пяти тысячах товаров всего три уникальные цены, и после первого форматирования каждой остальное — попадания в кеш:

```js
const cache = new Map();
const money = (p) => { let v = cache.get(p); if (v === undefined) { v = nf.format(p); cache.set(p, v); } return v; };
```

### Позже или не в главном потоке

Несрочное откладывают (ленивая загрузка маршрута, разбиение тяжёлой задачи), тяжёлые вычисления выносят из главного потока в [воркер](/content/additional-topics/web-workers-and-concurrency) или на GPU. Детали загрузки и рантайма — в [загрузке](/content/security-perfomance/loading-performance) и [производительности выполнения](/content/security-perfomance/runtime-performance).

## Восприятие важнее секундомера

Ощущаемая скорость иногда важнее реальной. Те же миллисекунды воспринимаются по-разному:

- **скелетон и плейсхолдеры** создают ощущение прогресса вместо пустого экрана;
- **оптимистичный интерфейс** показывает результат сразу, не дожидаясь сервера;
- **мгновенная реакция на действие** важнее общей длительности: отклик быстрее 100 мс ощущается как «сразу».

Пользователь судит по ощущению, а не по секундомеру: показать что-то быстро, дать обратную связь и не блокировать интерфейс часто ценнее, чем выиграть те же миллисекунды в фоне.

## Модель RAIL

RAIL — ориентиры Google, привязанные к восприятию пользователя. Для постановки новых целей их заменили [Core Web Vitals](/content/security-perfomance/core-web-vitals) с другими порогами, но как рамка для рассуждения RAIL по-прежнему удобна:

| Этап | Ориентир |
|------|----------|
| **Response** | реакция на ввод за 100 мс; сам обработчик — за 50 мс, чтобы осталось время на остальное |
| **Animation** | кадр за ~16 мс (60 к/с), из них около 6 мс забирает отрисовка браузера |
| **Idle** | фоновую работу дробить на куски до 50 мс, уступая главный поток вводу |
| **Load** | интерактивность за 5 с на среднем телефоне и медленном 3G, повторная загрузка — под 2 с |

В проверке эти пороги согласованы между собой: кадр для 60 к/с — это `Math.floor(1000 / 60)` = 16 мс, обработчик (50 мс) укладывается в реакцию (100 мс) с запасом, а фоновая задача на 120 мс превышает бюджет кадра простоя и подлежит дроблению.

## Бюджет производительности

**Бюджет производительности** — заданные лимиты (размер бандла, метрики), которые проверяет CI. Без бюджета производительность незаметно уезжает: каждая фича добавляет немного, и через полгода загрузка вдвое медленнее.

В проверке бюджет — 20 КБ gzip на точку входа. Крошечная точка входа укладывается с огромным запасом, а точка входа с `date-fns` и `lodash` в проверке дала больше 30 КБ gzip и бюджет превысила — в CI такая сборка падает:

```js
if (gzip > BUDGET_GZIP) { console.error(`точка входа ${gzip} Б > бюджета ${BUDGET_GZIP} Б`); process.exit(1); }
```

Готовые инструменты (`size-limit`, бюджеты Lighthouse CI) делают то же и пишут разницу в комментарий к PR. Подробнее о бюджете в конвейере — в [CI/CD](/content/advanced-tooling/ci-cd).

---

## Не переусердствуй

Преждевременная оптимизация — тоже проблема: она усложняет код ради выигрыша, которого пользователь не замечает. Оптимизируют то, что измеримо влияет на пользователя, а не ради красивой цифры. Часто простые меры — сжатие, ленивая загрузка, кеш, переиспользование дорогих объектов — дают почти весь эффект без микрооптимизаций, которые делают код непонятным.

---

## Красные флаги в ответе

- «Оптимизирую, где кажется медленным» — без профайлера и замеров.
- Оптимизация ради цифры в Lighthouse, а не ради пользователя на слабом устройстве.
- Микрооптимизации в холодном коде вместо дорогого объекта в горячем цикле.
- Нет бюджета — «следим за размером глазами на ревью».
- Производительность только про загрузку; восприятие (скелетон, оптимистичный интерфейс) не упомянуто.
- Оптимизация без повторного замера: «стало быстрее» без подтверждения.

## Как спрашивают на собеседовании

::question
Почему производительность важна?

#answer
Прямое влияние на бизнес: задержки снижают конверсию и удержание, Core Web Vitals влияют на SEO, а на слабых устройствах скорость решает, пользуются сайтом или нет. В публичном A/B-тесте Vodafone улучшение LCP на 31% дало 8% продаж. Это про пользователя, а не про цифру в отчёте.

#more
Эффект измеряют A/B-тестом на полевых данных, а не синтетикой: в лаборатории и на реальных устройствах картина разная. Поэтому у производительности есть владелец и бюджет, иначе она уезжает с каждой фичей.
::

::question
С чего начинать оптимизацию?

#answer
С измерения, а не с догадок. Профайлер, Lighthouse и полевые данные находят реальное узкое место; его оптимизируют и измеряют снова. Интуиция обманывает: тормозит часто не то, что выглядит тяжёлым.

#more
В проверке «сложная» функция оказалась в десять раз дешевле безобидной строки, создававшей форматтер в цикле. Обычно малая часть кода даёт большую часть тормозов — правило 80/20. Оптимизация без повторного замера может ничего не дать или даже ухудшить.
::

::question
Какие основные рычаги оптимизации?

#answer
Три: меньше работы (меньше байтов, кода, запросов, узлов, пересчётов), кеш (не делать повторно), позже или не в главном потоке (ленивая загрузка, откладывание, воркеры, GPU). Любая оптимизация — один из этих ходов.

#more
Рычаги комбинируют: дорогой объект создают один раз (меньше работы), повторяющийся результат запоминают (кеш), тяжёлую задачу дробят и уступают главный поток (позже). В проверке переиспользование форматтера ускорило список в разы без изменения результата.
::

::question
Что такое perceived performance?

#answer
Ощущаемая скорость. Скелетон, оптимистичный интерфейс и мгновенная реакция на действие делают те же миллисекунды быстрее на ощущение. Пользователь судит по ощущению, а не по секундомеру, поэтому важно показать что-то быстро и не блокировать интерфейс.

#more
По RAIL отклик до 100 мс ощущается как мгновенный, поэтому даже спиннер, показанный сразу, лучше молчания. Восприятие не отменяет реальные метрики: оптимистичный интерфейс поверх медленного сервера скрывает проблему, но не решает её.
::

::question
Что такое performance budget?

#answer
Заданные лимиты — размер бандла, значения метрик, — которые проверяет CI. Превышение валит сборку, поэтому производительность не деградирует незаметно. В проверке точка входа с `date-fns` и `lodash` превысила бюджет 20 КБ gzip, и такая сборка падает.

#more
Бюджет ставят на то, что влияет на пользователя: вес критического пути, LCP, INP. Инструменты вроде `size-limit` пишут разницу в комментарий к PR, так что рост видно до слияния. Поднять бюджет можно, но осознанно, а не молча.
::

## Практика

::practice{title="Список тормозит, а виноватой назначили не ту функцию"}
Страница каталога подтормаживает при отрисовке. На ревью предлагают оптимизировать `buildHeader` — она длинная, с условиями и циклом. Стоит ли начинать с неё?

#solution
Нет — сначала замерить. В проверке `buildHeader` при пяти тысячах вызовов оказалась более чем в десять раз дешевле форматирования списка цен. Настоящее узкое место — короткая строка, создающая форматтер на каждый товар:

```js
// было: новый форматтер на каждую цену
items.map((it) => new Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' }).format(it.price));

// стало: один форматтер на весь список
const nf = new Intl.NumberFormat('ru-RU', { style: 'currency', currency: 'RUB' });
items.map((it) => nf.format(it.price));
```

В проверке это ускорило форматирование в разы, а результат не изменился. Если цены повторяются, добавляют кеш по значению. Мораль: профайлер решает, что оптимизировать, а длина функции о её стоимости ничего не говорит.
::

::practice{title="Бандл вырос, и этого никто не заметил"}
За квартал время загрузки выросло вдвое. Каждый PR добавлял «всего пару килобайт», ревью смотрело на код, а не на размер. Как сделать, чтобы это не повторялось?

#solution
Поставить бюджет и проверять его в CI. Простой гейт падает, когда точка входа превышает лимит:

```js
const { gzip } = await measureEntry();
if (gzip > 20 * 1024) {
  console.error(`точка входа ${gzip} Б > бюджета ${20 * 1024} Б`);
  process.exit(1);
}
```

В проверке крошечная точка входа прошла, а с `date-fns` и `lodash` — нет (больше 30 КБ gzip). Теперь PR с тяжёлой зависимостью не сольётся молча: либо зависимость грузится лениво, либо берут легче, либо бюджет осознанно поднимают. `size-limit` и бюджеты Lighthouse CI делают это из коробки и показывают разницу прямо в PR ([CI/CD](/content/advanced-tooling/ci-cd)).
::
