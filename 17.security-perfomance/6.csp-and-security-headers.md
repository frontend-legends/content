# CSP и заголовки безопасности

HTTP-**заголовки безопасности** - дешёвый и мощный слой защиты, который сервер выставляет, а браузер исполняет. Главный из них - **Content-Security-Policy**: даже если злоумышленник внедрил скрипт, CSP может запретить его выполнение. Знать набор заголовков - стандарт для senior.

---

## Content-Security-Policy

**CSP** - заголовок, который говорит браузеру, **из каких источников** разрешено грузить ресурсы (скрипты, стили, картинки). Это **defense in depth** против [XSS](/content/security-perfomance/xss).

```
Content-Security-Policy: default-src 'self'; script-src 'self' https://cdn.com; img-src *
```

| Директива | Что ограничивает |
|-----------|------------------|
| `default-src` | дефолт для всего |
| `script-src` | откуда грузить/выполнять JS |
| `style-src` | стили |
| `img-src` | изображения |
| `connect-src` | fetch/XHR/WebSocket |
| `frame-ancestors` | кто может встроить страницу в iframe |

<b class="text-on-semi-light">Как CSP бьёт по XSS</b> - <span class="text-gray">`script-src 'self'` означает «выполнять только скрипты с моего origin». Тогда внедрённый `<script>evil()</script>` или inline-обработчик **не выполнится** - источник не разрешён. CSP не **предотвращает** инъекцию, но **не даёт внедрённому коду запуститься** - последний рубеж, когда экранирование пробито.</span>

---

## Inline-скрипты: nonce и hash

Строгий CSP блокирует **inline-скрипты** (включая `onclick=`) - это их сила (внедрённый inline не сработает). Для своих нужных inline-скриптов используют **nonce** или **hash**:

```html
<!-- сервер генерирует случайный nonce на каждый ответ -->
<!-- CSP: script-src 'nonce-abc123' -->
<script nonce="abc123">/* доверенный inline */</script>
<!-- внедрённый атакующим скрипт nonce не знает → заблокирован -->
```

`strict-dynamic` позволяет доверенному скрипту подгружать другие, упрощая строгий CSP.

> Избегай `'unsafe-inline'` и `'unsafe-eval'` - они **выключают** главные защиты CSP (разрешают любой inline и `eval`). Их наличие сводит пользу CSP почти к нулю.

---

## Report-only режим

CSP можно сначала **наблюдать**, не блокируя: `Content-Security-Policy-Report-Only` шлёт отчёты о нарушениях (`report-to`), не ломая страницу. Так настраивают политику без риска что-то сломать, а потом включают enforcement.

## Другие заголовки безопасности

| Заголовок | Зачем |
|-----------|-------|
| **Strict-Transport-Security (HSTS)** | заставить браузер всегда использовать HTTPS |
| **X-Frame-Options** / `frame-ancestors` | защита от [clickjacking](/content/security-perfomance/supply-chain-and-vulnerabilities) (запрет встраивания в iframe) |
| **X-Content-Type-Options: nosniff** | запретить браузеру угадывать MIME-тип |
| **Referrer-Policy** | контролировать, сколько URL утекает в `Referer` |
| **Permissions-Policy** | ограничить доступ к фичам (камера, гео, микрофон) |

### HSTS

`Strict-Transport-Security` говорит браузеру **всегда** ходить по HTTPS на этот домен, даже если пользователь ввёл `http://`. Защищает от downgrade-атак и перехвата на первом запросе (с `preload` - с самого начала).

### X-Content-Type-Options

`nosniff` запрещает браузеру «угадывать» тип контента: без него загруженный как картинка файл с JS-содержимым мог бы выполниться как скрипт.

> `X-XSS-Protection` - **устаревший** (старый встроенный XSS-фильтр браузеров); сейчас полагаются на CSP. Не использовать.

---

## Чья это зона

Заголовки выставляет **сервер** (или хостинг/CDN/мета-фреймворк - Next.js умеет задавать их в конфиге). Но фронтендер должен **знать** про них, **запрашивать** их настройку и понимать, как CSP влияет на загрузку скриптов/стилей в его приложении.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое CSP и как он защищает?</b>
<span class="text-gray">Content-Security-Policy - заголовок, ограничивающий источники ресурсов (скриптов, стилей). `script-src 'self'` не даёт выполниться внедрённому или inline-скрипту. Не предотвращает XSS, но блокирует запуск внедрённого кода - слой defense in depth.</span>

<b class="text-on-semi-light">Зачем nonce в CSP?</b>
<span class="text-gray">Строгий CSP блокирует inline-скрипты. Nonce (случайный на каждый ответ) разрешает выполнить конкретный доверенный inline; внедрённый атакующим скрипт nonce не знает и блокируется.</span>

<b class="text-on-semi-light">Почему опасен 'unsafe-inline' в CSP?</b>
<span class="text-gray">Он разрешает любые inline-скрипты, выключая главную защиту CSP от XSS. С ним политика почти бесполезна. То же с `'unsafe-eval'`.</span>

<b class="text-on-semi-light">Что делает HSTS?</b>
<span class="text-gray">Заставляет браузер всегда использовать HTTPS на домен, даже при вводе http://. Защищает от downgrade и перехвата; с preload - с первого запроса.</span>

<b class="text-on-semi-light">Какие ещё заголовки безопасности важны?</b>
<span class="text-gray">`X-Frame-Options`/`frame-ancestors` (clickjacking), `X-Content-Type-Options: nosniff` (MIME-sniffing), `Referrer-Policy` (утечка URL), `Permissions-Policy` (доступ к фичам). X-XSS-Protection устарел.</span>
