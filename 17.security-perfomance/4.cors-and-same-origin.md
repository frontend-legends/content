# CORS и Same-Origin Policy

**Same-Origin Policy (SOP)** - фундаментальное правило безопасности браузера: скрипт с одного origin не может читать данные с другого. **CORS** - контролируемый способ это правило ослабить. Эту пару путают и боятся, поэтому её любят на собеседованиях.

> HTTP-механика CORS-заголовков подробнее - в [Network & API](/content/network-api). Здесь - **зачем** это нужно с точки зрения безопасности.

---

## Same-Origin Policy

**Origin** = схема + хост + порт. Совпадают все три - один origin.

```
https://app.com         vs  https://app.com/page     → тот же origin ✓
https://app.com         vs  http://app.com           → разные (схема) ✗
https://app.com         vs  https://api.app.com       → разные (хост) ✗
https://app.com:443     vs  https://app.com:3000      → разные (порт) ✗
```

SOP запрещает скрипту **читать ответы** с другого origin.

<b class="text-on-semi-light">Зачем SOP существует</b> - <span class="text-gray">Без него скрипт на `evil.com` мог бы сделать `fetch('https://bank.com/account')` с твоими куками (которые отправятся автоматически) и **прочитать** твой баланс. SOP это запрещает: запрос может уйти, но **прочитать ответ** чужой скрипт не сможет. Это одна из основ безопасности веба.</span>

---

## Что SOP разрешает и запрещает

| Действие | SOP |
|----------|-----|
| Чтение ответа cross-origin (`fetch`/XHR) | ❌ запрещено (без CORS) |
| Доступ к DOM чужого iframe | ❌ запрещено |
| Встраивание `<img>`, `<script>`, `<link>` | ✅ разрешено |
| Отправка формы на чужой origin | ✅ разрешено (но не прочитать ответ) |

> Важная тонкость: встраивать и **отправлять** запросы cross-origin можно - именно поэтому возможен [CSRF](/content/security-perfomance/csrf) (отправить можно, прочитать - нет). SOP про **чтение**, а не про отправку.

---

## CORS

**Cross-Origin Resource Sharing** - механизм, которым сервер **разрешает** конкретным чужим origin читать свои ответы. CORS **ослабляет** SOP контролируемо.

```
Сервер отвечает заголовком:
Access-Control-Allow-Origin: https://app.com
→ браузер разрешает app.com прочитать этот ответ
```

---

## Как работает CORS

### Простые запросы

Для «простых» запросов (GET/POST с обычными заголовками) браузер шлёт запрос и проверяет в ответе `Access-Control-Allow-Origin`. Нет заголовка или не тот origin - браузер **блокирует чтение** (CORS-ошибка).

### Preflight

Для «непростых» запросов (методы PUT/DELETE, кастомные заголовки, `Content-Type: application/json`) браузер сначала шлёт **preflight** - запрос `OPTIONS`, спрашивая разрешение:

```
Браузер → OPTIONS /api (preflight)
          Access-Control-Request-Method: DELETE
          Access-Control-Request-Headers: authorization

Сервер  → Access-Control-Allow-Origin: https://app.com
          Access-Control-Allow-Methods: GET, POST, DELETE
          Access-Control-Allow-Headers: authorization

Браузер → если разрешено, шлёт реальный DELETE
```

### Credentials

Чтобы слать куки/авторизацию cross-origin, нужен `credentials: 'include'` на клиенте **и** `Access-Control-Allow-Credentials: true` на сервере. При этом **нельзя** использовать `Access-Control-Allow-Origin: *` - origin должен быть указан явно (иначе любой сайт читал бы данные с куками).

---

## CORS - это не серверная защита

<b class="text-on-semi-light">Частое заблуждение</b> - <span class="text-gray">CORS **не защищает сервер** и не является авторизацией. Это правило для **браузера**: запрещает чужому **фронтенду** прочитать ответ. Сам запрос часто **доходит** до сервера (и может выполнить действие!) - блокируется только чтение ответа в браузере. Серверу всё равно нужна своя авторизация. И CORS не действует вне браузера (curl, серверный код игнорируют его).</span>

---

## Частые мисконфиги

- **`Access-Control-Allow-Origin: *` с credentials** - запрещено браузером (и было бы дырой).
- **Слепое отражение Origin** - сервер берёт `Origin` из запроса и возвращает его в `Allow-Origin` без проверки - эффективно разрешает всем (с credentials - утечка данных).
- **Слишком широкие правила** - разрешить все методы/заголовки/origin «чтобы работало» - расширяет поверхность атаки.

> «У меня CORS-ошибка, добавлю `Allow-Origin: *`» - частая ошибка джуна. Правильный origin настраивается осознанно, а с credentials wildcard вообще запрещён.

---

## Site vs origin

Тонкое, но важное различие, которое путают:

- **Origin** = схема + хост + **порт** (строже).
- **Site** = схема + регистрируемый домен (eTLD+1), **без** субдомена и порта.

```
a.app.com и b.app.com  → один site, но РАЗНЫЕ origin
app.com:443 и app.com:3000 → один site, но разные origin
```

`SameSite`-куки оперируют **site**, а Same-Origin Policy - **origin**. Поэтому субдомены - «same-site, но cross-origin»: куки SameSite шлются, но SOP всё ещё разделяет.

---

## Cross-origin isolation (COOP/COEP/CORP)

Мощные API (`SharedArrayBuffer`, точный `performance.now()`) требуют, чтобы страница была **cross-origin isolated** - защищена от враждебных cross-origin документов (это защита от **Spectre** - атаки по таймингу на память).

| Заголовок | Что делает |
|-----------|-----------|
| **COOP** (`Cross-Origin-Opener-Policy`) | изолирует от открывших/открытых окон (рвёт `window.opener`) |
| **COEP** (`Cross-Origin-Embedder-Policy`) | требует явного разрешения для встраиваемых ресурсов |
| **CORP** (`Cross-Origin-Resource-Policy`) | ресурс заявляет, кто может его встраивать |

<b class="text-on-semi-light">Зачем знать</b> - <span class="text-gray">Используешь `SharedArrayBuffer` (потоки в воркерах, WASM-треды, `OffscreenCanvas`)? Нужна cross-origin isolation через COOP+COEP. Это вопрос на стыке безопасности (Spectre) и производительности - сильный senior-сигнал.</span>

---

## Opaque-ответы

`fetch` в режиме `no-cors` возвращает **opaque**-ответ: его нельзя прочитать из JS (статус 0, нет тела). Так браузер позволяет, например, закешировать cross-origin ресурс в Service Worker, **не давая** прочитать содержимое. Это не CORS-ошибка, а намеренное ограничение.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое Same-Origin Policy и зачем она?</b>
<span class="text-gray">Правило браузера: скрипт с одного origin (схема+хост+порт) не может читать ответы с другого. Без неё evil.com мог бы с твоими куками прочитать данные с bank.com. SOP запрещает чтение, но не отправку.</span>

<b class="text-on-semi-light">Что такое CORS?</b>
<span class="text-gray">Механизм, которым сервер заголовками (`Access-Control-Allow-Origin` и др.) разрешает конкретным чужим origin читать свои ответы - контролируемо ослабляет SOP.</span>

<b class="text-on-semi-light">Что такое preflight-запрос?</b>
<span class="text-gray">Предварительный `OPTIONS`-запрос, который браузер шлёт для «непростых» запросов (PUT/DELETE, кастомные заголовки, JSON), спрашивая у сервера разрешение по методам/заголовкам, прежде чем отправить реальный запрос.</span>

<b class="text-on-semi-light">CORS защищает сервер?</b>
<span class="text-gray">Нет. Это правило для браузера - запрещает чужому фронтенду прочитать ответ. Запрос часто доходит до сервера, и вне браузера (curl) CORS не действует. Серверу нужна своя авторизация.</span>

<b class="text-on-semi-light">Почему нельзя `Allow-Origin: *` с credentials?</b>
<span class="text-gray">Это позволило бы любому сайту читать ответы с куками пользователя - утечка. Браузер запрещает сочетание wildcard и credentials; origin должен быть указан явно.</span>

<b class="text-on-semi-light">Чем origin отличается от site?</b>
<span class="text-gray">Origin = схема+хост+порт (строже). Site = схема+регистрируемый домен (eTLD+1), без субдомена и порта. Субдомены - same-site, но cross-origin: SameSite-куки шлются, но SOP их разделяет.</span>

<b class="text-on-semi-light">Что такое cross-origin isolation и зачем?</b>
<span class="text-gray">Изоляция страницы от враждебных cross-origin документов через COOP+COEP (защита от Spectre). Нужна для мощных API вроде `SharedArrayBuffer` (потоки в воркерах, WASM-треды). Вопрос на стыке безопасности и производительности.</span>
