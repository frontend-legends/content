# Аутентификация и токены

Как приложение узнаёт, кто пользователь, и помнит его между запросами. Здесь — аутентификация против авторизации, сессии против JWT и их компромиссы, устройство и проверка JWT, где хранить токен, access и refresh с ротацией, OAuth и PKCE, passkeys и безопасность сессии. Спрашивают, чем сессии отличаются от JWT, где хранить токен и зачем нужны access и refresh. Глубже — почему подделанный и просроченный токен не проходят проверку, почему в JWT нельзя класть секреты и как ротация refresh ловит кражу.

::tldr
- **Аутентификация — кто ты, авторизация — что тебе можно; обе на сервере.** Сначала проверяют личность, потом права.
- **Сессии против JWT — компромисс отзыва и масштаба:** сессию легко отозвать, JWT самодостаточен и stateless, но мгновенно отозвать его нельзя. В проверке jose принял валидный токен и отклонил подделанный, просроченный и с `alg: none`.
- **JWT подписан, но не зашифрован:** в проверке payload читается без секрета, поэтому туда кладут только идентификаторы, не пароли.
- **Где хранить — выбор между XSS и CSRF:** HttpOnly-кука недоступна скрипту (XSS не украдёт), но отправляется сама (нужен SameSite); `localStorage` наоборот.
- **Короткий access плюс ротация refresh:** в проверке повторное использование старого refresh-токена распозналось как кража и отзывало всю семью.
::

## Аутентификация и авторизация

Их путают, но это разные шаги:

- **аутентификация** — кто ты: проверка личности (логин и пароль, OAuth, passkey);
- **авторизация** — что тебе можно: права и роли.

Сначала аутентификация, потом авторизация, и обе — на сервере. Клиент может скрыть кнопку по роли для удобства, но решение о доступе принимает сервер на каждый запрос ([основы безопасности](/content/security-perfomance/security-fundamentals)).

---

## Сессии против токенов

Два способа помнить пользователя между запросами.

- **Сессии (stateful).** Сервер хранит сессию, клиент получает session ID в куке и на каждый запрос сервер ищет сессию по ID. Отозвать легко — удалить сессию; но нужно общее хранилище.
- **Токены (stateless, JWT).** Сервер выдаёт самодостаточный подписанный токен и проверяет подпись, не храня состояние. Проще масштабировать; но мгновенно отозвать нельзя.

| | Сессии | JWT |
|--|--------|-----|
| Состояние | на сервере | в токене |
| Отзыв | легко (удалить) | трудно (валиден до истечения) |
| Масштаб | нужно общее хранилище | проще горизонтально |
| Размер | маленькая кука | больше, едет в каждом запросе |

Ключевой компромисс — отзыв. JWT сервер принимает по подписи, не сверяясь с хранилищем, поэтому отозвать его до истечения срока нельзя. Это решают коротким сроком жизни и ротацией refresh (ниже) или серверным denylist.

## Устройство и проверка JWT

JWT — три части через точку: `header.payload.signature`, закодированы base64url. В заголовке алгоритм, в payload — claims (`sub`, `role`, `exp`), подпись покрывает заголовок и payload секретом сервера.

В проверке настоящим `jose` валидный токен прошёл проверку и отдал claims, а дальше видно, что именно она отсекает:

- **подделку** — изменённый payload без секрета дал ошибку проверки подписи;
- **просрочку** — токен с истёкшим `exp` отклонён;
- **подмену алгоритма** — токен с `alg: none` отклонён, потому что проверка задаёт явный белый список алгоритмов (`algorithms: ['HS256']`). Это закрывает классическую атаку, когда злоумышленник меняет алгоритм на `none` или подменяет :term[HS256]{def="подпись JWT общим секретом по алгоритму HMAC-SHA256"} на :term[RS256]{def="подпись JWT ключами RSA: подписывают закрытым ключом, проверяют открытым"}.

```js
const { payload } = await jwtVerify(token, secret, { algorithms: ['HS256'] });
```

### Подписан, но не зашифрован

Подпись гарантирует целостность — подделать нельзя без секрета, — но payload не зашифрован. В проверке его удалось прочитать обычным декодированием, без секрета и без проверки подписи. Поэтому в JWT кладут только идентификаторы и неконфиденциальные claims, но не пароли и чувствительные данные. Это частая ошибка.

## Где хранить токен

Центральный вопрос безопасности фронтенда, и у обоих вариантов противоположные угрозы. В проверке это выражено матрицей:

| | HttpOnly-кука | localStorage / память |
|--|---------------|------------------------|
| Доступ из скрипта | нет — XSS не украдёт | да — уязвимо к XSS |
| Автоотправка | да — риск CSRF | нет — CSRF не грозит |
| Чем защищают | SameSite от CSRF | защита от XSS везде |

Предпочтительно — HttpOnly, Secure, SameSite кука: токен недоступен скрипту, поэтому XSS его не прочитает, а CSRF закрывается атрибутом SameSite. `localStorage` доступен любому скрипту, и одна XSS-дыра означает угон сессии. Память (переменная) лучше `localStorage` — исчезает при перезагрузке и не персистится, — но тоже доступна скрипту. Итог: токены в HttpOnly-куке и серьёзная защита от [XSS](/content/security-perfomance/xss). Это тот же компромисс, что в [CSRF](/content/security-perfomance/csrf): куки уязвимы к CSRF, заголовочные токены — к XSS.

## Access и refresh

Чтобы примирить короткий срок жизни ради безопасности и «не логиниться каждые пять минут»:

- **access-токен** — короткоживущий (минуты), едет в запросах; при краже быстро истечёт;
- **refresh-токен** — долгоживущий, хранится надёжно (HttpOnly-кука), используется только чтобы получить новый access.

**Ротация** ограничивает урон от кражи: каждый refresh выдаёт новый токен, а старый становится недействительным. Если старый токен используют повторно — это признак кражи, и сервер отзывает всю цепочку. В проверке так и вышло: ротация выдала новый токен, а повторное использование старого распозналось как `reuse-detected` и отзывало семью токенов, при этом актуальный токен продолжал работать.

## OAuth и PKCE

OAuth 2.0 — протокол делегированного доступа («Войти через Google»): приложение получает доступ без пароля пользователя. Для :term[SPA]{def="одностраничное приложение: страница загружается раз, а экраны меняет JavaScript"} используют Authorization Code Flow с :term[PKCE]{def="защита OAuth для публичных клиентов: одноразовый секрет доказывает, что код обменивает тот же клиент"}; устаревший implicit flow небезопасен. OpenID Connect (OIDC) — надстройка над OAuth, добавляющая идентичность через ID-токен: OAuth про доступ, OIDC про логин.

PKCE защищает от перехвата кода авторизации. Клиент генерирует секретный `code_verifier`, хранит его у себя и отправляет серверу только его хеш (`code_challenge`). При обмене кода на токен он предъявляет `verifier`, и сервер сверяет его с сохранённым хешем. В проверке обмен с правильным `verifier` прошёл, а перехвативший код без `verifier` обменять его не смог — хеш не совпал.

Писать аутентификацию самому опасно: хеширование паролей, потоки OAuth, ротация, защита от перебора полны тонкостей, а цена ошибки — утечка аккаунтов. Берут проверенные решения ([Auth.js, Clerk](/content/ecosystem-libs/auth-libraries)).

## Passkeys и безопасность сессии

Пароль — слабое звено: фишинг, переиспользование, утечки. Современная защита:

- **MFA** — второй фактор (TOTP-код, push; SMS слабее всего) резко снижает урон от украденного пароля;
- **passkeys / WebAuthn** — беспарольная аутентификация на криптографии: приватный ключ на устройстве, разблокировка биометрией. Устойчивы к фишингу by design — ключ привязан к origin — и не утекают, как пароли. Индустрия движется к ним как к замене паролей.

Безопасность самой сессии:

- **session fixation** — злоумышленник навязывает жертве известный ему session ID; защита — регенерировать ID при логине. В проверке логин сменил навязанный заранее ID на новый, и прежний перестал действовать;
- **logout** — инвалидировать сессию на сервере, а не только удалить куку, иначе токен ещё валиден;
- **таймауты** — сессия истекает и по бездействию, и по абсолютному времени.

## Красные флаги в ответе

- Авторизация только на клиенте, сервер доверяет роли из токена без проверки.
- Чувствительные данные в payload JWT — он читается всеми.
- Проверка JWT без явного списка алгоритмов — уязвимость к `alg: none` и подмене алгоритма.
- Токен в `localStorage` без серьёзной защиты от XSS.
- «Logout — удалить куку»: stateless-токен остаётся валидным до истечения.
- Один долгоживущий токен без access/refresh и ротации.
- implicit flow для SPA вместо Authorization Code с PKCE.

## Как спрашивают на собеседовании

::question
Чем аутентификация отличается от авторизации?

#answer
Аутентификация — кто ты (проверка личности: пароль, OAuth, passkey). Авторизация — что тебе можно (права и роли). Сначала аутентификация, потом авторизация, и обе выполняются на сервере — клиентские проверки лишь для удобства.

#more
Разделение важно для дизайна: личность подтверждают один раз за сессию, а права проверяют на каждое действие с каждым объектом. Скрыть кнопку по роли — удобство; доступ решает сервер, иначе получаются уязвимости вроде IDOR из [основ безопасности](/content/security-perfomance/security-fundamentals).
::

::question
Сессии или JWT — в чём разница и компромисс?

#answer
Сессии хранят состояние на сервере: легко отозвать, но нужно общее хранилище. JWT самодостаточен и stateless: проще масштабировать, но мгновенно отозвать нельзя — он валиден до истечения. Выбор — между управляемостью и масштабом.

#more
В проверке jose принимал токен по подписи, не сверяясь с хранилищем, — отсюда и сложность отзыва. Решают коротким сроком access, ротацией refresh и серверным denylist по `jti`. Часто берут гибрид: JWT для обычных запросов и проверку сессии для критичных действий.
::

::question
Где хранить токен — localStorage или кука?

#answer
Предпочтительно HttpOnly, Secure, SameSite кука: она недоступна скрипту (XSS не украдёт), а CSRF закрывается SameSite. `localStorage` доступен любому скрипту, поэтому одна XSS-дыра означает угон сессии. Память лучше `localStorage`, но тоже доступна скрипту.

#more
В проверке угрозы вышли противоположными: у куки главная угроза — CSRF (отправляется сама), у `localStorage` — XSS (читается скриптом). Поэтому выбор куки сопровождают защитой от CSRF, а любой вариант — защитой от XSS. Refresh-токен почти всегда держат в HttpOnly-куке.
::

::question
Можно ли класть чувствительные данные в JWT?

#answer
Нет. JWT подписан, что гарантирует целостность, но не зашифрован — payload читается кем угодно обычным декодированием base64url. В проверке его удалось прочитать без секрета. Кладут только идентификаторы и неконфиденциальные claims.

#more
Если данные нужно скрыть, используют шифрование (JWE) или вообще не передают их в токене, а хранят на сервере по идентификатору. И всегда проверяют подпись с явным списком алгоритмов: в проверке токен с `alg: none` был отклонён именно поэтому.
::

::question
Зачем access и refresh токены?

#answer
Короткий access ограничивает урон от кражи — он быстро истекает. Долгий refresh в HttpOnly-куке обновляет access без релогина. Ротация refresh (каждый обмен выдаёт новый, старый гасится) снижает риск дальше и позволяет заметить кражу.

#more
В проверке повторное использование старого refresh-токена распозналось как кража и отзывало всю семью токенов. Это обходит главный недостаток stateless-токенов — невозможность мгновенного отзыва: сам access короткий, а компрометацию refresh ловит ротация.
::

::question
Какой OAuth-флоу для SPA и зачем PKCE?

#answer
Authorization Code Flow с PKCE. PKCE защищает от перехвата кода авторизации: клиент хранит секретный `code_verifier`, отправляет серверу только его хеш, а при обмене кода предъявляет сам verifier. Implicit flow устарел как небезопасный.

#more
В проверке обмен с правильным verifier прошёл, а перехвативший код без verifier обменять его не смог. OIDC поверх OAuth добавляет идентичность через ID-токен. Писать это самому не стоит — берут проверенные библиотеки, потому что цена ошибки в потоках OAuth — утечка аккаунтов.
::

::question
Как правильно сделать logout с JWT?

#answer
Удалить куку мало — stateless-токен остаётся валидным до истечения. Нужны короткий срок access и ротация refresh, серверный denylist по `jti` для мгновенного отзыва или гибрид с проверкой сессии для критичных действий. При логине ещё регенерируют session ID против фиксации.

#more
В проверке регенерация ID при логине сделала навязанный заранее идентификатор недействительным. «Сложность отзыва JWT» бьёт именно при logout и компрометации, поэтому чистый stateless удобен для масштаба, но за управляемость доплачивают коротким TTL и denylist.
::

## Практика

::practice{title="Проверка JWT принимает подделанный токен"}
Сервис доверяет роли из токена, а проверку написали так:

```js
import { decodeJwt } from 'jose';
const payload = decodeJwt(token);          // только декодирование, без проверки подписи
if (payload.role === 'admin') grantAdmin();
```

Пользователь поменял `role` на `admin` и получил доступ.

#solution
`decodeJwt` только читает payload, не проверяя подпись, — а payload не зашифрован и правится тривиально. Нужна настоящая проверка с секретом и явным списком алгоритмов:

```js
import { jwtVerify } from 'jose';
const { payload } = await jwtVerify(token, secret, { algorithms: ['HS256'] });
if (payload.role === 'admin') grantAdmin();
```

В проверке так подделанный токен дал ошибку проверки подписи, просроченный — ошибку срока, а токен с `alg: none` был отклонён списком алгоритмов. Без указания `algorithms` библиотека может принять `alg: none` или токен, подписанный другим ключом, — это классическая атака. И роль всё равно сверяют с сервером при каждом чувствительном действии, а не только по токену.
::

::practice{title="Украденный refresh-токен работает месяцами"}
Refresh-токен живёт 30 дней и при обновлении access остаётся прежним. Если он утёк, злоумышленник пользуется им до конца срока, а настоящий пользователь ничего не замечает.

#solution
Включают ротацию с обнаружением повторного использования: каждый refresh выдаёт новый токен, старый гасится, а попытка использовать погашенный токен означает, что его кто-то скопировал, — тогда отзывают всю цепочку:

```js
function rotate(oldToken) {
  const family = store.get(oldToken);
  if (family === undefined) { store.revokeFamily(familyOf(oldToken)); return { error: 'reuse-detected' }; }
  store.delete(oldToken);                 // одноразовый
  return { token: store.issue(family) };  // новый токен той же семьи
}
```

В проверке ротация выдала новый токен, повторное использование старого вернуло `reuse-detected` и отозвало семью, а актуальный токен продолжил работать. Теперь, когда злоумышленник и жертва используют токены по очереди, один из обменов наткнётся на погашенный токен — и доступ закроется обоим, заставив заново войти. Сам access при этом короткий (минуты), чтобы окно кражи было мало.
::
