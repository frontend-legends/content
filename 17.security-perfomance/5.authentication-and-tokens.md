# Аутентификация и токены

Как приложение узнаёт, **кто** пользователь, и помнит его между запросами. Сессии vs JWT, где хранить токен, OAuth - темы, где легко ошибиться с безопасностью, и которые глубоко спрашивают на senior-собесах.

> Продукты авторизации (Auth.js, Clerk) - в [экосистеме](/content/ecosystem-libs/auth-libraries). Здесь - **концепции и безопасность**.

---

## Authentication vs authorization

Не путать:

- **Authentication (аутентификация)** - **кто** ты (проверка личности: логин/пароль, OAuth).
- **Authorization (авторизация)** - **что** тебе можно (права, роли).

Сначала authn, потом authz. И то, и другое - **на сервере**.

---

## Сессии vs токены

Два способа помнить пользователя между запросами.

### Сессии (stateful)

Сервер хранит сессию, клиент получает **session ID** в куке. На каждый запрос сервер ищет сессию по ID.

```
Логин → сервер создал сессию, отдал куку (session ID)
Запрос → кука → сервер находит сессию → знает пользователя
```

### Токены (stateless, JWT)

Сервер выдаёт **самодостаточный подписанный токен**. Сервер проверяет **подпись**, не храня состояние.

```
Логин → сервер подписал JWT, отдал клиенту
Запрос → токен → сервер проверяет подпись → доверяет содержимому
```

### Компромиссы

| | Сессии | JWT |
|--|--------|-----|
| Состояние | на сервере (хранилище) | без состояния (самодостаточен) |
| Отзыв | легко (удалить сессию) | **трудно** (валиден до истечения) |
| Масштаб | нужно общее хранилище | проще горизонтально |
| Размер | маленькая кука | больше (едет в каждом запросе) |

<b class="text-on-semi-light">Главный нюанс JWT - отзыв</b> - <span class="text-gray">JWT самодостаточен: сервер доверяет ему по подписи, **не сверяясь с хранилищем**. Поэтому **мгновенно отозвать** его нельзя - он валиден до истечения срока. Решают короткими access-токенами + refresh (ниже) и чёрными списками. Сессию же удалить тривиально. Это ключевой компромисс «stateless ради масштаба ценой управляемости».</span>

## JWT под капотом

JWT = три части через точку: `header.payload.signature`, закодированы base64url.

```
header:    { "alg": "HS256", "typ": "JWT" }
payload:   { "sub": "123", "role": "user", "exp": 1700000000 }  ← claims
signature: подпись header+payload секретом сервера
```

<b class="text-on-semi-light">JWT подписан, но НЕ зашифрован</b> - <span class="text-gray">Подпись гарантирует **целостность** (нельзя подделать без секрета), но payload **читается всеми** (base64 - не шифрование). Поэтому в JWT **нельзя класть секреты** (пароли, чувствительные данные) - только идентификаторы и неконфиденциальные claims. Это частая ошибка.</span>

## Где хранить токен

Центральный вопрос безопасности фронтенда. Два варианта, оба с компромиссом:

| | HttpOnly-кука | localStorage / память |
|--|----------------|------------------------|
| Доступ из JS | нет (защита от XSS) | да (**уязвимо к XSS**) |
| Автоотправка | да (**риск CSRF**) | нет (CSRF-безопасно) |
| Защита от CSRF | SameSite-кука | не нужна |
| Защита от XSS | встроена | нужна везде |

<b class="text-on-semi-light">Рекомендация</b> - <span class="text-gray">Предпочтительно - **HttpOnly + Secure + SameSite кука**: токен недоступен JS (XSS его не украдёт), а CSRF закрывается `SameSite`. `localStorage` доступен любому скрипту, поэтому одна XSS-дыра = угон сессии. Память (переменная) лучше localStorage (исчезает при перезагрузке, не персистится), но всё ещё доступна JS. Итог: токены - в HttpOnly-куке, и серьёзно защищайся от [XSS](/content/security-perfomance/xss).</span>

## Access + refresh токены

Чтобы примирить «короткий срок жизни ради безопасности» и «не логиниться каждые 5 минут»:

- **Access-токен** - короткоживущий (минуты), используется в запросах. Скомпрометирован - быстро истечёт.
- **Refresh-токен** - долгоживущий, хранится надёжно (HttpOnly-кука), используется **только** чтобы получить новый access-токен.

```
Access истёк → шлём refresh → получаем новый access (silent refresh)
```

**Ротация refresh-токенов** (каждый refresh выдаёт новый, старый инвалидируется) ограничивает урон от кражи.

## OAuth 2.0 и OIDC

**OAuth 2.0** - протокол **делегированного доступа** («Войти через Google»): приложение получает доступ без пароля пользователя.

- Для SPA - **Authorization Code Flow + PKCE** (PKCE защищает от перехвата кода; implicit flow устарел как небезопасный).
- **OpenID Connect (OIDC)** - надстройка над OAuth, добавляющая **идентичность** (ID-токен: кто пользователь). OAuth - про доступ, OIDC - про логин.

<b class="text-on-semi-light">Не пиши auth сам</b> - <span class="text-gray">Аутентификация полна тонкостей (хеширование паролей, потоки OAuth, ротация, защита от перебора). Цена ошибки - утечка аккаунтов. Используй проверенные решения ([Auth.js, Clerk](/content/ecosystem-libs/auth-libraries)) - переизобретать опасно.</span>

## MFA и passkeys

Пароль - слабое звено (фишинг, переиспользование, утечки). Современная защита:

- **MFA (многофакторная)** - второй фактор (TOTP-код, push; SMS слабее всего). Резко снижает урон от украденного пароля.
- **Passkeys / WebAuthn** - беспарольная аутентификация на криптографии: приватный ключ на устройстве, разблокировка биометрией/PIN. **Устойчивы к фишингу by design** (ключ привязан к origin) и не утекают, как пароли. Индустрия движется к passkeys как замене паролей - знать про них в 2026 важно.

```js
// WebAuthn (упрощённо): браузерное API для passkeys
navigator.credentials.get({ publicKey: { /* challenge от сервера */ } });
```

## Безопасность сессии

- **Session fixation** - атакующий навязывает жертве известный ему session ID; защита - **регенерировать** ID при логине.
- **Logout** - инвалидировать сессию **на сервере**, а не только удалить куку: иначе токен ещё валиден.
- **Ротация и отзыв** - короткие access + ротируемые refresh; denylist (по `jti`) для мгновенного отзыва.
- **Таймауты** - сессия истекает и по бездействию, и по абсолютному времени.

<b class="text-on-semi-light">Senior-нюанс с JWT</b> - <span class="text-gray">«Сложность отзыва JWT» бьёт именно при logout/компрометации: stateless-токен валиден до истечения. Решения - короткий TTL + ротация refresh, серверный denylist по `jti`, или гибрид (JWT + проверка сессии для критичных действий). Чистый stateless удобен для масштаба, но платит управляемостью.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Чем аутентификация отличается от авторизации?</b>
<span class="text-gray">Authentication - кто ты (проверка личности). Authorization - что тебе можно (права/роли). Сначала authn, потом authz; обе - на сервере.</span>

<b class="text-on-semi-light">Сессии или JWT - в чём разница и компромисс?</b>
<span class="text-gray">Сессии хранят состояние на сервере (легко отозвать, нужно хранилище). JWT самодостаточен и stateless (проще масштабировать), но его трудно мгновенно отозвать - валиден до истечения. Решают короткими access + refresh.</span>

<b class="text-on-semi-light">Где хранить токен - localStorage или кука?</b>
<span class="text-gray">Предпочтительно HttpOnly+Secure+SameSite кука: недоступна JS (защита от XSS), CSRF закрыт SameSite. localStorage доступен скриптам - одна XSS = угон. Памяти лучше localStorage, но тоже доступна JS.</span>

<b class="text-on-semi-light">Можно ли класть чувствительные данные в JWT?</b>
<span class="text-gray">Нет. JWT подписан (целостность), но не зашифрован - payload читается всеми (base64). Только идентификаторы и неконфиденциальные claims.</span>

<b class="text-on-semi-light">Зачем access + refresh токены?</b>
<span class="text-gray">Короткий access ограничивает урон от кражи (быстро истекает), долгий refresh (в HttpOnly-куке) обновляет access без релогина. Ротация refresh снижает риск дальше.</span>

<b class="text-on-semi-light">Какой OAuth-флоу для SPA?</b>
<span class="text-gray">Authorization Code Flow + PKCE (PKCE защищает от перехвата кода). Implicit flow устарел как небезопасный. OIDC поверх OAuth добавляет идентичность (ID-токен).</span>

<b class="text-on-semi-light">Что такое passkeys и чем они лучше паролей?</b>
<span class="text-gray">Беспарольная аутентификация (WebAuthn): приватный ключ на устройстве, разблокировка биометрией. Устойчивы к фишингу by design (ключ привязан к origin) и не утекают, как пароли. Индустрия движется к passkeys как замене паролей.</span>

<b class="text-on-semi-light">Как правильно реализовать logout с JWT?</b>
<span class="text-gray">Удалить куку мало - stateless-токен валиден до истечения. Нужны короткий TTL + ротация refresh, серверный denylist по `jti`, или гибрид (JWT + проверка сессии для критичных действий). Плюс регенерация ID при логине против session fixation.</span>
