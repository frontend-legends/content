# Производительность загрузки

Первая половина битвы за скорость — как быстро полезный контент доходит до экрана. Здесь — критический путь отрисовки, блокирующие ресурсы, `async` против `defer`, критический CSS, подсказки браузеру (preload, preconnect, prefetch), сжатие, протоколы HTTP/2 и HTTP/3, серверный рендеринг, bfcache и пререндеринг. Спрашивают, что такое критический путь, чем отличаются `async` и `defer` и как ускорить первый показ. Глубже — почему синхронный скрипт посреди страницы останавливает разбор HTML, почему `defer` сохраняет порядок несмотря на скорость загрузки и на сколько блокирующий CSS откладывает первую отрисовку.

::tldr
- **Критический путь отрисовки:** HTML → DOM, CSS → CSSOM, вместе → отрисовка. Цель загрузки — сократить и разблокировать этот путь, потому что он определяет LCP и FCP.
- **CSS блокирует отрисовку, синхронный JS — разбор:** браузер не рисует без CSSOM и останавливает разбор HTML на синхронном скрипте. В проверке блокирующий CSS отодвинул первую отрисовку с 20 до ~290 мс.
- **`defer` и `async` не блокируют разбор:** `defer` выполняется после разбора в порядке исходника, `async` — как только загрузился, без гарантий порядка. Для кода приложения — `defer` и модули.
- **Меньше и сжатее:** разделение кода, ленивая загрузка ниже сгиба, минификация и brotli. В проверке 31 КБ CSS сжались в gzip до 1,15 КБ, в brotli — до 637 байт.
- **Подсказки и предсказание:** preload поднимает приоритет ключевого ресурса, preconnect готовит соединение, bfcache и пререндеринг делают переходы мгновенными.
::

## Критический путь отрисовки

Чтобы показать хоть что-то, браузер проходит цепочку:

```text
HTML → DOM ┐
CSS  → CSSOM ┘ → дерево отрисовки → раскладка → отрисовка (paint)
```

DOM без CSSOM не рисуется: браузер ждёт стили, чтобы не показать неоформленную страницу. JavaScript может вмешаться в эту цепочку и остановить её. Задача оптимизации загрузки — сделать критический путь коротким (меньше байтов, меньше запросов) и не блокированным (ничего лишнего не держит первую отрисовку).

## Блокирующие ресурсы

| Ресурс | Что блокирует |
|--------|---------------|
| **CSS** | отрисовку — браузер не рисует без CSSOM |
| **Синхронный JS** | разбор HTML — останавливает его до загрузки и выполнения скрипта |

Синхронный скрипт опасен не только задержкой: он останавливает разбор ровно там, где стоит. В проверке скрипт посреди `<body>` увидел только две карточки, которые были выше него, а элемент ниже по странице для него ещё не существовал — браузер не дошёл до него, потому что выполнял скрипт. Поэтому скрипты, которые не должны тормозить показ, не ставят синхронно:

```html
<script src="app.js"></script>          <!-- блокирует разбор -->
<script src="app.js" defer></script>     <!-- не блокирует, выполнится после разбора, в порядке -->
<script src="analytics.js" async></script> <!-- не блокирует, выполнится как только загрузится -->
```

### async или defer

Оба атрибута грузят скрипт параллельно разбору, но выполняют по-разному:

- **`defer`** — после полного разбора HTML, в порядке следования в документе. Для кода, который зависит от DOM и от других скриптов.
- **`async`** — как только скрипт загрузился, в любой момент, без гарантий порядка. Для независимых скриптов вроде аналитики.

В проверке это видно по порядку выполнения: два `defer`-скрипта выполнились как `d1`, `d2` — в порядке исходника, — хотя `d2` отдавался сервером мгновенно, а `d1` с задержкой. Порядок сохранился, потому что это `defer`. Оба выполнились после синхронного скрипта в теле, то есть после конца разбора. А `async`-скрипт встал в разных прогонах на разное место — его позиция порядком не задана. Для большинства кода приложения выбирают `defer` или модули: `type="module"` отложены по умолчанию.

### Критический CSS

Раз CSS блокирует отрисовку, критические стили для первого экрана встраивают прямо в HTML, а остальное грузят асинхронно. В проверке страница с инлайновым критическим стилем отрисовалась за ~20 мс, а та же страница с внешним медленным стилем в `<head>` — только через ~290 мс: первая отрисовка ждала загрузки CSS. Разница — почти вся задержка первого показа.

## Меньше, позже, сжатее

Три приёма уменьшают сам объём работы на критическом пути:

- **разделение кода и ленивая загрузка** — не тащить весь JavaScript сразу, грузить маршруты и тяжёлые компоненты по требованию ([оптимизация сборки](/content/advanced-tooling/optimization), [производительность React](/content/reactjs/performance));
- **ленивые картинки ниже сгиба** — `loading="lazy"`, но никогда на LCP-элементе;
- **минификация и tree-shaking** — меньше байтов в бандле ([бандлеры](/content/advanced-tooling/bundlers)).

Поверх минификации сервер отдаёт ассеты сжатыми — gzip или brotli. Сжатие огромно на повторяющемся коде: в проверке 31 КБ однотипного CSS сжались gzip до 1,15 КБ, а brotli — до 637 байт. Поэтому вес ресурса оценивают после минификации и brotli, а не по исходному размеру, а сжатие настраивают на сервере или CDN.

## Подсказки браузеру

Подсказки ресурсам говорят браузеру, что готовить заранее:

| Подсказка | Что делает |
|-----------|------------|
| **preload** | грузить критичный ресурс сейчас с высоким приоритетом (шрифт, LCP-картинка) |
| **preconnect** | заранее установить соединение: DNS, TCP, TLS |
| **dns-prefetch** | заранее разрешить только DNS |
| **prefetch** | загрузить ресурс для вероятной следующей навигации, низкий приоритет |
| **modulepreload** | предзагрузить ES-модуль вместе с разбором |

```html
<link rel="preload" href="hero.webp" as="image" fetchpriority="high">
<link rel="preconnect" href="https://api.example.com">
```

`fetchpriority="high"` поднимает приоритет ключевого ресурса, `low` — понижает несрочное. Подсказками не злоупотребляют: если предзагрузить всё, приоритеты теряют смысл.

## Протоколы

Протокол соединения влияет на стратегию загрузки:

- **HTTP/2** — мультиплексирование: много запросов в одном соединении параллельно. Старый совет «склеить всё в один файл» из-за этого частично устарел — много мелких запросов стали дешёвыми;
- **HTTP/3** поверх QUIC (UDP) — быстрее устанавливает соединение и не страдает от блокировки очереди на уровне TCP, что заметно на нестабильных сетях.

Бандлинг всё равно нужен — ради сжатия и tree-shaking, — но дробить его на разумные части теперь безопасно.

## Готовый HTML и мгновенные переходы

- **Серверный рендеринг (SSR/SSG)** отдаёт готовый HTML, и первый показ наступает раньше, чем у пустого SPA, ждущего свой JavaScript ([рендеринг и гидратация](/content/reactjs/rendering-and-hydration)).
- **103 Early Hints** — промежуточный ответ, которым сервер шлёт `preload` и `preconnect` ещё до готовности основного HTML: браузер грузит критичное, пока сервер думает.
- **bfcache** (back/forward cache) — браузер держит снимок страницы в памяти и мгновенно восстанавливает её при переходе «назад/вперёд», без сети и перезагрузки. Его легко потерять: обработчик `unload` или `Cache-Control: no-store` отключают bfcache. Вместо `unload` используют `pagehide` и `visibilitychange`, а совместимость проверяют в DevTools.
- **Speculation Rules** — декларативно пререндерить вероятные следующие страницы, чтобы переход был мгновенным:

```html
<script type="speculationrules">
{ "prerender": [{ "where": { "href_matches": "/product/*" } }] }
</script>
```

---

## Красные флаги в ответе

- Синхронные `<script>` в `<head>` без `defer`/`async` и «потом разберёмся».
- Путают `async` и `defer` или считают, что `async` сохраняет порядок.
- Вес бандла оценивают по исходному размеру, а не после минификации и brotli.
- `loading="lazy"` на геройской картинке — она же LCP-элемент.
- preload на всё подряд — приоритеты перестают работать.
- Не знают про bfcache и вешают `unload`, бесплатно теряя мгновенную навигацию.

## Как спрашивают на собеседовании

::question
Что такое критический путь отрисовки?

#answer
Последовательность от HTML и CSS до первой отрисовки: DOM и CSSOM складываются в дерево отрисовки, затем раскладка и paint. CSS блокирует отрисовку, синхронный JS — разбор HTML. Цель загрузки — сделать этот путь коротким и ничем лишним не заблокированным.

#more
Браузер не рисует без CSSOM, чтобы не показать неоформленную страницу, поэтому критический CSS встраивают инлайн. В проверке блокирующий внешний стиль отодвинул первую отрисовку с ~20 до ~290 мс. Диагностируют путь во вкладке Performance и по метрикам FCP и LCP.
::

::question
В чём разница между async и defer?

#answer
Оба грузятся параллельно разбору HTML, не блокируя его. `defer` выполняется после полного разбора, в порядке следования в документе, — для кода, зависящего от DOM и других скриптов. `async` выполняется как только загрузился, без гарантий порядка, — для независимых скриптов вроде аналитики.

#more
В проверке два `defer`-скрипта выполнились в порядке исходника, хотя второй загружался быстрее первого; `async`-скрипт вставал на разное место в разных прогонах. Для кода приложения выбирают `defer` или модули (`type="module"` отложены по умолчанию). `async` на зависимом коде даёт плавающие баги порядка.
::

::question
Зачем нужны preload и preconnect?

#answer
`preload` велит грузить критичный ресурс сейчас с высоким приоритетом — шрифт, LCP-картинку, — чтобы он не ждал своей очереди. `preconnect` заранее устанавливает соединение (DNS, TCP, TLS) к нужному origin, экономя время первого запроса к нему.

#more
`fetchpriority="high"` поднимает приоритет, `low` понижает несрочное. Подсказками не злоупотребляют: если предзагрузить всё, приоритеты теряют смысл и можно отнять полосу у по-настоящему важного. Для вероятной следующей страницы — `prefetch` с низким приоритетом или Speculation Rules.
::

::question
Что даёт HTTP/2 и HTTP/3?

#answer
HTTP/2 — мультиплексирование: много запросов в одном соединении параллельно, без отдельного соединения на каждый файл. Из-за этого совет «всё в один бандл» частично устарел. HTTP/3 поверх QUIC устанавливает соединение быстрее и не страдает от блокировки очереди на уровне TCP, что помогает на нестабильных сетях.

#more
Бандлинг всё равно нужен ради сжатия и tree-shaking, но делить его на разумные части стало безопасно — это улучшает кеширование, потому что меняется только изменившийся чанк. Сжатие (brotli) даёт гораздо больше, чем склейка файлов: в проверке повторяющийся CSS сжался в десятки раз.
::

::question
Как ускорить первый показ контента?

#answer
Убрать блокировку (defer для JS, критический CSS инлайн), включить сжатие (brotli), preload ключевых ресурсов и preconnect к нужным origin, разделение кода, SSR или SSG для готового HTML, оптимизация и предзагрузка LCP-элемента.

#more
Начинают с измерения критического пути и определения LCP-элемента, потому что ускорять нужно именно его путь. Early Hints сокращают «мёртвое» время, пока сервер генерирует HTML. И проверяют, что LCP-картинка не помечена `loading="lazy"` — частая причина внезапно высокого LCP.
::

::question
Что такое bfcache и что его ломает?

#answer
Back/forward cache — снимок страницы в памяти, который браузер мгновенно восстанавливает при переходе «назад/вперёд» без сети и перезагрузки. Ломают его обработчик `unload` и заголовок `Cache-Control: no-store`, иногда открытые соединения.

#more
Вместо `unload` используют `pagehide` и `visibilitychange` — они совместимы с bfcache и к тому же надёжнее срабатывают на мобильных. Совместимость проверяют в DevTools (Application → Back/forward cache). Это бесплатная мгновенная навигация, которую легко потерять по неосторожности.
::

## Практика

::practice{title="Скрипт в шапке тормозит показ страницы"}
Страница долго показывает пустой экран. В `<head>` — синхронный тег виджета чата и шрифтовой CSS:

```html
<head>
  <link rel="stylesheet" href="/fonts.css">
  <script src="https://widget.example.com/chat.js"></script>
</head>
```

#solution
Синхронный скрипт останавливает разбор HTML до своей загрузки и выполнения, а внешний CSS блокирует первую отрисовку. В проверке блокирующий стиль отодвинул отрисовку на сотни миллисекунд, а синхронный скрипт в теле не дал разобрать то, что ниже него. Разблокируют путь:

```html
<head>
  <style>/* критический CSS первого экрана инлайн */</style>
  <link rel="preload" href="/fonts.css" as="style" onload="this.rel='stylesheet'">
  <script src="https://widget.example.com/chat.js" defer></script>
</head>
```

Критический CSS — инлайн, остальной грузится асинхронно; виджет чата не нужен для первого показа, поэтому `defer` (а лучше — загрузка после взаимодействия). Шрифт предзагружают и дают `font-display: swap`, чтобы текст не ждал его.
::

::practice{title="Переход «назад» каждый раз перезагружает страницу"}
В аналитике видно, что возврат на предыдущую страницу по кнопке браузера каждый раз делает полный запрос и показывает спиннер, хотя пользователь только что там был. В коде есть обработчик ухода:

```js
window.addEventListener('unload', () => sendAnalytics('leave'));
```

#solution
Обработчик `unload` отключает bfcache — браузер не может сохранить снимок страницы, и возврат грузит её заново. Заменяют на совместимые события:

```js
window.addEventListener('pagehide', () => sendAnalytics('leave'));
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') flushAnalytics();
});
```

`pagehide` и `visibilitychange` работают с bfcache и надёжнее срабатывают на мобильных, где вкладку часто закрывают без `unload`. Ещё проверяют, что у документа нет `Cache-Control: no-store`. После этого возврат восстанавливается из памяти мгновенно. Совместимость смотрят в DevTools → Application → Back/forward cache.
::
