# Производительность загрузки

Первая половина битвы за скорость - **как быстро полезный контент доходит до экрана**. Здесь решают критический путь рендеринга, блокирующие ресурсы, подсказки браузеру и протоколы. Это напрямую улучшает [LCP и FCP](/content/security-perfomance/core-web-vitals).

---

## Критический путь рендеринга

Чтобы что-то показать, браузер проходит цепочку:

```
HTML → DOM
CSS  → CSSOM
       ↓
   Render Tree → Layout → Paint
```

JS может **вмешаться и заблокировать** этот путь. Цель оптимизации загрузки - сократить и разблокировать критический путь.

---

## Блокирующие ресурсы

| Ресурс | Поведение |
|--------|-----------|
| **CSS** | блокирует **рендеринг** (браузер не рисует без CSSOM) |
| **Синхронный JS** | блокирует **парсинг** HTML (стоп до загрузки и выполнения) |

```html
<script src="app.js"></script>          <!-- ❌ блокирует парсинг -->
<script src="app.js" defer></script>     <!-- ✅ не блокирует, выполнится после парсинга -->
<script src="analytics.js" async></script> <!-- ✅ загрузится параллельно, выполнится когда готов -->
```

<b class="text-on-semi-light">async vs defer</b> - <span class="text-gray">Оба не блокируют парсинг при загрузке. **`defer`** - выполняется **после** парсинга HTML, в порядке следования (для кода, зависящего от DOM/порядка). **`async`** - выполняется **как только загрузился**, без гарантий порядка (для независимых скриптов вроде аналитики). Для большинства приложений - `defer` или модули (`type="module"` отложены по умолчанию).</span>

### Critical CSS

CSS блокирует рендер, поэтому критичные стили «над сгибом» **встраивают inline** в HTML, а остальное грузят асинхронно - страница рисуется раньше.

---

## Resource hints

Подсказки браузеру, что грузить раньше:

| Подсказка | Зачем |
|-----------|-------|
| **preload** | загрузить критичный ресурс **сейчас** с высоким приоритетом (шрифт, LCP-картинка) |
| **preconnect** | заранее установить соединение (DNS+TCP+TLS) к нужному origin |
| **dns-prefetch** | заранее резолвить DNS |
| **prefetch** | загрузить ресурс для **вероятной следующей** навигации (низкий приоритет) |
| **modulepreload** | предзагрузить ES-модуль |

```html
<link rel="preload" href="hero.webp" as="image" fetchpriority="high">
<link rel="preconnect" href="https://api.example.com">
```

> `fetchpriority="high"` повышает приоритет ключевого ресурса (например, LCP-изображения), `low` - понижает несрочное.

---

## Грузить меньше и позже

- **Code splitting** + ленивая загрузка по маршрутам/компонентам ([оптимизация сборки](/content/advanced-tooling/optimization), [производительность React](/content/reactjs/performance)) - не тащить весь JS сразу.
- **Lazy-load изображений** ниже сгиба: `<img loading="lazy">`.
- **Tree-shaking и минификация** - меньше байтов в бандле.

Меньше начального кода = быстрее интерактивность.

---

## Сжатие

Поверх минификации сервер отдаёт ассеты сжатыми - **gzip** или **brotli** (brotli сжимает сильнее). Размер для пользователя - это **min + brotli**, по нему и оценивают вес. Настраивается на сервере/CDN.

---

## HTTP/2 и HTTP/3

Протокол влияет на загрузку:

- **HTTP/2** - **мультиплексирование**: много запросов в одном соединении параллельно (раньше каждый файл - своё соединение, отсюда старый совет «бандлить всё в один файл» частично устарел).
- **HTTP/3** (поверх QUIC, UDP) - быстрее установка соединения, нет head-of-line blocking, лучше на нестабильных сетях.

> С HTTP/2+ много мелких запросов дешевле, но бандлинг всё ещё нужен ради сжатия и tree-shaking ([бандлеры](/content/advanced-tooling/bundlers)).

## Серверный рендеринг

Стратегия рендеринга - тоже про загрузку: **SSR/SSG** отдают готовый HTML, ускоряя первый показ (FCP/LCP) по сравнению с пустым SPA, ждущим JS ([рендеринг](/content/reactjs/rendering-and-hydration)).

---

## Back/forward cache (bfcache)

Браузер может сохранить **полный снимок** страницы в памяти при уходе и **мгновенно** восстановить при «назад/вперёд» - без перезагрузки и сети. Огромный выигрыш для навигации, который часто теряют по неосторожности.

<b class="text-on-semi-light">Что ломает bfcache</b> - <span class="text-gray">Обработчики `unload`, `Cache-Control: no-store`, иногда открытые соединения. Senior проверяет совместимость (DevTools → Application → Back/forward cache) и не вешает `unload` - вместо него `pagehide`/`visibilitychange`. Это бесплатная мгновенная навигация, которую легко потерять.</span>

---

## Early Hints и Speculation Rules

Два современных приёма ускорить переходы:

- **103 Early Hints** - промежуточный HTTP-ответ, которым сервер шлёт `preload`/`preconnect` **до** готовности основного ответа. Браузер грузит критичные ресурсы, пока сервер ещё генерирует HTML - сокращает «мёртвое» время TTFB.
- **Speculation Rules API** - декларативно **пререндерить** вероятные следующие страницы:

```html
<script type="speculationrules">
{ "prerender": [{ "where": { "href_matches": "/product/*" } }] }
</script>
```

Браузер заранее пререндерит страницу - переход становится мгновенным. Современная замена ручному prefetch для многостраничных сайтов.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое критический путь рендеринга?</b>
<span class="text-gray">Последовательность от HTML/CSS до первой отрисовки: DOM + CSSOM → render tree → layout → paint. CSS блокирует рендеринг, синхронный JS - парсинг. Цель - сократить и разблокировать путь.</span>

<b class="text-on-semi-light">В чём разница async и defer?</b>
<span class="text-gray">Оба грузятся не блокируя парсинг. `defer` выполняется после парсинга в порядке следования (зависит от DOM). `async` - сразу как загрузился, без порядка (независимые скрипты, аналитика).</span>

<b class="text-on-semi-light">Зачем preload и preconnect?</b>
<span class="text-gray">`preload` - загрузить критичный ресурс сейчас с высоким приоритетом (шрифт, LCP-картинка). `preconnect` - заранее установить соединение к origin (DNS+TCP+TLS), экономя время первого запроса.</span>

<b class="text-on-semi-light">Что даёт HTTP/2?</b>
<span class="text-gray">Мультиплексирование - много запросов в одном соединении параллельно, без затрат на отдельное соединение для каждого файла. Из-за этого старый совет «всё в один бандл» частично устарел, но бандлинг нужен ради сжатия/tree-shaking.</span>

<b class="text-on-semi-light">Как ускорить первый показ контента?</b>
<span class="text-gray">Убрать render-blocking (defer JS, critical CSS inline), сжатие (brotli), preload ключевых ресурсов, code splitting, SSR/SSG для готового HTML, оптимизация и приоритизация LCP-элемента.</span>

<b class="text-on-semi-light">Что такое bfcache и что его ломает?</b>
<span class="text-gray">Back/forward cache - снимок страницы в памяти для мгновенного восстановления при «назад/вперёд» без перезагрузки. Ломают `unload`-обработчики и `Cache-Control: no-store`. Вместо `unload` использовать `pagehide`/`visibilitychange`.</span>
