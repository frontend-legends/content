# Основы безопасности

Образ мышления, на котором держатся все остальные темы безопасности: не доверять вводу и клиенту, искать, кто и как может атаковать, защищаться слоями и давать минимум прав. Здесь — модель угроз, поверхность атаки фронтенда, контроль доступа на сервере, наименьшие привилегии, OWASP Top 10 и безопасность по умолчанию. Спрашивают, почему нельзя полагаться на проверки в браузере и какова роль фронтенда в безопасности. Глубже — как скрытая кнопка, перебор id, лишнее поле в форме и цена из корзины превращаются в уязвимости и что сервер должен проверять в каждом запросе.

::tldr
- **Клиент принадлежит пользователю:** код в браузере можно прочитать, изменить и обойти, запрос — отправить из консоли. Проверка на клиенте — удобство, защита — только на сервере.
- **Сервер проверяет каждый запрос:** кто пользователь, может ли он это действие с этим объектом, какие поля ему можно менять, — и сам считает всё, что влияет на деньги и права.
- **Модель угроз — привычка:** кто атакует, что ему нужно, через какие точки входа. Вопрос «как это сломать?» задают при проектировании каждой фичи.
- **Защита слоями и минимум прав:** экранирование, CSP, безопасные куки, проверка на сервере; токен и зависимость получают только нужные права. Пробитый слой не открывает всё.
- **Задача фронтенда — не открыть новых дыр и помочь серверу:** не допустить XSS, не хранить секреты в бандле, не раскрывать лишнего в ошибках.
::

## Образ мышления

Сквозной пример — интернет-магазин с личным кабинетом: заказы, профиль, админка для модераторов. На нём три принципа, на которых держится вся глава:

- **Не доверяй вводу.** Всё, что приходит извне, — форма, URL, заголовок, файл, ответ чужого API, — потенциально враждебно. Его проверяют и экранируют при выводе.
- **Не доверяй клиенту.** Браузер полностью под контролем пользователя: DevTools показывают код, позволяют изменить переменную и отправить любой запрос. Любая проверка в браузере — это удобство интерфейса, а не защита.
- **Защищайся слоями** (defense in depth). Не одна стена, а несколько: если один слой пробит, следующие держат.

Из этого следует роль фронтенда. Он не может обеспечить безопасность сам — он часть поверхности атаки. Настоящая защита — авторизация, проверка прав, проверка данных — живёт на сервере. Задача фронтенда — не создать новых дыр (XSS, утечка токенов, секреты в бандле) и помочь серверу: CSP, правильная работа с куки, понятные ошибки без внутренностей.

## Модель угроз

Думать о безопасности — значит отвечать на три вопроса:

- **Кто** — случайный бот, перебирающий известные уязвимости; целенаправленный атакующий; вредоносная зависимость; недобросовестный сотрудник.
- **Что ему нужно** — данные пользователей, аккаунты, деньги, ресурсы сервера, репутация компании.
- **Как** — через какие точки входа: формы, параметры URL, загрузка файлов, сторонние скрипты, API.

Моделирование угроз — не разовый аудит перед релизом, а вопрос, который задают при проектировании каждой фичи: «как это можно сломать?». Для формы отзыва это «что будет, если в тексте окажется `<script>`», для страницы заказа — «что будет, если поменять id в адресе».

### Триада CIA

Цели атак удобно раскладывать по трём свойствам:

- **конфиденциальность** — данные видят только те, кому положено: чужой заказ с адресом не должен открываться;
- **целостность** — данные не подменены: цена заказа не должна зависеть от того, что прислал браузер;
- **доступность** — сервис работает: отказ в обслуживании — атака именно на неё.

Любая угроза бьёт хотя бы по одному из трёх.

## Не доверяй клиенту — на практике

Каждый пример ниже проверен на настоящем HTTP-сервере в двух версиях: наивной и исправленной.

### Скрытая кнопка

Кнопку «удалить пост» показывают только админам. Обычный пользователь её не видит — но может отправить тот же запрос из консоли:

```js
await fetch('/api/posts/1', { method: 'DELETE' }); // куки сессии уйдут сами
```

В проверке наивный сервер ответил 204 и удалил пост. Исправленный проверяет роль из сессии — 403. Скрыть кнопку, защитить маршрут в роутере, не загрузить код админки — это всё интерфейс; права проверяет сервер на каждый запрос.

### Чужой объект по id

Страница заказа — `/orders/10`, данные — `GET /api/orders/10`. Пользователь меняет 10 на 11.

В проверке наивный сервер вернул чужой заказ с адресом доставки. Это **IDOR** (insecure direct object reference) — объект найден по id без проверки, что он принадлежит пользователю. Исправленный сервер ищет заказ среди заказов текущего пользователя и для чужого отвечает 404 — так же, как для несуществующего. В проверке ответы на чужой и несуществующий заказ совпали полностью, поэтому перебором нельзя узнать даже, какие заказы есть. Непредсказуемые id (UUID) усложняют перебор, но проверку владельца не заменяют.

### Лишнее поле в форме

Форма профиля отправляет только имя. Сервер делает `Object.assign(user, body)` — и принимает всё, что пришло:

```js
await fetch('/api/me', { method: 'PATCH', body: JSON.stringify({ name: 'Аня', role: 'admin' }) });
```

В проверке после такого запроса пользователь стал админом и сразу удалил пост. Это **mass assignment**. Исправление — явный список полей, которые можно менять, и схема проверки тела запроса; в исправленной версии роль осталась `user`.

### Цена из браузера

Корзина считает сумму на клиенте и отправляет её вместе с заказом. Наивный сервер берёт цену из запроса — в проверке заказ двух пачек чая по 4900 ₽ оформился на 2 ₽. Исправленный берёт цену из каталога и посчитал 9800 ₽. Всё, что влияет на деньги, права и лимиты, сервер вычисляет сам, а значения от клиента использует только как запрос: «хочу две пачки этого чая».

## Наименьшие привилегии

Каждая часть системы получает минимум прав, нужный для работы. Если её скомпрометируют, ущерб ограничен этими правами.

- **Токены** — с узким набором прав (scope): виджет истории заказов получает токен только на чтение. В проверке токен `orders:read` открыл заказ, но на создание заказа сервер ответил 403.
- **Ключи API** — отдельные для разных сред и задач, публичный ключ карт ограничен доменом.
- **Сторонние скрипты** — в изолированном фрейме или вовсе без доступа к странице, если им это не нужно.
- **Права сотрудников** — модератор отзывов не видит платёжные данные.

## Ошибки без внутренностей

Сообщение об ошибке — тоже канал утечки. Наивный сервер в проверке вернул клиенту текст исключения с путём к файлу и номером строки: `/srv/app/orders.js:42`. Атакующий узнаёт структуру проекта, версии библиотек, иногда — SQL-запрос. Исправленный сервер пишет полную ошибку в свой журнал, а клиенту отдаёт `{ error, incident }` — общий текст и номер инцидента, по которому поддержка найдёт запись. В OWASP Top 10:2025 для этого появилась отдельная категория — неправильная обработка исключительных ситуаций.

Фронтенд со своей стороны не показывает пользователю сырые ответы сервера и не отправляет в систему мониторинга токены и личные данные.

## OWASP Top 10

OWASP Top 10 — список самых распространённых категорий веб-уязвимостей, общий язык индустрии. В редакции 2025 года:

| Код | Категория | Что важно фронтенду |
|-----|-----------|---------------------|
| A01 | Broken Access Control | IDOR, скрытые кнопки, mass assignment — проверки на сервере |
| A02 | Security Misconfiguration | заголовки, CORS, открытые source maps, отладка в продакшене |
| A03 | Software Supply Chain Failures | зависимости, сторонние скрипты, сборка |
| A04 | Cryptographic Failures | HTTP без TLS, секреты в коде |
| A05 | Injection | XSS как частный случай внедрения |
| A06 | Insecure Design | бизнес-логика без модели угроз |
| A07 | Authentication Failures | хранение токенов, сессии, перебор паролей |
| A08 | Software or Data Integrity Failures | скрипты без SRI, неподписанные обновления |
| A09 | Security Logging and Alerting Failures | атаки, которые никто не заметил |
| A10 | Mishandling of Exceptional Conditions | ошибки с внутренностями, отказ в «открытое» состояние |

Список не нужно заучивать по номерам. Полезно знать, что на первом месте — контроль доступа, а цепочка поставок поднялась на третье.

## Безопасность по умолчанию

Зрелый подход — делать безопасное поведение поведением по умолчанию, а опасное — явным:

- React и Vue экранируют текст при выводе, а вставка HTML требует `dangerouslySetInnerHTML` или `v-html` — их легко найти поиском и на ревью;
- куки сессии — `HttpOnly`, `Secure`, `SameSite`, а не «добавим потом»;
- HTTPS везде, CSP со старта проекта, а не после инцидента;
- общий клиент API, который сам добавляет нужные заголовки и не логирует токены.

Тогда, чтобы создать дыру, нужно специально отключить защиту — и это видно в коде.

---

## Красные флаги в ответе

- «Кнопку же не видно» или «маршрут защищён в роутере» как защита.
- Проверка прав только на клиенте, а сервер доверяет роли или цене из запроса.
- Поиск объекта по id без проверки владельца.
- `Object.assign(user, req.body)` и «форма же отправляет только имя».
- Ключи API и секреты в клиентском коде, «потому что сборка их минифицирует».
- Стек ошибки и тексты исключений в ответах API.
- «Безопасность — задача бэкенда» без понимания, какие дыры открывает фронтенд.

## Как спрашивают на собеседовании

::question
Почему нельзя полагаться на проверки в браузере?

#answer
Браузер полностью под контролем пользователя: код видно в DevTools, переменные можно изменить, а любой запрос — отправить из консоли или curl. Скрытая кнопка не мешает отправить DELETE с куками сессии. Проверки на клиенте нужны для удобства; права и данные сервер проверяет на каждый запрос.

#more
Типичные уязвимости из этого — IDOR (чужой объект по id), mass assignment (лишнее поле в теле запроса) и доверие значениям от клиента: цене, роли, скидке. Всё, что влияет на деньги и права, сервер вычисляет сам. Это категория A01 в OWASP Top 10 — самая распространённая.
::

::question
Что такое defense in depth?

#answer
Многослойная защита: HTTPS, экранирование вывода, CSP, безопасные куки, проверка прав и данных на сервере, мониторинг. Если один слой пробит, следующие держат — например, ошибка экранирования не даёт XSS, потому что CSP не пускает чужой скрипт.

#more
Слои должны быть независимыми: два слоя, которые ломаются от одной ошибки, — это один слой. Последний слой — обнаружение: журнал и оповещения о подозрительной активности, чтобы атака не длилась месяцами незаметно.
::

::question
Какова роль фронтенда в безопасности?

#answer
Фронтенд не обеспечивает безопасность сам — он часть поверхности атаки. Его задача — не создавать дыр: не допускать XSS, не хранить секреты в бандле, не держать токены там, где их прочитает скрипт, — и помогать серверу: CSP, правильные куки, общий клиент API.

#more
Ещё фронтенд отвечает за то, что попадает к пользователю и в мониторинг: не показывать сырые ошибки сервера, не отправлять токены и личные данные в логи. И за сторонний код — каждый скрипт аналитики работает с правами страницы.
::

::question
Что такое модель угроз?

#answer
Анализ того, кто может атаковать, что ему нужно и через какие точки входа. Это привычка задавать вопрос «как это сломать?» при проектировании каждой фичи, а не разовый аудит перед релизом.

#more
Для каждой точки входа — формы, параметра URL, загрузки файла, API — перебирают последствия: что будет с конфиденциальностью, целостностью и доступностью. Из модели появляются требования: проверить владельца заказа, ограничить частоту попыток входа, не принимать роль из тела запроса.
::

::question
Что такое принцип наименьших привилегий?

#answer
Каждая часть системы получает минимум прав, нужный для работы: токен с узким scope, отдельные ключи API для задач и сред, сторонний скрипт без доступа к странице. Если часть скомпрометирована, ущерб ограничен её правами.

#more
Токен виджета истории заказов только на чтение не позволит создать заказ, даже если утечёт. Публичные ключи сервисов ограничивают по домену. Права пересматривают: доступы, выданные «на время», имеют свойство оставаться навсегда.
::

::question
Что такое OWASP Top 10 и что в нём важно фронтенду?

#answer
Список самых распространённых категорий веб-уязвимостей от OWASP, общий язык индустрии. В редакции 2025 года на первом месте — нарушение контроля доступа, дальше — ошибки конфигурации и сбои цепочки поставок; XSS входит в категорию внедрений.

#more
Фронтенду особенно близки контроль доступа (не доверять клиенту), конфигурация (заголовки, CORS, source maps), цепочка поставок (зависимости и сторонние скрипты), целостность (SRI) и обработка ошибок — новая категория 2025 года. Для практики полезнее OWASP Cheat Sheets, чем сам список.
::

## Практика

::practice{title="Пользователь открыл чужой заказ"}
Пользователь пишет в поддержку: поменял число в адресе `/orders/10` на 11 и увидел чужой заказ с адресом доставки. Обработчик на сервере:

```js
app.get('/api/orders/:id', (req, res) => {
  const order = db.orders.find(req.params.id);
  if (!order) return res.status(404).end();
  res.json(order);
});
```

#solution
Это IDOR: заказ ищется по id без проверки, что он принадлежит текущему пользователю. В проверке наивная версия вернула чужой заказ с адресом. Владельца проверяют на сервере, а для чужого объекта отвечают так же, как для несуществующего:

```js
app.get('/api/orders/:id', (req, res) => {
  const order = db.orders.find(req.params.id);
  if (!order || order.userId !== req.session.userId) return res.status(404).end();
  res.json(order);
});
```

В проверке ответы на чужой и несуществующий заказ совпали полностью — перебором не узнать, какие заказы есть. UUID вместо последовательных номеров усложняет перебор, но не заменяет проверку. Такие проверки удобнее делать в одном слое доступа к данным, а не в каждом обработчике, — иначе следующий эндпоинт забудет.
::

::practice{title="Обычный пользователь стал админом"}
В журнале видно, что пользователь без прав удалил пост. Перед этим он отправил запрос на изменение профиля. Обработчик профиля:

```js
app.patch('/api/me', (req, res) => {
  Object.assign(req.user, req.body);
  res.json(req.user);
});
```

#solution
Mass assignment: форма отправляет только имя, но тело запроса можно дописать — `{ "name": "Аня", "role": "admin" }`. В проверке наивный сервер принял роль, и следующий запрос на удаление прошёл. Сервер принимает только разрешённые поля:

```js
app.patch('/api/me', (req, res) => {
  const { name } = profileSchema.parse(req.body); // схема знает только name
  req.user.name = name;
  res.json(req.user);
});
```

В исправленной версии роль осталась `user`. Тот же принцип — для цены, скидки, статуса заказа: сервер не берёт их из запроса, а вычисляет или проверяет сам. На фронтенде ничего чинить не нужно — скрытое поле формы не защищает.
::
