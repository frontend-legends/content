# Основы безопасности

Прежде чем разбирать конкретные атаки (XSS, CSRF), нужно усвоить **образ мышления**. Безопасность - это не список фиксов, а постоянная установка: **не доверяй вводу, никогда не полагайся на клиент, защищайся слоями**. Это то, что проверяют на senior-собесах в первую очередь.

---

## Образ мышления

Три принципа, на которых держится всё остальное:

- **Не доверяй вводу.** Всё, что приходит извне (форма, URL, ответ API, заголовок, файл), потенциально враждебно. Валидируй и экранируй.
- **Никогда не доверяй клиенту.** Код в браузере **публичен и подконтролен пользователю** - его можно изменить, обойти, подделать запросы. Любая проверка на клиенте - это UX, а не защита.
- **Defense in depth.** Не одна стена, а слои: даже если один уровень пробит, следующие держат.

<b class="text-on-semi-light">Ключевая мысль</b> - <span class="text-gray">Фронтенд **не может** обеспечить безопасность сам - он часть поверхности атаки. Реальная защита (авторизация, валидация, проверка прав) живёт на сервере. Задача фронтенда - не открыть новых дыр (XSS, утечка токенов) и помочь серверу (CSP, корректная работа с куки).</span>

---

## Модель угроз

Думать о безопасности - значит спросить: **кто, что и как** может атаковать.

- **Кто** - случайный скрипт-кидди, целевой атакующий, вредоносная зависимость, инсайдер.
- **Что хотят** - данные пользователей, аккаунты, деньги, репутацию, ресурсы.
- **Как** - через какие точки входа (поверхность атаки).

Threat modeling - не разовый аудит, а привычка: проектируя фичу, спрашивай «как это можно сломать?».

---

## Поверхность атаки фронтенда

| Угроза | Суть |
|--------|------|
| **XSS** | внедрение чужого скрипта в страницу |
| **CSRF** | подделка запросов от имени пользователя |
| **Clickjacking** | обман кликом через невидимый iframe |
| **Supply chain** | вредоносная зависимость в бандле |
| **Утечка данных** | секреты/токены в клиентском коде |
| **Небезопасное хранение** | токены в уязвимом localStorage |
| **MITM** | перехват трафика без HTTPS |

Каждой посвящена своя глава далее.

---

## Триада CIA

Классическая модель целей безопасности:

- **Confidentiality (конфиденциальность)** - данные видят только те, кому положено.
- **Integrity (целостность)** - данные не подменены.
- **Availability (доступность)** - сервис работает (DoS - атака на доступность).

Любая угроза бьёт по одной из трёх.

---

## Принцип наименьших привилегий

Давай каждой части системы **минимум прав**, нужный для работы. Токен с минимальным скоупом, узкие права API, ограниченный доступ зависимостей. Если что-то скомпрометировано, ущерб ограничен.

---

## Никогда не доверяй клиенту - на практике

```js
// ❌ «защита» на клиенте, которую обходят за секунду
if (user.role === 'admin') showDeleteButton(); // спрятать кнопку ≠ запретить действие

// ✅ сервер проверяет права на КАЖДЫЙ запрос
// DELETE /api/posts/42 → сервер проверяет, что юзер - админ
```

<b class="text-on-semi-light">Правило</b> - <span class="text-gray">Клиентские проверки (спрятать кнопку, валидировать форму, защитить маршрут) - это **удобство**, не безопасность. Их видно в DevTools и легко обойти. **Каждое** чувствительное действие авторизует и валидирует сервер заново. Подробнее про маршруты - в [роутинге](/content/reactjs/routing), про валидацию - в [формах](/content/ecosystem-libs/forms-and-validation).</span>

## OWASP

**OWASP Top 10** - список самых распространённых веб-уязвимостей, индустриальный ориентир. Релевантные фронтенду: инъекции (XSS), сломанная аутентификация, небезопасная конфигурация, уязвимые зависимости, недостаточный контроль доступа. Знать OWASP - хороший сигнал на собесе.

---

## Secure by default

Зрелый подход - делать **безопасное поведением по умолчанию**, а не опцией: HTTPS везде, экранирование по умолчанию (как в React/Vue), безопасные дефолты куки (`HttpOnly`, `Secure`, `SameSite`), CSP. Тогда чтобы создать дыру, нужно явно «отключить» защиту (`dangerouslySetInnerHTML`), а не наоборот.

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему нельзя полагаться на проверки в браузере?</b>
<span class="text-gray">Клиентский код публичен и подконтролен пользователю - его видно в DevTools, можно изменить и подделать запросы. Клиентские проверки - это UX; реальную авторизацию и валидацию делает сервер на каждый запрос.</span>

<b class="text-on-semi-light">Что такое defense in depth?</b>
<span class="text-gray">Многослойная защита: HTTPS, CSP, серверная валидация, экранирование, безопасные куки. Если один слой пробит, следующие держат. Не полагаться на одну меру.</span>

<b class="text-on-semi-light">Какова роль фронтенда в безопасности?</b>
<span class="text-gray">Фронтенд не обеспечивает безопасность сам (он часть поверхности атаки), но обязан не создавать дыр (XSS, утечка токенов) и помогать: CSP, корректная работа с куки, санитизация, не хранить секреты на клиенте.</span>

<b class="text-on-semi-light">Что такое модель угроз?</b>
<span class="text-gray">Анализ «кто, что и как» может атаковать: какие злоумышленники, что хотят, через какие точки входа. Привычка спрашивать «как это сломать?» при проектировании каждой фичи.</span>

<b class="text-on-semi-light">Что такое принцип наименьших привилегий?</b>
<span class="text-gray">Давать каждой части минимум прав, нужный для работы (узкие скоупы токенов, права API). При компрометации ущерб ограничен.</span>
