# XSS

Межсайтовый скриптинг — когда чужой JavaScript выполняется в странице в сессии пользователя. Именно фронтенд решает, попадут ли недоверенные данные в DOM как код, поэтому понимать XSS обязан каждый. Здесь — три вида атаки, контекстное экранирование, автоэкранирование фреймворков и его лазейки, санитизация сырого HTML, опасные точки записи, проверка ссылок, слои защиты и Trusted Types. Спрашивают, какие бывают типы XSS и как защититься. Глубже — почему экранирование зависит от контекста, почему свой санитайзер на регулярках недостаточен и как сериализовать состояние для SSR, не открыв дыру.

::tldr
- **XSS — выполнение чужого скрипта в сессии жертвы:** он может действовать от её имени и читать данные страницы. Фронтенд решает, попадут ли данные в DOM как код.
- **Три вида:** хранимый (скрипт сохранён на сервере, бьёт по всем), отражённый (приходит в запросе и возвращается в ответе), DOM-based (баг целиком на клиенте — недоверенные данные пишутся в опасную точку).
- **Главная защита — контекстное экранирование вывода:** его делают фреймворки по умолчанию. В проверке React вывел строку с тегом как текст, тег не возник.
- **Сырой HTML санитизируют проверенной библиотекой:** в проверке DOMPurify убрал `<script>`, обработчики событий и `javascript:`-ссылки; санитайзер на регулярках обработчик пропустил.
- **Защита слоями:** экранирование, санитизация, CSP, HttpOnly-куки, Trusted Types. В проверке под Trusted Types присвоить строку в `innerHTML` стало нельзя — DOM-XSS закрыт на корню.
::

---

## Что это и чем опасно

XSS (cross-site scripting) — внедрение чужого JavaScript в страницу, где он выполняется в браузере жертвы, в её сессии и с её правами. Такой скрипт может действовать от имени пользователя, читать и отправлять данные страницы, подменять содержимое, вести кейлоггер. По сути атакующий получает контроль над тем, что пользователь видит и делает на странице.

Ключевая мысль: XSS возникает там, где недоверенные данные попадают в DOM **как код, а не как текст**. Поэтому вся защита — про то, чтобы данные оставались данными.

---

## Три вида

- **Хранимый (stored).** Скрипт сохраняется на сервере — в комментарии, имени, профиле — и отдаётся всем, кто откроет страницу. Самый опасный: бьёт по многим сразу.
- **Отражённый (reflected).** Скрипт приходит в запросе, обычно в параметре URL, и возвращается в ответе без экранирования. Доставляется ссылкой: жертва переходит по ней — срабатывает.
- **DOM-based.** Уязвимость целиком на клиенте: JavaScript берёт недоверенные данные (из URL, `location`, ввода) и пишет их в опасную точку DOM. Сервер тут ни при чём — баг в клиентском коде.

Первые два зависят от того, экранирует ли вывод сервер или шаблон, третий — от того, что делает клиентский код с данными.

---

## Экранирование зависит от контекста

Главная защита — контекстное экранирование вывода: спецсимволы превращаются в сущности, чтобы данные читались как текст, а не как разметка. Но правила зависят от того, **куда** вставляются данные.

В проверке полное HTML-экранирование превратило строку `<img src=x onerror=handler()>` в `&lt;img src=x onerror=handler()&gt;` — как текст она безвредна. А «экранирование только для тела», которое трогает лишь угловые скобки, оставило кавычки нетронутыми — в значении атрибута этого мало: закрывающая кавычка выходит из значения и открывает новый атрибут-обработчик. Поэтому:

| Контекст | Опасность | Чем закрывают |
|----------|-----------|---------------|
| HTML-тело | `<script>` | HTML-сущности |
| Значение атрибута | `" onmouseover=…` | кавычки плюс экранирование кавычек |
| JavaScript | вставка в скрипт или обработчик | не вставлять; если надо — JS-экранирование |
| URL (`href`, `src`) | `javascript:` | проверка протокола |
| CSS | старый `expression()`, `url()` | избегать динамики в стилях |

Вывод: «безопасная для HTML» строка может быть опасна в атрибуте, URL или JS. Поэтому полагаются на контекстно-осознанные механизмы, а не на ручную замену символов в одном контексте.

---

## Фреймворки экранируют по умолчанию

React и Vue автоматически экранируют данные, вставленные как текст ([React](/content/reactjs/security), [Vue](/content/vuejs/security)). В проверке React отрендерил `<div>` с недоверенной строкой внутри и вывел `<div>&lt;img src=x onerror=handler()&gt;</div>` — тег не возник, строка осталась текстом.

Но есть лазейки, которые отключают защиту и вставляют сырой HTML:

```jsx
<div dangerouslySetInnerHTML={{ __html: userInput }} /> // React
<div v-html="userInput"></div>                          // Vue
```

Сюда нельзя передавать недоверенные данные без санитизации. Эти точки легко найти поиском и на ревью — в этом смысл «безопасного по умолчанию»: чтобы создать дыру, нужно специально написать опасную конструкцию.

---

## Санитизация сырого HTML

Если нужно вставить именно HTML — например, форматированный текст из редактора, — его очищают: удаляют опасные теги и атрибуты. Стандарт — DOMPurify. В проверке он убрал `<script>`, оставив текст, вырезал атрибут `onerror`, обезвредил `javascript:`-ссылку и сохранил безопасную `https`-ссылку. В очищенном DOM не осталось ни тегов `script`, ни обработчиков `onclick`.

Свой санитайзер на регулярках писать нельзя: в проверке выражение, вырезающее `<script>`, оставило `onerror` в строке нетронутым — обойти такой фильтр тривиально, способов закодировать полезную нагрузку десятки. Отдельная ловушка — **mutation XSS**: очищенный HTML может измениться при повторном разборе браузером и восстановить опасную конструкцию уже после санитизации. Поэтому берут проверенную поддерживаемую библиотеку и регулярно её обновляют — в DOMPurify периодически находят и чинят обходы.

```js
import DOMPurify from 'dompurify';
el.innerHTML = DOMPurify.sanitize(dirtyHtml); // вырежет script, обработчики, опасные ссылки
```

---

## Опасные точки и ссылки

DOM-XSS возникает при записи недоверенных данных в опасные точки: `innerHTML`, `outerHTML`, `document.write`, `eval`, `new Function`, присваивание `location`. С непроверенными данными их избегают — текст пишут через `textContent`, а не `innerHTML`.

Экранирование текста не защищает ссылки: в `javascript:`-URL экранировать нечего, а при клике код выполнится. Протокол ссылки из пользовательских данных проверяют по белому списку. В проверке такая проверка отклонила `javascript:` и `data:`, вернув `#`, и пропустила `http`, `https` и `mailto`:

```js
function safeHref(raw) {
  let url;
  try { url = new URL(raw, location.origin); } catch { return '#'; }
  return ['http:', 'https:', 'mailto:'].includes(url.protocol) ? url.href : '#';
}
```

## Серверный рендеринг состояния

При :term[SSR]{def="серверный рендеринг: HTML страницы собирается на сервере на каждый запрос"} своя классическая ошибка — встраивание состояния в страницу. `JSON.stringify` не экранирует `</script>`: если в данных есть такая подстрока, браузер закроет тег скрипта раньше времени. В проверке наивная сериализация содержала `</script>`, а после замены `<` на `<` — нет, при этом данные после разбора остались прежними (`<` — тот же символ `<`):

```js
const json = JSON.stringify(state).replace(/</g, '\\u003c');
```

Фреймворки делают это сами, но при ручном SSR нужно помнить. Так же сервер должен экранировать любые пользовательские данные, которые подставляет в HTML вокруг разметки фреймворка.

---

## Слои защиты

XSS лечат в несколько слоёв — если один пробит, держат следующие:

1. **экранирование вывода** фреймворком — первая линия;
2. **санитизация** сырого HTML (DOMPurify);
3. **[CSP](/content/security-perfomance/csp-and-security-headers)** — даже внедрённый скрипт не выполнится без разрешения политики;
4. **HttpOnly-куки** — токен недоступен JavaScript, и XSS не прочитает его из куки;
5. **:term[Trusted Types]{def="механизм браузера: опасные места вроде innerHTML принимают только значения, прошедшие доверенную функцию"}** — браузер запрещает присваивать строку в опасную точку.

В проверке под заголовком `Content-Security-Policy: require-trusted-types-for 'script'` присвоить сырую строку в `innerHTML` стало нельзя — браузер бросил `TypeError`, а принял только значение, прошедшее через политику очистки. Это закрывает DOM-XSS на корню: любой путь данных в sink обязан пройти через проверенную функцию. CSP и HttpOnly сами XSS не предотвращают, но снижают урон.

---

## Красные флаги в ответе

- «React/Vue полностью защищают от XSS» — только текст; `dangerouslySetInnerHTML`, `v-html`, ссылки и ручной SSR на разработчике.
- Свой санитайзер на регулярках вместо DOMPurify.
- Экранирование «заменим `<` на `&lt;`» без учёта контекста атрибута, URL и JS.
- Запись пользовательских данных в `innerHTML`, `eval`, `href` без проверки.
- `JSON.stringify` состояния прямо в `<script>` при SSR без экранирования `<`.
- «HttpOnly спасёт от XSS» — он лишь не даёт украсть токен из куки, но не предотвращает выполнение скрипта.

## Как спрашивают на собеседовании

::question
Что такое XSS и чем он опасен?

#answer
Внедрение чужого JavaScript, который выполняется в браузере жертвы в её сессии и с её правами: может действовать от имени пользователя, читать и отправлять данные страницы, вести кейлоггер. Возникает, когда недоверенные данные попадают в DOM как код, а не как текст. Решает это фронтенд.

#more
Чтобы украсть сессию через XSS, токен должен быть доступен скрипту — поэтому его держат в HttpOnly-куке. Но XSS опасен и без кражи токена: скрипт уже в сессии и может сам выполнять действия от имени пользователя, так что HttpOnly снижает урон, но не отменяет проблему.
::

::question
Какие бывают типы XSS?

#answer
Хранимый — скрипт сохранён на сервере и отдаётся всем читателям, бьёт по многим. Отражённый — скрипт приходит в запросе (обычно URL) и возвращается в ответе без экранирования, доставляется ссылкой. DOM-based — баг целиком на клиенте: недоверенные данные пишутся в опасную точку вроде `innerHTML`, сервер ни при чём.

#more
Первые два зависят от экранирования на выводе — сервером или шаблоном, — третий от того, что клиентский код делает с данными из URL и ввода. Trusted Types нацелены именно на DOM-based: они запрещают путь строки в sink без проверки.
::

::question
Как защититься от XSS?

#answer
Слоями: контекстное экранирование вывода (фреймворки делают по умолчанию), санитизация сырого HTML проверенной библиотекой (DOMPurify), CSP, HttpOnly-куки, проверка протокола ссылок, избегание опасных точек (`innerHTML`, `eval`). Trusted Types закрывают DOM-XSS.

#more
Слои независимы: ошибка экранирования не даёт XSS, если CSP не пускает чужой скрипт. В проверке DOMPurify убирал обработчики и `javascript:`-ссылки, а под Trusted Types присвоить строку в `innerHTML` было нельзя. Главное — не писать свой санитайзер на регулярках: его тривиально обойти.
::

::question
Почему экранирование зависит от контекста?

#answer
Правила различаются для HTML-тела, значения атрибута, JavaScript, URL и CSS. «Безопасная для HTML» строка может быть опасна в атрибуте или в `href`. В проверке экранирование только угловых скобок оставило кавычки, а в атрибуте закрывающая кавычка открывает новый обработчик события.

#more
Поэтому полагаются на контекстно-осознанные механизмы фреймворка, а не на ручную замену символов в одном контексте. Для URL экранирование вообще не помогает — нужен белый список протоколов, потому что в `javascript:`-ссылке экранировать нечего.
::

::question
Почему нельзя писать свой санитайзер?

#answer
HTML-разбор полон краевых случаев, и обойти наивный фильтр тривиально. В проверке регулярное выражение, вырезавшее `<script>`, оставило атрибут `onerror`. Есть и mutation XSS, когда очищенный HTML восстанавливает опасную конструкцию при повторном разборе браузером.

#more
Поэтому берут проверенную поддерживаемую библиотеку (DOMPurify) и обновляют её — в ней периодически находят и чинят обходы mXSS. Санитизацию делают там, где вставляют сырой HTML; если его можно избежать и вывести данные как текст — это надёжнее любой очистки.
::

::question
Защищает ли HttpOnly-кука от XSS?

#answer
Не предотвращает XSS, но снижает урон: токен в HttpOnly-куке недоступен JavaScript, поэтому внедрённый скрипт не прочитает его из куки и не угонит сессию простым способом. Это слой защиты, а не панацея.

#more
Скрипт всё ещё в сессии и может выполнять действия от имени пользователя, пока страница открыта. Поэтому HttpOnly сочетают с другими слоями — CSP, экранированием, Trusted Types. Хранить токен в `localStorage`, доступном скрипту, — наоборот, облегчает кражу при XSS.
::

## Практика

::practice{title="Комментарии с разметкой выполняют скрипт"}
Блог показывает комментарии с форматированием, подставляя их HTML напрямую:

```js
commentEl.innerHTML = comment.html;
```

Пользователь оставил комментарий, и у читателей начал срабатывать чужой код. Это хранимый XSS.

#solution
Сырой HTML из комментария попадает в DOM как код. Если форматирование нужно, HTML очищают проверенной библиотекой перед вставкой:

```js
import DOMPurify from 'dompurify';
commentEl.innerHTML = DOMPurify.sanitize(comment.html);
```

В проверке DOMPurify убрал `<script>`, атрибут `onerror` и `javascript:`-ссылку, оставив безопасную разметку. Если форматирование не нужно, ещё надёжнее вывести комментарий как текст — `commentEl.textContent = comment.text` — тогда вставлять нечего. Свой фильтр на регулярках не подойдёт: в проверке он пропустил обработчик события. Дополнительный слой — CSP, который не даст выполниться скрипту, даже если очистку обойдут.
::

::practice{title="Ссылка профиля выполняет код при клике"}
Пользователь указывает сайт в профиле, и он выводится ссылкой. Текст экранируется, но при клике по некоторым ссылкам выполняется код:

```jsx
<a href={user.website}>{user.website}</a>
```

#solution
Экранирование текста не трогает значение `href`, а в ссылке со схемой `javascript:` при клике выполнится код. Протокол проверяют по белому списку:

```jsx
function safeHref(raw) {
  try {
    const url = new URL(raw, location.origin);
    return ['http:', 'https:', 'mailto:'].includes(url.protocol) ? url.href : '#';
  } catch { return '#'; }
}
<a href={safeHref(user.website)} rel="noopener noreferrer" target="_blank">{user.website}</a>
```

В проверке такая функция отклонила `javascript:` и `data:`, вернув `#`, и пропустила `http`, `https`, `mailto`. React 19 вдобавок блокирует `javascript:`-ссылки сам, но белый список нужен всё равно: другие опасные схемы он пропускает. Атрибут `rel="noopener"` закрывает отдельную проблему — доступ открытой вкладки к `window.opener`.
::
