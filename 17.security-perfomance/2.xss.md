# XSS

**Cross-Site Scripting (XSS)** - внедрение чужого JavaScript в страницу, который выполняется в браузере жертвы. Это самая распространённая и самая «фронтендовая» уязвимость: именно фронтенд решает, попадёт ли вредоносный код в DOM. Глубоко понимать XSS обязан каждый.

---

## Чем опасен

Внедрённый скрипт выполняется **в сессии жертвы** с её правами и может:

- украсть **куки/токены** (если они доступны JS) и угнать сессию;
- выполнять **действия от имени** пользователя (перевести деньги, сменить пароль);
- логировать ввод (кейлоггер), подменять контент, фишить;
- распространяться (XSS-червь).

По сути, атакующий получает полный контроль над тем, что пользователь видит и делает на странице.

---

## Три типа XSS

### Stored (хранимый)

Вредоносный скрипт **сохраняется на сервере** (в комментарии, имени, профиле) и отдаётся всем, кто откроет страницу. Самый опасный - бьёт по многим.

```
Атакующий пишет комментарий: <script>steal(document.cookie)</script>
→ сервер сохранил → каждый читатель выполняет скрипт
```

### Reflected (отражённый)

Скрипт приходит в **запросе** (обычно в URL) и **отражается** обратно в ответе без экранирования.

```
example.com/search?q=<script>...</script>
→ страница выводит «Результаты для: <script>...</script>» → выполняется
```

Доставляется через ссылку (фишинг): жертва кликает - срабатывает.

### DOM-based

Уязвимость **целиком на клиенте**: JS берёт недоверенные данные (из URL, `location`, ввода) и пишет их в опасный «sink» DOM.

```js
// ❌ DOM XSS: данные из URL напрямую в innerHTML
document.querySelector('#out').innerHTML = location.hash.slice(1);
// #<img src=x onerror=alert(1)> → выполнится
```

Сервер тут ни при чём - баг в клиентском коде.

## Защита: экранирование

Главная защита - **контекстно-зависимое экранирование** вывода. Спецсимволы (`<`, `>`, `&`, `"`) превращаются в безопасные сущности, чтобы данные трактовались как **текст**, а не код.

```
<script>  →  &lt;script&gt;   (выведется как текст, не выполнится)
```

<b class="text-on-semi-light">Контекст имеет значение</b> - <span class="text-gray">Экранирование зависит от того, **куда** вставляются данные: в HTML-тело, в значение атрибута, в JS, в URL - правила разные. Вставить «безопасную для HTML» строку в `href` или в `<script>` всё ещё опасно. Поэтому используют контекстно-осознанные механизмы, а не ручную замену символов.</span>

---

## Фреймворки экранируют по умолчанию

React и Vue **автоматически экранируют** данные, вставленные как текст ([React](/content/reactjs/security), [Vue](/content/vuejs/security)):

```jsx
<div>{userInput}</div>   // React: выведет как текст, скрипт не выполнится
```

Но есть **лазейки**, которые отключают защиту:

```jsx
<div dangerouslySetInnerHTML={{ __html: userInput }} /> // React
<div v-html="userInput"></div>                          // Vue
```

Сюда нельзя передавать недоверенные данные без санитизации.

## Санитизация

Если нужно вставить **сырой HTML** (например, форматированный текст из редактора), его **очищают** - удаляют опасные теги/атрибуты. Стандарт - **DOMPurify**.

```js
import DOMPurify from 'dompurify';
el.innerHTML = DOMPurify.sanitize(dirtyHtml); // вырежет <script>, onerror и т.п.
```

> Не пиши свой санитайзер регулярками - обойти их тривиально (десятки способов закодировать `<script>`). Используй проверенную библиотеку.

---

## Опасные «sinks»

DOM-XSS возникает при записи недоверенных данных в опасные точки. Избегай их с непроверенными данными:

```js
el.innerHTML = data;        // ❌
el.outerHTML = data;        // ❌
document.write(data);       // ❌
eval(data);                 // ❌
new Function(data);         // ❌
location = data;            // ❌ (javascript:-URL)
```

Безопасные альтернативы: `textContent` вместо `innerHTML`, валидация протокола URL.

---

## URL-инъекции

Экранирование текста **не защищает** ссылки. `javascript:`-URL в `href` выполнит код:

```js
// ❌ если url = "javascript:alert(document.cookie)"
a.href = url;
// ✅ валидировать протокол
const ok = ['http:', 'https:', 'mailto:'].includes(new URL(url, location.origin).protocol);
```

---

## Слои защиты

XSS лечат **в несколько слоёв** (defense in depth):

1. **Экранирование вывода** (фреймворк) - первая линия.
2. **Санитизация** сырого HTML (DOMPurify).
3. **[CSP](/content/security-perfomance/csp-and-security-headers)** - даже если скрипт внедрён, политика запрещает его выполнение.
4. **HttpOnly-куки** - токен недоступен JS, XSS не украдёт сессию из куки.
5. **Trusted Types** - современный API, запрещающий передавать строки в опасные sinks без проверки (убивает DOM-XSS).

> Ни один слой не идеален - вместе они дают надёжность. CSP и HttpOnly не предотвращают XSS, но **снижают урон**.

---

## Контексты экранирования

Экранирование зависит от того, **куда** попадают данные - это сложнее, чем «заменить `<` на `&lt;`»:

| Контекст | Опасность | Правильно |
|----------|-----------|-----------|
| HTML-тело | `<script>` | HTML-сущности |
| Атрибут | `" onmouseover=...` | кавычить значение + экранировать кавычки |
| JS-контекст | вставка в `<script>`/обработчик | JS-экранирование (лучше - не вставлять) |
| URL (`href`/`src`) | `javascript:` | валидировать протокол |
| CSS | `url()`, старый `expression()` | избегать динамики в стилях |

<b class="text-on-semi-light">Вывод</b> - <span class="text-gray">«Безопасная для HTML» строка может быть опасна в атрибуте, JS или URL. Поэтому полагаются на контекстно-осознанные механизмы фреймворка, а не на ручную замену символов в одном контексте.</span>

---

## Mutation XSS

Коварный класс: санированный HTML, который **мутирует** при повторном парсинге браузером и восстанавливает опасную конструкцию уже **после** очистки, обходя наивные санитайзеры.

<b class="text-on-semi-light">Почему важно</b> - <span class="text-gray">Именно поэтому нельзя писать свой санитайзер - и даже в DOMPurify периодически находят и чинят mXSS-обходы. Браузерный парсинг HTML полон краевых случаев; используй проверенную, **поддерживаемую** библиотеку и регулярно обновляй её.</span>

---

## Где ещё прячется XSS

Помимо `innerHTML`/`v-html`/`dangerouslySetInnerHTML`:

- `setAttribute` с обработчиком события или `href`/`src`;
- `iframe srcdoc`, `<svg>`/`<math>` с inline-обработчиками;
- прямая запись сырого HTML в DOM через ref;
- серверный рендеринг неэкранированных данных в HTML или состояние гидратации.

> **Self-XSS** - соцальная инженерия: жертву уговаривают вставить код в консоль («получи преимущество в игре»). Браузеры предупреждают в консоли, но защита здесь - осведомлённость пользователя.

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое XSS и чем он опасен?</b>
<span class="text-gray">Внедрение чужого JS, выполняющегося в браузере жертвы в её сессии. Может украсть куки/токены, действовать от имени пользователя, логировать ввод. Фронтенд решает, попадёт ли код в DOM.</span>

<b class="text-on-semi-light">Какие бывают типы XSS?</b>
<span class="text-gray">Stored (скрипт сохранён на сервере, бьёт по всем), Reflected (скрипт в запросе/URL отражается в ответе), DOM-based (баг целиком на клиенте: недоверенные данные пишутся в опасный sink вроде innerHTML).</span>

<b class="text-on-semi-light">Как защититься от XSS?</b>
<span class="text-gray">Слоями: контекстное экранирование вывода (фреймворки делают по умолчанию), санитизация сырого HTML (DOMPurify), CSP, HttpOnly-куки, избегать опасных sinks (innerHTML, eval), валидировать URL. Trusted Types против DOM-XSS.</span>

<b class="text-on-semi-light">Почему экранирование зависит от контекста?</b>
<span class="text-gray">Правила различаются для HTML-тела, атрибута, JS и URL. «Безопасная для HTML» строка в `href` или `<script>` всё равно опасна. Нужны контекстно-осознанные механизмы, а не ручная замена символов.</span>

<b class="text-on-semi-light">Защищает ли HttpOnly-кука от XSS?</b>
<span class="text-gray">Не предотвращает XSS, но снижает урон: токен в HttpOnly-куке недоступен JS, поэтому внедрённый скрипт не украдёт его из куки. Это слой defense in depth, а не панацея.</span>

<b class="text-on-semi-light">Что такое mutation XSS?</b>
<span class="text-gray">Санированный HTML, мутирующий при повторном парсинге браузером и восстанавливающий опасную конструкцию после очистки - обходит наивные санитайзеры. Поэтому используют проверенную поддерживаемую библиотеку (DOMPurify) и обновляют её, а не пишут свою.</span>

<b class="text-on-semi-light">Почему экранирование зависит от контекста?</b>
<span class="text-gray">Правила различаются для HTML-тела, атрибута, JS, URL и CSS. «Безопасная для HTML» строка опасна в атрибуте или `href`. Нужны контекстно-осознанные механизмы фреймворка, а не ручная замена символов в одном контексте.</span>
