# Производительность выполнения

Вторая половина битвы за скорость — оставаться отзывчивым после загрузки: плавная прокрутка, мгновенная реакция на клик, анимация без рывков. Здесь — главный поток и бюджет кадра, длинные задачи и их дробление, конвейер отрисовки, анимация transform против геометрии, layout thrashing, debounce и throttle, виртуализация, воркеры, `content-visibility` и утечки памяти. Спрашивают, почему интерфейс зависает, что такое бюджет кадра и чем debounce отличается от throttle. Глубже — почему чтение размеров после каждой записи замедляет цикл в сотни раз и как дробление задачи убирает длинную задачу с главного потока.

::tldr
- **Всё делит один главный поток:** JavaScript, раскладка, отрисовка и события. Длинная синхронная задача замораживает интерфейс. В проверке работа на 150 мс дала длинную задачу, та же работа кусками по 10 мс с уступкой потока — ни одной.
- **Бюджет кадра — 16 мс:** для 60 кадров в секунду браузер рисует кадр каждые ~16 мс; работа дольше — пропущенный кадр и рывок.
- **Анимируют transform и opacity:** они идут на композитор, минуя раскладку и отрисовку. Анимация `left`/`width` пересчитывает геометрию каждый кадр.
- **Layout thrashing — главный тормоз DOM-кода:** чтение размеров после каждой записи заставляет пересчитывать раскладку синхронно. В проверке батчинг чтений и записей ускорил цикл в сотни раз.
- **Меньше и реже:** виртуализация длинных списков, debounce и throttle частых событий, тяжёлое — в воркер, `content-visibility` пропускает отрисовку вне экрана.
::

## Главный поток

В браузере JavaScript, раскладка, отрисовка и обработка событий делят один главный поток. Пока он занят длинной синхронной задачей, всё остальное стоит: страница не отвечает на клики, не анимируется, «зависает».

```text
Главный поток: [тяжёлый JS 150 мс] → клики и отрисовка ждут → пользователь видит фриз
```

Почти все «тормоза интерфейса» — это занятый главный поток: долгий синхронный код не уступает управление. **Длинной задачей** браузер считает ту, что идёт дольше 50 мс без перерыва, — именно они портят [INP](/content/security-perfomance/core-web-vitals). Лечение — делать меньше, дробить работу и уступать поток между кусками:

```js
for (const chunk of chunks) {
  await scheduler.yield();  // уступить браузеру (или scheduler.postTask, setTimeout, requestIdleCallback)
  process(chunk);
}
```

В проверке это показано напрямую: одна задача на 150 мс дала одну запись `longtask` в `PerformanceObserver`, а та же работа пятнадцатью кусками по 10 мс, с возвратом управления между ними, — ни одной. Между кусками браузер успевает ответить на клик и нарисовать кадр.

---

## Бюджет кадра

Для плавности в 60 кадров в секунду браузер должен успеть отрисовать кадр за `1000 / 60` ≈ 16 мс. Если работа в кадре превышает бюджет, кадр пропускается и движение дёргается (jank). Поэтому важно не только не блокировать поток надолго, но и укладывать работу каждого кадра в бюджет.

## Конвейер отрисовки

Изменение на странице проходит этапы, и чем дальше по конвейеру удаётся остановиться, тем дешевле:

```text
JS → стили → раскладка (layout) → отрисовка (paint) → композиция (composite)
```

- **раскладка** — пересчёт позиций и размеров, дорого;
- **отрисовка** — перерисовка пикселей без изменения геометрии, дешевле;
- **композиция** — сборка готовых слоёв на GPU, самое дешёвое.

### Анимируют transform и opacity

```css
/* дёргает весь конвейер: раскладка каждый кадр */
.box { transition: left 0.3s; }
/* только композиция на GPU: плавно и дёшево */
.box { transition: transform 0.3s; }
```

`transform` и `opacity` обрабатываются на композиторе, минуя раскладку и отрисовку, поэтому анимация плавная. Анимация `left`, `top`, `width`, `height` пересчитывает геометрию на каждом кадре. `will-change: transform` заранее выносит элемент на отдельный слой перед анимацией, но каждый слой стоит памяти — его ставят точечно и убирают после.

### Layout thrashing

Самая частая ошибка в DOM-коде — чередование чтения и записи раскладки в цикле. Когда после записи сразу читают размер, браузер вынужден пересчитать раскладку синхронно, и так на каждой итерации:

```js
// дёргает раскладку: offsetWidth после каждой записи форсирует пересчёт
items.forEach((el) => { el.style.width = el.offsetWidth + 1 + 'px'; });

// батчинг: сначала все чтения, потом все записи — пересчёт один
const widths = items.map((el) => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + 1 + 'px'; });
```

В проверке на 800 элементах первый вариант занял около 74 мс, второй — около 0,5 мс: разделение чтений и записей ускорило цикл более чем в сто раз при том же результате.

## Меньше и реже

### Debounce и throttle

Частые события (ввод, прокрутка, изменение размера, движение мыши) с тяжёлым обработчиком заваливают главный поток. Частоту ограничивают:

- **debounce** — выполнить после паузы: поиск ждёт, пока перестанут печатать;
- **throttle** — выполнять не чаще раза в N мс: обработчик прокрутки раз в 100 мс.

В проверке на виртуальных часах debounce(300) при наборе пяти букв по одной каждые 50 мс не вызвал обработчик ни разу, пока шёл набор, и ровно один раз — с финальным значением «чайник» — после паузы. throttle(100) на одиннадцати событиях прокрутки за 500 мс вызвал обработчик с ведущим вызовом сразу и дальше не чаще раза в 100 мс — заметно реже, чем приходили события.

### Виртуализация

Тысячи узлов в DOM — дорого и по памяти, и по раскладке. Виртуализация рисует только видимые элементы с небольшим запасом, переиспользуя узлы при прокрутке ([производительность React](/content/reactjs/performance), разбор в [системном дизайне](/content/architecture/system-design-examples)).

### Воркеры

Тяжёлые вычисления — разбор больших данных, обработка изображений — выносят в [веб-воркер](/content/additional-topics/web-workers-and-concurrency), отдельный поток, чтобы главный оставался свободным для интерфейса.

### content-visibility

`content-visibility: auto` велит браузеру пропускать раскладку и отрисовку элементов вне экрана, пока прокрутка до них не дошла, — дешёвая «виртуализация из коробки» для длинных страниц без JavaScript. В проверке отрисовка 300 секций заняла около 37 мс обычно и около 5 мс с `content-visibility: auto`: невидимые секции браузер не раскладывал.

```css
.section { content-visibility: auto; contain-intrinsic-size: 0 400px; }
/* contain-intrinsic-size задаёт примерный размер, чтобы полоса прокрутки не прыгала */
```

## Память

Утечки памяти — тихий убийца долгоживущих :term[SPA]{def="одностраничное приложение: страница загружается раз, а экраны меняет JavaScript"}: куча растёт, паузы сборщика мусора учащаются, всё тормозит. Частые причины — забытые слушатели и таймеры, не снятые при размонтировании, замыкания, удерживающие большие объекты, ссылки на отсоединённые узлы DOM, бесконечно растущие кеши.

В проверке слушатель, добавленный без снятия, продолжал срабатывать и после того, как стал не нужен, а слушатель с `AbortController` переставал — один `abort()` снимает все подписки, привязанные к его сигналу:

```js
const ac = new AbortController();
bus.addEventListener('tick', onTick, { signal: ac.signal });
// при размонтировании:
ac.abort(); // снимает слушатель и любые другие подписки на этот сигнал
```

Это удобно в cleanup-функциях: один сигнал на все подписки компонента. Ограниченные по размеру кеши и слабые ссылки (`WeakMap`, `WeakRef`) не дают структурам расти бесконечно. Ищут утечки снимками кучи в [DevTools](/content/advanced-tooling/devtools-and-debugging).

## Красные флаги в ответе

- «Тормозит — значит, нужен компьютер помощнее»: причина обычно в занятом главном потоке.
- Тяжёлая задача одним синхронным куском, без дробления и уступки потока.
- Анимация `left`/`top`/`width` вместо `transform`/`opacity`.
- Чтение размеров в цикле сразу после записи стилей — layout thrashing.
- Обработчик прокрутки или ввода без throttle/debounce.
- Подписки и таймеры без снятия при размонтировании.
- `will-change` на множестве элементов «на всякий случай» — расход памяти.

## Как спрашивают на собеседовании

::question
Почему интерфейс зависает и дёргается?

#answer
Главный поток один: JavaScript, раскладка, отрисовка и события делят его. Длинная синхронная задача блокирует всё — нет реакции на клик, пропадают кадры анимации. Решение — делать меньше, дробить работу и уступать поток, выносить тяжёлое в воркер.

#more
Длинной браузер считает задачу дольше 50 мс; именно такие портят INP. В проверке работа на 150 мс дала длинную задачу, а та же работа кусками по 10 мс с `scheduler.yield` между ними — ни одной, потому что между кусками браузер успевал ответить на ввод.
::

::question
Что такое бюджет кадра 16 мс?

#answer
Для 60 кадров в секунду браузер рисует кадр каждые ~16 мс (1000/60). Если работа в кадре превышает бюджет, кадр пропускается и движение дёргается. Поэтому работу дробят и укладывают в бюджет, а не только избегают совсем долгих задач.

#more
Из 16 мс часть забирает сама отрисовка браузера, так что на JavaScript остаётся меньше. На экранах 120 Гц бюджет ещё жёстче — около 8 мс. Плавность достигается не «быстрым кодом вообще», а тем, что каждый кадр успевает завершиться вовремя.
::

::question
Почему анимируют transform и opacity, а не left и width?

#answer
`transform` и `opacity` обрабатываются на композиторе (GPU), минуя раскладку и отрисовку, поэтому анимация плавная и дешёвая. Анимация геометрии — `left`, `top`, `width`, `height` — вызывает пересчёт раскладки на каждом кадре, что дорого и ведёт к рывкам.

#more
`will-change: transform` заранее выносит элемент на отдельный слой, чтобы анимация стартовала плавно, но каждый слой стоит памяти — его ставят точечно и убирают после. Position/size-анимации иногда заменяют на `transform: scale`/`translate` с коррекцией.
::

::question
Что такое layout thrashing?

#answer
Чередование чтения и записи раскладки в цикле: после записи стиля сразу читают размер (`offsetWidth`, `getBoundingClientRect`), заставляя браузер синхронно пересчитывать геометрию на каждой итерации. Лечится батчингом: сначала все чтения, потом все записи.

#more
В проверке на 800 элементах чередование заняло ~74 мс, а разделение чтений и записей — ~0,5 мс при том же результате. Инструменты вроде `FastDOM` помогают группировать чтения и записи по фазам кадра. Это одна из самых частых причин заметных тормозов в DOM-коде.
::

::question
Чем debounce отличается от throttle?

#answer
Debounce выполняет обработчик после паузы в событиях — удобно для поиска по вводу: запрос уходит, когда перестали печатать. Throttle выполняет не чаще раза в N мс — удобно для прокрутки и движения мыши. Оба ограничивают частоту тяжёлых обработчиков.

#more
В проверке debounce(300) при наборе пяти букв дал один вызов с финальным значением, а throttle(100) на одиннадцати событиях — ведущий вызов и дальше не чаще раза в 100 мс. Выбор зависит от задачи: debounce ждёт тишины, throttle гарантирует регулярность. Часто комбинируют с `requestAnimationFrame`.
::

::question
Какие частые причины утечек памяти в SPA?

#answer
Забытые слушатели и таймеры, не снятые при размонтировании, замыкания, удерживающие большие объекты, ссылки на отсоединённые узлы DOM, бесконечно растущие кеши. Куча растёт, паузы сборщика мусора учащаются, приложение тормозит.

#more
В проверке слушатель без снятия продолжал срабатывать, а привязанный к `AbortController` переставал после `abort()` — один сигнал удобно снимает все подписки компонента в cleanup. Кеши ограничивают по размеру, для слабых ссылок используют `WeakMap` и `WeakRef`. Ищут утечки снимками кучи в DevTools.
::

## Практика

::practice{title="Пересчёт колонок вешает страницу"}
Скрипт выравнивает ширину карточек по содержимому и заметно подвешивает страницу на больших списках:

```js
cards.forEach((card) => {
  card.style.width = card.querySelector('.content').offsetWidth + 24 + 'px';
});
```

#solution
Это layout thrashing: каждая запись `style.width` делает раскладку «грязной», а следующее чтение `offsetWidth` заставляет браузер пересчитать её синхронно — и так на каждой карточке. В проверке подобный цикл на 800 элементах занял ~74 мс против ~0,5 мс у батченного. Разделяют фазы:

```js
const widths = cards.map((card) => card.querySelector('.content').offsetWidth); // все чтения
cards.forEach((card, i) => { card.style.width = widths[i] + 24 + 'px'; });        // все записи
```

Теперь браузер пересчитывает раскладку один раз. Если работа всё равно велика, её дробят по кадрам с уступкой потока или пересматривают подход — часто то же можно сделать на CSS (`grid`, `min-width`) без чтения размеров из JavaScript.
::

::practice{title="Приложение замедляется через час работы"}
Длинная сессия в SPA постепенно тормозит, вкладка ест всё больше памяти. При навигации между разделами открывается подписка на обновления:

```js
function mount() {
  socket.addEventListener('message', onMessage);
  const id = setInterval(poll, 5000);
}
```

#solution
Подписка и таймер создаются при входе в раздел, но нигде не снимаются при уходе — каждый визит добавляет ещё одну пару, они продолжают работать и удерживают связанные объекты. Классическая утечка. Снимают всё при размонтировании, удобнее через один сигнал:

```js
function mount() {
  const ac = new AbortController();
  socket.addEventListener('message', onMessage, { signal: ac.signal });
  const id = setInterval(poll, 5000);
  return () => { ac.abort(); clearInterval(id); }; // cleanup при уходе из раздела
}
```

В проверке слушатель с `AbortController` переставал срабатывать после `abort()`, а забытый — продолжал. Таймеры снимают `clearInterval`/`clearTimeout`, кеши ограничивают по размеру. Утечку подтверждают снимками кучи в DevTools: число отсоединённых узлов и слушателей растёт от визита к визиту.
::
