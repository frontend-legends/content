# Производительность в рантайме

Загрузить страницу быстро - половина дела; вторая - **оставаться отзывчивым** после загрузки: плавные анимации, мгновенная реакция на клик. Это про главный поток, бюджет кадра и [INP](/content/security-perfomance/core-web-vitals). Тема прямо связана с тем, почему интерфейс «тормозит».

---

## Главный поток

В браузере JavaScript, рендеринг и обработка событий делят **один главный поток**. Если он занят длинной задачей - всё стоит: страница не отвечает на клики, не анимируется, «зависает».

```
Главный поток: [тяжёлый JS 300мс] → клики и рендер ждут → пользователь видит фриз
```

<b class="text-on-semi-light">Корень runtime-проблем</b> - <span class="text-gray">Почти все «тормоза интерфейса» - это **занятый главный поток**: долгий синхронный код не уступает циклу событий. Решение - делать меньше, разбивать работу и выносить её из главного потока.</span>

---

## Бюджет кадра: 16мс

Для плавности (60fps) браузер должен рисовать кадр каждые **~16мс**. Если работа в кадре превышает бюджет - кадры «пропускаются», анимация дёргается (jank).

```
60fps → 1000мс / 60 ≈ 16.7мс на кадр
Работа > 16мс → пропущенный кадр → рывок
```

---

## Длинные задачи

**Long task** - задача дольше **50мс**, блокирующая отклик на ввод. Их разбивают, **уступая** управление браузеру между кусками:

```js
// разбить тяжёлую обработку, чтобы не блокировать главный поток
for (const chunk of chunks) {
  await scheduler.yield(); // уступить браузеру (или setTimeout / requestIdleCallback)
  process(chunk);
}
```

`scheduler.yield()`/`scheduler.postTask()`, `requestIdleCallback`, разбивка через `setTimeout` - дают браузеру вклиниться и ответить на ввод. Это ключ к хорошему INP.

## Конвейер рендеринга

Изменение на странице проходит этапы:

```
JS → Style → Layout (reflow) → Paint → Composite
```

- **Reflow (layout)** - пересчёт геометрии (позиции, размеры). Дорого.
- **Repaint** - перерисовка пикселей без изменения геометрии. Дешевле.
- **Composite** - сборка слоёв на GPU. Самое дешёвое.

### Анимируй transform и opacity

```css
/* ❌ анимация геометрии → reflow каждый кадр (дорого) */
.box { transition: left 0.3s; }
/* ✅ transform/opacity → только composite на GPU (дёшево, плавно) */
.box { transition: transform 0.3s; }
```

`transform` и `opacity` обрабатываются **на композиторе** (GPU), минуя layout и paint - поэтому плавные. Анимация `left`/`width`/`top` дёргает весь конвейер.

### Layout thrashing

Чередование **чтения** и **записи** layout в цикле заставляет браузер пересчитывать геометрию синхронно много раз:

```js
// ❌ thrashing: читаем layout после каждой записи
items.forEach(el => { el.style.width = el.offsetWidth + 10 + 'px'; });
// ✅ батчим: сначала все чтения, потом все записи
const widths = items.map(el => el.offsetWidth);
items.forEach((el, i) => { el.style.width = widths[i] + 10 + 'px'; });
```

## Debounce и throttle

Частые события (scroll, resize, input, mousemove) с тяжёлым обработчиком заваливают главный поток. Ограничивают частоту:

- **Debounce** - выполнить **после паузы** (поиск: ждём, пока перестали печатать).
- **Throttle** - выполнять **не чаще** раза в N мс (scroll: раз в 100мс).

```js
const onSearch = debounce(search, 300);   // после паузы
const onScroll = throttle(update, 100);    // не чаще 10 раз/сек
```

## Виртуализация

Рендерить тысячи DOM-узлов - дорого. **Виртуализация** рендерит только видимые элементы (+ буфер), переиспользуя узлы при скролле ([производительность React](/content/reactjs/performance)). Решение для длинных списков и таблиц.

---

## Web Workers

Тяжёлые вычисления (парсинг больших данных, обработка изображений) выносят в **отдельный поток** - [Web Worker](/content/additional-topics/web-workers-and-concurrency) - чтобы главный поток оставался свободным для UI.

---

## Меньше лишней работы

- **Мемоизация** дорогих вычислений и предотвращение лишних ререндеров ([React](/content/reactjs/performance)).
- **Утечки памяти** замедляют (растущая куча, GC-паузы) - искать в [DevTools](/content/advanced-tooling/devtools-and-debugging).

---

## content-visibility и will-change

Два CSS-инструмента производительности рендеринга:

- **`content-visibility: auto`** - браузер **пропускает рендеринг** (layout/paint) элементов вне экрана, пока до них не дошёл скролл. Дешёвая «виртуализация из коробки» для длинных страниц без JS.

```css
.section { content-visibility: auto; contain-intrinsic-size: 0 500px; }
/* contain-intrinsic-size задаёт примерный размер, чтобы скроллбар не «прыгал» */
```

- **`will-change: transform`** - подсказка заранее вынести элемент на отдельный слой композитора перед анимацией (плавнее старт). Но злоупотребление вредит: каждый слой ест память - ставить точечно и убирать после.

---

## Память

Утечки памяти - тихий убийца долгоживущих SPA: куча растёт, GC-паузы учащаются, всё тормозит.

<b class="text-on-semi-light">Частые утечки</b> - <span class="text-gray">Забытые слушатели и таймеры (не сняли при unmount), замыкания, удерживающие большие объекты, ссылки на отсоединённые DOM-узлы, бесконечно растущие кеши. Ищут снимками кучи в [DevTools](/content/advanced-tooling/devtools-and-debugging). Решение - убирать подписки в cleanup, ограничивать кеши, использовать `WeakMap`/`WeakRef` для слабых ссылок.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Почему интерфейс «тормозит» и зависает?</b>
<span class="text-gray">Главный поток занят: JS, рендеринг и события делят его, и длинная синхронная задача блокирует всё - нет реакции на клик, дёргается анимация. Решение - меньше работы, разбивать задачи, выносить в worker.</span>

<b class="text-on-semi-light">Что такое бюджет кадра 16мс?</b>
<span class="text-gray">Для 60fps браузер рисует кадр каждые ~16мс. Если работа в кадре превышает бюджет, кадры пропускаются и анимация дёргается (jank).</span>

<b class="text-on-semi-light">Почему анимировать transform/opacity, а не left/width?</b>
<span class="text-gray">`transform` и `opacity` идут на композитор (GPU), минуя layout и paint, - плавно и дёшево. Анимация геометрии (left/width) вызывает reflow каждый кадр - дорого.</span>

<b class="text-on-semi-light">Что такое layout thrashing?</b>
<span class="text-gray">Чередование чтения и записи layout в цикле заставляет браузер синхронно пересчитывать геометрию много раз. Лечится батчингом: сначала все чтения, потом все записи.</span>

<b class="text-on-semi-light">Чем debounce отличается от throttle?</b>
<span class="text-gray">Debounce выполняет после паузы в событиях (поиск по вводу). Throttle - не чаще раза в N мс (обработчик скролла). Оба ограничивают частоту тяжёлых обработчиков.</span>

<b class="text-on-semi-light">Как улучшить INP?</b>
<span class="text-gray">Разбивать длинные задачи (yield), меньше JS в обработчиках, выносить тяжёлое в web workers, оптимизировать ререндеры. INP - про занятость главного потока при взаимодействии.</span>

<b class="text-on-semi-light">Что делает content-visibility: auto?</b>
<span class="text-gray">Браузер пропускает рендеринг (layout/paint) элементов вне экрана до прокрутки к ним - дешёвая виртуализация для длинных страниц без JS. `contain-intrinsic-size` задаёт примерный размер, чтобы скроллбар не прыгал.</span>

<b class="text-on-semi-light">Какие частые причины утечек памяти в SPA?</b>
<span class="text-gray">Забытые слушатели и таймеры (не сняли при unmount), замыкания с большими объектами, ссылки на отсоединённые DOM-узлы, растущие кеши. Ищут снимками кучи в DevTools; лечат cleanup-ом подписок и `WeakMap`/`WeakRef`.</span>
