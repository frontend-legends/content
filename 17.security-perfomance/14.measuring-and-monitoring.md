# Измерение и мониторинг

Производительность начинается и заканчивается **измерением**: найти узкое место, исправить, не дать вернуться, следить за реальными пользователями. Без измерения оптимизация - угадывание. Эта глава закрывает блок производительности и связывает его с мониторингом в проде.

---

## Лабораторные инструменты

Контролируемые замеры для отладки и воспроизводимости:

| Инструмент | Для чего |
|-----------|----------|
| **Lighthouse** | аудит (производительность, доступность, SEO) + оценка и рекомендации |
| **DevTools Performance** | профиль исполнения, flame chart, главный поток, long tasks |
| **WebPageTest** | детальный водопад, filmstrip, реальные устройства и сети |
| **Coverage (DevTools)** | поиск неиспользуемого JS/CSS |

DevTools Performance - главный инструмент для runtime-проблем ([DevTools](/content/advanced-tooling/devtools-and-debugging)): записал сценарий, увидел, что грузило главный поток.

---

## Lab vs field - снова

<b class="text-on-semi-light">Ключевое напоминание</b> - <span class="text-gray">Lab (Lighthouse на твоей машине) хорош для **отладки** - воспроизводимо, можно сравнивать «до/после». Но он не отражает реальных пользователей на слабых телефонах и медленных сетях. **Финальная правда - в поле** ([Core Web Vitals](/content/security-perfomance/core-web-vitals) по CrUX). Оптимизируй по lab, **подтверждай** по field.</span>

---

## Полевые данные (RUM)

**Real User Monitoring** собирает метрики с **настоящих** пользователей:

- **web-vitals** (библиотека) - отправляет LCP/CLS/INP в аналитику.
- **CrUX** - данные реальных пользователей Chrome (основа CWV для SEO).
- Платформы (Sentry Performance, SpeedCurve, аналитика) - дашборды по полевым метрикам.

```js
import { onLCP, onCLS, onINP } from 'web-vitals';
onLCP(send); onCLS(send); onINP(send); // метрики реальных пользователей → аналитика
```

## Бюджеты производительности в CI

Чтобы производительность не деградировала с каждой фичей, её проверяют **автоматически**:

- **Lighthouse CI** - гонять Lighthouse в пайплайне, падать при просадке оценок.
- **size-limit / bundlesize** - лимит на размер бандла; превышение валит сборку.

```
PR увеличил бандл сверх бюджета → CI красный → не смержить
```

Это превращает «надо бы следить за скоростью» в исполняемое правило ([CI](/content/advanced-tooling/ci-cd)) - фитнес-функция производительности.

---

## Мониторинг в проде

Тесты и lab-замеры не покрывают всё разнообразие реального мира. В проде нужны:

- **RUM** - реальная производительность у пользователей.
- **Трекинг ошибок** (Sentry) - JS-ошибки, которых не было в тестах.
- **Synthetic / uptime** - регулярные проверки «жив и быстр ли».

Подробно про observability - в [мониторинге и наблюдаемости](/content/testing-deploying/monitoring-and-observability).

---

## Рабочий цикл

```
Измерь → поставь бюджет → оптимизируй узкое место
   → подтверди измерением → следи в проде (RUM) → повтори
```

<b class="text-on-semi-light">Производительность - процесс, не разовая акция</b> - <span class="text-gray">Сайт «разгоняют» не один раз: каждая фича добавляет вес, каждый релиз может что-то замедлить. Без бюджетов и мониторинга скорость незаметно деградирует. Непрерывное измерение - то, что отличает устойчиво быстрый продукт от «когда-то был быстрым».</span>

---

## Связь обеих половин

> И **безопасность**, и **производительность** - не галочки в чеклисте, а **постоянные дисциплины**. Обе сквозные (касаются всего), обе требуют измерения и мониторинга, обе незаметно деградируют без внимания. Их закладывают с самого начала и поддерживают всё время жизни продукта - это и есть инженерная зрелость, к которой ведёт весь справочник.

## Вопросы на собеседовании

<b class="text-on-semi-light">Какими инструментами измерять производительность?</b>
<span class="text-gray">Lab: Lighthouse (аудит и оценка), DevTools Performance (профиль главного потока), WebPageTest (водопад, реальные устройства), Coverage (неиспользуемый код). Field: web-vitals/CrUX (реальные пользователи).</span>

<b class="text-on-semi-light">Почему нельзя полагаться только на Lighthouse?</b>
<span class="text-gray">Это lab-данные на одной машине - не отражают реальных пользователей на слабых устройствах и сетях. CWV для SEO считаются по полевым данным. Lab для отладки, field для правды.</span>

<b class="text-on-semi-light">Как не дать производительности деградировать?</b>
<span class="text-gray">Бюджеты в CI: Lighthouse CI и size-limit/bundlesize валят сборку при просадке метрик или росте бандла. Плюс мониторинг RUM в проде. Производительность - процесс, а не разовая акция.</span>

<b class="text-on-semi-light">Зачем мониторить производительность в проде?</b>
<span class="text-gray">Lab и тесты не покрывают всё разнообразие устройств и сетей. RUM показывает реальную картину у пользователей и ловит регрессии, которых не видно в синтетике.</span>

<b class="text-on-semi-light">Каков правильный цикл оптимизации?</b>
<span class="text-gray">Измерь → поставь бюджет → оптимизируй узкое место → подтверди измерением → следи в проде → повтори. Не оптимизировать вслепую и подтверждать эффект данными.</span>
