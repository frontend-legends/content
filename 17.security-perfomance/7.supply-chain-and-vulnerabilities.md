# Supply chain и уязвимости

XSS и CSRF - не весь список. Большая часть твоего кода - **чужие зависимости**, а в бандле прячутся секреты; есть clickjacking, prototype pollution и другие классы атак. Эта глава собирает оставшиеся важные угрозы и завершает блок безопасности.

---

## Supply chain

Современное приложение - на 90% **чужой код** из npm. Каждая зависимость (и её транзитивные зависимости) - потенциальный вектор атаки.

| Атака | Суть |
|-------|------|
| **Typosquatting** | пакет с именем, похожим на популярный (`reakt` вместо `react`) |
| **Dependency confusion** | публичный пакет подменяет внутренний с тем же именем |
| **Компрометация мейнтейнера** | угнанный аккаунт публикует вредоносную версию |
| **Вредоносный `postinstall`** | скрипт пакета выполняется при установке |

<b class="text-on-semi-light">Это реальная, растущая угроза</b> - <span class="text-gray">Были громкие инциденты, когда популярный пакет (или его зависимость) внедрял майнер/стилер и попадал в тысячи проектов. Один скомпрометированный пакет в дереве - и его код выполняется в твоём приложении и на машинах разработчиков.</span>

### Защита

- **Lockfile + `npm ci`** - детерминированная установка, без неожиданных версий ([управление пакетами](/content/ecosystem-libs/package-management)).
- **Аудит** - `npm audit`, **Snyk**, **Dependabot/Renovate** (авто-обновления и оповещения об уязвимостях).
- **Минимум зависимостей** - меньше пакетов = меньше поверхность.
- **Provenance и 2FA** при публикации своих пакетов.
- **SCA-инструменты** и **SBOM** (опись компонентов) в зрелых процессах.
- Настороженность к `postinstall`-скриптам чужих пакетов.

## Секреты на клиенте

Повтор важнейшего: **клиентский бандл публичен**. Любой ключ, попавший в сборку (`VITE_*`, `NEXT_PUBLIC_*`), виден в DevTools.

```js
const apiSecret = import.meta.env.VITE_SECRET_KEY; // ❌ опубликованный секрет
```

На клиенте - только **публичные** ключи; приватные - на сервере ([основы](/content/security-perfomance/security-fundamentals)). Дополнительно: **сканировать** репозиторий на утёкшие секреты (gitleaks, GitHub secret scanning) и **ротировать** скомпрометированные.

## Clickjacking

Атакующий встраивает твой сайт в **невидимый iframe** поверх своей страницы и обманом заставляет пользователя кликать по нему («нажми на приз», а под ним - кнопка «удалить аккаунт»).

```
Защита: запретить встраивание в чужой iframe
Content-Security-Policy: frame-ancestors 'none'   (или 'self')
X-Frame-Options: DENY
```

Заголовки [CSP/X-Frame-Options](/content/security-perfomance/csp-and-security-headers) - основная защита.

## Prototype pollution

JS-специфичная уязвимость: загрязнение `Object.prototype` через недоверенные данные. Если код сливает/парсит внешний объект с ключом `__proto__`, можно подменить свойства **всех** объектов.

```js
// недоверенный JSON: { "__proto__": { "isAdmin": true } }
merge(target, untrustedInput);  // ❌ если merge небезопасен
({}).isAdmin; // → true  (загрязнён прототип всех объектов)
```

**Защита:** безопасные библиотеки merge/parse, валидация ключей, `Object.create(null)` для «чистых» словарей, заморозка прототипа. Был источником уязвимостей в популярных пакетах (lodash, minimist).

## Прочие классы

| Угроза | Защита |
|--------|--------|
| **Open redirect** | редирект на URL из параметра без проверки → валидировать целевой адрес |
| **ReDoS** | злая строка вешает «жадную» регулярку → безопасные паттерны, лимиты |
| **Tabnabbing** | `target="_blank"` без `rel="noopener"` → ставить `noopener noreferrer` |
| **Данные в URL/логах** | токены/PII в query или логах → не логировать секреты, не класть в URL |
| **Insecure deserialization** | доверие к сериализованным данным → валидировать на входе |

## Безопасность - это процесс

<b class="text-on-semi-light">Главный вывод</b> - <span class="text-gray">Безопасность не «сделал и забыл». Зависимости устаревают и обнаруживают уязвимости, появляются новые атаки. Нужны **постоянные** обновления, аудит, мониторинг ([наблюдаемость](/content/testing-deploying/monitoring-and-observability)) и культура «не доверяй вводу». Обновление зависимостей - не только про фичи, но и про закрытие дыр.</span>

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое supply chain атака и как защищаться?</b>
<span class="text-gray">Атака через зависимости: typosquatting, dependency confusion, компрометация пакета, вредоносный postinstall. Защита: lockfile + npm ci, аудит (npm audit/Snyk/Dependabot), минимум зависимостей, provenance/2FA, осторожность с postinstall.</span>

<b class="text-on-semi-light">Что такое prototype pollution?</b>
<span class="text-gray">Загрязнение `Object.prototype` через недоверенные данные с ключом `__proto__` (при небезопасном merge/parse), подменяющее свойства всех объектов. Защита: безопасные библиотеки, валидация ключей, `Object.create(null)`.</span>

<b class="text-on-semi-light">Что такое clickjacking и как защититься?</b>
<span class="text-gray">Встраивание сайта в невидимый iframe поверх ловушки, чтобы обманом получить клики. Защита: `frame-ancestors` в CSP или `X-Frame-Options: DENY` - запрет встраивания.</span>

<b class="text-on-semi-light">Почему нельзя хранить секреты в клиентском коде?</b>
<span class="text-gray">Бандл публичен - любой ключ виден в DevTools. На клиенте только публичные ключи; приватные - на сервере. Плюс сканировать репозиторий на утёкшие секреты и ротировать их.</span>

<b class="text-on-semi-light">Зачем rel="noopener" для target="_blank"?</b>
<span class="text-gray">Без него открытая вкладка через `window.opener` может подменить исходную (reverse tabnabbing). `rel="noopener noreferrer"` это закрывает.</span>
