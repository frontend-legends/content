# Цепочка поставок и уязвимости

XSS и CSRF — не весь список. Большая часть кода приложения — чужие зависимости, в бандл может утечь секрет, а кроме инъекций есть clickjacking, загрязнение прототипа и другие классы атак. Здесь — атаки через цепочку поставок и защита от них (lockfile, аудит, SRI), секреты в бандле, clickjacking, prototype pollution, tabnabbing, open redirect и мысль о том, что безопасность — процесс. Это завершающая история блока безопасности. Спрашивают, что такое supply chain атака, prototype pollution и зачем `rel="noopener"`. Глубже — как SRI не даёт выполниться подменённому скрипту и как безопасный merge защищает прототип.

::tldr
- **Приложение на 90% — чужой код:** каждая зависимость и её транзитивные зависимости — вектор атаки (тайпсквоттинг, dependency confusion, компрометация пакета, вредоносный `postinstall`).
- **Защита цепочки:** lockfile и `npm ci` для воспроизводимости, аудит (`npm audit`, Snyk, Dependabot), минимум зависимостей, SRI для сторонних скриптов. В проверке скрипт с неверным хешем браузер не выполнил.
- **Бандл публичен:** любой ключ в сборке виден в DevTools. В проверке сканер секретов нашёл ключи Stripe и AWS в коде; на клиенте — только публичные ключи.
- **Классы атак:** clickjacking (невидимый iframe) закрывают `frame-ancestors`; prototype pollution — безопасным merge; tabnabbing — `rel="noopener"`; open redirect — проверкой целевого адреса.
- **Безопасность — процесс:** зависимости устаревают, появляются новые атаки. Нужны постоянные обновления, аудит и мониторинг.
::

## Цепочка поставок

Современное приложение почти целиком собрано из пакетов npm, и каждый пакет вместе со своими транзитивными зависимостями — потенциальный вектор атаки:

| Атака | Суть |
|-------|------|
| **Typosquatting** | пакет с именем, похожим на популярный (`reakt` вместо `react`) |
| **Dependency confusion** | публичный пакет подменяет внутренний с тем же именем |
| **Компрометация мейнтейнера** | угнанный аккаунт публикует вредоносную версию |
| **Вредоносный `postinstall`** | скрипт пакета выполняется при установке |

Угроза реальна и растёт: были инциденты, когда популярный пакет или его зависимость внедряли майнер или стилер и попадали в тысячи проектов. Один скомпрометированный пакет в дереве — и его код выполняется и в приложении, и на машинах разработчиков.

### Защита

- **lockfile и `npm ci`** — детерминированная установка. В проверке `npm ci` брал точную версию из lockfile (`4.17.21`), а `npm install` в рамках диапазона `^4.17.0` мог подтянуть более новую (`4.18.0`), поэтому в CI используют именно `ci` ([управление пакетами](/content/ecosystem-libs/package-management));
- **аудит** — `npm audit`, Snyk, Dependabot и Renovate оповещают об уязвимостях и обновляют зависимости;
- **минимум зависимостей** — меньше пакетов, меньше поверхность атаки; подозрительные имена ловит и простая проверка на похожесть. В проверке детектор по расстоянию редактирования пометил `reakt` и `expres` как похожие на популярные пакеты;
- **provenance и 2FA** при публикации своих пакетов, SBOM (опись компонентов) в зрелых процессах;
- настороженность к `postinstall`-скриптам чужих пакетов.

### Subresource Integrity

Сторонний скрипт с CDN подключают с хешем содержимого — браузер выполнит его, только если хеш совпал:

```html
<script src="https://cdn.example/lib.js"
        integrity="sha384-…" crossorigin="anonymous"></script>
```

В проверке в Chromium скрипт с верным хешем выполнился, а с неверным — нет. Так подмена файла на CDN или в канале не приведёт к выполнению чужого кода: изменённый скрипт не совпадёт с заявленным хешем и будет заблокирован.

## Секреты в бандле

Повтор важнейшего: клиентский бандл публичен. Любой ключ, попавший в сборку (`VITE_*`, `NEXT_PUBLIC_*`), виден в DevTools:

```js
const apiSecret = import.meta.env.VITE_SECRET_KEY; // опубликованный секрет
```

На клиенте — только публичные ключи, приватные остаются на сервере ([основы безопасности](/content/security-perfomance/security-fundamentals)). В проверке сканер по шаблонам нашёл в коде ключ Stripe (`sk_live_…`) и ключ AWS (`AKIA…`), но не поднял тревогу на публичный ключ карт. Такой сканер (gitleaks, GitHub secret scanning) ставят в репозиторий, а утёкшие ключи ротируют — удаление из истории не отменяет компрометации.

## Классы атак и защита

### Clickjacking

Злоумышленник встраивает чужой сайт в невидимый iframe поверх своей страницы и обманом заставляет кликать по нему («нажми на приз», а под ним — кнопка «удалить аккаунт»). Защита — запретить встраивание заголовками:

```text
Content-Security-Policy: frame-ancestors 'none'   (или 'self')
X-Frame-Options: DENY
```

Подробнее о заголовках — в [CSP и заголовках безопасности](/content/security-perfomance/csp-and-security-headers).

### Prototype pollution

JS-специфичная уязвимость: недоверенный объект с ключом `__proto__` при небезопасном merge подменяет свойства всех объектов. Защита — merge, игнорирующий ключи-ловушки (`__proto__`, `constructor`, `prototype`), или «чистый» словарь без прототипа. В проверке безопасный merge внешнего объекта с `__proto__` не загрязнил `Object.prototype` — `{}.isAdmin` остался `undefined`, — а словарь, созданный через `Object.create(null)`, к такой подмене невосприимчив в принципе:

```js
const DANGEROUS = new Set(['__proto__', 'constructor', 'prototype']);
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (DANGEROUS.has(key)) continue;
    // …рекурсивно для вложенных объектов
  }
}
```

Это был источник уязвимостей в популярных пакетах (lodash, minimist), поэтому merge и парсинг берут из проверенных и обновлённых библиотек.

### Остальные

| Угроза | Защита |
|--------|--------|
| **Tabnabbing** | `target="_blank"` без `rel="noopener"` даёт открытой вкладке доступ к `window.opener` → ставить `noopener noreferrer` |
| **Open redirect** | редирект на адрес из параметра без проверки → разрешать только свой origin или белый список |
| **ReDoS** | злая строка вешает «жадную» регулярку → безопасные паттерны и лимиты |
| **Insecure deserialization** | доверие к сериализованным данным → валидировать на входе |

В проверке детектор небезопасных ссылок пометил `target="_blank"` без `noopener`, а безопасный редирект пропустил только свой путь, отклонив чужой origin и протокол-относительный `//evil.example`.

## Безопасность — это процесс

Безопасность не «сделал и забыл». Зависимости устаревают, в них находят уязвимости, появляются новые классы атак. Нужны постоянные обновления, аудит, [мониторинг](/content/testing-deploying/monitoring-and-observability) и культура «не доверяй вводу». Обновление зависимостей — не только про фичи, но и про закрытие дыр; отложенное обновление — это накопленный риск. Вместе с [основами](/content/security-perfomance/security-fundamentals), [XSS](/content/security-perfomance/xss), [CSRF](/content/security-perfomance/csrf) и заголовками это складывается в постоянную дисциплину, а не разовую проверку перед релизом.

---

## Красные флаги в ответе

- Сторонние скрипты с CDN без SRI.
- `npm install` в CI вместо `npm ci` — невоспроизводимые сборки.
- Секреты в клиентских переменных окружения «потому что минификация».
- Небезопасный merge внешних данных без защиты от `__proto__`.
- `target="_blank"` без `rel="noopener"`.
- Редирект на адрес из параметра без проверки origin.
- «Проверили один раз на релизе» вместо постоянного аудита зависимостей.

## Как спрашивают на собеседовании

::question
Что такое supply chain атака и как защищаться?

#answer
Атака через зависимости: тайпсквоттинг, dependency confusion, компрометация пакета, вредоносный `postinstall`. Один скомпрометированный пакет в дереве выполняет свой код в приложении и у разработчиков. Защита: lockfile и `npm ci`, аудит (`npm audit`, Snyk, Dependabot), минимум зависимостей, SRI для сторонних скриптов, 2FA и provenance при публикации.

#more
В проверке `npm ci` ставил точную версию из lockfile, а SRI не дал выполниться скрипту с неверным хешем. Простая проверка имён на похожесть ловит тайпсквоттинг. `postinstall`-скрипты чужих пакетов выполняются при установке, поэтому их отключают или проверяют в подозрительных зависимостях.
::

::question
Что такое prototype pollution?

#answer
Загрязнение `Object.prototype` через недоверенные данные с ключом `__proto__`: при небезопасном рекурсивном merge или парсинге подменяются свойства всех объектов сразу, например появляется `isAdmin: true`. Защита — merge, игнорирующий `__proto__`, `constructor`, `prototype`, валидация ключей и `Object.create(null)` для словарей.

#more
В проверке безопасный merge не загрязнил прототип, а словарь без прототипа невосприимчив к подмене. Это был источник уязвимостей в lodash и minimist, поэтому merge и парсинг берут из проверенных обновлённых библиотек. Последствия — от обхода проверок до RCE на сервере.
::

::question
Что такое clickjacking и как защититься?

#answer
Встраивание сайта в невидимый iframe поверх ловушки, чтобы обманом получить клики пользователя по настоящим кнопкам. Защита — запрет встраивания заголовками: `Content-Security-Policy: frame-ancestors 'none'` (или `'self'`) и `X-Frame-Options: DENY`.

#more
`frame-ancestors` — современный механизм, `X-Frame-Options` — старый, их ставят вместе для совместимости. Если встраивание нужно для партнёров, в `frame-ancestors` перечисляют разрешённые origin. Чувствительные действия дополнительно защищают подтверждением, чтобы один клик не выполнял необратимое.
::

::question
Почему нельзя хранить секреты в клиентском коде?

#answer
Клиентский бандл публичен — любой ключ виден в DevTools и в исходниках сборки, даже после минификации. На клиенте держат только публичные ключи; приватные остаются на сервере, который и ходит к защищённым API.

#more
В проверке сканер нашёл в коде ключи Stripe и AWS, не тронув публичный ключ карт. Такой сканер ставят в репозиторий (gitleaks, GitHub secret scanning), а утёкший ключ ротируют — удаление из истории git не отменяет того, что его уже могли скопировать.
::

::question
Зачем rel="noopener" для target="_blank"?

#answer
Без него новая вкладка через `window.opener` получает ссылку на открывшую страницу и может подменить её адрес (reverse tabnabbing) — например, увести на фишинговую копию. `rel="noopener noreferrer"` разрывает эту связь и заодно не передаёт `Referer`.

#more
В современных браузерах `target="_blank"` подразумевает `noopener` по умолчанию, но полагаться на это не стоит — старые браузеры и явные случаи остаются. В проверке детектор пометил ссылку с `target="_blank"` без `noopener`. Это дешёвая защита, которую ставят на все внешние ссылки.
::

## Практика

::practice{title="Подключение виджета с чужого CDN"}
На страницу добавляют скрипт аналитики со стороннего CDN. Безопасность беспокоит: если CDN скомпрометируют или подменят файл, чужой код выполнится у всех пользователей.

```html
<script src="https://cdn.partner.example/widget.js"></script>
```

#solution
Подключают с Subresource Integrity — хешем содержимого, — чтобы браузер выполнил скрипт только при совпадении:

```html
<script src="https://cdn.partner.example/widget.js"
        integrity="sha384-{хеш содержимого}" crossorigin="anonymous"></script>
```

В проверке скрипт с верным хешем выполнился, а с неверным браузер заблокировал. Хеш считают от конкретной версии файла; при обновлении виджета его обновляют (поэтому SRI удобнее для версионированных URL, чем для «последней» версии). Дополнительно сторонние скрипты ограничивает CSP через `script-src`, а критичные лучше не грузить с чужого CDN вовсе, а проксировать через свою сборку.
::

::practice{title="Слияние настроек из внешнего источника загрязняет объекты"}
Приложение сливает настройки пользователя (приходят JSON-ом с сервера) с дефолтами своим рекурсивным merge. После некоторых ответов у всех объектов в приложении появляется лишнее свойство.

#solution
Это prototype pollution: во входном JSON есть ключ `__proto__`, и небезопасный merge записывает в прототип. Защита — пропускать ключи-ловушки и/или использовать словарь без прототипа:

```js
const DANGEROUS = new Set(['__proto__', 'constructor', 'prototype']);
function safeMerge(target, source) {
  for (const key of Object.keys(source)) {
    if (DANGEROUS.has(key)) continue;
    if (source[key] && typeof source[key] === 'object') { target[key] ??= {}; safeMerge(target[key], source[key]); }
    else target[key] = source[key];
  }
  return target;
}
```

В проверке такой merge внешнего объекта с `__proto__` не загрязнил `Object.prototype`. Ещё надёжнее — валидировать вход схемой (zod) и парсить в `Object.create(null)`. Свой merge вообще стоит заменить проверенной обновлённой библиотекой: именно на этой уязвимости ловили lodash и minimist.
::
