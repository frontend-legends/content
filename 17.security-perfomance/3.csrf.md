# CSRF

Подделка межсайтового запроса — когда чужой сайт заставляет браузер жертвы отправить нежелательный запрос туда, где она авторизована. Атака держится на том, что браузер сам прикладывает куки к запросам на их домен. Здесь — механика, атрибут SameSite как главная современная защита, CSRF-токены (синхронизирующий и double-submit), кастомные заголовки, проверка Origin, отличие от XSS и связь с хранением токена. Спрашивают, как работает CSRF, как защититься и чем он отличается от XSS. Глубже — почему SameSite=Lax блокирует классическую атаку и почему API с токеном в заголовке к ней не уязвим.

::tldr
- **CSRF запускает действие, а не читает ответ:** браузер автоматически прикладывает куки к запросу на их домен, даже если запрос инициирован с чужого сайта. Если сервер верит только куке — действие выполняется от имени жертвы.
- **Главная защита — SameSite-куки:** в проверке правило `Lax` (умолчание браузеров) не отдаёт куку при фоновом межсайтовом POST, но пускает обычный переход по ссылке. `Strict` строже, `None` снова открывает запрос.
- **CSRF-токен подтверждает намерение:** сервер выдаёт непредсказуемый токен, запрос обязан его вернуть. В проверке запрос без токена и с неверным токеном отклонён, с верным — принят.
- **Другие слои:** double-submit cookie без серверного хранения, требование кастомного заголовка (чужой сайт не поставит его без CORS), проверка Origin.
- **XSS сильнее и обходит защиту от CSRF:** скрипт в контексте сайта прочитает токен. Защита от CSRF бессмысленна без защиты от XSS.
::

---

## Как работает

CSRF (cross-site request forgery) держится на одном свойстве куки: браузер прикладывает её ко всякому запросу на её домен, независимо от того, кто запрос инициировал. Это называется ambient authority — «фоновая власть» куки.

Классический сценарий: жертва авторизована на `bank.example` (есть кука сессии), заходит на чужой сайт, и тот в фоне отправляет POST на `bank.example/transfer`. Браузер сам прикладывает куку банка, и если сервер рассуждает «есть валидная кука — значит, это легитимный пользователь», перевод выполняется от имени жертвы. Важно: атакующий не видит ответ — этому мешает [Same-Origin Policy](/content/security-perfomance/cors-and-same-origin), — он лишь запускает действие вслепую.

Отсюда и защита: сервер не должен считать наличие куки достаточным доказательством намерения пользователя.

## SameSite-куки

Главная современная защита — атрибут `SameSite`, который ограничивает отправку куки межсайтовыми запросами:

```text
Set-Cookie: session=…; SameSite=Lax; Secure; HttpOnly
```

В проверке правило SameSite реализовано как функция от контекста запроса, и видно, что отдаётся кука, а что нет:

| Значение | Поведение |
|----------|-----------|
| `Strict` | не отправляется ни с каких чужих сайтов |
| `Lax` (умолчание) | только при навигации верхнего уровня (переход по ссылке, GET), не при фоновых запросах |
| `None` | отправляется всегда, требует `Secure` |

В проверке `Lax` не отдал куку при фоновом межсайтовом POST — именно это и есть классический CSRF, — но отдал при переходе по ссылке. `Strict` не отдал куку даже при переходе со стороны (поэтому ссылка на залогиненную страницу открывается разлогиненной), а `None` отдал всегда. Современные браузеры по умолчанию ставят `Lax`, что само по себе блокирует классическую атаку. Но полагаться только на умолчание нельзя: для `SameSite=None` (например, встраивание в iframe) и старых клиентов нужен явный второй слой.

## CSRF-токены

### Синхронизирующий токен

Сервер выдаёт уникальный непредсказуемый токен, который встраивается в форму или запрос. Чужой сайт не может его узнать: прочитать страницу с токеном ему не даёт Same-Origin Policy. В проверке на настоящем сервере легитимный запрос с полученным токеном прошёл (204), а запрос без токена и с неверным токеном был отклонён (403):

```text
Сервер → токен в форме → запрос возвращает токен → сервер сверяет
Подделанный запрос токена не знает → отклонён
```

Токен сверяют сравнением с защитой от тайминга, а генерируют из криптографически случайных байтов: в проверке тысяча токенов не дала ни одного совпадения, длина 64 hex-символа не оставляет шанса перебору.

### Double-submit cookie

Токен кладут и в куку, и в заголовок или поле запроса; сервер сверяет, что они совпадают, и ничего не хранит у себя. Свой код читает куку и дублирует значение в заголовок, а чужой сайт куку прочитать не может — значения не совпадут. В проверке совпадающие значения приняты, различные — отклонены.

## Другие слои

- **Кастомный заголовок.** Для API требуют заголовок вроде `X-Requested-With`. Браузер не позволяет чужому сайту поставить произвольный заголовок в кросс-доменном запросе без разрешения [CORS](/content/security-perfomance/cors-and-same-origin), поэтому подделать его нельзя. В проверке запрос без заголовка отклонён.
- **Проверка Origin.** Сервер сверяет заголовок `Origin` со своим источником. В проверке запрос с `Origin: https://evil.example` отклонён, со своим — принят. `Origin` браузер проставляет сам и подделать из скрипта его нельзя.

Эти слои комбинируют: SameSite закрывает большинство случаев на уровне браузера, токен или проверка Origin — на уровне сервера.

## XSS и CSRF — не путать

| | XSS | CSRF |
|--|-----|------|
| Суть | выполнить скрипт в браузере жертвы | подделать запрос от её имени |
| Читает ответ | да, полный контроль | нет, только запускает действие |
| Держится на | внедрении кода | автоотправке куки |
| Защита | экранирование, CSP, санитизация | SameSite, токены, проверка Origin |

Важная связь: XSS сильнее и обходит защиту от CSRF. Если на сайте есть XSS, скрипт выполняется в контексте сайта, читает CSRF-токен из страницы и отправляет валидный запрос. Поэтому защита от CSRF без защиты от XSS бессмысленна — XSS называют «царём» уязвимостей.

---

## Связь с хранением токена

CSRF бьёт по кукам, которые отправляются автоматически. API, использующие токен в заголовке `Authorization` (из памяти или `localStorage`), к классическому CSRF не уязвимы: такой токен не прикладывается сам, его надо явно подставить, а чужой сайт этого не сделает. Но за это платят уязвимостью к [XSS](/content/security-perfomance/xss) — токен доступен скрипту. Это центральный компромисс хранения, он разобран в [аутентификации и токенах](/content/security-perfomance/authentication-and-tokens).

## Красные флаги в ответе

- Сервер считает наличие куки достаточным доказательством намерения пользователя.
- «SameSite=Lax по умолчанию — значит, CSRF больше нет»: `None`, iframe и старые клиенты остаются.
- CSRF-токен в куке без второго канала (не double-submit) — отправится автоматически, защиты нет.
- Токен предсказуемый (счётчик, время) вместо криптослучайного.
- Защита от CSRF есть, а от XSS нет — скрипт прочитает токен и обойдёт её.
- Путают CSRF и XSS: думают, что CSRF читает ответ.

## Как спрашивают на собеседовании

::question
Что такое CSRF и как он работает?

#answer
Подделка межсайтового запроса: чужой сайт заставляет браузер жертвы отправить запрос туда, где она авторизована. Браузер автоматически прикладывает куку к запросу на её домен, и если сервер доверяет только куке, действие выполняется от имени жертвы. Ответ атакующий не видит — он лишь запускает действие.

#more
Основа атаки — ambient authority куки: она идёт с запросом независимо от инициатора. Поэтому сервер не должен считать наличие куки доказательством намерения: нужен второй сигнал — SameSite, токен или проверка Origin. Читать ответ мешает Same-Origin Policy, так что CSRF опасен для действий, а не для чтения данных.
::

::question
Как защититься от CSRF?

#answer
SameSite-куки — главная современная защита (умолчание `Lax` блокирует фоновые межсайтовые POST). Плюс CSRF-токены: синхронизирующий (сервер хранит и сверяет) или double-submit (токен в куке и заголовке совпадают). Для API — требование кастомного заголовка и проверка `Origin`.

#more
В проверке `Lax` не отдал куку при фоновом POST, а сервер отклонил запрос без токена, с неверным токеном и с чужим `Origin`. Слои комбинируют: SameSite закрывает браузерный уровень, токен и Origin — серверный. Токен должен быть криптослучайным и сверяться безопасным сравнением.
::

::question
Чем CSRF отличается от XSS?

#answer
XSS выполняет чужой скрипт в браузере жертвы — полный контроль, чтение ответа. CSRF лишь подделывает запрос, не видя ответа, эксплуатируя автоотправку куки. Защита тоже разная: от XSS — экранирование и CSP, от CSRF — SameSite и токены.

#more
XSS сильнее и обходит защиту от CSRF: скрипт в контексте сайта прочитает CSRF-токен и отправит валидный запрос. Поэтому защита от CSRF без защиты от XSS бессмысленна. CSRF опасен именно потому, что не требует выполнения кода на сайте — достаточно заставить браузер отправить запрос.
::

::question
Почему работает SameSite=Lax?

#answer
Кука с `SameSite=Lax` не отправляется при фоновых межсайтовых запросах — скрытый POST с чужого сайта её не получит, — а только при навигации верхнего уровня, то есть переходе по ссылке. Это блокирует классический CSRF прямо на уровне браузера, без изменений на сервере.

#more
В проверке `Lax` отдал куку при переходе по ссылке и не отдал при фоновом POST. `Strict` строже — не отдаёт куку даже при переходе со стороны, из-за чего ссылка на залогиненную страницу открывается разлогиненной. `None` отправляет всегда и требует `Secure`; для него нужен отдельный слой защиты.
::

::question
Уязвим ли к CSRF API с токеном в заголовке Authorization?

#answer
К классическому CSRF — нет: токен из памяти или `localStorage` не отправляется автоматически, его надо явно подставить в заголовок, а чужой сайт этого сделать не может. Куки с ambient authority здесь не участвуют.

#more
За это платят уязвимостью к XSS: токен доступен скрипту, и внедрённый код его прочитает. Это компромисс хранения — куки уязвимы к CSRF, но с HttpOnly недоступны скрипту; заголовочные токены неуязвимы к CSRF, но доступны при XSS. Выбор разбирается в аутентификации и токенах.
::

## Практика

::practice{title="Форма смены email уязвима к подделке запроса"}
Смена email делается POST-запросом, а сервер проверяет только куку сессии:

```js
app.post('/account/email', (req, res) => {
  if (!req.session) return res.sendStatus(401);
  updateEmail(req.session.userId, req.body.email); // доверяем куке
  res.sendStatus(204);
});
```

Чужой сайт может в фоне отправить такой POST, и браузер приложит куку.

#solution
Наличие куки — не доказательство намерения. Добавляют два слоя. Куку делают `SameSite=Lax` (или `Strict` для чувствительных действий), чтобы фоновый межсайтовый POST её не получил, и требуют CSRF-токен:

```js
app.post('/account/email', (req, res) => {
  if (!req.session) return res.sendStatus(401);
  if (req.get('origin') && req.get('origin') !== SELF) return res.sendStatus(403);
  if (!safeEqual(req.body.csrfToken, req.session.csrfToken)) return res.sendStatus(403);
  updateEmail(req.session.userId, req.body.email);
  res.sendStatus(204);
});
```

В проверке такой сервер пропустил запрос с верным токеном и своим `Origin` и отклонил запрос без токена, с неверным токеном и с чужим `Origin`. Токен берут криптослучайный и сверяют безопасным сравнением. И помнят: всё это держится, только если на сайте нет XSS.
::

::practice{title="Отдельный фронтенд и API: нужен ли CSRF-токен"}
SPA общается с API на другом поддомене, авторизация — токен в заголовке `Authorization`, который кладётся из памяти. Команда спорит, нужна ли защита от CSRF.

#solution
К классическому CSRF такой подход не уязвим: токен в заголовке не отправляется браузером автоматически, его подставляет сам код приложения, а чужой сайт этого сделать не может — куки с ambient authority здесь не участвуют. CSRF-токен не нужен.

Но если авторизация хоть где-то идёт через куку (например, refresh-токен в HttpOnly-куке на `/auth/refresh`), этот эндпоинт уязвим к CSRF и его защищают — `SameSite` и проверкой `Origin`:

```js
// запросы данных неуязвимы: токен кладёт сам код, браузер его не прикладывает
api.interceptors.request.use((cfg) => { cfg.headers.Authorization = `Bearer ${getAccessToken()}`; return cfg; });
// но refresh через куку защищают явно
app.post('/auth/refresh', (req, res) => {
  if (req.get('origin') !== SELF) return res.sendStatus(403); // кука SameSite=Strict + проверка Origin
  // …
});
```
 И главное смещается на [XSS](/content/security-perfomance/xss): токен в памяти доступен скрипту, поэтому в проверке защиты именно от XSS (экранирование, CSP, санитизация) здесь важнее. Выбор хранения — компромисс, он разобран в [аутентификации и токенах](/content/security-perfomance/authentication-and-tokens).
::
