# CSRF

**Cross-Site Request Forgery** - атака, заставляющая браузер жертвы отправить **нежелательный запрос** на сайт, где она авторизована. Работает на «фоновом доверии» куки, которые браузер шлёт автоматически. Понимать механику и отличие от XSS - классический вопрос.

---

## Как работает

Ключ - в том, что браузер **автоматически прикладывает куки** к запросам на сайт, **даже если запрос инициирован с чужого сайта**.

```
1. Жертва залогинена на bank.com (есть кука сессии).
2. Жертва заходит на evil.com.
3. evil.com тайно шлёт запрос на bank.com/transfer.
4. Браузер АВТОМАТИЧЕСКИ прикладывает куку bank.com.
5. Если bank.com доверяет только куке → перевод выполнен от имени жертвы.
```

```html
<!-- на evil.com: форма, отправляющая запрос на банк -->
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script> <!-- авто-отправка -->
```

<b class="text-on-semi-light">Почему это работает</b> - <span class="text-gray">Куки обладают **ambient authority** - прикладываются автоматически ко всем запросам на их домен, независимо от того, **кто** инициировал запрос. Если сервер считает «есть валидная кука → это легитимный пользователь», атакующий с чужого сайта подделывает действие. CSRF не **читает** ответ (этому мешает [Same-Origin Policy](/content/security-perfomance/cors-and-same-origin)) - он лишь **запускает** действие.</span>

## Защита

### SameSite-куки

Главная современная защита. Атрибут `SameSite` ограничивает отправку куки **межсайтовыми** запросами:

```
Set-Cookie: session=...; SameSite=Lax; Secure; HttpOnly
```

| Значение | Поведение |
|----------|-----------|
| `Strict` | кука **не** шлётся ни с каких чужих сайтов |
| `Lax` (дефолт) | шлётся только при навигации верхнего уровня (переход по ссылке), не при фоновых POST |
| `None` | шлётся всегда (нужен `Secure`) |

> Современные браузеры по умолчанию ставят `SameSite=Lax`, что само по себе блокирует классический CSRF (фоновый POST с чужого сайта куку не получит). Это сильно снизило актуальность атаки - но полагаться только на дефолт нельзя.

### CSRF-токены

**Synchronizer token pattern**: сервер выдаёт уникальный непредсказуемый токен, который встраивается в форму/запрос. Атакующий **не может его узнать** (его сайт не может прочитать страницу/токен из-за SOP).

```
Сервер → форма с скрытым токеном → запрос включает токен → сервер сверяет
Атакующий не знает токен → подделанный запрос отклонён
```

### Double-submit cookie

Токен кладётся и в куку, и в заголовок/поле формы; сервер сверяет, что они совпадают. Не требует серверного хранения токена.

### Кастомные заголовки

Для API: требовать кастомный заголовок (например, `X-Requested-With`). Браузер **не позволяет** чужому сайту ставить произвольные заголовки в кросс-доменном запросе без CORS-разрешения, поэтому подделать его нельзя.

### Проверка Origin/Referer

Сервер проверяет, что запрос пришёл со своего источника.

## XSS vs CSRF

Частый вопрос - не путать:

| | XSS | CSRF |
|--|-----|------|
| Суть | **выполнить скрипт** в браузере жертвы | **подделать запрос** от имени жертвы |
| Читает ответ | да (полный контроль) | нет (только запускает действие) |
| Основа | внедрение кода | автоотправка куки |
| Защита | экранирование, CSP, санитизация | SameSite, CSRF-токены |

<b class="text-on-semi-light">Важная связь</b> - <span class="text-gray">XSS **сильнее** CSRF и **обходит** его защиту: если на сайте есть XSS, скрипт выполняется в контексте сайта, может прочитать CSRF-токен и отправить валидный запрос. Поэтому защита от CSRF бессмысленна без защиты от XSS - XSS «царь» уязвимостей.</span>

## Связь с хранением токена

CSRF бьёт по **кукам** (автоотправляются). API, использующие токен в заголовке `Authorization` (из памяти/localStorage), к классическому CSRF **не уязвимы** - токен не отправляется автоматически. Но они уязвимее к [XSS](/content/security-perfomance/xss) (токен доступен JS). Это центральный компромисс хранения - разбираем в [аутентификации](/content/security-perfomance/authentication-and-tokens).

## Вопросы на собеседовании

<b class="text-on-semi-light">Что такое CSRF и как работает?</b>
<span class="text-gray">Подделка запроса: чужой сайт заставляет браузер жертвы отправить запрос на сайт, где она авторизована. Браузер автоматически прикладывает куки, и если сервер доверяет только куке - действие выполняется от имени жертвы.</span>

<b class="text-on-semi-light">Как защититься от CSRF?</b>
<span class="text-gray">`SameSite`-куки (главная современная защита, дефолт Lax блокирует фоновые межсайтовые POST), CSRF-токены (synchronizer/double-submit), кастомные заголовки, проверка Origin/Referer.</span>

<b class="text-on-semi-light">Чем CSRF отличается от XSS?</b>
<span class="text-gray">XSS выполняет скрипт в браузере (полный контроль, читает ответ). CSRF лишь подделывает запрос (не читает ответ), эксплуатируя автоотправку куки. XSS сильнее и обходит защиту от CSRF.</span>

<b class="text-on-semi-light">Почему работает SameSite=Lax?</b>
<span class="text-gray">Кука с `SameSite=Lax` не отправляется при фоновых межсайтовых запросах (скрытый POST с чужого сайта), только при навигации верхнего уровня. Это блокирует классический CSRF на уровне браузера.</span>

<b class="text-on-semi-light">Уязвим ли к CSRF API с токеном в заголовке Authorization?</b>
<span class="text-gray">К классическому CSRF - нет: токен из памяти/localStorage не отправляется автоматически, его надо явно подставить. Но такой подход уязвимее к XSS, который может прочитать токен. Это компромисс хранения.</span>
