# Стратегии кеширования

Самый быстрый запрос — тот, который не сделан. Кеширование — повторное использование уже полученного — один из мощнейших рычагов производительности. Здесь — слои кеша от памяти приложения до CDN, валидация HTTP-кеша через ETag, стратегии Service Worker (cache-first, network-first, stale-while-revalidate), предзагрузка, инвалидация через хеш в имени ассета и кеш состояния приложения. Спрашивают, какие бывают слои и стратегии и что такое stale-while-revalidate. Глубже — как ETag экономит трафик ответом 304, как изменение кода меняет имя файла и почему запрос останавливается на первом свежем слое.

::tldr
- **Кеш многослойный:** память приложения → Service Worker → HTTP-кеш браузера → CDN → сервер. Запрос идёт сверху вниз и останавливается на первом слое со свежими данными; чем выше попал, тем быстрее.
- **Валидация экономит трафик:** с ETag браузер спрашивает «изменилось?», и сервер отвечает 304 без тела. В проверке сервер отдал тело один раз, второй ответ был только заголовком.
- **Стратегии Service Worker:** cache-first для статики, network-first для свежих данных с откатом в кеш офлайн, stale-while-revalidate — кеш сразу и обновление в фоне.
- **Инвалидация через хеш в имени:** изменился код — изменилось имя файла, браузер скачивает новый, а `index.html` остаётся `no-cache` и указывает на актуальные файлы.
- **Самый верхний слой — кеш состояния приложения:** React Query и SWR убирают повторные запросы в рамках сессии.
::

---

## Слои кеширования

Прежде чем выбирать стратегию, важно видеть, что кешей несколько и они стоят друг над другом:

```text
Память приложения (React Query, SWR)
   ↓
Service Worker (Cache API, программируемый)
   ↓
HTTP-кеш браузера (Cache-Control, ETag)
   ↓
CDN / edge
   ↓
Сервер (origin)
```

Запрос идёт сверху вниз и останавливается на первом слое, где есть свежие данные. В проверке это смоделировано цепочкой слоёв: запрос ленты, которая лежит в кеше Service Worker, туда и остановился, не дойдя до HTTP-кеша и :term[CDN]{def="сеть серверов по миру, которая отдаёт файлы с ближайшего к пользователю"}; запрос логотипа, которого выше нет, дошёл до HTTP-кеша; запрос профиля, которого нет нигде, ушёл на сервер. Чем выше остановился запрос, тем он быстрее, поэтому стратегия — не один кеш, а согласованная работа слоёв.

## HTTP-кеш браузера

Браузер кеширует ответы по заголовкам сервера. Механика заголовков подробно разобрана в [кешировании HTTP](/content/network-api/caching); здесь важна общая картина:

- **`Cache-Control: max-age=N`** — хранить N секунд без перепроверки; `immutable` — не перепроверять вовсе; `no-cache` — хранить, но каждый раз валидировать; `no-store` — не хранить.
- **Валидация** через `ETag` или `Last-Modified` — спросить сервер «изменилось ли?». Если нет, сервер отвечает `304 Not Modified` без тела.

В проверке на настоящем сервере первый запрос получил тело и :term[ETag]{def="заголовок HTTP с отпечатком версии ресурса, по которому браузер проверяет кеш"}, а второй, отправленный с этим ETag в `If-None-Match`, вернулся как 304 с пустым телом — сервер отдал содержимое ровно один раз. Так браузер подтверждает свежесть кеша, не перекачивая данные.

### Паттерн для ассетов и HTML

Хешированные бандлы (`app.4f3a2b1c.js`) отдают с `Cache-Control: immutable, max-age=31536000` — имя меняется при изменении кода, поэтому файл можно кешировать на год. А `index.html` отдают с `no-cache`, чтобы он всегда был свежим и указывал на новые бандлы. Так пользователь берёт неизменные ассеты из кеша мгновенно и сразу видит новый деплой. Деплойная сторона этого — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching).

## Service Worker

Service Worker перехватывает сетевые запросы и управляет кешем программно через Cache API — это основа PWA и работы офлайн ([кроссплатформа](/content/additional-topics/cross-platform)). В проверке стратегии реализованы как функции над мок-кешем и мок-сетью, и видно, чем они отличаются:

| Стратегия | Логика | Когда |
|-----------|--------|-------|
| **cache-first** | сначала кеш, сеть если нет | статика, шрифты, иконки |
| **network-first** | сначала сеть, кеш если офлайн | свежие данные, API |
| **stale-while-revalidate** | кеш сразу, обновление в фоне | баланс скорости и свежести |
| **cache-only** | только кеш | заведомо закешированное |
| **network-only** | только сеть | некешируемое (платежи) |

- **cache-first** в проверке отдал логотип из кеша, ни разу не обратившись к сети, а отсутствующий шрифт взял из сети и положил в кеш.
- **network-first** онлайн вернул свежий ответ и обновил кеш, а в режиме офлайн, когда сеть бросила ошибку, отдал старое значение из кеша.
- **stale-while-revalidate** вернул кеш сразу, в фоне обновил его, и следующий запрос получил уже свежие данные:

```js
function staleWhileRevalidate(cache, network, key) {
  const cached = cache.get(key);
  const fresh = network(key).then((r) => { cache.set(key, r); return r; }).catch(() => cached);
  return cached ?? fresh; // есть кеш — отдать его мгновенно, обновление идёт в фоне
}
```

Выбор стратегии — это выбор между скоростью и свежестью: иконкам свежесть не нужна (cache-first), балансу ленты подходит stale-while-revalidate, а баланс счёта всегда берут из сети (network-only).

## Предзагрузка

Кеш можно заполнить заранее, предугадывая следующий шаг: подгрузить вероятную следующую страницу при наведении на ссылку или в простое, спекулятивно загрузить видимые маршруты в :term[SPA]{def="одностраничное приложение: страница загружается раз, а экраны меняет JavaScript"}. К моменту перехода данные уже в кеше, и переход мгновенный. Это та же идея, что пререндеринг в [производительности загрузки](/content/security-perfomance/loading-performance), но на уровне данных.

## Инвалидация

«Инвалидация кеша — одна из двух трудных задач в программировании». Способы:

- **хеш содержимого в имени** — новый контент даёт новое имя, старое просто перестаёт запрашиваться. В проверке один и тот же код дал одно и то же имя `app.<хеш>.js`, а изменённый — новое; политику кеша при этом выбирают по имени: хешированный файл — `immutable` на год, `index.html` — `no-cache`;
- **версионирование и purge на CDN** при деплое для контента, который нельзя переименовать;
- **инвалидация данных** — пометить кеш устаревшим после мутации, чтобы следующий запрос перечитал ([загрузка данных](/content/reactjs/data-fetching)).

## Кеш состояния приложения

Самый верхний слой — кеш серверного состояния в памяти (React Query, :term[SWR]{def="библиотека загрузки данных для React от Vercel: кеш и повторная проверка в фоне"}): дедупликация одинаковых запросов, фоновое обновление, инвалидация после мутаций ([загрузка данных](/content/reactjs/data-fetching)). Он убирает повторные запросы в рамках сессии ещё до того, как дело дойдёт до сети и HTTP-кеша, и поэтому стоит на вершине цепочки слоёв.

---

## Красные флаги в ответе

- Один кеш «в голове» вместо понимания слоёв и их порядка.
- `Cache-Control` путают с валидацией: `no-cache` — это «хранить и проверять», а не «не хранить».
- Хешированные ассеты с коротким `max-age` или `index.html` с годовым кешем — пользователь не видит деплой.
- network-first без отката в кеш — приложение не работает офлайн.
- stale-while-revalidate там, где нужна гарантированная свежесть (баланс, права).
- «Инвалидацию решим вручную» вместо хеша в имени файла.

## Как спрашивают на собеседовании

::question
Какие есть слои кеширования во фронтенде?

#answer
Память приложения (React Query, SWR), Service Worker (Cache API), HTTP-кеш браузера (Cache-Control, ETag), CDN или edge, сервер. Запрос идёт сверху вниз и останавливается на первом слое со свежими данными — чем выше, тем быстрее.

#more
В проверке запрос останавливался на самом высоком слое, где лежали данные: лента — в Service Worker, логотип — в HTTP-кеше, профиль, которого нигде не было, уходил на сервер. Слои согласуют: бессмысленно держать годовой HTTP-кеш и при этом каждый раз ходить в сеть из приложения.
::

::question
Какие стратегии кеширования в Service Worker?

#answer
Cache-first (кеш, сеть если нет) — для статики и шрифтов; network-first (сеть, кеш если офлайн) — для свежих данных; stale-while-revalidate (кеш сразу, обновление в фоне) — баланс; cache-only и network-only — для крайних случаев. Выбор — между скоростью и свежестью.

#more
В проверке cache-first отдал логотип без обращения к сети, network-first в офлайне вернул старое из кеша, а stale-while-revalidate отдал кеш сразу и обновил его в фоне. Для некешируемого (платежи) — network-only, для заведомо закешированного оболочки приложения — cache-only.
::

::question
Как правильно кешировать ассеты и HTML?

#answer
Хешированные бандлы — `immutable` на год: имя меняется при изменении кода, поэтому старый файл можно кешировать надолго. `index.html` — `no-cache`: он всегда свежий и указывает на актуальные бандлы. Так ассеты берутся из кеша мгновенно, а новый деплой виден сразу.

#more
В проверке политику выбирали по имени файла: файл с хешем получал годовой `immutable`, `index.html` — `no-cache`. Ошибка в обе стороны ломает всё: короткий кеш на хешированных ассетах теряет выигрыш, а годовой кеш на `index.html` прячет деплой от пользователей.
::

::question
Что такое stale-while-revalidate?

#answer
Отдать данные из кеша сразу, даже устаревшие, а в фоне перезапросить и обновить кеш к следующему разу. Пользователь получает мгновенный ответ без ожидания сети, а данные подтягиваются незаметно. Работает на CDN, в Service Worker и в библиотеках загрузки данных.

#more
В проверке первый запрос вернул старое значение из кеша, фоновое обновление заменило его, и второй запрос получил свежее. Подходит там, где небольшая задержка свежести приемлема — лента, профиль, — и не подходит для данных, где устаревшее значение опасно: баланс, остаток на складе, права.
::

::question
Как решается инвалидация кеша для ассетов?

#answer
Хеш содержимого в имени файла: изменился код — изменилось имя — браузер запрашивает новый файл, а старое имя просто перестаёт использоваться. Это cache busting без ручной чистки кеша.

#more
В проверке одинаковый код давал одинаковое имя (берётся из кеша), изменённый — новое. Поэтому хешированные файлы безопасно кешировать на год. Для контента, который нельзя переименовать, используют purge на CDN при деплое, а для данных — инвалидацию кеша после мутаций.
::

## Практика

::practice{title="После деплоя пользователи видят старую версию"}
После выкладки часть пользователей несколько часов работает со старым кодом, пока не нажмёт «обновить» с очисткой кеша. Сейчас всё отдаётся одинаково:

```text
Cache-Control: max-age=86400   # и для index.html, и для app.js
```

#solution
`index.html` закеширован на сутки, поэтому браузер не видит, что появились новые бандлы. Политику разделяют по типу файла. Бандлам дают хеш в имени и годовой неизменяемый кеш, а `index.html` делают всегда свежим:

```text
# app.4f3a2b1c.js — имя меняется при изменении кода
Cache-Control: immutable, max-age=31536000
# index.html — указывает на актуальные бандлы
Cache-Control: no-cache
```

В проверке имя `app.<хеш>.js` менялось ровно при изменении кода, а политику выбирали по имени файла. Теперь браузер при каждом заходе перепроверяет маленький `index.html` (через ETag это дёшево — 304 без тела), получает ссылки на новые хешированные бандлы и грузит только изменившиеся. Сборщик проставляет хеши сам ([CDN и кеширование](/content/testing-deploying/cdn-and-caching)).
::

::practice{title="Лента то мгновенная, то висит на спиннере"}
Лента новостей в PWA иногда открывается сразу, иногда показывает спиннер на всю загрузку. Сейчас Service Worker всегда идёт в сеть и только потом рисует. Хочется мгновенного показа, но со свежими данными.

#solution
Это выбор стратегии. Network-first всегда ждёт сеть — отсюда спиннер; cache-first отдаст мгновенно, но может застрять на старом. Для ленты подходит stale-while-revalidate: кеш сразу, обновление в фоне:

```js
self.addEventListener('fetch', (e) => {
  if (!e.request.url.includes('/feed')) return;
  e.respondWith((async () => {
    const cache = await caches.open('feed');
    const cached = await cache.match(e.request);
    const fresh = fetch(e.request).then((r) => { cache.put(e.request, r.clone()); return r; });
    return cached || fresh; // есть кеш — мгновенно, иначе ждём сеть
  })());
});
```

В проверке такая функция отдала кеш сразу и обновила его в фоне, а следующий запрос получил свежее. Для первого захода, когда кеша ещё нет, остаётся ожидание сети — это нормально. А вот для баланса счёта оставляют network-only: там устаревшее значение недопустимо.
::
