# Стратегии кеширования

Самый быстрый запрос - тот, который **не сделан**. Кеширование - повторное использование уже полученного - один из мощнейших рычагов производительности. Важно понимать **слои** кеша и **стратегии** на каждом.

> HTTP-механика заголовков - в [Network](/content/network-api), деплой-аспект (immutable-ассеты) - в [деплое](/content/testing-deploying/cdn-and-caching). Здесь - **сводная картина** кеширования как стратегии.

---

## Слои кеширования

```
Память приложения (React Query, in-memory)
   ↓
Service Worker (Cache API, программируемый)
   ↓
HTTP-кеш браузера (Cache-Control, ETag)
   ↓
CDN / edge-кеш
   ↓
Сервер / origin
```

Запрос идёт сверху вниз и останавливается на первом слое, где есть свежие данные. Чем выше попал - тем быстрее.

---

## HTTP-кеш браузера

Браузер кеширует ответы по заголовкам сервера:

- **`Cache-Control: max-age=N`** - кешировать N секунд; `immutable` - не перепроверять; `no-cache` - кешировать, но валидировать; `no-store` - не кешировать.
- **Валидация** (`ETag`/`Last-Modified`) - спросить сервер «изменилось?»; если нет - `304 Not Modified`, без перекачки тела.

<b class="text-on-semi-light">Паттерн для ассетов</b> - <span class="text-gray">Хешированные бандлы (`app.4f3a.js`) - `Cache-Control: immutable, max-age=1год` (имя меняется при изменении кода); `index.html` - `no-cache` (всегда свежий, чтобы указывать на новые бандлы). Так пользователь берёт неизменные ассеты из кеша мгновенно и сразу видит новый деплой. Детали - в [деплое](/content/testing-deploying/cdn-and-caching).</span>

---

## CDN и edge

CDN кеширует контент **близко к пользователю** и отдаёт его вместо origin. Кешируют не только статику, но и ответы (страницы, API) с коротким TTL и **stale-while-revalidate** (отдать из кеша, обновить в фоне). Edge-вычисления позволяют кешировать и персонализировать на узле ([edge](/content/modern-dev/edge-computing)).

---

## Service Worker

**Service Worker** перехватывает сетевые запросы и управляет кешем программно (Cache API) - основа PWA и **офлайна** ([Web Workers](/content/additional-topics/web-workers-and-concurrency)). Классические стратегии:

| Стратегия | Логика | Когда |
|-----------|--------|-------|
| **Cache-first** | сначала кеш, сеть если нет | статика, шрифты, ассеты |
| **Network-first** | сначала сеть, кеш если офлайн | свежие данные, API |
| **Stale-while-revalidate** | отдать кеш сразу, обновить в фоне | баланс скорости и свежести |
| **Cache-only** | только кеш | гарантированно закешированное |
| **Network-only** | только сеть | некешируемое (платежи) |

```js
// stale-while-revalidate: мгновенно из кеша + фоновое обновление
const cached = await cache.match(req);
const fresh = fetch(req).then(r => { cache.put(req, r.clone()); return r; });
return cached || fresh;
```

## Prefetching

Кеш можно **заполнить заранее**, предугадывая следующий шаг:

- **prefetch** вероятной следующей страницы/данных (при наведении на ссылку, на idle).
- **Спекулятивная** загрузка маршрутов в SPA (роутеры/мета-фреймворки prefetch'ат видимые ссылки).

К моменту перехода данные уже в кеше - переход мгновенный.

---

## Инвалидация

«Инвалидация кеша - одна из двух сложных задач в CS». Способы:

- **Хеш в имени** ассета - новый контент = новое имя, старое не запрашивается (cache busting без ручной чистки).
- **Версионирование/purge** на CDN при деплое.
- **Инвалидация данных** - пометить кеш устаревшим после мутации ([React Query](/content/reactjs/data-fetching)).

---

## Кеш данных приложения

На самом верхнем слое - кеш **server-state** (React Query/SWR): дедупликация, фоновое обновление, инвалидация ([загрузка данных](/content/reactjs/data-fetching)). Это «кеш в памяти приложения», избавляющий от повторных запросов в рамках сессии.

## Вопросы на собеседовании

<b class="text-on-semi-light">Какие есть слои кеширования во фронтенде?</b>
<span class="text-gray">Память приложения (React Query), Service Worker (Cache API), HTTP-кеш браузера (Cache-Control/ETag), CDN/edge, origin. Запрос останавливается на первом слое со свежими данными.</span>

<b class="text-on-semi-light">Какие стратегии кеширования в Service Worker?</b>
<span class="text-gray">Cache-first (статика), network-first (свежие данные/API), stale-while-revalidate (кеш сразу + фон), cache-only, network-only. Выбор зависит от баланса скорости и свежести.</span>

<b class="text-on-semi-light">Как правильно кешировать ассеты и HTML?</b>
<span class="text-gray">Хешированные бандлы - immutable на год (имя меняется при изменении кода); index.html - no-cache (свежий, указывает на новые бандлы). Ассеты из кеша мгновенно, деплой виден сразу.</span>

<b class="text-on-semi-light">Что такое stale-while-revalidate?</b>
<span class="text-gray">Отдать данные из кеша сразу (даже устаревшие), а в фоне перезапросить и обновить. Быстрый ответ без ожидания сети; работает на CDN, в SW и в data-библиотеках.</span>

<b class="text-on-semi-light">Как решается инвалидация кеша для ассетов?</b>
<span class="text-gray">Хеш содержимого в имени файла: изменился код - изменилось имя - браузер запрашивает новый файл, старое имя не используется. Cache busting без ручной чистки кеша.</span>
