# Графика: Canvas и WebGL

Что лежит под графиками, играми, редакторами и 3D в браузере: спектр от DOM до WebGPU, Canvas 2D и его модель немедленной отрисовки, чёткость на экранах с высокой плотностью, цикл кадров, работа с пикселями и «испорченный» canvas, WebGL с шейдерами, WebGPU и доступность. Спрашивают, чем SVG отличается от Canvas, зачем WebGL и чем WebGPU лучше. Глубже — почему canvas размыт на ноутбуке, почему `getImageData` бросает `SecurityError` и почему ошибка в шейдере не падает исключением.

::tldr
- **Спектр:** DOM и SVG — объекты, которые помнит браузер; Canvas 2D — пиксели, которые рисует твой код; WebGL и WebGPU — программы на видеокарте. Чем правее, тем больше объектов можно показать и тем больше работы руками.
- **Canvas работает в режиме немедленной отрисовки:** после рисования фигур нет, есть только пиксели. Попадание по клику считают сами — `isPointInPath`, — перерисовывают каждый кадр в `requestAnimationFrame`.
- **Canvas размыт на экранах с высокой плотностью,** если размер буфера не умножен на `devicePixelRatio`. Буфер `ширина × dpr` и `ctx.scale(dpr, dpr)` делают его чётким.
- **Картинка с другого источника без CORS «портит» canvas:** рисовать можно, читать пиксели — `SecurityError`.
- **WebGL — шейдеры на видеокарте,** обычно через Three.js или PixiJS. **WebGPU** — современная замена с вычислительными шейдерами, но поддержку проверяют, а не предполагают.
::

## Спектр

Сквозной пример — магазин: иконки и логотипы, график продаж в админке, редактор баннеров с перетаскиванием и 3D-просмотр товара.

```text
DOM и CSS  →  SVG  →  Canvas 2D  →  WebGL  →  WebGPU
объекты, которые помнит браузер     пиксели и программы на видеокарте
десятки и сотни элементов           тысячи и миллионы объектов
```

Чем правее, тем больше объектов можно показать и тем меньше браузер делает за тебя: события, доступность, стили, перерисовку придётся делать самому.

### SVG и Canvas

**SVG** — векторная графика из DOM-узлов: каждый `<circle>` и `<path>` можно стилизовать CSS, повесить на него событие и подписать для скринридера, но тысячи узлов тормозят. **Canvas** — один элемент и пиксели в нём: быстро для тысяч объектов и обработки изображений, но без событий на фигурах и встроенной доступности. Подробное сравнение и выбор для графиков — в [Визуализации данных](/content/ecosystem-libs/data-visualization). Здесь — как устроен Canvas и что под ним.

## Canvas 2D

```js
const ctx = canvas.getContext('2d');
ctx.fillStyle = 'tomato';
ctx.beginPath();
ctx.arc(50, 50, 40, 0, Math.PI * 2);
ctx.fill();
```

### Немедленная отрисовка

После `fill()` браузер не помнит круг — только окрашенные пиксели. В проверке у canvas не было ни одного дочернего элемента, а «кнопку» на нём пришлось проверять математикой:

```js
const button = new Path2D();
button.roundRect(10, 10, 80, 30, 6);
ctx.fill(button);

canvas.addEventListener('click', (e) => {
  if (ctx.isPointInPath(button, e.offsetX, e.offsetY)) addToCart();
});
```

`isPointInPath` вернул `true` для точки внутри и `false` снаружи. Для сотен фигур так и строят интерактивность: храни описание фигур в своих структурах и проверяй попадание сам. Для перетаскивания и выделения — пространственные индексы, например квадродерево.

### Цикл кадров

Анимация на canvas — перерисовка всего кадра:

```js
function frame(time) {
  ctx.clearRect(0, 0, canvas.width, canvas.height);   // иначе останется прошлый кадр
  update(time);
  draw();
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

`requestAnimationFrame` вызывает функцию перед отрисовкой кадра, с частотой экрана, и приостанавливается во вкладке в фоне — в отличие от `setInterval`. Время берут из аргумента, а не считают кадрами: на экране 120 Гц кадров вдвое больше, чем на 60 Гц (подробно о кадрах — в [Рендеринге](/content/web/rendering)).

## Чёткость и devicePixelRatio

На экране с высокой плотностью один CSS-пиксель — это несколько физических. `devicePixelRatio` на таком экране — 2 или 3.

У canvas два размера: CSS-размер на странице и размер буфера — `canvas.width` и `canvas.height`. Если буфер 100×100, а на экране он занимает 200×200 физических пикселей, браузер растягивает картинку — и она размыта.

```js
const dpr = window.devicePixelRatio;
canvas.style.width = '100px';
canvas.style.height = '100px';
canvas.width = 100 * dpr;
canvas.height = 100 * dpr;
ctx.scale(dpr, dpr);   // рисуем в CSS-пикселях, а буфер — физический
```

В проверке при `devicePixelRatio = 2` оба canvas заняли на экране 200×200 физических пикселей. У растянутого буфера 100×100 вдоль края круга было 1737 промежуточных серых пикселей, а у буфера 200×200 с `scale(2, 2)` — 437: край чёткий. Плотность меняется при переносе окна между мониторами и при масштабировании страницы, поэтому её отслеживают через `matchMedia` или `ResizeObserver` с `devicePixelContentBoxSize`.

## Пиксели

`getImageData` даёт массив байтов :term[RGBA]{def="четыре канала пикселя: красный, зелёный, синий и прозрачность"}, `putImageData` записывает его обратно — так делают фильтры, предпросмотр обработки фотографий, пипетку:

```js
const img = ctx.getImageData(0, 0, canvas.width, canvas.height);
for (let i = 0; i < img.data.length; i += 4) {
  const y = 0.299 * img.data[i] + 0.587 * img.data[i + 1] + 0.114 * img.data[i + 2];
  img.data[i] = img.data[i + 1] = img.data[i + 2] = y;
}
ctx.putImageData(img, 0, 0);
```

В проверке красный пиксель `rgb(255, 0, 0)` стал серым `76, 76, 76`. Для больших изображений такой цикл выносят в воркер или WebAssembly, а простые эффекты — в `ctx.filter` или CSS-фильтры, которые работают на видеокарте.

### Испорченный canvas

Нарисовать картинку с другого источника можно, а прочитать пиксели — нет, если источник не разрешил это через :term[CORS]{def="механизм, которым сервер разрешает страницам с другого origin читать свои ответы"}. Иначе страница могла бы читать чужие изображения — например, аватарку из личного кабинета на другом сайте.

В проверке картинка с другого порта без CORS-заголовка сделала canvas «испорченным»: `getImageData` бросил `SecurityError`. Та же картинка с `crossOrigin = 'anonymous'` и заголовком `Access-Control-Allow-Origin` прочиталась (подробно — в [CORS и same-origin](/content/security-perfomance/cors-and-same-origin)). Испорченный canvas нельзя прочитать ни через `toDataURL`, ни через `toBlob`.

## WebGL

**WebGL** — доступ к видеокарте, основанный на OpenGL ES. Ты пишешь **шейдеры** — маленькие программы на языке GLSL, которые видеокарта выполняет параллельно: вершинный шейдер считает положение каждой вершины, фрагментный — цвет каждого пикселя.

```text
вершины в буфере → вершинный шейдер → растеризация → фрагментный шейдер → пиксели
```

В проверке WebGL2 нарисовал треугольник: пиксель в центре оказался красным `[255, 0, 0, 255]`, а угол — синим цветом очистки. Шейдер с ошибкой типов не бросил исключение — `COMPILE_STATUS` был `false`, а причина нашлась только в `getShaderInfoLog`. Это частая ловушка: ошибки WebGL нужно проверять явно, иначе экран просто останется пустым.

Писать на голом WebGL долго, поэтому берут библиотеки:

| Библиотека | Для чего |
| --- | --- |
| Three.js, React Three Fiber | 3D-сцены, модели, свет, материалы |
| Babylon.js | 3D и игры |
| PixiJS | быстрая 2D-графика и спрайты |
| deck.gl, MapLibre | карты и геоданные |
| regl, twgl | тонкие обёртки над WebGL |

## WebGPU

**WebGPU** — современная замена WebGL с моделью, похожей на :term[Vulkan]{def="низкоуровневый API графики и вычислений на видеокарте"}, Metal и Direct3D 12:

- меньше накладных расходов на вызовы и явное управление ресурсами;
- **вычислительные шейдеры** — вычисления общего назначения на видеокарте, в том числе для машинного обучения в браузере;
- язык шейдеров WGSL.

Поддержка растёт, но не везде одинакова: в проверочном headless Chromium `navigator.gpu` не было вовсе. Поэтому WebGPU подключают с проверкой и запасным вариантом:

```js
const adapter = navigator.gpu && (await navigator.gpu.requestAdapter());
const renderer = adapter ? await createWebGPURenderer(adapter) : createWebGLRenderer();
```

Three.js и Babylon.js умеют работать и с WebGPU, и с WebGL — переключение делает библиотека.

## Отрисовка в воркере

Тяжёлую отрисовку переносят из главного потока через `OffscreenCanvas`: canvas передают в воркер, и рисует он (подробно — в [Web Workers](/content/additional-topics/web-workers-and-concurrency)). Интерфейс остаётся отзывчивым, пока считается сложная сцена.

## Доступность

Canvas для скринридера — пустое место. Что делают:

- **запасное содержимое** внутри `<canvas>` — текст или таблица с теми же данными; браузер показывает его вспомогательным технологиям;
- `role="img"` и `aria-label` для статичной картинки;
- **дублирующий интерфейс** в DOM для интерактивного: кнопки, список элементов редактора, таблица данных графика;
- управление с клавиатуры и видимый фокус для своих интерактивных элементов.

Основы — в [Доступности](/content/html/accessibility). Это ещё одна причина выбирать SVG или DOM, когда объектов немного.

## Как выбрать

| Задача | Технология |
| --- | --- |
| иконки, логотипы, простые графики | SVG |
| графики на тысячи точек, рисование, обработка изображений | Canvas 2D |
| редактор с сотнями объектов | Canvas 2D или PixiJS со своей моделью объектов |
| 3D, частицы, игры, карты | WebGL через Three.js, Babylon.js, PixiJS, deck.gl |
| вычисления на видеокарте | WebGPU с запасным вариантом |

## Красные флаги в ответе

- **«Canvas помнит нарисованные фигуры».** Остаются только пиксели, попадание считают сами.
- **«Canvas на ретина-экране размыт — так и должно быть».** Буфер умножают на `devicePixelRatio`.
- **«Анимирую через `setInterval`».** `requestAnimationFrame` синхронизирован с кадрами и останавливается в фоне.
- **«Прочитаю пиксели любой картинки».** Картинка с другого источника без CORS портит canvas.
- **«Ошибка в шейдере упадёт исключением».** Её видно только в журнале компиляции.
- **«WebGPU уже есть везде».** Поддержку проверяют и держат запасной вариант.

## Как спрашивают на собеседовании

::question
В чём ключевое различие SVG и Canvas?

#answer
SVG — векторные объекты в DOM: браузер их помнит, их можно стилизовать, подписать для скринридера и повесить события, но тысячи узлов тормозят. Canvas — пиксели в одном элементе: быстро для тысяч объектов и обработки изображений, но без событий на фигурах и встроенной доступности.

#more
SVG масштабируется без потерь, а Canvas нужно перерисовывать при смене размера и плотности экрана. Выбор для графиков — по числу элементов и нужной интерактивности.
::

::question
Почему canvas выглядит размытым и как это исправить?

#answer
На экране с высокой плотностью `devicePixelRatio` больше единицы, а буфер canvas по умолчанию равен его CSS-размеру. Браузер растягивает буфер, и картинка размывается. Буфер делают `CSS-размер × devicePixelRatio` и вызывают `ctx.scale(dpr, dpr)`.

#more
Плотность меняется при переносе окна между мониторами и масштабировании, поэтому её отслеживают и пересоздают буфер. Для WebGL — то же самое плюс `gl.viewport`.
::

::question
Как сделать интерактивность на canvas?

#answer
Хранить описание фигур в своих структурах и проверять попадание по координатам события — `isPointInPath` с `Path2D` или своя геометрия. Перерисовывать сцену каждый кадр в `requestAnimationFrame`.

#more
Для многих объектов — пространственные индексы вроде квадродерева, для готовой модели объектов — библиотеки вроде PixiJS или Konva. Для скринридера нужен дублирующий интерфейс в DOM.
::

::question
Почему `getImageData` бросает `SecurityError`?

#answer
На canvas нарисована картинка с другого источника без разрешения CORS — canvas «испорчен», и читать его пиксели нельзя, чтобы страница не могла выведать чужие изображения.

#more
Исправление — `img.crossOrigin = 'anonymous'` и заголовок `Access-Control-Allow-Origin` у картинки. Испорченный canvas блокирует и `toDataURL`, и `toBlob`.
::

::question
Зачем нужен WebGL и чем WebGPU лучше?

#answer
WebGL даёт доступ к видеокарте через шейдеры — для 3D, частиц, карт и тяжёлых визуализаций; обычно через Three.js или PixiJS. WebGPU — современная замена с меньшими накладными расходами и вычислительными шейдерами для расчётов на видеокарте.

#more
Ошибки WebGL проверяют явно — статус компиляции и журнал шейдера. Поддержка WebGPU пока неодинакова, поэтому его подключают с проверкой `navigator.gpu` и запасным WebGL.
::

## Практика

::practice{title="Размытый график на ноутбуке"}
График продаж в админке на canvas выглядит чётким на внешнем мониторе и размытым на экране ноутбука. Код задаёт `canvas.width = 600` и стиль `width: 600px`.

#solution
У ноутбука `devicePixelRatio` — 2, и буфер 600 пикселей растягивается на 1200 физических. В проверке растянутый буфер дал вчетверо больше промежуточных серых пикселей на краю фигуры, чем буфер с учётом плотности.

```js
function setupCanvas(canvas, width, height) {
  const dpr = window.devicePixelRatio || 1;
  canvas.style.width = `${width}px`;
  canvas.style.height = `${height}px`;
  canvas.width = Math.round(width * dpr);
  canvas.height = Math.round(height * dpr);
  const ctx = canvas.getContext('2d');
  ctx.scale(dpr, dpr);
  return ctx;
}
```

Если окно переносят между мониторами, плотность меняется — `setupCanvas` вызывают заново по событию `change` у `matchMedia('(resolution: 2dppx)')` для текущей плотности и перерисовывают.
::

::practice{title="Фильтр фото падает с SecurityError"}
Редактор баннеров загружает фото товаров с CDN `img.shop.example` и делает предпросмотр в оттенках серого. На проде `getImageData` бросает `SecurityError`, локально всё работает.

#solution
Локально картинки с того же источника, а на проде — с CDN на другом домене. Без CORS canvas становится «испорченным». В проверке картинка без CORS дала `SecurityError`, а с CORS — прочиталась.

```js
const img = new Image();
img.crossOrigin = 'anonymous';   // запрос с CORS
img.src = 'https://img.shop.example/products/7.jpg';
```

```text
# ответ CDN
Access-Control-Allow-Origin: https://admin.shop.example
```

Нужны обе части: атрибут без заголовка не загрузит картинку вовсе, заголовок без атрибута не снимет «порчу». Если картинка уже закеширована браузером без CORS, к адресу добавляют параметр, чтобы запросить её заново.
::
