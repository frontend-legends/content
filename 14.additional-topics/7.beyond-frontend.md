# За пределами фронтенда

Карта соседних областей разработки и что в каждой нового для фронтендера: бэкенд с базами данных, расширения браузера, нативная мобильная разработка, игры, web3, машинное обучение, DevOps и системное программирование, а также как переходить между ними. Спрашивают, какой переход из фронтенда самый естественный, чем разработка игр отличается от интерфейсов и какие навыки переносятся. Глубже — почему на бэкенде страница каталога делает пятьдесят запросов, почему в игре персонаж прыгает по-разному на разных мониторах и почему страница не видит переменные расширения.

::tldr
- **Ближе всего — бэкенд и расширения браузера:** тот же JavaScript, а новое — данные. Транзакции, индексы и число запросов к базе важнее выбора фреймворка.
- **Расширение браузера — это веб-стек со своей архитектурой:** скрипты на страницах в изолированном мире, фон как Service Worker, сообщения между ними и разрешения в манифесте.
- **Игры — другая модель:** не «интерфейс как функция состояния», а цикл, который обновляет мир с фиксированным шагом и рисует кадр. Переменный шаг делает физику зависимой от частоты экрана.
- **Нативные Swift UI и Jetpack Compose декларативны,** как React, — ментальная модель переносится. Web3 — тот же фронтенд, но вместо REST — кошелёк, подписи и контракты.
- **Переходят шагами:** одно новое измерение за раз — язык или парадигма, не всё сразу. Переносятся отладка, чтение кода, HTTP, тесты, Git и сам JavaScript.
::

## Карта

Сквозной пример — команда магазина: бэкенд API, расширение для сравнения цен, мобильное приложение, промо-игра к распродаже, инфраструктура выкладки.

| Область | Языки и стек | Что новое для фронтендера |
| --- | --- | --- |
| бэкенд | Node.js, Go, Python, Java, Kotlin, Rust | данные, транзакции, конкурентный доступ, очереди |
| расширения браузера | JavaScript и веб-API | архитектура MV3, разрешения, изолированные миры |
| нативная мобильная | Swift и SwiftUI, Kotlin и Jetpack Compose | жизненный цикл приложения, магазины, ограничения платформы |
| игры | C# в Unity, C++ в Unreal, GDScript в Godot, веб — Canvas и WebGL | игровой цикл, физика, ECS, производительность кадра |
| web3 | Solidity, TypeScript с viem и wagmi | кошельки, подписи, транзакции, газ |
| машинное обучение | Python | математика, данные, обучение и выкладка моделей |
| DevOps и платформа | YAML, Go, Bash, Terraform | облака, контейнеры, Kubernetes, надёжность |
| системное и встраиваемое | C, C++, Rust | память вручную, железо, ограничения ресурсов |

Кроссплатформенные приложения на веб-стеке — React Native, Capacitor, Electron, Tauri — разобраны в [Кроссплатформенной разработке](/content/additional-topics/cross-platform). Здесь — области, где меняется сама модель работы.

## Бэкенд

Самый естественный шаг: JavaScript, асинхронность, HTTP, JSON и npm уже знакомы. Node.js-фреймворки — Express, Fastify, :term[NestJS]{def="серверный фреймворк Node.js на TypeScript с декораторами и внедрением зависимостей"}, Hono — дают меньше всего нового. Главное новое — **данные**. В проверке на встроенном `node:sqlite` видно три вещи, с которыми фронтенд почти не сталкивается.

### Транзакции

Заказ — это две записи: строка в `orders` и уменьшение остатка в `products`. Если вторая не удалась, первая не должна остаться:

```js
db.exec('begin');
try {
  db.prepare('insert into orders (product_id, qty) values (?, ?)').run(productId, qty);
  db.prepare('update products set stock = stock - ? where id = ?').run(qty, productId);
  db.exec('commit');
} catch (e) {
  db.exec('rollback');
  throw e;
}
```

В проверке заказ на 5 упаковок при остатке 1 упал на ограничении `CHECK (stock >= 0)`, и `rollback` откатил вставку заказа: в базе остался только первый, успешный заказ. Без транзакции появился бы заказ на товар, которого нет.

### N+1 запросов

```js
const orders = db.prepare('select * from orders').all();
const withTitles = orders.map((o) => ({ ...o, title: productById.get(o.product_id).title }));
```

В проверке это дало **52 запроса**: один за заказы и по одному на каждый из 51 заказа. Один `JOIN` вернул те же данные **одним** запросом. Это та же проблема, что и каскад запросов на фронтенде, только дороже: каждый запрос — круг до базы. :term[ORM]{def="библиотека, которая отображает таблицы базы на объекты кода и сама строит SQL"} и GraphQL-резолверы делают N+1 особенно легко (подробно о GraphQL — в [GraphQL](/content/network-api/graphql)).

### Индексы

`EXPLAIN QUERY PLAN` для поиска заказов по товару показал `SCAN orders` — полный перебор таблицы. После `create index orders_product on orders (product_id)` план стал `SEARCH orders USING INDEX orders_product`. На миллионе строк это разница между миллисекундами и секундами. Индексы ускоряют чтение и замедляют запись — выбирать их по реальным запросам — отдельный навык (подробно о структурах данных — в [Computer Science](/content/computer-science)).

Дальше на бэкенде — авторизация и сессии, очереди и фоновые задачи, кеш, конкурентный доступ, наблюдаемость. Путь в fullstack — самый востребованный и доступный для фронтендера.

## Расширения браузера

Расширения пишут на обычном веб-стеке, но архитектура своя — **Manifest V3**:

```json
{
  "manifest_version": 3,
  "name": "Shop price helper",
  "version": "1.0",
  "content_scripts": [{ "matches": ["https://*.shop.example/*"], "js": ["content.js"] }],
  "background": { "service_worker": "background.js" },
  "permissions": ["storage"]
}
```

- **скрипт содержимого** — выполняется на страницах из `matches`, видит и меняет их DOM;
- **фон** — Service Worker без DOM, который браузер запускает по событиям и гасит в простое;
- **сообщения** — `chrome.runtime.sendMessage` и `onMessage` между частями;
- **разрешения** — в манифесте, и каждое лишнее снижает доверие пользователей и проверяющих магазина расширений.

В проверке настоящее расширение в Chromium: фон зарегистрировался как Service Worker по адресу `chrome-extension://…/background.js`, скрипт содержимого прочитал цену «1800 ₽» со страницы, отправил её фону и записал ответ «20.00 $» в DOM.

### Изолированный мир

Скрипт содержимого и страница делят **DOM**, но не JavaScript. В проверке страница видела атрибут, который записало расширение, но `window.secretFromExtension` для неё был `undefined`, а `chrome.runtime` — недоступен. Это защищает расширение от страницы и страницу — от случайного вмешательства. Общаются они через DOM-события или `postMessage`, проверяя источник.

Специфика области — разные API в Chrome и Firefox (WebExtensions с отличиями), проверка в магазинах, обновления через магазин и ограничения :term[MV3]{def="Manifest V3: текущий формат расширений Chrome, фоновый код — сервис-воркер"} по сравнению со старым MV2: например, блокировка запросов — декларативными правилами, а не произвольным кодом.

## Нативная мобильная разработка

iOS — Swift и :term[SwiftUI]{def="декларативный фреймворк интерфейсов Apple"}, Android — Kotlin и :term[Jetpack Compose]{def="декларативный фреймворк интерфейсов Android на Kotlin"}. Оба современных фреймворка интерфейса **декларативны**: интерфейс описывается как функция состояния, а фреймворк сам обновляет экран — идея, знакомая по React и Vue.

```text
React:     const [count, setCount] = useState(0)
SwiftUI:   @State private var count = 0
Compose:   var count by remember { mutableStateOf(0) }
```

Новое — языки, жизненный цикл приложения — фон, приостановка, восстановление, — разрешения платформы, выпуск через магазины с проверкой и медленными обновлениями. Путь без смены языка — React Native (подробно — в [Кроссплатформенной разработке](/content/additional-topics/cross-platform)).

## Игры

Интерфейс реагирует на события: состояние изменилось — перерисовали. Игра живёт в **цикле**: каждый кадр обновить мир — ввод, физику, логику — и нарисовать его.

### Фиксированный шаг

Если двигать мир на время кадра, физика зависит от частоты экрана. В проверке мяч, падающий две секунды, оказался на высоте 80,074 при 30 кадрах в секунду и 80,334 — при 144. На медленном ноутбуке персонаж прыгает ниже, чем на игровом мониторе.

Решение — **фиксированный шаг**: физика всегда считается шагами по 1/120 секунды, а кадр лишь выполняет столько шагов, сколько накопилось времени:

```js
const STEP = 1 / 120;
let accumulator = 0;

function frame(dt) {
  accumulator += dt;
  while (accumulator >= STEP) {
    updatePhysics(STEP);
    accumulator -= STEP;
  }
  render();
}
```

В проверке так получилось одинаково — 80,32 — при 30, 60 и 120 кадрах в секунду. Это основа детерминированной физики, повторов и сетевых игр.

Дальше — архитектура **ECS** (сущности, компоненты, системы), бюджет кадра, работа со звуком и ресурсами. Движки — Unity, Unreal, Godot; в вебе — Canvas, WebGL, Three.js, PixiJS, Phaser, и здесь фронтенд-навыки применяются напрямую (подробно — в [Графике](/content/additional-topics/graphics-canvas-webgl)).

## Web3

Логика децентрализованного приложения живёт в **смарт-контрактах** — чаще всего на Solidity в Ethereum-совместимых сетях, — а фронтенд остаётся привычным React или Vue. Меняется то, с чем он говорит:

| Обычный фронтенд | Web3-фронтенд |
| --- | --- |
| вход по паролю или OAuth | подключение кошелька и подпись сообщения |
| запрос к REST API | чтение состояния контракта через узел сети |
| POST на сервер | транзакция, которую подписывает пользователь и оплачивает газом |
| ответ за сотни миллисекунд | ожидание подтверждения блока |

Библиотеки — viem и wagmi, ethers.js. Новое — модель транзакций, необратимость, комиссии и особая цена ошибок: подписанную транзакцию не отменить.

## Как переходить

Переносится больше, чем кажется: отладка, чтение чужого кода, HTTP и API, Git, тесты и ревью, производительность, сам JavaScript — Node.js, расширения, React Native, web3-фронтенды, веб-игры.

Стратегия:

- **начать с ближайшего** — бэкенд на Node.js, расширение, игра на Canvas;
- **одно новое измерение за раз** — новый язык **или** новая парадигма, а не всё сразу;
- **проект, а не курс** — маленький настоящий проект в новой области учит быстрее (подробно — в [Непрерывном обучении](/content/final-steps/continuous-learning));
- **глубина плюс ширина** — сильная экспертиза во фронтенде и понимание соседних областей делают сильнее в команде и устойчивее в карьере.

## Красные флаги в ответе

- **«Бэкенд — это просто эндпоинты на Express».** Главное — данные: транзакции, индексы, число запросов.
- **«Расширение — обычный скрипт на странице».** Изолированный мир, фон как Service Worker и разрешения.
- **«В игре двигаю объекты на время кадра».** Физика станет зависеть от частоты экрана.
- **«Web3 — это другой фронтенд».** Интерфейс тот же, меняются авторизация, данные и цена ошибки.
- **«Перейду в новую область, выучив всё сразу».** Одно новое измерение за раз.

## Как спрашивают на собеседовании

::question
Какой переход из фронтенда самый естественный?

#answer
В бэкенд и fullstack через Node.js: язык, асинхронность, HTTP и npm уже знакомы. Новое — данные: схемы, транзакции, индексы, число запросов к базе, а также авторизация, очереди и конкурентный доступ.

#more
Типичная ошибка новичка на бэкенде — N+1 запросов: цикл, в котором для каждой записи делается отдельный запрос. Его заменяют одним `JOIN` или пакетной загрузкой.
::

::question
Чем разработка игр отличается от разработки интерфейсов?

#answer
Интерфейс реагирует на события и перерисовывается при изменении состояния. Игра живёт в цикле: каждый кадр обновляет мир — ввод, физику, логику — и рисует его.

#more
Физику считают фиксированным шагом, а кадр выполняет накопившиеся шаги, — иначе поведение зависит от частоты экрана. Архитектура — часто ECS, ограничение — бюджет кадра.
::

::question
Как устроено расширение браузера на Manifest V3?

#answer
Манифест описывает скрипты содержимого, которые выполняются на страницах и видят их DOM, фон — Service Worker без DOM, который запускается по событиям, — и разрешения. Части общаются сообщениями.

#more
Скрипт содержимого работает в изолированном мире: DOM общий со страницей, а переменные и API расширения странице недоступны. Лишние разрешения снижают доверие и затрудняют проверку в магазине.
::

::question
Какова роль фронтендера в web3?

#answer
Интерфейс тот же — React или Vue, — но вместо REST API — подключение кошелька, подпись сообщений и транзакций, чтение состояния контрактов через узел сети. Логика — в смарт-контрактах.

#more
Новое — модель транзакций: ожидание подтверждения, комиссия за газ и необратимость. Интерфейс должен ясно показывать, что именно пользователь подписывает.
::

::question
Какие навыки переносятся в другие области?

#answer
Отладка, чтение кода, HTTP и API, Git, тесты и ревью, мышление о производительности и сам JavaScript — в Node.js, расширениях, React Native, веб-играх и web3-фронтендах.

#more
Поэтому переходить лучше шагами: одно новое измерение за раз — язык или парадигма. Широта вокруг глубокой экспертизы делает сильнее и во фронтенде.
::

## Практика

::practice{title="Страница заказов в админке тормозит"}
Эндпоинт списка заказов на Node.js отвечает несколько секунд. Код:

```js
const orders = await db.all('select * from orders where created_at > ?', since);
for (const order of orders) {
  order.product = await db.get('select * from products where id = ?', order.product_id);
}
```

#solution
Две проблемы. Первая — N+1: один запрос за заказы и по одному на каждый заказ. В проверке 51 заказ дал 52 запроса, а `JOIN` — один:

```sql
select o.*, p.title, p.price
from orders o
join products p on p.id = o.product_id
where o.created_at > ?
```

Вторая — фильтр по `created_at` без индекса: план запроса показывает полный перебор `SCAN orders`. После индекса план в проверке сменился на `SEARCH … USING INDEX`:

```sql
create index orders_created_at on orders (created_at);
```

Список ещё и ограничивают страницей — `limit` и курсор, — чтобы ответ не рос вместе с базой.
::

::practice{title="Прыжок разной высоты на разных мониторах"}
В промо-игре к распродаже персонаж на игровом мониторе прыгает выше, чем на офисном ноутбуке. Физика обновляется так: `velocity += gravity * dt; y += velocity * dt`, где `dt` — время кадра.

#solution
Интегрирование с шагом, равным времени кадра, даёт разный результат при разной частоте: в проверке высота через две секунды была 80,074 при 30 кадрах в секунду и 80,334 при 144. Физику переводят на фиксированный шаг:

```js
const STEP = 1 / 120;
let accumulator = 0;

function frame(dt) {
  accumulator += Math.min(dt, 0.25);   // защита от «спирали смерти» после долгой паузы
  while (accumulator >= STEP) {
    updatePhysics(STEP);
    accumulator -= STEP;
  }
  render(accumulator / STEP);          // доля шага — для плавной интерполяции
}
```

В проверке с фиксированным шагом высота совпала при 30, 60 и 120 кадрах в секунду. Ограничение `dt` не даёт выполнить тысячи шагов после того, как вкладка была в фоне.
::
