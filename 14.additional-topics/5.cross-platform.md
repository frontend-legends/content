# Кроссплатформенная разработка

Как с веб-навыками делать мобильные и десктопные приложения: спектр от нативного интерфейса до веба в обёртке, React Native и почему React в нём рисует не DOM, Capacitor, Flutter, Electron и Tauri, PWA как приложение и общий код между платформами. Спрашивают, чем React Native отличается от Capacitor, чем Tauri лучше Electron и когда хватает PWA. Глубже — почему в React Native нет `div`, почему Electron-приложение весит сотню мегабайт и как один репозиторий собирает разные реализации под разные платформы.

::tldr
- **Спектр:** нативный интерфейс — React Native, Flutter — или веб внутри обёртки — Capacitor, Electron, Tauri — или просто браузер — PWA. Чем ближе к нативному, тем лучше ощущения и дальше от веб-стека.
- **React — ядро, рендерер решает, во что рисовать:** React DOM — в DOM, React Native — в нативные виды iOS и Android. Компоненты, состояние и хуки те же, а вместо `div` — `View`.
- **Capacitor** упаковывает веб-приложение в системный WebView с плагинами к камере, геолокации, уведомлениям — быстрый путь «сайт → приложение в магазине».
- **Electron** везёт с каждым приложением Chromium и Node.js — тяжело, но предсказуемо. **Tauri** использует системный WebView и бэкенд на Rust — приложения в разы меньше.
- **Общий код — логика, а не интерфейс:** типы, API-клиент, состояние, утилиты — в общем пакете монорепо; платформенные реализации — в файлах `.web.js` и `.native.js`, которые выбирает сборщик.
::

## Спектр

Сквозной пример — магазин хочет мобильное приложение, приложение для сотрудников склада на десктопе и не хочет писать всё трижды.

```text
нативный интерфейс ◄──────────────────────────────────────► веб
React Native   Flutter       Capacitor        Electron, Tauri     PWA
нативные виды  свой движок   веб в WebView    веб на десктопе     браузер
```

| | Нативный интерфейс | Веб в обёртке | PWA |
| --- | --- | --- | --- |
| Интерфейс | настоящие виджеты платформы или свой движок | HTML и CSS в WebView | HTML и CSS в браузере |
| Ощущение | ближе всего к нативному | зависит от качества вёрстки | как сайт, установленный на экран |
| Доступ к устройству | полный, через модули | через плагины | то, что даёт браузер |
| Переиспользование веб-кода | логика | почти всё | всё |
| Магазины приложений | да | да | не обязательно |

## React Native

React Native — тот же React, но вместо DOM он рисует **нативные виды**: `UIView` на iOS, `android.view.View` на Android.

```jsx
import { View, Text, Pressable } from 'react-native';

function Cart() {
  const [count, setCount] = useState(0);
  return (
    <View style={{ padding: 16 }}>
      <Text>В корзине: {count}</Text>
      <Pressable onPress={() => setCount((n) => n + 1)}>
        <Text>Добавить</Text>
      </Pressable>
    </View>
  );
}
```

### Рендерер

React разделён на две части: ядро — компоненты, состояние, хуки, согласование — и **рендерер**, который знает, как создать и обновить элементы конкретной платформы (подробно о согласовании — в [Согласовании и Fiber](/content/reactjs/reconciliation-and-fiber)). React DOM — один рендерер, React Native — другой.

В проверке свой рендерер на `react-reconciler` превратил этот компонент в дерево «нативных видов» — `View`, `Text`, `Pressable` — обычных объектов вместо DOM-узлов. После нажатия рендерер изменил текст на месте — «В корзине: 0 → В корзине: 1» — и не создал ни одного нового вида. А `<div>` упал с ошибкой «нет нативного компонента»: в нативном рендерере есть только те элементы, которые он знает. Поэтому в React Native нет `div`, `span` и CSS-файлов — есть `View`, `Text` и стили объектами с раскладкой Flexbox.

### Что переносится и что нет

- **переносится:** React, хуки, состояние, TypeScript, TanStack Query, валидация, бизнес-логика, тесты логики;
- **не переносится:** DOM, CSS-файлы и селекторы, браузерные API, библиотеки компонентов для веба;
- **по-другому:** навигация, жесты, списки — `FlatList` с виртуализацией вместо обычной разметки, — права доступа и жизненный цикл приложения.

Новая архитектура React Native — JSI вместо асинхронного «моста» и рендерер Fabric — позволяет JavaScript вызывать нативный код напрямую и синхронно. **Expo** — набор инструментов поверх React Native: сборка в облаке, доступ к API устройства, обновления без выпуска новой версии в магазин; сейчас это рекомендуемый способ начать проект. **react-native-web** позволяет запускать те же компоненты в браузере.

## Capacitor и Flutter

**Capacitor** от команды Ionic берёт обычное веб-приложение — React, Vue, любое — и упаковывает его в нативную оболочку с **системным WebView**. Доступ к камере, геолокации, уведомлениям, файлам — через плагины:

```js
import { Camera, CameraResultType } from '@capacitor/camera';

const photo = await Camera.getPhoto({ resultType: CameraResultType.Uri });
```

Это самый быстрый путь «сайт → приложение в магазине»: тот же код, тот же стек. Цена — интерфейс остаётся вебом в WebView, и качество ощущений целиком зависит от вёрстки, производительности и внимания к деталям платформы.

**Flutter** — на языке Dart, со своим движком отрисовки: рисует интерфейс сам, не используя виджеты платформы и не используя веб-стек. Веб-навыки переносятся слабо, но о нём стоит знать — это популярная альтернатива в кроссплатформе.

## Десктоп

### Electron

**Electron** упаковывает веб-приложение вместе с **Chromium и Node.js**. На нём построены VS Code, Slack, Discord, десктопные клиенты Figma и многие другие.

- **плюсы:** полный веб-стек, одинаковый движок на Windows, macOS и Linux, доступ к системе через Node.js, огромная экосистема;
- **минусы:** каждое приложение везёт свой браузер — сборка обычно весит порядка сотни мегабайт, а память расходуется как у браузера с открытой вкладкой.

Процессы разделены: **главный** — Node.js, окна, меню, доступ к системе; **процессы отрисовки** — страницы приложения. Связь — через IPC и `preload`-скрипт с `contextBridge`. Изоляция контекста и выключенный доступ к Node.js из страницы — настройки по умолчанию в современных версиях; включать `nodeIntegration` для страницы, которая показывает внешний контент, — прямой путь к выполнению кода на машине пользователя через XSS (подробно — в [XSS](/content/security-perfomance/xss)).

### Tauri

**Tauri** — бэкенд на Rust и **системный WebView**: WebView2 на Windows, WKWebView на macOS, WebKitGTK на Linux. Браузер не везётся с приложением, поэтому сборка весит единицы мегабайт, а потребление памяти ниже. Доступ к системе — через явно разрешённые команды на Rust, что сужает поверхность атаки. Tauri 2 добавил сборку под iOS и Android.

| | Electron | Tauri |
| --- | --- | --- |
| Движок страницы | свой Chromium | системный WebView |
| Бэкенд | Node.js | Rust |
| Размер сборки | порядка сотни мегабайт | единицы мегабайт |
| Одинаковость отрисовки | одна версия Chromium везде | разные движки на разных ОС |
| Зрелость экосистемы | очень зрелая | моложе, быстро растёт |

Главный компромисс Tauri — разные движки: на macOS страница идёт в WebKit, на Windows — в Chromium-основе WebView2, и вёрстку проверяют на обоих (подробно — в [Браузерных движках](/content/web/browser-engines)).

## PWA как приложение

Самый лёгкий путь — без обёртки вовсе. PWA устанавливается на экран телефона и рабочий стол, работает офлайн через Service Worker, умеет push-уведомления и открывается в своём окне (подробно — в [PWA](/content/web/pwa)). Ограничение — возможности браузера: часть API устройства недоступна или работает не во всех браузерах, особенно на iOS. Для каталога и личного кабинета магазина этого часто хватает, для приложения склада со сканером и офлайн-синхронизацией — уже нет.

## Общий код

Главная ценность кроссплатформы — один стек на несколько платформ. Но делят в первую очередь **логику**:

```text
packages/
  core/       типы, API-клиент, состояние, валидация, форматирование — общие
  web/        интерфейс для браузера
  mobile/     интерфейс на React Native
  desktop/    оболочка Electron или Tauri вокруг web
```

Такой монорепозиторий собирают workspaces и оркестратором задач (подробно — в [Монорепозиториях](/content/advanced-tooling/monorepo-tooling)).

### Платформенные файлы

Когда реализация различается — поделиться товаром, открыть камеру, сохранить файл, — пишут два файла с одним интерфейсом, а выбор оставляют сборщику:

```text
share.web.js       navigator.share или копирование ссылки
share.native.js    Share API платформы
cart.js            общая логика
```

Metro, сборщик React Native, ищет `.ios.js`, `.android.js` и `.native.js` раньше `.js`; для веба то же настраивают через `resolve.extensions`. В проверке сборка Vite со списком `['.web.js', '.js']` взяла `share.web.js`, а со списком `['.native.js', '.js']` — `share.native.js`; чужой реализации в каждой сборке не было, а общий `cart.js` попал в обе. Импорт в коде один — `import { share } from './share'`.

## Как выбрать

| Ситуация | Выбор |
| --- | --- |
| мобильное приложение с нативными ощущениями, команда на React | React Native и Expo |
| есть веб-приложение, нужно быстро в магазины | Capacitor |
| максимальная производительность интерфейса, свой дизайн, команда готова к Dart | Flutter |
| десктоп, важна одинаковость и зрелость | Electron |
| десктоп, важны размер, память и безопасность | Tauri |
| хватает возможностей браузера, магазин не обязателен | PWA |

---

## Красные флаги в ответе

- **«React Native — это сайт в WebView».** Он рисует нативные виды, а в WebView работает Capacitor.
- **«Перенесём веб-компоненты в React Native как есть».** DOM и CSS там нет — переносится логика, а не разметка.
- **«Electron лёгкий, это же просто сайт».** С каждым приложением едет Chromium и Node.js.
- **«Включим `nodeIntegration`, так удобнее».** XSS в окне становится выполнением кода на компьютере пользователя.
- **«Tauri выглядит одинаково везде».** На разных ОС разные движки WebView.
- **«PWA заменит любое приложение».** Возможности ограничены браузером, особенно на iOS.

## Как спрашивают на собеседовании

::question
Чем React Native отличается от Capacitor?

#answer
React Native рисует настоящие нативные виды платформы — `View` и `Text` превращаются в виджеты iOS и Android. Capacitor упаковывает обычное веб-приложение в системный WebView и даёт доступ к устройству через плагины.

#more
React Native ближе к нативным ощущениям, но требует отдельного интерфейса без DOM и CSS. Capacitor переиспользует почти весь веб-код, но интерфейс остаётся вебом, и качество зависит от вёрстки.
::

::question
Почему в React Native нет `div`?

#answer
React разделён на ядро — компоненты, состояние, согласование — и рендерер, который создаёт элементы платформы. Рендерер React Native знает только нативные компоненты — `View`, `Text`, `Image`, — а DOM-элементов у него нет.

#more
Тот же принцип позволяет React рисовать в терминал, в PDF или 3D-сцену — нужен только свой рендерер на `react-reconciler`. Хуки и логика работают одинаково, меняются только «теги».
::

::question
Чем Tauri лучше Electron?

#answer
Tauri использует системный WebView и бэкенд на Rust вместо своего Chromium и Node.js, поэтому сборки в разы меньше и потребляют меньше памяти, а доступ к системе ограничен явно разрешёнными командами.

#more
Цена — разные движки на разных ОС, поэтому вёрстку проверяют в WebKit и Chromium. Electron зрелее и даёт одинаковую отрисовку везде.
::

::question
Почему Electron-приложения такие тяжёлые?

#answer
Каждое приложение включает свою копию Chromium и Node.js, а не использует системный браузер. Отсюда размер порядка сотни мегабайт и потребление памяти как у браузера.

#more
Зато движок одинаковый на всех ОС и полностью под контролем разработчика. Для безопасности важно не включать доступ к Node.js из страницы и общаться с главным процессом через `contextBridge`.
::

::question
Как переиспользовать код между вебом и мобильным приложением?

#answer
Выносить логику — типы, API-клиент, состояние, валидацию, форматирование — в общий пакет монорепозитория, а интерфейс писать под каждую платформу.

#more
Где реализация различается, — файлы `.web.js` и `.native.js` с одним интерфейсом: сборщик выбирает нужный по списку расширений. react-native-web позволяет переиспользовать и компоненты, но с компромиссами для веба.
::

## Практика

::practice{title="Поделиться товаром на всех платформах"}
Кнопка «Поделиться» в вебе использует `navigator.share`, а в мобильном приложении на React Native этот код падает. Команда скопировала компонент и поддерживает две версии.

#solution
Логику кнопки оставляют общей, а различающуюся часть выносят в платформенные файлы с одним интерфейсом:

```js
// share.web.js
export const share = async (product) => {
  if (navigator.share) return navigator.share({ title: product.title, url: product.url });
  await navigator.clipboard.writeText(product.url);
};

// share.native.js
import { Share } from 'react-native';
export const share = (product) => Share.share({ message: `${product.title} ${product.url}` });

// ShareButton.js — один на все платформы
import { share } from './share';
```

Metro выбирает `share.native.js`, а веб-сборка — `share.web.js` через `resolve.extensions`. В проверке сборка Vite с `['.web.js', '.js']` взяла веб-реализацию, а с `['.native.js', '.js']` — нативную, и чужой реализации в сборке не было.
::
