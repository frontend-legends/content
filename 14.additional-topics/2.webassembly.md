# WebAssembly

Что такое WebAssembly и когда он нужен фронтенду: бинарный формат рядом с JavaScript, модуль, импорты и экспорты, линейная память и передача строк, ловушки вместо исключений, загрузка в браузере, инструменты для Rust, C++ и других языков, WASI вне браузера. Спрашивают, заменяет ли WebAssembly JavaScript, когда его стоит использовать и почему сложно передавать данные. Глубже — почему он не всегда быстрее JavaScript, почему после `memory.grow` массив стал пустым и почему модуль не загружается с сервера, который отдаёт его как обычный файл.

::tldr
- **WebAssembly — компактный бинарный формат,** в который компилируются Rust, C, C++, Go и другие языки. Он выполняется в той же песочнице, что и JavaScript, и работает рядом с ним.
- **Не замена JavaScript:** у модуля нет доступа к DOM и браузерным API — только к функциям, которые ему передал JavaScript. JavaScript управляет приложением, WebAssembly берёт тяжёлые вычисления.
- **На границе — только числа:** i32, i64 как BigInt, f32, f64. Строки и объекты кладут байтами в линейную память и передают адрес и длину — это делает связующий код инструментов.
- **Быстрее не всегда:** простой цикл после JIT в JavaScript сопоставим с WebAssembly. Выигрыш — в предсказуемости, готовых библиотеках на других языках и тяжёлых алгоритмах.
- **Загрузка:** `instantiateStreaming` компилирует по ходу загрузки, но требует `Content-Type: application/wasm`. Вне браузера модули запускаются через WASI.
::

---

## Что это

Сквозной пример — магазин: обработка фотографий товаров прямо в браузере перед загрузкой, поиск по каталогу в офлайне через :term[SQLite]{def="встраиваемая база данных SQL в одном файле, без отдельного сервера"} и проверка штрихкодов камерой.

```text
Rust / C / C++ / Go  ── компиляция ──►  module.wasm  ──►  браузер, рядом с JavaScript
```

WebAssembly — формат инструкций для стековой виртуальной машины. Модуль компактный: в проверке функция сложения двух чисел заняла **41 байт**. Движок браузера компилирует его в машинный код заранее, без долгого разогрева :term[JIT]{def="компиляция в машинный код во время выполнения — для кода, который вызывается часто"}, и выполняет в той же песочнице, что и JavaScript: доступ к системе — только тот, что дали снаружи.

У формата есть текстовое представление — WAT:

```text
(module
  (func (export "add") (param i32 i32) (result i32)
    local.get 0
    local.get 1
    i32.add))
```

Руками его пишут редко — обычно WebAssembly получают компиляцией с другого языка, — но на нём хорошо видна модель.

## Не замена JavaScript

У модуля **нет доступа к DOM, `fetch` и любым браузерным API**. Всё внешнее — импорты: функции, которые JavaScript передаёт при создании экземпляра.

```js
const { instance } = await WebAssembly.instantiate(bytes, {
  env: { log: (n) => console.log(n) },
});
instance.exports.run();   // модуль вызвал env.log(42)
```

В проверке модуль вызвал импортированную функцию и передал ей `42`, а без нужного импорта создание экземпляра упало с `TypeError`. Отсюда модель: JavaScript — интерфейс, события, сеть, состояние приложения; WebAssembly — вычислительные горячие точки, вызываемые из JavaScript.

---

## Числа на границе

Функции модуля принимают и возвращают только числа:

| Тип WebAssembly | В JavaScript | Что было в проверке |
| --- | --- | --- |
| `i32` | `number` | `add(2147483647, 1)` → `-2147483648`: переполнение по кругу; `add(1.9, 1)` → `2`: дробное приведено к целому |
| `i64` | `BigInt` | `add64(2n ** 62n, 2n ** 62n)` → `-(2n ** 63n)`; обычное число вместо BigInt — `TypeError` |
| `f32`, `f64` | `number` | |

### Ловушки

Ошибка внутри модуля — не исключение JavaScript и не `undefined`, а **ловушка**: выполнение прерывается, и в JavaScript приходит `WebAssembly.RuntimeError`. В проверке деление на ноль дало `divide by zero`, а чтение за пределами памяти — `memory access out of bounds`.

## Линейная память

Память модуля — один непрерывный `ArrayBuffer`, который растёт страницами по 64 КиБ. В проверке модуль с одной страницей дал `memory.buffer.byteLength === 65536`.

### Строки и объекты

Строку нельзя передать напрямую. Её кодируют в байты, кладут в память модуля и передают адрес и длину:

```js
const bytes = new TextEncoder().encode('banana');
new Uint8Array(instance.exports.memory.buffer).set(bytes, 0);
instance.exports.countA(0, bytes.length);   // 3
```

В проверке модуль посчитал три буквы `a` в «banana», читая байты из памяти. Обратно — так же: модуль пишет байты, JavaScript читает их и декодирует. Выделение памяти, кодирование строк, объекты и массивы берёт на себя **связующий код**, который генерируют инструменты: `wasm-bindgen` для Rust, Emscripten для C и C++.

Цена каждого пересечения границы — копирование данных. Поэтому выгодно передавать модулю большую порцию работы за раз, а не вызывать его тысячи раз с мелочами.

### memory.grow

Когда модулю нужно больше памяти, она растёт — и прежний `ArrayBuffer` **отсоединяется**:

```js
const view = new Uint8Array(instance.exports.memory.buffer);
instance.exports.memory.grow(1);
view.length;   // 0
```

В проверке представление длиной 65 536 после роста памяти стало пустым, а `memory.buffer` — новым буфером на 131 072 байта. Частая ошибка — закешировать `Uint8Array` над памятью и читать из него после вызова, во время которого модуль вырос. Представление берут заново после каждого вызова, который может выделять память.

## Загрузка в браузере

```js
const { instance } = await WebAssembly.instantiateStreaming(fetch('/codec.wasm'), imports);
```

`instantiateStreaming` компилирует модуль по ходу загрузки — не дожидаясь последнего байта. Но браузер требует правильный тип ответа. В проверке модуль с `Content-Type: application/wasm` загрузился, а тот же файл с `application/octet-stream` упал:

```text
TypeError: Incorrect response MIME type. Expected 'application/wasm'.
```

Запасной путь — `WebAssembly.instantiate(await response.arrayBuffer())` — в проверке сработал, но без компиляции по ходу загрузки. Правильнее настроить тип на сервере или CDN. Большие модули ещё и сжимают — :term[Brotli]{def="алгоритм сжатия Google, обычно сильнее gzip"} хорошо сжимает WebAssembly — и кешируют с хешем в имени (подробно — в [CDN и кешировании](/content/testing-deploying/cdn-and-caching)).

Тяжёлые вычисления в WebAssembly всё равно занимают поток, в котором выполняются. Чтобы не замораживать интерфейс, модуль запускают в воркере (подробно — в [Web Workers](/content/additional-topics/web-workers-and-concurrency)).

## Быстрее ли он

Распространённое заблуждение — «WebAssembly всегда быстрее JavaScript». В проверке сумма миллиона чисел двадцать раз заняла около 13 мс в JavaScript и около 10 мс в WebAssembly: один порядок. JIT-компилятор хорошо оптимизирует простые циклы по типизированным массивам.

Где WebAssembly действительно выигрывает:

- **предсказуемость** — нет разогрева JIT и деоптимизаций, скорость стабильна с первого вызова;
- **тяжёлые алгоритмы** с ручным управлением памятью и SIMD — кодеки, сжатие, физика, обработка изображений;
- **готовый код на других языках** — не переписывать на JavaScript библиотеку на C или Rust, проверенную годами: SQLite, :term[ffmpeg]{def="набор программ для обработки видео и звука"}, движки рендеринга шрифтов и PDF;
- **один код для браузера, сервера и мобильных** платформ.

Где проигрывает: работа с DOM, мелкие частые вызовы через границу, задачи, упирающиеся в сеть. Решение принимают по профилю, а не «для скорости вообще» (подробно — в [Производительности во время работы](/content/security-perfomance/runtime-performance)).

## Где применяют

- **графические редакторы** — Figma использует WebAssembly для движка рендеринга;
- **видео и аудио** — кодеки, `ffmpeg.wasm` для конвертации в браузере;
- **базы данных в браузере** — SQLite через официальную сборку `sqlite-wasm` или `wa-sqlite`, часто вместе с :term[OPFS]{def="Origin Private File System: приватная быстрая файловая система сайта в браузере"} для хранения;
- **игры и 3D** — Unity и Unreal умеют собирать сборку под веб;
- **машинное обучение** — ONNX Runtime Web и другие среды выполнения моделей (подробно — в [ИИ во фронтенде](/content/additional-topics/ai-in-the-frontend));
- **сжатие, хеширование, криптография**, распознавание штрихкодов, научные расчёты и CAD.

## Вне браузера

**WASI** — системный интерфейс WebAssembly: стандартный набор импортов для файлов, часов, случайных чисел и вывода. С ним модуль работает вне браузера — в Node.js, Wasmtime, Wasmer, на edge-платформах.

В проверке модуль без единой строки JavaScript-логики вызвал импорт `fd_write` и напечатал строку в стандартный вывод Node.js через `node:wasi`. Модули быстро стартуют и изолированы, поэтому их используют для плагинов, serverless- и edge-функций — Fastly Compute, Cloudflare Workers.

---

## Ограничения

- **нет доступа к DOM и API браузера** — только через импорты JavaScript;
- **размер** — модуль с рантаймом языка весит сотни килобайт и больше; для мелкой задачи это не окупается;
- **граница** — копирование данных и связующий код;
- **отладка** — сложнее, чем JavaScript, хотя DevTools поддерживают source maps и DWARF для WebAssembly;
- **сборка** — второй язык и второй набор инструментов в проекте.

---

## Красные флаги в ответе

- **«WebAssembly заменит JavaScript».** У него нет DOM и API браузера — он дополняет JavaScript.
- **«WebAssembly всегда быстрее».** Простой код после JIT сопоставим, выигрыш — в тяжёлых алгоритмах и предсказуемости.
- **«Передам модулю строку».** На границе только числа, строки идут через память.
- **«Закеширую представление памяти».** После `memory.grow` старый буфер отсоединяется.
- **«Сервер отдаст `.wasm` как любой файл».** `instantiateStreaming` требует `application/wasm`.
- **«Посчитаю в WebAssembly, и интерфейс не замрёт».** Модуль занимает поток — тяжёлую работу запускают в воркере.

## Как спрашивают на собеседовании

::question
Что такое WebAssembly?

#answer
Компактный бинарный формат инструкций, в который компилируются Rust, C, C++, Go и другие языки. Он выполняется в браузере в той же песочнице, что и JavaScript, и вызывается из него как набор функций.

#more
У формата есть текстовое представление WAT. Модуль экспортирует функции и память, а импортирует то, что ему даёт JavaScript. Вне браузера модули запускаются через WASI.
::

::question
Заменяет ли WebAssembly JavaScript?

#answer
Нет. У модуля нет доступа к DOM и браузерным API — только к импортированным функциям. JavaScript управляет интерфейсом и приложением, а WebAssembly берёт вычислительные горячие точки.

#more
Типичное приложение остаётся на JavaScript, а в WebAssembly выносят кодеки, обработку изображений, базы данных, движки рендеринга — часто готовые библиотеки на других языках.
::

::question
Почему передавать данные между JavaScript и WebAssembly непросто?

#answer
На границе передаются только числа. Строки, массивы и объекты нужно положить байтами в линейную память модуля и передать адрес и длину, а результат прочитать обратно.

#more
Это делает связующий код — `wasm-bindgen`, Emscripten. Каждое пересечение границы — копирование, поэтому модулю отдают большую порцию работы за раз. После `memory.grow` старые представления памяти становятся пустыми.
::

::question
Всегда ли WebAssembly быстрее JavaScript?

#answer
Нет. JIT хорошо оптимизирует простые циклы, и разница бывает небольшой. WebAssembly выигрывает в тяжёлых алгоритмах с ручным управлением памятью и SIMD, в предсказуемости без разогрева и деоптимизаций и тем, что позволяет взять готовый код на других языках.

#more
Решение принимают по профилю. Для работы с DOM и мелких частых вызовов WebAssembly проигрывает из-за стоимости границы.
::

::question
Как загрузить модуль в браузере?

#answer
`WebAssembly.instantiateStreaming(fetch(url), imports)` — компиляция идёт по ходу загрузки. Сервер должен отдавать модуль с `Content-Type: application/wasm`, иначе будет `TypeError`.

#more
Запасной вариант — `WebAssembly.instantiate` от `arrayBuffer()` ответа, но без потоковой компиляции. Модули сжимают и кешируют с хешем в имени, а тяжёлые запускают в воркере.
::

## Практика

::practice{title="Модуль не загружается в продакшене"}
Локально модуль обработки фотографий работает, а после выкладки на CDN падает с `TypeError: Incorrect response MIME type. Expected 'application/wasm'`.

#solution
`instantiateStreaming` требует правильный тип ответа, а CDN отдаёт `.wasm` как `application/octet-stream`. В проверке тот же файл с `application/wasm` загрузился, а с `application/octet-stream` — упал. Исправление — тип на сервере:

```text
# nginx
types { application/wasm wasm; }
```

```js
// запасной путь, если тип настроить нельзя
const response = await fetch('/photo.wasm');
const { instance } = await WebAssembly.instantiate(await response.arrayBuffer(), imports);
```

Запасной путь в проверке сработал, но теряет компиляцию по ходу загрузки. Заодно стоит проверить сжатие Brotli и кеш с хешем в имени.
::

::practice{title="Результат обработки иногда пустой"}
Код читает результат модуля через закешированное представление памяти. На маленьких фотографиях всё работает, на больших — массив результата пустой.

```js
const heap = new Uint8Array(instance.exports.memory.buffer);
const ptr = instance.exports.process(inputPtr, inputLen);
const result = heap.slice(ptr, ptr + outLen);   // иногда пусто
```

#solution
Для больших фотографий модулю не хватает памяти, и она растёт. Рост отсоединяет прежний `ArrayBuffer`: в проверке представление длиной 65 536 после `memory.grow(1)` стало длиной 0. Представление берут заново после вызова:

```js
const ptr = instance.exports.process(inputPtr, inputLen);
const heap = new Uint8Array(instance.exports.memory.buffer);   // свежий буфер
const result = heap.slice(ptr, ptr + outLen);
```

Связующий код `wasm-bindgen` и Emscripten делает это сам — проблема возникает при ручной работе с памятью.
::
