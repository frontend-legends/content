# Медиа и WebRTC

Как работать с камерой, микрофоном, звуком и видеосвязью из JavaScript: захват медиа и права, дорожки и их выключение, запись, граф Web Audio, WebRTC и что значит «без сервера», сигналинг, STUN и TURN, каналы данных, потоковое видео для больших аудиторий и готовые сервисы. Спрашивают, что такое WebRTC, правда ли он работает без сервера и зачем STUN и TURN. Глубже — почему камера не открывается на стенде по `http`, почему индикатор камеры не гаснет и почему соединение висит в состоянии `new`.

::tldr
- **Захват медиа только в безопасном контексте:** HTTPS или `localhost`. На обычном `http` `navigator.mediaDevices` нет вовсе. Доступ — по разрешению пользователя.
- **Поток состоит из дорожек:** видео и аудио. Камера выключается, только когда остановлены все её дорожки — `track.stop()`.
- **Web Audio — граф узлов:** источник → обработка → выход. Звуку нужен жест пользователя: контекст, созданный до клика, обычно приостановлен.
- **WebRTC передаёт медиа и данные напрямую между браузерами, но без серверов не работает:** сигналинг для обмена описаниями, STUN для внешнего адреса, TURN для ретрансляции, когда прямой путь закрыт.
- **Для трансляции на тысячи зрителей — не WebRTC,** а адаптивный поток HLS или DASH. Для звонков в продакшене обычно берут сервис: LiveKit, Daily, Twilio, Agora.
::

## Захват медиа

Сквозной пример — магазин: видеоконсультация с продавцом, голосовые отзывы о товаре и прямая трансляция распродажи.

```js
const stream = await navigator.mediaDevices.getUserMedia({
  video: { width: 640, height: 480 },
  audio: true,
});
videoElement.srcObject = stream;
```

`getUserMedia` спрашивает разрешение и возвращает **MediaStream** — набор дорожек. Возможные ошибки — `NotAllowedError`, если пользователь отказал, `NotFoundError`, если устройства нет, `NotReadableError`, если камеру занял другой процесс. Их обрабатывают и объясняют пользователю, что делать.

### Только безопасный контекст

В проверке на `http://shop.test` — обычный домен без HTTPS — `isSecureContext` был `false`, а `navigator.mediaDevices` — `undefined`: не ошибка доступа, а отсутствие API. На `http://localhost` всё работало — `localhost` считается безопасным. Отсюда частая ловушка: локально камера открывается, а на стенде по `http` код падает на `undefined`. Стенды для таких функций поднимают с HTTPS.

### Дорожки

В проверке поток с запросом 640×480 дал две дорожки — `audio` и `video`, — а `getSettings()` вернул фактические 640×480. Камеру выключают, останавливая дорожки:

```js
stream.getTracks().forEach((track) => track.stop());
```

После этого в проверке `readyState` дорожки стал `ended`. Если забыть, камера остаётся включённой и горит индикатор, даже когда элемент `video` убран со страницы. Во фреймворках дорожки останавливают при размонтировании компонента — в функции очистки эффекта (подробно — в [Эффектах и синхронизации](/content/reactjs/effects-and-synchronization)).

### Экран и запись

- `getDisplayMedia()` — захват экрана, окна или вкладки; только по жесту пользователя;
- `MediaRecorder` — запись потока в файл:

```js
const chunks = [];
const recorder = new MediaRecorder(stream);
recorder.ondataavailable = (e) => chunks.push(e.data);
recorder.onstop = () => upload(new Blob(chunks, { type: recorder.mimeType }));
recorder.start();
```

В проверке полсекунды записи с камеры дали файл `video/webm` больше килобайта. Формат зависит от браузера, поэтому его выбирают через `MediaRecorder.isTypeSupported` и берут фактический из `recorder.mimeType`. Голосовой отзыв — тот же `MediaRecorder` с одним аудио.

## Web Audio

**Web Audio API** строит граф узлов: источник → обработка → выход.

```js
const ctx = new AudioContext();
const osc = new OscillatorNode(ctx, { frequency: 440 });
const gain = new GainNode(ctx, { gain: 0.5 });
osc.connect(gain).connect(ctx.destination);
osc.start();
```

В проверке тот же граф отрисовали в `OfflineAudioContext` — без колонок, быстрее реального времени: секунда звука дала синусоиду с пиком 0,5 и 440 колебаниями. Так тестируют обработку звука и рендерят его в файл.

Узлы: источники — осциллятор, файл, поток с микрофона; обработка — громкость, фильтры, задержка, компрессор, панорама; `AnalyserNode` — спектр и громкость для визуализаторов; `AudioWorklet` — своя обработка в отдельном потоке.

### Жест пользователя

Браузеры не дают сайтам шуметь без спроса: `AudioContext`, созданный до взаимодействия со страницей, по правилам автозапуска обычно приостановлен. Его запускают по клику:

```js
button.addEventListener('click', () => ctx.resume());
```

В проверочном headless Chromium контекст был сразу `running` — там политику автозапуска ослабляют, — поэтому такие вещи проверяют и в обычном браузере.

## WebRTC

**WebRTC** — связь в реальном времени между браузерами: видео, аудио, экран и произвольные данные. Медиапоток идёт напрямую между участниками, зашифрованный DTLS и SRTP.

### Без сервера — не совсем

В проверке два `RTCPeerConnection` на одной странице соединились, передали видеодорожку и сообщение по каналу данных. Но только после того, как код **сам** передал между ними описания и кандидатов. Соединение, которое создало предложение и не получило ответа, осталось в состоянии `new`.

Это и есть **сигналинг** — обмен метаданными до соединения. WebRTC его не определяет: обычно это свой WebSocket-сервер (подробно — в [Реалтайме](/content/network-api/realtime)).

```text
1. A создаёт предложение (SDP) и отправляет B через сигналинг
2. B отвечает своим SDP
3. оба обмениваются ICE-кандидатами — возможными сетевыми путями
4. ICE находит рабочую пару и устанавливает соединение
5. медиа идёт напрямую — или через TURN
```

### SDP

**SDP** — текстовое описание сессии: какие дорожки, кодеки, параметры. В проверке в предложении были строки `m=video` для видео, `m=application … webrtc-datachannel` для канала данных и `a=fingerprint:sha-256` — отпечаток сертификата DTLS: шифрование в WebRTC обязательно, нешифрованного режима нет.

### STUN и TURN

Большинство устройств за NAT и не знают свой внешний адрес:

| Сервер | Зачем |
| --- | --- |
| STUN | узнать свой внешний адрес и порт, чтобы участники попробовали соединиться напрямую |
| TURN | ретранслировать трафик, когда прямой путь закрыт: строгий NAT, корпоративный файрвол |

В проверке без STUN-сервера у соединения были только кандидаты типа `host` — локальные адреса; через интернет этого не хватило бы. Часть звонков в продакшене всегда идёт через TURN, а это трафик и деньги — TURN-серверы считают в бюджете.

```js
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: 'stun:stun.shop.example:3478' },
    { urls: 'turn:turn.shop.example:3478', username, credential },
  ],
});
```

### Каналы данных

`createDataChannel` передаёт произвольные данные напрямую: чат, игровое состояние, передача файлов. Канал может быть упорядоченным и надёжным, как TCP, или неупорядоченным без повторов — для данных, где важна свежесть, а не полнота.

### Много участников

Прямое соединение каждого с каждым быстро упирается в канал отправителя: при пяти участниках каждый отправляет свой поток четырём. Поэтому группы идут через **SFU** — сервер, который принимает один поток от каждого и раздаёт остальным. Это ещё одна причина, по которой «WebRTC без серверов» — миф.

## Потоковое видео

Для трансляции на тысячи зрителей WebRTC не подходит — каждому зрителю нужно своё соединение. Используют **адаптивный поток**:

- **HLS** и **DASH** — видео нарезано на сегменты в нескольких качествах, плеер переключается по скорости сети;
- **Media Source Extensions** — подача сегментов в `<video>` из JavaScript; на них работают `hls.js` и dash.js;
- **WebCodecs** — низкоуровневое кодирование и декодирование кадров для своих конвейеров: редакторы, облачный гейминг.

Задержка у HLS — секунды и десятки секунд, у WebRTC — доли секунды. Для интерактивного эфира с вопросами зрителей есть промежуточные варианты — LL-HLS и раздача WebRTC через медиасерверы.

| Задача | Технология |
| --- | --- |
| звонок, консультация, небольшая группа | WebRTC через сервис или SFU |
| трансляция на массовую аудиторию | HLS или DASH через CDN |
| передача файлов между пользователями | канал данных WebRTC |
| запись с камеры, голосовые сообщения | `MediaRecorder` |
| эквалайзер, визуализатор, синтез | Web Audio |

## Сервисы

Свой WebRTC в продакшене — это сигналинг, STUN и TURN по регионам, SFU, запись, переподключения и мониторинг качества. Поэтому чаще берут сервис с SDK: **LiveKit** — с открытым кодом и облаком, **Daily**, **Twilio Video**, **Agora**, **100ms**, **Jitsi** — для своих серверов. Фронтенду остаются интерфейс звонка, выбор устройств, обработка ошибок и состояние сети.

---

## Красные флаги в ответе

- **«WebRTC работает без серверов».** Нужны сигналинг, STUN, часто TURN и SFU для групп.
- **«Камера не открывается — нет разрешения».** На `http` в обычном домене API нет вовсе.
- **«Убрал video со страницы — камера выключилась».** Выключает только `track.stop()` у всех дорожек.
- **«Трансляцию на десять тысяч зрителей сделаем на WebRTC».** Для массовой раздачи — HLS или DASH через CDN.
- **«Звук запустится сам».** Политика автозапуска требует жеста пользователя.
- **«Для звонков в продакшене напишем свой TURN и SFU за спринт».** Обычно берут сервис.

## Как спрашивают на собеседовании

::question
Что такое WebRTC?

#answer
API для связи в реальном времени между браузерами: видео, аудио, демонстрация экрана и произвольные данные. Медиапоток идёт напрямую между участниками, зашифрованный DTLS и SRTP.

#more
Соединение — `RTCPeerConnection`, данные — `createDataChannel`. Описание сессии — SDP, сетевые пути — ICE-кандидаты. Для групп используют SFU-сервер.
::

::question
Правда ли WebRTC работает без сервера?

#answer
Нет. Медиа идёт напрямую, но для знакомства участников нужен сигналинг — свой сервер, через который они обмениваются SDP и ICE-кандидатами. За NAT нужен STUN, а при закрытом прямом пути — TURN, который ретранслирует трафик.

#more
Без обмена описаниями соединение остаётся в состоянии `new`. Для групп больше трёх-четырёх человек добавляют SFU: прямое соединение каждого с каждым упирается в канал отправителя.
::

::question
Зачем нужны STUN и TURN?

#answer
STUN помогает устройству за NAT узнать свой внешний адрес, чтобы участники попробовали соединиться напрямую. TURN — ретранслятор, через который идёт трафик, когда прямое соединение невозможно.

#more
Без STUN у соединения только локальные кандидаты. Часть звонков всегда идёт через TURN, а это трафик, — его закладывают в инфраструктуру и бюджет.
::

::question
Как получить доступ к камере и выключить её?

#answer
`navigator.mediaDevices.getUserMedia` в безопасном контексте — HTTPS или `localhost` — с разрешения пользователя. Выключают, вызывая `stop()` у всех дорожек потока.

#more
На обычном `http` API нет вовсе. Ошибки — `NotAllowedError`, `NotFoundError`, `NotReadableError`. Во фреймворках дорожки останавливают при размонтировании, иначе камера остаётся включённой.
::

::question
Когда WebRTC не подходит?

#answer
Для трансляции на массовую аудиторию: каждому зрителю нужно своё соединение. Там используют адаптивный поток HLS или DASH через CDN.

#more
WebRTC даёт задержку в доли секунды, HLS — секунды и больше. Для интерактивных эфиров есть LL-HLS и раздача WebRTC через медиасерверы.
::

## Практика

::practice{title="Камера не включается на стенде"}
Видеоконсультация работает локально, а на стенде `http://staging.shop.internal` падает с `TypeError: Cannot read properties of undefined (reading 'getUserMedia')`.

#solution
Стенд открыт по `http` на обычном домене — это не безопасный контекст, и `navigator.mediaDevices` там нет. В проверке на `http://shop.test` API отсутствовал, а на `localhost` работал.

```js
if (!window.isSecureContext || !navigator.mediaDevices?.getUserMedia) {
  showError('Видеосвязь доступна только по HTTPS');
  return;
}
```

Исправление — HTTPS на стенде. Проверку оставляют, чтобы пользователь увидел понятное сообщение, а не падение.
::

::practice{title="Индикатор камеры горит после звонка"}
После завершения консультации окно звонка закрывается, но индикатор камеры на ноутбуке продолжает гореть до перезагрузки страницы.

#solution
Компонент убрал `video`, но не остановил дорожки потока — камера продолжает работать. В проверке после `track.stop()` дорожка перешла в `ended`.

```jsx
useEffect(() => {
  let stream;
  navigator.mediaDevices.getUserMedia({ video: true, audio: true }).then((s) => {
    stream = s;
    videoRef.current.srcObject = s;
  });
  return () => stream?.getTracks().forEach((track) => track.stop());
}, []);
```

Если поток передан в `RTCPeerConnection`, при завершении звонка закрывают и соединение — `pc.close()`.
::
