# Web Workers и параллельность

Как выполнять тяжёлую работу, не замораживая интерфейс: главный поток и его блокировка, Web Worker и обмен сообщениями, виды воркеров, копирование и передача данных, общая память с `Atomics`, отрисовка в воркере через OffscreenCanvas и удобная обёртка Comlink. Спрашивают, зачем воркеры, если JavaScript однопоточный, что воркер не умеет и как передать большие данные без копирования. Глубже — почему класс приходит в воркер простым объектом, почему `SharedArrayBuffer` бывает `undefined` и почему два потока, увеличивающие один счётчик, теряют половину увеличений.

::tldr
- **Главный поток один на всё:** твой код, стили, раскладка, отрисовка и ввод. Задача на 300 мс — это 300 мс без кадров и ответов на клики.
- **Воркер — отдельный поток со своим глобальным объектом:** без DOM и `window`, но с `fetch`, таймерами, IndexedDB и WebAssembly. Общение — сообщениями.
- **Сообщения копируются алгоритмом structured clone:** `Date`, `Map`, массивы — да, функции — `DataCloneError`, а экземпляр класса приходит простым объектом. Большой `ArrayBuffer` передают владением — без копии, у отправителя он становится пустым.
- **Общая память — `SharedArrayBuffer`, только при изоляции страницы** заголовками COOP и COEP. Изменения из нескольких потоков — только через `Atomics`.
- **Конкурентный рендеринг React — не многопоточность:** это планирование работы в том же главном потоке.
::

---

## Проблема главного потока

Сквозной пример — магазин: импорт прайс-листа на 200 000 строк, расчёт итогов корзины, предпросмотр обработанных фотографий товаров.

В браузере одна вкладка — один главный поток: он выполняет JavaScript, считает стили и раскладку, рисует и обрабатывает ввод. Пока выполняется долгая синхронная задача, ничего из остального не происходит (подробно — в [Event Loop](/content/javascript/event-loop)).

```js
const rows = parseCsv(priceList);   // 300 мс синхронной работы
```

В проверке таймер с интервалом 10 мс за 300 мс занятого главного потока не сработал **ни разу**. Для пользователя это замерший интерфейс: ни прокрутки, ни кликов, ни анимации. Задачи дольше 50 мс браузер считает долгими, и они напрямую ухудшают INP (подробно — в [Памяти и производительности](/content/javascript/memory-and-performance)).

Есть два выхода: **дробить** работу на части и уступать поток между ними — `scheduler.yield`, `setTimeout`, — или **вынести** её в другой поток. Если работа чисто вычислительная — второй вариант.

## Web Worker

Воркер — скрипт, который выполняется в отдельном потоке. Память у потоков раздельная, общение — сообщениями:

```js
// main.js
const worker = new Worker(new URL('./parse.worker.js', import.meta.url), { type: 'module' });
worker.postMessage(priceList);
worker.onmessage = (e) => renderTable(e.data);

// parse.worker.js
onmessage = (e) => {
  const rows = parseCsv(e.data);
  postMessage(rows);
};
```

В проверке та же работа на 300 мс в воркере не помешала главному потоку: таймер с интервалом 10 мс успел сработать больше десяти раз.

Запись `new URL('./…', import.meta.url)` понимают Vite, webpack и другие сборщики: они соберут воркер отдельным файлом и подставят правильный адрес. `{ type: 'module' }` позволяет использовать `import` внутри воркера.

### Что есть в воркере

В проверке внутри воркера:

| Что | Есть |
| --- | --- |
| `document`, `window` | нет — `undefined` |
| `fetch`, таймеры | да |
| `indexedDB` | да |
| `OffscreenCanvas` | да |
| глобальный объект | `self`, `DedicatedWorkerGlobalScope` |

Отсюда разделение труда: воркер считает и обрабатывает, главный поток рисует результат. Изменить DOM из воркера нельзя — только отправить данные, по которым главный поток его обновит.

---

## Виды воркеров

| Тип | Область | Зачем |
| --- | --- | --- |
| выделенный (`Worker`) | одна страница | вычисления — основной случай |
| общий (`SharedWorker`) | все вкладки одного источника | общее соединение или состояние между вкладками |
| Service Worker | между страницей и сетью | офлайн, кеш, push-уведомления |

Service Worker — не для вычислений: он перехватывает запросы страницы и живёт отдельно от неё (подробно — в [PWA](/content/web/pwa)). Для параллельной работы — выделенный воркер. В Node.js похожую роль играют `worker_threads`.

## Передача данных

### Копирование

По умолчанию `postMessage` копирует данные алгоритмом **structured clone**. В проверке:

- массив, изменённый в главном потоке сразу после отправки, пришёл в воркер в исходном виде — это копия;
- `Date` и `Map` пришли как `Date` и `Map`;
- экземпляр класса `Product` пришёл простым объектом: поля скопированы, прототип и методы — нет;
- объект с функцией внутри вызвал `DataCloneError`.

Копирование большого объекта стоит времени и памяти в обоих потоках. Для сотен мегабайт это заметно.

### Передача владения

`ArrayBuffer`, `MessagePort`, `ImageBitmap`, `OffscreenCanvas` и потоки можно **передать**, а не скопировать:

```js
const buffer = await file.arrayBuffer();
worker.postMessage(buffer, [buffer]);
```

В проверке буфер на 64 МБ пришёл в воркер целиком, а в главном потоке стал пустым: `byteLength === 0`, `detached === true`. Данные «переехали» без копирования, и пользоваться буфером в отправителе больше нельзя.

## Общая память

`SharedArrayBuffer` — память, которую видят несколько потоков одновременно, без копирования и передачи.

### Нужна изоляция

После атак Spectre браузеры дают общую память только **изолированным** страницам. В проверке без заголовков `crossOriginIsolated` был `false`, а `typeof SharedArrayBuffer` — `'undefined'`. С заголовками:

```text
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

— `true` и `'function'`. Цена изоляции: все ресурсы с других источников — картинки, скрипты, фреймы — должны явно разрешать встраивание (CORS или `Cross-Origin-Resource-Policy`), иначе не загрузятся (подробно — в [CORS и same-origin](/content/security-perfomance/cors-and-same-origin)).

### Atomics

Общая память возвращает классическую проблему потоков — гонки. В проверке два воркера по миллиону раз увеличивали один счётчик:

```js
const counter = new Int32Array(sharedBuffer);

counter[0]++;                 // прочитать, прибавить, записать — не атомарно
Atomics.add(counter, 0, 1);   // одна неделимая операция
```

С `Atomics.add` получилось ровно 2 000 000. С обычным `counter[0]++` — около миллиона: оба потока читали одно и то же значение и записывали одинаковый результат, и половина увеличений потерялась. `Atomics.wait` и `Atomics.notify` дают ожидание и пробуждение потоков. Общая память нужна редко — в основном для WebAssembly с потоками и тяжёлой обработки данных; в большинстве задач хватает сообщений.

## OffscreenCanvas

Отрисовку тоже можно вынести в воркер — для тяжёлых визуализаций, графиков на тысячи точек, игр:

```js
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]);

// в воркере
onmessage = (e) => {
  const ctx = e.data.canvas.getContext('2d');
  ctx.fillRect(0, 0, 10, 10);
};
```

В проверке воркер получил `OffscreenCanvasRenderingContext2D` и нарисовал прямоугольник, а главный поток после передачи не смог взять контекст того же canvas — `InvalidStateError`: управлять им теперь может только воркер. Подробно о Canvas и WebGL — в [Графике](/content/additional-topics/graphics-canvas-webgl).

---

## Comlink

Голые `postMessage` и `onmessage` неудобны: нужно придумывать формат сообщений, сопоставлять запросы с ответами, обрабатывать ошибки. **Comlink** от Google Chrome Labs превращает воркер в объект с асинхронными методами:

```js
// worker
import * as Comlink from 'comlink';
Comlink.expose({ total: (items) => items.reduce((s, i) => s + i.price * i.qty, 0) });

// main
const api = Comlink.wrap(new Worker(new URL('./cart.worker.js', import.meta.url), { type: 'module' }));
await api.total(items);   // 2700
```

В проверке вызов вернул `2700`, как обычная асинхронная функция. Внутри — те же сообщения и structured clone, поэтому ограничения на передаваемые данные остаются.

## Когда нужен воркер

| Подходит | Не подходит |
| --- | --- |
| разбор больших JSON и CSV, импорт файлов | обновление DOM |
| обработка изображений, видео, аудио | мелкие быстрые вычисления |
| сжатие, шифрование, хеширование | работа, которая упирается в сеть, а не в процессор |
| поиск и фильтрация больших наборов данных на клиенте | частый обмен мелкими сообщениями |
| WebAssembly с тяжёлыми расчётами | |

У воркера есть цена: создание потока, загрузка скрипта, копирование данных туда и обратно. Если работа занимает 5 мс, а сообщения — 20, воркер только замедлит. Сначала стоит измерить (подробно — в [Производительности во время работы](/content/security-perfomance/runtime-performance)).

### React и параллельность

Конкурентный рендеринг React — `useTransition`, `useDeferredValue` — это не многопоточность. React дробит рендер на части и уступает главный поток более срочной работе, но всё происходит в том же потоке (подробно — в [Производительности React](/content/reactjs/performance)). Если тормозит вычисление, а не рендер, его по-прежнему выносят в воркер.

---

## Красные флаги в ответе

- **«JavaScript однопоточный, значит, параллельности в браузере нет».** Воркеры — настоящие потоки, однопоточен каждый контекст.
- **«Из воркера обновлю DOM».** DOM в воркере нет, только сообщения в главный поток.
- **«Передам экземпляр класса и вызову метод».** Structured clone копирует поля, а прототип и методы теряются.
- **«Большой буфер просто отправлю».** Он скопируется; передачей владения — без копии.
- **«`SharedArrayBuffer` есть всегда».** Только на странице с COOP и COEP.
- **«`useTransition` выносит работу в другой поток».** Это планирование в том же главном потоке.

## Как спрашивают на собеседовании

::question
Зачем нужны Web Workers, если JavaScript однопоточный?

#answer
Именно поэтому: у страницы один главный поток для кода, раскладки, отрисовки и ввода, и долгая задача замораживает интерфейс. Воркер выполняет работу в отдельном потоке и общается с главным сообщениями.

#more
Альтернатива — дробить работу и уступать поток через `scheduler.yield` или `setTimeout`. Воркер лучше, когда работа чисто вычислительная и длится десятки миллисекунд и больше.
::

::question
Что воркер не может делать?

#answer
У него нет доступа к DOM, `window` и `document`. Зато есть `fetch`, таймеры, IndexedDB, `OffscreenCanvas` и WebAssembly. Поэтому воркер считает, а главный поток рисует.

#more
Глобальный объект воркера — `self` типа `DedicatedWorkerGlobalScope`. Модульный воркер, `{ type: 'module' }`, поддерживает `import`.
::

::question
Как данные попадают в воркер?

#answer
Копируются алгоритмом structured clone: примитивы, массивы, объекты, `Date`, `Map`, `Set`, `ArrayBuffer`. Функции не копируются — `DataCloneError`, — а экземпляр класса приходит простым объектом без методов.

#more
Большие `ArrayBuffer`, `ImageBitmap` и `OffscreenCanvas` передают владением: `postMessage(buffer, [buffer])`. Копии нет, но у отправителя буфер становится пустым.
::

::question
Что такое `SharedArrayBuffer` и почему он бывает недоступен?

#answer
Память, которую видят несколько потоков одновременно. После атак Spectre браузеры дают её только изолированным страницам — с заголовками `Cross-Origin-Opener-Policy: same-origin` и `Cross-Origin-Embedder-Policy: require-corp`.

#more
С общей памятью появляются гонки: обычное `counter[0]++` из двух потоков теряет увеличения, поэтому используют `Atomics`. Изоляция требует, чтобы ресурсы с других источников явно разрешали встраивание.
::

::question
Чем Service Worker отличается от Web Worker?

#answer
Web Worker — для вычислений в фоне одной страницы. Service Worker — посредник между страницами и сетью: перехватывает запросы, кеширует, работает офлайн и принимает push-уведомления, живёт отдельно от вкладок.

#more
Есть ещё `SharedWorker` — один поток на все вкладки одного источника, для общего соединения или состояния.
::

::question
Конкурентный рендеринг React — это многопоточность?

#answer
Нет. React дробит рендер на части и уступает главный поток более срочной работе, но всё выполняется в том же потоке.

#more
Если тормозит не рендер, а вычисление — фильтрация, разбор данных, — его выносят в воркер, а React рендерит готовый результат.
::

## Практика

::practice{title="Импорт прайс-листа замораживает страницу"}
Админка магазина разбирает загруженный CSV на 200 000 строк в обработчике `change` у поля файла. Пока идёт разбор, страница не реагирует несколько секунд.

#solution
Разбор занимает главный поток. В проверке за 300 мс такой работы таймер не сработал ни разу, а в воркере та же работа не мешала главному потоку. Переносим разбор и передаём файл владением:

```js
// main.js
const worker = new Worker(new URL('./price.worker.js', import.meta.url), { type: 'module' });

input.addEventListener('change', async () => {
  const buffer = await input.files[0].arrayBuffer();
  worker.postMessage(buffer, [buffer]);   // без копии
  showProgress();
});
worker.onmessage = (e) => renderTable(e.data);

// price.worker.js
onmessage = (e) => {
  const text = new TextDecoder().decode(e.data);
  postMessage(parseCsv(text));
};
```

Если результат огромный, его тоже стоит отдать частями или сразу посчитать в воркере то, что нужно показать, — иначе дорогим станет копирование обратно и отрисовка таблицы (подробно — в [Таблицах и гридах](/content/ecosystem-libs/tables-and-grids)).
::

::practice{title="Счётчик в общей памяти считает неправильно"}
Два воркера обрабатывают половины массива заказов и увеличивают общий счётчик найденных в `SharedArrayBuffer`. Итог каждый раз разный и меньше ожидаемого.

#solution
`counter[0]++` — это чтение, сложение и запись. Если оба потока читают одно значение, оба запишут одинаковый результат, и одно увеличение пропадёт. В проверке два потока по миллиону увеличений дали около миллиона вместо двух.

```js
const counter = new Int32Array(sharedBuffer);
Atomics.add(counter, 0, 1);   // неделимая операция
```

С `Atomics.add` в проверке получилось ровно 2 000 000. Ещё проще — не делить счётчик: каждый воркер считает своё и отправляет результат сообщением, а главный поток складывает.
::
