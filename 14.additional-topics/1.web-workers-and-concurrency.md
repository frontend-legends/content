# Web Workers и concurrency

JavaScript **однопоточный**: весь твой код, рендеринг и обработка событий делят один главный поток. Тяжёлое вычисление **блокирует** его - интерфейс замирает. **Web Workers** дают настоящую многопоточность в браузере: вынести работу в фоновый поток, не подвешивая UI.

---

## Проблема главного потока

```js
// блокирует UI на секунды: ни рендера, ни кликов, ни скролла
const result = hugeArray.map(expensiveTransform);
```

Пока выполняется тяжёлый цикл, главный поток занят - браузер не может ни перерисовать страницу, ни ответить на ввод. Пользователь видит «зависание». Связано с [event loop](/content/javascript): долгая синхронная задача не уступает циклу событий.

---

## Web Worker

Worker - это скрипт, выполняющийся в **отдельном потоке**. Главный поток и worker общаются **сообщениями** (`postMessage`), не разделяя память напрямую.

```js
// main.js
const worker = new Worker('worker.js');
worker.postMessage(hugeArray);            // отправить данные в worker
worker.onmessage = (e) => render(e.data); // получить результат

// worker.js
onmessage = (e) => {
  const result = e.data.map(expensiveTransform); // тяжёлая работа в фоне
  postMessage(result);
};
```

Главный поток остаётся свободным - UI отзывчив, пока worker считает.

<b class="text-on-semi-light">Что worker НЕ может</b> - <span class="text-gray">У worker **нет доступа к DOM**, `window`, `document`. Он живёт в изолированном контексте. Зато умеет `fetch`, таймеры, IndexedDB, тяжёлые вычисления, WASM. Поэтому worker считает/обрабатывает данные, а главный поток рисует результат.</span>

---

## Виды воркеров

| Тип | Область | Зачем |
|-----|---------|-------|
| **Dedicated Worker** | одна страница | вынести вычисления (основной кейс) |
| **Shared Worker** | несколько вкладок одного origin | общий поток между вкладками |
| **Service Worker** | проксирует сеть | офлайн, кеш, push ([PWA](/content/web)) |

> Service Worker - особый: он не для вычислений, а перехватывает сетевые запросы (основа PWA). Web Worker - именно для concurrency.

## Передача данных

Сообщения по умолчанию **копируются** алгоритмом structured clone - для больших данных это дорого.

### Transferable objects

Можно **передать владение** буфером без копирования (zero-copy) - данные «переезжают» в worker:

```js
const buffer = new ArrayBuffer(100_000_000);
worker.postMessage(buffer, [buffer]); // передаём владение, не копируем
// после этого buffer недоступен в главном потоке
```

### SharedArrayBuffer

**Разделяемая память** между потоками + `Atomics` для синхронизации - настоящая параллельность с общими данными. Мощно, но требует специальных HTTP-заголовков (COOP/COEP) из соображений безопасности (после Spectre).

---

## OffscreenCanvas

Позволяет **рендерить графику в worker**, не трогая главный поток - тяжёлая отрисовка (визуализации, игры) уходит в фон.

```js
const offscreen = canvas.transferControlToOffscreen();
worker.postMessage({ canvas: offscreen }, [offscreen]); // рисуем в worker
```

---

## Comlink

Голый `postMessage` неудобен (ручная маршрутизация сообщений). **Comlink** (Google) оборачивает worker в **RPC**: вызываешь методы worker как обычные async-функции.

```js
import * as Comlink from 'comlink';
const api = Comlink.wrap(new Worker('worker.js'));
const result = await api.process(data); // как будто обычный вызов
```

---

## Когда использовать

- Тяжёлые вычисления: парсинг больших JSON/CSV, обработка изображений, крипто, сжатие.
- Постоянная фоновая работа, которая иначе дёргает UI.
- WASM-модули с интенсивными расчётами.

> Не выноси в worker всё подряд - есть стоимость создания и обмена сообщениями. Worker оправдан, когда работа **реально** блокирует главный поток на десятки миллисекунд и больше.

---

## Concurrency в React - это другое

Важно не путать: «конкурентный рендеринг» React (`useTransition`, см. [продвинутые хуки](/content/reactjs/advanced-hooks)) - это **кооперативная многозадачность в одном потоке** (React прерывает и приоритизирует работу), а **не** многопоточность. Web Workers - настоящие потоки ОС. React не уносит рендер в worker; он лишь умнее планирует его в главном потоке.

## Вопросы на собеседовании

<b class="text-on-semi-light">Зачем нужны Web Workers, если JS однопоточный?</b>
<span class="text-gray">Именно поэтому: тяжёлая работа блокирует главный поток и подвешивает UI. Worker выполняет её в отдельном потоке, общаясь сообщениями, - интерфейс остаётся отзывчивым.</span>

<b class="text-on-semi-light">Что worker не может делать?</b>
<span class="text-gray">Нет доступа к DOM, window, document - изолированный контекст. Может fetch, таймеры, IndexedDB, вычисления, WASM. Поэтому он считает, а главный поток рисует.</span>

<b class="text-on-semi-light">Как передать большие данные в worker без копирования?</b>
<span class="text-gray">Transferable objects: `postMessage(buffer, [buffer])` передаёт владение ArrayBuffer без копии (zero-copy), после чего он недоступен в отправителе. Для общей памяти - SharedArrayBuffer + Atomics.</span>

<b class="text-on-semi-light">Чем Service Worker отличается от Web Worker?</b>
<span class="text-gray">Web Worker - для вычислений в фоне. Service Worker - сетевой прокси для офлайна, кеша и push (основа PWA), не для concurrency.</span>

<b class="text-on-semi-light">Конкурентный рендеринг React - это многопоточность?</b>
<span class="text-gray">Нет. Это кооперативное планирование в одном потоке (прерывание и приоритеты), а не настоящие потоки. Web Workers - реальная многопоточность.</span>
